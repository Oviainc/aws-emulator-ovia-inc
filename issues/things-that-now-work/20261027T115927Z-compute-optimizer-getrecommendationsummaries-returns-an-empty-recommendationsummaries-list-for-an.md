# GetRecommendationSummaries returns an empty recommendationSummaries list for an opted-in account instead of one summary per tracked resource type

> _Note: this issue was identified against the code base at commit `2463e7b3a1286c325e58f557528f9acecf88024e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRecommendationSummaries

## Description
One net-new root cause (Cause 1 of 1).

Cause 1 of 1: GetRecommendationSummaries builds its response from the findings-catalog rows the store happens to hold AND gates those rows behind a post-enrollment analysis delay, so an opted-in account whose analysis has not been seeded or is not yet 'due' is answered HTTP 200 with `recommendationSummaries: []` rather than a summary per recommendation resource type. Failing check: compute-optimizer.get-recommendation-summaries-matches-caller-account.

AWS: GetRecommendationSummaries "[r]eturns the optimization findings for an account. It returns the number of: Amazon EC2 instances in an account that are Underprovisioned, Overprovisioned, or Optimized. EC2 Auto Scaling groups ... Amazon EBS volumes ... Lambda functions ... Amazon ECS services ... Commercial software licenses ... Amazon Aurora and Amazon RDS databases ..." (Smithy: GetRecommendationSummaries doc). The output member is `recommendationSummaries` (RecommendationSummaries), each entry a `RecommendationSummary` whose `recommendationResourceType` targets the `RecommendationSourceType` enum (Smithy values: Ec2Instance, AutoScalingGroup, EbsVolume, LambdaFunction, EcsService, License, RdsDBInstance, RdsDBInstanceStorage, AuroraDBClusterStorage, NatGateway, DynamoDBTable, ElastiCacheCluster, MemoryDBCluster, DocumentDBCluster, WorkSpaces, SageMakerEndpoint), whose `accountId` is "[t]he Amazon Web Services account ID of the recommendation summary", and whose `summaries` are "objects that describe a recommendation summary" — a count per finding, where `Summary$value` is a required-with-default count that is legitimately 0. The summary is a per-resource-type count roll-up, so the set of entries is the vocabulary of resource types the service tracks for the enrolled account, not the subset that currently has non-zero findings. Recorded behavior (the check, which replays real AWS): an opted-in account receives at least one summary entry, "a summary entry per tracked resource type even with zero analyzed resources"; each entry's `accountId` equals the caller's own account and each `recommendationResourceType` is a documented RecommendationSourceType value. The model documents no error and no empty-result state for an enrolled account; OptInRequiredException (403) is the only modeled outcome for a non-enrolled one, which is not this case.

Emulator: the request succeeds (HTTP 200) and the body is `{"recommendationSummaries": []}` — observed verbatim in the replay as `resp={'recommendationSummaries': [], 'ResponseMetadata': {'HTTPStatusCode': 200, ...}}` — after UpdateEnrollmentStatus(status=Active) and after GetEnrollmentStatus reported `status=Active`. Two mechanisms in the handler produce that emptiness and both must be addressed for the list to be non-empty: (a) the response set is enumerated from the rows present — the loop iterates `guard.analysed_resources_by_type(&account_id)` and pushes one summary only for a resource type that has rows, and additionally `continue`s over any type for which `crate::state::findings_reported_for(resource_type)` is empty — so a tracked resource type with zero analyzed resources yields NO entry at all instead of an entry with zero counts; (b) every row is further hidden by the analysis-due gate (`enrollment.is_opted_in() && enrollment.analysis_due()`), so a caller that opts in and reads immediately — the documented and replayed happy path — sees the catalog as empty and gets the empty list.

Why: a client gets wrong. GetRecommendationSummaries is the entry point for reading an account's optimization posture: callers iterate `recommendationSummaries` to pick which resource types to drill into, to render a dashboard row per resource type, and to assert the zero-finding baseline for a newly enrolled account. Against the emulator that loop body never executes, so such a client cannot distinguish "enrolled, nothing to optimize yet" (AWS: entries with `Summary$value` 0) from "no data surface at all" (emulator: no entries), and any code that indexes the first summary, or that derives the tracked resource-type set from the response, fails or silently reports nothing. It also masks the per-resource-type accountId check the recording makes, since no entry is ever examined for cross-account leakage.

Fix: the operation's handler and its state view — `services/service-com-amazonaws-computeoptimizer-computeoptimizerservice/src/ops/get_recommendation_summaries.rs` (`handle`, and `summarise`/`finding_summaries` which already compute zero counts correctly for a finding no resource carries) must enumerate the summary set from the tracked `RecommendationSourceType` vocabulary for the enrolled account rather than from the rows present, emitting a zero-count summary for a type with no analyzed resources; and the visibility gate it reads through, `visible_analysed_resources`/`analysed_resources_by_type` in `src/state.rs`, must not make an opted-in account's summary surface vanish entirely while the post-enrollment analysis delay is in force. This is NOT the already-open issue 20261024T022952Z-compute-optimizer-getrecommendationsummaries-wrong-behavior.md, which concerns the content of an entry that IS emitted (`idleSummaries`, `idleSavingsOpportunity`, `aggregatedSavingsOpportunity`); this cause is that no entry is emitted at all.

Traces: compute-optimizer.get-recommendation-summaries-matches-caller-account (assertion `len(summaries) > 0` on the GetRecommendationSummaries response, after _ensure_opted_in drives enrollment to Active).

## Evidence
Check: compute-optimizer.get-recommendation-summaries-matches-caller-account (verdict: mismatch; group data-plane; tags axis:happy-path, concern:representation).

Expected (real AWS, per the recording): `recommendationSummaries` is a non-empty list for an opted-in account — "real AWS returns a summary entry per tracked resource type even with zero analyzed resources"; every entry's `accountId` equals the caller's STS account id, and every `recommendationResourceType` is one of the documented RecommendationSourceType values (Ec2Instance, AutoScalingGroup, EbsVolume, LambdaFunction, EcsService, License, RdsDBInstance, RdsDBInstanceStorage, AuroraDBClusterStorage, NatGateway, DynamoDBTable, ElastiCacheCluster, MemoryDBCluster, DocumentDBCluster, WorkSpaces, SageMakerEndpoint).

Actual (emulator): HTTP 200, content-type application/x-amz-json-1.0, body length 30, payload `{'recommendationSummaries': []}` — an empty list. Assertion raised:

  AssertionError: expected at least one recommendation summary for an opted-in account: real AWS returns a summary entry per tracked resource type even with zero analyzed resources, got an empty list from resp={'recommendationSummaries': [], 'ResponseMetadata': {'HTTPStatusCode': 200, ...}}

No status/error-code divergence: the status (200) matches AWS and no error is returned by either side. The divergence is purely the response shape's content — zero entries where AWS returns one per tracked resource type. The per-run values in the recorded response (date header, content-length, request metadata) are not part of the requirement.

Model evidence (smithy_query, services/service-com-amazonaws-computeoptimizer-computeoptimizerservice/smithy-model/com-amazonaws-computeoptimizer-computeoptimizerservice.json): GetRecommendationSummaries output = {nextToken: NextToken, recommendationSummaries: RecommendationSummaries}; errors = AccessDeniedException(403), InternalServerException(500), InvalidParameterValueException(400), MissingAuthenticationToken(403), OptInRequiredException(403), ServiceUnavailableException(503), ThrottlingException(429); paginated(items=recommendationSummaries, pageSize=maxResults). RecommendationSummary.recommendationResourceType -> RecommendationSourceType enum (16 values listed above); RecommendationSummary.accountId -> AccountId "The Amazon Web Services account ID of the recommendation summary"; RecommendationSummary.summaries -> Summaries "objects that describe a recommendation summary".

Code evidence: src/ops/get_recommendation_summaries.rs — handler loop `for (resource_type, resources) in guard.analysed_resources_by_type(&account_id)` with `if crate::state::findings_reported_for(resource_type).is_empty() { continue; }`, pushing a summary only per resource type that has catalog rows; `recommendation_summaries` is initialized `Vec::new()` and returned as-is, so a store with no visible rows yields `Some(vec![])`. src/state.rs — `visible_analysed_resources()` returns rows only when `self.enrollment.is_opted_in() && self.enrollment.analysis_due()`, and `analysis_due()` requires ANALYSIS_DELAY to have elapsed since the enrollment record was last written, so a caller that opts in and reads immediately observes zero rows and therefore zero summaries.

## Steps to Reproduce
1. Boot the compute-optimizer emulator.
2. Call GetEnrollmentStatus; if status is not "Active", call UpdateEnrollmentStatus(status="Active") and poll GetEnrollmentStatus until it reports "Active".
3. Call GetCallerIdentity on sts to note the caller's account id.
4. Immediately call GetRecommendationSummaries with no accountIds, no nextToken and no maxResults.
5. Observe HTTP 200 with `recommendationSummaries: []`. Real AWS returns at least one entry — one per tracked RecommendationSourceType for the caller's own account, with zero-valued Summary counts when no resources have been analyzed — so a client cannot read or iterate any summary, and the per-entry accountId / recommendationResourceType assertions never get a value to check.
