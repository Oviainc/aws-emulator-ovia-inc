# opensearch package-association lifecycle: DissociatePackages has no in-use guard, CreateIndex never resolves an analyzer's package reference, the in-flight serialization window is unobservable, and the upgrade-progress flow never converges (4 causes)

> _Note: this issue was identified against the code base at commit `92f4c5bcd7cf6181c0562fc9c30d986f00a088ec`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DissociatePackages

## Description
Four distinct root causes in the opensearch service. All four must be closed before this issue is resubmitted. None of the four grounding checks is marked ALREADY FILED or OWNED in the replay report. Related open issues are named per cause; note that two of them are stale with respect to the current checkout — 20261026T025630Z-opensearch-dissociatepackages-stub.md and cause 2 of 20261026T025630Z-opensearch-updatevpcendpoint-and-dissociatepackages-answer-501-notimplemented-so.md both describe DissociatePackages as a 501 scaffold stub, but services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/dissociate_packages.rs is now fully implemented. The causes below are about what that implementation DOES, not about it being absent, and none of them carries these four checks' replay keys.

Every one of the four checks ends with no response assertion at all ('Error: Check timed out after 60.0s'), so the per-cause 'Emulator' text states what the handler in the checkout does (which is what makes each check's awaited condition unreachable) and labels as 'Hypothesis' anything neither the model nor the replay output states.

=== Cause 1 of 4: DissociatePackages removes an association for a package a live index still references, instead of accepting the call and then failing the transition with DISSOCIATION_FAILED / 'Package is in use.' ===
AWS: DissociatePackages (Smithy: POST /2021-01-01/packages/dissociateMultiple; required PackageList (PackageIDList) and DomainName; output DomainPackageDetailsList) is accepted SYNCHRONOUSLY with 200 and reports the association in DISSOCIATING. The removal is asynchronous, and when the domain still holds an index whose analysis settings resolve a file by that package's reference path, the asynchronous step FAILS rather than detaching the package: ListPackagesForDomain (Smithy: GET /2021-01-01/domain/{DomainName}/packages) then reports that DomainPackageDetails with DomainPackageStatus=DISSOCIATION_FAILED (Smithy: DomainPackageStatus is one of ASSOCIATING | ASSOCIATION_FAILED | ACTIVE | DISSOCIATING | DISSOCIATION_FAILED) and with DomainPackageDetails.ErrorDetails populated — ErrorDetails is modeled as 'Additional information if the package is in an error state. Null otherwise.' and carries ErrorType and ErrorMessage. Recorded behavior (us-west-2, as the check's own audit note records): ErrorDetails.ErrorMessage is the fixed sentence 'Operation not allowed. Package is in use.' — fixed text in full, with no variable part taken from the request. Throughout, the association stays present and stays usable (an independent UpdateIndex on the dependent index still answers Status=UPDATED). Removing the one dependency — deleting that index — lifts the block: the IDENTICAL DissociatePackages call then dissociates the package and ListPackagesForDomain stops reporting it.
Emulator: there is no in-use guard anywhere on the dissociate path. crate::state::plan_package_dissociation judges exactly three things — the domain exists, no association on that domain is in_flight (ConflictException), and the named association exists (ResourceNotFoundException) — and never consults the domain's indexes. The handler then calls remove_package_association immediately, so the association is taken off the domain and reported as removed. No DISSOCIATION_FAILED status and no ErrorDetails are ever produced for this condition, so a client polling for either waits forever; the check is killed at the suite's 60 s budget having never observed it.
Why: a client can silently detach a dictionary/plug-in package out from under a running index whose analyzer resolves a file by its reference path. The guard AWS uses to make that state unreachable is absent, so an emulated domain reaches a configuration real OpenSearch Service refuses to enter, and automation that treats DISSOCIATION_FAILED + 'in use' as 'delete the dependent index first, then retry' never sees that signal and instead proceeds on a domain whose analyzers now point at nothing.
Fix: the shared dissociation decision and the association state it writes — crate::state::plan_package_dissociation / remove_package_association in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs, reached from src/ops/dissociate_packages.rs and src/ops/dissociate_package.rs. The association needs a failed-transition outcome (status DISSOCIATION_FAILED plus ErrorDetails) owed by the same clock that already owes it ACTIVE/removal, taken when any index of the domain references the package's reference path, and the association must survive it.
Traces: opensearch.update-index-dependency-failure-on-unavailable-package.

=== Cause 2 of 4: CreateIndex stores the index schema verbatim and never resolves an analyzer's package reference, so an index depending on a dissociated package is created instead of refused ===
AWS: CreateIndex (Smithy: POST /2021-01-01/opensearch/domain/{DomainName}/index; required DomainName, IndexName and IndexSchema (a document); output Status (IndexStatus)) is served by the cluster, so the analysis settings in IndexSchema must RESOLVE on the cluster. When a filter names a path under a custom package's mount point (synonyms_path = analyzers/<PackageID>) and that package is not associated with the domain, the file is not there to read and the create is refused with ValidationException, HTTP 400 (a modeled error of this operation alongside AccessDeniedException 403, DependencyFailureException 424, ResourceAlreadyExistsException 409, ResourceNotFoundException 409). Recorded message: 'IOException while reading synonyms_path_path: file not readable' — fixed text; it carries no value of the request. No index is created: a following GetIndex (Smithy: GET /2021-01-01/opensearch/domain/{DomainName}/index/{IndexName}) answers ResourceNotFoundException with message 'Resource index <IndexName> does not exist', whose only variable part is the IndexName taken from the request. Re-associating the SAME package and retrying the IDENTICAL CreateIndex then succeeds with Status=CREATED, and GetIndex reports a schema still referencing that package id.
Emulator: src/ops/create_index.rs validates only the index NAME's pattern, that IndexSchema is a JSON object, that the domain exists, that the name is not already taken, and a per-domain index quota; it then inserts the schema 'Stored VERBATIM' and answers Status=CREATED. The analysis section is never inspected and no package reference in it is ever resolved against the domain's associations, so the create that AWS refuses is accepted (200 CREATED) and the negative half of the check can never be satisfied; the check is killed at the 60 s budget.
Why: the association state stops being the thing that gates a dependent index. A client gets a 200-created index whose analyzer resolves nothing, so the failure surfaces later as wrong analysis results rather than at the create, and a client that relies on the 400 refusal to detect a missing/dissociated package never gets it. Together with cause 1 this makes package dependency unenforced in both directions.
Fix: the CreateIndex handler's validation (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/create_index.rs), resolving any package reference path the schema's analysis settings name against the domain's package_associations in src/state.rs before the index is stored, and refusing with the modeled ValidationException when it does not resolve. The open issue 20261025T111158Z-opensearch-updateindex-answers-501-notimplemented-instead-of-403.md and 20261025T163435Z-opensearch-updateindex-performs-no-iam-authorization-check-a.md concern UpdateIndex authorization, not schema resolution, and neither carries this check's replay key.
Traces: opensearch.package-dissociation-blocks-dependent-index-creation-rejected.

=== Cause 3 of 4: the in-flight window for a package association is too short to serialize concurrent writers, so neither of two racing calls is refused with ConflictException ===
AWS: AssociatePackages and DissociatePackages both model ConflictException, HTTP 409 — documented as 'An error occurred because the client attempts to remove a resource that is currently in use.' A domain runs one change to its package associations at a time, so while a pair is still mid-transition (DomainPackageStatus=ASSOCIATING, not yet ACTIVE) a second AssociatePackages for that pair and a DissociatePackages for it are BOTH refused 409 ConflictException rather than one overtaking the other; the transition then settles at exactly ONE ACTIVE association record for that package on that domain (never duplicated, never half-applied), and a solo dissociate afterwards both succeeds and actually removes it. AWS publishes no fixed text for this refusal, so the requirement is the 409 status and the ConflictException code; the recordings assert only the code.
Emulator: the rule itself exists — both crate::state::plan_package_association and plan_package_dissociation refuse with AssociationRefusal::Conflict(concurrent_package_operation()) when any association of the domain is in_flight — but the window in which it holds is crate::state::PROVISIONING = Duration::from_millis(500), the span the associate records as owed. Two calls released together by a client-side barrier arrive after that span has already elapsed and after some read has settled the record, so the association reads ACTIVE/not in_flight, the redundant associate is treated as a re-association and the dissociate as an ordinary removal, and NEITHER answers 409. Hypothesis: that is why the check never reaches its assertions and is killed at the 60 s budget — it chains a package-AVAILABLE wait, a domain-idle wait and an association-ACTIVE wait, each of which costs a full poll interval because every lifecycle value is reported in its transient form on the first read after the call that starts it (see cause 4). The refusal message the emulator would use is also its own invented constant ('Operation not allowed. A concurrent operation (associate/dissociate) is in progress for this domain.'), which no recording corroborates.
Why: a client that relies on the service serializing concurrent package writers — retry on ConflictException, then re-read — gets two successes instead, so the pair's final state depends on arrival order rather than on the service's own serialization, and a losing dissociate can undo an association the caller believes succeeded.
Fix: the shared association decision in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs (plan_package_association / plan_package_dissociation and the owed-status span that PackageAssociation::in_flight reads), so a pair that a call has just moved stays in flight long enough for a concurrently issued second writer to be refused with the modeled ConflictException. Related open issue 20261026T025630Z-opensearch-updatevpcendpoint-and-dissociatepackages-answer-501-notimplemented-so.md records the same race for the DIFFERENT check id opensearch.concurrent-associate-dissociate-packages-race-consistency and attributes it to a 501 stub that no longer exists; it does not carry this check's replay key.
Traces: opensearch.associate-dissociate-packages-concurrent-race-conflict.

=== Cause 4 of 4: the server-managed upgrade-progress flow never converges within a bounded client budget, because every state it polls is reported in its transient value on the first read ===
AWS: UpgradeDomain (Smithy: POST /2021-01-01/opensearch/upgradeDomain; required DomainName and TargetVersion; output UpgradeId, DomainName, TargetVersion, PerformCheckOnly, ChangeProgressDetails) starts a SERVICE-managed engine upgrade whose progress is observable purely through GetUpgradeStatus (Smithy: GET /2021-01-01/opensearch/upgradeDomain/{DomainName}/status; output UpgradeStep (PRE_UPGRADE_CHECK | SNAPSHOT | UPGRADE), StepStatus (IN_PROGRESS | SUCCEEDED | SUCCEEDED_WITH_ISSUES | FAILED) and UpgradeName) and GetUpgradeHistory (GET .../history), with no client-driven step call required to advance it. The run must reach a terminal UPGRADE step (SUCCEEDED or SUCCEEDED_WITH_ISSUES), GetUpgradeStatus must name the run in UpgradeName, the newest GetUpgradeHistory entry must carry the same terminal UpgradeStatus with a non-empty StepsList, and DescribeDomain must then report EngineVersion equal to the TargetVersion requested.
Emulator: the check produces no response assertion at all — it is killed at the suite's 60 s budget. The pieces it needs are all implemented and all settle on the same 500 ms span (src/state.rs PROVISIONING): CreateDomain's begin_change sets processing_until = now + PROVISIONING, Domain::settle clears Processing only once that instant has passed, and UpgradeRun::completes_at = now + PROVISIONING with current_step reporting PRE_UPGRADE_CHECK/IN_PROGRESS until then. Hypothesis: because every such value is still transient on the FIRST read after the call that starts it (the client round-trip is far under 500 ms), each bounded wait in this flow pays a full poll interval it would not pay if the first read already reported the settled value — the domain-idle wait needs two CONSECUTIVE idle observations 30 s apart and the GetUpgradeStatus wait polls at 20 s — so the flow needs more than the 60 s budget and is killed before its first assertion. The emulator's non-zero span is deliberate and AWS-faithful in direction (AWS is slower still), so a fixer should re-replay this check to confirm the convergence point rather than assume the span alone; what is required is that the whole server-managed progression be observable to its terminal state within a bounded client budget.
Why: a client that waits on the documented terminal states of a service-managed upgrade (domain idle, then UpgradeStep=UPGRADE terminal, then EngineVersion updated) gets neither a success nor an error — it simply hangs, which is the worst outcome: nothing to retry and nothing to handle. The server-managed upgrade capability is unusable end to end even though each individual operation answers.
Fix: the domain/upgrade settlement span and the states that read it — crate::state::PROVISIONING, Domain::begin_change / Domain::settle and UpgradeRun::completes_at / current_step in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs, as read by src/ops/upgrade_domain.rs, src/ops/get_upgrade_status.rs and src/ops/get_upgrade_history.rs. The open issue 20261026T043434Z-opensearch-a-repeat-upgradedomain-eligibility-check-appends-a.md concerns duplicate history entries for a repeated eligibility check, not convergence of a real upgrade, and does not carry this check's replay key.
Traces: opensearch.upgrade-domain-server-managed-progress-tracking.
