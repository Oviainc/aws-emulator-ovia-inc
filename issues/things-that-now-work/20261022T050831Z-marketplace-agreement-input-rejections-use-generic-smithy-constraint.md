# marketplace-agreement input rejections use generic Smithy constraint prose instead of the service's ValidationException message, and SearchAgreements accepts sortBy=StartTime scoped to PartyType=Acceptor

> _Note: this issue was identified against the code base at commit `7545d0b8b2e4fb4a41c801fcbb48b523234ffec8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchAgreements

## Description
Two distinct root causes in the marketplace-agreement emulator, both in how input validation is performed and reported. TWO causes; each must be closed before submitting.

Cause 1 of 2: every input-constraint rejection carries a generic framework constraint-violation message instead of the service's own member-named ValidationException message.
AWS: Smithy (services/service-com-amazonaws-marketplaceagreement-awsmpcommerceservice-v20200301/smithy-model): ValidationException is errorKind=client, httpError=400, members message -> ExceptionMessage (length 1..1024), reason -> ValidationExceptionReason, fields -> ValidationExceptionFieldList; ValidationException is a service-common error on every operation. The constraints the checks trip are all modeled: CreateAgreementRequest.intent -> Intent enum [NEW, AMEND, REPLACE]; DescribeAgreement.agreementId -> ResourceId pattern ^[A-Za-z0-9_/-]+$; ListBillingAdjustmentRequests.maxResults and SearchAgreements.maxResults -> MaxResults @range min 1 max 50; SearchAgreements.filters -> FilterList @length min 1 max 10; SendAgreementCancellationRequest.reasonCode -> AgreementCancellationRequestReasonCode enum; SendAgreementPaymentRequest.name -> PaymentRequestName @length min 5 max 64; UpdatePurchaseOrders.purchaseOrders -> PurchaseOrders @length min 1 max 86. Across eight independent recordings, AWS answers each with the SAME request-derived message rule: 400 / ValidationException whose top-level message is 'Provided <offending member, in the service's human form> is invalid.' -- 'Provided intent is invalid.', 'Provided agreement id is invalid.', 'Provided max results is invalid.', 'Provided filters is invalid.', 'Provided reason code is invalid.', 'Provided name is invalid.', 'Provided purchase orders is invalid.' The requirement is that rule (400 + ValidationException + a message naming the offending member in the service's phrasing, with reason drawn from ValidationExceptionReason, e.g. INVALID_INTENT / INVALID_AGREEMENT_ID / INVALID_MAX_RESULTS / INVALID_FILTERS / INVALID_REASON_CODE / INVALID_NAME / INVALID_PURCHASE_ORDERS), not any one recorded string.
Emulator: status 400 and code ValidationException are correct, but the message is the generic Smithy/framework constraint prose that leaks the model's internal constraint text and the raw request value, e.g. "1 validation error detected: Value 'SUPERSEDE_EVERYTHING' at 'intent' failed to satisfy constraint: Member must satisfy enum value set: [NEW, AMEND, REPLACE]", "1 validation error detected: Value '51' at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 50", "1 validation error detected: Value '11 items' at 'filters' failed to satisfy constraint: Member must have length less than or equal to 10", "1 validation error detected: Value 'hi' at 'name' failed to satisfy constraint: Member must have length greater than or equal to 5", "1 validation error detected: Value '87 items' at 'purchaseOrders' failed to satisfy constraint: Member must have length less than or equal to 86". The divergence is uniform, so it is one shared validation-error constructor, not per-operation.
Why: a client that matches on this service's documented rejection text (or renders it to an operator) sees the framework's internal phrasing instead; the same emission path is why ValidationException.reason/fields are not populated from the service's enum, so nothing downstream can classify WHICH member was rejected in the service's own vocabulary. The open issue 20261022T041017Z-marketplace-agreement-validationexception-envelope-omits-reason-and-fields-and-does.md records the structural half (missing reason/fields, wrong field path) from the wire corpus and explicitly declined the wording; this issue is the message rule itself, grounded in eight behavioral checks spanning seven operations, and the two should be fixed in the same emission path.
Fix: the service's shared input-validation / ValidationException construction for marketplace-agreement operations (the generated constraint-check layer feeding each op handler) -- emit the service's member-named message rather than the framework's constraint prose.
Traces: marketplace-agreement.create-agreement-request-invalid-intent-rejected, marketplace-agreement.describe-agreement-malformed-id-rejected, marketplace-agreement.list-billing-adjustment-requests-invalid-date-range-rejected, marketplace-agreement.search-agreements-maxresults-respected, marketplace-agreement.search-agreements-too-many-filters-rejected, marketplace-agreement.send-agreement-cancellation-request-invalid-reason-code-rejected, marketplace-agreement.send-agreement-payment-request-name-too-short-rejected, marketplace-agreement.update-purchase-orders-exceeds-max-entries-rejected.

Cause 2 of 2: SearchAgreements ACCEPTS a sort field that AWS refuses for the requested party type.
AWS: Smithy: SearchAgreementsInput.sort -> Sort{sortBy -> SortBy, sortOrder}, documented as "For SearchAgreements, SortBy supports EndTime for both party types, and StartTime and LastUpdateTime only when PartyType is Proposer" (the same restriction is repeated on Sort.sortBy). A SearchAgreements request carrying sort.sortBy=StartTime together with a filter PartyType=Acceptor is therefore an unsupported combination and is refused with 400 / ValidationException (ValidationExceptionReason models both INVALID_SORT_BY and UNSUPPORTED_FILTERS); recorded message example: 'Provided combination of filters is not supported.'
Emulator: the call SUCCEEDS (HTTP 200 with a SearchAgreements result) -- the PartyType restriction on sortBy is not enforced at all, only documented.
Why: this is a fail-open acceptance of input real AWS rejects. Code developed against the emulator ships a request AWS will reject at runtime, and tests that assert the restriction is enforced pass locally and fail against AWS; it also means the sort/party-type pairing is never validated, so any caller relying on the rejection to detect a mis-scoped query gets a silently different (unordered/unrestricted) result set instead.
Fix: SearchAgreements' handler input validation -- reject sort.sortBy of StartTime or LastUpdateTime unless the request is scoped to PartyType=Proposer, with ValidationException (400).
Traces: marketplace-agreement.search-agreements-sort-order-valid-field-accepted.

Not filed here: marketplace-agreement.accept-agreement-request-not-found diverges only in the message of an otherwise correct ResourceNotFoundException for an unknown 'ar-' id (emulator echoes the id: 'agreement request ar-... not found'); the error class on that path is already carried by the open issue 20261022T041017Z-marketplace-agreement-unknown-agreement-and-agreement-request-lookups-answer-404.md, and the rule producing AWS's fixed not-found wording is not request-derived, so it is not treated as a separate defect. marketplace-agreement.get-agreement-terms-for-active-agreement is also not filed: its assertion requires a real purchased/ACTIVE Marketplace agreement on the caller's account, which only a live run can produce.
