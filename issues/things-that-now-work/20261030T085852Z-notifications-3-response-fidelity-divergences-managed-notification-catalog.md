# notifications: 3 response-fidelity divergences — managed-notification catalog incomplete and wrong, 204 tag responses omit Content-Length

> _Note: this issue was identified against the code base at commit `a4d130d43457183d059e75e01489949cdd3b99ce`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListManagedNotificationConfigurations

## Description
Three net-new wire divergences in the notifications emulator's response fidelity. All three steps return the status AWS returns; what diverges is the CONTENT of the response — the published managed-notification catalog, and the headers of the 204 answers to the two tag mutations. 3 causes, numbered below; a fixer must close all three.

Cause 1 of 3: ListManagedNotificationConfigurations publishes an incomplete catalog and two wrong descriptions (fixture notifications-catalog-list-managed-notification-configurations, step task#1).
AWS: Smithy: ListManagedNotificationConfigurations GET /managed-notification-configurations -> 200, output member `managedNotificationConfigurations` (ManagedNotificationConfigurations) is @required; each entry is a ManagedNotificationConfigurationStructure of arn/name/description, the arn shaped `managed-notification-configuration/category/<category>/sub-category/<subCategory>` with each segment `[a-zA-Z0-9\-]{3,64}`, and ManagedNotificationConfigurationDescription bounded at 256 characters. The model does NOT enumerate the catalog, so the published SET and the per-entry display text are recorded behavior only. The recording shows a catalog that is strictly larger than the emulator's and whose descriptions differ: it contains an `AWS-Partner-Central/PCAccountManagement` entry (name "Account management") and entries under a whole category the emulator does not publish at all, `AWS-MP-Buyer` (e.g. sub-category `MPBuyerProducts`), and for the two sub-categories both sides do publish it carries different description prose — for `PCPaymentsAndDisbursements` and `PCOffersAndAgreements` the recorded descriptions are the payments/offers texts quoted under Traces below, which enumerate the covered marketplace event classes (disbursement failures and pauses, payment failures, payment request rejections, billing adjustments, invoice submission outcomes; and offer publishing, acceptance, agreement creation, amendment, cancellation, compliance failures, ISV entitlement events). Because a managed configuration is published by the service and no modelled operation creates or deletes one, this catalog is a fixed, account-independent set: every account sees the same arns, names and descriptions, so the whole set and its text are the requirement, not a per-run value.
Emulator: the catalog is a hard-coded 7-entry seed (4 AWS-Health sub-categories plus 3 AWS-Partner-Central ones) whose PCPaymentsAndDisbursements and PCOffersAndAgreements descriptions are locally authored summaries ('Marketplace events related to the money you are owed and paid, ...' / 'Marketplace events related to your offers and the agreements buyers hold with you, ...') rather than the published text, and which omits AWS-Partner-Central/PCAccountManagement and the entire AWS-MP-Buyer category. The replay reports value_mismatch on the two descriptions and `missing` for each entry the emulator never publishes.
Why: a client enumerating the catalog to let a user subscribe to managed notifications sees a short catalog — the arns it is missing simply do not exist as far as the emulator is concerned, so GetManagedNotificationConfiguration / channel-association calls against those arns cannot be exercised at all, and any UI or policy that keys off the published sub-category set silently drops marketplace buyer and seller-account notifications. The two wrong descriptions mean console/CLI text the user reads to decide what a subscription covers does not match AWS's.
Fix: the catalog seed in the notifications service state — the `MANAGED_NOTIFICATION_CATALOG` table and the `seeded_managed_configurations()` builder that turns it into store records. Add the missing category/sub-category entries with their published names and descriptions and correct the two divergent descriptions; the handler itself (ordering, paging, channelIdentifier filter) is not implicated.
Traces: notifications-catalog-list-managed-notification-configurations#task#1. Expected vs actual, from the replay: `$.managedNotificationConfigurations[arn="arn:aws:notifications::<account>:managed-notification-configuration/category/AWS-Partner-Central/sub-category/PCPaymentsAndDisbursements"].description` expected 'Marketplace events with payments and financial implications, including disbursement failures and pauses, payment failures, payment request rejections, billing adjustments on purchase agreements, and invoice submission outcomes.', got 'Marketplace events related to the money you are owed and paid, including disbursement status, buyer payment and invoice events, and changes to your bank or tax settings.'; `...PCOffersAndAgreements.description` expected 'Marketplace events related to private offers, reseller activity, and post-acceptance agreement lifecycle, including offer publishing, acceptance, agreement creation, amendment, cancellation, compliance failures, and ISV entitlement events.', got 'Marketplace events related to your offers and the agreements buyers hold with you, including offer creation and expiry, and agreement acceptance, renewal and cancellation.'; `...AWS-Partner-Central/sub-category/PCAccountManagement` missing (expected name 'Account management', description 'Marketplace events related to seller account standing, including business and bank account verification status.'); `...AWS-MP-Buyer/sub-category/MPBuyerProducts` missing, and further AWS-MP-Buyer entries in the same cluster. The 12-digit account segment of each arn is a per-environment value, not part of the requirement; the category/sub-category segments, names and descriptions are. Code: services/service-com-amazonaws-notifications-notifications/src/state.rs lines 632-675 (MANAGED_NOTIFICATION_CATALOG) and 721-763 (seeded_managed_configurations).

Cause 2 of 3: TagResource's 204 response omits the Content-Length header (fixture notifications-tag-resource-list-tags-untag-roundtrip, step task#5).
AWS: Smithy: TagResource POST /tags/{arn}, output shape TagResourceResponse has no members and the model leaves @http code defaulted; recorded behavior only for the status, which is 204 No Content. The recording shows the 204 response still carrying a `content-length` header (the fixture asserts its presence, not its value — for an empty body it is `0`). A bodyless success is therefore framed explicitly, not left unframed.
Emulator: answers 204 with the correct status but no `content-length` header at all — the replay reports `$headers.content-length: missing (expected '<shaped-not-asserted>', got None)`.
Why: an HTTP client or proxy that distinguishes an explicitly-zero-length body from an unframed response behaves differently — with neither Content-Length nor Transfer-Encoding the message length is determined by connection close for some client/HTTP-version combinations, so a client can hold the connection open waiting for a body, lose keep-alive reuse, or report a truncated response, on a call that in fact succeeded.
Fix: the success-response serializer path for a no-member output served with a 204 status (shared framework serialization for this service's bodyless successes), which must emit `Content-Length: 0` alongside the suppressed body rather than omitting the header.
Traces: notifications-tag-resource-list-tags-untag-roundtrip#task#5. Status 204 expected and 204 returned; the only divergence is the absent `content-length`. Code: services/service-com-amazonaws-notifications-notifications/src/ops/tag_resource.rs line 146 (SUCCESS_STATUS = 204) — the status is right, the framing is not.

Cause 3 of 3: UntagResource's 204 response omits the Content-Length header (fixture notifications-tag-resource-list-tags-untag-roundtrip, step task#7).
AWS: Smithy: UntagResource DELETE /tags/{arn}, output shape UntagResourceResponse has no members, @http code defaulted; recorded behavior only for the status, which is 204 No Content, and the recorded 204 carries a `content-length` header exactly as TagResource's does.
Emulator: answers 204 with no `content-length` header — `$headers.content-length: missing (expected '<shaped-not-asserted>', got None)`.
Why: same client-visible consequence as cause 2 — the bodyless success is unframed, so message-length determination falls back to connection behavior on a call that succeeded.
Fix: same component as cause 2 (the bodyless-success serializer). It is listed as its own cause because it is a second operation and a second fixture step: a fix that frames only TagResource leaves this step diverging.
Traces: notifications-tag-resource-list-tags-untag-roundtrip#task#7.

## Fix status

Cause 1: the two divergent AWS-Partner-Central descriptions now carry the published text, and the published `AWS-Partner-Central/PCAccountManagement` entry is part of the catalog seed. STILL OPEN: the recording's `AWS-MP-Buyer` cluster. The evidence available to a fixer names only the sub-category token `MPBuyerProducts` ("plus further AWS-MP-Buyer entries"), and a replay withholds recorded values, so neither the rest of that cluster's tokens nor any entry's published `name`/`description` is recoverable — publishing an invented token or invented display text would add a fidelity defect rather than remove one, so the category is left unpublished until its text is available. The `$.managedNotificationConfigurations` key therefore still diverges on that cluster alone.

Causes 2 and 3: the service now frames a bodyless 204 explicitly — the one no-content framing seam every response of this service passes through (`frame_empty_body` in src/service.rs) empties the rendered body and states `content-length: 0`, which the in-process front door, the inter-service callback path and the SDK connector all serve unchanged. STILL OPEN on a socket: the vendored listener hands the response to hyper's HTTP/1.1 writer (vendor/server/src/lib.rs, the `http::Response` handed to the hyper service), and that writer drops `content-length` from a 204, so no header a service crate states on a 204 reaches a socket client. `services/service-com-amazonaws-notifications-notifications/tests/all/no_content_framing.rs` pins both halves, including a socket probe showing what the wire really delivers. Closing these two keys needs a change in the vendored response writer: preserve a handler-set `content-length` on a bodyless success instead of stripping it.
