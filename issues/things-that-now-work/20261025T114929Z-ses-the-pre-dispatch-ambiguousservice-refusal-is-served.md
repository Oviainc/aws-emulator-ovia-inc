# ses: the pre-dispatch AmbiguousService refusal is served as a retryable 5xx, so a client with a larger retry budget never gets any answer — the SESv2 contact-list paginator walk hangs to the harness cap instead of failing

> _Note: this issue was identified against the code base at commit `a97363f812621dd47aa0891b39cb5eeebafd4acb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListContactLists

## Description
One root cause. Related open issue: 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md reports that the router resolves by sigv4 signing name so all four 'ses'-signed registrations collide, and that the pre-dispatch error body uses awsJson framing for awsQuery clients. That issue does NOT carry this check's replay key: in this run the check no longer surfaces any error at all, it never returns, so it is reported as a 60 s timeout rather than as the ClientError that issue's keys record. The retry classification of the pre-dispatch refusal is the facet reported here.

Cause 1 of 1: an unresolvable-service refusal is emitted with retryable (5xx) semantics, so SDK retry policy loops on it and the call never completes for any client whose retry budget is non-default.
AWS: ListContactLists is SESv2 restJson1, GET /v2/email/contact-lists, 200 with {ContactLists[], NextToken}; its only modeled errors are BadRequestException (400) and TooManyRequestsException (429) — both terminal client errors except the explicitly throttling one (Smithy, service-com-amazonaws-sesv2-simpleemailservice-v2: ListContactLists http GET /v2/email/contact-lists code 200, errors BadRequestException httpError 400, TooManyRequestsException httpError 429; paginated inputToken/outputToken NextToken, pageSize PageSize). ListContacts is POST /v2/email/contact-lists/{ContactListName}/contacts/list, 200, errors BadRequestException 400 / NotFoundException 404 / TooManyRequestsException 429. On AWS every one of these calls returns promptly — either a 200 page or a modeled 4xx — so a paginated walk terminates. A condition in which the endpoint cannot decide which service owns the request does not exist on AWS; AWS has no 'AmbiguousService' error code in any model, and a non-retryable configuration fault is never dressed as a retryable server fault. Recorded behavior only for the ambiguity condition itself.
Emulator: the request is refused before dispatch with the non-AWS code AmbiguousService and the message "4 emulated services all claim requests for 'ses': ses, ses, ses, ses; the request is rejected rather than served by an arbitrary one" (fixed text; the leading count and the repeated service-name list are derived from the emulator's own registry, not from the request). It is served with a status botocore treats as retryable, so the SDK retries it instead of surfacing it: sibling checks on the default config report '(reached max retries: 3)', and this check — whose client is built with Config(retries={'max_attempts': 10, 'mode': 'adaptive'}) — never gets past its first call, sesv2.list_contact_lists(), within the harness window. Replay verdict for ses.contact-list-and-contacts-paginators-walk-every-item-once is 'Check timed out after 60.0s': no status, no code and no message ever reach the caller. Hypothesis: the adaptive-mode backoff over 10 attempts of a retryable refusal exceeds the 60 s cap, which is why the same underlying refusal that other checks report as a ClientError is unobservable here.
Why: a client cannot distinguish 'the emulator cannot route this' from 'the service is overloaded'. Instead of a fast, classifiable failure it gets an unbounded stall: every SDK call blocks for the whole retry budget, paginated walks (ListContactLists/ListContacts NextToken loops) multiply the stall by the page count, and CI or application timeouts fire with no error code to diagnose. Even once routing is fixed, any future pre-dispatch refusal emitted this way will hang callers rather than refuse them.
Fix: the gateway's pre-dispatch refusal path — the service-resolution/registry layer that produces the AmbiguousService response and the error serializer that assigns its HTTP status. An unresolvable-service condition is a permanent, caller-visible fault: it must be answered with a terminal (non-retryable, 4xx-class) status so the SDK surfaces it on the first attempt, rather than with a retryable 5xx. The underlying routing collision itself belongs to 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md.
Traces: ses.contact-list-and-contacts-paginators-walk-every-item-once (verdict mismatch, 'Check timed out after 60.0s'; its first call is sesv2.list_contact_lists() on a client with max_attempts=10, mode=adaptive).

## Evidence
Expected: sesv2.list_contact_lists(PageSize=1) returns 200 with {ContactLists: [...], NextToken?}, and the ListContactLists/ListContacts NextToken walks terminate, visiting the created contact list and all 10 created contacts exactly once. A refusal, if any, is a modeled terminal error (BadRequestException 400 / NotFoundException 404) delivered on the first attempt.
Actual: ses.contact-list-and-contacts-paginators-walk-every-item-once — 'Error: Check timed out after 60.0s'. 'AmbiguousService' appears in no AWS model; the message's fixed text is the emulator's own, and its variable parts (the count '4' and the repeated registration names) come from the emulator's service registry.

## Steps to Reproduce
1. Boot the emulator and point botocore at it (any region; credentials are irrelevant — the refusal is pre-dispatch).
2. Build a client with a non-default retry budget: sesv2 = boto3.client('sesv2', config=Config(retries={'max_attempts': 10, 'mode': 'adaptive'}), endpoint_url=<emulator>).
3. Call sesv2.list_contact_lists(PageSize=1). Observe that the call does not return: it is refused pre-dispatch with AmbiguousService on a retryable status and the SDK keeps retrying for the whole budget (no status, code or message is surfaced to the caller inside 60 s).
4. Repeat with the default retry config (boto3.client('sesv2')) and observe the same refusal, this time surfaced after 3 retries as ClientError (AmbiguousService) — confirming the status is classified retryable rather than terminal.
5. Re-replay ses.contact-list-and-contacts-paginators-walk-every-item-once; it should fail fast with a classifiable error (and pass once routing is fixed), never time out.
