## Description
Six net-new wire-replay causes, all on agent-registry-control. Every replayed step — success paths, idempotency-conflict paths, validation paths and not-found paths alike — is refused BEFORE any operation handler runs, with HTTP 500, the non-AWS error code `AmbiguousService`, the awsJson content type `application/x-amz-json-1.1`, and the emulator-authored body message whose fixed text is `N emulated services all claim requests for '<route-key>': <claimant names>; the request is rejected rather than served by an arbitrary one` (here the variable parts all render as the shared signing scope token, which is itself the symptom: the two claimants are indistinguishable under the key being matched). Score for the corpus is 0% — 0 of 52 steps passed, 42 blocked behind these refusals. A related BEHAVIORAL issue is already open and names the same claim-time defect — 'Every AgentRegistryControl request is rejected with AmbiguousService: two services claim the shared signing name agent-registry' (20261029T185813Z-agent-registry-control-every-agentregistrycontrol-request-is-rejected-with-ambiguousservice-two.md) — and a sibling exists for the data plane (20261029T192216Z-agent-registry-wire-replay-every-request-refused-pre.md). Neither carries a replay key for any of the fixture steps below, so these wire causes are filed here and must each be re-replayed before closing.

Shared AWS framing for all six causes — Smithy (services/service-com-amazonaws-agentregistrycontrol-agentregistrycontrol/smithy-model/com-amazonaws-agentregistrycontrol-agentregistrycontrol.json): service AgentRegistryControl, protocol restJson1, authSchemes [sigv4]. restJson1 responses, success and error alike, are framed `Content-Type: application/json`; an error carries the shape name in `X-Amzn-Errortype` and the modeled HTTP status of that shape. `AmbiguousService` is in no error union of this service — its common errors are AccessDeniedException, InternalServerException, ThrottlingException and ValidationException — so no SDK catch of a modeled error matches it, and a 500 is retried as a transient fault, burning the whole retry budget before it ever surfaces.

Shared Fix: the service-claim seam, not any one handler. Both the control plane and the data plane crates still carry the generated default claim predicate that compares the resolved route key to the service identity's SigV4 signing name, and both identities carry the same signing name while their endpointPrefix values differ (`agent-registry-control` vs `agent-registry`). Each crate's predicate must claim only requests addressed to ITS OWN endpointPrefix so exactly one service claims any request and the router's two-claimant refusal is never reached; fixing only one crate is insufficient because both predicates currently answer true for both endpoints. After that, each cause below needs its own operation handler/validation/serializer to actually be exercised — the refusal has masked all of them, so re-replay rather than assume.

Cause 1 of 6 — CreateRegistry success envelope (fixture agent-registry-control-registry-idempotency-and-not-ready-conflict, step task#1; cluster also covers task#2 of the same fixture). AWS: Smithy CreateRegistry http { method POST, uri /registries, code 202 }; output CreateRegistryResponse with required member `registryArn` (RegistryArn, @length 46..2048, @pattern ^arn:aws(-[^:]+)?:agent-registry:[a-z0-9-]+:[0-9]{12}:registry/[a-zA-Z0-9]{12,16}$). So a valid create answers 202 with `Content-Type: application/json` and a body carrying a registry ARN of that shape (the account, region and registry id are per-environment values, not requirements). Emulator: 500, body has no `registryArn` at all, and `content-type` is `application/x-amz-json-1.1`. Why: a client cannot create a registry, so it has no ARN to address any later call with, and nothing in the control-plane surface is reachable. Fix: the CreateRegistry handler and its restJson1 serializer, once the claim predicate dispatches to it.

Cause 2 of 6 — CreateRegistry idempotency-token conflict (fixture agent-registry-control-registry-idempotency-and-not-ready-conflict, step task#3). AWS: `clientToken` is @idempotencyToken; replaying it with DIFFERENT request parameters is a conflict, and Smithy models ConflictException as a client error with @httpError 409 and a `message` member. The recorded refusal is 409 with the fixed message text `Idempotency token already used with different request parameters` — fixed text in full, no variable parts. Emulator: 500 AmbiguousService with the router's two-claimant message and awsJson framing, no 409 and no ConflictException errortype. Why: a client retrying a create with a mutated body gets an unclassifiable retryable 500 instead of a terminal 409, so it cannot tell a genuine conflict from a transient fault and may duplicate or abandon work. Fix: the CreateRegistry handler's idempotency-token fingerprint comparison and its ConflictException path.

Cause 3 of 6 — CreateRegistry setup step shared by four fixtures (representative fixture agent-registry-control-registry-record-approval-workflow, step setup#1; cluster also covers agent-registry-control-registry-record-lifecycle#setup#1, agent-registry-control-registry-record-tagging#setup#1 and agent-registry-control-registry-validation-and-conflict-errors#setup#1). Cause 4 of 6 — CreateRegistry name-pattern validation (fixture agent-registry-control-registry-validation-and-conflict-errors, step task#5). AWS: Smithy CreateRegistryRequest.name is required, target RegistryName @length 1..64 with @pattern ^[a-zA-Z0-9][a-zA-Z0-9_\-\.\/]*$; a violating name is refused 400 ValidationException (@httpError 400, members message/reason/fieldList, reason defaulting to FieldValidationFailed). The recorded message follows AWS's standard constraint-violation template: fixed text `<n> validation error(s) detected: Value at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>`, whose variable parts are the error count, the offending member path (`name`) and the pattern from the model; the recording's rendering is `1 validation error detected: Value at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9][a-zA-Z0-9_\-\.\/]*`. Emulator: 500, `x-amzn-errortype: AmbiguousService`, awsJson content type, and the router message in place of the validation message. Why: a client sending an invalid registry name is told the service is broken rather than which member failed which constraint, so it cannot correct the request. Fix: CreateRegistry input validation and the ValidationException serializer (message/reason rendering).

Cause 5 of 6 — TagResource unrecognized-ARN validation (fixture agent-registry-control-registry-validation-and-conflict-errors, step task#7). AWS: Smithy TagResource http { method POST, uri /tags/{resourceArn+}, code 204 }, errors ResourceNotFoundException and ServiceQuotaExceededException plus the common ValidationException. An ARN that is not a recognized Agent Registry resource ARN is refused 400 ValidationException carrying BOTH `message` and the required `reason` member, which here takes its modeled default `FieldValidationFailed`. Message template: fixed text `Unrecognized Agent Registry resource ARN: ` followed by the offending ARN taken verbatim from the request's resourceArn label (the recording's particular ARN string is that variable part, not part of the template). Emulator: 500, no `reason` member in the body at all, awsJson content type, errortype AmbiguousService. Why: a client tagging with a malformed ARN gets no ValidationException and no `reason` discriminator, so SDK-level reason switching on validation failures is impossible. Fix: TagResource's resourceArn parsing/validation and the ValidationException serializer, which must emit the required `reason` member (default FieldValidationFailed) and not just `message`.

Cause 6 of 6 — GetRegistry not-found (fixture agent-registry-control-registry-validation-and-conflict-errors, step task#8). AWS: Smithy GetRegistry http { method GET, uri /registries/{registryId} }, errors ResourceNotFoundException (@httpError 404, `message` member). An identifier that resolves to no registry is refused 404 ResourceNotFoundException; message template fixed text `Registry with ARN ` + the identifier as supplied in the request + `. not found.` — i.e. `Registry with ARN <identifier> not found.`, the identifier being the only variable part. Emulator: 500 with the router message, awsJson content type, errortype AmbiguousService. Why: a client probing for a registry's existence cannot distinguish absent from broken, and a 404-driven create-if-missing flow never fires. Fix: the GetRegistry handler's lookup-miss path and its ResourceNotFoundException serializer.
