# ses: 2 net-new behavioral root causes — a CFN-deployed AWS::SES::ConfigurationSet is visible to SES v1 but NotFound to SESv2 GetConfigurationSet, and an S3Action's KmsKeyArn is never authorized against the KMS key policy

> _Note: this issue was identified against the code base at commit `464a2835635950cb0afe23fa38546fc133c528e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetConfigurationSet

## Description
Two net-new behavioral root causes on the SES surface. Neither failing check was marked ALREADY FILED, and neither is OWNED by an open issue in this replay report, so no open issue carries their replay keys. Adjacent open issues are named per cause.

=== Cause 1 of 2: a CloudFormation-provisioned AWS::SES::ConfigurationSet lands in the SES v1 configuration-set store only — SESv2 GetConfigurationSet refuses it as nonexistent, so the two APIs do not share one configuration-set store. ===

AWS: recorded behavior only for the CloudFormation half (CFN resource types are not in the SES Smithy models); the SES-side reads are modeled. SES v1 and SESv2 are two APIs over ONE set of per-account, per-Region configuration sets, so a set that exists for one version exists for the other. Smithy (com.amazonaws.ses#DescribeConfigurationSet, awsQuery): input {ConfigurationSetName required, ConfigurationSetAttributeNames}, output {ConfigurationSet{Name}, ...}, single modeled error ConfigurationSetDoesNotExistException -> awsQuery code `ConfigurationSetDoesNotExist`, HTTP 400. Smithy (com.amazonaws.sesv2#GetConfigurationSet): GET /v2/email/configuration-sets/{ConfigurationSetName}, success 200, output {ConfigurationSetName, SendingOptions, DeliveryOptions, ReputationOptions, TrackingOptions, Tags, ...}, modeled errors BadRequestException 400, NotFoundException 404, TooManyRequestsException 429. After a stack declaring `AWS::SES::ConfigurationSet` with Name=<n> reaches CREATE_COMPLETE, BOTH reads resolve the same underlying resource: v1 DescribeConfigurationSet answers ConfigurationSet.Name == <n> AND v2 GetConfigurationSet answers 200 with ConfigurationSetName == <n> and SendingOptions.SendingEnabled == true (a fresh set defaults to sending enabled). A v1 UpdateConfigurationSetSendingEnabled toggle on that same name is then durably visible in the v2 SendingOptions.SendingEnabled flag (one resource, two projections), and deleting the stack removes it, after which v2 GetConfigurationSet answers NotFoundException 404.

Emulator: the stack is created, the stack_create_complete waiter returns, and v1 DescribeConfigurationSet DOES now resolve the declared name — but the very next read on the other API version is refused: SESv2 GetConfigurationSet answers HTTP 404, code `NotFoundException`, message "Configuration set <NAME> does not exist." (fixed text "Configuration set <" + the configuration-set name taken verbatim from the request + "> does not exist."; the per-run generated name is a value, not a requirement). The two crates keep independent collections: services/service-com-amazonaws-ses-simpleemailservice/src/ops/describe_configuration_set.rs:179 reads the ses v1 crate's `state.configuration_sets`, while services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/get_configuration_set.rs:184 reads the sesv2 crate's own `store.configuration_sets`. The CloudFormation provider materialises the resource into the v1 store only, so the set exists on one API version and not the other.

Why: a client cannot read, or carry forward, a configuration set across the two API versions. Infrastructure-as-code deploys the set with CloudFormation and modern application code reads and configures it through SESv2 — that read is refused 404 for a resource the deployment reports as CREATE_COMPLETE and that the v1 API confirms exists. A caller cannot distinguish "the stack created nothing" from "I am asking the wrong API version", and every v2 operation keyed on the set (sending options, tracking options, event destinations, suppression options, a send with ConfigurationSetName) is unreachable for a CFN-managed set.

Fix: the configuration-set state shared by the two crates plus the CloudFormation resource-type provider — `AWS::SES::ConfigurationSet` must be materialised into the ONE per-account/per-Region configuration-set store that both the ses v1 DescribeConfigurationSet/ListConfigurationSets handlers and the sesv2 GetConfigurationSet handler read (each version applying its own projection on read), and removed from it on stack delete.

=== Cause 2 of 2: an S3Action's KmsKeyArn is never authorized at rule-create time — the check never completes because CreateReceiptRule cannot accept any S3Action at all, and no KMS key-policy pre-flight exists. ===

AWS: Smithy (com.amazonaws.ses#CreateReceiptRule, awsQuery): input {RuleSetName required, After, Rule required}, output empty; modeled errors AlreadyExistsException, InvalidLambdaFunctionException, InvalidS3ConfigurationException, InvalidSnsTopicException, LimitExceededException, RuleDoesNotExistException, RuleSetDoesNotExistException — all client, HTTP 400, awsQuery codes AlreadyExists / InvalidLambdaFunction / InvalidS3Configuration / InvalidSnsTopic / LimitExceeded / RuleDoesNotExist / RuleSetDoesNotExist. Smithy (S3Action): {BucketName required, ObjectKeyPrefix, TopicArn, KmsKeyArn, IamRoleArn}; KmsKeyArn is documented as "a customer managed key that you created in Amazon Web Services KMS" for which the caller must "add a statement to your key's policy to give Amazon SES permission to use it". Smithy (InvalidS3ConfigurationException): members {Bucket, message}, documented "Indicates that the provided Amazon S3 bucket or Amazon Web Services KMS encryption key is invalid, or that Amazon SES could not publish to the bucket, possibly due to permissions issues" — i.e. the ONE error class covers both the bucket and the KMS key. So AWS pre-flights BOTH authorizations when the rule is created: an S3Action naming a bucket whose policy grants ses.amazonaws.com s3:PutObject and a KmsKeyArn whose key policy grants ses.amazonaws.com nothing is refused HTTP 400 `InvalidS3Configuration` and persists no rule (DescribeReceiptRuleSet lists none), while the byte-identical rule WITHOUT the KmsKeyArn is accepted, and adding the SES grant (kms:Encrypt / kms:GenerateDataKey*) to the key policy makes the encrypted rule succeed with KmsKeyArn readable back from DescribeReceiptRule. Hypothesis (this check is an unblessed DRAFT — its own header states no ground-truth recording exists, so the exact message templates are hypotheses, not recordings): the KMS refusal carries the message "Could not write to bucket: <BucketName>" (fixed text "Could not write to bucket: " + the bucket name from the request) and the nonexistent-bucket refusal carries "No such bucket: <BucketName>", i.e. the same code with two distinguishable sentences; the required code/status and the no-rule-persisted effect are the modeled part.

Emulator: the check never produces a response at all — verdict [mismatch], "Check timed out after 60.0s". Its first beat wraps CreateReceiptRule in a bounded retry poll (10s interval) waiting for the un-encrypted S3Action to be accepted; CreateReceiptRule is an unimplemented scaffold stub (services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_receipt_rule.rs) that refuses every call, so the poll consumes the whole harness budget and the check is killed before any assertion runs. Consequently neither authorization is evaluated: there is no bucket-policy pre-flight and no KMS key-policy pre-flight on this operation, and the InvalidS3Configuration class is never produced for either fault.

Why: silently accepting an S3Action whose KMS key refuses SES is the worst available failure mode on this surface — the rule is blessed at create time and inbound mail is then undeliverable at receive time with nothing in the API to diagnose it. A client that catches InvalidS3Configuration to surface a misconfigured key or bucket never sees it, and because the two faults are not told apart it cannot tell "my bucket policy is wrong" from "my key policy is wrong".

Fix: the CreateReceiptRule handler and its S3Action validation in the ses v1 crate — the handler must exist, and before persisting the rule it must resolve S3Action.BucketName against the S3 service's bucket store and its bucket policy, and S3Action.KmsKeyArn against the KMS service's key store and key policy for the request's account+region, refusing with InvalidS3ConfigurationException (HTTP 400, awsQuery code InvalidS3Configuration) and a message that distinguishes the bucket fault from the KMS fault, writing nothing on refusal.
