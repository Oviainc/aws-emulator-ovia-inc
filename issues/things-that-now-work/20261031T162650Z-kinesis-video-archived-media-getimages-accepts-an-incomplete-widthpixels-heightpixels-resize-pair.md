# GetImages accepts an incomplete WidthPixels/HeightPixels resize pair instead of refusing it with InvalidArgumentException

> _Note: this issue was identified against the code base at commit `ccf0c8e8a381d27e3dde753aee7f57a3ca4b8e44`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetImages

## Description
One net-new root cause found by the behavioral suite against the kinesis-video-archived-media (KVAM) data plane. Note on related open issues: 20261029T202349Z-kinesis-video-archived-media-getimages-stub.md lists this check id among the units its stub blocked, but GetImages now answers (the check's first assertion — the complete resize pair falling through to the fragment-absence refusal — PASSES), and the surviving failure is a MISSING pairing validation, which that stub issue does not describe and does not own under its recorded Issue-Key (`...|run#5|AssertionError|assert err == NO_FRAGMENTS, (`; this failure is at run#47 on `assert err_incomplete == INCOMPLETE_RESIZE`). 20261029T202349Z-kinesis-video-archived-media-data-plane-streams-never.md covers GetImages authorization, not resize-parameter validation.

Cause 1 of 1: GetImages does not enforce the both-or-neither rule on the WidthPixels/HeightPixels resize pair, so a request naming only one of the two side parameters is accepted as well-formed and falls through to the archive lookup.
AWS: Smithy GetImages (POST /getImages, httpError 200) models WidthPixels (target WidthPixels, @range min 1 max 3840) and HeightPixels (target HeightPixels, @range min 1 max 2160), both optional, and models InvalidArgumentException (errorKind client, httpError 400). The modeled documentation of GetImagesInput$WidthPixels states the rule explicitly: "When both WidthPixels and HeightPixels parameters are provided, the image will be stretched to fit the specified aspect ratio. If only the WidthPixels parameter is provided or if only the HeightPixels is provided, a ValidationException will be thrown. If neither parameter is provided, the original image size from the stream will be returned." Recorded behavior for the refusal's wire shape: HTTP 400, error code InvalidArgumentException, message 'Height and width for the images need to be provided or none.' — entirely fixed text, with no variable part taken from the request or from state (no side value, no member name, no stream name is interpolated). The refusal is an input-validation refusal and is raised BEFORE the archive is consulted: on the very same retention-enabled, fragment-less stream, the COMPLETE pair (WidthPixels=320 together with HeightPixels=240) is instead refused HTTP 404 ResourceNotFoundException with 'No fragments found in the stream for the GetImages request.', so the two cases are distinguishable by error code and the ordering of the two checks is part of the requirement. Hypothesis: the model documents the code as ValidationException while the recording shows InvalidArgumentException; the recorded code is the requirement, since InvalidArgumentException is the code the operation actually models for argument restrictions.
Emulator: the request carrying WidthPixels with NO HeightPixels is accepted by validation and falls through to the fragment lookup, so it is refused with ('ResourceNotFoundException', 'No fragments found in the stream for the GetImages request.') — identical to the complete-pair case — instead of ('InvalidArgumentException', 'Height and width for the images need to be provided or none.'). In services/service-com-amazonaws-kinesisvideoarchivedmedia-awsacuityreader/src/ops/get_images.rs the two sides are validated INDEPENDENTLY of each other (`bounded_side(input.width_pixels, "WidthPixels", MAX_WIDTH_PIXELS)` then `bounded_side(input.height_pixels, "HeightPixels", MAX_HEIGHT_PIXELS)`, around lines 426-429): each is range-checked when present, and nothing relates the presence of one to the presence of the other, so an incomplete pair is never refused.
Why: this is an overly-permissive failure. A client that sends only one side — a configuration real AWS rejects at the argument level — gets back a 'resource missing' signal (404) instead of a 'bad argument' signal (400), so it concludes the stream has no media in the window and keeps polling or provisions media, never correcting the request. Conversely, once the stream DOES hold fragments the emulator will serve images for a half-specified resize whose output size is undefined, while AWS never generates them at all; emulated tests of resize-parameter handling then pass against a request AWS refuses.
Fix: GetImages' input validation in the operation's handler — add the resize-pair presence check (reject when exactly one of WidthPixels / HeightPixels is present) raising InvalidArgumentException with AWS's fixed sentence, and order it with the existing side range checks so it is evaluated before the stream/fragment lookup, the same way the window checks are.
Traces: kinesis-video-archived-media.get-images-width-height-pixels-accepted-on-empty-stream.
