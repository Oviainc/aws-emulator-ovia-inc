# invoicing: own account refused by BatchGetInvoiceProfile, wrong ConflictException wording on duplicate portal preference, and SendProcurementPortalValidation never refuses an undeliverable test e-invoice

> _Note: this issue was identified against the code base at commit `221dd3602e5d0e66d71e70da1fb8509b07c948c5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetInvoiceProfile

## Description
THREE net-new root causes in the invoicing emulator, found by replaying the behavioral suite (18/21, all three failures in invoicing). They are independent defects in three different handlers; a fixer must close ALL THREE before submitting.

=== Cause 1 of 3: BatchGetInvoiceProfile refuses the CALLER'S OWN account with AccessDeniedException instead of returning its profile ===
Failing check: invoicing.batch-get-invoice-profile-unlinked-account-rejected

AWS: Smithy (services/service-com-amazonaws-invoicing-invoicing/smithy-model/com-amazonaws-invoicing-invoicing.json) models BatchGetInvoiceProfile with input AccountIds (AccountIdList, @required, @length 1..1000), output Profiles (ProfileList), and errors AccessDeniedException (httpError 403) / InternalServerException (500) / ResourceNotFoundException (404) / ThrottlingException (429) / ValidationException (400); the operation doc says "This gets the invoice profile associated with a set of accounts. The accounts must be linked accounts under the requester management account organization." The model says nothing further, so the rest is recorded behavior only: real AWS ANSWERS a request naming only the caller's own account with HTTP 200 and a Profiles entry whose AccountId equals the caller's account id — the caller's own account is readable by the caller. It is only a well-formed-but-foreign account id (one that is NOT a member of the caller's organization) that is refused, and then the WHOLE request is refused HTTP 403 AccessDeniedException with Message of the form "Account <callerAccountId> is not authorized to access resources for account <unauthorizedAccountId>" — fixed text "Account ", " is not authorized to access resources for account ", with the two substituted parts being the caller's own account id (from the signed request) and the account id from the AccountIds entry being refused. (The two 12-digit ids in any one replay are that run's values filling the template, never part of it.)
Emulator: the very first, positive-control call — BatchGetInvoiceProfile with AccountIds=[<caller's own account>] — is refused HTTP 403 AccessDeniedException with Message "Account 000000000000 is not authorized to access resources for account 000000000000", i.e. it names the caller and the target as the SAME account and still denies. services/service-com-amazonaws-invoicing-invoicing/src/ops/batch_get_invoice_profile.rs tests every requested id against store.linked_accounts() and nothing else, and its module doc asserts "The requester's own account is the MANAGEMENT account of this organization, and a management account is not a linked account under itself, so it takes the same test as every other account id" — that premise is what produces the refusal: the emulator's seeded linked-account set does not contain the emulator account, so no account at all is readable and the operation can never return a profile.
Why: BatchGetInvoiceProfile becomes unusable. A client reading its own invoice profile (the only account it is guaranteed to be able to read) gets a 403 that names it as unauthorized for itself, so every caller — including any caller that uses the own-account read as a connectivity/permission probe — concludes it lacks invoicing permissions. It also destroys the negative test's discriminating power: a target that denies EVERYTHING can never be distinguished from one that correctly enforces organization membership.
Fix: the BatchGetInvoiceProfile handler's authorization check, plus the linked-account membership source it consults in the invoicing crate's state. The caller's own account must be readable by the caller (independently of whatever linked-account set is seeded), while a foreign, non-member account id still refuses the whole request with the 403 and the message template above.

=== Cause 2 of 3: duplicate CreateProcurementPortalPreference answers ConflictException with the emulator's own wording, not AWS's ===
Failing check: invoicing.create-procurement-portal-preference-pending-verification

AWS: Smithy models CreateProcurementPortalPreference with ConflictException (httpError 409) among its errors; the model documents no message text, so the message is recorded behavior only. Creating a second preference whose portal identifiers duplicate an existing one is refused HTTP 409 ConflictException with Message exactly "There is a procurement portal preference already existed with same portal identifiers". That string is entirely FIXED text for this error class — it interpolates nothing from the request or from state (no ARN, no portal name, no buyer/supplier identifier).
Emulator: the error CODE is right (ConflictException) but the Message is the emulator's own hand-written sentence "A procurement portal preference already exists for this portal and buyer/supplier pair" — see services/service-com-amazonaws-invoicing-invoicing/src/ops/create_procurement_portal_preference.rs:268-284, where the ConflictException is constructed with that literal.
Why: AWS error messages are a client-visible contract. Any caller, SDK retry/classification wrapper, log-scraper, or test that matches on the conflict message (the only thing distinguishing this conflict from the other 409s on this plane, since the message carries no identifiers) fails to recognise the duplicate-preference conflict against the emulator, and user-facing text rendered from the message differs from production.
Fix: the CreateProcurementPortalPreference handler's conflict path — emit AWS's fixed sentence for the duplicate-portal-identifiers conflict. (Mind the message-key wiring already present on this plane: the text is served under the "Message" key.)

=== Cause 3 of 3: SendProcurementPortalValidation accepts a send to an unreachable portal endpoint, answering 200 instead of refusing it ===
Failing check: invoicing.list-procurement-portal-preferences-contains-created

AWS: Smithy models SendProcurementPortalValidation with required input ProcurementPortalPreferenceArn, required output ProcurementPortalPreferenceArn, and errors AccessDeniedException (403) / InternalServerException (500) / ResourceNotFoundException (404) / ThrottlingException (429) / ValidationException (400); no delivery gate is documented, so this is recorded behavior only. The operation actually ATTEMPTS to deliver a test e-invoice to the preference's configured ProcurementPortalInstanceEndpoint. When that endpoint cannot receive it, the call is refused HTTP 400 ValidationException with Message of the form: fixed text "We were unable to deliver the test e-invoice to the endpoint ", then the preference's configured ProcurementPortalInstanceEndpoint with the fixed suffix path "/cxml/invoices", then the fixed text ". Please confirm the endpoint URL is correct and reachable, then try again." The only substituted part is the endpoint stored on the preference; everything else is fixed text for this error class.
Emulator: answers HTTP 200 with a success body {"ProcurementPortalPreferenceArn": "<arn>"} and no __type/Message at all — the refusal does not exist in any form. The check's helper raises on the unexpected SUCCESS ("expected this call to be rejected, but it SUCCEEDED and returned {'ProcurementPortalPreferenceArn': 'arn:aws:invoicing::000000000000:procurement-portal-preference/000000000001', ... 'HTTPStatusCode': 200 ...}"), so the two assertions the check makes AFTER the send were never reached but are part of the same recorded behavior and must hold once the refusal exists: a REFUSED SendProcurementPortalValidation still advances the preference's Version by exactly one (the delivery attempt is recorded), and the subsequent VerifyProcurementPortalValidation with a wrong code is refused HTTP 400 ValidationException "The code you entered is invalid. Attempt 1 of 3 failed. Please try again." and likewise advances Version by exactly one — while both EinvoiceDeliveryPreferenceStatus and PurchaseOrderRetrievalPreferenceStatus stay PENDING_VERIFICATION throughout. Note this contradicts the invoicing state module's current stated rule (services/.../src/state.rs:44-54: "Version and LastUpdateDate are advanced by the calls that SUCCESSFULLY write a preference's configuration ... and by nothing else"), which is why the version bookkeeping for these two refusals belongs to this cause.
Why: a client driving the documented send/verify handshake is told the test e-invoice was delivered when it was not. It then polls VerifyProcurementPortalValidation for a code that can never arrive, and it never learns that its endpoint URL is wrong or unreachable — the diagnosis AWS hands back in the very first call. An overly permissive 200 here is the single worst outcome for this flow: it converts an immediately actionable configuration error into a silent dead end.
Fix: the SendProcurementPortalValidation handler and its refusal path — the delivery gate must run before the success response is built and emit the ValidationException above through the service's JSON error serializer (__type + Message, Message-key cased as this plane does), plus the Version bookkeeping shared by this plane's handlers so a refused send/verify advances Version by exactly one without changing either plane status.
Related open issue that does NOT cover this (no replay key for this check; it is grounded in a WIRE fixture and in a DIFFERENT refusal class — an OTP whose delivery could not be CONFIRMED, with its own distinct fixed message): 20261029T190320Z-invoicing-procurement-portal-preference-status-machine-two-refusals.md. The endpoint-unreachable refusal described here is a separate message for the same missing gate; closing both means SendProcurementPortalValidation refuses, with the right message, in each case. Also distinct from 20261028T151600Z-invoicing-sendprocurementportalvalidation-wrong-behavior--r3.md (the issued code's clock mixing) and 20261028T210717Z-invoicing-verifyprocurementportalvalidation-error-response.md (the attempt-budget counter not resetting).
