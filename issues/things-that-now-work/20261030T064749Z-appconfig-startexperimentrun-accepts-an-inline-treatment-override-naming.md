# AppConfig StartExperimentRun accepts an inline treatment-override naming a treatment the experiment definition does not define

> _Note: this issue was identified against the code base at commit `aa75f5d199f9816d8a358732bf51b7bd305abb42`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExperimentRun

## Description
One net-new root cause. Cause 1 of 1: StartExperimentRun validates the SHAPE of TreatmentOverrides.Inline but never checks the assigned treatment keys against the experiment definition's own treatments, so an allocation real AppConfig refuses starts a RUNNING run.

AWS: Smithy StartExperimentRun (POST /applications/{ApplicationIdentifier}/experimentdefinitions/{ExperimentDefinitionIdentifier}/experimentruns, success 201, output ExperimentRun) models BadRequestException (400), ConflictException (409), ResourceNotFoundException (404), InternalServerException (500). StartExperimentRun.TreatmentOverrides targets the union TreatmentOverrides whose single member Inline targets TreatmentOverrideMap (@length 0-32, key EntityId @length 1-2048, value TreatmentKey @pattern ^[a-zA-Z0-9]{1,8}$), documented as "A map of entity IDs to treatment keys. Each entry assigns the specified entity to the specified treatment, bypassing random assignment." The model states the KEY SHAPE only; that an assigned key must be one the addressed experiment definition actually defines is recorded behavior only. The recording shows AppConfig refusing such a start with BadRequestException / HTTP 400 and the message template "Invalid treatment name: <key>. Valid treatment names are: [<control key>, <treatment keys in declaration order>]" — fixed text "Invalid treatment name: ", ". Valid treatment names are: [", "]"; variable parts: the rejected treatment key taken from the request's Inline map, and the list of the definition's own generated keys read from state (the control's key first, then each treatment's key in declaration order; the recording's "nosuchtr" and "[c, t1]" are that run's values filling the template, not part of it). The refusal has no side effect: ListExperimentRuns stays empty, the definition stays Status IDLE, and the same call with an existing treatment key then starts a run with Status RUNNING.

Emulator: the key-existence rule is absent. services/service-com-amazonaws-appconfig-amazonappconfig/src/ops/start_experiment_run.rs validates only (a) tag keys via crate::state::first_tag_key_rejection and (b) the override map via crate::state::treatment_overrides_rejection, and that function (services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs) checks only the map's @length bound, each entity id's @length and each value against TREATMENT_KEY_PATTERN — it is handed the overrides alone and never the experiment definition, so it cannot and does not compare the assigned key to the definition's treatments. The handler then resolves the application and definition, refuses only an already-active run (ConflictException), and writes the run with `treatment_overrides: input.treatment_overrides` verbatim. An eight-character alphanumeric key that names no treatment therefore satisfies every check the emulator performs, and the call answers 201 with Status RUNNING, the bogus assignment echoed back in TreatmentOverrides, the run listed by ListExperimentRuns and the definition moved to ACTIVE — the over-permissive direction, where AWS answers 400 and writes nothing.

Why: TreatmentOverrides is the one place an experiment's assignment can be pinned deterministically (QA entities, allow-listed accounts). AWS validates the key so a typo or a stale treatment key is reported at the start call, before any audience is exposed. Against this emulator the typo is accepted and a run goes RUNNING with an assignment that can never resolve to a treatment, so the entity is silently served something other than what the caller pinned, the caller's negative test for BadRequestException passes on AWS and fails only here, and a run number plus the definition's ACTIVE status are consumed by a call AWS rejected.

Fix: the StartExperimentRun handler's pre-write validation in the appconfig service (services/service-com-amazonaws-appconfig-amazonappconfig/src/ops/start_experiment_run.rs) — after the definition is resolved and before any state is written, every value of TreatmentOverrides.Inline must be checked against that definition's control key and treatment keys and refused with BadRequestException/400 carrying the message above; the same rule belongs on the sibling write (UpdateExperimentRun) so the start side and the update side cannot drift, which is why crate::state::treatment_overrides_rejection needs the definition's keys passed in rather than the overrides alone. Note for the fixer: the key list in the message must be the keys AWS would have generated — the separately filed 20261029T195212Z-appconfig-deployment-and-experiment-state-machine-smuggled-type.md (cause 7) records that this emulator generates "C"/"T1" where AWS generates "c"/"t1", so the two interact in the rendered message. Open issues that do NOT cover this cause: 20261024T131534Z-appconfig-accepts-three-classes-of-invalid-configuration-experiment.md (CreateExperimentDefinition profile type, feature-flag attribute constraints, JSON_SCHEMA validator at deployment) and 20261029T195212Z-appconfig-control-plane-refusals-wrong-error-classes-and.md (refusals that DO happen with the wrong class/wording, including StopExperimentRun's class) — this is a refusal that does not happen at all.

## Evidence
Check appconfig.start-experiment-run-invalid-treatment-allocation-rejected [mismatch] — "Error: Check timed out after 60.0s".

What the check asserts about the operation under test: StartExperimentRun(ApplicationIdentifier=<app>, ExperimentDefinitionIdentifier=<def>, TreatmentOverrides={"Inline": {"entity-1": "nosuchtr"}}) against a definition created with Control={Weight:50, FlagValue:{Enabled:false}} and Treatments=[{Weight:50, FlagValue:{Enabled:true}}] must raise Code 'BadRequestException' with Message 'Invalid treatment name: nosuchtr. Valid treatment names are: [<control key>, <treatment key>]' (the recorded instance reads '[c, t1]'); ListExperimentRuns must then still return [], GetExperimentDefinition must still report Status 'IDLE', and the same call with the real treatment key must return Status 'RUNNING' and exactly one listed run. The check's own _error helper is explicit that an unexpected SUCCESS is the failure it is looking for: "expected rejection, but the call SUCCEEDED and returned ...".

Emulator behavior, from the handler that answers that call (no treatment-name rule exists anywhere in the path):
  services/.../src/ops/start_experiment_run.rs: the only pre-write refusals are `first_tag_key_rejection(input.tags)` -> BadRequestException, `treatment_overrides_rejection(input.treatment_overrides)` -> BadRequestException, unresolvable application/definition -> ResourceNotFoundException, and `definition.active_run().is_some()` -> ConflictException. The run is then written with `treatment_overrides: input.treatment_overrides` and answered with SUCCESS_STATUS 201, `status: EXPERIMENT_RUN_RUNNING`, and `definition.status = EXPERIMENT_DEFINITION_ACTIVE`.
  services/.../src/state.rs `treatment_overrides_rejection(&TreatmentOverrides)` -> `inline_override_violation(entity, treatment, ..)` enforces exactly three things: map length > MAX_INLINE_TREATMENT_OVERRIDES, the entity id's MIN/MAX_ENTITY_ID_LENGTH, and `matches_treatment_key_pattern(treatment)` = 1..=8 ASCII alphanumerics. "nosuchtr" is 8 ASCII alphanumerics, so it passes the pattern and the function returns None — nothing compares it to the definition's Treatments/Control, which the function is never given.

Why this check reports a timeout rather than that assertion: the replayed check is killed by the harness's 60.0s per-check cap inside its SETUP, before the graded call. _create_experiment_definition polls `get_deployment(...)['State']` for the literal 'Complete' with timeout_s=60.0 (check source line ~5137 of the suite report), and AppConfig's Deployment$State is served in SCREAMING_SNAKE_CASE — this emulator answers 'COMPLETE' (state.rs DEPLOYMENT_COMPLETE = "COMPLETE"), which is also what ~40 other sites in this same corpus assert ('COMPLETE', 'ROLLED_BACK', 'REVERTED'), while only Environment$State is CamelCase ('ReadyForDeployment', 'Deploying', 'RollingBack', 'RolledBack') and the emulator already serves that correctly. So that predicate never matches, the 60s poll consumes the whole per-check budget, and the StartExperimentRun call is never issued in this replay. That setup predicate is the check's own artifact and is NOT the divergence reported here; the divergence above is established from the handler that would answer the graded call, and is reproducible directly in two SDK calls (below) without the check's setup clock.
