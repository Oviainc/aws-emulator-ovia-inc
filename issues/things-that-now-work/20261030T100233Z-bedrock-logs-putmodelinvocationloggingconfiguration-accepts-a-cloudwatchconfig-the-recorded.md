# bedrock__logs: PutModelInvocationLoggingConfiguration accepts a cloudWatchConfig the recorded environment refuses 403 AccessDeniedException "Cross-account pass role is not allowed." — the pass-role gate is decided from the role ARN's account id alone (1 cause)

> _Note: this issue was identified against the code base at commit `4d1cac4581690df404b0414e482f7f8268561e90`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue carries 1 net-new root cause for the bedrock/cloudwatch-logs pair; the leading token of the failing check id is bedrock__logs. It is the ONLY failing check in this replay of simparity-behavioral-aws-v1 that the report marked neither "ALREADY FILED" nor "OWNED by" — every other failure in the 343 reported failing checks carries an owner. Read the conflict note at the end before changing the gate: this operation has already flip-flopped twice between accept-everything and deny-everything, and a blanket deny is NOT what is being asked for here.

Cause 1 of 1: the cloudWatchConfig branch of PutModelInvocationLoggingConfiguration reaches its success exit for any roleArn whose embedded account id equals the calling account, without ever evaluating the account's pass-role boundary for that role, so a destination the recorded environment refuses is installed and answered 200.

AWS: Smithy (com.amazonaws.bedrock) models PutModelInvocationLoggingConfiguration as PUT /logging/modelinvocations, success code 200, @idempotent, output shape with no members, one required input member loggingConfig -> LoggingConfig; modeled errors AccessDeniedException (@httpError 403), ValidationException (@httpError 400), ThrottlingException (429), InternalServerException (500). LoggingConfig.cloudWatchConfig targets CloudWatchConfig, whose logGroupName (@length 1..512) and roleArn (RoleArn, @pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$) are both required. The model does NOT state the outcome of the pass-role step, so for the outcome: recorded behavior only. What this check's recording measured (its header documents the measurement: account <leased-account>, 2026-09-17, plus two independent corpus siblings against other leased accounts) is that a cloudWatchConfig naming a log group created moments earlier in the same account, together with a freshly created role in the SAME account carrying an exactly correct Principal Service bedrock.amazonaws.com trust policy and a logs:CreateLogStream/logs:PutLogEvents/logs:DescribeLogStreams grant scoped to that very log group, is REFUSED on the first call with HTTP 403, error class AccessDeniedException, message "Cross-account pass role is not allowed." — that message is entirely FIXED text with no variable part taken from the request or from state. The refused call must also be effect-free: an independent GetModelInvocationLoggingConfiguration afterwards must report exactly the loggingConfig that was in place before the call (for a fresh account/region singleton, none at all), i.e. no partial cloudWatchConfig is left behind. The decision is a property of the account's pass-role/SCP boundary over the role being passed, NOT of the role's own trust policy and NOT of the role's account id — the role here is same-account and correctly trusted and is still refused.

Emulator: the call is ACCEPTED (HTTP 200, empty body) and the cloudWatchConfig is stored. The check's own assertion fires first: `AssertionError: PutModelInvocationLoggingConfiguration accepted a CloudWatch Logs destination in this environment; the withdrawal this check asserts no longer holds and it needs rewriting back to the log event shape its name promises.` No AccessDeniedException is produced, so neither the error class, the 403 status nor the fixed text "Cross-account pass role is not allowed." is ever served on this path, and the three assertions that follow it (code == AccessDeniedException, message contains the cross-account-pass-role text, and the effect-absent read-back) are never reached. Per the already-filed history of this handler the gate now consists of nothing but an account-id comparison on cloudWatchConfig.roleArn: any same-account ARN falls straight through to the store-and-200 exit, so the emulator cannot express a pass-role refusal that depends on the account's policy rather than on the ARN's digits.

Why: a client relying on AWS's behavior reads the 200 as "model-invocation logging is now on and audit/compliance records are being delivered to this log group". Against the emulator it gets that 200 unconditionally, so a configuration that the service refuses looks installed, GetModelInvocationLoggingConfiguration reports a destination that would never deliver, and the operator never sees the 403 that tells them the delivery role cannot be passed. The negative class disappears from the test matrix entirely: a caller cannot distinguish "this destination was accepted" from "this destination was refused at the pass-role boundary", and any code path that catches AccessDeniedException to surface a remediation message for the delivery role never runs.

Fix: the cloudWatchConfig branch of PutModelInvocationLoggingConfiguration's handler and the pass-role decision it calls (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/put_model_invocation_logging_configuration.rs and crate::state::pass_role_denial per the prior filings). The decision must be driven by a modelled pass-role boundary for the role being passed to bedrock.amazonaws.com — configurable account state that this check's environment can be represented by — instead of being derived solely from the 12-digit account id embedded in roleArn; when that boundary refuses, the handler must answer the modeled AccessDeniedException (HTTP 403, x-amzn-errortype AccessDeniedException, message exactly "Cross-account pass role is not allowed.") and commit nothing to the account/region logging singleton, so a following GetModelInvocationLoggingConfiguration returns the prior configuration unchanged.

Open issue 20261030T033702Z-bedrock-putmodelinvocationloggingconfiguration-refuses-an-unverifiable-cloudwatchconfig-with-403.md requires this branch to DECIDE over three outcomes (400 ValidationException when logGroupName/roleArn cannot be validated, 403 AccessDeniedException when a resolvable role is not passable, 200 otherwise). None of those issues was reported as owning this check. The requirement is therefore a decision the emulator can take either way from represented account state, not a constant: the 403 refusal this check measures must be reachable for a same-account, correctly-trusted role, while the 200 path the ga-prod recordings measure must stay reachable too.
