# SQS batch-send, visibility-change and AddPermission refusal taxonomy is absent: all three answer NotImplemented instead of the modeled AWS.SimpleQueueService.* / ReceiptHandleIsInvalid / InvalidParameterValue codes (3 causes)

> _Note: this issue was identified against the code base at commit `431499b2f1ea1a2609bf1973accd93d0291dafd1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendMessageBatch

## Description
Three net-new root causes, all in the SQS service. Each is the refusal/validation semantics of one operation whose handler is still a scaffold stub, so the operation answers a single generic NotImplemented for every input class instead of the per-input-class error SQS models. Related already-filed stub issues name the operations and files but state no required wire behavior: 20261023T114649Z-sqs-sendmessagebatch-stub.md, 20261025T065401Z-sqs-changemessagevisibility-stub.md, 20261025T065401Z-sqs-addpermission-stub.md. These causes supply the refusal taxonomy those handlers must have and should be closed together with them; they are filed separately because the suite did not mark these eight checks as covered.

=== Cause 1 of 3: SendMessageBatch performs no request-level batch validation (and is not implemented at all) ===
AWS: Smithy (com.amazonaws.sqs#SendMessageBatch) models three request-level, whole-batch refusals, each with an awsQueryError code in SQS's legacy namespace and httpError 400: EmptyBatchRequest -> code 'AWS.SimpleQueueService.EmptyBatchRequest'; TooManyEntriesInBatchRequest -> code 'AWS.SimpleQueueService.TooManyEntriesInBatchRequest'; BatchEntryIdsNotDistinct -> code 'AWS.SimpleQueueService.BatchEntryIdsNotDistinct' (also BatchRequestTooLong and InvalidBatchEntryId). These are request-level faults: they refuse the entire call with a 400 and an Error.Code, and NOTHING is enqueued — they are not reported through the per-entry Successful/Failed split that output_shape SendMessageBatchResult carries. A request-level fault also takes precedence over a per-entry fault present in the same batch (a batch holding both a repeated Id and an empty MessageBody is refused wholesale with BatchEntryIdsNotDistinct rather than degrading to a per-entry 'EmptyValue' entry in Failed). Entries max is 10, so an 11-entry batch is TooManyEntriesInBatchRequest. A well-formed batch on the same queue must still succeed and deliver afterwards, so the refusals are specific, not a broken queue.
Emulator: every SendMessageBatch call answers error code 'NotImplemented' with the message 'operation SendMessageBatch is scaffolded but not implemented in this emulator', whatever the Entries value — Entries=[], an 11-entry batch, a duplicate-Id batch, and a valid batch alike. So no request-level code is ever produced, the request-level-preempts-per-entry rule cannot hold, and the positive control (a valid 2-entry batch) cannot be sent either.
Why: batch send is a core SQS data-plane operation. A client that batches sends — every AWS SDK's high-throughput producer path, every SQS-backed worker fan-in, and the SQS targets of Lambda/EventBridge test harnesses — cannot send at all, and a client that relies on the distinct batch error codes to decide retry vs. repair (EmptyBatchRequest and BatchEntryIdsNotDistinct are caller bugs; BatchRequestTooLong needs resplitting) instead sees one opaque NotImplemented, which SDK retry policies do not classify as a client fault.
Fix: the SendMessageBatch handler and its input validation in the SQS service (the scaffold stub named by the replay report, services/service-com-amazonaws-sqs-amazonsqs/src/ops/send_message_batch.rs) — implement the operation, and in front of the per-entry send loop add the request-level checks (empty Entries, >10 entries, non-distinct Ids, aggregate payload size) that refuse the whole call with the modeled error before any entry is enqueued.
Traces: sqs.batch-request-validation-rejected, sqs.duplicate-batch-ids, sqs.send-message-batch-duplicate-ids-rejected-atomically, sqs.send-message-batch-too-many-entries-rejected, sqs.sqsbatch-send-request-level-error-preempts-entry-failures-rejected.

=== Cause 2 of 3: ChangeMessageVisibility never validates a receipt handle (and is not implemented at all) ===
AWS: Smithy (com.amazonaws.sqs#ChangeMessageVisibility) requires QueueUrl, ReceiptHandle and VisibilityTimeout, and models ReceiptHandleIsInvalid (awsQueryError code 'ReceiptHandleIsInvalid', httpError 404) and MessageNotInflight (code 'AWS.SimpleQueueService.MessageNotInflight', httpError 400). A syntactically bogus ReceiptHandle is refused with ReceiptHandleIsInvalid; recorded behavior for a handle whose message has already been deleted (so the handle no longer references an in-flight message) is a refusal carrying Error.Code 'InvalidParameterValue'. In every case the call is REFUSED, never accepted, while the same operation on a still-in-flight message succeeds with an empty body.
Emulator: both the bogus-handle and the retired-handle calls answer error code 'NotImplemented', so the operation is neither accepted nor refused in any AWS-modeled way; no receipt-handle validation exists to distinguish an invalid handle from a valid one.
Why: a consumer that extends the visibility timeout of a message it is still working on — the standard long-processing SQS pattern, and what every SDK's visibility-extension helper calls — cannot do so, and a consumer that handles ReceiptHandleIsInvalid / MessageNotInflight to decide 'drop this handle, the message is gone' instead receives an unclassified NotImplemented and will treat a permanent client fault as a retryable server fault.
Fix: the ChangeMessageVisibility handler and its receipt-handle resolution in the SQS service (services/service-com-amazonaws-sqs-amazonsqs/src/ops/change_message_visibility.rs) — implement the operation and resolve the handle against the queue's in-flight set, refusing with ReceiptHandleIsInvalid for an unparseable/foreign handle and the recorded InvalidParameterValue for a handle whose message is no longer in flight.
Traces: sqs.change-message-visibility-invalid-receipt-handle, sqs.change-visibility-on-expired-handle-rejected.

=== Cause 3 of 3: AddPermission never validates the Actions list (and is not implemented at all) ===
AWS: Smithy (com.amazonaws.sqs#AddPermission) requires QueueUrl, Label, AWSAccountIds and Actions (ActionNameList). Recorded behavior: an action name outside the SQS action set is refused with Error.Code 'InvalidParameterValue' and the queue's Policy attribute is left exactly as it was (a fresh queue still reports no Policy), while a well-formed Actions value on the same queue is accepted and does add the statement.
Emulator: AddPermission answers error code 'NotImplemented' for both the invalid-action call and the valid control, so the invalid-action refusal cannot be distinguished from the accepted case and no policy statement can be added at all.
Why: AddPermission is the shorthand clients use to grant cross-account send/receive on a queue (CLI and console wiring, and SNS/S3/EventBridge bootstrap scripts). Nothing can be granted through it, and a caller that mistypes an action gets NotImplemented rather than the client-fault InvalidParameterValue that tells it the request, not the service, is wrong.
Fix: the AddPermission handler and its validation in the SQS service (services/service-com-amazonaws-sqs-amazonsqs/src/ops/add_permission.rs) — implement the operation, validate each Actions element against the SQS action list before mutating the queue's Policy attribute, and refuse with InvalidParameterValue leaving the stored policy untouched.
Traces: sqs.add-permission-invalid-action-rejected.

## Steps to Reproduce
Cause 1: 1. sqs:CreateQueue a standard queue. 2. sqs:SendMessageBatch(QueueUrl=url, Entries=[]) -> AWS refuses 400 / 'AWS.SimpleQueueService.EmptyBatchRequest'; the emulator answers 'NotImplemented'. 3. SendMessageBatch with 11 entries [{Id:'id0..id10', MessageBody:'x'}] -> AWS refuses 400 / 'AWS.SimpleQueueService.TooManyEntriesInBatchRequest'. 4. SendMessageBatch with two entries both Id='same' -> AWS refuses 400 / 'AWS.SimpleQueueService.BatchEntryIdsNotDistinct' and ReceiveMessage shows nothing enqueued. 5. SendMessageBatch with a 10-entry batch where entry 4 has MessageBody='' and entry 7 repeats entry 2's Id -> AWS still refuses wholesale with BatchEntryIdsNotDistinct, not a per-entry 'EmptyValue' in Failed. 6. SendMessageBatch with two well-formed entries -> AWS returns both in Successful and both are receivable; the emulator refuses this too.

Cause 2: 1. sqs:CreateQueue. 2. sqs:ChangeMessageVisibility(QueueUrl=url, ReceiptHandle='<bogus>', VisibilityTimeout=30) -> AWS refuses with 'ReceiptHandleIsInvalid'; the emulator answers 'NotImplemented'. 3. SendMessage, ReceiveMessage to obtain a real handle, DeleteMessage(handle), then ChangeMessageVisibility with that same handle -> AWS refuses with 'InvalidParameterValue'. 4. Repeat step 3 without the delete, against a still-in-flight message -> AWS succeeds (empty body).

Cause 3: 1. sqs:CreateQueue, then GetQueueAttributes(AttributeNames=['Policy']) -> no Policy attribute. 2. sqs:AddPermission(QueueUrl=url, Label='<unique>', AWSAccountIds=[<own account>], Actions=['NotAnSqsAction']) -> AWS refuses with 'InvalidParameterValue' and GetQueueAttributes still reports no Policy; the emulator answers 'NotImplemented'. 3. AddPermission with Actions=['SendMessage'] -> AWS accepts and the Policy attribute now carries the statement.
