# Pipes DynamoDB-stream source: CreatePipe accepts a stream source with no DynamoDBStreamParameters, and a RUNNING stream-sourced pipe never reads the stream or delivers (2 causes)

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePipe

## Description
This bundle has 2 causes; both must be closed before submitting. Both concern an EventBridge Pipes pipe whose SOURCE is a DynamoDB stream. Attribution note: the leading tokens of the four grounding check ids are the multi-service suite directories dynamodb__pipes__sqs and dynamodb__lambda__pipes__sqs; the defects are attributed to pipes, which is the service that must validate the source and run the pipe (DynamoDB CreateTable with StreamSpecification, DescribeTable, Lambda and SQS all answer correctly in these same checks), and pipes is bootstrapped.

(c) The open issue 20261023T235727Z-dynamodb-createtable-with-streamspecification-answers-notimplemented-blocking-the.md carries the two dynamodb__lambda__pipes__sqs check ids for a DIFFERENT, now-resolved cause: in the previous run both aborted immediately on CreateTable(StreamSpecification) answering NotImplemented. Cause 1 of 2: CreatePipe accepts a DynamoDB-stream Source with SourceParameters omitted entirely and materialises the pipe, where AWS refuses the request and creates nothing.
AWS: Smithy (com.amazonaws.pipes#CreatePipe): Source is @required (ArnOrUrl, length 1..1600), SourceParameters -> PipeSourceParameters is optional and every member of it is optional, so the request is model-valid — but PipeSourceDynamoDBStreamParameters.StartingPosition is @required (target DynamoDBStreamStartPosition), so a DynamoDB stream source has no legal configuration without that member. CreatePipe models ValidationException (errorKind client, httpError 400). The requirement is therefore derived at the service from what kind of resource the Source ARN names, and AWS answers HTTP 400 ValidationException; the recorded body is the Pipes ValidationErrorFields envelope '{"ValidationErrorFields":[{"Name":"SourceParameters.DynamoDBStreamParameters","Message":"Missing required parameter."}]}' (an example of that envelope rule, which is built from the request). The refusal has no effect: the name does not appear in a fully paginated ListPipes and DescribePipe answers 404 NotFoundException.
Emulator: the identical request answers HTTP 200 with Name, Arn, DesiredState RUNNING and CurrentState CREATING, and the pipe is created. The same check's positive control — the byte-identical call plus SourceParameters={DynamoDBStreamParameters:{StartingPosition:'LATEST',BatchSize:1}} — is accepted, reaches RUNNING and echoes StartingPosition back from DescribePipe, so the ONLY difference between the accepted and the wrongly-accepted call is the missing required stream parameters.
Why: a client gets a pipe AWS would never have created, and one with no defined point to start reading the stream from — so it either silently starts at the tail or (see Cause 2) delivers nothing, and both look like a slow pipe rather than a rejected configuration. A template or CDK stack validated against this emulator fails only later against real AWS, which is the class of bug an emulator exists to catch.
Fix: CreatePipe validation in services/service-com-amazonaws-pipes-pipes (src/ops/create_pipe.rs) — resolve the Source ARN's service and resource type and require the matching SourceParameters member (for a dynamodb stream ARN: DynamoDBStreamParameters including StartingPosition), returning the modeled ValidationException (400) with the Pipes ValidationErrorFields body and creating no pipe record.
Traces: dynamodb__pipes__sqs.pipes-create-pipe-dynamodb-stream-source-without-stream-parameters-rejected.

Cause 2 of 2: a pipe whose source is a DynamoDB stream reaches CurrentState RUNNING but never reads the stream and never delivers anything, so no change-data-capture topology over DynamoDB works.
AWS: recorded behavior only for the data plane (the Smithy model describes only the pipes control plane). Smithy: PipeSourceDynamoDBStreamParameters models StartingPosition (@required), BatchSize, MaximumBatchingWindowInSeconds, ParallelizationFactor, OnPartialBatchItemFailure and DeadLetterConfig, and CreatePipe accepts FilterCriteria, Enrichment/EnrichmentParameters and TargetParameters — those members exist because the SERVICE polls the stream once the pipe is RUNNING. The documented contract: Pipes reads the stream's shards with no client action, preserves the order of changes to one partition key within a shard, applies FilterCriteria BEFORE the enrichment, invokes the enrichment with the batch, and sends the result to the target; stream sources are at-least-once. The three checks below wait on exactly one of those observables (per-key order at a FIFO target, MODIFY/REMOVE dropped before the enrichment, NewImage computed at the target).
Emulator: all three reach the harness cap ('Check timed out after 60.0s') while waiting for the first record at the target queue or the enrichment's audit queue — after CreateTable with StreamSpecification succeeded, DescribeTable reported the table ACTIVE with a LatestStreamArn, the IAM role was created and CreatePipe/DescribePipe reported the pipe settled. Nothing is ever read from the stream and nothing is ever sent to the target, while the pipe's own state says it is healthy.
Why: every DynamoDB change-data-capture topology built on a pipe (stream -> filter -> Lambda enrichment -> SQS/Step Functions) silently hangs or asserts against an empty target, and the pipe reports RUNNING throughout, so a client cannot distinguish 'no changes' from 'the pipe never ran'.
Fix: the pipes data-plane/dispatch engine in services/service-com-amazonaws-pipes-pipes — add a DynamoDB-streams source poller (driven by the stored DynamoDBStreamParameters: StartingPosition, BatchSize, MaximumBatchingWindowInSeconds, per-shard ordering) that reads through the emulator's dynamodbstreams surface and feeds the existing-or-new filter, enrichment and target stages. This shares the engine filed as Cause 1 of the open pipes-has-no-runtime issue; the stream-source poller is the part no filed trace covers.
Traces: dynamodb__pipes__sqs.pipes-dynamodb-stream-source-preserves-per-key-change-order, dynamodb__lambda__pipes__sqs.events-pipes-enrichment-dynamodb-stream-filter-drops-modify-and-remove-before-enrichment, dynamodb__lambda__pipes__sqs.events-pipes-enrichment-dynamodb-stream-newimage-computed-at-target.
