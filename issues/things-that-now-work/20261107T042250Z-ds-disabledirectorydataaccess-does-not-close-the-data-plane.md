# ds: DisableDirectoryDataAccess does not close the data plane — ds-data keeps serving a re-disabled directory instead of refusing with AccessDeniedException / Reason DATA_DISABLED, and the disable/re-enable cycle check never completes

> _Note: this issue was identified against the code base at commit `12bd58142e134c788a6e6e722018c3787d666c1f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DisableDirectoryDataAccess

## Description
One net-new root cause, grounded in the failing behavioral check the suite lists under service `ds`.

Cause 1 of 1: the ds control plane's DataAccessStatus is not a gate on the ds-data plane, so DisableDirectoryDataAccess has no observable effect on directory-object reads and writes.
Failing check: ds.disable-directory-data-access-recloses-the-door-without-losing-contents (reported verdict: mismatch, detail "Check timed out after 60.0s" — the check never produced a completed run against the emulator).

AWS: the Directory Service Data API is reachable only while the ds control plane says it is, and the switch works in BOTH directions. Smithy (com.amazonaws.directoryservice): EnableDirectoryDataAccess / DisableDirectoryDataAccess take only {DirectoryId: ^d-[0-9a-f]{10}$} and DescribeDirectoryDataAccess reports DataAccessStatus; the modelled DataAccessStatus enum carries the transient Disabling and the settled Disabled. Smithy (com.amazonaws.directoryservicedata): every operation (DescribeUser, CreateUser, ListUsers, DescribeGroup, ListGroupMembers, ListGroupsForMember, …) declares AccessDeniedException, @error client, httpError 403, with members {Message, Reason -> AccessDeniedReason enum [IAM_AUTH, DIRECTORY_AUTH, DATA_DISABLED]}; its doc reads "You don't have permission to perform the request or access the directory." The DATA_DISABLED value exists for exactly this predicate. Recorded behavior: once DisableDirectoryDataAccess has driven DataAccessStatus to Disabled, every ds-data call against that directory is refused with AccessDeniedException and Reason DATA_DISABLED; the refusal is DIRECTORY-scoped, not operation-scoped, so an object read (DescribeUser), a write (CreateUser) and an inventory read (ListUsers) carry the IDENTICAL error code and the IDENTICAL message (the diagnostic AWS words for a directory whose DS Data feature is off is the fixed sentence "DS Data feature is not enabled on this directory. This feature must first be enabled by calling the EnableDirectoryDataAccess API." — fixed text in full, no variable parts). The directory itself is untouched: ds DescribeDirectories keeps reporting Stage 'Active' while its data plane is shut. A CreateUser refused this way creates nothing, so after a later EnableDirectoryDataAccess the name it used is absent from the paginated ListUsers inventory, while the user/group/membership that existed before the disable come back as the SAME AD objects (the SID is minted by Active Directory and cannot be re-derived, so SIDs, EmailAddress, Enabled and the membership edge in both projections — ListGroupMembers and ListGroupsForMember — are unchanged across the cycle).

Emulator: the toggle is tracked by `ds` and ignored by `ds-data`. The control plane stores and settles it correctly (services/.../directoryservice-.../src/ops/disable_directory_data_access.rs sets Disabling with a 500 ms due instant and src/state.rs advance_clock settles it to Disabled), but the ONLY state shared between the two planes is the directory-id inventory in services/common/src/ad_directories.rs (`AdDirectoryInventory` with register/forget/holds — ids only, no data-access state at all), so no ds-data handler can see the toggle and none consults it: services/.../directoryservicedata/src/ops/describe_user.rs:176-227 goes straight from the store lookup to the projection with no data-access check, and create_user.rs materialises a directory record of its own. Consequence: after DisableDirectoryDataAccess every ds-data read and write still answers HTTP 200, so the check's refusal leg (which asserts AccessDeniedException with Reason DATA_DISABLED and the same code+message for a read, a write and a listing) cannot be satisfied, and the run exhausted the suite's 60 s budget without ever producing the cycle. Hypothesis (not stated by the model or the recording): the 60 s expiry is reached because the check must sit through the control plane's create/enable/disable polling intervals (20 s + 10 s + 15 s + 10 s of fixed sleeps) before it ever reaches the leg above, so the served-instead-of-refused calls are observed only as a timeout; the absent gate is verified from the checkout, not from the timed-out run.

Why: EnableDirectoryDataAccess/DisableDirectoryDataAccess are the only switch that makes the Directory Service Data API usable, and against the emulator the OFF direction is a no-op. A client that shuts the data plane for an audit or an incident is told by the emulator that users and groups are still readable and writable, and any code branching on Reason=DATA_DISABLED (retry after re-enabling, or surface "turn DS Data back on") is dead. Writes AWS discards are persisted, so the two inventories diverge permanently from that point, and the disable→re-enable round trip (object/SID survival) can never be exercised.

Fix: a shared data-access gate in the ds-data crate, applied ahead of every operation handler (before ClientToken/NextToken handling), reading the directory's DataAccessStatus through a cross-plane record instead of a local directory it materialises itself — which means services/common/src/ad_directories.rs must carry the toggle (written by the ds enable/disable handlers and by create) rather than ids only; the refusal belongs in that one shared gate so a read, a write and a listing produce one identical AccessDeniedException.

Relation to open issues: 20261104T054355Z-ds-data-serves-a-directory-whose-data-access.md (open) reports the NEVER-ENABLED predicate for CreateUser/ListUsers and does not carry this check's replay key, and nothing in it covers the DISABLE direction, the read/write/listing message identity, the directory staying Stage 'Active' while shut, or object/SID survival across a disable/re-enable cycle. Fixing that issue alone will not get this check re-replayed.

Traces: ds.disable-directory-data-access-recloses-the-door-without-losing-contents; emulator code cited above: services/common/src/ad_directories.rs:47-98, services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/ops/describe_user.rs:176-227, services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/disable_directory_data_access.rs:206-230.

## Evidence
Expected (AWS), with an Active Managed Microsoft AD whose DataAccessStatus has been driven to 'Disabled' by DisableDirectoryDataAccess:
  ds.describe_directory_data_access(DirectoryId=<id>) -> DataAccessStatus 'Disabling' then 'Disabled'
  dsdata.describe_user(DirectoryId=<id>, SAMAccountName=<existing user>) -> AccessDeniedException, HTTP 403, Reason 'DATA_DISABLED', Message "DS Data feature is not enabled on this directory. This feature must first be enabled by calling the EnableDirectoryDataAccess API." (fixed text, no variable parts)
  dsdata.create_user(DirectoryId=<id>, SAMAccountName=<new name>, ...) -> the IDENTICAL refusal (same Code, same Message as the read — the gate is on the directory, not the operation)
  dsdata.list_users(DirectoryId=<id>) -> the same Code
  ds.describe_directories(DirectoryIds=[<id>]) -> Stage 'Active' throughout
  after ds.enable_directory_data_access(DirectoryId=<id>) and DataAccessStatus 'Enabled': DescribeUser answers again with the SAME SID / EmailAddress / Enabled, DescribeGroup with the same group SID, ListGroupMembers and ListGroupsForMember still report the one membership edge, and the SAMAccountName the refused CreateUser used is ABSENT from the paginated ListUsers inventory.

Actual (emulator): no refusal is reachable on any ds-data operation. The data plane has no access to the control plane's DataAccessStatus — the only shared record is services/common/src/ad_directories.rs `AdDirectoryInventory`, which stores directory ids alone (register/forget/holds, MAX_RECORDED_DIRECTORIES) — and services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/ops/describe_user.rs:176-227 performs no data-access check before projecting the user, so a re-disabled directory answers HTTP 200 for reads, writes and listings alike. The suite's run of ds.disable-directory-data-access-recloses-the-door-without-losing-contents ended with "Check timed out after 60.0s" — the cycle (disable -> refuse -> re-enable -> same objects) never completed against the emulator.

Smithy consulted:
  com.amazonaws.directoryservice: DisableDirectoryDataAccess / EnableDirectoryDataAccess input {DirectoryId (required, ^d-[0-9a-f]{10}$)}; errors AccessDeniedException(400), ClientException(400), DirectoryDoesNotExistException(400), DirectoryInDesiredStateException(400), DirectoryUnavailableException(400), ServiceException(500), UnsupportedOperationException(400). DescribeDirectoryDataAccess output {DataAccessStatus} (enum carrying Disabling/Disabled/Enabling/Enabled).
  com.amazonaws.directoryservicedata: AccessDeniedException @error client, httpError 403, members {Message, Reason -> AccessDeniedReason}; AccessDeniedReason values = [IAM_AUTH, DIRECTORY_AUTH, DATA_DISABLED].

11. Re-replay ds.disable-directory-data-access-recloses-the-door-without-losing-contents.
