# GetRevocationStatus words two input refusals wrongly: generic framework text for an empty certificateHashes, and a platform-not-found error for a platformId that violates @pattern

> _Note: this issue was identified against the code base at commit `b67cec46cc74cc34fd8af0c0592a7b189d0e9cd6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRevocationStatus

## Description
Two distinct root causes behind GetRevocationStatus (the `signer` SDK client's `GET /revocations` data-plane read). Both must be closed before this issue is resolved. Both are refusals that fire with the correct HTTP 400 and the correct `ValidationException` error code but the WRONG message, and signer returns a single ValidationException code for every input fault, so the message is the only discriminator a client has.

Routing note for the fixer: the checks drive a botocore `signer` client, which signs for the shared `signer` signing name, so the request is resolved to the signer CONTROL-plane crate (services/service-com-amazonaws-signer-wallabyservice), not to the signer-data crate — services/service-com-amazonaws-signerdata-signerdataplane/src/service.rs claims only the `data-signer` route key. The modelled contract is identical in both models, so the fix belongs wherever that shared `/revocations` route is served; see Traces for the files.

Cause 1 of 2: an EMPTY `certificateHashes` list is refused with the generic Smithy framework required-member text instead of signer's own wording (check signer-data.certificate-hashes-empty-list-rejected).
AWS: Smithy GetRevocationStatus is GET /revocations; signatureTimestamp, platformId, profileVersionArn, jobArn and certificateHashes are all @required and @httpQuery-bound; certificateHashes targets CertificateHashes (list of CertificateHash, @length 1..2048 per member). Modeled client errors: AccessDeniedException/403, TooManyRequestsException/429, ValidationException/400 (members `message`, `code`). The model does not state how an EMPTY list is treated, so: recorded behavior only — a request whose certificateHashes query binding carries no entries is refused with HTTP 400, error code ValidationException and message `certificateHashes must not be null or empty`. Message decomposition: `must not be null or empty` is FIXED text; the leading token is a VARIABLE taken from the request — the offending input member's wire name as @httpQuery binds it (`certificateHashes`). There are no ids, counts, timestamps or other per-run values in it. AWS deliberately conflates the absent and the empty case in one message, because an empty @httpQuery list is indistinguishable on the wire from an absent one.
Emulator: HTTP 400 and code ValidationException are right, but the message is the generic framework constraint reporter's: `1 validation error detected: Value null at 'certificateHashes' failed to satisfy constraint: Member must not be null`. That text additionally asserts the value was `null`, misreporting a request that did supply the parameter.
Why: a client branching on signer's ValidationException text to tell "you sent no certificate hashes, retry with a populated list" from other input faults never matches, and the emulator's text claims a null member the caller did not send. GetRevocationStatus is a security decision point, so that branch decides whether a verification is retried or failed closed.
Fix: the refusal wording seam / input validation on the `/revocations` route of the crate that serves it — a required LIST member the request supplied nothing for must emit `<member> must not be null or empty` (member name taken from the request) for BOTH the absent and the empty-list case, instead of falling through to the shared `1 validation error detected: ...` required-member reporter.

Cause 2 of 2: a `platformId` that violates the modeled @pattern is not refused at the boundary; it reaches the platform-catalog lookup and is reported as a platform that does not exist (check signer-data.platform-id-pattern-rejected).
AWS: Smithy PlatformId is a string with @pattern `^[a-zA-Z0-9_-]+$`, bound as the @required @httpQuery member `platformId` of GetRevocationStatus. A value violating a modeled @pattern is refused at the protocol boundary, before any resource lookup, with HTTP 400 ValidationException and the framework constraint message `1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>`. Message decomposition: `1 validation error detected: Value '` / `' at '` / `' failed to satisfy constraint: Member must satisfy regular expression pattern: ` is FIXED text; the VARIABLES are the rejected value echoed from the request, the member name (`platformId`) and the pattern the model declares (`^[a-zA-Z0-9_-]+$`). No per-run values are involved.
Emulator: answers HTTP 400 with the existence error from its own platform catalog instead — message `Platform with id bad platform! does not exist` (the generic `Platform with id <value> does not exist` produced by the handler's platform lookup). So the modelled @pattern constraint is never enforced on this httpQuery member: the handler's catalog check runs first and reclassifies a SYNTACTICALLY invalid id as a non-existent platform. The same gap means any value outside the character class is reported as "does not exist" rather than as a constraint violation.
Why: the two conditions are different for a caller. "Does not exist" says the id was well-formed but unknown (retry with another platform id, or the platform was withdrawn); the pattern violation says the id is not a platform id at all (a client-side construction bug — a space, a `!`, a URL-encoding slip). A client that matches on AWS's `failed to satisfy constraint: Member must satisfy regular expression pattern` text, or that reports the echoed offending value back to its caller, gets neither. It also hides that constraint validation is skipped for this member, so no out-of-class value is ever refused at the boundary.
Fix: the boundary validation for GetRevocationStatus's input on the `/revocations` route — the @pattern on PlatformId must be enforced by the deserialize→validate step BEFORE `handle` runs (the signerdata handler's own comment already asserts this ordering: services/service-com-amazonaws-signerdata-signerdataplane/src/ops/get_revocation_status.rs lines 176-180), so the platform-catalog lookup only ever sees pattern-conforming ids.

Related but NOT the same causes: open issue 20261023T031331Z-signer-accepts-calls-aws-rejects-and-reports-signing.md covers GetRevocationStatus ACCEPTING a malformed profileVersionArn/jobArn with HTTP 200 (Cause 2 there) — a missing refusal, not a mis-worded one. Open issue 20261027T022736Z-signer-getrevocationstatus-rejects-an-empty-certificatehashes-with-the-generic.md records the SAME defect as Cause 1 here, but from the wire corpus against service `signer` (com.amazonaws.signer#WallabyService); this issue is grounded in the behavioral check against service `signer-data` and carries the behavioral replay key, so closing one does not re-replay the other. Neither covers Cause 2.
