# Service Quotas defaults for ds, dynamodb, ebs, ecr, eks, elasticache and 4 more ServiceCodes omit the AWS quota catalog and invent quota codes

> _Note: this issue was identified against the code base at commit `716594ad03747236be5f362ba3ba8170b7a2d152`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAWSDefaultServiceQuotas

## Description
This issue bundles 10 causes — one per ServiceCode — of the same defect: the emulator's default-quota catalog is a small hand-written table rather than the service's published catalog. Each cause is its own ServiceCode and its own fixture, and a fixer must close and re-replay all 10 before submitting.

AWS (applies to every cause): ListAWSDefaultServiceQuotas(ServiceCode) answers 200 with `Quotas`, the complete published default-quota catalog for that service. Every entry is keyed by the AWS-assigned quota code, which always has the form L-XXXXXXXX, and carries ServiceCode, ServiceName, QuotaCode, QuotaArn (arn:aws:servicequotas:<region>::<serviceCode>/<quotaCode>), QuotaName, Description, Value, Unit, Adjustable and GlobalQuota, plus Period, UsageMetric and QuotaContext for the quotas AWS publishes those for. Smithy: ListAWSDefaultServiceQuotasResponse.Quotas -> ServiceQuotaListDefinition, ServiceCode @required @pattern ^[a-zA-Z][a-zA-Z0-9-]{1,63}$. The per-ServiceCode catalog contents are recorded behavior only — each fixture's recorded 200 response is the reference.

Emulator (applies to every cause): 200 is returned, but the list holds only a few entries keyed by invented, human-readable codes (e.g. 'Directories', 'Repositories', 'Clusters', 'NodesPerRegion') that AWS does not publish, almost every real L- coded quota is absent, and a few of the entries that do exist carry a different Description or UsageMetric than AWS.

Why (applies to every cause): QuotaCode is the only stable key Service Quotas exposes — GetServiceQuota, GetAWSDefaultServiceQuota and RequestServiceQuotaIncrease all take it. A client that looks up a quota by its documented L- code gets nothing back and concludes the quota does not exist, while a client that enumerates the list is handed fabricated codes that no other API accepts and limit values that are not the service's defaults, so capacity planning, pre-flight limit checks and compliance reporting all draw the wrong conclusion.

Fix (applies to every cause): the ListAWSDefaultServiceQuotas handler's quota-catalog state for Service Quotas. Replace the hand-written per-service table with the published default-quota catalog keyed on AWS L- quota codes, populate Description/Unit/Adjustable/GlobalQuota/Period/UsageMetric/QuotaContext from it, and stop emitting codes AWS does not publish.
