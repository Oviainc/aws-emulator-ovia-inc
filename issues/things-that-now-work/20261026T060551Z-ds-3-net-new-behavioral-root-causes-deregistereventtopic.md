# ds: 3 net-new behavioral root causes — DeregisterEventTopic is a 501 scaffold stub, CreateComputer's DirectoryUnavailableException message is emulator-authored, and the enum-value-set ValidationException lists the allowed values in the wrong order

> _Note: this issue was identified against the code base at commit `60e29f2f6f2b3729516bc68f9c1725f27767e8dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeregisterEventTopic, CreateComputer, DescribeClientAuthenticationSettings

## Description
Behavioral replay of the ds suite (simparity-behavioral-ga-prod-v1) left three failing ds.* checks after skipping every check the report marks ALREADY FILED (scaffold stubs: DescribeCAEnrollmentPolicy, CreateInternetGateway, DeleteSnapshot, ListCertificates, EnableLDAPS, StartSchemaExtension) and every check marked OWNED by an open issue. They reduce to THREE independent root causes. A fixer must close all three before submitting.

Related open issues that do NOT cover these causes: 20261024T081601Z-ds-directory-service-control-plane-7-behavioral-divergences-error.md lists ds.enum-wire-values-precede-resource-resolution and ds.register-event-topic-absent-directory-rejected among its trace ids, but its replay keys are earlier legs of those checks (the missing ' : RequestId: <id>' envelope suffix on DescribeLDAPSSettings and on RegisterEventTopic). Those legs now PASS; the two checks fail further on, at the legs described below, which that issue carries no key for — which is why the suite did not mark them OWNED. 20261024T081601Z-ds-createcomputer-stub.md (CreateComputer scaffold stub) is resolved: CreateComputer now answers, and Cause 2 is about the wording of the refusal it correctly produces, not about the call being unavailable.

Cause 1 of 3: DeregisterEventTopic is still an unimplemented scaffold stub, so it answers 501 NotImplemented instead of the modelled not-found refusal.
AWS: Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json) models DeregisterEventTopic with required DirectoryId (@pattern ^d-[0-9a-f]{10}$) and required TopicName (@length 1..256, @pattern ^[a-zA-Z0-9_-]+$), an empty DeregisterEventTopicResult, and errors ClientException / EntityDoesNotExistException / InvalidParameterException (all client, HTTP 400) and ServiceException (500). Recorded behavior: DeregisterEventTopic naming a DirectoryId that satisfies the pattern but resolves to no directory is refused with 400 EntityDoesNotExistException whose Message is the fixed ds not-found sentence for a directory — "Directory: '<directory-id>' does not exist." followed by the ds envelope suffix " : RequestId: <request-id>". Fixed text: "Directory: '", "' does not exist. : RequestId: "; variable parts: the DirectoryId from the request and the response's own request id. Its sibling operations RegisterEventTopic and DescribeEventTopics already produce exactly this refusal in this emulator, so the wording is not in question.
Emulator: the call is answered 501 with code NotImplemented and message "operation DeregisterEventTopic is scaffolded but not implemented in this emulator" — services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/deregister_event_topic.rs still carries the SCAFFOLDED marker and its handle() body is `Err(crate::scaffolded::Scaffolded::not_implemented("DeregisterEventTopic"))`. The suite did NOT mark this check ALREADY FILED (the check catches the ClientError and asserts on its code, so no stub issue is carrying it), and no open or resolved stub issue names DeregisterEventTopic.
Why: the event-topic surface cannot be unregistered at all. A client can register a directory as an SNS publisher but never undo it, every teardown/cleanup path fails, and the 501 is outside the operation's modelled error set so an SDK cannot map it to any catchable exception class — code branching on EntityDoesNotExistException never runs.
Fix: implement the DeregisterEventTopic handler (src/ops/deregister_event_topic.rs) — resolve the DirectoryId against the directory store, refuse an unresolvable one with the modelled EntityDoesNotExistException carrying ds's not-found sentence and envelope suffix (reuse crate::state::no_such_directory / crate::state::refusal as register_event_topic.rs does), otherwise drop the directory→topic registration and answer 200 with the empty result; then delete the SCAFFOLDED marker line.
Traces: ds.register-event-topic-absent-directory-rejected (the RegisterEventTopic and DescribeEventTopics legs of this check pass; it fails at its DeregisterEventTopic leg).

Cause 2 of 3: CreateComputer against a directory that is not yet Active refuses with the right code but an emulator-invented message.
AWS: Smithy models CreateComputer errors AuthenticationFailedException / ClientException / DirectoryUnavailableException / EntityAlreadyExistsException / EntityDoesNotExistException / InvalidParameterException / UnsupportedOperationException (client, HTTP 400) and ServiceException (500); DirectoryUnavailableException = {Message: ExceptionMessage, RequestId: @pattern UUID}, documented "The specified directory is unavailable." The model does not state the text, so recorded behavior only: CreateComputer on a directory still provisioning (Stage is not Active) is refused 400 DirectoryUnavailableException whose Message is the directory not-found sentence plus the ds envelope suffix — "Directory: '<directory-id>' does not exist. : RequestId: <request-id>". Fixed text: "Directory: '", "' does not exist. : RequestId: "; variable parts: the DirectoryId from the request and the response's own request id (ds deliberately does not disclose the provisioning stage here).
Emulator: 400 DirectoryUnavailableException with "Directory <directory-id> is in stage <stage> and is not available for computer account changes : RequestId: <request-id>" — a sentence this crate authors (src/ops/create_computer.rs lines 193-205) that discloses the internal stage and uses neither AWS's wording nor its quoting of the id.
Why: a client or parity test that classifies ds failures on the service diagnostic (or scrapes the id out of it) never matches AWS, and the emulator leaks a stage value AWS does not report on this error class, so code written against the emulator reads a field of the message that is absent on real AWS.
Fix: the not-Active branch of the CreateComputer handler (src/ops/create_computer.rs) — build the DirectoryUnavailableException message from ds's shared not-found sentence (crate::state::no_such_directory) rather than a locally authored stage sentence. While re-replaying, note the legs of this check that have never been reached and are therefore ungraded: the Active-stage positive control (the response must echo ComputerName, a non-empty ComputerId and a ComputerAttributes entry re-cased to "Description") and the duplicate-name refusal, whose AWS message is the fixed "Could not create computer. RequestId: <request-id>" rather than this crate's "Directory <id> already holds the computer account <name>".
Traces: ds.create-computer-authentication-failed-rejected.

Cause 3 of 3: the enum-value-set ValidationException lists the allowed values in Smithy declaration order, not the order ds reports.
AWS: Smithy declares ClientAuthenticationType values in the order [SmartCard, SmartCardOrPassword] and UpdateType as [OS, NETWORK, SIZE]; the model says nothing about message rendering, so recorded behavior only: an out-of-vocabulary enum value is refused 400 ValidationException with "1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy enum value set: [<allowed>]", where <allowed> is ds's own fixed ordering of that enum's wire values — "SmartCardOrPassword, SmartCard" for ClientAuthenticationType and "SIZE, OS, NETWORK" for UpdateType, i.e. NOT the model's declaration order and not alphabetical. Fixed text: the "1 validation error detected: Value '", "' at '", "' failed to satisfy constraint: Member must satisfy enum value set: [", "]" frame and the per-enum value list; variable parts: the rejected value and the lowerCamel member name from the request.
Emulator: DescribeClientAuthenticationSettings(Type='SMART_CARD') is correctly refused 400 ValidationException at the right stage (before the DirectoryId is resolved) but renders "... enum value set: [SmartCard, SmartCardOrPassword]" — the model's declaration order — where ds sends "[SmartCardOrPassword, SmartCard]". The single-value LDAPSType leg ("[Client]") passes because order cannot differ there; the UpdateType leg ("[SIZE, OS, NETWORK]") is after the failing assertion and so is still ungraded, but the model order [OS, NETWORK, SIZE] predicts the same divergence.
Why: the error message is part of the contract. Any client, test or operator tooling that compares ds's validation diagnostic against AWS's text fails on an ordering the emulator derives from the model instead of from the service, and the enumerated remediation hint a caller is shown is not the one AWS shows.
Fix: the centralized input-validation constraint reporter that renders "Member must satisfy enum value set: [...]" for this service (the shared smithy server-runtime validation layer invoked on the deserialize→validate leg, which today emits the Smithy enum's declaration order) — render each ds enum's value list in the order ds reports it, pinned per enum rather than taken from model order.
Traces: ds.enum-wire-values-precede-resource-resolution.
