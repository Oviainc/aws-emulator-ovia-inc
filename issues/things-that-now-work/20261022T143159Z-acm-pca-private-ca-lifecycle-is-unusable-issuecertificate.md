# ACM PCA private-CA lifecycle is unusable: IssueCertificate refuses the documented root self-sign, GetCertificateAuthorityCsr is not a real PKCS#10, import/get-certificate/audit-report paths misclassify (6 causes)

> _Note: this issue was identified against the code base at commit `c73ebf67a23d923b166243bec836d38257c16c68`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IssueCertificate

## Description
Six distinct root causes on the acm-pca certificate path. Cause 1 blocks 62 of the suite's checks on its own: no CA in the emulator can ever be driven to ACTIVE, so every downstream capability (issuance, revocation, CRL, audit reports, policies, TLS) is unreachable.

=== Cause 1 of 6: IssueCertificate refuses the root-CA self-signing call against a PENDING_CERTIFICATE CA, so no CA can ever be activated ===
AWS: the documented root-CA installation sequence is GetCertificateAuthorityCsr -> IssueCertificate against the CA's OWN CertificateAuthorityArn with TemplateArn arn:aws:acm-pca:::template/RootCACertificate/V1 -> GetCertificate -> ImportCertificateAuthorityCertificate. That IssueCertificate call is made while the CA is still in PENDING_CERTIFICATE and AWS accepts it (HTTP 200, CertificateArn returned); it is the only way a CA leaves PENDING_CERTIFICATE. Smithy: IssueCertificate input {CertificateAuthorityArn @required, Csr @required (CsrBlob 1..32768), SigningAlgorithm @required, TemplateArn, Validity @required}, output CertificateArn; errors InvalidArgsException, InvalidArnException, InvalidStateException, LimitExceededException, MalformedCSRException, ResourceNotFoundException (all 400). The state gate is therefore template-sensitive: a leaf request (no TemplateArn / EndEntityCertificate/V1) against a PENDING_CERTIFICATE CA IS refused with InvalidStateException "The certificate authority is not in a valid state for issuing certificates" (that half of acm-pca.issue-certificate-not-ready-fails passes against the emulator), while a CA-certificate template against the CA's own CSR is permitted.
Emulator: every IssueCertificate against a PENDING_CERTIFICATE CA is refused, including the RootCACertificate/V1 self-sign, with 400 InvalidStateException "The certificate authority is not in a valid state for issuing certificates". Activation deadlocks: the CA can never be signed, so it can never become ACTIVE, so IssueCertificate can never be called.
Why: a client following the published root-CA bootstrap cannot stand up a private CA at all. Every acm-pca workflow beyond CreateCertificateAuthority/DescribeCertificateAuthority is dead, and the failure is indistinguishable from a legitimate state refusal, so clients retry forever instead of erroring out.
Fix: the IssueCertificate handler's CA-state guard (services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs) must admit PENDING_CERTIFICATE when the request is a CA-certificate template (RootCACertificate/*, SubordinateCACertificate*/*) signing that CA's own CSR, and the resulting certificate must be retrievable via GetCertificate and installable via ImportCertificateAuthorityCertificate so DescribeCertificateAuthority reports ACTIVE.
Traces: 62 failing checks, all failing on the same call inside their inlined _activate_root_ca helper (see trace_ids). Note several of them (the put-policy/delete-policy ones) will additionally need the already-filed PutPolicy/GetPolicy/DeletePolicy scaffold-stub issues, and two are cross-service checks reported under the composite tokens acm-pca__cloudwatch and acm-pca__iam whose failing call is this same acm-pca one.

=== Cause 2 of 6: GetCertificateAuthorityCsr returns a 250-byte blob that is not a valid PKCS#10 request ===
AWS: GetCertificateAuthorityCsr returns Csr (CsrBody, a string) holding a base64/PEM-armoured PKCS#10 CertificationRequest for the CA's generated key pair, carrying the CA's configured ASN1Subject and a SubjectPublicKeyInfo for the requested KeyAlgorithm. An RSA_2048 request with a populated subject decodes to well over 300 DER bytes and cryptography's load_pem_x509_csr(...).public_key() succeeds on it.
Emulator: the returned PEM decodes to 250 DER bytes and its SubjectPublicKeyInfo cannot be parsed — csr.public_key() raises "Could not deserialize key data ... ASN.1 parsing error: invalid length" / "... short data (needed at least 62 additional bytes)". It is a placeholder, not a real CSR.
Why: the subordinate-CA flow requires the caller to take this CSR to an external/parent CA and sign it. A client cannot parse, verify or sign this blob with any X.509 tooling, so subordinate CA enrolment and any CSR inspection is impossible, and the issued-certificate chain cannot be built.
Fix: the GetCertificateAuthorityCsr handler and the CA key/CSR generation in the service's CA state (services/service-com-amazonaws-acmpca-acmprivateca/src/ops/get_certificate_authority_csr.rs plus the CA-creation state that mints the key pair) must emit a real PKCS#10 request over a real generated key of the configured KeyAlgorithm, with the configured subject.
Traces: acm-pca.ca-csr-pem-structure-matches-requested-configuration, acm-pca.certificate-mismatch-import-rejected, acm-pca.server-side-ca-certificate-chain-auto-assembled.

=== Cause 3 of 6: ImportCertificateAuthorityCertificate accepts a certificate that does not match the CA's CSR ===
AWS: the imported certificate must correspond to the CA's outstanding CSR. A certificate carrying a different public key / key algorithm is refused 400 CertificateMismatchException (modeled: "The certificate authority certificate you are importing does not comply with conditions specified in the certificate that signed it."), with the recorded message "The certificate subject public key info field contains a different public key or key algorithm than the CA certificate signing request."; a certificate for a different subject is refused 400 CertificateMismatchException with "The certificate subject contains a different subject than the CA certificate signing request.". The CA stays in PENDING_CERTIFICATE. Smithy: ImportCertificateAuthorityCertificate errors include CertificateMismatchException and MalformedCertificateException, output is Unit.
Emulator: the mismatched import returns HTTP 200 with an empty body ({'HTTPStatusCode': 200, 'content-length': '2'}); nothing is verified.
Why: an emulator that installs any blob as the CA certificate lets a caller silently activate a CA with a certificate whose private key it does not hold. Everything the CA then signs is unverifiable, and the client's error path for a genuine key/subject mismatch is never exercised.
Fix: the ImportCertificateAuthorityCertificate handler (services/service-com-amazonaws-acmpca-acmprivateca/src/ops/import_certificate_authority_certificate.rs) must compare the submitted certificate's SubjectPublicKeyInfo and subject against the stored CSR and raise CertificateMismatchException (400) instead of succeeding.
Traces: acm-pca.import-ca-certificate-mismatched-key-rejected, acm-pca.import-certificate-mismatch-rejected.

=== Cause 4 of 6: a malformed certificate PEM is refused with MalformedCertificateException instead of the ValidationException pattern refusal ===
AWS: the Certificate member's PEM shape is enforced as a request-validation constraint before any semantic parse, so a malformed PEM is refused 400 ValidationException with "1 validation error detected: Value at 'certificate' failed to satisfy constraint: Member must satisfy regular expression pattern: -----BEGIN CERTIFICATE-----\r?\n([A-Za-z0-9/+]{64}\r?\n)*[A-Za-z0-9/+]{1,64}={0,2}\r?\n-----END CERTIFICATE-----(\r?\n)?." (recorded behavior; the pinned model has no pattern on CertificateBodyBlob, which is blob @length 1..32768, so MalformedCertificateException is reserved for a certificate that passes the shape check but fails to decode/verify).
Emulator: answers 400 MalformedCertificateException "Malformed certificate.".
Why: a client that branches on ValidationException (a schema fault, not retryable, not CA-specific) versus MalformedCertificateException (a semantic certificate fault) takes the wrong branch, and the response names neither the offending member nor the constraint.
Fix: add the shape/pattern validation stage for the Certificate member in the ImportCertificateAuthorityCertificate handler's validation, ahead of the certificate decode that raises MalformedCertificateException.
Traces: acm-pca.import-ca-certificate-malformed-rejected.

=== Cause 5 of 6: GetCertificate on a CA with no issued certificates answers RequestInProgressException instead of InvalidStateException ===
AWS: GetCertificate against a CA that is not yet in a state to have issued certificates is refused 400 InvalidStateException with "The certificate authority <arn> is not in the correct state to have issued certificates." RequestInProgressException is the distinct, retry-now signal meaning a requested certificate is still being minted. Smithy: GetCertificate errors are InvalidArnException, InvalidStateException, RequestFailedException, RequestInProgressException, ResourceNotFoundException (all 400).
Emulator: answers 400 RequestInProgressException "The request to create certificate authority is still in progress. Try again later."
Why: RequestInProgressException is the documented "retry" code and every AWS SDK waiter/poller loops on it. A client polling GetCertificate against a CA that will never have a certificate retries until its timeout instead of surfacing the state error immediately.
Fix: the GetCertificate handler's state classification (services/service-com-amazonaws-acmpca-acmprivateca/src/ops/get_certificate.rs) must distinguish "CA not in a state to have issued certificates" (InvalidStateException) from "this certificate is still being issued" (RequestInProgressException).
Traces: acm-pca.get-certificate-not-ready-fails.

=== Cause 6 of 6: CreateCertificateAuthorityAuditReport is an unimplemented scaffold stub ===
AWS: CreateCertificateAuthorityAuditReport against a CA that is not ready is refused 400 InvalidStateException with "The certificate authority <arn> is not in the correct state to have issued certificates.", and against an ACTIVE CA returns 200 with AuditReportId (@length 36, uuid pattern) and S3Key. Smithy: errors InvalidArgsException, InvalidArnException, InvalidStateException, RequestFailedException, RequestInProgressException, ResourceNotFoundException.
Emulator: answers the scaffold code NotImplemented ("operation CreateCertificateAuthorityAuditReport is scaffolded but not implemented in this emulator"), so neither the refusal nor the success path exists. This cause was NOT auto-attributed by the suite (the check compares the error code rather than letting the stub error escape), so no stub issue was filed for it.
Why: audit reporting is unavailable, and because the stub code is returned in place of InvalidStateException a client cannot tell a not-ready CA from a broken endpoint.
Fix: implement services/service-com-amazonaws-acmpca-acmprivateca/src/ops/create_certificate_authority_audit_report.rs, including the pre-ACTIVE InvalidStateException gate.
Traces: acm-pca.create-audit-report-not-ready-fails.
