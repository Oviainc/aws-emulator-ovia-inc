# xray: CancelTraceRetrieval refuses a case-mutated RetrievalToken with ResourceNotFoundException (404) instead of InvalidRequestException (400) — the integrity check is case-insensitive while the retrieval lookup is case-sensitive

## Description

ONE root cause (Cause 1 of 1). xray is bootstrapped and answering (106/125 xray checks pass in this run, bootstrap_signal false), so this is a fidelity defect, not a bootstrap gap.

Cause 1 of 1: the emulator's RetrievalToken integrity check compares case-INSENSITIVELY while the retrieval store is keyed case-SENSITIVELY, so a one-character mutation of a genuine token that changes only the CASE of a hex letter passes the pre-lookup gate as 'a token this service could have issued' and then misses the lookup, and the handler reports it as a retrieval that does not exist (404 ResourceNotFoundException) instead of as a malformed parameter (400 InvalidRequestException). Failing check: xray.start-trace-retrieval-unknown-destination-not-found.

AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models CancelTraceRetrieval as POST /CancelTraceRetrieval, input member RetrievalToken (target RetrievalToken, @required, @length min 0 max 1020), output CancelTraceRetrievalResult (empty body, HTTP 200), modeled errors InvalidRequestException (HTTP 400, defaulted) 'The request is missing required parameters or has invalid parameters', ResourceNotFoundException (HTTP 404) 'The resource was not found. Verify that the name or Amazon Resource Name (ARN) of the resource is correct', ThrottledException (HTTP 429). The model does not state which class a non-verifying token falls in, so the classification is recorded behavior only: the recording shows the RetrievalToken is INTEGRITY-CHECKED before any lookup, and that ANY in-place one-character mutation of a genuine token that preserves its length and its base64url alphabet — including a mutation that only changes a character's case, because the token alphabet is base64url and therefore case-SIGNIFICANT — is refused with HTTP 400 / InvalidRequestException and the message 'Invalid retrieval token <RetrievalToken> passed: Invalid execution id provided: <RetrievalToken>'. Fixed text of that message: 'Invalid retrieval token ' and ' passed: Invalid execution id provided: '; the only variable part is the request's RetrievalToken value, substituted TWICE (the inner clause is emitted by the execution-id decoder, which names the value it could not decode). HTTP 404 / ResourceNotFoundException is reserved for a token that DOES verify but names no live retrieval. Hypothesis: AWS embeds the execution id in the token with a self-check over the exact bytes, so any byte difference — case included — fails to decode before any job lookup happens.

Emulator: the handler's ordering is now right but its token predicate is too permissive. services/service-com-amazonaws-xray-awsxray/src/state.rs mints a RetrievalToken as RETRIEVAL_TOKEN_HEX_DIGITS = 32 LOWERCASE hex digits, identity half plus a check half from retrieval_token_check(identity) (ComAmazonawsXrayAwsxrayState::mint_retrieval_token). retrieval_token_defect() then lowercases the submitted value before recomputing the check ('let lowered = token.to_ascii_lowercase();'), deliberately treating a case-only difference as the SAME token, so it returns None for it. The handler (services/service-com-amazonaws-xray-awsxray/src/ops/cancel_trace_retrieval.rs lines 163-181) therefore skips the InvalidRequestException branch and falls through to store.cancel_trace_retrieval(&input.retrieval_token, now), which resolves the token with self.retrievals.get_mut(retrieval_token) — a case-SENSITIVE map keyed by the lowercase minted string. The case-mutated token is not found, the Err(None) arm fires, and the call is refused with ResourceNotFoundException (HTTP 404) and the message 'RetrievalToken `<token>` was not issued by this service, or its retrieval has timed out'. The two halves of the emulator thus disagree: the validator says the token is intact, the store says it was never issued, and the caller is handed the wrong error class. Because the mutation the check performs lands on the token's middle character, the divergence appears whenever that character is a hex LETTER (a-f) — the replacement picked from the base64url alphabet is 'A', a case-only change — and is masked whenever it is a digit, for which the replacement does change the value and the correct 400 is produced. So this is intermittent across runs by token value, not by environment.

Why: a client cannot tell a bad request from a missing resource. HTTP 400 InvalidRequestException is non-retryable and means 'fix the parameter'; HTTP 404 ResourceNotFoundException means 'the job is gone' and is exactly what SDK wrappers, console flows and cleanup helpers treat as benign and idempotent — this check's own helpers swallow ResourceNotFoundException. A token corrupted in transit or retyped with the wrong case therefore reads as a retrieval that already finished and vanished: callers silently stop cancelling real jobs, never surface the typo, and never see the offending token echoed. Every assertion downstream of the code (the exact message text, and that the genuine job stays uncancelled) is unreachable while the class is wrong, and the inconsistency is latent across all three token-consuming operations.

Fix: the shared token predicate in the operation's validation path, plus the store's key handling so the two agree — the handler's refusal ORDER and the store lookup itself are correct for the tokens that legitimately reach it. Either the integrity check must stop folding case (so a case-only mutation is classified UndecodableExecutionId and refused 400 InvalidRequestException with the integrity-failure message), or the retrieval map must be keyed by the same case-folded form the predicate accepts (so a case-only variant resolves to the genuine retrieval and is cancelled with HTTP 200); it must not be possible for a value to pass the predicate and then miss the lookup. The predicate and the refusal-message builder are shared with ListRetrievedTraces and GetRetrievedTracesGraph, whose currently-passing not-token-form wording must not regress.

That the check reached that assertion at all shows the whole setup path works at this commit: the logs resource policy, the destination switch to CloudWatchLogs/ACTIVE, PutTraceSegments and StartTraceRetrieval all succeeded and a genuine RetrievalToken was issued. The defect is confined to how CancelTraceRetrieval classifies a damaged token.

Mechanism, from the checkout (why the previous fix's gate does not catch this class):
- state.rs mint_retrieval_token builds a 32-digit LOWERCASE hex token: identity half + retrieval_token_check(identity).
- state.rs retrieval_token_defect: 'if token.len() != RETRIEVAL_TOKEN_HEX_DIGITS || !token.chars().all(|digit| digit.is_ascii_hexdigit()) { return Some(NotTokenForm); } let lowered = token.to_ascii_lowercase(); let (identity, check) = lowered.split_at(RETRIEVAL_TOKEN_HEX_DIGITS / 2); if retrieval_token_check(identity) == check { None } else { Some(UndecodableExecutionId) }'. 'A'..'F' are ascii hexdigits, and the lowercasing erases a case-only mutation, so the predicate answers None — 'a token this service could have issued'.
- state.rs cancel_trace_retrieval: 'let Some(retrieval) = self.retrievals.get_mut(retrieval_token) else { return Err(None); }' — the map is keyed by the lowercase minted string and the lookup is case-sensitive, so the uppercase variant is absent and Err(None) is returned.
- cancel_trace_retrieval.rs maps Err(None) to ResourceNotFoundException (404).
The check's mutation picks the first base64url character different from the original, i.e. 'A'; when the token's middle character is a hex letter the mutation is case-only and this path is taken (wrong code, 404), when it is a digit the value truly changes and the correct 400 is produced. Hence the divergence reproduces for a share of token values rather than every run, and the fix must remove the possibility rather than rely on a value.

Regression guards that pass in this run and must keep passing: xray.cancel-trace-retrieval-unknown-token-fails, xray.list-retrieved-traces-unknown-token-fails and xray.get-retrieved-traces-graph-unknown-token-fails (a string that is not of the issued form stays 400 / InvalidRequestException with the token substituted once).
