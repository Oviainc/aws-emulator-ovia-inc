# Config refusal messages: aggregator-not-found, SelectResourceConfig invalid-token and GROUP BY, and PutConnector Azure credential verification all use emulator-specific text (4 causes)

> _Note: this issue was identified against the code base at commit `21bca675a34dab10ee37fe0445fa59a838d6e2c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SelectResourceConfig

## Description
Every failure bundled here is a refusal whose HTTP status (400) and error CODE already match AWS, and whose MESSAGE is the only divergence. In each case the message is a requirement rather than an example, because it is the only signal that separates the leg from the other legs of the same operation that share one error code (and in two cases the check's own control proves the emulator reaches the right leg and then names it differently).

This is NOT covered by the open issue 20261023T140058Z-config-refusal-contract-validation-messages-report-one-violation.md: that issue's six causes are the shared constraint-validation message builder plus the tag-API, retention-configuration, GetCustomRulePolicy, aggregator-exclusivity and PutConfigRule messages. None of the four operations below (DescribeConfigurationAggregatorSourcesStatus, BatchGetAggregateResourceConfig, SelectResourceConfig, PutConnector) appears there, and none of the six check ids below is in its Issue-Trace-Ids. FOUR CAUSES must be closed.

Cause 1 of 4: NoSuchConfigurationAggregatorException interpolates the requested aggregator name instead of AWS's fixed, name-free sentence.
AWS: Smithy com.amazonaws.configservice#NoSuchConfigurationAggregatorException is errorKind client, httpError 400 (defaulted), doc "You have specified a configuration aggregator that does not exist."; it is modeled on both DescribeConfigurationAggregatorSourcesStatus and BatchGetAggregateResourceConfig. Recorded behavior: for an aggregator name that does not exist AWS returns the FIXED sentence "The configuration aggregator does not exist. Check the configuration aggregator name and try again." — with no aggregator name in it. Two independent checks, on two different operations and with two different randomly generated names, assert that identical constant, which is what establishes it as a fixed template rather than one recording's text.
Emulator: same code and status, but a request-interpolated template "The configuration aggregator '<name>' provided in the request does not exist. Please check the ConfigurationAggregatorName and try again." (observed with names sim2real-behav-cfg-absent-agg-4268d757ffa4 and sim2real-noagg-523e1434b417).
Why: AWS deliberately does not echo the caller's aggregator name for this error; a client matching AWS's sentence never matches, and anything parsing the message to recover the name gets a field AWS does not supply. NoSuchConfigurationAggregatorException is shared by many aggregator operations, so the sentence is the discriminator.
Fix: the NoSuchConfigurationAggregatorException message emitted by the aggregator-existence check, in the aggregator handlers / the shared aggregator lookup of the Config service (services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/describe_configuration_aggregator_sources_status.rs and .../src/ops/batch_get_aggregate_resource_config.rs).
Traces: config.aggregator-sources-status, config.batch-get-aggregate-resource-config-nonexistent-aggregator-rejected.

Cause 2 of 4: SelectResourceConfig's InvalidNextTokenException message.
AWS: Smithy InvalidNextTokenException is errorKind client, httpError 400 (defaulted), modeled on SelectResourceConfig, doc "The specified next token is not valid. Specify the nextToken string that was returned in the previous response to get the next page of results." Recorded behavior: a forged NextToken is refused with the fixed sentence "The nextToken provided is invalid".
Emulator: correct code InvalidNextTokenException, but the message "the specified NextToken is not valid; use the NextToken a previous SelectResourceConfig response returned".
Why: the same check's other leg shows the emulator DOES implement AWS's validation template where it is required (Limit=101 was refused with exactly "1 validation error detected: Value '101' at 'limit' failed to satisfy constraint: Member must have value less than or equal to 100", which passed), so this is an isolated per-handler wording divergence rather than a missing validator. A client keyed on AWS's pagination-error sentence does not match, and SelectResourceConfig is a data-plane paging API where clients commonly branch on that text.
Fix: the InvalidNextTokenException message in the SelectResourceConfig handler's pagination-token decoder (.../src/ops/select_resource_config.rs).
Traces: config.select-resource-config-limit-and-next-token-rejected.

Cause 3 of 4: SelectResourceConfig's InvalidExpressionException message for a GROUP BY that does not cover a projected field.
AWS: Smithy InvalidExpressionException is errorKind client, httpError 400 (defaulted), modeled on SelectResourceConfig, doc "The syntax of the query is incorrect." Recorded behavior for "SELECT resourceId GROUP BY resourceType": InvalidExpressionException with a message built from the request — it names the rule and the offending SELECTED fields in parentheses: "when a GROUP BY clause or Aggregate Function (AVG|COUNT|MAX|MIN|SUM) is present, selected fields (resourceId) must appear in the GROUP BY field list".
Emulator: correct code InvalidExpressionException, but "The expression is not a valid Config query: the property 'resourceId' is selected beside an aggregate, so the query must group by it."
Why: InvalidExpressionException is the single code for every semantic-analyser refusal of this operation (unprojected GROUP BY field, non-aggregatable aggregate, unknown function), so the message is the only thing telling a caller which rule it broke and which field to fix. The emulator's semantic analyser is otherwise reaching the right verdict here — the unknown-property leg of the same check passed (an unknown property is accepted, echoed in QueryInfo.SelectFields and omitted from the rows) — so only the refusal text diverges.
Fix: the InvalidExpressionException message built by SelectResourceConfig's expression semantic analyser (.../src/ops/select_resource_config.rs and the expression/analyser module behind it).
Traces: config.select-resource-config-unknown-property-rejected.

Cause 4 of 4: PutConnector's Azure credential-verification ValidationException message.
AWS: Smithy PutConnector takes a required ConnectorConfiguration and models ConflictException, InsufficientPermissionsException, MaxNumberOfConnectorsExceededException and ValidationException (all errorKind client, httpError 400 defaulted). Recorded behavior only: PutConnector(azure) validates the identifier pair in stages, and a GUID-shaped but unregistered tenantIdentifier/clientIdentifier pair passes shape validation and is then refused by the credential-verification stage with the fixed sentence "Unable to verify Azure credentials for the provided tenant configuration." Two independent checks assert that identical constant.
Emulator: correct code ValidationException and the correct staging — the non-GUID pair is refused "Invalid tenant identifier" and the GUID-shaped pair is refused with a DIFFERENT message, and no connector is left behind (ListConnectors count unchanged, and both concurrent racers were refused identically) — but the credential-verification sentence is "Unable to verify Azure credentials for the connector".
Why: all of PutConnector's refusal legs share ValidationException, so the sentence is the only way a client can tell the shape-validation refusal from the credential-verification refusal; the checks assert exactly that discrimination. A client keyed on AWS's text cannot classify the failure.
Fix: the ValidationException message for the Azure credential-verification stage in the PutConnector handler (.../src/ops/put_connector.rs).
Traces: config.concurrent-put-connector-name-race, config.put-connector-max-number-exceeded-blocked.
