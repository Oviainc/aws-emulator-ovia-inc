# signin: resource-policy and console-authorization operations unreachable (emulator announces public signin.<region>.api.aws), router refuses 'iam' as AmbiguousService, and OAuth2 validation diverges (5 causes)

> _Note: this issue was identified against the code base at commit `872e0ddf6cb614931de58689afe8393c02abd052`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetResourcePolicy, ListResourcePermissionStatements, PutResourcePermissionStatement, DeleteResourcePermissionStatement, GetConsoleAuthorizationConfiguration, PutConsoleAuthorizationConfiguration, DeleteConsoleAuthorizationConfiguration, RevokeOAuth2TokenWithIAM, IntrospectOAuth2TokenWithIAM, CreateOAuth2TokenWithIAM

## Description
Five distinct root causes in the signin emulator, all grounded in failing checks of the simparity-behavioral-aws-v1 behavioral suite (signin scored 0/19). The emulator IS serving signin (the /v1/* OAuth2 paths answer with emulator-generated errors), so these are fidelity defects, not a bootstrap gap. A fixer must close ALL FIVE causes below before submitting.

Note on scope: two further failures in this suite (signin.create-oauth2-token-with-iam-rotates-access-token and signin.revoke-oauth2-token-with-iam-idempotent-on-repeat, plus the checks they block) are already filed as unimplemented-scaffold-stub issues for CreateOAuth2TokenWithIAM / IntrospectOAuth2TokenWithIAM and are intentionally NOT part of this issue. Causes 4 and 5 below are independent of those stubs for the assertion they diverge on, but their positive controls also need those stubs implemented.

=== Cause 1 of 5: resource-policy operations never reach the endpoint under test; the SDK is sent to the public AWS host signin.us-west-2.api.aws ===
AWS: GetResourcePolicy (POST /get-resource-policy), ListResourcePermissionStatements (POST /list-resource-permission-statements), PutResourcePermissionStatement (POST /put-resource-permission-statement) and DeleteResourcePermissionStatement (POST /delete-resource-permission-statement) are ordinary restJson1 operations on the signin endpoint for the caller's own region; the recordings show them answering with ResourceNotFoundException / ValidationException / AccessDeniedException bodies (Smithy: signin 2023-01-01, restJson1, endpointPrefix 'signin'; these four ops are bound to the service and model ResourceNotFoundException httpError 404, ValidationException httpError 400).
Emulator: a client built exactly like the one the OAuth2 checks use successfully (default region, same ctx.client("signin")) is directed to the host 'signin.us-west-2.api.aws' for these four operations, and the run's egress guard refuses it: "egress refused: 'signin.us-west-2.api.aws' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on". The request therefore never reaches the emulator and no response is produced. Hypothesis: the resource-policy route either answers with a redirect/Location (or an endpoint field) carrying the public regional host, or is not registered on the served endpoint at all so endpoint resolution falls back to the public ruleset host; the distinguishing evidence is that the OAuth2 paths on an identically-constructed client DO reach 127.0.0.1, so the divergence tracks the operation, not the client.
Why: every client of the signin resource-based-policy surface is silently pointed at real AWS instead of the emulator. Nothing about the policy surface can be exercised; in a sandboxed run the call fails at the transport, and in a network-permitted run it would escape to the real service.
Fix: the signin service's endpoint/route registration and any endpoint announcement for these four operations (the service crate's router/endpoint wiring at services/service-com-amazonaws-signin-signin, plus the ops handlers for get_resource_policy / list_resource_permission_statements / put_resource_permission_statement / delete_resource_permission_statement). Every URL the emulator announces must be the endpoint it is reached on.
Traces: signin.delete-resource-permission-statement-invalid-sid-rejected, signin.get-resource-policy-not-found-without-statements, signin.list-resource-permission-statements-baseline-empty-shape, signin.put-resource-permission-statement-access-denied-without-permission.

=== Cause 2 of 5: console-authorization operations unreachable from a us-east-1 client; the SDK is sent to signin.us-east-1.api.aws ===
AWS: PutConsoleAuthorizationConfiguration (POST /put-console-authorization-configuration, idempotent), GetConsoleAuthorizationConfiguration (POST /get-console-authorization-configuration, readonly) and DeleteConsoleAuthorizationConfiguration (POST /delete-console-authorization-configuration) answer on the signin endpoint; the write operations are region-locked to us-east-1 (recorded behavior: a write from another region is a ValidationException 'Write operations only supported in us-east'), so clients legitimately target region us-east-1. Smithy: Put models ConflictException 409 / ResourceNotFoundException 404 / ValidationException 400, Get and Delete model ResourceNotFoundException 404, and all three return {targetId, scope, consoleAuthorizationEnabled} (all required).
Emulator: a signin client for region us-east-1 is directed to 'signin.us-east-1.api.aws' and the run's egress guard refuses it with the same message as Cause 1. No console-authorization request reaches the emulator, so the whole lifecycle (put -> get enabled -> delete reports consoleAuthorizationEnabled=false -> get/delete raise ResourceNotFoundException) is unverifiable.
Why: a client that follows AWS's own region-locking rule for this surface is pointed away from the emulator entirely; the emulated service appears to have no us-east-1 presence even though it is reached on one endpoint.
Fix: the signin service's endpoint/region routing so that every region the service accepts (notably us-east-1, the only region that accepts these writes) is served on the endpoint under test, plus the console-authorization handlers' own announcement of any URL (services/service-com-amazonaws-signin-signin ops put/get/delete_console_authorization_configuration).
Traces: signin.put-get-console-authorization-configuration-enables, signin.get-console-authorization-configuration-not-found-when-unset, signin.console-authorization-configuration-disabled-after-delete, signin.console-authorization-configuration-full-lifecycle-workflow, signin.put-console-authorization-configuration-double-put-conflict-rejected, signin.put-console-authorization-configuration-nonexistent-org-rejected.

=== Cause 3 of 5: the router refuses sigv4 'iam' requests with a non-AWS AmbiguousService body, so a signin check that must mint an IAM principal cannot run ===
AWS: IAM operations (CreateUser, PutUserPolicy, CreateAccessKey) answer on the iam endpoint with the awsQuery/XML protocol; a well-formed CreateUser returns 200 with a CreateUserResponse XML document, and any error is an XML ErrorResponse with an AWS error code.
Emulator: the request is answered with HTTP body {"__type":"AmbiguousService","message":"2 emulated services all claim requests for 'iam': iam, iam; the request is rejected rather than served by an arbitrary one"} — a JSON envelope on an XML-protocol service, so botocore cannot even parse it: botocore.parsers.ResponseParserError: Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received. Two registrations claim the same 'iam' sigv4 signing name and the router refuses rather than choosing.
Why: no caller can obtain an IAM principal, so every behavioral contract that depends on a second identity (here, signin's resource-permission-statement authorization contract) is unreachable, and the error is not representable in any SDK's error model.
Fix: the emulator's service-registration/routing layer (resolve the duplicate 'iam' signing-name registration to exactly one served service), and the fallback error serializer so a router-level refusal is encoded in the target service's protocol rather than as a JSON __type body. Related open issues report the same router defect from other services' suites — 20261021T234042Z-osis-router-refuses-every-sigv4-iam-request-as-ambiguousservice.md and 20261022T002237Z-ecr-router-refuses-every-iam-and-every-signer-sigv4.md — but neither carries this check's replay key, so this cause is filed here for the signin surface.
Traces: signin.put-resource-permission-statement-concurrent-same-token-idempotent.

=== Cause 4 of 5: RevokeOAuth2TokenWithIAM rejects an empty token with 400 ValidationException instead of the idempotent-safe 200 no-op ===
AWS: recorded behavior only — with client-side parameter validation disabled so the value actually reaches the wire, RevokeOAuth2TokenWithIAM(token="") is accepted as a no-op and returns HTTP 200 with an empty body (the operation is @idempotent and models an empty output; RFC 7009 revocation is idempotent-safe). The recording also shows the asymmetry: IntrospectOAuth2TokenWithIAM on the same empty token IS rejected with ValidationException. Smithy: RevokeOAuth2TokenWithIAM.token is @required with @length min 1 / @pattern ^ASOR[A-Za-z0-9+/=_\-]+$ and the op returns http 200 — i.e. the model's input constraints are stricter than the service's actual acceptance for this operation.
Emulator: the request is rejected with HTTP 400 ValidationException (example message: "2 validation errors detected: Value '' at 'token' failed to satisfy constraint: Member must have length greater than or equal to 1; Value '' at 'token' failed to satisfy constraint: Member must satisfy regular expression pattern: ^ASOR[A-Za-z0-9+/=_\-]+$"). The generic model-constraint layer answers before the handler, so the revoke-is-a-no-op contract never executes.
Why: a client that relies on revocation being safe to repeat (RFC 7009 / AWS's own behavior) gets a hard 400 where AWS returns 200, turning an idempotent cleanup path into an error path.
Fix: RevokeOAuth2TokenWithIAM's handler/validation (services/service-com-amazonaws-signin-signin ops revoke_o_auth2_token_with_iam) must own token acceptance for this operation — a token that does not match the revocation shape (including the empty string and an ASOA access-token-shaped value) is a 200 no-op that revokes nothing, rather than a generic constraint rejection.
Traces: signin.revoke-oauth2-token-with-iam-wrong-prefix-rejected.

=== Cause 5 of 5: input rejection is produced by the generic Smithy constraint reporter instead of the operation's own validation, so the error payload is the framework's multi-error report rather than the operation's field-specific message ===
AWS: recorded behavior only (the model documents neither message). Both recordings show a ValidationException whose message is produced by the operation's own validation and names the single offending condition, never a generic constraint listing: CreateOAuth2TokenWithIAM with an unsupported grantType answers with the OAuth2 invalid_request description "The request is missing a required parameter, includes an invalid parameter value, or is otherwise malformed." (example), and IntrospectOAuth2TokenWithIAM with a value not shaped like a Sign-In token answers "token has invalid format" (example); the companion recording in Cause 4 shows Introspect on an empty token answering "token is required" (example). The HTTP status (400) and the error code (ValidationException) match in all cases — the divergence is the payload's origin and shape. Smithy: CreateOAuth2TokenWithIAM.grantType @pattern ^client_credentials$; IntrospectOAuth2TokenWithIAM.token @pattern ^ASO[AR][A-Za-z0-9+/=_\-]+$, both modeling ValidationException httpError 400.
Emulator: the generic constraint validator short-circuits the handler and emits its own report, e.g. "1 validation error detected: Value 'authorization_code' at 'grantType' failed to satisfy constraint: Member must satisfy regular expression pattern: ^client_credentials$" and "1 validation error detected: Value 'not-a-signin-token-at-all' at 'token' failed to satisfy constraint: Member must satisfy regular expression pattern: ^ASO[AR][A-Za-z0-9+/=_\-]+$".
Why: a client that branches on the OAuth2 error description (or surfaces it to an end user) sees a framework constraint dump instead of the service's documented invalid_request/field message; more importantly, because the generic layer answers first, operation-specific acceptance rules (Cause 4) can never run.
Fix: move input rejection for the signin OAuth2 operations into their handlers/validation (services/service-com-amazonaws-signin-signin ops create_o_auth2_token_with_iam and introspect_o_auth2_token_with_iam) so each emits its own single-condition ValidationException message, and stop the generic constraint reporter from pre-empting them. Note both of these checks also need the already-filed CreateOAuth2TokenWithIAM / IntrospectOAuth2TokenWithIAM scaffold stubs implemented for their positive controls.
Traces: signin.create-oauth2-token-with-iam-wrong-grant-type-rejected, signin.introspect-oauth2-token-with-iam-malformed-token-rejected.
