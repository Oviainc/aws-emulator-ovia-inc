# eks: 4 net-new root causes — CreateCapability refuses the capabilities.eks service principal, the deleted-CA 404 sentence, an unusable certificateAuthority.data and UpdateNodegroupConfig's scaling refusal wording

> _Note: this issue was identified against the code base at commit `6596661b7bed7b2c68eacfc83c0e7a703969540b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCapability

## Description
Four net-new root causes under the `eks` suite heading, clustered from the failing behavioral checks that the replay report did not mark ALREADY FILED or OWNED. A fixer must close ALL FOUR before submitting. Every name, id, ARN, cluster name and number quoted below is a template slot filled from the request or the emulator's own state, never a literal requirement.

Cause 1 of 4: CreateCapability refuses a roleArn whose trust policy allows the EKS *capabilities* service principal.
  AWS: Smithy: CreateCapability (POST /clusters/{clusterName}/capabilities) requires `roleArn`, documented as "the IAM role that the capability uses to interact with Amazon Web Services services. This role must have a trust policy that allows the EKS service principal to assume it"; its errors include InvalidParameterException (400). The service principal a capability role must trust is `capabilities.eks.amazonaws.com` with Action [sts:AssumeRole, sts:TagSession] (recorded behavior: all three checks build exactly that trust policy and real AWS accepts the create, returning a capability in CREATING). A roleArn refusal is reserved for a role that is absent or that trusts neither.
  Emulator: InvalidParameterException with message `roleArn Nonexistent role or missing eks service principal in trust policy: <roleArn>` for a role the harness had just created through the emulator's own IAM with the `capabilities.eks.amazonaws.com` trust policy. The handler resolves the trust policy against the single constant `EKS_SERVICE_PRINCIPAL` (`eks.amazonaws.com`), so a correct capability role can never satisfy it.
  Why: the entire capability surface is unreachable for a client that follows AWS's documented trust policy. Checks that only use CreateCapability as a positive control abort there, and a check that retries the trust-policy refusal (believing it is IAM propagation lag) burns its whole retry window and then reports the refusal instead of the behavior under test.
  Fix: CreateCapability's roleArn validation (the `state::service_principal_trust_violation` call in services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_capability.rs, lines 381-390) must accept the capabilities service principal for capability roles, not only `eks.amazonaws.com`.
  Also blocked behind this refusal, and still asserted by these checks once it is lifted (recorded behavior; stated here so the fixer does not stop at the create): the malformed-capabilityName refusal message must be `Capability name must start with a letter or number and contain only letters, numbers, hyphens, and underscores` (whole sentence fixed text) rather than the handler's `capabilityName must be a non-empty string of alphanumeric characters, hyphens and underscores, got <value>`; and a type/configuration mismatch (an `argoCd` configuration on a `type=ACK` capability) must be refused InvalidParameterException with `Mismatch between capability type and configuration` (whole sentence fixed text) rather than the handler's `configuration.argoCd applies only to a capability of type ARGOCD, not to type ACK`.
  Note: open issue 20261104T105252Z-eks-10-net-new-root-causes-unvalidated-pod.md, Cause 10, describes this refusal as "CreateCapability refuses a role that exists and trusts EKS" and lists two of these check ids; it does not name the principal mismatch that causes it, and the replay report leaves these three checks unowned. This cause is the precise defect behind it.
  Traces: eks.capability-malformed-name-rejected, eks.create-capability-unsupported-type-rejected (both: "create_capability never accepted the role's trust policy: An error occurred (InvalidParameterException) ... roleArn Nonexistent role or missing eks service principal in trust policy: <arn>"), eks.create-capability-argocd-config-on-ack-type-rejected (the trust-policy retry loop exhausts, so the check sees code InvalidParameterException with no captured message).

Cause 2 of 4: the not-found refusal for a deleted certificate authority is an emulator-authored sentence, not EKS's wrapped not-found message.
  AWS: DescribeCertificateAuthority on a certificate-authority id that has been deleted answers ResourceNotFoundException (404) whose message is the wrapped backend message `certificate authority not found (Service: EksCertificateAuthority, Status Code: 404, Request ID: <request-id>) (SDK Attempt Count: 1)` — fixed text `certificate authority not found (Service: EksCertificateAuthority, Status Code: 404, Request ID: ` ... `) (SDK Attempt Count: 1)`, with only the request id varying per call (recorded behavior: both checks assert the prefix and the suffix and deliberately never pin the request id).
  Emulator: the error code is right (ResourceNotFoundException) but the message is its own sentence `No certificate authority found with id: <certificateAuthorityId> for cluster: <clusterName>.`
  Why: a client that matches on EKS's message text (or that parses the wrapped backend identity out of it) does not recognise the refusal; the emulator's sentence also claims a different error provenance than the one AWS reports.
  Fix: the certificate-authority not-found renderer behind services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/describe_certificate_authority.rs (and the shared message it takes from src/state.rs), so every deleted/unknown-CA 404 carries EKS's wrapped sentence.
  Note: open issues 20261105T111015Z-eks-describecertificateauthority-s-deleted-unknown-ca-404-uses.md and 20261103T041817Z-eks-describecertificateauthority-reports-an-unknown-deleted-certificate-authority.md describe the same wording for other checks; the replay report leaves these two checks unowned, so they are filed here and those issues are named rather than assumed to cover them.
  Traces: eks.certificate-authority-delete-while-active-blocked, eks.e2e-certificate-authority-activation-to-teardown (both fail on the `describe_msg.startswith(...)` assertion with the emulator sentence shown above; every earlier assertion in those checks — the ResourceInUseException refusal of the active signer and its message — passed).

Cause 3 of 4: cluster.certificateAuthority.data is a placeholder, not a Base64-encoded PEM certificate, so no TLS client can reach the cluster.
  AWS: Smithy: Certificate.data is "The Base64-encoded certificate data required to communicate with your cluster. Add this to the certificate-authority-data section of the kubeconfig file for your cluster." Base64-decoding it yields a PEM X.509 certificate that verifies the endpoint the same DescribeCluster response advertises, so a kubeconfig built from DescribeCluster works with kubectl and with any verifying HTTPS client.
  Emulator: the decoded value is not a PEM block. Every client fails identically: `kubectl get nodes -o json` exits 1 with `error: unable to load root certificates: unable to parse bytes as PEM block`, and python's `ssl_ctx.load_verify_locations(cadata=ca_pem)` raises `ssl.SSLError: no start line: cadata does not contain a certificate`.
  Why: the Kubernetes data plane is unreachable by any client that verifies TLS, which is every client built from EKS's own kubeconfig output — pod identity credential scoping, HPA scaling, node listing and every kubectl-driven behavior cannot be exercised at all.
  Fix: the cluster's certificateAuthority state/serializer must emit the Base64-encoded PEM certificate of the CA that signs the served Kubernetes endpoint (src/state.rs cluster record + the DescribeCluster projection).
  Also in this cause: eks.deploy-eks-cluster-cloudformation-active gets as far as a CREATE_COMPLETE stack with status ACTIVE, an `https://` endpoint and non-empty certificateAuthority.data, then never gets any HTTP status back from an unauthenticated `GET <endpoint>/version` — AWS answers that probe 401 with a body `{"kind": "Status", "reason": "Unauthorized", ...}`. Hypothesis: the probe builds its TLS context from the same certificateAuthority.data and `ssl.SSLError` is an `OSError` subclass, so the handshake failure is reported as "no status"; if the CA fix alone does not make that probe answer 401, the advertised endpoint is also serving no Kubernetes API (the condition open issue 20261104T105252Z-eks-10-net-new-root-causes-unvalidated-pod.md describes as its Cause 9) and that must be closed too.
  Note: the same placeholder is already described, for other checks and other service headings, in open issues 20261104T105252Z-eks-10-net-new-root-causes-unvalidated-pod.md (Cause 8), 20261104T060239Z-ecr-eks-logs-a-cluster-s-certificateauthority-data.md, 20261104T105252Z-eks-logs-the-cluster-s-certificateauthority-data-is.md and 20261104T053901Z-eks-auth-the-whole-pod-identity-data-plane.md. The five checks listed below are reported unowned under the `eks` heading, so they are filed here.
  Traces: eks.hpa-min-replicas-above-max-replicas-rejected, eks.hpa-scales-out-under-cpu-load-and-back-in-when-it-stops, eks.hpa-target-without-a-cpu-request-is-blocked-from-scaling (all three: `DATAPLANE_UNIMPLEMENTED: command failed (rc=1): kubectl get nodes -o json / stderr: error: unable to load root certificates: unable to parse bytes as PEM block`), eks.eks-pod-identity-credentials-are-scoped-and-an-unallowed-bucket-is-denied (`ssl.SSLError: no start line: cadata does not contain a certificate (_ssl.c:3977)`), eks.deploy-eks-cluster-cloudformation-active (`condition not met within 90.0s, last observed: (None, {})` from the unauthenticated /version probe).

Cause 4 of 4: UpdateNodegroupConfig's scalingConfig refusal is worded by the emulator instead of by EKS.
  AWS: Smithy: UpdateNodegroupConfig (POST /clusters/{clusterName}/node-groups/{nodegroupName}/update-config) declares InvalidParameterException (400). A scalingConfig whose minSize exceeds desiredSize is refused InvalidParameterException with `Minimum capacity <minSize> can't be greater than desired size <desiredSize>` — fixed text `Minimum capacity ` / ` can't be greater than desired size `, with the two numbers taken from the request (recorded behavior; the check sends minSize 5, maxSize 4, desiredSize 1).
  Emulator: the error code is right (InvalidParameterException) but the message is the emulator's own constraint restatement: `scalingConfig must satisfy minSize <= desiredSize <= maxSize, got minSize 5, desiredSize 1, maxSize 4`.
  Why: a client that surfaces or matches EKS's refusal text gets a sentence AWS never produces; the emulator also reports a different failing rule (the full three-way ordering) than the one AWS names (minimum vs desired).
  Fix: UpdateNodegroupConfig's scalingConfig validation message in services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/update_nodegroup_config.rs — word each ordering violation as EKS words it.
  Note: open issue 20261104T105252Z-eks-9-net-new-root-causes-in-parameter.md covers the sibling CreateNodegroup/scaling-range wording and owns other checks; this UpdateNodegroupConfig path is reported unowned.
  Traces: eks.nodegroup-update-config-lifecycle (`AssertionError: unexpected message 'scalingConfig must satisfy minSize <= desiredSize <= maxSize, got minSize 5, desiredSize 1, maxSize 4'`; the immediately preceding assertions — UpdateNodegroupVersion on an absent nodegroup answering ResourceNotFoundException "The requested resource does not exist." — passed).
