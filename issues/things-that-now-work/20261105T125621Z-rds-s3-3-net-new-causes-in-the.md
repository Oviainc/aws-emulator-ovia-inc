# rds__s3: 3 net-new causes in the DB instance engine endpoint — its SQLite SQL engine refuses CREATE EXTENSION, CREATE DATABASE and a no-op COMMIT, and reports SQLite's text under the wrong error classes

> _Note: this issue was identified against the code base at commit `9de1430d35a30df63dfe38bccf7c2cf4feacacf3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
Three net-new root causes, all in the DB instance DATA plane that `CreateDBInstance` publishes as `Endpoint{Address,Port}` and that `services/service-com-amazonaws-rds-amazonrdsv19/src/state/data_plane.rs` opens a listener for. The listener itself now works (sessions open and SQL executes, so the fixed issue `human-rds-the-published-db-instance-endpoint-refuses-every-engine.md` did land) — what diverges now is the statement layer: `src/state/data_plane/sql_engine.rs` runs each statement against an in-process SQLite database and renders SQLite's own refusal on the engine wire, so three statements that succeed on Amazon RDS come back as errors, with SQLite's message text and an error class/number neither engine uses. Every rds__s3 native import/export flow stops at the first of these statements. No open issue in this repository carries these nine check ids; the nearest open ones (`20261105T074335Z-rds-s3-a-provisioned-db-instance-s-reported.md` and `20261104T053605Z-rds-the-published-db-instance-cluster-endpoint-serves.md`) are about an endpoint that serves NO wire protocol at all, which is no longer what happens here.

Cause 1 of 3: RDS for PostgreSQL refuses `CREATE EXTENSION`, so the aws_s3 extension can never be installed.
AWS: recorded behavior only for the engine wire — the Smithy control-plane model describes `Endpoint`, not SQL. Amazon RDS for PostgreSQL ships the `aws_s3` extension, and AWS documents installing it exactly as the checks do: a session authenticated as the master user runs `CREATE EXTENSION IF NOT EXISTS aws_s3 CASCADE`, which succeeds and (because of CASCADE) also installs its `aws_commons` dependency; `IF NOT EXISTS` makes a repeat a no-op notice rather than an error. Only after that do `aws_s3.table_import_from_s3` and `aws_s3.query_export_to_s3` exist. PostgreSQL's refusals for this statement class are `ERROR:  extension "<name>" is not available` (SQLSTATE 0A000 feature_not_supported) or `ERROR:  permission denied to create extension "<name>"` (42501) — the fixed text with the extension name taken from the request. PostgreSQL never answers a syntax error positioned at the keyword EXTENSION, and never SQLSTATE class 58 (system_error).
Emulator: the statement is handed straight to the per-instance SQLite database, which has no CREATE EXTENSION grammar, and SQLite's parse error is returned on the PostgreSQL wire: psycopg raises `psycopg.errors.SystemError: near "EXTENSION": syntax error in CREATE EXTENSION IF NOT EXISTS aws_s3 CASCADE at offset 7`. `SystemError` is psycopg's mapping of SQLSTATE class 58, so both the outcome (error instead of success) and the error class are wrong, and the message is SQLite's `near "...": syntax error ... at offset N` wording rather than any PostgreSQL sentence.
Why: a client following AWS's documented procedure for RDS-for-PostgreSQL↔S3 integration cannot get past step one. aws_s3 import/export, and any application or migration that installs an extension (pgcrypto, postgis, uuid-ossp, aws_commons), fails on a server that reports itself as a PostgreSQL instance in state `available`. The 58-class error also tells the client the server is broken rather than that the feature is unavailable, so driver and ORM retry logic reacts wrongly.
Fix: the RDS data plane's SQL statement layer — `src/state/data_plane/sql_engine.rs` (the SQLite-backed executor) together with `src/state/data_plane/wire_session.rs`, which already intercepts server commands (`SHOW`, `SET`) before the engine sees them: CREATE EXTENSION belongs in that interception as a recorded per-instance extension registry, and whatever is still refused must be refused with the PostgreSQL error the condition calls for, not with SQLite's parse error under class 58.
Traces: rds__s3.cfn-rds-load-from-s3-role-missing-read-policy-negative, rds__s3.deploy-rds-instance-missing-associated-role-negative, rds__s3.rds-s3-import-missing-role-association-negative.

Cause 2 of 3: RDS for MySQL refuses `CREATE DATABASE`.
AWS: recorded behavior only for the engine wire. On RDS for MySQL and MariaDB the master user holds CREATE, and `CREATE DATABASE <name>` creates the schema and answers an OK packet (errno 0). The modelled refusals for this statement are MySQL's own: a name that already exists is errno 1007 ER_DB_CREATE_EXISTS, `Can't create database '<name>'; database exists`, with the name taken from the statement; a denied user is errno 1044 ER_DBACCESS_DENIED_ERROR. A statement MySQL genuinely cannot parse is errno 1064 ER_PARSE_ERROR worded `You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near '<offending text>' at line <n>`. MySQL never answers errno 1105 ER_UNKNOWN_ERROR for DDL it supports.
Emulator: `pymysql.err.OperationalError: (1105, 'near "DATABASE": syntax error in CREATE DATABASE <name> at offset 7')` — SQLite has no CREATE DATABASE, and its parse-error text is returned verbatim under the catch-all errno 1105. The schema is never created, so every statement the check runs inside it fails too.
Why: a client cannot create a schema on an instance the control plane reports as `available`, so no migration, no test fixture and no snapshot-then-export flow can set up its data. Because the error arrives as 1105 rather than 1007/1044/1064, a client cannot tell "already exists" from "denied" from "unsupported" and cannot make its create idempotent.
Fix: same component — `src/state/data_plane/sql_engine.rs` must map MySQL schema DDL onto per-instance schema state (or refuse it with the MySQL error the condition calls for), and `src/state/data_plane/mysql_wire.rs` must stop rendering a SQLite error string under errno 1105.
Traces: rds__s3.rds-export-task-parquet-format-schema-preserved, rds__s3.rds-export-task-partial-table-list-positive.

Cause 3 of 3: on the MySQL wire, COMMIT with no explicit transaction open is refused instead of being a successful no-op.
AWS: recorded behavior only for the engine wire. With `autocommit` on — the RDS for MySQL/MariaDB default — `COMMIT` issued when no explicit transaction is open is a successful no-op: the server answers OK with errno 0. This is not an edge case a client opts into: PyMySQL (and JDBC, and most pooling layers) call `Connection.commit()` after a statement batch whether or not a transaction was begun. MySQL defines no error code for "commit without an active transaction", and errno 1064 ER_PARSE_ERROR specifically means the server could not parse the statement — COMMIT parses.
Emulator: `pymysql.err.ProgrammingError: (1064, 'cannot commit - no transaction is active')` — the SQLite connection's own refusal (the per-instance connection is shared by all sessions, so no transaction is open at that point) is surfaced as errno 1064 with SQLite's message. The driver raises, and the check dies before it can snapshot or export.
Why: every ordinary client that commits defensively gets a hard failure on a healthy connection, and the 1064 classification tells it the SQL was malformed. This makes the MySQL data plane unusable by unmodified drivers regardless of what the client's SQL is.
Fix: the transaction handling in `src/state/data_plane/sql_engine.rs` / `src/state/data_plane/wire_session.rs` — COMMIT and ROLLBACK with no open transaction must answer OK on the MySQL wire (and PostgreSQL's `WARNING:  there is no transaction in progress` + COMMIT on the PostgreSQL wire), and no SQLite error string may be returned under an ER_PARSE_ERROR number.
Traces: rds__s3.cli-rds-export-task-status-poll-until-complete, rds__s3.rds-export-task-respects-s3-prefix-positive, rds__s3.rds-export-task-writes-to-s3-positive, rds__s3.rds-start-export-task-writes-objects-to-s3-positive.
