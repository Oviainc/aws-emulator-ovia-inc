# cloudformation: 5 net-new behavioral root causes — circular-dependency and template-limit refusal messages diverge, the 'supported functions' roster is wrong, auto-deployment targets are not gated to service-managed stack sets, and an in-place SNS topic property update ends UPDATE_FAILED

> _Note: this issue was identified against the code base at commit `840a27c480269ac38c11f96ab699adf96523de04`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Five distinct net-new root causes of service `cloudformation`, each grounded in its own failing behavioral check from suite simparity-behavioral-ga-prod-v1. None of these six checks was marked ALREADY FILED or OWNED by the replay report. A fixer must close all five causes before submitting.

Cause 1 of 5 — the circular-dependency refusal lists the cycle's resources in the wrong order.
AWS: recorded behavior only — the Smithy model does not describe template cycle detection; CreateStack's modelled errors are AlreadyExistsException / InsufficientCapabilitiesException / LimitExceededException / TokenAlreadyExistsException plus the service-common ValidationError. The recording shows a template whose two resources Fn::GetAtt each other is refused SYNCHRONOUSLY at CreateStack with Error.Code `ValidationError` (HTTP 400) and Error.Message built as the fixed text `Circular dependency between resources: [` + the cycle's logical ids, comma-and-space separated, + `]`. The variable part is the set of logical ids taken from the request's template, and AWS emits them in the order the template declares them (recorded example: resources declared Left then Right produce `Circular dependency between resources: [Left, Right]`). The ordering rule, not the recorded pair of names, is the requirement.
Emulator: same status and same code, but the ids come back in the opposite order: `Circular dependency between resources: [Right, Left]` for a template that declares Left before Right. Hypothesis: the message is rendered from a hash-map / graph-traversal iteration order rather than from the template's declaration order, so the list order is not derived from the request at all.
Why: the refusal text is the only machine-readable description of WHICH cycle was found. A client (CDK, the CLI, or any golden-output comparison) that matches or diffs this message against AWS's never matches, and because the order can vary per run it is not even stable for the same template.
Fix: the cycle-detection refusal builder in CreateStack's synchronous template validation in the cloudformation crate — it must render the cycle's logical ids in template declaration order.
Traces: cloudformation.cdk-synth-refuses-construct-cycle-but-emits-a-cfn-cycle

Cause 2 of 5 — the Outputs-count template-limit refusal says 'Output count' where AWS says 'Outputs count'.
AWS: recorded behavior only — DescribeAccountLimits (Smithy: output AccountLimits, no modelled errors) advertises the limit as the AccountLimit named `StackOutputsLimit`, and CreateStack enforces it synchronously with the service-common `ValidationError` (HTTP 400). The recorded Message is built as the fixed text `Template format error: Outputs count ` + the number of Outputs in the request's template + ` is greater than max allowed ` + the advertised StackOutputsLimit (recorded example at the limit 200: `Template format error: Outputs count 201 is greater than max allowed 200`). The fixed words, including the plural noun `Outputs count`, are the requirement; the two numbers come from the request and from the advertised limit.
Emulator: the status, code and both numbers are right, but the noun is singular: `Template format error: Output count 201 is greater than max allowed 200`.
Why: this message is the surface clients use to tell a template-CONTENT limit apart from the account/Region resource-count LimitExceededException; a message that does not follow AWS's construction rule breaks that discrimination and every golden-output comparison, even though the request was correctly refused.
Fix: the message template of the Outputs-count limit check in CreateStack's synchronous template validation in the cloudformation crate. Related but NOT covering: open issue 20261025T074044Z-cloudformation-2-net-new-causes-the-200-parameter.md records the mirror-image defect on the PARAMETER limit ('Parameters count' where AWS says 'Parameter count'); that is a different limit and a different message template, and fixing it does not fix this one — the two nouns diverge in opposite directions, so a blanket pluralisation change would break one while fixing the other.
Traces: cloudformation.describe-account-limits-enforced

Cause 3 of 5 — the 'Encountered unsupported function' refusal advertises the wrong roster of supported functions.
AWS: recorded behavior only (the function roster is not in the Smithy model). An unknown intrinsic anywhere in the template — in Outputs, with or without a transform — is refused synchronously by BOTH CreateStack and ValidateTemplate with `ValidationError` (HTTP 400) and Message built as the fixed text `Template Error: Encountered unsupported function: ` + the offending function name taken from the request + ` Supported functions are: [` + a FIXED roster + `]`. The roster is fixed text and in AWS's recording it is, in this exact order: Fn::GetStackOutput, Fn::AccountIdFromAlias, Fn::GetConstantAZs, Fn::Base64, Fn::GetAtt, Fn::GetAZs, Fn::ImportValue, Fn::Join, Fn::Split, Fn::FindInMap, Fn::Select, Ref, Fn::Equals, Fn::If, Fn::Not, Condition, Fn::And, Fn::Or, Fn::Contains, Fn::EachMemberEquals, Fn::EachMemberIn, Fn::ValueOf, Fn::ValueOfAll, Fn::RefAll, Fn::Sub, Fn::Cidr. Only the function name is variable; the roster is not.
Emulator: the prefix and the named function are correct, but the roster is a different list in a different order: Fn::GetStackOutput, Fn::AccountIdFromAlias, Fn::GetConstantAZs, Fn::Base64, Fn::GetAtt, Fn::GetAZs, Fn::ImportValue, Fn::Join, Fn::Select, Fn::Split, Fn::Sub, Ref, Fn::Cidr, Fn::FindInMap, Fn::Transform, Fn::If, Fn::And, Fn::Equals, Fn::Not, Fn::Or, Fn::Contains, Fn::EachMemberEquals, Fn::EachMemberIn, Fn::RefAll, Fn::ValueOf, Fn::ValueOfAll, Fn::Length, Fn::ToJsonString. It ADDS Fn::Transform, Fn::Length and Fn::ToJsonString, OMITS Condition, and permutes the rest. The added entries make the message self-contradictory on the transform-less path: the same response refuses Fn::Length while listing Fn::Length as supported (Fn::Length and Fn::ToJsonString require the AWS::LanguageExtensions transform, so they must not appear in the roster of a template that does not declare it).
Why: this is the one response that tells an author which intrinsics are usable. A client reading it is told to use Fn::Length on a template that will be refused for using Fn::Length, and any message comparison against AWS fails on every unknown-intrinsic refusal, in CreateStack and in ValidateTemplate alike.
Fix: the single shared supported-function roster constant used by the template intrinsic resolver's unsupported-function refusal (reached from CreateStack, UpdateStack and ValidateTemplate) in the cloudformation crate.
Traces: cloudformation.language-extensions-length-tojsonstring-and-dynamic-getatt, cloudformation.unresolvable-output-intrinsic-fails-the-stack-rather-than-vanishing

Cause 4 of 5 — ListStackSetAutoDeploymentTargets is not gated to service-managed stack sets: a SELF_MANAGED stack set is answered 200 with an empty list.
AWS: Smithy: ListStackSetAutoDeploymentTargets(StackSetName required, CallAs, MaxResults 1..100) -> Summaries: StackSetAutoDeploymentTargetSummaries; the only modelled error is StackSetNotFoundException (client, httpError 404, awsQueryError StackSetNotFoundException); doc: 'Returns summary information about deployment targets for a StackSet.' Auto-deployment exists only for SERVICE_MANAGED stack sets, and the recording shows that naming an EXISTING but SELF_MANAGED stack set is refused with the service-common `ValidationError` and the fixed Message `Auto-deployment targets are only available for service-managed stack sets` (entirely fixed text — no part of it comes from the request).
Emulator: the call SUCCEEDS with HTTP 200 and `{'Summaries': []}` for a stack set created with the default (SELF_MANAGED) permission model. The sibling not-found behaviour is correct (a name that does not exist is refused StackSetNotFoundException with `StackSet <name> not found`), so the emulator can see the stack set — it simply never checks its permission model.
Why: the emulator cannot tell 'exists but self-managed' apart from 'has no auto-deployment targets yet'. A caller that enumerates auto-deployment targets to decide whether a stack set is organisation-managed concludes it is service-managed with zero targets, and a wrongly-typed stack set is silently accepted where AWS refuses the request.
Fix: the ListStackSetAutoDeploymentTargets handler in the cloudformation crate must read the resolved stack set's PermissionModel and refuse SELF_MANAGED with ValidationError and AWS's fixed sentence, before returning any Summaries.
Traces: cloudformation.stack-instance-and-operation-not-found-errors

Cause 5 of 5 — an UpdateStack that changes only an AWS::SNS::Topic property lands UPDATE_FAILED instead of UPDATE_COMPLETE.
AWS: recorded behavior only — UpdateStack with a well-formed TemplateBody that changes one existing AWS::SNS::Topic's DisplayName is applied in place: the stack goes UPDATE_IN_PROGRESS then UPDATE_COMPLETE, and GetTemplate afterwards returns the new template (the new DisplayName).
Emulator: the stack reaches a terminal `UPDATE_FAILED` for exactly that update; the valid follow-up update never applies. In the same check the preceding negative arm is already correct (UpdateStack with syntactically invalid JSON is refused `ValidationError` / `Template format error: YAML not well-formed. (line 1, column 68)` and leaves the stack CREATE_COMPLETE on its original template), so this is the positive control — the ordinary, valid update path — failing.
Why: any stack containing an SNS topic becomes un-updatable, and because the emulator reports the failure as the STACK's verdict, a caller cannot distinguish an unsupported provisioner from a genuine resource failure; every rejection test that needs a working positive control on a topic-bearing stack is also unverifiable.
Fix: the AWS::SNS::Topic resource provisioner's in-place UPDATE path in the cloudformation crate's resource-provisioner layer. Named but NOT covering: open issue 20261026T235900Z-cloudformation-7-net-new-root-causes-in-the.md records the same family as its Cause 7 (grounded in cloudformation.export-value-update-refused-while-imported) — it does not carry this check's replay key, so this check must be re-replayed and the two closed together; if the shared provisioner fix lands under that issue, this cause closes with it.
Traces: cloudformation.update-stack-malformed-json-template-rejected
