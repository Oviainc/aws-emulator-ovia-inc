## Description
SIX distinct net-new root causes found in the `codebuild` behavioral suite, all in the CodeBuild service crate services/service-com-amazonaws-codebuild-codebuild-20161006 (plus its CloudFormation resource provider for cause 5). ALL SIX must be closed before this issue is resolved. Cause 1 of 6: StartBuildBatch accepts a project that has no buildBatchConfig.
AWS: Smithy StartBuildBatch(projectName @required NonEmptyString) -> BuildBatch, with modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400, defaulted). Recorded behavior (confirmed against real AWS in the check's own header note): a project's own `buildBatchConfig` is what makes the project batch-capable, and StartBuildBatch on a project that carries none is refused with 400 InvalidInputException and creates no batch; the identical call on an otherwise byte-identical project that DOES carry a buildBatchConfig succeeds, even when the buildspec has no `batch:` section at all.
Emulator: HTTP 200 — a batch is minted and persisted for the config-less project (buildBatchStatus IN_PROGRESS, currentPhase DOWNLOAD_BATCHSPEC, a build-batch id and ARN) and it is then listed by ListBuildBatchesForProject.
Why: a client cannot discover that its project is not batch-enabled; it is handed a batch id that AWS would never have created, so the whole batch-enablement precondition is invisible and CI logic that branches on this refusal never fires.
Fix: the project-precondition validation in the StartBuildBatch handler (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build_batch.rs) — consult the stored project's buildBatchConfig before minting a batch. NOTE: open issue 20261022T172625Z-codebuild-builds-never-execute-every-build-faults-at.md listed this check under its Cause 10 when the operation answered NotImplemented; the operation now answers 200, so that cause's description no longer matches what the emulator does and this replay key is not carried by it.
Traces: codebuild.start-build-batch-without-batch-config-rejected.

Cause 2 of 6: StartBuildBatch accepts a malformed buildBatchConfigOverride.timeoutInMins.
AWS: Smithy StartBuildBatch.buildBatchConfigOverride targets ProjectBuildBatchConfig, whose `timeoutInMins` member targets WrapperInt and carries NO @range — so the boundary/constraint walk cannot reject a negative value and the service itself must. Recorded behavior: a negative timeoutInMins is refused with 400 InvalidInputException (recorded message, as an example: 'TimeoutInMins must be between 5 and 2160' — the same 5..2160 window the model does pin on the sibling BuildTimeOut shape used by buildTimeoutInMinutesOverride) and no batch resource is created.
Emulator: the call SUCCEEDS (no ClientError at all) with buildBatchConfigOverride={serviceRole: <valid role>, timeoutInMins: -100}.
Why: an out-of-range timeout is silently accepted, so a batch is created with a timeout that can never be honoured and the caller gets no signal that the request was malformed; the InvalidInputException class for this operation is unreachable.
Fix: range validation of buildBatchConfigOverride (and of the project's own buildBatchConfig) in the StartBuildBatch handler's validation layer (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build_batch.rs) — the member is unconstrained in the model, so it must be checked in the handler.
Traces: codebuild.start-build-batch-malformed-input-rejected.

Cause 3 of 6: batch builds never execute — every batch ends FAULT at DOWNLOAD_BATCHSPEC, so no batch ever reaches a terminal status a caller can act on, and RetryBuildBatch / StopBuildBatch / DeleteBuildBatch are unreachable.
AWS: Smithy StatusType enumerates SUCCEEDED, FAILED, FAULT, TIMED_OUT, IN_PROGRESS, STOPPED. A batch build whose constituent build exits non-zero reaches buildBatchStatus FAILED; RetryBuildBatch then restarts that same batch id in place, StopBuildBatch moves the retried attempt to STOPPED (or FAILED), and once the batch is complete DeleteBuildBatch removes it (statusCode BATCH_DELETED) after which BatchGetBuildBatches reports the id in buildBatchesNotFound and RetryBuildBatch answers 400 ResourceNotFoundException.
Emulator: the batch terminates in FAULT, carrying the emulator's own explanation 'this emulator does not run CodeBuild build containers, so the batch build specification could not be downloaded and no build of the batch was started' (services/service-com-amazonaws-codebuild-codebuild-20161006/src/state.rs, BATCH_SPEC_NOT_DOWNLOADED_MESSAGE). FAULT is not in the terminal set {FAILED, STOPPED, SUCCEEDED} that the batch flow waits on, so the check's BatchGetBuildBatches poll never settles and the check exhausts its budget (reported as 'Check timed out after 60.0s'), and nothing downstream of a terminal batch — retry-in-place, stop, delete, not-found-after-delete — is ever exercised.
Why: FAULT is the status AWS reserves for an infrastructure failure of the build system, so every batch build looks like a service fault; a caller cannot tell a passing batch from a failing one and no batch can ever be retried, stopped or reaped.
Fix: the batch-build state machine behind the StartBuildBatch handler and the batch projection read back by batch_get_build_batches.rs (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_build_batch.rs and the batch/phase state in src/state.rs). A deterministic simulated batch walk driven by the project's buildspec `batch:` section is what the suite grades, not a real container. Related: open issues 20261022T172625Z-codebuild-builds-never-execute-every-build-faults-at.md (Cause 1) and 20261025T014438Z-codebuild-8-further-divergences-getresourcepolicy-updatewebhook-deletebuildbatch-stubs.md (Cause 1) describe the same never-executes defect for single BUILDS only; neither covers the batch path, the BATCH_SPEC_NOT_DOWNLOADED_MESSAGE constant, nor this check's replay key.
Traces: codebuild.e2e-build-batch-retry-and-cleanup-flow.

Cause 4 of 6: sandbox command executions never reach SUCCEEDED or FAILED — every execution ends FAULT with no exitCode and no stdout.
AWS: Smithy StartCommandExecution(sandboxId @required, command @required, type CommandType) -> CommandExecution; BatchGetCommandExecutions returns CommandExecution records whose members include `status`, `exitCode` (NonEmptyString), `standardOutputContent` and `standardErrContent`. A command run in a RUNNING sandbox reaches a terminal status that reflects the process: `echo <marker>` -> status SUCCEEDED, exitCode '0', the marker present in standardOutputContent; `exit 7` -> status FAILED, exitCode '7'. StartCommandExecution against a sandbox already STOPPED is refused with 400 InvalidInputException and records no execution.
Emulator: the sandbox itself does settle to RUNNING, but the execution transitions to FAULT, carrying the emulator's own explanation 'this emulator does not execute sandbox commands, so nothing ran this command: it produced no output and no exit code' (services/service-com-amazonaws-codebuild-codebuild-20161006/src/state.rs, COMMAND_EXECUTION_STATUS_FAULT / COMMAND_NOT_EXECUTED_MESSAGE), with no exitCode and no standardOutputContent. FAULT is in neither of the terminal sets these flows poll for ({SUCCEEDED, FAILED}), so every one of the five checks spins on BatchGetCommandExecutions until its budget is gone (reported as 'Check timed out after 60.0s'), and the positive control that must precede each negative never passes — so the STOPPED-sandbox refusal (InvalidInputException) and the 'no execution leaked after a rejected call' assertions are never reached either.
Why: the sandbox data plane is unusable: a caller can start a command and then never learn whether it ran, what it printed or what it returned, and every outcome AWS distinguishes (SUCCEEDED vs FAILED vs a refusal on a stopped sandbox) collapses into one infrastructure-fault status.
Fix: the command-execution state machine and projection behind StartCommandExecution / BatchGetCommandExecutions (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_command_execution.rs, batch_get_command_executions.rs and the StoredCommandExecution settle path in src/state.rs), plus the status gate StartCommandExecution must apply to a non-RUNNING sandbox. A deterministic simulated outcome derived from the submitted command is what the suite grades, not a real shell. Related: Cause 10 of 20261022T172625Z-codebuild-builds-never-execute-every-build-faults-at.md mentions a sandbox check that 'polls a sandbox that never becomes RUNNING' — that is no longer what happens (the sandbox reaches RUNNING; the EXECUTION faults), and none of these five replay keys is carried by it.
Traces: codebuild.command-execution-lifecycle-in-sandbox, codebuild.command-execution-lifecycle-reaches-terminal-state, codebuild.e2e-sandbox-command-execution-after-stop-rejected, codebuild.sandbox-lifecycle-active-to-terminated, codebuild.sandbox-lifecycle-transitions.

Cause 5 of 6: CloudFormation does not know the AWS::CodeBuild::Fleet resource type and refuses the template outright.
AWS: a CreateStack whose template declares an AWS::CodeBuild::Fleet resource is accepted; the stack reaches CREATE_COMPLETE and the fleet then exists in CodeBuild, so ListFleets/BatchGetFleets return its ARN.
Emulator: CreateStack is refused with HTTP 400 ValidationError, message 'Template format error: Unrecognized resource types: [AWS::CodeBuild::Fleet]' — the stack is never created at all.
Why: any CloudFormation template that provisions a CodeBuild compute fleet is rejected at submission, so an IaC-driven CI stack cannot be deployed against the emulator even partially.
Fix: register and implement the CloudFormation resource provider for AWS::CodeBuild::Fleet (the CFN resource-type registry plus the provider that must call into the CodeBuild service state to create the fleet record). NOTE: Cause 9 of open issue 20261022T172625Z-codebuild-builds-never-execute-every-build-faults-at.md lists this check and names AWS::CodeBuild::Project/Fleet, but describes a different, now-stale symptom (the stack COMPLETED and the resource was merely not materialized); the refusal now happens at template validation, before any stack exists, and that issue carries no replay key for this failure.
Traces: codebuild.deploy-fleet-list-reflects-fleet.

Cause 6 of 6: PutResourcePolicy enforces no read-only action allowlist — it answers NotImplemented where AWS answers InvalidInputException for a policy granting a write action.
AWS: Smithy PutResourcePolicy(policy @required NonEmptyString, resourceArn @required NonEmptyString) -> resourceArn, with modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400, defaulted). A CodeBuild resource policy on a report group may only grant the fixed set of read-only consumer actions (BatchGetReportGroups / BatchGetReports / ListReportsForReportGroup / DescribeTestCases); a policy whose Action grants a write such as codebuild:DeleteReportGroup is refused with 400 InvalidInputException and no policy is stored.
Emulator: error code 'NotImplemented' with message 'operation PutResourcePolicy is scaffolded but not implemented in this emulator'.
Why: a caller cannot distinguish an over-broad, rejected policy from an unavailable service, and once the stub is replaced a policy granting write actions would be silently accepted unless this allowlist is implemented with it — which is the requirement this check grades.
Fix: implement services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/put_resource_policy.rs INCLUDING the read-only action allowlist validation ahead of the write to the resource-policy state. The auto-filed scaffold-stub issue 20261022T172625Z-codebuild-putresourcepolicy-stub.md covers only the checks the stub blocked outright and says nothing about the allowlist; this check asserts the action-set rule and carries its own replay key.
Traces: codebuild.put-resource-policy-write-action-rejected.
