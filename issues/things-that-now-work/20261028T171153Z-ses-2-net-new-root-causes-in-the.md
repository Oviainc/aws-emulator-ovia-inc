## Description
Two net-new behavioral root causes on the SES configuration-set surface. Neither failing check is marked ALREADY FILED or OWNED in the replay report. Both check ids appear in the Issue-Trace-Ids of earlier OPEN issues whose replay keys they no longer match, because the failure has MOVED past what those issues describe: 20261026T065304Z-ses-6-net-new-behavioral-root-causes-sesv2.md Cause 1 recorded PutConfigurationSetSendingOptions answering 501 NotImplemented (it no longer does — the call is now accepted, and the divergence below is behind it), and 20261026T065304Z-ses-the-configuration-set-tracking-options-plane-diverges.md Cause 1 recorded the Create being refused InvalidTrackingOptions under a SESv2-verified apex (it is now accepted, and the duplicate-Create leg it only hypothesised about is what fails). Neither issue carries these replay keys, so both causes are filed here.

Cause 1 of 2: a configuration set whose sending is disabled still sends — the v2 SendEmail path never consults the set's SendingEnabled flag, so SendingPausedException is unreachable.
AWS: Smithy com.amazonaws.sesv2#PutConfigurationSetSendingOptions binds PUT /v2/email/configuration-sets/{ConfigurationSetName}/sending (input ConfigurationSetName @httpLabel required, SendingEnabled boolean default false; errors BadRequestException 400, NotFoundException 404, TooManyRequestsException 429) with success 200 and an empty body. SendEmail (POST /v2/email/outbound-emails) models SendingPausedException (httpError 400) exactly for this condition. A fresh configuration set defaults to SendingEnabled=true, so a send through it is accepted with a MessageId; after SendingEnabled=false, the NEXT SendEmail naming that ConfigurationSetName is refused 400 SendingPausedException with the message "Sending is paused for configuration set <ConfigurationSetName>" — fixed text "Sending is paused for configuration set " plus the configuration-set name taken from the request; setting SendingEnabled=true again restores sending, and the restored send mints its OWN MessageId (never a replay of the earlier one).
Emulator: PutConfigurationSetSendingOptions(SendingEnabled=False) is now accepted, but SendEmail through that very set keeps answering HTTP 200 with a MessageId. The check's bounded retry loop (it re-sends every 2s, accepting a brief lag between the control write and the send path) therefore never observes SendingPausedException and the check is killed at the 60s harness cap — the replay verdict is "Check timed out after 60.0s", with no error raised by any call. Hypothesis (the recording cannot distinguish it): the flag is persisted on the configuration-set record but the v2 send handler never reads it; the other possibility is that the write is accepted and discarded. Either way no refusal is ever produced.
Why: pausing a configuration set is the documented kill-switch for a sending programme (an incident, a reputation hold, a cost stop). A client that pauses a set and then relies on SES to refuse further sends has no kill-switch at all: traffic keeps flowing, and the SendingPausedException class it catches to back off or alert never arrives. A caller also cannot verify the pause took effect, since the only observable of the flag is the refusal.
Fix: the v2 send path — services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs must resolve the request's ConfigurationSetName in that crate's state and, when the set's SendingEnabled is false, refuse with SendingPausedException/400 carrying AWS's sentence before any message id is minted; and ops/put_configuration_set_sending_options.rs must persist the flag on the named set (refusing an unknown set with NotFoundException 404) so the send path can read it.
Traces: ses.configuration-set-sending-disabled-blocks-v2-send-email-then-restored.

Cause 2 of 2: a second CreateConfigurationSetTrackingOptions on a set that already has tracking options is refused with the error-shape's documentation sentence, under the code spelling 'TrackingOptionsAlreadyExistsException' instead of the wire code AWS returns.
AWS: Smithy com.amazonaws.ses#CreateConfigurationSetTrackingOptions (input ConfigurationSetName + TrackingOptions, both required) declares ConfigurationSetDoesNotExistException (awsQueryError ConfigurationSetDoesNotExist/400), InvalidTrackingOptionsException (InvalidTrackingOptions/400) and TrackingOptionsAlreadyExistsException/400 for exactly this condition. Recorded behavior: the duplicate Create is refused with awsQuery Error.Code "TrackingOptionsAlreadyExists" and Error.Message "There is already a tracking options for configuration set <name>" — the fixed text is "There is already a tracking options for configuration set <" ... ">", and the variable part is the ConfigurationSetName copied verbatim from the request, INSIDE the angle brackets; the refusal leaves the originally stored CustomRedirectDomain untouched (DescribeConfigurationSet with ConfigurationSetAttributeNames=['trackingOptions'] still reports the first domain). Note for the fixer: this crate's model declares the error's awsQueryError code AS "TrackingOptionsAlreadyExistsException" (shape com.amazonaws.ses#TrackingOptionsAlreadyExistsException), which contradicts the recording; the recorded wire value "TrackingOptionsAlreadyExists" is what a client sees and what this check asserts.
Emulator: the duplicate Create IS refused (400, and the stored domain is left alone), but with the pair ('TrackingOptionsAlreadyExistsException', 'The configuration set you specified already contains a TrackingOptions object.') — the code carries the shape's "Exception" suffix instead of the wire code, and the message is the error shape's own documentation prose, value-free, so it never names the configuration set it rejected. The predecessor issue 20261026T065304Z-ses-the-configuration-set-tracking-options-plane-diverges.md located this text at services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_configuration_set_tracking_options.rs (the already-exists branch).
Why: the Error.Code is the only thing a client branches on, and botocore surfaces it verbatim, so error-handling keyed to AWS's 'TrackingOptionsAlreadyExists' (and the typed exception name derived from it) does not match — a recoverable "already configured, switch to Update" condition reads as an unknown failure. The message additionally drops the configuration-set name, which is its entire diagnostic content when several sets are configured in one run.
Fix: the already-exists branch of services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_configuration_set_tracking_options.rs — emit the awsQuery Error.Code 'TrackingOptionsAlreadyExists' and AWS's templated sentence with the request's ConfigurationSetName interpolated between the angle brackets, leaving the stored TrackingOptions unchanged.
