# Redshift request validation answers a generic ValidationException (or nothing at all) instead of the query-protocol InvalidParameterValue/InvalidParameterCombination contract: MaxRecords bounds, DeleteCluster snapshot decision, parameter-group name/value domains, default-group delete, duplicate-group wording and resource-policy ARN validation (8 causes)

> _Note: this issue was identified against the code base at commit `5b71589754f95f05f88c1a0ee9ccd691bbc5f701`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyClusterParameterGroup

## Description
Eight distinct root causes, all in the redshift service, all about the refusal the emulator authors for an invalid request: it either emits the generic `ValidationException` where Redshift's query protocol emits `InvalidParameterValue`/`InvalidParameterCombination`, emits a different modeled fault, authors its own message text, or accepts a request AWS refuses outright. Each cause is a separate validation site and must be closed separately. Open issue 20261029T192501Z-redshift-parameter-group-hsm-snapshot-copy-grant-and.md describes a neighbouring family of emulator-authored parameter-group/HSM refusals and 20261029T192501Z-redshift-resource-policy-idc-application-and-event-subscription.md a neighbouring resource-policy family; neither carries the replay keys below.

Cause 1 of 8: MaxRecords bounds are enforced upside-down. AWS: MaxRecords on the Describe* operations has an ENFORCED lower bound of 20 — a value below it is rejected with error code `InvalidParameterValue` — while the documented upper bound of 100 is NOT enforced (MaxRecords=101 is accepted and answers 200). Smithy: DescribeClusters/DescribeClusterParameterGroups/DescribeClusterSnapshots MaxRecords targets IntegerOptional with no range constraint, so the bound is a service-side rule, not a modeled one (recorded behavior for the asymmetry). Emulator: DescribeClusters(MaxRecords=1), DescribeClusterParameterGroups(MaxRecords=0) AND DescribeClusterSnapshots(MaxRecords=101) all fail with `ValidationException`. Why: a paginating client that passes a small page size gets an unmodelled code it cannot classify, and one that legitimately passes 101 is refused a call AWS serves, so pagination loops break outright. Fix: the MaxRecords validation shared by the redshift Describe* handlers — reject only below-minimum values, as InvalidParameterValue, and stop enforcing a maximum. Traces: redshift.describe-maxrecords-boundary-fails.

Cause 2 of 8: DeleteCluster does not enforce the final-snapshot decision as a parameter combination. AWS: SkipFinalClusterSnapshot defaults to false, which REQUIRES FinalClusterSnapshotIdentifier; DeleteCluster with neither fails `InvalidParameterCombination` with the fixed message "FinalClusterSnapshotIdentifier is required unless SkipFinalClusterSnapshot is specified." (no variable parts), and the cluster stays available. Smithy: DeleteCluster input = {ClusterIdentifier (required), SkipFinalClusterSnapshot, FinalClusterSnapshotIdentifier, FinalClusterSnapshotRetentionPeriod}; the modeled errors are ClusterNotFoundFault/ClusterSnapshotAlreadyExistsFault/ClusterSnapshotQuotaExceededFault/InvalidClusterStateFault/InvalidRetentionPeriodFault, so the parameter-combination refusal is a service-level rule (recorded behavior). Emulator: `ValidationException`. Why: a client that treats InvalidParameterCombination as "supply a decision and retry" sees an unknown code; worse, any emulator that accepted the call would silently destroy a cluster AWS refuses to delete. Fix: the DeleteCluster handler's input validation. Traces: redshift.delete-cluster-without-snapshot-decision-fails.

Cause 3 of 8: ModifyClusterParameterGroup does not reject a parameter NAME the family does not define with the right code. AWS: a parameter name that is not defined for redshift-1.0 is rejected with `InvalidParameterValue` and nothing is stored. Smithy: ModifyClusterParameterGroup models ClusterParameterGroupNotFoundFault (`ClusterParameterGroupNotFound`, 404) and InvalidClusterParameterGroupStateFault (`InvalidClusterParameterGroupState`, 400) only, so the name-domain refusal is the service's own InvalidParameterValue (recorded behavior). Emulator: `ValidationException`. Why: a client cannot distinguish an unknown parameter name from a malformed request, and tooling that retries after dropping unknown keys never gets the signal. Fix: the ModifyClusterParameterGroup handler's parameter-name validation against the family's parameter catalog. Traces: redshift.parameter-group-unknown-parameter-fails.

Cause 4 of 8: ModifyClusterParameterGroup does not reject an out-of-domain VALUE for a known parameter with the right code. AWS: a known boolean parameter handed 'maybe' is rejected with `InvalidParameterValue`, the stored value is untouched, and a partially-invalid modify is rejected in its entirety. Emulator: `ValidationException`. Why: a config-management client that validates by submitting and reading the error code cannot tell "bad value for this parameter" from "malformed request", and an all-or-nothing modify cannot be verified. Fix: the ModifyClusterParameterGroup handler's per-parameter value-domain validation. Traces: redshift.parameter-group-known-parameter-value-validation.

Cause 5 of 8: DeleteClusterParameterGroup rejects the service-owned default group with the wrong fault. AWS: deleting `default.redshift-1.0` is refused with `InvalidParameterValue` (the group is service-owned, not in a bad state) and the group survives. Smithy: DeleteClusterParameterGroup models ClusterParameterGroupNotFoundFault and InvalidClusterParameterGroupStateFault (`InvalidClusterParameterGroupState`, 400); AWS uses neither for the default group (recorded behavior). Emulator: `InvalidClusterParameterGroupState`. Why: InvalidClusterParameterGroupState reads as transient — "the group is attached, retry later" — so cleanup code retries forever against an immutable, service-owned group instead of skipping it. Fix: the DeleteClusterParameterGroup handler's default-group guard. Traces: redshift.parameter-group-delete-default-fails.

Cause 6 of 8: the ClusterParameterGroupAlreadyExists message is emulator-authored. AWS: a duplicate CreateClusterParameterGroup is refused with code `ClusterParameterGroupAlreadyExists` (Smithy: ClusterParameterGroupAlreadyExistsFault, httpError 400, awsQueryError code `ClusterParameterGroupAlreadyExists`) whose message template is the fixed text "Parameter group " + the requested ParameterGroupName + " already exists". Emulator: the right code but the message "Cluster parameter group already exists: <name>" — a different fixed text with the name in a different position. Why: callers and log scrapers that match AWS's wording (and operators diffing emulator logs against AWS) see a message no AWS region ever emits; under concurrent creates every loser reports it. Fix: the CreateClusterParameterGroup handler's duplicate refusal message. Traces: redshift.concurrent-create-parameter-group-single-winner.

Cause 7 of 8: the InvalidPolicyFault message for malformed JSON is emulator-authored. AWS: PutResourcePolicy with syntactically broken JSON fails `InvalidPolicyFault` (Smithy: PutResourcePolicy errors include InvalidPolicyFault, httpError 400, awsQueryError code `InvalidPolicyFault`) with the fixed message "The resource policy can't be parsed." (no variable parts) and stores nothing. Emulator: the right code but "The resource policy must be a JSON policy document." Why: the text is the only thing distinguishing a parse failure from the other InvalidPolicyFault causes, so client-side policy editors surface the wrong diagnosis. Fix: the PutResourcePolicy handler's policy-parse refusal message. Traces: redshift.resource-policy-malformed-json-rejected.

Cause 8 of 8: the resource-policy operations do not validate the target ARN, and two of them mutate. AWS: Get/Put/DeleteResourcePolicy validate the ResourceArn up front — an ARN that does not identify a policy-attachable Redshift resource (here a datashare ARN naming no existing datashare) is refused by all three with `InvalidParameterValue`, and no policy is created or returned. Smithy: PutResourcePolicy errors = ConflictPolicyUpdateFault (409), InvalidPolicyFault (400), ResourceNotFoundFault (`ResourceNotFoundFault`, 404), UnsupportedOperationFault; the up-front parameter refusal is the service's own InvalidParameterValue (recorded behavior). Emulator: GetResourcePolicy answers `ResourceNotFoundFault` while PutResourcePolicy and DeleteResourcePolicy SUCCEED (HTTP 200) on the unresolvable ARN. Why: the emulator attaches a resource policy to a resource that does not exist, so a client can grant access against a typo'd ARN and believe it took effect — an over-permissive mutation, not just a code mismatch. Fix: ARN resolution/validation shared by the three resource-policy handlers, before any read or write of policy state. Traces: redshift.resource-policy-ops-semantics.
