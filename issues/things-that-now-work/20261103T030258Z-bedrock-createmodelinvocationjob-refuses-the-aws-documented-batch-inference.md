# bedrock CreateModelInvocationJob refuses the AWS-documented batch-inference service role: the pass-role gate leaves a trust condition over aws:SourceArn undecided and answers 403 AccessDeniedException, so no batch inference job can be submitted

> _Note: this issue was identified against the code base at commit `fb8daf436f9fd9e940d981e3a914142bad2da5ee`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateModelInvocationJob

## Description
ONE net-new root cause on the Bedrock control plane's batch-inference submission path (1 cause in this issue).

Cause 1 of 1: the shared `iam:PassRole` gate every job-creating operation of this service runs (`crate::state::job_pass_role_denial`) builds its authorization context with `aws:SourceAccount` and nothing else, and the role-pass decision treats a trust statement carrying a clause over any key the context does not hold as UNDECIDED, i.e. as no grant. A batch-inference service role whose trust statement narrows the pass with `ArnLike aws:SourceArn = arn:aws:bedrock:<region>:<account>:model-invocation-job/*` — the trust policy AWS documents for batch inference — therefore fails the gate, and CreateModelInvocationJob refuses the submission with 403 AccessDeniedException and the fixed sentence "Cross-account pass role is not allowed." for a role of the caller's OWN account. Failing check: bedrock.delete-inference-profile-while-referenced-blocked.

AWS: Smithy com.amazonaws.bedrock#CreateModelInvocationJob (POST /model-invocation-job) requires `roleArn` (RoleArn, len ..2048, pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$) "The Amazon Resource Name (ARN) of the service role with permissions to carry out and manage batch inference", `modelId` (ModelId, len 1..2048, whose pattern admits a bare foundation-model id, a foundation-model ARN, a custom-model ARN and an inference-profile ARN), `jobName`, `modelInvocationType`, `inputDataConfig` and `outputDataConfig`; it models AccessDeniedException @httpError(403) "The request is denied because of missing access permissions", ValidationException @httpError(400) and ResourceNotFoundException @httpError(404). The modelled 403 is for a pass the account genuinely may not make. Recorded behavior: a submission that passes a same-account role trusted to bedrock.amazonaws.com for sts:AssumeRole with Condition `StringEquals aws:SourceAccount = <caller account>` AND `ArnLike aws:SourceArn = arn:aws:bedrock:<region>:<account>:model-invocation-job/*` is ACCEPTED (200 with `jobArn`) and the job is then readable in a non-terminal status (Submitted | Validating | Scheduled | InProgress) — Bedrock supplies `aws:SourceArn` = the ARN of the job it is creating when it assumes the role, and that value matches the wildcard the trust statement allows, so the condition is satisfied rather than unresolved.

Emulator: the submission is refused. `job_pass_role_denial` (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/state.rs, the gate at ~3684-3702) passes only `(aws:SourceAccount, emulator_account_id)` into `service_common::iam_role::role_pass_is_unauthorized`, and its own documentation states the rule it applies: "a clause over any other key leaves the statement undecided, which IAM never reads as a grant" and "no value is guessed for a key the request does not carry". The `ArnLike aws:SourceArn` clause is consequently never decided, the statement is not read as a grant, and the gate returns `CROSS_ACCOUNT_PASS_ROLE_DENIED` = "Cross-account pass role is not allowed." (state.rs:3567) as a 403 AccessDeniedException. That gate runs FIRST in the handler (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_invocation_job.rs:225-234), before the store is touched, so no job is written and nothing about the request is reported. Every part of the refusal diverges from the accepted submission: status 403 instead of 200, an AccessDeniedException instead of a `jobArn`, and a message that is entirely fixed text (it carries no request or state value, so it is not a per-run value).

Hypothesis (the replay detail for this check is only "Check timed out after 60.0s", with no traceback, so the stall point is inferred rather than printed): the check treats AccessDeniedException and ValidationException as the transient IAM-propagation window and re-submits every 10s for its own 120s budget, so a permanently refused pass makes it loop until the harness's 60s budget expires — that retry loop is the only sleep in the check body. The inference is corroborated by the sibling check bedrock.e2e-evaluation-job-with-guardrail-results-teardown, whose role carries `aws:SourceAccount` ONLY: there the same gate admits the pass and CreateEvaluationJob returns a jobArn, so the one difference between the admitted and the stalled submission is the extra `aws:SourceArn` clause this gate cannot decide. Note also that the gate's own comment cites a recording of a refused pass whose grant is narrowed to the job ARN; whatever that one recording shows, a wildcard-scoped `aws:SourceArn` condition of the caller's own account must be ADMITTED, because the recorded batch-inference submission with exactly that trust policy is accepted and the job runs.

Why: this is the service role AWS's own batch-inference documentation tells callers to create — same account, trusted to bedrock.amazonaws.com, scoped with aws:SourceAccount and an aws:SourceArn wildcard over model-invocation-job. With this defect no such caller can submit a batch inference job at all: the 403 AccessDeniedException is terminal and non-retryable, and its wording sends an operator to edit cross-account trust on a trust policy that is already correct, while the real cause (the emulator asks IAM a question with an incomplete condition context) is invisible. Every downstream behavior that depends on a running batch job — reading its status, stopping it, and any guard or non-guard over resources the job names (here, deleting an application inference profile a running job uses) — becomes unreachable.

Fix: the shared pass-role gate in this crate's state (`job_pass_role_denial`) and its caller CreateModelInvocationJob. The gate must supply the condition context Bedrock would actually act under for a job creation — including the `aws:SourceArn` of the model-invocation-job the request is creating (or the job-ARN prefix for the account/region) — so a trust statement scoped with `ArnLike .../model-invocation-job/*` is decided and admits the pass; alternatively the decision must not convert an undecidable `aws:SourceArn` clause on a same-account, service-trusted role into a denial. The same gate is called by the other job-creating handlers, so the context it builds is the single place to fix.

Related open issue that does NOT cover this (it carries no replay key for this behavioral check and describes a different defect): 20261030T063647Z-bedrock-batch-job-creation-runs-its-pass-role.md is about the gate running BEFORE model-identifier validation when the modelId resolves to nothing (400 ValidationException expected, 403 answered). Fixing that ordering leaves this cause exactly as it is: here the modelId resolves fine (an application inference profile ARN, which create_model_invocation_job.rs:298-305 accepts) and the role is one AWS admits, yet the pass is still denied.

Traces: failing check bedrock.delete-inference-profile-while-referenced-blocked (GROUP overly-permissive).

1. git_clone the repo and let the behavioral suite build and boot the emulator; re-replay bedrock.delete-inference-profile-while-referenced-blocked.
2. By hand, against the emulator: create an S3 bucket and PutObject a .jsonl input at s3://<bucket>/input/input.jsonl with 100 records of the form {"recordId":"REC00001","modelInput":{"messages":[{"role":"user","content":[{"text":"Say hello."}]}]}}.
3. IAM CreateRole with AssumeRolePolicyDocument = {"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"bedrock.amazonaws.com"},"Action":"sts:AssumeRole","Condition":{"StringEquals":{"aws:SourceAccount":"<account>"},"ArnLike":{"aws:SourceArn":"arn:aws:bedrock:<region>:<account>:model-invocation-job/*"}}}]} and PutRolePolicy granting s3:GetObject/PutObject/ListBucket on the bucket plus bedrock:InvokeModel.
4. ListInferenceProfiles(typeEquals=SYSTEM_DEFINED) and CreateInferenceProfile(modelSource={copyFrom: <a system-defined profile ARN>}) to get an application inference profile ARN.
5. CreateModelInvocationJob(jobName=..., roleArn=<the role from step 3>, modelId=<the application inference profile ARN>, modelInvocationType="Converse", inputDataConfig={s3InputDataConfig:{s3Uri:"s3://<bucket>/input/input.jsonl"}}, outputDataConfig={s3OutputDataConfig:{s3Uri:"s3://<bucket>/output/"}}).
   Expected: HTTP 200 with a jobArn; GetModelInvocationJob then reports Submitted/Validating/Scheduled/InProgress.

6. Confirm the cause is the undecided condition key, not the account: re-create the role with the SAME trust statement minus the ArnLike aws:SourceArn clause (aws:SourceAccount only) and repeat step 5 — the submission is then accepted, which is also why the sibling evaluation-job checks get past their create call.
7. Clean up: StopModelInvocationJob (if a job was created), DeleteInferenceProfile, delete the role policy and role, empty and delete the bucket.
