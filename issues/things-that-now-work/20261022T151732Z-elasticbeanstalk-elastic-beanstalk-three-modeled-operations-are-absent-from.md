# Elastic Beanstalk: three modeled operations are absent from the routing table (400 InvalidAction "unknown action"), and the IAM CreateInstanceProfile prerequisite answers 501 — 110 checks never reach their assertion (4 causes)

> _Note: this issue was identified against the code base at commit `659e25b97046a77449047daf7fe310a5a83846e1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAvailableSolutionStacks

## Description
Four distinct root causes, all of which abort an Elastic Beanstalk behavioral check on a PREREQUISITE call, before the behavior under test is ever exercised. Causes 1-3 are worse than a scaffold stub: the operation is not in the service's routing table at all, so the request is refused by the router as an unknown Action (400 InvalidAction) rather than answered 501 by a stub handler. Cause 4 is a cross-service prerequisite (IAM) that every environment-launching check needs; it is filed here because the failing checks are Elastic Beanstalk's.

Cause 1 of 4: ListAvailableSolutionStacks is not routed.
AWS: Smithy model com.amazonaws.elasticbeanstalk#ListAvailableSolutionStacks is bound to AWSElasticBeanstalkService, takes no input (input_shape Unit), models NO errors, and returns 200 with ListAvailableSolutionStacksResultMessage {SolutionStacks: AvailableSolutionStackNamesList, SolutionStackDetails: AvailableSolutionStackDetailsList}.
Emulator: answers 400 InvalidAction, message "unknown action: ListAvailableSolutionStacks" — i.e. the router reached the service (src/service.rs can_handle matched) but neither override_operation nor the generated routing table named the operation, so override_routing_error's protocol default (query -> 400 InvalidAction) was rendered.
Why: a client cannot enumerate platforms at all, and botocore raises ClientError(InvalidAction) rather than returning a stack list. Because almost every Beanstalk workflow first picks a solution stack, this single gap aborts 56 checks on their very first call, masking every behavior they were written to measure.
Fix: the operation's handler is simply missing — there is no src/ops/list_available_solution_stacks.rs in the service crate, so the build-script-generated ops module and routing table omit it. Add the handler file so the generated routing table binds the Action, then implement it.
Traces: elasticbeanstalk.list-available-solution-stacks-details (the direct check) plus 55 more listed in trace_ids.

Cause 2 of 4: CreateStorageLocation is not routed.
AWS: Smithy model com.amazonaws.elasticbeanstalk#CreateStorageLocation, input_shape Unit, returns 200 with CreateStorageLocationResultMessage {S3Bucket: String len 0..255}; modeled errors are InsufficientPrivilegesException (403), S3SubscriptionRequiredException (400), TooManyBucketsException (400). It is idempotent — repeated calls return the same account/region bucket.
Emulator: 400 InvalidAction, "unknown action: CreateStorageLocation".
Why: application-version and custom-platform workflows cannot obtain the Beanstalk storage bucket, so every source-bundle upload path is unreachable; 28 checks (including the whole served-HTTP data-plane family) abort before any Beanstalk behavior is observed.
Fix: no src/ops/create_storage_location.rs exists in the service crate; add the handler so the Action is routed, then implement it (returning a stable per-account bucket name).
Traces: elasticbeanstalk.create-storage-location-idempotent plus 27 more in trace_ids, including the multi-service check elasticbeanstalk__logs.eb-stream-logs-delivers-the-application-stdout-to-the-derived-log-group.

Cause 3 of 4: DescribeAccountAttributes is not routed.
AWS: Smithy model com.amazonaws.elasticbeanstalk#DescribeAccountAttributes, input_shape Unit, returns 200 with DescribeAccountAttributesResult {ResourceQuotas}; single modeled error InsufficientPrivilegesException (403).
Emulator: 400 InvalidAction, "unknown action: DescribeAccountAttributes".
Why: a client cannot read its applications/environments/custom-platform quotas, so quota-boundary behavior is unobservable.
Fix: no src/ops/describe_account_attributes.rs exists; add the handler to get the Action routed, then implement it.
Traces: elasticbeanstalk.describe-account-attributes-quotas, elasticbeanstalk.create-platform-version-too-many-fails, elasticbeanstalk.create-platform-version-too-many-platforms-rejected.

Cause 4 of 4: the IAM CreateInstanceProfile prerequisite answers 501 NotImplemented.
AWS: IAM CreateInstanceProfile returns 200 with the created InstanceProfile. Elastic Beanstalk's API never creates the EC2 instance profile / service role for the caller (only the console does), so a check that launches an environment must create them itself; recorded behavior in these checks is that the profile creation succeeds and CreateEnvironment then accepts the IamInstanceProfile option setting.
Emulator: 400-level botocore ClientError (NotImplemented) "operation CreateInstanceProfile is scaffolded but not implemented in this emulator" from the emulator's HTTP 501 scaffold answer.
Why: no caller can provision the instance profile an Elastic Beanstalk environment requires, so the entire environment-launch prerequisite chain is dead and 25 Beanstalk checks abort before reaching Beanstalk at all. Note this is NOT marked ALREADY FILED by the replay report and no open issue mentions CreateInstanceProfile.
Fix: the handler is a scaffold stub at services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/create_instance_profile.rs (its '//! SCAFFOLDED, NOT IMPLEMENTED' marker is present and handle() returns Scaffolded::not_implemented). Implement it there (plus whatever instance-profile state AddRoleToInstanceProfile/GetInstanceProfile share).
Traces: elasticbeanstalk.e2e-operations-role-association-flow plus 24 more in trace_ids.
