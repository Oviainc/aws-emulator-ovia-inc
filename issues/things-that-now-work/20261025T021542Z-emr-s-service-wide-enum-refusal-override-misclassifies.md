# EMR's service-wide enum-refusal override misclassifies PutAutoScalingPolicy's out-of-enum rejection as InvalidRequestException, and the ListClusters enum refusal does not name the rejected ClusterStates values (2 causes)

> _Note: this issue was identified against the code base at commit `56c908e9384776713583471da50d0f78dde9fb40`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutAutoScalingPolicy

## Description
Two root causes, both in how the EMR service words a framework-level request refusal for a value outside a modelled enum. Both are reached on a served call that WAS refused (HTTP 400 in each case), so these are refusal-fidelity divergences, not scaffold gaps. The single seam behind both is `EmulatedService::override_refusal` in services/service-com-amazonaws-emr-elasticmapreduce/src/service.rs, which rewrites EVERY `ViolationKind::EnumValue` refusal of EVERY operation of this service to the code `InvalidRequestException` while keeping the framework's generic constraint message.

Neither cause is covered by an already-open issue. 20261025T000830Z-emr-putautoscalingpolicy-stub.md (open) covers PutAutoScalingPolicy's handler being an unimplemented stub, which is a DIFFERENT defect: the refusal below is produced by the pre-handler request validator and would still be produced verbatim once that handler exists, so implementing the stub does not fix Cause 1. 20261024T015202Z-emr-fidelity-gaps-in-served-operations-createstudio-rejects.md (open) covers unrelated EMR operations. The resolved 20261022T154846Z-emr-enum-filter-refusals-use-unmodeled-validationexception-runjobflow.md introduced the service-wide override named above and explicitly declined the ListClusters message; it does not cover either cause (Cause 1 is a NEW over-reach of that override onto an operation it was not recorded for, and Cause 2's check still fails).

Cause 1 of 2: PutAutoScalingPolicy refuses an out-of-enum ComparisonOperator with InvalidRequestException instead of ValidationException.
AWS: Smithy com.amazonaws.emr#PutAutoScalingPolicy declares NO errors at all (input: ClusterId, InstanceGroupId, AutoScalingPolicy, all required), so the refusal identity is recorded behavior only. Smithy com.amazonaws.emr#ComparisonOperator is an enum whose value set is [GREATER_THAN_OR_EQUAL, GREATER_THAN, LESS_THAN, LESS_THAN_OR_EQUAL], reached through AutoScalingPolicy.Rules[].Trigger.CloudWatchAlarmDefinition.ComparisonOperator. Recorded: a value outside that set is refused at request validation with HTTP 400 and error code `ValidationException` (the generic request-validation identity, one layer before EMR's own business logic), the instance group keeps no auto scaling policy, and a well-formed policy on the same group is then accepted. Recorded message example: "The supplied cloud watch comparison operator is invalid."
Emulator: answers HTTP 400 with error code `InvalidRequestException` and the generic validator message "1 validation error detected: Value 'NOT_A_REAL_COMPARISON_OPERATOR' at 'autoScalingPolicy.rules.1.member.trigger.cloudWatchAlarmDefinition.comparisonOperator' failed to satisfy constraint: Member must satisfy enum value set: [GREATER_THAN_OR_EQUAL, GREATER_THAN, LESS_THAN, LESS_THAN_OR_EQUAL]". The code is wrong because override_refusal applies the enum -> InvalidRequestException rewrite unconditionally across the service, including operations for which AWS is recorded answering ValidationException and which do not even model InvalidRequestException.
Why: a client branching on the refusal class cannot separate a malformed-policy rejection from an unknown-resource rejection: it catches ClientError with a code the operation never produces on real AWS, so validation/retry branches keyed on ValidationException never run, and a test asserting the malformed-input class inverts. The enum rewrite is correct only for the operations it was recorded for; applied service-wide it corrupts every other operation's refusal identity.
Fix: narrow the enum-refusal rewrite in services/service-com-amazonaws-emr-elasticmapreduce/src/service.rs::override_refusal so it applies only to the operations EMR is recorded validating itself ahead of the generic validator (and that model InvalidRequestException), leaving PutAutoScalingPolicy's out-of-enum refusal on the generic validator's ValidationException.
Traces: emr.put-autoscaling-policy-malformed-rule-rejected.

Cause 2 of 2: the ListClusters invalid-ClusterStates refusal carries the generic constraint message instead of a message naming the rejected state values.
AWS: Smithy com.amazonaws.emr#ListClusters models InvalidRequestException (HTTP 400, client) and InternalServerException (500); ClusterStates targets a list of the ClusterState enum [STARTING, BOOTSTRAPPING, RUNNING, WAITING, TERMINATING, TERMINATED, TERMINATED_WITH_ERRORS]. Code and status are recorded as 400 InvalidRequestException and the emulator already matches both. The refusal MESSAGE is built from the request, and that is the rule: it enumerates the submitted ClusterStates values that are not members of the enum, in the request's own order, e.g. "Cluster states [NOPE] are not valid." for ClusterStates=["NOPE"] (the recorded text is an example of that rule, not a literal requirement in itself).
Emulator: same code and status, but the message is the framework validator's member-path form, "1 validation error detected: Value 'NOPE' at 'clusterStates.1.member' failed to satisfy constraint: Member must satisfy enum value set: [STARTING, BOOTSTRAPPING, RUNNING, WAITING, TERMINATING, TERMINATED, TERMINATED_WITH_ERRORS]" — it names a wire member path and the whole value set rather than the rejected states.
Why: for this refusal the message is the only part that tells a caller WHICH of the submitted filter values was rejected when several states are passed; a client (or operator log scraper) that reads the rejected values out of the refusal gets a 1-based wire member path instead and cannot attribute the failure to a state it supplied. Note: the resolved issue named above deliberately declined this message as unmodelled per-member prose; it is re-reported here because the rule is request-derived and the check still fails, so a fixer should either satisfy the rule or record the declination against this check.
Fix: the enum-refusal path for ClusterStates in the ListClusters handler / its validation (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/list_clusters.rs), with the message built from the rejected request values rather than taken from the generic validator envelope in service.rs::override_refusal.
Traces: emr.op-list-clusters-rejects-invalid-state-filter.

## Evidence
Cause 1 — emr.put-autoscaling-policy-malformed-rule-rejected [mismatch]. Source of the rewrite: services/service-com-amazonaws-emr-elasticmapreduce/src/service.rs:133-145 (match on Refusal::Invalid with any ViolationKind::EnumValue -> code INVALID_REQUEST_EXCEPTION, service-wide, with no operation predicate).

Cause 2 — emr.op-list-clusters-rejects-invalid-state-filter [mismatch]. Expected (code already matches): 400 InvalidRequestException whose message names the rejected states, e.g. "Cluster states [NOPE] are not valid." for emr.list_clusters(ClusterStates=['NOPE']).
