# API Gateway: a deployed REST API's invoke URL answers 404 UnknownService instead of executing the stage's integration, and GetAccount is a 501 stub (2 causes)

> _Note: this issue was identified against the code base at commit `048778663a26e363156c6db724999c4fb229af36`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteApiInvoke

## Description
Two net-new root causes in the API Gateway emulator. BOTH must be closed before submitting.

Cause 1 of 2: the execute-api data plane is not routed at all.
AWS: once a REST API has a Deployment and a Stage, HTTP requests to the stage invoke URL (https://{api-id}.execute-api.{region}.amazonaws.com/{stage}/{path}) are handled by API Gateway: it matches the resource/method, runs the configured integration (AWS_PROXY to Lambda, or an AWS service integration such as DynamoDB PutItem) and returns the integration's status/body. Smithy (apigateway): the control plane models CreateDeployment/CreateStage/PutIntegration and execute-api is the data-plane counterpart; failures of the integration surface as 5xx (502/500) and an un-deployed stage as 403, never as a service-resolution error. Recorded behavior: the suite drives ctx.rest_api_url(api_id, stage) with urllib and expects 200 for a working integration, 403 before any deployment, and 500/502 when the integration target is missing or the Lambda permission is absent.
Emulator: every such request answers HTTP 404 with body {"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}. The front-door router only dispatches SigV4/X-Amz-Target/Host-identified control-plane calls, so an unsigned execute-api request is never recognised as API Gateway traffic.
Why: no client can exercise a deployed API. Positive flows never get a response body, and every negative flow (missing deployment -> 403, missing lambda:InvokeFunction permission -> 500, wrong integration URI -> 500) collapses to the same 404, so an application that distinguishes those cases cannot be tested or ported.
Fix: the request router / front-door service resolution plus an execute-api data-plane handler for the apigateway service crate (match stage+resource+method, invoke the integration, map integration failures to 502/500 and an un-deployed stage to 403).
Traces: apigateway__dynamodb__lambda__logs.cli-apigateway-create-deploy-invoke-roundtrip, .cli-apigateway-lambda-integration-setup-and-test, .cli-apigateway-missing-deployment-stage-negative, .deploy-cfn-apigateway-dynamodb-direct-integration-positive, .deploy-cfn-missing-lambda-permission-for-apigateway-negative, .deploy-missing-lambda-permission-blocks-apigateway-invoke-negative, .deploy-wrong-integration-uri-negative, .deploy-cfn-serverless-api-full-stack-positive, apigateway__cloudwatch__dynamodb__lambda__logs.sam-serverless-api-transform-workflow.

Cause 2 of 2: GetAccount is an unimplemented scaffold stub.
AWS: GET /account returns the account-level settings (cloudwatchRoleArn, throttleSettings, features, apiKeyVersion) and is the only way to read/confirm the account CloudWatch role that gates access and execution logging. Smithy (apigateway): GetAccount -> Account; modeled errors are BadRequestException/UnauthorizedException/NotFoundException/TooManyRequestsException - NotImplemented is not among them.
Emulator: answers ClientError code 'NotImplemented', message 'operation GetAccount is scaffolded but not implemented in this emulator'.
Why: every access-logging / execution-logging scenario begins by reading or asserting the account cloudwatchRoleArn, so all of them abort before touching the log plane; a client cannot tell an unconfigured account from a broken service.
Fix: implement the GetAccount handler in the apigateway service crate's ops module, backed by the account settings that UpdateAccount already writes.
Traces: the 19 GetAccount check ids in trace_ids below.
