# entityresolution response fidelity: wrong tagging success status, wrong lifecycle messages, and mis-rendered policy documents

> _Note: this issue was identified against the code base at commit `f4e5251e6df88363d8e23ace2ff5bff3be31b423`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
Five independent response-fidelity defects in the entityresolution emulator: two operations answer the wrong success status, two messages are not the text AWS returns, and the resource-policy document is rendered in a shape AWS never serves. There are 5 distinct causes in this issue and ALL FIVE must be closed. Related but different open issues: 20261022T191952Z-entityresolution-rule-based-matching-jobs-never-succeed-no.md covers AddPolicyStatement's duplicate-statementId/concurrency semantics (that operation is now implemented, and its duplicate-id refusal is not what fails here); 20261022T153803Z-entityresolution-control-plane-missing-reference-duplicate-validation-no.md covers DeleteSchemaMapping's conflict message and other control-plane validation; 20261022T101024Z-entityresolution-write-path-skips-validation-and-drops-schema.md covers the schema-mapping write path. None of the five causes below is one of those.

Cause 1 of 5 — TagResource answers HTTP 200 instead of 204.
AWS: POST /tags/{resourceArn} with a tags map. Smithy: TagResourceOutput has NO members and the operation's @http success code is DEFAULTED (codeDefaulted: true), so the model does not pin the status; recorded behavior shows AWS answering HTTP 204 with an empty body.
Emulator: answers HTTP 200 (with an empty body).
Why: a client or proxy that branches on the exact success status (204 = no content to read) sees a 200 and may try to parse a body, and status-code assertions written against AWS fail even though the tagging itself worked.
Fix: the TagResource handler's success status in the entityresolution service crate (its Operation SUCCESS_STATUS, services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/tag_resource.rs) — answer 204 for the empty output.
Traces: entityresolution-id-namespace-lifecycle#task#9, and the same cluster's entityresolution-schema-mapping-tagging#task#2.

Cause 2 of 5 — UntagResource answers HTTP 200 instead of 204.
AWS: DELETE /tags/{resourceArn}?tagKeys=... (@idempotent). Smithy: UntagResourceOutput has NO members and the @http code is DEFAULTED (codeDefaulted: true); recorded behavior shows AWS answering HTTP 204 with an empty body.
Emulator: answers HTTP 200.
Why: same as Cause 1 — the untag succeeds but the status a client branches on is wrong.
Fix: the UntagResource handler's success status in the entityresolution service crate (services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/untag_resource.rs) — answer 204.
Traces: entityresolution-id-namespace-lifecycle#task#11, and the same cluster's entityresolution-schema-mapping-tagging#task#4.

Cause 3 of 5 — DeleteIdNamespace's success message has the wrong capitalization.
AWS: DELETE /idnamespaces/{idNamespaceName} answers 200 with a @required message member; recorded behavior shows the fixed text 'IdNamespace deleted.' — all of it fixed text, with no variable parts (the namespace name is not echoed), and 'deleted' lowercase.
Emulator: returns 'IdNamespace Deleted.' (capital D).
Why: the message is part of the response contract; clients that assert on or log it see a different string from AWS's, and a title-cased variant signals the message is being generated by a generic formatter rather than reproducing the service's text.
Fix: the DeleteIdNamespace success-message construction in the entityresolution service crate (crate::state::messages) — emit the exact text AWS returns.
Traces: entityresolution-id-namespace-lifecycle#task#13.

Cause 4 of 5 — DeleteIdNamespace's not-found message is a constant and does not name the namespace.
AWS: deleting an idNamespaceName that does not exist fails with HTTP 404 ResourceNotFoundException whose message is built from the request: the fixed text 'IdNamespace ' + the requested idNamespaceName + ' does not exist' (in the recording the variable part is that run's generated namespace name, which is not part of the requirement — the requirement is that the requested name appears in that template).
Emulator: status 404 and error type are right, but the message is the constant 'IdNamespace Not Found' with no name and different fixed text.
Why: a caller deleting several namespaces, or reading logs, uses the name in the message to tell which delete failed; a constant message loses that and breaks message-based assertions written against AWS.
Fix: the DeleteIdNamespace not-found error construction in the entityresolution service crate (crate::state::messages) — format the message from the requested idNamespaceName instead of a constant.
Traces: entityresolution-error-paths-misc#task#2.

Cause 5 of 5 — the resource-policy document is rendered with list-valued Principal/Action and un-normalized principals.
AWS: AddPolicyStatement (POST /policies/{arn}/{statementId}) and GetPolicy (GET /policies/{arn}) answer the resource-based policy as a PolicyDocument string (@length 1..40960). Smithy: AddPolicyStatementInput.action is a StatementActionList (@length min 1) and .principal a StatementPrincipalList (@length min 1) — 'The Amazon Web Services service or Amazon Web Services account that can access the resource defined as ARN' — but the shape of the rendered document is recorded behavior only. The recording shows AWS normalizing when it writes the statement: a bare account id principal is expanded to its IAM root ARN ('Principal': {'AWS': 'arn:aws:iam::<account>:root'}) and a single-element list is collapsed to a scalar for both Principal.AWS and Action, i.e. {"Version":"2012-10-17","Statement":[{"Sid":"<statementId>","Effect":"Allow","Principal":{"AWS":"arn:aws:iam::<account>:root"},"Action":"<action>","Resource":"<arn>"}]}. GetPolicy serves back exactly what the add produced.
Emulator: renders the request lists verbatim — 'Principal': {'AWS': ['<account-id>']} and 'Action': ['<action>'] — so the principal is left as a bare account id inside a one-element array and the action stays an array. GetPolicy then serves the same mis-rendered document (it reads the stored record, so both operations diverge identically).
Why: clients parse this document (to assert a grant, diff it before a PutPolicy, or feed it to a policy-evaluation library). Against AWS the principal is an IAM ARN and single values are scalars, so emulator-produced documents fail those parsers and comparisons, and a round-trip through PutPolicy re-serializes something AWS would have normalized differently.
Fix: the policy-statement rendering in the entityresolution service crate's state — crate::state::policy_statement / crate::state::render_policy_document, called from services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/add_policy_statement.rs:279-294 — expand account-id principals to arn:aws:iam::<account>:root and collapse single-element Principal.AWS and Action lists to scalars, so both AddPolicyStatement and GetPolicy serve AWS's document shape.
Traces: entityresolution-resource-policy-lifecycle#task#4 (AddPolicyStatement) and entityresolution-resource-policy-lifecycle#task#5 (GetPolicy).
