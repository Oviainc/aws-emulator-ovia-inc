# arc-zonal-shift: an ELBv2 load balancer with zonal_shift.config.enabled=true is never registered as an ARC managed resource, so GetManagedResource never reports it and UpdateZonalShift flows never run

> _Note: this issue was identified against the code base at commit `ef6e0f5e66c899ede0df1e04050c78d39daac904`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause in the arc-zonal-shift emulator, found by replaying the behavioral suite (simparity-behavioral-aws-v1). This bundle has 1 cause; it must be closed before submitting.

RELATION TO AN OPEN ISSUE: open issue 20261029T193235Z-arc-zonal-shift-accessdenied-message-on-unknown-shift.md describes this same registration gap as its "Cause 3 of 3", but its recorded replay key for this check (`arc-zonal-shift.update-zonal-shift-extends-expiry|_create_nlb_managed_resource#2|Timeout|time.sleep(15)`) no longer binds — the check's managed-resource poll now sleeps 2s, not 15s, so the replay no longer attributes the failure to that issue and the check came back unowned. The other two open arc-zonal-shift issues (20261029T170702Z-… 403 body shape, 20261102T015300Z-… CancelZonalShift ValidationException value interpolation) are different causes and do not cover this check.

Cause 1 of 1 — a Network Load Balancer with zonal-shift integration enabled never becomes an ARC managed resource; GetManagedResource keeps answering as if the ARN were unregistered, so every managed-resource-backed flow (including UpdateZonalShift) is unreachable (check arc-zonal-shift.update-zonal-shift-extends-expiry).
AWS: Smithy: GetManagedResource = GET /managedresources/{resourceIdentifier}, success 200, input member resourceIdentifier (@httpLabel, required, @length 8..1024); output members appliedWeights (map AZ -> weight, REQUIRED) and zonalShifts (list, REQUIRED); modeled errors AccessDeniedException (client, 403), ResourceNotFoundException (client, 404), ValidationException (client, 400), ThrottlingException (429), InternalServerException (500). UpdateZonalShift = PATCH /zonalshifts/{zonalShiftId}, output ZonalShift with required zonalShiftId/resourceIdentifier/awayFrom/expiryTime/startTime/status/comment. AWS documents that an ALB/NLB becomes an ARC managed resource once zonal-shift integration is turned on for it (elbv2 ModifyLoadBalancerAttributes with Key=zonal_shift.config.enabled, Value=true); recorded behavior: after that call, GetManagedResource on the load balancer ARN answers 200 with a NON-EMPTY appliedWeights (one entry per AZ the load balancer spans) within well under a minute, and an UpdateZonalShift against a shift on that resource is then visible in the resource's `zonalShifts` with the new comment and expiryTime.
Emulator: registration never happens. GetManagedResource resolves exclusively out of the service's own store and 404s whenever that map has no entry for the identifier, and nothing on the ELBv2 side ever publishes an entry, so an ARN whose integration was just enabled is reported as unregistered indefinitely. The check provisions a VPC + two subnets in distinct AZs, an internal Type=network load balancer, waits for it to be available, calls ModifyLoadBalancerAttributes(zonal_shift.config.enabled=true), then polls GetManagedResource until appliedWeights is non-empty (treating ResourceNotFoundException/AccessDeniedException as not-yet-registered). The poll never succeeds and the check is killed by the harness: "Check timed out after 60.0s", so StartZonalShift/UpdateZonalShift's expiry-extension and comment-overwrite assertions are never evaluated. No exception propagated out of the provisioning calls, which rules out a hard failure in the EC2/ELBv2 steps.
Why: every ARC flow that needs a real managed resource is unreachable on the emulator — StartZonalShift / UpdateZonalShift / CancelZonalShift against an actual load balancer, practice runs, and zonal autoshift. A client that follows AWS's documented sequence (create NLB, enable zonal-shift integration, read GetManagedResource) blocks forever on a resource the real service registers in seconds, instead of receiving 200 with a populated appliedWeights map; a resource the service considers managed is answered 404 ResourceNotFoundException with the fixed text "no managed resource is registered with ARC for resourceIdentifier <identifier-from-request>" (the identifier is the request value; the rest is the emulator's own fixed text, which AWS does not emit for a registered resource at all).
Fix: the arc-zonal-shift managed-resource registration path — the service's state (services/service-com-amazonaws-arczonalshift-percdataplane/src/state.rs, the `managed_resources` map read by ops/get_managed_resource.rs) must gain an entry, with appliedWeights seeded to the full weight for each AZ the load balancer spans, when zonal-shift integration is enabled for an ELBv2 load balancer; i.e. the elbv2 ModifyLoadBalancerAttributes handler (or an equivalent cross-service registration seam) must publish that resource to ARC. The UpdateZonalShift handler's effect must then be visible through GetManagedResource.zonalShifts (comment overwritten, expiryTime moved forward, status still ACTIVE).
Traces: arc-zonal-shift.update-zonal-shift-extends-expiry. The sibling check arc-zonal-shift.cancel-practice-run-wrong-shift-type-rejected exercises the same provisioning but is separately blocked by the unimplemented EC2 CreateInternetGateway stub (already filed) — a different cause, not part of this bundle.
