# events__kinesis: an EventBridge rule's Kinesis-data-stream targets still yield no readable record, so PartitionKeyPath per-event routing and the eventId fallback stay ungraded (now a hang, not the GetRecords stub refusal)

> _Note: this issue was identified against the code base at commit `b76b7166d3d256a1ac9f503358a3b66c42be670e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTargets

## Description
One root cause. Cause count: 1.

=== Cause 1 of 1: a rule target whose Arn is a Kinesis data stream produces no record a consumer can read, so PartitionKeyPath's per-event routing and the eventId fallback of a sibling target without KinesisParameters are never exercised ===

AWS: Smithy (services/service-com-amazonaws-eventbridge-awsevents/smithy-model/com-amazonaws-eventbridge-awsevents.json) models com.amazonaws.eventbridge#Target with required Id and Arn plus optional RoleArn, DeadLetterConfig, RetryPolicy and KinesisParameters; com.amazonaws.eventbridge#KinesisParameters has exactly one required member, PartitionKeyPath (@length 0..256), documented as "This object enables you to specify a JSON path to extract from the event and use as the partition key for the Amazon Kinesis data stream, so that you can control the shard to which the event goes. If you do not include this parameter, the default is to use the eventId as the partition key." So for every event the rule matches, each Kinesis target must result in one PutRecord onto the named stream: the target carrying PartitionKeyPath keys its record on the value that JSON path selects from the DELIVERED ENVELOPE, evaluated PER EVENT (two events with different $.detail.tenant values must land under two different keys), and a sibling target on the same rule and the same stream with NO KinesisParameters keys its record on the delivered envelope's own event id. Each record's Data is the full delivered envelope, and the targets' DeadLetterConfig queue receives nothing on success. Recorded behavior only, for the two refinements the model does not state: the path-selected value arrives JSON-ENCODED (a string tenant arrives quoted, `"tenant-alpha"`, not bare), and the default target's key is the event id either bare or as the compound `{eventId}_{uuid}` — the check pins that SHAPE, not a literal second half. PutTargets and PutEvents themselves answer 200 with FailedEntryCount 0; the delivery is asynchronous and observable only through kinesis GetShardIterator + GetRecords.

Emulator: the check is cut off by the suite's 60 s cap — verdict `mismatch`, detail `Check timed out after 60.0s`. The check's own loop re-publishes a fresh pair of events, reads every shard from TRIM_HORIZON for 20 s, and drains the dead-letter queue each round for up to 180 s, exiting only once all four records (two events x two targets) are present; being cut at 60 s means no such record set ever appeared and the DLQ carried no ERROR_CODE other than the tolerated FAILED_TO_ASSUME_ROLE. This is a CHANGED failure mode for the same check: it previously terminated with `botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the GetRecords operation: operation GetRecords is scaffolded but not implemented in this emulator` (HTTP 501), which is the replay key of the open issue 20261026T022914Z-events-kinesis-the-eventbridge-kinesis-target-partitionkeypath-routing.md (Issue-Key `events__kinesis|GetRecords|NotImplemented`), and before that on the GetShardIterator stub keyed by 20261025T151735Z-events-kinesis-target-checks-cannot-be-graded-kinesis.md. Neither refusal is what the replay now reports, so neither issue's key matches this failure and the report marked the check neither ALREADY FILED nor OWNED. Hypothesis (neither the model nor this recording states which half is at fault): either the eventbridge Kinesis target branch performs no PutRecord at all, or the kinesis read path still returns nothing for records EventBridge wrote; the recording only establishes that no record is ever readable while both control-plane calls report success and the DLQ stays empty of other causes.

Why: a client relying on AWS's behavior loses the entire reason to point a rule at a stream rather than a queue — shard affinity chosen by PartitionKeyPath. A consumer reading the stream to partition work per tenant sees nothing arrive, and because PutTargets and PutEvents both answer FailedEntryCount 0 and no message appears on the target's dead-letter queue, there is no signal anywhere that the delivery was dropped: the failure is silent and indistinguishable from an idle bus. An implementation that resolves the path once to a constant, keys every record under a random value or the rule name, or omits the eventId fallback for a target without KinesisParameters is equally unobservable today.

Fix: the eventbridge crate's target-delivery path for Kinesis targets — the Target/KinesisParameters branch that must issue one PutRecord per matched event per target, with PartitionKey = the JSON text of the value PartitionKeyPath selects from the delivered envelope (evaluated per event) and the delivered envelope's event id (bare or `{id}_{uuid}`) when KinesisParameters is absent, Data = the delivered envelope, and no dead-letter message on success — together with whatever in the kinesis data-plane read path (shard/record state behind GetShardIterator/GetRecords) still prevents those records from being returned. File and line citations belong here only as pointers; see Traces for the failing check.
