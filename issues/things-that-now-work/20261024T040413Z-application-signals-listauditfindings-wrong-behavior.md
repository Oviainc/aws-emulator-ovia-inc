# ListAuditFindings ignores AuditTargets/Auditors/DetailLevel and always answers an empty finding list

_Filed: 2026-10-24T04:04:13Z_
_Operation: ListAuditFindings | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `5b1d79d167dfa72d8fff60e6631ca11c09e39e94`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

The handler never touches the service store (`let _ = (ctx, &self.engine);`) and pages over a literal `Vec::new()`, so `AuditFindings` is `[]` for every request. The required `AuditTargets`, plus `Auditors` and `DetailLevel`, are read only by the boundary validator and then dropped: a request naming a stored SLO as its audit target, a request naming a target that does not exist at all, and a request with an unknown auditor name all produce the identical empty 200.

Expected: the findings reported should be computed from the targets the request names and filtered by `Auditors`, with `DetailLevel` selecting how much per-finding context is returned; a finding carries the target's `KeyAttributes` (`@required` on `AuditFinding`) and its `AuditorResults`. For this emulator the one auditor whose input it actually holds is `slo` — "SloAuditor: Identifies SLO violations and detects breached thresholds" — whose targets (`AuditTargetEntity.Slo`) resolve against the stored SLOs, so an SLO audit target should at minimum be resolved against the store rather than ignored.

Actual: a hardcoded empty list, which claims an audit ran over the named targets when no target was even looked at.

## Evidence

Spec: `ListAuditFindings` input requires `AuditTargets` (`length 1..10`, elements `AuditTarget{Type@required, Data@required: AuditTargetEntity union of Service|Slo|ServiceOperation|Canary}`); `Auditors` doc enumerates the configurable auditors (`slo`, `operation_metric`, `service_quota`, `trace`, ...) and states "Only findings generated by the specified auditors will be returned"; output `AuditFindings` is `@required` with `AuditFinding.KeyAttributes` `@required`.

Handler: `src/ops/list_audit_findings.rs` `handle` — `let _ = (ctx, &self.engine);` then `crate::state::page_of(Vec::new(), AUDIT_FINDINGS_TOKEN_TAG, input.next_token.as_deref(), page_size)`; `input.audit_targets`, `input.auditors` and `input.detail_level` are never read.

Tests: no test file under `tests/` exercises `/auditFindings`.

## Steps to Reproduce

1. POST /slo creating an SLO named "checkout-latency"
2. POST /auditFindings?StartTime=<now-3600>&EndTime=<now> with AuditTargets=[{"Type":"slo","Data":{"Slo":{"SloName":"checkout-latency"}}}]
3. Observe HTTP 200 with AuditFindings == []
4. Repeat with AuditTargets naming an SLO that was never created, and again with Auditors=["not-an-auditor"] — the response is byte-identical, showing the required targets and the auditor filter are dropped
