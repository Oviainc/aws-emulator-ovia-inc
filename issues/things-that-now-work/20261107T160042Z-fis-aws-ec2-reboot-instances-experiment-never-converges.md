# FIS aws:ec2:reboot-instances experiment never converges: the reboot check hangs forever (no second guest boot / no console or experiment progress)

> _Note: this issue was identified against the code base at commit `6bba0ea93be6d4db7a2caa629527597bd59ab221`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExperiment

## Description
Cause 1 of 1: a FIS experiment whose single action is `aws:ec2:reboot-instances`, targeting one EC2 instance by explicit `resourceArns`, never reaches the observable end state AWS produces, and the behavioral check that exercises it makes no progress at all — it is killed by the harness watchdog at 60s without ever reaching an assertion, even though every one of its own poll budgets is 600-900s. Failing check: fis.fis-reboot-instances-restarts-the-guest-kernel-and-the-boot-id-changes.

AWS: On AWS, this flow converges in well under a minute of polling. RunInstances with a `#cloud-config` user-data that writes a marker from `bootcmd` to /dev/console makes EC2 GetConsoleOutput(InstanceId, Latest=true) return that boot's console log — a kernel log with printk timestamp prefixes (`[    6.096338] `), `cloud-init[...]` lines, and the guest-written marker line — roughly 30s after the instance reaches `running`. StartExperiment on a template with `actions={reboot:{actionId:'aws:ec2:reboot-instances',targets:{Instances:<target>}}}` then drives the experiment to a terminal state: GetExperiment (Smithy: GET /experiments/{id} -> Experiment) reports `experiment.state.status == 'completed'` and `experiment.actions.reboot.state.status == 'completed'`, ListExperimentResolvedTargets (Smithy: GET /experiments/{experimentId}/resolvedTargets, paginated on `resolvedTargets`) returns exactly the one targeted instance, and the guest really restarts: a second marker appears on the console with a NEW `/proc/sys/kernel/random/boot_id`, a root-volume boot counter of 2, an appended (not replaced) console buffer that grows by thousands of bytes of fresh kernel + cloud-init log, while DescribeInstances keeps the same InstanceId and the SAME LaunchTime (a reboot, not a stop/start or relaunch) and DescribeInstanceStatus settles back to InstanceStatus/SystemStatus ('ok','ok'). Everything above is the recorded behavior the check encodes; the FIS Smithy model itself says nothing about guest-visible effects of an action id, so for the reboot's guest effects this is recorded behavior only.

Emulator: the check produces no verdict whatsoever — the suite reports only `Check timed out after 60.0s`, so none of its assertions (first-boot marker, experiment terminal state, resolved target, second boot_id, counter=2, console growth, LaunchTime unchanged, ('ok','ok')) was ever reached. The only loops in the check that can absorb the whole wall-clock budget are its polling helpers, all of which retry quietly: `_poll_console_markers` (GetConsoleOutput until N `SIM2REAL_BOOT` markers appear), `_poll_experiment` (GetExperiment until status in completed/stopped/failed), `_poll_status_ok` (DescribeInstanceStatus until ('ok','ok')), `_create_template` / `_start_experiment` (retry on any ClientError). So the emulator is answering 2xx but never reaching the state AWS reaches: one or more of those predicates is never satisfied. Hypothesis: the emulated instance never produces guest console output at all (GetConsoleOutput returns an empty or static `Output`, with no cloud-init/user-data execution and no kernel log), so the very first `want=1` marker poll spins forever; a second, independent possibility on the same path is that the `aws:ec2:reboot-instances` action never drives the experiment to `completed` or never re-boots the instance, so the `want=2` poll and the ('ok','ok') poll never settle. The emulator never returns an error for any of these calls, which is why the failure surfaces as a watchdog timeout rather than a mismatch.

Why: a client that uses FIS the way it is meant to be used — start a reboot experiment and then wait for it to finish and for the target to come back — hangs indefinitely against the emulator instead of completing. Chaos-engineering pipelines and tests that gate on `experiment.state.status` reaching a terminal value, on an action's own `state.status`, or on the target instance returning to passing status checks never advance and eventually fail on their own timeouts, with no error to diagnose. Worse, because the emulator reports success for StartExperiment, a pipeline can conclude the fault was injected when the guest was never restarted at all, so a resiliency test silently proves nothing.

Fix: this is an action-execution and data-plane-effect gap, not a serialization gap. It belongs in (a) the FIS experiment orchestrator that executes an experiment's actions and advances `experiment.state`/`experiment.actions.<name>.state` to a terminal `completed`, specifically its handling of the built-in action id `aws:ec2:reboot-instances` for an `aws:ec2:instance` target resolved from `resourceArns`; and (b) the EC2 instance state/console model it must act on — the instance's console-output state behind GetConsoleOutput (it must hold a per-boot guest console log that is appended to on each boot and reflect user-data/cloud-init execution), the reboot transition itself (new kernel boot identity, preserved root-volume state, unchanged InstanceId and LaunchTime, instance remaining `running`), and DescribeInstanceStatus returning to ('ok','ok') after the reboot. Whichever of those predicates is unmet, the orchestrator and the EC2 instance model must converge in bounded time rather than leaving every poller spinning on a 200 response that never changes.

This is NOT covered by the open FIS issues: 20261029T183321Z-fis-4-net-new-root-causes-inject-api.md concerns the `aws:ec2:api-insufficient-instance-capacity-error`/inject-api privilege gate and multi-account role reads, and 20261104T032609Z-fis-tag-identified-targets-never-resolve-...md (and 20261024T000450Z-fis-listexperimentresolvedtargets-wrong-behavior.md) concern targets identified by `resourceTags`, whereas this check targets the instance by explicit `resourceArns` and fails before any resolution assertion is reached.

Traces: fis.fis-reboot-instances-restarts-the-guest-kernel-and-the-boot-id-changes (mismatch, `Check timed out after 60.0s`).

## Evidence
Expected (AWS, as recorded by the check): after RunInstances + instance_running, GetConsoleOutput(Latest=true) returns the guest's console log containing exactly one `SIM2REAL_BOOT <nonce> <boot_id> 1` line written by cloud-init `bootcmd`; after StartExperiment on the reboot template, GetExperiment reports experiment.state.status == 'completed' and experiment.actions.reboot.state.status == 'completed' with no 'skip' in its reason; ListExperimentResolvedTargets returns exactly 1 resolvedTarget whose targetInformation names the instance id; GetConsoleOutput then holds TWO markers, the first byte-identical to before, the second carrying a DIFFERENT valid UUID boot_id and counter '2'; the buffer has grown by >= 500 bytes with >= 20 printk timestamp prefixes and at least one 'cloud-init[' line between the markers; DescribeInstances shows the same InstanceId, the SAME LaunchTime and State 'running'; DescribeInstanceStatus settles at ('ok','ok'). All of this completes in roughly a minute of polling on AWS.

Actual (emulator): the check never reaches any of those assertions. Suite verdict: `[mismatch] fis.fis-reboot-instances-restarts-the-guest-kernel-and-the-boot-id-changes` / `Error: Check timed out after 60.0s`. No error code or non-2xx status is returned by the emulator anywhere in the flow — the calls succeed, but at least one of the polled predicates (console markers via GetConsoleOutput, terminal experiment status via GetExperiment, status checks via DescribeInstanceStatus) never becomes true, so every retry loop runs until the harness kills the check. Because the harness watchdog (60s) is far below the check's own first poll budget (600s), the emulator is observably not converging within the time AWS needs (~30-45s per phase); it is not merely slow by a small margin.

## Resolution
The orchestration half of this report is fixed: a started experiment now CARRIES OUT the actions its plan keeps against the resources its targets resolved to, so `aws:ec2:reboot-instances` reboots the EC2 instances its target resolved to on the EC2 store of the same engine, `experiment.actions.<name>.state` reaches a terminal `completed` with its `startTime`/`endTime`, `ListExperimentResolvedTargets` reports the targeted instance, and the reboot is a real guest boot — a new boot identity appended to the console the instance has written, with the instance keeping its InstanceId, its LaunchTime and its `running` state. See `services/service-com-amazonaws-fis-faultinjectionsimulator/src/state/action_execution.rs` and `services/service-com-amazonaws-ec2-amazonec2/src/state/instance_boots.rs`, covered by `tests/all/experiment_actions_reach_their_targets.rs` and `tests/all/instance_guest_boots.rs`.

Two predicates this report's check also polls are NOT closed here, and each is owned by an issue of the service that owns it:

* the guest's own console output — the `SIM2REAL_BOOT` marker a `#cloud-config` `bootcmd` writes, the printk-prefixed kernel lines and the `cloud-init[...]` lines — needs the instance's user-data to be EXECUTED in a guest: `issues/things-that-do-not-work/20261107T125432Z-ec2-4-net-new-data-plane-causes-a.md`, "Cause 2 of 4 — GetConsoleOutput never returns the output the guest wrote";
* `DescribeInstanceStatus` settling back to ('ok','ok') after the reboot: that operation is still an unmodified scaffold stub, `issues/things-that-do-not-work/20261103T071133Z-ec2-describeinstancestatus-stub.md`.
