Cause 1 of 3: a build started on a project with an inline buildspec never executes — it FAULTs in PROVISIONING, so no runtime is installed and no buildspec command ever runs.
AWS: Smithy StartBuild(projectName @required NonEmptyString, buildspecOverride, ...) -> {build}; BatchGetBuilds returns Build{buildStatus StatusType, phases BuildPhases}. A build on a LINUX_CONTAINER project with a valid buildspec runs its phases (SUBMITTED, QUEUED, PROVISIONING, DOWNLOAD_SOURCE, INSTALL, PRE_BUILD, BUILD, POST_BUILD, FINALIZING, COMPLETED) and reaches buildStatus SUCCEEDED, with the install phase's runtime-versions honoured (so `node -v` reports the configured nodejs major) and a buildspecOverride applying to that build only. Recorded behavior: PROVISIONING succeeds and the terminal buildStatus is SUCCEEDED for a buildspec whose commands exit 0; a buildspec requesting an unsupported runtime version FAILS (not FAULTs) with the phase diagnostic, while the control build at a supported version SUCCEEDS.
Emulator: every such build ends buildStatus 'FAULT' with phases [('SUBMITTED','SUCCEEDED'), ('QUEUED','SUCCEEDED'), ('PROVISIONING','FAULT', [{'message': 'this emulator does not run CodeBuild build containers, so the build could not be provisioned and no buildspec was executed'}]), ('COMPLETED', None)] — the emulator announces it does not run build containers at all, so the whole data plane past PROVISIONING is unobservable.
Why: FAULT is CodeBuild's "service-side error" outcome, not a build failure, so a client cannot distinguish an infrastructure fault from a legitimate build failure; retry logic that re-drives FAULTs loops, CI gates that read SUCCEEDED never pass, and nothing downstream of the build (installed runtime, exported variables, buildspec overrides) can be exercised. It also makes a NEGATIVE check unprovable: an unsupported-runtime build must FAIL while its control SUCCEEDS, and here both FAULT identically.
Fix: the build execution/phase engine behind StartBuild and BatchGetBuilds — the PROVISIONING phase and the phases that follow it, in the codebuild crate's build state machine.
Traces: codebuild.cbnv-build-installs-the-configured-nodejs-major, codebuild.cbnv-buildspec-override-runs-another-version-without-touching-the-project, codebuild.cbnv-unsupported-nodejs-version-build-fails.

Cause 2 of 3: CreateProject (and BatchGetProjects) refuses a project name containing an illegal character with the generic smithy-constraint template instead of CodeBuild's own project-name message.
AWS: Smithy CreateProject(name @required ProjectName, @length min 2 max 150, @pattern ^[A-Za-z0-9][A-Za-z0-9\-_]{1,149}$) -> {project}; modeled errors AccountLimitExceededException, InvalidInputException, ResourceAlreadyExistsException (all errorKind client, httpError 400). Recorded behavior: a name containing '/' is refused with HTTP 400, error code InvalidInputException and the message 'Invalid characters in project name. Only alphanumeric characters, dash, and underscore are supported' — wholly fixed text, with NO member name, submitted value, pattern or count interpolated and no trailing period. BatchGetProjects validates the name the same way and returns the IDENTICAL refusal rather than reporting the name under projectsNotFound.
Emulator: HTTP 400 with the correct code InvalidInputException but the message "1 validation error detected: Value '<the submitted name>' at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[A-Za-z0-9][A-Za-z0-9\-_]{1,149}$" — a generic constraint rendering that names the member, echoes the value and leaks the raw regex.
Why: status and error code already match, so the message is the only distinguishing payload on this refusal; a client or provisioning tool that matches CodeBuild's documented wording never recognizes an illegal project name, and operators see a message AWS never emits (with the wire member name and internal pattern exposed).
Fix: the CreateProject handler's name validation, and the shared project-name validation BatchGetProjects uses — emit the service's own project-name message instead of the generic constraint renderer.
Traces: codebuild.cbnv-project-name-with-a-slash-rejected.

Cause 3 of 3: UpdateProject on a project name that does not exist returns the right code with the ARN-interpolating not-found template where AWS emits a constant string.
AWS: Smithy UpdateProject(name @required NonEmptyString @length min 1) -> {project}; modeled errors InvalidInputException, ResourceNotFoundException (client, httpError 400). Recorded behavior: HTTP 400, error code ResourceNotFoundException, message exactly 'Project does not exist' — wholly fixed text, no project name or ARN interpolated and no trailing period. Existence is checked BEFORE the request body, so a body that is itself invalid on a real project (here source={type: NO_SOURCE, buildspec: ''}) still yields the not-found, while the same body against an existing project surfaces InvalidInputException 'Invalid input: a buildspec is required for source type NO_SOURCE'.
Emulator: HTTP 400 with the correct code ResourceNotFoundException but the message 'Project cannot be found: <project ARN>' (the ARN is a per-run value filling the emulator's template, not part of the requirement).
Why: the project-absent refusal is the most common CodeBuild error and the message is its only distinguishing payload; a caller matching AWS's constant phrase sees an unknown failure string, and the emulator makes the message vary per project where AWS keeps it constant.
Fix: the not-found message template in the UpdateProject handler's project lookup — the constant string, not the shared ARN-interpolating template.
Traces: codebuild.cbnv-update-of-an-absent-project-rejected-not-found.

## Fix status

Cause 1: NOT FIXED, and SPLIT OUT to `issues/things-that-do-not-work/20261108T000000Z-codebuild-a-build-still-faults-at-provisioning-the-nodejs-runtime-checks-remain-open.md`, which carries its three replay keys so they are not recorded as working. A build still ends `FAULT` with the PROVISIONING diagnostic, unchanged: the three checks need the buildspec's commands (`node -v`, `npm -v`) to run and exit 0, which needs a container or external-process runtime for the build image — this platform provides neither, no maintained crate executes POSIX shell in-process (a shell crate such as `brush-core` dispatches every external command to a host process), and there is no `node` or `npm` in-process to dispatch to. Reporting SUCCEEDED, an exit code or command output for commands nothing ran would be a status for work no engine performed, so this path was deliberately left untouched rather than re-worded.

Cause 2: FIXED. `src/state/identifiers.rs` states CodeBuild's own project-name sentence (`INVALID_PROJECT_NAME_MESSAGE`, the sibling of the fleet one already there) and `project_identifier_violation` applies the character rule; `src/service/refusal.rs` words a `@pattern` violation with that sentence whenever the pattern is the one the MODEL puts on the member naming that resource (`CreateProject$name`, `CreateFleet$name` — read from the schemas, so every member the model constrains with the same pattern is covered) and the value really carries a character outside the set; and `src/ops/batch_get_projects.rs` holds `names` (modelled as `NonEmptyString`, so unconstrained there) to the same rule before the lookup, refusing instead of reporting the value under `projectsNotFound`, with the documented ARN form exempt. The pattern's other clauses (length, leading character) keep the shared constraint envelope — the sentence names a character set and does not describe them. `tests/all/name_character_refusals.rs` pins it over nine character classes on CreateProject, BatchGetProjects and CreateFleet, with the controls (the same names written with supported characters created and read back, an absent name still reported in `projectsNotFound`, ARNs accepted, both published length bounds accepted and one past each refused).

Cause 3: FIXED (already satisfied before this work and verified). `src/ops/update_project.rs` resolves the project BEFORE the request body and answers `ResourceNotFoundException` with the wholly fixed `crate::state::PROJECT_NOT_FOUND_MESSAGE` ("Project does not exist"), interpolating neither the name nor an ARN; the body control on an existing project still answers `InvalidInputException` for a `NO_SOURCE` source with no buildspec. Pinned by `tests/all/absent_resource_wording.rs::project_management_states_codebuilds_fixed_absent_project_sentence` over a table of absent names. Its replay key passes.
