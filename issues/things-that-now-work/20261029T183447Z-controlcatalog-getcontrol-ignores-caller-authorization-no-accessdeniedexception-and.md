# ControlCatalog: GetControl ignores caller authorization (no AccessDeniedException), and two refusal messages are emulator-authored (list-member constraint envelope, invalid NextToken)

> _Note: this issue was identified against the code base at commit `b2028dd6393016a9896c0e35ff905bdd884f0327`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetControl

## Description
Three distinct root causes in the controlcatalog emulator, all grounded in failing behavioral checks. The operations involved are GetControl, ListControls and ListControlMappings. The open issues 20261029T152442Z-controlcatalog-getcontrol-validation.md (AccountlessArn partition membership) and 20261029T103342Z-controlcatalog-getcontrol-wrong-behavior.md (Parameters projection) touch GetControl but describe other defects and do not cover any cause below; the resolved issues 20261023T204557Z-controlcatalog-refusal-messages-are-emulator-authored-and-echo.md and 20261021T234107Z-controlcatalog-validation-error-messages-inject-a-rejected-value-rendering.md are in the same family as causes 2 and 3 but named other members/messages and are CLOSED, so they do not cover these checks either. All three causes must be closed.

Cause 1 of 3: GetControl performs no authorization check, so a principal with no identity-based permission is served the control instead of being denied.
  AWS: GetControl models AccessDeniedException (Smithy: com.amazonaws.controlcatalog#AccessDeniedException, errorKind client, @httpError 403, doc "You do not have sufficient access to perform this action."). An IAM principal with no policy granting controlcatalog:GetControl gets HTTP 403, code AccessDeniedException, with the standard implicit-deny message (recorded behavior for this error class): "User: {principal} is not authorized to perform: controlcatalog:GetControl on resource: {control} because no identity-based policy allows the controlcatalog:GetControl action". Fixed text is everything outside the two substitutions; {principal} is the signing principal's ARN derived from the credentials used (arn:aws:iam::{account}:user/{user-name} for an IAM user's access key, arn:aws:sts::{account}:assumed-role/{role-name}/{session-name} for a role session), and {control} is the ControlArn exactly as sent in the request. Nothing in this template is taken from one recording: the account id, user/role/session names and control ARN all come from the request and the emulator's own IAM/STS state.
  Emulator: the same request signed with the unprivileged principal's credentials returns HTTP 200 and the full GetControl payload (Arn, Aliases, Name, Behavior, Severity, RegionConfiguration, Implementation, Parameters, CreateTime, GovernedResources, GovernedProviders). No 403 is ever produced, for either an IAM user with no attached policy or a freshly assumed role with no permissions; the preceding iam:CreateUser / iam:CreateRole / sts:AssumeRole calls in both checks succeeded, so the credentials under test are real emulator principals and only the controlcatalog authorization decision is missing.
  Why: a client that relies on AWS refusing unauthorized reads sees the catalog served to every caller. Least-privilege tests and policy regressions pass against the emulator and fail against AWS, and any code path whose correctness depends on catching AccessDeniedException is never exercised.
  Fix: the GetControl handler's authorization gate (services/service-com-amazonaws-controlcatalog-controlcatalog/src/ops/get_control.rs) plus whatever shared principal/authorization seam the service uses for the caller's identity — the handler currently goes straight from input validation to the state lookup. Status and shape of the success path are correct; what is missing is the deny decision and its modeled error.
  Traces: controlcatalog.get-control-access-denied-without-permission, controlcatalog.get-control-missing-permission-denied.

Cause 2 of 3: a constraint violation on a LIST MEMBER is reported at the per-element path with only the violated constraint, instead of AWS's collection-level clause that wraps the member shape's whole constraint set.
  AWS: both filters are lists whose member carries the constraints (Smithy: ControlMappingFilter.MappingTypes -> MappingTypeFilterList, member MappingType enum [FRAMEWORK, COMMON_CONTROL, RELATED_CONTROL]; ControlFilter.GovernedProviders -> GovernedProviderFilterList, member GovernedProvider @length 2..64 and @pattern ^[A-Z]{2,64}$). The refusal is ValidationException (@httpError 400) and the message names the COLLECTION member path and nests the member requirements inside a "Member must satisfy constraint: [ ... ]" wrapper: "1 validation error detected: Value at 'filter.mappingTypes' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [RELATED_CONTROL, COMMON_CONTROL, FRAMEWORK]]" and "1 validation error detected: Value at 'filter.governedProviders' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 64, Member must have length greater than or equal to 2, Member must satisfy regular expression pattern: [A-Z]{2,64}]". Fixed text: the "N validation error(s) detected: ", "Value at '<path>' failed to satisfy constraint: ", the "Member must satisfy constraint: [...]" wrapper and each requirement sentence. Variable parts, all model- and request-derived: the collection's lowerCamel member path (filter.mappingTypes, filter.governedProviders), and the requirement clauses, which are the member shape's ENTIRE constraint set from the model (every @length bound and the unanchored @pattern, not only the one that was violated; the enum value set for an enum member). Recorded behavior for the enum case lists the value set as RELATED_CONTROL, COMMON_CONTROL, FRAMEWORK, i.e. not the model's declaration order; for the length case AWS lists max before min.
  Emulator: 400 / ValidationException (correct code and status) with "1 validation error detected: Value at 'filter.mappingTypes.1.member' failed to satisfy constraint: Member must satisfy enum value set: [FRAMEWORK, COMMON_CONTROL, RELATED_CONTROL]" and "1 validation error detected: Value at 'filter.governedProviders.1.member' failed to satisfy constraint: Member must satisfy regular expression pattern: [A-Z]{2,64}". Three divergences in one rendering: the path carries a synthetic element suffix (".<index>.member") AWS does not emit, the "Member must satisfy constraint: [...]" wrapper is absent, and only the violated constraint is listed rather than the member shape's full set.
  Why: a client or test that matches AWS's documented validation text — or that parses the member path out of the message to point a user at the offending field — gets a path that names no input member and a sentence shape AWS never produces, so the parse fails or blames the wrong field.
  Fix: this service's constraint renderer, constraint_clause / constraint_envelope in services/service-com-amazonaws-controlcatalog-controlcatalog/src/service.rs (lines 84-160, reached from override_refusal at line 212), together with how the collection-member violation path is collapsed before it gets there: a violation on a list member must render at the collection path and nest the member shape's constraint clauses in the wrapper.
  Traces: controlcatalog.list-control-mappings-invalid-mapping-type-filter-rejected, controlcatalog.list-controls-governed-provider-invalid-pattern-rejected.

Cause 3 of 3: an unusable NextToken is refused with an emulator-authored sentence instead of AWS's fixed NextToken text.
  AWS: ListControls is paginated (Smithy: inputToken/outputToken NextToken, PaginationToken @length max 1024) and declares ValidationException (@httpError 400, doc "The request has invalid or missing parameters."). A NextToken the service did not issue (or that has expired) is refused with the request-independent sentence "The NextToken parameter is not valid or expired." — the whole message is fixed text, with no part taken from the request: it names neither the submitted token, nor the operation, nor the parameters the token was issued for.
  Emulator: 400 / ValidationException (correct code and status) with "nextToken is not a pagination token issued by a previous ListControls call with the same parameters" — emulator-authored wording that interpolates the operation name and uses the wire-cased member spelling. Observed for both a plausible-looking token ("not-a-real-continuation-token") and an obvious garbage token; the positive controls in both checks show real freshly-issued tokens are honored and do advance, so only the message of the refusal class diverges.
  Why: clients that branch on the documented NextToken text (resetting pagination versus surfacing a hard validation failure) never match, and the message shape differs for every operation in the service because the operation name is interpolated.
  Fix: the shared pagination refusal wording, state::page_refusal in services/service-com-amazonaws-controlcatalog-controlcatalog/src/state.rs (the PageError::InvalidToken arm, lines 696-701), which every list operation funnels through (ListControls calls it at src/ops/list_controls.rs:274-278).
  Traces: controlcatalog.list-controls-invalid-next-token-rejected, controlcatalog.list-controls-next-token-malformed-rejected.
