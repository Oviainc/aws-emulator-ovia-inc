# dynamodb: 10 net-new root causes — validation that never runs, wrong error classes, and refusal messages that are generated prose instead of AWS's

> _Note: this issue was identified against the code base at commit `56c908e9384776713583471da50d0f78dde9fb40`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutItem

## Description
Ten distinct root causes in DynamoDB's request validation, error classification and error serialization. Each cause below must be closed before this issue is submitted.

=== Cause 1 of 10: an empty AttributeValue union is refused with the deserializer's internal wording ===
AWS: Smithy: AttributeValue is a union with members S, N, B, SS, NS, BS, M, L, NULL, BOOL — exactly one must be set. AWS refuses an AttributeValue with zero members with ValidationException, HTTP 400, and the message 'Supplied AttributeValue is empty, must contain exactly one of the supported datatypes'. The rule is known: it is AWS's fixed text for this constraint and it names the API concept (AttributeValue, supported datatypes).
Emulator: the refusal carries "union 'AttributeValue' had no member set" — the generated deserializer's internal phrasing, leaking the wire-layer term 'union' and the implementation's 'no member set'.
Why: a client or human operator debugging a malformed item sees emulator-internal terminology rather than the documented diagnosis; message-matching tooling and docs-driven troubleshooting break.
Fix: AttributeValue validation in the item deserialization/validation layer must raise DynamoDB's ValidationException with its own wording instead of letting the generic union deserializer's error escape (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/put_item.rs and the shared attribute-value validator).
Traces: dynamodb.attribute-value-union-requires-exactly-one-member, dynamodb.attribute-value-union-requires-exactly-one-member-rejected, dynamodb.validation-messages-are-customer-intelligible.

=== Cause 2 of 10: expression-validation messages omit AWS's 'N validation error detected:' envelope ===
AWS: expression validation failures raised by the request validator are wrapped in AWS's envelope, e.g. '1 validation error detected: Invalid UpdateExpression: Two document paths overlap with each other; must remove or rewrite one of these paths; path one: [l, [1]], path two: [l, [1]]', '1 validation error detected: Invalid ConditionExpression: An expression attribute name used in the document path is not defined; attribute name: #missing', '1 validation error detected: Invalid UpdateExpression: Incorrect operand type for operator or function; operator or function: list_append, operand type: S', '1 validation error detected: Invalid UpdateExpression: Syntax error; token: "<EOF>", near: "="'. The rule is known: the envelope counts the detected errors and the body is built from the request (the clause, the offending path/name/token).
Emulator: the envelope is absent and the body is reworded — e.g. 'Invalid UpdateExpression: Two document paths overlap with each other; ... path one: l[1], path two: l[1]' (path rendered in index syntax instead of AWS's token list), 'An expression attribute name used in the document path is not defined; attribute name: #missing' (no envelope, no 'Invalid ConditionExpression:' prefix), 'Invalid UpdateExpression: Incorrect operand type for operator or function; function: list_append, operand types: L and S' (wrong key names and operand set), 'Invalid UpdateExpression: syntax error' (no token/near detail). IdempotentParameterMismatchException likewise reports 'Request parameters differ from those of a request already completed with this ClientRequestToken' instead of AWS's text.
Why: a client that parses the validation envelope to count or classify failures, and a human reading the path/token detail, both get a different contract from the same request.
Fix: the shared expression-validation error constructor must emit AWS's envelope and per-clause body built from the request (services/service-com-amazonaws-dynamodb-dynamodb-20120810 expression validator + the update_item/delete_item/transact_write_items handlers).
Traces: dynamodb.deep-dynamodb-2-same-list-index-in-two-clauses-rejected, dynamodb.delete-item-condition-expression-invalid-attribute-name-rejected, dynamodb.list-append-operand-order-prepends-or-appends, dynamodb.update-expression-malformed-syntax-rejected, dynamodb.transact-write-idempotency-mismatch.

=== Cause 3 of 10: parameter-validation messages do not use AWS's 'One or more parameter values were invalid: ...' template and name emulator-internal concepts ===
AWS: control- and key-plane validation uses a fixed template plus request-derived detail, e.g. 'One or more parameter values were invalid: Some index key attributes are not defined in AttributeDefinitions. Keys: [gsi_pk], AttributeDefinitions: [pk]', 'Invalid KeySchema: Some index key attribute have no definition', 'One or more parameter values were invalid: Both ReadCapacityUnits and WriteCapacityUnits must be specified for index: idx1', 'One or more parameter values were invalid: Neither ReadCapacityUnits nor WriteCapacityUnits can be specified when BillingMode is PAY_PER_REQUEST', 'One or more parameter values were invalid: If stream is being enabled then UpdateViewType is required', 'Query condition missed key schema element: sk', 'Invalid KeyConditionExpression: Invalid operator used in KeyConditionExpression', 'This operation is not supported on an index', 'Attempt to change a resource which is still in use: Cannot delete table while indexes are being created, updated, or deleted.' The rule is known: each is AWS's template with the member names and values taken from the request.
Emulator: each is replaced by hand-written prose that names the emulator's own concepts, e.g. 'Invalid KeySchema for index gsi1: no AttributeDefinition was provided for key attribute gsi_pk', 'Invalid KeySchema: no AttributeDefinition was provided for key attribute sk', 'ProvisionedThroughput must be specified for index idx1 when BillingMode is PROVISIONED', 'ProvisionedThroughput cannot be specified when BillingMode is PAY_PER_REQUEST', 'One or more parameter values were invalid: StreamViewType is required when StreamEnabled is true', 'No AttributeDefinition was provided for key attribute extra', 'Invalid KeyConditionExpression: syntax error; pk = :p AND sk <> :s', 'Invalid Statement: an UPDATE addresses a table, not an index', 'Attempt to change a resource which is still in use: Table is being updated: <table>'. DeleteTable on a deletion-protected table also reports its own sentence rather than AWS's.
Why: the refusal no longer tells the client which AWS concept was violated; a key-schema mistake is diagnosed as a missing AttributeDefinition rather than as a missed key schema element, which sends a developer to the wrong fix.
Fix: the per-operation validators for CreateTable/UpdateTable/DeleteTable/Query/ExecuteStatement must build AWS's templated messages from the request members (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/create_table.rs, update_table.rs, delete_table.rs, query.rs, execute_statement.rs). The open issue 20261023T105249Z-dynamodb-request-validation-gaps-rejected-value-omitted-from-messages.md is adjacent but carries none of these replay keys.
Traces: dynamodb.create-table-gsi-key-not-in-attribute-definitions-rejected, dynamodb.create-table-invalid-key-schema-fails, dynamodb.new-index-on-a-provisioned-table-requires-its-own-throughput, dynamodb.provisioned-throughput-on-pay-per-request, dynamodb.update-table-refuses-to-enable-a-stream-without-a-view-type, dynamodb.query-key-condition-non-key-missing-partition-begins-with-partition-rejected, dynamodb.key-condition-illegal-sort-key-operator-rejected, dynamodb.partiql-write-through-index-qualifier-rejected, dynamodb.query-mixing-key-conditions-and-expression-rejected, dynamodb.deletion-protection-blocks-delete, dynamodb.gsi-creating-blocks-delete-table.

=== Cause 4 of 10: document-path refusals append the offending path to AWS's fixed message ===
AWS: an update expression whose document path has no parent is refused with the FIXED message 'The document path provided in the update expression is invalid for update' — AWS does not append the path. The rule is known: it is AWS's constant text for this condition.
Emulator: the message is 'The document path provided in the update expression is invalid for update: parent.child' / '...: m.a.b' — the path is appended.
Why: clients that match this message exactly (it is a constant, so exact matching is the normal pattern) fail to recognize the condition.
Fix: the update-expression path resolver's error construction (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/update_item.rs and the expression path validator).
Traces: dynamodb.deep-dynamodb-2-set-nested-path-on-missing-parent-rejected, dynamodb.update-set-through-missing-map-path-rejected.

=== Cause 5 of 10: stream enable/disable/view-type refusals are classified ResourceInUseException instead of ValidationException ===
AWS: UpdateTable asked to enable a stream that is already enabled, to disable a stream that does not exist, or to change StreamViewType in place is refused with ValidationException, HTTP 400 — these are parameter errors, not resource-state conflicts.
Emulator: all three answer ResourceInUseException, HTTP 400.
Why: the error CODE is part of the contract: a client that retries ResourceInUseException (a transient-conflict code) will retry forever on an input that can never succeed.
Fix: the StreamSpecification branch of UpdateTable's validation must classify these as ValidationException (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/update_table.rs).
Traces: dynamodb.disabling-a-stream-that-does-not-exist-rejected, dynamodb.enabling-a-stream-that-already-exists-rejected, dynamodb.stream-view-type-cannot-be-changed-in-place.

=== Cause 6 of 10: limit refusals use the wrong error class in both directions ===
AWS: TagResource exceeding the per-resource tag limit is refused with ValidationException, HTTP 400. UpdateTable asked to create more than one global secondary index in a single call is refused with LimitExceededException, HTTP 400 (LimitExceededException is a modeled UpdateTable error).
Emulator: the tag case answers LimitExceededException and the two-index case answers ValidationException — exactly inverted.
Why: both codes drive different client behavior (LimitExceededException is commonly treated as retry-after-backoff), so each case is handled with the other's policy.
Fix: the TagResource validator and UpdateTable's GlobalSecondaryIndexUpdates validator (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/tag_resource.rs, update_table.rs).
Traces: dynamodb.tag-resource-exceeds-tag-limit-rejected, dynamodb.update-table-creates-at-most-one-index-per-call.

=== Cause 7 of 10: requests AWS refuses are accepted with HTTP 200 (validation absent entirely) ===
AWS: each of these is refused with a 400-class error before any write: a BatchWriteItem whose item carries an empty-string GSI key (the whole request is rejected with ValidationException); a CreateTable whose secondary indexes project the same 20 attributes across six indexes (120 names against the 100-name budget) — ValidationException; a bare DynamoDB reserved word used as an attribute name in an update, filter or projection expression — ValidationException; a table addressed by an ARN with an empty vendor segment — ValidationException; a TransactWriteItems whose index key is the empty string — ValidationException (a validation failure, not a cancellation); a TransactWriteItems whose index key has the wrong type — TransactionCanceledException; ExecuteStatement with ConsistentRead on a global secondary index — ValidationException; a NextToken issued by one PartiQL statement presented to a different statement — ValidationException; PutResourcePolicy that would lock the caller out of its own table without the confirm flag — refused; and SET on a list index past the end with ReturnValues=UPDATED_NEW returns NO Attributes for the named (nonexistent) path.
Emulator: every one of these returns HTTP 200 and performs the write (observed 'the call was ACCEPTED; real AWS rejects it', 'expected a ClientError, but the call SUCCEEDED and returned {...HTTPStatusCode: 200...}', 'the service accepted it and returned [...]', and for the list-index case an Attributes payload AWS does not return).
Why: silently accepting an invalid write corrupts data that AWS would have protected, and a client's negative-path error handling is never exercised; worst of all, the self-lockout guard on PutResourcePolicy is bypassed.
Fix: the missing validators in the BatchWriteItem, CreateTable (index projection budget), expression-name, ARN-parsing, TransactWriteItems, ExecuteStatement/PartiQL token, PutResourcePolicy and UpdateItem ReturnValues paths (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/*).
Traces: dynamodb.ddb-frc-batch-write-with-an-empty-gsi-key-rejected-whole, dynamodb.index-projection-attribute-budget-counts-a-name-once-per-index, dynamodb.reserved-word-bare-rejected-across-update-filter-and-projection, dynamodb.table-arn-addresses-a-table-wherever-a-name-does, dynamodb.transact-write-items-empty-index-key-validates-not-cancels, dynamodb.transact-write-items-index-key-type-mismatch-cancels-not-validates, dynamodb.execute-statement-gsi-consistent-read-rejected-while-lsi-consistent-read-succeeds, dynamodb.execute-statement-rejects-foreign-next-token, dynamodb.ddb-rbp-self-lockout-policy-denied-without-confirmation, dynamodb.list-index-past-end-set-appends-and-remove-shifts.

=== Cause 8 of 10: update-expression list indices are resolved against the mutating item instead of the pre-image ===
AWS: all clauses of one UpdateExpression resolve their document paths against the item as it was BEFORE the update. 'REMOVE l[0] SET l[1] = :v' on ['a','b','c','d','e'] therefore yields ['X','c','d','e'] (index 1 named the original 'b'), and 'REMOVE l[1], l[2]' yields ['a','d','e'].
Emulator: the clauses are applied sequentially so a REMOVE shifts the list before the later index is resolved: the first case stored ['b','X','d','e'] and the second returned ['a','c','e'] in ALL_NEW.
Why: a single-call multi-clause update silently writes different data than AWS would, with no error to signal it.
Fix: the update-expression evaluator must snapshot the pre-image and resolve every clause's indices against it before applying any mutation (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/update_item.rs).
Traces: dynamodb.deep-dynamodb-2-list-index-clauses-read-one-pre-image, dynamodb.deep-dynamodb-2-remove-list-indices-resolve-against-original.

=== Cause 9 of 10: the awsJson1_0 error body's __type is not namespace-qualified ===
AWS: DynamoDB is an awsJson1_0 service whose error bodies carry __type as the API-version-qualified shape id, e.g. 'com.amazonaws.dynamodb.v20120810#ResourceNotFoundException'. The Smithy shape ids are in com.amazonaws.dynamodb, and the wire form DynamoDB emits is the versioned namespace.
Emulator: __type is the bare 'ResourceNotFoundException'.
Whi: any client or proxy that keys on the qualified __type (rather than the x-amzn-errortype header) cannot classify the error at all.
Why: see above — error classification by body __type fails.
Fix: the awsJson error serializer for this service must emit the qualified __type (the service's error response writer, not any individual handler).
Traces: dynamodb.awsjson-error-code-carrier-is-body-only-rejected.

=== Cause 10 of 10: size() in a condition expression measures the wrong unit for a String ===
AWS: size() applied to a String attribute in a ConditionExpression returns the number of UTF-8 BYTES of the string, and the condition the check writes is therefore satisfied, so PutItem succeeds (HTTP 200).
Emulator: the conditional write is refused with ConditionalCheckFailedException, HTTP 400, message 'The conditional request failed' — the size() comparison evaluated to the opposite truth value.
Why: a conditional write guarded by size() is rejected where AWS accepts it, so a correct client's write silently never lands.
Fix: the size() implementation in the condition-expression evaluator (services/service-com-amazonaws-dynamodb-dynamodb-20120810 condition expression functions).
Traces: dynamodb.condition-size-counts-string-length-not-bytes.
