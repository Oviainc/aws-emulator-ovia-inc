Its only operation-specific modelled errors are InsufficientCapabilitiesException (client, httpError 400, awsQueryError InsufficientCapabilitiesException) and TokenAlreadyExistsException (client, httpError 400), so a template whose resource graph cannot be scheduled is refused through the service-common ValidationError at HTTP 400 — which is exactly what the emulator does, correctly. The model says nothing about the message, so for the message this is recorded behavior only. What the recording shows: for a template that declares two AWS::SSM::Parameter resources, ParamA first and ParamB second, where ParamA's Value is {"Fn::Sub": "a-of-${ParamB}"} and ParamB's Value is {"Fn::Sub": "b-of-${ParamA}"}, AWS refuses the UpdateStack with code ValidationError and the message `Circular dependency between resources: [ParamB, ParamA]`. Fixed text: "Circular dependency between resources: [", the ", " separator and the closing "]". Variable parts: the logical ids of the resources forming the cycle, taken from the submitted template's Resources section — here ParamB then ParamA. Hypothesis (neither the model nor the single recording states the rule): AWS enumerates the cycle in the order its own dependency walk retires the unschedulable set, which for this body is the REVERSE of the order the template declares the resources in; what the recording establishes as a requirement is that the member order is NOT the ascending-logical-id order the emulator produces.

Emulator: the refusal reaches the right status and the right code but the wrong member order. services/service-com-amazonaws-cloudformation-cloudformation/src/state/template_validation.rs builds the message in cycle_refusal() as `format!("Circular dependency between resources: [{}]", from_its_first_member(&cycle).join(", "))`, and from_its_first_member() deliberately ROTATES the cycle to begin at the member whose logical id sorts first (min_by_key over logical_id). Its own doc comment states why it cannot do otherwise: "The order a body DECLARES its resources in is not available to this rule: a template is read into a document whose object members are sorted, so the declarations' own order is gone before any rule sees them." Replaying the check, the emulator answers ValidationError (correct) with `Circular dependency between resources: [ParamA, ParamB]` where AWS says `Circular dependency between resources: [ParamB, ParamA]`. Everything else in the first arm of the check passes: the acyclic control template creates to CREATE_COMPLETE, Fn::Sub over a resource Ref resolves to the referenced physical id, and the code is ValidationError. The check stops on this assertion, so the arms after it were never reached and are NOT part of this report: the dangling-Ref refusal message ("Template format error: Unresolved resource dependencies [DoesNotExist] in the Resources block of the template"), the effect-absent invariants (stack still CREATE_COMPLETE, resource set unchanged, provisioned SSM parameter value untouched), and the recovery update to UPDATE_COMPLETE are all unverified rather than known-good — closing this cause should re-replay the whole check.

Why: a client that reads this message is being told which resources form the cycle, and the member order is how an operator traces the chain (each id followed by the resource it depends on). An ascending-id rotation reports a chain that does not correspond to the dependency direction AWS reports, so a tool or runbook that parses the bracketed list and walks it in order derives the reverse chain. More sharply, any error-matching layer, test, or snapshot that compares the message against AWS's sentence for this class never matches, so a caller that correctly classifies a cyclic-template refusal against AWS sees an unrecognised ValidationError against the emulator.

Fix: the template-validation pass of the cloudformation crate — the cycle rule and the template reader it depends on. The cycle's member order has to be derived from the submitted template's own declaration order rather than normalised to ascending logical id, which means the reader that produces the document the rules see must preserve object-member order for the Resources section (the sorted map noted in cycle_refusal's doc comment is what currently destroys it), and from_its_first_member's lexicographic rotation must be replaced by AWS's chain order. The HTTP 400, the ValidationError code and the fixed text of the sentence are already right and must not change. No open issue names this message: 20261025T015306Z-cloudformation-refusal-taxonomy-diverges-wrong-not-found-validation.md covers not-found/validation message templates on other operations and does not cover the cyclic-template refusal, and 20261026T044414Z-cloudformation-3-net-new-behavioral-root-causes-parameter.md owns the parameter-constraint refusals, not this one.
