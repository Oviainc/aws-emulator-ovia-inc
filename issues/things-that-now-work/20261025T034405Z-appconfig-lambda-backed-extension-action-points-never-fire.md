# AppConfig Lambda-backed extension action points never fire, so PRE_START_DEPLOYMENT veto, AT_DEPLOYMENT_TICK directives and PRE_CREATE_HOSTED_CONFIGURATION_VERSION content transforms are all unobservable (3 causes)

> _Note: this issue was identified against the code base at commit `9181cd543fe84fac851a491e53a22f2746df95d8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartDeployment

## Description
Three net-new root causes, one per AppConfig extension action-point family, all grounded in replayed behavioral checks that are killed at the harness 60 s cap because the invocation they wait on never happens. Numbered; close ALL THREE before submitting. Both constituent services are bootstrapped (appconfig, lambda); the issue's defect is on the AppConfig side — AppConfig is the party that must invoke the action target and act on its response. The separately-filed lambda issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md covers direct client Invoke only and does not describe any AppConfig behavior; if lambda Invoke is still a stub when this is fixed, the AppConfig side must still be implemented and will need a working Invoke to be observable.

=== Cause 1 of 3: a PRE_START_DEPLOYMENT extension action is never invoked and never gates StartDeployment ===
AWS: with an extension whose Actions declare PRE_START_DEPLOYMENT {Name, Uri=<lambda ARN>, RoleArn} associated to an environment ARN, StartDeployment synchronously invokes that Lambda before creating the deployment. Recorded behavior (the check states it was MEASURED against real AWS): the event handed to the target carries Application{Id,Name}, Environment{Id,Name}, ConfigurationProfile{Id,Name}, Content (base64 of the exact candidate configuration bytes), ContentType, ContentVersion (a STRING), DeploymentNumber, PreviousDeploymentNumber, InvocationId, Parameters and Type="PreStartDeployment" (PascalCase, not the SCREAMING_SNAKE action-point key); when the target raises, StartDeployment is refused BadRequestException / HTTP 400 with the request-derived template 'Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <the invocation's request id>', NO deployment record is created, and the data plane keeps serving the previous version. When the target returns normally the deployment proceeds and reaches State=COMPLETE. Smithy: StartDeployment POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / InternalServerException 500.
Emulator: the check never completes — it is killed at the 60 s harness cap. Nothing ever reaches the observation sink the target forwards its event to, and the deployment never reaches a terminal state, so neither the invocation, nor the event payload, nor the veto refusal is observable. Hypothesis: extension associations are stored as metadata only and no action-point dispatch exists in the StartDeployment path, which is also consistent with a 0-minute strategy 'completing' while a non-zero-duration one never settles.
Why: PRE_START_DEPLOYMENT is the one hook a customer uses to VETO a release. An emulator that treats action points as decorative deploys configuration that production would have blocked (over-permissive on the safety hook), and any client that waits for the deployment to settle waits forever.
Traces: appconfig__lambda.extension-action-point-invokes-lambda-during-deployment.

=== Cause 2 of 3: AT_DEPLOYMENT_TICK is never invoked during an in-flight deployment, so a ROLL_BACK directive cannot revert it ===
AWS (per the check's own hypotheses, drawn from the AppConfig user guide's custom-Lambda extension page — this check is marked DRAFT/unblessed, so its payload details are hypotheses the first replay must confirm): an extension action bound to AT_DEPLOYMENT_TICK is invoked repeatedly while a deployment is in flight, and a target response of {"Directive": "ROLL_BACK", "Description": "<text>"} makes AppConfig roll the deployment back; the deployment then settles in a terminal state (ROLLED_BACK/REVERTED) and the environment leaves its transitional Deploying/RollingBack state.
Emulator: the check is killed at the 60 s harness cap. The deployment is never ticked, the directive is never read, and the deployment/environment never leave their transitional states, so no rollback is observable.
Why: AT_DEPLOYMENT_TICK plus ROLL_BACK is AppConfig's programmable abort. Against this emulator a deployment that production would have rolled back instead stays in flight forever and its configuration remains in service; teardown is also blocked because the environment never leaves Deploying.
Traces: appconfig__lambda.at-deployment-tick-directive-rollback-reverts-the-deployment.

=== Cause 3 of 3: PRE_CREATE_HOSTED_CONFIGURATION_VERSION is never invoked, so the action's replacement Content never changes the stored bytes ===
AWS (per the check's hypotheses from the same user-guide page; this check is also marked DRAFT/unblessed): an extension action bound to PRE_CREATE_HOSTED_CONFIGURATION_VERSION is consulted synchronously by CreateHostedConfigurationVersion, is handed an event with Type="PreCreateHostedConfigurationVersion", ContentType, ContentVersion (the version being created, as a STRING), Content (base64 of the unmodified request bytes) and, from the second version on, PreviousContent{ContentType,ContentVersion,Content} carrying the previously STORED bytes; a response of {"Content": "<base64>"} REPLACES what is stored, and both CreateHostedConfigurationVersion's own response body and a later GetHostedConfigurationVersion return the transformed bytes. Removing the association restores byte-faithful storage. Smithy: CreateHostedConfigurationVersion POST /applications/{ApplicationId}/configurationprofiles/{ConfigurationProfileId}/hostedconfigurationversions, Content is the httpPayload, success 201.
Emulator: the check is killed at the 60 s harness cap before it can grade the transform; nothing reaches the observation sink, so the action point is never consulted. Hypothesis: CreateHostedConfigurationVersion stores the request bytes verbatim with no PRE_* dispatch (byte-faithful by default), which is exactly the plausible-but-wrong behavior the check was written to catch.
Why: PRE_CREATE_HOSTED_CONFIGURATION_VERSION is one of only two places where customer code can rewrite the configuration payload itself. A client relying on it (injecting a stamp, normalizing, redacting) gets its untransformed document stored and later served, silently.
Traces: appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content.

Fix (shared component): AppConfig extension action-point dispatch — i.e. the extension/extension-association state plus the invocation seam called from the StartDeployment handler (PRE_START_DEPLOYMENT and the deployment state machine's tick loop) and from the CreateHostedConfigurationVersion handler (PRE_CREATE_HOSTED_CONFIGURATION_VERSION). Each site must resolve the associations bound to the target resource (environment/application/configuration-profile ARN), build the documented event (PascalCase Type, base64 Content, string ContentVersion, PreviousContent where applicable), invoke the action's Uri, and interpret the response: a raising target refuses the calling operation with BadRequestException and leaves no record, a {"Content": ...} response replaces the stored payload, and a {"Directive": "ROLL_BACK"} response drives the deployment state machine to a terminal rolled-back state. The deployment state machine for non-zero-duration strategies must also progress to a terminal state; that symptom is already filed for the Monitors path as 20261025T020208Z-appconfig-cloudwatch-appconfig-deployments-with-cloudwatch-alarm-monitors-never-reach.md, but these three deployments carry NO Monitors, so that issue does not cover them.

## Evidence
Behavioral replay, suite simparity-behavioral-ga-prod-v1. All three checks report exactly 'Error: Check timed out after 60.0s' (verdict [mismatch]) — none of them reached an assertion, which is itself the finding: every wait they contain is on something the emulator never produces.

appconfig__lambda.extension-action-point-invokes-lambda-during-deployment declares _ACTION_POINT_TIMEOUT_S=600 and waits, in order, for (a) StartDeployment to be accepted through the PRE_START_DEPLOYMENT action, (b) the action's event to arrive at the observation queue ('the PRE_START_DEPLOYMENT action point did not invoke the Lambda — nothing reached the observation queue, so the extension association is decorative'), (c) GetDeployment.State in ('COMPLETE','ROLLED_BACK','REVERTED'). Its later legs would have asserted event['Type']=='PreStartDeployment', base64decode(event['Content'])==the candidate bytes, the BadRequestException veto with message 'Error invoking extension <name>: Unhandled error, Lambda Request ID: <id>', and that the vetoed version never reaches the data plane.

appconfig__lambda.at-deployment-tick-directive-rollback-reverts-the-deployment (DRAFT/unblessed header) waits for the tick invocation and for the deployment/environment to leave their transitional states.

appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content (DRAFT/unblessed header) passes a byte-faithful control (no association -> stored == sent) and then waits for the action's event before asserting stored_v2 == the transformed document and PreviousContent carrying version 1's stored bytes.

The generated names, ids and request ids in these checks are per-run values and are examples; the requirements are the invocation itself, the event's documented key/case shape, the 400 BadRequestException veto and the terminal deployment state.

## Steps to Reproduce
Cause 1: create an execution role and a Lambda that forwards its event to an SQS queue and optionally raises; add_permission for Principal appconfig.amazonaws.com; create_extension(Actions={'PRE_START_DEPLOYMENT': [{'Name':'gate','Uri':<fn arn>,'RoleArn':<invoke role>}]}); create application/environment/hosted profile with two hosted versions; create_extension_association to the ENVIRONMENT arn; create_deployment_strategy(DeploymentDurationInMinutes=1, GrowthFactor=100, GrowthType='LINEAR', FinalBakeTimeInMinutes=0, ReplicateTo='NONE'); start_deployment for version 1 -> expect a message on the queue whose Type is 'PreStartDeployment' and whose Content base64-decodes to version 1's bytes, and GetDeployment to reach COMPLETE. Then flip the Lambda to raise and start_deployment for version 2 -> expect 400 BadRequestException 'Error invoking extension <name>: Unhandled error, Lambda Request ID: <id>', no new deployment record, and the data plane still serving version 1. Observed: nothing is ever enqueued and the deployment never settles.

Cause 2: same wiring but Actions={'AT_DEPLOYMENT_TICK': [...]} with a target returning {'Directive':'ROLL_BACK','Description':'<text>'}; start a non-instant deployment -> expect repeated tick invocations and the deployment to settle rolled back. Observed: no invocation, no terminal state.

Cause 3: same wiring but Actions={'PRE_CREATE_HOSTED_CONFIGURATION_VERSION': [...]} with a target returning {'Content': base64(<stamped document>)}; create_hosted_configuration_version once with no association (control: stored == sent), associate, then create the same bytes again -> expect the action's event (Type 'PreCreateHostedConfigurationVersion', PreviousContent for version 1) and GetHostedConfigurationVersion(version 2) to return the TRANSFORMED bytes; delete the association and expect byte-faithful storage again. Observed: the action is never consulted.
