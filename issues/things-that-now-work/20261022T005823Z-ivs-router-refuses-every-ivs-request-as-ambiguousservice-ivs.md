# Router refuses every IVS request as AmbiguousService ('ivs' sigv4 signing name registered by both ivs and ivs-realtime), so no IVS operation is reachable

> _Note: this issue was identified against the code base at commit `09c29ed8e99ab10517eef5fd4d5c2097ded28d72`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
Cause 1 of 1: the emulator's request router resolves an incoming sigv4 request to an emulated service by its signing name alone. Two emulated services declare sigv4 name 'ivs' — AmazonInteractiveVideoService (sdkId 'ivs', endpointPrefix 'ivs') and AmazonInteractiveVideoServiceRealTime (sdkId 'IVS RealTime', endpointPrefix 'ivsrealtime'). The router therefore finds two candidates for every 'ivs'-signed request and refuses it instead of dispatching, so NOT ONE of the 67 IVS checks below ever reached an IVS handler.

AWS: ivs and ivs-realtime are two distinct endpoints that share one sigv4 signing name and one arnNamespace; they are distinguished by endpoint/host, not by signing name. Smithy (services/service-com-amazonaws-ivs-amazoninteractivevideoservice/smithy-model): service AmazonInteractiveVideoService, protocol restJson1, aws.auth#sigv4 name 'ivs', awsService.sdkId 'ivs', endpoint template 'https://ivs.{Region}.{dnsSuffix}'. Smithy (services/service-com-amazonaws-ivsrealtime-amazoninteractivevideoservicerealtime/smithy-model): service AmazonInteractiveVideoServiceRealTime, protocol restJson1, aws.auth#sigv4 name 'ivs', awsService.sdkId 'IVS RealTime', awsService.endpointPrefix 'ivsrealtime', arnNamespace 'ivs'. On real AWS a CreateChannel request signed for service 'ivs' and sent to the ivs endpoint is served by IVS and returns HTTP 200 with the modeled CreateChannelResponse; the modeled failure modes for these operations are ValidationException (common error), ResourceNotFoundException, ConflictException, AccessDeniedException, PendingVerification, ServiceQuotaExceededException, ThrottlingException, InternalServerException. 'AmbiguousService' is not a modeled IVS error and does not exist in AWS.

Emulator: every IVS request is answered with error code 'AmbiguousService' and a body of the form {"__type":"AmbiguousService","message":"2 emulated services all claim requests for 'ivs': ivs, ivs; the request is rejected rather than served by an arbitrary one"}. The response is additionally classified as retryable by botocore, which retries and then raises 'reached max retries: 3' — so the refusal is served with a retryable status rather than a client-error status. Happy-path checks blow up on their very first call (CreateChannel / CreatePlaybackRestrictionPolicy / ImportPlaybackKeyPair / ListPlaybackKeyPairs / ListRecordingConfigurations); negative checks that assert on the error code see 'AmbiguousService' where AWS returns 'ValidationException' (e.g. ivs.create-channel-invalid-name-rejected, ivs.multitrack-requires-fragmented-mp4-rejected), 'ResourceNotFoundException' (e.g. ivs.get-channel-not-found, ivs.create-stream-key-resource-not-found-bad-channel, ivs.start-viewer-session-revocation-resource-not-found) or 'NotFoundException' (ivs.list-tags-for-resource-not-found). The same routing defect also makes the collision message name the registry entries ambiguously ('ivs, ivs'), i.e. the two candidates are reported by signing name instead of by their distinct sdkId/endpointPrefix.

Why: a client gets an error code that exists in no AWS model for an otherwise valid request, and because the refusal is retryable the SDK burns its full retry budget before surfacing it. No IVS functionality — channels, stream keys, playback key pairs, playback restriction policies, viewer-session revocation, tagging — can be exercised at all against the emulator. Any SDK/CLI/CloudFormation consumer that selects an endpoint the way AWS does (per-service endpointPrefix/host) is unserviceable.

Fix: the shared request router / service registry that maps an inbound request to an emulated service. Disambiguation must not be keyed on the sigv4 signing name alone: resolve the target using the request's endpoint host / endpointPrefix (ivs vs ivsrealtime) — and, for restJson1, the operation's HTTP method+URI binding — so that 'ivs'-signed requests reach AmazonInteractiveVideoService and 'ivsrealtime' requests reach AmazonInteractiveVideoServiceRealTime. Registering both services under one key and then refusing the key is the bug. Note the same router defect has been filed for other colliding signing names ('iam' in 20261021T234042Z-osis-router-refuses-every-sigv4-iam-request-as-ambiguousservice.md and 20261022T002237Z-ecr-router-refuses-every-iam-and-every-signer-sigv4.md, 'sagemaker' in 20261021T234924Z-featurestore-runtime-sagemaker-..., plus the Marketplace Catalog/Discovery issues); none of those names 'ivs', so this collision is unowned. ivs.create-channel-missing-permission-rejected additionally trips the already-filed 'iam' collision on its IAM setup call (returned as a JSON __type body to an XML-protocol client); that part is covered by the iam issues above, while its IVS leg is covered here.

Traces: all 67 ivs checks listed in trace_ids. Representative details from the replay: 'An error occurred (AmbiguousService) when calling the CreateChannel operation (reached max retries: 3)'; "expected ValidationException, got {'Code': 'AmbiguousService'}"; "expected ResourceNotFoundException for a nonexistent channel, got 'AmbiguousService'".

## Evidence
Expected (AWS): CreateChannel on the ivs endpoint, signed for service 'ivs', returns HTTP 200 and the modeled CreateChannelResponse {channel:{arn,name,...}, streamKey:{...}}; invalid input returns 400 ValidationException; a missing channel/stream-key/key-pair ARN returns 404 ResourceNotFoundException (NotFoundException for ListTagsForResource).

Actual (emulator): every IVS call is refused before dispatch with error code 'AmbiguousService', body {"__type":"AmbiguousService","message":"2 emulated services all claim requests for 'ivs': ivs, ivs; the request is rejected rather than served by an arbitrary one"}, classified retryable so botocore reports 'reached max retries: 3'. 0/79 ivs behavioral checks pass; 67 of them fail with this error (the other 12 are blocked earlier by s3 CreateBucket, which is not this issue).

Examples from the replay:
- ivs.channel-lifecycle-create-get-delete: ClientError (AmbiguousService) when calling CreateChannel (reached max retries: 3).
- ivs.create-channel-invalid-name-rejected: AssertionError: expected ValidationException, got {'Message': "2 emulated services all claim requests for 'ivs': ivs, ivs; ...", 'Code': 'AmbiguousService'}.
- ivs.get-channel-not-found: AssertionError: expected ResourceNotFoundException for a nonexistent channel, got 'AmbiguousService'.
- ivs.list-tags-for-resource-not-found: expected NotFoundException, got AmbiguousService.
- ivs.concurrent-import-playback-key-pair-race: expected exactly 1 success, got 0 — all five concurrent ImportPlaybackKeyPair calls returned ('AmbiguousService', None, ...).

Model evidence: sigv4Name 'ivs' for BOTH services; endpointPrefix differs ('ivs' vs 'ivsrealtime'), sdkId differs ('ivs' vs 'IVS RealTime').

## Steps to Reproduce
1. Boot the emulator from mainline.
2. Point an SDK client at it: `aws --endpoint-url <emulator> ivs create-channel --name sim2real-ivs-demo` (or botocore client('ivs').create_channel(name=...)).
3. Observe the response: error code AmbiguousService with body {"__type":"AmbiguousService","message":"2 emulated services all claim requests for 'ivs': ivs, ivs; the request is rejected rather than served by an arbitrary one"}, retried to 'reached max retries: 3', instead of HTTP 200 and a CreateChannelResponse.
4. Any other IVS operation behaves identically: get-channel with a nonexistent ARN returns AmbiguousService instead of ResourceNotFoundException; create-channel with an invalid name returns AmbiguousService instead of ValidationException.
5. Replay the behavioral suite and re-run the 67 ivs checks in trace_ids — all fail on this refusal.
