# dynamodb: 2 net-new root causes — Contributor Insights reads never reject a missing table with ResourceNotFoundException, and an on-demand throughput ceiling on a PROVISIONED table is never refused with ValidationException

> _Note: this issue was identified against the code base at commit `69d9d2e12a458c911688cbf85bce3839498ad470`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeContributorInsights

## Description
Two distinct root causes in the DynamoDB emulator, both grounded in failing behavioral checks of this suite that no open issue carries the replay key for. Each cause below must be closed before this issue is submitted.

=== Cause 1 of 2: the Contributor Insights read/write surface never produces the modeled ResourceNotFoundException for a table that does not exist ===
AWS: Smithy (com.amazonaws.dynamodb#DynamoDB_20120810): DescribeContributorInsights takes a required TableName (target TableArn, @length 1-1024) and an optional IndexName; its modeled error set is exactly InternalServerError (server, HTTP 500) and ResourceNotFoundException (client, HTTP 400). ListContributorInsights (optional TableName, NextToken, MaxResults @range max 100) and UpdateContributorInsights (required TableName + required ContributorInsightsAction enum) model the same two errors. There is no NotImplemented error and no 501 anywhere in these operations' error sets. Against a table name that does not exist, all three answer ResourceNotFoundException with HTTP 400 and DynamoDB's standard missing-table message; its fixed text is `Requested resource not found: Table: ` + `<TableName>` + ` not found`, where `<TableName>` is the value taken verbatim from the request's TableName member — the name in any one recording only fills that slot. Against a real table the same three calls succeed: DescribeContributorInsights returns ContributorInsightsStatus `DISABLED` by default, ListContributorInsights returns a ContributorInsightsSummaries list, and UpdateContributorInsights with ContributorInsightsAction=ENABLE returns ContributorInsightsStatus `ENABLING` or `ENABLED`.
Emulator: DescribeContributorInsights answers HTTP 501 with error code `NotImplemented` and the message `operation DescribeContributorInsights is scaffolded but not implemented in this emulator` for EVERY input, so the missing-table branch is never reached — the check observed `expected ResourceNotFoundException, got NotImplemented` on the very first call. Because the refusal is unconditional, the whole negative surface (and the positive control on a real table that distinguishes 'rejects a nonexistent table' from 'rejects every call') is unreachable.
Why: a client cannot tell a missing table from an outage. ResourceNotFoundException is a 400 client error that an SDK surfaces by name and never retries; NotImplemented at 501 is unmodeled, so it falls through every typed catch block and is treated by retry policies as a server-side failure. Any caller that probes whether Contributor Insights is on for a table, or that handles the missing-table case, takes the wrong branch.
Fix: the Contributor Insights handlers and their input validation — services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/describe_contributor_insights.rs, .../list_contributor_insights.rs and .../update_contributor_insights.rs — must resolve TableName against the service's table state and return the modeled ResourceNotFoundException (HTTP 400, message as above) when it does not resolve, and must carry Contributor Insights status on the table state so the default DISABLED and the ENABLE transition are readable back. The table-existence check must run ahead of any not-implemented branch, exactly as this slice already orders UpdateTable's no-updatable-member ValidationException ahead of its scaffold refusal. Related open issues that do NOT carry this check's replay key (their Issue-Trace-Ids list only dynamodb.contributor-insights-enable-describe-list and dynamodb.contributor-insights-lifecycle): 20261025T024002Z-dynamodb-describecontributorinsights-stub.md and 20261025T020208Z-dynamodb-updatecontributorinsights-stub.md — those ask for the operations to be implemented at all; this cause is the missing-table rejection semantics and message, which must hold once they are.
Traces: dynamodb.contributor-insights-not-found.

=== Cause 2 of 2: UpdateTable does not refuse an OnDemandThroughput ceiling on a PROVISIONED table — the scaffold's 501 pre-empts the validation ===
AWS: Smithy: UpdateTableInput.OnDemandThroughput is an optional member (target OnDemandThroughput, carrying MaxReadRequestUnits/MaxWriteRequestUnits) alongside BillingMode and ProvisionedThroughput; UpdateTable's modeled errors are InternalServerError (500), InvalidEndpointException (421), LimitExceededException (400), ResourceInUseException (400) and ResourceNotFoundException (400), plus DynamoDB's common ValidationException (400). No NotImplemented error and no 501 is modeled. The on-demand ceilings belong to the on-demand capacity model only, so naming one on a table whose BillingMode is PROVISIONED is a permanently invalid request and is refused with ValidationException, HTTP 400. The recorded message's fixed text is `One or more parameter values were invalid: ` + `<member>` + ` for OnDemandThroughput cannot be specified when the table BillingMode is ` + `<billingMode>`, where `<member>` is the OnDemandThroughput member actually supplied by the request (MaxReadRequestUnits here) and `<billingMode>` is the table's stored billing mode (PROVISIONED here) — both are values from the request and from state, not literals. The refused update must also leave the table untouched: DescribeTable still reports the pre-call ProvisionedThroughput.
Emulator: the call answers HTTP 501 with error code `NotImplemented` and the message `operation UpdateTable with OnDemandThroughput is scaffolded but not implemented in this emulator`; the check observed `expected ValidationException, got NotImplemented`. The handler's own module header states the ordering defect plainly: it refuses the members it does not store (`SSE, replicas, witnesses, on-demand throughput, a PER-INDEX warm throughput, multi-region consistency and vector indexes`) with the scaffold's 501, while only the no-updatable-member case is validated first — so the capacity-model contradiction is never evaluated.
Why: a client that mixes the two capacity models gets an unmodeled server-class 501 instead of the modeled 400 client error. SDK retry policies retry it, the typed ValidationException catch never fires, and the caller is given no indication that the request is invalid rather than the service unavailable — which is the opposite of the signal AWS sends for an input it will never accept.
Fix: UpdateTable's input validation in services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/update_table.rs must evaluate OnDemandThroughput against the stored table's BillingMode and return ValidationException (HTTP 400, message as templated above) BEFORE the OnDemandThroughput scaffold branch, leaving the stored table's throughput unchanged. Open issue 20261025T024002Z-dynamodb-10-net-new-root-causes-query-scan.md names the same 501 under its Cause 5 for the POSITIVE path (setting/clearing a ceiling on an on-demand table, trace dynamodb.update-table-sets-and-clears-the-on-demand-read-ceiling) and does not carry this check's replay key; this cause is the validation-ordering refusal, which must hold whether or not the positive branch is implemented.
Traces: dynamodb.provisioned-table-rejects-an-on-demand-throughput-ceiling.
