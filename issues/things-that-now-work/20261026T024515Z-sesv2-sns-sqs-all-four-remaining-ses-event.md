# sesv2__sns__sqs: all four remaining SES event-publication scenarios abort at setup — CreateConfigurationSetEventDestination is an unimplemented scaffold stub answering 501 NotImplemented

## Description
Attribution note: this check id's leading token is the composite 'sesv2__sns__sqs'. The per-service bootstrap gate cannot match that composite literally, but all three constituent services are stood up in this checkout (sesv2 -> service-com-amazonaws-sesv2-simpleemailservice-v2, sns -> service-com-amazonaws-sns-amazonsimplenotificationservice, sqs -> service-com-amazonaws-sqs-amazonsqs are all in the bootstrapped set; none appears in pending), so the verdict is FILE. The refused call is the SESv2 one.

One root cause (Cause 1 of 1) shared by four failing checks.

Related OPEN issues that do NOT cover these failures: 20261025T220900Z-sesv2-sns-sqs-the-whole-ses-configuration-set.md reports this group blocked on CreateConfigurationSet and GetAccount, and 20261023T183615Z-sesv2-sns-sqs-all-seven-ses-send-event.md reports it blocked pre-dispatch on CreateEmailIdentity with the router's non-AWS 'AmbiguousService'. Neither is what happens now: identity creation, GetAccount and configuration-set creation all succeed and every one of these four checks progresses to the NEXT call, which is the one reported here. Those issues' replay keys are operation- and error-code-qualified, so they do not carry these checks' current failure and the suite marked none of the four as owned.

Cause 1 of 1: CreateConfigurationSetEventDestination answers HTTP 501 with error code 'NotImplemented' instead of attaching an event destination to the configuration set.
AWS: Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json): SimpleEmailService_v2 2019-09-27, restJson1. CreateConfigurationSetEventDestination is POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations, success code 200 with an EMPTY response body (CreateConfigurationSetEventDestinationResponse declares no members). Required input: ConfigurationSetName (httpLabel), EventDestinationName, EventDestination (EventDestinationDefinition, whose SnsDestination.TopicArn names the topic and whose Enabled flag gates publication). Modeled errors — the ONLY refusals AWS gives for this operation — are AlreadyExistsException 400, BadRequestException 400, LimitExceededException 400, NotFoundException 404, TooManyRequestsException 429. No 'NotImplemented' code and no 501 status exists anywhere in this model. The per-check behavior these four then grade (that Enabled=false publishes nothing, that SendBulkEmail per-entry ReplacementHeaders override the template default in the published event, that SendRawEmail custom headers survive byte-exact into the published event, and that a templated send with a missing variable publishes a RENDERING_FAILURE event) is recorded behavior only; it is unreachable while the destination cannot be created.
Emulator: the call is refused. HTTP 501, error code 'NotImplemented', message "operation CreateConfigurationSetEventDestination is scaffolded but not implemented in this emulator". In that message everything is fixed text — "operation <Op> is scaffolded but not implemented in this emulator" — and the only variable part is the operation name taken from the request's resolved operation; nothing comes from the request body or emulator state. No event destination is stored, so no SES event is ever published to SNS and the SQS subscriber these checks drain stays empty for a reason that is indistinguishable from "the event legitimately did not happen".
Why: SES's entire event-publication surface is unreachable. A client can verify identities, create configuration sets and send mail, but can never route SEND/DELIVERY/BOUNCE/COMPLAINT/RENDERING_FAILURE events anywhere, so no bounce handling, suppression automation or deliverability pipeline can be built or tested. Because the status/code pair is in no AWS model, an SDK cannot classify the failure: setup code that treats AlreadyExistsException as success-on-retry and code that backs off on TooManyRequestsException both take the wrong branch, and a disabled-destination negative control cannot be distinguished from an unimplemented one.
Fix: implement the operation in its handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set_event_destination.rs (the only file for this operation), with event-destination storage hung off the configuration-set record in the service's state module so GetConfigurationSetEventDestinations reads it back and the send path consults Enabled and MatchingEventTypes before publishing to SnsDestination.TopicArn; delete the '//! SCAFFOLDED, NOT IMPLEMENTED' marker at the top of that file; and refuse bad requests with the modeled errors (NotFoundException for an unknown configuration set, AlreadyExistsException for a duplicate destination name, BadRequestException for an unusable destination) rather than a 501.
Traces: sesv2__sns__sqs.event-destination-disabled-publishes-no-events, sesv2__sns__sqs.send-bulk-email-per-entry-replacement-headers-override-the-template-default, sesv2__sns__sqs.send-raw-email-preserves-custom-headers-exactly-in-the-published-event, sesv2__sns__sqs.templated-send-with-missing-variable-publishes-rendering-failure — all four abort on their first CreateConfigurationSetEventDestination call, after identity/topic/queue setup succeeded.
