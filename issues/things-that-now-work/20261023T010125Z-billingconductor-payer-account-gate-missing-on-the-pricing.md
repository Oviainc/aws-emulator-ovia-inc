# billingconductor payer-account gate missing on the pricing-rule, delete, update, batch-association and cross-reference-list surfaces (5 causes: 200/400/404 instead of 403 AccessDeniedException)

> _Note: this issue was identified against the code base at commit `ee002e577bc0f1571995f44867241dcee6b1ff11`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePricingRule

## Description
This issue carries 5 causes. AWS Billing Conductor is a payer-account-only API: every operation is gated on the caller being the AWS Organizations payer (management) account, and a non-payer caller is rejected with HTTP 403 AccessDeniedException whose Message is built from the request as "Account <caller-account-id> is not authorized to call <OperationName>. Only payer account is authorized" (that construction is the requirement; the account id in any recording is environment-specific and an example only). Crucially the gate is a pre-check: it runs BEFORE input/semantic validation, before resource-existence resolution, and before idempotency-token lookup, so a non-payer caller never observes 400 ValidationException, 404 ResourceNotFoundException, 409 ConflictException or a success. The emulator implements no such gate on any of the operations below, so each either succeeds outright or falls through to its resource-existence/validation stage and answers a 4xx of the wrong class.

Relationship to already-open issues: 20261022T200837Z-billingconductor-payer-account-authorization-gate-absent-across-the.md carries the gate for CreateBillingGroup, CreatePricingPlan, ListBillingGroups/ListPricingRules/ListAccountAssociations, Associate/DisassociatePricingRules, the custom-line-item read ops, TagResource and DisassociateAccounts; 20261022T134058Z-billingconductor-listbillinggroups-...md carries only the ListBillingGroups wire key. NONE of them carry the five operation families below, which is what this issue is for.

Cause 1 of 5: CreatePricingRule is not payer-gated at all — it succeeds, and the gate is independent of idempotency-token state and of concurrency.
AWS: Smithy — CreatePricingRule (POST /create-pricing-rule, success code 200) models AccessDeniedException (errorKind client, httpError 403), ConflictException (409), ServiceLimitExceededException (402), ThrottlingException (429), ValidationException (400); its ClientToken member is @idempotencyToken bound to header X-Amzn-Client-Token. Recorded behavior: from a non-payer account every CreatePricingRule is rejected 403 AccessDeniedException with the request-derived payer message; the denial is identical on a repeat call reusing the SAME ClientToken (no cached "already succeeded" response may be laundered through the idempotency path) and on a fresh ClientToken for the same Name; and under N concurrent racers on one Name every racer is denied identically with zero winners — the eligibility check never races into the name-conflict stage or into success.
Emulator: answers HTTP 200 with {"Arn": "arn:aws:billingconductor::<acct>:pricingrule/<id>"} for the plain call, for both ClientToken variants, and for concurrent racers (at least one racer returned ('ok', <pricingrule arn>)). No error code is ever produced and a pricing rule is actually created in emulator state.
Why: an unauthorized caller mutates billing configuration that cannot exist on AWS; a client that probes the payer precondition by catching AccessDeniedException takes the success branch, never exercises its authorization-failure path, and its idempotency/retry and race-resolution logic is validated against behavior AWS never produces.
Fix: the CreatePricingRule handler's authorization gate, placed ahead of input validation, ahead of the ClientToken/idempotency lookup and ahead of state mutation — preferably as a service-wide caller-eligibility pre-check in the billingconductor dispatch path so it is inherently deterministic under concurrency — plus the error serializer rendering the modeled AccessDeniedException as 403 with x-amzn-errortype: AccessDeniedException.
Traces: billingconductor.create-pricing-rule-requires-payer-account, billingconductor.create-pricing-rule-client-token-reuse-still-payer-gated, billingconductor.create-pricing-rule-concurrent-denial-consistency.

Cause 2 of 5: the Delete* family is not payer-gated; a nonexistent-ARN delete is answered from the existence check instead of the gate.
AWS: Smithy — DeletePricingRule, DeletePricingPlan, DeleteBillingGroup and DeleteCustomLineItem each model AccessDeniedException (errorKind client, httpError 403) alongside ValidationException (400) (and ConflictException 409 on the rule/plan/line-item ops). Recorded behavior: from a non-payer account each Delete* against a syntactically well-formed but nonexistent ARN is rejected 403 AccessDeniedException with the payer message — the account-eligibility gate precedes resource-existence resolution, so no not-found/validation outcome is reachable.
Emulator: DeletePricingRule answers error code ValidationException (HTTP 400) with an existence message (example: "the pricing rule arn:aws:billingconductor::<acct>:pricingrule/BOGUS00002 does not exist"), i.e. the request reached the existence check; the sibling Delete* assertions are never reached because the first one already diverges, and those handlers are ungated by the same omission.
Why: the caller cannot distinguish "not authorized" (403, a permanent entitlement failure that must not be retried or treated as idempotent-success) from "already gone" (which many delete flows swallow as success), so teardown logic silently reports success where AWS refuses the caller outright.
Fix: the shared authorization gate applied in the dispatch path ahead of the four Delete* handlers, before their ARN existence lookup.
Traces: billingconductor.delete-operations-require-payer-account.

Cause 3 of 5: the Update* family is not payer-gated; a nonexistent-ARN update returns 404 instead of 403.
AWS: Smithy — UpdatePricingRule (PUT /update-pricing-rule), UpdateBillingGroup (POST /update-billing-group) and UpdateCustomLineItem (POST /update-custom-line-item) each model AccessDeniedException (errorKind client, httpError 403) and ResourceNotFoundException (errorKind client, httpError 404). Recorded behavior: from a non-payer account each is rejected 403 AccessDeniedException against a well-formed but nonexistent ARN — NOT 404 ResourceNotFoundException — because the gate runs before existence resolution.
Emulator: UpdatePricingRule answers error code ResourceNotFoundException (example message "the pricing rule does not exist"); UpdateBillingGroup and UpdateCustomLineItem are ungated by the same omission.
Why: 404 invites the caller to create-then-retry, which on AWS will also be denied; an entitlement failure is misclassified as a transient/recoverable resource state, and no SDK auth-failure handling fires.
Fix: the shared authorization gate applied ahead of the three Update* handlers, before their existence lookup.
Traces: billingconductor.update-operations-require-payer-account.

Cause 4 of 5: the batch custom-line-item association ops are not payer-gated; they answer 404 instead of a top-level 403.
AWS: Smithy — BatchAssociateResourcesToCustomLineItem and BatchDisassociateResourcesFromCustomLineItem (both PUT, success code 200) model AccessDeniedException (errorKind client, httpError 403) and ResourceNotFoundException (404), and their outputs carry FailedAssociatedResources/FailedDisassociatedResources per-resource error lists. Recorded behavior: from a non-payer account each call is rejected at the TOP level with 403 AccessDeniedException and the payer message, even when TargetArn and ResourceArns name nonexistent resources — the denial is never reported as a per-resource failure entry inside a 200 response, and never as 404.
Emulator: BatchAssociateResourcesToCustomLineItem answers error code ResourceNotFoundException (example message "the custom line item does not exist"); BatchDisassociateResourcesFromCustomLineItem is ungated by the same omission.
Why: a client that inspects FailedAssociatedResources, or that retries on 404 after creating the line item, is given a resource-shaped answer to an authorization refusal and will loop or report partial success where AWS denies the whole call.
Fix: the shared authorization gate ahead of both batch-association handlers, before TargetArn resolution and before any per-resource result assembly.
Traces: billingconductor.batch-associate-and-disassociate-resources-require-payer-account.

Cause 5 of 5: the bidirectional pricing cross-reference list reads are not payer-gated; they answer 404 instead of 403.
AWS: Smithy — ListPricingRulesAssociatedToPricingPlan and ListPricingPlansAssociatedWithPricingRule (both POST, @readonly, @paginated) each model AccessDeniedException (errorKind client, httpError 403) and ResourceNotFoundException (404). Recorded behavior: from a non-payer account both sides of the relationship reject a syntactically well-formed ARN with 403 AccessDeniedException and the payer message, consistently — read-only cross-reference listing is not exempt from the payer restriction.
Emulator: ListPricingRulesAssociatedToPricingPlan answers error code ResourceNotFoundException (example message "the pricing plan does not exist"); the sibling ListPricingPlansAssociatedWithPricingRule is ungated by the same omission.
Why: 404 says "the caller may read this surface, the plan merely is not there", so entitlement probes and proof-of-absence logic conclude the account has visibility it does not have on AWS.
Fix: the shared authorization gate applied to both cross-reference read handlers, ahead of the ARN resolution and the state read.
Traces: billingconductor.pricing-rule-plan-bidirectional-listing-requires-payer-account.
