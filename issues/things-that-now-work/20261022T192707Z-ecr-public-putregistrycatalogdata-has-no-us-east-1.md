# ECR Public: PutRegistryCatalogData has no us-east-1 region gate, CompleteLayerUpload is a 501 stub, and its InvalidParameterException message uses a generic template (3 causes)

> _Note: this issue was identified against the code base at commit `17f16131651e3a76635c083c093a8581359ec045`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRegistryCatalogData

## Description
Behavioral replay of the simparity-behavioral-aws-v1 ecr-public suite surfaced THREE independent root causes in the ecr-public emulator that no already-filed issue carries (the auto-filed scaffold-stub issues name GetAuthorizationToken, UploadLayerPart, PutRepositoryCatalogData, TagResource and SetRepositoryPolicy; the open issue 20261022T154435Z-ecr-public-cfn-publicrepository-creates-nothing-putimage-accepts.md names CFN PublicRepository, PutImage, DeleteRepositoryPolicy, GetRepositoryCatalogData and three OTHER InvalidParameterException legs). ALL THREE causes below must be closed before this issue is resolved.

=== Cause 1 of 3: PutRegistryCatalogData accepts the call from a non-us-east-1 signing region and mutates account-global registry catalog data, instead of refusing with UnsupportedCommandException ===
AWS: Smithy PutRegistryCatalogData (input displayName -> RegistryDisplayName, @length 0..100; output registryCatalogData required) models UnsupportedCommandException (errorKind client, httpError 400), documented in the model as "The action isn't supported in this Region." ECR Public publishes endpoints in more than one Region, but registry catalog-data management is served only from us-east-1, so a PutRegistryCatalogData request signed for another Region (the SigV4 credential scope carries it) is refused with 400 UnsupportedCommandException and the account's registry catalog data is left untouched. Recorded behavior only for the message, whose rule is the operation name: an example is "PutRegistryCatalogData command is only supported in us-east-1."
Emulator: the same call signed for us-west-2 returns HTTP 200 with {'registryCatalogData': {'displayName': 'should-not-apply'}} and the write takes effect on the one account-global registry record. The handler (services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/ops/put_registry_catalog_data.rs) stores input.display_name into the shared state with no inspection of the request's signing Region, so no Region gate exists for this operation.
Why: this is an over-permissive accept on account-global, externally visible state. A client that relies on the Region gate (a deploy script pinned to the wrong Region, a multi-Region fan-out that should fail fast) silently overwrites the registry display name against the emulator and gets 400 UnsupportedCommandException against AWS; conversely, code that handles UnsupportedCommandException can never be exercised. Because the record is account-global and has no resource identifier, the wrong-Region write is also unrecoverable without knowing the previous value.
Fix: the PutRegistryCatalogData handler (or a shared ecr-public Region-gate check that runs before the registry-level handlers) must read the request's signing Region and return the modeled UnsupportedCommandException (400) for any Region other than us-east-1, leaving registry state unmodified.
Traces: ecr-public.put-registry-catalog-data-unsupported-command-rejected.

=== Cause 2 of 3: CompleteLayerUpload is an unimplemented scaffold and answers NotImplemented ===
AWS: Smithy CompleteLayerUpload (input repositoryName required, uploadId required, layerDigests required @length 1..100, optional registryId; output registryId/repositoryName/uploadId/layerDigest) models EmptyUploadException, UploadNotFoundException, InvalidLayerException, LayerPartTooSmallException, LayerAlreadyExistsException, InvalidParameterException, RepositoryNotFoundException and RegistryNotFoundException, all errorKind client with httpError 400. So an uploadId for which no UploadLayerPart call was ever made fails with 400 EmptyUploadException and the digest never enters the blob store, while an upload whose parts were actually uploaded completes 200 echoing layerDigest. Recorded behavior for the message, which is built from the request: an example is "The upload with id '<uploadId>' in the repository with name '<repo>' in registry with id '<account>' cannot be completed because it does not have any parts".
Emulator: every CompleteLayerUpload call returns the scaffold's 501 NotImplemented — services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/ops/complete_layer_upload.rs still carries the SCAFFOLDED, NOT IMPLEMENTED marker and returns Scaffolded::not_implemented. The suite observes error code NotImplemented where EmptyUploadException is required. This operation is NOT named by any already-filed stub issue.
Why: CompleteLayerUpload is the commit point of the ECR Public layer-upload data plane. 501 is not a modeled error for it, so SDK/docker-push error handling that branches on EmptyUploadException or UploadNotFoundException falls through to a generic failure, no layer can ever be finalized, and the negative path (completing an upload with no parts) cannot be verified at all.
Fix: implement the handler in complete_layer_upload.rs against the layer-upload/blob state, returning 400 EmptyUploadException when the named uploadId has no uploaded parts, the other modeled 400s for the absent-upload/absent-repository/digest-mismatch cases, and a 200 echoing the completed layerDigest otherwise.
Traces: ecr-public.complete-layer-upload-empty.

=== Cause 3 of 3: PutRegistryCatalogData's InvalidParameterException carries the generic framework validation message instead of ECR Public's 'Invalid parameter at ...' template, and interpolates the rejected value ===
AWS: Smithy PutRegistryCatalogData.displayName -> RegistryDisplayName (@length min 0, max 100) and the operation models InvalidParameterException (client, httpError 400). A displayName of 101 characters is refused with 400 InvalidParameterException whose message ECR Public fills from the request as a fixed template naming the member path and the violated rule only, never the rejected value: "Invalid parameter at 'displayName' failed to satisfy constraint: 'Member must have length less than or equal to 100'". The message is a deterministic function of the request (member + constraint), so the template is the requirement and the quoted string is an example over an example value; three independent checks observe the same template.
Emulator: status 400 and code InvalidParameterException are correct, but the message is the generic framework template "1 validation error detected: Value '<the entire rejected 101-character value>' at 'displayName' failed to satisfy constraint: Member must have length less than or equal to 100" — the rejected value is echoed back into the error body and the leading "N validation error detected" preamble replaces the service's wording. NOTE: Cause 5 of the open issue 20261022T154435Z-ecr-public-cfn-publicrepository-creates-nothing-putimage-accepts.md describes this same template defect on CreateRepository.repositoryName, CreateRepository.catalogData.description and SetRepositoryPolicy.policyText; it does not carry the PutRegistryCatalogData.displayName legs recorded here, so if that cause is fixed in the shared validation layer these three checks should be re-replayed to confirm this one closes with it.
Why: this message is the only place the service states which member and which constraint was violated, and clients, CLIs and conformance suites pin it; a caller matching the AWS template to surface a field-level error fails to match. Interpolating the rejected value also makes error bodies unbounded in size and copies caller content back over the wire.
Fix: the shared modeled-constraint -> InvalidParameterException mapping for this service (the validation layer that runs before the ecr-public handlers) must render the ECR Public template over the member path and rule only, with no rejected value interpolated.
Traces: ecr-public.put-registry-catalog-data-invalid-input-rejected, ecr-public.put-registry-catalog-data-invalid-parameter-rejected, ecr-public.registry-catalog-display-name-round-trip-and-limit.
