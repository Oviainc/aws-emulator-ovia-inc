# marketplace-catalog: request validation, BatchDescribeEntities partial errors, EntityType enum check and access-denied messages all diverge from AWS (5 root causes)

> _Note: this issue was identified against the code base at commit `9979b14c0e509985792db6dac0171a1eff5d6a10`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartChangeSet

## Description
The marketplace-catalog emulator answers (9/25 behavioral checks pass), but 16 checks fail across five distinct root causes. This issue bundles all five; each must be closed before submitting.

=== Cause 1 of 5: request-validation faults are emitted as generic aggregated Smithy constraint text instead of AWS Marketplace Catalog's single bracketed fault ===
AWS: recorded behavior only (the Smithy model constrains the members but says nothing about fault text). Smithy: Catalog @length 1..64 @pattern ^[a-zA-Z]+$; EntityType @length 1..255 @pattern ^[a-zA-Z]+$; NextToken @pattern ^[\w+=.:@\-\/]+$; ChangeSetName @pattern ^[\w\s+=.:@-]+$; ClientRequestToken @pattern ^[!-~]+$; Entity$Identifier @pattern ^[\w\-@]+$; modeled error ValidationException (httpError 422) on CancelChangeSet / DescribeChangeSet / DescribeAssessment / ListAssessments / ListChangeSets / ListEntities / StartChangeSet. The recorded responses show AWS returns ValidationException whose Message is ONE bracketed fault, built from the request: the field label, the offending value, and the pattern the service documents for that field — e.g. "[Requested catalog '<value>' is invalid. It should match with <catalog pattern>.]", "[Requested assessment identifier '<value>' is invalid. It should match with <assessment-id pattern>.]", "[Requested entity identifier '<value>' is invalid. It should match with <identifier pattern>.]", "[Requested change set name '<value>' is invalid. It should match with ^[\\w\\s+=.:@-]{1,100}$.]", "[Requested client request token '<value>' is invalid. It should match with ^[!-~]{1,64}$.]", "[Requested entity type '<value>' is invalid.]", "[Requested page token is invalid.]". Two observable sub-rules: (a) exactly one fault is reported even when several members are malformed, and (b) the quoted pattern is the service's own documented pattern, which is wider than the Smithy member pattern (catalog: ^(?![.-])(?!.*[.-]{2})(?![0-9]+\.[0-9.]+$)[a-zA-Z0-9.-]{1,47}(?<![.-])$; entity identifier: (^[a-zA-Z0-9][.a-zA-Z0-9/-]+[a-zA-Z0-9](@\d+)?$)|(^\$[a-zA-Z]{1,72}\.Entity\.Identifier$)).
Emulator: returns ValidationException (code matches) but with the generic framework message, aggregated over every violating member and addressed by wire path — e.g. "1 validation error detected: Value 'AWS_Marketplace' at 'catalog' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[a-zA-Z]+$" and "2 validation errors detected: Value 'DataProduct@1.0' at 'changeSet.1.member.entity.type' ...; Value 'bad#identifier' at 'changeSet.1.member.entity.identifier' ...".
Why: a client that parses or surfaces the service's fault text (or asserts on it in a test) sees a message in a different grammar, keyed by lowercase wire paths rather than the field label, listing N faults where AWS lists one, and quoting a narrower pattern than the one AWS tells the caller to satisfy. Because the fault text is produced by a known rule (it is built from the request member and its documented constraint) it is a requirement, not an example.
Fix: the per-operation input validation layer for marketplace-catalog — the service should run its own field validation (one fault, service-documented pattern, bracketed message) ahead of the generic model-constraint pass, rather than letting the generic constraint reporter format the ValidationException.
Traces: marketplace-catalog.cancel-change-set-not-found, marketplace-catalog.describe-change-set-id-not-found, marketplace-catalog.list-assessments-invalid-catalog-pattern-rejected, marketplace-catalog.describe-assessment-identifier-validation-boundary, marketplace-catalog.list-change-sets-invalid-next-token-rejected, marketplace-catalog.list-entities-invalid-entity-type-pattern-rejected, marketplace-catalog.start-change-set-entity-identifier-pattern-rejected, marketplace-catalog.start-change-set-invalid-change-set-name-rejected, marketplace-catalog.start-change-set-invalid-client-request-token-rejected, marketplace-catalog.start-change-set-entity-not-found. (Each of these checks stops at the first message assertion, so the ResourceNotFoundException legs that follow in the same checks were never exercised and may hide further divergence.)

=== Cause 2 of 5: StartChangeSet rejects a versioned Entity.Type that AWS accepts ===
AWS: recorded behavior only, and it contradicts the model here. Smithy: Entity$Type -> EntityType @pattern ^[a-zA-Z]+$, so 'DataProduct@1.0' violates the modeled pattern; the recordings nevertheless show real StartChangeSet accepting Entity.Type values of the form '<Type>@<version>' (e.g. 'DataProduct@1.0') and proceeding to later checks — the duplicate entity/change-type rule, then entity resolution — returning ValidationException for a duplicated (entity, change type) pair and ResourceNotFoundException ("Requested entity '<id>' does not exist.") for a well-formed but absent entity.
Emulator: fails the request up front with ValidationException naming 'changeSet.N.member.entity.type' as violating ^[a-zA-Z]+$, so no StartChangeSet request carrying a versioned entity type can reach any downstream rule. This also masks whether the duplicate (entity, change type) rule and the entity-existence lookup are implemented at all.
Why: every real StartChangeSet caller sends versioned entity types (that is how the Marketplace Catalog API addresses entity schema versions), so the emulator rejects the normal case; the emulator is strictly more restrictive than AWS and no change set can be started.
Fix: StartChangeSet's input validation / the Entity.Type constraint check — relax Entity.Type to the form the service actually accepts ('<Type>' or '<Type>@<version>') rather than enforcing the raw model pattern, then the duplicate-pair rule and entity lookup in the StartChangeSet handler/state.
Traces: marketplace-catalog.start-change-set-duplicate-change-type-rejected, marketplace-catalog.start-change-set-entity-identifier-pattern-rejected, marketplace-catalog.start-change-set-entity-not-found, marketplace-catalog.start-change-set-invalid-change-set-name-rejected, marketplace-catalog.start-change-set-invalid-client-request-token-rejected.

=== Cause 3 of 5: BatchDescribeEntities raises a request-level ValidationException instead of reporting per-item failures in Errors ===
AWS: Smithy: BatchDescribeEntities input EntityRequestList @required @length 1..20; output members EntityDetails (map) and Errors (map); modeled errors AccessDeniedException(403), InternalServiceException(500), ThrottlingException(429), ValidationException(422). Recorded behavior: BatchDescribeEntities returns HTTP 200 and reports each entry's failure per-item in the Errors map, keyed by the exact requested EntityId — ErrorCode 'ValidationException' for an EntityId that fails the documented entity-id pattern (message example "Requested entity id 'bad entity id!' is invalid. It should match with ^[a-zA-Z0-9][.a-zA-Z0-9/-]+[a-zA-Z0-9]$.") and ErrorCode 'ResourceNotFoundException' for a well-formed id that does not exist (message example "Requested entity '<id>' does not exist."); the failing key is omitted from EntityDetails. Mixed batches therefore succeed at the request level with two different per-item codes.
Emulator: fails the whole call with a request-level ValidationException ("1 validation error detected: Value 'bad entity id!' at 'entityRequestList.1.member.entityId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[a-zA-Z0-9][.a-zA-Z0-9/-]+[a-zA-Z0-9]$"), so no response body, no Errors map and no EntityDetails are ever produced for a batch containing a bad entry.
Why: the whole point of a batch API is partial failure. A client that submits 20 ids and reads Errors/EntityDetails gets an exception instead of a 200, loses the results for the valid ids in the same batch, and cannot distinguish a malformed id from a missing one.
Fix: the BatchDescribeEntities handler — per-item validation and lookup that populates the Errors map (keyed by the requested EntityId, with ErrorCode/ErrorMessage) and returns 200, instead of letting entityRequestList member constraints fail the request.
Traces: marketplace-catalog.batch-describe-entities-invalid-entity-id-pattern-rejected, marketplace-catalog.batch-describe-entities-partial-errors.

=== Cause 4 of 5: ListEntities accepts an unsupported EntityType and returns an empty page instead of ValidationException ===
AWS: Smithy: ListEntities input Catalog @required and EntityType @required (@pattern ^[a-zA-Z]+$); modeled error ValidationException (httpError 422). Recorded behavior: AWS validates EntityType against its set of known Marketplace entity types, not just the regex shape — a letters-only value that names no real entity type ('Frobnicator', 'NotARealMarketplaceProductType') is rejected with ValidationException (message example "[Requested entity type 'Frobnicator' is invalid.]"), while a real type such as 'AmiProduct' succeeds.
Emulator: returns HTTP 200 with {"EntitySummaryList": []} for EntityType='Frobnicator' (observed response metadata: HTTPStatusCode 200, content-length 24).
Why: the emulator is overly permissive — a caller that typos an entity type, or targets a type this account cannot list, sees "no entities" instead of the rejection AWS gives, so the typo is silently indistinguishable from an empty catalog.
Fix: ListEntities' input validation — check EntityType against the known entity-type set and raise ValidationException before any listing is performed.
Traces: marketplace-catalog.list-entities-unsupported-entity-type-not-found, marketplace-catalog.list-entities-invalid-entity-type-pattern-rejected (whose second leg exercises the same letters-only-but-unsupported case).

=== Cause 5 of 5: AccessDeniedException on the tagging operations does not use AWS's authorization-failure message rule ===
AWS: Smithy: TagResource / UntagResource / ListTagsForResource take ResourceArn @required @pattern ^arn:[\w+=/,.@-]+:aws-marketplace:[\w+=/,.@-]*:[0-9]+:[\w+=,.@-]+(/[\w+=,.@-]+)*$ and model AccessDeniedException (httpError 403). Recorded behavior: for an entity ARN the caller does not own, the authorization check fails before any existence lookup and the message follows AWS's standard authorization-failure rule, built from the caller identity and the request: "User: <caller principal ARN, as returned by sts:GetCallerIdentity> is not authorized to perform: aws-marketplace:<Action> on resource: <resource id from the ARN> because no resource-based policy allows the aws-marketplace:<Action> action".
Emulator: returns the correct code (AccessDeniedException) but a message in a different grammar that names no principal and uses the full catalog/type path instead of the resource id — e.g. "Access is denied. The caller is not authorized to perform: aws-marketplace:TagResource on resource: AWSMarketplace/AmiProduct/<id> because no resource-based policy allows the aws-marketplace:TagResource action" (same shape for UntagResource and ListTagsForResource).
Why: the message is produced by a known rule (AWS's documented 'User: <principal> is not authorized to perform: <action> on resource: <resource>' form, assembled from the authenticated principal and the request's ARN), so clients, log scrapers and IAM-troubleshooting tooling that extract the denied principal from the message find none. This is a message-grammar divergence only — the 403/AccessDeniedException classification is already correct — hence the lowest severity in this bundle.
Fix: the tagging operations' authorization error construction (shared access-denied message builder for TagResource / UntagResource / ListTagsForResource) — render the caller principal ARN and the resource id from the request.
Traces: marketplace-catalog.tag-resource-not-found, marketplace-catalog.untag-resource-not-found.
