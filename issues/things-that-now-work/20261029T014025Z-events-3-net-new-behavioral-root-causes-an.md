## Operation
PutTargets, PutEvents

## Description
Three distinct, independent EventBridge ('events') root causes found by the behavioral replay. None of the three failing checks was reported ALREADY FILED or OWNED by an open issue, so no existing work item carries them. Cause 1 is a rendering defect on a path that DOES deliver; causes 2 and 3 are delivery/dead-letter paths that produce nothing at all. A fixer must close all THREE before submitting.

=== Cause 1 of 3: an InputTransformer InputPathsMap path whose array index is out of range renders as JSON null instead of AWS's empty string ===
AWS: Smithy: PutTargets.Targets -> Target$InputTransformer -> InputTransformer{InputPathsMap: TransformerPaths @length(0..100) "Map of JSON paths to be extracted from the event", InputTemplate: TransformerInput required @length(1..8192)}. The model does not state per-path rendering semantics, so for the rendering rule itself this is recorded behavior only: EventBridge resolves each InputPathsMap path against the envelope and substitutes it for the matching <key> placeholder in the template. A path that resolves to NOTHING — here $.detail.items[7] against detail.items = [10, 20, 30] — is substituted as the EMPTY STRING, so an unquoted placeholder ("beyond": <beyond>) renders as the JSON string "" and the delivered payload carries "beyond": "". This is distinct from a path that resolves to a JSON null ($.detail.nul): that renders as the literal null unquoted and as the text "null" when the placeholder is quoted, which the emulator already gets right. Every other form graded by this check — whole array, index, nested index, [*] projection, empty array, quoted whole-array text — matched.
Emulator: the same target delivers, but the unresolvable path is substituted as a JSON null, so the payload is {... 'beyond': None ...} where AWS sends {... 'beyond': '' ...}. Every other key in the rendered object is byte-identical to AWS's. Hypothesis: the transformer resolves a missing/out-of-range path to the same "absent" value it uses for an explicit JSON null, collapsing two cases AWS keeps apart.
Why: a consumer of a transformed payload cannot distinguish "the event had no such element" from "the element was present and null". A typed deserializer on the target side that accepts a string for that field (as AWS always sends) fails on null, and any downstream equality/schema check against the AWS-shaped payload diverges on exactly this field.
Emulator: see above.
Fix: the InputTransformer path-resolution/rendering component in the eventbridge service's rule target delivery path — the substitution step that fills <key> placeholders from InputPathsMap — must render a path that resolves to no value as the empty string, keeping an explicit JSON null rendering as null.

=== Cause 2 of 3: a rule with EXPRESS and STANDARD state-machine targets never starts an execution, so the envelope-as-input and <event id>_<uuid> naming contract is unobservable ===
AWS: recorded behavior only (no Smithy member governs target invocation). One rule carrying two Step Functions targets (an EXPRESS and a STANDARD state machine, each with a RoleArn granting states:StartExecution) starts exactly ONE execution per machine per matched event. Each execution's input is exactly the EventBridge envelope — keys {account, detail, detail-type, id, region, resources, source, time, version}, with source/detail-type/detail/account/region as published and resources []. Each execution's NAME is "<event id>_<uuid>": the fixed part is the "_" separator, the variable parts are the PutEvents result EventId of the delivered event and a per-execution UUID, so the two targets' executions of one event have DIFFERENT names. The STANDARD execution id is arn:aws:states:<region>:<account>:execution:<machine name>:<execution name>; the EXPRESS execution id is prefixed arn:aws:states:<region>:<account>:express:<machine name>:<execution name>: (express ids carry a further per-invocation suffix). The STANDARD execution is listed by ListExecutions on its machine.
Emulator: nothing observable happens. The check reports "Error: Check timed out after 60.0s" while re-publishing a matched event every 20 s and draining the queue the two state machines write to; no report from either machine ever arrives, so the first gate ("no single event started both state machines") is never satisfied and none of the input/name/ARN assertions is ever reached. Hypothesis: the rule's target-delivery path does not perform states:StartExecution for a state-machine target ARN at all.
Why: a client that fans an event out to a state machine gets no execution and no failure signal — no dead letter, no FailedEntryCount, nothing in ListExecutions — so an event-driven workflow silently never runs, and the execution name AWS derives from the event id (the only join key between the event and its execution) never exists.
Fix: rule target delivery in the eventbridge service — invoke StartExecution for a state-machine target under the target's RoleArn, pass the full envelope as the execution input, and mint the execution name as "<event id>_<uuid>" independently per target. Related open issue 20261024T190039Z-events-lambda-stepfunctions-eventbridge-delivered-step-functions-executions-never-progress-the.md concerns a delivered execution that does not progress and does not carry this check.

=== Cause 3 of 3: an SNS target on a CMK-encrypted topic is neither dead-lettered as NO_PERMISSIONS while the key policy excludes events.amazonaws.com nor published once the key policy grants it ===
AWS: recorded behavior only. For a rule target that is an SNS topic with KmsMasterKeyId set to a CMK whose key policy grants only the account root (the topic policy itself DOES allow events.amazonaws.com sns:Publish), configured with DeadLetterConfig and RetryPolicy {MaximumRetryAttempts: 0, MaximumEventAgeInSeconds: 60}: the publish fails inside SNS because SNS cannot call kms:GenerateDataKey, and the event lands in the target's dead-letter queue with message attributes ERROR_CODE = "NO_PERMISSIONS", RULE_ARN = the rule's ARN, TARGET_ARN = the topic ARN, and ERROR_MESSAGE carrying the nested KMS/SNS denial: "User: events.amazonaws.com is not authorized to perform: kms:GenerateDataKey on this resource because the resource does not exist in this Region, no resource-based policies allow access, or a resource-based policy explicitly denies access (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <id>; Proxy: null) (Service: AmazonSNS; Status Code: 400; Error Code: KMSAccessDenied; Request ID: <id>; Proxy: null)" — all of that is fixed text except the two per-call Request IDs (the check normalizes them to <id> before comparing, so they are explicitly not part of the requirement). No denied event reaches a queue subscribed to the topic. After PutKeyPolicy adds a statement allowing events.amazonaws.com kms:GenerateDataKey*/kms:Decrypt, an identical event IS published and the subscriber receives the envelope (source and detail as published).
Emulator: no outcome at all — "Error: Check timed out after 60.0s". While the key policy still excludes events, nothing arrives at the dead-letter queue within the window (the check's own budget is 180 s), so neither ERROR_CODE nor ERROR_MESSAGE nor the RULE_ARN/TARGET_ARN pair is ever produced, and the post-grant publish leg is never reached. Hypothesis: the SNS target delivery path never runs, so the topic's CMK is never consulted and the target-level DeadLetterConfig is never written.
Why: a client that encrypts a notification topic with a customer-managed key and attaches a dead-letter queue to detect a mis-scoped key policy sees absolutely nothing: no notification, no dead letter, no retry exhaustion. The one diagnostic that names kms:GenerateDataKey as the missing grant is absent, so the misconfiguration is undiagnosable, and after the key policy is fixed delivery still does not resume. Open issue 20261027T052336Z-events-4-net-new-behavioral-root-causes-api.md covers the sibling case where the TOPIC policy denies Publish (ERROR_CODE NO_PERMISSIONS with SNS's AuthorizationError text) and a CMK-encrypted BUS key being disabled; it does not carry this check or the KMS-key-policy-on-a-topic path.
Fix: rule target delivery and failure classification in the eventbridge service — perform the SNS publish for an encrypted topic, classify the SNS KMSAccessDenied failure as ERROR_CODE NO_PERMISSIONS, do not retry it past MaximumRetryAttempts: 0, write the envelope plus the four dead-letter attributes to the target's DeadLetterConfig queue, and publish normally once the key policy admits events.amazonaws.com.
