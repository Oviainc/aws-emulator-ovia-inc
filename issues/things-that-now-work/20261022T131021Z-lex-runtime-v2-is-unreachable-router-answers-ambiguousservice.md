# Lex Runtime V2 is unreachable: router answers AmbiguousService for every 'lex'-signed request, so no runtime dialog check runs

> _Note: this issue was identified against the code base at commit `6f82ed95aacdd57d8c8c0220ec6b50c75b2537e1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateBot

## Description
Cause 1 of 1: every lex-runtime-v2 behavioral check dies on its first call — lexmodelsv2 CreateBot, the fixture step that stands up the bot the runtime checks then talk to — because the emulator's request router resolves the target service from the sigv4 signing name / endpoint prefix alone. Four emulated services legitimately share the signing name 'lex', so the router refuses the request instead of dispatching it, and no runtime operation (RecognizeText, RecognizeUtterance, PutSession, GetSession, DeleteSession) is ever reached. All 10 lex-runtime-v2 checks error identically. Failing check ids: lex-runtime-v2.deleted-session-state-is-gone-and-get-session-rejected, lex-runtime-v2.put-session-rejects-an-intent-the-locale-does-not-define, lex-runtime-v2.put-session-seeds-dialog-state-for-the-next-turn, lex-runtime-v2.recognize-text-elicits-missing-required-slot, lex-runtime-v2.recognize-text-fills-slot-and-fulfills-intent, lex-runtime-v2.recognize-text-rejects-an-unbuilt-locale, lex-runtime-v2.recognize-text-rejects-an-unknown-bot-alias, lex-runtime-v2.recognize-utterance-text-stream-agrees-with-recognize-text, lex-runtime-v2.session-state-persists-across-turns, lex-runtime-v2.unmatched-utterance-returns-fallback-intent.

AWS: a shared sigv4 signing name across the Lex family is normal AWS and is NOT an error condition — the services are distinguished by endpoint/host, not by signing name. Smithy services/service-com-amazonaws-lexruntimev2-awsdeepsenseruntimeserviceapi2-0/smithy-model/com-amazonaws-lexruntimev2-awsdeepsenseruntimeserviceapi2-0.json declares service AWSDeepSenseRunTimeServiceApi2_0, version 2020-08-07, protocol restJson1, sdkId 'Lex Runtime V2', awsService.endpointPrefix 'runtime-v2-lex', arnNamespace 'lex', sigv4Name 'lex'. The sibling models declare the SAME sigv4Name 'lex' with DIFFERENT endpointPrefixes: lexmodelsv2 (LexModelBuildingServiceV2, 2020-08-07, restJson1) endpointPrefix 'models-v2-lex'; lexmodelbuildingservice (AWSDeepSenseModelBuildingService, 2017-04-19, restJson1) endpointPrefix 'models.lex'; lexruntimeservice (AWSDeepSenseRunTimeService) is the fourth claimant of 'lex'. Smithy also pins each operation's HTTP binding, which is what disambiguates these restJson1 APIs on the wire: CreateBot is PUT /bots -> 202 with botId/botStatus (errors ValidationException 400, ConflictException 409, PreconditionFailedException 412, ServiceQuotaExceededException 402, ThrottlingException 429, InternalServerException 500); RecognizeText is POST /bots/{botId}/botAliases/{botAliasId}/botLocales/{localeId}/sessions/{sessionId}/text -> 200 with sessionState/interpretations/messages; PutSession POST and GetSession GET and DeleteSession DELETE on /bots/{botId}/botAliases/{botAliasId}/botLocales/{localeId}/sessions/{sessionId} -> 200. 'AmbiguousService' is not a modeled error of either Lex service and does not exist in AWS.

Emulator: every request signed for 'lex' is rejected with error code AmbiguousService; the recorded message (example only) is "4 emulated services all claim requests for 'lex': lex, lex, lex, lex; the request is rejected rather than served by an arbitrary one". botocore retried to its ceiling ('reached max retries: 3'), i.e. the response is classified as retryable/server-side rather than as a modeled client error.

Why: a client cannot use Amazon Lex V2 against this emulator at all — neither the model-building control plane nor the runtime. Instead of a 202 CreateBot response or a modeled 400/404/409, the SDK sees a non-AWS error code, retries it three times and surfaces it as an unknown fault. Everything these checks exist to verify is therefore unverified: slot elicitation of a missing required slot, slot filling and intent fulfilment, session state persisting across turns, PutSession seeding dialog state, PutSession rejecting an intent the locale does not define, GetSession after DeleteSession answering 404, RecognizeText rejecting an unbuilt locale or an unknown bot alias, the fallback intent for an unmatched utterance, and RecognizeUtterance agreeing with RecognizeText.

Fix: the shared request router / service-resolution layer. For restJson1 services sharing a signing name it must dispatch on the awsService endpointPrefix taken from the request Host (runtime-v2-lex vs models-v2-lex vs models.lex vs runtime.lex) and/or on the operation's modeled HTTP method+URI, and must never answer AmbiguousService for a signing name AWS legitimately shares across services and API versions. Note: open issue 20261022T124043Z-glue-kinesis-analytics-v2-cross-service-glue-kinesis-analytics-v2-studio-notebook.md and 20261022T071206Z-kinesis-analytics-v2-is-entirely-unreachable-router-refuses.md report the same router defect for the 'kinesisanalytics' signing name (an awsJson1_1 pair, disambiguated by X-Amz-Target); neither carries any lex replay key, so the lex collision is filed here.

Traces: the 10 lex-runtime-v2 check ids listed above; all 10 report verdict 'error' at CreateBot.

## Evidence
Expected (AWS, per the Smithy models cited above): lexmodelsv2 CreateBot returns HTTP 202 with botId/botName/botStatus, or a modeled client error (ValidationException 400, ServiceQuotaExceededException 402, ConflictException 409, PreconditionFailedException 412, ThrottlingException 429). Subsequent lex-runtime-v2 calls return 200 (RecognizeText/PutSession/GetSession/DeleteSession) or a modeled ResourceNotFoundException 404 / ValidationException 400. Sharing sigv4Name 'lex' with the three sibling Lex services is expected and harmless because the four declare distinct endpointPrefixes (runtime-v2-lex, models-v2-lex, models.lex, runtime.lex).

Actual (emulator replay, all 10 lex-runtime-v2 checks, identical): botocore.exceptions.ClientError: An error occurred (AmbiguousService) when calling the CreateBot operation (reached max retries: 3): 4 emulated services all claim requests for 'lex': lex, lex, lex, lex; the request is rejected rather than served by an arbitrary one.

Suite report: Total 0/14 passed (0.0%); per-service pass rate lex-runtime-v2 0/10 (0%), 10 failed, every verdict 'error'. No RecognizeText/PutSession/GetSession/DeleteSession request was ever served, so no runtime assertion was evaluated. No failing lex check is marked ALREADY FILED or OWNED by an existing issue.

## Steps to Reproduce
1. Boot the emulator from mainline.
2. Create a role lexv2.amazonaws.com can assume via iam.create_role + iam.put_role_policy.
3. Point a botocore client at the emulator: lex = boto3.client('lexv2-models', endpoint_url=<emulator>).
4. Call lex.create_bot(botName=<name>, roleArn=<role arn>, dataPrivacy={'childDirected': False}, idleSessionTTLInSeconds=300, botType='Bot').
5. Observe error code AmbiguousService naming a 4-way 'lex' collision, retried to the botocore ceiling, instead of HTTP 202 with botId/botStatus. Any lexv2-runtime call (boto3.client('lexv2-runtime').recognize_text(...), put_session, get_session, delete_session) reproduces it identically, since those services also sign as 'lex'.
6. Replay the 10 lex-runtime-v2 check ids in trace_ids to confirm the fix; each must then get past CreateBot and exercise its runtime dialog assertions.
