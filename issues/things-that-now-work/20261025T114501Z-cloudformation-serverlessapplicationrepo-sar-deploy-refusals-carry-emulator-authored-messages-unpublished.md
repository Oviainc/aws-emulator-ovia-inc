# SAR deploy refusals carry emulator-authored messages: unpublished-version 404 and versionless-application 400 do not use AWS's wording

> _Note: this issue was identified against the code base at commit `a97363f812621dd47aa0891b39cb5eeebafd4acb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCloudFormationChangeSet

## Description
Both causes are grounded in the cross-service SAR deploy checks (groups deploy-serverlessrepo-changeset / deploy-sar-changeset), whose check-id service token is the composite `cloudformation__serverlessapplicationrepository__sqs`; the defective component in both is the serverlessapplicationrepository crate. This bundle carries 2 causes; BOTH must be closed before submitting.

Note on neighbouring filings: the open issue 20261022T182143Z-cloudformation-serverlessapplicationrepo-sar-deploy-path-requiredcapabilities-is-always-empty-never.md covers RequiredCapabilities derivation and the (now-landed) implementation of CreateCloudFormationChangeSet, and it does NOT cover the message wording below — CreateCloudFormationChangeSet now correctly answers 404/NotFoundException and 400/BadRequestException with the right status and error code, and only the message text diverges. These are new, distinct defects in the message templates.

Cause 1 of 2 — the 404 for a SemanticVersion the application never published uses the wrong message template.
AWS: Smithy models CreateCloudFormationChangeSet (POST /applications/{ApplicationId}/changesets, success 201) with BadRequestException(400)/ForbiddenException(403)/TooManyRequestsException(429)/InternalServerErrorException(500); the service additionally models NotFoundException (httpError 404), which this condition uses. The model does not specify message text, so recorded behavior only: when the request names a SemanticVersion the application has not published, SAR answers HTTP 404, Error.Code NotFoundException, and Error.Message "Application <application-arn> does not have a version <semantic-version>" — fixed text "Application " ... " does not have a version ", with the application ARN taken from the request's ApplicationId and the version string taken from the request's SemanticVersion; there is no trailing period.
Emulator: the same call answers HTTP 404 / NotFoundException (correct) but with the message "Version <semantic-version> could not be found for application <application-arn>." — a different sentence shape, the two variables in the opposite order, and a trailing period AWS does not emit. The text comes from the shared helper `crate::state::version_not_found_message(application_id, semantic_version)`, which the change-set handler calls on both version-resolution paths (the SemanticVersion path and the TemplateId-derived path).
Why: a client or test asserting on the refusal message — the common way to distinguish "that version was never published" from the other 404s this operation can raise (unknown application, unknown TemplateId), which all share error code NotFoundException — matches nothing. Anything that surfaces the message to a user (a SAM/CLI deploy wrapper) prints text no AWS user or runbook will recognise.
Fix: the message template in the version-not-found helper used by the operation's refusal path in the serverlessapplicationrepository crate — `crate::state::version_not_found_message` in src/state.rs, as called from src/ops/create_cloud_formation_change_set.rs. Because that helper is shared "with every other operation that resolves a version" (its own comment), the change must be made where the wording actually belongs so sibling operations that have their own AWS wording are not regressed.
Traces: cloudformation__serverlessapplicationrepository__sqs.deploy-sar-changeset-for-unpublished-version-rejected.

Cause 2 of 2 — the 400 for an application with nothing published is an emulator-authored sentence with remediation advice AWS does not give.
AWS: recorded behavior only (the model specifies BadRequestException 400 for this operation but no message text): asking for a change set on an application that has published no version at all is refused with HTTP 400, Error.Code BadRequestException, Error.Message "Can't create cloudformation changeset from application with no version." This message is entirely FIXED text — it interpolates nothing from the request or from state (no application ARN, no name, no version). The same precondition governs the sibling deploy path CreateCloudFormationTemplate (POST /applications/{ApplicationId}/templates), whose recorded refusal is HTTP 400 / BadRequestException with the fixed text "CloudFormation template can't be created from application with no version."
Emulator: CreateCloudFormationChangeSet answers HTTP 400 / BadRequestException (correct) with "Application <application-arn> does not have any versions. Create one with CreateApplicationVersion before deploying it." — a message built from the request (it interpolates the ApplicationId, which AWS's does not) plus a remediation sentence AWS never emits. The text is inlined in the handler's latest-version fallback (src/ops/create_cloud_formation_change_set.rs, the `application.latest().ok_or_else(...)` arm, around line 308). The replay never reached the CreateCloudFormationTemplate assertion in the same check because this one fails first, so the sibling path's wording must be corrected and verified together.
Why: the two deploy paths have DIFFERENT fixed AWS sentences for the same precondition, and a client that keys off the message (or a test fixture recorded against AWS) sees neither. The interpolated ARN also makes the message non-deterministic across accounts/regions where AWS's is constant, so message-equality checks that pass against AWS fail here for reasons unrelated to the request.
Fix: the refusal/validation path of the two deploy handlers in the serverlessapplicationrepository crate — src/ops/create_cloud_formation_change_set.rs (no-version fallback) and src/ops/create_cloud_formation_template.rs (its corresponding no-version 400) — each emitting its own fixed AWS sentence rather than one shared, request-derived sentence.
Traces: cloudformation__serverlessapplicationrepository__sqs.rejects-changeset-for-versionless-application.
