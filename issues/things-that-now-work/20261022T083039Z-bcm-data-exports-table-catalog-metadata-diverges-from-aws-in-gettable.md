# Table catalog metadata diverges from AWS in GetTable and ListTables

> _Note: this issue was identified against the code base at commit `20bba7fc76a2a325f0c97185e3cb0c31983ebe87`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
The emulator serves its own hand-written version of the Data Exports table catalog instead of the catalog AWS publishes. Every read of the catalog (GetTable for each supported table, and ListTables) answers HTTP 200 with a body whose column set, column types, table properties and description strings differ from AWS's. The catalog is static AWS reference data — identical in every account and Region — so the recorded responses are the contract, not environment-specific values. The faults are of three kinds: whole columns/properties absent or substituted, column Type values wrong, and Description strings paraphrased. 8 causes.

Cause 1 of 8: GetTable for the carbon-emissions table returns a column set and column descriptions that are not AWS's. AWS: Smithy GetTable -> GetTableResponse{TableName, Description, TableProperties, Schema: ColumnList}, Column{Name, Type, Description}; the model does not enumerate the catalog contents, so recorded behavior only — the recording shows AWS's columns for this table (payer_account_id, usage_account_id, usage_period_start/end, last_refresh_timestamp, product_code, region_code, model_version, location and the total_* emissions columns) each with AWS's own Description text. Emulator: HTTP 200 but with paraphrased Description text on every column (e.g. payer_account_id expected 'The account ID of the paying account. For an organization in AWS Organizations, this is the account ID of the management account.', got 'The account ID of the management account that pays for the usage the emissions are estimated for.') and a divergent set of emissions columns — the total_lbm_*, total_mbm_* and total_scope_*_emissions_* entries mismatch as whole Schema entries, i.e. the emulator's names do not line up with AWS's. Why: clients generate SQL/queries and downstream table definitions from this catalog, so a column AWS exposes under a different name simply is not queryable, and a consumer that renders the column documentation shows text AWS never emits. Fix: the static table-catalog data backing the GetTable handler for this table. Traces: bcm-data-exports-catalog-get-table#task#1.

Cause 2 of 8: GetTable for COST_AND_USAGE_DASHBOARD returns an empty/absent schema and the wrong table description. AWS: recorded behavior only — AWS answers with Description 'A view over CUR for CostAndUsageDashboard' and a full Schema (billing_period, usage_date, payer_account_id, payer_account_name, linked_account_id, linked_account_name, invoice_id, charge_type and the rest of the dashboard view's columns, each with Name/Type/Description). Emulator: HTTP 200, Description 'Cost and Usage Dashboard', and every one of those Schema entries is missing (got None). Why: a client that introspects this table to discover its columns gets nothing at all, so query generation, schema validation and any UI driven by the catalog break outright even though the call succeeded. Fix: the static table-catalog data backing GetTable — the COST_AND_USAGE_DASHBOARD entry needs its column list and AWS's description. Traces: bcm-data-exports-catalog-get-table#task#2.

Cause 3 of 8: GetTable for the CUR 2.0 table returns wrong column Types and paraphrased descriptions. AWS: recorded behavior only; Smithy Column.Type is the kind of data a column stores, and the recording shows AWS's Type and Description for each of the ~120 identity_*/bill_*/line_item_*/pricing_*/product_*/reservation_*/savings_plan_* columns. Emulator: HTTP 200 with a paraphrased Description on essentially every column (e.g. identity_line_item_id expected "This field is generated for each line item and is unique in a given partition. ...", got 'A unique identifier for every line item in a single delivery of the export.') and with the wrong Type on savings_plan_amortized_upfront_commitment_for_billing_period and savings_plan_savings_plan_rate. Why: a wrong Type makes a consumer cast or compare the column incorrectly (numeric columns typed as something else are the classic case), and the catalog is the only place a client can learn it. Fix: the static table-catalog data backing GetTable for the CUR 2.0 table (Type values first, then descriptions). Traces: bcm-data-exports-catalog-get-table#task#3 (cluster also covers bcm-data-exports-table-catalog-inspection#task#2).

Cause 4 of 8: GetTable for the cost-optimization-recommendations table reports numeric columns as Type 'Number' where AWS reports 'Double'. AWS: recorded behavior only — the recording shows Type 'Double' for estimated_monthly_cost_before_discount, estimated_monthly_cost_after_discount, estimated_monthly_savings_before_discount/after_discount, estimated_savings_percentage_before_discount/after_discount, and a distinct Type for recommendation_lookback_period_in_days and tags; the per-column Descriptions also differ (e.g. recommendation_id expected 'The ID for the recommendation.', got 'The identifier of the recommendation.'). Emulator: HTTP 200 with Type 'Number' on the money/percentage columns plus the paraphrased descriptions. Why: 'Number' is not a type name AWS emits here, so a client that maps catalog types onto its own (Athena/Glue/driver type maps) fails to resolve it and either errors or silently falls back to string for cost figures. Fix: the static table-catalog data backing GetTable for the recommendations table — emit AWS's Type tokens verbatim. Traces: bcm-data-exports-catalog-get-table#task#4.

Cause 5 of 8: GetTable for the FOCUS 1.0 table paraphrases every column description. AWS: recorded behavior only — the recording carries AWS's FOCUS column documentation (e.g. BilledCost 'A charge serving as the basis for invoicing, inclusive of all reduced rates and discounts while excluding the amortization of upfront charges (one-time or recurring).'; ChargeCategory 'Indicates whether the row represents an upfront or recurring fee, cost of usage that already occurred, an after-the-fact adjustment (e.g., credits), or taxes.'). Emulator: HTTP 200 with shortened rewrites for all ~42 columns (BilledCost 'A charge serving as the basis for invoicing, inclusive of all reduced rates and discounts.'; ChargeCategory 'The highest-level classification of a charge, based on the nature of how it is billed.'). Why: FOCUS column semantics are normative — the description is the spec text a consumer relies on to interpret the column, and a rewrite that drops a qualifier (here, the exclusion of upfront amortization) changes its meaning. Fix: the static table-catalog data backing GetTable for the FOCUS 1.0 table. Traces: bcm-data-exports-catalog-get-table#task#5.

Cause 6 of 8: GetTable for the FOCUS 1.0 preview table diverges on the DEPRECATED table property as well as on its column descriptions. AWS: recorded behavior only; Smithy GetTableResponse.TableProperties is a map echoed back for the requested table, and the recording shows a DEPRECATED entry for this preview table alongside AWS's FOCUS column descriptions. Emulator: HTTP 200 with $.TableProperties.DEPRECATED diverging and the same paraphrased FOCUS descriptions as cause 5. Why: DEPRECATED is how a client learns the preview table is on its way out; losing or altering it means a consumer keeps building exports on a table AWS flags as deprecated. Fix: the static table-catalog data backing GetTable — the preview table's TableProperties and descriptions. Traces: bcm-data-exports-catalog-get-table#task#6.

Cause 7 of 8: GetTable for the FOCUS 1.2 table diverges on TableProperties.TIME_GRANULARITY and on two whole columns. AWS: recorded behavior only — the recording shows AWS's TIME_GRANULARITY table property for this table and its x_CostCategories / x_UsageType columns, plus AWS's descriptions for the ~56 FOCUS 1.2 columns (e.g. BillingPeriodEnd 'The exclusive end bound of a billing period.'). Emulator: HTTP 200 with $.TableProperties.TIME_GRANULARITY diverging, $.Schema[Name="x_CostCategories"] and $.Schema[Name="x_UsageType"] mismatching as whole entries, and paraphrased descriptions throughout. Why: TIME_GRANULARITY is an input a client must supply when creating an export over this table, so a catalog that misstates it leads to CreateExport calls with an unsupported granularity; the two x_* columns are AWS-extension columns a consumer cannot query if the catalog does not describe them. Fix: the static table-catalog data backing GetTable for the FOCUS 1.2 table. Traces: bcm-data-exports-catalog-get-table#task#7.

Cause 8 of 8: ListTables returns the wrong table-property list for the catalog's tables. AWS: recorded behavior only; Smithy ListTables -> ListTablesResponse{Tables: TableList}, Table{TableName, Description, TableProperties: TablePropertyDescriptionList}, TablePropertyDescription{Name, ValidValues, DefaultValue, Description}. The recording shows AWS's property descriptions for COST_AND_USAGE_REPORT and COST_OPTIMIZATION_RECOMMENDATIONS, an INCLUDE_IAM_PRINCIPAL_DATA property ('Whether IAM principal columns should be included or not.', ValidValues TRUE/FALSE), AWS's Description for COST_AND_USAGE_DASHBOARD, and the first TableProperties entry of the FOCUS preview and FOCUS 1.2 tables.
