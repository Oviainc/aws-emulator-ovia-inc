# Route 53 Resolver endpoint state is fabricated (HostVPCId, no IP addresses) and CreateOutpostResolver/ListResolverConfigs are unimplemented

> _Note: this issue was identified against the code base at commit `df1261813c70037074c7525ba4fddd96df97f3b7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateResolverEndpoint

## Description
Four independent root causes in the route53resolver service's own handlers, found by the behavioral suite. A fixer must close ALL FOUR before submitting. (Note: the open issue 20261022T084101Z-route53resolver-route-53-resolver-endpoint-ops-skip-resource-validation.md covers CreateResolverEndpoint not REJECTING a nonexistent subnet and ListResolverEndpoints not echoing MaxResults; none of the four causes below is that defect.)

Cause 1 of 4: the Resolver endpoint's HostVPCId is synthesized from the request's subnet ids instead of being resolved to the VPC that owns those subnets.
AWS: ResolverEndpoint.HostVPCId is documented as "The ID of the VPC that you want to create the Resolver endpoint in" (Smithy: ResolverEndpoint.HostVPCId, target ResourceId, @length 1..64). Because CreateResolverEndpoint takes only IpAddresses[].SubnetId (Smithy: CreateResolverEndpoint.IpAddresses, required, @length 2..20), AWS derives HostVPCId from the VPC that owns the referenced subnets; it is always an existing vpc-* id a caller can join back to EC2 (DescribeVpcs/DescribeSubnets).
Emulator: CreateResolverEndpoint stores host_vpc_id = crate::state::host_vpc_id(&subnet_ids), a value computed from the subnet id strings. Against subnets created in VPC vpc-0000000000000001c the endpoint reported HostVPCId 'vpc-0197173960b6f189' — a VPC that exists nowhere in the emulator's EC2 state. Both checks fail the same way ('expected HostVPCId=<the created VPC>, got <a hash-derived id>'). The same value is what the HostVPCId ListResolverEndpoints filter matches on, so filtering by the real VPC id finds nothing either.
Why: a client that reads HostVPCId to associate resolver rules, to audit which VPC an endpoint serves, to filter ListResolverEndpoints, or to cross-check against EC2 gets an id that does not name any VPC. Infrastructure code that joins Resolver output to EC2 state silently diverges from AWS, and the endpoint appears to live in a VPC the account never created.
Why (requirement): the requirement is that HostVPCId equals the VPC of the subnets named in IpAddresses, not any particular string.
Fix: CreateResolverEndpoint's handler must resolve IpAddresses[].SubnetId against the emulator's EC2 subnet/VPC state and store that VPC's id as the record's host_vpc_id, instead of deriving an id from the subnet id strings; GetResolverEndpoint/ListResolverEndpoints then project the real value.
Traces: route53resolver.create-resolver-endpoint-nonexistent-subnet-rejected, route53resolver.resolver-endpoint-lifecycle-creating-to-operational. Code: services/service-com-amazonaws-route53resolver-route53resolver/src/ops/create_resolver_endpoint.rs:352.

Cause 2 of 4: a Resolver endpoint's IP addresses are stored with no IPv4 address, so ListResolverEndpointIpAddresses returns entries with the Ip member absent and no ENI ever exists.
AWS: IpAddressResponse.Ip is "One IPv4 address that the Resolver endpoint uses for DNS queries" (Smithy: IpAddressResponse.Ip, @length 7..36), and ListResolverEndpointIpAddresses returns IpAddresses of that shape. When a CreateResolverEndpoint request supplies only SubnetId, AWS ASSIGNS an address out of that subnet's CIDR and creates a matching VPC network interface, so every entry reaching status ATTACHED carries an Ip that EC2 also reports as an ENI PrivateIpAddress.
Emulator: the create path deliberately leaves ip unset when the request omits it ("the emulator holds no subnet inventory, so it cannot know a value"), and IpAddressRecord::to_response passes that None through. The check crashes with KeyError: 'Ip' reading ListResolverEndpointIpAddresses output: entries carry IpId/SubnetId/Status but no Ip at all, and no ENI is created in EC2 for the endpoint.
Why: the IP addresses are the only thing a caller can point a DNS client or a forwarding rule at. A client that reads them to configure on-premises forwarders, or that joins them to EC2 ENIs, gets null where AWS returns an address, so every address-driven workflow is unexercisable against the emulator even though IpAddressCount reports 2.
Fix: CreateResolverEndpoint (and AssociateResolverEndpointIpAddress) must allocate an address from the referenced subnet's CIDR in the emulator's EC2 state when the request omits Ip, record it on the IpAddressRecord, and create the corresponding network interface so EC2 and Resolver report the same addresses.
Traces: route53resolver.resolver-endpoint-ip-addresses-are-exactly-the-enis-ec2-reports. Code: services/service-com-amazonaws-route53resolver-route53resolver/src/ops/create_resolver_endpoint.rs:326-342, services/service-com-amazonaws-route53resolver-route53resolver/src/state.rs:184-195.

Cause 3 of 4: CreateOutpostResolver answers 501 NotImplemented, so no InstanceCount range validation happens.
AWS: CreateOutpostResolver takes InstanceCount (Smithy: CreateOutpostResolverRequest.InstanceCount, target InstanceCount) and models ValidationException (Smithy: CreateOutpostResolver errors include ValidationException, errorKind client, httpError 400). A request with an out-of-range InstanceCount is rejected with HTTP 400 / ValidationException whose message names the instance count; the recorded example is '[RSLVR-03002] The instance count must be equal to or greater than "4".' A request with a valid count against an Outpost that does not exist is also ValidationException, recorded example '[RSLVR-03007] Cannot find the Outpost with Arn "...".' The requirement is the 400 and the code ValidationException, with the message distinguishing the instance-count fault from the Outpost-lookup fault; the recorded texts are examples.
Emulator: the operation is a scaffold stub — services/.../src/ops/create_outpost_resolver.rs still carries the "SCAFFOLDED, NOT IMPLEMENTED" marker and answers HTTP 501 with error code NotImplemented. The check fails with 'expected ValidationException, got NotImplemented'. ListOutpostResolvers, used for the effect-absent read, is also a stub.
Why: a client cannot distinguish "the parameter is invalid" from "this emulator has no such operation": error-path tests of the Outpost resolver surface get 501 for every call, and nothing that validates an Outpost resolver configuration can run.
Fix: implement CreateOutpostResolver in its handler file, including the InstanceCount range check and the Outpost-existence check, both surfaced as ValidationException at HTTP 400, before any record is created.
Traces: route53resolver.create-outpost-resolver-invalid-instance-count-rejected. Code: services/service-com-amazonaws-route53resolver-route53resolver/src/ops/create_outpost_resolver.rs.

Cause 4 of 4: ListResolverConfigs answers 501 NotImplemented, so neither its success page nor its NextToken refusal exists.
AWS: ListResolverConfigs is @paginated (inputToken NextToken, outputToken NextToken, items ResolverConfigs, pageSize MaxResults) and models InvalidParameterException (Smithy: ListResolverConfigs errors include InvalidParameterException, errorKind client, httpError 400). A NextToken the service did not itself issue — garbage text, or a real token minted by a different List operation — is rejected with HTTP 400 / InvalidParameterException; the recorded message is built from the request and is therefore a requirement of that form: "Value ( <token> ) for parameter NextToken is invalid. The token is invalid." A call with no NextToken returns 200 with a ResolverConfigs page.
Emulator: the operation is a scaffold stub ("SCAFFOLDED, NOT IMPLEMENTED" marker) and answers HTTP 501 NotImplemented for every call. The check fails with 'expected InvalidParameterException for garbage NextToken, got NotImplemented'.
Why: paginating clients get 501 instead of either a page or a modeled pagination error, so any code that enumerates per-VPC resolver configuration cannot run, and token-validation behavior (which AWS deliberately makes InvalidParameterException here rather than InvalidNextTokenException) cannot be observed at all.
Fix: implement ListResolverConfigs in its handler file: return a ResolverConfigs page honouring MaxResults, mint/verify its own opaque cursor using the service's existing page-token helper, and refuse a token it did not mint with InvalidParameterException at HTTP 400.
Traces: route53resolver.list-resolver-configs-invalid-next-token-rejected. Code: services/service-com-amazonaws-route53resolver-route53resolver/src/ops/list_resolver_configs.rs.
