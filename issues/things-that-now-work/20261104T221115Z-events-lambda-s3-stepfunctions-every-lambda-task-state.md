# events__lambda__s3__stepfunctions: every Lambda Task state ends FAILED with error States.Runtime and an emulator-authored cause, and a state-machine role that does not trust states.amazonaws.com is not rejected (2 causes)

> _Note: this issue was identified against the code base at commit `d9cf74aafe764d4a8806a821a1189d14d75bb9bb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeExecution

## Description
Two net-new root causes behind seven failing checks in the events/lambda/s3/stepfunctions surface. All seven executions terminate in half a second with the same emulator-authored failure, so no Task-state semantics (ResultPath, input passthrough, task tokens, downstream S3 writes, permission boundaries) can be observed at all.

Cause 1 of 2: a Task state that targets a Lambda function is never dispatched; the execution ends FAILED with error "States.Runtime" and an emulator-authored cause. Failing checks: events__lambda__s3__stepfunctions.lambda-task-sfn-resultpath-merges-with-original-input, events__lambda__s3__stepfunctions.sfn-startexecution-input-passthrough-to-lambda-task, events__lambda__s3__stepfunctions.sfn-task-lambda-s3-write-denied-without-permission, events__lambda__s3__stepfunctions.sfn-task-lambda-writes-result-to-s3, events__lambda__s3__stepfunctions.sfn-waitfortasktoken-lambda-sendtaskfailure-fails-execution, events__lambda__s3__stepfunctions.sfn-waitfortasktoken-lambda-sendtasksuccess-resumes.
  AWS:      Smithy: DescribeExecution output carries status (ExecutionStatus enum), output (SensitiveData, max 262144) and, only on failure, error (SensitiveError, max 256) and cause (SensitiveCause, max 32768). A Task state whose Resource is a Lambda function ARN (or arn:aws:states:::lambda:invoke) invokes that function; on success the execution reaches status SUCCEEDED and `output` is the function's return value shaped by ResultPath/ResultSelector, and `error`/`cause` are absent. When the invocation itself fails, AWS reports the failure in Lambda's/States' own vocabulary — error names such as Lambda.ServiceException, Lambda.AWSLambdaException, States.TaskFailed, or the function-reported error name — with a cause produced by Lambda or by the interpreter, never a sentence about the emulator. For .waitForTaskToken, the execution stays RUNNING until SendTaskSuccess (output becomes the supplied output, status SUCCEEDED) or SendTaskFailure, whose modeled `error`/`cause` inputs become the execution's `error`/`cause` verbatim — so a SendTaskFailure with error "LambdaReportedFailure" must surface as error "LambdaReportedFailure".
  Emulator: every one of these executions ends, ~0.5 s after StartExecution, with status "FAILED", error "States.Runtime" and cause "the 'Invoke' operation of Lambda is not implemented by this emulator, so nothing was run for this task" — an emulator-authored sentence that is not an AWS cause, paired with an error name AWS does not use for a Lambda-integration failure. `output` is absent (None). The function body is never executed, so no S3 object is written and no task token is ever handed out.
  Why:      a client cannot run any Lambda-backed state machine. Happy paths never reach SUCCEEDED, so ResultPath merging, StartExecution input passthrough and the result-to-S3 side effect are unobservable; permission-boundary tests cannot distinguish a denied call from this blanket failure; and callback (.waitForTaskToken) flows never block, so SendTaskSuccess/SendTaskFailure can never be exercised. Error-handling code keyed on Lambda.* / States.TaskFailed or on the function-reported error name sees States.Runtime and takes the wrong branch, and anything parsing `cause` gets emulator prose.
  Fix:      the Step Functions interpreter's Task-state dispatch for the Lambda integration, and the Lambda Invoke handler it calls; the failure-mapping code that currently synthesises error "States.Runtime" plus the emulator sentence must map real invocation failures to AWS's error names and causes instead.
  Related:  open issues 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md, 20261029T065131Z-events-lambda-stepfunctions-a-task-state-with-resource.md and 20261102T091831Z-events-lambda-stepfunctions-every-task-state-invoking-lambda.md describe the same shape for OTHER service headings; none of them carries these seven checks' replay keys, so these are unowned here.
  Traces:   the six check ids above.

Cause 2 of 2: a state machine whose execution role does not trust states.amazonaws.com is accepted and its execution fails with the generic interpreter failure instead of a not-authorized-to-assume failure. Failing check: events__lambda__s3__stepfunctions.sfn-execution-role-wrong-trust-blocks-lambda-task.
  AWS:      recorded behavior only (role trust evaluation is not expressed in the Smithy model). A state machine created with a role whose trust policy names lambda.amazonaws.com but not states.amazonaws.com cannot be assumed by Step Functions: the execution terminates FAILED and its `cause` states that the role is not authorized to be assumed — the cause text contains "not authorized to assume" and names the role ARN taken from the state machine's roleArn. The correctly-trusted twin machine in the same check succeeds. The fixed part of the requirement is that the failure is attributed to the un-assumable role; the role ARN is a value from the request.
  Emulator: the wrongly-trusted machine fails identically to the correctly-trusted one — status "FAILED", error "States.Runtime", cause "the 'Invoke' operation of Lambda is not implemented by this emulator, so nothing was run for this task". The role's trust policy is never evaluated, so the two machines are indistinguishable and the assertion on "not authorized to assume" fails. (This cause is currently masked by Cause 1; it must be verified again once Lambda Task dispatch works.)
  Why:      a client gets no signal that its state machine role is misconfigured. A missing states.amazonaws.com trust relationship — one of the most common Step Functions setup errors — is reported as a runtime fault of the task rather than an authorization failure, so operators debug the wrong component, and negative-path tests that assert the authorization failure pass or fail for the wrong reason.
  Fix:      the Step Functions execution start/dispatch path must evaluate the state machine roleArn's trust policy for the states.amazonaws.com service principal and fail the execution with the not-authorized-to-assume cause naming that role.
  Traces:   events__lambda__s3__stepfunctions.sfn-execution-role-wrong-trust-blocks-lambda-task
