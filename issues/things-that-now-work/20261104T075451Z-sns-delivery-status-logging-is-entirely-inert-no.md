# sns: delivery-status logging is entirely inert — no SUCCESS/FAILURE record and no sns/<region>/<account>/<topic> log group is ever written for any protocol

> _Note: this issue was identified against the code base at commit `685d7dc1b36320cc963844050fe238af8df0451a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Publish

## Description
This issue carries 1 root cause, grounded in 5 failing behavioral checks (all of GROUP delivery-status-logging). Related OPEN issues name the same area but do NOT carry these replay keys and do not cover them: 20261029T065537Z-sns-delivery-status-logging-is-inert-for-the.md (lambda protocol, via a CFN-deployed role) and 20261025T064350Z-lambda-sns-sqs-a-cfn-deployed-sns-deliverystatuslogging.md (a CFN-deployed feedback role never assumed).

Cause 1 of 1: a topic configured with <ENDPOINT>SuccessFeedbackRoleArn / <ENDPOINT>FailureFeedbackRoleArn (+ SampleRate) produces no CloudWatch Logs output at all.

AWS: Smithy — SetTopicAttributes.Attributes documents the delivery-status attributes SQSSuccessFeedbackRoleArn, SQSSuccessFeedbackSampleRate, SQSFailureFeedbackRoleArn, LambdaSuccessFeedbackRoleArn, LambdaSuccessFeedbackSampleRate, LambdaFailureFeedbackRoleArn (and the HTTP/Firehose/Application equivalents), with the note: "The <ENDPOINT>SuccessFeedbackRoleArn and <ENDPOINT>FailureFeedbackRoleArn attributes are used to give Amazon SNS write access to use CloudWatch Logs on your behalf. The <ENDPOINT>SuccessFeedbackSampleRate attribute is for specifying the sample rate percentage (0-100) of successfully delivered messages. After you configure the <ENDPOINT>FailureFeedbackRoleArn attribute, then all failed message deliveries generate CloudWatch Logs." The observable contract the recordings exercise: for each delivery attempt SNS assumes that role and writes one JSON record into the log group named sns/<region>/<account-id>/<topic-name> for a success (and sns/<region>/<account-id>/<topic-name>/Failure for a failure), where <region>, <account-id> and <topic-name> are taken from the topic's own ARN. Each record carries notification.messageId (the MessageId Publish returned), status ("SUCCESS" or "FAILURE"), and a delivery object carrying destination (the subscription endpoint ARN), statusCode (202 for a lambda invoke, 403 for a denied SQS SendMessage) and providerResponse. For a denied SQS delivery providerResponse is a JSON document whose ErrorCode is exactly "AccessDenied" and whose ErrorMessage has the fixed text "User: sns.amazonaws.com is not authorized to perform: sqs:sendmessage on resource: <queue-arn> because no resource-based policy allows the sqs:sendmessage action" — only <queue-arn> is variable (the subscribed queue from the request/state); the rest is fixed. SampleRate gates success records only: 100 logs every delivery, 0 logs none, and failures are logged regardless of the sample rate. A feedback role that cannot write logs must NOT block delivery and must create no log group (recorded behavior for the negative half of that check). For the lambda protocol a successful invoke is logged SUCCESS/202 and a function SNS may not invoke is logged FAILURE/403 with AccessDeniedException in the provider response.

Emulator: nothing is ever written. All five checks publish probe messages in a bounded retry loop and poll logs:FilterLogEvents on the expected group; the group never comes into existence (ResourceNotFoundException for the whole window) and no record ever appears, so each check consumes its budget and is reported "Check timed out after 60.0s". The feedback attributes themselves are accepted and stored — services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/state.rs lists them in TOPIC_ATTRIBUTE_NAMES — but no code path turns a delivery attempt into a log record, for any protocol (sqs and lambda are both exercised here) and in either direction (success and failure).

Why: a client relying on AWS's behavior loses the only audit trail SNS gives for deliveries it cannot otherwise see. Operators and tests that assert "the message was delivered" / "the delivery was denied with 403 AccessDenied" by reading sns/<region>/<account>/<topic>[/Failure] get a ResourceNotFoundException instead of records, so delivery failures are silent, dashboards and alarms built on the feedback log groups never fire, and any workflow that waits for a delivery-status record hangs forever rather than failing.

Fix: the SNS Publish delivery path — services/service-com-amazonaws-sns-amazonaws... see services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/publish.rs (per-subscription delivery) plus the topic record that holds the feedback attributes in services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/state.rs. Each delivery attempt must emit a delivery-status record (create the log group/stream on first write, honour the success sample rate, always log failures) through the in-process callback into CloudWatch Logs, and must swallow a logging failure without affecting the delivery itself.

Traces: sns.sqs-success-feedback-role-writes-the-delivery-record-to-cloudwatch-logs; sns.sqs-failure-feedback-role-logs-the-denied-delivery-while-the-message-never-reaches-the-queue; sns.success-feedback-sample-rate-zero-writes-no-log-while-full-rate-logs-every-delivery; sns.feedback-role-without-logs-permission-still-delivers-and-writes-no-log-record; sns.lambda-feedback-roles-log-the-invocation-delivery-record-and-the-uninvokable-function-failure.

## Evidence
Expected (AWS): after Publish to a topic whose attributes include SQSSuccessFeedbackRoleArn + SQSSuccessFeedbackSampleRate=100 (role trusts sns.amazonaws.com and may logs:CreateLogGroup/CreateLogStream/PutLogEvents), logs:FilterLogEvents on log group "sns/<region>/<account>/<topic-name>" returns a record {"notification":{"messageId":"<published MessageId>",...},"status":"SUCCESS","delivery":{"destination":"<granted queue ARN>","statusCode":200,...}}; with SQSFailureFeedbackRoleArn set, a queue whose policy does not grant sns.amazonaws.com sqs:SendMessage yields exactly one record in "sns/<region>/<account>/<topic-name>/Failure" with status="FAILURE", delivery.destination = the denied queue ARN, delivery.statusCode = 403 and providerResponse parsing to ErrorCode="AccessDenied" and ErrorMessage="User: sns.amazonaws.com is not authorized to perform: sqs:sendmessage on resource: <denied queue arn> because no resource-based policy allows the sqs:sendmessage action". SampleRate=0 writes no success record while a twin topic at 100 writes one per delivery; the lambda protocol logs SUCCESS/202 for an invokable function and FAILURE/403 AccessDeniedException for one SNS may not invoke.

Actual (emulator): no log group named sns/<region>/<account>/<topic-name> or .../Failure is ever created and FilterLogEvents answers ResourceNotFoundException for the entire polling window, for every protocol and both directions. The five checks publish repeated probe messages and never observe a single record, ending as "Check timed out after 60.0s" (sns.feedback-role-without-logs-permission-..., sns.lambda-feedback-roles-..., sns.sqs-failure-feedback-role-..., sns.sqs-success-feedback-role-..., sns.success-feedback-sample-rate-zero-...). The feedback attributes round-trip fine (they are in TOPIC_ATTRIBUTE_NAMES in src/state.rs), so the configuration is accepted but inert.

## Steps to Reproduce
1. iam:CreateRole with a trust policy allowing sns.amazonaws.com sts:AssumeRole, and an inline policy allowing logs:CreateLogGroup, logs:CreateLogStream, logs:PutLogEvents on *.
2. sns:CreateTopic Name=<topic> Attributes={SQSSuccessFeedbackRoleArn=<role arn>, SQSSuccessFeedbackSampleRate="100", SQSFailureFeedbackRoleArn=<role arn>}.
3. sqs:CreateQueue twice: one with a queue Policy granting Principal {"Service":"sns.amazonaws.com"} sqs:SendMessage on the queue (condition ArnEquals aws:SourceArn=<topic arn>), one with NO policy. Subscribe both to the topic with Protocol=sqs.
4. sns:Publish to the topic and keep the returned MessageId.
5. logs:FilterLogEvents logGroupName="sns/<region>/<account>/<topic>" and logGroupName="sns/<region>/<account>/<topic>/Failure", polling for up to two minutes.
Observed: both calls raise ResourceNotFoundException for the whole window — no group, no SUCCESS record for the granted queue, no FAILURE/403 AccessDenied record for the denied queue. Repeating the same wiring with LambdaSuccessFeedbackRoleArn/LambdaFailureFeedbackRoleArn and a lambda subscription, or with SQSSuccessFeedbackSampleRate="0" against a twin topic at "100", likewise produces no records at all.
