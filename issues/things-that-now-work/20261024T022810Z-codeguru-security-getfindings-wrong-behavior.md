# No request path ever produces findings, so GetFindings always answers with an empty list

_Filed: 2026-10-24T02:28:10Z_
_Operation: GetFindings | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `d5cb6525aec300e57e039668d831e20baadf847e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Expected: GetFindings "Returns a list of all findings generated by a particular scan" — after a scan over code containing a detectable issue completes, the response carries Finding objects (id, severity, status, detectorId/detectorName, vulnerability, remediation, createdAt...), and the status filter / maxResults paging select among them.

Actual: the store's `findings` map (src/state.rs: `pub findings: BTreeMap<(String, String), Finding>`) has NO writer anywhere in src/ — its own doc comment says "`findings` is written only by a scan run's analysis, which this emulator does not perform". Consequently GetFindings returns `findings: []` for every settled scan regardless of what was scanned, the `status` filter and nextToken paging are dead code in practice, and BatchGetFindings can only ever answer with failedFindings entries carrying ITEM_DOES_NOT_EXIST. The service's primary read path therefore reports a hollow success: 200 with no data, for a scan the emulator itself recorded.

## Evidence

Smithy model: GetFindings is the paginated reader over Findings (items=findings) and Finding/FindingIdentifier shapes are fully modelled; BatchGetFindings resolves (scanName, findingId) against the same set. Handler: src/ops/get_findings.rs lines 253-286 reads store.findings_of(&scan_name), which is always empty; src/ops/batch_get_findings.rs lines 194-206 therefore always takes the ITEM_DOES_NOT_EXIST branch. Writers: grep for `findings.insert` in the crate matches only tests (tests/all/scan_lifecycle.rs:831/836, tests/all/metrics_summary.rs:178), which poke the store directly through the engine — no HTTP request can create a finding. Tests ASSERT the empty answer (tests/all/scan_lifecycle.rs:423-428: "a run nothing analyzed produced no findings").

## Steps to Reproduce

1. POST /uploadUrl {"scanName":"demo"}; POST /scans with the returned codeArtifactId and scanName=demo
2. Wait for the run to settle, then GET /findings/demo?status=All
3. Observe 200 with findings: [] and no nextToken; no sequence of API calls can ever make this list non-empty
4. POST /batchGetFindings with any {scanName: "demo", findingId: <anything>} -> findings: [] and failedFindings[0].errorCode = ITEM_DOES_NOT_EXIST
