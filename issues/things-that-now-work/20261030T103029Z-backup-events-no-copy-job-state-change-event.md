# backup__events: no "Copy Job State Change" event is ever published for a StartCopyJob, so every copy-job EventBridge delivery check hangs until the harness cap

> _Note: this issue was identified against the code base at commit `a7e7c796199c3206e516e4419763bcfe6474bea3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartCopyJob

## Description
One root cause behind the 3 net-new failing checks in the `backup__events` group (the group's other failures are ALREADY FILED stub clusters for UpdateFramework/StartRestoreJob/FilterLogEvents, or OWNED by an open issue, and are not re-filed here).

Related open issue, named for the fixer: 20261029T175130Z-backup-events-no-backup-copy-restore-recovery-point.md describes the same missing emission as its cause 1, but it does NOT carry the three replay keys below (its trace list names copy-job-state-change-event-pattern-match and the backup-job checks only), so those three checks are not gated by it and are filed here. Closing that issue's cause 1 will very likely close this one — but this issue's three check ids must be re-replayed before this work item is submitted. Note that since that issue was written StartCopyJob is no longer a scaffold stub (services/service-com-amazonaws-backup-cryocontrollerusermanager/src/ops/start_copy_job.rs now creates the copy job and the destination recovery point), which is why these three checks now reach the event-wait stage instead of erroring on NotImplemented; the emission gap is what remains.

=== Cause 1 of 1: a copy job's state transitions publish nothing onto the EventBridge default bus, so a rule matching source=aws.backup / detail-type="Copy Job State Change" never delivers to its target ===
AWS: recorded behavior only — the event envelope is not in the Backup or EventBridge Smithy model. AWS Backup natively emits a state-change event on the default event bus for each copy-job transition, with `source` = "aws.backup", `detail-type` = "Copy Job State Change" and a `detail` carrying at least `copyJobId`, `state` (one of the modeled CopyJobState values CREATED/RUNNING/COMPLETED/FAILED/PARTIAL — Smithy: CopyJob.State -> CopyJobState), `sourceBackupVaultArn`, `destinationBackupVaultArn` and `resourceArn`, alongside the standard envelope members (version, id, account, time, region, resources). Those two vault ARNs are the same values DescribeCopyJob reports in CopyJob.SourceBackupVaultArn / CopyJob.DestinationBackupVaultArn (Smithy: both @ARN on shape CopyJob), including when the destination vault lives in a different region than the source. An ENABLED rule whose pattern matches — whether the pattern filters on `source` alone, or lists several detail-types ("Backup Job State Change" and "Copy Job State Change") in one rule — delivers that envelope UNCHANGED to every configured target, so one rule with one SQS target receives both a backup-job and a copy-job envelope.
Emulator: nothing is published for any copy-job transition. start_copy_job.rs writes only the CopyJobRecord, the destination RecoveryPoint, the idempotency record and the by-vault index into crate::state, and the settle path that later moves the job to COMPLETED likewise only mutates stored records — there is no emission to the EventBridge default bus anywhere in the copy-job lifecycle (the same hole the related issue reports for backup/restore/recovery-point transitions). All three checks therefore sit in their sqs.ReceiveMessage loop until the harness's cap and are reported as `Error: Check timed out after 60.0s`; no error distinguishes "never delivered" from "not yet delivered".
Why: a client that reacts to copy completion — cross-region copy monitors, a queue or Lambda consumer that fans out on copy state, a rule that watches both job kinds with one pattern — observes absolutely nothing and blocks forever rather than receiving a terminal envelope. Because the emulator delivers no copy event at all, any downstream assertion about the event's content (its detail-type, its state, its source/destination vault ARNs for a cross-region copy) is unverifiable, and a suppression test on the same bus would pass vacuously.
Fix: the copy-job lifecycle's event-emission path in the backup crate (publish a state-change event onto the EventBridge default bus on every copy-job transition, with AWS's source, detail-type and detail members, taking the vault ARNs from the stored CopyJobRecord so a cross-region copy reports the destination vault's own region), plus the EventBridge rule-matching and target-dispatch path that must deliver one matched envelope to ALL of a rule's targets and must match a pattern that lists multiple detail-types.
Traces: backup__events.copy-job-state-change-event-triggers-rule, backup__events.backup-copy-job-cross-region-event-detail-fields, backup__events.backup-job-eventbridge-detail-type-list-matches-multiple-states.

## Evidence
Suite: backup__events 8/50 (16%), 42 failed; 3 of those are net-new (the rest are ALREADY FILED stub clusters or OWNED by open issues).

[mismatch] backup__events.copy-job-state-change-event-triggers-rule — `Error: Check timed out after 60.0s`. Rule pattern is source-only ({"source":["aws.backup"]}) with an SQS target; after StartBackupJob -> COMPLETED and StartCopyJob -> COMPLETED, the check's `_wait_for_message` predicate (body["detail"]["copyJobId"] == <copy job id>) never matches. Expected: one envelope with source=='aws.backup', detail-type=='Copy Job State Change', detail.state=='COMPLETED', detail.destinationBackupVaultArn == the destination vault ARN. Actual: no message ever arrives.

[mismatch] backup__events.backup-copy-job-cross-region-event-detail-fields — `Error: Check timed out after 60.0s`. Rule pattern {"source":["aws.backup"],"detail-type":["Copy Job State Change"]} + SQS target; copy is started into a vault created through a client in a DIFFERENT region than the source vault. Expected: an envelope whose detail.sourceBackupVaultArn and detail.destinationBackupVaultArn equal the two distinct vault ARNs and agree with DescribeCopyJob's CopyJob.SourceBackupVaultArn / CopyJob.DestinationBackupVaultArn. Actual: `_poll_sqs_for_event` never observes any event, so the detail fields cannot be compared at all.

[mismatch] backup__events.backup-job-eventbridge-detail-type-list-matches-multiple-states — `Error: Check timed out after 60.0s`. ONE rule whose pattern lists both "Backup Job State Change" and "Copy Job State Change", one SQS target. Expected: both detail-types delivered to that single target, each with detail.state=='COMPLETED'. Actual: `_wait_for_terminal_events` collects neither.

All three are emulator-caused: the emulator serves StartCopyJob 200 and settles the copy job in its own state, then publishes no event for that transition. No per-run value (request id, clock time, generated name) is part of the divergence.

## Steps to Reproduce
1. dynamodb.CreateTable -> poll DescribeTable to ACTIVE; iam.CreateRole trusting backup.amazonaws.com with the AWSBackupServiceRolePolicyForBackup/ForRestores managed policies attached.
2. backup.CreateBackupVault twice — a source vault and a destination vault (for the cross-region case, create the destination through a client in a different region).
3. events.PutRule(Name=r, State=ENABLED, EventPattern={"source":["aws.backup"],"detail-type":["Copy Job State Change"]}); repeat the run with the source-only pattern {"source":["aws.backup"]} and with a pattern listing both "Backup Job State Change" and "Copy Job State Change".
4. sqs.CreateQueue, set a queue Policy allowing events.amazonaws.com sqs:SendMessage with aws:SourceArn = the rule ARN, then events.PutTargets(Rule=r, Targets=[{Id:'target-1', Arn:<queue arn>}]).
5. backup.StartBackupJob(BackupVaultName=<source>, ResourceArn=<table arn>, IamRoleArn=<role>) and poll DescribeBackupJob to COMPLETED; take RecoveryPointArn.
6. backup.StartCopyJob(RecoveryPointArn=<that>, SourceBackupVaultName=<source>, DestinationBackupVaultArn=<destination arn>, IamRoleArn=<role>) and poll DescribeCopyJob until CopyJob.State is COMPLETED.
7. sqs.ReceiveMessage in a loop -> AWS delivers an envelope with source='aws.backup', detail-type='Copy Job State Change' and a detail carrying copyJobId, state='COMPLETED', sourceBackupVaultArn and destinationBackupVaultArn; the emulator delivers nothing and the loop runs until the harness cap (`Check timed out after 60.0s`). With the multi-detail-type pattern, neither the backup-job nor the copy-job envelope arrives on the single target.
