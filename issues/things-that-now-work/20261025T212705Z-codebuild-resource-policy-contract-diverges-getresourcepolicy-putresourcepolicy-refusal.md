# CodeBuild resource-policy contract diverges: GetResourcePolicy/PutResourcePolicy refusal messages are emulator-invented, and PutResourcePolicy accepts a report-group policy granting a disallowed mutating action

> _Note: this issue was identified against the code base at commit `6c3c71af8518aefa24fa94ce6987bd799f7db4df`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutResourcePolicy

## Description
FOUR distinct net-new root causes on the CodeBuild resource-sharing surface (PutResourcePolicy / GetResourcePolicy), all in the service crate services/service-com-amazonaws-codebuild-codebuild-20161006. ALL FOUR must be closed before this issue is resolved. Three are refusal-message divergences (the emulator reaches the right decision, right modeled error code and right HTTP 400, but serializes a sentence it composed itself); the fourth is a MISSING validation, where the emulator accepts with HTTP 200 a policy real CodeBuild refuses. These are not covered by the open codebuild issues the suite report names (20261022T172625Z-codebuild-builds-never-execute-every-build-faults-at.md, 20261025T014438Z-codebuild-8-further-divergences-getresourcepolicy-updatewebhook-deletebuildbatch-stubs.md, 20261025T062553Z-codebuild-6-further-divergences-startbuildbatch-takes-no-input.md, 20261025T192356Z-codebuild-updatewebhook-accepts-a-webhook-mutation-with-no.md): none of them carries any of the six replay keys listed below, and the suite marked none of these six checks ALREADY FILED or OWNED. The already-fixed 20261025T114418Z-codebuild-5-refusals-carry-emulator-invented-error-messages.md is the same CLASS of defect (invented refusal wording) but on five other operations (UpdateProject, CreateFleet, CreateWebhook, ListBuildsForProject, StartCommandExecution) — it is not a reopen: none of the resource-policy sites below was in its scope, and causes 1-3 here are refusals AWS also makes, so no previously-fixed call is left refused.

Cause 1 of 4: GetResourcePolicy's "no policy attached" refusal uses the wrong message.
AWS: Smithy GetResourcePolicy(resourceArn @required NonEmptyString @length min 1) -> { policy NonEmptyString }, modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400 defaulted). A well-formed Project or ReportGroup ARN that this account owns but that has no policy attached is refused with 400 ResourceNotFoundException and message `Resource ARN resource policy does not exist`. That string is wholly FIXED text — CodeBuild does not interpolate the ARN, the resource name or the account; the literal words `Resource ARN` are part of the sentence, not a substitution. The message text is recorded behavior only (the model documents the error only as "The specified Amazon Web Services resource cannot be found."); the code and the 400 are modeled and the emulator already matches them.
Emulator: 400 ResourceNotFoundException with message `Resource policy does not exist` — the emulator's own shorter sentence, emitted from the single constant crate::state::RESOURCE_POLICY_NOT_FOUND_MESSAGE.
Why: a client, CLI or sharing-automation wrapper that surfaces or string-matches the refusal reason (to tell "never shared" apart from "ARN invalid") gets text AWS never emits, so the branch keyed on AWS's sentence never fires and operators cannot match the reason to AWS documentation.
Fix: the not-found path of the GetResourcePolicy handler and the shared message constant it reads.
Traces: codebuild.get-resource-policy-absent-resource-not-found, codebuild.resource-policy-sharing-not-listed-for-owner.

Cause 2 of 4: PutResourcePolicy's malformed-document refusal uses the wrong message.
AWS: Smithy PutResourcePolicy(policy @required NonEmptyString @length min 1, resourceArn @required NonEmptyString @length min 1) -> { resourceArn }, modeled errors InvalidInputException and ResourceNotFoundException (both client, httpError 400 defaulted). A policy argument that is not a parseable JSON policy document (e.g. the string `{ not json`) is refused with 400 InvalidInputException and message `Problem parsing given policy`. That string is wholly FIXED text: CodeBuild quotes neither the submitted document (which is caller text), nor the member name, nor a parser position. Message text is recorded behavior only. Effect-absence is also required and the emulator already gets it right: the rejected call must not clobber a previously stored policy.
Emulator: 400 InvalidInputException with message `Invalid policy document` (constant crate::state::INVALID_POLICY_DOCUMENT_MESSAGE).
Why: the refusal reason is unmatchable against AWS; a caller cannot distinguish "document did not parse" from any other input rejection by the text AWS specifies, and deploy tooling that asserts on CodeBuild's wording reports a spurious difference.
Fix: the policy-document validation branch of the PutResourcePolicy handler (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/put_resource_policy.rs, the `is_policy_document` refusal at the `invalid_input(INVALID_POLICY_DOCUMENT_MESSAGE)` site) and the shared constant in src/state.rs.
Traces: codebuild.deploy-codebuild-report-group-put-resource-policy-malformed-rejected, codebuild.resource-policy-put-get-delete-roundtrip.

Cause 3 of 4: the invalid/unsupported resourceArn refusal uses the wrong message, on both PutResourcePolicy and GetResourcePolicy.
AWS: same modeled signature as above. A resourceArn that is not the ARN of a Project or ReportGroup (an ARN of an unsupported resource type) is refused BEFORE any state lookup with 400 InvalidInputException and message `Resource ARN is invalid` — again wholly FIXED text that echoes nothing from the request. GetResourcePolicy on that same ARN must refuse identically (InvalidInputException, `Resource ARN is invalid`), i.e. the bad resource type is a malformed input, never a valid-but-empty resource. Message text is recorded behavior only; code and status are modeled and already correct.
Emulator: 400 InvalidInputException with message `Invalid resource ARN` — the words of AWS's sentence reordered into the emulator's own phrasing (constant crate::state::INVALID_RESOURCE_ARN_MESSAGE, used by both handlers).
Why: byte-for-byte message mismatch on the one refusal that tells a caller "this ARN can never carry a CodeBuild policy"; wrappers that key on AWS's sentence mis-sort it, and the divergence hits both the write and the read path from one shared constant.
Fix: the shared INVALID_RESOURCE_ARN_MESSAGE constant in src/state.rs and its two use sites (src/ops/put_resource_policy.rs, src/ops/get_resource_policy.rs).
Traces: codebuild.put-resource-policy-unsupported-resource-type-rejected.

Cause 4 of 4: PutResourcePolicy stores a report-group policy that grants a mutating action instead of refusing it.
AWS: a CodeBuild report-group resource policy may grant only the fixed set of read-only consumer actions (codebuild:BatchGetReportGroups, codebuild:BatchGetReports, codebuild:ListReportsForReportGroup, codebuild:DescribeTestCases) — a consumer "cannot edit a report group or its reports" (report-groups-sharing-perms.html). A policy whose Statement grants a mutating action such as codebuild:DeleteReportGroup is refused with 400 InvalidInputException and message `Proposed policy was not valid: InvalidPolicy: Input policy containing action that is not allowed for resource type codebuild:ReportGroup`. Fixed text: the whole sentence including the `Proposed policy was not valid: InvalidPolicy: ` prefix; the only variable part is the resource-type token (`codebuild:ReportGroup`), derived from the type of the resourceArn in the request. Nothing of the submitted document is echoed. The refused call must leave NO policy attached, so a following GetResourcePolicy on the same ARN is 400 ResourceNotFoundException `Resource ARN resource policy does not exist` (see Cause 1), and a subsequent policy granting only a supported read action on the SAME report group must still be accepted. The action allow-list is not modeled (the model types `policy` only as NonEmptyString), so this rule and its message are recorded behavior only; the error code and 400 are modeled.
Emulator: the call SUCCEEDS — HTTP 200 with body {"resourceArn": "<the report-group ARN>"} — and the disallowed grant is stored and later read back. The handler's only policy check is a parseability test (`is_policy_document`); there is no action allow-list anywhere on the write path.
Why: this is a security-relevant permissive acceptance, not a cosmetic one. A caller is told it has shared a report group with a grant AWS would never store, so code validated against the emulator ships a policy real CodeBuild rejects at deploy time, and any test asserting that CodeBuild refuses write grants passes against the emulator while the grant appears to exist.
Fix: add the report-group action allow-list to the PutResourcePolicy validation in services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/put_resource_policy.rs (after the document parses and the ARN's PolicyTarget is resolved, before the insert into state), raising InvalidInputException with CodeBuild's sentence and leaving crate::state resource_policies untouched.
Traces: codebuild.put-resource-policy-write-action-rejected.
