# Payment Cryptography (control plane) is entirely unreachable: the router refuses every request with a non-AWS 'AmbiguousService' code because the control plane and the data plane share the SigV4 signing name 'payment-cryptography'

> _Note: this issue was identified against the code base at commit `864130c27fac834624c923941bb3208370e0885b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateKey

## Description
Cause 1 of 1: the router cannot decide which emulated service owns a 'payment-cryptography'-signed request, so it refuses the request before any handler runs. Every one of the 21 behavioral checks for this service fails on its FIRST call with the same refusal, so no control-plane operation is reachable at all.

AWS: Payment Cryptography is two distinct wire services that share one SigV4 signing name and are told apart by their endpoint and their protocol. Smithy (services/service-com-amazonaws-paymentcryptography-paymentcryptographycontrolplane/smithy-model): service PaymentCryptographyControlPlane, version 2021-09-14, protocol awsJson1_0, sdkId "Payment Cryptography", awsService.endpointPrefix "controlplane.payment-cryptography", arnNamespace "payment-cryptography", sigv4Name "payment-cryptography", 32 operations. Smithy (services/service-com-amazonaws-paymentcryptographydata-paymentcryptographydataplane/smithy-model): service PaymentCryptographyDataPlane, version 2022-02-03, protocol restJson1, sdkId "Payment Cryptography Data", awsService.endpointPrefix "dataplane.payment-cryptography", sigv4Name "payment-cryptography", 15 operations. On real AWS a control-plane call goes to controlplane.payment-cryptography.<region>.amazonaws.com as awsJson1_0 with X-Amz-Target "PaymentCryptographyControlPlane.<Operation>", and a data-plane call goes to dataplane.payment-cryptography.<region>.amazonaws.com as restJson1 on its own HTTP paths; neither endpoint ever answers for the other. CreateKey (KeyAttributes, Exportable required) answers 200 with the required Key member; its only modeled errors are AccessDeniedException 403, ConflictException 409, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ServiceUnavailableException 503, ThrottlingException 429, ValidationException 400. 'AmbiguousService' is not a modeled error of either service and is not an AWS error code at all; AWS never refuses a well-formed, correctly-signed request for being ambiguous.

Emulator: every request whose resolved route key is 'payment-cryptography' is refused pre-dispatch with error code 'AmbiguousService' and the message "2 emulated services all claim requests for 'payment-cryptography': payment-cryptography, payment-cryptography; the request is rejected rather than served by an arbitrary one". That whole message is emulator-authored framework text — AWS has no such wording; its only variable parts are the count and the repeated claimant name, both from the emulator's own service registry, not from the request. botocore classifies it as retryable and the SDK exhausts its retries first ("reached max retries: 3"), so each check dies on its first call: CreateKey for 19 checks, GetDefaultKeyReplicationRegions for default-replication-regions-enable-disable-roundtrip, GetParametersForExport for get-parameters-for-export-token-reuse-semantics. The one check reported as a [mismatch] rather than an error, create-key-invalid-attribute-combo-rejected, shows the same cause surfacing as a wrong error code: "an incoherent (asymmetric-signature KeyUsage + SYMMETRIC_KEY KeyClass + AES KeyAlgorithm) combination was rejected with 'AmbiguousService', expected \"ValidationException\"" — the refusal pre-empts CreateKey's attribute validation, so whether that validation itself is correct cannot be observed until routing is fixed.

Why: the Payment Cryptography control plane is bootstrapped but serves nothing. A client cannot create, read, tag, enable/disable, delete, restore, export, import or replicate a key, nor manage aliases or resource policies. Because the refusal arrives with an unmodeled error code that the SDK treats as retryable, a client does not even get a deterministic client error it could branch on — it burns its retry budget and then surfaces an error code absent from the service's error union, so error-handling code written against AWS (catch ValidationException / ResourceNotFoundException / ConflictException) never matches. The mismatch case shows the second-order harm: negative-path behavior is masked, so a caller that relies on AWS refusing an incoherent request sees the wrong code and the wrong status.

Fix: the control-plane crate's request-claim seam — `can_handle` in services/service-com-amazonaws-paymentcryptography-paymentcryptographycontrolplane/src/service.rs, whose default implementation compares the resolved route key only against `self.entry.identity().signing_name()`. Since both services' models declare sigv4Name "payment-cryptography", both claim identically and the router sees two claimants. That file's own documentation names this exact case ("Edit it for anything the model does not express: a signing name shared by several services"). Disambiguation must key on something the two services do not share — the awsJson1_0 X-Amz-Target prefix "PaymentCryptographyControlPlane." (and/or the "controlplane." vs "dataplane." endpoint prefix) for the control plane, and the restJson1 method+path bindings for the data plane — in both crates' `can_handle`, so exactly one service claims any given request and no request is refused with 'AmbiguousService'. Fixing it in only one crate leaves the other still claiming both. This is the same defect class already filed for other signing-name-sharing pairs (20261022T071206Z-kinesis-analytics-v2-is-entirely-unreachable-router-refuses.md, 20261022T092619Z-greengrassv2-every-request-rejected-with-ambiguousservice-because-greengrass.md, 20261022T110819Z-migrationhub-config-is-entirely-unreachable-router-resolves-by.md, 20261022T145747Z-connectcampaigns-is-entirely-unreachable-router-resolves-services-by.md); none of those issues covers payment-cryptography, and the open data-plane bootstrap issue (20261021T231811Z-bootstrap-service-com-amazonaws-paymentcryptographydata-paymentcryptographydataplane.md) does not cover it either — the control plane is bootstrapped and this is its routing defect.

Traces: all 21 payment-cryptography checks, listed in trace_ids; representative examples are payment-cryptography.create-key-reaches-create-complete-state (CreateKey), payment-cryptography.create-key-invalid-attribute-combo-rejected (the mismatch form), payment-cryptography.default-replication-regions-enable-disable-roundtrip (GetDefaultKeyReplicationRegions) and payment-cryptography.get-parameters-for-export-token-reuse-semantics (GetParametersForExport).

## Steps to Reproduce
1. Boot the emulator (both service-com-amazonaws-paymentcryptography-paymentcryptographycontrolplane and service-com-amazonaws-paymentcryptographydata-paymentcryptographydataplane are mounted from the workspace).
2. Point a botocore/boto3 'payment-cryptography' client at the emulator endpoint and call any control-plane operation, e.g.:
     pc = boto3.client("payment-cryptography", endpoint_url=<emulator>)
     pc.create_key(KeyAttributes={"KeyUsage": "TR31_D0_SYMMETRIC_DATA_ENCRYPTION_KEY", "KeyClass": "SYMMETRIC_KEY", "KeyAlgorithm": "AES_128", "KeyModesOfUse": {"Encrypt": True, "Decrypt": True, "Wrap": True, "Unwrap": True}}, Exportable=True)
3. Observe the call is retried 3 times and then fails with error code 'AmbiguousService' and the message "2 emulated services all claim requests for 'payment-cryptography': payment-cryptography, payment-cryptography; ..." instead of returning 200 with a Key.
4. Repeat with GetDefaultKeyReplicationRegions() and GetParametersForExport(...) — same refusal, so the defect is at routing, not in any one operation.
5. Replay the 21 checks in trace_ids to confirm a fix; all of them currently die on their first call. Note create-key-invalid-attribute-combo-rejected additionally asserts the incoherent-attribute CreateKey is refused with ValidationException (400), which can only be evaluated once routing resolves.
