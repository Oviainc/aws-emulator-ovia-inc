# sagemaker-featurestore-runtime refusal messages are emulator-authored prose: five diverging error texts across BatchGetRecord, GetRecord, PutRecord and UpdateRecord (5 causes)

> _Note: this issue was identified against the code base at commit `5b71589754f95f05f88c1a0ee9ccd691bbc5f701`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateRecord, PutRecord, GetRecord, BatchGetRecord

## Description
Five distinct root causes in the SageMaker Feature Store runtime (data-plane) error surface. In every case the HTTP status and the wire error CODE are correct — only the `Message` text diverges, and each diverging text is emulator-authored prose (or, in cause 3, the Smithy exception's DOC paragraph used verbatim as a runtime message) rather than the message AWS emits for that error class. All five live in the same service crate (`sagemakerfeaturestoreruntime`) and all are grounded in failing behavioral checks. None of the open SageMaker issues cover this service: 20261023T183034Z-sagemaker-feature-store-data-plane-is-not-event.md covers event-time ORDERING of PutRecord and offline-store propagation under service `sagemaker`, not the data-plane refusal texts below, and 20261029T072224Z-s3-sagemaker-a-feature-store-feature-group-with.md owns the two s3__sagemaker offline-store checks.

Cause 1 of 5: BatchGetRecord's over-limit Identifiers list is refused with a non-AWS validation message.
Failing check ids: sagemaker-featurestore-runtime.batch-get-record-too-many-identifiers-rejected
AWS: Smithy (com.amazonaws.sagemakerfeaturestoreruntime) BatchGetRecordRequest.Identifiers -> BatchGetRecordIdentifiers, a list with @length {min: 1, max: 100}; the operation declares no modeled error for it, so the service-common `ValidationError` family carries it and the recorded wire code for this constraint is `ValidationException` (HTTP 400). Recorded behavior for the text: AWS returns the standard constraint-violation rendering, whose FIXED text is `N validation error detected: Value '<rendered value>' at '<member path>' failed to satisfy constraint: Member must have length less than or equal to 100`. Its VARIABLE parts are: the error count (`1` here), the member path taken from the request member (`identifiers`), the constraint bound taken from the model (`100`), and the rendered value — the submitted list serialised as the service's Java-style struct rendering, one `BatchGetRecordIdentifier(featureGroupName=<name from request>, recordIdentifiersValueAsString=[<values from request>], featureNames=null)` per submitted element, comma-separated inside `[...]`, with `featureNames=null` where the request omitted FeatureNames.
Emulator: the code is right (`ValidationException`) but the Message is not the constraint-violation rendering above — the assertion `message == expected` fails, so no `N validation error detected: ... at 'identifiers' failed to satisfy constraint: Member must have length less than or equal to 100` text with the serialised identifier list is produced.
Why: clients and test suites that parse the `N validation error detected: ... at '<member>' failed to satisfy constraint: ...` rendering to report which request member was invalid get no member path and no bound, so a 101-element batch surfaces as an opaque 400 instead of a diagnosable list-length violation.
Fix: the request-validation layer for BatchGetRecord in this service crate — the list-length check on `Identifiers` must raise the shared constraint-violation message builder (count + value rendering + member path + bound) instead of a hand-written sentence.
Traces: sagemaker-featurestore-runtime.batch-get-record-too-many-identifiers-rejected (assertion at run():40).

Cause 2 of 5: an unresolvable FeatureGroupName is refused with the emulator's own "does not exist" sentence instead of AWS's ARN-bearing not-found text.
Failing check ids: sagemaker-featurestore-runtime.get-record-nonexistent-feature-group-rejected, sagemaker-featurestore-runtime.put-record-nonexistent-feature-group-validation-rejected
AWS: Smithy models `ValidationError` as a service-common error (errorKind client, httpError 400, doc "There was an error validating your request."); PutRecord declares no ResourceNotFound at all, and FeatureGroupName accepts a name OR an ARN (FeatureGroupNameOrArn pattern `^(arn:aws[a-z\-]*:sagemaker:[a-z0-9\-]*:[0-9]{12}:feature-group/)?([a-zA-Z0-9]([-_]*[a-zA-Z0-9]){0,63})$`). Recorded behavior for the text: an unresolvable FeatureGroupName on GetRecord and PutRecord is refused with code `ValidationError` and the message whose FIXED text is `Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name [` ... `].`, the VARIABLE part being the fully-qualified feature-group ARN the service resolved the request's name to — `arn:aws:sagemaker:<region of the endpoint>:<account id of the caller>:feature-group/<FeatureGroupName from the request>`.
Emulator: returns the correct code `ValidationError` but the message `Validation Error: FeatureGroup with name <name> does not exist.` — a different fixed text, and it reports the bare name where AWS reports the resolved ARN.
Why: a client that keys its handling (or its logs/alarms) off the `Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name [...]` text, or that extracts the feature-group ARN from the refusal to report which account/region it looked in, gets neither; the refusal is also not distinguishable from an input-syntax validation failure.
Fix: the feature-group resolution step shared by the GetRecord and PutRecord handlers — when the lookup misses, construct the ValidationError message from the AWS template, qualifying the requested name into a feature-group ARN using the request's region and account.
Traces: sagemaker-featurestore-runtime.get-record-nonexistent-feature-group-rejected (assertion at run():42), sagemaker-featurestore-runtime.put-record-nonexistent-feature-group-validation-rejected (assertion at run():39). The same text is additionally asserted for UpdateRecord by update-record-missing-record-resource-not-found, which fails earlier on cause 4.

Cause 3 of 5: UpdateRecord's stale-EventTime ConflictException message is the Smithy exception's documentation paragraph, not AWS's runtime message.
Failing check ids: sagemaker-featurestore-runtime.update-record-conflict-stale-event-time-rejected, sagemaker-featurestore-runtime.update-record-event-time-omitted-preserves-existing-event-time
AWS: Smithy `ConflictException` (errorKind client, httpError 409, Message @length max 2048) is the modeled error for UpdateRecord; its DOC paragraph reads "The service rejected the update because the provided EventTime is older than the record's current EventTime. To persist the update, retrieve the record's latest EventTime and resubmit the request with an EventTime that is equal to or newer than the current value." Recorded behavior for the message actually sent on the wire: code `ConflictException` with the wholly fixed text `Update rejected: the provided EventTime is older than the record's current EventTime. The record was not modified.` — no variable parts; it names no identifier, timestamp or feature group.
Emulator: answers the correct code `ConflictException` but puts the model's DOC paragraph in the Message, i.e. "The service rejected the update because the provided EventTime is older than the record's current EventTime. To persist the update, retrieve the record's latest EventTime and resubmit the request with an EventTime that is equal to or newer than the current value."
Why: documentation prose is not a wire message — a client matching on AWS's refusal text never recognises the conflict, and the emulator's text omits AWS's explicit statement that the record was NOT modified, which is the fact a retry path keys on.
Fix: the UpdateRecord handler's conflict path / error construction — emit the fixed runtime text rather than defaulting the Message to the exception shape's documentation string (the same defaulting is likely shared by other modeled errors in this crate).
Traces: sagemaker-featurestore-runtime.update-record-conflict-stale-event-time-rejected (assertion at run():45), sagemaker-featurestore-runtime.update-record-event-time-omitted-preserves-existing-event-time (assertion at run():59; the rest of that check — EventTime preserved when omitted, feature applied, stale update not applied — passed).

Cause 4 of 5: UpdateRecord's record-level not-found message uses the wrong prefix and a request-member-flavoured sentence.
Failing check ids: sagemaker-featurestore-runtime.update-record-missing-record-resource-not-found
AWS: Smithy UpdateRecord declares `ResourceNotFound` (errorKind client, httpError 404, doc "A resource that is required to perform an action was not found."). Recorded behavior for the text: code `ResourceNotFound` with FIXED text `Record Not Found: Record not found with record identifier [` ... `].`, the VARIABLE part being the request's `RecordIdentifierValueAsString`. Note AWS distinguishes the two absences by PREFIX as well as code: `Record Not Found: ...` for a missing record (404 ResourceNotFound) versus `Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name [...]` for a missing feature group (400 ValidationError, cause 2).
Emulator: returns `Resource Not Found: Record with RecordIdentifierValueAsString rec-never-ingested was not found in FeatureGroup <fg name>.` — the feature-group-flavoured `Resource Not Found:` prefix, a different fixed sentence, the SDK member name echoed as prose, and a feature-group name AWS does not include.
Why: the two not-found classes become indistinguishable by message prefix, so a client that routes "record absent" (ingest it) differently from "feature group absent" (configuration error) mis-routes, and any assertion on AWS's wording fails.
Fix: the UpdateRecord handler's record-lookup miss path — build the `Record Not Found: Record not found with record identifier [<RecordIdentifierValueAsString>].` message, keeping the 404/ResourceNotFound classification it already gets right.
Traces: sagemaker-featurestore-runtime.update-record-missing-record-resource-not-found (assertion at run():31).

Cause 5 of 5: UpdateRecord's TtlDuration-without-EventTime refusal text diverges from AWS's.
Failing check ids: sagemaker-featurestore-runtime.update-record-ttl-without-event-time-rejected
AWS: Smithy UpdateRecordRequest.TtlDuration doc — "Amazon SageMaker Feature Store deletes the record when EventTime + TtlDuration elapses. If you omit this parameter, the record's existing TTL setting remains unchanged" — i.e. the TTL is only meaningful relative to an EventTime; the refusal itself is carried by the service-common `ValidationError` (400). Recorded behavior for the text: code `ValidationError` with the wholly fixed text `Validation Error: EventTime is required when TtlDuration is specified or when the feature group has a default TTL configured. Include the EventTime feature in the Features list.` — no variable parts; it does not name the feature group's EventTimeFeatureName.
Emulator: returns the correct code `ValidationError` but the message `Validation Error: TtlDuration requires an EventTime in the same request; include the feature group's EventTime feature 'event_time' in Features.` — a different fixed sentence that also interpolates the feature group's EventTimeFeatureName, a value AWS's message does not contain.
Why: the emulator drops the second half of AWS's rule (the requirement also applies when the feature group has a DEFAULT TTL configured and no TtlDuration is passed), so a client reading the refusal is told a narrower rule than AWS enforces; text-matching clients fail outright.
Fix: the UpdateRecord handler's TTL/EventTime co-requirement validation — emit AWS's fixed sentence, and apply the same gate to the default-TTL case the message describes.
Traces: sagemaker-featurestore-runtime.update-record-ttl-without-event-time-rejected (assertion at run():34; the positive control — TtlDuration together with EventTime accepted — passed).

## Evidence
Cause 1 — expected (AWS): code ValidationException, Message "1 validation error detected: Value '[BatchGetRecordIdentifier(featureGroupName=<fg>, recordIdentifiersValueAsString=[<id>], featureNames=null), ... x101]' at 'identifiers' failed to satisfy constraint: Member must have length less than or equal to 100". Actual (emulator): code ValidationException but a Message that is not that rendering — AssertionError at check line 40 (`assert message == expected`). Model ground truth: BatchGetRecordIdentifiers @length max 100.

Cause 2 — expected (AWS): code ValidationError, Message "Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name [arn:aws:sagemaker:<region>:<account>:feature-group/<name>].". Actual (emulator): code ValidationError, Message 'Validation Error: FeatureGroup with name <name> does not exist.' (observed for both GetRecord and PutRecord against a freshly generated, never-created feature-group name).

Cause 3 — expected (AWS): code ConflictException, Message "Update rejected: the provided EventTime is older than the record's current EventTime. The record was not modified.". Actual (emulator): code ConflictException, Message "The service rejected the update because the provided EventTime is older than the record's current EventTime. To persist the update, retrieve the record's latest EventTime and resubmit the request with an EventTime that is equal to or newer than the current value." — verbatim the Smithy ConflictException doc paragraph.

Cause 4 — expected (AWS): code ResourceNotFound, Message 'Record Not Found: Record not found with record identifier [<RecordIdentifierValueAsString>].'. Actual (emulator): 'Resource Not Found: Record with RecordIdentifierValueAsString <id> was not found in FeatureGroup <fg>.'

Cause 5 — expected (AWS): code ValidationError, Message 'Validation Error: EventTime is required when TtlDuration is specified or when the feature group has a default TTL configured. Include the EventTime feature in the Features list.'. Actual (emulator): "Validation Error: TtlDuration requires an EventTime in the same request; include the feature group's EventTime feature '<EventTimeFeatureName>' in Features."

In all five, the HTTP status and error code matched; only the Message text diverged, so each failure is an assertion on the message and nothing else in the surrounding check (positive controls, state-unchanged assertions, EventTime-preservation assertions) failed.

## Steps to Reproduce
Common setup for every cause: CreateFeatureGroup (sagemaker) with RecordIdentifierFeatureName=record_id, EventTimeFeatureName=event_time (Fractional), FeatureDefinitions record_id/event_time/feature_a/feature_b/feature_c, OnlineStoreConfig.EnableOnlineStore=true; wait for FeatureGroupStatus=Created. Then, with the sagemaker-featurestore-runtime client:

Cause 1: PutRecord one record, then BatchGetRecord with Identifiers = 101 entries [{FeatureGroupName: <fg>, RecordIdentifiersValueAsString: ['id-<i>']} for i in 0..100]. Read Error.Code (ValidationException) and Error.Message; AWS returns the '1 validation error detected: ... at \'identifiers\' failed to satisfy constraint: Member must have length less than or equal to 100' rendering, the emulator does not.

Cause 2: GetRecord(FeatureGroupName=<a never-created name>, RecordIdentifierValueAsString='rec-control') and PutRecord(FeatureGroupName=<a never-created name>, Record=[record_id, event_time]). Both: AWS -> ValidationError with the ARN-bearing 'Resource Not Found: Amazon SageMaker can't find a FeatureGroup with name [...]' text; emulator -> ValidationError with 'Validation Error: FeatureGroup with name ... does not exist.'

Cause 3: PutRecord record_id='rec-conf', event_time=<t>; wait until GetRecord returns it; then UpdateRecord with Features=[{event_time: <t-1000>}, {feature_a: 'should-not-apply'}]. AWS -> ConflictException 'Update rejected: ... The record was not modified.'; emulator -> ConflictException carrying the model's doc paragraph. Same divergence is reached via: PutRecord 'rec-noet'; UpdateRecord with Features=[{feature_a:'a2'}] (no EventTime); then UpdateRecord with Features=[{event_time:<t-5>},{feature_b:'b2'}].

Cause 4: against the existing feature group, UpdateRecord(RecordIdentifierValueAsString='rec-never-ingested', Features=[{event_time: now}, {feature_a:'x'}]) without ever having put that record. AWS -> ResourceNotFound 'Record Not Found: Record not found with record identifier [rec-never-ingested].'; emulator -> ResourceNotFound 'Resource Not Found: Record with RecordIdentifierValueAsString ... was not found in FeatureGroup ....'

Cause 5: PutRecord 'rec-ttlreq'; then UpdateRecord(RecordIdentifierValueAsString='rec-ttlreq', Features=[{feature_a:'should-not-apply'}], TtlDuration={Unit:'Hours', Value:1}) — i.e. a TTL with no EventTime feature in Features. AWS -> ValidationError 'Validation Error: EventTime is required when TtlDuration is specified or when the feature group has a default TTL configured. Include the EventTime feature in the Features list.'; emulator -> a differently worded ValidationError naming the feature group's EventTimeFeatureName.
