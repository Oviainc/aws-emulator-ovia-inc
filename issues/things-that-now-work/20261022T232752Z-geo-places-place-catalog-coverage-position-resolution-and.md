# geo-places place catalog coverage, position resolution and ValidationException message format diverge from AWS (8 causes)

> _Note: this issue was identified against the code base at commit `eb39d16500e074a8b39339f856d6c2c91f8a4fdc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Geocode

## Description
The geo-places emulator answers all five implemented Places operations (Geocode, ReverseGeocode, SearchText, SearchNearby, GetPlace) out of one small seeded catalog in services/service-com-amazonaws-geoplaces-placesservice/src/state.rs (seed_catalog()). Replaying the behavioral suite shows 8 distinct root causes: six are consequences of what that catalog does and does not hold (coverage, place-type coverage, density, position resolution, supported political views) and two are response-composition rules (result sizing from a sparse catalog, and ValidationException message construction). All 8 causes are in the geo-places service and must each be closed. 8 causes total.

Cause 1 of 8: Geocode and SearchText return an empty ResultItems list for well-known places outside the three seeded cities.
AWS: Smithy (services/service-com-amazonaws-geoplaces-placesservice/smithy-model/com-amazonaws-geoplaces-placesservice.json) models Geocode (POST /v2/geocode) and SearchText (POST /v2/search-text) as @readonly queries over AWS's own global place data; GeocodeResponse.ResultItems / SearchTextResponse.ResultItems are lists of 0..100 items, and the documented purpose of Geocode is to "convert a textual address or place into geographic coordinates". For a free-form query naming a globally unique landmark (e.g. "Golden Gate Bridge, San Francisco, CA, USA" or "Eiffel Tower" biased at its own coordinates) AWS returns at least one matching item whose Position is at that landmark and whose PlaceId resolves through GetPlace (/v2/place/{PlaceId}) to the same Title and Position.
Emulator: returns HTTP 200 with an empty ResultItems list for any place not in the seeded catalog. seed_catalog() holds places only in Washington DC, Seattle WA and Paris FR, so queries for landmarks elsewhere match nothing. (The roundtrip check shows the Seattle leg succeeding and the San Francisco leg returning no items at all, so this is coverage, not a matching bug.)
Why: a client doing address/landmark lookup, or chaining Geocode -> GetPlace, gets a silent empty page for valid real-world queries and cannot distinguish "no such place" from "this emulator has no data there"; any test or feature keyed on a landmark outside those three cities cannot run.
Fix: the service's seeded place catalog in src/state.rs (seed_catalog) must cover the landmark/address space these operations are expected to answer over, across multiple countries and regions, with the same records projected by Geocode, SearchText, SearchNearby, ReverseGeocode and GetPlace.
Traces: geo-places.geocode-getplace-roundtrip-consistency (assertion: "expected a geocode result for 'Golden Gate Bridge, San Francisco, CA, USA' to seed the round trip"), geo-places.search-text-finds-known-landmark ("expected SearchText to find results for 'Eiffel Tower'").

Cause 2 of 8: Geocode with Filter.IncludeCountries restricting an ambiguous name to a country returns no results, because the catalog holds only one homonym.
AWS: Smithy GeocodeRequest.Filter is a GeocodeFilter carrying IncludeCountries; AWS resolves "Paris" unfiltered towards Paris, France and, with Filter.IncludeCountries=["USA"], returns the US homonym (Paris, Texas) instead — every returned item's Address.Country.Code3 equal to "USA".
Emulator: the unfiltered query does return FRA (the control passes), but the USA-filtered query returns HTTP 200 with an empty ResultItems list. The country filter itself is applied in the Geocode handler (src/ops/geocode.rs, filter.include_countries -> in_countries), so the divergence is that no US place named "Paris" exists in the catalog to survive the filter.
Why: a client that uses Filter.IncludeCountries to disambiguate — the documented use of the member — gets an empty page rather than the in-country match, so country-scoped geocoding appears broken even though the filter code runs.
Fix: the seeded catalog in src/state.rs must carry homonymous place names in more than one country so inclusion filters have something to select rather than only something to exclude.
Traces: geo-places.geocode-include-countries-filter ("expected Geocode to return a USA-filtered match for 'Paris'").

Cause 3 of 8: the catalog exposes no Region-level place, so PlaceType coverage is incomplete.
AWS: Smithy models PlaceType as an enum including Country, Region, SubRegion, Locality, District, PostalCode, Block, Street, PointAddress, PointOfInterest, and GeocodeRequest.Filter.IncludePlaceTypes selects among them. An unfiltered Geocode for "Washington" returns both the Locality (Washington, DC) and the Region (Washington state).
Emulator: the same query returns only PlaceType values ['District', 'PointAddress', 'PointOfInterest', 'SubRegion'] — no Region (and no Locality for the ambiguity AWS resolves). src/state.rs defines PLACE_TYPE_REGION but seed_catalog() seeds no record of that type.
Why: a client filtering or branching on PlaceType (administrative-hierarchy UIs, "is this a city or a state" logic) never sees a whole class of results, and an IncludePlaceTypes filter for a type the catalog lacks can only ever return empty.
Fix: the seeded catalog in src/state.rs must include records at every administrative level the model's PlaceType enum names (notably Region and Country rows for the seeded countries), each projecting the correct PlaceType.
Traces: geo-places.geocode-include-place-types-filter ("expected the unfiltered 'Washington' query to include a Region match ..., got ['District', 'PointAddress', 'PointOfInterest', 'SubRegion']").

Cause 4 of 8: SearchText returns far fewer items than MaxResults and nothing for category-style queries, because of catalog density and because text matching ignores a place's categories.
AWS: Smithy SearchTextRequest.MaxResults is an Integer in range 1..100, documented as "an optional limit for the number of results returned in a single call"; SearchTextResponse.ResultItems is 0..100. For a chain name ("Starbucks") biased at downtown Seattle AWS fills the page (3 items for MaxResults=3), and for a category word ("coffee") inside a small downtown-Seattle Filter.BoundingBox it returns coffee-shop POIs whose Position lies inside the box.
Emulator: "Starbucks" with MaxResults=3 returns exactly 1 item, and "coffee" with Filter.BoundingBox=[-122.36, 47.60, -122.33, 47.62] returns an empty list. The BoundingBox filter itself is implemented (src/ops/search_text.rs, within_bounding_box), so the divergence is that the catalog holds at most one business per chain and no POI matching a category/food-type word — state.text_candidates matches titles and address components, not the Categories/FoodTypes a place carries.
Why: paging and "find me N nearby X" flows are untestable: a client asking for N results gets 1, and a category search (the dominant real use of SearchText) returns nothing, so it reads as "no coffee shops in downtown Seattle".
Fix: the catalog seeding in src/state.rs must hold several instances per business chain and per category within each seeded area, and the text-matching path (state.text_candidates / the relevance scorer) must also match a query against a place's Categories and FoodTypes so a category word is a query term.
Traces: geo-places.search-text-max-results-enforced ("expected exactly 3 results when MaxResults=3, got 1"), geo-places.search-text-bounding-box-filter ("expected SearchText to find coffee shops inside the bounding box").

Cause 5 of 8: SearchNearby's QueryRadius cannot be observed as a filter because the catalog has no density around a queried position.
AWS: Smithy SearchNearbyRequest.QueryPosition is @required and QueryRadius is DistanceMeters in range 1..21000000; SearchNearbyResultItem.Distance is the distance from QueryPosition. Widening the radius around a dense location (downtown Seattle, 40m -> 85m) strictly increases the set of places returned, and the narrower result set is a subset of the wider one.
Emulator: both radii return the same 2 places. The radius bound itself is applied (src/ops/search_nearby.rs -> state.nearby(query_position, query_radius)), but only two seeded records sit within 85m of the Space Needle, so radius changes are unobservable.
Why: a client cannot exercise proximity search or verify its radius handling; "nearby" always returns the same handful of places regardless of the radius asked for, so radius-driven UI (zoom-dependent result density) has no data to show.
Fix: the seeded catalog in src/state.rs must place enough records at varied distances around each seeded anchor position for QueryRadius to select between them.
Traces: geo-places.search-nearby-results-within-radius ("widening QueryRadius from 40m to 85m did not surface any additional results (2 places at both radii)").

Cause 6 of 8: ReverseGeocode resolves a position to an arbitrarily distant catalog entry instead of the place at that position.
AWS: Smithy ReverseGeocode (POST /v2/reverse-geocode) takes @required QueryPosition [longitude, latitude] with optional QueryRadius (1..21000000) and returns the place(s) at/nearest that point, with ReverseGeocodeResultItem.Distance measured from QueryPosition and Address naming that point's country/region/locality. For the Statue of Liberty's coordinates [-74.0445, 40.6892] AWS returns a New York place (Address.Country.Code2 "US", Region.Code "NY", Locality "New York") whose echoed Position is within ~0.01 degrees of the query.
Emulator: returns "District of Columbia, United States" — a Washington DC entry roughly 330 km away — i.e. nearest-of-catalog with no coverage or default-radius bound (Hypothesis: nearest-neighbour over the seeded records with no containment test and no bound when QueryRadius is absent).
Why: reverse geocoding is positional by definition; a client turning coordinates into an address silently gets an address in another state/country rather than an empty ResultItems list, so check-in, delivery and geofence-labelling features produce confidently wrong data.
Fix: ReverseGeocode's position resolution in src/state.rs (the nearest/containment lookup) must bound candidates to places that actually contain or lie near QueryPosition (and return an empty ResultItems list when nothing is in range), and the catalog must cover the positions it is expected to resolve. The open issue "geo-places ReverseGeocode rejects valid PoliticalView and ignores QueryPosition" (20261022T192438Z-geo-places-reversegeocode-rejects-valid-politicalview-and-ignores.md) describes the same unbounded nearest-of-catalog behavior from a wire fixture; this behavioral check is additional grounding and must pass too.
Traces: geo-places.reverse-geocode-country-for-known-position ("expected the Statue of Liberty, got District of Columbia, United States").

Cause 7 of 8: a valid, documented PoliticalView is rejected with ValidationException because the catalog holds no place in that country.
AWS: Smithy models PoliticalView on Geocode/ReverseGeocode/SearchText/SearchNearby/GetPlace as CountryCode, @length(min:2,max:3), @pattern ^([A-Z]{2}|[A-Z]{3})$, documented as "the alpha-2 or alpha-3 character code for the political view of a country ... to represent unresolved territorial claims through the point of view of the specified country". "RUS" satisfies that constraint and is a documented supported political view (the reverse-geocode-political-view developer-guide example), so AWS answers HTTP 200 and echoes ResultItem.PoliticalView = "RUS" (output member CountryCode3, @pattern ^[A-Z]{3}$), attributing a Crimean position to Russia (Country.Code2 "RU").
Emulator: answers HTTP 400 ValidationException with message "PoliticalView must name a country this service holds place data for" — src/state.rs political_view() resolves the requested view by searching the seeded catalog for a place with that country_code3 and fails when there is none. A constraint-satisfying political view is therefore a hard client error on every operation that accepts one.
Why: 400 is non-retryable, so any client that sets PoliticalView — the entire purpose of the member, for dispute-aware rendering — cannot make the call at all, instead of receiving a political-view-adjusted result set with PoliticalView echoed.
Fix: the political-view resolution in src/state.rs must accept any value satisfying the modelled CountryCode pattern (decoupled from catalog membership), echo it on each result item, and the catalog must carry the disputed-territory records whose attribution the view changes. The open issue 20261022T192438Z-geo-places-reversegeocode-rejects-valid-politicalview-and-ignores.md reports the same rejection from a wire fixture on ReverseGeocode; this check also exercises it and must pass.
Traces: geo-places.political-view-changes-country-code (ValidationException on ReverseGeocode with PoliticalView="RUS").

Cause 8 of 8: ValidationException messages are built in the wrong form for geo-places (status 400 and code ValidationException are already correct).
AWS: geo-places phrases input-validation failures as a short sentence naming the member at fault and the rule it broke, built from the request and the member's modelled constraint. Recorded behavior across five distinct validation paths: a missing-alternative violation is "At least one of the following fields must be set: 'QueryText', 'QueryComponents'."; a @pattern violation is "'PoliticalView' must match regex ^([A-Z]{2}|[A-Z]{3})$" (the pattern is the modelled one on CountryCode); a @range violation is "'QueryRadius' must not be less than 1" (DistanceMeters range 1..21000000); an unresolvable opaque identifier is "'PlaceId' must be a valid ID."; an unusable cursor is "'NextToken' must be a valid token.". The rule is: single-quoted member name + the violated constraint, and the modelled error is ValidationException (HTTP 400) in every case.
Emulator: returns ValidationException/400 (correct) with prose of its own construction, e.g. "either QueryText or QueryComponents must be provided", "PlaceId is not a place identifier issued by this service", "QueryRadius must be between 1 and 21000000 metres; 0 was supplied", "NextToken is not a pagination token issued by a previous SearchNearby call with the same parameters" (all from crate::state::validation_exception call sites in src/ops/*.rs and src/state.rs), and for the pattern violation the generic framework constraint text "1 validation error detected: Value 'us' at 'politicalView' failed to satisfy constraint: Member must satisfy regular expression pattern: ^([A-Z]{2}|[A-Z]{3})$" from the boundary validator rather than the service's own phrasing.
Why: clients and operators that surface or match on the service's validation text (log scraping, user-facing form errors, assertions pinned to AWS's wording) see a different sentence for every rule; the pattern case additionally leaks the generic smithy constraint-validator format, which no geo-places response uses. Only the message differs here — status and error code match.
Fix: the service's ValidationException construction (crate::state::validation_exception in src/state.rs, plus the boundary constraint validator's hook for this service) must format messages in the member-named form above, deriving member name and constraint from the request and the model instead of per-call-site prose. The exact sentences quoted above are the recorded examples of that rule, not literals to hard-code per check.
Traces: geo-places.geocode-missing-query-input-rejected, geo-places.getplace-unresolvable-place-id-rejected, geo-places.political-view-invalid-pattern-rejected, geo-places.reverse-geocode-radius-out-of-range-rejected, geo-places.search-nearby-invalid-next-token-rejected.
