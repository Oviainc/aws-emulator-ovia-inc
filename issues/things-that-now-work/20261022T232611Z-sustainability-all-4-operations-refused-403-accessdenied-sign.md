# Sustainability: all 4 operations refused 403 AccessDenied ("Sign the request with the emulator credentials") before dispatch, and the refusal uses code AccessDenied instead of the modeled AccessDeniedException

> _Note: this issue was identified against the code base at commit `eb39d16500e074a8b39339f856d6c2c91f8a4fdc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Resolution

Cause 2 is FIXED; Cause 1 is fixed for every signature the emulator can verify, and its residue — a `SigV4A`-signed request — is DECLINED as a vendor-level gap.

Fixed (Cause 2): `src/service.rs`'s `override_refusal` states every pre-dispatch refusal of this service in its OWN modelled terms — `Refusal::Unauthenticated` renders as `AccessDeniedException` (the only 403 identity this model declares: `errorKind client`, `@httpError 403`, required `Message` with `jsonName "message"`) with the message that shape documents, carried in `x-amzn-errortype` and the body's `__type` as `restJson1` carries an error shape. The generic, unmodelled `AccessDenied` (and the signing hint it came with) is gone, so a client that catches `AccessDeniedException` matches. `Refusal::Unauthenticated` carries no sub-kind, so a bad signature collapses into the same modelled identity — correct for this service, whose model can express no other 403. (The same mapping landed for the sibling wire-corpus issue `20261022T200433Z-sustainability-getestimatedwaterallocation-rejected-with-403-accessdenied-instead-of-being`; the two converged on it.) `tests/all/signed_requests.rs` pins the rule over the REFUSAL SPACE with request authentication ON — ten ways a caller fails verification (the `AWS4-ECDSA-P256-SHA256` algorithm the authenticator cannot read, a region-less scope, a terminator that is not `aws4_request`, a scope naming another service, an access key the emulator never minted, a header-signed request with no `x-amz-date`, the same scope carried in a presigned query, a presigned validity that has elapsed, one past the seven-day maximum, and nothing at all) × all four routes, asserting the modelled shape name in both carriers and that no unmodelled framework code (`AccessDenied`, `SignatureDoesNotMatch`) reaches the caller.

Fixed (Cause 1, for SigV4): a request the emulator can verify is DISPATCHED and answered by its operation — the modelled `200` with `Results` computed from the rows the request selects, or the modelled `ValidationException` (400) when the input is outside the model — which `tests/all/signed_request_refusals.rs` and `tests/all/request_claiming.rs` pin route by route (including a presigned and a `SigV4A`-scoped caller) and which the framework pins on the verification side beside the verifier it belongs to (`vendor/server/src/request_authentication_tests.rs`: a request header-signed with the emulator's published key verifies, whatever the serving signing name). Nothing in this service's own path refuses a verifiable caller.

Declined (vendor-level): this model lists `aws.auth#sigv4a` FIRST (`smithy.api#auth`), so an SDK that supports SigV4A signs these requests `Authorization: AWS4-ECDSA-P256-SHA256` — exactly the difference from STS, whose model lists `aws.auth#sigv4` first and whose calls the same checks make successfully. The emulator's only authenticator is `SigV4Authenticator` in `vendor/server/src/request_authentication.rs`, whose `recognizes` accepts `AWS4-HMAC-SHA256` only; it is the only one `MultiServiceRouter::new` / `set_request_authentication` register (`vendor/smithy-server-runtime/src/multi_service_router.rs`), and the `Service` trait has no authentication seam, so no service crate can add one — and `vendor/` is read-only here. Such a request is therefore still refused before dispatch; it is now refused with this service's modelled `403 AccessDeniedException`. Closing it needs a SigV4A authenticator in the core library (`AWS4-ECDSA-P256-SHA256`, the region-less credential scope, `X-Amz-Region-Set`), registered beside the SigV4 one, which would serve every `aws.auth#sigv4a` service rather than this one. Same residue as the already-resolved `20261022T004906Z-partnercentral-channel-listchannelhandshakes-returns-404-and-awsjson1-1`.

## Operation
GetEstimatedCarbonEmissions, GetEstimatedCarbonEmissionsDimensionValues, GetEstimatedWaterAllocation, GetEstimatedWaterAllocationDimensionValues

## Description
Every behavioral check against the sustainability emulator fails (0/32 passed). Each one is answered 403 with error code AccessDenied and the body message 'Sign the request with the emulator credentials', identically for well-formed requests, for requests that violate a modeled enum/range constraint, and for requests made with credentials minted by the emulator's own STS. The refusal happens in the service's request-authentication path before the operation is dispatched, so no input validation, no pagination and no state lookup ever runs. 2 causes, both in the sustainability service's auth/error path.

Related already-open issue: '20261022T200433Z-sustainability-getestimatedwaterallocation-rejected-with-403-accessdenied-instead-of-being' (wire corpus) reports the same blanket refusal, but only for GetEstimatedWaterAllocation and only from the wire fixture; the behavioral replay shows it on all four operations and additionally pins the error-identity defect of Cause 2. The replay report marked none of these checks ALREADY FILED or OWNED, so they are filed here and that issue is named for cross-reference.

Cause 1 of 2: correctly signed requests to all four sustainability operations are refused 403 AccessDenied instead of being dispatched.
AWS: Smithy model services/service-com-amazonaws-sustainability-awssustainabilityapiservice/smithy-model/com-amazonaws-sustainability-awssustainabilityapiservice.json — sdkId 'Sustainability', protocol restJson1, authSchemes [sigv4, sigv4a]. The four bound operations are GetEstimatedCarbonEmissions (POST /v1/estimated-carbon-emissions), GetEstimatedCarbonEmissionsDimensionValues (POST /v1/estimated-carbon-emissions-dimension-values), GetEstimatedWaterAllocation (POST /v1/estimated-water-allocation) and GetEstimatedWaterAllocationDimensionValues (POST /v1/estimated-water-allocation-dimension-values); all are @readonly with modeled success code 200 and @paginated (items=Results, inputToken/outputToken NextToken, pageSize MaxResults). A request signed with valid credentials for this service must be dispatched: the success path answers 200 with the Results member present (an empty list when nothing matches), and an input that breaks a modeled constraint — a Dimensions/GroupBy member outside the Dimension enum [USAGE_ACCOUNT_ID, REGION, SERVICE], an AllocationTypes member outside [TOTAL_WATER_WITHDRAWALS], a MaxResults outside @range min 1 max 5000, a TimePeriod whose End precedes its Start, an unsupported Granularity — must be answered 400 ValidationException (client error, @httpError 400, required Message with jsonName 'message'). Note these checks pin the client to region us-east-1 (real Sustainability only accepts us-east-1-signed requests), which is the signing scope the emulator is being handed.
Emulator: every call returns HTTP 403, error code AccessDenied, message 'Sign the request with the emulator credentials' (example text), regardless of operation, input validity or credentials used. 22 checks error out on the very first API call; 8 of the rejection checks see AccessDenied where they assert ValidationException.
Why: the whole service is unusable against the emulator. A client can never read a carbon-emissions or water-allocation estimate, never observe the required Results member, never page with NextToken, and cannot distinguish 'bad input' from 'not permitted' — an out-of-range enum or an inverted TimePeriod surfaces as a credential/permission failure that SDK error handling escalates or retries instead of a ValidationException naming the field to correct.
Fix: the sustainability service's request-authentication / signature-verification layer must accept the emulator's standard signed request for this service (including a request signed for us-east-1 and one signed with emulator-STS session credentials) so the operation reaches its handler; the four operations' input validation then has to enforce the modeled enum/range/TimePeriod constraints as ValidationException (400) and their handlers/serializers must return 200 with Results always emitted.

Cause 2 of 2: the authorization refusal carries error code 'AccessDenied' where this service models 'AccessDeniedException'.
AWS: the same Smithy model declares AccessDeniedException as a common error bound to all four operations — com.amazonaws.sustainability#AccessDeniedException, errorKind client, @httpError 403, required member Message with jsonName 'message', doc 'You do not have sufficient access to perform this action.' Under restJson1 the error identity is carried as the shape name AccessDeniedException (x-amzn-errortype / __type), which is what an SDK maps to its modeled exception. So a caller refused by an explicit Deny policy, or calling without the required sustainability permission, gets 403 with code AccessDeniedException.
Emulator: 403 with code 'AccessDenied' (the generic, unmodeled code), message 'Sign the request with the emulator credentials' as an example. The two authorization checks assert the modeled code and fail with 'expected AccessDeniedException, got AccessDenied'.
Why: a client that branches on the modeled exception type never matches. botocore/SDK error handling for Sustainability looks for AccessDeniedException, so the raised exception falls through to a generic ClientError and permission-denied handling (re-auth, escalate, report the missing IAM action) does not trigger; code that catches AccessDeniedException sees an unhandled error instead.
Fix: the sustainability error serializer (and whatever emits the auth-path refusal) must render refusals using this service's modeled error shape name AccessDeniedException with @httpError 403 and the required 'message' member, not the bare 'AccessDenied' code — and once Cause 1 is fixed, an IAM-denied principal must produce that same modeled error rather than the signing refusal.
Traces: sustainability.explicit-deny-policy-overrides-allow-rejected, sustainability.get-carbon-emissions-denied-without-permission-rejected.
