# Secrets Manager authorization over-refuses: conditioned identity grants and resource-policy Allows never admit a caller AWS permits (3 causes)

> _Note: this issue was identified against the code base at commit `1349203334c72f1c0ca71c4b073e11dccaca8841`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
REOPENS 20261025T093540Z-iam-secretsmanager-secrets-manager-performs-no-identity-based.md: its fix left the call refused.

That issue's fix installed the deny-by-default identity-authorization gate in front of every Secrets Manager operation, and the deny-by-default half now works (a role with no grant is refused with AWS's exact message). What the gate recognises, however, is only an UNCONDITIONED identity Allow: it evaluates no request- or resource-derived condition key, and it does not consult the secret's resource-based policy on the grant side. The result is the inverse of the original defect — calls that AWS PERMITS are now refused with AccessDeniedException, forever, so every check that first establishes its positive control never gets past it and runs to the suite's 60 s cap.

Three distinct root causes, all grounded in failing behavioral checks. Cause count: 3. Each cause below must be closed before submitting.

Related OPEN issues that do NOT carry these checks' replay keys, named so this is not re-discovered as the same work: 20261024T190718Z-secretsmanager-secrets-manager-enforces-no-authorization-and-never-consults.md — its Cause 2 names three of the checks below, but it describes the OPPOSITE symptom ("all of these calls SUCCEED", 200 where a refusal was due); a fixer closing it from its own text would make the gate deny more, which is exactly what is already wrong. And 20261025T031105Z-secretsmanager-secrets-manager-resource-based-policies-and-the-blockpublicpolicy.md — its Cause 1 describes a resource policy that is stored but never evaluated so an explicit DENY did not deny; the deny leg now works and the ALLOW leg (Cause 3 here) does not.

=== Cause 1 of 3: an identity-policy Allow carrying a condition on a request- or resource-derived key is never satisfied, so the permitted call is refused ===
AWS: Secrets Manager builds an IAM condition context from the request and the addressed resource and evaluates the caller's identity policy against it, so an Allow qualified by a condition permits the matching call and the call answers 2xx. The keys exercised here are the documented Secrets Manager / global ones (service-authorization reference for secretsmanager): the Tags of a CreateSecret request populate aws:RequestTag/<key>; the addressed secret's CURRENT tags populate aws:ResourceTag/<key>; the request's VersionStage populates secretsmanager:VersionStage; the request's BlockPublicPolicy populates secretsmanager:BlockPublicPolicy. Concretely: an Allow on secretsmanager:CreateSecret conditioned StringEquals aws:RequestTag/<k> = <v> admits CreateSecret(Tags=[{<k>:<v>}]); an Allow on secretsmanager:GetSecretValue conditioned StringEquals aws:ResourceTag/<k> = <v> admits the read of a secret carrying that tag; an Allow conditioned StringEquals secretsmanager:VersionStage = AWSCURRENT admits GetSecretValue(VersionStage="AWSCURRENT"); an Allow on secretsmanager:PutResourcePolicy conditioned Bool secretsmanager:BlockPublicPolicy = true admits PutResourcePolicy(..., BlockPublicPolicy=True). Smithy: none of CreateSecret, GetSecretValue or PutResourcePolicy models an authorization error of its own (CreateSecret errors: DecryptionFailure, EncryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, LimitExceededException, MalformedPolicyDocumentException, PreconditionNotMetException, ResourceExistsException, ResourceNotFoundException; GetSecretValue: DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException; PutResourcePolicy: InternalServiceError, InvalidParameterException, InvalidRequestException, MalformedPolicyDocumentException, PublicPolicyException, ResourceNotFoundException), so a denial can only arrive as the protocol's AccessDeniedException on HTTP 400 — and for the matching request the requirement is that there is NO denial: HTTP 200 with the operation's modelled output (CreateSecret -> ARN/Name/VersionId, GetSecretValue -> SecretString/VersionId/VersionStages, PutResourcePolicy -> ARN/Name).
Emulator: the matching, permitted call is refused with AccessDeniedException and never stops being refused. Each of the four checks issues its positive control in a bounded retry loop that treats AccessDeniedException as not-yet-propagated IAM state (90 s, 120 s), so the loop never exits and the check is cut at the suite's cap: "Check timed out after 60.0s". The same four checks' negative probes (the untagged create, the untagged/retagged read, the AWSPENDING read, the BlockPublicPolicy=False put) are never reached, so this issue asserts nothing about them beyond the fact that the gate currently refuses everything conditioned.
Hypothesis: the authorization layer resolves the principal and matches action/resource but populates an empty condition context, and a statement whose Condition block cannot be satisfied from an empty context is treated as non-matching — which, applied to an Allow, denies every conditioned grant.
Why: a client relying on AWS's behavior loses tag-based (ABAC) and stage-scoped access control entirely, in the direction that breaks working deployments: the role that production grants via aws:ResourceTag or secretsmanager:VersionStage cannot read its secret at all, and a CreateSecret that carries the mandated aws:RequestTag is rejected. Any least-privilege design that expresses "allow only under this condition" is unusable against this emulator, and a client cannot tell a policy bug from an emulator that ignores conditions.
Fix: the Secrets Manager request-authorization layer, specifically its condition-context builder and the condition evaluator it feeds — populate aws:RequestTag/<key> from the request's Tags, aws:ResourceTag/<key> from the addressed secret's stored tags, secretsmanager:VersionStage from the request's VersionStage and secretsmanager:BlockPublicPolicy from the request's BlockPublicPolicy before the policy decision, and evaluate Condition blocks (StringEquals, Bool) against that context so a matching conditioned Allow permits the call and dispatches to the handler.
Traces: secretsmanager.request-tag-condition-refuses-a-create-secret-without-the-required-tag, secretsmanager.resource-tag-condition-grants-get-secret-value-only-while-the-tag-matches, secretsmanager.version-stage-condition-key-scopes-a-read-to-one-staging-label, secretsmanager.block-public-policy-condition-key-refuses-a-put-resource-policy-that-disables-the-check.

=== Cause 2 of 3: a conditioned identity-policy Deny refuses a DeleteSecret whose request values do not satisfy that condition ===
AWS: secretsmanager:ForceDeleteWithoutRecovery and secretsmanager:RecoveryWindowInDays are request condition keys on secretsmanager:DeleteSecret, and a condition over a key that is ABSENT from the request does not match, so it cannot fire a Deny. A role holding (a) Allow DeleteSecret/DescribeSecret on *, (b) Deny DeleteSecret when Bool secretsmanager:ForceDeleteWithoutRecovery is true and (c) Deny DeleteSecret when NumericLessThan secretsmanager:RecoveryWindowInDays is 30, is PERMITTED to call DeleteSecret(SecretId=<arn>, RecoveryWindowInDays=30): the response is HTTP 200 carrying ARN, Name and DeletionDate ~30 days after the call (Smithy: DeleteSecret output is ARN/Name/DeletionDate), and DescribeSecret then reports DeletedDate. Only the two non-compliant shapes are refused, with AccessDeniedException on HTTP 400 and the explicit-deny message "User: <caller session ARN> is not authorized to perform: secretsmanager:DeleteSecret on resource: <secret ARN> with an explicit deny in an identity-based policy" — the fixed text is everything but the two variable parts, which are the caller's assumed-role session ARN as GetCallerIdentity reports it and the addressed secret's ARN.
Emulator: the COMPLIANT 30-day delete is refused. The check polls that permitted delete for an "OK" (bounded at 120 s, retrying AccessDeniedException as IAM propagation) and it never succeeds, so the check is cut at the suite's cap: "Check timed out after 60.0s". The two refusals that are actually due (force delete, 7-day window) and their message text are never reached. The control immediately above it in the same check shows RecoveryWindowInDays=7 is a valid request for an unrestricted principal, so this is an authorization decision and not input validation.
Hypothesis: the mirror image of Cause 1 — with the condition keys absent from the context the emulator cannot evaluate the Deny statements' conditions and treats them as matching, so the guardrail denies every DeleteSecret by this role rather than only the two shapes it names.
Why: this is the standard Secrets Manager guardrail shape (allow deletes, forbid irreversible ones). On AWS it leaves compliant deletes working; on this emulator attaching the guardrail locks the role out of DeleteSecret entirely, so a client's cleanup path breaks and the guardrail's actual effect is untestable in either direction.
Fix: the same request-authorization layer as Cause 1 — populate secretsmanager:ForceDeleteWithoutRecovery and secretsmanager:RecoveryWindowInDays from the DeleteSecret request, and make an unsatisfied/absent-key condition NOT match, for Deny statements as well as Allow, so a conditioned Deny fires only on the request values it names.
Traces: secretsmanager.recovery-window-condition-keys-forbid-a-force-delete-and-a-short-window.

=== Cause 3 of 3: a secret's resource-based policy Allow does not admit a principal that holds no identity-based grant ===
AWS: Secrets Manager authorizes a secret-value call against the UNION of the caller's identity policy and the secret's resource-based policy. A resource policy of {Effect: Allow, Principal: {AWS: <role ARN>}, Action: secretsmanager:GetSecretValue, Resource: "*"} attached to the secret is by itself sufficient: the named role — which holds no identity policy at all — then reads the secret, GetSecretValue answering HTTP 200 with the SecretString (Smithy: GetSecretValue output SecretString/VersionId/VersionStages; it models no authorization error, so the refusal case is the protocol's AccessDeniedException on 400). DeleteResourcePolicy revokes that access again, and the owner's own access is unaffected throughout. With the same resource-policy Allow in place, adding an identity-policy Deny for secretsmanager:GetSecretValue to the role refuses the read with AccessDeniedException / 400 and the message "User: <caller session ARN> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret ARN> with an explicit deny in an identity-based policy" (fixed text apart from the session ARN and secret ARN), and removing the Deny restores the read.
Emulator: the role is refused even though PutResourcePolicy accepted the Allow and GetResourcePolicy returns it verbatim. The refusal is AccessDeniedException / 400 with the implicit-deny message "...because no identity-based policy allows the secretsmanager:GetSecretValue action" — i.e. the decision consults identity policy only and the stored resource policy contributes nothing on the grant side. Both checks poll the read for an "ok" (60 s and 90 s bounds) and are cut at the suite's cap: "Check timed out after 60.0s". In e2e-resource-policy-attach-detach-consequence the baseline half — the same role denied with that exact implicit-deny message BEFORE any policy is attached — now passes, which locates the gap precisely in the resource-policy leg; in identity-policy-deny-overrides-a-resource-policy-allow-for-the-same-role the Deny-beats-Allow assertion and its explicit-deny message are never reached because the read is already refused.
Why: a resource policy is how an account shares one secret with a principal that is deliberately given no identity permissions (and how cross-account access is granted at all). On this emulator attaching the documented Allow changes nothing, so that sharing pattern simply does not work, and the follow-on guarantee under test — that an identity Deny overrides a resource Allow — is unobservable.
Fix: the Secrets Manager request-authorization layer plus the GetSecretValue pre-dispatch check — read the addressed secret's stored resource policy, resolve its Principal against the caller, and decide on the union (an explicit Deny in either policy wins; a resource-policy Allow alone is sufficient; absence of any Allow in either remains the implicit deny that already works). The same decision must be reachable from DescribeSecret/PutSecretValue so a per-action resource policy scopes only the action it names.
Traces: secretsmanager.e2e-resource-policy-attach-detach-consequence, secretsmanager.identity-policy-deny-overrides-a-resource-policy-allow-for-the-same-role.
