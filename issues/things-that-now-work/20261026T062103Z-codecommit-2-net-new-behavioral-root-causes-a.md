# CodeCommit: 2 net-new behavioral root causes — a CFN-declared AWS::CodeCommit::Repository (with Triggers) does not exist after CREATE_COMPLETE, and InvalidRepositoryTriggerDestinationArnException carries the Smithy doc blurb instead of AWS's message

> _Note: this issue was identified against the code base at commit `8328721890835ec05ad2e88ea1239c6c1115d880`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRepositoryTriggers

## Description
Two net-new root causes in the codecommit crate, each grounded in a failing behavioral check the replay report left unmarked (not ALREADY FILED, not OWNED). Related-but-not-covering open issues are named per cause. A fixer must close BOTH causes before submitting.

Cause 1 of 2: a CloudFormation stack whose AWS::CodeCommit::Repository declares a Triggers block reaches CREATE_COMPLETE without the repository (or its trigger configuration) existing, so the whole CFN-declared trigger surface is unreachable.
AWS: recorded behavior only — AWS::CodeCommit::Repository is a CloudFormation resource type, not a Smithy operation, so the Smithy model says nothing about it. Recorded behavior: a stack whose only resource is AWS::CodeCommit::Repository with RepositoryName=R and Triggers=[{Name:T, DestinationArn:<sns topic arn>, Events:["all"], Branches:[]}] reaches CREATE_COMPLETE only once the repository exists AND carries that trigger configuration; immediately afterwards codecommit.GetRepositoryTriggers(repositoryName=R) answers 200 with exactly one trigger whose name is T, whose destinationArn is the template's DestinationArn and whose events are ["all"], TestRepositoryTriggers(repositoryName=R, triggers=[that trigger]) answers 200 with the trigger named in successfulExecutions and an empty failedExecutions, and a subsequent real commit actually delivers an SNS notification observable on a queue subscribed to the topic. The template's Triggers property is therefore not inert metadata: it must land in the repository's trigger configuration as if PutRepositoryTriggers had been called.
Emulator: describe_stacks reports CREATE_COMPLETE (that assertion passes), and the very next call, GetRepositoryTriggers, is refused with HTTP 400 RepositoryDoesNotExistException, message '<repositoryName> for <accountId>' — the 12-digit account id is the caller's and the name is the template's RepositoryName, so the whole message is request/state-derived and only the template is the requirement. The stack's CodeCommit resource was never provisioned at all, so neither the repository nor its triggers exist and the trigger-delivery legs behind this call are entirely unverified.
Why: CREATE_COMPLETE is the contract every IaC pipeline gates on. A stack that reports success while creating nothing lets every CloudFormation-driven CodeCommit deploy-then-use workflow pass against a repository that does not exist, and the failure then surfaces far from its cause; CFN-declared repository triggers — the documented way to wire CodeCommit to SNS/Lambda from a template — never fire, so notification and review automation silently does nothing.
Note: the open issue 20261023T072048Z-codecommit-10-behavioral-root-causes-three-operations-answer.md describes the same unprovisioned-repository cause as its Cause 4, but its replay list names only codecommit.deploy-codecommit-repository-behaves and codecommit.deploy-codecommit-repository-behaves-after-stack-create; this check id is not on it, and neither of those two checks exercises the Triggers property at all, so that cause as written would be closed without the trigger propagation ever being provisioned. Fixing it may close part of this cause; this check id must be re-replayed to confirm.
Fix: the CloudFormation resource provider for AWS::CodeCommit::Repository — the cloudformation crate's resource-type dispatch must call through to the codecommit crate's repository state on stack create (and release it on stack delete) instead of recording a resource with no backing object, and must map the resource's Triggers property onto the repository's trigger configuration (the same state the codecommit crate's PutRepositoryTriggers writes, so GetRepositoryTriggers/TestRepositoryTriggers and real trigger delivery read it).
Traces: codecommit.deploy-codecommit-repository-trigger-enforced.

Cause 2 of 2: PutRepositoryTriggers rejects a malformed destinationArn with the right code and status but with the Smithy documentation blurb as the error message instead of AWS's message.
AWS: Smithy (com.amazonaws.codecommit#CodeCommit_20150413) PutRepositoryTriggers takes repositoryName (@required, @length 1..100, @pattern ^[\w\.-]+$) and triggers (@required, RepositoryTriggersList) and models InvalidRepositoryTriggerDestinationArnException as a client error with httpError 400. A trigger whose destinationArn is not an ARN at all is refused with HTTP 400 / InvalidRepositoryTriggerDestinationArnException, the repository's existing trigger configuration is left untouched, and a same-shaped trigger with a syntactically valid SNS ARN still applies afterwards. The message is the fixed text 'Repository trigger destination arn is incorrectly formatted' — it is entirely fixed, with NO variable parts: it interpolates neither the offending ARN, nor the trigger name, nor the repository name.
Emulator: status 400 and code InvalidRepositoryTriggerDestinationArnException are correct, but the message is 'The Amazon Resource Name (ARN) for the trigger is not valid for the specified destination. The most common reason for this error is that the ARN does not meet the requirements for the service type.' That string is the Smithy @documentation of the InvalidRepositoryTriggerDestinationArnException shape, reproduced verbatim as the wire message rather than AWS's actual message.
Why: the documentation blurb is prose about the error class, not the error AWS returns. Clients, samples and differential harnesses that match on this message flag every malformed-trigger path; the emulator also trains callers on a message real CodeCommit never sends, so error handling written against the emulator breaks on AWS and vice versa. The same defect pattern (doc-blurb-as-message) is likely to be present on the sibling TriggerProblem variants, which all build their messages the same way, so they should be reviewed together.
Note: the open issue 20261022T213415Z-codecommit-putcommentreaction-is-a-501-stub-cmk-disablement.md covers two other diverging codecommit error-message templates (GetCommit's CommitIdDoesNotExistException and RepositoryDoesNotExistException) but names neither this check nor this error class, so it does not cover this cause.
Fix: the message construction for the trigger-configuration refusals in the codecommit crate's shared trigger validator — crate::state::TriggerProblem::message() (services/service-com-amazonaws-codecommit-codecommit-20150413/src/state.rs:4281-4286 for the DestinationArnInvalid arm), which services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/put_repository_triggers.rs:171-232 (`refusal`) turns into the modeled error. The validation and the status/code mapping are already correct; only the message text is wrong.
Traces: codecommit.put-repository-triggers-invalid-destination-arn.
