# sesv2__sns__sqs: the whole SES configuration-set/event-publication surface is unreachable — CreateConfigurationSet and GetAccount are unimplemented scaffold stubs (2 causes)

> _Note: this issue was identified against the code base at commit `ca265ed85df5a1b6b7b5ff6c2c813551ab1096d8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationSet

## Description
Attribution note: these check ids' leading token is the composite 'sesv2__sns__sqs'; all three constituent services (sesv2, sns, sqs) are stood up in this checkout, so the per-service bootstrap gate is FILE. The refused call in each is the SESv2 one.

This issue bundles 2 net-new root causes of the sesv2 service. Related OPEN issue: 20261023T183615Z-sesv2-sns-sqs-all-seven-ses-send-event.md reports the same five checks aborting at setup because CreateEmailIdentity was refused with the non-AWS code 'AmbiguousService' by the sigv4-name router. That refusal no longer occurs — SESv2 requests now reach their handlers — and that issue's replay key is error-code-qualified ('sesv2__sns__sqs|CreateEmailIdentity|AmbiguousService'), so it does NOT carry these checks' current failure. What blocks them now is a different defect: the operations the scenarios need are scaffold stubs that answer HTTP 501.

Cause 1 of 2: CreateConfigurationSet answers HTTP 501 'NotImplemented' instead of creating a configuration set. Failing checks: sesv2__sns__sqs.event-destination-disabled-publishes-no-events, sesv2__sns__sqs.send-bulk-email-per-entry-replacement-headers-override-the-template-default, sesv2__sns__sqs.send-raw-email-preserves-custom-headers-exactly-in-the-published-event, sesv2__sns__sqs.templated-send-with-missing-variable-publishes-rendering-failure.
AWS: Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json): SimpleEmailService_v2 2019-09-27, restJson1, sigv4Name 'ses', endpointPrefix 'email'. CreateConfigurationSet is POST /v2/email/configuration-sets with success code 200 and an EMPTY response body (output_shape CreateConfigurationSetResponse has no members); required input member ConfigurationSetName (the model documents it as up to 64 alphanumeric characters, hyphens and underscores only), optional TrackingOptions/DeliveryOptions/ReputationOptions/SendingOptions/SuppressionOptions/VdmOptions/ArchivingOptions/MessageSecurityOptions/Tags. Its ONLY modeled errors are AlreadyExistsException 400, BadRequestException 400, LimitExceededException 400, NotFoundException 404, ConcurrentModificationException 500, TooManyRequestsException 429. There is no 'NotImplemented' error and no 501 status anywhere in this service model. A created configuration set must then be readable and extendable: CreateConfigurationSetEventDestination POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations and UpdateConfigurationSetEventDestination PUT .../event-destinations/{EventDestinationName} both answer 200 and 404 NotFoundException for an unknown set, and sends naming the set (SendEmail POST /v2/email/outbound-emails, SendBulkEmail POST /v2/email/outbound-bulk-emails) publish Send/Delivery/Bounce/Rendering-failure events to the set's SnsDestination TopicArn.
Emulator: every call is refused. HTTP 501, error code 'NotImplemented', message "operation CreateConfigurationSet is scaffolded but not implemented in this emulator" — fixed text apart from the operation name, which is the only request-derived part; neither the code, the status nor the message exists in AWS. services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and its handle() body ends in Err(crate::scaffolded::Scaffolded::not_implemented("CreateConfigurationSet")), so no configuration set is ever stored.
Why: a client cannot create a configuration set at all, so nothing downstream of one exists: no event destination can be attached, enabled or disabled, no SNS->SQS event publication happens, and no send can be correlated to a configuration set. The returned code is in no AWS model, so an SDK cannot classify it (it is neither the retryable TooManyRequestsException nor a terminal modeled BadRequestException), and any client that branches on AlreadyExistsException for idempotent setup takes the wrong path. Four whole behavioral scenarios — disabled-destination gating, per-entry bulk ReplacementHeaders, raw-MIME header preservation, and template rendering-failure events — are unobservable.
Fix: implement the operation in its handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set.rs (the only file for this operation), plus the service state that holds configuration sets (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/state.rs) so the event-destination and send handlers can resolve a set by name; delete the SCAFFOLDED marker once done, and return the modeled AlreadyExistsException/BadRequestException rather than a 501 for refusals.
Traces: sesv2__sns__sqs.event-destination-disabled-publishes-no-events, sesv2__sns__sqs.send-bulk-email-per-entry-replacement-headers-override-the-template-default, sesv2__sns__sqs.send-raw-email-preserves-custom-headers-exactly-in-the-published-event, sesv2__sns__sqs.templated-send-with-missing-variable-publishes-rendering-failure (all four fail on their first SESv2 setup call).

Cause 2 of 2: GetAccount answers HTTP 501 'NotImplemented' instead of reporting the account's sending status. Failing check: sesv2__sns__sqs.account-suppression-from-a-hard-bounce-blocks-the-next-send.
AWS: Smithy (same model): GetAccount is GET /v2/email/account, success code 200, input has no members, and the response carries DedicatedIpAutoWarmupEnabled (boolean, default false), EnforcementStatus, ProductionAccessEnabled (boolean, default false), SendQuota, SendingEnabled (boolean, default false), SuppressionAttributes, Details, VdmAttributes, PricingAttributes. Its only modeled errors are BadRequestException 400 and TooManyRequestsException 429 — there is no 501 and no 'NotImplemented'. SuppressionAttributes.SuppressedReasons is what tells a caller whether BOUNCE/COMPLAINT addresses are auto-added to the account suppression list, which is the precondition the suppression scenario reads before sending.
Emulator: HTTP 501, error code 'NotImplemented', message "operation GetAccount is scaffolded but not implemented in this emulator" (fixed text apart from the operation name). services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/get_account.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker.
Why: a client cannot read its own sending status, send quota, production-access state or suppression-list configuration, so it cannot tell whether a send will be accepted or whether a hard bounce will suppress the address. The account-level suppression behavior (a hard bounce adding the address to the account suppression list, and the next send to it being blocked with bounceSubType 'OnAccountSuppressionList') is unreachable, and the refusal code is unclassifiable by the SDK.
Fix: implement the operation in its handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/get_account.rs, backed by account-level state (send quota, SendingEnabled, SuppressionAttributes.SuppressedReasons) in the service's state module; delete the SCAFFOLDED marker once done.
Traces: sesv2__sns__sqs.account-suppression-from-a-hard-bounce-blocks-the-next-send (fails on its first call, sesv2.get_account()).
