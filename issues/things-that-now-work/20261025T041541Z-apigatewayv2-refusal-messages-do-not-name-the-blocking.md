# apigatewayv2: refusal messages do not name the blocking route and NotFound messages leak the internal account-qualified key (2 causes)

> _Note: this issue was identified against the code base at commit `0216dcd5498391d4123810a7938f513e2bc3675a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteIntegration, GetDeployment, CreateRouteResponse

## Description
Two distinct root causes in the apigatewayv2 emulator's rejection-message construction, both grounded in failing behavioral checks of this suite. In every case below the HTTP status and the error CODE match AWS; what diverges is message CONTENT whose rule is known (an id built from request/state, and the identity of the resource the error names) rather than wording alone. A fixer must close BOTH before submitting; they are numbered and each carries its own failing check ids.

=== Cause 1 of 2: DeleteIntegration's conflict refusal does not name the Route(s) that reference the integration ===
AWS: Smithy (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model): DeleteIntegration DELETE /v2/apis/{ApiId}/integrations/{IntegrationId}, success code 204, modeled errors NotFoundException (httpError 404) and TooManyRequestsException (429); ConflictException (httpError 409) is the service's conflict error, modeled on the sibling Create/UpdateIntegration operations. Recorded behavior: DeleteIntegration on an integration a route targets is refused with ConflictException, and the message is BUILT FROM STATE — it enumerates the identifiers of the routes that block the delete: 'Cannot delete Integration because it is referenced by the following Routes with Ids: [<RouteId>]'. The requirement is that rule (the refusal names the referencing RouteId(s)), not the recorded wording.
Emulator: the code is correct (ConflictException) and the route's Target is correctly left unchanged, but the message is 'Integration 8sh3tqaaaa cannot be deleted while route(s) 8sh3tqaaaa target it.' — the identifier reported for the blocking route is the SAME string as the integration's own id, so no RouteId is conveyed at all. Hypothesis: either the conflict path interpolates the integration id where the referencing route ids belong, or the emulator's id generator mints the same id for an integration and for a route (the same 10-character value also shows up as an ApiId in another check of this run, in 'Invalid API identifier specified 000000000000:8sh3tqaaaa'); if the second is true, the non-unique id generation is the more serious defect and the message is merely reporting it.
Why: the only way a client can resolve this conflict is to delete or retarget the routes the message names. With the integration's own id echoed in place of the route ids, an automation that parses the conflict (or a human following it) retargets nothing and the delete can never be made to succeed; and if ids really are shared between resource types, every client that keys resources by id in one map will collide.
Fix: the DeleteIntegration handler's in-use/conflict path — collect the RouteIds whose Target is 'integrations/<IntegrationId>' from state and report those in the ConflictException — and, if the two ids were genuinely equal, the id-minting helper that must make integration and route ids distinct.
Traces: apigatewayv2.delete-integration-in-use-by-a-route-rejected.

=== Cause 2 of 2: NotFoundException messages embed the emulator's internal account-qualified state key, and GetDeployment names the API instead of the deployment ===
AWS: recorded behavior only (the model carries no message text; Smithy only states NotFoundException with httpError 404 on GetDeployment and on CreateRouteResponse). Recorded behavior: GetDeployment for a deployment that does not exist answers NotFoundException with a message that identifies the DEPLOYMENT ('Invalid Deployment identifier specified', as an example of the wording), and CreateRouteResponse against a RouteId that does not exist on the API answers NotFoundException identifying the ROUTE ('Invalid route identifier specified'). Neither message contains an AWS account id or any account-qualified key. The requirements here are (a) no account-qualified internal key in a client-visible message, and (b) the error identifies the resource the operation addresses.
Emulator: the status and code are right (NotFoundException 404) but the message is built as 'Invalid <Resource> identifier specified <account>:<id>' — observed 'Invalid API identifier specified 000000000000:8sh3tqaaaa' from GetDeployment(ApiId=<deleted api>, DeploymentId=<id>) and 'Invalid Route identifier specified 000000000000:bogusrt5af3643bdb83' from CreateRouteResponse with an unknown RouteId. So the emulator (i) appends its internal account-qualified state key to the message, and (ii) for GetDeployment reports the API as the invalid identifier even though the deployment is the resource being read.
Why: a client that reads a NotFound to decide WHICH resource is missing is told the wrong one (GetDeployment after its API is gone blames the API id, so a reconciler re-creates the wrong resource), and every such message hands the caller an internal '<account>:<id>' partition key that no AWS response contains — log scrapers and error-classifying wrappers written against AWS see a shape they never see in production.
Fix: the shared NotFound error builder used by the apigatewayv2 operation handlers — format the message from the resource the operation addresses and drop the account-qualified state key from the client-visible text.
Traces: apigatewayv2.delete-api-removes-its-routes-integrations-and-stages (the DeleteApi cascade itself is correct: GetApi/GetRoute/GetIntegration/GetStage all answer NotFoundException and the sibling API is untouched — only the GetDeployment message diverges), apigatewayv2.create-route-response-invalid-route-rejected (the NotFoundException code and the absence of any created route response are correct; the positive control was never reached).
