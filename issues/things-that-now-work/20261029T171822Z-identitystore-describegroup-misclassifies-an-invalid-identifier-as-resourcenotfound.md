# identitystore DescribeGroup misclassifies an invalid identifier as ResourceNotFound

> _Note: this issue was identified against the code base at commit `9fc346ef5fefb977b4ef554789eaaa17a76a6a1a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeGroup

## Description
One recorded DescribeGroup step whose response AWS returns as a client validation failure is answered by the emulator as a not-found, and the error body it does return omits the modeled RequestId member. Two causes, both observed on the same recorded step; a fixer must close BOTH before submitting.

Cause 1 of 2: wrong error class / HTTP status for an identifier DescribeGroup cannot accept.
AWS: Smithy DescribeGroup models ValidationException (httpError 400, "The request failed because it contains a syntax error") and ResourceNotFoundException (httpError 404, "Indicates that a requested resource is not found") as two distinct errors. The recorded response for this step is HTTP 400, and ValidationException is the only 400 DescribeGroup models, so the required error class is ValidationException with status 400 — AWS separates an identifier the operation cannot accept (a request-shape fault, 400) from a well-formed identifier that names a resource the store does not hold (404). The modeled 404 body additionally carries ResourceType (enum USER | GROUP | IDENTITY_STORE) and ResourceId, which is only meaningful once the identifier is accepted at all.
Emulator: answers HTTP 404 ResourceNotFoundException. ops/describe_group.rs resolves the store with crate::state::resolve_store and maps every failure to ResourceNotFoundException, then maps a missing group key to crate::state::not_found(ResourceKind::Group, ...); state.rs itself documents the identity-store path as "refused with the modelled not-found" and the message as the per-class constant ("Identity store not found" / the Group class's fixed not-found text). There is no path in the handler that can produce a 400, so a request AWS rejects as invalid is reported as a missing resource.
Why: a client branches on the error class. A 404 ResourceNotFoundException reads as "this group does not exist (yet)" — retry-after-create, treat-as-absent, idempotent-delete logic all take that branch — whereas AWS's 400 ValidationException means the request itself must be corrected and is never retried. The emulator therefore sends callers down a silent-success or infinite-poll path for a malformed request, and SDK error-type matching (ValidationException vs ResourceNotFoundException) does not fire.
Fix: the DescribeGroup handler's identifier-acceptance path and the service's validation wording seam — ops/describe_group.rs together with crate::state identifier resolution (identity_store_key / resolve_store / not_found) and crate::service::validation, which is where a refused request is worded. The 404 classification must be reserved for a well-formed identifier that resolves to no record.
Traces: identitystore-create-group-describe-fields#task#6.

Cause 2 of 2: RequestId omitted from the exception body.
AWS: ValidationException and ResourceNotFoundException both model a RequestId member (target RequestId, length 1..36, pattern ^[A-Fa-f0-9]{8}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{12}$) documented as "The identifier for each request. This value is a globally unique ID that is generated by the identity store service for each sent request, and is then returned inside the exception if the request fails." So every identity-store error body carries a RequestId in that UUID form. The concrete value is per-run and is NOT a requirement; its PRESENCE and form are.
Emulator: the member is absent — the replay reports `$.RequestId: missing (expected '<shaped-not-asserted>', got None)`. The error constructors in state.rs hard-code `request_id: None` (see not_found, member_not_found, not_found_by_alternate_identifier and the conflict/precondition builders), so no identity-store exception ever carries one.
Why: a client or support workflow that logs or echoes the identity-store RequestId from a failure has nothing to log, and a consumer that treats the field as always-present on an identity-store exception sees a null where AWS guarantees a value.
Fix: the service's error serialization / error-construction seam — populate RequestId for every modeled identity-store exception (a per-request UUID minted in the service error channel, crate::scaffolded / crate::service, rather than at each of the ~6 call sites in state.rs that currently pass None).
Traces: identitystore-create-group-describe-fields#task#6.

No open issue covers either cause (list_existing_issues for 'identitystore' returns none).
