# Chime SDK Media Pipelines is entirely unreachable: the router resolves by sigv4 signing name, so all 'chime'-signed services collide and every request is refused with AmbiguousService

> _Note: this issue was identified against the code base at commit `4cbced68d8f61275ceb5b427ff8478e9aa7bafe5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMediaPipeline

## Description
Cause 1 of 1: the emulator's front-door request router dispatches on the sigv4 signing name (the credential-scope service field of the Authorization header) instead of the request's endpoint prefix / Host and the restJson1 @http URI path. Chime is a service family in which several distinct AWS services deliberately share one signing name, so that key is not unique: the router finds 5 (and in one check 6) candidate services for every Chime-signed request and refuses to serve any of them. No chime-sdk-media-pipelines handler is ever reached.

AWS: Smithy (services/service-com-amazonaws-chimesdkmediapipelines-chimesdkmediapipelinesservice/smithy-model/com-amazonaws-chimesdkmediapipelines-chimesdkmediapipelinesservice.json) — service ChimeSDKMediaPipelinesService, version 2021-07-15, protocol restJson1, aws.auth#sigv4 name = 'chime', aws.api#service endpointPrefix = 'media-pipelines-chime', arnNamespace = 'chime', 31 operations. The sibling Chime SDK services (Chime, Chime SDK Identity, Chime SDK Messaging, Chime SDK Meetings, Chime SDK Voice) share the SAME sigv4 signing name 'chime' while each carrying its OWN endpointPrefix ('chime', 'identity-chime', 'messaging-chime', 'meetings-chime', 'voice-chime'). Real AWS therefore disambiguates by the endpoint host the client was pointed at and by the operation's restJson1 URI path, never by signing name alone. Concretely, per the model: GetMediaPipeline is GET /sdk-media-pipelines/{MediaPipelineId} -> 200 MediaPipeline, and for an unknown id -> NotFoundException (httpError 404); DeleteMediaInsightsPipelineConfiguration is DELETE /media-insights-pipeline-configurations/{Identifier} -> 204, unknown identifier -> NotFoundException 404; UpdateMediaInsightsPipelineStatus is PUT /media-insights-pipeline-status/{Identifier} -> 200, unknown identifier -> NotFoundException 404; GetSpeakerSearchTask is GET /media-insights-pipelines/{Identifier}/speaker-search-tasks/{SpeakerSearchTaskId} -> 200, unknown -> NotFoundException 404; CreateMediaPipelineKinesisVideoStreamPool is POST /media-pipeline-kinesis-video-stream-pools -> 201 KinesisVideoStreamPoolConfiguration, with ConflictException (409) for a duplicate PoolName and ForbiddenException/AccessDenied-class rejection for an unauthorized caller. The service's modeled/common errors are BadRequestException, ConflictException, ForbiddenException, NotFoundException, ResourceLimitExceededException, ServiceFailureException, ServiceUnavailableException, ThrottledClientException, UnauthorizedClientException. 'AmbiguousService' is not a modeled error of this service.

Emulator: every call made by a correctly configured botocore 'chime-sdk-media-pipelines' client is refused with error code 'AmbiguousService' before any handler runs, with the message (example text from the replay) "5 emulated services all claim requests for 'chime': chime, chime, chime, chime, chime; the request is rejected rather than served by an arbitrary one". botocore also exhausted its retry budget on several of these ('reached max retries: 3'), i.e. the refusal is delivered in a form the SDK classifies as retryable rather than as a terminal 4xx. Hypothesis: the refusal is emitted as a 5xx from the router layer; the replay output records only the parsed error code and message. The message also renders all candidates with the same display name 'chime' rather than their distinct sdkIds, so the refusal does not even identify which services collided. Observed substitutions: not-found paths return AmbiguousService instead of NotFoundException (delete-media-insights-pipeline-configuration-not-found, get-media-pipeline-not-found, update-media-insights-pipeline-status-not-found, get-speaker-search-task-not-found, start-speaker-search-task-pipeline-not-found); the authorization path returns AmbiguousService instead of an AccessDeniedException-class rejection (create-media-pipeline-kinesis-video-stream-pool-missing-permission-rejected); pool create/list/delete and the duplicate-name conflict paths never execute at all (kinesis-video-stream-pool-delete-removes-from-list, kinesis-video-stream-pool-duplicate-name-rejected, kinesis-video-stream-pool-duplicate-name-concurrent-create-race — 5 concurrent creates all errored, 0 winners instead of exactly 1); and media-capture-pipeline-lifecycle-with-chime-meeting is refused on its first setup call (CreateMeeting) with the same code reporting a 6-way 'chime' collision, showing the defect spans the whole family.

Why: a client relying on AWS's behavior cannot reach Chime SDK Media Pipelines at all. None of the 31 modeled operations is exercisable — media capture / media insights pipeline lifecycle, Kinesis Video Stream pool CRUD, speaker-search tasks, and every modeled error path are shadowed by a router-level refusal. Worse, the refusal masquerades as a retryable server fault, so SDK and application retry loops spin to max attempts and then surface an error code AWS never returns, instead of failing fast with NotFoundException/ConflictException/AccessDenied or succeeding. Error handling keyed on the documented codes (retry-on-conflict loops, delete-if-exists cleanup, not-found probes) all break.

Fix: the front-door service-resolution/routing layer (the component that maps an inbound request to an emulated service), not any chime-sdk-media-pipelines handler. Resolution must key on the request's endpoint prefix / Host header — and, where that is absent, on the operation's restJson1 method + URI path — with the sigv4 signing name used only as a weak hint; a shared signing name must not be treated as a service identity. A resolution failure must additionally be rendered as a terminal AWS error shape rather than a retryable one. This is the same class of defect already filed for other signing-name families, including the sibling Chime service in 20261022T042904Z-chime-sdk-identity-is-entirely-unreachable-the-router.md ('chime' family, chime-sdk-identity) and 20261022T031220Z-wisdom-all-wisdom-requests-rejected-with-ambiguousservice-two-emulated.md, 20261022T032542Z-application-autoscaling-lambda-lambda-is-unreachable-four-emulated-services-all-claim.md, 20261022T035032Z-events-every-eventbridge-events-request-is-refused-with-ambiguousservice.md — none of which carries this service's replay keys, so this issue is filed separately and must be re-replayed against chime-sdk-media-pipelines.

Traces: the 10 chime-sdk-media-pipelines checks listed in trace_ids, each aborting on a chime-signed call with AmbiguousService.
