# GetStyleDescriptor synthesizes a stub style instead of the published AWS style document

> _Note: this issue was identified against the code base at commit `d4c3381173b09dc1be1da315e64a87a78d438272`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetStyleDescriptor

## Description
GetStyleDescriptor answers 200 with a MapLibre style document, but the document is a small emulator-generated stub: it is missing most of the style's layers, carries a truncated attribution, uses hex colors where AWS uses hsl()/zoom interpolations, and drops the metadata that advertises optional variants. Three causes, one per requested style/option combination exercised by the corpus.

This bundle contains 3 causes. All three must be closed before submitting.

Cause 1 of 3 - Standard/Dark descriptor requested with rich options is missing layers, attribution, sky/light settings and variant metadata.
AWS: Smithy GetStyleDescriptor -> GET /v2/styles/{Style}/descriptor with required enum @httpLabel Style and @httpQuery color-scheme, political-view, terrain, contour-density, traffic, travel-modes, buildings, poi-density, poi-categories, key; output GetStyleDescriptorResponse.Blob is the @httpPayload (the style JSON) with Content-Type/Cache-Control/ETag; no modeled errors, so the whole contract is the body. The model does not describe the body's contents, so: recorded behavior only - the recording shows (a) a complete layer list for the style, including the tunnel/bridge/rail/shield/traffic/poi/landuse layer families (e.g. rail_tunnel, rail_tie_tunnel and ~200 further layer ids), (b) sources.aws.attribution and sources.traffic.attribution carrying the full AWS + HERE attribution HTML ("© <a href='https://docs.aws.amazon.com/location/latest/developerguide/data-attribution.html'>AWS</a>, <a href='https://legal.here.com/en-gb/terms/general-content-supplier-terms-and-notices'>HERE</a>"), (c) layer paint colors expressed as hsl()/hsla() strings or zoom interpolate expressions, and (d) metadata['aws:virtual-variant'] listing the variants enabled by the request's options (for a terrain= request, [{key: 'terrain', variants: [{id: '3d_terrain'}]}]).
Emulator: 200 with a stub - metadata['aws:virtual-variant'] absent entirely; sources.aws.attribution and sources.traffic.attribution are the literal string '© AWS'; the rail_tunnel, rail_tie_tunnel and ~200 other layer objects are absent; layers[id="land"].paint.background-color is the hex '#26282b' where AWS gives an hsl() value; light.*, sky.* (sky-color, sky-horizon-blend, horizon-color, horizon-fog-blend, fog-color, fog-ground-blend, atmosphere-blend) all diverge.
Why: this document IS the map. A client that fetches it renders a map with no roads, rails, tunnels, bridges, shields, POIs, buildings or traffic layers, with wrong sky/fog, and with an attribution that omits the legally required HERE supplier notice - and because metadata['aws:virtual-variant'] is missing, a client cannot discover that the terrain variant it asked for exists, so terrain is silently never enabled.
Fix: the GetStyleDescriptor handler and the style-document source it serializes from (src/ops/ plus the style data in src/state.rs) - the handler must serve the full style document for the requested Style/ColorScheme and apply the query options (terrain, traffic, buildings, poi-*, travel-modes, contour-density, political-view) to the layer set, metadata variants and attribution, rather than emitting a fixed stub.
Traces: geo-maps-style-descriptor-rich-options#task#1.

Cause 2 of 3 - the same stub is served for Monochrome/Light, and the land background is the wrong JSON type.
AWS: recorded behavior only. For Monochrome/Light the recording shows layers[id="land"].paint.background-color as a zoom interpolate EXPRESSION (a JSON array: ['interpolate', ['linear'], ['zoom'], 15.5, 'hsl(228, 0%, 87%)', 16, 'hsl(228, 0%, 85%)']), the full layer list for that style (rail_tunnel, rail_tie_tunnel, landuse_desert, poi_landuse_park, ... ), the full AWS + HERE attribution on sources.aws, and the style's own sky.* values.
Emulator: background-color is the scalar string '#f2f2f2' - a TYPE mismatch, not just a value mismatch, so a renderer that expects an expression here gets a string; the layer families are again absent; sources.aws.attribution is '© AWS'; metadata['aws:virtual-variant'] is absent; sky.* diverges.
Why: beyond the missing-map problem of cause 1, the scalar-where-an-expression-is-expected means the colour cannot vary with zoom, and a strict style parser rejects or mis-handles the paint property outright.
Fix: same component as cause 1; the style serializer must preserve MapLibre expression values (arrays) and must be keyed by the requested Style and ColorScheme - the identical stub being returned for both Standard/Dark and Monochrome/Light shows it currently is not.
Traces: geo-maps-style-descriptor-rich-options#task#2.

Cause 3 of 3 - Standard/Light descriptor: attribution, sky/atmosphere settings and variant metadata diverge on the default option set.
AWS: recorded behavior only - for Standard/Light the recording gives sky.sky-color 'hsl(208, 90%, 72%)', sky.sky-horizon-blend 0.2, sky.horizon-color 'hsl(0, 0%, 100%)', sky.horizon-fog-blend 0.9, sky.fog-color 'hsla(0, 0%, 100%, 0.2)', sky.fog-ground-blend 0.8, sky.atmosphere-blend 0.2, the full AWS + HERE attribution on sources.aws, and metadata['aws:virtual-variant'] present.
Emulator: sky.sky-color '#a0c8f0', sky-horizon-blend 0.8, horizon-color '#d9d2c7', horizon-fog-blend 0.6, fog-color '#f7f5f2', fog-ground-blend 0.5, atmosphere-blend 0.8; sources.aws.attribution '© AWS'; metadata['aws:virtual-variant'] absent. These are hard-coded constants, not the style's values.
Why: the sky/fog/atmosphere block drives the rendered horizon and haze; wrong constants give a visibly different map, and the colour-format difference (hex vs hsl/hsla with alpha) also loses the alpha channel on fog-color, so the fog renders opaque.
Fix: same component as cause 1 - these values belong to the style document for the requested Style/ColorScheme and must be read from it.
Traces: geo-maps-vector-basemap-style-workflow#task#1.

Excluded from this issue (not emulator defects, reported for completeness): $.sprite is a self-referential URL whose host:port is the environment's own listener, and $.metadata.version / the version suffix in $.id ('...-4.1.0-beta.1' vs '...-4.1.0') are style-catalogue version values; the corpus marks $.sprite and $.metadata.version '<shaped-not-asserted>'. None of those are requirements and no fix should chase them.
