# dynamodb__kms: 3 net-new causes — a nonexistent-CMK CreateTable refusal does not wrap the KMS NotFoundException, and the data plane never consults the table's CMK state (Disabled / PendingDeletion reads and writes keep succeeding)

> _Note: this issue was identified against the code base at commit `755fa21f4b5f658e5c42cafb46f764c1d29f1673`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTable, GetItem, PutItem

## Description
Three net-new root causes in DynamoDB's SSE-KMS surface. CreateTable with an SSESpecification now succeeds (it is no longer the 501 scaffold), so the open issue 20261024T102105Z-dynamodb-kms-dynamodb-createtable-with-an-ssespecification-is-an-unimplemented.md (still open, keyed on `dynamodb__kms|CreateTable|NotImplemented`) no longer describes what these checks hit: the key-state surface it predicted is now reachable and diverges in three distinct, separately-fixable ways. None of the three checks below was marked ALREADY FILED or OWNED by the replay report.

Cause 1 of 3 — CreateTable's refusal for a well-formed but nonexistent CMK does not wrap the KMS cause.
AWS: recorded behavior only (the model documents the member, not the message): CreateTable with SSESpecification{Enabled:true, SSEType:'KMS', KMSMasterKeyId:<a well-formed key ARN in this Region that names no key} is refused with HTTP 400 and Error.Code 'ValidationException', and DynamoDB wraps the KMS fault in the message rather than surfacing the KMS error code: the fixed text is "KMS validation error: com.amazonaws.services.kms.model.NotFoundException: Key '" ... "' does not exist (Service: Kms, Status Code: 400, Request ID: " ... "; Proxy: null)"; the variable parts are the key ARN taken verbatim from the request's KMSMasterKeyId and the per-call KMS request id. The requirement is that the message name the wrapped KMS exception class (NotFoundException), not any one recording's ARN or request id. Smithy: CreateTableInput.SSESpecification.KMSMasterKeyId — "The KMS key that should be used for the KMS encryption. To specify a key, use its key ID, Amazon Resource Name (ARN), alias name, or alias ARN."
Emulator: the status and code are right but the message is emulator-authored and names no KMS cause: 'One or more parameter values were invalid: KMSMasterKeyId arn:aws:kms:<region>:<account>:key/<uuid> does not resolve to a KMS key in this Region'.
Why: a client cannot tell WHICH KMS fault refused the create. On AWS the wrapped class is the whole diagnosis — NotFoundException (no such key) vs DisabledException vs KMSInvalidStateException — and runbooks, retry policies and alarm filters match on that substring. Against the emulator every SSE-KMS fault collapses into one opaque sentence, so error-classification code that works on AWS silently stops classifying.
Fix: the DynamoDB crate's SSE resolution refusal — `crate::state::requested_encryption` / `resolve_sse_key` (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state.rs) and the `sse_unresolved` mapping that lifts it in services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/create_table.rs (~line 581, called at ~line 472).
Traces: dynamodb__kms.xsvc-dynamodb-1-create-table-with-nonexistent-cmk-rejected.

Cause 2 of 3 — GetItem and PutItem on a table whose CMK is DISABLED keep succeeding; no key-state gate exists on the data path.
AWS: recorded behavior only: after kms:DisableKey on the CMK a table was created with, GetItem and PutItem on that table fail with HTTP 400 and Error.Code 'ValidationException' whose message has the fixed text "KMS key disabled error: com.amazonaws.services.kms.model.DisabledException: " <key arn> " is disabled. (Service: AWSKMS; Status Code: 400; Error Code: DisabledException; Request ID: " <per-call id> "; Proxy: null)" — fixed text as quoted, variable parts being the table's CMK ARN (from the table's stored SSE key) and the per-call KMS request id. A PutItem refused that way persists nothing, a table on a DIFFERENT enabled CMK is unaffected, and after kms:EnableKey the same reads and writes succeed with every item written before the disable intact. Smithy corroborates that DynamoDB tracks this: SSEDescription.InaccessibleEncryptionDateTime — "Indicates the time ... when DynamoDB detected that the table's KMS key was inaccessible".
Emulator: no refusal ever arrives. The check polls GetItem every 2 s and leaves its loop ONLY on a ClientError (its own ceiling is 480 s); it never received one and the check ended at the suite's ceiling, reported as 'Check timed out after 180.0s'. The emulator's DisableKey is effective immediately (the check asserts DescribeKey reports KeyState='Disabled' before polling), so no data-key cache window explains it: the DynamoDB data plane simply never consults the state of the table's CMK.
Why: encryption-credential loss is invisible. Reads and writes that production refuses with 400 succeed against the emulator, so the exact failure mode this scenario exists to rehearse — a disabled CMK taking a table offline — cannot be reproduced, and any client or test that asserts the refusal passes for the wrong reason.
Fix: a KMS key-state gate on the DynamoDB data path — the GetItem/PutItem (and Query/Scan/BatchGetItem/BatchWriteItem) handlers under services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/ must resolve the stored table's SSE key against KMS and refuse with ValidationException wrapping the KMS cause, leaving state unchanged.
Traces: dynamodb__kms.xsvc-dynamodb-1-disabled-cmk-reads-and-writes-rejected.

Cause 3 of 3 — GetItem and PutItem on a table whose CMK is PendingDeletion keep succeeding, and the PendingDeletion message class is absent.
AWS: recorded behavior only: after kms:ScheduleKeyDeletion leaves the CMK in KeyState 'PendingDeletion', GetItem and PutItem on the table fail HTTP 400 'ValidationException' with the fixed text "KMS validation error: com.amazonaws.services.kms.model.KMSInvalidStateException: " <key arn> " is pending deletion. (Service: AWSKMS; Status Code: 400; Error Code: KMSInvalidStateException; Request ID: " <per-call id> "; Proxy: null)" — note this class uses "KMS validation error:" and "is pending deletion", a DIFFERENT template from the Disabled case in cause 2, so the two are not one message. CancelKeyDeletion (which must leave the key Disabled, not re-enable it) followed by EnableKey restores reads and writes, the refused PutItem never persisted, and the pre-existing item survives.
Emulator: as in cause 2, GetItem keeps answering 200 for the whole poll and the check ends at the suite ceiling ('Check timed out after 180.0s'); PendingDeletion is never consulted and the KMSInvalidStateException message class is never produced.
Why: the pending-deletion incident (the most destructive CMK state, because the window is finite) is unobservable, and a client that distinguishes a recoverable Disabled key from a key being destroyed gets neither signal.
Fix: same data-path gate as cause 2, with KeyState PendingDeletion mapped to the KMSInvalidStateException-wrapped ValidationException template rather than the DisabledException one.
Traces: dynamodb__kms.xsvc-dynamodb-1-pending-deletion-cmk-reads-and-writes-rejected.

## Steps to Reproduce
1. kms:CreateKey (symmetric ENCRYPT_DECRYPT) -> note KeyId/Arn.
2. Cause 1: dynamodb:CreateTable(TableName=T1, KeySchema=[{pk,HASH}], AttributeDefinitions=[{pk,S}], BillingMode=PAY_PER_REQUEST, SSESpecification={Enabled:true, SSEType:'KMS', KMSMasterKeyId:'arn:aws:kms:<region>:<account>:key/<random uuid that names no key>'}). Observe ValidationException whose message does NOT contain 'com.amazonaws.services.kms.model.NotFoundException'.
3. Create two tables T_target and T_control the same way, each with SSESpecification naming a DIFFERENT real CMK; wait for ACTIVE and confirm DescribeTable.SSEDescription.KMSMasterKeyArn names the key.
4. PutItem then GetItem(ConsistentRead=True) on both to prove both work.
5. Cause 2: kms:DisableKey(KeyId=<target key>); confirm DescribeKey reports KeyState='Disabled'. Poll GetItem(T_target) — it keeps returning 200 indefinitely instead of ValidationException naming DisabledException. PutItem(T_target) also succeeds. T_control is (correctly) unaffected. kms:EnableKey to restore.
6. Cause 3: kms:ScheduleKeyDeletion(KeyId=<target key>, PendingWindowInDays=7); confirm KeyState='PendingDeletion'. Poll GetItem/PutItem(T_target) — both keep returning 200 instead of ValidationException naming KMSInvalidStateException. kms:CancelKeyDeletion (key must land Disabled) + kms:EnableKey to restore.
