=== Cause 1 of 2: DescribeManagedRuleGroup returns an empty AvailableLabels for an AWS-vendor managed rule group ===
Failing check: wafv2.managed-rule-group-describe-catalog-contents

AWS: the label surface of an AWS managed rule group is catalog reference data the service KNOWS, not something derived from the request. Smithy (com-amazonaws-wafv2-awswaf-20190729): DescribeManagedRuleGroup output carries AvailableLabels -> LabelSummaries (list of LabelSummary{Name -> LabelName, @length 1..1024, @pattern ^[0-9A-Za-z_\-:]+$}) and ConsumedLabels -> LabelSummaries, alongside Capacity, Rules, VersionName and SnsTopicArn. Every label an AWS-vendor group publishes lives under the reserved namespace awswaf:managed:aws:<group-slug>:, where <group-slug> is the group's PUBLISHED slug and not its API name — AWSManagedRulesCommonRuleSet publishes under awswaf:managed:aws:core-rule-set:, AWSManagedRulesSQLiRuleSet under awswaf:managed:aws:sql-database:. For an AWS-vendor group the modeled LabelNamespace member is NOT returned at all (recorded behavior only; the namespace must be read off the labels), the core rule set omits ConsumedLabels entirely rather than returning an empty list, AWSManagedRulesBotControlRuleSet DOES return a non-empty ConsumedLabels under awswaf:managed:aws:bot-control: and additionally publishes the vendor-independent token namespaces (awswaf:managed:token:absent:), and SnsTopicArn is an SNS ARN in us-east-1 regardless of the caller's region whose resource segment is aws-managed-waf-rule-notifications.
Emulator: DescribeManagedRuleGroup(VendorName='AWS', Name='AWSManagedRulesCommonRuleSet', Scope='REGIONAL') succeeds (HTTP 200, no error code) but AvailableLabels is empty/absent. AssertionError: "the core rule set publishes AvailableLabels; got none" (check_wafv2_managed_rule_group_describe_catalog_contents.py line 172). The preceding assertions now pass — the catalog lists all 14 AWS-vendor groups with Descriptions and the correct per-group VersioningSupported, the core rule set reports Capacity 700, >=10 member Rules including NoUserAgent_HEADER and SizeRestrictions_BODY, each with an Action — so the group's rules are known but its label catalog is not. Because the label assertion fails first, the remaining label-surface facts in the same check are unverified and may diverge too: LabelNamespace must be ABSENT for an AWS-vendor group, ConsumedLabels must be ABSENT on the core rule set and non-empty on Bot Control under its own namespace and a subset of Bot Control's AvailableLabels, Bot Control must also publish awswaf:managed:token:absent:, SQLiRuleSet's labels must sit under awswaf:managed:aws:sql-database: and differ from the core rule set's, and SnsTopicArn must be the us-east-1 aws-managed-waf-rule-notifications topic.
Why: labels are the documented way to compose managed rule groups — a client writes a LabelMatchStatement against awswaf:managed:aws:core-rule-set:<label> to except or escalate a managed rule's verdict, and discovers the legal label names via DescribeManagedRuleGroup. Against the emulator that discovery returns nothing, so label-based composition cannot be authored or validated at all, and tooling that enumerates labels to build a rule concludes the group emits none and silently drops the exception rule it was written to add.
Fix: the managed-rule-group catalog reference data in the wafv2 crate (services/service-com-amazonaws-wafv2-awswaf-20190729) must hold each AWS-vendor group's published labels (and its published slug, which is not derivable from the API name) and its consumed labels, and the DescribeManagedRuleGroup handler/serializer must emit AvailableLabels from that stored data, omit LabelNamespace for AWS-vendor groups, omit ConsumedLabels when the group consumes none rather than emitting an empty list, and emit the us-east-1 notification topic ARN.
Traces: wafv2.managed-rule-group-describe-catalog-contents (verdict mismatch).

=== Cause 2 of 2: traffic to an API Gateway stage protected by a stack-deployed WAFv2 web ACL never gets a WAF decision ===
Failing checks: wafv2.deploy-ipset-cloudformation-membership-enforced, wafv2.deploy-webacl-cfn-blocks-matching-request, wafv2.deploy-webacl-cfn-enforces-default-block-action

AWS: once an AWS::WAFv2::WebACL (and, where present, AWS::WAFv2::IPSet and AWS::WAFv2::WebACLAssociation) reaches CREATE_COMPLETE and AssociateWebACL has succeeded for the REST API stage ARN, every request to that stage's invoke URL is answered with the web ACL applied. Recorded behavior only for the per-case statuses; what is structural is that a request to the protected endpoint ALWAYS produces an HTTP response, and that the response reflects the ACL: a request whose forwarded IP (X-Forwarded-For, Position FIRST) falls inside a referenced IPSet's CIDR is answered 403 while one outside it is answered 200; a request matching a ByteMatchStatement Block rule on a single header is answered 403 while a non-matching request is answered 200; and with DefaultAction Block and no rules, unmatched traffic is answered 403. AssociateWebACL's documented propagation window ('a few seconds to a number of minutes') is why each check polls rather than asserting once.
Emulator: no HTTP status is ever observed from the protected stage. All three checks exhaust the harness budget and the detail is exactly "Check timed out after 60.0s", so no allow decision, no block decision, and in fact no response of any kind is observable — there is no status, error code or body to compare. Note that in wafv2.deploy-webacl-cfn-enforces-default-block-action the FIRST poll is a positive control on the UNPROTECTED mock REST API serving HTTP 200 before any web ACL exists, so the hang is not necessarily downstream of WAF evaluation. Hypothesis: the API Gateway REST stage invoke path (MOCK integration) does not answer at all, which would make every WAF-at-the-edge decision unreachable; the emulator's own behavior shows only that nothing answers.
Why: the entire IaC-deployed WAF enforcement path is unobservable. A client or test suite that deploys a web ACL by template and then sends traffic to confirm the block sees a hang where AWS serves a 403 or a 200 — it cannot verify that its rules work, and a request that AWS would refuse is neither refused nor allowed.
Fix: the data-plane request path for a REST API stage that has a web ACL associated — the stage invoke handler plus web-ACL evaluation and response generation — must always produce a response, applying the associated ACL's rules (IPSetReferenceStatement with IPSetForwardedIPConfig, ByteMatchStatement on SingleHeader) and its DefaultAction, and the unprotected stage must serve its integration response. The components are the API Gateway stage invoke/data plane and the wafv2 web-ACL evaluation that it must consult.
Traces: wafv2.deploy-ipset-cloudformation-membership-enforced, wafv2.deploy-webacl-cfn-blocks-matching-request, wafv2.deploy-webacl-cfn-enforces-default-block-action (all verdict mismatch).
