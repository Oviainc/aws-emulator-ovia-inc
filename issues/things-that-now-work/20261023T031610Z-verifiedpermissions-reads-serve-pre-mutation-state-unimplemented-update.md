# VerifiedPermissions reads serve pre-mutation state: unimplemented Update/Delete handlers leave identity sources, templates and linked policies stale

> _Note: this issue was identified against the code base at commit `7f205ee96657d4151f96c4aa7296372f34590a63`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIdentitySource

## Description
FOUR distinct causes in service-com-amazonaws-verifiedpermissions-verifiedpermissions, sharing one fault: a mutating control-plane handler is still an unimplemented 501 scaffold, so the mutation never reaches state and the wire-visible divergence lands on the LATER READ, which answers 200 with pre-mutation data instead of the recorded post-mutation response. All four must be closed before this issue is submitted. (The 501 steps themselves are counted separately by the replay as not-implemented operations; what is filed here is the read-side divergence each stub causes, and a fix is only complete when these reads match.)

Cause 1 of 4: GetIdentitySource returns the pre-update identity-source configuration. AWS: Smithy — UpdateIdentitySource(policyStoreId, identitySourceId, updateConfiguration [required], principalEntityType) returns 200 {policyStoreId, identitySourceId, createdDate, lastUpdatedDate}; its modeled doc is "Updates the specified identity source to use a new identity provider (IdP), or to change the mapping of identities from the IdP to a different principal entity type", and its modeled errors are ConflictException(409), ResourceNotFoundException(404), AccessDeniedException(403), InternalServerException(500), ThrottlingException(429), ValidationException(400) — NotImplemented/501 is not a modeled outcome. A following GetIdentitySource must report the NEW openIdConnectConfiguration, entityIdPrefix included. Emulator: GetIdentitySource answers 200 with $.configuration.openIdConnectConfiguration.entityIdPrefix still at the create-time value (recorded run: got 'ExampleOIDC' where the recording has the updated 'UpdatedOIDC'), because services/service-com-amazonaws-verifiedpermissions-verifiedpermissions/src/ops/update_identity_source.rs is the untouched scaffold — its handle body is Err(crate::scaffolded::Scaffolded::not_implemented("UpdateIdentitySource")) and the '//! SCAFFOLDED, NOT IMPLEMENTED' marker is still on line 4. Why: a client that reconfigures an identity source (new issuer, new entityIdPrefix, new token selection, new principal entity type) gets an unmodeled 501 for the write and, if it ignores that, a read that silently reports the stale IdP binding — so every token-based authorization path keeps resolving principals through the OLD provider configuration. Fix: implement the UpdateIdentitySource handler (resolve store + identity source, apply the updateConfiguration union arm and principalEntityType to the stored identity source, advance lastUpdatedDate, return the modeled output) so GetIdentitySource/ListIdentitySources read the updated record. Traces: verifiedpermissions-identity-source-lifecycle#task#7.

Cause 2 of 4: ListIdentitySources still returns an identity source that was deleted. AWS: Smithy — DeleteIdentitySource(policyStoreId, identitySourceId) is idempotent, returns an empty 200 body, and models ConflictException(409), ResourceNotFoundException(404), AccessDeniedException(403), InternalServerException(500), ThrottlingException(429), ValidationException(400). ListIdentitySources output requires identitySources; after the delete the recording returns that list with the deleted source absent (the recorded response has no element at $.identitySources[0]). Emulator: ListIdentitySources answers 200 with the source still present ($.identitySources[0] = the full IdentitySourceItem — identitySourceId, policyStoreId, principalEntityType 'MyCorp::User' and the original openIdConnectConfiguration), because services/service-com-amazonaws-verifiedpermissions-verifiedpermissions/src/ops/delete_identity_source.rs is the untouched scaffold (handle returns Err(crate::scaffolded::Scaffolded::not_implemented("DeleteIdentitySource")), '//! SCAFFOLDED, NOT IMPLEMENTED' on line 4). Why: a client cannot tear down an identity source, and teardown/recreate flows and quota-style assertions that list sources after a delete see a resource AWS has already removed; test fixtures that clean up between cases leak state into the next case. Fix: implement the DeleteIdentitySource handler to remove the identity source from the policy store's state (404 ResourceNotFoundException when the store or source does not resolve) so ListIdentitySources/GetIdentitySource stop serving it. Traces: verifiedpermissions-identity-source-lifecycle#task#9.

Cause 3 of 4: GetPolicyTemplate returns the pre-update template statement. AWS: Smithy — UpdatePolicyTemplate(policyStoreId, policyTemplateId, statement [required], description, name) is idempotent, returns 200 {policyStoreId, policyTemplateId, createdDate, lastUpdatedDate}, and models ConflictException(409), ResourceNotFoundException(404), AccessDeniedException(403), InternalServerException(500), ThrottlingException(429), ValidationException(400). GetPolicyTemplate output requires `statement`, so after a successful update it must return the REPLACEMENT statement. Emulator: GetPolicyTemplate answers 200 with the original statement (recorded run: got 'permit(principal == ?principal, action == Action::"view", resource == ?resource);' where the recording has the updated '... action == Action::"edit" ...'), because services/service-com-amazonaws-verifiedpermissions-verifiedpermissions/src/ops/update_policy_template.rs is the untouched scaffold ('//! SCAFFOLDED, NOT IMPLEMENTED' on line 4, handle returns not_implemented("UpdatePolicyTemplate")). Why: policy templates exist to be edited centrally — every policy linked to the template is supposed to pick up the new statement. A client that edits a template gets an unmodeled 501, and a reader sees the old statement, so authorization decisions for every template-linked policy keep following the superseded rule. Fix: implement the UpdatePolicyTemplate handler (resolve store + template, validate the replacement statement as a Cedar TEMPLATE, store it, advance lastUpdatedDate) so GetPolicyTemplate and template-linked evaluation observe the new statement. Traces: verifiedpermissions-policy-template-workflow#task#8.

Cause 4 of 4: after a policy template is deleted, GetPolicy still returns 200 for the policy that was created from it, instead of 404 ResourceNotFoundException. AWS: Smithy — DeletePolicyTemplate's modeled doc is explicit: "Deletes the specified policy template from the policy store. This operation also deletes any policies that were created from the specified policy template. Those policies are immediately removed from all future API responses, and are asynchronously deleted from the policy store." GetPolicy models ResourceNotFoundException(404), whose shape requires message, resourceId and resourceType (ResourceType enum); the recording for this step is 404 with __type 'com.aws.verifiedpermissions#ResourceNotFoundException', resourceType 'POLICY' and resourceId set to the deleted policy's id. Emulator: GetPolicy answers 200 with the template-linked policy still present — the recorded 404 body members are all absent ($.message, $.resourceId, $.resourceType, $.__type missing). Hypothesis for the mechanism: services/service-com-amazonaws-verifiedpermissions-verifiedpermissions/src/ops/delete_policy_template.rs is the untouched scaffold (handle returns Err(crate::scaffolded::Scaffolded::not_implemented("DeletePolicyTemplate")), line 161, marker on line 4), so neither the template nor its documented cascade onto linked policies ever runs; note that plain DeletePolicy IS implemented and does remove the policy (delete_policy.rs:148), so the gap is specifically the template delete + cascade. Why: a client that removes a template expects the derived permissions to vanish with it — this is a security-relevant invariant. Here the linked policy survives, so IsAuthorized keeps returning ALLOW for a grant the caller believes it revoked, and the resourceId/resourceType a client uses to identify what was missing never arrive. Fix: implement the DeletePolicyTemplate handler — remove the template and every policy whose definition is templateLinked to it from the store's policy state, so a following GetPolicy/ListPolicies answers the modeled 404 ResourceNotFoundException with resourceType POLICY. The exact recorded resourceId is a generated id and is an example, not a requirement; the 404 status, the __type/error code and the presence of resourceId/resourceType are. Traces: verifiedpermissions-policy-template-workflow#task#10.
