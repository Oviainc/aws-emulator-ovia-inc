# mediapackagev2 builds rejection messages from the request (not-found identifiers, ClientToken) and UpdateOriginEndpoint does not rotate the ETag (3 causes)

> _Note: this issue was identified against the code base at commit `6d3a954d57304c873e4e6a3ccc977c1ac1664bbd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateOriginEndpoint

## Description
The mediapackagev2 emulator answers these paths with the right HTTP status, the right error code and the right discriminator enum, but it DERIVES its rejection text from the caller's request where the service's text is request-independent, and its origin-endpoint entity tag does not change when the endpoint is mutated. 3 causes.

Cause 1 of 3: ResourceNotFoundException messages are formatted from the caller's resource identifiers instead of the service's fixed per-resource sentence.
AWS: Smithy: ResourceNotFoundException (com.amazonaws.mediapackagev2#ResourceNotFoundException, errorKind client, httpError 404) binds Message and ResourceTypeNotFound; GetChannel / GetOriginEndpoint declare it. Recorded behavior only for the text, but the RULE the recordings establish is that the message is a fixed sentence per resource type that contains NONE of the caller's identifiers: channel -> "MediaPackage can't process your request because we can't find your channel. Verify your channel name or add a channel and then try again"; origin endpoint -> "MediaPackage can't process your request because we can't find your origin endpoint. Verify your origin endpoint name or add an origin endpoint and then try again".
Emulator: 404 and the code are correct, but the message is interpolated from the request — e.g. 'Channel <channelName> not found in channel group <groupName>' and 'Origin endpoint <endpointName> not found on channel <channelName> in channel group <groupName>'.
Why: the divergence is in the rule that produces the message, not merely in recorded wording: AWS's text is request-independent and the emulator's is request-derived. Clients and conformance suites matching MediaPackage's sentences do not match, and a service that is documented never to echo customer resource names back in an error body now does.
Relation to already-open issues: 20261022T023331Z-mediapackagev2-error-message-rule-tagging-policy-negative-paths.md (Cause 1) and 20261022T021034Z-mediapackagev2-error-bodies-diverge-empty-validationexception-and-identifier.md describe this same root cause for other operations/scopes; neither carries these two check ids, which exercise the channel-scope and origin-endpoint-scope not-found messages reached as the 'effect absent' read of a rejected CreateChannel / CreateOriginEndpoint. Fix them together.
Fix: the shared mediapackagev2 not-found error builder used by the Get*/Create* handlers — emit the fixed per-resource sentence instead of formatting the requested identifiers into it.
Traces: mediapackagev2.create-channel-invalid-locking-mode-combo-rejected, mediapackagev2.create-origin-endpoint-num-manifests-low-rejected.

Cause 2 of 3: the idempotency-token parameter-mismatch ConflictException message embeds the caller's ClientToken where AWS returns a fixed sentence.
AWS: Smithy: CreateChannelGroup and CreateChannel bind ClientToken (IdempotencyToken, @idempotencyToken, httpHeader x-amzn-client-token, @length 1..256, @pattern ^[\S]+$) and declare ConflictException (httpError 409) with members Message and ConflictExceptionType, whose enum values include IDEMPOTENT_PARAMETER_MISMATCH. Recorded behavior only for the text, and the rule it establishes is a fixed, request-independent sentence: "You've specified a client token with your request using parameter values that differ from a previous request that used the same client token. Check your parameters and then try again".
Emulator: the classification is right — HTTP 409, Error.Code 'ConflictException', ConflictExceptionType 'IDEMPOTENT_PARAMETER_MISMATCH', and the resource's Description is correctly left unchanged — but the message is built from the request: 'The ClientToken <token> was already used for a request with different parameters. Repeat the original request, or use a new ClientToken'.
Why: same rule divergence as Cause 1 at the idempotency-conflict scope — the emulator echoes a caller-supplied credential-like value (the client token) into the error body, which the service does not, and text-matching clients/conformance checks on the documented sentence fail.
Fix: the CreateChannelGroup / CreateChannel handlers' idempotency-token mismatch path (the shared conflict-error builder) — emit the service's fixed sentence and keep the ConflictExceptionType discriminator as the machine-readable signal.
Traces: mediapackagev2.channel-group-idempotent-token-mismatch-rejected, mediapackagev2.create-channel-idempotent-token-mismatch-rejected.

Cause 3 of 3: a successful UpdateOriginEndpoint persists the mutation but returns the SAME ETag as the create, so the entity tag never rotates.
AWS: Smithy: UpdateOriginEndpoint (PUT /channelGroup/{ChannelGroupName}/channel/{ChannelName}/originEndpoint/{OriginEndpointName}, success 200) takes the conditional entity tag as ETag -> EntityTag via httpHeader x-amzn-update-if-match (@length 1..256, @pattern ^[\S]+$) and RETURNS ETag plus ModifiedAt; it declares ConflictException (409). That is the optimistic-concurrency contract: the ETag is a function of the stored resource version, so a committed mutation yields a NEW tag and the tag a client held before the update stops matching.
Emulator: the update is applied and echoed (HlsManifests[0].ManifestWindowSeconds goes 60 -> 120 in the update response) but the ETag in that response is byte-identical to the one CreateOriginEndpoint returned, so the check fails on 'ETag did not rotate after a successful update'.
Why: optimistic concurrency is silently defeated. A client that re-sends its stale pre-update ETag in x-amzn-update-if-match is accepted when it must be refused with the conflict class, so a lost-update race cannot be detected; and any cache keyed on the endpoint's ETag never invalidates after a real configuration change.
Relation to already-open issues: 20261022T021034Z-mediapackagev2-update-operations-do-not-persist-mutations-so.md (Cause 3) reports the adjacent symptom that GetOriginEndpoint's ETag differs from the update's ETag (tag recomputed per response); it does not carry this behavioral check id and does not state this requirement — that the tag must CHANGE across a committed mutation. 20261022T023331Z-mediapackagev2-updateoriginendpoint-stub.md predates the operation answering at all. Both must be satisfied by making the tag a function of stored resource version.
Fix: the UpdateOriginEndpoint handler and the origin-endpoint record in mediapackagev2 service state — bump the stored version on commit and derive ETag from it, so the update's ETag differs from the previous one and a following GetOriginEndpoint reports exactly the update's tag.
Traces: mediapackagev2.update-origin-endpoint-manifest-change-persists.

All resource names, tokens, ETag encodings and timestamps quoted are per-run values and are examples; the requirements are the 404/409/200 statuses, the error codes, the ConflictExceptionType/ResourceTypeNotFound discriminators, the request-independent message rule in Causes 1-2, and the ETag-rotation invariant in Cause 3.
