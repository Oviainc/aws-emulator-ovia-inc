# MediaPackage VOD negative classes diverge: DeletePackagingGroup deletes a group with an attached asset, and ListAssets words its invalid-NextToken refusal differently from AWS (2 causes)

> _Note: this issue was identified against the code base at commit `e0f3b342c2995e24bb81f3397837b3776f1c553b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeletePackagingGroup

## Description
Two distinct causes on the MediaPackage VOD (restJson1, sdkId "MediaPackage Vod") control plane, both in the refusal path: one call AWS refuses is performed, and one call AWS refuses is refused with the wrong message text. A fixer MUST close BOTH causes below before submitting.

=== Cause 1 of 2: DeletePackagingGroup destroys a packaging group that still has an attached asset, instead of refusing it 422 UnprocessableEntityException ===
AWS: Smithy (services/service-com-amazonaws-mediapackagevod-mediapackagevod/smithy-model/com-amazonaws-mediapackagevod-mediapackagevod.json): DeletePackagingGroup DELETE /packaging_groups/{Id}, input {Id @httpLabel @required}, empty output, modeled errors ForbiddenException(403), NotFoundException(404), UnprocessableEntityException(errorKind client, httpError 422), TooManyRequestsException(429), InternalServerErrorException(500), ServiceUnavailableException(503). Recorded behavior: while ANY asset still names that packaging group (even with no PackagingConfiguration attached to it), the delete is refused with error code UnprocessableEntityException and the message "id cannot be deleted because it has attached assets" — fixed text in this crate's documented `<member_name> <phrase>` refusal form, where the member name is the DeletePackagingGroup input member `Id` rendered as `id` and the phrase "cannot be deleted because it has attached assets" is constant for this refusal class. The refusal has no side effect: DescribePackagingGroup still returns the group, DescribeAsset still reports the asset with the same PackagingGroupId, and once the asset is deleted the very same DeletePackagingGroup succeeds and DescribePackagingGroup then answers NotFoundException with the message "PackagingGroup with id=<Id> not found" (fixed text around the requested Id).
Emulator: performs the delete. The call returns a success (observed HTTP 204, empty body) with the asset still attached, so the group is gone and the asset is orphaned; the check aborts at that first assertion, so the post-refusal survival assertions (group still describable, asset still naming the group) and the positive control (delete succeeds after the asset is removed, DescribePackagingGroup then says "PackagingGroup with id=<Id> not found") were never exercised and are unverified rather than known-good.
Why: a client relying on AWS's referential-integrity guard loses data and ends up with state AWS cannot produce — assets whose packaging group does not exist, hence un-packageable and un-cleanable through the normal order (delete assets, then configurations, then the group). Teardown and infrastructure tools that treat the 422 as "dependencies remain, retry after removing them" instead take the success branch, and any test asserting the guard gets a false pass.
Fix: the DeletePackagingGroup handler in the mediapackagevod service crate plus the asset state it must consult — before any state write, count stored assets whose PackagingGroupId equals the requested Id and, if non-zero, reject with UnprocessableEntityException / HTTP 422 carrying the attached-assets message (and the per-member `errors` attribution this crate uses for its 422s) while leaving group and asset state untouched. The guard must be independent of whether any PackagingConfiguration references the group.
Traces: mediapackage-vod.delete-packaging-group-with-attached-asset-rejected (AssertionError: expected the call to be rejected, but it succeeded and returned {'ResponseMetadata': {'HTTPStatusCode': 204, ...}}).
Related FIXED issue, not a duplicate and NOT reopened: 20261023T091538Z-mediapackage-vod-deletepackaginggroup-deletes-a-group-that-a.md added the refusal for a group a PackagingConfiguration still references. That fix did not add the ATTACHED-ASSET precondition, which is a separate dependency class; the call here is not refused at all, so this is not a refusal left behind by that fix.

=== Cause 2 of 2: ListAssets refuses a bogus NextToken with the crate's own wording instead of AWS's "Invalid NextToken" ===
AWS: Smithy: ListAssets GET /assets, code 200, input {MaxResults @httpQuery("maxResults") @range(min 1,max 1000), NextToken @httpQuery("nextToken"), PackagingGroupId @httpQuery("packagingGroupId")}, @paginated(inputToken NextToken, outputToken NextToken, items Assets), errors include UnprocessableEntityException (errorKind client, httpError 422, member Message jsonName "message"). Recorded behavior: a syntactically bogus nextToken (one this service never issued) is refused with error code UnprocessableEntityException and the message "Invalid NextToken" — that string is entirely FIXED text for this refusal class: it interpolates nothing from the request, does not name the input member and does not echo the offending token.
Emulator: refuses with the right error code (UnprocessableEntityException) but words the message as "next_token is not a cursor this service issued", i.e. it applies this crate's generic `<member_name> <phrase>` refusal form (member rendered as `next_token`) to a case where AWS uses a fixed sentence instead. Replay detail: `AssertionError: expected message 'Invalid NextToken', got 'next_token is not a cursor this service issued'`. Status and error code match; only the message text diverges.
Why: the error message is part of the contract a client sees. Clients, log scrapers and test suites that match on AWS's "Invalid NextToken" never match, and anyone reading the emulator's message is told the refusal is about a member named `next_token`, which is not an AWS input member name (the wire member is `nextToken`) — so the message both fails to match and misnames the field.
Fix: the invalid-pagination-token refusal for ListAssets in the mediapackagevod service crate (the forged-cursor branch of its page-token decoding, whose refusal builder currently composes the per-member phrase). It must emit the fixed message "Invalid NextToken" for an undecodable/unissued nextToken while keeping error code UnprocessableEntityException and HTTP 422. Check the sibling listings (ListPackagingGroups, ListPackagingConfigurations) for the same wording so the rule is applied consistently where the recordings show it.
Traces: mediapackage-vod.list-assets-invalid-next-token-rejected (the positive control in the same check — the untokened ListAssets listing the created asset — was not reached).
Related FIXED issue, not a duplicate: 20261024T211538Z-mediapackage-vod-listassets-error-response.md moved framework-found violations into this service's 422/errors envelope and explicitly lists the "forged nextToken" case as already handled by the handler. The code and status it is about are correct here; what diverges is only the message text of that handler-built refusal, so this is a wording defect on top of that fix, not a call left refused by it.

Related OPEN issues, neither a duplicate: 20261025T172535Z (DeletePackagingGroup empty 204 omits Content-Length: 0) and 20261029T174428Z (ListAssets filtered body / empty-204 Content-Length) are serialization-framing and body-projection defects on these same two operations; neither adds the attached-asset precondition nor changes the invalid-NextToken message.
