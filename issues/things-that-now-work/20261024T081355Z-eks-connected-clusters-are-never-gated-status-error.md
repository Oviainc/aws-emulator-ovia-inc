# EKS: connected clusters are never gated (status error instead of ClientException), the version catalog serves out-of-support versions, ListClusters include refusals use the wrong code, and DeleteAccessEntry is a 501 stub (4 causes)

> _Note: this issue was identified against the code base at commit `3a80585caf3e9f62e646ed534a139af0bb6604b7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateEncryptionConfig

## Description
Replaying the behavioral suite against the EKS emulator (service crate services/service-com-amazonaws-eks-awswesleyfrontend) shows FOUR distinct root causes that are not covered by any open issue on this service. Each must be closed; the issue is NOT complete until all four are.

Cause 1 of 4 - a REGISTERED (connected) cluster is not gated: EKS-managed-plane operations answer a cluster-status error instead of the connected-cluster refusal.
AWS: Smithy (com-amazonaws-eks-awswesleyfrontend): AssociateEncryptionConfig (POST /clusters/{clusterName}/encryption-config/associate) and CreateAddon (POST /clusters/{clusterName}/addons) both model ClientException (httpError 400) alongside InvalidParameterException (400), InvalidRequestException (400) and ResourceNotFoundException (404), so ClientException is the modeled class for "this operation does not apply to this cluster". Recorded behavior for the gate itself: on a cluster created with RegisterCluster (one EKS does not manage), every operation that belongs to the EKS-managed plane is refused with error code ClientException and the fixed sentence "This operation is not supported for connected clusters" - observed for CreateAddon, CreateAccessEntry, UpdateClusterVersion, UpdateClusterConfig, ListAddons, ListNodegroups, ListAccessEntries, DescribeAddon, DescribeAccessEntry and AssociateEncryptionConfig. The ordering is also recorded: request-payload validation runs BEFORE the gate (CreateFargateProfile with no selectors on the same connected cluster is refused InvalidParameterException naming the selector constraint), an unknown cluster name is still ResourceNotFoundException, and replaying a refused call returns the identical refusal (nothing was created).
Emulator: the connected-cluster gate does not exist; the cluster-status gate fires instead. AssociateEncryptionConfig on a registered cluster answers InvalidRequestException "Cluster <name> is in PENDING status; it must be ACTIVE to associate an encryption configuration" and CreateAddon answers InvalidRequestException "Cluster <name> is in PENDING status; it must be ACTIVE to create an add-on.". (The record carries connector_config - see ClusterRecord in src/state.rs - but no handler consults it.)
Why: ClientException/"not supported for connected clusters" is a PERMANENT refusal a client uses to decide the cluster is externally managed and to stop; InvalidRequestException "...must be ACTIVE" reads as transient, so a client (or a waiter) retries forever waiting for a connected cluster to become ACTIVE, which it never will. It also means an emulator-backed test cannot distinguish "EKS does not manage this cluster" from "not ready yet".
Fix: the shared cluster-resolution path in src/state.rs plus the per-operation handlers in src/ops/ - after resolving the cluster and validating the payload, and before the status gate, refuse with ClientException when ClusterRecord::connector_config is set.
Traces: eks.associate-encryption-config-invalid-parameter, eks.connected-cluster-refuses-eks-managed-children.

Cause 2 of 4 - DescribeClusterVersions serves versions whose extended support has already ended when includeAll was not asked for.
AWS: Smithy: DescribeClusterVersions is GET /cluster-versions; its input carries includeAll (BoxedBoolean, httpQuery "includeAll", documented "Include all available versions in the response"), versionStatus (VersionStatus) and the deprecated status (ClusterVersionStatus); each ClusterVersionInformation carries endOfStandardSupportDate, endOfExtendedSupportDate and versionStatus (UNSUPPORTED | STANDARD_SUPPORT | EXTENDED_SUPPORT). Recorded behavior: an UNFILTERED call returns only versions still inside standard or extended support, and each entry's versionStatus agrees with its own dates (STANDARD_SUPPORT while now < endOfStandardSupportDate, EXTENDED_SUPPORT between the two end dates); a version whose endOfExtendedSupportDate has passed appears only when the caller asks for it (includeAll=true, or versionStatus/status naming the unsupported state). The specific version numbers and dates are catalog values and are examples; the requirement is the filter.
Emulator: the static calendar is served unfiltered. src/state.rs VERSION_CALENDAR contains ("1.30", release 2024-05-23, standard end 2025-07-23, extended end 2026-07-23) and the paginated unfiltered DescribeClusterVersions still lists 1.30 after 2026-07-23 - even though the crate's own ClusterVersionRecord::support_status() classifies it UNSUPPORTED at that point, so the served entry contradicts its own dates.
Why: version discovery is the first call of every provisioning flow: a client picks a clusterVersion off the unfiltered catalog and hands it to CreateCluster. Against this emulator it can pick a version AWS no longer offers, so code that is correct against AWS fails (or silently pins an unsupported version), and upgrade planners that read versionStatus see a status its dates contradict.
Why this is net-new: the open issue "EKS read-only catalog operations serve an incomplete static catalog (3 causes)" (20261023T152714Z) covers the catalog being EMPTY / structurally incomplete in the wire corpus; it does not carry this check's key and says nothing about the support-window filter.
Fix: the DescribeClusterVersions handler in src/ops/ - exclude rows whose support_status() is UNSUPPORTED unless includeAll (or an explicit status/versionStatus filter) asks for them, keeping the result consistent with each row's dates.
Traces: eks.ekscc-cluster-versions-support-status-agrees-with-support-dates.

Cause 3 of 4 - ListClusters refuses an invalid include token with the wrong error code.
AWS: Smithy: ListClusters is GET /clusters with include -> IncludeClustersList (httpQuery "include"); its modeled errors are ClientException (400), InvalidParameterException (400), ServerException (500) and ServiceUnavailableException (503). Recorded behavior: the include token set is matched as an exact set-membership test and is never case-folded, so an uppercase 'ALL' is refused exactly like a wholly unknown token - HTTP 400 with error code InvalidRequestException and the fixed sentence "One or more values in the 'include' parameter is not valid".
Emulator: include=['ALL'] is refused 400 with error code InvalidParameterException instead.
Why: the error code is what a client branches on. A caller that distinguishes "bad include projection" (InvalidRequestException) from a parameter-shape complaint takes the wrong branch, and a suite asserting the documented refusal class fails against the emulator while passing against AWS. The lowercase include=['all'] projection itself behaves (the check's paginated 'all' assertions passed before this point), so only the refusal class is wrong.
Fix: the ListClusters handler's include validation in src/ops/ - validate the token by exact membership and raise the InvalidRequestException refusal.
Traces: eks.list-clusters-include-projection-under-pagination.

Cause 4 of 4 - DeleteAccessEntry is an unimplemented scaffold stub answering 501, which also hangs the CloudFormation access-entry flow.
AWS: Smithy: DeleteAccessEntry is DELETE /clusters/{clusterName}/access-entries/{principalArn} with an empty 200 response, and models InvalidParameterException (400), ResourceNotFoundException (404), ClientException (400) and ServerException (500) - it never answers 501, and deleting an existing entry succeeds and removes it (a later DescribeAccessEntry is ResourceNotFoundException).
Emulator: services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/delete_access_entry.rs still carries the "SCAFFOLDED, NOT IMPLEMENTED" marker and answers HTTP 501 NotImplemented. Because the failing check probes the principal with a create-then-delete pair inside a bounded retry loop that swallows ClientError, the 501 is retried for 90s instead of surfacing, so the check never reaches its CloudFormation stage and is killed at the 60s harness cap ("Check timed out after 60.0s"). No open issue names this operation, and the suite did not attribute the check to it precisely because the error is swallowed.
Why: an access entry can never be removed, so access revocation is unexpressible and every create/delete round trip over access entries (including the AWS::EKS::AccessEntry teardown path) either hangs or leaves state behind; a 501 is also an unmodeled class no client branches on.
Fix: implement src/ops/delete_access_entry.rs - resolve the cluster, remove the principal's entry from ClusterRecord::access_entries, answer 200 with an empty body, and 404 ResourceNotFoundException when the entry (or cluster) is absent; then drop the SCAFFOLDED marker line.
Traces: eks.deploy-accessentry-via-cloudformation-grants-access.
