## Description
Five of the parent report's six causes are untouched, and the first cause is closed only for the integrations this emulator can make the call for. What the parent fix DID land, so a later fixer does not redo it: a `Task` state's integration names its service by the token its family uses (the ARN namespace for `arn:aws:states:::<namespace>:<action>`, the AWS SDK name for `arn:aws:states:::aws-sdk:<sdk name>:<action>`), its request reaches the invoked operation under that model's own member spelling, its result comes back in PascalCase, the optimized nested-execution integration carries `Input` as the JSON text `StartExecution` types, `.sync:2` reports the job's `Input` and `Output` parsed, and a `Resource`'s integration pattern stays part of the action its history events name.

Cause 1 of 6: a `Task` state still cannot call four kinds of work, so the executions that need them never succeed.
AWS: a `Task` whose `Resource` is a Lambda function ARN invokes that function and binds its payload as the state result; `arn:aws:states:::lambda:invoke` does the same and reports the SDK's own envelope; `aws-sdk:sts:*` and `glue:startJobRun.sync` run equally; and the state machine's execution ROLE authorizes each call, so a parent whose role lacks `states:StartExecution` on the child fails with `States.TaskFailed` rather than succeeding.
Emulator, and WHY each one is still open:
* a Lambda `Resource` (a function ARN or `lambda:invoke`) — the Lambda emulator's own `Invoke` answers HTTP 501 for `RequestResponse` because nothing in this process runs a deployment package (`services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs`, the `NotImplemented` arm of its `handle`). Routing a task there would only exchange one refusal for another, so no Lambda entry was added to the integration table; this cause is BLOCKED on an in-process Lambda runtime, which is that crate's own work.
* `aws-sdk:sts:getCallerIdentity` — STS binds its request to `awsQuery` form fields rather than to one JSON document, and `src/state/integration.rs` makes a call only for the services whose protocol carries the request as one JSON document (its `APIS` table). An `awsQuery`/`restJson1`/`restXml` request binding is the work this needs, and it is also what `s3`, `xray` and `lambda` need.
* `glue:startJobRun.sync` — Glue IS an `awsJson1_1` service, but its run-a-job pattern does not fit the catalogue's shape: `GetJobRun` needs the job NAME beside the run id and `BatchStopJobRun` takes a list, while `RunAJob` carries one identifier member per call. The entry needs the reporting and stopping requests to be built from the STARTING request as well as from its answer.
* no authorization at all — every integration call is signed with the emulator's own credentials (`src/state/integration.rs`, `credentials`), so the execution role is never consulted. `sfn.deep-sfn-1-sfn-sync-start-unpermitted-child-rejected` now gets past its own key and fails on exactly this: the parent targeting a child its role does not permit SUCCEEDS where AWS fails it. The same gap is what `s3__sfn.sfn-distributed-map-without-start-execution-permission-fails-with-zero-children` and `events__lambda__stepfunctions.refarch-sfn-nonexistent-role-accepted-at-create-rejected-on-data-plane` need.
* the SDK response envelope — an optimized request-response integration reports `SdkHttpMetadata` (the answer's status and headers) and `SdkResponseMetadata` (its request id) beside the response members; `sfn.nested-fire-and-forget-start-execution-does-not-block-on-child` now fails on their absence. The status is known in process, but the in-process connector REBUILDS an answer from its status and body alone and drops its headers (`vendor/server/src/lib.rs`, `http_connector_call`), so the request id and the headers cannot be read from here: this one needs that vendored connector to carry the response headers.
* the `.sync` pattern on an EXPRESS machine — `sfn.deep-sfn-1-sfn-sync-express-machine-sync-task-rejected-at-runtime` gets past its own key and fails on the cause wording of the refusal, which must be AWS's own for a run-a-job task inside a synchronous execution.
* the member spelling of a NESTED structure in a result — AWS reports an integration's result in PascalCase at every level of the operation's own structures (`StateMachines[0].StateMachineArn`), while this emulator re-spells the top level only, because below it a document also carries a caller's data (a DynamoDB attribute name, a child execution's output) and the invoked model's member names are not readable from this crate. A state reading a nested structure member therefore still sees the invoked model's spelling. Re-spelling further needs the member names of the invoked operation, which is the same model access cause 1's other halves need.

AWS: a state machine whose top-level `QueryLanguage` is `JSONata` (or a state with a per-state `QueryLanguage`) evaluates `{% ... %}` expressions for Choice `Condition`, Task `Arguments`/`Output` and `Assign` variable scoping, reads `$states.input`/`$states.result`/`$states.context`, and runs to SUCCEEDED; a `Condition` that evaluates to a non-boolean is refused with the language's own query error.
Emulator: every JSONata definition fails at the first state with `error='States.Runtime'`, `cause="state '<Name>' is written in 'JSONata', and this emulator evaluates only 'JSONPath' states, so nothing was run for it"` (`src/state/asl.rs`).
Fix: an expression evaluator in the interpreter's expression component plus honouring `QueryLanguage` at the definition and state level. A maintained crate exists for the language itself (`jsonata-rs`, 0.3.4 on crates.io, Apache-2.0) — the hand-written half is the ASL side: which members are expressions, the `$states` context, and `Assign` scoping.

Cause 5 of 6: the callback (`.waitForTaskToken`) pattern never produces or consumes a task token, and the checks hang. UNTOUCHED by the parent fix.
AWS: a `Task` whose `Resource` ends in `.waitForTaskToken` emits `$$.Task.Token` in the request it sends, pauses the execution, and resumes on `SendTaskSuccess`/`SendTaskFailure`; `SendTaskHeartbeat` resets the heartbeat clock and a missed heartbeat fails the execution with `States.HeartbeatTimeout`; an unknown token is refused with `TaskDoesNotExist`.
Emulator: `src/state/integration.rs` `read` refuses the pattern ("whose outcome is a later 'SendTaskSuccess' from outside the execution, so nothing was run for it"), so no token is ever delivered and no execution resumes.
What the parent fix established as the way in: the machinery this needs already exists for ACTIVITY tasks — `ActivityTask` keyed by its token, the heartbeat and timeout clock on it (`src/state.rs`), the suspension of the walk (`Run::waiting`) and the `SendTaskSuccess`/`SendTaskFailure`/`SendTaskHeartbeat` handlers that resolve one. A callback task is that record with no activity to be polled under and with its token minted DURING the walk, because the token is part of the request the state sends.
