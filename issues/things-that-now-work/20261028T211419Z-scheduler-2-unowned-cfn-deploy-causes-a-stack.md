# scheduler: 2 unowned CFN-deploy causes — a stack-created AWS::Scheduler::Schedule never delivers to its SQS target, and a stack UPDATE never re-arms/redirects the schedule's Target

> _Note: this issue was identified against the code base at commit `6d6ad5a616787271919bea7a2385fb4712ae6496`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSchedule

## Description
Two net-new root causes in the scheduler service, both reached through CloudFormation-owned schedules. Neither is carried by any open issue's replay key: 20261025T034039Z-scheduler-a-cloudformation-deployed-aws-scheduler-schedule-never-fires.md owns only scheduler.deploy-cfn-schedule-invokes-sqs-target, and 20261023T191008Z-scheduler-eventbridge-scheduler-never-fires-a-schedule-no-invocation.md owns only API-created-schedule checks, so these two checks are ungated and must be re-replayed in their own right. Neither check fails on a refusal of an operation a fixed issue claimed to fix, so neither is a reopen.

Cause 1 of 2: a schedule provisioned by CloudFormation as AWS::Scheduler::Schedule, whose target queue URL is read back from the stack's Outputs (Ref on the AWS::SQS::Queue), never produces an invocation, so the deployed one-time occurrence never delivers its Target.Input to the queue. Failing check: scheduler.deploy-cloudformation-schedule-invokes-target.
AWS: AWS::Scheduler::Schedule maps onto the scheduler control plane operation CreateSchedule (Smithy, scheduler/AWSChronosService: CreateSchedule POST /schedules/{Name}, 200; required members ScheduleExpression (@length 1..256), Target, FlexibleTimeWindow; Name @length 1..64 @pattern ^[0-9a-zA-Z-_.]+$; ScheduleExpressionTimezone @length 1..50; output ScheduleArn @pattern ^arn:aws(-[a-z]+)?:scheduler:[a-z0-9\-]+:\d{12}:schedule\/[0-9a-zA-Z-_.]+\/[0-9a-zA-Z-_.]+$; errors ConflictException 409, ResourceNotFoundException 404, ValidationException 400, ThrottlingException 429, ServiceQuotaExceededException 402, InternalServerException 500). The model says nothing about occurrence firing — recorded behavior only: once the stack reaches CREATE_COMPLETE, the schedule's at(<fire-time>) occurrence fires exactly once at that instant with ScheduleExpressionTimezone=UTC and FlexibleTimeWindow Mode=OFF, scheduler assumes Target.RoleArn and sends Target.Input verbatim as the body of one SQS message to the queue named by Fn::GetAtt [Queue, Arn], and the queue URL exposed in the stack Output (Ref Queue) is the same queue that receives it.
Emulator: the queue addressed by the stack Output stays empty for the entire poll window and the check never reaches its assertions; the suite reports '[mismatch] Error: Check timed out after 60.0s'. No message, no error, nothing on any queue — the control-plane read of the schedule looks healthy while the data plane produces nothing.
Why: a client that owns schedules as IaC gets a green CREATE_COMPLETE and a dead timer: work meant to be enqueued on the deployed schedule is silently never enqueued, with no error or status anywhere to signal it, and negative expectations (nothing delivered after teardown) appear satisfied for the wrong reason.
Fix: the scheduler crate's occurrence-evaluation and target-dispatch component, armed from the create/update/delete schedule handlers, plus the CloudFormation resource-provider mapping for AWS::Scheduler::Schedule so that a stack-created schedule is armed by exactly the same path as an API-created one (and the stack's SQS Output resolves to that same queue).
Traces: scheduler.deploy-cloudformation-schedule-invokes-target.

Cause 2 of 2: a CloudFormation stack UPDATE that changes the schedule's Target (new target ARN and new Input, selected by a template Condition/Fn::If on a changed parameter, with a new at() fire time) does not re-arm the schedule, so the post-update occurrence is never delivered to the new target. This is distinct from Cause 1: it is the stack-update path (UpdateStack -> UpdateSchedule) rather than the create path, and the requirement is redirection — the new target receives exactly one message and the old target receives nothing more. Failing check: scheduler.deploy-cfn-schedule-update-changes-target-behavior.
AWS: the update maps onto UpdateSchedule (Smithy, scheduler/AWSChronosService: UpdateSchedule PUT /schedules/{Name}, 200; required members ScheduleExpression, Target, FlexibleTimeWindow — UpdateSchedule is a full replacement, so the supplied Target wholly replaces the stored one; output ScheduleArn with the same pattern; errors ConflictException 409, ResourceNotFoundException 404, ValidationException 400). Occurrence behavior is recorded behavior only: after stack_update_complete, the schedule's next at(<new-fire-time>) occurrence fires once and delivers the new Target.Input to the NEW Target.Arn queue, and the previously targeted queue receives no further message at all.
Emulator: the check times out ('[mismatch] Error: Check timed out after 60.0s') before any delivery assertion; neither the pre-update delivery to the first queue nor the post-update delivery to the second queue occurs, so the redirection requirement and the 'old target receives nothing more' requirement are never exercised. The schedule's stored Target may be updated in state, but nothing is armed or re-armed, so no occurrence is ever dispatched to either target.
Why: a client that redirects a schedule's target through its stack template sees a successful UPDATE_COMPLETE while deliveries silently stop (or, if firing is later added without re-arming on update, continue going to the stale target) — an IaC change that appears applied is not in effect in the data plane.
Fix: the scheduler crate's dispatch component must be re-armed from the UpdateSchedule handler on a full Target replacement (old target disarmed, new Target.Arn/RoleArn/Input used for subsequent occurrences), and the CloudFormation provider's update path for AWS::Scheduler::Schedule must drive that same UpdateSchedule handler on stack update.
Traces: scheduler.deploy-cfn-schedule-update-changes-target-behavior.

## Evidence
Cause 1 — check scheduler.deploy-cloudformation-schedule-invokes-target: [mismatch] 'Error: Check timed out after 60.0s'.
Expected: create_stack with AWS::SQS::Queue + AWS::IAM::Role (trusting scheduler.amazonaws.com, inline sqs:SendMessage on Fn::GetAtt Queue.Arn) + AWS::Scheduler::Schedule{Name: <name>, ScheduleExpression: 'at(<now+150s>)', ScheduleExpressionTimezone: 'UTC', FlexibleTimeWindow:{Mode:'OFF'}, Target:{Arn: GetAtt Queue.Arn, RoleArn: GetAtt SchedulerRole.Arn, Input: <payload JSON>}} and Outputs.QueueUrl = Ref Queue reaches CREATE_COMPLETE; then polling sqs.receive_message on that Output URL (WaitTimeSeconds=10, up to 300 s) yields exactly one message whose Body equals the Payload parameter verbatim.
Actual: the Output queue stays empty for the whole window; the check is cut off at the harness 60 s cap, so 'CloudFormation-deployed schedule never delivered a message' and the Body-equality assertion are never evaluated. No error response is produced by any operation — the divergence is the absent delivery.

Cause 2 — check scheduler.deploy-cfn-schedule-update-changes-target-behavior: [mismatch] 'Error: Check timed out after 60.0s'.
Expected: stack with QueueA, QueueB, a scheduler-trusted role allowed sqs:SendMessage on both queue ARNs, and AWS::Scheduler::Schedule whose Target.Arn is {Fn::If:[IsQueueB, GetAtt QueueB.Arn, GetAtt QueueA.Arn]} and Target.Input is {Ref MessageBody}. With UseQueueB=false, exactly one message with Body equal to the first MessageBody parameter value arrives on QueueA at the first at() fire time. After update_stack flips UseQueueB to true, changes MessageBody and sets a new at() fire time and stack_update_complete returns, exactly one message with Body equal to the new MessageBody value arrives on QueueB, and a further poll of QueueA returns no message at all.
Actual: no message is ever delivered to QueueA or QueueB; the check is killed at the 60 s cap before 'initial deploy never delivered to queue A', the post-update delivery to queue B, and the 'old target queue A received a message after the target was updated' assertions can be evaluated.

## Steps to Reproduce
Cause 1 (scheduler.deploy-cloudformation-schedule-invokes-target):
1. Build a template with Parameters ScheduleName, QueueName, ScheduleExpression, Payload and Resources: Queue (AWS::SQS::Queue, QueueName from the parameter), SchedulerRole (AWS::IAM::Role, AssumeRolePolicyDocument allowing sts:AssumeRole for Service scheduler.amazonaws.com, inline policy allowing sqs:SendMessage on {Fn::GetAtt:[Queue,Arn]}), Schedule (AWS::Scheduler::Schedule, Name=Ref ScheduleName, ScheduleExpression=Ref ScheduleExpression, ScheduleExpressionTimezone='UTC', FlexibleTimeWindow={Mode:'OFF'}, Target={Arn: GetAtt Queue.Arn, RoleArn: GetAtt SchedulerRole.Arn, Input: Ref Payload}); Outputs.QueueUrl = {Ref: Queue}.
2. cloudformation.create_stack(StackName=s, TemplateBody=<template>, Parameters with ScheduleExpression='at(<now+150s UTC, %Y-%m-%dT%H:%M:%S>)' and Payload a JSON string, Capabilities=['CAPABILITY_IAM'], OnFailure='DELETE'); wait the stack_create_complete waiter and assert StackStatus == 'CREATE_COMPLETE'.
3. Read Outputs.QueueUrl from describe_stacks and poll sqs.receive_message(QueueUrl=that URL, MaxNumberOfMessages=1, WaitTimeSeconds=10) for up to 300 s. On AWS one message arrives whose Body equals the Payload parameter; on the emulator the queue stays empty and the check is killed at the 60 s cap.

Cause 2 (scheduler.deploy-cfn-schedule-update-changes-target-behavior):
1. Build a template with Parameters ScheduleName, QueueAName, QueueBName, RoleName, FireTime, MessageBody, UseQueueB (AllowedValues true/false, Default false), Condition IsQueueB = Fn::Equals[Ref UseQueueB, 'true'], Resources QueueA and QueueB (AWS::SQS::Queue), SchedulerRole (AWS::IAM::Role with RoleName, trusting scheduler.amazonaws.com, inline sqs:SendMessage on both queue ARNs) and MySchedule (AWS::Scheduler::Schedule, ScheduleExpression={Fn::Sub:'at(${FireTime})'}, FlexibleTimeWindow={Mode:'OFF'}, Target={Arn: Fn::If[IsQueueB, GetAtt QueueB.Arn, GetAtt QueueA.Arn], RoleArn: GetAtt SchedulerRole.Arn, Input: Ref MessageBody}).
2. create_stack with UseQueueB='false', FireTime=<now+4min>, MessageBody=<marker A>, Capabilities=['CAPABILITY_NAMED_IAM'], OnFailure='DELETE'; wait stack_create_complete.
3. sqs.get_queue_url for both queue names, then poll receive_message on queue A until 3 minutes past the fire time: on AWS one message with Body == <marker A> arrives; delete it.
4. update_stack with the same template, UseQueueB='true', a new FireTime=<now+4min> and MessageBody=<marker B>; wait stack_update_complete.
5. Poll receive_message on queue B until 3 minutes past the new fire time: on AWS one message with Body == <marker B> arrives. Then poll queue A for ~10 s: on AWS nothing arrives. On the emulator neither queue ever receives a message and the check is killed at the 60 s cap.
