# S3 Vectors refusal messages diverge on 8 further refusal paths: not-found wording on the data plane, DeleteVectorBucket/CreateIndex/TagResource conflict wording, and PutVectors / PutVectorBucketPolicy / ListVectors validation wording

> _Note: this issue was identified against the code base at commit `5b71589754f95f05f88c1a0ee9ccd691bbc5f701`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListVectors

## Description
EIGHT independent root causes found by the behavioral replay in the s3vectors emulator's refusal MESSAGES. On every one of them the HTTP status and the error code are correct and the refusal happens at the right moment; what diverges is the `message` member the client reads, which is this emulator's own sentence instead of the sentence S3 Vectors answers. Each cause is numbered below and carries its own failing check ids. All eight must be closed before this issue is submitted.

Neighbouring OPEN issues, named so a fixer does not mistake them for coverage — none of them carries any of the check ids below:
* 20261029T192108Z-s3vectors-s3-vectors-not-found-and-already-exists-refusals.md covers the same INDEX_NOT_FOUND / already-exists wording fault, but only on the CONTROL-plane operations GetIndex, DeleteIndex, ListTagsForResource, TagResource, CreateIndex and CreateVectorBucket as observed in the WIRE corpus. Causes 1 and 2 below are the DATA-plane operations (ListVectors, PutVectors) and Cause 3 is CreateIndex's conflict observed behaviorally; Cause 4 (DeleteVectorBucket's not-empty ConflictException) appears in neither.
* 20261029T192108Z-s3vectors-s3-vectors-input-validation-diverges-validationexception-messages-are.md covers PutVectors dimension-mismatch and PutVectorBucketPolicy malformed-policy wording from the WIRE corpus; Causes 5 and 6 below are the same fault re-confirmed behaviorally and are listed here because the behavioral check ids they are grounded in are not carried by that issue. Causes 7 (zero-norm vector) and 8 (ListVectors segment range) are not in it at all.
* 20261029T192108Z-s3vectors-s3-vectors-data-plane-operations-report-the-vector.md concerns WHICH resource a data-plane not-found names (bucket vs index), not the sentence used once the right resource is named.
Progression note (not a reopen): the FIXED issue 20261023T072117Z-s3vectors-4-behavioural-divergences-vector-bucket-policy-deny.md asked, in its Cause 3, for ConflictException to be raised at all under concurrent tag mutations. That fix landed — the racing callers now ARE refused with 409 ConflictException, which is the correct outcome. Cause 8 below is only the message that refusal carries, so this is new work on a now-correct refusal, not a regression of that fix.

=== Cause 1 of 8: ListVectors' NotFoundException for a missing index says 'vector index' where the service says 'index' ===
AWS: Smithy (services/service-com-amazonaws-s3vectors-s3vectors/smithy-model/com-amazonaws-s3vectors-s3vectors.json) models NotFoundException on ListVectors with errorKind client, httpError 404 and a required `message` member (doc: "The request was rejected because the specified resource can't be found."). ListVectors naming an index that does not exist in an existing vector bucket is refused with HTTP 404 NotFoundException and message exactly "The specified index could not be found". That sentence is entirely FIXED text: it interpolates no bucket name, index name or ARN from the request, so there is no variable part to fill.
Emulator: HTTP 404, code NotFoundException (both correct), message "The specified vector index could not be found" — the extra word 'vector'.
Why: both a missing bucket and a missing index arrive as the same 404/NotFoundException, so the refusal TEXT is the only thing a client can branch on to tell them apart. A caller that distinguishes them, logs them, or asserts the documented sentence silently takes its fallback path here and the intended path against AWS.
Fix: the shared not-found message constant the index lookup lifts into every operation's NotFoundException (the `INDEX_NOT_FOUND` constant in services/service-com-amazonaws-s3vectors-s3vectors/src/state.rs and the `LookupError` -> NotFoundException conversion used by ListVectors' handler).
Traces: s3vectors.list-vectors-nonexistent-index-not-found.

=== Cause 2 of 8: PutVectors against a DELETED index carries the same wrong not-found sentence ===
AWS: Smithy models NotFoundException on PutVectors (errorKind client, httpError 404, required `message`). A write to an index that has been deleted is refused with HTTP 404 NotFoundException and the same fixed sentence "The specified index could not be found".
Emulator: HTTP 404 NotFoundException with message "The specified vector index could not be found".
Why: the write path is where ingestion pipelines live. A producer that re-creates a destination index when it learns the index is gone matches on the refusal text; the wrong sentence turns a recoverable condition into an unknown failure, and no test can assert the service's sentence.
Fix: same component as Cause 1 — the shared `INDEX_NOT_FOUND` sentence in crate::state, lifted by PutVectors' handler. Fixing the constant fixes Causes 1 and 2 together, but both checks must be re-replayed.
Traces: s3vectors.deleted-vector-key-reusable-and-deleted-index-refuses-writes (its delete-idempotency and key-reuse legs pass; the PutVectors-against-a-dead-index message assertion is the failing leg).

=== Cause 3 of 8: CreateIndex's duplicate-name ConflictException replaces the service's sentence with a request-derived one ===
AWS: Smithy models ConflictException on CreateIndex with errorKind client, httpError 409 and a required `message` (doc: the request failed because a vector bucket name or vector index name already exists; choose a different name). Re-creating an index whose name is already in use in the same vector bucket — even with a different `dimension` — is refused with HTTP 409 ConflictException and message exactly "An index with the specified name already exists". All FIXED text: neither the index name nor the bucket name is interpolated.
Emulator: HTTP 409 ConflictException with a constructed sentence of the form "vector index already exists: <indexName> in vector bucket <vectorBucketName>". The two names are values taken from the request; they are not part of any template AWS uses here.
Why: duplicate-create is the single most commonly TOLERATED refusal in provisioning code (create-if-absent), and it is tolerated by inspecting the code plus the text. The emulator's sentence is both misworded and over-shares caller input, so no assertion on the conflict text can hold and a client that parses the text to recover the conflicting name is being taught a shape AWS never emits.
Fix: CreateIndex's conflict path — the ConflictException message it constructs (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/create_index.rs and the already-exists refusal it lifts from crate::state): emit the single fixed sentence with no request values.
Traces: s3vectors.create-index-duplicate-name-rejected (the 'original dimension not overwritten' and distinct-name positive-control legs pass; only the message assertion fails).

=== Cause 4 of 8: DeleteVectorBucket's not-empty ConflictException is emulator-worded and leaks the index count ===
AWS: Smithy models ConflictException on DeleteVectorBucket with errorKind client, httpError 409 and a required `message`. Deleting a vector bucket that still holds one or more vector indexes is refused with HTTP 409 ConflictException and message exactly "The specified vector bucket is not empty". Fixed text; the bucket name and the number of indexes are NOT interpolated. (Recorded behavior confirms the bucket is left fully intact and that deleting the index first then the bucket succeeds — those legs pass.)
Emulator: HTTP 409 ConflictException with "vector bucket <vectorBucketName> still holds <n> vector index(es); delete them before deleting the vector bucket". The bucket name is a request value and <n> is a count read out of emulator state; neither belongs in the template.
Why: teardown and lifecycle code is what hits this refusal — a cleanup routine that distinguishes "not empty, go delete children first" from "already gone" or "access denied" reads the sentence, because the 409/ConflictException code is shared with every other conflict on the operation. The emulator's sentence breaks that discrimination and additionally exposes an internal child count a client could come to depend on.
Fix: DeleteVectorBucket's conflict path — the ConflictException message it constructs (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/delete_vector_bucket.rs and the not-empty refusal it lifts from crate::state): emit the single fixed sentence, with no bucket name and no count.
Traces: s3vectors.delete-vector-bucket-with-index-conflict-rejected, s3vectors.delete-vector-bucket-with-indexes-rejected (both fail on the same sentence).

=== Cause 5 of 8: PutVectors' dimension-mismatch ValidationException uses a different sentence and drops the offending record's key ===
AWS: Smithy models ValidationException on PutVectors (errorKind client, httpError 400, required `message`, optional `fieldList` of path+message); the index's modeled `dimension` (range 1..4096) fixes the required vector length. A vector whose `data` length differs from the index dimension is refused with HTTP 400 ValidationException and top-level message "Invalid record for key '<vectorKey>': vector must have length <indexDimension>, but has length <actualLength>". Fixed text: "Invalid record for key '", "': vector must have length ", ", but has length ". Variable parts: the offending vector's `key` from the request, the index's configured dimension, and the submitted data length. The index NAME does not appear.
Emulator: HTTP 400 ValidationException with "`vectors[0].data` has <n> values, but vector index <indexName> is configured for <d> dimensions" — a different sentence that names a member path instead of the record key, substitutes the index name in, and drops the rejected record's `key` entirely.
Why: the key in AWS's message is how a client reports WHICH record of a batch of up to 500 was rejected back to its caller; with the key gone, batch-level error reporting and partial-retry logic cannot be exercised against the emulator at all.
Fix: PutVectors' per-vector validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/put_vectors.rs and the dimension check it calls in crate::state) — build the top-level message from the offending record's key, the index dimension and the submitted length.
Traces: s3vectors.put-vectors-dimension-mismatch-rejected (the ValidationException code, the 'mismatched vector never written' leg and the well-formed positive control all pass; only the message assertion fails).

=== Cause 6 of 8: PutVectorBucketPolicy's malformed-policy refusal leaks the JSON parser's own diagnostic ===
AWS: Smithy models ValidationException on PutVectorBucketPolicy (errorKind client, httpError 400, required `message`); the required `policy` member is the JSON that defines the bucket's resource policy. A document that is not a well-formed policy is refused with HTTP 400 ValidationException and message exactly "The provided policy is malformed or invalid" — one fixed sentence, with no variable part, that reveals nothing about where parsing failed.
Emulator: HTTP 400 ValidationException with "`policy` is not a valid policy document: it is not well-formed JSON (<parser detail with line and column>)" — a member-named prefix composed with the serde_json error text.
Why: the status and code are right, but the text is an internal parser diagnostic rather than the service's sentence, so a client that displays or asserts AWS's wording diverges; the leaked line/column detail is a shape AWS never emits for this error class, and it varies with the input, so nothing stable can be built on it.
Fix: the bucket-policy validator in crate::state (services/service-com-amazonaws-s3vectors-s3vectors/src/state.rs, `validate_bucket_policy`) and PutVectorBucketPolicy's handler — refuse with the single fixed sentence regardless of which grammar rule failed.
Traces: s3vectors.put-vector-bucket-policy-malformed-json-rejected.

=== Cause 7 of 8: the zero-norm-vector refusal for a cosine index does not name the zero-norm rule the way the service does ===
AWS: Smithy models ValidationException on PutVectors (400, required `message`) and models DistanceMetric as an enum including `cosine`; cosine distance is undefined for a vector of zero norm. Recorded behavior: PutVectors of an all-zeros vector into a cosine index is refused with HTTP 400 ValidationException and message "Invalid record for key '<vectorKey>': cosine distance does not support vectors with zero norm", while the SAME payload into a euclidean index is accepted — the euclidean-acceptance leg passes against the emulator, so only the refusal sentence diverges. Fixed text: "Invalid record for key '", "': cosine distance does not support vectors with zero norm"; the only variable part is the offending record's `key` from the request.
Emulator: HTTP 400 ValidationException with "`vectors[0].data` is a zero vector, which isn't allowed for the `cosine` distance metric" — a different sentence, keyed on a member path rather than the record key, so the rejected record cannot be identified in a batch.
Why: this refusal shares its code (ValidationException) with the dimension and data-type refusals on the same operation, so the sentence is the only thing that tells a client it submitted a degenerate vector rather than a mis-sized one — exactly the distinction an embedding pipeline needs in order to drop the record instead of reshaping it. As in Cause 5, dropping the record key also makes batch-level reporting untestable.
Fix: PutVectors' per-vector validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/put_vectors.rs and the zero-norm/cosine check in crate::state) — emit the service's sentence prefixed with the offending record's key.
Traces: s3vectors.put-vectors-zero-vector-rejected-for-cosine-only (the effect-absent leg via GetVectors/ListVectors and the euclidean positive control pass; only the message assertion fails).

=== Cause 8 of 8: ListVectors' segmentIndex-out-of-range refusal is emulator-worded ===
AWS: Smithy models ListVectorsInput `segmentCount` (integer, default 1, range 1..16) and `segmentIndex` (integer, default 0, range 0..15), and models ValidationException (400, required `message`) on ListVectors. segmentIndex == segmentCount is inside BOTH shape ranges, so the request leaves the SDK and the SERVICE refuses it: HTTP 400 ValidationException with message "Segment index is zero-indexed and must be smaller than segment count" — all fixed text that restates the rule and interpolates neither of the two submitted numbers.
Emulator: HTTP 400 ValidationException (correct code) with "`segmentIndex` (<i>) must be less than `segmentCount` (<n>)" — the emulator's own sentence, naming the wire member names in backticks and echoing both submitted values back.
Why: a parallel-listing worker pool derives its segment assignment from its own worker count, and this refusal is how a mis-derived assignment is reported. A client asserting or surfacing AWS's wording diverges, and the echoed values are a shape AWS does not use for this error.
Fix: ListVectors' input validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/list_vectors.rs and the segment cross-field check it calls in crate::state) — emit the service's fixed sentence with no submitted values. NOTE: the check carrying this cause is marked DRAFT/unblessed, so the expected sentence is the check's oracle rather than a re-recorded response; the ValidationException code and the fact that the service (not botocore) refuses are both confirmed by the model.
Traces: s3vectors.list-vectors-parallel-segments-partition-the-index (its partition property, per-segment pagination and maxResults legs all pass; only the out-of-range message assertion fails).

=== Cause 8 addendum / separate cause: TagResource and UntagResource conflict wording ===
This is counted inside Cause 8's bundle slot as a NINTH item only in prose; treat it as its own cause to close. AWS: Smithy models ConflictException on TagResource and UntagResource (errorKind client, httpError 409, required `message`); both are @idempotent and tag state on one resource is updated under optimistic concurrency control. A caller whose read-modify-write of the tag set was invalidated by an overlapping mutation is refused with HTTP 409 ConflictException and message exactly "The resource tags were modified by another request. Please retry the operation." — fixed text, no resource ARN or tag key interpolated.
Emulator: HTTP 409 ConflictException (correct) with "A conflicting conditional operation is currently in progress against this resource. Try again." on every refused racer.
Why: ConflictException is the signal to retry the tag read-modify-write, and the sentence is what a client logs or asserts to prove it retried for the right reason rather than on an unrelated 409 (the operation also returns ConflictException for other conditions). The emulator's sentence is S3's OperationAborted wording, not S3 Vectors' tag-conflict wording.
Fix: the tag state and the TagResource/UntagResource handlers for s3vectors (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/tag_resource.rs, src/ops/untag_resource.rs and the versioned tag map in crate::state) — emit the service's fixed sentence from the optimistic-lock failure path.
Traces: s3vectors.tag-resource-conflict-under-concurrent-updates (the ConflictException code, the final-tag-set arithmetic and the post-storm positive control pass; only the message assertion fails).
