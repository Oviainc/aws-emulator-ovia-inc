## Description
Three distinct, net-new behavioral causes in the neptune-graph service, all surviving the already-filed stub/owned clusters of this replay (the ExecuteQuery scaffold issue 20261023T175427Z-neptune-graph-executequery-stub.md and the owned refusal-path issue 20261023T175427Z-neptune-graph-7-refusal-path-fidelity-causes-wrong.md). Smithy model consulted: services/service-com-amazonaws-neptunegraph-amazonneptunegraph/smithy-model/com-amazonaws-neptunegraph-amazonneptunegraph.json.

=== Cause 1 of 3: the CANCEL task operations must word their not-found identifier clause as "task id", not "<resource> task id" ===
AWS: CancelImportTask and CancelExportTask refuse an unknown but well-formed taskIdentifier with ResourceNotFoundException (Smithy: CancelImportTask errors ResourceNotFoundException @httpError 404; taskIdentifier pattern ^t-[a-z0-9]{10}$, so a well-formed unknown id reaches resource lookup). Recorded behavior shows the identifier clause is NOT spelled the same way on the read and the cancel operation of a task: GetImportTask answers 'No import task found for customer [<account>] with import task id [<taskIdentifier>]' while CancelImportTask answers 'No import task found for customer [<account>] with task id [<taskIdentifier>]' — and symmetrically GetExportTask answers '... with export task id [...]' while CancelExportTask answers '... with task id [...]'. Fixed text per operation: 'No import task found for customer [' / 'No export task found for customer [' + '] with ' + ('import task id ['|'export task id ['|'task id [') + ']'. Variable parts: the account the lookup was resolved in (emulator account, from the request's credentials) and the taskIdentifier taken verbatim from the request.
Emulator: both operations reach ONE shared builder, so the cancel operations inherit the read operation's spelling. services/service-com-amazonaws-neptunegraph-amazonneptunegraph/src/ops/cancel_import_task.rs calls crate::state::import_task_not_found(&input.task_identifier), which calls resource_not_found_for_caller("import task", "id", ...) and formats "No {resource} found for customer [{acct}] with {resource} {identifier_kind} [{id}]" — i.e. CancelImportTask answers 'No import task found for customer [000000000000] with import task id [t-0000000000]' where AWS answers '... with task id [t-0000000000]'. The export pair has the identical structure through export_task_not_found. The code (ResourceNotFoundException) and status (404) are correct; only the message rule diverges.
Why: a client, log scraper or test that matches AWS's refusal text for a cancel of a vanished task does not recognise the refusal, and the per-operation wording difference AWS actually has is erased, so the four task operations can no longer be told apart from their messages. NOTE on provenance: the fixed issue 20261024T161935Z-neptune-graph-getimporttask-error-response.md correctly changed the READ wording to 'import task id' but applied it through the shared helper that CancelImportTask/CancelExportTask also reach, which is what over-spells the cancel clause; this is not a REOPEN (the call is still refused exactly as AWS refuses it, with the right code and status) but the fix has to be split per operation.
Fix: the not-found refusal wording in crate::state (the resource_not_found_for_caller / import_task_not_found / export_task_not_found builders) must let the cancel operations' handlers (ops/cancel_import_task.rs, ops/cancel_export_task.rs) render the bare 'task id' identifier clause while ops/get_import_task.rs and ops/get_export_task.rs keep the spelled-out 'import task id' / 'export task id' clause.
Traces: neptune-graph.import-export-task-nonexistent-not-found — GetImportTask's message now matches, then the check fails at the CancelImportTask assertion: expected message 'No import task found for customer [000000000000] with task id [t-0000000000]', got 'No import task found for customer [000000000000] with import task id [t-0000000000]'. (The check aborts there, so the GetExportTask/CancelExportTask assertions were not reached; the same shared builder makes CancelExportTask diverge identically and must be fixed with it.)

=== Cause 2 of 3: StartImportTask's pass-role AccessDeniedException names the request's access key id as an IAM user instead of the caller's principal ===
AWS: StartImportTask authorizes roleArn before any other validation and refuses a value that names no role the caller may pass with AccessDeniedException (403). Recorded behavior only — AccessDeniedException is not in StartImportTask's modeled error list (Smithy: ConflictException 409, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400). The message's fixed text is 'User: ' + <principal> + ' is not authorized to perform: null'; its ONE variable part is the IAM principal that signed the request — the same identity STS GetCallerIdentity reports for those credentials (Arn), which is the contract the check asserts against rather than any literal recorded ARN.
Emulator: the code and status are now correct, but the principal is fabricated from the SigV4 access key id: crate::state::caller_principal (src/state.rs, the 'Passing an IAM role' section) takes ::engine::extract_akid(headers), strips it to alphanumerics and renders ::engine::emulator_arn("iam", "", &format!("user/{akid}")), so the refusal reads 'User: arn:aws:iam::000000000000:user/EMULATORB0A2891F4D08 is not authorized to perform: null' — an ARN naming the access key id, not the caller. The emulator's own STS resolves the same access key id through the IAM/credential store (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/get_caller_identity.rs -> crate::state::resolve_request_caller), so the two components disagree about who the caller is for one set of credentials.
Why: a client (or an operator reading the log) cannot tell WHICH principal was denied, so the standard remediation of a pass-role denial — attach the missing permission to the named principal — is impossible; and for a request signed with an assumed-role session the message names an IAM user that does not exist, so the denial misreports the identity type as well.
Fix: the pass-role denial path (crate::state::caller_principal, reached by crate::state::pass_role_denial from ops/start_import_task.rs, ops/create_graph_using_import_task.rs and ops/start_export_task.rs) must resolve the request's credential to the caller's principal through the same identity resolution the emulator's STS GetCallerIdentity uses, rather than embedding the access key id as a user name.
Traces: neptune-graph.import-task-invalid-role-arn-rejected — StartImportTask(roleArn='not-an-arn') returns AccessDeniedException as required, then the message assertion fails: the message carried 'arn:aws:iam::000000000000:user/EMULATORB0A2891F4D08' where the caller identity reported by sts.GetCallerIdentity for the same credentials was a different ARN.

=== Cause 3 of 3: no query is ever in flight, so the ListQueries -> CancelQuery -> GetQuery lifecycle cannot be observed ===
AWS: a submitted openCypher query is a tracked, addressable record while it runs: ListQueries(graphIdentifier, state='RUNNING') reports it with its id and queryString (Smithy: ListQueries output queries: QuerySummaryList required, state QueryStateInput, hostPrefix '{graphIdentifier}.'), CancelQuery(queryId) ends it (Smithy: CancelQuery errors AccessDeniedException 403, ResourceNotFoundException 404, ValidationException 400), and GetQuery for the cancelled id is then refused — confirmed by replay — with ValidationException (400) whose message is 'Supplied queryId ' + <queryId> + ' is invalid' (fixed text around the queryId taken from the request), NOT ResourceNotFoundException. A long-running query stays RUNNING until it is cancelled.
Emulator: ListQueries(state='RUNNING') never reports the query the check submitted, so the whole lifecycle is unreachable: nothing admits a query record, because ExecuteQuery is still the scaffold stub (ops/execute_query.rs, HTTP 501 NotImplemented) and it is the only operation that would file one, and crate::state's query store (Query/live_queries_on/reap_terminated_queries) is therefore always empty for a graph. Two further divergences sit behind the same cause once a record exists: (a) crate::state::QUERY_RUN_SPAN is 750ms and every admitted query is auto-terminated and reaped at that instant, so a query the caller never cancelled stops being reported on its own and CancelQuery can never be the thing that ends it; (b) crate::state::query_not_found builds ResourceNotFoundException 'No query found on graph [<graphId>] with query id [<queryId>]' for an id GetQuery no longer tracks, where AWS answers ValidationException 400 'Supplied queryId <queryId> is invalid'.
Why: a client that submits a query and then manages it — lists in-flight work, cancels a runaway query, and polls the cancelled id to confirm it is gone — gets an empty listing, has no queryId to cancel, and (once there is one) a 404 where it must distinguish a 400 'invalid queryId'; query management on this service is unusable and a cancel can never be shown to have taken effect.
Fix: ExecuteQuery's handler (ops/execute_query.rs) must admit a query record into crate::state's query store so ListQueries reports it as RUNNING for as long as it runs; the query-record lifetime in crate::state must not self-terminate a query that nothing cancelled within the window a caller needs to list and cancel it; and GetQuery's unknown/cancelled-id path (ops/get_query.rs via crate::state::query_not_found) must answer the modeled ValidationException with the 'Supplied queryId ... is invalid' wording. The already-filed stub issue 20261023T175427Z-neptune-graph-executequery-stub.md covers only making ExecuteQuery answer at all, and cause 6 of 20261023T175427Z-neptune-graph-7-refusal-path-fidelity-causes-wrong.md covers only its three refusal paths — neither covers the query-record lifecycle this cause requires.
Traces: neptune-graph.neptune-graph-query-cancel-transitions-state — AssertionError: condition not met within 39.9s; last=None, polling ListQueries(graphIdentifier=<graph>, maxResults=10, state='RUNNING') every 0.5s for the submitted query; the check never reached its CancelQuery/GetQuery assertions.
