# CreateConnection refuses a well-formed remoteAccount.identifier whose text does not match the Environment's remoteIdentifierType, making the whole Connection lifecycle unreachable

> _Note: this issue was identified against the code base at commit `3a5777642c2144d422034a2df8d16fbd36d2448f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConnection

## Description
One cause (Cause 1 of 1), grounded in three failing behavioral checks that all die on the same CreateConnection call.

AWS: `CreateConnection$remoteAccount` targets the union `RemoteAccountIdentifier` (Smithy: com.amazonaws.interconnect#RemoteAccountIdentifier), whose ONLY member is `identifier` -> `RemoteOwnerAccount`, `@length(min:1,max:255)`, `@pattern(^[-a-zA-Z0-9_@\.]+$)`, documented verbatim as "A generic bit of identifying information. Can be used in place of any of the more specific types." `Environment$remoteIdentifierType` (enum `RemoteAccountIdentifierType`, values [account, email]) is documented as "The type of identifying information that should be supplied to the remoteAccount parameter of a CreateConnection call for this specific Environment" — it tells the caller WHICH kind of identity the partner will verify on its portal; the model states no format rule that CreateConnection enforces on the generic `identifier` member, and the union offers no type-specific variant to carry instead. Recorded behavior (the checks' inlined `_remote_account_param`, documented as empirically confirmed against real AWS): on an Environment whose `remoteIdentifierType` is `account`, CreateConnection with `remoteAccount={"identifier": "<any string matching the member's pattern>"}` is ACCEPTED with HTTP 200 and a connection in state `requested`; what real AWS refuses is the ABSENCE of `remoteAccount` on such an Environment (InterconnectValidationException, "Unable to process request: remoteAccount.identifier is required"). Verification of the identity itself happens later, at the partner portal, not in the create.

Emulator: `CreateConnection` rejects the accepted request with HTTP 400 `InterconnectValidationException` and the message `Unable to process request: remoteAccount does not carry the <declared-type> environment <environmentId> requires` (fixed text: "Unable to process request: remoteAccount does not carry the " / " environment " / " requires"; variable parts: the Environment's declared `remoteIdentifierType` and the requested `environmentId` — in the replay the seeded Azure environment of the addressed region). The rule lives in `remote_account_violation` and requires the supplied `identifier` text to pass an invented per-kind format test: exactly twelve ASCII digits when the Environment declares `account`, and a local@domain shape when it declares `email`. Any other identifier string — including every opaque partner-issued identity the member's pattern permits — is refused, so no Connection can be created at all against a seeded Environment that declares `account` unless the caller happens to send a 12-digit number.

Why: a client that supplies the identity its partner issued (and that AWS accepts) cannot create a Connection in the emulator. Because CreateConnection is the entry point for the resource, everything downstream becomes unreachable: UpdateConnection on a live connection, the delete -> `deleted` terminal-state progression, the state refusal on a deleted connection, ListAttachPoints echo of the created attach point, and the not-found semantics of UpdateConnection/GetConnection are all untestable and unusable. Code written against AWS fails on a parameter AWS validates only for presence.

Note: this over-strict rule appears to be the remedy direction of the still-open issue 20261024T124529Z-interconnect-createconnection-parameter-ignored.md ("remoteAccount is stored write-only: never checked against the Environment's remoteIdentifierType"). That issue is about the member being unobservable; it does not license a create-time FORMAT check on the generic `identifier`, which AWS does not perform. Making `remoteAccount` matter must stop at refusing its ABSENCE on an Environment that declares a `remoteIdentifierType` (AWS's recorded message "Unable to process request: remoteAccount.identifier is required") and at including it in the `clientToken` replay comparison.

Fix: the create-time validation for this operation — `remote_account_violation` in the service's state module and its call site in the CreateConnection handler's store judgement. The kind-specific text tests (`is_account_identifier` / `is_email_identifier` applied to the supplied identifier) must not refuse a `RemoteAccountIdentifier::Identifier` that satisfies the member's modeled length and pattern; only absence on an Environment that declares a `remoteIdentifierType` is a refusal, and it must be worded as AWS words it.

Traces: interconnect.list-attach-points-matches-created-connection-attach-point, interconnect.update-connection-after-deletion-rejected, interconnect.update-connection-nonexistent-id-rejected — all three raise InterconnectValidationException on the CreateConnection prerequisite, before reaching their own assertions.

## Evidence
Expected (real AWS, per the checks' empirically-confirmed prerequisite helper and the Smithy model): CreateConnection(bandwidth=<an available bandwidth of the Environment>, attachPoint=<an attach point listed for the Environment>, environmentId=<an Environment whose state != 'unavailable' and whose remoteIdentifierType is 'account'>, remoteAccount={'identifier': 'sim2real-behav-remote-account'}) -> HTTP 200, {"connection": {... "state": "requested" ...}}.

Actual (emulator replay, all three checks): HTTP 400, error code InterconnectValidationException, message "Unable to process request: remoteAccount does not carry the account environment env-csp-azure-us-east-1 requires" (botocore: `An error occurred (InterconnectValidationException) when calling the CreateConnection operation: Unable to process request: remoteAccount does not carry the account environment env-csp-azure-us-east-1 requires`). The environment id and the declared type in that message are values taken from the request and the seeded catalog; the refusal itself is the divergence.

Source of the rule: services/service-com-amazonaws-interconnect-interconnect/src/state.rs lines 492-564 (`remote_account_violation`, `is_account_identifier` requiring exactly 12 ASCII digits, `is_email_identifier` requiring local@domain) and services/service-com-amazonaws-interconnect-interconnect/src/ops/create_connection.rs lines 252-263 (the call site inside `judge_against_store`, which is run twice per create).

Model evidence (smithy_query on services/service-com-amazonaws-interconnect-interconnect/smithy-model/com-amazonaws-interconnect-interconnect.json): RemoteAccountIdentifier = union { identifier: RemoteOwnerAccount, length 1..255, pattern ^[-a-zA-Z0-9_@\.]+$, doc "A generic bit of identifying information. Can be used in place of any of the more specific types." }; Environment$remoteIdentifierType = RemoteAccountIdentifierType enum [account, email]; CreateConnection$remoteAccount is NOT @required. 'sim2real-behav-remote-account' satisfies the member's length and pattern, so wire-level validation passes and the refusal is purely the emulator's extra semantic rule.

## Steps to Reproduce
1. Boot the emulator and call ListEnvironments; pick an Environment whose `state` is not "unavailable", that has at least one entry in `bandwidths.available`, and whose `remoteIdentifierType` is "account" (the seeded Azure/GoogleCloud environments).
2. Obtain an attach point for it: ListAttachPoints(environmentId=<that id>) and take the first entry, or create a Direct Connect gateway and poll until it lists.
3. Call CreateConnection(bandwidth=<bandwidths.available[0]>, attachPoint=<that attach point as directConnectGateway or arn>, environmentId=<that id>, remoteAccount={"identifier": "sim2real-behav-remote-account"}).
4. Observe HTTP 400 InterconnectValidationException "Unable to process request: remoteAccount does not carry the account environment <environmentId> requires", where AWS returns HTTP 200 with a `requested` connection.
5. Repeat step 3 with remoteAccount={"identifier": "000000000000"} -> accepted, confirming the refusal is driven solely by the identifier's text shape; and with remoteAccount omitted -> also refused (that refusal is correct in kind but is worded "...requires remoteAccount to carry the account of the remote side" instead of AWS's "Unable to process request: remoteAccount.identifier is required").
6. Because step 3 is the prerequisite of every connection-lifecycle check, re-running interconnect.list-attach-points-matches-created-connection-attach-point, interconnect.update-connection-after-deletion-rejected and interconnect.update-connection-nonexistent-id-rejected reproduces the same error at the create call.
