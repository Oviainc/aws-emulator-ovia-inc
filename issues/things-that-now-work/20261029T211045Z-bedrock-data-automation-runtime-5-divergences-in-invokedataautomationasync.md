# bedrock-data-automation-runtime: 5 divergences in InvokeDataAutomationAsync / GetDataAutomationStatus / TagResource (clientToken dedup, job terminal status, cross-account profile ARN, EventBridge completion event, quota message)

> _Note: this issue was identified against the code base at commit `95ee1f215215607c18ab877072afcef7ad3742b1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeDataAutomationAsync

## Description
Five distinct root causes in the bedrock-data-automation-runtime emulator, all surfaced by the behavioral suite. They share the service and are bundled here; each must be closed before submitting. The service's bootstrap issue (20261021T211817Z-bootstrap-service-com-amazonaws-bedrockdataautomationruntime-amazonbedrockkeystoneruntimeservice.md) is already resolved, and these are fidelity defects on top of it, not bootstrap gaps. The sixth suite failure (invoke-sync-returns-semantic-modality-for-image) is ALREADY FILED against the unimplemented InvokeDataAutomation stub and is deliberately NOT part of this issue.

=== Cause 1 of 5: InvokeDataAutomationAsync deduplicates on a repeated clientToken ===
AWS: Smithy models InvokeDataAutomationAsync with @idempotent and clientToken as @idempotencyToken (IdempotencyToken, @length 1..256, @pattern ^[a-zA-Z0-9](-*[a-zA-Z0-9]){1,256}$), but recorded behavior only: against real AWS, two back-to-back InvokeDataAutomationAsync calls carrying the IDENTICAL clientToken and otherwise identical parameters both succeed and each mints an independent job with a DISTINCT invocationArn. For this operation the token is accepted for request validation and is not an application-level dedup key; both returned ARNs resolve independently via GetDataAutomationStatus to two separately tracked jobs.
Emulator: the second call is folded into the first and replays the first job's ARN. services/service-com-amazonaws-bedrockdataautomationruntime-amazonbedrockkeystoneruntimeservice/src/ops/invoke_data_automation_async.rs deliberately implements token replay (store.replay_for_client_token(token) returning the previously minted ARN), so both calls returned the same invocationArn and only one job record exists.
Why: a client that retries a submission under a stable token (an SDK retry, a workflow step re-run, a token derived from an input key) loses a job silently. On AWS the retry creates a second job and a second set of outputs; on the emulator the caller gets a duplicate ARN, polls a job it did not submit, and the second unit of work is never scheduled. Conversely a client writing a dedup-sensitive test against the emulator will believe AWS dedups when it does not.
Fix: InvokeDataAutomationAsync's handler and the clientToken index in the service state — stop consulting the token as a replay key on this operation (retain the token on the record if it is wanted for diagnostics, but always mint a fresh invocation and a fresh ARN).
Traces: bedrock-data-automation-runtime.invoke-async-client-token-idempotent-retry-returns-same-arn.

=== Cause 2 of 5: job lifecycle always ends in Success; no ClientError/InvalidImage terminal state ===
AWS: recorded behavior only for the content rule; the model supplies the vocabulary. Smithy: GetDataAutomationStatusResponse.status targets AutomationJobStatus, an enum whose values are Created | InProgress | Success | ServiceError | ClientError, alongside errorType (String), errorMessage (String), jobSubmissionTime and jobCompletionTime (both @timestampFormat date-time). Against real AWS, a job whose input asset cannot be processed as an image reaches the TERMINAL status ClientError with errorType "InvalidImage" and errorMessage "Image format is invalid or not supported." — that message is entirely fixed text for this error class, with no variable part — and jobCompletionTime set.
Emulator: every admitted job advances unconditionally to Success. The recorded poll ended with status 'Success' instead of 'ClientError' (assertion: "expected the one-pixel PNG job to end in ClientError, got 'Success'"), so errorType and errorMessage are never populated and the ClientError/ServiceError branches of the enum are unreachable. GetDataAutomationStatus itself just projects the record (get_data_automation_status.rs calls invocation.advance_to(now) and serializes the result), so the defect is in the lifecycle advance in the service state, which has no notion of whether the referenced input asset is processable.
Why: the whole point of polling GetDataAutomationStatus is to distinguish success from a client-side input failure. A client built against the emulator never exercises its own failure path: it reads Success, then tries to fetch outputs that do not exist, and its error-classification code (branching on status == ClientError, on errorType, or on errorMessage) is dead code that fails on first contact with AWS.
Fix: the job-lifecycle advance in this service's state (the status machine that advance_to drives) plus the submission path that records the input asset — classify the referenced input and drive unprocessable input to the terminal ClientError status with errorType "InvalidImage", the fixed errorMessage above, and jobCompletionTime set.
Traces: bedrock-data-automation-runtime.get-status-reports-created-or-in-progress-immediately-after-submission (the non-terminal prefix of this check passed — jobSubmissionTime present, jobCompletionTime absent — only the terminal classification diverged).

=== Cause 3 of 5: cross-account dataAutomationProfileArn is accepted instead of refused with AccessDeniedException ===
AWS: Smithy models AccessDeniedException on InvokeDataAutomationAsync (errorKind client, httpError 403, single member message: NonBlankString); dataAutomationProfileArn is required, @length 1..128, @pattern ^arn:aws(|-cn|-iso|-iso-[a-z]|-us-gov):bedrock:[a-zA-Z0-9-]*:(aws|[0-9]{12}):data-automation-profile/[a-zA-Z0-9-_.]+$ — so an ARN naming a FOREIGN twelve-digit account is pattern-valid and must be rejected on authorization, not on shape. Recorded behavior: a profile ARN scoped to an account the caller has no access to is refused with HTTP 403, error code AccessDeniedException and message "User: <account-id> is not authorized to access this resource", and NO invocation is created. In that message the fixed text is "User: " and " is not authorized to access this resource"; the only variable part is the CALLER's own account id, taken from the request's credentials (not the foreign account in the ARN).
Emulator: the call SUCCEEDS with HTTP 200 and mints an invocation. Recorded response: {'invocationArn': 'arn:aws:bedrock:<region>:<account>:data-automation-invocation/<id>'} with HTTPStatusCode 200 (the concrete arn/id/account in the recording are per-run values, not part of the requirement). The handler's own module docs state caller-identity authorization is deliberately not emulated and that the modelled AccessDeniedException is unreachable from it, and that dataAutomationProfileArn "stays recorded rather than resolved" with the @pattern/@length walk as the whole check — so no account comparison happens at all.
Why: this is an overly-permissive accept. A caller that in AWS would be denied gets a live job on the emulator, so a client's 403 handling (and any test asserting the denial) never runs, and misconfigured cross-account wiring passes locally and fails in production. The positive control in the same check — the caller's OWN profile ARN succeeding and resolving via GetDataAutomationStatus — must keep working.
Fix: InvokeDataAutomationAsync's validation/authorization step (and the equivalent on the sync InvokeDataAutomation once that stub lands) — compare the account component of dataAutomationProfileArn against the request's own account and refuse a mismatch with the modelled AccessDeniedException (403) carrying the message above, before anything is minted or persisted.
Traces: bedrock-data-automation-runtime.invoke-async-cross-account-profile-arn-access-denied-rejected.

=== Cause 4 of 5: no EventBridge event emitted on job completion when eventBridgeEnabled is true ===
AWS: recorded behavior only (the runtime model carries notificationConfiguration.eventBridgeConfiguration.eventBridgeEnabled but says nothing about delivery). Against real AWS, a job submitted with notificationConfiguration={"eventBridgeConfiguration": {"eventBridgeEnabled": true}} causes Bedrock to publish an event to the default EventBridge bus on completion, with source "aws.bedrock" and detail-type one of "Bedrock Data Automation Job Created" / "Bedrock Data Automation Job Succeeded" / "Bedrock Data Automation Job Failed With Client Error" / "Bedrock Data Automation Job Failed With Service Error", whose detail carries job_id = the id segment of the job's invocationArn. A rule matching that pattern with an SQS target observes the event. AWS documents this delivery as best-effort, hence the check's bounded poll.
Emulator: no event is ever published. The check created the queue, rule, target and queue policy successfully, submitted the job with eventBridgeEnabled true, then polled for the completion event and the check ran out of time ("Check timed out after 60.0s") with nothing delivered. The submission handler stores notification_configuration on the invocation record and nothing else consumes it, so eventBridgeEnabled is accepted and silently ignored.
Why: eventing is how callers avoid polling. A client whose pipeline is driven by the completion event (EventBridge rule -> SQS/Lambda) simply never advances against the emulator, and the accept-then-ignore makes it look configured. Accepting the flag while emitting nothing is worse than refusing it.
Fix: the job-lifecycle advance in this service's state (where a job reaches a terminal status) — when the record's notificationConfiguration.eventBridgeConfiguration.eventBridgeEnabled is true, publish to the emulated EventBridge default bus an event with source "aws.bedrock", the matching detail-type for the terminal status, and detail.job_id set to the invocationArn's id segment.
Traces: bedrock-data-automation-runtime.invoke-async-completion-event-delivered-via-eventbridge.

=== Cause 5 of 5: TagResource quota rejection carries the wrong error message ===
AWS: Smithy models ServiceQuotaExceededException on TagResource (errorKind client, httpError 402, member message: NonBlankString); TagResource.tags is required with @length 0..200, and the quota is CUMULATIVE per resource. Recorded behavior: exceeding the per-resource tag quota is refused with error code ServiceQuotaExceededException and message "The number of the provided tags is beyond the limit, or the number of total tags you are trying to attach to the specified resource exceeds the limit." That message is entirely FIXED text for this error class — it names no resource, no count and no limit, so there is no variable part to fill.
Emulator: the error code is correct, but the message is "Cannot have more than 200 tags on a data automation invocation" — different fixed wording, and it leaks a specific limit and resource kind AWS does not mention. Assertion: expected 'The number of the provided tags is beyond the limit, or the number of total tags you are trying to attach to the specified resource exceeds the limit.', got 'Cannot have more than 200 tags on a data automation invocation'. The rest of the check passed: the 50-tag positive control succeeded, the 210-tag cumulative total was refused with the right code, and none of the overflow tags landed.
Why: a client that matches on or surfaces the error message (log assertions, user-facing error mapping, retry classification keyed on message text) behaves differently against the emulator than against AWS. A message that differs from AWS's wording is itself the defect.
Fix: the tag-quota refusal message in this service's state (the message constructor the TagResource handler passes into ServiceQuotaExceededException) — replace it with AWS's fixed text verbatim.
Traces: bedrock-data-automation-runtime.tag-resource-exceeds-two-hundred-tag-limit-rejected.

## Steps to Reproduce
Common setup for every cause (as the checks do it): create a data-automation project via bedrock-data-automation CreateDataAutomationProject (projectStage LIVE, standardOutputConfiguration {}); create an S3 bucket in the request region and PutObject a one-pixel PNG at input/asset.png; build the profile ARN as arn:aws:bedrock:<region>:<caller-account>:data-automation-profile/<region-group>.data-automation-v1 (us.* for us-east-1/us-west-2/us-east-2, na.* for ca-central-1, eu.* for the eu regions, apac.* for the ap regions, us-gov.* for us-gov-west-1).

Cause 1: call InvokeDataAutomationAsync twice back-to-back with identical inputConfiguration/outputConfiguration/dataAutomationProfileArn/dataAutomationConfiguration AND the identical clientToken. Compare the two invocationArns — they must differ, and GetDataAutomationStatus must resolve each independently. Emulator returns one ARN twice.

Cause 2: call InvokeDataAutomationAsync for the one-pixel PNG input, then poll GetDataAutomationStatus until status leaves {Created, InProgress}. Submit InvokeDataAutomationAsync with notificationConfiguration={"eventBridgeConfiguration":{"eventBridgeEnabled":true}}. Poll the queue for an event whose detail.job_id equals the invocationArn's id segment. Emulator delivers nothing.

Cause 5: submit a job, TagResource the returned invocationArn with 50 tags (succeeds; ListTagsForResource returns 50), then TagResource the same ARN with 160 more tags.
