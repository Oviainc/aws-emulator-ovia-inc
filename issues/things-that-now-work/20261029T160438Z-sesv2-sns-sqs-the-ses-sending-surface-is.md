# sesv2__sns__sqs: the SES sending surface is still unreachable — the account's DNS-baseline public hosted zone is not discoverable through route53 ListHostedZones/ListTagsForResource, so no verified sending domain can be resolved (blocks 5 checks)

> _Note: this issue was identified against the code base at commit `e4cbe047d5984815ac113e95db79725169e307b1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListHostedZones

## Description
One root cause, grounded in five failing behavioral checks that all abort in their very first statement.

NOTE ON PRIOR WORK: the RESOLVED issue 20261029T065537Z-sesv2-the-whole-ses-sending-surface-is-unreachable.md filed this same cause against exactly these five check ids, and it is now in the resolved folder — but all five still fail identically on this replay, so the cause is not closed. This is not a refusal (both route53 reads answer HTTP 200 and no error code is returned), it is a divergence in WHAT those reads enumerate/return, so it is re-filed here rather than opened as a REOPENS of a refused call. The related open issues 20261029T085623Z-sesv2-two-causes-the-dns-baseline-hosted-zone.md (same route53 cause, but carrying the two plain `sesv2.*` check ids), 20261029T093731Z-acm-dns-validated-certificate-issuance-is-unreachable-the.md, 20261029T133540Z-s3-ses-sesv2-ses-inbound-mail-receiving-is-unreachable-the-account.md and 20261029T143522Z-ses-the-account-s-dns-baseline-public-hosted.md describe the same discoverability defect for OTHER check ids; none of them carries the five replay keys below, so none covers this failure.

Cause 1 of 1: the account's tagged PUBLIC hosted zone — the DNS baseline from which every SESv2 sending check resolves its verified sending domain — cannot be found through route53's own listing and tagging reads, so every SESv2 send scenario aborts before it sends anything.

AWS: Smithy (com.amazonaws.route53): ListHostedZones — GET /2013-04-01/hostedzone, 200, input {Marker (httpQuery marker, @length 0..64), MaxItems (httpQuery maxitems), DelegationSetId, HostedZoneType}, output ListHostedZonesResponse{HostedZones (required, list), Marker (required), IsTruncated (required, default false), NextMarker, MaxItems (required)}, paginated inputToken=Marker / outputToken=NextMarker / items=HostedZones; modeled refusals InvalidInput(400), NoSuchDelegationSet(400), DelegationSetNotReusable(400). ListTagsForResource — GET /2013-04-01/tags/{ResourceType}/{ResourceId}, 200, input {ResourceType (httpLabel, required, enum), ResourceId (httpLabel, required, @length 0..64)}, output {ResourceTagSet (required)}; modeled refusals InvalidInput(400), NoSuchHostedZone(404), NoSuchHealthCheck(404), PriorRequestNotComplete(400), ThrottlingException(400). Smithy (com.amazonaws.sesv2): GetEmailIdentity GET /v2/email/identities/{EmailIdentity} -> {IdentityType, VerifiedForSendingStatus, DkimAttributes, ...}. Beyond those signatures this is recorded behavior only: the account holds a hosted zone with Config.PrivateZone false that ListHostedZones enumerates; ListTagsForResource(ResourceType='hostedzone', ResourceId=<the zone id after the last '/'>) returns that zone's written tags in ResourceTagSet.Tags (here the baseline marker tag the harness put on it); and sesv2 GetEmailIdentity on the zone apex (trailing dot stripped) is 200 with VerifiedForSendingStatus true. Both route53 calls are 200s — no refusal appears anywhere in the recording. The requirement is general and carries no account values: a hosted zone that was created and tagged in the account is enumerated by ListHostedZones (with the correct PrivateZone flag, across the Marker/NextMarker pagination) and reports, through ListTagsForResource, the tags that were put on it. The specific zone id, domain name and tag value are per-environment values, not part of the contract.

Emulator: the pagination completes normally (200, no error code, no refusal) and not one enumerated public hosted zone reports the baseline tag, so the shared lookup helper raises before any SES call is made. Hypothesis: either ListHostedZones enumerates no (or not this) public hosted zone for the account, or ListTagsForResource('hostedzone', <id>) projects a ResourceTagSet that omits the tags that were written — the replay cannot distinguish the two because neither call is refused. All five checks die at their first statement with the identical `AssertionError: no public hosted zone carries the DNS baseline tag, so the account has no verified domain to send from`.

Why: a client cannot discover, enumerate or tag-select its own DNS zones — tag-driven tooling (`aws route53 list-hosted-zones` + `list-tags-for-resource`, Terraform/CDK data sources, inventory and compliance scans) sees an account with no zones at all. Downstream, nothing that presupposes a verified sending domain is reachable: account-level suppression after a hard bounce (SendEmail still accepted, bounce subType OnAccountSuppressionList and the suppression-list diagnostic), an event destination with Enabled=false publishing nothing, SendBulkEmail per-entry ReplacementHeaders overriding the template default, raw-MIME custom-header preservation in the published Send event, and the asynchronous Rendering Failure event for a templated send with a missing variable are all masked by this one read.

Fix: route53's hosted-zone enumeration and hostedzone tag reads in the route53 service — the ListHostedZones handler/state that enumerates the account's zones (its Marker/NextMarker pagination and the PrivateZone flag it reports) and the hostedzone tag store that ListTagsForResource projects, so a zone created and tagged in the account is both enumerated and reports its tags. Then the sesv2 GetEmailIdentity state for that zone's apex (VerifiedForSendingStatus) must agree.

Service attribution: these check ids carry the compound leading token 'sesv2__sns__sqs' (SERVICES = sesv2, sns, sqs) and the behavior under test is SESv2's; the failing reads belong to route53, which the check id does not name, so the issue is filed under the check id's own leading token and the route53 operations are named here and in the fix. sesv2, sns, sqs and route53 are all bootstrapped.
