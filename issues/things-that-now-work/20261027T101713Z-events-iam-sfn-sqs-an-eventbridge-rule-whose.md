# events__iam__sfn__sqs: an EventBridge rule whose Step Functions target role lacks states:StartExecution produces no delivery, no DLQ dead-letter and no FailedInvocations datapoint, so the check hangs to the 60 s cap

> _Note: this issue was identified against the code base at commit `415bc37b6ebe55c6c7e638f2212d4379947a3e7c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents

## Description
Cause 1 of 1: EventBridge target delivery to a Step Functions state machine neither starts an execution nor dead-letters the event when the target role is unauthorized, and publishes no per-rule AWS/Events invocation metrics.

AWS: a rule target is authorized at DELIVERY time, not at PutTargets time (Smithy: eventbridge#Target.RoleArn — "The ARN of the IAM role to be used for this target when the rule is triggered"; PutTargets accepts the target and returns FailedEntryCount=0). When a matching event is delivered and the target role is trusted by events.amazonaws.com but holds no states:StartExecution grant on the target state machine, EventBridge performs the invocation, is refused by Step Functions, and — because the target carries DeadLetterConfig.Arn with RetryPolicy.MaximumRetryAttempts=0 (Smithy: eventbridge#DeadLetterConfig.Arn, "The ARN of the SQS queue specified as the target for the dead-letter queue", documented at eventbridge/latest/userguide/eb-rule-event-delivery.html#eb-rule-dlq) — sends exactly one copy of the ORIGINAL PutEvents envelope to that SQS queue, carrying the message attributes RULE_ARN, TARGET_ARN, ERROR_CODE and ERROR_MESSAGE. For this failure class ERROR_CODE is the fixed string NO_PERMISSIONS and ERROR_MESSAGE is the relayed authorization refusal, whose text names the refused action (states:StartExecution) and the assumed-role session of the target role (assumed-role/<role-name>/<session>); the role name is taken from the request's target RoleArn and the session name is minted per call. TARGET_ARN is the state machine ARN from the target, and the body is byte-for-byte the envelope PutEvents minted (same id, same detail). The denied state machine starts NOTHING. In the same delivery round a sibling rule on the same bus whose role DOES grant states:StartExecution starts exactly one execution whose input is that envelope. Per-rule metrics: AWS/Events FailedInvocations under dimensions {EventBusName, RuleName} counts exactly one per refused delivery for the denied rule only, and Invocations counts the healthy rule's successful deliveries; neither is attributed to the sibling. Granting states:StartExecution afterwards makes the identical wiring deliver, and the already dead-lettered events are NOT replayed. These delivery/DLQ/metric semantics are AWS-documented behavior, not modeled in Smithy — recorded behavior only for the attribute names and the NO_PERMISSIONS code.

Emulator: nothing observable is produced. The replay output for this check is only `Check timed out after 60.0s`: the check sits in its bounded wait for "every rule resolved event <nonce> (execution started or dead-lettered)" until the suite's per-check cap, i.e. within the observation window the denied rule's event never reached the DLQ and the healthy rule's state machine never showed an execution carrying the fired nonce. No dead-letter message (and therefore no ERROR_CODE/ERROR_MESSAGE/TARGET_ARN attributes), no execution and no AWS/Events datapoint were seen. Hypothesis: this is the same EventBridge-target-delivery silence already open as 20261025T002357Z-events-eventbridge-target-delivery-never-completes-for-sns-step.md and 20261024T190039Z-events-lambda-stepfunctions-eventbridge-delivered-step-functions-executions-never-progress-the.md, plus the missing DLQ path noted in 20261022T194351Z-events-firehose-s3-...; none of those open issues carries this check's replay key, and none covers the IAM-refusal leg (NO_PERMISSIONS dead-letter + per-rule FailedInvocations attribution) this check grades.

Why: a client that wires a rule to a Step Functions target and relies on EventBridge for at-least-once delivery sees no execution at all, so every event-driven workflow silently stops at the bus. Worse for the negative path: an operator who deliberately tests a misconfigured target role gets no dead-letter and no FailedInvocations datapoint, so a permanently refused delivery is indistinguishable from a delivered one — the event is lost with no signal, and alarms built on AWS/Events FailedInvocations never fire.

Fix: the EventBridge rule-delivery path (the dispatcher that matches an event and invokes each target) in the eventbridge service: it must assume/evaluate the target RoleArn against the target resource, invoke states:StartExecution for stateMachine target ARNs, and on a permanent refusal honour RetryPolicy and emit the DLQ copy with the RULE_ARN/TARGET_ARN/ERROR_CODE/ERROR_MESSAGE attributes; and the AWS/Events metric emission for Invocations/FailedInvocations keyed by {EventBusName, RuleName}.

Traces: events__iam__sfn__sqs.xsvc-iam-3-role-without-start-execution-denied-dead-letters-and-counts-failed-invocations (verdict mismatch, `Check timed out after 60.0s`). Note for the fixer: this check's own waits (role propagation sleep, delivery poll, then the AWS/Events metric poll) exceed the suite's 60 s per-check cap, so the cap bounds how much of the divergence the replay could observe; confirm the fix by running the check without the cap.

## Evidence
Expected (AWS): PutEvents envelope matched by two rules on a custom bus; the rule whose target role lacks states:StartExecution starts no execution and one copy of the envelope lands on the target's DeadLetterConfig SQS queue with MessageAttributes RULE_ARN=<denied rule arn>, TARGET_ARN=<denied state machine arn>, ERROR_CODE="NO_PERMISSIONS", ERROR_MESSAGE naming states:StartExecution and assumed-role/<denied-role-name>/<session>; the sibling rule starts exactly one execution with that envelope as input; AWS/Events FailedInvocations{EventBusName,RuleName=<denied rule>} == 1 per round and FailedInvocations for the sibling == 0; after granting states:StartExecution the same rule starts an execution for post-repair events only.
Actual (emulator): no DLQ message and no execution for the fired nonce within the observation window — the check never leaves its "execution started or dead-lettered" wait and the suite reports `Check timed out after 60.0s`. No AWS/Events datapoint observed either.

## Steps to Reproduce
1. iam.CreateRole x3: two roles trusted by events.amazonaws.com (one granted states:StartExecution on state machine A, one granted only states:DescribeStateMachine on state machine B) and one states.amazonaws.com execution role.
2. sfn.CreateStateMachine A and B with a single Pass state.
3. events.CreateEventBus; sqs.CreateQueue as DLQ and set a policy allowing events.amazonaws.com sqs:SendMessage.
4. events.PutRule (same pattern) + events.PutTargets for both rules, each target carrying Arn=<state machine>, RoleArn=<its role>, RetryPolicy{MaximumRetryAttempts:0,MaximumEventAgeInSeconds:60} and DeadLetterConfig{Arn:<dlq>}; assert FailedEntryCount==0.
5. events.PutEvents one entry matching both rules.
6. Poll sqs.ReceiveMessage on the DLQ (MessageAttributeNames=["All"]) and sfn.ListExecutions/DescribeExecution on both state machines: expect one NO_PERMISSIONS dead-letter for the denied rule and one execution of A. Observed: neither appears.
7. cloudwatch.GetMetricStatistics Namespace=AWS/Events MetricName=FailedInvocations Dimensions={EventBusName,RuleName=<denied rule>}: expect Sum==1; observed no datapoints.
