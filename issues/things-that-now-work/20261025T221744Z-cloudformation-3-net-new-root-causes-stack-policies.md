# cloudformation: 3 net-new root causes — stack policies are stored but never enforced on UpdateStack (Update:*/Update:Modify/StackPolicyDuringUpdateBody), AWS::SNS::Topic properties cannot be updated in place, and AWS::LanguageExtensions Fn::Length over a Ref'd CommaDelimitedList fails the stack

## Operation
UpdateStack

## Description
This issue bundles 3 net-new behavioral root causes in the CloudFormation update/template engine. None of the five failing checks below is marked ALREADY FILED or OWNED by an open issue, so none of their replay keys is carried anywhere else.

Related-but-not-covering open issues, named here so a fixer can see the overlap: 20261025T210446Z-cloudformation-2-net-new-behavioral-root-causes-fn.md carries ONE stack-policy replay key (cloudformation__sqs.cfn-stack-policy-protected-resource-replacement-rejected, Deny Update:Replace) and one Fn::ForEach-in-Outputs key — it does not carry any of the keys below, and Cause 1 here extends the same missing evaluation to Update:*, Update:Modify, the per-update StackPolicyDuringUpdateBody override and the stack-event/rollback evidence; Cause 3 is a DIFFERENT intrinsic (Fn::Length) in a different code path from Fn::ForEach. 20261023T135552Z-cloudtrail-cloudformation-cloudformation-cannot-update-aws-sqs-queue-properties-in.md is FIXED and was scoped to AWS::SQS::Queue (in-place SQS updates do now succeed — the positive control in cloudformation.stack-policy-roundtrip-and-enforcement updates two queues' VisibilityTimeout to 45 and reaches UPDATE_COMPLETE); Cause 2 is the same defect still present for AWS::SNS::Topic.

Cause 1 of 3: a stack policy is stored and round-trips, but no UpdateStack path evaluates it — every Deny is ignored, the update completes, and no rollback or policy event is produced.
AWS: SetStackPolicy associates a policy document with a live stack (Smithy: SetStackPolicy input StackName required, StackPolicyBody @length 1..16384, StackPolicyURL @length 1..5120, output Unit, no modeled errors; GetStackPolicy returns StackPolicyBody). On a subsequent UpdateStack (Smithy: UpdateStack output {StackId, OperationId}; modeled errors only InsufficientCapabilitiesException and TokenAlreadyExistsException, both httpError 400 — so the verdict is asynchronous, never a synchronous refusal), CloudFormation evaluates the policy against every planned resource action. A statement {"Effect":"Deny","Action":"Update:*"|"Update:Modify","Principal":"*","Resource":"LogicalResourceId/<id>"} makes that resource's update FAIL: DescribeStacks settles at StackStatus UPDATE_ROLLBACK_COMPLETE, DescribeStackEvents carries an UPDATE_FAILED event for that logical id whose ResourceStatusReason names the stack policy and the denied action — AWS's wording for this class is "Action denied by stack policy: Statement [#<n>] does not allow [<Update:Action>] for resource [LogicalResourceId/<LogicalId>];", where the fixed text is "Action denied by stack policy: Statement [#", "] does not allow [", "] for resource [", "];" and the variable parts are the matching statement's index, the denied action and the protected logical id, all taken from the request's policy and template. The already-applied siblings are reverted, the protected resource keeps its PhysicalResourceId and property values, and the byte-identical update succeeds (UPDATE_COMPLETE) only once the Deny is lifted. UpdateStack's StackPolicyDuringUpdateBody (Smithy: @length 1..16384) is a TEMPORARY override applying to exactly that one update: GetStackPolicy afterwards still returns the stored Deny document, and the very next update with no override is denied again.
Emulator: the policy body is stored (GetStackPolicy round-trips the exact document) and nothing reads it on the update path, so each denied update is executed and reported StackStatus 'UPDATE_COMPLETE' where UPDATE_ROLLBACK_COMPLETE is owed, with no UPDATE_FAILED event and no policy reason anywhere in the event stream. Observed in three shapes: (a) Deny Update:* on one of two SQS queues — expected UPDATE_ROLLBACK_COMPLETE, got UPDATE_COMPLETE and both queues moved to the new VisibilityTimeout; (b) Deny Update:* against a QueueName (create-only) change, i.e. a replacement — expected UPDATE_ROLLBACK_COMPLETE, got UPDATE_COMPLETE; (c) Deny Update:Modify on an AWS::SSM::Parameter — the update completed and the parameter took the new value, and because the Deny is never in effect the StackPolicyDuringUpdateBody override beats cannot be distinguished either (the check reports evidence='Resource creation Initiated', i.e. an ordinary event, not a policy denial).
Why: a stack policy is a protection mechanism. A client that guards a stateful resource (queue, table, parameter, bucket) believes it cannot be modified or replaced by an update; the emulator performs the modification/replacement silently, leaves the stack UPDATE_COMPLETE instead of rolling back, and produces no auditable denial. Infrastructure-protection tests pass against the emulator and destroy data under real AWS semantics, and clients that key on the denial reason see nothing.
Fix: the UpdateStack handler and the stack update engine of the cloudformation service — evaluate the stack's stored policy (and the per-update StackPolicyDuringUpdateBody, scoped to that single update and never overwriting the stored document) against each planned resource action (Update:Modify / Update:Replace / Update:Delete / Update:*), fail the denied resource, roll the stack back to UPDATE_ROLLBACK_COMPLETE restoring the siblings, and emit the UPDATE_FAILED event with the stack-policy reason above.
Traces: cloudformation.stack-policy-roundtrip-and-enforcement, cloudformation.stack-policy-delete-protected-resource-rejected, cloudformation.stack-policy-during-update-body-overrides-for-one-update-only.

Cause 2 of 3: an in-place property update of an existing AWS::SNS::Topic is refused by the provisioner, so the whole stack update fails.
AWS: an UpdateStack that changes a mutable AWS::SNS::Topic property (e.g. DisplayName) updates the topic in place — the resource keeps its PhysicalResourceId (the topic ARN), its event is UPDATE_COMPLETE, and the stack reaches UPDATE_COMPLETE. No modeled error exists for this: UpdateStack's only modeled errors are InsufficientCapabilitiesException and TokenAlreadyExistsException, and 'NotImplemented' is not in CloudFormation's taxonomy at all.
Emulator: the stack settles UPDATE_FAILED with StackStatusReason "The following resource(s) failed to update: [Topic]. NotImplemented: this emulator does not change the properties of an existing AWS::SNS::Topic in place; the resource was left as it is." Both the status and the reason are emulator-authored — the fixed text is the whole 'NotImplemented: this emulator does not change the properties of an existing AWS::SNS::Topic in place; the resource was left as it is.' sentence, the only variable part being the failing logical id list ([Topic], taken from the template). The same defect was filed and FIXED for AWS::SQS::Queue (20261023T135552Z-...): SQS in-place updates now succeed, SNS::Topic still refuses, so the fix was resource-type-scoped.
Why: any stack that updates an SNS topic's properties is undeployable past its first create; the client gets a terminal UPDATE_FAILED carrying a status reason real CloudFormation never emits, and anything built on top (here, a stack-policy enforcement test that needs an ALLOWED update to complete first) cannot run at all.
Fix: the AWS::SNS::Topic resource provisioner in the cloudformation service's update engine — implement the in-place property update (mutable properties applied via the SNS service's own SetTopicAttributes-equivalent state, PhysicalResourceId preserved) instead of returning NotImplemented, and audit the other resource types for the same stub.
Traces: cloudformation.stack-policy-blocks-unauthorized-updates.

Cause 3 of 3: with Transform: AWS::LanguageExtensions, Fn::Length over a Ref to a CommaDelimitedList parameter is not resolved and the whole create fails.
AWS: under Transform: AWS::LanguageExtensions (CreateStack.Capabilities enum Capability includes CAPABILITY_AUTO_EXPAND; InsufficientCapabilitiesException, httpError 400, is what gates transform processing), Fn::Length evaluates at transform time to the element count of its list argument, and that argument may be {"Ref": "<param>"} naming a CommaDelimitedList parameter — resolved from the supplied Parameters, else from the parameter's Default. A template with Items: {Type: CommaDelimitedList, Default: "a,b,c"} and Output Count: {"Fn::Length": {"Ref": "Items"}} reaches CREATE_COMPLETE with OutputValue "3" (and in the same template Fn::ToJsonString serialises its object argument and Fn::GetAtt with a Ref'd attribute name resolves).
Emulator: the create ends StackStatus 'CREATE_FAILED' with StackStatusReason "Fn::Length: the argument is not a list this service can count from the template alone" — emulator-authored prose (fixed text: the whole clause after the function name; variable part: the intrinsic name taken from the template). The Ref to the CommaDelimitedList parameter is evidently not resolved before the intrinsic is evaluated, which is the same unresolved-collection shape already filed for Fn::ForEach in 20261025T210446Z-cloudformation-2-net-new-behavioral-root-causes-fn.md, in a different intrinsic's code path; because the stack fails, the Fn::ToJsonString and dynamic-GetAtt legs of the same template, and the no-transform refusal leg (ValidationError "Template Error: Encountered unsupported function: Fn::Length Supported functions are: [...]"), are never reached.
Why: any template written against the language extensions that counts a list parameter is undeployable — the client gets a terminal CREATE_FAILED for a template real CloudFormation deploys, with a reason CloudFormation cannot produce, so error handling keyed on AWS's wording does not match either.
Fix: the AWS::LanguageExtensions transform pass in the cloudformation template pipeline — resolve parameter Refs (supplied value, else Default) for CommaDelimitedList/list parameters before evaluating Fn::Length (and share that resolver with Fn::ForEach), and evaluate the intrinsic in the Outputs section as well as Resources.
Traces: cloudformation.language-extensions-length-tojsonstring-and-dynamic-getatt.
