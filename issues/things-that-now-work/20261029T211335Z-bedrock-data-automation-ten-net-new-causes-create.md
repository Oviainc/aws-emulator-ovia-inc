=== Cause 1 of 10: CreateBlueprint without blueprintStage settles at DEVELOPMENT, where AWS settles at LIVE ===
AWS: Smithy: CreateBlueprintRequest.blueprintStage targets the enum BlueprintStage (values DEVELOPMENT, LIVE) and is OPTIONAL; CreateBlueprint -> 201 with required member blueprint (Blueprint), whose blueprintStage reports the stage the blueprint actually holds. Recorded behavior: a CreateBlueprint that omits blueprintStage comes back with blueprintStage LIVE, and a later GetBlueprint that omits blueprintStage (which resolves LIVE) finds it; a DEVELOPMENT-only blueprint is only readable with blueprintStage named explicitly.
Emulator: the 201 reports blueprint.blueprintStage "DEVELOPMENT" for a create that named no stage, and every read-back repeats it.
Why: a client that gates servability on the stage sees a development artefact it never asked for and will refuse or re-stage a blueprint AWS already published; worse, a stage-promotion flow (CopyBlueprintStage DEVELOPMENT->LIVE) has its pre-condition inverted — the stage that must be absent exists and the stage that must exist does not.
Fix: the CreateBlueprint handler's stage default (and the stage the Blueprint projection carries over into CreateBlueprintVersion).
Traces: bedrock-data-automation.create-blueprint-defaults-to-live-stage, bedrock-data-automation.create-blueprint-version-increments-version-number, bedrock-data-automation.copy-blueprint-stage-missing-source-not-found-rejected.

=== Cause 2 of 10: blueprint ResourceNotFoundException is worded by the emulator and echoes the requested ARN ===
AWS: Smithy: GetBlueprint (and DeleteBlueprint/CreateBlueprintVersion) model ResourceNotFoundException, errorKind client, @httpError(404), single member message. Recorded behavior: the 404 message is exactly "Blueprint Arn not found." — entirely FIXED text, with NO part taken from the request or from state.
Emulator: status 404 and code ResourceNotFoundException are correct, but the message is "blueprint <blueprintArn> does not exist" — different fixed text, plus the request's ARN interpolated into it.
Why: ResourceNotFoundException carries no code member, so the message is the only discriminator a client has; idempotent teardown that swallows the service's not-found wording escalates on this one, and the message length becomes a function of the request where AWS's never is.
Fix: the not-found refusal wording in the blueprint lookup path shared by the GetBlueprint/DeleteBlueprint/CreateBlueprintVersion handlers — single-home it so the doors cannot drift.
Traces: bedrock-data-automation.get-blueprint-nonexistent-arn-not-found, bedrock-data-automation.delete-blueprint-removes-resource, bedrock-data-automation.delete-blueprint-specific-version-leaves-other-versions-intact, bedrock-data-automation.concurrent-blueprint-version-creation-unique-versions, bedrock-data-automation.list-blueprints-filtered-by-arn-reflects-created.

=== Cause 3 of 10: CreateBlueprint duplicate-name ConflictException is re-worded and leaks the @sensitive blueprintName ===

=== Cause 6 of 10: pattern-violation ValidationException echoes the rejected @sensitive value and reports the pattern with its anchors ===
AWS: Smithy: blueprintName -> BlueprintName, libraryName -> the library-name shape and projectName -> DataAutomationProjectName all carry pattern ^[a-zA-Z0-9-_]+$ and are @sensitive; ValidationException is errorKind client, @httpError(400), members message + fieldList. Recorded behavior: the 400 message is "1 validation error detected: Value at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9-_]+". Its FIXED text is "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy regular expression pattern: "; its VARIABLE parts are the member path (blueprintName / libraryName / projectName, from the request) and the pattern (from the model, reported WITHOUT the ^ and $ anchors). There is deliberately NO offending value between "Value" and "at", because the member is @sensitive.
Emulator: status 400 and code ValidationException are correct, but the message is "1 validation error detected: Value '<the rejected name>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[a-zA-Z0-9-_]+$" — it inserts the @sensitive value and prints the anchored pattern.
Why: the emulator writes a @sensitive value into an error body, so it reaches every client log and trace; and a client or test comparing against AWS's value-suppressed, unanchored message never matches, so the validation contract cannot be asserted at all.
Fix: the shared ValidationException message builder used by these three operations' input validation — suppress the offending value for @sensitive members and render the pattern unanchored.

=== Cause 7 of 10: TagResource / UntagResource / ListTagsForResource validate resourceARN against the Bedrock CONTROL-PLANE pattern, so every Bedrock Data Automation ARN is refused 400 ===
AWS: Smithy: TagResourceRequest.resourceARN, UntagResourceRequest.resourceARN and ListTagsForResourceRequest.resourceARN all target TaggableResourceArn, @length(20..1011), pattern ^arn:aws(|-cn|-iso|-iso-[a-z]|-us-gov):bedrock:[a-z0-9-]*:[0-9]{12}:(blueprint|data-automation-project|blueprint-optimization-invocation|data-automation-library|data-automation-library-ingestion-job)/[a-zA-Z0-9-]{12,36}$; the ops return 200 (empty body for Tag/Untag, tags for List) and model ResourceNotFoundException @httpError(404) for a resource that is gone.
Emulator: a blueprint or project ARN the emulator itself minted seconds earlier (arn:aws:bedrock:<region>:<account>:blueprint/<id>, which satisfies the modelled pattern) is refused 400 ValidationException whose message reports the neighbouring bedrock control-plane alternation (custom-model/guardrail/inference-profile/provisioned-model/...), a pattern that contains no blueprint or data-automation-project alternative at all. The whole tagging surface of this service is therefore unreachable, and with it the modelled 404 path.
Why: tags can never be read, set or removed on any Bedrock Data Automation resource, so cost allocation, tag-based access control and tag-driven inventory all fail closed — and they fail naming a pattern the client's own SDK model does not contain, so the client concludes its request was malformed rather than that the service is wrong. It also makes tags-on-create unverifiable.
Fix: the input validation for the three tagging operations — validate resourceARN against THIS service's TaggableResourceArn, not the bedrock control-plane ARN pattern.
Traces: bedrock-data-automation.tag-resource-merges-with-existing-tags, bedrock-data-automation.tag-resource-list-and-untag-round-trip, bedrock-data-automation.untag-resource-nonexistent-key-is-noop, bedrock-data-automation.list-tags-for-resource-reflects-tags-from-create-call, bedrock-data-automation.concurrent-tag-resource-calls-merge-under-contention, bedrock-data-automation.tag-resource-exceeds-array-limit-rejected.

AWS: Smithy: CreateBlueprint models AccessDeniedException, errorKind client, @httpError(403), doc "This exception is thrown when a request is denied per access permissions". Recorded behavior: a caller that assumes an IAM role with NO attached identity-based policy and calls CreateBlueprint is refused 403 AccessDeniedException with the message "User: arn:aws:sts::<account>:assumed-role/<roleName>/<sessionName> is not authorized to perform: bedrock:CreateBlueprint on resource: arn:aws:bedrock:<region>:<account>:blueprint/* because no identity-based policy allows the bedrock:CreateBlueprint action".
