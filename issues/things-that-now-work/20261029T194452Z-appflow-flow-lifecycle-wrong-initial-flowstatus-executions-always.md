# AppFlow flow lifecycle: wrong initial flowStatus, executions always Error, and three missing/ wrong CreateFlow rejections

> _Note: this issue was identified against the code base at commit `a2b95246df63384d1b9b9d3ee28f05a727c934df`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFlow

## Description
AppFlow answers on the wire, but its flow lifecycle and its CreateFlow rejection surface diverge from AWS in five independent ways. 5 causes. (Related but NOT covering these: open issue 20261029T192701Z-appflow-describeflow-and-listflows-omit-flow-state-fidelity.md describes DescribeFlow/ListFlows projection from the wire corpus, and 20261029T192701Z-appflow-error-message-text-diverges-from-aws-wording.md describes the CreateConnectorProfile pattern-anchor message and the DescribeFlow not-found sentence. Neither carries the behavioral checks below.)

Cause 1 of 5: the initial flowStatus a flow gets does not depend on triggerConfig.triggerType; the two cases are effectively inverted.
AWS: Smithy: CreateFlow output member flowStatus targets enum FlowStatus (Active|Deprecated|Deleted|Draft|Errored|Suspended); triggerConfig.triggerType targets enum TriggerType (Scheduled|Event|OnDemand). Recorded behavior only for the defaulting rule: a flow created with triggerType=OnDemand is immediately usable and comes back (and is independently reported by DescribeFlow and in the ListFlows FlowDefinition) with flowStatus=Active; a flow created with triggerType=Scheduled comes back with flowStatus=Draft and only becomes Active when StartFlow activates its schedule.
Emulator: exactly reversed. CreateFlow with OnDemand returns flowStatus "Draft" (and DescribeFlow/ListFlows keep reporting Draft); CreateFlow with Scheduled returns flowStatus "Active". Two further checks never reach the behavior they probe because of this: on a Scheduled flow StartFlow is refused with 409 ConflictException "Flow <flowName> is already activated and cannot be started again" (the flow was wrongly born Active), and a wait for an OnDemand flow to reach Active never terminates, so appflow.stop-flow-state-conflicts-rejected times out after 60s without ever issuing its StopFlow calls.
Why: every status-gated client workflow breaks. A caller that waits for Active before StartFlow hangs forever on an on-demand flow; a caller that treats Active as "schedule is running" sees a scheduled flow as live before it ever activated it, and its StartFlow activation is refused as a conflict. Downstream DeleteFlow-without-forceDelete and StopFlow conflict semantics cannot be exercised at all.
Fix: the appflow CreateFlow handler / the flow state machine in appflow state that assigns the initial FlowStatus - it must derive it from triggerConfig.triggerType (OnDemand -> Active, Scheduled -> Draft) rather than using one fixed default, and DescribeFlow/ListFlows must project that value.
Traces: appflow.create-flow-ondemand-defaults-active, appflow.create-flow-scheduled-defaults-draft, appflow.describe-flow-after-delete-not-found, appflow.list-flows-reflects-flow-lifecycle, appflow.scheduled-flow-start-stop-state-transitions, appflow.delete-active-flow-without-force-rejected, appflow.stop-flow-state-conflicts-rejected.

Cause 2 of 5: every flow execution terminates in executionStatus=Error; no S3-to-S3 transfer is ever performed.
AWS: Smithy: ExecutionStatus enum = InProgress|Successful|Error|CancelStarted|Canceled; ExecutionRecord.executionResult is ExecutionResult{errorInfo, bytesProcessed, bytesWritten, recordsProcessed,...}. Recorded behavior only: an on-demand S3-to-S3 flow whose source and destination buckets carry the AppFlow resource policies, started with StartFlow, reaches executionStatus=Successful in DescribeFlowExecutionRecords with non-zero bytesProcessed/bytesWritten/recordsProcessed and no errorInfo, and the source object's records appear under the destination prefix.
Emulator: the execution is recorded but always lands on executionStatus "Error" with executionResult.errorInfo.executionMessage "This emulator does not connect to source or destination connector endpoints so the flow run was not performed." and bytesProcessed/bytesWritten/recordsProcessed all 0, so no data is moved to the destination bucket.
Why: a client that starts a flow and polls for a terminal state always sees failure, so any pipeline gated on a successful transfer (and any test asserting the destination objects exist) fails even though the flow definition and the bucket policies are correct. The accompanying conflict/execution-id semantics on top of a run cannot be validated either.
Fix: the appflow StartFlow execution path and the flow-execution state it writes - an S3 source/destination flow must actually read the source prefix from the emulator's S3 state, write the mapped records to the destination prefix, and record a Successful ExecutionRecord with real byte/record counts instead of a canned Error.
Traces: appflow.start-flow-returns-new-execution-id-each-run, appflow.concurrent-start-flow-second-call-conflicts, appflow.s3-to-s3-flow-data-transfer-requires-bucket-policy.

Cause 3 of 5: the duplicate-flow-name ConflictException message is emulator prose.
AWS: Smithy: CreateFlow models ConflictException (httpError 409, "There was a conflict when processing the request (for example, a flow with the given name already exists within the account..."); its only member is message. Recorded behavior for the text: the FIXED text is "Conflict executing request: Flow with name " + the flowName taken verbatim from the request + " already exists." - the flow name is the only variable part.
Emulator: correct 409/ConflictException, but message "A flow with the name <flowName> already exists in this account" - different fixed text (and no trailing period).
Why: clients and tests that match AWS's conflict sentence, or that parse the flow name out of its documented position, do not recognise the emulator's error; the status and code being right makes the divergence silent.
Fix: the appflow CreateFlow handler's duplicate-name branch where the ConflictException message is built.
Traces: appflow.create-flow-duplicate-name-rejected.

Cause 4 of 5: the flowName @pattern ValidationException message quotes the regex anchored and with an extra character class member.
AWS: Smithy: CreateFlow.flowName is @required, @length min 0 max 256, @pattern "^[a-zA-Z0-9][\\w!@#.-]+$"; modeled error ValidationException (httpError 400, "The request has invalid or missing parameters."). The constraint-violation message's FIXED text is "<n> validation error detected: Value '<value>' at '<memberName>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>"; its VARIABLE parts are the error count, the rejected value from the request, the member name and the pattern. Recorded behavior: for flowName AWS renders that pattern as "[a-zA-Z0-9][\\w!@.-]+" - unanchored (no leading ^, no trailing $) and without the '#'.
Emulator: same 400/ValidationException and same template, but it interpolates the raw modeled pattern: "...Member must satisfy regular expression pattern: ^[a-zA-Z0-9][\\w!@#.-]+$".
Why: a client that asserts on the documented constraint message, or lifts the pattern out of the message to re-validate input client-side, gets a regex string AWS never sends, so message equality and pattern round-trips fail even though the request was correctly rejected. This is the same formatter defect already reported for CreateConnectorProfile in 20261029T192701Z-appflow-error-message-text-diverges-from-aws-wording.md, now observed on CreateFlow.flowName with the additional character-class divergence.
Fix: the shared constraint-violation message formatter used by appflow input validation (and CreateFlow's flowName validation specifically) - it must render the @pattern as AWS does for this member.
Traces: appflow.create-flow-invalid-name-pattern-rejected.

Cause 5 of 5: CreateFlow does not validate that a referenced connectorProfileName exists.
AWS: Smithy: CreateFlow models ResourceNotFoundException (httpError 404, "The resource specified in the request (such as the source or destination connector profile) is not found."). Recorded behavior: a CreateFlow whose sourceFlowConfig names a connectorProfileName that was never created is rejected 404 ResourceNotFoundException with fixed text "Connector Profile with name " + the connectorProfileName from the request + " does not exist.", and no flow resource is left behind (it is absent from ListFlows and DescribeFlow on it answers 404 ResourceNotFoundException "There is no flow with the name <flowName>").
Emulator: the call SUCCEEDS - HTTP 200 with {"flowArn": "arn:aws:appflow:<region>:<account>:flow/<flowName>", "flowStatus": "Draft"} - so a flow referencing a non-existent connector profile is created and persisted.
Why: the misconfiguration is accepted silently instead of being refused at definition time; the caller believes it has a working flow, and the account accumulates flows that can never run. A client relying on the 404 to detect a missing connector profile gets no signal at all.
Fix: the appflow CreateFlow handler's validation stage - resolve every connectorProfileName referenced by sourceFlowConfig/destinationFlowConfigList against the connector-profile store and raise ResourceNotFoundException with the AWS message before any flow record is written.
Traces: appflow.create-flow-nonexistent-connector-profile-rejected.
