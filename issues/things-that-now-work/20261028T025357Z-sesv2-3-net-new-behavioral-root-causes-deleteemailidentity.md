# sesv2: 3 net-new behavioral root causes — DeleteEmailIdentity's not-found sentence is over-bracketed, SendEmail's ListManagementOptions auto-created contact carries no TopicPreferences, and an unknown topic is refused BadRequestException instead of NotFoundException

> _Note: this issue was identified against the code base at commit `cfba8734135a5a589a22a2abb68b652faa765932`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail

## Description
Three net-new root causes in the sesv2 email-identity and contact-list/list-management planes. All three are grounded in failing behavioral checks of this suite and are distinct from the open issues that already own other sesv2 failures (notably 20261026T065823Z-sesv2-the-notfoundexception-message-for-a-missing-configuration.md, which is about the CONFIGURATION SET sentence missing its brackets — the opposite direction and a different message builder, and 20261027T083802Z-sesv2-5-net-new-behavioral-root-causes-in.md, which owns the reputation-entity/tenant/event-destination causes).

=== Cause 1 of 3: DeleteEmailIdentity's NotFoundException message wraps the identity in angle brackets, which AWS does not do for this operation ===
AWS: Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json) models DeleteEmailIdentity (DELETE /v2/email/identities/{EmailIdentity}) with NotFoundException at HTTP 404, "The resource you attempted to access doesn't exist." The model does not carry the sentence, so this is recorded behavior: deleting an identity that does not exist is refused 404 NotFoundException whose message is the fixed text "Email identity " + the request's EmailIdentity + " does not exist." — with NO angle brackets around the identity. The SIBLING read, GetEmailIdentity, refuses the same missing identity with the bracketed form "Email identity <" + EmailIdentity + "> does not exist." The two operations' sentences differ in exactly that bracketing; the only variable part of each is the EmailIdentity taken from the request.
Emulator: status (4xx) and code (NotFoundException) are right, but DeleteEmailIdentity serves the BRACKETED sentence: for the identity requested, it returned 'Email identity <IDENTITY> does not exist.' where AWS returns 'Email identity IDENTITY does not exist.' One shared message builder, crate::state::email_identity_not_found, is used for both the delete path and the get path (call site: src/ops/delete_email_identity.rs line 154), so the bracketed form leaks into the operation that must not have it.
Why: the error message is part of the contract. A client that asserts or parses SES's not-found sentence per operation (or an operator diffing AWS and emulator logs) sees a different sentence for an otherwise byte-identical request/status/code pair, and a parser that strips the brackets on GetEmailIdentity but not DeleteEmailIdentity extracts the wrong resource name.
Fix: the DeleteEmailIdentity handler's not-found path and the shared identity-not-found message builder in the sesv2 state module — the delete refusal must render the identity unbracketed while the get refusal keeps the brackets.
Traces: sesv2.email-identity-lifecycle.

=== Cause 2 of 3: SendEmail with ListManagementOptions.TopicName auto-creates the contact with no TopicPreferences entry ===
AWS: Smithy models SendEmail.ListManagementOptions as {ContactListName (required), TopicName}, documented as "An object used to specify a list or topic to which an email belongs, which will be used when a contact chooses to unsubscribe", and GetContact returns TopicPreferences as a list of TopicPreference{TopicName (required), SubscriptionStatus (required, OPT_IN|OPT_OUT)}. Recorded behavior: a SendEmail that names an existing contact list AND a topic that list publishes auto-creates the recipient as a contact of that list AND records a TopicPreferences entry for the named topic (the recipient is subscribed to the topic the message belongs to), while the same send WITHOUT a TopicName auto-creates the contact with no topic subscription at all.
Emulator: the contact is auto-created (GetContact finds it with the right EmailAddress) but TopicPreferences is absent — GetContact returned TopicPreferences=None for the contact created by a send that named the topic, so the check's required single-entry set for the named topic is empty. The handler inserts crate::state::ContactRecord::new(address, now) and never consults the request's TopicName (src/ops/send_email.rs lines 412-428, where only the contact-list name is carried forward from the list-management resolution at lines 302-323).
Why: the topic subscription is the whole point of list management — the unsubscribe link in the message unsubscribes the contact from THAT topic. A client that sends with a TopicName and then reads the contact back (GetContact/ListContacts, or filters contacts by TopicFilter) sees a contact with no subscription, so later opt-out/opt-in flows and per-topic suppression behave differently against the emulator than against AWS, and the distinction between a send with a TopicName and one without is lost.
Fix: the SendEmail handler's list-management contact-creation path (src/ops/send_email.rs) and the contact record it builds in the sesv2 state module — carry the resolved TopicName into the auto-created ContactRecord as a TopicPreferences entry for that topic (with the subscription status AWS records for a contact created this way), and keep the no-TopicName case preference-free.
Traces: sesv2.list-management-options-unknown-list-rejected-contact-auto-created.

=== Cause 3 of 3: SendEmail naming a topic the contact list does not publish is refused BadRequestException/400 instead of NotFoundException/404 ===
AWS: Smithy declares both BadRequestException (400) and NotFoundException (404) on SendEmail; NotFoundException is documented "The resource you attempted to access doesn't exist." Recorded behavior: a SendEmail whose ListManagementOptions names an EXISTING contact list but a TopicName that list does not publish is refused HTTP 404 NotFoundException with the message "List: " + ContactListName + " doesn't contain Topic: " + TopicName — fixed text "List: "/" doesn't contain Topic: ", variable parts taken from the request. The sibling fault (an unknown ContactListName) is likewise NotFoundException, "List with name: " + ContactListName + " doesn't exist."
Emulator: the message text is already correct, but the error is classified as the wrong class: it answered ('BadRequestException', "List: LIST doesn't contain Topic: TOPIC") — HTTP 400 — where AWS answers ('NotFoundException', the same sentence) at HTTP 404. The unknown-LIST case is correctly NotFoundException, so only the unknown-TOPIC branch is misclassified: src/ops/send_email.rs lines 313-320 returns bad_request(crate::state::contact_list_topic_not_found(..)) instead of the modeled NotFoundException.
Why: clients branch on the error code and the HTTP status, not the sentence. Retry/recovery logic that treats 404 NotFoundException as "create the topic / fix the reference" and 400 BadRequestException as "malformed request" takes the wrong branch, and SDK error-type matching (NotFoundException) never fires for a missing topic against the emulator.
Fix: the SendEmail handler's list-management topic resolution (src/ops/send_email.rs) — return the modeled NotFoundException (404) for a topic the named list does not publish, keeping the existing message text.
Traces: sesv2.send-email-list-management-options-are-resolved-against-the-contact-list.
