# AppConfig: GetDeployment not-found message wording, DeleteApplication is not gated on child environments, and a JSON_SCHEMA validator is not evaluated at StartDeployment (3 causes)

> _Note: this issue was identified against the code base at commit `0790bb7a78fe50d7afa4bce89d8f5918d3395bcd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

StartDeployment

## Description
Three net-new root causes in the bootstrapped `appconfig` control plane, each grounded in its own replayed behavioral check. They are numbered below; close ALL THREE and re-replay every check id in trace_ids before submitting. None of these three checks was marked ALREADY FILED and none was marked OWNED by an open issue. Related open issues that do NOT cover them: 20261024T131534Z-appconfig-refusal-messages-on-the-tagging-pagination-hosted.md (refusal-message templates on the tagging/pagination/hosted-version/experiment/extension paths — it does not mention the GetDeployment not-found template of Cause 1), 20261025T110244Z-appconfig-lambda-appconfig-startdeployment-never-runs-a-configuration-profile-s.md (StartDeployment does not run LAMBDA validators — Cause 3 is the JSON_SCHEMA validator type, a different validator engine in the same gate). === Cause 1 of 3: GetDeployment's not-found message renders the deployment-number label as 'Deployment Number' instead of AWS's 'deploymentNumber' ===
AWS: GetDeployment is GET /applications/{ApplicationId}/environments/{EnvironmentId}/deployments/{DeploymentNumber}, success 200, modeled errors BadRequestException 400, ResourceNotFoundException 404, InternalServerException 500 (Smithy, services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model: GetDeployment, input ApplicationId/EnvironmentId/DeploymentNumber all @required @httpLabel). The model carries no message text, so the template is recorded behavior only: addressing a deployment number that does not exist under the addressed environment answers ResourceNotFoundException / HTTP 404 with the message `Deployment with Application Id <ApplicationId>, Environment Id <EnvironmentId>, and deploymentNumber <DeploymentNumber> could not be found for account <accountId>.` Its FIXED text is `Deployment with Application Id `, `, Environment Id `, `, and deploymentNumber `, ` could not be found for account `, and the final `.`; its VARIABLE parts are the ApplicationId, EnvironmentId and DeploymentNumber taken verbatim from the request and the caller's 12-digit account id taken from the emulator's identity. Note the deliberate casing asymmetry: the two resource-id labels are title-case with a space, the deployment-number label is the lowerCamelCase wire/member spelling `deploymentNumber`.
Emulator: the status (404) and the error code (ResourceNotFoundException) are right, the message label is not. Replay recorded `Deployment with Application Id ho65pb1, Environment Id tn20ygr, and Deployment Number 2 could not be found for account 000000000000.` where AWS says `... and deploymentNumber 2 could not be found for account 000000000000.` — the label was title-cased and split into two words. (The ids and the account digits in that line are per-run values filling the template, not requirements.)
Why: clients and operators parse and assert on these templates; AWS's own console/CLI output and customer log scrapers key on the `deploymentNumber` token. A client that matches the AWS wording sees no match against the emulator, and a test suite pinned to the emulator's wording fails against production.
Fix: the GetDeployment handler's not-found path and the shared AppConfig refusal-message formatter it uses to build ResourceNotFoundException messages — only the label text for the deployment-number component is wrong, the id/account substitution is already correct.
Traces: appconfig.deployment-number-is-per-environment-sequence.

=== Cause 2 of 3: DeleteApplication succeeds while environments still exist under the application, instead of being refused with BadRequestException ===
AWS: DeleteApplication is DELETE /applications/{ApplicationId}, success 204, modeled errors BadRequestException 400, ResourceNotFoundException 404, InternalServerException 500 (Smithy, same model). AppConfig gates application deletion on CHILD EXISTENCE, not on deployment state: while at least one environment exists under the application the call is refused with BadRequestException / HTTP 400 and the message `Cannot delete application <ApplicationId>, because there are still environments existing under it.` (recorded behavior; the model carries no message text). Fixed text: `Cannot delete application `, `, because there are still environments existing under it.`; variable part: the ApplicationId from the request. The refusal must have NO effect — the application stays readable via GetApplication and its environments stay listed by ListEnvironments. The gate is on the first child type AppConfig checks (environments), independent of whether any deployment is in flight.
Emulator: delete_application(ApplicationId=<app with one environment and one configuration profile beneath it>) raised no ClientError at all. Replay: `AssertionError: DeleteApplication must be refused while children exist, got None` — i.e. the emulator answered a 2xx/204 success for a call AWS answers 400 BadRequestException. This is an over-permissiveness defect: the parent of live children is deletable.
Why: a client that relies on AWS's ordering contract (tear down bottom-up, and trust that a mistaken top-down delete is refused) gets silent destruction of the application node on the emulator while production refuses the same call — teardown scripts and CloudFormation-style dependency logic that are 'proved' against the emulator break in production, and an accidental DeleteApplication that AWS protects against appears to succeed here. It also hides the orphan-state question entirely (what happened to the environments and profiles beneath the deleted application is unobservable).
Fix: the DeleteApplication handler's pre-delete validation plus the AppConfig resource-tree state it must consult (count environments under the application id before deleting), and the BadRequestException message template in that service's error serializer. Note the check aborts at this leg, so the sibling gate it asserts immediately after — DeleteConfigurationProfile refused with BadRequestException / 400 and `Cannot delete configuration profile <ConfigurationProfileId> because there are still hosted configuration versions existing under it.` — is NOT verified by this run and must be confirmed in the same pass.
Traces: appconfig.in-flight-deployment-does-not-block-leaf-deletion.

=== Cause 3 of 3: a JSON_SCHEMA validator attached to a configuration profile after a version is stored does not gate StartDeployment of that stored version ===
AWS: StartDeployment is POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, modeled errors BadRequestException 400, ConflictException 409, ResourceNotFoundException 404, InternalServerException 500; a configuration profile carries Validators (ValidatorList, @length 0..2, member Validator{Type: JSON_SCHEMA|LAMBDA, Content}) settable on CreateConfigurationProfile and UpdateConfigurationProfile (Smithy, same model). A profile's validators are consulted at DEPLOYMENT time as well as at CreateHostedConfigurationVersion time, so attaching a JSON_SCHEMA validator that an ALREADY-STORED version violates makes StartDeployment of that version refused with BadRequestException / HTTP 400, with no deployment record created, the environment left out of the Deploying state, the data plane still serving the previously deployed bytes, and the non-compliant hosted version still STORED (the validator gates deployment, not storage). The deployment-time arm of this gate is MEASURED in this corpus for the LAMBDA validator type (appconfig__lambda.validator-lambda-rejects-noncompliant-content-rejected asserts StartDeployment answers BadRequestException), and the create-time arm is measured for JSON_SCHEMA; that JSON_SCHEMA is also evaluated at deployment time is, per the replayed check's own DRAFT header, a Hypothesis (H1) the check's first replay was to confirm. The recorded refusal message the check pins is `Could not build JSON schema from invalid input:\n <validatorContent>.\n Original error message:\n[message: "instance type (string) does not match any allowed primitive type (allowed: [\"integer\"])" - parent node: /replicas]` — fixed text is the preamble `Could not build JSON schema from invalid input:` and `Original error message:`; variable parts are the validator's own schema document (echoed from the profile) and the violation report derived from the stored content and that schema (the offending node path, here /replicas, and the actual vs allowed primitive types). Hypothesis: the message's inner bracketed report is produced by AWS's JSON-schema library, so the primary requirement is the 400 BadRequestException refusal plus a message naming the violating node and the type mismatch; its exact punctuation is draft-level evidence, not confirmed ground truth.
Emulator: the identical StartDeployment that legitimately succeeded before the validator existed is still ACCEPTED after `UpdateConfigurationProfile(Validators=[{Type: JSON_SCHEMA, Content: <schema>}])` lands and GetConfigurationProfile confirms the validator is attached. Replay: `AssertionError: the call under test SUCCEEDED where real AWS refuses it — this is an over-permissiveness failure, not an error-code mismatch` at the BEAT-3 StartDeployment. The validator list is stored as metadata and is evidently only consulted (if at all) on CreateHostedConfigurationVersion. Note this replay also shows the control-plane and appconfigdata legs before it now working (the pre-validator deployment reached COMPLETE and the data plane served the deployed bytes byte-exactly), so the failure is attributable to the validator gate alone.
Why: this is a safety inversion — an operator adds a schema guard to a profile and the guard does nothing. Content that production would refuse to roll out deploys on the emulator and is served to every client of that environment, so a release pipeline validated against the emulator ships a configuration that real AppConfig blocks at StartDeployment (and conversely a pipeline that handles the 400 never exercises that path).
Fix: the StartDeployment handler's pre-flight validation stage and the configuration-profile state it reads — resolve the profile's Validators for the requested ConfigurationVersion, run each JSON_SCHEMA validator against the stored content, and on violation refuse with BadRequestException/400 and the schema-violation message, creating no deployment record and leaving the environment state and the stored version untouched. The same seam carries the already-filed LAMBDA validator arm.
Traces: appconfig.json-schema-validator-added-later-blocks-deploying-a-stored-version.
