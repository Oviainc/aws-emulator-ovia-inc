# ECR basic image scanning can never reach COMPLETE: every scan settles at FAILED/UnsupportedImageError, so scan findings are unreachable (1 cause)

> _Note: this issue was identified against the code base at commit `ef659389d11311dc27a7ee58cb593d22d3f663cf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeImageScanFindings

## Description
One root cause, in ECR.

Context on already-filed work that does NOT cover this check (the replay report did not mark this check as owned by any open issue): the open issue 20261024T014332Z-ecr-asynchronous-effects-never-occur-and-several-enforcement.md stops at a DescribeImageScanFindings `NotImplemented` stub, which this check now gets past (the operation answers HTTP 200). The resolved issue 20261024T080016Z-ecr-image-storage-class-transitions-scan-evaluation-media.md (Cause 2) reported the mirror-image defect — the scan always reported COMPLETE — and asked for the terminal status to be DERIVED from the stored image. That change landed as a constant in the other direction, which is the defect below. This is not a REOPENS: the call is not refused, it answers HTTP 200 with a terminal scan status that is simply always the failure one.

Cause 1 of 1: the basic-scan outcome is a constant FAILED/"unsupported image" for every image, so COMPLETE and the findings projection are unreachable.
AWS: Smithy: StartImageScan and DescribeImageScanFindings both return `imageScanStatus` (ImageScanStatus{status: ScanStatus, description}) with ScanStatus = IN_PROGRESS|COMPLETE|FAILED|UNSUPPORTED_IMAGE|ACTIVE|PENDING|SCAN_ELIGIBILITY_EXPIRED|FINDINGS_UNAVAILABLE|LIMIT_EXCEEDED|IMAGE_ARCHIVED; DescribeImageScanFindings additionally returns `imageScanFindings` (ImageScanFindings{imageScanCompletedAt, vulnerabilitySourceUpdatedAt, findingSeverityCounts, findings, enhancedFindings}). Recorded behavior: with BASIC scanning enabled on the registry, StartImageScan on a pushed single-layer image whose filesystem layer carries a recognizable OS release file and package database (here `/etc/os-release` identifying Alpine Linux plus an empty `lib/apk/db/installed`) answers PENDING/IN_PROGRESS and then settles at the terminal status COMPLETE, and the terminal DescribeImageScanFindings read carries an `imageScanFindings` object populated with `findingSeverityCounts` and `imageScanCompletedAt` (the findings list may legitimately be empty for a package-less image — the severity-count map and the completion timestamp are what COMPLETE guarantees). The recorded contrast case is encoded by a second check in this same suite: an image whose layer carries NO OS or package manager settles at FAILED with description "UnsupportedImageError: The operating system and/or package manager are not supported." So the terminal status is a FUNCTION of the scanned image, and both outcomes are reachable against AWS.
Emulator: every scan settles at the FAILED outcome regardless of the image. DescribeImageScanFindings answers HTTP 200 with {'imageScanStatus': {'status': 'FAILED', 'description': 'UnsupportedImageError: The operating system and/or package manager are not supported.'}} and no `imageScanFindings` member, for an image whose uploaded layer does contain an OS release file and a package database. The outcome is computed by `basic_scan_outcome`, which branches on `scanned_operating_system`; that walks the manifest's layer descriptors and calls `operating_system_in_layer`, which returns `None` unconditionally (the layer's bytes are discarded at CompleteLayerUpload and only digest/size/media-type are retained), so the COMPLETE arm of the branch is dead code and `basic_scan_findings` likewise returns an empty vector for every image.
Why: a client cannot ever observe a successful basic scan. CI/CD gates that require the terminal status COMPLETE before promoting an image block or fail permanently; policy code that reads `imageScanFindings.findingSeverityCounts` or `imageScanCompletedAt` off a COMPLETE scan never gets the member at all (reading it raises KeyError); and the FAILED/unsupported path — which a real client uses to detect genuinely unscannable images — is now indistinguishable from a healthy scan of a normal OS-based image, so the diagnostic value of that status is lost too. Together with the resolved issue above, the scan outcome has only ever been a constant, first COMPLETE and now FAILED; neither is a function of the image.
Fix: the basic-scan evaluation behind StartImageScan and the DescribeImageScanFindings projection — the terminal status must be derived from the scanned image's content, which requires the layer content that identifies the OS/package manager to be reachable from the image record (today it is not retained), and a COMPLETE run must populate `imageScanFindings` with at least `findingSeverityCounts` and `imageScanCompletedAt`. Not a message-only difference: the diverging value is the modelled `ScanStatus` enum member and a missing modelled output member. The check pushed a single-layer image whose gzipped tar layer contains `etc/os-release` (NAME="Alpine Linux", ID=alpine, VERSION_ID=3.18.4), an empty `lib/apk/db/installed` apk package database, and a marker file; the config declares architecture amd64 / os linux with that layer's diff_id. StartImageScan was accepted and reported PENDING/IN_PROGRESS (that assertion passed). The terminal poll (budget 180 s, interval 5 s, accepting any of COMPLETE/FAILED/UNSUPPORTED_IMAGE/FINDINGS_UNAVAILABLE/SCAN_ELIGIBILITY_EXPIRED/LIMIT_EXCEEDED/IMAGE_ARCHIVED) settled immediately at FAILED. Expected: status COMPLETE, with `imageScanFindings` present and carrying `findingSeverityCounts` and `imageScanCompletedAt` (the two subsequent assertions never ran).

Source of the constant, in the checkout: state.rs `operating_system_in_layer(layer) -> Option<String>` is `{ let _ = layer; None }`, so `scanned_operating_system` is always None and `basic_scan_outcome` always takes the FAILED arm; `basic_scan_findings(image)` is `{ let _ = image; Vec::new() }`. The emulator's own doc comment on `operating_system_in_layer` states the cause: CompleteLayerUpload registers only a layer's digest, size and media type and keeps none of its bytes, so no OS release file is observable — but the check does upload those bytes via UploadLayerPart.
