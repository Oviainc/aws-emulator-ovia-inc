# Route 53 Resolver: CreateOutpostResolver skips the Outpost-existence check, DeleteOutpostResolver/GetOutpostResolver refuse a never-created id instead of answering 200, and managed-firewall-domain-list refusals use the wrong error class and message

> _Note: this issue was identified against the code base at commit `f9472a4c5be477aaebd68fc2f06dbf73c1bcd8d6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateOutpostResolver

## Description
THREE distinct root causes in the Route 53 Resolver control plane, all in the route53resolver service. A fixer must close ALL THREE before submitting; each cause lists its own failing check ids below.

Related open issues that do NOT cover these (named for context, not as coverage): 20261025T012620Z-route53resolver-route-53-resolver-rule-firewall-write-path-disassociateresolverrule.md (its Cause 4 describes the SAME defect as Cause 1 here, but it is grounded in other check ids, it does not carry route53resolver.create-outpost-resolver-invalid-instance-count-rejected, and it states the refusal message WITHOUT the service's '[RSLVR-03007] ' code prefix that the replay asserts verbatim — so a fix that satisfies only that issue's wording still fails the checks listed here); 20261024T062131Z-route53resolver-route-53-resolver-endpoint-state-is-fabricated-hostvpcid.md (endpoint state, and it calls CreateOutpostResolver 'unimplemented', which is no longer the observed behavior — it now succeeds); 20261024T150703Z-ec2-lambda-logs-route53resolver-route-53-resolver-createfirewalldomainlist.md and the per-operation stub issues (CreateFirewallRuleGroup, ImportFirewallDomains, GetFirewallConfig, ...), none of which name UpdateFirewallDomains, DeleteFirewallDomainList, ListFirewallDomains, DeleteOutpostResolver or GetOutpostResolver.

Cause 1 of 3: CreateOutpostResolver does not resolve OutpostArn against any Outpost registry — it creates a Resolver on an Outpost for any ARN that merely matches the modeled pattern.
AWS: Smithy: CreateOutpostResolver input CreatorRequestId (@required, @length 1..255), Name (@required, @length 1..255), PreferredInstanceType (@required), InstanceCount (integer, no @range — minimum 4 is enforced server-side), OutpostArn (@required, @length 1..255, @pattern ^arn:aws([a-z-]+)?:outposts:[a-z\d-]+:\d{12}:outpost/op-[a-f0-9]{17}$); modeled errors include ValidationException and ResourceNotFoundException, both HTTP 400. Recorded behavior: an OutpostArn that matches the pattern but names no Outpost racked in the account is refused deterministically, before anything is provisioned, with HTTP 400, error code ValidationException and message '[RSLVR-03007] Cannot find the Outpost with Arn "<OutpostArn>".' — fixed text '[RSLVR-03002]'-style bracketed service code plus 'Cannot find the Outpost with Arn "' ... '".', with the ARN taken verbatim from the request's OutpostArn member; AWS may append its per-request ' Trace Id: "..."' suffix, which is a per-run value and not part of the requirement. No OutpostResolver is created. The existence check runs AFTER the cheap InstanceCount range check, which the emulator already gets right (an InstanceCount of 1 is correctly refused HTTP 400 ValidationException '[RSLVR-03002] The instance count must be equal to or greater than "4".').
Emulator: the call SUCCEEDS with HTTP 200 and stores a record, e.g. {'OutpostResolver': {'Arn': 'arn:aws:route53resolver:<region>:<account>:outpost-resolver/rslvr-op-...', 'Id': 'rslvr-op-...', 'InstanceCount': 4, 'PreferredInstanceType': 'r5.large', 'Status': 'CREATING', 'OutpostArn': '<the nonexistent arn>'}}. services/service-com-amazonaws-route53resolver-route53resolver/src/ops/create_outpost_resolver.rs enforces InstanceCount (lines 182-190) and the store cap, then mints the record (lines 236-269) with no lookup of input.outpost_arn at all.
Why: the only deterministic Outpost contract an unracked account can observe is inverted. A client cannot distinguish 'your Outpost is not racked' from 'your Resolver is provisioning', its error handling for the ValidationException path is never exercised, and the emulator accumulates Resolvers on Outposts that do not exist — in one of these checks the caller is handed a resolver it never expected and has no cleanup for, and ListOutpostResolvers then reports phantom hardware.
Fix: in the CreateOutpostResolver handler (services/service-com-amazonaws-route53resolver-route53resolver/src/ops/create_outpost_resolver.rs), after the InstanceCount check and before anything is written, resolve OutpostArn against the Outposts state (the same set ListOutposts answers from) and return ValidationException (HTTP 400) with the '[RSLVR-03007] Cannot find the Outpost with Arn "<arn>".' message when it is absent, creating nothing. The message template belongs with this service's other '[RSLVR-...]' refusal builders in src/state.rs.
Traces: route53resolver.create-outpost-resolver-invalid-instance-count-rejected, route53resolver.outpost-resolver-lifecycle-creating-to-active-to-deleted.

Cause 2 of 3: DeleteOutpostResolver (and GetOutpostResolver) refuse an OutpostResolverId that was never created with ResourceNotFoundException, where AWS answers HTTP 200 quietly.
AWS: Smithy: DeleteOutpostResolver(Id: ResourceId @required @length 1..64) -> DeleteOutpostResolverResponse{OutpostResolver}; GetOutpostResolver(Id @required) -> GetOutpostResolverResponse{OutpostResolver}; both model ResourceNotFoundException (HTTP 400). Recorded behavior contradicts the docs-literal reading and is what the replay asserts: for an Id that was never associated with any Resolver, DeleteOutpostResolver returns HTTP 200 (idempotent, no error) and GetOutpostResolver returns HTTP 200 with the OutpostResolver member OMITTED from the response body entirely — neither throws ResourceNotFoundException — and the id never appears in ListOutpostResolvers.
Emulator: DeleteOutpostResolver answers HTTP 400 ResourceNotFoundException with message 'Resolver on Outpost with ID "<id>" does not exist.' (also not AWS's wording or error class). src/ops/delete_outpost_resolver.rs lines 167-174 return crate::state::outpost_resolver_not_found(&input.id) when the store holds nothing under the id; src/ops/get_outpost_resolver.rs lines 159-164 take the identical refusal path, so the Get half of the same contract diverges for the same reason (the replay stops at the Delete call, so Get is unverified in this run but is the same code path and the same cause).
Why: teardown and idempotent-retry paths break. A client that deletes defensively, or retries a delete after a timeout, gets a hard 400 where AWS returns success, so cleanup code aborts; a client probing existence with Get sees an exception instead of a 200 with an absent member.
Fix: in services/service-com-amazonaws-route53resolver-route53resolver/src/ops/delete_outpost_resolver.rs, make the unknown-id branch a success with no OutpostResolver member rather than ResourceNotFoundException; apply the same to src/ops/get_outpost_resolver.rs (200 with the member omitted). Keep ListOutpostResolvers unchanged — it must continue not to list the id.
Traces: route53resolver.get-outpost-resolver-not-found-after-delete.

Cause 3 of 3: writes against an AWS-managed DNS Firewall domain list are refused with the wrong error class and an invented message.
AWS: Smithy: UpdateFirewallDomains(FirewallDomainListId: ResourceId @required, Operation: ADD|REMOVE|REPLACE @required, Domains @required) models ResourceNotFoundException, ValidationException, AccessDeniedException, ConflictException, LimitExceededException (all HTTP 400); DeleteFirewallDomainList models ResourceNotFoundException and AccessDeniedException; ListFirewallDomains models AccessDeniedException and ResourceNotFoundException. Recorded behavior: a list with ManagedOwnerName set is not visible as a writable resource to the caller, so AWS hides it on the write path — UpdateFirewallDomains and DeleteFirewallDomainList against a managed list are refused HTTP 400 ResourceNotFoundException with message '[RSLVR-02025] Can’t find the resource with ID "<FirewallDomainListId>".' (fixed text, note the U+2019 typographic apostrophe in 'Can’t', with the id taken from the request), while ListFirewallDomains against the same list is refused HTTP 400 AccessDeniedException with the fixed message "You don't have a permission to list the domains inside a Route 53 Resolver DNS Firewall managed list." — and GetFirewallDomainList continues to return the list with its Status and DomainCount unchanged.
Emulator: UpdateFirewallDomains answers error code ValidationException with an invented message of the form 'Firewall domain list with ID "<id>" is managed by <owner> and its domains cannot be updated'. The replay reports: expected the AWS-managed list to be rejected ResourceNotFoundException, got 'ValidationException'. src/ops/update_firewall_domains.rs lines 255-267 build that ValidationException in the managed-list branch instead of reusing crate::state::firewall_domain_list_not_found; the same managed-list branch must be checked in src/ops/delete_firewall_domain_list.rs (ResourceNotFoundException, same [RSLVR-02025] message) and src/ops/list_firewall_domains.rs (AccessDeniedException, the permission message above) — the replay stops at the first assertion, so those two are unverified in this run but are the same cause, and a fix limited to UpdateFirewallDomains will not make the check pass.
Why: a client branching on the error code cannot tell 'this list is not yours to write' from 'your request was malformed'. ValidationException reads as a client-fixable input problem, so retry/repair logic rewrites the request and retries forever, and tooling that special-cases ResourceNotFoundException (to skip managed threat-intel lists) never takes that branch; the message text also leaks an emulator-specific sentence no AWS client has ever seen.
Fix: in the managed-list branches of services/service-com-amazonaws-route53resolver-route53resolver/src/ops/update_firewall_domains.rs and src/ops/delete_firewall_domain_list.rs, return ResourceNotFoundException built from the shared '[RSLVR-02025] Can’t find the resource with ID "<id>".' builder in src/state.rs, and in src/ops/list_firewall_domains.rs return AccessDeniedException with the fixed managed-list permission message. The managed list's stored Status, DomainCount and domains must be left untouched by every one of those refusals.
Traces: route53resolver.firewall-domain-list-aws-managed-immutable.
