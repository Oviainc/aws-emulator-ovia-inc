# CodeBuild sandboxes never provision: StartSandbox settles the session into FAULT at PROVISIONING so no sandbox ever reaches RUNNING, plus ListSandboxesForProject answers NotImplemented for an unknown project

> _Note: this issue was identified against the code base at commit `699f6ed7a7b73d87a9db3c950b6f69a120aa392c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartSandbox

## Description
Two distinct root causes in this service's sandbox surface, both grounded in failing behavioral checks of this run. NOTE for the fixer: this issue carries 2 causes — close BOTH before submitting.

Cause 1 of 2: StartSandbox mints a sandbox that can never become usable — its session settles into FAULT at the PROVISIONING phase instead of reaching RUNNING.
  AWS: Smithy (com.amazonaws.codebuild) models StartSandbox -> StartSandboxOutput{sandbox: Sandbox}, with errors AccountSuspendedException/InvalidInputException/ResourceNotFoundException (all HTTP 400). Sandbox.status is a String and Sandbox.currentSession is a SandboryySession with currentPhase/phases (SandboxSessionPhase.phaseStatus is StatusType) and Sandbox.timeoutInMinutes is documented as "How long, in minutes, from 5 to 2160 (36 hours), for CodeBuild to wait before timing out this sandbox if it does not get marked as completed" — i.e. a sandbox is expected to be a long-lived, live session, not something that terminates in under a second. Recorded behavior (from the checks' own re-recordings against real AWS): a sandbox started on an existing NO_SOURCE project transitions out of QUEUED and is reported by BatchGetSandboxes with status 'RUNNING' and currentSession.currentPhase == 'RUN_SANDBOX', and StartCommandExecution/StartSandboxConnection then work against it until StopSandbox.
  Emulator: the sandbox is persisted QUEUED and the clock-owed transition ends the session in FAULT about 500 ms later. BatchGetSandboxes reports status 'FAULT' with currentSession.status 'FAULT', currentSession.currentPhase 'COMPLETED' and phases [SUBMITTED SUCCEEDED, QUEUED SUCCEEDED, PROVISIONING FAULT, COMPLETED] — never RUNNING, never RUN_SANDBOX. Checks that poll for RUNNING therefore either assert on the FAULT status directly (codebuild.command-execution-lifecycle-in-sandbox: 'AssertionError: status=FAULT'; codebuild.sandbox-connection-invalid-after-stop: 'sandbox never reached RUNNING (last status=FAULT ...)') or never finish and are cut off by the harness ('Check timed out after 60.0s').
  Why: a client that starts a sandbox and waits for it to become connectable waits forever and then sees a terminal FAULT. Everything downstream of a live sandbox is unreachable: StartCommandExecution/BatchGetCommandExecutions (modeled with sandboxId + ResourceNotFoundException), StartSandboxConnection's ssmSession, the project-level timeoutInMinutes echo on the sandbox record, idle auto-stop, and the StopSandbox-then-reject boundary. No sandbox-based workflow can be exercised against this emulator at all.
  Fix: the sandbox state machine — services/service-com-amazonaws-codebuild-codebuild-20161006/src/state.rs (StoredSandbox::settle / SANDBOX_NOT_PROVISIONED_MESSAGE / SANDBOX_SETTLE_MILLIS) together with src/ops/start_sandbox.rs, which documents the FAULT outcome as deliberate ("Nothing in this emulator starts a sandbox container"). A sandbox must settle QUEUED -> PROVISIONING(SUCCEEDED) -> RUNNING with currentSession.currentPhase RUN_SANDBOX and stay there until StopSandbox or its timeoutInMinutes elapses, so the command-execution and connection operations have a live session to act on.
  Traces: codebuild.command-execution-lifecycle-in-sandbox, codebuild.sandbox-connection-invalid-after-stop, codebuild.sandbox-lifecycle-active-to-terminated, codebuild.command-execution-lifecycle-reaches-terminal-state, codebuild.codebuild-sandbox-command-execution-returns-the-commands-real-stdout, codebuild.sandbox-connection-token-ttl-expires, codebuild.sandbox-idle-timeout-auto-stop, codebuild.sandbox-timeout-minutes-preserved.

Cause 2 of 2: ListSandboxesForProject on a project name that does not exist returns the scaffold's NotImplemented error instead of the modeled not-found refusal.
  AWS: Smithy models ListSandboxesForProject(projectName @required, len 1..) with errors InvalidInputException and ResourceNotFoundException, both HTTP 400; ResourceNotFoundException is documented as "The specified Amazon Web Services resource cannot be found." Recorded behavior: a read of the sandboxes of an unknown project is rejected with error code ResourceNotFoundException (the recorded message, an example built from the request, is "The provided project arn:aws:codebuild:<region>:<account>:project/<name> does not exist.").
  Emulator: the call returns error code 'NotImplemented' (scaffold stub channel), so clients see an unmodeled error code for a plain not-found condition.
  Why: a client that distinguishes "no such project" from a server fault cannot: NotImplemented is not in this operation's modeled error set, boto3 surfaces it as an unexpected/retryable-looking failure, and the ResourceNotFoundException branch is never observable.
  Fix: services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/list_sandboxes_for_project.rs — implement the operation and raise ResourceNotFoundException (HTTP 400) when projectName names no stored project. Overlap note: this run also files a separate stub issue for the unimplemented ListSandboxesForProject operation ("Implement codebuild ListSandboxesForProject: unimplemented scaffold stub", raised from the checkout because the same stub blocks codebuild.list-sandboxes-for-project-reflects-start-order); the two checks named here were NOT marked as owned by it, and they pin the specific error-code requirement above, so implementing that op must also satisfy this cause and the two can be closed together.
  Traces: codebuild.start-sandbox-account-suspended-blocked, codebuild.start-sandbox-suspended-account-blocked.

## Evidence
Cause 1 — expected: BatchGetSandboxes(ids=[<id>]) reports status 'RUNNING' with currentSession.currentPhase 'RUN_SANDBOX' within the polling window (checks allow 240-300s). Actual: status 'FAULT' ~0.5s after StartSandbox, e.g. {'id': '<project>:<uuid>', 'status': 'FAULT', 'currentSession': {'status': 'FAULT', 'currentPhase': 'COMPLETED', 'phases': [SUBMITTED/SUCCEEDED, QUEUED/SUCCEEDED, PROVISIONING/FAULT, COMPLETED]}} (codebuild.sandbox-connection-invalid-after-stop); 'AssertionError: status=FAULT' (codebuild.command-execution-lifecycle-in-sandbox); six further sandbox checks were cut off by the harness at 60s while polling for RUNNING. src/ops/start_sandbox.rs states the design explicitly: the QUEUED transition "ends the sandbox's session in FAULT with a phase context saying why — see crate::state::SANDBOX_NOT_PROVISIONED_MESSAGE".
Cause 2 — expected: ClientError code 'ResourceNotFoundException' (HTTP 400) from list_sandboxes_for_project(projectName=<unknown>). Actual: code 'NotImplemented' ('AssertionError: unexpected code: NotImplemented' / "expected ResourceNotFoundException, got 'NotImplemented'").
