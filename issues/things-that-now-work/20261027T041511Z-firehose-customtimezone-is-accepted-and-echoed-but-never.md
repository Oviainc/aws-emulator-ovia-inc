=== Cause 1 of 1: the destination's CustomTimeZone does not move the digits the delivery prefix expands to ===
Failing check: firehose.custom-time-zone-shifts-the-timestamp-prefix-expansion.
AWS: Smithy (model_path services/service-com-amazonaws-firehose-firehose-20150804/smithy-model/com-amazonaws-firehose-firehose-20150804.json) ExtendedS3DestinationConfiguration.CustomTimeZone, target CustomTimeZone, @length 0..50, @pattern ^$|[a-zA-Z/_]+$, doc "The time zone you prefer. UTC is the default."; ExtendedS3DestinationConfiguration.Prefix (@length 0..1024) is documented as "The \"YYYY/MM/DD/HH\" time format prefix is automatically used for delivered Amazon S3 files" and supports the !{timestamp:<java-pattern>} namespace. So the time-prefix expansion is performed in the destination's configured zone, defaulting to UTC when CustomTimeZone is absent or empty: two DirectPut streams fed the same payload at the same instant, one with no CustomTimeZone and one with CustomTimeZone set to a zone whose offset is fixed, expand the same !{timestamp:...} pattern to digits that differ by exactly that zone's UTC offset (for the check's zone, Asia/Tokyo, that is +09:00 year round — Japan observes no DST). Hypothesis (the check labels it so, and neither the model nor a recording states it): the same zone also moves the object-name suffix timestamp <stream>-<version>-yyyy-MM-dd-HH-mm-ss-<uuid>.
Emulator: CustomTimeZone is accepted at CreateDeliveryStream (no validation or use of it in services/service-com-amazonaws-firehose-firehose-20150804/src/ops/create_delivery_stream.rs) and the delivery writer never reads it: the prefix expander resolves every !{timestamp:<pattern>} through format_timestamp, which calls utc_fields(at) unconditionally, and the automatic "<year>/<month>/<day>/<hour>/" segment appended when a Prefix carries no expression is built from utc_fields too. There is no custom_time_zone anywhere in the delivery module. The consequence recorded on an earlier replay of this same check: both legs expanded to the identical instant, "CustomTimeZone='Asia/Tokyo' did not shift the expanded timestamp prefix: the UTC-default leg expanded to ...T08:00:00+00:00 (key 'tz-utc/d=<date>/h=<hour>/...') and the Asia/Tokyo leg to the same instant (key 'tz-tokyo/d=<date>/h=<hour>/...'), a delta of 0:00:00, expected exactly 9:00:00" — the dates/hours there are that run's wall clock, the requirement is only the fixed offset between the two legs.
Why: the delivered prefix is the partition layout, i.e. a contract with the query layer. A table partitioned on local-time digits has every row placed in the UTC partition on the emulator, so date-ranged queries, Glue/Athena partition projection, local-day lifecycle rules and log-shipper routing all select the wrong objects, and the only observable effect of setting CustomTimeZone is unverifiable: the member round-trips through DescribeDeliveryStream while changing nothing about where data lands.
Fix: the prefix-expansion component of the Firehose delivery path (services/service-com-amazonaws-firehose-firehose-20150804/src/state/delivery.rs — expand_prefix, format_timestamp and the automatic-time-prefix branch at its end, all of which today go through utc_fields) must take the zone from the destination configuration in force at the flush (ExtendedS3DestinationConfiguration/ExtendedS3DestinationDescription.CustomTimeZone, as the delivery already reads BucketARN/Prefix/BufferingHints from it), defaulting to UTC when the member is absent or empty; the S3Target carried into the writer needs that zone alongside prefix/error_output_prefix. If the suffix leg is found not to move on real AWS, only that leg is wrong — the prefix leg stands on its own.
Traces: firehose.custom-time-zone-shifts-the-timestamp-prefix-expansion.
