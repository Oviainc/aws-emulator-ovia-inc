# lambda: CreateFunction(Publish=true) answers the version-qualified ARN, and GetFunctionScalingConfig never drops RequestedFunctionScalingConfig once applied

> _Note: this issue was identified against the code base at commit `6ad1863e43f5664fac16df5e246702230b6849d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

> _Split note: this report was filed as a bundle of THREE causes. Causes 2 and 3 — the two below, keeping their original numbering — are fixed, and the two checks above pass. Cause 1 of 3 (a durable execution started through `Invoke` is recorded but never EXECUTES) was NOT fixed and is re-filed on its own, with its own six replay keys, as `issues/things-that-do-not-work/20261027T203721Z-lambda-a-durable-execution-is-accepted-but-never-runs.md`: it needs the function's own deployment package to run in-process, which this emulator has no runtime for._

## Operation
CreateFunction

## Description
Two root causes in the `lambda` service, both grounded in failing behavioral checks of this suite.

=== Cause 2 of 3: CreateFunction with Publish=true reports the VERSION-QUALIFIED ARN in FunctionArn, where AWS reports the unqualified function ARN ===
Failing check: lambda.delete-capacity-provider-with-attached-function-rejected.

AWS: CreateFunction's output is FunctionConfiguration, whose FunctionArn is documented only as "The function's Amazon Resource Name (ARN)" and targets NameSpacedFunctionArn (a pattern that PERMITS a qualifier), so the model does not settle this — recorded behavior only: AWS answers CreateFunction with the UNQUALIFIED function ARN (arn:<partition>:lambda:<region>:<account>:function:<name>) and reports the published version separately in the Version member ("1"). The check's oracle depends on exactly that: it forms the version ARN as CreateFunction's FunctionArn with ":1" appended and compares it to the version ARN AWS names in DeleteCapacityProvider's ResourceConflictException message. The message itself is a requirement: HTTP 409, code `ResourceConflictException`, message `The capacity provider is currently in use by <N> function. To delete this capacity provider, first remove its association with <version-arn>.` — the fixed text is everything but <N> (the number of associated functions, from state) and <version-arn> (the qualified ARN of the associated function version, from state).

Emulator: CreateFunction(..., Publish=True) returned FunctionArn = `arn:aws:lambda:<region>:<account>:function:<name>:1` — the qualified ARN — because the handler answered `stored.configuration(&reported_version, &config)` and FunctionRecord::configuration sets function_arn to versioned_arn(version), which appends `:<version>` for anything but $LATEST. The DeleteCapacityProvider refusal itself is correct (409 ResourceConflictException with exactly the message text above, naming the version ARN `...:function:<name>:1`), but the client's notion of the function ARN was already one qualifier off, so the two could not agree: the check computed the expected version ARN as `...:function:<name>:1:1` and reported `AssertionError: unexpected DeleteCapacityProvider message: 'The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with arn:aws:lambda:<region>:<account>:function:<name>:1.'`

Why: every client that creates a function with Publish=true and then uses the returned FunctionArn gets a version-pinned ARN where AWS gives it the function's own ARN. It writes that string into IAM and resource policies, event source mappings, API Gateway and EventBridge targets, CloudFormation outputs and CloudWatch dimensions — all of which then address `<fn>:1` instead of `<fn>`, or, when the client appends its own qualifier, a nonexistent `<fn>:1:<qualifier>`. The divergence is silent: nothing refuses the malformed ARN at the point of use.

Fix: the CreateFunction handler's response construction (and the shared FunctionRecord::configuration it reads through) — the ARN reported for a create must be the function's unqualified ARN with the published version carried only in Version, while PublishVersion and qualified reads keep reporting the qualified form.

Traces: lambda.delete-capacity-provider-with-attached-function-rejected. Handler: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/create_function.rs (the Publish arm and the final configuration call); state: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (FunctionRecord::configuration -> versioned_arn).

=== Cause 3 of 3: GetFunctionScalingConfig always reports RequestedFunctionScalingConfig, so the "request fully applied" signal never appears and a Managed-Instances scaling request can never be observed to converge ===
Failing check: lambda.put-function-scaling-config-then-capacity-provider-list-reflects.

AWS: Smithy GetFunctionScalingConfig (GET /2025-11-30/functions/{FunctionName}/function-scaling-config, required FunctionName and Qualifier) has output members FunctionArn, AppliedFunctionScalingConfig and RequestedFunctionScalingConfig, both of type FunctionScalingConfig. Recorded behavior only (this check's oracle, stated in the check itself): once a PutFunctionScalingConfig request is FULLY APPLIED, `RequestedFunctionScalingConfig` is omitted from the response entirely — its ABSENCE, not its equality with the applied configuration, is the convergence signal a client polls on — while AppliedFunctionScalingConfig then reports the bounds in effect ({MinExecutionEnvironments: 1, MaxExecutionEnvironments: 2} for the request this check makes).

Emulator: the member was unconditionally present. FunctionScalingConfigRecord::reported built `requested_function_scaling_config: Some(self.requested.clone())` with no dependence on whether the request had been applied, so after PutFunctionScalingConfig the response carried RequestedFunctionScalingConfig forever. The check's bounded poll for the member's absence could therefore never be satisfied and the runner reported `Check timed out after 60.0s`.

Why: a client that reconciles Lambda Managed Instances scaling bounds has no way to learn that its request landed. Code written against AWS polls GetFunctionScalingConfig until RequestedFunctionScalingConfig disappears and then reads AppliedFunctionScalingConfig; against the emulator that loop never terminates, so deployments and autoscaling reconcilers that gate on convergence hang or time out even though the bounds were in fact applied.

Fix: the GetFunctionScalingConfig response construction in the lambda service's scaling-config state (FunctionScalingConfigRecord::reported) — once the requested configuration has become the applied one, the response must omit RequestedFunctionScalingConfig and report only FunctionArn plus AppliedFunctionScalingConfig; it should be reported only while a request is still outstanding. Related open issue 20261025T100455Z-lambda-getfunctionscalingconfig-accepts-a-function-with-no-capacity.md covers two different causes of the same operation (a 200 for a function with no capacity-provider configuration, and the missing service-managed default for a never-configured version); it does not cover the member never being dropped after a request IS applied.

Traces: lambda.put-function-scaling-config-then-capacity-provider-list-reflects. State: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (FunctionScalingConfigRecord::request / ::materialize / ::reported); handler: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/get_function_scaling_config.rs.

## Evidence
Cause 2 — expected (AWS, recorded): CreateFunction(..., Publish=True) answers FunctionArn = `arn:aws:lambda:<region>:<account-id>:function:<function-name>` with Version = "1"; DeleteCapacityProvider on a provider that version runs on is refused HTTP 409 `ResourceConflictException` with message `The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with <CreateFunction FunctionArn>:1.` — so the ARN in the message equals the created function's ARN plus ":1".
Actual (emulator, before the fix): the refusal's message was `The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with arn:aws:lambda:us-west-2:000000000000:function:sim2real-neg-cp-fn-7cb2dfc14610:1.` while CreateFunction had already returned that same qualified string as the function's FunctionArn, so the version ARN the client forms was `...:sim2real-neg-cp-fn-7cb2dfc14610:1:1`. Reported by the replay as:
  check_lambda_delete_capacity_provider_with_attached_function_rejected.py, line 110, in run
  AssertionError: unexpected DeleteCapacityProvider message: 'The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with arn:aws:lambda:us-west-2:000000000000:function:sim2real-neg-cp-fn-7cb2dfc14610:1.'
The region, account id and function name above are values that run filled in; the requirement is that CreateFunction's FunctionArn carry no version qualifier, and that the 409 message's fixed text be exactly as quoted with the association's version ARN taken from state.

Cause 3 — expected (AWS, recorded): after PutFunctionScalingConfig(FunctionName=<mi fn>, Qualifier="1", FunctionScalingConfig={MinExecutionEnvironments:1, MaxExecutionEnvironments:2}) has been fully applied, GetFunctionScalingConfig(FunctionName=<mi fn>, Qualifier="1") returns a response with NO RequestedFunctionScalingConfig member and AppliedFunctionScalingConfig == {"MinExecutionEnvironments": 1, "MaxExecutionEnvironments": 2}.
Actual (emulator, before the fix): RequestedFunctionScalingConfig was present in every response for the rest of the record's life — `FunctionScalingConfigRecord::reported` set it to `Some(self.requested.clone())` unconditionally — so the check's poll for its absence (600 s budget, 15 s interval) could never succeed and the runner cut the check off: `Error: Check timed out after 60.0s` for lambda.put-function-scaling-config-then-capacity-provider-list-reflects. Every upstream call in that check succeeded (ec2 network, both IAM roles, CreateCapacityProvider reaching Active, CreateFunction with CapacityProviderConfig reporting State=ActiveNonInvocable, PublishVersion, PutFunctionScalingConfig).

## Steps to Reproduce
Cause 2: 1) ec2:CreateVpc/CreateSubnet/CreateSecurityGroup. 2) iam:CreateRole for the capacity-provider operator (AWSLambdaManagedEC2ResourceOperator) and a Lambda execution role (AWSLambdaBasicExecutionRole). 3) lambda:CreateCapacityProvider with that VpcConfig, PermissionsConfig.CapacityProviderOperatorRoleArn, InstanceRequirements.Architectures=['x86_64'] and CapacityProviderScalingConfig {MaxVCpuCount:16, ScalingMode:'Auto'}; wait for State=Active. 4) lambda:CreateFunction(Runtime='python3.13', Publish=True, CapacityProviderConfig.LambdaManagedInstancesCapacityProviderConfig.CapacityProviderArn=<cp arn>, ...) and inspect the returned FunctionArn: AWS returns the UNQUALIFIED ARN with Version='1'; the emulator returned `...:function:<name>:1`. 5) lambda:PutFunctionScalingConfig(Qualifier='1', {MinExecutionEnvironments:1, MaxExecutionEnvironments:2}) and wait for the version to be Active. 6) lambda:DeleteCapacityProvider(CapacityProviderName=<cp>) and compare the 409 message's ARN with `CreateFunction FunctionArn + ':1'` — they agree on AWS and differed by one qualifier on the emulator.

Cause 3: steps 1-3 of Cause 2, then 4) lambda:CreateFunction with CapacityProviderConfig and WITHOUT Publish; wait until State=ActiveNonInvocable. 5) lambda:PublishVersion -> '1'. 6) lambda:PutFunctionScalingConfig(FunctionName=<fn>, Qualifier='1', FunctionScalingConfig={MinExecutionEnvironments:1, MaxExecutionEnvironments:2}). 7) poll lambda:GetFunctionScalingConfig(FunctionName=<fn>, Qualifier='1') until 'RequestedFunctionScalingConfig' is absent from the response: on AWS it disappears once the request is applied and AppliedFunctionScalingConfig reports {1, 2}; on the emulator the member was present in every response and the poll never terminated.
