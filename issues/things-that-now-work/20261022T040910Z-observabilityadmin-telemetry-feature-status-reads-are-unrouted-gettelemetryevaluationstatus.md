# observabilityadmin telemetry feature-status reads are unrouted: GetTelemetryEvaluationStatus and GetTelemetryEnrichmentStatus answer NotImplemented instead of a 200 status document (2 causes)

> _Note: this issue was identified against the code base at commit `6d3a954d57304c873e4e6a3ccc977c1ac1664bbd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTelemetryEvaluationStatus

## Description
Two modeled, service-bound read operations of the observabilityadmin telemetry-feature surface are not served at all. Both answer an emulator-level `NotImplemented` whose message names the HTTP route rather than a scaffold ("operation POST /<Name> is not implemented in this emulator"), and neither has a handler file under services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/ — so this is a routing/handler gap distinct from the scaffolded-but-unimplemented stubs the suite already filed separately (ListCentralizationRulesForOrganization, CreateTelemetryPipeline, TestTelemetryPipeline, ValidateTelemetryPipelineConfiguration). Because both operations are the feature-enablement gate that every telemetry-rule check must pass through first, these two causes block 11 of the 18 behavioral checks in this service, including every telemetry-rule lifecycle, filter and validation check.

Cause 1 of 2: GetTelemetryEvaluationStatus is not routed.
AWS: Smithy model (com-amazonaws-observabilityadmin-observabilityadmin.json) binds GetTelemetryEvaluationStatus to the service with http {method: POST, uri: "/GetTelemetryEvaluationStatus"}, code 200 (defaulted), input shape Unit, output shape GetTelemetryEvaluationStatusOutput with members Status (enum Status), FailureReason, HomeRegion (Region, @length min 1) and RegionStatuses (list). It is @readonly. Its only modeled errors are AccessDeniedException (400), InternalServerException (500) and TooManyRequestsException (429) — NotImplemented is not among them, and there is no modeled condition under which a well-formed call fails. The checks use it as the poll for the account's telemetry-evaluation feature reaching RUNNING after StartTelemetryEvaluation (which IS routed per the model: POST /StartTelemetryEvaluation).
Emulator: every call returns the emulator's NotImplemented error with message "operation POST /GetTelemetryEvaluationStatus is not implemented in this emulator". No handler file get_telemetry_evaluation_status.rs exists in the service's src/ops/ directory.
Why: a client cannot read, or wait on, the telemetry-evaluation feature status at all. Worse, because the telemetry-rule APIs are gated behind that feature being RUNNING, every client workflow that enables the feature and then creates/gets/updates/lists/deletes a telemetry rule dies at the first poll with an unmodeled error code. A caller that retries on the service's modeled throttling/server errors will not retry on NotImplemented, so the failure is terminal rather than transient, and no telemetry-rule behavior behind the gate is reachable or observable.
Fix: the operation's handler — add the GetTelemetryEvaluationStatus handler and its route registration in the observabilityadmin service crate (src/ops/, alongside the already-present telemetry-evaluation state), returning a 200 GetTelemetryEvaluationStatusOutput whose Status reflects the account's stored telemetry-evaluation state as set by StartTelemetryEvaluation/StopTelemetryEvaluation, with HomeRegion and RegionStatuses derived from the Regions/AllRegions that Start was called with, and FailureReason populated only in the failure states.
Traces: observabilityadmin.get-telemetry-rule-not-found, observabilityadmin.list-resource-telemetry-resource-type-filter-invariant, observabilityadmin.list-telemetry-rules-name-prefix-filter, observabilityadmin.telemetry-evaluation-start-stop-lifecycle, observabilityadmin.telemetry-rule-concurrent-update-conflict, observabilityadmin.telemetry-rule-create-get-delete-lifecycle, observabilityadmin.telemetry-rule-duplicate-name-conflict-rejected, observabilityadmin.telemetry-rule-invalid-resource-type-enum-rejected, observabilityadmin.telemetry-rule-regions-allregions-mutually-exclusive-rejected, observabilityadmin.telemetry-rule-update-persists-configuration.

Cause 2 of 2: GetTelemetryEnrichmentStatus is not routed.
AWS: Smithy model binds GetTelemetryEnrichmentStatus with http {method: POST, uri: "/GetTelemetryEnrichmentStatus"}, code 200 (defaulted), input Unit, output GetTelemetryEnrichmentStatusOutput with Status (enum TelemetryEnrichmentStatus) and AwsResourceExplorerManagedViewArn (@length 20..2048, @pattern ^arn:aws([a-z0-9\\-]+)?:resource-explorer-2:([a-z0-9\\-]+)?:([0-9]{12})?:managed-view/(.+)$). It is @readonly. Modeled errors: AccessDeniedException (400), InternalServerException (500), ResourceNotFoundException (404), TooManyRequestsException (429) — the 404 being the documented answer before the enrichment feature has ever been started. Recorded behavior in the check: a repeated StopTelemetryEnrichment on an already-Stopped feature is an idempotent no-op that leaves Status exactly Stopped (StopTelemetryEnrichment is modeled with http code 202 and a ConflictException, but the recording shows no conflict for the redundant stop), and the status read is how that invariant is observed.
Emulator: every call returns NotImplemented with message "operation POST /GetTelemetryEnrichmentStatus is not implemented in this emulator". No handler file get_telemetry_enrichment_status.rs exists in the service's src/ops/ directory.
Why: a client has no way to observe the telemetry-enrichment feature's state, so it cannot distinguish "never started" (AWS: 404 ResourceNotFoundException) from Stopped/Running, and cannot confirm that a redundant Stop was the no-op AWS performs. Any client that gates enrichment setup on the current status sees an unmodeled, non-retryable error instead of either the 200 document or the modeled 404.
Fix: the operation's handler — add the GetTelemetryEnrichmentStatus handler and its route registration in the observabilityadmin service crate (src/ops/), returning 200 with Status from the account's stored enrichment state and the managed-view ARN when one exists, and the modeled 404 ResourceNotFoundException when the feature has never been started; the enrichment state must also be kept consistent by the Start/Stop handlers so a second Stop leaves Status Stopped.
Traces: observabilityadmin.telemetry-enrichment-double-stop-is-an-idempotent-no-op.

## Steps to Reproduce
1. Boot the emulator from this checkout and point a botocore client at it: client = session.client("observabilityadmin", endpoint_url=<emulator>).
2. Cause 1: call client.start_telemetry_evaluation(Regions=[<region>]) and then client.get_telemetry_evaluation_status(). The Get fails with ClientError code NotImplemented and message "operation POST /GetTelemetryEvaluationStatus is not implemented in this emulator" instead of returning HTTP 200 with Status/HomeRegion/RegionStatuses. Real AWS returns a 200 status document and reports the feature progressing to RUNNING.
3. Cause 2: call client.get_telemetry_enrichment_status() on a fresh account. It fails with code NotImplemented and message "operation POST /GetTelemetryEnrichmentStatus is not implemented in this emulator" instead of either HTTP 200 with Status (Stopped/Running plus AwsResourceExplorerManagedViewArn) or the modeled 404 ResourceNotFoundException for a never-started feature. Then call client.stop_telemetry_enrichment() twice and re-read the status: the redundant Stop must be an idempotent no-op leaving Status exactly Stopped, which is unobservable today.
4. Replay the checks in trace_ids to confirm: all 11 currently die on their first status read, before any telemetry-rule assertion runs.
