=== Cause 1 of 2: the announced DataEndpoint is published as https:// on a TLS-only listener with a self-signed certificate, so every discovered-endpoint call (PutMedia ingest and all media/archived-media reads) fails TLS verification before a request is sent ===
AWS: Smithy com.amazonaws.kinesisvideo#GetDataEndpoint, POST /getDataEndpoint -> 200; input APIName required (enum GET_CLIP | GET_DASH_STREAMING_SESSION_URL | GET_HLS_STREAMING_SESSION_URL | GET_IMAGES | GET_MEDIA | GET_MEDIA_FOR_FRAGMENT_LIST | LIST_FRAGMENTS | PUT_MEDIA) plus StreamName (len 1..256, pattern ^[a-zA-Z0-9_.-]+$) or StreamARN (ResourceARN); output DataEndpoint, documented 'The endpoint value. Operation doc: 'Gets an endpoint for a specified stream for either reading or writing ... The returned endpoint does not have the API name appended.' Beyond the shape, recorded behavior only: the value is a bare http(s) origin (scheme and host, empty path) that the client then ADDRESSES with a DEFAULT-configured client and no extra trust material — on AWS the announced host serves a publicly trusted certificate, so POST /putMedia and /getMedia, /listFragments, /getMediaForFragmentList, /getClip all connect. The requirement is operational: the announced origin must be dialable, as-is, by the same client that just made the control call. Hosts, ports, labels and certificates are per-environment and are not themselves the requirement.
Emulator: GetDataEndpoint opens a core resource listener and announces `https://` + that listener's authority (services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs:159-208, the scheme hard-coded at :188-191). This is not the runner's trust configuration: the same process reaches the CONTROL-plane origin of the same emulator successfully in every one of these checks (CreateStream, DescribeStream and GetDataEndpoint all succeed, and in kinesisvideo.put-media-against-control-plane-host-rejected a raw hand-built POST /putMedia to the control origin completes) — only the origin GetDataEndpoint announces is undiallable.
Why: the entire documented producer/consumer path of Kinesis Video Streams is unusable through the only way to find it. A client does exactly what the docs say — kvssink, the KVS producer/consumer SDKs, or boto3 with endpoint_url=DataEndpoint — and gets a certificate-verification failure instead of a connection, so PutMedia ingest, GetMedia, ListFragments, GetMediaForFragmentList and GetClip cannot be exercised, and none of the refusal contracts on those paths (absent stream, malformed container, undeclared track, unknown track number, regressed cluster timecode, missing x-amz-content-sha256, future producer timestamp, wrong plane) can be observed. A client cannot work around it without disabling TLS verification, which no AWS SDK does by default.
Fix: GetDataEndpoint's endpoint projection — ensure_data_endpoint/DataPlaneEndpoint in services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs (the plane listener it opens and the scheme it prefixes), together with whatever the core offers for serving a plane on a transport a default client already trusts: announce the plane on the same scheme/trust the emulator's own front door is reached on (keeping the planes distinct by port), rather than hard-coding https:// over a self-signed resource listener. Keep the bare-origin, empty-path, per-plane-distinct form; change only the transport the announced origin is served on.

=== Cause 2 of 2: POST /putMedia sent to the CONTROL-plane origin is served and ingests the media (HTTP 200 with an acknowledgement stream) instead of being refused HTTP 404 with the body <UnknownOperationException/> and no x-amzn-ErrorType ===
AWS: recorded behavior only (PutMedia is in no AWS SDK model — the control-plane model binds only the control operations to the control endpoint, which is why GetDataEndpoint exists). The recording shows the control-plane origin does not route /putMedia at all: HTTP 404, response body exactly the bare element `<UnknownOperationException/>` (that text is fixed — it carries nothing from the request: no stream name, no ARN, no path), and NO x-amzn-ErrorType response header, because the path is refused before any operation is identified. Nothing is ingested: the stream's archive stays empty (ListFragments on the discovered read endpoint returns no fragments), while the identical bytes sent to the discovered PUT_MEDIA origin persist one fragment.
Emulator: the control-plane origin serves POST /putMedia as if it were the ingest plane and ARCHIVES the media. Replay: expected 404, got `HTTP 200 (x-amzn-ErrorType None)` with the acknowledgement stream `{"EventType":"BUFFERING","FragmentTimecode":0,"FragmentNumber":"1"}` / `{"EventType":"RECEIVED",...}` / `{"EventType":"PERSISTED",...}` (the fragment numbers and timecodes there are per-run values; the 200 and the ingestion are the divergence). The cause is that no address of this emulator is scoped to a plane: the front door resolves the target service from the SigV4 signing name and the modelled path and ignores the host entirely — stated as intended in services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs:21-27 ('every address of this emulator is served by its one front door ... Each plane's address is reachable and serves this emulator's whole surface') — so the ingest route is bound on the control-plane origin too.
Why: endpoint discovery becomes unverifiable and misrouting silently succeeds. A producer that skips GetDataEndpoint, caches a stale endpoint, or is misconfigured to the control endpoint is told its media was PERSISTED instead of being refused, so the error that makes a KVS producer re-discover its endpoint never fires and operators cannot tell a correctly addressed producer from a broken one. It also means the wrong-plane refusal contract the sibling checks assert can never be observed, and a client that trusts the 404 to mean 'nothing was ingested' sees fragments appear in the stream anyway.
Fix: route scoping in the kinesisvideo front door together with the plane addressing in src/state/data_endpoint.rs — bind the ingest route (/putMedia) and the archived-media routes only on the origin of the plane that owns them, and answer an unrouted path on the control-plane origin with HTTP 404, body `<UnknownOperationException/>` and no x-amzn-ErrorType header, ingesting nothing.
