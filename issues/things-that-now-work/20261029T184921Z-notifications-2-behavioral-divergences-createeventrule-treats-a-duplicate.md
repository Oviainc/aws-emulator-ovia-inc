# notifications: 2 behavioral divergences — CreateEventRule treats a duplicate (source, eventType) as an idempotent hit instead of ConflictException, and DisassociateChannel's not-found message is not AWS's sentence

> _Note: this issue was identified against the code base at commit `92c3b140342b1bc1fab2a232b8cee3f25ea78ff5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEventRule

## Description
Replaying the simparity-behavioral-aws-v1 suite against the emulator produced 5 failures in this service. Three of them (cloudwatch-alarm-state-change-delivers-notification-event, delete-event-rule-removes-it, event-rule-update-regions-persisted) are marked ALREADY FILED against the unimplemented ListNotificationEvents / DeleteEventRule / UpdateEventRule scaffold stubs and are NOT part of this issue. The remaining TWO are net-new and are TWO SEPARATE root causes; both must be closed before this issue is submitted.

Cause 1 of 2: CreateEventRule does not enforce the per-configuration uniqueness of the (source, eventType) pair — it silently serves every duplicate create as an idempotent hit on the first rule.
AWS: Smithy (services/service-com-amazonaws-notifications-notifications/smithy-model/com-amazonaws-notifications-notifications.json): CreateEventRule, POST /event-rules, @http code 201, @idempotent; required input members notificationConfigurationArn (pattern ^arn:[a-z-]{3,10}:notifications::[0-9]{12}:configuration/[a-z0-9]{27}$), source (@length 1..36, pattern ^aws.([a-z0-9\-])+$), eventType (@length 1..128), regions (@length min 1); eventPattern optional (@length 0..4096). Modelled errors include ConflictException (HTTP 409, "Updating or deleting a resource can cause an inconsistent state"). The model does not spell out WHICH pair is unique, so the uniqueness rule itself is recorded behavior only: the recording shows a second CreateEventRule naming an (source, eventType) pair a rule of that same NotificationConfiguration already covers being REFUSED with ConflictException (409) even when eventPattern and regions differ — so a rule for that pair already exists and a second one cannot be created. AWS's @idempotent therefore covers a RETRY of the identical request, not the creation of a second rule for an already-covered pair, and a burst of N concurrent creates for one pair resolves to exactly ONE created rule (one 201 with a fresh EventRuleArn) and N-1 ConflictException refusals, with the single winner being the only rule ListEventRules reports for that pair.
Emulator: the handler never looks for an existing rule on the (configuration, source, eventType) pair at all. It asks crate::state::matching_event_rule for a rule matching the FULL request — configuration + source + eventType + eventPattern + regions-as-a-set — and when one matches returns that rule's existing arn with a 201 success; when none matches it inserts a new rule. ConflictException is never constructed by this handler. Five concurrent creates for source=aws.ec2 / eventType="EC2 Instance State-change Notification" against one configuration therefore all answered 201 ok and all five returned the SAME EventRuleArn (…/configuration/<configId>/rule/<ruleId>): zero refusals, five winners.
Why: a client that relies on CreateEventRule being the serialization point for a rule mistakes an idempotent echo for a creation. Two independent callers (or two racing control loops) each believe they own a distinct EventRule and each hold what is actually the same arn; one of them then deletes or updates "its" rule and silently destroys the other's. Conversely the refusal AWS uses to tell a caller "this pair is already covered, read the existing rule" never arrives, so error-handling paths keyed on ConflictException (back off, re-read, reconcile) are dead code against the emulator, and a create whose eventPattern/regions differ from the existing rule's is quietly accepted as a second rule where AWS rejects it — the emulator is strictly more permissive than AWS on this operation.
Fix: the duplicate-detection predicate behind this operation — the (configuration, source, eventType) lookup in the service's state plus the branch in the operation's handler that decides between echoing and refusing. The handler must distinguish a true idempotent retry (every member of the request, including eventPattern and the regions set, agrees with the stored rule) from a conflicting duplicate (the pair is already covered but the request differs), answering ConflictException (HTTP 409) for the latter, and must take the pair lock for the whole check-then-insert so concurrent creates cannot both pass the check. Citations: src/ops/create_event_rule.rs (the `existing`/`matching_event_rule` branch, ~lines 240-288, and the lack of any ConflictException construction) and src/state.rs (matching_event_rule, ~line 908, whose own doc defines sameness as "every member they carry agrees").
Traces: notifications.concurrent-event-rule-creation-yields-distinct-rules (asserted exactly one winner and 4 ConflictException losers; got 5 'ok' results all carrying one identical rule arn).

Cause 2 of 2: DisassociateChannel refuses a never-associated channel with the right code but the wrong message sentence.
AWS: Smithy: DisassociateChannel, POST /channels/disassociate/{arn}, @idempotent, empty output; required arn (@httpLabel, pattern ^arn:[a-z-]{3,10}:(chatbot|consoleapp|notifications-contacts):[a-zA-Z0-9-]*:[0-9]{12}:[a-zA-Z0-9-_.@]+/[a-zA-Z0-9/_.@:-]+$) and notificationConfigurationArn; modelled errors include ResourceNotFoundException (HTTP 404, "Request references a resource which does not exist"). The message text is not in the model, so it is recorded behavior only: for a Channel that EXISTS but was never associated with the named NotificationConfiguration, AWS answers ResourceNotFoundException (404) with the message `channel with arn <channelArn> not found`. Fixed text: the lowercase words "channel with arn " and " not found"; the one variable part is <channelArn>, taken verbatim from the request's `arn` member. Note AWS states the missing resource as the CHANNEL (it does not mention the configuration arn at all), which is the same `<resource> with <identifier> <value> not found` sentence this service's other not-found refusals use.
Emulator: the code and status are correct (ResourceNotFoundException / 404) but the handler hand-rolls a different sentence: `Channel <channelArn> is not associated with NotificationConfiguration <configurationArn>` — capitalised "Channel", the phrase "is not associated with" instead of "not found", no "with arn" identifier label, and an extra variable part (the configuration arn) AWS does not include. Observed: expected 'channel with arn arn:aws:notifications-contacts::<account>:emailcontact/<contactId> not found', got 'Channel arn:aws:notifications-contacts::<account>:emailcontact/<contactId> is not associated with NotificationConfiguration arn:aws:notifications::<account>:configuration/<configId>'.
Why: the error message is part of the response contract. A client, SDK retry/classification wrapper or test that matches on AWS's wording (or on the uniform `... with arn ... not found` sentence the rest of this service emits) does not recognise the emulator's string, so a parity test passes on AWS and fails here, and log/alert matchers keyed to AWS's phrasing never fire. It also leaks the configuration arn into a message AWS keeps scoped to the channel.
Fix: the message construction in this operation's handler, which should route through the service's single not-found sentence helper (adding the missing `channel` resource label beside the existing ones) instead of formatting its own string, so this refusal reads the same way as every other not-found in the service. Citations: src/ops/disassociate_channel.rs (the ResourceNotFoundException built at ~lines 178-189) and src/state.rs (not_found_message, ~line 1312, `format!("{resource} with {identifier} {value} not found")`; labels HUB_RESOURCE_LABEL / CONFIGURATION_RESOURCE_LABEL / EVENT_RULE_RESOURCE_LABEL / ARN_IDENTIFIER_LABEL, ~lines 1275-1290 — there is no `channel` label yet).
Traces: notifications.disassociate-channel-not-associated-rejected (code assertion passed, message assertion failed).

No open issue covers either cause. The one open notifications issue, 20261029T174835Z-notifications-3-wire-divergences-managed-catalog-short-and, is about the managed-configuration catalog seed and the 200-vs-204 success status of TagResource/UntagResource — different operations and different causes.
