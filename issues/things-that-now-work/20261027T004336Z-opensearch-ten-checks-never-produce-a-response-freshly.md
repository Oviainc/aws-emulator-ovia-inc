# opensearch: ten checks never produce a response — freshly created domains/packages/associations/VPC endpoints are never reported settled on the read that follows their create, and the domain REST data plane is still unserved

> _Note: this issue was identified against the code base at commit `88eb145164ed6e7175261f755ebef46622c173d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDomain

## Description
Two root causes, both of which end in the same symptom: the emulator answers nothing the check can assert on, because a bounded readiness poll never observes its terminal condition and the check is killed at the suite's 60 s budget. A fixer must close BOTH before submitting.

=== Cause 1 of 2: a just-created domain / package / domain-package association / VPC endpoint is not reported settled on the read that immediately follows its create, so every AWS-sized readiness poll burns a whole interval and eight checks exhaust the harness cap ===
AWS: Smithy: `CreateDomain` answers 200 with `DomainStatus` whose `Created`, `Processing` and `DomainProcessingStatus` members are the documented readiness signals, and `DescribeDomain` is the read a client polls; `CreatePackage`/`UpdatePackage` publish `PackageDetails.PackageStatus` (settling to `AVAILABLE`), `AssociatePackages`/`DissociatePackages` publish `DomainPackageDetails.DomainPackageStatus` (settling to `ACTIVE`, or leaving the association absent after a dissociation), and `CreateVpcEndpoint`/`UpdateVpcEndpoint` publish `VpcEndpoint.Status` (settling to `ACTIVE`). AWS takes minutes to settle these, so a client polls at AWS-sized intervals (10-30 s) with long overall deadlines; the contract a client depends on is simply that the state it was told to wait for is OBSERVABLE on a read at some point — recorded behavior for every one of these surfaces.
Emulator: the readiness value is never observed by a poll sized for AWS. Each of these resources is reported not-yet-ready on the read that immediately follows its create (src/state.rs `PROVISIONING` / `Domain::settle`), and the clock-owed transition then lands inside a sub-second span, so the transient value (`Creating`/`Processing`, `ASSOCIATING`, `CREATING`, `UPDATING`) rests for less than one poll interval while the poll's FIRST sample is still the un-settled one. A caller at a 10-30 s interval therefore pays a whole interval per probe and, where several such waits are chained (domain Active, then package AVAILABLE, then association ACTIVE, then endpoint ACTIVE, then a service-software settling read), the 60 s budget is gone before the graded call is ever issued. All eight checks below end as `Check timed out after 60.0s` with no status, code or message reported at all. The same mechanism is recorded as cause 5 and cause 6 of the open issue 20261025T124157Z-opensearch-six-net-new-control-plane-causes-describedomainhealth.md and as cause 2 of 20261026T044500Z-opensearch-package-association-e2e-flows-need-the-domain-data-plane-and.md, neither of which carries the eight replay keys listed here (`opensearch.visibility-timeout-ttl-service-software-rollback-window-accepted` is the ACCEPTED-side sibling of the two rollback checks that issue names, and `opensearch.update-vpc-endpoint-concurrent-modification-conflict` now fails on a different frame than the `run#20` assertion key that issue carries).
Why: a client that waits for a documented terminal state neither proceeds nor receives an error — there is no success and no failure to handle, only a hang. Every contract that sits BEHIND a readiness wait is therefore unverifiable: the concurrent associate/dissociate ConflictException, the "package is in use" DissociatePackages guard, the package-version propagation rule, the UltraWarm/VPC-endpoint update serialization, the service-managed UpgradeDomain progress reported through GetUpgradeStatus/GetUpgradeHistory, and the 200-with-RollbackAvailable-false decline of RollbackServiceSoftwareUpdate.
Fix: the settling model in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs — `PROVISIONING`, `Domain::settle`, the package and `PackageAssociation` status clocks, and the VPC-endpoint status clock — so that a resource's settled state is observable to a caller that polls at AWS-sized intervals (either reported ready on the read that follows the create, or resting in its transient state long enough for one poll to sample it) rather than resting only inside a sub-second window.
Traces: opensearch.associate-dissociate-packages-concurrent-race-conflict, opensearch.e2e-package-association-index-effect-teardown, opensearch.e2e-package-version-update-domain-propagation, opensearch.package-dissociation-blocks-dependent-index-creation-rejected, opensearch.update-index-dependency-failure-on-unavailable-package, opensearch.update-vpc-endpoint-concurrent-modification-conflict, opensearch.upgrade-domain-server-managed-progress-tracking, opensearch.visibility-timeout-ttl-service-software-rollback-window-accepted.

=== Cause 2 of 2: the two deep data-plane scenarios never get an engine on the published domain endpoint ===
AWS: recorded behavior only (the control-plane Smithy model does not describe the engine): a domain publishes `DomainStatus.Endpoint`, and SigV4-signed (`es`) or HTTP-basic (FGAC) requests to that host are answered by the OpenSearch engine — documents indexed into a multi-shard index stay queryable across a blue/green scale-out and the new node holds shard copies, and a cross-cluster search through a configured outbound connection returns the REMOTE cluster's documents under the same index name rather than the local ones.
Emulator: no service answers on the host the control plane advertises; a signed request to the published endpoint is answered `404 {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"}` (the opensearch crate claims only its modelled `/2021-01-01/...` control-plane path space). Both checks spend their whole budget on the readiness/data-plane wait and end as `Check timed out after 60.0s`, reporting no status, code or body.
Why: the entire index/search capability behind a domain is unreachable, so a client exercising a domain as a search cluster hangs instead of indexing or searching, and neither data continuity across a scale-out nor cross-cluster query routing can be observed at all.
Fix: serve the published domain endpoint host as an OpenSearch engine, backed by a real in-process index/search engine, in the opensearch crate's data-plane routing (services/service-com-amazonaws-opensearch-amazonopensearchservice). This is the SAME capability recorded as cause 1 of the open issue 20261024T055421Z-opensearch-domain-data-plane-is-not-served-and.md and as cause 1 of 20261026T044500Z-opensearch-package-association-e2e-flows-need-the-domain-data-plane-and.md; neither carries these two replay keys, and these two checks additionally require shard placement across a scaled-out cluster and cross-cluster search routing, which those issues do not describe.
Traces: opensearch.osx-deep-opensearch-3-blue-green-scale-out-data-continuity, opensearch.osx-deep-opensearch-3-cross-cluster-search-propagation.

## Evidence
Replay output (suite simparity-behavioral-ga-prod-v1). All ten checks report exactly `Error: Check timed out after 60.0s` and no HTTP status, error code or message — the emulator never produces a response the check can grade.

Cause 1 (eight checks, each killed inside a chained readiness wait):
  opensearch.associate-dissociate-packages-concurrent-race-conflict — `_wait_domain_active(ctx, domain_name, timeout_s=1800)` after CreateDomain, before the barrier-released AssociatePackages/DissociatePackages pair whose ConflictException is the graded requirement.
  opensearch.e2e-package-association-index-effect-teardown — `_poll_until(_package_status, {AVAILABLE,...}, timeout_s=300, interval_s=10)` then `_poll_domain_package_active`.
  opensearch.e2e-package-version-update-domain-propagation — `_wait_package_status` / `_create_minimal_domain` / `_wait_domain_package_status(..., {ACTIVE})` before UpdatePackage.
  opensearch.package-dissociation-blocks-dependent-index-creation-rejected — `_poll_until(..., timeout_s=600.0, interval_s=10.0)` on DomainPackageStatus==ACTIVE / association absent.
  opensearch.update-index-dependency-failure-on-unavailable-package — `_wait_domain_active` then `_wait_domain_package_active` before the DISSOCIATION_FAILED / `Operation not allowed. Package is in use.` requirement.
  opensearch.update-vpc-endpoint-concurrent-modification-conflict — `_wait_domain_active(timeout_s=1800)` then `_wait_endpoint_status(..., {ACTIVE}, timeout_s=600)`.
  opensearch.upgrade-domain-server-managed-progress-tracking — `_wait_domain_active(timeout_s=1100.0, interval_s=30.0, quiescent_polls=2)`: two quiescent polls at a 30 s interval already exceed the 60 s cap on their own.
  opensearch.visibility-timeout-ttl-service-software-rollback-window-accepted — `_wait_domain_active` then `_wait_service_software_settled` (`time.sleep(20)` per read, three agreeing reads required) before the graded 200/RollbackAvailable=false decline.

Cause 2 (two checks): opensearch.osx-deep-opensearch-3-blue-green-scale-out-data-continuity and opensearch.osx-deep-opensearch-3-cross-cluster-search-propagation both sign requests to `DomainStatus['Endpoint']` (SigV4 `es` / HTTP-basic FGAC). The published endpoint answers `404 {'__type': 'UnknownService', 'message': "no emulated service is registered for 'es'"}`, so their readiness waits never clear and both are killed at the cap.
