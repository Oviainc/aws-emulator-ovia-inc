# batch: refusal classification and message fidelity — tag-plane errors are all ClientException, quota/validation refusals use emulator-authored text instead of AWS's envelope, and error responses carry no RequestId (5 causes)

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListTagsForResource

## Description
FIVE distinct root causes in how the AWS Batch emulator classifies and renders refusals. All are grounded in failing checks of the simparity-behavioral-ga-prod-v1 replay that the report does NOT mark ALREADY FILED or OWNED. Each cause is numbered; a fixer must close all five before submitting. In every cause below the refusal itself happens — it is the error CODE, the message RULE, or the response metadata that diverges.

Related open issues that do NOT carry these replay keys: '20261024T014332Z-batch-ecr-lambda-logs-batch-error-responses-carry-no-request-id-so' (the same defect as cause 5, but keyed only to the batch__ecr__lambda__logs check — the two batch-service checks named in cause 5 are unreplayed by it), '20261022T221856Z-batch-listtagsforresource-stub' (ListTagsForResource now answers, so cause 1 is about its error classification, not a stub) and '20261023T081835Z-batch-missing-and-spurious-refusals-plus-stale-describe' (wire corpus).

=== Cause 1 of 5: the Batch tag plane raises ClientException for every refusal instead of the tagging layer's BadRequestException / NotFoundException ===
AWS: Smithy com.amazonaws.batch#ListTagsForResource (GET /v1/tags/{resourceArn}) and #UntagResource (DELETE /v1/tags/{resourceArn}) declare only ClientException (400) and ServerException (500), so the codes below are recorded behavior only: Batch's tag plane answers a MALFORMED resourceArn with error code 'BadRequestException', and an UntagResource against a well-formed ARN for a job queue that does not exist with error code 'NotFoundException'. Both are 4xx refusals; the distinction between 'the ARN is not an ARN' and 'the resource is gone' is what the two codes carry.
Emulator: both answer error code 'ClientException'.
Why: the two refusal classes collapse into one, so a client cannot tell a programming error (bad ARN) from an expected race (resource already deleted). Idempotent teardown that swallows NotFoundException and re-raises everything else now re-raises, and retry logic keyed on the code mis-routes.
Fix: the error classification of the Batch tag-plane handlers (ListTagsForResource, UntagResource, TagResource) — emit BadRequestException for an unparseable resourceArn and NotFoundException for a well-formed ARN that resolves to nothing, instead of the blanket ClientException.
Traces: batch.list-tags-for-resource-contract ('expected BadRequestException for malformed ARN, got ClientException'), batch.tag-and-untag-resource-lifecycle ('expected NotFoundException untagging a nonexistent job queue, got ClientException').

=== Cause 2 of 5: the over-50-tags refusal renders a generic Smithy constraint message instead of Batch's tag-set refusal ===
AWS: Smithy TagResource.tags is a TagrisTagsMap with @length min 1 max 50 (and the same constraint on the tags member of CreateJobQueue), so the limit itself is modeled; the refusal text is a fixed constant of the tagging layer and does not vary with the request — AWS answers 'The resultant tag set must not have more than 50 user tags.' The rule is therefore known: for any request whose resultant tag set exceeds 50 user tags, that exact sentence is the message.
Emulator: the status and the error code are correct (the checks pass their code assertion and fail on the message), but the message is the generic framework constraint rendering, e.g. "1 validation error detected: Value '51 entries' at 'tags' failed to satisfy constraint: Member must have length less than or equal to 50" (and the same with '60 entries' from TagResource).
Why: the emulator leaks its own validation framework's phrasing in place of a service message AWS keeps constant, so operators matching on the known sentence, and golden-file/snapshot tests over error payloads, diverge; the message also exposes an entry count AWS never reports.
Fix: the tag-count validation in the Batch tag write path (TagResource and the tags member of CreateJobQueue) must raise the service's own refusal carrying the constant tag-set sentence rather than falling through to the generic constraint validator.
Traces: batch.job-queue-tag-limit-exceeded-rejected (51 tags on CreateJobQueue), batch.tag-resource-exceeds-limit-fails (60 tags on TagResource).

=== Cause 3 of 5: control-plane ClientException details are emulator-authored sentences and omit Batch's message envelope ===
AWS: these operations all declare ClientException (400) in Smithy (DeleteComputeEnvironment, UpdateComputeEnvironment, CreateConsumableResource, CreateSchedulingPolicy — each POST /v1/<op>, success 200, errors ClientException/ServerException only). The message text is recorded behavior only, but it is a fixed per-rule constant AWS does not derive from the request, and validation refusals are wrapped in Batch's envelope 'Error executing request, Exception : <detail>, RequestId: <request id>'. Recorded details: DeleteComputeEnvironment on an ENABLED compute environment -> 'Cannot delete an enabled compute environment, set the state to DISABLED first.'; UpdateComputeEnvironment with computeResources on an UNMANAGED environment -> 'Cannot update, compute resources not supported on unmanaged compute environment <ce arn>.'; CreateConsumableResource with an unknown resourceType -> envelope + 'resourceType needs to be one of the following values: [REPLENISHABLE, NON_REPLENISHABLE]'; CreateSchedulingPolicy with both fairsharePolicy and quotaSharePolicy -> envelope + 'A scheduling policy can have either fairsharePolicy or quotaSharePolicy, but not both.'
Emulator: the refusal, its 400 status and its ClientException code are right, but each detail is a differently-worded, emulator-authored sentence and the envelope is dropped entirely — e.g. 'Cannot delete compute environment <name> while its state is ENABLED: set it to DISABLED with UpdateComputeEnvironment first', 'computeResources can only be updated for a MANAGED compute environment, and <name> is UNMANAGED', 'resourceType INFINITE is not one of REPLENISHABLE, NON_REPLENISHABLE', 'Only one of fairsharePolicy or quotaSharePolicy can be set on a scheduling policy'. Note the last two: AWS wraps them in the envelope and the emulator emits a bare sentence, so the response shape differs, not merely the wording.
Why: the message is the only place Batch states WHICH rule fired, so operators, log scrapers and support tooling that match on the known sentence (or that parse the 'Error executing request, Exception : ... , RequestId: ...' envelope to split detail from request id) break; two emulator messages also name a compute environment by short name where AWS names it by ARN.
Fix: the refusal construction shared by these handlers — route validation refusals through the Batch ClientException envelope and carry the service's own per-rule detail text, instead of each handler composing its own sentence.
Traces: batch.ce-delete-while-enabled-fails, batch.ce-update-unmanaged-with-compute-resources-fails, batch.create-consumable-resource-invalid-type-rejected, batch.scheduling-policy-exclusive-fairshare-quotashare-rejected.

=== Cause 4 of 5: the CreateQuotaShare name-pattern refusal states the emulator's own constraint instead of AWS's pattern detail ===
AWS: Smithy CreateQuotaShare requires quotaShareName (String, no @pattern in the model), so the text is recorded behavior only and is a per-rule constant: a malformed quotaShareName is refused with HTTP 400 / ClientException and the envelope detail 'quotaShareName should match a valid pattern.'
Emulator: status 400 and code ClientException are right and the envelope is present, but the detail is the emulator's own constraint prose: 'quotaShareName must be 1 to 128 letters, numbers, hyphens (-) or underscores (_).'
Why: same consequence as cause 3 — a client matching the known refusal sentence does not match, and the emulator asserts a specific length/charset rule AWS does not state in that response, which invites clients to encode a bound AWS may not share.
Fix: the quotaShareName validation in the CreateQuotaShare handler — emit AWS's pattern detail for the pattern refusal.
Traces: batch.create-quota-share-malformed-share-identifier-rejected.

=== Cause 5 of 5: Batch error responses carry no ResponseMetadata.RequestId, so the id embedded in the message corresponds to nothing ===
AWS: recorded behavior only (no model member describes it). A Batch ClientException message ends with 'RequestId: <id>' where <id> is the request id of that same response — the value the SDK surfaces as ResponseMetadata.RequestId from the x-amzn-RequestId header. The two are the same string by construction, which is the rule the checks encode: they read the id off the response metadata and rebuild the expected message from it.
Emulator: the status (400), the code (ClientException) and the sentence are all right, and the message embeds a UUID, but the same response's ResponseMetadata.RequestId is absent, so the reconstructed expectation renders as '... RequestId: None' while the message says '... RequestId: <uuid>'.
Why: a client that logs ResponseMetadata.RequestId on failure records nothing, and a client that parses the id out of the message holds a value it cannot match to any response it has. The message and the metadata of one response contradict each other, breaking correlation and support-case workflows. This is the same root cause as open issue '20261024T014332Z-batch-ecr-lambda-logs-batch-error-responses-carry-no-request-id-so', whose pointer replays only the batch__ecr__lambda__logs check; the two batch-service checks below are unreplayed by it and are recorded here so a fix is confirmed against them too.
Fix: the error-serialization path for this service — emit the request-id response header/metadata on ERROR responses, using the one id the handler already interpolates into the ClientException message.
Traces: batch.op-contract-registerJobDefinition, batch.register-fargate-job-definition-without-execution-role-fails (in both, the only divergence is the request id; the executionRoleArn refusal itself matches).
