# EventBridge never delivers a matched event to any target, CloudFront emits no events of its own, PutEvents is unauthorized, and CFN-declared rules/functions are not provisioned (4 causes)

> _STATUS: cause 3 is fixed — `PutEvents` is authorized the way AWS authorizes any call on a resource, against the calling principal's identity-based policies and the bus's resource policy together, so a principal with no grant is refused with `AccessDeniedException` and nothing of its request is published. Cause 1 is fixed for the delivery that never happened at all: a queue target's `SqsParameters.MessageGroupId` now travels with the `sqs:SendMessage` each matched event is delivered by, which is what a FIFO (or fair) queue requires of every message it takes. The OTHER three causes — a target's own resource-based policy never being evaluated, the checks whose effect only a running Lambda deployment package can produce, CloudFront emitting no `aws.cloudfront` events, and CloudFormation registering no `AWS::Lambda::Function` — are re-filed with their replay keys as `issues/things-that-do-not-work/20261023T140640Z-cloudfront-events-3-of-the-4-causes-remain-open.md`, so none of them is recorded as working._

## Description
Four independent defects surfaced by the cloudfront/events cross-service behavioral checks. Each is its own root cause and its own work item; this issue bundles FOUR causes and all four must be closed before submitting. Causes 1 and 2 share a symptom — the check polls its destination until the 60 s budget expires — and are told apart by which side of the pipeline the check's own positive control exercises.

Cause 1 of 4: an event that matches an enabled rule is never delivered to the rule's target. PutRule + PutTargets succeed, PutEvents answers 200 with FailedEntryCount 0 and an EventId, and nothing ever arrives at the SQS queue, SNS topic, Lambda function or Step Functions state machine named as the target.
AWS: recorded behavior only — PutEvents entries matched by an enabled rule are delivered to each configured target within seconds; one check asserts this directly by comparing an ENABLED rule (must invoke) with a DISABLED one (must not).
Emulator: the delivery never happens: the ENABLED-rule positive control fails with "the ENABLED rule never invoked its Lambda target", and every poll-for-the-effect check in this group exhausts its wait and the suite kills it at the 60 s budget.
Why: every event-driven workflow is silently broken — the producer sees a successful PutEvents, so nothing in the client's code path reports an error, yet no consumer is ever run. Negative checks are equally unusable because their positive control also never fires.
Fix: the EventBridge rule-matching and target-dispatch path (match PutEvents entries against each enabled rule's EventPattern and invoke the target with the assumed role / resource policy), in the eventbridge/cloudwatchevents service crate.

Cause 2 of 4: CloudFront emits no events of its own onto the default event bus — neither distribution state-change events nor the API-call events that accompany CreateDistribution/UpdateDistribution/DeleteDistribution, nor tag-change events.
AWS: recorded behavior only — creating/updating/deleting a distribution and changing its tags produce events on the default bus (source aws.cloudfront, with the API-call detail carrying requestParameters), which a rule can match and forward to SQS/SNS.
Emulator: the rule and target exist and the mutation is performed, but no event is ever produced, so the destination stays empty and the check runs to the 60 s budget.
Why: a client that reacts to CloudFront lifecycle changes (invalidate on deploy, alert on delete, audit tag changes) never reacts at all, and there is no way to tell this from a rule-pattern mistake.
Fix: the CloudFront control-plane mutation handlers must publish their state-change / API-call / tag-change events to the EventBridge default bus (the event-emission side of the cloudfront crate plus the bus ingestion path).
Traces: cloudfront__events.cloudfront-distribution-deployed-event-delivered-to-sqs, cloudfront__events.cloudfront-distribution-inprogress-event-filtered-by-pattern, cloudfront__events.cloudfront-event-detail-payload-format-preserved, cloudfront__events.cloudfront-event-sns-topic-policy-missing-blocks-delivery, cloudfront__events.cloudfront-event-source-mismatch-not-delivered, cloudfront__events.cloudfront-event-to-sns-notifies-subscribers, cloudfront__events.eventbridge-rule-matches-cloudfront-createdistribution-api-call, cloudfront__events.eventbridge-rule-matches-cloudfront-deletedistribution-api-call, cloudfront__events.eventbridge-rule-matches-cloudfront-updatedistribution-api-call, cloudfront__events.eventbridge-cloudfront-tag-change-event-invokes-target.

Cause 3 of 4: PutEvents performs no authorization — a principal with no events:PutEvents grant is accepted.
AWS: recorded behavior only — a cross-account/unauthorized principal calling PutEvents against a bus it was granted nothing on is refused (403 AccessDeniedException, or the entry comes back failed); the check asserts the call does not succeed.
Emulator: the call returns 200 with {'FailedEntryCount': 0, 'Entries': [{'EventId': ...}]}, i.e. the event is accepted as if the grant existed.
Why: bus resource policies and identity policies are unenforceable, so an estate that relies on them for isolation cannot be validated and a real cross-account leak would never be caught.
Fix: IAM/resource-policy evaluation on the PutEvents path (bus resource policy + caller identity policy) in the eventbridge crate.
Traces: cloudfront__events.eventbridge-cross-account-cloudfront-event-not-matched-without-resource-policy.

Cause 4 of 4: resources a CloudFormation stack declares are not registered in their services — a stack's AWS::Lambda::Function and AWS::Events::Rule do not exist after CREATE_COMPLETE.
AWS: recorded behavior only — after the stack completes, GetFunction on the stack's function and DescribeRule on the stack's rule both succeed with the stack-generated physical names.
Emulator: the stack reports success, then GetFunction answers `ResourceNotFoundException` "Function not found: arn:aws:lambda:<region>:<account>:function:<stack>-MarkerFunction-..." and DescribeRule answers `ResourceNotFoundException` "Rule <stack>-TestRule-... does not exist on event bus default.".
Why: nothing deployed by template can be addressed afterwards, so every CFN-driven eventing scenario fails at its first read, and the error wrongly blames the client for naming a nonexistent resource.
Fix: the CloudFormation resource providers for AWS::Lambda::Function and AWS::Events::Rule (create the resource in the target service's state and resolve Ref/Fn::GetAtt to its real physical id).
