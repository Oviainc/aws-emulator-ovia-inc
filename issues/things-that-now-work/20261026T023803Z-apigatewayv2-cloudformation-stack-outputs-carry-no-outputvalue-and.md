# apigatewayv2: CloudFormation stack outputs carry no OutputValue and AWS::ApiGatewayV2::DomainName creates nothing, WEBSOCKET quick create is refused, a published portal serves 404, and GetRoute's NotFound message leaks an account-qualified id (5 causes)

> _Note: this issue was identified against the code base at commit `1030924aed157d95218fdb79c11a6b06e677df02`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi, GetDomainName, GetRoute, PublishPortal

## Description
Five distinct root causes, each grounded in a failing behavioral check of this suite. A fixer must close ALL FIVE before submitting; they are numbered and each carries its own failing check ids.

Related open issues that do NOT carry these checks' replay keys and do not cover these causes: 20261023T125319Z-apigatewayv2-cloudformation-deployed-api-gateway-v2-stacks-are-unusable.md (Ref of AWS::ApiGatewayV2::Api yielding the API name, over-long generated IAM role names), 20261023T151412Z-apigatewayv2-cloudformation-stacks-containing-aws-apigatewayv2-stage-route.md (Stage/Route stacks never converging), and, for cause 5, 20261025T041541Z-apigatewayv2-refusal-messages-do-not-name-the-blocking.md (its cause 2 names the same shared NotFound builder but carries only the GetDeployment and CreateRouteResponse message sites and their replay keys, not GetRoute/UpdateRoute). On cause 3 this is NOT a reopen of the fixed 20261023T124140Z-apigatewayv2-createapi-a-websocket-api-s-apiendpoint-is.md: that issue claimed only CreateApi's ApiEndpoint scheme, and no filed issue has claimed quick create's Target handling.

=== Cause 1 of 5: DescribeStacks returns stack Outputs entries with no OutputValue for AWS::ApiGatewayV2 resources ===
AWS: recorded behavior only (shape is CloudFormation's). Once a stack is CREATE_COMPLETE, every entry of Stacks[0].Outputs carries BOTH OutputKey and the resolved OutputValue; a template whose Outputs are 'Value: !Ref <AWS::ApiGatewayV2::Api>', 'Value: !GetAtt <Api>.ApiEndpoint' and 'Value: !GetAtt <ApiMapping>.ApiMappingId' therefore yields three key/value pairs, and the values are usable as real identifiers (the ApiMappingId can be read back with GetApiMapping).
Emulator: the stack reaches CREATE_COMPLETE (the stack_create_complete waiter returns), but building a dict from the Outputs raises KeyError: 'OutputValue' — at least one Outputs entry has an OutputKey and no OutputValue member. Hypothesis: the attribute resolution for AWS::ApiGatewayV2::Api / AWS::ApiGatewayV2::ApiMapping (Ref, GetAtt ApiEndpoint, GetAtt ApiMappingId) produces no value and the Output is emitted anyway instead of failing the stack.
Why: every client and IaC wrapper reads deployed identifiers out of stack outputs; an output without a value makes the whole stack unusable downstream (here the API id and the mapping id are unobtainable) while the stack still claims CREATE_COMPLETE, so the failure surfaces far from its cause.
Fix: the CloudFormation resource provider / output resolution for the AWS::ApiGatewayV2::* resource types — resolve Ref and the GetAtt attributes to the created resources' real identifiers, and never serialize an Output entry without OutputValue.
Traces: apigatewayv2.deploy-api-mapping-cfn-behaves.

=== Cause 2 of 5: a CloudFormation AWS::ApiGatewayV2::DomainName reaches CREATE_COMPLETE without creating the domain name ===
AWS: recorded behavior only. A stack declaring AWS::ApiGatewayV2::DomainName (DomainName, DomainNameConfigurations=[{EndpointType: REGIONAL, CertificateArn, SecurityPolicy: TLS_1_2}]) creates a real, independently usable apigatewayv2 object: after CREATE_COMPLETE, GetDomainName(DomainName=<the declared name>) returns 200 with exactly the declared configuration and the domain reaches its own DomainNameStatus=AVAILABLE; the resource can then be used by a direct, non-CloudFormation CreateApiMapping call.
Emulator: the stack reports CREATE_COMPLETE, but GetDomainName for the declared domain answers NotFoundException — 'Invalid domain name identifier specified' — i.e. the resource was never created in the apigatewayv2 state the control plane reads.
Why: this is a silent lie about deployment: the client is told the custom domain exists, then every subsequent control-plane read or mapping against it 404s. Rollback/reconcile logic keyed on stack status diverges from the service state.
Fix: the CloudFormation provider for AWS::ApiGatewayV2::DomainName — create the domain in the apigatewayv2 state (same path as CreateDomainName) and fail the stack when it cannot.
Traces: apigatewayv2.deploy-domain-name-cfn-behaves.

=== Cause 3 of 5: CreateApi refuses a WEBSOCKET quick create (ProtocolType=WEBSOCKET with Target) that AWS accepts ===
AWS: Smithy: CreateApi POST /v2/apis, success code 201; input Target -> UriWithLengthBetween1And2048 (jsonName target) with NO modeled dependency on ProtocolType, and no trait gating Target by protocol; modeled errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429). Recorded behavior: CreateApi(ProtocolType=WEBSOCKET, RouteSelectionExpression=..., Target=<url>) is ACCEPTED (201) and Target is silently ignored — the API comes back with a wss:// endpoint, zero integrations, zero routes and zero stages, and GetApi carries no Target member. Documentation describes Target as HTTP-only, but the service does not enforce it; the refusals AWS does make on an HTTP API are RouteKey without Target ("Target is a required property in this context") and a non-proxy Target ("Target only supports HTTP Proxy or Lambda Proxy").
Emulator: the call is refused with HTTP 400 BadRequestException, message 'Currently, Target is not permitted for APIs with a protocol type of WEBSOCKET', so a request real AWS answers 201 to fails, and the rest of the check (including the HTTP quick-create legs' assertions after it) cannot run.
Why: under-permissiveness on the shortest path from zero to a working API — 'aws apigatewayv2 create-api --target' and several IaC modules emit exactly this call shape; a WEBSOCKET API created that way works on AWS and 400s here.
Fix: the ProtocolType/Target gating in the CreateApi handler (ops/create_api.rs) — accept Target on a WEBSOCKET API, ignore it (synthesize no integration, route or stage) and do not echo it back; keep the two HTTP-API quick-create preconditions.
Traces: apigatewayv2.http-api-quick-create-synthesizes-integration-route-stage.

=== Cause 4 of 5: a PUBLISHED portal's default domain serves HTTP 404 instead of content ===
AWS: Smithy: PublishPortal POST /v2/portals/{PortalId}/publish, success code 202; CreatePortal returns EndpointConfiguration.PortalDefaultDomainName. Recorded behavior: after PublishPortal and once GetPortal reports PublishStatus=PUBLISHED, an HTTPS GET of PortalDefaultDomainName answers HTTP 200 with the portal's content (for a portal with an attached PortalProduct/ProductPage); after DisablePortal and PublishStatus=DISABLED, the same GET stops answering 200.
Emulator: the control-plane legs work (the portal is created, a default domain is assigned, PublishStatus reaches PUBLISHED) but the portal's default domain answers HTTP 404 — the portal data plane serves nothing, so neither the published nor the disabled state can be told apart on the wire.
Why: publishing is the entire point of a portal; a client that publishes and then fetches the portal URL (or asserts the published/disabled transition) sees a 404 that AWS never returns for a published portal.
Fix: the portal data-plane listener for PortalDefaultDomainName — serve the published portal's product pages, and stop serving once the portal is disabled.
Traces: apigatewayv2.e2e-portal-product-publish-flow.

=== Cause 5 of 5: GetRoute/UpdateRoute on a deleted route answer a NotFound message that renames the resource and appends the emulator's account-qualified key ===
AWS: Smithy: GetRoute GET /v2/apis/{ApiId}/routes/{RouteId}, errors NotFoundException (client, httpError 404) and TooManyRequestsException (429); the model carries no message text. Recorded behavior: reading or mutating a route that was deleted answers NotFoundException 404 whose message identifies the ROUTE with the fixed, lower-case text 'Invalid route identifier specified' and contains NO identifier and no account id. (By contrast, and asserted in the same check, the API-level message DOES carry the id: 'Invalid API identifier specified <account>:<apiId>' — so the requirement is per-resource, not a blanket ban on ids.)
Emulator: the status and code are right (404 NotFoundException) but the message is 'Invalid Route identifier specified 000000000000:8sh3tqaaaa' — the resource word is capitalised ('Route' instead of 'route') and the emulator's internal '<account>:<id>' state key is appended; the id shown is also the same 10-character value the run uses for other resource types, so it does not even identify the route.
Why: callers that classify a NotFound by its message (the only way to tell WHICH resource is missing) do not match AWS's text, and every such response hands the client an internal account-qualified partition key that no AWS response contains. The deleted-route listing and mutation-refusal effects are correct; only the message diverges.
Fix: the shared NotFound message builder used by the apigatewayv2 route handlers (get_route.rs / update_route.rs) — emit AWS's fixed per-resource text and drop the account-qualified state key. Same builder as cause 2 of open issue 20261025T041541Z, which covers the GetDeployment and CreateRouteResponse sites only.
Traces: apigatewayv2.websocket-api-create-route-delete.
