# CloudWatch: 4 net-new root causes — CFN-deployed dashboards are never provisioned, PutManagedInsightRules never reports per-entry Failures, the GetMetricStatistics Period refusal message is invented, and AWS/Usage CallCount is never published

> _Note: this issue was identified against the code base at commit `4796804db60a5ab3806f979c3ef85367d1923885`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutManagedInsightRules

## Description
Four net-new root causes in the cloudwatch service, left over after every failing check the replay report marked ALREADY FILED or OWNED was removed. Each cause below must be closed before this issue is submitted.

Cause 1 of 4: a CloudFormation-deployed AWS::CloudWatch::Dashboard resource is never provisioned in CloudWatch, even though the stack reaches CREATE_COMPLETE.
Failing check ids: cloudwatch.deploy-cloudformation-dashboard-renders-widgets, cloudwatch.deploy-cloudformation-dashboard-widgets-render.
AWS: Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/com-amazonaws-cloudwatch-graniteserviceversion20100801.json) models PutDashboard with required DashboardName and DashboardBody and output DashboardValidationMessages, and GetDashboard as the read path returning DashboardArn/DashboardName/DashboardBody. Recorded behavior: a stack whose only resource is AWS::CloudWatch::Dashboard, once it reports CREATE_COMPLETE, has actually called the dashboard write path — GetDashboard on the declared DashboardName returns 200 with that name and with the DashboardBody the template supplied, byte-for-byte (widget list length and every widget `properties` key preserved through the CFN round-trip, including a body passed in through a template Parameter). After DeleteStack the dashboard is genuinely gone: GetDashboard answers error code ResourceNotFound (404) with the message `Dashboard <DashboardName> does not exist` — fixed text `Dashboard ` + ` does not exist` around the DashboardName taken from the request.
Emulator: the stack settles at CREATE_COMPLETE, but the very first GetDashboard on the declared name is refused ResourceNotFound (404) with `Dashboard <name> does not exist`. The dashboard the stack claims to have created does not exist, so the body round-trip, the widget render and the post-delete absence are all unreachable. Note GetDashboard itself now answers correctly (the modeled ResourceNotFound, not the NotImplemented of open issues 20261025T015306Z-cloudwatch-getdashboard-is-an-unimplemented-scaffold-stub-so.md and 20261025T020208Z-cloudwatch-getdashboard-stub.md), so the refusal is truthful about state — nothing was written.
Why: every dashboard provisioned through infrastructure-as-code silently does not exist while the deployment pipeline reports success; nothing surfaces until an operator opens the dashboard. The same class for CloudWatch alarms is open issue 20261025T020208Z-cloudwatch-cfn-deployed-alarms-are-never-created-the.md (cause 1) and for Logs/ECS resources 20261023T113357Z-cloudformation-reports-create-complete-for-logs-cloudwatch-ecs.md; neither carries these two replay keys. Open issue 20261025T024908Z-cloudwatch-four-scaffolded-operations-answer-notimplemented-so-getmetricdata.md (cause 2) covers only the REFUSAL leg of the CFN dashboard resource (an invalid DashboardBody must fail the resource) and carries the two checks for that leg; it does not carry these two, which grade the positive leg — a VALID template body must actually create a readable dashboard.
Fix: the CloudFormation resource provider for AWS::CloudWatch::Dashboard must call through to the cloudwatch dashboard state on create/update (and remove it on stack delete) instead of recording the resource as complete; the dashboard state is the one PutDashboard/GetDashboard already serve.
Traces: cloudwatch.deploy-cloudformation-dashboard-renders-widgets, cloudwatch.deploy-cloudformation-dashboard-widgets-render.

Cause 2 of 4: PutManagedInsightRules accepts every ManagedRule entry and returns an empty Failures list, so no per-entry failure is ever reported.
Failing check ids: cloudwatch.managed-insight-rules-enable-list-lifecycle, cloudwatch.put-managed-insight-rules-invalid-definition-rejected, cloudwatch.put-managed-insight-rules-invalid-resource-arn-rejected, cloudwatch.put-managed-insight-rules-missing-param-rejected.
AWS: Smithy models PutManagedInsightRules with input ManagedRules (@required list of ManagedRule {TemplateName @required @length 1..128 @pattern, ResourceARN @required @length 1..1024, Tags}) and output Failures: BatchFailures, a list of PartialFailure {FailureResource, ExceptionType, FailureCode, FailureDescription}; the shape documentation states Failures "is empty if the API operation was successful for all the rules specified in the request" and that per-rule data is returned for each rule the operation could not process. Its modeled top-level errors are InvalidParameterValueException (awsQueryError code InvalidParameterValue, 400) and MissingRequiredParameterException. Recorded behavior pins the per-entry shapes on an HTTP 200: (a) a TemplateName that resolves to no managed-rule template, against a real eligible resource, yields exactly one PartialFailure {FailureResource: the submitted TemplateName, ExceptionType: "ResourceNotFoundException", FailureCode: "TEMPLATE_NAME", FailureDescription: "Could not find template with the specified templateName."} — fixed text, with FailureResource taken from the request; (b) the same unresolvable TemplateName paired with a malformed/unsupported ResourceARN yields exactly one PartialFailure {FailureResource: the submitted TemplateName, ExceptionType: "InvalidParameterException", FailureCode: "TEMPLATE_NAME", FailureDescription: "Invalid ResourceArn."} — the ARN problem is reported in preference to the template problem; (c) enabling a template for a resource type that has no managed catalog (a DynamoDB table) yields exactly one PartialFailure with ExceptionType "ResourceNotFoundException" and FailureCode "TEMPLATE_NAME"; and in every case nothing is enabled — ListManagedInsightRules for the resource still reports no rule with a RuleState.
Emulator: every one of these calls answers HTTP 200 with the body {"Failures":[]} (content-length 15), i.e. a blanket success. The top-level refusals this operation does get right (ManagedRules=[] -> InvalidParameterValue "EMPTY_MANAGED_RULES: ManagedRules cannot be an empty array.", and ListManagedInsightRules(ResourceARN="not-a-valid-arn-at-all") -> InvalidParameterValue) are reached and pass, so the gap is specifically the per-entry processing path. Open issue 20261025T020208Z-cloudwatch-putmanagedinsightrules-stub.md tracks this operation as an unimplemented scaffold stub; it does not describe these per-entry Failure semantics and does not carry these four replay keys — and the operation no longer answers NotImplemented, so implementing the stub alone is not what these checks grade.
Why: a caller cannot tell an enabled managed Contributor Insights rule from a silently dropped one. Tooling that enables a catalog of templates across an estate reads "all succeeded", builds dashboards and alarms on rules that do not exist, and never surfaces the unsupported resource type or the bad ARN that caused it.
Fix: per-entry processing in the PutManagedInsightRules handler and the managed-insight-rule state it writes — resolve each entry's TemplateName against the managed-rule catalog and validate its ResourceARN, emitting a PartialFailure per unprocessable entry (ARN problem taking precedence over template problem) and enabling only the entries that resolve.
Traces: cloudwatch.managed-insight-rules-enable-list-lifecycle, cloudwatch.put-managed-insight-rules-invalid-definition-rejected, cloudwatch.put-managed-insight-rules-invalid-resource-arn-rejected, cloudwatch.put-managed-insight-rules-missing-param-rejected.

Cause 3 of 4: the GetMetricStatistics refusal message for a Period that is not an allowed granularity is emulator-authored.
Failing check id: cloudwatch.invalid-parameter-value-family.
AWS: Smithy models GetMetricStatistics.Period as @required integer with @range(min: 1) only — the allowed granularities are a service rule, not a model constraint — and models InvalidParameterValueException (awsQueryError code InvalidParameterValue, 400) on the operation. Recorded behavior: Period=7 is refused 400 with code InvalidParameterValue and the message `The parameter Period must be a value in the set [1, 5, 10, 20, 30].` That text is entirely fixed: it names the parameter and enumerates the allowed sub-minute granularities, and it does NOT echo the submitted value. The surrounding checks in the same family pass, so only this message diverges.
Emulator: refuses with the right code, InvalidParameterValue, but the message `Period must be a positive 1, 5, 10, 20, 30 or multiple of 60; got 7` — invented wording, and it appends the submitted value, which AWS's message for this error class does not carry.
Why: operators and clients key refusal handling and user-facing text on these messages; a rewritten message breaks string-matching retry/repair logic and makes emulator-based tests assert text real AWS never sends. Open issue 20261025T020208Z-cloudwatch-metric-read-path-unit-is-dropped-from.md reports other GetMetricStatistics message/classification divergences (the 1440-datapoint cap text, the Statistics/ExtendedStatistics combination) and does not carry this replay key or this message.
Fix: the refusal message in the GetMetricStatistics handler's Period validation.
Traces: cloudwatch.invalid-parameter-value-family.

Cause 4 of 4: CloudWatch publishes no AWS/Usage per-API usage telemetry, so CallCount is never readable.
Failing check id: cloudwatch.obs-cloudwatch-1-usage-callcount-tracks-calls-against-never-called-control.
AWS: recorded behavior only — the Smithy model does not describe AWS/Usage publication. Recorded: CloudWatch itself publishes, off the response path and asynchronously, a CallCount metric into the reserved namespace AWS/Usage under the dimension set exactly {Service, Class, Type, Resource} — Service=CloudWatch, Class=None, Type=API, Resource=<operation name> — readable via GetMetricData with Stat=Sum, Period=60; GetMetricStatistics reports Unit 'None'. Every served call is counted, including a FAILED one (a GetDashboard that answered 404 ResourceNotFound still increments Resource=GetDashboard), and an operation that was never called in the window has no datapoints rather than a zero series. ListMetrics discovers the newly published CallCount series for the same dimension set.
Emulator: the check is killed with "Error: Check timed out after 60.0s" inside its bounded GetMetricData poll (the check's own declared ceiling is 600 s, so it never reaches an assertion): no AWS/Usage CallCount datapoint for Resource=ListMetrics or Resource=GetDashboard is ever produced, so neither the positive reads nor the never-called control can be graded. Nothing in the emulator writes usage telemetry; it stores only what PutMetricData was given.
Why: AWS/Usage CallCount is the series every service-quota dashboard, throttle alarm and API-usage report is built on. A client that monitors its own API consumption, or that alarms on approaching a request-rate quota, reads an empty namespace and silently never alarms.
Fix: per-operation usage metering in the cloudwatch service's request path, publishing CallCount into the reserved AWS/Usage namespace with the {Service, Class, Type, Resource} dimension set (counting refused calls too) and making it discoverable through ListMetrics and readable through GetMetricData/GetMetricStatistics.
Traces: cloudwatch.obs-cloudwatch-1-usage-callcount-tracks-calls-against-never-called-control.
