# ecs: 2 net-new root causes — UpdateContainerInstancesState failure entries keep the cluster segment in the container-instance ARN, and DeregisterTaskDefinition refuses a malformed identifier with ClientException 'Family contains invalid characters.' instead of InvalidParameterException 'Revision is missing'

> _Note: this issue was identified against the code base at commit `5e55ca226e42cc2f7e063620f74c9d72d8541e31`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateContainerInstancesState

## Description
Two independent ECS defects, both surfaced by behavioral checks that now run past the assertions earlier issues fixed. This bundle contains 2 causes; BOTH must be closed before submitting.

Cause 1 of 2: UpdateContainerInstancesState's `failures[]` entry for an unresolvable container instance carries a cluster-qualified ARN.
AWS: UpdateContainerInstancesState answers HTTP 200 and reports every container instance it could not resolve through `failures` (Smithy: UpdateContainerInstancesState output members `containerInstances`/`failures`; `failures` targets `Failures`, whose `Failure` has `arn`/`reason`/`detail`; the model does not constrain the ARN's resource layout, so the ARN form is recorded behavior only). For a request that names an instance by its FULL, cluster-qualified ARN (`arn:aws:ecs:<region>:<account>:container-instance/<clusterName>/<instance-id>`) against an existing cluster in which no such instance is registered, AWS answers one failure whose `reason` is the fixed string `MISSING` and whose `arn` is the UNQUALIFIED container-instance ARN: `arn:aws:ecs:<region>:<account>:container-instance/<instance-id>` — fixed parts are the `arn:aws:ecs:` prefix and the literal resource type `container-instance/`; the variable parts are the region and account id from the request context and the instance id taken from the identifier the request supplied. The cluster name does NOT appear in the resource part of the failure ARN. (Note the sibling read is different and must not be changed to match: DescribeContainerInstances' failure entry for the same identifier echoes the cluster-qualified ARN the request sent, so this normalisation belongs to the UpdateContainerInstancesState failure path, not to a shared helper applied uniformly.)
Emulator: HTTP 200 with the correct `reason` `MISSING`, but `arn` is the cluster-qualified form `arn:aws:ecs:<region>:<account>:container-instance/<clusterName>/<instance-id>` — one extra path segment (the cluster) in the resource part. Replay: expected `[('arn:aws:ecs:<region>:<account>:container-instance/<instance-id>', 'MISSING')]`, got `[('arn:aws:ecs:<region>:<account>:container-instance/<clusterName>/<instance-id>', 'MISSING')]`.
Why: a client that drains instances in batches correlates `failures[].arn` back to the ids it submitted, and a client that stores the returned ARN uses it on later calls. Because the emulator returns an ARN in a form AWS never emits for this operation, the correlation on the recorded form fails and the stored ARN is not the one AWS would have handed back, so "this instance is gone" cannot be distinguished from "an unknown instance failed", and reconcilers keyed on the echoed ARN never converge.
Fix: the failure-entry construction in the UpdateContainerInstancesState handler — `services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/src/ops/update_container_instances_state.rs` around the `crate::state::unresolved_failure(&region, CONTAINER_INSTANCE_RESOURCE_TYPE, reference)` call (handler lines ~311-336), and/or the ARN-form helper it calls in `src/state.rs` (`unresolved_failure` / `container_instance_arn_from_reference`), which must emit the unqualified container-instance ARN for this operation's failures while leaving the DescribeContainerInstances failure form alone.
Not covered by an existing issue: the open 20261030T130106Z-ecs-describetasksets-failure-entries-re-synthesize-task-set.md concerns the DescribeTaskSets `failures[].arn` and carries no replay key for UpdateContainerInstancesState; the fixed 20261029T175650Z-ecs-7-net-new-root-causes-in-not.md owns only the RegisterContainerInstance error class in this same check (the assertion that now passes).
Traces: ecs.container-instance-ops-on-missing-cluster-not-found.

Cause 2 of 2: DeregisterTaskDefinition refuses a malformed task-definition identifier with the DescribeTaskDefinition error class and wording instead of the missing-revision refusal.
AWS: DeregisterTaskDefinition's `taskDefinition` member is "the family and revision (family:revision) or full Amazon Resource Name (ARN) of the task definition to deregister. You must specify a revision." (Smithy: DeregisterTaskDefinition input `taskDefinition` required; modeled errors ClientException | InvalidParameterException | AccessDeniedException | ServerException, all httpError 400/403.) Recorded behavior: on this operation the missing-revision rule is what decides the refusal — an identifier that does not name a revision is refused with HTTP 400, error code `InvalidParameterException`, message `Revision is missing` (entirely fixed text, nothing interpolated from the request), and that holds even when the identifier is also not a well-formed family (the check sends `"not a valid @@@ identifier"`). The family-charset sentence `Family contains invalid characters.` belongs to the READ path: DescribeTaskDefinition refuses the very same identifier with ClientException and that message.
Emulator: DeregisterTaskDefinition(taskDefinition="not a valid @@@ identifier") is refused with code `ClientException` and message `Family contains invalid characters.` — the describe-path class and sentence. Replay: expected `('InvalidParameterException', 'Revision is missing')`, got `('ClientException', 'Family contains invalid characters.')`.
Why: a client (or IaC provider) that branches on `InvalidParameterException` to report a malformed/revision-less task-definition reference never takes that branch, sees the generic `ClientException` class instead, and gets a message about the family's characters rather than the missing revision — so the actionable diagnosis ("you must specify a revision") is lost and error handling written against AWS does not fire.
Emulator code path: `src/ops/deregister_task_definition.rs` refuses on the first branch, where `crate::state::parse_task_definition_reference` returns `None` and the handler answers `ClientException` with `crate::state::TASK_DEFINITION_REFERENCE_MESSAGE` (handler lines ~162-171); the second branch (a parseable family with no revision) answers `ClientException` with `task_definition_revision_required_message` (lines ~181-190). Both branches must answer `InvalidParameterException` with the fixed message `Revision is missing`.
Fix: the identifier validation in the DeregisterTaskDefinition handler (`src/ops/deregister_task_definition.rs`) — classify and word the no-revision refusal there, ahead of (and independent of) the shared task-definition reference parser's describe-path message in `src/state.rs`.
Related but NOT covering it: open issue 20261029T220901Z-ecs-task-definition-and-list-operations-drop-previousstatus.md cause 4 names the family-WITH-no-revision variant of this refusal from the wire corpus and carries no replay key for this check; a fix that only re-words that second branch leaves the malformed-identifier branch diverging. The fixed issue 20261029T175650Z-ecs-7-net-new-root-causes-in-not.md cause 7 changed the shared reference parser's message for DescribeTaskDefinition, which is where DeregisterTaskDefinition's current wording comes from; DescribeTaskDefinition itself is correct now and must stay correct.
Traces: ecs.invalid-parameter-task-definition-ops.
