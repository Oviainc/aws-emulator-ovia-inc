# s3: UpdateBucketMetadataAnnotationTableConfiguration is an unimplemented scaffold stub (501 NotImplemented), so an S3 Metadata configuration's annotation table can never be enabled, disabled or re-pointed after creation

> _Note: this issue was identified against the code base at commit `a897c1908ff5595645e24c2ee983a2dd8fc3b256`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateBucketMetadataAnnotationTableConfiguration

## Description
Cause 1 of 1: the UpdateBucketMetadataAnnotationTableConfiguration handler is still a scaffold stub and answers HTTP 501 NotImplemented, so the annotation sub-resource of an S3 Metadata V2 configuration is write-once at create time and can never be updated in place. Both grounded checks are blocked on exactly this call. Failing check ids for this cause: s3.bucket-metadata-table-update-roundtrip, s3.metadata-table-server-managed-updates.

AWS: Smithy (com.amazonaws.s3#AmazonS3, restXml): UpdateBucketMetadataAnnotationTableConfiguration binds PUT /{Bucket}?metadataAnnotationTable with modelled success code 200 and an empty (Unit) output; input is {Bucket (BucketName) @httpLabel required, AnnotationTableConfiguration (AnnotationTableConfigurationUpdates) @httpPayload @xmlName("AnnotationTableConfiguration") required, ContentMD5 -> Content-MD5, ChecksumAlgorithm -> x-amz-sdk-checksum-algorithm, ExpectedBucketOwner -> x-amz-expected-bucket-owner}, with @httpChecksum{requestChecksumRequired:true}; errors: [] (the operation models none). AnnotationTableConfigurationUpdates = {ConfigurationState (AnnotationConfigurationState enum) required — "The new configuration state to apply", EncryptionConfiguration (MetadataTableEncryptionConfiguration), Role (Role) — "The new IAM role ARN to apply"}. After a successful call, GetBucketMetadataConfiguration's MetadataConfigurationResult.AnnotationTableConfigurationResult reports the NEW ConfigurationState (required) and the Role ARN that was passed, with TableStatus moving CREATING -> ACTIVE for a newly enabled annotation table (AnnotationTableConfigurationResult.TableStatus documents "Possible values: CREATING, BACKFILLING, ACTIVE, FAILED"), and the sibling JournalTableConfigurationResult / InventoryTableConfigurationResult sub-resources are left exactly as they were. Recorded behavior only for one adjacent rule the checks rely on: real AWS refuses ConfigurationState=ENABLED with no Role beside it with InvalidRequest, so an ENABLED update must carry a Role whose trust policy lets metadata.s3.amazonaws.com assume it.

Emulator: the handler at services/service-com-amazonaws-s3-amazons3/src/ops/update_bucket_metadata_annotation_table_configuration.rs still carries the machine-readable marker `//! SCAFFOLDED, NOT IMPLEMENTED:` and its handle() returns the scaffold refusal: HTTP 501, code `NotImplemented`, message `operation UpdateBucketMetadataAnnotationTableConfiguration is scaffolded but not implemented in this emulator` (fixed text with the operation name as its only variable part). The surrounding surface IS implemented — CreateBucketMetadataConfiguration provisions the journal/inventory/annotation tables and GetBucketMetadataConfiguration renders AnnotationTableConfigurationResult including Role and TableStatus, and the journal and inventory update operations are implemented — so this one operation is the only gap. Both checks wrap the call in a bounded retry-through-ClientError loop (90 s / 5 s interval, written to ride out IAM trust-policy propagation), so the 501 is swallowed and retried until the harness kills the check; the replay report therefore shows only `Error: Check timed out after 60.0s` for each, with no exception surfaced. That masking is also why the suite's blocked-by-unimplemented detector did not mark these two checks ALREADY FILED, and why no stub issue exists for this operation (the sibling stub issues 20261027T001031Z-s3-updatebucketmetadatajournaltableconfiguration-stub.md and 20261027T001031Z-s3-updatebucketmetadatainventorytableconfiguration-stub.md are both already fixed, and the open 20261027T001031Z-s3-deletebucketmetadataconfiguration-stub.md names a different operation).

Why: a client cannot turn annotations on or off, change the annotation table's IAM role, or change its encryption configuration for a metadata configuration that already exists — the only path left is delete-and-recreate the whole configuration, which AWS does not require and which strands the journal/inventory tables in the managed table bucket's namespace. Worse, because the refusal is a 501 rather than a modelled error, any client that retries through transient failures (the documented pattern here, since the role's trust policy is eventually consistent from S3's point of view) spins until its own deadline instead of failing fast: it cannot tell "not supported" from "not yet assumable". Nothing about the annotation sub-resource's lifecycle, nor the per-sub-resource isolation guarantee (one update must not clobber its siblings), is observable at all.

Fix: the UpdateBucketMetadataAnnotationTableConfiguration handler — replace the scaffold's `Err(Scaffolded::not_implemented(..))` with the real update over the named bucket's stored metadata configuration, following exactly the shape the already-implemented inventory and journal updates use (the annotation slot of the stored BucketMetadataConfiguration and the shared optional-table state transition, so an enable creates the annotation table as CREATING and it falls due ACTIVE, a disable drops it, and the journal/inventory sub-resources and the journal's record expiration are untouched), apply the documented refusals (NoSuchBucket 404 for a bucket the emulator does not hold, the no-such-configuration 404 for a bucket carrying no metadata configuration, 403 AccessDenied for a mismatched x-amz-expected-bucket-owner, InvalidArgument/InvalidRequest for SSE-KMS with no KmsKeyArn and for ENABLED with no Role), and delete the SCAFFOLDED marker line so the stub inventory stops over-reporting it. Related but DISTINCT open issue: 20261027T235025Z-s3-6-net-new-root-causes-per-bucket.md cause 6 covers the post-delete not-found CODE for GetBucketMetadataConfiguration and owns two other metadata-table checks; it does not name this operation and does not carry either of these two checks' replay keys.

Traces: s3.bucket-metadata-table-update-roundtrip, s3.metadata-table-server-managed-updates.

## Evidence
Cause 1 — s3.bucket-metadata-table-update-roundtrip [mismatch] and s3.metadata-table-server-managed-updates [mismatch]

Request sequence common to both checks (all of these SUCCEED against the emulator):
  1. CreateBucket.
  2. CreateBucketMetadataConfiguration(Bucket, MetadataConfiguration={"JournalTableConfiguration":{"RecordExpiration":{"Expiration":"DISABLED"}},"InventoryTableConfiguration":{"ConfigurationState":"DISABLED"}}).
  3. GetBucketMetadataConfiguration polled until MetadataConfigurationResult.JournalTableConfigurationResult.TableStatus == "ACTIVE" — converges (the emulator activates a table a short span after the create).
  4. UpdateBucketMetadataJournalTableConfiguration(RecordExpiration={"Expiration":"ENABLED","Days":7}) and UpdateBucketMetadataInventoryTableConfiguration(ConfigurationState="ENABLED") — both accepted and reflected by the following reads.
  5. iam.CreateRole with a trust policy for Principal {"Service":"metadata.s3.amazonaws.com"} conditioned on aws:SourceAccount, plus iam.PutRolePolicy granting s3:GetObject/s3:ListBucket on the bucket.
  6. UpdateBucketMetadataAnnotationTableConfiguration(Bucket, AnnotationTableConfiguration={"ConfigurationState":"ENABLED","Role":<role arn>}), issued inside a bounded retry-through-ClientError loop (timeout_s=90, interval_s=5).

Expected (AWS): step 6 answers HTTP 200 with an empty body; the next GetBucketMetadataConfiguration reports AnnotationTableConfigurationResult with ConfigurationState "ENABLED" and Role equal to the role ARN that was passed, a TableStatus in {CREATING, BACKFILLING, ACTIVE} (never FAILED), and leaves JournalTableConfigurationResult.RecordExpiration at Expiration "ENABLED"/Days 7 and InventoryTableConfigurationResult.ConfigurationState at "ENABLED".

Actual (emulator): step 6 is refused every time with HTTP 501, code `NotImplemented`, message `operation UpdateBucketMetadataAnnotationTableConfiguration is scaffolded but not implemented in this emulator`. Because the checks' retry helper catches ClientError and sleeps, the refusal is never surfaced and the loop keeps re-issuing it; the harness kills both checks inside that loop and the replay report shows, for each, only:
  s3.bucket-metadata-table-update-roundtrip  -> Error: Check timed out after 60.0s
  s3.metadata-table-server-managed-updates   -> Error: Check timed out after 60.0s
No assertion past step 6 is ever evaluated in either check (the annotation ConfigurationState/Role read-back, the sibling-isolation assertions, and — in the roundtrip check — the closing DeleteBucketMetadataConfiguration and the MetadataConfigurationNotFound read-back).

Source corroboration (citations, not a patch): services/service-com-amazonaws-s3-amazons3/src/ops/update_bucket_metadata_annotation_table_configuration.rs line 4 — `//! SCAFFOLDED, NOT IMPLEMENTED: this operation answers HTTP 501 NotImplemented and asserts NOTHING about UpdateBucketMetadataAnnotationTableConfiguration's real behaviour`; contrast services/service-com-amazonaws-s3-amazons3/src/ops/update_bucket_metadata_inventory_table_configuration.rs line 4 (`//! IMPLEMENTED: enables or disables the live inventory table ...`) and services/service-com-amazonaws-s3-amazons3/src/ops/get_bucket_metadata_configuration.rs lines 280-298, which already render AnnotationTableConfigurationResult (ConfigurationState, TableStatus, Error, TableName, TableArn, Role) from stored state.

## Steps to Reproduce
1. Boot the emulator and point a boto3 s3/iam/sts client at it.
2. s3.create_bucket(Bucket=B) (with CreateBucketConfiguration.LocationConstraint for any region other than us-east-1).
3. s3.create_bucket_metadata_configuration(Bucket=B, MetadataConfiguration={"JournalTableConfiguration":{"RecordExpiration":{"Expiration":"DISABLED"}},"InventoryTableConfiguration":{"ConfigurationState":"DISABLED"}}).
4. Poll s3.get_bucket_metadata_configuration(Bucket=B) until MetadataConfigurationResult.JournalTableConfigurationResult.TableStatus == "ACTIVE" (converges).
5. iam.create_role(RoleName=R, AssumeRolePolicyDocument=<trust policy allowing Service metadata.s3.amazonaws.com to sts:AssumeRole, Condition StringEquals aws:SourceAccount=<account>>) and iam.put_role_policy(RoleName=R, PolicyName="read-annotations", PolicyDocument=<Allow s3:GetObject,s3:ListBucket on arn:aws:s3:::B and arn:aws:s3:::B/*>).
6. s3.update_bucket_metadata_annotation_table_configuration(Bucket=B, AnnotationTableConfiguration={"ConfigurationState":"ENABLED","Role":<role arn>}).
   Expect HTTP 200 and an empty body; observe HTTP 501 NotImplemented "operation UpdateBucketMetadataAnnotationTableConfiguration is scaffolded but not implemented in this emulator".
7. Call it again inside a loop that catches ClientError and sleeps (as both checks do) to see the hang the stub produces rather than a fast failure.
8. Also call s3.update_bucket_metadata_annotation_table_configuration(Bucket=B, AnnotationTableConfiguration={"ConfigurationState":"ENABLED"}) with NO Role and confirm the InvalidRequest refusal AWS gives is likewise absent.
9. Re-replay exactly the check ids in trace_ids: s3.bucket-metadata-table-update-roundtrip and s3.metadata-table-server-managed-updates.
