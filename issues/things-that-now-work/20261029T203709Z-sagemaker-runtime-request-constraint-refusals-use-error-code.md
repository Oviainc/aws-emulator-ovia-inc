# sagemaker-runtime: request-constraint refusals use error code ValidationException instead of the modeled ValidationError, echo the sensitive CustomAttributes value in the message, and InvokeEndpointAsync never enforces the Body/InputLocation disjunction before the endpoint lookup (3 causes)

> _Note: this issue was identified against the code base at commit `355c5d16add239c66c8799ffa26377be788e0f43`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeEndpoint

## Description
Three distinct root causes in the sagemaker-runtime data plane. All three must be closed before submitting. (Related but non-covering: 20261024T183933Z-sagemaker-runtime-invokeendpoint-evaluates-no-caller-authorization-a.md owns a different replay key — missing authorization — and 20261029T192819Z-sagemaker-validationexception-rendering-diverges-ordering-list-constraints-enum.md is about the separate `sagemaker` control-plane service.)

Cause 1 of 3: the constraint layer refuses malformed requests with error code "ValidationException", but this service models no such error — the only client validation error is ValidationError. Failing checks: sagemaker-runtime.rejects-malformed-fields-before-endpoint-lookup, sagemaker-runtime.new-session-sentinel-is-operation-scoped, sagemaker-runtime.invoke-endpoint-oversized-custom-attributes-rejected, sagemaker-runtime.invoke-endpoint-async-missing-input-failure-location-rejected.
AWS: Smithy com.amazonaws.sagemakerruntime declares, on InvokeEndpoint, InvokeEndpointAsync and InvokeEndpointWithResponseStream, the client error ValidationError (httpError 400, doc "Inspect your request and try again."); there is no ValidationException shape in the model at all. Every request-shape violation — EndpointName against pattern ^[a-zA-Z0-9](-*[a-zA-Z0-9])*$, SessionId against ^(NEW_SESSION)$|^[a-zA-Z0-9](-*[a-zA-Z0-9])*$, CustomAttributes @length max 1024, InputLocation against ^(https|s3)://([^/]+)/?(.*)$, RequestTTLSeconds @range 60..21600 — is returned as HTTP 400 with Error.Code "ValidationError" and the standard constraint message "1 validation error detected: Value '<value>' at '<memberName>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>" / "Member must have length less than or equal to <max>" (fixed text is the template; the value, member name, pattern and limit come from the request and the model). The emulator already uses ValidationError for the endpoint-not-found refusal on the same operations, so the two paths disagree with each other.
Emulator: the constraint layer returns Error.Code "ValidationException" (message body otherwise matching the AWS template) for all of those violations, e.g. ValidationException: "1 validation error detected: Value '<name>' at 'endpointName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9](-*[a-zA-Z0-9])*".
Why: a client branching on Error.Code — botocore's modeled exception classes, retry/alerting policy, negative tests — never sees the error the SDK generated for this service, so the ValidationError handler is dead code and the refusal surfaces as a generic ClientError. The same request is a different error class on the emulator than on AWS.
Fix: the service's request-validation/error-serialization layer — the code that names the constraint-violation error for sagemaker-runtime operations must emit the modeled ValidationError (400), consistently with the endpoint-lookup refusal path in the InvokeEndpoint/InvokeEndpointAsync handlers.

Cause 2 of 3: the constraint message echoes the value of CustomAttributes, which the model marks sensitive. Failing check: sagemaker-runtime.invoke-endpoint-oversized-custom-attributes-rejected.
AWS: CustomAttributesHeader is @sensitive with @length max 1024 (Smithy InvokeEndpoint.CustomAttributes). A violation is reported WITHOUT the offending value: "1 validation error detected: Value at 'customAttributes' failed to satisfy constraint: Member must have length less than or equal to 1024" — the value slot is omitted precisely because the member is sensitive, unlike a non-sensitive member such as endpointName whose value IS quoted.
Emulator: the message interpolates the value anyway: "1 validation error detected: Value 'aaaa…aaa... [1025 bytes]' at 'customAttributes' failed to satisfy constraint: Member must have length less than or equal to 1024" (the long literal is the request's own attribute value).
Why: the emulator leaks a value the model forbids echoing — a customer-supplied header carrying tokens or PII lands in error text, client logs and traces — and the refusal message differs from AWS's for the same request, so a client asserting on it diverges.
Fix: the constraint-message formatter in the request-validation layer must consult the member's @sensitive trait and omit the value slot (render "Value at '<member>'") rather than always interpolating it.

Cause 3 of 3: InvokeEndpointAsync does not enforce the "exactly one of Body or InputLocation" rule, so a request carrying neither source falls through to the endpoint lookup. Failing check: sagemaker-runtime.async-invoke-rejects-neither-and-both-input-sources.
AWS: recorded behavior only — the disjunction is not expressed in the Smithy model (both Body and InputLocation are optional on InvokeEndpointAsyncInput). AWS refuses a request with NEITHER source with HTTP 400 ValidationError and the exact message "One of Body or InputLocation is required" (fixed text, no request-derived parts), and this rule is evaluated BEFORE the endpoint is resolved, so the message never mentions the endpoint. A request carrying BOTH is refused with its own distinct message, "Both Body and InputLocation were provided. Provide exactly one." Either source alone is a valid request and only then does the endpoint lookup run, producing "Endpoint <name> of account <account> not found."
Emulator: the no-source request skips the disjunction check entirely and is answered with the endpoint-lookup refusal, ValidationError "Endpoint <endpoint-name> of account <account-id> not found." (fixed text "Endpoint … of account … not found."; the name and account come from the request/credentials). The emulator's ordering therefore also exposes the endpoint lookup to requests AWS rejects earlier; the both-sources half of the same rule is unverified because the check stops at the first divergence.
Why: a client that forgets its input source is told its endpoint does not exist, sending the caller to fix infrastructure rather than its request; and a validator relying on the emulator to catch the malformed call accepts code that AWS rejects. Pre-lookup ordering matters because it is what makes the two outcomes distinguishable.
Fix: the InvokeEndpointAsync handler's request-validation step — add the exactly-one-of(Body, InputLocation) gate ahead of the endpoint resolution, with the two distinct ValidationError messages above.

Traces: see trace_ids.

## Steps to Reproduce
1. Boot the emulator.
2. Cause 1: call sagemaker-runtime InvokeEndpoint with EndpointName="sim2real_bad_name" (underscores violate the modeled pattern) and Body=b'{"instances": [[1.0, 2.0]]}'. Observe HTTP 400 with Error.Code "ValidationException" instead of "ValidationError". Repeat with SessionId="NEW_SESSIONS" against a well-formed but absent endpoint name, and with InvokeEndpointAsync InputLocation="ftp://not-a-supported-scheme/input.bin" — all three answer ValidationException.
3. Cause 2: call InvokeEndpoint with a well-formed absent EndpointName, Body=b"x" and CustomAttributes="a"*1025. Observe the refusal message interpolates the 1025-character sensitive value ("Value '<aaaa…>' at 'customAttributes' …") instead of AWS's "Value at 'customAttributes' …". A short CustomAttributes value in the same call shape correctly reaches the endpoint lookup, proving the constraint layer is the component at fault.
4. Cause 3: call InvokeEndpointAsync(EndpointName=<a well-formed name that was never created>, ContentType="application/json") with NEITHER Body nor InputLocation. Observe ValidationError "Endpoint <name> of account <account> not found." instead of ValidationError "One of Body or InputLocation is required". Then repeat passing BOTH InputLocation="s3://<bucket>/input.json" and Body=b'{"inputs": "sim2real"}' and confirm whether the distinct both-sources message is produced. Controls: either source alone must reach the endpoint lookup and return the identical not-found message, and a Body past AsyncBodyBlob's 128000-byte ceiling must be refused before the lookup.
