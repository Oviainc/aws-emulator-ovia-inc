# firehose__s3__sesv2: both SESv2→Firehose event-destination checks abort at setup — CreateConfigurationSet is an unimplemented scaffold stub answering 501 NotImplemented

> _Note: this issue was identified against the code base at commit `fb1de11771ea07ab11d207d382a4d90e01236a0b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationSet

## Description
One net-new root cause.

Context on neighbouring issues (neither covers this): 20261023T183615Z-sesv2-sns-the-ses-event-destination-sns-topic.md reports CreateConfigurationSet being refused pre-dispatch with the non-AWS code 'AmbiguousService' by the sigv4-name router, and 20261025T114929Z-ses-the-pre-dispatch-ambiguousservice-refusal-is-served.md (fixed) concerned the retry classification of that pre-dispatch refusal. In this run the request is no longer refused by the router at all — it now reaches the sesv2 service and is refused by the operation itself with a different status and code (501 NotImplemented, not 400/5xx AmbiguousService). That is a distinct cause with a distinct fix site, so this is NOT a REOPENS of the fixed issue and is not the routing issue's replay key either.

Cause 1 of 1: sesv2 CreateConfigurationSet is still a scaffold stub, so every scenario whose setup needs a configuration set cannot start.

AWS: CreateConfigurationSet is SESv2 restJson1, POST /v2/email/configuration-sets, success 200 with an EMPTY response body (Smithy, services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json: CreateConfigurationSet input CreateConfigurationSetRequest {ConfigurationSetName required; TrackingOptions, DeliveryOptions, ReputationOptions, SendingOptions, Tags, SuppressionOptions, VdmOptions, ArchivingOptions, MessageSecurityOptions}, output CreateConfigurationSetResponse {} , http POST /v2/email/configuration-sets code 200). Its ONLY modeled errors are AlreadyExistsException (400), BadRequestException (400), ConcurrentModificationException (500), LimitExceededException (400), NotFoundException (404) and TooManyRequestsException (429); the model documents ConfigurationSetName as 'up to 64 alphanumeric characters, including letters, numbers, hyphens (-) and underscores (_) only', so a name violating that is BadRequestException 400 and a duplicate name is AlreadyExistsException 400. There is no condition under which AWS answers this operation 501, and 'NotImplemented' is not in the model. After a 200, the set is addressable by name: CreateConfigurationSetEventDestination (POST /v2/email/configuration-sets/{ConfigurationSetName}/event-destinations, 200) must accept a KinesisFirehoseDestination {IamRoleArn, DeliveryStreamArn} against it, SendEmail must accept ConfigurationSetName, and DeleteConfigurationSet must remove it; a name that was never created must answer NotFoundException 404 instead.

Emulator: the call is answered HTTP 501 with code 'NotImplemented' and the message "operation CreateConfigurationSet is scaffolded but not implemented in this emulator" (the fixed text is the emulator's scaffold wording; its only variable part is the operation name 'CreateConfigurationSet' interpolated from the stub). The handler is services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set.rs, whose `handle` body is still `Err(crate::scaffolded::Scaffolded::not_implemented("CreateConfigurationSet"))` and which still carries the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker. Because the refusal happens at the first SESv2 call of each scenario's setup, nothing downstream is exercised: the SES configuration set, its Firehose event destination, the two SendEmail calls and the S3 objects behind the delivery stream are all unreached, and the negative sibling's assertion (that a role whose trust policy never allows ses.amazonaws.com is permanently refused, not transiently) is never evaluated.

Why: a client that groups sending rules into a configuration set — the normal way SES event publication to Firehose is configured — cannot create one at all. It receives a 501 with a code that appears in no AWS model, which SDK error handling cannot classify: it is neither a modeled client error it can branch on (AlreadyExistsException/BadRequestException) nor a retryable throttle (TooManyRequestsException). Any SES event-publication pipeline, and every call that takes a ConfigurationSetName, is unusable, and the emulator's whole SESv2→Firehose→S3 event path is ungraded.

Fix: the operation's handler, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set.rs — implement `handle` against the sesv2 service state (register the named configuration set with its TrackingOptions/DeliveryOptions/ReputationOptions/SendingOptions/SuppressionOptions/VdmOptions/ArchivingOptions/MessageSecurityOptions and Tags, return the empty 200 output, refuse a duplicate name with AlreadyExistsException and a name violating the modeled ConfigurationSetName constraint with BadRequestException) and delete the SCAFFOLDED marker line. The set must then be visible to CreateConfigurationSetEventDestination, SendEmail's ConfigurationSetName and DeleteConfigurationSet in the same state.

Traces: firehose__s3__sesv2.firehose-destination-delivers-two-send-events-within-the-buffering-interval and firehose__s3__sesv2.firehose-destination-rejects-a-role-the-stream-cannot-be-assumed-by — both [error], both aborting on the same first call, sesv2.create_configuration_set(ConfigurationSetName=<generated name>).

## Evidence
Expected: sesv2.create_configuration_set(ConfigurationSetName='sim2real-xsvc-sesfh-<suffix>') returns HTTP 200 with an empty body (CreateConfigurationSetResponse has no members), and the named set is then usable by sesv2.create_configuration_set_event_destination(..., EventDestination={'Enabled': True, 'MatchingEventTypes': ['SEND'], 'KinesisFirehoseDestination': {'IamRoleArn': ..., 'DeliveryStreamArn': ...}}), by sesv2.send_email(ConfigurationSetName=...) and by sesv2.delete_configuration_set(ConfigurationSetName=...). A refusal, if any, is one of the modeled errors: AlreadyExistsException 400 for a name already taken, BadRequestException 400 for a name outside the modeled ConfigurationSetName character/length rule, TooManyRequestsException 429 when throttled.

Actual: both checks fail with botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the CreateConfigurationSet operation: operation CreateConfigurationSet is scaffolded but not implemented in this emulator — HTTP 501, code 'NotImplemented', raised from the first SESv2 setup call in each check. 'NotImplemented' and HTTP 501 appear nowhere in the SESv2 Smithy model for this operation (modeled errors are AlreadyExistsException 400, BadRequestException 400, ConcurrentModificationException 500, LimitExceededException 400, NotFoundException 404, TooManyRequestsException 429). In the message, 'operation ... is scaffolded but not implemented in this emulator' is the emulator's own fixed text and 'CreateConfigurationSet' is the operation name interpolated from the stub; no part of it comes from the request. The handler file confirms the cause: services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_configuration_set.rs line 4 still carries '//! SCAFFOLDED, NOT IMPLEMENTED:' and line 187 is Err(crate::scaffolded::Scaffolded::not_implemented("CreateConfigurationSet")).

Suite context: 107/180 passed. These two are the only failing checks in the run that are neither already filed against an unimplemented-stub issue nor owned by an open issue, and sesv2, firehose and s3 are all bootstrapped.
