# Transcribe Streaming WebSocket data plane is unreachable: /stream-transcription-websocket upgrade answered 404 UnknownService instead of 101 Switching Protocols

> _Note: this issue was identified against the code base at commit `242e2a822ca6eb3fec2aad3ba89160f0a6f40669`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartStreamTranscription

## Description
Cause 1 of 1: the Transcribe Streaming WebSocket data plane endpoint is not reachable on the emulator at all, so every streaming behavior the suite grades is blocked at the connection handshake. All 14 failing transcribe-streaming checks fail identically, before any transcription semantics are exercised.

AWS: Transcribe Streaming exposes StartStreamTranscription over two transports. The HTTP/2 transport is the modeled one -- Smithy: StartStreamTranscription @http {method: POST, uri: /stream-transcription, code: 200}, input AudioStream @httpPayload @streaming @required, output TranscriptResultStream @httpPayload @streaming, parameters carried as x-amzn-transcribe-* headers (MediaSampleRateHertz @required @range 8000..48000, MediaEncoding @required, EnableChannelIdentification default false, NumberOfChannels @range min 2, PartialResultsStability, IdentifyLanguage, LanguageOptions, VocabularyFilterName/Method, ShowSpeakerLabel), modeled errors BadRequestException (400), ConflictException (409), LimitExceededException (429), InternalFailureException (500), ServiceUnavailableException (503); service com-amazonaws-transcribestreaming-transcribe, protocol restJson1, protocol_config eventStreamHttp: [h2], endpointPrefix transcribestreaming, sigv4Name transcribe. The documented WebSocket transport of the SAME operation is reached at the path /stream-transcription-websocket with the StartStreamTranscription parameters moved from x-amzn-transcribe-* headers into query parameters (language-code, media-encoding, sample-rate, enable-channel-identification, number-of-channels, partial-results-stability, identify-language, language-options, ...), the request SigV4 query-signed (X-Amz-Algorithm/X-Amz-Credential/X-Amz-Signature) with signing name transcribe. AWS answers that upgrade request with HTTP/1.1 101 Switching Protocols and a correct Sec-WebSocket-Accept, after which both directions carry vnd.amazon.eventstream messages (AudioEvent up; TranscriptEvent / modeled exceptions down), and the session closes with WebSocket close code 1000. The Smithy model does not describe the WebSocket binding -- it binds only POST /stream-transcription -- so for the WebSocket transport this is recorded behavior only, as exercised by the suite's 14 checks.

Emulator: the upgrade request to /stream-transcription-websocket is not claimed by any emulated service. The emulator answers HTTP/1.1 404 Not Found with content-type: application/x-amz-json-1.1, header x-amzn-errortype: UnknownService and body {"__type":"UnknownService","message":"no emulated service is registered for 'transcribe'"} -- i.e. the router resolved the request's route key to the signing name transcribe from the SigV4 credential scope, found no service claiming it, and returned a service-level 404 rather than a WebSocket handshake. This reproduces for every parameter combination the checks send, including the ones that should be REJECTED with a modeled BadRequestException (media-encoding=mp3, sample-rate=4000, number-of-channels=2 without enable-channel-identification, partial-results-stability without enable-partial-results-stabilization, a tampered X-Amz-Signature, a corrupted eventstream frame, an oversized audio frame): those also get the same 404 UnknownService, so even the negative paths diverge.

Why: a client of the Transcribe Streaming data plane cannot open a session at all. The AWS SDKs and the documented raw-WebSocket integration both open the stream before sending any audio, so the failure is total and immediate: no TranscriptEvent is ever delivered, no partial/final transcript, no ChannelId/ResultId demultiplexing, no speaker labels, no vocabulary-filter masking, no language identification. Worse for test suites written against AWS, the error a client sees is a 404 UnknownService -- an "this API does not exist" shape -- rather than any modeled Transcribe error, so client code that retries or branches on BadRequestException/LimitExceededException/ServiceUnavailableException takes an unrelated branch, and validation tests that expect a 400 BadRequestException for a bad media-encoding or sample-rate cannot distinguish a rejected request from an absent service.

Fix: belongs in this service's request-claim seam and the StartStreamTranscription operation's event-stream transport. services/service-com-amazonaws-transcribestreaming-transcribe/src/service.rs delegates Service::can_handle to can_handle_parts, which calls emulator_server::can_handle_based_on_route_key_and_path with the model-derived crate::ROUTE_PATH_SEGMENTS and requires exact equality of the first URI path segment. Because the Smithy model binds only /stream-transcription, the literal segment stream-transcription-websocket is not in ROUTE_PATH_SEGMENTS, so this service declines the upgrade and the router falls through to its no-service-registered 404. The claim rule must additionally admit the WebSocket data-plane path, and Service::override_operation (which today matches only POST /stream-transcription, /medical-stream-transcription, /medical-scribe-stream) must route the WebSocket path -- noting the upgrade arrives as GET, which the current method != POST guard rejects outright. The handshake itself (101 Switching Protocols, Sec-WebSocket-Accept derived from Sec-WebSocket-Key, framed vnd.amazon.eventstream in both directions, close code 1000) and the mapping of the query-parameter spelling of the StartStreamTranscription input onto the existing EventStreamRoute handler need to live with that operation. Request validation and SigV4-on-the-stream must then surface the operation's modeled errors rather than a router-level 404.

Traces: all 14 transcribe-streaming checks listed in trace_ids; each one aborts at its _stream() helper's `assert upgrade["status"] == 101` with the 404 UnknownService body above. No open issue covers this -- list_existing_issues found no transcribe issue filed, and the report marked none of these checks ALREADY FILED or OWNED.

## Steps to Reproduce
1. Boot the emulator and resolve its harness endpoint (the checks resolve it via ctx.client("sts").meta.endpoint_url rather than formatting a host).
2. Build a SigV4 *query*-signed request for the WebSocket data plane: GET /stream-transcription-websocket?language-code=en-US&media-encoding=pcm&sample-rate=16000, signed with signing name 'transcribe' (X-Amz-Algorithm, X-Amz-Credential, X-Amz-Date, X-Amz-SignedHeaders, X-Amz-Signature in the query string).
3. Open a TCP (or TLS) connection to that endpoint and send the WebSocket upgrade: GET <path+query> HTTP/1.1, Host: <endpoint>, Upgrade: websocket, Connection: Upgrade, Sec-WebSocket-Key: <base64 16 bytes>, Sec-WebSocket-Version: 13.
4. Read the status line. Observed: 'HTTP/1.1 404 Not Found' with x-amzn-errortype: UnknownService and body {"__type":"UnknownService","message":"no emulated service is registered for 'transcribe'"}. Expected: 'HTTP/1.1 101 Switching Protocols' with a valid Sec-WebSocket-Accept.
5. Repeat with an invalid parameter (media-encoding=mp3, or sample-rate=4000, or number-of-channels=2 without enable-channel-identification). Observed: the same 404 UnknownService. Expected: the stream is refused with the operation's modeled BadRequestException (HTTP 400).
6. Replaying the behavioral suite reproduces all of this: run_behavioral_suite reports transcribe-streaming 0/14, every check aborting on `assert upgrade["status"] == 101`.
