# S3 tagging notifications are never published, so the tag-sub-type routing differential never delivers on either the classic s3:ObjectTagging:* subscription or the EventBridge "Object Tags Added"/"Object Tags Deleted" rules (1 cause)

> _Note: this issue was identified against the code base at commit `552fdfb2e9baae984e24adf445e8358a0949e3d3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteObjectTagging

## Description
Cause 1 of 1 — PutObjectTagging and DeleteObjectTagging publish no notification at all, so the sub-type-scoped routes that must distinguish a tag ADDITION from a tag DELETION never receive their own event and the check stalls until the replay budget expires. Failing check: events__s3__sqs.obs-s3-3-tags-deleted-withheld-from-tags-added-routes.

AWS: Smithy (com.amazonaws.s3) — PutBucketNotificationConfiguration takes NotificationConfiguration with QueueConfiguration{QueueArn (required), Events: EventList (required)} and EventBridgeConfiguration{} (empty container); the Event enum enumerates s3:ObjectTagging:*, s3:ObjectTagging:Put and s3:ObjectTagging:Delete as distinct values, so the sub-type is part of the wire contract and a subscription for one value must not receive the other. On the classic path a successful PutObjectTagging delivers an SQS message whose Records[].eventName is "ObjectTagging:Put" and whose Records[].s3.object.key is the tagged key; a successful DeleteObjectTagging delivers Records[].eventName "ObjectTagging:Delete" for the same key. With EventBridgeConfiguration:{} set on the same bucket, S3 additionally publishes to the account's default event bus an envelope with source "aws.s3" and detail-type "Object Tags Added" for PutObjectTagging and "Object Tags Deleted" for DeleteObjectTagging, with detail.bucket.name = the bucket and detail.object.key = the key. Both paths fire for the same call, and each path's two sub-types are routed independently. S3 also validates each QueueConfiguration destination at configuration time by sending an s3:TestEvent, refusing with HTTP 400 InvalidArgument while the queue policy has not yet admitted s3.amazonaws.com.

Emulator: nothing is delivered on either path for either tagging call. The check first configures one bucket with two QueueConfigurations (s3:ObjectTagging:Put -> queue A, s3:ObjectTagging:Delete -> queue B) plus EventBridgeConfiguration:{}, and two EventBridge rules (detail-type ["Object Tags Added"] -> queue C, detail-type ["Object Tags Deleted"] -> queue D), each queue policy admitting the producing principal. CreateBucket, CreateQueue, SetQueueAttributes, PutBucketNotificationConfiguration, GetBucketNotificationConfiguration (which reads the configuration back correctly), PutRule and PutTargets (FailedEntryCount 0) all succeed; PutObject, PutObjectTagging and DeleteObjectTagging all succeed. Then every ReceiveMessage on all four queues returns no messages, so the warm-up loop that requires two consecutive rounds of delivery to all four probes never advances and the replay terminates the check: "Error: Check timed out after 60.0s". No status or error code diverges here — the divergence is the total absence of the published events.

Why: a client relying on AWS's behavior wires tag-governance and audit pipelines on the tagging sub-types — e.g. a compliance consumer subscribed only to s3:ObjectTagging:Delete / "Object Tags Deleted" to catch tag removal, and a classification consumer on s3:ObjectTagging:Put / "Object Tags Added". Against the emulator both consumers are silent forever while the bucket, the rules and the targets all report healthy, so the client cannot distinguish "no tag change happened" from "the notification path is dead", and a test suite that asserts the add-routes stay SILENT for a deletion passes vacuously: the differential is unobservable because nothing is delivered at all, so a later regression that maps both tagging calls to one event type, or ignores the sub-type in a subscription or in a detail-type pattern, would not be caught.

Fix: the S3 notification publisher — the emission of classic QueueConfiguration records and of default-bus aws.s3 envelopes from the PutObjectTagging and DeleteObjectTagging handlers in services/service-com-amazonaws-s3-amazons3/src/ops/, including the per-event-type matching of QueueConfiguration.Events (s3:ObjectTagging:Put vs s3:ObjectTagging:Delete vs s3:ObjectTagging:*) and the detail-type selection ("Object Tags Added" vs "Object Tags Deleted"); plus the EventBridge default-bus ingestion that must match those envelopes against rule patterns and fan them out to SQS targets.

Related open issue, NOT the same work item and it does not cover this check: 20261025T002357Z-events-s3-sqs-s3-produces-no-aws-s3-events-on-either.md describes the same family of silence but carries only the replay keys of events__s3__sqs.s3-notification-to-sqs-direct, .object-restore-initiated-and-tags-added-carry-their-own-detail-types, .obs-s3-3-object-acl-put-reaches-both-paths, .obs-s3-3-object-tagging-put-and-delete-reach-both-paths, .xsvc-s3-1-acl-update-and-tag-delete-route-to-their-own-rules and .obs-s3-3-acl-rejected-under-bucket-owner-enforced-emits-no-event; the check filed here is absent from it, and its specific requirement — that the two tagging sub-types route to DIFFERENT subscriptions and detail-types on one bucket, and that the add-routes stay live after the delete — is not among that issue's assertions.

Traces: events__s3__sqs.obs-s3-3-tags-deleted-withheld-from-tags-added-routes (verdict mismatch, "Check timed out after 60.0s").

## Evidence
Failing check events__s3__sqs.obs-s3-3-tags-deleted-withheld-from-tags-added-routes, verdict mismatch, detail "Error: Check timed out after 60.0s".

Expected (AWS): after PutObjectTagging(Bucket=b, Key=k, Tagging={TagSet:[{Key:'k',Value:'1'}]}) the queue subscribed with Events=["s3:ObjectTagging:Put"] receives a message whose Records[0].eventName == "ObjectTagging:Put" and Records[0].s3.object.key == k, and the queue targeted by the rule EventPattern {"source":["aws.s3"],"detail-type":["Object Tags Added"],"detail":{"bucket":{"name":[b]}}} receives an envelope with source "aws.s3", detail-type "Object Tags Added" and detail.object.key == k. After DeleteObjectTagging(Bucket=b, Key=k) the same holds with eventName "ObjectTagging:Delete" and detail-type "Object Tags Deleted" on the OTHER two queues, and the two add-scoped queues receive nothing for the deletion. The check's own delivery budget is 90 s per await and 150 s for the warm-up, so these arrivals are expected well inside it.

Actual (emulator): all configuration and all data-plane calls return 200 — GetBucketNotificationConfiguration reads back both QueueConfigurations and the EventBridgeConfiguration exactly as written, PutTargets reports FailedEntryCount 0, PutObject/PutObjectTagging/DeleteObjectTagging succeed — but ReceiveMessage on all four queues (classic-put, classic-delete, eb-added, eb-deleted) returns no messages for the whole run. The check never gets past its warm-up stage (two consecutive rounds in which all four probes must receive their own event) and is cut off at 60 s. Nothing is published on either path, so neither the positive controls nor the negative differential can be observed.

Note on what is and is not a requirement here: the bucket name, queue names, rule names, object keys and the exact timings in a run are per-run values. The requirements are the delivery itself and the fixed field values — Records[].eventName "ObjectTagging:Put" / "ObjectTagging:Delete" on the classic path, and source "aws.s3" with detail-type "Object Tags Added" / "Object Tags Deleted" on the EventBridge path — with the bucket and key taken from the request.
