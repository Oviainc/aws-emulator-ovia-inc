# RUM reads report emulator-minted values instead of the API's own: GetAppMonitor's vended CwLogGroup and BatchGetRumMetricDefinitions' id-ordered listing

> _Note: this issue was identified against the code base at commit `80961682c94094ddbc8e099b7f0d738124a427db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetAppMonitor

## Description
This issue bundles TWO distinct net-new wire divergences of the CloudWatch RUM emulator (service token `rum`, bootstrapped as service-com-amazonaws-rum-rum). BOTH must be closed before submitting; each is numbered below and carries its own fixture and step. Neither is covered by an open issue: the replay marked no owner for either cluster, and the two adjacent open issues (20261029T133728Z-rum-batchgetrummetricdefinitions-pagination.md, which is about decode_pagination_token accepting uppercase hex spellings, and 20261029T072756Z-rum-createappmonitor-event-propagation.md, which is about a refused create having already provisioned the vended log group) describe different defects in the same files.

Cause 1 of 2: GetAppMonitor advertises a DataStorage.CwLog.CwLogGroup that is not the vended log-group name the rest of the recorded session uses for that monitor, and it suppresses the name entirely while delivery is off.
AWS: Smithy: GetAppMonitor -> AppMonitor.DataStorage (DataStorage) -> CwLog (CwLog) with members CwLogEnabled (Boolean, "Indicated whether the app monitor stores copies of the data that RUM collects in CloudWatch Logs") and CwLogGroup (String, "The name of the log group where the copies are stored"); the model places no @pattern and no @length on CwLogGroup, so recorded behavior only: RUM vends ONE CloudWatch Logs group per app monitor, named with the vended-logs prefix and the monitor's own name followed by a service-chosen suffix, and every read of that monitor reports that SAME value — which is why the corpus binds it as the fixture variable `{{cw_log_group}}` and then requires each later read of the monitor to report the bound value. The value is a generated name, so no literal from any one recording is a requirement; what is required is that the name a read reports is the one this API already established for that monitor, for a monitor read after its configuration changes as well as for a freshly created one.
Emulator: the step answers HTTP 200 with the right body shape but with a CwLogGroup the fixture's binding does not match: `$.AppMonitor.DataStorage.CwLog.CwLogGroup: value_mismatch (expected '{{cw_log_group}}', got '/aws/vendedlogs/RUMService_<app monitor name><12 hex characters>')`. The name is minted by ComAmazonawsRumRumState::mint_cw_log_group (services/service-com-amazonaws-rum-rum/src/state.rs:1349) out of this emulator's own id machinery — CW_LOG_GROUP_PREFIX plus the monitor name plus CW_LOG_GROUP_SUFFIX_LEN=12 hex characters of a minted token (state.rs:137-147, 2491) — a width and alphabet the comment itself calls "this emulator's own". Beside that, AppMonitorRecord::cw_log_group (state.rs:986) returns None whenever cw_log_enabled is false, so the monitor's stored vended_log_group — which the record holds for every monitor, delivery on or off (state.rs:920-935) — is invisible to a reader until delivery is turned on, and the name the fixture needs to bind is therefore not observable from the first read of a monitor created with CwLogEnabled false. Hypothesis: that is how the binding is left unsatisfied in the basic-lifecycle fixture, whose divergent read comes after the monitor's configuration was changed.
Why: CwLogGroup is the handle a client uses against CloudWatch Logs — tailing the group, setting retention on it, reading its resource policy. A client that reads the name from one GetAppMonitor and uses it later addresses a group that the API's other reads of the same monitor do not agree on, and a client that reads a monitor before enabling delivery gets null for a group the service has already chosen, so it cannot pre-create permissions or dashboards for it.
Fix: the vended log-group name in this service's state — mint_cw_log_group / cw_log_group_name and the AppMonitorRecord::cw_log_group projection that GetAppMonitor (services/service-com-amazonaws-rum-rum/src/ops/get_app_monitor.rs:193) reports through — must report the one name this service vended for the monitor on every read of it, including the reads taken before CwLogEnabled is turned on, and must shape the service-chosen part the way RUM's vended group names are shaped rather than with a self-chosen 12-hex-character width.
Traces: rum-app-monitor-full-configuration#task#2 (the representative in Issue-Trace/Issue-Step) and rum-basic-app-monitor-lifecycle#task#4 — 2 steps in the cluster.

Cause 2 of 2: BatchGetRumMetricDefinitions reports a destination's metric definitions ordered by the minted MetricDefinitionId instead of in the order they were created, so the Nth entry of the listing is a different definition than AWS's Nth.
AWS: Smithy: BatchGetRumMetricDefinitions is @readonly and @paginated (items MetricDefinitions, inputToken/outputToken NextToken, pageSize MaxResults) and returns MetricDefinitions, a list of MetricDefinition{MetricDefinitionId @required, Name @required, ValueKey, UnitLabel, DimensionKeys, EventPattern, Namespace}; the model documents no sort order, so recorded behavior only: the recorded listing enumerates the destination's definitions in the order BatchCreateRumMetricDefinitions created them, so position N of the listing is the Nth definition created and is stable across calls. In the recording, after a partial BatchDeleteRumMetricDefinitions the surviving definition at index 0 is the third one created (Name "MetricC").
Emulator: the same step answers HTTP 200 with a definition whose MetricDefinitionId is the one the corpus bound at that position but whose Name is the FIRST definition created: `$.MetricDefinitions[0]: expected {... 'Name': 'MetricC' ...}, got {... 'Name': 'MetricA' ...}` with identical MetricDefinitionId, EventPattern and Namespace in both. The cause is in the reader: metric definitions are held in a BTreeMap keyed by the minted MetricDefinitionId and the page is produced by a range scan over that map (services/service-com-amazonaws-rum-rum/src/ops/batch_get_rum_metric_definitions.rs:283-308, resuming on an id with Bound::Excluded), and the id is a hash-derived version-4 UUID minted per definition (state.rs:1359-1372). The resulting order is UUID-lexicographic, i.e. arbitrary with respect to creation order and different for every run, and the continuation token encodes that id as the resume point, so the paged order is arbitrary too. BatchDeleteRumMetricDefinitions itself removes exactly the ids it is given and is not at fault.
Why: callers correlate a destination's definitions by position in the listing — it is the only ordering the API offers, and (because BatchCreateRumMetricDefinitions does not echo what it created, open issue 20261031T062024Z) the listing is also the only way to learn the ids. With an arbitrary order, the id a client reads at a given position names a different definition than it does against AWS, so an update or a batch delete driven off that listing touches the wrong definition; the surviving definition after the recorded partial delete is MetricA where AWS leaves MetricC. The order also changes from run to run, so nothing built on it is reproducible.
Fix: the listing and resume logic of the BatchGetRumMetricDefinitions handler, together with the per-destination definition store in state.rs that it ranges over — definitions must be enumerated in creation order (an insertion-ordered sequence, or an explicit creation sequence number used as the sort and pagination key) rather than by minted id, and the continuation token must resume on that ordering.
Traces: rum-batch-delete-partial-metrics#task#6 — 1 step in the cluster.
