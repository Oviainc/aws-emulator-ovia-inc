# managedblockchain-query query responses diverge: wrong chain data, un-normalized addresses, mis-shaped batch error items, partial validation

> _Note: this issue was identified against the code base at commit `bd3308b0c8d992d57414e8fe0564c68280e702c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListTransactions

## Description
Replay of the wire corpus (trace set simparity-wire-aws-v1, 8 fixtures / 20 steps, 5 passed) shows that the SUCCESS paths of this service are as divergent as its error paths: the read operations answer HTTP 200 but with bodies that are not the bodies AWS returns for the queried dataset, chain addresses are echoed in the caller's casing instead of AWS's lowercase form, and one 400 reports only the first of several violated fields. SIX independent causes, all net-new (no stub_path, no owning open issue). Each needs its own fix; a fixer must close all six before submitting.

Related open issue (it carries NONE of the six replay keys below, so it does not cover any of them): "managedblockchain-query error responses are not AWS-shaped: ValidationException omits required reason, per-field detail and batch item errors" (20261022T132335Z-...). That issue owns the pure 4xx shaping steps; the causes here are about 200-body content, address normalization, batch per-item error CONTENT, and multi-field validation coverage.

--- Cause 1 of 6: ListTransactions returns an empty transactions list for an address that has transactions in the dataset ---
AWS: Smithy ListTransactions (POST /list-transactions, http code 200, readonly, paginated{items: transactions, inputToken/outputToken nextToken, pageSize maxResults}) takes required address (ChainAddress, @pattern ^[-A-Za-z0-9]{13,74}$) and required network (QueryNetwork: ETHEREUM_MAINNET | ETHEREUM_SEPOLIA_TESTNET | BITCOIN_MAINNET | BITCOIN_TESTNET), and returns required transactions (TransactionOutputList, @length 0..250) of TransactionOutputItem{transactionHash required, network required, transactionTimestamp required, transactionId, confirmationStatus}. Recorded behavior: querying the fixture's Ethereum address on ETHEREUM_MAINNET returns a non-empty page whose first item is a FINAL transaction on ETHEREUM_MAINNET (recorded values are an example: transactionHash 0x7671e86accfb3cd75a9000e2d7eabced7fedab72aadeb93a4232cf1729b4e219, transactionTimestamp 1619073240). The requirement is that a transaction held for an address/network pair is listed for that pair.
Emulator: HTTP 200 with the transactions list missing its first element (replay: "$.transactions[0]: missing ... got None") — i.e. an empty page for an address the dataset has transactions for.
Why: this is the entry point of the service's main workflow. A client that lists an address's history and then fetches each transaction gets nothing to iterate, so it concludes the address is unused; nothing downstream of the listing can be reached. Hypothesis: this is also why the replay reports 2 blocked steps in this corpus — the dependent get-transaction step in this fixture has no hash to carry forward.
Fix: the ListTransactions handler and the state lookup it calls (src/ops/list_transactions.rs plus the transaction index in src/state.rs of the managedblockchain-query service crate) — resolve transactions by participating address + network out of the seeded chain data instead of returning an empty list.
Traces: managedblockchain-query-list-transactions-then-get-transaction#task#1.

--- Cause 2 of 6: ListFilteredTransactionEvents serves a page of events that is not the dataset's matching events, and a non-matching nextToken ---
AWS: Smithy ListFilteredTransactionEvents (POST /list-filtered-transaction-events, http code 200, paginated{items: events}) takes required network and required addressIdentifierFilter (AddressIdentifierFilter{transactionEventToAddress required, ChainAddresses @length 1..1}) and returns required events (TransactionEventList @length 0..250) of TransactionEvent{network required, transactionHash required, eventType required, to, value, tokenId, transactionId, voutIndex, voutSpent, blockchainInstant, confirmationStatus} plus optional nextToken. Recorded behavior: for the Bitcoin recipient address in the filter, the response is the dataset's BITCOIN_VOUT events for that recipient on BITCOIN_MAINNET, each with to = the filtered address, tokenId btc, voutIndex/voutSpent populated and confirmationStatus FINAL, ordered newest-first by blockchainInstant, together with the page's nextToken. The requirement is that the events returned are the events the dataset holds for the filtered recipient; the individual hashes/values/timestamps in the recording are examples.
Emulator: HTTP 200, but both $.events and $.nextToken diverge from the recorded page (divergence key keys=$.events,$.nextToken) — the served page is not the recorded event set for that address filter.
Why: this is the only API for Bitcoin vout history. A client reconciling unspent outputs gets a page it cannot reconcile against the chain data the same emulator serves through ListTransactions/GetTransaction, and a nextToken that does not continue the recorded page.
Fix: the ListFilteredTransactionEvents handler and the event index it queries (src/ops/list_filtered_transaction_events.rs plus the transaction-event index in src/state.rs) — select events whose `to` matches the single filtered address, honour the time/vout/confirmation filters and the sort, and page them with a token consistent with that selection.
Traces: managedblockchain-query-bitcoin-filtered-transaction-events#task#1.

--- Cause 3 of 6: ListFilteredTransactionEvents validation stops at the first bad field, so fieldList omits the addressIdentifierFilter violation ---
AWS: ValidationException (httpError 400) models message (required), reason (required) and fieldList (ValidationExceptionFieldList of ValidationExceptionField{name required, message required}), described as the container for the exception's field list. Note that ListFilteredTransactionEventsInput$network targets a plain String rather than QueryNetwork, so the network check is service-side rather than a modeled enum. Recorded behavior: a request that names a non-Bitcoin network AND an address that is not valid for Bitcoin is answered 400 ValidationException with TWO fieldList entries — one named "network" and one named "addressIdentifierFilter" (recorded messages "Please use a blockchain network supported by this API." and "Please provide a valid bitcoin address." are examples). The requirement is one fieldList entry per violated field: every field that failed is reported in the same response.
Emulator: HTTP 400 (status and error code agree) with only the "network" entry; $.fieldList[name="addressIdentifierFilter"] is absent entirely, so the second violation is never reported. Its network entry's message is additionally handler-built from the enum set ("network must be one of [BITCOIN_MAINNET, BITCOIN_TESTNET], not ETHEREUM_MAINNET") where AWS sends a request-independent sentence; the recorded sentence is an example only and the message difference alone is not what is filed here — the missing per-field entry is.
Why: fieldList is the machine-readable half of this error. A client that reads it to repair its request fixes the network, resubmits, and is rejected again for an address problem it was never told about — one round trip per violated field instead of one.
Fix: input validation for this operation (src/ops/list_filtered_transaction_events.rs plus the ValidationException construction helper in src/state.rs) — accumulate every field violation into fieldList rather than returning on the first.
Traces: managedblockchain-query-bitcoin-filtered-transaction-events#task#2.

--- Cause 4 of 6: chain addresses are echoed back in the caller's casing instead of this API's lowercase form ---
AWS: ChainAddress (@pattern ^[-A-Za-z0-9]{13,74}$) is the type of GetAssetContractOutput$deployerAddress, ContractIdentifier$contractAddress, OwnerIdentifier$address and TransactionEvent$from/to/contractAddress — the pattern admits mixed case, so the model does not settle the rendering and this is recorded behavior only. Both recordings show the same rule: an EVM address supplied to the request in EIP-55 checksum casing comes back LOWERCASED in the response, both in GetAssetContract's echoed contractIdentifier.contractAddress and in BatchGetTokenBalance's per-item errors[].ownerIdentifier.address. The requirement is the normalization, not the particular address.
Emulator: echoes the request bytes verbatim, so the checksum casing survives into the response — GetAssetContract returned 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48 where AWS returns 0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48, and the batch error item returned 0xd8dA6BF26964aF9D7eEd9e03E53415D37aA96045 where AWS returns 0xd8da6bf26964af9d7eed9e03e53415d37aa96045.
Why: clients key caches, dedupe sets and joins on the address string returned by the API. Against AWS those keys are lowercase and stable regardless of how the request was written; against the emulator they vary with the caller's casing, so the same holding appears as two different owners and a lookup by a response-derived key misses.
Fix: the response serialization path for ChainAddress-typed members shared by these handlers (the address normalization helper used by src/ops/get_asset_contract.rs and src/ops/batch_get_token_balance.rs, or the ChainAddress serializer in src/state.rs) — lowercase on the way out rather than echoing the request.
Traces: managedblockchain-query-get-asset-contract-lookup#task#1 (contractIdentifier.contractAddress) and managedblockchain-query-batch-get-token-balance-mixed#task#1 (errors[0].ownerIdentifier.address).

--- Cause 5 of 6: balances and contract metadata are synthesized rather than read from the queried dataset, and the same wrong balance is served by both balance operations ---
AWS: recorded behavior only for the values themselves. GetTokenBalance (POST /get-token-balance) returns required balance (String) and required atBlockchainInstant for a (tokenIdentifier, ownerIdentifier) pair; BatchGetTokenBalanceOutput$tokenBalances carries the same per-item shape; GetAssetContractOutput$deployerAddress is a required ChainAddress. The recordings show these are properties of the queried dataset, identical across operations: the same owner/token pair reports balance 119094756568 through BOTH GetTokenBalance and BatchGetTokenBalance, and the queried contract reports deployerAddress 0x95ba4cf87d6723ad9c0db21737d862be80e93911. The requirement is that a balance/contract fact is read from the chain data the service holds, so repeated and batched reads of the same key agree with the single read and with the dataset.
Emulator: serves values unrelated to the dataset — balance 996250000000 for that owner/token pair on both GetTokenBalance and the batch form (so it is internally consistent but externally wrong, which points at a generator rather than a lookup), and deployerAddress 0x6117ad6d33522adfc168aa29a7c4fca3597710a8 for the queried contract. Statuses are 200 as expected.
Why: a client that reads a balance and asserts on it, reconciles a batch against single reads, or resolves a contract's deployer gets numbers the service itself did not record. Hypothesis: the handlers derive these fields from the request (hash/seed) instead of resolving the seeded holding, which is why the wrong value is stable.
Fix: the balance and contract lookups in state (src/ops/get_token_balance.rs, src/ops/batch_get_token_balance.rs and src/ops/get_asset_contract.rs resolving against the seeded holdings/contract tables in src/state.rs) — look the fact up and surface not-found rather than generating a value.
Traces: managedblockchain-query-token-balance-single-and-list#task#1 ($.balance) plus managedblockchain-query-batch-get-token-balance-mixed#task#1 ($.tokenBalances[0].balance) and managedblockchain-query-get-asset-contract-lookup#task#1 ($.deployerAddress).

--- Cause 6 of 6: BatchGetTokenBalance per-item error entries carry the exception NAME in errorCode and omit atBlockchainInstant ---
AWS: Smithy BatchGetTokenBalanceErrorItem requires errorCode (String, "the error code associated with the error"), errorMessage (String) and errorType (ErrorType: VALIDATION_EXCEPTION | RESOURCE_NOT_FOUND_EXCEPTION), and additionally carries tokenIdentifier, ownerIdentifier and atBlockchainInstant to identify WHICH input item failed. Recorded behavior: errorCode holds the numeric HTTP status string of the per-item failure ("404" for an unresolvable item here, "400" for a validation failure in the sibling recording), with the exception identity carried by errorType — and the failing item's atBlockchainInstant is echoed in the entry (recorded {"time": 1788657502.0}, an example value). The requirement is the numeric-status errorCode plus a populated atBlockchainInstant identifying the item; errorType already agrees.
Emulator: HTTP 200 with the entry present but errorCode set to "ResourceNotFoundException" — the exception name, duplicating errorType — and atBlockchainInstant absent from the entry.
Why: errorCode and errorType are two different fields precisely so a client can branch on the status class and on the exception kind separately; collapsing one into the other leaves a client that switches on errorCode == "404" never matching. With atBlockchainInstant missing, the entry cannot be joined back to the submitted input item when the same token/owner was queried at several instants in one batch.
Fix: the per-item error construction in src/ops/batch_get_token_balance.rs — set errorCode from the per-item failure's HTTP status and echo the item's atBlockchainInstant (alongside tokenIdentifier/ownerIdentifier) into the BatchGetTokenBalanceErrorItem.
Traces: managedblockchain-query-batch-get-token-balance-mixed#task#1.
