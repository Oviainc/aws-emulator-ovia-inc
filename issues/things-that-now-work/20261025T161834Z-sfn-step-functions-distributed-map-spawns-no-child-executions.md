# Step Functions: Distributed Map spawns no child executions (ListExecutions(mapRunArn) empty) and a States.Runtime failure is wrongly retried and caught (2 causes)

> _Note: this issue was identified against the code base at commit `f869d1ee30dbd1fe652bf17033c00c4415346847`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListExecutions

## Description
This issue bundles TWO distinct net-new root causes in the Step Functions execution interpreter. BOTH must be closed before submitting; re-replay every check id listed in trace_ids.

=== Cause 1 of 2: a Distributed Map state spawns no child executions, so ListExecutions(mapRunArn) returns an empty list ===
Failing check id: sfn.conc-distributed-map-child-executions-listed-and-describable-per-item.
AWS: Smithy (services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json) models ListExecutions with input members stateMachineArn (Arn, @length 1..256), mapRunArn (LongArn, @length 1..2000), statusFilter, redriveFilter, maxResults (@range 0..1000), nextToken, and output {executions: ExecutionList (required), nextToken}; errors InvalidArn, InvalidToken, ResourceNotFound (404), StateMachineDoesNotExist, StateMachineTypeNotSupported, ValidationException. DescribeExecution output carries mapRunArn (LongArn) alongside input/output/status. The end-to-end semantics are recorded behavior only: entering a Map state whose ItemProcessor.ProcessorConfig.Mode is DISTRIBUTED creates one MapRun and starts exactly ONE child execution per item of ItemsPath. ListExecutions(mapRunArn=<the map run>) then enumerates exactly those N children, each with status SUCCEEDED when its inner workflow succeeded; DescribeExecution on each child returns that child's OWN input (the ItemSelector projection for its item) and its OWN output, and names the parent map run in mapRunArn. The ARNs the listing returns are the same values the children observe as $$.Execution.Id, and the children run under the state machine ListMapRuns reports in stateMachineArn. Children are indexed under the map run only: ListExecutions(stateMachineArn=<parent machine>) returns the parent execution and NONE of the children.
Emulator: the parent execution reaches SUCCEEDED, a map run is obtained, but ListExecutions(mapRunArn=<map run>) returns zero executions for a run over 8 items — AssertionError: "ListExecutions(mapRunArn) returned 0 children (0 distinct) for 8 items". No child execution exists, so the per-child DescribeExecution input/output assertions, the $$.Execution.Id ledger cross-check and the parent-vs-children indexing assertion are all unreachable. Note the already-open issue 20261025T053834Z-sfn-step-functions-distributed-map-creates-no-map-run.md covers only ListMapRuns being empty for check s3__sfn.sfn-redrive-of-a-partly-failed-map-run-reruns-only-the-failed-items; it does not carry this check's replay key and it does not cover the child-execution listing/indexing described here. Related-but-not-covering: 20261024T043150Z-sfn-step-functions-interpreter-does-not-run-the-workflow.md.
Why: a client cannot observe, enumerate or inspect the executions a Distributed Map spawned. Code that polls ListExecutions(mapRunArn) to find per-item children gets an empty page and either loops forever or concludes the map processed nothing; per-item inputs/outputs and per-item failure attribution are invisible; and because nothing is spawned, a Distributed Map silently processes no items while the parent still reports SUCCEEDED, which is strictly worse than a failure because it looks like success.
Fix: the Step Functions interpreter's Map-state handler in DISTRIBUTED mode must start one real child execution per item (bound to the MapRun and to the map run's stateMachineArn, with the ItemSelector projection as the child's input and the inner workflow's result as its output), and the execution state must index those children under the MapRun so ListExecutions' handler serves them for mapRunArn while ListExecutions for the parent's stateMachineArn continues to exclude them; DescribeExecution's serializer must populate mapRunArn for a child.
Traces: sfn.conc-distributed-map-child-executions-listed-and-describable-per-item.

=== Cause 2 of 2: a States.Runtime failure is retried by a States.ALL retrier and caught by a catcher, instead of terminating the execution ===
Failing check id: sfn.deep-sfn-language-states-runtime-escapes-retry-and-catch-rejected.
AWS: recorded behavior only — the Smithy model describes no ASL error-handling semantics. AWS classifies States.Runtime as a terminal, non-retriable and non-catchable error: a States.Runtime failure is NOT retried by a Retry block (not even one whose ErrorEquals is ["States.ALL"]) and is NOT matched by any Catch block, including a catcher naming States.Runtime explicitly or States.ALL. The execution terminates immediately: DescribeExecution reports status FAILED with error exactly "States.Runtime" and a cause naming the construct that failed (here the intrinsic invocation, so the cause text contains "States.MathAdd"). The fixed text is the error name "States.Runtime"; the cause's variable parts are the failing expression and argument taken from the definition and the request input. Consequently the failing branch runs exactly ONCE (one side-effect write, not one per retry attempt) and no catcher target state is ever entered.
Emulator: the same machine, given input {"num": "one"}, ends SUCCEEDED. The intrinsic failure is reported as error name "States.IntrinsicFailure" (cause "'States.MathAdd($.num, 1)': argument 1 of 'States.MathAdd' must be a finite number") and that error is treated as an ordinary, catchable error: the States.ALL catcher matches it and routes to its Next state, so the execution recovers and DescribeExecution returns status 'SUCCEEDED' with output {"pk":<pk>,"num":"one","err":{"Error":"States.IntrinsicFailure","Cause":"'States.MathAdd($.num, 1)': argument 1 of 'States.MathAdd' must be a finite number"}} instead of FAILED / error "States.Runtime". The positive control in the same machine (a Fail state raising Tally.Boom, retried 3 times then caught) passes, so the Retry/Catch wiring itself works — what diverges is the terminal classification of States.Runtime. The already-open issue 20261024T043150Z-sfn-step-functions-intrinsic-functions-diverge-wrong-error-name.md Cause 1 covers only the error NAME emitted for a failed intrinsic; it does not carry this check's replay key and it does not cover the retriability/catchability classification, which is a separate decision in the error-handling path and must be fixed even after the name is corrected.
Why: a client relying on AWS's behavior gets the opposite outcome in two ways. Non-retriability is a safety property: on AWS a States.Runtime failure performs the branch's side effects once, while the emulator re-runs the branch under a States.ALL retrier, duplicating every side effect the branch performed before the failure (the check counts this with a DynamoDB counter: AWS yields 1, a retrying implementation yields more). Non-catchability is a correctness property: on AWS the execution FAILS and the operator sees error "States.Runtime"; in the emulator a catcher swallows it and the execution reports SUCCEEDED, so a workflow with a broad States.ALL catcher masks a definition bug entirely and monitoring on ExecutionsFailed never fires.
Fix: the error-classification step of the Step Functions interpreter's Retry/Catch evaluator — a States.Runtime failure (including an intrinsic-evaluation failure, which must also be named States.Runtime per the related issue) must bypass retrier matching and catcher matching altogether and terminate the execution as FAILED with error "States.Runtime" and a cause naming the failing expression. This is the retry/catch matching component, not the intrinsic evaluator itself.
Traces: sfn.deep-sfn-language-states-runtime-escapes-retry-and-catch-rejected.
