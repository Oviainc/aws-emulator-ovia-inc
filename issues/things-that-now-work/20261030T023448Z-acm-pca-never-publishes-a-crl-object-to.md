# ACM PCA never publishes a CRL object to the configured S3 bucket, so server-side CRL generation and post-revocation CRL refresh never happen

> _Note: this issue was identified against the code base at commit `d2ebcd8c12cc6501ce5e652d8f3a2ce865548576`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateCertificateAuthority

## Description
Cause 1 of 1: the emulator accepts and stores an enabled CrlConfiguration but never writes the CRL object the CA is supposed to publish, so no client can ever observe `crl/<ca-id>.crl` in the configured bucket — neither the initial CRL that follows the first issuance, nor the refreshed CRL that follows a RevokeCertificate.

AWS: Smithy model, shape `CrlConfiguration` (acm-pca-2017-08-22): "You can enable CRLs for your new or an existing private CA by setting the Enabled parameter to true. Your private CA writes CRLs to an S3 bucket that you specify in the S3BucketName parameter." The same doc states the publication is server-side and autonomous ("The CRL is refreshed prior to a certificate's expiration date or when a certificate is revoked. When a certificate is revoked, it appears in the CRL until the certificate expires", and "A CRL is typically updated approximately 30 minutes after a certificate is revoked"). The object is a DER-encoded RFC 5280 v2 CRL, keyed `crl/<ca-id>.crl` under the bucket named by `CrlConfiguration.S3BucketName`, whose `nextUpdate` is derived from `CrlConfiguration.ExpirationInDays` and whose `Issuer` is the private CA's X.500 distinguished name. There is NO client-callable publish or regenerate operation anywhere in the model — the only way a client can observe a CRL is for the service to deposit it itself. The CA's own CRL lifecycle is therefore a required server-side effect of enabling CRLs plus issuing/revoking, not of any API call.

Emulator: `UpdateCertificateAuthority` (services/service-com-amazonaws-acmpca-acmprivateca/src/ops/update_certificate_authority.rs) validates the revocation configuration (`crate::state::invalid_revocation_configuration_reason`), resolves the bucket with `HeadBucket` (`crate::state::unresolvable_crl_bucket`), and then merely records the configuration on the CA record (`record.revocation_configuration = Some(revocation)`). Nothing in the service crate ever constructs, signs, or PUTs a CRL: `services/service-com-amazonaws-acmpca-acmprivateca/src/state.rs` contains only CRL *validation* and bucket-*resolution* helpers, and its only S3 use is the `HeadBucket` existence probe in `unresolvable_crl_bucket`. Consequently a client that enables CRLs, issues a leaf, and lists/gets `crl/<ca-id>.crl` sees the bucket stay empty forever; both grounded checks sit in their polling loop and are killed by the harness ceiling (reported as `Check timed out after 60.0s` — the checks themselves budget 1500s/2400s because real AWS takes minutes, so the ceiling only truncates an already-unbounded wait on an object that is never written). The second check cannot even reach its RevokeCertificate step, because it blocks on the initial CRL first.

Why: revocation is unobservable. A relying party in the emulated environment validates certificates against the CRL distribution point the CA advertises; with no CRL object ever deposited, every CRL fetch 404s, so a TLS client configured for hard-fail CRL checking rejects all certificates and one configured for soft-fail accepts revoked ones. Any client that drives the documented flow "enable CRLs -> issue -> revoke -> re-read the CRL" hangs or times out instead of seeing the serial appear, and code that waits for the CRL before declaring a CA ready never proceeds. No error is returned to tell the client the mechanism is inert — the CA reports `CrlConfiguration.Enabled == true` and the configured bucket, which the emulator does serve correctly, so the failure is silent.

Fix: the CA's revocation state and its CRL writer. `UpdateCertificateAuthority`/`CreateCertificateAuthority` should arm CRL publication when an enabled `CrlConfiguration` is stored, and the private-CA state (`src/state.rs`) should own generating the DER-encoded RFC 5280 v2 CRL for a CA — issuer DN from the CA certificate, `nextUpdate` from `ExpirationInDays`, a monotonically increasing CRL number, the revoked-serial list with per-entry revocation date and reason code — and PUT it to `crl/<ca-id>.crl` in the configured bucket through the same in-process S3 client `state.rs` already builds for `HeadBucket`, on first issuance and again on every `RevokeCertificate`. The publication must be prompt in emulated time rather than reproducing AWS's ~30-minute delay. `RevokeCertificate` (src/ops/revoke_certificate.rs) is additionally an unimplemented stub, filed separately as 20261029T193511Z-acm-pca-revokecertificate-stub.md; implementing it is a prerequisite for the refresh half of this cause but does not by itself produce the initial CRL, which is what both grounded checks block on.

Traces: acm-pca.crl-generation-server-managed-publish (enable CRLs via UpdateCertificateAuthority, issue a leaf, wait for crl/<ca-id>.crl to appear — object never appears); acm-pca.revoke-certificate-triggers-server-side-crl-update (same setup, then expects the published CRL to gain the revoked serial — blocks on the initial CRL that is never written).

## Evidence
Expected (AWS): after `UpdateCertificateAuthority(RevocationConfiguration={CrlConfiguration:{Enabled:true, ExpirationInDays:N, S3BucketName:<bucket>, S3ObjectAcl:"BUCKET_OWNER_FULL_CONTROL"}})` and an `IssueCertificate`/`GetCertificate` on an ACTIVE CA, S3 `ListObjectsV2`/`GetObject` on `<bucket>` returns the key `crl/<ca-id>.crl` (`<ca-id>` is the last ARN path segment of `CertificateAuthorityArn`) whose body is a DER-encoded RFC 5280 v2 CRL issued by the CA; after `RevokeCertificate(CertificateSerial=<serial>, RevocationReason=UNSPECIFIED)` the object is rewritten and its revoked-certificate list contains `<serial>` with a revocation date and the X509v3 CRL Reason Code. No client-side publish call exists.

Actual (emulator): `UpdateCertificateAuthority` returns 200 and `DescribeCertificateAuthority` echoes `RevocationConfiguration.CrlConfiguration.Enabled == true` with the correct `S3BucketName`, but the bucket remains empty indefinitely — `crl/<ca-id>.crl` is never created, so every `GetObject` for it fails with NoSuchKey. Both grounded checks poll and are terminated by the harness: `Error: Check timed out after 60.0s` for acm-pca.crl-generation-server-managed-publish and acm-pca.revoke-certificate-triggers-server-side-crl-update. Code evidence that no writer exists: services/service-com-amazonaws-acmpca-acmprivateca/src/ops/update_certificate_authority.rs stores the config only (line ~285, `record.revocation_configuration = Some(revocation)`); services/service-com-amazonaws-acmpca-acmprivateca/src/state.rs has CRL validation (`invalid_revocation_configuration_reason`) and a bucket probe (`unresolvable_crl_bucket`, `s3_client`, `CRL_BUCKET_ABSENT_MESSAGE = "The S3 bucket you provided does not exist."`) and no CRL construction or S3 PutObject at all.

## Steps to Reproduce
1. CreateCertificateAuthority (RootCACertificate config) and activate it: GetCertificateAuthorityCsr -> IssueCertificate with the RootCACertificate/V1 template -> ImportCertificateAuthorityCertificate, and wait for status ACTIVE.
2. s3.CreateBucket on a fresh bucket and attach a bucket policy granting acm-pca write access; confirm s3.ListObjectsV2 reports KeyCount 0.
3. acm-pca.UpdateCertificateAuthority(CertificateAuthorityArn=<ca-arn>, RevocationConfiguration={CrlConfiguration:{Enabled:true, ExpirationInDays:7, S3BucketName:<bucket>, S3ObjectAcl:"BUCKET_OWNER_FULL_CONTROL"}}).
4. DescribeCertificateAuthority — the CRL configuration is echoed back enabled with the right bucket (this part is correct).
5. IssueCertificate for a leaf CSR and GetCertificate until it is issued.
6. Poll s3.ListObjectsV2/GetObject for key `crl/<last-ARN-segment>.crl`. Observed: the key never appears and the bucket stays empty. Expected: a DER-encoded CRL object appears.
7. (Second cause-half) RevokeCertificate(CertificateSerial=<leaf serial>, RevocationReason="UNSPECIFIED") and re-read the CRL object. Observed: there is still no object to read.
