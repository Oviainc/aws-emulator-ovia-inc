# EMR: 3 net-new root causes — ModifyInstanceFleet accepts an out-of-range target capacity, StartSession/ListSessions are 501 on a non-session-enabled cluster, and a notebook execution fails instead of running

> _Note: this issue was identified against the code base at commit `a27fb6d1af0279893787d520ac4dc13c8147b724`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyInstanceFleet

## Description
Three net-new root causes in the elasticmapreduce emulator, each grounded in a failing behavioral check that the replay report marked neither ALREADY FILED nor OWNED. Neighbouring open issues exist for related symptoms and are named per cause for context; none of them carries these checks' replay keys, so they are filed here.

Cause 1 of 3: ModifyInstanceFleet enforces no UPPER bound on a target capacity, so a request far past the per-fleet instance ceiling is accepted and applied.
AWS: ModifyInstanceFleet is documented as atomic ("The call either succeeds or fails atomically") and models exactly two errors — Smithy (com.amazonaws.emr#ModifyInstanceFleet): input ClusterId (required) + InstanceFleet (InstanceFleetModifyConfig, required); errors InvalidRequestException (HTTP 400, "This exception occurs when there is something wrong with user input") and InternalServerException (HTTP 500). A TargetOnDemandCapacity that exceeds the maximum number of instances EMR will provision for one instance fleet is refused with HTTP 400 InvalidRequestException and EMR's fixed sentence: "The maximum number of possible instances to be provisioned per instance fleet has been exceeded. Revise the configuration and resubmit." That message is entirely fixed text — it carries no values from the request — and because the call is atomic the fleet's TargetOnDemandCapacity/TargetSpotCapacity are left exactly as RunJobFlow set them. Beyond the two modeled errors the ceiling itself is recorded behavior only (the model puts no @range max on these members).
Emulator: the request is ACCEPTED. ModifyInstanceFleet answers HTTP 200 with an empty body (content-type application/x-amz-json-1.1, content-length 2) for an InstanceFleet whose TargetOnDemandCapacity is an absurdly large count, and the oversized value is merged into the stored fleet, so the following ListInstanceFleets reports the out-of-range target instead of the unchanged one. The handler validates only the shape of the cluster id, an unknown cluster, a terminating/terminal cluster, an unknown InstanceFleetId, a NEGATIVE target capacity and the instance-type-config ceiling — there is no maximum-capacity rule on the path at all, so the refusal above can never be produced.
Why: a client that sizes a fleet from user input or a scaling calculation gets a silent accept for a capacity AWS rejects, then reads back a fleet state that cannot exist on AWS. Code that handles InvalidRequestException to clamp or re-plan the resize is never exercised, and the emulator's fleet state diverges permanently from what the same call would leave on AWS.
Fix: the ModifyInstanceFleet handler's validation and the shared capacity-rule helper it calls (the fleet-capacity refusal currently covers only the negative case), in the elasticmapreduce service crate. Context: the fixed issue 20261105T093917Z-emr-refusals-on-the-step-scaling-fleet-modify.md touched fleet-modify refusals; the maximum-capacity refusal is still missing and this is not a regression of a refusal that once worked — the call succeeds.
Traces: emr.modify-instance-fleet-out-of-range-capacity-rejected ("expected the call to be rejected, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}}").

Cause 2 of 3: the Spark Connect session surface is unimplemented, so the SessionEnabled gate on StartSession/ListSessions answers 501 NotImplemented instead of AWS's refusal.
AWS: Smithy (com.amazonaws.emr#StartSession): "Creates and starts a new Spark Connect session on the specified cluster. The cluster must be in the RUNNING or WAITING state and have sessions enabled." StartSession and ListSessions each model InvalidRequestException (HTTP 400) and InternalServerException (HTTP 500) and nothing else. On a cluster created WITHOUT sessions enabled, both StartSession and ListSessions are refused with HTTP 400 InvalidRequestException; the recorded message is "Sessions are not enabled on cluster '<clusterId>'. Set SessionEnabled to true when creating the cluster to enable sessions." — fixed text apart from <clusterId>, which is the ClusterId taken verbatim from the request (quoted). Notably ListSessions refuses rather than returning an empty Sessions list.
Emulator: StartSession answers the scaffold's HTTP 501 with error code NotImplemented and message "operation StartSession is scaffolded but not implemented in this emulator" (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/start_session.rs:184 returns crate::scaffolded::Scaffolded::not_implemented("StartSession"), and the file still carries the SCAFFOLDED marker at line 4). The check observed code 'NotImplemented' where InvalidParameter/InvalidRequestException was required, so neither the SessionEnabled gate nor its sentence exists, and the positive control (a session-enabled emr-spark-8.0.0 cluster) cannot start a session either.
Why: a client cannot tell "this cluster has no sessions" (a 400 it must handle and correct) from "this API does not exist" (a 501 that looks like a broken endpoint); retry/fallback logic keyed on InvalidRequestException never runs, and no Spark Connect session workflow can be exercised at all.
Fix: implement the StartSession handler (and the matching cluster-session gate shared with ListSessions) in the elasticmapreduce service crate, returning the modeled InvalidRequestException for a cluster without SessionEnabled. Context: the open stub issue 20261104T102001Z-emr-startsession-stub.md names the same handler file but states only that it is a stub; the requirement filed here is the SessionEnabled refusal rule, its exact sentence, and that ListSessions refuses with the same code and message rather than answering an empty page.
Traces: emr.start-session-non-studio-cluster-rejected ("expected InvalidRequestException, got 'NotImplemented'").

Cause 3 of 3: a headless notebook execution never runs — it leaves START_PENDING straight into FAILED with an emulator-authored reason.
AWS: Smithy (com.amazonaws.emr#StartNotebookExecution / DescribeNotebookExecution): StartNotebookExecution returns a NotebookExecutionId and DescribeNotebookExecution reports NotebookExecution.Status through the modeled lifecycle; a well-formed notebook (valid nbformat JSON in S3, an EMR execution engine whose cluster is WAITING with Hadoop/Spark/Livy/JupyterEnterpriseGateway, a service role and an output location) moves out of START_PENDING towards RUNNING and, once StopNotebookExecution is called, deterministically reaches STOPPED. FAILED/FAILING with LastStateChangeReason is reserved for an execution that actually failed. That the healthy notebook runs is recorded behavior only (the model describes the states, not the execution).
Emulator: the execution leaves START_PENDING already failed. DescribeNotebookExecution reports Status FAILED/FAILING with LastStateChangeReason = "This emulator records notebook executions but runs no notebook, so the execution ended without running." — an emulator-authored sentence AWS never emits — so STOPPED is unreachable and the StopNotebookExecution leg of the lifecycle is never exercised (the execution id, bucket and key in the recording are per-run values, not part of the requirement).
Why: every notebook-driven workflow is unusable: a client waiting for RUNNING or STOPPED instead sees a failure it cannot act on, and a status-based branch (retry on FAILED, poll on RUNNING) always takes the failure path.
Fix: the notebook-execution lifecycle/executor behind StartNotebookExecution/DescribeNotebookExecution/StopNotebookExecution in the elasticmapreduce service crate (the state machine must run the notebook instead of settling FAILED, and must honour StopNotebookExecution by reaching STOPPED). Context: open issues 20261107T182201Z-emr-notebook-executions-never-run-a-healthy-notebook.md and 20261108T151103Z-emr-4-net-new-root-causes-every-job.md describe the same behaviour for other checks but do not carry this check's replay key.
Traces: emr.notebook-execution-lifecycle-transitions ("notebook execution failed early: This emulator records notebook executions but runs no notebook, so the execution ended without running.").

## Evidence
Cause 1 — expected (AWS): ModifyInstanceFleet with InstanceFleet.TargetOnDemandCapacity far above the per-fleet instance ceiling answers HTTP 400 InvalidRequestException with the fixed sentence "The maximum number of possible instances to be provisioned per instance fleet has been exceeded. Revise the configuration and resubmit." (no variable parts), and ListInstanceFleets still reports TargetOnDemandCapacity=1 as RunJobFlow set it. Actual (emulator): HTTP 200 with an empty JSON body ({'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'application/x-amz-json-1.1', 'content-length': '2', ...}}}) and the oversized capacity applied to the stored fleet. Handler: services/service-com-amazonaws-emr-elasticmapreduce/src/ops/modify_instance_fleet.rs:209-218 refuses only a NEGATIVE capacity (crate::state::instance_fleet_capacity_violation); no upper bound is checked anywhere on the path.

Cause 2 — expected (AWS): StartSession on a cluster created without SessionEnabled answers HTTP 400 InvalidRequestException, message "Sessions are not enabled on cluster '<clusterId>'. Set SessionEnabled to true when creating the cluster to enable sessions." (fixed text; <clusterId> is the request's ClusterId), and ListSessions on that same cluster answers the SAME code and message rather than an empty Sessions list. Actual (emulator): error code 'NotImplemented' (HTTP 501), message "operation StartSession is scaffolded but not implemented in this emulator"; see services/service-com-amazonaws-emr-elasticmapreduce/src/ops/start_session.rs:4 (SCAFFOLDED marker) and :184 (Scaffolded::not_implemented("StartSession")).

Cause 3 — expected (AWS): DescribeNotebookExecution on a healthy headless notebook reports a Status out of START_PENDING that is NOT FAILED/FAILING, and after StopNotebookExecution reaches STOPPED with the same NotebookExecutionId. Actual (emulator): the first status after START_PENDING is FAILED/FAILING with LastStateChangeReason = "This emulator records notebook executions but runs no notebook, so the execution ended without running."

## Steps to Reproduce
Cause 1:
1. RunJobFlow an instance-fleet cluster (release emr-6.15.0) with a 1-unit CORE fleet; wait for WAITING/RUNNING and read the CORE fleet id from ListInstanceFleets.
2. Call ModifyInstanceFleet(ClusterId=<cluster>, InstanceFleet={InstanceFleetId=<core fleet>, TargetOnDemandCapacity=999999999, TargetSpotCapacity=0}).
3. Observed: HTTP 200, empty body, and ListInstanceFleets then reports the oversized TargetOnDemandCapacity. Expected: HTTP 400 InvalidRequestException "The maximum number of possible instances to be provisioned per instance fleet has been exceeded. Revise the configuration and resubmit." with the fleet's capacity unchanged, after which a valid modify to 2 succeeds.

Cause 2:
1. RunJobFlow a plain cluster (no SessionEnabled) and wait for WAITING/RUNNING.
2. Call StartSession(ClusterId=<cluster>, Name=<name>) and then ListSessions(ClusterId=<cluster>).
3. Observed: 501 NotImplemented from StartSession. Expected: 400 InvalidRequestException from BOTH calls with "Sessions are not enabled on cluster '<clusterId>'. Set SessionEnabled to true when creating the cluster to enable sessions."
4. Positive control: create a session-enabled emr-spark-8.0.0 cluster and StartSession on it — expected to return a session Id that ListSessions reports.

Cause 3:
1. PutObject a minimal valid .ipynb into an S3 bucket.
2. RunJobFlow a cluster with Hadoop/Spark/Livy/JupyterEnterpriseGateway and wait for WAITING.
3. StartNotebookExecution(ExecutionEngine={Id=<cluster>,Type=EMR}, ServiceRole=<role>, NotebookS3Location=..., OutputNotebookS3Location=..., OutputNotebookFormat=HTML, NotebookParams="{}").
4. Poll DescribeNotebookExecution until Status leaves START_PENDING. Observed: FAILED with LastStateChangeReason "This emulator records notebook executions but runs no notebook, so the execution ended without running." Expected: a non-failed status progressing towards RUNNING.
5. StopNotebookExecution and poll again. Expected: STOPPED with the same NotebookExecutionId.
