# createdAt is reported for a `standard` recommendation, although the model scopes it to recommendations created by Trusted Advisor Priority

_Filed: 2026-10-28T16:28:20Z_
_Operation: GetRecommendation | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `182c84ca61543123e671d6f76b1915991455e92b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

The account-level recommendation surface reports `createdAt` for EVERY stored recommendation, including the ones whose `type` is `standard`. The model documents that member as present only for a recommendation created by Trusted Advisor Priority, and `type` is documented as exactly that distinction ("Whether the Recommendation was automated or generated by AWS Trusted Advisor Priority"). So for the two seeded `standard` recommendations (`amazon-ebs-snapshots`, `iam-access-key-rotation`) a `GetRecommendation` / `ListRecommendations` response carries a creation timestamp for a recommendation the service itself says was not created by Priority.

This is also inconsistent with how the same crate treats the other Priority-only members of the same shape: the seed deliberately leaves `lifecycle_stage` absent for a non-`priority` row ("The lifecycle stage from AWS Trusted Advisor Priority"), a test pins that absence, and the handler leaves `createdBy`/`updatedOnBehalfOf`/`updatedOnBehalfOfJobTitle` absent — but `created_at` is written unconditionally by the seed and reported unconditionally by the handler, so the one Priority-scoped member that happens to have a value in the store is the one that leaks onto a non-Priority recommendation.

The organization-level handlers are unaffected: the store holds an organization recommendation only for a prioritized recommendation, so every `createdAt` they report is a Priority one. The defect is confined to the account-level pair (`get_recommendation.rs` / `list_recommendations.rs`), which build `Recommendation` / `RecommendationSummary` from the same `state::RecommendationEntry::created_at_millis`.

## Evidence

Model (the sentence that scopes the member) — smithy_query(query="doc", shape="Recommendation", member="createdAt"):
```
"<p>When the Recommendation was created, if created by AWS Trusted Advisor Priority</p>"
```
The same sentence is on `RecommendationSummary$createdAt`. And `Recommendation$type` is modelled as that very distinction — smithy_query(query="shape", shape="Recommendation"): `"type": {"target": "RecommendationType", "required": true, "doc": "<p>Whether the Recommendation was automated or generated by AWS Trusted Advisor Priority</p>"}`.

Handler side — services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/ops/get_recommendation.rs:122 (unconditional, with no test of `entry.r#type`):
```
        created_at: Some(crate::state::date_time(entry.created_at_millis)),
```
and the sibling listing, services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/ops/list_recommendations.rs:139:
```
        created_at: Some(crate::state::date_time(entry.created_at_millis)),
```

The store stamps it on every row regardless of type — services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/state.rs:1588 (inside `for (index, row) in SEED.iter().enumerate()`):
```
                    created_at_millis: SEED_CREATED_AT_MILLIS,
```
while the same seed rows are `standard` — services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/state.rs:1284-1286:
```
        recommendation_type: "standard",
        recommendation_status: "error",
        lifecycle_stage: None,
```

The crate's own, contrary handling of a Priority-only member on the SAME rows (both sides of the inconsistency):
* services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/state.rs:1584 reports the seeded stage as `lifecycle_stage: row.lifecycle_stage.map(str::to_string)`, i.e. absent for a `standard` row, and services/service-com-amazonaws-trustedadvisor-trustedadvisor/tests/all/recommendation_loop.rs:1007-1012 pins that:
```
        assert_eq!(
            body["recommendation"]["lifecycleStage"],
            Value::Null,
            "case {check_id}: expected the seeded (absent) lifecycleStage, got {:?}",
```
  over `for check_id in ["amazon-ebs-snapshots", "iam-access-key-rotation"]` (recommendation_loop.rs:981) — the same two recommendations that nonetheless come back with a `createdAt`.
* services/service-com-amazonaws-trustedadvisor-trustedadvisor/src/ops/get_recommendation.rs:93-96 leaves the other Priority members absent on purpose: "`createdBy`, `updatedOnBehalfOf` and `updatedOnBehalfOfJobTitle` identify the Trusted Advisor Priority person who acted on the recommendation; the store holds no such actor, so those optional members stay absent rather than carrying an invented name."

No comment, test or doc in the crate justifies reporting `createdAt` for a non-prioritized recommendation: `grep -n 'createdAt\|created_at'` over the crate shows the member asserted only for organization recommendations (tests/all/organization_recommendations.rs:339-344, tests/all/organization_recommendation_lifecycle.rs:222-224), which are prioritized-only.

## Steps to Reproduce

1. Start the emulator with EMULATOR_TRUSTEDADVISOR_SUPPORT_PLAN=business so the support-level gate admits the calls (src/state.rs:182).
2. GET /v1/recommendations/arn%3Aaws%3Atrustedadvisor%3A%3A<account>%3Arecommendation%2Famazon-ebs-snapshots-recommendation — the seeded recommendation whose `type` is `standard` (src/state.rs:1284).
3. Observe the body: `"type": "standard"`, `"lifecycleStage"` absent (correctly, as a Priority-only member) — and `"createdAt": "2024-01-01T00:00:00Z"` present, although the model documents `createdAt` as "When the Recommendation was created, if created by AWS Trusted Advisor Priority".
4. GET /v1/recommendations?type=standard and see the same `createdAt` on every `standard` summary (src/ops/list_recommendations.rs:139).
5. Compare with the prioritized rows (`low-utilization-ec2-instances-recommendation`), where `createdAt` is the only member whose presence is the same for both types.
