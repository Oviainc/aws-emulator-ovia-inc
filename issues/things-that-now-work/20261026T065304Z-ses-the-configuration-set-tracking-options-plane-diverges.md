## Operation
UpdateConfigurationSetTrackingOptions

## Description
REOPENS 20261025T214303Z-ses-updateconfigurationsettrackingoptions-stub.md: its fix left the call refused. The operation is no longer a 501 scaffold — it now reaches the shared tracking-domain rule and answers the modeled InvalidTrackingOptionsException/400 — but every one of the five checks below still fails on that refusal: the refusal class is right and its MESSAGE is the emulator's own wording, and on the one path AWS accepts, the call is refused anyway. Three root causes, all in the tracking-options write path shared by CreateConfigurationSetTrackingOptions and UpdateConfigurationSetTrackingOptions.

Cause 1 of 3: a CustomRedirectDomain that sits under a domain identity verified through SESv2 is refused as unverified, because the v1 tracking-domain rule reads an identity store the v2 writer never wrote to.
AWS: Smithy com.amazonaws.ses#CreateConfigurationSetTrackingOptions (input ConfigurationSetName + TrackingOptions, both required; errors ConfigurationSetDoesNotExistException 400 / InvalidTrackingOptionsException 400 / TrackingOptionsAlreadyExistsException 400) is accepted with HTTP 200 whenever the custom redirect domain, or any parent of it, is a verified identity in the account — v1 and v2 are two APIs over ONE set of account identities, so a domain verified with sesv2 CreateEmailIdentity covers a never-before-seen label beneath it without creating or touching any further identity, record or zone. DescribeConfigurationSet(ConfigurationSetAttributeNames=['trackingOptions']) then reports exactly the domain that was stored.
Emulator: the call is refused 400 `InvalidTrackingOptions` "The tracking domain you specified is not verified in Amazon SES." for a label under an apex the same account verified through SESv2 moments earlier. The parent-coverage rule itself exists and is correct (services/service-com-amazonaws-ses-simpleemailservice/src/state.rs: `tracking_domain` at line 672 calls `covers_verified_domain` at line 618, which walks the domain suffixes) — what fails is that the identity it walks against is the ses v1 crate's own `identities` map, which holds nothing created through the sesv2 crate. Same root cause as Cause 3 of the open issue 20261025T214303Z-ses-identity-verification-is-auto-completed-and-the.md ("identities created through SESv2 are invisible to the SES v1 API — the two surfaces do not share one identity store"), whose replay keys do not include this check; fixing that shared store is what unblocks this one.
Why: the documented way to set up a custom open/click tracking domain is to verify the apex once and point a subdomain at it. With the two stores split, a client that verifies with the modern API and configures tracking with the legacy one can never attach a tracking domain at all, and the refusal blames the domain's verification instead of naming the real problem. Hypothesis (not reached in this replay, read from the handler source): once cause 1 is fixed this check continues into its duplicate-Create leg, which expects code `TrackingOptionsAlreadyExists` with the message "There is already a tracking options for configuration set <ConfigurationSetName>", where services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_configuration_set_tracking_options.rs lines 203-216 currently answers the doc sentence "The configuration set you specified already contains a TrackingOptions object." — expect a further message divergence there.
Traces: ses.configuration-set-tracking-options-lifecycle-with-verified-domain.

Cause 2 of 3: the unverified-domain refusal message is the InvalidTrackingOptionsException documentation prose, not AWS's templated sentence.
AWS: the model documents InvalidTrackingOptionsException only as a condition list ("This error appears most often in the following situations: When the tracking domain you specified is not verified in Amazon SES. When the tracking domain you specified is not a valid domain or subdomain."); the runtime message for the unverified case is "Domain <domain> is not verified under this account." — fixed text "Domain <", then the CustomRedirectDomain copied verbatim from the request, then "> is not verified under this account." The same code and the same templated message come from CreateConfigurationSetTrackingOptions and from UpdateConfigurationSetTrackingOptions, and on Update the domain check runs AHEAD of both the TrackingOptions-object-existence check and the configuration-set-existence check, so a well-formed unverified domain yields this message even for a configuration set that does not exist.
Emulator: the error code is right (`InvalidTrackingOptions`, 400) but the message is the fixed, value-free doc sentence "The tracking domain you specified is not verified in Amazon SES." (services/service-com-amazonaws-ses-simpleemailservice/src/state.rs lines 681-684), so it never names the domain it rejected.
Why: the rejected domain is the whole diagnostic content of this refusal — with it dropped, a caller submitting several domains cannot tell which one failed, and any code or log tooling matching AWS's sentence never matches. The ordering claim above is also what distinguishes this boundary from ConfigurationSetDoesNotExist/TrackingOptionsDoesNotExist, so a wrong message here hides which rule fired.
Traces: ses.tracking-options-unverified-domain-fails, ses.update-configuration-set-tracking-options-missing-tracking-options-rejected, ses.update-configuration-set-tracking-options-unknown-configuration-set-rejected, ses.update-configuration-set-tracking-options-invalid-custom-redirect-rejected.

Cause 3 of 3: the malformed-domain refusal message is likewise doc prose instead of AWS's templated sentence.
AWS: a syntactically invalid CustomRedirectDomain (e.g. a URL scheme plus an empty label) is refused 400 `InvalidTrackingOptions` with "Domain <domain> is not a valid domain." — fixed text "Domain <" + the submitted value verbatim + "> is not a valid domain." — from both Create and Update, and no TrackingOptions object is left on the configuration set.
Emulator: code right, message wrong: "The tracking domain you specified is not a valid domain or subdomain." (services/service-com-amazonaws-ses-simpleemailservice/src/state.rs lines 675-680), which again omits the offending value and merges AWS's two distinct sentences into one wording family.
Why: the syntactic and the ownership refusal are different conditions AWS words differently; collapsing them into doc prose means a client cannot tell a typo'd domain from an unverified one, and neither message names the value at fault.
Fix for causes 2 and 3: the shared rule `ComAmazonawsSesSimpleemailserviceState::tracking_domain` in services/service-com-amazonaws-ses-simpleemailservice/src/state.rs (lines 672-685) — return AWS's two templated sentences with the request's domain interpolated; both wrapping handlers (ops/create_configuration_set_tracking_options.rs `invalid_tracking_options`, ops/update_configuration_set_tracking_options.rs) pass the string straight through, so one change fixes both operations. Note: the later legs of three of these checks assert DeleteConfigurationSetTrackingOptions' own messages (TrackingOptionsDoesNotExist "There are no tracking options for configuration set <name>" and ConfigurationSetDoesNotExist "Configuration set <name> does not exist."); that operation is still an unimplemented stub covered by its own ALREADY FILED issue, so expect those legs to gate next.
Traces: ses.update-configuration-set-tracking-options-invalid-custom-redirect-rejected.
