# CloudWatch: Unit is not part of a datapoint's storage/read identity — unit-selected GetMetricStatistics/GetMetricData reads never resolve the per-unit datapoints (1 cause)

> _Note: this issue was identified against the code base at commit `9dfd5bd5800ceb89967be182e813f239a03c5430`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricStatistics

## Description
Cause 1 of 1: `Unit` is not honoured as part of a datapoint's storage and read identity, so a metric that holds data under several units cannot be read back per unit. Failing check id: cloudwatch.unit-is-part-of-a-datapoints-read-identity.

AWS: the Smithy model states the rule on GetMetricStatisticsInput$Unit (target StandardUnit, an enum of 27 values: Seconds, Microseconds, Milliseconds, Bytes, Kilobytes, Megabytes, Gigabytes, Terabytes, Bits, Kilobits, Megabits, Gigabits, Terabits, Percent, Count, Bytes/Second, Kilobytes/Second, Megabytes/Second, Gigabytes/Second, Terabytes/Second, Bits/Second, Kilobits/Second, Megabits/Second, Gigabits/Second, Terabits/Second, Count/Second, None): "If you omit Unit, all data that was collected with any unit is returned, along with the corresponding units that were specified when the data was reported to CloudWatch. If you specify a unit, the operation returns only data that was collected with that unit specified. If you specify a unit that does not match the data collected, the results of the operation are null. CloudWatch does not perform unit conversions." Smithy: Datapoint$Unit (target StandardUnit) is the per-datapoint unit echoed back on every read. Consequences of that rule, each of which this check asserts: (a) when one PutMetricData call publishes several values at ONE timestamp for ONE Namespace/MetricName/Dimensions triple but under different units, each unit is its own storage bucket, so a Unit-selected read returns exactly one datapoint whose Sum/SampleCount are only that unit's datum, unconverted; (b) a read that omits Unit returns one datapoint PER published unit at that one timestamp — it is NOT a single aggregate across units; (c) a read for a valid StandardUnit value that was never published is an EMPTY SUCCESSFUL result (HTTP 200, no Datapoints; on GetMetricData, StatusCode "Complete" with Values []), not an error and not the other units' data; (d) Unit is NOT part of a metric's CATALOGUE identity — ListMetrics for that namespace must still return exactly ONE metric entry (one MetricName with its one dimension set) however many units were published under it. This asymmetry — unit in the datapoint's read identity, absent from the catalogue's — is the behaviour under test. The two read paths also validate the same enum through different machinery and report it with different error classes: GetMetricStatistics with a string that is not a StandardUnit at all refuses with HTTP 400, Error.Code "InvalidParameterValue" (Smithy: InvalidParameterValueException, awsQueryError code InvalidParameterValue, 400) and the message whose fixed text is "The parameter Unit must be a value in the set [ " ... " ]." with the bracketed list being the StandardUnit enum members; GetMetricData with MetricStat.Unit set to the same string refuses with HTTP 400 and Error.Code "ValidationError" and the generic constraint message whose fixed text is "1 validation error detected: Value at '" + the request path of the offending member (here metricDataQueries.1.member.metricStat.unit, the index taken from the request) + "' failed to satisfy constraint: Member must satisfy enum value set: [" + the StandardUnit enum members + "]". An emulator returning ONE code for both read paths has one validator where AWS has two.

Emulator: the check never completes. Replay output is `Error: Check timed out after 60.0s`, with the run blocked in its first barrier — the one that polls GetMetricStatistics once per unit for the three units just published (Bytes=100.0, Kilobytes=7.0, None=3.0, all at one closed whole-minute bucket, all under one namespace/metric/dimension) and requires all three unit-selected reads to be simultaneously non-empty before it may proceed. That barrier treats an empty reading as a reset, so the timeout means at least one unit-selected read kept coming back with zero Datapoints for a minute bucket that had just been written. The emulator therefore does not key stored datapoints by unit on the write path, or does not select by Unit on the read path (last-write-wins on the Namespace/MetricName/Dimensions/Timestamp key, so only one of the three units is ever retrievable, or the Unit filter is applied against a value that was never stored). Because the run never got past that barrier, the downstream arms — the unitless read returning one datapoint per unit, the GetMetricData per-unit selection, the empty-but-successful reads for never-published valid units (Terabytes/Percent/Count), the single-entry ListMetrics catalogue, and the two differently-classed invalid-unit refusals (InvalidParameterValue on GetMetricStatistics vs ValidationError on GetMetricData) — were never reached and must all be brought up to the behaviour above as part of this fix, not just the first barrier.

Why: a client gets silently wrong numbers and silently missing series. Any caller that publishes one metric under more than one unit (the EMF/agent/SDK pattern of reporting both a Bytes gauge and a Count gauge, or re-reporting a metric after a unit change) loses datapoints outright: a Unit-qualified GetMetricStatistics or GetMetricData returns nothing, so dashboards render blank, alarms over a unit-qualified metric sit in INSUFFICIENT_DATA forever, and autoscaling that reads a unit-qualified series never scales. Conversely, if the units are folded into one bucket, a caller reading Unit=Bytes receives a figure contaminated by the Kilobytes and None values (100.0 vs the union 110.0) and, because CloudWatch is documented to do no unit conversion, has no way to detect or undo the mixing — it bills, alarms and capacity-plans on a number AWS would never return. If instead the unit were made part of the CATALOGUE key, ListMetrics would report three metrics where AWS reports one, and every consumer that enumerates metrics to build dashboards or metric streams triples its series count. The invalid-unit arms matter for the same reason: a client that distinguishes the two read paths by error code (retrying one, surfacing the other) branches wrongly if both paths answer with the same code.

Fix: CloudWatch's metric-data state, plus the two read handlers and their validation. The datapoint store's key must include the StandardUnit alongside namespace, metric name, the dimension set and the timestamp bucket, so PutMetricData appends per unit rather than overwriting; the metric CATALOGUE key must deliberately exclude the unit, so ListMetrics stays one entry. GetMetricStatistics' handler must filter by the Unit input when present, emit one Datapoint per stored unit (each carrying its own Datapoint$Unit) when absent, and return an empty 200 for a valid-but-unpublished unit; GetMetricData's handler must apply the same selection through MetricStat.Unit and return StatusCode "Complete" with empty Values for a valid-but-unpublished unit. Each read path's unit validation belongs in its own validator so the two enum refusals keep their distinct codes and message shapes.

## Evidence
Expected (AWS, per Smithy GetMetricStatisticsInput$Unit documentation and Datapoint$Unit):
- One PutMetricData publishing three values at one timestamp for one Namespace/MetricName/Dimensions triple under units Bytes, Kilobytes and None stores THREE datapoints, one per unit.
- GetMetricStatistics(Unit="Bytes") -> HTTP 200, exactly 1 Datapoint with Sum = the Bytes value, SampleCount = 1.0, Unit = "Bytes".
- GetMetricStatistics(Unit="Kilobytes") -> exactly 1 Datapoint, Sum = the Kilobytes value, Unit = "Kilobytes"; NOT normalised to Bytes (no unit conversion) and NOT present in the Bytes series.
- GetMetricStatistics(Unit="None") -> exactly 1 Datapoint, Sum = the None value, Unit = "None" ('None' is a real unit value and its own bucket, not a wildcard).
- GetMetricStatistics with Unit omitted -> 3 Datapoints sharing the one published minute bucket, each carrying its own Unit and its own unsummed value — not one aggregate.
- GetMetricData with MetricStat.Unit set to each published unit -> StatusCode "Complete", Values = [that unit's value].
- GetMetricStatistics / GetMetricData for valid-but-never-published units (Terabytes, Percent, Count) -> empty successful result (no Datapoints; StatusCode "Complete" with Values []), and it stays empty.
- ListMetrics for that namespace -> exactly ONE metric entry (the one MetricName with its one dimension set), because Unit is not part of the catalogue identity.
- GetMetricStatistics(Unit="Furlongs") -> HTTP 400, Error.Code "InvalidParameterValue", Error.Message fixed text "The parameter Unit must be a value in the set [ ... ]." where the bracketed list is the StandardUnit enum members.
- GetMetricData with MetricStat.Unit="Furlongs" -> HTTP 400, Error.Code "ValidationError", Error.Message fixed text "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [<StandardUnit members>]", where <member path> (e.g. metricDataQueries.1.member.metricStat.unit) is taken from the request's query index.

Actual (emulator, from the replay report):
- cloudwatch.unit-is-part-of-a-datapoints-read-identity -> [mismatch] `Error: Check timed out after 60.0s`.
- The run is blocked in its first barrier, which requires the three unit-selected GetMetricStatistics reads to be simultaneously non-empty; an empty reading resets that barrier, so the timeout proves at least one unit-selected read returned zero Datapoints for a minute bucket that had just been written by PutMetricData. Had the three reads returned a stable non-empty (but wrong, e.g. unit-aggregated) value, the check would have failed with the value AssertionError instead of timing out.

## Steps to Reproduce
1. Build and boot the emulator from the checkout and point a botocore CloudWatch client at it.
2. Pick a fresh custom namespace and a metric name with one dimension, e.g. Namespace="<unique>", MetricName="Payload", Dimensions=[{"Name":"Probe","Value":"unit-identity"}].
3. Choose a closed whole-minute bucket three minutes in the past (second=0, microsecond=0) so no partial period can move underneath the assertions.
4. Call PutMetricData ONCE with three MetricData entries, all at that same Timestamp and for that same MetricName/Dimensions, differing only in unit: {Value: 100.0, Unit: "Bytes"}, {Value: 7.0, Unit: "Kilobytes"}, {Value: 3.0, Unit: "None"}.
5. For each of Unit="Bytes", "Kilobytes", "None", call GetMetricStatistics(Namespace, MetricName, Dimensions, StartTime=bucket-2min, EndTime=bucket+5min, Period=60, Statistics=["Sum","SampleCount"], Unit=<unit>). Each must return exactly ONE datapoint whose Sum is that unit's value (100.0 / 7.0 / 3.0), SampleCount 1.0, and Unit echoed as the requested unit. Observed: at least one of these returns no datapoints, so the check's stability barrier never clears and the run is killed at 60s.
6. Call the same GetMetricStatistics with Unit omitted: expect 3 datapoints at the one timestamp, one per unit, unsummed and unconverted.
7. Call GetMetricData with MetricDataQueries=[{Id:"q", MetricStat:{Metric:{Namespace,MetricName,Dimensions}, Period:60, Stat:"Sum", Unit:<unit>}}] for each published unit: expect StatusCode "Complete" and Values=[that unit's value].
8. Repeat steps 5 and 7 for Terabytes, Percent and Count (all valid StandardUnit values, none published): expect an empty successful result on both paths, held stable, not an error and not the other units' data.
9. Call ListMetrics(Namespace=<unique>) and page it: expect exactly one metric entry despite the three units.
10. Call GetMetricStatistics with Unit="Furlongs": expect HTTP 400 / "InvalidParameterValue" with the "The parameter Unit must be a value in the set [ ... ]." message. Then call GetMetricData with MetricStat.Unit="Furlongs": expect HTTP 400 / "ValidationError" with the "1 validation error detected: Value at '<path>' failed to satisfy constraint: Member must satisfy enum value set: [...]" message — a different code from the same enum, via the other read path.
11. Re-read Unit="Bytes": the stored datapoints must be unchanged (Sum 100.0) after the rejected and empty reads.
