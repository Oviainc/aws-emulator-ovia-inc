=== Cause 1 of 2: TestConnection can never report a usable connection — Status is unconditionally ERROR and SftpConnectionDetails is never populated, so every connector-gated flow polls forever ===
AWS: Smithy TestConnection input ConnectorId (@required, @length 19..19, pattern ^c-([0-9a-f]{17})$); output {ConnectorId, Status, StatusMessage, SftpConnectionDetails (SftpConnectorConnectionDetails, carrying the connector host key)}; modeled errors InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503. The model documents Status as 'Returns OK for successful test, or ERROR if the test fails', StatusMessage as 'Returns Connection succeeded if the test is successful', and SftpConnectionDetails as the structure that contains the SFTP connector host key observed during the initial connection attempt. Recorded behavior: for an SFTP connector whose Url names a reachable Transfer server and whose SftpConfig.UserSecretId holds that server user's {Username, PrivateKey}, TestConnection eventually returns SftpConnectionDetails.HostKey; after UpdateConnector pins that key as SftpConfig.TrustedHostKeys, a later TestConnection returns Status 'OK'. The host key VALUE, the server id and the host name are environment-specific and are NOT requirements — only that a key is reported and that the pinned-key retest reaches Status 'OK' with the success StatusMessage.
Emulator: the handler builds its output with status = crate::state::TEST_CONNECTION_STATUS_ERROR and sftp_connection_details: None for EVERY connector that configures SftpConfig, with no reference to the emulated Transfer server the connector Url names; its own module doc states the emulator 'opens no outbound connection, so no session can run here ... this handler reports neither'. Status therefore never becomes 'OK' and no host key is ever observable.
Why: a client cannot bring a connector into service at all. The documented provisioning sequence — probe TestConnection, read SftpConnectionDetails.HostKey, pin it with UpdateConnector, re-probe until Status 'OK', then transfer — never advances, so the caller HANGS instead of failing, and cannot tell 'this connector is misconfigured' (a genuine ERROR verdict) from 'this target never evaluates connections'. The check is killed inside exactly this poll loop, having asserted nothing.
Fix: the TestConnection handler and the connector state it reads must derive the verdict from the emulated target — resolve the Transfer server named by the connector Url, report that server's host key in SftpConnectionDetails.HostKey, and answer Status 'OK' with the success StatusMessage when the stored secret and TrustedHostKeys match it, while keeping Status 'ERROR' with the defect-naming StatusMessage when they do not.
Traces: transfer.workflow-step-state-out-of-order-rejected (polls test_connection for SftpConnectionDetails.HostKey, then for Status == 'OK'); file/line citations under Traces in Evidence.

=== Cause 2 of 2: a file pushed through a connector is only recorded QUEUED and fires no OnUpload workflow execution, so no CUSTOM-step callback token is ever issued and the replayed-token refusal cannot occur ===
AWS: Smithy StartFileTransfer(ConnectorId @required, SendFilePaths, RemoteDirectoryPath) -> TransferId @required; ListFileTransferResults(ConnectorId @required, TransferId @required) -> FileTransferResults @required (list 0..1000, entries carrying StatusCode, FilePath and, on failure, FailureCode/FailureMessage) + NextToken; CreateWorkflow(Steps with Type CUSTOM and CustomStepDetails{Name, Target, TimeoutSeconds, SourceFileLocation}); UpdateServer(WorkflowDetails.OnUpload=[{WorkflowId, ExecutionRole}]); SendWorkflowStepState(WorkflowId @required len 19..19 ^w-([a-z0-9]{17})$, ExecutionId @required len 36..36 UUID pattern, Token @required len 1..64 ^\w+$, Status @required CustomStepStatus) -> empty output, modeled errors AccessDeniedException 403, InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429, ServiceUnavailableException 503. Recorded behavior: a file uploaded to a server whose WorkflowDetails.OnUpload names the workflow starts an execution; the CUSTOM step invokes its Lambda Target with serviceMetadata.executionDetails.{workflowId, executionId} and a callback token; the step's in-order SendWorkflowStepState(Status='SUCCESS') succeeds, and the accepted transfer reaches a terminal StatusCode ('COMPLETED', FilePath equal to the path sent). Replaying that SAME token after the step has already completed is refused with HTTP 404, error code ResourceNotFoundException and the message exactly 'Unknown execution' — that message is entirely FIXED text, it carries no request- or state-derived part — and DescribeExecution's answer for that ExecutionId is unchanged by the refused replay.
Emulator: nothing on the connector/upload path creates a workflow execution. StartFileTransfer only records the request: its module doc states each accepted file 'stays QUEUED ... and nothing here ever reports a file as transferred, failed or in progress, because nothing attempted it', and ListFileTransferResults serves exactly those non-terminal records. No OnUpload execution, no CUSTOM-step invocation and no callback token therefore exist. Hypothesis (the check is killed by cause 1 before it reaches the call, so the replay output does not state this): with no execution record, SendWorkflowStepState for a consumed token cannot produce AWS's 404 ResourceNotFoundException 'Unknown execution'.
Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback token) sees its workflow never run on upload, its transfer never reach a terminal status, and the at-most-once guarantee of a callback token — the property that makes a token safe to retry against — cannot be exercised at all, so retry/idempotency logic written against real Transfer Family is untestable here.
Fix: the connector data-plane state machine (crate::state ConnectorTransfer plus the StartFileTransfer and ListFileTransferResults handlers) must advance an accepted transfer to a terminal state and apply it against the emulated storage the connector's Url/paths name; and the server upload path plus the workflow/execution state (crate::state executions plus the SendWorkflowStepState, ListExecutions and DescribeExecution handlers) must start an execution for a server whose WorkflowDetails.OnUpload names a workflow, issue the CUSTOM step's callback token, accept the in-order SendWorkflowStepState once, and refuse a replay of the same token with the modeled HTTP 404 ResourceNotFoundException whose message is exactly 'Unknown execution', leaving DescribeExecution's answer unchanged.
Traces: transfer.workflow-step-state-out-of-order-rejected (its final assertions).
