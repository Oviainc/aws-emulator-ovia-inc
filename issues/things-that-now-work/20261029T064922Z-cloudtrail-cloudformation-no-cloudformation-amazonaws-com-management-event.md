# cloudtrail__cloudformation: no cloudformation.amazonaws.com management event is ever recorded, so an accepted and a refused CreateStack are never auditable through LookupEvents

> _Note: this issue was identified against the code base at commit `004a13bc6b62a404600c0a09686b1d7dd87c7440`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
One net-new root cause. The failing check is not marked ALREADY FILED or OWNED in the replay report, so no existing issue carries its replay key. (Service token: the check id's leading token is `cloudtrail__cloudformation`, a cross-service check over cloudtrail and cloudformation; both underlying services are bootstrapped.)

Cause 1 of 1 — CloudFormation calls produce no CloudTrail management event, so LookupEvents(EventSource=cloudformation.amazonaws.com) is permanently empty.
AWS: every CloudFormation API call of the account is recorded as a CloudTrail management event with eventSource "cloudformation.amazonaws.com" and eventName "CreateStack", retrievable by LookupEvents (Smithy: LookupEvents supports the EventSource lookup attribute — LookupAttributeKey values include EventSource; Event carries EventId, EventName, EventSource, EventTime, Username, Resources and CloudTrailEvent, "A JSON string that contains a representation of the event returned"). For a REFUSED CreateStack (a RoleARN CloudFormation cannot assume: SDK sees ValidationError / HTTP 400, message "Role <role-arn> is invalid or cannot be assumed") AWS records errorCode "ValidationException" — the exception name, not the awsQuery wire code the SDK saw — the SDK's errorMessage verbatim, null responseElements because nothing was minted, userIdentity.arn of the caller, and requestID equal to the SDK's ResponseMetadata.RequestId. For an ACCEPTED CreateStack it records no errorCode, responseElements.stackId equal to the returned StackId, and requestParameters.roleARN equal to the RoleARN sent. Records are indexed within minutes.
Emulator: the CloudFormation half of the contract holds — the untrusted-role CreateStack is refused ValidationError/400 with the expected message, the refused call provisions nothing (DescribeStacks gives ValidationError "Stack with id <name> does not exist", GetQueueUrl gives AWS.SimpleQueueService.NonExistentQueue "The specified queue does not exist."), and repairing the trust lets the same stack name reach CREATE_COMPLETE. But the subsequent poll of LookupEvents filtered by EventSource=cloudformation.amazonaws.com never returns ANY record: none of the three refusals' request ids, nor the control create's, nor the repaired create's, is ever indexed, and the check exhausts its budget with `TimeoutError: CloudTrail to index this check's CreateStack records: the run budget ended first; not graded` (raise at line 423 of the check). The account's management-event log that services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/lookup_events.rs reads holds nothing for this event source.
Why: a client cannot audit CloudFormation at all. The join every consumer relies on — correlate the SDK RequestId with the audit record to learn whether a call was accepted, which role it used, and what the service told the caller — returns nothing, so a refusal is indistinguishable from an unlogged call. Detection and incident-response code keyed on eventSource cloudformation.amazonaws.com with errorCode ValidationException never fires, and the readOnly/errorCode/responseElements fidelity of those records cannot be observed at all.
Fix: the management-event recording seam shared by the emulated services (`service_common::management_events`): CloudFormation's operation dispatch must append a record for each call — accepted and refused alike — carrying eventSource "cloudformation.amazonaws.com", eventName, the caller's userIdentity, requestID equal to the response's request id, requestParameters (including roleARN), responseElements (stackId on success, null on refusal) and, on the refusal path, errorCode as the modelled exception name ("ValidationException") with the caller's errorMessage.

## Evidence
Expected: after three refused CreateStack calls with an untrusted RoleARN, one accepted control CreateStack and one accepted repaired CreateStack, LookupEvents with LookupAttributes=[{AttributeKey: EventSource, AttributeValue: cloudformation.amazonaws.com}] over the covering window returns five records keyed by requestID — each refusal with eventName "CreateStack", errorCode "ValidationException", errorMessage equal to the SDK's "Role <role-arn> is invalid or cannot be assumed", responseElements null and userIdentity.arn of the caller; each acceptance with no errorCode, responseElements.stackId equal to the returned StackId and requestParameters.roleARN equal to the RoleARN sent. Actual: the lookup returns no cloudformation.amazonaws.com record at all for the entire budget; the check terminates with `TimeoutError: CloudTrail to index this check's CreateStack records: the run budget ended first; not graded`. The CreateStack refusals and acceptances themselves matched AWS (ValidationError / HTTP 400 and CREATE_COMPLETE), so the calls were served — only the audit record is missing.

## Steps to Reproduce
(1) Create an IAM role whose trust policy does NOT name cloudformation.amazonaws.com; (2) call cloudformation CreateStack with that RoleARN and observe the expected ValidationError/400 "Role <role-arn> is invalid or cannot be assumed"; (3) call CreateStack with a correctly trusted role and wait for CREATE_COMPLETE; (4) poll cloudtrail LookupEvents with LookupAttributes=[{AttributeKey: EventSource, AttributeValue: cloudformation.amazonaws.com}] over a window covering all the calls — no record is ever returned, so the request ids from steps 2 and 3 can never be joined to an audit record.
