# cloudfront/events: 3 of the 4 causes remain open — CloudFront emits no events of its own, a target's resource-based policy is never evaluated, CloudFormation registers no Lambda function, and nothing runs a function's code

> _Split out of `issues/things-that-now-work/20261023T140640Z-cloudfront-events-eventbridge-never-delivers-a-matched-event-to-any.md`, whose cause 3 is fixed and whose cause 1 is fixed for the FIFO/fair queue target. This report carries the replay keys that do NOT pass, re-filed here so they are not recorded as working. Everything below is what that fix established about them; a later fixer starts from here rather than from scratch._

> _Note: the parent issue was identified against the code base at commit `a59989a9f63c403b66485a4e93f54ab6df22c2a6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
What the parent fix LANDED, so a later fixer does not redo it:
* `PutEvents` is now authorized as AWS authorizes any call on a resource — the calling principal's identity-based policies (resolved from the presented access key id through STS's own caller resolution, then IAM's `principal_policies`) and the bus's resource policy together, with an explicit deny in either refusing and the account's own published credential refused only by an explicit deny (`services/service-com-amazonaws-eventbridge-awsevents/src/state/authorization.rs`). That closed the parent's cause 3.
* A queue target's `SqsParameters.MessageGroupId` now travels with the `sqs:SendMessage` a matched event is delivered by, so a FIFO (or fair) queue target receives at all — Amazon SQS fails a send that carries no group id (`src/ops/put_events.rs`, `TargetKind::Queue`).
* Delivery of a published event to a standard queue, a topic, a function and a state machine, under the matched rule's own fan-out, is in place and observable (the crate's `target_dispatch`, `target_delivery` and `events_fan_out_to_each_matched_target` suites). What is NOT in place is everything below.

Cause 1 of 3: a target whose own RESOURCE-BASED policy does not admit `events.amazonaws.com` is invoked anyway, so no negative check of this group can pass and no positive one is attributable.
AWS: "For Lambda functions, Amazon SNS topics and Amazon SQS queues, EventBridge relies on resource-based policies" — a queue whose `Policy` does not grant `sqs:SendMessage` to `events.amazonaws.com`, a topic whose policy does not grant `sns:Publish`, and a function with no `lambda:InvokeFunction` permission for that service principal are each a delivery EventBridge does NOT make: the event goes to the target's dead-letter queue with `ERROR_CODE = NO_PERMISSIONS` and is counted on the rule's `FailedInvocations`.
Emulator: `src/ops/put_events.rs::deliver` says so in its own doc comment — the role gate is asked only of the kinds AWS invokes under the target's `RoleArn` (`TargetKind::invoked_under_target_role`), and "for a kind whose invocation is governed by the target's own resource policy instead … this emulator does not evaluate a resource-based policy, so it has nothing to show against such a target". The in-process call is signed with the emulator's own credentials, so the target service sees the account's own principal and allows it.
Why this is more than a negative-path gap: `cloudfront-event-sns-topic-policy-missing-blocks-delivery` now gets PAST its own key — the positive leg delivers — and fails on its negative assertion (`assert not any(marker in m["Body"] for m in blocked_messages)`), i.e. the emulator delivered what AWS suppresses.
Fix: evaluate the target resource's own policy for the EventBridge service principal before the invocation, in the eventbridge crate's delivery path, and record the refusal through the existing `NO_PERMISSIONS` / dead-letter / `FailedInvocations` channel. Note for whoever takes it: the queue, topic and function policies live in the SQS, SNS and Lambda stores of the same shared engine (reachable the way `crate::state::IamState` already is), none of which depends on this crate, so there is no dependency cycle. It is a BEHAVIOUR CHANGE for every policy-free SQS/SNS/Lambda target in the tree: some twenty existing suites in this crate and in `core/router/tests` create a queue with no policy and expect delivery, and each of those fixtures has to grant `events.amazonaws.com` the way AWS requires.

Cause 1b (the same group, a different blocker): the checks whose effect only a RUNNING Lambda deployment package can produce.
These poll a queue for a marker the function itself writes (`eventbridge-rule-disabled-state-does-not-invoke-cloudfront-lambda` asserts "the ENABLED rule never invoked its Lambda target" from the messages the function sent; `lambda-cloudfront-createinvalidation-response-propagated-to-sqs` wants the function's CloudFront `CreateInvalidation` answer in a queue; `lambda-role-missing-cloudfront-permission-denied-invalidation` wants the denial the function's own call earned).
Emulator: nothing in this process runs a deployment package — `services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs` (`FunctionRecord::materialize`) settles every accepted asynchronous invocation as "not executed" for exactly that reason, and `Invoke` answers no result for a `RequestResponse` call. EventBridge's side of these checks is already correct: the invocation IS made and recorded. They are BLOCKED on an in-process Lambda runtime, which is that crate's own work, not this one's.

Cause 2 of 3: CloudFront emits no events of its own onto the default event bus. UNTOUCHED by the parent fix.
AWS: recorded behavior only — creating/updating/deleting a distribution and changing its tags produce events on the default bus (source `aws.cloudfront`, with the API-call detail carrying `requestParameters`), which a rule can match and forward to SQS/SNS.
Emulator: the rule and target exist and the mutation is performed, but no event is ever produced, so the destination stays empty and each check runs to its 60 s budget. `grep` of `services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src` for `put_events`/`eventbridge` finds nothing.
What the parent fix established as the way in: the publication seam EXISTS and is used by other services — `services/service-com-amazonaws-batch-awsbatchv20160810/src/state.rs::publish_job_state_changes` publishes onto the default bus through the in-process callback with an `aws.<service>` source, and `put_events::is_service_publication` admits the reserved `aws.` namespace for exactly that path (and for nothing a client can send). So the CloudFront side is one call per mutation handler, after its own lock is released.
What is MISSING and is why this was not attempted blind: the recorded SHAPE of those events — the `detail-type` and the `detail` members each check's `EventPattern` matches on (a status member for the deployed/in-progress pair, `requestParameters` for the API-call trio, the tag-change event's source and detail). A guessed `detail-type` would be a memorised answer rather than a rule. A fixer needs the recorded envelopes for these trace ids, or the published AWS reference for them, before writing the emission. Related: the same "AWS API Call via CloudTrail" fan-out is cause 3 of `issues/things-that-do-not-work/20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md`, which states the rule for it generally (a trail that is logging publishes each recorded call as `detail-type` "AWS API Call via CloudTrail" with source `aws.<service>` and the CloudTrail record as the detail) — the three `eventbridge-rule-matches-cloudfront-*distribution-api-call` checks of this group are that channel for `aws.cloudfront`, so the two should be fixed together in the shared management-event seam (`services/common/src/management_events.rs`) rather than once per service.
