# CreateIntegration resolves TargetArn only against provisioned clusters: a redshift-serverless namespace target answers IntegrationTargetNotFoundFault (404) instead of IntegrationConflictOperationFault (400) while the target warehouse is not active

> _Note: this issue was identified against the code base at commit `156576781ed83437dd2a27a13713f17f66ab67eb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateIntegration

## Description
One net-new root cause found replaying the redshift behavioral checks.

=== Cause 1 of 1: a zero-ETL integration target that EXISTS but is not yet active is reported as a target that does not exist ===
Failing check: redshift.integration-conflict-and-quota-errors

AWS: CreateIntegration's TargetArn is 'the Amazon Resource Name (ARN) of the Amazon Redshift data warehouse to use as the target for replication'. Smithy (redshift, com-amazonaws-redshift-redshiftserviceversion20121201): CreateIntegration.TargetArn @required @length 20..2048 @pattern ^arn:aws[a-z\-]*:redshift(-serverless)?:[a-z0-9\-]+:[0-9]{12}:(namespace\/|namespace:)[a-z0-9\-]+$ — the pattern admits BOTH a provisioned-cluster namespace ARN and a redshift-SERVERLESS namespace ARN, so a serverless namespace is a first-class target. Modeled errors include IntegrationTargetNotFoundFault (httpError 404, awsQueryError IntegrationTargetNotFoundFault/404, doc: 'The specified integration target can't be found.') and IntegrationConflictOperationFault (httpError 400, awsQueryError IntegrationConflictOperationFault/400, doc: 'A conflicting conditional operation is currently in progress against this resource.'). AWS distinguishes the two cases: a TargetArn naming a namespace that does not exist is the 404 not-found class; a TargetArn naming a namespace that DOES exist but whose data warehouse (its workgroup) is still provisioning is the 400 conflict class, with the message AWS words for that error as fixed text and no variable parts: "Unable to perform create operation on the specified zero-ETL integration because its target Redshift data warehouse is not active. Wait until the data warehouse is active and try again." Once the workgroup reaches AVAILABLE the identical create must SUCCEED and return Status 'creating'.

Emulator: against a redshift-serverless namespace that was created, waited to available, and given a freshly created (still provisioning) workgroup, and whose resource policy authorizes the inbound integration, CreateIntegration is refused with error code 'IntegrationTargetNotFoundFault' — the check's assertion reads: AssertionError: expected ConflictOperation, got IntegrationTargetNotFoundFault. The handler resolves the target ONLY against this service's own provisioned-cluster store (`store.cluster_with_namespace_arn(&input.target_arn)`), and a serverless namespace is held by the redshift-serverless store, not that one; so every serverless-namespace target falls into the not-found branch regardless of the namespace's or workgroup's actual state — and never into the conflict branch, nor into a successful create once the warehouse IS active.

Why: a client that targets a redshift-serverless namespace (the ordinary zero-ETL target) can never create an integration at all — it gets a 404 'target can't be found' for a namespace it just created and can read back from redshift-serverless. The two refusal classes are also not distinguishable: 404 not-found is a permanent, non-retryable condition that tells a client its ARN is wrong, while 400 IntegrationConflictOperationFault is a transient condition whose documented message tells the client to wait for the warehouse to become active and retry. Collapsing the transient case into the permanent one makes correct client retry logic give up on a request that would have succeeded seconds later.

Fix: the CreateIntegration handler's target resolution (services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/create_integration.rs, the `cluster_with_namespace_arn` lookup and the status check immediately after it) must resolve a redshift-serverless namespace TargetArn against the serverless namespace/workgroup state as well as the provisioned-cluster store, and must classify the outcome three ways: namespace absent -> IntegrationTargetNotFoundFault (404); namespace present but its data warehouse not active -> IntegrationConflictOperationFault (400) carrying AWS's fixed conflict message above; warehouse active -> record the integration and return Status 'creating'. A refused create must still leave no integration behind (DescribeIntegrations must not list it), which the current handler does correctly. While in this handler, note that the same check next asserts the DUPLICATE-create class: AWS refuses a second integration for the same (SourceArn, TargetArn) PAIR with IntegrationAlreadyExistsFault whose message is "An integration from source {source} to target {target} already exists. Only one integration is allowed." (fixed text; {source} and {target} are the request's SourceArn and TargetArn), whereas this handler keys duplicate detection on IntegrationName only (`store.integration_named`) and words the message "Cannot create the integration because an integration with the name <name> already exists." That assertion is unreachable until the cause above is fixed, so it is reported here from the handler source rather than from an observed response; expect it to surface on the next replay of this check.

Traces: redshift.integration-conflict-and-quota-errors. Not covered by the open issue 20261024T115115Z-redshift-zero-etl-integration-error-semantics-unreachable-dynamodb.md: that one's CreateIntegration cause is a DynamoDB CreateTable SSESpecification stub blocking a DIFFERENT check (redshift.integration-error-semantics), and this check reaches Redshift and gets a wrong refusal class from the handler itself.

## Evidence
Expected: redshift.create_integration(IntegrationName=<name>, SourceArn='arn:aws:s3:::<bucket>', TargetArn='arn:aws:redshift-serverless:<region>:<account>:namespace/<ns>', TagList=[...]) while the namespace's workgroup is still provisioning -> HTTP 400, Error.Code 'IntegrationConflictOperationFault', Error.Message "Unable to perform create operation on the specified zero-ETL integration because its target Redshift data warehouse is not active. Wait until the data warehouse is active and try again." (entirely fixed text), and DescribeIntegrations lists no integration with that name. Then, after the workgroup reaches AVAILABLE, the identical call -> HTTP 200 with Status 'creating'.

Actual: HTTP 404, Error.Code 'IntegrationTargetNotFoundFault', message of the form 'Integration target not found: <TargetArn>' (the handler's own wording; the ARN is the request's). Replay assertion: check_redshift_integration_conflict_and_quota_errors.py line 172 -> AssertionError: expected ConflictOperation, got IntegrationTargetNotFoundFault. Handler evidence: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/create_integration.rs lines 284-311 resolve the target with store.cluster_with_namespace_arn(&input.target_arn) over the provisioned-cluster store only, returning IntegrationTargetNotFoundFault when it misses and InvalidClusterStateFault (never IntegrationConflictOperationFault) when the resolved cluster is not available.

## Steps to Reproduce
1. s3 CreateBucket <bucket> (+ a bucket policy allowing redshift.amazonaws.com s3:GetBucketNotification/PutBucketNotification/GetBucketLocation on it).
2. redshift-serverless CreateNamespace <ns>; wait for it to become available.
3. ec2: create a VPC/subnets; redshift-serverless CreateWorkgroup <wg> in namespace <ns> with those subnetIds, and do NOT wait for it.
4. redshift PutResourcePolicy on the namespace ARN authorizing redshift:AuthorizeInboundIntegration / redshift:CreateInboundIntegration for the bucket ARN.
5. IMMEDIATELY call redshift CreateIntegration with SourceArn='arn:aws:s3:::<bucket>' and TargetArn=<namespace ARN>. Observe HTTP 404 IntegrationTargetNotFoundFault instead of HTTP 400 IntegrationConflictOperationFault with the documented 'target Redshift data warehouse is not active' message.
6. Wait for the workgroup to reach AVAILABLE and repeat the identical CreateIntegration: observe it is still refused as a not-found target instead of returning 200 with Status 'creating'.
Replay: redshift.integration-conflict-and-quota-errors.
