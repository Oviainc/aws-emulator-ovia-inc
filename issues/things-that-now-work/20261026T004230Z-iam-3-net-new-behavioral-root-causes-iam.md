=== Cause 1 of 3: IAM policy variables are never expanded, so a Resource element written as `user/${aws:username}` grants nothing per-caller and the refusal it exists to produce never happens ===

AWS: an IAM policy document may contain policy VARIABLES — `${aws:username}`, `${aws:userid}`, `${aws:PrincipalTag/<key>}` and the rest — and they are placeholders substituted from the REQUEST CONTEXT at evaluation time, not at write time (IAM User Guide, "IAM policy elements: variables and tags"). They are legal inside a Resource ARN as well as inside a Condition value, and `${aws:username}` expands to the signing IAM user's friendly name without its path. The consequences that follow from that one rule, and that this check grades: (a) the document is STORED verbatim — GetPolicy/GetPolicyVersion return the document still containing the literal `${aws:username}`; (b) ONE managed policy naming `arn:aws:iam::<account>:user/${aws:username}`, attached to two users, permits each user's own iam:ListAccessKeys / iam:ListUserTags, because the variable expands to a different value per signer; (c) the SAME policy grants nothing on the OTHER user, so each user's iam:ListAccessKeys addressed at its sibling is refused — HTTP 403, awsQuery error code `AccessDenied` (Smithy com.amazonaws.iam#ListAccessKeys declares only NoSuchEntityException 404 / ServiceFailureException 500, so the authorization refusal is the service-common `AccessDenied` 403 and is recorded behavior rather than modeled); (d) adding an inline policy that names the sibling's ARN LITERALLY makes that same call succeed, and deleting it restores the refusal — which is what proves the refusal was the variable's scoping rather than a blanket ban on cross-user reads.

Emulator: there is no policy-variable substitution anywhere in the evaluator. services/common/src/iam_authorization.rs is the single evaluation of policy documents against a request, and neither its module documentation (lines 3-72, which enumerates exactly what it reads: Action/NotAction, Resource/NotResource, Principal/NotPrincipal, the string and ARN condition operators, the set qualifiers) nor its matcher mentions a variable: `wildcard_match` (line 271) compares the Resource element to the resource ARN as a literal pattern whose only metacharacters are `*` and `?`, so `${aws:username}` is matched as the eleven literal characters `${aws:username}` and can never equal a user name. On top of that the request never reaches the evaluator for these actions at all: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs declares action constants for only seven actions (lines 49-68: iam:ListGroups, iam:ListRoles, iam:ListUsers, iam:ListPolicies, iam:CreateGroup, iam:ListUserTags, iam:ListPolicyTags) and iam:ListAccessKeys is not one of them. Replay therefore shows the OVER-PERMISSIVE symptom, not the literal-match symptom: user A's signed `ListAccessKeys(UserName=<user B>)` answered HTTP 200 with user B's key metadata where AWS answers `AccessDenied` 403. The two legs that passed first pin that down — the stored document still carried the literal variable (so the write path is right) and each user's own read succeeded — so the divergence is exactly the cross-user leg.

Why: a developer's single-policy self-service pattern — one shared managed policy that lets every user administer only itself — is the canonical use of `${aws:username}`, and against this emulator it reads as working while granting every user full access to every other user's credentials metadata. The failure is silent and in the dangerous direction: the self-read succeeds (so the policy looks effective) and the cross-read also succeeds (so the scoping is absent). Once the gate is wired without variable support the same policy flips to the opposite wrong answer — both self-reads refused — and the developer still cannot tell a real scoping decision from an unmodelled one.

Fix: services/common/src/iam_authorization.rs must substitute policy variables into a statement's Resource/NotResource values (and into Condition values) from the request context before matching, using the request's resolved principal for `${aws:username}`/`${aws:userid}` and the principal's stored tags for `${aws:PrincipalTag/<key>}`, with IAM's `${...}` grammar (including the `${?}`, `${*}`, `${$}` literal escapes) so a `$` that is not a variable is still matched literally; and services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/list_access_keys.rs must call crate::state::authorization::authorize_named with an `iam:ListAccessKeys` action constant and the addressed user's ARN before building its page, with the caller's resolved identity supplied to the request so the variable has a value to expand to. PREREQUISITE, not a duplicate: the open issue 20261025T170540Z-iam-4-net-new-root-causes-the-authorization.md Cause 1 reports that most IAM handlers (ListAccessKeys among them) reach no gate at all, and its Cause 2 reports that the gate builds an empty condition context; wiring those two is necessary but NOT sufficient for this check, because neither of them makes `${aws:username}` expand — with the gate wired and no variable support this check's two positive legs (each user's own read) become permanent refusals. No open issue names policy-variable expansion.

=== Cause 2 of 3: TagPolicy's NoSuchEntity message is the emulator's own wording, not AWS's ===

AWS: TagPolicy against a PolicyArn the account holds no customer managed policy under is refused with NoSuchEntityException — Smithy com.amazonaws.iam#TagPolicy errors: ConcurrentModificationException 409 / InvalidInputException 400 / LimitExceededException 409 / NoSuchEntityException 404 / ServiceFailureException 500; NoSuchEntityException carries awsQueryError code `NoSuchEntity` with httpResponseCode 404 and is documented "The request was rejected because it referenced a resource entity that does not exist. The error message describes the resource." The message AWS produces for this error class is `Policy <PolicyArn> was not found.` — its FIXED text is `Policy ` and ` was not found.`, and its one VARIABLE part is the PolicyArn exactly as the request supplied it (the check builds that ARN from the account id the target itself reports, so no account, name or id from one run is part of the requirement).

Emulator: the handler mints its own sentence. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/tag_policy.rs line 256 returns `NoSuchEntityException { message: Some(format!("Policy {} does not exist.", input.policy_arn)) }`. Replay: the status and the code are right (404 / `NoSuchEntity`) and the whole happy path of the check passed (TagPolicy persisted the tag and both ListPolicyTags and GetPolicy reflected it), so the ONLY divergence is the message body — `Policy arn:aws:iam::<account>:policy/<name> does not exist.` where AWS says `Policy arn:aws:iam::<account>:policy/<name> was not found.`

Why: the error message is part of the contract. A client, test harness or operator runbook that matches AWS's `was not found.` wording — and anything that reports the message to a human — sees text AWS never emits, so a correct 404/NoSuchEntity refusal still reads as an unknown failure.

Fix: the NoSuchEntityException construction in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/tag_policy.rs (the `policy_by_arn_mut` miss, line 253-260) must use AWS's wording for this error class. Related but a different handler and a different message, so NOT the same defect: the open issue 20261025T050617Z-iam-2-net-new-root-causes-listentitiesforpolicy-s.md reports ListEntitiesForPolicy's NoSuchEntity message dropping AWS's 'or is not attachable' clause; it does not name TagPolicy or this wording.

=== Cause 3 of 3: an aws:PrincipalTag-conditioned decision on iam:ListUserPolicies never changes, so the retag-driven refusal is unobservable and the check runs to the harness cap ===

AWS: `aws:PrincipalTag/<key>` is read from the SIGNING principal's CURRENT tags at request time — nothing in the request carries them, so the authorizer must look them up on the caller. With an identity policy containing {Allow iam:ListUserPolicies on <own user ARN>, Condition StringEquals aws:PrincipalTag/team == <v1>} the behavior is a state transition over a retag that changes no request byte: while the user is tagged team=<v1> the real signed ListUserPolicies succeeds; retagging ONLY the user to team=<v2> makes the same call `AccessDenied` 403 (Smithy com.amazonaws.iam#ListUserPolicies models no authorization error, so AccessDenied 403 is the service-common refusal — recorded behavior only); retagging back restores the success, and an unconditioned iam:GetUser control succeeds throughout. The SimulatePrincipalPolicy view must agree with the real call: fed `ContextEntries=[{aws:PrincipalTag/team: <the user's actual tag>}]` its EvalDecision is `allowed` for <v1> and `implicitDeny` for <v2> (Smithy com.amazonaws.iam#SimulatePrincipalPolicy -> SimulatePolicyResponse$EvaluationResults), and given NO context it does not guess: the decision is `implicitDeny` and the key is named in EvaluationResult$MissingContextValues.

Emulator: the check never completes — the replay verdict is `Check timed out after 60.0s`, so every poll in it is a 150 s settle that the 60 s harness cap kills. The harness reports no intermediate observation, so which leg stalls is not stated by the recording; the two legs that can stall forever are both visible in this checkout. (1) iam:ListUserPolicies reaches no authorization gate: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs lines 49-68 declare action constants for only seven actions and iam:ListUserPolicies is not among them, so the real call answers 200 for any signer and the post-retag poll for `AccessDenied` can never converge. (2) No aws:PrincipalTag value is ever derivable: services/common/src/iam_authorization.rs decides a Condition clause only for keys the request's context carries and leaves any other key UNDECIDED fail-closed (module docs lines 51-72), and the gate's request is built with `iam::Request::new(...)` whose context is empty, so the tag-conditioned Allow can never grant either — meaning the pre-retag poll for `OK` cannot converge once the gate IS wired. Either way the transition this check measures — allow, then deny, then allow again, driven only by a retag — is never produced.

Why: ABAC over principal tags is the mechanism a team uses to scope IAM self-administration, and here it is inert in both directions: today every tag-conditioned Allow over-permits (the action is ungated) and after the gate is wired, with no principal-tag context, every one of them under-permits permanently. A developer cannot tell "my condition does not match" from "this emulator does not model the key", and because the check consumes the whole 60 s budget it also returns no diagnosis at all. The simulator-vs-real-call agreement this check pins is the thing a reviewer leans on before shipping a tag-scoped policy.

Fix: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/list_user_policies.rs must call crate::state::authorization::authorize_named with an `iam:ListUserPolicies` action constant and the addressed user's ARN before reading the store, and src/state/authorization.rs must assemble the request's condition context through `iam::Request::with_context` (service-common already exposes it, iam_authorization.rs line 160), populating `aws:PrincipalTag/<key>` from the resolved signing principal's stored tags in src/state.rs and declaring the key through `Request::published`; src/ops/simulate_principal_policy.rs must decide the same clause from a supplied `aws:PrincipalTag/*` ContextEntry so the simulated and the real decision cannot disagree. Related open issues, named so a fixer can see the overlap and NOT close this cause by closing them: 20261025T170540Z-iam-4-net-new-root-causes-the-authorization.md (Causes 1 and 2 — gate wiring for other operations, and the empty condition context), 20261025T121312Z-iam-request-time-authorization-supplies-no-condition-context.md, and the SimulatePrincipalPolicy issues 20261025T102129Z-iam-10-net-new-behavioral-root-causes-simulateprincipalpolicy.md and 20261025T085808Z-iam-kms-simulateprincipalpolicy-ignores-the-simulated-principal-when-evaluating-resourcepolicy.md. None of them names iam:ListUserPolicies, and none grades the retag-driven allow->deny->allow transition this check is the only grader of.
