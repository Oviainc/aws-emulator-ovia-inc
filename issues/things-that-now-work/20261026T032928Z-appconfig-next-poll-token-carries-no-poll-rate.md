# AppConfig next-poll token carries no poll-rate obligation and the deployed configuration never reaches the poll loop, so the early-poll refusal is unreachable

> _Note: this issue was identified against the code base at commit `632275b31d4caea8230a511abd27a180321ca025`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause in the bootstrapped appconfig/appconfigdata poll surface, grounded in the replayed behavioral check appconfig.next-poll-token-before-minimum-interval-rejected (verdict: mismatch, detail 'Check timed out after 60.0s'). Close Cause 1 of 1 before submitting and re-replay the check id listed in trace_ids.

NOTE ON OVERLAP: the open issue 20261024T112615Z-appconfigdata-data-plane-deployed-configuration-never-served-sessions.md describes the same data plane under the service token `appconfigdata` (its Cause 1 is 'GetLatestConfiguration answers 404 No deployed configuration found after the control plane reports the deployment COMPLETE'). That issue does NOT carry this check id as a replay key and this check was NOT marked OWNED by it, so this issue binds it; the poll-RATE half below is behavior that issue does not describe at all.

=== Cause 1 of 1: a NextPollConfigurationToken is accepted (or the session never gets that far) instead of being refused before NextPollIntervalInSeconds has elapsed ===
AWS: StartConfigurationSession with RequiredMinimumPollIntervalInSeconds=N returns a session whose first GetLatestConfiguration serves the deployed bytes with NextPollIntervalInSeconds >= N and a ROTATED NextPollConfigurationToken (Smithy, services/service-com-amazonaws-appconfigdata-appconfigdata/smithy-model/com-amazonaws-appconfigdata-appconfigdata.json: GetLatestConfiguration GET /configuration, success 200; input ConfigurationToken @httpQuery configuration_token @required pattern ^\S{1,8192}$; output Configuration @httpPayload blob (sensitive), NextPollConfigurationToken @httpHeader Next-Poll-Configuration-Token, NextPollIntervalInSeconds @httpHeader Next-Poll-Interval-In-Seconds, ContentType @httpHeader Content-Type, VersionLabel @httpHeader Version-Label; errors BadRequestException 400, ResourceNotFoundException 404, InternalServerException 500, ThrottlingException 429). Re-presenting that next-poll token BEFORE the interval has elapsed is refused with BadRequestException, HTTP 400, Reason=InvalidParameters and the recorded message 'Request too early'. The model carries the structured discriminator for exactly this class: BadRequestException.Details is a BadRequestDetails union whose InvalidParameters member maps a parameter name to InvalidParameterDetail{Problem}, and InvalidParameterProblem enumerates Corrupted, Expired and PollIntervalNotSatisfied — PollIntervalNotSatisfied exists only to name this refusal. The message's fixed text is the whole sentence 'Request too early'; it has no variable parts taken from the request or state. The refusal must have NO effect: it serves no configuration and does NOT consume or invalidate the token — once the interval passes the SAME token is accepted and returns the documented EMPTY payload (meaning 'unchanged') plus a freshly rotated next-poll token. Recorded behavior (us-west-2, 2026-09-11) for the interval itself: RequiredMinimumPollIntervalInSeconds=60 yields NextPollIntervalInSeconds=60. Only the code, the message and the no-effect invariant are requirements; the token values and the interval number come from the request and the emulator's own state.
Emulator: the check never reaches a verdict — it is cut off at the harness budget ('Check timed out after 60.0s') while polling. Up to that point the emulator offers no early-poll refusal at all: the session's own first-poll acceptance loop (get_latest_configuration every 5s until the deployed bytes come back) does not terminate, which is the already-filed data-plane defect — GetLatestConfiguration refuses with ResourceNotFoundException/404 'No deployed configuration found for application <app>, environment <env> and configuration profile <profile>' even after the appconfig control plane reports the deployment State COMPLETE, so no NextPollConfigurationToken is ever handed back and the rate rule it would carry is never exercised. Hypothesis: the poll chain is implemented as a stateless token lookup with no per-session issue time, so even once the data plane serves content, a next-poll token presented immediately would be answered 200 with the payload rather than 400 'Request too early'.
Why: a long-polling client gets the opposite of AWS on both halves. Today it cannot retrieve its configuration at all; once that is fixed, a client that re-presents its next-poll token immediately is served instead of being rate-refused, so a poll loop written against the emulator hammers the real service and is throttled/refused in production, and a client that keys its back-off on BadRequestException + Details.InvalidParameters.ConfigurationToken.Problem == PollIntervalNotSatisfied never sees that signal and cannot distinguish 'back off and retry the SAME token' from 'the token is dead, restart the session'. Conversely an emulator that refuses every re-presentation unconditionally would break the no-effect invariant the check also pins (the same token must become acceptable after the interval, and a brand-new session must be served with no wait at all).
Fix: the GetLatestConfiguration handler and the appconfigdata session state it reads, plus that service's error serializer. The session record must carry the negotiated poll interval and the issue time of each token it mints; the handler must resolve the presented token to its session, refuse a presentation earlier than issue_time + NextPollIntervalInSeconds with BadRequestException/400, message 'Request too early', Reason=InvalidParameters and Details.InvalidParameters['ConfigurationToken'].Problem = PollIntervalNotSatisfied, WITHOUT rotating or invalidating that token, and otherwise serve the latest COMPLETE deployment's content for the session's application/environment/profile triple (empty payload when nothing changed since the last served version) with a rotated token and NextPollIntervalInSeconds honouring RequiredMinimumPollIntervalInSeconds. The not-found that blocks the loop today belongs to the deployment lookup in the same handler.
Traces: appconfig.next-poll-token-before-minimum-interval-rejected.

## Steps to Reproduce
Boot the emulator and point an appconfig client and an appconfigdata client at its data listener.

1. appconfig: create_application -> create_environment -> create_configuration_profile(LocationUri='hosted') -> create_deployment_strategy(DeploymentDurationInMinutes=0, GrowthFactor=100, FinalBakeTimeInMinutes=0, ReplicateTo='NONE') -> create_hosted_configuration_version(Content=b'{"tier":"one"}', ContentType='application/json') -> start_deployment(ConfigurationVersion=<that version>) and poll get_deployment until State == 'COMPLETE'.
2. appconfigdata: start_configuration_session(ApplicationIdentifier=<app>, EnvironmentIdentifier=<env>, ConfigurationProfileIdentifier=<profile>, RequiredMinimumPollIntervalInSeconds=60).
3. get_latest_configuration(ConfigurationToken=<InitialConfigurationToken>). EXPECTED: HTTP 200, payload == b'{"tier":"one"}', NextPollIntervalInSeconds >= 60, NextPollConfigurationToken != the initial token. OBSERVED today: ResourceNotFoundException / 404 'No deployed configuration found for application ... environment ... and configuration profile ...', so no next-poll token exists — this is the blocking half.
4. Immediately (no sleep) call get_latest_configuration(ConfigurationToken=<NextPollConfigurationToken from step 3>). EXPECTED: BadRequestException, HTTP 400, Error['Message'] == 'Request too early', Reason == 'InvalidParameters', Details.InvalidParameters['ConfigurationToken'].Problem == 'PollIntervalNotSatisfied', and NO configuration served. A 200 with the payload here is the over-permissiveness failure.
5. Re-present the SAME token in a loop with 5s sleeps. EXPECTED: at least one further 'Request too early' refusal, then an ACCEPTED 200 whose payload is EMPTY (b'') and whose NextPollConfigurationToken differs again — i.e. the refusals neither consumed nor invalidated the token.
6. Positive control: start a brand-new session on the same triple and call get_latest_configuration on its InitialConfigurationToken with no wait. EXPECTED: HTTP 200 with the deployed bytes — the rate rule is per-session, not per-configuration.
