# ses v1 identity plane reports no identity with VerificationStatus 'Success', so the positive control of CreateCustomVerificationEmailTemplate's FromEmailAddressNotVerified gate cannot be reached

> _Note: this issue was identified against the code base at commit `dbd8b6da40b3283b718ba9768f41bda1f397bd18`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIdentityVerificationAttributes

## Description
One root cause, grounded in one failing check of the `ses` suite directory.

Cause 1 of 1: the SES v1 identity-verification plane never projects a verified identity. ListIdentities/GetIdentityVerificationAttributes answer 200 but no identity in the account — neither an EmailAddress identity nor a Domain identity — is reported with VerificationStatus 'Success', so the check's positive control (`_verified_sender_email` -> `_find_verified_identity`) can resolve no sender and aborts with `AssertionError: the account has no SES identity verified for sending`. The negative half of the same check already passes: CreateCustomVerificationEmailTemplate for an unverified FromEmailAddress is refused correctly and leaves nothing behind, so the remaining divergence is confined to the verification-state reads.

AWS: Smithy (com.amazonaws.ses) ListIdentities -> output ListIdentitiesResponse{Identities (required, IdentityList)}, input {IdentityType (enum IdentityType: EmailAddress|Domain), NextToken, MaxItems}, paginated inputToken=NextToken/outputToken=NextToken/items=Identities, no modeled errors. GetIdentityVerificationAttributes -> input {Identities (required)}, output {VerificationAttributes (required, map of identity -> IdentityVerificationAttributes{VerificationStatus (required, enum Pending|Success|Failed|TemporaryFailure|NotStarted), VerificationToken})}, no modeled errors; the member doc states the status is "Pending", "Success", "Failed" or "TemporaryFailure". CreateCustomVerificationEmailTemplate -> input {TemplateName, FromEmailAddress, TemplateSubject, TemplateContent, SuccessRedirectionURL, FailureRedirectionURL} all required, empty output, modeled refusals FromEmailAddressNotVerifiedException (400, awsQueryError code FromEmailAddressNotVerified), CustomVerificationEmailTemplateAlreadyExistsException (400), CustomVerificationEmailInvalidContentException (400), LimitExceededException (400); GetCustomVerificationEmailTemplate refuses an absent name with CustomVerificationEmailTemplateDoesNotExistException (400). Beyond those signatures this is recorded behavior only: against real AWS an identity the account has completed verification for (a domain whose Easy DKIM CNAMEs are published in its public hosted zone, or an email address whose confirmation link was followed) is enumerated by ListIdentities for its IdentityType and GetIdentityVerificationAttributes reports that identity with VerificationStatus 'Success' (and, for a domain, a VerificationToken; null for an email address). CreateCustomVerificationEmailTemplate with a FromEmailAddress under such an identity then succeeds (200, empty body) and GetCustomVerificationEmailTemplate echoes that FromEmailAddress verbatim. The requirement is general and about no particular identity name: whatever identity the account has verified must read back as 'Success' through the v1 attributes map.

Emulator: nothing is refused — verify_email_identity, list_identities and get_identity_verification_attributes all answer 2xx — but the account presents no identity whose VerificationStatus is 'Success'. Paging ListIdentities(IdentityType='EmailAddress') and then ListIdentities(IdentityType='Domain') and feeding each result to GetIdentityVerificationAttributes yields a VerificationAttributes map in which no entry carries 'Success' (either the lists come back empty, or every entry reads 'Pending'/'NotStarted'). The check therefore raises its precondition assertion — fixed text "the account has no SES identity verified for sending", no variable parts — and the success path of CreateCustomVerificationEmailTemplate plus the FromEmailAddress echo on GetCustomVerificationEmailTemplate are never exercised. Hypothesis: the v1 identity store holds no identity that ever transitions to 'Success' (the sesv2 email-identity verification state, where VerifiedForSendingStatus is set, is not projected into the v1 VerificationAttributes map), so no verified sender exists for any v1 caller.

Why: a client cannot discover which of its identities is usable as a sender — the standard pre-flight for every SES send and for every operation gated on sender verification. Because no identity reads 'Success', the emulator's FromEmailAddressNotVerified refusal is indistinguishable from a blanket denial of CreateCustomVerificationEmailTemplate: a caller that does hold a verified sender is refused identically to one that does not, and tooling that branches on VerificationStatus concludes the account can send from nothing.

Fix: the ses (v1) identity state and its verification-attribute reads — the identity registry behind ListIdentities (its IdentityType partitioning) and the VerificationStatus/VerificationToken that GetIdentityVerificationAttributes projects for each identity — must reach and report 'Success' for an identity the account has verified, and must agree with the sesv2 email-identity verification state (VerifiedForSendingStatus / DkimAttributes.Status) for the same identity; the FromEmailAddress verification gate in CreateCustomVerificationEmailTemplate's handler must then admit a sender under such an identity. Related but non-covering: 20261029T143522Z-ses-the-account-s-dns-baseline-public-hosted.md reports the route53 tag-discovery path for four other ses checks and carries only their check ids; this check does not use route53 at all — it reads verification state through the ses v1 identity APIs — so that issue does not cover it.

Traces: ses.custom-verification-template-unverified-from-fails (run line 69 -> _verified_sender_email line 92).

## Evidence
Expected (AWS, recorded): ses.list_identities(IdentityType='EmailAddress'|'Domain', MaxItems=100) enumerates the account's identities and ses.get_identity_verification_attributes(Identities=[...]) returns a VerificationAttributes map containing at least one entry with VerificationStatus == 'Success'; a FromEmailAddress under that identity is then accepted by CreateCustomVerificationEmailTemplate (200, empty body) and GetCustomVerificationEmailTemplate returns that same FromEmailAddress.

Actual (emulator): the negative assertions of the check pass — CreateCustomVerificationEmailTemplate with an unverified FromEmailAddress is refused 400 FromEmailAddressNotVerified with message "The from email address <from-email> is not verified." (fixed text "The from email address " + " is not verified.", the address taken from the request), and GetCustomVerificationEmailTemplate on the rejected name is refused 400 CustomVerificationEmailTemplateDoesNotExist with "Provided custom verification email template name does not exist." — but the positive control cannot run:
[mismatch] ses.custom-verification-template-unverified-from-fails — check_ses_custom_verification_template_unverified_from_fails.py line 69 (run) -> line 92 (_verified_sender_email): AssertionError: the account has no SES identity verified for sending

The divergence is in what the v1 verification reads report, not in any status code: every call answers 2xx, yet no identity in the account is ever reported with VerificationStatus 'Success' (the modeled enum admits Pending|Success|Failed|TemporaryFailure|NotStarted). The assertion's text is entirely fixed; the identities and statuses it inspected are values from the emulator's state.

## Steps to Reproduce
1. Build and boot the emulator, then run the behavioral suite.
2. Bring an identity to verified in the emulator the way a customer does (sesv2 CreateEmailIdentity for a domain whose Easy DKIM CNAMEs are published in its public hosted zone, or ses VerifyEmailIdentity followed by the account's confirmation path) and confirm sesv2 GetEmailIdentity reports VerifiedForSendingStatus true.
3. Call ses.list_identities(IdentityType='EmailAddress', MaxItems=100) and ses.list_identities(IdentityType='Domain', MaxItems=100), then ses.get_identity_verification_attributes(Identities=<each result>).
4. Observe: every call answers 200, but no entry of VerificationAttributes carries VerificationStatus 'Success' (lists empty, or statuses stuck at 'Pending'/'NotStarted'), so no sender address can be derived.
5. Re-replay ses.custom-verification-template-unverified-from-fails: its unverified-sender refusal and the absent-template Get both assert correctly, then it aborts in _verified_sender_email before the positive CreateCustomVerificationEmailTemplate / GetCustomVerificationEmailTemplate pair is issued.
