# CloudWatch alarm evaluator: StateReasonData datapoint timestamps are rendered as RFC3339 'Z' instead of AWS's '.SSS+0000' form, and the evaluation tick ignores the alarm's Period (2 causes)

> _Note: this issue was identified against the code base at commit `96aab6874df7daa64c84ed9b117b617756506559`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlarms

## Description
Two net-new root causes in the CloudWatch emulator's alarm evaluator. Both are reached only AFTER an evaluation has run and produced a correctly-worded verdict, so they are NOT the already-open 20261025T020208Z-cloudwatch-alarms-never-evaluate-published-metric-data-no.md (no evaluation at all). Cause 1 is adjacent to, but distinct from, the still-open 20261025T053543Z-cloudwatch-alarm-evaluation-and-metric-read-fidelity-statereason.md: that issue reports StateReasonData with the `recentDatapoints` key and the `evaluatedDatapoints[].timestamp` key MISSING (KeyError) and the StateReason sentence not matching AWS's 'Threshold Crossed' format. In this replay all of that now holds — the StateReason regex matches, `recentDatapoints` is present, `evaluatedDatapoints` entries carry a `timestamp` — and the remaining divergence is the SERIALIZED FORM of that timestamp value. Cause 2 is named by no open issue.

=== Cause 1 of 2: StateReasonData / HistoryData datapoint timestamps use the wrong timestamp format ===
AWS: Smithy: MetricAlarm.StateReasonData -> StateReasonData, a string @length 0..4000 documented "An explanation for the alarm state, in JSON format."; AlarmHistoryItem.HistoryData -> HistoryData @length 1..4095, "Data about the alarm, in JSON format." The model does not fix the inner JSON, so the timestamp rendering is recorded behavior only: real CloudWatch stamps every datapoint inside that JSON (`evaluatedDatapoints[].timestamp`, and the same renderer's `startDate`/`queryDate`) in the Java `yyyy-MM-dd'T'HH:mm:ss.SSSZ` form — a 3-digit millisecond field and a numeric UTC offset, e.g. `2026-09-22T23:06:00.000+0000` and `2026-10-01T19:50:00.000+0000` as recorded by these checks. The fixed text of that template is the `-`/`T`/`:` separators, the literal `.` before a 3-digit millisecond field, and the trailing `+0000` numeric offset; the variable parts are the date and time of the evaluated bucket, taken from the alarm's own evaluation window.
Emulator: the same member is rendered as RFC3339-with-Z and with NO millisecond field: `2026-10-27T01:40:30Z` (also observed `2026-10-27T01:53:20Z`, `2026-10-27T02:00:20Z`, `2026-10-27T01:42:30Z` — the clock values differ per run, the FORM does not). The millisecond field is absent and `Z` replaces `+0000`.
Why: StateReasonData and HistoryData are the machine-readable half of an alarm decision, and the documented AWS form is what every consumer parses with `%Y-%m-%dT%H:%M:%S.%f%z` (or a Java `SimpleDateFormat` with the same pattern). Against the emulator that parse raises instead of yielding a datetime, so a client cannot recover WHEN the evaluator graded a datapoint, cannot join the evaluated datapoint back onto a GetMetricData/GetMetricStatistics bucket, and cannot cross-check the cited value against the series — the alarm's reason becomes unparseable rather than merely different.
Fix: the StateReasonData/HistoryData JSON serializer in the cloudwatch service crate's alarm evaluator — the same component the open statereason issue names, on its timestamp-formatting path (it must emit the millisecond field and the `+0000` offset rather than delegating to a default RFC3339/`Z` timestamp writer).
Traces: cloudwatch.alarm-evaluation-engine-greater-than-operators-split-at-equal-threshold, cloudwatch.alarm-evaluation-engine-less-than-operators-split-at-equal-threshold, cloudwatch.alarm-evaluation-engine-statistic-maximum-alarms-where-average-does-not, cloudwatch.alarm-unit-and-percentile-traps-standard-resolution-accepts-sub-minute-period-but-buckets-by-minute

=== Cause 2 of 2: the evaluation tick is not the alarm's Period — an alarm transitions before its window can close ===
AWS: Smithy: PutMetricAlarm.Period -> Period, integer @range min 1, documented "The length, in seconds, used each time the metric specified in MetricName is evaluated. Valid values are 10, 20, 30, and any multiple of 60 ... Specifying 10, 20, or 30 also sets this alarm as a high-resolution alarm"; EvaluationPeriods is "the number of periods over which data is compared to the specified threshold". The requirement that follows: an alarm cannot reach ALARM before DatapointsToAlarm periods of Period seconds each have been aggregated and graded, so between two alarms over the SAME metric and the SAME data a 3x10s window must close before a 1x60s one. Recorded on real AWS (us-west-2): the Period=10/EvaluationPeriods=3/DatapointsToAlarm=3 alarm reached ALARM 40.3 s after the first publish and the Period=60/1-of-1 control took 100.9 s — the high-resolution alarm first, each no sooner than its own window width.
Emulator: the ordering is inverted and both transitions happen sooner than one window: on the same metric and the same single PutMetricData burst, the Period=10 3-of-3 alarm reached ALARM at 15.0 s and the Period=60 1-of-1 control at 5.0 s. A 1x60s window cannot have closed 5 s after the first and only publish, and a 3x10s window cannot have closed at 15 s. Everything the same check asserts before this point passes: Period=10/30 round-trip unchanged through DescribeAlarms, all three alarms are created INSUFFICIENT_DATA on a metric that has never been written, and Period=45 is refused with code ValidationError and a message containing "Period must be 10, 20, 30 or a multiple of 60" leaving no alarm behind. Hypothesis: the evaluator grades on datapoint arrival (or on a fixed internal tick) using whatever datapoints exist, rather than laying Period-wide buckets and requiring DatapointsToAlarm of them.
Why: Period and EvaluationPeriods are the only controls a client has over alarm sensitivity, and here they do not control anything observable. A deliberately-damped alarm (long period, many evaluation periods) fires as fast as a twitchy one, so every alarm behaves as 1-of-1 on the newest data: flap suppression, m-of-n damping and the high-resolution/standard-resolution distinction are all unobtainable, and a client cannot tell a genuinely sustained breach from a single spike.
Fix: the alarm evaluator's scheduling and window assembly in the cloudwatch service crate — the component that decides when an alarm is re-graded and which Period-wide buckets form its EvaluationPeriods window.
Traces: cloudwatch.high-resolution-alarm-evaluates-ten-second-periods-and-rejects-invalid-period
