# Route 53 Resolver rule error messages omit the RSLVR-nnnnn service error code and use non-AWS wording (ResourceInUseException on DeleteResolverRule, ResourceNotFoundException on GetResolverRule and DisassociateResolverRule)

> _Note: this issue was identified against the code base at commit `444cbe40db1434e138785b95152adaa2e53ade67`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteResolverRule

## Description
THREE distinct root causes, all in the route53resolver service, all in the Resolver-RULE error bodies. The HTTP status (400) and the wire error code are already correct in every one of them; what diverges is the Error.Message, which Route 53 Resolver words with its own `[RSLVR-nnnnn]` service error code followed by a fixed sentence. A fixer must close ALL THREE before submitting; each cause lists its own failing check ids.

The emulator already knows this convention and applies it for ENDPOINT faults: services/service-com-amazonaws-route53resolver-route53resolver/src/state.rs documents "Route 53 Resolver carries its own `RSLVR-nnnnn` code inside every exception message" and ships `rslvr_message(code, sentence)` plus RSLVR_CODE_ENDPOINT_NOT_FOUND ("RSLVR-00501"), RSLVR_CODE_SYSTEM_RULE_FORWARDING_TARGET ("RSLVR-00707"), RSLVR_CODE_FORWARD_RULE_FORWARDING_TARGET_REQUIRED ("RSLVR-00706") and RSLVR_CODE_INSTANCE_COUNT_BELOW_MINIMUM ("RSLVR-03002"). The three rule helpers below deliberately omit a code, each carrying a doc comment saying "no recorded response available here states the code Route 53 Resolver uses for a missing rule ... so the message states the fault plainly instead of inventing one". These three replayed checks ARE that missing evidence: they state the codes AWS uses (RSLVR-00702, RSLVR-00703, RSLVR-00800), so the wording is no longer an unconstrained choice.

(Related but NOT covering these: open issue 20261025T012620Z-route53resolver-route-53-resolver-rule-firewall-write-path-disassociateresolverrule.md and 20261025T131134Z-route53resolver-disassociateresolverrule-stub.md concern DisassociateResolverRule being a 501 stub and AssociateResolverRule skipping VPC validation — a different failure mode; the check below now gets the correct code 400/ResourceNotFoundException and fails only on the message. 20261025T012620Z-route53resolver-deleteresolverrule-stub.md concerns DeleteResolverRule being a stub; it is implemented in the replayed build and fails only on the message.)

Cause 1 of 3: DeleteResolverRule's ResourceInUseException message is entirely different prose from AWS's.
AWS: Smithy: DeleteResolverRule(ResolverRuleId: ResourceId @length 1..64, required) models ResourceInUseException at HTTP 400 ("The resource that you tried to update or delete is currently in use."); the model states no message text. Recorded behavior: deleting a rule that is still associated with a VPC is refused with HTTP 400, error code ResourceInUseException and the message '[RSLVR-00702] Please disassociate this resolver rule from VPC first before deleting.' That message is ENTIRELY fixed text — it has no variable parts at all: no rule id, no VPC id and no association count appear in it.
Emulator: same status and same code, but the message is 'Before you can delete a Resolver rule, you must disassociate it from all the VPCs that you associated the Resolver rule with. Resolver rule with ID "<rule-id>" is still associated with <n> VPC(s).' — the operation's doc sentence plus the rule id and the store's association count, with no RSLVR code. Built by `resolver_rule_in_use(resolver_rule_id, associations)`.
Why: Route 53 Resolver returns HTTP 400 for every modeled error, so the RSLVR code inside the message is the only discriminator a client, log pipeline or operator can key on to tell this fault from the other 400s of the same shape. A client that matches on '[RSLVR-00702]' (or just on the leading '[RSLVR-' code) never matches, so its retry/remediation branch for "disassociate first" is dead against the emulator while it fires against AWS.
Fix: the message helper in the service state — `resolver_rule_in_use` in services/service-com-amazonaws-route53resolver-route53resolver/src/state.rs — must emit the RSLVR-coded fixed sentence through the existing `rslvr_message` helper and stop echoing the rule id and association count, which AWS does not include.
Traces: route53resolver.delete-resolver-rule-in-use-rejected.

Cause 2 of 3: the ResourceNotFoundException for an unknown/deleted Resolver rule is missing its '[RSLVR-00703] ' prefix.
AWS: Smithy: GetResolverRule and UpdateResolverRule both model ResourceNotFoundException at HTTP 400 ("The specified resource doesn't exist."); the model states no message text. Recorded behavior: reading or updating a rule id the account holds no rule under answers HTTP 400 / ResourceNotFoundException with message '[RSLVR-00703] Resolver rule with ID "<rule-id>" does not exist.' Fixed text: '[RSLVR-00703] Resolver rule with ID "' ... '" does not exist.'; the single variable part is the ResolverRuleId taken verbatim from the request.
Emulator: the sentence and the double-quoted id are already right, but the code prefix is absent — 'Resolver rule with ID "<rule-id>" does not exist.' Built by `resolver_rule_not_found(resolver_rule_id)`, whose doc comment explicitly declines to invent a code.
Why: same discriminator problem as Cause 1, and this is the most frequently observed Resolver fault of all (every post-delete read and every stale id hits it). Any client, test or log matcher anchored on the RSLVR code — or on the message as a whole — diverges on the single most common error path of the service.
Fix: same helper module — `resolver_rule_not_found` in src/state.rs must route its sentence through `rslvr_message` with a new RSLVR-00703 constant beside the existing RSLVR_CODE_* ones. The sentence and the quoting are already correct and must not change. The same correction is owed to `resolver_rule_not_found`'s callers transitively (DeleteResolverRule, GetResolverRule, UpdateResolverRule) since they all share this one body.
Traces: route53resolver.resolver-rule-target-ip-port-round-trip (asserts the GetResolverRule body after the rule is deleted), route53resolver.delete-resolver-rule-in-use-rejected (also asserts the UpdateResolverRule-after-delete body '[RSLVR-00703] Resolver rule with ID "<rule-id>" does not exist.').

Cause 3 of 3: DisassociateResolverRule's ResourceNotFoundException for a never-associated rule/VPC pair describes the wrong resource and omits '[RSLVR-00800] '.
AWS: Smithy: DisassociateResolverRule(VPCId required, ResolverRuleId required -> ResolverRuleAssociation) models ResourceNotFoundException at HTTP 400; the model states no message text. Recorded behavior: a pair that was never associated answers HTTP 400 / ResourceNotFoundException with '[RSLVR-00800] Resolver Rule Association between Resolver Rule "<rule-id>" and VPC "<vpc-id>" does not exist.' Fixed text: '[RSLVR-00800] Resolver Rule Association between Resolver Rule "' ... '" and VPC "' ... '" does not exist.'; the two variable parts are the ResolverRuleId and the VPCId taken verbatim from the request. AWS names the missing resource as the ASSOCIATION, not as a property of the rule.
Emulator: same status and code, but the message is 'Resolver rule with ID "<rule-id>" is not associated with VPC with ID "<vpc-id>".' — no RSLVR code and a different subject (the rule's association state rather than a missing ResolverRuleAssociation resource). Built by `resolver_rule_vpc_association_not_found(resolver_rule_id, vpc_id)`.
Why: same discriminator problem, plus the message describes a different thing than AWS's does, so a client that surfaces the service message to a user or matches on 'Resolver Rule Association' sees text AWS never produces.
Fix: `resolver_rule_vpc_association_not_found` in src/state.rs must emit the RSLVR-00800-coded sentence in AWS's wording via `rslvr_message`, with the rule id and VPC id as its only interpolated values. `resource_type: ResolverRuleAssociation` is already correct.
Traces: route53resolver.disassociate-resolver-rule-not-associated-invalid-request.
