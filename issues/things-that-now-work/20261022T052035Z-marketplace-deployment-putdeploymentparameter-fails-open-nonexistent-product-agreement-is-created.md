# PutDeploymentParameter fails open: nonexistent product/agreement is created with 200 instead of ResourceNotFoundException, and catalog ValidationException message emits the anchored regex (2 causes)

> _Note: this issue was identified against the code base at commit `f2a9c91c50f7e55687472cf5b456a197c6c3ca83`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutDeploymentParameter

## Description
Two independent root causes in marketplace-deployment's PutDeploymentParameter path. Both were found by replaying the behavioral suite against the running emulator; marketplace-deployment answers requests, so these are fidelity divergences, not bootstrap gaps.

Cause 1 of 2: PutDeploymentParameter never checks that the targeted product/agreement exists, so every syntactically valid request creates a deployment parameter and answers 200.
AWS: PutDeploymentParameter targets a real, fulfilled AWS Marketplace agreement. Smithy (com.amazonaws.marketplacedeployment#PutDeploymentParameter) models ResourceNotFoundException with httpError 404 ("The specified resource wasn't found") on this operation, and productId/agreementId are ResourceId (@length 1..64, pattern ^[A-Za-z0-9_/-]+$) — i.e. a value can be well-formed and still name nothing. Recorded behavior: a well-formed but never-provisioned productId/agreementId pair is rejected with ResourceNotFoundException (HTTP 404); the recorded messages are examples, e.g. "ProductId: Request references a resource which does not exist." and "AgreementId: Request references a resource which does not exist." The requirement is the 404 / ResourceNotFoundException rejection, not that text. Because this existence check runs before the handler's own field checks, it is also the positive control every negative check of this operation depends on.
Emulator: the call succeeds with HTTP 200 and mints a resource — e.g. {'agreementId': 'agr-786ab14210cf', 'deploymentParameterId': 'dp-0000000000000001', 'resourceArn': 'arn:aws:aws-marketplace:us-east-1:000000000000:deployment-parameter/dp-0000000000000001', 'tags': {}} — for a productId and agreementId that were never provisioned. The handler goes straight from the clientToken/idempotency lookup to the by_name index and inserts a new record; there is no entitlement or agreement lookup anywhere in it, and no code path constructs ResourceNotFoundException for this operation. The same 200 is returned when the request also carries an over-limit tags map (51 entries, max 50) or an over-limit secretString, so those rejections are unreachable too.
Why: a client that uses PutDeploymentParameter to seed Quick Launch fulfillment gets a success for an agreement it has no entitlement to. Code that relies on the 404 to discover "this buyer is not entitled yet" instead proceeds as if the secret were stored against a real agreement, and the emulator accumulates deployment parameters for ids that do not exist. Every negative test of this operation also silently loses its control.
Fix: PutDeploymentParameter's handler/validation in services/service-com-amazonaws-marketplacedeployment-awsmpdeploymentparametersservice/src/ops/put_deployment_parameter.rs (handle(), the None arm beginning at the by_name lookup) plus the backing store in src/state.rs: the operation needs a product/agreement existence step that answers ResourceNotFoundException (404) before any record is created, and the handler's own constraint checks (tags max 50, secretString max 15000) must be ordered relative to it as AWS orders them.
Traces: marketplace-deployment.put-deployment-parameter-catalog-validation-rejected, marketplace-deployment.put-deployment-parameter-name-pattern-violation-rejected, marketplace-deployment.put-deployment-parameter-secret-string-too-long-rejected, marketplace-deployment.put-deployment-parameter-tags-exceed-max-rejected (all four fail on their first/positive-control call, which the emulator answers 200), and the second phase of marketplace-deployment.put-deployment-parameter-nonexistent-agreement-not-found.

Cause 2 of 2: the ValidationException message for a pattern violation renders the Smithy-anchored regex instead of AWS's unanchored pattern text.
AWS: catalog is Catalog (@length 1..64, @pattern ^[a-zA-Z_-]+$) and a violating value is rejected with ValidationException (Smithy: httpError 400). AWS's validation message is built from the request and names the member and its constraint, so the rule is known: "1 validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern without anchors>". Recorded: catalog='Not-A-Real-Catalog!' -> "... Member must satisfy regular expression pattern: [a-zA-Z_-]+".
Emulator: the code and status are right (ValidationException/400) but the message reproduces the model's anchored form verbatim: "1 validation error detected: Value 'Not-A-Real-Catalog!' at 'catalog' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[a-zA-Z_-]+$" — the ^ and $ are AWS-model syntax, not part of the pattern AWS reports to clients. This affects every @pattern-constrained member of this service (catalog, productId, agreementId, deploymentParameter.name, clientToken, tag keys/values), not just catalog.
Why: clients and test harnesses that assert on, log, or surface the documented validation text see a pattern they never sent and cannot match AWS's wording; the rendered constraint is also misleading as documentation, since ^/$ are not part of the accepted character class.
Fix: the shared constraint-validation message renderer used by this service's request-validation layer (the restJson1 validate step that produces the "1 validation error detected" envelope) — strip the leading ^ and trailing $ from a @pattern before interpolating it into the message.
Traces: marketplace-deployment.put-deployment-parameter-nonexistent-agreement-not-found (control-phase assertion on the catalog pattern message).

## Evidence
Cause 1 — expected: HTTP 404 / ResourceNotFoundException for a never-provisioned productId+agreementId. Actual: HTTP 200 with a newly minted resource.
  put-deployment-parameter-catalog-validation-rejected: AssertionError: expected the call to be rejected, but it succeeded: {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'agreementId': 'agr-786ab14210cf', 'deploymentParameterId': 'dp-0000000000000001', 'resourceArn': 'arn:aws:aws-marketplace:us-east-1:000000000000:deployment-parameter/dp-0000000000000001', 'tags': {}}
  put-deployment-parameter-name-pattern-violation-rejected: same, HTTP 200 for a pattern-valid name on a never-provisioned agreement.
  put-deployment-parameter-secret-string-too-long-rejected: same, HTTP 200 on the control call.
  put-deployment-parameter-tags-exceed-max-rejected: same, HTTP 200 and the response echoes 'tags': {'one-tag': 'under-the-limit'}.
Handler evidence: src/ops/put_deployment_parameter.rs handle() contains no product/agreement lookup; its None arm inserts a DeploymentParameterRecord directly (lines ~250-290) and the only rejections it can produce are ConflictException (client-token reuse), ServiceQuotaExceededException (store capacity), ValidationException (tag merge) and InternalServerException.

Cause 2 — expected message (rule: AWS interpolates the unanchored pattern): "1 validation error detected: Value 'Not-A-Real-Catalog!' at 'catalog' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z_-]+". Actual: "...regular expression pattern: ^[a-zA-Z_-]+$". Error code and status matched (ValidationException, 400).
