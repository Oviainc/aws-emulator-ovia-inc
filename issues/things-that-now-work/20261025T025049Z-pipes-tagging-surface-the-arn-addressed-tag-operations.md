# Pipes tagging surface: the ARN-addressed tag operations use the name-interpolated not-found sentence, report tag constraint violations as ValidationException instead of BadRequestException, and never enforce the tag character set

> _Note: this issue was identified against the code base at commit `8e40a1008c33b06d6b244a457efc673d78e6bf69`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
This bundle has 3 causes; all three must be closed before submitting. All three are fidelity defects of the now-implemented pipes tagging surface (TagResource/UntagResource/ListTagsForResource), grounded in failing checks of this run that no filed issue carries. Related, not covering: the open 20261023T235727Z-pipes-control-plane-cross-resource-createpipe-validation-is.md recorded these operations answering the non-modeled NotImplemented (its Cause 6) and the stub issues 20261023T235727Z-pipes-tagresource-stub.md / -listtagsforresource-stub.md are marked fixed — the operations now answer, and these are the divergences that survived. The calls are no longer refused with NotImplemented, so this is not a reopen of those stubs: each cause below is a distinct wrong answer from a working handler.

Cause 1 of 3: NotFoundException for the ARN-addressed tagging operations carries the pipe-name sentence instead of the fixed, resource-agnostic one AWS returns.
AWS: Smithy — TagResource, UntagResource and ListTagsForResource each model NotFoundException (HTTP 404, member message, doc 'An entity that you specified does not exist.'); all three are addressed by resourceArn (PipeArn), not by Name. Recorded behavior only for the message: across five independent blessed checks covering all three operations, the 404 message is the fixed constant 'Resource was not found' — it does NOT interpolate the pipe name or the ARN. The rule is therefore 'these ARN-addressed tagging operations return a constant, resource-agnostic sentence', which is what distinguishes them from the name-addressed control-plane operations (DescribePipe/StartPipe/StopPipe/DeletePipe), whose recorded message is 'Pipe <name> does not exist.' (the template the companion control-plane issue requires). Hypothesis: the tagging surface is served by the generic resource-tagging layer in front of Pipes, which has no pipe name to interpolate.
Emulator: all three answer 404/NotFoundException — the code and status are right — with 'Pipe <name> does not exist.', e.g. "expected message 'Resource was not found', got 'Pipe sim2real-behav-ghost-215989d40887 does not exist.'". services/service-com-amazonaws-pipes-pipes/src/state.rs:187-198 has ONE constructor, pipe_not_found(), whose message is 'Pipe {pipe} does not exist.', and it is fed pipe_name_in_arn(resource_arn) from the tagging handlers (see src/ops/tag_resource.rs:182-186, and the same path in untag_resource.rs / list_tags_for_resource.rs).
Why: a client or operator that distinguishes the two 404 shapes (asserting on the documented sentence, or parsing a log line) is told the emulator resolved a pipe name where AWS resolved none, and the emulator additionally echoes the caller's ARN tail into a message AWS keeps opaque.
Fix: the tagging handlers in services/service-com-amazonaws-pipes-pipes — give the ARN-addressed tagging operations their own not-found construction ('Resource was not found'), and keep state::pipe_not_found() for the name-addressed control-plane operations.
Traces: pipes.list-tags-for-nonexistent-pipe-not-found, pipes.list-tags-for-resource-nonexistent-pipe-not-found, pipes.tag-resource-nonexistent-pipe-not-found, pipes.untag-resource-nonexistent-pipe-not-found, pipes.tag-operations-on-deleted-pipe-rejected.

Cause 2 of 3: a tag key over the 128-character bound is refused with the modeled ValidationException where AWS answers BadRequestException.
AWS: Smithy — TagKey is @length(min 1, max 128) (the TagMap key member and TagKeyList member both target it); TagResource and UntagResource model only InternalException (500), NotFoundException (404) and ValidationException (400) — BadRequestException is NOT in either model. Recorded behavior: real AWS refuses an oversized tag key on both operations with HTTP 400 and error code BadRequestException, carrying the standard validation-framework body built from the request and the violated constraint — '{"message": "1 validation error detected: Value \'{<key>=<value>}\' at \'addedTags\' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]"}' for TagResource, and the same form at 'removedTagKeys' with 'Member must satisfy constraint: [...]' for UntagResource. Both checks state this explicitly ('empirically real AWS surfaces this as BadRequestException, not the modeled ValidationException'). The requirement is the 400 status, the BadRequestException code, and that message RULE (the operation's internal member name plus the violated bound); the recorded literal is an example.
Emulator: code 'ValidationException' for both — 'AssertionError: expected a validation-style rejection, got ClientError code \'ValidationException\'' and 'AssertionError: code=\'ValidationException\''. The effect-absence legs pass (nothing is persisted), so only the classification diverges: src/ops/tag_resource.rs:173-180 maps every state::tag_violation() to TagResourceErrorModeled::ValidationException via state::tag_violation_error(), and untag_resource.rs does the same.
Why: SDK error handling branches on the error code. A client that catches BadRequestException to report a malformed tag back to its user sees an unexpected ValidationException and falls through to its generic/unknown-error path, and a test written against AWS fails against the emulator for a request both services refuse.
Fix: the tag-key/tag-value constraint branch of the pipes TagResource and UntagResource handlers (and the shared construction in state.rs) — answer HTTP 400 with error code BadRequestException and the validation-framework message built from the offending member ('addedTags' / 'removedTagKeys') and the violated TagKey bound.
Traces: pipes.tag-resource-invalid-key-rejected, pipes.untag-resource-malformed-key-validation-rejected.

Cause 3 of 3: a tag VALUE outside the allowed character set is accepted and persisted, where AWS refuses the call.
AWS: Smithy — TagValue is @length(min 0, max 256) and sensitive; the character set is not modeled, so recorded behavior only: AWS refuses a tag value containing a character outside letters, numbers, spaces and _ . : / = + - @ with HTTP 400, error code BadRequestException and the documented sentence 'Tags can only contain letters, numbers, spaces, and the following special characters: _ . : / = + - @'. That sentence is a fixed, documented rule (not built from the request), so it is a requirement here. Multi-byte LETTERS are allowed and must still round-trip byte-identically (the same check proves that leg with CJK/accented Latin plus the allowed punctuation).
Emulator: TagResource(resourceArn=<pipe arn>, tags={'emoji-tag': '\U0001F680'}) returns HTTP 200 with an empty body and the tag is stored — 'AssertionError: expected the call to be rejected, but it SUCCEEDED and returned {... \'HTTPStatusCode\': 200 ...}'. services/service-com-amazonaws-pipes-pipes/src/state.rs:107-134 (tag_violation) checks only TagKey/TagValue @length and the reserved 'aws:' key prefix; there is no character-set rule for either key or value, so every code point within the length bound is accepted.
Why: this is a silent success the client pays for later — tagging code that the emulator validates clean is refused by real AWS on the first deploy, which is exactly the class of bug the emulator exists to catch. Cost-allocation and policy tooling also ends up reading tag values AWS would never have stored.
Fix: extend crate::state::tag_violation in services/service-com-amazonaws-pipes-pipes/src/state.rs with the documented tag character set (so the CreatePipe tag path and TagResource refuse identically) and answer it as Cause 2 requires (400 BadRequestException) with the documented sentence.
Traces: pipes.tag-value-unicode-round-trip.
