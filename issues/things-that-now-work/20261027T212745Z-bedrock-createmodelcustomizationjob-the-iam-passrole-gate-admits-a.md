# bedrock CreateModelCustomizationJob: the iam:PassRole gate admits a same-account role AWS refuses, and a modelled foundation-model ARN is refused 404 ResourceNotFoundException

> _Note: this issue was identified against the code base at commit `c0eb4295fc6918b9011f996ea325c28045b54b65`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateModelCustomizationJob

## Description
TWO CAUSES reached through the `bedrock` behavioral checks, both in the CreateModelCustomizationJob handler. Each is a distinct contract a fixer must see answer correctly before submitting. Smithy model read: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json (smithy_query query="operation" operation="CreateModelCustomizationJob").

Cause 1 of 2 — the model-customization pass-role gate is OVER-PERMISSIVE: a same-account service role is accepted and a job plus a custom model are minted, where AWS refuses the call outright.
AWS: Smithy CreateModelCustomizationJob -> POST /model-customization-jobs, success 201 {jobArn}, modelled errors AccessDeniedException(403), ConflictException(400), ResourceNotFoundException(404), ServiceQuotaExceededException(400), ThrottlingException(429), TooManyTagsException(400), ValidationException(400); `roleArn` is documented as the role Bedrock assumes and "the caller of this API must have the iam:PassRole permission". Recorded behavior only for the decision itself: in the recorded account, CreateModelCustomizationJob carrying a well-formed, SAME-ACCOUNT role whose trust policy names bedrock.amazonaws.com (scoped by aws:SourceAccount and an aws:SourceArn of arn:aws:bedrock:<region>:<account>:model-customization-job/*) is refused 403 AccessDeniedException whose message contains the fixed text "Cross-account pass role" — an account-level gate on model customization that fires before any training is billed — and the refusal writes nothing: ListModelCustomizationJobs(nameContains=<jobName>) and ListCustomModels(nameContains=<customModelName>) both stay empty. Message rule: the fixed text is "Cross-account pass role" (the emulator already words it that way elsewhere, via crate::state::customization_pass_role_denial); any role ARN or account id in the message is a value taken from the request, not part of the template.
Emulator: the call SUCCEEDS with 201 and a jobArn. crate::state::customization_pass_role_denial only yields a denial when the roleArn names a role of ANOTHER account, so a same-account role passes the gate, the handler goes on to mint a ModelCustomizationJobRecord with status InProgress and a completed_due_at, registers the job name and the pending custom model, and the subsequent ListModelCustomizationJobs/ListCustomModels therefore do NOT come back empty. The check reads (code, message) == (None, None) because no ClientError was raised at all.
Why: a caller that AWS refuses 403 is told its customization job started. Fine-tuning is a billed, long-running job, so a client (or a CI pipeline, or a CloudFormation/Step Functions workflow) built against the emulator believes model customization is permitted in the account, waits on a job id AWS would never have minted, and the whole authorization class it must handle (403 AccessDeniedException on pass-role) is never exercised. It also leaves state behind — a job name and a reserved custom-model name — that AWS would not have created, so later Conflict/quota behavior diverges too.
Fix: the pass-role decision consulted by the CreateModelCustomizationJob handler — crate::state::customization_pass_role_denial and its use at the top of handle (see Traces for file/line) — must reproduce the account-level model-customization denial, not merely a cross-account-ARN test, and must stay a write-nothing refusal.
Traces: bedrock.e2e-fine-tune-deploy-invoke-teardown (AssertionError: (None, None) at the `assert code == "AccessDeniedException"` leg). Code: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_customization_job.rs lines 209-224 (the gate) and 417-484 (the job it mints when the gate admits).

Cause 2 of 2 — a `baseModelIdentifier` in the modelled foundation-model ARN form is refused 404 ResourceNotFoundException with the emulator's own wording, so the request never reaches the decision AWS makes.
AWS: Smithy CreateModelCustomizationJob.baseModelIdentifier is required, @length 1..2048, and its @pattern explicitly admits the foundation-model ARN alternative `arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}::foundation-model/[a-z0-9-]{1,63}[.][a-z0-9-]{1,63}([:][a-z0-9-]{1,63}){0,2}` as well as the bare `vendor.model` id and a custom-model ARN. Recorded behavior only: a request whose baseModelIdentifier is `arn:aws:bedrock:<region>::foundation-model/amazon.titan-text-express-v1` is NOT reported as an absent resource — the recorded answer is the 403 AccessDeniedException "Cross-account pass role" of cause 1, i.e. AWS settles the pass-role question for this operation and never answers 404 for that identifier.
Emulator: 404 ResourceNotFoundException with the message "baseModelIdentifier arn:aws:bedrock:us-west-2::foundation-model/amazon.titan-text-express-v1 does not name a base model in this account in us-west-2". That message is the emulator's own invention (fixed text "does not name a base model in this account in" plus the region) and it echoes the caller-supplied identifier verbatim; AWS's modelled ResourceNotFoundException is documented as "The specified resource Amazon Resource Name (ARN) was not found." and is not the answer to this request at all. The refusal is raised by the catalog lookup in handle: `store.foundation_models.qualified_model(crate::state::base_model_id_of(&input.base_model_identifier))` misses and the custom-model fallback misses, so the handler reports the identifier absent. Hypothesis: the emulator's published foundation-model catalog does not carry amazon.titan-text-express-v1 (the sibling check that picks its base model from ListFoundationModels(byOutputModality=TEXT) + customizationsSupported=FINE_TUNING gets past this step), and/or base_model_id_of does not reduce the `::foundation-model/<id>` ARN form to the catalogued id.
Why: a client that names a base model by the ARN form the model documents is told the model does not exist in its account — a terminal 404 it cannot work around, with a wrong status (404 vs 403) and a wrong error code (ResourceNotFoundException vs AccessDeniedException), so an SDK's retry/handling branch for authorization failures is never taken. Because the 404 is raised before the authorization decision, it also masks cause 1 for this identifier: fixing only cause 1 will leave this check failing, and fixing only cause 2 will leave it failing with the over-permissive 201.
Fix: the base-model resolution used by the CreateModelCustomizationJob handler — the published foundation-model catalog in crate::state (foundation_models / qualified_model) and crate::state::base_model_id_of's handling of the `::foundation-model/<id>` ARN alternative.
