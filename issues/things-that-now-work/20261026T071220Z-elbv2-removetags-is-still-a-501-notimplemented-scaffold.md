# ELBv2 RemoveTags is still a 501 NotImplemented scaffold stub: tags can never be cleared and the TargetGroupNotFound refusal is unreachable

> _Note: this issue was identified against the code base at commit `71cff0481dbaf9b41262283aed7350a64aff149f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RemoveTags

## Description
ONE root cause (Cause 1 of 1): the ELBv2 `RemoveTags` handler is an unimplemented scaffold that answers HTTP 501 `NotImplemented` for every request, so neither the modeled 200 success nor any of its modeled 400 refusals can ever be observed. Sibling operations of the same family are now implemented — AddTags (fixed issue 20261025T135132Z-elbv2-addtags-answers-501-notimplemented-instead-of-the.md) and DescribeTags (fixed issue 20261023T135552Z-cloudtrail-elbv2-elbv2-describetags-answers-notimplemented.md) both succeed in these replays — which is exactly why RemoveTags is now the only remaining divergence in two checks that previously failed earlier on AddTags.

NOT a reopen: no fixed issue ever claimed RemoveTags. The fixed AddTags issue states explicitly that it covers AddTags only. Overlap note: the OPEN issue 20261023T205437Z-elbv2-ten-control-plane-operation-families-answer-501.md names "AddTags / RemoveTags" together in its Cause 1 and lists these two check ids, but its Issue-Key for that cause is `elbv2|AddTags|NotImplemented` — the key that is now FIXED — so a fixer can legitimately close that cause on the strength of AddTags alone and leave RemoveTags refused. The replay key for these two checks (`elbv2|RemoveTags|NotImplemented`) is carried by no open issue, which is why the suite did not mark them owned, and why this is filed as its own work item.

Cause 1 of 1 — RemoveTags answers 501 NotImplemented for every input.
AWS: Smithy `RemoveTags(ResourceArns: ResourceArns required, TagKeys: TagKeys required) -> RemoveTagsOutput` with SUCCESS status 200 and an empty output body. Modeled errors, all client/HTTP 400 with awsQuery codes: ListenerNotFoundException (`ListenerNotFound`), LoadBalancerNotFoundException (`LoadBalancerNotFound`), RuleNotFoundException (`RuleNotFound`), TargetGroupNotFoundException (`TargetGroupNotFound`), TooManyTagsException (`TooManyTags`), TrustStoreNotFoundException (`TrustStoreNotFound`). Model doc for the operation: "Removes the specified tags from the specified Elastic Load Balancing resources..."; for TargetGroupNotFoundException: "The specified target group does not exist." Two behaviors follow. (a) Success path: removing the named TagKeys leaves every other key on the resource untouched, and removing the LAST key converges on the same representation as a resource that was never tagged — DescribeTags returns a TagDescriptions entry for the ARN with `Tags: []`, not a missing entry and not a residual empty-value tag. (b) Refusal path: a ResourceArns entry whose resource does not exist is refused with HTTP 400 / Error.Code `TargetGroupNotFound` for a targetgroup-shaped ARN, and the rejected call must not mutate any tag on the real resources in the same request. The message template for that error class, as the recording pins it, is the fixed text `Target groups '<arn>' not found` — `Target groups ` and ` not found` are fixed, and the quoted ARN is taken verbatim from the request's ResourceArns (the recorded run's ARN value itself is not part of the template).
Emulator: every RemoveTags call returns HTTP 501 with Error.Code `NotImplemented` and message "operation RemoveTags is scaffolded but not implemented in this emulator". Both checks die on the first remove_tags call: botocore raises `ClientError: An error occurred (NotImplemented) when calling the RemoveTags operation`. The nonexistent-ARN assertion (`expected TargetGroupNotFound, got ...`) and the cleared-tags convergence assertion are therefore never reached.
Why: tags can be written but never withdrawn on any ELBv2 resource, so cost-allocation tags, tag-based discovery and reconciliation-after-delete workflows are one-way. A client cannot distinguish "that target group does not exist" from "this service is unavailable", and 501 is not a client error, so SDK retry logic treats a terminal bad request as a retryable server fault.
Fix: the RemoveTags handler and the ELBv2 tag store it must mutate — services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/ops/remove_tags.rs, whose `handle` returns `Err(crate::scaffolded::Scaffolded::not_implemented("RemoveTags"))` (line 160) under the SCAFFOLDED marker at line 4. It must resolve each ResourceArn to a live resource, raise the matching modeled *NotFoundException (TargetGroupNotFoundException for a targetgroup ARN with nothing behind it) instead of the scaffold channel, apply the removal atomically only when every ARN resolves, and leave a fully-cleared resource reporting `Tags: []` through DescribeTags.
Traces: elbv2.remove-tags-then-verify-and-reject-missing-resource (success path + TargetGroupNotFound refusal + message text), elbv2.create-load-balancer-empty-vs-absent-tags-preserved (never-tagged vs tagged-then-cleared must be indistinguishable).
