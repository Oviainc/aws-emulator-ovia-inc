# cloudfront__lambda: a Deployed distribution's edge never answers, so AllowedMethods/CachedMethods are not enforced at the edge and the check hangs to the 60 s cap

> _Note: this issue was identified against the code base at commit `35f0669fbed72946ad7349f4657cbc8fac9f7c2b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDistribution

## Description
One root cause.

=== Cause 1 of 1: the CloudFront edge data plane serves nothing, so a cache behavior's AllowedMethods/CachedMethods have no observable effect ===
AWS: AllowedMethods and CachedMethods on a cache behavior are enforced BY CLOUDFRONT at the edge, not by the origin. A viewer POST to a behavior whose AllowedMethods is GET,HEAD is refused by CloudFront itself with 403 and the response header X-Cache: "Error from cloudfront"; the request never reaches the origin (the origin's own invocation counter stays at zero), while the identical POST sent directly to the origin (a Lambda function URL, SigV4-signed) succeeds with 200. A method that is allowed but absent from CachedMethods (OPTIONS) is forwarded to the origin on every request and never answered from cache, while repeated GETs on a caching cache policy eventually get X-Cache: "Hit from cloudfront". Recorded behavior only for the X-Cache header values and the 403 body; the requirement is that the distribution's own hostname answers at all and that CloudFront — not the origin — produces the refusal.
Emulator: the check never completes: verdict [mismatch], "Check timed out after 60.0s". The distribution is created and reaches Deployed through the control plane, but requests to the distribution's own domain name never produce an HTTP response, so the check's bounded poll for a first 200 through the edge (and every subsequent POST/OPTIONS/GET beat) never terminates inside the harness budget. Nothing about AllowedMethods/CachedMethods enforcement is observable: the control plane echoes both fields back verbatim while no edge enforces them.
Why: a client that relies on CloudFront to reject disallowed methods at the edge gets no enforcement boundary at all — in this emulator the only thing that could refuse a POST is the origin, which accepts it, so a configuration AWS treats as a security control (GET/HEAD-only behavior in front of a writable Lambda function URL) silently becomes wide open. Equally, nothing distinguishes a cached from an uncached method, so cache-keying and origin-offload behavior cannot be relied on.
Fix: the distribution data plane — the edge listener that resolves a distribution domain name to its DistributionConfig, selects the matching cache behavior by path pattern, enforces AllowedMethods (403 + X-Cache: Error from cloudfront, no origin fetch), applies CachedMethods/cache-policy to decide cache vs. forward, and only then fetches from the configured origin (here a Lambda function URL fronted by an OAC). This belongs in the cloudfront crate's data-plane/edge component rather than in any single control-plane op handler.
Related open issues describe the same missing edge from other service tuples and do not carry this check's replay key: 20261024T182555Z-cloudfront-cloudwatch-no-edge-traffic-is-ever-served.md, 20261024T182555Z-cloudfront-s3-distributions-over-s3-origins-serve-nothing.md, 20261024T102105Z-cloudfront-kms-s3-a-cloudfront-distribution-with-an-oac-over-an.md. This check is the only one in the suite that grades method enforcement at the edge plus the Lambda-function-URL origin path.

The check marks this class of exhaustion with DATAPLANE_UNIMPLEMENTED precisely so it cannot be read as an environment problem: the hostname polled is the emulator's own.

## Steps to Reproduce
1. Create a Lambda function with a function URL that echoes the request method and a per-request nonce, fronted by a CloudFront OAC.
2. cf.create_distribution with a default cache behavior over that function-URL origin using AllowedMethods={GET,HEAD} and a second behavior /opt/* with AllowedMethods={GET,HEAD,OPTIONS}, CachedMethods={GET,HEAD} and a caching cache policy.
3. Poll cf.get_distribution until Status == Deployed, then issue a plain HTTPS GET to the distribution's DomainName -> observe no HTTP response at all (never 200).
4. Issue a POST to the same hostname -> expect 403 with X-Cache: "Error from cloudfront" and no origin invocation; observe no response.
5. Replay cloudfront__lambda.deep-cloudfront-2-cf-edge-enforce-allowed-methods-post-rejected to confirm.
