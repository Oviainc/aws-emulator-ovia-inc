# mediapackagev2 error-message rule, tagging/policy negative paths, ETag concurrency and the ingest/egress data plane all diverge (6 causes)

> _Note: this issue was identified against the code base at commit `b8bbb064bfede5b5be6782e6b85c8258ff782b33`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetChannelGroup

## Description
Beyond input validation, the mediapackagev2 emulator diverges in how it WORDS its rejections, in which operations answer a modeled rejection at all, in whether concurrent conditional updates resolve to one winner, and in whether the ingest/egress URLs it hands out are served. 6 causes.

Cause 1 of 6: not-found and conflict messages are built by interpolating the caller's resource identifiers (and a child count), where AWS returns a fixed per-resource-type sentence.
AWS: Smithy: ResourceNotFoundException (httpError 404) binds Message and ResourceTypeNotFound; ConflictException (httpError 409) binds Message and ConflictExceptionType (enum values RESOURCE_IN_USE, RESOURCE_ALREADY_EXISTS, IDEMPOTENT_PARAMETER_MISMATCH, CONFLICTING_OPERATION). DeleteChannel declares ConflictException and NOT ResourceNotFoundException; CreateChannel declares both. Recorded behavior only for the text, but the RULE the recordings establish is that the message is a fixed sentence per resource type and per rejection class, containing none of the caller's identifiers: channel group — "MediaPackage can't process your request because we can't find your channel group. Verify your channel group name or add a channel group and then try again"; channel — "MediaPackage can't process your request because we can't find your channel. Verify your channel name or add a channel and then try again"; origin endpoint — "MediaPackage can't process your request because we can't find your origin endpoint. Verify your origin endpoint name or add an origin endpoint and then try again"; duplicate create — "MediaPackage can't create the resource you requested because a resource with that name already exists. Verify the name of the resource and then try again"; delete-with-children at channel-group scope — 'The channel group you tried to delete has channels attached to it. If you want to delete this channel group, you must first delete the channels attached to it'; delete-with-children at channel scope — 'The channel you tried to delete has origin endpoints attached to it. If you want to delete this channel, you must first delete the origin endpoints attached to it'.
Emulator: the statuses (404/409) and the discriminators (ResourceTypeNotFound 'CHANNEL_GROUP', ConflictExceptionType 'RESOURCE_ALREADY_EXISTS'/'RESOURCE_IN_USE') are right, but every message is formatted from the request — 'Channel group <name> not found', 'Channel <name> not found in channel group <group>', 'Origin endpoint <ep> not found on channel <ch> in channel group <cg>', 'Channel group <name> already exists', 'Channel <name> already exists in channel group <group>', 'Channel group <name> still has 1 channel(s); delete them first', 'Channel <name> still has 1 origin endpoint(s); delete them first'.
Why: the divergence is in the rule producing the message, not merely the recorded wording: AWS's text is request-independent and the emulator's is request-derived. Clients and conformance suites that match MediaPackage's documented sentences do not match, cascade-delete retry logic keyed on the attached-children wording does not fire, and log pipelines built on the assumption that the service does not echo customer resource names back in error bodies now see them.
Relation to an already-open issue: 20261022T021034Z-mediapackagev2-error-bodies-diverge-empty-validationexception-and-identifier.md (filed from the WIRE corpus) describes the same root cause for GetChannelGroup / GetChannel / GetOriginEndpoint / CreateChannel / CreateChannelGroup / DeleteChannelGroup. It does NOT carry these behavioral check ids, and it does not cover the two scopes these checks add: the CreateChannel duplicate-name conflict message and the DeleteChannel (channel-scope) attached-children conflict message. Fix them together.
Fix: the mediapackagev2 not-found and conflict error construction (shared error builders used by the Get*/Create*/Delete* handlers) — emit the service's fixed per-resource, per-class sentence instead of formatting the requested identifiers and child counts into it.
Traces: mediapackagev2.get-channel-group-nonexistent-not-found, mediapackagev2.channel-creation-populates-ingest-endpoints, mediapackagev2.get-origin-endpoint-not-found-after-delete, mediapackagev2.create-channel-missing-channel-group-not-found, mediapackagev2.create-channel-nonexistent-channel-group-not-found, mediapackagev2.channel-group-duplicate-name-rejected, mediapackagev2.concurrent-channel-group-create-race, mediapackagev2.create-channel-duplicate-name-conflict-rejected, mediapackagev2.delete-channel-group-in-use-rejected, mediapackagev2.delete-channel-conflict-when-origin-endpoint-exists, mediapackagev2.hierarchical-delete-blocked-by-dependents-rejected.

Cause 2 of 6: the tagging operations answer 501 NotImplemented for a malformed or non-existent ResourceArn instead of the modeled 4xx rejection.
AWS: Smithy: ListTagsForResource (GET /tags/{ResourceArn}) and TagResource (POST /tags/{ResourceArn}, success code 204) bind ResourceArn -> TagArn as a required @httpLabel and declare ValidationException (400); ValidationExceptionType includes INVALID_ARN. Recorded behavior: a syntactically non-ARN ResourceArn is refused by the tagging framework with code BadRequestException and message 'Invalid input resource arn: bad syntax', and a well-formed ARN naming a resource that does not exist is refused with NotFoundException — in both cases a 4xx client error, never a server fault, and the call resolves no tag data.
Emulator: both paths answer error code 'NotImplemented' (HTTP 501, 'operation ListTagsForResource / TagResource is scaffolded but not implemented in this emulator'), so neither the ARN-syntax class nor the unknown-resource class exists.
Why: a 501 is a retryable server-fault class, so a caller that passed a bad ARN retries forever instead of being told the ARN is wrong, and tag-propagation tooling cannot distinguish 'bad ARN' from 'resource gone'. (The bare 'operation is a scaffold stub' gap for list_tags_for_resource.rs and tag_resource.rs is filed separately by the suite; these two checks were not attributed to those clusters, and the requirement recorded here is the ARN-validation ordering and error class the implemented operations must carry.)
Fix: the ListTagsForResource / TagResource handlers in mediapackagev2 — parse and validate ResourceArn before resource lookup, answering BadRequestException (400) for a syntactically invalid ARN and NotFoundException for a well-formed ARN with no such resource.
Traces: mediapackagev2.list-tags-for-resource-invalid-arn-rejected, mediapackagev2.tag-resource-nonexistent-resource-arn-rejected.

Cause 3 of 6: the resource-policy operations answer 501 NotImplemented where AWS answers a modeled rejection for a malformed policy or a missing parent resource.
AWS: Smithy: PutChannelPolicy (PUT /channelGroup/{ChannelGroupName}/channel/{ChannelName}/policy) requires Policy -> PolicyText (@length max 6144) and declares ValidationException (400), ResourceNotFoundException (404), ConflictException (409), AccessDeniedException (403); PutOriginEndpointPolicy is modeled the same way at endpoint scope. ValidationExceptionType includes INVALID_POLICY. So a Policy that is not valid JSON / not a valid policy document is a 400 ValidationException, and a PutChannelPolicy naming a channel that does not exist is a 404 ResourceNotFoundException (with the fixed channel sentence from Cause 1).
Emulator: all three paths answer error code 'NotImplemented' (HTTP 501), so a malformed policy is indistinguishable from a missing resource and from a server fault.
Why: resource policies are the gate on MediaPackage egress and harvesting; a client cannot tell a rejected policy document from an absent channel, and a 501 invites retries of a permanently invalid request. (The scaffold-stub issues for put_channel_policy.rs and put_origin_endpoint_policy.rs cover standing the operations up; these checks, which the suite did not attribute to those clusters, record the negative-path semantics the implementations must have.)
Fix: the PutChannelPolicy / PutOriginEndpointPolicy handlers — validate the policy document (ValidationException + ValidationExceptionType INVALID_POLICY) and resolve the parent channel/endpoint first (ResourceNotFoundException, fixed message) before storing anything.
Traces: mediapackagev2.put-channel-policy-invalid-json-rejected, mediapackagev2.put-channel-policy-resource-not-found-missing-channel, mediapackagev2.put-origin-endpoint-policy-invalid-policy-rejected.

Cause 4 of 6: concurrent conditional updates do not resolve to exactly one winner — no racer succeeds.
AWS: Smithy: UpdateChannel and UpdateChannelGroup take the conditional entity tag via httpHeader x-amzn-update-if-match (ETag -> EntityTag, @length 1..256, @pattern ^[\S]+$), return ETag, and declare ConflictException (409); ConflictExceptionType includes CONFLICTING_OPERATION. That is the optimistic-concurrency contract: when N callers read the same ETag and update concurrently, exactly one update commits (200, new ETag) and the others are refused (the stale-ETag/conflict class) — never zero.
Emulator: both racers of a concurrent UpdateChannel receive 'NotImplemented', and the concurrent UpdateChannelGroup race produces an empty winner set, so the single-winner invariant holds trivially-falsely (zero winners) and no conditional-update outcome is observable at all.
Why: a client built on x-amzn-update-if-match cannot make progress: a correct implementation guarantees forward progress for one racer, while here every concurrent writer fails and a 501 makes every one of them retry. Nothing in the emulator exercises or protects the conditional-update path.
Fix: the UpdateChannel / UpdateChannelGroup handlers and the mediapackagev2 state's per-resource ETag/version — evaluate x-amzn-update-if-match against committed state under a single serialization point so one concurrent update commits and the rest get the conflict class. (Related but distinct: the open issue 20261022T021034Z-mediapackagev2-update-operations-do-not-persist-mutations-so.md covers read-after-write and ETag continuity for a SINGLE update; this cause is the concurrent-racer outcome, and the scaffold-stub issues for update_channel.rs / update_channel_group.rs cover merely standing the operations up.)
Traces: mediapackagev2.update-channel-etag-optimistic-lock-concurrency, mediapackagev2.update-channel-group-concurrent-racers-single-winner.

Cause 5 of 6: the ingest and egress URLs the control plane publishes are not served — requests to them are answered by the control-plane router, which cannot resolve a service and returns 404.
AWS: Smithy: CreateChannel returns IngestEndpoints (IngestEndpointList of Id + Url) and CreateOriginEndpoint returns HlsManifests[].Url; these are the service's data plane, plain HTTPS, with no credential ever returned for ingest. Recorded behavior: both published URLs are live TLS listeners that enforce access control. An unauthenticated PUT to an ingest Url is HTTP 403 with an 'Access denied' body (and a syntactically valid but cryptographically wrong SigV4 Authorization gets a DIFFERENT 403, a signature-mismatch denial). An anonymous GET of an origin endpoint's manifest Url before any resource policy grants mediapackagev2:GetObject is HTTP 403; once a policy grants it but before any content is ingested it is HTTP 404.
Emulator: the published hostnames resolve to the emulator, but it answers the data-plane request from its control-plane router: HTTP 404 with body {"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"} for the unauthenticated ingest PUT, and HTTP 404 for the anonymous egress manifest GET where 403 is required. So the URLs are announced as real endpoints while nothing serves them, and the authorization distinction (403 vs 404, denied vs no-content-yet) does not exist.
Why: a player or encoder driven off these URLs cannot distinguish 'not authorized' from 'no content yet' — the two states a MediaPackage client branches on. Anything validating that an endpoint's resource policy actually gates egress gets a false result, and a workflow that waits for 404-after-grant as its readiness signal sees 404 immediately and proceeds against an endpoint that denies nothing.
Fix: the mediapackagev2 data-plane listeners (ingest and egress) and the emulator's host-based request routing — route requests whose Host matches a published ingest/egress domain to a mediapackagev2 data-plane handler rather than the control-plane service resolver, and have it enforce the endpoint's resource policy: 403 (access-denied body) with no grant, 404 once granted but with no ingested content.
Traces: mediapackagev2.cmaf-ingest-native-protocol-round-trip, mediapackagev2.origin-endpoint-manifest-url-data-plane-reachable.

Cause 6 of 6: the entire harvest-job surface is unexercisable because its S3 destination setup answers 501 NotImplemented.
AWS: Smithy: CreateHarvestJob/GetHarvestJob/CancelHarvestJob/ListHarvestJobs take an S3 destination, and ValidationExceptionType carries HARVEST_JOB_S3_DESTINATION_MISSING_OR_INCOMPLETE, HARVEST_JOB_UNABLE_TO_WRITE_TO_S3_DESTINATION, HARVEST_JOB_INELIGIBLE_FOR_CANCELLATION and END_TIME_EARLIER_THAN_START_TIME — i.e. a harvest job is only accepted once a real S3 bucket grants the harvester write access. Recorded behavior: the destination bucket is prepared with S3 CreateBucket + PutBucketPolicy (+ PutBucketTagging), all of which succeed, and only then does the mediapackagev2 harvest-job lifecycle run (CreateHarvestJob -> QUEUED/IN_PROGRESS, CancelHarvestJob -> CANCELLED visible to GetHarvestJob; ListHarvestJobs filters by Status).
Emulator: the setup calls fail — 'An error occurred (NotImplemented) when calling the PutBucketTagging operation' and 'An error occurred (NotImplemented) when calling the PutBucketPolicy operation' (HTTP 501, S3 scaffold stubs) — so all three harvest-job checks abort before any mediapackagev2 call is made and the harvest-job state machine, its cancellation transition and its status filter are completely unverified.
Why: a user cannot run any MediaPackage harvesting workflow against the emulator, and the harvest-job behavior remains entirely unmeasured rather than merely wrong. NOTE for the fixer: the failing call is in the S3 service (PutBucketTagging / PutBucketPolicy), which is not stood up in this checkout, so the unblocking work is there; the open issue 20261022T012742Z-osis-pipeline-lifecycle-checks-all-blocked-s3-putbuckettagging.md reports the same S3 stub blocking a different service's checks and does not carry these mediapackagev2 check ids. Once the S3 dependency answers, re-replay these three checks — they are expected to expose mediapackagev2 harvest-job behavior that has never been exercised.
Fix: the S3 PutBucketPolicy / PutBucketTagging handlers the harvest-destination setup depends on, then the mediapackagev2 harvest-job handlers and state (job status lifecycle, CancelHarvestJob transition to CANCELLED, ListHarvestJobs Status filter, end-time-before-start-time rejection with END_TIME_EARLIER_THAN_START_TIME).
Traces: mediapackagev2.harvest-job-cancel-transitions-to-cancelled, mediapackagev2.harvest-job-end-time-before-start-time-rejected, mediapackagev2.list-harvest-jobs-status-filter.

All resource names, ARNs, hostnames, ETags and timestamps quoted are per-run values and are examples; the requirements are the HTTP statuses, the error codes, the discriminator enum values, the fixed-message rule in Cause 1, and the single-winner / data-plane-authorization invariants.
