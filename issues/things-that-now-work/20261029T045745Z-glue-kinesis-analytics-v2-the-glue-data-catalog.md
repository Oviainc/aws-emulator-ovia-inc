# glue__kinesis-analytics-v2: the Glue Data Catalog is never resolved by Studio-notebook CreateApplication, and UpdateApplication is still a 501 scaffold stub (2 causes)

> _Note: this issue was identified against the code base at commit `060392db00c5b3260ef85f15c64a4c64c2352242`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApplication

## Description
This bundle carries 2 net-new root causes, both in the Kinesis Analytics V2 (Managed Service for Apache Flink) Studio-notebook surface where it must consult Glue. Note on prior art: open issue 20261022T124043Z-glue-kinesis-analytics-v2-cross-service-glue-kinesis-analytics-v2-studio-notebook.md carries these same two check ids but its Issue-Key is `glue__kinesis-analytics-v2|CreateApplication|AmbiguousService` — that routing refusal is GONE (CreateApplication now dispatches and answers 200), so the two causes below are what the checks now hit and are not covered by it. The open wire issue 20261022T145625Z-kinesisanalyticsv2-kinesis-analytics-v2-wire-lifecycle-operations-all-answer.md describes UpdateApplication's success envelope but carries only wire fixture/step keys and attributes it to routing, not to the stub; neither of the behavioral keys below is gated by it.

Cause 1 of 2: CreateApplication accepts a Studio notebook whose CatalogConfiguration names a Glue database that does not exist.
AWS: Smithy com.amazonaws.kinesisanalyticsv2#CreateApplication takes ApplicationConfiguration.ZeppelinApplicationConfiguration.CatalogConfiguration, whose required member GlueDataCatalogConfiguration carries required DatabaseARN (@length 1..2048, @pattern ^arn:); the model documents it as "the configuration parameters for the default Amazon Glue database" used by the Studio notebook. CreateApplication models InvalidArgumentException (errorKind client, HTTP 400, member Message) — "The specified input parameter value is not valid." Recorded behavior: a CreateApplication whose DatabaseARN names a database Glue does not hold is REFUSED with HTTP 400, error code InvalidArgumentException, and message of the form "Cannot find database with name '<database-name>' in Glue Data Catalog". In that message the fixed text is "Cannot find database with name '" ... "' in Glue Data Catalog"; the single variable part is the database name parsed out of the request's DatabaseARN (the recording's own name is one filling of that template, never part of it). The refused create leaves nothing behind: DescribeApplication on the named application then answers ResourceNotFoundException "Application '<name>' does not exist." and Glue GetDatabase still answers EntityNotFoundException "Database <name> not found.".
Emulator: the create is accepted. It answers HTTP 200 with a full ApplicationDetail — ApplicationStatus READY, ApplicationVersionId 1, an ApplicationARN minted for the notebook, and a ZeppelinApplicationConfigurationDescription echoing the dangling catalog. The DatabaseARN is stored verbatim and never resolved against the Glue service's database store.
Why: a client gets a notebook that looks READY but references a catalog that does not exist, so the failure surfaces later as a broken Zeppelin session instead of at the API boundary where AWS reports it. Code that depends on CreateApplication being the validation point — provisioning that creates the database first and relies on the refusal to catch an ordering or name mistake, or negative tests asserting InvalidArgumentException — passes against the emulator and fails against AWS. The modeled InvalidArgumentException path of this operation is unreachable, and an unwanted application plus its ARN are left in state where AWS created none.
Fix: the CreateApplication handler's validation in the kinesisanalyticsv2 crate (services/service-com-amazonaws-kinesisanalyticsv2-kinesisanalytics-20180523/src/ops/create_application.rs): before any state is written, parse ApplicationConfiguration.ZeppelinApplicationConfiguration.CatalogConfiguration.GlueDataCatalogConfiguration.DatabaseARN and resolve the database name through the Glue service's catalog state, returning InvalidArgumentException at 400 with the message template above when it does not resolve, and leaving no application and no ARN behind. This needs the cross-service read path from the kinesisanalyticsv2 crate to the Glue database store.
Traces: glue__kinesis-analytics-v2.studio-notebook-naming-a-catalog-database-that-does-not-exist-rejected.

Cause 2 of 2: UpdateApplication answers 501 NotImplemented — the operation is an unimplemented scaffold stub, so no Studio-notebook update (and no re-resolution of its catalog) exists at all.
AWS: Smithy com.amazonaws.kinesisanalyticsv2#UpdateApplication answers HTTP 200 with REQUIRED output member ApplicationDetail (plus optional OperationId @length 1..64); input ApplicationName is required, CurrentApplicationVersionId is @range 1..999999999, and ApplicationConfigurationUpdate carries ZeppelinApplicationConfigurationUpdate.MonitoringConfigurationUpdate.LogLevelUpdate (required enum LogLevel). The model documents that the service "updates the ApplicationVersionId each time you update your application". Its modeled errors are CodeValidationException/InvalidApplicationConfigurationException/InvalidArgumentException/InvalidRequestException/LimitExceededException/ResourceInUseException/ResourceNotFoundException at 400 and ConcurrentModificationException at 409. 'NotImplemented' is not among them and does not exist in AWS. Recorded behavior for the specific scenario: while the notebook's Glue database is absent, even a configuration-only update (a LogLevelUpdate of WARN) is refused with HTTP 400 InvalidArgumentException and the SAME message template as Cause 1, "Cannot find database with name '<database-name>' in Glue Data Catalog" (fixed text as above; the variable part is the database name taken from the stored DatabaseARN), and the refusal is side-effect free — DescribeApplication still reports ApplicationVersionId 1 and the prior LogLevel. Once the database is re-created under the same name, the IDENTICAL update is accepted and answers 200 with ApplicationVersionId 2, and DescribeApplication then reports the new LogLevel.
Emulator: every UpdateApplication answers HTTP 501 with error code NotImplemented. The handler at services/service-com-amazonaws-kinesisanalyticsv2-kinesisanalytics-20180523/src/ops/update_application.rs:202 still returns `Err(crate::scaffolded::Scaffolded::not_implemented("UpdateApplication"))` and the file still carries the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker; the handler body binds and discards its input.
Why: an application created against the emulator can never be reconfigured, so version history, optimistic concurrency on CurrentApplicationVersionId/ConditionalToken, and the Zeppelin monitoring/catalog update paths are all unreachable. Clients see a 501 with an unmodeled error code where AWS returns either an ApplicationDetail or a modeled 4xx, so neither the success branch nor any error branch can be exercised; in particular the catalog referential rule — that a notebook whose database was dropped is stranded until the database is re-created, and that the refusal moves neither the version nor the log level — is entirely absent.
Fix: implement UpdateApplication in its own handler file (services/service-com-amazonaws-kinesisanalyticsv2-kinesisanalytics-20180523/src/ops/update_application.rs) and delete the SCAFFOLDED marker: apply the ApplicationConfigurationUpdate to the stored application, increment ApplicationVersionId and set ApplicationVersionUpdatedFrom, return the required ApplicationDetail at 200; and gate the whole update on re-resolving the stored GlueDataCatalogConfiguration.DatabaseARN through the Glue database store (the same resolution Cause 1 adds), refusing with InvalidArgumentException at 400 and leaving version and configuration untouched when it does not resolve.
Traces: glue__kinesis-analytics-v2.dropping-the-catalog-database-strands-the-notebook-until-it-is-recreated.
