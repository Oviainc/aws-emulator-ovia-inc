# CreateDeployment's ValidationException message diverges from AWS: wrong report wording for a disallowed specification, and the deploymentName pattern rule is never applied

> _Note: this issue was identified against the code base at commit `dc7d1cb059ddc05800728693f0165ec8a2a1b13e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
CreateDeployment on a real catalog workload/pattern with a specifications map the pattern does not define IS refused with HTTP 400 ValidationException, so the status and the error code are right. The MESSAGE is not: the emulator renders its own aggregate report instead of AWS's finding list, and it never applies the server-side deploymentName rule, so one finding AWS reports is missing entirely. 2 causes.

--- Cause 1 of 2: the validation report is worded as the emulator's own counted-clause envelope, not as AWS's comma-separated finding list, and the disallowed-specification finding has different text and position (failing checks: launch-wizard.create-deployment-invalid-specifications-map-rejected, launch-wizard.e2e-workload-discovery-to-deployment-attempt-workflow) ---
AWS: Smithy: CreateDeployment, restJson1, POST /createDeployment, success 200; input `specifications` is @required, target DeploymentSpecifications (@sensitive map, @length 1..100, key KeyString @length 3..256 @pattern ^[a-zA-Z0-9-:]+$); modeled errors ValidationException (400, single `message` member), ResourceNotFoundException (404), ResourceLimitException (400), InternalServerException (500). The model constrains only the shapes, not the message text, so the message wording is recorded behavior only. The recording shows AWS accumulating EVERY validation finding for the request into one ValidationException message, each finding being a sentence terminated by a period and joined by ", " (so the message reads "<finding>., <finding>., <finding>., ..."), with NO count preamble and NO trailing advisory sentence. A specifications key the deployment pattern does not define is reported as the fixed-text finding "Specification <key> is not allowed." — fixed text "Specification " / " is not allowed.", variable part the submitted specifications key taken from the request — and that finding comes FIRST, before the deploymentName finding and before the per-specification findings the pattern's own schema raises.
Emulator: HTTP 400 ValidationException, but the message is `state::specification_create_refusal` over `state::specification_warnings`: a count preamble, "; "-joined clauses, and a trailing advisory — "9 validation errors detected: 'KeyPairName' is required by deployment pattern 'AWSManagedAD'; ... ; 'Sim2RealUnknownSpecificationKey123' is not a specification of deployment pattern 'AWSManagedAD'; the specifications a deployment pattern accepts are reported by GetWorkloadDeploymentPattern." The disallowed-key finding is worded "'<key>' is not a specification of deployment pattern '<pattern>'" (quoted key, pattern name appended, no terminating period) instead of "Specification <key> is not allowed.", and `specification_warnings` emits it LAST (it walks the pattern's schema fields before walking the submitted map's keys) where AWS reports it first.
Why: the message is the only place a 400 ValidationException says WHICH input was wrong — the shape carries nothing else. A client that parses the message to tell the operator which specification key to drop (or that asserts on AWS's wording in a test, which is exactly what these checks do) sees neither AWS's finding text nor AWS's separator/ordering, so the parse fails or points at the wrong input. The count preamble also advertises a number AWS never emits, and the trailing "...reported by GetWorkloadDeploymentPattern." clause is appended as if it were a finding.
Fix: the CreateDeployment validation path — `state::specification_create_refusal` (the report envelope: drop the counted-clause preamble and the trailing advisory, terminate each finding with a period and join with ", ") and `state::specification_warnings` (the disallowed-key clause's text and its position in the finding order), both consumed by `ops/create_deployment.rs` where the warnings are turned into the refusal.
Traces: launch-wizard.create-deployment-invalid-specifications-map-rejected, launch-wizard.e2e-workload-discovery-to-deployment-attempt-workflow.

--- Cause 2 of 2: the deploymentName pattern rule AWS enforces server-side is never applied, so a name AWS refuses raises no finding (failing checks: launch-wizard.create-deployment-invalid-specifications-map-rejected, launch-wizard.e2e-workload-discovery-to-deployment-attempt-workflow) ---
AWS: recorded behavior only — the on-disk model constrains `name` as DeploymentName @length 1..50 @pattern ^[A-Za-z0-9_\.-]+$, which is PERMISSIVE enough to admit the names these checks submit, but the recording shows the service applying a STRICTER server-side rule to the same member and reporting a violation of it as the finding "The value of 'deploymentName' doesn't match the regular expression pattern <'^[a-zA-Z][a-zA-Z0-9]+$'>." Fixed text: "The value of '", "' doesn't match the regular expression pattern <'", "'>."; variable parts: the member name as the service names it on the wire (deploymentName) and the pattern it was judged against (^[a-zA-Z][a-zA-Z0-9]+$ — a leading letter followed by one or more alphanumerics, i.e. no hyphen, underscore or dot anywhere, and length at least 2). In the recording this finding appears alongside the specification findings in the same accumulated ValidationException, immediately after the disallowed-specification finding; a request whose only defect is the name is refused on this rule alone.
Emulator: no such finding is ever produced. Both checks submit a hyphenated deployment name (a `sim2real-lw-`/`sim2real-lw-e2e-` prefixed unique name) and the emulator's message contains nothing about deploymentName at all — `ops/create_deployment.rs` judges only the specification-map keys (`state::specification_key_refusal`), the pattern's specification schema (`state::specification_warnings`), live-name reuse and the store ceiling, and otherwise relies on the generated pre-handler constraint walk, which only enforces the model's looser ^[A-Za-z0-9_\.-]+$. Consequently a CreateDeployment whose specifications are valid but whose name contains a hyphen/underscore/dot — or is a single character — is ACCEPTED and a deployment is stored, where AWS refuses it with 400 ValidationException.
Why: this is an overly-permissive acceptance, the worst class for a client: code written against the emulator creates deployments under names AWS rejects outright, and the failure only surfaces in production. Clients that pre-validate names, or that surface the service's finding so an operator can rename, get no finding to surface.
Fix: CreateDeployment's input validation in `ops/create_deployment.rs` (alongside the existing `state::specification_key_refusal` key check, which exists for the same reason: a rule the generated schema walk does not carry), with the message rendered through the same report builder Cause 1 corrects so the name finding is accumulated with the specification findings in AWS's order rather than answered on its own.
Traces: launch-wizard.create-deployment-invalid-specifications-map-rejected, launch-wizard.e2e-workload-discovery-to-deployment-attempt-workflow.

Not covered by the open launch-wizard issues: 20261028T114957Z (ListDeploymentPatternVersions filter-value pattern text) and 20261029T234833Z (placeholder workload catalog contents) concern other operations. The catalog issue does affect the TAIL of this message (which specifications the resolved pattern marks required), which is why both checks assert only on the leading, catalog-independent part of the message — the divergences above are independent of the catalog seed.
