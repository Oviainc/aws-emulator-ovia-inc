# ECR signing-on-push never records a signing status: DescribeImageSigningStatus stays empty for an image matched by a PutSigningConfiguration rule (1 cause)

> _Note: this issue was identified against the code base at commit `3d2bed9d9c0136653e6daec548ca7ef547e87a29`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeImageSigningStatus

## Description
One cause, in ECR. Related open issue that does NOT carry these two checks' replay keys: 20261024T014332Z-ecr-asynchronous-effects-never-occur-and-several-enforcement.md — its Cause 3 is grounded only in ecr.signing-configuration-enforced-verification (a rule naming an unresolvable signer profile, expected to settle to FAILED). The two checks filed here push an image under a rule naming a signer profile that EXISTS (created by signer:PutSigningProfile with platformId Notation-OCI-SHA384-ECDSA) and require the status to settle to COMPLETE, and additionally require that a repository outside the rule's filter gets no status entry at all; neither is covered by that issue's key list, so they are filed here.

Cause 1 of 1: a registry signing configuration has no effect on PutImage — no signing job is created, so DescribeImageSigningStatus never returns a settled (or any) status entry for an image in a repository matched by a signing rule.
AWS: Smithy (com.amazonaws.ecr): PutSigningConfiguration takes SigningConfiguration{rules: SigningRuleList (@length 0..10)}; SigningRule{signingProfileArn (required, @pattern ^arn:aws(-[a-z]+)*:signer:[a-z0-9-]+:[0-9]{12}:/signing-profiles/[a-zA-Z0-9_]{2,}$), repositoryFilters}, documented as "When an image is pushed to a matching repository, a signing job is created using the specified profile." DescribeImageSigningStatus returns signingStatuses: ImageSigningStatusList of ImageSigningStatus{signingProfileArn, status: SigningStatus enum IN_PROGRESS|COMPLETE|FAILED, failureCode, failureReason (both documented as present only when status is FAILED)}; its modeled errors are ImageNotFoundException, RepositoryNotFoundException, InvalidParameterException, ValidationException (400) and ServerException (500). Recorded behavior: after PutSigningConfiguration with one rule whose repositoryFilters WILDCARD_MATCH the repository, pushing an image creates exactly ONE signing job for that image: DescribeImageSigningStatus returns exactly one entry whose signingProfileArn equals the rule's profile ARN, and whose status leaves IN_PROGRESS and settles to a terminal value (COMPLETE for a resolvable signing profile) well inside the checks' poll budgets (180 s and 240 s). An image pushed to a repository that matches NO rule keeps signingStatuses == [].
Emulator: PutSigningConfiguration and GetSigningConfiguration answer and round-trip the rule (the checks get past the write and the read-back of signingProfileArn), but the push has no signing side effect: DescribeImageSigningStatus for the pushed image returns no entry — signingStatuses never becomes non-empty and never reaches COMPLETE or FAILED. Both checks sit in their terminal-status polls (DescribeImageSigningStatus every 5 s / 10 s) observing nothing and are cut off by the harness's 60 s cap ("Check timed out after 60.0s"), so the later assertions in those flows (one-entry-only, the unmatched repository staying empty, and GetSigningConfiguration answering SigningConfigurationNotFoundException with message "The signing configuration does not exist in the registry with id '<account-id>'" after DeleteSigningConfiguration — fixed text with the caller's registry/account id substituted) are never reached and remain unverified.
Why: a client that gates promotion or deployment on an image's signature can never read a signing status, so a signed and an unsigned image are indistinguishable; any supply-chain policy expressed as an ECR signing configuration silently does nothing, and code that waits for IN_PROGRESS to settle hangs until its own timeout.
Fix: the signing-job state machine that PutImage must trigger when the pushed repository matches a rule of the stored registry signing configuration (create one IN_PROGRESS ImageSigningStatus per matching rule, keyed by image digest, and settle it to COMPLETE when the rule's signer profile resolves, or to FAILED with failureCode/failureReason when it does not), plus the DescribeImageSigningStatus handler projecting those entries — in the ECR service's signing state and its put_image / describe_image_signing_status operation handlers. No status must be created for a repository matched by no rule.
Traces: ecr.e2e-signing-and-status-flow, ecr.e2e-signing-configuration-drives-signing-status.
