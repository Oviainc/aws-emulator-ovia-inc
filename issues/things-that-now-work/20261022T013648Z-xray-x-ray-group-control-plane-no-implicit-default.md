# X-Ray group control plane: no implicit Default group, FilterExpression never parsed, constraint violations misclassified, group error messages leak Rust Debug formatting

> _Note: this issue was identified against the code base at commit `5b247f22dea7573e9fb6c4376c776b3a345a666f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateGroup

## Description
Six distinct root causes in the X-Ray group/control-plane surface of services/service-com-amazonaws-xray-awsxray. All are grounded in failing behavioral checks of the `xray` suite. No open issue covers any of them (list_existing_issues query='xray' returns nothing).

Cause 1 of 6: GetGroups does not expose the implicit account-level "Default" group.
AWS: every account/region has an X-Ray group named `Default` that GetGroups returns in `Groups` with a `GroupARN` of the form arn:aws:xray:<region>:<account>:group/Default/<id>; it is not created by the caller and cannot be deleted. Smithy: GetGroups output `Groups` (GroupSummaryList) with GroupName/GroupARN/FilterExpression; recorded behavior for the Default entry itself. Emulator: state starts with an entirely empty group map (services/service-com-amazonaws-xray-awsxray/src/state.rs seeds `groups: BTreeMap` via `#[derive(Default)]`, no Default record) and GetGroups lists only `store.groups`, so a fresh emulator answers `Groups: []`. Why: any client that derives its own account id or a resource ARN from "the group that always exists" gets nothing back and falls through to a create path. All five X-Ray resource-policy checks do exactly that: finding no group with a GroupARN they fall back to CreateGroup with a 37-character name and are then refused with InvalidRequestException "Value '…' at 'groupName' failed to satisfy constraint: Member must have length less than or equal to 32", so the resource-policy surface is never reached at all. Fix: seed the Default group in the service state (crate state init) and have the GetGroups handler include it. Traces: xray.put-resource-policy-roundtrip-and-list, xray.put-resource-policy-malformed-document-fails, xray.put-resource-policy-optimistic-lock-fails, xray.delete-resource-policy-wrong-revision-fails, xray.concurrent-put-resource-policy-optimistic-lock (all five error out on the fallback CreateGroup; see services/service-com-amazonaws-xray-awsxray/src/ops/get_groups.rs:171-193 and src/state.rs:93-107).

Cause 2 of 6: CreateGroup/UpdateGroup accept a syntactically invalid FilterExpression.
AWS: FilterExpression is written in X-Ray's filter-expression language and is parsed at Create/UpdateGroup; a syntactically invalid expression is refused with InvalidRequestException (HTTP 400) and no group is created or mutated. Smithy: CreateGroup/UpdateGroup model InvalidRequestException (client, HTTP 400) and ThrottledException (429) only — there is no success path for an unparseable expression; the expression grammar itself is recorded behavior only. Emulator: stores FilterExpression as an opaque string and answers HTTP 200, e.g. CreateGroup returned Group{FilterExpression: 'this is (not a valid filter'}, 'annotation.marker === "x" AND AND (((' and 'service("unclosed' all with 200. Why: a client that relies on the group's filter actually selecting traces gets a group that silently matches nothing/everything, and the corrupting write is persisted, so UpdateGroup's "prior expression preserved on rejection" contract is also lost. Fix: a filter-expression parser invoked from the CreateGroup and UpdateGroup handlers' validation, rejecting before any state mutation. Traces: xray.create-group-invalid-filter-expression-fails, xray.e2e-group-malformed-filter-expression-rejected, xray.update-group-invalid-filter-expression-preserves-prior.

Cause 3 of 6: CreateGroup accepts a FilterExpression over `metadata.*`, which X-Ray does not index.
AWS: only indexed fields (annotations, service, http, fault/error/throttle, duration, responsetime …) are addressable in a filter expression; `metadata.<key>` is not indexed and the expression is refused with InvalidRequestException (HTTP 400). Recorded behavior only (the model documents no field list). Emulator: CreateGroup returned 200 with Group{FilterExpression: 'metadata.probe_key = "0bbb73411a"'}. Why: a caller believes it has a group filtering on metadata and silently never matches a trace. Fix: field/keyword validation in the same CreateGroup/UpdateGroup filter-expression validator as Cause 2. Traces: xray.group-filter-expression-on-metadata-field-rejected.

Cause 4 of 6: CreateGroup accepts an empty or omitted FilterExpression.
AWS: an explicitly empty string and an omitted FilterExpression are treated identically and both refused with InvalidRequestException and the message "Filter Expression is empty"; no group is created (a subsequent GetGroup on that name answers InvalidRequestException "Group not found"). Smithy: CreateGroup.FilterExpression is optional in the model, so this is a service-side rule — recorded behavior; the message is a fixed AWS string. Emulator: CreateGroup(GroupName=…, FilterExpression="") answered HTTP 200 with Group{FilterExpression: ''} and persisted the group. Why: a client that omits the filter gets a group that AWS would never have created, so state diverges permanently from that point on. Fix: CreateGroup handler validation (reject empty/absent FilterExpression before minting the ARN). Traces: xray.create-group-empty-filter-expression-persists.

Cause 5 of 6: input-constraint violations are reported as the service's own InvalidRequestException instead of ValidationException.
AWS: a violation of a modeled @length/@range constraint is refused by the request layer with error code ValidationException at HTTP 400, message "1 validation error detected: Value '…' at '<member>' failed to satisfy constraint: …". Smithy: CreateGroup.GroupName @length(min:1,max:32); SamplingRule.Priority and SamplingRule.FixedRate carry @range bounds; CreateGroup/CreateSamplingRule model InvalidRequestException and ThrottledException (ValidationException is the protocol-level constraint envelope, not a modeled operation error). Emulator: returns Code 'InvalidRequestException' with the constraint text, e.g. "Value 'sim2real-behav-xray-g-0c95ae643be' at 'groupName' failed to satisfy constraint: Member must have length less than or equal to 32" for a 33-character name, "Value '' at 'groupName' …greater than or equal to 1" for an empty name, and "Value '0' at 'samplingRule.priority' …greater than or equal to 1". Why: clients branch on the error code — code that retries/handles ValidationException separately from the service's InvalidRequestException takes the wrong branch, and SDK error-typed catch blocks (`except ValidationException`) never fire. Fix: the shared request-layer constraint validator should emit the ValidationException envelope rather than mapping into each operation's modeled InvalidRequestException. Traces: xray.create-group-name-exceeds-max-length-rejected, xray.create-group-empty-name-rejected, xray.create-sampling-rule-out-of-range-priority-rejected, xray.e2e-sampling-rule-invalid-fixed-rate-rejected, xray.sampling-rule-fixed-rate-out-of-range-rejected.

Cause 6 of 6: group collision and group-not-found messages do not follow AWS's message rule, and one leaks Rust Debug formatting of internal types.
AWS: the duplicate-group refusal is InvalidRequestException whose message is built from the request as "<GroupName> already exists"; a lookup of a group that does not exist is InvalidRequestException with the fixed message "Group not found" (asserted on both DeleteGroup-then-GetGroup and on GetGroup in two independent checks). Both are rules (one request-derived, one fixed), so the text is a requirement here, not an example. Emulator: duplicate -> "a group named `sim2real-xr-dup-2d31741c6966` already exists"; missing group -> "no group matches GroupName Some(\"sim2real-behav-xray-grp-3cb1137b\") / GroupARN None". The second renders Rust `Option` Debug output (`Some("…")` / `None`) into a customer-facing message, exposing the emulator's internal representation. Error codes match (InvalidRequestException, 400). Why: clients and log scrapers that match AWS's documented text mis-handle the refusal, and the Debug leak is not a message AWS could ever produce. Fix: message construction in the CreateGroup / GetGroup / DeleteGroup handlers' error paths. Traces: xray.create-group-duplicate-name-fails, xray.create-group-duplicate-name-rejected, xray.delete-group-lifecycle.
