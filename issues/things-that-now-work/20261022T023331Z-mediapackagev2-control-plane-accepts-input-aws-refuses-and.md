# mediapackagev2 control plane accepts input AWS refuses and misclassifies rejections: idempotency tokens, input/output-mode and container/manifest combos, pagination and container-type immutability (7 causes)

> _Note: this issue was identified against the code base at commit `b8bbb064bfede5b5be6782e6b85c8258ff782b33`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
The mediapackagev2 emulator's create/list/update paths skip whole classes of server-side semantic validation that real AWS performs, and where it does reject it picks the wrong exception class or message rule. 7 causes.

Cause 1 of 7: ClientToken idempotency is not implemented on the create operations — a replay with the SAME token and SAME parameters is rejected as a duplicate, and a replay with the same token and DIFFERENT parameters is not distinguished.
AWS: Smithy (com.amazonaws.mediapackagev2): CreateChannelGroup, CreateChannel and CreateOriginEndpoint each bind ClientToken -> IdempotencyToken with @idempotencyToken, carried in httpHeader x-amzn-client-token, and each operation is @idempotent; each declares ConflictException (httpError 409), whose ConflictExceptionType enum includes both RESOURCE_ALREADY_EXISTS and IDEMPOTENT_PARAMETER_MISMATCH. The two values exist precisely because a repeat create must be split in two: a repeat with the same token and an identical request replays the original result (200, same Arn, no error), while a repeat with the same token and a changed member is 409 with ConflictExceptionType IDEMPOTENT_PARAMETER_MISMATCH and must leave the stored resource untouched.
Emulator: the token is ignored entirely. A same-token/same-params CreateChannelGroup retry answers 409 ConflictException ('Channel group <name> already exists'), and the same-token/different-Description case answers that same already-exists conflict rather than IDEMPOTENT_PARAMETER_MISMATCH. CreateChannel behaves identically ('Channel <name> already exists in channel group <group>').
Why: every AWS SDK retries a create on a timeout or 5xx using the token it already sent. Against this emulator that retry turns a succeeded create into a hard 409, so a client that cannot distinguish 'already created by my own retry' from 'someone else took the name' either fails the workflow or deletes a resource it did create. Code that branches on ConflictExceptionType to tell a genuine parameter mismatch from a benign replay has nothing to branch on.
Fix: the CreateChannelGroup / CreateChannel / CreateOriginEndpoint handlers and the mediapackagev2 service state — record the idempotency token with the created resource's request fingerprint, replay the stored response on an identical repeat, and emit ConflictException with ConflictExceptionType IDEMPOTENT_PARAMETER_MISMATCH when the token matches but the request does not.
Traces: mediapackagev2.create-channel-group-idempotent-retry-same-params-succeeds, mediapackagev2.channel-group-idempotent-token-mismatch-rejected, mediapackagev2.create-channel-idempotent-token-mismatch-rejected.

Cause 2 of 7: CreateChannel accepts OutputLockingMode on a non-CMAF input type.
AWS: Smithy: CreateChannel input binds InputType (enum InputType: HLS | CMAF | MULTIVIEW) and OutputLockingMode (enum OutputLockingMode: EPOCH_LOCKED | NON_EPOCH_LOCKED), and declares ValidationException (httpError 400). ValidationExceptionType carries the dedicated discriminator ONLY_CMAF_INPUT_TYPE_ALLOW_OUTPUT_LOCKING_MODE, i.e. the model states that OutputLockingMode is only configurable for a CMAF/MULTIVIEW-input channel; combining it with InputType=HLS is a 400 ValidationException and no channel is created. The message is a requirement here because it is built from the request — it names the rejected member path and restates the rule; recorded form: "Validation error encountered at request.outputLockingMode: OutputLockingMode can only be configured when the channel InputType is CMAF or MULTIVIEW. To use OutputLockingMode, create a channel with CMAF or MULTIVIEW input type".
Emulator: the call SUCCEEDS with HTTP 200, creating the channel and echoing InputType 'HLS' together with OutputLockingMode 'EPOCH_LOCKED'.
Why: the emulator is over-permissive on a cross-member rule, so a client's invalid encoder configuration is silently persisted and the same template fails only in production; a test suite relying on the emulator to reject it gets a false pass.
Fix: CreateChannel's validation stage in the mediapackagev2 handler — add the InputType/OutputLockingMode compatibility check before any state mutation, rejecting with ValidationException and ValidationExceptionType ONLY_CMAF_INPUT_TYPE_ALLOW_OUTPUT_LOCKING_MODE.
Traces: mediapackagev2.create-channel-invalid-locking-mode-combo-rejected.

Cause 3 of 7: CreateOriginEndpoint accepts a DASH manifest on a TS-container endpoint.
AWS: Smithy: CreateOriginEndpoint requires ContainerType (enum ContainerType: TS | CMAF | ISM) and takes DashManifests/HlsManifests/LowLatencyHlsManifests/MssManifests; it declares ValidationException (400), and ValidationExceptionType includes TS_CONTAINER_TYPE_WITH_DASH_MANIFEST — the manifest families are not all legal in every container, and a TS container with a DASH manifest is that named violation. AWS rejects with 400 ValidationException and creates nothing.
Emulator: the call SUCCEEDS with HTTP 200 and returns an endpoint whose ContainerType is 'TS' and whose DashManifests list contains the requested manifest with a generated egress Url.
Why: an unplayable combination is accepted and published as a real endpoint URL, so the failure surfaces at the player instead of at the API; again a false pass for anything asserting the rejection.
Fix: CreateOriginEndpoint's validation stage — enforce container/manifest-family compatibility, rejecting with ValidationException + ValidationExceptionType TS_CONTAINER_TYPE_WITH_DASH_MANIFEST.
Traces: mediapackagev2.create-origin-endpoint-container-manifest-mismatch-rejected, mediapackagev2.origin-endpoint-container-manifest-mismatch-rejected.

Cause 4 of 7: CreateOriginEndpoint accepts an endpoint with no manifest at all.
AWS: Smithy: ValidationExceptionType includes NUM_MANIFESTS_LOW (and NUM_MANIFESTS_HIGH), i.e. the service enforces a minimum manifest count on an origin endpoint; a CreateOriginEndpoint with ContainerType=TS and none of HlsManifests/LowLatencyHlsManifests/DashManifests/MssManifests set is a 400 ValidationException and no endpoint is created. The message is request-derived and therefore a requirement: recorded form "Validation error encountered at request: You've requested an origin endpoint without a manifest. Your origin endpoint needs to contain at least one manifest. Add a manifest and try to create your origin endpoint again".
Emulator: the call SUCCEEDS with HTTP 200 and returns an endpoint with all four manifest lists empty.
Why: the emulator materialises an origin endpoint that can never serve anything, and a client never learns that its request was incomplete.
Fix: CreateOriginEndpoint's validation stage — reject when the total number of configured manifests is below the minimum, with ValidationExceptionType NUM_MANIFESTS_LOW.
Traces: mediapackagev2.create-origin-endpoint-num-manifests-low-rejected.

Cause 5 of 7: a malformed pagination token is answered with 501 NotImplemented instead of a 400 ValidationException.
AWS: Smithy: ListChannelGroups (GET /channelGroup) binds NextToken via httpQuery 'nextToken' and is @paginated (inputToken/outputToken NextToken); it declares ValidationException (400). ValidationExceptionType includes INVALID_PAGINATION_TOKEN, so an opaque token the service did not issue is a modeled 400, not a server-side failure. Message is request-derived, recorded form: "Validation error encountered at request.nextToken: You've provided an invalid pagination token in your request. Check your token and then try again".
Emulator: the request is answered with error code 'NotImplemented' (HTTP 501) — the token path is unhandled rather than validated.
Why: a 501 is a server-fault class: SDK retry policies treat it very differently from a 400, so a client that passed a stale or truncated token retries a request that can never succeed instead of surfacing a validation error, and never learns the token is the problem.
Fix: the ListChannelGroups handler's pagination decoding in mediapackagev2 — reject an undecodable NextToken with ValidationException + ValidationExceptionType INVALID_PAGINATION_TOKEN instead of falling through to the not-implemented path.
Traces: mediapackagev2.list-channel-groups-pagination-invalid-token-rejected.

Cause 6 of 7: an out-of-range MaxResults is rejected with the generic framework constraint message instead of the service's own ValidationException form.
AWS: Smithy: ListOriginEndpoints.MaxResults -> ListResourceMaxResults, httpQuery 'maxResults', @range min 1 max 100, default 10; the operation declares ValidationException (400) and ValidationExceptionType includes INVALID_PAGINATION_MAX_RESULTS. The code (ValidationException) and status (400) match; what diverges is the message, and here the message IS a requirement because it is built from the request: mediapackagev2 names the member path and restates the violated constraint in its own fixed form — recorded as "Validation error encountered at request.maxResults: Member must have value less than or equal to 100. Check the value you specified in your request and then try again".
Emulator: returns the generic Smithy/AWS-framework constraint sentence instead: "1 validation error detected: Value '1001' at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 100".
Why: the whole mediapackagev2 surface reports constraint violations in the 'Validation error encountered at request.<member>: ...' form with a ValidationExceptionType discriminator; emitting the generic framework form means a client parsing or matching mediapackagev2's documented validation text (or reading the discriminator) does not recognise the rejection, and the two error families are inconsistent within one service.
Fix: the mediapackagev2 range/constraint validation and ValidationException serializer for the list operations — route declared @range violations through the service's own message builder and set ValidationExceptionType (INVALID_PAGINATION_MAX_RESULTS for maxResults, MEMBER_MAX_VALUE for a plain range violation) rather than emitting the generic framework message.
Traces: mediapackagev2.list-origin-endpoints-max-results-out-of-range-rejected.

Cause 7 of 7: UpdateOriginEndpoint does not enforce ContainerType immutability — the attempt is answered 501 NotImplemented.
AWS: Smithy: UpdateOriginEndpoint (PUT /channelGroup/{ChannelGroupName}/channel/{ChannelName}/originEndpoint/{OriginEndpointName}) requires ContainerType and declares ValidationException (400); ValidationExceptionType includes CONTAINER_TYPE_IMMUTABLE. Changing ContainerType after creation is therefore a modeled 400 that leaves ContainerType and the endpoint's ETag unchanged, while an update that keeps ContainerType and changes only Description succeeds with a rotated ETag. Message is request-derived, recorded form: "Validation error encountered at request.containerType: You can't change the container type after you create an origin endpoint. To use a different container type, you'll need to create a new origin endpoint".
Emulator: answers error code 'NotImplemented' (HTTP 501, body 'operation UpdateOriginEndpoint is scaffolded but not implemented in this emulator'), so the immutability rule is neither enforced nor reportable.
Why: a client gets a retryable server-fault class for what is a permanent client error, and the immutability invariant that protects an endpoint's published URLs is unverifiable. (The bare 'UpdateOriginEndpoint is a scaffold stub' gap is filed separately by the suite's scaffold-stub issue for update_origin_endpoint.rs; this cause is the rejection semantics the implemented operation must carry, and is listed here because the check was not attributed to that stub cluster.)
Fix: the UpdateOriginEndpoint handler — compare the requested ContainerType against the stored endpoint and reject a change with ValidationException + ValidationExceptionType CONTAINER_TYPE_IMMUTABLE before applying any mutation.
Traces: mediapackagev2.update-origin-endpoint-container-type-immutable-rejected.
