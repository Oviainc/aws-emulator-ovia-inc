## Description
Four net-new behavioral root causes on the SES surface. None of the four failing checks was marked ALREADY FILED or OWNED by the replay report. Two related open issues do NOT cover them: 20261025T214303Z-ses-putidentitypolicy-stub.md claims PutIdentityPolicy is still an unimplemented scaffold answering 501, which is now stale — the handler at services/service-com-amazonaws-ses-simpleemailservice/src/ops/put_identity_policy.rs is implemented and answers 200/400, which is why causes 1 and 2 below are now observable; and 20261025T214303Z-ses-account-statistics-plane-is-unreachable-and-three.md covers SESv2 GetAccount (now implemented) but not PutAccountDedicatedIpWarmupAttributes (cause 3), and describes the missing region clause only for the SES v1 send path (its Cause 5), while cause 4 below is the same defect reached through SESv2 SendEmail and still present — treat cause 4 as the same root cause if that issue's Cause 5 is fixed first.

Cause 1 of 4: PutIdentityPolicy accepts a sending-authorization policy whose Resource is a bare "*".
AWS: Smithy com.amazonaws.ses#PutIdentityPolicy models exactly one error, InvalidPolicyException (errorKind client, httpError 400, awsQueryError code InvalidPolicy), documented as "Indicates that the provided policy is invalid". SES is stricter than generic IAM here: the Resource element of a sending-authorization policy must be an identity ARN, so a bare "*" is refused 400 InvalidPolicy with the message "Invalid ARN: ARNs must start with 'arn:': <value>" — the fixed text is "Invalid ARN: ARNs must start with 'arn:': " and the trailing token is the offending Resource value copied from the request (here "*"). The rejected policy is not stored, and an otherwise-identical policy naming the identity's own ARN as Resource is accepted for the same identity and policy name.
Emulator: the call SUCCEEDS — HTTP 200, empty PutIdentityPolicyResponse — and the wildcard policy is stored. The handler's only document check is `service_common::iam_policy::resource_policy_defect`, a generic IAM resource-policy grammar read that treats "*" as a legal Resource, so no InvalidPolicy is ever raised for a non-ARN Resource.
Why: this is an over-permissiveness divergence. A client (or an infrastructure test) that relies on SES refusing a world-open sending-authorization policy gets a 200 and a stored policy that grants ses:SendEmail on "*" to Principal "*"; code that catches InvalidPolicy to surface a configuration error never runs, and the emulator silently blesses a policy real AWS will not hold.
Fix: the policy-document validation in the PutIdentityPolicy handler (services/service-com-amazonaws-ses-simpleemailservice/src/ops/put_identity_policy.rs, the `resource_policy_defect` gate around line 206) — read the Resource element and refuse a value that is not an identity ARN with InvalidPolicyException carrying AWS's "Invalid ARN: ARNs must start with 'arn:': <value>" text, before anything is written to state.
Traces: ses.identity-policy-wildcard-resource-rejected.

Cause 2 of 4: the oversize-policy refusal uses the emulator's own limit (4096) and its own sentence instead of AWS's 4000-byte rule and message.
AWS: PutIdentityPolicy.Policy carries only @length min 1 in the model, so the size ceiling is a service-side rule the model states in prose: "The text of the policy in JSON format. The policy cannot exceed 4 KB." Recorded behavior: the limit enforced is 4000 bytes and a longer document is refused 400 InvalidPolicy with the message "The policy size, <size>, is larger than the max policy size, 4000. " — fixed text "The policy size, ", the submitted document's size in bytes taken from the request, ", is larger than the max policy size, 4000. ", including the trailing space, which is part of AWS's text. The oversized policy is not stored.
Emulator: the right error class but the wrong rule and the wrong message — "Policy exceeds the maximum size of 4096 bytes." The threshold compared against is `crate::state::MAX_POLICY_BYTES` (4096), not 4000, and the sentence is handler-authored: it neither reports the submitted size nor names 4000.
Why: documents between 4001 and 4096 bytes are accepted and stored where AWS refuses them, so a client's policy works against the emulator and fails in production; and every caller or log-scraper that matches AWS's message (the only machine-readable statement of the actual limit and of how big the submitted document was) diverges.
Fix: the size gate in the same handler (services/service-com-amazonaws-ses-simpleemailservice/src/ops/put_identity_policy.rs, the `input.policy.len() > crate::state::MAX_POLICY_BYTES` branch around lines 193-198) plus the constant it reads in services/service-com-amazonaws-ses-simpleemailservice/src/state.rs — compare against 4000 bytes and emit AWS's templated sentence.
Traces: ses.put-identity-policy-oversized-document-rejected.

Cause 3 of 4: SESv2 PutAccountDedicatedIpWarmupAttributes is an unimplemented scaffold stub, so the account's auto-warmup flag cannot be written.
AWS: Smithy com.amazonaws.sesv2#PutAccountDedicatedIpWarmupAttributes is PUT /v2/email/account/dedicated-ips/warmup, success 200 with an empty body, input {AutoWarmupEnabled: boolean, default false}, modeled errors BadRequestException (400) and TooManyRequestsException (429) only. It sets the account-level flag that GetAccount reports as DedicatedIpAutoWarmupEnabled, and the very next GetAccount reflects the new value.
Emulator: the call is refused with HTTP 501 and code NotImplemented — "operation PutAccountDedicatedIpWarmupAttributes is scaffolded but not implemented in this emulator". The handler still carries the scaffold marker: services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/put_account_dedicated_ip_warmup_attributes.rs line 4, "//! SCAFFOLDED, NOT IMPLEMENTED".
Why: NotImplemented/501 appears in no SESv2 model, so a client sees an unmodeled failure class it cannot branch on, and the account attribute is write-only-absent: GetAccount now answers but its DedicatedIpAutoWarmupEnabled can never be changed, so no dedicated-IP warmup configuration is reachable.
Fix: implement the operation in its own handler file, services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/put_account_dedicated_ip_warmup_attributes.rs, writing the flag into the account record in that crate's state so GetAccount reads it back, and remove that file's scaffold header line.
Traces: ses.account-dedicated-ip-auto-warmup-togglable.

Cause 4 of 4: the MessageRejected text for a send from an unverified identity omits the " in region <REGION>" clause (SESv2 SendEmail, and the v1 path too).
AWS: SendEmail models MessageRejected (errorKind client, httpError 400, awsQueryError code MessageRejected). A send whose From identity exists but is not verified is refused 400 MessageRejected with the message "Email address is not verified. The following identities failed the check in region <REGION>: <identities>" — fixed text "Email address is not verified. The following identities failed the check in region ", then the signing region upper-cased (endpoint-derived), then ": ", then the failing identity/identities taken from the request. Two different unverified senders therefore produce two different messages.
Emulator: the code is right and the leading sentence is right, but the region clause is dropped: "Email address is not verified. The following identities failed the check: <identity>".
Why: SES identities are per-region, so the region is the diagnostic half of this refusal — a client or a human reading the log cannot tell which region's identity list failed, and any code that string-matches AWS's message (as AWS documents and the console presents it) never matches.
Fix: the unverified-identity gate's message formatter in the SESv2 send handler (services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs) and its SES v1 SendEmail/SendRawEmail counterpart — include the request's region, upper-cased, in the fixed clause. Same root cause as Cause 5 of the open issue 20261025T214303Z-ses-account-statistics-plane-is-unreachable-and-three.md, which that issue's replay key does not cover for this check.
Traces: ses.send-unverified-identity-rejected-quota-unchanged.
