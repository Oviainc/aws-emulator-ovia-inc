=== Cause 1 of 1: the aws:CurrentTime-denied iam:ListUserTags refusal stops at '... action' and omits the authorization-details sentence ===
AWS: IAM speaks awsQuery (service com.amazonaws.iam#AWSIdentityManagementV20100508, version 2010-05-08). Smithy: ListUserTags takes UserName (existingUserNameType, @required, @length 1..128, @pattern ^[\w+=,.@-]+$), Marker and MaxItems (@range 1..1000), returns Tags (@required, @length 0..50) and models only NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404) and ServiceFailureException (ServiceFailure, HTTP 500). The authorization refusal AccessDenied / HTTP 403 is a service-common error whose message text is not modeled, so this is recorded behavior only: when a DateGreaterThan/aws:CurrentTime grant has not yet become true, nothing allows the action and the recorded refusal is TWO sentences — the documented implicit-deny sentence followed by a pointer to the request's authorization details:
  `User: <caller-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> because no identity-based policy allows the <service>:<Action> action. Go to https://<iam-console-authorization-details-url> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`
Fixed text (must appear verbatim): `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no identity-based policy allows the `, ` action. Go to `, ` for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: `. Variable parts, taken from the signed request and the emulator's own state: <caller-arn> (the ARN of the principal whose access key signed the request), <service>:<Action> (the IAM action of the refused operation — here `iam:ListUserTags`, appearing twice), <resource-description> (how IAM names the evaluated resource for this action — for ListUserTags the recorded form is `user <UserName>`, with UserName taken from the request), the console authorization-details URL, and <authorization-id> (the per-request authorization id). The check matches the URL by shape (\S+) and the id by shape ([A-Za-z0-9]+) and never pins their values, so no per-run value is being compared: the requirement is that the sentence exist at all.
Emulator: the decision and the code are right — the future-instant DateGreaterThan condition does deny, Error.Code is `AccessDenied`, and the first sentence is byte-for-byte correct — and then the message ends. Observed Error.Message: `User: arn:aws:iam::<account>:user/<user> is not authorized to perform: iam:ListUserTags on resource: user <user> because no identity-based policy allows the iam:ListUserTags action`, with the entire second sentence (console URL + 'or call the GetRequestAuthorizationDetails API with the following authorization id: <id>') missing, and with it any authorization id to point at. The expected text is the received text plus that whole trailing sentence. The divergence is the missing sentence on every such refusal, not a per-run id or clock value.
Why: a client that reads AWS's denial text to route a developer to the authorization-details page, or that parses the message to hand an authorization id to GetRequestAuthorizationDetails, receives a truncated string and has nothing to follow — the very troubleshooting hook IAM refusals exist to provide. Parity harnesses and log scrapers matching the full documented refusal do not recognise it. Hypothesis: the trailer is decided globally in one shared denial-message builder rather than per refusal, so each successive 'remove it' fix flips every IAM refusal at once; this check is the third observed oscillation of the same text and the second in the absent direction.
Fix: the shared authorization-refusal denial-message builder in the IAM crate — the component that renders the AccessDenied message for iam operations ahead of the operation handlers (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/service.rs and the policy-evaluation / denial-message module it calls), not the ListUserTags handler, which is reached only after the refusal. It must select the trailer PER refusal from that action's recorded message instead of appending or suppressing it unconditionally: refusals AWS records with the authorization-details pointer (iam:ListUserTags and iam:ListAccessKeys among them) must carry the console-URL + GetRequestAuthorizationDetails sentence with the authorization id taken from the request's authorization context, while the refusals already filed in the opposite direction (iam:UntagPolicy, iam:ListPoliciesGrantingServiceAccess, iam:ListUsers) must end at '... action'.
