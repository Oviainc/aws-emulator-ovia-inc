# Transfer fidelity gaps: API_GATEWAY CreateServer always refused, TestConnection never reaches a reachable endpoint, agreements outlive DeleteServer, ImportSshPublicKey over-permissive, DeleteWebAppCustomization 501, no customization optimistic lock, denial message omits resource (7 causes)

> _Note: this issue was identified against the code base at commit `3ecafc116f2b44ac9fb7ddf17b83f092c778a529`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateServer

## Description
SEVEN distinct root causes in the transfer emulator, each grounded in failing behavioral checks of this suite. All seven must be closed before this issue is submitted.

=== Cause 1 of 7: CreateServer refuses EVERY API_GATEWAY identity provider, because the invocation-role verification only recognizes AWS-shaped execute-api hostnames ===
AWS: Smithy (com.amazonaws.transfer) CreateServer.IdentityProviderType -> IdentityProviderType enum (API_GATEWAY among its values), IdentityProviderDetails carries Url and InvocationRole; modeled errors AccessDeniedException 403, InvalidRequestException 400, ResourceExistsException 409, ResourceNotFoundException 404, ServiceUnavailableException 503, ThrottlingException 429, InternalServiceError 503. Recorded behavior: CreateServer(IdentityProviderType='API_GATEWAY', IdentityProviderDetails={'Url': <a deployed REST API stage invoke URL>, 'InvocationRole': <role whose inline policy Allows execute-api:Invoke on that API>}) succeeds with HTTP 200 and a ServerId, and DescribeServer then reports IdentityProviderType='API_GATEWAY'.
Emulator: every such CreateServer is refused with HTTP 400 InvalidRequestException, message example 'Unable to verify access to API https://127.0.0.1:39477/_aws/execute-api/8sh3tqaaaa/sim2real'. The cause is deterministic and visible in the code: services/service-com-amazonaws-transfer-transferservice/src/state/authorization.rs::execute_api_arn only parses the AWS production invoke host form '<api-id>.execute-api.<region>.amazonaws.com/<stage>' (see its own unit test an_invoke_url_resolves_to_the_apis_execute_api_arn). The invoke URL this emulator's own apigateway emulation hands out has the path form '<host>/_aws/execute-api/<api-id>/<stage>', so execute_api_arn returns None, the verification is evaluated with the empty resource NO_RESOURCE, the role's statement scoped to 'arn:aws:execute-api:<region>:<account>:<api-id>/*' cannot match it, iam_authorization answers NotStated, invocation_role_can_invoke returns false and create_server.rs raises the refusal.
Why: no API_GATEWAY-backed (custom IdP) server can be created at all against this emulator, so every scenario that needs one — CreateAccess/DescribeAccess IdP-type preconditions, TestIdentityProvider positive controls, any customer custom-IdP provisioning flow or IaC — fails at its first call with a 400 that names the caller's own, valid API URL as unverifiable. It is also self-inconsistent: the emulator refuses to verify a URL that its own API Gateway emulation minted and serves.
Fix: the API-Gateway URL -> execute-api ARN derivation used by the CreateServer API_GATEWAY precondition (services/service-com-amazonaws-transfer-transferservice/src/state/authorization.rs, consumed by src/ops/create_server.rs) must recognize the invoke-endpoint form this emulator publishes in addition to the production hostname form, so a role allowed to invoke that API verifies.
Traces: transfer.create-access-duplicate-external-id-rejected, transfer.test-identity-provider-invalid-request-error, transfer.test-identity-provider-service-managed-rejected.

=== Cause 2 of 7: TestConnection can never report a usable connection — Status is unconditionally ERROR and SftpConnectionDetails is never populated ===
AWS: Smithy TestConnection input ConnectorId (@required, ^c-([0-9a-f]{17})$), output Status, StatusMessage, SftpConnectionDetails (SftpConnectorConnectionDetails, carrying HostKey); errors InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503, InternalServiceError 503. Recorded behavior: for an SFTP connector whose Url names a reachable Transfer server and whose SftpConfig.UserSecretId holds that server user's credentials, TestConnection reports the observed remote host key in SftpConnectionDetails.HostKey; once that key is pinned with UpdateConnector(SftpConfig.TrustedHostKeys=[key]), a subsequent TestConnection reports Status='OK'. (The host key value itself is environment-specific and is NOT a requirement — only that a key is reported and that the pinned-key retest reaches Status OK.)
Emulator: src/ops/test_connection.rs always answers Status = ERROR with sftp_connection_details = None for any connector that configures SftpConfig, with no attempt to resolve the server the connector Url names inside the same emulator. Status never becomes 'OK' and no host key is ever observable, so every flow that gates on a verified connector stalls: the three checks below spin in their TestConnection poll loops until the harness kills them ('Check timed out after 60.0s').
Why: a client cannot bring a connector into service at all. Connector provisioning flows that legitimately wait for Status OK before transferring never proceed, and a caller cannot distinguish 'this connector is misconfigured' (a real ERROR) from 'this emulator does not evaluate connections'. It also hides the downstream data plane entirely — the same checks would next hit StartFileTransfer, whose 501 NotImplemented is already filed as cause 4 of open issue 20261022T202037Z-transfer-host-key-plane-broken-importhostkey-refuses-valid.md; that issue does NOT cover TestConnection's verdict, which is what blocks these three checks before StartFileTransfer is ever reached.
Fix: the TestConnection handler (src/ops/test_connection.rs) and the connector state it reads must derive the verdict from the emulated target — resolve the Transfer server the connector Url names, report its host key in SftpConnectionDetails.HostKey, and answer Status OK when the secret and TrustedHostKeys match it (keeping ERROR, with StatusMessage, when they do not).
Traces: transfer.e2e-connector-remote-directory-flow, transfer.file-transfer-result-status-visibility-ttl, transfer.workflow-step-state-out-of-order-rejected.

=== Cause 3 of 7: an agreement remains readable and mutable after its server is deleted ===
AWS: Smithy DescribeAgreement takes AgreementId + ServerId (both @required) and models ResourceNotFoundException (client, HTTP 404); DeleteAgreement models the same. Recorded behavior: DeleteServer on a server that still has an ACTIVE agreement succeeds (no referential-integrity refusal), and afterwards the agreement is no longer reachable through the ServerId+AgreementId lookup — DescribeAgreement answers 404 ResourceNotFoundException, and DeleteAgreement on it answers 404 as well, so the agreement is genuinely gone rather than half-deleted.
Emulator: after DeleteServer the server is correctly gone (DescribeServer -> 404), but DescribeAgreement(ServerId=<deleted server>, AgreementId=<agreement>) returns HTTP 200 with the full DescribedAgreement (Status 'ACTIVE', its ARN still naming the deleted server). src/ops/describe_agreement.rs deliberately does not re-resolve the server, and DeleteServer does not remove the server's agreements from state.
Why: a client reading back its own teardown sees an ACTIVE agreement attached to a server that does not exist, so cleanup/reconciliation loops never converge and an orphan check that branches on 404 takes the wrong path.
Fix: the DeleteServer handler / agreement state in the transfer crate (src/ops/delete_server.rs plus src/state) must drop the deleted server's agreements, or DescribeAgreement/DeleteAgreement must resolve the server before the agreement so the pair lookup answers the modeled 404.
Traces: transfer.delete-server-referenced-by-agreement-succeeds-and-orphans-agreement.

=== Cause 4 of 7: ImportSshPublicKey stores key bodies AWS refuses — unsupported algorithm name, empty or undecodable base64 payload ===
AWS: Smithy ImportSshPublicKey.SshPublicKeyBody @required, @length 0..2048, @pattern ^\s*(ssh|ecdsa)-[a-z0-9-]+[ \t]+((base64 groups))(\s*|[ \t]+[\S \t]*\s*)$ — so bodies like 'ssh-dss <payload>', 'ssh-foo <payload>', 'ssh-rsa ' and 'ssh-rsa A' all satisfy the modeled pattern and reach the service. The service then validates two things: the algorithm NAME is one it supports, and the base64 payload is non-empty and decodable. Every failure of either is refused with the modeled InvalidRequestException (client, HTTP 400); recorded message example 'Unsupported or invalid SSH public key format'. The complementary side is asserted too and currently passes: a payload truncated mid-modulus, an RSA payload labelled ssh-ed25519, and any 'ecdsa-*' label ARE accepted and stored verbatim, so the fix must not over-validate the key material.
Emulator: each of the four refused bodies is accepted with HTTP 200 and a fresh SshPublicKeyId (example {'ServerId': 's-00000000000000001', 'SshPublicKeyId': 'key-00000000000000003'}), and the key is stored on the user. No algorithm-name or payload check exists.
Why: a client that relies on the service to reject a malformed or unsupported key persists a key that can never authenticate an SFTP session, and gets no signal at provisioning time where AWS returns 400. Open issue 20261022T202037Z-transfer-input-validation-authorization-and-reference-data-diverge.md names this same check for a DIFFERENT, now-passing cause (whitespace-normalized duplicate detection, its cause 3) and does not cover algorithm-name/payload validation.
Fix: SshPublicKeyBody validation in the ImportSshPublicKey handler (src/ops/import_ssh_public_key.rs) of the transfer crate: refuse an algorithm name outside the supported set and a payload that is empty or not decodable base64 with the modeled 400 InvalidRequestException, while still accepting the ecdsa- prefix family and unparsed-but-decodable key material.
Traces: transfer.import-ssh-public-key-body-validated-and-scoped-to-user.

=== Cause 5 of 7: DeleteWebAppCustomization is an unimplemented scaffold stub answering 501 NotImplemented ===
AWS: Smithy DeleteWebAppCustomization input WebAppId (@required, len 24, ^webapp-[0-9a-f]{17}$), output Unit, @idempotent; modeled errors AccessDeniedException 403, ConflictException 409, InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429. A successful delete answers HTTP 200 with an empty body, and any failure comes from that modeled set.
Emulator: services/service-com-amazonaws-transfer-transferservice/src/ops/delete_web_app_customization.rs still carries the 'SCAFFOLDED, NOT IMPLEMENTED' marker and returns Scaffolded::not_implemented, i.e. HTTP 501 with the unmodeled code 'NotImplemented' ('operation DeleteWebAppCustomization is scaffolded but not implemented in this emulator'). Observed in the racer set as codes {None, 'NotImplemented'}.
Why: NotImplemented is not in this operation's modeled error set, so an SDK client gets an error class it cannot handle, retry or distinguish from a service fault; a web app's customization can never be removed, and no customization-conflict semantics can be exercised.
Fix: implement the handler in src/ops/delete_web_app_customization.rs against the web-app customization state (404 for an unknown WebAppId, 409 ConflictException where the real service conflicts) and delete the SCAFFOLDED marker line.
Traces: transfer.delete-webapp-customization-conflict-while-in-use.

=== Cause 6 of 7: UpdateWebAppCustomization has no optimistic concurrency control — concurrent writers all win ===
AWS: Smithy UpdateWebAppCustomization input WebAppId (@required), Title (len 0..100), LogoFile, FaviconFile; output WebAppId; modeled errors include ConflictException (client, HTTP 409). Recorded behavior only: two UpdateWebAppCustomization calls issued concurrently against the same web app do not both commit — exactly one succeeds and the stale writer is refused with 409 ConflictException, so the surviving customization is one submitter's value and never a half-applied mix.
Emulator: two concurrent UpdateWebAppCustomization calls on the same WebAppId both return success — observed results [(True, None), (True, None)], i.e. no ConflictException is ever produced and the later write silently clobbers the earlier one.
Why: a client that uses the 409 to detect a lost update (read-modify-write on Title/LogoFile) never sees it and silently discards a concurrent change; the emulator cannot be used to test that retry path at all.
Fix: the UpdateWebAppCustomization handler and the web-app customization state in the transfer crate (src/ops/update_web_app_customization.rs plus src/state) need a per-web-app modification guard that admits one writer and refuses the racing one with the modeled 409 ConflictException. (Open issue 20261022T202037Z-transfer-host-key-plane-broken-importhostkey-refuses-valid.md covers the same shortcoming for UpdateWebApp, a different operation, via its cause 4; the customization operation is not covered there.)
Traces: transfer.concurrent-update-webapp-customization-optimistic-lock.

=== Cause 7 of 7: the explicit-deny AccessDeniedException message omits the 'on resource: <arn>' clause ===
AWS: Smithy CreateServer models AccessDeniedException (client, HTTP 403). The IAM denial sentence is request-derived and documented: 'User: <principal arn> is not authorized to perform: <service:Action> on resource: <resource arn> with an explicit deny in an identity-based policy'. For a user explicitly denied transfer:CreateServer the resource clause is the server wildcard the action is evaluated against, 'arn:aws:transfer:<region>:<account>:server/*'.
Emulator: the code and status are correct (403 AccessDeniedException) but the message drops the resource clause entirely: observed 'User: arn:aws:iam::000000000000:user/<user> is not authorized to perform: transfer:CreateServer with an explicit deny in an identity-based policy'. The renderer in src/state/authorization.rs::not_authorized formats only principal + action, and create_server.rs passes resource=None to explicit_deny, so no ARN is available to render.
Why: tooling and least-privilege regression tests parse that sentence to report WHICH resource was denied; with the clause missing they cannot attribute the denial, and a client comparing against AWS's message rule sees a different sentence for the same decision. (The related, already-filed cause 4(b) of open issue 20261022T202037Z-transfer-input-validation-authorization-and-reference-data-diverge.md concerns the IMPLICIT-deny sentence on other operations; the explicit-deny renderer and CreateServer's missing resource ARN are not covered there.)
Fix: the shared denial renderer (src/state/authorization.rs) must include the resource ARN clause, and CreateServer must pass the server-wildcard ARN it evaluates the action against to explicit_deny.
Traces: transfer.create-server-missing-permission-denied.
