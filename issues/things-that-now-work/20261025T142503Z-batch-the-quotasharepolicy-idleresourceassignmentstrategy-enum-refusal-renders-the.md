=== Cause 1 of 1: an idleResourceAssignmentStrategy outside the closed enum is refused with the emulator framework's constraint rendering instead of Batch's enum refusal inside its ClientException envelope ===
AWS: Smithy com.amazonaws.batch#CreateSchedulingPolicy (POST /v1/createschedulingpolicy, success 200) declares exactly ClientException (httpError 400) and ServerException (500). Its quotaSharePolicy member targets com.amazonaws.batch#QuotaSharePolicy, whose single member idleResourceAssignmentStrategy is required and targets com.amazonaws.batch#QuotaShareIdleResourceAssignmentStrategy — an enum whose ONLY value is FIFO (member doc: "Currently, only FIFO is supported"). So the closed set is modeled; the refusal TEXT is recorded behavior only and is a fixed per-rule constant wrapped in Batch's standard validation envelope: HTTP 400, error code ClientException, message 'Error executing request, Exception : Idle resource assignment strategy must be one of [FIFO]., RequestId: <request id>'. Fixed text of that message: 'Error executing request, Exception : Idle resource assignment strategy must be one of [FIFO]., RequestId: '. Variable parts: ONLY the trailing request id, which is the request id of that same response (the value the SDK surfaces as ResponseMetadata.RequestId). The rejected value ('STRICT' in the recording) does not appear in AWS's message at all — the message names the closed set it enforced, not the input.
Emulator: the 400 status and the ClientException code are correct (the check reaches and passes its code assertion and fails on the message), and the positive control — quotaSharePolicy={"idleResourceAssignmentStrategy": "FIFO"} created, described, listed, with no fairsharePolicy populated — passes. The message is instead the generic schema-constraint rendering of the emulator's validation framework: "1 validation error detected: Value '<rejected value>' at 'quotaSharePolicy.idleResourceAssignmentStrategy' failed to satisfy constraint: Member must satisfy enum value set: [FIFO]". Batch's 'Error executing request, Exception : ..., RequestId: ...' envelope is absent entirely, the service's own sentence is absent, and the response instead echoes the rejected input value and a member path AWS never reports for this refusal.
Why: the message is the only place Batch states WHICH rule fired, so a client that matches the known sentence, a log scraper that splits detail from request id by parsing the envelope, or a golden-file test over the error payload all diverge. The response also leaks the emulator's validation-framework phrasing and the caller's rejected value, inviting clients to parse a member-path/constraint format AWS does not emit for this API — and because the envelope is dropped, the request id AWS carries at the end of this message is not present in any form.
Fix: the refusal path for CreateSchedulingPolicy's quotaSharePolicy validation (the operation's handler at services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/create_scheduling_policy.rs, which today validates `name` and delegates policy-kind checks to crate::state::validate_policy_kinds and lets enum membership fall through to the shared schema validator) — enum membership on idleResourceAssignmentStrategy must be refused by the service's own validation, routed through the Batch ClientException envelope with the service's per-rule detail, rather than falling through to the generic constraint validator. This is the same construction the related issue above asks for on other Batch refusals, so a shared envelope/detail helper is the natural place.
