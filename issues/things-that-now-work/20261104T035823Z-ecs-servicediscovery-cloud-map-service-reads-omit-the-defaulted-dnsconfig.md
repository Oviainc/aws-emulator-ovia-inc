# Cloud Map service reads omit the defaulted DnsConfig.RoutingPolicy and a custom-health instance never initialises HEALTHY, so the UNHEALTHY-suppression discovery chain never converges

> _Note: this issue was identified against the code base at commit `c083bea380b29cc5238d586af0774e0d5864cbe3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetService

## Description
TWO independent, net-new root causes in the servicediscovery (Cloud Map) emulator, grounded in failing behavioral checks the suite lists under the ecs__servicediscovery heading. Each must be closed before this issue is submitted. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json.

Cause 1 of 2: a service created with a DnsConfig that omits RoutingPolicy is stored and read back WITHOUT RoutingPolicy, where AWS fills in the MULTIVALUE default.
AWS: Smithy CreateService -> Service{..., DnsConfig: DnsConfig{NamespaceId (deprecated), RoutingPolicy: RoutingPolicy enum [MULTIVALUE, WEIGHTED], DnsRecords (required)}}; GetService{Id (required)} -> Service. RoutingPolicy is optional on input and MULTIVALUE is the service default, so the member is always populated on the read path even when the caller never sent it; AWS likewise fills DnsConfig.NamespaceId from the service's namespace. Recorded behavior: GetService on a service created with only DnsConfig={'DnsRecords':[{'Type':'SRV','TTL':60}]} returns DnsConfig with RoutingPolicy='MULTIVALUE', the single SRV record, and NamespaceId set to the owning namespace.
Emulator: GetService answers 200 with a DnsConfig that has no RoutingPolicy member at all (the check raises KeyError: 'RoutingPolicy' indexing DnsConfig). The Service Type assertion (DNS_HTTP) before it passes, so the shape is otherwise reaching the client.
Why: a client that reads Service['DnsConfig']['RoutingPolicy'] to decide how records will be answered (and anything that round-trips a GetService result back into an update or an IaC diff) gets a KeyError where AWS always supplies the member, and cannot tell MULTIVALUE from WEIGHTED. Distinct from the open wire issue 20261029T203804Z-servicediscovery-cloud-map-namespace-service-and-operation-responses-omit.md, whose causes 3-5 are about DnsConfig being absent ENTIRELY on an HTTP-namespace service: here DnsConfig is present and only the defaulted members inside it are missing.
Fix: the DnsConfig projection in the Service serializer shared by CreateService/GetService/ListServices, plus the service record in the service's state — apply the MULTIVALUE default and the namespace back-fill at create time so every read path agrees.
Traces: ecs__servicediscovery.cloudmap-srv-service-defaults-to-multivalue-routing-and-type-dns-http.

Cause 2 of 2: an instance registered into a service that carries HealthCheckCustomConfig does not initialise to HEALTHY, so the whole custom-health discovery chain (HEALTHY -> UNHEALTHY suppression -> HealthStatus=ALL -> repair) never converges and the check exhausts its budget.
AWS: Smithy RegisterInstance{ServiceId (required), InstanceId (required), CreatorRequestId, Attributes (required)} documents AWS_INIT_HEALTH_STATUS as 'If the service configuration includes HealthCheckCustomConfig, you can optionally use AWS_INIT_HEALTH_STATUS to specify the initial status of the custom health check, HEALTHY or UNHEALTHY. If you don't specify a value for AWS_INIT_HEALTH_STATUS, the initial status is HEALTHY.' The recorded chain is: GetInstancesHealthStatus answers {<instanceId>: 'HEALTHY'} shortly after the register operation reaches SUCCESS; DiscoverInstances with no HealthStatus filter serves that instance; after UpdateInstanceCustomHealthStatus(Status='UNHEALTHY') both the default view and HealthStatus='HEALTHY' go empty while HealthStatus='ALL' still returns the instance with HealthStatus='UNHEALTHY'; setting it back to HEALTHY restores the default view.
Emulator: the check does not get through that chain inside its budget — it is reported as 'Check timed out after 60.0s' while polling. Hypothesis (the emulator's already-reported health behavior is that GetInstancesHealthStatus answers an 'UNKNOWN' placeholder - see cause 3 of the open issue 20261102T113941Z-servicediscovery-cloud-map-servicediscovery-8-net-new-behavioral-causes.md, which covers only the service WITHOUT a health config): the first poll, 'the custom health surface initialises the instance HEALTHY', can never be satisfied if a freshly registered instance of a HealthCheckCustomConfig service reports UNKNOWN instead of HEALTHY, which leaves every later step of the chain unreached.
Why: custom health checks are the only mechanism by which a non-Route-53-probed instance is taken out of discovery; if the initial status is not HEALTHY and/or DiscoverInstances does not filter on it, a client cannot drain an instance and cannot distinguish suppression from deregistration.
Fix: the custom-health state initialised by RegisterInstance for a service carrying HealthCheckCustomConfig (default HEALTHY, honouring AWS_INIT_HEALTH_STATUS when sent), the GetInstancesHealthStatus read of it, and the HealthStatus filter in DiscoverInstances (default and 'HEALTHY' hide an UNHEALTHY instance; 'ALL' returns it with HealthStatus='UNHEALTHY').
Traces: ecs__servicediscovery.cloudmap-unhealthy-custom-health-status-blocks-an-instance-from-discovery.
