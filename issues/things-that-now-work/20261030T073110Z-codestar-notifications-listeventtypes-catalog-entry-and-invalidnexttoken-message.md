# codestar-notifications ListEventTypes: catalog entry and InvalidNextToken message diverge from AWS

> _Note: this issue was identified against the code base at commit `905a16186afdeacb839ec937e7b07de764f3a136`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListEventTypes

## Description
Wire replay of simparity-wire-aws-v1 against the codestar-notifications emulator shows ListEventTypes answering HTTP 200/400 with the right shapes and the right error class, but with two distinct fidelity defects in what it publishes: the reference catalog it serves disagrees with the service's published catalog for one event type (both in that entry's name text and in its position in the published order), and the InvalidNextTokenException it raises carries the model's documentation sentence instead of the message AWS words for that error. This bundle has 2 causes; BOTH must be closed before submitting.

Cause 1 of 2: the ListEventTypes catalog publishes the CodeBuild 'build state: in progress' event type with the wrong EventTypeName and at the wrong position in the catalog order (fixtures codestar-notifications-catalog-list-event-types#task#1 and codestar-notifications-list-and-filter-rules#setup#3).
AWS: Smithy (services/service-com-amazonaws-codestarnotifications-codestarnotifications-20191015/smithy-model/com-amazonaws-codestarnotifications-codestarnotifications-20191015.json): ListEventTypes (POST /listEventTypes, 200) returns ListEventTypesResult{EventTypes: EventTypeBatch, NextToken}, and each EventTypeSummary carries EventTypeId (length 1..200, doc 'The system-generated ID of the event. For a complete list of event types and IDs, see ...concepts.html'), ServiceName ('The name of the service for which the event applies'), EventTypeName ('The name of the event') and ResourceType (length min 1, pattern ^([a-zA-Z0-9-])+$). The model constrains the members but does not enumerate the catalog, so the catalog's CONTENT and ORDER are recorded behavior only: the recording shows the CodeBuild in-progress event type published as {EventTypeId 'codebuild-project-build-state-in-progress', ServiceName 'CodeBuild', ResourceType 'Project', EventTypeName 'Build state: In-progress'} — the name's state word is HYPHENATED ('In-progress') — and shows it at catalog position 28 of the unfiltered listing, i.e. after the CodePipeline manual-approval entries, with 'codecommit-repository-pull-request-source-updated' at position 13. Every other catalog entry in the recording matches the emulator exactly; the whole divergence is this one entry's name text and its place in the published order.
Emulator: publishes the same id with EventTypeName 'Build state: In progress' (space, not hyphen) and places it at position 13 of the unfiltered listing, so the recorded entry is reported MISSING at index 28 and an EXTRA entry (the mis-spelled one) appears at index 13, with 'codepipeline-pipeline-manual-approval-succeeded' sitting at 28 and 'codecommit-repository-pull-request-source-updated' at 7. Status is 200 in both, and the handler reports the catalog verbatim in its stored order, so the defect is in the seeded catalog data, not the paging or filtering code (both of which replay clean).
Why: the event-type catalog is reference data clients consume directly — a console or a reconciler lists it, shows the EventTypeName to a user, and matches the id/name pair recorded from AWS. A caller that renders or asserts on the published name gets text AWS never emits, and because ListEventTypes is paginated over the catalog's own order with MaxResults/NextToken, an entry sitting at a different position changes which page an event type lands on: a client paging with MaxResults<=28 sees the CodeBuild in-progress type on a different page than AWS serves it on, and a client that caches by (page, index) mismatches. The same mis-spelled name is also what DescribeNotificationRule resolves a stored event-type id through, so the wrong text leaks into rule descriptions too.
Fix: the seeded reference data in the service's state layer (the EVENT_TYPE_CATALOG table that ListEventTypes reports and resolve_event_type looks up), not the handler: correct that entry's EventTypeName to AWS's hyphenated spelling and move it to the position the published catalog gives it, keeping the table's order the stable total order pages walk.

Source: services/service-com-amazonaws-codestarnotifications-codestarnotifications-20191015/src/state.rs line 558 (the catalog entry) and src/ops/list_event_types.rs lines 220-254 (reports the catalog in its stored order).

Cause 2 of 2: ListEventTypes answers an unparseable NextToken with InvalidNextTokenException carrying the model's doc sentence instead of AWS's message (fixture codestar-notifications-event-types-catalog#task#5).
AWS: Smithy: ListEventTypes models InvalidNextTokenException (errorKind client, httpError 400) with a single member Message (length min 1); the shape's DOC is 'The value for the enumeration token used in the request to return the next batch of the results is not valid.' — documentation of the condition, not the wire message. NextToken itself is pattern ^[\w/+=]+$. The message is recorded behavior only: AWS answers HTTP 400 with code InvalidNextTokenException and Message of the form fixed text 'Invalid nextToken parameter ' + the token exactly as submitted in the request + the fixed terminator '.'. The only variable part is the submitted token value; the particular token in the recording is request-derived, not part of the template.
Emulator: answers the correct 400 and the correct error code, but Message is the model's documentation sentence 'The value for the enumeration token used in the request to return the next batch of the results is not valid' (no trailing period, no echo of the offending token) — the hard-coded string in the handler's NextToken decode branch.
Why: the message is the only part of this error that tells a caller WHICH token was rejected. A client or operator debugging a paging loop that re-submits a stale or mangled NextToken gets no value back to correlate against the token it sent, and any test or log-scraper matching AWS's wording fails. ListNotificationRules models the same error and must use the same template so the two paging surfaces are consistent.
Fix: the ListEventTypes handler's NextToken decode branch (and the matching branch in ListNotificationRules): when the token fails to decode, raise InvalidNextTokenException (400) rendering 'Invalid nextToken parameter <the submitted NextToken>.' — fixed text either side of the request's own token value — instead of the modeled doc sentence.
