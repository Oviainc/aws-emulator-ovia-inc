# BackupSearch export/stop refusals: non-IAM RoleArn misclassified as ValidationException, and state-conflict messages do not follow AWS's templates (3 causes)

> _Note: this issue was identified against the code base at commit `048778663a26e363156c6db724999c4fb229af36`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartSearchResultExportJob

## Description
Three distinct root causes in the BackupSearch (sdkId BackupSearch, restJson1) emulator's refusal paths on the export-job and stop-job surface. Each cause must be closed before this issue is done. Related open issues carry no key for anything below: 20261022T200842Z-backupsearch-search-job-lifecycle-iam-authorization-tag-api.md covers the search-job terminal status, StopSearchJob idempotency on an already-STOPPED job, the tag-API not-found CODE, IAM authorization and EncryptionKeyArn resolution (not the conflict-message templates or RoleArn classification below), and 20261022T215802Z-backupsearch-refusal-fidelity-on-the-wire-not-found.md covers wire-corpus message rendering (regex anchors in the RoleArn pattern message, not-found text, TagResource 204) — neither addresses the error CODE chosen for a well-formed non-IAM-role RoleArn nor the two state-conflict message templates.

=== Cause 1 of 3: a well-formed ARN that is not an assumable IAM role is refused as ValidationException instead of AccessDeniedException ===
AWS: Smithy StartSearchResultExportJob (PUT /export-search-jobs) declares both AccessDeniedException (httpError 403, errorKind client) and ValidationException (httpError 400); RoleArn targets IamRoleArn (@length 20..2048, @pattern "^arn:(?:aws|aws-cn|aws-us-gov):iam::[a-z0-9-]+:role/(.+)$"). Recorded behavior shows the service does NOT refuse an ARN of this kind on input syntax: for a RoleArn that is a syntactically well-formed ARN but names no assumable role in the caller's account (recording used "arn:aws:s3:::not-an-iam-role-arn-xxxxxxxx"), the service attempts to assume the role and refuses with error code AccessDeniedException (403); the recorded message is the fixed text "Cross-account pass role is not allowed." (request-independent, so quoted here as the recorded example). The rule is the classification: a RoleArn the service cannot assume/pass is an authorization refusal (AccessDeniedException), not an input-validation refusal.
Emulator: the same call is refused with error code ValidationException (the request-validation layer rejects the member against the modeled @pattern before any role resolution runs), so the caller never sees the 403 AccessDeniedException AWS raises.
Why: callers branch on the error code. AccessDeniedException tells an operator to fix the role/trust policy or the pass-role permission — the standard remediation path, often routed to a different handler or alert than a 400 — while ValidationException says the request itself is malformed and is treated as terminal and non-actionable. Code written against AWS that catches AccessDeniedException around the export call does not catch the emulator's ValidationException, and the error escapes as an unhandled fault; least-privilege/pass-role test matrices are also inverted.
Fix: the StartSearchResultExportJob handler's RoleArn handling and the ordering of its request validation — resolve/assume the supplied RoleArn in the handler and serialize the modeled AccessDeniedException when it cannot be assumed, rather than letting the pattern check own every rejected RoleArn.
Traces: backupsearch.start-search-result-export-job-invalid-role-arn-rejected (replay: "AssertionError: expected AccessDeniedException, got code='ValidationException'"). Handler: services/service-com-amazonaws-backupsearch-cryobackupsearchservice/src/ops/start_search_result_export_job.rs and the shared request-validation layer.

=== Cause 2 of 3: the export-on-non-terminal-job refusal message does not follow the service's status-parameterized template ===
AWS: recorded behavior only — the Smithy model states no message text for ValidationException. The recordings show that StartSearchResultExportJob against a search job that has not reached a terminal state is refused 400 ValidationException with a fixed template whose only variable is the job's current status: "Export is only supported for search job with COMPLETED,STOPPED statuses. SearchJob has status <STATUS>. Please try again later" — recorded with both <STATUS>=CREATING and <STATUS>=RUNNING, which is what identifies it as a service template rather than one call's text (it names the allowed statuses and the observed status and carries no request id, identifier or timestamp). The template, with the job's status interpolated, is the requirement; the status/code (400 ValidationException) already match.
Emulator: same status and code, but an emulator-authored sentence built from the job identifier: "search job '<job-id>' is RUNNING; its results can only be exported once it is COMPLETED or STOPPED".
Why: ValidationException carries no structured detail, so the message is the entire machine- and human-readable description of why the export was refused; it reaches operator logs, user-facing surfaces and retry logic that keys off the "Please try again later" / allowed-status wording. A caller that reads or matches the service's template sees a different string, and the emulator additionally echoes the job identifier back where AWS does not.
Fix: the StartSearchResultExportJob handler's status-gate error construction — render the service's template naming the allowed statuses (COMPLETED,STOPPED) and the job's current status, not a per-request sentence.
Traces: backupsearch.start-search-result-export-job-immediately-after-start-rejected (replay: expected one of the CREATING/RUNNING forms of the template, got "search job '1fa8144f-...' is RUNNING; its results can only be exported once it is COMPLETED or STOPPED").

=== Cause 3 of 3: the StopSearchJob conflict message on a FAILED job does not follow the service's state-parameterized template ===
AWS: recorded behavior only — Smithy StopSearchJob (PUT /search-jobs/{SearchJobIdentifier}/actions/cancel, @idempotent) declares ConflictException (httpError 409) and the model states no message text. The recordings show that stopping a job in a non-stoppable terminal state is refused 409 ConflictException with the state-parameterized template "SearchJob can not be stopped since it is in <STATE> state. Please try again later" — recorded here with <STATE>=FAILED. The template with the job's state interpolated is the requirement; the 409/ConflictException classification already matches.
Emulator: same status and code, but the message is "search job '<job-id>' is FAILED and can no longer be stopped" — a different sentence that also echoes the identifier AWS does not include.
Why: same consumer as Cause 2 — the conflict message is the only explanation a caller gets for a refused stop, and clients that surface or match the service's wording (including the "Please try again later" suffix) see a string AWS never emits.
Fix: the StopSearchJob handler's conflict error construction — render the service's template naming the job's state.
Traces: backupsearch.e2e-search-job-tag-lifecycle (this check is listed under the open lifecycle issue's trace ids for the earlier COMPLETED-vs-FAILED cause, which has since advanced; the replay now fails later in the same check, at this message assertion, and the replay key is not carried by that issue). Handler: services/service-com-amazonaws-backupsearch-cryobackupsearchservice/src/ops/stop_search_job.rs.
