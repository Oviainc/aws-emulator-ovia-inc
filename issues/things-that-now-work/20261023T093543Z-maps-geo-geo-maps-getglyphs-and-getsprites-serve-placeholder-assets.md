# Geo Maps GetGlyphs and GetSprites serve placeholder assets with wrong payload, Content-Type and no S3 object headers

> _Note: this issue was identified against the code base at commit `2e4907a2bf61bceaa5da57e6115b53662c30dcb9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSprites

## Description
The Geo Maps static-asset operations (GetGlyphs, GetSprites) answer 200 but return synthesized placeholder bodies and drop the object-store response headers the recordings carry. Four distinct causes, all on service maps.geo.

Cause 1 of 4: GetGlyphs returns a body that is not the requested glyph range, and omits the object headers.
  AWS: Smithy (com-amazonaws-geomaps-mapsservice) GetGlyphs GET /v2/glyphs/{FontStack}/{FontUnicodeRange}, FontStack @length max 1000 required, FontUnicodeRange @pattern ^[0-9]+-[0-9]+\.pbf$ required; output is a @httpPayload Blob plus Content-Type/Cache-Control/ETag headers. The model does not state the body encoding, so recorded behavior only: the recording returns a glyph PBF of 74786 bytes with Content-Type 'binary/octet-stream' and the asset-delivery headers x-amz-version-id and x-amz-server-side-encryption: AES256.
  Emulator: 200 with a 121491-byte body (sha256 7170b45e... vs recorded 73b6ca0b...), Content-Type 'application/octet-stream', and neither x-amz-version-id nor x-amz-server-side-encryption present. The same body is produced for every fontstack/range in the fixture, so the payload is a constant placeholder rather than a per-range glyph blob.
  Why: a MapLibre/GL client fetches glyph ranges and parses them as SDF glyph protobufs for the fontstack it asked for; a constant placeholder of the wrong length yields missing or wrong label glyphs, and the wrong Content-Type pushes clients that branch on it (binary/octet-stream vs application/octet-stream) down a different decode path. Clients and caches that key on x-amz-version-id / rely on the SSE header see an asset served unlike the real endpoint.
  Fix: the GetGlyphs handler and its response serializer in the geo-maps service crate — emit a glyph payload derived from the requested FontStack/FontUnicodeRange, set Content-Type 'binary/octet-stream', and add the x-amz-version-id and x-amz-server-side-encryption response headers.
  Traces: geo-maps-glyphs-fontstack-unicode-ranges#task#1 (cluster also covers task#2, task#3 and geo-maps-vector-basemap-style-workflow#task#4).

Cause 2 of 4: GetSprites for the PNG sheet returns a tiny image with the wrong Content-Type and no object headers.
  AWS: Smithy GetSprites GET /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName}, FileName @pattern ^sprites(@2x)?\.(png|json)$; output @httpPayload Blob + Content-Type/Cache-Control/ETag. Recorded behavior only: the sprite sheet comes back as 121655 bytes with Content-Type 'binary/octet-stream' and x-amz-version-id plus x-amz-server-side-encryption: AES256.
  Emulator: 200 with a 1519-byte body (sha256 33798f47... vs recorded f0d727b2...), Content-Type 'image/png', and both x-amz-* headers absent — i.e. a stub image, not a sprite atlas, for every style/color-scheme/variant.
  Why: the sheet must be large enough to contain the icons the accompanying sprites.json manifest indexes by x/y/width/height; a 1519-byte stub means every icon lookup samples empty pixels, so all map symbols render blank.
  Fix: the GetSprites handler/serializer for the .png FileName branch — serve a sprite atlas consistent with the manifest, with Content-Type 'binary/octet-stream' and the object headers.
  Traces: geo-maps-sprites-style-color-variants#task#1 (cluster also covers task#2 and geo-maps-vector-basemap-style-workflow#task#2).

Cause 3 of 4: GetSprites for sprites.json returns no icon manifest at all.
  AWS: Smithy GetSprites, FileName @pattern allows sprites.json / sprites@2x.json. Recorded behavior only: the .json FileName returns a JSON object whose keys are icon names, each mapping to {width, height, x, y, pixelRatio} — e.g. accident {32,32,0,0,1}, accommodation {21,21,32,0,1}, airport {21,21,53,0,1}, plus the marker_* and shield-* families (several hundred entries).
  Emulator: 200, but every manifest key is missing (replay reports $.accident, $.accommodation, $.airport, $.attraction, ... $.marker.width/height/x/y, $.shield-* all 'missing (got None)'), so the body carries no icon index.
  Why: a style descriptor points its 'sprite' at this manifest; with no entries a client cannot resolve any icon-image name, so every symbol layer silently renders without an icon. This is not a value difference, it is an absent response body shape.
  Fix: the GetSprites handler's .json branch — generate/serve the icon manifest for the requested Style/ColorScheme/Variant keyed by icon name with width/height/x/y/pixelRatio members.
  Traces: geo-maps-sprites-style-color-variants#task#3.

Cause 4 of 4: the same empty sprites.json manifest on the basemap-style workflow, where the manifest divergence also drops the object headers.
  AWS: as cause 3; recorded response additionally carries Content-Type, x-amz-version-id and x-amz-server-side-encryption: AES256.
  Emulator: 200 with no manifest entries and the x-amz-* headers missing, for the Style/ColorScheme/Variant used by the vector basemap workflow — so the gap is not specific to one style's fixture data.
  Why: a client walking the full style -> sprite -> glyph chain gets a style it can parse but no icons, so the whole workflow silently degrades instead of failing loudly.
  Fix: same component as cause 3, plus the shared response-header path for GetSprites.
  Traces: geo-maps-vector-basemap-style-workflow#task#3.
