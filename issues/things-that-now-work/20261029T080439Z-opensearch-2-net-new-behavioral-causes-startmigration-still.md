=== Cause 1 of 2: StartMigration does not enforce the OpenSearch Serverless collection-ARN rule on migrationOptions.source.datasourceArn — a domain ARN is accepted, a PENDING migration record is minted, and this holds under concurrent requests on independent applications ===
AWS: Smithy com.amazonaws.opensearch#StartMigration — POST /2021-01-01/opensearch/app-migrations, success 200, output {migrationId, status}; input applicationId (@required, pattern ^[a-z0-9]{3,30}$), migrationOptions (@required) and clientToken. The model does not express the source constraint: MigrationSource.datasourceArn targets com.amazonaws.opensearch#ARN, @length {min 20, max 2048} with pattern '.*', so the modeled constraint is length-only; the narrower rule — the source must be an OpenSearch Serverless (aoss) COLLECTION ARN — is server-side and recorded behavior only. StartMigration DOES model ValidationException (client, HTTP 400), and the recording shows AWS refusing a non-collection source with it, per request, before any migration record exists: status 400, code `ValidationException`, message `1 validation error detected: Value '<datasourceArn>' at 'migrationOptions.source.datasourceArn' failed to satisfy constraint: Member must satisfy regular expression pattern: arn:aws[a-z\-]*:aoss:[a-z0-9\-]+:[0-9]{12}:collection/[a-z0-9]+`. Message template — FIXED text: `1 validation error detected: Value '` and `' at 'migrationOptions.source.datasourceArn' failed to satisfy constraint: Member must satisfy regular expression pattern: arn:aws[a-z\-]*:aoss:[a-z0-9\-]+:[0-9]{12}:collection/[a-z0-9]+` (the member path and the pattern are fixed text, never per-run values); VARIABLE part: the single-quoted value, which is the rejected datasourceArn copied verbatim from the request. Because the refusal is per-request validation, two simultaneous StartMigration calls on two different applications are each refused independently, and ListMigrations(applicationId=...) (GET /2021-01-01/opensearch/app-migrations, output migrations) then returns an EMPTY list for both — a refused start is never half-applied and never attributed to a neighbouring request.
Emulator: both concurrent calls SUCCEED. Replay shows HTTP 200 with body `{"migrationId": "mig-<id>", "status": "PENDING"}` for a datasourceArn of the form `arn:aws:es:<region>:<account>:domain/<name>`, on two applications that were each asserted ATTACHED first (so the expected refusal cannot be confused with a missing-attachment ResourceNotFoundException). No ValidationException is produced at any concurrency, and a migration record is persisted, so the "no migration record after a rejected start" invariant is violated too.
Why: a client relying on AWS's behavior gets a 200 and a migration id for a migration that can never run, instead of an up-front 400 naming the offending member. Negative-path code that catches ValidationException and reads the member path out of the message to report which field was wrong never fires, so pointing a migration at an `es` domain instead of an `aoss` collection surfaces as a phantom PENDING job. ListMigrations then reports a record AWS would never have created, so quota/idempotency accounting diverges from AWS for every subsequent read.
Fix: StartMigration's input validation in its handler — reject any datasourceArn that does not match the aoss collection-ARN pattern with the modeled ValidationException (400) carrying the message template above, and do so BEFORE a migration record is minted or inserted into state, so a refused start leaves the application with no migration. The existing generic ARN-shape guard remains as the length/shape check; the collection-ARN rule is an additional, narrower one that must be applied per request (not behind any shared/once-only path), since the check issues the two starts simultaneously.
Traces: opensearch.concurrent-start-migration-independent-domains. Handler cited by the related open issue: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/start_migration.rs (the `is_arn`/`malformed_arn` guard, then the record mint/insert).

=== Cause 2 of 2: CloudFormation cannot create a stack whose AWS::OpenSearchService::Domain carries AccessPolicies as a policy-document object; with OnFailure=DELETE the stack is destroyed, so the StackCreateComplete waiter terminates on ValidationError and the CFN-deployed index CRUD surface is never reachable ===
AWS: Smithy com.amazonaws.opensearch#CreateDomain — POST /2021-01-01/opensearch/domain, success 200, output DomainStatus; member AccessPolicies targets PolicyDocument, a STRING with @length {min 0, max 102400} and @pattern '.*'; modeled client errors ValidationException (400), BaseException (400, defaulted), InvalidTypeException / LimitExceededException / ResourceAlreadyExistsException / DisabledOperationException (409). On AWS the AWS::OpenSearchService::Domain resource handler accepts AccessPolicies written the normal CloudFormation way — a nested policy-document OBJECT containing intrinsics (!Sub / !Ref / !GetAtt) — resolves the intrinsics, serializes the document to a JSON string and calls CreateDomain with that string. A stack declaring DomainName, ClusterConfig, EBSOptions and an object AccessPolicies therefore reaches CREATE_COMPLETE, DescribeStacks publishes its Outputs with resolved OutputValues, and the domain then answers the control-plane index APIs: CreateIndex (POST /2021-01-01/opensearch/domain/{DomainName}/index, output Status required, enum IndexStatus -> 'CREATED'), GetIndex (GET .../index/{IndexName}, output IndexSchema document), UpdateIndex -> 'UPDATED', DeleteIndex -> 'DELETED', and afterwards GetIndex/UpdateIndex on the deleted index refuse with ResourceNotFoundException (409, modeled on both). Recorded behavior only for CloudFormation's wrapper text, in AWS's documented resource-failure shape `Resource handler returned message: "<service message> (Service: OpenSearch, Status Code: <status>, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: <code>)` — that frame is fixed text, while <service message>, <status>, <id>, <token> and <code> are per-request values.
Emulator: the Domain resource fails at create, and because this check creates the stack with OnFailure='DELETE' the stack is removed, so every later DescribeStacks on it is refused. The StackCreateComplete waiter terminates with `botocore.exceptions.WaiterError: Waiter StackCreateComplete failed: Waiter encountered a terminal failure state: Matched expected service error code: ValidationError` — i.e. CloudFormation answers DescribeStacks with error code `ValidationError` and the message `Stack with id <stack-name> does not exist` (fixed text `Stack with id ` + ` does not exist`; the stack name is the request's value). The create failure itself is the OpenSearch CreateDomain refusal HTTP 400 with the service message `Invalid request provided: expected string, got object start`, surfaced as the resource reason `Resource handler returned message: "Invalid request provided: expected string, got object start (Service: OpenSearch, Status Code: 400, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)`. In that message `Invalid request provided: expected string, got object start` is entirely FIXED deserializer text — it names no member and carries no value from the request; only Request ID and RequestToken vary per run, so this is a template-level divergence, not a per-run value difference. Two things diverge: (a) a stack AWS creates successfully never creates at all, and (b) the refusal is reported with the request deserializer's internal parser text instead of a modeled client error (ValidationException/BaseException, 400) whose message names `AccessPolicies` and the expected type.
Why: a client relying on AWS's behavior cannot deploy an OpenSearch domain through infrastructure-as-code whenever the domain has a resource policy — the normal case, since AccessPolicies is how a domain is made reachable. With OnFailure=DELETE the stack is gone, so the caller's own readiness poll gets `ValidationError: Stack with id <name> does not exist` rather than a stack-level failure reason it can log, and no Outputs (here DomainArn from !GetAtt Domain.Arn) are ever published. Everything behind the deploy is unverifiable: that a CFN-deployed domain accepts CreateIndex with Status=CREATED, that GetIndex reflects the created `title: {type: text}` mapping, that UpdateIndex merges `body: {type: keyword}` while keeping the original field, that DeleteIndex answers DELETED and that GetIndex/UpdateIndex then answer ResourceNotFoundException. An IaC user also reads the raw parser text as a fault in their own template and cannot tell which property is wrong.
Fix: the CloudFormation AWS::OpenSearchService::Domain resource provisioner's property-to-request mapping — after resolving intrinsics, a policy-document property must be serialized to a JSON string before it is placed in the CreateDomain body, so every forwarded member matches its modeled type. Secondarily, the OpenSearch CreateDomain input deserializer/handler must report a genuine type mismatch through a modeled client error whose message names the member and the expected type, instead of emitting internal parser text as the service message.
Traces: opensearch.deploy-domain-cfn-index-operations-behave.
