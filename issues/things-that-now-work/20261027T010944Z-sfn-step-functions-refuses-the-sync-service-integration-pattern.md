# Step Functions refuses the `.sync` service-integration pattern outright: a Task on arn:aws:states:::athena:startQueryExecution.sync fails the execution with States.Runtime, so StopExecution can never propagate an abort to the downstream query

> _Note: this issue was identified against the code base at commit `c80575fbbaf36d0a7150291b1a3e8f1ca5d00b60`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
This issue carries ONE root cause. A fixer should re-replay the single check id listed in trace_ids before submitting.

Cause 1 of 1: the sfn execution interpreter has a dedicated refusal for the `.sync` (run-a-job) service-integration PATTERN. Any Task state whose `Resource` ends in `.sync` is terminated immediately with `States.Runtime` instead of being invoked, parked and polled, so the whole class of run-a-job integrations — and anything that depends on an execution being parked inside one, such as StopExecution propagating the abort to the downstream resource — is unreachable. Failing check: athena__s3__sfn.xsvc-sfn-1-athena-sync-stop-execution-cancels-the-running-query.

AWS: a Task whose `Resource` is `arn:aws:states:::<service>:<action>.sync` is invoked by Step Functions under the execution role; Step Functions records a `TaskSubmitted` history event whose `taskSubmittedEventDetails.output` carries the downstream job's identifier (for Athena, `{"QueryExecutionId": "<id>"}`), leaves the state PARKED while the job runs (DescribeExecution keeps reporting `status=RUNNING`), and only then emits `TaskSucceeded`/`TaskFailed`. While parked, StopExecution(executionArn, error, cause) must (a) return 200 with `stopDate`, (b) propagate the abort across the service boundary — for `athena:startQueryExecution.sync` it calls athena:StopQueryExecution so the query ends `Status.State == "CANCELLED"` with no `AthenaError` member — and (c) leave DescribeExecution reporting `status="ABORTED"` with `error`/`cause` echoing exactly the values passed to StopExecution, and a history whose LAST event is `ExecutionAborted` and which contains neither `TaskSucceeded` nor `TaskFailed`. Smithy (com.amazonaws.sfn): StopExecution input `executionArn` (required), `error` (SensitiveError, @length 0..256), `cause` (SensitiveCause, @length 0..32768); output `stopDate` (required); DescribeExecution output carries the required `status` (ExecutionStatus enum, which includes ABORTED) plus optional `error`/`cause`. The ASL integration catalogue and the `.sync` pattern semantics are not in the Smithy model, so those parts are recorded behavior only (the check's control legs succeed on real AWS).

Emulator: StartExecution accepts the definition, then the execution terminates at once with `status="FAILED"`, `error="States.Runtime"` and `cause="state '<StateName>': '<Resource ARN>' asks for the 'sync' integration pattern, whose outcome arrives after the call that starts it, so nothing was run for it"` — observed as `state 'Query': 'arn:aws:states:::athena:startQueryExecution.sync' asks for the 'sync' integration pattern, whose outcome arrives after the call that starts it, so nothing was run for it`. In that message the fixed text is the emulator's own invented sentence (`asks for the 'sync' integration pattern, whose outcome arrives after the call that starts it, so nothing was run for it`); the only variable parts are the state name and the Resource ARN, both taken from the submitted definition. AWS emits no such error name or message for a valid `.sync` Task: `States.Runtime` here is wholly spurious. No downstream job is started, so no `TaskSubmitted` event and no `QueryExecutionId` ever appear, the execution is never RUNNING-while-parked, and StopExecution is never exercised against a parked task at all.

Note: this is NOT the same refusal as the one already filed in the open issue 20261025T112726Z-sfn-step-functions-does-not-execute-optimized-athena-service.md. That issue records the message `state '<Name>' invokes '<ARN>', a service integration this emulator does not make, so nothing was run for it` (per-integration dispatch table) and explicitly states that this check is "already filed against the unimplemented GetExecutionHistory stub and is not bundled here" — that is no longer what this check hits, and no open issue carries this check's replay key. It is also distinct from 20261024T043150Z-sfn-step-functions-interpreter-does-not-run-the-workflow.md (whose message is `state '<Name>' is of type 'Task', which this emulator does not execute`). The text quoted above names the `.sync` INTEGRATION PATTERN, i.e. a separate guard that fires before any per-integration dispatch, and it hides a second behaviour no other issue covers: the abort propagation performed by StopExecution on a parked `.sync` task.

Why: a client cannot use any run-a-job (`.sync`) integration from Step Functions, which is the normal way to orchestrate long-running work (Athena queries, Glue jobs, Batch jobs, ECS tasks, nested state machines). Workflows AWS runs to SUCCEEDED are reported FAILED with a non-existent runtime error, so callers branching on `error`/`cause` see a bogus `States.Runtime` instead of a success output or a `States.TaskFailed` carrying the downstream service's error. Worse, cancellation is silently lost: on AWS stopping the execution cancels the downstream job, while here there is no parked task to stop, so a client that aborts a workflow has no way to observe — or achieve — the downstream cancellation, and the job would keep running and keep billing.

Fix: the sfn execution interpreter's Task-state integration-pattern handling — the `.sync` branch of the `Resource` resolver must invoke the integration, emit `TaskSubmitted` carrying the downstream job id, park the state and poll the downstream job to terminal state, and the StopExecution path must cancel the in-flight downstream job of a parked `.sync` task before recording `ExecutionAborted` with the caller's `error`/`cause`. The sfn control plane is not implicated: CreateStateMachine already accepts the definition.

Traces: athena__s3__sfn.xsvc-sfn-1-athena-sync-stop-execution-cancels-the-running-query. Attribution note: the check id's leading token is the composite group `athena__s3__sfn`, which is not a service token; the divergence is raised and observed entirely inside sfn (the execution is terminated before Athena is ever called), and the sibling checks of this same group are already filed under service `sfn`, so this issue is filed as `sfn`.
