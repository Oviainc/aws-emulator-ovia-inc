# VerifiedPermissions response fidelity: GetSchema drops definition and reformats the schema text, and error field path/message are not AWS's

> _Note: this issue was identified against the code base at commit `7f205ee96657d4151f96c4aa7296372f34590a63`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSchema

## Description
THREE distinct causes in service-com-amazonaws-verifiedpermissions-verifiedpermissions, sharing one fault: the emulator returns the right HTTP status and error code but builds the response PAYLOAD itself instead of reproducing the fields AWS populates — a document it must pass through verbatim, a missing output member, a wrongly anchored ValidationException field path, and a not-found message that does not identify the resource from the request. All three must be closed before this issue is submitted.

Cause 1 of 3: GetSchema re-serializes the stored schema document and omits the `definition` member. AWS: Smithy — PutSchema takes definition: SchemaDefinition, a union whose only arm is cedarJson ("A JSON string representation of the schema..."); GetSchemaOutput requires policyStoreId, schema (SchemaJson, length min 1, sensitive), createdDate, lastUpdatedDate plus namespaces. `schema` is an opaque STRING carrying the document the caller submitted, so the service hands back the same text. The recording shows exactly that — the compact text submitted via cedarJson, '{"PhotoApp":{"entityTypes":{"Employee":{"shape":{"type":"Record","attributes":{"jobLevel":{"type":"Long"}}}}},"actions":{"viewDocument":{"appliesTo":{"principalTypes":["Employee"],"resourceTypes":["Employee"]}}}}}' — and ALSO a top-level `definition` member, {'cedarJson': <that same string>}, alongside `schema`. The on-disk model's GetSchemaOutput does not declare `definition`, so for that member this is recorded behavior only (the recording is the ground truth for the wire; the checked-in model predates it). Emulator: 200, but $.schema is the document parsed and re-encoded by a JSON encoder that inserts a space after every ':' and ',' ('{"PhotoApp": {"entityTypes": {"Employee": {"shape": {"type": "Record", ... }' ), and $.definition is absent entirely. Why: the schema text is opaque to the service, so a client that round-trips PutSchema -> GetSchema and compares, hashes, checksums, or diffs the document sees a change it never made — config-drift detectors and IaC providers report a permanent diff and may re-PUT on every run. A client on an SDK that reads definition.cedarJson gets nothing at all, i.e. no schema. Fix: GetSchema's handler/serializer and the state that holds the schema — store and return the submitted cedarJson string verbatim rather than parse-and-re-encode it, and emit the `definition` member next to `schema`. Traces: verifiedpermissions-schema-management#task#3 (same cluster also covers verifiedpermissions-schema-management#task#5).

Cause 2 of 3: CreatePolicyTemplate's ValidationException anchors fieldList[0].path at '/statement' instead of AWS's '/template/statement'. AWS: Smithy — ValidationException(400) carries fieldList of ValidationExceptionField{path [required], message [required]}; `path` is documented as "The path to the specific element that Verified Permissions found to be not valid." CreatePolicyTemplate(statement [required], policyStoreId [required], description, name) models ValidationException(400); the recording of a static (non-template) statement submitted to CreatePolicyTemplate is 400 with fieldList[0].path = '/template/statement' and message 'expected a template, got a static policy'. Emulator: the 400 status, the error code and the top-level message all match, but fieldList[0].path = '/statement'. The emulator's fieldList[0].message ('the policy template statement is not valid Cedar: expected a template, got a static policy' vs the recorded 'expected a template, got a static policy') is reported as an EXAMPLE difference only and is not part of this requirement. Why: clients, consoles and IaC providers key remediation and field highlighting off `path` to point at the offending request member; a path AWS never emits fails to match, so the validation failure is surfaced as un-attributed. The already-open issue "VerifiedPermissions control plane: template-linked CreatePolicy, UpdatePolicy, and STRICT-mode ValidationException fieldList all diverge" reports the same CLASS of defect for CreatePolicy's schema-validation fieldList; it does not cover CreatePolicyTemplate and carries no wire replay key for this step, so this cause is net-new. Fix: the CreatePolicyTemplate validation path that constructs ValidationExceptionField — anchor `path` at the element path AWS uses for a policy-template statement. Traces: verifiedpermissions-token-authorization-error-paths#task#5.

Cause 3 of 3: ResourceNotFoundException's message is a constant and does not identify the resource named in the request. AWS: Smithy — ResourceNotFoundException(404) requires message, resourceId ("The unique ID of the resource referenced in the failed request") and resourceType (ResourceType enum). IsAuthorized models ResourceNotFoundException(404). In the recording the message is BUILT FROM THE REQUEST — "Policy store with id 'PSNONEXISTENT00000000' not found", naming the resource kind and echoing the policyStoreId that was sent — so the rule, not the sentence, is the requirement: the message states which resource kind was missing and the id taken from the request. Status 404, resourceId, resourceType and __type all matched. Emulator: answers 404 with the fixed string 'Resource not found' for every not-found, whatever resource or id was requested; the shared construction is crate::state::policy_store_reference(..).not_found() in the service's state module (used e.g. by src/ops/delete_policy.rs:123). Why: operators and client-side diagnostics read the message to learn WHICH id of several in flight did not exist; a constant string erases that, and assertions on a message that names the id (a common pattern when several stores/policies are probed in one flow) fail against the emulator. Fix: the shared not-found construction in the service's state module — render the message from the resource kind and the requested id, keeping resourceId/resourceType as they already are. Traces: verifiedpermissions-authorization-decisions#task#6.
