# EKS read-only catalog operations serve an incomplete static catalog (3 causes)

> _Note: this issue was identified against the code base at commit `6d7833292dd9d4a45d8e52e2aa7ee7e5a822f7f5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeClusterVersions

## Description
Replaying the wire corpus (simparity-wire-aws-v1) against the EKS emulator (service crate services/service-com-amazonaws-eks-awswesleyfrontend) shows that the service's read-only CATALOG operations answer HTTP 200 but with catalog content that does not match what AWS serves: entries the recording contains are absent from the emulator's response, or present with a different structure. These are unauthenticated-style discovery calls with no request state behind them, so the gap is entirely in the catalog data the handlers serve. THREE distinct causes are bundled here; the issue is NOT complete until all three are closed.

Cause 1 of 3 - DescribeClusterVersions returns no version entries at all.
AWS: Smithy (com-amazonaws-eks-awswesleyfrontend): DescribeClusterVersions is GET /cluster-versions, success code 200, output DescribeClusterVersionsResponse{nextToken, clusterVersions: ClusterVersionList}, @paginated(items: clusterVersions); each element is a ClusterVersionInformation with members clusterVersion, clusterType, defaultPlatformVersion, defaultVersion (boolean, default false), releaseDate / endOfStandardSupportDate / endOfExtendedSupportDate (Timestamp), status (deprecated since 2025-02-15) and versionStatus (enum), kubernetesPatchVersion, controlPlaneScalingTiers (ControlPlaneScalingTierList, @length 0..10) and controlPlaneComponentConfig. The only modeled errors are InvalidParameterException/InvalidRequestException (400) and ServerException (500), so an unfiltered call always succeeds with the catalog. Recorded behavior: 200 with a populated list of version entries, each element fully populated (recorded example element: clusterVersion '1.37', clusterType 'eks', defaultPlatformVersion 'eks.4', defaultVersion false, versionStatus/status STANDARD_SUPPORT, kubernetesPatchVersion '1.37.0', plus controlPlaneScalingTiers entries carrying tierName, apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb and controlPlaneComponentConfigOverrides). The specific version numbers, platform versions and support dates are catalog values that move over time and are examples, not requirements; the requirement is that an unfiltered DescribeClusterVersions returns the catalog's version entries with those modeled members populated.
Emulator: answers 200, but every element position the recording holds is absent - the replay reports $.clusterVersions[0] through $.clusterVersions[7] all as 'missing' (expected an object, got nothing), i.e. the emulator serves an empty or near-empty clusterVersions list.
Why: version discovery is the first call in almost every EKS provisioning flow - a client picks a supported clusterVersion (or the default, or checks endOfStandardSupportDate) before CreateCluster. Against this emulator the list is empty, so such a client either crashes on an empty selection or concludes that no Kubernetes version is supported and never attempts a create; upgrade-planning code keyed on versionStatus/support dates has nothing to read.
Fix: the DescribeClusterVersions handler in the eks crate and the version-catalog seed data it reads from (the static catalog must be populated and projected into ClusterVersionInformation, honouring the clusterType/defaultOnly/includeAll/versionStatus query filters and the nextToken/maxResults pagination contract).
Traces: eks-catalog-describe-cluster-versions#task#1.

Cause 2 of 3 - DescribeClusterVersions entries, where present, are not the recorded ClusterVersionInformation structure.
AWS: same Smithy signature and element shape as cause 1. Recorded behavior: the discovery fixture reads element $.clusterVersions[0] and finds a complete ClusterVersionInformation, including the nested controlPlaneScalingTiers tier objects (tierName, apiRequestConcurrency, podSchedulingRatePerSecond, clusterDatabaseSizeGb, controlPlaneComponentConfigOverrides with kubeApiServerConfig / kubeSchedulerConfig / kubeControllerManagerConfig sub-structures) and kubernetesPatchVersion plus the three support-date timestamps.
Emulator: answers 200 and does return an element at index 0, but it is a value_mismatch against the recorded element - the object the emulator serves is not the recorded ClusterVersionInformation (members such as kubernetesPatchVersion, the support-date timestamps and the controlPlaneScalingTiers sub-tree are not reproduced). Hypothesis: this is the same catalog-data gap as cause 1 observed through a fixture that asserts on element content rather than element presence, so the two may close together - but it is reported as its own divergence cluster with its own replay key and must be re-replayed separately.
Why: a client that reads a version's scaling tiers or patch version off the catalog (control-plane sizing, patch-level reporting) gets absent or wrongly-shaped members behind a 200, which is worse than an error: the call appears to succeed and the client silently proceeds with missing capability data.
Fix: same component as cause 1 - the DescribeClusterVersions handler and its catalog seed data, specifically the per-version nested controlPlaneScalingTiers / controlPlaneComponentConfig projection.
Traces: eks-eks-catalog-read-only-discovery#task#1.

Cause 3 of 3 - ListAccessPolicies omits most of the EKS-managed cluster access policies.
AWS: Smithy: ListAccessPolicies is GET /access-policies, success code 200, output ListAccessPoliciesResponse{accessPolicies: AccessPoliciesList, nextToken}, @paginated(items: accessPolicies); each element is AccessPolicy{name, arn}. Its ONLY modeled error is ServerException (500), so a well-formed call always returns the full managed set - this is a fixed, account-independent catalog of EKS-managed policies whose ARNs have the form arn:aws:eks::aws:cluster-access-policy/<name>. Recorded behavior: 200 with the managed set including AmazonEKSServiceAccountImpersonationPolicy, AmazonEMRClusterPolicy, AmazonEMRJobPolicy, AmazonSagemakerHyperpodClusterPolicy, AmazonSagemakerHyperpodControllerPolicy, AmazonSagemakerHyperpodInferencePolicy, AmazonSagemakerHyperpodSpacePolicy and AmazonSagemakerHyperpodSpaceTemplatePolicy, each with its matching name and arn.
Emulator: answers 200 with a strictly smaller catalog - looked up by arn, every one of the policies listed above resolves to None in the emulator's accessPolicies list, so only a subset of the managed policies is served.
Why: AssociateAccessPolicy requires a policyArn, and clients (and infra tooling for the EMR-on-EKS and SageMaker HyperPod integrations) discover that ARN by listing access policies and matching on name. Against this emulator the lookup returns nothing for those policies, so the client either fails at discovery or hands AssociateAccessPolicy an ARN it just failed to confirm - an access-management flow AWS supports cannot be exercised at all.
Why this is net-new: the open issues on this service (notably 'EKS control-plane operations answer 501 NotImplemented or validate in the wrong order' and 'EKS access-entry not-found refusals do not name the missing cluster') cover control-plane mutations and not-found refusals; neither carries the replay keys of these three read-only catalog clusters.
Fix: the ListAccessPolicies handler in the eks crate and the static managed-access-policy catalog it serves (complete the policy list; keep name/arn consistent and honour maxResults/nextToken).
Traces: eks-catalog-list-access-policies#task#1.
