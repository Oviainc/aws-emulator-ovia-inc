# batch: ListJobsByConsumableResource keeps returning a job after it goes terminal

> _Note: this issue was identified against the code base at commit `281440c6fd2fb349634dcc135fbec4e15edad452`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Resolution
Fixed (cause 2 of the two this report was filed with). A Batch job requires a consumable resource only while it can still consume it: reaching a terminal `JobStatus` releases every consumable-resource requirement it carried — whatever took it there (the clock, `CancelJob`, `TerminateJob`, the deletion of its queue) — so `ListJobsByConsumableResource`, whose result set is "Batch jobs that require a specific consumable resource", selects only jobs that are not terminal and the caller's `JOB_STATUS`/`JOB_NAME` filters narrow that set afterwards. `services/service-com-amazonaws-batch-awsbatchv20160810/src/state.rs` carries the release rule as `requires_consumable_resources`, and `.../src/ops/list_jobs_by_consumable_resource.rs` selects through it; the job record is untouched, so `DescribeJobs` still replays its terminal status and the `consumableResourceProperties` it was submitted with. Covered by `.../tests/all/consumable_resource_release.rs` (a table over the route to the terminal status, the status before it, the quantity required and the name/ARN form of the requirement, asserting absence unfiltered, under every documented `JOB_STATUS` value and under `JOB_NAME`, with a live witness job on the same resource).

This report was filed with TWO causes. The first — a `SAGEMAKER_TRAINING` service job driven to `FAILED` at submit time with an emulator-authored `statusReason` instead of running to `SUCCEEDED` — is NOT fixed: it is gated on a container runtime this emulator does not have (the terminal status AWS reports there is the outcome of a SageMaker training run), and it was re-filed, with its own `Issue-Key`, as `issues/things-that-do-not-work/20261027T090000Z-batch-a-sagemaker-training-service-job-is-never-dispatched.md` so that it stays open work rather than being recorded here as working. Only cause 2's trace and key are kept above.

=== Cause 1 of 2: MOVED, still open — a SAGEMAKER_TRAINING service job submitted to a CloudFormation-deployed service job queue is never dispatched ===
Re-filed unfixed as `issues/things-that-do-not-work/20261027T090000Z-batch-a-sagemaker-training-service-job-is-never-dispatched.md`, which carries its trace, its `Issue-Key` and the blocker. The original text of this cause follows, for the record only.

AWS: Smithy com.amazonaws.batch#SubmitServiceJob binds POST /v1/submitservicejob (success 200, errors exactly ClientException httpError 400 and ServerException 500) and returns {jobArn, jobName, jobId}; serviceJobType is the ServiceJobType enum covering the SAGEMAKER_TRAINING flavour, and quotaShareName/schedulingPriority are optional members. DescribeServiceJob (POST /v1/describeservicejob) returns required status (ServiceJobStatus enum) plus optional statusReason, startedAt, stoppedAt, capacityUsage and attempts. Recorded behavior: a service job submitted with a valid serviceRequestPayload to an ENABLED SAGEMAKER_TRAINING job queue backed by a VALID service environment and an existing quota share is dispatched by the service and progresses through non-terminal statuses to terminal SUCCEEDED; the statusReason of a successful job is not an emulator-specific string.
Emulator: DescribeServiceJob reports status 'FAILED' with statusReason 'This emulator does not run SageMaker AI, so the service job was never dispatched'. The job goes terminal immediately at submit time; it is never RUNNING and never SUCCEEDED. The fixed-text part of that message exists nowhere in AWS — it is wholly emulator-authored and has no variable parts taken from the request or from state; AWS's own terminal reason for a service job is produced by the dispatching service, never a statement about the emulator.
Why: the whole service-job plane is unobservable, and now specifically the CloudFormation path to it: a client can stand up AWS::Batch::SchedulingPolicy + AWS::Batch::ServiceEnvironment + AWS::Batch::JobQueue + AWS::Batch::QuotaShare, see CREATE_COMPLETE and a VALID/ENABLED queue, and then every job submitted to that queue fails instantly. Any code that waits for RUNNING/SUCCEEDED sees a spurious terminal failure, and failure-handling code keys off a reason string AWS never emits, so even the error path diverges. Quota-share capacity accounting and preemption are unmeasurable because no job ever holds capacity.
Fix: the service-job state machine in the Batch service state together with the SubmitServiceJob / DescribeServiceJob handlers (services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/submit_service_job.rs, .../describe_service_job.rs, .../state.rs) — drive an accepted service job SUBMITTED -> RUNNABLE -> RUNNING -> SUCCEEDED against the service environment's capacity limits and the named quota share, instead of marking it FAILED at submit time with a 'not dispatched' reason. Service jobs submitted to a CFN-provisioned queue must take the same path as ones submitted through the API.
Traces: batch.deploy-compute-environment-cloudformation-behaves — AssertionError: expected the CFN-deployed queue to run the job to SUCCEEDED, got 'FAILED' ('This emulator does not run SageMaker AI, so the service job was never dispatched'). The stack's CREATE_COMPLETE assertion and the describe_job_queues status=VALID / state=ENABLED assertions before it passed.

=== Cause 2 of 2: ListJobsByConsumableResource keeps reporting a job after it reaches a terminal status, so the listing never converges and a caller waiting for the association to be released hangs ===
AWS: Smithy ListJobsByConsumableResource binds POST /v1/listjobsbyconsumableresource (success 200, errors ClientException 400 / ServerException 500), takes required consumableResource plus optional filters (JOB_STATUS, JOB_NAME), maxResults and nextToken, and is @paginated over jobs. The model documents only 'Returns a list of Batch jobs that require a specific consumable resource' and does not state the lifetime of that requirement, so the release rule is recorded behavior only: once a job reaches a terminal status it releases its consumable-resource association and real AWS stops returning it from this listing entirely — not just under the non-terminal JOB_STATUS filters but under every filter, including JOB_STATUS=FAILED and the unfiltered listing.
Emulator: the handler selects every stored job whose consumableResourceProperties name the resource, with no status predicate at all, so a terminated job keeps appearing in the unfiltered listing (and under JOB_STATUS=FAILED) indefinitely. The check's bounded wait for the job to drop out of the unfiltered listing therefore never converges and the check is killed by the harness ('Check timed out after 60.0s'); no response is wrong on the wire, the result set simply never shrinks. Hypothesis: the hang is at that final wait — every earlier step of the check converges against this emulator (the job is listed while RUNNABLE, the JOB_NAME filter narrows to it, TerminateJob drives it to FAILED immediately and the three non-terminal JOB_STATUS filters then exclude it), and the only loop with no satisfying state in the implemented handler is the 'job has fully dropped out of the listing' wait, since .../ops/list_jobs_by_consumable_resource.rs filters jobs solely by required_quantity() and by the caller's filters.
Why: a client that polls this listing to learn when a consumable resource has been released (the normal way to know that capacity is free again, e.g. before deleting the resource or admitting the next job) waits forever, and any accounting built on 'jobs currently holding this resource' permanently over-counts by every job that has ever used it. The listing also grows without bound for a long-lived resource.
Fix: the selection in the ListJobsByConsumableResource handler plus the consumable-resource association in the Batch service state (services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/list_jobs_by_consumable_resource.rs and .../state.rs) — release a job's consumable-resource requirement when the job reaches a terminal status and exclude released jobs from this listing under every filter, rather than reporting every job that ever named the resource.
Traces: batch.list-jobs-by-consumable-resource-returns-associated-jobs — 'Check timed out after 60.0s' with the terminal-release wait as the only non-converging loop.
