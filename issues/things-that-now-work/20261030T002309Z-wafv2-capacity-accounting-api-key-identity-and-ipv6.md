# wafv2 capacity accounting, API-key identity and IPv6 address canonicalization do not reproduce WAF

> _Note: this issue was identified against the code base at commit `de414c514180eddfb96a534a3f6304a808cc952a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CheckCapacity

## Description
Four successful-status (200) wafv2 responses carry values WAF would not return: the WCU cost model is not statement-type-and-modifier sensitive, API keys are not keyed on their token-domain set, decrypted token domains are unsorted, and IPv6 addresses are stored uncanonicalized. This is ONE issue with FOUR causes; every cause below must be closed before the fix is submitted. (The open issue 20261029T192556Z-wafv2-managed-rule-catalog-contents-and-wcu-capacity covers the WCU charged for a ManagedRuleGroupStatement (710 vs 712) and 20261029T192556Z-wafv2-api-key-responses-and-list-ordering-marker covers the APIKey encoding, ApplicationIntegrationURL/Version and GetIPSet address ORDER; neither carries the replay keys below, and neither describes the per-statement base costs, the additive modifiers, CreateAPIKey idempotency or IPv6 canonicalization.)

Cause 1 of 4: CheckCapacity ignores the published per-statement-type base costs and the additive per-modifier deltas, returning a flat figure per rule.
AWS: Smithy: CheckCapacity.Rules is required and output Capacity targets ConsumedCapacity (long, @default 0, @range min 0); the figure is a deterministic function of the statement types and their modifiers, not of the rule count. The published base costs are SizeConstraintStatement 1, GeoMatchStatement 1, LabelMatchStatement 1, ByteMatchStatement 2 for PositionalConstraint EXACTLY/STARTS_WITH/ENDS_WITH and 10 for CONTAINS/CONTAINS_WORD, RegexMatchStatement 3, SqliMatchStatement 20 at SensitivityLevel LOW and 30 at HIGH, XssMatchStatement 40, RateBasedStatement 2 as a base plus 30 per custom aggregation key plus the full cost of any ScopeDownStatement. On top of the base: each non-NONE TextTransformation adds 10 (NONE adds 0), the AllQueryArguments request component adds 10, and the JsonBody component doubles the base; the modifiers compose (JsonBody doubles the base, then each transformation still adds a flat 10). Across a rule set the text-transformation charge is counted once for the whole set rather than per rule, so cost(N) = cost(1) + (N-1)*marginal with marginal strictly less than cost(1).
Emulator: ByteMatchStatement costs 10 for every PositionalConstraint (EXACTLY/STARTS_WITH/ENDS_WITH/CONTAINS/CONTAINS_WORD all 10); a RateBasedStatement with two custom aggregation keys costs 32 instead of 2+2*30=62, i.e. the per-key increment is applied at most once; and a five-transformation ByteMatch rule costs 10 whether there is one such rule or two, so no transformation delta is charged and no shared-charge discount exists (marginal == cost(1) == 10).
Why: WCU is a hard account limit and the number a client uses to size a rule group — CreateRuleGroup.Capacity is immutable once set. A cost model that is flat in the statement type and blind to transformations/components makes every capacity-planning decision wrong in both directions: a rule group sized against the emulator is rejected by AWS at the limit, and the ceiling check in Cause 1 of the companion write-path issue cannot be reached with realistic rule sets.
Fix: the per-statement WCU cost table and the modifier arithmetic behind the CheckCapacity handler (and the same accounting that persists WebACL.Capacity) — per-type base costs including the ByteMatch PositionalConstraint split and the Sqli sensitivity split, +30 per RateBasedStatement custom key, nested ScopeDownStatement cost added, +10 per non-NONE transformation, +10 for AllQueryArguments, base doubled for JsonBody, and the transformation charge counted once per rule set.
Traces: wafv2.check-capacity-statement-type-base-wcus, wafv2.check-capacity-text-transformation-wcu-delta, wafv2.check-capacity-rate-based-custom-key-increments, wafv2.capacity-scales-linearly-with-rule-count.

Cause 2 of 4: CreateAPIKey mints a new key on every call instead of being idempotent on the token-domain SET.
AWS: Smithy: CreateAPIKey takes required Scope and TokenDomains and returns APIKey (@length 1..2048, @pattern \S); recorded behavior: the key is a deterministic function of the account/scope and the SET of token domains — repeating the call with the same domains returns the byte-identical key, reordering the domains returns that same key, concurrent calls for one domain set all return the one key, and ListAPIKeys holds exactly ONE summary per domain set (each at Version 1) naming the key CreateAPIKey returned. A different domain set mints a different key, and DeleteAPIKey removes that one summary and nothing else.
Emulator: two successive CreateAPIKey calls with the identical TokenDomains return different 64-character keys, so each call mints a fresh key and (by construction) a fresh ListAPIKeys summary per call.
Why: the API key is copied into a client's JavaScript CAPTCHA integration and is expected to be stable for a domain set; a client that calls CreateAPIKey on every deploy accumulates one key and summary per deploy, invalidating the integration it already shipped and drifting ListAPIKeys away from AWS's one-per-domain-set view.
Fix: key the API-key record in state on (scope, sorted token-domain set) in the CreateAPIKey handler and return the existing key when one is present, rather than generating unconditionally.
Traces: wafv2.apikey-create-idempotent-on-domain-set.

Cause 3 of 4: GetDecryptedAPIKey returns TokenDomains in request order rather than WAF's lexicographic order.
AWS: Smithy: GetDecryptedAPIKey output TokenDomains targets the `TokenDomains` list (member TokenDomain @length 1..253 @pattern ^[\w\.\-/]+$) — a list, so element order is part of the response. Recorded behavior: WAF normalizes the domains to lexicographic order, so the decrypted list is sorted regardless of the order CreateAPIKey was given.
Emulator: the list comes back in the exact order the request supplied, unsorted.
Why: a client that compares the decrypted domains positionally, or hashes/diffs the list for drift detection, sees the emulator and AWS disagree for the same key, and any assertion written against AWS's sorted output fails locally.
Fix: normalize TokenDomains to lexicographic order when the API-key record is written, so GetDecryptedAPIKey (and the ListAPIKeys summaries) report WAF's order. Cause 4 of the open issue 20261029T192556Z-wafv2-api-key-responses-and-list-ordering-marker reports the same ordering surface from the wire corpus without the sortedness requirement and does not carry this check's key.
Traces: wafv2.apikey-decrypt-payload-round-trip.

Cause 4 of 4: IPv6 addresses in an IPSet are stored verbatim instead of canonicalized to fully-expanded, zero-padded, lowercase form.
AWS: Smithy: CreateIPSet/UpdateIPSet Addresses target `IPAddresses` (member IPAddress, @length 1..50, @pattern \S) and IPAddressVersion is required. Recorded behavior: for an IPV6 set WAF canonicalizes every entry to fully-expanded, zero-padded, lowercase notation with the prefix length preserved — `2001:db8::1/128` becomes `2001:0db8:0000:0000:0000:0000:0000:0001/128`, `2001:db8:0:0:0:0:0:2/128` becomes `2001:0db8:0000:0000:0000:0000:0000:0002/128`, `fe80::/64` becomes `fe80:0000:0000:0000:0000:0000:0000:0000/64` — so GetIPSet returns the canonical form, not the submitted notation, with no entry duplicated or dropped, and resubmitting that canonical list through UpdateIPSet round-trips the same set. IPv4 entries, by contrast, are preserved byte-for-byte with no re-normalization.
Emulator: GetIPSet returns the submitted IPv6 strings unchanged (`['2001:db8::1/128', '2001:db8:0:0:0:0:0:2/128', 'fe80::/64']` and `['2001:db8::/32', '::1/128', 'fe80::/64']`), so two different notations for the same address stay distinct instead of collapsing to one canonical entry.
Why: canonicalization is what makes the set's membership well-defined — a client that submits `2001:db8::1/128` and later `2001:0db8:0000:0000:0000:0000:0000:0001/128` gets one entry on AWS and two here, and any diff of GetIPSet against intended configuration reports spurious drift and triggers an avoidable LockToken-consuming UpdateIPSet.
Fix: canonicalize IPv6 entries on write in the CreateIPSet/UpdateIPSet handlers (or the IP-set state), keyed off IPAddressVersion, leaving IPV4 entries untouched.
Traces: wafv2.ipset-ipv6-cidr-notation-preserved, wafv2.ipset-address-list-round-trip-preserves-order-and-cidr.
