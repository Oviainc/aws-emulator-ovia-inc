# SimulatePrincipalPolicy ignores the simulated principal when evaluating ResourcePolicy and never populates MatchedStatements (2 causes)

> _Note: this issue was identified against the code base at commit `7d606a3ca79b6754c530277f3c69cfc57aa8c885`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Two distinct net-new root causes in the bootstrapped `iam` service's SimulatePrincipalPolicy handler, both grounded in the failing check iam__kms.sep-policy-composition-kms-key-policy-required-identity-policy-alone-denied. Neither is marked ALREADY FILED or OWNED in the replay report, and neither is covered by the open iam bundles 20261025T000319Z-iam-10-net-new-behavioral-root-causes-four.md / 20261025T000319Z-iam-9-net-new-behavioral-root-causes-cloudformation.md (which cover unrouted operation families, policy-document validation, credential shapes, boundary serialization and the missing authorization gate, but say nothing about the simulator's ResourcePolicy handling or MatchedStatements). The open stub issue 20261022T131025Z-iam-simulateprincipalpolicy-stub.md no longer applies: the operation is implemented and answers 200 with EvaluationResults. A fixer must close BOTH causes before submitting.

Cause 1 of 2: the resource-based policy supplied in ResourcePolicy is evaluated against a request that carries NO principal, so a statement whose Principal names the simulated principal can never match and the decision comes back implicitDeny instead of allowed.
AWS: Smithy (com.amazonaws.iam) SimulatePrincipalPolicy input member `ResourcePolicy` (policyDocumentType, len 1..131072) is documented 'A resource-based policy to include in the simulation provided as a string. Each resource in the simulation is treated as if it had this policy attached', and `CallerArn` is documented 'The ARN of the IAM user, group, or role that you want to specify as the simulated caller of the API operations. If you do not specify a CallerArn, it defaults to the ARN of the user, group, or role that you specify in PolicySourceArn' — i.e. the simulation has a principal identity, and the operation documentation states that for cross-account simulations EvalDecisionDetails 'returns the decision for each policy type (identity-based policy, resource-based policy, and permissions boundary)'. Output EvaluationResult.EvalDecision targets PolicyEvaluationDecisionType (allowed / explicitDeny / implicitDeny). Recorded behavior (this check's oracle, measured on real AWS 2026-09-22): with PolicySourceArn set to an IAM user that has NO identity policy, and ResourcePolicy set to a KMS key policy containing an Allow of kms:Encrypt whose Principal.AWS is that exact user ARN, AWS answers EvalDecision 'allowed'.
Emulator: EvalDecision 'implicitDeny', with ResourceSpecificResults[0].EvalResourceDecision also 'implicitDeny' — the resource policy contributes nothing. The handler at services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/simulate_principal_policy.rs builds the evaluation request with a hard-coded empty principal set (`let principals: [String; 0] = [];` then `iam::Request::new(action, resource, &principals)`) before calling `iam::resource_decision(document, &request)`, so every Principal element in the supplied ResourcePolicy fails to match and the resource decision degrades to NotStated; neither `input.policy_source_arn` nor `input.caller_arn` is ever threaded into the request.
Why: the IAM policy simulator is the API clients use to validate least-privilege designs before deploying them. A caller that is in fact permitted purely by a resource-based policy (a KMS key policy, S3 bucket policy, SQS queue policy, Secrets Manager resource policy) is reported as implicitDeny, so permission-analysis tooling, CI policy gates and 'can this principal do X' pre-flight checks conclude a working grant is broken and either fail the build or push the author to widen identity policies that did not need widening. The inverse risk is equally real: because the Principal element is never consulted, a ResourcePolicy that names a DIFFERENT principal would be evaluated the same way, so the simulator cannot distinguish 'the resource policy names me' from 'the resource policy names someone else'.
Fix: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/simulate_principal_policy.rs — the `decide` helper must receive the simulated caller identity (CallerArn when present, otherwise PolicySourceArn, per the modeled default) and pass it as the request's principal so `service_common::iam_authorization::resource_decision` can match the ResourcePolicy's Principal element; the same identity belongs in the ResourceOwner/cross-account handling the ResourcePolicy member's documentation describes.
Traces: iam__kms.sep-policy-composition-kms-key-policy-required-identity-policy-alone-denied.

Cause 2 of 2: MatchedStatements is unconditionally absent from every result, so no caller can learn which policy type produced the decision.
AWS: Smithy EvaluationResult.MatchedStatements (StatementListType) is documented 'A list of the statements in the input policies that determine the result for this scenario ... Only statements that contributed to the reported decision are included', and ResourceSpecificResult.MatchedStatements carries the per-resource equivalent. Each entry is a `Statement` with SourcePolicyId, SourcePolicyType (PolicySourceType), StartPosition and EndPosition. Recorded behavior (same oracle): for an `allowed` decision reached through the supplied ResourcePolicy, AWS returns a MatchedStatements entry whose SourcePolicyType is the resource-policy source, and for an allow reached through the principal's attached identity policy it returns the identity-policy source; the check reads exactly that discriminator (the set of SourcePolicyType values) and the recorded value for the resource-policy leg is 'Resource Policy'.
Emulator: MatchedStatements is hard-coded `None` on every EvaluationResult (the handler comments that the shared evaluator does not track statement source positions, so the member is omitted), and the per-resource results carry none either. The observed result object is {'EvalActionName': 'kms:Encrypt', 'EvalResourceName': <key arn>, 'EvalDecision': 'implicitDeny', 'ResourceSpecificResults': [{'EvalResourceName': <key arn>, 'EvalResourceDecision': 'implicitDeny'}]} — no MatchedStatements key at all.
Why: MatchedStatements is the only part of the response that explains a decision. Without it a client cannot tell an allow granted by an identity policy from one granted by a resource policy or by a permissions boundary, which is precisely the question the simulator exists to answer; policy-explanation UIs, drift detectors and the documented 'which policy type is responsible for an allow or deny decision' workflow have nothing to read. Omitting the member because statement source POSITIONS are untracked drops the SourcePolicyId/SourcePolicyType discriminators too, which need no position tracking.
Fix: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/simulate_principal_policy.rs together with the shared evaluator in service_common::iam_authorization — the evaluator must report which document (and which statement within it) contributed to the decision so the handler can emit MatchedStatements with SourcePolicyId and SourcePolicyType on both the top-level EvaluationResult and each ResourceSpecificResult. StartPosition/EndPosition may legitimately stay absent if positions are not measured; the source identification may not.
Traces: iam__kms.sep-policy-composition-kms-key-policy-required-identity-policy-alone-denied.
