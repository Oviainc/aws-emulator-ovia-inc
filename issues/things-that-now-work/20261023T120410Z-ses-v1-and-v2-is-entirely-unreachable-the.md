# SES (v1 and v2) is entirely unreachable: the router resolves by sigv4 signing name, so all four 'ses'-signed services collide and every request is refused 500 AmbiguousService (2 causes)

> _Note: this issue was identified against the code base at commit `982a07ada62dfbeb289a85399a86f8ade68b0ada`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEmailIdentity

## Description
Two root causes, both in the pre-dispatch request router / service registry. Every one of the 139 checks in this behavioral suite fails here; 0/139 passed.

Cause 1 of 2: requests signed for 'ses' are never dispatched — four registered emulated services all claim them, and the router refuses rather than choosing.
AWS: the SES surface is reached through ordinary sigv4-signed calls. Smithy (services/service-com-amazonaws-ses-simpleemailservice): service SimpleEmailService, version 2010-12-01, protocols [awsQuery], sigv4Name 'ses', awsService.endpointPrefix 'email', xmlNamespace http://ses.amazonaws.com/doc/2010-12-01/. Smithy (service-com-amazonaws-sesv2-simpleemailservice-v2): SimpleEmailService_v2, 2019-09-27, protocols [restJson1], sigv4Name 'ses', endpointPrefix 'email'. Two further models share that same sigv4Name 'ses': AmazonPinpointEmailService (2018-07-26, restJson1, endpointPrefix 'email') and MailManagerSvc (2023-10-17, awsJson1_0 + rpcv2Cbor, endpointPrefix 'mail-manager'). On AWS a client sees exactly one service behind the endpoint it addressed: ses.CreateEmailIdentity/CreateConfigurationSet/CreateEmailTemplate/CreateDedicatedIpPool/GetAccount/ListContactLists return 200 with their modeled output, and refusals come back as the operation's modeled client errors (e.g. sesv2 BadRequestException/NotFoundException/AlreadyExistsException, SES v1 awsQuery Error envelopes). The signing name is NOT an identity: disambiguation must use the protocol and the request shape (awsQuery POST / with an Action= body vs restJson1 URI paths /v2/email/... vs /v1/email/... vs awsJson1_0 with X-Amz-Target), and the endpoint prefix where it differs ('mail-manager').
Emulator: no SES request ever reaches a handler. Every call is answered with the non-AWS code AmbiguousService: "4 emulated services all claim requests for 'ses': ses, ses, ses, ses; the request is rejected rather than served by an arbitrary one". Observed on CreateEmailIdentity, CreateConfigurationSet, CreateEmailTemplate, CreateDedicatedIpPool, GetAccount and ListContactLists; because it is served as a 5xx, botocore first retries it to exhaustion ("reached max retries: 3", and 10 on the paginated ListContactLists check). Where the check asserted a specific modeled refusal, the ambiguity error arrives in its place — e.g. ses.list-contacts-unknown-contact-list-rejected expected ('NotFoundException', "List with name: ... doesn't exist.") and got ('AmbiguousService', '4 emulated services all claim requests for ...').
Why: the entire SES v1 and SESv2 surface is dead for every client. No identity, configuration set, template, receipt rule set, contact list or dedicated IP pool can be created, so nothing downstream (sending, event destinations, receipt-rule actions into S3/SNS/Lambda, CloudWatch metric delivery, CFN-deployed SES resources) can be configured or observed. The emulator advertises an endpoint it then refuses to serve, and the code it returns is not in any AWS model, so SDK error handling cannot classify it — clients burn their full retry budget on it.
Fix: the request router / service-registry resolution layer (service selection before operation dispatch), not any SES operation handler: the four registrations claiming sigv4 name 'ses' must be disambiguated to exactly one target per request by protocol + endpoint prefix + request shape. Cause 2 of 2: the pre-dispatch refusal is serialized with awsJson framing regardless of the addressed service's protocol, so an awsQuery (SES v1) client cannot parse the response at all.
AWS: SES v1 is awsQuery (Smithy: SimpleEmailService protocols [awsQuery], xmlNamespace http://ses.amazonaws.com/doc/2010-12-01/), so every response — success or error — is XML; an error is an <ErrorResponse><Error><Code>/<Message></Error></ErrorResponse> envelope and the SDK surfaces it as a ClientError with a Code. Recorded behavior only for the ambiguity case itself (AWS has no such condition), but the protocol framing of an error response is fixed by the model.
Emulator: the router's error body is JSON — b'{"__type":"AmbiguousService","message":"4 emulated services all claim requests for \'ses\': ses, ses, ses, ses; ..."}' — served to an awsQuery client. botocore cannot parse it: 'Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received. Further retries may succeed', raising ResponseParserError instead of any ClientError. The four concurrency checks therefore see codes ['ResponseParserError', ...] with no Code at all, so even their fallback expectation ('exactly one winner' / 'must not raise under concurrency') cannot be evaluated; the sesv2 restJson1 callers in the same suite do get a parseable (if wrong) ClientError, which isolates this to protocol selection for the pre-dispatch error path.
Why: a client of a query-protocol service gets an unparseable body rather than a modeled error, so it cannot read a status/code pair at all and retries a non-retryable condition. Any pre-dispatch refusal the emulator emits for an awsQuery/ec2Query/restXml service is invisible to the SDK.
Fix: the gateway's error serializer for pre-dispatch failures must select the framing of the addressed service's protocol (XML ErrorResponse for awsQuery, awsJson '__type' only for JSON protocols) instead of always emitting awsJson.
