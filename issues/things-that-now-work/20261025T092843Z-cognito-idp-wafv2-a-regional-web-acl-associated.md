# cognito-idp__wafv2: a REGIONAL web ACL associated with a Cognito user pool never governs InitiateAuth, and the association call itself never succeeds, so the check hangs to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `514ee8d309269afe8b01855a48e0cc24b8bc9f45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateWebACL

## Description
Cause 1 of 1: the WAFv2-in-front-of-Cognito surface never reaches an observable state — neither the association nor its enforcement on the user pool's API operations is ever produced, so the only cross-service check of it (cognito-idp__wafv2.xsvc-cognito-idp-3-wafv2-block-rule-matching-header-blocked-unmatched-call-allowed) never completes a single leg and is killed by the harness.

AWS: Smithy (wafv2): AssociateWebACL(WebACLArn required, ResourceArn required) returns an empty 200 body on success and is modeled to refuse only with WAFNonexistentItemException / WAFInvalidParameterException / WAFInvalidOperationException / WAFUnavailableEntityException / WAFLimitsExceededException / WAFFeatureNotIncludedInPricingPlanException (400) or WAFInternalErrorException (500) — an Amazon Cognito user pool ARN is one of the protected-resource types it accepts for Scope=REGIONAL. Once associated, the web ACL governs the pool's unauthenticated API operations: with a ByteMatchStatement rule whose Action is Block matching a request header, cognito-idp InitiateAuth carrying that header is refused at the edge with HTTP 403 and an error code, while the identical call without the header proceeds to the pool's normal 200/AuthenticationResult outcome. UpdateWebACL changing that same rule's Action from Block to Count takes effect on the LIVE association without re-associating, after which the previously blocked call returns 200. Smithy (wafv2): GetSampledRequests(WebAclArn, RuleMetricName, Scope, TimeWindow, MaxItems) returns SampledRequests with each sample's Action and Request (Method, Headers, ClientIP) plus PopulationSize. Recorded behavior only for the per-leg status/code pairing (the check prints the observed BLOCK status/code rather than asserting a literal code); what is structural is that every leg produces a response.

Emulator: no leg produces an observable outcome. The check's detail is exactly 'Error: Check timed out after 60.0s' with no frame, which means one of its bounded polls never saw its condition: first the AssociateWebACL poll (`_associate`, which retries every 10 s for up to 300 s and swallows the error code of each failed attempt, so a refusal never surfaces as an exception), then the poll for the marked InitiateAuth to be refused with HTTP 403 (240 s), then the unmatched-call-succeeds poll, the Block->Count poll and the GetSampledRequests poll. Nothing before that point is slow — the pre-WAF InitiateAuth control, CreateUserPool, CreateUserPoolClient, AdminCreateUser, AdminSetUserPassword and CreateWebACL all complete — so the emulator stalls the check at the association/enforcement boundary. Open issue 20261024T065754Z-wafv2-associatewebacl-stub.md reports wafv2 AssociateWebACL as an unimplemented scaffold stub, which is consistent with the first poll being the one that never clears and explains why the suite could not attribute this timeout to a stub automatically (the check catches the stub's error inside its retry loop). Open issue 20261024T065754Z-cognito-idp-wafv2-a-web-acl-associated-with-a-cognito-user.md describes the same symptom for this check but does NOT cover it (the suite reports this failure as neither ALREADY FILED nor OWNED, i.e. its replay key is not carried by that issue), and it attributes the stall only to missing enforcement in the cognito-idp request path, not to AssociateWebACL never succeeding; both halves have to work for any leg to be observable. Open issues 20261023T210711Z-apigateway-wafv2-all-eleven-wafv2-at-the-edge.md and 20261025T081755Z-apigateway-wafv2-six-more-wafv2-at-the-edge.md record the same no-response symptom at an API Gateway stage and are apigateway-scoped.

Why: a client that protects a Cognito user pool with WAFv2 gets a hang instead of an answer. AssociateWebACL never confirms the association, so provisioning code that waits for it (or that treats a non-2xx as retryable, as the AWS-recommended pattern does) never proceeds; and because the pool's API calls are never evaluated against the web ACL, a Block rule that is supposed to refuse abusive InitiateAuth traffic with 403 is silently inert — every request is let through, which is a fail-open of the exact control the association exists to provide. The Block->Count transition and GetSampledRequests attribution are likewise unverifiable.

Fix: two components on one path — the wafv2 AssociateWebACL handler (accept a Cognito user-pool ResourceArn for Scope=REGIONAL, persist the association, and answer 200 with an empty body, or one of the modeled WAF* errors) and the cognito-idp request path for user-pool API operations (evaluate the associated web ACL's rules against the inbound HTTP request — including SingleHeader ByteMatchStatement fields — honour the current rule Action on the live association, refuse a Block match with 403 and an error code, allow a non-match, and record the match for GetSampledRequests). Every leg must always produce a response rather than leaving the caller polling.

Traces: cognito-idp__wafv2.xsvc-cognito-idp-3-wafv2-block-rule-matching-header-blocked-unmatched-call-allowed.

## Evidence
Failing check (verdict mismatch): cognito-idp__wafv2.xsvc-cognito-idp-3-wafv2-block-rule-matching-header-blocked-unmatched-call-allowed — detail is exactly 'Error: Check timed out after 60.0s', with no traceback frame and no marker from the suite (not ALREADY FILED, not OWNED).

Expected (AWS): (1) AssociateWebACL(WebACLArn=<REGIONAL acl>, ResourceArn=<user pool ARN>) returns 200 with an empty body; (2) InitiateAuth(USER_PASSWORD_AUTH) carrying the rule's marked header is refused with HTTPStatusCode 403 and a non-empty Error.Code; (3) the identical call without that header returns 200 with AuthenticationResult; (4) after UpdateWebACL flips the same rule's Action to Count, the marked call returns 200 with AuthenticationResult, with no re-association; (5) GetSampledRequests(RuleMetricName=<the rule's metric>) returns PopulationSize > 0 and at least one sample with Action == 'COUNT' whose Request carries the marker header, Method 'POST', an x-amz-target header and an IP-address ClientIP.

Actual (emulator): none of those five outcomes is ever observed. Every step of the check's setup succeeds (CreateUserPool, CreateUserPoolClient, AdminCreateUser, AdminSetUserPassword, the pre-WAF InitiateAuth control asserting AuthenticationResult, CreateWebACL with the Block-on-header rule), and then the check spends its whole remaining budget inside bounded polls (interval 10 s, budgets 300 s/240 s/120 s/240 s) until the 60 s harness cap kills it, so the emulator produced no 403 for the matched call, no 200/Count transition, and no sample — and, per open issue 20261024T065754Z-wafv2-associatewebacl-stub.md, most likely no successful AssociateWebACL either, since the check converts each failed association attempt into a retry rather than an exception.

1. cognito-idp:CreateUserPool, then CreateUserPoolClient with ExplicitAuthFlows=['ALLOW_USER_PASSWORD_AUTH','ALLOW_REFRESH_TOKEN_AUTH'] and GenerateSecret=False; AdminCreateUser(MessageAction='SUPPRESS') and AdminSetUserPassword(Permanent=True).
2. Confirm the control: InitiateAuth(AuthFlow='USER_PASSWORD_AUTH') returns AuthenticationResult before any WAF is attached.
3. wafv2:CreateWebACL with Scope='REGIONAL', DefaultAction Allow and one rule: Statement.ByteMatchStatement{FieldToMatch.SingleHeader.Name='x-sim2real-waf-marker', PositionalConstraint='EXACTLY', SearchString=<marker>, TextTransformations=[{Priority:0,Type:'NONE'}]}, Action={'Block':{}}, VisibilityConfig with SampledRequestsEnabled=True and a unique MetricName.
4. wafv2:AssociateWebACL(WebACLArn=<acl ARN>, ResourceArn=<user pool ARN>) — AWS answers 200 with an empty body; observe what the emulator answers (do not swallow the error).
5. Call cognito-idp:InitiateAuth again with the marker header injected via a before-send hook — AWS refuses it with HTTP 403 and an error code; the emulator returns 200.
6. Call it once more with the header absent — must still be 200 with AuthenticationResult.
7. wafv2:GetWebACL for the LockToken, then UpdateWebACL with the same rule but Action={'Count':{}}; repeat the marked InitiateAuth — it must now return 200 without re-associating.
8. wafv2:GetSampledRequests(WebAclArn=<acl ARN>, RuleMetricName=<the rule metric>, Scope='REGIONAL', TimeWindow spanning the Count phase, MaxItems=500) — must report PopulationSize > 0 and a sample with Action 'COUNT' carrying the marker header.
