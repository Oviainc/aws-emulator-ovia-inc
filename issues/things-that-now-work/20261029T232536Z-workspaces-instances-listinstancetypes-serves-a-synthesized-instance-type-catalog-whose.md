# ListInstanceTypes serves a synthesized instance-type catalog whose entries never match the service's

> _Note: this issue was identified against the code base at commit `54073c01592ce4e56a3cca58cb5387afed010108`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListInstanceTypes

## Description
One net-new root cause on the WorkSpaces Instances (sdkId workspaces-instances, crate services/service-com-amazonaws-workspacesinstances-eucmifrontendapiservice) instance-type discovery path, found by replaying the wire fixture corpus simparity-wire-aws-v1. Smithy citations are from services/service-com-amazonaws-workspacesinstances-eucmifrontendapiservice/smithy-model/com-amazonaws-workspacesinstances-eucmifrontendapiservice.json.

Context on prior work: the resolved issue 20261022T121938Z-workspaces-instances-catalogs-and-error-resourcetype-diverge-from.md was filed against this same fixture step when the handler reported an 18-row hand-written table. That issue is RESOLVED, so it does not cover this failure, and its two sibling causes (ListRegions membership, DeleteVolume ResourceType) now pass. The catalog was replaced by a family x size expansion, which is a much larger catalog — but the step still diverges, because the entries the expansion produces are still not the entries the service reports. The open issues on this service (20261029T190356Z-workspaces-instances-6-fidelity-divergences-across-createvolume-listregions.md, 20261029T164737Z-workspaces-instances-listinstancetypes-pagination.md, 20261029T023633Z-workspaces-instances-listinstancetypes-maintainability.md) cover CreateVolume/ListRegions/ListWorkspaceInstances fidelity, NextToken decoding and duplicated paging code respectively; none of them covers the content of the reported catalog.

Cause 1 of 1: ListInstanceTypes answers HTTP 200 but reproduces NONE of the InstanceTypeInfo entries the service reports, because both halves of each entry are computed by this emulator rather than taken from the service's published catalog.
AWS: ListInstanceTypes (Smithy: @readonly, @paginated items=InstanceTypes; output InstanceTypes @required, target InstanceTypes = list of InstanceTypeInfo; InstanceTypeInfo.InstanceType @length 1..64 @pattern ^([a-z0-9-]+)\.([a-z0-9]+)$, InstanceTypeInfo.SupportedInstanceConfigurations = list of SupportedInstanceConfiguration{BillingMode, PlatformType, Tenancy}; MaxResults @range 1..600; errors AccessDeniedException 403, ValidationException 400, ThrottlingException 429, InternalServerException 500) reports the service's whole supported instance-type catalog, each entry carrying that type's complete set of valid (BillingMode, PlatformType, Tenancy) combinations as the service publishes them, in the sequence the service serializes them. Recorded behavior only for catalog CONTENT: the model enumerates no instance type and prescribes no ordering, so the requirement is that each reported entry — its name AND its SupportedInstanceConfigurations sequence — is the entry the service serves for that instance type. The recording answers 200 with 597 entries; the first is InstanceType 'c5.12xlarge' carrying 28 combinations (the 7 modelled PlatformTypeEnum values crossed with SHARED/DEDICATED and MONTHLY/HOURLY) in a sequence that is NOT a nested cross product — it opens MONTHLY/Red Hat Enterprise Linux/DEDICATED, then HOURLY/Windows BYOL/SHARED, then HOURLY/Red Hat BYOL Linux/SHARED. The entry count, the names present, and each entry's configuration sequence are all service facts here, not per-run values: no id, timestamp, host or request id appears anywhere in this response.
Emulator: HTTP 200, and the replay reports EVERY expected entry $.InstanceTypes[0] .. $.InstanceTypes[596] (597 keys) as 'missing' — not one recorded entry is matched, including c5.12xlarge, whose name the emulator's catalog does hold. The catalog is synthesized in this service's state module: INSTANCE_TYPE_FAMILIES (families x published size ladders) is expanded and sorted by name by instance_type_catalog(), and each row's configurations are generated by InstanceTypeSpec::supported_configurations() as a cross product nested platform type -> tenancy -> billing mode, which for a non-GPU family emits {MONTHLY, Windows, SHARED} first and so differs from the service's sequence for every one of the 597 entries. For the graphics families the configuration SET is smaller than the service's as well: those rows carry GPU_PLATFORM_TYPES, a 4-value subset (Linux/UNIX, Ubuntu Pro Linux, Windows, Windows BYOL) that the constant's own doc comment calls 'this emulator's catalog data', instead of the 7 values PlatformTypeEnum enumerates. The handler itself is not at fault: its filtering, page sizing and NextToken minting behave as modelled.
Why: this operation is how a client discovers which instance types it may pass to CreateWorkspaceInstance and which (BillingMode, PlatformType, Tenancy) combination each supports. Because no reported entry equals the service's, any client that pins, snapshots, diffs or indexes the catalog answer — a capacity planner, an infrastructure-as-code type selector, a test asserting on a specific entry, or anything that caches the response and keys off the first configuration — reads a different configuration list against the emulator than against AWS, and for a GPU type it is told that RHEL, Red Hat BYOL Linux and SUSE Linux images are unavailable, so it takes the unsupported-configuration branch for requests AWS accepts (and InstanceConfigurationFilter on those platform/GPU combinations wrongly returns no instance type).
Fix: this service's instance-type catalog DATA and the InstanceTypeInfo projection over it, in the service's state module — the INSTANCE_TYPE_FAMILIES rows (so the catalog's membership is the service's), the GPU_PLATFORM_TYPES subset (so a graphics family publishes the platform set the service publishes), and InstanceTypeSpec::supported_configurations()/info() (so an entry's SupportedInstanceConfigurations is the service's set in the service's order rather than a locally nested cross product). The ListInstanceTypes handler's paging, filtering and token logic need no change.

## Resolution

FIXED: the configuration SET of every entry the catalog reports. `GPU_PLATFORM_TYPES` — a
locally invented four-value subset of `PlatformTypeEnum` — is gone, and every row of
`INSTANCE_TYPE_FAMILIES` names the whole modelled platform list, because
`InstanceTypeInfo$SupportedInstanceConfigurations` is documented as "all valid combinations …
the complete set of configuration options available for this instance type". A graphics entry
now carries its 28 combinations rather than 16, and `InstanceConfigurationFilter` on the Red
Hat Enterprise Linux, Red Hat BYOL Linux and SUSE Linux images reports the graphics types too.
Covered by `tests/all/instance_type_configuration_completeness.rs`.

RESIDUAL, declined — the replay key `workspaces-instances|ListInstanceTypes|2xx->2xx|$.InstanceTypes[*]`
still diverges, so do NOT read this file as that key passing:

1. The SEQUENCE the combinations are serialised in. The member is a set, the model attaches no
   ordering to it, and the recorded permutation follows no rule AWS publishes; reproducing it
   would mean pasting one run's recorded sequence into the catalog. The served sequence is
   deterministic and stable across calls.
2. The entry COUNT: the recording holds 597 names, this catalog holds 588. Membership follows
   the rule "the documented supported families × each family's published EC2 size ladder, bare
   metal excluded", and every ladder matches the EC2 API's own modelled instance-type
   enumeration; which further names the service's catalog holds is service data that no model
   or published list in this checkout enumerates.
