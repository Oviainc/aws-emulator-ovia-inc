# ACM ACME account surface diverges in two places: CreateAcmeExternalAccountBinding never evaluates the role's trust policy, and the ACME data-plane newAccount interaction answers 501 (2 causes)

> _Note: this issue was identified against the code base at commit `b17317436abe1a5dae1bd1120020acb35c8cff22`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAcmeExternalAccountBinding

## Description
Two distinct net-new root causes in ACM's ACME external-account-binding / ACME account surface. Both are grounded in behavioral checks that pass against real AWS. Fix BOTH before submitting.

Neither cause is covered by an existing issue. The resolved issue 20261024T113112Z-acm-acme-surface-diverges-directory-url-path-prevalidationtype.md covers the directory URL path, PrevalidationType, cross-account CreateAcmeDomainValidation, the VALIDATING update guard and the CloudFormation AcmeEndpoint type -- it says nothing about role-trust evaluation or the JWS data plane. The open issue 20261025T052312Z-acm-acme-endpoint-contracts-diverge-deleteacmeendpoint-is-served.md covers DeleteAcmeEndpoint authorization and UntagResource's not-found message only.

Cause 1 of 2: CreateAcmeExternalAccountBinding accepts a RoleArn whose trust policy does not let the ACME service principal assume it, and mints a binding.
AWS: Smithy CreateAcmeExternalAccountBinding(IdempotencyToken, AcmeEndpointArn required @length 1..200 @pattern ^arn:aws[a-z-]*:acm:[a-z0-9-]+:[0-9]{12}:acme-endpoint/[a-zA-Z0-9-]+$, RoleArn required @length 1..2048 @pattern ^arn:aws[a-z-]*:iam::[0-9]{12}:role/.+$, Expiration, Tags) -> CreateAcmeExternalAccountBindingResponse{ExternalAccountBinding: AcmeExternalAccountBinding}, @idempotent; modeled errors AccessDeniedException (403), ConflictException (400), InternalServerException (500), ResourceNotFoundException (400), ServiceQuotaExceededException (400), ThrottlingException (400), ValidationException (400). RoleArn's doc is only "<p>The Amazon Resource Name (ARN) of the IAM role to associate with the external account binding.</p>", so the trust rule is recorded behavior only: ACM assumes that role as the service principal acm-acme.amazonaws.com, and a role whose trust policy does not grant that principal sts:AssumeRole / sts:SetSourceIdentity / sts:TagSession is refused with HTTP 403 AccessDeniedException and NO binding is created. The recorded message is "Unable to assume role for <RoleArn>. Verify that the role exists and its trust policy grants acm-acme.amazonaws.com access to sts:AssumeRole, sts:SetSourceIdentity, and sts:TagSession." -- everything outside <RoleArn> is this error class's FIXED text (including the service principal name and the three sts action names); the single variable part is the RoleArn echoed verbatim from the request. The same recording confirms the positive control: a role that DOES trust acm-acme.amazonaws.com is accepted, and a subsequent ListAcmeExternalAccountBindings on the endpoint lists only that binding.
Emulator: the call SUCCEEDS. The handler answers HTTP 200 with a fully-formed ExternalAccountBinding (AcmeExternalAccountBindingArn under the endpoint, AcmeEndpointArn, the rejected RoleArn echoed back, CreatedAt/UpdatedAt) for a role whose trust policy names only ec2.amazonaws.com. The RoleArn is validated against the model's pattern and then stored; the role is never resolved in IAM and its AssumeRolePolicyDocument is never evaluated against the ACME service principal, so no AccessDeniedException can ever be produced on this path.
Why: this is an over-permissive accept of a call AWS refuses. A client that mis-scopes a trust policy is told its binding is ready; on AWS the binding does not exist and the misconfiguration is reported at creation time. Worse, the listing then contains a binding backed by a role ACM could never assume, so any test of ACME's cross-service pass-role boundary silently passes against the emulator and fails in production, and an IAM-boundary regression in a caller's template is undetectable here.
Fix: authorization/validation in the CreateAcmeExternalAccountBinding handler (services/service-com-amazonaws-acm-certificatemanager/src/ops/create_acme_external_account_binding.rs): before writing the binding, resolve RoleArn in the IAM store and evaluate its trust policy for the acm-acme.amazonaws.com service principal over sts:AssumeRole, sts:SetSourceIdentity and sts:TagSession; on failure raise AccessDeniedException (403) with the message above and mutate no state.
Traces: acm.create-acme-external-account-binding-unassumable-role-rejected.

Cause 2 of 2: the ACME data plane answers every JWS POST -- including newAccount -- with 501, so no ACME account can be registered, described or revoked.
AWS: recorded behavior only (the ACME wire is RFC 8555, not a modeled Smithy operation; the control-plane operations that read its result ARE modeled -- DescribeAcmeAccount(AcmeEndpointArn required, AccountUrl required) -> AcmeAccount and RevokeAcmeAccount(AcmeEndpointArn required, AccountUrl required) -> Unit @idempotent, both erroring AccessDeniedException(403)/ResourceNotFoundException(400)/ValidationException(400)/ThrottlingException(400)/InternalServerException(500)). The recording shows: GET <EndpointUrl> returns the directory, HEAD <newNonce> returns a Replay-Nonce, and an RS256 JWS POST to the directory's newAccount URL with payload {"termsOfServiceAgreed": true, "contact": [...]} is answered 200/201 with a Location header carrying the new account URL. Where the endpoint requires an external account binding, newAccount first answers HTTP 400 with the RFC 8555 problem type urn:ietf:params:acme:error:externalAccountRequired, and the retry carrying an HS256 externalAccountBinding JWS built from GetAcmeExternalAccountBindingCredentials' KeyId/MacKey is then accepted. That account URL is what DescribeAcmeAccount and RevokeAcmeAccount take, and after RevokeAcmeAccount the account reports Status REVOKED.
Emulator: the POST is answered HTTP 501 with the problem document {"type": "urn:ietf:params:acme:error:serverInternal", "detail": "This ACME server does not implement the new-account interaction yet", "status": 501}. Only the directory (GET) and newNonce (HEAD/GET) resources are served; newAccount, newOrder, revokeCert, keyChange and an account's own URL are all collapsed onto one not-implemented refusal because the emulator verifies no JWS signature.
Why: 501 with type serverInternal tells an ACME client (certbot, lego, acme.sh) that the CA itself is broken, and such a client retries or aborts rather than branching -- it is the opposite of the externalAccountRequired(400) signal the real flow depends on to know it must attach its EAB. Because no account URL can ever be minted, the entire downstream ACME account lifecycle is unreachable: DescribeAcmeAccount and RevokeAcmeAccount have no addressable AccountUrl, the AcmeAccount ACTIVE -> REVOKED transition can never be observed, and dependent-cleanup ordering (delete the domain validation and the EAB, then DeleteAcmeEndpoint) cannot be exercised at all.
Fix: the ACME data-plane handler, services/service-com-amazonaws-acm-certificatemanager/src/service/acme_http.rs -- the ("POST", AcmeResource::Jws) arm of AcmeHttpSurface::serve (line 179) routes to not_implemented (lines 299-307). Implement the newAccount interaction there: verify the request's JWS, enforce the endpoint's external-account-binding requirement by answering the RFC 8555 externalAccountRequired problem at 400 and accepting the HS256 EAB JWS keyed by the binding's KeyId/MacKey, mint and store the account record (so the nonce store that acme_http's mint_nonce comment defers can make each nonce single-use), and answer 201 with the account's Location URL -- the same URL DescribeAcmeAccount/RevokeAcmeAccount in src/ops/ must then resolve against ACME-endpoint state in src/state.rs.
Traces: acm.e2e-acme-endpoint-binding-revoke-flow.
