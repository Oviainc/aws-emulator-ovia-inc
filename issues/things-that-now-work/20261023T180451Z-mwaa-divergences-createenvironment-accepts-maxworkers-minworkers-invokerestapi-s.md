# MWAA divergences: CreateEnvironment accepts MaxWorkers < MinWorkers, InvokeRestApi's 404 body is unparseable by the AWS SDK, and CreateWebLoginToken's not-found message uses the control-plane wording (3 root causes)

> _Note: this issue was identified against the code base at commit `d46c9ea0387b1ea18140666d9f1aeb4877a1d699`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEnvironment, InvokeRestApi, CreateWebLoginToken

## Description
The MWAA (AmazonMWAA, restJson1) emulator is bootstrapped and answers, but three independent root causes make its CreateEnvironment validation and its env.*-hosted operations diverge from AWS. Each cause below must be closed separately.

Cause 1 of 3: CreateEnvironment does not enforce the MinWorkers <= MaxWorkers business rule and CREATES the environment instead of rejecting the request.
AWS: Smithy (services/service-com-amazonaws-mwaa-amazonmwaa/smithy-model/com-amazonaws-mwaa-amazonmwaa.json) binds CreateEnvironment as PUT /environments/{Name} with errors InternalServerException (500), ServiceUnavailableException (503) and ValidationException (errorKind client, httpError 400). MinWorkers and MaxWorkers are each modeled only as @range(min: 1), so the cross-member rule is not expressible in the model: recorded behavior only — a request whose MaxWorkers is below its MinWorkers is refused with HTTP 400 / ValidationException and no environment record is created (a following GetEnvironment answers 404 ResourceNotFoundException). The message rule here is known because AWS states the violated rule itself rather than echoing the request: "MinWorkers must be less than or equal to MaxWorkers."
Emulator: HTTP 200 with an Arn — the environment is created. Observed: CreateEnvironment(MinWorkers=5, MaxWorkers=1) returned 200 and Arn 'arn:aws:airflow:<region>:<account>:environment/<name>' (the generated name/account are environment-specific and are not the requirement). services/service-com-amazonaws-mwaa-amazonmwaa/src/ops/create_environment.rs validates only NetworkConfiguration.SubnetIds / SecurityGroupIds (lines 279-288) and then copies max_workers/min_workers straight into the stored spec (lines 318-319) with no relational check.
Why: a client relying on AWS's behavior gets an environment that AWS would never have provisioned, so its error branch for an impossible worker range never runs, and every later read (GetEnvironment, ListEnvironments) reports a record that cannot exist on AWS. An emulator accepting input real AWS refuses is the strongest kind of fidelity break: tests written against it pass and then fail in production.
Fix: CreateEnvironment's request validation in its handler (services/service-com-amazonaws-mwaa-amazonmwaa/src/ops/create_environment.rs, beside the existing NetworkConfiguration checks), returning the operation's modeled ValidationException; the same rule applies to UpdateEnvironment, which shares the worker members.
Traces: mwaa.create-environment-max-workers-less-than-min-workers-rejected.

Cause 2 of 3: InvokeRestApi's not-found answer carries a body no AWS SDK can parse — the AWS SDK's restJson1 error parser crashes on it, so the caller never receives an error at all.
AWS: Smithy binds InvokeRestApi as POST /restapi/{Name} (@endpoint hostPrefix "env.") with errors including ResourceNotFoundException (errorKind client, httpError 404). Recorded behavior only for the payload: a Name matching no environment is refused with HTTP 404, error code ResourceNotFoundException, and a body the SDK's restJson1 error parser can read a code and a message out of — i.e. a JSON OBJECT. The recorded message is the env endpoint's fixed wording, "Environment not found" (an example of the text; the requirements are the 404 status, the ResourceNotFoundException code, and an object body carrying them). This is provable from the replay itself: botocore resolves the error by calling body.get('message') on the parsed body, so a root-level JSON string cannot be what AWS serves.
Emulator: HTTP 404 whose body root is a bare JSON string. botocore raises AttributeError: 'str' object has no attribute 'get' from parsers.py:739 inside _do_error_parse — no ClientError, no error code, no message reaches the caller. The reshaping is deliberate: services/service-com-amazonaws-mwaa-amazonmwaa/src/service/env_endpoint.rs:96-142 (document_payload / bare_document) rewrites this one 404 body into Value::String, and src/ops/invoke_rest_api.rs:188-204 is the handler whose modeled 404 it rewrites.
Why: a client relying on AWS's behavior cannot handle the condition at all. Against AWS it catches a 404 ClientError and branches on the absent environment; against the emulator the SDK aborts with an AttributeError before any error object exists, so retry logic, not-found branches and error logging are all bypassed and the failure surfaces as a client-library bug. NOTE: this regressed from the resolved wire issue 20261023T103829Z-mwaa-invokerestapi-returns-modeled-resourcenotfoundexception-body-instead-of-the, which asked for a root-level string payload; that resolved issue does not cover this behavioral check and its two expectations are in direct conflict — the 404 must still carry the ResourceNotFoundException code and the message in a form the SDK's error parser can read.
Fix: the InvokeRestApi not-found response serialization for the env.* data endpoint (src/service/env_endpoint.rs, with src/ops/invoke_rest_api.rs's modeled 404 left as the source of the status, code and message).
Traces: mwaa.invoke-rest-api-nonexistent-environment-not-found.

Cause 3 of 3: CreateWebLoginToken's not-found message uses the control-plane wording instead of the env endpoint's fixed wording.
AWS: Smithy binds CreateWebLoginToken as POST /webtoken/{Name} with @endpoint hostPrefix "env." and errors AccessDeniedException (403), InternalServerException (500), ResourceNotFoundException (404), ValidationException (400). Recorded behavior only for the text, but the rule is known and is per-operation: the env.*-hosted operations (CreateWebLoginToken, InvokeRestApi) answer with the endpoint's FIXED wording, which names no environment and ends without a period — "Environment not found" — whereas the control-plane lookups (GetEnvironment, UpdateEnvironment) build the message from the request: "Environment <Name> not found.". The status (404) and the code (ResourceNotFoundException) already match.
Emulator: the message is built by the shared control-plane builder, so it names the requested environment and ends with a period. Observed: 'Environment sim2real-mwaa-missing-0eab86df730b not found.' where AWS answers the fixed 'Environment not found'. Source: src/ops/create_web_login_token.rs:172-176 calls crate::state::environment_not_found_message(&input.name) instead of the endpoint constant the sibling handler uses (crate::state::ENVIRONMENT_ENDPOINT_NOT_FOUND_MESSAGE, src/ops/invoke_rest_api.rs:199).
Why: a client or operator tool that matches or displays AWS's not-found text for the web-login path sees a different sentence for the same condition, and the environment name leaks into a message AWS keeps name-free.
Fix: the not-found message construction in CreateWebLoginToken's handler — use the env endpoint's fixed message constant rather than the request-derived control-plane builder.
Traces: mwaa.create-web-login-token-nonexistent-environment-not-found.
