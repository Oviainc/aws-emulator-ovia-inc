=== Cause 1 of 2: the DISABLED precondition on DeleteQuotaShare is never enforced, because the handler answers NotImplemented ===
AWS: Smithy com.amazonaws.batch#DeleteQuotaShare binds POST /v1/deletequotashare, takes required input member quotaShareArn (String), returns an EMPTY body with HTTP 200 on success, and models exactly two errors — ClientException (httpError 400) and ServerException (httpError 500). NotImplemented is not a response this operation can produce. The precondition itself is recorded behavior only (the model carries no state machine): deleting a quota share whose state is still ENABLED is refused with HTTP 400, error code ClientException, message "Quota Share must be DISABLED before deleting." — that message is entirely FIXED text, with no value substituted from the request or from state. The refusal must be effect-free: the share remains describable through DescribeQuotaShare with its name unchanged and state still ENABLED, and remains present in ListQuotaShares for its job queue. The positive control in every one of these checks then proves the complement: after UpdateQuotaShare state=DISABLED settles (state DISABLED, status VALID), the same DeleteQuotaShare succeeds with an empty 200, DescribeQuotaShare on the dead ARN then fails 400 ClientException with message "<quotaShareArn> does not exist." (fixed text " does not exist." suffixed to the ARN taken from the request) and UpdateQuotaShare on the dead ARN fails identically.
Emulator: every DeleteQuotaShare call is refused with error code NotImplemented and message "operation DeleteQuotaShare is scaffolded but not implemented in this emulator" (the handler still returns crate::scaffolded::Scaffolded::not_implemented). Six checks assert the refusal code and get 'NotImplemented' instead of 'ClientException', so neither the ENABLED guard, nor the empty-200 success after DISABLED, nor the subsequent not-found contract for the deleted id exists at all.
Why: a client cannot delete a quota share by any path, so teardown of any fair-share/quota-managed Batch setup is impossible and leaks state. Worse, the guard that protects an in-use share is unobservable: code written against the emulator cannot discover that AWS requires UpdateQuotaShare state=DISABLED first, and a retry loop keyed on ClientException sees an unmodeled 501 that botocore treats as a different error class entirely.
Fix: the DeleteQuotaShare handler and the quota-share state it owns (services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/delete_quota_share.rs) — resolve the share from its ARN, refuse with ClientException 400 while state is ENABLED without mutating anything, and remove the share from the job queue's quota-share state once it is DISABLED so later Describe/Update/List calls report it gone.
Traces: batch.delete-quota-share-in-use-by-scheduling-policy-blocked, batch.delete-quota-share-in-use-rejected, batch.delete-quota-share-referenced-by-active-policy-fails, batch.delete-quota-share-referenced-by-scheduling-policy-fails, batch.delete-quota-share-while-enabled-rejected, batch.quota-share-delete-while-enabled-rejected.

=== Cause 2 of 2: DeleteQuotaShare never pattern-validates the quota-share ARN, so the malformed-ARN refusal and its message template do not exist ===
AWS: DeleteQuotaShare.quotaShareArn is an unconstrained required String in the Smithy model (no @pattern), so the ARN shape rule is recorded behavior only: a quota-share ARN that is missing the job-queue path segment — i.e. arn:aws:batch:<region>:<account>:quota-share/<name> instead of arn:aws:batch:<region>:<account>:job-queue/<queue>/quota-share/<name> — is refused BEFORE any lookup with HTTP 400, error code ClientException and message "Error executing request, Exception : Quota Share arn should match a valid Quota Share arn pattern, RequestId: <request id>". In that message the fixed text is "Error executing request, Exception : Quota Share arn should match a valid Quota Share arn pattern, RequestId: "; the only variable part is the trailing request id, which must be the responding call's OWN request id (the same value the response's x-amzn-requestid header carries) — not a recorded constant. DescribeQuotaShare refuses the same malformed ARN with the identical code and message template, and the refusal is effect-free: an unrelated real quota share on the same account keeps its state.
Emulator: the same NotImplemented refusal arrives first, so the ARN is never examined — the check gets code 'NotImplemented' where 'ClientException' is required, and the distinct malformed-ARN message template is unreachable. This is a validation rule separate from Cause 1 (it must fire for an ARN that names no resource, before any state lookup or state check), and it is not described in either open issue named above.
Why: a client that passes a syntactically wrong ARN gets an unmodeled 501 instead of the 400 ClientException that tells it the ARN is malformed, so ARN-construction bugs are indistinguishable from an unimplemented service, and the two different not-found-style messages AWS uses ("... should match a valid Quota Share arn pattern" for a malformed ARN vs "<arn> does not exist." for a well-formed but absent one) collapse into one unrelated error.
Fix: input validation in the DeleteQuotaShare handler (and the shared quota-share ARN parser it uses with DescribeQuotaShare/UpdateQuotaShare) — parse the ARN and refuse a non-conforming one with ClientException 400 carrying the message template above, with the per-call request id interpolated, ahead of the state lookup and the ENABLED check.
Traces: batch.delete-quota-share-unknown-fails.
