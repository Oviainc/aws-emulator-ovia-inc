=== Cause 1 of 1: PutRegistryCatalogData signed for a Region other than the one that serves it is accepted (HTTP 200) instead of refused with UnsupportedCommandException, and it writes the account-global record ===
AWS: Smithy PutRegistryCatalogData — input displayName -> RegistryDisplayName (string, @length min 0, max 100); output registryCatalogData (required); modeled errors InvalidParameterException (client, httpError 400), ServerException (server, 500) and UnsupportedCommandException (client, httpError 400), documented "The action isn't supported in this Region". Registry catalog-data management is the one Region-scoped call on this surface: ECR Public publishes API endpoints in more than one Region, but the registry catalog record (the Gallery author metadata) is written only from us-east-1, so the same well-formed request addressed to another published Region (here us-west-2) is refused 400 UnsupportedCommandException and the account's registry catalog data is left exactly as it was. Recorded behavior for the message, which is a fixed template whose variable parts come from the request and the service's serving Region: "<OperationName> command is only supported in <serving Region>." — for this operation "PutRegistryCatalogData command is only supported in us-east-1." ("command is only supported in" and the trailing period are the fixed text; the operation name is the one the caller invoked and the Region is the single Region the write is served from, not a per-run value). The positive control in the same check is unchanged: the call from the Region that does serve it answers 200 echoing registryCatalogData.displayName, readable back through GetRegistryCatalogData.
Emulator: the us-west-2-signed call SUCCEEDS — HTTP 200, content-type application/x-amz-json-1.1, body {"registryCatalogData": {"displayName": "should-not-apply"}} — so no UnsupportedCommandException is produced for any Region, and the account-global record is overwritten by a request AWS never serves (the check's follow-up read through the serving-Region client would therefore no longer show the control value). The gate itself is still wired: src/ops/put_registry_catalog_data.rs consults crate::state::unsupported_in_region(ctx.parts(), "PutRegistryCatalogData") before touching state, and that helper parses the Region out of the request's SigV4 credential scope and formats exactly the required message using API_REGION. It never fires, because crate::state::serves_region() treats EVERY entry of ENDPOINT_REGIONS (= ["us-east-1", "us-west-2"]) as serving the Region-scoped write, plus the optionally configured deployment Region. The predicate for "which Regions publish an ECR Public endpoint" has been reused as the predicate for "which Region serves the registry-catalog write", and those are different sets: the first is every published endpoint, the second is API_REGION alone (widened only by the Region this instance is deployed/served as, which is what the previous fix needed).
Why: a client relying on AWS's behavior gets no error where AWS returns one, and gets a silent cross-Region mutation of an account-global record. Code that handles UnsupportedCommandException (falling back to a us-east-1 client, surfacing "this call is us-east-1 only", or aborting a multi-Region deploy) never takes that path against the emulator, so the handling is never exercised and ships broken; worse, a publish script that fans the same catalog write out across Regions appears to succeed everywhere against the emulator while AWS rejects all but one, and the emulator's last-writer-wins overwrite of displayName hides the divergence behind a plausible 200. The modeled 400 refusal becomes unreachable for this operation in every Region.
Fix: the Region gate — crate::state::unsupported_in_region / crate::state::serves_region in services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/state.rs, consulted by the PutRegistryCatalogData handler — must test the request's SigV4 credential-scope Region against the Region that SERVES this call (API_REGION, widened only by configured_region() so an instance deployed as a Region is still served its own Region, which is what keeps the primary-client leg from regressing), not against the whole ENDPOINT_REGIONS endpoint list. Keep the two legs together: a request reaching this instance as the Region it is served as must still be answered 200 (ecr-public.registry-catalog-display-name-round-trip-and-limit), and a request signed for any other published Region must be refused 400 UnsupportedCommandException with the message template above, before the registry catalog record is touched, leaving it unchanged. The sibling read GetRegistryCatalogData must keep consulting no such gate.
