# ACM error-message envelopes diverge: validation errors never echo the submitted value, and the reserved-tag-key / tag-quota messages are the emulator's own prose (3 causes)

> _Note: this issue was identified against the code base at commit `2c888af5aa33aca2a1e4835e22187ff259bac9bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAcmeDomainValidation

## Description
Three distinct root causes in ACM's error envelope. In all three the HTTP status (400) and the error code are CORRECT and the side effects are correct (no domain validation created, no partial tag apply, the 51st tag not persisted) — the divergence is the message, and in each case the message is produced by a rule the recording pins down, not by an environment-dependent value.

Cause 1 of 3: the constraint-violation ValidationException never echoes the submitted value, even for a plain non-sensitive string member.
AWS: Smithy CreateAcmeDomainValidation.PrevalidationOptions -> DnsPrevalidationOptions.HostedZoneId targets HostedZoneId with @length(min 1, max 32) and @pattern "^Z[A-Z0-9]+$"; errors include ValidationException (400, awsQueryError ValidationError), whose shape doc is "The supplied input failed to satisfy constraints of an Amazon Web Services service." The model does not state the message text, so: recorded behavior — an explicit empty string for that member is refused with code ValidationException and the message "2 validation errors detected: Value '' at 'prevalidationOptions.dnsPrevalidation.hostedZoneId' failed to satisfy constraint: Member must have length greater than or equal to 1; Value '' at 'prevalidationOptions.dnsPrevalidation.hostedZoneId' failed to satisfy constraint: Member must satisfy regular expression pattern: Z[A-Z0-9]+". The rule the recording fixes is: one clause per violated constraint, the member named by its lowerCamel wire path, the pattern quoted WITHOUT the model's ^...$ anchors, and the offending value echoed as "Value '<value>' at '<path>'" for a non-sensitive scalar member.
Emulator: same code, same two clauses, same unanchored pattern, but the value is never echoed — "2 validation errors detected: Value of the input at 'prevalidationOptions.dnsPrevalidation.hostedZoneId' failed to satisfy constraint: Member must have length greater than or equal to 1; ... Member must satisfy regular expression pattern: Z[A-Z0-9]+". The emulator appears to use the value-withholding form unconditionally.
Why: a client or fixture that parses ACM's envelope to recover WHICH value was rejected (common when a batch of names/ids is submitted and the caller must report the bad one) gets nothing back, and any byte-for-byte comparison against ACM's envelope diverges on every constraint violation of a plain string member.
Fix: the shared constraint-violation message builder for this service's ValidationException — select the echoing form ("Value '<value>' at '<path>'") for non-sensitive scalar members and reserve "Value of the input at '<path>'" for the members where ACM withholds the value. IMPORTANT interaction: open issue 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md cause 7 records the OPPOSITE direction for IdempotencyToken (a sensitive token), ResourceArn and the Tags LIST, where ACM does NOT echo. Both are the same builder, so the fix is the per-member/per-shape SELECTION rule, not a global flip either way — flipping it globally will break that issue's three checks or this one.
Traces: acm.domain-validation-optional-field-empty-vs-absent-preserved.

Cause 2 of 3: the reserved-"aws:"-prefix tag rejection carries the emulator's own wording instead of ACM's request-derived InvalidTagException text.
AWS: Smithy AddTagsToCertificate(CertificateArn, Tags: TagList @length 1..50) models InvalidTagException (client, 400), doc "One or both of the values that make up the key-value pair is not valid. For example, you cannot specify a tag value that begins with aws:." The model does not state the text, so: recorded behavior — a tag whose Key is "aws:reserved" is refused with code InvalidTagException and the message `Invalid Tag Key: "aws:reserved". AWS internal tags cannot be changed with this API.` The rule is a fixed template with the offending tag key interpolated in double quotes.
Emulator: code InvalidTagException (correct), message 'tag aws:reserved is reserved: neither a tag key nor its value may begin with aws:'.
Why: the message is built from the request by a known template, so the template is the requirement; tooling that surfaces or matches ACM's tag-rejection text (and anything that extracts the quoted key from it) does not recognise the emulator's sentence.
Fix: the InvalidTagException construction in the AddTagsToCertificate handler's tag validation (shared with the other tag-writing operations) — emit ACM's template with the rejected key interpolated.
Traces: acm.op-contract-addTagsToCertificate.

Cause 3 of 3: the 50-tag quota rejection carries the emulator's own wording instead of ACM's ServiceQuotaExceededException text.
AWS: Smithy TagResource(ResourceArn, Tags: TagList @length 1..50) models ServiceQuotaExceededException (client, 400), doc "A service quota has been exceeded." The model does not state the text, so: recorded behavior only — tagging a resource already carrying 50 tags is refused with code ServiceQuotaExceededException and the fixed message "The resultant tag set must not have more than 50 user tags." (a constant sentence, no request values in it). The enforced limit itself (50 user tags per resource, the 51st not persisted) is emulated correctly.
Emulator: code ServiceQuotaExceededException (correct), message 'a resource may carry at most 50 tags; this request would leave 51'.
Why: the recorded message is a deterministic constant rather than an environment-dependent value, so a client pinned to ACM's quota wording (or a test fixture asserting it) diverges even though the quota itself is enforced.
Fix: the ServiceQuotaExceededException construction in the TagResource handler's tag-quota check.
Traces: acm.tag-resource-exceeds-quota-rejected.
