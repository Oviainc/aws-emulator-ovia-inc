# cloudformation: 2 net-new root causes — a DisableRollback create whose wait condition times out never parks in CREATE_FAILED (RollbackStack's physical delete unreachable), and a failed update never reaches UPDATE_ROLLBACK_COMPLETE

> _Note: this issue was identified against the code base at commit `cfbdbd19120bc4eb7cd4848a49718d75d65d840b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RollbackStack

## Description
Two distinct net-new root causes in the CloudFormation create/update FAILURE-AND-ROLLBACK state machine. Both are grounded in cloudformation.* behavioral checks that the replay report marked neither ALREADY FILED nor OWNED, and neither check's replay key is carried by any open issue. Related work that does NOT cover them: 20261025T015306Z-cloudformation-long-running-operations-never-converge-23-behavioral.md is marked FIXED and its resolution note claims the wait-condition half of the async driver now honours a wait condition's declared Timeout and fails the operation — neither of the two checks below appears in that issue's trace list, and both still produce no terminal stack status at all; 20261025T150742Z-cloudformation-3-net-new-behavioral-root-causes-an.md (open) describes the UPDATE side of a wait-condition timeout as ending in UPDATE_COMPLETE for a DIFFERENT check (deep-cloudformation-1) and says nothing about DisableRollback parking or RollbackStack's physical delete; 20261025T015306Z-cloudformation-never-rolls-a-failed-stack-back-failed.md (open) describes stacks reaching a WRONG terminal state, whereas here they reach NO state. Each cause below must be closed on its own.

=== Cause 1 of 2: CreateStack(DisableRollback=true) whose second resource is an unsignalled AWS::CloudFormation::WaitCondition with CreationPolicy.ResourceSignal{Timeout:PT1M,Count:1} never parks the stack in CREATE_FAILED, so the whole RollbackStack leg (which must physically delete the resource that was preserved) is unreachable ===
AWS: Smithy: CreateStack(StackName, TemplateBody, DisableRollback: boolean, Tags) -> {StackId}; RollbackStack(StackName, RoleARN, ClientRequestToken, RetainExceptOnCreate) -> {StackId, OperationId}; StackStatus enum contains CREATE_IN_PROGRESS, CREATE_FAILED, ROLLBACK_IN_PROGRESS, ROLLBACK_COMPLETE, ROLLBACK_FAILED. AWS behaviour the check encodes: a resource whose CreationPolicy.ResourceSignal is never satisfied FAILS when the declared Timeout elapses; because the create was submitted with DisableRollback=true the stack then stops at the terminal CREATE_FAILED (it does NOT roll back), the earlier resource (an AWS::SSM::Parameter) stays physically alive and readable at SSM, and the stack's event history carries a CREATE_COMPLETE event for that earlier logical id. A later RollbackStack on that CREATE_FAILED stack drives the stack to the terminal ROLLBACK_COMPLETE and actually DELETES the preserved resource at its own service, so ssm:GetParameter on it is then refused ParameterNotFound (HTTP 400) and ssm:DescribeParameters no longer lists it.
Emulator: DescribeStacks never reports ANY of {CREATE_FAILED, CREATE_COMPLETE, ROLLBACK_COMPLETE, ROLLBACK_FAILED} for this stack — the poll loop is still reading a non-terminal status when the harness cuts the check off at its 60s budget, so no terminal status, no CREATE_FAILED parking, and no RollbackStack leg is observable at all. Nothing after beat 1 of the check is ever reached.
Why: a client that uses DisableRollback to keep a partially-created stack for inspection, and RollbackStack to tear it down afterwards, can never observe either step: the waiter hangs instead of returning CREATE_FAILED, and the resource the deployment created is left live with no API-visible way to learn the create had failed. Recovery tooling keyed on CREATE_FAILED + RollbackStack cannot be rehearsed against the emulator.
Fix: the stack-operation driver in the cloudformation service crate — the task that must fail a resource whose CreationPolicy.ResourceSignal Timeout has elapsed, then apply DisableRollback by settling the stack in the terminal CREATE_FAILED rather than leaving it *_IN_PROGRESS — plus the RollbackStack handler's drive to ROLLBACK_COMPLETE, which has to issue the real delete at the owning service (SSM DeleteParameter here), not just publish a status word.
Traces: cloudformation.rollback-stack-physically-deletes-the-preserved-resource (replay detail: 'Error: Check timed out after 60.0s'; it times out inside _poll_status(cfn, stack, {CREATE_FAILED, CREATE_COMPLETE, ROLLBACK_COMPLETE, ROLLBACK_FAILED})).

=== Cause 2 of 2: an UpdateStack that modifies a resource and then adds an unsignalled AWS::CloudFormation::WaitCondition (Properties.Timeout "60", Count 1) never reaches UPDATE_ROLLBACK_COMPLETE, so the already-applied half of the update is never undone ===
AWS: Smithy: UpdateStack(StackName, TemplateBody, ...) -> {StackId}; StackStatus enum contains UPDATE_IN_PROGRESS, UPDATE_FAILED, UPDATE_ROLLBACK_IN_PROGRESS, UPDATE_ROLLBACK_COMPLETE. AWS behaviour the check encodes: the update first modifies the AWS::SSM::Parameter (DependsOn forces that ordering), then the unsignalled WaitCondition fails when its Timeout elapses; CloudFormation rolls the update back and settles in the terminal UPDATE_ROLLBACK_COMPLETE, the parameter's value is restored to its pre-update value, the resource the failed update added (the WaitCondition) is absent from ListStackResources, an UPDATE_ROLLBACK_IN_PROGRESS stack event is present in DescribeStackEvents, and a subsequent valid UpdateStack still succeeds to UPDATE_COMPLETE.
Emulator: after the failing UpdateStack, DescribeStacks never reports any terminal StackStatus (the check's _wait_terminal accepts the full terminal set incl. UPDATE_FAILED and UPDATE_ROLLBACK_COMPLETE) within the harness's 60s budget — the update neither fails nor rolls back nor completes. Consequently the pre-update value is never restored, the added WaitCondition is never removed, and no UPDATE_ROLLBACK_IN_PROGRESS event is emitted.
Why: a client's deploy waiter hangs on a failing update instead of returning a rollback terminal, and the stack is left half-updated: the mutated property keeps the new value that AWS would have reverted, so emulated and real state diverge permanently for any deployment whose update fails part-way.
Fix: the same stack-operation driver plus the update-rollback path of the cloudformation crate: the wait-condition timeout must fail the in-flight UPDATE, the engine must then re-apply the previous template's property values to the already-mutated resources, delete the resources the failed update added, publish UPDATE_ROLLBACK_IN_PROGRESS stack events and settle in the terminal UPDATE_ROLLBACK_COMPLETE, leaving the stack updatable.
Traces: cloudformation.update-rollback-restores-pre-update-state (replay detail: 'Error: Check timed out after 60.0s'; it times out inside _wait_terminal(cf, stack) after the failing UpdateStack).

## Evidence
Cause 1 — cloudformation.rollback-stack-physically-deletes-the-preserved-resource
  Request: CreateStack(StackName=<stack>, DisableRollback=True, TemplateBody={Resources:{Keep:{Type:AWS::SSM::Parameter, Properties:{Name:<name>, Type:String, Value:<value>}}, Doomed:{Type:AWS::CloudFormation::WaitCondition, DependsOn:Keep, CreationPolicy:{ResourceSignal:{Timeout:"PT1M", Count:1}}}}}), then poll DescribeStacks(StackName=<stack>).
  Expected (AWS): StackStatus settles at the terminal CREATE_FAILED; a CREATE_COMPLETE event exists for logical id 'Keep'; ssm:GetParameter(<name>) still returns the value; after RollbackStack the status settles ROLLBACK_COMPLETE and ssm:GetParameter(<name>) is refused ParameterNotFound / HTTP 400 and DescribeParameters no longer lists it.
  Actual (emulator): no terminal StackStatus is ever observed — DescribeStacks keeps returning a non-terminal status and the replay reports 'Error: Check timed out after 60.0s' with the poll still in beat 1, so RollbackStack is never issued. (The stack name, parameter name and value are per-run generated values; the requirement is the status sequence, not those strings.)

Cause 2 — cloudformation.update-rollback-restores-pre-update-state
  Request: CreateStack(TemplateBody={Resources:{Param:{Type:AWS::SSM::Parameter, Properties:{Name:<p>, Type:String, Value:"v1"}}}}) -> CREATE_COMPLETE, GetParameter(<p>) == "v1"; then UpdateStack(TemplateBody= Param.Value "v2" PLUS GateHandle:{Type:AWS::CloudFormation::WaitConditionHandle} and Gate:{Type:AWS::CloudFormation::WaitCondition, DependsOn:Param, Properties:{Handle:{Ref:GateHandle}, Timeout:"60", Count:1}}) and never signal the handle; poll DescribeStacks.
  Expected (AWS): StackStatus == UPDATE_ROLLBACK_COMPLETE; GetParameter(<p>) == "v1" again; ListStackResources has 'Param' and NOT 'Gate'; DescribeStackEvents contains ResourceStatus UPDATE_ROLLBACK_IN_PROGRESS; a following UpdateStack to "v3" reaches UPDATE_COMPLETE with GetParameter(<p>) == "v3".
  Actual (emulator): no terminal StackStatus at all after the failing update — 'Error: Check timed out after 60.0s' with _wait_terminal still polling; the parameter is therefore left at "v2" and 'Gate' is still a stack resource.

## Steps to Reproduce
Cause 1:
1. cfn:CreateStack(StackName=S, DisableRollback=True, TemplateBody={"Resources":{"Keep":{"Type":"AWS::SSM::Parameter","Properties":{"Name":"/p","Type":"String","Value":"kept"}},"Doomed":{"Type":"AWS::CloudFormation::WaitCondition","DependsOn":"Keep","CreationPolicy":{"ResourceSignal":{"Timeout":"PT1M","Count":1}}}}}). Never call SignalResource.
2. Poll cfn:DescribeStacks(StackName=S) past the PT1M timeout. Observe that StackStatus never becomes CREATE_FAILED (nor any other terminal); AWS parks it at CREATE_FAILED with the 'Keep' parameter still readable at ssm:GetParameter.
3. Then cfn:RollbackStack(StackName=S) and poll again: AWS reaches ROLLBACK_COMPLETE and ssm:GetParameter("/p") is refused ParameterNotFound/400 while ssm:DescribeParameters no longer lists it.

Cause 2:
1. cfn:CreateStack(StackName=S, TemplateBody={"Resources":{"Param":{"Type":"AWS::SSM::Parameter","Properties":{"Name":"/p","Type":"String","Value":"v1"}}}}) and wait for CREATE_COMPLETE.
2. cfn:UpdateStack(StackName=S, TemplateBody= same with Param.Value "v2" plus "GateHandle":{"Type":"AWS::CloudFormation::WaitConditionHandle"} and "Gate":{"Type":"AWS::CloudFormation::WaitCondition","DependsOn":"Param","Properties":{"Handle":{"Ref":"GateHandle"},"Timeout":"60","Count":1}}). Never signal the handle.
3. Poll cfn:DescribeStacks(StackName=S) past the 60s timeout: no terminal status is reached. AWS gives UPDATE_ROLLBACK_COMPLETE, ssm:GetParameter("/p") back at "v1", 'Gate' gone from ListStackResources and an UPDATE_ROLLBACK_IN_PROGRESS event in DescribeStackEvents.
4. Control: a following cfn:UpdateStack back to a single Param with Value "v3" must still reach UPDATE_COMPLETE.
