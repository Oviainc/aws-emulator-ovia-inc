# migrationhubstrategy: StartAssessment silently accepts a request in an account with no registered collector, StartImportFileTask reports a bucket-prefix violation under the transient [S3BucketNotFound] reason, and imported servers never enter the server inventory — 3 causes

> _Note: this issue was identified against the code base at commit `0adaad19e8652dfd7295bc52b170efe472707b44`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartAssessment

## Description
The behavioral suite drove MigrationHubStrategy's import-then-assess loop. Excluding the failures already covered by the filed scaffold-stub issues (GetPortfolioPreferences, StartRecommendationReportGeneration) and by the open issue 20261022T213955Z-migrationhubstrategy-import-loop-broken-end-to-end-the.md, FOUR failing checks remain and cluster into exactly THREE root causes. All three must be closed before re-submitting.

=== Cause 1 of 3: StartAssessment mints an assessment in an account with no registered data collector, returning HTTP 200 instead of refusing the request ===
AWS: StartAssessment "Starts the assessment of an on-premises environment" and therefore needs a data source to assess — either a registered Strategy Recommendations application data collector or Application Discovery Service inventory. In an account with neither, POST /start-assessment is refused with error code ValidationException at HTTP 400 and no assessment is created; this holds for the default data-source type and for assessmentDataSourceType="ManualImport" alike. Smithy (com.amazonaws.migrationhubstrategy#StartAssessment): the operation models only AccessDeniedException(403), InternalServerException(500), ServiceQuotaExceededException(402) and ThrottlingException(429) — the service-level shape ValidationException (httpError 400, "The request body isn't valid.") is NOT in this operation's errors list, so the refusal is recorded behavior only. The emulator's own handler already widens ValidationException in via extra_errors for its bucket checks, so the error channel to answer this exists. Recorded message, as an example: "No connectors are registered. please register collector to perform assessment".
Emulator: the handler validates only the two S3 bucket members and then unconditionally mints an assessment — it answers HTTP 200 with {"assessmentId": "assessment-000000000001"}. There is no collector/data-source precondition anywhere in the path: it reads imported_server_count() purely to populate counters and inserts the Assessment record regardless of whether the account has any data source at all.
Why: this is an over-permissive silent success, the class of divergence a client cannot detect. A caller that has not registered a collector is told its assessment started and is handed an id; it then polls GetAssessment and consumes DataCollectionDetails that describe a collection that can never happen, instead of receiving the 400 that tells it to register a collector first. Any test or deployment gate that asserts "assessment refused until the collector is registered" passes against the emulator and fails against AWS.
Fix: StartAssessment's handler/validation in the migrationhubstrategy service — a data-source precondition must be evaluated BEFORE anything is minted (so a refused start leaves no assessment behind, as the existing bucket checks already do) and must answer ValidationException/400 when the account has no registered collector and no discovery inventory.
Traces: migrationhubstrategy.stop-assessment-transitions-data-collection-status-to-stopped — the check's _error() helper reports "expected a rejection, but the call SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'assessmentId': 'assessment-000000000001'}". Note this check's _ensure_service_linked_role helper does NOT poll IAM, which is why it gets past the prerequisite and isolates this cause. Code: services/service-com-amazonaws-migrationhubstrategy-awsmigrationhubstrategyrecommendation/src/ops/start_assessment.rs:174-245.

=== Cause 2 of 3: a bucket name that violates the documented migrationhub-strategy- prefix is refused with the NOT-FOUND failure reason, making a permanent misconfiguration indistinguishable from a transient one ===
AWS: StartImportFileTask's S3Bucket is documented "The bucket name is required to begin with migrationhub-strategy-" (Smithy: StartImportFileTaskRequest$S3Bucket, @length 0..63, @pattern [0-9a-z]+[0-9a-z\.\-]*[0-9a-z]+ — neither can express a prefix). A real, readable bucket whose name lacks that prefix is refused with error code ValidationException at HTTP 400, and the refusal names the prefix requirement and carries the permissions/prefix failure reason, NOT the bucket-not-found one. Recorded message, as an example: 'The service doesn't have permissions to specified S3 Bucket Service doesn't hv permissions to access bucket, please make sure bucket name begins with "migrationhub-strategy". [S3PermissionsIsIncorrect]'. The rule producing it is known and is the requirement here: AWS distinguishes a prefix/permissions violation (permanent, the caller must rename the bucket) from an unreachable or not-yet-visible bucket (transient, the caller should retry); the bracketed reason tag is how a client tells them apart.
Emulator: state.rs::check_bucket_usable implements the prefix rule as its ONLY check and reports every failure as 'S3 bucket "<name>" does not exist or is not accessible [S3BucketNotFound]'. The status (400) and code (ValidationException) are right, but the prefix violation is classified as a not-found, i.e. as the transient condition. A caller that retries on S3BucketNotFound — the documented, correct reaction to a freshly created bucket not yet visible to the service's cross-account HeadBucket check — therefore retries a request that can never succeed, and loops until its own deadline. In replay this is what consumed the check's entire budget ("Check timed out after 60.0s"): the bounded S3BucketNotFound retry never terminated, so the check never reached a single assertion.
Why: the emulator converts a permanent caller error into an apparently transient one. Client code and the service's own documented retry guidance key on this distinction, so a misnamed bucket produces a hang against the emulator where AWS produces an immediate, actionable rejection naming the prefix. It also means a non-conforming bucket and a genuinely missing bucket are the same observable event, so nothing can be written that handles them differently.
Fix: StartImportFileTask/StartAssessment bucket validation in the migrationhubstrategy service (state.rs::check_bucket_usable and its callers) — the prefix-rule violation must carry its own failure reason naming the required migrationhub-strategy- prefix, distinct from the not-found/not-accessible reason, which should be reserved for a bucket the service cannot reach.
Traces: migrationhubstrategy.import-file-task-bucket-prefix-violation-rejected (Check timed out after 60.0s; the check asserts code == "ValidationException" and the prefix-naming message, then asserts no task was created against the non-conforming bucket). Code: services/service-com-amazonaws-migrationhubstrategy-awsmigrationhubstrategyrecommendation/src/state.rs:710-741, and src/ops/start_assessment.rs:190-193.

=== Cause 3 of 3: after an import reaches ImportSuccess the imported servers are absent from ListServers, so the entire server read path (GetServerDetails, GetServerStrategies, groupIdFilter) is unreachable ===
AWS: an import file task that reaches ImportSuccess has ingested the SERVER resources the import file declares, and those servers become visible on the service's read path: ListServers returns them in serverInfos (Smithy: ListServers -> ListServersResponse$serverInfos, paginated on nextToken/maxResults, accepting an optional groupIdFilter), GetServerDetails resolves each by its id, and GetServerStrategies returns a non-empty serverStrategies list carrying a baseline recommendation (a "Rehost" entry with status one of recommended/notRecommended/potentialPreferred) computed at import time, before any deep binary/antipattern analysis. Recorded behavior additionally shows groupIdFilter is accepted syntactically but is not an isolation boundary for ManualImport-sourced servers: a filter value never used on any import still returns the same full account-wide set as an unfiltered call.
Emulator: after StartImportFileTask and a poll to status ImportSuccess, ListServers answers 200 with an EMPTY serverInfos for the just-imported server — "expected exactly one server named 'sim2real-mhs-server-...', found []" — and the groupIdFilter'd listing is empty too, so the server is not discoverable by its own group id. Because no server id is ever obtained, GetServerDetails and GetServerStrategies are never reachable and the baseline Rehost strategy set cannot be observed at all. state.rs documents this as by construction: IMPORT_SUCCESS is "the terminal status an import file task reaches ... the task completes having imported no records", and no ServerRecord is ever created, so the inventory ListServers reads from stays empty for every import.
Why: a silent wrong answer. The API reports the import succeeded, so a client proceeds to read its inventory and gets nothing back — no error to branch on. Every downstream workflow (per-server strategy review, group-scoped listing, server config updates, assessment targeting) operates on an empty account while the import claims success.
Fix: the StartImportFileTask ingestion and the server inventory it feeds — the import must materialise a ServerRecord per ingested SERVER resource (carrying the import's groupId values and the OS/CPU attributes from the file) into service state, and ListServers/GetServerDetails/GetServerStrategies must read from that inventory, with GetServerStrategies returning the baseline recommendation set for a freshly imported server.
Traces: migrationhubstrategy.server-strategies-unavailable-before-analysis-completes (ImportSuccess reached, then ListServers found []), migrationhubstrategy.group-id-filter-scopes-server-list-results ("server imported under group_a must be discoverable by its own groupIdFilter"). Code: services/service-com-amazonaws-migrationhubstrategy-awsmigrationhubstrategyrecommendation/src/state.rs:35-41,100-104. RELATED: the open issue 20261022T213955Z-migrationhubstrategy-import-loop-broken-end-to-end-the.md describes the same empty ingestion from the WRITE side (its Cause 2: numberOfRecordsSuccess always 0), grounded in two different checks (import-pagination-across-multiple-servers, update-application-component-config-inclusion-status-transitions). Neither of the two checks named here is in that issue's trace list or Issue-Key set, and it says nothing about the ListServers/GetServerDetails/GetServerStrategies read path or the groupIdFilter contract, so this cause is filed to carry those. A fixer closing that issue should re-replay the two checks above as well; fixing the record counters alone will not make either pass.
