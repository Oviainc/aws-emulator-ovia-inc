# Cost Optimization Hub: maxResults range bound, enrollment enum value set, management-account gating of discount visibility and GetRecommendation not-found envelope diverge (4 causes)

> _Note: this issue was identified against the code base at commit `f95a296744f71657ae3614221270df79d0b4a393`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListRecommendations

## Description
Four distinct root causes in the Cost Optimization Hub emulator, each grounded in a failing check of the simparity-behavioral-aws-v1 behavioral replay against this checkout. The service is bootstrapped and answered every call, so these are fidelity divergences, not a bootstrap gap. A fixer must close all four before submitting.

Cause 1 of 4: ListRecommendations validates maxResults against the 0..100 shape bound instead of this operation's own 0..1000 range.
AWS: Smithy: ListRecommendations.maxResults targets com.amazonaws.costoptimizationhub#MaxResults, and the operation's input member carries an overriding @range of min 0, max 1000 (the bare MaxResults shape is 0..100, which is what ListEnrollmentStatuses uses). So maxResults values 0..1000 must be accepted (HTTP 200) and only values above 1000 are refused with the modeled ValidationException (client, httpError 400), whose per-field detail names the member and the constraint actually applied - fields=[{fieldName: 'maxResults', message: 'Member must have value less than or equal to 1000'}]. Because that detail is built from the request member and its modeled constraint, the stated bound is a requirement, not example text.
Emulator: the HTTP 400 / ValidationException classification is right and the fields[] list is now populated, but the detail states the wrong bound: fields=[{fieldName: 'maxResults', message: 'Member must have value less than or equal to 100'}]. The emulator is therefore enforcing 0..100, so every request with maxResults in 101..1000 - including the modeled maximum page size - is refused where AWS answers 200.
Why: a client paging recommendations at the documented maximum page size (maxResults=1000, which is what the SDK's own model advertises) gets a 400 on every call and cannot list recommendations at all; the constraint the emulator advertises in its error contradicts the service model the SDK was generated from, so the client has no way to pick a page size that works.
Fix: the ListRecommendations input validation - bind maxResults to this operation's member-level range (0..1000) rather than the narrower target-shape/other-operation bound, and derive the ValidationExceptionDetail message from the bound actually applied.
Traces: cost-optimization-hub.list-recommendations-max-results-out-of-range-rejected. NOTE: the open issue 20261022T041336Z-cost-optimization-hub-management-account-gating-enum-range.md describes this same wrong bound as its Cause 5, but the replay no longer binds this check to that issue (its failing assertion moved from the envelope message to fields[] once the envelope was corrected), so it is filed here to keep the still-failing check gated; a fixer closing that issue's Cause 5 closes this one too.

Cause 2 of 4: UpdateEnrollmentStatus's accepted enum value set for status omits 'Failed'.
AWS: recorded behavior only for the value set. Smithy models UpdateEnrollmentStatus.status as required, targeting enum EnrollmentStatus with values [Active, Inactive]; ValidationException (client, httpError 400) is modeled with fields -> list<ValidationExceptionDetail{fieldName, message}>. The recorded real-AWS rejection of an out-of-enum status reports the accepted set as three values - fields=[{fieldName: 'status', message: 'Member must satisfy enum value set: [Active, Inactive, Failed]'}] - i.e. the service's validator admits 'Failed' in addition to the two values the published model lists. Hypothesis: 'Failed' is a terminal enrollment state the service added to the wire enum ahead of the published model. The requirement is the accepted value set itself (UpdateEnrollmentStatus(status='Failed') must not be refused as out-of-enum), and the per-field detail text follows from it; the top-level summary message is unchanged and correct.
Emulator: HTTP 400 / ValidationException with fields=[{fieldName: 'status', message: 'Member must satisfy enum value set: [Active, Inactive]'}] - the validator admits only the two modeled values, so a request carrying status='Failed' is rejected where AWS accepts it, and the advertised set is narrower than the service's.
Why: a client that round-trips an enrollment status it read back from the service (or that handles the terminal 'Failed' state) is refused with a 400 on a value the real service accepts, and a client that renders the advertised value set to a user offers a set that does not match AWS.
Fix: the UpdateEnrollmentStatus input validation / the enrollment-status enum used by this service's validator - widen the accepted set to the wire set and emit it in the ValidationExceptionDetail.
Traces: cost-optimization-hub.update-enrollment-status-invalid-value-rejected.

Cause 3 of 4: UpdatePreferences accepts memberAccountDiscountVisibility from a caller that is not the organization's management account.
AWS: Smithy: UpdatePreferences.memberAccountDiscountVisibility targets enum MemberAccountDiscountVisibility ([All, None]); modeled errors include ValidationException (client, httpError 400) and AccessDeniedException (403). Recorded behavior: this field is writable only by an organization's management account. Two distinct rejections exist and must stay distinguishable - an out-of-enum value fails generic input validation (400 ValidationException, summary 'Input validation failed. Please check the field list for more details.' plus fields=[{fieldName: 'memberAccountDiscountVisibility', message: 'Member must satisfy enum value set: [All, None]'}]), while a WITHIN-enum value from a non-management caller is refused for the specific authorization reason (HTTP 400 ValidationException; message example: 'Only management accounts can update member account discount visibility.'). The rule producing the second text is the management-account restriction, so the requirement is the 400/ValidationException refusal of an in-enum value, a message distinct from the generic input-validation summary, and no state change - GetPreferences must still not report memberAccountDiscountVisibility.
Emulator: HTTP 200 - UpdatePreferences(memberAccountDiscountVisibility='All') succeeds and the value is stored and echoed, e.g. {'savingsEstimationMode': 'AfterDiscounts', 'memberAccountDiscountVisibility': 'All', 'preferredCommitment': {...}} with HTTPStatusCode 200. The out-of-enum rejection in the same check now passes, so only the authorization gate is missing.
Why: a client probing which preference fields it may write concludes it is the management account, writes member-account discount visibility, and reads back a value real AWS would never have stored; the restricted-field error branch is unreachable, and code that distinguishes the authorization refusal from a plain input error cannot be exercised at all.
Fix: the UpdatePreferences handler's authorization step, ahead of the preference state write (state must be untouched on refusal), plus the GetPreferences serializer, which must not report memberAccountDiscountVisibility for a non-management caller.
Traces: cost-optimization-hub.update-preferences-invalid-discount-visibility-rejected. NOTE: the open issue 20261022T041336Z-cost-optimization-hub-management-account-gating-enum-range.md describes this gate as its Cause 1, grounded in preferences-member-account-discount-visibility-roundtrip; the replay no longer binds THIS check to that issue (its failing assertion moved from the envelope message to the in-enum refusal), so it is filed here to keep the check gated.

Cause 4 of 4: GetRecommendation's ResourceNotFoundException carries a generated prose message where AWS carries none and identifies the resource through resourceId.
AWS: Smithy: GetRecommendation.recommendationId is required; modeled errors include ResourceNotFoundException (client, httpError 404) with required members message and resourceId ('The identifier of the resource that was not found.'). Recorded behavior only for the envelope's content: for a well-formed but non-existent recommendationId on an enrolled account, the recorded response carries NO error message - the diagnosis is the echoed resourceId, equal to the requested recommendationId. The requirement is the 404 / ResourceNotFoundException classification with resourceId echoing the requested id and no prose message substituted for it.
Emulator: the error code is correct, but the envelope carries a generated message instead of an empty one: 'no recommendation with the ID dc9df624-5ed8-442d-948d-4cdce4656ce4 exists' (the uuid is the requested id and varies per run - it is an example, not a requirement). The check fails on the presence of that message before it can assert the resourceId echo, so whether resourceId is populated at all is unverified and must be checked as part of the fix.
Why: a client that reads ResourceNotFoundException.resourceId to learn which id was missing - the only machine-readable field AWS populates here - cannot rely on it being the carrier, and one that treats a non-empty message as the authoritative diagnosis renders text AWS never sends.
Fix: the GetRecommendation handler's not-found path and the ResourceNotFoundException serializer for this service - populate resourceId with the requested recommendationId and leave message empty rather than synthesising prose.
Traces: cost-optimization-hub.get-recommendation-nonexistent-id-not-found.
