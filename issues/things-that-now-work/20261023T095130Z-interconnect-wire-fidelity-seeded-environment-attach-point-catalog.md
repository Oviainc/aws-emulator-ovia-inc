=== Cause 1 of 4: the seeded Environment catalog is synthetic — ListEnvironments and GetEnvironment serve environments that are not the ones the service publishes ===
AWS: Smithy: ListEnvironments is @readonly, output environments (EnvironmentList, @required), "Lists all of the environments that can produce connections that will land in the called AWS region"; GetEnvironment output environment (Environment, @required). Environment requires provider (Provider union: cloudServiceProvider | lastMileProvider), location (@length ..255), environmentId (@length 1..64), state (EnvironmentState: available | limited | unavailable), bandwidths (Bandwidths{available, supported: BandwidthList}) and type (ProductType). The model binds no CreateEnvironment, so the catalog is service-owned and is NOT account- or run-specific: it is the same for every caller in a region, which is why the recording is authoritative here — recorded behavior only, since the model publishes no catalog contents. The recorded ListEnvironments response for the replayed region carries a SINGLE environment: environmentId "mce-aws-gcp-pdx", provider {cloudServiceProvider: "gcp"} (lower-case partner token), location "us-west1" (the partner's own region naming, not an AWS region id), state "limited", type "Multicloud", remoteIdentifierType "account", bandwidths.available [1Gbps, 2Gbps, 5Gbps, 10Gbps, 20Gbps, 50Gbps, 500Mbps] and bandwidths.supported the same set plus 100Gbps, and NO activationPageUrl. GetEnvironment on that id returns the identical record.
Emulator: serves a hard-coded catalog of five invented environments — env-csp-azure-us-east-1 (provider "Azure", location us-east-1, state available), env-csp-googlecloud-us-west-2 (provider "GoogleCloud"), env-csp-oraclecloud-eu-west-1, env-lmp-lumen-ashburn, env-lmp-megaport-sydney — each with a two/three-element bandwidth set ([1Gbps, 10Gbps] available, [1Gbps, 10Gbps, 100Gbps] supported) and an invented activationPageUrl on "portal.example-*.test". ListEnvironments therefore returns 5 entries where 1 was recorded, with no entry matching the recorded one; GetEnvironment answers 200 from the same store, so its environment.provider.cloudServiceProvider, location, state and both bandwidth lists all diverge (expected gcp/us-west1/limited and the 7- and 8-element bandwidth sets, got Azure/us-east-1/available and the 2- and 3-element sets).
Why: the environment catalog is the entry point of the whole service — a client lists environments, picks one and passes its environmentId, provider-dictated product type and one of its bandwidths to CreateConnection. Against this emulator every id, partner name, location and bandwidth a client discovers is one that does not exist on AWS, so nothing recorded or written against the emulator replays against the service, and bandwidth-dependent paths (the 500Mbps/2Gbps/5Gbps/20Gbps/50Gbps offers, and the limited-state rule that available is a strict subset of supported) are never exercised.
Fix: the catalog seed in the service's state — services/service-com-amazonaws-interconnect-interconnect/src/state.rs seed_environments() (lines 523-609), which ListEnvironments (src/ops/list_environments.rs lines 156-175) and GetEnvironment read. Seed the environments the recordings show, with the partner-token spelling, partner-location naming and bandwidth sets they carry, and do not add members (activationPageUrl) the recorded records omit.
Traces: interconnect-catalog-list-environments#task#1 (ListEnvironments, 5 entries vs 1); interconnect-discover-environments-and-attach-points#task#1 (ListEnvironments, also affects interconnect-environment-lookup-errors#task#1); interconnect-discover-environments-and-attach-points#task#2 (GetEnvironment, 13 diverging members on the single returned record).

=== Cause 2 of 4: ListAttachPoints invents Direct Connect gateway attach points the account does not own ===
AWS: Smithy: ListAttachPoints is @readonly, "Lists all Attach Points the caller has access to that are valid for the specified Environment", output attachPoints (AttachPointDescriptorList, @required) + nextToken; AttachPoint$directConnectGateway is @pattern ^[0-9a-fA-F]{8}-...-[0-9a-fA-F]{12}$. The set is therefore derived from resources the CALLER owns, not from the environment. Recorded behavior: for the replayed environment the response carries an EMPTY attachPoints list — the account owns no Direct Connect gateway, so there is nothing valid to attach.
Emulator: returns a fabricated descriptor {type: DirectConnectGateway, identifier: <name-based v5 UUID>, name: "dxgw-<n>-for-<environmentId>"} — one to three per environment, derived from the environment id by src/state.rs seed_attach_points() (lines 637-659) and seeded_attach_point_count() (lines 625-627). The particular uuid and name in the replay are examples; the defect is that any attach point exists at all with no gateway created.
Why: a client that lists attach points to offer the user a choice, or that feeds attachPoints[0].identifier straight into CreateConnection, succeeds against the emulator on a gateway id that does not exist in the account and then fails against AWS; and the real empty-catalog path ("no attach points, tell the user to create a gateway first") can never be reached.
Fix: the ListAttachPoints handler and the attach-point state it reads — derive the list from gateways the caller actually owns in the emulator (empty when none has been created) instead of seeding per-environment descriptors in src/state.rs.
Traces: interconnect-discover-environments-and-attach-points#task#3.

=== Cause 3 of 4: a connection identifier that names no connection is answered HTTP 404 instead of the recorded HTTP 400 ===
AWS: Smithy: GetConnection, DeleteConnection and UpdateConnection all take identifier (required, ConnectionId @length 1..32, @pattern ^(mcc|lmcc)-[a-z0-9]{8}$) and model both InterconnectClientException (@httpError 400) and ResourceNotFoundException (@httpError 404). Recorded behavior: for a pattern-valid identifier that names no connection, all three operations answer with HTTP status 400. In each of these three clusters the replay reports `status` as the ONLY diverging key, i.e. the response body the emulator produced (error shape and message) already agrees with the recording and only the status line does not — so the requirement at issue is purely the status this not-found rejection is serialized with: 400, not 404.
Emulator: answers 404. GetConnection builds ResourceNotFoundException { message: connection_not_retrievable_message(identifier) } (src/ops/get_connection.rs lines 153-162) and DeleteConnection/UpdateConnection use the same not-found classification (src/state.rs connection_not_retrievable_message line 407, connection_absent_message line 416), and the error is serialized with the model's @httpError 404.
Why: SDKs, proxies and alarms classify by HTTP status before they look at the error code — 4xx retry policy, API-Gateway/ALB status-based routing and per-status dashboards all split on it. A client sees 404 where AWS sends 400 for the single most common negative path of three operations, so status-driven handling and any recorded HTTP comparison diverge on every missing connection.
Fix: the status mapping for the not-found rejection these three handlers return — either the error class chosen for a missing connection or the httpError the serializer applies to it, in src/ops/get_connection.rs, src/ops/delete_connection.rs and src/ops/update_connection.rs (and the shared message/classification helpers in src/state.rs). Keep the body as it is; it already matches.
Traces: interconnect-connection-lookup-list-delete-not-found#task#1 (GetConnection, expected 400 got 404); interconnect-connection-lookup-list-delete-not-found#task#4 (DeleteConnection, expected 400 got 404); interconnect-update-connection-not-found-and-invalid-bandwidth#task#1 (UpdateConnection, expected 400 got 404).

=== Cause 4 of 4: the @pattern validation message splices in the rejected value and renders the pattern with its anchors ===
AWS: Smithy: UpdateConnection$bandwidth targets ConnectionBandwidth, @length 1..8, @pattern ^\d+[MG]bps$. The rejection is generated from the member name and the violated constraint, so the rule is known: recorded message "1 validation error detected: Value at 'bandwidth' failed to satisfy constraint: Member must satisfy regular expression pattern: \d+[MG]bps" — the member is named, the pattern is rendered WITHOUT its ^/$ anchors, and the submitted value is NOT echoed. HTTP 400 is correct and matches.
Emulator: emits "1 validation error detected: Value '10xbps' at 'bandwidth' failed to satisfy constraint: Member must satisfy regular expression pattern: ^\d+[MG]bps$" — same generated rule plus the rejected value spliced in after "Value", and the anchored pattern printed verbatim from the model.
Why: this is the generated validation layer, so the deviation applies to every @pattern-constrained member of the service (UpdateConnection$description, GetConnection/DeleteConnection/UpdateConnection$identifier, TagResource$arn, AttachPoint$directConnectGateway), not just bandwidth. Clients and tests that match AWS's generated validation text, or diff an emulated run against a recorded one, diverge on every pattern violation; echoing the submitted value also puts caller data into a message AWS keeps value-free. Same value-splicing defect the open behavioral issue reports for @range (its Cause 6) — fixing both renderings together is the point.
Fix: the request-validation layer that renders @pattern violations for this service's input shapes (the generated validation that runs before the UpdateConnection handler) — drop the "Value '<submitted>' " segment and strip the leading ^ and trailing $ when rendering the pattern.
Traces: interconnect-update-connection-not-found-and-invalid-bandwidth#task#2.
