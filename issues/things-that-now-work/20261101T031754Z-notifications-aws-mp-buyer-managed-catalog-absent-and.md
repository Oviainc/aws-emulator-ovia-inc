Cause 1 of 3: ListManagedNotificationConfigurations publishes no AWS-MP-Buyer category at all, so the Marketplace-buyer managed notification configurations do not exist in the emulator (fixture notifications-catalog-list-managed-notification-configurations, step task#1).
AWS: Smithy: ListManagedNotificationConfigurations GET /managed-notification-configurations -> 200; output member `managedNotificationConfigurations` (list of ManagedNotificationConfigurationStructure) is @required. Each entry's `arn` (ManagedNotificationConfigurationOsArn) is @required and @pattern `^arn:[a-z-]{3,10}:notifications::[0-9]{12}:managed-notification-configuration/category/[a-zA-Z0-9\-]{3,64}/sub-category/[a-zA-Z0-9\-]{3,64}$`; `name` (@required, @length 1..64, @pattern `^[A-Za-z0-9\-]+$`) and `description` (@required, @length 0..256) are the entry's own published display text. The model does NOT enumerate the catalog, so the published SET and each entry's text are recorded behavior only. The recording shows a strictly larger catalog that includes a whole category the emulator does not publish, `AWS-MP-Buyer`, with at least these sub-categories and published text: `MPBuyerProducts` name 'Products and solutions', description "Notifications about changes to products you've subscribed to, including new versions, instance type updates, visibility changes, region restrictions, and security profile snapshots."; `MPBuyerPrivateOffers` name 'Private offers', description 'Notifications about private offers extended to you, including new offers, offer set availability, and channel partner offer lifecycle updates.'; `MPBuyerPricing` name 'Pricing changes', description "Notifications about price changes to products you're subscribed to, including hourly, monthly, and usage-based pricing updates."; and `MPBuyerAgreements` name 'Agreements' with a description about your agreements and subscriptions, including new agreements (the recorded detail string is cut off at that point in the replay output, so the remainder of that one description and any further AWS-MP-Buyer sub-categories must be read off the fixture itself rather than invented). Because a managed configuration is published BY the service and no modelled operation creates or deletes one, this catalog is a fixed, account-independent set: every account sees the same category/sub-category arn segments, names and descriptions, so the whole set and its prose are the requirement. Only the 12-digit account segment of each arn is a per-environment value.
Emulator: the published catalog is a hard-coded 8-entry seed — 4 AWS-Health sub-categories (Issue, AccountNotification, ScheduledChange, Investigation) and 4 AWS-Partner-Central ones (PCProductListings, PCOffersAndAgreements, PCPaymentsAndDisbursements, PCAccountManagement). No AWS-MP-Buyer entry exists, so the replay reports `missing (expected {...}, got None)` for each recorded AWS-MP-Buyer arn under `$.managedNotificationConfigurations`. Status 200 expected, 200 returned; only the set diverges.
Why: a client enumerating the catalog to let a user subscribe to managed notifications sees a seller-side-only catalog. Every AWS-MP-Buyer arn simply does not exist to the emulator, so GetManagedNotificationConfiguration, AssociateManagedNotificationAdditionalChannel and the `channelIdentifier`-filtered managed listings cannot be exercised against those arns at all, and any console view, policy or subscription flow that keys off the published sub-category set silently drops all Marketplace BUYER notifications (product changes, private offers, pricing changes, agreements).
Fix: the catalog seed in the service's state, not the handler — `MANAGED_NOTIFICATION_CATALOG` and the `seeded_managed_configurations()` builder that turns it into store records. The handler's ordering, paging and channelIdentifier filter are not implicated. Add the AWS-MP-Buyer category's entries with their published names and descriptions taken from the fixture recording (not invented prose, which would substitute one fidelity defect for another).

Cause 2 of 3: TagResource's 204 answer carries no Content-Length on the wire (fixture notifications-tag-resource-list-tags-untag-roundtrip, step task#5).
AWS: Smithy: TagResource POST /tags/{arn}; output shape TagResourceResponse declares NO members and the @http code is defaulted (200 in the model), so the 204 status is recorded behavior only. The recording shows that 204 still carrying a `content-length` header — the fixture asserts the header's PRESENCE, not its value (for an empty body it is `0`). A bodyless success is therefore framed explicitly rather than left for the client to delimit.
Emulator: answers 204 with the right status and an empty body but NO `content-length` header reaches the client: the replay reports `$headers.content-length: missing (expected '<shaped-not-asserted>', got None)`.
Why: with neither Content-Length nor Transfer-Encoding, message length is determined by connection behavior for some client/HTTP-version combinations, so a client or intermediary that frames a bodyless answer by its stated length can hold the connection open waiting for a body, lose keep-alive reuse, or report a truncated response — on a call that in fact succeeded.
Fix: the response-writing transport, not this operation's handler. The service crate already states the length at its one no-content framing seam (`override_protocol` / `frame_empty_body` in src/service.rs, documented at lines 47-71), and the in-process front door serves it; the HTTP/1.1 writer the vendored listener is built on then STRIPS `content-length` from a 204, so nothing a service states on a 204 survives onto a socket. The change belongs in that vendored response writer: preserve a handler-stated `content-length` on a bodyless success instead of dropping it.
Traces: notifications-tag-resource-list-tags-untag-roundtrip#task#5. Status 204 expected and 204 returned; the absent `content-length` is the whole divergence. Code: services/service-com-amazonaws-notifications-notifications/src/service.rs lines 47-71 (the framing seam and its note that the vendored writer drops the header), src/ops/tag_resource.rs (SUCCESS_STATUS = 204 — the status is right, the framing is not), and tests/all/no_content_framing.rs, which already pins the in-process header and the socket's lack of it.

Cause 3 of 3: UntagResource's 204 answer carries no Content-Length on the wire (fixture notifications-tag-resource-list-tags-untag-roundtrip, step task#7).
AWS: Smithy: UntagResource DELETE /tags/{arn}; output shape UntagResourceResponse declares no members, @http code defaulted; recorded behavior only for the 204 status, and the recorded 204 carries a `content-length` header exactly as TagResource's does.
Emulator: answers 204 with no `content-length` header — `$headers.content-length: missing (expected '<shaped-not-asserted>', got None)`.
Why: same client-visible consequence as cause 2 — a successful bodyless answer is unframed, so message-length determination falls back to connection behavior.
Fix: same component as cause 2 (the vendored bodyless-success response writer). It is listed as its own cause because it is a second operation, a second HTTP method and a second fixture step: a change that frames only POST /tags/{arn} leaves this DELETE step diverging.
