# Trusted Advisor ValidationException message rendering diverges (4 causes): anchored @pattern, wrong enum value-set order, @sensitive value echoed, oversized-list value rendering

> _Note: this issue was identified against the code base at commit `242e2a822ca6eb3fec2aad3ba89160f0a6f40669`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRecommendation (bundle also covers ListRecommendationResources, UpdateRecommendationLifecycle, ListChecks, ListRecommendations, BatchUpdateRecommendationResourceExclusion)

## Description
Four independent fidelity defects in the Trusted Advisor request-validation message path. All four produce the correct HTTP status (400) and the correct error code (ValidationException) — only the message text diverges, and in each case the rule that produces that text is known (the message is built from the request plus the member's modeled constraint), so the rule is part of the contract. This issue bundles FOUR causes; each is its own root cause and all four must be closed before submitting.

Cause 1 of 4: the pattern-violation message echoes the Smithy @pattern verbatim, including the leading ^ and trailing $ anchors.
AWS: the message has the fixed form "1 validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>", and <pattern> is reported WITHOUT the anchors. Smithy: com.amazonaws.trustedadvisor#AccountRecommendationIdentifier is a string with @length(min:20,max:200) and @pattern "^arn:[\\w-]+:trustedadvisor::\\d{12}:recommendation\\/[\\w-]+$"; recorded AWS reports it as "arn:[\\w-]+:trustedadvisor::\\d{12}:recommendation\\/[\\w-]+". Status 400, code ValidationException.
Emulator: same status and code, but the message prints the anchored pattern ("... pattern: ^arn:[\\w-]+:trustedadvisor::\\d{12}:recommendation\\/[\\w-]+$").
Why: a client (or an operator) that reads or compares the reported constraint gets a regex string AWS never emits; the message rule for a constraint violation is known, so the anchor stripping is a requirement, not an environment detail.
Fix: the shared request-validation message formatter for this service (strip the anchors when rendering a @pattern into the ValidationException message), not the individual operation handlers.
Traces: trustedadvisor.get-recommendation-malformed-arn-rejected, trustedadvisor.get-recommendation-matches-list-summary, trustedadvisor.list-recommendation-resources-status-partition-invariant, trustedadvisor.update-recommendation-lifecycle-concurrent-idempotent-writes.

Cause 2 of 4: the enum-violation message lists the enum value set in the Smithy model's member declaration order, which is NOT the order AWS reports.
AWS: recorded behavior only for the ordering — AWS emits "1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy enum value set: [<values>]" with a fixed service-side order per enum, observed as: pillar -> [security, service_limits, cost_optimizing, operational_excellence, fault_tolerance, performance]; source -> [rds, pse, well_architected, aws_config, manual, resilience_hub, stir, compute_optimizer, resilience, cost_explorer, cost_optimization_hub, ta_check, security_hub, lse]; type -> [priority, standard]; status -> [error, warning, ok]. Status 400, code ValidationException.
Emulator: emits the model declaration order instead (Smithy: RecommendationPillar values [cost_optimizing, performance, security, service_limits, fault_tolerance, operational_excellence]; RecommendationSource [aws_config, compute_optimizer, cost_explorer, lse, manual, pse, rds, resilience, resilience_hub, security_hub, stir, ta_check, well_architected, cost_optimization_hub]; RecommendationType [standard, priority]; RecommendationStatus [ok, warning, error]) — exactly the strings the replay reports as actual.
Why: the enum listing is the part of the message that tells a caller which values are legal; a client or test that compares the rendered set (or a human diffing it) sees a set AWS never sends for that member. The order is deterministic and per-enum on the AWS side, so it is reproducible, not an environment artifact.
Fix: the shared enum-constraint message rendering in this service's validation layer — render each enum in AWS's reported order rather than the model's member order.
Traces: trustedadvisor.list-checks-invalid-pillar-enum-rejected, trustedadvisor.list-checks-pagination-no-duplicates, trustedadvisor.list-checks-source-filter-consistency, trustedadvisor.list-recommendations-invalid-type-enum-rejected, trustedadvisor.list-recommendations-status-partition-invariant.

Cause 3 of 4: a length violation on a @sensitive member echoes the caller's value into the message.
AWS: Smithy: UpdateRecommendationLifecycle.updateReason targets com.amazonaws.trustedadvisor#RecommendationUpdateReason, a string with @length(min:10,max:4096) and @sensitive. For a sensitive member AWS omits the offending value from the validation message, emitting "1 validation error detected: Value at 'updateReason' failed to satisfy constraint: Member must have length greater than or equal to 10" (no quoted value), status 400, code ValidationException.
Emulator: includes the value — "1 validation error detected: Value 'short' at 'updateReason' failed to satisfy constraint: Member must have length greater than or equal to 10".
Why: the rule is stated by the model (@sensitive), so echoing the value both diverges from the contract and writes caller-supplied sensitive content into an error surface that clients log — exactly what @sensitive exists to prevent.
Fix: the shared validation message formatter must suppress the "Value '<v>'" clause for members whose target shape carries @sensitive (and the length-constraint branch in UpdateRecommendationLifecycle's validation).
Traces: trustedadvisor.update-recommendation-lifecycle-short-reason-rejected.

Cause 4 of 4: the list max-items violation message does not render the list value the way AWS does.
AWS: Smithy: BatchUpdateRecommendationResourceExclusion.recommendationResourceExclusions targets RecommendationResourceExclusionList, @length(min:1,max:25), @uniqueItems. A 26-item batch is rejected before any per-item processing with status 400, code ValidationException, and the message renders the whole list value in AWS's struct form: "1 validation error detected: Value '[RecommendationResourceExclusion(arn=<arn>, isExcluded=true), ...]' at 'recommendationResourceExclusions' failed to satisfy constraint: Member must have length less than or equal to 25".
Emulator: returns the right status (400) and code (ValidationException) — those assertions pass — but the exact-message assertion fails, so the rendering of the structure-list value and/or the constraint clause diverges. The replay report truncates the actual string, so re-run this one check locally to capture the emulator's exact rendering.
Why: the message rule here is known (it is built from the request's list value and the modeled max), so a caller that surfaces or parses the rejection sees a value rendering AWS never produces.
Fix: the list-length branch of the shared validation message formatter — render structure members as <ShapeName>(<member>=<value>, ...) joined by ", " inside [ ], matching the member-name/constraint clause AWS emits.
Traces: trustedadvisor.batch-update-resource-exclusion-exceeds-max-items-rejected.
