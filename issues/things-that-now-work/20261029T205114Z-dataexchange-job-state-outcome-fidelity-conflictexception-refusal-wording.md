# DataExchange job state/outcome fidelity: ConflictException refusal wording for CancelJob and StartJob, and the job error Code a started CREATE_S3_DATA_ACCESS_FROM_S3_BUCKET job reports

> _Note: this issue was identified against the code base at commit `4bd656ceb6ae5ffdb198db72ede94ac7bf108594`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJob

## Description
Three net-new root causes in the dataexchange job plane. The job state machine itself is right (WAITING -> CANCELLED / IN_PROGRESS -> terminal, and a re-cancel or re-start is correctly refused with 409 ConflictException and correctly leaves the stored state unchanged); what diverges is the TEXT of those refusals and the CODE a started job's execution reports.

An open issue, 20261029T172356Z-dataexchange-client-error-messages-are-emulator-prose-instead.md ("DataExchange client-error messages are emulator prose instead of AWS's fixed wording"), covers the same family of defect for ResourceNotFoundException's Message and for CreateJob's ValidationException Message. It does NOT cover any of the causes below: causes 1 and 2 are ConflictException (409) on CancelJob/StartJob, an exception and a wording that issue never names, and cause 3 is not a client-error body at all but the JobError carried in GetJob's Errors list. Likewise 20261029T183418Z-dataexchange-resourcenotfoundexception-message-is-emulator-composed-prose-with.md covers only ResourceNotFoundException's Message.

Cause 1 of 3: CancelJob on a job that is not WAITING returns the right 409 ConflictException but the wrong Message.
AWS: 409 ConflictException with the FIXED message 'Cannot cancel the requested Job. To cancel a Job, it must be in the WAITING state.' This sentence has NO variable part — no job id, no observed state is interpolated. The identity of the conflicting resource is carried by the exception's own members, not the prose (Smithy: ConflictException { Message: __string required, ResourceId: __string "The unique identifier for the resource with the conflict.", ResourceType: ResourceType } @error client @httpError 409; CancelJob errors include ConflictException @httpError 409, DELETE /v1/jobs/{JobId}, success 204). The model documents the rule as "Jobs can be cancelled only when they are in the WAITING state"; the exact sentence above is recorded behavior.
Emulator: 409 ConflictException, but Message is the emulator's own composed sentence of the form 'The job <JobId> is in state <State> and can't be cancelled. Jobs can be cancelled only when they are in the WAITING state.' The <JobId> there is the request's JobId and <State> is the emulator's stored state — both are request/state values interpolated into prose AWS never emits. (One run read: "The job a754a09f93e3254676801b9ae598436e is in state CANCELLED and can't be cancelled. Jobs can be cancelled only when they are in the WAITING state." — that id and that state fill the emulator's template; they are not part of any requirement.)
Why: a client that matches on, asserts against, or logs the documented refusal text sees text AWS never serves, and the conflicting resource's identity lands in a sentence instead of in ResourceId/ResourceType where a client reads it programmatically.
Fix: the shared conflict-error constructor for the dataexchange crate (error construction, not CancelJob's state logic, which is already correct) — the helper CancelJob's handler calls to build this 409, together with the per-operation verb constant that feeds it.
Traces: dataexchange.cancel-terminal-job-rejected. Citations: services/service-com-amazonaws-dataexchange-dataexchange/src/ops/cancel_job.rs lines 68-70 (CANCELLED_VERB) and 196-201 (the ConflictException construction via crate::state::job_state_conflict); the message template lives in services/service-com-amazonaws-dataexchange-dataexchange/src/state.rs (job_state_conflict).

Cause 2 of 3: StartJob on a job that has left WAITING returns the right 409 ConflictException but the wrong Message.
AWS: 409 ConflictException with the FIXED message 'Cannot start the requested Job. To start a Job, it must be in the WAITING state.' Again no variable part (Smithy: StartJob errors include ConflictException @httpError 409; PATCH /v1/jobs/{JobId}, success 202; ConflictException.Message required).
Emulator: 409 ConflictException with 'The job <JobId> is in state <State> and can't be started. Jobs can be started only when they are in the WAITING state.' — same emulator-composed template as cause 1, with the request's JobId and the stored State interpolated. (One run read: "The job 36018d2e1cbb11162f50b68e88469ae3 is in state ERROR and can't be started. Jobs can be started only when they are in the WAITING state.")
Why: same as cause 1 — the refusal is recognisable to AWS clients only by its fixed text, and that text is absent.
Fix: the same shared conflict-error constructor plus StartJob's verb constant.
Traces: dataexchange.start-job-already-started-rejected. Citations: services/service-com-amazonaws-dataexchange-dataexchange/src/ops/start_job.rs lines 170-175 and 189-191 (STARTED_VERB).

Cause 3 of 3: a started CREATE_S3_DATA_ACCESS_FROM_S3_BUCKET job reports the wrong JobError Code and Message — the emulator reports a missing source object for EVERY job type instead of the validation failure AWS reports for this type.
AWS: wiring an S3_DATA_ACCESS data set to a real, already-provisioned bucket and object with Type=CREATE_S3_DATA_ACCESS_FROM_S3_BUCKET ends the job in State ERROR carrying a JobError whose Code is VALIDATION_EXCEPTION, whose Message states the deploy-time IAM prerequisite (that AWS Data Exchange must be granted s3:GetObject on the named bucket) — the variable part being the bucket named in the request's AssetSource, the rest fixed text. Smithy: JobError { Code: Code required, Message: __string required, Details, LimitName, LimitValue (double, default 0), ResourceId, ResourceType: JobErrorResourceTypes }; Code enum values are ACCESS_DENIED_EXCEPTION, INTERNAL_SERVER_EXCEPTION, MALWARE_DETECTED, RESOURCE_NOT_FOUND_EXCEPTION, SERVICE_QUOTA_EXCEEDED_EXCEPTION, VALIDATION_EXCEPTION, MALWARE_SCAN_ENCRYPTED_FILE — so VALIDATION_EXCEPTION is a modelled Code this emulator never produces. The requirement that this type fails on the IAM prerequisite is recorded behavior only.
Emulator: State ERROR (correct) but Errors = [{ Code: 'RESOURCE_NOT_FOUND_EXCEPTION', Message: 'Resource not found. Unable to find source Amazon S3 object.', LimitValue: 0.0 }]. The source object in question had just been created through the emulator's own S3 (CreateBucket + PutObject + PutBucketPolicy all succeeded in the same check), so the emulator is asserting the absence of an object it is itself serving. The cause is that StartJob hard-codes one outcome for every modelled Type: a terminal ERROR with Code RESOURCE_NOT_FOUND_EXCEPTION and a message naming a per-Type source string, with no per-Type outcome and no consultation of the actual source.
Why: a client cannot tell a genuine missing-source failure from the IAM/validation prerequisite that AWS reports here. The two demand opposite remediations — re-stage the data versus fix the bucket policy — so a deploy pipeline keyed on Code retries or aborts wrongly, and a pipeline that treats VALIDATION_EXCEPTION as the signal that the prerequisite is enforced sees that enforcement silently skipped.
Fix: StartJob's execution-outcome logic — the per-Type settlement table and the JobError it mints must distinguish the validation/prerequisite outcome from a missing-source outcome, rather than returning one hard-coded RESOURCE_NOT_FOUND_EXCEPTION for every Type.
Traces: dataexchange.tag-resource-roundtrip-and-export-deploy (its TagResource/ListTagsForResource/UntagResource roundtrip assertions all PASSED; the check fails only on the job's error Code). Citations: services/service-com-amazonaws-dataexchange-dataexchange/src/ops/start_job.rs lines 193-201 (CODE_RESOURCE_NOT_FOUND, SOURCE_S3_OBJECT), 222-238 (CONTENT_SOURCE_FOR_TYPE) and 240-260 (execution_outcome, which mints the same Code for every Type).
