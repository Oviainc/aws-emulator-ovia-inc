# ACM ImportCertificate validation diverges in two places: a certificate chain that does not issue the leaf is refused (AWS accepts it), and a certificate/private-key mismatch is refused with the wrong error code and message (2 causes)

> _Note: this issue was identified against the code base at commit `df009dd79b3a670d3c0c53c12bb5e37a115b862c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportCertificate

## Description
TWO distinct net-new root causes in the ACM ImportCertificate handler, both grounded in failing behavioral checks of this suite. A fixer must close BOTH before submitting. Neither is covered by an open issue: 20261025T172549Z-acm-certificate-representation-and-state-gating-diverge-in.md Cause 4 covers only the re-import-into-an-AMAZON_ISSUED-ARN code (ResourceNotFoundException vs InvalidParameterException), and 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md covers certificate representation and DNS validation; neither says anything about chain issuance linkage or the key/certificate correspondence refusal.

Cause 1 of 2: ImportCertificate verifies that the supplied CertificateChain's first certificate issued the leaf and refuses when it does not -- AWS performs no such check, and the three chain defects AWS DOES refuse are refused here with the wrong error class and wording.
AWS: Smithy ImportCertificate(Certificate required CertificateBodyBlob @length 1..32768, PrivateKey required PrivateKeyBlob @sensitive @length 1..5120, CertificateChain CertificateChainBlob @length 1..2097152, CertificateArn Arn, Tags @length 1..50) -> {CertificateArn}; modeled errors ConflictException, InvalidArnException, InvalidParameterException, InvalidTagException, LimitExceededException, ResourceNotFoundException, TagPolicyException, TooManyTagsException, ValidationException (all HTTP 400). The operation's own documentation lists what it validates about the material (private key matches the certificate, key unencrypted and <= 5 KB, all three bodies PEM-encoded, current time between Not Before and Not After, Issuer not empty) and says NOTHING about the chain issuing the leaf. Recorded behavior (measured against real ACM in us-west-2 and stated in the check's own docstring, which was authored on the opposite premise and corrected from the recording): ACM does not verify the issuance linkage between the chain and the leaf at all -- a leaf issued by CA-A imported with an unrelated CA-B as its chain is ACCEPTED, reaches Status ISSUED, DescribeCertificate still reports Issuer parsed from the LEAF's DER (CA-A, not CA-B), and GetCertificate hands CA-B back verbatim. The same holds for a chain that is the leaf itself and for a chain whose only member has BasicConstraints ca=false. What ACM does validate about the chain is its ENCODING and its VALIDITY WINDOW, each refused with HTTP 400 ValidationException and its own message -- fixed text in full, no variable parts: an expired chain member -> 'A certificate in the chain is expired. You can Import a certificate only during its validity period.'; a chain that is not parseable as PEM certificates -> 'The certificate chain is not PEM-encoded or is not valid.'; a well-formed PEM of the wrong type (a private key) -> 'Passed PEM is not a certificate chain.'. The message is the only thing distinguishing these three from each other and from every other material defect, which all share the ValidationException code.
Emulator: the import of a leaf whose chain is an unrelated CA is REFUSED with HTTP 400 InvalidParameterException, message 'the CertificateChain must begin with the certificate of the authority that issued the Certificate' -- a check AWS does not perform. services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs compares issuer.tbs_certificate.subject against certificate.tbs_certificate.issuer and rejects on inequality. The same code path also answers the encoding defects with InvalidParameterException and paraphrases ('the CertificateChain must be PEM-encoded X.509 certificates', 'the CertificateChain must carry at least one PEM-encoded X.509 certificate'), has no validity-window check over chain members at all, and so can produce none of the three AWS messages.
Why: this breaks in both directions. A caller that intentionally ships a partial or cross-signed chain -- a common, AWS-supported pattern -- has its import rejected here and succeeds in production, so the emulator refuses work AWS accepts. Conversely a caller whose chain really is expired or malformed gets InvalidParameterException with emulator wording instead of ValidationException with the specific sentence, so error-class branching and log/message matching pick the wrong remediation, and the three defects become indistinguishable.
Fix: the chain handling in the ImportCertificate handler, services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs (imported_certificate(): delete the subject/issuer linkage refusal and store the supplied chain verbatim; add a validity-window check over every chain member; raise ValidationException, not InvalidParameterException, for the expired / unparseable-PEM / wrong-PEM-type cases with the AWS messages above). Issuer must keep being read from the LEAF's DER, never from the supplied chain.
Traces: acm.import-certificate-chain-not-matching-leaf-rejected.

Cause 2 of 2: importing a certificate with a PrivateKey that does not correspond to the certificate's public key is refused with InvalidParameterException and emulator wording instead of ValidationException with AWS's message.
AWS: same Smithy signature as above; ValidationException ('The supplied input failed to satisfy constraints of an Amazon Web Services service.', HTTP 400) and InvalidParameterException ('An input parameter was invalid.', HTTP 400) are both modeled, and the operation's documentation makes the correspondence a guideline: 'You must enter the private key that matches the certificate you are importing.' Recorded behavior: the mismatch is refused with HTTP 400 ValidationException and message 'Key provided does not match the certificate.' -- the whole sentence is this error class's fixed text, with no variable parts -- and the certificate already stored at the targeted CertificateArn is left untouched (GetCertificate still returns the original body byte-identically).
Emulator: HTTP 400 InvalidParameterException, message 'the PrivateKey does not match the public key in the certificate' (import_certificate.rs builds it through invalid_parameter() in the private-key/public-key comparison helper).
Why: clients branch on Error.Code. ValidationException is the class AWS uses for bad certificate material, so a caller that catches ValidationException to report 'your key and certificate do not match' never sees it here, while the InvalidParameterException it does get is the class the emulator also uses for unrelated defects -- and the message differs from AWS's, breaking the only signal that separates this refusal from a malformed-PEM or size rejection.
Fix: the private-key/certificate correspondence check in services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs -- raise ValidationException with the message 'Key provided does not match the certificate.' instead of invalid_parameter(...), and keep the no-mutation guarantee on a re-import that targets an existing CertificateArn.
Traces: acm.reimport-certificate-public-key-mismatch-rejected.

## Steps to Reproduce
1. Boot the emulator and point botocore at it.
2. Cause 1 control: mint CA-A (self-signed, ca=true) and a leaf signed by CA-A; acm.import_certificate(Certificate=leaf, PrivateKey=leaf_key, CertificateChain=PEM(CA-A)) -- succeeds, Status ISSUED.
3. Cause 1 boundary: mint an unrelated CA-B and import a second CA-A-signed leaf with CertificateChain=PEM(CA-B). The emulator answers HTTP 400 InvalidParameterException 'the CertificateChain must begin with the certificate of the authority that issued the Certificate'; AWS accepts the import, reports Issuer from the LEAF (CA-A), and GetCertificate returns CA-B verbatim as the chain.
4. Cause 1 refusals: import a fresh leaf three times with (a) an EXPIRED CA as the chain, (b) CertificateChain=b'-----BEGIN CERTIFICATE-----\nnot-base64!!!\n-----END CERTIFICATE-----\n', (c) a PEM private key as the chain. AWS refuses each with HTTP 400 ValidationException and, respectively, 'A certificate in the chain is expired. You can Import a certificate only during its validity period.', 'The certificate chain is not PEM-encoded or is not valid.', 'Passed PEM is not a certificate chain.'; the emulator answers InvalidParameterException with its own paraphrase (and accepts (a) outright, since it never checks chain validity windows). After each refusal, ListCertificates must not contain the refused leaf's domain.
5. Cause 2: import leaf1 with key1 (succeeds); mint leaf2 for the same domain with an unrelated key2; call acm.import_certificate(Certificate=leaf2, PrivateKey=key1, CertificateArn=<leaf1 ARN>). The emulator answers InvalidParameterException 'the PrivateKey does not match the public key in the certificate'; AWS answers ValidationException 'Key provided does not match the certificate.'. Then acm.get_certificate(CertificateArn=<leaf1 ARN>) must still return leaf1 byte-identically.
6. Re-replay the 2 checks in trace_ids.
