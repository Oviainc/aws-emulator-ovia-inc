=== Cause 1 of 2: ListAgreementCharges answers a constraint-satisfying agreementId with 400 ValidationException instead of HTTP 200 and an empty `items` page ===
AWS: Smithy: ListAgreementCharges is @readonly and @paginated (items=items, pageSize=maxResults, inputToken/outputToken=nextToken). NO member of ListAgreementChargesInput is @required: catalog (Catalog @length 1..64, @pattern ^[a-zA-Z0-9.-]+$), agreementId (ResourceId @length 1..64, @pattern ^[A-Za-z0-9_/-]+$), agreementType (AgreementType @length 1..64, @pattern ^[A-Za-z]+$), maxResults (MaxResults @range 1..50), nextToken (NextToken @length max 8192, @pattern ^[a-zA-Z0-9+/=_-]+$). The operation's modeled errors are AccessDeniedException(403), ThrottlingException(429), ValidationException(400) and InternalServerException(500); ValidationException is documented "The input fails to satisfy the constraints specified by the service." and is therefore reserved for input that FAILS a modeled constraint. An agreementId that satisfies ResourceId's length and pattern but names no agreement is not a constraint violation and is not a 404 class for this operation (ResourceNotFoundException is not even modeled here): the filter simply matches nothing, so the service answers HTTP 200 with the `items` member PRESENT and empty and `nextToken` omitted. An empty match set is the normal state of any agreement that has not been charged yet.
Emulator: the same request is refused with HTTP 400 ValidationException, message "Provided agreement id is invalid." (the emulator's reason for this class is INVALID_AGREEMENT_ID, which the enum ValidationExceptionReason does carry). The agreementId sent is a lowercase-hex-and-hyphen UUID, 36 characters — inside @length 1..64 and fully matching @pattern ^[A-Za-z0-9_/-]+$ — so no modeled constraint is violated. The handler is treating "unknown identifier" as "malformed identifier": well-formedness, not resolvability, is what ResourceId constrains. No `items` member comes back at all.
Message detail: the diverging status is 400 where AWS gives 200; the diverging error code is ValidationException where AWS raises none; the diverging message is the fixed text "Provided agreement id is invalid." (entirely fixed text — it carries no value from the request or state), emitted where AWS emits no error body at all. The correct response body has no message: it carries `items` as an empty list with `nextToken` absent.
Why: a client that paginates charges for an agreement with zero charges — a brand-new agreement, or any catalog/agreementType filter that matches nothing — receives a client error and concludes its own request is malformed. Pagination loops that branch on items/nextToken never execute; retry logic keyed on ValidationException will not retry, because a 400 is correctly treated as non-retryable. Since the operation is @readonly the caller has no way to distinguish this from a genuine input rejection, and the emulator makes an "empty" result indistinguishable from "bad request".
Fix: ListAgreementCharges' input validation (the operation's handler/validation in its own op file under the marketplace-agreement crate's src/ops/) must enforce only the modeled input constraints — length/pattern on catalog, agreementId, agreementType, nextToken and @range on maxResults — and must NOT resolve agreementId against stored agreements as a validation step. When the filter matches nothing the handler must return 200 and its serializer must emit `items` as a present, empty list with `nextToken` omitted, not drop the member.

=== Cause 2 of 2: a size-compliant UpdatePurchaseOrders request is refused for an unresolvable chargeId instead of being refused as an unsupported action ===
AWS: Smithy: UpdatePurchaseOrders(purchaseOrders: PurchaseOrders @required, @length min 1 max 86) -> UpdatePurchaseOrdersOutput; errors AccessDeniedException(403), ConflictException(409), ResourceNotFoundException(404), ThrottlingException(429), ValidationException(400), InternalServerException(500). ValidationExceptionReason carries both UNSUPPORTED_ACTION and INVALID_CHARGE_ID, so the model distinguishes the two classes. Recorded behavior: a list of 87 entries violates @length max 86 and is refused 400 ValidationException with the fixed message "Provided purchase orders is invalid." (this leg passes today). The same call trimmed to exactly 86 entries clears the size check and is then refused with 400 ValidationException whose fixed message is "This action is not supported." — purchase-order association is not available to the caller at all, so the service answers the unsupported-action class BEFORE it resolves any entry's chargeId against charge records. The message is wholly fixed text for that class; it carries no id, index or member name from the request.
Emulator: the 86-entry call is refused 400 ValidationException with message "Provided charge id is invalid." — the INVALID_CHARGE_ID class — because the handler now walks the list and resolves each entry's chargeId against stored charges. The chargeIds sent are well-formed ResourceIds (hyphenated alphanumerics inside @length 1..64, matching @pattern ^[A-Za-z0-9_/-]+$) that simply name no stored charge, so as in Cause 1 the handler conflates "unknown identifier" with "invalid identifier"; and it does so instead of answering the unsupported-action refusal that applies to the whole request regardless of entry content.
Message detail: status 400 and code ValidationException both match AWS; the divergence is the message and its reason — fixed text "Provided charge id is invalid." (reason INVALID_CHARGE_ID) where AWS's fixed text is "This action is not supported." (reason UNSUPPORTED_ACTION). Neither string has variable parts.
Why: a client reads the reason/message to decide what to do next. Told its charge id is invalid, it re-reads or re-mints charge ids and resubmits forever, instead of learning that purchase-order association is unavailable and giving up or escalating. It also hides the real behavioral contract: that the 86-entry cap, not the entries' content, is what the oversized request violated — a negative-path test written against the emulator asserts the wrong refusal class and fails against AWS. Additionally, resolving per-entry chargeIds before the request-level support check means a request that AWS refuses uniformly gets refused differently depending on account state.
Fix: UpdatePurchaseOrders' handler (the operation's own op file in the marketplace-agreement crate's src/ops/) must apply the request-level unsupported-action refusal — ValidationException 400, reason UNSUPPORTED_ACTION, fixed message "This action is not supported." — before it resolves any entry's chargeId against state; and chargeId resolution must not be reported as INVALID_CHARGE_ID merely because a well-formed ResourceId names no stored charge.
