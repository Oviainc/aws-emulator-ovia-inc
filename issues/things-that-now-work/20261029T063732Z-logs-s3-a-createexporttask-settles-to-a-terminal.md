## Description
One net-new root cause in the CloudWatch-Logs-to-S3 export surface, grounded in the single failing behavioral check whose id leads with `logs__s3` and which the replay report marks neither ALREADY FILED nor OWNED (its replay key has moved again: the check now fails at a much EARLIER assertion than any open issue carries). Cause 1 of 1: an accepted export task leaves PENDING and reaches a terminal status within a few hundred milliseconds of the create, so a caller that reads DescribeExportTasks immediately after CreateExportTask sees a task that is already settled — and the account's one-active-export quota can therefore never be exercised.
Failing check: logs__s3.log-cwl-plumbing-second-concurrent-export-task-rejected

AWS: Smithy (com.amazonaws.cloudwatchlogs#Logs_20140328) models CreateExportTask(logGroupName @required @length 1..512 @pattern ^[\.\-_/#A-Za-z0-9]+$, from @required long @range min 0, to @required long @range min 0, destination @required @length 1..512, destinationPrefix, logStreamNamePrefix, taskName) -> CreateExportTaskResponse{taskId}, with errors InvalidParameterException (400), LimitExceededException (400), OperationAbortedException (400), ResourceAlreadyExistsException (400), ResourceNotFoundException (400) and ServiceUnavailableException (500); DescribeExportTasks -> ExportTasks whose status.code comes from enum ExportTaskStatusCode [CANCELLED, COMPLETED, FAILED, PENDING, PENDING_CANCEL, RUNNING]. CreateExportTask's own modeled documentation states: "This is an asynchronous call. If all the required information is provided, this operation initiates an export task and responds with the ID of the task. After the task has started, you can use DescribeExportTasks to get the status of the export task. Each account can only have one active (RUNNING or PENDING) export task at a time. To cancel an export task, use CancelExportTask." Two requirements follow from that text. (a) A just-created task is ACTIVE and observably so: the task is minted in PENDING and a DescribeExportTasks issued right after the create reports PENDING (or RUNNING) — a real export of a log group reads the group, gzips the selection and writes it to S3, which takes seconds to minutes, not one API round-trip. (b) While that task is active, a second CreateExportTask in the same account is refused 400 LimitExceededException whose message is the fixed text `Resource limit exceeded.` — entirely fixed, with no variable parts (it names neither the task id nor its status). The duration of an export is not modeled, so the exact dwell is recorded behavior only; what the model DOES pin is that the call is asynchronous and that the active (RUNNING/PENDING) state is a state clients both observe and are rate-limited by.
Emulator: the export task is accepted and then settles essentially instantly. The check creates a first export and immediately calls DescribeExportTasks on it; on all five bounded attempts the status is already in {COMPLETED, CANCELLED, FAILED}, so the check never gets to issue the concurrent second create at all and fails with `AssertionError: never caught the first export while still active in 5 attempts`. The checkout shows why by construction: services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/create_export_task.rs mints the record and advances status purely off a stored clock (`store.materialize_due_export_transitions(now)` at line 243; the record is inserted at line 269), and the dwell constants in that crate's state.rs are EXPORT_TASK_RUNNING_DELAY_MS = 250 (line 720) and EXPORT_TASK_COMPLETION_DELAY_MS = 250 (line 724) — ExportTaskRecord::new sets running_due_ms = creation + 250 ms and completion_due_ms = running_due + 250 ms (state.rs lines ~2089-2106). The whole PENDING -> RUNNING -> COMPLETED lifetime is therefore ~500 ms of wall clock, shorter than a single client API round-trip, and the state.rs comment above those constants asserts the opposite of what is observed ("each is deliberately not zero, so a caller that reads or cancels the task straight after creating it still observes PENDING").
Why: a client relying on AWS's behavior gets two things wrong. First, the active state is unreachable: a client that creates an export and then polls, cancels, or reports on it cannot see PENDING/RUNNING, so CancelExportTask on a freshly created task hits an already-settled task, and any UI or orchestration that models "export in progress" has no state to show. Second, and the reason the check exists, the one-active-export-per-account quota becomes unenforceable in practice: no client can ever provoke the 400 LimitExceededException `Resource limit exceeded.` refusal, so code that handles that quota (back-off, queueing of exports, treating it as throttling) is never exercised against the emulator and a caller that batch-submits exports is silently allowed to do what AWS refuses. Because the status is driven by a clock alone and never by the export actually running, COMPLETED is also reported without any data having been written.
Fix: the export-task lifecycle in the cloudwatch-logs crate — the dwell/clock in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/state.rs that `materialize_due_export_transitions` drives, and the task the handler services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/create_export_task.rs mints. A created task must remain in an active status (PENDING, then RUNNING) long enough for the API to be observed in that state across at least one client round-trip, and it must reach COMPLETED only after the export has actually run (the group's events in the requested window selected, gzipped and written through the S3 data plane under destinationPrefix) rather than on a fixed timer; while it is active, CreateExportTask must keep refusing a second create 400 LimitExceededException with the fixed message `Resource limit exceeded.`.
