# FIS: 4 fidelity divergences — non-wait experiment actions end 'failed' immediately (no action execution / fault injection), permission failures mis-attributed, wait runs only settle after full real time, roleArn account-ownership rule not enforced

> _Note: this issue was identified against the code base at commit `a25176d5b2a976d6230e754c8e419e3d957ef7d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExperiment

## Description
FOUR distinct root causes in the emulated FIS surface, each grounded in failing behavioral checks of the replay suite. A fixer must close ALL FOUR causes before submitting. Smithy citations are from services/service-com-amazonaws-fis-faultinjectionsimulator/smithy-model/com-amazonaws-fis-faultinjectionsimulator.json. Three issues are already open on this service (20261022T063355Z-fis-8-fidelity-divergences-targetaccountconfiguration-accepts-invalid-accountid.md, 20261022T093447Z-fis-4-fidelity-divergences-cloudformation-aws-fis-experimenttemplate.md, 20261022T043627Z-fis-describestacks-omits-the-outputs-member-for-a-stack.md). The replay suite did NOT report any of the checks below as owned by them: the emulator's behaviour on these checks has CHANGED (it no longer times out or accepts the bad input, it now fails the experiment outright or refuses with a different rule), so these are new failure modes and are recorded here; where a cause is the successor of a cause in 20261022T063355Z it is noted explicitly.

Cause 1 of 4: an experiment whose template carries ANY action other than aws:fis:wait is driven to the terminal status 'failed' about half a second after StartExperiment, instead of running the action.
AWS: StartExperiment runs the template's actions under the template roleArn; the experiment walks pending/initiating -> running for the action's duration and then reaches 'completed' (Smithy: ExperimentStatus = pending, initiating, running, completed, stopping, stopped, failed, cancelled; ExperimentState = {status, reason, error}). While an aws:fis:inject-api-internal-error / aws:fis:inject-api-throttle-error action is running, the fault is actually live: the check records (real AWS us-west-2, 2026-09-14, service=ec2, operations=DescribeAvailabilityZones, percentage=100, duration=PT2M) that calls made under the targeted role answer HTTP 500 with Error.Code 'InternalError' while a control caller and an unlisted operation are unaffected. The requirement is that a non-wait action does not terminate the experiment: the experiment must be observable in 'running' for the action's duration and end in a terminal status earned by the action ('completed', or 'stopped' when a stop condition or StopExperiment intervenes).
Emulator: the run span for any template containing a non-wait action is fixed at the 0.5 s transition delay and the outcome is hardcoded to failed with reason 'This emulator does not inject faults, so the experiment's <actionId> action could not be run' (state.rs run_plan / ExperimentOutcome::Failed). Replay observes state.status == 'failed' (never 'running') for aws:fis:inject-api-internal-error, aws:fis:inject-api-throttle-error and aws:cloudwatch:assert-alarm-state templates, including in the single-account and multi-account end-to-end flows.
Why: every client workflow that starts a real FIS experiment and waits for it to run or complete gets an immediate failure instead; fault-injection tests pass vacuously or break, resolved-targets and stop/teardown paths downstream of 'running' are unreachable, and the state.reason is emulator prose rather than an AWS experiment outcome.
Fix: the experiment runtime in the FIS state/engine (state.rs run_plan/settle plus the StartExperiment handler): give every action with a duration a real run span, carry the experiment through 'running' to a terminal status, and model the injected API fault for the targeted role rather than declining the run.
Traces: fis.e2e-experiment-create-start-observe-stop-teardown, fis.e2e-experiment-full-flow-with-target-accounts, fis.fis-injected-api-internal-error-fails-a-role-scoped-ec2-call-and-spares-a-control-caller, fis.fis-stop-condition-breach-halts-a-live-api-fault-and-the-fault-actually-stops

Cause 2 of 4: an execution-role permission failure is not evaluated, so the experiment's failure is mis-attributed.
AWS: an action is executed under the template's roleArn; when that role lacks the permission the action needs (cloudwatch:DescribeAlarms for aws:cloudwatch:assert-alarm-state) the experiment ends in terminal status 'failed' and ExperimentState.reason names an insufficient-privileges failure (recorded behaviour: the reason contains 'not enough privileges'; Smithy: ExperimentState.reason -> ExperimentStatusReason, 'The reason for the state', and ExperimentState.error -> ExperimentError 'the error information of the experiment when the action has failed'). An otherwise identical template whose role DOES carry the permission reaches 'completed'. The requirement is the attribution: a privileges failure must be distinguishable from any other execution failure, and a permissioned role must not fail.
Emulator: the status is 'failed' but for the wrong reason — reason is 'This emulator does not inject faults, so the experiment's aws:cloudwatch:assert-alarm-state action could not be run', and the permissioned sibling template fails identically, so least-privilege enforcement is unobservable and the two runs are indistinguishable. This is the successor of Cause 7 of open issue 20261022T063355Z (which recorded the same check timing out); the emulator now fails fast instead of hanging, so the key no longer matches.
Why: a client cannot tell a run AWS would have refused on IAM from one it would have completed; failure-handling branches keyed on the privileges reason never fire, and an IAM misconfiguration looks exactly like a success-path run.
Fix: the experiment runtime (evaluate the template role's permissions for each action before/while executing it and set state.status='failed' with a privileges reason, populating ExperimentState.error), in the FIS state/engine alongside Cause 1.
Traces: fis.start-experiment-with-role-lacking-permissions-denied

Cause 3 of 4: a wait-only experiment settles only after the action's FULL wall-clock duration has elapsed, so a PT1M run never reaches a terminal status inside the suite's per-check budget.
AWS: a template whose single action is aws:fis:wait with duration PT1M walks pending/initiating -> running -> completed, with startTime and endTime set, and StopExperiment on the resulting completed experiment is then refused with ValidationException (HTTP 400). Recorded behaviour only for the pacing: AWS publishes no duration for initiating -> running.
Emulator: the experiment reaches 'running' after 0.5 s but the run span is the literal parsed wait duration, materialised only by clock-driven settle (state.rs TRANSITION_DELAY = 500 ms; run_plan -> critical_path; ExperimentRecord::settle), so 'completed' first becomes observable just past 60 s after StartExperiment. All three wait-lifecycle checks are reported as 'Check timed out after 60.0s' and never observe a terminal status; the StopExperiment-on-completed assertion (expected ValidationException, message rule 'Cannot modify the state of an experiment in final state: <id>.') is never reached. Hypothesis: the full real-time run span is what pushes completion outside the budget — the emulator progresses correctly, just too slowly to be observed. Note that a previous issue on wait-action completion (20261022T043627Z-fis-control-plane-9-fidelity-divergences-no-wait.md) is resolved; this is the pacing remnant, not the missing transition.
Why: every client (and every test) that starts a wait experiment against the emulator and waits for it to finish must block for the entire modelled duration — up to the documented 720-minute maximum — so emulator-based lifecycle and final-state tests cannot complete, and the terminal-state behaviours that follow completion (endTime, StopExperiment refusal on a final state) are unreachable.
Fix: the experiment runtime's pacing in the FIS state (state.rs run_plan/critical_path/settle): drive the modelled run on a compressed clock so a wait experiment reaches 'running' and then its terminal status promptly, while still exposing each transient status at least once.
Traces: fis.experiment-lifecycle-pending-to-completed, fis.start-experiment-transitions-to-running-then-completed, fis.stop-completed-experiment-rejected

Cause 4 of 4: CreateTargetAccountConfiguration validates roleArn's SYNTAX only, not the rule that the role must belong to accountId.
AWS: roleArn is modelled loosely (Smithy: RoleArn, @length 20..2048, @pattern ^[\S]+$), so the rule is enforced server-side: a roleArn whose account part is not the accountId being configured is refused with ValidationException (HTTP 400) and nothing is persisted, with a request-derived message naming the roleArn parameter and the role/accountId relationship — recorded example 'The roleArn parameter value is not valid. The IAM role must belong to the account specified in the accountId parameter value.' That relationship is the requirement; the text is an example.
Emulator: the status (400) and code (ValidationException) are right but the refusal is taken on ARN syntax alone — message 'Value for roleArn is not a valid ARN.' — so the account-ownership check is not the one being applied, and a syntactically valid ARN belonging to a DIFFERENT account is not covered by it. This is the successor of Cause 2 of open issue 20261022T063355Z (which recorded this call returning HTTP 200); the emulator now refuses the malformed ARN, so that issue's key no longer matches, but the account-ownership rule is still missing.
Why: a client's negative path is classified by the wrong rule, and a well-formed roleArn from an account other than accountId is still accepted, persisting a configuration real FIS never would and deferring the failure to experiment execution.
Fix: CreateTargetAccountConfiguration's input validation (parse roleArn and compare its account id to the accountId member, in addition to the syntax check), in the FIS handler/state validation path.
Traces: fis.create-target-account-configuration-malformed-role-arn-rejected
