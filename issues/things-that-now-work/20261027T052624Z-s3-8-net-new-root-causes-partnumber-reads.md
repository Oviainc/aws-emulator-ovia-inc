# s3: 8 net-new root causes — PartNumber reads, ranged GET, conditional PutObject, multipart/encryption refusal wording, archived-class GET, presigned GET, and metadata-configuration provisioning

> _Note: this issue was identified against the code base at commit `fbdf9d3baa643423c5a7eac120dec57cfd2abcbc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
Eight distinct net-new root causes in the s3 service. Each is numbered below and carries its own failing check ids; all eight must be closed before this issue is submitted. None of these checks was marked ALREADY FILED or OWNED by the replay report. Where an existing open issue sounds adjacent it is named in the cause, but it does not carry these replay keys: the s3 object-plane bundle `20261025T032458Z-s3-object-plane-10-root-causes-conditional-requests.md` names 'conditional requests / Range / archived state' generically and the metadata-configuration scaffold issues name only `DeleteBucketMetadataConfiguration` / `UpdateBucketMetadataJournalTableConfiguration`.

Cause 1 of 8 — HeadObject/GetObject with PartNumber answers a bare 501.
AWS: Smithy (s3) HeadObject.PartNumber is a modelled input member bound to httpQuery `partNumber`, and HeadObject/GetObject output carries PartsCount (httpHeader `x-amz-mp-parts-count`) and ContentRange (httpHeader `Content-Range`). A part-scoped read of a completed multipart object answers HTTP 206 with ContentLength equal to that part's length, ContentRange `bytes <first>-<last>/<total>` and PartsCount equal to the object's part count; a part number greater than PartsCount is refused with error code `InvalidPartNumber`, HTTP 416 and the message `The requested partnumber is not satisfiable` (fixed text, no variable parts). A whole-object read reports no PartsCount. Emulator: `HeadObject` with PartNumber answers `ClientError (501) ... Not Implemented` — a bare status with no S3 error code at all, so the part-discovery call cannot be made. Why: every parallel-download client (the AWS CRT, s3transfer, `aws s3 cp`) discovers part boundaries with one HEAD at PartNumber=1 and then fans out; against this emulator that first call fails hard, and an emulator that instead silently ignored PartNumber would hand back the whole object and look like success. Fix: PartNumber handling in the HeadObject and GetObject handlers (part-boundary retention through CompleteMultipartUpload in the object state, the 206/PartsCount/ContentRange serialization, and the InvalidPartNumber refusal). Traces: s3.get-object-part-number-reads-single-part.

Cause 2 of 8 — GetObject with a Range header is an unimplemented scaffold stub.
AWS: Smithy (s3) GetObject.Range is a modelled input member bound to httpHeader `Range`; a ranged read answers HTTP 206 with Content-Range and the requested byte span. Emulator: the call is refused with error code `NotImplemented` and the message `operation GetObject with Range is scaffolded but not implemented in this emulator`. Why: ranged GET is how every multi-threaded download path reads a large object, so `aws s3 cp` of any object above the CLI's multipart threshold fails outright with `download failed: ... An error occurred (NotImplemented)`; no large object can be read back. Fix: the Range branch of the GetObject handler (byte-span slicing in the object read path plus the 206/Content-Range serialization). Traces: s3.cli-s3-cp-large-file-multipart-checksum-defaults.

Cause 3 of 8 — PutObject with If-Match is an unimplemented scaffold stub instead of a precondition refusal.
AWS: Smithy (s3) PutObject.IfMatch is a modelled input member bound to httpHeader `If-Match`. A conditional write whose If-Match ETag does not match the current object is refused with error code `PreconditionFailed`, HTTP 412 and the message `At least one of the pre-conditions you specified did not hold` (fixed text, no variable parts), and the stored object is left intact. Emulator: the call is refused with error code `NotImplemented` and the message `operation PutObject with If-Match is scaffolded but not implemented in this emulator`. Why: If-Match on PutObject is S3's compare-and-swap primitive; a client using it for optimistic concurrency cannot distinguish 'my write lost the race' from 'the service has no idea what I asked', and retry logic keyed on PreconditionFailed never fires. Fix: the If-Match branch of the PutObject handler — the ETag comparison against current object state and the PreconditionFailed refusal. Traces: s3.put-object-if-match-conditional.

Cause 4 of 8 — CompleteMultipartUpload's out-of-order refusal uses different wording than AWS.
AWS: an unordered part list is refused with error code `InvalidPartOrder` and the message `The list of parts was not in ascending order. Parts must be ordered by part number.` — entirely fixed text, no values from the request. The s3 Smithy model declares no errors on CompleteMultipartUpload, so the exact text is recorded behavior only. Emulator: the same refusal carries `The list of parts was not in ascending order. The parts list must be specified in order by part number.` — the first sentence matches, the second is reworded. Why: clients and test suites that match on S3's refusal text (and human operators reading it) see a message AWS never emits. Fix: the message template for the InvalidPartOrder refusal in the CompleteMultipartUpload handler's validation. Traces: s3.multipart-complete-part-ordering-enforced.

Cause 5 of 8 — PutBucketEncryption's KMSMasterKeyID-with-AES256 refusal emits an internal diagnostic instead of AWS's message.
AWS: Smithy (s3) PutBucketEncryption takes ServerSideEncryptionConfiguration; a rule whose ApplyServerSideEncryptionByDefault names a KMSMasterKeyID while SSEAlgorithm is `AES256` is refused with error code `InvalidArgument` and the message `a KMSMasterKeyID is not applicable if the default sse algorithm is not aws:kms or aws:kms:dsse` — entirely fixed text (recorded behavior only for the text; the model declares no errors on this operation). Emulator: the code is correct (`InvalidArgument`) but the message is `ApplyServerSideEncryptionByDefault.KMSMasterKeyID is allowed if and only if SSEAlgorithm is one of ["aws:kms", "aws:kms:dsse"], got Some("AES256")` — a Rust-shaped diagnostic including a `Some(..)` debug rendering, which AWS never produces. Why: the refusal is correct in class but unrecognizable; anything asserting on S3's documented message, and any operator reading the error, is misled, and the `Some(..)` leak exposes emulator internals. Fix: the message template for this InvalidArgument refusal in the PutBucketEncryption validation. Traces: s3.sseinv-kms-master-key-id-with-an-aes256-default-rejected.

Cause 6 of 8 — GetObject serves an archived-storage-class object instead of refusing it.
AWS: Smithy (s3) models `InvalidObjectState` (errorKind client, httpError 403) and documents it as 'Object is archived and inaccessible until restored' for the GLACIER / DEEP_ARCHIVE classes; a GetObject against such an object is refused with code `InvalidObjectState`, HTTP 403 and the message `The operation is not valid for the object's storage class` (fixed text) until RestoreObject has run. The object's class here is set on CreateMultipartUpload (StorageClass=GLACIER) and survives CompleteMultipartUpload. Emulator: GetObject answers HTTP 200 and streams the body, with `x-amz-storage-class: GLACIER` on the very same response — so it reports the archived class and serves the bytes anyway. Why: a client never learns it must restore first; archival workflows appear to work against the emulator and then fail in production, and cost/latency behavior that depends on the restore step is never exercised. Fix: the storage-class gate in the GetObject read path (and the same gate for objects whose class was set through the multipart create). Traces: s3.deep-s3-storage-class-multipart-class-complete-after-abort-rejected.

Cause 7 of 8 — a presigned GET URL for a completed multipart object answers 404.
AWS: a presigned GET generated for an existing key serves that object's bytes over the data-plane endpoint with HTTP 200, exactly as a signed GetObject would; the signature is the only difference. Recorded behavior only (presigning is an SDK/endpoint concern, not a modelled operation). Emulator: fetching the presigned URL returns `HTTP Error 404: Not Found` for a key that CompleteMultipartUpload just created and that GetObject can read. Why: presigned URLs are the standard way browsers and third parties read S3 objects; every such flow is unusable, and the 404 misreports an existing object as absent rather than reporting an auth problem. Fix: the data-plane route that serves presigned (query-string-authenticated) object reads — it must resolve the same object state the signed API path resolves. Traces: s3.multipart-upload-and-presigned-get-round-trip.

Cause 8 of 8 — a created bucket metadata configuration never reaches ACTIVE, so its conflict refusal is unreachable.
AWS: Smithy (s3) CreateBucketMetadataConfiguration (POST /{Bucket}?metadataConfiguration) provisions the journal table asynchronously; GetBucketMetadataConfiguration then reports GetBucketMetadataConfigurationResult.MetadataConfigurationResult.JournalTableConfigurationResult.TableStatus transitioning to `ACTIVE`. A second create while a configuration is active is refused with code `MetadataConfigurationAlreadyExists` and the message `The metadata configuration already exists`; after the configuration is deleted, an identical create is accepted but its provisioning lands in TableStatus `FAILED` carrying ErrorCode `JournalTableAlreadyExists` and the message `A journal table already exists in the AWS managed table bucket's namespace. Delete the journal table, and then try again. To create a new S3 Metadata table, you must delete the S3 Metadata configuration for this bucket, and then create a new S3 Metadata configuration.` (fixed text). Emulator: the create is accepted but the polled TableStatus never becomes ACTIVE, so the check exhausts its 60s budget before it can assert anything — no status transition, hence no conflict refusal and no FAILED/JournalTableAlreadyExists path. Why: S3 Metadata is unusable — a client that waits for ACTIVE (as the API requires) hangs forever, and the two documented conflict behaviors can never be observed. Fix: the metadata-configuration state machine behind CreateBucketMetadataConfiguration / GetBucketMetadataConfiguration (status progression to ACTIVE, the already-exists refusal, and the leftover-journal-table FAILED result). Traces: s3.create-bucket-metadata-table-configuration-name-conflict-rejected.
