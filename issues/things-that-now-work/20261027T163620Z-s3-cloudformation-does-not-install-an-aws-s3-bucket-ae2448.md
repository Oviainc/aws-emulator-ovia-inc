# CloudFormation does not install an AWS::S3::Bucket InventoryConfigurations property: after CREATE_COMPLETE ListBucketInventoryConfigurations reports an empty list

> _Note: this issue was identified against the code base at commit `de2a758d888a26724f6774bb8d661e6e5775621b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListBucketInventoryConfigurations

## Description
One net-new root cause in the S3 surface, grounded in one failing behavioral check.

Cause 1 of 1: an AWS::S3::Bucket that declares an InventoryConfigurations property is provisioned WITHOUT it. The stack reaches CREATE_COMPLETE and publishes both bucket names as outputs, but ListBucketInventoryConfigurations on the deployed source bucket answers HTTP 200 with no InventoryConfigurationList entries, so the whole IaC -> API translation this scenario exists for is unobservable. Failing check: s3.s3-inventory-e2e-configs-with-prefix-lifecycle (verdict: mismatch, phase 1/4 'deploy').

AWS: Smithy s3#ListBucketInventoryConfigurations is GET /{Bucket}?inventory&x-id=ListBucketInventoryConfigurations, HTTP 200, output shape ListBucketInventoryConfigurationsOutput (xmlName ListInventoryConfigurationsResult) with members IsTruncated (boolean), ContinuationToken, NextContinuationToken and InventoryConfigurationList (xmlName InventoryConfiguration, xmlFlattened; the operation's own documentation states a bucket may carry up to 1,000 configurations and the listing 'does not return more than 100 configurations at a time'); errors: []. Each entry is s3#InventoryConfiguration { Id (required), IsEnabled (required, boolean), Destination (required), Schedule (required), IncludedObjectVersions (required, enum), Filter, OptionalFields }. s3#InventoryDestination = { S3BucketDestination (required) } = s3#InventoryS3BucketDestination { Bucket (required — documented as 'The Amazon Resource Name (ARN) of the bucket where inventory results will be published'), Format (required, enum), AccountId, Prefix, Encryption }. s3#InventorySchedule = { Frequency (required, enum) }; s3#InventoryFilter = { Prefix (required) }.
CloudFormation is handed the FLAT form on AWS::S3::Bucket — InventoryConfiguration[] entries carrying Id, Enabled, Prefix, ScheduleFrequency, DestinationBucketArn, Format, IncludedObjectVersions — and S3's API must report the same configuration in the NESTED modeled form: the template's flat `Prefix` surfacing as Filter.Prefix, its flat `ScheduleFrequency` surfacing as Schedule = { Frequency: <that value> }, its `Enabled: true` surfacing as IsEnabled = true (a bool, not a string), its DestinationBucketArn (resolved by GetAtt on the destination bucket) surfacing as Destination.S3BucketDestination.Bucket, and — because the template sets NO destination prefix — Destination.S3BucketDestination carrying NO Prefix member at all. On real AWS, a bucket created from that template lists exactly the declared Ids. The per-run values here (the generated bucket names, the destination bucket ARN, the configuration id string the stack parameter supplies, the source prefix) come from the request and the account; only the SHAPE, the key presence/absence, and the set of declared Ids are the requirement.

Emulator: the stack reaches CREATE_COMPLETE and the SourceBucketName/DestinationBucketName/DestinationBucketArn outputs all resolve (the check got past those assertions), but ListBucketInventoryConfigurations on the deployed source bucket returns a well-formed, untruncated, EMPTY listing. Replay detail: `AssertionError: [phase 1/4 deploy] the template declares exactly one inventory configuration; the API reports []`. This is not an S3 handler stub: services/service-com-amazonaws-s3-amazons3/src/ops/put_bucket_inventory_configuration.rs and .../list_bucket_inventory_configurations.rs are both documented IMPLEMENTED (put records one configuration per id on an existing bucket and refuses NoSuchBucket/404 for a bucket the emulator does not hold; list walks that same store in ascending id order with 100-per-page paging and answers NoSuchBucket/404 for an unheld bucket), and the replayed call returned a 200 empty listing rather than a refusal. The declared configuration is therefore dropped during stack provisioning and never written into the S3 inventory store.

Why: a client that manages S3 Inventory through IaC — which is the only way this scenario configures it — gets a stack that reports success and a bucket with no inventory configuration. Every downstream read then fails silently: list-bucket-inventory-configurations returns nothing to filter, the JMESPath query over InventoryConfigurationList[?Destination.S3BucketDestination.Prefix==null].Id selects nothing, the source-side Filter.Prefix and the destination bucket ARN cannot be recovered, and a configuration that deliberately omits its destination prefix cannot be told from one that sets it. Because CREATE_COMPLETE is still reported there is no deploy-time failure signal either, so the gap is only discovered by the consumer that cannot find the configuration.

Fix: the CloudFormation resource provisioner for AWS::S3::Bucket — translate the template's InventoryConfigurations list into the S3 inventory configuration store (one stored configuration per declared Id, mapping the flat template members onto the modeled nested shapes: Prefix -> Filter.Prefix, ScheduleFrequency -> Schedule.Frequency, Enabled -> IsEnabled as a bool, DestinationBucketArn -> Destination.S3BucketDestination.Bucket with the GetAtt-resolved ARN, Format -> Destination.S3BucketDestination.Format, IncludedObjectVersions passed through, and NO Destination.S3BucketDestination.Prefix member when the template declares none), so that S3's already-implemented Put/Get/List inventory handlers report it. No change is needed inside those S3 handlers.

Related (does NOT cover this): 20261026T052114Z-s3-cloudformation-does-not-install-an-aws-s3-bucket.md reports the identical provisioning pattern for the bucket's AnalyticsConfigurations property and names neither InventoryConfigurations nor this check id; the DeleteBucketInventoryConfiguration scaffold stub is separately filed from s3.bucket-inventory-configuration-roundtrip and blocks this check's LATER 'cleanup' phase, but this check never reaches it — it fails in phase 1 on the missing configuration.

Traces: s3.s3-inventory-e2e-configs-with-prefix-lifecycle (fails in its first phase, 'deploy').

## Evidence
Failing check: s3.s3-inventory-e2e-configs-with-prefix-lifecycle (verdict: mismatch), phase 1/4 'deploy'.

Actual: `AssertionError: [phase 1/4 deploy] the template declares exactly one inventory configuration; the API reports []` — ListBucketInventoryConfigurations answered HTTP 200 with an empty InventoryConfigurationList (and IsTruncated=false, so no further page) for the bucket the stack had just created. The stack itself reached CREATE_COMPLETE and published SourceBucketName, DestinationBucketName and DestinationBucketArn as outputs, so the check passed both of the assertions that precede this one.

Expected (real AWS, same template): ListBucketInventoryConfigurations on the deployed source bucket lists exactly ONE s3#InventoryConfiguration, carrying
- Id = the id the template declared (supplied as the InventoryConfigurationId stack parameter);
- Filter = { Prefix: <the SourcePrefix the template declared> } — CloudFormation's flat `Prefix` surfacing as the nested Filter.Prefix;
- Schedule = { Frequency: 'Daily' } — CloudFormation's flat `ScheduleFrequency` surfacing as the nested single-member map;
- IsEnabled = true, a boolean, from the template's `Enabled: true`;
- Destination.S3BucketDestination.Bucket = the destination bucket ARN CloudFormation resolved from GetAtt (the same value the stack published as its DestinationBucketArn output), a six-field `arn:<partition>:s3:::<name>` ARN;
- Destination.S3BucketDestination carrying NO `Prefix` member, because the template sets no destination prefix — that OMISSION is the scenario's answer, and reporting an empty-string Prefix would also be a divergence.
And, in the check's later 'cleanup' phase, after DeleteBucketInventoryConfiguration for that id the response body must OMIT InventoryConfigurationList entirely (exactly as a never-configured bucket does, not return it empty) while still carrying IsTruncated=false.

Smithy cited: s3#ListBucketInventoryConfigurations — GET /{Bucket}?inventory&x-id=ListBucketInventoryConfigurations, code 200; input { Bucket required @httpLabel, ContinuationToken @httpQuery continuation-token, ExpectedBucketOwner @httpHeader x-amz-expected-bucket-owner }; output ListBucketInventoryConfigurationsOutput (xmlName ListInventoryConfigurationsResult) { IsTruncated boolean, ContinuationToken, NextContinuationToken, InventoryConfigurationList (xmlName InventoryConfiguration, xmlFlattened) }; errors: []. s3#InventoryConfiguration { Id required, IsEnabled required boolean, Destination required, Schedule required, IncludedObjectVersions required enum, Filter, OptionalFields }. s3#InventoryDestination { S3BucketDestination required }. s3#InventoryS3BucketDestination { Bucket required (the destination bucket ARN), Format required enum, AccountId, Prefix, Encryption }. s3#InventorySchedule { Frequency required enum }. s3#InventoryFilter { Prefix required }. Companion writes: s3#PutBucketInventoryConfiguration PUT /{Bucket}?inventory (Id @httpQuery id required, InventoryConfiguration @httpPayload required, 200) and s3#DeleteBucketInventoryConfiguration DELETE /{Bucket}?inventory (204). The CloudFormation-side FLAT property shape, and the fact that a CREATE_COMPLETE stack's configuration is immediately listable, are recorded behavior from the check's own frozen oracle — not modeled by the S3 Smithy model.

Emulator-side grounding that this is a provisioning gap and not an S3 stub: services/service-com-amazonaws-s3-amazons3/src/ops/put_bucket_inventory_configuration.rs line 4 declares 'IMPLEMENTED: records an S3 Inventory configuration on an existing bucket under the inventory id the request identifies it by' and its handle() writes through bucket.put_inventory_configuration (line 339); services/service-com-amazonaws-s3-amazons3/src/ops/list_bucket_inventory_configurations.rs line 4 declares 'IMPLEMENTED: reports the S3 Inventory configurations the named bucket carries, in ascending id order, computed from the store PutBucketInventoryConfiguration wrote to', walks bucket.inventory_configurations() (line 298) and answers NoSuchBucket for an unheld bucket (line 285). The replayed list call returned a 200 empty listing, not that 404 and not a 501 — so the bucket exists in the emulator's store and simply carries no inventory configuration.

## Steps to Reproduce
1. Boot the emulator and re-replay the behavioral check s3.s3-inventory-e2e-configs-with-prefix-lifecycle (the only id in trace_ids). It fails in phase 1/4 'deploy'.

Manual repro:
2. CreateStack with a template declaring two AWS::S3::Bucket resources — a destination bucket, and a source bucket whose InventoryConfigurations property carries exactly one entry: Id = <some id>, Enabled = true, Prefix = <some source prefix>, ScheduleFrequency = 'Daily', IncludedObjectVersions = 'Current', Format = 'CSV', DestinationBucketArn = !GetAtt <destination bucket>.Arn, and NO destination prefix. Publish the source bucket name, the destination bucket name and the destination bucket ARN as stack Outputs.
3. Wait for CREATE_COMPLETE and read the source bucket name and the destination ARN from describe-stacks Outputs.
4. Call `aws s3api list-bucket-inventory-configurations --bucket <the source bucket>`. Expected: one InventoryConfiguration whose Id is the declared id, whose Filter is { Prefix: <the source prefix> }, whose Schedule is { Frequency: 'Daily' }, whose IsEnabled is true, and whose Destination.S3BucketDestination has Bucket = the destination ARN and NO Prefix key. Actual: HTTP 200 with an empty listing (no InventoryConfigurationList entries, IsTruncated false).
5. Control, to isolate the loss to the stack provisioner rather than S3: PutBucketInventoryConfiguration the same configuration directly on a hand-made bucket and list it back — it is reported with the nested shapes, which shows the S3 inventory store and listing work.
6. Then DeleteBucketInventoryConfiguration for that id on the hand-made bucket and list again: the body must be exactly { IsTruncated: false } with InventoryConfigurationList OMITTED (this leg is additionally blocked by the separately-filed DeleteBucketInventoryConfiguration scaffold stub).
