# license-manager-user-subscriptions refusal fidelity: IAM not enforced on ListInstances, filter/directory refusal wording, and StopProductSubscription fails open as ResourceNotFound

> _Note: this issue was identified against the code base at commit `f4d2c47849283505bef5d66ed0dfe45248bd135a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListInstances

## Description
SHARED FAULT (4 causes, all in the license-manager-user-subscriptions crate): the service's negative paths diverge from AWS - one refusal is not produced at all (no identity-based authorization), two refusals carry emulator-authored text or report the wrong precondition, and one refusal uses the wrong error class entirely. All four were found by replaying the behavioral suite simparity-behavioral-aws-v1 (13/18 passed; all 5 failures are in this service). A fixer must close all FOUR causes.

Cause 1 of 4 - ListInstances with a Filter.Attribute the service does not support is refused with emulator-authored text.
AWS: recorded behavior only. Smithy (services/service-com-amazonaws-licensemanagerusersubscriptions-licensemanagerusersubscriptions): Filter is a structure of three plain Strings (Attribute/Operation/Value) with no enum, so the filterable-attribute set is not modeled; ListInstances binds ValidationException (errorKind client, httpError 400 defaulted). The recorded refusal is HTTP 400 ValidationException with the message template "Invalid Filter attribute <attribute>": the fixed text is "Invalid Filter attribute " and the single variable part is the rejected attribute name copied verbatim from the request's Filters[].Attribute (NotARealAttributeXYZ is this run's value, not part of the template). A documented attribute (e.g. InstanceId with Operation Equals) is still accepted and returns InstanceSummaries.
Emulator: HTTP 400 ValidationException, but the message is 'Filter.Attribute NotARealAttributeXYZ is not filterable; supported attributes: Status, InstanceId' - different fixed text, a member-path prefix the service does not use, and an emulator-invented enumeration of supported attributes appended.
Why: a client or test matching the service's refusal text does not match, and the appended "supported attributes" list is guidance AWS never emits and that may not reflect what the service accepts.
Fix: the ListInstances handler's filter validation - emit the service's message template instead of composing one locally.
Traces: check license-manager-user-subscriptions.list-instances-bogus-filter-attribute-rejected (the valid-filter positive control in the same check passes).
Note: open issue 20261029T234938Z-license-manager-user-subscriptions-400-refusal-bodies-are.md describes this same wording fault from the WIRE corpus (its cause 1) but does not carry this behavioral check id; it is named here so a fixer can close both with one change.

Cause 2 of 4 - no identity-based authorization is enforced: a caller with no permissions at all is served ListInstances successfully.
AWS: recorded behavior only for the message; the class is modeled - ListInstances binds AccessDeniedException (errorKind client, httpError 400 defaulted). A request signed with the credentials of a freshly created IAM user that has no policy attached is refused with AccessDeniedException and the standard identity-based-denial sentence: fixed text "User: " / " is not authorized to perform: " / " on resource: " / " because no identity-based policy allows the " / " action", whose variable parts are all taken from the request and the account - the caller's IAM user ARN (arn:aws:iam::<account>:user/<user-name>), the action "license-manager-user-subscriptions:ListInstances", and the resource ARN arn:aws:license-manager-user-subscriptions:<region>:<account>:/instance/ListInstances. The <account>, <region> and <user-name> values from any single run fill the template; they are not part of it.
Emulator: the unprivileged caller's ListInstances call SUCCEEDS and returns a normal InstanceSummaries response - no refusal of any kind, so no status/code/message is produced where AWS produces 400 AccessDeniedException.
Why: this is the overly-permissive failure mode. Any test or client that validates least-privilege behavior (expecting a denial for an unauthorized principal) passes against the emulator and fails against AWS; policy-regression suites built on the emulator are worthless because every principal is effectively an administrator.
Fix: an authorization gate in the service's request pipeline (the crate's per-operation authorization step, before the operation handler's own validation) that resolves the signing credentials to an IAM principal, evaluates license-manager-user-subscriptions:<Operation> against that principal's identity-based policies and raises AccessDeniedException with the template above when nothing allows it.
Traces: check license-manager-user-subscriptions.list-instances-missing-permission-rejected (the permissioned positive control in the same check succeeds, as it must).

Cause 3 of 4 - RegisterIdentityProvider resolves Settings.Subnets before the DirectoryId, so the directory prerequisite is never reported.
AWS: recorded behavior only. Smithy: RegisterIdentityProviderRequest requires IdentityProvider and Product, with optional Settings (Subnets @length min 1 required, SecurityGroupId @pattern ^sg-(([0-9a-z]{8})|([0-9a-z]{17}))$ required); the refusal class is ValidationException (httpError 400). For a syntactically valid but non-existent/inactive AWS Directory Service DirectoryId the service refuses with HTTP 400 ValidationException and the template "<directoryId> directory either cannot be found or is not in active state" - fixed text " directory either cannot be found or is not in active state" preceded by the one variable part, the DirectoryId copied from the request's IdentityProvider.ActiveDirectoryIdentityProvider.DirectoryId. The directory is resolved BEFORE the Settings' network resources, so two calls naming two different bogus directories each name their OWN id, and an equally bogus subnet/security group in Settings is never what is reported. Product is validated first and independently (the invalid-Product refusal "Invalid product <product>" is produced correctly by the emulator today).
Emulator: HTTP 400 ValidationException with "The subnet ID 'subnet-0123456789abcdef0' does not exist" - it resolves Settings.Subnets first, so the caller is told about the wrong missing prerequisite and can never learn the DirectoryId was wrong.
Why: a client that fixes the reported problem (creating/correcting the subnet) retries and is refused again, because the actual blocker - the directory - is never named; nothing in the response distinguishes two different non-existent directories.
Fix: the RegisterIdentityProvider handler's precondition ordering - resolve and refuse on IdentityProvider's DirectoryId (using the service's directory-refusal template) before validating Settings' Subnets and SecurityGroupId.
Traces: checks license-manager-user-subscriptions.register-identity-provider-directory-not-found and license-manager-user-subscriptions.register-identity-provider-invalid-product-rejected (the latter's invalid-Product assertion passes; it fails on the same directory-vs-subnet ordering at its second call).
Note: open issue 20261029T234938Z-license-manager-user-subscriptions-400-refusal-bodies-are.md cause 3 reports the same ordering fault surfacing via SecurityGroupId, and 20261024T124828Z-license-manager-user-subscriptions-registeridentityprovider-event-propagation.md is about whether network resources are resolved at all; neither carries these behavioral check ids.

Cause 4 of 4 - StopProductSubscription with a well-formed but never-created ProductUserArn answers ResourceNotFoundException instead of failing closed with UnauthorizedException.
AWS: recorded behavior only for this path. Smithy: StopProductSubscriptionRequest accepts either ProductUserArn (target Arn, @pattern ^arn:[a-z0-9-\.]{1,63}:[a-z0-9-\.]{1,63}:[a-z0-9-\.]{1,63}:[a-z0-9-\.]{1,63}:[a-zA-Z0-9-\.]{1,510}/[a-zA-Z0-9-\.]{1,510}$) or the Username/IdentityProvider/Product triple; the modeled errors include ResourceNotFoundException (httpError 404) and ValidationException (400), and UnauthorizedException is NOT modeled at all. Calling with neither identifier is refused with ValidationException "IdentityProvider, Product, and Username must be provided" (entirely fixed text - the emulator already matches this). Supplying a fully-specified ProductUserArn for a product-subscription that does not exist moves past that gate and is refused as an owned resource would be: UnauthorizedException with the body message "Unauthorized. Please check the request and access policy and try again." - entirely fixed text, with no ARN, id or name interpolated.
Emulator: ResourceNotFoundException - a different error class (and, per the recorded wire behavior for this service's Unauthorized refusals, a different status: 404/400 rather than 401).
Why: the two failures are supposed to be distinguishable - "you did not identify a user" versus "that subscription is not yours". Reporting ResourceNotFoundException discloses that the ARN resolves to nothing and sends a client down a create/retry branch instead of an access branch; a client branching on the error class takes the wrong path for every unknown-ProductUserArn call.
Fix: the StopProductSubscription handler's ProductUserArn resolution arm - fail closed with the service's UnauthorizedException and its fixed message when the ARN names no product-subscription the caller owns, instead of mapping the lookup miss to ResourceNotFoundException.
Traces: check license-manager-user-subscriptions.stop-product-subscription-ambiguous-identifiers-rejected (its ValidationException assertion for the no-identifier call passes).
Note: open issues 20261029T234938Z-license-manager-user-subscriptions-unauthorized-refusals-answer-http.md (StopProductSubscription for an UNREGISTERED identity provider answering 400 instead of 401) and 20261029T165944Z-license-manager-user-subscriptions-stopproductsubscription-error-response.md (second Stop during the teardown window) are about other StopProductSubscription paths and neither covers the unknown-ProductUserArn class divergence; the 401 status mapping named there is a prerequisite for this cause's response.
