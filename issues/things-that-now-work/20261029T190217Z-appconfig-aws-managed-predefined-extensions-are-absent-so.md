# AppConfig AWS-managed predefined extensions are absent, so ListExtensions is empty and StartDeployment reports no AppliedExtensions

> _Note: this issue was identified against the code base at commit `473105e5105ba5cee28620541f40434a5fe4ef94`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListExtensions

## Description
The emulator does not have AppConfig's AWS-authored predefined extensions in its state, so both the catalog that should list them and the deployment field that should report the auto-associated one come back empty. 2 causes are bundled; they are the same missing seed data observed through two operations.

Cause 1 of 2: ListExtensions returns none of the AWS-managed extensions - fixture appconfig-catalog-list-extensions, step task#1.
AWS: Smithy ListExtensions (GET /extensions, success 200, output shape Extensions {Items: ExtensionSummaries, NextToken}, errors BadRequestException 400 / InternalServerException 500). Recorded behavior: in an account/region with no customer-authored extensions, AWS still returns the predefined AWS extensions as Items, each an ExtensionSummary carrying Id, Name, VersionNumber, Description and an Arn of the form arn:aws:appconfig:<region>::extension/<Id>/<VersionNumber> (note the empty account-id field - these are service-owned, not account-owned). The recorded set includes at least AWS.AppConfig.FeatureFlags ("AppConfig Feature Flags Helper"), AWS.AppConfig.JiraIntegration ("AppConfig integration with Atlassian Jira"), AWS.Evidently.ProjectImporter ("Amazon CloudWatch Evidently Project importer") and AWS.AppConfig.DeploymentNotificationsToEventBridge, all at VersionNumber 1.
Emulator: answers 200 but Items does not contain any of those entries - every expected predefined extension is reported missing.
Why: a client that discovers extensions by listing them (the documented way to find the Id/Arn to pass to CreateExtensionAssociation) finds nothing, so no extension can be associated by discovery. Code that asserts a predefined extension exists before using it takes a not-found path that cannot happen on AWS.
Fix: seed the appconfig service state with the AWS-managed predefined extensions (id, name, version, description and service-owned ARN) and have the ListExtensions handler return them alongside any customer-authored ones, honouring the operation's @paginated contract and its name= filter.

Cause 2 of 2: StartDeployment omits the auto-applied FeatureFlags extension - fixture appconfig-experiment-run-full-lifecycle, step setup#6 (cluster also covers appconfig-experiment-run-lifecycle#task#6, appconfig-experiment-run-multiple-runs#setup#6 and appconfig-experiment-run-treatment-overrides#setup#6).
AWS: the Deployment output shape carries AppliedExtensions (list of AppliedExtension). Recorded behavior: deploying a configuration profile of type AWS.AppConfig.FeatureFlags returns 201 with one AppliedExtensions entry for the extension AppConfig auto-associates with such profiles - ExtensionId "AWS.AppConfig.FeatureFlags", ProvidedIdentifier "AWS.AppConfig.FeatureFlags", VersionNumber 1, Parameters {} (empty map, present), plus an ExtensionAssociationId generated by the service (per-run value, not a requirement).
Emulator: returns 201 with the AppliedExtensions entry absent, so the deployment reports that no extension applied.
Why: the FeatureFlags extension is what validates and transforms feature-flag data on the way to the client, so a client inspecting AppliedExtensions to confirm that flag validation/transformation was in force concludes it was not. The association is also the only wire evidence that a feature-flag profile is being treated as one.
Fix: the StartDeployment handler and the extension-association state - when the deployed configuration profile's type is AWS.AppConfig.FeatureFlags, materialise the implicit association and report it in the Deployment's AppliedExtensions (on StartDeployment and on the deployment read paths).

Related open issues (neither covers these steps): "AppConfig's predefined 'deployment events to Amazon SQS' extension delivers no lifecycle notifications..." concerns a predefined extension's runtime effect, not the presence of the extensions in the catalog or in AppliedExtensions; "AppConfig Lambda-backed extension action points still never fire" concerns action-point invocation.

## Resolution

Both causes are implemented in `services/service-com-amazonaws-appconfig-amazonappconfig`:
the published AWS-authored catalogue now holds every entry named above (each with its own
published id, prose name, version 1 and service-owned ARN) and `ListExtensions` reports it
beside the account's own extensions; and a configuration profile whose `Type` names the
feature-flag helper is associated with that extension when it is created, so
`StartDeployment`, `GetDeployment` and `StopDeployment` report the association in
`AppliedExtensions` (with the `ProvidedIdentifier` the association was created with).

Residue, left deliberately: the recorded `ListExtensions` item check still differs on
per-entry PROSE the recording withholds and this report clips — the feature-flag helper's
`Description` beyond "… against a JSON schema" and the EventBridge entry's `Name` and
`Description`, which this report does not state at all. Every id, name, version and ARN
quoted above is reported exactly (pinned by `tests/all/aws_authored_extensions.rs`), and
the catalogue's own documentation marks which of its columns are inferred rather than
published, so a later reading of one of those entries can correct them.
