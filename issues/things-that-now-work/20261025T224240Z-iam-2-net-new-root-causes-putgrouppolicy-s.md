=== Cause 1 of 2: PutGroupPolicy now reaches its 5,120 group inline-policy quota but words the refusal with "characters" where AWS says "bytes", and it counts the quota over raw characters including the whitespace AWS excludes. ===

AWS: Smithy (com.amazonaws.iam#PutGroupPolicy) binds GroupName (groupNameType, @length 1..128, pattern ^[\w+=,.@-]+$), PolicyName (policyNameType, @length 1..128) and PolicyDocument (policyDocumentType, @length 1..131072), and models LimitExceededException -> awsQueryError code `LimitExceeded`, httpResponseCode 409; MalformedPolicyDocumentException (`MalformedPolicyDocument`, 400); NoSuchEntityException (`NoSuchEntity`, 404); ServiceFailureException (`ServiceFailure`, 500). The 5,120 figure is NOT a model constraint — the model allows 131,072 — it is IAM's documented, non-adjustable quota "Group policy size: 5,120 characters", aggregated over a group's inline policies and applied by the service, and IAM does not count whitespace toward it. The refusal message template, with its parts named: FIXED text `Maximum policy size of 5120 bytes exceeded for group `, then the VARIABLE group name taken verbatim from the request's GroupName. The 5120 literal is the API constant for the group principal type (a role uses 10,240, a managed policy 6,144) and is part of the template, not a recorded value. Recorded behavior for the accepting side: a document whose SIGNIFICANT (non-whitespace) length is exactly 5,120, padded with ~4 KB of whitespace so its raw length is far above 5,120, is ACCEPTED with HTTP 200 and GetGroupPolicy reads the document back intact; replacing it with a 5,121-significant-character document is refused `LimitExceeded` again and the stored policy survives unchanged.

Emulator: the status and error code are now right — a 5,121-significant-character document is refused HTTP 409 `LimitExceeded` — but the message diverges in its FIXED text: it reads `Maximum policy size of 5120 characters exceeded for group <group>` where AWS reads `Maximum policy size of 5120 bytes exceeded for group <group>`. The single fixed word `bytes` is rendered `characters`; the variable group name is correct. The same handler also computes the quota over raw characters, whitespace included (`already_embedded + input.policy_document.chars().count()` compared against `crate::state::MAX_GROUP_INLINE_POLICY_CHARACTERS`), so the whitespace-padded at-limit document AWS accepts is refused `LimitExceeded` as well — that is the very next assertion in this same check, which the message assertion currently fails ahead of.

Why: a client that matches IAM's refusal text (log scrapers, CDK/Terraform error classifiers, retry-vs-shrink decision logic) sees an error message real IAM never emits, so it cannot recognise a policy-size rejection. Worse, with whitespace counted, a document that fits IAM's quota is rejected here: a developer shrinks and reformats a policy that would have deployed fine against AWS, and conversely cannot verify that a pretty-printed generated policy fits.

Fix: the operation's handler — services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/put_group_policy.rs — must emit AWS's fixed sentence `Maximum policy size of {limit} bytes exceeded for group {GroupName}` on LimitExceededException, and must aggregate the group's inline-policy size with whitespace EXCLUDED before comparing it to the 5,120 constant in src/state.rs, leaving stored state untouched on refusal. The related open issue 20261025T113013Z-iam-4-net-new-behavioral-root-causes-putaccountproperties.md describes this same operation in its Cause 2, but as a 501 scaffold stub: its recorded replay key for this check is the `code == "LimitExceeded"` assertion, which now PASSES, which is why the replay report no longer marks this check OWNED. That issue says nothing about the "bytes" wording or the whitespace-excluded count, so closing it as written would leave this check failing.

=== Cause 2 of 2: UpdateSAMLProvider is an unimplemented 501 scaffold, so a deleted SAML provider is not refused NoSuchEntity as a mutation target — "gone" is only observable through GET. ===

AWS: Smithy (com.amazonaws.iam#UpdateSAMLProvider) takes required SAMLProviderArn (arnType, @length 20..2048) plus optional SAMLMetadataDocument (SAMLMetadataDocumentType, @length 1000..10000000), AssertionEncryptionMode, AddPrivateKey, RemovePrivateKey, returns SAMLProviderArn, and models ConcurrentModificationException (`ConcurrentModification`, 409), InvalidInputException (`InvalidInput`, 400), LimitExceededException (`LimitExceeded`, 409), NoSuchEntityException -> awsQueryError code `NoSuchEntity`, httpResponseCode 404, and ServiceFailureException (`ServiceFailure`, 500). There is no modeled "not implemented" outcome. Recorded behavior: after DeleteSAMLProvider, the same ARN is unreachable for BOTH reads and writes — GetSAMLProvider answers `NoSuchEntity` with the message whose FIXED text is `Manifest not found for arn ` followed by the VARIABLE SAMLProviderArn from the request (the emulator already matches this leg exactly), and UpdateSAMLProvider on that ARN answers the SAME refusal: HTTP 404, code `NoSuchEntity`, message `Manifest not found for arn ` + the SAMLProviderArn from the request. Independently, the role whose trust policy names the deleted provider as its Federated principal keeps that document byte-for-byte: IAM runs no cascading integrity check on provider deletion.

Emulator: every UpdateSAMLProvider call — against a live provider or a deleted one — is refused HTTP 501 with error code `NotImplemented` and the message `operation UpdateSAMLProvider is scaffolded but not implemented in this emulator`, because services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/update_saml_provider.rs is still a SCAFFOLDED stub. The check captured the error and compared codes, so the replay report recorded a `mismatch` (`expected update_saml_provider on a deleted provider to raise NoSuchEntity, got 'NotImplemented'`) and did not attribute it to the blocked-operation cluster.

Why: no SAML federation provider can be rotated or re-keyed at all (metadata refresh, AssertionEncryptionMode flip, private-key add/remove are the normal lifecycle of a federated IdP), and the deleted-target contract is unobservable: a client that distinguishes "the provider is gone" (NoSuchEntity, 404, terminal — stop retrying, recreate) from a server fault treats the 501 as transient and retries forever, or reports an infrastructure outage where AWS reports a missing entity. Because the surrounding legs of this flow already behave correctly, this single stub is the only thing hiding the whole update path.

Fix: the operation's handler — services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/update_saml_provider.rs — must resolve SAMLProviderArn against the SAML-provider store in src/state.rs and, when it names no stored provider (including one deleted earlier in the session), return NoSuchEntityException (`NoSuchEntity`, 404) with the fixed sentence `Manifest not found for arn {SAMLProviderArn}`; otherwise replace the stored metadata document / assertion-encryption mode / private keys and return the provider ARN. Its SCAFFOLDED marker must then be deleted. The open issue 20261025T113013Z-iam-updatesamlprovider-stub.md names the same operation but is a bare implement-the-stub work item: the replay report attributes exactly one check to it (iam.saml-provider-lifecycle), it does not carry THIS check's replay key, and it says nothing about the deleted-provider NoSuchEntity refusal or its `Manifest not found for arn <arn>` wording — so a fixer closing it would never re-replay this check and would report it as still failing.
