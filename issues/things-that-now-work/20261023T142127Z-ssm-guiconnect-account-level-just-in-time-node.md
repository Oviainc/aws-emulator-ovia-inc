# ssm-guiconnect: account-level just-in-time node access gate missing on Update, Delete 404s on an unconfigured account, and not-found / constraint messages diverge (4 causes)

> _Note: this issue was identified against the code base at commit `17c220c4f82dc0c00315f2111baf55aa4ec61156`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateConnectionRecordingPreferences

## Description
Four distinct root causes in the SSM GuiConnect emulator, all grounded in the behavioral suite (15/15 ssm-guiconnect checks fail). Each cause is numbered and carries its own failing check ids; all four must be closed before this issue is submitted.

Model used throughout: services/service-com-amazonaws-ssmguiconnect-ssmguiconnect/smithy-model/com-amazonaws-ssmguiconnect-ssmguiconnect.json (sdkId "SSM GuiConnect", restJson1, 3 operations: Get/Update/DeleteConnectionRecordingPreferences; every operation models AccessDeniedException=403, ValidationException=400, ResourceNotFoundException=404, ConflictException=409).

=== Cause 1 of 4: UpdateConnectionRecordingPreferences is not gated by the account-level just-in-time node access feature ===
AWS: UpdateConnectionRecordingPreferences is refused for any account that has not been enrolled in just-in-time node access (SSM Quick Setup). Every Update — however well-formed — comes back as AccessDeniedException (Smithy: AccessDeniedException, httpError 403, "You do not have sufficient access to perform this action"), with the gate's own message, recorded as "Just-in-time node access is not enabled. You must set up just-in-time node access to record RDP connections." The gate runs ahead of any resource lookup (a well-formed but nonexistent S3 bucket is still denied by the gate, never with a bucket-existence error) and ahead of the lenient KMSKeyArn shape check (Smithy: ConnectionRecordingPreferences.KMSKeyArn is @length(1,2048) String, so a non-ARN string passes shape validation and is denied by the gate). The denial is stable: replaying the same ClientToken yields the same AccessDeniedException, concurrent Updates are ALL denied (never a partial success, never a ConflictException leaking through), and no Update leaves any state behind — a following Get still reports the singleton as absent. The message here is a requirement only to the extent that the rejection class is: status 403 / code AccessDeniedException is the requirement, and the quoted JIT text is the recorded message example that distinguishes the feature gate from an IAM denial.
Emulator: the Update handler has no gate at all. It validates, writes the singleton and answers HTTP 200 with ClientToken + ConnectionRecordingPreferences echoed back (replay output: "expected the JIT gate to deny the call, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200 ...}, 'ClientToken': 'bad-...', 'ConnectionRecordingPreferences': {...}}"), so concurrent racers all succeed, the retried token succeeds, and the positive controls that are supposed to prove the gate exists all succeed.
Why: a client that relies on AWS refusing recording configuration until the account is enrolled sees the emulator accept it. Enrollment-gating logic, setup wizards and error-handling paths for AccessDeniedException are never exercised; worse, the emulator reports RDP-connection recording as configured on an account where AWS would record nothing, and ordering-sensitive clients (shape error vs gate error) get the opposite ordering.
Fix: UpdateConnectionRecordingPreferences handler — add the account-level just-in-time-node-access precondition, evaluated AFTER the request-shape validation that AWS performs first (BucketName/BucketOwner patterns) and BEFORE resource existence and the lenient KMSKeyArn check, returning the modeled AccessDeniedException (403); the account-level enrollment flag belongs in the service state alongside the preferences singleton (see Traces for file citations).

Handler: services/service-com-amazonaws-ssmguiconnect-ssmguiconnect/src/ops/update_connection_recording_preferences.rs lines 137-213 (no precondition between the store lookup and put_preferences).

=== Cause 2 of 4: DeleteConnectionRecordingPreferences refuses an unconfigured account with ResourceNotFoundException instead of succeeding idempotently ===
AWS: Delete is NOT gated by just-in-time node access and is idempotent on an account/Region with nothing configured: it answers HTTP 200 with the caller-supplied ClientToken echoed back verbatim (Smithy: DeleteConnectionRecordingPreferences is @idempotent, input/output both carry ClientToken @length(1,64) @idempotencyToken, success status 200), repeated calls behave identically, and a following Get still reports the resource absent. No ResourceNotFoundException, ConflictException or AccessDeniedException on that path.
Emulator: Delete on an unconfigured account returns 404 ResourceNotFoundException ("no connection recording preferences are configured for this account and Region"). Replay: "Delete is not gated by just-in-time node access and must succeed on an unconfigured account, got error: ResourceNotFoundException", and the ClientToken-echo check never gets a response to read (botocore raises ResourceNotFoundException from DeleteConnectionRecordingPreferences).
Why: cleanup and teardown code that unconditionally calls Delete (the idiomatic way to force the unconfigured state) fails against the emulator with a 404 it would never see on AWS; retry-safe delete loops break, and the idempotency-token echo contract is unobservable.
Fix: DeleteConnectionRecordingPreferences handler — treat "nothing configured" as success (200, echo the effective ClientToken) rather than mapping the absent singleton to ResourceNotFoundException; the not-found branch in the handler/state remove path should go away.
Traces: ssm-guiconnect.delete-not-configured-is-idempotent, ssm-guiconnect.delete-echoes-client-token-in-response. Handler: services/service-com-amazonaws-ssmguiconnect-ssmguiconnect/src/ops/delete_connection_recording_preferences.rs lines 181-193.

=== Cause 3 of 4: ResourceNotFoundException message for the absent preferences singleton does not follow the service's template ===
AWS: when no recording preferences exist, Get (and any path reporting the singleton missing) returns 404 / ResourceNotFoundException (Smithy: ResourceNotFoundException, httpError 404, required `message`) whose message is built from the missing resource's name — recorded as "The following  resource cannot be found: 'ConnectionRecordingPreferences'" (the doubled space is in the real text, the resource name is the variable part). Rule: a fixed template naming the resource type, not free prose. Status and code are the requirement; the template is the requirement for the message because it is derived from the request's target resource.
Emulator: the same 404/ResourceNotFoundException, but with its own prose "no connection recording preferences are configured for this account and Region". Four checks fail on exactly this comparison, including the bracketing Gets that other checks use as their healthy-read baseline.
Why: clients and test suites that key off the AWS message template (or surface it to operators) see a message AWS never emits; the emulator's text also carries no resource name, so a client that parses which resource was missing gets nothing.
Fix: the ResourceNotFoundException construction for this service — emit the service's resource-not-found template naming 'ConnectionRecordingPreferences' from one shared place (crate state / error helpers) so Get, Delete and any future reader agree.

=== Cause 4 of 4: ValidationException messages use the generic boundary-validator text instead of this service's constraint-message rule ===
AWS: constraint violations on this API are 400 / ValidationException (Smithy: ValidationException, httpError 400) with a message built from the violated member and its bound, in SSM GuiConnect's own form — for a 65-char ClientToken (Smithy: ClientToken @length(min 1, max 64)) recorded as "The length for ClientToken cannot be greater than 64."; for an empty S3Buckets list (Smithy: S3Buckets is a list with @length(min 1, max 1)) recorded as "ConnectionRecordingPreferences.RecordingDestinations.S3Buckets must contain at least 1 value." (and the upper bound as "... cannot contain more than 1 value."). Rule: one sentence naming the member path and the violated bound, no "N validation error(s) detected" prefix and no quoted offending value.
Emulator: the status and code are right (400 ValidationException) but the message is the generic aggregated boundary text — "1 validation error detected: Value 'xxxxxxxx…' at 'clientToken' failed to satisfy constraint: Member must have length less than or equal to 64" and "1 validation error detected: Value '0 items' at 'connectionRecordingPreferences.recordingDestinations.s3Buckets' failed to satisfy constraint: Member must have length greater than or equal to 1". It also echoes the offending value, which this service does not.
Why: a client that matches on the service's constraint message (or shows it to a user) gets a differently-shaped string, and the echoed offending value leaks request content the real service withholds.
Fix: this service's validation/error-message layer — override the framework boundary-validator message format for ssmguiconnect so length and list-cardinality violations render the per-member sentence above (the S3Buckets cardinality bounds and the ClientToken length bound should share that formatter with crate::state::refuse_preferences).
