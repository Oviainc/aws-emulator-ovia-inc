# GuardDuty custom detection rule association identity diverges across create, read and list (4 causes)

> _Note: this issue was identified against the code base at commit `4865c47dc859ac2a859fc100d3e8b00c14cee382`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCustomDetectionRuleAssociation

## Description
This issue bundles 4 distinct net-new causes, all in the guardduty crate and all on the IDENTITY (`associationId`, and the `arn` derived from it) of a custom detection rule association as it is reported by create, read and list. Fix all 4 before submitting, and re-replay every fixture#step listed in Traces. None of the four replay clusters is marked owned by an open issue. Two neighbouring guardduty association issues exist and do NOT cover this: 20261101T205734Z-guardduty-deletecustomdetectionruleassociation-is-not-idempotent-deleting-an-already-deleted.md (delete idempotency) and 20261030T120002Z-guardduty-iam-authorization-is-not-enforced-on-createcustomdetectionruleassociation.md (authorization and not-found wording). The shared fault is that the emulator treats the association id as a value it is free to mint afresh on every create, rather than as the stable handle the rest of the scenario resolves the association by.

Cause 1 of 4: CreateCustomDetectionRuleAssociation answers with a freshly minted `associationId` where the recording carries the association identity the scenario has already bound, and the association `arn` inherits the same wrong id. Fixture guardduty-association-duplicate-conflict, step task#3.
AWS: Smithy CreateCustomDetectionRuleAssociation (POST /custom-detection-rule/association; RuleId required, length 1..100, pattern ^[a-z0-9]+(-[a-z0-9]+)*$; Mode required (LIVE|DRY_RUN); ClientToken @idempotencyToken, length 0..64) returns AssociationDetail with `associationId` (AssociationId, required, length 1..64, pattern ^[a-zA-Z0-9_-]{1,64}$, "The unique identifier for the association") and `arn` (DetectionRuleArn, required). Recorded behavior only for the id's VALUE: the recording does not pin a literal id, it pins the id to the scenario's bound association identity (rendered by the replay as the unresolved template `{{assoc_conflict_id}}`) and requires `arn` to end in exactly that same id, i.e. one association of one (account, region, ruleId) has ONE id for the whole scenario and every response that names it must repeat it.
Emulator: HTTP 200 matches, but `$.ruleAssociation.associationId` is a new id ('23b6cad3a46d519c9a457ff532190002' in this run) instead of the bound identity, and `$.ruleAssociation.arn` is 'arn:aws:guardduty:<region>:<account>:detection-rule/custom/<ruleId>/association/<that new id>'. Neither the id nor the host/region/account parts of the ARN are requirements; the requirement is that the id equals the association's established identity and that the ARN's trailing id segment equals the `associationId` in the same payload. Hypothesis: the handler unconditionally calls `state.mint_id()` (services/service-com-amazonaws-guardduty-guarddutyapiservice/src/state.rs, `mint_id`, a 32-hex id whose low 16 bits are the store's own sequence counter — which is also why every id in this run ends in a 4-hex counter such as '0002') on every create path that is not the exact ClientToken replay, so a repeat create for an association that already exists re-mints rather than resolving.
Why: a client that creates an association, then re-issues the create (retry, duplicate-conflict probe, or a replay whose ClientToken it did not keep) is handed an id that names nothing it can subsequently resolve: GetCustomDetectionRuleAssociation is keyed by (RuleId, AssociationId) and the store keeps one association per (region, ruleId), so the caller's recorded handle and the handle the service just reported disagree and one of them 404s. ARN-based IAM policies and tag/resource bookkeeping written against the first ARN stop matching.
Fix: the create handler's id-resolution path and the AssociationDetail projection it builds, in the guardduty crate — services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/create_custom_detection_rule_association.rs (the `state.mint_id()` call and the `DetectionRuleAssociationRecord`/view construction below it, plus the shared `crate::state` helper that renders the association ARN so the ARN's trailing segment is always the record's `association_id`).
Traces: guardduty-association-duplicate-conflict#task#3 (also guardduty-association-list-filters-across-two-rules#task#3, guardduty-association-list-filters-across-two-rules#task#4, guardduty-custom-detection-rule-association-errors#task#3).

Cause 2 of 4: the same create divergence on the association-lifecycle path, where only `associationId` is asserted. Fixture guardduty-association-lifecycle, step task#3.
AWS: same model citation as cause 1 (CreateCustomDetectionRuleAssociation -> AssociationDetail.associationId, required, pattern ^[a-zA-Z0-9_-]{1,64}$). Recorded behavior only: the response's id must be the association identity the scenario binds (rendered as `{{assoc_lifecycle_id}}`), which later steps of the same fixture use as the path label for Get/Update/Delete and as the ARN suffix for List.
Emulator: `$.ruleAssociation.associationId` is a newly minted id ('c9f90e0fcfa7142af2f1d6fe0d1a0002' in this run) rather than the bound identity. Status 200 matches.
Why: the whole create -> get -> update -> list -> delete lifecycle is keyed by the id the create returned, so a create that mints an identity other than the association's makes every later step in the lifecycle address a different resource than the one the caller believes it created.
Fix: same component as cause 1 — services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/create_custom_detection_rule_association.rs. This cause is listed separately because it is a separate replay cluster with its own fixture and step and must be re-replayed on its own.
Traces: guardduty-association-lifecycle#task#3 (also guardduty-custom-detection-rule-association-lifecycle#task#3).

Cause 3 of 4: GetCustomDetectionRuleAssociation's read-back reports an `associationId` that does not satisfy the association identity the scenario resolved the resource by. Fixture guardduty-association-duplicate-conflict, step task#5.
AWS: Smithy GetCustomDetectionRuleAssociation (GET /custom-detection-rule/rule/{RuleId}/association/{AssociationId}; RuleId and AssociationId both httpLabel and required; AssociationId length 1..64, pattern ^[a-zA-Z0-9_-]{1,64}$; readonly) returns AssociationDetail with required `associationId`. Recorded behavior only: a read reached through an association's id echoes that SAME id back in `associationId` — the read is identity-preserving, so the value in the response body and the value in the request path are the same string.
Emulator: the replay reports `$.ruleAssociation.associationId: value_mismatch` on this step (HTTP 200 matches, and the cluster covers four further steps). Note for the fixer: the replay renders this cluster's expected and actual id as the same characters ('23b6cad3a46d519c9a457ff532190002'), so the divergence is in a dimension the rendering collapses (JSON type, case, or surrounding whitespace in the serialized member) rather than in the visible id digits — compare the serialized `associationId` member byte-for-byte against the id used in the request path when re-replaying, do not assume it is the digits alone.
Why: a client that stores the id returned by create and reads the association back cannot round-trip its own handle: the value it sent as the path label and the value it gets back in the body are not interchangeable, so caches, ARN construction and subsequent Update/Delete calls keyed on the body's value address nothing.
Fix: the AssociationDetail projection of the read handler in the guardduty crate — services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/get_custom_detection_rule_association.rs and the shared `crate::state` association-view/serializer it calls (the same view cause 1 builds), so one projection serves create, get and list.
Traces: guardduty-association-duplicate-conflict#task#5 (also guardduty-association-lifecycle#task#4, guardduty-association-lifecycle#task#6, guardduty-custom-detection-rule-association-lifecycle#task#4, guardduty-custom-detection-rule-association-lifecycle#task#6).

Cause 4 of 4: ListCustomDetectionRuleAssociations emits a summary whose `associationId` does not agree with the id embedded in that same entry's `arn`. Fixture guardduty-association-lifecycle, step task#7.
AWS: Smithy ListCustomDetectionRuleAssociations (GET /custom-detection-rule/association; MaxResults range 1..100, NextToken, RuleId, Mode as query params; readonly; paginated on NextToken/RuleAssociations) returns a required `ruleAssociations` list of AssociationSummary, each with required `associationId` (pattern ^[a-zA-Z0-9_-]{1,64}$) and required `arn` (DetectionRuleArn, pattern ^arn:[a-zA-Z0-9\-]+:[a-zA-Z0-9\-]+:[a-zA-Z0-9\-]*:([0-9]*|aws):.+$). Recorded behavior only: the two members of one summary are consistent — the ARN's trailing `.../association/<id>` segment is exactly that entry's `associationId`, which is what lets a caller select a listed association by ARN and then act on it by id.
Emulator: the replay selects the entry by its own ARN (`$.ruleAssociations[arn="arn:aws:guardduty:<region>:<account>:detection-rule/custom/<ruleId>/association/<id>"].associationId`) and reports `value_mismatch` on that entry's `associationId`, on a 200 response. As in cause 3 the rendered expected and actual read as the same characters ('c9f90e0fcfa7142af2f1d6fe0d1a0002'), so the fixer must compare the serialized summary member against the ARN's trailing segment exactly rather than by eye.
Why: list-then-act is the normal discovery path. If the id a listed entry advertises is not the id its own ARN names, a client that lists associations and then calls Get/Update/Delete with the listed id operates on a handle the service does not recognize, and ARN-keyed policy or inventory joins silently fail to match.
Fix: the AssociationSummary projection of the list handler in the guardduty crate — services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/list_custom_detection_rule_associations.rs, derived from the same shared association view as causes 1 and 3 so the id and the ARN cannot drift apart.
Traces: guardduty-association-lifecycle#task#7 (also guardduty-association-list-filters-across-two-rules#task#5, guardduty-association-list-filters-across-two-rules#task#6, guardduty-custom-detection-rule-association-lifecycle#task#7).
