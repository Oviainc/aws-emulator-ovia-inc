# SAR deploy path: RequiredCapabilities is always empty (never derived per version) and CreateCloudFormationChangeSet answers NotImplemented instead of SAR's accept/refuse semantics

> _Note: this issue was identified against the code base at commit `00577afa9aa0eead33f7dafc8adac2dd3659e1fc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCloudFormationChangeSet

## Description
Both causes are grounded in the cross-service deploy checks (group deploy-sar-changeset / deploy-serverlessrepo-changeset), whose service token is the composite `cloudformation__serverlessapplicationrepository__sqs`; the defective component in both is the serverlessapplicationrepository crate. This bundle carries 2 causes; BOTH must be closed before submitting.

Cause 1 of 2 — RequiredCapabilities is hardcoded empty instead of derived from the version's template.
AWS: Smithy: CreateApplicationVersion output member RequiredCapabilities targets __listOfCapability (enum Capability = CAPABILITY_IAM | CAPABILITY_NAMED_IAM | CAPABILITY_AUTO_EXPAND | CAPABILITY_RESOURCE_POLICY), and the member's own documentation states the rule: "The following resources require you to specify CAPABILITY_IAM or CAPABILITY_NAMED_IAM: AWS::IAM::Group, AWS::IAM::InstanceProfile, AWS::IAM::Policy, and AWS::IAM::Role" — and CAPABILITY_NAMED_IAM when such a resource carries a custom (pinned) name. The same required list appears on the Version shape GetApplication serializes. Recorded behavior: a version whose template declares an AWS::IAM::Role with no RoleName reports RequiredCapabilities ['CAPABILITY_IAM']; the same template with `RoleName:` pinned reports ['CAPABILITY_NAMED_IAM']; a template with only an AWS::SQS::Queue reports []. The derivation is per version from that version's own template, not per application, and an already-published version's list is never rewritten by a later publish.
Emulator: every version reports RequiredCapabilities [] — src/ops/create_application_version.rs builds AppVersion with `required_capabilities: Vec::new()`, so no template content is ever inspected (and the template reader itself does not read YAML; see the companion serverlessapplicationrepository issue on parse_template).
Why: capabilities are the acknowledgement gate of the SAR deploy flow. A client reading RequiredCapabilities to decide what to acknowledge sees nothing to acknowledge, so it will call CreateCloudFormationChangeSet with Capabilities=[] — which real SAR refuses with 400 — and a deploy wrapper that shows the user what permissions an application wants shows none even for a template that creates named IAM roles.
Fix: the version-publish handler/state of serverlessapplicationrepository (src/ops/create_application_version.rs and src/ops/create_application.rs, deriving through crate::state::parse_template) must derive RequiredCapabilities per version by scanning the template's Resources for IAM-affecting types, raising the requirement to CAPABILITY_NAMED_IAM when such a resource pins a name, and persist it with the version so GetApplication/ListApplicationVersions serve the stored derivation.

Cause 2 of 2 — CreateCloudFormationChangeSet answers NotImplemented, so neither its refusals nor its accept path exist.
AWS: Smithy: CreateCloudFormationChangeSet POST /applications/{ApplicationId}/changesets, success 201, output ApplicationId/ChangeSetId/SemanticVersion/StackId; modeled errors BadRequestException (400), ForbiddenException (403), TooManyRequestsException (429), InternalServerErrorException (500); the service also models NotFoundException (httpError 404, errorCode member documented as 404). Recorded behavior: (a) a SemanticVersion the application never published is refused with HTTP 404 and error code NotFoundException (example message "Application <app-arn> does not have a version 9.9.9"), and NO stack is left behind — not even the empty REVIEW_IN_PROGRESS shell a successful change set creates, so DescribeStacks on `serverlessrepo-<StackName>` answers CloudFormation's ValidationError for a missing stack; (b) a request that does not acknowledge the version's derived capabilities is refused with HTTP 400 / BadRequestException (example message "Required capabilities [CAPABILITY_IAM] were not provided."), capabilities being compared as a hierarchy — CAPABILITY_NAMED_IAM satisfies a CAPABILITY_IAM requirement, the reverse is refused — and again leaves no stack; (c) an accepted request returns 201 and creates the CloudFormation stack `serverlessrepo-<StackName>` in REVIEW_IN_PROGRESS with an executable change set (DescribeChangeSet Status CREATE_COMPLETE, ExecutionStatus AVAILABLE).
Emulator: the operation is an unimplemented scaffold stub: the call fails with error code 'NotImplemented' (HTTP 501), so no version check, no capability check and no stack creation happen at all. The bare "implement this operation" work item is ALREADY FILED for services/service-com-amazonaws-serverlessapplicationrepository-serverlessapplicationrepository/src/ops/create_cloud_formation_change_set.rs; this cause records the behavioral contract that filing does not state (404/NotFoundException for an unpublished version, 400/BadRequestException with hierarchical capability comparison, and that a refusal must create no stack).
Why: SAR's entire deploy path is unreachable, and a client cannot distinguish "this version does not exist" or "acknowledge these capabilities" from a server fault; a 501 is also not retry-classified like the 4xx AWS returns.
Fix: implement CreateCloudFormationChangeSet in its handler (src/ops/create_cloud_formation_change_set.rs) over the stored application/version state, including the version lookup (404 NotFoundException), the capability acknowledgement check against the version's derived RequiredCapabilities (400 BadRequestException, hierarchical), and the CloudFormation side effect — creating `serverlessrepo-<StackName>` in REVIEW_IN_PROGRESS with an AVAILABLE change set only on the accepted path.

Traces: cloudformation__serverlessapplicationrepository__sqs.rejects-changeset-missing-required-capability (Cause 1, and Cause 2's capability refusals, which it never reaches), cloudformation__serverlessapplicationrepository__sqs.deploy-sar-changeset-for-unpublished-version-rejected (Cause 2).

## Evidence
Cause 1 — check cloudformation__serverlessapplicationrepository__sqs.rejects-changeset-missing-required-capability: after CreateApplication 1.0.0 with a SAM template whose AWS::IAM::Role has a generated name, `create_application_version(SemanticVersion='1.1.0', TemplateBody=<same template with RoleName pinned>)` returned RequiredCapabilities []. AssertionError: "a template pinning RoleName required capabilities [], expected ['CAPABILITY_NAMED_IAM'] — naming the role is what raises the bar". The check's next assertions (version 1.0.0 must report ['CAPABILITY_IAM']; 1.1.0 refused with 400 "Required capabilities [CAPABILITY_NAMED_IAM] were not provided."; CAPABILITY_NAMED_IAM accepted where CAPABILITY_IAM is required) were never reached.

Cause 2 — check cloudformation__serverlessapplicationrepository__sqs.deploy-sar-changeset-for-unpublished-version-rejected: `create_cloud_formation_change_set(ApplicationId=<app with only 1.0.0 published>, StackName=..., SemanticVersion='9.9.9', ParameterOverrides=[...])` raised a ClientError with Error.Code 'NotImplemented'. AssertionError: "rejection code is 'NotImplemented', expected NotFoundException"; the check then expects HTTPStatusCode 404 and no `serverlessrepo-<StackName>` stack, and a positive control differing only in the version string ('1.0.0') expects 201 plus a REVIEW_IN_PROGRESS stack with a CREATE_COMPLETE/AVAILABLE change set.

Code: src/ops/create_application_version.rs builds AppVersion with `required_capabilities: Vec::new()` (line ~262) and never inspects the template for IAM resources; src/ops/create_cloud_formation_change_set.rs is the unimplemented scaffold stub answering NotImplemented (501).
