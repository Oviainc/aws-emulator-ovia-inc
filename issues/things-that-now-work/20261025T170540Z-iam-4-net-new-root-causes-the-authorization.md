# iam: 4 net-new root causes — the authorization gate is wired into only a handful of operations (ListAccessKeys/TagUser serve any principal), authorize() carries no condition context, the AccessDenied message drops AWS's authorization-details pointer, and SimulatePrincipalPolicy reports MissingContextValues for keys a negated operator decides

## Operation
ListAccessKeys

## Description
FOUR net-new root causes (Cause 1 of 4 .. Cause 4 of 4) in the bootstrapped `iam` service, each grounded in failing behavioral checks the replay report marks neither ALREADY FILED nor OWNED. A fixer must close all four before submitting; closing any one of them leaves the others' checks still failing.

=== Cause 1 of 4: the IAM request-authorization gate is called by only a handful of operations, so most IAM operations serve any principal that can sign ===

AWS: IAM's own API is governed by IAM. For EVERY iam: action, the calling principal's identity-based policies are evaluated before the operation reports or changes anything: an explicit Deny about the request wins, an Allow with no Deny permits, and a principal with neither is refused with the implicit deny — HTTP 403, error code `AccessDenied` (awsQuery protocol). A statement is about the request only when its action element (Action, or the set complement of NotAction) matches the requested action, its resource element matches the requested resource ARN, and its Condition holds. Consequences the failing checks grade, all of them AWS's documented evaluation rather than one recording: (a) an `Allow` + `NotAction: [iam:ListAccessKeys]` with `Resource: <own user arn>` grants the COMPLEMENT of the listed actions and only within that Resource, so iam:GetUser and iam:ListUserTags on the own ARN are permitted while iam:ListAccessKeys on the own ARN and iam:GetUser on a sibling user are refused `AccessDenied`; (b) an action that only an attached PERMISSIONS BOUNDARY allows is still refused `AccessDenied`, because a boundary is a ceiling and never a grant — Smithy com.amazonaws.iam#PermissionsBoundaryDecisionDetail$AllowedByPermissionsBoundary: "A value of true means that the permissions boundary does not deny the action... In this case, if an identity-based policy also allows the action, the request is allowed"; (c) a tag-conditioned Allow refuses the combination that does not match the condition. The modeled error sets do not contain the authorization refusal (Smithy com.amazonaws.iam#TagUser errors: ConcurrentModification 409 / InvalidInput 400 / LimitExceeded 409 / NoSuchEntity 404 / ServiceFailure 500; com.amazonaws.iam#ListAccessKeys errors: NoSuchEntity 404 / ServiceFailure 500), so `AccessDenied` 403 is the service-common refusal every operation answers and is recorded behavior rather than modeled.

Emulator: the gate exists but is wired into almost nothing. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs declares action constants for exactly six actions (iam:ListGroups, iam:ListRoles, iam:ListUsers, iam:ListPolicies, iam:CreateGroup, iam:ListUserTags), and the handlers for the operations these checks exercise never call `authorize`/`authorize_named` at all: src/ops/list_access_keys.rs::handle goes straight from the store lookup to building the page, and src/ops/tag_user.rs::handle begins `let _ = ctx;` ("tagging a user depends on nothing in it") and writes the merged tags with no authorization step. So ListAccessKeys and TagUser are served HTTP 200 for a principal whose identity policy excludes them by action, by resource, by NotAction complement, or by Condition — and for a principal whose only permission comes from a permissions boundary. Replay confirms it on every leg: ListAccessKeys returned `{'AccessKeyMetadata': [...], 'IsTruncated': False, 'HTTPStatusCode': 200}` where AWS answers `AccessDenied` 403, and TagUser returned 200 for the tag value the policy's Condition excludes. Note that the boundary itself is NOT unioned into the principal's permissions — src/state.rs::principal_sourced_policies collects only inline and attached managed policies — so the boundary leg fails for this cause and not because the boundary is read as a grant.

Why: every negative IAM test passes vacuously against this emulator, and in the most dangerous direction. A client validating least privilege, a break-glass drill, an ABAC design review or a NotAction complement cannot observe a single refusal on the operations that are not gated; a policy that is strictly more permissive than intended is indistinguishable from the intended one. Worse, the six gated actions make the gap look like it works: the same check sees iam:ListUserTags correctly refused and iam:ListAccessKeys wrongly served in one run.

Fix: the per-operation handlers in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/ must call crate::state::authorization::authorize / authorize_named (one call per operation, with that operation's action name and the ARN of the entity the request addresses) before reading or writing the store — not just the six operations that do today. The decision itself belongs where it already is (src/state/authorization.rs and services/common/src/iam_authorization.rs, which already implements Action/NotAction and Resource/NotResource as set complement), so this cause is call-site wiring plus the action-name constants each operation needs.

=== Cause 2 of 4: the authorizer builds its request with an EMPTY condition context, so no tag-derived condition key can ever be decided ===

AWS: IAM itself populates the request context, and a Condition is evaluated against it — aws:ResourceTag/<key> from the tags stored on the TARGET entity, aws:RequestTag/<key> from the tag the request body writes, aws:TagKeys from the set of keys the request writes, aws:PrincipalTag/<key> from the signing principal's tags (and usable as a policy variable `${aws:PrincipalTag/<key>}` inside a Condition value). Several keys in one Condition block AND together. The absent-key rule is documented verbatim (IAM User Guide, condition operators): "If the key that you specify in a policy condition is not present in the request context, the values do not match and the condition is false. If the policy condition requires that the key is not matched, such as StringNotLike or ArnNotLike, and the right key is not present, the condition is true" — so for a key the request omits, `StringEquals` is FALSE (an Allow guarded by it does not grant), `StringEqualsIfExists` is TRUE, `Null: {key: true}` is TRUE, and the negated string operators are TRUE. Under the set qualifiers, `ForAllValues:StringEquals` over aws:TagKeys holds only when every key the request writes is inside the policy's set, and `ForAnyValue:` when at least one is.

Emulator: src/state/authorization.rs::authorize_named line 138 builds `let request = iam::Request::new(action, resource, &principals);` — the constructor whose context is `&[]` — and `Request::with_context` appears nowhere in the file, so no tag key is ever in the context. services/common/src/iam_authorization.rs then applies its documented fail-closed reading ("A clause this CANNOT decide — an operator it does not implement, or a key the request context does not carry — makes the statement UNDECIDED, and an undecided statement never grants... nothing here guesses a condition value"), and its STRING_OPERATORS list excludes `Null` entirely. So once Cause 1 is fixed these five checks will flip from "wrongly allowed" to "wrongly refused": the matching tag combination will never grant, and StringEquals / StringEqualsIfExists / Null over an omitted key will all behave identically instead of diverging. Today the symptom is the over-permissive one (`AssertionError: StringEquals with the 'omitted' probe ({'tier': 'gold'}) must be denied; it was allowed`, `AssertionError: env=prod violates aws:RequestTag; got 'OK'`, `ForAllValues: {env,owner} (owner outside the set) must be AccessDenied; got ('OK', None)`) because the gate is not reached at all.

Why: ABAC is unusable in both directions. Before Cause 1 is fixed every tag-conditioned Allow is silently inert in the permissive direction; after it is fixed, and if this cause is left standing, every tag-conditioned Allow becomes a permanent refusal and a client cannot tell "my condition does not match" from "this emulator does not model the key". A refused write must also leave the target's tags untouched, which cannot be shown while the matching and non-matching combinations produce the same answer.

Fix: src/state/authorization.rs must assemble the request's condition context and pass it through `iam::Request::with_context` — aws:ResourceTag/* read from the target entity in src/state.rs, aws:RequestTag/* and aws:TagKeys from the calling operation's tag input (so the Tag*/Untag* call sites must hand their tag list to the gate), aws:PrincipalTag/* from the resolved signing principal's stored tags, declaring the modeled keys through `Request::published` so the empty-set qualifier rule applies; and services/common/src/iam_authorization.rs must implement the documented absent-key asymmetry (positive string operator false, `…IfExists` true, negated operator true) and the `Null` operator, instead of leaving an absent-key clause undecided.

=== Cause 3 of 4: the AccessDenied message omits AWS's authorization-details pointer ===

AWS: an IAM authorization refusal carries a message of the form `User: <principal ARN> is not authorized to perform: <action> on resource: <resource as the request named it> because no identity-based policy allows the <action> action. Go to https://<console URL> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization id>` (and, for an explicit deny, the same head ending `with an explicit deny in an identity-based policy` followed by the identical pointer). The fixed text is everything outside the angle brackets, including the whole sentence `. Go to … for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: `; the variable parts are the principal ARN, the action, the resource naming taken from the request, the console URL and the server-minted authorization id. The REQUIREMENT is the presence and wording of that trailing sentence, not the value of the id — the id and the URL differ on every call and the check matches them as a pattern (`[A-Za-z0-9]+`), never literally. Recorded behavior only: the model declares no AccessDenied shape for IAM.

Emulator: src/state/authorization.rs lines 170-172 build the message as exactly `format!("User: {principal} is not authorized to perform: {action} on resource: {named_as} {reason}")` and stop there. Replay: the refusal for a correctly-denied call read `User: arn:aws:iam::000000000000:user/sim2real-behav-after-<id> is not authorized to perform: iam:ListUserTags on resource: user sim2real-behav-after-<id> because no identity-based policy allows the iam:ListUserTags action` — the head is right, the pointer sentence is absent. Everything else in that check passed: the DateGreaterThan condition over aws:CurrentTime was evaluated correctly (the past instant allowed iam:GetUser, the future instant refused iam:ListUserTags with `AccessDenied`), so the ONLY divergence is the missing tail.

Why: a client that parses or asserts on the denial — a troubleshooting tool, a test harness, or an operator following the console link — sees a message AWS never produces, and loses the one handle AWS gives for getting the full decision (the GetRequestAuthorizationDetails authorization id). It also makes every other denial assertion in this suite unreachable, since the head alone never matches a full-message oracle.

Fix: the refusal construction in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs (`AccessDenied::new(...)` in `authorize_named`) must append the pointer sentence, minting a per-request authorization id and embedding it in both the console URL and the trailing `authorization id: ` clause, for both the implicit-deny and the explicit-deny wordings.

Traces: iam.iam-eval-deep-iam-1-date-greater-than-past-instant-allows. The same tail is asserted by iam.permissions-boundary-alone-never-grants-a-real-signed-call once Cause 1 lets it reach a refusal.

=== Cause 4 of 4: SimulatePrincipalPolicy reports MissingContextValues for a key whose clause a negated operator DECIDES ===

AWS: Smithy com.amazonaws.iam#EvaluationResult$MissingContextValues is "a list of context keys that are required by the included input policies but that were not provided by one of the input parameters" — the keys the simulation could not decide. A key absent under a NEGATED operator is decided, not undecidable: by the documented asymmetry quoted in Cause 2, `StringNotEquals: {"aws:SourceVpce": "<vpce id>"}` with no aws:SourceVpce in the context is TRUE, so a Deny guarded by it APPLIES and the result is `explicitDeny` with `MissingContextValues` EMPTY. Supplying the key with the matching value makes the condition false and the decision flips to `allowed`; swapping only the operator to the positive `StringEquals` with the key still absent makes the condition false, so the Deny does not apply and the decision is `allowed`.

Emulator: `MissingContextValues` is computed syntactically, with no reference to the operator. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/simulate_principal_policy.rs lines 523-536 take `crate::state::context_keys_in_policies(deciding)` — every context key mentioned anywhere in the deciding documents — and keep each one the request supplied no value for, then report that one list on every EvaluationResult and ResourceSpecificResult. Replay: the decision was right (`explicitDeny`) but the result also carried `MissingContextValues: ['aws:SourceVpce']` — `AssertionError: an absent key under a negated operator is DECIDED (condition true), not undecidable, so the simulator must not report it missing; got ['aws:SourceVpce']`.

Why: MissingContextValues is how a client knows which keys it must supply for the simulation to mean anything. Reporting a key that was decided tells the client its "deny unless via my VPC endpoint" policy is unevaluated when it was in fact enforced, so the client supplies context it does not need — or, worse, discounts a correct explicitDeny as unreliable and ships the policy untested.

Fix: src/ops/simulate_principal_policy.rs must derive MissingContextValues from the EVALUATION rather than from a scan of the documents — a key belongs in the list only when the clause mentioning it could not be decided — which means services/common/src/iam_authorization.rs has to report, per decided statement, which keys it could not decide (today the evaluator only returns a Decision), and the handler must report that per (action, resource) pair rather than one document-wide list.

Distinct from the open SimulatePrincipalPolicy issues 20261025T102129Z-iam-10-net-new-behavioral-root-causes-simulateprincipalpolicy.md and 20261025T085808Z-iam-kms-simulateprincipalpolicy-ignores-the-simulated-principal-when-evaluating-resourcepolicy.md, which are about MatchedStatements attribution, the stored permissions boundary and ResourcePolicy principals; neither names MissingContextValues or the negated-operator rule.
