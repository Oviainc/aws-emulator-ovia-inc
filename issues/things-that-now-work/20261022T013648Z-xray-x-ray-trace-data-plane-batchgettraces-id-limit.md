# X-Ray trace data plane: BatchGetTraces id limit and unknown-id reporting wrong, no segment-derived flags/root-causes/inferred segments, PutTraceSegments error codes diverge, every FilterExpression refused, no time-range validation

> _Note: this issue was identified against the code base at commit `5b247f22dea7573e9fb6c4376c776b3a345a666f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTraceSummaries

## Description
Nine distinct root causes in the X-Ray trace data plane (PutTraceSegments / BatchGetTraces / GetTraceSummaries / PutTelemetryRecords) of services/service-com-amazonaws-xray-awsxray. All grounded in failing behavioral checks of the `xray` suite; no open issue covers any of them.

Cause 1 of 9: BatchGetTraces does not enforce the 5-trace-id-per-call limit.
AWS: BatchGetTraces retrieves at most 5 traces per request; a 6-id request is refused with InvalidRequestException at HTTP 400. Smithy: BatchGetTraces.TraceIds (TraceIdList) carries NO modeled length bound and the operation models InvalidRequestException (client, 400) / ThrottledException (429), so the bound is service-side — recorded behavior plus the AWS BatchGetTraces documentation. Emulator: caps at 500 (src/state.rs `MAX_TRACE_IDS_PER_CALL: usize = 500`, enforced in src/ops/batch_get_traces.rs:157-168), so 6 ids answer HTTP 200. Why: a client that batches more than 5 ids silently works against the emulator and then fails in production. Fix: the per-call id bound used by the BatchGetTraces handler's validation. Traces: xray.batch-get-traces-five-id-limit-boundary.

Cause 2 of 9: BatchGetTraces reports well-formed but unknown trace ids in UnprocessedTraceIds.
AWS: a syntactically valid trace id that is not stored is silently omitted from the response — neither in Traces nor in UnprocessedTraceIds (UnprocessedTraceIds is for ids the service failed to process, not for misses). Recorded behavior only. Emulator: src/ops/batch_get_traces.rs:203-213 pushes every store miss onto `unprocessed_trace_ids`, so an unknown id comes back as `UnprocessedTraceIds: ['1-6ad9672f-0fd4371d22e7c4019a2b81cb']`. Why: a client that treats UnprocessedTraceIds as a retryable/partial-failure signal retries forever on ids that simply do not exist. Fix: the BatchGetTraces handler's miss branch. Traces: xray.batch-get-traces-invalid-format-fails, xray.batch-get-traces-mixed-known-unknown.

Cause 3 of 9: the stored segment document does not round-trip and no `inferred` segment is synthesised for a `namespace: "remote"` subsegment.
AWS: BatchGetTraces returns Segments[].Document as the submitted document (subsegments, annotations and http block intact), Trace.Duration derived from the segment's own start/end times, and X-Ray synthesises an extra top-level segment carrying `"inferred": true` with a service-assigned id whose parent_id is the remote subsegment's id — the same document with `namespace` removed comes back with exactly one segment. Recorded behavior (check documents REAL-AWS VERIFIED us-west-2 2026-09-07). Emulator: the check never observes the second segment and the poll runs to the harness deadline ("Check timed out after 60.0s"). Why: a client building a service map or reading back its own instrumentation sees no downstream node at all. Fix: the PutTraceSegments ingest/state derivation plus the BatchGetTraces projection. Traces: xray.batch-get-traces-segment-document-round-trip.

Cause 4 of 9: TraceSummary HasFault / HasError / HasThrottle and RootCauses are not derived from the submitted segment document.
AWS: the three flags are derived independently from the segment document's `fault`/`error`/`throttle` fields — a document with `throttle: true, error: true` summarises as HasThrottle=true with HasError=false (X-Ray reclassifies rather than unions) — and a segment-level `cause` block yields a FaultRootCause whose Services[0].EntityPath[0].Exceptions[0].Name is the submitted exception type. Recorded behavior (REAL-AWS VERIFIED us-west-2 2026-09-11). Emulator: the summaries never acquire the flags/root causes and the check runs to the deadline ("Check timed out after 60.0s"). Why: every consumer of GetTraceSummaries filtering on fault/error/throttle or reading RootCauses sees nothing. Fix: the summary derivation in the X-Ray state/GetTraceSummaries projection. Traces: xray.fault-error-throttle-flags-and-root-causes-derived-from-segment-document.

Cause 5 of 9: PutTraceSegments accepts a segment whose `trace_id` is malformed.
AWS: a document whose trace_id is not a well-formed `1-<8 hex>-<24 hex>` id is refused per-document and reported in UnprocessedTraceSegments, identified by the document's own segment `Id`, while the valid members of the same batch are stored. Recorded behavior; Smithy: PutTraceSegments output UnprocessedTraceSegments (UnprocessedTraceSegmentList of Id/ErrorCode/Message). Emulator: returns `UnprocessedTraceSegments: []` — the malformed document is accepted. Why: the caller believes a trace was ingested under an id X-Ray would never index, and the batch's partial-failure contract silently disappears. Fix: trace_id syntax validation in the PutTraceSegments ingest path (src/state.rs segment parsing + src/ops/put_trace_segments.rs). Traces: xray.put-trace-segments-invalid-trace-id-reports-segment-id.

Cause 6 of 9: UnprocessedTraceSegment ErrorCode values are the emulator's own, and the Message does not restate the code.
AWS: a document missing the required `name` field is reported with ErrorCode `MissingName`, and the accompanying Message restates the error code. Recorded behavior only (the model documents ErrorCode merely as "The error that caused processing to fail" and publishes no value set — see src/state.rs:29-48, where the emulator acknowledges inventing them). Emulator: ErrorCode 'MissingRequiredField' with Message 'segment document is missing the required field `name`', and for unparseable JSON ErrorCode 'ParseError' with a Message that does not restate the code. An ErrorCode is an error code, so its value is a requirement. Why: a client switching on ErrorCode to decide whether to fix and resend a segment never matches AWS's codes. Fix: the error-code constants and message construction used by the PutTraceSegments ingest path. Traces: xray.put-trace-segments-partial-failure-preserves-valid-members, xray.put-trace-segments-malformed-partial-failure.

Cause 7 of 9: GetTraceSummaries refuses EVERY request that carries a FilterExpression.
AWS: FilterExpression selects a subset of traces in [StartTime, EndTime); a well-formed expression returns the matching summaries at HTTP 200, and only a malformed one is refused with InvalidRequestException (400). Smithy: GetTraceSummaries.FilterExpression is a modeled optional input member; errors are InvalidRequestException (400) and ThrottledException (429). Emulator: answers 400 InvalidRequestException with "FilterExpression is not evaluated by this emulator yet; omit it to select every trace in [StartTime, EndTime)" for every expression, well-formed or not. Why: filtering is the primary query surface of X-Ray — duration vs responsetime selection, root-cause entity filters, group-filter consequence and remote-namespace inference are all unreachable, and a malformed expression is "rejected" for the wrong reason so a client cannot distinguish its own bad expression from an unsupported one. Fix: implement filter-expression evaluation in the GetTraceSummaries handler (shared with the CreateGroup/UpdateGroup parser). Traces: xray.get-trace-summaries-filter-expression-excludes-non-matching, xray.get-trace-summaries-malformed-filter-expression-rejected, xray.duration-filter-keeps-an-async-tail-trace-that-responsetime-excludes, xray.e2e-trace-lifecycle-group-filter-consequence, xray.filter-expression-operand-type-mismatch-rejected-on-both-surfaces, xray.remote-namespace-marks-the-quartz-root-cause-remote-and-infers-its-service, xray.rootcause-entity-filter-comparing-name-to-a-number-rejected, xray.rootcause-entity-filter-separates-dependency-bound-from-pipeline-bound-frames.

Cause 8 of 9: GetTraceSummaries accepts a time range whose EndTime precedes StartTime.
AWS: an inverted [StartTime, EndTime) window is refused with InvalidRequestException at HTTP 400. Smithy: StartTime and EndTime are both @required timestamps; InvalidRequestException (400) is modeled. Emulator: answers HTTP 200 with `TraceSummaries: [], TracesProcessedCount: 0`. Why: a client with reversed arguments gets a successful empty page instead of being told its request is invalid, and silently reports "no traces". Fix: time-range validation in the GetTraceSummaries handler. Traces: xray.get-trace-summaries-end-before-start-fails.

Cause 9 of 9: a wrong-typed member in the request body is reported as ValidationException instead of SerializationException.
AWS: a JSON value that cannot be deserialized into the modeled type is refused at the deserialization layer with error code SerializationException (HTTP 400) and the fixed message "STRING_VALUE can not be converted to an Integer". Smithy: TelemetryRecord's SegmentsReceivedCount/SentCount/SpilloverCount/RejectedCount are integer members; PutTelemetryRecords models InvalidRequestException/ThrottledException, so SerializationException is the protocol-level envelope. Emulator: answers code ValidationException. Why: a client distinguishing a malformed payload (do not retry, fix the serializer) from a constraint violation takes the wrong branch, and SDK error-typed handlers never match. Fix: the request deserialization layer's error mapping (shared, not the PutTelemetryRecords handler body). Traces: xray.put-telemetry-records-malformed-payload-rejected.
