# CodeCommit pull-request approval surface: UpdatePullRequestApprovalState answers 501, squash-merge does not gate on approval rules, and GetFile's FileDoesNotExistException message diverges (3 causes)

## Operation
UpdatePullRequestApprovalState

## Description
Three net-new root causes in the codecommit crate, each grounded in a failing behavioral check the replay report left UNMARKED (not ALREADY FILED, not OWNED by an open issue). Related-but-not-covering open issues are named per cause. A fixer must close all three causes before submitting.

Cause 1 of 3: UpdatePullRequestApprovalState answers HTTP 501 `NotImplemented`, so the author-cannot-approve-their-own-pull-request restriction is never enforced and no approval can ever be recorded.
AWS: Smithy models UpdatePullRequestApprovalState with input pullRequestId (@required, PullRequestId), revisionId (@required, RevisionId) and approvalState (@required, enum ApprovalState one of APPROVE | REVOKE), an empty (Unit) output, and among its errors PullRequestCannotBeApprovedByAuthorException (errorKind client, httpError 400), RevisionNotCurrentException (400), PullRequestAlreadyClosedException (400) and InvalidApprovalStateException (400). The operation doc states 'Updates the state of a user's approval on a pull request. The user is derived from the signed-in account when the request is made.' The model's documentation for PullRequestCannotBeApprovedByAuthorException is the error message itself: 'The approval cannot be applied because the user approving the pull request matches the user who created the pull request. You cannot approve a pull request that you created.' That text is entirely FIXED — it interpolates nothing from the request or state. So when the caller is the pull request's own author, AWS answers HTTP 400 with code PullRequestCannotBeApprovedByAuthorException and exactly that message, records NO approval (GetPullRequestApprovalStates returns approvals == []), and leaves the rule unsatisfied (EvaluatePullRequestApprovalRules reports approved=false with the rule name in approvalRulesNotSatisfied). When a DIFFERENT principal (here an assumed IAM role) calls the identical operation on the same pullRequestId/revisionId, it succeeds (HTTP 200, empty body), one approval with approvalState 'APPROVE' appears, the rule moves into approvalRulesSatisfied, and the merge is then allowed.
Emulator: every call to the operation comes back with error code 'NotImplemented' (HTTP 501). services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/update_pull_request_approval_state.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker on line 4 and its handle() body ends in `Err(crate::scaffolded::Scaffolded::not_implemented("UpdatePullRequestApprovalState"))`. No per-operation stub issue exists for this operation: the filed codecommit stub issues name GetRepositoryTriggers, PutRepositoryTriggers, DescribeMergeConflicts, GetBlobDifferences, GetMergeConflicts, ListPullRequests, GetCommentReactions, MergeBranchesByThreeWay, UpdatePullRequestStatus, CreatePullRequestApprovalRule, EvaluatePullRequestApprovalRules, MergePullRequestBySquash, UpdatePullRequestTitle, MergePullRequestByThreeWay and PostCommentReply — not UpdatePullRequestApprovalState.
Why: a client cannot distinguish 'you may not approve your own pull request' from 'this API does not exist'. Because 501 is not a modeled error, botocore surfaces a code no CodeCommit client handles, so review tooling that catches PullRequestCannotBeApprovedByAuthorException to fall back to a second reviewer crashes instead; and since no approval can be recorded at all, every approval-gated merge workflow is unreachable.
Fix: implement the handler in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/update_pull_request_approval_state.rs — resolve the caller's principal from the signed request, refuse with PullRequestCannotBeApprovedByAuthorException when it equals the pull request's recorded author, and otherwise persist the approval into the pull-request approval state that GetPullRequestApprovalStates and EvaluatePullRequestApprovalRules read.
Traces: codecommit.author-cannot-approve-own-pull-request-rejected.

Cause 2 of 3: MergePullRequestBySquash does not refuse a merge whose approval rules are unsatisfied — it answers 501 `NotImplemented`, so the approval gate on merging is absent.
AWS: Smithy models MergePullRequestBySquash with input pullRequestId (@required) and repositoryName (@required, @length 1..100, @pattern ^[\w\.-]+$), output pullRequest (PullRequest), and among its errors PullRequestApprovalRulesNotSatisfiedException (errorKind client, httpError 400), PullRequestAlreadyClosedException (400) and TipOfSourceReferenceIsDifferentException (400). When an approval rule attached to the pull request still has unmet requirements, AWS refuses the merge with HTTP 400 / PullRequestApprovalRulesNotSatisfiedException and the message 'You cannot merge the pull request because the requirements for one or more approval rules have not been met. For details about the approval rules that still have requirements, use EvaluatePullRequestApprovalRules.' — fixed text that interpolates nothing from the request. The refusal has no effect: the pull request stays OPEN and the destination branch head stays where it was. Once the rule is satisfied by a non-author approval, the IDENTICAL call succeeds, returns pullRequest.pullRequestStatus 'CLOSED', advances the destination branch head, and the new head commit lists the pre-merge destination commit id among its parents.
Emulator: the call comes back with error code 'NotImplemented' (HTTP 501) instead of the modeled 400, so the refusal, its message, and the subsequent successful merge are all unverifiable.
Note: the open issue '20261025T013318Z-codecommit-mergepullrequestbysquash-stub.md' names this operation as an unimplemented scaffold stub, and the replay report's ALREADY FILED cluster for MergePullRequestBySquash covers only codecommit.e2e-merge-pull-request-approval-rules-not-satisfied-rejected. That issue asks only for the operation to exist; it does not record the approval-rule gating contract above, and it does not carry this check's replay key — so this cause is recorded here. Fixing that stub issue may close this cause; codecommit.e2e-pull-request-approval-and-merge-flow must be re-replayed to confirm, and it also depends on Cause 1 (the approval itself must become recordable).
Why: the approval rule is the only thing standing between an unreviewed branch and the default branch. An emulator that neither enforces the rule nor merges at all lets a release pipeline's 'merge only when approved' guard be exercised against a path that never refuses and never merges, so the guard is untested and a client that catches PullRequestApprovalRulesNotSatisfiedException to re-request review sees an unhandled code instead.
Fix: implement services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/merge_pull_request_by_squash.rs — evaluate the pull request's approval rules before merging, return PullRequestApprovalRulesNotSatisfiedException with the documented message (leaving pull-request status and the destination reference untouched) when any rule is unmet, and otherwise create the squash commit, advance the destination reference and set the pull request to CLOSED.
Traces: codecommit.e2e-pull-request-approval-and-merge-flow.

Cause 3 of 3: GetFile's FileDoesNotExistException message is the emulator's own prose instead of AWS's request-derived template 'Could not find path <filePath>'.
AWS: Smithy models FileDoesNotExistException on GetFile (errorKind client, httpError 400; shape doc 'The specified file does not exist. Verify that you have used the correct file name, full path, and extension.'). Recorded behavior: for a path absent from the resolved commit's tree, the message is the fixed text 'Could not find path ' followed by the filePath taken from the request, and it names NO commit id and no repository. The fixed part is 'Could not find path'; the only variable part is the request's filePath.
Emulator: the status 400 and the code FileDoesNotExistException are correct (the check's `assert code == "FileDoesNotExistException"` passes), but the message is 'the file <filePath> does not exist in the commit <commitId>' — a different template that additionally leaks the resolved commit id. Built at services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/get_file.rs:237-240.
Note: this is the same class of defect as the message-template causes on the open issue '20261022T213415Z-codecommit-putcommentreaction-is-a-501-stub-cmk-disablement.md' (GetCommit's CommitIdDoesNotExistException, RepositoryDoesNotExistException), but that issue's replay list is codecommit.put-comment-reaction-invalid-value-rejected, codecommit.reads-blocked-when-the-repository-kms-key-is-disabled, codecommit.get-commit-unknown-id-rejected, codecommit.update-repository-name-reflected and codecommit.update-repository-name-conflict — it does not cover GetFile or this check.
Why: callers that prove a write was rejected by confirming the path is absent, and differential clients comparing emulator output against AWS, flag every missing-file path; the emulator is also more informative than AWS (it discloses the commit id), so code written against AWS's message cannot parse it.
Fix: the FileDoesNotExistException message construction in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/get_file.rs (the `commit.files.get(&file_path).ok_or_else(..)` arm), ideally via a shared helper alongside the crate's other repository/commit rejection-message helpers in src/state.rs.
Traces: codecommit.concurrent-put-file-same-parent-single-winner (the concurrency assertions in that check — exactly one winner, seven ParentCommitIdOutdatedException losers, winner blobId/treeId/branch tip — all pass; it fails only on this message).
