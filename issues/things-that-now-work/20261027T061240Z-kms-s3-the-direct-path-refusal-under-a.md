# kms__s3: the direct-path refusal under a kms:ViaService key policy names the identity-based policy where AWS names the resource-based one

> _Note: this issue was identified against the code base at commit `b76363ba3639c1fb1d2b9b08f3e303f98ad8a036`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GenerateDataKey

## Description
Cause 1 of 1 — the AccessDeniedException that refuses a direct GenerateDataKey on a CMK whose key policy permits the cryptographic actions only with kms:ViaService carries the wrong policy-type clause.
AWS: when a key policy allows the cryptographic actions only under Condition {"StringEquals": {"kms:ViaService": "s3.<region>.amazonaws.com"}}, an SSE-KMS write and read through S3 satisfy the condition and round-trip, while the SAME caller calling kms:GenerateDataKey directly is refused AccessDeniedException with HTTP 400 and the message "User: <caller ARN> is not authorized to perform: kms:GenerateDataKey on resource: <key ARN> because no resource-based policy allows the kms:GenerateDataKey action". Fixed text: "User: ", " is not authorized to perform: ", " on resource: ", " because no resource-based policy allows the ", " action"; variable parts: the caller ARN from the request's signing identity, the action name kms:GenerateDataKey (twice), and the key ARN resolved from the request's KeyId against state. The clause names the RESOURCE-based policy because the key policy is the authority that failed to allow the request — the condition it attaches to its only cryptographic Allow was not satisfied. Smithy: the KMS model lists AccessDeniedException on no operation (GenerateDataKey models DependencyTimeoutException, DisabledException, DryRunOperationException, InvalidGrantTokenException, InvalidKeyUsageException, KeyUnavailableException, KMSInternalException, KMSInvalidStateException, NotFoundException), so the code, the 400 status and the sentence are recorded behavior only; kms:ViaService is a documented KMS condition key (AWS KMS developer guide, "kms:ViaService").
Emulator: everything about the refusal except the clause is right — HTTP 400 (asserted and PASSED), Error.Code AccessDeniedException (asserted and PASSED), the caller ARN, the action and the key ARN all match — but the sentence ends "because no identity-based policy allows the kms:GenerateDataKey action". Replay evidence: expected '... because no resource-based policy allows the kms:GenerateDataKey action', got '... because no identity-based policy allows the kms:GenerateDataKey action'. Hypothesis: the refusal is produced by the one service-wide no-allow message helper in the KMS authorization component, which hardcodes the identity-based clause for every terminal refusal; the denial itself may be arriving for an adjacent reason, because the conditioned Allow is also what a dropped Condition block would make non-matching (see the dropped-Condition causes filed in this sweep for services kms and iam__kms), so the fixer should confirm that the direct call is refused BECAUSE kms:ViaService was evaluated and not satisfied, and that removing the condition re-allows it.
Why: the clause is the only part of the refusal that tells a caller which document to repair, and for a service-confined key it is the most load-bearing part: "no identity-based policy allows it" sends an engineer to attach an IAM policy, which can never unblock a direct call that the key policy confines to a service path, while "no resource-based policy allows it" correctly points at the key policy's kms:ViaService condition. Harnesses and runbooks that assert AWS's sentence do not match, and an operator is told a different rule than the one in force.
Relation to what is already filed: open 20261024T140708Z-kms-s3-a-kms-viaservice-scoped-key-policy-is-not.md recorded this check answering NotImplemented, and open 20261026T090118Z-kms-s3-the-kms-viaservice-key-policy-condition.md recorded the condition being ignored so the direct GenerateDataKey SUCCEEDED. Both of those divergences are gone: the direct call is now refused with the right code and status, and the only remaining divergence is this message clause. Neither open issue carries this replay key or claims the message text, so it is filed here.
Fix: the KMS state module's authorization component — the refusal-message helper and its selection by the terminal no-allow path must name the resource-based policy for a KMS key's authorization failure rather than reusing the identity-based wording. One helper serves every KMS operation, so the same fix closes the kms-service occurrences of this sentence filed in this sweep.
