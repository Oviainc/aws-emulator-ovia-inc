# Secrets Manager enforces no authorization and never consults KMS, and RotateSecret never rotates (3 causes)

> _Note: this issue was identified against the code base at commit `ee21bdc0559bb252101e2375a2c132d26bd8f920`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
Three root causes. Cause count: 3.

=== Cause 1 of 3: secret value operations never consult the secret's CMK (key state or key policy) ===
AWS: CreateSecret/PutSecretValue/GetSecretValue are KMS-backed and model EncryptionFailure and DecryptionFailure (Smithy: CreateSecret errors include EncryptionFailure+DecryptionFailure; PutSecretValue the same; GetSecretValue models DecryptionFailure; all 400). A write needs kms:GenerateDataKey and an enabled key, a read needs kms:Decrypt on an enabled key. So: CreateSecret under a CMK in PendingDeletion is refused; PutSecretValue under a disabled CMK is refused with EncryptionFailure and mints no version; GetSecretValue after the key is disabled fails with DecryptionFailure; a key policy granting only kms:Decrypt lets the role read but refuses its write.
Emulator: every one of these calls succeeds with HTTP 200. The replay shows CreateSecret under a CMK pending deletion returning 200 with an ARN/VersionId, GetSecretValue still serving plaintext after DisableKey, and a write succeeding with no kms:GenerateDataKey permission ('got (\'ok\', ...)'). The disabled-key check never converges: its helper polls GetSecretValue until it fails and the secret keeps decrypting, so the check runs to the suite's 60 s cap.
Why: the CMK is the secret's access-control and availability boundary. A client that revokes a key, disables it or schedules it for deletion believes the material is now unreadable; this emulator keeps serving it, and key-state incident drills and envelope-encryption tests pass against an emulator that never encrypts at all.
Fix: the CreateSecret / PutSecretValue / GetSecretValue handlers' KMS dependency - resolve the secret's KmsKeyId, check key state and the caller's kms:GenerateDataKey / kms:Decrypt before the state mutation or the read, and map the refusal onto EncryptionFailure / DecryptionFailure.
Traces: secretsmanager.cmk-key-policy-granting-only-decrypt-lets-a-role-read-but-refuses-its-write, secretsmanager.create-secret-under-a-cmk-pending-deletion-rejected, secretsmanager.put-secret-value-under-a-disabled-cmk-rejected-and-the-current-version-kept, secretsmanager.server-side-kms-encryption-transparent-decryption.

=== Cause 2 of 3: identity-based policy and Secrets Manager condition keys are not evaluated ===
AWS: Secrets Manager authorizes every call against the caller's identity policy, including the service's condition keys. aws:RequestTag/<key> on secretsmanager:CreateSecret refuses a create that omits the required tag; aws:ResourceTag/<key> scopes GetSecretValue to secrets whose tag still matches (and starts refusing once the tag is changed); secretsmanager:VersionStage scopes a read to one staging label, so the same principal/action/resource with VersionStage=AWSPENDING is refused; and RotateSecret requires lambda:InvokeFunction on the rotation function, which is refused when the function's resource policy does not admit secretsmanager.amazonaws.com. The refusal is 400 AccessDeniedException (awsJson1_1 folds denials onto 400).
Emulator: all of these calls SUCCEED. The replay shows CreateSecret without the required tag returning 200, GetSecretValue returning the material for an untagged/non-matching secret ('got (\'ok\', \'untagged-value\')'), a VersionStage=AWSPENDING read returning 'OK' with payload 'pending-credential', and RotateSecret returning 200 where the invoke permission is missing. The account-scoped wildcard-principal check never converges and hits the 60 s cap (it also depends on PutResourcePolicy, which open issue 20261024T030130Z-lambda-rds-secretsmanager-secrets-manager-putresourcepolicy-is-an-unimplemented-scaffold-stub.md records as a stub; this cause is about the missing authorization decision itself, not that stub).
Why: these condition keys are how teams fence off production secrets. An emulator that ignores them green-lights a policy that does not actually restrict anything, and the test that was supposed to prove 'this role cannot read that secret' proves nothing.
Fix: the service's request-authorization layer - evaluate the caller's identity policy and the secretsmanager condition keys (aws:RequestTag, aws:ResourceTag, secretsmanager:VersionStage) before the handler runs, and answer AccessDeniedException (400) when no statement allows the action; plus the RotateSecret handler's lambda:InvokeFunction pre-check.
Traces: secretsmanager.request-tag-condition-refuses-a-create-secret-without-the-required-tag, secretsmanager.resource-tag-condition-grants-get-secret-value-only-while-the-tag-matches, secretsmanager.version-stage-condition-key-scopes-a-read-to-one-staging-label, secretsmanager.rotate-secret-lambda-invoke-permission-missing-denied, secretsmanager.rotate-secret-lambda-without-invoke-permission-denied, secretsmanager.wildcard-principal-scoped-by-principal-account-is-not-public-and-admits-a-same-account-role.

=== Cause 3 of 3: RotateSecret is accepted but no rotation ever happens ===
AWS: RotateSecret drives the configured rotation function through createSecret/setSecret/testSecret/finishSecret, stages the candidate under AWSPENDING and moves AWSCURRENT on finishSecret; DescribeSecret then reports LastRotatedDate, NextRotationDate inside the schedule window, and the version history keeps chronological order (Smithy: RotateSecret -> ARN/Name/VersionId; DescribeSecret exposes RotationEnabled, LastRotatedDate, NextRotationDate, VersionIdsToStages).
Emulator: RotateSecret answers 200 and nothing advances - no AWSPENDING version appears, AWSCURRENT never moves, no second rotation is refused while one is in flight, and NextRotationDate/rotation history are never produced. Every rotation-dependent check polls for that progress and runs to the suite's 60 s cap ('Check timed out after 60.0s'). Open issue 20261024T150703Z-lambda-logs-secretsmanager-a-secrets-manager-rotation-never.md records the same cause from the lambda__logs__secretsmanager side (its replay key covers only those two checks); the eight secretsmanager checks listed here are not carried by it.
Why: rotation is the product. A client sees an accepted RotateSecret and a secret that never changes, and concurrency/ordering guarantees around rotation (single execution at a time, chronological version history, schedule windows) are unobservable.
Fix: the RotateSecret handler's step driver (invoke the rotation function per step, stage AWSPENDING, promote AWSCURRENT on finishSecret, stamp LastRotatedDate/NextRotationDate, and refuse a concurrent rotation) and the Lambda invocation runtime it depends on (open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md).
Traces: secretsmanager.concurrent-rotate-secret-single-execution-enforced, secretsmanager.e2e-create-use-rotate-delete-restore, secretsmanager.e2e-cross-service-lambda-rotation-consequence, secretsmanager.e2e-rotate-secret-lambda-invocation-flow, secretsmanager.rotation-history-preserves-chronological-version-order, secretsmanager.rotation-rules-sets-next-rotation-date-window, secretsmanager.rotation-schedule-expression-with-duration-places-next-rotation-in-the-window, secretsmanager.server-side-managed-rotation-lambda-invocation-enforced.
