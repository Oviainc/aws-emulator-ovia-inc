# UpdateWorkloadShare (and DeleteWorkloadShare, ListLensReviews, …) refuse a malformed WorkloadId with 400 at the boundary, although the handler says the lookup owns it and four sibling workload operations skip that validation so it does

_Filed: 2026-10-29T02:38:15Z_
_Operation: UpdateWorkloadShare | Class: error-response_

> _Note: this issue was identified against the code base at commit `2271003192907dc435917d10fce42c387f42c2e4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

This crate has ONE rule for a path-bound `WorkloadId`: it is RESOLVED, not validated — a value that names no workload is answered `404 ResourceNotFoundException` naming the id as sent, whatever the value's syntax. The rule is implemented by putting `skip_validation = ["WorkloadId"]` on the input shape so the boundary validator does not refuse the id's `@length(32,32)` / `@pattern(^[0-9a-f]{32}$)` with a 400 first, and it is applied to exactly eight of the twenty-seven inputs that carry a `WorkloadId` path label: GetWorkload, UpdateWorkload, DeleteWorkload, CreateMilestone, GetMilestone, ListMilestones, CreateWorkloadShare and ListWorkloadShares.

`UpdateWorkloadShareInput` is NOT one of them, yet the handler states that very rule for its own lookup ("an id no workload carries is that lookup's 404 whatever its syntax"). Because the shape keeps the constraint traits, the boundary refuses `PATCH /workloads/not-a-workload-id/shares/{ShareId}` with a 400 `ValidationException` before the handler runs, so the handler's lookup never sees the id and the promised 404 is unreachable for any id outside the pattern. The same request shape one operation earlier in the share lifecycle — `CreateWorkloadShare`, `POST /workloads/not-a-workload-id/shares` — answers 404, pinned by a test, so two operations on the same path prefix disagree about the same member.

The same omission affects every other handler of the workload plane that states or relies on the lookup owning the id: `DeleteWorkloadShare` ("that workload has to resolve first — through the same lookup `GetWorkload` and `UpdateWorkloadShare` resolve a `WorkloadId` through") and `ListLensReviews` ("an id no workload carries is the lookup's 404 whatever its syntax"), plus AssociateLenses, DisassociateLenses, AssociateProfiles, DisassociateProfiles, UpgradeLensReview, UpgradeProfileVersion, UpdateIntegration, UpdateLensReview, GetAnswer, ListAnswers, UpdateAnswer, GetLensReview, ListLensReviewImprovements, ListCheckDetails and ListCheckSummaries. It is reported here on UpdateWorkloadShare, the one whose own handler comment asserts the 404 it cannot give.

Note this is NOT the crate's ARN rule: for `ProfileArn` / `TemplateArn` the crate deliberately pins the boundary 400 and says so ("An ARN the modelled `ProfileArn` pattern refuses never reaches the lookup: it is a 400 from the boundary validator on both operations", tests/all/profile_shares.rs:816-817). The divergence here is within the `WorkloadId` rule alone.

## Evidence

Side 1 — the crate's rule and how it is implemented. `src/ops/types/get_workload_types.rs:14-19`: "`WorkloadId` is a path label this operation RESOLVES: the lookup in `ops::get_workload` owns a value that names no workload, and answers the modelled 404 `ResourceNotFoundException` for it (with `ResourceId` as sent), so the boundary validator must not refuse the id's `@length`/`@pattern` with a 400 first. `skip_validation` drops only that member's constraint traits" followed by `skip_validation = ["WorkloadId"]` (`:20-23`). The same note is carried onto the share operations: `src/ops/types/create_workload_share_types.rs:14-21` — "`WorkloadId` is a path label this operation RESOLVES; see the note in `get_workload_types.rs`" with `skip_validation = ["WorkloadId"]`; `src/ops/types/list_workload_shares_types.rs:14-21`, identical.

Side 2 — the same member, same rule asserted, constraint traits left on. `src/ops/update_workload_share.rs:181-184`: "// The share belongs to the workload it shares, so the workload is resolved first: // an id no workload carries is that lookup's 404 whatever its syntax." But `src/ops/types/update_workload_share_types.rs:14-20` declares the input with NO `skip_validation`: `#[smithy_macros::smithy(shape = "com.amazonaws.wellarchitected#UpdateWorkloadShareInput")]` / `pub struct UpdateWorkloadShareInput { pub share_id: String, pub workload_id: String, pub permission_type: String, }`. The model keeps the constraints on that label: `smithy_query(query="operation", operation="UpdateWorkloadShare")` → `"WorkloadId": {"target": "WorkloadId", "httpLabel": true, "required": true, "length": {"min": 32, "max": 32}, "pattern": "^[0-9a-f]{32}$"}`. That the boundary really enforces an `httpLabel` member's constraints is pinned elsewhere in this crate: `tests/all/profile_shares.rs:816-846` asserts HTTP 400 / `ValidationException` for a malformed `ProfileArn` path label on CreateProfileShare and ListProfileShares.

Same omission, same family: `src/ops/types/delete_workload_share_types.rs:14-20` (no `skip_validation`) against `src/ops/delete_workload_share.rs:209-213` — "so that workload has to resolve first — through the same lookup `GetWorkload` and `UpdateWorkloadShare` resolve a `WorkloadId` through"; and `src/ops/types/list_lens_reviews_types.rs:17` (no `skip_validation`) against `src/ops/list_lens_reviews.rs:180` — "so an id no workload carries is the lookup's 404 whatever its syntax".

Test coverage of the rule, which the two operations above are outside of: `tests/all/lookup_error_envelopes.rs:9-13` — "A path-bound resource identifier is RESOLVED, not validated: a value naming no stored resource is answered `404 ResourceNotFoundException` carrying the identifier as sent and the missing resource's type — whatever the value's syntax, so a `WorkloadId` outside `^[0-9a-f]{32}$` ... take the lookup's answer, not a 400", exercised over the rows `("not-hex-at-all", "not-a-workload-id")`, `("one-character-short", …)`, `("uppercase-hex", …)` on GetWorkload/UpdateWorkload/DeleteWorkload/CreateMilestone (`:95-149`); and `tests/all/workload_shares.rs:649-683` — "// A `WorkloadId` naming no workload is the lookup's 404 on both operations." with the row `("not-hex-at-all", "not-a-workload-id")` asserted 404 / `ResourceNotFoundException` / `ResourceId` as sent on CreateWorkloadShare and ListWorkloadShares. No test asserts a 400 for a malformed `WorkloadId` on UpdateWorkloadShare or DeleteWorkloadShare (`tests/all/workload_share_permissions.rs:35,344-348` uses only the well-formed `ABSENT_WORKLOAD_ID`).

## Steps to Reproduce

1. POST /workloads with a minimal create body to obtain a WorkloadId, then POST /workloads/{WorkloadId}/shares with {"SharedWith":"111122223333","PermissionType":"READONLY","ClientRequestToken":"tok-1"} to obtain a ShareId
2. Send PATCH /workloads/not-a-workload-id/shares/<ShareId> with body {"PermissionType":"READONLY"}
3. Observe HTTP 400 ValidationException raised by the boundary walk for the WorkloadId's @length/@pattern — the handler never runs, so the 404 its own comment promises (src/ops/update_workload_share.rs:181-184) cannot be produced
4. Send POST /workloads/not-a-workload-id/shares with {"SharedWith":"111122223333","PermissionType":"READONLY","ClientRequestToken":"tok-2"} and GET /workloads/not-a-workload-id/shares: both answer 404 ResourceNotFoundException with ResourceId "not-a-workload-id" (pinned by tests/all/workload_shares.rs:649-683), so the same malformed id gets two different answers on the same path prefix
5. Send DELETE /workloads/not-a-workload-id/shares/<ShareId>?ClientRequestToken=tok-3 and GET /workloads/not-a-workload-id/lensReviews for the same divergence on DeleteWorkloadShare and ListLensReviews
