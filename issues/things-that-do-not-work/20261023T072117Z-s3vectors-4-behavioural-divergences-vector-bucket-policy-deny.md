# s3vectors: 4 behavioural divergences — vector-bucket policy Deny is stored but never enforced, TagResource accepts reserved aws: keys, no ConflictException under concurrent tag mutations, QueryVectors ignores the post-delete tombstone candidate slot

> _Note: this issue was identified against the code base at commit `0b023ce22a329ff2896e758c2b0769a212a04448`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListVectors

## Description
Four independent root causes found in the s3vectors emulator by the behavioral suite replay. Each cause is numbered and carries its own failing check ids. All four must be closed before this issue is submitted.

Note on neighbouring issues (named here so a fixer does not mistake them for coverage): the open issue 20261023T014718Z-s3vectors-6-behavioural-divergences-no-iam-authorization-on.md covers IDENTITY-based authorization on ListVectors (an IAM principal without s3vectors:ListVectors is served) — Cause 1 below is the RESOURCE-policy path (PutVectorBucketPolicy Deny) and is a different evaluation input, so it is not covered there. The open issue 20261023T014718Z-s3vectors-tagresource-stub.md asks for TagResource to be implemented at all (it answered HTTP 501 NotImplemented at that commit); in this replay TagResource answers HTTP 200, so that stub is gone and Causes 2 and 3 are what the now-live handler gets wrong — they are not the stub.

=== Cause 1 of 4: a vector-bucket resource policy is accepted and stored but never evaluated — an explicit Deny does not refuse anything ===
AWS: Smithy (services/service-com-amazonaws-s3vectors-s3vectors/smithy-model/com-amazonaws-s3vectors-s3vectors.json) models AccessDeniedException (errorKind client, httpError 403) on BOTH ListVectors and GetVectors, and PutVectorBucketPolicy takes a required `policy` document that is the bucket's resource policy. A resource policy whose Deny statement names an s3vectors action on the bucket/index is enforced SERVER-SIDE on the next call to that action: the denied operation is refused with 403 AccessDeniedException, an operation NOT covered by the Deny (GetIndex in the recording) still succeeds, and replacing the policy with an allow-only document restores access. Recorded behavior only for the exact message text; the status (403) and the error code (AccessDeniedException) are the requirement.
Emulator: the policy is stored and then ignored. After PutVectorBucketPolicy with an explicit Deny on s3vectors:ListVectors, ListVectors answers HTTP 200 with {'vectors': []}; after a restrictive Deny covering reads, GetVectors(keys=['probe']) answers HTTP 200 with {'vectors': [{'key': 'probe'}]}. No refusal is ever produced, so the checks fail on an unexpected SUCCESS rather than on a code mismatch.
Why: a client that partitions a vector store with a bucket policy (deny-by-default buckets, read-only indexes, cross-account grants narrowed by Deny) sees every denied call succeed. A policy regression in the application under test — a Deny that was dropped, a resource ARN that no longer matches, a policy written to the wrong bucket — is invisible here and only surfaces as a 403 against real AWS. Negative-path tests asserting a 403 can never pass.
Fix: the authorization step that must run before the s3vectors data-plane handlers — resolve the bucket's stored resource policy, evaluate the request's action/resource/principal against it, and return AccessDeniedException (403) on an applicable Deny; the policy is currently only persisted by PutVectorBucketPolicy's handler/state and read back by GetVectorBucketPolicy.
Traces: s3vectors.vector-bucket-policy-enforced-denies-list-vectors-rejected (ListVectors leg), s3vectors.vector-bucket-policy-enforced-on-access-denied (GetVectors leg).

=== Cause 2 of 4: TagResource accepts a reserved `aws:`-prefixed tag key instead of refusing it ===
AWS: Smithy models ValidationException (errorKind client, httpError 400) on TagResource (input: required resourceArn httpLabel, required tags map). AWS reserves the `aws:` tag-key prefix for system tags: TagResource with a key such as `aws:Reserved` is refused with 400 ValidationException and the key is never stored. Recorded message example: "System tags cannot be added/updated by requester".
Emulator: the call succeeds — HTTP 200 with an empty body ({'ResponseMetadata': {'HTTPStatusCode': 200, ...}}) — so the reserved key is accepted.
Why: a client that generates tag keys from user input or from a tagging convention gets no feedback that it is writing into AWS's reserved namespace; the same payload is refused by real AWS. Any negative test for the reserved-prefix rule passes here and fails in production, and the emulator's tag store can hold keys that cannot exist in AWS.
Fix: TagResource's input validation in its handler (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/tag_resource.rs) — reject any tag key beginning with the reserved `aws:` prefix with ValidationException (400) before any state is written; the same rule belongs on CreateVectorBucket/CreateIndex `tags` and UntagResource `tagKeys` if they share the validator.
Traces: s3vectors.tag-resource-invalid-key-rejected.

=== Cause 3 of 4: concurrent tag mutations on one resource never produce ConflictException ===
AWS: Smithy models ConflictException (errorKind client, httpError 409) on TagResource and UntagResource, and both are @idempotent. Tag state on a single vector bucket is updated under optimistic concurrency control, so when TagResource/UntagResource calls against the SAME resource overlap, at least one of the racing callers is refused with 409 ConflictException rather than all of them being serialised silently. Recorded behavior only (the recording observes at least one ConflictException across the concurrent fan-out); the requirement is the 409/ConflictException outcome, not any particular message.
Emulator: no caller is ever refused. Firing concurrent TagResource/UntagResource calls at one vector-bucket ARN returns success for every call — "expected at least one ConflictException under concurrent tag mutations on the same resource (optimistic-locking not observed)".
Why: ConflictException is the signal a client must retry its read-modify-write of a tag set. A client with no retry/backoff on 409, or one that drops the conflict and reports success, is never exercised here, and lost-update bugs in concurrent taggers (two writers each overwriting the other's tag) are invisible in the emulator but real against AWS.
Fix: the tag state for s3vectors resources and the TagResource/UntagResource handlers — guard the tag map with a version/generation check and return ConflictException (409) when a concurrent mutation invalidated the read the write was based on.
Traces: s3vectors.tag-resource-conflict-under-concurrent-updates.

=== Cause 4 of 4: after DeleteVectors, QueryVectors with topK <= surviving population returns a full topK instead of being short by exactly one ===
AWS: recorded behavior only — the Smithy model says nothing about ANN candidate accounting (QueryVectors: required topK range min 1, required queryVector, @paginated on nextToken/vectors). The check records, and re-confirms over 4 minutes of continuous polling plus two independent green live replays, that once DeleteVectors has returned 200 for a vector that was inside the result set, the deleted vector keeps occupying one ANN-graph candidate slot: for every 1 <= topK <= surviving population, QueryVectors returns exactly topK-1 results, and they are a correctly ordered PREFIX of the surviving ranking (never a wrong or reordered entry). A query for population+1 or more candidates has slots to spare and returns the complete surviving ranking — that leg passes against the emulator, so only the short-by-one leg diverges.
Emulator: the deleted vector frees its slot immediately and the query backfills. For topK=1 just after the interloper was deleted the emulator returned ['vec-x2'] (1 result) where the recording requires [] (0 results); the same +1 offset repeats for each topK in 1..population.
Why: a client tuned against AWS sizes topK with headroom precisely because a recent delete costs it a candidate slot (re-ranking pipelines that ask for topK and then filter, recall assertions in retrieval tests). Against the emulator a topK with no headroom always looks sufficient, so an under-sized topK ships and silently returns one result fewer on real AWS right after any delete.
Fix: QueryVectors' handler/ranking over the index state — account for recently deleted (tombstoned) vectors as consumed candidates for the lifetime of the tombstone rather than removing them from the candidate pool at DeleteVectors time; the delete path in DeleteVectors' state update is the other half.
Traces: s3vectors.query-vectors-reranks-when-a-nearer-vector-is-inserted (its re-rank-on-insert and restore-on-oversized-topK legs pass; the topK<=population loop after the delete is the failing leg).
