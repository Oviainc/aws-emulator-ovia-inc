# cloudformation__ec2__neptune: 3 net-new causes — AWS::Neptune::DBSubnetGroup provisions nothing in Neptune and never validates, Neptune GetAtt outputs are emitted without OutputValue, and DescribeDBEngineVersions(DefaultOnly) refuses with InvalidParameterCombination

> _Note: this issue was identified against the code base at commit `e0227173af353a179b5497df80ad91b1569c5be2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Three independent root causes make the CloudFormation-driven Neptune cluster/subnet-group deploy surface unusable. All four failing checks under this heading die inside the emulator's own responses; none is a runner or environment problem.

Cause 1 of 3: the AWS::Neptune::DBSubnetGroup resource provisioner is effectively a no-op — it marks the resource CREATE_COMPLETE without creating anything in Neptune and without letting Neptune validate the declared properties.
AWS: CloudFormation's AWS::Neptune::DBSubnetGroup handler calls Neptune CreateDBSubnetGroup (Smithy, com-amazonaws-neptune-amazonrdsv19: CreateDBSubnetGroup takes required DBSubnetGroupName, DBSubnetGroupDescription and SubnetIds, plus Tags). On success the group is a real Neptune resource: DescribeDBSubnetGroups(DBSubnetGroupName=<name>) returns exactly one DBSubnetGroup whose DBSubnetGroupName equals the declared name, DBSubnetGroupDescription equals the declared description, VpcId equals the subnets' VPC, Subnets carries one SubnetIdentifier per declared subnet with its SubnetAvailabilityZone.Name, and DBSubnetGroupArn is tag-readable through ListTagsForResource — carrying the resource's own template Tags plus the aws:cloudformation:stack-name / aws:cloudformation:logical-id / aws:cloudformation:stack-id tags CloudFormation propagates. The resource's Ref is the group name. Conversely, when every declared subnet sits in ONE Availability Zone, Neptune REFUSES the create: CloudFormation does not refuse at template validation, it accepts the stack, the SubnetGroup resource goes CREATE_FAILED, the stack ends ROLLBACK_COMPLETE, the rollback removes the group and the stack's VPC and subnets, and the CREATE_FAILED StackEvent's ResourceStatusReason is the registry-handler envelope: Resource handler returned message: "<service message>" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest). For this class the service message's fixed text is "The DB subnet group doesn't meet Availability Zone (AZ) coverage requirement. Current AZ coverage: " + "<the zone(s) the declared subnets actually cover, comma-separated>" + ". Add subnets to cover at least 2 AZs. (Service: Neptune, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)"; the AZ list is a value taken from the request's subnets, and the request id and attempt count are per-run. After the rollback, DescribeDBSubnetGroups(<name>) must answer HTTP 404 error code DBSubnetGroupNotFoundFault with message "DB Subnet group '<name>' not found." — fixed text "DB Subnet group '" ... "' not found." around the requested name.
Emulator: the happy-path stack reaches CREATE_COMPLETE, but the very next call, neptune.DescribeDBSubnetGroups(DBSubnetGroupName=<the declared name>), answers the NotFound refusal — "An error occurred (DBSubnetGroupNotFoundFault) when calling the DescribeDBSubnetGroups operation: DB Subnet group '<name>' not found." — so the group CloudFormation claims to have created does not exist in Neptune's state at all. The single-AZ stack, which AWS rolls back, also reaches CREATE_COMPLETE: the check asserts the terminal status and gets 'CREATE_COMPLETE' where ROLLBACK_COMPLETE is required, so there is no CREATE_FAILED event, no handler reason and no rollback of the VPC/subnets either. Both symptoms are the one missing behaviour: the provisioner never reaches the Neptune control plane, so it can neither record the group nor surface Neptune's refusal.
Why: a client that deploys a Neptune subnet group through IaC gets a green stack and then cannot use the group — every subsequent Neptune call that references it (CreateDBCluster, DescribeDBSubnetGroups, tagging) fails as if the group were never declared. Worse, an invalid single-AZ group is reported as a successful deployment, so a pipeline that relies on CloudFormation to catch and roll back the AZ-coverage violation ships a broken topology and never sees the error AWS would have raised.
Why (cont.): the silent success is the dangerous half — a rollback that does not happen also leaves the stack's VPC and subnets behind, which AWS would have reaped.
Fix: the CloudFormation service's AWS::Neptune::DBSubnetGroup resource provisioner — its create/update/delete path must dispatch to the Neptune CreateDBSubnetGroup / DeleteDBSubnetGroup handlers and write Neptune state, propagate the resource Tags and the three aws:cloudformation:* tags, expose Ref as the group name, and translate a Neptune refusal into a CREATE_FAILED resource with the handler-error envelope and HandlerErrorCode InvalidRequest so the stack rolls back.
Traces: cloudformation__ec2__neptune.cfn-deploy-neptune-db-subnet-group-round-trip-and-delete (errors on the post-CREATE_COMPLETE DescribeDBSubnetGroups) and cloudformation__ec2__neptune.cfn-deploy-neptune-db-subnet-group-single-az-rejected-and-rolled-back (mismatch: CREATE_COMPLETE where ROLLBACK_COMPLETE is required).

Cause 2 of 3: DescribeStacks reports Outputs rows for a Neptune stack that have no OutputValue member at all.
AWS: DescribeStacks returns, for a CREATE_COMPLETE stack, one Output per template Outputs entry, each carrying OutputKey and the RESOLVED OutputValue as a string. For the Neptune cluster/instance template that means ClusterRef (Ref Cluster = the DBClusterIdentifier), ClusterEndpoint / ClusterReadEndpoint / ClusterPort / ClusterResourceId (GetAtt Cluster.Endpoint, .ReadEndpoint, .Port, .ClusterResourceId), InstanceRef (Ref Instance), InstanceEndpoint / InstancePort (GetAtt Instance.Endpoint, .Port) and the EC2 Refs — each one a resolved scalar string that must equal what Neptune's own DescribeDBClusters / DescribeDBInstances report for that cluster and instance (recorded behavior plus the Neptune model's DBCluster.Endpoint/ReaderEndpoint/Port/DbClusterResourceId and DBInstance.Endpoint.Address/Port members).
Emulator: the stack reaches CREATE_COMPLETE and DescribeStacks does return Outputs rows, but at least one row omits OutputValue entirely, so building {OutputKey: OutputValue} raises KeyError: 'OutputValue'. An unresolvable GetAtt is being emitted as a key-only Output instead of either a resolved value or a stack failure.
Why: a client reading stack outputs — the normal way to hand a Neptune endpoint, port or resource id to the next deployment step — gets a malformed Output object. Every SDK and IaC tool indexes OutputValue directly, so the consumer crashes on a stack CloudFormation reported as successfully created, and nothing in the stack status hints that an attribute failed to resolve.
Fix: the cloudformation service's output-resolution and DescribeStacks serializer, together with the Neptune resource provisioners' GetAtt attribute table — Cluster.Endpoint/.ReadEndpoint/.Port/.ClusterResourceId and Instance.Endpoint/.Port must resolve to the values Neptune reports for the created resources, and an attribute that cannot be resolved must fail the stack rather than produce an Output with no OutputValue.
Traces: cloudformation__ec2__neptune.deploy-neptune-cluster-and-instance-provisioned (KeyError: 'OutputValue' in stack_outputs after CREATE_COMPLETE).

Cause 3 of 3: Neptune DescribeDBEngineVersions with DefaultOnly=true refuses instead of returning the engine's default version.
AWS: Smithy, com-amazonaws-neptune-amazonrdsv19: DescribeDBEngineVersions(Engine, EngineVersion, DBParameterGroupFamily, Filters, MaxRecords, Marker, DefaultOnly, ListSupportedCharacterSets, ListSupportedTimezones) -> DBEngineVersionMessage{Marker, DBEngineVersions}. The operation models NO errors. For Engine="neptune", DefaultOnly=true AWS answers HTTP 200 with a one-element DBEngineVersions list: the engine version Neptune currently defaults to, whose EngineVersion is a dotted major.minor.patch.build string. A refusal is not a modeled outcome of this call for a valid engine name.
Emulator: the call is refused with error code InvalidParameterCombination and message "RDS can't find a default engine version." — RDS's wording, for a Neptune request, on an operation that models no errors. The message is wholly fixed text; it carries no value from the request, and it names RDS rather than Neptune.
Why: discovering the default engine version is the first step of every Neptune provisioning flow, including any template that must pin EngineVersion. The refusal makes that discovery impossible, so the caller cannot build a valid CreateDBCluster request or a valid AWS::Neptune::DBCluster template, and an InvalidParameterCombination on a request with a single valid parameter combination sends the caller looking for a client bug that does not exist. It also blocks the whole invalid-engine-version rejection path downstream.
Fix: the Neptune service's DescribeDBEngineVersions handler and the engine-version catalog it reads — the catalog must carry Neptune engine versions with one marked default so DefaultOnly=true returns it with HTTP 200 instead of raising. Note: open issues 20261030T024450Z-neptune-3-net-new-catalog-causes-engine-version.md, 20261103T175309Z-neptune-parameter-and-engine-version-catalogs-serve-rds.md and 20261108T233943Z-rds-describedbengineversions-serves-a-synthetic-engine-version-catalog-for.md report neighbouring engine-version catalog gaps and do not cover this DefaultOnly refusal.
Traces: cloudformation__ec2__neptune.deploy-neptune-cluster-invalid-engine-version-rejected (errors on the first describe_db_engine_versions(Engine='neptune', DefaultOnly=True)).
