# efs__lambda: the shared-EFS-mount check never completes — a lifecycle/invoke poll loop never converges and the check is killed at the 60s cap (1 cause)

> _Note: this issue was identified against the code base at commit `6d7833292dd9d4a45d8e52e2aa7ee7e5a822f7f5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Replay of the behavioral suite simparity-behavioral-aws-v1 against the emulator built from this checkout found one surviving, unowned root cause in the cross-service efs+lambda group (service token `efs__lambda`). THIS ISSUE HAS 1 CAUSE.

Cause 1 of 1 — the EFS-access-point-mounted Lambda flow (CreateFunction with VpcConfig + FileSystemConfigs, then RequestResponse Invoke, then a cold-start re-mount after an IAM change) never reaches a terminal answer: the check makes no assertion failure at all, it is killed by the harness at the 60s cap, which means one of its bounded poll loops is still spinning on a condition the emulator never satisfies (check efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied).

AWS: recorded behavior only for the data-plane part; the wire contract is modelled. Smithy (services/service-com-amazonaws-lambda-awsgirapiservice/smithy-model/com-amazonaws-lambda-awsgirapiservice.json): FileSystemConfig{Arn (required, @pattern for an EFS access-point ARN arn:aws*:elasticfilesystem:<region>:<account>:access-point/fsap-[a-f0-9]{17}), LocalMountPath (required, @pattern ^/mnt/[a-zA-Z0-9-_.]+$)}; error EFSMountFailureException, errorKind client, httpError 403, doc "The Lambda function couldn't mount the configured file system due to a permission or configuration issue." Smithy (services/service-com-amazonaws-efs-magnolioapiservice-v20150201/...): CreateMountTarget / DescribeMountTargets expose LifeCycleState, and the FileSystemDescription / AccessPointDescription LifeCycleState enums settle at `available`. What the recording shows, end to end: a file system and one mount target per subnet both settle at LifeCycleState=available; an access point settles at available; CreateFunction with VpcConfig and FileSystemConfigs is accepted and GetFunctionConfiguration leaves State=Pending for State=Active and echoes FileSystemConfigs verbatim; a RequestResponse Invoke returns StatusCode=200 with no FunctionError and a JSON payload in which os.path.ismount('/mnt/shared') is true, bytes written by function A are read back byte-identical by a DIFFERENT function B, both stamped with the access point's PosixUser uid/gid, while A's /tmp copy is NOT visible to B; after elasticfilesystem:ClientMount is removed from B's execution role, B's next cold Invoke is refused with error code EFSMountFailureException at HTTP 403 while A (ClientMount intact, also cold) still mounts and reads; restoring the grant heals B. Every one of those steps is reached through a bounded poll (file system available 180s, both mount targets available 420s, CreateFunction role-propagation retry 180s, State leaving Pending 600s, first successful Invoke 180s, refusal-after-cold-start 300s, heal 300s), so on AWS each poll converges and the check terminates.

Emulator: no response of any kind is produced for the condition being awaited — the replay reports exactly `Check timed out after 60.0s` with no AssertionError and no ClientError, i.e. the harness killed the check inside one of those poll loops. Because the poll predicates swallow the per-call outcome (ClientError is converted to a non-ok tuple and retried, LifeCycleState is compared for equality), a permanently-wrong answer from any step in the chain presents as an unterminating wait rather than a failed assertion. Hypothesis: the stall is in the first loop whose condition the emulator cannot satisfy — either an EFS/mount-target/access-point LifeCycleState that never reaches `available`, a Lambda function State that never leaves Pending, or the first `_poll` over Invoke, whose per-attempt refusal is retried until the budget is gone. Two open issues describe answers that would produce exactly that last stall and are named here so the work can be merged rather than done twice: 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md (Invoke answers NotImplemented instead of running the function and returning its payload — the poll waits for an ok tuple that can never arrive) and 20261023T114649Z-lambda-updatefunctionconfiguration-stub.md (the cold-start step the refusal/heal phases depend on). Neither names this check or this cross-service flow, and neither accounts for the possibility that the stall happens earlier, in an EFS or Lambda lifecycle transition.

Why: a client gets no answer at all rather than a wrong one. A caller that waits on DescribeMountTargets/GetFunctionConfiguration for a settled lifecycle state, or that retries Invoke until it succeeds, hangs until its own timeout instead of either succeeding or receiving a classifiable refusal — the worst failure mode for a client, because there is no error code to branch on. Functionally, the capability under test is also absent: an emulator that gives each function a private directory would pass CreateFunction and the FileSystemConfigs echo and then silently diverge on the shared bytes, and one that ignores IAM on the mount would let B in with no ClientMount (over-permissive) instead of refusing with EFSMountFailureException at 403.

Fix: three components, in the order the flow reaches them. (1) The EFS lifecycle state machine behind CreateFileSystem/CreateMountTarget/CreateAccessPoint and their Describe reads, so every created resource converges to LifeCycleState=available. (2) The Lambda CreateFunction/GetFunctionConfiguration handlers and function state, so a VpcConfig+FileSystemConfigs function leaves State=Pending for Active and echoes FileSystemConfigs. (3) The Invoke handler and the EFS mount it stands on: a function configured with a FileSystemConfig must see the access point's root directory at LocalMountPath as ONE shared store across functions (not a per-function private directory), stamped with the access point's PosixUser identity, and the mount must be authorized at environment-build time against that function's execution role, refusing with EFSMountFailureException (403) when elasticfilesystem:ClientMount is absent. Whichever loop is stalling should first be made to answer at all — an unimplemented step on this path must return its modeled error rather than a value that a retry loop treats as "not yet".

Traces: efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied.

## Evidence
Behavioral suite simparity-behavioral-aws-v1 replayed against the emulator built from this checkout: 14/27 passed (51.9%), bootstrap_signal=false — the emulator was serving (14 efs checks passed, and the ec2/efs/lambda calls in other checks were answered). Per-service: efs__lambda 0/1 (0%), 1 failed.

The failure, verbatim from the report:

  [mismatch] efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied
  Error: Check timed out after 60.0s

There is no AssertionError and no ClientError traceback: the check produced no assertion verdict, so it was still inside a poll loop when the 60s cap fired. The loops it can be inside, with their own budgets (all > 60s, so none of them had expired), are, in order:

  1. ec2.get_waiter('vpc_available').wait(VpcIds=[vpc_id])
  2. _poll(describe_file_systems(...)['FileSystems'][0]['LifeCycleState'], == 'available', timeout_s=180)
  3. _poll(describe_mount_targets(...) states, all == 'available', timeout_s=420)
  4. _poll(describe_access_points(...)[0]['LifeCycleState'], == 'available', timeout_s=120)
  5. lam.create_function(... VpcConfig, FileSystemConfigs ...) role-propagation retry, deadline 180s
  6. _poll(get_function_configuration(...), State in ('Active','Failed'), timeout_s=600)
  7. _poll(_invoke(fn_a, {'op':'write',...}), r[0] == 'ok', timeout_s=180)

Loop 7 is the first whose predicate a refusing emulator can never satisfy, because _invoke() converts a ClientError into an ('error', code, status, message) tuple that _poll treats as "not yet" and retries — which is the behavior the open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md would produce. That attribution is a hypothesis, not a measurement: the report's single line does not say which loop stalled.

Expected (AWS, from the recording the check encodes): A's Invoke returns StatusCode=200, no FunctionError, payload with ismount=true, uid=gid=1001 and sha256 of the 4096+ random bytes written; B's Invoke returns those exact bytes with tmp_has_it=false; after ClientMount is dropped from B's role, B's cold Invoke raises error code 'EFSMountFailureException' with HTTPStatusCode 403; A still reads the bytes in the same window; restoring the grant makes B read them again. Actual (emulator): the check never reaches any of those assertions.

Models consulted: services/service-com-amazonaws-lambda-awsgirapiservice/smithy-model/com-amazonaws-lambda-awsgirapiservice.json — FileSystemConfig{Arn required @pattern access-point/fsap-[a-f0-9]{17}, LocalMountPath required @pattern ^/mnt/[a-zA-Z0-9-_.]+$}, EFSMountFailureException (errorKind client, httpError 403); services/service-com-amazonaws-efs-magnolioapiservice-v20150201/smithy-model/com-amazonaws-efs-magnolioapiservice-v20150201.json — LifeCycleState on FileSystemDescription / MountTargetDescription / AccessPointDescription. Generated VPC/subnet/security-group ids, file-system, mount-target and access-point ids, function names, role names, the random payload and its sha256, hosts and timestamps are environment-specific examples and not requirements; the HTTP statuses, error codes, the FileSystemConfigs echo, the settled lifecycle states and the cross-function visibility of the mounted bytes are.
