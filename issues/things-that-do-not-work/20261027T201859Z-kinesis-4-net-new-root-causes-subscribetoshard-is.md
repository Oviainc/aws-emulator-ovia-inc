# kinesis: 4 net-new root causes — SubscribeToShard is not implemented at all (enhanced fan-out entirely unavailable), the DeleteStream consumers-present refusal is reworded, the ShardLevelMetrics enum ValidationException message is the wrong shape, and no AWS/Kinesis CloudWatch metrics are ever published

> _Note: this issue was identified against the code base at commit `4e290f8d6b034b90409323db1641d26f5c9d1b54`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SubscribeToShard

## Description
Four distinct root causes in the kinesis emulator, all grounded in failing behavioral checks of this suite. None is marked ALREADY FILED or OWNED in the replay report, and none is covered by an open issue (the open kinesis issues cover CloudFormation/DryRun/not-found messages, per-shard quotas, StartStreamEncryption, CreateStream's shard ceiling and the Channel/resource-policy/account-settings scaffold stubs; there is no open issue naming SubscribeToShard, the DeleteStream consumer refusal, the constraint-walk enum message, or AWS/Kinesis CloudWatch metrics).

=== Cause 1 of 4: SubscribeToShard answers 501 NotImplemented — the whole enhanced fan-out data plane is missing ===
AWS: Smithy: SubscribeToShard input { ConsumerARN (required, len 1..2048, pattern ^(arn):aws.*:kinesis:.*:\d{12}:.*stream\/[a-zA-Z0-9_.-]+\/consumer\/[a-zA-Z0-9_.-]+:[0-9]+$), ShardId (required), StartingPosition (required), DryRun (boolean) }; output { EventStream: SubscribeToShardEventStream, required, streaming }; modeled errors AccessDeniedException, DryRunOperationException, InvalidArgumentException, LimitExceededException, ResourceInUseException, ResourceNotFoundException (all HTTP 400). AWS answers HTTP 200 and frames SubscribeToShardEvent messages (Records, ContinuationSequenceNumber, MillisBehindLatest, ChildShards) as an application/vnd.amazon.eventstream body over HTTP/2; a subscription lives ~5 minutes, a second concurrent subscription on the same consumer+shard is refused with ResourceInUseException, DryRun=true is refused with DryRunOperationException and establishes nothing, a caller without kinesis:SubscribeToShard gets AccessDeniedException, and a ShardId that does not belong to the consumer's stream is refused rather than served.
Emulator: every SubscribeToShard call is refused with HTTP 501, error code 'NotImplemented' and message "operation SubscribeToShard is not implemented in this emulator". The hand-signed HTTP/2 probe recorded the raw response headers {':status': '501', 'content-type': 'application/x-amz-json-1.1', 'content-length': '102'} where AWS answers ':status' '200' with an event-stream content type. The negative legs therefore also see 'NotImplemented' where they expect 'DryRunOperationException' or 'AccessDeniedException'.
Why: a client using enhanced fan-out (the KCL's default consumer path, and every EFO consumer) cannot read a single record; neither the delivery contract, the per-consumer exclusivity, the 5-minute expiry, the DryRun refusal nor the IAM refusal can be exercised, and a 501 with a non-modeled error code is not retried or classified correctly by any SDK.
Fix: an operation handler for SubscribeToShard in the kinesis service crate's ops module (src/ops/mod.rs declares one file per operation and no subscribe_to_shard.rs exists), plus event-stream (application/vnd.amazon.eventstream) output framing in that service's serializer, reading shard records from the service state the GetRecords handler already uses.
Traces: kinesis.subscribe-to-shard-delivers-records-in-order, kinesis.subscribe-to-shard-delivers-records-in-sequence-order, kinesis.subscribe-to-shard-delivers-records-in-write-order, kinesis.subscribe-to-shard-honors-starting-position-latest, kinesis.subscribe-to-shard-expires-after-five-minutes, kinesis.subscribe-to-shard-second-subscription-rejected, kinesis.subscribe-to-shard-with-shard-id-from-another-stream-rejected, kinesis.subscribe-to-shard-dry-run-rejected, kinesis.subscribe-to-shard-dry-run-skips-execution, kinesis.subscribe-to-shard-dry-run-does-not-deliver-records, kinesis.subscribe-to-shard-missing-permission-denied, kinesis.subscribe-to-shard-without-permission-denied, kinesis.subscribe-to-shard-without-permission-must-be-denied, kinesis.subscribe-to-shard-event-stream-framing-over-a-hand-signed-http2-request, kinesis.two-enhanced-fanout-consumers-each-receive-all-records, kinesis.e2e-enhanced-fanout-consumer-lifecycle, kinesis.e2e-stream-consumer-fanout-subscribe-flow, kinesis.deep-kinesis-resharding-efo-subscription-on-split-parent-ends-with-child-shards.

=== Cause 2 of 4: DeleteStream's consumers-present refusal message is reworded in its tail ===
AWS: Smithy: DeleteStream { StreamName, StreamARN, EnforceConsumerDeletion } models ResourceInUseException (HTTP 400) — "The resource is not available for this operation. For successful operation, the resource must be in the ACTIVE state". Recorded behavior for a stream that still has registered consumers and EnforceConsumerDeletion unset: 400 ResourceInUseException whose message is the fixed text "DeleteStream can\u2019t delete <account>:<streamName> because there are consumers associated with this data stream. To delete <streamName> anyway, set the EnforceConsumerDeletion parameter to true to force the deletion of all the consumers that are associated with it." (note the typographic apostrophe in "can\u2019t"). The only variable parts are the 12-digit account id and the stream name, both taken from the request and the emulator's state; everything else is fixed.
Emulator: same code and status, but the final clause is rewritten: it ends "...to force the deletion of all the consumers associated with this data stream." instead of AWS's "...to force the deletion of all the consumers that are associated with it." The account:stream prefix and the rest of the sentence match.
Why: a client or test that matches on the refusal text (the common way to distinguish "needs EnforceConsumerDeletion" from the other ResourceInUseException causes, which share one code) does not match, and the emulator teaches a wording AWS does not use.
Fix: the DeleteStream handler's refusal message (or the shared stream-message helper in the kinesis service crate's state module that composes it).
Traces: kinesis.delete-stream-with-active-consumer-requires-enforce-flag.

=== Cause 3 of 4: the ValidationException for an invalid ShardLevelMetrics enum member is the wrong shape (per-index path, no outer constraint wrapper, wrong value rendering) ===
AWS: Smithy: DisableEnhancedMonitoring.ShardLevelMetrics targets MetricsNameList (len 1..7) whose member is the MetricsName enum [IncomingBytes, IncomingRecords, OutgoingBytes, OutgoingRecords, WriteProvisionedThroughputExceeded, ReadProvisionedThroughputExceeded, IteratorAgeMilliseconds, ALL]. For ShardLevelMetrics=["NotARealMetric"] AWS answers 400 ValidationException with "1 validation error detected: Value '[<the whole list, comma-separated>]' at 'shardLevelMetrics' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [ALL, IteratorAgeMilliseconds, IncomingBytes, WriteProvisionedThroughputExceeded, OutgoingRecords, ReadProvisionedThroughputExceeded, IncomingRecords, OutgoingBytes]]". Fixed text: the "N validation error(s) detected: Value ... at ... failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [...]]" frame, including the OUTER "Member must satisfy constraint: [...]" wrapper AWS adds when the violated constraint is on a list's member; variable parts: the rejected value rendered as the whole list in brackets, the member path (the unindexed input member name 'shardLevelMetrics'), and the enum value set in the order AWS prints it.
Emulator: 400 ValidationException with "1 validation error detected: Value 'NotARealMetric' at 'shardLevelMetrics.1.member' failed to satisfy constraint: Member must satisfy enum value set: [IncomingBytes, IncomingRecords, OutgoingBytes, OutgoingRecords, WriteProvisionedThroughputExceeded, ReadProvisionedThroughputExceeded, IteratorAgeMilliseconds, ALL]" — it names the single offending element instead of the whole list value, uses an indexed path 'shardLevelMetrics.1.member' instead of 'shardLevelMetrics', drops the outer "Member must satisfy constraint: [ ... ]" wrapper, and prints the enum in model-declaration order rather than AWS's order.
Why: this is the generic constraint-walk renderer for list-of-enum members, so every kinesis operation that takes such a list (EnableEnhancedMonitoring too) teaches a path and a message shape AWS never emits; clients that parse the member path out of a ValidationException resolve it to a non-existent member.
Fix: the framework constraint-walk/validation message renderer for list members (the layer that refuses before the handler runs — see the handler note in services/service-com-amazonaws-kinesis-kinesis-20131202/src/ops/enable_enhanced_monitoring.rs, lines 8-15: the invalid enum value is "refused with a 400 ValidationException by the framework's constraint walk, before this handler runs").
Traces: kinesis.disable-enhanced-monitoring-invalid-metric-fails.

=== Cause 4 of 4: Kinesis publishes no AWS/Kinesis datapoints to CloudWatch, armed or not ===
AWS: recorded behavior only (no kinesis model operation covers metric emission). Kinesis delivers AWS/Kinesis metrics to CloudWatch: stream-level IncomingRecords/IncomingBytes/OutgoingRecords dimensioned by StreamName for every stream, and additionally ShardId-dimensioned series once EnableEnhancedMonitoring(ShardLevelMetrics=["ALL"]) has taken effect — IncomingRecords Sum equals the number of records put, IncomingBytes counts the data blob PLUS the partition key, OutgoingRecords counts records read, the SampleCount statistic counts put OPERATIONS, and ListMetrics registers the metric with dimensions {StreamName, ShardId}. A stream with enhanced monitoring OFF has no ShardId-dimensioned series at all and ListMetrics registers none, while its stream-level series still arrives.
Emulator: the control-plane half is implemented (EnableEnhancedMonitoring stores and reports the metric set — services/service-com-amazonaws-kinesis-kinesis-20131202/src/ops/enable_enhanced_monitoring.rs), but no AWS/Kinesis datapoint ever becomes readable: both checks that terminate at CloudWatch (GetMetricStatistics/ListMetrics in namespace AWS/Kinesis, polling for the exact expected Sums) never satisfy their predicate and are reported as "Check timed out after 60.0s" at the harness cap, where a service that published promptly would satisfy them in seconds. Hypothesis: there is no emission path from the kinesis data plane into the cloudwatch service's metric store, so neither the stream-level series nor the shard-dimensioned series exists.
Why: a client that measures throughput, alarms on IteratorAgeMilliseconds/WriteProvisionedThroughputExceeded, or verifies that shard-level metrics are withheld until enhanced monitoring is armed, sees a permanently empty AWS/Kinesis namespace; EnableEnhancedMonitoring appears to work while changing nothing observable.
Fix: metric emission in the kinesis data-plane handlers (put_record / put_records / get_records) writing AWS/Kinesis datapoints into the cloudwatch service state — stream-dimensioned always, ShardId-dimensioned gated on the stream's stored shard-level metric set, with IncomingBytes including the partition key bytes and per-call sample counts.
Traces: kinesis.enhanced-shard-level-metrics-land-in-cloudwatch-with-shard-dimension, kinesis.shard-dimensioned-metrics-absent-until-enhanced-monitoring-is-enabled.
