=== Cause 1 of 2: an EMPTY ConfigurationToken is refused with the 'Corrupted' token verdict instead of a missing-required-parameter validation refusal ===
AWS: ConfigurationToken is @required and bound to the query string (Smithy: GetLatestConfigurationRequest$ConfigurationToken, @httpQuery configuration_token, required, target Token with @pattern ^\S{1,8192}$ - a blank value cannot satisfy that pattern), and the refusal is BadRequestException, httpError 400. A request that supplies no usable value for that member is a VALIDATION failure, not a verdict about a token: the refusal's message is built mechanically from the request - it names the member and tells the caller where a token comes from ('ConfigurationToken must be provided. Use the StartConfigurationSession API to obtain an InitialConfigurationToken'), so the rule is the requirement, not the recorded sentence - and the envelope carries NO Details union, because Details.InvalidParameters[<param>].Problem (Corrupted / Expired / PollIntervalNotSatisfied) is a verdict ON a presented token and there is no token here. The same expectation was recorded on the wire corpus for the tokenless GET (see Cause 5 of the fixed issue named above).
Emulator: the blank value is not refused by required/pattern validation at all. It reaches the handler's session lookup, misses, and is answered with the Corrupted branch: HTTP 400, code BadRequestException, message 'Token not valid', and (from the same branch) Reason 'InvalidParameters' plus Details.InvalidParameters.ConfigurationToken = {'Problem': 'Corrupted'}.
Why: a client that branches on the modelled discriminator is told the token it never sent is corrupted, so it restarts the configuration session (the documented response to Corrupted/Expired) instead of fixing its own request, and the message names nothing it got wrong. The empty-token case and the garbage-token case become indistinguishable, which is exactly the distinction the Details union exists to carry.
Fix: GetLatestConfiguration's input validation layer (required-member and @pattern enforcement on ConfigurationToken) must refuse a blank/absent value BEFORE the handler's token lookup runs, emitting the request-derived missing-parameter message and omitting the Details union; the handler's token-verdict path must only be reached by a value that actually looks like a token.

In the checkout, services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs lines 246-258 take the request value straight to state.session(&token) and return bad_configuration_token("Corrupted") on a miss, with the message table at lines 176-180 mapping Corrupted -> 'Token not valid'.

=== Cause 2 of 2: a token that has already served one poll is refused BadRequestException 'Token expired', where AWS still serves it within the token's lifetime ===
AWS: a configuration token is limited by TIME, not by consumption. The model's own documentation for the operation states 'To support long poll use cases, the token is valid for up to 24 hours. If a GetLatestConfiguration call uses an expired token, the system returns BadRequestException', and the single-use wording is client guidance ('This token should only be used once', 'should always replace the token used for the just-completed call'). Recorded behavior: re-presenting a session's InitialConfigurationToken after the first poll already rotated it is ACCEPTED immediately and serves the same deployed content - the requested minimum poll interval binds the next-poll token that was handed back, not the session, and a poll refused for PollIntervalNotSatisfied leaves that token unconsumed. So within 24 hours of minting, a previously used token must still answer 200 with the configuration bytes, ContentType, a fresh NextPollConfigurationToken and NextPollIntervalInSeconds.
Emulator: any token that has served one call is refused with BadRequestException, HTTP 400, message 'Token expired' and Details.InvalidParameters.ConfigurationToken = {'Problem': 'Expired'}: the poll marks the session consumed and the expiry test treats 'consumed' as identical to 'past its lifetime'.
Why: a client or test that re-presents a token it still holds - the documented recovery after a poll whose response it failed to persist, or any replay of the initial token - gets a hard 400 and the Expired discriminator, whose documented remedy is to restart the session, where AWS would have served the configuration. The whole poll chain becomes strictly one-shot per token, so retry logic that is correct against AWS fails here, and this is also what stops the gated-session check from reaching its remaining assertions.
Fix: the GetLatestConfiguration handler's token-lifetime check and the session state behind it - 'Expired' must be decided by the token's mint time against the token lifetime (and nothing else), so a token that has already served a call is still accepted while it is inside that window; rotation should continue to mint and return a successor token without making the presented token unusable.
Traces: appconfigdata.early-poll-rejected-when-minimum-interval-requested [error] - 'botocore.errorfactory.BadRequestException: An error occurred (BadRequestException) when calling the GetLatestConfiguration operation: Token expired', raised after the check's early-poll assertions (BadRequestException, 400, Reason 'InvalidParameters', Details.InvalidParameters.ConfigurationToken.Problem == 'PollIntervalNotSatisfied', no Configuration, no NextPollConfigurationToken) had all passed. Hypothesis (the replay report does not show the check's line number): the refused call is the check's positive control that re-presents the gated session's InitialConfigurationToken, which the first poll already consumed - the check's only other unwrapped polls use freshly minted tokens and those same calls succeed in appconfigdata.appconfigdata-first-poll-returns-deployed-configuration. In the checkout this is services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs: expiry_refusal() at lines 402-408 returns the 'Expired' refusal when session.is_consumed() OR now >= session.expires_at, consulted at lines 262-264 and 338-340, with state.consume_token(&token, now) at line 343.
