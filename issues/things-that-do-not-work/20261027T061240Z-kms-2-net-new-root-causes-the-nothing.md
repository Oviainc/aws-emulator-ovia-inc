# KMS: 2 net-new root causes — the "nothing allowed" AccessDeniedException names the identity-based policy where AWS names the resource-based one, and a key-policy Deny's Condition block is never evaluated (2 causes)

> _Note: this issue was identified against the code base at commit `b76363ba3639c1fb1d2b9b08f3e303f98ad8a036`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Decrypt

## Description
Two independent net-new root causes in the KMS authorization gate, each grounded in failing behavioral checks the replay report marked neither ALREADY FILED nor OWNED. Both are downstream of the authorization gate that now exists (the gate itself was reported absent by the still-open 20261024T102105Z-kms-no-authorization-is-evaluated-putkeypolicy-has-no.md and, for the key-policy Deny half, by Cause 1 of the still-open 20261027T005501Z-kms-4-net-new-root-causes-a-key.md): the gate now refuses, but it words the refusal wrongly and it ignores the Condition block of the statement it refuses on. Neither open issue carries either replay key below, and neither describes the message clause or the Condition evaluation. There are 2 causes; both must be closed before submitting.

=== Cause 1 of 2: the terminal "no authority allowed this" refusal always blames the IDENTITY-based policy, where AWS blames the RESOURCE-based policy ===
AWS: on a KMS cryptographic call the key's own key policy is the resource-based authority that is always present, and it is the authority a caller must be let through by (directly, or because the key policy delegates to the account's identity policies). When no authority allows the action, AWS refuses AccessDeniedException with HTTP 400 and the message "User: <caller ARN> is not authorized to perform: kms:<Action> on resource: <key ARN> because no resource-based policy allows the kms:<Action> action". Fixed text: "User: ", " is not authorized to perform: ", " on resource: ", " because no resource-based policy allows the ", " action". Variable parts: the caller ARN from the request's signing identity, the kms:<Action> name of the operation being refused (appearing TWICE in the sentence), and the key ARN resolved from the request's KeyId against state. Smithy: the KMS model lists AccessDeniedException on no operation (Encrypt/Decrypt/GenerateDataKey model only DisabledException, InvalidKeyUsageException, NotFoundException, KMSInvalidStateException, InvalidGrantTokenException, InvalidCiphertextException on Decrypt, etc.), so the code, the 400 status and the sentence are recorded behavior only; the three grounding checks each assert this exact template for a key whose policy grants only grant-administration actions and never the cryptographic one.
Emulator: the same refusal is produced with the clause "because no identity-based policy allows the kms:<Action> action". The code (AccessDeniedException) and the status (400) are correct, and every other token of the sentence matches; only the policy-type word diverges. Replay evidence: "User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: kms:Encrypt on resource: arn:aws:kms:us-west-2:000000000000:key/<id> because no identity-based policy allows the kms:Encrypt action" where the expected clause is "because no resource-based policy allows the kms:Encrypt action"; the same substitution appears on kms:Decrypt. One service-wide helper produces this text for every terminal refusal, so every KMS operation's no-allow refusal carries the wrong clause.
Why: the clause is the only part of the refusal that tells an operator WHICH document to repair. "No identity-based policy allows it" sends an engineer to attach an IAM policy, which on a key whose key policy does not delegate to IAM changes nothing — the repair is in the key policy (or in a grant). Clients and runbooks that branch on the two clauses (and the many test harnesses that assert AWS's sentence verbatim) take the wrong branch, and the misdirection is worst on exactly the keys that are locked down hardest.
Fix: the KMS state module's authorization component — the refusal-message helper and its selection by the terminal no-allow path, which must name the resource-based policy for a KMS key's authorization failure rather than reusing the identity-based wording.
Failing checks: kms.grant-token-bypasses-listing-eventual-consistency, kms.grant-token-enables-immediate-use-before-propagation, kms.grant-token-immediate-use-bypasses-propagation-delay. (All three are blocked at their FIRST assertion, a baseline refusal taken before any grant exists, so the grant-token contract each of them exists to grade — that a fresh GrantToken authorizes the operation immediately, before the grant is visible in ListGrants — is still entirely ungraded behind this message and must also hold once the sentence is fixed.)
Traces: services/service-com-amazonaws-kms-trentservice/src/state/authorization.rs lines 200-212 (fn no_identity_policy_message, the format! at 208-211), reached from fn authorize at line 197 (the terminal refusal) and at line 173 (the presented-grant-token refusal).

=== Cause 2 of 2: a key-policy Deny statement's Condition block is not evaluated, so a conditioned Deny refuses every request for that action ===
AWS: a policy statement applies only when its Condition block is satisfied. A key-policy statement with Effect Deny, Principal {"AWS":"*"}, Action "kms:Decrypt" and Condition {"StringNotEquals": {"kms:EncryptionContext:tenant": "<allowed>"}} therefore denies Decrypt ONLY for a request whose encryption context's "tenant" entry is not <allowed>; a Decrypt carrying the allowed context is unaffected and succeeds, returning the plaintext, and Encrypt/GenerateDataKey under the same policy are unaffected because the statement names kms:Decrypt alone. kms:EncryptionContext:<key> is a documented KMS condition key evaluated against the request's EncryptionContext (AWS KMS developer guide, "Condition keys for AWS KMS"). Smithy: Decrypt.EncryptionContext targets EncryptionContextType (a map) and the key policy is server state reachable through GetKeyPolicy/PutKeyPolicy, so this is a server-side authorization decision made per request; the AccessDeniedException the denied branch produces is recorded behavior only (the model lists it on no operation).
Emulator: the Condition block is dropped, so the conditioned Deny matches unconditionally and Decrypt is refused for EVERY caller and EVERY encryption context — including the allowed one, and including the key's own owner. Replay evidence: after PutKeyPolicy appends that statement, Decrypt with the ALLOWED context (EncryptionContext={"tenant":"allowed"}) raises an uncaught "botocore.exceptions.ClientError: An error occurred (AccessDeniedException) when calling the Decrypt operation: User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: kms:Decrypt on resource: arn:aws:kms:us-west-2:000000000000:key/<id> with an explicit deny in a resource-based policy" — the explicit-deny branch, taken for a request the condition excludes from that statement. The denied-context leg immediately before it did produce AccessDeniedException, so the gate fires; it fires on the wrong requests. Hypothesis: the deny decision is taken from (action, resource, principals) only — no request condition context is passed to the shared policy evaluator — so a statement carrying any Condition is treated as matching on the Deny path. The mirror of the same mechanism on the Allow path is reported separately for kms__s3 (a conditioned Allow never allows).
Why: this is a correctness AND an availability defect in the same place. Fine-grained KMS authorization is built almost entirely out of conditioned statements (per-tenant kms:EncryptionContext scoping, aws:PrincipalArn carve-outs, kms:ViaService confinement); against this emulator any such statement becomes a blanket deny of its action, so the legitimate traffic it is designed to permit is refused and a developer validating a per-tenant key policy sees total loss of access instead of the scoped behavior. A caller cannot distinguish "your context is outside the permitted scope" from "this key denies everyone", because both produce the identical explicit-deny sentence.
Fix: the KMS state module's authorization component — the deny evaluation must pass the request's condition context (the request's EncryptionContext for kms:EncryptionContext:<key>, the caller's ARN for aws:PrincipalArn, the calling service for kms:ViaService) into the shared policy evaluator, and a statement whose Condition is not satisfied must not contribute a Deny.
Failing check: kms.key-policy-encryption-context-condition-gates-decrypt. (The check stops at the allowed-context Decrypt, so its remaining legs are ungraded and must also hold: Encrypt and GenerateDataKey under the DENIED context must still succeed because the Deny names kms:Decrypt only, DescribeKey must still report KeyState Enabled, and restoring the original policy must make the identical ciphertext open again.)
Traces: services/service-com-amazonaws-kms-trentservice/src/state/authorization.rs lines 138-151 (fn authorize's deny path: iam::Request::new(&action, &key.arn, &denying) carries no condition context, and iam::resource_decision == Decision::Denied returns explicit_deny_message).
