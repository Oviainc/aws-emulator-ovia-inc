# cloudformation__ec2: 6 net-new causes — 26 AWS::EC2::* resource types unregistered, CREATE_COMPLETE for resources EC2 never created, Outputs without OutputValue, invalid properties accepted, missing template validation, wrong VPCGatewayAttachment Ref

> _Note: this issue was identified against the code base at commit `e85d2009e41cfda8a7867f84cab4a050d23db70a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Six distinct root causes in the CloudFormation+EC2 surface. Each is numbered with its own failing check ids; all six must be closed before this issue is done.

Cause 1 of 6: CloudFormation does not register 26 modelled AWS::EC2::* resource types.
AWS: CreateStack/UpdateStack accept any resource type in the CloudFormation registry; AWS::EC2::TransitGatewayVpcAttachment, TransitGatewayRouteTableAssociation, TransitGatewayRouteTablePropagation, TransitGatewayPolicyTable, CapacityReservation, CapacityReservationFleet, VPCEncryptionControl, InstanceEventWindow, IPAM, IPAMPool, IpamExternalResourceVerificationToken, IPAMPrefixListResolver, IPAMPrefixListResolverTarget, IPAMPoolCidr, IPAMAllocation, IPv4Pool, ApplicationStatusCheck, NetworkInsightsAccessScope, NetworkInsightsAccessScopeAnalysis, NetworkInsightsPath, NetworkInsightsAnalysis, RouteServer, RouteServerAssociation, RouteServerEndpoint, RouteServerPeer, RouteServerPropagation, Snapshot, TrafficMirrorFilter, TrafficMirrorFilterRule, TrafficMirrorTarget, TrafficMirrorSession, VerifiedAccessTrustProvider, VerifiedAccessInstance, VerifiedAccessGroup, VPCBlockPublicAccessExclusion, SubnetCidrBlock, SecurityGroupVpcAssociation, VPNConcentrator, VPNConnectionRoute and VPNGatewayRoutePropagation are all public types, so a template declaring them is accepted and the stack provisions. Smithy: CreateStack models AlreadyExistsException/InsufficientCapabilitiesException/LimitExceededException/TokenAlreadyExistsException only; `ValidationError` is the service-common query error used for template format errors.
Emulator: CreateStack (and UpdateStack) answer HTTP 400 `ValidationError` with message `Template format error: Unrecognized resource types: [<comma-separated type list>]`. The fixed text is "Template format error: Unrecognized resource types: " followed by the bracketed list of the types from the request; nothing in the recording's list is a per-run value.
Why: every stack that touches one of these types is refused outright, so transit-gateway, IPAM, route-server, traffic-mirror, verified-access, snapshot and VPN estates cannot be deployed at all.
Fix: the CloudFormation resource-type registry and the per-type resource handlers for these AWS::EC2::* types.

Cause 2 of 6: a stack reaches CREATE_COMPLETE but the EC2 resource it reports created does not exist in EC2.
AWS: after CREATE_COMPLETE, the physical id a stack resource reports is readable through the owning EC2 Describe* call; an id EC2 does not know is answered with that resource's own NotFound code (e.g. InvalidDhcpOptionID.NotFound "The dhcpOption ID '<id>' does not exist").
Emulator: DescribeDhcpOptions answers `InvalidDhcpOptionID.NotFound` for the DhcpOptions id the stack minted; DescribeNetworkInterfaces answers `InvalidNetworkInterfaceID.NotFound`; DescribeNetworkAcls answers `InvalidNetworkAclID.NotFound`; tag-filtered DescribeCustomerGateways and DescribeManagedPrefixLists return an empty list for the stack's Ref. The ids and names in those messages come from the request; the fixed text is the per-resource NotFound wording.
Why: a client that deploys network plumbing with CloudFormation and then drives it through the EC2 API finds nothing there, so every follow-on call fails even though the stack says the resource exists.
Fix: the AWS::EC2::DHCPOptions, NetworkInterface, NetworkAcl/NetworkAclEntry, CustomerGateway and PrefixList resource handlers must create the resource in EC2 state, not only record a physical id.
Traces: cloudformation__ec2.cfn-dhcp-options-invalid-ntp-server-rolls-back, .cfn-dhcp-options-read-back-through-ec2-api, .deploy-ec2-eip-network-interface-association-round-trip-and-delete, .deploy-ec2-network-acl-entry-and-subnet-association-round-trip-and-delete, .deploy-ec2-customer-gateway-and-vpn-gateway-round-trip-and-delete, .deploy-ec2-customer-gateway-invalid-bgp-asn-rejected, .deploy-ec2-prefix-list-max-entries-below-minimum-rejected.

Cause 3 of 6: DescribeStacks returns Outputs entries with no OutputValue.
AWS: Smithy: cloudformation#Output carries OutputKey, OutputValue, Description and ExportName; a resolved stack output always carries OutputValue.
Emulator: the Output entries carry OutputKey only, so a client reading output["OutputValue"] raises KeyError: 'OutputValue'.
Why: every consumer that reads a stack output to find the id of what it just deployed breaks.
Fix: the DescribeStacks serializer / stack-output resolution in the CloudFormation state.
Traces: cloudformation__ec2.deploy-ec2-instance-read-back-and-removed, .deploy-ec2-launch-template-read-back-and-removed, .deploy-ec2-nat-gateway-round-trip-and-delete, .deploy-ec2-route-round-trip-and-delete, .deploy-ec2-network-interface-and-volume-attachment-read-back-and-removed. (An open issue 20261022T235108Z-cloudformation-stack-outputs-carry-no-outputvalue-failing-resources.md describes the same shape for other checks; these five are not carried by it.)

Cause 4 of 6: invalid EC2 property values are accepted and the stack reaches CREATE_COMPLETE instead of rolling back.
AWS: a resource whose create the EC2 API refuses makes CloudFormation emit CREATE_FAILED for it and drive the stack to ROLLBACK_COMPLETE. A launch-template name already registered is refused; a security-group rule whose FromPort is above its ToPort is refused.
Emulator: the stacks end 'CREATE_COMPLETE' — for a launch template reusing an already-registered name, and for SecurityGroupIngress / SecurityGroupEgress with an inverted port range.
Why: templates that are invalid in AWS appear to deploy, so a client never learns its configuration is wrong and later EC2 behaviour silently differs.
Fix: the AWS::EC2::LaunchTemplate, SecurityGroupIngress and SecurityGroupEgress handlers must propagate the EC2 API refusal into CREATE_FAILED/rollback.
Traces: cloudformation__ec2.deploy-ec2-launch-template-duplicate-name-rejected, .deploy-ec2-security-group-egress-invalid-port-range-rejected-and-rolled-back, .deploy-ec2-security-group-ingress-invalid-port-range-rejected-and-rolled-back.

Cause 5 of 6: pre-provision template validation does not report required-property and property-type errors.
AWS: a missing required property on AWS::EC2::SecurityGroup surfaces as the EC2-wrapped handler message for the service's own validation failure; a property declared with the wrong JSON type is reported by ValidateTemplate/CreateStack as `Property [<Name>] expected type: Integer, found: String` against the template path `/Resources/<Logical>/Properties/<Name>`.
Emulator: the missing-GroupDescription reason is an un-wrapped `Resource handler returned message: "1 validation error detected: Value null at 'description' failed to satisfy constraint: Member must not be null"` with no (Service: …, Status Code: …, Request ID: …) suffix; the non-numeric Size on AWS::EC2::Volume yields an empty validation-error list instead of the single expected-type error.
Why: a client cannot tell a schema mistake from a runtime failure, and type errors are not surfaced at all.
Fix: CloudFormation's resource-schema validation pass and the handler-message wrapper that adds the owning service, status code and request id.
Traces: cloudformation__ec2.cfn-ec2-securitygroup-schema-structure-defers-to-ec2-api-and-warns, .cfn-ec2-volume-size-type-mismatch-rejected.

Cause 6 of 6: AWS::EC2::VPCGatewayAttachment Ref is a generated stack name rather than the attachment id.
AWS: Ref on AWS::EC2::VPCGatewayAttachment returns the attachment id, of the form `IGW|<vpc-id>` for an internet gateway attachment (or `VGW|<vpc-id>` for a virtual private gateway).
Emulator: Ref returns `<stack-name>-<logical-id>-<suffix>`.
Why: a template that passes the attachment Ref to another resource or output hands downstream code a value EC2 does not recognise.
Fix: the AWS::EC2::VPCGatewayAttachment handler's physical-resource-id/Ref resolution.
Traces: cloudformation__ec2.deploy-ec2-vpc-gateway-attachment-round-trip-and-delete.
