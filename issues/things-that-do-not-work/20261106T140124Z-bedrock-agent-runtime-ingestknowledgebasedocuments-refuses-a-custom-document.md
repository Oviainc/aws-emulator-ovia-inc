# bedrock-agent-runtime: IngestKnowledgeBaseDocuments refuses a CUSTOM document against a MANAGED_KNOWLEDGE_BASE_CONNECTOR data source, so a managed knowledge base can never be loaded (1 cause)

> _Note: this issue was identified against the code base at commit `0f21bdaacf606a414ed170f95e60e0507d4ecb5b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IngestKnowledgeBaseDocuments

## Description
Cause 1 of 1: IngestKnowledgeBaseDocuments compares the document's `content.dataSourceType` against the data source's `dataSourceConfiguration.type` by raw string equality, so a data source created with type MANAGED_KNOWLEDGE_BASE_CONNECTOR (the managed-knowledge-base CUSTOM connector) can never accept any document: the request is refused 400 ValidationException instead of being accepted 202. Failing check ids (1): bedrock-agent-runtime.get-document-content-nonexistent-document-not-found.

AWS: Smithy (com.amazonaws.bedrockagent#IngestKnowledgeBaseDocuments) — http {method: PUT, uri: /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/documents, code: 202}; input members knowledgeBaseId/dataSourceId (@httpLabel, pattern ^[0-9a-zA-Z]{10}$, required) and documents (KnowledgeBaseDocuments, @length 1..10, required); modeled errors AccessDeniedException 403, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ThrottlingException 429, ValidationException 400. Smithy: DocumentContent.dataSourceType targets ContentDataSourceType, whose complete value set is CUSTOM | S3 — there is NO MANAGED_KNOWLEDGE_BASE_CONNECTOR value a caller could put there. Smithy: DataSourceConfiguration.type targets DataSourceType = S3 | WEB | CONFLUENCE | SALESFORCE | SHAREPOINT | CUSTOM | REDSHIFT_METADATA | MANAGED_KNOWLEDGE_BASE_CONNECTOR, and DataSourceConfiguration.managedKnowledgeBaseConnectorConfiguration.connectorParameters is a @document whose `type` names the connector (here "CUSTOM"). The operation's own doc says the content's dataSourceType "must match the type of the data source that you specify in the header" — matching means the CONTENT kind (CUSTOM/S3), which for a MANAGED_KNOWLEDGE_BASE_CONNECTOR data source whose connectorParameters.type is CUSTOM is CUSTOM. Recorded behavior: AWS accepts CreateDataSource(type=MANAGED_KNOWLEDGE_BASE_CONNECTOR, connectorParameters={type: CUSTOM, version: 1, aclEnabled: false}) and then accepts IngestKnowledgeBaseDocuments with documents[0].content.dataSourceType = CUSTOM and content.custom.sourceType = IN_LINE with 202, returning documentDetails whose status advances to INDEXED.

Emulator: the request is refused 400 ValidationException with the message "The dataSourceType that you specified in CUSTOM doesn't match the type of the data source specified in the request header. Check that both types match and retry your request." Fixed text of that message: "The dataSourceType that you specified in <content dataSourceType> doesn't match the type of the data source specified in the request header. Check that both types match and retry your request."; the only variable part is the content's dataSourceType value taken from the request (here CUSTOM). That sentence is AWS's wording for a genuine mismatch (e.g. dataSourceType=S3 addressed at a CUSTOM data source) and must not fire for this request at all. The comparison is unsatisfiable for this data source kind: the content value can only be CUSTOM or S3, while the stored configuration type is the literal "MANAGED_KNOWLEDGE_BASE_CONNECTOR".

Why: a client cannot put a single document into a managed knowledge base. Every direct-ingestion workflow — ingest, poll GetKnowledgeBaseDocuments to INDEXED, then read the document back with bedrock-agent-runtime GetDocumentContent or retrieve it — dies at the first ingest with a ValidationException blaming the caller's dataSourceType, which is in fact the only value the model permits. The user re-reads the docs, re-sends CUSTOM, and is refused again; nothing they can send is accepted. Because the ingest never lands, the downstream GetDocumentContent semantics this check exists to verify (the ingested text behind presignedUrl, ResourceNotFoundException for a never-ingested documentId, and the "Knowledge Base with id <kbId> does not exist" message for a fabricated triple) are never exercised either.

Fix: the IngestKnowledgeBaseDocuments handler's validation of the content/data-source kind pairing — services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/ingest_knowledge_base_documents.rs, the per-document loop (the `content_type != data_source_type` guard and the message helper crate::state::document_data_source_type_message). The pairing must be resolved against the data source's CONTENT kind, not its connector enum: a MANAGED_KNOWLEDGE_BASE_CONNECTOR data source whose connectorParameters.type is CUSTOM accepts dataSourceType=CUSTOM documents (and the S3 connector accepts S3), with the ValidationException reserved for a content kind that really does not correspond to the addressed data source. Not the serializer: the 202 output shape is right; the request never reaches it.

Related open work (does NOT cover this check; the suite marked it neither owned nor already filed): 20261103T030007Z-bedrock-agent-runtime-getdocumentcontent-stub.md covers GetDocumentContent being an unimplemented stub. This check never reaches GetDocumentContent — it dies in its setup on the ingest refusal above — so implementing GetDocumentContent alone does not close it.

Traces: bedrock-agent-runtime.get-document-content-nonexistent-document-not-found.

## Steps to Reproduce
1. iam CreateRole with a trust policy allowing bedrock.amazonaws.com to sts:AssumeRole; keep the role ARN.
2. bedrock-agent CreateKnowledgeBase(name=<name>, roleArn=<role arn>, knowledgeBaseConfiguration={"type":"MANAGED","managedKnowledgeBaseConfiguration":{"embeddingModelType":"MANAGED"}}); poll GetKnowledgeBase until knowledgeBase.status == ACTIVE.
3. bedrock-agent CreateDataSource(knowledgeBaseId=<kbId>, name=<name>, dataSourceConfiguration={"type":"MANAGED_KNOWLEDGE_BASE_CONNECTOR","managedKnowledgeBaseConnectorConfiguration":{"connectorParameters":{"type":"CUSTOM","version":"1","aclEnabled":false}}}); poll GetDataSource until dataSource.status == AVAILABLE.
4. bedrock-agent IngestKnowledgeBaseDocuments(knowledgeBaseId=<kbId>, dataSourceId=<dsId>, documents=[{"content":{"dataSourceType":"CUSTOM","custom":{"customDocumentIdentifier":{"id":"<docId>"},"sourceType":"IN_LINE","inlineContent":{"type":"TEXT","textContent":{"data":"any text"}}}}}]).
5. Observe 400 ValidationException "The dataSourceType that you specified in CUSTOM doesn't match the type of the data source specified in the request header. …" where AWS answers 202 with documentDetails for <docId>. No value of content.dataSourceType succeeds: S3 is refused with the same sentence, and the data source's own kind (MANAGED_KNOWLEDGE_BASE_CONNECTOR) is not a member of ContentDataSourceType so the SDK rejects it client-side.
6. Downstream, bedrock-agent-runtime GetDocumentContent(knowledgeBaseId=<kbId>, dataSourceId=<dsId>, documentId=<docId>) can therefore never be exercised on a real ingested document.
