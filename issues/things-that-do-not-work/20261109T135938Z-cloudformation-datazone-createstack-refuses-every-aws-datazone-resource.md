# cloudformation__datazone: CreateStack refuses every AWS::DataZone::* resource type as "Unrecognized resource types" — 2 net-new causes, no DataZone estate is deployable by IaC

> _Note: this issue was identified against the code base at commit `00353ccf65811f65ad7f73dbcefa75ea121211d3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
The emulator's CloudFormation template resource-type registry knows no AWS::DataZone::* type, so CreateStack rejects the template during template validation (HTTP 400 ValidationError, "Template format error: Unrecognized resource types: [...]") and no DataZone resource can be provisioned through CloudFormation/CDK at all. Both behavioral checks in this service pairing die on their very first CloudFormation call, before any DataZone operation is reached.

Two net-new causes, one per resource family a check deploys. They are listed separately because each needs its own resource provider (create/read/update/delete plus its own Ref and GetAtt attribute set, and its own mapping of DataZone's refusals onto registry-handler failure reasons); merely registering the type names closes neither.

No open issue covers these. The closest open issues are the same SHAPE of defect for other services — e.g. 20261109T113556Z-cloudformation-omics-createstack-refuses-every-aws-omics-resource.md (AWS::Omics::*) and 20261109T113428Z-cloudformation-mwaa-createstack-refuses-aws-mwaa-environment-as.md (AWS::MWAA::Environment) — and neither mentions AWS::DataZone. The open datazone issues (domain lifecycle, error wording, the CreateSubscriptionRequest/DeleteAssetType/DeleteGlossaryTerm/UpdateAccountPool stubs) are all about the DataZone data-plane/control-plane API itself and own none of the CloudFormation paths below.

Cause 1 of 2: AWS::DataZone::Domain, AWS::DataZone::Project and AWS::DataZone::EnvironmentProfile are unrecognized, so the domain/project/environment-profile round trip and the child-removal update are unreachable.
AWS: CloudFormation accepts a template declaring Type: AWS::DataZone::Domain (Name, DomainExecutionRole, SingleSignOn: {Type: DISABLED}, Tags), Type: AWS::DataZone::Project (DomainIdentifier, Name) and Type: AWS::DataZone::EnvironmentProfile (DomainIdentifier, ProjectIdentifier, EnvironmentBlueprintIdentifier, Name, AwsAccountId, AwsAccountRegion) and converges to CREATE_COMPLETE / UPDATE_COMPLETE, provisioning real DataZone resources. Ref of the domain yields the domain id (Smithy datazone CreateDomain.output.id -> DomainId, @pattern ^dzd[-_][a-zA-Z0-9_-]{1,36}$; HTTP 201). Ref of a domain-scoped child is the composite "<domainId>|<childId>" and GetAtt Id is the bare child id (CreateProject.output.id -> ProjectId @pattern ^[a-zA-Z0-9_-]{1,36}$; CreateEnvironmentProfile.output.id -> EnvironmentProfileId @pattern ^[a-zA-Z0-9_-]{0,36}$); the environment profile additionally exposes GetAtt ProjectId, EnvironmentBlueprintId and CreatedAt (CreateEnvironmentProfile.output.projectId / .environmentBlueprintId / .createdAt, timestampFormat date-time, rendered by CloudFormation as an ISO8601 timestamp). The deployed resources are then independently readable: ListDomains/GetDomain show the templated name, domainExecutionRole, singleSignOn.type DISABLED, status AVAILABLE and the template's Tags; ListProjects/GetProject and ListEnvironmentProfiles/GetEnvironmentProfile show exactly the templated name, awsAccountId, awsAccountRegion, environmentBlueprintId, projectId, domainId and createdAt. An UpdateStack that drops only the Project and EnvironmentProfile reaches UPDATE_COMPLETE and deletes only those two (neither is listed any more) while the domain still reads back unchanged; after DeleteStack the domain is gone, so a domain-scoped read is refused — the check asserts 403 AccessDeniedException with message "User is not permitted to perform operation: GetEnvironmentProfile" (fixed text "User is not permitted to perform operation: " + the operation name; AccessDeniedException is modelled on GetEnvironmentProfile with httpError 403).
Emulator: the first call already fails — CreateStack returns HTTP 400 ValidationError with message "Template format error: Unrecognized resource types: [AWS::DataZone::Domain]". In that message "Template format error: Unrecognized resource types: [" ... "]" is fixed text and the bracketed, comma-separated type list is the variable part, taken from the request's TemplateBody. Nothing is provisioned, so no Ref, no GetAtt, no UPDATE_COMPLETE child-removal and no post-delete refusal is ever observable.
Why: a client that manages a DataZone domain/project/environment-profile estate with CloudFormation or CDK cannot create a stack at all, and because the refusal is classified as a template-format error the client blames its own template rather than a missing resource provider. Tear-down-by-template (removing children on update, removing the domain on DeleteStack) is likewise impossible.
Fix: the CloudFormation resource-type registry and its provider set — register AWS::DataZone::Domain, ::Project and ::EnvironmentProfile and back them with providers over the datazone CreateDomain/CreateProject/CreateEnvironmentProfile and the corresponding deletes, exposing Ref = domain id for the domain and "<domainId>|<childId>" for domain-scoped children, plus GetAtt Id/ProjectId/EnvironmentBlueprintId/CreatedAt, and honouring the inter-resource dependencies expressed by Ref/GetAtt between them.
Traces: cloudformation__datazone.deploy-datazone-environment-profile-round-trip-and-delete.

Cause 2 of 2: AWS::DataZone::ProjectProfile (and the V2 flavour of AWS::DataZone::Domain) is unrecognized, so neither the domain-version rejection nor its positive control is reachable.
AWS: a template may declare two AWS::DataZone::Domain resources, one default (V1) and one with DomainVersion: V2 plus ServiceRole (Smithy datazone CreateDomain.input.domainVersion -> DomainVersion enum and .serviceRole -> RoleArn @pattern ^arn:aws[^:]*:iam::\d{12}:role(/[a-zA-Z0-9+=,.@_-]+)*/[a-zA-Z0-9+=,.@_-]+$; both echoed in CreateDomain.output), and both reach CREATE_COMPLETE with GetDomain reading back domainVersion V2 and the serviceRole ARN for the second. An UpdateStack adding Type: AWS::DataZone::ProjectProfile (DomainIdentifier: Ref of the V1 domain, Name) must FAIL: project profiles are a V2-only API, so the resource's handler refusal rolls the stack back to UPDATE_ROLLBACK_COMPLETE and the Profile resource's UPDATE_FAILED/CREATE_FAILED StackEvent carries the registry-handler ResourceStatusReason 'Resource handler returned message: "API not supported for domain version (Service: DataZone, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)' — fixed text "API not supported for domain version" wrapped in the standard service/status/request-id envelope, with HandlerErrorCode InvalidRequest; the request id, request token and attempt count are per-run values and not part of the requirement. The same template with DomainIdentifier naming the V2 domain reaches UPDATE_COMPLETE, Ref of the profile is "<domainId>|<projectProfileId>" and GetAtt Id / CreatedAt are CreateProjectProfile.output.id (ProjectProfileId @pattern ^[a-zA-Z0-9_-]{1,36}$) / .createdAt; ListProjectProfiles and GetProjectProfile in the V2 domain then show exactly that id, the templated name and that createdAt.
Emulator: CreateStack answers HTTP 400 ValidationError "Template format error: Unrecognized resource types: [AWS::DataZone::Domain]" for the very first template (the two domains), so the ProjectProfile update is never attempted: the UPDATE_ROLLBACK_COMPLETE status, the InvalidRequest HandlerErrorCode and the "API not supported for domain version" reason are all unreachable, and so is the V2 positive control.
Why: an IaC caller gets neither a deployable V2 project-profile path nor AWS's precise, actionable refusal when a profile is attached to a V1 domain — once the type exists it must surface DataZone's own InvalidRequest/"API not supported for domain version" handler reason and roll the stack back rather than fail generically or silently succeed.
Fix: the CloudFormation resource-type registry and the AWS::DataZone::ProjectProfile provider (plus the Domain provider's DomainVersion/ServiceRole properties) — register the type, back it with datazone CreateProjectProfile/DeleteProjectProfile, expose Ref = "<domainId>|<profileId>" and GetAtt Id/CreatedAt, and map the DataZone refusal onto a registry-handler failure reason with HandlerErrorCode InvalidRequest that rolls the stack back.
Traces: cloudformation__datazone.deploy-datazone-project-profile-v1-domain-rejected-v2-round-trips.

## Evidence
Both checks fail on their first CloudFormation call, with the identical refusal.

Expected (AWS): CreateStack accepts the template (HTTP 200, a StackId is returned) and DescribeStacks converges to CREATE_COMPLETE; the subsequent UpdateStack calls reach UPDATE_COMPLETE, except the deliberately-rejected ProjectProfile-on-V1-domain update, which reaches UPDATE_ROLLBACK_COMPLETE with the Profile resource's failure reason 'Resource handler returned message: "API not supported for domain version (Service: DataZone, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)'.

Actual (emulator), verbatim from the replay:
- cloudformation__datazone.deploy-datazone-environment-profile-round-trip-and-delete: botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::DataZone::Domain]
- cloudformation__datazone.deploy-datazone-project-profile-v1-domain-rejected-v2-round-trips: botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::DataZone::Domain]

The HTTP status (400) and the error code (ValidationError) are AWS's own for a genuinely unknown resource type; the divergence is that AWS::DataZone::Domain, ::Project, ::EnvironmentProfile and ::ProjectProfile are NOT unknown to AWS. In the message, "Template format error: Unrecognized resource types: [" and "]" are fixed text and the comma-separated type list inside the brackets is taken from the request's TemplateBody; the templates here also declare AWS::DataZone::Project, ::EnvironmentProfile and ::ProjectProfile, which the registry would reject the same way once the Domain type is added in isolation.

Model support (Smithy, service-com-amazonaws-datazone-datazone): CreateDomain POST /v2/domains, HTTP 201, input name (required), domainExecutionRole, singleSignOn, tags, domainVersion, serviceRole -> output id (DomainId ^dzd[-_][a-zA-Z0-9_-]{1,36}$), status (DomainStatus), domainVersion, serviceRole, tags. CreateProject POST /v2/domains/{domainIdentifier}/projects, 201 -> output domainId, id (ProjectId), name, createdAt. CreateEnvironmentProfile POST /v2/domains/{domainIdentifier}/environment-profiles, 201, input environmentBlueprintIdentifier/projectIdentifier (required), awsAccountId ^\d{12}$, awsAccountRegion ^[a-z]{2}-[a-z]{4,10}-\d$ -> output id, domainId, projectId, environmentBlueprintId, createdAt. CreateProjectProfile POST /v2/domains/{domainIdentifier}/project-profiles, 201 -> output domainId, id (ProjectProfileId), name, createdAt. GetEnvironmentProfile / GetProjectProfile are GET reads with AccessDeniedException (403), ResourceNotFoundException (404) and ValidationException (400) modelled.
