# iam: 2 net-new behavioral root causes — a DateLessThan/aws:CurrentTime Allow never grants inside its window, and ForAllValues/ForAnyValue on aws:TagKeys never inverts a decision (both checks exhaust the 60 s cap)

> _Note: this issue was identified against the code base at commit `2b443a1d32fe9865f4d2b32010552c8e62eefe3f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListUserTags

## Description
Two distinct net-new root causes in the bootstrapped `iam` service, each grounded in a failing behavioral check of this suite that the replay report marks neither ALREADY FILED nor OWNED. Cause count: 2. A fixer must close BOTH before submitting.

IAM speaks awsQuery (service com.amazonaws.iam#AWSIdentityManagementV20100508, version 2010-05-08); every status/code below is the awsQueryError form. Both causes sit in the request authorizer that runs ahead of the operation handlers, but they are separate defects: one is the Date* operator family over the request-time global key aws:CurrentTime, the other is the ForAllValues:/ForAnyValue: set-operator qualifiers over the request-time key aws:TagKeys. Fixing either one alone leaves the other check failing.

=== Cause 1 of 2: a DateLessThan condition on aws:CurrentTime never grants, so a time-boxed Allow is refused for the whole life of its window ===
AWS: Smithy models ListUserTags with input UserName (existingUserNameType, @required, @length 1..128, @pattern ^[\w+=,.@-]+$) and output Tags (@required) / IsTruncated / Marker; its only modeled errors are NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404) and ServiceFailureException (ServiceFailure, 500). The authorization decision itself is not modeled (AccessDenied/403 is a service-common refusal), so it is recorded behavior only, read against AWS's documented condition-operator semantics (reference_policies_elements_condition_operators): `DateLessThan` on `aws:CurrentTime` is TRUE while the request instant is BEFORE the named instant. Therefore an inline user policy statement {"Effect":"Allow","Action":"iam:ListUserTags","Resource":"<user-arn>","Condition":{"DateLessThan":{"aws:CurrentTime":"<deadline>"}}} must serve the signed iam:ListUserTags with HTTP 200 and the user's Tags repeatedly while the deadline is in the future, and only once the deadline passes refuse it HTTP 403 Error.Code `AccessDenied` with Error.Message whose fixed text is `User: ` + ` is not authorized to perform: iam:ListUserTags on resource: user ` + ` because no identity-based policy allows the iam:ListUserTags action` and whose variable parts are the caller's ARN (the principal whose access key signed the request) and the target user's name, both taken from the request and the emulator's own state. The flip must be observable in wall-clock time at the named instant, not earlier.
Emulator: the conditioned Allow never grants at all. The check never gets a single success out of the conditioned statement, so its poll for three consecutive in-window successes never reaches its predicate and the check is killed at the harness cap: `Error: Check timed out after 60.0s`. This is not a dead key or a dead document: the SAME check first polls an UNCONDITIONED statement in the same user policy (Allow iam:GetUser on the same user ARN) to three consecutive successes with the same minted access key before it writes the conditioned statement, and that barrier passes. Only the conditioned statement is being dropped. Hypothesis: the authorizer builds a condition context that contains no `aws:CurrentTime`, so every Date* operator evaluates false and the statement is discarded regardless of the operator's direction.

Why: a client cannot validate any time-boxed grant against this emulator. Every least-privilege policy that opens a window with DateGreaterThan or closes one with DateLessThan is treated as granting nothing, so a policy that works in production is refused here; and a policy author cannot distinguish "my date window is not open" from "my document is wrong", because both read as the same implicit-deny message.
Fix: the request authorizer's condition-context builder and its Date* operator evaluation in the iam crate's authorization gate — the component that resolves the signing principal and evaluates attached/inline/session policies ahead of the operation handlers (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/service.rs and the policy-evaluation module it calls). It must populate the request-time global condition keys aws:CurrentTime and aws:EpochTime from the request instant and evaluate DateLessThan / DateLessThanEquals / DateGreaterThan / DateGreaterThanEquals against them.

=== Cause 2 of 2: the ForAllValues:/ForAnyValue: set-operator qualifiers over aws:TagKeys never invert an authorization decision ===
AWS: Smithy models TagUser with input UserName (@required) and Tags (tagListType, @required, @length 0..50), output Unit, and errors ConcurrentModificationException (ConcurrentModification, 409), InvalidInputException (InvalidInput, 400), LimitExceededException (LimitExceeded, 409), NoSuchEntityException (NoSuchEntity, 404) and ServiceFailureException (ServiceFailure, 500); GetUser and ListUserTags model only NoSuchEntity 404 / ServiceFailure 500. The decision is again recorded behavior only (AccessDenied/403 service-common), read against AWS's documented single-vs-multi-valued context-key semantics (reference_policies_condition-single-vs-multi-valued-context-keys): with the condition key `aws:TagKeys` bound to the set [env, tier], `ForAllValues:StringEquals` is true iff EVERY tag key in the request is in that set — and vacuously true when the request supplies no tag keys at all — while `ForAnyValue:StringEquals` is true iff AT LEAST ONE request key is in the set, and false over an empty key set. So swapping the qualifier in place on an otherwise identical document must INVERT exactly two outcomes and leave three unchanged: TagUser with keys {env, owner} goes from AccessDenied to applied in full, a key-less GetUser goes from allowed to AccessDenied, while {env} and {env, tier} stay allowed and {owner} stays denied. Each refusal is HTTP 403 `AccessDenied` with the fixed text `User: ` + ` is not authorized to perform: iam:TagUser on resource: user ` + ` because no identity-based policy allows the iam:TagUser action` (variable parts: the caller ARN and the target user name, from the request/state) followed by AWS's authorization-details trailer, and a denied TagUser must apply NOTHING — the target's tag map read back through ListUserTags is byte-for-byte what it was before, with no partial application of the in-set keys.
Emulator: no leg of the swap converges. The check is killed at the harness cap with `Error: Check timed out after 60.0s`, so not one of its set-operator assertions is ever reached. Every step of this check is gated on the emulator producing a specific allow/deny pattern: a propagation barrier that polls the document's unconditioned ListUserTags grant to three consecutive successes, a read-after-write poll of the target's tag map toward an exact expected map after each allowed TagUser, and — after the in-place operator swap — a barrier that waits for the NEW sentinel action to be allowed WHILE the OLD sentinel action is denied, three times running. One of those predicates is never satisfied inside the cap, so the aws:TagKeys set-operator semantics are unobservable against this emulator; the timeout is the only observable, and no decision on a set-operator statement was ever returned to assert on. Hypothesis: as in Cause 1, the request condition context is built empty, so aws:TagKeys is absent and the qualified conditions evaluate uniformly (never inverting), and/or the ForAllValues:/ForAnyValue: qualifiers are not parsed at all.
Related open issues, named because they look similar and do NOT cover this check: 20261025T121312Z-iam-request-time-authorization-supplies-no-condition-context.md reports an empty request-time condition context for aws:ResourceTag AND aws:RequestTag on TagUser — different keys, and it says nothing about the ForAllValues:/ForAnyValue: qualifiers or about aws:TagKeys; 20261025T000319Z-iam-10-net-new-behavioral-root-causes-four.md Cause 10 lists this check id under the key `iam.iam-eval-deep-iam-1-tag-keys-set-operator-swap-inverts-denied|_poll#20|Timeout` from when IAM authorized nothing at all, and the replay report no longer attributes this check to it.
Why: set operators on aws:TagKeys are the documented way to constrain WHICH tag keys a principal may set, and they are the backbone of ABAC guardrails. Here the constraint can be neither proved nor disproved: the emulator does not grant where AWS grants nor deny where AWS denies, so a tagging guardrail validated against this emulator tells the author nothing, and an over-permissive production policy ships unnoticed.
Fix: the same authorization gate named in Cause 1 — the condition-context builder must supply the request-time tag keys (aws:TagKeys, and the aws:RequestTag/${key} family) from the operation's tag input, and the policy evaluator must implement the ForAllValues: and ForAnyValue: qualifiers including their empty-key-set semantics (ForAllValues true over an empty set, ForAnyValue false), so that swapping the qualifier changes the decision.
Traces: iam.iam-eval-deep-iam-1-tag-keys-set-operator-swap-inverts-denied.

## Evidence
Suite: simparity-behavioral-ga-prod-v1. Both checks are verdict `mismatch` against the bootstrapped `iam` service, and both are reported with the same single observable:

Cause 1 — check iam.iam-eval-deep-iam-1-date-less-than-deadline-passes-then-denied:
  Error: Check timed out after 60.0s
The check's shape localises it. Before the conditioned policy is written it (a) creates a user, (b) puts an UNCONDITIONED inline policy `{Allow iam:GetUser on <user-arn>}`, (c) mints an access key for that user and builds an iam client signing with that key alone, and (d) polls GetUser with it until it succeeds THREE TIMES IN A ROW (timeout 120 s, interval 2 s) — that barrier passes, so the key and the document are live and the gate serves unconditioned Allows. It then reads the server's `Date` response header, rounds it up a second, sets deadline = that + 90 s, and puts a SECOND inline policy `{Allow iam:ListUserTags on <user-arn>, Condition:{DateLessThan:{aws:CurrentTime:<deadline>}}}`. The next step is `_poll(three_in_a_row, lambda n: n >= 3, timeout_s=60, interval_s=1)` on `list_user_tags(UserName=<user>)`, which requires the conditioned grant to succeed three times running WELL INSIDE the 90 s window. The check dies at the 60 s cap, i.e. that predicate was never reached: the in-window conditioned Allow never produced three successes. Expected from AWS: HTTP 200 with the user's Tags on every in-window call, then HTTP 403 `AccessDenied` with `User: arn:<partition>:iam::<account>:user/<user> is not authorized to perform: iam:ListUserTags on resource: user <user> because no identity-based policy allows the iam:ListUserTags action` only after the named instant, with measured elapsed time at the refusal >= 90 s.

Cause 2 — check iam.iam-eval-deep-iam-1-tag-keys-set-operator-swap-inverts-denied:
  Error: Check timed out after 60.0s
The check puts one inline policy on a caller user with four statements — Allow iam:TagUser on <target-arn> conditioned `{ForAllValues:StringEquals:{aws:TagKeys:[env,tier]}}`, Allow iam:GetUser on <target-arn> under the same condition, an UNCONDITIONED Allow iam:ListUserTags on <target-arn> (the read-back grant), and an unconditioned Allow of a sentinel action on the caller itself — then mints an access key for the caller and drives everything through that key. It polls the unconditioned ListUserTags grant to three consecutive successes as its propagation barrier, polls the target's tag map to an exact expected map after each allowed TagUser, and after rewriting the SAME policy name with `ForAnyValue:StringEquals` (confirming via GetUserPolicy that the stored document now carries ForAnyValue) it polls for the new sentinel being allowed while the old sentinel is denied, three times running. The run never leaves those polls inside the cap, so none of the five set-operator outcomes — {env} allowed, {env,tier} allowed, {env,owner} denied-then-allowed, {owner} denied, key-less GetUser allowed-then-denied — nor the "a denied TagUser applies nothing" read-back was ever evaluated. Expected from AWS: the operator swap inverts exactly the {env,owner} TagUser and the key-less GetUser, each refusal being HTTP 403 `AccessDenied` with `User: <caller-arn> is not authorized to perform: iam:TagUser on resource: user <target> because no identity-based policy allows the iam:TagUser action` plus the authorization-details trailer (the per-call authorization id in that trailer is a per-run value the check reads back out of the received message and never compares).

Neither check is marked ALREADY FILED or OWNED in this replay report. Both check ids appear in the Issue-Trace-Ids of open issue 20261025T000319Z-iam-10-net-new-behavioral-root-causes-four.md under `_poll#28|Timeout` / `_poll#20|Timeout` keys recorded when IAM performed no authorization at all; the gate now answers (the unconditioned barriers in both checks pass), so those keys no longer match and the report attributes the checks to no issue.

## Steps to Reproduce
Build and boot the emulator from this checkout and replay the two checks in trace_ids. Each cause also reproduces standalone against the iam endpoint:

Cause 1 (DateLessThan / aws:CurrentTime):
1. iam CreateUser(UserName=<u>).
2. iam PutUserPolicy(UserName=<u>, PolicyName='base', PolicyDocument={Version:'2012-10-17', Statement:[{Effect:'Allow', Action:'iam:GetUser', Resource:'arn:aws:iam::<account>:user/<u>'}]}).
3. iam CreateAccessKey(UserName=<u>); build an iam client that signs with that key alone.
4. Poll iam GetUser(UserName=<u>) with that client until it succeeds three times in a row — it does, so the key and the gate work for an unconditioned Allow.
5. Take the `Date` response header from that GetUser, round it up to the next whole second, and let deadline = that instant + 90 s.
6. iam PutUserPolicy(UserName=<u>, PolicyName='deadline', PolicyDocument={Version:'2012-10-17', Statement:[{Effect:'Allow', Action:'iam:ListUserTags', Resource:'arn:aws:iam::<account>:user/<u>', Condition:{DateLessThan:{'aws:CurrentTime':<deadline, ISO-8601 Z>}}}]}).
7. Call iam ListUserTags(UserName=<u>) with the minted-key client, repeatedly, starting immediately. Observe that it is never served inside the window (the conditioned Allow does not grant), so no in-window success is obtainable and a bounded poll for it exhausts its budget. AWS returns HTTP 200 with the Tags on every call before <deadline>.
8. Keep calling past <deadline>: AWS flips to HTTP 403 AccessDenied '... because no identity-based policy allows the iam:ListUserTags action', while the unconditioned iam:GetUser grant on the same principal keeps working.

Cause 2 (ForAllValues/ForAnyValue over aws:TagKeys):
1. iam CreateUser for a target <t> and for a caller <c>.
2. iam PutUserPolicy(UserName=<c>, PolicyName='setop') with four statements: {Sid:'TagUnderTest', Allow, Action:'iam:TagUser', Resource:'<t-arn>', Condition:{'ForAllValues:StringEquals':{'aws:TagKeys':['env','tier']}}}, {Sid:'AbsentKeyProbe', Allow, Action:'iam:GetUser', Resource:'<t-arn>', same Condition}, {Sid:'ReadBack', Allow, Action:'iam:ListUserTags', Resource:'<t-arn>'} with no condition, {Sid:'Sentinel', Allow, Action:'iam:ListAttachedUserPolicies', Resource:'<c-arn>'} with no condition.
3. iam CreateAccessKey(UserName=<c>); build an iam client signing with that key alone and use it for every call below.
4. Poll iam ListUserTags(UserName=<t>) to three consecutive successes (the propagation barrier on the unconditioned statement).
5. iam TagUser(UserName=<t>, Tags=[{env:a1}]) — AWS allows ({env} is a subset of {env,tier}); then TagUser with [{env:b1},{tier:t1}] — allowed; then TagUser with [{env:c1},{owner:o1}] — AWS refuses AccessDenied and applies NOTHING (ListUserTags still shows env=b1,tier=t1); then TagUser with [{owner:x1}] — refused; then GetUser(UserName=<t>) — ALLOWED, because ForAllValues over a request with no tag keys is true.
6. iam PutUserPolicy on <c> with the SAME PolicyName but 'ForAnyValue:StringEquals' in both Conditions and a different sentinel action ('iam:ListGroupsForUser'); confirm via GetUserPolicy that the stored document carries ForAnyValue.
7. Poll until the new sentinel is allowed and the old sentinel is denied, three times running.
8. Repeat the five calls of step 5: AWS now ALLOWS [{env:c2},{owner:o2}] in full (owner present on read-back) and DENIES the key-less GetUser(UserName=<t>) with '... because no identity-based policy allows the iam:GetUser action' plus the authorization-details trailer, while {env}, {env,tier} stay allowed and {owner} stays denied. Observe that the emulator produces none of these transitions, so the barriers/read-back polls never converge and the replay is killed at the 60 s cap.
