# CloudWatch request-validation and error-envelope divergences: 10 net-new root causes (ValidationException envelope, NextToken text, alarm/insight-rule/dashboard/tag validation)

> _Note: this issue was identified against the code base at commit `ec258a82c643322f3f1b10a7ea424abc4c176038`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
This issue bundles 10 net-new root causes in the CloudWatch control plane's request validation and error envelope. Every cause is independent; all 10 must be closed before submitting.

Cause 1 of 10: the emulator answers invalid requests with a Smithy-style `ValidationException` and a `1 validation error detected: Value ... failed to satisfy constraint: ...` message, where CloudWatch answers with its own Query/JSON error codes and its own texts.
AWS: the Smithy model binds CloudWatch's errors with explicit awsQueryError codes — e.g. DeleteInsightRules declares `InvalidParameterValueException` (awsQueryError `InvalidParameterValue`, 400) and `MissingRequiredParameterException` (awsQueryError `MissingParameter`, 400); TagResource declares `InvalidParameterValueException` / `ResourceNotFoundException`. `ValidationException` is not a CloudWatch error shape at all, and CloudWatch never emits the "N validation error(s) detected" text. The required codes per check are `ValidationError` (DeleteMetricStream, StartMetricStreams, ListMetricStreams MaxResults=501, GetDataset malformed DatasetIdentifier, PutMetricAlarm with Threshold dropped from the wire), `MissingParameter` (ListManagedInsightRules with ResourceARN omitted, GetInsightRuleReport with Period omitted), and `InvalidParameterValue` (ListMetrics, PutMetricData invalid Unit). The message is AWS's own text: for an out-of-enum Unit, `The value for parameter MetricData.member.1.Unit is not valid.`-class InvalidParameterValue text rather than an enum-set dump; for GetMetricStatistics with a bad Period, the fixed text `The parameter Period must be a multiple of 60.` (the emulator instead returns `The parameter Period must be a value in the set [1, 5, 10, 20, 30].`). Where an enum-set message IS correct (DescribeAlarmHistory historyItemType), the value list must be rendered in the model's declaration order `[AlarmContributorAction, AlarmContributorStateUpdate, Action, StateUpdate, ConfigurationUpdate]`, not re-ordered. One sub-case is the inverse: `PutMetricData` with a Namespace starting with ':' must SUCCEED — the model's `pattern: "^[^:]"` on Namespace is documented but not enforced server-side (recorded behavior) — and the emulator refuses it with ValidationException.
Emulator: `ValidationException` + `1 validation error detected: ...` on every one of those calls, and a refusal where AWS accepts the ':' namespace.
Why: a client that catches `ValidationError`/`MissingParameter`/`InvalidParameterValue` (the codes botocore's error factory exposes for CloudWatch) sees an unmodelled `ValidationException` instead, so its except-clause never fires and the error surfaces as a generic ClientError; IaC that publishes under a ':'-prefixed namespace fails only against the emulator.
Fix: the shared Query/JSON error serializer for this service plus each named operation's input validation — the generic constraint-violation path must be replaced by CloudWatch's per-operation codes and texts.
Traces: cloudwatch.delete-metric-stream-missing-required-parameter-rejected, cloudwatch.start-metric-streams-missing-required-parameter-rejected, cloudwatch.stop-metric-streams-missing-required-parameter-rejected, cloudwatch.list-metric-streams-max-results-out-of-bounds-rejected, cloudwatch.list-managed-insight-rules-missing-required-param, cloudwatch.list-managed-insight-rules-missing-required-param-rejected, cloudwatch.get-insight-rule-report-missing-required-param, cloudwatch.get-dataset-readonly-reflects-configuration, cloudwatch.put-log-alarm-limit-exceeded-enforced, cloudwatch.put-anomaly-detector-invalid-stat-rejected, cloudwatch.list-metrics-pagination-stability, cloudwatch.op-contract-listMetrics, cloudwatch.op-contract-listMetrics-namespace-pattern, cloudwatch.put-metric-data-invalid-unit-rejected, cloudwatch.get-metric-statistics-invalid-period-rejected, cloudwatch.describe-alarm-history-invalid-history-item-type-rejected. (The open issue 20261028T043126Z-cloudwatch-enum-constraint-validationerror-messages-are-rendered-from.md covers the enum-ordering family for other operations; these replay keys are not on it.)

Cause 2 of 10: the pagination-token refusal is one generic string, and DescribeAlarms refuses a token it must ignore.
AWS: `InvalidNextToken` is modelled on DescribeAlarms/DescribeAlarmHistory/DescribeInsightRules/ListManagedInsightRules (awsQueryError `InvalidNextToken`, 400), but its MESSAGE is per-operation fixed text with the caller's token interpolated: DescribeAlarmHistory answers `Invalid NextToken : <token>` (fixed prefix `Invalid NextToken : `, variable part = the NextToken from the request), while DescribeInsightRules and ListManagedInsightRules answer the fixed text `INVALID_TOKEN: Unsupported token version.` with no variable part. DescribeAlarms is different again: recorded behavior shows an undecodable token is treated as if none had been supplied and the FIRST PAGE is served (200), despite InvalidNextToken being modelled on it.
Emulator: every one of those operations returns the single invented message `NextToken is not a token this service issued`, and DescribeAlarms raises `InvalidNextToken` instead of serving the first page.
Why: a paginator or retry wrapper that resumes DescribeAlarms after a token round-trips through a store (or a client that logs the token back) gets a hard 400 where AWS silently restarts the listing; and message-matching clients see text AWS never produces.
Fix: the pagination-token decoder shared by these list operations (per-operation message template), and DescribeAlarms' handler must fall back to page one on an undecodable token instead of raising.
Traces: cloudwatch.alarm-history-chronological-ordering, cloudwatch.describe-alarm-history-invalid-next-token-rejected, cloudwatch.describe-insight-rules-and-invalid-next-token-rejected, cloudwatch.op-contract-describeAlarmHistory, cloudwatch.op-contract-describeInsightRules-dup, cloudwatch.list-managed-insight-rules-invalid-next-token, cloudwatch.describe-alarms-invalid-next-token-is-ignored, cloudwatch.describe-alarms-state-filter-and-invalid-next-token-ignored.

Cause 3 of 10: the anomaly-detector operations share one invented refusal message and one unstable member ordering, and an anomaly-band alarm that must be refused is accepted.
AWS: PutAnomalyDetector/DeleteAnomalyDetector with no identification answer the fixed text `Input missing required parameter.`; DeleteAnomalyDetector specifically answers `Either an AnomalyDetectorId or a metric definition must be provided to identify the anomaly detector to delete.`; DescribeAnomalyDetectors with AnomalyDetectorIds plus metric filters answers the fixed text `AnomalyDetectorIds cannot be combined with metric filters (Namespace, MetricName, Dimensions, AnomalyDetectorTypes, or AnomalyDetectorSearchTerms). Provide either AnomalyDetectorIds for a direct lookup, or metric filters to list, but not both.`; and when more than one detector style is set the message lists the offending members in the model's declaration order (`found MetricMathAnomalyDetector, SingleMetricAnomalyDetector.`). PutMetricAlarm with a ThresholdMetricId whose band is misconfigured is refused.
Emulator: one message, `Either single metric attributes, SingleMetricAnomalyDetector or MetricMathAnomalyDetector must be set.`, for all three missing-identification cases; `When using AnomalyDetectorIds, you cannot also specify the Namespace, MetricName, Dimensions, or AnomalyDetectorTypes metric filters` for the combination case; the "found ..." list emitted in request order (`found SingleMetricAnomalyDetector, MetricMathAnomalyDetector.`); and the anomaly-band alarm call returns 200.
Why: operators keying on the message to tell "no identifier" from "too many identifiers" cannot distinguish them, and an unrefused anomaly-band alarm is stored with a threshold metric that will never evaluate.
Fix: the anomaly-detector handlers' validation and their message templates (declaration-order member rendering), and PutMetricAlarm's ThresholdMetricId validation.
Traces: cloudwatch.anomaly-detector-missing-required-param-rejected, cloudwatch.delete-anomaly-detector-and-missing-identifier-rejected, cloudwatch.op-contract-deleteAnomalyDetector-dup, cloudwatch.put-anomaly-detector-missing-identification-rejected, cloudwatch.describe-anomaly-detectors-invalid-combination, cloudwatch.describe-anomaly-detectors-invalid-parameter-combination-rejected, cloudwatch.op-contract-describeAnomalyDetectors, cloudwatch.op-contract-putAnomalyDetector-delete-lifecycle, cloudwatch.anomaly-detection-band-alarm-threshold-metric-id.

Cause 4 of 10: PutMetricAlarm / PutCompositeAlarm / DeleteAlarms accept configurations AWS refuses.
AWS: PutMetricAlarm refuses, with `ValidationError` 400, (a) `DatapointsToAlarm` greater than `EvaluationPeriods` (an impossible M-of-N window), (b) a `Period` that is not 10, 20, 30 or a multiple of 60 — the recorded refusal for Period=45 — (c) `Statistic` and `ExtendedStatistic` both set, (d) a `TreatMissingData` value outside {missing, notBreaching, breaching, ignore}, (e) a Metrics array in which no member has ReturnData=true, (f) other mutually-exclusive combinations of single-metric and Metrics form. PutCompositeAlarm refuses an `ActionsSuppressor` naming an alarm that does not exist with `ValidationError` and the message `Could not save the composite alarm as the actions suppressor alarm [arn:aws:cloudwatch:<region>:<account>:alarm:<suppressorName>] does not exist` (fixed text around a bracketed ARN built from the request's suppressor name and the caller's region/account), and a syntactically malformed AlarmRule is a PARSE failure worded `Error in AlarmRule [Unsupported token '<EOF>' at char <offset>]`. DeleteAlarms refuses deletion of an alarm that is still referenced by a composite alarm's rule.
Emulator: every one of those calls returns HTTP 200 with an empty body; the malformed-AlarmRule refusal uses the emulator's own wording `AlarmRule: expected ')' after an alarm reference at offset <n>`.
Why: an invalid alarm is stored and silently never evaluates (or evaluates on a window AWS would not allow), so IaC and alarm-provisioning tools validate clean against the emulator and fail in the real account; deleting a composite's child silently breaks the composite.
Fix: PutMetricAlarm's and PutCompositeAlarm's input validation (period set, M-of-N window, statistic exclusivity, TreatMissingData enum, ReturnData requirement, suppressor existence, AlarmRule parser error text) and DeleteAlarms' referential check.
Traces: cloudwatch.alarm-datapoints-to-alarm-exceeds-evaluation-periods-rejected, cloudwatch.put-metric-alarm-period-not-multiple-of-sixty-rejected, cloudwatch.put-metric-alarm-rejects-invalid-period, cloudwatch.put-metric-alarm-rejects-statistic-and-extended-statistic, cloudwatch.put-metric-alarm-invalid-treat-missing-data-rejected, cloudwatch.put-metric-alarm-invalid-combo-rejected, cloudwatch.alarm-math-and-anomaly-return-data-count-rejected, cloudwatch.alarm-composite-and-actions-suppressor-naming-missing-alarm-rejected, cloudwatch.delete-alarms-referenced-by-composite-rejected, cloudwatch.op-contract-put-composite-alarm.

Cause 5 of 10: account quotas are never enforced, so LimitExceeded is unreachable — and where a limit message IS produced it is invented.
AWS: PutMetricAlarm and PutCompositeAlarm declare `LimitExceededFault` (awsQueryError `LimitExceeded`, 400) as their only modelled error; the alarm-count quota, the composite-parent quota and the Contributor Insights rule quota are all enforced server-side, and a composite AlarmRule referencing more alarms than a rule may include is refused with AWS's own text.
Emulator: 201 Metrics-Insights alarms were created without ever hitting LimitExceeded; PutInsightRule kept succeeding past the rule quota; the composite-parent limit was not applied; and the over-limit AlarmRule refusal carries the emulator-authored text `AlarmRule references 101 alarms, which is more than the 100 a composite alarm's rule can include`.
Why: capacity-planning and error-handling paths that depend on LimitExceeded can never be exercised, and a message-matching client sees text AWS never emits.
Fix: the alarm/insight-rule state store must carry per-account counters and raise LimitExceededFault from PutMetricAlarm, PutCompositeAlarm and PutInsightRule, with AWS's message text.
Traces: cloudwatch.put-metric-alarm-limit-exceeded-enforced, cloudwatch.put-composite-alarm-parent-limit-exceeded-rejected, cloudwatch.enable-insight-rules-limit-exceeded-rejected, cloudwatch.limit-exceeded-family.

Cause 6 of 10: SetAlarmState accepts a malformed StateReasonData instead of refusing it with InvalidFormat.
AWS: SetAlarmState's only modelled client errors are `InvalidFormatFault` (awsQueryError `InvalidFormat`, HTTP 400) and `ResourceNotFound` (404). StateReasonData is documented as a JSON document (model: @length 0–4000); a body that is not valid JSON is refused with InvalidFormat, and the refusal leaves the alarm's state untouched.
Emulator: every malformed StateReasonData variant — not-JSON, truncated JSON, a JSON scalar where an object is required — returns HTTP 200 with an empty body and mutates the alarm state.
Why: a caller that drives alarm state from templated JSON gets a silent success for a corrupt payload; the alarm then carries unparseable reason data that downstream consumers of the state-change notification cannot read.
Fix: SetAlarmState's handler must parse/validate StateReasonData and raise InvalidFormatFault before touching alarm state.
Traces: cloudwatch.set-alarm-state-invalid-format-rejected, cloudwatch.set-alarm-state-invalid-json-reason-rejected, cloudwatch.set-alarm-state-invalid-json-state-reason-rejected, cloudwatch.set-alarm-state-invalid-reason-data-rejected, cloudwatch.set-alarm-state-invalid-state-reason-data-json, cloudwatch.set-alarm-state-invalid-state-reason-data-rejected, cloudwatch.set-alarm-state-malformed-reason-data-rejected, cloudwatch.alarm-state-reason-data-invalid-json-rejected, cloudwatch.op-contract-set-alarm-state.

Cause 7 of 10: Contributor Insights rule-name handling is inverted — unknown names are reported as failures, and syntactically invalid names are reported as "not found" (or wrongly rejected outright).
AWS: DeleteInsightRules is a batch operation whose `Failures` list reports only real failures; a name that never existed is tolerated silently (no Failures entry). A name that violates the rule-name pattern IS reported, as `{"FailureResource": "<name>", "ExceptionType": "InvalidParameterException", "FailureCode": "INVALID_RULE_NAME", "FailureDescription": "RuleName \"<name>\" does not match the pattern: [A-Za-z0-9][A-Za-z0-9\\-\\_\\.]{0,126}[A-Za-z0-9]"}` — fixed text around the offending name and the pattern. DisableInsightRules/EnableInsightRules accept any printable-ASCII name (`^[\x20-\x7E]+$`) and report a pattern violation as InvalidParameterException.
Emulator: unknown names produce `{"ExceptionType": "ResourceNotFoundException", "FailureCode": "RULE_NAME", "FailureDescription": "Rule <name> does not exist."}` entries; a pattern-violating name produces that same not-found entry instead of INVALID_RULE_NAME; and DisableInsightRules/EnableInsightRules reject the perfectly printable name `bad-rule` with `ValidationException: 1 validation error detected: Value 'bad-rule' at 'ruleNames.3.member' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[\x20-\x7E]+$`, which that value satisfies. PutInsightRule's invalid-RuleDefinition refusal also carries invented text (`The value for parameter RuleDefinition is not valid: it names no log group in LogGroupNames or LogGroupARNArray`).
Why: idempotent teardown scripts that delete a rule list twice see spurious Failures and abort; and the printable-ASCII regex is applied wrongly, refusing valid rule names outright.
Fix: the insight-rule handlers' batch-failure construction and their name-pattern validator.
Traces: cloudwatch.delete-insight-rules-failures-and-malformed-name-rejected, cloudwatch.delete-insight-rules-partial-failure, cloudwatch.delete-insight-rules-partial-failure-reported, cloudwatch.insight-rule-delete-nonexistent-reported-in-failures, cloudwatch.op-contract-deleteInsightRules-dup, cloudwatch.disable-insight-rules-and-malformed-name-reported-as-failure-entry, cloudwatch.op-contract-disableInsightRules, cloudwatch.put-insight-rule-invalid-definition-rejected.

Cause 8 of 10: GetInsightRuleReport classifies its refusals under the wrong error code.
AWS: GetInsightRuleReport answers `InvalidParameterValue` for a rule name that does not exist (and for a rule that has been deleted), and `InvalidParameterValue` with AWS's own time-range text for EndTime before StartTime.
Emulator: answers `ResourceNotFoundException` with `Rule <name> does not exist.` for the unknown/deleted rule, and the bare token `INVALID_TIME_RANGE` as the InvalidParameterValue message.
Why: a client distinguishing "bad argument" (do not retry, fix the call) from "resource gone" (recreate it) takes the wrong branch; `INVALID_TIME_RANGE` is a code leaked into the message slot, not a sentence AWS emits.
Fix: GetInsightRuleReport's handler error mapping and message text.
Traces: cloudwatch.get-insight-rule-report-end-before-start-rejected, cloudwatch.get-insight-rule-report-nonexistent-rule-not-found, cloudwatch.insight-rule-report-lifecycle-and-not-found.

Cause 9 of 10: the dashboard operations neither validate their inputs nor use AWS's InvalidParameterValue texts, and a CloudFormation-deployed dashboard never materialises.
AWS: DeleteDashboards with an empty DashboardNames list is refused; a batch beyond the 100-dashboard limit is refused outright (nothing partially applied) with the fixed text `Field DashboardNames can contain up to 100 elements.\n`; a DashboardNamePrefix containing an unsupported character is refused with `The value for field DashboardNamePrefix contains invalid characters. It can only contain alphanumerics, dash (-) and underscore (_).\n` (period is NOT allowed in the prefix); PutDashboard returns `DashboardValidationMessages` entries for widgets whose type it does not recognise while still storing the body.
Emulator: the empty-list delete returns 200; the over-sized batch and the prefix refusals carry rewritten texts (`The value for field DashboardNames is too long. It must have length less than or equal to 100.\n`, and a prefix message that additionally permits `period (.)`); GetDashboard's too-long-name message is likewise rewritten; PutDashboard returns `DashboardValidationMessages: []` for an unrecognised widget type; and the CloudFormation-deployed dashboard check never observes the dashboard body (the check exhausts its budget).
Why: a console/IaC client that surfaces DashboardValidationMessages to the user shows nothing for a broken widget, and prefix validation that accepts '.' lets a name through that AWS will refuse.
Fix: the dashboard handlers' validation and message templates, plus the CloudFormation provider for AWS::CloudWatch::Dashboard.
Traces: cloudwatch.delete-dashboards-empty-name-list-rejected, cloudwatch.delete-dashboards-oversized-batch-preserves-existing-rejected, cloudwatch.get-dashboard-invalid-parameter-value-rejected, cloudwatch.list-dashboards-invalid-parameter-value-rejected, cloudwatch.op-contract-listDashboards, cloudwatch.put-dashboard-invalid-body-rejected, cloudwatch.deploy-cloudformation-dashboard-body-matches-template.

Cause 10 of 10: TagResource accepts tag keys AWS refuses.
AWS: TagResource declares `InvalidParameterValueException` (awsQueryError `InvalidParameterValue`, 400). A tag key containing a character outside the allowed tag-key set, and a tag key using the reserved `aws:` prefix, are both refused with InvalidParameterValue, and no tag is stored.
Emulator: both calls are accepted — one returns HTTP 200 with an empty body, the other returns 200 and stores the reserved-prefix tag.
Why: a reserved `aws:`-prefixed tag that only the emulator accepts makes cost-allocation and policy tooling behave differently against the real account, and the tag cannot be removed by the same code path there.
Fix: TagResource's input validation for tag keys.
Traces: cloudwatch.tag-resource-invalid-key-character-rejected, cloudwatch.tag-resource-invalid-tag-key-prefix-aws-rejected.
