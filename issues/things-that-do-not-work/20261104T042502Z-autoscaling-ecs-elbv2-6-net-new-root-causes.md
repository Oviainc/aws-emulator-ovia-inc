# autoscaling__ecs__elbv2: 6 net-new root causes — Fargate task/target-group convergence never happens, task ENIs carry no private IP, CFN cannot resolve SSM AMI dynamic references, two ASG/ECS stacks roll back, ListTasks loses a stack-created service, and ELB authorization is not enforced

## Operation
CreateService

## Description
Six independent root causes in the Auto Scaling / ECS / ELBv2 surface. Each must be closed before submitting.

Cause 1 of 6: an ECS (Fargate/awsvpc) service or task never converges into an observable steady state — tasks do not reach RUNNING, their ENI IPs never become registered targets, draining/deregistration never completes, and no ECS Task State Change event is delivered — so every check that polls for one of those transitions exhausts its budget with no terminal result. Failing check ids: autoscaling__ecs__elbv2.alb-listener-forwards-request-to-ecs-task-ip, autoscaling__ecs__elbv2.alb-target-group-health-check-marks-ecs-task-healthy, autoscaling__ecs__elbv2.cli-describe-target-health-matches-ecs-task-count, autoscaling__ecs__elbv2.cli-ecs-service-nonexistent-target-group-arn-fails-creation, autoscaling__ecs__elbv2.cli-ecs-service-update-desired-count-reflects-target-group-targets, autoscaling__ecs__elbv2.ecs-run-task-fails-without-ecs-tasks-trust-policy, autoscaling__ecs__elbv2.ecs-service-action-event-triggers-target-lambda, autoscaling__ecs__elbv2.ecs-service-deregisters-tasks-on-scale-down, autoscaling__ecs__elbv2.ecs-service-registers-tasks-with-target-group-arn, autoscaling__ecs__elbv2.ecs-task-execution-role-trusts-ecs-tasks-service, autoscaling__ecs__elbv2.ecs-task-state-change-event-delivered-to-eventbridge-rule, autoscaling__ecs__elbv2.eventbridge-rule-without-target-permission-no-invocation, autoscaling__ecs__elbv2.target-group-port-mismatch-container-port-no-healthy-targets.
  AWS: a Fargate service created with a `loadBalancers` entry naming a target group brings its tasks to RUNNING, registers each task's ENI private IP as a target, reports it healthy once the health check passes, holds it `draining` for the configured deregistration delay on scale-in and then removes it, and publishes RUNNING/STOPPED ECS Task State Change events to EventBridge. The recordings reach these states inside the checks' own deadlines. Recorded behavior only — the model describes the shapes, not the reconciliation.
  Emulator: every one of these polls times out (`Check timed out after 60.0s`): no task ever observed RUNNING with a registered target, no healthy target, no draining-then-removed transition, no task-state-change event. The emulator produced no convergence rather than a wrong value.
  Why: a client that creates a load-balanced Fargate service and waits for its targets (the standard deploy gate) hangs indefinitely; health-check, scale-in and eventing contracts built on these transitions can never be satisfied, and negative-delivery assertions cannot be distinguished from a platform that publishes nothing.
  Fix: the ECS task/service reconciliation and its propagation into ELBv2 target registration and the EventBridge task-state-change publisher (the ECS crate's task/service state machine), not the describe serializers.

Cause 2 of 6: a RUNNING ECS task's attached ENI carries no private IP, so no target IP can be derived from it. Failing check id: autoscaling__ecs__elbv2.cli-create-alb-target-group-ecs-service-e2e.
  AWS: an awsvpc task's `attachments[].details` include `networkInterfaceId` and `privateIPv4Address`, and the corresponding EC2 network interface describes with a private IP in the task's subnet; that IP is what gets registered as an `ip`-type target. Recorded behavior only.
  Emulator: the task reports attachments from which no ENI private IP can be read — `AssertionError: no ENI private IPs found on the running task(s)`.
  Why: every ip-target registration, ALB forwarding check and in-VPC connectivity flow derives the target from that address; without it the client cannot register the task at all even though the task is reported running.
  Fix: the ECS task ENI attachment representation and the EC2 network-interface state it is backed by (the ECS crate's task attachment projection), not the ELBv2 registration call.

Cause 3 of 6: CloudFormation cannot resolve `{{resolve:ssm:...}}` dynamic references to the public AWS AMI parameters, so any stack that picks an AMI that way fails and rolls back. Failing check ids: autoscaling__ecs__elbv2.deploy-asg-missing-trust-policy-fails-instance-registration, autoscaling__ecs__elbv2.deploy-ecs-service-missing-target-group-permission-fails-stack.
  AWS: `/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64` and `/aws/service/ecs/optimized-ami/amazon-linux-2/recommended/image_id` are public SSM Parameter Store parameters that resolve to a current AMI id, so a template using `ImageId: '{{resolve:ssm:/aws/service/...}}'` creates the stack (CREATE_COMPLETE). Recorded behavior only (these are public-parameter contents, not Smithy).
  Emulator: the stack ends `ROLLBACK_COMPLETE` with the failed-resource reason `Unable to resolve the dynamic reference '{{resolve:ssm:/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64}}': ParameterNotFound` (and the same for the ECS-optimized AMI path) — the parameter does not exist in the emulator's SSM state. The parameter path is the fixed part; the stack name in the message is a per-run value.
  Why: the AMI dynamic reference is the canonical way templates pick an image, so essentially every EC2/ASG/ECS-on-EC2 stack fails to deploy; both the positive control and the permission-boundary comparison in these checks become unreachable.
  Fix: the SSM public-parameter seed/state the CloudFormation dynamic-reference resolver reads (the SSM parameter store state, plus the resolver's not-found path), not the per-resource provisioners.

Cause 4 of 6: two ASG/ECS CloudFormation stacks end ROLLBACK_COMPLETE with no resource-level reason surfaced. Failing check ids: autoscaling__ecs__elbv2.deploy-asg-with-elb-target-group-attachment-cfn, autoscaling__ecs__elbv2.deploy-ecs-capacity-provider-autoscaling-cfn.
  AWS: a stack declaring a security group, launch template/configuration, an ASG with an ELB target-group attachment (and, in the second, an ECS cluster with a capacity provider bound to that ASG) reaches CREATE_COMPLETE. Recorded behavior only.
  Emulator: `AssertionError: Stack <name> ended in ROLLBACK_COMPLETE` — the create fails and the emulator exposes no failed-resource status/reason for the client to act on (unlike cause 3, where a reason was surfaced).
  Why: the stack never provisions, and because no resource-level failure reason is reported the client cannot tell which resource type is unsupported; template-driven ASG/ECS estates cannot be stood up.
  Fix: the CloudFormation resource provisioners for AWS::AutoScaling::AutoScalingGroup + target-group attachment and AWS::ECS::CapacityProvider, and the stack-event/failure-reason reporting that must name the failing resource.

Cause 5 of 6: a service created by a CloudFormation stack is unknown to the ECS service lookups. Failing check id: autoscaling__ecs__elbv2.deploy-ecs-task-role-trust-policy-cfn.
  AWS: after a stack containing an AWS::ECS::Service reaches CREATE_COMPLETE, `ecs list-tasks --cluster <c> --service-name <s>` resolves the service and returns its task ARNs. Recorded behavior only.
  Emulator: `ListTasks` refuses with `ServiceNotFoundException` and message `Service not found.` — the stack-created service is not in ECS state.
  Why: anything that drives a stack-declared ECS service through the ECS API (waiters, task-role verification, scaling) is refused as not-found even though CloudFormation reported the resource created.
  Fix: the CloudFormation AWS::ECS::Service provisioner must register the service in ECS state (the same class of gap as the already-open 20261023T205437Z-cloudformation-reports-create-complete-for-resources-it-never.md and 20261102T101202Z-cloudformation-ecs-a-cloudformation-created-aws-ecs-capacityprovider.md, neither of which carries this check's replay key).

Cause 6 of 6: attaching an ECS task as an ALB target is performed without evaluating `elasticloadbalancing:RegisterTargets`, so a role without it succeeds. Failing check id: autoscaling__ecs__elbv2.ecs-service-create-without-elb-permission-fails-target-group-attachment.
  AWS: registering a target into a target group requires `elasticloadbalancing:RegisterTargets` on that target group; a principal without it is refused with an authorization error — HTTP 403, code `AccessDenied`/`AccessDeniedException`, AWS's standard sentence `User: <caller-arn> is not authorized to perform: elasticloadbalancing:RegisterTargets on resource: <target-group-arn> because no identity-based policy allows the elasticloadbalancing:RegisterTargets action` (fixed sentence; caller ARN and target-group ARN come from the request and the evaluated policy) — and no target is registered. Recorded behavior for the exact wording.
  Emulator: the call SUCCEEDS — `expected AccessDenied, but the call SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}` (the request id and date in that dict are per-run values).
  Why: the emulator reports a more permissive authorization model than AWS; least-privilege rollouts that rely on the registration being refused instead register the target.
  Fix: the authorization step in front of the ELBv2 RegisterTargets path used by ECS service creation. Related open issue that does NOT carry this replay key: 20261024T081305Z-ecs-is-overly-permissive-ten-validations-authorizations-aws.md.
