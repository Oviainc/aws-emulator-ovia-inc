# opensearchserverless: 3 net-new causes on the collection data plane — data-access-policy permissions are not enforced (a withdrawn aoss:WriteDocument keeps accepting writes), network policies are not enforced (narrowing SourceVPCEs or deleting the only network policy leaves the endpoint serving), and the data plane's 403 carries the AWS-JSON control-plane error body instead of an OpenSearch error document

> _Note: this issue was identified against the code base at commit `e9bfe98bd62d322ad396805fe7cc77738e607075`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateAccessPolicy

## Description
THREE net-new root causes on the OpenSearch Serverless collection DATA plane, grounded in four failing behavioral checks of the opensearchserverless service token.

Overlap note (not a duplicate): open issue 20261104T072704Z-opensearchserverless-the-published-collectionendpoint-serves-the-aws-json.md (and 'Cause 5 of 5' of 20261029T191222Z-opensearchserverless-5-net-new-causes-in-the-state.md) describe an EARLIER wall — the published collectionEndpoint routed to the AWS-JSON x-amz-target dispatcher, so every OpenSearch REST verb answered 400 SerializationException. That wall is gone in this replay: the data plane now SERVES OpenSearch REST, and the checks' positive controls pass (an aoss-signed `PUT /<index>/_doc/<id>` is accepted 200/201 and returns a real `{_index,_id,_version,result,_shards,_seq_no,_primary_term}` body, `GET /<index>/_doc/<id>` returns the stored `_source`, `POST /<index>/_search` and `GET /<index>/_mapping` answer 200). The suite marked NONE of these four checks OWNED by that issue. What fails now is the authorization layer BEHIND that front door, which is new behavior, so it is filed here; if that issue is reworked to add policy evaluation, these close with it.

Shared model context for all three causes: the aoss data plane is not Smithy-modeled. Smithy (com.amazonaws.opensearchserverless) documents CollectionDetail.collectionEndpoint as the 'Collection-specific endpoint used to submit index, search, and data upload requests to an OpenSearch Serverless collection', and models the control-plane writers that configure its authorization — UpdateAccessPolicy(type: AccessPolicyType, name, policyVersion, policy) and UpdateSecurityPolicy(type: SecurityPolicyType, name, policyVersion, policy), both of which REPLACE the policy document. The wire behavior of the endpoint itself is recorded behavior only, as noted per cause.

=== Cause 1 of 3: a data access policy's per-operation Permission list is not evaluated on the data plane, so withdrawing a permission has no effect ===
Failing check: opensearchserverless.data-access-policy-read-permission-without-write-blocks-indexing
AWS: recorded behavior only (the data plane is unmodeled); the rule is documented in 'Supported operations and plugins in Amazon OpenSearch Serverless' (serverless-genref.html), which maps aoss:WriteDocument -> PUT /<index>/_doc/<id>, aoss:ReadDocument -> GET /<index>/_doc/<id> and GET/POST /<index>/_search, aoss:DescribeIndex -> GET /<index>/_mapping. UpdateAccessPolicy REPLACES the policy document, so dropping a Permission entry really withdraws that permission. Recorded: after the index rule for `index/<collection>/*` is narrowed to `["aoss:ReadDocument"]` only, the SAME aoss-signed `PUT /<index>/_doc/<id>` that was accepted before is refused with HTTP 403 and an OpenSearch error document whose `error.type` is the fixed text `forbidden`, `GET /<index>/_mapping` is likewise refused 403 (aoss:DescribeIndex withdrawn in the same edit), while `GET /<index>/_doc/<id>` and `POST /<index>/_search` keep answering 200 because aoss:ReadDocument was never withdrawn; the refused write does not advance the document's `_version`. The 403 status and the fixed `forbidden` type are the requirement; the index name, document id, collection name and version number are request/state values that fill the template.
Emulator: the withdrawal is ignored. After UpdateAccessPolicy replaced the document with the read-only index rule, the check re-attempted the identical write every 3s for the full 105s budget and EVERY attempt was accepted: the last observation was `(200, {'_index': 'sim2real-perm', '_id': 'blocked', '_version': 35, 'result': 'updated', '_shards': {'total': 1, 'successful': 1, 'failed': 0}, '_seq_no': 35, '_primary_term': 1})` — i.e. ~35 real writes landed under a policy that grants no aoss:WriteDocument, and the document's `_version` kept advancing. No 403 was ever produced, so the subsequent `GET /<index>/_mapping` refusal and the EFFECT-ABSENT version assertion were never reached.
Why: a client that relies on a data access policy as its authorization boundary gets none. A principal granted read-only on an index can still index, update and overwrite documents, and an operator who narrows a policy to revoke write access sees UpdateAccessPolicy succeed while writes keep landing — a silent privilege escalation with no observable signal anywhere in the API.
Fix: the collection data-plane request handler's authorization step in the opensearchserverless service crate — it must resolve the signing principal, select the data access policies whose Principal matches and whose Rules' Resource matches the target `collection/<name>` and `index/<name>/<index>`, map the HTTP verb+path to the aoss permission it requires, and refuse with 403 plus an OpenSearch error body when that permission is absent, instead of serving every signed request unconditionally.

=== Cause 2 of 3: a collection's network policy is not evaluated on the data plane, so neither narrowing SourceVPCEs nor deleting the only network policy stops the endpoint from serving ===
Failing checks: opensearchserverless.server-side-network-policy-enforces-vpc-only-access, opensearchserverless.deleting-network-policy-stops-the-live-collection-endpoint-serving
AWS: recorded behavior only (the data plane is unmodeled); the control-plane writers are Smithy-modeled UpdateSecurityPolicy / DeleteSecurityPolicy with type=network. Recorded: with a network policy whose Rules target `collection/<name>`, `AllowFromPublic: false` and `SourceVPCEs: [<vpce-id>]`, a correctly aoss-signed, data-access-authorised request reaching the collection from the admitted VPC endpoint is served; once UpdateSecurityPolicy narrows SourceVPCEs to a DIFFERENT endpoint, the identical request from outside it is refused BY THE SERVICE with HTTP 401 or 403 (opensearch-py surfaces it as a TransportError whose status_code is 401/403), and restoring the original policy makes the identical request succeed again. Deleting the only network policy a live ACTIVE collection matches is accepted by the control plane and the endpoint then refuses even a fully authorised request with HTTP 401 and an EMPTY body — the request is refused before aoss builds the JSON 403 it returns for an authorization failure — while the collection stays ACTIVE and documents written earlier survive. The 401/403 statuses are the requirement; the vpce ids, collection and index names are request/state values.
Emulator: no network-policy decision is ever observable. Both checks are reported by the suite as 'Check timed out after 180.0s': each performs its positive control, then polls the identical data-plane probe on a bounded window waiting for the service to start refusing, and the refusal never comes, so the probe loop runs until the check budget is exhausted and no 401/403 is ever returned. Allowed and denied are indistinguishable at the endpoint.
Why: the network policy is advertised as a network boundary. A client (or a compliance control) that restricts a collection to a private VPC endpoint, or that deletes the network policy to take an endpoint out of service, believes the endpoint is unreachable from anywhere else while the emulator keeps serving every signed request from everywhere — and no response distinguishes the two configurations.
Fix: the same collection data-plane request handler — before authorization, it must resolve the network security policies matching the target collection and refuse a request that arrives from outside every admitted SourceVPCE (or that matches no network policy at all) with 401/403, instead of serving it. Note the refusal must be driven by the policy state the control plane holds, so that UpdateSecurityPolicy / DeleteSecurityPolicy on type=network changes what the endpoint serves.

=== Cause 3 of 3: a data-plane refusal is serialized with the AWS-JSON control-plane error shape instead of an OpenSearch error document ===
Failing check: opensearchserverless.collection-endpoint-requires-aoss-sigv4-service-name
AWS: recorded behavior only (the data plane is unmodeled). Recorded: the generic front-door 403 the collection endpoint returns for a request whose SigV4 credential scope names a service other than `aoss` (here `es`, with the SAME identity, the SAME data access grant and the SAME x-amz-content-sha256 discipline as an accepted aoss-signed write) is an OpenSearch JSON error document — `{"status": 403, "error": {"type": "forbidden", "reason": "403 Forbidden"}}` — carrying no explanatory message. `error.type` is fixed text and is the discriminator that tells the front-door rejection apart from OpenSearch's own permission layer, which always names itself `security_exception`. The status (403) and the `error.type` value are the requirement; nothing in the body derives from the request.
Emulator: the status is right but the body is the control plane's AWS-JSON error envelope: HTTP 403 with `{"__type": "AccessDenied", "message": "Sign the request with the emulator credentials"}`. There is no `error` object at all, so `error.type` is None; the error code `AccessDenied` is not an OpenSearch error type, and the message text `Sign the request with the emulator credentials` is emulator-specific prose that no AWS endpoint ever returns.
Why: every OpenSearch client parses data-plane failures out of the `error`/`error.type`/`error.reason` document, so a refusal arrives as an unparseable body: opensearch-py and friends cannot classify it, and client code that branches on `forbidden` (front door, retry with the right signing scope) versus `security_exception` (permission layer, fix the policy) takes the wrong branch or crashes on the missing key.
Fix: the collection data-plane error serializer in the opensearchserverless service crate — data-plane responses on the collectionEndpoint host must be serialized as OpenSearch error documents (`{"status": <code>, "error": {"type": ..., "reason": ...}}`), not with the AWS-JSON `__type`/`message` envelope used by the control-plane front door.
