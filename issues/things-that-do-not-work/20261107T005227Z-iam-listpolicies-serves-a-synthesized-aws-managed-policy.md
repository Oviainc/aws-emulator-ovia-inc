# iam ListPolicies serves a synthesized AWS-managed policy catalog: invented PolicyIds, pinned v1 default versions, one constant date, wrong IsAttachable and missing policies

> _Note: this issue was identified against the code base at commit `1b064f119d6a2bdadd353b8b6f400830e73a40d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPolicies

## Description
ListPolicies with Scope=AWS answers HTTP 200 with a Policies list whose members are SYNTHESIZED from the policy's own path and name rather than reproducing the real AWS-managed policy catalog. Every AWS-managed policy the emulator does serve carries a derived PolicyId, a default version pinned to v1, a single shared CreateDate/UpdateDate and (for service-linked-role policies) IsAttachable=false; on top of that the catalog is incomplete, so well-known managed policies are absent from the page entirely. The three causes below are the three ListPolicies pages the corpus replays (one per managed-policy path prefix); each must be closed before this issue is submitted.

Cause 1 of 3: the /aws-service-role/ page of Scope=AWS.
AWS: Smithy — ListPolicies output Policies targets policyListType of com.amazonaws.iam#Policy; Policy.PolicyId targets idType (@length min 16 max 128, @pattern ^[\w]+$) and is documented as "The stable and unique string identifying the policy"; Policy.DefaultVersionId targets policyVersionIdType (@pattern ^v[1-9][0-9]*(\.[A-Za-z0-9-]*)?$) and is "The identifier for the version of the policy that is set as the default version"; Policy.CreateDate and Policy.UpdateDate are dateType timestamps documented as when THAT policy was created and last updated; Policy.IsAttachable is booleanType with @default false. AWS's managed-policy catalog is a fixed, published set of resources: each entry has its own opaque account-independent unique id (an ANPA-prefixed 21-character identifier that is NOT a function of the policy name), its own current default version (frequently far past v1, because AWS revises managed policies), its own creation instant and its own last-update instant, and the recorded catalog reports IsAttachable true for these entries. Recorded behavior only for the per-policy id/version/date values themselves — they are the catalog's published contents, not a per-run value.
Emulator: for every /aws-service-role/ entry the replay reports PolicyId as a name-derived string of the form ANPA_<PATH-SEGMENT>_<POLICYNAME-UPPERCASED> instead of the catalog's opaque id, DefaultVersionId as 'v1' regardless of the policy's real default version, CreateDate and UpdateDate both as one single constant timestamp shared by every policy in the catalog, and IsAttachable as 'false' where the recording has 'true'.
Why: a client that keys managed policies by PolicyId (the documented stable identifier) resolves nothing against real AWS and cannot correlate an emulator id with the published catalog; a client that reads DefaultVersionId to fetch the current document (GetPolicyVersion) always asks for v1, which for a revised managed policy is not the effective document; a client that sorts, diffs or caches on CreateDate/UpdateDate sees every policy as created and updated at the same instant, so change detection and "newest policy" ordering are meaningless; and IsAttachable=false makes an attachable policy look un-attachable, so a caller skips an Attach*Policy call AWS would have accepted.
Fix: the iam crate's built-in AWS-managed policy catalog (the seed data that supplies each entry's id, default version, dates and attachability) and the ListPolicies handler's projection of those fields onto the Policy shape — the id must be a stored per-policy value, not computed from path+name, and the dates must be per-entry.
Traces: iam-catalog-list-policies#task#1.

Cause 2 of 3: the /job-function/ page of Scope=AWS carries the same synthesized metadata.
AWS: as Cause 1 — each job-function managed policy has its own opaque ANPA unique id, its own current default version, and its own create/update instants.
Emulator: PolicyId is again the name-derived ANPA_<PATH-SEGMENT>_<POLICYNAME> form, DefaultVersionId is 'v1' for every entry, and CreateDate/UpdateDate are the same single constant timestamp used across the whole catalog.
Why: same as Cause 1, on the job-function scope — these are the policies consoles and setup scripts attach by name and then version-pin, so a v1 default and a derived id break both the pin and the correlation.
Fix: same component as Cause 1; this page confirms the defect is in the shared catalog seed rather than in one path's handling.
Traces: iam-catalog-list-policies#task#2.

Cause 3 of 3: the /service-role/ page of Scope=AWS carries the same synthesized metadata AND omits catalog entries altogether.
AWS: ListPolicies with Scope=AWS enumerates the complete published managed-policy catalog for the requested path prefix; each entry appears with PolicyName, Arn, Path, PolicyId, DefaultVersionId, IsAttachable, CreateDate and UpdateDate. ListPolicies models only ServiceFailureException (HTTP 500, awsQueryError ServiceFailure), so there is no error path for "policy not in catalog" — a missing entry is simply invisible.
Emulator: besides the derived PolicyId, the 'v1' DefaultVersionId and the one constant CreateDate/UpdateDate, whole policies the recording returns are absent from the response (the replay reports them as `missing (expected {...}, got None)` — e.g. the EMR-for-EC2 and the Auto Scaling notification service-role policies), so the emulator's /service-role/ catalog is a strict subset of AWS's.
Why: a managed policy that does not appear in ListPolicies cannot be discovered, and any subsequent GetPolicy / AttachRolePolicy on its well-known ARN has no backing resource — so a scenario that bootstraps a service role from a published managed policy cannot run at all, and it fails as "policy does not exist" rather than as a fidelity gap.
Fix: the iam crate's built-in AWS-managed policy catalog must be completed for the /service-role/ prefix (and audited against the published catalog for the other prefixes), with per-entry ids, default versions and dates as in Cause 1.
Traces: iam-catalog-list-policies#task#4.
