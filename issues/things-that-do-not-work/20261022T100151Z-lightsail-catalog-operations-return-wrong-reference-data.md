# Lightsail catalog operations return wrong reference data

> _Note: this issue was identified against the code base at commit `196bb4609762a23c3b17bc928bd901fcc92dc085`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRegions

## Description
The emulator's static reference catalogs behind the Lightsail read-only catalog operations (GetRegions, GetBucketBundles, GetRelationalDatabaseBlueprints) are populated with made-up tables rather than AWS's. Every cause below is one cluster of that single fault: the catalog table that backs the operation does not carry AWS's member set, element ordering, naming or value content. There are 5 causes in this issue and all 5 must be closed.

Cause 1 of 5: GetRegions element ordering (fixture lightsail-catalog-and-operations-lifecycle, step task#6).
AWS: Smithy: GetRegions -> GetRegionsResult.regions : RegionList of Region{continentCode, description, displayName, name (RegionName enum), availabilityZones, relationalDatabaseAvailabilityZones}. The model does not constrain list order, so recorded behavior only: the recording shows AWS returning the US regions first, with regions[0] being name=us-east-1 / displayName=Virginia / continentCode=NA.
Emulator: returns regions[0] = name=ap-east-1 / displayName=Hong Kong / continentCode=AP, i.e. the catalog is emitted in plain name-sorted order.
Why: a client that reads the first element of regions as its default/home region (a common pattern for region pickers and for tests that pin regions[0]) silently gets an Asia-Pacific region where AWS gives a US one, so subsequent resource creation goes to the wrong region.
Fix: the GetRegions handler's region catalog ordering (the static region table and the order it is serialized in), in the lightsail service crate.
Traces: lightsail-catalog-and-operations-lifecycle#task#6 (status 200 -> 200, key $.regions[0]).

Cause 2 of 5: GetBucketBundles bundle names (fixture lightsail-catalog-get-bucket-bundles, step task#1).
AWS: Smithy: GetBucketBundles -> GetBucketBundlesResult.bundles : BucketBundleList of BucketBundle{bundleId, name, price, storagePerMonthInGb, transferPerMonthInGb, isActive}. Recorded behavior only for the values: AWS returns name='Object Storage 5GB' for bundleId small_1_0, 'Object Storage 100GB' for medium_1_0 and 'Object Storage 250GB' for large_1_0.
Emulator: returns the same bundleIds, prices, storage and transfer values but names them '5 GB', '100 GB' and '250 GB'.
Why: BucketBundle.name is the human-facing label clients display and the field some clients match on when selecting a bundle by name; a lookup by AWS's bundle name finds nothing against the emulator, so bucket creation flows that resolve a bundle by name fail even though the bundle exists.
Fix: the GetBucketBundles handler's bucket-bundle catalog table (the name field of each entry), in the lightsail service crate.
Traces: lightsail-catalog-get-bucket-bundles#task#1 (status 200 -> 200, 3 bundles missing / 3 extra).

Cause 3 of 5: GetRegions member set, region set and descriptions when the availability-zone include flags are not set (fixture lightsail-catalog-get-regions, step task#1).
AWS: Smithy: GetRegionsRequest{includeAvailabilityZones, includeRelationalDatabaseAvailabilityZones}; Region.availabilityZones and Region.relationalDatabaseAvailabilityZones are AvailabilityZoneList. Recorded behavior: AWS emits both list members on every Region as present-but-empty arrays when the corresponding include flag is not requested, emits a fixed region set, and emits a specific description per region.
Emulator: omits availabilityZones and relationalDatabaseAvailabilityZones entirely (expected [], got None) on every region; returns a different region set (e.g. an extra us-west-1 entry that AWS does not return); and returns different description/displayName text for many regions (e.g. us-east-1 'This region is recommended to serve users in the eastern United States' vs the emulator's '...eastern United States and eastern Canada', and a differing sa-east-1 displayName).
Why: an absent member is not an empty list to a typed SDK - callers that iterate region.availabilityZones get a null/None instead of an empty collection and either throw or branch wrongly, and a client enumerating supported regions sees a region (us-west-1) the real service rejects.
Fix: the GetRegions handler's response serializer (always emit both availability-zone lists, empty when not requested) and its static region catalog (region membership and per-region description/displayName), in the lightsail service crate.
Traces: lightsail-catalog-get-regions#task#1 (status 200 -> 200, ~60 diverging keys across the region list).

Cause 4 of 5: GetRelationalDatabaseBlueprints catalog content (fixture lightsail-catalog-get-relational-database-blueprints, step task#1).
AWS: Smithy: GetRelationalDatabaseBlueprints -> RelationalDatabaseBlueprintList of RelationalDatabaseBlueprint{blueprintId, engine (RelationalDatabaseEngine enum), engineVersion, engineDescription, engineVersionDescription, isEngineDefault}. Recorded behavior for the contents: AWS returns a mixed mysql/postgres catalog whose first entry is blueprintId=mysql_8_4 (engineVersion 8.4.11, isEngineDefault=true) followed by postgres_13..postgres_16 entries.
Emulator: returns a mysql-only catalog (mysql_5_6, mysql_5_7, mysql_8_0 with isEngineDefault=true, mysql_8_4 with engineVersion 8.4.4) and no postgres blueprint at all; the default-engine flag also lands on a different blueprint.
Why: a client provisioning a Lightsail managed database for PostgreSQL enumerates blueprints, finds no postgres blueprint, and cannot proceed at all; one that picks the isEngineDefault entry gets a different (older) engine than AWS would give it.
Fix: the GetRelationalDatabaseBlueprints handler's blueprint catalog table (entry set, versions and the isEngineDefault flag), in the lightsail service crate.
Traces: lightsail-catalog-get-relational-database-blueprints#task#1 (status 200 -> 200, blueprints[0..6]).

Cause 5 of 5: GetRegions availability-zone content when zones are requested (fixture lightsail-cloudformation-and-copy-error-paths, step task#1; also affects lightsail-instance-error-paths#task#7).
AWS: Smithy: as in cause 3. Recorded behavior: AWS returns a specific per-region availability-zone membership (e.g. us-west-2 carries four zones including us-west-2d) and does not return zones for every region, while still emitting relationalDatabaseAvailabilityZones as an empty array.
Emulator: synthesizes exactly three zones (<region>a/b/c, state=available) for every region - adding zones AWS does not report (us-east-1a/b/c, us-east-2a/b/c, eu-west-1...) and omitting ones it does (us-west-2d) - and again omits relationalDatabaseAvailabilityZones (expected [], got None). The same per-region description divergences as cause 3 appear here.
Why: availability-zone names are passed straight back to CreateInstances/CreateRelationalDatabase as availabilityZone; a client that round-trips a zone learned from the emulator uses a zone AWS does not have, and one that pins a real zone (us-west-2d) cannot find it.
Fix: the GetRegions handler's availability-zone catalog (per-region zone membership, not a generated a/b/c triple) and the same always-emit-empty-list serializer fix as cause 3, in the lightsail service crate.
Traces: lightsail-cloudformation-and-copy-error-paths#task#1 and lightsail-instance-error-paths#task#7 (status 200 -> 200, ~100 diverging keys).
