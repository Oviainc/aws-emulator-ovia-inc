# eks: 6 net-new root causes — cluster.endpoint is published on a real eks.amazonaws.com host, two CFN EKS resource types never reach CREATE_COMPLETE, the already-deleted-CA refusal is emulator-worded, and add-on / certificate-authority updates never converge

> _Note: this issue was identified against the code base at commit `d523205a25e89799b79f6d7553b80badf0bb176e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCluster

## Description
Six independent defects in the emulator's EKS surface, every one grounded in a failing behavioral check of this suite that the replay report marks neither ALREADY FILED nor OWNED.

Cause 1 of 6: Cluster.endpoint is published as a real-AWS Kubernetes API hostname the emulator does not serve, so the whole Kubernetes data plane behind an ACTIVE cluster is unreachable.
AWS: Smithy (com.amazonaws.eks#Cluster$endpoint): "The endpoint for your Kubernetes API server." On AWS the host named there is the address that serves that cluster's Kubernetes API path space (/version, /api/v1/..., /apis/apps/v1/...), and the recorded runs reach it with the CA bundle and a bearer token and get Kubernetes responses. Recorded behavior only for the address form: a client is expected to use whatever host the API hands it.
Emulator: CreateCluster/DescribeCluster project endpoint as https://<32-hex>.<3-hex>.<region>.eks.amazonaws.com — an AWS-owned address, not a host the emulator listens on. The harness refuses the announced address with "simparity.published.PublishedUrlRejected: endpoint_url was given https://<ID>.<xxx>.<region>.eks.amazonaws.com/<path> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener", and where a client dials it directly with "simparity.egress.EgressRefused: egress refused: '<ID>.<xxx>.<region>.eks.amazonaws.com' is not the endpoint under test (127.0.0.1); ... If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on". The host id, the region and the port differ per run and are not part of the requirement; the requirement is that the announced host be one the emulator serves.
Why: a client that does exactly what the API tells it (kubectl via a generated kubeconfig, an in-pod client, an add-on probe, CoreDNS/EBS-CSI/IRSA checks, an audit-log producer) is sent to an address the emulator never answers on — it either escapes to the internet or fails to connect. No Kubernetes-side behavior (access entries vs aws-auth, RBAC forbids, service ClusterIP, node labels/taints, projected-token OIDC/JWKS, add-on image pinning) can be observed even though the control plane reports ACTIVE.
Fix: the Cluster response projection for `endpoint` (the EKS cluster serializer/state that mints the host) must announce an address on a listener the emulator actually serves, and that listener must route the cluster's Kubernetes API path space. Open issues 20261109T160052Z-eks-3-net-new-root-causes-cluster-endpoint.md, 20261109T141609Z-ecr-eks-logs-a-cluster-s-published-api.md and 20261109T131727Z-eks-auth-the-pod-identity-data-plane-is.md describe the same shape of defect under other check sets/headings, but none of them carries the replay keys of the checks listed here.
Traces: eks.access-entry-takes-precedence-over-the-aws-auth-configmap, eks.deploy-cluster-active-and-api-reachable, eks.deploy-eks-cluster-cloudformation-active, eks.eks-coredns-resolves-a-service-to-the-clusterip-the-api-reports, eks.eks-delete-cluster-with-a-live-node-is-rejected, eks.eks-deployment-pod-is-reachable-through-a-cluster-service, eks.eks-ebs-csi-volume-data-survives-a-pod-reschedule, eks.eks-irsa-projected-token-assumed-inside-the-pod-and-sub-condition-denied, eks.eks-oidc-discovery-and-jwks-verify-a-projected-token-offline, eks.eks-pod-ip-is-a-secondary-address-on-a-real-vpc-eni, eks.eks-view-access-policy-write-is-forbidden-by-the-api-server, eks.namespace-scoped-access-policy-confines-reads-to-its-namespace, eks.nodegroup-taint-effect-is-translated-and-repels-an-untolerating-pod, eks.e2e-access-entry-kubectl-authorization-flow, eks.eks-access-entry-deletion-leaves-the-principal-unauthorized, eks.eks-pinned-addon-version-is-the-image-running-in-the-cluster.

Cause 2 of 6: a CloudFormation AWS::EKS::Nodegroup resource never reaches CREATE_COMPLETE, so the stack rolls back.
AWS: Smithy: CreateNodegroup returns Nodegroup with status CREATING and the nodegroup settles at ACTIVE; CloudFormation's AWS::EKS::Nodegroup reaches CREATE_COMPLETE once the nodegroup is ACTIVE. Recorded behavior: the stack reaches CREATE_COMPLETE and the nodegroup is then describable as ACTIVE.
Emulator: the nodegroup resource stays CREATE_IN_PROGRESS until CloudFormation's own create wait expires, which emits the event "Nodegroup=CREATE_FAILED: AWS::EKS::Nodegroup <nodegroup-name> was still CREATE_IN_PROGRESS when the wait for it to be created ran out" and the stack then goes ROLLBACK_IN_PROGRESS → ROLLBACK_COMPLETE with StackStatusReason "The following resource(s) failed to create: [Nodegroup]. ". Every other resource in the same template (VPC, subnets, IGW, route table, roles, Cluster) reaches CREATE_COMPLETE, so the stall is specific to the nodegroup's state machine, not to the stack.
Why: no template that declares a managed node group can be deployed against the emulator — the stack always rolls back, and a client cannot provision nodes, scale them or read any nodegroup attribute through infrastructure-as-code.
Fix: the EKS nodegroup state machine (the CreateNodegroup handler's state transition to ACTIVE) and/or the CloudFormation AWS::EKS::Nodegroup resource provider's stabilization check, so the resource becomes ACTIVE/CREATE_COMPLETE.
Traces: eks.deploy-cfn-nodegroup-joins-cluster.

Cause 3 of 6: a CloudFormation AWS::EKS::PodIdentityAssociation resource fails to create, so the stack rolls back.
AWS: Smithy: CreatePodIdentityAssociation (POST /clusters/{clusterName}/pod-identity-associations, required clusterName/namespace/serviceAccount/roleArn) returns the association synchronously with its associationId; AWS::EKS::PodIdentityAssociation therefore reaches CREATE_COMPLETE and exposes AssociationId via Fn::GetAtt. Recorded behavior: the stack reaches CREATE_COMPLETE and DescribePodIdentityAssociation then returns the bound role.
Emulator: the stack ends ROLLBACK_COMPLETE with StackStatusReason "The following resource(s) failed to create: [PodIdentityAssociation]." The sibling resources in the same template (VPC, two subnets, the cluster role, the pod role trusting pods.eks.amazonaws.com, AWS::EKS::Cluster) all create, so the failure is in the PodIdentityAssociation resource itself.
Why: pod identity cannot be declared in a template at all; a client gets a rolled-back stack instead of a usable association and the AssociationId output it would wire into its workload.
Fix: the CloudFormation AWS::EKS::PodIdentityAssociation resource provider (its create path and its GetAtt/AssociationId projection) and the CreatePodIdentityAssociation handler it calls.
Traces: eks.deploy-cfn-podidentity-association-usable.

Cause 4 of 6: DeleteCertificateAuthority on an already-deleted certificate authority answers the right code with an emulator-authored message.
AWS: Smithy: DeleteCertificateAuthority models ResourceNotFoundException with httpError 404. Recorded behavior: a second DeleteCertificateAuthority on an id whose delete already completed is refused ResourceNotFoundException with the message "Certificate authority <certificateAuthorityId> not found for cluster <clusterName>" — the fixed text is "Certificate authority ", " not found for cluster " and no trailing period; the two variable parts are the certificateAuthorityId and the clusterName taken straight from the request.
Emulator: same code, but the message is "No certificate authority found with id: <certificateAuthorityId> for cluster: <clusterName>." (observed with a per-run CA uuid and cluster name filling those slots) — different fixed text, different slot order and an extra trailing period.
Why: a client that matches on AWS's refusal sentence (error-mapping tables, log assertions, idempotent-delete runbooks) does not recognise the refusal and treats a benign already-deleted id as an unknown failure.
Fix: the DeleteCertificateAuthority handler's not-found path must emit AWS's sentence template rather than composing its own.
Traces: eks.certificate-authority-lifecycle-transitions.

Cause 5 of 6: the add-on lifecycle never converges, so the check makes no progress and is killed at the harness cap.
AWS: Smithy: CreateAddon returns Addon (status CREATING) and the add-on settles at ACTIVE; UpdateAddon returns an Update that reaches status Successful; after DeleteAddon, DescribeAddon is refused ResourceNotFoundException (404) and ListAddons omits it. Recorded behavior: each of those transitions is observed within the check's budget.
Emulator: the check reaches no verdict at all — "Error: Check timed out after 60.0s" — i.e. one of the awaited add-on transitions (the cluster/add-on reaching ACTIVE, or the UpdateAddon update reaching a terminal status) never happens, so the poll spins until the harness cap. Other EKS checks in this same run do create clusters and observe ACTIVE, so the stall is in the add-on state machine rather than in cluster provisioning.
Why: a client that waits for an add-on to become ACTIVE, for an add-on update to finish, or for a deleted add-on to disappear hangs forever; no add-on lifecycle can be automated against the emulator.
Fix: the add-on state machine behind CreateAddon/UpdateAddon/DeleteAddon (its status progression and the Update record it publishes) must advance to its terminal states.
Traces: eks.addon-full-lifecycle.

Cause 6 of 6: the Update returned by CreateCertificateAuthority never reaches a terminal status, so a check that waits on it burns its whole budget.
AWS: Smithy: CreateCertificateAuthority returns update: Update alongside the new CertificateAuthoritySummary (signingStatus NOT_USED); that update is tracked with DescribeUpdate and ends Successful (or Failed), after which the cluster's update slot is free and the not-yet-activated successor CA can be deleted.
Emulator: DescribeUpdate on the CreateCertificateAuthority update never reports Successful/Failed; the dependent wait consumes the entire remaining run budget and the check then fails with "AssertionError: condition not met within 0.0s; last observed=None" (the deadline had already been reduced to zero by the preceding non-converging wait). The earlier asserts in the same check — the ResourceInUseException refusal of the IN_USE signer and the CA remaining IN_USE — passed, so the defect is specifically the asynchronous update never settling.
Why: every certificate-authority rotation flow (append successor → wait → activate → delete the retired CA) blocks indefinitely; a client polling DescribeUpdate as AWS documents never gets a terminal answer.
Fix: the certificate-authority update state machine (the Update record CreateCertificateAuthority/ActivateCertificateAuthority/DeleteCertificateAuthority publish, and the CA's own signingStatus/distributionStatus progression) must reach terminal states. Open issue 20261106T022127Z-eks-a-successor-certificate-authority-never-finishes-distribution.md describes the same family of stall for a different check set but does not carry this check's replay key.
Traces: eks.delete-certificate-authority-in-use-blocked.
