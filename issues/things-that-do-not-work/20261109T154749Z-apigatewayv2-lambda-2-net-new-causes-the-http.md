# apigatewayv2__lambda: 2 net-new causes — the HTTP API's published ApiEndpoint is an AWS execute-api host the emulator does not serve, and upgraded WebSocket frames answer 'Internal server error' instead of the route's Lambda reply

> _Note: this issue was identified against the code base at commit `39b863d101414613449d16e44f0b23fd775a8d87`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApi

## Description
Two net-new root causes behind the surviving apigatewayv2+lambda checks. Both must be closed.

Cause 1 of 2: the HTTP API's published ApiEndpoint is an AWS public execute-api hostname the emulator does not serve, so no Lambda-backed route is ever invoked over HTTP (8 checks).
AWS: Smithy (service-com-amazonaws-apigatewayv2-apigatewayv2): CreateApi/GetApi output member ApiEndpoint (jsonName apiEndpoint), documented as "The URI of the API, of the form {api-id}.execute-api.{region}.amazonaws.com" — the address the API is served on, so GET/POST <ApiEndpoint>/<path> reaches the route's AWS_PROXY or HTTP_PROXY integration. The invoke-time contracts the checks grade (a Lambda authorizer raising Unauthorized -> 401, an ESM handler's statusCode/headers/body/isBase64Encoded shaping, HTTP_PROXY overwriting Via and X-Forwarded-For, a status-keyed response mapping rewriting 500 to 403, a 50 ms integration timeout -> 503, a raising handler -> 500, a missing lambda:InvokeFunction grant -> 500, a malformed proxy response -> 500 rather than 502) all depend on that address being reachable.
Emulator: the published value is "https://<api-id>.execute-api.<region>.amazonaws.com", a host the emulator does not listen on; replay refuses it with simparity.published.PublishedUrlRejected ("its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener"), so no request is made.
Why: the only documented way a client finds an HTTP API sends it off the emulator; every Lambda-integration behaviour of the API is unreachable even though the control plane answers correctly.
Fix: the ApiEndpoint construction in the apigatewayv2 crate's CreateApi/GetApi/ImportApi handlers plus the execute-api front-door listener that must serve the published address.

Cause 2 of 2: on an upgraded WebSocket connection, every inbound frame is answered with the gateway's own error frame instead of the selected route's Lambda reply (5 checks).
AWS: recorded behavior only. A frame dispatched by RouteSelectionExpression to a route with a healthy Lambda (AWS_PROXY, or AWS with a request template) is answered with the function's own payload — the echo of the sent body, the 'received' acknowledgement, or the model-validated body — and an unmatched action without $default produces API Gateway's specific no-route refusal, not a generic integration failure. "Internal server error" is reserved for a real integration fault.
Emulator: the client receives {"connectionId":"<id>","message":"Internal server error","requestId":"<id>"} on the control legs of all five checks, so $default fallback, route-model validation, request-template dispatch, never-passthrough refusal and the unmatched-action error frame are all ungradeable. Fixed text "Internal server error"; connectionId/requestId are per-run values.
Why: a WebSocket client sees a backend failure for a request AWS answers successfully, so route selection, request templates and model validation cannot be relied on at all.
Fix: the WEBSOCKET route-dispatch path of the apigatewayv2 data-plane handler — route-selection-expression evaluation, request-template/model-validation application and the Lambda integration invocation — which must return the integration's reply and only frame genuine failures.
