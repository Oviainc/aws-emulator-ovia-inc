# cloudtrail__stepfunctions: CloudTrail event history indexes no states.amazonaws.com management events, so StartExecution and a rejected/successful DescribeStateMachine from an assumed-role session are never auditable via LookupEvents

> _Note: this issue was identified against the code base at commit `f42419e01630977583bc09726b6f41b0d8951344`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
ONE net-new root cause in this issue (Cause 1 of 1).

Cause 1 of 1 — Step Functions management calls (StartExecution, DescribeStateMachine, including the rejected one) are never recorded in the Region's CloudTrail event history, so LookupEvents returns no record for them and the audit of a Step Functions session is impossible.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) models LookupEvents with LookupAttributes/StartTime/EndTime/EventCategory/MaxResults (range 1-50) and an Events list of envelopes carrying CloudTrailEvent, and its own documentation lists the supported lookup attributes (Event ID, Event name, Event source, Read only, Resource name, Resource type, User name, access key). Every management call of every service — reads as well as writes, successful as well as refused — is recorded in the Region's event history and readable through LookupEvents; the per-record field semantics are recorded behavior only (measured by this check against real AWS): eventSource "states.amazonaws.com", eventCategory "Management", awsRegion and recipientAccountId of the call, userIdentity.type "AssumedRole" with userIdentity.arn equal to the caller's assumed-role session ARN and sessionContext.sessionIssuer.arn equal to the role ARN (envelope Username equal to the role session name), requestID equal to the ResponseMetadata.RequestId the SDK saw on that very call, envelope EventId equal to the record's eventID, readOnly false for StartExecution and true for DescribeStateMachine (true even when the DescribeStateMachine was refused, with envelope ReadOnly "true"), requestParameters carrying the arguments actually sent (stateMachineArn and name for StartExecution; exactly {"stateMachineArn": <arn>} for DescribeStateMachine), responseElements.executionArn equal to the ARN StartExecution returned, no errorCode/errorMessage member on a successful call, and on the rejected DescribeStateMachine errorCode "StateMachineDoesNotExist" (the Step Functions model declares StateMachineDoesNotExist as a client error of DescribeStateMachine and StartExecution) with errorMessage identical to the message the caller received — fixed text "State Machine Does Not Exist: '" + the ARN from the request + "'" — and responseElements absent.

Emulator: event history holds none of these calls. The check assumes a role, calls StartExecution (the execution runs to SUCCEEDED and echoes its input), gets StateMachineDoesNotExist from DescribeStateMachine on a never-created ARN, then DescribeStateMachine on the real machine, and polls LookupEvents by EventName 'StartExecution' and 'DescribeStateMachine' over a window covering them, filtering on userIdentity.arn == the session ARN. No record attributed to that session is ever returned, so the poll never completes and the check is still polling when the harness cap ends it: verdict 'mismatch', detail 'Check timed out after 180.0s'. Diagnosis: the lookup poll is the only wait that can run to the cap — its budget is _LOOKUP_BUDGET_S = 900.0 with a 2 s interval, while every earlier wait is bounded at 90-120 s and raises an AssertionError (a different, non-timeout detail) rather than hanging.

Why: the emulator cannot answer "who ran this state machine". Every detective control a client builds on event history — incident reconstruction, compliance evidence that a specific role session started an execution, reconciliation of refused calls, correlating a record back to the SDK's request id — reads an empty history and silently passes, so a client cannot distinguish "nothing happened" from "nothing was recorded".

Fix: the shared management-event recording seam CloudTrail's LookupEvents already reads (service_common::management_events via the CloudTrail service's state) must be driven from Step Functions' served operations — for read-only and refused calls as well as writes — populating eventSource/eventName/eventCategory/readOnly/requestParameters/responseElements/requestID/eventID, the caller's assumed-role userIdentity with its sessionContext.sessionIssuer, and errorCode/errorMessage taken from the refusal the caller received.

## Evidence
cloudtrail__stepfunctions.obs-sfn-2-lookup-events-audits-start-execution-and-a-rejected-describe-state-machine — verdict 'mismatch', detail 'Check timed out after 180.0s'.

The check reaches its LookupEvents poll only after its subject calls have already returned: CreateRole (execution role and caller role) + PutRolePolicy, CreateStateMachine, a warm-up session whose probes must answer StateMachineDoesNotExist / ExecutionDoesNotExist, AssumeRole (asserting AssumedRoleUser.Arn == arn:aws:sts::<account>:assumed-role/<role>/<session>), StartExecution, DescribeExecution until terminal (asserting status SUCCEEDED and output == the input), the refused DescribeStateMachine on a missing ARN (asserting code 'StateMachineDoesNotExist' and message "State Machine Does Not Exist: '<missing-arn>'"), and the control DescribeStateMachine on the real machine. All of those assertions passed. The poll loop then calls ct.lookup_events(MaxResults=50, StartTime=<now-3min>, EndTime=<now+5min>, LookupAttributes=[{AttributeKey:'EventName', AttributeValue:'StartExecution'|'DescribeStateMachine'}]) paging to exhaustion, keeping only records whose userIdentity.arn equals the session ARN, and exits only when all three of 'start', 'missing' and 'control' are found. Its budget is _LOOKUP_BUDGET_S = 900.0 with _POLL_INTERVAL_S = 2.0 and a stall detector at _STALL_WAIT_S = 420.0, i.e. far beyond the 180 s harness cap, and it counts the records seen for the session (seen_ids) — none accumulate. Every earlier wait is bounded at 90 s (_IAM_RETRY_DEADLINE_S) or 120 s (_wait_terminal) and raises an AssertionError instead of hanging, so the plain timeout detail places the block in the lookup poll.

The record fields the check would grade, and which are therefore unverifiable, are: eventSource 'states.amazonaws.com' (record and envelope EventSource), eventCategory 'Management', awsRegion == the call's Region, recipientAccountId == the account, userIdentity.type 'AssumedRole' with arn == the session ARN and sessionContext.sessionIssuer.arn == the caller role ARN, envelope Username == the session name, envelope EventId == record eventID, requestID == the SDK's ResponseMetadata.RequestId per call, readOnly False for StartExecution / True for both DescribeStateMachine records (envelope ReadOnly 'true'), requestParameters {stateMachineArn, name} for StartExecution and exactly {'stateMachineArn': <missing-arn>} for the rejection, responseElements.executionArn == the returned execution ARN on StartExecution and None on the rejection, no errorCode/errorMessage on the two successes, and errorCode 'StateMachineDoesNotExist' with errorMessage "State Machine Does Not Exist: '<missing-arn>'" (fixed text plus the ARN from the request) on the rejection.

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. CreateRole a states.amazonaws.com-assumable execution role and CreateStateMachine a STANDARD machine with a single Pass state.
3. CreateRole a caller role the account can assume, PutRolePolicy allowing states:StartExecution/DescribeStateMachine/DescribeExecution, then AssumeRole with a known RoleSessionName.
4. With the session's credentials: StartExecution(stateMachineArn=<sm>, name=<exec>, input={"probe":<exec>}) and wait for SUCCEEDED; DescribeStateMachine on an ARN in the same namespace that was never created (expect StateMachineDoesNotExist, message "State Machine Does Not Exist: '<arn>'"); DescribeStateMachine on the real machine. Record each call's ResponseMetadata.RequestId.
5. Call cloudtrail LookupEvents over a window covering those calls with LookupAttributes [{AttributeKey:'EventName', AttributeValue:'StartExecution'}] and [{AttributeKey:'EventName', AttributeValue:'DescribeStateMachine'}], paging NextToken. Expect three records attributed to the session ARN with eventSource 'states.amazonaws.com', eventCategory 'Management', the per-call requestID, readOnly per operation, the request parameters sent, responseElements.executionArn on the start, and errorCode 'StateMachineDoesNotExist' / errorMessage equal to the SDK's message on the rejected read. Observe that LookupEvents returns no record for any of them, so the poll runs until the harness cap.
