# ELB Classic: the published DNSName is a real-AWS *.elb.amazonaws.com host the emulator does not serve, so no Classic load balancer data plane is ever reachable (1 cause)

> _Note: this issue was identified against the code base at commit `6bab9504f4457a639e729a9dc2b08c46f536304f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLoadBalancer

## Description
1 cause.

Cause 1 of 1: the `DNSName` that CreateLoadBalancer answers — and that DescribeLoadBalancers reports in `LoadBalancerDescription$DNSName` / `$CanonicalHostedZoneName` — is a synthesized real-AWS Elastic Load Balancing hostname of the form `<LoadBalancerName>-<10 digits>.<region>.elb.amazonaws.com` (prefixed `internal-` for the `internal` scheme). That host is not an address this emulator serves or resolves: it is neither the emulator's own host/port nor a per-resource listener it published. Every client that does the one thing a load balancer exists for — open an HTTP connection to the name the API handed back — is pointed off the emulator entirely, so the Classic ELB data plane cannot be exercised at all. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic.

AWS: Smithy: CreateLoadBalancer output `CreateAccessPointOutput$DNSName` (target `DNSName`) — "The DNS name of the load balancer"; `LoadBalancerDescription$DNSName` and `$CanonicalHostedZoneName` — "The DNS name of the load balancer"; `LoadBalancerDescription$Scheme` — "If Scheme is internet-facing, the load balancer has a public DNS name that resolves to a public IP address. If Scheme is internal, the load balancer has a public DNS name that resolves to a private IP address." The model states the member's MEANING, not its text: the requirement is that the returned name is the address on which the load balancer's configured listeners actually accept connections and forward to registered, InService instances. The textual form `<name>-<id>.<region>.elb.amazonaws.com` is a real-AWS artifact, not a modeled constraint; what is modeled/required is that the value is resolvable and reachable by the caller. Recorded behavior: a GET to the value returned by CreateLoadBalancer, against an HTTP:80 listener with a registered healthy backend, returns the backend's HTTP 200 body; against a load balancer whose only registered instance is OutOfService, the load balancer itself answers (HTTP 503 from the load balancer, not the backend).

Emulator: services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/state.rs `dns_name()` formats `"{name}-{suffix}.{region}.elb.amazonaws.com"` (or `internal-...`) from a SHA-256-derived 10-digit `dns_suffix()`, and CreateLoadBalancer stores and returns it verbatim. The emulator stands up no listener for that host and publishes no mapping from it to its own host/port, so the harness refuses the published value outright: `simparity.published.PublishedUrlRejected: endpoint_url was given http://<name>-<digits>.<region>.elb.amazonaws.com/ (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener` (elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic), and `AssertionError: the emulator published http://<name>-<digits>.<region>.elb.amazonaws.com: its host is not one of the emulator's own hosts; ...` (elb.registered-instance-serves-real-http-through-elb-dns-name). The control-plane call itself is HTTP 200, so the divergence is the VALUE of DNSName, not the wire shape. Note these three checks previously stalled on the DescribeInstanceHealth InService wait filed as 20261107T072636Z-elb-classic-a-registered-backend-that-passes-its.md; they now get past that wait and fail on the published name instead, which is the distinct, downstream cause reported here.

Why: a client relying on AWS's behavior takes the returned DNSName and connects to it — that is the whole contract of a load balancer. Against this emulator the name resolves to real AWS DNS space (or to nothing), so the request leaves the emulator, is refused, or hits an unrelated host. Nothing a caller does — register instances, add listeners, configure stickiness or cross-zone balancing, point a Route 53 alias at CanonicalHostedZoneName/CanonicalHostedZoneNameID — can ever be observed, because there is no address at which the emulated load balancer listens. Load-balancer-generated responses (the 503 for a fleet with no InService instance) are likewise unobservable.

Fix: the DNS-name minting in the ELB Classic crate's state (`dns_name`/`dns_suffix` in src/state.rs) together with the data-plane listener the load-balancer record should own: CreateLoadBalancer must publish a name/address the emulator actually serves (one of its own hosts, or a per-resource listener host:port it stands up for the load balancer's listeners), and DescribeLoadBalancers must report that same reachable value for DNSName and CanonicalHostedZoneName; the listener for each configured `Listener$LoadBalancerPort` must accept connections there and forward to registered instances per their DescribeInstanceHealth state.

Related (not covering this): open issues 20261109T132410Z-acm-elbv2-the-alb-s-published-dnsname-is.md and 20261109T124858Z-cognito-idp-elbv2-an-alb-s-published-dnsname.md describe the same shape of defect in the ELBv2 crate (ALB/NLB), a different service and different code path; 20261107T072636Z-elb-classic-a-registered-backend-that-passes-its.md covers the DescribeInstanceHealth InService verdict, not the published address.

Traces: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.out-of-service-instance-blocked-from-receiving-traffic.

## Evidence
Cause 1 — CreateLoadBalancer / DescribeLoadBalancers DNSName.

Expected (AWS): CreateLoadBalancer answers HTTP 200 with a DNSName that is REACHABLE by the caller; an unsigned HTTP GET to `http://<DNSName>/<path>` on a configured HTTP:80 listener is served — by a registered InService backend (the backend's body, HTTP 200) when one exists, and by the load balancer itself (HTTP 503) when no registered instance is InService. DescribeLoadBalancers reports that same reachable value in DNSName and CanonicalHostedZoneName. The name's real-AWS spelling is not the requirement; its reachability is.

Actual (emulator): DNSName is a synthesized real-AWS host the emulator does not serve, so the GET never leaves for a listener the emulator owns. Replay output, verbatim except for the per-run name/port (which are environment values, not part of the requirement):

Model evidence: `CreateAccessPointOutput$DNSName` and `LoadBalancerDescription$DNSName`/`$CanonicalHostedZoneName` are both documented "The DNS name of the load balancer"; `LoadBalancerDescription$Scheme` documents that an internet-facing load balancer "has a public DNS name that resolves to a public IP address" and an internal one a name that "resolves to a private IP address" — i.e. the member is an address that resolves, not a label.
