# apigatewayv2: WEBSOCKET stage never completes the RFC 6455 upgrade, so route dispatch, @connections push and post-close GoneException are all unreachable

> _Note: this issue was identified against the code base at commit `448dbaa5987c679f4ac9bf289637b03678756bff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke (execute-api WebSocket data plane), PostToConnection, GetConnection, DeleteConnection

## Description
One net-new root cause in the apigatewayv2 emulator, grounded in a failing behavioral check of this suite whose replay key is carried by no open issue. A fixer must close this ONE cause before submitting.

=== Cause 1 of 1: a deployed WEBSOCKET API's stage URL never completes the WebSocket upgrade, so nothing downstream of the handshake can happen ===
AWS: recorded behavior only for the handshake and frame dispatch (the execute-api data plane is not modeled in Smithy). After CreateApi(ProtocolType=WEBSOCKET, RouteSelectionExpression="$request.body.action") + CreateIntegration(MOCK) + CreateIntegrationResponse + CreateRoute + CreateRouteResponse + CreateStage + CreateDeployment (deployment reaching DEPLOYED), an RFC 6455 upgrade to that stage's wss:// URL is answered HTTP 101 Switching Protocols. A text frame whose body selects the 'whoami' route is answered on the SAME socket by the MOCK integration's response template (so the client learns $context.connectionId and $context.routeKey); a body whose action matches no route, with no $default route present, is answered on the same socket with a frame carrying message 'Forbidden' addressed to the same connectionId. The @connections side IS modeled: Smithy apigatewaymanagementapi GetConnection GET /@connections/{ConnectionId} -> 200 with connectedAt; PostToConnection POST /@connections/{ConnectionId}, Data @length max 131072 -> 200, delivering exactly the posted bytes to the live socket; DeleteConnection DELETE /@connections/{ConnectionId} -> 204. All three model GoneException with httpError 410, which is what each must answer for a connection the CLIENT closed (client sends opcode 0x8, server echoes a close frame). Also recorded: after DeleteApi, GetApi answers NotFoundException 404, GetApis no longer lists the id, and CreateRoute on the dead id is refused NotFoundException 404.
Emulator: no WebSocket listener ever accepts a connection on the stage URL the emulator itself announced. The check polls the upgrade for up to 120 s (3 s interval) and never observes status 101, so it is killed at the suite's 60 s cap: 'Error: Check timed out after 60.0s'. The check carries an explicit DATAPLANE_UNIMPLEMENTED marker for exactly this outcome. Because the handshake never completes, no connectionId is ever minted, so the entire remainder of the lifecycle — route selection by $request.body.action, the MOCK integration/route response on the socket, the 'Forbidden' frame for an unmatched action, GetConnection's ConnectedAt, PostToConnection's byte-exact delivery, the server's close echo, and the GoneException 410 that all three @connections operations must answer afterwards — is unobservable.
Why: a client building a WebSocket API gets a control plane that bookkeeps an API, a route, an integration and a DEPLOYED deployment, and an ApiEndpoint that looks like a wss:// URL, but no socket can ever be opened against it. Every realtime application pattern (connect, action routing, server push via @connections, and the 410-on-gone contract that tells a backend to evict a dead connection) silently cannot be exercised, so tests that pass here fail on AWS.
Fix: the execute-api WebSocket listener for a WEBSOCKET stage — the upgrade handler and the router entry that maps the announced host/path for (api id, stage) to it — plus the per-connection store it must feed so the apigatewaymanagementapi handlers can answer GetConnection/PostToConnection/DeleteConnection for a live id and GoneException 410 for a closed one. Related open issue 20261024T120951Z-apigatewayv2-the-execute-api-data-plane-never-serves.md describes the same WebSocket surface (its Cause 2 observed the upgrade answered HTTP/1.1 404 Not Found with x-amzn-errortype: UnknownService) but does NOT carry this check's replay key, and open issue 20261023T124140Z-apigatewayv2-websocket-duplex-data-plane-is-not-served.md does not either; this cause adds the @connections-after-client-close leg of the contract.
Traces: apigatewayv2.websocket-post-to-connection-delivers-then-gone-after-disconnect.

## Evidence
Check apigatewayv2.websocket-post-to-connection-delivers-then-gone-after-disconnect, verdict mismatch.
Expected: the poll `_poll_until(_connect, lambda r: r["status"] == 101, timeout_s=120.0, interval_s=3.0, description=f"a 101 WebSocket upgrade at {url}")` observes HTTP 101 on ctx.api_url(api_id, 's', websocket=True); then opcode-1 reply with routeKey 'whoami' and a non-empty connectionId; then a frame with message 'Forbidden' for action 'no-such-route'; then GetConnection 200 with ConnectedAt; then PostToConnection(Data=b'sim2real-server-push') delivering (opcode 1, b'sim2real-server-push'); then after the client's opcode-0x8 close, PostToConnection / GetConnection / DeleteConnection each GoneException with HTTPStatusCode 410.
Actual: no upgrade is ever accepted at the announced stage URL, so the check never gets past the handshake poll and is killed by the runner: `Error: Check timed out after 60.0s`. The check's own guard for this state is `AssertionError("DATAPLANE_UNIMPLEMENTED: no WebSocket listener accepted a connection at {url} within 120s, so the route and @connections data plane could not be reached")`.
Model citations used: apigatewaymanagementapi PostToConnection POST /@connections/{ConnectionId} code 200, Data @length 0..131072, errors ForbiddenException 403 / GoneException 410 / LimitExceededException 429 / PayloadTooLargeException 413; GetConnection GET code 200 (connectedAt, lastActiveAt, identity), errors ... GoneException 410; DeleteConnection DELETE code 204, errors ... GoneException 410. The handshake, route selection and close echo are recorded behavior only.

## Steps to Reproduce
1. Boot the emulator from this checkout and point an SDK/CLI at it.
2. apigatewayv2 CreateApi(Name=..., ProtocolType='WEBSOCKET', RouteSelectionExpression='$request.body.action'); note the returned ApiEndpoint is ws(s)://.
3. CreateIntegration(ApiId, IntegrationType='MOCK', RequestTemplates={'$default': '{"statusCode": 200}'}, TemplateSelectionExpression='\\$default'); CreateIntegrationResponse(IntegrationResponseKey='$default', ResponseTemplates={'$default': '{"connectionId": "$context.connectionId", "routeKey": "$context.routeKey"}'}).
4. CreateRoute(RouteKey='whoami', Target='integrations/<id>', RouteResponseSelectionExpression='$default'); CreateRouteResponse(RouteResponseKey='$default'); CreateStage(StageName='s'); CreateDeployment(StageName='s') and wait for DeploymentStatus=DEPLOYED.
5. Open an RFC 6455 upgrade (GET with Connection: Upgrade / Upgrade: websocket / Sec-WebSocket-Key / Sec-WebSocket-Version: 13) against the emulator's announced WebSocket URL for (that api id, stage 's'). No 101 is ever returned — nothing accepts the connection.
6. Consequently none of the following can be reached: sending {"action":"whoami"} and receiving the MOCK route reply with connectionId/routeKey; sending {"action":"no-such-route"} and receiving message 'Forbidden'; apigatewaymanagementapi GetConnection/PostToConnection against that connectionId on the stage endpoint; and, after the client sends a close frame (opcode 0x8, status 1000), PostToConnection / GetConnection / DeleteConnection answering GoneException with HTTP 410.
7. Replay apigatewayv2.websocket-post-to-connection-delivers-then-gone-after-disconnect to confirm the fix.
