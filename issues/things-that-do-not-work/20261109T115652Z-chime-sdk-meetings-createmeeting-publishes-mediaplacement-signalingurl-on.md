# chime-sdk-meetings: CreateMeeting publishes MediaPlacement.SignalingUrl on a real AWS host (signal.m3.<region>.app.chime.aws) instead of an address the emulator serves

> _Note: this issue was identified against the code base at commit `86c25e3173c48b1c4d4a9173324e183693bfe876`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue carries 1 CAUSE, in the chime-sdk-meetings emulator (crate services/service-com-amazonaws-chimesdkmeetings-chimemeetingssdkservice).

Relation to already-open chime-sdk-meetings issues: the suite did NOT mark this check as OWNED by any of them, and none covers this cause. 20261102T093423Z-chime-sdk-meetings-the-signalingurl-createmeeting-advertises-in.md is the closest: it is about the published signaling endpoint not being SERVED (its recorded key is a ConnectionRefusedError raised inside _tls_websocket_probe, and its Evidence states explicitly that "the published URL passes that gate", i.e. ctx.published_url_mismatch reported no mismatch at the time it was filed). That is no longer where the check fails: the replay now never reaches the probe at all, because the published-URL gate itself rejects the value — the URL's HOST is a third-party AWS production hostname rather than one of the emulator's own hosts. Addressing "nothing listens behind the advertised address" without changing which address is advertised leaves this failure standing, and vice versa, so this is a distinct cause from that issue and must be closed on its own. The other open chime-sdk-meetings issues (20261029T175426Z-...-6-net-new-root-causes.md, the UpdateAttendeeCapabilities and StartMeetingTranscription message issues, and the BatchCreateAttendee stub issue) concern unrelated operations and members.

Cause 1 of 1: Meeting.MediaPlacement.SignalingUrl is built from a hard-coded real-AWS host template, so the emulator announces an address other than the one it is reached on.
AWS: Smithy models MediaPlacement as "A set of endpoints used by clients to connect to the media service group for an Amazon Chime SDK meeting", and MediaPlacement$SignalingUrl as String @length(0..4096) documented only as "The signaling URL". The model states no host format, so this is recorded behavior only: CreateMeeting answers 200 and the SignalingUrl it returns names an endpoint of the service the client is actually talking to — the host:port that serves the meeting's signaling control path, reachable from the caller, which terminates TLS and answers an unauthenticated WebSocket upgrade on that path with an HTTP/1.1 4xx status line. The invariant a client depends on is the RELATION, not any literal host: the advertised signaling address belongs to the deployment that minted the meeting. For an emulator that deployment is the emulator itself, so the published URL must be ws(s)://<a host the emulator serves>:<the port it is reached on>/<the meeting's control path> (equivalently a per-resource listener on one of its own hosts).
Emulator: CreateMeeting answers 200 with signaling_url formatted from a fixed production template, "wss://signal.m3.{media_region}.app.chime.aws/control/{meeting_id}" — a host in Amazon's real chime.aws domain that the emulator does not and cannot serve, and with no port component so the effective port is 443 regardless of the port the emulator is reached on. The harness's published-URL gate therefore reports: "the emulator published wss://signal.m3.<media-region>.app.chime.aws/control/<meeting-id>: its host is not one of the emulator's own hosts; a customer of the emulator needs ws(s)://<emulator host>:<emulator port>/<resource path>, or ws(s)://<own host>:<port> on a per-resource listener". (The region label, meeting GUID, host and port in that text are per-run values; the requirement is that the host is the emulator's own and the port is the one it is reached on.) The crate states the defect in its own comment above the builder: "The shapes of the host names mirror the ones the real service hands out ... this emulator runs no Chime SDK media service, so nothing answers behind them." Every CreateMeeting and every GetMeeting read of the same meeting republishes the same foreign address.
Why: a client that does what the MediaPlacement contract invites — take SignalingUrl and open the media/signaling session to join the meeting — is sent off the emulator entirely, at a real AWS production hostname. In a sandbox or CI network that is a DNS/egress failure, and on a machine with egress it is an attempt to reach Amazon's live service with emulator-minted credentials and a meeting id that does not exist there. Either way the meeting's data plane is unusable even though the control plane reported success, and the failure surfaces as a name-resolution or transport error rather than any HTTP status or modeled error code, so client code that handles a signaling-endpoint refusal (re-fetch the meeting, refresh the join token, back off) never runs. Nothing here depends on the concrete region or meeting id: every meeting in every media region is published at a foreign host the same way.
Fix: the MediaPlacement derivation in this service's state module — the media_placement() helper that CreateMeeting (and GetMeeting) project into Meeting.MediaPlacement — must build SignalingUrl from the emulator's own advertised host and port (the same self-address the rest of the emulator publishes) plus the meeting's control path, instead of from a hard-coded *.app.chime.aws template with no port; the sibling AudioHostUrl/AudioFallbackUrl/ScreenDataUrl/ScreenSharingUrl/TurnControlUrl/EventIngestionUrl templates beside it are built the same foreign way and must move with it so one meeting's endpoints stay mutually consistent. That address must then be served (see the related issue named above). File and line citations are under Traces.

## Steps to Reproduce
1. Clone the repo and boot the emulator built from it (the behavioral suite simparity-behavioral-aws-v1 does this). Note the host and port the emulator is reached on.
2. Point a chime-sdk-meetings client at the emulator and call CreateMeeting with a ClientRequestToken, an ExternalMeetingId and MediaRegion="us-east-1" (any supported media region behaves identically). It answers 200.
3. Read Meeting.MediaPlacement.SignalingUrl from the response. Its host is signal.m3.us-east-1.app.chime.aws — a real AWS production hostname, not the host the emulator is reached on — and the URL carries no port component, so its effective port is 443 rather than the emulator's port.
4. Compare that host:port with the emulator's own advertised host:port from step 1: they differ. Attempting to use the URL as a client would leaves the emulator (DNS lookup of a live chime.aws host, or an egress refusal in a sandboxed network) instead of reaching the deployment that minted the meeting.
5. GetMeeting on the same MeetingId republishes the identical foreign URL, as do the sibling MediaPlacement members (AudioHostUrl, AudioFallbackUrl, TurnControlUrl, ScreenDataUrl, ScreenSharingUrl).
