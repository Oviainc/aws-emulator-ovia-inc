=== Cause 1 of 2: a deployed WEBSOCKET stage never serves a client socket, so none of the per-route Lambda behaviours (lifecycle routes, identity-source short-circuit, body-action dispatch) can happen. ===
Failing checks: apigatewayv2__lambda.xsvc-apigatewayv2-2-ws-connect-and-disconnect-routes-fire-their-own-lambdas, apigatewayv2__lambda.xsvc-apigatewayv2-2-ws-request-authorizer-missing-identity-source-unauthorized-401, apigatewayv2__lambda.xsvc-apigatewayv2-2-ws-route-selection-dispatches-each-action-to-its-own-lambda.
AWS: recorded behavior only for the socket; Smithy grounds the control plane — CreateAuthorizer (AuthorizerType required, IdentitySource required @list, AuthorizerUri, EnableSimpleResponses, AuthorizerPayloadFormatVersion), CreateRoute/CreateIntegration, CreateDeployment/CreateStage, and UpdateApi.RouteSelectionExpression. The recordings pin three distinct behaviours on one WEBSOCKET api whose system and message routes each have their OWN integration:
  (a) the handshake invokes the $connect route's own Lambda with requestContext.eventType == "CONNECT", the handshake query string, and the connectionId the service minted; a frame on the open socket reaches the `ping` route's own Lambda with that SAME connectionId and eventType == "MESSAGE"; a clean client CLOSE invokes the $disconnect route's own Lambda with eventType == "DISCONNECT" and the same connectionId — in that order. The $default integration is NOT fired for lifecycle events.
  (b) a handshake that OMITS a REQUEST authorizer's identity source (route.request.querystring.token) is refused with HTTP 401 WITHOUT the authorizer Lambda being invoked and without $connect running — the gateway decides from the request alone. This is distinct from a Deny policy, which is 403 after the authorizer RAN. With the token present the authorizer runs, the handshake upgrades (101) and frames route.
  (c) RouteSelectionExpression "$request.body.action" dispatches each frame on ONE socket to the route its `action` names, each route reaching its OWN function with requestContext.routeKey equal to that route; an unknown action, a frame with no `action` member, and a frame that is not JSON at all ALL fall back to $default and its function; every reply carries the same connectionId, eventType == "MESSAGE", and the routed body is the frame verbatim.
Emulator: all three checks are killed at the 60 s cap ("Error: Check timed out after 60.0s"). The deployed WEBSOCKET stage never completes the RFC 6455 upgrade, so the watcher connection each check opens never admits, and no lifecycle invocation, refusal status or dispatch can be observed.
Why: a WebSocket API is unusable. Worse, these three properties are exactly the ones an incorrect implementation gets wrong silently — firing $default for lifecycle events, calling the authorizer and letting it deny (403 and an invocation real AWS never makes, instead of 401 and none), or ignoring the selection expression and sending every frame to $default. None of that can be detected while the socket never opens.
Fix: the execute-api WEBSOCKET data plane — the RFC 6455 upgrade on a deployed stage, the identity-source presence check in front of the authorizer, authorizer invocation and its allow/deny mapping to 101/401/403, and frame dispatch via RouteSelectionExpression to the matched route's OWN integration with the correct eventType/connectionId/routeKey in the event.
Traces: the three check ids listed at the head of this cause. Handler area: services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ (WebSocket data plane) and the vendored listener's upgrade path.

=== Cause 2 of 2: an HTTP API's translation of a Lambda proxy integration's outcome into an HTTP response cannot be exercised, because the well-formed positive control on the same function never serves. ===
Failing checks: apigatewayv2__lambda.xsvc-apigatewayv2-3-http-api-lambda-handler-raises-rejected-500, apigatewayv2__lambda.xsvc-apigatewayv2-3-http-api-lambda-without-invoke-permission-rejected-500, apigatewayv2__lambda.xsvc-apigatewayv2-3-http-api-malformed-proxy-response-rejected-500-not-502.
AWS: recorded behavior only (execute-api has no Smithy model); Smithy grounds the setup: CreateIntegration.IntegrationType = AWS_PROXY with PayloadFormatVersion ("1.0"/"2.0"). Measured on real AWS (us-west-2, 2026-10-01) the gateway answers all three refusal classes with EXACTLY status 500, body {"message":"Internal Server Error"} and content-type: application/json — the status, the body and its casing are wholly fixed text, with no request- or state-derived parts:
  (a) a handler that RAISES: 500 {"message":"Internal Server Error"} at BOTH payload format 1.0 and 2.0, with the exception's message and the Lambda error type WITHHELD (no errorMessage/errorType in the body), while the twin /ok route on each integration served by the same function returns 200. Not 502, and not the Lambda error document.
  (b) a route whose function grants API Gateway no lambda:InvokeFunction for THAT route (a route-scoped SourceArn <api>/<stage>/GET/<path> that does not cover it): 500 {"message":"Internal Server Error"} — not 403 — while a twin route on the SAME api, integration and function, covered by a statement, serves 200; adding the one missing statement makes the identical request succeed.
  (c) a MALFORMED proxy response: 500 {"message":"Internal Server Error"} and NOT the 502 "Internal server error" a REST API proxy integration returns — at 1.0 for a missing statusCode, a non-string body, a non-integer statusCode and a bare string return; at 2.0 for a non-string body and a non-integer statusCode. The 2.0 bare-string return is instead INFERRED into a 200 with the string verbatim as the body, so PayloadFormatVersion is the only thing separating the two outcomes for byte-identical handler output.
Emulator: all three checks are killed at the 60 s cap ("Error: Check timed out after 60.0s"). Each one begins by polling its well-formed twin route for 200 with the handler's marker, and that control never converges — consistent with Cause 1 of the companion report for service apigatewayv2, where an AWS_PROXY route answers 500 {"message":"Internal Server Error"} unconditionally. Hypothesis: one data-plane gap underlies both, but it is reported separately here because the evidence differs (no observed response at all vs. an observed 500) and because fixing the invocation alone would not prove these three distinctions — 500-not-502, the withheld error document, the per-route permission evaluation, and 1.0-vs-2.0 bare-string inference — are implemented.
Why: an emulator that forwards the Lambda error document as the body, answers 502 the way REST APIs do, returns 200 with the error JSON, or skips resource-policy evaluation and serves an ungranted route, is indistinguishable here from a faithful one. The permission leg is the classic over-permissive failure: traffic the real gateway refuses is served. And a leaked errorMessage can carry a secret the real gateway hides.
Fix: the execute-api HTTP data plane's AWS_PROXY response translation (parse the function's return value per PayloadFormatVersion; map FunctionError: Unhandled and every malformed shape to 500 {"message":"Internal Server Error"} with content-type application/json and no error detail; infer a bare string into a 200 body at 2.0 only) and the invoke-time permission check that matches the request's execute-api ARN <api>/<stage>/<METHOD>/<path> against the function's resource policy.
Traces: the three check ids listed at the head of this cause. Handler area: services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ (HTTP data plane) and services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs.
