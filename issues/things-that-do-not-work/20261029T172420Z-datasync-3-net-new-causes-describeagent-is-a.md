# DataSync: 3 net-new causes — DescribeAgent is a 501 stub (no unregistered-agent refusal), the skip/verify accounting of an already-synced CHANGED execution is absent, and Includes/Excludes SIMPLE_PATTERN filters are never applied

> _Note: this issue was identified against the code base at commit `7b78f885090352093daa8ac758bd09ec0b97c628`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTaskExecution

## Description
Three distinct net-new root causes in the DataSync emulator, each grounded in a failing behavioral check of the simparity-behavioral-aws-v1 suite (datasync scored 0/12). Model consulted: services/service-com-amazonaws-datasync-fmrsservice/smithy-model/com-amazonaws-datasync-fmrsservice.json (DescribeAgent, CreateLocationNfs/Smb/Hdfs, StartTaskExecution, DescribeTaskExecution, shapes Options, FilterList/FilterRule/FilterType, TaskExecutionResultDetail, InvalidRequestException).

RELATED, NOT DUPLICATE: the open issue 20261023T110503Z-datasync-createtask-createlocations3-cross-member-and-access-validation.md carries six other datasync causes, including the generic "a successful S3->S3 execution reports zero counters and copies no bytes" (its Cause 6) and the role-denial / OverwriteMode=NEVER failure paths (its Causes 4-5). None of the three causes below are in that issue's Issue-Trace-Ids, and the suite did not mark these three checks OWNED. Causes 2 and 3 here are separate behavioral rules of the same execution engine (skip-vs-transfer accounting with a still-running verify phase, and filter-driven partitioning of the transferred set) that remain broken even once a plain full copy is made to work, so each must be closed on its own.

=== Cause 1 of 3: DescribeAgent is an unimplemented 501 scaffold, so an unregistered agent ARN is never refused with the modeled client error ===
AWS: Smithy models DescribeAgent with a single required member AgentArn (@length 0..128, @pattern ^arn:(aws|aws-cn|aws-us-gov|aws-eusc|aws-iso|aws-iso-b):datasync:[a-z\-0-9]+:[0-9]{12}:agent/agent-[0-9a-z]{17}$) and exactly two errors: InternalException (server, HTTP 500) and InvalidRequestException (client, HTTP 400) — documented as "thrown when the client submits a malformed request". For an ARN that satisfies that pattern but names no agent in the account, real AWS answers HTTP 400 with Error.Code=InvalidRequestException and the message "<agent-id> does not exist or has been deleted." — fixed text " does not exist or has been deleted.", with the variable part being the agent id segment of the supplied AgentArn (the `agent-xxxxxxxxxxxxxxxxx` token, not the whole ARN) taken from the request. The same refusal, byte-identical code and message, is what every Create*Location operation that names that ARN in AgentArns returns (CreateLocationNfs via OnPremConfig.AgentArns, CreateLocationSmb.AgentArns, CreateLocationHdfs.AgentArns — all three declare InvalidRequestException as their only client error), i.e. agent resolution is one rule shared by the agent read and the location creators, not a per-operation message.
Emulator: DescribeAgent answers HTTP 501 with Error.Code=NotImplemented and the message "operation DescribeAgent is scaffolded but not implemented in this emulator". services/service-com-amazonaws-datasync-fmrsservice/src/ops/describe_agent.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its handle() body is `Err(crate::scaffolded::Scaffolded::not_implemented("DescribeAgent"))` — no state is consulted at all. Because the check stops at that first call, the agent-existence rule in the three Create*Location handlers was not reached in this run and is unverified; it must be implemented from the same shared resolution so the codes and messages match.
Why: a client cannot tell "this agent was never activated / has been deleted" from "this emulator has a hole": it gets a 501 server-class code that no DataSync SDK retry/branch logic models, where AWS gives a 400 client error it is expected to handle. Agent lifecycle tests (activate -> describe -> delete -> describe) and the cross-operation consistency guarantee (the same wording from DescribeAgent and from each location creator) cannot be written at all, and NotImplemented is not even in the operation's modeled error set, so a typed SDK deserializes it as an unmodeled failure.
Fix: implement the handler at services/service-com-amazonaws-datasync-fmrsservice/src/ops/describe_agent.rs — resolve AgentArn against the service state's agent store, return the modeled DescribeAgentOutput for a registered agent and InvalidRequestException (400) with the "does not exist or has been deleted." wording otherwise, then delete the SCAFFOLDED marker. The agent-resolution helper belongs in src/state.rs so the Create*Location handlers refuse the same ARN with the same code and message.

=== Cause 2 of 3: a CHANGED-mode execution onto an already-identical destination reports no skipped files and no verified files ===
AWS: Smithy gives DescribeTaskExecution the counters EstimatedFilesToTransfer, EstimatedBytesToTransfer, FilesTransferred, BytesTransferred, BytesWritten, FilesSkipped, FilesDeleted and FilesVerified (all `long`, @default 0) plus Result (TaskExecutionResultDetail with PrepareStatus/TransferStatus/VerifyStatus of enum PhaseStatus). DataSync has no "verify only" mode: a TransferMode=CHANGED execution whose destination already holds every source key with identical content degrades into one. Real AWS then reports a terminal Status=SUCCESS with Result.VerifyStatus=SUCCESS, every source object counted in FilesSkipped and in FilesVerified (verification still runs over the files it did not have to move), FilesTransferred=0, BytesTransferred=0, BytesWritten=0, EstimatedFilesToTransfer=0, EstimatedBytesToTransfer=0, FilesDeleted=0, and each destination object left byte-for-byte as S3 wrote it (unchanged ETag and LastModified). The requirement is the partition of the file count: skipped-and-verified, not transferred, and never zero across the board.
Emulator: the execution reaches Status=SUCCESS but reports FilesVerified=0 where 3 identical objects were staged ("AssertionError: FilesVerified was 0, expected 3 — verification must still run"), with the same fixed, all-SUCCESS Result stub and every counter left at the modeled default 0; FilesSkipped is likewise 0, so the run is indistinguishable from an execution that found nothing. StartTaskExecution persists `counters: crate::state::ExecutionCounters::default()` and nothing ever updates it, so no phase of the execution ever enumerates either location or accounts for a file as skipped or verified.
Why: a client cannot distinguish the normal steady-state DataSync run (everything already in sync: 0 bytes moved, all files verified) from a run that saw an empty source or skipped verification — the two produce identical output. Idempotency/re-run tests, "did verification actually happen" assertions, and dashboards that chart FilesSkipped/FilesVerified against FilesTransferred all read zero for a run AWS reports as fully verified.
Fix: the task-execution state machine and its counter state (services/service-com-amazonaws-datasync-fmrsservice/src/state.rs, ExecutionCounters, written from the phase advance driven by start_task_execution.rs) — the prepare phase must diff source against destination and classify each already-matching key as skipped, and the verify phase must count every file it verified, including skipped ones, before DescribeTaskExecution serializes the counters.
Traces: datasync.already-synced-destination-transfers-no-bytes-but-verifies

=== Cause 3 of 3: a task's Includes/Excludes SIMPLE_PATTERN filter does not select the transferred set ===
AWS: Smithy models Excludes and Includes on CreateTask/StartTaskExecution/DescribeTaskExecution as FilterList (@length 0..1) of FilterRule{FilterType: enum FilterType [SIMPLE_PATTERN], Value}. A filter is not decoration: an Excludes rule of SIMPLE_PATTERN "/logs*" makes real AWS transfer exactly the source keys that do NOT match it, and the identical rule under Includes makes it transfer exactly the keys that DO match, so the two executions partition the source — the two destinations are disjoint and jointly equal the source. Each execution's counters describe its own half: FilesTransferred and BytesTransferred count only the files that half moved, not the whole bucket. Both executions end Status=SUCCESS and echo their own rule back in DescribeTaskExecution.Excludes / .Includes.
Emulator: both executions report Status=SUCCESS but neither destination receives anything — "AssertionError: excluding '/logs*' landed [], expected ['alpha.txt', 'beta.txt']". The filter value is stored and echoed (start_task_execution.rs carries `includes`/`excludes` onto the execution record) but is never evaluated against any key, because no phase of the execution enumerates the source or writes to the destination; the filtered and unfiltered cases are therefore indistinguishable, and the per-half counters stay at the default 0.
Why: filter rules are how clients scope a DataSync task to a subset of a bucket. Against the emulator an exclude that is silently ignored and an exclude that excludes everything look the same, so no test can prove a key was kept out of a destination or that two filtered tasks cover the source without overlap — exactly the property a staged-migration pipeline depends on.
Fix: the execution engine's prepare/transfer phases (services/service-com-amazonaws-datasync-fmrsservice/src/state.rs execution advance, fed from ops/start_task_execution.rs) must apply the execution's effective FilterList — SIMPLE_PATTERN semantics, Excludes removing matching keys and Includes restricting to matching keys — when enumerating the source location, and then report FilesTransferred/BytesTransferred for the selected subset only.
Traces: datasync.simple-pattern-filters-partition-the-transferred-set
