=== Cause 1 of 2: S3 delivery is performed without authorizing the destination RoleARN, so a delivery stream whose role lacks s3:PutObject still writes the object, and no S3.AccessDenied delivery error is emitted ===
AWS: recorded behavior only for the delivery-time authorization — the Smithy model describes only the control plane (S3DestinationConfiguration / ExtendedS3DestinationConfiguration carry required `RoleARN` and `BucketARN` plus optional `Prefix` and `CloudWatchLoggingOptions{Enabled,LogGroupName,LogStreamName}`; CreateDeliveryStream and UpdateDestination model only InvalidArgumentException / InvalidKMSResourceException / LimitExceededException / ResourceInUseException / ResourceNotFoundException / ConcurrentModificationException, all HTTP 400), so a delivery-time denial is not an API error at all. AWS behavior the recording shows: Firehose assumes the destination RoleARN and calls s3:PutObject with those credentials; when that role's policy omits s3:PutObject for the bucket, the write is denied, NO object is ever created under the configured Prefix for as long as the stream is polled, and Firehose instead writes a delivery-error event into the stream's configured CloudWatch log stream whose JSON carries `"errorCode":"S3.AccessDenied"`. In that event, `errorCode` and the literal `S3.AccessDenied` are fixed text; the log group name, log stream name and the record payload are values taken from the stack and the request, never part of the requirement. A sibling stream in the same stack sourcing the same Kinesis stream, whose role DOES carry s3:PutObject, delivers normally — so the difference is attributable to the role alone.
Emulator: the record delivered to the under-permissioned stream's prefix anyway. The check puts one marker for the good role and one for the bad role to the same Kinesis stream, waits for the good marker to land (it did, in about 5 s), then holds an absence window of max(60 s, 3x that latency) over the bad role's prefix; the emulator wrote the bad marker there, producing `AssertionError: bad/ prefix must stay empty of 'bad-<marker>' for the full 60s absence window (>=3x the 5s positive-control latency); BadRole lacks s3:PutObject so this delivery must never succeed`. Because the write succeeded, the follow-on assertion that the CloudWatch log stream carries `errorCode` `S3.AccessDenied` is never reached either, and no such event exists.
Why: a client validating IAM against the emulator is told a delivery role that cannot write to the bucket works. The same stack shipped to AWS silently drops every record, and the one diagnostic the client monitors for exactly this misconfiguration (the S3.AccessDenied delivery error in CloudWatch Logs) never appears in the emulator, so a negative test that should fail passes. The emulator is over-permissive on a security boundary.
Fix: the Firehose S3 delivery worker (the component that flushes a buffered record to the destination) must authorize the destination configuration's RoleARN — its assume-role trust and its effective policy for s3:PutObject on the destination bucket ARN and key prefix — BEFORE writing, must write nothing when the role is not authorized, and must emit the delivery-error event carrying errorCode S3.AccessDenied to the stream's CloudWatchLoggingOptions log stream. The CFN resource provider for AWS::KinesisFirehose::DeliveryStream must hand the template's RoleARN through to that worker unchanged.
Traces: firehose__kinesis__s3.cfn-deploy-firehose-missing-s3-permission-negative.

=== Cause 2 of 2: an UpdateStack that only changes the Firehose destination Prefix ends in UPDATE_ROLLBACK_COMPLETE instead of UPDATE_COMPLETE ===
AWS: recorded behavior only for the CloudFormation provider. Smithy: Firehose `UpdateDestination` takes required `DeliveryStreamName` (length 1-64, pattern ^[a-zA-Z0-9_.-]+$), required `CurrentDeliveryStreamVersionId` (length 1-50, pattern ^[0-9]+$), required `DestinationId` (length 1-100, pattern ^[a-zA-Z0-9-]+$) and one destination update member (`S3DestinationUpdate` deprecated, `ExtendedS3DestinationUpdate`), and errors only with ConcurrentModificationException / InvalidArgumentException / ResourceInUseException / ResourceNotFoundException, all HTTP 400. AWS behavior the recording shows: a stack whose AWS::KinesisFirehose::DeliveryStream sets S3DestinationConfiguration.Prefix from {"Ref": "S3Prefix"} and that is updated with the same template and only a new value for that parameter is an in-place destination update — the stack transitions UPDATE_IN_PROGRESS -> UPDATE_COMPLETE_CLEANUP_IN_PROGRESS -> UPDATE_COMPLETE, the delivery stream keeps its identity (no replacement), and records put after the update land under the NEW prefix and not under the old one.
Emulator: the update is not applied; the stack ends in `UPDATE_ROLLBACK_COMPLETE`, reported as `AssertionError: Stack update <stack> ended in UPDATE_ROLLBACK_COMPLETE`. The pre-update delivery under the old prefix had already succeeded in the same check, so the failure is introduced by the update itself, not by the data path. Hypothesis: the AWS::KinesisFirehose::DeliveryStream update path errors (for example its UpdateDestination call supplies a CurrentDeliveryStreamVersionId or DestinationId the stream does not have, or the change is attempted as a replacement that the provider cannot complete), and CloudFormation rolls the stack back. The replay output does not show the resource-level status reason, so the specific refusal is not attributable from the trace.
Why: an IaC client cannot evolve a Firehose destination at all. A legitimate, non-replacing parameter change is reported as a failed update, the stack is rolled back to the old prefix, and every object keeps landing under the old key structure — while against AWS the same change succeeds. Clients that gate a deployment on UPDATE_COMPLETE block on a change AWS accepts.
Fix: the CloudFormation resource provider's UPDATE path for AWS::KinesisFirehose::DeliveryStream, and the Firehose UpdateDestination handler it calls — a change confined to the S3/ExtendedS3 destination Prefix must be applied in place (resolving the stream's current DeliveryStreamVersionId and DestinationId from state), must leave the stack in UPDATE_COMPLETE, and must make the delivery worker write subsequent records under the new Prefix.
Traces: firehose__kinesis__s3.cfn-stack-update-firehose-s3-prefix-positive.
