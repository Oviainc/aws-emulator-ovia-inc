# CloudTrail event history records nothing for read-only or STS calls, returns an empty Events list over the whole retention window, never matches the ResourceName lookup attribute, and PutEventSelectors accepts a selector that logs nothing

> _Note: this issue was identified against the code base at commit `2882fa01447cddf34bfea2947358b39ec0b8885e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
FOUR distinct net-new root causes in this issue; all 4 must be closed before submitting. Causes 1-3 are all in CloudTrail's event-history read path, but they are separately observable and separately fixable; Cause 4 is PutEventSelectors input validation.

Related open issue, which does NOT cover these checks: 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md. Its Cause 1 names the same recording seam (state.rs::record_management_event driven only from this service's mutating handlers), but its Issue-Trace-Ids list contains none of the eight checks below, so a fixer replaying that issue's set would never exercise them. They are filed here.

Cause 1 of 4: no record is ever produced for a READ-ONLY management call or for any STS call, so a caller cannot look up the audit record of the call it just made.
AWS: every management API call in the Region, read-only included, is written to the always-on 90-day event history and is retrievable by LookupEvents; the record carries EventId/EventName/EventSource/EventTime plus the CloudTrailEvent JSON string whose eventName/eventSource/readOnly/requestParameters describe that call (Smithy: LookupEvents, input LookupAttributes/StartTime/EndTime/EventCategory/MaxResults range 1-50, output Events + NextToken; LookupAttributeKey enum values EventId, EventName, ReadOnly, Username, ResourceType, ResourceName, EventSource, AccessKeyId - the presence of a ReadOnly key is the model's own statement that read-only calls are recorded). Recorded behavior for the latency: the checks measured the record becoming findable 135-136 s after the call on real AWS. A cloudtrail DescribeTrails or ListTags, and an sts GetCallerIdentity, each produce one record (EventSource cloudtrail.amazonaws.com / sts.amazonaws.com).
Emulator: the record never appears. Each check makes its marker call, then polls LookupEvents filtered on that EventName under a 150-900 s budget and gets Events: [] every time, so it is still polling when the harness 60 s cap kills it ('Check timed out after 60.0s') and never reaches its field assertions. No status/error-code divergence is involved: LookupEvents answers 200 with an empty list.
Why: a client cannot answer 'who called this' for its own traffic. Read-only auditing is the basis of access reviews and of detecting reconnaissance, and sts.amazonaws.com records are how a session is tied to a human; both read as 'nothing happened', which a client cannot distinguish from 'nothing is recorded'.
Fix: the shared management-event recording seam used by this service's LookupEvents handler must also be driven for read-only operations and for STS's served operations, populating eventSource/eventName/readOnly/requestParameters and the caller identity.
Traces: cloudtrail.lookup-events-returns-the-record-for-my-own-api-call (marker: cloudtrail DescribeTrails with a unique trailNameList token), cloudtrail.op-contract-lookup-events (marker: sts GetCallerIdentity; its later assertion that LookupEvents with StartTime after EndTime answers InvalidTimeRangeException / 'The start time precedes the end time.' was never reached, so it is NOT claimed as a divergence here), cloudtrail.e2e-trail-create-log-lookup-delete (marker: cloudtrail ListTags on the trail ARN, after a full create-trail/start-logging lifecycle that otherwise succeeded).

Cause 2 of 4: an UNFILTERED LookupEvents over the full retention window returns an empty list, so event history is empty even of the events the emulator does record.
AWS: LookupEvents with only StartTime/EndTime/MaxResults returns the account's management events for that window, newest first, bounded by MaxResults, each event carrying EventId, EventName, EventSource and CloudTrailEvent. Recorded behavior: on the real account the checks measured 193 events for a single 45-minute window, and a closed past window re-read 20 s later was identical.
Emulator: zero events. The checks ask for 7 days and then widen to 89 days with MaxResults=5 and still get Events: [], and the one-hour-window check gets 0 events for [T-59m, T]. These fail as explicit assertions carrying the suite's DATAPLANE_UNIMPLEMENTED marker rather than as timeouts, so they are evidence that the list is empty for EVERY event class, not just the ones in Cause 1 - the window-boundary and ordering/shape contracts cannot be probed at all without records to place either side of a boundary.
Why: any consumer that pages event history rather than filtering by name - an ordering assumption, a backfill, a boundary-exact export, 'show me the last hour' - gets an empty page and silently reports a quiet account.
Fix: once recording is driven (Cause 1), the LookupEvents handler's unfiltered/ time-window read path must return those records newest-first and honour MaxResults and the inclusive/exclusive window edges.
Traces: cloudtrail.lookup-events-ordering-and-shape, cloudtrail.lookup-events-cloudtrail-event-is-json-string, cloudtrail.lookup-events-window-boundary-is-exact-and-future-window-is-empty.

Cause 3 of 4: the ResourceName lookup attribute never matches, so even the trail-management writes the emulator does record are unfindable by the resource they touched.
AWS: LookupAttributes with AttributeKey ResourceName and AttributeValue <trail name> returns the records whose resources name that resource - for a trail that is its own CreateTrail, PutEventSelectors and StartLogging - and each returned envelope's EventName equals the embedded CloudTrailEvent's eventName (Smithy: LookupAttributeKey includes ResourceName; LookupAttribute members AttributeKey/AttributeValue are both required, and InvalidLookupAttributesException/400 is the modelled refusal for an attribute the service will not accept).
Emulator: LookupEvents(LookupAttributes=[{AttributeKey: ResourceName, AttributeValue: <trail name>}], MaxResults=50) returns Events: [] for a trail this check just created, configured and started, so the check polls for 250 s and is cut off by the 60 s harness cap. It is not refused with InvalidLookupAttributesException either - the attribute is accepted and matches nothing. Hypothesis: the records are written without a resources entry (or ResourceName is simply not an indexed attribute), since the same operations are reported as recorded in the related issue above.
Why: resource-scoped lookup is how an operator asks 'what happened to THIS resource'. A silent empty answer for a resource that was just mutated makes the attribute unusable while appearing supported.
Fix: the LookupEvents filter path plus the record-construction seam must populate and index the record's resources (ResourceName/ResourceType) for the resource each operation acts on.
Traces: cloudtrail.event-history-is-independent-of-the-trail-lifecycle.

Cause 4 of 4: PutEventSelectors ACCEPTS a selector combination real AWS refuses - IncludeManagementEvents=false with an empty DataResources list.
AWS: this selector logs nothing and is refused with InvalidEventSelectorsException, HTTP 400, message 'Invalid combination of parameters in EventSelectors. When includeManagementEvents is false, DataResources must not be empty' (entirely fixed text for this error class - no request-derived values). Smithy: PutEventSelectors declares InvalidEventSelectorsException (client, httpError 400, awsQueryError InvalidEventSelectors), and that error's own doc says it is thrown when 'the combination of event selectors or advanced event selectors and data resources is not valid'. The trail's previously applied selector set must be left untouched by the rejected write.
Emulator: the call succeeds with HTTP 200 and echoes EventSelectors [{'ReadWriteType': 'All', 'IncludeManagementEvents': False, 'DataResources': [], 'ExcludeManagementEventSources': []}], silently replacing the non-default baseline the check had applied.
Why: the client is told its trail is configured when it has configured a trail that logs nothing - a silent audit blackout, which is the exact failure mode AWS refuses the call to prevent. It also makes the emulator's 'left untouched on rejection' guarantee unverifiable.
Fix: PutEventSelectors input validation in that operation's handler, alongside the >5-selector check it already performs (the 6-selector leg of the same check was refused correctly).
Traces: cloudtrail.put-event-selectors-invalid-fails. Note: the related open issue 20261023T135552Z-cloudtrail-createtrail-updatetrail-skip-every-referenced-resource-and.md covers selector validation on CreateTrail/UpdateTrail and the AdvancedEventSelectors field grammar; it does not name this PutEventSelectors combination or this check.

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. Cause 1: call sts GetCallerIdentity and cloudtrail DescribeTrails(trailNameList=['<unique-token>']) and ListTags(ResourceIdList=['<trail arn>']). Then call cloudtrail LookupEvents with LookupAttributes [{AttributeKey: 'EventName', AttributeValue: 'GetCallerIdentity'}], then 'DescribeTrails', then 'ListTags', with StartTime a minute before each call. Expect one record each (EventSource sts.amazonaws.com / cloudtrail.amazonaws.com, readOnly true, requestParameters echoing the token); observe Events: [] on every poll.
3. Cause 2: call LookupEvents with only StartTime=now-7d, EndTime=now, MaxResults=5, then widen to now-89d. Expect a non-empty, newest-first page of at most 5 events each carrying EventId/EventName/EventSource/CloudTrailEvent; observe Events: []. Repeat for a one-hour window [now-59m, now]; observe 0 events.
4. Cause 3: CreateTrail on a policy-ready bucket, PutEventSelectors(ReadWriteType=All, IncludeManagementEvents=true), StartLogging. Then LookupEvents(LookupAttributes=[{AttributeKey: 'ResourceName', AttributeValue: '<trail name>'}], MaxResults=50). Expect records for CreateTrail/PutEventSelectors/StartLogging whose envelope EventName equals the embedded CloudTrailEvent eventName; observe Events: [] (and no InvalidLookupAttributesException).
5. Cause 4: on that trail, PutEventSelectors(EventSelectors=[{'ReadWriteType':'WriteOnly','IncludeManagementEvents':True}]) and read it back as the baseline. Then PutEventSelectors(EventSelectors=[{'ReadWriteType':'All','IncludeManagementEvents':False,'DataResources':[]}]). Expect InvalidEventSelectorsException / HTTP 400 / 'Invalid combination of parameters in EventSelectors. When includeManagementEvents is false, DataResources must not be empty' and the baseline unchanged; observe HTTP 200 with the nothing-logging selector echoed and installed.
