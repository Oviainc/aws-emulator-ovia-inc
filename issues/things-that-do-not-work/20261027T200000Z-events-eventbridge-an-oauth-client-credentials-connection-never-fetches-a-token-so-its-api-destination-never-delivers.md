# EventBridge: an OAUTH_CLIENT_CREDENTIALS connection never obtains a token, so its api destination never delivers the event

> _Note: this cause was identified against the code base at commit `74cfda6b1b1701e11661fc7b5d0b64a8c57e063b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

Cause 1 of that issue (the wording of CreateConnection's non-HTTPS AuthorizationEndpoint refusal, and of the connection refusals around it) is fixed and that report now sits under `issues/things-that-now-work/`; this cause is unfixed and is re-filed here so it is not recorded as working. ## Operation
CreateConnection / CreateApiDestination / PutEvents (the api-destination delivery path)

## Description
AWS: recorded behavior only — the Smithy model describes the connection and destination resources, not the delivery mechanics. Recorded/documented behavior: when a rule's target `Arn` is an api destination whose connection has `AuthorizationType` `OAUTH_CLIENT_CREDENTIALS`, EventBridge first makes the connection's `HttpMethod` request to its `AuthorizationEndpoint`, carrying the connection's `OAuthHttpParameters` (`QueryStringParameters` on the query string, `HeaderParameters` as request headers) and an `application/x-www-form-urlencoded` body whose fields are exactly `client_id`, `client_secret` and any `BodyParameters` (for example `scope`), with the client id and secret taken from `ClientParameters` as submitted. The connection then becomes `AUTHORIZED`, and the event request to the destination's `InvocationEndpoint` carries `Authorization: Bearer <access_token from the token response>` with the EventBridge envelope as the JSON body and no client secret anywhere in it.

Emulator: `PutTargets` accepts the api-destination target (`FailedEntryCount` 0) and `PutEvents` accepts the entry (`FailedEntryCount` 0), but a capture endpoint standing outside the emulator records no request at all — neither a token request nor the event request — so the check waits for the whole window and is killed at the 60 s harness cap. Both requests ARE made in code: `crate::state::authorization_exchange` (`services/service-com-amazonaws-eventbridge-awsevents/src/state.rs`) performs the connection's exchange and `invoke_api_destination` (`src/ops/put_events.rs`) performs the invocation. What they cannot do is leave the emulator, so the exchange reports "Could not connect to the specified endpoint.", the connection settles `DEAUTHORIZED`, and the destination that invokes through it stays `INACTIVE` — which is why no invocation follows either. Beside that, the exchange request itself is not yet the client-credentials grant: it carries no form body, no `client_id`/`client_secret` and none of the connection's `OAuthHttpParameters`, no token response is parsed or cached, and no `Authorization: Bearer` header is applied to the invocation.

Why: every webhook or third-party integration built on an OAuth api destination silently does nothing — the connection never reaches `AUTHORIZED` through a real token fetch, no Bearer credential is ever minted, and no event is delivered — while every control-plane call reports success, so a client has no signal that delivery is dead.

The ONE blocker, for whoever picks this up: a handler's only transport is the in-process emulator transport. `EmbeddedEmulator::http_connector` (`vendor/smithy-server-runtime/src/operation.rs:121-130`) hands back the router itself, so a request a handler makes is dispatched to the services this emulator hosts; no socket is opened and no name is resolved. Reaching an endpoint a caller stored — the recorded check's own HTTPS capture server — would mean an outbound connection to a caller-chosen address from the developer's machine, which this project prohibits on the production path (no outbound HTTP/TCP, no request-configurable forward target), and the merge gate's scanners block it: a submit of the wording fix above drew a HIGH finding on the scheme check alone (`CWE-918`, `state.rs` `authorization_endpoint_violation`) for merely appearing to admit an attacker-chosen egress destination. Marking the connection `AUTHORIZED`, or minting a Bearer token, with no token response would be a status and a credential for work nothing performed, and is not a fix. So this cause is gated on a way for a destination the caller names to resolve to something the emulator itself serves (an in-process, loopback-hosted endpoint the control plane reports), or on a core transport that may reach a loopback endpoint the test harness owns.

The work left in THIS crate, once such a destination can be reached, is: build the token request as the grant (the `HttpMethod` request to `AuthorizationEndpoint`, `OAuthHttpParameters` merged — query string, headers, body — and the form body's `client_id`/`client_secret` from `ClientParameters`), parse `access_token`/`expires_in` from the response and keep the token off every read of the connection, settle the connection to `AUTHORIZED` on a token and `DEAUTHORIZED` otherwise (`record_authorization` already does this half), and apply `Authorization: Bearer <token>` — and, for the other authorization types, the credential each of them is — to the api-destination invocation in `invoke_api_destination`. The generic api-destination delivery gap and the `InvocationHttpParameters` merge beside it are cause 1 of `20261025T084539Z-events-eventbridge-api-destinations-and-connections-diverge-no-http.md`.

1. Stand up an HTTPS endpoint that records each request (method, path, query, headers, body) and answers a path ending in `/token` with `{"access_token": "<tok>", "token_type": "Bearer", "expires_in": 3600}`.
2. `create_connection(AuthorizationType='OAUTH_CLIENT_CREDENTIALS', AuthParameters={'OAuthParameters': {'ClientParameters': {...}, 'AuthorizationEndpoint': '<base>/token', 'HttpMethod': 'POST', 'OAuthHttpParameters': {'BodyParameters': [{'Key':'scope','Value':'orders/write'}], 'HeaderParameters': [{'Key':'x-oauth-h','Value':'oh'}], 'QueryStringParameters': [{'Key':'aq','Value':'a1'}]}}})`.
3. `create_api_destination(ConnectionArn=<conn arn>, InvocationEndpoint='<base>/api', HttpMethod='POST')`; create an IAM role trusted by `events.amazonaws.com` allowing `events:InvokeApiDestination` on the destination ARN.
4. `create_event_bus`; `put_rule(EventPattern={"source":["<source>"]})`; `put_targets(Targets=[{Id:'api', Arn:<destination arn>, RoleArn:<role arn>}])`.
5. `put_events(Entries=[{EventBusName:<bus>, Source:'<source>', DetailType:'oauth', Detail:'{"n":1}'}])` repeatedly.
6. Observe that the capture endpoint records no token request and no event request, and that `describe_connection` reports `DEAUTHORIZED` with `StateReason` "Could not connect to the specified endpoint." while `describe_api_destination` reports `INACTIVE`.
