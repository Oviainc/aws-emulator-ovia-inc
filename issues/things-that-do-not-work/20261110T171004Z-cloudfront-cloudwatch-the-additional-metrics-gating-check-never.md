# cloudfront__cloudwatch: the additional-metrics gating check never reaches a verdict — no AWS/CloudFront CacheHitRate datapoint ever appears after CreateMonitoringSubscription and the edge serves no warm-up traffic

> _Note: this issue was identified against the code base at commit `0c065617979d1ee76fa77b423bd58183fc04c861`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricStatistics

## Description
One net-new root cause, grounded in a failing behavioural check that no open issue carries the replay key for. Its sibling check (obs-cloudfront-1-additional-metrics-match-recorded-edge-outcomes) is owned by 20261024T182555Z-cloudfront-cloudwatch-no-edge-traffic-is-ever-served.md, and 20261110T090020Z-cloudfront-cloudwatch-a-served-edge-produces-no-aws.md / 20261109T181319Z-cloudfront-cloudwatch-the-distribution-s-published-domainname-is.md describe neighbouring symptoms — none of them covers this check, which asserts the opposite-signed claim (that the gated metrics are WITHHELD for an unsubscribed distribution while its default metrics still match the traffic it served).

Cause 1 of 1: a monitoring subscription publishes no additional AWS/CloudFront metrics, and the distribution endpoint serves no traffic, so the check's barrier never clears.
AWS: recorded behavior only for the metric emission; the control-plane operations are modeled (CloudFront CreateMonitoringSubscription / GetMonitoringSubscription / DeleteMonitoringSubscription, and CloudWatch GetMetricStatistics / ListMetrics). The recording shows two sibling distributions over one OAC-locked bucket receiving IDENTICAL traffic, differing only in that one (A) has a monitoring subscription with RealtimeMetricsSubscriptionStatus 'Enabled' and the other (B) has none — GetMonitoringSubscription on B is refused with code NoSuchMonitoringSubscription and the message 'The monitoring subscription does not exist.' (fixed text, no variable part). After the subscription goes live, AWS publishes the ADDITIONAL metrics for A in namespace AWS/CloudFront under dimensions DistributionId=<id> and Region=Global: CacheHitRate, OriginLatency (p90) and 403ErrorRate. For B those same metrics are published in NO minute — GetMetricStatistics returns an empty Datapoints list and ListMetrics returns an empty Metrics list for each of them — while B's DEFAULT metrics ARE published for the minute it served: Requests (Sum) equals the number of requests it answered, and 4xxErrorRate (Average) equals the percentage of its responses with a 4xx status, both for the 60-second period covering that traffic.
Emulator: the check never reaches any of those assertions. It resolves each distribution's DomainName through ctx.endpoint_route() and issues warm-up GETs expecting 200 with the origin body; it then polls GetMetricStatistics for AWS/CloudFront CacheHitRate on the SUBSCRIBED distribution's dimensions as its barrier ('the monitoring subscription to go live (a first CacheHitRate point ...)'). That barrier never clears — no CacheHitRate datapoint is ever returned — so the check burns its whole budget and is killed at the harness cap ('Check timed out after 600.0s'). Consequently neither the gated-metric absence for the unsubscribed control, nor the Requests/4xxErrorRate agreement with what it served, is ever evaluated.
Why: a client cannot observe the only thing a monitoring subscription buys. Dashboards and alarms built on CacheHitRate, OriginLatency or 403ErrorRate stay permanently empty, which is indistinguishable from the correct AWS behaviour for an UNsubscribed distribution — so the emulator gives no way to tell 'subscription missing' from 'subscription not implemented', and a cost-conscious client cannot verify that the additional metrics really are gated behind the subscription it is paying for.
Fix: CloudFront's metric emission for served edge requests, gated on the distribution's monitoring subscription — publish the additional AWS/CloudFront series (CacheHitRate, OriginLatency, 403ErrorRate) under DistributionId + Region=Global only while a subscription is Enabled, keep publishing the default series (Requests, 4xxErrorRate) regardless, and make ListMetrics agree with what GetMetricStatistics can answer. This also requires the distribution's served endpoint to answer the warm-up and measured requests at all, since the metrics are derived from them.
Traces: cloudfront__cloudwatch.obs-cloudfront-1-additional-metrics-withheld-without-monitoring-subscription.

## Evidence
cloudfront__cloudwatch.obs-cloudfront-1-additional-metrics-withheld-without-monitoring-subscription, verdict mismatch:
  Error: Check timed out after 600.0s
Expected (from the check body): GetMonitoringSubscription on the subscribed distribution reads RealtimeMetricsSubscriptionStatus == 'Enabled'; on the control it is refused with ('NoSuchMonitoringSubscription', 'The monitoring subscription does not exist.'); warm-up GETs through both DomainNames return 200 with the warm-up body; a first AWS/CloudFront CacheHitRate datapoint appears for the subscribed distribution (Dimensions DistributionId=<A>, Region=Global, Period 60, Statistics ['Average']) — this is the barrier; then, per measured minute, B's Requests Sum equals the number of requests B served and B's 4xxErrorRate Average equals its 4xx percentage, while for B each of CacheHitRate, OriginLatency (ExtendedStatistics p90) and 403ErrorRate yields Datapoints == [] and ListMetrics yields Metrics == [].
Actual: the barrier poll for the first CacheHitRate datapoint never clears (GetMetricStatistics keeps returning no datapoints for the SUBSCRIBED distribution), and the warm-up traffic through the published DomainName does not serve, so the check is killed at the 600 s cap with none of those assertions evaluated.

## Steps to Reproduce
Create a private bucket with a warm-up object and a payload object plus an OAC (s3/always/sigv4); create two distributions A and B over that bucket, both using the managed cache policy Managed-CachingOptimized (658327ea-f89d-4fab-a63d-7e88639e58f6); call cloudfront CreateMonitoringSubscription(DistributionId=A, MonitoringSubscription={RealtimeMetricsSubscriptionConfig:{RealtimeMetricsSubscriptionStatus:'Enabled'}}) and leave B unsubscribed; wait for both to be Deployed; issue identical GETs for the warm-up key through both DomainNames; then poll cloudwatch GetMetricStatistics(Namespace='AWS/CloudFront', MetricName='CacheHitRate', Dimensions=[{DistributionId:A},{Region:'Global'}], Period=60, Statistics=['Average']). Observe that no datapoint ever appears for the subscribed distribution A (and that the warm-up GETs do not serve), so the gating contrast against B can never be measured.
