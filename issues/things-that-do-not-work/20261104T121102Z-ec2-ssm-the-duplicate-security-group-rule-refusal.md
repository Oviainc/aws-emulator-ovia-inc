# ec2__ssm: the duplicate security-group-rule refusal names the stored rule id instead of AWS's rule descriptor, and every SSM-observed in-guest data-plane scenario never settles (2 causes)

> _Note: this issue was identified against the code base at commit `3bd56f3581a93dde5b982de16e37f58616506edc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AuthorizeSecurityGroupIngress

## Description
Two net-new root causes grounded in failing checks listed under '### ec2__ssm'. 2 CAUSES — both must be closed before submitting.

Cause 1 of 2: AuthorizeSecurityGroupIngress's duplicate-rule refusal message renders the stored rule id where AWS renders the rule itself.
AWS: re-authorizing a rule whose protocol, port range and peer already exist on the group is refused 400 InvalidPermission.Duplicate, and the message describes the RULE, not its id: `the specified rule "peer: <peer>, <PROTOCOL>, from port: <fromPort>, to port: <toPort>, <ACTION>" already exists`. The fixed text is `the specified rule "` ... `" already exists` and the inner descriptor's fixed labels `peer: `, `, `, `from port: `, `, to port: `, `, `; its variable parts come from the request — the peer (the CidrIp, or the referenced group id), the protocol upper-cased (TCP), the from/to ports, and the rule action (ALLOW). A rule's identity does not include its Description, so a re-authorization that changes only the description is still this duplicate refusal (the emulator does refuse here, which is correct). Recorded behavior only: EC2's ec2Query errors are not in the Smithy model, so the code and message come from the recorded response.
Emulator: the status and the code are right, but the message is `the specified rule "sgr-00000000000000046" already exists` — the descriptor is replaced by the emulator's security-group-rule id, which is an identifier of the stored rule and is not part of AWS's message at all.
Why: a client that parses the duplicate message to learn WHICH rule collided (the only thing AWS tells it, since the call returns no rule set) gets an opaque id instead of the protocol/port/peer tuple, and any matcher on AWS's sentence fails. The open issue 20261103T021956Z-ec2-security-group-and-network-interface-refusals-wrong.md describes rule-id-based duplicate messages from another corpus but does not carry this check id.
Fix: the AuthorizeSecurityGroupIngress handler's duplicate-detection error construction — render the rule descriptor from the requested permission rather than the stored rule id.
Traces: ec2__ssm.duplicate-ssh-ingress-rule-rejected-and-rule-count-unchanged.

Cause 2 of 2: an EC2 instance the emulator launched never becomes a Systems Manager managed node, so every scenario that observes the guest through SSM polls forever and is killed by the harness.
AWS: an instance launched from an Amazon Linux/Windows AMI with an instance profile carrying AmazonSSMManagedInstanceCore registers with Systems Manager shortly after boot; DescribeInstanceInformation then reports it with PingStatus Online (Smithy, services/service-com-amazonaws-ssm-amazonssm: InstanceInformation$PingStatus -> enum PingStatus Online | ConnectionLost | Inactive, plus LastPingDateTime, AgentVersion, PlatformType, IamRole), and SendCommand/GetCommandInvocation then execute in the guest and return its stdout. Every one of the grounding checks uses that as its only observation point: they launch instances, wait for the agent to come up, and then read the VPC data plane from inside the guest (jumbo/path MTU and TCP MSS across AZs and through an internet gateway, transit-gateway forwarding and a blackholed route, VPC peering with routes on one or both sides, a source-group rule dropping as a timeout rather than a refusal, and the SSM inventory's agent version against the installed rpm).
Emulator: none of these checks ever reaches its assertions — each is killed with `Error: Check timed out after 60.0s` and no response divergence is printed, because the check never gets an answer to assert on. Hypothesis: the stall is the managed-node gate — nothing in the emulator registers an EC2-launched instance as an SSM managed node, so DescribeInstanceInformation never reports PingStatus Online and the agent-online poll in each check never converges. The open issue 20261027T034339Z-ec2-ssm-a-launched-ec2-instance-never-becomes.md diagnoses exactly that gate (services/service-com-amazonaws-ssm-amazonssm/src/ops/describe_instance_information.rs reports only nodes held in state's managed_nodes, which nothing populates for a launched instance) for two other checks, but it does not carry any of these eight check ids.
Why: the failure mode is a hang, not an error: a client waiting for `PingStatus == Online` (or for `aws ssm wait`) before it does anything has no error code to branch on and no service-side timeout, and every SSM-observed network-behaviour workflow — MTU/path-MTU discovery, transit-gateway and peering reachability, security-group source-group semantics, inventory agent version — never starts.
Fix: SSM managed-node registration in the ssm crate's state (the managed_nodes inventory populated for an instance whose profile can reach Systems Manager, projected with PingStatus Online/LastPingDateTime/PlatformType/IamRole on the emulator's owed-transition clock), and then in-guest execution for SendCommand/GetCommandInvocation plus the EC2 data-plane behaviour each scenario reads (MTU/MSS, TGW and peering route evaluation, source-group admission dropping as a timeout).
Traces: ec2__ssm.mtu-jumbo-frames-carry-an-unfragmented-payload-across-availability-zones-in-one-vpc, ec2__ssm.mtu-path-mtu-collapses-to-1500-when-the-same-eni-sends-through-the-internet-gateway, ec2__ssm.mtu-tcp-negotiates-a-segment-size-that-reveals-the-path-mtu-without-losing-a-byte, ec2__ssm.dtgw-transit-gateway-forwards-packets-between-two-vpcs-and-a-blackholed-route-stops-them, ec2__ssm.sep-network-truth-vpc-peering-carries-packets-only-with-routes-on-both-sides, ec2__ssm.sep-network-truth-sg-source-group-rule-admits-members-only-and-drops-as-timeout-not-refusal, ec2__ssm.vscan-inventory-agent-version-matches-the-installed-rpm-on-a-deprecated-ami.
