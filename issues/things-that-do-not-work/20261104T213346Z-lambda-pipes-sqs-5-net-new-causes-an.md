Cause 1 of 5: a pipe in CurrentState RUNNING whose Source is an SQS queue and whose Target is a Lambda function never receives a message from the source and never invokes the target, so nothing is ever in flight and nothing is ever delivered.
AWS: Smithy (com.amazonaws.pipes#CreatePipe) models Source (ArnOrUrl, required), SourceParameters -> PipeSourceParameters (for SQS: BatchSize, MaximumBatchingWindowInSeconds), Target (Arn, required), TargetParameters -> PipeTargetParameters (LambdaFunctionParameters.InvocationType, InputTemplate) and RoleArn; DescribePipe reports CurrentState (PipeState) and StateReason. The model describes only the control plane, so the data movement is recorded behavior only: once the pipe is RUNNING the SERVICE polls the source with no client action, makes the batch invisible for the source queue's VisibilityTimeout while the target runs, invokes the target once per batch, deletes the source message only after a successful target invocation, and UpdatePipe changing TargetArn redirects subsequent deliveries to the new target while the old target stops receiving.
Emulator: no message is ever picked up. lambda__pipes__sqs.pipes-sqs-visibility-timeout-respected-during-processing fails the explicit assertion `assert in_flight["ApproximateNumberOfMessagesNotVisible"] != "0"` with AssertionError: pipe never picked up the message — the source queue reports ApproximateNumberOfMessagesNotVisible = "0" the whole time the target should be processing. The other three checks exhaust the 60 s harness budget ('Error: Check timed out after 60.0s') waiting for the first delivery, including the positive-control legs of the two permission negatives, so those negatives are unprovable rather than passing.
Why: a client that wires a queue to a function through a pipe sees a pipe reporting RUNNING that transports nothing: no in-flight accounting on the source, no invocation, no deletion-on-success, and an UpdatePipe target change that cannot be observed. Every permission negative loses its control, so a real IAM denial is indistinguishable from a dead pipe.
Fix: the pipes data-plane engine for SQS sources in the pipes service — the per-pipe poller driven by the stored SourceParameters, the in-flight/visibility accounting against the sqs surface, the Lambda target invoker, delete-on-success, and honouring an UpdatePipe Target change in the running poller.

Cause 2 of 5: a pipe whose execution role has no permission on its source queue is never reported as failed — it neither self-disables nor carries a StateReason attributing the failure to the source queue.
AWS: Smithy (com.amazonaws.pipes#DescribePipe) returns CurrentState from PipeState — whose values include STOPPED, CREATE_FAILED, START_FAILED — together with StateReason (PipeStateReason, @length 0..512); those members exist because pipe creation/start validates the role's source access asynchronously and surfaces the failure as a terminal CurrentState plus a human-readable reason. The required source actions for an SQS source are sqs:ReceiveMessage, sqs:DeleteMessage and sqs:GetQueueAttributes, and the recorded expectation is a non-healthy CurrentState whose StateReason names the denied action or the denial (its fixed text is the denial wording; the variable parts are the action name and the source queue identity taken from the pipe's own Source and RoleArn).
Emulator: the pipe created with a role holding only lambda:InvokeFunction on the target never reaches STOPPED/START_FAILED/CREATE_FAILED with such a reason — lambda__pipes__sqs.pipes-missing-source-role-permission-negative times out at the harness cap in `_poll_pipe_state(..., {"STOPPED", "START_FAILED", "CREATE_FAILED"}, timeout_s=120)` and never sees a StateReason containing any of ReceiveMessage / DeleteMessage / GetQueueAttributes / AccessDenied / "not authorized" / "does not have permission". Hypothesis: the create/start path stores RoleArn and Source verbatim and performs no role-vs-source authorization at all.
Why: the single most common pipe misconfiguration — a role missing sqs:ReceiveMessage on the source — is reported as a healthy pipe with an empty StateReason, so a client has no signal to act on and (because of Cause 1) no data movement to distinguish it from an idle source either.
Fix: asynchronous create/start validation in the pipes state machine — resolve Source against the sqs surface, check the role's policy for the required source actions against iam, and set CurrentState to the modeled terminal failure value with a populated StateReason instead of settling into DesiredState.
Traces: lambda__pipes__sqs.pipes-missing-source-role-permission-negative.

Cause 3 of 5: the pipe's enrichment stage never runs and the target's InputTemplate is never rendered, so the target receives neither the enrichment's return value nor the templated payload.
AWS: Smithy (com.amazonaws.pipes#CreatePipe) models Enrichment (OptionalArn) and EnrichmentParameters (PipeEnrichmentParameters, including InputTemplate) and TargetParameters -> PipeTargetParameters.InputTemplate; the behavior is recorded only: a Lambda enrichment is handed the batch as a JSON LIST of source records, its return value (not the raw source body) becomes the record set handed to the target stage, and the target's InputTemplate is then rendered against that enrichment output with `<$.path>` substitutions, so fields the template does not name do not appear at the target.
Emulator: both checks exhaust the 60 s harness budget with no message at the target — the enrichment function is never invoked and no templated payload is ever produced.
Why: a client cannot use Pipes to transform a payload at all; enrichment-computed fields and InputTemplate projection — the whole reason to put a pipe between a queue and a target — are unobservable.
Fix: the enrichment and input-template stages of the pipes execution engine (invoke the Enrichment ARN with the batch as a list, feed its result to the target stage, render TargetParameters.InputTemplate against that result). Depends on Cause 1 existing first.
Traces: lambda__pipes__sqs.pipes-enrichment-transforms-payload-before-target, lambda__pipes__sqs.events-pipes-enrichment-computed-field-shapes-target-via-input-template.

Cause 4 of 5: an SQS event source mapping never invokes its function, for a standard queue or a FIFO queue, so neither the enabled control nor the Disabled/re-enabled transition can be observed.
AWS: Smithy (com.amazonaws.lambda#CreateEventSourceMapping) models EventSourceArn, FunctionName, BatchSize, Enabled and (read-side) State; the polling itself is recorded behavior only: an Enabled mapping on an SQS queue invokes the function with the queue's records and deletes them on successful processing; a mapping in state Disabled invokes nothing and the message stays on the queue until the mapping is re-enabled, at which point that same retained message is delivered; for a FIFO source the records of one MessageGroupId are delivered in send order across batches.
Emulator: all three checks exhaust the 60 s harness budget with no invocation — the enabled control never delivers, so the Disabled negative has no control, and the FIFO ordering claim is never reached.
Why: clients cannot tell a mis-configured mapping from an event-source-mapping subsystem that never polls; Enabled/Disabled has no observable effect and FIFO ordering guarantees cannot be validated.
Fix: the Lambda event-source-mapping poller/invoker for SQS sources — poll per BatchSize, gate on the mapping's Enabled/State, invoke the function, delete on success, and serialize per MessageGroupId for FIFO queues.
Traces: lambda__pipes__sqs.sqs-event-source-mapping-invokes-lambda-positive, lambda__pipes__sqs.sqs-esm-disabled-mapping-no-invocation-negative, lambda__pipes__sqs.sqs-esm-fifo-queue-message-group-ordering-preserved.

Cause 5 of 5: a CloudFormation stack declaring an AWS::Pipes::Pipe or an AWS::Lambda::EventSourceMapping deploys but the declared wiring never moves a message, and a stack whose mapping role lacks the queue's poll permissions is not failed and rolled back.
AWS: recorded behavior only (CloudFormation resource providers). A stack that reports CREATE_COMPLETE has created every declared resource and that resource behaves exactly as the equivalent API-created one: the template's pipe delivers source->target, the template's FilterCriteria drops the non-matching record and delivers the matching one, and the template's event source mapping invokes the function. A resource whose creation cannot succeed — here a mapping whose role cannot poll the queue — must fail the stack, which then reaches ROLLBACK_COMPLETE with a permission reason on the failing resource.
Emulator: all five checks exhaust the 60 s harness budget. The three positive stacks never deliver the message their declared pipe/mapping should move; the two negatives never reach their verdict because their in-stack positive control never delivers either.
Why: every pipe and every event source mapping deployed as infrastructure-as-code (CDK, SAM, plain CFN) appears to deploy and then transports nothing, and a template with a role that cannot poll its queue is reported as a successful deployment — a client that reads stack status as its gate proceeds against wiring that does not work.
Fix: the CloudFormation AWS::Pipes::Pipe and AWS::Lambda::EventSourceMapping resource providers — create the resource through the same pipes/lambda state the API path uses (so it inherits the runtimes of Causes 1 and 4, including template FilterCriteria), propagate the resource's terminal failure into the stack event, and roll the stack back when the resource cannot be created.
Traces: lambda__pipes__sqs.deploy-esm-sqs-lambda-cfn-positive, lambda__pipes__sqs.deploy-esm-missing-permission-cfn-negative, lambda__pipes__sqs.deploy-pipes-sqs-lambda-stack-positive, lambda__pipes__sqs.deploy-pipes-filter-pattern-config-positive, lambda__pipes__sqs.deploy-pipes-missing-role-negative.
