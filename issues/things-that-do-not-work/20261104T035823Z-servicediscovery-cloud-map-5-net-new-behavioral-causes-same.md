# Cloud Map: 5 net-new behavioral causes — same-name namespace conflict answers DuplicateRequest, InvalidInput aggregates only one violation, GetNamespace omits DnsProperties.SOA, RegisterInstance skips required DNS attributes, CFN Service Ref returns an ARN

> _Note: this issue was identified against the code base at commit `c083bea380b29cc5238d586af0774e0d5864cbe3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePrivateDnsNamespace

## Description
FIVE independent, net-new root causes in the servicediscovery (Cloud Map) emulator, each grounded in failing checks of the behavioral replay against the bootstrapped service. They are numbered below and EACH must be closed before this issue is submitted: Cause 1 of 5 .. Cause 5 of 5, each with its own failing check ids. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json.

Cause 1 of 5: a second CreatePrivateDnsNamespace for a Name that already exists (sent with a DIFFERENT CreatorRequestId) is refused with DuplicateRequest instead of NamespaceAlreadyExists.
AWS: Smithy CreatePrivateDnsNamespace{Name (required), CreatorRequestId (idempotencyToken), Description, Vpc (required), Tags, Properties} -> {OperationId}; errors DuplicateRequest (HTTP 409, documented 'The operation is already in progress', carrying DuplicateOperationId), InvalidInput, NamespaceAlreadyExists (HTTP 400, documented 'The namespace that you're trying to create already exists', carrying CreatorRequestId and NamespaceId), ResourceLimitExceeded, TooManyTagsException. The two errors classify different conflicts: DuplicateRequest is a REPLAY of the same CreatorRequestId whose operation is still in progress; a distinct CreatorRequestId colliding on the NAME is NamespaceAlreadyExists. Recorded behavior: a synchronously-refused racer for one Name/Vpc with its own CreatorRequestId carries Code 'NamespaceAlreadyExists' (HTTP 400) and may carry NamespaceId = the existing namespace; the alternative AWS behavior the checks also accept is to accept both and FAIL the loser's operation with a non-empty ErrorMessage.
Emulator: Code 'DuplicateRequest' (the 409 class) for the losing create, even though the two calls used distinct CreatorRequestIds.
Why: the code is the whole contract here — DuplicateRequest tells a client 'your own retry is still running, poll it', NamespaceAlreadyExists tells it 'someone else owns this name, pick another'. Retry loops that treat 409/DuplicateRequest as transient spin forever against the emulator, and name-conflict handling never runs. The NamespaceAlreadyExists members (NamespaceId, CreatorRequestId) that identify the winner are also unreachable.
Fix: the conflict classification in CreatePrivateDnsNamespace's handler (and the shared namespace-create path): key DuplicateRequest off an in-flight CreatorRequestId only, and raise NamespaceAlreadyExists with the existing namespace's id for a name collision.
Traces: servicediscovery.namespace-already-exists-private-dns, servicediscovery.concurrent-create-namespace-same-name-different-request-id-conflict.

Cause 2 of 5: an over-length namespace Name produces an InvalidInput message that reports only ONE of the two violated constraints and elides the offending value.
AWS: Smithy CreatePrivateDnsNamespace.Name targets NamespaceNamePrivate with @length max 253 AND @pattern ^(?!arn:)[!-~]{1,253}$. A 301-character name violates BOTH, and AWS's framework validator aggregates them into one InvalidInput (HTTP 400) whose message template is: fixed text '<n> validation errors detected: ', then one clause per violation joined by '; ', each clause being "Value '<the value sent>' at '<member path>' failed to satisfy constraint: " plus the constraint sentence ('Member must satisfy regular expression pattern: ^(?!arn:)[!-~]{1,253}$', 'Member must have length less than or equal to 253'). The variable parts are the count, the value from the request and the member path ('name'); the clause order is pattern first, then length. The same check's 'arn:'-prefixed-name assertion (1 validation error, the pattern clause) PASSES, so only the aggregation and the value rendering diverge.
Emulator: '1 validation error detected: Value \'sim2real-toolong-...xxx... [301 bytes]\' at \'name\' failed to satisfy constraint: Member must have length less than or equal to 253' — the pattern violation is dropped, the count is 1 instead of 2, and the value is truncated with an invented ' [301 bytes]' marker instead of being echoed in full.
Why: clients and tests parse this message to learn WHICH constraints failed; an emulator that reports one of two teaches a caller that fixing the length is enough, and the ' [N bytes]' elision is a rendering AWS never emits.
Fix: the InvalidInput construction in the request validator shared by the namespace-create operations — collect every violated constraint for a member, emit them in the pattern-then-length order with the plural count, and echo the full value.
Traces: servicediscovery.create-private-dns-namespace-invalid-domain-rejected.

Cause 3 of 5: GetNamespace's Properties.DnsProperties omits the SOA structure, so the namespace's negative-caching TTL is unreadable (and UpdatePrivateDnsNamespace's SOA TTL range refusal is unreachable behind it).
AWS: Smithy GetNamespace{Id (required)} -> Namespace{..., Properties: NamespaceProperties{DnsProperties: DnsProperties{HostedZoneId, SOA: SOA{TTL (required, @range 0..2147483647)}}, HttpProperties}}. SOA.TTL is a REQUIRED member of SOA, so a DNS namespace always reports it. UpdatePrivateDnsNamespace{Id (required), UpdaterRequestId, Namespace (required: PrivateDnsNamespaceChange{Properties.DnsProperties.SOA: SOAChange{TTL required, @range 0..2147483647}})} -> {OperationId}; errors DuplicateRequest, InvalidInput, NamespaceNotFound, ResourceInUse. A TTL above the range maximum is refused with InvalidInput whose message template is: fixed text '1 validation error detected: ', then "Value '<the TTL sent>' at 'namespace.properties.dnsProperties.sOA.tTL' failed to satisfy constraint: Member must have value less than or equal to 2147483647" (the member path, including AWS's 'sOA.tTL' lower-camel rendering, is fixed text; the value comes from the request), the persisted TTL must be unchanged, and an in-range TTL update must persist.
Emulator: GetNamespace on a freshly created private DNS namespace returns Properties with a DnsProperties that has no SOA member (the check raises KeyError: 'SOA' reading Namespace['Properties']['DnsProperties']['SOA']['TTL']), so the TTL rules above are never even exercised. Related to cause 1 of the open wire issue 20261029T203804Z-servicediscovery-cloud-map-namespace-service-and-operation-responses-omit.md, which reports DnsProperties missing entirely on GetNamespace; DnsProperties is now present and the SOA inside it is what is absent, and that issue says nothing about the UpdatePrivateDnsNamespace TTL validation.
Why: SOA.TTL is the only way a client can read or confirm the namespace's negative-caching TTL, and it is a required member — reading it unconditionally (as AWS's own docs and SDK examples do) raises against the emulator; an out-of-range TTL update is also left unvalidated.
Fix: the Namespace properties projection in GetNamespace's handler and the namespace record in the service's state (populate DnsProperties.SOA.TTL at create time for DNS namespaces), plus the SOA TTL range validation in UpdatePrivateDnsNamespace's handler.
Traces: servicediscovery.update-private-dns-namespace-invalid-ttl-rejected.

Cause 4 of 5: RegisterInstance ACCEPTS an instance whose Attributes omit the attribute the service's DnsConfig record type requires, where AWS refuses with InvalidInput.
AWS: Smithy RegisterInstance{ServiceId (required), InstanceId (required), CreatorRequestId, Attributes (required)} -> {OperationId}; errors DuplicateRequest, InvalidInput, ResourceInUse, ResourceLimitExceeded, ServiceNotFound. The Attributes documentation states for AWS_INSTANCE_IPV4: 'This value is required if the service specified by ServiceId includes settings for an A record' (correspondingly AWS_INSTANCE_IPV6 for AAAA, AWS_INSTANCE_CNAME for CNAME, AWS_INSTANCE_PORT for SRV). The refusal is InvalidInput (HTTP 400) with the recorded message template 'Required attribute(s) <names> are missing.' — fixed text 'Required attribute(s) ' and ' are missing.' around the missing attribute key(s) derived from the service's DnsConfig (here AWS_INSTANCE_IPV4). After the refusal GetInstance answers InstanceNotFound whose Message is the InstanceId from the request, and the same InstanceId registers successfully once the attribute is supplied.
Emulator: HTTP 200 with an OperationId for register_instance(ServiceId=<A-record service>, InstanceId=<id>, Attributes={'custom':'no-ip'}).
Why: an instance with no address can never be answered by the A record it was registered against, so the emulator silently stores a registration that resolves to nothing and hides a client bug AWS catches at the API boundary. Distinct from the already-filed check servicediscovery.register-instance-missing-required-attribute-rejected owned by 20261023T124702Z-servicediscovery-cloud-map-servicediscovery-8-fidelity-divergences-missing-dnsconfig.md; the fix must satisfy this check too.
Fix: the Attributes validation in RegisterInstance's handler — derive the required attribute set from the target service's DnsConfig.DnsRecords (and HealthCheckConfig) and raise InvalidInput with the template above before any instance row or operation is created.
Traces: servicediscovery.register-instance-missing-required-dns-attribute-rejected.

Cause 5 of 5: the CloudFormation resource AWS::ServiceDiscovery::Service resolves {Ref} to a service ARN built from the service NAME, instead of the Cloud Map service Id, so the stack output cannot be used as a ServiceId.
AWS: {Ref} on AWS::ServiceDiscovery::Service returns the service's Id (the 'srv-...' ResourceId that every Cloud Map ServiceId parameter takes); the ARN is reachable only via Fn::GetAtt .Arn, and a Cloud Map service ARN always ends in 'service/<srv-id>', never in the service name. Recorded behavior: the stack reaches CREATE_COMPLETE and the Ref value feeds straight into RegisterInstance/DiscoverInstances — RegisterInstance{ServiceId} + DiscoverInstances(NamespaceName, ServiceName) round-trip the instance and its AWS_INSTANCE_IPV4, and DeregisterInstance removes it.
Emulator: the stack's ServiceId output is 'arn:aws:servicediscovery:<region>:<account>:service/<the service NAME>' and RegisterInstance with it is refused: ServiceNotFound, Message = that same ARN. So the deployed service cannot be driven at all through the stack's own output.
Why: this is the documented way to wire a Cloud Map service created by CloudFormation into anything else (ECS serviceRegistries, a registering task, another stack) — every consumer of the Ref gets an identifier the API rejects. Sibling CFN checks are carried by the open issue 20261023T124702Z-servicediscovery-cloud-map-servicediscovery-8-fidelity-divergences-missing-dnsconfig.md, which does not cover the Ref/ARN-vs-Id resolution of this resource.
Fix: the AWS::ServiceDiscovery::Service resource provider in the CloudFormation emulator — return the created service's Id as the Ref/physical-resource-id, expose the ARN (built from the Id, not the Name) and Id/Name as GetAtt attributes.
Traces: servicediscovery.deploy-private-dns-namespace-cfn-service-discovery.
