# cloudformation__iam__s3: 2 net-new root causes — AWS::IAM::Group/UserToGroupAddition in a CREATE_COMPLETE stack never exist in IAM, and the AWS::IAM::AccessKey Status/Serial rotation path never reaches a verdict

> _Note: this issue was identified against the code base at commit `01964283ae746bd4bc050654141badf53a1b32d1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two distinct root causes in the CloudFormation-deploys-IAM-identities-then-signs-S3 group. Both are grounded in failing behavioral checks of this suite; neither is marked ALREADY FILED or OWNED in the replay report. The only open issue for this service token, 20261029T192356Z-cloudformation-iam-s3-createchangeset-with-a-templateurl-never.md, is about CreateChangeSet TemplateURL authorization and covers neither cause below.

Cause 1 of 2: a stack that declares AWS::IAM::Group (and AWS::IAM::UserToGroupAddition) reaches CREATE_COMPLETE, but the group was never created in IAM.
AWS: CloudFormation only reports CREATE_COMPLETE once every resource in the template has been created in its owning service. A template whose Resources contain an AWS::IAM::Group with GroupName plus an inline Policies entry, and an AWS::IAM::UserToGroupAddition binding the template's AWS::IAM::User into it, results in a real IAM group: iam:CreateGroup is performed, the inline policy is attached, and the user is added. iam:GetGroup on that name then returns 200 with the modeled required members Group and Users, and Users contains exactly the added user. Smithy (com-amazonaws-iam-awsidentitymanagementv20100508): CreateGroup input GroupName @required, groupNameType @length 1..128 @pattern ^[\w+=,.@-]+$, output Group @required; GetGroup output Group @required, Users @required (userListType), errors NoSuchEntityException (awsQueryError code NoSuchEntity, httpResponseCode 404) only when the group genuinely does not exist. So on AWS, GetGroup after a CREATE_COMPLETE of this stack is a 200, never a 404.
Emulator: the create_stack call returns a StackId, the stack settles to CREATE_COMPLETE, and the stack's Outputs are complete enough that the check's assertions on AccessKeyId / SecretAccessKey / UserArn and on iam:ListAccessKeys all pass — so the AWS::IAM::User and AWS::IAM::AccessKey resources were materialized. The very next call, iam:GetGroup on the GroupName the template declared, is refused: HTTP 404, error code NoSuchEntity, message "The group with name <GroupName> cannot be found." (observed as botocore.errorfactory.NoSuchEntityException: An error occurred (NoSuchEntity) when calling the GetGroup operation: The group with name sim2real-xsvc-cfnkey-g-c7a42a938c67 cannot be found.). In that message the fixed text is "The group with name " ... " cannot be found." and the variable part is the GroupName taken from the request — here a per-run generated name, which is NOT part of the requirement. The AWS::IAM::Group resource type (and with it AWS::IAM::UserToGroupAddition, which cannot bind a non-existent group) is therefore reported as created while nothing was created; CloudFormation's own status surface and the IAM state disagree.
Why: a client that deploys its identity estate by CloudFormation and then operates on it by name gets a hard NoSuchEntity 404 from a stack CloudFormation told it was CREATE_COMPLETE. Every downstream step is unreachable: group membership cannot be read or asserted, the group's inline policy (Allow s3:*, explicit Deny s3:DeleteObject) is never part of the deployed key's effective permissions, so the whole explicit-Deny-beats-Allow evaluation path and the later implicit-deny path after the membership is dropped cannot be exercised at all. Infrastructure-as-code rollouts silently deploy a partial estate and only discover it when an unrelated call 404s.
Fix: the CloudFormation stack resource provisioner — the mapping from a template resource Type to a create call against the owning service's state — in the cloudformation service crate (services/service-com-amazonaws-cloudformation-cloudformation/src), for the AWS::IAM::Group and AWS::IAM::UserToGroupAddition types, writing into the IAM service's group state (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src) the same way the already-working AWS::IAM::User and AWS::IAM::AccessKey types do; and the stack status machine must not advance a resource to CREATE_COMPLETE when its provisioning was a no-op.
Traces: cloudformation__iam__s3.deploy-iam-2-cfn-group-explicit-deny-overrides-allow-for-deployed-access-key-denied (verdict error, raised at the check's first iam.get_group after asserting CREATE_COMPLETE and the stack Outputs).

Cause 2 of 2: the AWS::IAM::AccessKey Status / Serial rotation path never produces an observable verdict — the check is killed at the harness's 60 s ceiling.
AWS: AWS::IAM::AccessKey is an in-place update for the Status property and a replacement for the Serial property. Updating Status from Active to Inactive keeps the SAME access key id (Ref of the resource is unchanged, iam:ListAccessKeys reports that one key id with Status "Inactive"); a SigV4-signed S3 request made with a deactivated key is then refused with HTTP 403, error code InvalidAccessKeyId and the fixed message "The AWS Access Key Id you provided does not exist in our records." Bumping Serial replaces the resource: a NEW key id is created, the old one is deleted, iam:ListAccessKeys reports only the new key as Active, requests signed by the new key succeed and return the object's exact bytes, and requests signed by the replaced key are refused InvalidAccessKeyId with that same fixed message. Smithy: IAM ListAccessKeys/UpdateAccessKey model Status as statusType (Active|Inactive); S3's InvalidAccessKeyId code and message are recorded behavior of the signing path, not modeled members.
Emulator: the check does not reach any of those assertions. Replay verdict is error with detail "Check timed out after 60.0s" — the check is terminated at the harness ceiling having produced no response divergence to quote, after create_stack, the first signed GetObject settle, and the update_stack to Status: Inactive. The check's own internal budgets (a 180 s settle for the deactivated key, 300 s stack waits) all exceed that ceiling, so any step that does not settle promptly consumes the whole run. Hypothesis: the settle loop that polls a GetObject signed by the deactivated key for error code InvalidAccessKeyId never sees it, because the emulator's signing path does not consult the key's Status (an Inactive key keeps being honoured), so the loop runs to its own timeout and the harness kills it first. The replay output does not state this, so the fix must confirm which step stalls; what IS established is that this operation sequence yields no verdict at all.
Why: a client cannot use CloudFormation to deactivate or rotate credentials. If an Inactive key keeps being honoured, the deployment's single most security-relevant control — revoking a key by flipping Status, or retiring it by bumping Serial — is silently inert, and a key the client believes is dead still signs successful S3 requests. Even in the best case the sequence never settles, so no automation built on it can make progress.
Fix: the IAM access-key state and the request-signing credential lookup — the AWS::IAM::AccessKey update path in the CloudFormation resource provisioner (in-place for Status, replacement with deletion of the old key for Serial) in services/service-com-amazonaws-cloudformation-cloudformation/src, and the signature-verification/credential resolution shared by the S3 request path, which must refuse a key whose Status is Inactive or that no longer exists with 403 InvalidAccessKeyId and AWS's fixed message.
Traces: cloudformation__iam__s3.deploy-iam-2-cfn-access-key-deactivate-and-serial-rotation-old-key-rejected (verdict error, "Check timed out after 60.0s").
