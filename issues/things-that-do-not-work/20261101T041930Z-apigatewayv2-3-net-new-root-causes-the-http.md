# apigatewayv2: 3 net-new root causes — the HTTP_PROXY 10 MiB payload ceiling, the non-autoDeploy stage deployment snapshot, and the custom-domain API-mapping invoke flow all reach no verdict

> _Note: this issue was identified against the code base at commit `eb844afaf59a11d83d27e34f4871afac942136a7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
execute-api Invoke / CreateDeployment / CreateApiMapping

## Description
Three net-new root causes in the apigatewayv2 emulator, each grounded in a failing behavioral check that was NOT marked ALREADY FILED and is NOT owned by any open issue. All three replays end in `Check timed out after 60.0s`: the check's own polling helpers never reach an accepted answer, so the 60 s cap is hit without any assertion ever being evaluated.

Several open issues describe a neighbouring symptom — 20261024T120951Z-apigatewayv2-the-execute-api-data-plane-never-serves.md, 20261027T053233Z-apigatewayv2-an-http-api-aws-proxy-route-still.md, 20261029T194243Z-apigatewayv2-2-net-new-root-causes-an-http.md and 20261026T023803Z-apigatewayv2-custom-domain-and-api-mapping-control-plane.md — but none of them carries the replay keys below, and each cause here names a behaviour (the 10 MiB ceiling and its 413 envelope, deployment-snapshot pinning, the mapped-custom-domain invoke flow) that those issues do not state. They must be closed as three separate causes.

=== Cause 1 of 3: an HTTP_PROXY route never answers, so the HTTP API 10 MiB request-payload ceiling is never enforced and the 413 refusal envelope is never produced ===
Failing check: apigatewayv2.deep-apigatewayv2-2-enforce-payload-10mib-limit-413-not-delivered

AWS: An HTTP API route whose integration is `IntegrationType=HTTP_PROXY` with `IntegrationMethod=PUT` and an `IntegrationUri` pointing at an HTTPS origin forwards the request method, path and body to that origin and returns the origin's status and body to the caller. On top of that, HTTP APIs impose a non-adjustable maximum request payload size of 10 MB = 10 * 1024 * 1024 bytes (AWS doc: https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-quotas.html). A body of exactly 10485760 bytes is within the limit and is proxied byte-for-byte to the integration (200 from the origin, the origin object's length equals the body length and its ETag equals the MD5 of the body sent). A body of 10485761 bytes (limit + 1) is refused by the gateway BEFORE the integration is called, with HTTP status 413 and the gateway's JSON envelope body `{"message":"Request Entity Too Large"}` — the whole body is the fixed text `{"message":"Request Entity Too Large"}`; there are no variable parts. Because the refusal happens at the gateway, the integration target is never written: a repeat over-limit PUT leaves a previously delivered object completely untouched (same length, same ETag). Smithy: CreateIntegration.IntegrationType enum includes HTTP_PROXY; CreateIntegration.IntegrationUri target UriWithLengthBetween1And2048; CreateIntegration.PayloadFormatVersion StringWithLengthBetween1And64. The 10 MiB ceiling itself is NOT in the Smithy model — it is a service quota (recorded behavior / AWS quota doc only).
Emulator: The check never gets past its positive control. It first creates the API, two HTTP_PROXY integrations (`PUT /warm` and `PUT /upload`, each pointing at an S3 presigned PUT URL) and a `$default` stage with AutoDeploy=true, then polls `PUT <invoke-url>/warm` with a 4-byte body for a 200 (`_poll_http`, 150 s budget, accept = status == 200). No 200 ever arrives, so the replay is cut off by the suite's 60 s cap and NEITHER the 413 leg nor the exactly-10-MiB leg is ever reached. The emulator therefore has no observable 10 MiB enforcement and no 413 `Request Entity Too Large` envelope at all.
Why: A client that uploads through an HTTP_PROXY route gets nothing instead of its origin's response, so an HTTP_PROXY integration is unusable. Worse, a client relying on the gateway to be the size gate sees no 413 at all: an SDK/retry layer that treats 413 as terminal will instead hang or see an unrelated status, and an oversize body that AWS would have stopped at the edge can reach — and overwrite — the integration target, which is a correctness and a data-loss hazard, not just a status mismatch.
Fix: the execute-api data-plane request path for HTTP_PROXY integrations (forwarding method/path/body to IntegrationUri and returning the origin's status/body), plus a request-size gate in front of integration dispatch that rejects a body larger than 10 * 1024 * 1024 bytes with 413 and the fixed body `{"message":"Request Entity Too Large"}` before any integration call is made.

=== Cause 2 of 3: a stage pinned to a DeploymentId does not serve its deployment snapshot — the manual/autoDeploy stage split produces no verdict ===
Failing check: apigatewayv2.deep-apigatewayv2-3-stagesem-manual-stage-serves-deployment-snapshot

AWS: Stage semantics for HTTP APIs (https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-stages.html): a stage created with an explicit `DeploymentId` and without `AutoDeploy` serves the frozen snapshot of the API configuration captured by that deployment. Changing the API afterwards (here `UpdateIntegration` repointing `IntegrationUri` from function A to function B) must NOT change what that stage serves; its `GetStage.DeploymentId` must stay the deployment it was bound to until an explicit `CreateDeployment` is made. A sibling `$default` stage with `AutoDeploy=true` must pick the change up on its own and must have a NEW `DeploymentId` afterwards (`GetStage.AutoDeploy` true, `DeploymentId` changed). `CreateDeployment(ApiId, StageName=<pinned stage>)` must mint a new deployment id (different from the first), rebind that stage (`GetStage.DeploymentId` == the new id) and make it serve the new configuration. Smithy: CreateDeployment input {ApiId (httpLabel, required), Description, StageName (StringWithLengthBetween1And128)} -> output {DeploymentId (Id), AutoDeployed, CreatedDate, DeploymentStatus (enum), DeploymentStatusMessage, Description}, HTTP POST /v2/apis/{ApiId}/deployments, success code 201, errors BadRequestException(400)/ConflictException(409)/NotFoundException(404)/TooManyRequestsException(429); GetStage output carries `autoDeploy` and `deploymentId`, HTTP GET /v2/apis/{ApiId}/stages/{StageName}; UpdateIntegration is PATCH /v2/apis/{ApiId}/integrations/{IntegrationId} with IntegrationUri (UriWithLengthBetween1And2048).
Emulator: The check creates two Lambdas (A/B with distinct MARKER env values), one AWS_PROXY integration pointing at A, route `GET /snap`, an AutoDeploy `$default` stage, an explicit `CreateDeployment`, and a `pinned` stage bound to that deployment id. It then waits for BOTH stage URLs to serve `(200, markerA)` continuously (`_wait_stable`) before it will assert anything. That readiness gate never passes, so the replay hits the 60 s cap and the whole snapshot contract — hold the snapshot for 3x the measured autoDeploy latency, pinned `DeploymentId` unmoved, release on explicit `CreateDeployment` — is never observed. The emulator therefore exhibits no deployment-snapshot semantics for a non-autoDeploy stage.
Why: Deployment pinning is the mechanism clients use to keep production on a known-good snapshot while they edit the API. If a pinned stage does not freeze (or, as here, does not serve at all), a client's blue/green or canary flow silently loses its isolation: an in-progress edit can be exposed on a stage that was supposed to be frozen, or the stage serves nothing and the release never completes. `GetStage.DeploymentId` also stops being a trustworthy description of what a stage is serving.
Fix: the stage/deployment state model (binding a stage to a deployment snapshot of routes+integrations rather than to live config, minting a new deployment id on CreateDeployment and on autoDeploy, and rebinding the named stage when CreateDeployment carries StageName) plus the execute-api data-plane resolution step that must read the stage's snapshot, not current config, when dispatching.
Traces: apigatewayv2.deep-apigatewayv2-3-stagesem-manual-stage-serves-deployment-snapshot

=== Cause 3 of 3: a custom DomainName mapped to an HTTP API stage never routes HTTPS traffic to that stage, so the end-to-end mapping invoke flow reaches no verdict ===
Failing check: apigatewayv2.e2e-custom-domain-mapping-invoke-flow

AWS: `CreateDomainName` with `DomainNameConfigurations=[{CertificateArn, EndpointType: REGIONAL}]` creates a regional custom domain whose configuration converges to `DomainNameStatus=AVAILABLE` and exposes an `ApiGatewayDomainName` and a `HostedZoneId` usable as a Route 53 alias target. `CreateApiMapping(ApiId, DomainName, Stage)` then makes HTTPS requests that arrive at that domain route to the named stage: a request for a path the stage serves answers that stage's response (here 200 from a MOCK backend at `/ping`). `DeleteApiMapping` removes the mapping from the control plane immediately: the id disappears from `GetApiMappings.Items`, and `GetApiMapping` for it raises `NotFoundException` (HTTP 404) whose message is `Unable to find ApiMapping with ID <apiMappingId>` — the fixed text is `Unable to find ApiMapping with ID ` and the only variable part is the mapping id taken from the request. Smithy: GetDomainName output DomainNameConfigurations -> DomainNameConfiguration {apiGatewayDomainName, certificateArn, domainNameStatus (enum DomainNameStatus: AVAILABLE|UPDATING|PENDING_CERTIFICATE_REIMPORT|PENDING_OWNERSHIP_VERIFICATION), endpointType, hostedZoneId, securityPolicy}; GetApiMapping is GET /v2/domainnames/{DomainName}/apimappings/{ApiMappingId} with errors BadRequestException(400)/NotFoundException(404)/TooManyRequestsException(429); NotFoundException carries `message` and `resourceType`.
Emulator: The check imports a self-signed cert via ACM, calls CreateDomainName, then polls GetDomainName for `DomainNameConfigurations[0].DomainNameStatus == AVAILABLE` (300 s budget) to read `ApiGatewayDomainName`/`HostedZoneId`, builds an in-account Route 53 alias zone, resolves the address, creates the API mapping, and polls the HTTPS request to the mapped domain for a 200 (90 s budget). The replay never produces a verdict and is cut off at the 60 s cap, so neither the mapped-domain 200 nor the post-DeleteApiMapping control-plane assertions (absence from GetApiMappings, the `Unable to find ApiMapping with ID <id>` NotFoundException) are ever observed. Note: this check calls `require_tools("openssl")` and uses ACM/Route 53, but it fails with a timeout, not a missing-tool or resolution error — the hang is in the domain/mapping path itself, not in the runner's tooling.
Why: A custom domain plus an API mapping is the normal production front door for an HTTP API. If a mapped domain never routes to the stage, every client that addresses the API by its own hostname gets nothing, and the whole `CreateDomainName` -> `CreateApiMapping` flow is unusable. If `DomainNameStatus` never reaches AVAILABLE, client code that waits for readiness (as every SDK waiter and IaC provider does) blocks forever instead of proceeding.
Fix: the custom-domain and API-mapping handlers and their state (CreateDomainName/GetDomainName must converge DomainNameStatus to AVAILABLE and populate apiGatewayDomainName + hostedZoneId; CreateApiMapping/DeleteApiMapping/GetApiMappings must maintain the mapping set), plus the execute-api data-plane host-routing step that resolves an inbound Host header to the mapped (api, stage) pair; GetApiMapping's not-found path must raise NotFoundException/404 with the message `Unable to find ApiMapping with ID <apiMappingId>`.
Traces: apigatewayv2.e2e-custom-domain-mapping-invoke-flow

## Steps to Reproduce
Clone the repo, build and boot the emulator, then replay the behavioral suite (run_behavioral_suite) and look at these three check ids:

Cause 1 — apigatewayv2.deep-apigatewayv2-2-enforce-payload-10mib-limit-413-not-delivered:
1. CreateBucket (S3) and generate two presigned PUT URLs, for keys `warm` and `payload`.
2. CreateApi(ProtocolType='HTTP'); CreateIntegration(IntegrationType='HTTP_PROXY', IntegrationMethod='PUT', IntegrationUri=<presigned url>, PayloadFormatVersion='1.0') twice; CreateRoute 'PUT /warm' and 'PUT /upload' targeting them; CreateStage(StageName='$default', AutoDeploy=true).
3. PUT a 4-byte body to <invoke-url>/warm — expect 200 and HeadObject(key='warm').ContentLength == 4. Observed: no 200 ever arrives.
4. PUT 10*1024*1024+1 bytes to <invoke-url>/upload — expect 413 with body {"message":"Request Entity Too Large"} and HeadObject(key='payload') failing with code 404.
5. PUT exactly 10*1024*1024 bytes — expect 200, ContentLength == 10485760, ETag == MD5 of the body; then repeat step 4 and expect the object unchanged.

5. UpdateIntegration(IntegrationUri=<B>); expect $default to converge to markerB with a new GetStage('$default').DeploymentId while every sample of the pinned stage stays markerA and GetStage('pinned').DeploymentId == D1.
6. CreateDeployment(ApiId, StageName='pinned') -> D2 != D1; expect the pinned stage to serve markerB and GetStage('pinned').DeploymentId == D2.
