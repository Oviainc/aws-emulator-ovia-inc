# kinesis: 4 net-new root causes — ListChannels classifies a malformed NextToken as ExpiredNextTokenException, the PROVISIONED-without-ShardCount refusal message is emulator-authored, a retention change to the CURRENT value is refused instead of a no-op, and the HTTPS front door does not negotiate h2 by ALPN so SubscribeToShard has no HTTP/2 data plane

> _Note: this issue was identified against the code base at commit `7195bbe1a56e23a345d06755b702cd8074478e3d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListChannels, CreateStream, IncreaseStreamRetentionPeriod, DecreaseStreamRetentionPeriod, SubscribeToShard

## Description
Four root causes in the Kinesis Data Streams surface. All four are grounded in failing checks the replay report lists under `### kinesis` and marks NEITHER "ALREADY FILED" nor "OWNED by" — every other kinesis failure in this replay is owned by an existing issue. Open issue 20261103T071946Z-kinesis-4-net-new-root-causes-listchannels-misclassifies.md describes the same four causes but carries NO replay key (no check ids a fixer can re-replay); this issue re-files them WITH their replay keys so the fix can be gated, and is otherwise the same work item.

=== Cause 1 of 4: ListChannels classifies a syntactically-invalid NextToken as ExpiredNextTokenException ===
AWS: Smithy (com-amazonaws-kinesis-kinesis-20131202) binds BOTH ExpiredNextTokenException and ValidationException to ListChannels (plus AccessDeniedException, InvalidArgumentException, LimitExceededException), and models ListChannels.NextToken as NextToken @length min 1 max 1048576 with @paginated inputToken/outputToken NextToken. The two token error classes are not interchangeable: a well-formed token whose TTL has lapsed is ExpiredNextTokenException, whereas a string that is not a token at all is a request-shape defect — recorded behavior: HTTP 400 `ValidationException`, message `Invalid NextToken.` (that sentence is ENTIRELY fixed text; the offending token is NOT echoed and no value from the request appears in it).
Emulator: ListChannels(NextToken=<any string the emulator did not mint>) answers `ExpiredNextTokenException`. ListChannels with no token succeeds immediately before and after, so the misclassification is specific to the token-validation path, not a sick API.
Why: ExpiredNextTokenException is the signal a paginating client uses to RESTART the listing from page one — a client handed it for a corrupt or hand-written token loops forever re-listing instead of surfacing the caller's bug, and never sees the `Invalid NextToken.` diagnosis.
Fix: the NextToken decode/validation step of the ListChannels handler — separate "undecodable / not one of ours" (ValidationException, `Invalid NextToken.`) from "decoded but past its TTL" (ExpiredNextTokenException). Open issue 20261029T140704Z-kinesis-liststreamconsumers-misclassifies-a-malformed-nexttoken-as-expirednexttokenexception.md reports the same defect for ListStreamConsumers and does not cover the ListChannels call site.
Traces: kinesis.list-channels-malformed-next-token-rejected.

=== Cause 2 of 4: CreateStream's PROVISIONED-without-ShardCount refusal message is invented ===
AWS: Smithy models CreateStream.ShardCount as optional (PositiveIntegerObject, @range min 1) and StreamModeDetails as a separate optional member, so the pairing rule is a runtime validation, not a shape constraint; CreateStream's modeled errors are InvalidArgumentException, LimitExceededException, ResourceInUseException, ValidationException. Recorded behavior: CreateStream with StreamModeDetails.StreamMode=PROVISIONED and no ShardCount is refused HTTP 400 `InvalidArgumentException` with the message `ShardCount cannot be null when creating stream in PROVISIONED StreamMode` — entirely fixed text, with no stream name or value interpolated — and no stream is created (DescribeStreamSummary for that name is then ResourceNotFoundException `Stream <StreamName> under account <account id> not found.`, where <StreamName> comes from the request and <account id> from the caller).
Emulator: the right code and the right absence, but the message is `ShardCount is required for a PROVISIONED stream` — emulator-authored text AWS never serves for this error class.
Why: the error message is part of the contract; clients and operators that match or display AWS's sentence (and tests pinned to it) see text that is not AWS's.
Fix: the PROVISIONED/ShardCount pairing check in the CreateStream handler's validation — emit AWS's fixed sentence. Open issue 20261027T011654Z-kinesis-9-net-new-root-causes-dryrun-not.md covers the converse case (ON_DEMAND *with* ShardCount) and other invented CreateStream messages, not this one.
Traces: kinesis.provisioned-stream-created-without-a-shard-count-rejected.

=== Cause 3 of 4: a retention change naming the stream's CURRENT value is refused instead of accepted as a no-op ===
AWS: Smithy models IncreaseStreamRetentionPeriod and DecreaseStreamRetentionPeriod with required RetentionPeriodHours, output Unit, and errors AccessDeniedException, InvalidArgumentException, LimitExceededException, ResourceInUseException, ResourceNotFoundException. Recorded behavior: on a stream at the 24-hour default, BOTH increase_stream_retention_period(RetentionPeriodHours=24) and decrease_stream_retention_period(RetentionPeriodHours=24) SUCCEED as no-ops and the stream reads (ACTIVE, 24) after each. The guards are strict: Increase refuses only a requested value SHORTER than the current one, Decrease only one LONGER than it — the equal boundary is accepted on both paths.
Emulator: IncreaseStreamRetentionPeriod(24) against a 24-hour stream is refused HTTP 400 `InvalidArgumentException` with `Requested retention period (<requested> hours) for stream <stream name> can not be shorter than existing retention period (<current> hours). Use DecreaseRetentionPeriod API.` — the fixed frame is that sentence; <requested>, <current> and <stream name> are filled from the request and state, and in this check both numbers are the same value, so the message contradicts itself. The comparison is `<=`/`>=` where AWS uses strict `<`/`>`, dropping the equal case into the refusal branch.
Why: idempotent configuration appliers (Terraform/CDK/CloudFormation converge loops, retried control-plane calls) re-apply the desired retention on every run; AWS accepts that as a no-op while the emulator fails the apply, so an already-converged stream can never be re-applied.
Fix: the boundary comparison in the IncreaseStreamRetentionPeriod and DecreaseStreamRetentionPeriod handlers — accept requested == current on both. Open issue 20261027T095220Z-kinesis-6-net-new-root-causes-startstreamencryption-accepts.md covers a retention-too-short refusal, not the equal-value no-op.
Traces: kinesis.retention-change-to-current-value-is-accepted-no-op.

=== Cause 4 of 4: the HTTPS front door does not advertise h2 in ALPN, so SubscribeToShard's enhanced fan-out data plane is unreachable ===
AWS: Smithy models SubscribeToShard with required output member EventStream targeting SubscribeToShardEventStream marked @streaming — an `application/vnd.amazon.eventstream` response body — and the operation is offered ONLY over HTTP/2, so the endpoint must advertise `h2` in the TLS ALPN extension. Recorded behavior: a hand-signed HTTP/2 POST (X-Amz-Target: Kinesis_20131202.SubscribeToShard) is answered :status 200 with content-type `application/vnd.amazon.eventstream`, frames laid out [total_length:4][headers_length:4][prelude_crc:4][headers][payload][message_crc:4] (both CRCs CRC-32 over the preceding bytes, header value type 7 throughout), an `initial-response` message preceding the first SubscribeToShardEvent, and each event's JSON payload carrying :content-type `application/x-amz-json-1.1`.
Emulator: the server aborts the TLS handshake during ALPN with a fatal no_application_protocol alert (TLS alert number 120) — `SSL routines:ssl3_read_bytes:tlsv1 alert no application protocol` — when an HTTP/2 client connects to the emulator's own announced HTTPS endpoint. No HTTP/2 session can be established, no :status is ever seen and zero response bytes arrive, so the EFO data plane is unreachable regardless of the SubscribeToShard handler's state. The address is the one the emulator announced for itself, so this refusal is the emulator's, not the runner's network.
Why: every enhanced fan-out consumer (the KCL 2.x default, any SDK subscribeToShard call) needs h2 on this endpoint; with ALPN refusing it no EFO client can connect at all, and the event-stream framing/CRC contract above can never be served.
Fix: the HTTPS front door's TLS configuration — advertise `h2` alongside `http/1.1` in ALPN and serve HTTP/2 on the Kinesis endpoint so the streaming SubscribeToShard response can be framed. Related but distinct open issues: 20261101T034628Z-kinesis-the-https-front-door-aborts-the-tls.md (a different alert, decode_error, under concurrent PutRecords), and 20261027T201859Z-kinesis-4-net-new-root-causes-subscribetoshard-is.md / 20261029T174012Z-kinesis-subscribetoshard-answers-501-notimplemented-on-the-wire.md (the SubscribeToShard HANDLER over HTTP/1); the ALPN gap would still block EFO after the handler exists.
Traces: kinesis.subscribe-to-shard-event-stream-framing-over-a-hand-signed-http2-request.
