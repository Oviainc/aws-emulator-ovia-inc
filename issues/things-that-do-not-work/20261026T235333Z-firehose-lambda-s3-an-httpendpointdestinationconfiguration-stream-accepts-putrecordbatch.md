# firehose__lambda__s3: an HttpEndpointDestinationConfiguration stream accepts PutRecordBatch but never issues the documented HTTPS request to the endpoint (1 cause)

> _Note: this issue was identified against the code base at commit `da7bc09c8c1c199d36cb9fc39c5c5796d768dc3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRecordBatch

## Description
ONE net-new root cause: the Firehose HTTP-endpoint destination has no delivery path.

=== Cause 1 of 1: records put to a stream with an HttpEndpointDestinationConfiguration are accepted but no HTTPS request is ever sent to the configured Url ===
Failing check: firehose__lambda__s3.firehose-http-endpoint-request-envelope-conforms-to-the-documented-protocol.

AWS: Smithy (model_path services/service-com-amazonaws-firehose-firehose-20150804/smithy-model/com-amazonaws-firehose-firehose-20150804.json) HttpEndpointDestinationConfiguration has @required EndpointConfiguration (HttpEndpointConfiguration: Url, Name, AccessKey) and @required S3Configuration, plus BufferingHints (HttpEndpointBufferingHints: SizeInMBs @range 1..64 default 5, IntervalInSeconds @range 0..900 default 300), RequestConfiguration (HttpEndpointRequestConfiguration: ContentEncoding enum, CommonAttributes list length 0..50), RetryOptions, RoleARN and S3BackupMode (AllData | FailedDataOnly, "back up all documents or only the documents that Firehose could not deliver to the specified HTTP endpoint destination"). Firehose therefore POSTs each buffered batch to EndpointConfiguration.Url. The wire envelope is documented at docs.aws.amazon.com/firehose/latest/dev/httpdeliveryrequestresponse.html and the check records it as confirmed against real AWS (us-west-2, 2026-09-17, 409.9 s wall clock, PASS): headers X-Amz-Firehose-Protocol-Version: "1.0"; X-Amz-Firehose-Request-Id: an opaque GUID in 8-4-4-4-12 hex form; X-Amz-Firehose-Source-Arn: the stream's own DeliveryStreamARN as DescribeDeliveryStream reports it; X-Amz-Firehose-Access-Key: EndpointConfiguration.AccessKey copied verbatim, neither interpreted nor re-encoded; Content-Type: "application/json"; X-Amz-Firehose-Common-Attributes: the JSON object {"commonAttributes": {<AttributeName>: <AttributeValue>, ...}} built from RequestConfiguration.CommonAttributes; and NO Content-Encoding header at all when RequestConfiguration.ContentEncoding is NONE. The body is one JSON document {requestId, timestamp, records: [{data: <base64>}]} where requestId equals the X-Amz-Firehose-Request-Id header, timestamp is milliseconds since the epoch at which Firehose generated the request, each records[] entry has exactly the single member `data`, and that member base64-decodes to EXACTLY the bytes PutRecordBatch was given — no envelope, no appended delimiter. All of those values except AccessKey, the common attributes and the record bytes (which come from the request) and the ARN (which comes from the stream) are fixed text. Finally, a conforming 200 whose body echoes the requestId ENDS the attempt: nothing is copied to the S3 error prefix, and with S3BackupMode=FailedDataOnly nothing is copied to the backup prefix either.
Emulator: nothing is ever delivered. The check is cut off by the harness — "Error: Check timed out after 60.0s" — without reaching a single envelope assertion. Everything before the data plane is immediate and passes (sts.GetCallerIdentity, the Lambda function reaching State=Active, CreateFunctionUrlConfig returning an https:// Url, CreateDeliveryStream with the HttpEndpointDestinationConfiguration, DescribeDeliveryStream reporting ACTIVE with Destinations[0].HttpEndpointDestinationDescription.EndpointConfiguration.Url equal to the configured Url, and PutRecordBatch answering FailedPutCount=0 for 3 records). The only wait that can then consume the budget is the terminal data-plane poll _poll_until(_read_captures(...), budget_s=300) — the one whose own timeout message reads "DATAPLANE_UNIMPLEMENTED?: ... A target that accepts an HttpEndpointDestinationConfiguration and never issues an HTTPS request has no HTTP delivery path at all." Hypothesis: the HttpEndpoint destination is accepted and echoed by the control plane but is not wired to any delivery/flush implementation, so the buffered batch is never POSTed and the endpoint's capture objects never appear; the envelope itself is consequently unverified rather than wrong.
Why: the HTTP-endpoint destination is how Firehose feeds every third-party and custom sink (Datadog, Splunk, New Relic, a bespoke webhook). Against the emulator such a stream reports ACTIVE, echoes its Url, and answers PutRecordBatch with FailedPutCount=0 and a RecordId per record — indistinguishable from success — while the receiver gets nothing. A client therefore cannot test its endpoint's contract at all: not the headers it must authenticate on (X-Amz-Firehose-Access-Key), not the request/response correlation it must echo (requestId), not the retry/backup semantics of a non-conforming answer. Worse, because no failure is recorded either, the S3 error and backup prefixes stay empty, so the emulator asserts the "everything was delivered" state while delivering nothing.
Fix: the delivery/flush component of the Firehose service crate needs an HttpEndpoint destination writer alongside the S3 one: when a flush fires for a stream whose destination is HttpEndpointDestinationConfiguration, POST the buffered batch to EndpointConfiguration.Url with the documented headers (protocol version, a freshly minted GUID request id, the stream's own ARN, the configured AccessKey verbatim, Content-Type application/json, the CommonAttributes object, and no Content-Encoding when ContentEncoding is NONE) and the documented body ({requestId, timestamp, records:[{data}]} with the record bytes base64-encoded and nothing else), then treat a 200 whose body echoes the requestId as success — not copying the batch to the error prefix, and honouring S3BackupMode (AllData vs FailedDataOnly) for what reaches S3. Flush timing must come from HttpEndpointBufferingHints (defaults 5 MiB / 300 s).
