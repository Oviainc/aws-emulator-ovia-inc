# lambda: 2 net-new causes — an Invoke inside the LastUpdateStatus=InProgress window already serves the NEW code, and VpcConfigResponse omits VpcId after a VpcConfig attach

> _Note: this issue was identified against the code base at commit `6b512def31f7223c9d34f1f96480dd1fa7227928`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateFunctionCode

## Description
Two distinct net-new root causes in the Lambda emulation's function-state machine, both grounded in the failing checks named per cause. Neither failing check is marked ALREADY FILED or OWNED in the replay report.

Cause 1 of 2 — an Invoke made while LastUpdateStatus=InProgress is served by the NEW code instead of the previously deployed package.
AWS: Smithy: FunctionConfiguration.LastUpdateStatus is the enum LastUpdateStatus with values Successful | Failed | InProgress, and UpdateFunctionCode/UpdateFunctionConfiguration model ResourceConflictException (httpError 409). AWS's function-states contract (https://docs.aws.amazon.com/lambda/latest/dg/functions-states.html) is that an update on an Active function leaves State=Active and sets LastUpdateStatus=InProgress; during that window the function stays invokable and an invocation runs the code that was already deployed, and the newly uploaded package only serves once LastUpdateStatus becomes Successful (at which point CodeSha256 is the new package's). A competing mutation inside the window is refused 409 ResourceConflictException whose message is the fixed text "The operation cannot be performed at this time. An update is in progress for resource: " followed by the function ARN taken from the request/state. The emulator already satisfies the state reporting and the 409 refusal — only which code runs diverges.
Emulator: inside the same InProgress window (the check re-reads GetFunctionConfiguration after the Invoke returns and only grades probes that provably landed inside the window), the invocation already runs the package that is still being deployed. Replay: `AssertionError: Invoke while the padded update is InProgress must be served by the PREVIOUS code ('old-v1'), got 'new-v2'` — the handler returned the new marker while LastUpdateStatus was still InProgress.
Why: the code swap is not atomic with the update's completion. A client that follows AWS's documented pattern — issue UpdateFunctionCode, then wait for LastUpdateStatus=Successful before shifting traffic — has already been serving the new code for the whole window, so a canary/blue-green or a rollback-on-failure flow cannot bound when the swap happened, and an update that ends Failed would have served code that was never accepted.
Fix: the UpdateFunctionCode handler and the function's code resolution in state/the invoke path — stage the uploaded package and keep resolving invocations to the last settled code revision until the update transitions out of InProgress.
Traces: lambda.deep-lambda-1-fn-state-padded-code-update-in-progress-serves-previous-code.

Cause 2 of 2 — the VpcConfig a function is attached to reads back without VpcId.
AWS: Smithy: VpcConfigResponse has members SubnetIds, SecurityGroupIds, VpcId ("The ID of the VPC") and Ipv6AllowedForDualStack; FunctionConfiguration.VpcConfig (returned by UpdateFunctionConfiguration, GetFunctionConfiguration and GetFunction) is that shape. UpdateFunctionConfiguration accepts a VpcConfig naming only SubnetIds and SecurityGroupIds, and the service resolves the VPC that owns those subnets and reports it as VpcConfig.VpcId on every subsequent read; before any attachment VpcConfig carries no VpcId.
Emulator: after attaching a VpcConfig to an Active function and after the update settles LastUpdateStatus=Successful, the read-back VpcConfig has no VpcId member at all. Replay: `KeyError: 'VpcId'` at `assert settled["VpcConfig"]["VpcId"] == vpc_id` — VpcConfig is present but the modeled VpcId member is absent, so the ID of the VPC the function is now attached to is unreadable.
Why: a client cannot discover which VPC its function is attached to; any read of VpcConfig.VpcId raises KeyError (SDKs surface the member as absent rather than as the VPC id), and configuration round-trips plus every VPC/ENI-dependent branch built on it break.
Fix: the VpcConfig write in the UpdateFunctionConfiguration handler (resolve the owning VPC from the named subnets) and the FunctionConfiguration/VpcConfigResponse serializer so VpcId is emitted. Related but not covering: open issue 20261023T114649Z-lambda-function-urls-unrouted-configuration-blocks-dropped-from.md, whose Cause 2 describes configuration blocks dropped from reads on the CreateFunction path (VpcConfig wholly absent or empty); here VpcConfig is returned on the update path and only the VpcId member is missing, and the check below is not owned by that issue.
Traces: lambda.deep-lambda-1-fn-state-vpc-attach-in-progress-invoke-allowed-code-update-rejected.

## Evidence
Cause 1: expected — an Invoke issued while GetFunctionConfiguration reports LastUpdateStatus=InProgress runs the previously deployed package (marker 'old-v1'), and only after LastUpdateStatus=Successful does the new package (marker 'new-v2', CodeSha256 = the uploaded zip's base64 SHA-256) serve. Actual — the mid-flight Invoke returned the in-flight package's marker: `AssertionError: Invoke while the padded update is InProgress must be served by the PREVIOUS code ('old-v1'), got 'new-v2'`. The surrounding legs pass: UpdateFunctionCode starts the update, an independent GetFunctionConfiguration shows LastUpdateStatus=InProgress with State=Active, and the competing UpdateFunctionCode inside the window is refused 409 ResourceConflictException with "The operation cannot be performed at this time. An update is in progress for resource: <function ARN>" (fixed text; the ARN is the value from state). The markers 'old-v1'/'new-v2' and the ~10MB padded package are the check's own values, not part of the requirement — the requirement is that the code serving an invocation does not change before the update leaves InProgress.

Cause 2: expected — after UpdateFunctionConfiguration(FunctionName, VpcConfig={SubnetIds=[...], SecurityGroupIds=[...]}) settles LastUpdateStatus=Successful, GetFunctionConfiguration returns VpcConfig with SubnetIds, SecurityGroupIds and VpcId set to the id of the VPC that owns those subnets. Actual — VpcConfig is returned without a VpcId member: `KeyError: 'VpcId'` raised at `settled["VpcConfig"]["VpcId"]`. The pre-attach read correctly shows no VPC attachment. The specific VPC id in the run is request/state data filling the template, not a requirement; the requirement is that VpcId is present and names the subnets' VPC.

## Steps to Reproduce
Cause 1: (1) CreateFunction with a python handler returning marker 'old-v1'; wait State=Active. (2) Invoke — confirm 'old-v1'. (3) UpdateFunctionCode with a large (≈10MB, STORED/incompressible) zip whose handler returns 'new-v2', so the update stays in flight. (4) GetFunctionConfiguration — LastUpdateStatus=InProgress, State=Active. (5) Invoke inside that window and then re-read GetFunctionConfiguration to confirm LastUpdateStatus is still InProgress: the Invoke returns 'new-v2', where AWS serves 'old-v1'. (6) After the update settles Successful, Invoke returns 'new-v2' and CodeSha256 is the padded package's digest.

Cause 2: (1) Create a VPC with two subnets and a security group. (2) CreateFunction (no VpcConfig); wait State=Active; confirm VpcConfig carries no VpcId. (3) UpdateFunctionConfiguration(FunctionName=fn, VpcConfig={"SubnetIds": subnet_ids, "SecurityGroupIds": [sg_id]}). (4) Poll GetFunctionConfiguration until LastUpdateStatus=Successful. (5) Read response["VpcConfig"]["VpcId"] — the member is absent (KeyError) instead of naming the subnets' VPC.
