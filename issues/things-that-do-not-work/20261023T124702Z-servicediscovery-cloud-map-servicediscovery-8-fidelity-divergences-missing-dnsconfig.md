# Cloud Map (servicediscovery): 8 fidelity divergences — missing DnsConfig/instance-attribute validation, over-strict ListNamespaces filter validation, synchronous namespace delete, non-derived Service Id, CFN-created namespace undiscoverable, and wrong error message bodies

> _Note: this issue was identified against the code base at commit `001920e7906d433f041aca694d32f13b44f642fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateService (bundle: RegisterInstance, ListNamespaces, CreatePrivateDnsNamespace, DeleteNamespace, DiscoverInstances, GetService, GetInstance, UpdateInstanceCustomHealthStatus, DeleteService, GetServiceAttributes, UpdateHttpNamespace)

## Description
Eight independent root causes in the servicediscovery (Cloud Map) emulator, all found by the behavioral replay against the bootstrapped service. They are numbered below; each must be closed before this issue is submitted. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json.

Cause 1 of 8: CreateService does not reject a CNAME DnsRecord paired with the MULTIVALUE routing policy.
AWS: Smithy CreateService.DnsConfig -> DnsConfig{RoutingPolicy: RoutingPolicy enum [MULTIVALUE, WEIGHTED], DnsRecords: DnsRecordList of RecordType [SRV, A, AAAA, CNAME]}; CreateService models InvalidInput (HTTP 400). DnsConfig.RoutingPolicy documentation states a CNAME service must use WEIGHTED. The recording shows HTTP 400 InvalidInput, message example 'WEIGHTED routing policy must be used with DNS Record Type CNAME'.
Emulator: returns HTTP 200 with a fully-formed Service (Type DNS_HTTP, DnsConfig RoutingPolicy MULTIVALUE, DnsRecords [{Type: CNAME, TTL: 60}]).
Why: a client that relies on AWS refusing this combination silently gets a service whose DNS records can never be created, so the failure surfaces later (or never) instead of at the create call; negative tests of this rejection pass against the emulator and fail against AWS.
Fix: CreateService's input validation (the handler's pre-store checks, which today validate only tags, health-check exclusivity, namespace presence and hosted-zone presence).
Traces: servicediscovery.create-service-invalid-dns-config-rejected; handler services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/src/ops/create_service.rs lines 197-280 contain the only validation performed.

Cause 2 of 8: RegisterInstance does not enforce the record-type-required attributes of the target service's DnsConfig.
AWS: Smithy RegisterInstance.Attributes (required, Attributes map) documentation: 'AWS_INSTANCE_IPV4 ... This value is required if the service specified by ServiceId includes settings for an A record'; RegisterInstance models InvalidInput (HTTP 400). Recorded response: HTTP 400 InvalidInput, message example 'Required attribute(s) AWS_INSTANCE_IPV4 are missing.'
Emulator: for a service created with DnsConfig {DnsRecords: [{Type: A, TTL: 60}], RoutingPolicy: WEIGHTED}, RegisterInstance with Attributes={'unrelated': 'x'} answers HTTP 200 and an OperationId, and the instance is registered.
Why: a caller that omits the address attribute gets an instance registered that no DNS record can represent; the API's own contract (attribute required per record type) is unenforced, so client-side bugs pass silently.
Fix: RegisterInstance's validation, which must read the target service's DnsConfig record types and require AWS_INSTANCE_IPV4 / AWS_INSTANCE_IPV6 / AWS_INSTANCE_CNAME / AWS_INSTANCE_PORT accordingly (or accept AWS_ALIAS_DNS_NAME as the documented alternative).
Traces: servicediscovery.register-instance-missing-required-attribute-rejected; handler .../src/ops/register_instance.rs.

Cause 3 of 8: ListNamespaces rejects a well-formed TYPE filter whose Values are outside the namespace-type set, instead of returning an empty page.
AWS: Smithy ListNamespaces.Filters -> NamespaceFilters of NamespaceFilter{Name: NamespaceFilterName enum [TYPE, NAME, HTTP_NAME, RESOURCE_OWNER] (required), Values: FilterValues (required, an unconstrained string list), Condition: FilterCondition}. Values is NOT an enum in the model, and the recording shows Filters=[{Name: TYPE, Values: ['NOT_A_REAL_NAMESPACE_TYPE'], Condition: EQ}] accepted with HTTP 200 and an empty Namespaces list.
Emulator: answers HTTP 400 InvalidInput — 'Filters.Values NOT_A_REAL_NAMESPACE_TYPE isn't a valid namespace type. Valid values are DNS_PRIVATE, DNS_PUBLIC, HTTP.' (the replay aborts on this call, which the check uses as a positive control).
Why: list calls that pass through a caller-supplied or future type value break against the emulator where AWS simply matches nothing; an over-strict refusal on an unconstrained member turns a successful empty page into a client error.
Fix: ListNamespaces' filter validation — validate the filter Name against the NamespaceFilterName enum and the Name/Condition pairing, but treat Values as opaque match terms.
Traces: servicediscovery.list-namespaces-invalid-input-error; handler .../src/ops/list_namespaces.rs.

Cause 4 of 8: CreatePrivateDnsNamespace's async Operation reports SUCCESS when its Vpc does not exist.
AWS: Smithy CreatePrivateDnsNamespace{Name (required, pattern ^(?!arn:)[!-~]{1,253}$), Vpc: ResourceId (required)} -> OperationId; the namespace only exists once GetOperation reports a terminal state. Recorded behavior only: with Vpc='vpc-0123456789abcdef0' (a VPC that does not exist) the operation reaches terminal Status='FAIL' because the hosted-zone-association step cannot complete; the synchronous call itself still returns an OperationId.
Emulator: GetOperation for that OperationId reaches Status='SUCCESS' with ErrorMessage=None.
Why: the async failure channel of this operation is unobservable — a client that polls GetOperation to learn whether its private namespace was really created is told it succeeded, and then finds a namespace bound to a VPC that does not exist. Any test of operation FAIL handling passes vacuously.
Fix: CreatePrivateDnsNamespace's async-operation state machine — the operation's target VPC must be resolved when the operation is advanced, and the operation must land FAIL with an ErrorCode/ErrorMessage when it is absent.
Traces: servicediscovery.create-namespace-invalid-dns-name-rejected (the InvalidInput name rejection in the same check passes; only the async-FAIL assertion fails); handler .../src/ops/create_private_dns_namespace.rs plus the operation store in .../src/state.rs.

Cause 5 of 8: DeleteNamespace applies the deletion synchronously, before its Operation reaches a terminal state.
AWS: Smithy DeleteNamespace{Id (required)} -> OperationId, errors DuplicateRequest 409 / InvalidInput 400 / NamespaceNotFound 404 / ResourceInUse 409. Recorded behavior only: while GetOperation for the returned OperationId still reports SUBMITTED or PENDING, GetNamespace(Id) still returns the Namespace; NamespaceNotFound starts only after the operation reports SUCCESS.
Emulator: GetNamespace(Id) raises NamespaceNotFound (HTTP 404) while the delete Operation is still SUBMITTED/PENDING — the record is removed inside the DeleteNamespace call itself.
Why: clients that implement the documented poll-then-confirm pattern see a 404 they treat as a hard error in the middle of a normal delete, and the pre-SUCCESS invariant (resource still readable) cannot be relied on.
Fix: DeleteNamespace's handler/state transition — mark the namespace as deleting and apply the removal when the operation is advanced to SUCCESS, not at request time.
Traces: servicediscovery.namespace-delete-async-operation-completes; handler .../src/ops/delete_namespace.rs plus .../src/state.rs.

Cause 6 of 8: a Service Id is minted at random instead of being derived from Name + NamespaceId, so an identical re-create after delete returns a different Id.
AWS: recorded behavior only — after DeleteService, re-creating the same Name in the same NamespaceId returns the SAME Service Id as the first create (the recording shows Id 'srv-n52nc4hipafj08f3' both times). Hypothesis: AWS derives the service identifier from Name+NamespaceId rather than from a random sequence.
Emulator: the second CreateService returns a fresh random Id ('srv-5vwrm045zi6zk2pn'); .../src/ops/create_service.rs calls state.next_id("srv", 16).
Why: a client or IaC layer that caches/reconstructs the Service Id for a known Name+Namespace pair (or asserts idempotent re-create) diverges from AWS after any delete/re-create cycle.
Fix: the Service Id derivation in CreateService / the id allocator in state.rs.
Traces: servicediscovery.create-service-lifecycle (every other assertion in the check — synchronous create, GetService shape, ServiceNotFound after delete — passes).

Cause 7 of 8: resources deployed through CloudFormation's AWS::ServiceDiscovery::* types are not usable through the Cloud Map data plane.
AWS: Smithy DiscoverInstances{NamespaceName (required), ServiceName (required)} -> Instances, errors InvalidInput 400 / NamespaceNotFound 404 / ServiceNotFound 404 / RequestLimitExceeded 429. Recorded behavior: a stack containing AWS::ServiceDiscovery::HttpNamespace + ::Service + ::Instance reaches CREATE_COMPLETE, and DiscoverInstances(NamespaceName=<the stack's namespace name>, ServiceName=<the stack's service name>, HealthStatus=ALL) returns the declared instance with its InstanceAttributes (custom-attr='cfn-value').
Emulator: the stack reaches CREATE_COMPLETE and publishes NamespaceId/ServiceId outputs, but DiscoverInstances answers HTTP 404 NamespaceNotFound (empty message), so nothing the stack declared exists in the Cloud Map store.
Why: CFN-provisioned service discovery is behaviorally dead — the control-plane stack says the resources exist while every data-plane lookup 404s, so any deploy-then-use flow breaks. Related but not the same as the open issue 20261023T114649Z-cloudformation-outputs-carry-no-outputvalue-failed-resources-never (outputs were present here); the gap is that the AWS::ServiceDiscovery::* resource providers do not create records in the servicediscovery state (or DiscoverInstances cannot resolve them by NamespaceName).
Fix: the CFN resource providers for AWS::ServiceDiscovery::HttpNamespace/Service/Instance must create the same records the native CreateHttpNamespace/CreateService/RegisterInstance handlers create, and DiscoverInstances must resolve a namespace by its name.
Traces: servicediscovery.deploy-http-namespace-service-via-cloudformation; handler .../src/ops/discover_instances.rs and the CloudFormation resource-provider registry.

Cause 8 of 8: the Message body of Cloud Map's not-found / conflict / filter-validation errors is emulator-authored prose instead of the per-operation message AWS builds from the request.
AWS: the status and error code match in every case below; only the Message diverges. The message rule is per-operation and is built from the request (or deliberately empty), consistently across several independent recordings: GetService / GetServiceAttributes -> ServiceNotFound (404) with an EMPTY message; GetNamespace -> NamespaceNotFound (404) with an EMPTY message; UpdateHttpNamespace on a deleted namespace -> NamespaceNotFound (404) whose message is the namespace id; RegisterInstance on a deleted service -> ServiceNotFound (404) whose message is the service ARN; GetInstance after deregister -> InstanceNotFound (404) whose message is the instance id; UpdateInstanceCustomHealthStatus on a service with no HealthCheckCustomConfig -> ServiceNotFound (404) whose message is "no service '<service ARN>'"; GetInstancesHealthStatus for such an instance -> InstanceNotFound (404) whose message is "Instance(s) not found for service '<service ARN>' when trying to retreive: <instanceId>" (AWS's own spelling); DeleteService with a registered instance -> ResourceInUse (409) message 'Service contains registered instances; delete the instances before deleting the service'; DeleteNamespace with an associated service -> ResourceInUse (409) message 'Namespace has associated services; delete the services before deleting the namespace'; ListNamespaces with NAME+BETWEEN -> InvalidInput (400) message naming the filter and its supported conditions, recorded as 'Invalid filter condition(s) provided: filter NAME supports condition(s) [BEGINS_WITH, EQ], but got BETWEEN; '.
Emulator: substitutes its own prose and never the empty message, e.g. 'No service exists with the specified ID srv-...', 'No instance exists with the specified ID <id> in service srv-...', "The service srv-... can't be deleted because it still contains 1 registered instance(s).", "The namespace ns-... can't be deleted because it still contains 1 service(s).", "Filters.Condition BETWEEN isn't supported for a namespace filter. Valid values are EQ and BEGINS_WITH.", and an empty message where AWS puts the namespace id (UpdateHttpNamespace).
Why: clients and test suites that parse these messages for the resource identifier (the id/ARN AWS echoes) or that assert the documented conflict text get a different payload; the recorded texts above are the templates to reproduce, not one recording's values (ids, region and account come from the request).
Fix: the error construction in each named operation's handler (and the shared message constants in .../src/state.rs, e.g. SERVICE_ALREADY_EXISTS_MESSAGE-style constants) so each error carries the per-operation message rule above.
Traces: servicediscovery.custom-health-status-not-configured-error, servicediscovery.custom-health-status-without-custom-health-config-rejected, servicediscovery.delete-namespace-with-active-service-rejected, servicediscovery.delete-service-in-use-conflict, servicediscovery.e2e-service-discovery-full-lifecycle-flow, servicediscovery.list-namespaces-invalid-filter-error, servicediscovery.register-deregister-instance-lifecycle, servicediscovery.service-attributes-crud, servicediscovery.service-attributes-delete-unknown-key-idempotent, servicediscovery.update-http-namespace-description.
