# cloudwatch: a metric-math (Metrics[]) alarm reaches OK with an EMPTY StateReasonData.recentDatapoints — the expression is never graded, the state comes from the missing-data policy

## Description
ONE net-new root cause in the CloudWatch alarm evaluation engine, grounded in a failing behavioral check this replay marked NEITHER 'ALREADY FILED' NOR 'OWNED by' any open issue. The bundle carries exactly one cause.

=== Cause 1 of 1: an alarm defined over a Metrics[] metric-math expression transitions to an evaluated state whose StateReasonData.recentDatapoints is EMPTY — the computed expression is never evaluated into a decision window ===
Failing check id: cloudwatch.metric-math-alarm-evaluates-the-computed-expression-not-its-inputs

AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) models PutMetricAlarm.Metrics as an array of MetricDataQuery structures; its documentation states 'One item in the Metrics array is the expression that the alarm watches. You designate this expression by setting ReturnData to true for this object in the array', and 'If you use the Metrics parameter, you cannot include the Namespace, MetricName, Dimensions, Period, Unit, Statistic, or ExtendedStatistic parameters of PutMetricAlarm in the same operation.' EvaluationPeriods and DatapointsToAlarm are @range min 1; MetricAlarm.StateReasonData is documented 'An explanation for the alarm state, in JSON format.' The content of that JSON is recorded behavior only: for an alarm whose watched series is the ReturnData=true expression item, every evaluated verdict carries StateReasonData.recentDatapoints holding exactly EvaluationPeriods per-period values of the COMPUTED EXPRESSION (not of its ReturnData=false source metrics), plus .threshold echoing the alarm's own Threshold and .evaluatedDatapoints holding the datapoints that justified the verdict. In the recording the expression is '(errors / requests) * 100' over two Maximum source series, so the OK verdict's single recentDatapoint is the expression result (errors/requests*100) and the later ALARM verdict's is the breaching expression result — the particular numbers 25.0/75.0, the 5/15/20 source values, the Threshold 50.0 and the generated namespace/alarm names are that run's filling of the template; the requirement is len(recentDatapoints) == EvaluationPeriods and each value equal to the expression computed over the stored source series for that period.

Emulator: PutMetricAlarm accepts the Metrics[] array and DescribeAlarms echoes all three query ids ('errors'/'requests' with ReturnData False, 'rate' with Expression '(errors / requests) * 100' and ReturnData True), reports no scalar MetricName/Namespace/Statistic, and starts the alarm in INSUFFICIENT_DATA — all of that is correct. The alarm then DOES move to StateValue 'OK', but its StateReasonData.recentDatapoints is the EMPTY list: the check fails at the first verdict assertion with 'AssertionError: the OK verdict evaluated 0 datapoints []; EvaluationPeriods=1 means exactly one'. So the state change was not produced by grading the expression over a decision window — zero datapoints were evaluated for a 1-period alarm, i.e. the evaluator reached its verdict from the TreatMissingData='notBreaching' policy with an empty window rather than from the metric-math result. Everything downstream is therefore never reached: the ALARM leg where the expression crosses the threshold while every raw input stays below it, the echoed .threshold in the ALARM decision, the DescribeAlarmHistory StateUpdate item whose oldState is OK and whose newState.stateReasonData.recentDatapoints must contain the computed value, and the two refusal arms (Metrics combined with Namespace/MetricName/Statistic/Period must be refused 'ValidationError' / 'MetricName should not be set if list of Metrics is set.', and a Metrics array with no ReturnData=true item must be refused 'ValidationError' / 'Exactly one element of the metrics list should return data.') — all fixed text with no variable parts.

Why: a client that alarms on a ratio or rate (error rate, p99 over throughput, any expression) gets an alarm that changes state without ever computing the expression. The state is whatever the missing-data policy yields, so an alarm whose expression is breaching can report OK (and vice versa), and every consumer that reads StateReasonData to explain or audit a verdict — dashboards, runbooks, incident tooling — sees an empty window and cannot tell the alarm from one that has no data at all. Because the window is empty rather than wrong, M-of-N and TreatMissingData also silently mean something else than on AWS for every math alarm.

Fix: the CloudWatch alarm evaluation engine in the cloudwatch service crate — the evaluator must take the Metrics[] path, resolve the MetricDataQuery closure through the metric-math engine (bucketing each ReturnData=false MetricStat by its own Period/Stat and then computing the ReturnData=true expression per period), materialise exactly EvaluationPeriods expression values as the decision window, grade that window against Threshold/ComparisonOperator, and render StateReason/StateReasonData (recentDatapoints, evaluatedDatapoints, threshold) from it on the DescribeAlarms and DescribeAlarmHistory read paths instead of falling through to the missing-data policy with an empty window. The PutMetricAlarm handler's storage and echo of Metrics[] are already correct, so no input-side change is needed for the positive arm; the two refusal arms belong in PutMetricAlarm validation.
