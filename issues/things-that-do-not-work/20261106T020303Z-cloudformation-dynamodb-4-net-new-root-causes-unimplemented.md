# cloudformation__dynamodb: 4 net-new root causes — unimplemented AWS::DynamoDB::Table properties fail the stack, the KeySchema/AttributeDefinitions failure text is DynamoDB's instead of the CFN handler's, a KeySchema edit is classified Replacement=False instead of Conditional, and an unknown Fn::GetAtt attribute is accepted

> _Note: this issue was identified against the code base at commit `cc6137e930728edc173d6e704b5a7c1716e7fffd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Four net-new behavioral root causes of service `cloudformation__dynamodb`, grounded in eight failing behavioral checks. A fixer must close all four before submitting.

Cause 1 of 4: the AWS::DynamoDB::Table resource provider refuses template properties it does not implement instead of applying them, so any table declaring TimeToLiveSpecification, StreamSpecification, SSESpecification, ContributorInsightsSpecification, TableClass or a GSI alongside them fails to create and the stack rolls back.
AWS: all of these are supported AWS::DynamoDB::Table properties. Smithy (dynamodb) CreateTable accepts StreamSpecification, SSESpecification, TableClass, GlobalSecondaryIndexes and ProvisionedThroughput directly; TimeToLiveSpecification is applied post-create by UpdateTimeToLive and contributor insights by UpdateContributorInsights. The stack reaches CREATE_COMPLETE and the live table reports each setting: DescribeTable carries LatestStreamArn/StreamSpecification, SSEDescription, TableClassSummary and the GSI, and DescribeTimeToLive reports ENABLED on the attribute the template named. AWS emits no error for any of them.
Emulator: the Table resource goes CREATE_FAILED and the stack ends ROLLBACK_COMPLETE with the aggregate stack reason `The following resource(s) failed to create: [Table]. `; the per-resource reason is the emulator's own self-announced refusal `Resource handler returned message: "this emulator does not apply the <PropertyName> property of AWS::DynamoDB::Table" (HandlerErrorCode: InvalidRequest)` (the wording captured verbatim for PointInTimeRecoverySpecification under the `cloudformation` heading in the companion issue filed in this sweep). The fixed text is `this emulator does not apply the ` + the property name + ` property of AWS::DynamoDB::Table`; the property name is taken from the template and the RequestToken is per-run.
Why: no realistic DynamoDB template deploys — TTL, streams, encryption and table class are the ordinary properties of a production table — and the client is told with HandlerErrorCode InvalidRequest that its own valid template is wrong. Downstream, Fn::GetAtt StreamArn can never resolve because the streamed table never exists.
Fix: the AWS::DynamoDB::Table resource provider in the cloudformation resource-provisioning layer — apply each of these properties (post-create UpdateTimeToLive / UpdateContributorInsights, and the CreateTable members for stream, SSE, class and GSIs) instead of raising an unsupported-property refusal.
Traces: cloudformation__dynamodb.cfn-unsupported-table-property-is-not-silently-discarded (TimeToLiveSpecification), cloudformation__dynamodb.deploy-cfn-dynamodb-getatt-stream-arn-follows-stream-view-change (StreamSpecification NEW_AND_OLD_IMAGES), cloudformation__dynamodb.deploy-cfn-dynamodb-table-settings-apply-and-flip-in-place (KMS SSE, TTL, PITR, contributor insights, STANDARD_INFREQUENT_ACCESS class, KEYS_ONLY GSI).

Cause 2 of 4: when a KeySchema names an attribute absent from AttributeDefinitions, the CREATE_FAILED reason is DynamoDB's index-level validation string rather than the CloudFormation handler message that states the rule.
AWS: recorded behavior only (StackEvent.ResourceStatusReason is a free string; Smithy dynamodb CreateTable does not model this refusal — ValidationException is a common error). The resource's CREATE_FAILED event carries the fixed text `Resource handler returned message: "An attribute referenced in a KeySchema element is not defined in AttributeDefinitions"` with HandlerErrorCode `InvalidRequest`; the message names no attribute and no index — it states the rule — and it is a resource-handler failure, so it sits on the resource event, with the stack-level reason being the aggregate `The following resource(s) failed to create: [<logical ids>]. Rollback requested by user.`
Emulator: the reason is `Resource handler returned message: "Invalid KeySchema: Some index key attribute have no definition" (RequestToken: <per-run token>, HandlerErrorCode: InvalidRequest)` — DynamoDB's own index-oriented string, which names the wrong rule (there is no index in these templates) and is not the text CloudFormation surfaces.
Why: the reason is the only thing distinguishing a template defect from a throttle, a quota or a permission failure — all of which also end in ROLLBACK_COMPLETE. A client (or CI gate) matching on the documented rule text cannot classify the failure, and the message it does get points at an index that does not exist.
Fix: the AWS::DynamoDB::Table resource provider's pre-flight validation in the cloudformation resource-provisioning layer — emit the CloudFormation handler message for the KeySchema/AttributeDefinitions rule rather than passing through DynamoDB's index validation string.
Traces: cloudformation__dynamodb.cfn-key-schema-without-attribute-definition-fails-the-stack, cloudformation__dynamodb.deploy-dynamodb-2-multi-resource-rollback, cloudformation__dynamodb.deploy-dynamodb-2-update-rollback-removes-added-table.

Cause 3 of 4: a change set that edits a table's KeySchema from a template parameter is classified Replacement=False, so a replacement that will actually be refused is previewed as a harmless in-place modify.
AWS: Smithy (cloudformation) ResourceChange.Replacement is the enum `True | False | Conditional`, and its documentation states the rule: when RequiresRecreation is `Always` and Evaluation is `Dynamic` — exactly a KeySchema change whose value comes from a Parameter — Replacement is `Conditional`. DescribeChangeSet therefore reports Replacement=Conditional for the table whose key attribute changes, and executing it against a custom-named table is then refused (CloudFormation cannot replace a resource whose name is set explicitly), leaving the resource and its items intact.
Emulator: DescribeChangeSet reports `Replacement='False'` for that resource change.
Why: Replacement is the field every reviewer and every CI gate reads before executing a change set. `False` promises the resource and its data survive; the change set then either replaces or refuses, so the preview actively misleads the client about data loss on its named table.
Fix: the change-set resource-difference classifier in the cloudformation change-set engine — derive Replacement from the resource type's RequiresRecreation for the changed property and the Static/Dynamic evaluation of its new value, so an Always+Dynamic change reports Conditional.
Traces: cloudformation__dynamodb.cfn-custom-named-resource-replacement-refused-and-data-survives.

Cause 4 of 4: an Fn::GetAtt naming an attribute AWS::DynamoDB::Table does not have is accepted and the stack reaches CREATE_COMPLETE instead of failing and rolling back.
AWS: recorded behavior only (Fn::GetAtt is a template intrinsic, not a modeled member). The template passes ValidateTemplate and CreateStack, then the stack fails during provisioning and rolls back to ROLLBACK_COMPLETE, deleting the table, with the fixed reason text `Requested attribute ` + the attribute name taken from the template + ` does not exist in schema for AWS::DynamoDB::Table`. Added by UpdateStack the same reference rolls the update back with outputs and table untouched.
Emulator: the stack reaches `CREATE_COMPLETE` with StackStatusReason None — the unknown attribute is resolved (or silently dropped) instead of failing the stack.
Why: a typo'd GetAtt is one of the most common template defects. The stack is reported healthy while an output or a dependent resource carries a bogus value, so the error surfaces later in whatever consumes that output, with nothing in CloudFormation pointing at the cause.
Fix: the Fn::GetAtt resolution in the cloudformation template/intrinsic evaluation path — validate the requested attribute against the resource type's attribute schema during provisioning and fail the resource with the schema reason above.
Traces: cloudformation__dynamodb.deploy-cfn-dynamodb-getatt-unknown-attribute-rejected-after-the-table-is-built.
