# CodeBuild: 3 net-new divergences — sandbox command stdout never materializes (execution FAULTs), CreateWebhook accepts a provider-rejected source credential, and UpdateWebhook's not-found refusal is worded by the emulator

> _Note: this issue was identified against the code base at commit `f2163892bf40cea6da7d1662f28c14ec75c797c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartCommandExecution

## Description
THREE distinct net-new root causes found in the `codebuild` behavioral suite, all in the CodeBuild service crate services/service-com-amazonaws-codebuild-codebuild-20161006. ALL THREE must be closed before this issue is resolved. Every check the replay report marked ALREADY FILED or OWNED is excluded here; each cause below names the related open/fixed issue where one exists, and none of those issues carries the replay keys listed here.

Cause 1 of 3: a sandbox command execution never reaches a terminal outcome and never returns the command's standard output, so a full sandbox session (start -> connect -> run -> read result -> stop) cannot complete.
AWS: Smithy StartCommandExecution(sandboxId @required NonEmptyString @length min 1, command @required SensitiveNonEmptyString, type CommandType) -> { commandExecution }, errors InvalidInputException and ResourceNotFoundException (both client, httpError 400, defaulted); BatchGetCommandExecutions(sandboxId @required, commandExecutionIds @required @length 1..100) -> { commandExecutions, commandExecutionsNotFound }, whose CommandExecution records carry status (StatusType: SUCCEEDED, FAILED, FAULT, TIMED_OUT, IN_PROGRESS, STOPPED), exitCode, standardOutputContent and standardErrContent. Recorded behavior: a shell command run inside a RUNNING sandbox settles to SUCCEEDED and its ACTUAL stdout is readable back through standardOutputContent — an `echo <marker>` returns that marker — and StopSandbox then drives the sandbox to STOPPED.
Emulator: the sandbox does reach RUNNING (currentSession.currentPhase RUN_SANDBOX) and StartSandboxConnection/ListCommandExecutionsForSandbox answer, but the execution settles to FAULT with no exitCode and no standardOutputContent (the crate's own explanation in services/service-com-amazonaws-codebuild-codebuild-20161006/src/state.rs: 'this emulator does not execute sandbox commands, so nothing ran this command: it produced no output and no exit code'). FAULT is not in the terminal set {SUCCEEDED, FAILED} the flow polls for, so the check's BatchGetCommandExecutions poll never settles and the check exhausts its budget ('Check timed out after 60.0s'); the StopSandbox -> STOPPED tail is therefore never exercised either.
Why: the sandbox data plane is unusable — a client can start a command and never learn whether it ran, what it printed, or what it exited with, and every outcome AWS distinguishes collapses into one infrastructure-fault status.
Fix: the command-execution settle path and projection behind StartCommandExecution / BatchGetCommandExecutions (services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/start_command_execution.rs, batch_get_command_executions.rs, and the StoredCommandExecution settle in src/state.rs) must produce a deterministic simulated outcome derived from the submitted command, including stdout for a plain `echo`. Related: Cause 4 of open issue 20261025T062553Z-codebuild-6-further-divergences-startbuildbatch-takes-no-input.md describes the same FAULT settle for five OTHER sandbox checks and carries none of this check's replay key — this check additionally grades that the command's real stdout is echoed back in standardOutputContent and that the session ends STOPPED, so it must be replayed before that fix is confirmed.
Traces: codebuild.codebuild-sandbox-command-execution-returns-the-commands-real-stdout.

Cause 2 of 3: CreateWebhook (non-manual) mints a webhook even when the account's stored source credential is one the source provider itself rejects — the OAuthProviderException auth boundary is unreachable.
AWS: Smithy CreateWebhook(projectName @required ProjectName) -> { webhook }, modeled errors InvalidInputException, OAuthProviderException, ResourceAlreadyExistsException, ResourceNotFoundException (all client, httpError 400, defaulted). Two distinct boundaries exist: with NO stored credential for the project's source provider the call is refused ResourceNotFoundException ('Access token not found in CodeBuild project for server type github' — fixed text whose only variable part is the server-type token taken from the project's source type); with a credential that IS stored but that the provider refuses, CodeBuild forwards it, is rejected, and surfaces 400 OAuthProviderException with the fixed message 'Unable to create webhook at this time. Please try again later.' (no variable parts). Message text is recorded behavior only; the error codes and 400 statuses are modeled. Nothing is created in either case.
Emulator: the first boundary is now honoured, but after ImportSourceCredentials(serverType=GITHUB, authType=PERSONAL_ACCESS_TOKEN, token=<a syntactically valid but non-functional PAT>) the same CreateWebhook answers HTTP 200 and mints a webhook ({payloadUrl 'https://codebuild.<region>.amazonaws.com/webhooks?t=<uuid>&v=1', secret <40-char token>, lastModifiedSecret <ts>, status 'ACTIVE'}).
Why: a client is told a webhook is ACTIVE when nothing can authenticate to the repository, so the provider-authorization failure class AWS reports is invisible; code that branches on OAuthProviderException (re-import the token, prompt for re-auth) can never fire, and the downstream 'the rejected create left no webhook behind' invariant is violated because a webhook WAS persisted.
Fix: the credential-validity precondition in services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/create_webhook.rs — a non-manual CreateWebhook must consult the imported source-credential state and classify a stored-but-unusable credential as OAuthProviderException (distinct from the no-credential ResourceNotFoundException it already raises), persisting nothing; manualCreation=true must keep bypassing the provider dependency and succeed. Related: Cause 6 of open issue 20261025T014438Z-codebuild-8-further-divergences-getresourcepolicy-updatewebhook-deletebuildbatch-stubs.md describes the NO-credential boundary (which now behaves) and does not carry this failure's replay key; fixed issue 20261025T114418Z-codebuild-5-refusals-carry-emulator-invented-error-messages.md (Cause 3) covers only the NO_SOURCE source-type refusal message of the same handler.
Traces: codebuild.delete-webhook-oauth-provider-error-blocked.

Cause 3 of 3: UpdateWebhook's 'no webhook on this project' refusal carries an emulator-authored message instead of CodeBuild's wording.
AWS: Smithy UpdateWebhook(projectName @required ProjectName @length 2..150) -> { webhook }, modeled errors InvalidInputException, OAuthProviderException, ResourceNotFoundException (all client, httpError 400, defaulted). After DeleteWebhook, a further UpdateWebhook on that project is refused 400 ResourceNotFoundException with the message 'Webhook does not exist for this project' — wholly fixed text: CodeBuild names neither the project, nor its ARN, nor any identifier, so no part of it comes from the request or from state. Message text is recorded behavior only; the code and status are modeled.
Emulator: the decision and the code are right (400 ResourceNotFoundException) but the message is 'A webhook does not exist for CodeBuild project: arn:aws:codebuild:<region>:<account>:project/<project-name>' — invented prose whose appended project ARN is assembled from region, account and project name, so the string differs on every run and account where AWS's is constant.
Why: a client, CLI or retry wrapper that surfaces or matches on the refusal reason gets text AWS never emits and that cannot be keyed on at all, because it varies per environment; it also discloses a resource ARN in a not-found refusal.
Fix: the webhook-existence not-found path in services/service-com-amazonaws-codebuild-codebuild-20161006/src/ops/update_webhook.rs (and the shared webhook-lookup helper, so delete_webhook.rs reports the same sentence) must emit CodeBuild's fixed sentence. Related: UpdateWebhook was a 501 stub when Cause 3 of open issue 20261025T014438Z-codebuild-8-further-divergences-....md and fixed issue 20261025T192356Z-codebuild-updatewebhook-accepts-a-webhook-mutation-with-no.md were written; the operation now answers with the correct code, so this is the next layer and neither carries this check's replay key. Fixed issue 20261025T114418Z-codebuild-5-refusals-carry-emulator-invented-error-messages.md is the same defect CLASS at five other validation sites and does not include this one.
Traces: codebuild.webhook-lifecycle-create-update-delete.
