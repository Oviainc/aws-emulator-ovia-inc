# bedrock model-invocation-logging delivery is inert for both destinations: an accepted cloudWatchConfig and an accepted s3Config never receive a ModelInvocationLog record, so all three delivery checks consume the whole replay budget (2 causes, 3 checks)

> _Note: this issue was identified against the code base at commit `3d6b446e08b087d2665f5ca5dd389ba075b4c25a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutModelInvocationLoggingConfiguration

## Description
This issue carries 2 root causes grounded in 3 failing checks listed under the suite's `bedrock` service heading. Related open issues report the same family of defect but do NOT carry these three replay keys: 20261102T125313Z-bedrock-model-invocation-logging-is-inert-an-accepted.md (s3Config delivery, its own key only), 20261104T033011Z-bedrock-logs-an-accepted-cloudwatchconfig-invocation-logging-destination.md (cloudWatchConfig delivery, filed under the `bedrock__logs` heading), and 20261109T011501Z-bedrock-model-invocation-logging-delivers-no-record-to.md, which names these same three check ids but keys them to AssertionError sites inside `_poll_until`/`_await_record`; in this replay the three checks never reach those assertions — they are killed by the suite's 60.0s budget while still polling, so none of their current keys is carried by any open issue. This issue exists to carry those keys, not to describe a third defect. No fixed issue claims to have implemented delivery (the fixed bedrock logging issues concern whether a cloudWatchConfig is accepted or denied, not whether a record is ever written), so this is not a reopen. The emulator answered every control-plane call in these checks with 200 — Put, Get and Delete all succeed and Get echoes the stored configuration — so the service is up and answering wrongly, not unbootstrapped.

---
Cause 1 of 2: a model-invocation-logging configuration with a cloudWatchConfig destination is accepted and echoed back, but no invocation ever produces a log event in the named CloudWatch Logs group.
AWS: Smithy (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json) models PutModelInvocationLoggingConfiguration PUT /logging/modelinvocations -> 200 with required input member `loggingConfig` (LoggingConfig) and errors AccessDeniedException 403 / ValidationException 400 / ThrottlingException 429 / InternalServerException 500, and GetModelInvocationLoggingConfiguration GET /logging/modelinvocations -> 200 with `loggingConfig`. Delivery itself is not modeled, so recorded behavior only: once loggingConfig.cloudWatchConfig={logGroupName,roleArn} is stored with textDataDeliveryEnabled true, every subsequent bedrock-runtime inference made with no per-call logging opt-in writes an invocation log event into that log group within the delivery window, and the event's message carries at least the invoked modelId and the prompt text of that invocation. The log group name, role ARN, model id and prompt token are all per-request values taken from the request and the caller's state, never literals.
Emulator: Put is accepted (200) and Get echoes `cloudWatchConfig.logGroupName` exactly as configured — those assertions pass — but `logs:FilterLogEvents` on that log group returns an empty `events` list forever. The check's bounded 120.0s poll never observes any message, so the check is still spinning when the suite's 60.0s per-check budget expires and it is reported as `Error: Check timed out after 60.0s`. No event bearing the modelId or the prompt marker is ever delivered.
Why: a client cannot distinguish "invocation logging is configured" from "invocation logging works". Audit and compliance pipelines that tail the configured log group see nothing while the control plane reports logging enabled; an operator who reads the echoed configuration back concludes prompts and completions are being recorded when nothing is.
Fix: the bedrock control plane's invocation-logging component plus a post-inference delivery hook in the bedrock-runtime inference handlers (Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream): after a successful inference, resolve the stored loggingConfig and, when a cloudWatchConfig is present, emit the invocation record as a CloudWatch Logs event into the configured log group (creating the log stream as needed) under the configured role.
Traces: bedrock.put-model-invocation-logging-config-enforced-on-invoke.

---
Cause 2 of 2: a model-invocation-logging configuration with an s3Config destination is accepted and echoed back, but no record object is ever written under the configured bucket and keyPrefix, so the per-datatype delivery switches and the stop-after-delete guarantee are both unobservable.
AWS: same three modeled operations as above (Put PUT -> 200, Get GET -> 200 with loggingConfig, DeleteModelInvocationLoggingConfiguration DELETE /logging/modelinvocations -> 200). Delivery is not modeled, so recorded behavior only: with loggingConfig.s3Config={bucketName,keyPrefix}, each subsequent inference writes a JSON-lines record object into that bucket whose key sits under the configured keyPrefix and carries the documented layout `<keyPrefix>/AWSLogs/<accountId>/BedrockModelInvocationLogs/<region>/...` — accountId and region taken from the live caller and the call's region, never pinned. Each record declares `schemaType` = "ModelInvocationLog" (fixed text) and carries that invocation's own `requestId`, its `operation` (e.g. the operation actually invoked), its `modelId`, `accountId`, `region` and an `identity.arn`. With textDataDeliveryEnabled false the record STILL arrives but omits `input.inputBodyJson` / `output.outputBodyJson` and must not contain the prompt text anywhere; with it true the record carries the prompt verbatim and an `output.outputBodyJson` whose completion text equals the text the API returned. After DeleteModelInvocationLoggingConfiguration, further invocations produce NO new record and nothing buffered is flushed when the configuration is re-Put.
Emulator: Put and Get succeed and the stored flags (`textDataDeliveryEnabled`, `s3Config.bucketName`) read back correctly, but ListObjectsV2/GetObject under the configured prefix return nothing for any invocation: zero record objects, zero requestIds. Both checks therefore sit in their delivery polls (110.0s and 120.0s waits) until the suite's 60.0s budget kills them — `Error: Check timed out after 60.0s`. Because nothing is ever delivered, the text-delivery-disabled leg can never observe a body-less record and the post-delete leg has no positive-control record to contrast with the withheld one.
Why: every consumer of invocation logs — prompt/completion review, token accounting, audit export, the textDataDeliveryEnabled/imageDataDeliveryEnabled/embeddingDataDeliveryEnabled semantics and the "delete stops delivery" guarantee — is silently non-functional while the control plane reports success, so code that depends on records existing passes against the emulator and fails against AWS.
Fix: the same invocation-logging delivery path, in its s3 branch: the bedrock control plane's logging component must resolve the stored s3Config (bucketName/keyPrefix), write the JSON-lines record object at the documented key layout, populate schemaType/requestId/operation/modelId/accountId/region/identity, honour the three per-datatype delivery flags when deciding whether to include inputBodyJson/outputBodyJson, and stop emitting (without buffering) once the configuration is deleted.
Note on bedrock.delete-model-invocation-logging-withholds-further-records: its leg A is the absent positive-control delivery described above, which is this cause. Hypothesis: even once delivery works, that check holds its post-delete absence for `max(3 x measured leg-A latency, 90s)` and then waits up to a further `max(3 x latency, 120s)` for leg C redelivery, so it needs more wall clock than this suite's 60.0s per-check budget; re-replay it after the fix to confirm the withhold and redelivery legs, and treat a remaining bare timeout there as a budget artifact rather than a second defect.
Traces: bedrock.model-invocation-logging-text-delivery-disabled-omits-bodies, bedrock.delete-model-invocation-logging-withholds-further-records.
