# CloudFormation refuses AWS::NetworkMonitor::Monitor and AWS::NetworkMonitor::Probe as unrecognized resource types, so no Network Monitor estate can be deployed by template

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's resource-type registry does not carry the two CloudWatch Network Monitor resource types, so CreateStack refuses any template that declares them and both cross-service deploy checks die on their first call. Failing checks: cloudformation__ec2__networkmonitor.deploy-networkmonitor-monitor-and-probe-round-trip-and-delete, cloudformation__ec2__networkmonitor.deploy-networkmonitor-probe-invalid-destination-rejected-and-rolled-back.

AWS: recorded behavior only for the registry membership itself (a resource type is a CloudFormation registry fact and is not part of the networkmonitor Smithy model). Real CloudFormation recognizes AWS::NetworkMonitor::Monitor and AWS::NetworkMonitor::Probe and accepts a CreateStack that declares them: the stack reaches CREATE_COMPLETE, the Monitor's Ref resolves to the monitor ARN (the same value ListMonitors/GetMonitor report for that monitorName), the Probe's Ref resolves to the composite '<MonitorName>|<ProbeId>', and GetAtt exposes Probe.ProbeId, Probe.ProbeArn, Probe.VpcId and Probe.AddressFamily. The modeled control plane behind those types is networkmonitor CreateMonitor (POST /monitors; monitorName ResourceName length 1-200 pattern ^[a-zA-Z0-9_-]+$, aggregationPeriod @range min 30, tags TagMap) and CreateProbe (POST /monitors/{monitorName}/probes; probe.sourceArn Arn, probe.destination Destination length 1-255, probe.protocol Protocol enum, errors include ValidationException httpError 400). Stack-level tags propagate to both taggable resources alongside the template's own Tags, an update that drops the Probe resource leaves the monitor present with no probes and state INACTIVE, and DeleteStack removes the monitor so GetMonitor then answers ResourceNotFoundException with AWS's message 'No existing monitor found for account <accountId> and monitorName <monitorName>.' (fixed text; the account id and monitor name come from the request/state). When the Probe's Destination is a domain name rather than a literal address, the resource create fails and the stack rolls back to ROLLBACK_COMPLETE with the Probe's CREATE_FAILED ResourceStatusReason carrying the relayed registry-handler envelope whose message is 'destination must be a valid IPv4 or IPv6 address: [<destination>] (Service: NetworkMonitor; Operation: CreateProbe; Status Code: 400; Error Code: ValidationException; Request ID: <id>)' and HandlerErrorCode InvalidRequest — fixed text apart from the destination echoed from the request and the per-run request id.

Emulator: CreateStack is refused outright with HTTP 400 ValidationError and the message 'Template format error: Unrecognized resource types: [AWS::NetworkMonitor::Monitor, AWS::NetworkMonitor::Probe]' (fixed text 'Template format error: Unrecognized resource types: [...]' with the unrecognized type names listed from the template). Nothing after the create is exercised: no monitor, no probe, no Ref/GetAtt resolution, no probe-removing update, no rollback path and no delete-removes-the-monitor behavior.

Why: Network Monitor estates are stood up as infrastructure-as-code (CDK/CFN), not by hand-written API calls. A client whose stack is refused cannot provision a monitor or probe at all, and the refusal says 'Template format error', which blames the user's template instead of a missing resource-type implementation — so the user has no path forward. The negative path is equally unavailable: a template with an invalid probe Destination is refused at submit time instead of producing the ROLLBACK_COMPLETE plus relayed handler reason a client's failure handling is written against.

Fix: the CloudFormation crate's resource-type registry and its provisioner must carry AWS::NetworkMonitor::Monitor and AWS::NetworkMonitor::Probe — mapping MonitorName/AggregationPeriod/Tags onto networkmonitor CreateMonitor and MonitorName/SourceArn/Destination/Protocol/Tags onto CreateProbe, resolving Ref to the monitor ARN and to '<MonitorName>|<ProbeId>', resolving the Probe's ProbeId/ProbeArn/VpcId/AddressFamily GetAtts, propagating stack tags, supporting update (dropping the Probe) and delete of both, and relaying the networkmonitor ValidationException into the resource's CREATE_FAILED reason so the stack rolls back. The defect lives in the CloudFormation crate's resource-type support, not in the networkmonitor handlers.

Traces: cloudformation__ec2__networkmonitor.deploy-networkmonitor-monitor-and-probe-round-trip-and-delete, cloudformation__ec2__networkmonitor.deploy-networkmonitor-probe-invalid-destination-rejected-and-rolled-back. Related but not covering: existing open issues report the same missing-registry-entry shape for other types (20261102T084333Z-iotsitewise-... for AWS::IoTSiteWise::AssetModel, 20261103T041241Z-ec2-ecs-elasticache-... for the EC2 transit-gateway association types, 20261107T075601Z-cloudformation-ec2-ssm-... for AWS::SSM::MaintenanceWindowTarget); none of them names the AWS::NetworkMonitor::* types.
