# codestar-notifications: four behavioral divergences — CreateNotificationRule accepts unknown event types and unsupported resource types, DescribeNotificationRule misclassifies a malformed ARN, TagResource is a 501 stub

> _Note: this issue was identified against the code base at commit `2f933b71caa2a46f81d276f12cbb60da2946d084`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateNotificationRule

## Description
The codestar-notifications emulator boots and serves 13/23 behavioral checks, but four distinct root causes remain: two inputs real AWS refuses are accepted and create a rule, one refusal is raised under the wrong error class, and one implemented-looking tagging operation is still a scaffold stub. This bundle has 4 causes; all four must be closed before submitting.

Cause 1 of 4: CreateNotificationRule accepts an EventTypeIds entry that is not in the service's event-type catalog (failing check: codestar-notifications.create-rule-nonexistent-event-type-rejected).
AWS: Smithy: CreateNotificationRule (POST /createNotificationRule) input CreateNotificationRuleRequest.EventTypeIds is required, target EventTypeIds (list of EventTypeId, member length 1..200); the operation's modeled errors are AccessDeniedException(403), ConcurrentModificationException, ConfigurationException, LimitExceededException, ResourceAlreadyExistsException(409), plus the service-common ValidationException (httpError 400, member Message, length min 1, doc 'One or more parameter values are not valid.'). The model constrains only the member's length, so the catalog check itself is recorded behavior only: AWS is permissive about target existence and target publish permission at create time, but it DOES validate every EventTypeIds entry against its known event-type catalog (the same catalog ListEventTypes returns) and refuses an unknown id with 400 ValidationException. The check asserts the error CODE only, so the required behavior here is the 400/ValidationException classification and the absence of any created rule, not a particular message string.
Emulator: returns HTTP 200 with a body containing a freshly minted Arn ('arn:aws:codestar-notifications:<region>:<account>:notificationrule/<uuid>') for EventTypeIds=['sim2real-behav-nonexistent-event-type-id'] — i.e. the rule is created and persisted.
Why: a client that submits a mistyped or deprecated event-type id gets a success and an ARN, then owns a rule that can never fire. The validation error AWS uses to surface typos at create time never arrives, so configuration drift is silent and the client's reconciliation logic sees a rule it believes is wired to an event that does not exist.
Fix: CreateNotificationRule's input validation in its handler — resolve each EventTypeIds entry against the service's seeded event-type catalog in the state layer and refuse an unresolvable id with ValidationException (400) before any rule is inserted; UpdateNotificationRule's EventTypeIds path needs the same check.
Traces: codestar-notifications.create-rule-nonexistent-event-type-rejected.

Cause 2 of 4: CreateNotificationRule accepts a Resource ARN of a type CodeStar Notifications does not support (failing check: codestar-notifications.create-rule-unsupported-resource-type-rejected).
AWS: Smithy: CreateNotificationRuleRequest.Resource is required, target NotificationRuleResource with pattern ^arn:aws[^:\s]*:[^:\s]*:[^:\s]*:[0-9]{12}:[^\s]+$ — i.e. the model accepts ANY service's ARN, and documents the member as 'the resource to associate with the notification rule. Supported resources include pipelines in CodePipeline, repositories in CodeCommit, and build projects...'. The type restriction is therefore enforced by the service, not the model: recorded behavior is 400 ValidationException whose message is entirely FIXED service text with no request- or state-derived parts: 'The resource ARN is not valid. The ARN must be a supported AWS CodeStar Notifications resource type. Valid resource types include AWS CodeBuild, AWS CodeCommit, AWS CodeDeploy and AWS CodePipeline resources.' A supported type (a CodeDeploy application ARN) still succeeds.
Emulator: returns HTTP 200 with a new Arn for Resource = a real SNS topic ARN, so the unsupported-type rule is created; no ValidationException and none of the fixed message text is ever produced.
Why: the service-ARN segment of Resource is the only thing distinguishing a rule that can ever match an event from one that cannot. A client that passes the wrong ARN (a topic instead of the pipeline/repository/application it meant) is told the rule was created, and AWS's fixed, documentation-bearing refusal — the text that tells the caller which four resource types are valid — never reaches it.
Fix: CreateNotificationRule's input validation in its handler — reject a Resource ARN whose service/resource-type segment is not one of the supported Developer Tools resource types with ValidationException (400), emitting the fixed message above verbatim (no interpolation of the submitted ARN); UpdateNotificationRule must not be able to re-point a rule at an unsupported type either.
Traces: codestar-notifications.create-rule-unsupported-resource-type-rejected.

Cause 3 of 4: DescribeNotificationRule answers a malformed rule ARN with 400 ValidationException instead of 403 AccessDeniedException (failing check: codestar-notifications.describe-rule-malformed-arn-rejected).
AWS: Smithy: DescribeNotificationRuleRequest.Arn targets NotificationRuleArn with pattern ^arn:aws[^:\s]*:codestar-notifications:[^:\s]+:\d{12}:notificationrule\/(.*\S)?$; the operation models ResourceNotFoundException(404) and the service-common ValidationException(400); AccessDeniedException is modeled in this service with httpError 403, member Message (length min 1), doc 'CodeStar Notifications can't create the notification rule because you do not have sufficient permissions.' Recorded behavior: an Arn whose fixed resource-type segment is not 'notificationrule' (here 'wrongsegment/<id>') fails the resource-based authorization check BEFORE any lookup, so AWS answers 403 AccessDeniedException — deliberately distinct from the 404 ResourceNotFoundException it returns for a well-formed-but-unknown Arn. Its message is a template: fixed text 'You don't have sufficient permissions to perform operations on the following resource: ' + the ARN exactly as submitted + fixed text '. For more information, see the notifications feature documentation in the user guide for the Developer Tools console.' The only variable part is the submitted Arn; the per-run id inside it is not a requirement.
Emulator: answers 400 with Error.Code 'ValidationException' — the malformed ARN is being refused by the modeled pattern constraint on NotificationRuleArn in the centralized pre-handler validation, so the request never reaches the operation's authorization branch and the AccessDeniedException template is never rendered.
Why: the three-way distinction AWS draws (403 malformed/not-authorized, 404 well-formed-but-absent, 200 found) is how a client decides whether to fix credentials, to treat the rule as deleted, or to proceed. Collapsing the 403 case into a 400 ValidationException makes an authorization problem look like a client-side input problem: retry/permission-escalation logic keyed on AccessDeniedException never fires, and a caller that classifies 400 as non-retryable-but-local mis-reports the cause. Note the related fixed issue 20261023T092145Z-codestar-notifications-error-responses-carry-non-aws-message.md repaired DescribeNotificationRule's 404 not-found MESSAGE (that path now passes); this cause is a different one — the error CLASS chosen for a malformed ARN.
Fix: the DescribeNotificationRule handler's ARN-authorization branch (and the shape-level pattern enforcement in front of it) — an Arn that does not match the notificationrule ARN form must be answered by this operation as AccessDeniedException (403) with the message template above, rather than being rejected generically as a modeled pattern violation.
Traces: codestar-notifications.describe-rule-malformed-arn-rejected.

Cause 4 of 4: TagResource is an unimplemented scaffold stub, so every tagging call answers 501 NotImplemented (failing check: codestar-notifications.list-notification-rules-filter-by-resource).
AWS: Smithy: TagResource (POST /tagResource), input TagResourceRequest{Arn (NotificationRuleArn, required), Tags (map, required, 'Tag key names cannot start with "aws"')}, output TagResourceResult{Tags}; modeled errors ConcurrentModificationException(400), LimitExceededException(400), ResourceNotFoundException(404, doc 'CodeStar Notifications can't find a resource that matches the provided ARN.') plus common ValidationException(400). For a rule ARN that has been deleted, recorded behavior is 404 ResourceNotFoundException whose message is a template: fixed text 'The following resource ARN was not found: ' + the submitted rule ARN + fixed text '. Make sure that the resource ARN is correct and then try again.' (note this is a DIFFERENT template from the describe path's ID-based not-found text, which the same check verifies and which passes). For an existing rule, AWS associates the tags and returns the resulting Tags map.
Emulator: answers HTTP 501 with Error.Code 'NotImplemented' and message 'operation TagResource is scaffolded but not implemented in this emulator'; services/service-com-amazonaws-codestarnotifications-codestarnotifications-20191015/src/ops/tag_resource.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and its handle() returns Scaffolded::not_implemented("TagResource"). The failing check reaches this after its RESOURCE-filter listing and delete assertions all pass, so the only thing standing between the check and green is TagResource. (The suite separately marks DeleteTarget, ListEventTypes, ListTargets and ListTagsForResource as already-filed stubs; TagResource is NOT among them and is reported here.)
Why: tagging is how callers attribute and later discover notification rules, and a 501 is not a modeled outcome of this API at all — botocore surfaces it as an unmodeled NotImplemented error, so a client cannot distinguish 'rule gone' (404 ResourceNotFoundException, a terminal, classifiable condition) from a server fault, and any tag-on-create or tag-based reconciliation flow aborts.
Fix: implement handle() in services/service-com-amazonaws-codestarnotifications-codestarnotifications-20191015/src/ops/tag_resource.rs against the rule store in src/state.rs — merge the supplied Tags into the rule identified by Arn and return the resulting Tags map, refuse an unknown/deleted rule ARN with ResourceNotFoundException(404) rendering the 'The following resource ARN was not found: <arn>. Make sure that the resource ARN is correct and then try again.' template, refuse a key beginning with 'aws' with ValidationException(400), and delete the SCAFFOLDED marker line.
Traces: codestar-notifications.list-notification-rules-filter-by-resource.
