# Config: aggregate compliance summary still never converges, DeleteEvaluationResults is not denied for a pack-managed process-check rule, remediation execution always ends SUCCEEDED, and InvalidResultTokenException uses the wrong message (4 causes)

> _Note: this issue was identified against the code base at commit `02b425f47b189ddc53bb2814f48205d6f54220de`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetAggregateConfigRuleComplianceSummary

## Description
FOUR net-new root causes in the Config (StarlingDoveService) emulator, each grounded in a failing behavioral check of simparity-behavioral-ga-prod-v1 that is neither marked ALREADY FILED nor OWNED by an open issue. FOUR CAUSES must be closed before submitting.

Cause 1 of 4: the aggregate compliance SUMMARY still never reflects a verdict a custom rule produced, so the whole flow runs to the harness ceiling.
AWS: recorded behavior only, with model grounding. The recorded flow is: deploy a CUSTOM_LAMBDA Config rule whose function calls PutEvaluations, wait for ConfigRuleState==ACTIVE, read the verdict through GetComplianceDetailsByConfigRule, then read the same verdict through the aggregator surfaces — GetAggregateComplianceDetailsByConfigRule returns the per-source account/region result and GetAggregateConfigRuleComplianceSummary's NonCompliantResourceCount.CappedCount for Filters={AccountId, AwsRegion} rises by exactly one. Smithy: GetAggregateConfigRuleComplianceSummary models only client/400 errors (InvalidLimitException, InvalidNextTokenException, NoSuchConfigurationAggregatorException, ValidationException), so a healthy aggregator never answers a request about an existing rule with a permanently unchanged summary.
Emulator: the check is killed with 'Check timed out after 60.0s'; nothing is refused — no evaluation result and no change to the aggregate counts ever materialises. The timeout carries no stack frame, so the first non-converging leg is not pinned by the replay; the check polls (a) DescribeConfigRules for ACTIVE, (b) GetComplianceDetailsByConfigRule for a NON_COMPLIANT result, (c) GetAggregateComplianceDetailsByConfigRule, (d) GetAggregateConfigRuleComplianceSummary, and a fixer should drive those legs separately. The resolved issue 20261025T014224Z-config-aggregate-compliance-summary-never-reflects-an-evaluation.md (Cause 1) claimed this check; its fix did not land — the check still never converges, and because no call is refused this is not a refusal regression but the same missing convergence. Related open issue, named for overlap but NOT relied on as cover (it does not carry this check id): 20261024T114729Z-config-never-converges-on-an-evaluation-or-a.md.
Why: a client building a compliance dashboard on the aggregate summary can never observe a verdict and cannot distinguish 'nothing is non-compliant' from 'evaluation/aggregation is not implemented' — no call fails, the numbers simply never move.
Fix: the custom-rule evaluation pipeline and the aggregate read path of the Config service — src/ops/put_evaluations.rs and the compliance state it writes, plus src/ops/get_aggregate_config_rule_compliance_summary.rs and src/ops/get_aggregate_compliance_details_by_config_rule.rs.
Traces: config.aggregate-compliance-summary-reflects-source-evaluations.

Cause 2 of 4: DeleteEvaluationResults is NOT denied for a conformance-pack-managed process-check rule, so a caller can clear evaluation results AWS protects.
AWS: recorded behavior only. For an AWS_CONFIG_PROCESS_CHECK rule deployed through PutConformancePack (a service-linked rule owned by the conformance-pack service), DeleteEvaluationResults is refused — recorded code AccessDeniedException — and the previously injected PutExternalEvaluation result remains readable through GetComplianceDetailsByConfigRule. Smithy grounding: DeleteEvaluationResults models only NoSuchConfigRuleException and ResourceInUseException, i.e. the authorization refusal is a service-common error, not an operation-modeled one; the requirement is the refusal (code AccessDeniedException) for a rule the caller does not own.
Emulator: the call is not refused with AccessDeniedException — the check's `_error_code` helper returns None on success, and the assertion `assert delete_code == "AccessDeniedException"` fails, so the emulator either accepted the delete (2xx) or refused it with some other code. Note the earlier conformance-pack rule-name length defect on this same check (resolved issue 20261025T014224Z-config-aggregate-compliance-summary-never-reflects-an-evaluation.md, Cause 2) no longer fires: the check now gets past PutConformancePack/GetComplianceDetailsByConfigRule and fails on this later step, which is a distinct, net-new cause.
Why: a client (or a guardrail test) that relies on service-linked process-check results being immutable by the caller sees them silently destroyed; conversely, code that branches on AccessDeniedException to fall back to the owning service never takes that branch.
Fix: the authorization/ownership gate in the operation's handler — src/ops/delete_evaluation_results.rs must detect that the named rule is conformance-pack/service-linked owned and refuse with AccessDeniedException, leaving the stored evaluation results intact.
Traces: config.e2e-external-evaluation-persists-when-delete-evaluation-results-denied.

Cause 3 of 4: a remediation execution whose SSM automation cannot possibly succeed is reported as SUCCEEDED, so DescribeRemediationExecutionStatus never reports a failed remediation.
AWS: recorded behavior only, with model grounding. Smithy: RemediationExecutionStatus.State targets RemediationExecutionState with values QUEUED | IN_PROGRESS | SUCCEEDED | FAILED | UNKNOWN, and StepDetails carries each step's state and ErrorMessage. Recorded behavior: StartRemediationExecution on an S3_BUCKET_VERSIONING_ENABLED rule whose remediation is the SSM document AWS-ConfigureS3BucketVersioning with an AutomationAssumeRole that carries NO permissions progresses forward only (QUEUED/PENDING -> IN_PROGRESS -> terminal) and ends in the terminal state FAILED, because the automation fails at its first privileged step.
Emulator: the polled progression ends 'SUCCEEDED' ('AssertionError: expected the execution to end FAILED, ended \'SUCCEEDED\''), i.e. the remediation state machine reports success unconditionally and never derives the outcome from actually invoking the SSM document under the supplied AutomationAssumeRole.
Why: remediation is reported as having repaired a resource that was never repaired. Any client that waits for a terminal state and branches on FAILED (alerting, retry with a corrected role, surfacing StepDetails[].ErrorMessage) can never see a failure, and a failing remediation is indistinguishable from a successful one.
Fix: the remediation execution state machine in the Config service — src/ops/start_remediation_execution.rs and the remediation execution state that src/ops/describe_remediation_execution_status.rs reads: the terminal state must come from the outcome of the targeted SSM automation (including the assume-role's permissions), with FAILED on failure.
Traces: config.describe-remediation-execution-status-monotonic-transitions.

Cause 4 of 4: PutEvaluations refuses an invalid ResultToken with the right code but the wrong message.
AWS: Smithy — PutEvaluations(ResultToken required) models InvalidResultTokenException (errorKind client, httpError 400), documented 'The specified ResultToken is not valid.' Recorded behavior: the wire message for this error class is the fixed text 'Result Token provided is invalid' — it has no variable parts (it echoes neither the token nor the rule name).
Emulator: code InvalidResultTokenException is correct, but the message is 'The specified ResultToken is not valid. Use the ResultToken Config delivered with the evaluation event for the rule you are evaluating.' — the error shape's documentation plus emulator-authored guidance, instead of AWS's message. Fixed text is the entire requirement here; nothing in the message is request- or state-derived.
Why: tests and clients that assert on or log the AWS error message for a forged/expired result token see emulator-authored prose, so message-level parity checks fail and operator runbooks keyed on AWS's wording do not match. A sibling check (config.overly-permissive-put-evaluations-invalid-result-token, OWNED by 20261024T114729Z-config-never-converges-on-an-evaluation-or-a.md) asserts the same message but times out before reaching it, so that issue does not cover this message defect.
Fix: the refusal message in the operation's handler/validation — src/ops/put_evaluations.rs (and any shared Config error-message helper it uses) must emit the fixed text 'Result Token provided is invalid' for InvalidResultTokenException.
Traces: config.start-config-rules-evaluation-transition.
