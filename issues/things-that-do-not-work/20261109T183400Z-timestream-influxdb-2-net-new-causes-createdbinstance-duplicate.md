# timestream-influxdb: 2 net-new causes — CreateDbInstance duplicate-name ConflictException message does not follow AWS's already-exists rule, and an AVAILABLE instance's endpoint is published as a public AWS host the emulator does not serve

> _Note: this issue was identified against the code base at commit `41c5ae389f495755d1c1e47282b4b58fd25764aa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDbInstance

## Description
Two net-new root causes in the timestream-influxdb emulator, each grounded in its own failing behavioral check. A fixer must close both; each is separately observable.

Cause 1 of 2: the ConflictException raised when CreateDbInstance reuses a name already owned by a live DB instance carries an emulator-authored message instead of AWS's already-exists message.
AWS: Smithy: CreateDbInstance.name is required, DbInstanceName @length 3..40 @pattern ^[a-zA-Z][a-zA-Z0-9]*(-[a-zA-Z0-9]+)*$; the operation models ConflictException (client, httpError 409). Recorded behavior: a second CreateDbInstance with a name a live instance still owns is refused with HTTP 409 / Error.Code "ConflictException" and Error.Message "The DbInstance with id [<id>], name [<name>], customer [<accountId>] already exists". Fixed text: "The DbInstance with id [", "], name [", "], customer [", "] already exists". Variable parts, all taken from the request and the emulator's state: <id> is the id of the EXISTING instance that owns the name (the `id` the first CreateDbInstance returned), <name> is the `name` member of the rejected request, <accountId> is the caller's 12-digit account id. The conflict is a state, not an always-invalid input: after the owning instance is deleted the identical call must succeed and return a NEW id with status CREATING.
Emulator: returns Error.Code "ConflictException" (correct) with Error.Message "DB instance <name> already exists" — a different template entirely: it drops the "The DbInstance with id [...]" lead-in, the existing instance's id and the customer/account clause, and uses the prose "DB instance" rather than the API type name "DbInstance".
Why: a client or operator that matches or parses the AWS conflict message cannot identify the instance that holds the name (AWS hands back the conflicting id in the message; the emulator does not), and message-sensitive error handling for the duplicate-name class never matches, so a well-understood 409 is treated as an unknown failure.
Fix: the CreateDbInstance handler's name-uniqueness check (the conflict branch that renders the ConflictException message), which must render the existing instance's id, the requested name and the caller's account id into AWS's template.
Traces: timestream-influxdb.create-db-instance-duplicate-name-conflict-rejected. Related but NOT covering: open issue 20261030T010007Z-timestream-influxdb-createdbparametergroup-conflictexception-message-does-not-follow.md reports the same message rule for CreateDbParameterGroup only; this cause is on the CreateDbInstance handler.

Cause 2 of 2: GetDbInstance/CreateDbInstance publish `endpoint` as a public AWS-style hostname the emulator does not serve, so the instance's native InfluxDB v2 data plane is unreachable at the address the control plane announces.
AWS: recorded behavior only (the Smithy model describes only the control plane: CreateDbInstance/GetDbInstance output members `endpoint` (String) and `port` (Port, @range 1024..65535, default 8086)). The recording shows that once the instance reports status AVAILABLE, the host in `endpoint` listening on `port` serves the InfluxDB v2 HTTP API: GET /health -> 200 with a JSON body whose "status" is "pass"; POST /api/v2/signin with the instance's username/password -> 204; POST /api/v2/write?org=<organization>&bucket=<bucket>&precision=ns with a line-protocol body -> 204; POST /api/v2/query?org=<organization> with a Flux body and Accept: application/csv -> 200 containing the written measurement and value. The requirement is that the announced endpoint/port is the address a customer of the service can actually reach the instance on.
Emulator: `endpoint` is a synthesized public AWS host of the form <name>-<suffix>.timestream-influxdb.<region>.on.aws, advertised with port 8086. That host is not one of the emulator's own hosts and nothing of the emulator answers on it: the client is refused before any request is made ("endpoint_url was given https://<name>-<suffix>.timestream-influxdb.us-west-2.on.aws:8086 (published by the emulator or built by the check): its host is not one of the emulator's own hosts"). The emulator must publish an address it serves — its own host/port, or a per-resource listener on one of its own hosts. (The host, suffix and port in the quoted line are this run's values; the defect is that the published host is an AWS public host rather than an address the emulator serves.)
Why: the entire data plane of Timestream for InfluxDB is unusable. A client that creates an instance, waits for AVAILABLE and then writes/queries points through the InfluxDB v2 API — the normal use of this service — is pointed at an unreachable address while the control plane reports the instance ready to serve.
Fix: the instance state/serializer that computes the published `endpoint` (and `port`) for CreateDbInstance/GetDbInstance/ListDbInstances must announce the emulator's own reachable address, and an InfluxDB v2 HTTP surface (/health, /api/v2/signin, /api/v2/write, /api/v2/query) must be served there for an AVAILABLE instance.
Traces: timestream-influxdb.native-influxdb-http-protocol-round-trip. Related but NOT covering as filed: open issue 20261104T042504Z-timestream-influxdb-validationexception-constraint-violation-message-wording-diverges.md records, as its Cause 4, that the data plane never answered and only HYPOTHESIZED a wrong address; this check now fails earlier and deterministically on the published host itself, which is the concrete defect and is not carried by that issue's replay key.
