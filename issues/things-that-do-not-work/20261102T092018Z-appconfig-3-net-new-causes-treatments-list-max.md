# AppConfig: 3 net-new causes — Treatments list max over-enforced on Create/UpdateExperimentDefinition, and both optimistic-lock conflict messages are emulator-authored

> _Note: this issue was identified against the code base at commit `e5a3e8eb74dcb2b43ac4e38f0bb7bcf8e9a5cd29`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateExperimentDefinition

## Description
Three net-new root causes in the appconfig service, grounded in four replayed behavioral checks. All three are separate defects and EVERY ONE must be closed before this issue is submitted; re-replay every check id in trace_ids to confirm. None of these four checks was marked ALREADY FILED and none was marked OWNED by an open issue in this replay.

=== Cause 1 of 3: CreateExperimentDefinition and UpdateExperimentDefinition refuse a Treatments list of 6, which AWS accepts ===
AWS: Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json) models CreateExperimentDefinition.Treatments -> TreatmentInputList @length min 1 max 5 (POST /applications/{ApplicationIdentifier}/experimentdefinitions, success 201, errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / ServiceQuotaExceededException 402 / InternalServerException 500) and UpdateExperimentDefinition.Treatments -> the same TreatmentInputList @length 1..5 (PATCH /applications/{ApplicationIdentifier}/experimentdefinitions/{ExperimentDefinitionIdentifier}, success 200). Recorded behavior contradicts that bound for this member: AWS ACCEPTS a Treatments list of 6 — CreateExperimentDefinition answers 201 with Status 'IDLE' and the definition is then listed by name through ListExperimentDefinitions, and UpdateExperimentDefinition answers 200 with Status 'IDLE' and GetExperimentDefinition then returns all 6 Treatments. The modeled @length max on this list is not enforced server-side, so an acceptance is the requirement here, not a refusal.
Emulator: both operations refuse the call with BadRequestException (HTTP 400) and the message "1 validation error detected: Value '6 items' at 'treatments' failed to satisfy constraint: Member must have length less than or equal to 5" (the botocore surface raises BadRequestException before the check can read any response), so neither definition is ever created or updated.
Why: this is an UNDER-permissive refusal of a call real AppConfig performs. A client that legitimately defines six treatments gets a hard 400 against the emulator and a working experiment against AWS, so the divergence is invisible until production. It also makes every downstream assertion (Status IDLE, the listing, the persisted treatment count) unreachable.
Fix: the input-validation layer for the appconfig experiment-definition handlers — the Treatments list-length check in the CreateExperimentDefinition and UpdateExperimentDefinition handlers must not be derived from TreatmentInputList's modeled @length max, because AppConfig does not apply it to this member. Other constraints on the same list's members (Weight @range) stay enforced.
Traces: appconfig.create-experiment-definition-invalid-treatment-rejected, appconfig.update-experiment-definition-invalid-treatment-rejected.

=== Cause 2 of 3: CreateExtension's optimistic-lock (LatestVersionNumber) conflict message is the emulator's own prose ===
AWS: Smithy CreateExtension (POST /extensions, success 201) models ConflictException httpError 409; the message text is not modeled, so recorded behavior only. A CreateExtension that pins LatestVersionNumber to a value that is no longer the extension's current version is refused with ConflictException and one of two messages, depending on how far the winning writer got: "LatestVersionNumber supplied in request <supplied> does not match latest version <actual>." — fixed text "LatestVersionNumber supplied in request " / " does not match latest version " / ".", variable parts the LatestVersionNumber from the request and the extension's current version from state — or "Extension with id <extensionId> and versionNumber <version> already exists for account <accountId>." — fixed text "Extension with id " / " and versionNumber " / " already exists for account " / ".", variable parts the extension id and version from state and the caller's account. The error CLASS and the race outcome are correct in the emulator: exactly one of two concurrent racers wins, the loser gets ConflictException, and the extension ends at version 2.
Emulator: refuses with ConflictException but the message "Extension <name> is at version <actual>, not <supplied>." (replayed: 'Extension sim2real-behav-ext-7c87c125f993 is at version 2, not 1.'), which is neither AWS form and additionally leaks the extension NAME where AWS reports only ids/version numbers.
Why: the message is the only place a conditional-write failure explains itself. A client or operator matching or displaying AWS's wording sees unrecognised text, and a compare-and-swap retry loop keyed on either AWS sentence never matches.
Fix: the CreateExtension handler's optimistic-lock failure path in the appconfig service (the same formatter that must produce the "already exists for account" variant when the version row has already been written).
Related open issue, which does NOT cover this check: 20261029T195212Z-appconfig-control-plane-refusals-wrong-error-classes-and.md Cause 5 records this same message defect, but it is grounded solely in appconfig.create-extension-version-conflict-rejected (the sequential stale-lock path) and its replay set does not include appconfig.concurrent-extension-version-optimistic-lock; the concurrent path additionally requires the second, 'already exists for account' wording that that cause does not mention. Fixing one should fix the other — close both deliberately rather than assuming.
Traces: appconfig.concurrent-extension-version-optimistic-lock.

=== Cause 3 of 3: CreateHostedConfigurationVersion's optimistic-lock conflict message is the emulator's own prose ===
AWS: Smithy CreateHostedConfigurationVersion (POST /applications/{ApplicationId}/configurationprofiles/{ConfigurationProfileId}/hostedconfigurationversions, LatestVersionNumber bound to the Latest-Version-Number header, success 201) models ConflictException httpError 409; the text is not modeled, so recorded behavior only. Concurrent creates that all pin the same LatestVersionNumber are serialized so exactly one wins, and every loser is refused ConflictException with the message "Hosted configuration version <n> already exists" — fixed text "Hosted configuration version " / " already exists" (no trailing period), the single variable part being the version number the write would have created (i.e. the pinned LatestVersionNumber + 1). The error class, the single-winner outcome and the resulting version set {base, base+1} are correct in the emulator.
Emulator: every loser is refused with ConflictException but the message "Expected latest version <supplied> does not match actual latest version <actual>" (replayed, 4 of 5 racers: 'Expected latest version 1 does not match actual latest version 2'). Different sentence, and it reports the lock comparison instead of naming the version that already exists.
Why: same class of breakage as Cause 2 — a caller that parses, logs or matches AppConfig's conflict wording to decide whether to re-read and retry gets text AWS never emits; the two defects are separate because they live in different handlers and AWS words them differently (one names the supplied/actual versions, the other names the already-existing version).
Fix: the CreateHostedConfigurationVersion handler's optimistic-lock failure path in the appconfig service.
Traces: appconfig.concurrent-hosted-configuration-version-optimistic-lock.
