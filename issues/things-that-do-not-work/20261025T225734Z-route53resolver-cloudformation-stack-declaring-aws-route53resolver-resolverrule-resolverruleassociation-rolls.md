# CloudFormation stack declaring AWS::Route53Resolver::ResolverRule + ResolverRuleAssociation rolls back (ROLLBACK_COMPLETE) instead of creating the rule and its VPC association

> _Note: this issue was identified against the code base at commit `444cbe40db1434e138785b95152adaa2e53ade67`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: a CloudFormation template that deploys a Route 53 Resolver FORWARD rule and its VPC association — AWS::EC2::VPC + two AWS::EC2::Subnet + AWS::EC2::SecurityGroup + AWS::Route53Resolver::ResolverEndpoint + AWS::Route53Resolver::ResolverRule + AWS::Route53Resolver::ResolverRuleAssociation — is accepted by CreateStack but at least one resource fails to create, so the stack goes to ROLLBACK_COMPLETE and nothing is deployed.
AWS: AWS::Route53Resolver::ResolverRule and AWS::Route53Resolver::ResolverRuleAssociation are published CloudFormation resource types; recorded behavior only (the model has no CloudFormation surface) — the recording shows this stack reaching CREATE_COMPLETE, Outputs carrying the !Ref values (the rslvr-rr-… rule id and the rslvr-rrassoc-… association id), GetResolverRuleAssociation on that output reporting Status COMPLETE with the rule id and VPC id the template wired together, and the rule's TargetIps being the declared 10.254.254.254:53. On stack deletion both resources are removed and GetResolverRule/GetResolverRuleAssociation answer ResourceNotFoundException.
Emulator: CreateStack is accepted (the three Route53Resolver types ARE registered — services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs lines ~313-315 and ~358-360 declare Route53ResolverEndpoint / Route53ResolverRule / Route53ResolverRuleAssociation, with create arms at ~493-504), but the create fails mid-way: botocore WaiterError 'Waiter StackCreateComplete failed: Waiter encountered a terminal failure state: For expression "Stacks[].StackStatus" we matched expected path: "ROLLBACK_COMPLETE" at least once'. The replay never gets past _deploy_cfn, so no Outputs, no rule and no association exist. Hypothesis (neither the model nor the replay output states which resource failed — the fixer should read DescribeStackEvents' ResourceStatusReason for the stack): the Route 53 Resolver arms are fed ids produced for the template's EC2 dependencies, and provisioner.rs contains no AWS::EC2::VPC / Subnet / SecurityGroup entry at all (no match for 'AWS::EC2::' or an Ec2* Provisioner variant in that file), so a declared-only VPC/subnet/security group hands CreateResolverEndpoint and AssociateResolverRule template-derived names rather than vpc-/subnet-/sg- ids, and the owning service refuses them.
Why: every infrastructure-as-code path to a Resolver forwarding rule is closed, and it is closed in the worst way for a client — the template is valid and accepted, so the failure looks like a defect in the caller's template or in their account, and the stack self-destructs (ROLLBACK_COMPLETE) leaving nothing to inspect. A CI pipeline that deploys Resolver forwarding with CloudFormation fails against the emulator while succeeding on AWS, and there is no workaround via the control plane because the same stack also owns the VPC the rule must be associated with.
Fix: CloudFormation's provisioning path for this stack — services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs (the Route53ResolverEndpoint / Route53ResolverRule / Route53ResolverRuleAssociation create arms and the helpers they call) together with whatever resolves the template's EC2 network dependencies for them — must make each declared resource really exist and report the owning service's own identifier as the physical resource id, so !Ref on the rule and the association yield the rslvr-rr-… and rslvr-rrassoc-… ids and the stack reaches CREATE_COMPLETE. Note this is NOT covered by open issue 20261024T062131Z-route53resolver-cloudformation-cannot-deploy-route-53-resolver-resources-firewall.md: that issue's Cause 1 is the three AWS::Route53Resolver::*Firewall* types being unrecognized by CreateStack (ValidationError), and its Cause 2 is AWS::Route53Resolver::ResolverEndpoint having no provisioner and the stack completing anyway — the opposite symptom to this rollback, and neither names the ResolverRule or ResolverRuleAssociation types.
Traces: route53resolver.deploy-resolver-rule-cfn-forwards-queries.

## Evidence
route53resolver.deploy-resolver-rule-cfn-forwards-queries: CreateStack with the template below is accepted, then the StackCreateComplete waiter fails — botocore.exceptions.WaiterError: 'Waiter StackCreateComplete failed: Waiter encountered a terminal failure state: For expression "Stacks[].StackStatus" we matched expected path: "ROLLBACK_COMPLETE" at least once'. Expected: the stack reaches CREATE_COMPLETE and exports Outputs RuleId (!Ref Rule -> rslvr-rr-…), AssociationId (!Ref RuleAssociation -> rslvr-rrassoc-…) and VpcId; the check then asserts GetResolverRuleAssociation(ResolverRuleAssociationId=<AssociationId>).Status == 'COMPLETE' and that the association references that rule and that VPC. Actual: the stack rolled back, so none of those assertions were ever reached and no Resolver rule or association was created.

Template resources (all in one stack): Vpc (AWS::EC2::VPC, 10.81.0.0/16); SubnetA/SubnetB (AWS::EC2::Subnet, 10.81.1.0/24 and 10.81.2.0/24, AvailabilityZone !Select [0|1, !GetAZs '']); Sg (AWS::EC2::SecurityGroup); OutboundEndpoint (AWS::Route53Resolver::ResolverEndpoint, Direction OUTBOUND, IpAddresses [{SubnetId: !Ref SubnetA}, {SubnetId: !Ref SubnetB}], SecurityGroupIds [!Ref Sg]); Rule (AWS::Route53Resolver::ResolverRule, RuleType FORWARD, DomainName sim2real-cfn-forward.test., ResolverEndpointId !Ref OutboundEndpoint, TargetIps [{Ip: 10.254.254.254, Port: 53}]); RuleAssociation (AWS::Route53Resolver::ResolverRuleAssociation, ResolverRuleId !Ref Rule, VPCId !Ref Vpc).

Code state: provisioner.rs DOES carry the three Route53Resolver provisioner variants and their create/delete/describe arms (lines ~313-315, ~358-360, ~493-504, ~779-789, ~911-919), and its module docs (~line 179) state those types' properties are passed through to the creates with a minted CreatorRequestId. The same file has no AWS::EC2::VPC / Subnet / SecurityGroup entry (no 'AWS::EC2::' occurrence), and its docs state that a type with no entry here is left declared-only with a CloudFormation-computed physical id — which is the most likely source of the failing create, to be confirmed from DescribeStackEvents.

## Steps to Reproduce
1. Clone the repo and boot the emulator built from it.
2. CreateStack with the template described in Evidence (VPC + two subnets + security group + OUTBOUND AWS::Route53Resolver::ResolverEndpoint + AWS::Route53Resolver::ResolverRule of RuleType FORWARD + AWS::Route53Resolver::ResolverRuleAssociation, Outputs !Ref Rule / !Ref RuleAssociation / !Ref Vpc).
3. Wait with the stack_create_complete waiter: it terminates on StackStatus ROLLBACK_COMPLETE instead of CREATE_COMPLETE.
4. Call DescribeStackEvents for the stack and read the first CREATE_FAILED event's ResourceStatusReason to identify which resource's create was refused and by which owning service.
5. Confirm nothing was deployed: ListResolverRules shows no rule with Name 'sim2real-r53r-cfn-rule' and the stack has no Outputs.
6. Replay behavioral check route53resolver.deploy-resolver-rule-cfn-forwards-queries.
