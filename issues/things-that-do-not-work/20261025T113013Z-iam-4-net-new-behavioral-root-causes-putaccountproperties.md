# iam: 4 net-new behavioral root causes — PutAccountProperties is served to a zero-permission principal, PutGroupPolicy's 5,120-character group inline limit is never reached, and three policy-composition checks never converge

> _Note: this issue was identified against the code base at commit `1f7e5adccf9e411825240a72188af4d50262df19`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutAccountProperties

## Description
Four distinct root causes in the bootstrapped `iam` service, each grounded in a failing behavioral check of suite simparity-behavioral-ga-prod-v1 that the replay report marks NEITHER "ALREADY FILED" nor "OWNED by". A fixer must close all four before submitting; the per-cause check ids under each cause's Traces line are what to re-replay.

=== Cause 1 of 4: PutAccountProperties performs no IAM authorization, so a zero-permission principal flips an account-wide IAM feature toggle. ===

AWS: Smithy (com.amazonaws.iam) PutAccountProperties takes a required `Properties` map (accountPropertiesMapType) and models only ConcurrentModificationException (awsQuery code `ConcurrentModification`, 409), InvalidInputException (`InvalidInput`, 400) and ServiceFailureException (`ServiceFailure`, 500) — it declares NO success-for-anyone contract, because IAM authorizes every IAM API call against the caller's identity-based policies before the operation changes anything. Recorded behavior: a brand-new IAM user with ZERO attached or inline policies (the implicit deny) is refused HTTP 403 with error code `AccessDenied`, and the message is IAM's enhanced access-denied text. The message template, with the fixed text and the variable parts named: fixed — `User: ` / ` is not authorized to perform: ` / ` on resource: ` / ` because no identity-based policy allows the ` / ` action. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/` / ` for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: `; variable — the signing principal's ARN (from the request's SigV4 key), the action name `iam:PutAccountProperties` (twice, from the request), the resource `*` (this operation acts on the account singleton, not a named entity), and the per-request authorization id IAM mints for that one refusal. The region in the console URL is `us-east-1` for every refusal because IAM's global endpoint signs there; the authorization id is the only per-run value and is not itself a requirement.

Emulator: the identical mutating call, signed by that zero-permission user's minted access key, returned HTTP 200 with an empty body (`{'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'text/xml', 'content-length': '264'}}}`) — no error at all. Two contributing defects in the same component: (a) the operation handler never calls `crate::state::authorization::authorize`, so the gate is simply absent for this operation (the gate in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs is applied per-operation, not ahead of the handlers); and (b) even where it IS called, `authorize` words its refusal as `User: {principal} is not authorized to perform: {action} on resource: {resource} because no identity-based policy allows the {action} action` and stops there — it never appends AWS's authorization-details sentence, so no `GetRequestAuthorizationDetails` pointer and no console link are emitted.

Why: the emulator is strictly MORE permissive than AWS on an account-wide IAM control plane write. A developer validating that an unprivileged role cannot toggle `RoleManager/Enabled` is told the guard holds when nothing guards it; the same deployment against real AWS refuses, and any least-privilege assertion about this operation passes vacuously here. Secondarily, a client that parses the refusal to surface the authorization id (the documented route to the full decision detail) finds no id even on refusals the emulator does produce.

Fix: the operation's handler — services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/put_account_properties.rs — must authorize `iam:PutAccountProperties` on resource `*` through src/state/authorization.rs before mutating state; better, the gate belongs ahead of the operation handlers (src/service.rs) so no operation can be added without one. The message template belongs in `authorize` in src/state/authorization.rs, which must append the authorization-details sentence to every AccessDenied it builds.

Traces: iam.put-account-properties. No open issue names this operation (list_existing_issues query='account-properties' returns none).

=== Cause 2 of 4: PutGroupPolicy is a 501 scaffold, so the group-specific 5,120-significant-character inline-policy limit is never enforced. ===

AWS: Smithy binds PutGroupPolicy with GroupName (groupNameType), PolicyName (policyNameType) and PolicyDocument (policyDocumentType, @length 1..131072) and models LimitExceededException → awsQuery code `LimitExceeded` at HTTP 409, MalformedPolicyDocument (400), NoSuchEntity (404), ServiceFailure (500). The quota is IAM's documented, non-adjustable "Group policy size: 5,120 characters" aggregate over a group's inline policies, and IAM does not count whitespace toward it. So: a document with 5,121 significant characters is refused `LimitExceeded` and stores nothing (ListGroupPolicies stays empty); a document with exactly 5,120 significant characters padded with ~4 KB of whitespace is ACCEPTED and GetGroupPolicy reads it back intact; replacing the accepted one with the 5,121-character document is refused `LimitExceeded` again while the stored policy survives unchanged. The refusal message template: fixed text `Maximum policy size of 5120 bytes exceeded for group `, followed by the group name taken from the request. The 5120 literal is the API constant for the group principal type (a role uses 10,240 and a managed policy 6,144), not a recorded value.

Emulator: every PutGroupPolicy call is refused HTTP 501 with error code `NotImplemented` and the message `operation PutGroupPolicy is scaffolded but not implemented in this emulator`, because services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/put_group_policy.rs is still a SCAFFOLDED stub. The check captured that error internally and compared codes, which is why the replay report recorded a `mismatch` (`PutGroupPolicy over the group limit returned 'NotImplemented', expected 'LimitExceeded'`) and did not attribute it to the blocked-operation cluster.

Why: no inline group policy can be written at all, so group-based permissions cannot be modelled; and the size quota — the thing a client relies on to know a generated policy will fit before it deploys — is untestable. A client that treats 501 as a transport fault retries forever; one that treats it as a size failure reports the wrong cause.

Fix: the operation's handler — src/ops/put_group_policy.rs — must store the inline document in src/state.rs (NoSuchEntity when the group does not exist, MalformedPolicyDocument for an unparseable document) and enforce the 5,120-character aggregate counted with whitespace EXCLUDED, raising LimitExceededException (`LimitExceeded`, 409) with the fixed sentence above and leaving state untouched on refusal; the SCAFFOLDED marker line must then be deleted. The open issue 20261025T102129Z-iam-putgrouppolicy-stub.md ("Implement iam PutGroupPolicy: unimplemented scaffold stub") names the same operation but is a bare implement-the-stub item: it does NOT carry this check's replay key and says nothing about the whitespace-excluded 5,120 aggregate or its refusal wording, so implementing the handler without this cause would still leave this check failing.

Traces: iam.iam-bound-deep-iam-3-group-inline-policy-over-5120-significant-chars-rejected.

=== Cause 3 of 4: two condition keys ANDed in one block — one read from the target resource, one from the request body — plus a ForAllValues: set qualifier are all permanently undecidable, so the grant never applies. ===

AWS: IAM evaluates a statement's Condition against the request context that AWS itself populates — `aws:ResourceTag/<key>` from the TARGET resource's stored tags, `aws:RequestTag/<key>` from the request body, `aws:TagKeys` from the set of keys the request writes — and multiple keys inside one Condition block AND together. SimulatePrincipalPolicy additionally accepts those values as ContextEntries. So an `Allow iam:TagUser on [X,Y] Condition {StringEquals: {aws:ResourceTag/owner: <X-owner>, aws:RequestTag/env: dev}, ForAllValues:StringEquals: {aws:TagKeys: [env]}}` yields: `allowed` / a succeeding TagUser when the target carries owner=<X-owner> and the request writes env=dev; `implicitDeny` / `AccessDenied` when the request writes env=prod; `implicitDeny` / `AccessDenied` on the owner=<Y-owner> target; and retagging only target Y to owner=<X-owner> flips its outcome to allowed. The operator set and the `ForAllValues:`/`ForAnyValue:` qualifiers are IAM's documented condition grammar; the decisions are recorded behavior.

Emulator: the shared evaluator decides only the string family. services/common/src/iam_authorization.rs lines 64-74 declare `const STRING_OPERATORS: &[&str] = &["StringEquals", "StringNotEquals", "StringEqualsIgnoreCase", "StringNotEqualsIgnoreCase", "StringLike", "StringNotLike"];` with the comment "Everything else — the numeric, date, IP, ARN and `Null` operators, and the `ForAnyValue:`/`ForAllValues:` set qualifiers — leaves the statement undecided", and the module docs state that an undecided Allow never grants (the fail-closed reading). Separately, the request-time authorizer supplies no context at all: src/state/authorization.rs line 111 builds `iam::Request::new(action, resource, &principals)`, the constructor documented in services/common/src/iam_authorization.rs lines 114-120 as "A request with no condition context" (`context: &[]`), and `with_context` is never called in that file — so `aws:ResourceTag/*` and `aws:RequestTag/*` are keys the context does not carry, which is the other way a clause becomes undecided. The result is that the simulator never returns `allowed` for the matching combination and the real signed TagUser is refused forever; the check polls for the matching decision and the harness reports `Check timed out after 60.0s` with no converged response.

Why: every ABAC grant that combines a resource-tag condition with a request-tag condition, or that uses a set qualifier to bound which tag keys may be written, is silently inert — the call is refused where AWS permits it. A developer cannot validate tag-based least privilege at all, and the natural workaround is to delete the conditions, shipping a policy strictly broader than the one that was tested.

Fix: services/common/src/iam_authorization.rs must implement the `ForAllValues:`/`ForAnyValue:` set qualifiers (and the remaining operator families), keeping the fail-closed reading only for operators that genuinely remain unimplemented; and the IAM request authorizer src/state/authorization.rs must assemble the condition context and pass it via `Request::with_context` — at minimum `aws:ResourceTag/*` from the target entity's stored tags, `aws:RequestTag/*` and `aws:TagKeys` from the operation's tag input. Both src/ops/simulate_principal_policy.rs and the authorizer then inherit it. Two open issues describe the same two components under DIFFERENT replay keys and do not cover this check: 20261025T102129Z-iam-10-net-new-behavioral-root-causes-simulateprincipalpolicy.md (its Cause 3 is the empty condition context, grounded in the principal-tag check; its Cause 4 is the non-string operators, grounded in the sourceip check) and 20261025T000319Z-iam-10-net-new-behavioral-root-causes-four.md (date-operator and set-qualifier checks under its own ids). This check is the two-keys-ANDed-across-resource-and-request unit neither re-replays.

Traces: iam.sep-policy-composition-request-and-resource-tag-conditions-and-together-denied-when-either-fails.

=== Cause 4 of 4: the ListUserTags 501 scaffold also blocks the real-call leg of two policy-composition checks, which no filed issue re-replays. ===

AWS: ListUserTags is bound to the service and returns the user's tag list (HTTP 200, possibly empty) for an existing user, with NoSuchEntity (404) as its client refusal; there is no modeled "not implemented" outcome. In both checks below it is the action under test: once as the complement member of an `Allow NotAction [iam:ListAccessKeys] Resource <own ARN>` statement (so AWS answers 200), and once as the single action a group-attached managed `Deny` names (so AWS answers `AccessDenied` 403 while the user is in the group and 200 after it leaves).

Emulator: ListUserTags answers HTTP 501 with error code `NotImplemented`. Both checks poll the real signed `list_user_tags` call for `OK` as their positive leg before asserting anything about the deny, so the poll can never converge and the harness reports `Check timed out after 60.0s` for each — no emulator decision is ever observed, and the authorization claim each check exists to grade is never reached. Hypothesis: for iam.sep-policy-composition-group-managed-deny-overrides-user-allows-denied-by-simulator-and-real-call the 501 is hit at the baseline poll, before `AddUserToGroup` (itself a filed 501 stub) is reached, which is why that check times out rather than erroring; the replay output records only the timeout, so the exact poll is not stated.

Why: two cross-policy composition contracts — that `Allow` + `NotAction` grants the set COMPLEMENT and only on the statement's Resource (never a wildcard grant), and that an explicit `Deny` reaching a user through a group-attached managed policy beats both an inline and an attached-managed `Allow` — are completely ungraded on this emulator. Those are exactly the shapes where over-permission hides, and the emulator currently gives no signal either way.

Fix: the operation's handler — src/ops/list_user_tags.rs — must return the user's stored tags from src/state.rs (NoSuchEntity when the user does not exist) and its SCAFFOLDED marker must be deleted. That is the same stub the already-filed 20261025T000319Z-iam-listusertags-stub.md owns; this cause exists because that issue's replay keys are other units, so a fixer closing it would never re-replay these two checks and would report them as still failing. After the stub is implemented these two checks must be re-run, and any remaining divergence will be in the shared evaluator's `NotAction` complement handling (services/common/src/iam_authorization.rs) or in whether src/state/authorization.rs walks group membership when collecting the principal's documents (`store.principal_policies(&user.arn)` in src/state/authorization.rs line 157).

Traces: iam.sep-policy-composition-allow-notaction-grants-complement-on-named-resource-only-denied-elsewhere, iam.sep-policy-composition-group-managed-deny-overrides-user-allows-denied-by-simulator-and-real-call.
