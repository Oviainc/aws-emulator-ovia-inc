# Glue catalog read and create refusals restate the rule and misclassify an unknown CatalogId

> _Note: this issue was identified against the code base at commit `deff4a6e6d31627acea4018c09886a861433b132`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTable

## Description
Four net-new wire-replay root causes in the Glue Data Catalog's refusal path. Three carry the right HTTP status and error code but a message the emulator authored itself — it states a different rule, interpolates request values where Glue's text is fixed, or replaces Glue's fixed sentence with a request-derived one. The fourth also returns the WRONG error code, one that is not in the operation's modeled error set. A fixer must close ALL FOUR before submitting; each has its own fixture#step and they are independent code paths.

Cause 1 of 4: CreateTable carrying OpenTableFormatInput whose Iceberg input is absent is refused with a message that blames the wrong member. AWS: Smithy (services/service-com-amazonaws-glue-awsglue/smithy-model/com-amazonaws-glue-awsglue.json) models CreateTable with optional TableInput and optional OpenTableFormatInput, and the client error InvalidInputException (errorKind client, httpError 400, documented 'The input provided was not valid'). Recorded response: HTTP 400, __type InvalidInputException, Message exactly 'CreateIcebergTableInput cannot be equal to null' — 100% FIXED text naming the missing nested input shape, with no request value interpolated at all. Emulator: same status and same code, but Message 'TableInput is required unless OpenTableFormatInput is supplied'. Why: the emulator states a rule Glue does not apply here — it blames the top-level TableInput when the actual fault is an incomplete OpenTableFormatInput, so a client (or a CloudFormation/Iceberg tool) that reads the message supplies TableInput and is refused again by real Glue, and message-equality assertions never match. Fix: CreateTable's input validation, in the OpenTableFormatInput branch of the handler (services/service-com-amazonaws-glue-awsglue/src/ops/create_table.rs) — the absent Iceberg sub-input must raise InvalidInputException with Glue's fixed sentence instead of the generic 'TableInput is required ...' rule. Traces: glue-cflog-create-input-validation-mistakes#task#5.

Cause 2 of 4: GetTables with MaxResults 0 is refused with a message that interpolates the request value and the limit. AWS: Smithy GetTables.MaxResults targets CatalogGetterPageSize with @range min 1 max 100, and GetTables models InvalidInputException (400). Recorded response: HTTP 400, InvalidInputException, Message exactly 'MaxItems has to be a positive number' — entirely FIXED text: no rejected value, no limit, and Glue's internal member name 'MaxItems' rather than the wire member name. Emulator: 'MaxResults 0 is below the minimum page size of 1', which interpolates the request's value and the modeled minimum and names the wire member. Why: the message is the only statement of the rule on the wire; a client matching Glue's documented sentence sees text AWS never produces, and the emulator's text varies per request where AWS's is constant, so nothing can match it exactly. Fix: GetTables' page-size validation message (services/service-com-amazonaws-glue-awsglue/src/ops/get_tables.rs and the shared page-size validator it calls) must emit the fixed sentence. Traces: glue-cflog-get-tables-paginated-and-filtered#task#11; the same cluster also covers glue-tsd-attributes-to-get-names-then-describe#task#4 and #task#6 and glue-tsd-expression-filter-mistakes#task#7.

Cause 3 of 4: GetTable naming a DATABASE that does not exist reports GetDatabase's templated sentence. AWS: Smithy GetTable takes required DatabaseName and Name and models EntityNotFoundException (client, httpError 400, 'A specified entity does not exist'). Recorded response: HTTP 400, EntityNotFoundException, Message exactly 'Entity Not Found' — entirely FIXED text, with no name interpolated and no trailing period, and the same text whichever of the two lookups missed. Emulator: status (400) and code (EntityNotFoundException) are already right; the Message is 'Database ' + the request's DatabaseName + ' not found.' — the database name in any one replay line is a per-run generated name filling that template, not part of the requirement. Why: the message is the only thing distinguishing this refusal, and the emulator's varies per request where AWS's is constant, so a client verifying that a table (or its database) is really gone cannot recognize the refusal. Fix: the database-lookup-miss branch of the GetTable handler (services/service-com-amazonaws-glue-awsglue/src/ops/get_table.rs) must raise the same fixed text its table-miss branch already uses (crate::state::messages::TABLE_ENTITY_NOT_FOUND) instead of crate::state::messages::database_not_found; GetDatabase's own templated message must stay as it is. Traces: glue-cflog-table-before-database-then-duplicate-retry#teardown#11.

Cause 4 of 4: GetTables against a CatalogId that does not exist answers AccessDeniedException instead of EntityNotFoundException. AWS: Smithy GetTables models exactly EntityNotFoundException, FederationSourceException, FederationSourceRetryableException, GlueEncryptionException, InternalServiceException, InvalidInputException and OperationTimeoutException — AccessDeniedException is NOT a modeled error of this operation. Recorded response: HTTP 400, __type EntityNotFoundException, Message exactly 'Catalog not found.' — entirely FIXED text. Emulator: HTTP 400 with __type AccessDeniedException and an IAM-shaped sentence of the form 'User: <caller principal ARN> is not authorized to perform: glue:GetTables on resource: <catalog ARN built from the requested CatalogId> because no resource-based policy allows the glue:GetTables action'; the ARNs in a replay line come from the emulator's identity and the request's CatalogId and are not part of any requirement. Why: the error CODE is wrong and outside the operation's modeled set, so a strongly typed SDK cannot map it, and the refusal mis-attributes a non-existent catalog to an authorization failure — a client adds IAM or resource policy to fix a catalog that simply does not exist, and never falls into its not-found path. Fix: GetTables' catalog resolution (services/service-com-amazonaws-glue-awsglue/src/ops/get_tables.rs) must resolve the catalog and raise EntityNotFoundException('Catalog not found.') before the foreign-catalog authorization decision (crate::state::foreign_catalog_refusal) is taken. Traces: glue-tsd-foreign-and-malformed-catalog-id#task#7; the same cluster also covers glue-tsd-page-size-and-parameter-shape-mistakes#task#5.

Related open issues, named for the fixer — none of them carries these fixture#step replay keys, so none covers these steps (the replay reports all four clusters as unowned): 20261102T132146Z-glue-refusal-messages-name-the-wrong-member-path.md describes causes 1 and 2 in prose but its Issue-Trace-Ids list fixture ids with no step half, so its replay pointer does not bind these steps; 20261102T132146Z-glue-entity-lookup-refusals-report-the-wrong-message.md describes cause 3 and the GetDatabase analogue of cause 4 with the same step-less pointer; 20261101T211008Z-glue-gettable-reports-an-absent-database-with-the.md and 20261029T185330Z-glue-10-net-new-root-causes-ten-refusal.md describe cause 3's behaviour from behavioral checks only. Fixing the shared lookup-miss and catalog-resolution paths should close those too.
