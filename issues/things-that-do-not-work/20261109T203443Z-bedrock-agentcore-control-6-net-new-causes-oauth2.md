# bedrock-agentcore-control: 6 net-new causes — OAuth2 credentialProviderArn namespace makes CreateConsentPortal unusable, GetOauth2CredentialProvider/discoveryUrl refusal wording, UpdateOauth2CredentialProvider and UpdatePaymentManager error semantics unreachable, and dense EC2 subnet ids

> _Note: this issue was identified against the code base at commit `19c62db1539bfab1a25075fa0f8ae1a77a215876`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateOauth2CredentialProvider

## Description
This bundle has 6 net-new root causes, all of them on checks the suite report lists under `### bedrock-agentcore-control` and none of them marked ALREADY FILED or OWNED.

Cause 1 of 6 — the OAuth2 credential provider ARN is minted in a service namespace CreateConsentPortal's own input pattern rejects, so the whole consent-portal surface is unreachable.
AWS: CreateOauth2CredentialProvider returns a `credentialProviderArn` that CreateConsentPortal accepts as `idpConfig.credentialProviderArn`; the two surfaces compose. Smithy: CreateConsentPortal input `idpConfig` -> ConsentPortalIdpConfig, whose `credentialProviderArn` carries @pattern `arn:(aws|aws-cn|aws-us-gov|aws-iso|aws-iso-b|aws-iso-e|aws-iso-f|aws-eusc):bedrock-agentcore:[a-z0-9-]{1,32}:[0-9]{12}:token-vault/[a-zA-Z0-9_-]{1,64}/oauth2credentialprovider/[a-zA-Z0-9_-]{1,128}` — i.e. the `bedrock-agentcore` ARN service namespace. CreateOauth2CredentialProviderResponse.credentialProviderArn -> CredentialProviderArnType still carries the legacy @pattern `^arn:(aws|aws-us-gov):acps:...:token-vault/<vault>/oauth2credentialprovider/<name>$`, so the model is internally inconsistent and the composing pattern (bedrock-agentcore) is the one AWS actually honours.
Emulator: `crate::state::oauth2_credential_provider_arn(&region, vault, &name)` (called from ops/create_oauth2_credential_provider.rs) mints the ARN in the legacy namespace, not `bedrock-agentcore`. CreateConsentPortal then refuses the provider's own ARN with 400 ValidationException and the message "1 validation error detected: Value at 'idpConfig.credentialProviderArn' failed to satisfy constraint: Member must satisfy regular expression pattern: <the ConsentPortalIdpConfig pattern above>" — fixed text apart from the member path and the pattern, which are both constants of the model. The already-filed 20261108T204036Z-bedrock-agentcore-control-api-key-credential-provider-representation-diverges-acps-arn.md records the identical namespace defect for the API-KEY provider ARN and confirms AWS issues `arn:aws:bedrock-agentcore:<region>:<account>:token-vault/default/<kind>/<name>`; it does NOT cover the OAuth2 ARN builder or this CreateConsentPortal blockage, which is why this is net-new.
Why: a client cannot create a consent portal at all. Every call that hands an OAuth2 provider ARN to another AgentCore surface (consent portals, gateway credential-provider configurations, IAM/resource policies built from the ARN) is refused or mis-scoped, and the ARN a client persists as the provider's identity names a namespace AWS does not issue.
Fix: the shared OAuth2 credential-provider ARN builder in the service state (used by CreateOauth2CredentialProvider's and GetOauth2CredentialProvider's response construction) — build it in the `bedrock-agentcore` namespace so it satisfies ConsentPortalIdpConfig's pattern.
Traces: bedrock-agentcore-control.consent-portal-lifecycle-transitions, bedrock-agentcore-control.update-consent-portal-after-final-state-blocked.

Cause 2 of 6 — GetOauth2CredentialProvider's not-found message is reworded and leaks the requested name.
AWS: POST /identities/GetOauth2CredentialProvider for a name that holds no OAuth2 provider (here, a name that exists only as an API-KEY provider) answers 404 ResourceNotFoundException with the message "CredentialProvider not found" — entirely fixed text, naming no identifier and not naming the provider TYPE. Smithy: GetOauth2CredentialProvider errors include ResourceNotFoundException @httpError 404. The sibling GetApiKeyCredentialProvider refusal does name the request's value ("ApiKeyCredentialProvider not found for " + the requested name), so the two templates genuinely differ and the OAuth2 one must not be derived from it.
Emulator: 404 with "Oauth2CredentialProvider not found for <name>" — the provider type plus the name from the request, where AWS emits neither.
Why: a client or test matching AWS's sentence does not match, and the emulator echoes back the requested name on a path where AWS deliberately says nothing about it, so cross-type probing becomes a name-existence oracle.
Fix: `crate::state::oauth2_credential_provider_not_found`, as called from services/service-com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol/src/ops/get_oauth2_credential_provider.rs — give the OAuth2 read its own fixed sentence instead of the shared "<Type> not found for <name>" template.
Traces: bedrock-agentcore-control.credential-provider-type-isolation-get-rejected.

Cause 3 of 6 — CreateOauth2CredentialProvider's discoveryUrl refusal quotes a stale regular expression, and therefore enforces a different accepted set.
AWS: a `oauth2ProviderConfigInput.customOauth2ProviderConfig.oauthDiscovery.discoveryUrl` that is not a discovery endpoint is refused with 400 ValidationException whose message is the counted-constraint form: fixed text "1 validation error detected: Value at '" + the member path + "' failed to satisfy constraint: Member must satisfy regular expression pattern: " + the pattern, where the pattern AWS states is `[^\s?#]+/\.well-known/(openid-configuration|oauth-authorization-server)(/[^\s?#]+)?`. The member path is fixed for this input shape; nothing in the message comes from the request's value. Smithy (on disk): Oauth2Discovery.discoveryUrl -> DiscoveryUrlType @pattern `^.+/\.well-known/(openid-configuration|oauth-authorization-server)$` — the model shipped in this repo carries the OLDER pattern, so for this message the recorded AWS behavior, not the on-disk pattern, is the requirement.
Emulator: 400 ValidationException with the right code and the right counted form, but it quotes the on-disk pattern `.+/\.well-known/(openid-configuration|oauth-authorization-server)`. Because the quoted expression is what it validates against, the accepted set also diverges: AWS accepts a discovery URL with a trailing path segment after the well-known suffix and rejects one containing whitespace, `?` or `#`, while the emulator does the opposite on both.
Why: a client matching AWS's refusal sentence never matches, and a legitimate discovery URL carrying a trailing path segment (an AWS-accepted form) is refused by the emulator while a URL with a query string or fragment is wrongly accepted and stored.
Fix: the discoveryUrl validation in CreateOauth2CredentialProvider's input validation (`crate::state::RequestedOauth2Configuration::from_input`, which the handler calls because the pattern sits inside a union the framework's constraint walk does not reach) — validate against, and quote, AWS's current pattern.
Traces: bedrock-agentcore-control.create-oauth2-credential-provider-malformed-input-rejected.

Cause 4 of 6 — UpdateOauth2CredentialProvider answers 501 NotImplemented, so its DecryptionFailure path never exists.
AWS: rotating an EXTERNAL-secret OAuth2 provider onto a Secrets Manager secret whose KMS key is DISABLED is refused with DecryptionFailure and the message "Unable to decrypt the provided secret. Verify KMS key permissions." — entirely fixed text, no request values — and the provider's stored configuration is left unchanged; re-enabling the key makes the byte-identical rotation succeed. Smithy: UpdateOauth2CredentialProvider models DecryptionFailure @httpError 400 (as does CreateOauth2CredentialProvider, where the emulator already implements it via `crate::state::SECRET_UNDECRYPTABLE_MESSAGE`).
Emulator: the operation is an unimplemented scaffold stub and answers error code `NotImplemented` ("operation UpdateOauth2CredentialProvider is scaffolded but not implemented in this emulator") for every request, refused or not.
Why: no client can rotate an OAuth2 provider's credentials at all, and a client's KMS-failure branch is never exercised.
Fix: ops/update_oauth2_credential_provider.rs. The bare "implement the stub" work item is already filed for you from the checkout (the suite marks bedrock-agentcore-control.oauth2-credential-provider-lifecycle-transitions ALREADY FILED against this same file); what is net-new here and must also hold once it is implemented is the refusal semantics above — DecryptionFailure with that exact sentence, and the stored clientId unchanged after the refused rotation.
Traces: bedrock-agentcore-control.update-oauth2-credential-provider-decryption-failure-on-rotated-kms.

Cause 5 of 6 — UpdatePaymentManager answers 501 NotImplemented, so its concurrency contract never exists.
AWS: two concurrent UpdatePaymentManager calls against one READY payment manager either both apply (serialized internally) or the loser is refused with 409 ConflictException whose message is fixed text "Conflict while updating payment manager: accountId=" + the caller's account id + ", managerId=" + the paymentManagerId from the request + ", version=" + the manager version the writer raced against; the manager then settles READY carrying one of the two submitted descriptions. Smithy: UpdatePaymentManager models ConflictException @httpError 409. Only the account id, manager id and version number come from the request/state; the rest of the sentence is fixed.
Emulator: the operation is an unimplemented scaffold stub and answers error code `NotImplemented`, so neither writer applies and the ConflictException path is unreachable.
Why: a payment manager can never be updated, and a client's conflict-retry loop is never exercised; a 501 is also not retryable the way a 409 is, so the client gives up instead of retrying.
Fix: ops/update_payment_manager.rs. As with cause 4, the bare stub work item is already filed for you (the suite marks bedrock-agentcore-control.payment-manager-lifecycle-transitions ALREADY FILED against this file); net-new here is the concurrency contract and the exact ConflictException sentence above.
Traces: bedrock-agentcore-control.update-payment-manager-concurrent-update-conflict.

Cause 6 of 6 — EC2 subnet ids are minted so densely that a well-formed-but-absent subnet id cannot be derived, and DescribeSubnets does not refuse one.
AWS: a subnet id is `subnet-` followed by 17 effectively random hexadecimal characters, so changing one character of a real id yields an id no subnet holds, and ec2 DescribeSubnets with `SubnetIds=[that id]` is refused with `InvalidSubnetID.NotFound`. Recorded behavior only for the id format; the refusal code is EC2's documented not-found code for an explicitly named subnet id.
Emulator: after the check created a VPC with three subnets, ec2 DescribeSubnets(SubnetIds=['subnet-00000000000000090']) answered 2xx with a non-empty `Subnets` list for an id the check never created — the assertion that ran was `premise broken: 'subnet-00000000000000090' actually exists in this account`. Hypothesis: the emulator mints subnet ids as a dense zero-padded counter, so ids differing in one character are all live at once (AWS's random 17-hex ids are not); a second possibility consistent with the same observation is that DescribeSubnets ignores the `SubnetIds` filter and returns every subnet of the account. Either way the emulator reports a subnet for an id it never issued.
Why: any caller that validates a subnet id, or that asserts a given subnet is absent before binding a resource to it, gets the wrong answer; a negative test can never be constructed, and an id-existence check silently passes for ids that do not exist.
Fix: the ec2 crate — DescribeSubnets' `SubnetIds` filtering and its not-found path (it must raise `InvalidSubnetID.NotFound` for an explicitly named id no subnet holds), and the subnet-id minting in ec2's state so ids are not dense neighbours. NOTE on this issue's `service` field: the failing check is listed by the suite under `### bedrock-agentcore-control` (it is a bedrock-agentcore-control browser VPC check that uses ec2 only to establish its premise), so per the report's heading that is this issue's service token — but the component to change is the ec2 emulator, not bedrock-agentcore-control.
Traces: bedrock-agentcore-control.browser-vpc-network-mode-requires-real-vpc-config.
