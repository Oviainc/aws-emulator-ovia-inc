# cloudformation__iam__lambda__s3: a Custom:: resource backed by an out-of-band Lambda provider never settles — it stays CREATE_IN_PROGRESS until CloudFormation's own wait runs out, so the happy-path stack rolls back and a provider denied s3:PutObject reports a stabilisation timeout instead of AccessDenied

## Description
One net-new behavioral root cause of this service group, grounded in two failing behavioral checks of this replay. Neither check is marked OWNED or ALREADY FILED in the replay report. The open issue 20261104T160000Z-cloudformation-iam-lambda-s3-six-causes-awaiting-the-lambda-provisioner-and-an-in-process-runtime.md does list one of these check ids (cfn-custom-resource-role-least-privilege-positive) under its cause 6, but its replay key for it is `cloudformation__iam__lambda__s3|GetObject|NoSuchKey` — the stack then reached CREATE_COMPLETE and only the object the provider should have written was missing. The emulator's behaviour has since changed shape: the stack no longer completes at all, it fails the custom resource and rolls back, and the sibling negative check now fails on the refusal WORDING. Those are different observables with different keys, so they are filed here. That issue and 20261025T180059Z-cloudformation-custom-resource-providers-and-hook-configuration.md are named as the neighbourhood, not as cover.

Cause 1 of 1: CloudFormation never receives a response for a Custom:: resource whose ServiceToken is a Lambda function created out of band, so the resource is abandoned on a stabilisation timeout and the stack rolls back — on the happy path, and with the wrong reason on the denial path.
AWS: recorded behavior only for the custom-resource protocol; the shapes are modelled (Smithy com.amazonaws.cloudformation#StackStatus includes CREATE_IN_PROGRESS, CREATE_COMPLETE, ROLLBACK_COMPLETE, UPDATE_COMPLETE; com.amazonaws.cloudformation#ResourceStatus includes CREATE_FAILED; com.amazonaws.cloudformation#StackEvent.ResourceStatusReason is documented as the 'Success/failure message associated with the resource'). CloudFormation invokes the ServiceToken function with a Create request carrying a pre-signed ResponseURL; the handler does its work (here s3:PutObject of a body under a key) and PUTs SUCCESS, so the resource reaches CREATE_COMPLETE, the stack reaches CREATE_COMPLETE, and s3:GetObject on that key answers 200 with the written body. An UpdateStack that changes the resource's properties sends an Update request to the same provider, which writes the new key, and the key written on Create is untouched (the stack reaches UPDATE_COMPLETE). When the provider's execution role lacks s3:PutObject, the handler's PutObject is refused AccessDenied and the handler answers FAILED with that refusal as its Reason; CloudFormation records it on the resource's CREATE_FAILED event as `Received response status [FAILED] from custom resource. Message returned: <the provider's reason> (RequestId: <RequestId>)` — fixed text whose variable parts are the provider's own reason text (which contains the S3 error code AccessDenied) and the RequestId of the request being answered — and the stack rolls back to ROLLBACK_COMPLETE with s3:HeadObject on the key answering 404.
Emulator: no provider response is ever recorded. On the happy path the create ends ROLLBACK_COMPLETE instead of CREATE_COMPLETE (so the v1 object is never written and the UpdateStack half is never reached). On the denial path the stack does roll back, but the custom resource's CREATE_FAILED ResourceStatusReason is the emulator's own stabilisation-timeout sentence — `Custom::S3Writer <stack>-Writer-<suffix> was still CREATE_IN_PROGRESS when the wait for it to be created ran out` — which names neither the provider's answer nor AccessDenied, and is not a wording AWS produces for any error class. The two paths are therefore indistinguishable: a provider that would have succeeded and one that was denied both end as the same timeout.
Why: a client cannot deploy any template using the custom-resource extension point against this emulator, and when a deploy fails it is told only that a wait ran out. The denial that actually caused the failure (an execution role missing s3:PutObject) is invisible, so the one diagnostic AWS guarantees — the provider's own failure reason, verbatim, on the resource's CREATE_FAILED event — is lost, and a client cannot tell a permissions problem from a hung provider, a bad handler or a missing invoke permission.
Fix: the cloudformation crate's custom-resource provisioning and stabilising path — invoke the ServiceToken function, accept the provider's response at the ResponseURL, transition the resource to CREATE_COMPLETE/CREATE_FAILED on it, and wrap a FAILED answer's reason into ResourceStatusReason in AWS's `Received response status [FAILED] from custom resource. Message returned: … (RequestId: …)` form rather than falling through to a stabilisation-timeout sentence — together with the lambda Invoke execution path that must actually run the provider's deployment package (and have its S3 call authorized against the function's execution role).
Traces: cloudformation__iam__lambda__s3.cfn-custom-resource-role-least-privilege-positive, cloudformation__iam__lambda__s3.cfn-custom-resource-lambda-missing-s3-permission-negative. Relevant components: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/custom_resource.rs, services/service-com-amazonaws-cloudformation-cloudformation/src/state/stabilising.rs.

## Evidence
Check cloudformation__iam__lambda__s3.cfn-custom-resource-role-least-privilege-positive [mismatch] — happy path.
Setup: an S3 bucket; an IAM role for Lambda whose extra statement is {Effect: Allow, Action: s3:PutObject, Resource: arn:aws:s3:::<bucket>/*}; a Lambda function created out of band with that role; CreateStack with a template declaring a Custom::S3Writer whose ServiceToken is that function ARN and whose properties name the bucket, the key and the body.
Expected: DescribeStacks StackStatus == 'CREATE_COMPLETE' and s3:GetObject on the v1 key returning the declared body; then UpdateStack to a new key/body -> 'UPDATE_COMPLETE', the v2 object written, the v1 object unchanged.
Actual, from the replay: `AssertionError: create ended in ROLLBACK_COMPLETE` (check line 51). The UpdateStack half was never exercised.

Check cloudformation__iam__lambda__s3.cfn-custom-resource-lambda-missing-s3-permission-negative [mismatch] — denial path.
Setup: the same shape with the provider role carrying logs permissions only and no S3 access.
Passes: DescribeStacks reaches 'ROLLBACK_COMPLETE', and a CREATE_FAILED event exists for LogicalResourceId 'Writer'.
Fails: the reason on that event. Expected a ResourceStatusReason containing 'AccessDenied' (AWS's form being `Received response status [FAILED] from custom resource. Message returned: <provider reason naming AccessDenied> (RequestId: <uuid>)`). Actual: `AssertionError: expected AccessDenied in the custom resource's failure reason, got: 'Custom::S3Writer sim2real-xsvc-stk-bad-1e0b74b30302-Writer-E8E154B63D3E was still CREATE_IN_PROGRESS when the wait for it to be created ran out'`. The fixed text of the diverging emulator message is ` was still CREATE_IN_PROGRESS when the wait for it to be created ran out`, prefixed by the resource type and physical id taken from the stack's state; the stack name and suffix are per-run values. AWS emits no such wording for this error class.

## Steps to Reproduce
1. Create an S3 bucket. Create an IAM role for lambda.amazonaws.com with basic logs permissions plus {Allow, s3:PutObject, arn:aws:s3:::<bucket>/*}, and create a Lambda function with that role whose handler PutObjects a body at a key given in the custom resource's ResourceProperties and then answers the CloudFormation request with SUCCESS.
2. CreateStack with a template whose only resource is a Custom::S3Writer with ServiceToken = that function ARN plus Bucket/Key/Body properties. Poll DescribeStacks to a terminal status: expected CREATE_COMPLETE with the object readable via s3:GetObject; observed ROLLBACK_COMPLETE.
3. UpdateStack the same stack with a new Key/Body: expected UPDATE_COMPLETE with the new object written and the first one intact (unreachable today).
4. Repeat step 2 with a provider role that has NO s3 permissions. The stack does reach ROLLBACK_COMPLETE; call DescribeStackEvents and read the ResourceStatusReason of the 'Writer' CREATE_FAILED event. Expected it to carry the provider's own failure reason naming AccessDenied; observed the emulator's '… was still CREATE_IN_PROGRESS when the wait for it to be created ran out' sentence. s3:HeadObject on the key correctly answers 404.
5. Re-replay: cloudformation__iam__lambda__s3.cfn-custom-resource-role-least-privilege-positive, cloudformation__iam__lambda__s3.cfn-custom-resource-lambda-missing-s3-permission-negative.
