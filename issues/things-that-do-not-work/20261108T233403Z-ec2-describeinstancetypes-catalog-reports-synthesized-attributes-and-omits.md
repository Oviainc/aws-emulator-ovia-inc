# ec2 DescribeInstanceTypes catalog reports synthesized attributes and omits modeled members

> _Note: this issue was identified against the code base at commit `3b62b2c2884780aa78691e31a574f6e99c14f5dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 with a well-formed InstanceTypeInfo list, but the per-instance-type attribute values are SYNTHESIZED from a generic formula instead of the per-type data AWS publishes, and several modeled members are left out of the projection entirely. The fault is in the emulator's static instance-type catalog (and in the InstanceTypeInfo projection that drops members), so it reproduces identically for every instance family the corpus asks about.

Two symptom families recur in every cause below:
(a) OMITTED modeled members — the emulator emits no element at all where AWS always emits one: instanceTypeSet.item[].cpuBurstModel, .phcSupport, .rebootMigrationSupport, .nitroEnclavesSupport, .nitroTpmSupport, .autoRecoverySupported, .supportedBootModes, and under networkInfo: .defaultNetworkCardIndex, .enaSrdSupported, .flexibleEnaQueuesSupport, .maximumNetworkCards, .networkCards, .secondaryNetworkSupported, .trafficMirroringSupport, .efaSupported/.efaInfo.
(b) WRONG values from a one-size-fits-all formula — ebsInfo.maximumEbsAttachments is pinned at 28 regardless of type; ebsInfo.attachmentLimitType is always 'shared'; networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout is always 432000; and ebsInfo.ebsOptimizedInfo.{baseline,maximum}{BandwidthInMbps,Iops,ThroughputInMBps}, instanceStorageInfo.disks.item.count/.sizeInGB, instanceStorageInfo.totalSizeInGB, memoryInfo.sizeInMiB, networkInfo.networkPerformance, networkInfo.ipv4AddressesPerInterface/.ipv6AddressesPerInterface/.maximumNetworkInterfaces, processorInfo.sustainedClockSpeedInGhz, hibernationSupported and vCpuInfo.defaultCores/.defaultThreadsPerCore/.validCores/.validThreadsPerCore are scaled off a default rather than read from the type's published specification.

This bundle carries 4 causes, one per diverging fixture step. The IDENTICAL cluster (same divergence_key family service=ec2|DescribeInstanceTypes|status=200->200) recurs in 61 further steps of the ec2-catalog-describe-instance-types-* fixture family — 65 net-new clusters in all for this replay — and one corrected catalog closes all of them, so the whole ec2-catalog-describe-instance-types-* family should be re-replayed, not only the four steps named here.
