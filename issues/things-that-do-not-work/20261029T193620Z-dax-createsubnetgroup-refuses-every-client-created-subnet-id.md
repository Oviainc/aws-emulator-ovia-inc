# dax: CreateSubnetGroup refuses every client-created subnet id, and the default parameter group's delete refusal carries emulator-authored wording (2 causes)

> _Note: this issue was identified against the code base at commit `f2787435e57e1f73549a447346b8d4a825f78f07`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSubnetGroup

## Description
Two net-new behavioral root causes in the DAX control plane, grounded in the behavioral replay of this emulator. A fixer must close BOTH before submitting. Cause 1 is the same handler/state defect already described as Cause 1 of the open wire issue 20261029T172212Z-dax-create-path-refuses-valid-requests-and-raises.md (CreateSubnetGroup refusing a group AWS accepts); that issue is named here because it is NOT marked as owning these behavioral checks, and these four check ids are the behavioral grounding that must re-pass.

Cause 1 of 2: CreateSubnetGroup refuses SubnetIds that name subnets the caller just created in EC2, so no DAX subnet group — and therefore no DAX cluster — can ever be created.
AWS: Smithy (services/service-com-amazonaws-dax-amazondaxv3/smithy-model/com-amazonaws-dax-amazondaxv3.json): CreateSubnetGroup input SubnetGroupName (String, @required), SubnetIds (SubnetIdentifierList, @required), Description (String); output member SubnetGroup; success status 200. Modeled refusals for a bad subnet are InvalidSubnet (400) and SubnetNotAllowedFault (400); InvalidParameterValueException is not even modeled on this operation. AWS resolves each element of SubnetIds against the subnets that exist in the caller's account and Region — including subnets created moments earlier by ec2:CreateSubnet in a caller-created VPC — and answers 200 with the SubnetGroup (name lower-cased, VpcId and each Subnet's SubnetAvailabilityZone filled in). Only an identifier that resolves to nothing is refused.
Emulator: answers 400 InvalidParameterValueException with message "Some input subnets in :[<subnet ids>] are invalid." for subnet ids that DO exist in the emulator's EC2 state. The fixed text is "Some input subnets in :[" + the unresolved identifiers joined by ", " + "] are invalid."; the identifiers are values taken from the request (the ids in the replay output are one run's values, not part of the template). services/service-com-amazonaws-dax-amazondaxv3/src/ops/create_subnet_group.rs resolves every element through crate::state::resolve_subnet(&region, subnet_id), which matches only against a SYNTHETIC per-Region subnet set derived in src/state.rs (region_subnets(): one subnet per AZ, subnet_id derived from a hash of the availability-zone name). It never consults the EC2 service's subnet state, so any identifier a client actually holds is "unresolved". The error class is also wrong: InvalidParameterValueException is not a modeled error of CreateSubnetGroup, where InvalidSubnet is.
Why: a client cannot create a DAX subnet group at all. Everything downstream is unreachable — CreateCluster with SubnetGroupName, DescribeSubnetGroups/DeleteSubnetGroup lifecycle, the SubnetGroupInUseFault refusal, RebootNode and the cluster state machine — and the failure surfaces as a parameter error naming the client's own well-formed, existing subnet ids, pointing the client at its own correct input. A client also cannot catch it by error code, since the code is not one the model declares for the operation.
Fix: CreateSubnetGroup's handler and the subnet resolution it calls — services/service-com-amazonaws-dax-amazondaxv3/src/ops/create_subnet_group.rs (the resolve loop) together with resolve_subnet/region_subnets/invalid_subnets in services/service-com-amazonaws-dax-amazondaxv3/src/state.rs: a subnet id that exists in the emulator's EC2 state must resolve (VpcId and AZ taken from that subnet) and the create must store the group and answer 200; a genuinely unresolvable id belongs in the modeled InvalidSubnet/SubnetNotAllowedFault class, not InvalidParameterValueException.
Traces: dax.subnet-group-lifecycle-crud, dax.subnet-group-in-use-rejected, dax.delete-cluster-while-creating-rejected, dax.reboot-node-state-transition (all four fail on the setup CreateSubnetGroup call).

Cause 2 of 2: DeleteParameterGroup on the system default parameter group answers the right error code with an emulator-invented message.
AWS: Smithy: DeleteParameterGroup input ParameterGroupName (String, @required); modeled errors InvalidParameterValueException (400, "The value for a parameter is invalid."), InvalidParameterGroupStateFault (400), ParameterGroupNotFoundFault (404). Recorded behavior: deleting the account/Region's system default group (the one whose name begins "default.") is refused 400 InvalidParameterValueException with the message "The parameter CacheParameterGroupName is not a valid identifier. Identifiers must begin with a letter; must contain only ASCII letters, digits, and hyphens; and must not end with a hyphen or contain two consecutive hyphens." — that text is entirely FIXED, with no part interpolated from the request (AWS refuses the "default." name on the identifier rule, because the dot is not an allowed identifier character; the member it names is CacheParameterGroupName). The group is left in place and a subsequent DescribeParameterGroups still reports it.
Emulator: status 400 and code InvalidParameterValueException match, but the message is "Default parameter group cannot be deleted." — authored in services/service-com-amazonaws-dax-amazondaxv3/src/ops/delete_parameter_group.rs (the `group.default_group` branch, the literal passed as InvalidParameterValueException.message).
Why: a client that asserts on or surfaces the refusal message (log scraping, UI text, tests pinned to AWS wording) sees text AWS never emits, and the message no longer tells the client WHY the name was rejected (the identifier rule), which is the part AWS's wording carries.
Fix: DeleteParameterGroup's handler in services/service-com-amazonaws-dax-amazondaxv3/src/ops/delete_parameter_group.rs — the default-group branch must raise InvalidParameterValueException with AWS's fixed identifier-rule wording (shared with the other DAX parameter-group paths via src/state.rs if the message is reused).
Traces: dax.delete-default-parameter-group-rejected.
