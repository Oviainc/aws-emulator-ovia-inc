## What is known

* The control plane the remaining causes build on is in place: `AddRoleToDBInstance`, `RemoveRoleFromDBInstance`, `AddRoleToDBCluster` and `RemoveRoleFromDBCluster` store an association on the resource (validated against the engine version's `SupportedFeatureNames` and the role's trust policy) and `AssociatedRoles` reports it, and `StartExportTask` runs a real export. Both are pinned by `services/service-com-amazonaws-rds-amazonrdsv19/tests/all/rds_s3_integration.rs`, so a fixer need not re-derive them — cause 2's engine statements can read the association to decide whether the statement is permitted.
* The data plane a cause-2 fix extends already exists for DB INSTANCES: `src/state/data_plane/` holds both wire halves, the per-database in-process SQLite engine, and `server_statements.rs`, which is where a statement the embedded engine has no grammar for is served from the instance's own state (that module already serves `CREATE EXTENSION aws_s3`). The S3 object the statement reads or writes is reachable without leaving the process, the way the export reaches it: Amazon S3's own store on the same engine (`src/state/export_objects.rs`).
* The CloudFormation arms for causes 7 to 9 belong in `services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/application_services/databases_and_networks.rs`, beside the `AWS::RDS::DBInstance`, `AWS::RDS::DBSubnetGroup` and parameter-group arms it already carries; `AWS::RDS::DBCluster` and `AWS::RDS::OptionGroup` are already admitted types (`src/state/resource_types.rs`) with no arm behind them.
