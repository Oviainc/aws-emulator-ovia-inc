# apigatewayv2__lambda__logs: the malformed-connection-id fan-out check now reaches no verdict at all — the deployed WEBSOCKET stage neither completes nor refuses the RFC 6455 upgrade, so the check hangs to the harness cap

> _Note: this issue was identified against the code base at commit `7f27151474f220c715589d81820913dcd4b7b62b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
ONE net-new root cause on the apigatewayv2__lambda__logs service token: the single failing check in that group the replay marks neither ALREADY FILED nor OWNED. It must be closed before this issue is submitted.

=== Cause 1 of 1: a WebSocket opening handshake against a deployed apigatewayv2 WEBSOCKET stage is never completed AND never promptly refused — the stage absorbs the upgrade, so the whole scenario stalls and the check expires at the harness's 60 s cap without reaching any assertion ===

AWS: the opening handshake on the execute-api data plane is not a modelled operation, so this is recorded behavior only. Recorded: a `GET /<stage> HTTP/1.1` carrying `Connection: Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Key: <base64 of 16 bytes>` and `Sec-WebSocket-Version: 13`, addressed to a deployed stage of a WEBSOCKET-protocol API, is answered `HTTP/1.1 101 Switching Protocols` with `Upgrade: websocket`, `Connection: Upgrade` and `Sec-WebSocket-Accept: base64(SHA1(Sec-WebSocket-Key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"))`. The $connect route then runs, the service mints the connection id, and that id is what the modelled @connections surface addresses (Smithy, apigatewaymanagementapi restJson1/sigv4: PostToConnection POST /@connections/{ConnectionId}, Data @httpPayload blob @length{min 0,max 131072}, errors ForbiddenException 403 / GoneException 410 / LimitExceededException 429 / PayloadTooLargeException 413; GetConnection GET /@connections/{ConnectionId} code 200; DeleteConnection DELETE /@connections/{ConnectionId} code 204). Crucially, AWS always answers an upgrade request — either the 101 switch or an immediate HTTP refusal status; it never leaves the handshake outstanding. The application contract this check grades is also AWS behaviour: PostToConnection with a syntactically invalid connection id is BadRequestException 400 with the message `Invalid connectionId: <id>` (fixed text "Invalid connectionId: " plus the ConnectionId value taken verbatim from the request), NOT GoneException 410 — so a handler whose catch prunes only on 410 must leave the row in place, while a genuinely live connection on the same stage is still notified.

Emulator: the check now produces `Check timed out after 60.0s` — no verdict, no refusal, no handshake. This is a REGRESSION IN FAILURE MODE from the state recorded in the related open issue 20261104T221013Z-apigatewayv2-lambda-logs-the-malformed-connection-id-fan.md, where the same check reached `_ws_connect` well inside the cap and failed fast on `AssertionError: the WebSocket upgrade to the prod stage answered 404: 'HTTP/1.1 404 Not Found\r\ncontent-type: application/x-amz-json-1.1\r\nx-amzn-errortype: UnknownService...'`. That issue's replay key is bound to that 404 assertion in `_ws_connect`, which is why the replay reports NO owner for this check today. The check's own `_ws_connect` only retries a status >= 500 and asserts on any other non-101 status, so a fast 404 could never consume the cap; a stall means the stage now either holds the upgrade socket open without replying, or answers 5xx repeatedly so the retry loop (3 s sleep, 120 s internal deadline) outlives the 60 s harness cap. Either way the emulator answers neither 101 nor a terminal refusal.

Why: a client relying on AWS's behaviour gets the worst of both worlds. No connection id is ever minted, so $connect/$default/$disconnect never fire, the registration reply never comes back over the socket, the connections table never gains a live row, and server-push fan-out cannot be exercised — the graded contract (a 400 BadRequestException must not trigger a GoneException-only prune while the live UI connection on the same stage is still notified) is ungradeable. Worse than the previous 404: a developer now sees a wss:// client that simply hangs, with no status to diagnose, so correctly configured client code is indistinguishable from a dead endpoint, and any CI job wrapping it burns its whole timeout budget instead of failing fast.

Fix: the emulator's front door / service router plus the apigatewayv2 WEBSOCKET session layer. The router must claim an upgrade request addressed to a deployed WEBSOCKET-protocol API's stage path and hand the connection to the apigatewayv2 service rather than falling through (today it falls through to UnknownService or to nothing at all); the session layer must complete the handshake with 101 + a correct Sec-WebSocket-Accept, mint a connection id, dispatch $connect/$disconnect and route selection, and register the connection in the store the apigatewaymanagementapi @connections handlers read. Two sub-requirements follow: (a) an upgrade that cannot be served must still be answered with a terminal HTTP status immediately, never absorbed; (b) PostToConnection's malformed-id branch must stay BadRequestException 400 `Invalid connectionId: <id>` (it passed before and must not regress to 410 once the data plane exists).

Related (does NOT cover this check): 20261104T160000Z-apigatewayv2-websocket-execute-api-upgrade-remains-unservable.md owns the four sibling checks of this group; 20261104T221013Z-apigatewayv2-lambda-logs-the-malformed-connection-id-fan.md carries this check's OLD 404 replay key and no longer matches its failure; the apigatewaymanagementapi-side issues 20261023T223918Z-… and 20261103T054456Z-… describe the same missing upgrade under a different service token. None of them is marked as owning this check in the replay.
