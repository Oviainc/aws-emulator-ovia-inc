=== Cause 1 of 3: GetSSHPublicKey is an unimplemented 501 scaffold stub, so a nonexistent user is answered NotImplemented instead of NoSuchEntity ===
AWS: Smithy models GetSSHPublicKey with input UserName (userNameType, @required, @length 1..64, @pattern ^[\w+=,.@-]+$), SSHPublicKeyId (publicKeyIdType, @required, @length 20..128, @pattern ^[\w]+$) and Encoding (encodingType, @required, enum PEM|SSH), output SSHPublicKey, and exactly two modeled errors: NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404 — "referenced a resource entity that does not exist") and UnrecognizedPublicKeyEncodingException (UnrecognizedPublicKeyEncoding, HTTP 400). A GetSSHPublicKey naming a UserName that does not exist must therefore be refused HTTP 404 Error.Code `NoSuchEntity` with the message whose fixed text is `The user with name ` + ` cannot be found.` and whose single variable part is the UserName taken verbatim from the request — the same template every other IAM user-addressed Get* uses, which this very check verifies passes for GetUser, GetGroup, GetRole, GetLoginProfile and GetServerCertificate.
Emulator: the operation is a scaffold stub. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/get_ssh_public_key.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its `handle` body is `Err(crate::scaffolded::Scaffolded::not_implemented("GetSSHPublicKey"))`, so the call is answered HTTP 501 with the unmodeled Error.Code `NotImplemented` and the message `operation GetSSHPublicKey is scaffolded but not implemented in this emulator`. Observed: `AssertionError: GetSSHPublicKey: expected NoSuchEntity, got NotImplemented`.
Why: a client cannot exercise the CodeCommit SSH-key surface at all, and — worse for a negative-path harness — the refusal is an unmodeled code with an unmodeled status, so SDK error handling written against NoSuchEntity (retry/branch on a missing user) takes the wrong branch and surfaces a 501 the real API never returns.
Fix: implement the handler in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/get_ssh_public_key.rs (the only file for this operation): resolve UserName in the IAM store, refuse an unknown user with NoSuchEntityException carrying the `The user with name <UserName> cannot be found.` message, refuse an unknown SSHPublicKeyId for an existing user with NoSuchEntityException, refuse an Encoding the key cannot be rendered in with UnrecognizedPublicKeyEncodingException, and delete the SCAFFOLDED marker line. Related open issue, named because it looks similar and does NOT cover this check: 20261025T000319Z-iam-uploadsshpublickey-stub.md is the write side of the same SSH-key surface (UploadSSHPublicKey) and says nothing about GetSSHPublicKey; this replay report attributes UploadSSHPublicKey's blocked checks there and attributes this one to no issue.

=== Cause 2 of 3: the implicit-deny AccessDenied message appends a second 'Go to <console URL> ... authorization id: <id>' sentence AWS does not emit, now on UntagPolicy and ListPoliciesGrantingServiceAccess ===
AWS: Smithy models UntagPolicy with input PolicyArn (arnType, @required, @length 20..2048) and TagKeys (tagKeyListType, @required, @length 0..50) and errors ConcurrentModification 409 / InvalidInput 400 / NoSuchEntity 404 / ServiceFailure 500; ListPoliciesGrantingServiceAccess with input Arn (@required) and ServiceNamespaces (@required, @length 1..200) and errors InvalidInput 400 / NoSuchEntity 404. The authorization refusal (AccessDenied / HTTP 403) is a service-common error whose text is not modeled, so this is recorded behavior only: the refusal of either action for a principal that no identity-based policy permits is exactly ONE sentence, with no trailing period and no pointer sentence — fixed text `User: ` + ` is not authorized to perform: ` + ` on resource: ` + ` because no identity-based policy allows the ` + ` action` (and nothing after `action`). Variable parts, from the signed request and the emulator's own state: the caller ARN (the principal whose access key signed the request), the IAM action of the refused operation (`iam:UntagPolicy` / `iam:ListPoliciesGrantingServiceAccess`, appearing twice), and the resource description IAM uses for that action (`policy <policy-arn>` for UntagPolicy, the target user's ARN for ListPoliciesGrantingServiceAccess). Any one run's account id, user name and policy name merely fill that template.
Emulator: the error code is right (AccessDenied) and the first sentence is right, then a whole extra sentence is appended: `. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`. The divergence is that entire sentence, emitted on every such refusal — not a per-run value inside a message; the per-request authorization id only fills a slot in text that must not be there at all. The expected string is a strict prefix of what was returned in both checks.
Why: policy-troubleshooting tooling, CLI/SDK assertions, log scrapers and parity harnesses that match AWS's documented implicit-deny sentence do not recognise or cannot parse the refusal, even though the decision itself is correct. Hypothesis: the trailer is decided globally in one shared denial-message builder instead of per refusal, so each successive fix flips every refusal at once — this is the third oscillation of the same text (see below).
Fix: the shared authorization-refusal denial-message builder in the IAM crate — the component that renders the AccessDenied message ahead of the operation handlers (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/service.rs and the policy-evaluation/denial-message module it calls). It must select the trailer per refusal (per that action's recorded message) rather than appending or suppressing it unconditionally, so the iam:UntagPolicy and iam:ListPoliciesGrantingServiceAccess implicit-deny messages end at `... action` while refusals AWS does record with the authorization-details pointer keep theirs. Related issues, named because they look similar and do NOT cover these two checks: open 20261028T163805Z-iam-secretsmanager-the-iam-listusers-implicit-deny-accessdenied.md reports exactly this trailer for iam:ListUsers and carries only that check's replay key; open 20261028T012639Z-iam-the-implicit-deny-accessdenied-message-no-longer.md reports the OPPOSITE direction for iam:ListAccessKeys (recording carries the trailer, emulator omitted it); fixed 20261027T032337Z-iam-secretsmanager-iam-accessdenied-message-appends-a-console-url-getrequestauthorizationdetails.md asked for the trailer to be removed from the ListUsers message. === Cause 3 of 3: the four AccessDenied causes on iam:GetUser never settle into four distinct reason clauses — the check exhausts the 60 s cap ===
AWS: Smithy models GetUser with input UserName (existingUserNameType, @length 1..128, @pattern ^[\w+=,.@-]+$) and output User (@required), with only NoSuchEntity 404 / ServiceFailure 500 modeled; the refusal is the service-common AccessDenied / HTTP 403, so the message text is recorded behavior only, read against AWS's documented troubleshooting contract (troubleshoot_access-denied): the reason clause that follows `User: <principal-arn> is not authorized to perform: iam:GetUser on resource: user <target> ` names the CAUSE of the denial and is different for each cause — `because no identity-based policy allows the iam:GetUser action` when nothing allows it, `with an explicit deny in an identity-based policy` when an inline/attached policy denies it, `with an explicit deny in a permissions boundary: <boundary-policy-arn>` when the principal's permissions boundary denies it (the boundary ARN is a variable part taken from the principal's stored PermissionsBoundary), and `with an explicit deny in a session policy` when the assumed-role session's scoped-down policy denies it. All four must be HTTP 403 `AccessDenied`, all four must be pairwise distinct, and each principal must first be SERVED the same operation on a control target it is allowed to read (a boundary/session policy must narrow, not revoke).
Emulator: none of the four denials is ever observed. The check is killed at the harness cap — `Error: Check timed out after 60.0s` — so not one reason clause was asserted on. Every leg of the check is gated on the emulator producing a specific decision: a 3-consecutive-success barrier on the unconditioned control grant, then, per cause, a bounded poll (60 s, 3 s interval) for the FIRST observation that is neither a credential-propagation code nor a success, i.e. for the call to actually be refused. One of those polls never leaves its predicate inside the cap. Hypothesis: at least one of the explicit-deny paths is not applied at all (the call keeps answering 200, so the poll for a settled refusal never terminates) — the stored PermissionsBoundary is accepted and read back by GetUser but not evaluated at authorization time, and/or the per-cause attribution does not exist so no distinct clause can be produced.
Why: a client cannot tell WHY it was denied. Explicit-deny-vs-no-allow, a boundary and a session policy are the three things an operator must distinguish to debug least-privilege, and the emulator either serves the call (silently over-permissive against a policy production refuses) or refuses it without naming the cause. A guardrail validated here tells its author nothing.
Fix: the request authorizer's deny attribution in the iam crate — the component that resolves the signing principal and evaluates identity policies, the stored permissions boundary and the session (scoped-down) policy ahead of the operation handlers (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/service.rs and the policy-evaluation module it calls). It must (a) actually apply an explicit Deny from an inline/attached identity policy, from the principal's PermissionsBoundary and from an AssumeRole session policy, and (b) render the matching reason clause for each, including the boundary's ARN, so the four causes are pairwise distinct. Related open issue, named because it looks similar and does NOT cover this check: 20261028T152840Z-iam-2-net-new-behavioral-root-causes-a.md covers two sibling checks of the same iam-eval-deep family (Date* on aws:CurrentTime, ForAllValues/ForAnyValue on aws:TagKeys) and carries only their replay keys; those are condition-operator gaps, this is deny attribution, and 20261025T102129Z-iam-10-net-new-behavioral-root-causes-simulateprincipalpolicy.md reports the boundary being ignored only inside SimulatePrincipalPolicy, not on a live signed call.
