# healthlake: 3 net-new causes — DatastoreEndpoint is published as a real-AWS host the emulator does not serve, POST /transform-data is answered by the RPC dispatcher (400 SerializationException), and StartDataTransformationJob's not-found uses Get's wording

> _Note: this issue was identified against the code base at commit `01e7e7e4d8371571a5c4b5afb30bf8b87d00507b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeFHIRDatastore, TransformData, StartDataTransformationJob

## Description
Three distinct root causes in the healthlake service, found by replaying the simparity-behavioral-aws-v1 behavioral suite against the emulator built from this checkout (heading '### healthlake': 13/20, 7 failed; 3 of those failures are marked OWNED by 20261029T182942Z-healthlake-data-transformation-profile-surface-7-divergences-fixed.md and are excluded). They share one service and are bundled here; each is numbered and carries its own failing check ids. A fixer must close ALL THREE before submitting.

=== Cause 1 of 3: DatastoreProperties.DatastoreEndpoint is published as a real-AWS hostname, so the FHIR REST data plane is not addressable on the emulator ===
Failing checks: healthlake.fhir-rest-api-native-protocol-roundtrip, healthlake.fhir-import-job-delivers-resource-to-datastore
AWS: Smithy (services/service-com-amazonaws-healthlake-healthlake/smithy-model/com-amazonaws-healthlake-healthlake.json): DescribeFHIRDatastore -> DatastoreProperties, whose member DatastoreEndpoint is REQUIRED and documented as "The Amazon Web Services endpoint for the data store"; the FHIR REST interactions served at it are not modelled, so recorded behavior only. The contract of that member is that the URL it carries is the base address at which THAT service answers the FHIR R4 interactions (create POST [base]/{type}, read GET [base]/{type}/{id}, update PUT [base]/{type}/{id}, search GET [base]/{type}) for SigV4-signed requests with service name 'healthlake'. On AWS the value is the production host for the data store; on an emulator the value must be an address the emulator itself serves, because the member is a routable address and nothing else in the API tells a client where the data plane is.
Emulator: DescribeFHIRDatastore publishes DatastoreEndpoint on the real AWS production host — https://healthlake.<region>.amazonaws.com/datastore/<datastore-id>/r4/ — which is not an address this emulator answers on (the suite's harness refuses the egress before a byte is sent: "endpoint_url was given https://healthlake.<region>.amazonaws.com/datastore/<id>/r4/<path> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://<emulator host>:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener"). The host and the per-run datastore id in that text are this run's values; the defect is the class of host announced. Note the fixed issue 20261022T185152Z-healthlake-non-rpc-http-surfaces-are-unroutable-datastore.md made the datastore FHIR plane routable behind the emulator's own address; what diverges now is the ADDRESS the service announces for it, which is a different component (the projection of the endpoint value) and no open issue covers it.
Why: a client follows the published DatastoreEndpoint to do everything the data plane exists for (write a Patient, read it back, search it, verify what an import job delivered). Pointed at an amazonaws.com host, that request either leaves for the real internet or fails as a DNS/connection error, so every FHIR data-plane workflow — and every control-plane assertion that depends on the data plane, such as 'the imported resource is now queryable' — is unreachable, and the failure looks like the client's own network problem rather than an emulator gap.
Fix: the projection of DatastoreProperties.DatastoreEndpoint in the healthlake crate's data-store state/serializer (the single place CreateFHIRDatastore / DescribeFHIRDatastore / ListFHIRDatastores and the CloudFormation GetAtt read): build it from the address the emulator is reached on (scheme/host/port of the serving listener, with the /datastore/<id>/r4/ path prefix the FHIR router already accepts, or the per-resource listener's host:port), never from a hard-coded healthlake.<region>.amazonaws.com template.
Traces: healthlake.fhir-rest-api-native-protocol-roundtrip (create+read Patient over the FHIR wire), healthlake.fhir-import-job-delivers-resource-to-datastore (GET [base]/Patient/<id> after StartFHIRImportJob reaches COMPLETED).

=== Cause 2 of 3: TransformData is answered by the awsJson1_0 RPC dispatcher — POST /transform-data on the data-transformation endpoint returns 400 SerializationException 'missing required header `x-amz-target`' ===
Failing check: healthlake.transform-data-sync-csv-to-fhir-bundle
AWS: Smithy: TransformData, input ProfileId (required, @length 32/32, @pattern ^[a-f0-9]{32}$) and InputData (required, @sensitive union TransformInputData with CcdaInput (String) or CsvInput (FileInputMap: filename -> file content)), plus DriftDetectionEnabled and ProvenanceEnabled (@default true); output TransformedData (required String) and DriftReport; @http(method POST, uri /transform-data, code 200); errors AccessDeniedException 403, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400. The model marks the service awsJson1_0 (so @http is inert for the modelled RPC dispatch), but the recorded behavior of this surface is a path-routed POST /transform-data on the data-transformation endpoint (the datatransformation.healthlake.<region>.amazonaws.com host) carrying the plain JSON input body with NO X-Amz-Target header, answered 200 with TransformedData holding a FHIR Bundle: the stored profile's mapping applied to the submitted input, so a CSV profile's YAML tables/resourceMappings/fieldMappings (sourceColumn -> fhirPath) produce one resource per CSV data row, each carrying that row's values; an unknown or deleted ProfileId is refused ResourceNotFoundException (404).
Emulator: the request now reaches the emulator (TLS and routing to the data-transformation host succeed) but is handed to the generic awsJson1_0 RPC dispatcher, which refuses it with HTTP 400 and body {"__type": "SerializationException", "message": "missing required header `x-amz-target`"} — whole-sentence fixed emulator text; AWS never answers this surface with SerializationException. So neither the 200 + TransformedData/Bundle response nor the modelled ResourceNotFoundException is reachable, and the path-routed data-transformation surface is effectively unimplemented.
Why: the service's headline synchronous data-plane workflow (create a CSV/CCDA transformation profile, then convert input into a FHIR R4 Bundle) returns a serialization error for a perfectly well-formed request, so a client cannot distinguish 'my request is malformed' from 'this surface does not exist', and every FHIR-conversion path built on TransformData is untestable.
Fix: route POST /transform-data through the healthlake crate's non-RPC/override_operation seam path-based and host-insensitive (as /validate-source and the REST tagging paths already are) BEFORE the X-Amz-Target RPC dispatcher sees it, and add the TransformData handler: read the profile named by ProfileId from the crate state, apply its mapping to InputData (CSV: the profile's YAML column mapping per data row; CCDA: its template mapping), answer 200 with TransformedData carrying the FHIR Bundle (plus DriftReport when DriftDetectionEnabled), and refuse an unknown/deleted ProfileId with ResourceNotFoundException (404). Open issues named here because none of them covers this failure, which the suite does not report as owned and whose symptom is new: 20261024T000307Z-healthlake-transformdata-missing.md (missing handler, from the static surface, no replay key), 20261101T195947Z-healthlake-transformdata-synchronous-csv-fhir-transform-is-unreachable-the.md (keyed on an EgressRefused signature: the harness refused the egress) and 20261103T013034Z-healthlake-transformdata-is-unserved-the-data-transformation-endpoint-aborts.md (keyed on a TLS illegal_parameter handshake abort). Both transport failures are gone in this replay — the endpoint now completes TLS and answers HTTP — and the remaining divergence is the dispatch/handler one described here.
Traces: healthlake.transform-data-sync-csv-to-fhir-bundle.

=== Cause 3 of 3: StartDataTransformationJob's profile-not-found refusal reuses GetDataTransformationProfile's wording ===
Failing check: healthlake.start-transformation-job-nonexistent-profile-not-found
AWS: Smithy: StartDataTransformationJob models ResourceNotFoundException (HTTP 404) and its ProfileId is required (@pattern ^[a-f0-9]{32}$); the model documents no message text, so recorded behavior only. The recording words THIS operation's refusal as "Data transformation profile not found: <ProfileId>" — fixed text "Data transformation profile not found: " with the ProfileId taken from the request appended. That is deliberately different from the profile-read surface, where GetDataTransformationProfile words a missing profile as "Profile '<ProfileId>' not found".
Emulator: the error CODE is right (ResourceNotFoundException) but the message is GetDataTransformationProfile's sentence: "Profile '<ProfileId>' not found" — the handler reuses the shared profile-read wording instead of its own.
Why: a client that matches or surfaces the refusal text cannot distinguish the job-submission failure from a profile-read failure, and message assertions against AWS wording fail on text AWS never emits for this operation.
Fix: the profile lookup refusal in StartDataTransformationJob's handler (its not_found() call and the shared message constant it reads) — emit this operation's own sentence with the requested ProfileId interpolated. Note: open issue 20261029T182942Z-healthlake-data-transformation-profile-surface-7-divergences-fixed.md describes this same divergence as its Cause 5, but against the older emulator wording ('Could not find specified profile.') and keyed on a replay key this check no longer produces (its key is run#36; the check now fails at run#126 with the new text), so the suite does not report it as owned; the sentence has moved from the generic constant to Get's wording and is still not AWS's. If that issue's Cause 5 is being fixed, re-replay this check to confirm.
Traces: healthlake.start-transformation-job-nonexistent-profile-not-found.
