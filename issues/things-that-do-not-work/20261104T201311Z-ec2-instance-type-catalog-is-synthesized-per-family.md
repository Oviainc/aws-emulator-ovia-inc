# ec2 instance-type catalog is synthesized per-family: DescribeInstanceTypes rows for c8a, gr6, m3, r5a and t3a diverge from the recorded AWS catalog

> _Note: this issue was identified against the code base at commit `26511efcb51aa0c8f5bf3ace614d1ff380fd4a98`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 with an instance-type catalog whose per-type attributes are computed from a generic family heuristic instead of being served from AWS's instance-type catalog. Every replayed step below is a 200->200 body mismatch: the status and the envelope are right, the per-type attribute values are not, and several modeled members are omitted entirely. 5 net-new causes are bundled here; each cause is one divergence cluster of this corpus with its own fixture and step.

There is an open ec2 issue on the same operation, 20261104T175304Z-ec2-describeinstancetypes-serves-instance-type-catalog-attributes-that.md, but its replay pointer is ec2-catalog-describe-instance-types-a1-c9g#task#22 and its Issue-Trace-Ids name fixtures without steps, so none of the clusters below are owned by it (the replay reports owned_by = [] for all of them). This corpus contains 117 unowned DescribeInstanceTypes clusters with the same shape of defect; the five named here are the ones this pass verified and they are what a fixer should re-replay.

Cause 1 of 5 - EBS performance figures, EBS attachment limits/limit type, network-card and vCPU facts for the c8a family (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#23).
AWS: Smithy com.amazonaws.ec2#InstanceTypeInfo binds ebsInfo -> EbsInfo, whose ebsOptimizedInfo -> EbsOptimizedInfo carries baselineBandwidthInMbps (integer), baselineIops (integer), baselineThroughputInMBps (double), maximumBandwidthInMbps (integer), maximumIops (integer), maximumThroughputInMBps (double), plus EbsInfo.maximumEbsAttachments (integer) and EbsInfo.attachmentLimitType (enum shared|dedicated); networkInfo -> NetworkInfo carries defaultNetworkCardIndex, maximumNetworkCards, networkCards, networkPerformance, connectionTrackingConfiguration, bandwidthWeightings, enaSrdSupported, flexibleEnaQueuesSupport, ipv4AddressesPerInterface/ipv6AddressesPerInterface; vCpuInfo -> VCpuInfo carries defaultCores, defaultThreadsPerCore, validCores, validThreadsPerCore; phcSupport and rebootMigrationSupport are modeled enums on InstanceTypeInfo. These are catalog facts per instance type, fixed by AWS for a given type, not derived quantities. cpuBurstModel is not present in the on-disk model: recorded behavior only - AWS serves it for every type in the recording ('none' for fixed-performance types, 'credit' for T types).
Emulator: for c8a.12xlarge it answers attachmentLimitType 'shared' where AWS answers 'dedicated'; ebsOptimizedInfo.baselineBandwidthInMbps 10200 and maximumBandwidthInMbps 10200 where AWS answers 15000 for both; baselineIops/maximumIops 45000 where AWS answers 60000; baselineThroughputInMBps/maximumThroughputInMBps 1275 where AWS answers 1875.0; maximumEbsAttachments 28 where AWS answers 32; networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 where AWS answers 350; and it omits cpuBurstModel and networkInfo.bandwidthWeightings altogether. The same cluster also diverges on defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, ipv4AddressesPerInterface, ipv6AddressesPerInterface, maximumNetworkCards, maximumNetworkInterfaces, networkCards, networkPerformance, secondaryNetworkSupported, trafficMirroringSupport, phcSupport, processorInfo.sustainedClockSpeedInGhz, rebootMigrationSupport and the whole vCpuInfo.validCores list, for c8a.12xlarge, c8a.16xlarge, c8a.24xlarge, c8a.2xlarge and c8a.48xlarge.
Why: a client that sizes storage or network from this catalog gets wrong answers - an EBS-attachment planner reads 28 instead of 32 slots and a dedicated-limit type as shared, a throughput planner under-reads 10200 Mbps instead of 15000, and code that keys off cpuBurstModel or bandwidthWeightings sees an absent member and cannot distinguish 'unsupported' from 'not reported'.
Fix: the DescribeInstanceTypes catalog data behind the operation's handler - the per-type attribute table must hold AWS's recorded values per instance type rather than deriving them from size multipliers, and the serializer must emit the modeled members the table now leaves unset.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#23.

Cause 2 of 5 - accelerator and instance-storage facts are wrong for the gr6 family (fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#15).
AWS: InstanceTypeInfo.gpuInfo -> GpuInfo, instanceStorageInfo -> InstanceStorageInfo and instanceStorageSupported -> boolean are modeled; autoRecoverySupported and dedicatedHostsSupported are modeled booleans; processorInfo.manufacturer is a modeled string. For gr6.4xlarge the recording carries gpuInfo with a gpus item (count 1, logicalGpuCount 1, gpuPartitionSize 1.0, manufacturer present), autoRecoverySupported 'false' and dedicatedHostsSupported 'false'.
Emulator: for gr6.4xlarge it omits gpuInfo and instanceStorageInfo entirely, reports instanceStorageSupported and autoRecoverySupported and dedicatedHostsSupported as 'true' where AWS reports 'false', attachmentLimitType 'shared' where AWS reports 'dedicated', ebsOptimizedInfo baseline/maximum bandwidth 4600/4750 where AWS reports 8000/8000, baselineIops/maximumIops 18750 where AWS reports 32000, baseline/maximum throughput 575/593.75 where AWS reports 1000.0, maximumEbsAttachments 28 where AWS reports 32, and diverges on processorInfo.manufacturer and sustainedClockSpeedInGhz. gr6.8xlarge additionally diverges on networkInfo.efaInfo/efaSupported.
Why: a GPU-aware scheduler sees no gpuInfo at all for a GPU instance type and treats gr6 as a non-accelerated type, and a client that checks instanceStorageSupported provisions for local disks the type does not have.
Fix: the DescribeInstanceTypes catalog data behind the operation's handler - accelerator, instance-storage and host-support facts must come from the per-type catalog rather than family defaults.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#15.

Why: a client that reads memory or local-disk geometry to place a workload gets a type profile that does not exist in AWS, and code that gates on ebsOptimizedSupport == 'unsupported' takes the wrong branch for previous-generation types.
Fix: the DescribeInstanceTypes catalog data behind the operation's handler - previous-generation types must be served from recorded catalog rows, not from current-generation family defaults.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#33.
