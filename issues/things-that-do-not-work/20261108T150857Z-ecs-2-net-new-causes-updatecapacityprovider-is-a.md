# ecs: 2 net-new causes — UpdateCapacityProvider is a 501 NotImplemented scaffold stub (so its ClusterNotFoundException refusal never happens), and the Managed Instances daemon rolling-update scenario never converges inside its budget

> _Note: this issue was identified against the code base at commit `85304fbaaec1e137da409d02b027804fcd09632b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateCapacityProvider

## Description
Two independent root causes in the ECS surface, both grounded in failing checks the suite lists under `### ecs`, neither marked ALREADY FILED nor OWNED by an open issue. Both must be closed before submitting.

Cause 1 of 2: UpdateCapacityProvider is an unimplemented scaffold stub, so every call — including the one AWS refuses with ClusterNotFoundException — answers HTTP 501 `NotImplemented`.
  AWS: UpdateCapacityProvider modifies a capacity provider's parameters and returns HTTP 200 with `capacityProvider`. Smithy (com.amazonaws.ecs#AmazonEC2ContainerServiceV20141113): UpdateCapacityProvider input {name (required, CapacityProviderName), cluster, autoScalingGroupProvider: AutoScalingGroupProviderUpdate, managedInstancesProvider: UpdateManagedInstancesProviderConfiguration}, output {capacityProvider: CapacityProvider}; modeled errors AccessDeniedException (403), ClientException (400), ClusterNotFoundException (400), InvalidParameterException (400), ServerException (500), UnsupportedFeatureException (400). The `cluster` member is documented as "The name of the cluster that contains the capacity provider to update. Managed instances capacity providers are cluster-scoped and can only be updated within their associated cluster", and ClusterNotFoundException is documented as "The specified cluster wasn't found" — so an update naming a cluster this account does not hold is refused with HTTP 400, error code ClusterNotFoundException. Recorded behavior for the message: the whole message is AWS's fixed sentence `Cluster not found.` with no value from the request in it (the emulator already produces exactly that sentence on CreateCapacityProvider and DescribeCapacityProviders in the same check, and both of those assertions pass).
  Emulator: the call is refused with error code `NotImplemented` (HTTP 501) regardless of input — `services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/src/ops/update_capacity_provider.rs` still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its `handle` body is `Err(crate::scaffolded::Scaffolded::not_implemented("UpdateCapacityProvider"))`. The check fails with `AssertionError: UpdateCapacityProvider: got NotImplemented` where ClusterNotFoundException was required.
  Why: a client cannot change a capacity provider at all — managed scaling, the infrastructure role, the instance launch template and tag propagation are all immutable in the emulator — and a client that probes an operation's scoping (a wrong/missing cluster) gets a 501 server-class error instead of the modeled 400 client-class refusal, so retry and error-handling logic keyed on ClusterNotFoundException/ClientException takes the wrong branch and SDK error classification flips from client to server.
  Fix: implement the operation in its own handler, `services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/src/ops/update_capacity_provider.rs` (resolve the named provider, apply the autoScalingGroupProvider / managedInstancesProvider update onto the stored CapacityProviderRecord in `crate::state`, and return the updated provider), and refuse a `cluster` that is not an active cluster with ClusterNotFoundException carrying the same `Cluster not found.` message the create/describe paths already use; delete the SCAFFOLDED marker line once done. No existing open issue names this operation (the only `UpdateCapacityProvider` issue on file, 20261025T073911Z-lambda-updatecapacityprovider-performs-no-caller-authorization-an-explicit.md, is a different service), and the suite did not auto-file it because the check swallows the ClientError and asserts on its code.
  Failing check id: ecs.capacity-provider-ops-on-missing-cluster-not-found.

Cause 2 of 2: with a Managed Instances capacity provider now accepted and ACTIVE, the daemon rolling-update scenario still never reaches any of its gates and burns the whole harness budget.
  AWS: on a cluster whose default capacity comes from an ACTIVE ECS Managed Instances capacity provider, an application service placed on that provider causes ECS to provision a container instance that ListContainerInstances reports with status ACTIVE; CreateDaemon's deployment then reaches status SUCCESSFUL (DescribeDaemonDeployments) and ListTasks(daemonName=…) reports one RUNNING task per eligible container instance running the daemon task definition's current revision; after UpdateDaemon to a new revision the deployment again reaches SUCCESSFUL, a replacement task starts on the new revision and the old-revision task reaches lastStatus STOPPED. Smithy: ListContainerInstances is readonly and returns `containerInstanceArns` with a `status` filter (ContainerInstanceStatus); CreateDaemon returns {daemonArn, status: DaemonStatus, deploymentArn}; the model states the shapes, not the convergence timing, so the timing is recorded behavior only — in the recording every one of these gates is reached well inside the check's budget.
  Emulator: the check produces no verdict at all — `Error: Check timed out after 180.0s`. It gets further than it used to (CreateCapacityProvider with a `managedInstancesProvider` whose instanceLaunchTemplate.monitoring is `basic` is now accepted, so the 120s create-retry poll succeeds), and then stalls in the first poll that waits for the data plane rather than for an API answer: the provider's ACTIVE wait, the `ListContainerInstances(status="ACTIVE")` wait for at least one container instance behind the Managed Instances provider (budget 900s) and the `DescribeDaemonDeployments` wait for SUCCESSFUL (budget 600s) are all far longer than the 180s harness budget, so the run is cut mid-poll. Hypothesis: the Managed Instances provider never produces a container instance for the demand service, so ListContainerInstances stays empty and nothing daemon-scheduled can ever be placed; DescribeDaemonDeployments is additionally still a 501 stub (covered by 20261104T062603Z-ecs-describedaemondeployments-stub.md), which would make the later gate unreachable even once placement works.
  Why: a client that models per-instance agents on ECS Managed Instances gets resources that are accepted and then never converge and never fail — no container instance, no daemon task, no rollout verdict — so a deployment wait hangs instead of either succeeding or returning an error to react to.
  Fix: the ECS Managed Instances capacity plane and the daemon scheduler in `crate::state` plus the reads over them — a provider with application demand must register a container instance that ListContainerInstances reports ACTIVE, and the daemon deployment/revision bookkeeping must progress to SUCCESSFUL and place/stop one task per eligible instance. Two open issues describe this scenario but neither carries this run's replay key, so neither owns this check: 20261104T062603Z-ecs-daemon-scheduling-never-progresses-and-createcapacityprovider-rejects.md (its key for this check is a 60s `_poll_until#12` Timeout) and 20261108T105810Z-ecs-e2e-daemon-rolling-update-across-instances-cannot.md (its key is a `_poll_until#12` AssertionError from the CreateCapacityProvider refusal, which no longer reproduces). Closing either without replaying this check would leave this failure unrun.
  Failing check id: ecs.e2e-daemon-rolling-update-across-instances.
