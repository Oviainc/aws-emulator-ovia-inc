# apigateway__dynamodb__lambda__logs: 6 net-new causes — REST AWS-service integrations never perform the action (500 API_CONFIGURATION_ERROR), WebSocket $connect 404s, stage access/execution logs are never delivered, a stage invoke URL is refused as UnknownService, GetAccount loses cloudwatchRoleArn, and DynamoDB-stream ESM delivery stalls

> _Note: this issue was identified against the code base at commit `edd8d27229a8bc99e308a4b32d393f13d6f32cb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutIntegration

## Description
Six independent root causes in this scenario group. Each is listed with its own failing check ids; all six must be closed before this issue is submitted.

Cause 1 of 6: a REST `AWS` service integration never performs the named AWS action — every invoke is answered 500 through API_CONFIGURATION_ERROR.
AWS: Smithy: apigateway PutIntegration with type=AWS (IntegrationType enum), uri=`arn:aws:apigateway:<region>:dynamodb:action/<Action>`, credentials=<role ARN>, requestTemplates (VTL) and the method's integrationResponses/responseTemplates. API Gateway assumes `credentials`, renders the request template into the DynamoDB action body, calls the action, and maps the reply through the matching integration response; a successful PutItem/GetItem/Query/BatchWriteItem returns the method's 200 response and the item is observable in DynamoDB. When the integration's role is NOT permitted the action, AWS still answers 500 with body {"message": "Internal server error"} but the execution log records the backend refusal (DynamoDB AccessDeniedException) and the method is answered through the integration-failure path; API_CONFIGURATION_ERROR is reserved for an integration that cannot be routed at all, not for a refused backend call. Likewise a uri naming a table that does not exist surfaces the backend ResourceNotFoundException in the execution log.
Emulator: every such invoke answers HTTP 500 with body {"message":"Internal server error"}, and the execution log reads `Execution failed due to configuration error: the AWS integration names a backend this emulator cannot call: no deployment package runs in process and no outbound connection is made, so no backend answer exists to map` followed by `Answered through this API's API_CONFIGURATION_ERROR gateway response`. The fixed text of that message is emulator-authored — no AWS error class says it. No DynamoDB action is ever performed, so the positive checks never see the item and the negative checks never see the backend's own refusal.
Why: a client that wires a service proxy (the documented API Gateway pattern for direct DynamoDB access) gets no persistence at all, and a client testing least-privilege cannot tell an authorization failure from an unroutable integration, because both arrive as the same configuration error.
Fix: the apigateway data-plane integration dispatcher for type=AWS — it must resolve `uri`'s service/action, render requestTemplates, invoke the target service in-emulator under the `credentials` role, and map the result through integrationResponses; the API_CONFIGURATION_ERROR gateway-response path must be reserved for unroutable integrations.
Traces: apigateway__dynamodb__lambda__logs.apigw-dynamodb-putitem-integration-positive, .apigw-dynamodb-getitem-integration-positive, .apigw-dynamodb-query-integration-response-mapping-positive, .apigw-dynamodb-batch-write-integration-positive, .apigw-dynamodb-missing-execution-role-permission-negative, .apigw-dynamodb-wrong-table-arn-in-integration-negative, .iam-role-trusts-apigateway-service-positive (expected 200, got 500), .iam-role-wrong-trust-principal-apigateway-negative (the correctly-trusted control integration also got 500). Related open issue for the apigateway heading: 20261030T120000Z-apigateway-aws-service-integration-to-another-services-action-is-not-performed.md — it does not carry these checks' replay keys.

Cause 2 of 6: a deployed WebSocket API stage does not serve the WebSocket handshake.
AWS: a WebSocket API (apigatewayv2 CreateApi ProtocolType=WEBSOCKET) deployed to a stage answers a `wss://<api-id>.execute-api.<region>.amazonaws.com/<stage>` Upgrade request with HTTP/1.1 101 Switching Protocols after the $connect route's integration returns 200, and only then delivers $default/$disconnect routes.
Emulator: the handshake is refused with `HTTP/1.1 404 Not Found` for the whole 90s poll window, so $connect never completes and nothing downstream (route dispatch, connect/disconnect logging) can be exercised.
Why: no WebSocket client can connect, so the entire duplex surface is unusable.
Fix: the execute-api data-plane router — it must recognise the WebSocket stage path and perform the RFC 6455 upgrade, not fall through to the 404 handler.
Traces: apigateway__dynamodb__lambda__logs.apigw-websocket-api-lambda-integration-positive, .apigw-websocket-connect-disconnect-logged.

Cause 3 of 6: stage access logs are never delivered to CloudWatch Logs, so no access-log record ever lands in the configured destination.
AWS: a stage with accessLogSettings (destinationArn = a log group ARN, format = a JSON template of $context.* variables) writes one log event per request into that log group; for a REST stage the group is used as given and for an HTTP API the JSON format is emitted verbatim with the $context values substituted. A destination the CloudWatch role may not create is simply never created while the stage keeps serving 200.
Emulator: no event is ever delivered — `no JSON access-log entry landed in <group> within 150s; raw_events_seen=[]` and `access log entries never landed in <group> within the harness's check budget`. The two negative checks that assert the "denied destination is never created, a clean destination IS created" pair never converge either and run to the 180s check cap, because the positive half never happens.
Why: a client that relies on access logging for request auditing sees an empty log group and cannot distinguish "delivery is broken" from "no traffic".
Fix: the apigateway stage access-log emitter (the component that should write to CloudWatch Logs on each data-plane request) and its log-group creation path.
Traces: apigateway__dynamodb__lambda__logs.apigw-http-api-access-logs-json-format, .cli-apigateway-stage-access-log-missing-destination-rejected, .apigateway-access-log-wrong-destination-arn-negative (timed out after 180.0s), .apigateway-log-group-resource-policy-missing-negative (timed out after 180.0s). Related open issue: 20261107T035448Z-apigateway-dynamodb-lambda-logs-3-net-new-causes.md — it does not carry these checks' replay keys.

Cause 4 of 6: a deployed stage's invoke URL is refused by the request router as an unknown service instead of being dispatched to execute-api.
AWS: `GET https://<api-id>.execute-api.<region>.amazonaws.com/<stage>/<path>` on a deployed REST API is served by the stage and returns the method's response (200 for the wired happy path). The request carries no SigV4 scope and no X-Amz-Target — that is normal for execute-api.
Emulator: the call is answered 404 with body {"__type": "UnknownService", "message": "could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}. Both the status and that error body are emulator-authored: AWS has no `UnknownService` error on the execute-api data plane. The fixed text here is the whole message; nothing in it comes from the request.
Why: an unsigned browser/curl client — the only way a REST API is normally consumed — cannot reach a deployed API at all.
Fix: the front-door service-resolution layer: an execute-api host/path must route to the apigateway data plane before the "resolve target service" fallback rejects it.
Traces: apigateway__dynamodb__lambda__logs.deploy-full-stack-apigateway-lambda-dynamodb-logs.

Cause 5 of 6: the account-level CloudWatch role is not retained, so GetAccount reports no cloudwatchRoleArn after it is set.
AWS: Smithy: apigateway UpdateAccount (PATCH /account, patchOperations) sets `cloudwatchRoleArn` and GetAccount (GET /account) returns it in the Account shape's `cloudwatchRoleArn` member; the value is the role ARN that was set (also settable via an AWS::ApiGateway::Account resource).
Emulator: GetAccount's cloudwatchRoleArn stays absent — the poll for "apigateway account cloudwatchRoleArn matches deployed role" reports `Last result: None` for 60s.
Why: a client cannot verify the account is configured for logging, and every stage-logging feature that depends on the account role reads as unconfigured.
Fix: apigateway account state — UpdateAccount's patch must persist cloudwatchRoleArn and GetAccount must serialize it.
Traces: apigateway__dynamodb__lambda__logs.deploy-apigateway-account-cloudwatch-role-configured. Related open issue: 20261106T204222Z-apigateway-dynamodb-lambda-logs-updateaccount-with-a-cloudwatch.md — it does not carry this check's replay key.

Cause 6 of 6: a DynamoDB-stream event source mapping stops delivering after a failing batch, and a tumbling-window mapping never aggregates.
AWS: Smithy: lambda CreateEventSourceMapping members DestinationConfig, MaximumRetryAttempts, BisectBatchOnFunctionError, TumblingWindowInSeconds (range 0-900). With no OnFailure destination configured and the retry budget exhausted, the poller DISCARDS the failing batch and continues with the next records, so a record written after an always-failing one is still processed. With TumblingWindowInSeconds set, the handler is invoked per window and its returned `state` is carried into the next window's event until the window closes.
Emulator: after the always-failing record, nothing further is delivered — `record after the always-failing one was still processed not met within 150.0s. Last result: set()` — and the tumbling-window check never progresses, running to the 180.0s cap.
Why: a client's stream consumer silently stops at the first poison record even though AWS would drop that batch and move on; windowed aggregation produces no result at all.
Fix: the lambda event-source-mapping poller — retry-exhaustion/discard advancement of the shard iterator, and tumbling-window state accumulation.
Traces: apigateway__dynamodb__lambda__logs.ddb-esm-destination-on-failure-missing-config-negative, .ddb-esm-tumbling-window-aggregation-positive.
