=== Cause 1 of 2: the discontinued cluster-security-group family is only PARTLY refused — four of the five operations answer NotImplemented (501) instead of a 400 InvalidParameterValue ===
Failing check: redshift.cluster-security-group-ops-semantics

AWS: EC2-Classic cluster security groups are discontinued, so the whole family is refused rather than served: CreateClusterSecurityGroup, DescribeClusterSecurityGroups (with or without a ClusterSecurityGroupName filter), AuthorizeClusterSecurityGroupIngress, RevokeClusterSecurityGroupIngress and DeleteClusterSecurityGroup each answer HTTP 400 with error code `InvalidParameterValue` and the service's discontinuation message. Smithy: the model still declares the normal, pre-discontinuation contract for these operations (CreateClusterSecurityGroup -> ClusterSecurityGroup, errors ClusterSecurityGroupAlreadyExistsFault/ClusterSecurityGroupQuotaExceededFault/InvalidTagFault/TagLimitExceededFault; DescribeClusterSecurityGroups, AuthorizeClusterSecurityGroupIngress, RevokeClusterSecurityGroupIngress and DeleteClusterSecurityGroup model ClusterSecurityGroupNotFoundFault httpError 404 awsQueryError `ClusterSecurityGroupNotFound`, and the two ingress/delete ops also InvalidClusterSecurityGroupStateFault 400) and documents nothing about the discontinuation, so the refusal code/status is recorded behavior only: 400 / `InvalidParameterValue` for every one of the five.
Emulator: only CreateClusterSecurityGroup refuses — it answers `InvalidParameterValue` (400), which is the right code. The other four (DescribeClusterSecurityGroups, AuthorizeClusterSecurityGroupIngress, RevokeClusterSecurityGroupIngress, DeleteClusterSecurityGroup) answer error code `NotImplemented` (scaffold 501, "operation <X> is scaffolded but not implemented in this emulator"), so the family is half-refused and half-unwritten. The replay stops at the first assertion (see the message note below) before it reaches those four, so the suite did not mark this check as already filed against any stub issue; the four handlers are still the uncovered scaffold `not_implemented` returns.
Secondary, message-only observation (NOT the requirement): the emulator's create refusal carries the text "Cluster security groups are discontinued. Use VPC security groups to control access to an Amazon Redshift cluster." where the recorded AWS message is "Amazon Redshift has discontinued cluster security groups. For security group configuration, associate VPC security groups when creating or modifying your cluster." The model states no message rule and the text is not built from the request, so the recorded text is an example; it is quoted only because this check compares the message verbatim and will keep failing on it. The requirement for all five operations is the status/code pair 400 + `InvalidParameterValue`.
Why: a client probing whether cluster security groups are usable cannot distinguish "the service removed this feature" (a 400 it must stop retrying) from "the service is broken" (a 501 it should retry or escalate). Worse, 501 `NotImplemented` is not a modeled Redshift error at all, so SDK error handling has no branch for it, and an emulator that answers it on a read while refusing the write presents a surface no real account can present.
Fix: the DescribeClusterSecurityGroups, AuthorizeClusterSecurityGroupIngress, RevokeClusterSecurityGroupIngress and DeleteClusterSecurityGroup handlers must take the same discontinuation path CreateClusterSecurityGroup already takes (the `cluster_security_groups_available()` gate and the shared discontinuation message in the redshift service state) instead of returning the scaffold's not-implemented error.
Traces: redshift.cluster-security-group-ops-semantics.

=== Cause 2 of 2: the CreateCluster -> availability-fields -> ModifyClusterIamRoles attach/detach lifecycle produces no verdict inside the harness budget ===
Failing check: redshift.create-cluster-availability-fields-and-iam-roles-attach-detach-nonexistent-role-accepted

AWS: a single-node CreateCluster settles to ClusterStatus `available` and then reports ClusterAvailabilityStatus `Available` and AvailabilityZoneRelocationStatus `enabled` by default for an eligible node type, with IamRoles empty. ModifyClusterIamRoles with AddIamRoles returns a Cluster in a transient (non-`available`) status and the association becomes visible on the next DescribeClusters; a syntactically well-formed role ARN that names a role which does not exist is ACCEPTED and its ClusterIamRole.ApplyStatus converges to `in-sync` (AWS defers the role-existence check to first use), and RemoveIamRoles leaves IamRoles empty again. Smithy: ModifyClusterIamRoles -> ModifyClusterIamRolesResult{Cluster}, errors ClusterNotFoundFault (httpError 404, awsQueryError `ClusterNotFound`) and InvalidClusterStateFault (400); ClusterIamRole = {IamRoleArn, ApplyStatus}; no existence validation of the role ARN is modeled. The convergence timing is recorded behavior only.
Emulator: the check yields no verdict at all — "Check timed out after 60.0s". None of the four bounded DescribeClusters polls (after create, after the real-role attach, after the nonexistent-role attach, after the detach) completes the sequence inside the budget, so neither the availability-field assertions nor the `in-sync` convergence of the nonexistent role is ever observed. The replay output carries no frame, so the stall point is recorded behavior only. Hypothesis: each mutating call leaves the cluster in a transient state (`creating` / `modifying`) that only clears on a later poll, so the four poll cycles the check needs consume the whole budget and the lifecycle never reaches its end — i.e. the cluster/IAM-role state machine does not converge promptly enough to be observable in bounded time.
Why: a client that attaches or detaches an IAM role and then polls DescribeClusters gets no completion signal in bounded time; the two fields Terraform's AWS provider polls on create (ClusterAvailabilityStatus, AvailabilityZoneRelocationStatus) and the `adding` -> `in-sync` convergence it reconciles against are unobservable, so a correct emulator and one that silently drops the association are indistinguishable.
Fix: the redshift cluster state machine and the ModifyClusterIamRoles path — the clock-owed `creating`/`modifying` -> `available` transition and the `adding`/`removing` -> `in-sync`/removed IAM-role settlement in the service state, plus the derived ClusterAvailabilityStatus / AvailabilityZoneRelocationStatus members — must each converge promptly so a poll loop terminates, and the nonexistent role ARN must stay attached at ApplyStatus `in-sync` rather than being validated away.
Traces: redshift.create-cluster-availability-fields-and-iam-roles-attach-detach-nonexistent-role-accepted.
