# Glue: 4 net-new root causes — CreateColumnStatisticsTaskSettings starts no task run, a CFN AWS::Glue::Trigger never exists after CREATE_COMPLETE, the job-run AccessDenied ErrorMessage is mis-composed, and GlueEncryptionException drops the relayed KMS envelope

## Description
Four (4) net-new root causes in the Glue service. Each is independent and ALL FOUR must be closed before this issue is submitted. === Cause 1 of 4: CreateColumnStatisticsTaskSettings returns 200 but starts no column-statistics task run, so the whole in-flight state machine behind it is unreachable ===
AWS: Smithy: CreateColumnStatisticsTaskSettings(DatabaseName, TableName, Role all @required NameString @length 1..255; optional Schedule/ColumnNameList/SampleSize/CatalogID/SecurityConfiguration/Tags), errors AccessDeniedException, AlreadyExistsException, ColumnStatisticsTaskRunningException, EntityNotFoundException, InvalidInputException, OperationTimeoutException, ResourceNumberLimitExceededException (all client, httpError 400). GetColumnStatisticsTaskRuns(DatabaseName, TableName @required) -> ColumnStatisticsTaskRuns, each ColumnStatisticsTaskRun carrying ColumnStatisticsTaskRunId, Role, Status (ColumnStatisticsState). Recorded behavior: a Create with NO Schedule immediately starts a run, so GetColumnStatisticsTaskRuns for that (DatabaseName, TableName) lists exactly one run whose Role is the Role submitted to Create and whose Status is still in flight (STARTING or RUNNING) when polled right after. That in-flight run is the precondition for the rest of the surface: a second Create for the same table with a different Role is refused 400 ColumnStatisticsTaskRunningException with message "Column statistics task for input table has already started" (fixed text, no variable parts) and starts no new run, StopColumnStatisticsTaskRun drives the run to STOPPED, and the identical Create then succeeds.
Emulator: Create answers 200, but GetColumnStatisticsTaskRuns(DatabaseName, TableName) stays EMPTY — the check polled it every 3 s for 60 s and never saw a run. Because no run ever exists, nothing downstream can be exercised: the duplicate-Create refusal, the no-side-effect assertion over the run-id set, the Stop -> STOPPED transition, and the re-Create.
Why: a client that registers settings and then waits on GetColumnStatisticsTaskRuns for its statistics job waits forever and can never obtain a ColumnStatisticsTaskRunId; and with no run in flight, a second Create for the same table is accepted where AWS refuses it, so two conflicting Roles can be registered for one table.
Related but NOT covering: open issue 20261108T041805Z-glue-5-net-new-root-causes-createcolumnstatisticstasksettings-starts.md describes this same fault as its Cause 1 and even lists this check, but the report left the check unowned, so no open issue carries its current replay key; 20261025T170315Z-glue-2-net-new-root-causes-column-statistics.md describes a run that IS auto-started and then settles FAILED, which is a different place (the run's terminal state, not the auto-start).
Fix: the CreateColumnStatisticsTaskSettings handler and the column-statistics task state it writes — a Create with no Schedule must register the settings AND enqueue a task run for that table so GetColumnStatisticsTaskRuns lists it with the submitted Role and an in-flight Status.
Traces: glue.column-statistics-task-settings-duplicate-create-rejected.

=== Cause 2 of 4: a CloudFormation stack containing AWS::Glue::Trigger reaches CREATE_COMPLETE but the trigger does not exist in Glue at all ===
AWS: Smithy: GetTrigger(Name @required) -> Trigger, errors EntityNotFoundException/InvalidInputException/InternalServiceException/OperationTimeoutException. Recorded behavior: once the stack that declares a resource of type AWS::Glue::Trigger (Type: SCHEDULED, Schedule: cron(...), StartOnCreation: true, Actions: [{JobName: <job>}]) reaches CREATE_COMPLETE, GetTrigger(Name=<trigger name>) resolves: Trigger.Type == "SCHEDULED" and Trigger.State reaches ACTIVATED; and because StartOnCreation is true the schedule then actually starts runs of the target job, so GetJobRuns(JobName=<job>) lists a run whose TriggerName is that trigger and that run progresses to SUCCEEDED.
Emulator: the stack create waiter completes, and the very first read after it, GetTrigger(Name=<trigger name>), is refused 400 EntityNotFoundException with message "Trigger not found." — the CREATE_COMPLETE stack provisioned no Glue trigger, so neither Type/State projection nor the scheduled firing can be observed. (Only the absence of the resource is the defect being filed here; the wording of GetTrigger's not-found message is already carried by 20261030T010615Z-glue-5-net-new-root-causes-deleteformtype-ignores.md.)
Why: a client that deploys its Glue scheduling as infrastructure-as-code is told the deployment succeeded while the trigger it declared does not exist; nothing is ever scheduled, and every subsequent Glue read of that trigger 400s on a resource CloudFormation reported as created.
Related but NOT covering: 20261029T185330Z-glue-9-net-new-root-causes-in-control.md (CreateTrigger refuses a late-bound job), 20261027T003436Z-glue-sqs-an-on-demand-trigger-that-starts.md (an ON_DEMAND trigger starts no job run) and 20261109T085123Z-glue-s3-a-workflow-s-conditional-trigger-never.md (a CONDITIONAL trigger never fires) all concern triggers created through the Glue API; none covers a CFN-declared trigger that is never created, and none carries this check's replay key.
Fix: the CloudFormation provisioning of the AWS::Glue::Trigger resource type (it must create the trigger in Glue's trigger state, honouring Type/Schedule/Actions/StartOnCreation) and, behind it, the scheduled-trigger firing in Glue's trigger/job-run state so a cron schedule starts runs tagged with TriggerName.
Traces: glue.deploy-glue-trigger-cfn-fires-scheduled-job.

=== Cause 3 of 4: a job run that fails on a denied AWS call composes JobRun.ErrorMessage with the wrong prefix and a wrong assumed-role session name ===
AWS: Smithy: GetJobRun -> JobRun{JobRunState (JobRunState enum), ErrorMessage (ErrorString), ...}; the model does not fix the text, so this is recorded behavior. Recorded behavior: when a pythonshell job's script calls PutObject and the job's Role lacks s3:PutObject, the run settles JobRunState=FAILED with ErrorMessage of the form "ClientError: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account>:assumed-role/<roleName>/GlueJobRunnerSession is not authorized to perform: s3:PutObject on resource: \"arn:aws:s3:::<bucket>/<key>\" because no identity-based policy allows the s3:PutObject action". Fixed text, exactly as quoted: the leading "ClientError: " (the botocore exception class raised inside the script), "An error occurred (AccessDenied) when calling the PutObject operation: User: ", the literal session-name segment "/GlueJobRunnerSession", " is not authorized to perform: ", " on resource: " and " because no identity-based policy allows the s3:PutObject action". Variable parts, taken from the request and from state: the account id, the role NAME of the job's Role, the denied action, and the bucket/key ARN of the object the script tried to write.
Emulator: the run does settle FAILED, but ErrorMessage is "AccessDenied: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account>:assumed-role/<roleName>/<jobName> is not authorized to perform: s3:PutObject on resource: \"arn:aws:s3:::<bucket>/<key>\" because no identity-based policy allows the s3:PutObject action". Two parts diverge: the prefix is the error CODE "AccessDenied: " instead of the exception class "ClientError: ", and the assumed-role session name is the JOB NAME instead of the fixed "GlueJobRunnerSession". (The account id, role name, bucket and key in the recorded line are that run's values and are not part of the requirement.)
Why: a client (or an operator's log scraper) that matches a failed run's ErrorMessage to decide the failure was an IAM denial of its own script sees a line Glue never emits; and the session name is how the role session is identified in CloudTrail and in IAM policy conditions, so the run attributes the denial to a session that does not exist.
Related but NOT covering: 20261108T041805Z-glue-5-net-new-root-causes-createcolumnstatisticstasksettings-starts.md Cause 3 records the older behavior of this same check, where the job run executed no script at all and ErrorMessage was "This emulator records job runs but executes no job script, so the job run ended without running." On this commit the positive control now SUCCEEDS and the object is written, so what remains is only the composition of the failed run's message; that issue does not carry this check's current replay key.
Fix: the composition of JobRun.ErrorMessage in the job-run execution path (the relay of an SDK error raised by the job script into ErrorMessage, and the assumed-role session name the run's credentials are minted with).
Traces: glue.deploy-job-missing-output-permission-rejected.

=== Cause 4 of 4: GlueEncryptionException on a catalog read whose CMK is disabled drops the relayed KMS error envelope from its message ===
AWS: Smithy: GlueEncryptionException is a client error, httpError 400, with a single Message member documented as "The message describing the problem"; its shape doc is "An encryption operation failed." The text is recorded behavior, not modeled. Recorded behavior: with catalog encryption set to EncryptionAtRest {CatalogEncryptionMode: SSE-KMS, SseAwsKmsKeyId: <key>}, GetTable after DisableKey on that CMK is refused 400 GlueEncryptionException whose Message relays the KMS refusal with the full AWS SDK envelope: "<key ARN> is disabled. (Service: AWSKMS; Status Code: 400; Error Code: DisabledException; Request ID: <kms request id>; Proxy: null)". Fixed text: " is disabled. (Service: AWSKMS; Status Code: 400; Error Code: DisabledException; Request ID: " and "; Proxy: null)". Variable parts: the key ARN, which comes from the catalog's SseAwsKmsKeyId state, and the per-call KMS request id (a per-run value the check fills in from whatever the response carries — it is not itself a requirement).
Emulator: the error class and status are right (400 GlueEncryptionException) and the read does depend on the key, but Message is only "<key ARN> is disabled." — the whole relayed "(Service: AWSKMS; Status Code: 400; Error Code: DisabledException; Request ID: ...; Proxy: null)" envelope is missing.
Why: the relayed envelope is how a client distinguishes WHICH KMS failure broke the catalog read (DisabledException vs KMSInvalidStateException vs AccessDeniedException) without a second KMS call; a bare sentence forces it to guess, and any handler keyed on "Error Code: <X>" in the message never matches.
Fix: the relay of KMS errors into GlueEncryptionException.Message on the catalog decrypt path used by GetTable (the encryption/decrypt wrapper of the catalog read), not the error class.
Traces: glue.server-side-encryption-enforced-on-new-tables.
