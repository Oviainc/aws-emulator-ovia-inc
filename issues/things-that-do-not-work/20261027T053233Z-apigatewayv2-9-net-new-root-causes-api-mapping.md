=== Cause 1 of 9: the duplicate-ApiMappingKey ConflictException message is built from the request instead of AWS's constant text ===
AWS: Smithy: CreateApiMapping POST /v2/domainnames/{DomainName}/apimappings, success code 201, input ApiMappingKey -> SelectionKey, modeled errors BadRequestException (client, httpError 400), ConflictException (client, 409), NotFoundException (404), TooManyRequestsException (429). Recorded behavior for the text: a second CreateApiMapping for a DomainName + ApiMappingKey pair already mapped is refused 409 ConflictException with the constant message "ApiMapping key already exists for this domain name" — fixed text for the whole class, interpolating NOTHING from the request (no domain name, no key), and the first mapping is left untouched.
Emulator: the error code and status are right (ConflictException) but the message is a different template, built from the request: 'An API mapping already exists for the domain name <requested DomainName> with the specified API mapping key.' (replayed with four different generated domains, e.g. 'An API mapping already exists for the domain name sim2real-behav-d4fa91c282fc.example.com with the specified API mapping key.'). Fixed part of AWS's required text: the whole sentence "ApiMapping key already exists for this domain name"; variable parts: none.
Why: the message is part of the refusal contract. A caller that recognises AWS's constant text (or logs/asserts on it) does not recognise this refusal, and the emulator advertises a request-derived message where AWS advertises a constant, so no stable matching is possible.
Fix: the duplicate-key conflict message site in the CreateApiMapping handler (services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ops/create_api_mapping.rs).
Traces: apigatewayv2.api-mapping-duplicate-path-rejected, apigatewayv2.api-mapping-key-collision-rejected, apigatewayv2.api-mapping-key-conflict-rejected, apigatewayv2.create-api-mapping-duplicate-path-conflict (in every one of the four, the 409/ConflictException code, the 'original mapping untouched' effect and the distinct-key positive control pass; only the message diverges).

=== Cause 2 of 9: the unknown-ApiMappingId NotFoundException message does not name the mapping id ===
AWS: Smithy: GetApiMapping GET /v2/domainnames/{DomainName}/apimappings/{ApiMappingId} and DeleteApiMapping DELETE on the same URI, both modeling NotFoundException (client, httpError 404). Recorded behavior for the text: reading or deleting an ApiMappingId that does not exist (here: one that was just deleted) is refused 404 NotFoundException with the message "Unable to find ApiMapping with ID <ApiMappingId>" — fixed text "Unable to find ApiMapping with ID " plus one variable part taken from the request, the ApiMappingId; the same message is emitted on both the read and the repeated delete.
Emulator: NotFoundException (correct code) with the constant message 'Invalid API mapping identifier specified' — a different template that drops the id entirely.
Why: AWS's message tells the caller WHICH mapping id was not found, which is how a client distinguishes a stale id from a malformed request; a caller matching AWS's text sees an unrecognised refusal, and the shape of the contract (names the id vs names nothing) differs.
Fix: the not-found message site shared by the GetApiMapping and DeleteApiMapping handlers (src/ops/get_api_mapping.rs, src/ops/delete_api_mapping.rs) — the lookup must report the requested ApiMappingId.
Traces: apigatewayv2.api-mapping-path-special-chars-round-trip (the special-character ApiMappingKey round-trip through CreateApiMapping/GetApiMapping passed byte-identically; the check fails at the post-delete read).

=== Cause 3 of 9: UpdateDomainName does not validate the request body before resolving the domain, so an empty update answers 404 instead of 400 ===
AWS: Smithy: UpdateDomainName PATCH /v2/domainnames/{DomainName}, success 200, every body member optional (DomainNameConfigurations, MutualTlsAuthentication, RoutingMode), modeled errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429). Recorded behavior: an UpdateDomainName carrying NO body member at all is refused 400 BadRequestException with the constant message "UpdateDomainName request cannot be empty or null", and that request-shape check runs BEFORE the domain is looked up — the same refusal is returned for a domain that has already been deleted.
Emulator: the call is refused 404 NotFoundException with 'Invalid domain name identifier specified', i.e. the handler resolves the domain first and never applies the empty-request rule. (The sibling leg of the same check — GetDomainName on the deleted domain returning NotFoundException 'Invalid domain name identifier specified' — matches AWS and passes, as do GetDomainNames reflecting the create and the delete.)
Why: validation ORDER is observable. A client that sends an empty PATCH gets the wrong typed exception (botocore's BadRequestException never matches), so retry/branch logic written against AWS takes the not-found branch, and on a live domain the emulator would silently accept a no-op where AWS refuses.
Fix: request-shape validation in the UpdateDomainName handler (src/ops/update_domain_name.rs), applied before the domain-name lookup.
Traces: apigatewayv2.list-domain-names-reflects-created.

=== Cause 4 of 9: CreateRoutingRule accepts a second rule at a Priority already in use on the domain ===
AWS: Smithy: CreateRoutingRule POST /v2/domainnames/{DomainName}/routingrules, success 201, Priority -> RoutingRulePriority @range 1..1000000, required; modeled errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429). Recorded behavior: a second CreateRoutingRule on the same DomainName with a Priority an existing rule already holds is refused 400 BadRequestException — not the generically plausible ConflictException — with the message "Trying to add rule with duplicate priority: <Priority>" (fixed text "Trying to add rule with duplicate priority: " plus one variable part, the rejected Priority value from the request); no rule is created, the existing rule keeps its Priority/Conditions, and once the holding rule is deleted the identical call succeeds.
Emulator: the duplicate-Priority call SUCCEEDS with HTTP 201 and returns a second rule (Priority 100, a fresh RoutingRuleId and RoutingRuleArn) on the same domain, so the per-domain Priority uniqueness invariant is not enforced at all.
Why: over-permissiveness. Priority is what orders rule evaluation, so two rules at one priority make routing non-deterministic; a configuration the emulator accepts is refused by AWS, and the state-dependent refusal (reject while taken, accept once freed) cannot be exercised locally.
Fix: the per-domain Priority uniqueness guard in the CreateRoutingRule handler (src/ops/create_routing_rule.rs) and the routing-rule state keyed by (DomainName, Priority).
Traces: apigatewayv2.routing-rule-duplicate-priority-rejected.

=== Cause 5 of 9: CreateRoutingRule accepts an InvokeApi action naming an API id that does not exist ===
AWS: Smithy: CreateRoutingRule Actions -> __listOfRoutingRuleAction, required; modeled errors include BadRequestException (client, httpError 400). Recorded behavior: a rule whose InvokeApi.ApiId references an API that does not exist is refused 400 BadRequestException with the message "Invalid API identifier specified: <ApiId>" (fixed text "Invalid API identifier specified: " plus one variable part, the unresolvable ApiId from the request), and ListRoutingRules on the domain then holds no rule; a rule naming the real deployed REST API still succeeds and is readable through GetRoutingRule.
Emulator: the call SUCCEEDS with HTTP 201 for ApiId 'zzzzzzzzzz' (a well-formed but nonexistent id) and persists a rule whose InvokeApi target cannot be resolved, so the reference is never validated.
Why: a dangling routing-rule target is accepted locally and rejected by AWS at deploy time, and the rule the emulator stores can never route anything — the failure surfaces as a data-plane mystery instead of the 400 AWS returns at create time.
Fix: target-reference resolution in the CreateRoutingRule handler (src/ops/create_routing_rule.rs) — resolve InvokeApi.ApiId (and its Stage) against existing APIs before the rule is stored.
Traces: apigatewayv2.routing-rule-invalid-target-api-rejected.

=== Cause 6 of 9: AWS::ApiGatewayV2::Route and ::Stage resources declared in a CloudFormation stack do not exist after the stack completes ===
AWS: recorded behavior only (CloudFormation resource provisioning is not described by the apigatewayv2 model); the read-backs are modeled: GetRoutes GET /v2/apis/{ApiId}/routes -> Items (list of Route, each with RouteKey and Target), GetStages GET /v2/apis/{ApiId}/stages -> Items (list of Stage, each with StageName and AutoDeploy). Recorded behavior: once a stack containing AWS::ApiGatewayV2::Api + ::Integration + ::Route + ::Stage reaches CREATE_COMPLETE, GetRoutes returns the declared routes with Target = "integrations/<integration id>" and GetStages returns the declared stage (for a CDK-synthesised HttpApi: exactly one stage named "$default" with AutoDeploy true).
Emulator: after the same stacks complete, the control plane answers but reports nothing: GetRoutes Items is empty (assertion 'deployed routes [], expected [\'$default\']'), GetStages Items is empty (assertion 'deployed stages [], expected only $default with AutoDeploy true'), and the route-target map read back for a template's second route is {} where it must be 'integrations/<id>' (assertion "the control's second route must target the real integration ..."). So the Api resource exists while its child Route/Stage resources are never created from the template.
Why: every IaC path — raw CloudFormation templates and CDK-synthesised apps alike — produces an API with no routes and no stage, so nothing can be invoked and no stack-driven test of routing, autodeploy or rollback can run; the stack nevertheless reports success, which is worse than failing.
Fix: the CloudFormation resource providers for AWS::ApiGatewayV2::Route and AWS::ApiGatewayV2::Stage (and the Ref/GetAtt wiring from ::Integration that a route's Target is built from) in the CloudFormation provisioning layer, so a completed stack's resources are present in apigatewayv2 state.
Traces: apigatewayv2.deploy-apigatewayv2-1-dangling-route-target-rejected-rolls-back-api, apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-cors-lambda-default-route-serves-then-destroys, apigatewayv2.deploy-apigatewayv2-3-cdk-http-api-stripped-lambda-permission-invoke-rejected.

=== Cause 7 of 9: a CloudFormation-declared CorsConfiguration on AWS::ApiGatewayV2::Api is dropped ===
AWS: Smithy: GetApi GET /v2/apis/{ApiId} output member CorsConfiguration -> Cors (jsonName corsConfiguration), carrying AllowOrigins/AllowMethods. Recorded behavior: when a stack declares CorsConfiguration on its AWS::ApiGatewayV2::Api, GetApi after CREATE_COMPLETE returns that configuration verbatim (AllowOrigins = the declared origin list, AllowMethods = the declared method list), and removing it from the template in an UPDATE clears it.
Emulator: GetApi on the stack's API returns no CorsConfiguration member at all (assertion 'GetApi must return the stack\'s CorsConfiguration, got None'), so the property is accepted by the stack and then lost — the in-place removal half of the check can never be observed because there is nothing to remove.
Why: a client cannot verify (or exercise) CORS configured through IaC; a template that configures an origin allowlist produces an API the emulator reports as having no CORS, so a preflight-dependent application behaves differently locally and in AWS.
Fix: the CloudFormation resource provider for AWS::ApiGatewayV2::Api — map the template's CorsConfiguration property into the Api's state so GetApi serialises it (and clear it on an update that drops it).
Traces: apigatewayv2.deploy-apigatewayv2-1-http-api-cors-removed-in-place-then-api-replaced.

=== Cause 8 of 9: a REGIONAL custom domain never serves a request, so no API mapping can be exercised through it ===
AWS: recorded behavior only (the custom-domain data plane has no Smithy model; the control plane is modeled: CreateDomainName/GetDomainName return DomainNameConfigurations with ApiGatewayDomainName and HostedZoneId, and CreateApiMapping binds an ApiMappingKey to a stage). Recorded behavior: once a REGIONAL domain reports DomainNameStatus=AVAILABLE, the dedicated host returned in ApiGatewayDomainName accepts TLS by SNI and serves the mapped stage's routes at the mapping key's base path, and an unmapped host answers 403 {"message":"Forbidden"}.
Emulator: both checks that drive traffic through a custom domain hang until the harness kills them — 'Error: Check timed out after 60.0s' — having never completed a request through the domain (one creates the domain + mapping + Lambda-backed stage directly, the other through a CloudFormation template). Hypothesis: the emulator announces the AWS host form (d-xxxxxxxxxx.execute-api.<region>.amazonaws.com) in ApiGatewayDomainName rather than an address the client that created the domain can reach, so the client's first connection to the announced host never completes — the same 'announce what the caller can reach' defect recorded for Api$ApiEndpoint in 20261025T113951Z-apigatewayv2-http-api-invoke-url-answers-500-for.md, and the same symptom as 20261025T210904Z-acm-apigatewayv2-a-regional-custom-domain-never-presents.md for a third check. An alternative mechanism with the same evidence is that nothing is served on that host at all; both must be checked together.
Why: a custom domain plus API mapping is the normal production front door for an HTTP API. If nothing ever answers on the announced host, no mapping-key routing, base-path stripping or multi-stage domain layout can be tested, and a caller cannot tell a misconfiguration from an unreachable emulator.
Fix: the custom-domain data plane — serve the domain on the address its own DomainNameConfiguration announces (and announce the address the caller can reach, as the portal data plane already does via crate::state::announced_portal_default_domain_name), then dispatch by ApiMappingKey to the mapped stage.
Traces: apigatewayv2.custom-domain-mapping-key-routes-to-stage-routes, apigatewayv2.deploy-api-mapping-cfn-behaves.

=== Cause 9 of 9: a CORS preflight is never caught by an API's route, so preflight-vs-authorizer ordering is unobservable ===
AWS: recorded behavior only (execute-api has no Smithy model); the configuration is modeled: Api$CorsConfiguration -> Cors, Route$AuthorizationType. Recorded behavior: on an HTTP API carrying a CorsConfiguration, an OPTIONS preflight (Origin + Access-Control-Request-Method) that matches a route — including an AWS_IAM-protected ANY /{proxy+} route — is answered by API Gateway's CORS layer with the allow-origin/allow-methods headers and WITHOUT the route's authorizer running, while the same route answers an unsigned GET 403 {"message":"Forbidden"}.
Emulator: the check is killed at the 60 s cap ('Error: Check timed out after 60.0s') before its CORS assertions, exactly as it was when this behaviour was last reported in the now-fixed 20261025T113951Z-apigatewayv2-http-api-invoke-url-answers-500-for.md; that report's own note states the GET half now answers 403 on the first probe, so the leg that does not converge is the preflight. Hypothesis (from that note): the core listener answers every OPTIONS request itself before any emulated service handler runs, so no route of an API can ever catch a preflight.
Why: CORS is the one behaviour where API Gateway must answer in FRONT of authorization; if preflights never reach the API, a browser-facing application cannot be exercised at all and an emulator cannot show whether a preflight bypasses the authorizer.
Fix: preflight handling must be owned by the apigatewayv2 execute-api data plane (route match -> CorsConfiguration response, ahead of the route's authorizer) instead of being short-circuited by the generic HTTP listener's OPTIONS branch; if that branch is in read-only vendor code, the listener needs a hook that lets a service claim OPTIONS for its own hosts.
Traces: apigatewayv2.http-api-cors-preflight-caught-by-any-route-is-authorized.
