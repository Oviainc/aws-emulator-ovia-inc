=== Cause 1 of 2: CompleteSnapshot never compares the declared ChangedBlocksCount with the blocks actually written, so a snapshot that was under-filled is sealed 'completed' instead of converging to 'error' ===
AWS: Smithy com.amazonaws.ebs#CompleteSnapshot — http POST /snapshots/completion/{SnapshotId}, code 202; `ChangedBlocksCount` is an @required header member (`x-amz-ChangedBlocksCount`, @range min 0); output `Status` targets com.amazonaws.ebs#Status (values completed|pending|error); modeled errors AccessDeniedException 403, InternalServerException 500, RequestThrottledException 400, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ValidationException 400. ChangedBlocksCount is NOT validated synchronously: a count that disagrees with the blocks received is accepted (HTTP 202, Status pending|completed, no refusal). It is enforced ASYNCHRONOUSLY — the snapshot then converges to the terminal state `error` (observable as ec2:DescribeSnapshots State 'error') and never to 'completed', and the snapshot is unusable. Recorded behavior only for the asynchronous convergence and its latency (the recording notes it on the order of 150 s); the model states only the member, its constraints, and that `error` is a Status value.
Emulator: the comparison is absent by design. services/service-com-amazonaws-ebs-ebs/src/ops/complete_snapshot.rs discards the value (`let _ = input.changed_blocks_count;`, with a comment stating it 'is NOT a precondition this call verifies against the blocks the snapshot holds'), then unconditionally transitions a Pending snapshot to `SnapshotStatus::Completed`. Replaying CompleteSnapshot(ChangedBlocksCount=5) against a snapshot with exactly ONE 524288-byte block written is accepted (correct) and the snapshot then converges to State 'completed' (wrong): the check fails with `AssertionError: a mismatched ChangedBlocksCount is not validated synchronously but IS enforced asynchronously: expected the snapshot to converge to 'error', got 'completed'`. A correct count and an incorrect count are indistinguishable to this handler.
Why: ChangedBlocksCount is the direct API's only integrity check that a producer uploaded everything it claimed. A client whose uploader crashed or wrote a partial set is never told — against the emulator a truncated snapshot reads as a complete, usable one, and any client or test that relies on the snapshot going to `error` to detect and retry its own partial upload never sees that signal and silently restores incomplete data.
Fix: the CompleteSnapshot handler and the snapshot state it finalises (services/service-com-amazonaws-ebs-ebs/src/ops/complete_snapshot.rs, around the ChangedBlocksCount discard and the Pending→Completed transition, plus the shared snapshot record in src/state.rs that ec2:DescribeSnapshots reads). Keep the synchronous answer a 202 with Status pending|completed — never a refusal — but record the declared count, compare it against the number of distinct block indices PutSnapshotBlock accepted for that snapshot, and finalise the record to Status/State `error` when they disagree.
Traces: ebs.complete-snapshot-wrong-changed-blocks-count-is-accepted.

=== Cause 2 of 2: PutSnapshotBlock's refusal of a write to an already-completed snapshot carries the emulator's own sentence instead of AWS's ValidationException message ===
AWS: Smithy com.amazonaws.ebs#PutSnapshotBlock — http PUT /snapshots/{SnapshotId}/blocks/{BlockIndex}, code 201; its documentation states 'The target snapshot must be in the pending state.' A write to a snapshot that has left `pending` is refused synchronously with the modeled `ValidationException` (@httpError 400, members Message @length 0..256 and Reason from com.amazonaws.ebs#ValidationExceptionReason). The message is the fixed sentence `Snapshot is already completed` — it is entirely fixed text with NO variable parts: it names neither the snapshot id nor the state. Taken from the recorded response (the model constrains the shape, not the wording); status 400 and error code `ValidationException` are the recorded refusal's own.
Emulator: the code is right and the message is not. services/service-com-amazonaws-ebs-ebs/src/ops/put_snapshot_block.rs (the `write_refusal` branch, ~lines 265-281) answers `ValidationException` with Reason `INVALID_SNAPSHOT_ID` and the message template `snapshot <snapshot-id> has been completed; blocks can only be written to a pending snapshot` — a different sentence that additionally interpolates the request's SnapshotId, which AWS's message does not carry. The replay shows `AssertionError: got msg='snapshot snap-846671afbc0506095 has been completed; blocks can only be written to a pending snapshot'` (the snap- id is a per-run value, not part of the requirement; the defect is the sentence and the fact that it is parameterised at all). The sibling branch for a non-completed, non-pending snapshot (`snapshot <id> is <status>; ...`) is the same invented wording and should be reviewed with it.
Why: callers and SDK/test code match on AWS's exact message text to distinguish 'already completed' from the other ValidationException reasons PutSnapshotBlock can raise (malformed snapshot id, bad DataLength, out-of-range block index), because the error code is the same for all of them. A client that branches on `Snapshot is already completed` never matches here, so a benign late write is handled as an unknown validation failure; log-scraping and assertion code that expects the fixed sentence breaks.
Fix: the PutSnapshotBlock handler's validation/refusal path (services/service-com-amazonaws-ebs-ebs/src/ops/put_snapshot_block.rs, the `write_refusal` message construction and the message helpers it uses in src/state.rs) — emit AWS's fixed sentence for this class with no interpolated id.
Traces: ebs.put-snapshot-block-after-completion-rejected.
