# EMR TerminateJobFlows on a termination-protected cluster answers 200 and silently does nothing instead of refusing with ValidationException (1 cause)

> _Note: this issue was identified against the code base at commit `e545f454eaa3062865bf1b3f8da00afa40e078cd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TerminateJobFlows

## Description
This issue carries 1 net-new root cause in the EMR (elasticmapreduce) crate, grounded in the only failing check of this replay that is neither ALREADY FILED on an unimplemented stub nor OWNED by an open issue: emr.termination-protection-blocks-terminate-job-flows.

--- Cause 1 of 1: TerminateJobFlows does not refuse a termination-protected cluster; it returns a success with no effect ---
AWS: Smithy: TerminateJobFlows takes JobFlowIds (XmlStringList, required) and models only InternalServerError, so the refusal travels on EMR's client-error channel; SetTerminationProtection's own doc states the contract — it "locks a cluster (job flow) so the Amazon EC2 instances in the cluster cannot be terminated by user intervention, an API call, or in the event of a job-flow error", and "to terminate a cluster that has been locked ... you must first unlock the job flow by a subsequent call to SetTerminationProtection in which you set the value to false". Beyond that, recorded behavior only for the shape of the answer: the behavioral check pins real EMR's refusal of a terminate against a protected cluster as HTTP 400 with one of EMR's two cluster-validation codes (ValidationException or InvalidRequestException — the corpus shows the same cluster-validation surface using both, see wire/emr/cluster-mutations-on-unknown-cluster.json) and the CONSTANT message text `Could not shut down one or more job flows since they are termination protected.` That message is entirely fixed text: it interpolates no job-flow id, name, count or timestamp, so nothing in it comes from the request or from state. The check's own HONESTY NOTE records that the corpus does not independently pin whether AWS answers 200-with-no-effect or a 4xx here, so treat the status/code/message triple above as the check's ground truth, and the following as the reading of it: Hypothesis: EMR evaluates the protection flag per named job flow before starting any shutdown and fails the whole request, which is why the sentence is plural ("one or more job flows") and id-free.
Emulator: the handler accepts the request and answers HTTP 200 with an empty TerminateJobFlowsOutput for a protected cluster. The protection flag IS stored and IS honoured as an effect (SetTerminationProtection writes it, DescribeCluster reports it, and the cluster is left in WAITING), but the caller is told the terminate succeeded: the state transition helper reports that it refused to start the shutdown and the operation discards that answer instead of turning it into a refusal, so no error code and no message ever reach the client. The emulator therefore has NO wording for this error class at all, not merely diverging wording.
Why: a client that asks to terminate a protected cluster gets a 2xx and reasonably concludes the fleet is shutting down — the exact opposite of what happened. Clean-up and cost-control code that terminates and moves on leaves a protected, per-second-billed cluster running while believing it reclaimed it; the documented unlock-then-terminate sequence is never forced, because the failing step reports success; and no negative test of termination protection can be graded, since the only observable difference from a real terminate is the absence of the state change.
Fix: the TerminateJobFlows handler in the EMR crate (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/terminate_job_flows.rs): it already resolves every named id before mutating anything and then calls the cluster record's begin-termination helper in a second pass, ignoring that helper's boolean. Make the protected case a refusal on the 400 ValidationException channel carrying the constant sentence above, decided in the same pre-pass that resolves the ids so that a request naming one protected cluster terminates none of the clusters it names. Keep the existing idempotent no-op for a cluster that is already TERMINATING/terminal — that case is not protection and must stay a success. Related open issue 20261031T093431Z-elasticmapreduce-emr-setterminationprotection-appends-the-job-flow-id-to.md concerns the message SetTerminationProtection emits for an unknown job flow and does not cover TerminateJobFlows' protected-cluster path or this check id; 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md covers step execution and cluster self-termination, not the protection gate.
