# cognito-identity: a CloudFormation AWS::Cognito::IdentityPoolRoleAttachment is never applied through SetIdentityPoolRoles, so a RoleMappings entry with Type=Rules and no RulesConfiguration is accepted and the stack reaches CREATE_COMPLETE instead of ROLLBACK_COMPLETE

## Operation
SetIdentityPoolRoles

## Description
This issue carries ONE net-new root cause reached through a cognito-identity behavioral check in suite simparity-behavioral-ga-prod-v1. It must be fixed and the trace_ids list re-replayed before closing.

=== Cause 1 of 1: AWS::Cognito::IdentityPoolRoleAttachment is left declared-only, so an invalid role mapping is never refused and the stack never rolls back ===

AWS: an AWS::Cognito::IdentityPoolRoleAttachment resource is created by calling cognito-identity SetIdentityPoolRoles with the declaration's IdentityPoolId, Roles and RoleMappings. A RoleMappings entry is a RoleMapping (Smithy: RoleMapping.Type @required, enum RoleMappingType values [Token, Rules]; RoleMapping.RulesConfiguration -> RulesConfigurationType, documented "The rules to be used for mapping users to roles. If you specify Rules as the role mapping type, RulesConfiguration is required."; RulesConfigurationType.Rules @required MappingRulesList @length{1,400}). So an entry with Type=Rules and NO RulesConfiguration is an invalid role mapping and SetIdentityPoolRoles refuses it with a modelled client error (Smithy: SetIdentityPoolRoles errors include InvalidParameterException httpError 400, ResourceNotFoundException 404, ResourceConflictException 409). Recorded behavior for the CloudFormation path: that refusal fails exactly the attachment resource — a CREATE_FAILED event for the AWS::Cognito::IdentityPoolRoleAttachment logical resource whose ResourceStatusReason carries the service's refusal, whose fixed text for this condition is "RuleConfiguration is required for Rules" (no variable parts) — and because "ROLLBACK — Roll back the stack creation" is OnFailure's documented default, the stack then rolls back: the resources the create had already made (here the identity pool and the IAM role) each get a DELETE_COMPLETE, the stack's single ROLLBACK_IN_PROGRESS event names the failed logical id (the reason naming [<logical id of the attachment>], the variable part being the template's own logical id), and the stack settles in ROLLBACK_COMPLETE. The rolled-back pool is then gone through cognito-identity's own API: DescribeIdentityPool on it answers ResourceNotFoundException "IdentityPool '<pool id>' not found." (fixed text around the request's pool id) and ListIdentityPools no longer lists it.

Emulator: the stack with the broken attachment reaches CREATE_COMPLETE. Its events are IdentityPool CREATE_IN_PROGRESS -> CREATE_COMPLETE, AuthRole CREATE_IN_PROGRESS -> CREATE_COMPLETE, RoleAttachment CREATE_IN_PROGRESS -> CREATE_COMPLETE, stack CREATE_COMPLETE — there is NO CREATE_FAILED event for the attachment, no ROLLBACK_IN_PROGRESS, no DELETE_COMPLETE for the pool or the role, and no ROLLBACK_COMPLETE. The twin control stack (identical but Type=Token with AmbiguousRoleResolution=AuthenticatedRole) also reports CREATE_COMPLETE, so the emulator reports the SAME outcome for a valid and an invalid role mapping. The cause is that the role attachment is never applied anywhere: the CloudFormation crate's per-type provisioner table has no arm for AWS::Cognito::IdentityPoolRoleAttachment (state/provisioner.rs documents "A type with no entry here is left declared-only ... nothing is created in any service", and its imported type-constant list carries COGNITO_USER_POOL_GROUP but no Cognito identity-pool type), so SetIdentityPoolRoles is never called for the resource, its input is never validated, and the resource is synthesised as CREATE_COMPLETE regardless of what it declares.

Why: a client relying on AWS's behavior gets a green stack for an identity-pool configuration AWS refuses. Two things break together. First, the invalid-configuration guard rail is gone: CloudFormation is the gate that catches a Rules mapping with no rules before it ships, and here it reports success instead, so the broken declaration is promoted. Second, the stack's success is a lie about state even when the declaration is valid: nothing was attached, so the pool has no authenticated role and no role mappings, every subsequent GetIdentityPoolRoles / GetCredentialsForIdentity / GetOpenIdTokenForDeveloperIdentity flow behaves as if the attachment resource did not exist, and the failure-and-rollback contract (failed resource named, already-created resources deleted, ROLLBACK_COMPLETE) that IaC tooling and drift detection depend on never fires — the orphaned pool and role are left behind with no event saying so.

Fix: the CloudFormation per-type resource provisioner — add the arm for AWS::Cognito::IdentityPoolRoleAttachment so the resource is created through cognito-identity's own SetIdentityPoolRoles over the existing in-process signed callback (mapping the declaration's IdentityPoolId, Roles and RoleMappings, which are that call's own members), with the delete path clearing the attachment; and the cognito-identity SetIdentityPoolRoles input validation, which must refuse a RoleMappings entry whose Type is Rules and whose RulesConfiguration is absent with the modelled InvalidParameterException (400) carrying AWS's fixed sentence for the condition, so that the refusal flows into the already-implemented create-failure/rollback path and produces the attachment's CREATE_FAILED event and the stack's ROLLBACK_COMPLETE.
