# sso-admin serves a synthesized application provider catalog instead of AWS's

> _Note: this issue was identified against the code base at commit `92cfd533f2bcf50b623c79e1d9c332a026d07827`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeApplicationProvider

## Description
THREE causes, all one fault in sso-admin's application-provider catalog: the emulator does not serve IAM Identity Center's application-provider catalog at all, it serves a catalog it synthesizes itself (entries named after AWS services, ARNs of the form .../<service> instead of .../catalog/<ProviderName>, FederationProtocol fixed to OAUTH, DisplayData text and IconUrl generated from the synthesized entry). Every read of the catalog therefore answers 200 with content a client cannot have asked for. A fixer must close ALL THREE before submitting: cause 1 and 3 are the catalog contents as seen through each of the two read paths, cause 2 is the DisplayData of an entry that does survive the lookup, so a fix to the seed table alone can leave either read path still diverging.

NOTE ON PRIOR ISSUES: two resolved issues describe this area - 20261023T071252Z-sso-admin-application-provider-catalog-is-a-placeholder.md and 20261029T184546Z-sso-admin-application-provider-catalog-is-wrong-describe-ignores-the.md. Both are in the RESOLVED folder, so neither covers these clusters, and the replay report confirms all three are unowned. The catalog is still synthesized after those fixes. The one OPEN issue on this operation, 20261030T043338Z-sso-admin-enumeration-responses-omit-output-members-listapplicationproviders-returns-no.md, owns only the missing $.NextToken on ListApplicationProviders (pagination), not the catalog's CONTENT; its replay keys do not include any of the clusters below.

Cause 1 of 3: DescribeApplicationProvider does not return the provider whose ARN was requested (fixture sso-admin-application-provider-describe-round-trip, step task#2).
AWS: DescribeApplicationProvider takes one required input member ApplicationProviderArn (Smithy: @required, @length 10-1224, @pattern ^arn:aws(-[a-z]{1,5}){0,3}:sso::aws:applicationProvider/[a-zA-Z0-9-/]+$) and returns that same provider: the output's ApplicationProviderArn is itself @required and must echo the requested ARN, alongside FederationProtocol (enum SAML|OAUTH), DisplayData {DisplayName, IconUrl, Description} and ResourceServerConfig. An ARN that names no provider in the catalog is ResourceNotFoundException / HTTP 404, which the operation models; it is never a 200 carrying a different provider. The recording shows the ARN arn:aws:sso::aws:applicationProvider/catalog/Statuspage resolving to the catalog's Statuspage entry: FederationProtocol SAML, DisplayName "Statuspage", Description "Statuspage Application". The requirement is the lookup rule - the response describes the requested ARN - not these particular Statuspage values; the catalog of third-party SaaS providers under the catalog/ prefix and their SAML federation is AWS's data, recorded behavior for the exact per-provider strings.
Emulator: 200, but describing an entirely different provider than the one asked for. Every identifying member diverged: $.ApplicationProviderArn 'arn:aws:sso::aws:applicationProvider/catalog/Statuspage' -> 'arn:aws:sso::aws:applicationProvider/custom', $.FederationProtocol 'SAML' -> 'OAUTH', $.DisplayData.DisplayName 'Statuspage' -> 'SSO Custom Application Provider', $.DisplayData.Description 'Statuspage Application' -> 'SSO Custom Application Provider Application', $.DisplayData.IconUrl path segment app-d77638588eff9057 -> app-6cdfd271da635d49 (and identically on the nested $.ApplicationProvider.* view of the same body). The returned ARN is not the requested one, so the handler is falling back to a default/first entry of its synthesized table rather than either resolving the requested ARN or raising ResourceNotFoundException.
Why: a client that describes a provider before connecting an application to it - reading FederationProtocol to decide whether to configure SAML or OAUTH, reading DisplayData to render the provider in a UI - is handed a different provider under a 200 and has no signal that its lookup missed. It configures OAUTH for a SAML provider, and because the ARN it gets back is not the ARN it sent, even a client that defensively re-checks the echo cannot trust the response. The 404 path is also unreachable, so error handling for an unknown provider is never exercised.
Fix: the DescribeApplicationProvider handler's ARN lookup plus the catalog seed data it reads - resolve the request's ApplicationProviderArn against the catalog, return that entry, and return ResourceNotFoundException (404) when no entry matches, instead of defaulting to an arbitrary entry.
Traces: sso-admin-application-provider-describe-round-trip#task#2.

Cause 2 of 3: the DisplayData.IconUrl served for a provider is a fabricated URL, not the provider's icon (fixture sso-admin-application-provider-not-found-describe-rejected, step task#2).
AWS: DisplayData.IconUrl is modelled @length 1-768, @pattern ^(http|https):\/\/.*$ and documented as "A URL that points to an icon that represents the application provider". Recorded behavior only for its construction: the recordings show AWS serving icons from the fixed host https://static.global.sso.amazonaws.com under a path /app-<provider-app-id>/icons/default.png, where the app id segment is a stable attribute of that provider in AWS's catalog - it is constant across accounts, regions and runs (the same provider yields the same URL in every recording), so it is catalog data and not a per-run value. The requirement is that the URL served for a provider is that provider's own icon URL as carried in the catalog, with only the app-id segment varying between providers.
Emulator: 200 in which every other member of the described provider matched - the ARN, FederationProtocol, DisplayName and Description all agreed - and ONLY the icon diverged: $.DisplayData.IconUrl (and $.ApplicationProvider.DisplayData.IconUrl) expected the path segment app-efbe0dd582ec4f87, got app-6cdfd271da635d49, on the same host and the same /icons/default.png suffix. Hypothesis: the emulator derives the app-id segment from the synthesized entry (e.g. a hash of its own name or ARN) rather than storing the provider's real icon URL, which is why the host and the URL template are right while the identifying segment is not - and why the SAME wrong segment app-6cdfd271da635d49 appears in cause 1 and cause 3 for different providers.
Why: a portal or console-like client renders the provider with a URL that resolves to the wrong icon or to nothing on AWS's CDN, and a client that caches or compares icon URLs per provider sees providers collide, because the emulator reuses one fabricated segment where AWS gives each provider a distinct one.
Fix: the application-provider catalog seed data - carry each provider's real IconUrl from the catalog and have the DisplayData serializer emit it verbatim, rather than generating the app-id path segment at serialization time.
Traces: sso-admin-application-provider-not-found-describe-rejected#task#2.

Cause 3 of 3: ListApplicationProviders enumerates a synthesized provider list, not the Identity Center catalog (fixture sso-admin-catalog-list-application-providers, step task#1).
AWS: ListApplicationProviders returns ApplicationProviders, an ApplicationProviderList of ApplicationProvider structures (@required ApplicationProviderArn, FederationProtocol, DisplayData, ResourceServerConfig). The recorded 200 enumerates the Identity Center application-provider catalog: entries whose ARNs take the form arn:aws:sso::aws:applicationProvider/catalog/<ProviderName> for the third-party SaaS catalog (recorded examples at the head of the list: catalog/Statuspage "Statuspage", catalog/DuoNetworkGateway "Duo Network Gateway", catalog/DruvaInSync "DruvaInSync"), each with FederationProtocol SAML and a DisplayData whose DisplayName is the provider's display name, whose Description is that display name followed by " Application", and whose IconUrl is that provider's own icon URL. The requirement is that the enumeration serves the real catalog and that an entry listed here is the same entry DescribeApplicationProvider returns for its ARN; the specific provider names are recorded behavior.
Emulator: 200 whose entries are positionally wrong from index 0 onward - the report flags $.ApplicationProviders[0] through $.ApplicationProviders[393], i.e. the whole list. Instead of the catalog the emulator lists providers it made up from AWS service names: index 0 'arn:aws:sso::aws:applicationProvider/custom' / 'SSO Custom Application Provider' / OAUTH, index 1 '.../athena' / 'Amazon Athena' / OAUTH, index 2 '.../emr' / 'Amazon EMR' / OAUTH. No entry uses the catalog/<ProviderName> ARN form, none uses SAML, and every Description is the mechanical "<DisplayName> Application" of a synthesized name. This is the same synthesized table cause 1's lookup falls back into - index 0 is exactly the 'custom' entry Describe wrongly returned.
Why: the catalog listing is how a client discovers which application providers it may connect an application to. Here it discovers a set of providers that does not exist on AWS, so every id it carries forward - into DescribeApplicationProvider, into CreateApplication - is an ARN AWS rejects, while the real catalog/<Provider> ARNs a client already holds appear nowhere in the listing and look deleted. Code that filters the catalog by FederationProtocol == SAML gets an empty result.
Fix: the application-provider catalog seed data behind the ListApplicationProviders handler - seed the real Identity Center catalog (catalog/<ProviderName> ARNs, each provider's FederationProtocol, DisplayName, Description and IconUrl) and serve it from the one table both List and Describe read, so the two read paths agree.
Traces: sso-admin-catalog-list-application-providers#task#1.
