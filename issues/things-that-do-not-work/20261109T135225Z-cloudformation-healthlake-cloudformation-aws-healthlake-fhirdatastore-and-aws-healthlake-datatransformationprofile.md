# cloudformation: AWS::HealthLake::FHIRDatastore and AWS::HealthLake::DataTransformationProfile are rejected as unrecognized resource types, so no HealthLake stack can be deployed

> _Note: this issue was identified against the code base at commit `01e7e7e4d8371571a5c4b5afb30bf8b87d00507b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One cause, found by replaying the simparity-behavioral-aws-v1 behavioral suite against the emulator built from this checkout. All four failing checks under the suite heading '### cloudformation__healthlake' (0/4 passed) fail on their very FIRST CreateStack, with the same refusal.

Cause 1 of 1: CloudFormation's template resource-type registry does not know the AWS::HealthLake::* resource types, so CreateStack refuses at template validation any stack that declares a HealthLake FHIR data store or a HealthLake data transformation profile. Failing checks: cloudformation__healthlake.deploy-healthlake-fhir-datastore-round-trip-and-delete, cloudformation__healthlake.deploy-healthlake-fhir-datastore-invalid-type-version-rejected, cloudformation__healthlake.deploy-healthlake-data-transformation-profile-round-trip-and-delete, cloudformation__healthlake.deploy-healthlake-data-transformation-profile-invalid-source-format-rejected.

AWS: CloudFormation publishes AWS::HealthLake::FHIRDatastore and AWS::HealthLake::DataTransformationProfile as first-class resource types (see the template reference for aws-resource-healthlake-fhirdatastore and aws-resource-healthlake-datatransformationprofile), so a template declaring them is ACCEPTED by CreateStack and provisioned through the HealthLake control plane. Smithy (services/service-com-amazonaws-healthlake-healthlake/smithy-model/com-amazonaws-healthlake-healthlake.json, service HealthLake, awsJson1_0, sigv4 'healthlake'): CreateFHIRDatastore (DatastoreName, DatastoreTypeVersion enum FHIRVersion with the single value R4, Tags) returns DatastoreId/DatastoreArn/DatastoreStatus/DatastoreEndpoint; DescribeFHIRDatastore returns DatastoreProperties with DatastoreStatus reaching ACTIVE, and CreateDataTransformationProfile (ProfileName, SourceFormat enum [CCDA, CSV], Source.ProfileMapping.ProfileMapping map, Tags) returns ProfileId/ProfileArn, readable through GetDataTransformationProfile and ListDataTransformationProfiles. On the deploy path that means: the stack reaches CREATE_COMPLETE, Ref on the data-store resource yields the DatastoreId and Fn::GetAtt yields DatastoreArn / DatastoreEndpoint / DatastoreStatus, Ref on the profile resource yields its ARN and Fn::GetAtt ProfileId its id, and DeleteStack removes the underlying HealthLake resources. For the two rejection checks, the property-level refusal happens inside the stack, NOT at CreateStack: AWS accepts the template, early property validation fails, the stack ends ROLLBACK_COMPLETE with one stack-level CREATE_FAILED event whose ResourceStatusReason is the fixed sentence "Validation failed with 1 error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.", DescribeEvents reports exactly one VALIDATION_ERROR row (ValidationName PROPERTY_VALIDATION, ValidationStatus FAILED, ValidationFailureMode FAIL) whose ValidationStatusReason is "<rejected value> is not a valid enum value. Supported values: [<allowed values>]" — fixed text " is not a valid enum value. Supported values: [" with the rejected value from the request and the member's modelled enum values as its variable parts — and whose ValidationPath is /Resources/<LogicalId>/Properties/<PropertyName>; the logical resource itself has no entry (DescribeStackResource answers ValidationError "Resource <LogicalId> does not exist for stack <StackName>") and no HealthLake resource is created.

Emulator: every such CreateStack is refused synchronously with HTTP 400, error code ValidationError and message "Template format error: Unrecognized resource types: [AWS::HealthLake::DataTransformationProfile]" (profile templates) or "Template format error: Unrecognized resource types: [AWS::HealthLake::FHIRDatastore]" (data-store templates). Fixed text of that message is "Template format error: Unrecognized resource types: [" ... "]"; the bracketed list is the set of type names taken from the submitted template. That code/message shape is what AWS emits for a genuinely unknown type — the defect is that these two HealthLake types are classified as unknown at all. No StackId is returned, so nothing downstream (stack status, events, outputs, Ref/GetAtt, the HealthLake resources themselves, the property-validation rejection path) is reachable.

Why: a client that provisions HealthLake through IaC (CloudFormation, CDK, SAM) cannot create a stack at all — the call fails before a stack exists, so there is no stack id to poll and no rollback to inspect. A caller that reads ValidationError/"Template format error" as "my template is wrong" hunts a template bug that does not exist, and the whole HealthLake-through-CloudFormation surface (including the in-stack property-validation refusal, which AWS reports as stack events rather than a CreateStack error) is unobservable.

Fix: the cloudformation service crate's template resource-type registry consulted during CreateStack template validation, plus the per-type provisioner it dispatches to — add AWS::HealthLake::FHIRDatastore (create/delete, Ref = DatastoreId, GetAtt DatastoreArn/DatastoreEndpoint/DatastoreStatus, and the DatastoreTypeVersion enum property validation that must surface as a PROPERTY_VALIDATION event rather than a CreateStack error) and AWS::HealthLake::DataTransformationProfile (create/delete, Ref = profile ARN, GetAtt ProfileId, SourceFormat enum property validation), each driving the HealthLake crate's own state so the resources read back through DescribeFHIRDatastore / ListFHIRDatastores / GetDataTransformationProfile / ListDataTransformationProfiles. Related open issues of the same class, named here because neither covers the HealthLake types: 20261109T115129Z-cloudformation-ec2-neptune-graph-cloudformation-aws-neptunegraph-graph-and-aws-neptunegraph-privategraphendpoint.md (AWS::NeptuneGraph::*) and 20261109T123922Z-acm-cloudformation-ec2-aws-ec2-clientvpnendpoint-clientvpnauthorizationrule-are.md (AWS::EC2::ClientVpn*).

Traces: all four checks listed above; each raises the ClientError at its first create_stack() call.
