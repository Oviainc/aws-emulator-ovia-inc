# efs__lambda: 2 net-new causes — an EFS access point is never mounted in the Lambda execution environment (every handler filesystem/POSIX call raises OSError), and CreateFunction accepts FileSystemConfigs with no VpcConfig

> _Note: this issue was identified against the code base at commit `54b3fe10738e925f02de63999e233b2f22231166`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two net-new root causes in the EFS-backed Lambda surface. Both were replayed against the running emulator (CreateFileSystem/CreateMountTarget/CreateAccessPoint/CreateFunction all answered 2xx), so the services answer — they answer wrongly.

Cause 1 of 2: the Lambda execution environment never mounts the EFS access point at FileSystemConfigs[].LocalMountPath, and the sandbox has no filesystem or process surface at all.
AWS: Smithy (lambda) CreateFunction.FileSystemConfigs -> FileSystemConfig{Arn (required, pattern ^arn:aws[a-zA-Z-]*:elasticfilesystem:...:access-point/fsap-[a-f0-9]{17}$), LocalMountPath (required, pattern ^/mnt/[a-zA-Z0-9-_.]+$)}, documented as "The path where the function can access the file system, starting with /mnt/" (https://docs.aws.amazon.com/lambda/latest/dg/configuration-filesystem.html). On AWS the access point's root directory is NFS-mounted at that path inside every execution environment: the handler's os.path.ismount('/mnt/<x>') is true, os.getuid() returns the access point's PosixUser Uid, open(...,'w') under the mount succeeds when the role has elasticfilesystem:ClientWrite, and fails with OSError errno EROFS when the role has only ClientMount. Invoke answers HTTP 200 with the handler's own payload and NO FunctionError.
Emulator: Invoke answers StatusCode 200 with FunctionError='Unhandled' and an OSError payload from the emulator's own runtime, not from the handler's logic. Two distinct refusal texts are emitted: errorType 'OSError', errorMessage 'a Lambda function in this emulator has no host filesystem or process to reach' (raised at the handler line calling os.path.ismount(ROOT)/os.getuid()), and errorType 'OSError', errorMessage 'a Lambda function in this emulator cannot open a file of the host' (raised at the handler line calling open(os.path.join(MOUNT, name), 'w')). Where a handler catches OSError and reports errno, the exception carries exc.errno = None, so a write that AWS would have let through under a ClientWrite role reports {'written': False, 'errno': 'None'} instead of {'written': True}, and a write AWS would refuse under a ClientMount-only role reports 'None' instead of 'EROFS'. These texts are the emulator's own wording, not anything AWS ever sends; the mount path ('/mnt/shared', '/mnt/data') and file names are request values, the quoted sentences are the emulator's fixed text.
Why: EFS-backed Lambda has no data plane. A client cannot verify that a mount exists, that an access point confines a function to its own RootDirectory, that two functions share one file system, or that the ClientMount-vs-ClientWrite permission boundary is enforced read-only — every such invoke comes back as an unhandled runtime error, and any handler that catches OSError sees errno None, so code branching on EROFS/EACCES takes the wrong branch. Worse, the failure is reported as the customer's function failing (FunctionError 'Unhandled') rather than as an unimplemented emulator capability.
Fix: the Lambda runtime/execution-environment component that builds a function's sandbox — it must materialise each FileSystemConfigs entry as a readable/writable directory at LocalMountPath backed by the access point's RootDirectory in EFS state, expose the access point PosixUser Uid/Gid to the handler process, and when it must refuse, refuse with an OSError carrying the errno AWS's NFS client would set (EROFS without elasticfilesystem:ClientWrite, EACCES for a denied path) rather than a bare message with errno None.
Traces: efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied (os.path.ismount/os.getuid), efs__lambda.efs-access-point-confines-each-function-to-its-own-root-directory (open for write), efs__lambda.efs-mount-without-client-write-is-read-only-and-write-rejected ({'written': False, 'errno': 'None'}). Open issues 20261023T153329Z-efs-lambda-the-shared-efs-mount-check-never.md and 20261024T012650Z-efs-lambda-the-shared-efs-access-point-lambda.md report these scenarios only as never-terminating poll loops and do not carry these checks' current replay keys; the checks now get all the way to an invoke and fail on the mount itself.

Cause 2 of 2: CreateFunction accepts FileSystemConfigs referencing an EFS access point when the function has no VpcConfig.
AWS: an EFS file system is only reachable through a mount target in a VPC, so Lambda requires the function to be VPC-configured before it will attach an access point (https://docs.aws.amazon.com/lambda/latest/dg/configuration-filesystem-efs.html). Smithy (lambda) CreateFunction declares InvalidParameterValueException (client error, HTTP 400) for a request parameter that is not valid, and AWS refuses this request with HTTP 400, Error.Code 'InvalidParameterValueException' and message 'Function must be configured to execute in a VPC to reference access point <access-point-arn>. Please update the function configuration to include VPC subnets and security groups.' — the two sentences are AWS's fixed text, and the only variable part is the access point ARN taken from the request's FileSystemConfigs[].Arn. Nothing is created: a following GetFunction answers ResourceNotFoundException 'Function not found: <function-arn>'.
Emulator: the same CreateFunction (Runtime python3.13, Role set, FileSystemConfigs=[{Arn: <access-point arn>, LocalMountPath: '/mnt/data'}], NO VpcConfig) is accepted with HTTP 201 and a full function configuration that echoes FileSystemConfigs and reports State 'Pending'/StateReasonCode 'Creating'. No refusal is emitted and the function exists afterwards.
Why: a client that relies on Lambda to catch this misconfiguration gets a function that AWS would never have created; on real AWS it would be refused at create time, while here it is created and will simply never have a working mount, so negative tests of this configuration rule pass where they must fail and the misconfiguration surfaces only at invoke time.
Fix: the CreateFunction handler's request validation (and the same check in UpdateFunctionConfiguration), after the FileSystemConfigs pattern checks: when FileSystemConfigs is non-empty and VpcConfig carries no SubnetIds/SecurityGroupIds, refuse with InvalidParameterValueException and the message above, and create no function state.
Traces: efs__lambda.filesystemconfigs-mount-path-outside-mnt-and-missing-vpc-rejected (step 1 of that check, the LocalMountPath pattern refusal, now passes; it fails on step 2). Open issue 20261109T132032Z-efs-lambda-the-access-point-id-efs-mints.md carries this check's replay key for the earlier access-point-id cause and does not cover this missing VpcConfig validation.

## Steps to Reproduce
Common setup: CreateFileSystem, poll DescribeFileSystems until LifeCycleState 'available', CreateMountTarget in a VPC subnet with a security group, poll until the mount target is 'available', CreateAccessPoint with RootDirectory Path '/shared' (or '/export/lambda') and PosixUser Uid/Gid 1001, and create an execution role allowing the ec2 network-interface actions plus elasticfilesystem:ClientMount (+ClientWrite where noted).

Cause 1:
1. CreateFunction (runtime python3.13) with VpcConfig={SubnetIds:[subnet], SecurityGroupIds:[sg]} and FileSystemConfigs=[{Arn: <access point arn>, LocalMountPath: '/mnt/data'}]; wait for State 'Active'.
2. Invoke it with a handler that returns {'ismount': os.path.ismount('/mnt/data'), 'proc_uid': os.getuid()} — observe StatusCode 200 with FunctionError 'Unhandled' and errorMessage 'a Lambda function in this emulator has no host filesystem or process to reach'.
3. Invoke a handler that does open('/mnt/data/a.txt','w') — observe FunctionError 'Unhandled' and errorMessage 'a Lambda function in this emulator cannot open a file of the host'; if the handler catches OSError it sees exc.errno is None.
4. Repeat step 3 with a role granting only ClientMount: the answer is indistinguishable from the ClientWrite case (errno 'None'), where AWS gives EROFS only for the ClientMount-only role.

Cause 2:
1. CreateFunction with the same Role, Runtime python3.13, Handler index.handler, a zip Code, FileSystemConfigs=[{Arn: <access point arn>, LocalMountPath: '/mnt/data'}] and NO VpcConfig.
2. Observe HTTP 201 and a function configuration echoing FileSystemConfigs, instead of HTTP 400 InvalidParameterValueException 'Function must be configured to execute in a VPC to reference access point <arn>. Please update the function configuration to include VPC subnets and security groups.'
3. GetFunction on that name: it is found, where AWS answers ResourceNotFoundException 'Function not found: <function-arn>'.
