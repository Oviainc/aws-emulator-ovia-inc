# CodeArtifact list reads project resource fields that diverge: ListDomains encryptionKey and the root package group description

> _Note: this issue was identified against the code base at commit `216f714d250c6d780581584a9f6355ede0acb526`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDomains

## Description
This issue bundles the TWO clusters of the simparity-wire-aws-v1 wire replay that no open issue's replay key covers (the replay reports owned_by EMPTY and stub_path empty for both). Both are a CodeArtifact list/read projection reporting a resource field whose value is not the one AWS reports: ListDomains reports a domain encryptionKey that is not the key bound to the domain, and ListPackageGroups reports the implicit root package group with no description. A fixer must close BOTH causes before submitting; each names its own failing fixture step. Domain names, group patterns, account numbers and KMS key UUIDs quoted below are one run's values filling a template - the FIELD and its derivation rule are the requirement, never the literal value.

=== Cause 1 of 2: ListDomains reports an encryptionKey that is not the key bound to the domain ===
AWS: Smithy DomainSummary.encryptionKey is an Arn (@length 1..1011, @pattern ^\S+$), documented as "The key used to encrypt the domain", and is a member of every DomainSummary that ListDomains (POST /v1/domains, 200) returns; the sibling DomainDescription.encryptionKey is "The ARN of an Key Management Service (KMS) key associated with a domain". CreateDomain.encryptionKey is the key the CALLER names (a key id, key ARN, alias or alias ARN). The key a domain is listed with is therefore the key that domain was actually created against, resolved to a key ARN, and it is the SAME string every later read of that domain reports (DescribeDomain, ListDomains, DeleteDomain).
Emulator: the DomainSummary for the listed domain carries a DIFFERENT KMS key ARN from the one the replayed CreateDomain bound to that domain, in the same account and region - recorded 'arn:aws:kms:<region>:<account>:key/<key-bound-by-the-request>', served 'arn:aws:kms:<region>:<account>:key/<a-key-the-emulator-synthesised>' - and it repeats that substituted value consistently. The listing itself is a faithful projection: services/service-com-amazonaws-codeartifact-codeartifactcontrolplaneservice/src/ops/list_domains.rs pages the store through crate::state::Domain::summary, so it reports whatever encryption_key the domain record was stored with. Hypothesis: the domain record is seeded with a synthesised per-domain key (crate::state::default_encryption_key_arn) instead of the key the CreateDomain request named, so the wrong value is already in state by the time any read runs.
Why: callers read this field to grant kms:Decrypt / kms:CreateGrant on the right key, to assert a domain was created with the CMK they passed, and to correlate a domain with its key in inventory or audit output. A listing that names a key the caller never supplied - and that no KMS store holds - breaks all three, and the error stays invisible until a key-scoped policy or a key-to-domain join fails.
Fix: the encryption-key derivation on the domain-creation path (src/ops/create_domain.rs) and the fallback it uses in src/state.rs: a request that names a key must store and report that key resolved to its key ARN, so Domain::summary projects it for ListDomains; only a request naming no key may fall back, and the fallback must be a key the emulator's KMS actually holds. No change is needed in list_domains.rs itself beyond it projecting the corrected stored value.
Related but NOT covering this: open issue 20261029T203338Z-codeartifact-domain-policy-and-package-group-resource-fields.md discusses the same encryptionKey substitution as its Cause 2 and mentions this fixture, but its stored replay keys do not match this ListDomains cluster (the replay reports owned_by empty for it, and the issue's Issue-Key for ListDomains is truncated mid-ARN-selector), so closing that issue does not re-replay this step. This issue carries the key that does.
Traces: codeartifact-list-domains-pagination#task#4 (ListDomains, 200 -> 200; the cluster also covers codeartifact-list-domains-pagination#task#5).

=== Cause 2 of 2: the root package group is listed with no description ===
AWS: Smithy PackageGroupSummary.description is a Description (@length 0..1000, @pattern ^\P{C}*$), "The description of the package group", a member of the PackageGroupSummaryList that ListPackageGroups (POST /v1/package-groups, 200) returns. CodeArtifact creates the root package group '/*' implicitly with every domain; recorded behavior: the root group's summary carries description = "Default root package group" - fixed text the service assigns, identical for every domain and derived from nothing in the request. Here the entry is addressed by its package-group ARN arn:aws:codeartifact:<region>:<account>:package-group/<domain>/%2a (the URL-encoded '/*' pattern), in a listing that also contains caller-created groups.
Emulator: that entry's description member is ABSENT (expected 'Default root package group', got None) while every other asserted member of the summary matches and the caller-created groups' own descriptions are reported - so the record exists and the projection works; only the root group's description was never populated.
Why: a client that lists package groups to display or diff them, or that identifies the service-created default by its description, sees an unset field where AWS always sets one; a round-trip of listing output back into UpdatePackageGroup also drops the description.
Fix: the root package-group record the domain-creation path seeds in src/state.rs must carry the service's fixed description "Default root package group", and/or the summary projection that src/ops/list_package_groups.rs calls must populate it for the root group. Verify in a domain holding several caller-created groups, not only a fresh one.
Related but NOT covering this: open issue 20261101T115804Z-codeartifact-root-package-group-is-listed-with-no.md describes this same omission and lists this step as its Cause 2, but its replay key for the ARN-addressed cluster is truncated mid-selector, so the replay reports owned_by empty here and closing that issue does not re-replay this step.
Traces: codeartifact-package-group-lifecycle-and-hierarchy#task#7 (ListPackageGroups, 200 -> 200).
