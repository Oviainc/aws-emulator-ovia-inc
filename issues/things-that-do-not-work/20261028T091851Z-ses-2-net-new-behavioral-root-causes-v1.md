# ses: 2 net-new behavioral root causes — v1 GetIdentityDkimAttributes omits a requested identity from its required DkimAttributes map, and CreateCustomVerificationEmailTemplate never applies the FromEmailAddress verification gate

> _Note: this issue was identified against the code base at commit `990798dd89dc113e12b8dff945243bd6ffa338e5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetIdentityDkimAttributes

## Description
Two net-new behavioral root causes in the SES v1 surface. Neither is one of the scaffold-stub clusters the report marked ALREADY FILED, and neither check is marked OWNED by an open issue. Related open issues are named per cause below; neither carries these checks' replay keys.

Cause 1 of 2: SES v1 GetIdentityDkimAttributes answers 200 with a DkimAttributes map that has NO entry for an identity that was named in the request, so the required map cannot be indexed by the identity the caller asked about.
AWS: Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery) GetIdentityDkimAttributes input {Identities: IdentityList, required}; output {DkimAttributes: DkimAttributes, required}, where DkimAttributes is a map keyed by Identity with value IdentityDkimAttributes{DkimEnabled: Enabled required default false, documented "Is true if DKIM signing is enabled for email sent from the identity ... The default value is true"; DkimVerificationStatus: VerificationStatus required; DkimTokens: VerificationTokenList}. The operation models NO errors at all, so the only way it can report on an identity is through that map — AWS therefore returns one entry per identity named in Identities. SES v1 and SESv2 are two APIs over ONE set of account identities, so a domain identity created with sesv2 CreateEmailIdentity (POST /v2/email/identities) is reported through v1 with DkimEnabled=true, DkimVerificationStatus spelled in v1's TitleCase ('Pending') mirroring v2's SCREAMING_CASE ('PENDING'), and the SAME Easy DKIM tokens v2's DkimAttributes.Tokens returned for that domain.
Emulator: sesv2 CreateEmailIdentity on a fresh domain succeeds and v2 GetEmailIdentity reports a well-formed DkimAttributes (SigningAttributesOrigin AWS_SES, Status PENDING, SigningEnabled true, three distinct 32-character tokens) — every v2 assertion in the check passes. The very next call, ses(v1).get_identity_dkim_attributes(Identities=[<that domain>]), answers 200 but its DkimAttributes map contains no key for the domain, so the client's lookup raises KeyError on the requested identity. The map is served as if the identity did not exist, and because the operation models no errors there is no refusal either — the identity is simply absent.
Why: a client that creates identities with the modern API and reads DKIM state with the legacy one sees nothing: it cannot learn DkimEnabled, cannot read DkimVerificationStatus, and cannot fetch the CNAME tokens it must publish, so the Easy DKIM setup loop never completes. Worse, every AWS SDK treats DkimAttributes as a required map keyed by the requested identities and indexes it directly; an absent key is an unmodelled outcome that crashes the caller instead of yielding a status it can branch on.
Fix: the ses v1 GetIdentityDkimAttributes handler (services/service-com-amazonaws-ses-simpleemailservice/src/ops/get_identity_dkim_attributes.rs) and the identity state it reads: it must resolve every identity named in Identities out of the one account+region identity store that the sesv2 CreateEmailIdentity handler writes (mapping the v2 DKIM status spelling to v1's on read and serving the stored tokens), and must emit an entry for each requested identity rather than silently dropping it. Related open issue 20261025T214303Z-ses-identity-verification-is-auto-completed-and-the.md Cause 3 describes the unshared v1/v2 identity store for GetIdentityVerificationAttributes and ListIdentities; it does not name GetIdentityDkimAttributes and does not carry this check's replay key, so this map-entry defect is not closed by it.
Traces: ses.dkim-cname-token-shape-and-cross-api-identity.

Cause 2 of 2: CreateCustomVerificationEmailTemplate accepts a FromEmailAddress that is not a verified sending identity — the modelled FromEmailAddressNotVerified gate is never applied and the template is created.
AWS: Smithy CreateCustomVerificationEmailTemplate input {TemplateName, FromEmailAddress: FromAddress, TemplateSubject, TemplateContent, SuccessRedirectionURL, FailureRedirectionURL — all required}, output {} (Unit); modelled errors CustomVerificationEmailInvalidContentException, CustomVerificationEmailTemplateAlreadyExistsException, FromEmailAddressNotVerifiedException and LimitExceededException. FromEmailAddressNotVerifiedException carries awsQueryError code "FromEmailAddressNotVerified" with httpResponseCode 400 (httpError 400), has a FromEmailAddress member documented "Indicates that the from email address associated with the custom verification email template is not verified", and is itself documented "Indicates that the sender address specified for a custom verification email is not verified, and is therefore not eligible to send the custom verification email." So the create is a refusal, not a success, whenever FromEmailAddress is not a Success-verified identity of the account: HTTP 400, Error.Code "FromEmailAddressNotVerified", and the error message names the offending from-address — the address is a value taken from the request (FromEmailAddress), not fixed text. The refusal is also atomic: nothing is created, so an immediately following GetCustomVerificationEmailTemplate on that TemplateName is refused CustomVerificationEmailTemplateDoesNotExist (its only modelled error, httpError 400). The identical call with a verified sender succeeds, and GetCustomVerificationEmailTemplate then echoes that FromEmailAddress.
Emulator: for a from-address whose verification was only *requested* a moment earlier (ses.verify_email_identity with no confirmation click), CreateCustomVerificationEmailTemplate returns success — no ClientError is raised at all, so the check reports "expected FromEmailAddressNotVerified for an unverified sender, got None" — and the template is left behind in the account. The gate that distinguishes an eligible sender from an ineligible one is absent: the only modelled negative class for this operation's sender check never fires. Hypothesis: the handler performs no identity lookup for FromEmailAddress at all; alternatively the lookup finds the identity already reporting VerificationStatus 'Success' because of the auto-completed v1 verification described in open issue 20261025T214303Z-ses-identity-verification-is-auto-completed-and-the.md Cause 1. Either way the refusal path must exist and be driven by the stored verification status, and that issue does not carry this check's replay key.
Why: custom verification email templates are how a sender bootstraps recipient verification, and AWS deliberately refuses one whose from-address cannot send — accepting it produces a template that can never deliver, with the failure surfacing much later (at send time, or not at all). A client that relies on the refusal to validate operator input gets a silent success, cannot tell an unverified sender from a verified one, and must also contend with the leftover template the rejected call should never have created.
Fix: the ses v1 CreateCustomVerificationEmailTemplate handler's pre-flight validation (services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_custom_verification_email_template.rs): resolve FromEmailAddress in the account+region identity store, and when it is not verified for sending, refuse with FromEmailAddressNotVerifiedException (400, awsQuery code FromEmailAddressNotVerified, FromEmailAddress member set to the request's address) before any state is written, so the template is not persisted.
Traces: ses.custom-verification-template-unverified-from-fails.
