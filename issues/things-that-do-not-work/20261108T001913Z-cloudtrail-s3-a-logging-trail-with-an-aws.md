# cloudtrail__s3: a logging trail with an AWS::S3::Object advanced selector delivers no object data-event log file, so the success/NoSuchKey/AccessDenied classification of object calls is never auditable

> _Note: this issue was identified against the code base at commit `f42419e01630977583bc09726b6f41b0d8951344`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
ONE net-new root cause in this issue (Cause 1 of 1).

Cause 1 of 1 — an S3 object-level call made while a trail is logging with an advanced event selector scoped to AWS::S3::Object is never delivered as a data-event record to the trail's S3 bucket, so neither successful nor refused object calls can be audited.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) models the selector this check installs — PutEventSelectors with AdvancedEventSelectors whose FieldSelectors are eventCategory Equals ["Data"], resources.type Equals ["AWS::S3::Object"] and resources.ARN StartsWith [the data bucket's object prefix] — and GetTrailStatus.IsLogging reports the logging state. The delivery itself is recorded behavior only (measured by this check against real AWS): while such a trail is logging, every matching S3 object-level call is delivered as a gzipped JSON log object under the trail's bucket prefix AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/, one record per call, with eventSource "s3.amazonaws.com", eventCategory "Data", managementEvent false, requestParameters.bucketName / requestParameters.key taken from the request, exactly one resources[] entry of type AWS::S3::Object whose ARN is arn:aws:s3:::<bucket>/<key>, readOnly true for GetObject and false for PutObject, no errorCode/errorMessage member at all on a call that succeeded, and on a refused call errorCode plus the errorMessage the caller received — "NoSuchKey" with the fixed text "The specified key does not exist." for a GetObject on a key that is absent, and "AccessDenied" with the fixed text "User: ", " is not authorized to perform: ", " on resource: " (the resource ARN double-quoted) and " with an explicit deny in a resource-based policy", whose variable parts come from the request and state (the caller's assumed-role session ARN, the action name s3:GetObject / s3:PutObject, the target object ARN). The identity on each record is the principal that made the call (type AssumedRole with sessionContext.sessionIssuer.arn equal to the role for the denied role-session calls, the account's own principal otherwise, accountId equal to the calling account).

Emulator: nothing is ever delivered. The check creates the log bucket with the CloudTrail delivery policy and the data bucket, installs the advanced selector, calls StartLogging and confirms GetTrailStatus reports IsLogging=true, then issues its PutObject/GetObject/missing-key/denied rounds (which all return from S3) and polls ListObjectsV2 + GetObject over AWSLogs/ in the log bucket for the six records of any one round. Its own delivery budget is 600 s with a 2 s poll interval and up to 20 call rounds, so the poll never exits and the check is still polling when the harness cap ends it: verdict 'mismatch', detail 'Check timed out after 180.0s'. The check carries DATAPLANE_MARKER = 'DATAPLANE_UNIMPLEMENTED' for exactly this absence — no log object with any record appears in the bucket.

Why: S3 object data events are the highest-volume and most security-relevant audit stream AWS emits. A client that consumes the trail's S3 prefix (Athena/Glue over the log layout, SIEM ingestion, incident reconstruction) sees a permanently empty prefix and cannot distinguish "no one touched the data" from "nothing was recorded"; in particular a refused read (NoSuchKey) and a policy-denied read (AccessDenied) leave no evidence, so detective controls built on denied-access alerting silently never fire.

Fix: S3 object data-event capture plus trail log-file delivery — S3's object operations must feed the shared event-recording seam as eventCategory Data records carrying the AWS::S3::Object resource ARN, the request parameters, the readOnly class and, for refusals, the error code and the message the caller received; the trail's logging state must evaluate the stored advanced event selectors against those records and write the matching ones as gzipped objects into the configured bucket under the documented key layout.

NOTE: the open issue 20261102T102343Z-cloudtrail-s3-2-net-new-root-causes-s3.md describes this same delivery gap as its Cause 1 and even lists this check among its trace ids, but it bound this check under a different replay key (an AssertionError in _error, i.e. the bucket-policy Deny leg, which now progresses), and the replay report did NOT mark this check as owned by it. 3. Confirm GetTrailStatus reports IsLogging=true.
