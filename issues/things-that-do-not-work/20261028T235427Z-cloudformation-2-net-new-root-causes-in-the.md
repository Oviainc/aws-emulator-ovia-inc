# cloudformation: 2 net-new root causes in the resource-scan surface — the ResourceScanInProgress message is the model's doc sentence, and a scan never discovers an UNMANAGED resource

> _Note: this issue was identified against the code base at commit `92bcdac01f88c8b4612f5537a2ed608090c91758`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListResourceScanResources

## Description
REOPENS 20261026T235900Z-cloudformation-listresourcescanresources-stub.md: its fix left the call refused. ListResourceScanResources is no longer a 501 scaffold stub, but the in-progress gate it now serves refuses with a message AWS never sends, and the scan it reads from holds no unmanaged resources at all.

Two distinct net-new root causes of service `cloudformation`, each grounded in its own failing behavioral check(s). A fixer must close BOTH before submitting. Neither is covered by the open issue 20261026T235900Z-cloudformation-7-net-new-root-causes-in-the.md: that issue's causes 1-3 for this surface are the ResourceScanNotFound wording (now correct), ListResourceScans not sharing the scan index, and ListResourceScanResources answering NotImplemented (now implemented) — the failure modes below are what the operation does NOW.

Cause 1 of 2 — the ResourceScanInProgress refusal carries the exception shape's DOCUMENTATION sentence instead of the message AWS answers for this gate.
AWS: Smithy: ListResourceScanResources models ResourceScanInProgressException (errorKind client, httpError 400, awsQueryError code `ResourceScanInProgress`, member Message @length 1..255). Recorded behavior: while the named scan is IN_PROGRESS the call is refused 400 ResourceScanInProgress with the Message `The ResourceScan is in progress. Please wait for it to finish before performing any further operations on it. Describe ResourceScans to see the status of the in-progress ResourceScan.` — that whole sentence is FIXED text: nothing in it is taken from the request or from state (the scan id is not echoed, no count or timestamp appears). The same shape's doc sentence (`A resource scan is currently in progress. Only one can be run at a time for an account in a Region.`) is the StartResourceScan one-at-a-time refusal, a different message for a different gate.
Emulator: 400 ResourceScanInProgress with Message `A resource scan is currently in progress. Only one can be run at a time for an account in a Region.` — the modelled shape's documentation text, reused verbatim for the results gate.
Why: the code is right but the sentence is wrong, so a client (or an error-mapping layer, or a doc-driven test) that matches AWS's in-progress sentence to decide "not ready yet, keep polling" never matches, and the emulator tells a caller it is being rate-limited to one scan per Region when in fact the scan it asked about simply has not finished.
Fix: the resource-scan state module's message constants and the ListResourceScanResources handler in the cloudformation crate — the results gate must not share StartResourceScan's one-at-a-time sentence; it needs its own fixed in-progress sentence. Citations: services/service-com-amazonaws-cloudformation-cloudformation/src/state/resource_scans.rs (`pub const SCAN_IN_PROGRESS`, around line 672, documented as "the sentence the modelled ResourceScanInProgressException documents") used by services/service-com-amazonaws-cloudformation-cloudformation/src/ops/list_resource_scan_resources.rs (around line 195).
Traces: cloudformation.generated-template-and-scan-not-found-errors, cloudformation.resource-scan-result-ttl-expiry

Cause 2 of 2 — a resource scan only ever reads the resources of live CloudFormation stacks, so an UNMANAGED resource is never discoverable and ManagedByStack is never false.
AWS: Smithy: ScannedResource carries ResourceType, ResourceIdentifier and ManagedByStack ("If true, the resource is managed by a CloudFormation stack"); ListResourceScanResources is documented as "Lists the resources from a resource scan ... The response indicates whether each returned resource is already managed by CloudFormation." Recorded behavior: a resource scan is an account/Region inventory whose purpose is discovering resources CloudFormation does NOT manage — a topic created directly through the owning service's API (no stack involved) appears among a COMPLETE scan's rows for its type, identified by its primary identifier (for AWS::SNS::Topic, `TopicArn`), with ManagedByStack false; it can then be named in CreateGeneratedTemplate and imported into a new stack through an IMPORT change set, after which it reads back as a managed stack resource.
Emulator: the scan's rows are taken exclusively from this service's own stack records — "every resource of every live stack of that Region", so "[e]ach one is therefore managed by a CloudFormation stack" and ManagedByStack is derived as "the row records a stack id". A resource created outside CloudFormation is in no stack, so it is in no scan: ListResourceScanResources answers 200 with a Resources list that can never contain it, and no row can ever report ManagedByStack false.
Why: the entire discover -> generate-template -> import workflow (the reason resource scans exist) is unreachable: a client scanning for unmanaged resources always sees an empty or stack-only inventory, concludes nothing exists to adopt, and the IMPORT path is never exercised. Worse, the divergence is silent — a 200 with no rows reads as "nothing unmanaged in this account" rather than "unsupported".
Hypothesis (attribution of the replay verdict): the end-to-end check produces no assertion, only `Check timed out after 60.0s`. Its only poll bounded at exactly 60s is `_find_scanned_topic`, which does nothing but call ListResourceScanResources(ResourceScanId, ResourceTypePrefix='AWS::SNS::Topic') every 5s looking for the topic it created out of band; the earlier scan wait (420s budget) ends as soon as DescribeResourceScan reports COMPLETE, which this emulator does. The 60s wall is therefore consumed inside that loop, which the state module above shows can never succeed.
Fix: the resource-scan state module must build a scan's rows from the account/Region inventory the emulator holds across services (not only from this service's stack records) and must set ManagedByStack per row from whether a live stack manages it; the row's ResourceIdentifier must use the type's primary identifier. Citation: services/service-com-amazonaws-cloudformation-cloudformation/src/state/resource_scans.rs ("What a scan READS", lines ~40-52, and `is_managed_by_stack` at ~216).
Traces: cloudformation.e2e-resource-scan-generated-template-to-managed-stack
