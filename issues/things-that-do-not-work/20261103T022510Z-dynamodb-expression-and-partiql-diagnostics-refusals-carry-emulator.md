# DynamoDB expression and PartiQL diagnostics: refusals carry emulator-authored text and malformed operands are evaluated instead of validated (5 causes)

> _Note: this issue was identified against the code base at commit `6a6bdf627b2774134f5b74f649503c2b12968e19`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
Five net-new root causes in DynamoDB's request-validation/diagnostic layer. All of them are refusals that DO happen but with the wrong error code or the wrong message, so a client that parses or asserts on AWS's wording breaks. The open issue 20261030T060227Z-dynamodb-validationexception-messages-diverge-from-the-wording-aws.md describes the same family in general terms but does not carry any of the replay keys below; the open issue 20261029T180026Z-dynamodb-partiql-resource-policy-arn-addressing-crc32-header.md covers a different set of PartiQL checks.

=== Cause 1 of 5: every PartiQL parse/validation failure collapses to one generic message ===
AWS: ExecuteStatement/BatchExecuteStatement/ExecuteTransaction answer ValidationException (HTTP 400) whose Message names the specific defect. Smithy: ExecuteStatement.Statement -> PartiQLStatement @length min 1 max 8192; the service-common ValidationException carries the diagnosis. Recorded AWS wording, by defect class, is a template whose fixed text is the whole sentence and whose variable parts are the offending token/identifier/position taken from the submitted statement: "Statement wasn't well formed, can't be processed: Unexpected token after expression" (trailing token), "Statement wasn't well formed, can't be processed: Expected data manipulation", "Statement wasn't well formed, can't be processed: Expected identifier for simple path" (single-quoted table name), "Operator or function requires a document path; operator or function: <fn>", "Unrecognized function: <name> at <line>:<col>:<len>", "A path may contain at most 2 components in the FROM clause", "FROM clause may only contain a single table name in data manipulation statements at <line>:<col>:<len>", and inside a transaction the per-slot prefix "Validation failed in TransactStatements[<i>]: " followed by that same sentence.
Emulator: every one of those answers the single string "Invalid Statement: statement wasn't well formed, could not be parsed" (or, for a write through an index qualifier, "This operation is not supported on an index"; for parameter arity, "Invalid Statement: the number of parameters in the request and in the statement do not match"; for 38-digit overflow, "1 validation error detected: Attempting to store more than 38 significant digits in a Number"). A transaction slot failure is not prefixed with "Validation failed in TransactStatements[<i>]: " and execute-transaction-index-select-top-level-validation-not-cancellation answers an invented sentence ("a read statement in a transaction must address one item of the table: ...") instead of AWS's top-level ValidationException text.
Why: a client cannot tell a syntax error from an unknown function from an index-qualifier misuse, and SDK/tooling that surfaces the message to a developer shows a diagnosis AWS never produces. Transaction callers lose the slot index entirely.
Fix: the PartiQL parser/validator behind the ExecuteStatement, BatchExecuteStatement and ExecuteTransaction handlers must classify the parse failure and render AWS's per-class message, including the per-slot prefix for transactions.
Traces: batch-execute-statement-malformed-slot-siblings-execute, execute-statement-extra-token-after-complete-statement-rejected, execute-statement-malformed-literal-rejected, execute-statement-missing-clause-rejected, execute-statement-quoting-rules, execute-statement-function-requires-document-path-or-operand-count-rejected, execute-statement-undefined-function-and-projection-function-rejected, execute-transaction-malformed-statement-rejects-whole-call, partiql-from-clause-path-arity-rejected, partiql-unknown-index-qualifier-rejected, partiql-write-through-index-qualifier-rejected, execute-statement-parameter-count-and-key-type-mismatch-rejected, execute-statement-number-precision-in-update-set-and-key-equality, execute-transaction-index-select-top-level-validation-not-cancellation.

=== Cause 2 of 5: expression-language refusals report a generic token-level syntax error instead of AWS's operator/function diagnosis ===
AWS: a malformed ConditionExpression/FilterExpression/UpdateExpression/ProjectionExpression is refused with ValidationException (HTTP 400) whose message names the rule that was broken. Fixed text with request-supplied variables: "Invalid <ExpressionKind>: The expression can not be empty;" for an empty expression; "Invalid <ExpressionKind>: Operator or function requires a document path; operator or function: <fn>" when a value placeholder is passed where a path is required; "Invalid <ExpressionKind>: Incorrect number of operands for operator or function; operator or function: <fn>, number of operands: <n>"; "Invalid <ExpressionKind>: Expression size has exceeded the maximum allowed size;" at the 4096-byte ceiling. Item-level calls prefix "1 validation error detected: " only where AWS does.
Emulator: all of these answer "Invalid <ExpressionKind>: Syntax error; token: \"<tok>\", near: \"<ctx>\"" — for example an empty FilterExpression answers 'Invalid FilterExpression: Syntax error; token: "<EOF>", near: ""' where AWS answers 'Invalid FilterExpression: The expression can not be empty;', and attribute_exists(:v) answers 'Invalid FilterExpression: Syntax error; token: ")", near: ":v )"' where AWS answers the "requires a document path" sentence. duplicate-set-members-in-condition-key-and-transact-rejected is answered with an unrelated reserved-keyword message.
Why: the message is the only machine-readable statement of which expression rule was broken; a generic token dump tells a client nothing, and does not match AWS for any of these classes.
Fix: the expression parser/validator shared by the item and query/scan handlers must emit AWS's per-rule message, and only a true syntax error may use the "Syntax error; token:" form.
Traces: ddb-frc-empty-filter-expression-rejected, ddb-sfa-attribute-exists-on-a-value-placeholder-rejected, ddb-sfa-attribute-exists-with-two-operands-rejected, ddb-sfa-unused-expression-attribute-name-in-scan-rejected, empty-string-expression-rejected-across-operations, transact-write-items-condition-expression-defects-match-putitem-message, expression-attribute-map-key-syntax-and-length-rejected, filter-and-key-condition-expression-size-limit-rejected, duplicate-set-members-in-condition-key-and-transact-rejected, transact-write-expression-parse-errors-rejected-top-level.

=== Cause 3 of 5: KeyConditionExpression operand/shape defects are reported as key-type mismatches or schema-coverage errors ===
AWS: a KeyConditionExpression whose operator/operand pairing is illegal is refused with ValidationException and a KeyConditionExpression-scoped message: "Invalid KeyConditionExpression: Incorrect operand type for operator or function; operator or function: <op>, operand type: <T>" (e.g. begins_with with an N operand against an S sort key), "Invalid KeyConditionExpression: KeyConditionExpressions must only contain one condition per key" when a key is constrained twice, and a document path or reserved head in a key position is likewise reported against KeyConditionExpression. Value-first comparison forms (":lo <= sk") are legal and must be served.
Emulator: begins_with with an N operand answers 'One or more parameter values were invalid: Type mismatch for key sk expected: S actual: N'; a doubly-constrained sort key answers 'Invalid key condition: the sort key sk is constrained more than once'; 'pk.foo = :v' answers 'Query condition missed key schema element: pk'; and ':lo <= sk' is refused outright with 'Invalid KeyConditionExpression: Syntax error; token: "<=", near: ":lo <= sk"' instead of being evaluated.
Why: a client cannot distinguish a schema/type problem from an expression-grammar problem, and the last case refuses a query AWS answers, so a working query fails against the emulator.
Fix: the Query handler's key-condition parser and validator.
Traces: key-condition-illegal-sort-key-operator-rejected, query-key-condition-operand-type-vs-schema-type-rejected, query-key-condition-duplicate-sort-key-clause-and-nested-path-rejected, query-key-condition-document-path-forms-and-reserved-head-rejected, query-value-first-sort-key-comparison-and-size-of-absent-attribute.

=== Cause 4 of 5: ill-typed or malformed condition operands are evaluated instead of validated ===
AWS: a condition whose shape is illegal is a request defect, refused before any item is read, with ValidationException (HTTP 400). Examples: an ordering comparator against a non-orderable literal (n < :v where :v is BOOL), BETWEEN with reversed bounds, contains(path, path) with the same path on both sides, attribute_type with a type name outside the AttributeValue type set, and a malformed N literal in ExpressionAttributeValues. Inside TransactWriteItems these are top-level ValidationException, not a cancellation.
Emulator: each of these is evaluated as a predicate that simply does not match, so the call is refused with ConditionalCheckFailedException "The conditional request failed" (HTTP 400) — and inside a transaction with TransactionCanceledException "Transaction cancelled, please refer cancellation reasons for specific reasons [ConditionalCheckFailed, None]". ddb-ss-attribute-type-with-an-unknown-type-name-rejected is not refused at all: the call succeeds.
Why: ConditionalCheckFailedException is retryable-looking application state ("someone else changed the item") while ValidationException is a programming error; a client retries forever or writes the wrong branch. Conditional-write idioms that key on the error code behave incorrectly.
Fix: validate condition shape and operand types in the expression validator, before condition evaluation, in the PutItem/UpdateItem/DeleteItem/TransactWriteItems and Query/Scan handlers.
Traces: condition-expression-contains-same-path-and-between-reversed-rejected, condition-ordering-comparison-non-orderable-literal-rejected, ddb-sfa-condition-attribute-type-with-an-unknown-type-name-rejected, ddb-ss-attribute-type-with-an-unknown-type-name-rejected, delete-item-condition-between-bounds-validated, malformed-n-in-expression-value-rejected-before-evaluation, transact-write-condition-non-orderable-literal-rejected.

=== Cause 5 of 5: the ExpressionAttributeNames/Values-without-an-expression rule is the wrong rule, and the "1 validation error detected:" prefix is applied inconsistently ===
AWS: supplying ExpressionAttributeNames or ExpressionAttributeValues on a call that carries NO expression parameter at all is refused with "1 validation error detected: ExpressionAttributeValues can only be specified when using expressions" (and the ExpressionAttributeNames counterpart). The different defect of supplying a placeholder that no expression references is the separate message "Value provided in ExpressionAttributeValues unused in expressions: keys: {<k>}" — and AWS serves that one WITHOUT the "1 validation error detected: " prefix on the transaction and item paths exercised here.
Emulator: the "no expression at all" case is answered with the "unused in expressions" message, so the two distinct defects are indistinguishable; and the prefix is inverted — the emulator emits '1 validation error detected: Value provided in ExpressionAttributeValues unused in expressions: keys: {:unused}' where AWS emits the bare sentence, and emits the bare sentence where AWS prefixes.
Why: the message is the contract; a client (or a test suite) that matches AWS's text fails on both halves, and the two defects cannot be told apart.
Fix: the shared expression-parameter validation used by PutItem/UpdateItem/GetItem/Query and by the TransactWriteItems/TransactGetItems per-action validation; the prefix must be decided per AWS, not applied uniformly.
Traces: expression-attribute-keys-without-prefix-rejected-on-item-ops, expression-attribute-placeholders-without-an-expression-rejected, query-and-update-item-placeholders-without-an-expression-rejected, transact-items-accept-placeholders-without-an-expression, transact-unused-expression-attribute-name-on-condition-check-and-get-rejected, transact-write-items-duplicate-key-rejected, transact-write-items-unused-expression-attribute-value-on-second-action-rejected.
