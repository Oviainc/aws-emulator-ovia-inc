# lambda-core DeleteNetworkConnector is not idempotent once deletion completes, and the connector lifecycle only settles on a later read, so the name-reuse check never completes

> _Note: this issue was identified against the code base at commit `b76363ba3639c1fb1d2b9b08f3e303f98ad8a036`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteNetworkConnector

## Description
Two net-new root causes in the lambda-core network-connector delete/recreate path, grounded in the one failing behavioral check that is not already filed or owned: lambda-core.delete-releases-connector-name-for-reuse (reported verdict: mismatch, detail 'Check timed out after 60.0s'). Neither cause is covered by the two open lambda-core issues: 20261024T113459Z-lambda-core-network-connectors-clienttoken-reuse-never-refused.md carries six causes about ClientToken fingerprinting, the Name-vs-Id ARN, OperatorRole/SubnetIds validation and the PENDING conflict wording — none of them touches DeleteNetworkConnector idempotency or the lifecycle settle cadence; and 20261023T022015Z-lambda-core-admits-requests-aws-refuses-and-misclassifies.md is a WIRE issue about Create/Update/Get refusal classification only. DeleteNetworkConnector appears in no open issue at all.

--- Cause 1 of 2: DeleteNetworkConnector answers ResourceNotFoundException (404) for a connector whose deletion has already completed, instead of succeeding. ---
AWS: Smithy (com.amazonaws.lambdacore) DeleteNetworkConnector is marked `idempotent: true`, http DELETE /2026-04-04/network-connectors/{Identifier} with success code 202, and its own model documentation states the rule verbatim: "This operation is idempotent — calling delete on a connector that is already deleting or has been deleted succeeds without error." So for ANY identifier that named a connector this account deleted, the service answers 202 with the output envelope (Arn, Name, Id required; State typically DELETING) rather than the modeled ResourceNotFoundException (httpError 404), whose documented meaning is "The specified network connector does not exist. Verify the identifier (ID, name, or ARN) and Region." — i.e. an identifier that never named anything, not one whose deletion finished.
Emulator: services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/ops/delete_network_connector.rs resolves the identifier through crate::state::ComAmazonawsLambdacoreLambdacoreapiserviceState::settled_mut, which forgets the record the moment the pending Removal falls due (crate::state::NetworkConnector::settle returning true -> forget). When the record is gone, settled_mut answers None and the handler returns ResourceNotFoundException built by crate::state::connector_not_found, i.e. HTTP 404 with code ResourceNotFoundException and message "Network connector not found: <Identifier>" (fixed text "Network connector not found: " plus the Identifier copied from the request). The handler's own comment concedes the deviation, reasoning that Arn/Name/Id are @required answers a forgotten record cannot supply. Within the window before the removal falls due the same call succeeds, so the operation's answer for one logical state ("already deleted") depends only on how long the caller waited.
Why: a client retrying a delete after a network timeout, or a teardown helper that deletes unconditionally, gets a 404 where AWS gives 202. Idempotent-delete retry code written against AWS either raises or has to special-case 404 as success, and a cleanup path that treats 404 as a hard failure aborts. It also makes the answer time-dependent: the identical second DELETE is accepted while the record is still DELETING and refused a moment later, which no documented rule allows.
Fix: DeleteNetworkConnector's handler in delete_network_connector.rs, together with the record retention it depends on in src/state.rs. Deletion must leave behind enough of the connector (name, id, arn) for the idempotent answer to be served after the record is otherwise forgotten — a tombstone the identifier resolver can still answer from — so a repeat delete of an already-deleted connector returns 202 with State DELETING instead of falling through to connector_not_found. The not-found path must remain for an identifier that never named a connector in this account and Region.
Traces: lambda-core.delete-releases-connector-name-for-reuse (its `_delete_outcome` leg asserts that a repeat DeleteNetworkConnector is "accepted", and its `_best_effort_delete` cleanup is written around the same documented rule).

--- Cause 2 of 2: connector lifecycle transitions are never observable at the instant they are due; they are materialised only by a later call, after a fixed non-zero delay, so a client polling the documented way cannot observe them promptly and the full name-reuse path does not finish inside the suite's per-check budget. ---
AWS: GetNetworkConnector is documented as the way to "poll connector state after creation or update": PENDING ("Being created, resources provisioning") -> ACTIVE, and after a delete the connector goes DELETING and then "subsequent calls to GetNetworkConnector return ResourceNotFoundException". The service advances these states on its own, so each poll reports the state as of that instant and a connector that has finished provisioning reports ACTIVE on the very next poll. Recorded behavior only for timing: the model fixes no duration, and CreateNetworkConnector's documentation only says provisioning "typically takes up to 10 minutes". The requirement is that the state a poll reports is the state the resource has reached, with no transition that is due but withheld.
Emulator: crate::state::LIFECYCLE_TRANSITION (src/state.rs) is a fixed 500 ms applied to every transition — PENDING->ACTIVE in create_network_connector.rs, InProgress->Successful in update_network_connector.rs and DELETING->forgotten in delete_network_connector.rs — and the transition is stored as a PendingTransition that "nothing sleeps" on: it is materialised only when a subsequent call runs settled_mut/settle_all. So the state is deliberately withheld from the first read after each call, and the transition then becomes visible only on the following one. A client polling on the interval AWS's own latency makes sensible therefore burns a whole poll interval on every transition. In this check the consequence is terminal: the path creates a connector and waits for ACTIVE, deletes it and waits for it to stop answering Get, re-creates on the freed name and waits for ACTIVE again, then deletes and waits again — four withheld transitions, each costing one client poll — and the check never reaches its assertions, failing as "Check timed out after 60.0s". Hypothesis: that accumulated polling is what exhausts the budget; the report carries no traceback, so the exact stall point is not stated by the replay, and nothing else in the path loops — ListNetworkConnectors mints NextMarker only when a matching connector is left over (list_network_connectors.rs) and ec2 DescribeNetworkInterfaces mints NextToken only when another item follows, so neither pages forever.
Why: the single behavioral check covering the released-name contract — that a deleted connector frees its Name, that re-creating it mints a NEW Id, that Get by name rebinds to the new connector rather than a tombstone, and that the dead Id refuses Update with ResourceNotFoundException — never executes, so that whole contract is unverified against this emulator. More generally, a client that polls Get for a state change is told the old state at least once after the change was due, and the amount of wall-clock it loses is set by its own poll interval rather than by the service.
Fix: the lifecycle settle machinery in src/state.rs (LIFECYCLE_TRANSITION, PendingTransition, NetworkConnector::settle, settled_mut, settle_all) and the three handlers that schedule through it. A transition must be due such that the first Get after the call that started it already reports the reached state — the transient state is still observable, because the create/update/delete response itself carries it (PENDING, InProgress, DELETING) — rather than being withheld behind a fixed delay that each caller pays for at its own poll cadence.
Traces: lambda-core.delete-releases-connector-name-for-reuse.

Cause 1 evidence (code and model, since the check did not reach its assertion): Smithy DeleteNetworkConnector carries `idempotent: true`, http {method DELETE, uri /2026-04-04/network-connectors/{Identifier}, code 202}, output members Arn/Name/Id @required plus State, and models ResourceNotFoundException at httpError 404. Its model documentation states "This operation is idempotent — calling delete on a connector that is already deleting or has been deleted succeeds without error." delete_network_connector.rs lines 190-201 instead return ResourceNotFoundException via crate::state::connector_not_found whenever settled_mut yields None, which is exactly the already-deleted case, with the message "Network connector not found: <Identifier>" (src/state.rs NOT_FOUND_PREFIX). The accompanying comment states the choice explicitly. Expected for a repeat delete of a deleted connector: HTTP 202, no error code, Id/Name/Arn of the connector and State DELETING. Actual: HTTP 404, code ResourceNotFoundException, message "Network connector not found: " + the Identifier from the request.

Cause 2 evidence: src/state.rs LIFECYCLE_TRANSITION = Duration::from_millis(500), documented there as "deliberately NOT zero so a caller acting straight after the call still observes the transient state", with "the instant it falls due is stored on the record and materialised by whichever later call reads it — nothing sleeps". create_network_connector.rs schedules PendingChange::State(ACTIVE) at now + LIFECYCLE_TRANSITION; delete_network_connector.rs schedules PendingChange::Removal at now + LIFECYCLE_TRANSITION; NetworkConnector::settle applies them only when a later call passes `now >= due`. The transient state is already carried by the create/delete response itself (CreateNetworkConnectorOutput.state = PENDING; DeleteNetworkConnectorOutput.state = DELETING), so withholding it from the first subsequent Get adds nothing a caller can read and costs that caller one full poll interval per transition. The check waits on four such transitions.

## Steps to Reproduce
Run run_behavioral_suite and re-replay the check id in trace_ids (lambda-core.delete-releases-connector-name-for-reuse). Against a booted emulator in us-west-2:

Cause 1 — DeleteNetworkConnector idempotency after deletion completes:
1. Create a VPC, a subnet and a security group, and an IAM role whose trust policy names lambda.amazonaws.com.
2. POST /2026-04-04/network-connectors with Name=N, a VpcEgressConfiguration over that subnet and security group, and that role as OperatorRole. Note the returned Id.
3. Poll GET /2026-04-04/network-connectors/{Id} until State is ACTIVE.
4. DELETE /2026-04-04/network-connectors/{Id} — observe 202 with State DELETING (correct).
5. Poll GET /2026-04-04/network-connectors/{Id} until it answers 404 ResourceNotFoundException, i.e. the deletion has completed.
6. DELETE /2026-04-04/network-connectors/{Id} again. Expect HTTP 202 with the connector's Arn, Name and Id and State DELETING, because the operation is modeled @idempotent and documented to succeed "on a connector that is already deleting or has been deleted". Observe HTTP 404, code ResourceNotFoundException, message "Network connector not found: <Id>".
7. Repeat step 6 immediately after step 4 instead (before the removal falls due) and observe 202 — the same logical request is accepted or refused purely on elapsed time.

Cause 2 — withheld lifecycle transitions and the un-runnable name-reuse path:
1. POST /2026-04-04/network-connectors as above; the response carries State PENDING.
2. Immediately GET /2026-04-04/network-connectors/{Id}. Expect the connector to report the state it has reached, so a client polling once per interval observes ACTIVE on its next poll without waiting out that interval. Observe PENDING for the first 500 ms after the create, after which the transition is materialised only by whichever call reads the record next — so a client polling on a 15 s cadence sees PENDING on poll 1 and ACTIVE only on poll 2.
3. DELETE the connector and immediately GET it: the removal is likewise withheld for 500 ms and then materialised by a later read, costing another poll interval.
4.
