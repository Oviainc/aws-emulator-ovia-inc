# cloudformation__sns__sqs: 4 net-new root causes in the SNS-backed custom-resource protocol — GetAtt on provider Data resolves to nothing, ServiceToken ServiceTimeout bounds unenforced, the rollback Delete discards the provider's PhysicalResourceId, and follow-up provider requests are never published

> _Note: this issue was identified against the code base at commit `68ec0c9cae77cfbc133f0186a4c923306bef5402`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Four distinct root causes in the CloudFormation custom-resource (Custom::*) protocol when the provider named by `ServiceToken` is an SNS topic with a raw SQS subscriber. None of the five failing checks below is marked OWNED or ALREADY FILED in the replay report. Open issues cover neighbouring ground but not these: `20261103T061702Z-cloudformation-lambda-ssm-3-net-new-root-causes.md` (GetAtt wiring, Lambda-backed provider), `20261102T101202Z-cloudformation-dynamodb-lambda-3-net-new-root-causes.md` (custom-resource Provider timeout), `20261105T022225Z-cloudformation-lambda-sqs-2-net-new-causes-the.md` (PhysicalResourceId not adopted, Lambda-backed provider) and `20261105T040000Z-cloudformation-6-of-the-7-custom-resource-and-hook-keys-remain-open.md` (later provider requests never arrive — it lists one of the check ids below in its own Issue-Trace-Ids, but the replay report did not mark that check OWNED, so its replay key no longer matches and the check is unaccounted for).

=== Cause 1 of 4: Fn::GetAtt on a key the provider DID return resolves to nothing, and the consuming resource's property is dropped rather than carrying the value ===
AWS: recorded behavior only, against the documented custom-resource response protocol (CloudFormation User Guide, crpg-ref: a provider's response `Data` object supplies the resource's attributes, which `Fn::GetAtt ["<LogicalId>", "<Key>"]` resolves to). Smithy: CreateStack, DescribeStackEvents.ResourceStatus is an enum including CREATE_FAILED and ROLLBACK_COMPLETE (com.amazonaws.cloudformation#ResourceStatus), so the failure arm below is modellable. The provider answered SUCCESS with `Data: {"Present": "<value>"}`; the dependent resource's request must then carry `ResourceProperties` = {ServiceToken: <topic arn>, Value: <that value>}. For a key the Data lacks, the dependent resource is never invoked and CloudFormation fails it with the exact reason `CustomResource attribute error: Vendor response doesn't contain <Attribute> attribute in object <StackId>|<ProviderLogicalId>|<RequestId>` — fixed text `CustomResource attribute error: Vendor response doesn't contain `, ` attribute in object `, with the attribute name taken from the template's GetAtt and the stack id / logical id / provider RequestId taken from state — then rolls the stack to ROLLBACK_COMPLETE.
Emulator: the dependent resource's Create request arrives with the GetAtt-derived member missing altogether: `ResourceProperties` was `{'ServiceToken': 'arn:aws:sns:...:<topic>'}` where `{ServiceToken: ..., Value: <provider Data value>}` was required. So a GetAtt against a custom resource resolves to no value and the member is silently omitted instead of being substituted (and, for a missing key, instead of failing the consumer).
Why: a client whose provider returns data for its consumers (an endpoint, an id, a rendered string) gets that property deleted from the consumer's request, so the consumer is invoked with an incomplete document and provisions the wrong thing; a typo in a GetAtt key is never reported at all.
Fix: the custom-resource provisioner's attribute resolution — the stored response `Data` of a Custom::* resource must back `Fn::GetAtt` for the resource's intrinsic resolution, and an unknown key must fail the consuming resource with the attribute-error reason instead of dropping the member.
Traces: cloudformation__sns__sqs.custom-resource-getatt-missing-data-key-fails.

=== Cause 2 of 4: a Custom::* resource's ServiceTimeout outside 1–14400 is accepted and the stack completes ===
AWS: recorded behavior only, against the documented AWS::CloudFormation::CustomResource `ServiceTimeout` property (integer seconds, 1–14400). A value outside that range fails the resource BEFORE any request reaches the provider: the resource goes CREATE_FAILED with ResourceStatusReason exactly `ServiceTimeout must be an integer between 1 and 14400 seconds` (entirely fixed text — no request- or state-derived parts), the stack rolls back to ROLLBACK_COMPLETE, and no Create/Delete request for that stack is ever published to the provider. The boundary value 14400 is accepted and deploys.
Emulator: `ServiceTimeout: "0"` (and `"14401"`) deploys: the stack's terminal status was `CREATE_COMPLETE` where `ROLLBACK_COMPLETE` was required, with no CREATE_FAILED event and no such reason — the property is not validated at all.
Why: a client that mistypes or computes an out-of-range timeout gets a green stack whose custom resources have no enforceable timeout, and loses the early, pre-provider refusal AWS gives; the same template is rejected in real AWS.
Fix: template/property validation for Custom::*/AWS::CloudFormation::CustomResource in the custom-resource provisioner — bound ServiceTimeout before the provider request is built, and route the violation through the resource-failure/rollback path that records ResourceStatusReason.
Traces: cloudformation__sns__sqs.custom-resource-service-timeout-out-of-range-fails-the-resource.

=== Cause 3 of 4: the rollback Delete after a provider's FAILED response targets an emulator-minted id instead of the PhysicalResourceId the provider returned ===
AWS: recorded behavior only (crpg-ref response protocol). The provider's response document carries `PhysicalResourceId`; CloudFormation adopts that exact string whatever the Status, so the rollback's Delete request for a resource whose Create answered FAILED carries the id the provider named, and the CREATE_FAILED event reports the same id.
Emulator: the rollback Delete request carried a CloudFormation-generated id of the form `<StackName>-<LogicalId>-<SUFFIX>` where the provider's own id was required — the `PhysicalResourceId` of a FAILED response is discarded. (The two ids in the recorded message are per-run values; the requirement is that the Delete echoes whatever the response body named.)
Why: a provider that created something before failing is asked to delete an id it has never heard of, so the rollback cannot clean up — the half-created external resource leaks, and the CREATE_FAILED event cannot be correlated with what was made.
Fix: the custom-resource response handling/state — store the `PhysicalResourceId` from the response body for FAILED as well as SUCCESS, and have the rollback Delete request and the resource's events read it back. Note the same adoption defect is filed for the Lambda-backed provider in `20261105T022225Z-cloudformation-lambda-sqs-2-net-new-causes-the.md` cause 1; this is the SNS-backed FAILED/rollback path.
Traces: cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-failed-response-rolls-back-with-its-reason.

=== Cause 4 of 4: a provider request that a LATER phase of the same stack operation owes is never published, so the client waits for it forever ===
AWS: recorded behavior only (crpg-ref). Once a provider's response lands at the ResponseURL, CloudFormation itself drives the next request the operation owes, with no further client call: an answered Update that returns a NEW PhysicalResourceId is a replacement, so CloudFormation sends a cleanup Delete for the OLD id carrying the OLD ResourceProperties while the stack reports UPDATE_COMPLETE_CLEANUP_IN_PROGRESS (Smithy: com.amazonaws.cloudformation#StackStatus includes UPDATE_COMPLETE_CLEANUP_IN_PROGRESS) and only then UPDATE_COMPLETE; a response CloudFormation cannot read a PhysicalResourceId from (a body over 4,096 bytes, which fails the resource with reason exactly `Response object is too long.`) is still followed by a Delete for that resource under a CloudFormation-assigned id, before the rollback deletes anything the resource depended on.
Emulator: both checks answer one request and then wait on the provider's queue without making another CloudFormation call, and the follow-up request never arrives — each ran out its window (`Check timed out after 60.0s`). Hypothesis: the follow-up request is only built while a CloudFormation API call is being served (the emulator's own note in `state::provisioning::advance_stabilisations`), so nothing publishes it between calls; for the oversized-response arm the alternative is that the 4,096-byte limit is not enforced at all, so no failure and hence no Delete is ever owed. Because both checks blocked here, the downstream requirements they also assert are unverified by this replay: the `Response object is too long.` reason, the CloudFormation-assigned id on that Delete, the Overflows-before-Fits delete ordering, and the replacement's UPDATE_COMPLETE_CLEANUP_IN_PROGRESS window and post-replacement Outputs.
Why: a client that answers a custom-resource request and then waits for the next one — the normal provider loop, and the only way a replacement's old resource is cleaned up — hangs indefinitely; stale resources are never deleted and oversized provider responses are never reported.
Fix: the custom-resource plane plus the provisioning driver — the work a landed response owes (replacement cleanup Delete, failure-path Delete, response-size check) must be driven by the emulator itself rather than by the next client CloudFormation call. The open issue `20261105T040000Z-cloudformation-6-of-the-7-custom-resource-and-hook-keys-remain-open.md` describes this same seam and names one of these two check ids in its Issue-Trace-Ids, but the replay report did not mark either check OWNED, so they are re-grounded here.

Cause 4 — cloudformation__sns__sqs.custom-resource-response-over-4096-bytes-fails and cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-new-physical-id-on-update-triggers-cleanup-delete-of-old, both [mismatch] with "Check timed out after 60.0s":
  expected: after the oversized SUCCESS response is PUT, a Delete request for Overflows arrives (CloudFormation-assigned id, before any Delete for Fits), and after an Update answered with a new PhysicalResourceId, a cleanup Delete for the OLD id carrying the OLD ResourceProperties arrives while DescribeStacks reports UPDATE_COMPLETE_CLEANUP_IN_PROGRESS.
  actual: no further provider request is ever delivered to the subscribed queue; each check consumed its whole window waiting on SQS after answering the previous request, making no intervening CloudFormation call.

## Steps to Reproduce
Common setup for every cause: create an SNS topic, create an SQS queue, set a queue policy allowing sns.amazonaws.com sqs:SendMessage from that topic, and subscribe the queue with RawMessageDelivery=true. The topic ARN is the custom resources' ServiceToken; each custom-resource request arrives as a queue message and is answered by PUTting a response document at the request's ResponseURL.

Cause 1: CreateStack with Resources {Provider: Custom::Source {ServiceToken: <topic>}, Consumer: Custom::Sink {ServiceToken: <topic>, Value: {"Fn::GetAtt": ["Provider", "Present"]}}}. Answer the Provider Create with Status SUCCESS, a PhysicalResourceId and Data {"Present": "<value>"}. Read the Consumer Create request off the queue: its ResourceProperties lack the Value member. Repeat with {"Fn::GetAtt": ["Provider", "Missing"]} and poll DescribeStacks/DescribeStackEvents — no CREATE_FAILED attribute error is recorded.

Cause 2: CreateStack three stacks whose single resource is Custom::Bounded {ServiceToken: <topic>, ServiceTimeout: "14400" | "0" | "14401"}. Answer the 14400 stack's Create and poll it to CREATE_COMPLETE. Poll the "0" and "14401" stacks: both reach CREATE_COMPLETE instead of ROLLBACK_COMPLETE, and DescribeStackEvents shows no CREATE_FAILED with "ServiceTimeout must be an integer between 1 and 14400 seconds".

Cause 3: CreateStack with one Custom::Verdict resource. Answer its Create with Status FAILED, a Reason, and a PhysicalResourceId of your own choosing; then poll DescribeStacks (which is what drives the rollback) and read the Delete request off the queue — its PhysicalResourceId is <StackName>-<LogicalId>-<generated>, not the id you returned.

Cause 4a: CreateStack with Fits and Overflows (Overflows DependsOn Fits), both Custom::Sized. Answer Fits with a response body of exactly 4096 bytes and poll until Fits is CREATE_COMPLETE. Answer Overflows with a body of 4097 bytes, then poll only the queue: no Delete for Overflows ever arrives.
Cause 4b: CreateStack one Custom::Versioned resource, answer Create with PhysicalResourceId pid1 and Data {"Version": "1"}, poll to CREATE_COMPLETE. UpdateStack with a changed property, answer the Update with a DIFFERENT PhysicalResourceId pid2, then poll only the queue: the cleanup Delete for pid1 with the old properties never arrives.
