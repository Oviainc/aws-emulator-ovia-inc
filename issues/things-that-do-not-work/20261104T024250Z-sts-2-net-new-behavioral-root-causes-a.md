=== Cause 1 of 2: AssumeRoleWithWebIdentity never accepts a genuine, untampered Amazon Cognito user-pool ID token, so the whole web-identity federation path is unreachable ===
AWS: Smithy (com.amazonaws.sts#AssumeRoleWithWebIdentity) — input WebIdentityToken (clientTokenType, @required, @length 4..20000, @sensitive), RoleArn and RoleSessionName @required; output Credentials, AssumedRoleUser, SubjectFromWebIdentityToken, Provider, Audience; errors InvalidIdentityTokenException (httpError 400, awsQueryError InvalidIdentityToken), ExpiredTokenException (400), IDPRejectedClaimException (403), the operation is anonymous (auth: [], optionalAuth). AWS behavior: an OpenID Connect ID token issued by a Cognito user pool, presented for a role whose trust policy Allows the Federated principal (the account's IAM OIDC provider for that issuer) the action sts:AssumeRoleWithWebIdentity under a StringEquals condition on <issuer-host-and-path>:aud equal to the token's audience, is EXCHANGED: HTTP 200 with Credentials and AssumedRoleUser.Arn of the form arn:aws:sts::<account>:assumed-role/<RoleName>/<RoleSessionName>. Only after that control succeeds does the negative leg apply: the same token with one signature byte flipped is refused with error code InvalidIdentityToken and the message "The web identity token provided could not be validated. See the AssumeRoleWithWebIdentity documentation for requirements." — that message is entirely FIXED text with no variable parts (the crate already carries it verbatim as UNVALIDATED_TOKEN_MESSAGE in services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state/web_identity.rs).
Emulator: the exchange of the genuine token never succeeds. The check establishes its positive control by retrying AssumeRoleWithWebIdentity with the untampered IdToken that cognito-idp AdminInitiateAuth returned (retrying only on ClientError, for a 90 s budget), and every attempt is refused, so the check exhausts the harness's 60 s cap with "Check timed out after 60.0s" and never reaches the tampered-token leg at all. No divergent body is captured because no accepting response is ever produced. Hypothesis (the recording does not state which refusal class is served): the token's iss claim as the hosted user pool writes it, or the audience/subject the role trust policy is matched against, does not line up with the issuer the account registered through iam:CreateOpenIDConnectProvider, so verification or trust-policy evaluation in crate::state::web_identity resolves UnregisteredIssuer / KeyUnretrievable / AccessDenied instead of verifying the signature against the in-process key set its own module documentation says it publishes.
Why: a client cannot federate a web identity against this emulator at all. Every mobile/web/OIDC login flow — exchange a Cognito ID token for role credentials, then call AWS with them — fails, and because the accept path never runs, the negative classes layered on top of it (expired token, tampered signature, wrong audience, IDPRejectedClaim) are untestable too: an application validated here would be exercising none of its federation code.
Fix: the token-verification and trust-evaluation path of AssumeRoleWithWebIdentity — services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state/web_identity.rs (issuer resolution against the account's registered OIDC providers, and signature verification against the key set the hosted Cognito user pool publishes in-process) together with the handler services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/assume_role_with_web_identity.rs (audience/subject matching of the role's trust policy). A genuine pool-issued ID token for a registered issuer must verify and exchange on the FIRST attempt — there is no propagation delay to wait out in an emulator.

=== Cause 2 of 2: PackedPolicyTooLarge reports the size of the emulator's own JSON-then-base64 token, not AWS's packed binary size, so the reported byte figure and the accept/refuse threshold both diverge ===
AWS: Smithy — AssumeRole error PackedPolicyTooLargeException (errorKind client, httpError 400, awsQueryError {code: PackedPolicyTooLarge, httpResponseCode: 400}); its documentation: "An Amazon Web Services conversion compresses the session policy document, session policy ARNs, and session tags into a packed binary format that has a separate limit". Input Tags is tagListType @length 0..50, keys up to 128 and values up to 256 plaintext characters. The model does not state the message, so recorded behavior: AWS refuses with error code PackedPolicyTooLarge, HTTP 400, and the message "Serialized token too large for session. Token size of <n> bytes exceeds the maximum allowed limit of 4096 bytes." The fixed text is "Serialized token too large for session. Token size of " / " bytes exceeds the maximum allowed limit of " / " bytes."; the two variable parts are <n>, the size AWS's packed binary format measures for THIS request's session state, and the limit, 4096. For the check's deterministic tag set (50 tags, each key "T<nnn>" + 120 'k' = 124 characters, each value 256 'v' characters, no inline policy, no policy ARNs) AWS measures <n> = 26092 bytes — a value fixed by the request, not a per-run one.
Emulator: the code and status are right, but the measured size is 26816 bytes for that same request. That figure is exactly the length of base64(JSON) of the emulator's own packing: crate::state::packed_session_token (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs) serializes {"Tags":[{"Key":...,"Value":...},...]} as serde_json (401 bytes per tag + separators = 20110 bytes) and the encoded form is 4/3 of that, 26816; packed_policy_bytes returns that length and packed_policy_too_large_message interpolates it. So the emulator over-measures AWS's packed size by ~2.8% here.
Why: two things break for a client. (1) The refusal message is wrong in its variable part: a caller that trims session tags using the reported figure (and callers do: the message exists so they can compute how much to remove) computes against a size AWS never reports. (2) More seriously, the same mis-measurement is the accept/refuse threshold and the PackedPolicySize percentage: because the emulator's packing expands differently from AWS's, session-tag/policy sets near the 4096-byte budget are classified differently — a request AWS accepts (and reports as, say, 97%) can be refused PackedPolicyTooLarge here, and the reported PackedPolicySize percentage of an accepted mint diverges from AWS's for the same request.
Fix: the packing measurement in services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs — packed_session_token / packed_policy_bytes (and therefore packed_policy_size and packed_policy_too_large_message, consumed by ops/assume_role.rs and the other minting handlers). The measured size must reproduce AWS's packed binary size for a given inline policy, policy ARN list and session tag set — notably not inflated by a base64 4/3 expansion over a JSON document with per-member framing — so that both the reported <n> and the 4096-byte threshold agree with AWS.
