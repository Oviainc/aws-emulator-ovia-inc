# API Gateway log delivery, the REST `AWS` DynamoDB integration and the DynamoDB-Streams event source mapping: 4 of the 9 causes remain open

> _Split out of `issues/things-that-now-work/20261029T180026Z-apigateway-dynamodb-lambda-logs-api-gateway-deployed-stage-invoke-account-logging-role.md`, whose causes 1–5 are fixed (the deployed `execute-api` invoke URL is routed and served, the `AWS_PROXY` Lambda proxy integration is performed on both sides of the data plane, `UpdateAccount` validates the account's CloudWatch role against IAM, a well-formed role ARN is accepted, and the access-log-format refusal names both request identifiers). This report carries the replay keys that do NOT pass, re-filed here so they are not recorded as working. Everything below is what that fix established about them; a later fixer starts from here rather than from scratch._

## Operation
TestInvokeMethod

## Description
Four of the parent report's nine causes are untouched. Each is a different missing capability, in a different place, and none is a per-run value or a non-defect — so none is declined.

What the parent fix DID land, so a later fixer does not redo it:
* the `execute-api` data plane of the REST service recognises and serves a deployed stage's invoke URL in full (`services/service-com-amazonaws-apigateway-backplanecontrolservice/src/service/invoke.rs`), so an end-to-end HTTPS request to a stage now gets a computed answer rather than a front-door `404`;
* an `AWS_PROXY` integration is PERFORMED — the function its `uri` names is invoked over the in-process transport and its proxy response is passed on unmapped, gated on the function's own resource policy (`src/service/invoke/lambda_proxy.rs`). AWS Lambda really runs a deployment package in this process, so there is a real answer to pass on;
* `performed_integration` in `src/service/invoke.rs` is the ONE seam both the data plane and `TestInvokeMethod` reach, so a new integration type is served by adding one module behind it rather than by touching either caller;
* a proxy integration whose backend answered no proxy response is answered `502` by the module itself (`lambda_proxy`), which builds that response rather than going through a `GatewayResponseType` — no modelled type documents a 502;
* `UpdateAccount` resolves a `cloudwatchRoleArn` against IAM through `service_common::iam_role::role_is_unassumable`, so the account-level logging role is now configurable AND validated — which is the precondition the execution-log half of cause 1 below needs.

Cause 1 of 4 (cause 6 of the parent): access logs and execution logs are never delivered to CloudWatch Logs, so the checks never finish. UNTOUCHED.
AWS: a stage with `accessLogSettings` writes one log event per request to the destination log group named by `destinationArn`, rendered through the stage's `format`; a stage whose method settings enable `loggingLevel` publishes EXECUTION logs to the group API Gateway creates for it (`API-Gateway-Execution-Logs_{api-id}/{stage}`), which it can only do once the account carries a usable `cloudwatchRoleArn`.
Emulator: nothing is ever written. `StageEntry::access_log_settings` is stored and reported by `GetStage`/`UpdateStage` and read by nothing else — `grep access_log` over `services/service-com-amazonaws-apigateway-backplanecontrolservice/src` finds no reader outside the control plane — so every check polling the destination runs to its 60s budget (`Check timed out after 60.0s`), and the negative cases (a wrong destination ARN, a missing log-group resource policy, a missing destination) cannot be told from a hang.
Fix: an access-log and execution-log emitter on the data plane's one serving funnel (`serve_resolved` in `src/service/invoke.rs`), writing through CloudWatch Logs' own `PutLogEvents` over the in-process transport (`aws-sdk-cloudwatchlogs` is already in `Cargo.lock`) rather than into that service's store by hand — `PutLogEvents` owns the `storedBytes` accounting, the event ordering, the storage ceiling and the subscription fan-out. It also needs the `$context` members an access log format renders that `call_context` does not yet carry: `status`, `responseLength`, `requestId`, `requestTime`/`requestTimeEpoch`, `protocol` and `identity.sourceIp`. Note the ORDER constraint: the line is about the response, so the emission happens after the integration answered, and the stage's own `format` decides the text.

Cause 2 of 4 (cause 7 of the parent): the REST `AWS` (non-proxy) DynamoDB integration never answers. UNTOUCHED.
AWS: a method with an `AWS` integration whose `uri` names a DynamoDB action (`arn:aws:apigateway:{region}:dynamodb:action/{Action}`) answers with the mapped DynamoDB reply — the integration request template is the operation's input document and the integration response's template maps the answer — and 403/500 for the missing-role and wrong-table-ARN negatives.
Emulator: `src/service/invoke/aws_integration.rs` serves AMAZON S3 ONLY. Its own header states that scope, and its `uri` reading accepts only the `s3` subdomain in the `path/{bucket}/{key}` and `action/{GetObject|PutObject|HeadObject|DeleteObject}` forms; every other subdomain falls through to `perform_integration`'s refusal, so these checks get no answer at all.
Fix: generalise that module from "the Amazon S3 object actions" to the rule `Integration$uri` states — an `AWS` integration names ANOTHER SERVICE'S ACTION, and where that service's protocol carries its request as ONE JSON document the call is made by signing that document under the action named in `X-Amz-Target`. `services/service-com-amazonaws-lambda-awsgirapiservice/src/state/execution/aws_api.rs` already holds exactly that reading (its `APIS` table carries DynamoDB's own wire facts and `service_common::in_process_sigv4` signs it), so the work is to reach it from here rather than to write a second one; the execution role (`Integration$credentials`) is already resolved by this module's `authorization`, so the missing-role negative follows from the generalisation. Do NOT add a per-action table: a case keyed to `PutItem`/`GetItem`/`Query`/`BatchWriteItem` would be fitted to these six checks.

Cause 3 of 4 (cause 8 of the parent): DynamoDB-Streams event source mappings never deliver, so the ESM checks hang. UNTOUCHED.
AWS: an enabled event source mapping on a DynamoDB stream polls that stream's shards and invokes the function with the batch it read, honouring `BatchSize`, the on-failure destination and tumbling windows.
Emulator: `services/service-com-amazonaws-lambda-awsgirapiservice/src/state/event_source_poller.rs` claims a mapping only when its `event_source_arn` names a KINESIS data stream (its `reads_kinesis` gate), so a mapping on a DynamoDB stream is never claimed and nothing is ever read or delivered; `src/state/sqs_poller.rs` is the queue half and does not apply either. Writes to the table are accepted and nothing downstream runs.
Fix: a DynamoDB-stream poller beside the Kinesis one, reading through the `dynamodbstreams` surface of this same emulator (`DescribeStream`, `GetShardIterator`, `GetRecords`) and invoking the function through its own `Invoke`. `services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs` already builds the DynamoDB stream RECORD ENVELOPE a consumer expects (`stream_record_envelope`, `attribute_json`) and already holds the `aws-sdk-dynamodbstreams` client; `crate::state::event_source_authorization` already states what reading such a stream takes of the function's execution role, including the DynamoDB stream ARN. `crate::state::batch_item_failures` already holds the partial-batch checkpointing.

Cause 4 of 4 (cause 9 of the parent): the IAM trust-policy negatives on the invoke roles hang. PARTLY ESTABLISHED.
AWS: creating or using a role whose trust policy names the wrong service principal is refused promptly.
Emulator, and what the parent fix changed: the APIGATEWAY half is closed — `UpdateAccount` now refuses a `cloudwatchRoleArn` whose trust policy does not let `apigateway.amazonaws.com` assume it (`src/ops/update_account.rs`), which is what `.iam-role-missing-apigateway-trust-negative` drove, and `.iam-role-wrong-trust-principal-apigateway-negative` now gets a prompt answer from the proxy integration instead of none. The two LAMBDA-side rows are still open and their keys are `_retry_negative_create#10` and `_retry_negative_update#14` — the harness retrying its own `CreateRole`/`UpdateAssumeRolePolicy` negative, which means what blocks them is upstream of the trust evaluation rather than in it. A fixer should establish WHICH call that retry loop is waiting on before touching any trust reading: these two units are also not servable by the behavioral suite today (`replay_issue_units` reports them "not listed"), so the parent issue could never be replayed and there is no divergence recorded for them.
