# CloudWatch: 7 net-new root causes — AssociateDatasetKmsKey validates no KMS key at all, GetDataset's cross-account AccessDenied text, composite alarms still never evaluate, StorageResolution read identity, and three refusal-text/code divergences

> _Note: this issue was identified against the code base at commit `be77232b1086b1a9cf38f8c20a09a045e40c3e43`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateDatasetKmsKey

## Description
This issue bundles 7 independent net-new root causes in the CloudWatch dataset/KMS control plane, the composite-alarm evaluator, the metric read path and three refusal renderings. Every cause is independent; all 7 must be closed before submitting.

NOTE on prior work: the resolved issue 20261029T182452Z-cloudwatch-metric-alarm-data-plane-9-net-new.md carried cloudwatch.composite-alarm-*, cloudwatch.metric-data-high-resolution-period, cloudwatch.values-counts-histogram-query-aggregation, cloudwatch.metric-stream-start-stop-timing, cloudwatch.get-dataset-nonexistent-not-found and cloudwatch.get-dataset-not-found-for-unknown-dataset. Those checks still fail. Causes 2, 5 and 6 below are now a DIFFERENT divergence from the one that issue described (the error class is right and only the message text/code remains wrong), and Causes 3 and 4 are unchanged behaviour. The open issue 20261028T043126Z-cloudwatch-enum-constraint-validationerror-messages-are-rendered-from.md describes enum-constraint messages rendered in Smithy declaration order; Cause 7 is a different rendering (alphabetical) on a member that issue does not name.

Cause 1 of 7: AssociateDatasetKmsKey performs no KMS validation whatsoever — every syntactically valid KmsKeyArn is accepted with 200.
AWS: Smithy: AssociateDatasetKmsKey takes DatasetIdentifier (@required, @length 1-2048, @pattern ^(default|arn:...:cloudwatch:...:\d{12}:dataset/default)$) and KmsKeyArn (@required, @length 20-2048, @pattern ^arn:...:kms:...:\d{12}:key/[a-f0-9-]+$), and models the errors ConflictException (409), KmsAccessDeniedException (400), KmsKeyDisabledException (400), KmsKeyNotFoundException (400) and ResourceNotFoundException (404). KmsAccessDeniedException is documented as "The operation was denied because either the calling principal lacks the required ... KMS permission on the key, or the key policy does not grant Amazon CloudWatch the permissions it needs to use the key. Verify that the caller has kms:Decrypt permission on the key, and that the key policy grants the CloudWatch service principal the kms:DescribeKey, kms:GenerateDataKey, kms:Encrypt, kms:Decrypt, and kms:ReEncrypt* permissions"; KmsKeyDisabledException as "The specified ... KMS key is disabled or pending deletion"; KmsKeyNotFoundException as "The specified ... KMS key could not be found". Per the recordings the service runs a dry-run against the key before completing the association and surfaces every failure mode as a generic 400 AccessDenied (it deliberately does not distinguish "key does not exist" from "key cannot be used"), except for an ARN whose account segment names an unreachable account, which is a 400 ValidationError whose message begins "KMS key account ". In every refused case the dataset's existing association is left untouched, and the identical call succeeds once the key is usable (the positive control each check runs).
Emulator: every one of these calls returns HTTP 200 with an empty JSON body ({} , content-length 2) and no error at all: a nonexistent key ARN, a key in a foreign/nonexistent account, a disabled key, a key whose policy grants the CloudWatch service principal nothing, a key that explicitly denies the calling principal kms:Decrypt, and an under-permissioned key presented as a re-association over a working one. Checks that read back the association after the (unrefused) call therefore also observe the dataset silently repointed at a key it cannot use.
Why: a client gets a dataset whose encryption is pointed at a key CloudWatch cannot use, with no error to react to — the failure surfaces later as unreadable data instead of at configuration time, and every negative authorization boundary around customer-managed keys is absent, so a caller with no kms:Decrypt can bind any key ARN it can spell.
Fix: the AssociateDatasetKmsKey handler's validation — it must resolve the KmsKeyArn (account reachability, key existence, key enabled state, caller kms:Decrypt, and the CloudWatch service principal's key-policy grants) before mutating dataset state, and map each failure to the modeled error class with AWS's message for that class; a refused call must leave the stored association unchanged.
Traces: cloudwatch.associate-dataset-kms-key-access-denied, cloudwatch.associate-dataset-kms-key-access-denied-rejected, cloudwatch.associate-dataset-kms-key-caller-missing-permission-rejected, cloudwatch.associate-dataset-kms-key-cross-account-key-denied, cloudwatch.associate-dataset-kms-key-disabled-key-rejected, cloudwatch.associate-dataset-kms-key-missing-permission-denied, cloudwatch.associate-dataset-kms-key-nonexistent-key-rejected, cloudwatch.associate-dataset-kms-key-reassociation-conflict-rejected, cloudwatch.dataset-kms-key-disabled-key-rejected, cloudwatch.duplicate-kms-association-rejected, cloudwatch.kms-key-access-errors.

Cause 2 of 7: GetDataset's cross-account refusal carries a generic IAM-authorization message instead of CloudWatch's dataset text.
AWS: Smithy: GetDataset's DatasetIdentifier is @required with @pattern ^(default|arn:[a-zA-Z0-9-]+:cloudwatch:[a-zA-Z0-9-]*:\d{12}:dataset/default)$, so the only way to name a dataset outside the caller's account is a well-formed ARN whose account segment is another account. Recorded behavior: that request is refused with error code AccessDenied (the authorization decision is made before any existence determination, so existence is never confirmed or denied) and the message is the fixed sentence "Caller account <X> is not authorized to access resource in account <Y>" — fixed text "Caller account ", " is not authorized to access resource in account "; the variable parts are X = the calling identity's own account id and Y = the account segment of the DatasetIdentifier ARN in the request. GetDataset("default") for the caller's own account resolves normally.
Emulator: the error code is now AccessDenied (correct), but the message is an IAM policy-evaluation template: "User: <caller arn> is not authorized to perform: cloudwatch:GetDataset on resource: <dataset arn> because no resource-based policy allows the cloudwatch:GetDataset action".
Why: a client matching on CloudWatch's wording for this refusal does not recognise it, and the message leaks a policy-evaluation rationale CloudWatch does not state for datasets.
Fix: the GetDataset handler's cross-account authorization refusal message (it must use the service's own fixed sentence with the caller account and the requested ARN's account substituted, not the generic IAM not-authorized template).
Traces: cloudwatch.get-dataset-nonexistent-not-found, cloudwatch.get-dataset-not-found-for-unknown-dataset.

Cause 3 of 7: composite alarms are still never evaluated server-side from their AlarmRule, and ActionsSuppressedBy is never reported.
AWS: recorded behavior only (PutCompositeAlarm models AlarmRule, ActionsSuppressor, ActionsSuppressorWaitPeriod and ActionsSuppressorExtensionPeriod as plain members; no trait expresses the evaluation). A composite alarm's StateValue is derived continuously server-side from its children's current states per its AlarmRule, with no SetAlarmState on the composite itself: two OK children under an OR/AND rule put the composite in OK (not INSUFFICIENT_DATA); an AND rule stays out of ALARM until every referenced child is in ALARM and then transitions; a client-forced SetAlarmState on the composite does not durably stick (the next child state change re-derives it). With an ActionsSuppressor in ALARM the composite reports ActionsSuppressedBy == "Alarm" while itself ALARM; once the suppressor leaves ALARM the composite reports ActionsSuppressedBy == "ExtensionPeriod" for the configured ActionsSuppressorExtensionPeriod and then stops reporting ActionsSuppressedBy at all.
Emulator: a freshly created composite over two OK children reads StateValue INSUFFICIENT_DATA and never leaves it; the AND-rule, boolean-AND and suppressor checks poll DescribeAlarms(AlarmTypes=["CompositeAlarm"]) and observe no state transition and no ActionsSuppressedBy value at all, exhausting the 60 s check budget.
Why: composite alarms — the standard way to de-noise paging — never change state, so neither their notifications nor their suppression windows can ever fire or be observed.
Fix: the composite-alarm evaluator in the alarm state engine: evaluate AlarmRule against the children's current states on every child transition and on creation, and implement the ActionsSuppressor gate (Alarm / ExtensionPeriod / cleared) reported through DescribeAlarms' ActionsSuppressedBy.
Traces: cloudwatch.composite-alarm-server-side-evaluation, cloudwatch.composite-alarm-and-rule-requires-all-children, cloudwatch.composite-alarm-boolean-and-logic, cloudwatch.composite-alarm-actions-suppressed-by-alarm.

Cause 4 of 7: StorageResolution is not part of a datapoint's read identity — a standard-resolution datum answers a sub-minute query.
AWS: Smithy: MetricDatum$StorageResolution is documented "Valid values are 1 and 60. Setting this to 1 specifies this metric as a high-resolution metric, so that CloudWatch stores the metric with sub-minute resolution". Recorded behavior: a datum published WITHOUT StorageResolution is stored at standard (60 s) resolution and a GetMetricStatistics query at Period=1 over it returns NO datapoints, while its high-resolution twin (StorageResolution=1), published at the same instant in the same namespace and queried identically, does return the sub-minute datapoint.
Emulator: the standard-resolution datum also answers the Period=1 query, returning a datapoint (Sum 42.0, Unit Count) where the result must be empty — the storage class is not part of the key the read path consults.
Why: a dashboard or alarm built on a sub-minute period silently fabricates sub-minute resolution for metrics that were never published at it, so a Period=1 panel shows data AWS would not serve and a high-resolution alarm evaluates on data it should not see.
Fix: the metric store's datapoint key and the GetMetricStatistics/GetMetricData aggregation path must include the storage resolution and must not serve a standard-resolution datum to a sub-minute period query.
Traces: cloudwatch.metric-data-high-resolution-period.

Fix: PutMetricData's Values/Counts validation message template in the operation's validation path.

Fix: the StartMetricStreams/StopMetricStreams input validation and its ValidationError message template (list-level path, bracketed list value, nested both-bounds constraint clause) plus the error-code mapping for constraint violations on these operations.
Traces: cloudwatch.metric-stream-start-stop-timing.
