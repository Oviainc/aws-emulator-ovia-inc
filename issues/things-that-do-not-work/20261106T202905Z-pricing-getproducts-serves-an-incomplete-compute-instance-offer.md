# pricing GetProducts serves an incomplete Compute Instance offer document: product.attributes omits most published EC2 attributes, the Reserved usage dimension description is reworded, and the publication metadata is frozen at a seed constant

> _Note: this issue was identified against the code base at commit `14b50dd5b1a37831270f0fabc7b7cd82f4b7ecdf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetProducts

## Description
Three net-new WIRE root causes in the Price List Query API's GetProducts read path, both clusters replayed HTTP 200 -> 200 (the service answers; this is a fidelity defect, not a bootstrap gap) and both diverge on the SAME jsonpath, $.PriceList[0] — the `aws_v1` product-offer document the emulator serves for an EC2 Compute Instance product. Neither cluster is marked `owned_by` any open issue and neither is blocked by a stub.

Cause 1 of 3: the Compute Instance offer document's `product.attributes` block omits most of the attributes AWS publishes for an EC2 instance product.
AWS: recorded behavior only for the attribute inventory (the Smithy model — com.amazonaws.pricing#AWSPriceListService, awsJson1_1 — types GetProducts output `PriceList` as PriceListJsonItems, a list of opaque JSON strings, and documents it only as "The list of products that match your filters. The list contains both the product metadata and the price information"; it constrains nothing inside the document). The recorded offer document for an on-demand Compute Instance carries, besides the attributes the emulator already has (capacitystatus, currentGeneration, instanceFamily, instanceType, licenseModel, location, locationType, memory, normalizationSizeFactor, operatingSystem, operation, physicalProcessor, preInstalledSw, regionCode, servicecode, servicename, tenancy, usagetype, vcpu), these further attributes, which the service derives from the instance type / platform: storage, networkPerformance, clockSpeed, ecu, processorArchitecture, processorFeatures, instanceFamilyCategory, dedicatedEbsThroughput, dedicatedEbsThroughputDescription, enhancedNetworkingSupported, intelAvxAvailable, intelAvx2Available, intelTurboAvailable, classicnetworkingsupport, vpcnetworkingsupport, gpuMemory, marketoption and availabilityzone. It is the PRESENCE of these attributes per instance type/platform that is the requirement, not any one recording's values (and `sku` is an opaque per-environment id, so its value is explicitly not part of this finding).
Emulator: the document it serves carries only the 19-attribute subset above, so every one of the ~18 attributes named is absent from the product block. Source: the EC2 compute draft in the pricing crate's state builds `attributes(...)` from exactly those 19 pairs (services/service-com-amazonaws-pricing-awspricelistservice/src/state.rs, ec2_products(), lines 1718-1747) and the document is rendered verbatim from that map (offer_document(), line 881; product_from_draft(), line 851).
Why: a cost or right-sizing client parses the offer document and reads these attributes — it keys on `marketoption`/`availabilityzone` to tell an on-demand offer from a spot/AZ-scoped one, on `networkPerformance`/`storage`/`clockSpeed`/`ecu` to compare shapes, and on `processorFeatures`/`intel*Available` to decide instruction-set fitness. Against the emulator each of those lookups is a missing key, so the client either KeyErrors on a product AWS prices fully or silently treats the capability as absent. The same attributes are also legitimate GetProducts filter Fields, so a filtered query on one of them matches nothing.
Fix: the EC2 compute product seed in the pricing crate's state (the attribute map built for each Compute Instance draft, plus whatever per-instance-type seed data the new attributes need), so the published document carries the attribute set AWS publishes for each (instanceType, operatingSystem, region).
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4 (plus pricing-ecc-traj-get-products-request-mistakes#task#7 and pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#1 / #task#4 in the same cluster); pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#3.

Cause 2 of 3: the Reserved term's usage price-dimension `description` is reworded with a rate prefix AWS does not put there.
AWS: recorded behavior only (the model says nothing about term text). In the recorded document a reserved compute term's usage dimension description is exactly the platform-and-type sentence: "<reserved platform>, <instanceType> reserved instance applied" — fixed text ", " and " reserved instance applied", with the platform (Linux written as "Linux/UNIX (Amazon VPC)") and the instance type taken from the product. The rate is carried in `pricePerUnit`, not restated in the description. The sibling OnDemand dimension DOES carry the rate ("$<rate> per On Demand <os> <instanceType> Instance Hour"), and the upfront fee dimension's description is "Upfront Fee" with unit "Quantity" — both of which the emulator already words correctly.
Emulator: it prefixes the reserved usage description with the rate, emitting "USD <rate> per <reserved platform>, <instanceType> reserved instance applied". Source: reserved_description() in src/state.rs lines 982-991 (`format!("USD {rate} per {}, {instance_type} reserved instance applied", ...)`), rendered into every Reserved term by reserved_terms() (lines 924-963).
Why: the whole PriceList item is a byte-compared JSON document for clients that cache or diff offer files, and the description is the human-facing text a cost report prints for a reservation line. A client that matches or displays the reserved-term description sees a sentence AWS never emits, and a diff against a real offer file reports every reserved dimension as changed.
Fix: the reserved-term description builder in the pricing crate's state (reserved_description), so the reserved usage dimension carries only the platform/instance-type sentence while the fee and on-demand wordings stay as they are.
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4; pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#3.

Cause 3 of 3: the offer document's publication metadata is a frozen seed constant instead of the catalog's current publication.
AWS: recorded behavior only. Each term in a recorded offer document carries an `effectiveDate` equal to the start of the publication month in effect when the document is served (the October-2026 recordings show "2026-10-01T00:00:00Z" on both the OnDemand and the Reserved terms), and the document's publication stamp agrees with it. The requirement is that the date tracks the catalog's current publication and that `effectiveDate`, the document's `publicationDate` and its `version` stamp all agree — the particular month in any one recording is a recording-time value and is NOT the requirement.
Emulator: every term and every document carries the hardcoded constant CATALOG_PUBLICATION_DATE = "2024-01-01T00:00:00Z" (src/state.rs line 1184; used as `effectiveDate` at lines 909 and 953 and as the `version`/`publicationDate` source at lines 863, 886-887), so the served offer is permanently dated to a point two years before it is served, and no clock or state change ever moves it.
Why: a client that filters or orders offers by effectiveDate — picking the rate in effect for the current month, or refusing an offer that predates its billing period — discards the emulator's offers as stale, and a price-list consumer that keys a cache on (version, effectiveDate) never sees a new publication.
Fix: the publication metadata the pricing crate's state puts on each offer document and term (the CATALOG_PUBLICATION_DATE seam used by offer_document/on_demand_term/reserved_terms), so the date is derived from the catalog's current publication rather than frozen, with version/publicationDate/effectiveDate kept in agreement.
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4; pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#3.
