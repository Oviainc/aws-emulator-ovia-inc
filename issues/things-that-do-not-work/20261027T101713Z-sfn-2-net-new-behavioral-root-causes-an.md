# sfn: 2 net-new behavioral root causes — an activity task is never claimable so its TimeoutSeconds clock (claim-time, States.Timeout, ActivityTimedOut) is never exercised, and SendTaskFailure on a CMK-encrypted state machine never produces the KmsAccessDeniedException refusal

> _Note: this issue was identified against the code base at commit `415bc37b6ebe55c6c7e638f2212d4379947a3e7c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetActivityTask

## Description
Two net-new root causes in the Step Functions activity/callback data plane. Both surviving checks ended with the suite's only diagnostic, `Check timed out after 60.0s`: the graded behaviour was never produced, so the run never reached a terminal observation.

Cause 1 of 2 — the activity task clock and its timeout events (check: sfn.activity-task-timeout-starts-at-the-claim-not-the-schedule).
AWS: an Activity Task's ASL TimeoutSeconds clock starts when a worker CLAIMS the task (GetActivityTask hands back taskToken + the execution input; history records ActivityStarted), not when the task is scheduled. While unclaimed the task stays deliverable indefinitely — the execution stays RUNNING across many multiples of TimeoutSeconds, history holds ActivityScheduled (Smithy: ActivityScheduledEventDetails.timeoutInSeconds, "The maximum allowed duration of the activity task", carrying the definition's TimeoutSeconds) and NO ActivityStarted/ActivityTimedOut, and a later GetActivityTask still returns the token with the exact input StartExecution was given (Smithy: GetActivityTask output taskToken/input; it long-polls ~60 s and returns an empty response on expiry). Once claimed and abandoned past TimeoutSeconds, Step Functions records ActivityTimedOut (Smithy: HistoryEventType includes ActivityTimedOut; ActivityTimedOutEventDetails.error) with error = the fixed ASL error name "States.Timeout", and DescribeExecution reports status FAILED, error "States.Timeout" and NO output; ActivitySucceeded never appears, and ActivityTimedOut cannot precede its own TimeoutSeconds after ActivityStarted. A worker that answers SendTaskSuccess inside the window instead completes the execution SUCCEEDED with the worker's output.
Emulator: no part of the claim leg was observed. The replay reports only `Check timed out after 60.0s`, i.e. the check's unclaimed-window samples of DescribeExecution did not catch a divergence, and the run was cut before the GetActivityTask claim, the States.Timeout failure and the SendTaskSuccess positive control could be graded. Hypothesis: the activity task is never enqueued for a worker, so GetActivityTask hands out no token and the claim-time clock does not exist; that silence is already open as 20261025T075213Z-sfn-step-functions-activity-tasks-are-never-delivered-to.md (and its cloudwatch__sfn siblings 20261025T100143Z / 20261025T172604Z), but none of those issues carries this check's replay key, and none grades the claim-vs-schedule clock origin, the ActivityScheduled.timeoutInSeconds value, or the ActivityTimedOut/States.Timeout terminal shape.

Cause 2 of 2 — SendTaskFailure must be refused KmsAccessDeniedException when the state machine's customer-managed key denies crypto (check: sfn.send-task-failure-kms-access-denied).
AWS: for a state machine created with encryptionConfiguration {type: CUSTOMER_MANAGED_KMS_KEY, kmsKeyId: <cmk>, kmsDataKeyReusePeriodSeconds: 60}, SendTaskFailure's error/cause are encrypted under that CMK, so after the data-key reuse window elapses the call needs a fresh data key. If the key policy explicitly denies the crypto actions to every principal, SendTaskFailure is refused with the modeled error KmsAccessDeniedException (Smithy: SendTaskFailure errors include KmsAccessDeniedException, client error, HTTP 400, doc "Either your KMS key policy or API caller does not have the required permissions."); it must NOT fall back to an AWS-owned key and must NOT silently skip encryption and succeed. The message is the relayed KMS/STS authorization refusal; its fixed text is "User: <principal> is not authorized to perform: kms:Decrypt on resource: <key-arn> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)", where the variable parts are taken from the request and state: the principal is arn:aws:sts::<account>:assumed-role/<execution-role-name>/<session> (account from the caller, role name from the state machine's roleArn, session name minted per call), <key-arn> is the state machine's kmsKeyId, and the trailing request id / attempt count are per-call values.
Emulator: the refusal was never observed. The replay reports only `Check timed out after 60.0s`; the check is cut before its SendTaskFailure assertion, so the emulator produced neither the KmsAccessDeniedException code nor its message. Hypothesis: the run stalls earlier, in the 65 s GetActivityTask poll of Cause 1 (no token is ever handed out), so the CMK-encrypted callback path is unreachable; the related open issue 20261027T005501Z-kms-sfn-step-functions-execution-reads-are-never.md covers execution READS under a CMK, not the SendTaskFailure write path, and does not carry this check's replay key.

Why: a client that builds a worker-pool workflow on activities gets a task queue that never hands out work — executions hang until a timeout the service also does not model, so no worker can ever complete or time out a task, and retry/catch logic keyed on States.Timeout never runs. A client that encrypts a state machine with its own CMK and then revokes the key gets no KmsAccessDeniedException: either its callback appears to succeed (data silently unencrypted or encrypted under the wrong key) or it fails with an unrelated error, so key-revocation drills and KMS-denial handling cannot be validated.

Fix: the activity task store and the execution interpreter's task timers in the sfn service — GetActivityTask's handler (enqueue on ActivityScheduled, long-poll, hand out taskToken + input, emit ActivityStarted and arm TimeoutSeconds AT the claim, emit ActivityTimedOut/States.Timeout and fail the execution on expiry); and the KMS integration shared by the callback handlers (SendTaskFailure/SendTaskSuccess), which must request a data key under the state machine's encryptionConfiguration and surface the KMS refusal as the modeled KmsAccessDeniedException with the relayed message.

Traces: sfn.activity-task-timeout-starts-at-the-claim-not-the-schedule; sfn.send-task-failure-kms-access-denied (both verdict mismatch, `Check timed out after 60.0s`). Note for the fixer: both checks contain deliberate wall-clock windows (a 60 s unclaimed-observation window; a 70 s data-key-reuse wait) that exceed the suite's 60 s per-check cap, so the cap bounds how much of each divergence the replay could observe; confirm the fix by replaying these two checks without the cap.

## Evidence
Cause 1 — Expected (AWS): with a Task state {Resource:<activityArn>, TimeoutSeconds:10}, DescribeExecution stays RUNNING for ~60 s with no worker polling; history has exactly one ActivityScheduled with activityScheduledEventDetails.timeoutInSeconds == 10 and no ActivityStarted/ActivityTimedOut; GetActivityTask then returns a taskToken and input == the StartExecution input; abandoning it yields DescribeExecution status FAILED, error "States.Timeout", no output, exactly one ActivityTimedOut whose activityTimedOutEventDetails.error == "States.Timeout", no ActivitySucceeded, ActivityTimedOut.timestamp - ActivityStarted.timestamp >= 10 s and ActivityTimedOut.timestamp - ActivityScheduled.timestamp > 20 s; a control execution whose worker calls SendTaskSuccess ends SUCCEEDED with that output.
Actual (emulator): the graded leg never happened — the suite reports `Check timed out after 60.0s` with no terminal execution, no handed-out task token and no ActivityStarted/ActivityTimedOut observed.
Cause 2 — Expected (AWS): sfn.SendTaskFailure(taskToken=<activity token>, error="BoomWithKms", cause="needs encryption") on a CUSTOMER_MANAGED_KMS_KEY state machine whose key policy explicitly denies kms:Decrypt/kms:GenerateDataKey is refused HTTP 400 Code="KmsAccessDeniedException", Message="User: arn:aws:sts::<account>:assumed-role/<execution-role-name>/<session> is not authorized to perform: kms:Decrypt on resource: <state machine kmsKeyId> with an explicit deny in a resource-based policy (Service: Kms, Status Code: 400, Request ID: <request-id>) (SDK Attempt Count: <n>)" (fixed text as quoted; account/role name/session/key ARN/request id/attempt count are request- and state-derived).
Actual (emulator): no refusal observed at all — the run is cut at the 60 s cap before SendTaskFailure is graded, so neither the code nor the message was produced.

## Steps to Reproduce
Cause 1: (1) iam.CreateRole trusted by states.amazonaws.com; (2) sfn.CreateActivity; (3) sfn.CreateStateMachine STANDARD with {"StartAt":"HandOff","States":{"HandOff":{"Type":"Task","Resource":<activityArn>,"TimeoutSeconds":10,"End":true}}}; (4) sfn.StartExecution with input {"leg":"unclaimed-then-claimed"}; (5) with NO worker polling, call sfn.DescribeExecution every 5 s for 60 s — expect status RUNNING throughout; (6) sfn.GetExecutionHistory — expect ActivityScheduled.timeoutInSeconds==10, no ActivityStarted, no ActivityTimedOut; (7) sfn.GetActivityTask — expect a taskToken and the original input; (8) abandon it and poll DescribeExecution — expect FAILED/States.Timeout, no output, and one ActivityTimedOut with error States.Timeout; (9) positive control: start a second execution, GetActivityTask, SendTaskSuccess — expect SUCCEEDED with that output.
Cause 2: (1) kms.CreateKey; (2) iam.CreateRole trusted by states.amazonaws.com with kms:Decrypt/kms:GenerateDataKey on that key; (3) sfn.CreateActivity; (4) sfn.CreateStateMachine with that role and encryptionConfiguration {type:CUSTOMER_MANAGED_KMS_KEY, kmsKeyId:<key arn>, kmsDataKeyReusePeriodSeconds:60} over {"StartAt":"T","States":{"T":{"Type":"Task","Resource":<activityArn>,"TimeoutSeconds":180,"End":true}}}; (5) sfn.StartExecution, then sfn.GetActivityTask to claim the token; (6) kms.PutKeyPolicy replacing the policy with an explicit Deny of kms:Encrypt/Decrypt/ReEncrypt*/GenerateDataKey* for Principal "*" (root keeps kms:*), and poll kms.GenerateDataKey until it is refused AccessDeniedException; (7) wait out kmsDataKeyReusePeriodSeconds (70 s); (8) sfn.SendTaskFailure with that token — expect KmsAccessDeniedException and the message above.
