# cloudformation: 3 net-new behavioral root causes — WaitConditionHandle Ref is not a presigned URL, SNS-backed custom resources are never invoked, and a macro-Transform change set never holds in CREATE_IN_PROGRESS

> _Note: this issue was identified against the code base at commit `446e5d40b4aa72232e72e50ee85b856a1859ebd6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Three root causes of service `cloudformation`, grounded in the six failing behavioral checks listed in trace_ids. The replay report did NOT mark any of these six as ALREADY FILED or OWNED, so they are filed here; two open issues describe adjacent shapes and are named per cause below so a fixer can close them together. A fixer must close all three causes before submitting.

=== Cause 1 of 3: the physical resource id of an AWS::CloudFormation::WaitConditionHandle is a generated name, not a presigned HTTPS URL, so a signal can never be PUT ===
AWS: smithy_query on this service's model (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json) models no CloudFormation resource types at all — the members that carry this value (StackResource$PhysicalResourceId, StackResourceDetail$PhysicalResourceId, StackResourceSummary$PhysicalResourceId, Output$OutputValue) are unconstrained strings — so this is recorded behavior only. For AWS::CloudFormation::WaitConditionHandle the physical resource id, and therefore `Ref` on the handle, is an absolute presigned HTTPS S3 URL in the stack's region. The fixed part of the contract is the SHAPE: scheme `https`, an S3 host of the stack's region, and presigned query parameters; the bucket, key, signature and expiry are per-run values and are NOT part of the requirement. A client PUTs `{"Status":"SUCCESS","UniqueId":<id>,"Data":<string>,"Reason":<string>}` to that URL to release an AWS::CloudFormation::WaitCondition, and the counted signals surface through `Fn::GetAtt <WaitCondition>.Data`.
Emulator: the handle's physical id is a stack-and-logical-id derived name with no scheme (the two replays show values of the form `<stack-name>-<LogicalId>-<hex>`, e.g. `sim2real-signalres-172b94a5b28c-handle-eec6dee8ed12` and `sim2real-wc-count2-83033d6730d9-handle-7649b1b22cb2`; those exact tokens are per-run values, the divergence is that they are names and not URLs). Both checks then treat the value as a URL and are stopped by the harness egress guard: `simparity.egress.EgressRefused: egress refused: '<handle value>' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on`. That refusal is the emulator's: it announced an address other than the endpoint it is reached on.
Why: the WaitConditionHandle contract IS the URL. A client relying on AWS's behavior cannot release a WaitCondition, cannot hold a stack in CREATE_IN_PROGRESS behind a signal, and cannot read the signal accounting (count, per-UniqueId Data) back — the standard bootstrap/user-data signalling pattern is unusable.
Fix: the CloudFormation resource-provider/physical-id assignment for AWS::CloudFormation::WaitConditionHandle must mint and store a presigned HTTPS PUT URL the emulator itself serves, the Ref/GetAtt, DescribeStackResource(s), ListStackResources and stack-Outputs serializers must surface that stored value, and the handle-URL ingest path must accept the PUT and feed the WaitCondition's signal accounting (count and Data). Related open issue, which lists these same two check ids but did not own them in this replay: 20261029T214321Z-cloudformation-aws-cloudformation-waitconditionhandle-ref-returns-the-logical.md.
Traces: cloudformation.signal-resource-completes-wait-condition, cloudformation.wait-condition-count-and-data-signal-accounting.

=== Cause 2 of 3: a Custom:: resource whose ServiceToken is an SNS topic is never invoked — no provider request is ever published ===
AWS: the custom-resource protocol is not in the Smithy model (recorded behavior only). A resource of type `Custom::<Name>` or `AWS::CloudFormation::CustomResource` names its provider in the `ServiceToken` property (an SNS topic ARN or a Lambda ARN). On every stack operation touching the resource CloudFormation publishes a provider request to that token and holds the stack at `CREATE_IN_PROGRESS` / `UPDATE_IN_PROGRESS` / `DELETE_IN_PROGRESS` until the provider PUTs a response to the request's presigned `ResponseURL`. The request carries `RequestType` (`Create`|`Update`|`Delete`), `RequestId`, `StackId`, `LogicalResourceId`, `ResponseURL`, `ResourceProperties`, and additionally `PhysicalResourceId` and `OldResourceProperties` on Update/Delete. A `FAILED` response fails the resource and rolls the stack back; a rollback update re-sends the previous properties.
Emulator: no provider request is ever published. Each of these three checks creates an SNS topic, subscribes an SQS queue to it, passes the topic ARN as `ServiceToken`, creates/updates the stack and then blocks on ReceiveMessage for the lifecycle request. Nothing arrives, so the check makes no further progress and is killed at the harness ceiling: `Check timed out after 60.0s`. Because the handler request is never sent, the UPDATE_ROLLBACK_FAILED state these checks need to reach is unreachable, and with it the ContinueUpdateRollback and CancelUpdateStack rules they grade.
Why: custom resources are unusable. Every CDK/SAM construct backed by one hangs instead of completing, and the whole UPDATE_FAILED -> UPDATE_ROLLBACK_FAILED -> ContinueUpdateRollback recovery path — including the ValidationError refusal `RollbackUpdatedStack cannot be called from current stack status` that ContinueUpdateRollback must answer on a CREATE_COMPLETE stack — cannot be exercised at all.
Fix: the provisioning path needs a provisioner arm for `Custom::*` / `AWS::CloudFormation::CustomResource` that publishes the provider request to the `ServiceToken`, a `ResponseURL` the emulator serves in process, and a stabilisation barrier that holds the resource until the response lands (carrying the provider's PhysicalResourceId and Data back for Fn::GetAtt). Related open issue, which lists the first three of these check ids but did not own them in this replay: 20261025T180059Z-cloudformation-custom-resource-providers-and-hook-configuration.md.
Traces: cloudformation.continue-update-rollback-on-stable-stack-fails, cloudformation.stack-continue-update-rollback-lifecycle, cloudformation.stack-update-cancel-then-continue-rollback.

=== Cause 3 of 3: a change set over a template carrying a macro `Transform` never passes through CREATE_IN_PROGRESS, so ExecuteChangeSet's InvalidChangeSetStatus refusal is unobservable ===
AWS: recorded behavior only (the model's CreateChangeSet/DescribeChangeSet carry no rule about macro processing time; ExecuteChangeSet models InvalidChangeSetStatusException). CreateChangeSet over a template whose `Transform` names an AWS::CloudFormation::Macro returns immediately with the change set in `CREATE_IN_PROGRESS` and invokes the macro's Lambda; the change set stays in `CREATE_IN_PROGRESS` for as long as the macro takes to return its fragment, and the CREATE-type stack sits in `REVIEW_IN_PROGRESS` meanwhile. ExecuteChangeSet during that window is refused with HTTP 400, error code `InvalidChangeSetStatus` (the wire code has no `Exception` suffix) and the message `ChangeSet [<change set ARN>] cannot be executed in its current status of [CREATE_IN_PROGRESS]` — the fixed text is `ChangeSet [` ... `] cannot be executed in its current status of [` ... `]`, with the change set ARN taken from the request/state and the status taken from the change set's current state. The refusal touches nothing: the change set stays CREATE_IN_PROGRESS and the stack stays REVIEW_IN_PROGRESS, and once the macro returns the identical call succeeds and provisions the resource.
Emulator: the change set is never observable in `CREATE_IN_PROGRESS`. The check polls DescribeChangeSet once a second for up to 60s for that status and never sees it, so it makes no progress and is killed at the harness ceiling: `Check timed out after 60.0s`. Hypothesis: CreateChangeSet settles the change set synchronously (straight to a terminal status) and the macro named by `Transform` is never invoked, so there is no in-progress window to refuse an execute in and the `InvalidChangeSetStatus` arm of ExecuteChangeSet is dead code.
Why: a client cannot use macros at all, and cannot rely on the change-set status gate — a caller that races ExecuteChangeSet against a still-building change set gets a different outcome from AWS (either an accepted execution of a half-built change set, or a success where AWS refuses), and template authors using Transform macros see their fragment silently un-expanded. A related open issue covers the macro fragment itself in another service group (20261029T211043Z-cloudformation-lambda-ssm-cloudformation-a-failed-ssm-dynamic-reference-produces-no.md, which carries cfn-macro-transform-injects-working-resource); it does not cover the change-set status lifecycle graded here.
Fix: the change-set creation path must run template transforms asynchronously — publish the macro request to the macro's Lambda, keep the change set at `CREATE_IN_PROGRESS` until the fragment comes back, and have ExecuteChangeSet refuse a non-CREATE_COMPLETE change set with `InvalidChangeSetStatus` and the message above without mutating the change set or the stack.
Traces: cloudformation.changeset-execute-invalid-status-rejected.
