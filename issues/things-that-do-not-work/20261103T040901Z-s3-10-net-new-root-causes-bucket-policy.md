# s3: 10 net-new root causes — bucket-policy/PAB/ObjectOwnership authorization not enforced, delete-marker and version refusal metadata missing, conditional headers unimplemented

> _Note: this issue was identified against the code base at commit `56c3e2d5db4619f120a986f75a3622f8f9af8979`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutBucketPolicy

## Description
Ten distinct net-new root causes in the S3 emulator, all grounded in failing behavioural checks listed under `### s3`. Close all ten before submitting.

Cause 1 of 10: PutBucketPolicy performs no policy-document validation.
AWS: Smithy (services/service-com-amazonaws-s3-amazons3/smithy-model) — PutBucketPolicy, PUT /{Bucket}?policy, `Policy` is @httpPayload @required; the model declares no modeled errors, so the refusal is a REST-XML `<Error>` body. AWS parses the submitted document and refuses it with HTTP 400 and `<Code>MalformedPolicy</Code>` when it names an s3 action that does not exist, an s3 condition key that does not exist, or a `Resource` ARN that is not within the bucket being addressed. Fixed text is AWS's MalformedPolicy wording for that class; the variable part is the offending action / condition key / ARN copied from the submitted document. Hypothesis: the exact sentence (e.g. "Policy has invalid action" / "Policy has invalid condition key" / "Policy has invalid resource") — the recordings only show acceptance, so the code and status are the hard requirement.
Emulator: accepts every one of these documents and answers 2xx (204 on the PutBucketPolicy variants, 200 on the GetBucketPolicyStatus-driven variant) and stores them.
Why: a client that relies on S3 to reject a typo in an action name or condition key ships a policy that silently grants or denies nothing; the stored policy is then read back as valid and the whole authorization story of the bucket is wrong with no error anywhere.
Fix: the PutBucketPolicy handler's policy-document validation.
Traces: s3.s3-bucket-policy-with-an-unknown-s3-condition-key-rejected-malformed-policy, s3.s3-oac-grant-with-an-unknown-s3-action-rejected-malformed-policy, s3.s3-policy-status-public-only-when-the-source-vpc-condition-is-a-wildcard, s3.s3-tls-deny-policy-naming-another-buckets-arn-rejected-malformed-policy.

Cause 2 of 10: an explicit bucket-policy Deny produces a bare `Access Denied` message, and prefix-scoped policy conditions are not evaluated at all.
AWS: recorded behavior plus AWS's documented AccessDenied wording. When a resource-based policy explicitly denies the call, S3 answers HTTP 403 `<Code>AccessDenied</Code>` with the message template `User: <caller-arn> is not authorized to perform: <action> on resource: "<resource-arn>" with an explicit deny in a resource-based policy`. Fixed text: "User: ", " is not authorized to perform: ", " on resource: ", " with an explicit deny in a resource-based policy". Variable parts: the caller ARN from the signing identity, the action (`s3:GetObject`, `s3:PutObject`, …) from the request, and the object ARN built from the addressed bucket and key. A policy whose Deny is conditioned on `s3:prefix` / a key prefix must also be enforced, so a listing or write outside the allowed prefix is refused.
Emulator: the Deny is reached but the message is the literal string `Access Denied` with no principal, action, resource or explicit-deny clause; and the prefix-conditioned cases are never enforced at all — the checks poll for the refusal and the run ends with `Error: Check timed out after 60.0s`.
Why: a client that parses the AccessDenied message to tell "an explicit deny" from "no matching allow" cannot; and a prefix-scoped multi-tenant bucket policy is a no-op, so one tenant can read and overwrite another tenant's prefix. The open issue 20261102T091623Z-s3-the-data-plane-performs-no-iam-bucket.md is adjacent but does not carry these replay keys.
Fix: the S3 data-plane authorization path (bucket-policy evaluation and the AccessDenied serializer).
Traces: s3.bucket-policy-deny-enforcement, s3.s3-csv-explicit-deny-on-the-csv-key-denies-the-owner-but-not-other-keys, s3.bucket-policy-prefix-condition-listing-denied, s3.s3-prefix-scoped-deny-refuses-a-tenant-reseed-and-adds-no-version, s3.s3-oc-preferred-bucket-policy-requiring-bucket-owner-full-control-denies-puts-without-it.

Cause 3 of 10: Public Access Block and ObjectOwnership are not consulted by the ACL-bearing object operations.
AWS: recorded behavior. With BlockPublicAcls in force, an object operation carrying a public canned ACL (`x-amz-acl: public-read`) is refused HTTP 403 `<Code>AccessDenied</Code>`; on a bucket whose ObjectOwnership is BucketOwnerEnforced any ACL-bearing request is refused HTTP 400 `<Code>AccessControlListNotSupported</Code>` with "The bucket does not allow ACLs" — but an owner-only canned ACL (`bucket-owner-full-control` / `private`) must still be ACCEPTED on BucketOwnerEnforced, and ObjectOwnership=BucketOwnerEnforced outranks BlockPublicAcls so the refusal is the ACL-not-supported one, not the PAB one.
Emulator: CreateMultipartUpload with `ACL=public-read` under BlockPublicAcls returns 200 with an UploadId; CopyObject with a public ACL onto a BucketOwnerEnforced bucket returns 200; CreateBucket with ObjectWriter + public-read under Block Public Access succeeds; PutObject under enforced ownership answers AccessControlListNotSupported even for the owner-only canned ACLs AWS accepts, so the precedence is inverted in both directions.
Why: a bucket the account believes is private is made world-readable through multipart upload or copy, and conversely a correct owner-only ACL write is refused — both silently diverge from what the console/CLI reports.
Fix: the PAB / ObjectOwnership gate shared by PutObject, CopyObject, CreateMultipartUpload, PutObjectAcl and CreateBucket.
Traces: s3.block-public-acls-rejects-a-public-read-create-multipart-upload, s3.public-acl-on-an-owner-enforced-bucket-rejected, s3.s3-oc-create-bucket-object-writer-public-read-rejected-by-block-public-access, s3.s3-pab-object-ownership-enforced-outranks-block-public-acls-on-put-object, s3.s3-oc-enforced-accepts-owner-only-canned-acls-on-put-object.

Cause 4 of 10: PutBucketOwnershipControls accepts documents AWS refuses, and ExpectedBucketOwner is not evaluated before the body.
AWS: recorded behavior. OwnershipControls carries exactly one Rule; two Rules, or an ObjectOwnership value outside {BucketOwnerPreferred, ObjectWriter, BucketOwnerEnforced}, is refused HTTP 400 `<Code>MalformedXML</Code>`. A request whose `x-amz-expected-bucket-owner` names an account that does not own the bucket is refused HTTP 403 `<Code>AccessDenied</Code>` BEFORE the body is validated, and leaves the stored rule untouched. A default (BucketOwnerEnforced) bucket named as a server-access-logging target refuses TargetGrants.
Emulator: the two-rule and unknown-ObjectOwnership documents are accepted ("the call succeeded; real AWS rejects it"); when both a foreign ExpectedBucketOwner and a malformed body are present the emulator answers MalformedXML, i.e. it validates the body first; and the log-target TargetGrants request succeeds.
Why: a caller cannot trust the ownership state it reads back, and the confused-deputy guard that ExpectedBucketOwner exists to provide is bypassed whenever the body is also wrong.
Fix: PutBucketOwnershipControls / PutBucketLogging validation and the ExpectedBucketOwner pre-check ordering in those handlers.
Traces: s3.s3-oc-put-two-rules-rejected-malformed-xml, s3.s3-oc-put-unknown-object-ownership-rejected-malformed-xml, s3.s3-oc-put-with-a-foreign-expected-bucket-owner-denied-and-leaves-the-rule, s3.s3-oc-default-bucket-as-log-target-rejects-target-grants.

Cause 5 of 10: Public Access Block does not gate anonymous access, and PutPublicAccessBlock / GetBucketPolicyStatus skip their own validation.
AWS: recorded behavior. With IgnorePublicAcls set, an anonymous GetObject of a public-read object and an anonymous ListObjects of a public-read bucket are refused HTTP 403 `<Code>AccessDenied</Code>`; with RestrictPublicBuckets set, an anonymous GET through a public bucket policy is refused the same way. PutPublicAccessBlock with an empty PublicAccessBlockConfiguration is refused HTTP 400 `<Code>InvalidRequest</Code>`. GetBucketPolicyStatus on a bucket with no policy is refused HTTP 404 `<Code>NoSuchBucketPolicy</Code>` with "The bucket policy does not exist".
Emulator: the three anonymous-access checks never observe a refusal and end `Error: Check timed out after 60.0s`; the empty PAB document and the policy-status call on a policy-less bucket both succeed ("the call succeeded; real AWS rejects it, so there is no error code").
Why: Block Public Access is the control an account uses to prove no bucket is public; here it is inert, so an emulated estate reports itself protected while anonymous reads still work, and tooling that branches on NoSuchBucketPolicy takes the wrong branch.
Fix: the anonymous-request authorization path's PAB gate, plus PutPublicAccessBlock and GetBucketPolicyStatus validation.
Traces: s3.s3-pab-ignore-public-acls-denies-anonymous-get-of-a-public-read-object, s3.s3-pab-ignore-public-acls-denies-anonymous-list-of-a-public-read-bucket, s3.s3-pab-restrict-public-buckets-denies-anonymous-get-through-a-public-policy, s3.s3-pab-empty-configuration-put-rejected-invalid-request, s3.s3-pab-policy-status-without-a-policy-rejected-no-such-bucket-policy.

Cause 6 of 10: Requester Pays is not enforced.
AWS: Smithy — `RequestPayer` is bound to `x-amz-request-payer` on the object operations and `RequestCharged` to `x-amz-request-charged` on their output. On a bucket whose RequestPaymentConfiguration is `Requester`, an anonymous request is refused HTTP 403 `<Code>AccessDenied</Code>` and a request that does carry `x-amz-request-payer: requester` from an anonymous caller is also refused (an anonymous caller cannot be billed); once the payer is reset to `BucketOwner`, the anonymous read succeeds again.
Emulator: the anonymous-with-payer-header case never converges (`Error: Check timed out after 60.0s`), and after RequestPayment is reset to BucketOwner the anonymous GetObject keeps answering `('AccessDenied', 'Access Denied')` for the whole 30s window — the payer setting is not read on either edge.
Why: a requester-pays bucket neither bills nor refuses correctly, and a bucket taken OUT of requester-pays stays unreadable, so a configuration change has no observable effect.
Fix: the RequestPayment state and its gate in the object-plane handlers.
Traces: s3.deep-s3-immutability-requester-pays-anonymous-with-payer-header-rejected, s3.requester-pays-enforcement.

Cause 7 of 10: conditional request headers are unimplemented or rejected as malformed timestamps.
AWS: Smithy — GetObject/HeadObject/CopyObject bind `IfMatch`, `IfNoneMatch`, `IfModifiedSince`, `IfUnmodifiedSince`, `CopySourceIfMatch`, `CopySourceIfUnmodifiedSince` as HTTP headers; the timestamp members use the HTTP-date format on the wire. An If-None-Match matching the current ETag answers HTTP 304 with no body (Range header or not); an If-Unmodified-Since earlier than LastModified answers HTTP 412 `<Code>PreconditionFailed</Code>` with "At least one of the pre-conditions you specified did not hold" — that message is fixed text with NO trailing header name.
Emulator: GetObject with If-None-Match answers HTTP 501 `<Code>NotImplemented</Code>` "operation GetObject with If-None-Match is scaffolded but not implemented in this emulator"; HeadObject with conditional headers answers 501 Not Implemented; the HTTP-date headers are refused HTTP 400 `<Code>ValidationException</Code>` "invalid timestamp `<the RFC 7231 date sent>`: invalid date-time: Smithy does not support timezone offsets in RFC-3339 date times" — i.e. the HTTP-date is being parsed as RFC-3339; and CopyObject's PreconditionFailed message appends ": x-amz-copy-source-if-match" to AWS's fixed sentence.
Why: every caching client and every optimistic-concurrency client breaks: 501 and 400 are not retryable-as-304, and the extra suffix defeats exact-message matching.
Fix: the conditional-header evaluation in the GetObject/HeadObject/CopyObject handlers and the HTTP-date deserializer for those members.
Traces: s3.s3-get-object-if-match-foreign-etag-rejected-precondition-failed, s3.s3-conditional-precedence-and-lifecycle-headers-get, s3.s3-csvcols-head-object-conditional-headers-refuse-with-bare-status, s3.s3-txtsim-get-matching-if-none-match-rejected-not-modified, s3.s3-copy-object-source-if-match-mismatch-rejected.

Cause 8 of 10: refusals that hit a delete marker carry none of the metadata that identifies them as such.
AWS: recorded behavior. A GET/HEAD/GetObjectAcl/GetObjectAttributes addressed at a delete-marker VERSION is refused HTTP 405 `<Code>MethodNotAllowed</Code>` and the response carries `x-amz-delete-marker: true`, `x-amz-version-id: <that marker's id>`, `Allow: DELETE`, and an `<Error>` body whose `Method` is the refused method and whose `ResourceType` is `DeleteMarker`. An unqualified GET of a key whose latest version is a delete marker is HTTP 404 `<Code>NoSuchKey</Code>` but still carries `x-amz-delete-marker: true` and the marker's version id — that header is the only thing separating "hidden by a marker" from "never existed". GetObjectTagging has no unversioned form of that refusal, so an unqualified GetObjectTagging on a marker-hidden key is HTTP 405 `<Code>MethodNotAllowed</Code>` flagged as a delete marker, not NoSuchKey.
Emulator: every one of those responses comes back with an empty/absent header set (`headers were {}`, `got None`), no Method/ResourceType in the body, and GetObjectTagging answers `('NoSuchKey', 'The specified key does not exist.', 404)`.
Why: a client cannot distinguish a deleted object from a never-created one, so undelete/restore tooling and tag-management tooling take the wrong path.
Fix: the delete-marker branch of the object-read handlers and their error serializer (headers + Error body members).
Traces: s3.mbes-get-on-a-delete-marker-version-is-method-not-allowed, s3.s3-csvcols-get-object-acl-of-a-delete-marker-version-rejected-method-not-allowed, s3.s3-objver-get-object-attributes-on-a-delete-marker-rejected, s3.s3-objver-get-of-a-delete-marker-version-rejected-method-not-allowed, s3.s3-objver-get-of-a-key-behind-a-delete-marker-rejected-nosuchkey, s3.s3-objver-head-of-a-delete-marker-version-rejected-405, s3.s3-csv-delete-marker-hides-the-tag-set-and-get-tagging-by-marker-version-rejected.

Cause 9 of 10: ListObjectVersions accepts a VersionIdMarker with no KeyMarker, omits Owner, and orders its checks wrongly; malformed version ids are answered NoSuchVersion.
AWS: Smithy — ListObjectVersions GET /{Bucket}?versions binds `KeyMarker` (key-marker) and `VersionIdMarker` (version-id-marker) as query params, and `ObjectVersion` carries an `Owner` member. A `version-id-marker` without a `key-marker` is refused HTTP 400 `<Code>InvalidArgument</Code>`, and that parameter check happens BEFORE bucket existence, so a dangling marker against a missing bucket is InvalidArgument rather than NoSuchBucket. Every `<Version>` entry carries `Owner.ID`. A version id S3 never issued (wrong alphabet/length) is refused HTTP 400 `<Code>InvalidArgument</Code>`, not 404 NoSuchVersion.
Emulator: the version-id-marker-without-key-marker request succeeds ("the call succeeded; real AWS rejects it, so there is no error code"); against a missing bucket it answers `('NoSuchBucket', 404)`; every listed version's Owner.ID is `None`; and a malformed version id answers `('NoSuchVersion', 404)`.
Why: a paginating client that drops KeyMarker gets a silently wrong page instead of an error, ownership-based tooling sees no owner, and a client that branches on InvalidArgument vs NoSuchVersion mistakes a typo for a deleted version.
Fix: ListObjectVersions input validation and its result serializer, plus the version-id parsing shared by the object-read handlers.
Traces: s3.mbes-version-id-marker-without-key-marker-rejected, s3.s3-objver-version-id-marker-without-key-marker-rejected, s3.s3-objver-list-objects-v2-agrees-with-latest-versions-and-omits-owner, s3.s3-objver-list-versions-of-an-absent-bucket-rejected-nosuchbucket, s3.s3-objver-get-with-a-malformed-version-id-rejected-invalid-argument.

Cause 10 of 10: HeadObject reports StorageClass for STANDARD objects and a LastModified that does not agree with the listing.
AWS: recorded behavior, consistent with the model (`StorageClass` is an optional output member). HeadObject OMITS `x-amz-storage-class` for an object in STANDARD — the header appears only for non-STANDARD classes. HeadObject's `Last-Modified` is the same second-precision instant the version listing reports for that version; both are truncated to whole seconds in UTC.
Emulator: HeadObject returns `StorageClass: 'STANDARD'`, and its LastModified disagrees with ListObjectVersions for the same version — the listing carries sub-second microseconds in a local-offset timezone while HEAD carries a whole-second UTC value, so a client comparing the two sees two different timestamps for one version.
Why: tooling that treats the presence of StorageClass as "not STANDARD" mis-tiers objects, and any read-after-list consistency check on LastModified fails spuriously.
Fix: the HeadObject output serializer and the shared last-modified normalisation used by HeadObject and the listing handlers.
Traces: s3.s3-objver-head-object-agrees-with-the-version-listing, s3.s3-itc-copy-in-place-moves-an-object-into-and-out-of-intelligent-tiering.
