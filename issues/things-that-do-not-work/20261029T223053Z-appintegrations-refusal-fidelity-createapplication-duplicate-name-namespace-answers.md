# appintegrations refusal fidelity: CreateApplication duplicate Name+Namespace answers the wrong class, CreateDataIntegrationAssociation and UpdateDataIntegrationAssociation messages are emulator-authored

> _Note: this issue was identified against the code base at commit `900a7beaab356ed52889492ca7befa08b17bdc0c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApplication

## Description
THREE net-new root causes on the AppIntegrations emulator, all on refusal paths of operations that are implemented and answering (the service is bootstrapped; these are fidelity defects, not bootstrap gaps). Cause 1 is the same defect that the OPEN wire issue 20261029T192932Z-app-integrations-appintegrations-mutation-and-refusal-paths-diverge-update-delete.md records as its Cause 1 from the wire corpus; that issue does not carry this behavioral check's replay key, so the check is filed here and the two should be fixed together. Causes 2 and 3 are not covered by any open issue. The RESOLVED issue 20261023T123004Z-appintegrations-constraint-rejections-answer-validationexception-instead-of-badrequestexception.md established the generic "Could not find <Resource> with identifier: <value>." not-found template for this service; Cause 3 is NOT a regression of that fix but the case where AWS does not use that generic form at all — the DataIntegrationAssociation not-found message is two-part and names BOTH identifiers. The four checks the report marks ALREADY FILED (DeleteApplication, UpdateApplication, ListApplicationAssociations, ListTagsForResource scaffold stubs) are deliberately not included here.

Cause 1 of 3 — CreateApplication refuses a duplicate Name+Namespace with the wrong error class and an emulator-authored message.
AWS: recorded behavior only for the choice of class — Smithy models BOTH InvalidRequestException (HTTP 400) and DuplicateResourceException (HTTP 409) on CreateApplication (model: services/service-com-amazonaws-appintegrations-amazonappintegrationservice/smithy-model/com-amazonaws-appintegrations-amazonappintegrationservice.json; CreateApplication.Name -> ApplicationName @required @length 1..255 @pattern ^[a-zA-Z0-9\/\._ \-]+$, Namespace -> ApplicationNamespace @required @length 1..211), so the model alone does not pick one. The recording picks InvalidRequestException: a second CreateApplication with a Name already in use in the same Namespace is refused with HTTP 400, error code InvalidRequestException and the message "Application name is invalid. Name already in use." — that message is ENTIRELY FIXED text with NO variable parts; AWS deliberately echoes neither the Name nor the Namespace back.
Emulator: HTTP 409 with error code DuplicateResourceException and an emulator-authored template message that interpolates the request's Name and Namespace ("An application named <Name> already exists in namespace <Namespace>.").
Why: a client branching on the error code or on the 4xx class takes its conflict/retry path instead of its invalid-input path, and any assertion on AWS's sentence can never match. A caller that treats 409 as retryable will loop on a request that AWS says is permanently invalid.
Fix: the duplicate-name branch of the CreateApplication handler (services/service-com-amazonaws-appintegrations-amazonappintegrationservice/src/ops/create_application.rs) — raise InvalidRequestException (400) carrying AWS's fixed sentence verbatim.
Traces: appintegrations.create-application-duplicate-name-namespace-rejected.

Cause 2 of 3 — CreateDataIntegrationAssociation's rejection message for an ExecutionMode/configuration-shape mismatch is emulator-authored.
AWS: Smithy CreateDataIntegrationAssociation (POST /dataIntegrations/{DataIntegrationIdentifier}/associations) models InvalidRequestException (HTTP 400) and ResourceNotFoundException (HTTP 404); ExecutionConfiguration.ExecutionMode -> ExecutionMode enum [ON_DEMAND, SCHEDULED] @required, with the optional OnDemandConfiguration / ScheduleConfiguration siblings. The model states no cross-member rule, so the refusal text is recorded behavior only: a request pairing ExecutionMode ON_DEMAND with ScheduleConfiguration is refused with HTTP 400 InvalidRequestException whose message is "Failed to create DataIntegrationAssociation for DataIntegration <DataIntegrationId>. DATA_INTEGRATION_ASSOCIATION_VALIDATION_EXCEPTION: Access Denied to S3 Bucket" — fixed text "Failed to create DataIntegrationAssociation for DataIntegration ", then ". DATA_INTEGRATION_ASSOCIATION_VALIDATION_EXCEPTION: Access Denied to S3 Bucket"; the single variable part is the DataIntegration id taken from the request path (the Id CreateDataIntegration minted). Hypothesis: AWS runs its source-access validation for the association before (or instead of) any ExecutionConfiguration shape check, so this request class surfaces as that wrapped validation failure rather than as a per-member complaint. No association is persisted either way, and the status 400 and code InvalidRequestException already match.
Emulator: HTTP 400 InvalidRequestException with its own sentence "ExecutionConfiguration with ExecutionMode ON_DEMAND requires OnDemandConfiguration." (built by crate::state::execution_configuration_problem and raised from src/ops/create_data_integration_association.rs).
Why: the message is part of the contract; clients, operators and test suites that match on AWS's wrapped DATA_INTEGRATION_ASSOCIATION_VALIDATION_EXCEPTION text see a sentence AWS cannot produce, and tooling that extracts the failing DataIntegration id from the message finds nothing to extract.
Fix: the refusal-message construction for this operation — the create handler's ExecutionConfiguration validation branch and the shared helper it calls (crate::state::execution_configuration_problem) must emit AWS's wrapped sentence with the request's DataIntegration id interpolated, keeping 400/InvalidRequestException and persisting nothing.
Traces: appintegrations.create-data-integration-association-invalid-execution-configuration-rejected. Code: src/ops/create_data_integration_association.rs:166-229 (validation path), src/state.rs (execution_configuration_problem).

Cause 3 of 3 — UpdateDataIntegrationAssociation's ResourceNotFoundException message uses the generic single-identifier template instead of AWS's two-identifier one.
AWS: Smithy UpdateDataIntegrationAssociation (PATCH /dataIntegrations/{DataIntegrationIdentifier}/associations/{DataIntegrationAssociationIdentifier}, both @httpLabel @required, empty output) models ResourceNotFoundException (HTTP 404). Recorded behavior: when the association cannot be resolved, the message names BOTH path identifiers: "Could not find DataIntegrationAssociation with DataIntegrationName: <DataIntegrationIdentifier> and DataIntegrationAssociationId: <DataIntegrationAssociationIdentifier>." — fixed text "Could not find DataIntegrationAssociation with DataIntegrationName: ", " and DataIntegrationAssociationId: " and the trailing period; the two variable parts are the identifiers the request sent. The SAME message is returned when the parent DataIntegration itself does not exist (AWS does not fall back to a DataIntegration-scoped not-found there).
Emulator: 404/ResourceNotFoundException are correct, but the message is "Could not find DataIntegrationAssociation with identifier: <DataIntegrationAssociationIdentifier>." — the generic one-identifier family template, which drops the parent DataIntegration entirely; and for a nonexistent parent DataIntegration the handler answers the DataIntegration-scoped "Could not find DataIntegration with identifier: <id>." instead.
Why: not-found handling that keys on the message, and operators diagnosing which of the two identifiers was wrong, get text AWS never produces and lose the parent identifier from the diagnostic.
Fix: the two not-found branches of the UpdateDataIntegrationAssociation handler and the helper they call (crate::state::data_integration_association_not_found) must take both identifiers and render AWS's two-part sentence, including when the parent DataIntegration lookup is what failed.
Traces: appintegrations.update-data-integration-association-nonexistent-identifiers-rejected. Code: src/ops/update_data_integration_association.rs:156-180, src/state.rs (data_integration_association_not_found, data_integration_not_found).
