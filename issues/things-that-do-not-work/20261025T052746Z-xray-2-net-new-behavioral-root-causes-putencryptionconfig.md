Cause 1 of 2: the templated enum-constraint ValidationException message for PutEncryptionConfig renders the enum value set in the wrong order.
AWS: PutEncryptionConfig(Type=<value outside the enum>) is refused at HTTP 400 with error code ValidationException and the standard AWS constraint-violation message, which is BUILT FROM THE REQUEST: "1 validation error detected: Value '<submitted value>' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [KMS, NONE]". The rule — not the recorded text — is the requirement: the message names the offending value, the member (`type`, the wire/jsonName casing of the input member), the constraint class (enum value set) and the admissible set rendered as a bracketed comma-separated list, and real X-Ray renders that set as `[KMS, NONE]`. Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json): PutEncryptionConfig.Type is @required and targets enum com.amazonaws.xray#EncryptionType; the model declares its values in the order [NONE, KMS], i.e. the service does NOT render the set in model-declaration order, so the rendering order itself is recorded behavior. Status 400 and code ValidationException match.
Emulator: status and code are correct, but the rendered set is reversed — observed message "1 validation error detected: Value 'NOT_A_TYPE' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [NONE, KMS]" (the emulator appears to emit the set in Smithy declaration order).
Why: the message is the only place this surface tells a caller WHICH values are legal. A client, CLI wrapper, or test harness that pattern-matches AWS's fixed constraint text (log scrapers, error-mapping layers, contract tests asserting the documented wording) does not match, and an operator reading the emulator's text is told a different admissible-set rendering than the service's. Because the check never gets past this assertion, the rest of the same check is also left unverified behind it: that PutEncryptionConfig(Type=NONE) returns Type=NONE with Status in (UPDATING, ACTIVE) and that GetEncryptionConfig eventually settles on Status=ACTIVE — confirm those still hold once the message is corrected.
Fix: the enum-constraint message construction used by the PutEncryptionConfig input validation (the shared ValidationException formatter for enum violations in services/service-com-amazonaws-xray-awsxray) must render the admissible set in the service's order rather than the model's declaration order.
Traces: xray.put-get-encryption-config-transitions.

Cause 2 of 2: an AWS::XRay::SamplingRule declared in a CloudFormation template is never created, so a client polling GetSamplingRules for it never terminates and the check is cut off by the harness ceiling.
AWS: CreateStack on a template whose only resource is {"Type": "AWS::XRay::SamplingRule", "Properties": {"SamplingRule": {RuleName, ResourceARN, Priority, FixedRate, ReservoirSize, ServiceName, ServiceType, Host, HTTPMethod, URLPath, Version}}} invokes X-Ray CreateSamplingRule as part of stack creation; once the stack reaches CREATE_COMPLETE, GetSamplingRules returns a SamplingRuleRecord for that RuleName carrying the declared Priority / FixedRate / ReservoirSize / ServiceName and a populated RuleARN, GetSamplingTargets then serves an allocation for it (not UnprocessedStatistics), and deleting the stack removes the rule again. Smithy: CreateSamplingRule -> SamplingRuleRecord{SamplingRule{RuleName, RuleARN, FixedRate, ReservoirSize, Priority, ...}}, GetSamplingRules -> SamplingRuleRecords, GetSamplingTargets -> SamplingTargetDocuments/UnprocessedStatistics. The CloudFormation resource-type-to-API mapping is recorded behavior only.
Emulator: the check never completes — it is terminated by the suite at the 60s ceiling ("Check timed out after 60.0s"). The check's only unbounded work is (a) the stack_create_complete waiter and (b) a 60s poll of a full paginated GetSamplingRules walk looking for the declared RuleName; the rule is never provisioned, so that poll can never satisfy its predicate and burns the entire budget. No sampling rule, no RuleARN and no sampling-target allocation is ever observable for the stack.
Why: a client that provisions sampling rules by stack sees a stack it cannot distinguish from a successful deploy and then an account with no such rule: GetSamplingRules cannot see it, GetSamplingTargets can never allocate a reservoir for it, and the sampling behavior the deploy was supposed to establish silently never takes effect — while any wait-for-the-rule loop hangs instead of failing fast.
Fix: a resource provider for AWS::XRay::SamplingRule in the CloudFormation stack-resource provisioning layer (services/service-com-amazonaws-cloudformation-cloudformation), calling the X-Ray CreateSamplingRule / DeleteSamplingRule handlers on stack create and delete. Reconcile with 20261025T032230Z-xray-cloudformation-still-does-not-provision-aws-xray-samplingrule.md Cause 1 — the same provider closes both.
Traces: xray.deploy-sampling-rule-via-cloudformation-active.
