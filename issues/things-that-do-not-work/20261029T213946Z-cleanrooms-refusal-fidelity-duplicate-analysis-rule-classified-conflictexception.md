# cleanrooms refusal fidelity: duplicate analysis-rule classified ConflictException instead of ValidationException, three emulator-worded refusal messages, tagging not-found code, and GetConfiguredTableAssociationAnalysisRule unimplemented

> _Note: this issue was identified against the code base at commit `7240e32f2500d20910730c71d4ad0714ff1f3217`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfiguredTableAnalysisRule

## Description
Five net-new root causes on the cleanrooms control plane, all reached through refusal paths (plus one operation that never answers at all). Each is an independent defect in how the emulator classifies or words a refusal. 5 causes must be closed before this issue is submitted.

Cause 1 of 5: a second analysis rule of the same type on a configured table is refused as ConflictException (409) instead of ValidationException (400), with the emulator's own message.
AWS: Smithy: CreateConfiguredTableAnalysisRule (POST /configuredTables/{configuredTableIdentifier}/analysisRule) models both ConflictException (httpError 409) and ValidationException (httpError 400); ValidationException is documented "The input fails to satisfy the specified constraints." Recorded behavior: AWS refuses the duplicate with code ValidationException, i.e. HTTP 400, and the message template "Only one Analysis Rule is allowed per Configured Table Configured Table <configuredTableId> already has a <analysisRuleType> analysis rule." — the fixed text is "Only one Analysis Rule is allowed per Configured Table Configured Table ", " already has a " and " analysis rule."; the two variable parts are the configuredTableIdentifier from the request path and the analysisRuleType from the request body. AWS treats "one analysis rule per configured table" as an input constraint, not a resource conflict.
Emulator: refuses with Code 'ConflictException' (HTTP 409) and the message "configured table <id> already has a LIST analysis rule; only one analysis rule can be created for a given configured table" — a wholly emulator-authored sentence, lower-cased and with the clauses in the opposite order from AWS's.
Why: a client that branches on the error code takes its conflict/retry path (ConflictException is the code AWS uses for retryable state conflicts and is what SDK retry and reconcile logic keys on) instead of its permanent-input-error path, so a duplicate-rule bug is retried forever rather than surfaced; error-classification tables and log scrapers matching AWS's documented sentence never match.
Fix: the CreateConfiguredTableAnalysisRule handler's duplicate-rule validation — raise the modeled ValidationException (400) with AWS's message template instead of ConflictException.
Traces: cleanrooms.create-configured-table-analysis-rule-duplicate-conflict.

Cause 2 of 5: DeleteMembership on the collaboration creator's own ACTIVE membership is refused with the right code but an emulator-authored message.
AWS: Smithy: DeleteMembership (DELETE /memberships/{membershipIdentifier}, success 204) models ConflictException (httpError 409), documented "Updating or deleting a resource can cause an inconsistent state." Recorded behavior: deleting the creator's still-ACTIVE membership is refused 409 ConflictException with the message "Cannot delete membership for the creator of the collaboration while their membership is still ACTIVE." — that sentence is entirely fixed text, with no interpolated membership id, collaboration id or account id.
Emulator: answers 409 ConflictException (code correct) but with "Cannot delete membership <membershipId> while collaboration <collaborationId> exists. The collaboration creator's membership is removed by deleting the collaboration" — its own two-sentence wording, with the membership and collaboration ids interpolated into text AWS does not interpolate anything into, and no trailing period on the second sentence. The ids in the observed string are per-run values and are not part of any requirement; the requirement is AWS's fixed sentence.
Why: clients and test suites that assert on, or display, the documented refusal text do not recognise the emulator's sentence, and the interpolated ids make it impossible to match the refusal with a fixed string at all.
Fix: the DeleteMembership handler's creator-membership guard — emit AWS's fixed message (and populate the modeled ConflictException resourceId/resourceType/reason members consistently with it).
Traces: cleanrooms.create-membership-duplicate-conflict.

Cause 3 of 5: GetPrivacyBudgetTemplate for a deleted template reports the wrong missing resource and an emulator-authored message.
AWS: Smithy: GetPrivacyBudgetTemplate (GET /memberships/{membershipIdentifier}/privacybudgettemplates/{privacyBudgetTemplateIdentifier}) models ResourceNotFoundException (httpError 404), whose shape REQUIRES message, resourceId and resourceType (resourceType = ResourceType enum including COLLABORATION, MEMBERSHIP, CONFIGURED_TABLE, CONFIGURED_TABLE_ASSOCIATION). Recorded behavior: reading a template that has been deleted is refused 404 with the message template "No privacy budget template found with id <privacyBudgetTemplateIdentifier> for membership <membershipIdentifier>." — the fixed text is "No privacy budget template found with id ", " for membership " and the trailing "."; the two variable parts are the two identifiers taken verbatim from the request path. The refusal names the template that is missing and the membership it was scoped to.
Emulator: answers 404 ResourceNotFoundException (code correct) with "privacy budget template <templateId> not found in collaboration <collaborationId>", and the payload's resourceId is the COLLABORATION id with resourceType 'COLLABORATION'. So the emulator both rewords the sentence and attributes the miss to the wrong resource: it substitutes the collaboration for the membership that was actually addressed, and reports the collaboration as the missing resource rather than the privacy budget template the client asked for.
Why: a client inspecting ResourceNotFoundException.resourceId/resourceType to decide what to recreate is told the COLLABORATION is missing, and will tear down or recreate the collaboration instead of re-creating the budget template; message-matching error handling fails because the sentence and the identifier it names both differ from AWS's.
Fix: the GetPrivacyBudgetTemplate handler's not-found path and the shared cleanrooms not-found error mapper — emit AWS's message template keyed on (privacyBudgetTemplateIdentifier, membershipIdentifier) and set resourceId/resourceType to the resource that was actually addressed.
Traces: cleanrooms.create-privacy-budget-template-duplicate-conflict.

Cause 4 of 5: GetConfiguredTableAssociationAnalysisRule is an unimplemented scaffold stub, so every read of a configured-table-association analysis rule is refused NotImplemented.
AWS: Smithy: GetConfiguredTableAssociationAnalysisRule, GET /memberships/{membershipIdentifier}/configuredTableAssociations/{configuredTableAssociationIdentifier}/analysisRule/{analysisRuleType} (@readonly, success 200, required output member analysisRule), modeled errors AccessDenied(403) | InternalServer(500) | ResourceNotFound(404) | Throttling(429) | Validation(400). Recorded behavior: when the association carries no rule of the requested type the call is refused 404 ResourceNotFoundException with the message template "No such analysis rule with configuredTableAssociationId: <configuredTableAssociationIdentifier> and type <internalRuleTypeName>" — the fixed text is "No such analysis rule with configuredTableAssociationId: " and " and type "; the variable parts are the association id from the request path and the rule type, which AWS renders by its INTERNAL name (the modeled LIST member is reported as "IntersectionList"). Once the rule is created the same GET answers 200 with analysisRule.type equal to the modeled type ("LIST"), and after DeleteConfiguredTableAssociationAnalysisRule it returns to the same 404.
Emulator: the operation is a scaffold stub — it answers Code 'NotImplemented' with "operation GetConfiguredTableAssociationAnalysisRule is scaffolded but not implemented in this emulator" for every call, so neither the 404-before-create leg, the 200 read-back, nor the 404-after-delete leg can be observed. Note this is a DIFFERENT operation from the already-filed CreateConfiguredTableAssociationAnalysisRule stub; implementing the create does not make this read answer.
Why: NotImplemented is not a modeled error for this operation, so an SDK cannot deserialize it into any known exception and client code probing whether an association already has an analysis rule crashes instead of taking its create-or-update branch; the entire association analysis-rule read plane is unusable.
Fix: implement the GetConfiguredTableAssociationAnalysisRule handler (its ops module under the cleanrooms service crate) against the stored association analysis-rule state, keyed by (membershipIdentifier, configuredTableAssociationIdentifier, analysisRuleType), returning 200 with the stored rule or the modeled 404 with AWS's message template and the internal rule-type name.
Traces: cleanrooms.get-configured-table-association-analysis-rule-not-found-before-creation.

Cause 5 of 5: the cleanrooms tagging plane refuses an unknown resource ARN with error code ResourceNotFoundException where AWS uses a distinct NotFoundException.
AWS: Smithy: TagResource (POST /tags/{resourceArn}) models only ResourceNotFoundException (404) and ValidationException (400) on the CleanRooms shape, so the model does not state this case; recorded behavior is the authority. Recorded behavior: tagging a well-formed cleanrooms ARN that names no existing resource is refused with error code "NotFoundException" — the tagging API surfaces its own not-found error code, distinct from the ResourceNotFoundException the core CleanRooms CRUD operations use — and the fixed message "Resource was not found" (entirely fixed text, with no ARN, id or type interpolated).
Emulator: refuses with Code 'ResourceNotFoundException' and the message "No such resource: <resourceArn>", i.e. the core-CRUD error code plus its own sentence with the requested ARN interpolated. The account id, region and resource id in the observed ARN are per-run values and not part of any requirement.
Why: a client that catches the tagging API's NotFoundException (the code botocore/SDK exception classes are generated and keyed by for this error) does not catch ResourceNotFoundException, so the refusal escapes as an unhandled error instead of being handled as "resource absent"; message-matching handling also fails on the reworded sentence.
Fix: the cleanrooms TagResource/UntagResource/ListTagsForResource not-found path — emit the tagging plane's NotFoundException code with AWS's fixed message, keeping the core CRUD operations on ResourceNotFoundException.
Note on overlap: the open issue 20261029T175308Z-cleanrooms-tagging-responses-answer-200-instead-of-204.md records the tagging MESSAGE wording and the 200-vs-204 statuses from a wire replay, but it states AWS's code for this refusal as ResourceNotFoundException; it therefore does not cover the error-CODE divergence reported here (NotFoundException vs ResourceNotFoundException), which this cause owns.
Traces: cleanrooms.tag-resource-round-trip.
