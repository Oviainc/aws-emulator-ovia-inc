# CodeDeploy never refuses an alarm-enabled deployment whose service role is denied cloudwatch:DescribeAlarms, so ignorePollAlarmFailure=true and =false are indistinguishable (1 cause)

> _Note: this issue was identified against the code base at commit `a946db3d2c92d3ec27b0f0d3beb3e4ffad06b536`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
One net-new root cause in the codedeploy emulator's Lambda deployment executor, grounded in the only failing check of this run that the replay report did not mark as owned by an open issue. Related but NOT marked as covering it: open issue 20261108T015127Z-codedeploy-deployment-outcomes-diverge-iam-role-permissions-never.md describes the sibling cause (IAM_ROLE_PERMISSIONS never raised for a role with no lambda:* grant) and names this check in its prose, but the replay report did not attribute this check's current failure to that issue's replay key (that key points at a Timeout inside _await_probe_refused; this run's failure is the whole check being killed at the 180s harness budget), so it is filed here as its own work item. 20261029T180825Z-codedeploy-rejection-paths-return-the-right-error-codes.md covers client-visible ClientError refusals, not this in-band deployment outcome.

=== Cause 1 of 1: an alarm-enabled deployment group whose service role cannot read its CloudWatch alarms must fail the deployment with IAM_ROLE_PERMISSIONS, regardless of ignorePollAlarmFailure; the emulator never produces that outcome ===
AWS: Smithy (com.amazonaws.codedeploy#CodeDeploy_20141006) models AlarmConfiguration{enabled: Boolean(default false), ignorePollAlarmFailure: Boolean(default false), alarms: AlarmList} and DeploymentInfo.errorInformation as ErrorInformation{code: ErrorCode, message: ErrorMessage}; the ErrorCode enum contains IAM_ROLE_PERMISSIONS (alongside ALARM_ACTIVE, IAM_ROLE_MISSING, ...). The model documents ignorePollAlarmFailure as governing only whether a deployment continues when alarm STATE information 'can't be retrieved from Amazon CloudWatch'. Recorded behavior: CodeDeploy performs a pre-flight authorization check of the group's serviceRoleArn whenever alarmConfiguration.enabled is true — it must be able to call cloudwatch:DescribeAlarms — and an explicit IAM Deny on that action makes the deployment reach terminal status 'Failed' with errorInformation.code = IAM_ROLE_PERMISSIONS, before any bake-window polling, for BOTH values of ignorePollAlarmFailure (the flag does not excuse an authorization failure). The accompanying errorInformation.message is AWS's fixed sentence "The IAM role <serviceRoleArn> does not give you permission to perform operations in the following AWS service: <serviceName>. Contact your AWS administrator if you need help. If you are an AWS administrator, you can grant permissions to your users or groups by creating IAM policies." — the fixed text is everything outside the two angle-bracketed slots; the variable parts are the deployment group's serviceRoleArn (from group state) and the AWS service that could not be reached, taken from the denied call. The refused deployment must have no effect: the Lambda alias stays on its prior version with no RoutingConfig.AdditionalVersionWeights. Once the grant is restored, the identical deployment must reach 'Succeeded' and move the alias.
Emulator: the group's service role is never consulted. After the shared role's policy is rewritten to Deny cloudwatch:DescribeAlarms/DescribeAlarmHistory, deployments on alarm-enabled groups keep reaching a non-refused outcome, so the check's loop that re-creates a probe deployment until one ends Failed/IAM_ROLE_PERMISSIONS never exits and the whole check is killed by the 180s harness budget ('Check timed out after 180.0s'). No deployment on either twin group is ever marked Failed with IAM_ROLE_PERMISSIONS, so the strict (ignorePollAlarmFailure=false) and lenient (=true) groups behave identically for the wrong reason: neither is ever refused.
Why: this is an overly-permissive divergence. A client validating a least-privilege CodeDeploy service role — or testing that a mis-scoped role is caught before production — gets a green release from a configuration real CodeDeploy refuses, and a client that waits (as real tooling does) for the IAM_ROLE_PERMISSIONS outcome hangs forever instead of seeing a terminal Failed. The two documented meanings of ignorePollAlarmFailure also become unobservable.
Fix: the CreateDeployment / deployment-executor pre-flight authorization step for the group's serviceRoleArn (when alarmConfiguration.enabled is true, evaluate the role's policy for cloudwatch:DescribeAlarms before any alarm polling and independently of ignorePollAlarmFailure), plus the terminal-state and errorInformation authoring that must then mark the deployment Failed with code IAM_ROLE_PERMISSIONS and AWS's message template, while leaving the alias version and its routing config untouched.

## Evidence
Cause 1 — codedeploy.ignore-poll-alarm-failure-decides-whether-an-unpollable-alarm-stops-the-deployment (mismatch):
  Error: Check timed out after 180.0s.
  The check first establishes its positive controls (with cloudwatch:DescribeAlarms GRANTED both the strict and the lenient alarm-enabled group deploy and move the alias), then rewrites the shared service role to Deny cloudwatch:DescribeAlarms/DescribeAlarmHistory and polls a third 'probe' group, re-creating a deployment until one ends Failed with errorInformation.code 'IAM_ROLE_PERMISSIONS'. That refusal never arrives from the emulator, so the wait loop runs until the harness kills the check.
  Expected (AWS): for each of the twin groups (alarmConfiguration.enabled=true, ignorePollAlarmFailure=false and =true), GetDeployment reaches status 'Failed' with errorInformation.code 'IAM_ROLE_PERMISSIONS' and errorInformation.message 'The IAM role <serviceRoleArn> does not give you permission to perform operations in the following AWS service: <serviceName>. Contact your AWS administrator if you need help. If you are an AWS administrator, you can grant permissions to your users or groups by creating IAM policies.' — fixed text as quoted, with <serviceRoleArn> from the deployment group's state and <serviceName> the AWS service whose call was denied; GetAlias still reports the prior FunctionVersion and no RoutingConfig.AdditionalVersionWeights. After the grant is restored, the identical deployments reach 'Succeeded' and the alias advances to the target version.
  Actual (emulator): no deployment is ever refused for the denied grant; no Failed/IAM_ROLE_PERMISSIONS terminal state is produced for either group, and the check never gets past the wait for it.

## Steps to Reproduce
1. Create an IAM role CodeDeploy can assume whose inline policy allows lambda:*, codedeploy:*, cloudwatch:PutMetricData/GetMetricData/GetMetricStatistics, sns:Publish, s3:Get*/List*, iam:PassRole AND cloudwatch:DescribeAlarms/DescribeAlarmHistory.
2. PutMetricAlarm on a namespace that receives no datapoints with TreatMissingData=notBreaching (so the alarm reads OK/INSUFFICIENT_DATA and only its READABILITY varies).
3. CreateDeploymentConfig with a TimeBasedCanary traffic-routing config (10% / 1 minute). Create Lambda functions with versions and an alias, and CreateApplication(computePlatform='Lambda').
4. CreateDeploymentGroup three times on that role and config with alarmConfiguration={enabled: true, alarms: [<the alarm>]}, differing only in ignorePollAlarmFailure: false (strict), true (lenient), false (probe).
5. Positive control: CreateDeployment on the strict and lenient groups shifting the alias to the next version; both reach 'Succeeded' and GetAlias shows the new version.
6. Rewrite the shared role's policy so cloudwatch:DescribeAlarms and cloudwatch:DescribeAlarmHistory are explicitly Denied (everything else unchanged).
7. CreateDeployment on the probe group and poll GetDeployment to a terminal state. Observed: it is never Failed with IAM_ROLE_PERMISSIONS, so a client waiting for that refusal never returns (the check is killed at 180s). Expected: 'Failed' with errorInformation.code 'IAM_ROLE_PERMISSIONS' and AWS's message naming the group's serviceRoleArn and the denied AWS service.
8. Repeat step 7 on the strict and the lenient group: both must be refused identically, with the alias still on its prior version and no AdditionalVersionWeights.
9. Restore the DescribeAlarms grant and re-issue the identical deployments on both groups: both must reach 'Succeeded' and the alias must advance to the target version.
