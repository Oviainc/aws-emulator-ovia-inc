# lambda__s3__stepfunctions: a Lambda handler's stepfunctions.StartExecution never returns an executionArn, so the grant/revoke/restore check never gets past its positive control

> _Note: this issue was identified against the code base at commit `a03774f23cc5bdf1e5b1829d2570750b16716bf1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
One net-new root cause (1 of 1). Related open issue 20261105T081644Z-lambda-s3-stepfunctions-the-lambda-python-runtime-ships.md describes the same family of Lambda-handler-uses-the-AWS-SDK failures for the OTHER checks of this service, but the replay report does NOT mark this check as owned by it (its recorded replay key for this check no longer matches: the check now dies on the suite's own 60s budget with no traceback instead of inside _poll_until), so it is filed here as a surviving failure and that issue is named rather than duplicated.

Cause 1 of 1: an Invoke of a Python-runtime function whose handler calls Step Functions StartExecution through the AWS SDK never produces the StartExecution result document, so a workflow that drives Step Functions from Lambda makes no progress at all.
AWS: Smithy lambda#Invoke is POST /2015-03-31/functions/{FunctionName}/invocations with output members StatusCode (httpResponseCode), FunctionError (httpHeader X-Amz-Function-Error) and Payload (httpPayload). For InvocationType=RequestResponse on a handler that completes normally, AWS answers HTTP 200 with NO X-Amz-Function-Error header and Payload = the JSON document the handler returned. The managed Python runtimes bundle the AWS SDK for Python, so `import boto3` resolves in a bare one-file .zip with no layer, and the SDK picks up the region and the function role's temporary credentials from the runtime environment (AWS_REGION, AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_SESSION_TOKEN). The handler's states:StartExecution therefore actually reaches Step Functions: with the grant in place the Invoke payload carries {"executionArn": "<arn>"} and ListExecutions on the state machine shows exactly one new execution; with states:StartExecution removed from the role the SDK call is refused by Step Functions and the handler reports Error.Code `AccessDeniedException` while ListExecutions is unchanged; after the grant is restored the identical Invoke starts exactly one further, distinct execution. (Smithy: sfn#StartExecution output executionArn/startDate; its refusal class is the service-common AccessDeniedException.)
Emulator: the first Invoke of the positive control never yields a payload containing `executionArn` within the check's polling window, so the check is killed by the suite with `Error: Check timed out after 60.0s` before beats 2-6 (revoke, three consecutive denials, restore) are ever reached. No execution is observable at Step Functions for the granted arm either. The already-open companion issue records the concrete payload for the sibling checks of this same service: HTTP 200 with `X-Amz-Function-Error: Unhandled` and a body whose fixed text is "Unable to import module '<module>': No module named 'boto3'" with `errorType` `Runtime.ImportModuleError` — the module name coming from the function's Handler setting and requestId being per-invocation — i.e. the handler body never runs. Hypothesis: this check fails for that same reason; the only evidence this check itself yields is the timeout, because a handler that returns an error document can never satisfy the `executionArn` predicate.
Why: a client cannot drive Step Functions from Lambda at all. The positive arm produces no execution and no executionArn to describe, and — just as damaging — the negative arm is indistinguishable from the positive one: a revoked states:StartExecution is supposed to come back as `AccessDeniedException` from Step Functions, but the call never reaches Step Functions, so IAM-denial behaviour cannot be observed and an over-permissive emulator cannot be told from a correctly denying one. Every grant/revoke/restore audit built on Lambda-side SDK calls silently stalls instead of reporting.
Fix: the Lambda Invoke data-plane runtime/sandbox for the Python runtimes — it must make the AWS SDK importable on the handler's sys.path and export the region plus the function role's credentials into the handler environment, so the handler's own states:StartExecution is dispatched to the Step Functions data plane and its success document or its AccessDeniedException is returned as the Invoke payload.
Traces: lambda__s3__stepfunctions.lambda-starts-sfn-missing-permission-negative.

## Evidence
Failing check lambda__s3__stepfunctions.lambda-starts-sfn-missing-permission-negative — verdict: mismatch. Reported detail: `Error: Check timed out after 60.0s`.

Expected (AWS): beat 1, with inline policy allowing states:StartExecution on the state machine, Invoke returns HTTP 200, no X-Amz-Function-Error, payload {"executionArn": "arn:aws:states:<region>:<account>:execution:<smName>:<execName>"}; DescribeExecution on it reports status RUNNING or SUCCEEDED and ListExecutions returns exactly 1 execution. Beat 2-4, after the role's inline policy is replaced with a logs-only document, three consecutive Invokes return payload Error.Code `AccessDeniedException` and ListExecutions count is unchanged across that streak. Beat 5-6, after the grant is re-put, the identical Invoke returns a NEW executionArn (different from the control's) and ListExecutions grows by exactly one.

Actual (emulator): the beat-1 poll (`positive control: Lambda starts the execution once granted`, predicate `"executionArn" in r["payload"]`) never succeeds, and the check is terminated by the suite's 60s budget. Beats 2-6 are never exercised. For the sibling checks of the same service, the recorded payload for this emulator behaviour is HTTP 200 + `X-Amz-Function-Error: Unhandled` + {"errorMessage": "Unable to import module '<handler module>': No module named 'boto3'", "errorType": "Runtime.ImportModuleError", "requestId": "<per-invocation id>", "stackTrace": []} — fixed text "Unable to import module '<module>': No module named 'boto3'", with <module> taken from the function's Handler setting and requestId a per-run value that is not part of the requirement.

## Steps to Reproduce
1. iam:CreateRole a role trusted by states.amazonaws.com; sfn:CreateStateMachine name=<sm>, type=STANDARD, definition={"StartAt":"Pass","States":{"Pass":{"Type":"Pass","End":true}}}, roleArn=<that role>.
2. iam:CreateRole a role trusted by lambda.amazonaws.com with an inline policy allowing logs:CreateLogGroup/CreateLogStream/PutLogEvents and states:StartExecution on the state machine ARN.
3. lambda:CreateFunction with Runtime=python3.12, Handler=lambda_function.lambda_handler, Code.ZipFile = a one-file zip containing a handler that does `import boto3` and `boto3.client('stepfunctions').start_execution(stateMachineArn=os.environ['STATE_MACHINE_ARN'], input=json.dumps(event))`, returning {'executionArn': resp['executionArn']} or, on exception, the exception's Error.Code. Environment.Variables.STATE_MACHINE_ARN = <sm arn>. Wait for State=Active.
4. lambda:Invoke it with InvocationType=RequestResponse. Observe: the payload contains no `executionArn` (it is a Runtime.ImportModuleError document with X-Amz-Function-Error: Unhandled), and sfn:ListExecutions on the state machine returns 0 executions, where AWS returns the executionArn and 1 execution.
5. iam:PutRolePolicy replacing the inline policy with the logs-only document and Invoke again: AWS answers with the handler's reported code `AccessDeniedException`; the emulator cannot reach this beat because step 4 never succeeds.
