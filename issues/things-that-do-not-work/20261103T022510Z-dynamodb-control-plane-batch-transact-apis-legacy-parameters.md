# DynamoDB control plane, batch/transact APIs, legacy parameters and resource-based policies diverge from AWS (7 causes)

> _Note: this issue was identified against the code base at commit `6a6bdf627b2774134f5b74f649503c2b12968e19`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTable

## Description
Seven net-new root causes across CreateTable/UpdateTable, the batch and transaction APIs, the legacy (non-expression) parameter family, and resource-based policies. Related open issues exist (20261029T180026Z-dynamodb-createtable-updatetable-putitem-validation-10-missing-or.md, 20261030T060227Z-dynamodb-resource-policy-refusals-name-the-wrong-resource.md, 20261029T180026Z-dynamodb-partiql-resource-policy-arn-addressing-crc32-header.md) but none of them carries the replay keys below.

=== Cause 1 of 7: CreateTable/UpdateTable validation is incomplete and its refusals are worded wrongly ===
AWS: CreateTable models LimitExceededException and ResourceInUseException (Smithy: CreateTable errors = InternalServerError, InvalidEndpointException, LimitExceededException, ResourceInUseException) and refuses schema defects with ValidationException. A GSI KeySchema of HASH,RANGE,HASH is refused naming the position; an index key attribute with no AttributeDefinition is refused with "One or more parameter values were invalid: Some index key attributes are not defined in AttributeDefinitions. Keys: [<every key of the first invalid index, in schema order>], AttributeDefinitions: [<declared names>]"; an INCLUDE projection with no NonKeyAttributes, a VectorIndexes Dimensions above the configured maximum, a Create and a Delete of the same index in one UpdateTable, deleting an absent GSI ("Attempting to delete an index which does not exist: <name>"), AttributeDefinitions that no live key uses, a misspelled StreamViewType, ProvisionedThroughput on a PAY_PER_REQUEST table ("One or more parameter values were invalid: ProvisionedThroughput cannot be specified when BillingMode is PAY_PER_REQUEST") are all refused; and an index reaches ACTIVE and WarmThroughput defaults are reported.
Emulator: create-table-rejects-malformed-requests, create-table-vector-index-validation-rejected, ddb-gsi-create-and-delete-paired-in-one-update-rejected and update-table-gsi-attribute-definitions-track-live-keys all SUCCEED (HTTP 200). Where a refusal does fire the message is emulator-authored: 'Invalid KeySchema for index <n>: The third KeySchemaElement is not a RANGE key type', 'Invalid KeySchema: Some index key attribute have no definition', the undeclared-index-key message lists only the one missing attribute instead of the whole key schema of the first invalid index, 'One or more parameter values were invalid: Neither ReadCapacityUnits nor WriteCapacityUnits can be specified when BillingMode is PAY_PER_REQUEST', 'Requested resource not found: Index not found for table <t>: <idx>' with code ResourceNotFoundException for an absent-GSI delete, and the StreamViewType enum refusal lists the enum members in a different order. ddb-wf-warm-throughput-defaults-applied never sees its index reach ACTIVE.
Why: invalid tables are created (and then behave unlike AWS), and a client cannot branch on the refusal.
Fix: CreateTable/UpdateTable input validation and the table-state machine in the control-plane handlers and table state.
Traces: create-table-gsi-key-schema-hash-after-range-rejected, create-table-rejects-malformed-requests, create-table-vector-index-validation-rejected, ddb-gsi-create-and-delete-paired-in-one-update-rejected, ddb-gsi-create-table-with-an-undeclared-index-key-rejected, vvd-key-schema-attribute-without-definition-rejected, vvd-on-demand-table-with-provisioned-throughput-rejected, update-table-delete-of-an-absent-gsi-rejected, update-table-gsi-attribute-definitions-track-live-keys, update-table-misspelled-stream-view-type-rejected-and-enables-no-stream, update-table-throughput-on-on-demand-table-and-zero-capacity-rejected, ddb-wf-warm-throughput-defaults-applied.

=== Cause 2 of 7: a duplicate CreateTable while the table is still CREATING reports "Table already exists" ===
AWS: CreateTable for a name that exists but is not yet ACTIVE answers ResourceInUseException whose message is "Attempt to change a resource which is still in use: Table is being created: <tableName>" — the fixed sentence with the requested table name substituted. Every loser of a concurrent race gets that same message.
Emulator: every loser gets 'Table already exists: <tableName>'.
Whi: a client that distinguishes "still being created, retry" from "already exists, give up" by message takes the wrong branch; concurrent create-or-get idioms break.
Fix: the CreateTable handler's existing-resource branch, keyed on the stored TableStatus.
Traces: concurrent-create-table-single-winner, vvd-duplicate-table-name-rejected.

=== Cause 3 of 7: the batch APIs diverge in refusal text, member paths, per-slot shape and limits ===
AWS: BatchWriteItem input RequestItems is @length min 1 max 25 (Smithy) and a 26-entry batch is refused with AWS's verbose rendered-request message; an empty RequestItems map is refused naming 'RequestItems'; a RequestItems key that is not a legal table name is refused naming that member path; a wrong-typed or missing key element in a PutRequest/DeleteRequest is refused with "The provided key element does not match the schema" (the same sentence PutItem uses); one oversized or over-nested nested Put refuses the whole call with AWS's sentence; BatchGetItem supports ProjectionExpression and refuses an unaliased reserved word in it with ValidationException; a mixed BatchGetItem with both ProjectionExpression and AttributesToGet on one table is refused. BatchExecuteStatement's successful UPDATE slot echoes TableName.
Emulator: BatchGetItem with ProjectionExpression answers 501 NotImplemented ('operation BatchGetItem with ProjectionExpression is scaffolded but not implemented in this emulator'); the key-defect message is 'One or more parameter values were invalid: Type mismatch for key pk expected: S actual: N' / 'One of the required keys was not given a value'; the over-25 and empty-map refusals carry different text; the table-name defect is reported against 'tableName' with a length constraint; the oversized nested Put message is emulator-authored; validation-messages-are-customer-intelligible and null-false-batchget-mixed-projection-and-query-keyconditions-with-expressions SUCCEED where AWS refuses; and the BatchExecuteStatement UPDATE slot returns an Item map with no TableName.
Why: a batch client cannot tell which slot/table was at fault, loses ProjectionExpression entirely, and writes batches AWS refuses.
Fix: the BatchWriteItem/BatchGetItem/BatchExecuteStatement handlers — per-slot validation, member-path rendering, the ProjectionExpression path, and the per-slot response shape.
Traces: batch-get-item-expression-and-legacy-parameter-rules, batch-request-items-key-not-a-table-name-rejected, batch-request-shape-defects-rejected, batch-write-item-key-defects-message-diverges-from-put-item, batch-write-item-rejects-whole-call-for-one-oversized-nested-put, batch-write-over-25-rejected, ddb-wf-batch-write-item-missing-the-sort-key-rejected-whole, ddb-wf-unaliased-reserved-word-projection-rejected, null-false-batchget-mixed-projection-and-query-keyconditions-with-expressions, validation-messages-are-customer-intelligible, batch-execute-statement-returning-update-vs-delete-rejected.

=== Cause 4 of 7: the legacy (non-expression) parameter family is wrong in both wording and semantics ===
AWS: ScanFilter/QueryFilter/KeyConditions/Expected/ConditionalOperator/AttributesToGet are still served. ConditionalOperator is an enum [AND, OR] and its refusal precedes a nesting-depth defect in the same request; NOT_NULL takes 0 values in AttributeValueList and a value list is refused with "One or more parameter values were invalid: Invalid number of argument(s) for the NOT_NULL ComparisonOperator"; Expected with Exists=true and no Value is refused with AWS's sentence; ConditionalOperator with an empty or absent filter is refused naming every offending parameter; mixing legacy and expression parameters is refused listing ALL the non-expression parameters present ("Non-expression parameters: {ScanFilter, ConditionalOperator}"); and semantically NOT_CONTAINS and NE exclude items that do not carry the attribute, CONTAINS over B compares unsigned bytes, and begins_with with a non-string operand is refused. A request-shape defect is reported before the table lookup.
Emulator: the ConditionalOperator enum refusal interpolates the value and loses precedence; NOT_NULL answers 'One or more parameter values were invalid: NOT_NULL takes 0 value(s) in AttributeValueList, got 1'; Expected answers 'One or more parameter values were invalid: Value must also be used when Exists is true for attribute attr'; ConditionalOperator answers 'ConditionalOperator can only be used together with ScanFilter' / '... together with Expected'; the mixing refusal lists only {ScanFilter}; QueryFilter/EQ answers 501 NotImplemented; NOT_CONTAINS returns items lacking the attribute; CONTAINS 0x00 over B returns nothing; begins_with with a non-string operand succeeds; and a request defect against a missing table answers ResourceNotFoundException instead of ValidationException.
Why: legacy-parameter clients (and the AWS SDK document/legacy layers) get wrong result sets and unparseable refusals.
Fix: the legacy-parameter translation/validation layer shared by Scan, Query, PutItem/UpdateItem/DeleteItem, plus the validation-before-lookup ordering.
Traces: conditionaloperator-enum-error-precedes-nesting-depth-in-legacy-expected, ddb-sfa-legacy-not-null-with-a-value-list-rejected, ddb-sfa-legacy-scan-filter-not-null-and-null-match-the-expression-functions, legacy-expected-exists-value-comparator-matrix, legacy-queryfilter-scanfilter-keyconditions-argument-rules, scan-filter-conditional-operator-document-value-equality, scan-filter-ne-and-not-contains-on-missing-attribute, scan-query-conditional-operator-needs-two-filter-conditions-rejected, scan-query-legacy-and-expression-mixing-names-every-parameter-rejected, write-conditional-operator-needs-two-expected-conditions-rejected, ddb-ss-scan-filter-mixed-with-filter-expression-rejected, scan-filter-begins-with-non-string-operand-rejected, scan-filter-binary-attribute-unsigned-byte-order, request-validation-precedes-missing-table-lookup-rejected, multiple-simultaneous-constraint-violations-rejected.

=== Cause 5 of 7: TransactWriteItems/TransactGetItems misclassify validation versus cancellation and do not name the member path ===
AWS: Smithy models TransactWriteItems with both ValidationException-class request defects and TransactionCanceledException. A request-shape defect (invalid table name, over-deep attribute, over-long ClientRequestToken — ClientRequestToken is @length min 1 max 36 — a Select on an index inside a read transaction) is a top-level ValidationException reported against the member path AWS uses, e.g. "1 validation error detected: Value '<v>' at 'transactItems.<i>.member.put.tableName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9_.-]+"; AWS reports only the masking violation where it masks others; a wrong-typed key or an attempt to update a key attribute is a CANCELLATION (TransactionCanceledException), not a top-level ValidationException; and the first fatal defect reported depends on its class in AWS's documented order.
Emulator: the member path is flattened to 'tableName' with no transactItems.<i>.member.<action> prefix; the over-long-token case reports 2 validation errors where AWS reports only the token one; a wrong-typed Delete key answers ValidationException 'The provided key element does not match the schema' instead of a cancellation; updating a key attribute answers ValidationException instead of TransactionCanceledException; a nesting violation and a missing table are classified in the wrong order (ResourceNotFoundException where AWS answers ValidationException); and TransactGetItems answers 501 NotImplemented where AWS answers a modeled error.
Why: a transaction client cannot locate the offending action, and cannot distinguish "fix your request" from "retry, the transaction was cancelled" — the two have opposite handling.
Fix: TransactWriteItems/TransactGetItems input validation, its member-path renderer, and the validation-versus-cancellation classification in those handlers.
Traces: transact-get-items-top-level-vs-cancellation-error-class, transact-write-items-first-fatal-defect-reported-depends-on-defect-class, transact-write-items-invalid-table-name-names-member-path, transact-write-items-nesting-violation-is-top-level-validation-not-cancellation, transact-write-items-overlength-token-masks-other-violations-rejected, transact-write-items-update-key-and-empty-index-key-rejections, transact-wrong-typed-key-cancels-and-empty-put-key-validates.

=== Cause 6 of 7: key-schema mismatch and empty-secondary-index-key refusals use the wrong sentence ===
AWS: a key element whose type does not match the schema is refused with exactly "The provided key element does not match the schema" (no parameter interpolation), and an update that sets a secondary-index key to the empty string is refused with "One or more parameter values are not valid. The update expression attempted to update a secondary index key to a value that is not supported. The AttributeValue for a key attribute cannot contain an empty string value."
Emulator: the first answers 'One or more parameter values were invalid: Type mismatch for key <k> expected: <T> actual: <U>'; the second answers 'One or more parameter values are not valid. A value specified for a secondary index key is not supported. The AttributeValue for a key attribute cannot contain an empty string value. IndexName: <idx>, IndexKey: <attr>' — a different sentence that additionally leaks index internals AWS does not name here.
Why: the message is the contract; clients and test suites matching AWS's text fail, and the leaked IndexName/IndexKey is not part of AWS's template.
Fix: the key-validation and index-key-validation renderers shared by PutItem/UpdateItem/DeleteItem, BatchWriteItem and TransactWriteItems.
Traces: update-item-key-schema-mismatch, put-batch-write-update-index-key-empty-value-rejected, transact-write-items-empty-index-key-validates-not-cancels, update-item-and-transact-update-empty-gsi-and-lsi-keys-rejected.

=== Cause 7 of 7: resource-based policies — ARN handling, policy validation, not-found wording and the size-limit error class ===
AWS: PutResourcePolicy/GetResourcePolicy/DeleteResourcePolicy take ResourceArn (Smithy: ResourceArnString @length 1..1283) and accept BOTH a table ARN and a stream ARN, holding independent policies for each; an index ARN is refused with "One or more parameter values were invalid: Invalid resource arn provided, only table or stream is accepted. Provided resource arn: <arn>"; an ARN for another region is refused with "One or more parameter values were invalid: Invalid resource Arn: <arn>"; a never-created or deleted table is reported as "Requested resource not found: Table: <tableName> not found" (the table NAME, not the ARN); malformed policy JSON is refused with "One or more parameter values were invalid: Invalid policy document: This policy contains invalid Json"; a policy whose Version is omitted is stored with the IAM default Version 2008-10-17 filled in; and a policy naming a public principal, a foreign-service action, or a nonexistent principal is refused. A document over the 20480-byte limit is refused with ValidationException (recorded behavior; the Smithy model also binds LimitExceededException to PutResourcePolicy, but the recorded refusal for an over-limit document is ValidationException).
Emulator: a stream ARN is refused outright — 'Invalid TableArn: Invalid ResourceArn provided as input arn:aws:dynamodb:<region>:<acct>:table/<t>/stream/<label>' — so a stream can hold no policy at all; the index-ARN and cross-region refusals use that same invented 'Invalid TableArn: Invalid ResourceArn provided as input <arn>' sentence; not-found is reported as 'Requested resource not found: ResourceArn: <full arn> not found'; malformed JSON leaks the parser's own diagnosis ('Resource-based policy is not valid JSON: EOF while parsing a string at line 1 column 234'); an omitted Version is stored verbatim with no Version key; the over-limit document answers LimitExceededException; and the public-principal, foreign-service-action and nonexistent-principal policies are all ACCEPTED (a RevisionId is returned). ddb-rbp-deleted-principal-is-lazily-rewritten-to-its-unique-id-without-revoking-the-grant never completes (60 s harness cap).
Why: stream resource policies are unusable; every refusal message and the size-limit error code differ from AWS; and dangerously over-broad policies AWS rejects are stored and enforced.
Fix: the ResourceArn parser shared by the PutResourcePolicy/GetResourcePolicy/DeleteResourcePolicy handlers, their policy-document validator, the not-found renderer, and the policy state (stream-scoped policies, Version defaulting).
Traces: ddb-rbp-another-regions-table-arn-rejected, ddb-rbp-deleted-table-drops-out-of-the-policy-derivation, ddb-rbp-foreign-service-action-rejected, ddb-rbp-index-arn-as-policy-resource-rejected, ddb-rbp-malformed-policy-json-rejected, ddb-rbp-never-created-table-arn-rejected, ddb-rbp-omitted-policy-version-defaults-to-2008-10-17, ddb-rbp-policy-over-20480-bytes-rejected, ddb-rbp-public-principal-policy-rejected, ddb-rbp-stream-and-table-hold-independent-policies, ddb-rbp-table-action-in-a-stream-policy-rejected, ddb-ltr-resource-policy-naming-a-nonexistent-principal-rejected, ddb-rbp-deleted-principal-is-lazily-rewritten-to-its-unique-id-without-revoking-the-grant.
