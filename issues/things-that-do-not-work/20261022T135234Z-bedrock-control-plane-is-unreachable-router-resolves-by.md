# Bedrock control plane is unreachable: router resolves by SigV4 signing name, so every request is refused 500 AmbiguousService and no behavioral check can run

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateGuardrail

## Description
Cause 1 of 1 — the emulator's request router resolves an incoming request to an emulated service by its SigV4 signing name, and the whole Bedrock family shares one signing name, so resolution is ambiguous and NOTHING on the Bedrock control plane is dispatched. Every one of the 62 behavioral checks listed in trace_ids fails on its first Bedrock call with the same emulator-invented refusal.

AWS: Smithy (smithy_query service_info on services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json) — service AmazonBedrockControlPlaneService, version 2023-04-20, sdkId 'Bedrock', awsService.endpointPrefix 'bedrock', sigv4Name 'bedrock', protocols ['restJson1'], 108 bound operations. The companion data-plane model (services/service-com-amazonaws-bedrockruntime-amazonbedrockfrontendservice/...) reports sdkId 'Bedrock Runtime', endpointPrefix 'bedrock-runtime' and the SAME sigv4Name 'bedrock'. So the signing name is explicitly NOT a unique key across these services, while the endpoint prefix is. AWS itself has no 'AmbiguousService' error: each Bedrock operation answers either its modeled success status (e.g. CreateGuardrail POST /guardrails @http code 202; Converse/InvokeModel 200) or a modeled error from its own error list (ValidationException 400, ResourceNotFoundException 404, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500). The control-plane model's service-common error set is ['InternalServerException'] only.

Emulator: every request signed for signing name 'bedrock' is answered HTTP 500 with header x-amzn-errortype 'AmbiguousService', content-type 'application/x-amz-json-1.1', and body {"__type":"AmbiguousService","message":"6 emulated services all claim requests for 'bedrock': bedrock, bedrock, bedrock, bedrock, bedrock, bedrock; the request is rejected rather than served by an arbitrary one"} (that message is an example of the router's text; the 500 status and the 'AmbiguousService' code are the divergence). This is uniform across control-plane and data-plane operations the bedrock checks call: CreateGuardrail, GetGuardrail, DeleteGuardrail, GetModelInvocationLoggingConfiguration, ListFoundationModels, Converse, ConverseStream, InvokeModel, InvokeModelWithResponseStream, CreateKnowledgeBase. A second defect is visible in the same response: this service speaks restJson1, whose responses — errors included — carry content-type 'application/json', but the refusal is serialized as 'application/x-amz-json-1.1'.

Why: no client can use Bedrock at all. Worse than being unavailable, the refusal is a retryable 500 with an error code no SDK models, so botocore exhausts its retries ('reached max retries: 3') and then surfaces a server fault for requests that can never succeed; code that branches on ValidationException / ResourceNotFoundException / AccessDeniedException never sees them, and guardrail, model-invocation-logging and CloudFormation-deployed-guardrail flows cannot even reach their setup step.

Fix: the request router / service-resolution layer — dispatch on the endpoint prefix (host) and the URI path rather than on the SigV4 signing name, so 'bedrock' and 'bedrock-runtime' (and the bedrock-agent / bedrock-data-automation families) resolve distinctly; the same layer must serialize its own refusals with the resolved service's protocol content-type. Only after that can the individual Bedrock handlers, their validation and their serializers be graded.

Traces: all 62 check ids in trace_ids. Representative: bedrock.apply-guardrail-response-shape (CreateGuardrail), bedrock.bedrock-model-invocation-logging-records-the-prompt-and-the-completion (GetModelInvocationLoggingConfiguration), bedrock.e2e-fine-tune-deploy-invoke-teardown (ListFoundationModels), bedrock.converse-basic-response-shape (Converse), bedrock.invoke-model-basic (InvokeModel). The five cross-service ids (bedrock__bedrock-runtime.*, bedrock__cloudwatch.*) carry composite service tokens whose leading service is bedrock; each fails on a bedrock-family call refused by the router, which is why they are bundled here.
