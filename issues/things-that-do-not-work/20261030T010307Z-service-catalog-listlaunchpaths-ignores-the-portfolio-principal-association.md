# service-catalog ListLaunchPaths ignores the portfolio-principal association: a product becomes launchable on the product association alone

> _Note: this issue was identified against the code base at commit `d5912a3a34a2e2faa23a606635408f9fea83c969`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListLaunchPaths

## Description
One net-new root cause in the emulated AWS Service Catalog service (sdkId servicecatalog, crate services/service-com-amazonaws-servicecatalog-aws242servicecatalogservice). The service IS stood up and answering — its bootstrap issue is resolved and other checks in this suite get real responses from it — so this is a fidelity divergence, not a bootstrap gap.

Cause 1 of 1: ListLaunchPaths resolves a launch path from the product-portfolio association alone, with no portfolio-principal association for the calling principal.

AWS: Smithy: ListLaunchPaths (input ProductId: Id, required, @length 1..100, pattern ^[a-zA-Z0-9_\-]*$; PageSize 0..20 default 0; PageToken @length 0..2024; output LaunchPathSummaries + NextPageToken; errors InvalidParametersException and ResourceNotFoundException, both errorKind client, httpError 400). The operation's own modeled documentation states the rule this issue is about: "A path describes how the user gets access to a specified product and is necessary when provisioning a product. ... A path is dependent on a specific product, porfolio, and principal", with the note "When provisioning a product that's been added to a portfolio, you must grant your user, group, or role access to the portfolio" (Granting users access, Service Catalog User Guide). So launchability is a TWO-key gate: AssociateProductWithPortfolio puts the product in the portfolio, and AssociatePrincipalWithPortfolio grants the calling principal access through it; only then does a path exist, and the path's Id/Name are the granting portfolio's id and DisplayName. Until the principal half exists, ListLaunchPaths for that ProductId resolves no path: recorded behavior (measured against real AWS in us-west-2, documented in the check header) is a refusal with HTTP 400 and error code ResourceNotFoundException — the check treats that code as "not launchable" rather than "no such product" — and it kept answering that code for 120s of polling after the product association succeeded, then resolved a path in 0.1s once AssociatePrincipalWithPortfolio was called for the caller. The gate is also LIVE state, not a latch: after DisassociatePrincipalFromPortfolio (modeled: PortfolioId + PrincipalARN required, errors InvalidParametersException/ResourceNotFoundException, 400) the product must stop being launchable and ListLaunchPaths must go back to refusing. The error message for the refusal is not pinned by the model or the recording beyond the code; the requirement here is the status 400 and the code ResourceNotFoundException, whose fixed text per the model is the shape's documentation "The specified resource was not found." and whose only variable part in any Service Catalog not-found message is the requested resource id taken from the request.

Emulator: ListLaunchPaths derives the path set purely from state.products[ProductId].portfolio_ids and never consults the portfolio's stored principal associations. The handler says so in a comment at services/service-com-amazonaws-servicecatalog-aws242servicecatalogservice/src/ops/list_launch_paths.rs: "the principal half of 'a path is dependent on a specific product, porfolio, and principal' cannot be evaluated here ... The paths reported are therefore the product-portfolio ones, unfiltered by the stored `Portfolio::principals`; a path that exists for one principal is reported to every caller." In replay, immediately after AssociateProductWithPortfolio and with NO AssociatePrincipalWithPortfolio call made, ListLaunchPaths answered HTTP 200 with one LaunchPathSummary (Id = the portfolio id, Name = the portfolio DisplayName, ConstraintSummaries [], the portfolio's Tags) where AWS answers 400 ResourceNotFoundException. The emulator does hold the state needed to decide this: Portfolio::principals is a BTreeMap<principal ARN, PrincipalAssociation> populated by AssociatePrincipalWithPortfolio and removed by DisassociatePrincipalFromPortfolio (services/.../src/state.rs).

Why: the emulator is over-permissive on an authorization gate. A client that relies on AWS's two-key behavior gets the opposite verdict: code that probes ListLaunchPaths to decide whether a product is launchable (or to pick a PathId before ProvisionProduct) believes an unshared product is launchable, so the negative branch — handling ResourceNotFoundException and then calling AssociatePrincipalWithPortfolio — is never exercised and a provisioning attempt that AWS refuses looks viable. Symmetrically, a client that revokes access with DisassociatePrincipalFromPortfolio and then re-reads ListLaunchPaths to confirm the revocation sees the path still present, so a revocation it believes it made reads as ineffective-but-silent. Every caller also sees every other principal's paths, which leaks the catalog's portfolio grants across principals.

Fix: the path-resolution step of the ListLaunchPaths handler (services/service-com-amazonaws-servicecatalog-aws242servicecatalogservice/src/ops/list_launch_paths.rs, the block that builds `paths` from product.portfolio_ids) must intersect the product's portfolio associations with the portfolios whose Portfolio::principals contains the CALLING principal, and refuse with ResourceNotFoundException (400) when that intersection is empty — the same refusal it already produces for a product in no portfolio. That requires resolving the request's signing identity to a principal ARN (the seam the handler's comment says it lacks): the caller identity available to the request, as the emulator's STS GetCallerIdentity derives it from the SigV4 credential's access key id, including the assumed-role session ARN form, matched against the stored association ARNs (PrincipalType IAM exact-match, IAM_PATTERN by pattern). The same filter must be applied consistently to whatever else derives launchability from this state (DescribeProduct's LaunchPaths / HasDefaultPath), so two responses of the service do not contradict each other.

Traces: service-catalog.launch-path-requires-product-and-principal-association (behavioral suite simparity-behavioral-aws-v1, group launch-paths).

No open issue covers this: the open service-catalog issues are unimplemented-stub issues for CopyProduct, AssociateTagOptionWithResource, DescribeProvisioningParameters and ProvisionProduct, and 20261029T191224Z-servicecatalog-service-catalog-portfolio-and-product-operations-diverge-from.md, which covers AssociatePrincipalWithPortfolio/CreateProduct/DescribeProductAsAdmin message, validation and metadata defects and says nothing about launch-path resolution.
