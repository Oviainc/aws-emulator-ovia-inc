# CloudFormation does not recognize or provision the AWS::EventsV2::* resource types, so every EventBridge v2 template is refused at CreateStack

> _Note: this issue was identified against the code base at commit `3b4b4e2df28997ae7cbb85154b0c83cf06a43ef8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause in the CloudFormation emulator, grounded in the two behavioral deploy checks that submit EventBridge v2 templates. The suite lists them under the composite headings `cloudformation__eventbridgev2` and `cloudformation__eventbridgev2__iam__sqs`; the diverging call in both is CloudFormation's own CreateStack, so both are filed here as one cause. Both failing checks must be re-replayed before this is closed.

Cause 1 of 1 — CreateStack refuses a template that declares AWS::EventsV2::EventBus / AWS::EventsV2::EventSource / AWS::EventsV2::ResourcePolicy / AWS::EventsV2::Subscriber as "Unrecognized resource types", so no EventBridge v2 resource can ever be deployed from a stack.
AWS: recorded behavior only for the CloudFormation side — the service's Smithy model enumerates no resource types at all (CreateStack declares only AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException; the recognised-type set comes from the published resource reference, which is exactly how this emulator's own `src/state/resource_types.rs` module documents it). The recordings show AWS ACCEPTING both templates: CreateStack answers a StackId, the stack reaches CREATE_COMPLETE for the well-formed template, `Ref` on each resource resolves to that resource's own ARN (and on AWS::EventsV2::ResourcePolicy to the bus ARN, its primary identifier), `Fn::GetAtt` resolves EventBus.State, EventSource.State, ResourcePolicy.RevisionId and Subscriber.BusName, and the resources exist in EventBridge v2 itself — ListEventBuses/DescribeEventBus, ListEventSources/DescribeEventSource (Configuration read back as declared), GetResourcePolicy (declared document plus the same RevisionId) and ListSubscribers/DescribeSubscriber (InvokeConfiguration.TargetArn/RoleArn, State RUNNING) all agree with the stack's outputs; DeleteStack removes them in EventBridge v2 too, each subsequent read refusing with that service's own not-found error. The owning APIs those deployments call are modelled in EventBridgeV2 (CreateEventBus, CreateEventSource, PutResourcePolicy, CreateSubscriber — each with Name/EventBusArn/Configuration members matching the template property names). For the negative template, AWS also accepts the submission and fails it in-stack: the stack settles ROLLBACK_COMPLETE and DescribeEvents reports one VALIDATION_ERROR OperationEvent with ValidationName PROPERTY_VALIDATION, ValidationStatus FAILED, ValidationFailureMode FAIL, ValidationPath "/Resources/EventSource/Properties/Configuration" and ValidationStatusReason "#/Configuration: #: 2 subschemas matched instead of one" — that reason is fixed text for the one-of violation on EventSourceConfiguration apart from the member path it names (`#/Configuration`), and nothing reaches EventBridge v2 (no bus carries the rejected template's name).
Emulator: CreateStack is refused outright, before any stack exists, with HTTP 400 ValidationError and the message "Template format error: Unrecognized resource types: [AWS::EventsV2::EventBus, AWS::EventsV2::EventSource]" for the two-resource template and "Template format error: Unrecognized resource types: [AWS::EventsV2::EventBus, AWS::EventsV2::EventSource, AWS::EventsV2::ResourcePolicy, AWS::EventsV2::Subscriber]" for the four-resource one. In that message "Template format error: Unrecognized resource types: [...]" is the fixed text and the bracketed list is the set of types the submitted template declared. The refusal is correct machinery pointed at the wrong set: the recognised catalogue AWS_RESOURCE_TYPES carries the EventBridge v1 namespace only ("AWS::Events::ApiDestination", "AWS::Events::Archive", "AWS::Events::Connection", "AWS::Events::EventBus", "AWS::Events::EventBusPolicy", "AWS::Events::Rule") and has no AWS::EventsV2 entry at all, and the per-type halves are missing with it — `provisioner_for` has an EventsRule arm and no EventsV2 arm, so even once the types are catalogued they would deploy declared-only, with no create in EventBridge v2, no published return values for Ref/GetAtt, and no delete on stack deletion.
Why: a client whose template provisions an EventBridge v2 bus, event source, bus resource policy or subscriber cannot deploy it against the emulator at all — CreateStack never returns a StackId, so there is nothing to wait on, no outputs to read and no rollback to inspect. Infrastructure-as-code that works in a real account fails at submission here, which inverts the safe direction of this check: the emulator refuses what AWS deploys. The negative check is equally unreachable: a client that relies on CloudFormation accepting the submission and reporting the property-validation failure as an in-stack VALIDATION_ERROR event (with the stack rolled back and nothing created in EventBridge v2) instead sees a client-side CreateStack error, so its rollback and validation-event handling is never exercised.
Fix: three places in the CloudFormation crate, all per-resource-type and none in the deployment algorithm itself — (1) the recognised-type catalogue so a template may declare the four AWS::EventsV2 types; (2) the per-type published return values/primary identifiers used for Ref and Fn::GetAtt (EventBus.State, EventSource.State, ResourcePolicy.RevisionId with the bus ARN as the policy's Ref, Subscriber.BusName), so the stack's outputs are computed rather than left unevaluated; (3) the per-type provisioner arms that create, update and delete each type through EventBridgeV2's own CreateEventBus/CreateEventSource/PutResourcePolicy/CreateSubscriber (and their deletes) over the existing in-process callback, including the property validation of EventSourceConfiguration's mutually exclusive variants that must fail the resource in-stack and roll the stack back. File and line citations are under Traces. Note the four-resource check additionally needs EventBridgeV2 CreateSubscriber, which is an unimplemented scaffold stub tracked by the already-open issue 20261104T183027Z-eventbridgev2-createsubscriber-stub.md; that issue does not cover anything described here, and this issue does not cover that stub.

## Steps to Reproduce
1. git_clone the repo and run run_behavioral_suite (it builds and boots the emulator).

Check cloudformation__eventbridgev2__iam__sqs.deploy-eventsv2-eventsource-conflicting-configuration-rejected:
  a. CreateStack with a template whose Resources declare {EventBus: AWS::EventsV2::EventBus (Name), EventSource: AWS::EventsV2::EventSource (Name, EventBusArn={Ref: EventBus}, Configuration with BOTH AwsServiceEventsConfiguration and PartnerEventsConfiguration)} and Outputs Ref-ing both.
  b. AWS accepts the submission and answers a StackId; the emulator refuses the call with HTTP 400 ValidationError "Template format error: Unrecognized resource types: [AWS::EventsV2::EventBus, AWS::EventsV2::EventSource]".
  c. Against AWS the stack then settles ROLLBACK_COMPLETE, DescribeEvents reports the single PROPERTY_VALIDATION/FAILED/FAIL row for /Resources/EventSource/Properties/Configuration with reason "#/Configuration: #: 2 subschemas matched instead of one", and ListEventBuses(NamePrefix=<bus name>) is empty. Submitting the same template with ONE Configuration variant reaches CREATE_COMPLETE and DescribeEventSource reads back the declared Configuration.

Check cloudformation__eventbridgev2__iam__sqs.deploy-eventsv2-bus-source-policy-subscriber-round-trip-and-delete:
  a. CreateStack(Capabilities=['CAPABILITY_IAM']) with a template declaring AWS::EventsV2::EventBus, AWS::EventsV2::EventSource, AWS::EventsV2::ResourcePolicy and AWS::EventsV2::Subscriber beside the SQS queue and IAM role the subscriber invokes.
  b. AWS accepts it, reaches CREATE_COMPLETE, and each Ref/GetAtt output matches what EventBridge v2 reports for the resource; the emulator refuses the call with HTTP 400 ValidationError "Template format error: Unrecognized resource types: [AWS::EventsV2::EventBus, AWS::EventsV2::EventSource, AWS::EventsV2::ResourcePolicy, AWS::EventsV2::Subscriber]".
  c. DeleteStack and confirm every resource is gone in EventBridge v2, not only in CloudFormation.
