# kms__lambda: a handler's boto3.client("kms") dies with UnknownServiceError, so neither a KMS grant nor a key-policy Deny is ever exercised from inside an invocation

> _Note: this issue was identified against the code base at commit `5678b2d659e23eeff4b2f39316abc675f4291395`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Cause 1 of 1: the AWS SDK installed in the emulator's managed python Lambda execution environment carries a truncated botocore service-model data directory that has no `kms` model, so a handler's `boto3.client("kms")` call raises botocore.exceptions.UnknownServiceError before any request leaves the sandbox. Every in-function KMS authorization contract — a grant that authorizes kms:Decrypt for the execution role, its withdrawal by RevokeGrant, and an explicit key-policy Deny overriding an identity-policy Allow — is therefore unobservable. Failing check ids for this cause (2): kms__lambda.kms-grant-authorizes-lambda-decrypt-then-revoke-denies, kms__lambda.kms-key-policy-deny-overrides-lambda-identity-allow.

AWS: recorded behavior only for the CONTENTS of the managed runtime (the Smithy model describes the Invoke wire shape, not the execution environment). AWS's managed python3.x runtimes ship a current boto3/botocore whose data directory holds the service model of every public AWS service, so inside a handler `boto3.client("kms")` always constructs and the call is dispatched to KMS with the execution role's credentials; the handler then observes KMS's own answer. Smithy (lambda Invoke -> InvocationResponse, http {method: POST, uri: /2015-03-31/functions/{FunctionName}/invocations, code: 200}): StatusCode is httpResponseCode, FunctionError is the header X-Amz-Function-Error, Payload is the httpPayload blob — a successful RequestResponse invocation answers HTTP 200 with X-Amz-Function-Error ABSENT and Payload equal to exactly the JSON the handler returned. Smithy (kms Decrypt, input CiphertextBlob/KeyId/EncryptionContext/GrantTokens; modelled errors DisabledException 409, KMSInvalidStateException 409, NotFoundException 404, InvalidCiphertextException 400, IncorrectKeyException 400): an AUTHORIZATION refusal is not in that list — KMS reports it with the service-common AccessDeniedException (HTTP 400, Error.Code `AccessDeniedException`). Its message is templated: the fixed text is `User: ` + ` is not authorized to perform: ` + ` on resource: ` plus the reason clause, and the variable parts come from the request and state — the caller's assumed-role session ARN (arn:aws:sts::<account>:assumed-role/<execution-role-name>/<function-name>), the action `kms:Decrypt`, and the key ARN from KeyId. The reason clause states which policy produced the decision: `because no identity-based policy allows the kms:Decrypt action` for a role with no kms actions and no grant, and `with an explicit deny in a resource-based policy` when the key policy carries an explicit Deny for that principal. So on AWS the expected handler payloads are: refused with AccessDeniedException before CreateGrant, the exact plaintext while the grant is live, AccessDeniedException again after RevokeGrant, and — for the key-policy check — AccessDeniedException with the explicit-deny clause on the denied key while kms:Encrypt on the same key and kms:Decrypt on the untouched control key still succeed.

Emulator: Invoke answers HTTP 200 and the handler runs (`import boto3` succeeds), but the client is never built. In kms-grant-authorizes-lambda-decrypt-then-revoke-denies the handler's except-branch reports the botocore exception type and the invocation payload comes back as {'denied': True, 'code': 'UnknownServiceError'} where AWS returns {'denied': True, 'code': 'AccessDeniedException'}; botocore's message for this failure is `Unknown service: '<service-name>'. Valid service names are: <comma-separated list of the models the runtime actually has>` — fixed text as quoted, with the requested service id (`kms`) coming from the boto3.client call and the list being merely the models the runtime image contains (an already-filed sibling cause under another grouping recorded that list as sqs, events, eventbridge, dynamodb). No KMS HTTP request leaves the sandbox, so neither the grant nor the key policy is consulted. kms-key-policy-deny-overrides-lambda-identity-allow shows the SAME cause as a hang: its handler encrypts then decrypts through the same client, so its baseline poll (`_poll_until(..., timeout_s=120.0, interval_s=5.0)`, waiting for decrypt_denied is False on both keys) can never be satisfied and the run is killed at the harness's cap — 'Check timed out after 60.0s'. Hypothesis: the unsatisfiable predicate is exactly the unconstructable client; it is listed here as a second example of the one cause, not a separate defect.

Why: a client gets a Lambda that cannot talk to KMS at all. The positive arm never recovers the plaintext a live grant authorizes, and the negative arms are worse than failed — an unauthorized decrypt surfaces a botocore UnknownServiceError instead of KMS's AccessDeniedException, so an operator cannot tell an IAM/key-policy denial from a broken runtime image and concludes their grant or key policy is wrong when neither is. Bulk revocation controls (RevokeGrant, an explicit key-policy Deny) cannot be verified against the emulator.

Fix: the Lambda service's execution-environment component — the part that assembles the python runtime filesystem for the sandbox and puts boto3/botocore on the handler's import path (the Invoke path of services/service-com-amazonaws-lambda-awsgirapiservice and the python runtime bundle it loads). It must install a botocore whose data directory carries the full set of service models (at minimum every service the emulator serves), as the managed python3.x runtime does, instead of a small subset. The Invoke response wire shape itself is correct. Behind it, the KMS Decrypt authorization path must then consult grants and the key policy for the calling role — the enforcement side is described by the related open issue named below.

Related open work that does NOT cover these checks (the suite marked neither as owned): 20261105T111951Z-kms-lambda-environment-variable-kms-enforcement-and-kms.md lists both check ids but under the earlier symptom 'handler faulted instead of returning a result' (Runtime.ImportModuleError, boto3 absent), and 20261106T131020Z-bedrock-agent-runtime-lambda-s3vectors-the-lambda-python.md records this same truncated-catalog cause under another service grouping. Adding boto3 alone did not close these checks: the failure has moved to the botocore data catalog.

Traces: the 2 failing check ids above; see trace_ids.

## Evidence
Expected (AWS): lambda Invoke(InvocationType=RequestResponse) of a python3.x function whose handler does `import boto3`, `kms = boto3.client("kms")` and `kms.decrypt(CiphertextBlob=..., KeyId=<key-arn>, EncryptionContext={'tenant':'alpha'})` -> HTTP 200, no X-Amz-Function-Error, Payload = the handler's own JSON reporting KMS's outcome: {'denied': True, 'code': 'AccessDeniedException'} while the execution role has no kms action and no grant; {'denied': False, 'plaintext': '<the exact plaintext>'} while a CreateGrant naming the role as GranteePrincipal with Operations=['Decrypt'] is live; {'denied': True, 'code': 'AccessDeniedException'} again after RevokeGrant. For the key-policy check: after PutKeyPolicy adds an explicit Deny of kms:Decrypt for the function's role, the denied key reports code 'AccessDeniedException' with message 'User: arn:aws:sts::<account>:assumed-role/<role-name>/<function-name> is not authorized to perform: kms:Decrypt on resource: <denied-key-arn> with an explicit deny in a resource-based policy', no plaintext, kms:Encrypt on the same key still succeeding, and the control key still decrypting.

Actual (emulator):
- kms__lambda.kms-grant-authorizes-lambda-decrypt-then-revoke-denies: AssertionError: expected AccessDeniedException before the grant, got {'denied': True, 'code': 'UnknownServiceError'} (check source line 332: `assert before.get("code") == "AccessDeniedException"`). The handler caught botocore.exceptions.UnknownServiceError from client construction, so no kms:Decrypt was ever attempted; the grant/revoke arms are never reached.
- kms__lambda.kms-key-policy-deny-overrides-lambda-identity-allow: 'Check timed out after 60.0s' — its first poll waits (timeout_s=120.0, interval_s=5.0) for the same handler body to report decrypt_denied False on both keys, which the unconstructable client makes unsatisfiable.

Diverging error identity: Error.Code 'UnknownServiceError' (a botocore client-construction failure reported inside the handler payload) instead of KMS's 'AccessDeniedException'. Fixed text of the botocore message: "Unknown service: '<service-name>'. Valid service names are: <installed model list>"; its variable parts are the service id the handler asked for ('kms') and the list of models the runtime image happens to contain. Generated key ids/ARNs, role and function names, request ids and timestamps in these payloads vary per run and are not requirements.

## Steps to Reproduce
1. kms CreateKey (symmetric, ENCRYPT_DECRYPT) and kms Encrypt a known plaintext under it with EncryptionContext {'tenant':'alpha'}.
2. iam CreateRole trusting lambda.amazonaws.com with an inline policy allowing ONLY logs:CreateLogGroup/CreateLogStream/PutLogEvents (no kms action).
3. lambda CreateFunction Runtime=python3.12, Handler=lambda_function.lambda_handler, Code.ZipFile = a zip whose lambda_function.py is:
       import base64, os, boto3
       kms = boto3.client("kms")
       def lambda_handler(event, context):
           try:
               r = kms.decrypt(CiphertextBlob=base64.b64decode(event["ciphertext_b64"]), KeyId=os.environ["KEY_ARN"], EncryptionContext=event["encryption_context"])
               return {"denied": False, "plaintext": r["Plaintext"].decode()}
           except Exception as exc:
               err = getattr(exc, "response", None) or {}
               return {"denied": True, "code": err.get("Error", {}).get("Code", type(exc).__name__)}
   with Environment.Variables.KEY_ARN = the key ARN; wait for State == Active.
4. lambda Invoke(InvocationType=RequestResponse) with the base64 ciphertext and encryption context. Observe HTTP 200 whose Payload is {'denied': True, 'code': 'UnknownServiceError'} instead of {'denied': True, 'code': 'AccessDeniedException'} — the handler never reached KMS.
5. kms CreateGrant(KeyId=<key-arn>, GranteePrincipal=<role-arn>, Operations=['Decrypt'], Constraints.EncryptionContextSubset={'tenant':'alpha'}) and Invoke again: the payload is unchanged, so the grant is never observable; RevokeGrant likewise.
6. For the hang manifestation: give the role kms:Encrypt+kms:Decrypt on two keys, PutKeyPolicy an explicit Deny of kms:Decrypt for the role on one of them, and poll Invoke every 5s for the handler to report decrypt_denied on the denied key and success on the control key — the predicate never becomes true and the run is killed at the 60s cap.
7. Re-replay kms__lambda.kms-grant-authorizes-lambda-decrypt-then-revoke-denies and kms__lambda.kms-key-policy-deny-overrides-lambda-identity-allow to confirm.
