# ECR Public: repositoryUri and registryUri are minted on the hard-coded public.ecr.aws host instead of an address the emulator answers on

> _Note: this issue was identified against the code base at commit `d115796fe5713602f1adc3e09d553e6de30aa6e5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateRepository

## Description
Wire replay of simparity-wire-aws-v1 against this checkout: 12 fixtures replayed, 138/165 steps passed (score 83.6%), 27 steps mismatched in 6 clusters, all on ecr-public. The emulator IS serving (/__admin/health 200, every one of these steps answers HTTP 200 with a correctly shaped body) and ecr-public is bootstrapped (service-com-amazonaws-ecrpublic-spencerfrontendservice; get_bootstrap_status reports NO pending bootstrap issues), so these are fidelity findings, not a bootstrap gap. One of the 6 clusters (DescribeImages, ImageDetail.repositoryType) is marked OWNED by 20261031T173815Z-ecr-public-describeimages-omits-imagedetail-repositorytype-so-every.md and is excluded. The remaining 5 clusters are bundled here because they are ONE root cause reached through four operations: every URI this service publishes is built from a compiled-in real-AWS host rather than from the address the emulator is reached on, so the replay checker rejects each of them with 'host_not_own'.

THE SHARED FAULT. Smithy models both URI members on the same shape: Repository$repositoryUri -> Url, documented 'The URI for the repository. You can use this URI for container image push and pull operations', and Registry$registryUri -> Url (@required), documented 'The URI of a public registry. The URI contains a universal prefix and the registry alias'. Both are therefore published, dereferenceable addresses, not opaque labels: a client is told to point `docker push`/`docker pull` at repositoryUri. On real AWS the universal prefix is public.ecr.aws because that is the host that serves the registry; the alias segment is an opaque per-account value the service mints ('a6g2m9v2' in the recordings). For an emulator the requirement that carries over is the one the host encodes: the URI must name a scheme/host/port the EMULATOR answers on, so that a client of the emulator that pushes or pulls at the advertised URI reaches the emulator. The registry alias and the path shape are free per-run values and are NOT the defect; the fixed host is. This is the same class of defect as open issue 20261109T130943Z-ecr-public-putrepositorycatalogdata-mints-logourl-on-the-real.md, which covers catalogData.logoUrl only — repositoryUri and registryUri are a different set of members on different operations and are not covered by it, nor by any other open ecr-public issue.

In this checkout the host and the alias are compiled in: services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/state.rs:133 declares `pub const GALLERY_HOST: &str = "public.ecr.aws"` and :143 `pub const DEFAULT_REGISTRY_ALIAS: &str = "emulator"`; CreateRepository stores the URI once at src/ops/create_repository.rs:242 (`uri: store.repository_uri(&input.repository_name)`), and the module header of state.rs says that stored Repository is 'read back verbatim by every reporting operation' — which is exactly why one wrong base leaks out of four operations.

=== Cause 1 of 5: CreateRepository reports a repository.repositoryUri on the real gallery host ===
AWS: Smithy CreateRepository -> CreateRepositoryResponse.repository -> Repository.repositoryUri (target Url), 'The URI for the repository. You can use this URI for container image push and pull operations.' Recorded behavior for the URI's composition: <registry-host>/<registryAlias>/<repositoryName>, HTTP 200, no error involved. Requirement for the emulator: the host:port component must be one the emulator serves on, so the advertised push/pull target resolves to the emulator.
Emulator: answers 200 and reports repositoryUri 'public.ecr.aws/emulator/<repositoryName>' — the literal real-AWS host. The checker's verdict is `$.repository.repositoryUri: host_not_own` (expected 'public.ecr.aws/a6g2m9v2/<repositoryName>' from the recording, got 'public.ecr.aws/emulator/<repositoryName>'). Of the observed string, 'public.ecr.aws' is fixed emulator output and is the defect; '<repositoryName>' comes from the request and the alias segment is a per-run value.
Why: a client that creates a repository and then pushes to the URI the API handed it does not reach the emulator at all. It either fails to resolve/connect, or — worse — reaches the real public.ecr.aws and pushes to or reads from an unrelated registry, so a build or test passes/fails for reasons entirely outside the emulated account. The create call reports success with a well-formed URI, so the defect only surfaces later, at the registry fetch.
Fix: the repository-URI minting in the ecr-public state module (the `repository_uri` builder that CreateRepository stores through) must compose the URI from the emulator's own advertised scheme/host/port instead of the compiled-in GALLERY_HOST constant, and the emulator's front door must claim the registry paths under it.
Traces: api-image-layer-upload-and-push-workflow#setup#1 (cluster of 8: also api-multi-repository-isolation#setup#1, api-multi-repository-isolation#setup#2, api-repository-creation-catalog-lifecycle#setup#1, api-repository-policy-management#setup#1, api-repository-uri-arn-alias-scoped-regionless#task#2, api-repository-uri-arn-alias-scoped-regionless#task#4, api-resource-tagging-workflow#setup#1).

=== Cause 2 of 5: DeleteRepository echoes the same unreachable repositoryUri ===
AWS: Smithy DeleteRepository -> DeleteRepositoryResponse.repository -> Repository.repositoryUri, same member and same documentation as cause 1; the deleted repository is echoed back, HTTP 200.
Emulator: answers 200 but the echoed `$.repository.repositoryUri` is again 'public.ecr.aws/emulator/<repositoryName>' — `host_not_own`.
Why: a client that logs or asserts on the deleted repository's URI (teardown bookkeeping, IaC state reconciliation) records an address that is not the emulator's, so the URI it saw at create time and the one it sees at delete time are both unusable and indistinguishable from a real-AWS registry.
Fix: same single URI composition as cause 1 — DeleteRepository serves the stored StoredRepository verbatim, so correcting the minting fixes this echo; nothing in the DeleteRepository handler needs its own base.
Traces: api-image-layer-upload-and-push-workflow#teardown#17 (cluster of 8: also api-multi-repository-isolation#task#12, api-multi-repository-isolation#teardown#15, api-repository-creation-catalog-lifecycle#teardown#8, api-repository-deletion-and-non-empty-error-paths#task#14, api-repository-deletion-and-non-empty-error-paths#task#23, api-repository-policy-management#teardown#11, api-resource-tagging-workflow#teardown#11).

=== Cause 3 of 5: DescribeRepositories reports the unreachable repositoryUri for a multi-repository page ===
AWS: Smithy DescribeRepositories -> DescribeRepositoriesResponse.repositories -> RepositoryList of Repository, each carrying repositoryUri as above; paginated (maxResults 1..1000, nextToken). HTTP 200.
Emulator: answers 200 with the right repositories but every element's URI is on the fixed host: `$.repositories[0].repositoryUri` and `$.repositories[1].repositoryUri` are both reported `host_not_own` ('public.ecr.aws/emulator/<repositoryName>' for each). Only the URI host key is flagged; the repository identities themselves are accepted.
Why: listing is how a client discovers push targets it did not create itself (a deploy step that enumerates repositories and then pulls from each). Every discovered target points off the emulator, so a whole enumerate-then-pull workflow is broken at once rather than one repository at a time.
Fix: no per-operation change — DescribeRepositories serializes the stored Repository, so the state module's URI base is the single point to fix; confirm the listing path does not recompute a URI from its own constant.
Traces: api-multi-repository-isolation#task#11 (cluster of 2: also ecr-public-describe-repositories-max-results-pagination#task#5).

=== Cause 4 of 5: DescribeRepositories reports the unreachable repositoryUri for a single-repository/paged response ===
AWS: same member and modeled contract as cause 3, on a response carrying one repository (including the max-results paging legs).
Emulator: answers 200; `$.repositories[0].repositoryUri` is `host_not_own` — got 'public.ecr.aws/emulator/<repositoryName>' where the recording carries the gallery host plus the account's own alias. This is a separate cluster from cause 3 (one URI key rather than two), so it must be re-replayed separately.
Why: same as cause 3 — the single-repository describe is the common case a client uses to resolve a push target by name, and it hands back an address that is not the emulator's.
Fix: same URI composition; this cluster exists to prove the fix holds on the one-element and paged responses too.
Traces: api-multi-repository-isolation#task#14 (cluster of 5: also api-repository-creation-catalog-lifecycle#task#2, api-repository-deletion-and-non-empty-error-paths#task#12, ecr-public-describe-repositories-max-results-pagination#task#3, ecr-public-describe-repositories-max-results-pagination#task#4).

=== Cause 5 of 5: DescribeRegistries reports a registryUri on the real gallery host ===
AWS: Smithy DescribeRegistries -> DescribeRegistriesResponse.registries (@required) -> Registry, whose registryUri (@required, target Url) is documented 'The URI of a public registry. The URI contains a universal prefix and the registry alias.' HTTP 200. The recording does not assert the literal value ('<shaped-not-asserted>'), because the alias is per-account; the requirement that remains is that the universal prefix be the host serving that registry — for the emulator, its own.
Emulator: answers 200 with `$.registries[0].registryUri` = 'public.ecr.aws/emulator' — `host_not_own`. 'public.ecr.aws' is fixed emulator output (state.rs GALLERY_HOST) and is the defect; the 'emulator' alias segment is free.
Why: registryUri is the registry-wide prefix a client prepends to a repository name (and the value `docker login` is pointed at). Even a client that never calls DescribeRepositories derives unreachable push/pull targets from it, and a login against the advertised registry leaves the emulator entirely.
Fix: the registry record's URI composition in the ecr-public state module (the registry/alias base that DescribeRegistries serves, alongside the repository base of cause 1) must be built from the emulator's own advertised host:port; keep the alias and ARN/registryId as they are.
Traces: api-registry-level-operations-and-authorization#task#3 (cluster of 2: also api-repository-uri-arn-alias-scoped-regionless#task#1).
