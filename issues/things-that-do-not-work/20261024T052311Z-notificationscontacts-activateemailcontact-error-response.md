# Return ResourceNotFoundException (404) when no activation code was ever issued for the contact

_Filed: 2026-10-24T05:23:11Z_
_Operation: ActivateEmailContact | Class: error-response_

> _Note: this issue was identified against the code base at commit `7eba44b4c78724d09fd14d928dd44bf5d39abe6e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Real AWS distinguishes two failure modes for ActivateEmailContact:

1. A code WAS issued by SendActivationCode but the supplied code does not match it -> ValidationException (HTTP 400), message "Input token did not match stored Activation Token for arn <arn>".
2. NO activation code was ever issued for the contact (CreateEmailContact, then ActivateEmailContact without any SendActivationCode) -> ResourceNotFoundException (HTTP 404), message "Activation Token with arn <arn> not found" — there is no stored activation token resource to compare against.

The emulator collapses both modes into case 1: `src/ops/activate_email_contact.rs` compares `contact.pending_activation_code.as_deref() != Some(input.code)` and, when the record carries `None` (no code ever sent), returns the same 400 `ValidationException` with reason `fieldValidationFailed` and `fieldList=[{name:"code"}]`. A client that activates before sending a code therefore sees 400/ValidationException where AWS answers 404/ResourceNotFoundException, so the error code, the HTTP status and the error shape (fieldList vs resourceId/resourceType) all diverge.

Expected: activating a contact that has no outstanding activation token -> 404 ResourceNotFoundException carrying resourceId/resourceType. Actual: 400 ValidationException.

## Evidence

Model (smithy_query operation=ActivateEmailContact) declares BOTH ResourceNotFoundException (404) and ValidationException (400) for this operation, and `ActivateEmailContactRequest$code` documents that codes "are generated by the SendActivationCode API action" — i.e. no token exists until one is sent. Recorded AWS behavior for the two modes is cited in the already-filed open issue 20261023T000909Z-notificationscontacts-error-message-fidelity-divergences-in-validation-and (Cause 5), which notes the never-issued case is "ResourceNotFoundException 'Activation Token with arn <arn> not found'" — that issue only asks for the MESSAGE of the mismatch case (operation CreateEmailContact), not for the status/code of the never-issued case, so this is net-new. Handler: services/service-com-amazonaws-notificationscontacts-notificationscontacts/src/ops/activate_email_contact.rs lines ~165-184. Test coverage: tests/all/email_contacts.rs::activation_turns_only_on_the_code_this_service_issued asserts the contact with NO code and a wrong code both answer the same refusal (ValidationException), i.e. the current behavior is pinned as the 400 — no test asserts the 404 AWS returns.

## Steps to Reproduce

1. CreateEmailContact(name="contact-a", emailAddress="contact-a@example.com") -> note the returned arn
2. Do NOT call SendActivationCode
3. ActivateEmailContact(arn=<arn>, code="0000000")
4. Observe the emulator answers HTTP 400 ValidationException; real AWS answers HTTP 404 ResourceNotFoundException ("Activation Token with arn <arn> not found")
5. For contrast: call SendActivationCode(arn) first, then ActivateEmailContact with a wrong 7-char code -> that case is the 400 ValidationException
