# DynamoDB expression validation runs at evaluation time, so malformed conditions are answered ConditionalCheckFailedException and every expression diagnostic is invented (4 causes)

> _Note: this issue was identified against the code base at commit `a2c0c19d1874b6d8f510c899cc1a51333f7d4b07`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutItem

## Description
Four net-new root causes in the shared expression layer (ConditionExpression, FilterExpression, KeyConditionExpression, ExpressionAttributeNames/Values) used by PutItem, UpdateItem, DeleteItem, Query, Scan and TransactWriteItems. Open issue 20261030T060227Z-dynamodb-validationexception-messages-diverge-from-the-wording-aws.md and 20261103T022510Z-dynamodb-expression-and-partiql-diagnostics-refusals-carry-emulator.md are adjacent but the suite did not mark any check below as owned; file-and-close together if the fix lands in one place.

=== Cause 1 of 4: operand-type and function-shape defects are evaluated instead of validated ===
AWS: an expression whose operand type cannot satisfy the operator is a REQUEST defect, refused with ValidationException (HTTP 400) before the item is read, e.g. an ordering comparison (<, >, BETWEEN) against a BOOL or a malformed N literal, contains(path, path) where AWS requires an operand, attribute_type with a type name outside {S,SS,N,NS,B,BS,BOOL,NULL,L,M}, begins_with with a non-string operand. The condition is never evaluated, so ConditionalCheckFailedException cannot be the answer.
Emulator: the expression is parsed loosely and evaluated; the predicate simply does not match, so the call comes back ConditionalCheckFailedException 'The conditional request failed' (PutItem/DeleteItem/UpdateItem), TransactionCanceledException 'Transaction cancelled, please refer cancellation reasons for specific reasons [ConditionalCheckFailed, None]' (TransactWriteItems), or HTTP 200 with an empty page (Scan with a begins_with over a non-string, attribute_type with an unknown type name).
Why: a client cannot distinguish "my request is malformed" from "the item did not satisfy my condition" — the first must be fixed in code and never retried, the second is a normal optimistic-concurrency outcome that is retried. Retrying a malformed request forever is the failure mode.
Fix: operand/type/arity checking in the expression validator, run before the item is fetched, in the shared condition-expression component used by the item, query/scan and transaction handlers.
Traces: condition-expression-contains-same-path-and-between-reversed-rejected, condition-ordering-comparison-non-orderable-literal-rejected, delete-item-condition-between-bounds-validated, malformed-n-in-expression-value-rejected-before-evaluation, transact-write-condition-non-orderable-literal-rejected, ddb-sfa-condition-attribute-type-with-an-unknown-type-name-rejected, ddb-ss-attribute-type-with-an-unknown-type-name-rejected, scan-filter-begins-with-non-string-operand-rejected.

=== Cause 2 of 4: expression syntax/structure refusals carry the emulator's parser text, not AWS's ===
AWS: ValidationException messages here are fixed sentences naming the CONCEPT, with only the expression kind and the offending name substituted: an empty expression is "Invalid <Kind>Expression: The expression can not be empty;"; a function given a value placeholder where a document path belongs is "Invalid <Kind>Expression: Operator or function requires a document path; operator or function: <name>"; a wrong operand count is "Invalid <Kind>Expression: Incorrect number of operands for operator or function; operator or function: <name>, number of operands: <n>"; an over-long expression is "Invalid <Kind>Expression: Expression size has exceeded the maximum allowed size;" — and where AWS prefixes "1 validation error detected: " it does so consistently per operation.
Emulator: these all come back as the parser's own token dump, e.g. 'Invalid FilterExpression: Syntax error; token: "<EOF>", near: ""' for an empty expression, 'Invalid FilterExpression: Syntax error; token: ")", near: ":v )"' for attribute_exists(:v), 'Invalid FilterExpression: Syntax error; token: ",", near: "#a , #a"' for a two-operand attribute_exists, and 'Invalid ProjectionExpression: Syntax error; token: "#", near: "#"' for a malformed name key.
Why: the message is part of the contract; the token/near dump is emulator-internal and does not name the rule the caller broke.
Fix: the expression-parser error mapper — classify the defect (empty / operand-count / document-path-required / size) and render AWS's sentence for that class.
Traces: ddb-frc-empty-filter-expression-rejected, ddb-sfa-unused-expression-attribute-name-in-scan-rejected, empty-string-expression-rejected-across-operations, transact-write-items-condition-expression-defects-match-putitem-message, ddb-sfa-attribute-exists-on-a-value-placeholder-rejected, ddb-sfa-attribute-exists-with-two-operands-rejected, expression-attribute-map-key-syntax-and-length-rejected, filter-and-key-condition-expression-size-limit-rejected.

=== Cause 3 of 4: KeyConditionExpression diagnostics report the wrong rule, and a value-first comparison is rejected outright ===
AWS: Query key-condition defects are refused with ValidationException naming the key-condition rule: an operand whose type does not match the schema type is "Invalid KeyConditionExpression: Incorrect operand type for operator or function; operator or function: <op>, operand type: <T>"; two clauses on the same key is "Invalid KeyConditionExpression: KeyConditionExpressions must only contain one condition per key"; a document path or reserved head where a key attribute belongs is a key-condition defect, not a missing-key-schema-element defect. AWS also accepts the value-first form ":lo <= sk" as a legal sort-key comparison.
Emulator: the operand-type defect is reported as the key-schema message 'One or more parameter values were invalid: Type mismatch for key sk expected: S actual: N'; the duplicate-clause defect as the emulator-authored 'Invalid key condition: the sort key sk is constrained more than once'; a dotted path on the partition key as 'Query condition missed key schema element: pk'; and ":lo <= sk" is refused outright with 'Invalid KeyConditionExpression: Syntax error; token: "<=", near: ":lo <= sk"'.
Why: a legal query is refused (value-first comparison), and the refusals that do fire point the caller at the wrong rule.
Fix: the KeyConditionExpression parser/validator in the Query handler — accept the value-first comparison form and classify defects as key-condition defects with AWS's sentences.
Traces: query-key-condition-document-path-forms-and-reserved-head-rejected, query-key-condition-duplicate-sort-key-clause-and-nested-path-rejected, query-key-condition-operand-type-vs-schema-type-rejected, key-condition-illegal-sort-key-operator-rejected, query-value-first-sort-key-comparison-and-size-of-absent-attribute.

=== Cause 4 of 4: ExpressionAttributeNames/Values with no expression is misclassified as "unused", and the "1 validation error detected: " prefix is applied inconsistently ===
AWS: supplying ExpressionAttributeNames or ExpressionAttributeValues on a request that carries NO expression at all is its own defect — "1 validation error detected: ExpressionAttributeValues can only be specified when using expressions" (and the Names analogue) — distinct from supplying a placeholder an expression does not reference, which is "Value provided in ExpressionAttributeValues unused in expressions: keys: {<key>}". Whether the "1 validation error detected: " prefix appears is fixed per operation: TransactWriteItems serves the unused-placeholder message WITHOUT it, single-item PutItem WITH it. A name key not starting with '#' / a value key not starting with ':' is also its own defect, not a reserved-keyword defect.
Emulator: every one of these collapses to the unused-placeholder message, and the prefix is attached uniformly to the transaction forms where AWS omits it ('1 validation error detected: Value provided in ExpressionAttributeValues unused in expressions: keys: {:unused}') and omitted where AWS includes it. A duplicate set member in a condition value is reported as '1 validation error detected: Invalid ConditionExpression: Attribute name is a reserved keyword; reserved keyword: other'.
Why: a client branching on the message sees the wrong defect class, and the prefix difference breaks exact-match assertions and error parsing.
Fix: placeholder-presence checking must run before placeholder-usage checking in the shared expression validator, and the "1 validation error detected: " prefix must be driven per operation by the same renderer rather than applied globally.
Traces: expression-attribute-keys-without-prefix-rejected-on-item-ops, expression-attribute-placeholders-without-an-expression-rejected, query-and-update-item-placeholders-without-an-expression-rejected, transact-items-accept-placeholders-without-an-expression, transact-unused-expression-attribute-name-on-condition-check-and-get-rejected, duplicate-set-members-in-condition-key-and-transact-rejected, transact-write-items-duplicate-key-rejected, transact-write-items-unused-expression-attribute-value-on-second-action-rejected, transact-write-expression-parse-errors-rejected-top-level.

## Steps to Reproduce
1. Create a table with HASH pk (S) and RANGE sk (S); put an item.
2. ddb.put_item(..., ConditionExpression='n < :v', ExpressionAttributeValues={':v': {'BOOL': True}}) — expect ValidationException, observe ConditionalCheckFailedException.
3. ddb.scan(TableName=t, FilterExpression='') — read Error.Message; expect 'Invalid FilterExpression: The expression can not be empty;'.
4. ddb.query(TableName=t, KeyConditionExpression='pk = :p AND :lo <= sk', ExpressionAttributeValues={...}) — expect HTTP 200, observe ValidationException syntax error.
5. ddb.put_item(TableName=t, Item={...}, ExpressionAttributeValues={':v': {'S': 'x'}}) with no ConditionExpression — expect '... can only be specified when using expressions'.
6. ddb.transact_write_items with an unused :extra on the second action and compare the message prefix with the single-item PutItem form.
