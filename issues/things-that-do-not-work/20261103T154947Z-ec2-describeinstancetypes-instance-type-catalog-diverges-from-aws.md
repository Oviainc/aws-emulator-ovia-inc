# EC2 DescribeInstanceTypes instance-type catalog diverges from AWS: synthesized attribute values and omitted optional members

> _Note: this issue was identified against the code base at commit `16c881ed26ef4e30669bd1a48293a88cc368ef87`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 but the instance-type catalog behind it is emulator-authored: the per-type hardware facts AWS publishes are replaced by values the emulator derives (they scale smoothly with vCPU count instead of matching the family's published figures), and a group of optional InstanceTypeInfo members is never serialized at all. The replay shows 133 DescribeInstanceTypes divergence clusters across the ec2-catalog-describe-instance-types-* fixtures; the three causes below are the ones this issue carries, one per bundled cluster.

Cause 1 of 3 - compute-with-local-storage families (c6id...), fixture ec2-catalog-describe-instance-types-a1-c9g step task#15.
AWS: Smithy (com.amazonaws.ec2) DescribeInstanceTypes -> InstanceTypeInfo. EbsInfo.EbsOptimizedInfo carries baselineBandwidthInMbps (integer), baselineIops (integer), baselineThroughputInMBps (double), maximumBandwidthInMbps, maximumIops, maximumThroughputInMBps; InstanceStorageInfo carries totalSizeInGB (long) and disks (DiskInfoList, each with count/sizeInGB/type). For every instance type these are the published hardware figures for that exact type, not a function of its size; the same response also carries cpuBurstModel, phcSupport, rebootMigrationSupport, processorInfo.sustainedClockSpeedInGhz, vCpuInfo.validCores and networkInfo.{defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, maximumNetworkCards, networkCards, networkPerformance, secondaryNetworkSupported, trafficMirroringSupport}. The recording is the authority for the values themselves (recorded behavior only for which types the corpus asserts).
Emulator: same 200, but every ebsOptimizedInfo figure, ebsInfo.maximumEbsAttachments, instanceStorageInfo.disks.item.sizeInGB/count and instanceStorageInfo.totalSizeInGB differ from the recorded ones, and cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.networkCards, phcSupport and rebootMigrationSupport are absent from the item.
Why: a client that sizes EBS throughput/IOPS, counts instance-store capacity, picks a network-card layout or gates on ENA-SRD/PHC/reboot-migration support reads numbers and absences that no real instance type has; capacity-planning and instance-selection logic silently picks the wrong type, and code that requires a modelled member sees it missing.
Fix: the static instance-type catalog that backs the DescribeInstanceTypes handler in the ec2 service crate (services/service-com-amazonaws-ec2-amazonec2) - the per-type attribute table and the serializer that drops the optional members.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#15.

Cause 2 of 3 - network-optimized and bare-metal types (c6in..., including .metal), fixture ec2-catalog-describe-instance-types-a1-c9g step task#16.
AWS: same model surface, plus InstanceTypeInfo.autoRecoverySupported and networkInfo.efaInfo.maximumEfaInterfaces, which AWS reports per type (bare-metal and multi-card network-optimized types support simplified automatic recovery and more than one EFA interface where published).
Emulator: autoRecoverySupported is reported false where the recording has true, networkInfo.efaInfo.maximumEfaInterfaces is lower than recorded, and the same ebsOptimizedInfo / maximumEbsAttachments drift and missing optional members as Cause 1 appear on this family.
Why: a client that filters instance types by auto-recovery support or sizes an EFA-based HPC placement is told a capability the type actually has is unavailable, so it rejects a valid type.
Fix: same per-type catalog table and serializer; capability flags must come from the per-type record, not from a default.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#16.

Cause 3 of 3 - Graviton local-storage families (m7gd...), fixture ec2-catalog-describe-instance-types-m6i-r4 step task#7.
AWS: same model surface; instanceStorageInfo.totalSizeInGB/disks.item.sizeInGB are the published NVMe sizes of that type, ebsInfo.maximumEbsAttachments is the published attachment limit, and nitroEnclavesSupport / nitroTpmSupport are per-type.
Emulator: instance-store disk size and totalSizeInGB, all six ebsOptimizedInfo figures, maximumEbsAttachments and processorInfo.sustainedClockSpeedInGhz differ from the recorded values, nitroEnclavesSupport/nitroTpmSupport differ on the small and metal sizes, and the same optional members (cpuBurstModel, networkInfo.defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, networkCards, maximumNetworkCards, phcSupport, rebootMigrationSupport) are omitted.
Why: a client provisioning Graviton local-storage instances mis-sizes ephemeral storage and EBS attachments, and enclave/TPM gating is wrong.
Fix: same per-type catalog table; the ARM families need their own records rather than being derived from the x86 formula.
Traces: ec2-catalog-describe-instance-types-m6i-r4#task#7.
