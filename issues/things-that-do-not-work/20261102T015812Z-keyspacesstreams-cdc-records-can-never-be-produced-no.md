# keyspacesstreams CDC records can never be produced: no Cassandra native-protocol (CQL) listener answers on the published cassandra.<region>.amazonaws.com:9142 data-plane endpoint, so every row-change check dies at connect

> _Note: this issue was identified against the code base at commit `86294b81c3bdab5f6a26606f5f9507599ec174dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRecords

## Description
One root cause (Cause 1 of 1), grounded in six failing keyspacesstreams checks that all abort at the same point: the TCP/TLS connect to the Cassandra CQL data-plane endpoint, before any GetRecords assertion is reached.

Note: the open issue 20261029T194003Z-keyspaces-serves-no-cassandra-native-protocol-cql-data.md reports the same missing listener for the `keyspaces` service, grounded in the three `keyspaces.native-cql-*` checks. It does not cover these checks: they are a different service's checks (keyspacesstreams) with their own replay keys, and they grade a different contract — not that a row round-trips over CQL, but that a row mutation made over CQL is turned into keyspacesstreams change records with the modeled shape, images, origin and sequencing. The listener is the shared prerequisite; the change-record production this issue is about is this service's own.

Cause 1 of 1 — no CQL listener, so no change record is ever generated and the entire keyspacesstreams data plane is unobservable.
Failing checks: keyspacesstreams.cdc-native-protocol-insert-update-delete-round-trip, keyspacesstreams.cdc-batch-operation-decomposes-into-row-records, keyspacesstreams.cdc-concurrent-inserts-preserve-sequence-ordering, keyspacesstreams.cdc-keys-only-view-type-omits-images, keyspacesstreams.get-records-pagination-via-next-shard-iterator, keyspacesstreams.get-shard-iterator-sequence-number-boundary-semantics.

AWS: the keyspacesstreams Smithy model (com.amazonaws.keyspacesstreams#KeyspacesStreams) declares only the stream-reading surface — GetStream (output streamArn/streamLabel/streamStatus/streamViewType/keyspaceName/tableName/shards, paginated on nextToken), GetShardIterator (streamArn+shardId+shardIteratorType required, optional sequenceNumber @length 21-48) and GetRecords (shardIterator required @length 1-4096, maxResults @range 1-1000; output changeRecords/nextShardIterator/iteratorDescription). The records those operations serve are shape `Record` with members eventVersion, createdAt, origin (enum OriginType = USER|REPLICATION|TTL), partitionKeys, clusteringKeys, newImage, oldImage, sequenceNumber; the view type that decides which images appear is StreamViewType = NEW_IMAGE|OLD_IMAGE|NEW_AND_OLD_IMAGES|KEYS_ONLY. There is deliberately NO modeled operation that writes a row: for the write side this is recorded behavior only — Amazon Keyspaces' data plane is the Apache Cassandra native binary protocol over TLS on port 9142 at cassandra.<region>.amazonaws.com, and the recordings show that each accepted row mutation on a CDC-enabled table is published to the table's stream as one row-level `Record` per affected row (a single CQL BATCH over two rows decomposes into two independently sequenced records, each origin=USER; an INSERT/UPDATE/DELETE sequence yields records whose newImage/oldImage follow the table's streamViewType, with KEYS_ONLY omitting both images; concurrent inserts are each assigned a distinct sequenceNumber within a shard; and the records are then readable through GetRecords/nextShardIterator pagination and addressable by AT_SEQUENCE_NUMBER / AFTER_SEQUENCE_NUMBER iterators).

Emulator: the emulator publishes that data-plane endpoint — the checks resolve cassandra.<region>.amazonaws.com port 9142 through the harness endpoint mapping and are handed the emulator's own loopback address and port — but nothing is listening on it. Every one of the six checks fails inside cassandra-driver's control connection with `cassandra.cluster.NoHostAvailable: ('Unable to connect to any servers', {...: ConnectionRefusedError(111, ... Connection refused)})`, before a single CQL frame is written. Everything upstream of the connect succeeds in these checks: the keyspace is created, the CDC-enabled table is created and its cdcStatus reaches ENABLED, the stream reaches streamStatus ENABLED, and GetStream returns its shard list (one check even obtains a TRIM_HORIZON shardIterator for every shard successfully). Because no write can be made, GetRecords always answers with an empty `changeRecords` list, so no record shape, image, origin, sequencing or pagination behavior of this service is exercised at all. The driver is installed — the checks assert that first (`_require_cassandra_driver`) and would have reported an ImportError instead — so this is the emulator's missing listener, not a missing runner dependency: the emulator announces an endpoint it does not answer on.

Why: a client gets an emulated Keyspaces CDC stream that can never contain anything. Code under test that reads a stream (a change-data pipeline, a replicator, a CDC consumer) sees a permanently empty, permanently at-tip stream and cannot be exercised; nothing distinguishes "no changes yet" from "changes are never captured". Every row-level fidelity question of the service is ungradable: whether a BATCH decomposes into one record per row, whether origin is USER for a user write, whether KEYS_ONLY suppresses newImage/oldImage, whether concurrent writes get distinct sequenceNumbers, whether nextShardIterator pages through a backlog, and whether AT_SEQUENCE_NUMBER is inclusive while AFTER_SEQUENCE_NUMBER is exclusive. A connect refused at the socket also misleads a user into debugging their own client configuration.

Fix: a data-plane listener for the Keyspaces CQL endpoint — a TLS server bound to the published cassandra.<region>.amazonaws.com:9142 endpoint speaking the Cassandra native binary protocol (OPTIONS/SUPPORTED, STARTUP/AUTHENTICATE, AUTH_RESPONSE/AUTH_SUCCESS, QUERY/PREPARE/EXECUTE/RESULT, ERROR) over the same keyspace/table state the keyspaces control-plane crate owns — plus, in this service, the change-capture producer that the executor of those CQL writes must feed: for each accepted row mutation on a CDC-enabled table, append one Record per affected row to the owning stream's shard state, with origin, partitionKeys, clusteringKeys and newImage/oldImage populated per the table's streamViewType and a distinct monotonically increasing sequenceNumber, so that the existing GetShardIterator/GetRecords handlers (iterator positioning, nextShardIterator paging and sequence-number boundary semantics) read real data instead of an always-empty shard. Until the listener exists and records are produced, none of the six checks can get past connect.

Traces: the six failing check ids listed above; all six report the same ConnectionRefusedError against the mapped CQL endpoint. The host/port shown in the replay output is this environment's mapping of cassandra.<region>.amazonaws.com:9142 and is not itself the requirement — the requirement is that the endpoint the emulator publishes for the CQL data plane answers, and that writes made over it surface as keyspacesstreams records.

Expected: the published CQL endpoint accepts the TLS connection; an INSERT/UPDATE/DELETE (or a BEGIN BATCH ... APPLY BATCH over two rows of one partition) executed over it is captured by the table's CDC stream, and GetRecords on the shard iterators obtained before the write returns one `Record` per affected row — origin=USER, partitionKeys/clusteringKeys set from the mutated row, newImage/oldImage present or omitted according to the table's streamViewType (KEYS_ONLY omits both), each record carrying its own distinct sequenceNumber, reachable via nextShardIterator paging and addressable by AT_SEQUENCE_NUMBER (inclusive) / AFTER_SEQUENCE_NUMBER (exclusive).
Actual: the TCP connect to the published CQL port is refused (Errno 111) — zero CQL frames are exchanged, no row is ever written, and GetRecords consequently answers 200 with an empty `changeRecords` list forever. Control-plane steps preceding the connect all succeed in every check: CreateKeyspace, CreateTable with a cdcSpecification, cdcStatus reaching ENABLED, GetStream reporting streamStatus ENABLED with its shard list, and GetShardIterator(TRIM_HORIZON) per shard.

The cassandra-driver / cassandra-sigv4 dependencies are present: each check calls `_require_cassandra_driver()` first and would have failed with an ImportError-derived AssertionError instead of a connect refusal.

## Steps to Reproduce
1. Against the emulator's keyspaces control plane: CreateKeyspace(K); CreateTable(K, T) with allColumns=[pk text, ck text, val text], partitionKeys=[pk], clusteringKeys=[ck] and a cdcSpecification with status ENABLED and viewType NEW_IMAGE (repeat with KEYS_ONLY for the images case); poll GetTable until cdcStatus is ENABLED and note the returned stream ARN.
2. keyspacesstreams GetStream(streamArn) — observe streamStatus ENABLED and its shards; for each shardId call GetShardIterator(streamArn, shardId, shardIteratorType=TRIM_HORIZON) and keep the iterators. (All of this succeeds today.)
3. Resolve the data-plane endpoint the emulator publishes for cassandra.<region>.amazonaws.com port 9142 and open a TLS Cassandra native-protocol connection to it, authenticating as the caller's SigV4 identity.
4. Observe: the TCP connect is refused (ConnectionRefusedError, Errno 111) — no TLS handshake and no CQL frame, so step 5 can never be attempted.
5. Expected instead: the connection is accepted and `INSERT INTO K.T (pk, ck, val) VALUES ('row1','b1','first')`, then an UPDATE and a DELETE of that row, succeed; polling GetRecords on the iterators from step 2 returns one Record per mutated row with origin=USER, partitionKeys/clusteringKeys from the row, newImage/oldImage per the table's streamViewType, and a distinct sequenceNumber each; a single `BEGIN BATCH <two INSERTs for ck=b1 and ck=b2> APPLY BATCH` yields exactly two records (one per row, distinct sequenceNumbers); GetRecords walks the backlog via nextShardIterator; and an AT_SEQUENCE_NUMBER iterator re-reads the record at that sequence number while AFTER_SEQUENCE_NUMBER starts at the next one.
