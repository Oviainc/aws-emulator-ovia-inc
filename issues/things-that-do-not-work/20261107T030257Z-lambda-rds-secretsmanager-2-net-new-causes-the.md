# lambda__rds__secretsmanager: 2 net-new causes — the DB-instance managed master secret is not marked owned by rds nor tagged with its instance ARN, and the PostgreSQL endpoint refuses every GRANT statement as a syntax error

> _Note: this issue was identified against the code base at commit `d2ccc1a1188e008fb4f624824feca16be793f9fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
This issue bundles 2 net-new root causes in the lambda__rds__secretsmanager service, both grounded in failing behavioural checks the suite marked neither ALREADY FILED nor OWNED. A fixer must close BOTH causes below before submitting.

=== Cause 1 of 2: the DB instance's RDS-managed master user secret reports no OwningService and carries no aws:rds:primaryDBInstanceArn tag ===
AWS: Smithy: secretsmanager#DescribeSecretResponse$OwningService — "The ID of the service that created this secret" (see 'Secrets managed by other Amazon Web Services services'); rds#MasterUserSecret is "the secret managed by RDS in Amazon Web Services Secrets Manager for the master user password". For an instance created with ManageMasterUserPassword=true, DescribeSecret on the reported SecretArn returns OwningService = "rds", and the secret carries the AWS-applied tag aws:rds:primaryDBInstanceArn whose value is that instance's DBInstanceArn (fixed tag key, value taken from the owning instance). AWS also names the secret with the reserved, caller-unmintable prefix 'rds!db-<dbi resource id>'.
Emulator: DescribeSecret on the ARN the instance reported returns OwningService absent (None) and no aws:rds:primaryDBInstanceArn tag, and the secret is named with a plain-hyphen, caller-mintable prefix of the form 'rds-db-db-<dbi resource id>-<suffix>' instead of 'rds!db-<dbi resource id>'. The SecretString itself does carry username/password. (The recorded name in this run was 'rds-db-db-00000000000000000000000001-0nYAtX'; the id and suffix are this run's generated values, the prefix shape is the requirement.)
Why: the reverse lookup from a secret back to the DB instance that owns it does not exist — a client cannot answer "which database does this credential belong to?" from the secret, cannot distinguish an RDS-managed credential from a user secret, and tag- or name-scoped IAM policies written against 'rds!*' or aws:rds:primaryDBInstanceArn match nothing.
Fix: the CreateDBInstance/ModifyDBInstance managed-master-secret minting path in the rds handler (the name it composes, the owning service it records and the aws:rds:primaryDBInstanceArn tag it applies) plus the secretsmanager state/DescribeSecret serializer that must carry and emit OwningService and those AWS-applied tags.
Traces: lambda__rds__secretsmanager.rds-credentials-stored-in-secretsmanager-resource-reference.

=== Cause 2 of 2: the published PostgreSQL endpoint refuses GRANT entirely — 'syntax error at or near "GRANT"' — so rds_iam cannot be granted and IAM database authentication is unreachable ===
AWS: recorded behavior only (the engine surface is a PostgreSQL contract, not a Smithy one). A PostgreSQL DB instance accepts role DDL from the master user: after CREATE USER <name>, the statement GRANT rds_iam TO <name> succeeds and makes that database user authenticate with an IAM auth token, which is the engine-side half of EnableIAMDatabaseAuthentication=true. PostgreSQL only emits 'syntax error at or near "<token>"' (SQLSTATE 42601) for a statement it cannot parse; GRANT is parsed, so no error is returned here at all.
Emulator: the statement is refused at the very first keyword — psycopg.errors.SyntaxError: syntax error at or near "GRANT" — for GRANT rds_iam TO <user>, on a connection the master user successfully opened on the instance's published Endpoint.Address/Port. The fixed part of such a message is PostgreSQL's 'syntax error at or near "…"' and the quoted token is the offending token from the submitted statement; here the offending token is the statement's own leading keyword, i.e. no GRANT form is parsed at all. Nothing is granted, so the Lambda-minted IAM auth token can never authenticate and the check's SELECT 1 over the token connection is never reached.
Why: IAM database authentication is unusable end to end — a caller can mint a token with generate_db_auth_token but no database user can ever be enabled for it — and every privilege-scoped behaviour that depends on granting a role or a privilege fails with a syntax error from an endpoint advertised as PostgreSQL.
Fix: the engine data plane's PostgreSQL statement parser/executor for GRANT (GRANT <role> TO <role>, GRANT <privilege> ON <object> TO <role>) and the pg_roles/pg_auth_members catalogs plus the IAM-auth role binding it must update.
Note on an adjacent open issue: 20261105T224225Z-rds-5-net-new-causes-the-postgresql-endpoint.md records role DDL refusals under the rds service with the key 'syntax error at or near "ROLE"' (CREATE ROLE … WITH LOGIN); it does not carry this check or this service, and the refusal recorded here is on the GRANT keyword itself after CREATE USER succeeded, so GRANT must be fixed explicitly and re-verified against the check listed below.
Traces: lambda__rds__secretsmanager.lambda-rds-generate-auth-token-positive.

## Evidence
Cause 1: AssertionError: secret arn:aws:secretsmanager:<region>:<account>:secret:rds-db-db-00000000000000000000000001-0nYAtX OwningService None != 'rds' — it should be owned by RDS, not created independently (check rds-credentials-stored-in-secretsmanager-resource-reference, line 67), after CreateDBInstance(Engine=mysql, MasterUsername=admin, ManageMasterUserPassword=true) reached available and GetSecretValue returned a username/password payload. Expected: DescribeSecret.OwningService="rds", Tags containing aws:rds:primaryDBInstanceArn=<DBInstanceArn>, and Name starting 'rds!db-'; actual: OwningService absent, that tag absent, name 'rds-db-db-…'.
Cause 2: psycopg.errors.SyntaxError: syntax error at or near "GRANT" raised from cur.execute() for the statement GRANT rds_iam TO iamuser; on a master-user psycopg session (sslmode=require) against the instance's published Endpoint.Address/Port, after CREATE USER iamuser; succeeded on the same endpoint. AWS returns no error for that GRANT; the emulator refuses it with PostgreSQL syntax-error class 42601 whose offending token is the statement's leading keyword.

## Steps to Reproduce
Cause 1: CreateDBSubnetGroup over the shared network; CreateDBInstance(DBInstanceIdentifier=<id>, DBInstanceClass=db.t3.micro, Engine=mysql, MasterUsername=admin, ManageMasterUserPassword=true, AllocatedStorage=20, BackupRetentionPeriod=0, PubliclyAccessible=false, DBSubnetGroupName=<group>); poll DescribeDBInstances to available; take MasterUserSecret.SecretArn and DBInstanceArn; call secretsmanager DescribeSecret(SecretId=<SecretArn>) — OwningService is absent (expected "rds"), there is no aws:rds:primaryDBInstanceArn tag equal to DBInstanceArn, and Name begins 'rds-db-db-' instead of 'rds!db-'.
Cause 2: CreateDBInstance(Engine=postgres, DBInstanceClass=db.t4g.micro, MasterUsername=dbadmin, ManageMasterUserPassword=true, EnableIAMDatabaseAuthentication=true, PubliclyAccessible=false, DBSubnetGroupName=<group>, VpcSecurityGroupIds=[<sg allowing 5432>]); poll to available; read the master password from MasterUserSecret via GetSecretValue; open a psycopg connection (sslmode=require) to Endpoint.Address/Port as dbadmin on database postgres; run CREATE USER iamuser; (succeeds) then GRANT rds_iam TO iamuser; — the server answers 'syntax error at or near "GRANT"'. With the grant impossible, a token from rds.generate_db_auth_token(DBHostname=<endpoint>, Port=<port>, DBUsername=iamuser) can never log in and SELECT 1 over that connection is unreachable.
