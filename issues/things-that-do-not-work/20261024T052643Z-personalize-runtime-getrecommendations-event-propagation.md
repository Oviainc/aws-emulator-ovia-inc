# Runtime recommendations never reflect personalize-events ingestion: interaction-based filters are rejected outright and PutItems/PutEvents data is invisible

_Filed: 2026-10-24T05:26:43Z_
_Operation: GetRecommendations | Class: event-propagation_

> _Note: this issue was identified against the code base at commit `7eba44b4c78724d09fd14d928dd44bf5d39abe6e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Amazon Personalize's real-time data plane is coupled to real-time ingestion: interactions recorded through personalize-events PutEvents / PutActionInteractions and items added through PutItems change what GetRecommendations (and GetPersonalizedRanking / GetActionRecommendations) return for the same campaign. The two canonical observable behaviours are:

1. An interaction-based FILTER. The filter expression language used by `filterArn` routinely references the Interactions / Action_Interactions datasets — the canonical published example being a filter that excludes items a user already interacted with, e.g. `EXCLUDE ItemID WHERE Interactions.EVENT_TYPE IN ("purchase")`. Against real AWS, sending a `purchase` event for item X through PutEvents and then calling GetRecommendations with that filterArn stops returning X for that user. In this emulator such a filter cannot even exist: `src/state/filter.rs` `Parser::clause()` hard-rejects any dataset other than `Items`/`Actions` ("this emulator evaluates filter expressions over Items and Actions only"), and `register_filter` validates the expression at registration, so the filter is refused at creation time and, once the control plane's CreateFilter is wired, a legitimate customer filter expression will be refused outright instead of applied. A GetRecommendations call that names such a filter can therefore only ever be a 400.

2. Incremental catalog / interaction data. The runtime's item and action catalogs live ONLY on the campaign/recommender record registered through the in-process `register_campaign` / `register_recommender` seams (`src/state.rs`). Nothing in the three handlers ever reads the personalize-events registry, which already persists exactly the data that should feed them: `StoredEvent { user_id, item_id, event_type, sent_at, impression, ... }` per event tracker, `StoredActionInteraction { action_id, user_id, event_type, ... }`, and Items/Users/Actions metadata records written by PutItems/PutUsers/PutActions. So an item put through PutItems is never recommendable and never supplies `metadataColumns` values, and no amount of PutEvents traffic changes an ordering, where against AWS recent interactions and newly imported items do.

Expected: a recommendation response computed from the campaign's catalog AND the interaction/catalog state ingested through personalize-events — an interaction-dataset filter expression parses, binds and removes the items whose events match, and items/metadata added through PutItems become visible to the runtime. Actual: the two services share an engine but no data: interaction-dataset filter expressions are refused by the parser, and every response is a function of the in-process-registered catalog only.

This is distinct from the open issue "No wire path registers a Personalize campaign" (which is about a campaign being creatable over the wire at all, and names CreateCampaign/CreateRecommender/CreateFilter as the fix) and from the open per-operation score-normalization issues: even with a campaign registered and CreateFilter wired, the interaction half of the data plane still has no path into the runtime.

## Evidence

Well-established Personalize semantics: filter expressions may reference the Interactions / Action_Interactions datasets (the "exclude items the user already purchased/watched" filter is the standard real-time filter), and real-time events sent through PutEvents are taken into account by campaign inference; PutItems exists specifically so new items become recommendable without a full import. Smithy: `GetRecommendations$filterArn` doc — "The ARN of the filter to apply to the returned recommendations... When using this parameter, be sure the filter resource is ACTIVE" — places no restriction on which dataset the filter's expression reads, and `GetRecommendations$filterValues` doc describes binding placeholders in that expression.
Handler/state: `services/service-com-amazonaws-personalizeruntime-amazonpersonalizeruntime/src/state/filter.rs` lines 336-345 (`clause()` returns an error for any dataset that is not `Items`/`Actions`) and lines 25-31 of its module doc, which states the limitation explicitly; `src/state.rs` lines 749-776 (`register_filter` parses and therefore refuses such an expression at registration). `src/ops/get_recommendations.rs` lines 189-336, `get_personalized_ranking.rs` lines 176-305 and `get_action_recommendations.rs` lines 155-233 read only `crate::state::service_state(...)` — neither handler ever touches `service_com_amazonaws_personalizeevents_amazonpersonalizeevents::state`, whose `EventTracker { events: VecDeque<StoredEvent>, action_interactions: ... }` and `Dataset`/`Record` metadata stores (`services/service-com-amazonaws-personalizeevents-amazonpersonalizeevents/src/state.rs` lines 155-225, 356-447) already hold the per-user interaction and item data, written by the implemented PutEvents/PutActionInteractions/PutItems handlers.
Tests: `tests/all/inference.rs` `the_filter_seam_refuses_an_expression_the_runtime_cannot_apply` (line 1350) asserts the refusal of expressions the runtime cannot apply, i.e. the limitation is codified rather than accidental; no test in either crate sends PutEvents and then checks a runtime response, so the propagation is untested.

## Steps to Reproduce

1. Boot the emulator with both personalize-events and personalize-runtime mounted on the same engine.
2. Register (today only through the in-process `state::register_filter` seam; over the wire once CreateFilter is implemented) a filter whose expression is the canonical interaction filter `EXCLUDE ItemID WHERE Interactions.EVENT_TYPE IN ("purchase")`. Observed: the expression is refused — `filter expression references the Interactions dataset; this emulator evaluates filter expressions over Items and Actions only` — so no such filter can exist and any GetRecommendations naming it can only be 400 "does not exist or is not active yet". Expected: the filter is accepted, as AWS CreateFilter accepts it.
3. Call personalize-events PutEvents with trackingId=<tracker>, userId=user-1, an event of eventType=purchase and itemId=item-3 (returns 200 and persists a StoredEvent).
4. Call personalize-runtime GetRecommendations with the campaignArn, userId=user-1, numResults=10 and that filterArn. Expected: item-3 is absent from itemList because the purchase event matched the filter. Observed: the call is refused for the filter ARN (and with no filter at all, the response is byte-identical before and after PutEvents).
5. Call personalize-events PutItems to add item-NEW with an Items-dataset property, then GetRecommendations with numResults=10 and metadataColumns={"ITEMS":[that property]}. Expected: item-NEW can be recommended and its metadata is served. Observed: item-NEW is unknown to the runtime (it is not in the campaign record's catalog) and requesting that column fails the "not in the Items dataset" check unless the in-process seam happened to register it.
