# Cloud Map (servicediscovery): 5 fidelity divergences — ServiceNotFound/NamespaceNotFound message bodies, DiscoverInstances accepts reserved AWS_ filter keys, non-derived Service Id on re-create, wrong UpdateService record-type InvalidInput message

> _Note: this issue was identified against the code base at commit `ff63bbd76f191efb9689374a4f98215607f4bd70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetService (bundle: DiscoverInstances, CreateService, UpdateService, UpdatePrivateDnsNamespace)

## Description
FIVE independent, net-new root causes in the servicediscovery (Cloud Map) emulator, all grounded in behavioral checks that are NOT covered by the open issue 20261023T124702Z-servicediscovery-cloud-map-servicediscovery-8-fidelity-divergences-missing-dnsconfig.md (that issue owns a different set of replay keys). Causes 1, 3 and 5 are in the same families that issue's Cause 8 and Cause 6 describe for OTHER operations; they are listed here because they are reached through operations that issue does not name (GetService's empty message under a different check, UpdatePrivateDnsNamespace rather than UpdateHttpNamespace, CreateService re-create after an explicit DeleteService), so closing that issue does not close these. Each of the five causes below must be closed before this issue is submitted. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json.

Cause 1 of 5: GetService answers ServiceNotFound with emulator-authored prose where AWS sends an EMPTY message.
AWS: Smithy GetService{Id: Arn (required, len 0..255)} -> Service, errors InvalidInput (400) and ServiceNotFound (404). The status and the error code match; only the Message diverges. Recorded behavior: GetService against a service id that was deleted returns HTTP 404 ServiceNotFound with an EMPTY message body — AWS echoes no identifier for this error class on this operation. The requirement is the empty message itself; there is no fixed text and no variable part.
Emulator: HTTP 404 ServiceNotFound with Message 'No service exists with the specified ID srv-91lm0w8httextxbe.' — emulator prose whose variable part is the requested service id (the modelled ServiceNotFound documentation string, used as a runtime message).
Why: a client or test that reads Error['Message'] for this operation gets a non-empty body where AWS gives none; any caller that distinguishes 'AWS said nothing' from 'AWS named the resource' (several Cloud Map not-found errors DO echo an id or ARN, so the distinction is load-bearing) reads the wrong signal, and negative tests that assert the empty body fail against the emulator.
Fix: the ServiceNotFound construction in GetService's handler (and the shared not-found message helper/constant it uses), so this operation's error carries no message.
Traces: servicediscovery.create-service-dnsconfig-in-http-namespace-rejected (the InvalidInput DnsConfig-in-HTTP-namespace rejection, the positive control and the delete all pass; only the final ServiceNotFound message assertion fails). Handler services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/src/ops/get_service.rs; the same prose template appears at src/ops/update_service.rs lines 213-219.

Cause 2 of 5: DiscoverInstances accepts a reserved AWS_-prefixed key in QueryParameters / OptionalParameters instead of refusing it with InvalidInput.
AWS: Smithy DiscoverInstances{NamespaceName (required), ServiceName (required), QueryParameters: Attributes, OptionalParameters: Attributes, HealthStatus, MaxResults, OwnerAccount} -> Instances + InstancesRevision; models InvalidInput (400), NamespaceNotFound (404), ServiceNotFound (404), RequestLimitExceeded (429). QueryParameters is documented as 'Filters to scope the results based on CUSTOM attributes for the instance (for example, {version=v1, az=1a})' and OptionalParameters as 'Opportunistic filters to scope the results based on CUSTOM attributes' — the AWS_ prefix namespace (AWS_INSTANCE_IPV4, AWS_INSTANCE_PORT, AWS_ALIAS_DNS_NAME, ...) is reserved by the service and is not a custom attribute. Recorded behavior: HTTP 400 InvalidInput with message 'Request QueryParameters contains invalid attribute: [<key>]. [aws_] prefix is reserved for AWS attributes.' and, for the other member, 'Request OptionalParameters contains invalid attribute: [<key>]. [aws_] prefix is reserved for AWS attributes.' Fixed text: 'Request ', ' contains invalid attribute: [', ']. [aws_] prefix is reserved for AWS attributes.'; variable parts: the member name taken from the request (QueryParameters or OptionalParameters) and the offending attribute key(s) taken from the request, bracketed.
Emulator: HTTP 200 with the instance list. With QueryParameters={'AWS_INSTANCE_IPV4': '192.0.2.10'} it treats the reserved key as an ordinary attribute filter and matches it against the stored attribute map, returning both registered instances (InstancesRevision 2); OptionalParameters behaves the same.
Why: overly permissive — a caller that mistakenly filters on a reserved key gets a plausible-looking 200 whose result set is governed by an undefined filter rather than the 400 AWS raises, so the bug is never surfaced and negative tests of the reservation pass against the emulator and fail against AWS.
Fix: DiscoverInstances' input validation, which today performs none: src/ops/discover_instances.rs passes input.query_parameters / input.optional_parameters straight into matches_every() (lines 264-289) with no pre-check. The validation must reject any key in the reserved AWS_ prefix namespace, case-insensitively, naming the member and the key(s).
Traces: servicediscovery.discover-instances-reserved-aws-query-parameter-rejected (every custom-attribute filtering case in the same check — exact match, case sensitivity, multi-key AND, OptionalParameters narrow-else-fall-back — passes; only the two reserved-key refusals fail).

Cause 3 of 5: a Service Id is minted randomly rather than derived from Name + NamespaceId, so an identical CreateService after DeleteService returns a different Id.
AWS: Smithy CreateService{Name (required, ServiceName pattern), NamespaceId: Arn, CreatorRequestId (idempotency token), DnsConfig, HealthCheckConfig, HealthCheckCustomConfig, Tags, Type} -> Service; errors InvalidInput 400 / NamespaceNotFound 404 / ResourceLimitExceeded 400 / ServiceAlreadyExists 400 / TooManyTagsException 400. Recorded behavior only: after DeleteService frees the name, re-creating the SAME Name in the SAME NamespaceId returns the SAME Service Id the first create returned. Hypothesis: AWS derives the service identifier from Name+NamespaceId rather than from a random sequence. The requirement is the relationship (identical Name+NamespaceId -> identical Id), never one recording's literal id.
Emulator: the second CreateService mints a fresh id — original srv-asq6pcptxf86imhq, recreated srv-tfieesvgvyjs2vip — via state.next_id("srv", 16).
Why: a client, IaC layer or cache that reconstructs or remembers the Service Id for a known Name+Namespace pair diverges from AWS after any delete/re-create cycle, and an idempotent-re-create assertion that holds on AWS fails here.
Fix: the Service Id derivation in CreateService's handler / the id allocator in src/state.rs. NOTE: the open issue ...-8-fidelity-divergences-missing-dnsconfig.md names this same derivation under its Cause 6 for check servicediscovery.create-service-lifecycle; this check reaches it through the ServiceAlreadyExists-then-delete-then-recreate path and is a separate replay key, so it must be re-replayed too.
Traces: servicediscovery.service-already-exists-error (the ServiceAlreadyExists code, its 'Service already exists.' message, the single-surviving-service read and the name being freed by DeleteService all pass; only the id-reuse assertion fails).

Cause 4 of 5: UpdateService's refusal of a DnsRecord Type change carries the wrong InvalidInput message.
AWS: Smithy UpdateService{Id (required), Service: ServiceChange (required)} -> OperationId; errors DuplicateRequest 409 / InvalidInput 400 / ServiceNotFound 404. ServiceChange.DnsConfig is a DnsConfigChange carrying only DnsRecords, and DnsConfig$DnsRecords documents that a record type cannot be updated. The status (400) and the code (InvalidInput) match; only the Message diverges. Recorded behavior: 'The record types in the request must be the same as those present in the existing service. Records in the existing service are [<stored types>], but the records in the request are [<requested types>]. The record types of a service cannot be changed.' Fixed text: 'The record types in the request must be the same as those present in the existing service. Records in the existing service are [', '], but the records in the request are [', ']. The record types of a service cannot be changed.'; variable parts: the record types of the STORED service's DnsConfig and the record types named in the REQUEST, each as a bracketed list.
Emulator: 'The service srv-dk84vzktt06ik3lu has no CNAME record configuration. The record type of a service specified in a DnsRecord object can\'t be updated. To change a record type, you need to delete the service and recreate it with a new DnsConfig.' — emulator-authored prose whose variable parts are the service id and the single requested type, and which never reports the stored record types AWS echoes.
Why: the message is a different template from AWS's, so a client or test that parses it to learn which record types the existing service actually carries (the information AWS puts in the body) gets the service id instead, and assertions on the documented text fail.
Fix: the InvalidInput construction in UpdateService's record-type check — src/ops/update_service.rs lines 263-292, which formats the per-record 'has no <type> record configuration' message inside the loop; it must instead compare the full stored type set against the full requested type set and emit the message above.
Traces: servicediscovery.service-dns-record-type-change-rejected (the InvalidInput code, the no-effect read showing Type A / TTL 60 unchanged, and the same-type TTL positive control all pass; only the message assertion fails).

Cause 5 of 5: UpdatePrivateDnsNamespace answers NamespaceNotFound with an EMPTY message where AWS echoes the namespace id.
AWS: Smithy UpdatePrivateDnsNamespace{Id: Arn (required), UpdaterRequestId (idempotency token), Namespace: PrivateDnsNamespaceChange (required)} -> OperationId; errors DuplicateRequest 409 / InvalidInput 400 / NamespaceNotFound 404 / ResourceInUse 409. The status (404) and the code (NamespaceNotFound) match; only the Message diverges. Recorded behavior: for an update against a namespace that was deleted, the NamespaceNotFound message IS the namespace id from the request — no fixed text at all, the whole body is the request's Id value. (The same recordings show GetNamespace's NamespaceNotFound message EMPTY, so the rule is per-operation: this operation echoes the id, the read does not.)
Emulator: HTTP 404 NamespaceNotFound with an empty Message.
Why: a client that reads this message to learn which namespace was rejected (the one place AWS reports it for this operation) gets nothing, and the asymmetry that distinguishes the update's error from the read's error is lost — both become indistinguishable empty bodies.
Fix: the NamespaceNotFound construction in UpdatePrivateDnsNamespace's handler (src/ops/update_private_dns_namespace.rs), so the error's message is the resolved input Id. NOTE: the open issue ...-8-fidelity-divergences-missing-dnsconfig.md names this echo-the-id rule for UpdateHttpNamespace only, under its Cause 8; UpdatePrivateDnsNamespace is a separate handler and separate replay keys.
Traces: servicediscovery.update-namespace-not-found-error and servicediscovery.update-private-dns-namespace-properties — in both, every other assertion passes (the Description mutates in place with Id and Arn unchanged, GetNamespace reflects it, DeleteNamespace's operation reaches SUCCESS, GetNamespace then returns NamespaceNotFound with the correct EMPTY message, and the failed update resurrects nothing); both fail on exactly this message.
