# omics: 4 net-new root causes — StartRun refuses a run with no storageCapacity (positive control hangs), unknown-workflow not-found wording, CreateWorkflowVersion 501s instead of 404, and CloudFormation does not recognize AWS::Omics::RunGroup

> _Note: this issue was identified against the code base at commit `92c3b140342b1bc1fab2a232b8cee3f25ea78ff5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartRun

## Description
Four distinct net-new root causes in the HealthOmics (omics) emulator, all grounded in failing behavioral checks of this suite. The already-filed scaffold-stub issues for CreateSequenceStore, CreateRunGroup, CreateShare, CreateRunCache and CreateWorkflowVersion are NOT these causes and do not cover them; each cause below must be closed on its own before submitting.

=== Cause 1 of 4: StartRun invents a storageCapacity requirement and refuses a run real AWS accepts (check: omics.start-run-missing-workflow-not-found-rejected) ===
AWS: StartRun requires only roleArn, outputUri, requestId and a workflow reference (Smithy: StartRunRequest.roleArn/outputUri/requestId @required; storageCapacity is OPTIONAL, Integer @range 0..100000; storageType is OPTIONAL, StorageType enum DYNAMIC|STATIC). Recorded behavior: a StartRun that names a real, ACTIVE private workflow and supplies roleArn + outputUri + requestId + name, and names NEITHER storageType NOR storageCapacity (and whose workflow declared neither default), is ACCEPTED — the check's positive control asserts it returns a run id, and the operation's modeled success is HTTP 201. AWS resolves the capacity itself for such a run rather than refusing the request.
Emulator: the run resolves to the STATIC storage type and, because no storageCapacity was supplied anywhere, the handler refuses with 400 ValidationException whose message is the emulator's own text "storageCapacity is required for a run with the STATIC storage type". Because the check's role-propagation retry wrapper retries while StartRun answers ValidationException or AccessDeniedException, the call is refused repeatedly and the check never reaches a verdict: the suite reports "Check timed out after 60.0s". Hypothesis (code path, from reading the handler): the refusal is the storage-type branch in the StartRun handler; the suite output itself only proves the check spent its whole 60 s budget in a path whose sole 60 s wait is that ValidationException/AccessDeniedException retry loop.
Why: a client that starts a run the way AWS documents (no storageType, no storageCapacity) can never start a run at all against this emulator. Every downstream behavior — GetRun, ListRuns, CancelRun, DeleteRun, run-status progression — becomes unreachable, and a caller cannot distinguish "my request is invalid" from "this operation refuses everything".
Fix: StartRun's validation/defaulting in the operation's handler (services/service-com-amazonaws-omics-omics/src/ops/start_run.rs, the storage_type/storage_capacity resolution and the ValidationException it raises) plus the defaults it reads from crate::state. A run that resolves to STATIC with no capacity named anywhere must be accepted and given a capacity, not refused; only values outside the modeled range are refusable, and any refusal must carry AWS's wording for that class, not emulator prose.
Traces: omics.start-run-missing-workflow-not-found-rejected.

=== Cause 2 of 4: StartRun's unknown-workflow ResourceNotFoundException message is emulator-authored (check: omics.start-run-missing-workflow-not-found-rejected) ===
AWS: StartRun with a workflowId no workflow holds is refused with ResourceNotFoundException (Smithy: StartRun errors include ResourceNotFoundException, httpError 404). Recorded behavior: the message is the fixed text "Workflow " + the requested workflowId + " not found" — fixed text "Workflow" and "not found", with the workflow id taken verbatim from the request (the check asserts exactly this string for the id it sent).
Emulator: the handler composes its own sentence instead, of the form "no <workflowType> workflow with id <workflowId> exists in this region" (and, for the sibling reference members, "<member> names <resource> <value>, which does not exist in this region; <resource>s are not emulated yet"). The status and code are right; the message text is not AWS's.
Why: a client that matches, logs or surfaces the not-found message — and any test or runbook asserting on it — sees text AWS never produces, and the "not emulated yet" phrasing leaks emulator internals into a response a caller treats as service output.
Trace note: this assertion sits after the positive control, so Cause 1 masks it at replay time; it is grounded in the check's recorded expectation together with the message template in the handler. Fixing Cause 1 alone will leave this check failing on the message assertion.
Fix: the message construction for StartRun's ResourceNotFoundException in that operation's handler (services/service-com-amazonaws-omics-omics/src/ops/start_run.rs, the workflow-resolution and reference-member not-found branches).
Traces: omics.start-run-missing-workflow-not-found-rejected.

=== Cause 3 of 4: CreateWorkflowVersion answers 501 NotImplemented where AWS answers 404 ResourceNotFoundException for a missing workflow (check: omics.create-workflow-version-missing-workflow-not-found-rejected) ===
AWS: CreateWorkflowVersion is bound to a workflow by its @httpLabel workflowId (Smithy: POST /workflow/{workflowId}/version, workflowId @required, success 201; errors include ResourceNotFoundException httpError 404, ValidationException 400). Recorded behavior: a CreateWorkflowVersion whose workflowId names no workflow is refused with ResourceNotFoundException and the message "Workflow " + requested workflowId + " not found" (fixed text "Workflow"/"not found", id from the request), and ListWorkflowVersions on that same nonexistent workflowId is refused the same way with the same message.
Emulator: the call is answered "An error occurred (NotImplemented) when calling the CreateWorkflowVersion operation: operation CreateWorkflowVersion is scaffolded but not implemented in this emulator" — a non-modeled error code (NotImplemented, HTTP 501) that is not in the operation's error set. Replay: "AssertionError: expected ResourceNotFoundException, got 'NotImplemented'".
Why: a client cannot tell a missing workflow from a broken service; the negative class AWS defines for this operation (and for ListWorkflowVersions) is unobservable, and a 501 is not retry- or branch-equivalent to a 404 for any SDK error handler.
Related filed issue: the suite's already-filed scaffold-stub issue for CreateWorkflowVersion (services/service-com-amazonaws-omics-omics/src/ops/create_workflow_version.rs) covers standing the operation up for the checks it blocks; it does NOT carry this check's replay key or this requirement. This cause records the behavior the implementation must have: a 404 ResourceNotFoundException with AWS's message for an unknown workflowId on both CreateWorkflowVersion and ListWorkflowVersions, and a 201 with status reaching ACTIVE for the same call against a real workflow.
Fix: implement the operation's handler and its not-found validation (services/service-com-amazonaws-omics-omics/src/ops/create_workflow_version.rs), resolving workflowId against the workflow store in crate::state and classifying an unresolved id as the modeled ResourceNotFoundException; the same resolution is owed by list_workflow_versions.rs.
Traces: omics.create-workflow-version-missing-workflow-not-found-rejected.

=== Cause 4 of 4: CloudFormation does not recognize AWS::Omics::RunGroup, so no HealthOmics resource can be deployed by a stack (check: omics.deploy-run-group-via-cloudformation-reaches-create-complete) ===
AWS: AWS::Omics::RunGroup is a supported CloudFormation resource type (the omics model carries CFN resource traits on the run-group surface, e.g. GetRunGroup's Id/Arn/Name/MaxCpus/MaxRuns/MaxDuration are the readable properties a stack's !GetAtt exposes). Recorded behavior: CreateStack with a template declaring Type: AWS::Omics::RunGroup is ACCEPTED, the stack reaches CREATE_COMPLETE, the run group is really provisioned (GetRunGroup reports the templated name/maxCpus/maxDuration/maxRuns), the stack's Outputs carry the resource's Id and Arn, and after DeleteStack GetRunGroup answers ResourceNotFoundException with the message "Run group " + id + " not found".
Emulator: CreateStack refuses the template outright with 400 ValidationError and the message "Template format error: Unrecognized resource types: [AWS::Omics::RunGroup]", so nothing is deployed and the deploy/describe/delete flow is unobservable.
Why: any infrastructure-as-code path (CloudFormation, SAM, CDK) that declares a HealthOmics run group fails at template validation, and a user cannot provision or tear down omics resources the way they do in AWS.
Fix: register AWS::Omics::RunGroup in CloudFormation's resource-type registry and give it a provisioner that creates/reads/deletes the run group in the omics service state (the CFN resource-type table plus an omics run-group provisioner), with !GetAtt Id/Arn resolving to the created resource's real id and ARN. This depends on the omics run-group resource existing (the already-filed CreateRunGroup scaffold-stub issue), but the unrecognized-resource-type refusal is a separate defect: the template is rejected before any omics call is made.
Traces: omics.deploy-run-group-via-cloudformation-reaches-create-complete.
