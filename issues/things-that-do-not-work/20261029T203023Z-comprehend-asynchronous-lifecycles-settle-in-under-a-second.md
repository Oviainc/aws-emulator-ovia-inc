# Comprehend asynchronous lifecycles settle in under a second, so IN_PROGRESS is unobservable and StopTrainingDocumentClassifier is a no-op (2 causes)

> _Note: this issue was identified against the code base at commit `6bd726e14a5c3a202f9e89e1e854b8dfcc8d4492`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StopTrainingDocumentClassifier

## Description
Two net-new root causes with one shared shape: the emulator's asynchronous state machines are driven by sub-second dwell spans, so every intermediate state exists only inside the first few hundred milliseconds after the create/start call. An out-of-process client polling Describe* on any realistic cadence never sees them, and — worse — a cancellation request that arrives after the machine has already settled is silently dropped, so the cancelled terminal state is unreachable.

Cause 1 of 2: an analysis job goes SUBMITTED -> COMPLETED with no observable IN_PROGRESS.
  AWS: Smithy: JobStatus enum = SUBMITTED | IN_PROGRESS | COMPLETED | FAILED | STOP_REQUESTED | STOPPED, and StartDominantLanguageDetectionJob$JobStatus documents the walk: "SUBMITTED - The job has been received and is queued for processing. IN_PROGRESS - Amazon Comprehend is processing the job. COMPLETED - The job was successfully completed and the output is available." Recorded behavior: DescribeDominantLanguageDetectionJob reports IN_PROGRESS for the whole processing phase (minutes on real AWS), so a client polling every few seconds between the start call and completion always observes SUBMITTED, then IN_PROGRESS, then COMPLETED.
  Emulator: the job reaches COMPLETED without IN_PROGRESS ever being readable. In services/service-com-amazonaws-comprehend-comprehend-20171127/src/state.rs the dwell spans are QUEUE_SPAN = 300 ms (SUBMITTED -> IN_PROGRESS) and PROCESSING_SPAN = 300 ms (IN_PROGRESS -> terminal), so the entire IN_PROGRESS window is 300 ms wide and `AnalysisJob::settle` has already moved the record to its terminal status by the first poll.
  Why: a client that waits for IN_PROGRESS before attaching progress reporting, or that treats "never saw IN_PROGRESS" as a dropped job, hangs or errors; more generally any code exercising the documented three-state walk cannot observe it. The window must be wide enough that an out-of-process poller sees the phase, not merely non-zero.
  Fix: the analysis-job lifecycle in state.rs — the QUEUE_SPAN/PROCESSING_SPAN dwell band (and the span carried forward by `AnalysisJob::record_run_outcome`) must keep each non-terminal phase observable to a client polling Describe* from another process.
  Traces: comprehend.dominant-language-detection-job-completes-and-writes-output.

Cause 2 of 2: a document classifier finishes training before any stop can land, so StopTrainingDocumentClassifier never produces STOP_REQUESTED or STOPPED.
  AWS: Smithy: ModelStatus enum = SUBMITTED | TRAINING | DELETING | STOP_REQUESTED | STOPPED | IN_ERROR | TRAINED | TRAINED_WITH_WARNING; StopTrainingDocumentClassifier is documented as "Stops a document classifier training job while in progress. If the training job state is TRAINING, the job is marked for termination and put into the STOP_REQUESTED state. If the training job completes before it can be stopped, it is put into the TRAINED; otherwise the training job is stopped and put into the STOPPED state and the service sends back an HTTP 200 response with an empty HTTP body." Recorded behavior: training takes minutes, so a stop issued once the classifier is observed TRAINING reliably takes the STOP_REQUESTED -> STOPPED branch, and DescribeDocumentClassifier then reports Status STOPPED.
  Emulator: after StopTrainingDocumentClassifier returns 200, DescribeDocumentClassifier reports Status 'TRAINED' and never STOPPED. In state.rs the classifier dwell spans are CLASSIFIER_SUBMITTED_SPAN plus CLASSIFIER_TRAINING_SPAN = 450 ms, and `terminal_due_at` is set to `submit_time + CLASSIFIER_SUBMITTED_SPAN + CLASSIFIER_TRAINING_SPAN` at creation, so by the time any client issues the stop the record has already settled to TRAINED. `DocumentClassifier::request_stop` matches only "SUBMITTED" and "TRAINING" and returns silently on every other status, so the stop is dropped: the handler (src/ops/stop_training_document_classifier.rs, which calls `store.settle_document_classifiers(now)` and then `classifier.request_stop(now)`) answers 200 while changing nothing. The documented "completes before it can be stopped" escape hatch is not an excuse — here it is the ONLY reachable branch, so the STOP_REQUESTED and STOPPED statuses are dead states.
  Why: cancellation is effectively inoperative. A client that stops a training run to avoid cost and then waits for STOPPED waits forever and ends up with a TRAINED model it explicitly cancelled, and nothing exercising STOP_REQUESTED/STOPPED can ever be tested against the emulator.
  Fix: the document-classifier lifecycle in state.rs — the CLASSIFIER_SUBMITTED_SPAN/CLASSIFIER_TRAINING_SPAN dwell band must leave the TRAINING phase wide enough for an out-of-process stop to land, so `request_stop` takes the TRAINING branch and `DocumentClassifier::settle` materialises STOP_REQUESTED -> STOPPED.
  Traces: comprehend.document-classifier-lifecycle-training-to-stopped.

## Evidence
Cause 1 (comprehend.dominant-language-detection-job-completes-and-writes-output): after StartDominantLanguageDetectionJob returned a JobId, DescribeDominantLanguageDetectionJob was polled until terminal; the distinct JobStatus sequence observed was ['SUBMITTED', 'COMPLETED']. AssertionError: job never observed IN_PROGRESS, statuses seen: ['SUBMITTED', 'COMPLETED']. Expected the documented walk SUBMITTED -> IN_PROGRESS -> COMPLETED to be observable from the client. Source: state.rs QUEUE_SPAN = Duration::from_millis(300), PROCESSING_SPAN = Duration::from_millis(300).

Cause 2 (comprehend.document-classifier-lifecycle-training-to-stopped): CreateDocumentClassifier -> poll DescribeDocumentClassifier -> StopTrainingDocumentClassifier(DocumentClassifierArn=<arn>) returned HTTP 200 with an empty body -> poll DescribeDocumentClassifier until terminal: DocumentClassifierProperties.Status = 'TRAINED'. AssertionError: expected STOPPED after stop request, got 'TRAINED'. Neither STOP_REQUESTED nor STOPPED was ever observed. Source: state.rs CLASSIFIER_TRAINING_SPAN = Duration::from_millis(450), CLASSIFIER_STOPPING_SPAN = Duration::from_millis(300), `terminal_due_at: submit_time + CLASSIFIER_SUBMITTED_SPAN + CLASSIFIER_TRAINING_SPAN`, and `DocumentClassifier::request_stop` returning on the `_ =>` arm for a TRAINED record. The ARNs/job ids here are per-run values; the requirement is that the stop reaches a TRAINING classifier and that STOPPED is the resulting terminal status.

## Steps to Reproduce
1. Boot the emulator from mainline and replay the behavioral suite (simparity-behavioral-aws-v1).
2. Cause 1: create an S3 bucket plus a Comprehend data-access role, put one text object under input/, then call comprehend.StartDominantLanguageDetectionJob with InputDataConfig S3Uri s3://<bucket>/input/ (ONE_DOC_PER_FILE) and OutputDataConfig S3Uri s3://<bucket>/output/. Poll DescribeDominantLanguageDetectionJob(JobId=...) on any cadence of a second or more and record the distinct JobStatus values: only SUBMITTED then COMPLETED appear, never IN_PROGRESS.
3. Cause 2: upload a training CSV, call comprehend.CreateDocumentClassifier(DocumentClassifierName=..., DataAccessRoleArn=..., LanguageCode="en", InputDataConfig={S3Uri: s3://<bucket>/train.csv}), then call comprehend.StopTrainingDocumentClassifier(DocumentClassifierArn=<arn>) and poll DescribeDocumentClassifier until the status is terminal. The status is TRAINED; STOP_REQUESTED and STOPPED are never reported.
