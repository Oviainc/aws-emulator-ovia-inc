# SESv2 is unreachable: every request is refused 'AmbiguousService' by the sigv4-name router, and the pre-dispatch refusal is JSON-framed for awsQuery callers (2 causes)

> _Note: this issue was identified against the code base at commit `3dc196f76d19116b5d570e1dc438e2b93d0e0d47`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEmailIdentity

## Description
Two root causes, both in the pre-dispatch request router / service registry, not in any SESv2 operation handler. 0/100 sesv2 behavioral checks pass; 90 of them are net-new replay keys not carried by any open issue (10 are already OWNED by 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md, whose Issue-Keys cover only sesv2|ListContactLists|AmbiguousService and sesv2|CreateEmailTemplate|AmbiguousService). That issue and 20261022T194351Z-firehose-s3-sesv2-ses-v2-is-unreachable-the-router-answers-ambiguousservice.md describe the same router defect from other replay keys; neither carries the keys listed here, so they must be re-replayed with this issue.

=== Cause 1 of 2: every sigv4-'ses' request is refused with the non-AWS code AmbiguousService instead of being dispatched to SESv2 ===
AWS: a client reaches exactly one service behind the endpoint it addressed. Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2): service SimpleEmailService_v2, version 2019-09-27, protocols [restJson1], sigv4Name 'ses', awsService.endpointPrefix 'email', arnNamespace 'ses'; three further on-disk models share sigv4Name 'ses' (SES v1 SimpleEmailService awsQuery, AmazonPinpointEmailService restJson1, MailManagerSvc awsJson1_0/rpcv2Cbor). The signing name is therefore not an identity. Successful calls are 200 with the modeled output (Smithy: CreateEmailIdentity POST /v2/email/identities code 200; GetTenant POST /v2/email/tenants/get code 200; GetDedicatedIp GET /v2/email/dedicated-ips/{Ip} code 200), and refusals are the operation's own modeled client errors — NotFoundException (httpError 404), BadRequestException (400), AlreadyExistsException (400), InvalidNextTokenException (400), TooManyRequestsException (429). AmbiguousService is in no AWS model.
Emulator: no SESv2 request ever reaches a handler. Every operation exercised in this suite — CreateEmailIdentity, CreateConfigurationSet, CreateContactList, CreateTenant, CreateDedicatedIpPool, CreateMultiRegionEndpoint, GetAccount, GetBlacklistReports, GetEmailAddressInsights, ListRecommendations, ListSuppressedDestinations — is answered with code 'AmbiguousService' and the message "4 emulated services all claim requests for 'ses': ses, ses, ses, ses; the request is rejected rather than served by an arbitrary one" (message quoted as an example; the code and the 5xx class are the requirement). Because it is served as a server fault, botocore retries it to exhaustion ('reached max retries: 3'). Where a check asserted a specific modeled refusal, this code arrives in its place: sesv2.tenant-get-unknown-rejected expected NotFoundException for GetTenant and got 'AmbiguousService'; sesv2.get-dedicated-ip-unknown-rejected expected NotFoundException and got 'AmbiguousService'; sesv2.list-suppressed-destinations-invalid-next-token-rejected expected InvalidNextTokenException; sesv2.import-job-invalid-data-source-rejected and sesv2.put-account-dedicated-ip-warmup-attributes-out-of-range-percentage-rejected expected BadRequestException.
Why: the whole SESv2 surface is dead for every client. No identity, configuration set, contact list, template, tenant, dedicated IP pool, multi-region endpoint, suppression entry, import/export job or tag can be created or read, so nothing downstream (sending, event destinations, VDM metrics, tenancy, reputation) is configurable or observable. The returned code is in no AWS model, so SDK error classification cannot place it and clients burn their full retry budget on a non-retryable condition.
Fix: the request router / service-registry resolution layer that selects a target service before operation dispatch. The four registrations claiming sigv4 name 'ses' must resolve to exactly one target per request using protocol + endpoint prefix + request shape (restJson1 /v2/email/... for SESv2, /v1/email/... for Pinpoint Email, awsQuery POST / with Action= for SES v1, awsJson1_0 X-Amz-Target with endpointPrefix 'mail-manager' for MailManager), never by signing name alone.
Traces: 89 of the check ids in trace_ids (all except sesv2.v1-template-token-continues-the-v2-list). Representative: sesv2.email-identity-lifecycle, sesv2.tenant-create-get-list-delete-lifecycle, sesv2.configuration-set-lifecycle, sesv2.suppressed-destination-put-get-delete-lifecycle, sesv2.tenant-get-unknown-rejected.

=== Cause 2 of 2: the pre-dispatch refusal is serialized with awsJson framing regardless of the addressed service's protocol ===
AWS: SES v1 (Smithy: SimpleEmailService, protocols [awsQuery], xmlNamespace http://ses.amazonaws.com/doc/2010-12-01/) answers every response, success or error, as XML; an error is an <ErrorResponse><Error><Code>/<Message></Error></ErrorResponse> envelope that the SDK surfaces as a ClientError carrying a Code. Recorded behavior only for the ambiguity condition itself (AWS has no such condition), but the protocol framing of an error response is fixed by the model.
Emulator: the router's refusal body is JSON — b'{"__type":"AmbiguousService","message":"4 emulated services all claim requests for \'ses\': ..."}' — served to the awsQuery caller. botocore cannot parse it and raises ResponseParserError ('Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received') instead of any ClientError, so the client sees no status/code pair at all.
Why: a query-protocol client cannot classify or stop retrying a pre-dispatch refusal; any such refusal the emulator emits for an awsQuery/ec2Query/restXml service is invisible to the SDK. This is also reported as cause 2 of 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md, which does not carry this replay key.
Fix: the gateway's error serializer for pre-dispatch failures must select the framing of the addressed service's protocol (XML ErrorResponse for awsQuery, awsJson '__type' only for JSON protocols).
Traces: sesv2.v1-template-token-continues-the-v2-list (the check drives the legacy v1 ListTemplates call whose token must continue the v2 list).
