# 6 net-new causes: custom-resource ResponseURL points at the real AWS host, no stack-level CREATE_FAILED/PROPERTY_VALIDATION on property validation, and AWS::SNS::Subscription update/replacement defects

> _Note: this issue was identified against the code base at commit `b4090e4eff86c6645a745aa23fbd4b95671a37a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Six distinct root causes in the cloudformation__sns__sqs suite. Each is listed with its own failing check ids; all six must be closed.

Cause 1 of 6 — the custom-resource ResponseURL is published as a real AWS endpoint, so no provider can ever answer. AWS: the ResponseURL in the custom-resource request is a pre-signed URL the provider PUTs its SUCCESS/FAILED response to; it must be an endpoint the provider can actually reach. Emulator: it publishes https://cloudformation-custom-resource-response.us-west-2.amazonaws.com/<url-encoded stack arn>|<logical id>|<request id>?X-Amz-... — a host that is not one of the emulator's own hosts (a client of the emulator needs http(s)://<the host:port it is reached on>/<resource path>). Every custom-resource round trip therefore hangs or errors. Why: Custom::* resources, CDK custom resources and the SAM/CDK providers built on them cannot complete; the provider's response is posted to the internet instead of the emulator. Fix: the ResponseURL/presigned-response-URL construction in the AWS::CloudFormation::CustomResource (Custom::*) handler — announce the address the emulator is reached on. Traces: cloudformation__sns__sqs.custom-resource-getatt-missing-data-key-fails, cloudformation__sns__sqs.custom-resource-response-over-4096-bytes-fails, cloudformation__sns__sqs.custom-resource-service-timeout-out-of-range-fails-the-resource, cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-failed-response-rolls-back-with-its-reason, cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-new-physical-id-on-update-triggers-cleanup-delete-of-old, cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-request-roundtrip-and-getatt-returns-response-data.

Cause 2 of 6 — a template that fails property validation emits no stack-level CREATE_FAILED event and no PROPERTY_VALIDATION rows. AWS: when a resource's properties fail schema validation (wrong type, missing required member), the STACK's own event stream carries a CREATE_FAILED row whose ResourceStatusReason is the fixed text 'Validation failed with 1 error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.' (the error count is the variable part), and the validation rows read (<LogicalId>, 'PROPERTY_VALIDATION', 'FAILED', 'FAIL', <detail>, <json pointer>) — e.g. detail 'Property [RawMessageDelivery] expected type: Boolean, found: String' at '/Resources/Subscription/Properties/RawMessageDelivery', or 'Required property [Protocol] not found' at '/Resources/Subscription/Properties'. Emulator: the stack goes CREATE_IN_PROGRESS -> ROLLBACK_IN_PROGRESS -> ROLLBACK_COMPLETE with no CREATE_FAILED row on the stack and no validation rows; the refusal only appears as a resource-handler failure. Why: a client cannot tell a property-validation failure from a provisioning failure, and the documented DescribeEvents diagnosis is absent. Fix: the CloudFormation property-validation stage (type/required checks against the resource schema, before provisioning) and the stack-event emitter. Traces: cloudformation__sns__sqs.cfn-subscription-raw-message-delivery-non-boolean-rejected-creates-nothing, cloudformation__sns__sqs.deploy-sns-subscription-missing-protocol-rejected.

Cause 3 of 6 — a custom resource that exceeds its ServiceTimeout never gets a rollback Delete request. AWS: when a custom resource fails (including by service timeout), the rollback sends the provider a Delete request for that logical resource. Emulator: no provider request arrives within 240s; the pending list stays empty. Why: providers leak whatever they created, because the cleanup request CloudFormation guarantees never comes. Fix: the Custom::* resource handler's rollback path. Traces: cloudformation__sns__sqs.custom-resource-service-timeout-fails-create.

Cause 4 of 6 — changing the create-only Endpoint of AWS::SNS::Subscription is classified as a non-replacement. AWS: Endpoint is create-only for AWS::SNS::Subscription, so a change set reports Replacement='True' (and RequiresRecreation='Always') for it, while RawMessageDelivery is updatable in place. Emulator: Replacement='False'. Why: a client reviewing a change set is told a destructive replacement is an in-place edit; the subscription that exists afterwards is not the one the plan described. Fix: the create-only/replacement metadata of the AWS::SNS::Subscription resource type used by change-set evaluation. Traces: cloudformation__sns__sqs.deploy-sns-subscription-endpoint-change-replaces-raw-delivery-change-updates-in-place.

Cause 5 of 6 — AWS::SNS::Subscription in-place property update is unimplemented, and the refusal is reported as the resource's failure reason. AWS: an update that must replace the subscription performs the replacement and, if the new TopicArn does not exist, fails with SNS's NotFound reason, leaving the original SubscriptionArn in place. Emulator: UPDATE_FAILED with 'NotImplemented: this emulator does not change the properties of an existing AWS::SNS::Subscription in place; the resource was left as it is.' — an emulator-authored sentence no AWS client can handle. Why: no stack containing a subscription can be updated; the reason text is not an AWS error. Fix: the AWS::SNS::Subscription resource handler's update/replace path. Traces: cloudformation__sns__sqs.deploy-sns-subscription-topic-arn-to-missing-topic-blocks-replacement-rolls-back.

Cause 6 of 6 — a nested sibling stack containing AWS::SQS::QueuePolicy plus an SNS subscription fails to create, rolling the root back. AWS: the root reaches CREATE_COMPLETE; both child stacks provision, each resolving the producer sibling's topic ARN via Fn::GetAtt Producer.Outputs.TopicArn. Emulator: the root ends ROLLBACK_COMPLETE with StackStatusReason 'The following resource(s) failed to create: [Good]. ' — the child whose template adds the QueuePolicy (with DependsOn) is the one that fails. Hypothesis: the AWS::SQS::QueuePolicy handler or the DependsOn ordering inside a nested stack fails the child; the recorded evidence only names the failing child. Why: nested-stack compositions that grant SNS->SQS delivery cannot be deployed. Fix: the nested-stack child provisioning path and the AWS::SQS::QueuePolicy handler. Traces: cloudformation__sns__sqs.cfn-nested-sibling-stacks-getatt-wiring-missing-queue-policy-blocks-delivery.
