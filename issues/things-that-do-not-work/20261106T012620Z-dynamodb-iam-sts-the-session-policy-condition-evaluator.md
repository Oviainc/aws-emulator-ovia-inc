# dynamodb__iam__sts: the session-policy condition evaluator refuses requests the policy ALLOWS — dynamodb:Select/dynamodb:Attributes are not derived from the request, and ForAllValues over an absent key evaluates FALSE (2 causes)

> _Note: this issue was identified against the code base at commit `ed195bdda9ffdbdf051f799fc5087e4de9084b05`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetItem

## Description
Two net-new root causes in the DynamoDB data-plane authorization gate as reached by an assumed-role session carrying an inline STS session policy. The emulator now DOES evaluate the session policy (so the earlier 'session policy is ignored, the full item is served' state is past), but it decides conditioned statements wrongly in the restrictive direction: compliant requests are refused AccessDeniedException. Open issues that do NOT carry these replay keys as graded requirements and must not be mistaken for coverage: 20261105T054223Z-dynamodb-iam-sts-dynamodb-data-plane-ignores-the-session-policy-s.md (same check id, but it grades the OPPOSITE outcome — an unprojected full read being SERVED — and its Fix paragraph is what, applied partially, produced the behaviour below) and 20261031T102348Z-dynamodb-iam-sts-dynamodb-data-plane-authorization-ignores-session-policies-and.md. Close them together with this one.

=== Cause 1 of 2: dynamodb:Select and dynamodb:Attributes are not derived from the request, so a conditioned Allow never matches and a compliant projected read is denied ===
AWS: recorded behavior only for the refusal shape — the Smithy model for GetItem/Query/BatchGetItem declares InternalServerError, InvalidEndpointException, ProvisionedThroughputExceededException, RequestLimitExceeded, ResourceNotFoundException and ThrottlingException and NO AccessDeniedException, and carries no authorization trait, so the oracle is the recorded AWS response. DynamoDB derives its request-level condition keys from the request itself: dynamodb:Select is the explicit Select, or SPECIFIC_ATTRIBUTES when the request carries a ProjectionExpression (or AttributesToGet) and no Select; dynamodb:Attributes is the set of attribute names the request projects, including the key attributes it addresses; dynamodb:LeadingKeys is the partition-key value(s) addressed. A session policy of the form {"Effect":"Allow","Action":["dynamodb:GetItem","dynamodb:Query","dynamodb:BatchGetItem"],"Resource":<table ARN>,"Condition":{"ForAllValues:StringEquals":{"dynamodb:LeadingKeys":[<allowed pk>],"dynamodb:Attributes":[<visible names>]},"StringEquals":{"dynamodb:Select":"SPECIFIC_ATTRIBUTES"}}} therefore ADMITS GetItem(Key=<allowed pk>, ProjectionExpression='<visible names>') and serves exactly the projected attributes.
Emulator: that admitted request is refused AccessDeniedException with "User: <session ARN> is not authorized to perform: dynamodb:GetItem on resource: <table ARN> because no session policy allows the dynamodb:GetItem action" — the correct refusal wording, served for a request the session policy allows. The conditioned Allow cannot match because the two keys it tests are never populated from the request, so the statement is treated as non-matching rather than satisfied.
Why: this is a false denial of a credential's whole intended use. Field-level tenancy and PII-withholding credentials — vended precisely so a reader can see only a projection — can read NOTHING at all; the positive path of every projection-scoped session policy is dead. A client cannot distinguish 'my policy is wrong' from 'the service cannot evaluate the key my policy tests', and the refusal wording asserts the policy does not allow an action the policy does allow.
Fix: the DynamoDB data-plane authorization path (the GetItem/Query/BatchGetItem handlers' request-condition-context builder) must populate dynamodb:Select (explicit Select, else SPECIFIC_ATTRIBUTES when a projection is present), dynamodb:Attributes (projected names plus addressed key attributes) and dynamodb:LeadingKeys (addressed partition-key values) before evaluating identity and session policies, so a conditioned clause is DECIDED on the request's own values instead of failing for want of a key.
Traces: dynamodb__iam__sts.xsvc-dynamodb-2-attributes-select-specific-full-item-read-denied.

=== Cause 2 of 2: ForAllValues over a condition key ABSENT from the request context evaluates FALSE instead of TRUE, so Scan and a key-less PartiQL SELECT are denied ===
AWS: recorded behavior only (same modeling note as Cause 1). IAM's ForAllValues set operator has empty-set semantics: when the request context contains NO value for the tested multivalued key, the condition evaluates TRUE. A Scan and a key-less PartiQL SELECT address no partition key, so they carry no dynamodb:LeadingKeys; a session policy whose ONLY condition is {"ForAllValues:StringEquals":{"dynamodb:LeadingKeys":[<allowed pk>]}} therefore ALLOWS them, and they return every partition of the table — which is exactly why AWS documents adding a {"Null":{"dynamodb:LeadingKeys":"false"}} guard to close that hole. With the guard present the same Scan and SELECT are refused AccessDeniedException "User: <session ARN> is not authorized to perform: dynamodb:<Scan|PartiQLSelect> on resource: <table ARN> because no session policy allows the dynamodb:<Scan|PartiQLSelect> action" (fixed text "User: ", " is not authorized to perform: dynamodb:", " on resource: ", " because no session policy allows the dynamodb:", " action"; the session ARN, table ARN and the repeated action name are values from the session and the request).
Emulator: under the UNGUARDED session policy the Scan is refused with that very message, i.e. the absent LeadingKeys makes ForAllValues evaluate FALSE. The refusal is raised as an uncaught AccessDeniedException on the Scan that should have succeeded, so the guarded half of the contract — where the Null guard must turn that same Scan and SELECT into refusals while keyed reads keep working — is never reached and remains ungraded.
Why: a client that reads 'ForAllValues is not a guard on its own' from AWS's docs and adds the Null guard sees no difference between the two policies here, because the unguarded one already denies. The over-permissive hole the guard exists to close is invisible, so a control proving the guard works passes for the wrong reason, and legitimate unkeyed scans under a LeadingKeys-scoped credential are refused.
Fix: the IAM condition evaluator's set-operator handling used by the DynamoDB data-plane authorization path — ForAllValues:<operator> over a key with no value in the request context must evaluate TRUE (and ForAnyValue over an absent key FALSE), with the Null operator the only thing that tests presence.
Traces: dynamodb__iam__sts.xsvc-dynamodb-2-leading-keys-scan-unguarded-leaks-guarded-denied.
