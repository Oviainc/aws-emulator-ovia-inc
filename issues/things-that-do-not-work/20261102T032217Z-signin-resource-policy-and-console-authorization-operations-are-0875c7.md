# signin resource-policy and console-authorization operations are STILL unreachable: the SDK is addressed to the public host signin.<region>.api.aws instead of the endpoint under test (2 causes)

> _Note: this issue was identified against the code base at commit `9d7649b3311435a15d98db18f1b7b1fd192e85c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

=== Cause 1 of 2: the four resource-based-policy operations are addressed to the public regional host signin.<caller-region>.api.aws, so no request reaches the emulator ===
AWS: GetResourcePolicy (POST /get-resource-policy), ListResourcePermissionStatements (POST /list-resource-permission-statements), PutResourcePermissionStatement (POST /put-resource-permission-statement) and DeleteResourcePermissionStatement (POST /delete-resource-permission-statement) are ordinary restJson1 operations bound to the signin service and served on the signin endpoint for the caller's own region (Smithy: service Signin 2023-01-01, protocols [restJson1], awsService sdkId/endpointPrefix/arnNamespace 'signin', sigv4Name 'signin', standardRegionalEndpoints with the aws-partition special case https://{region}.signin.aws.amazon.com; endpointResolution.endpointRuleSet true). Modeled refusals (Smithy): GetResourcePolicy -> ResourceNotFoundException; ListResourcePermissionStatements and DeleteResourcePermissionStatement -> ResourceNotFoundException + ValidationException; PutResourcePermissionStatement -> ConflictException + ServiceQuotaExceededException + ValidationException; all four additionally carry the service-common AccessDeniedException. Recorded behavior for the asserted payloads: a baseline account with no policy answers ResourceNotFoundException whose message is the fixed text "Requested resource not found" (no variable part); a principal without the capability is refused AccessDeniedException whose message is the fixed template "No Access to <OperationName> API" where the operation name is the only variable part, taken from the request's target ("No Access to PutResourcePermissionStatement API", "No Access to DeleteResourcePermissionStatement API"); a statementId that violates the member's pattern is refused ValidationException whose message is the fixed template "1 validation error detected: Value '<value>' at 'statementId' failed to satisfy constraint: Member must satisfy regular expression pattern: [A-Za-z0-9+/]{64}=?", with <value> the rejected request value and the member name and pattern taken from the model.
Emulator: every request for these four operations is addressed to the host 'signin.<caller-region>.api.aws' (the public regional signin host for whatever region the client uses — 'signin.us-west-2.api.aws' in this run — not the endpoint under test), and the run's egress guard refuses it before any bytes reach the emulator: simparity.egress.EgressRefused: "egress refused: 'signin.us-west-2.api.aws' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on". No HTTP status, error code or body is ever produced for these operations. Decisive evidence that the divergence tracks the OPERATION and not the client: in the same run the signin OAuth2 operations on an identically built ctx.client("signin") (same region, same credential path) reach 127.0.0.1 and are answered (8 checks pass), and in signin.put-resource-permission-statement-concurrent-same-token-idempotent the preceding iam.create_user / put_user_policy / create_access_key calls all succeed against the emulator immediately before the first signin resource-policy call is refused. Hypothesis: these four routes are not registered on the served endpoint, so endpoint resolution falls back to the public signin ruleset host; alternatively the emulator answers them with a redirect/endpoint field carrying the public regional host.
Why: every client of signin's resource-based-policy surface is silently pointed at real AWS instead of the emulator, so nothing on that surface is observable — the ResourceNotFoundException "Requested resource not found" baseline, the AccessDeniedException capability gate, the malformed-statementId ValidationException and the paginated empty-list shape are all unreachable; in a network-permitted run the call would escape to the real service and mutate a real account.
Fix: the signin service's route/endpoint registration and any URL the emulator announces for these four operations — the signin crate's router/endpoint wiring plus the handlers for get_resource_policy, list_resource_permission_statements, put_resource_permission_statement and delete_resource_permission_statement under services/service-com-amazonaws-signin-signin. Every URL the emulator announces must be the endpoint it is reached on, and every region the service accepts must be served there.
Traces: signin.get-resource-policy-not-found-without-statements, signin.list-resource-permission-statements-baseline-empty-shape, signin.put-resource-permission-statement-access-denied-without-permission, signin.delete-resource-permission-statement-invalid-sid-rejected, signin.put-resource-permission-statement-concurrent-same-token-idempotent.

=== Cause 2 of 2: the three console-authorization operations are addressed to signin.us-east-1.api.aws, so a us-east-1 client never reaches the emulator ===
AWS: PutConsoleAuthorizationConfiguration (POST /put-console-authorization-configuration), GetConsoleAuthorizationConfiguration (POST /get-console-authorization-configuration) and DeleteConsoleAuthorizationConfiguration (POST /delete-console-authorization-configuration) are restJson1 operations served on the signin endpoint; Smithy models ResourceNotFoundException + ValidationException on all three and ConflictException additionally on Put, plus the service-common AccessDeniedException, and each returns {targetId, scope, consoleAuthorizationEnabled}. Recorded behavior: the write operations are region-locked to us-east-1 (a write from another region is a ValidationException whose message is the fixed text "Write operations only supported in us-east"), so a conforming client legitimately builds a us-east-1 client for this surface; reading or deleting a configuration that does not exist answers ResourceNotFoundException with the fixed message text "Console authorization configuration not found" (no variable part); a target organization the caller is not authorized for is refused AccessDeniedException with the fixed text "Caller is not authorized for this organization"; re-Putting an already-enabled target is ConflictException.
Emulator: a signin client for region us-east-1 is addressed to 'signin.us-east-1.api.aws' and the egress guard refuses it with the same EgressRefused text as Cause 1 ("egress refused: 'signin.us-east-1.api.aws' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator ..."). No console-authorization request reaches the emulator, so no status, error code or body exists for any of them.
Why: a client that follows AWS's own region-locking rule for this surface is pointed away from the emulator entirely — the emulated service appears to have no us-east-1 presence even though it is reached on one endpoint. The whole lifecycle contract is unverifiable: put -> get reports consoleAuthorizationEnabled=true; delete reports consoleAuthorizationEnabled=false in its OWN response and removes the record; a subsequent get and a second delete answer ResourceNotFoundException / "Console authorization configuration not found"; a double put conflicts; an unauthorized/nonexistent organization target is denied.
Fix: the signin service's region/endpoint routing so every region the service accepts (notably us-east-1, the only region that accepts these writes) is served on the endpoint under test, plus any URL announced by the console-authorization handlers (services/service-com-amazonaws-signin-signin, ops put/get/delete_console_authorization_configuration).
Traces: signin.put-get-console-authorization-configuration-enables, signin.get-console-authorization-configuration-not-found-when-unset, signin.console-authorization-configuration-disabled-after-delete, signin.console-authorization-configuration-full-lifecycle-workflow, signin.put-console-authorization-configuration-double-put-conflict-rejected, signin.put-console-authorization-configuration-nonexistent-org-rejected.
