# DescribeLocations availableProviders is a seeded partner list AWS does not publish

> _Note: this issue was identified against the code base at commit `ab6490681e1ab26d5567ff83a1d290924eb5dab0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeLocations

## Description
Cause 1 of 1: every Location the emulator answers from DescribeLocations carries an availableProviders list that is not the list AWS publishes for that facility, so all ten locations of the us-west-2 catalog diverge on that one member even though the status (200) and every other member of the element now match. Fixture directconnect-catalog-describe-locations step task#1.

AWS: Smithy (services/service-com-amazonaws-directconnect-overtureservice/smithy-model/com-amazonaws-directconnect-overtureservice.json) models DescribeLocations with input smithy.api#Unit and output Locations{locations: LocationList of Location{locationCode, locationName, region, availablePortSpeeds, availableProviders (ProviderList), availableMacSecPortSpeeds, availableBillingModes}}; errors DirectConnectClientException (400) and DirectConnectServerException (500). Location$availableProviders is documented only as "The name of the service provider for the location", and ProviderList is an ordered list of strings with no constraint on its members, so the CONTENT of the list is recorded behavior only: the operation takes no input and no caller identity narrows it, so what it answers is the public per-facility delivery-partner list for the signed Region, identical for every caller. The recording shows, per Location: the partner names AWS itself prints, in AWS's own (non-alphabetical, non-lexicographic) published order, and only partners that actually have presence at that facility -- for the carrier-hotel demarcations in us-west-2 roughly thirty entries beginning 'Pureport', 'Beanfield Metroconnect', 'ePLDT', 'Datapipe', 'Telstra', 'Colt', 'Verizon', 'Console Connect', ... and also carrying 'Internet2', 'Transtelco', 'Megaport', 'GTT', 'Layer42', 'Allstream', 'Equinix, Inc.', 'Zayo Group', 'Masergy', 'CenturyLink', 'AT&T', 'IX Reach', 'Comcast', 'Sprint', 'XO Communications', 'HopOne', 'RCN', 'PacketFabric', 'Telus', 'Arelion', 'China Mobile International', 'Epsilon'. Note the spelling AWS uses for several partners is the SHORT trade form -- 'Colt', 'GTT', 'Comcast', 'Console Connect' -- not the expanded company name.

Emulator: answers 200 with a hand-seeded, alphabetically sorted 30-entry provider list (plus three smaller regional subsets) that overlaps the published list only partly. At $.locations[0] ('EqSe2-EQ') it returns ['AT&T', 'Arelion', 'BT', 'CenturyLink', 'Cogent Communications', 'Cologix', 'Colt Technology Services', 'Comcast Business', 'Console Connect by PCCW Global', 'CoreSite', 'Cox Business', 'Crown Castle', 'Digital Realty', 'Equinix, Inc.', 'Flexential', 'GTT Communications', 'Internet2', 'Lumen Technologies', 'Megaport', 'NTT Communications', 'Orange Business Services', 'PacketFabric', 'Rogers Communications', 'Sify Technologies', 'Tata Communications', 'Telstra', 'Verizon', 'Vodafone', 'Windstream', 'Zayo Group']. Three faults in one list: (a) partners the recorded catalog lists are absent entirely (Pureport, Beanfield Metroconnect, ePLDT, Datapipe, Transtelco, Layer42, Allstream, Masergy, IX Reach, Sprint, XO Communications, HopOne, RCN, Telus, China Mobile International, Epsilon); (b) partners the recorded catalog never lists are invented (BT, Cogent Communications, Cologix, CoreSite, Cox Business, Crown Castle, Digital Realty, Flexential, Lumen Technologies, NTT Communications, Orange Business Services, Rogers Communications, Sify Technologies, Vodafone, Windstream); (c) shared partners are renamed to an expanded company form AWS does not print ('Colt Technology Services' for 'Colt', 'GTT Communications' for 'GTT', 'Comcast Business' for 'Comcast', 'Console Connect by PCCW Global' for 'Console Connect'), and the whole list is emitted in sorted order rather than the order AWS publishes. Because ProviderList is an ordered member of the Location element, each of $.locations[0] through $.locations[9] is reported as the whole element missing.

Why: availableProviders is how a client discovers which delivery partner it can order a hosted connection or a cross connect through at a given locationCode, and the provider name it reads here is the string it carries forward (e.g. as CreateConnection/AllocateConnectionOnInterconnect providerName, or into partner-selection UI and policy). Against the emulator a client resolves partners that exist at no AWS facility, fails to resolve the partners that do, and matches on a spelling AWS never returns -- so provider-selection, provider allow/deny lists and any snapshot comparison of the DescribeLocations catalog all validate against a fiction, and code that works on the emulator breaks on AWS and vice versa. A strict client or test that compares the full Location element sees every location diverge.

Fix: the seeded location catalog in this service's state -- the provider constants and the per-facility provider assignment, not the handler, which only renders what is stored. The provider names must be the strings AWS prints (short trade forms where AWS uses them) in AWS's published order rather than sorted, and each facility's list must be the partners actually published for that facility rather than a shared alphabetized superset.
