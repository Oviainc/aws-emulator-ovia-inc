## Operation
InvokeWithResponseStream

## Description
AWS: Smithy (lambda) InvokeWithResponseStream — POST /2021-11-15/functions/{FunctionName}/response-streaming-invocations, success code 200. Output InvokeWithResponseStreamResponse carries StatusCode (httpResponseCode), ExecutedVersion (header X-Amz-Executed-Version, e.g. $LATEST), ResponseStreamContentType (header Content-Type) and EventStream (httpPayload, @streaming union InvokeWithResponseStreamResponseEvent) — i.e. PayloadChunk frames as the handler writes them, then an InvokeComplete frame that carries ErrorCode/ErrorDetails only when the handler itself failed, plus LogResult. The modeled error set is the Invoke family (InvalidRequestContentException 400, InvalidParameterValueException 400, ResourceNotFoundException 404, RequestTooLargeException 413, TooManyRequestsException 429, ServiceException 500, and the 502 EC2/ENI/KMS/runtime family: EC2AccessDeniedException, EC2ThrottledException, EC2UnexpectedException, ENILimitReachedException, InvalidRuntimeException, KMS*Exception, ResourceNotReadyException, …). NotImplemented is NOT a modeled error: a function that exists and is Active is executed and its bytes are streamed back.

Emulator: the call is refused with error code 'NotImplemented' and the message 'InvokeWithResponseStream resolved <function ARN> at version <qualifier>, but running its <runtime> deployment package is not implemented in this emulator: there is no in-process runtime for it, so no response chunk, trailer error code or log tail is streamed that the function did not produce. InvocationType=DryRun validates an invocation without running the function.' The fixed text is everything outside the angle brackets; the function ARN, the resolved version and the runtime identifier come from the request and the emulator's own state (observed with nodejs20.x, nodejs22.x and python3.12). Control-plane resolution clearly works (the ARN and $LATEST are resolved and named) — only execution/streaming is absent. The refusal is built in `services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke_with_response_stream.rs`, at the end of `InvokeWithResponseStream::invoke`, which is reached only after the request has been read through the model's bindings, the function and version resolved, the lifecycle state checked and the payload bounded — all of which already work.

Why: no client can observe anything that streaming exists for. Time-to-first-byte is unobservable (a chunk never arrives before the handler returns), the chunk boundaries that map onto the handler's writes never exist, a handler that throws after the first chunk can never be distinguished from a service refusal because the trailer ErrorCode/ErrorDetails never arrive, and a provisioned-concurrency streaming invocation can never be shown to run from a prewarmed environment. Every one of these is a documented, load-bearing property of response streaming.

The ONE blocker, for whoever picks this up: the bytes AWS streams here are the OUTPUT OF THE CUSTOMER'S HANDLER — the nodejs20.x / nodejs22.x / python3.12 deployment package the function was created with, wrapped in `awslambda.streamifyResponse` — and this emulator has no in-process runtime that runs one. `vendor/engine/src/lib.rs` states the contract for execution that IS in scope ("user-provided code … run under that language's documented semantics, so the result is what the real service returns for ANY code of that runtime, not only for the code a test happens to use") and the same gap is what the synchronous operation answers 501 for (`src/ops/invoke.rs`, and its own open issue `20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md`, whose Issue-Key is `lambda|Invoke|NotImplemented` and which does NOT cover this operation: InvokeWithResponseStream is a separate operation with its own URI, output shape, event-stream framing and trailer semantics). Inventing a chunk sequence, a trailer error code or a log tail for a handler that never ran would be output synthesised to look computed, and answering one error code instead of another would only re-word the same refusal, so neither is a fix.

What is left to do in THIS crate once a deployment package can actually be run: the execution and event-stream framing path of `InvokeWithResponseStream` — PayloadChunk frames emitted AS the handler writes them (so the first chunk reaches the client before the handler returns), the terminal InvokeComplete frame carrying ErrorCode/ErrorDetails only when the handler itself failed plus LogResult, `ResponseStreamContentType` on the response, and the error mapping, which must never answer NotImplemented for a function that resolved. The framing helper the operation will reach for is `service_common::event_stream`. What already works and must be preserved: `InvocationType=DryRun` validation without running the function, the 404 for a name/qualifier pair that resolves to nothing, the 409 inside the provisioning window, the 413 past the synchronous payload limit and the 400 for a body that is not JSON.

Expect HTTP 200 plus PayloadChunk frames and a terminal InvokeComplete frame; the emulator answers error code NotImplemented.
