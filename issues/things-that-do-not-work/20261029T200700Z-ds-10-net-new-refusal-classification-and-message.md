## Description
Behavioral replay of the ds suite (simparity-behavioral-aws-v1) against this emulator left these failing checks after skipping every check the report marks ALREADY FILED (scaffold stubs CreateInternetGateway, DescribeCAEnrollmentPolicy, DeregisterCertificate, EnableSso, CancelSchemaExtension) or OWNED by an open issue. Cause 1 of 10: AddIpRoutes refuses an already-routed CIDR with the wrong error class and an emulator-authored message.
AWS: Smithy: AddIpRoutes (input DirectoryId @pattern ^d-[0-9a-f]{10}$, IpRoutes @required) models BOTH ClientException and EntityAlreadyExistsException as client errors, HTTP 400, so the model does not disambiguate; the recorded behavior the checks state (measured on real AWS) does: re-adding a CIDR the directory already routes is refused HTTP 400 ClientException. Message template — fixed text "The IP route(s) [<cidr>] already exist. If you want to recreate them, please delete the existing routes first. : RequestId: <request id>"; variable parts: the CIDR taken from the request's IpRoutes entry and the per-run request id (the id itself is not a requirement).
Emulator: HTTP 400 with code EntityAlreadyExistsException and the message "Directory <directory id> already routes the address block <cidr> : RequestId: <id>" — both the code an SDK maps to a typed exception and the whole fixed text diverge.
Why: a caller's duplicate-route branch is keyed on ClientException (that is what AWS raises), so it never runs, and a benign duplicate surfaces as an unexpected entity conflict; any client or test that matches the "already exist … please delete the existing routes first" text fails to match.
Fix: the duplicate-block branch of the AddIpRoutes handler (src/ops/add_ip_routes.rs) — refuse with ClientException carrying AWS's route-already-exists diagnostic.
Traces: ds.add-ip-routes-duplicate-rejected, ds.add-ip-routes-overlapping-conflict.

Cause 2 of 10: CreateConditionalForwarder's list-member constraint violation is reported per element instead of aggregated per list member.
AWS: Smithy: CreateConditionalForwarder.DnsIpAddrs targets DnsIpAddrs whose members carry the IPv4 pattern ^(?:(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)\.){3}(?:25[0-5]|2[0-4][0-9]|[01]?[0-9][0-9]?)$; a violating entry is refused before any forwarder is stored, HTTP 400, __type ValidationException (the framework-level class, not in the operation's modelled error list). Message template — fixed text "1 validation error detected: Value '[<offending entries, comma-space separated>]' at '<list member path>' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy regular expression pattern: <pattern>]"; variable parts: the offending entries and the path ('dnsIpAddrs') from the request, the pattern from the model. The count prefix stays 1 for one list and element indices never appear in the path.
Emulator: same status and code, but "1 validation error detected: Value '999.999.999.999' at 'dnsIpAddrs.1.member' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>" — a per-element '.N.member' path, the bare value instead of the bracketed value list, and no "Member must satisfy constraint: [...]" wrapper.
Why: clients and suites that surface the failing member path to a user read 'dnsIpAddrs.1.member', a path AWS never emits, so field-level error mapping points at the wrong member; the aggregation rule also changes the error count for multi-entry lists.
Fix: the shared constraint-violation aggregator/serializer that builds the "N validation error(s) detected" body for this service (reached from CreateConditionalForwarder's pre-handler validation) — list-member violations must collapse to one entry keyed by the list's path.
Traces: ds.create-conditional-forwarder-invalid-dns-ip-rejected.

Cause 3 of 10: CreateMicrosoftAD accepts VpcSettings whose two subnets are in the SAME Availability Zone.
AWS: Smithy: CreateMicrosoftAD.VpcSettings is @required (DirectoryVpcSettings{VpcId, SubnetIds}) and the operation models ClientException (client, 400). Recorded behavior: a Managed Microsoft AD is Multi-AZ by requirement, so two real subnets in one AZ are refused HTTP 400 ClientException at the resource-semantics stage — after the subnet-id pattern check, so this refusal is DISTINCT from the ValidationException a malformed subnet id gets. Message template — fixed text "Invalid subnet ID(s). The two subnets must be in different Availability Zones. : RequestId: <request id>"; the request id is per-run.
Emulator: HTTP 200 with a created DirectoryId (replay: "CreateMicrosoftAD unexpectedly succeeded with VpcSettings={'VpcId': 'vpc-…', 'SubnetIds': ['subnet-…', 'subnet-…']}") — the AZ topology of the requested subnets is never resolved, so every topology is accepted.
Why: the two-subnets-in-two-AZs rule is the constraint callers most often get wrong; against this emulator an invalid deployment template provisions cleanly and then fails on AWS, and the distinction between a malformed id (validation) and an invalid topology (resource semantics) is lost.
Fix: the CreateMicrosoftAD handler (src/ops/create_microsoft_ad.rs) — resolve the requested SubnetIds' Availability Zones from EC2 state and refuse a single-AZ pair with ClientException carrying the AZ-topology diagnostic, after modelled constraint validation.
Traces: ds.create-directory-rejects-single-az-vpc-settings.

Cause 4 of 10: CreateTrust's duplicate-remote-domain refusal carries an emulator-authored message.
AWS: Smithy: CreateTrust (DirectoryId, RemoteDomainName, TrustPassword @sensitive, TrustDirection all @required) models EntityAlreadyExistsException (client, 400) with members Message and RequestId. Recorded behavior for a second trust to a remote domain the directory already trusts — fixed text "Trust already exists for directory: <directory id> and remote domain: <remote domain>. : RequestId: <request id>"; variable parts: the directory id and remote domain taken from the request, both UNQUOTED, the clause terminated with a full stop, and the per-run request id.

Fix: the duplicate-trust branch of the CreateTrust handler (src/ops/create_trust.rs) — word the refusal with AWS's template and feed the identifiers straight from the request.
Traces: ds.create-trust-duplicate-name-rejected.

Cause 5 of 10: DescribeDomainControllers' InvalidNextTokenException message is the model's doc sentence, not AWS's message.
AWS: Smithy: DescribeDomainControllers is @paginated (inputToken/outputToken NextToken) and models InvalidNextTokenException (client, 400) with members Message and RequestId. Cause 6 of 10: EnableDirectoryDataAccess's already-enabled refusal carries an emulator-authored message.

Cause 7 of 10: RemoveRegion's refusal ladder is wrong — no edition gate, no replica-entry lookup, and an invented primary-Region message.
AWS: Smithy: RemoveRegion (DirectoryId @required) models AccessDeniedException, ClientException, DirectoryDoesNotExistException, DirectoryUnavailableException, UnsupportedOperationException (all client, 400) and ServiceException (500). Recorded behavior, two distinct branches: (a) on a STANDARD-edition Managed Microsoft AD every multi-Region call is refused first by the edition gate — HTTP 400 UnsupportedOperationException, fixed text "Multi-region replication is only supported for AWS Managed Microsoft AD (Enterprise edition) directories. : RequestId: <request id>"; (b) on an ENTERPRISE directory that has never had AddRegion called, the per-Region lookup runs before any "is this the primary" check and finds no tracked replica entry, so the call is refused HTTP 400 DirectoryDoesNotExistException.
Emulator: both branches get the same single refusal — UnsupportedOperationException with "Region <region> is the primary Region of directory <directory id> and cannot be removed with RemoveRegion; use DeleteDirectory instead : RequestId: <id>" — wrong fixed text for (a) and the wrong error class for (b).
Why: the two branches mean different things to a caller (unsupported directory edition vs. no such replicated Region), and neither the edition precondition nor the replica inventory is consulted, so a multi-Region client cannot tell why its call was refused and sees a message AWS never sends.
Fix: the RemoveRegion handler (src/ops/remove_region.rs) — evaluate the edition gate first with AWS's edition message, then look the caller's Region up in the directory's tracked replica entries and refuse DirectoryDoesNotExistException when there is none; keep the primary-Region special case only where a replica entry actually exists.
Traces: ds.remove-primary-region-denied, ds.remove-region-primary-denied.

Cause 8 of 10: UnshareDirectory's not-shared refusal message is re-worded (identifiers quoted, label case changed).
AWS: Smithy: UnshareDirectory (DirectoryId, UnshareTarget @required) models DirectoryNotSharedException (client, 400; doc "The specified directory has not been shared with this Amazon Web Services account.") with members Message and RequestId. Recorded behavior — fixed text "Directory <directory id> is not shared with Account: <account id>. : RequestId: <request id>": the directory id and the target account id are taken from the request UNQUOTED, the label is "Account:" with a capital A, and the clause ends with a full stop before the " : RequestId: " separator.
Emulator: "Directory: '<directory id>' is not shared with account: '<account id>'. : RequestId: <id>" — an extra "Directory:" colon, both identifiers single-quoted and a lower-case "account:" label.
Why: this text is the requirement for the not-shared class; clients matching it (and recorded-response assertions) fail, and the user-visible wording differs from AWS's.
Fix: the not-shared branch of the UnshareDirectory handler (src/ops/unshare_directory.rs) and the shared ds message builder it uses — do not quote identifiers and keep AWS's labels.
Traces: ds.unshare-directory-not-shared-rejected.

Cause 9 of 10: CreateAlias has no Active-stage precondition — it succeeds against a directory that is not yet Active.
AWS: Smithy: CreateAlias (DirectoryId @required, Alias @required len 1-62 @pattern ^(?!D-|d-)([\da-zA-Z]+)([-]*[\da-zA-Z])*$) models ClientException, EntityAlreadyExistsException, EntityDoesNotExistException and InvalidParameterException (all client, 400). Recorded behavior: CreateAlias against a directory that has not reached Stage=Active is refused HTTP 400 InvalidParameterException and the directory gets NO alias while non-Active; once the SAME directory is Active the identical call succeeds and DescribeDirectories shows the alias.
Emulator: HTTP 200 with {"DirectoryId": "<id>", "Alias": "<alias>"} immediately after CreateMicrosoftAD returns — the alias is assigned with no stage check. Hypothesis (neither the model nor the recording states it): the emulator also reports the fresh directory as Active right away, which is the ground of 20261024T015148Z-ds-directory-service-a-new-microsoft-ad-is-instantly.md; either way CreateAlias itself never evaluates the stage it must gate on, so the refusal is unreachable for any input.
Why: a state-conflict boundary disappears — callers that rely on AWS refusing an alias on a provisioning directory build flows the real service rejects, and the InvalidParameterException branch of their error handling is never exercised.
Fix: the CreateAlias handler (src/ops/create_alias.rs) — refuse with InvalidParameterException unless the target directory's stage is Active, and keep the alias unassigned on refusal.
Traces: ds.create-alias-before-active-rejected.

Cause 10 of 10: DescribeDirectories refuses a deleted directory id with 400 EntityDoesNotExistException where AWS answers 200 with an empty list.
AWS: Smithy: DescribeDirectories (DirectoryIds list, NextToken, Limit) is @paginated over DirectoryDescriptions and models EntityDoesNotExistException (client, 400) — but recorded behavior is that once a directory is fully gone after DeleteDirectory, DescribeDirectories(DirectoryIds=[<id>]) answers HTTP 200 with DirectoryDescriptions = [] rather than raising; the id is also absent from the unfiltered listing, and only MUTATING calls against it refuse.
Emulator: HTTP 400 EntityDoesNotExistException for the deleted id (replay: "DescribeDirectories on the deleted directory must answer an empty list (HTTP 200), got EntityDoesNotExistException HTTP 400").
Why: a client that polls DescribeDirectories to confirm a deletion completed gets a thrown exception where AWS gives it a clean empty result, so deletion-wait loops and inventory reconciliations either crash or must special-case an error AWS does not raise.
Fix: the id-resolution path of the DescribeDirectories handler (src/ops/describe_directories.rs) plus the deleted-directory retention in src/state.rs — a requested id that no longer exists must be omitted from DirectoryDescriptions and answered 200, keeping the 400 for ids rejected on other grounds and for mutating operations.
Traces: ds.state-machine-directory-create-active-delete-404.
