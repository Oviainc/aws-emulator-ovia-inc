# GetTable table-schema catalog diverges from AWS column metadata

> _Note: this issue was identified against the code base at commit `7989461dab1376fa9328422991037f021a607176`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
GetTable answers HTTP 200 for every table in the data-exports catalog, but the Schema list it returns is a stale, paraphrased copy of AWS's column catalog rather than the catalog AWS serves. Across six recorded table reads the per-column Column.Description text diverges wholesale, and in two of them the divergence goes past prose into Column.Type and into whole column entries that are present on one side only. The shared root cause is the emulator's static GetTable column catalog: it carries one hand-written description set (and, for the two FOCUS table versions, ONE shared set reused for both versions), so it cannot reproduce AWS's per-table, per-version column metadata.

No open issue covers this. The open issue 20261023T074806Z-bcm-data-exports-tagresource-not-found-answers-404-and-gettable-unknown.md touches GetTable, but only its unknown-table ValidationException Message on the 4xx path (Issue-Key bcm-data-exports|GetTable|4xx->4xx|$.Message); every cause below is a 200-path response-body divergence and the replay reports owned_by=[] and stub_path='' for each. 6 causes.

Cause 1 of 6: the carbon-emissions table's column descriptions are a different text set.
AWS: Smithy GetTable (input TableName required @length 0..1024 @pattern ^[\S\s]*$; output Schema -> ColumnList of Column{Name, Type, Description}, Description doc 'The description for a column.') does not fix the catalog's contents, so this is recorded behavior only: the recording shows AWS returning HTTP 200 with a specific Description for each column of this table. Emissions-table columns such as product_code, region_code, location, last_refresh_timestamp, total_lbm_emissions_value, total_mbm_emissions_value and the total_scope_1/2/3_* family each carry AWS's own wording, e.g. product_code -> 'The code of the product measured. For example, Amazon EC2 is the product code for Amazon Elastic Compute Cloud.'
Emulator: HTTP 200, same status, but 19 Column.Description values differ, each a shorter paraphrase, e.g. product_code -> 'The code of the AWS service that is associated with the carbon footprint value.' and location -> 'The location that is associated with the carbon footprint value.'
Why: GetTable is the discovery call a client makes before CreateExport to learn what the table offers; a client that surfaces or indexes these descriptions shows text AWS never returns, and any consumer that keys off the catalog text sees a catalog that does not match the one the real service publishes.
Fix: the GetTable handler's static table catalog (the column data for the carbon-emissions table), not the serializer - the shape and status are already correct.
Traces: bcm-data-exports-catalog-get-table#task#1.

Cause 2 of 6: the account/usage cost table diverges in descriptions AND in which columns exist at all.
AWS: recorded behavior only (same Smithy surface as Cause 1). The recording returns 200 with AWS's wording for payer_account_name, linked_account_id, linked_account_name, purchase_option, ri_sp_arn, product_name, service, amortized_cost, unblended_cost, availability_zone, instance_type_family, platform, processor, processor_features, tenancy, legal_entity, region and more - e.g. purchase_option -> 'The purchase option for this line item possible values are SavingsPLan, Reserved, Spot, and OnDemand.' Critically, three divergence keys name the column ENTRY and not a member - $.Schema[Name="pricing_unit"], $.Schema[Name="product_from_location"], $.Schema[Name="product_to_location"] - i.e. those columns are present on only one side, so the emulator's column SET for this table is wrong, not merely its prose.
Emulator: HTTP 200 with 25 diverging keys: 22 Description paraphrases (e.g. purchase_option -> 'Whether your AWS usage is Reserved, On-Demand, or Spot.') plus the three whole-column entries above.
Why: a column that GetTable omits is a column a client cannot discover or request in an export definition, and an extra one is a column a client requests and the real service rejects. This turns a discovery read into a wrong export definition.
Fix: the GetTable handler's static table catalog for this table - reconcile the column list itself, then the per-column Description.
Traces: bcm-data-exports-catalog-get-table#task#2.

Cause 3 of 6: the line-item (CUR-style) table's column descriptions are truncated paraphrases, and the same stale catalog is served to a second fixture.
AWS: recorded behavior only. The recording returns 200 with AWS's full wording for the line_item_*, product_*, pricing_*, reservation_* and savings_plan_* families, e.g. line_item_usage_amount -> 'The amount of usage that you incurred during the specified time period. For size-flexible Reserved Instances, use the reservation_total_reserved_units column instead. Certain subscription charges will have a UsageAmount of 0.'
Emulator: HTTP 200 with roughly 70 diverging Column.Description values, consistently the AWS sentence with its qualifying clauses dropped, e.g. the same column -> 'The amount of usage that you incurred during the specified time period.' The identical cluster reproduces from a second fixture (bcm-data-exports-table-catalog-inspection#task#2), confirming one shared catalog rather than a fixture-specific response.
Why: the dropped clauses are exactly the usage caveats a client needs (which column to use for size-flexible RIs, that some charges report 0), so a client reading the catalog loses guidance AWS does ship.
Fix: the GetTable handler's static table catalog for the line-item table.
Traces: bcm-data-exports-catalog-get-table#task#3 (also bcm-data-exports-table-catalog-inspection#task#2).

Cause 4 of 6: the cost-optimization-recommendations table reports the wrong Column.Type for two columns.
AWS: recorded behavior only; Smithy Column.Type doc 'The kind of data a column stores.' The recording returns 200 with a specific Type for recommendation_lookback_period_in_days and for tags, plus AWS's own Description for current_resource_type, recommended_resource_type, action_type, current_resource_summary, recommended_resource_summary, estimated_monthly_cost_after_discount and the estimated_savings_percentage_* pair.
Emulator: HTTP 200 with 15 diverging keys, including $.Schema[Name="recommendation_lookback_period_in_days"].Type and $.Schema[Name="tags"].Type - the emulator declares a different data type than AWS - plus 13 Description paraphrases, e.g. estimated_monthly_cost_after_discount described as the RECOMMENDED resource's cost where AWS describes the CURRENT resource's cost (a semantic inversion, not just wording).
Why: Column.Type is what a client uses to type the parquet/CSV column it will read; a wrong Type produces a parse or cast failure downstream, and an inverted description makes a client attribute a cost to the wrong resource.
Fix: the GetTable handler's static table catalog for the recommendations table - correct the two Type values first, then the Description text.
Traces: bcm-data-exports-catalog-get-table#task#4.

Cause 5 of 6: the FOCUS 1.0 table's column descriptions diverge.
AWS: recorded behavior only. The recording returns 200 with AWS's wording for BillingPeriodStart/End, ChargePeriodStart/End, EffectiveCost, ListCost, ResourceType, ServiceName, Tags, x_CostCategories, x_Discounts, x_Operation, x_ServiceCode and x_UsageType, e.g. BillingPeriodEnd -> 'The exclusive end date and time of a billing period.' and EffectiveCost -> 'Cost inclusive of the impacts of all reduced rates and discounts, augmented with the amortization of relevant purchases (one-time or recurring) paid to cover future eligible charges.'
Emulator: HTTP 200 with 14 diverging Description values, e.g. BillingPeriodEnd -> 'Represents the exclusive end date and time of a billing period.' and a reworded EffectiveCost definition.
Why: FOCUS column descriptions are the specification text clients match against when mapping a FOCUS export; a rewritten definition is not the published one.
Fix: the GetTable handler's static table catalog, FOCUS 1.0 entry.
Traces: bcm-data-exports-catalog-get-table#task#5 (same cluster also covers #task#6).

Cause 6 of 6: the second FOCUS table version is served the SAME catalog text as FOCUS 1.0 instead of its own.
AWS: recorded behavior only. The recording shows AWS returning version-specific wording for this table version: BillingPeriodEnd -> 'The exclusive end bound of a billing period.', ChargePeriodStart -> 'The inclusive start bound of a charge period.', and the CommitmentDiscount* family worded as 'commitment discount' (CommitmentDiscountId -> 'The identifier assigned to a commitment discount by the provider.'), distinct from the other version's text.
Emulator: HTTP 200 with 32 diverging Description values, and the emulator's values for the shared columns are byte-identical to what it returned in Cause 5 ('Represents the exclusive end date and time of a billing period.'), plus 'commitment-based discount' wording throughout - proving one catalog entry is reused for both table versions rather than one per version.
Why: a client that reads the catalog to tell the two FOCUS versions apart cannot: the emulator reports the same metadata for both, so version-specific column semantics are invisible.
