# cloudwatch: 2 net-new root causes — PutManagedInsightRules accepts an unresolvable TemplateName with an empty Failures list, and the AWS/Lambda concurrency-metering check never completes (hangs to the 60 s harness cap)

> _Note: this issue was identified against the code base at commit `8c118d1d43e9fad6226f410894186130d2b1ac53`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutManagedInsightRules

## Description
Two net-new root causes in the cloudwatch service. They are what is left after every failing check the replay report marked ALREADY FILED or OWNED was removed, and after removing one check already carried verbatim by an open issue and one check whose only failing assertion is on generated model text (both named in the sweep summary). Each cause below must be closed before this issue is submitted.

=== Cause 1 of 2: PutManagedInsightRules accepts a ManagedRule entry whose TemplateName resolves to no managed-rule template and answers a blanket success with an empty Failures list. ===
Failing check id: cloudwatch.managed-insight-rules-server-side-enforcement.

AWS: Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/com-amazonaws-cloudwatch-graniteserviceversion20100801.json) models PutManagedInsightRules with input ManagedRules (@required list of ManagedRule) and output Failures: BatchFailures, a list of PartialFailure {FailureResource, ExceptionType, FailureCode, FailureDescription}. ManagedRule.TemplateName is @required, @length min 1 max 128, @pattern ^[0-9A-Za-z][\-\.\_0-9A-Za-z]{0,126}[0-9A-Za-z]$, and its documentation states it is "The template name for the managed Contributor Insights rule, as returned by ListManagedInsightRules" — i.e. the value is drawn from a server-side catalog, not invented by the client. ManagedRule.ResourceARN is @required, @length min 1 max 1024. The PartialFailure shape documentation states: "This array is empty if the API operation was successful for all the rules specified in the request. If the operation could not process one of the rules, the following data is returned for each of those rules." The operation's modeled top-level errors are InvalidParameterValueException (awsQueryError code InvalidParameterValue, HTTP 400) and MissingRequiredParameterException (MissingParameter, 400) — neither of which is how an unresolvable TemplateName is reported.
Recorded behavior pins the per-entry shape on an HTTP 200: a TemplateName that resolves to no managed-rule template yields exactly ONE PartialFailure entry — ExceptionType "ResourceNotFoundException", FailureCode "TEMPLATE_NAME", FailureDescription "Could not find template with the specified templateName.", FailureResource = the TemplateName submitted in the request. In that message, "Could not find template with the specified templateName." is entirely FIXED text (it carries no variable part and does not echo the submitted name); the only request-derived value in the entry is FailureResource. The recording measures this identically for two different ResourceARN types — a live DynamoDB table ARN and a live CloudWatch alarm ARN — which establishes that this is TemplateName validation against the catalog, not a per-resource-type eligibility signal. Nothing is enabled: ListManagedInsightRules for the resource still reports no rule.

Emulator: both calls answer HTTP 200 with the body {"Failures":[]} (content-type application/x-amz-json-1.0, content-length 15). The entry is accepted without the TemplateName ever being resolved. The legs of the same check that exercise the surrounding, correctly-implemented behavior all pass first and are NOT part of this cause: ListManagedInsightRules(ResourceARN=<live table ARN>) correctly returns an empty ManagedRules list, ListManagedInsightRules(ResourceARN="not-a-valid-arn-at-all") is correctly refused InvalidParameterValue with the message "INVALID_RESOURCE_ARN: Invalid ARN.", and ListManagedInsightRules on a valid alarm ARN correctly returns an empty list. So the gap is specifically the per-entry processing path inside PutManagedInsightRules.

Why: a caller cannot distinguish an enabled managed Contributor Insights rule from a silently dropped one. Tooling that enables a catalog of templates across an estate reads "all succeeded" from the empty Failures array, then builds dashboards, reports and alarms on rules that were never created, and never surfaces the bad template name that caused it. It is also an over-permissiveness divergence: the emulator accepts an identity a client invented, which real AWS refuses to resolve.

Fix: per-entry processing in the PutManagedInsightRules handler and the managed-insight-rule state it writes — each ManagedRule entry's TemplateName must be resolved against the managed-rule catalog (the same catalog ListManagedInsightRules reports from), and an unresolvable one must emit one PartialFailure carrying the submitted TemplateName as FailureResource, ExceptionType "ResourceNotFoundException", FailureCode "TEMPLATE_NAME" and the fixed FailureDescription above, while enabling only the entries that do resolve.

Related already-open issues, neither of which covers this check: 20261025T151319Z-cloudwatch-4-net-new-root-causes-cfn-deployed.md (its cause 2) describes the same empty-Failures gap for four OTHER checks, but its Issue-Trace-Ids and Issue-Keys do not carry cloudwatch.managed-insight-rules-server-side-enforcement, so a fixer re-replaying that issue's list never exercises the TEMPLATE_NAME/ResourceNotFoundException entry as THIS check asserts it (exactly one entry, for both a table ARN and an alarm ARN); and 20261025T020208Z-cloudwatch-putmanagedinsightrules-stub.md tracks the operation as an unimplemented scaffold stub, which it no longer is — it answers 200, so implementing the stub is not what this check grades.

Traces: cloudwatch.managed-insight-rules-server-side-enforcement — AssertionError at check line 142, "expected PutManagedInsightRules to flag an unrecognized TemplateName via exactly one TEMPLATE_NAME Failures entry".

=== Cause 2 of 2: the AWS/Lambda concurrency-metering check never reaches an assertion — it is killed at the suite's 60 s cap while still inside a pre-invoke poll, so neither the provisioned-concurrency allocation nor the account-level concurrency series can be observed. ===
Failing check id: cloudwatch__lambda.obs-lambda-1-reserved-burst-meters-function-concurrency-and-claimed-account-identity.

AWS: recorded behavior only — the Smithy models do not describe metric publication or allocation-state timing. Recorded: PutProvisionedConcurrencyConfig on an alias leaves GetProvisionedConcurrencyConfig reporting Status IN_PROGRESS and then READY (never stuck IN_PROGRESS, never FAILED for a valid, in-budget allocation). Lambda itself then publishes, off the response path, the AWS/Lambda series this check reads with GetMetricData at Period 60: ConcurrentExecutions dimensioned by FunctionName, Invocations and Throttles dimensioned by FunctionName, and the DIMENSIONLESS account-level series UnreservedConcurrentExecutions and ClaimedAccountConcurrency. Two recorded properties are the substance of the check: a reserved function's concurrent executions are charged to its reservation and NOT to the unreserved pool (so UnreservedConcurrentExecutions tracks only the unreserved function's burst), and at the same timestamp ClaimedAccountConcurrency minus UnreservedConcurrentExecutions equals the account's allocated concurrency as Lambda itself lists it (each function's reserved concurrency, or for a function with none the sum of its provisioned allocations) — which includes this check's reserved 6 plus provisioned 1.

Emulator: the check is killed with "Error: Check timed out after 60.0s" before any assertion in the metric phase is reached, so none of the above is observable. The calls it makes before that first assertion, in order, are lambda GetAccountSettings, iam CreateRole, three CreateFunction + function_active_v2 waits, PutFunctionConcurrency/GetFunctionConcurrency, PublishVersion, CreateAlias, PutProvisionedConcurrencyConfig, and then a 420 s-budget poll of GetProvisionedConcurrencyConfig for Status in (READY, FAILED). Hypothesis: the stall is that provisioned-concurrency readiness poll — the allocation never leaves IN_PROGRESS — because lambda Invoke, the next blocking step, is known to REFUSE rather than hang (open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md), which would have surfaced as an error verdict rather than a timeout, and the AWS/Lambda series are read only after the invokes. Either way, what is established by the replay is that this emulator never produces the state the check reads, within a window in which the recording had already progressed past allocation.

Why: an operator cannot tell when a provisioned-concurrency allocation is actually serving, and cannot alarm on account concurrency headroom at all. Every capacity-planning dashboard built on UnreservedConcurrentExecutions / ClaimedAccountConcurrency, and every deployment gate that waits for a provisioned-concurrency config to report READY before shifting traffic, blocks or reads an empty series forever.

Fix: this issue is filed under the cloudwatch service because that is the leading token of the failing check id, but the component is the lambda service: the provisioned-concurrency allocation state machine behind PutProvisionedConcurrencyConfig / GetProvisionedConcurrencyConfig must settle to READY, and the concurrency metering that publishes the AWS/Lambda ConcurrentExecutions, UnreservedConcurrentExecutions and ClaimedAccountConcurrency series must charge reserved executions to the reservation and include reserved plus provisioned allocations in ClaimedAccountConcurrency, so cloudwatch GetMetricData can read them. No existing open issue carries this check: the lambda concurrency issues 20261025T035202Z-lambda-four-concurrency-runtime-management-refusals-diagnose-the.md and 20261025T160055Z-lambda-three-refusal-message-rules-still-diverge-putfunctionconcurrency.md are about refusal messages, and 20261025T020208Z-cloudwatch-dynamodb-lambda-lambda-listeventsourcemappings-answers-resourcenotfoundexception-function-not-found-for.md covers reserved-concurrency ADMISSION control, not allocation readiness or the account-level metric identity.

Traces: cloudwatch__lambda.obs-lambda-1-reserved-burst-meters-function-concurrency-and-claimed-account-identity.
