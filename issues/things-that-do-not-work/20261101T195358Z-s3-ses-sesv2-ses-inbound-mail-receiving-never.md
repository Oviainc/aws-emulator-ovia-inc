# s3__ses__sesv2: SES inbound mail receiving never delivers — mail accepted for a recipient matched by the ACTIVE receipt rule set's S3Action is never stored in the bucket, so all four inbound-receiving checks stall at the delivery poll (1 cause)

> _Note: this issue was identified against the code base at commit `dcd780eb1101df66f5a3df0652981e1ede476908`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRule

## Description
One net-new root cause, grounded in the four failing checks of the s3__ses__sesv2 group. None of the four is marked "ALREADY FILED" and none is marked "OWNED by" in this replay, so they are filed here.

Stage note: the prior open issue 20261030T123517Z-s3-ses-sesv2-ses-inbound-mail-receiving-is.md recorded these same four check ids failing EARLIER, inside the `_receiving_domain` precondition helper (no baseline-tagged public hosted zone discoverable through route53 ListHostedZones/ListTagsForResource). On this run that stage passes: each check resolves a verified receiving domain (recipients are minted on a `sim2real-baseline-<hex>.example.net` apex), creates its S3 bucket and bucket policy, creates the receipt rule set and rule, activates the set, and gets an accepted send. The run now dies strictly LATER, in the loop that polls S3 for the delivered object. That narrows the defect to the receiving/delivery step, which is the behavior described below. Related open issues describe this same stage but carry different replay keys and so do not cover these failures: 20261027T223106Z-s3-ses-sesv2-inbound-email-receiving-never-completes.md, 20261027T223115Z-s3-ses-sesv2-ses-email-receiving-never-runs.md, 20261028T141517Z-s3-ses-sesv2-a-raw-multipart-message-accepted.md.

Cause 1 of 1: a message accepted by the SES sending surface for a recipient that the ACTIVE receipt rule set matches is never run through the receiving pipeline — no object is ever written to the rule's S3Action bucket under its ObjectKeyPrefix — so every assertion that depends on the stored raw message (its Subject/To, the domain's DKIM-Signature, the ScanEnabled stamps, byte-exact attachment storage, and the S3-encryption-client envelope for a KmsKeyArn'd action) is unreachable. Failing check ids: s3__ses__sesv2.mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule, s3__ses__sesv2.inbound-message-carries-authentication-and-scan-headers, s3__ses__sesv2.raw-multipart-attachment-arrives-byte-exact, s3__ses__sesv2.s3-action-object-key-prefix-and-kms-encryption.

AWS: the envelopes are modelled; the cross-service delivery effect is recorded behavior only. Smithy (com.amazonaws.ses): CreateReceiptRule — input {RuleSetName @required (ReceiptRuleSetName), After, Rule @required (ReceiptRule)}, empty output, 200; modeled refusals AlreadyExistsException/AlreadyExists(400), InvalidS3ConfigurationException/InvalidS3Configuration(400), InvalidSnsTopicException/InvalidSnsTopic(400), InvalidLambdaFunctionException/InvalidLambdaFunction(400), LimitExceededException(400), RuleDoesNotExistException(400), RuleSetDoesNotExistException(400). ReceiptRule carries Name @required, Enabled (default false), ScanEnabled (default false), TlsPolicy, Recipients (RecipientsList — "the recipient domains and email addresses that the receipt rule applies to"), Actions (ordered ReceiptActionsList). S3Action carries BucketName @required, ObjectKeyPrefix ("the key prefix of the Amazon S3 bucket"), KmsKeyArn ("the customer managed key that Amazon SES should use to encrypt your emails before saving them" — the docs state the mail "is encrypted by Amazon SES using the Amazon S3 encryption client"), TopicArn, IamRoleArn. SetActiveReceiptRuleSet — input {RuleSetName}, empty output, 200, refusal RuleSetDoesNotExistException/RuleSetDoesNotExist(400). Recorded behavior for the effect: once a rule set is active and holds an Enabled rule whose Recipients match the envelope recipient, mail accepted for that recipient is stored as ONE S3 object under <ObjectKeyPrefix><message-id-ish key> in BucketName, and that object's body is the raw RFC 5322 message SES received — carrying the sender's Subject and To, a DKIM-Signature with d=<the verified sending domain>, and, when ScanEnabled is true, the stamped Received-SPF, Authentication-Results (with dkim=pass for the domain's own verified signing), X-SES-Spam-Verdict and X-SES-Virus-Verdict headers whose values are verdict tokens (PASS/FAIL). A raw multipart message delivered this way is byte-exact: the attachment part decodes to the same bytes that were sent (same SHA-256), with its filename and Content-Type application/octet-stream intact. When the S3Action names a KmsKeyArn, the stored object is written by the S3 encryption client: object metadata x-amz-wrap-alg = "kms" and x-amz-matdesc a JSON material description naming kms_cmk_id = <the rule's configured key ARN> and aws:ses:rule-name = <the triggering rule's name>, and the object body is ciphertext (the plaintext message, e.g. its Subject token, is NOT readable in it). Activating a rule set also fires SES's own "Amazon SES Setup Notification" probe, which the checks exclude by key suffix AMAZON_SES_SETUP_NOTIFICATION.

Emulator: nothing is refused. s3 CreateBucket/PutBucketPolicy, ses CreateReceiptRuleSet, ses CreateReceiptRule (including the KmsKeyArn'd S3Action, which stops being refused with InvalidS3Configuration once the key grant is in place), ses SetActiveReceiptRuleSet and the send (sesv2 SendEmail, returning a non-empty MessageId, or ses SendRawEmail) all answer 2xx. But s3 ListObjectsV2(Bucket=<rule's bucket>, Prefix=<the rule's ObjectKeyPrefix>) returns an empty Contents for the entire run — not even the setup-notification object — while the checks re-send the same message every 20 s. Each check therefore ends in its delivery poll: three raise TimeoutError "mail to '<recipient>' under '<prefix>': the run budget ended first; not graded" (the prefix being inbox/, scan/ and sim2real-inbox/) and mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule is killed by the harness at its 60 s cap inside the same loop. No status, error code or error message diverges: the divergence is the missing cross-service effect — zero objects delivered where AWS delivers exactly one per received message.

Why: a client that wires SES email receiving the documented way — a bucket with a policy granting s3:PutObject to ses.amazonaws.com, a receipt rule set holding an Enabled rule with Recipients and an S3Action, that set made active — sees mail accepted by SES and then silently lost. Every inbound workflow built on this emulator (store-and-process pipelines, mail archiving, parsers that read the raw MIME out of S3) gets nothing and cannot distinguish a dropped message from a misconfigured rule. Because no object ever lands, the correctness of everything downstream is also unknown on this emulator: prefix placement, DKIM signing of the stored message, the ScanEnabled header stamps, byte-exactness of attachments, and the KMS envelope of a KmsKeyArn'd action would all pass review unimplemented.

Fix: the SES receiving pipeline and its hand-off into s3 — the receipt-rule-set evaluation that must run on an accepted inbound message (the ses crate, services/service-com-amazonaws-ses-simpleemailservice: the active-rule-set state written by SetActiveReceiptRuleSet and the rules written by CreateReceiptRule, matching the envelope recipient against each Enabled rule's Recipients in order) and the S3Action executor that must PutObject the raw message into BucketName under ObjectKeyPrefix in the s3 crate's object store, stamping the ScanEnabled headers when the matched rule has ScanEnabled true and writing the S3-encryption-client envelope (x-amz-wrap-alg/x-amz-matdesc metadata, ciphertext body) when the action carries a KmsKeyArn. The send side (sesv2 SendEmail / ses SendRawEmail) must feed that pipeline for a recipient on a verified receiving domain instead of accepting and discarding the message.

Traces: s3__ses__sesv2.mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule, s3__ses__sesv2.inbound-message-carries-authentication-and-scan-headers, s3__ses__sesv2.raw-multipart-attachment-arrives-byte-exact, s3__ses__sesv2.s3-action-object-key-prefix-and-kms-encryption.

2. Obtain a verified receiving domain <domain> (a public hosted zone whose Easy DKIM CNAMEs are published and whose apex reports sesv2 GetEmailIdentity VerifiedForSendingStatus true).
3. s3 CreateBucket <bucket>; s3 PutBucketPolicy allowing Principal {"Service":"ses.amazonaws.com"} s3:PutObject on arn:aws:s3:::<bucket>/inbox/* with Condition AWS:SourceAccount = <account>.
4. ses CreateReceiptRuleSet RuleSetName=<set>; ses CreateReceiptRule RuleSetName=<set>, Rule={"Name":"to-s3","Enabled":true,"ScanEnabled":false,"Recipients":["<local>@<domain>"],"Actions":[{"S3Action":{"BucketName":"<bucket>","ObjectKeyPrefix":"inbox/"}}]}.
5. ses SetActiveReceiptRuleSet RuleSetName=<set> (DescribeActiveReceiptRuleSet now reports <set>).
6. sesv2 SendEmail FromEmailAddress=<any>@<domain>, Destination.ToAddresses=["<local>@<domain>"], Content.Simple with Subject=<token>. It returns a non-empty MessageId.
7. Poll s3 ListObjectsV2(Bucket=<bucket>, Prefix="inbox/").
   Expected: one object besides inbox/AMAZON_SES_SETUP_NOTIFICATION appears; GetObject returns the raw message with Subject=<token>, To containing the recipient and a DKIM-Signature with d=<domain>.
