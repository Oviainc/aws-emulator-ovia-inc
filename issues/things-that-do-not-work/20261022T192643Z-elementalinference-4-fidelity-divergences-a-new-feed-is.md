# elementalinference: 4 fidelity divergences — a new feed is unassociable for its artificial CREATING window, two refusals omit the state they are decided from, and the fixture catalog is always empty

> _Note: this issue was identified against the code base at commit `17f16131651e3a76635c083c093a8581359ec045`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateFeed, DisassociateFeed, DeleteDictionary, SearchFixtures

## Description
Four distinct root causes in the elementalinference emulator, all grounded in failing behavioral checks. No open issue covers any of them (the only open elementalinference issues are the two scaffold-stub issues for ListDictionaries and ListTagsForResource, which are separate work items).

=== Cause 1 of 4: a freshly created feed admits no association until an emulator-internal 400 ms timer fires, so AssociateFeed (and the whole associate/disassociate lifecycle behind it) is refused right after CreateFeed ===
AWS: recorded behavior. CreateFeed answers 202 (Smithy: CreateFeed http POST /v1/feed, code 202; CreateFeedResponse$status -> FeedStatus enum CREATING|AVAILABLE|ACTIVE|UPDATING|DELETING|DELETED|ARCHIVED) and the feed is immediately usable: in every recorded check the very next call is AssociateFeed (Smithy: AssociateFeed POST /v1/feed/{id}/associate, errors ValidationException 400, ConflictException 409, ResourceNotFoundException 404) and it SUCCEEDS, and a GetFeed taken immediately after CreateFeed reports status AVAILABLE. The recorded DisassociateFeed refusal on a never-associated feed even states the status it observed at that moment: "...It has status AVAILABLE which indicate that it's not currently associated with a resource." So a caller that creates a feed and associates it in the next request gets a 200, not a refusal.
Emulator: CreateFeed stores the feed with status CREATING and a transition due 400 ms later (services/.../src/ops/create_feed.rs sets FeedStatus::Creating + transition_due_at = now + TRANSITION_SPAN; services/.../src/state.rs TRANSITION_SPAN = 400 ms). AssociateFeed's status gate admits only AVAILABLE, or ACTIVE for the same resource, and answers everything else ValidationException 400 with the fixed sentence "You can't associate this feed because its current status doesn't allow an association." (services/.../src/ops/associate_feed.rs, the match on feed.status; message constant state.rs FEED_NOT_ASSOCIABLE_MESSAGE). A client that calls AssociateFeed in the request immediately following CreateFeed therefore always loses the race against the emulator's own timer and is refused. In the two-caller race check BOTH concurrent AssociateFeed calls were refused with ValidationException (0 winners, expected exactly 1), which is the same gate firing for both.
Why: the normal lifecycle (create -> associate -> get -> disassociate) is unreachable without an artificial client-side sleep. Callers see a 400 ValidationException for a request AWS accepts; dryRun semantics, PATCH append semantics, the one-resource-per-feed rule, the ARCHIVED one-way transition and the feed's data-plane endpoint can none of them be exercised at all, because every one of those checks is stopped at the first AssociateFeed.
Fix: the feed's post-create status/gating — services/.../src/ops/create_feed.rs (the CREATING + transition_due_at it stores) together with the status precondition in services/.../src/ops/associate_feed.rs and services/.../src/ops/disassociate_feed.rs: a feed must be associable as soon as CreateFeed has answered, and GetFeed on it must report AVAILABLE.
Traces: elementalinference.associate-feed-appends-outputs-patch-semantics, elementalinference.associate-feed-concurrent-race-single-winner, elementalinference.associate-feed-dry-run-does-not-persist, elementalinference.associate-feed-second-resource-rejected, elementalinference.disassociate-feed-archives-feed-irreversibly, elementalinference.disassociate-feed-dry-run-does-not-persist, elementalinference.disassociate-feed-wrong-resource-name-rejected, elementalinference.feed-media-data-plane-not-reachable. NOTE: the last of these additionally asserts that the feed's advertised dataEndpoints entry is a live sigv4 REST endpoint; it never reached that leg, so it must be re-replayed after this cause is fixed and may expose a further gap.

=== Cause 2 of 4: DisassociateFeed's "not associated" refusal does not report the feed's current status ===
AWS: recorded behavior. DisassociateFeed on a feed that holds no association is refused with ValidationException (HTTP 400; Smithy: DisassociateFeed errors include ValidationException httpError 400) and the message is built from the stored feed: it names the status the feed is in — recorded example: "You can't disassociate this feed. It has status AVAILABLE which indicate that it's not currently associated with a resource." The requirement is the rule (400 / ValidationException, message reporting the feed's current status), not that exact wording.
Emulator: same status code and error code, but one fixed sentence that interpolates nothing from state: "You can't disassociate this feed because it isn't associated with a resource." (services/.../src/state.rs FEED_NOT_ASSOCIATED_MESSAGE, used by disassociate_feed.rs; the constant's doc comment states the deliberate choice to carry no status).
Why: a client or operator diagnosing the refusal cannot tell which status blocked it (AVAILABLE vs CREATING vs ARCHIVED all collapse into one sentence), and tooling that parses the status out of the message gets nothing.
Fix: the refusal path in the DisassociateFeed handler / its message constant in state.rs — render the status of the stored feed into the refusal.
Traces: elementalinference.disassociate-feed-never-associated-rejected (the check reached the message assertion, so code and status matched).

=== Cause 3 of 4: DeleteDictionary's referenced-by-feed ConflictException does not report how many feeds reference the dictionary ===
AWS: recorded behavior. DeleteDictionary on a REFERENCED dictionary is refused with ConflictException (HTTP 409; Smithy: DeleteDictionary errors ConflictException httpError 409, retryable; DictionaryStatus enum includes REFERENCED) and the message is derived from state — it states the NUMBER of referencing feeds and tells the caller to remove or disable the related feed output(s). Recorded example: "Cannot delete dictionary because it is referenced by 1 feed(s). Remove all references by delete or disable related feed output(s) before deleting dictionary." The requirement is 409/ConflictException plus a message carrying the reference count, not the literal wording.
Emulator: correct status and error code, but a fixed sentence with no count: "You can't delete this dictionary because it is referenced by a feed. Remove the dictionary from the feed's subtitling configuration and try again." (services/.../src/state.rs DICTIONARY_REFERENCED_MESSAGE, used by the DeleteDictionary handler; the state already derives the referencing feeds via feeds_referencing/delete_blocked_by_feed).
Why: a caller cleaning up cannot tell from the refusal whether one or many feeds still hold the dictionary, so it cannot report progress or decide how much teardown is left.
Fix: the DeleteDictionary handler's conflict path / its message constant in state.rs — interpolate the count from the derived reference list it already computes.
Traces: elementalinference.delete-dictionary-referenced-by-feed-rejected (the check reached the message assertion, so ConflictException matched).

=== Cause 4 of 4: the fixture catalog is never populated, so SearchFixtures always answers an empty list and GetFixture is unreachable ===
AWS: recorded behavior. SearchFixtures (Smithy: POST /v1/fixtures, readonly, paginated, output fixtures: FixtureSummaryList required) reports the sports events the data source holds for the requested sport and startDate..endDate window; a recent-window search for basketball/american-football returns fixture summaries each carrying fixtureId, name and status, and GetFixture on such a fixtureId agrees with the summary.
Emulator: the fixture store starts EMPTY and is only fillable through an in-process seeding seam that nothing on the wire or in boot calls (services/.../src/state.rs module docs and ComAmazonawsElementalinferenceElementalinferenceState::fixtures / seed_fixtures). Every SearchFixtures therefore returns fixtures: [] regardless of sport or window, and no fixtureId exists for GetFixture.
Why: the fixtures data-plane pair is unusable: a client can never obtain a fixtureId from a search, so GetFixture and the search/get consistency contract can never be exercised against the emulator. (Caveat recorded for the fixer: on real AWS the content of this list depends on the live season schedule, and the check's own failure text says closing the gap needs a deterministic always-available fixture; the emulator-side gap is that the catalog holds nothing at all, not the specific games it holds.)
Fix: the fixture store's population seam in services/.../src/state.rs (seed the catalog at engine construction) so SearchFixtures/GetFixture answer out of a non-empty, self-consistent catalog.
Traces: elementalinference.search-and-get-fixture-consistent.
