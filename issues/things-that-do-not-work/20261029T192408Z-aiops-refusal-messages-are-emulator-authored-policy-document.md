# aiops refusal MESSAGES are emulator-authored: policy-document, singleton-quota and cross-account-source-role rejections all word the wrong sentence (3 causes)

> _Note: this issue was identified against the code base at commit `5b3f288c64c79f31818824eff80fa309a30ec0e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutInvestigationGroupPolicy

## Description
Three distinct root causes in the aiops (CloudWatch investigations) emulator, all grounded in failing behavioral checks of this suite, all bundled because they belong to one service. Each is an independent defect and each must be closed before this issue is submitted.

In all three the HTTP status and the error CODE are now correct — the refusals themselves exist — but the error MESSAGE the emulator serves is text the emulator authored rather than the sentence the service words for that error class. Context (not a duplicate): the resolved issue 20261023T031320Z-aiops-investigation-group-fidelity-7-divergences-singleton-quota.md made these three calls refuse at all (its causes 1, 4 and 5) and quoted the recorded sentences; the landed fix produced the status/code but substituted generated wording, so what remains is purely the message. The resolved issue 20261022T184922Z-aiops-error-messages-are-emulator-authored-instead-of.md is the same CLASS of defect on other messages and covers none of the three sentences below. The open issue 20261028T232143Z-aiops-createinvestigationgroup-validation.md concerns an entry that names NO account passing the own-account rule — a different condition from cause 3, which is about how the refusal that DOES fire is worded.

Cause 1 of 3: PutInvestigationGroupPolicy's ValidationException for a non-JSON policy document is worded with the Smithy constraint envelope instead of the service's resource-policy sentence.
AWS: Smithy — PutInvestigationGroupPolicy.policy @required, @length 1..32768, pattern '^[\u0009\u000A\u000D\u0020-\u00FF]+$'; modelled error ValidationException (errorKind client, httpError 400). The model expresses no JSON requirement, so the boundary admits the body and the operation's own semantic check refuses it; the recorded refusal for a body that is not a JSON policy document is HTTP 400 ValidationException with the message 'The specified resource policy document is invalid.' That sentence is entirely FIXED text — it draws nothing from the request (no member path, no document excerpt, no count) — so it is the whole requirement for this error class.
Emulator: HTTP 400 ValidationException with "1 validation error detected: Value at 'policy' failed to satisfy constraint: Member must be a resource policy document in JSON format" — the modelled-constraint envelope ('<n> validation error(s) detected: Value at '<path>' failed to satisfy constraint: <requirement>') applied to a rule the model does not state.
Why: a client that matches on the service's message (log assertions, user-facing surfacing of an invalid policy, support tooling that distinguishes 'document invalid' from a constraint violation on the member) sees a constraint-violation sentence about a member path and cannot recognise the condition; it also wrongly implies the refusal came from modelled validation of 'policy'.
Fix: the PutInvestigationGroupPolicy validation wording — the helper that owns this refusal must return the service's own fixed sentence rather than routing through the generic validation-envelope/constraint-clause builders. File and line citations under Traces.
Traces: aiops.put-investigation-group-policy-malformed-json-rejected. Wording site: services/service-com-amazonaws-aiops-aiops/src/state.rs:1316-1324 (policy_document_rejection -> validation_message("policy", "Member must be a resource policy document in JSON format")), built by validation_message/validation_envelope at src/state.rs:571-593.

Cause 2 of 3: the per-account/Region singleton quota refusal of CreateInvestigationGroup states the quota rule instead of the service's sentence.
AWS: Smithy — CreateInvestigationGroup errors include ServiceQuotaExceededException (errorKind client, httpError 402); CreateInvestigationGroup is documented 'Currently, you can have one investigation group in each Region in your account.' The model states no message. Recorded behavior: the second create in a Region is refused with ServiceQuotaExceededException and the message 'Cannot create another investigation group.' — again entirely FIXED text: it names no count, no Region, no name and no ARN from the request or from state.
Emulator: ServiceQuotaExceededException with 'An account can have only 1 investigation group in each Region.' — an emulator-composed sentence that interpolates the configured cap.
Why: a client or operator tool keying off the quota message (retry/backoff selection, surfacing 'a group already exists here') does not match; the interpolated cap also makes the message a function of emulator configuration, so it changes when the cap constant changes while AWS's does not.
Fix: the CreateInvestigationGroup quota refusal's wording in the state helper that single-homes it — serve the fixed sentence and keep the cap constant out of the message. File and line citations under Traces.
Traces: aiops.singleton-second-create-conflict-rejected. Wording site: services/service-com-amazonaws-aiops-aiops/src/state.rs:1356-1366 (region_quota_exceeded, format! over MAX_INVESTIGATION_GROUPS_PER_REGION at src/state.rs:110).

Cause 3 of 3: the cross-account same-account source-role refusal is worded with the constraint envelope and withholds the offending ARN, where AWS words a service sentence that names the investigation account and echoes the ARN.
AWS: Smithy — UpdateInvestigationGroup.crossAccountConfigurations -> CrossAccountConfigurations @length 0..25 of CrossAccountConfiguration{sourceRoleArn: RoleArn, @length 20..2048, pattern '^arn:.*$'}; modelled error ValidationException (errorKind client, httpError 400). The modelled constraints cannot express 'must name another account', so this is the operation's own check. Recorded behavior: HTTP 400 ValidationException with 'Source role ARN cannot belong to the investigation account <account>. Found ARN: <sourceRoleArn>'. Its FIXED text is 'Source role ARN cannot belong to the investigation account ' and '. Found ARN: '; its VARIABLE parts are the investigation group's own account id (taken from emulator state / the group's ARN) and the rejected sourceRoleArn taken verbatim FROM THE REQUEST. The replay's values ('000000000000' and 'arn:aws:iam::000000000000:role/sim2real-aiops-role-7ea7e44ed6de') are one run filling that template, not part of it. AWS therefore DOES echo the offending ARN here — the crate's current rule of withholding what the request sent is wrong for this error class.
Emulator: HTTP 400 ValidationException with "1 validation error detected: Value at 'crossAccountConfigurations.1.member.sourceRoleArn' failed to satisfy constraint: Member must name an account other than the investigation account 000000000000" — the modelled-constraint envelope with a list-element member path, and no ARN.
Why: a client cannot learn WHICH role ARN was refused from the message AWS puts it in (a caller sending up to 25 entries relies on the echoed ARN to identify the bad one), and anything matching the service's sentence sees a constraint-violation sentence instead. The same applies to CreateInvestigationGroup, which shares this helper.
Fix: the cross-account validation wording shared by CreateInvestigationGroup and UpdateInvestigationGroup — compose the service sentence (fixed text + investigation account id + the request's sourceRoleArn) instead of the constraint-clause/validation-envelope builders; one clause per offending entry must still be reconciled with AWS's single-sentence form. File and line citations under Traces.
Traces: aiops.update-cross-account-configurations-persist. Wording site: services/service-com-amazonaws-aiops-aiops/src/state.rs:1217-1265 (cross_account_configurations_rejection -> constraint_clause + list_element_member_path inside validation_envelope), reached from write_configuration_rejection at src/state.rs:1293-1302. Note the doc comment at src/state.rs:1228-1236 states the withhold-the-ARN rule that this divergence contradicts, and the resolved issue 20261028T230355Z-aiops-updateinvestigationgroup-error-response.md pinned the list-position path that AWS's sentence does not use.

Cause 1: aiops.create_investigation_group(name=<n>, roleArn=<role>); aiops.put_investigation_group_policy(identifier=<arn>, policy='{not-valid-json:::') -> HTTP 400 ValidationException, but Error.Message is the '1 validation error detected: Value at 'policy' ...' envelope; AWS's message for this class is the fixed sentence 'The specified resource policy document is invalid.'

Cause 2: with one group already present in the Region, aiops.create_investigation_group(name=<another>, roleArn=<role>) -> HTTP 402 ServiceQuotaExceededException, but Error.Message is 'An account can have only 1 investigation group in each Region.'; AWS's message for this class is the fixed sentence 'Cannot create another investigation group.'

Cause 3: create two IAM roles in the caller's own account and one group; aiops.update_investigation_group(identifier=<arn>, crossAccountConfigurations=[{'sourceRoleArn': '<arn of a role in the caller's OWN account>'}]) -> HTTP 400 ValidationException, but Error.Message is the "1 validation error detected: Value at 'crossAccountConfigurations.1.member.sourceRoleArn' ..." envelope with the ARN withheld; AWS's message for this class is 'Source role ARN cannot belong to the investigation account <the investigation group's account id>. Found ARN: <the sourceRoleArn the request sent>'. Repeat the same call against CreateInvestigationGroup's crossAccountConfigurations — it shares the helper and words the same envelope.
