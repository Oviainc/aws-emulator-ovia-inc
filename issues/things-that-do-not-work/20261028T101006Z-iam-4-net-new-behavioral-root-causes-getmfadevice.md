# iam: 4 net-new behavioral root causes — GetMFADevice is a 501 scaffold stub, a DateGreaterThan/aws:CurrentTime Allow is refused AccessDenied, and two AccessDenied messages drop clauses AWS emits

> _Note: this issue was identified against the code base at commit `108dc15ccd6b289eadce56e149ee9ac4dd02b1ab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMFADevice

## Description
Four distinct net-new root causes in the bootstrapped `iam` service, each grounded in a failing behavioral check of this suite that the replay report marks neither ALREADY FILED nor OWNED. Cause count: 4. A fixer must close all four before submitting.

IAM speaks awsQuery (service com.amazonaws.iam#AWSIdentityManagementV20100508, version 2010-05-08); every status/code below is the awsQueryError form.

=== Cause 1 of 4: GetMFADevice is an unimplemented 501 scaffold stub, so the FIDO-only SerialNumber validation never happens ===
AWS: Smithy binds GetMFADevice to the service. Input `SerialNumber` (serialNumberType, @required, @length 9..256, @pattern ^[\w+=/:,.@-]+$) and optional `UserName`; output UserName/SerialNumber/EnableDate/Certifications; modeled errors NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404) and ServiceFailureException (ServiceFailure, 500). The member documentation states "For this API, we only accept FIDO security key ARNs". The refusal for a SerialNumber that is ARN-shaped but not the FIDO grammar is NOT modeled, so it is recorded behavior only: HTTP 400, Error.Code `ValidationError`, Error.Message — entirely fixed text, no variable part — `The MFA device serial number sent in the request is invalid or not supported by this API. Currently, only hardware FIDO security keys are supported. Please use the compatible device or API.` AWS raises it BEFORE any existence lookup, so it is returned even when neither the user nor the device exists.
Emulator: the operation is a scaffold. It answers HTTP 501 with Error.Code `NotImplemented` and the message `operation GetMFADevice is scaffolded but not implemented in this emulator` for every input. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/get_mfa_device.rs still carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its `handle` body returns `Err(crate::scaffolded::Scaffolded::not_implemented("GetMFADevice"))`.
Why: a client cannot read an MFA device at all, and the one validation boundary AWS enforces on this API (FIDO-only serial numbers) is replaced by an unmodeled 501 that no SDK retry or error handler classifies — `NotImplemented` is not in this operation's error union, so generated clients surface it as an unknown/unmodeled failure rather than the 400 ValidationError the caller must handle.
Fix: the operation's handler, services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/get_mfa_device.rs — implement the lookup against the MFA-device records in src/state.rs, refuse a non-FIDO SerialNumber with the 400 ValidationError above before any existence check, and answer NoSuchEntity 404 for an unknown FIDO device/user; then delete the SCAFFOLDED marker line.
Traces: iam.get-nonexistent-entity-returns-nosuchentity (every other Get* leg of this check — GetUser, GetGroup, GetRole, GetPolicy, GetPolicyVersion, GetInstanceProfile, GetOpenIDConnectProvider, GetSAMLProvider, GetServerCertificate, GetLoginProfile — now passes; the check stops at its GetMFADevice leg).

=== Cause 2 of 4: a DateGreaterThan condition on aws:CurrentTime naming a PAST instant does not grant, so an allowed call is refused AccessDenied ===
AWS: recorded behavior only for the decision itself (the authorization outcome is not modeled; GetUser models only NoSuchEntityException 404 and ServiceFailureException 500, and AccessDenied/403 is a service-common refusal). AWS's documented condition-operator semantics (reference_policies_elements_condition_operators) make `DateGreaterThan` on `aws:CurrentTime` TRUE whenever the request instant is after the named instant, so a statement `{"Effect":"Allow","Action":"iam:GetUser","Resource":<user arn>,"Condition":{"DateGreaterThan":{"aws:CurrentTime":"<past instant>"}}}` matches and the signed iam:GetUser succeeds with HTTP 200 and a User describing the named user. The sibling statement conditioned on a FUTURE instant must NOT match, and that call is the one refused.
Emulator: the past-instant statement does not grant. The signed GetUser is refused HTTP 403 `AccessDenied` with `User: <caller-arn> is not authorized to perform: iam:GetUser on resource: user <user-name> because no identity-based policy allows the iam:GetUser action` — i.e. the authorizer reports that NO statement allowed the action, on the same document whose unconditioned barrier statement (iam:ListAccessKeys) the check had already polled to a three-in-a-row success, so the document itself is live and only the conditioned statement is being dropped. Hypothesis: the request authorizer supplies no `aws:CurrentTime` in the condition context, so every date-operator condition evaluates false and the statement is discarded regardless of direction. Related but NOT covering, and neither carries this check's replay key: open issue 20261027T182652Z-iam-3-net-new-behavioral-root-causes-the.md reports the authorizer building an EMPTY condition context for iam:ResourceTag/${aws:username} ABAC, and open issue 20261025T121312Z-iam-request-time-authorization-supplies-no-condition-context.md reports it for aws:ResourceTag AND aws:RequestTag on TagUser; both are tag keys, neither covers the request-time global key aws:CurrentTime or the Date* operator family. Open issue 20261025T000319Z-iam-10-net-new-behavioral-root-causes-four.md Cause 10 carries the sibling check iam.iam-eval-deep-iam-1-date-less-than-deadline-passes-then-denied, but that check's recorded failure there is the 60 s poll timeout from IAM authorizing nothing at all; the authorization gate now answers, and the surviving defect is this one — a conditioned Allow that must grant and does not.
Why: the failure direction is over-restrictive. Any least-privilege policy that time-boxes a grant (`DateGreaterThan` to open a window, `DateLessThan` to close it) is treated as granting nothing, so a client whose production policy works is refused here, and conversely a policy author cannot distinguish "my date window is not open yet" from "my document is wrong". A time-boxed grant can never be validated against this emulator.
Fix: the request authorizer's condition-context builder and its Date* operator evaluation in the IAM crate's authorization gate (the component that resolves the signing principal and evaluates attached/inline/session policies ahead of the operation handlers) — it must populate the request-time global condition keys, aws:CurrentTime (and aws:EpochTime) among them, from the request instant, and evaluate DateGreaterThan/DateGreaterThanEquals/DateLessThan/DateLessThanEquals against them.
Traces: iam.iam-eval-deep-iam-1-date-greater-than-past-instant-allows (assertion at check line 118, `assert got == ("OK", None)`, on call 1 of 3).

=== Cause 3 of 4: the explicit-deny-in-a-permissions-boundary AccessDenied message omits the boundary policy's ARN ===
AWS: recorded behavior only (the refusal text is not modeled; AccessDenied/403 is a service-common error). AWS distinguishes the four denial causes for the SAME action by the reason clause that follows the common head `User: <principal-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> `. The four recorded clauses are `because no identity-based policy allows the <service>:<Action> action`, `with an explicit deny in an identity-based policy`, `with an explicit deny in a permissions boundary: <boundary-policy-arn>`, and `with an explicit deny in a session policy`. The boundary clause is the only one of the four that NAMES the policy that denied: its fixed text is `with an explicit deny in a permissions boundary: ` and its single variable part is `<boundary-policy-arn>`, the ARN of the permissions-boundary policy attached to the principal, taken from the emulator's own state (the value the check read back from GetUser's PermissionsBoundary.PermissionsBoundaryArn). The documented troubleshooting guidance (troubleshoot_access-denied) is built on these clauses being distinct and on the boundary one identifying the boundary.
Emulator: it reaches the correct code (AccessDenied) and the correct head and the correct clause prefix, then stops: the observed message ends `... on resource: user <target> with an explicit deny in a permissions boundary`, with the `: <boundary-policy-arn>` suffix absent. The divergence is the whole missing `: <ARN>` suffix on every boundary refusal, not one run's ARN value.
Why: a client or operator reading the denial cannot tell WHICH boundary denied — in an account with several boundaries that is the only identifying information in the message, and policy-troubleshooting tooling that parses the clause to fetch the offending policy has nothing to fetch.
Fix: the shared authorization-refusal denial-message builder in the IAM crate (the component that renders AccessDenied for iam operations) — when the deciding statement came from the principal's permissions boundary, append `: ` plus the boundary policy's ARN as held in src/state.rs.
Traces: iam.iam-eval-deep-iam-1-denial-reason-messages-are-distinct (assertion at check line 231, `assert reason == expected`, on the 'bound' leg; the check's 'none' and 'ident' legs pass, so the other two clauses are already right).

AWS: recorded behavior only (service-common AccessDenied/403; ListOpenIDConnectProviders models only ServiceFailureException 500 and takes no input, so there is no validation boundary ahead of the decision). Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/`, ` for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: `. Why: a client that routes a developer to the authorization-details page, or asserts on the full documented denial text, receives a truncated string with no authorization id to pass to GetRequestAuthorizationDetails, so policy troubleshooting has nothing to follow.
Fix: the same shared authorization-refusal denial-message builder named in Cause 3 — it must decide the trailer per refusal rather than globally: emit the implicit-deny sentence and, for the refusals AWS records with the pointer, the authorization-details sentence as well, with the console host and the region query parameter pinned to us-east-1 and the authorization id taken from the request's authorization context.
