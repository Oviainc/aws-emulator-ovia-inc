# cloudwatch__logs__sns__sqs: a CloudWatch log alarm (PutLogAlarm + service-managed scheduled query) is never evaluated, so M-of-N state transitions and their SNS->SQS notifications never happen (1 cause)

> _Note: this issue was identified against the code base at commit `37938bae9928f6f0327a9972c93fc7656bc513a9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutLogAlarm

## Description
One root cause. Cause count: 1.

=== Cause 1 of 1: nothing drives a log alarm's evaluation — no AWS-managed scheduled query, no aggregate, no state transition, no notification ===

AWS: PutLogAlarm with a ScheduledQueryConfiguration (QueryString, LogGroupIdentifiers, ScheduledQueryRoleARN, ScheduleConfiguration{ScheduleExpression, StartTimeOffset, EndTimeOffset}, AggregationExpression) returns an empty 200 and, as a side effect, creates a service-managed CloudWatch Logs scheduled query for that alarm. From then on: (a) DescribeAlarms(AlarmTypes=['LogAlarm']) populates ScheduledQueryConfiguration.QueryARN with a `arn:<partition>:logs:<region>:<account>:scheduled-query:<id>` ARN — one per alarm, never shared — and round-trips ActionLogLineCount, ActionLogLineRoleArn and ScheduleConfiguration verbatim; (b) logs GetScheduledQuery(identifier=<that QueryARN>) resolves it with scheduleType=AWS_MANAGED and the alarm's queryString / logGroupIdentifiers / scheduleExpression / executionRoleArn; (c) the evaluator runs the query on its schedule over the lookback window, and each execution's aggregate becomes a result in the alarm's StateReasonData (threshold, queryResultsToEvaluate, queryResultsToAlarm, results[] of {queryResultId, status:'COMPLETE', value}); (d) M-of-N decides the state asymmetrically — ALARM once M results breach, OK only after N non-breaching results — and the breaching value equals the count the query actually computed over the published lines (matching lines only, non-matching lines excluded); (e) DescribeAlarmHistory(AlarmTypes=['LogAlarm'], HistoryItemType='StateUpdate') records the transitions; (f) each transition is published to AlarmActions/OKActions and the SNS message carries AlarmName, AlarmArn, OldStateValue/NewStateValue, LogGroups, QueryString, AggregationExpression and a QueryExecutionId that appears in logs GetScheduledQueryHistory(identifier=<QueryARN>).triggerHistory with executionStatus='Complete'. Recorded behavior only for the timings (the check records us-west-2, 2026-10-01: ALARM 72-136 s after PutLogAlarm, OK on the sub-threshold control at ~164 s because OK needs two executions).

Emulator: none of that observable chain ever appears. The check publishes 7 matching + 3 non-matching lines to a breach group and 2 matching + 1 non-matching to a control group, puts one identically-configured log alarm on each, then polls DescribeAlarms (_poll_until, 300 s budget, 10 s interval, returning on the FIRST satisfying reading), DescribeAlarmHistory, and SQS (_await_payload, 180 s). No reading ever satisfied any predicate and the check consumed the whole suite budget, so the alarm never left its initial state, no StateReasonData results were produced, and no notification was published. Hypothesis (neither the model nor the recording states which link is missing): the alarm is stored by PutLogAlarm but no service-managed scheduled query is minted and no evaluator ever executes it, so QueryARN/EvaluationState/StateReasonData stay empty and every downstream assertion is unreachable.

Why: this is the log-alarm alerting topology — alert when a Logs Insights aggregate over a log group crosses a threshold. A client gets a log alarm that exists, a topic that exists and a queue that exists with no signal flowing between them, and cannot distinguish "the aggregate is below threshold" from "nothing is evaluating": both look like a permanently INSUFFICIENT_DATA alarm. Runbooks, on-call wiring and IaC that validate an alarm fires are silently unverifiable, and the M-of-N asymmetry (ALARM on M, OK only on N) that governs flap suppression cannot be exercised at all.

Fix: the CloudWatch log-alarm evaluator and its CloudWatch Logs side effects — (1) the PutLogAlarm handler must mint the AWS-managed scheduled query for the alarm and expose its ARN through DescribeAlarms' ScheduledQueryConfiguration.QueryARN, resolvable by logs GetScheduledQuery with scheduleType=AWS_MANAGED; (2) a scheduled-query execution path must run the alarm's query over the configured lookback window and record each execution in GetScheduledQueryHistory; (3) the alarm evaluator must fold the per-execution aggregates into StateReasonData and apply M-of-N to choose the state and write DescribeAlarmHistory StateUpdate items; (4) the transition must publish to AlarmActions/OKActions with the payload members above. Related but distinct from the open issue 20261024T150703Z-cloudwatch-logs-sns-sqs-a-log-metric-filter.md, which covers the PutMetricFilter -> CloudWatch metric -> metric-alarm chain; that issue's cause is metric-filter datapoint emission and it does not carry this check's replay key, whereas this cause is the log-alarm/scheduled-query evaluator, which emits no metric at all.
