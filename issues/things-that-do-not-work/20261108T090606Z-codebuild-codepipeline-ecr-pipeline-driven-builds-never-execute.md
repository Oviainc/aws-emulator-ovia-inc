# CodeBuild/CodePipeline/ECR: pipeline-driven builds never execute (FAULT at PROVISIONING) and the pipeline role's codebuild:StartBuild grant is never enforced (2 causes)

> _Note: this issue was identified against the code base at commit `a946db3d2c92d3ec27b0f0d3beb3e4ffad06b536`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBuild

## Description
Two net-new root causes in the CodeBuild-inside-CodePipeline path, both grounded in failing behavioral checks that the suite did NOT mark as already filed or owned. Similar open issues exist for other checks of the same chain (20261022T172625Z-codebuild-codepipeline-ecr-ci-chain-pipeline-executions-never.md, 20261024T014332Z-codebuild-codepipeline-ecr-codepipeline-build-stages-fail-and-record-no-action.md, 20261029T174654Z-codebuild-codepipeline-ecr-build-actions-are-never-executed.md, 20261028T112857Z-codebuild-codepipeline-ecr-codebuild-in-codepipeline-3-net-new-root-causes.md); none of them carries the replay keys below, so Cause 1 is re-filed here with the checks it actually blocks, and Cause 2 is an authorization defect no open issue covers.

Cause 1 of 2: a build invoked by a CodePipeline Build action is never executed, so every build terminates buildStatus FAULT in phase PROVISIONING instead of SUCCEEDED or FAILED.
AWS: Smithy (codebuild-20161006) StatusType = {SUCCEEDED, FAILED, FAULT, TIMED_OUT, IN_PROGRESS, STOPPED}, used for Build.buildStatus and BuildPhase.phaseStatus. AWS runs the project's buildspec in a container: a build whose configuration and permissions are correct ends buildStatus SUCCEEDED with phases SUBMITTED/QUEUED/PROVISIONING/DOWNLOAD_SOURCE/INSTALL/PRE_BUILD/BUILD/POST_BUILD/... all SUCCEEDED, and a build whose buildspec command exits non-zero (for example `aws ecr get-login-password` denied because the service role lacks ecr:GetAuthorizationToken) ends buildStatus FAILED with the failing phase's phaseStatus FAILED and the command's stdout/stderr delivered to the configured CloudWatch Logs group/stream. FAULT is reserved for an internal CodeBuild fault, i.e. a condition the caller did not cause; AWS does not use it for a denied or failing buildspec command. CodePipeline then maps SUCCEEDED/FAILED onto the Build action's status (recorded behavior of the chain).
Emulator: every build ends buildStatus 'FAULT' with phases SUBMITTED(SUCCEEDED), QUEUED(SUCCEEDED), PROVISIONING(FAULT, contexts[0].message = "this emulator does not run CodeBuild build containers, so the build could not be provisioned and no buildspec was executed"), COMPLETED. No buildspec runs, so no log events are produced, no image is pushed to ECR, and the containing pipeline execution ends 'Failed' with a Build action summary 'Build terminated with state: FAULT' — including for correctly permitted and correctly trusted positive controls that AWS lets succeed.
Why: a client cannot distinguish 'the build failed because of my configuration/permissions' (FAILED, retry after a fix) from 'CodeBuild broke' (FAULT, retry as-is); CI logic keyed on buildStatus FAILED or on a SUCCEEDED positive control never fires, no artifact or container image is ever delivered, and permission-boundary expectations (the denied-ECR build must FAIL and log the AccessDeniedException line that the AWS CLI emits inside the container) are unobservable.
Fix: the CodeBuild build execution path — the component behind StartBuild that drives phase transitions and terminal buildStatus (and the pipeline Build-action poller that consumes it); PROVISIONING must not short-circuit to FAULT, and a non-zero buildspec command must yield FAILED.
Traces: codebuild__codepipeline__ecr.cli-pipeline-execution-fails-when-codebuild-role-lacks-ecr-permissions (expected buildStatus FAILED, got 'FAULT'), codebuild__codepipeline__ecr.codebuild-build-status-propagates-to-pipeline-action-result (expected the action's build to report FAILED, got 'FAULT'), codebuild__codepipeline__ecr.codebuild-role-missing-trust-policy-blocks-assume-role-during-build-rejected (the InvalidInputException refusal for the untrusted role is correct; the positive control with a role trusting codebuild.amazonaws.com got pipeline status Failed, expected Succeeded), codebuild__codepipeline__ecr.deploy-stack-codebuild-role-trust-policy-allows-codebuild-service and codebuild__codepipeline__ecr.deploy-stack-pipeline-role-trust-policy-allows-codepipeline-service (both: 'pipeline execution ended in Failed: Build/Build=Failed: Build terminated with state: FAULT'), codebuild__codepipeline__ecr.deploy-stack-missing-ecr-repository-policy-blocks-codebuild-push ('build ended in FAULT' where the buildspec swallows the expected push failure and the build must end SUCCEEDED).

Cause 2 of 2: CodePipeline does not evaluate the pipeline service role's identity policy before invoking a Build action, so a build is started for a role that holds no codebuild:StartBuild permission.
AWS: CodePipeline calls CodeBuild's StartBuild under the pipeline's roleArn. With no codebuild:StartBuild grant on that role the call is denied (AccessDeniedException), so no build is created — CodeBuild's ListBuildsForProject for the project stays empty, and the Build action fails with ActionExecutionResult.errorDetails.code 'JobFailed' and NO externalExecutionId (Smithy codepipeline-20150709: ActionExecutionResult{externalExecutionId, externalExecutionSummary, externalExecutionUrl, errorDetails, logStreamARN}, ErrorDetails{code, message}); errorDetails.message is AWS's denial text naming the principal, the action codebuild:StartBuild and the project resource. Granting codebuild:StartBuild on the same role makes the identical pipeline run start a real build.
Emulator: the action does end Failed, but ActionExecutionResult.externalExecutionId is populated — a CodeBuild build was created for the project even though the pipeline role grants nothing on codebuild — and the Failed status comes from that build FAULTing (Cause 1), not from an authorization decision. The emulator therefore reports an authorization-independent outcome: a role with zero codebuild permissions behaves exactly like a fully permitted one.
Why: a client cannot use CodePipeline to verify or to rely on least-privilege role scoping — an under-permissioned pipeline role is not refused, the action's errorDetails do not identify the missing permission, and side effects (a started build, consumed concurrency, emitted build records) happen for calls real AWS never performs.
Fix: the CodePipeline Build-action invocation path — it must evaluate the pipeline roleArn's IAM policy for codebuild:StartBuild on the target project ARN before creating any build, and on denial record the action as Failed with errorDetails.code 'JobFailed' and no externalExecutionId.
Traces: codebuild__codepipeline__ecr.pipeline-role-missing-codebuild-startbuild-permission-blocks-invocation-rejected ('a CodeBuild build was started despite missing permission').
