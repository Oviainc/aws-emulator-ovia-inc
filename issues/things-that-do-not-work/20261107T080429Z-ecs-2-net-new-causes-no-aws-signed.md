# ecs: 2 net-new causes — no AWS-signed EC2 instance identity document is obtainable, so every container-instance/agent-plane flow never starts (18 checks), and CreateCapacityProvider accepts an autoScalingGroupArn that resolves to no Auto Scaling group

> _Note: this issue was identified against the code base at commit `620c90c23a321396910fd66a692ef2fcecf33f7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterContainerInstance

## Description
Two independent root causes in the ECS surface. Each must be closed before submitting.

Cause 1 of 18-check group (Cause 1 of 2): the emulator provides no way to obtain a genuine, AWS-signed EC2 instance identity document for an instance it launched, so RegisterContainerInstance can never be called with an acceptable (instanceIdentityDocument, instanceIdentityDocumentSignature) pair and every container-instance / agent-plane scenario stalls before it reaches its subject. Failing check ids: ecs.attribute-put-list-delete-roundtrip, ecs.attributes-put-list-delete-lifecycle, ecs.container-instance-agent-update-rejected-missing-version, ecs.container-instance-deregister-not-found, ecs.container-instance-deregister-removes-from-list, ecs.container-instance-register-deregister-lifecycle, ecs.delete-attributes-missing-target-rejected, ecs.delete-attributes-removes-attribute, ecs.discover-poll-endpoint-returns-agent-endpoint, ecs.discover-poll-endpoint-returns-endpoint-for-registered-instance, ecs.execute-command-requires-enabled-flag, ecs.list-attributes-filters-by-target-type, ecs.put-attributes-target-not-found-rejected, ecs.register-container-instance-malformed-identity-document-rejected, ecs.submit-attachment-state-changes-updates-attachment-status, ecs.submit-container-state-change-updates-container-status, ecs.submit-task-state-change-updates-task-status, ecs.update-container-agent-triggers-update-state.
  AWS: RegisterContainerInstance cryptographically validates the instanceIdentityDocument/signature pair and refuses a synthetic one with InvalidParameterException (Smithy: ecs RegisterContainerInstance takes instanceIdentityDocument + instanceIdentityDocumentSignature and models InvalidParameterException/ClientException/AccessDeniedException at 400/403), so the only way a client obtains the pair is from the instance itself: launch an EC2 instance with an SSM-capable instance profile, wait for DescribeInstanceInformation to report it PingStatus=Online, and read http://169.254.169.254/latest/dynamic/instance-identity/document and .../signature through an AWS-RunShellScript Run Command whose GetCommandInvocation ends Status=Success with the document and signature in StandardOutputContent. The recordings complete that chain well inside each check's budget. Recorded behavior only for the chain itself.
  Emulator: none of the 18 checks ever gets past that chain — each ends `Error: Check timed out after 60.0s`, so no container instance is ever registered and nothing downstream (PutAttributes/ListAttributes/DeleteAttributes against a container-instance target, DeregisterContainerInstance, DiscoverPollEndpoint, SubmitTaskStateChange / SubmitContainerStateChange / SubmitAttachmentStateChanges, UpdateContainerAgent, ExecuteCommand on an EC2-launched task) is exercised at all. Hypothesis: the launched instance never becomes an SSM-managed Online instance and no Run Command invocation returns in-guest output, so the identity document is unobtainable — consistent with the open 20261104T042502Z-autoscaling-ec2-iam-ssm-an-asg-instance-never.md and 20261107T064927Z-cloudwatch-ec2-ssm-the-ssm-installed-cloudwatch-agent.md, neither of which carries any of these replay keys.
  Why: the whole ECS-on-EC2 agent plane is unreachable for a client that follows AWS's only supported registration path: it cannot register a container instance, so attributes, placement on real instances, agent state reporting and exec on EC2 tasks can never be driven, and a negative test such as 'a malformed identity document is rejected' cannot even be set up.
  Fix: whatever must make an emulator-launched EC2 instance produce a usable identity document — the EC2 instance-metadata/identity-document source plus the SSM managed-instance registration and Run Command execution path that exposes it — and, downstream of that, the ECS RegisterContainerInstance handler's acceptance of that pair (the ECS crate's register_container_instance op and the EC2/SSM state it must read).

Cause 2 of 2: ECS CreateCapacityProvider accepts an autoScalingGroupArn that resolves to no Auto Scaling group and creates the provider anyway. Failing check id: ecs.capacity-provider-create-invalid-asg-fails.
  AWS: a correctly shaped autoScalingGroupArn that names no existing group is refused with HTTP 400, error code `ClientException` and the fixed sentence "The specified Auto Scaling group does not exist. Specify a valid Auto Scaling group and try again." (no request values appear in it), and nothing is created — DescribeCapacityProviders for that name returns an empty list. Smithy: ecs CreateCapacityProvider models ClientException and InvalidParameterException at httpError 400; the existence rule and wording are recorded behavior.
  Emulator: the call returns HTTP 200 with the provider `ACTIVE` and echoes the nonexistent ASG ARN back — `AssertionError: CreateCapacityProvider accepted a nonexistent ASG: {'capacityProvider': {... 'status': 'ACTIVE', 'autoScalingGroupProvider': {'autoScalingGroupArn': 'arn:aws:autoscaling:<region>:111122223333:autoScalingGroup:…'} ...}, 'ResponseMetadata': {'HTTPStatusCode': 200, ...}}` (the provider name, ARN, date and content-length are per-run values; the 200 and the ACTIVE provider are the divergence).
  Why: a client gets an ACTIVE capacity provider bound to nothing, so cluster strategies and RunTask placements built on it fail later and far from the real error, instead of the request being refused at creation; the related open 20261106T135659Z-ecs-ec2-autoscaling-capacity-providers-are-invisible-after.md describes a different cause (providers invisible after creation) and does not carry this replay key.
  Fix: the existence check in the ECS CreateCapacityProvider handler's autoScalingGroupProvider validation (it must resolve the ARN against Auto Scaling state before persisting), and the ClientException it must raise.

Traces: the nineteen failing check ids listed under the two causes above, all reported by the suite under `### ecs`.

## Evidence
Cause 1 — expected: an EC2 instance launched with an SSM-capable profile reports PingStatus=Online, an AWS-RunShellScript invocation returns the IMDS instance-identity document and signature with Status=Success, RegisterContainerInstance accepts that pair and returns a containerInstanceArn, and the check then exercises its ECS subject. Actual: `Error: Check timed out after 60.0s` for all 18 listed checks — the registration prerequisite never completes, so no container instance exists and no ECS agent-plane assertion is ever reached.
Cause 2 — expected: HTTP 400 `ClientException` with message "The specified Auto Scaling group does not exist. Specify a valid Auto Scaling group and try again." and DescribeCapacityProviders returning []. Actual: `AssertionError: CreateCapacityProvider accepted a nonexistent ASG: {'capacityProvider': {'capacityProviderArn': 'arn:aws:ecs:…:capacity-provider/<name>', 'name': '<name>', 'status': 'ACTIVE', 'autoScalingGroupProvider': {'autoScalingGroupArn': 'arn:aws:autoscaling:…:autoScalingGroupName/<name>', 'managedScaling': {'status': 'DISABLED'}}, 'tags': []}, 'ResponseMetadata': {'HTTPStatusCode': 200, …}}`.

## Steps to Reproduce
Cause 1: create an IAM role with AmazonSSMManagedInstanceCore and an instance profile, `ec2 run-instances` with it, poll `ec2 describe-instances` for state running, poll `ssm describe-instance-information` for PingStatus=Online, `ssm send-command --document-name AWS-RunShellScript` fetching http://169.254.169.254/latest/dynamic/instance-identity/document and .../signature, then `ecs register-container-instance --instance-identity-document <doc> --instance-identity-document-signature <sig>` and continue with PutAttributes/ListAttributes/DeleteAttributes, DeregisterContainerInstance, DiscoverPollEndpoint, SubmitTaskStateChange/SubmitContainerStateChange/SubmitAttachmentStateChanges, UpdateContainerAgent or ExecuteCommand. Replay the 18 check ids listed in cause 1.
Cause 2: call `ecs create-capacity-provider --name <n> --auto-scaling-group-provider autoScalingGroupArn=arn:aws:autoscaling:<region>:<acct>:autoScalingGroup:00000000-0000-0000-0000-000000000000:autoScalingGroupName/<n>,managedScaling={status=DISABLED}` for a group that does not exist, then `ecs describe-capacity-providers --capacity-providers <n>`. Replay ecs.capacity-provider-create-invalid-asg-fails.
