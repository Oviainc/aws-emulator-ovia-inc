# lambda__sqs: the asynchronous-invocation plane is inert — destinations, dead-letter queues and retries produce nothing, plus two missing/misworded refusals (5 causes)

> _Note: this issue was identified against the code base at commit `486a0852ab6c107011e8dec7ea6574940ef62e53`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutFunctionEventInvokeConfig

## Description
Five net-new root causes on Lambda's asynchronous (InvocationType=Event) invocation plane. None of these failing checks is marked ALREADY FILED or OWNED in the replay report. The open issues 20261105T022225Z-lambda-sqs-an-enabled-sqs-event-source-mapping.md and 20261106T134622Z-lambda-sqs-a-number-message-attribute-is-not.md concern the SQS event-source-mapping path, not the async-invoke path described here; the open issue 20261104T232822Z-lambda-s3-sqs-2-net-new-root-causes.md names the same OnFailure-destination defect under a different service heading. Those issues do not cover these checks.

Cause 1 of 5: an asynchronous invocation never delivers an invocation record to its OnSuccess/OnFailure destination.
AWS: Smithy (lambda PutFunctionEventInvokeConfig -> DestinationConfig{OnSuccess,OnFailure}, MaximumRetryAttempts @range 0..2; PUT /2019-09-25/functions/{FunctionName}/event-invoke-config) models the configuration; the delivery contract is recorded behavior only. After an async Invoke (202) completes, Lambda builds an invocation record — version, timestamp, requestContext (requestId, functionArn including the executed qualifier, condition 'Success'/'RetriesExhausted', approximateInvokeCount), requestPayload and responsePayload — and delivers it to the configured destination (SQS SendMessage for a queue ARN, Invoke for a function ARN). The qualifier-scoped config applies: an alias invoke reports the alias-qualified functionArn and the alias's executedVersion; a published version with no config of its own inherits nothing from $LATEST; a DryRun invoke and a synchronous (RequestResponse) invoke produce NO record; PutFunctionEventInvokeConfig without DestinationConfig clears the previous destinations; DeleteFunctionEventInvokeConfig stops delivery until a Put restores it; a non-object request/response payload is carried verbatim.
Emulator: nothing is ever delivered. Every one of these checks is abandoned with 'Check timed out after 60.0s' while polling the destination queue/function, so neither the positive deliveries nor the negative 'no record' assertions can be graded.
Why: a client that routes async results to a queue or a relay function for auditing, alerting or replay loses every invocation record silently; the condition and approximateInvokeCount that distinguish success from an exhausted retry are never observable, and code that keys on executedVersion for alias rollouts cannot be exercised.
Fix: the Lambda asynchronous-invocation pipeline — after the handler settles it must build the invocation record and deliver it to the qualifier-resolved EventInvokeConfig's destination; the event-invoke-config store must honour qualifier scoping, clearing and deletion.
Traces: lambda__sqs.alias-async-record-reports-the-alias-target-version-and-follows-a-repoint, lambda__sqs.alias-event-invoke-config-overrides-the-unqualified-config-for-alias-invokes, lambda__sqs.async-event-that-fails-once-then-succeeds-on-retry-is-recorded-on-success-only, lambda__sqs.async-timeout-is-a-function-error-recorded-on-failure-with-the-timeout-message, lambda__sqs.deleted-event-invoke-config-stops-destination-delivery-until-put-again, lambda__sqs.destination-record-carries-non-object-request-and-response-payloads-verbatim, lambda__sqs.dry-run-invoke-produces-no-destination-record, lambda__sqs.lambda-async-retry-exhausted-routes-to-onfailure-destination, lambda__sqs.on-success-destination-function-is-invoked-with-the-invocation-record, lambda__sqs.published-version-without-its-own-event-invoke-config-gets-no-latest-destination, lambda__sqs.put-event-invoke-config-without-destinations-clears-the-previous-ones, lambda__sqs.update-event-invoke-config-redirects-on-success-and-keeps-on-failure, lambda__sqs.xsvc-lambda-3-async-onsuccess-destination-record-shape, lambda__sqs.xsvc-lambda-3-sync-invoke-produces-no-onsuccess-destination-record, lambda__sqs.zero-reserved-concurrency-sends-async-events-to-on-failure-without-running-them.

Cause 2 of 5: a function's DeadLetterConfig never receives the failed event.
AWS: Smithy (lambda UpdateFunctionConfiguration -> DeadLetterConfig.TargetArn) models the configuration; the delivery contract is recorded behavior only. When an asynchronous invocation exhausts its retries, Lambda sends the ORIGINAL event payload (not an invocation record) to the DeadLetterConfig target, carrying the message attributes RequestID, ErrorCode and ErrorMessage; ErrorMessage is truncated to the first 1 KB. A successful invocation and a synchronous failure send nothing. A published version uses the dead-letter queue configured at publish time, not the one $LATEST later points at.
Emulator: nothing is ever sent to the dead-letter target. Each of these checks is abandoned with 'Check timed out after 60.0s' waiting on the configured queue.
Why: a client whose only record of a poison event is the dead-letter queue loses the event itself plus the request id and error text needed to attribute it, and the 'withheld on success' guarantee cannot be relied on either.
Fix: the asynchronous-invocation pipeline's dead-letter path (original-payload send with the RequestID/ErrorCode/ErrorMessage attributes and the 1 KB ErrorMessage cap), and version-scoped resolution of DeadLetterConfig.
Traces: lambda__sqs.dead-letter-error-message-attribute-keeps-only-the-first-kilobyte, lambda__sqs.dead-letter-queue-and-on-failure-destination-both-receive-the-failed-event, lambda__sqs.dead-letter-queue-receives-the-original-event-with-request-id-and-error-attributes, lambda__sqs.dead-letter-queue-withholds-successful-and-synchronous-failures, lambda__sqs.published-version-failure-uses-its-publish-time-dead-letter-queue.

Cause 3 of 5: MaximumRetryAttempts is not honoured — a failing asynchronous invocation is never retried.
AWS: Smithy (lambda PutFunctionEventInvokeConfig -> MaximumRetryAttempts @range min 0 max 2) models the budget; the attempt count is recorded behavior only. An async invocation whose handler raises runs 1 + MaximumRetryAttempts times: with MaximumRetryAttempts=1 the handler is entered exactly twice, with 2 exactly three times, and the invocation record's approximateInvokeCount reports that count.
Emulator: the extra attempts never happen; both checks are abandoned with 'Check timed out after 60.0s' while waiting for the second (resp. third) handler entry.
Why: retry-sensitive handlers (idempotency keys, at-least-once side effects) are exercised under semantics the emulator does not reproduce, and a client tuning MaximumRetryAttempts sees no difference between 0 and 2.
Fix: the retry driver of the asynchronous-invocation pipeline (attempt loop bounded by the resolved MaximumRetryAttempts, with approximateInvokeCount carried into the record).
Traces: lambda__sqs.async-retry-budget-of-one-runs-the-handler-twice-and-reports-two-invokes, lambda__sqs.async-retry-budget-of-two-yields-exactly-three-attempts.

Cause 4 of 5: UpdateFunctionConfiguration accepts a DeadLetterConfig target the execution role cannot send to.
AWS: Smithy (lambda UpdateFunctionConfiguration -> DeadLetterConfig; error InvalidParameterValueException, httpError 400). A DeadLetterConfig.TargetArn naming an SQS queue the function's execution role has no sqs:SendMessage on is refused with HTTP 400 InvalidParameterValueException and the message 'The provided execution role does not have permissions to call SendMessage on SQS' (that sentence is entirely fixed text — it names the API and the service, not the queue), the previously configured dead-letter queue is kept, and the identical call succeeds once the grant is added.
Emulator: the call is accepted — HTTP 200 with the response echoing DeadLetterConfig.TargetArn = the ungranted queue ('AssertionError: call was expected to fail but succeeded: {... HTTPStatusCode: 200 ... DeadLetterConfig: {TargetArn: arn:aws:sqs:...}}'), so the stored configuration points at a queue the function can never write to.
Why: a misconfiguration AWS rejects at configure time becomes a silent runtime hole — every dead-lettered event is dropped with no refusal and no error anywhere.
Fix: the UpdateFunctionConfiguration handler's DeadLetterConfig validation (resolve the target's service from the ARN and authorize the execution role for the matching action before storing).
Traces: lambda__sqs.dead-letter-queue-the-execution-role-cannot-send-to-is-rejected.

Cause 5 of 5: PutFunctionEventInvokeConfig's ungranted-destination refusal carries the wrong message.
AWS: Smithy (lambda PutFunctionEventInvokeConfig -> DestinationConfig; error InvalidParameterValueException, httpError 400). A DestinationConfig whose destination the execution role cannot invoke/send to is refused 400 InvalidParameterValueException with the message 'The function execution role does not have permissions to call InvokeFunction on <destination ARN>' — fixed text 'The function execution role does not have permissions to call ', then the API name implied by the destination's type, then ' on ', then the destination ARN taken from the request. The refused Put stores nothing, so GetFunctionEventInvokeConfig then answers ResourceNotFoundException 'The function <function ARN>:$LATEST doesn't have an EventInvokeConfig'.
Emulator: the error class is right but the message is emulator-authored and loses the destination: 'The provided execution role does not have permissions to call InvokeFunction on Lambda' — the subject is 'The provided execution role' instead of 'The function execution role', and the ARN is replaced by the service name 'Lambda'. The same wrong template appears on the SQS destination path (see the lambda__sns__sqs issue filed in this pass); the resolved issue 20261030T121631Z-events-lambda-sqs-createeventsourcemapping-s-under-privileged-execution.md fixed this wording only for CreateEventSourceMapping, so this door was left behind.
Why: clients and operators match on that sentence to tell which destination was rejected; with the ARN replaced by a service name an error handler cannot name the offending destination, and strict message comparison fails.
Fix: the destination-validation refusal in the PutFunctionEventInvokeConfig handler (message template and the ARN interpolation).
Traces: lambda__sqs.function-destination-without-invoke-permission-is-rejected.
