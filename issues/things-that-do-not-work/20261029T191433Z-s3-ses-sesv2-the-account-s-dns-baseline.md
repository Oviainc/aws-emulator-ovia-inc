# s3__ses__sesv2: the account's DNS-baseline public hosted zone is not tag-discoverable through route53 ListHostedZones/ListTagsForResource, so all four inbound-receiving e2e checks abort in their precondition helper before any SES/S3 call is made

> _Note: this issue was identified against the code base at commit `9cdb0b3f0824f3a0ed0e0c6187c880d28eaa4218`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListHostedZones

## Description
One root cause, grounded in the four failing checks of the `s3__ses__sesv2` suite directory. All four now fail EARLIER than the receive-path issues already on file: they never reach a send or an S3 read at all.

Cause 1 of 1: tag-based discovery of the account's public hosted zones yields nothing, so the checks' `_receiving_domain` helper cannot resolve a verified domain to receive mail for and each check aborts on its first statement. Failing checks: s3__ses__sesv2.inbound-message-carries-authentication-and-scan-headers, s3__ses__sesv2.mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule, s3__ses__sesv2.raw-multipart-attachment-arrives-byte-exact, s3__ses__sesv2.s3-action-object-key-prefix-and-kms-encryption.

AWS: Smithy (com.amazonaws.route53) ListHostedZones — GET /2013-04-01/hostedzone, code 200, input {Marker (httpQuery marker, @length 0..64), MaxItems (httpQuery maxitems), DelegationSetId, HostedZoneType}, output ListHostedZonesResponse{HostedZones (required, list), Marker (required), IsTruncated (required, default false), NextMarker, MaxItems (required)}, paginated inputToken=Marker / outputToken=NextMarker / items=HostedZones; modeled refusals InvalidInput(400), NoSuchDelegationSet(400), DelegationSetNotReusable(400). Beyond those signatures this is recorded behavior only: against real AWS the ListHostedZones pagination enumerates EVERY hosted zone that exists in the account, a public zone reports HostedZone.Config.PrivateZone false, ListTagsForResource(ResourceType='hostedzone', ResourceId=<the segment of HostedZone.Id after the last '/'>) answers 200 with a ResourceTagSet whose Tags are exactly the tags ChangeTagsForResource wrote on that zone, and GetEmailIdentity on that zone's apex (trailing dot stripped) answers 200 with VerifiedForSendingStatus true. The requirement is general and names no particular zone: a zone that exists is enumerated, is reported public when it is public, and the tags written on it are projected back for ResourceType 'hostedzone'.

Emulator: nothing is refused — every read in the discovery loop answers 2xx — yet not one enumerated public zone carries the tag the account baseline writes, so the helper falls through to its precondition assertion and the check stops before its first SES/S3 operation. Two message variants of the same helper: `AssertionError: this account has no DNS baseline zone (a public hosted zone tagged sim2real-infra-dns-baseline) and so no domain to receive mail for; provision it with SimParityProbe infra/pool/setup_domain_baseline.py` (three checks) and `AssertionError: no public hosted zone carries the DNS baseline tag, so the account has no verified domain to receive mail for` (mail-to-a-verified-domain...). Those are the harness's own fixed assertion texts; the tag it looks for ({'Key': 'sim2real-infra-dns-baseline', 'Value': 'true'}) and the zone apex it would have returned are values from the account's state, not part of any template. Hypothesis: either ListHostedZones enumerates no public zone for the account (HostedZones empty, or zones reported with Config.PrivateZone true), or the hostedzone tag store is not projected by ListTagsForResource so the ResourceTagSet comes back without the tags ChangeTagsForResource recorded.

Why: a client cannot tag-discover its own DNS zones — the standard way SES receiving tooling locates the domain it receives mail for — and because the identity it needs is undiscoverable, the whole inbound half of SES behind these checks is masked and its fidelity is unknown: mail to a verified domain landing in the active receipt rule set's S3Action bucket, the Authentication-Results / Received-SPF / X-SES-Spam-Verdict / X-SES-Virus-Verdict headers SES adds when ScanEnabled is true, byte-exact storage of a raw multipart message, and S3Action ObjectKeyPrefix + KmsKeyArn behavior. None of these can even be attempted while this read comes back untagged.

Fix: route53's hosted-zone enumeration and its hostedzone tag reads — ListHostedZones' listing/pagination and the Config.PrivateZone flag it reports, and the tag state ListTagsForResource projects for ResourceType 'hostedzone' — must agree with what CreateHostedZone/ChangeTagsForResource recorded; the sesv2 email-identity state for that apex must then report VerifiedForSendingStatus true. This belongs in the route53 crate's ListHostedZones / ListTagsForResource handlers and their hosted-zone/tag state, not in the SES crates.

## Evidence

2. Ensure the account holds a PUBLIC hosted zone: route53.create_hosted_zone(Name=D, CallerReference=<uuid>), then route53.change_tags_for_resource(ResourceType='hostedzone', ResourceId=<id segment after the last '/'>, AddTags=[{'Key':'sim2real-infra-dns-baseline','Value':'true'}]); verify D as a sesv2 email identity so get_email_identity(EmailIdentity=D) reports VerifiedForSendingStatus true.
3. Page route53.list_hosted_zones(); for every returned zone whose Config.PrivateZone is false, call route53.list_tags_for_resource(ResourceType='hostedzone', ResourceId=<id segment after the last '/'>).
4. Observe: no enumerated public zone reports the baseline tag (either HostedZones is empty / private-only, or the ResourceTagSet omits the written tag) while both calls still answer 200.
