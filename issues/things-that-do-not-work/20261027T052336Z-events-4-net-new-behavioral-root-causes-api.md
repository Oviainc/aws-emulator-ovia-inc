# events: 4 net-new behavioral root causes — api-destination rate-limit and TestEventPattern refusal messages are rewritten, and neither a CMK-encrypted bus's disabled key nor an SNS target's AccessDenied ever produces a dead letter

> _Note: this issue was identified against the code base at commit `4846872b237bc4d9f92d9945507291eab648a721`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateApiDestination, CreateApiDestination, TestEventPattern, PutEvents

## Description
Four distinct, independent EventBridge ('events') root causes found by the behavioral replay. All four failing checks were reported neither ALREADY FILED nor OWNED by an open issue, so none is carried by an existing work item. Causes 1 and 2 are refusal-message defects on operations that DO answer and answer with the right error code; causes 3 and 4 are delivery/dead-letter paths that never produce anything. A fixer must close all FOUR before submitting.

=== Cause 1 of 4: the InvocationRateLimitPerSecond over-maximum refusal message is hand-written instead of AWS's api-destination wording ===
AWS: Smithy: UpdateApiDestination.InvocationRateLimitPerSecond -> ApiDestinationInvocationRateLimitPerSecond, @range(min: 1) with NO modeled maximum (the maximum is a service-side rule, documented as 300 requests/second); UpdateApiDestination and CreateApiDestination both model LimitExceededException (errorKind client, httpError 400). Recorded behavior for the over-maximum value: HTTP 400, code LimitExceededException, message "Failed to <verb> the api-destination(s). Invalid Invocation Rate Limit: Rate specified '<rate>' for '<name>' exceeds maximum allowed of '<maximum>'." The FIXED text is "Failed to ", " the api-destination(s). Invalid Invocation Rate Limit: Rate specified '", "' for '", "' exceeds maximum allowed of '", "'."; the VARIABLE parts are <verb> ("update" for UpdateApiDestination, "create" for CreateApiDestination), <rate> = the InvocationRateLimitPerSecond in the request, <name> = the destination Name in the request, and <maximum> = the maximum the service enforces. Both the create and the update path must produce the same message modulo the verb.
Emulator: the right code with the wrong text — LimitExceededException, 'InvocationRateLimitPerSecond 1024 exceeds the maximum of 300 requests per second for an api destination.' It carries no "Failed to <verb> the api-destination(s)." prefix, never names the destination, and does not quote the rate or the maximum in AWS's '<value>' form. (The maximum itself is now enforced at 300, so this is only the message; the open issue 20261025T084539Z-events-eventbridge-api-destinations-and-connections-diverge-no-http.md, which reported the maximum as 1, does not cover this check — the suite did not mark it owned.)
Why: a client that keys on the refusal text — a CLI/console surface, a retry or quota-tuning path, or a log matcher — cannot tell which api-destination of a batch was refused, because the emulator's message omits the destination name AWS puts there, and matches none of AWS's fixed text.
Fix: the refusal construction in the eventbridge service's api-destination validation, shared by the UpdateApiDestination and CreateApiDestination handlers, must emit AWS's message template rather than a locally worded one.
Traces: events.api-destination-invocation-rate-limit-maximum-is-enforced

=== Cause 2 of 4: TestEventPattern's InvalidEventPatternException message reports the JSON parser's own words and drops AWS's [Source: ...] location clause ===
AWS: Smithy: TestEventPattern.EventPattern is required, @length(0..4096); errors InternalException and InvalidEventPatternException (errorKind client, httpError 400). Recorded behavior: for an EventPattern that is not valid JSON the call is refused HTTP 400 / InvalidEventPatternException with message "Event pattern is not valid. Reason: <reason>\n at [Source: (String)\"<pattern text>\"; line: <line>, column: <column>]". The FIXED text is the prefix "Event pattern is not valid. Reason: " and the suffix "\n at [Source: (String)\"", "\"; line: ", ", column: ", "]"; the VARIABLE parts are <reason> (the parser's diagnosis of the offending token, e.g. "Unexpected character ('n' (code 110)): was expecting double-quote to start field name" for a bare key), <pattern text> = the EventPattern from the request reproduced verbatim, and <line>/<column> = the position of the offending character. The same check grades two further reasons AWS produces from the same builder — "\"<member>\" must be an object or an array" for a filter value that is a bare scalar, and "Empty arrays are not allowed" for an empty filter array — each with the same "\n at [Source: (String)...; line: N, column: N]" suffix; the check stopped at the first, so the other two are unverified but must come out of the same template.
Emulator: code InvalidEventPatternException is right, text is the Rust JSON library's — 'Event pattern is not valid. Reason: Event pattern is not valid JSON: key must be a string at line 1 column 2'. It substitutes serde's wording for AWS's reason, inserts "Event pattern is not valid JSON: " that AWS does not emit, and omits the entire " at [Source: (String)\"...\"; line: N, column: N]" clause.
Why: the [Source:...] clause is the only place AWS echoes the rejected pattern and the exact position, so a caller validating a generated pattern before relying on a rule gets no location to correct and no text it can match; a pattern linter keyed on AWS's reason strings reads every refusal as unrecognized.
Fix: the pattern-validation error formatting behind the TestEventPattern handler (the shared event-pattern parser/validator also reached by PutRule) must render AWS's reason + [Source:] template rather than passing the deserializer's error through. Open issue 20261025T084539Z-events-eventbridge-pattern-engine-and-pattern-validation-refusals-diverge.md covers other pattern refusals but not this check.
Traces: events.test-event-pattern-invalid-fails

=== Cause 3 of 4: a CMK-encrypted custom bus with a DeadLetterConfig produces no observable outcome at all — no delivery, no KMSEncryptionException, no "Encrypted Events" dead letter ===
AWS: recorded behavior only (no Smithy member governs this). On a custom bus created with KmsKeyIdentifier and DeadLetterConfig, an event put while the key is ENABLED is delivered to the matching rule's SQS target. After DisableKey on that CMK, each PutEvents entry is either refused inside FailedEntries with ErrorCode KMSEncryptionException and ErrorMessage "<key arn> is disabled." (the variable part being the key ARN from the bus's configuration), or accepted and, instead of reaching the rule's target, delivered to the BUS's DeadLetterConfig queue as an aws.events "Encrypted Events" envelope that keeps the original event id and names the bus and the key, with an ERROR_CODE message attribute of RULE_DECRYPTION_FAILURE ("Unable to decrypt rule using the Kms key.") or EVENT_DECRYPTION_FAILURE ("Unable to decrypt events using the Kms key."). After EnableKey, delivery resumes.
Emulator: nothing observable happens. The check hangs to the harness cap — "Error: Check timed out after 60.0s" — with no event reaching the rule's SQS target, so the positive control (delivery while the key is enabled) never completes and neither the per-entry KMSEncryptionException nor any bus-level dead letter is ever produced. Hypothesis: the bus's KmsKeyIdentifier and bus-level DeadLetterConfig are stored but never consulted, and the rule-to-target delivery path on a CMK bus never runs.
Why: a client that encrypts a bus with a customer-managed key and relies on the key as a kill switch gets the opposite of AWS's behavior — events are neither refused, nor delivered, nor captured in the bus dead-letter queue, so they are lost silently with no FailedEntries signal and no dead letter to replay from.
Fix: the event-bus delivery path in the eventbridge service — consult the bus's KMS key state when encrypting/decrypting rules and events, surface the per-entry KMSEncryptionException from PutEvents, and route accepted-but-undecryptable events to the bus's DeadLetterConfig queue as the aws.events "Encrypted Events" envelope with the ERROR_CODE attribute. Related open issue 20261025T002357Z-events-eventbridge-target-delivery-never-completes-for-sns-step.md does not carry this check.
Traces: events.disabled-bus-key-stops-delivery-dead-letters-encrypted-events-until-reenabled

=== Cause 4 of 4: an SNS target whose topic policy denies events:Publish is never dead-lettered as NO_PERMISSIONS, and the healthy sibling target of the same rule receives nothing either ===
AWS: recorded behavior only. For one rule with two targets — an SNS topic carrying only its bare owner-only default policy, configured with RetryPolicy {MaximumRetryAttempts: 180, MaximumEventAgeInSeconds: 86400} and a DeadLetterConfig queue, plus a healthy SQS queue — a matching PutEvents reaches the healthy queue, and the SNS publish is refused by SNS's own resource policy. That refusal lands in the target's dead-letter queue, not retried despite the many-attempt RetryPolicy, as a message whose attribute set is exactly {ERROR_CODE, ERROR_MESSAGE, RULE_ARN, TARGET_ARN}, with ERROR_CODE = "NO_PERMISSIONS", RULE_ARN = the rule's ARN, TARGET_ARN = the topic ARN, the body identical to what the healthy sibling received, and ERROR_MESSAGE = SNS's own AccessDenied text of the form "User: <principal> is not authorized to perform: SNS:Publish on resource: <topic arn> because no resource-based policy allows the SNS:Publish action (Service: AmazonSNS; Status Code: 403; Error Code: AuthorizationError; Request ID: <request id>; Proxy: null)" — fixed text apart from the principal, the topic ARN and the per-call request id. Granting the withheld events.amazonaws.com sns:Publish statement then lets an identical event reach a queue subscribed to the topic.
Emulator: no outcome at all — "Error: Check timed out after 60.0s". Neither the healthy SQS sibling delivery nor any dead-letter message for the denied SNS target appears within the window. Hypothesis: the rule's target-delivery path does not run for this rule, so the SNS authorization decision is never taken and the target-level DeadLetterConfig is never written.
Why: a client that wires an SNS target behind a dead-letter queue to detect a missing topic policy sees no notification, no dead letter and no failure signal — the diagnostic that tells it the topic policy is the one broken thing is absent, and the unrelated healthy target of the same rule silently loses its copy of the event too.
Fix: rule target delivery and failure classification in the eventbridge service — perform the SNS publish, classify an SNS AuthorizationError as ERROR_CODE NO_PERMISSIONS without retrying it, and write the envelope plus the four dead-letter attributes to the target's DeadLetterConfig queue while still delivering to the rule's other targets. Related open issues 20261025T002357Z-events-eventbridge-target-delivery-never-completes-for-sns-step.md and 20261024T190039Z-events-iam-sfn-sqs-eventbridge-dead-letter-error-code-misclassifies-target-delivery.md do not carry this check.
Traces: events.sns-target-without-topic-policy-dead-letters-as-access-denied-until-the-policy-grants-publish
