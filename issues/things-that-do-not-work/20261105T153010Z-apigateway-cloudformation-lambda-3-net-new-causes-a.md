## Operation

## Description
Three net-new root causes, all reached through a CloudFormation stack that carries a Custom:: resource whose ServiceToken is an AWS::Lambda::Function declared in the same template with inline Code.ZipFile. None of these seven failing checks is marked OWNED or ALREADY FILED in the replay report.

Related open issues that do NOT carry these replay keys (named here so a fixer can see the neighbourhood, not because they cover these causes): 20261105T022225Z-apigateway-cloudformation-lambda-3-net-new-causes-describestacks.md (same seven check ids, but its keys are the previous failure signature — Outputs missing OutputValue, and stacks reaching CREATE_COMPLETE where a rollback was owed; the emulator now fails these stacks instead, which is the opposite symptom and a different key); 20261105T111951Z-apigateway-cloudformation-lambda-the-lambda-python-runtime-has.md (cause 1 there: the managed python runtime bundles no boto3) ; 20261105T040000Z-cloudformation-6-of-the-7-custom-resource-and-hook-keys-remain-open.md.

Cause 1 of 3: a Custom:: resource backed by a Lambda provider never settles, so the whole stack fails and rolls back where AWS reaches CREATE_COMPLETE.
AWS: recorded behavior only for the custom-resource protocol; the shapes are modelled (Smithy com.amazonaws.cloudformation#StackStatus includes CREATE_COMPLETE, ROLLBACK_IN_PROGRESS, ROLLBACK_COMPLETE, ROLLBACK_FAILED; com.amazonaws.cloudformation#ResourceStatus likewise). CloudFormation sends the function named by ServiceToken a Create/Update/Delete request, the handler answers at the request's pre-signed ResponseURL with Status SUCCESS plus PhysicalResourceId and Data, the resource becomes CREATE_COMPLETE, Fn::GetAtt on the resource resolves against that Data, and the stack settles CREATE_COMPLETE. For a function whose code is inline (Code.ZipFile) in a CloudFormation template, AWS makes the cfnresponse module importable in the python runtime alongside the runtime's bundled boto3, which is how the documented `import cfnresponse` / `cfnresponse.send(event, context, cfnresponse.SUCCESS, data, id)` provider idiom works.
Emulator: every such stack ends in a terminal failure status instead — ROLLBACK_COMPLETE (four checks) and ROLLBACK_FAILED (one, see cause 2) — so the provider's SUCCESS answer never arrives and no custom-resource Data is ever published. The same happens when the provider is shared by a nested child stack. Hypothesis: the provider handler cannot initialise at all, because the python runtime supplies neither boto3 (already filed as cause 1 of 20261105T111951Z) nor the CloudFormation-injected cfnresponse module, so it never PUTs to the ResponseURL and the resource's barrier fails.
Why: a client cannot deploy any template that uses the custom-resource extension point — the single mechanism by which templates provision anything CloudFormation does not model natively. A green deploy becomes a rollback, every resource the stack did create is torn down, and Fn::GetAtt on provider Data resolves to nothing.
Fix: the Lambda transport of the custom-resource provider request and the module set the python runtime exposes to an inline-ZipFile function (the cloudformation crate's custom-resource provisioning/stabilising path — services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/custom_resource.rs, src/state/stabilising.rs, src/service/custom_resource_plane.rs — together with the lambda runtime's python module search path).
Traces: apigateway__cloudformation__lambda.cfn-custom-resource-invokes-lambda-create-positive, .cfn-custom-resource-invokes-lambda-delete-positive, .cfn-custom-resource-invokes-lambda-update-positive, .cfn-custom-resource-signals-success-updates-stack-status-positive, .cfn-nested-stack-lambda-provider-reuse-positive.

Cause 2 of 3: the rollback that follows a custom-resource failure itself ends ROLLBACK_FAILED.
AWS: Smithy com.amazonaws.cloudformation#StackStatus — ROLLBACK_FAILED is reached only when the rollback could not remove a resource it had created; the ordinary rollback of a failed create settles ROLLBACK_IN_PROGRESS then ROLLBACK_COMPLETE, and DescribeStackEvents carries a DELETE_* event per resource naming what could not be removed in ResourceStatusReason.
Emulator: the same template that lands in ROLLBACK_COMPLETE in the sibling checks lands in ROLLBACK_FAILED here, so the stack is left in a state from which only DeleteStack with RetainResources can proceed, with no event explaining which resource blocked the rollback.
Why: a client that polls for a terminal status and then retries the deploy is stuck — ROLLBACK_FAILED is not a state a CreateStack retry can leave, and the caller is given no reason naming the stuck resource.
Fix: the stack state machine's rollback path (the delete of already-provisioned resources during ROLLBACK_IN_PROGRESS) and the ResourceStatusReason it records when it cannot finish.
Traces: apigateway__cloudformation__lambda.cfn-custom-resource-signals-success-updates-stack-status-positive.

Cause 3 of 3: a custom resource whose provider could not be invoked fails with a reason that does not name the denied action, and the CREATE_COMPLETE event of a sibling resource created before the failure is not in the event stream.
AWS: recorded behavior only. (a) When the stack's service role (CreateStack RoleARN) has no lambda:InvokeFunction on the ServiceToken function, the custom resource's CREATE_FAILED event carries a ResourceStatusReason that names the denied action — the fixed text is of the form "... is not authorized to perform: lambda:InvokeFunction on resource: ...", with the assumed-role principal ARN and the function ARN taken from the request and the stack's state; the substring "lambda:InvokeFunction" is the part a client keys on. (b) DescribeStackEvents is an append-only history (Smithy com.amazonaws.cloudformation#StackEvent has LogicalResourceId, ResourceStatus, PhysicalResourceId, ResourceStatusReason, Timestamp), so an independent sibling resource (here an AWS::SNS::Topic with no dependency on the custom resource) that was created before the failure still has its CREATE_COMPLETE event, with its PhysicalResourceId, after the stack has rolled back — and that physical resource has been deleted by the rollback.
Emulator: (a) the stack does reach ROLLBACK_COMPLETE and does emit a CREATE_FAILED event for the custom resource, but its ResourceStatusReason does not contain "lambda:InvokeFunction", so the denial is indistinguishable from any other provider failure. (b) after a rollback no CREATE_COMPLETE event for the sibling topic is present in DescribeStackEvents at all, so a client cannot learn which resources were created and then removed, nor their physical ids.
Why: a client diagnosing a failed deploy cannot tell a permissions problem on the ServiceToken from a provider that answered FAILED, and cannot audit from the event history what the stack created before it failed.
Fix: the custom-resource provider invocation's authorization check and the reason text it records on CREATE_FAILED, and the stack event recorder (events must be appended and retained across the ROLLBACK transition, including the CREATE_COMPLETE of resources later deleted).
Traces: apigateway__cloudformation__lambda.cfn-custom-resource-lambda-missing-servicetoken-permission-rejected, .cfn-stack-rollback-on-custom-resource-failure.

## Steps to Reproduce
1. Create an SQS queue. CreateStack with a template declaring: an AWS::IAM::Role trusting lambda.amazonaws.com; an AWS::Lambda::Function (Runtime python3.12, Handler index.handler, inline Code.ZipFile) whose handler does `import boto3` and `import cfnresponse`, sends one SQS message, then calls `cfnresponse.send(event, context, cfnresponse.SUCCESS, {"RequestType": event["RequestType"], "NewValue": "v1"}, "fixed-id")`; a Custom::Sim2RealTest whose ServiceToken is Fn::GetAtt [ProviderFunction, Arn]; and Outputs taking Fn::GetAtt on the custom resource. Poll DescribeStacks: the terminal status is ROLLBACK_COMPLETE, not CREATE_COMPLETE, and no message reaches the queue (cause 1). The same holds for an UpdateStack that changes the resource's properties, for the Delete request on DeleteStack, and when a nested child stack reuses the parent's provider function.
2. Repeat with the handler writing a marker output and poll for CREATE_COMPLETE: the stack reaches ROLLBACK_FAILED (cause 2).
3. Create the provider function out-of-band, create two CloudFormation service roles — one with and one without lambda:InvokeFunction on that function ARN — and CreateStack with RoleARN set to the denied one. Poll to ROLLBACK_COMPLETE, then DescribeStackEvents and read the ResourceStatusReason of the custom resource's CREATE_FAILED event: it does not mention lambda:InvokeFunction (cause 3a).
4. CreateStack with a template holding both a Custom:: resource whose provider answers FAILED and an independent AWS::SNS::Topic. After ROLLBACK_COMPLETE, DescribeStackEvents: there is no CREATE_COMPLETE event for the topic, so its PhysicalResourceId cannot be read back (cause 3b).
