# BatchGetTaxExemptions omits an accessible account from taxExemptionDetailsMap when it has no exemptions, and PutTaxRegistration's pending-TRN ConflictException message is the emulator's own wording

> _Note: this issue was identified against the code base at commit `3a6da8cf7ceece0dec1bbe7fd5ea27cdc5dd3e62`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetTaxExemptions

## Description
Two distinct root causes in the taxsettings emulator, both grounded in failing behavioral checks.

Cause 1 of 2: BatchGetTaxExemptions reports NO entry at all for an account it accepts as accessible (an account not listed in failedAccounts) whenever that account currently holds no stored exemption, so the response's taxExemptionDetailsMap comes back empty.
  AWS: BatchGetTaxExemptions is modeled as a batch read with two parallel channels — `BatchGetTaxExemptionsResponse$taxExemptionDetailsMap` ("The tax exemption details map of accountId and tax exemption details", keyed by AccountId, value TaxExemptionDetails) and `BatchGetTaxExemptionsResponse$failedAccounts` ("The list of accounts that failed to get tax exemptions"). `TaxExemptionDetails$taxExemptions` is a list member with no @required, i.e. an account with no active exemptions is representable as an entry whose taxExemptions list is empty. Recorded behavior: for the caller's own account AWS answers 200 with that account PRESENT as a key of taxExemptionDetailsMap and a `taxExemptions` list in its value, whether or not the account has any active exemption, and the account is NOT in failedAccounts. The same holds in a mixed-tenant request: the foreign account id goes to failedAccounts and the caller's own account is still served in taxExemptionDetailsMap in that very same 200 response. The two channels are therefore exhaustive over the requested ids: every requested account appears in exactly one of them.
  Emulator: the per-account loop classifies an account into three outcomes instead of two. `src/ops/batch_get_tax_exemptions.rs::handle` pushes the id to failed_accounts when `store.reports_exemptions_for(id)` is false, and otherwise inserts into the map only `if let Some(details) = store.exemption_details(id, now)`. `crate::state::ComAmazonawsTaxsettingsTaxsettingsState::exemption_details` returns None both when the store holds no exemptions entry for the account and when that entry is empty (its doc states "An account the service knows but holds no exemption for therefore gets no entry in the reported map"). The result is a 200 whose taxExemptionDetailsMap is `{}` and whose failedAccounts does not name the account either: the account silently falls out of both channels.
  Why: a client cannot distinguish "this account is accessible and has zero exemptions" from "this account was not reported on". Code that reads `resp['taxExemptionDetailsMap'][account_id]['taxExemptions']` — the natural shape of the modeled response — raises KeyError against the emulator where it returns an empty list against AWS, and a tenant-isolation check that asserts the caller's own account is served in the same request that rejects a foreign account sees an empty map. Exhaustiveness over requested ids is the property the per-account failure channel exists to provide, and the emulator breaks it.
  Fix: the operation's handler and the state projection it reads — `src/ops/batch_get_tax_exemptions.rs::handle`'s per-account loop and `src/state.rs::exemption_details` — must emit a TaxExemptionDetails entry (with `taxExemptions` present, empty when there is nothing stored) for every account the call accepted as accessible, so each requested id lands in taxExemptionDetailsMap or in failedAccounts and never in neither. The same projection backs the single-account exemption reads, so the fix belongs in state.rs rather than being special-cased in the batch handler.
  Traces: taxsettings.batch-get-tax-exemptions-own-account-accessible (AssertionError: own account missing from taxExemptionDetailsMap despite not being in failedAccounts: keys=[]); taxsettings.batch-get-tax-exemptions-foreign-account-rejected (failedAccounts == ['999999999999'] was correct, then AssertionError: own account missing from taxExemptionDetailsMap in the very same request that rejected the foreign account: map_keys=[]). Note the fixed issue 20261024T151653Z-taxsettings-batchgettaxexemptions-wrong-behavior.md added the failedAccounts channel; this is not a reopen of it — the call is no longer refused (it answers 200 and the foreign account is correctly reported in failedAccounts) — the remaining defect is the missing map entry for the accessible account.

Cause 2 of 2: the pending-TRN ConflictException raised by PutTaxRegistration carries a message the emulator invented rather than the message AWS words for that error class.
  AWS: PutTaxRegistration's documentation states the rule "You can't set a TRN if there's a pending TRN. You'll need to delete the pending TRN first" and models ConflictException (httpError 409, required members `message` and `errorCode`). Recorded behavior: a second PutTaxRegistration for a different jurisdiction while the account's TRN is still Pending is refused with Error.Code "ConflictException" and the message, in full fixed text with no variable parts: "There is a pending TRN for the account. Please delete that first and retry the request." (no account id, registration id or country appears in it).
  Emulator: the status (409) and code (ConflictException) match, but `src/state.rs::pending_registration_conflict()` returns message "You can't set a TRN while there's a pending TRN for this account. Delete the pending TRN first." — a paraphrase of the doc sentence, which the function's own comment admits is "this emulator's own statement of the rule". Both strings are entirely fixed text, so the divergence is not a per-run value.
  Why: the error message is part of the contract a client sees. Clients, SDK wrappers and operator tooling that match or display the refusal reason (and conformance suites that pin it) read a message AWS never emits, and anything keying on AWS's fixed text does not match.
  Fix: the error constructor for this refusal — `pending_registration_conflict()` in src/state.rs, used by both PutTaxRegistration and the per-account rows of BatchPutTaxRegistration — must carry AWS's fixed text for this error class verbatim: "There is a pending TRN for the account. Please delete that first and retry the request."
  Traces: taxsettings.primary-tax-registration-full-lifecycle (AssertionError: expected conflict message 'There is a pending TRN for the account. Please delete that first and retry the request.', got "You can't set a TRN while there's a pending TRN for this account. Delete the pending TRN first."). This check aborts at that assertion, so the later lifecycle assertions it carries (the KE business-rule ValidationException message, the BatchPut submission-time status, the polled-to-terminal Rejected status, BatchDelete) were never exercised and are not claimed here.

## Steps to Reproduce
Cause 1:
1. Resolve the caller account id with sts:GetCallerIdentity.
2. POST /BatchGetTaxExemptions with {"accountIds":["<caller account id>"]} on an account that has no tax exemption recorded. Observe 200 with "taxExemptionDetailsMap": {} and "failedAccounts": [] — the account is in neither channel; AWS returns an entry for that account whose "taxExemptions" is a (possibly empty) list.
3. POST /BatchGetTaxExemptions with {"accountIds":["<caller account id>","999999999999"]}. Observe 200 with "failedAccounts": ["999999999999"] (correct) but "taxExemptionDetailsMap": {} — the caller's own account is not served in the same response.

Cause 2:
1. POST /DeleteTaxRegistration (tolerating ResourceNotFoundException) so the account has no primary TRN.
2. POST /PutTaxRegistration with a DE VAT entry, e.g. taxRegistrationEntry {registrationId "DE123456789", registrationType "VAT", legalName any, legalAddress {addressLine1, city, postalCode, countryCode "DE"}}. Observe 200 with status "Pending".
3. Immediately POST /PutTaxRegistration again with a second DE entry (registrationId "DE987654321") while the first is still Pending.
4. Observe 409 ConflictException whose message is "You can't set a TRN while there's a pending TRN for this account. Delete the pending TRN first." instead of AWS's "There is a pending TRN for the account. Please delete that first and retry the request."
