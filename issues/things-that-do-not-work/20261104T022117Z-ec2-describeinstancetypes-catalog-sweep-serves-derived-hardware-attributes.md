AWS: Smithy com.amazonaws.ec2#DescribeInstanceTypes returns InstanceTypeInfo rows whose EbsInfo models MaximumEbsAttachments, AttachmentLimitType (enum, 'dedicated' or 'shared') and EbsOptimizedInfo{BaselineBandwidthInMbps:integer, BaselineIops:integer, BaselineThroughputInMBps:double, MaximumBandwidthInMbps:integer, MaximumIops:integer, MaximumThroughputInMBps:double}, whose VCpuInfo models DefaultCores, DefaultThreadsPerCore, ValidCores and ValidThreadsPerCore, and whose NetworkInfo/row level carry defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, ipv4AddressesPerSecondaryInterface, maximumNetworkCards, networkCards, networkPerformance, secondaryNetworkSupported, trafficMirroringSupport, cpuBurstModel, phcSupport, rebootMigrationSupport and processorInfo.sustainedClockSpeedInGhz. Each of these is a per-instance-type fact of AWS's published catalog (the recording is the authority for the values); the response must serve the catalog row for the requested type, with every member AWS emits present.
Emulator: for the swept types it reports values derived from a generic size-scaling rule rather than the catalog (for c7a.12xlarge: attachmentLimitType 'shared' instead of 'dedicated', ebsOptimizedInfo baselineBandwidthInMbps/maximumBandwidthInMbps 10200 instead of 15000, baselineIops/maximumIops 45000 instead of 60000, baselineThroughputInMBps/maximumThroughputInMBps 1275 instead of 1875.0 - note the modeled double is also rendered without its fractional part - and maximumEbsAttachments 28 instead of 32), and omits cpuBurstModel, phcSupport, rebootMigrationSupport, networkInfo.defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, maximumNetworkCards, networkCards, secondaryNetworkSupported and trafficMirroringSupport, plus vCpuInfo.defaultCores/defaultThreadsPerCore and most validCores/validThreadsPerCore entries. The same divergence repeats across the swept instance types in the catalog fixtures.
Why: capacity and placement decisions are made from this response - an EBS attachment limit, an EBS-optimized bandwidth/IOPS ceiling or a vCPU core option that is wrong by 25-50% makes a client size volumes, threads or network cards against hardware that does not exist, and a missing modeled member makes a feature probe (ENA SRD, PHC, reboot migration, traffic mirroring) read as unsupported on types where AWS reports support.
Fix: the DescribeInstanceTypes handler must serve a static per-instance-type catalog table (services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_instance_types.rs and the instance-type reference data it reads) instead of deriving attributes from the type name/size, and the serializer must emit the optional members AWS returns, including the double-typed throughput members with their fractional rendering.

None of them carries this fixture step's replay key, so this sweep is not re-run when they are closed.
