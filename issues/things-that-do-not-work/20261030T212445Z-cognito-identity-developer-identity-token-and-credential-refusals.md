# cognito-identity: developer-identity token and credential refusals are mis-classified

> _Note: this issue was identified against the code base at commit `7e40a03527fe455980798ee437e03ca50107a3c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetOpenIdTokenForDeveloperIdentity

## Description
This issue bundles 3 root causes on the developer-authenticated identity path (GetOpenIdTokenForDeveloperIdentity and GetCredentialsForIdentity). In each one the emulator picks the wrong modeled error class and re-words the refusal message, or does not refuse at all. The HTTP status itself is already 400 in causes 1 and 2, so this is NOT the error-status mapping already tracked by '20261029T230931Z-cognito-identity-identity-scoped-refusals-answer-403-404.md'; what diverges here is which error is selected, its message text, and in cause 3 whether any error is raised. Protocol is awsJson1_1, so the error class is carried both in the body member `__type` and in the `x-amzn-errortype` response header, and a wrong class is wrong in both places.

Cause 1 of 3: GetCredentialsForIdentity called with a Logins entry whose login token is not a Cognito-issued OpenID token, together with a CustomRoleArn that the pool's configuration does not permit. AWS: the login token is validated BEFORE the CustomRoleArn eligibility rule, so the refusal is the token one — HTTP 400, `__type` NotAuthorizedException, header `x-amzn-errortype: NotAuthorizedException:`, message entirely fixed text with no variable parts: 'Invalid login token. Not a Cognito token.' Smithy: GetCredentialsForIdentity errors include NotAuthorizedException and InvalidParameterException (both modeled, awsJson1_1); the ordering between the two checks is recorded behavior only. Emulator: HTTP 400 but `__type` InvalidParameterException, header `x-amzn-errortype: InvalidParameterException:`, message 'Only SAML providers and providers with RoleMappings support custom role ARN.' — it evaluates the CustomRoleArn rule first and never reaches the token check. Why: a client that branches on NotAuthorizedException to re-authenticate (refresh the federated login) instead sees a parameter-validation error about a role ARN it did not get wrong, so it retries the same bad token forever or surfaces a misleading error to the user. Fix: the validation ordering and error selection in the GetCredentialsForIdentity handler — validate each Logins token before applying CustomRoleArn eligibility. Traces: cogid-creds-developer-authenticated-credentials-envelope#task#7 (2 steps).

Cause 2 of 3: GetOpenIdTokenForDeveloperIdentity whose Logins carry BOTH a developer-provider login and a public-provider (IdP-proven) login, where the public-provider login is already linked to a different identity than the developer login's identity — the implicit merge the call would require is not possible. AWS: HTTP 400 with `__type` ResourceConflictException and the fixed message text 'Cannot merge these identities.' (no variable parts). Smithy: ResourceConflictException is a modeled error of GetOpenIdTokenForDeveloperIdentity (@httpError 409, but the recorded AWS status on the wire is 400). Emulator: HTTP 400 with `__type` NotAuthorizedException, header `x-amzn-errortype: NotAuthorizedException:`, and the unrelated message "Logins don't match. Please include at least one valid login for this identity or identity pool." Why: the condition is a conflict between two existing identities, not an authorization failure; a client distinguishing 'this login is bad' from 'these identities cannot be merged' takes the wrong branch, and the suggested remedy in the emulator's message (supply a valid login) cannot fix the situation. Fix: the error selection in the GetOpenIdTokenForDeveloperIdentity handler — a cross-identity login conflict must raise ResourceConflictException with AWS's fixed message. Traces: cogid-merge-idp-proven-identity-login-conflicts#task#12.

Cause 3 of 3: GetOpenIdTokenForDeveloperIdentity whose Logins map carries more than one developer-provider key. AWS: HTTP 400 with `__type` InvalidParameterException, header `x-amzn-errortype: InvalidParameterException:`, and the fixed message text 'An identity pool only supports one developer provider. The logins provided have more than one developer provider.' (no variable parts) — an identity pool has at most one DeveloperProviderName, so two developer providers in one Logins map is unsatisfiable. Smithy: GetOpenIdTokenForDeveloperIdentity.Logins is required, a LoginsMap with @length min 0 max 10 — the one-developer-provider rule is not expressible as a member constraint, so it is a handler-level semantic check (recorded behavior). Emulator: HTTP 200, returning an IdentityId and a Token as though the request were valid. Why: this is the most severe cause — the emulator ACCEPTS a request AWS refuses and vends a token for an ambiguous developer identity. A caller that mistakenly sends two developer providers is told it succeeded, builds a session on the resulting token, and the identity-to-developer-user linkage is silently whichever provider the emulator happened to pick; the negative test a client writes against AWS fails only on the emulator. Fix: add the one-developer-provider validation to the GetOpenIdTokenForDeveloperIdentity handler's input validation, raising InvalidParameterException before any token is minted. Traces: cognito-identity-developer-authenticated-identity-flow#task#5.
