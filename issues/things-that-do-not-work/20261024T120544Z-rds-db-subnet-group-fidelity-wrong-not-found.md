# RDS DB-subnet-group fidelity: wrong not-found and in-use error-message templates, and a CloudFormation-created EC2 subnet whose Ref is not a subnet id fails every RDS stack

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteDBSubnetGroup

## Description
Three independent root causes around RDS DB subnet groups. All three are grounded in failing behavioral checks of the `rds` service. THREE causes — close all three before submitting.

These are distinct from the already-open RDS issues 'RDS state and validation fidelity: CA-certificate modification, ... DBSubnetGroup.VpcId, ...' (20261024T030130Z-rds-state-and-validation-fidelity-ca-certificate-modification.md, which covers the MISSING DBSubnetGroup.VpcId member, not the error-message templates below), 'RDS omits state and existence preconditions and misclassifies the resulting errors' (the error CODES here are already correct) and 'RDS awsQuery error envelopes omit RequestId and misclassify parameter validation'. Cause 3 is distinct from the open CloudFormation issues 'CloudFormation stack outputs carry no OutputValue for failing resources' and 'Implement ec2 CreateSubnet: unimplemented scaffold stub' (the EC2 CreateSubnet API itself answers in this suite — other rds checks create subnets through it successfully; what fails is CloudFormation's own physical-resource-id minting for AWS::EC2::Subnet).

Cause 1 of 3: DescribeDBSubnetGroups returns the wrong not-found message template. AWS: Smithy DescribeDBSubnetGroups models exactly one error, DBSubnetGroupNotFoundFault (errorKind client, httpError 404, awsQueryError code DBSubnetGroupNotFoundFault / 404), raised when DBSubnetGroupName names no group. The message is built from the request — it quotes the requested DBSubnetGroupName — and recorded behavior for DescribeDBSubnetGroups is the template "DB Subnet group '<DBSubnetGroupName>' not found." (for example, for a group named `sim2real-behav-sng-ctrl-b830601d76a4`: `DB Subnet group 'sim2real-behav-sng-ctrl-b830601d76a4' not found.`). Recorded behavior also shows AWS uses a DIFFERENT template on the mutating paths for the same code: DeleteDBSubnetGroup and ModifyDBSubnetGroup answer "DB subnet group '<name>' does not exist.". Emulator: HTTP 404 with the correct code DBSubnetGroupNotFoundFault, but a single template "DBSubnetGroup '<name>' not found." (observed: `DBSubnetGroup 'sim2real-behav-sng-ctrl-b830601d76a4' not found.`) — the resource-name wording is the raw shape name and the read/mutate distinction is absent. Why: the status and code are matchable, but a client (or a human operator reading a CLI transcript, or a log-scraping/alerting rule keyed on the service's wording) that distinguishes 'this group was never created' from 'this group cannot be mutated' by the message text sees one undifferentiated string, and any assertion on the documented wording fails. Fix: the not-found message construction in the DescribeDBSubnetGroups handler and in the DeleteDBSubnetGroup / ModifyDBSubnetGroup handlers (they must not share one template). Traces: rds.delete-nonexistent-subnet-group.

Cause 2 of 3: DeleteDBSubnetGroup's in-use rejection uses the wrong message template. AWS: Smithy DeleteDBSubnetGroup models InvalidDBSubnetGroupStateFault (errorKind client, httpError 400, awsQueryError code InvalidDBSubnetGroupStateFault / 400) for a group still referenced by a DB instance or cluster. The message is built from the request and from the blocking resource, and recorded behavior is the template "Cannot delete the subnet group '<DBSubnetGroupName>' because at least one database instance: <DBInstanceIdentifier> is still using it." (example: `Cannot delete the subnet group 'sim2real-behav-subg-inuse-9d1796688cd2' because at least one database instance: sim2real-behav-dbi-2b17ed10864e is still using it.`). Emulator: HTTP 400 with the correct code InvalidDBSubnetGroupStateFault but the template "DB subnet group <name> can't be deleted because it is in use by DB instance <id>" — the group name is unquoted and the sentence is rephrased. Why: the precondition and classification are right, so this is a wording-only divergence, but it is a wording produced by a known rule (the AWS template parameterized by the group name and the holding instance id), so a caller that parses the blocking resource out of the message, or a transcript comparison against AWS, diverges. Fix: the in-use message construction in the DeleteDBSubnetGroup handler. Traces: rds.delete-subnet-group-in-use.

Cause 3 of 3: a CloudFormation-provisioned AWS::EC2::Subnet gets a synthesized physical resource id that is not an EC2 subnet id, so !Ref on it is rejected by RDS and every stack that places an RDS resource in its own VPC fails. AWS: a provisioned AWS::EC2::Subnet's physical resource id IS its EC2 subnet id, so `!Ref` of that resource yields `subnet-` followed by 8 or 17 hexadecimal characters, which is what AWS::RDS::DBSubnetGroup's SubnetIds requires; Smithy models CreateDBSubnetGroup/ModifyDBSubnetGroup with the error InvalidSubnet (errorKind client, httpError 400, awsQueryError code InvalidSubnet / 400) for a value that is not a subnet of the account. Recorded behavior for this template is CREATE_COMPLETE: the subnets are created, their ids are substituted into the DB subnet group, and the group is created. Emulator: CloudFormation gives the AWS::EC2::Subnet resource a generic, name-derived physical id of the form `<stack-name>-<LogicalId>-<hex>` (observed: `sim2real-rds-dp-a239d9e4f9a1-SubA-A0F4C1B27F02`), `!Ref SubA` resolves to that string, RDS correctly refuses it with InvalidSubnet ("... is not an EC2 subnet id (expected subnet- followed by 8 or 17 hexadecimal characters)"), and the stack ends CREATE_FAILED with "The following resource(s) failed to create: [SubnetGroup]." Why: no IaC deployment that creates its own VPC/subnets and then places an RDS DB subnet group, DB instance, DB cluster or DB proxy in them can ever reach CREATE_COMPLETE — the whole CloudFormation+RDS deployment path is unusable, and the failure is misattributed to RDS (which is behaving correctly) rather than to the CloudFormation resource provider. Hypothesis: AWS::EC2::Subnet has no dedicated resource provider in the CloudFormation engine and falls through to the generic physical-id generator instead of calling EC2 CreateSubnet and recording the returned SubnetId. Fix: the CloudFormation engine's resource-provisioning/physical-resource-id resolution for AWS::EC2::Subnet (it must provision through the EC2 service and record the real `subnet-...` id as the resource's physical id, so Ref/GetAtt hand downstream services a usable value); the RDS side needs no change. Traces: rds.deploy-rds-1-protected-stack-delete-blocked-then-snapshot-retain-honored.
