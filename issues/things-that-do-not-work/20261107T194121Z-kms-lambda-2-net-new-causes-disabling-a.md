# kms__lambda: 2 net-new causes — disabling a function's environment CMK produces no Environment.Error and no KMSDisabledException on a cold Invoke, and a handler's boto3.client("kms") still dies with UnknownServiceError

> _Note: this issue was identified against the code base at commit `d58fa0759c246b06d8eee65f217a3be5842074ab`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two root causes, reached by two checks the suite marked neither ALREADY FILED nor OWNED (their replay keys drifted when the emulator's symptoms moved, so no open issue currently gates them).

Cause 1 of 2 — the availability of the CMK that encrypts a function's environment variables is never enforced: DisableKey changes nothing on the configuration read or on a cold invocation. Failing check id (1): kms__lambda.deep-lambda-2-env-kms-disable-blocks-cold-invoke-then-enable-restores.
AWS: Smithy (lambda) GetFunctionConfiguration -> FunctionConfiguration.Environment targets EnvironmentResponse, a union of Variables (sensitive map) and Error -> EnvironmentError{ErrorCode, Message}, documented as 'Error messages for environment variables that couldn't be applied'; Invoke declares KMSDisabledException as a server error with httpError 502, documented 'Lambda couldn't decrypt the environment variables because the KMS key used is disabled.' Recorded behavior fills in the texts: while the key is enabled, GetFunctionConfiguration reports Environment.Variables and NO Error. Once the CMK named by KMSKeyArn is disabled, GetFunctionConfiguration reports Environment.Error with ErrorCode 'DisabledException' and Message whose fixed text is 'Lambda was unable to decrypt your environment variables because the KMS key used is disabled. Please check your KMS key settings. KMS Exception: DisabledException KMS Message: ' + ' is disabled.' with the key ARN as its only variable part, and it no longer reports Variables at all (the plaintext must not stay readable). A cold Invoke is then refused with Error.Code 'KMSDisabledException' at HTTP 502 and the message whose fixed text is 'Lambda was unable to decrypt the environment variables because the KMS key used is disabled. Please check the function's KMS key settings. KMS Exception: DisabledExceptionKMS Message: ' + ' is disabled. (Service: Kms, Status Code: 400, Request ID: ' + ') (SDK Attempt Count: 1)' — variable parts being the key ARN and the relayed per-call KMS request id — and it is refused on every retry, not only once. kms EnableKey restores both the successful Invoke and the Variables-without-Error configuration.
Emulator: nothing changes after kms DisableKey. GetFunctionConfiguration keeps answering 200 with Environment={'Variables': {'SECRET': '<marker>'}} and KMSKeyArn still echoed, so the check's 120 s poll for Environment.Error raises 'Environment.Error after DisableKey not observed within 120s'. The plaintext environment variable stays readable through the API, and the cold-Invoke refusal (KMSDisabledException/502) is never reached.
Why: environment-variable encryption gives a client no protection and no diagnosis. Disabling the CMK — the standard bulk-revocation control — neither hides the plaintext from GetFunctionConfiguration nor stops the function from running, and an operator debugging a real 502 KMSDisabledException sees a healthy configuration instead of Environment.Error naming the disabled key.
Fix: the function cold-start/configuration-read path of the Lambda service must decrypt Environment.Variables through the CMK in KMSKeyArn and surface the failure: GetFunctionConfiguration must replace Variables with EnvironmentError{ErrorCode:'DisabledException', Message:<the template above>} while the key is unusable, and Invoke must answer KMSDisabledException at HTTP 502 with its own message template, both clearing when the key is re-enabled. Related open issue that no longer carries this replay key: 20261105T111951Z-kms-lambda-environment-variable-kms-enforcement-and-kms.md (it describes this contract, but its recorded symptom was a 60 s hang; the emulator now answers quickly with an un-erroring configuration).

Cause 2 of 2 — a handler cannot construct a KMS client at all: boto3.client("kms") raises botocore UnknownServiceError inside the managed python runtime, so no in-function KMS authorization contract is observable. Failing check id (1): kms__lambda.kms-key-policy-deny-overrides-lambda-identity-allow.
AWS: recorded behavior only for the CONTENTS of the managed runtime (the model describes the Invoke wire shape, not the execution environment). AWS's managed python3.x runtimes ship a botocore whose data directory holds every public service model, so boto3.client("kms") always constructs and the call is dispatched with the execution role's credentials. KMS then answers: an authorization refusal is the service-common AccessDeniedException (HTTP 400, Error.Code 'AccessDeniedException') whose message template is 'User: ' + ' is not authorized to perform: ' + ' on resource: ' + the reason clause 'with an explicit deny in a resource-based policy' when the key policy carries an explicit Deny for that principal — variable parts being the assumed-role session ARN, the action (kms:Decrypt) and the key ARN. So the expected handler payloads are: both keys encrypt and decrypt while only the identity policy allows, then the denied key reports AccessDeniedException for kms:Decrypt while kms:Encrypt on it and kms:Decrypt on the control key still succeed.
Emulator: the baseline poll never satisfies its predicate — last result {'denied': {'encrypt_ok': False, 'encrypt_code': 'UnknownServiceError'}, 'control': {'encrypt_ok': False, 'encrypt_code': 'UnknownServiceError'}} — i.e. the handler caught a botocore client-construction failure before any request left the sandbox. botocore's message template here is "Unknown service: '<service-name>'. Valid service names are: <the models the runtime image actually contains>"; the requested id 'kms' comes from the boto3.client call. No KMS request is ever made, so neither the identity Allow nor the key-policy Deny is exercised.
Why: an explicit key-policy Deny — the control that overrides an identity-policy Allow — cannot be verified against the emulator, and the failure surfaces as a non-service exception rather than KMS's AccessDeniedException, so an operator cannot tell a policy denial from a broken runtime image.
Fix: the Lambda execution-environment component that assembles the python runtime filesystem must install a botocore whose data directory carries the full service-model set (at minimum every service the emulator serves), and behind it the KMS Decrypt path must evaluate the key policy and grants for the calling role. Related open issue that no longer carries this replay key: 20261106T143106Z-kms-lambda-a-handler-s-boto3-client-kms.md describes exactly this cause but was keyed to the earlier timeout signature, which has since become this AssertionError.

Traces: the 2 failing check ids above; see trace_ids.
