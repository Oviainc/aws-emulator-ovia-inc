# CodeArtifact control plane: 10 fidelity divergences in GetAuthorizationToken duration semantics/messages, conflict + not-found wording, origin-block and digest-mismatch classification, and the package-version status machine

> _Note: this issue was identified against the code base at commit `ec258a82c643322f3f1b10a7ea424abc4c176038`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PublishPackageVersion

## Description
This issue bundles TEN distinct net-new root causes in the CodeArtifact control plane, all grounded in failing behavioral checks of this replay. A fixer must close all ten before submitting; each cause below names its own failing check ids.

=== Cause 1 of 10: GetAuthorizationToken's in-gap durationSeconds refusal uses the wrong message text ===
AWS: Smithy GetAuthorizationTokenRequest.durationSeconds targets AuthorizationTokenDurationSeconds @range(min 0, max 43200); its own documentation states "Valid values are 0 and any number between 900 (15 minutes) and 43200 (12 hours)", i.e. the accepted set is DISCONTINUOUS. A non-zero value below 900 is refused with ValidationException (modeled httpError 400) whose message is "Invalid durationSeconds value of <N>: value must be 0 or between 900 and 43200 (inclusive)." — fixed text "Invalid durationSeconds value of ", ": value must be 0 or between 900 and 43200 (inclusive).", with <N> the durationSeconds the request sent. A value ABOVE the modeled ceiling is refused by the modeled-range layer instead, with the shared constraint-violation sentence "1 validation error detected: Value '<N>' at 'durationSeconds' failed to satisfy constraint: Member must have value less than or equal to 43200" (fixed text apart from <N>). The two ends are therefore two different layers with two different sentences.
Emulator: the gap refusal is ValidationException (correct code) but the message is "durationSeconds value <N> is not valid; valid values are 0 and any number between 900 and 43200." — built in services/service-com-amazonaws-codeartifact-codeartifactcontrolplaneservice/src/ops/get_authorization_token.rs at the authorization_period() guard.
Why: a client that matches or surfaces the service's validation sentence (CLI output assertions, log scrapers, error-classification tests) sees text AWS never emits, and cannot distinguish the service-rule refusal from the modeled-range refusal.
Fix: the message construction in that operation's validation branch in src/ops/get_authorization_token.rs; the high end must keep going through the shared modeled-constraint sentence.
Traces: codeartifact.authorization-token-duration-below-minimum-rejected, codeartifact.authorization-token-duration-out-of-range-rejected.

=== Cause 2 of 10: durationSeconds=0 mints a 1-hour token instead of the maximum session lifetime ===
AWS: the member's documentation — "A value of 0 will set the expiration of the authorization token to the same expiration of the user's role's temporary credentials" — combined with the operation's "CodeArtifact authorization tokens are valid for a period of 12 hours". Recorded behavior: durationSeconds=0 yields an expiration strictly MORE than 3600s away (the maximum session lifetime), while durationSeconds=900 and 3600 yield expiries about 900s and 3600s away, 2700s apart.
Emulator: durationSeconds=0 produced a token lasting 3600.0s. The handler maps 0 to Period::CallerCredentials and, when the request was not signed with a session the emulator's STS store holds, falls back to CALLER_CREDENTIAL_PERIOD = 3600s (src/ops/get_authorization_token.rs). So a caller with a long-term key gets an hour where AWS gives the maximum.
Why: 0 is what the CLI's `codeartifact login` path relies on for a long-lived credential; a 1-hour token makes long builds and any test that asserts "0 means maximum, not minimum" fail against the emulator while passing on AWS.
Fix: the fallback period for Period::CallerCredentials in src/ops/get_authorization_token.rs — with no session behind the credential it must be the documented maximum authorization period, not AssumeRole's 3600s default.
Traces: codeartifact.authorization-token-duration-shapes-expiry.

=== Cause 3 of 10: CreateRepository's duplicate-name ConflictException message is reworded ===
AWS: Smithy CreateRepository (POST /v1/repository) models ConflictException httpError 409. For a repository name already taken inside the addressed domain the message is "Repository <repository> already exists in domain <domain>." — fixed text "Repository ", " already exists in domain ", "."; <repository> and <domain> are the request's own values. The account is NOT part of the sentence and neither value is quoted.
Emulator: ConflictException (correct code) with "Repository '<repository>' in domain '<domain>' owned by '<account>' already exists." — different word order, quoted values, and an extra owner clause.
Why: the conflict is the normal idempotency signal for provisioning code; any client that parses or asserts the sentence (and the CFN/IaC layers that surface it verbatim) sees text AWS never produces.
Fix: the duplicate-name refusal message in the CreateRepository handler (src/ops/create_repository.rs) / the shared repository-conflict message helper in src/state.rs. The rest of both checks' assertions (no clobbering of description/upstreams/createdTime, name free again after delete, same name reusable in another domain) are satisfied once the sentence matches.
Traces: codeartifact.create-repository-duplicate-name-rejected, codeartifact.create-repository-duplicate-does-not-clobber.

=== Cause 4 of 10: a publish blocked by the package origin configuration is answered AccessDeniedException instead of ValidationException ===
AWS: Smithy PublishPackageVersion models both AccessDeniedException (httpError 403) and ValidationException (httpError 400). A publish into a package whose originConfiguration.restrictions.publish is BLOCK is refused as a VALIDATION failure: ValidationException, HTTP 400, message "This package is configured to block new versions from being published." — that sentence is entirely fixed text, it names no package. (PutPackageOriginConfiguration's `publish` member is documented as deciding whether new versions can be published to the repository, so the refusal is about the request being invalid for that package, not about the caller's permissions.)
Emulator: AccessDeniedException with "Publishing package <package> is blocked by its package origin configuration." — wrong error class (403 instead of 400), wrong message, and it interpolates the package name into a sentence that has none.
Why: AccessDenied vs Validation is the branch every SDK retry/permission-diagnosis path takes: a client sees a 403 and concludes its IAM principal is wrong (and tools escalate to credential refresh or alarm on authorization failures) when the actual condition is a repository origin control that no credential change can fix.
Fix: the origin-restriction branch of the PublishPackageVersion handler (src/ops/publish_package_version.rs) — it must raise the modeled ValidationException with the fixed sentence. The open issue 20261024T061931Z-codeartifact-cfn-provisioned-domains-absent-resource-policies-never.md mentions an origin-block mis-classification among its causes and owns the checks codeartifact.publish-to-read-only-upstream-repository-blocked and codeartifact.publish-duplicate-immutable-version-rejected; it does NOT carry the three checks listed here, which still fail on this exact verdict.
Traces: codeartifact.codeartifact-package-origin-configuration-blocks-direct-publish, codeartifact.package-origin-configuration-blocks-direct-publish, codeartifact.package-origin-configuration-blocks-publish.

=== Cause 5 of 10: a mismatched assetSHA256 is answered SignatureDoesNotMatch instead of ValidationException naming both digests ===
AWS: PublishPackageVersion.assetSHA256 is bound to the header x-amz-content-sha256 (SHA256, @length 64, pattern ^[0-9a-f]+$) and assetContent is the streaming httpPayload. The service HASHES the payload and compares: a mismatch is ValidationException, HTTP 400, message "The provided content hashes do not match the calculated content hashes. Hash algorithm 'SHA-256', Expected hash '<the assetSHA256 the request declared>', Actual hash '<the SHA-256 the service computed over the uploaded bytes>'" — the two hex digests are values from the request and from the uploaded bytes, the rest is fixed text. The published version must then be ABSENT.
Emulator: ('SignatureDoesNotMatch', 'The request signature does not match') — not a modeled error of this operation at all. Hypothesis: because assetSHA256 rides on x-amz-content-sha256, the emulator's SigV4 request-authentication middleware compares that header to the body and rejects the request before the operation handler ever runs, so the service never performs (or reports) a content-hash comparison.
Why: clients retry/re-sign on SignatureDoesNotMatch and alarm on it as a credential or clock problem, so a corrupted upload is diagnosed as a signing failure; and the ValidationException wording — which is what proves the service hashed the payload rather than trusting the header — is never produced.
Fix: the payload-digest comparison must happen in the PublishPackageVersion handler (src/ops/publish_package_version.rs) with the modeled ValidationException above, and the generic signature-verification middleware must not treat this operation's x-amz-content-sha256 payload digest as a signature mismatch. Open issue 20261022T171312Z-codeartifact-no-iam-authorization-on-reads-publishpackageversion-digest.md names this symptom and owns codeartifact.codeartifact-publish-with-mismatched-asset-sha256-rejected-and-version-absent; it does not carry the check below, which still fails identically.
Traces: codeartifact.publish-asset-sha256-mismatch-rejected.

=== Cause 6 of 10: UpdatePackageVersionsStatus refuses targetStatus=Disposed with a modeled-enum constraint sentence instead of the service's rule ===
AWS: Smithy PackageVersionStatus enumerates Published | Unfinished | Unlisted | Archived | Disposed | Deleted, and UpdatePackageVersionsStatus.targetStatus targets that whole enum, so Disposed is a WIRE-VALID value. The service refuses it by its own rule ("To set the status of a package version to Disposed, use DisposePackageVersions"): ValidationException, HTTP 400, message "Target status is not allowed." — entirely fixed text, naming neither the member nor the value set.
Emulator: ValidationException whose message is the modeled-constraint sentence "1 validation error detected: Value 'Disposed' at 'targetStatus' failed to satisfy constraint: Member must satisfy enum value set: [Archived, Published, Unlisted]", produced in src/ops/update_package_versions_status.rs by the UPDATABLE_PACKAGE_VERSION_STATUSES guard via crate::state::constraint_violation_message.
Why: the emulator advertises a narrower enum than the service models, so a client that validates against the model (or renders the service's rule to a user) is told the value is structurally invalid rather than routed to DisposePackageVersions, which is the operation that owns the transition.
Fix: that guard in src/ops/update_package_versions_status.rs must raise ValidationException with the fixed sentence "Target status is not allowed." instead of the constraint-violation sentence; the no-effect read-back and the DisposePackageVersions positive control are already correct.
Traces: codeartifact.update-status-to-disposed-rejected.

=== Cause 7 of 10: UpdatePackageVersionsStatus grades a batch per version instead of SKIPPING the siblings of a forbidden transition ===
AWS: the operation answers 200 with successfulVersions + failedVersions (PackageVersionError, errorCode from PackageVersionErrorCode: ALREADY_EXISTS | MISMATCHED_REVISION | MISMATCHED_STATUS | NOT_ALLOWED | NOT_FOUND | SKIPPED). Recorded behavior: when one named version cannot make the transition (a Disposed version -> Archived, reported errorCode NOT_ALLOWED), the OTHER versions in the same call are not applied — each appears in failedVersions with errorCode SKIPPED and keeps its previous status. SKIPPED exists for exactly this. The identical transition issued alone afterwards succeeds, which is how we know nothing was wrong with the sibling itself.
Emulator: the sibling is applied and reported in successfulVersions ({'revision': ..., 'status': 'Archived'}); src/ops/update_package_versions_status.rs decides and commits each version independently in one pass, and never emits the SKIPPED error code at all.
Why: a caller batching status moves gets a partial, half-applied mutation where AWS makes the call all-or-nothing: versions the caller believes were rejected have in fact been relabelled, and the SKIPPED code a client branches on is never returned.
Fix: make move_versions in src/ops/update_package_versions_status.rs two-phase — decide every named version first, and if any decision is a failure, commit nothing and report the otherwise-valid versions in failedVersions with errorCode SKIPPED (and a message of that class) instead of writing them.
Traces: codeartifact.update-package-version-status-invalid-target-rejected.

=== Cause 8 of 10: a status change republishes the version — versionRevision is advanced where AWS keeps it ===
AWS: PackageVersionRevision identifies the version's CONTENT. A status move (Published -> Unlisted / Archived) relabels a version and leaves its revision as the publish produced it; recorded behavior shows the revision reported before and after the move identical.
Emulator: the move changes the revision — the handler calls stored.advance_sequence() whenever the status actually differs (src/ops/update_package_versions_status.rs), and the SuccessfulPackageVersionInfo.revision plus every later read report the new value.
Why: revisions are the optimistic-concurrency token clients pin in versionRevisions / expectedStatus workflows and in DisposePackageVersions. If a status relabel rotates it, every pinned revision a client holds goes stale and its next conditional call fails MISMATCHED_REVISION against AWS-correct code. (The related check codeartifact.disposed-package-version-is-terminal, which sees the same rotation on disposal, is OWNED by 20261024T061931Z and is not re-filed here — but the fix belongs in the same revision-derivation logic.)
Fix: the revision derivation in src/state.rs (the stored version's revision()/advance_sequence() pair) and its call site in src/ops/update_package_versions_status.rs: a status transition must not advance the content revision.
Traces: codeartifact.package-version-status-progresses-to-archived.

=== Cause 9 of 10: DisposePackageVersions deletes the assets synchronously, so the version's assets vanish the instant it is disposed ===
AWS: DisposePackageVersions (POST /v1/package/versions/dispose) reports the version in successfulVersions with status Disposed and DescribePackageVersion shows Disposed immediately — but the asset deletion it documents is NOT synchronous. Recorded behavior, sampled across a 120-240s window: ListPackageVersionAssets still lists the version's assets unchanged, and GetPackageVersionAsset still streams the ORIGINAL bytes. The version's metadata record is retained (same version, listable under status='Disposed').
Emulator: the assets are gone at once — ListPackageVersionAssets returns assets=[] immediately after disposal, and GetPackageVersionAsset is refused ResourceNotFoundException "Asset <assetName> not found in package version <package> <version> in repository <repository>." on the first call after disposal.
Why: a client reading a disposed version's assets (an audit or retention tool, or anything draining in-flight downloads after a dispose) gets a 404 where AWS still serves the bytes, so retention/undo windows that work on AWS break here; and a test asserting the asset is still listed cannot pass.
Fix: the asset-removal step of the DisposePackageVersions handler (src/ops/dispose_package_versions.rs) and the asset-visibility predicates the ListPackageVersionAssets / GetPackageVersionAsset handlers apply to a Disposed version in src/state.rs: disposal must set the status and retain the asset records rather than deleting them in the same call.
Traces: codeartifact.package-version-status-lifecycle-publish-to-disposed, codeartifact.get-package-version-asset-after-disposal-blocked.

=== Cause 10 of 10: DescribePackageGroup's not-found sentence is reworded ===
AWS: DescribePackageGroup (GET /v1/package-group) models ResourceNotFoundException httpError 404. For a deleted/absent group the message is "Package Group not found not found. Package Group '<pattern>' in domain <domain> owned by account <account> does not exist" — note the service's own capitalisation "Package Group", its doubled "not found not found.", the pattern in single quotes, the domain and account NOT quoted, and NO trailing period. <pattern>, <domain> and <account> come from the request and the caller's account; the rest is fixed text.
Emulator: ResourceNotFoundException (correct code) with "Package group not found. Package group '<pattern>' in domain '<domain>' owned by account '<account>' does not exist." — different capitalisation, the doubled clause dropped, the domain and account quoted, trailing period added.

Fix: the not-found message helper used by the DescribePackageGroup handler (src/ops/describe_package_group.rs and the package-group message helper in src/state.rs).
Traces: codeartifact.package-group-lifecycle-create-active-delete.
