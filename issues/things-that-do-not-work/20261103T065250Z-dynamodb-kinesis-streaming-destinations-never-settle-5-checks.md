# DynamoDB Kinesis streaming destinations never settle (5 checks hang), malformed/second stream ARNs mis-validated, and the CFN-deployed streaming table is missing

> _Note: this issue was identified against the code base at commit `ce4f28f15b4841beefbad6c596b9d2158570753e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
EnableKinesisStreamingDestination

## Description
Four net-new root causes on the DynamoDB -> Kinesis streaming-destination surface. All four must be closed before submitting.

Cause 1 of 4: a streaming destination never reaches a TERMINAL status, so every caller that waits for one hangs. AWS: EnableKinesisStreamingDestination returns DestinationStatus=ENABLING and the destination then settles -- to ACTIVE when the stream is usable, or to ENABLE_FAILED when it is not (a stream in another region, a stream that does not exist); DisableKinesisStreamingDestination settles to DISABLED, and after the table is deleted the stream and the records already delivered survive. The settled status is what DescribeKinesisStreamingDestination reports and what the ACTIVE filter selects on (Smithy: KinesisStreamingDestinationOutput.DestinationStatus -> DestinationStatus enum; errors ResourceInUseException, ResourceNotFoundException, LimitExceededException). Emulator: the status never leaves its initial value and no record is ever delivered, so five checks that poll for a settled destination ran to the 60.0s check deadline and were killed; in a related already-filed case a destination pointed at a nonexistent stream was reported ACTIVE. Why: a hang is the worst failure mode for a client -- the call neither succeeds nor fails -- and an ACTIVE-but-dead destination silently drops the change stream. Fix: the destination state machine and record delivery in the EnableKinesisStreamingDestination / DescribeKinesisStreamingDestination handlers and the table's streaming state. Checks: dynamodb__kinesis.ddbkds-cross-region-stream-arn-settles-to-enable-failed, dynamodb__kinesis.ddbkds-deleting-a-streaming-table-leaves-its-stream-and-delivered-records, dynamodb__kinesis.ddbkds-destination-precision-sets-the-unit-of-each-record-creation-time, dynamodb__kinesis.ddbkds-enable-failed-destination-is-excluded-by-the-active-filter, dynamodb__kinesis.ddbkds-precision-update-switches-the-creation-time-unit-of-later-records.

Cause 2 of 4: a StreamArn that clears the modeled length floor but is not an ARN is refused up front instead of settling to ENABLE_FAILED. AWS: StreamArn is @length 37..1024 (Smithy: EnableKinesisStreamingDestination.StreamArn, required); a value that satisfies the length constraint is ACCEPTED by the call and the destination then settles to ENABLE_FAILED. Emulator: answers 400 ValidationException 'Invalid StreamArn: Invalid StreamArn provided as input <value>'. Why: the client never sees the asynchronous failure path AWS models, and a value AWS accepts is rejected at the API. Fix: EnableKinesisStreamingDestination's StreamArn validation (accept past the length floor, fail asynchronously). Check: dynamodb__kinesis.ddbkds-malformed-stream-arn-settles-to-enable-failed.

Cause 3 of 4: re-enabling and second-destination refusals diverge. AWS: an ENABLE against a destination that is not DISABLED or ENABLE_FAILED is refused with 'Table is not in a valid state to enable Kinesis Streaming Destination: EnableKinesisStreamingDestination must be DISABLED or ENABLE_FAILED to perform ENABLE operation.' -- fixed text, no stream/table interpolation -- and a SECOND stream while one is already active is refused outright. Emulator: answers 'Table is not in a valid state to enable Kinesis Streaming Destination: Streaming destination with streamArn: <arn> is already enabled for table with tableName: <table>' for the re-enable, and ACCEPTS the second stream with HTTP 200 and DestinationStatus ENABLING. Why: a table ends up with two destinations that AWS would never allow. Fix: the destination admission checks in EnableKinesisStreamingDestination. Checks: dynamodb__kinesis.ddbkds-re-enabling-the-active-stream-rejected, dynamodb__kinesis.ddbkds-second-stream-while-one-is-active-rejected.

Cause 4 of 4: the CloudFormation-deployed streaming table does not exist after the stack reports deployed. AWS: once the stack is CREATE_COMPLETE its AWS::DynamoDB::Table exists and DescribeTable returns it with the declared 5/5 provisioned throughput. Emulator: DescribeTable for the stack's table answered ResourceNotFoundException 'Requested resource not found: Table: <stack-table> not found' in the deploy phase, so the all-regions inventory can never be derived. Why: the deploy reports success while the resource is absent, which is indistinguishable from a successful deploy until the next call fails. Fix: the CloudFormation resource provider for AWS::DynamoDB::Table (the same area as open issue 20261025T015306Z-cloudformation-cannot-deploy-large-parts-of-the-resource.md, which does not carry this check's replay key). Check: dynamodb__kinesis.e2e-ddbkds-list-streaming-tables-all-regions-lifecycle.
