# cloudformation__signer: 2 net-new causes — Signer stack Outputs come back without OutputValue, and an AWS::Signer::ProfilePermission naming an unsupported action reaches CREATE_COMPLETE instead of rolling back with Signer's refusal

> _Note: this issue was identified against the code base at commit `5b2a9eedb8fa287cac2318fd09ae07f52de03ab6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeStacks

## Description
Two independent net-new root causes on CloudFormation stacks that deploy AWS::Signer::SigningProfile + AWS::Signer::ProfilePermission. BOTH must be closed before this issue is submitted.

Cause 1 of 2: DescribeStacks returns Outputs entries with no OutputValue, so Ref/Fn::GetAtt results of the Signer resources are unobtainable.
AWS: DescribeStacks returns each declared Output as a com.amazonaws.cloudformation#Output carrying OutputKey and OutputValue (Smithy, services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json: members OutputKey, OutputValue, Description, ExportName). The template under test declares ProfileArn={Ref: Profile}, ProfileName/ProfileVersion/ProfileVersionArn={Fn::GetAtt: [Profile, ...]} and PermissionRef={Ref: Permission}; AWS resolves them to the values Signer itself reports for the profile (arn, profileName, profileVersion, profileVersionArn) and, for the permission, to '<StatementId>|<ProfileName>'. 200 response, no error code — the defect is a missing response member.
Emulator: the stack reaches CREATE_COMPLETE and DescribeStacks lists Outputs, but an entry carries no OutputValue, so reading it raises KeyError: 'OutputValue'.
Why: a client cannot read back any identifier of the resources the stack created, so the profile ARN/version it must hand to a code-signing config, and the permission's composite Ref, are unavailable; nested stacks, exports and deploy scripts that consume these Outputs get nothing.
Fix: CloudFormation's Outputs resolution and the DescribeStacks serializer — Ref/Fn::GetAtt on AWS::Signer::SigningProfile (Ref = the profile ARN; ProfileName, ProfileVersion, ProfileVersionArn) and on AWS::Signer::ProfilePermission (Ref = '<StatementId>|<ProfileName>') must resolve against Signer's own state for the created resource, and every Output row must carry OutputValue. The same missing-OutputValue family is already filed for other resource sets (20261109T141301Z-cloudformation-s3tables-…, 20261109T143402Z-cloudformation-mq-…, 20261109T144605Z-cloudformation-elasticbeanstalk-…); none covers AWS::Signer::* outputs, which is what this cause is grounded in.
Failing check ids: cloudformation__signer.deploy-signer-signingprofile-and-profilepermission-round-trip-and-delete.

Cause 2 of 2: an AWS::Signer::ProfilePermission whose Action the profile's platform does not support is provisioned successfully instead of being refused by Signer and rolling the stack back.
AWS: the resource handler calls Signer, Signer refuses the action, the stack ends ROLLBACK_COMPLETE and the Permission resource's single CREATE_FAILED event carries ResourceStatusReason 'Resource handler returned message: "Invalid request provided: Action <action> not supported for platform <platformId>. Action must be one of [signer:StartSigningJob, signer:GetSigningProfile, signer:RevokeSignature] (Service: Signer, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)'. Fixed text: the 'Invalid request provided: ' prefix CloudFormation adds, Signer's own sentence 'Action … not supported for platform …. Action must be one of [signer:StartSigningJob, signer:GetSigningProfile, signer:RevokeSignature]', the '(Service: Signer, Status Code: 400, Request ID: …) (SDK Attempt Count: …)' suffix, and the handler envelope with HandlerErrorCode InvalidRequest; variable parts are the request's Action value, the profile's PlatformId, and the per-run request id / token / attempt count. Recorded behavior for the rollback's effect, read through Signer: the profile the rolled-back stack created is left in status 'Canceled' (Signer's tombstone, it is never hard-deleted) and ListProfilePermissions on it answers 404 ResourceNotFoundException 'No policies associated with profile <profileName>'.
Emulator: the stack with Action 'signer:NotARealAction' ends CREATE_COMPLETE ('AssertionError: rejected stack ended \'CREATE_COMPLETE\''), so no CREATE_FAILED row, no handler reason, and a permission statement for an action Signer does not support is left on the profile's policy.
Why: the emulator green-lights a deployment AWS refuses, so a template with a typo'd or unsupported action deploys a resource policy that grants an action no principal can ever use, and the caller never sees the refusal that names the allowed action set for the platform. The rollback semantics the check reads through Signer (profile Canceled, policy absent) are equally unreachable.
Fix: the AWS::Signer::ProfilePermission resource handler in CloudFormation — it must perform the create through Signer's AddProfilePermission path (whose platform-derived allowed-action validation is the authority) and surface the refusal as a CREATE_FAILED with HandlerErrorCode InvalidRequest and the 'Invalid request provided: ' + Signer-worded reason above, then roll the stack back. Note the related open issue 20261024T054020Z-signer-addprofilepermission-validation.md is about AddProfilePermission accepting a non-AWS principal and does not cover the CFN handler bypassing the action check; the exact Signer wording this reason must carry is the one the resolved wire issue 20261029T191542Z-signer-error-paths-diverge-from-aws-in-message.md specified for AddProfilePermission.
Failing check ids: cloudformation__signer.deploy-signer-profilepermission-invalid-action-rejected-and-rolled-back.
