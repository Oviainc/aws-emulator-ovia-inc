=== Cause 1 of 2: a snapshot minted by EBS StartSnapshot (and driven to completion by CompleteSnapshot) is never registered in the snapshot state EC2 DescribeSnapshots reads, so the lifecycle is unobservable and every write-then-wait-then-read flow dead-ends ===
AWS: Smithy com.amazonaws.ebs#StartSnapshot — http POST /snapshots, code 201, output SnapshotId/OwnerId/Status/StartTime/VolumeSize/BlockSize/Tags/ParentSnapshotId; Status targets the `Status` enum. Smithy com.amazonaws.ebs#CompleteSnapshot — http POST /snapshots/completion/{SnapshotId}, code 202, required header x-amz-ChangedBlocksCount, output Status. The EBS model exposes NO read of snapshot state, so ec2:DescribeSnapshots is the only way a caller observes the lifecycle: the id StartSnapshot returns resolves immediately with State `pending`, and after CompleteSnapshot the same id resolves with State `completed` and Progress `100%`; tags and Description passed to StartSnapshot are readable on that EC2 snapshot record. An id EC2 genuinely does not hold is refused with error code `InvalidSnapshot.NotFound` (recorded behavior only for the EC2 response shape and that code; the message's fixed text is "The snapshot '<snapshot-id>' does not exist." with the id taken from the request).
Emulator: `ec2.describe_snapshots(SnapshotIds=[<id StartSnapshot just returned>])` is refused with `InvalidSnapshot.NotFound` for the entire 150 s poll window — in every one of these 15 checks the poll helper exits with `last=None`, i.e. DescribeSnapshots never once returned a record for the id. The EBS StartSnapshot/PutSnapshotBlock/CompleteSnapshot handlers answer 2xx and write their own block/snapshot state, but nothing registers the snapshot where the EC2 read path looks. Every assertion the checks make BEFORE the poll (StartSnapshot Status `pending`, PutSnapshotBlock 201 with x-amz-checksum/x-amz-checksum-algorithm, CompleteSnapshot Status pending|completed, the checksum/DataLength/block-index refusals) passes; the run dies the moment it needs to read the snapshot back.
Why: the EBS direct API's contract is write → wait for `completed` → read. A client (or the botocore `snapshot_completed` waiter) is told the snapshot it just created does not exist, so it never learns the snapshot is usable, cannot verify Progress 100%, cannot read back its Description/Tags, cannot drive GetSnapshotBlock/ListSnapshotBlocks/ListChangedBlocks against a completed snapshot, and cannot clean up — ec2:DeleteSnapshot refuses the same id. The individual operations look healthy while the end-to-end feature is unusable.
Fix: the snapshot state shared between the ebs and ec2 service crates — the EBS StartSnapshot handler must register the new snapshot in the same store the EC2 DescribeSnapshots/DeleteSnapshot handlers read (State `pending`, Description/Tags/VolumeSize/OwnerId as given), and the CompleteSnapshot handler must transition that same record to State `completed` with Progress `100%`.

=== Cause 2 of 2: ec2:DeleteSnapshot is an unimplemented scaffold stub answering NotImplemented, so an EBS caller cannot delete a snapshot at all — the deleted-but-well-formed ParentSnapshotId boundary is unreachable ===
AWS: DeleteSnapshot deletes a snapshot the account owns and answers 200 with an empty body; a snapshot id the account does not hold is refused `InvalidSnapshot.NotFound`. After the delete, EBS StartSnapshot with that id as ParentSnapshotId is refused with the modeled `ResourceNotFoundException` (Smithy com.amazonaws.ebs#StartSnapshot errors include ResourceNotFoundException, @httpError 404); the message's fixed text is "The snapshot '<snapshot-id>' does not exist." with the id taken from the request's ParentSnapshotId. ParentSnapshotId is constrained @pattern ^snap-[0-9a-f]+$, @length 1..64, so a fabricated id can be refused as a ValidationException instead — deleting a real snapshot is the only way to reach the not-found boundary.
Emulator: `ec2.delete_snapshot(SnapshotId=...)` is refused with HTTP error code `NotImplemented` and message "operation DeleteSnapshot is scaffolded but not implemented in this emulator". The check raises `botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the DeleteSnapshot operation: ...` from inside the check body (not cleanup), so the ResourceNotFoundException assertion on StartSnapshot is never reached.
Why: no client can retire an EBS direct-API snapshot, snapshots accumulate without bound, and the entire not-found/deleted-parent class of EBS behaviour is unverifiable. Any caller that treats delete as part of its lifecycle sees a 501-class failure where AWS answers 200.
Fix: implement the EC2 DeleteSnapshot handler against the same shared snapshot state cause 1 names — remove the snapshot, answer 200 with an empty body, and refuse an unknown id with `InvalidSnapshot.NotFound`; a subsequently reused id must then be refused `ResourceNotFoundException` by the EBS StartSnapshot ParentSnapshotId resolution.
Traces: ebs.start-snapshot-nonexistent-parent-rejected (1 check id).
