# cloudformation: 4 net-new behavioral root causes — ActivateType refuses with the wrong error class, DeletionMode=FORCE_DELETE_STACK never converges, ListImports accepts a nonexistent export, and UpdateStack's not-found message uses DescribeStacks' template

> _Note: this issue was identified against the code base at commit `1aab6ad9a4dd8a2817d61de8022dab6fc1da2f9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack, ListImports, DeleteStack, ActivateType

## Description
Four net-new behavioral root causes in the cloudformation service, clustered from the five failing checks in this replay that the report left unattributed (no ALREADY FILED, no OWNED by). Each cause below must be closed before this issue is submitted; the checks naming each cause are listed under its own Traces line.

Cause 1 of 4: ActivateType refuses a never-published public extension with ValidationError instead of CloudFormation's registry error.
AWS: ActivateType takes PublicTypeArn (Smithy: ThirdPartyTypeArn, @length 0..1024, @pattern ^arn:aws[A-Za-z0-9-]{0,64}:cloudformation:[A-Za-z0-9-]{1,64}::type/.+/[0-9a-zA-Z]{12,40}/.+$) and models exactly two errors — CFNRegistryException (HTTP 400, 'An error occurred during a CloudFormation registry operation.') and TypeNotFoundException (HTTP 404). For a PublicTypeArn that names an extension the public registry never published, AWS answers HTTP 400 with error code CFNRegistryException and the message 'TypeName is invalid' (recorded behavior; the message is fixed text with no variable part). It does NOT answer the generic ValidationError: the ARN is parsed and the refusal comes from the registry lookup, not from a syntax gate.
Emulator: the call is refused with error code 'ValidationError' — the request never reaches the operation's own logic, it is rejected by the modeled @pattern gate (the submitted ARN has three path segments after type/, which the model's pattern does not admit), and ActivateType itself is still a scaffold (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/activate_type.rs answers 501 NotImplemented from its handler), so no registry lookup exists to produce CFNRegistryException.
Why: a client that activates third-party extensions cannot distinguish 'this extension is not published' from 'your request was malformed'. Error-class-driven code (retry/report on CFNRegistryException, fall through on ValidationError) takes the wrong branch, and the sibling registry refusals (TypeNotFoundException 404) are equally unreachable.
Fix: the ActivateType handler and its refusal path (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/activate_type.rs) plus the type-registry state it must consult; the modeled pattern gate must not pre-empt the registry's own refusal for an ARN AWS itself parses. Related but NOT covering this: open issue 20261025T115133Z-cloudformation-registry-registerpublisher-accepts-a-non-marketplace-seller.md (the PUBLIC registry exposes no activatable THIRD_PARTY type) — it carries neither this check nor this error class.
Traces: cloudformation.activate-nonexistent-public-type-fails.

Cause 2 of 4: DeleteStack with DeletionMode=FORCE_DELETE_STACK is not honoured — the stack stays DELETE_FAILED forever.
AWS: Smithy DeleteStackInput.DeletionMode documents 'STANDARD - Use the standard behavior. Specifying this value is the same as not specifying this parameter.' and 'FORCE_DELETE_STACK - Delete the stack if it's stuck in a DELETE_FAILED state due to resource deletion failure.' So a stack parked in DELETE_FAILED because one resource refused to delete (here an AWS::S3::Bucket that is non-empty) reaches DELETE_COMPLETE when DeleteStack is re-issued with DeletionMode=FORCE_DELETE_STACK, the stuck resource is ABANDONED rather than deleted (it stays a fully usable bucket, still holding its object and still writable), and DescribeStacks by stack NAME afterwards is refused ValidationError with 'Stack with id <stack-name> does not exist' (fixed text around the requested name).
Emulator: the force delete is accepted but behaves exactly like the standard one — the stack re-enters StackStatus 'DELETE_FAILED' with StackStatusReason 'The following resource(s) failed to delete: [<LogicalResourceId>]. ' instead of DELETE_COMPLETE. The preceding beats of the same check pass (a plain DeleteStack of the non-empty-bucket stack does land in DELETE_FAILED, a plain retry records a fresh per-resource DELETE_FAILED event, and the object survives), so the gap is specifically that DeletionMode is read but never changes the teardown decision.
Why: a stack that is stuck is stuck permanently. FORCE_DELETE_STACK is the documented and only escape hatch for a DELETE_FAILED stack, so a client (or any teardown/cleanup automation, including CDK destroy and CI fixtures) can never retire such a stack, and the stack name remains taken.
Fix: the DeleteStack handler's deletion-mode handling and the stack teardown planner it drives (the delete path of the cloudformation provisioning engine) — under FORCE_DELETE_STACK a resource whose delete fails must be recorded as abandoned and the stack must still settle to DELETE_COMPLETE, after which by-name resolution must stop finding it.
Traces: cloudformation.deep-cloudformation-1-cfn-enforce-force-delete-stack-orphans-functional-bucket.

Cause 3 of 4: ListImports answers 200 with an empty list where AWS refuses — both the zero-importer and the never-existed export name.
AWS: ListImports (Smithy: input ExportName required, output Imports + NextToken, @paginated, NO modeled errors) does not treat an unknown export as an empty result. Real AWS distinguishes two refusals, both HTTP 400 ValidationError (a service-common error, not in the operation's modeled error list): for an export name that EXISTS but no stack imports, the message is "Export '<export-name>' is not imported by any stack."; for an export name that was never published at all, it is "Export '<export-name>' does not exist.". In both messages everything outside the quoted name is fixed text and the quoted value is the ExportName from the request.
Emulator: both calls SUCCEED. The handler (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/list_imports.rs, handle(), the comment at the importing_stacks() call: 'This operation models NO error, so an export name nothing publishes and one nothing imports are both the empty list rather than a refusal') returns HTTP 200 with Imports: [] in both cases, so the check's first assertion ('expected ListImports to raise, it returned normally') fails before the positive control is reached.
Why: the documented workflow for retiring or editing an export is 'call ListImports first to see who uses it'. A client cannot tell a typo'd/absent export from a live export with no importers — both read as 'safe to change' — and any code that branches on the ValidationError refusal never takes that branch. Note the already-FIXED issue 20261026T000642Z-cloudformation-3-net-new-root-causes-the-stackset.md made ListImports reflect a live Fn::ImportValue (that part now works: the operation is implemented, it is no longer the stub open issue 20261025T133035Z-cloudformation-listimports-stub.md describes); the refusal taxonomy for unknown/unimported export names is what remains, and this check fails on an ACCEPTANCE, not on a refusal of that fix.
Fix: the ListImports handler's lookup result handling in services/service-com-amazonaws-cloudformation-cloudformation/src/ops/list_imports.rs — it needs the export index (does this export exist at all?) in addition to the importer set, and must raise the two distinct ValidationError messages instead of returning an empty page.
Traces: cloudformation.list-imports-nonexistent-export-rejected.

Cause 4 of 4: UpdateStack's stack-not-found refusal carries DescribeStacks' message template instead of UpdateStack's.
AWS: UpdateStack on a stack that does not exist (deleted, or never created) is refused HTTP 400 ValidationError with the message 'Stack [<stack-name>] does not exist' — the stack name the request named appears in SQUARE BRACKETS. This is UpdateStack's own template and it differs from the DescribeStacks template 'Stack with id <stack-name> does not exist', which the same checks assert and which the emulator gets right. UpdateTerminationProtection uses the same bracketed template ('Stack [<stack-name>] does not exist'), as the second check's later assertion records. In each message the only variable part is the caller-supplied StackName; the rest is fixed text. Smithy: UpdateStack models only InsufficientCapabilitiesException and TokenAlreadyExistsException, so this refusal rides the service-common ValidationError.
Emulator: both checks get ('ValidationError', 'Stack with id <stack-name> does not exist') from UpdateStack. The handler builds its refusal from the shared DescribeStacks-shaped helper: services/service-com-amazonaws-cloudformation-cloudformation/src/ops/update_stack.rs, handle(), the not_found closure at ~line 405 calls crate::state::stack_does_not_exist(&input.stack_name) for both the unresolvable name and the resolved-but-not-live stack.
Why: the message is part of the refusal contract. Clients and CLIs match on it to decide 'create instead of update' or to treat a teardown as already done; a wrongly templated message makes those matches fail, and it also hides which API refused when both appear in one log.
Fix: UpdateStack's not-found refusal path (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/update_stack.rs) must use the bracketed per-operation template rather than the shared crate::state::stack_does_not_exist() helper, and UpdateTerminationProtection must use the same bracketed form. Related but NOT covering these checks: open issue 20261025T015306Z-cloudformation-refusal-taxonomy-diverges-wrong-not-found-validation.md records wrong not-found message templates generally but carries neither of these two checks' replay keys nor the UpdateStack template.
Traces: cloudformation.stack-deploys-real-queue, cloudformation.termination-protection-blocks-delete.
