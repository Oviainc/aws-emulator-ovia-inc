# apigateway__dynamodb__lambda__s3__xray: the traced REST API stage -> Lambda -> DynamoDB/S3 trace tree is never observable — the check runs out the harness budget with no trace ever produced (1 cause)

> _Note: this issue was identified against the code base at commit `5d5ee4285f9d2aaa876a013aeae04fab091110e5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetTraces

## Description
Cause 1 of 1: the whole producer-to-X-Ray path for an API-Gateway-fronted Lambda is unobservable — the distributed-trace shape check never reaches a single assertion and is killed at the 60 s harness cap. Failing check: apigateway__dynamodb__lambda__s3__xray.apigw-lambda-ddb-s3-trace-tree-shape.

AWS: the query side is modeled — Smithy xray BatchGetTraces POST /Traces -> BatchGetTracesResult{Traces[], UnprocessedTraceIds[]}, HTTP 200, errors InvalidRequestException (400) / ThrottledException (429); GetTraceSummaries POST /TraceSummaries -> TraceSummaryList, HTTP 200, same two errors. The producer side is recorded behavior only (no Smithy shape describes it): a GET on the invoke URL of a REST API stage whose tracingEnabled=true answers HTTP 200 with the AWS_PROXY integration's response, and the edge stamps the invocation environment's _X_AMZN_TRACE_ID with Root=1-<8 hex>-<24 hex>;Parent=<16 hex>;Sampled=1 (fixed text 'Root=', 'Parent=', 'Sampled=' and the 1-<epoch-hex>-<random-hex> id shape are the requirement; the particular id/parent digits are per-run values). Reading that Root back through BatchGetTraces returns exactly one trace under that id, whose flattened documents form ONE closed tree (a single parentless document, n-1 parent edges, acyclic, no dangling parent_id) spanning three independent producers — origin AWS::ApiGateway::Stage as the root, named <api-id>/<stage-name>, carrying a nested namespace="aws" subsegment named Lambda whose aws.function_name is the integration target; origin AWS::Lambda; and origin AWS::Lambda::Function whose parent_id is the AWS::Lambda segment id — plus two nodes X-Ray SYNTHESISES itself, AWS::DynamoDB::Table and AWS::S3::Bucket, each with inferred:true and hanging from the handler's own aws-namespace subsegment for that call. Subsegment documents the handler sends by UDP to AWS_XRAY_DAEMON_ADDRESS are accepted and stored nested inside the segment their parent_id names, preserving namespace="aws", aws.operation, aws.table_name / aws.bucket_name and the aws.request_id the DynamoDB/S3 call actually returned. Child start/end times nest inside their parent's. The negative arm: the same request through a stage with tracingEnabled=false yields NO AWS::ApiGateway::Stage segment while the Lambda segments (and the handler's own subsegments) still appear, with AWS::Lambda as the parentless root.

Emulator: no assertion in the check is ever reached — the replay reports only 'Error: Check timed out after 60.0s'. Nothing in the sequence (create table, create bucket, create a TracingConfig Mode=Active python function, deploy an AWS_PROXY REST API to a tracingEnabled stage, GET the stage, then poll BatchGetTraces for the trace) returns a usable result within the budget. The check's own waits are longer than the cap (the stage GET is a 90 s bounded retry that only loops while the response is 403/429/5xx or does not answer at all, and the trace poll is 240 s and exits only once the five origins are present), so both a stage that neither serves 200 nor refuses outright and a trace store that never receives a document present identically as this hang. No AWS::ApiGateway::Stage / AWS::Lambda / AWS::Lambda::Function segment, no daemon-delivered subsegment and no inferred AWS::DynamoDB::Table / AWS::S3::Bucket node is ever observed, and the tracingEnabled=false control arm is never executed.

Why: a client cannot observe its own application's distributed traces at all. Every AWS-native tracing workflow on an API-fronted Lambda — trace-tree shape, edge-to-service linkage through the stage's nested Lambda subsegment, downstream-resource inference for DynamoDB and S3, and the per-stage tracing toggle — is unavailable, and it fails as an indefinite hang rather than as a status/error code a client can handle, so callers and the suite alike get no diagnosis. Because the hang consumes the whole budget, every narrower divergence behind it is ungradeable too.

Fix: belongs in two components. (a) The execute-api stage data plane — the front-door routing for a deployed REST API stage's invoke URL and its AWS_PROXY integration dispatch — must answer the stage GET with the integration's 200 and must mint/propagate the X-Amzn-Trace-Id context into the invocation environment. (b) The X-Ray segment-ingestion and trace-assembly state must accept segments from the API Gateway edge and the Lambda service, accept the handler's UDP daemon datagrams, stitch documents from several producers into one trace by trace_id/parent_id, synthesise the inferred downstream resource nodes, and suppress the edge segment when the stage has tracingEnabled=false, so that BatchGetTraces/GetTraceSummaries can serve the assembled tree. ## Steps to Reproduce
1. Create a PAY_PER_REQUEST DynamoDB table with an S hash key 'pk', and an S3 bucket.
2. Create a python3.12 Lambda with TracingConfig={'Mode':'Active'} on an execution role granting xray:PutTraceSegments, xray:PutTelemetryRecords, dynamodb:PutItem on the table and s3:PutObject on the bucket. The handler echoes os.environ['_X_AMZN_TRACE_ID'], does one PutItem and one PutObject, and sends one namespace="aws" subsegment per call by UDP to AWS_XRAY_DAEMON_ADDRESS with trace_id=Root, parent_id=Parent, caller-chosen subsegment ids, and the request_id each call returned.
3. Create a REST API with GET /x wired to an AWS_PROXY integration on that function, add the lambda:InvokeFunction permission for apigateway.amazonaws.com, create_deployment to stage 'traced' and update_stage with /tracingEnabled=true; deploy a second stage 'untraced' leaving tracingEnabled false.
4. GET https://<api-id>.execute-api.<region>.amazonaws.com/traced/x?ddb_sub_id=<16hex>&s3_sub_id=<16hex>&k=traced-probe. Expect HTTP 200 and a well-formed Root=...;Parent=...;Sampled=1 in the echoed header.

6. Repeat the GET through the 'untraced' stage and assert no AWS::ApiGateway::Stage origin while the Lambda segments and the handler subsegment are still there.
7. Observe that the sequence never yields a trace: the check runs to the 60 s harness cap with no assertion reached.
