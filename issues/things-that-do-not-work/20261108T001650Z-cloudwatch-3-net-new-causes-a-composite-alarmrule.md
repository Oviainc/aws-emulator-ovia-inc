# cloudwatch: 3 net-new causes — a composite AlarmRule's AND combinator is never evaluated, ActionsSuppressedBy never reaches ExtensionPeriod, and a rendered metric widget ignores the metric store

> _Note: this issue was identified against the code base at commit `f42419e01630977583bc09726b6f41b0d8951344`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

PutCompositeAlarm

## Description
Three independent net-new root causes in the cloudwatch alarm-evaluation and widget-render paths. None of the failing checks below was marked ALREADY FILED or OWNED by the replay report. THREE causes must be closed before submitting.

Prior work that does NOT carry these failures: 20261031T235853Z-cloudwatch-7-net-new-root-causes-associatedatasetkmskey-validates.md (its Cause 3) listed all three composite-alarm checks with replay keys of the form `<check>|_poll*#NN|Timeout`, because at that time the composite never left INSUFFICIENT_DATA and nothing was ever observed. === Cause 1 of 3: a composite AlarmRule combining two children with AND never evaluates to ALARM ===
Failing check ids: cloudwatch.composite-alarm-and-rule-requires-all-children, cloudwatch.composite-alarm-boolean-and-logic.
AWS: Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/com-amazonaws-cloudwatch-graniteserviceversion20100801.json) — PutCompositeAlarm input AlarmRule is @required, @length 1-10240, documented as "An expression that specifies which other alarms are to be evaluated to determine this composite alarm's state... You can use operators (AND, OR and NOT) to combine multiple functions in a single expression", with the worked example "ALARM(CPUUtilizationTooHigh) AND ALARM(DiskReadOpsTooHigh) specifies that the composite alarm goes into ALARM state only if both CPUUtilizationTooHigh and DiskReadOpsTooHigh alarms are in ALARM state"; DescribeAlarms returns composite alarms in the CompositeAlarms output list (and only when AlarmTypes names CompositeAlarm). Recorded behavior: the composite's StateValue is re-derived server-side from the children's CURRENT states on every child transition — with one of two AND-ed children in ALARM it stays out of ALARM, and once the last referenced child enters ALARM it transitions to ALARM within the evaluation delay. No SetAlarmState is ever issued on the composite itself.
Emulator: the composite is visible via DescribeAlarms(AlarmTypes=["CompositeAlarm"]) and settles on OK (both checks' earlier legs now pass, including the negative leg that one tripped child must not trip it), but driving BOTH children to ALARM with SetAlarmState leaves it at OK for the whole polling window — StateValue never changes. A single-function rule DOES work (cloudwatch.composite-alarm-actions-suppressed-by-alarm, Cause 2 below, got its ALARM("child") composite to ALARM), so what is absent is the boolean combinator, not evaluation as such. Hypothesis: the AlarmRule expression evaluator handles only a bare ALARM(<name>) term and yields a non-ALARM result for any expression containing AND/OR/NOT.
Why: composite alarms exist to AND several noisy conditions into one page. A composite that can never reach ALARM never runs its AlarmActions, so an emulator-based test of a de-noised alarm topology passes while the real topology would have paged, and "nothing is wrong" is indistinguishable from "the rule was never evaluated".
Fix: the composite-alarm evaluator in the alarm state engine — parse and evaluate the full AlarmRule grammar (ALARM/OK/INSUFFICIENT_DATA functions, TRUE/FALSE, AND/OR/NOT, parentheses) against the children's current states on creation and on every child transition, and write the derived StateValue the DescribeAlarms CompositeAlarms serializer reads.
Traces: cloudwatch.composite-alarm-and-rule-requires-all-children (`AssertionError: composite did not transition to ALARM once both children tripped: OK`), cloudwatch.composite-alarm-boolean-and-logic (`AssertionError: composite AND-rule never became ALARM once both children alarmed, last=OK`).

=== Cause 2 of 3: ActionsSuppressedBy never reports ExtensionPeriod once the suppressor leaves ALARM ===
Failing check id: cloudwatch.composite-alarm-actions-suppressed-by-alarm.
AWS: Smithy — PutCompositeAlarm models ActionsSuppressor (an alarm ARN), ActionsSuppressorWaitPeriod and ActionsSuppressorExtensionPeriod (SuppressorPeriod, seconds); CompositeAlarm$ActionsSuppressedBy is documented: "When the value is ALARM, it means that the actions are suppressed because the suppressor alarm is in ALARM. When the value is WaitPeriod, it means that the actions are suppressed because the composite alarm is waiting for the suppressor alarm to go into the ALARM state... When the value is ExtensionPeriod, it means that the actions are suppressed because the composite alarm is waiting after the suppressor alarm went out of the ALARM state. The maximum waiting time is as specified in ActionsSuppressorExtensionPeriod. After this time, the composite alarm performs its actions." So suppression is a THREE-phase state machine, not a boolean: while the suppressor is in ALARM the composite reports ActionsSuppressedBy == "Alarm"; for ActionsSuppressorExtensionPeriod seconds after the suppressor leaves ALARM it reports "ExtensionPeriod" while its own StateValue stays ALARM; only then does the field stop being reported.
Emulator: the first phase is now right — with the suppressor in ALARM, DescribeAlarms reports StateValue ALARM and ActionsSuppressedBy "Alarm". After SetAlarmState(suppressor, OK) the field is simply gone: the check polls for ActionsSuppressedBy == "ExtensionPeriod" for the whole window and reads None. The extension phase is never rendered, i.e. suppression is modelled as a boolean read off the suppressor's current state rather than a timed machine keyed on ActionsSuppressorExtensionPeriod.
Why: the extension period is the whole point of the suppressor contract — it is what stops a composite from paging during the settle window after a maintenance/deployment suppressor clears. A client reading ActionsSuppressedBy cannot tell "actions are being withheld for the configured extension window" from "actions are live again", and any alarm-action gating logic built on that field releases notifications early.
Fix: the ActionsSuppressor gate in the composite-alarm evaluator — track the suppressor's transition out of ALARM, report ActionsSuppressedBy = ExtensionPeriod (and WaitPeriod on the opposite edge) for the configured period while actions stay withheld, then clear the field; the DescribeAlarms CompositeAlarms serializer must emit the field only while a phase is active.
Traces: cloudwatch.composite-alarm-actions-suppressed-by-alarm (`AssertionError: composite alarm never reported ActionsSuppressedBy=='ExtensionPeriod' after the suppressor left ALARM, got None`).

=== Cause 3 of 3: GetMetricWidgetImage renders independently of the metric data in the requested window ===
Failing check ids: cloudwatch.get-metric-widget-image-renders-for-valid-metric, cloudwatch.dashboard-widget-image-render-freshness-window.
AWS: Smithy — GetMetricWidgetImage input MetricWidget @required ("A JSON string that defines the bitmap graph to be retrieved", which "includes the metrics to include in the graph, statistics, annotations, title, axis limits, and so on"), output MetricWidgetImage is a blob, and the operation models NO errors, so the only observable is the bytes. Recorded behavior: the render reads CURRENT data — the same widget document over a fixed absolute window with unchanged data returns the SAME bytes, and the same document re-rendered after a datapoint is written into that window returns DIFFERENT bytes (materially larger once a previously empty series has data). The requirement is that dependence, never a byte count.
Emulator: both renders answer 200 with PNG-signed bytes and repeat renders over unchanged data are stable (that half is correct), but writing a datapoint into the queried namespace/metric inside the rendered window changes nothing: every subsequent render of the identical document returns byte-identical output for the full poll window (90 s and 120 s respectively; last renders 16409 and 10482 bytes). PutMetricData is accepted, so the datapoint exists for the read APIs; the render never consults it.
Why: for this operation the image IS the answer — it is embedded in alarm notifications, chat messages, tickets and reports. A chart that never reflects the data means an operator looking at the graph attached to a firing alarm sees a series that is empty (or stale) regardless of what the metric did, and a caller cannot distinguish a rendered chart from a stub.
Fix: the image serializer in the GetMetricWidgetImage handler must read the metric store on the same terms as the metric read path (namespace, metric name, dimensions, stat, period, start/end resolved from the widget document) and plot the datapoints found in the requested window, so the bytes vary with the data as well as with the document.
Traces: cloudwatch.get-metric-widget-image-renders-for-valid-metric (`AssertionError: rendered widget growing once WidgetMetric has a published datapoint not observed within 120s; last saw 10482 bytes`), cloudwatch.dashboard-widget-image-render-freshness-window (`AssertionError: condition not met within 90s (last render was 16409 bytes)`).
