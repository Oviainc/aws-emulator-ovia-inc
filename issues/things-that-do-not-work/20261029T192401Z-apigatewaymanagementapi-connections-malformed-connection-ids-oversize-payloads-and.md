# ApiGatewayManagementApi @connections: malformed connection ids, oversize payloads and undeployed stages are all answered GoneException/the wrong envelope, and the WEBSOCKET upgrade still answers 404 (4 causes, 12 checks)

> _Note: this issue was identified against the code base at commit `c8d80ea15f1454d07f388eb2b932b3a5430349f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PostToConnection

## Description
FOUR net-new root causes in the ApiGatewayManagementApi (@connections) data plane. They are numbered below and each carries its own failing check ids; all four must be closed before this issue is submitted.

=== Cause 1 of 4: a malformed ConnectionId is not refused — it reaches the connection store and is answered GoneException instead of BadRequestException (400) ===
AWS: Smithy (ApiGatewayManagementApi 2018-11-29, restJson1, sigv4/execute-api) models GetConnection GET /@connections/{ConnectionId}, PostToConnection POST /@connections/{ConnectionId} and DeleteConnection DELETE /@connections/{ConnectionId} (code 204); ConnectionId is an @httpLabel @required __string with NO pattern or length constraint, and BadRequestException is NOT in the model (service common_errors are ForbiddenException, GoneException, LimitExceededException) — so the refusal itself is recorded behavior only. Recorded: an id that is not the shape API Gateway mints (base64 of 11 bytes) is refused on all three operations with HTTP 400, error code BadRequestException and the message "Invalid connectionId: <ConnectionId>" — the fixed text is "Invalid connectionId: " and the variable part is the ConnectionId exactly as the request sent it — and the refusal happens BEFORE the connection store is consulted. The recorded malformation classes are: a single character, a string with characters outside the base64 alphabet, unpadded base64, and an overlong (200-character) id. A well-formed but unknown id instead reaches the store and is refused HTTP 410 GoneException with an EMPTY message.
Emulator: all four malformed ids are answered ('GoneException', '') on GetConnection — i.e. the id was handed to the connection store and missed there, so no shape validation exists at all. Replay detail: "GetConnection returned {'single-char': ('GoneException', ''), 'not-base64': ('GoneException', ''), 'unpadded': ('GoneException', ''), 'overlong': ('GoneException', '')} for malformed connection ids".
Why: a client cannot distinguish "I built the id wrong" (400, retry is pointless, fix the code) from "the client has gone away" (410, the documented signal to drop the connection from your own store). Applications that prune their connection table on GoneException will silently delete live connections whenever they pass a corrupted id, and a validation bug in the caller is invisible on this emulator.
Fix: the shared @connections request validation in front of the three handlers (GetConnection/PostToConnection/DeleteConnection), which must validate the ConnectionId path label's shape and return a 400 BadRequestException envelope before any connection lookup.
Traces: apigatewaymanagementapi.agwmgmt-malformed-connection-id-rejected.

=== Cause 2 of 4: PostToConnection's oversize-payload refusal returns the modelled PayloadTooLargeException envelope with an emulator-authored message instead of AWS's bare HTTP 413 ===
AWS: Smithy models PostToConnection's Data member as an @httpPayload blob with @length min 0 / max 131072 and declares the error PayloadTooLargeException (@httpError 413, single member Message with jsonName "message", doc "The data has exceeded the maximum size allowed."). Recorded behavior, which differs from the model: real AWS does NOT serialize that modelled error for an oversize payload — one byte over the ceiling is answered with a bare HTTP 413 carrying NO x-amzn-errortype header and no error code/message body, which botocore surfaces as Error.Code '413' with no message. The refusal is also ORDERED ahead of everything else: at exactly 131072 bytes the same unknown connection id still answers 410 GoneException (the size is accepted and the lookup is what fails), and at 131073 bytes a MALFORMED connection id — which would otherwise be a 400 BadRequestException per Cause 1 — is likewise answered 413, so the payload gate precedes both id validation and connection resolution.
Emulator: the 131073-byte PostToConnection answers error Code 'PayloadTooLargeException' with the message 'Data payload of 131073 bytes exceeds the maximum of 131072 bytes' — both the typed error envelope (x-amzn-errortype / modelled shape) and that message text are things AWS does not emit here; the message is emulator-authored wording with the byte counts interpolated.
Why: a client that keys retry/abort logic on the absence of an error type (or on the literal Code '413' botocore produces for a typeless 413) takes the wrong branch, and generated SDK code that catches PayloadTooLargeException is exercised on the emulator but never fires against AWS. Conversely, an SDK user who writes against the emulator's message will never see it in production.
Fix: PostToConnection's payload-size gate and its error serializer — emit a bare 413 response with no x-amzn-errortype header and no error body, and run the gate before ConnectionId validation and before the connection lookup.
Traces: apigatewaymanagementapi.agwmgmt-post-oversize-payload-rejected-before-lookup.

=== Cause 3 of 4: the management endpoint's STAGE segment is ignored — an undeployed stage reaches the connection store and answers GoneException instead of ForbiddenException (403) ===
AWS: the @connections endpoint is always the per-API https://<api-id>.execute-api.<region>.amazonaws.com/<stage>, so the stage is part of the request path; stage routing itself is the execute-api data plane and is not a modelled operation, so this is recorded behavior. The modelled surface does carry the error AWS uses: ForbiddenException, @httpError 403, errorKind client, no members, doc "The caller is not authorized to invoke this operation." Recorded: addressing a stage name that is NOT a deployed stage of that API answers HTTP 403 ForbiddenException (message 'Forbidden') on GetConnection, PostToConnection and DeleteConnection alike, WITHOUT consulting the connection store, while the identical request against the same API's deployed stage answers 410 GoneException for an unknown id. Addressing an undeployed stage must also create nothing — the API still reports exactly the stages it was given.
Emulator: all three operations on the undeployed-stage endpoint answer GoneException. Replay detail: "the undeployed-stage endpoint returned {'GetConnection': 'GoneException', 'PostToConnection': 'GoneException', 'DeleteConnection': 'GoneException'}" — the stage segment was ignored and the request reached the connection store anyway.
Why: the endpoint's stage is the only thing that scopes a @connections call to a deployment. Ignoring it makes the emulator over-permissive: a client pointed at a stage that was never deployed (a typo, a stale stage name, a stage deleted under it) is told the connection is gone rather than that it is not authorized to invoke that endpoint, so misconfiguration is indistinguishable from a closed socket and a per-stage authorization boundary that exists on AWS does not exist here.
Fix: the @connections request router / endpoint resolution — resolve {api-id, stage} from the request path against the API's deployed stages and return 403 ForbiddenException before dispatching to the connection store.
Traces: apigatewaymanagementapi.agwmgmt-undeployed-stage-endpoint-forbidden.

=== Cause 4 of 4: the client WebSocket upgrade on a deployed apigatewayv2 WEBSOCKET stage answers HTTP/1.1 404 Not Found, so no connection ever exists for these nine checks ===
AWS: recorded behavior only for the handshake (the opening upgrade is the execute-api data plane, not a modelled operation). The modelled surface it feeds is: GetConnection -> GetConnectionResponse{ConnectedAt (iso8601 date-time, jsonName connectedAt), LastActiveAt (iso8601, lastActiveAt), Identity{SourceIp, UserAgent, both required}}; PostToConnection Data blob @length 0..131072; DeleteConnection code 204; common errors ForbiddenException(403)/GoneException(410)/LimitExceededException. Recorded: a client RFC 6455 opening handshake (GET /<stage> with Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key, Sec-WebSocket-Version: 13) against the deployed stage is answered HTTP/1.1 101 Switching Protocols with a Sec-WebSocket-Accept derived from the client key; $connect runs and the service mints the connection id that @connections then addresses.
Emulator: the upgrade is answered with the status line b'HTTP/1.1 404 Not Found' — no 101, no Sec-WebSocket-Accept, no socket. Six checks raise ConnectionError on the first non-101 ("websocket handshake failed: b'HTTP/1.1 404 Not Found'"); three more poll the same upgrade for a 101 (120 s poll) and are cut by the 60 s harness cap, reporting "Check timed out after 60.0s". The control plane up to the handshake (sts, iam role, lambda create/Active, create_api/create_integration/create_route/create_deployment/create_stage) completes, so the divergence is isolated to the upgrade.
Why: with no socket, no connection id is ever minted, so the entire server-push surface is dead: GetConnection's ConnectedAt/LastActiveAt ordering and Identity{SourceIp,UserAgent}, text/binary/empty payload delivery, >32 KB payload fragmentation across RFC 6455 continuation frames, the 128 KB boundary refusal on a LIVE connection, the get/post/delete lifecycle, and the cross-API id isolation are all unobservable. A developer sees a plain 404 on wss:// and cannot tell a missing data plane from a misconfigured stage.
Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer — recognise an upgrade request on a deployed WEBSOCKET-protocol API's stage path, complete the handshake (101 + Sec-WebSocket-Accept) instead of falling through to the generic 404 path, mint a connection id, dispatch $connect/$disconnect/route-selection routes, and register the connection in the store the @connections handlers read. This is a capability gap, not an error-shape bug.
Related: the open issue 20261023T223918Z-apigatewaymanagementapi-is-untestable-end-to-end-the-websocket.md describes the same 404 for a DIFFERENT set of 12 checks and does not carry the replay keys of the nine listed here; fixing it should fix these too, but they are not covered by it. The apigatewayv2-side issues 20261025T023548Z-apigatewayv2-websocket-stage-never-completes-the-rfc-6455.md and 20261029T023500Z-...-the-rfc-6455-upgrade-to-a-deployed.md cover the apigatewayv2 service token, not these apigatewaymanagementapi checks.
Traces: apigatewaymanagementapi.get-connection-last-active-at-not-before-connected-at, apigatewaymanagementapi.get-connection-returns-identity-metadata, apigatewaymanagementapi.payload-too-large-rejected-at-boundary, apigatewaymanagementapi.post-to-connection-binary-payload-roundtrip, apigatewaymanagementapi.post-to-connection-delivers-text-payload, apigatewaymanagementapi.post-to-connection-empty-payload-delivers (ConnectionError on the 404), apigatewaymanagementapi.agwmgmt-cross-api-connection-id-rejected, apigatewaymanagementapi.agwmgmt-live-connection-get-post-delete-lifecycle, apigatewaymanagementapi.post-to-connection-fragments-large-payload-across-frames (same step, polled, cut by the 60 s cap).
