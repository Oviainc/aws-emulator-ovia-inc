# Transfer connector plane: UpdateConnector replaces SftpConfig wholesale, so pinning the observed host key erases UserSecretId and TestConnection never reaches OK; and the OnUpload-workflow callback flow still never settles (2 causes)

> _Note: this issue was identified against the code base at commit `8f4dc4c9e0f22e0a535198a62ecfcb2392866dea`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateConnector

## Description
TWO distinct root causes in the transfer emulator, grounded in the two behavioral checks listed in trace_ids. Both must be closed before this issue is submitted.

These are the only two transfer failures this replay marked neither 'ALREADY FILED' nor 'OWNED by'. Related OPEN issues that do NOT carry these checks' current replay keys: '20261102T102840Z-transfer-connector-plane-never-becomes-usable-testconnection-reports.md' (its cause 1 described TestConnection as unconditionally ERROR with no host key — that is no longer what happens: TestConnection now resolves the emulated endpoint and reports a HostKey, and the connector flows it covered, transfer.e2e-server-user-file-transfer-flow and transfer.file-transfer-result-status-visibility-ttl, now PASS; what remains on this path is the net-new UpdateConnector defect in cause 1 below) and '20261029T193150Z-transfer-the-sftp-connector-data-plane-never-settles-the.md' (its single cause covers two checks that now pass). If either fix lands first, re-replay the two checks named here before closing this one.

=== Cause 1 of 2: UpdateConnector REPLACES the stored SftpConfig structure instead of updating the members the request names, so the documented 'pin the host key TestConnection observed' update silently erases UserSecretId and the connector can never be brought into service ===
AWS: Smithy UpdateConnector input {ConnectorId @required, Url, As2Config, AccessRole, LoggingRole, SftpConfig (SftpConnectorConfig), SecurityPolicyName, EgressConfig, IpAddressType} -> {ConnectorId @required}; SftpConnectorConfig members UserSecretId (SecretId, len 1..2048), TrustedHostKeys (list 0..10), MaxConcurrentConnections (default 1), OrderedUserSecretVersionStages. The model documents the exact provisioning sequence this check performs, on SftpConnectorConfig.TrustedHostKeys: "TrustedHostKeys is optional for CreateConnector. If not provided, you can use TestConnection to retrieve the server host key during the initial connection attempt, and subsequently update the connector with the observed host key." So an UpdateConnector that carries SftpConfig={TrustedHostKeys:[<key TestConnection reported>]} leaves the connector's credentials in place and a following TestConnection returns Status 'OK' with the success StatusMessage. Recorded behavior: after that pin-the-key update, TestConnection answers HTTP 200 with Status='OK'; the connector's UserSecretId is still the one CreateConnector was given.
Emulator: services/service-com-amazonaws-transfer-transferservice/src/ops/update_connector.rs builds next_sftp_config as input.sftp_config.clone().map(resolve_sftp_connector_config).or_else(|| stored.sftp_config.clone()) and assigns it to stored.sftp_config — i.e. ANY request that names SftpConfig at all replaces the whole stored structure, dropping every member the request did not repeat. After the documented TrustedHostKeys-only pin, the connector holds no UserSecretId, so crate::state::sftp_configuration_defect short-circuits the probe and TestConnection answers HTTP 200 Status='ERROR' with StatusMessage "The connector configuration names no UserSecretId, so the SFTP user's credentials cannot be read. Verify that the secret exists and is formatted correctly." (that whole sentence is emulator-authored fixed text; no part of it comes from the request). Status 'OK' is then unreachable for the rest of the connector's life, and every downstream connector operation that needs a session (StartDirectoryListing, StartRemoteMove, StartRemoteDelete, StartFileTransfer) has no session to run over.
Why: a client that follows the AWS-documented bootstrap — create the connector without TrustedHostKeys, call TestConnection to learn the server's host key, UpdateConnector to pin it, re-probe until Status 'OK' — destroys its own connector with the second step. The client sees a 200 OK from UpdateConnector and then a permanent ERROR verdict whose message blames a configuration it never changed, so the only way to use a connector here is to re-send members the request never needed to name. Credentials also vanish from a connector merely because a caller updated its trusted keys, which on real AWS is a safe, additive operation.
Fix: the UpdateConnector handler (services/service-com-amazonaws-transfer-transferservice/src/ops/update_connector.rs) must merge SftpConfig MEMBER-WISE against the stored configuration — each member the request names replaces that member, each member it omits keeps its stored value — the same way it already treats EgressConfig via crate::state::merge_connector_egress_config, and only then apply the cross-member validation. The same member-wise rule belongs on As2Config.
Traces: transfer.e2e-connector-remote-directory-flow (assertion in _establish_trust_and_verify_connection: "TestConnection did not succeed after pinning the host key", with the ERROR/StatusMessage pair quoted above and SftpConnectionDetails.HostKey present).

=== Cause 2 of 2: an SFTP upload that arrives through a connector still produces no observable OnUpload workflow execution, so the CUSTOM-step callback token never appears and the whole managed-workflow flow stalls ===
AWS: Smithy CreateWorkflow(Steps, Type CUSTOM with CustomStepDetails{Name, Target, TimeoutSeconds, SourceFileLocation}); UpdateServer(WorkflowDetails.OnUpload=[{WorkflowId, ExecutionRole}]); StartFileTransfer(ConnectorId @required, SendFilePaths @length 1..10, RemoteDirectoryPath) -> TransferId @required; ListFileTransferResults -> FileTransferResults @required with StatusCode; SendWorkflowStepState(WorkflowId, ExecutionId, Token, Status @required) -> empty, errors AccessDeniedException 403, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429. Recorded behavior: a file uploaded to a server whose WorkflowDetails.OnUpload names the workflow starts one execution, the CUSTOM step's Lambda Target is invoked with serviceMetadata.executionDetails.{workflowId, executionId} and a callback token, the in-order SendWorkflowStepState(Status='SUCCESS') succeeds, and REPLAYING that same token is refused with HTTP 404 ResourceNotFoundException whose message is exactly 'Unknown execution' (fixed text, no request-derived part), leaving DescribeExecution's answer for that ExecutionId unchanged.
Emulator: the check is killed at the suite's 60s per-check budget with NO assertion raised, i.e. it stalls inside one of its poll loops, each of which polls emulator-served state only (DescribeServer.State=='ONLINE'; TestConnection.SftpConnectionDetails.HostKey then Status=='OK'; the first ListFileTransferResults entry reaching COMPLETED/FAILED; then the tokens/<token>.json marker the step's Lambda writes to S3, then its .done sibling). Hypothesis (neither the model nor the replay output names the stalled call, because no exception was produced): the upload path does not carry a delivered file into an OnUpload execution with an invoked CUSTOM step — crate::state::connector_delivery documents that behavior as the intended producer of the callback, so the marker object the check waits on is never written and the replayed-token refusal is never reached.
Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback token) sees its workflow never run on upload and hangs instead of failing; the at-most-once guarantee of a callback token — the property that makes a token safe to retry — cannot be exercised at all, so retry/idempotency logic written against real Transfer Family is untestable here. A stall is also strictly worse than an error: the caller cannot tell 'not yet' from 'never'.
Fix: the server upload path plus the workflow/execution state of the transfer crate (crate::state connector_delivery and the workflow-execution store, with the SendWorkflowStepState, DescribeExecution and ListExecutions handlers in services/service-com-amazonaws-transfer-transferservice/src/ops) must start one execution per attached OnUpload workflow when a file arrives through the server, invoke each CUSTOM step's Lambda Target with the documented event and its callback token, accept the in-order SendWorkflowStepState exactly once, and refuse a replay of the same token with the modeled 404 ResourceNotFoundException message 'Unknown execution' while leaving DescribeExecution's answer unchanged. Note that the replay refusal itself is already coded in send_workflow_step_state.rs; what is missing is an execution and token for it to act on.
Traces: transfer.workflow-step-state-out-of-order-rejected (Error: Check timed out after 60.0s, no assertion).
