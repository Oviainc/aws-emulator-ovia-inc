# CloudWatch Logs performs no IAM authorization: an assumed-role session reads, writes and lists log groups its identity policy implicitly or explicitly denies (1 cause)

> _Note: this issue was identified against the code base at commit `eb1ede2cbce186d0b7cae6d474f923ddb0f91b8a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FilterLogEvents

## Description
Cause 1 of 1: the CloudWatch Logs request path never evaluates the caller's identity-based policy, so every logs call from an assumed-role session is carried out regardless of what that session is allowed to do. All four failing checks assume one role whose only inline logs policy is an Allow of logs:DescribeLogGroups/FilterLogEvents/GetLogEvents on log-group:/aws/bedrock-agentcore/*, /aws/lambda/* and /aws/batch/*, plus an explicit Deny of logs:FilterLogEvents/GetLogEvents on log-group:/aws/vendedlogs/bedrock-agentcore/runtime/APPLICATION_LOGS/* and .../USAGE_LOGS/*. Each then issues a call that policy does not permit.

AWS: recorded behavior only — the CloudWatch Logs Smithy model does not enumerate the IAM refusal (FilterLogEvents, GetLogEvents and DescribeLogGroups model only InvalidParameterException/ResourceNotFoundException/ServiceUnavailableException; PutLogEvents adds DataAlreadyAccepted/InvalidSequenceToken/UnrecognizedClient), because authorization is enforced by the service in front of the modeled errors. The recordings show the request refused with error code AccessDeniedException and this message, whose fixed text is exactly as shown and whose variable parts all come from the request and account state:
  "User: <callerArn> is not authorized to perform: logs:<Action> on resource: <resourceArn> because no identity-based policy allows the logs:<Action> action" when no statement grants the action at all, and
  "User: <callerArn> is not authorized to perform: logs:<Action> on resource: <resourceArn> with an explicit deny in an identity-based policy" when a Deny statement matches.
<callerArn> is the caller's assumed-role ARN (arn:aws:sts::<account>:assumed-role/<roleName>/<sessionName>), <Action> the operation name, <resourceArn> the ARN the action authorizes against: the log-group ARN for FilterLogEvents, the log-group ARN plus ":log-stream:<logStreamName>" for GetLogEvents and PutLogEvents, and — because DescribeLogGroups names no group — the empty form "arn:aws:logs:<region>:<account>:log-group::log-stream:". The refusal is decided BEFORE existence, so a missing log stream inside a denied group is still AccessDeniedException, not ResourceNotFoundException. No state changes on a refused call.

Emulator: every one of these calls succeeds. FilterLogEvents on both explicitly denied vended groups answers HTTP 200 with {'events': [], 'searchedLogStreams': []}; PutLogEvents into the denied APPLICATION_LOGS stream answers HTTP 200 with a nextSequenceToken and actually stores the event; DescribeLogGroups answers HTTP 200 listing the matching groups for every prefix, including prefixes the role's resource-scoped Allow cannot cover; and GetLogEvents for a nonexistent stream in the denied group answers ResourceNotFoundException "The specified log stream does not exist." — the existence check runs where the authorization refusal belongs. The same session's allowed reads of the /aws/bedrock-agentcore/* runtime group succeed, so the sessions are live and the divergence is purely the missing authorization gate.

Why: a client cannot rely on CloudWatch Logs least privilege at all. A scoped session reads and writes log data an explicit Deny was written to protect (log data is exactly the material such a Deny exists to hide), a caller that distinguishes 403-class AccessDeniedException from ResourceNotFoundException takes the wrong branch, and any test of a logs permission boundary passes against the emulator and fails against AWS.

Fix: an identity-policy authorization check in the CloudWatch Logs service's request dispatch / handler entry, evaluating the signing principal's identity-based policies (Deny over Allow) against the operation's action and the ARN it authorizes against, emitting AccessDeniedException with the message templates above, and running BEFORE the handlers' existence lookups so a denied group masks a missing stream.

Traces: iam__logs__sts.team-session-vended-reads-denied-runtime-reads-allowed (FilterLogEvents/GetLogEvents, explicit deny), iam__logs__sts.team-session-cannot-write-vended-group-owner-can (PutLogEvents, implicit deny), iam__logs__sts.team-session-prefix-scoped-describe-log-groups-denied (DescribeLogGroups, implicit deny, empty resource clause), iam__logs__sts.team-session-denied-group-masks-missing-stream (GetLogEvents, authorization decided before existence). No open issue claims this: the open CloudWatch Logs issues cover query, delivery, transformer, export and validation paths, not identity authorization.

## Steps to Reproduce
1. Boot the emulator and replay the behavioral suite (service iam__logs__sts).
2. Create log groups /aws/bedrock-agentcore/runtimes/<tok>-DEFAULT, /aws/vendedlogs/bedrock-agentcore/runtime/APPLICATION_LOGS/<tok> and .../USAGE_LOGS/<tok>, each with a stream sim2real-session, and put two events into the runtime group's stream.
3. Create a role trusted by arn:aws:iam::<account>:root with an inline policy that Allows logs:DescribeLogGroups/FilterLogEvents/GetLogEvents on log-group:/aws/bedrock-agentcore/*, /aws/lambda/*, /aws/batch/* and Denies logs:FilterLogEvents/GetLogEvents on log-group:/aws/vendedlogs/bedrock-agentcore/runtime/APPLICATION_LOGS/* and .../USAGE_LOGS/*; sts:AssumeRole it as sim2real-team.
4. With that session: FilterLogEvents and GetLogEvents on each vended group (expect AccessDeniedException, explicit deny); PutLogEvents into the APPLICATION_LOGS stream (expect AccessDeniedException, implicit deny, and no stored event); DescribeLogGroups with any logGroupNamePrefix (expect AccessDeniedException with the empty log-group:/log-stream: resource clause); GetLogEvents for stream sim2real-nope in the APPLICATION_LOGS group (expect AccessDeniedException, not ResourceNotFoundException) and in the runtime group (expect ResourceNotFoundException).
