## Description

=== Cause 1 of 2: DisassociateSourceGraphqlApi classifies a well-formed-but-unknown associationId as a malformed request ===
Failing check: appsync.op-contract-disassociateSourceGraphqlApi
AWS: Smithy (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/smithy-model/com-amazonaws-appsync-awsdeepdishcontrolplaneservice.json) DisassociateSourceGraphqlApi = DELETE /v1/mergedApis/{mergedApiIdentifier}/sourceApiAssociations/{associationId}, success 200, modeled errors BadRequestException|400, ConcurrentModificationException|409, InternalFailureException|500, NotFoundException|404, UnauthorizedException|401. The model documents NotFoundException as "The resource specified in the request was not found. Check the resource, and then try again." and BadRequestException as "The request is not well formed. For example, a value is invalid or a required field is missing." Recorded behavior draws the line between the two by shape of the identifier, not by its existence: a UUID-shaped associationId that names no association on that merged API is looked up and reported missing with HTTP 404 NotFoundException and the message "No source API association was found" (entirely fixed text — AWS puts NO identifier in it), and the SAME 404/message is returned when the call is repeated after the association has actually been removed; only an associationId that is not UUID-shaped is refused at request validation with HTTP 400 BadRequestException and the message "Invalid SourceApi Association ID <associationId>", whose fixed text is "Invalid SourceApi Association ID " plus the associationId taken verbatim from the request.
Emulator: the well-formed unknown id takes the malformed-input path. For associationId=<a fresh random UUID> on an existing merged API, the emulator answers HTTP 400 BadRequestException (message "Invalid SourceApi Association ID <uuid>") where AWS answers HTTP 404 NotFoundException "No source API association was found". The check aborts at that first probe, so the dead-identifier repeat (also owed 404 "No source API association was found") and the genuinely malformed id (owed 400 "Invalid SourceApi Association ID assoc-does-not-exist-1234") are not reached and must be verified by the fix too.
Why: both the HTTP status (400 vs 404) and the error code differ, so a client cannot distinguish "this association is already gone" from "you sent me garbage". Merged-API orchestration and teardown code that treats NotFoundException as already-converged (the idempotent-delete pattern, including the suite's own cleanup handler) instead sees a non-retryable 400 input error and fails the teardown; conversely code that validates its own input against the 400 class now gets it for a perfectly well-formed id.
Fix: the shared association-refusal rule behind both disassociate handlers — crate::state::delete_source_api_association (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/state.rs), whose AssociationRefusal variants services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/disassociate_source_graphql_api.rs maps 1:1 onto the modeled errors in `refuse` (lines 200-221). The id-shape check must produce AssociationRefusal::BadRequest ONLY for an associationId that is not UUID-shaped; a well-formed id that resolves to no association must produce AssociationRefusal::NotFound with the fixed message "No source API association was found".
Related open issue that does NOT cover this: 20261029T174359Z-appsync-control-plane-error-semantics-not-found-bad.md describes the same inversion in its Cause 4 and carries the replay key for the sibling check appsync.op-contract-disassociate-source-graphql-api, but it does NOT carry appsync.op-contract-disassociateSourceGraphqlApi — the suite accordingly reports this check as unowned, so closing that issue's keys alone leaves this check failing.
Traces: appsync.op-contract-disassociateSourceGraphqlApi (assertion `assert unknown_code == "NotFoundException"` -> "expected NotFoundException, got BadRequestException").

=== Cause 2 of 2: the AppSync custom-domain CRUD lifecycle is unreachable because an ACM DNS-validated certificate for a name in the account's own tagged public hosted zone ends FAILED ===
Failing check: appsync.domain-name-crud-lifecycle
AWS: Smithy (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) CertificateDetail$Status -> CertificateStatus [PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED]; the documented rule is that a requested AMAZON_ISSUED certificate enters PENDING_VALIDATION, ACM retries validation for 72 hours, and "If validation succeeds, the certificate enters status ISSUED"; FailureReason "exists only when the certificate status is FAILED". DomainValidation$ResourceRecord is the CNAME the requester publishes and DomainValidation$ValidationStatus -> DomainStatus [PENDING_VALIDATION, SUCCESS, FAILED] turns SUCCESS once it is observed. Recorded behavior: for a label under the account's own tagged public hosted zone, RequestCertificate(ValidationMethod='DNS') -> DescribeCertificate PENDING_VALIDATION with a CNAME ResourceRecord; after that record is UPSERTed through route53, DescribeCertificate reports Status 'ISSUED' / ValidationStatus 'SUCCESS', which is the only certificate AppSync CreateDomainName accepts. The particular label, apex, ARN and timestamps are per-run values; the PENDING_VALIDATION -> ISSUED transition after the record is published is the requirement.
Emulator: DescribeCertificate reports the terminal Status 'FAILED' (HTTP 200, no FailureReason) for a name under that very zone, so the check aborts in its `_dns_validated_cert` helper on `assert status == "ISSUED"` before it issues a single AppSync call — the whole CreateDomainName/GetDomainName/UpdateDomainName/ListDomainNames/DeleteDomainName lifecycle, including the post-delete 404 NotFoundException "Domain name not found" this check asserts, is never exercised.
Why: a client that asks ACM for a certificate for a name it demonstrably controls (the emulator's own route53 serves that zone) is told terminally that the request failed; FAILED means "delete the request and try again", so the client stops polling and reports a hard provisioning error. Every feature that needs an ACM-issued certificate — AppSync custom domains here — becomes unreachable.
Fix: the ACM certificate state machine, not AppSync: the validation-outcome decision in services/service-com-amazonaws-acm-certificatemanager/src/ops/request_certificate.rs and the reserved-name judgement it consults in services/service-com-amazonaws-acm-certificatemanager/src/state.rs. A name under a public hosted zone this account holds must enter PENDING_VALIDATION with its challenge CNAME live and reach ISSUED once that record resolves; FAILED must be reserved for a modeled FailureReason (and then populate it).
Related open issue that does NOT cover this check: 20261101T214920Z-appsync-custom-domain-checks-are-all-blocked-upstream.md describes the same ACM behavior and carries six other appsync check keys, but NOT appsync.domain-name-crud-lifecycle — the suite reports this check as unowned, so that issue's replay list would close without ever re-running it.
Traces: appsync.domain-name-crud-lifecycle (AssertionError: DNS-validated certificate for <label>.<baseline-zone-apex> ended 'FAILED').
