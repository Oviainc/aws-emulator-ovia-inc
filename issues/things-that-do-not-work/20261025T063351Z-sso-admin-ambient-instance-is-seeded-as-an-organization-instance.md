# Ambient instance is seeded as an ORGANIZATION instance, so the account-instance restriction never fires: ABAC create returns 200 and CreateAccountAssignment returns ResourceNotFoundException instead of ValidationException

> _Note: this issue was identified against the code base at commit `8a89cb0fad828a594e64b8a31f073b52ff4869bb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateInstanceAccessControlAttributeConfiguration

## Description
This issue carries ONE root cause. Cause 1 of 1: the instance `ListInstances` hands out is seeded as an IAM Identity Center ORGANIZATION instance, so `permission_sets_enabled` is true on it and the account-instance withdrawal of the permission-set / account-assignment / ABAC surface is never reached for the only instance a client can discover. Failing check ids for this cause: sso-admin.abac-configuration-lifecycle, sso-admin.account-assignment-full-lifecycle.

AWS: in the recorded account the ambient instance — the one `ListInstances` returns — is an ACCOUNT instance of IAM Identity Center, which supports neither permission sets nor the account assignments and ABAC configuration built on them. Every operation of that surface is therefore refused on that instance up front, before any resource lookup, with HTTP 400 and error code `ValidationException`. Smithy: `CreateInstanceAccessControlAttributeConfiguration` and `DescribeInstanceAccessControlAttributeConfiguration` both model `ValidationException` (httpError 400) alongside `ResourceNotFoundException` (404); `CreateAccountAssignment`, `DeleteAccountAssignment`, `DescribeAccountAssignmentCreationStatus`, `DescribeAccountAssignmentDeletionStatus` and `ListAccountAssignments` likewise each model `ValidationException` 400 and `ResourceNotFoundException` 404. The refusal message is a known rule, not incidental recorded text — it is AWS's own fixed wording for this restriction and the emulator already encodes it verbatim as `state::ACCOUNT_INSTANCE_UNSUPPORTED_MESSAGE`: "This operation is not supported for account instances of IAM Identity Center." The distinction that matters on the wire is the error CLASS: 400 `ValidationException` says "this instance kind can never do this", whereas 404 `ResourceNotFoundException` says "the permission set is merely missing" — the emulator's own state.rs documents exactly that contrast.

Emulator: `state::SEED_INSTANCE_TYPE` is `InstanceType::Organization`, and `Instance::active` initialises `permission_sets_enabled` from `InstanceType::permission_sets_enabled()` (true only for `Organization`). `permission_set_surface_withdrawn` / `abac_surface_withdrawn` consequently return false for the ambient instance, so the withdrawal every handler of that surface checks never triggers for it. Observed in replay against that ARN: (a) `CreateInstanceAccessControlAttributeConfiguration` with one `AccessControlAttribute` returns HTTP 200 with an empty body instead of being refused — the call AWS rejects is ACCEPTED and the ABAC configuration is persisted, and the follow-up `DescribeInstanceAccessControlAttributeConfiguration` is likewise not refused; (b) `CreateAccountAssignment` for a syntactically valid but nonexistent `PermissionSetArn` falls through the missing withdrawal into the permission-set lookup and answers error code `ResourceNotFoundException` (404) where AWS answers `ValidationException` (400). The positive controls in the same check pass, so this is not a blanket outage: `ListInstances`, `DescribeInstance` and identitystore `CreateGroup` all succeed, and only the instance's KIND is wrong.

Why: a client that branches on this restriction is misled in both directions. On the over-permissive side it believes it has configured ABAC on an instance that can never honour it — the 200 is indistinguishable from a real success, so the misconfiguration is discovered only when sessions carry no attribute tags, and nothing in the emulator ever tells the client this account cannot do ABAC. On the error-class side, retry and provisioning logic that treats `ResourceNotFoundException` as "create the permission set first, then retry" will loop forever creating prerequisites, because the real cause is a permanent instance-type restriction that no amount of resource creation clears; code that correctly handles 400 `ValidationException` as terminal never runs. Clients also cannot discover the restriction by reading the instance, since `DescribeInstance$PermissionSetsEnabled` reports true.

NOTE this contradicts the premise of the open issue 20261024T170542Z-sso-admin-listinstances-wrong-behavior.md, which asked for exactly this seeding change (ambient instance = organization instance, permission sets served by default) and whose reasoning is already reflected in state.rs's doc comments. The replayed behavioral ground truth is the opposite: the recorded account's ambient instance IS an account instance and the withdrawn surface is refused on it. These two cannot both hold, so that issue should be reconciled against this one rather than fixed independently — flipping the seed back without closing that issue will simply flip these checks and that issue's checks alternately. The account-instance restriction logic itself (`permission_set_surface_withdrawn`, `abac_surface_withdrawn`, the 400/`ValidationException` classification and its message) is correct and should be kept as-is; only which kind of instance the account's ambient instance is, is wrong.

Fix: the service's seeded state — `SEED_INSTANCE_TYPE` and the ambient-instance enablement in `src/state.rs` that feeds `Instance::active`'s `permission_sets_enabled` — so the instance `ListInstances` discovers is an account instance and the existing withdrawal applies to it. Secondarily, confirm each handler of that surface asks the withdrawal BEFORE its resource lookup, so `CreateAccountAssignment` and `ListAccountAssignments` with a nonexistent `PermissionSetArn` answer 400 `ValidationException` rather than 404 `ResourceNotFoundException`; the ABAC read path must be gated by the same restriction rather than returning an empty configuration. File/line citations: `src/state.rs` SEED_INSTANCE_TYPE (l.182), `InstanceType::permission_sets_enabled` (l.166), `Instance::active` permission_sets_enabled init (l.1115), `enable_ambient_instance` (l.2064), `permission_set_surface_withdrawn` (l.2155), `abac_surface_withdrawn` (l.2172), `ACCOUNT_INSTANCE_UNSUPPORTED_MESSAGE` (l.192).

Traces: sso-admin.abac-configuration-lifecycle (CreateInstanceAccessControlAttributeConfiguration accepted with 200 where a refusal is required), sso-admin.account-assignment-full-lifecycle (CreateAccountAssignment answered ResourceNotFoundException where ValidationException is required).

Code grounding in the checkout: src/state.rs l.182 `pub const SEED_INSTANCE_TYPE: InstanceType = InstanceType::Organization;`, l.166-168 `permission_sets_enabled` returns `matches!(self, Self::Organization)`, l.1115 `permission_sets_enabled: instance_type.permission_sets_enabled()`, l.2155-2157 `permission_set_surface_withdrawn` = `!instance.permission_sets_enabled`, l.2172-2173 `abac_surface_withdrawn` delegates to it. ## Steps to Reproduce
1. Start the emulator with a fresh (empty) engine and point an sso-admin client at it.
2. Call ListInstances and capture the single returned InstanceArn. Poll DescribeInstance until Status == ACTIVE.
3. Call DescribeInstance with that ARN and observe PermissionSetsEnabled: true — the ambient instance is seeded as an organization instance, whereas the recorded account's ambient instance is an account instance.
4. Call CreateInstanceAccessControlAttributeConfiguration(InstanceArn=<that ARN>, InstanceAccessControlAttributeConfiguration={"AccessControlAttributes": [{"Key": "department", "Value": {"Source": ["${path:enterprise.department}"]}}]}). Observe HTTP 200 with an empty body. Expected: HTTP 400, error code ValidationException, message "This operation is not supported for account instances of IAM Identity Center."
5. Call DescribeInstanceAccessControlAttributeConfiguration(InstanceArn=<that ARN>). Observe it is not refused and reports the configuration persisted by step 4. Expected: the same HTTP 400 ValidationException, since the ABAC read path is gated by the identical instance-type restriction rather than a plain not-found or an empty configuration.
6. Build a syntactically valid but nonexistent permission set ARN: arn:aws:sso:::permissionSet/<instance-id>/ps-0123456789abcdef, where <instance-id> is the trailing segment of the InstanceArn.
7. Call CreateAccountAssignment(InstanceArn=<that ARN>, TargetId=<your 12-digit account id>, TargetType="AWS_ACCOUNT", PermissionSetArn=<the ARN from step 6>, PrincipalType="GROUP", PrincipalId=<a GroupId from identitystore CreateGroup>). Observe error code ResourceNotFoundException (HTTP 404). Expected: error code ValidationException (HTTP 400) with the account-instance message, because the restriction is asked before any permission-set lookup.
8. Repeat with DeleteAccountAssignment (same arguments), DescribeAccountAssignmentCreationStatus(AccountAssignmentCreationRequestId="00000000-0000-0000-0000-000000000000"), DescribeAccountAssignmentDeletionStatus(same request id) and ListAccountAssignments(AccountId=<account>, PermissionSetArn=<step 6 ARN>): each must answer HTTP 400 ValidationException with that message rather than a 404 or a success.
9. Confirm the cause is the seed alone: in src/state.rs set SEED_INSTANCE_TYPE to InstanceType::Account, restart, and re-run steps 4-8 — every call is then refused with 400 ValidationException.
