# opensearch: the domain REST data plane answers 404 UnknownService 'es' for every signed request, so no index/search behaviour can be exercised (3 causes)

> _Note: this issue was identified against the code base at commit `1a0d537a6f45d8cc06f79b3c3e7692a297108dcd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateIndex

## Description
This issue bundles 3 root causes, all in the opensearch service. The existing open issue 20261024T055421Z-opensearch-domain-data-plane-is-not-served-and.md describes the same family of symptoms for a different set of checks; the checks listed here were NOT marked owned by it in this replay and are therefore filed with it named for cross-reference. Each cause below must be closed before submitting.

Cause 1 of 3: a SigV4-signed HTTP request to the endpoint the control plane published for a domain is not routed to an OpenSearch REST data plane at all.
AWS: DescribeDomain publishes DomainStatus.Endpoint (or Endpoints.vpc) as a host that serves the OpenSearch REST API. A signed `GET /` on it returns HTTP 200 with the cluster banner; `PUT /<index>` with a mappings/settings body returns 200/201 with {"acknowledged": true, "index": "<index>"}; `POST /<index>/_doc`, `GET /<index>/_search`, `_cluster/health`, `_nodes`, `_bulk`, `_msearch`, `_cluster/settings`, `_search/scroll`, `_pit`, `_reindex`, `_update_by_query`, `_ingest/pipeline/<id>` and the ISM `_plugins/_ism/policies/<id>` paths all answer on that same host. Smithy: the opensearch model covers only the control plane, so the data plane is recorded behavior only — the recordings show 2xx OpenSearch REST payloads on the published endpoint.
Emulator: every signed request to the published endpoint answers HTTP 404 with the AWS-JSON error body {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"}. The fixed text is `no emulated service is registered for '<sigv4 service name>'` and the variable part is the signing name taken from the request's Authorization credential scope (here `es`). That is the emulator's front door reporting that no handler is bound for the domain host; it is not any OpenSearch REST status, body or error type.
Why: a client that provisions a domain and then indexes or searches through the endpoint AWS handed it gets a 404 with a non-OpenSearch error envelope. Every behaviour that depends on the engine — mapping conflicts, refresh/visibility, optimistic concurrency, scroll/PIT/search_after paging, aggregations, sorting, kNN, bulk item errors, msearch slot isolation, aliases/rollover, reindex, update_by_query, ingest pipelines, ISM, cluster/node introspection — is unobservable and uncheckable.
Fix: the request router/front door must bind the domain endpoint host to an OpenSearch REST data-plane handler for the `es` signing name, and that handler must implement the index/document/search/cluster REST surface; it belongs with the domain's state (the index and document store keyed by domain) rather than in any single control-plane operation handler.

Cause 2 of 3: the FGAC/basic-auth and native-client data-plane scenarios never produce a response at all — they exhaust the 60 s harness cap polling the published endpoint.
AWS: an FGAC domain (AdvancedSecurityOptions with an internal master user) serves HTTPS basic-auth requests on the published endpoint, and document-level security, field-level security and role-pattern mappings are enforced there; an unmapped index read answers 403 with a security_exception. The opensearch-py native client reaches the same endpoint with SigV4. Recorded behavior only (data plane is outside the Smithy model).
Emulator: these checks never receive a terminal answer within the budget — the polled endpoint never becomes an OpenSearch REST responder, so the check is cut off ("Check timed out after 60.0s") rather than failing an assertion.
Why: a client cannot distinguish "authorization denied" from "nothing is listening". Security behaviour that AWS enforces at the endpoint is neither allowed nor denied — the request simply never resolves, so an FGAC deployment appears to hang.
Fix: same component as cause 1 — once the endpoint is bound and answers, the FGAC authorization layer (internal user database, role mappings, DLS/FLS filtering) must be applied on that data-plane handler.

Cause 3 of 3: DescribeDomainConfig omits the AccessPolicies member entirely after UpdateDomainConfig sets it.
AWS: Smithy: UpdateDomainConfig.AccessPolicies targets PolicyDocument (@length 0..102400). DescribeDomainConfig returns DomainConfig.AccessPolicies as an AccessPoliciesStatus whose Options holds the policy document string and whose Status carries the usual OptionStatus. After an UpdateDomainConfig that supplies AccessPolicies, the member is present and Options is the document that was sent.
Emulator: the DomainConfig returned has no AccessPolicies key at all, so a client reading stored["AccessPolicies"]["Options"] raises KeyError: 'AccessPolicies'.
Why: a client cannot read back the resource policy it just applied, so it cannot confirm convergence of an access-policy change nor diff the current policy before updating it. Combined with cause 1 the policy is also never enforced.
Fix: the DescribeDomainConfig/UpdateDomainConfig serializer and the domain config state must carry AccessPolicies as an AccessPoliciesStatus whenever a policy has been set.
Traces: opensearch.access-policy-denies-data-plane-index-path.
