# Polly SynthesizeSpeech output stream diverges from the rendered speech it must return: mp3 payload and word-mark timings (2 causes)

> _Note: this issue was identified against the code base at commit `533efece7fa11c0e537273065624bf5d01aa80f8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SynthesizeSpeech

## Description
SynthesizeSpeech answers 200 with the right framing for both the audio and the speech-mark request, but the payload it streams is generated by a placeholder renderer rather than derived from the requested text/voice, so neither the audio bytes nor the mark timings match what AWS returns for the same request.

Cause 1 of 2 (fixture polly-synthesize-speech-roundtrip, step task#1 — audio payload): the mp3 AudioStream differs from the recorded stream in both length and content.
AWS: Smithy (services/service-com-amazonaws-polly-parrot-v1/smithy-model/com-amazonaws-polly-parrot-v1.json) models SynthesizeSpeech as POST /v1/speech -> 200 with AudioStream as the @httpPayload streaming blob, ContentType in the Content-Type header and RequestCharacters in x-amzn-RequestCharacters. The model does not state waveform content, so for the payload this is recorded behavior only: for a given Text + VoiceId + Engine + OutputFormat + SampleRate, real Polly returns a deterministic encoded rendering of that text in that voice — the stream's length and its bytes are a function of the request, and a short sentence yields a correspondingly short mp3.
Emulator: for the same request it streams a payload of a different length and a different digest — roughly half again as long as the recorded rendering — because the audio is produced by a content-independent placeholder generator rather than by rendering the request's text in the requested voice. Status, Content-Type framing and streaming all behave; only the bytes are not the requested speech.
Why: a client that measures the returned audio (duration from byte length or sample count, loudness, a digest/fingerprint comparison, or a transcription round-trip) gets a value unrelated to the text it asked to synthesize, so audio regressions cannot be detected against this emulator and any size-budgeted consumer mis-sizes its buffers.
Fix: the audio rendering/encoding path of this operation's handler (services/service-com-amazonaws-polly-parrot-v1/src/ops/synthesize_speech.rs): the emitted stream must be derived from the request's Text, VoiceId, Engine, OutputFormat and SampleRate.
Related open issue: 20261022T175007Z-polly-synthesizespeech-returns-placeholder-audio-payloads-are-digital.md reports the placeholder waveform from the BEHAVIORAL suite (silence for pcm/mulaw) and carries no wire replay key for this fixture; it does not cover the mp3 stream's divergence from the recorded rendering. This entry carries the wire step so the fix can be re-replayed against it.

Cause 2 of 2 (fixture polly-synthesize-speech-roundtrip, step task#3 — speech marks): the JSON speech-mark stream has the right structure and the right text offsets but the wrong `time` values.
AWS: Smithy models OutputFormat=json with SpeechMarkTypes (SpeechMarkType = [sentence, ssml, viseme, word], @length max 4) and documents the json format as the speech-mark channel; recorded behavior for the mark stream: one JSON object per line, a sentence mark followed by the word marks in text order, each carrying type, the start/end byte offsets into the input text, value, and `time` — the millisecond onset of that unit IN THE RENDERED AUDIO. In the recording the first word's onset is NOT 0 (the sentence mark is at time 0, the first word begins after the leading audio), and the subsequent onsets follow the voice's actual prosody, so successive gaps are uneven.
Emulator: the stream's line count, ordering, types, start/end offsets and values all match, but every `time` differs: the first word mark is emitted at time 0 and the remaining onsets advance on a smooth per-character/per-word estimate, so the marks do not line up with the audio the same request returns.
Why: speech marks exist to synchronize an external timeline — captions, lip-sync, karaoke highlighting, cue triggering — with the audio stream. Onsets computed from a uniform estimate drift against the real rendering and start the first word at the very first audio sample, so a client that validates its synchronization logic against this emulator sees timings that are self-consistent but wrong, and a client that seeks the audio by a mark's time lands in the wrong place.
Fix: the speech-mark generation path of the SynthesizeSpeech handler (src/ops/synthesize_speech.rs): mark onsets must be taken from the same rendering that produces the audio stream (a non-zero onset for the first word), not from a fixed-rate estimate over the text.
