# ListPurchaseOptions returns an empty purchaseOptions list for filtered queries

> _Note: this issue was identified against the code base at commit `415bb240c081114340f3b6ac41e90b57c519fa79`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPurchaseOptions

## Description
This issue bundles 2 net-new root causes, both in marketplace-discovery and both on ListPurchaseOptions, found by replaying the wire corpus simparity-wire-aws-v1 against the emulator built from this checkout (13/28 steps passed, 12 mismatched, 3 blocked, score 46.4%). They share one fault: a ListPurchaseOptions call that AWS answers with at least one PurchaseOptionSummary is answered by the emulator with NO purchase options at all, so the purchase-option listing is empty and every drill-down step that must follow a returned purchaseOptionId/offerId has nothing to follow (the replay reports 3 blocked steps).

The other seven divergence clusters in this service are already owned by open issues (20261029T201942Z-marketplace-discovery-refusals-carry-messages-aws-does-not.md, ...-searchlistings-returns-no-nexttoken-....md, ...-getlisting-getproduct-and-listfulfillmentoptions-serve-synthesized-placeholder-records.md) and are NOT re-filed here. Two adjacent open issues must not be read as covering these causes: the placeholder-records issue is about the CONTENT of the records GetListing/GetProduct/ListFulfillmentOptions serve, not about ListPurchaseOptions returning nothing; and 20261030T005652Z-marketplace-discovery-iam-authorization-never-evaluated-on-getlisting.md touches ListPurchaseOptions only for the ORDER of the PurchaseOptionFilterType value set inside a ValidationException message, i.e. a refusal's wording, not the result set of a successful call. Neither carries these replay keys.

=== Cause 1 of 2: a ListPurchaseOptions query filtered by product and seller matches nothing, so purchaseOptions comes back empty ===
AWS: Smithy (model services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json): ListPurchaseOptions POST /2026-02-05/listPurchaseOptions, success status 200, input filters -> PurchaseOptionFilterList @length(1..10), output purchaseOptions -> PurchaseOptionSummaryList @length(..100) plus nextToken; @paginated{inputToken:nextToken,outputToken:nextToken,items:purchaseOptions}; errors AccessDeniedException(403)/ValidationException(400)/ThrottlingException(429)/InternalServerException(500). PurchaseOptionFilter.filterValues doc: "PRODUCT_ID - One or more product identifiers to filter by", "SELLER_OF_RECORD_PROFILE_ID - One or more seller profile identifiers to filter by", with "Multiple filters are combined with AND logic. Multiple values within the same filter are combined with OR logic" (ListPurchaseOptions doc). PurchaseOptionSummary requires purchaseOptionId, catalog, purchaseOptionType (OFFER | OFFERSET), sellerOfRecord and associatedEntities. So a request naming a product that the catalog holds, together with that product's own seller of record, must return the purchase option(s) of that product - at minimum the OFFER whose associatedEntities carry that product and that seller. Recorded behavior: 200 with purchaseOptions[0] present, an OFFER-type summary whose associatedEntities carry the filtered product and whose sellerOfRecord is the filtered seller profile, plus a badges list.
Emulator: 200 with the right status and a well-formed body, but purchaseOptions is EMPTY - the replay reports "$.purchaseOptions[0]: missing (expected {...}, got None)". The same empty result appears on the offer-drill-down fixture's first step, whose returned offer is what its later steps dereference. No error and no nextToken: the emulator simply reports that nothing matches a product+seller pair the corpus established from this same service.
Why: a client reads an empty purchaseOptions as "this buyer has no purchase options for this product" - it is indistinguishable from a legitimately empty catalog, so there is nothing to retry or report. Every workflow that starts by listing purchase options and then drills into the returned offer or offer set (GetOffer, GetOfferTerms, GetOfferSet) is dead on the first call, and the emulator cannot exercise a client's pagination or selection logic over purchase options at all. It is also the silent direction of failure: no status or error code signals it.
Fix: ListPurchaseOptions' handler and the catalog state it reads - the per-filter matching in matches_every_filter (PRODUCT_ID matched against the entry's product ids, SELLER_OF_RECORD_PROFILE_ID against the entry's seller profile id, AND-combined across filters) together with the projection that builds the candidate rows, so that a product the catalog holds and that product's seller of record select the purchase options associated with it. Hypothesis: the AND-combination over the corpus' filter set selects no seeded row - either the entry's indexed product/seller facts are not the same identifiers the service hands out elsewhere, or the seeded catalog holds no purchase option satisfying the combination the corpus uses (note the one PRIVATE-visibility offer in the seed is also the EXPIRED one, so a PRIVATE+AVAILABLE combination can never match). Traces: .../src/ops/list_purchase_options.rs (handle, matches_every_filter) and the catalog seed plus purchase_options() projection in .../src/state.rs.
Traces: marketplace-discovery-purchase-options-filter-by-product-and-seller#task#1 (cluster also covers marketplace-discovery-purchase-options-offer-drilldown#task#1).

=== Cause 2 of 2: the offer-set drill-down's ListPurchaseOptions step returns [] instead of the offer-set's purchase option ===
AWS: Smithy: same operation and output contract as above; PurchaseOptionType is OFFER for a single-product offer and OFFERSET for a bundled offer set, and PurchaseOptionSummary.associatedEntities (required) carries "The products, offers, and offer sets associated with this purchase option". Recorded behavior: 200 with purchaseOptions holding one summary - purchaseOptionType OFFER, a sellerOfRecord, a badges entry, and associatedEntities naming both the offer and the product - reached as the second step of an offer-set drill-down, i.e. after the preceding step has established the offer set/seller the filter names.
Emulator: 200 with purchaseOptions present but EMPTY - the replay reports "$.purchaseOptions: value_mismatch (expected [ {...one OFFER summary...} ], got [])". The list member is serialized, so the shape is right and only the result set is wrong; the drill-down steps that would dereference the missing purchaseOptionId cannot run.
Why: same client-visible consequence as Cause 1, on the offer-set path: the buyer's purchase options for an offer set are unreachable, and because the response is a normal 200 with an empty list the client concludes there are none. A test suite built on the emulator would record "no purchase options" as the expected state and keep passing while the real service returns one.
Fix: same component as Cause 1 - ListPurchaseOptions' filter matching and the catalog rows it filters - but this is the offer-set-reached query rather than the product+seller one, and it is a separate replay key: it must be confirmed empty-to-non-empty on its own fixture, because a fix that only repairs the product+seller combination leaves this one returning []. Traces: .../src/ops/list_purchase_options.rs (handle, matches_every_filter) and purchase_options() in .../src/state.rs.
Traces: marketplace-discovery-purchase-options-offerset-drilldown#task#2.
