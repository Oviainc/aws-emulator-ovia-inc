# bedrock-agent: 4 net-new causes — CreateFlowAlias has no name-uniqueness pre-condition, DeleteFlow/DeleteFlowVersion have no in-use guard (DeleteFlowVersion still 501), and InvokeFlow is unrouted

> _Note: this issue was identified against the code base at commit `a25c82394d1a52e3f7a14fc6dffbcc94599db86a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFlowAlias

## Description
Four net-new root causes in the bedrock-agent flow control plane and its flow data plane, all reached through replayed behavioral checks of this suite. Smithy model consulted: services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/smithy-model/com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda.json. Not covered by the open issues 20261105T003415Z-bedrock-agent-createflowalias-stub.md (CreateFlowAlias is now implemented and answers 201 — the stub issue carries only the concurrent-flow-alias-name-race replay key, not the serial conflicting-name check below), 20261030T053655Z-bedrock-agent-deleteflow-stub.md (DeleteFlow is now implemented and answers 200 — what is missing is its in-use pre-condition), 20261102T104226Z-bedrock-agent-prepareflow-has-no-mutual-exclusion-guard.md, or 20261029T214059Z-bedrock-agent-runtime-streaming-and-agent-invocation-surface.md (a WIRE finding filed under service bedrock-agent-runtime; it carries no behavioral check key and none of the check ids below, so Cause 4's check is not gated by it).

=== Cause 1 of 4: CreateFlowAlias accepts a duplicate alias name on the same flow instead of refusing 409 ConflictException ===
AWS: Smithy: CreateFlowAlias POST /flows/{flowIdentifier}/aliases, success code 201, `name` required (pattern ^([0-9a-zA-Z][_-]?){1,100}$), and it models ConflictException @httpError 409 ("There was a conflict performing an operation."). Recorded behavior: an alias name must be unique per flow — a second CreateFlowAlias with a name that an existing alias on the same flow already holds is refused HTTP 409 ConflictException with the message template `Couldn't perform CreateFlowAlias operation. The name <name> already exists for id <existingAliasId>. Retry your request with a different name.` Fixed text: "Couldn't perform CreateFlowAlias operation. The name " / " already exists for id " / ". Retry your request with a different name."; the variable parts are the requested alias name (taken from the request) and the id of the alias already holding that name (taken from the emulator's state). After the refusal exactly one alias with that name exists on the flow.
Emulator: the duplicate create SUCCEEDS with HTTP 201 and mints a second alias (a fresh 10-character id and its own alias ARN) carrying the same name on the same flow — no ConflictException is raised at all, so two aliases share one name and ListFlowAliases reports both.
Why: alias names are a client-visible identifier; code that relies on CreateFlowAlias being the uniqueness gate (promote-by-name deploys, idempotent re-provisioning, CFN-style create-or-conflict logic) never sees the 409 it branches on, and the flow then carries duplicate-named aliases that AWS can never produce, so name-based alias resolution becomes ambiguous.
Fix: CreateFlowAlias's handler/validation in services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/create_flow_alias.rs — add the per-flow alias-name uniqueness pre-condition before minting, returning the modeled ConflictException with the template above.
Traces: bedrock-agent.create-flow-alias-conflicting-name-rejected.

=== Cause 2 of 4: DeleteFlow has no in-use guard — a flow still referenced by an alias is deleted instead of refused 409 ConflictException ===
AWS: Smithy: DeleteFlow DELETE /flows/{flowIdentifier}/ with `skipResourceInUseCheck` (@httpQuery, default false — "deletion is stopped if the resource is in use"), success 200, models ConflictException @httpError 409. Recorded behavior: with skipResourceInUseCheck absent/false, deleting a flow that still has an alias referencing it is refused HTTP 409 ConflictException with the template `Couldn't perform DeleteFlow operation. The Flow that you specified is currently in use by the following alias: <aliasId>. Retry your request after the alias has finished using the Flow.` Fixed text: "Couldn't perform DeleteFlow operation. The Flow that you specified is currently in use by the following alias: " / ". Retry your request after the alias has finished using the Flow."; the one variable part is the referencing alias id, taken from the emulator's state. The flow survives the refusal (GetFlow still answers it), and once the alias is deleted the same DeleteFlow succeeds.
Emulator: DeleteFlow answers HTTP 200 with the flow id and removes the flow while an alias still routes to it — the skipResourceInUseCheck=false path performs no in-use check whatsoever.
Why: this is an over-permissive destroy. A caller that deletes a flow by mistake while an alias is live gets no protection, the alias is orphaned, and any client that treats the 409 as "detach the alias first" never runs that branch; teardown ordering bugs become silent data loss instead of a refusal.
Fix: DeleteFlow's handler in services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/delete_flow.rs — honour skipResourceInUseCheck by scanning the flow's aliases first and returning the modeled ConflictException with the template above when any alias references the flow.
Traces: bedrock-agent.flow-delete-in-use-by-alias-rejected.

=== Cause 3 of 4: DeleteFlowVersion answers 501 NotImplemented, so its in-use guard (and its whole delete effect) never happens ===
AWS: Smithy: DeleteFlowVersion DELETE /flows/{flowIdentifier}/versions/{flowVersion}/, success 200 returning `id` + `version`, with `skipResourceInUseCheck` (@httpQuery, default false) and modeled ConflictException @httpError 409. Recorded behavior: deleting a flow version that an alias's routingConfiguration still points at is refused HTTP 409 ConflictException with the template `Couldn't perform DeleteFlowVersion operation. The Flow that you specified is currently in use by the following alias: <aliasId>. Retry your request after the alias has finished using the Flow.` Fixed text: "Couldn't perform DeleteFlowVersion operation. The Flow that you specified is currently in use by the following alias: " / ". Retry your request after the alias has finished using the Flow."; the variable part is the referencing alias id from state. Deleting the alias first unblocks the version delete, which then answers 200.
Emulator: the call is refused with the non-modeled error code `NotImplemented` (HTTP 501) — services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/delete_flow_version.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker and its handle() returns Scaffolded::not_implemented("DeleteFlowVersion"). Note the suite did NOT auto-file this one: the check catches the ClientError and asserts on its code, so no stub issue was raised for it.
Why: no flow version can ever be deleted, and the distinction between "version in use by an alias" (409) and a successful delete (200) is unobservable. A client gets an unmodeled 501 that no SDK error branch for DeleteFlowVersion handles, so version-retention/cleanup logic cannot run and cannot even report why.
Fix: implement DeleteFlowVersion in services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/delete_flow_version.rs (and drop the SCAFFOLDED marker): resolve the flow and version from state, apply the alias-reference in-use pre-condition unless skipResourceInUseCheck is true, then remove the version and return id+version.
Traces: bedrock-agent.flow-version-delete-in-use-by-alias-rejected.

=== Cause 4 of 4: InvokeFlow is not routed to any emulated service, so a prepared flow+alias cannot be executed at all ===
AWS: Smithy: InvokeFlow (bedrock-agent-runtime) POST /flows/{flowIdentifier}/aliases/{flowAliasIdentifier}, @http code 200, output member `responseStream` (FlowResponseStream, @httpPayload @streaming). Recorded behavior: invoking a Prepared flow whose alias routes to a numbered version answers HTTP 200 with Content-Type application/vnd.amazon.eventstream; iterating the stream yields a `flowOutputEvent` whose content.document is the exact document submitted in `inputs[0].content.document` for a passthrough Input->Output flow, followed by a `flowCompletionEvent` whose completionReason is `SUCCESS`.
Emulator: the request never reaches a handler — it is refused with error code `UnknownService` and the emulator-internal message `no emulated service is registered for 'bedrock'`, i.e. the front door resolves the bedrock-agent-runtime request to the signing name `bedrock` and finds nothing mounted there, even though the bedrock-agent-runtime crate is built into the emulator.
Why: the flow data plane is unreachable. Nothing created on the control plane (CreateFlow/PrepareFlow/CreateFlowVersion/CreateFlowAlias) can ever be executed, and the client receives neither a modeled error class nor an event stream — just a routing diagnostic with an error code no SDK models, so every end-to-end flow workload dead-ends.
Why this is net-new here: the open issue 20261029T214059Z-bedrock-agent-runtime-streaming-and-agent-invocation-surface.md describes the same routing gap from WIRE fixtures under service bedrock-agent-runtime, but it carries no behavioral replay key and does not name this check, so this check is not gated by it; a fixer closing that issue should re-replay this check too.
Fix: the emulator's endpoint/service router — map the bedrock-agent-runtime endpoint/signing name (`bedrock`) to the mounted bedrock-agent-runtime service and register the /flows/{flowIdentifier}/aliases/{flowAliasIdentifier} route, then serve InvokeFlow's FlowResponseStream event-stream serializer so flowOutputEvent/flowCompletionEvent are emitted.
Traces: bedrock-agent.flow-invoke-end-to-end-via-runtime.
