# dynamodb: 4 net-new root causes — Scan refuses IndexName, ProjectionExpression and the legacy ScanFilter with 501 NotImplemented, and a consistent GSI Scan 501s instead of ValidationException

> _Note: this issue was identified against the code base at commit `861e7723cbd520f91d3c8b29f6571221cf90c671`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Scan

## Description
Four distinct root causes in the DynamoDB emulator's Scan handler, every one grounded in a failing behavioral check that no open issue carries the replay key for. Each cause below must be closed before this issue is submitted.

NOTE ON RELATED FILED WORK: the open issue 20261025T024002Z-dynamodb-10-net-new-root-causes-query-scan.md describes Scan's scaffolded branches in its Cause 2, but it does NOT carry any of the replay keys listed here (its Scan traces are dynamodb.ddb-sfa-cli-attribute-exists-scan-derives-the-status-tally, dynamodb.ddb-ss-cli-scan-pages-merge-into-the-solve-answer and dynamodb.ddb-ss-filter-naming-an-undefined-expression-value-rejected only), and it says nothing about Cause 4 below. The handler's own module doc states the gap explicitly and calls these "their own gap issues" (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs lines 27-30).

=== Cause 1 of 4: Scan with IndexName answers 501 NotImplemented ===
AWS: Smithy: ScanInput.IndexName is an OPTIONAL member (target IndexName, @length 3-255, @pattern ^[a-zA-Z0-9_.-]+$), and the operation doc states Scan "returns one or more items and item attributes by accessing every item in a table or a secondary index". Scan's modeled error set is InternalServerError (500), InvalidEndpointException (421), ProvisionedThroughputExceededException (400), RequestLimitExceeded (400), ResourceNotFoundException (400) and ThrottlingException (400) — there is no NotImplemented error and no 501 anywhere in it. AWS serves a Scan naming a GSI or LSI and answers HTTP 200 with ScanOutput (Items / Count / ScannedCount / LastEvaluatedKey / ConsumedCapacity); on an index the ConsumedCapacity differs from the base-table scan and the projected attribute set is the index's, not the item's.
Emulator: every Scan that carries IndexName is refused with HTTP 501, error code NotImplemented and the message 'operation Scan with IndexName is scaffolded but not implemented in this emulator'. Fixed text of that message: 'operation ' + <op> + ' with ' + <member> + ' is scaffolded but not implemented in this emulator'; the only variable parts are the operation name and the input member name. AWS emits no message of this class at all here — the correct response is a 200 body.
Why: a client cannot scan a secondary index at all. Index projection, index pagination on an LSI (ExclusiveStartKey), sparse-index semantics, GSI fan-out across many indexes, and the agreement between an index read and a filtered base scan are all unreachable, and a client has no retry or error-handling path for an unmodeled 501/NotImplemented — SDK retry classifiers treat a 501 as non-retryable server failure rather than as a feature gap.
Fix: the Scan handler's IndexName branch and the secondary-index read path in the service state (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs, which currently documents at lines 27-30 that IndexName "is refused with the scaffold's 501", plus the index read path in the crate's state module).
Traces: dynamodb.ddb-gsi-composite-index-sort-key-narrows-within-the-partition, dynamodb.ddb-gsi-index-query-and-filtered-scan-agree-on-the-item-and-differ-on-cost, dynamodb.ddb-gsi-one-write-propagates-to-all-six-indexes, dynamodb.ddb-gsi-put-item-loop-reaches-the-same-estate-as-batch-write-item, dynamodb.ddb-wf-per-workflow-gsi-queries-reproduce-the-scan-grouping, dynamodb.ddb-wf-sparse-gsi-never-indexes-items-without-the-index-key, dynamodb.lsi-scan-pagination-exclusive-start-key.

=== Cause 2 of 4: Scan with ProjectionExpression answers 501 NotImplemented ===
AWS: Smithy: ScanInput.ProjectionExpression is an OPTIONAL member (target ProjectionExpression); ExpressionAttributeNames is the companion optional map used to alias reserved words. No NotImplemented error is modeled for Scan. AWS serves the Scan and returns in each item ONLY the attributes the projection names, with '#alias' substitutions resolved from ExpressionAttributeNames (this is how a reserved word such as 'status' is projected at all); ScannedCount and ConsumedCapacity are unaffected by the projection because projection is applied after the page is read.
Emulator: HTTP 501, code NotImplemented, message 'operation Scan with ProjectionExpression is scaffolded but not implemented in this emulator' (same fixed template as Cause 1, variable part = the member name ProjectionExpression).
Why: no Scan can project. Any client that pages a table reading only its key attributes — the standard way to enumerate keys cheaply, and the way these checks drain and verify a table — fails outright, and a reserved-word attribute becomes unreadable by scan since the only way to read it is via an ExpressionAttributeNames alias in a ProjectionExpression.
Fix: the Scan handler's ProjectionExpression branch, sharing the projection/ExpressionAttributeNames evaluator with the other read operations (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs lines 27-30).
Traces: dynamodb.batch-write-item-throttle-accounting-loses-no-key, dynamodb.ddb-sfa-filter-on-an-unprojected-attribute-still-narrows-the-scan, dynamodb.ddb-ss-consistent-scan-costs-double-and-filters-cost-nothing, dynamodb.ddb-wf-scan-projection-aliases-reserved-word-status.

=== Cause 3 of 4: Scan with the legacy ScanFilter / ConditionalOperator answers 501 NotImplemented ===
AWS: Smithy: ScanInput.ScanFilter is an OPTIONAL map (target FilterConditionMap) and ConditionalOperator an OPTIONAL enum; both are the pre-expression legacy parameters and both are still served. A ScanFilter entry with ComparisonOperator NOT_NULL or NULL is equivalent to the expression functions attribute_exists / attribute_not_exists and must select exactly the same items. No NotImplemented error is modeled.
Emulator: HTTP 501, code NotImplemented, message 'operation Scan with ScanFilter is scaffolded but not implemented in this emulator'.
Why: the legacy filter surface is dead, so SDKs and tooling that still emit ScanFilter (and every client verifying that legacy and expression filters agree) get an unmodeled server error instead of results.
Fix: the Scan handler's ScanFilter/ConditionalOperator branch, lowered onto the same filter evaluator the FilterExpression path already uses (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs lines 27-30).
Traces: dynamodb.ddb-sfa-legacy-scan-filter-not-null-and-null-match-the-expression-functions.

=== Cause 4 of 4: a strongly consistent Scan of a global secondary index answers 501 NotImplemented instead of the modeled ValidationException ===
AWS: a Scan that sets ConsistentRead=true together with an IndexName naming a GLOBAL secondary index is a client error: global secondary indexes support eventually consistent reads only, so the request is refused with ValidationException, HTTP 400, and no items. This is an input-validation outcome reached before any read, and ValidationException is DynamoDB's service-common client error (400). The same Scan without the flag succeeds, and ConsistentRead=true on the BASE table succeeds. Recorded behavior for the message wording: the check asserts only the error CODE, so the requirement here is the code and status; the message is AWS's standard validation sentence naming the unsupported consistency on the index.
Emulator: the scaffold check for the IndexName branch runs AHEAD of input validation, so the call answers HTTP 501 / NotImplemented with 'operation Scan with IndexName is scaffolded but not implemented in this emulator'. A client cannot distinguish a request it must fix (400) from a server-side gap (501).
Why: a refusal AWS classifies as a non-retryable client error is reported as a server error, which SDK retry policies and client error handling treat differently; and the negative half of the index-consistency contract can never be observed even once Cause 1 is fixed unless validation is ordered first.
Fix: order Scan's input validation (including the ConsistentRead-with-GSI rule) ahead of the not-implemented branch check in the Scan handler (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs), so a malformed request is still refused with ValidationException / 400 regardless of which branches are scaffolded.
Traces: dynamodb.ddbgsi-scan-consistent-read-on-an-index-rejected-while-base-scan-succeeds.

## Evidence
Cause 1: botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the Scan operation: operation Scan with IndexName is scaffolded but not implemented in this emulator. Expected: HTTP 200 with ScanOutput (Items/Count/ScannedCount/LastEvaluatedKey/ConsumedCapacity). Smithy models IndexName as an optional member of ScanInput and models NO NotImplemented error and no 501 for Scan.
Cause 2: ClientError (NotImplemented) when calling the Scan operation: operation Scan with ProjectionExpression is scaffolded but not implemented in this emulator. Expected: HTTP 200 with each item reduced to the projected attributes, '#alias' names resolved from ExpressionAttributeNames.
Cause 3: ClientError (NotImplemented) when calling the Scan operation: operation Scan with ScanFilter is scaffolded but not implemented in this emulator. Expected: HTTP 200 whose selected items equal those the attribute_exists/attribute_not_exists FilterExpression selects.
Cause 4: the check asserts "real AWS refuses a strongly consistent Scan of a global secondary index" and compares the raised code against 'ValidationException'; the emulator raised NotImplemented with HTTP 501 and the message 'operation Scan with IndexName is scaffolded but not implemented in this emulator'. Expected: ValidationException, HTTP 400, no items, while the same index Scan without ConsistentRead and a consistent base-table Scan both succeed.
The handler itself records the gap: services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/scan.rs lines 27-30 — "Secondary indexes (IndexName), the legacy filters (ScanFilter, ConditionalOperator) and projections (ProjectionExpression, the legacy AttributesToGet) are refused with the scaffold's 501 and are their own gap issues."

4. Cause 3: Scan with the legacy ScanFilter={'attr': {'ComparisonOperator': 'NOT_NULL'}} (and 'NULL') -> observe HTTP 501 / NotImplemented instead of the same item set the attribute_exists / attribute_not_exists FilterExpression returns.
5. Cause 4: CreateTable with a GSI, then Scan with IndexName=<gsi> and ConsistentRead=True -> observe HTTP 501 / NotImplemented instead of HTTP 400 ValidationException; confirm the same Scan without ConsistentRead and a ConsistentRead Scan of the base table are the success cases.
