# kinesis-video: 4 net-new root causes — the PutMedia ingest data plane is not served at all (404 UnknownService), GetDataEndpoint hands back the control-plane host for every APIName, an unrouted path is refused as JSON UnknownService instead of <UnknownOperationException/>, and the archive/media planes cannot see a stream CreateStream made

> _Note: this issue was identified against the code base at commit `42eb24959c6a4eb33ac3ba3d48b702ee83f6032d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMedia

## Description
Four net-new root causes in the Kinesis Video Streams data plane. The control plane answers (CreateStream/DescribeStream reach ACTIVE, GetDataEndpoint returns 200), so every one of the 24 failing kinesis-video behavioral checks is a fidelity divergence, not a bootstrap gap. Cause 4 is the same root cause an already-open issue describes for a sibling service (20261022T180000Z-kinesis-video-media-getmedia-cannot-see-a-stream-createstream-made.md, filed against service kinesis-video-media); it is reported here because these two kinesis-video checks fail on it and the suite did not mark them owned.

=== Cause 1 of 4: GetDataEndpoint returns the control-plane host for every APIName, so there is no data plane to reach ===
AWS: Smithy kinesisvideo#GetDataEndpoint, POST /getDataEndpoint, input APIName (required enum: GET_CLIP | GET_DASH_STREAMING_SESSION_URL | GET_HLS_STREAMING_SESSION_URL | GET_IMAGES | GET_MEDIA | GET_MEDIA_FOR_FRAGMENT_LIST | LIST_FRAGMENTS | PUT_MEDIA), output DataEndpoint. The model documents the purpose as "Gets an endpoint for a specified stream for either reading or writing ... The returned endpoint does not have the API name appended." The whole reason the operation exists is that the media planes do NOT live on the control-plane host: the returned DataEndpoint is a bare https host (no path) that differs from the control-plane endpoint; all ingest APIs (PUT_MEDIA) share one host, all archive/read APIs (GET_MEDIA, GET_MEDIA_FOR_FRAGMENT_LIST, LIST_FRAGMENTS, GET_CLIP, GET_HLS_STREAMING_SESSION_URL, GET_DASH_STREAMING_SESSION_URL, GET_IMAGES) share another, and the two groups are different hosts. A data host also serves only its own plane: a control-plane call such as DescribeStream sent to a media host is refused UnknownOperationException with NO message member at all.
Emulator: the handler ignores APIName entirely and echoes back the host the request arrived on — services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/ops/get_data_endpoint.rs returns `data_endpoint: Some(crate::state::request_endpoint(ctx.parts(), &region))` after only resolving the stream. Replay shows GetDataEndpoint(PUT_MEDIA) handing back the very control-plane host the call was made on, and the PUT_MEDIA and the archive endpoints coming back as one identical host:port, so ingest and archive are indistinguishable.
Why: a client that follows the documented flow (GetDataEndpoint, then address the returned host) is sent straight back to the control plane, where no media operation is routed — which is exactly what Cause 2 then reports as a 404. Producer SDKs (the KVS C/Java producer, GStreamer kvssink) are unusable, and nothing can distinguish ingest from archive or detect a call aimed at the wrong plane.
Fix: the GetDataEndpoint handler plus the engine's endpoint/host mapping for the kinesis-video family — it must mint a per-plane (ingest vs archive) data host per the requested APIName, distinct from the control-plane host, and those hosts must serve only their own plane's operations (a control-plane operation there answers UnknownOperationException with no message).

=== Cause 2 of 4: PutMedia is not served anywhere — every ingest attempt is refused 404 UnknownService instead of a 200 acknowledgement stream ===
AWS: recorded behavior only — PutMedia is in no SDK model (com.amazonaws.kinesisvideo declares 32 operations, none of them PutMedia; com.amazonaws.kinesisvideomedia declares GetMedia only), so this is the recorded ingest front end. The recording shows: POST /putMedia to the PUT_MEDIA data host, SigV4-signed over the literal string UNSIGNED-PAYLOAD with the header x-amz-content-sha256 present and signed, headers x-amzn-stream-name (or x-amzn-stream-arn), x-amzn-fragment-timecode-type (RELATIVE|ABSOLUTE) and x-amzn-producer-start-timestamp, body a Matroska document where ONE Cluster is ONE fragment. The response is HTTP 200 whose body is a stream of JSON Acknowledgement objects: one PERSISTED acknowledgement per accepted cluster carrying FragmentNumber and FragmentTimecode, and under ABSOLUTE the acknowledged FragmentTimecode is the epoch-millisecond cluster timecode that was sent. Container-level faults are reported IN BAND as ERROR acknowledgements inside that same 200 (never as an HTTP error): a cluster timecode moving backwards is ErrorCode FRAGMENT_TIMECODE_LESSER_THAN_PREVIOUS with ErrorId 4004 and FragmentTimecode naming the offending cluster's own timecode, the session is torn down at that cluster so no PERSISTED acknowledgement follows it, and clusters accepted before it survive in the archive; a malformed container, a SimpleBlock on an undeclared track number, and a producer start timestamp in the future are likewise in-band ERROR acknowledgements. Request-level faults are HTTP errors: a stream name no stream has is 404 ResourceNotFoundException (x-amzn-ErrorType: ResourceNotFoundException), a missing x-amz-content-sha256 header is 403 InvalidSignatureException, and media naming a stream other than the one this ingest host was handed out for is refused rather than ingested. Fixed text is the error code/ErrorCode token and ErrorId; the variable parts are the stream name from the request headers, the FragmentNumber the service mints and the FragmentTimecode read from the cluster.
Emulator: there is no /putMedia route and no handler — the front door answers HTTP 404 with x-amzn-ErrorType: UnknownService and body {"__type":"UnknownService","message":"no emulated service is registered for 'kinesisvideo'"} (some ports answer the same 404 with an empty body). services/service-com-amazonaws-kinesisvideomedia-awsacuityinletservice/src/state.rs states it outright: the only writer of the fragment log is the internal put_fragment helper, and "The producer side of the same data (PutMedia) belongs to the sibling kinesisvideo service, whose handlers are all still scaffolded". So no fragment can ever be produced, and the read side (GetMedia, GetMediaForFragmentList, ListFragments) can only ever be tested against an empty stream — four read-path checks fail on the PutMedia 404 before they reach the read they exist to make.
Why: the entire producer half of Kinesis Video Streams is unavailable. No client can get media into a stream, so nothing can be read back, no fragment metadata exists, and every producer-side validation contract (timecode ordering, track declaration, timestamp sanity, signing requirements) is silently absent rather than enforced. A caller sees UnknownService, an error Kinesis Video Streams never returns, instead of either a 200 ack stream or a modeled refusal.
Fix: the ingest data plane needs an implementation — a /putMedia route on the PUT_MEDIA data host (Cause 1) whose handler parses the Matroska container cluster by cluster, appends each cluster to the stream's fragment log as the one shared registry record (Cause 4), and streams back PERSISTED/ERROR acknowledgements with the codes and ids above, plus the request-level refusals (ResourceNotFoundException for an unknown stream, InvalidSignatureException for a missing x-amz-content-sha256, refusal for a stream this host was not handed out for).

=== Cause 3 of 4: a path no operation is bound to is refused as a JSON UnknownService with an x-amzn-ErrorType header, instead of the bare <UnknownOperationException/> body with no error-type header ===
AWS: recorded behavior only. Posting /putMedia at the CONTROL-plane host (which routes no such path) is refused before any operation is identified: HTTP 404, NO x-amzn-ErrorType response header at all, and the body is exactly the bare XML element <UnknownOperationException/> — fixed text, no message and no variable part. The media must also not reach the stream: the archive still lists no fragments afterwards.
Emulator: the status is right (404) but the shape is invented — the response carries x-amzn-ErrorType: UnknownService and a JSON body {"__type":"UnknownService","message":"no emulated service is registered for 'kinesisvideo'"}. Both the error-type header and the body differ: UnknownService is not an error Kinesis Video Streams (or any AWS front door) returns for an unrouted path, and the message text is emulator-internal prose naming its own service registry.
Why: a client or SDK that probes an endpoint to decide which plane it is talking to reads a per-operation error type where AWS reports none, and parsers that match the documented <UnknownOperationException/> body see JSON. Emulator-internal wording ("no emulated service is registered for ...") also leaks into a client-visible response.
Fix: the front-door router's no-route refusal path for this family — when no operation is bound to the requested path, answer 404 with the bare <UnknownOperationException/> body and emit no x-amzn-ErrorType header, rather than synthesising an UnknownService JSON error from the request's signing name.

=== Cause 4 of 4: the archive and media planes keep their own stream registries, so a stream CreateStream made is ResourceNotFoundException there ===
AWS: Smithy kinesisvideoarchivedmedia#ListFragments (POST /listFragments) and kinesisvideomedia#GetMedia both model ResourceNotFoundException (HTTP 404) as "Amazon Kinesis Video Streams can't find the stream that you specified" — i.e. only for a stream that does not exist. One stream is ONE resource: kinesisvideo:CreateStream creates it and the data planes reached through GetDataEndpoint read THAT stream by the same StreamName/StreamARN. A created stream that holds no media is therefore an EMPTY read, not a 404: ListFragments returns Fragments: [] and GetMedia returns 200 with Content-Type video/webm and an empty payload.
Emulator: for a stream just created on the control plane and polled to ACTIVE, ListFragments answers 404 ResourceNotFoundException with message "No such stream: StreamName <name>" and GetMedia answers 404 ResourceNotFoundException with message "No such stream: <name>." (the two planes do not even word it the same way; the stream name is the only variable part). The cause is that each crate owns a separate registry — the control plane writes ComAmazonawsKinesisvideoKinesisvideo20170930State::streams while services/service-com-amazonaws-kinesisvideomedia-awsacuityinletservice/src/state.rs and the archived-media crate each hold their own streams/arn_index maps that nothing on the control plane writes.
Why: the documented create-then-read flow is impossible — a client cannot distinguish "stream exists but is empty" from "stream does not exist", DeleteStream cannot make a data plane forget a stream, and the two planes can mint different StreamARNs for one name. Already described for the sibling service in open issue 20261022T180000Z-kinesis-video-media-getmedia-cannot-see-a-stream-createstream-made.md; these two kinesis-video checks are additional grounding, and the empty-read behavior (Fragments: [] / empty video/webm payload) is part of the requirement.
Fix: one shared stream registry for the kinesis-video family (the control-plane record is the resource; each data plane keeps only its per-stream media keyed by that identity, with the ARN minted in exactly one place), so the read paths answer an empty result for a created-but-empty stream and ResourceNotFoundException only for a stream the registry does not hold.
