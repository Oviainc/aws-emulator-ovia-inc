# autoscaling: 3 net-new causes — a SkipMatching instance refresh still replaces the matching instance, and SetInstanceProtection's oversized-list and non-member refusals diverge in code and wording

> _Note: this issue was identified against the code base at commit `e88affa0c81a58fb8423ccb328f6804dccd04335`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetInstanceProtection

## Description
Three net-new root causes in the Auto Scaling control plane, all surfaced by behavioral checks the suite lists under `### autoscaling`. One is a data-plane effect defect (an instance refresh that must be a no-op replaces the group's instance), two are client-error fidelity defects on SetInstanceProtection (wrong error code on the oversized-list refusal, emulator-authored sentence on the non-member refusal). This bundle carries 3 causes and ALL 3 must be closed before submitting.

Cause 1 of 3: StartInstanceRefresh with Preferences.SkipMatching=true replaces the instance that already matches the desired configuration.
AWS: Smithy com.amazonaws.autoscaling#RefreshPreferences member SkipMatching is documented '(Optional) Indicates whether skip matching is enabled. If enabled (true), then Amazon EC2 Auto Scaling skips replacing instances that match the desired configuration. If no desired configuration is specified, then it skips replacing instances that have the same launch template and instance types that the Auto Scaling group was using before the start of the instance refresh. The default is false.' So when StartInstanceRefresh is given Strategy=Rolling plus a DesiredConfiguration naming the SAME launch template the group is already running (version $Latest) and SkipMatching=true, every in-service instance matches and NONE is replaced: the refresh still runs to completion and DescribeInstanceRefreshes reports Status=Successful, PercentageComplete=100, InstancesToUpdate=0 and a non-null EndTime, while the group's set of InService instance ids is byte-for-byte the set that existed before the refresh started. The group's membership is the requirement here — skip matching exists precisely so that a no-change refresh costs no instance churn.
Emulator: the refresh's terminal representation is right (the check's asserts on Status=Successful, PercentageComplete=100, InstancesToUpdate=0 and EndTime all pass), but the group's InService instance-id list afterwards is NOT the pre-refresh list — the emulator's refresh engine replaced (or dropped) the matching instance anyway, so the check fails on `assert _in_service_ids(as_, name) == [original]` with 'a fully-matching refresh must not replace the existing instance'. The SkipMatching preference is recorded and echoed back but never gates replacement.
Why: a client that uses SkipMatching to make a redeploy idempotent — the documented pattern for 'refresh only what drifted' — sees its whole fleet cycled on every call. In-flight work on those instances is destroyed, connection draining and warmup budgets are spent, and the InstancesToUpdate=0 the API reports contradicts the churn the caller actually observes, so there is no signal a client could use to detect the divergence.
Fix: the StartInstanceRefresh handler's refresh engine (and the state it drives instance replacement from) — Preferences.SkipMatching must be evaluated against DesiredConfiguration (and, when DesiredConfiguration is absent, against the group's current launch template and instance types) and must exclude matching instances from replacement, so a fully-matching refresh completes without touching group membership.
Traces: behavioral check autoscaling.instance-refresh-skip-matching-completes-successfully. Related but NOT covering: open issues 20261108T052358Z-autoscaling-startinstancerefresh-creates-an-already-terminal-refresh-describeinstancerefreshes-reports.md (refresh is terminal immediately, never InProgress) and 20261108T203125Z-autoscaling-ec2-elbv2-startinstancerefresh-reports-successful-without-ever-terminating-the-instances.md (the opposite effect: no replacement at all) — neither carries this check, and neither concerns the SkipMatching gate.

Cause 2 of 3: SetInstanceProtection refuses an InstanceIds list longer than 50 with the wrong error code (LimitExceeded instead of ValidationError).
AWS: Smithy com.amazonaws.autoscaling#SetInstanceProtection requires InstanceIds, AutoScalingGroupName and ProtectedFromScaleIn, and models exactly two errors — LimitExceededFault (awsQueryError code 'LimitExceeded', HTTP 400) and ResourceContentionFault (code 'ResourceContention', HTTP 500). LimitExceededFault is documented 'You have already reached a limit for your Amazon EC2 Auto Scaling resources (for example, Auto Scaling groups, launch configurations, or lifecycle hooks)' — an ACCOUNT-resource-limit condition, not a request-shape one. The documented per-call cap of 50 instance ids is therefore enforced as the awsQuery service-common parameter-validation fault: HTTP 400, Code 'ValidationError', Type 'Sender', Message 'Exceeded maximum allowed instances to protect simultaneously; can provide at most 50 instances.' That sentence is entirely fixed text apart from the cap (50), which is the documented per-call limit, not a value from the request. The count check runs BEFORE any per-id membership validation (none of the 51 fabricated ids belongs to the group, and AWS still reports the count defect), and the rejected call changes no instance's ProtectedFromScaleIn flag.
Emulator: HTTP 400 with Code 'LimitExceeded' — the account-limit fault — so the check fails at `assert code == "ValidationError", f"expected ValidationError, got {code}"` with 'expected ValidationError, got LimitExceeded'. (The message assertion is never reached, so the message must be brought in line with AWS's sentence above as part of this fix.)
Why: the two codes mean opposite things to a caller. 'ValidationError' says 'your request is malformed — split the ids into batches of 50 and retry'; 'LimitExceeded' says 'your ACCOUNT has run out of Auto Scaling resources', which is the family clients back off on, surface as a quota page, or escalate for a limit increase. A client batching protection updates is steered into retry/backoff on a request that can never succeed as sent, and never learns to chunk it.
Fix: the SetInstanceProtection handler's input validation — the InstanceIds count check must raise the service-common ValidationError (HTTP 400, Sender) with AWS's sentence, and must run ahead of group-membership resolution; LimitExceededFault must be reserved for account-resource limits.
Traces: behavioral check autoscaling.op-contract-set-instance-protection. Related but NOT covering: open issues 20261110T100847Z-autoscaling-refusal-fidelity-wrong-codes-and-emulator-authored.md and 20261107T124656Z-autoscaling-auto-scaling-argument-validation-never-happens-8-operations.md — neither names SetInstanceProtection nor carries this check's replay key.

Cause 3 of 3: SetInstanceProtection's non-member-instance refusal serves an emulator-authored sentence that omits the group name.
AWS: an instance id that is not a member of the named Auto Scaling group is refused HTTP 400, Code 'ValidationError', with Message 'The instance <instance-id> is not part of Auto Scaling group <group-name>.' Fixed text of that template: 'The instance ' + ' is not part of Auto Scaling group ' + '.' (one instance id per sentence, terminated by a period). The two variable parts come from the request: <instance-id> is the offending entry of InstanceIds and <group-name> is the request's AutoScalingGroupName. Smithy models only LimitExceededFault and ResourceContentionFault on SetInstanceProtection, so the membership failure is the awsQuery service-common ValidationError; recorded behavior supplies the sentence. The refusal has no effect: the non-member id does not join the group, and a real member's ProtectedFromScaleIn flag set by an earlier successful call stays as it was.
Emulator: the code is right ('ValidationError') but the message is 'Trying to update Instances that are not part of the group: i-0123456789abcdef0' — a sentence AWS never emits. It renames the subject ('Trying to update Instances' instead of 'The instance ...'), drops the group name entirely, replaces the terminating period with a colon-plus-id-list, and pluralises the instance clause. The check fails on `assert message == expected` with: expected 'The instance i-0123456789abcdef0 is not part of Auto Scaling group <group-name>.', got 'Trying to update Instances that are not part of the group: i-0123456789abcdef0'.
Why: the message is part of the API contract for this refusal class. A client or operator reading the refusal is not told WHICH group the instance is missing from — the single most useful fact when the same id is being protected across several groups — and any exact-match assertion or log-scraping rule written against AWS's wording fails against the emulator.
Fix: the SetInstanceProtection handler's membership validation, in the ValidationError message template it formats (one sentence per offending id, in AWS's phrasing, interpolating the request's AutoScalingGroupName).
Traces: behavioral check autoscaling.set-instance-protection-foreign-instance-fails. Related but NOT covering: 20261110T100847Z-autoscaling-refusal-fidelity-wrong-codes-and-emulator-authored.md (six other operations' refusal wording) and 20261107T071147Z-autoscaling-auto-scaling-argument-validation-refusals-use-the-wrong.md — neither carries this check.
