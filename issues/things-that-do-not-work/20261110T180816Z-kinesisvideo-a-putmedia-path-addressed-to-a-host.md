# kinesisvideo: a /putMedia path addressed to a host that does not route it is refused HTTP 400 with the front door's {"Output":{...},"Version":"1.0"} envelope instead of HTTP 404 with the bare <UnknownOperationException/> body

None of them carries the replay key of either check below.

=== Cause 1 of 1: the kinesisvideo family serves ONE unknown-operation envelope (HTTP 400, awsJson-style {"Output":{"__type":"...#UnknownOperationException","Message":"Unable to determine operation name"},"Version":"1.0"}) for every unroutable request, so POST /putMedia addressed to a host that does not route the ingest plane — the control-plane endpoint, or the data endpoint announced for LIST_FRAGMENTS — is refused 400 with that JSON envelope instead of HTTP 404 with the body <UnknownOperationException/> ===
AWS: recorded behavior only. PutMedia is in no SDK model: Smithy com.amazonaws.kinesisvideo#KinesisVideo_20170930 (restJson1, sigv4Name kinesisvideo, 32 operations) binds the control routes (POST /createStream, /describeStream, /getDataEndpoint, ...) and binds NO /putMedia at all, and com.amazonaws.kinesisvideoarchivedmedia#AWSAcuityReader (restJson1, 6 operations: POST /listFragments, /getMediaForFragmentList, /getHLSStreamingSessionURL, ...) binds no /putMedia either; UnknownOperationException is likewise a modeled shape of neither. The recordings show how a kinesisvideo-family endpoint refuses a PATH it binds no operation for: HTTP 404, NO x-amzn-ErrorType response header (no operation was identified, so no shape of a service is named), and a response body that is exactly the bare element <UnknownOperationException/> — that element is the whole fixed text of the refusal and it interpolates nothing from the request: no stream name, no path, no operation name, no message member. The same 404/<UnknownOperationException/> refusal is recorded on the control-plane host and on the data endpoint announced for LIST_FRAGMENTS (the second check grades only that the status is 404 and the body names UnknownOperationException, which the recorded body satisfies). Nothing is archived by a refused request, on either host.
Emulator: both hosts answer HTTP 400 with the front door's JSON envelope and no x-amzn-ErrorType. The status, the type string and the sentence are module constants and one renderer serves every address: services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/service/unknown_operation.rs declares UNKNOWN_OPERATION_STATUS = 400, UNKNOWN_OPERATION_TYPE = "com.amazon.kinesis.video.v20170930#UnknownOperationException" and UNKNOWN_OPERATION_MESSAGE = "Unable to determine operation name", and unknown_operation_response() builds that 400 with content-type application/json and no error-type header; its own module doc states the intent ("Why ONE wording serves every address"), and src/service/data_plane_address.rs:74-76 (unrouted_address_response) forwards the data-plane case straight to it. Replay: against the control host, `the control-plane host does not route /putMedia, so it must answer 404; it answered HTTP 400 (x-amzn-ErrorType None): b'{"Output":{"__type":"com.amazon.kinesis.video.v20170930#UnknownOperationException","Message":"Unable to determine operation name"},"Version":"1.0"}'`; against the archive host, `PutMedia against the archive host expected HTTP 404, got 400`, with the identical envelope parsed out of the body. The absent x-amzn-ErrorType is already correct; the status and the body are not.
Why: a producer cannot distinguish "you are talking to the wrong host, re-discover the endpoint" from "your request was malformed". 404 is the signal a KVS producer branches on to call GetDataEndpoint again and retry the fragment; a 400 is a client-fault class that SDK and application retry logic treats as non-retryable, so the documented re-discovery loop never fires and the media is dropped. A client that parses the refusal body for the element AWS returns sees a JSON envelope naming a namespace (com.amazon.kinesis.video.v20170930) that no model declares, so wrong-host handling written against AWS does not fire against the emulator either. This also makes the cross-plane isolation of announced data endpoints unverifiable from the client side.
Fix: the family's unroutable-path refusal rendering — services/.../src/service/unknown_operation.rs and the data-plane seam that reuses it (src/service/data_plane_address.rs) — must distinguish a media path arriving at a host that does not route its plane from the front door's undeterminable-operation case: refuse POST /putMedia (and the symmetric /getMedia) on the control-plane endpoint and on an announced endpoint of another plane with HTTP 404, body exactly <UnknownOperationException/>, no x-amzn-ErrorType header, and no state change (nothing buffered, acknowledged or archived). The existing 400 envelope must stay where the recordings put it, so the change belongs in that seam's classification and not in a blanket status swap.
Traces: kinesisvideo.put-media-against-control-plane-host-rejected (control-plane host), kinesisvideo.putmedia-on-the-archive-endpoint-rejected (LIST_FRAGMENTS data endpoint).
