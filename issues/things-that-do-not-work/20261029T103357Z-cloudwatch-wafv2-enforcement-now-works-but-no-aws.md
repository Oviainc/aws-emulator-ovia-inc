## Description

Failing check: cloudwatch__wafv2.blocked-and-counted-requests-carry-the-webacl-and-rule-dimensions

AWS: a rule in a web ACL whose VisibilityConfig.CloudWatchMetricsEnabled is true publishes its action counters to the CloudWatch namespace AWS/WAFV2 under the dimensions WebACL, Rule and Region together, where the Rule dimension value is that rule's VisibilityConfig.MetricName: BlockedRequests for each request a terminating Block rule refused and CountedRequests for each request a Count rule matched (Count does not terminate), with Sums equal to the exact number of requests each rule acted on, and with the CloudWatch Unit "None" on the datapoints; ListMetrics for that WebACL reports a dimension set containing WebACL, Rule and Region together; a rule with CloudWatchMetricsEnabled=false publishes no datapoint at all while still enforcing. Smithy (services/service-com-amazonaws-wafv2-awswaf-20190729/smithy-model/...json): VisibilityConfig.CloudWatchMetricsEnabled (Boolean, required, "Indicates whether the associated resource sends metrics to Amazon CloudWatch") and VisibilityConfig.MetricName (required, @length 1..255, pattern ^[\w#:\.\-/]+$, documented as "A name of the Amazon CloudWatch metric dimension") are the modeled switches for this emission. Smithy (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/smithy-model/...json): GetMetricStatistics takes Namespace/MetricName/StartTime/EndTime/Period (required) plus Dimensions (@length 0..30) and Statistics, and returns Datapoints; ListMetrics takes Namespace + Dimensions filters and returns Metrics with their Dimensions. The AWS/WAFV2 namespace, the metric names and the Unit "None" are recorded behavior only (the WAF metric pipeline is not Smithy-modelled); what is structural is that a rule with CloudWatchMetricsEnabled=true produces a per-rule series a customer can read back, and that its Sum equals the traffic that rule acted on.

Emulator: after the 7 blocked / 3 counted / 5 quiet requests were enforced, repeated GetMetricStatistics(Namespace=AWS/WAFV2, MetricName=BlockedRequests|CountedRequests, Dimensions WebACL=<acl name>/Rule=<that rule's MetricName>/Region=<region>, Period=60, Statistics=[Sum,SampleCount]) never yields datapoints whose summed Sum reaches 7 and 3; the poll's predicate also requires a non-empty Datapoints list for BOTH series (the check maps an empty Datapoints to None), so no readable per-rule AWS/WAFV2 series appeared at all in the window. Replay detail: `TimeoutError: AWS/WAFV2 BlockedRequests for Rule=<blocked rule MetricName> and CountedRequests for Rule=<counted rule MetricName> under WebACL=<acl name> reaching at least 7 and 3: the run budget ended first; not graded`, raised from the check's `_poll_until` at line 160. The wait ended on the runner's remaining time rather than on the check's own 600 s metric budget, because the enforcement legs consumed the run window — so the absence is observed over the remainder of the run rather than over a full propagation budget. What is grounded is that the emulator served every enforcement request and published nothing readable for those rules in that window. Hypothesis: the WAFv2 inspection hook that now terminates requests has no AWS/WAFV2 metric publisher behind it, so neither BlockedRequests nor CountedRequests is ever written into the CloudWatch metric store, and the WebACL/Rule/Region dimension set never exists.

Why: a client that fronts an API with WAF has no way to see what WAF did. BlockedRequests/CountedRequests under WebACL+Rule+Region is the only evidence a customer has of WHICH rule acted — and for a Count-mode rule, whose request is allowed through, the metric is the ONLY evidence the rule matched at all. Dashboards, alarms on a 4xx/blocked spike, and any CloudWatch-driven automation built on AWS/WAFV2 read empty against the emulator, so a negative security/observability test passes while production would alarm. CloudWatchMetricsEnabled is also indistinguishable from decoration today: publishing nothing, publishing only a per-web-ACL total, and publishing regardless of the flag all look the same.

Fix: the AWS/WAFV2 metric publisher behind the execute-api WAFv2 inspection hook — on each inspected request the emulator must write, into the same CloudWatch metric store GetMetricStatistics/ListMetrics read, BlockedRequests for the terminating Block rule and CountedRequests for the matched Count rule, dimensioned WebACL=<web ACL name>, Rule=<the acting rule's VisibilityConfig.MetricName> and Region=<region> together, with Unit "None", and must write nothing for a rule whose VisibilityConfig.CloudWatchMetricsEnabled is false; the per-web-ACL aggregate series (the web ACL's own VisibilityConfig.MetricName) belongs in the same publisher. No change is needed in the enforcement path, which now behaves.
