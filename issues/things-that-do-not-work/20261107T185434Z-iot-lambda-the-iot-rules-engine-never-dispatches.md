=== Cause 1 of 7: an ENABLED topic rule whose action is `lambda` never invokes the target function on a matching MQTT publish ===
Failing check ids: iot__lambda.iot-rule-lambda-action-positive, iot__lambda.iot-rule-action-role-trusts-iot-service-positive, iot__lambda.iot-rule-disabled-no-invocation-negative, iot__lambda.iot-rule-disabled-rule-no-invocation-negative, iot__lambda.iot-rule-lambda-missing-invoke-permission-negative, iot__lambda.iot-rule-lambda-wrong-arn-negative, iot__lambda.iot-rule-lambda-wrong-source-arn-negative, iot__lambda.iot-rule-action-role-wrong-trust-negative, iot__lambda.iot-topicrule-create-with-untrusted-role-negative, iot__lambda.cli-iot-create-topic-rule-lambda-invoke, iot__lambda.cli-iot-delete-topic-rule-then-publish-no-invoke-negative, iot__lambda.cli-lambda-add-permission-wrong-principal-negative.
AWS: Smithy (com.amazonaws.iot) models TopicRulePayload with required `sql` and required `actions` (ActionList, @length 0..10) and an optional boolean `ruleDisabled`; Action.lambda targets LambdaAction, whose only member `functionArn` is @required and documented "Invoke a Lambda function". CreateTopicRule therefore registers a rule that, for every message published to a topic the rule's SQL FROM clause matches and whose WHERE clause it satisfies, invokes the named function once per matched message with the SQL-projected document as the invocation event, provided the target function's resource policy allows Principal=iot.amazonaws.com to lambda:InvokeFunction for SourceArn=arn:aws:iot:<region>:<account>:rule/<ruleName>. Recorded behavior only for the gating details (the model does not describe dispatch): the effect is observable through the invoked function's own side effects, the invocation is suppressed when `ruleDisabled` is true, when the rule has been deleted, when the functionArn names no function, and when the function's policy grants no matching statement (wrong Principal or wrong SourceArn). The data-plane trigger is iot-data Publish, POST /topics/{topic} (topic @httpLabel @required, qos @httpQuery range 0..1 default 0, payload @httpPayload), which answers HTTP 200 with an empty body.
Emulator: CreateTopicRule (both through the SDK and through the `aws iot create-topic-rule` CLI), lambda:AddPermission and iot-data Publish are all accepted, but no invocation ever happens. Every one of these twelve checks fails on its POSITIVE half, with the harness assertion `expected the lambda action to forward the message to SQS` / `matching queue message not met within 90s. Last result: []` / `expected the IoT rule's lambda action to deliver a message via SQS` / `positive control: correctly-scoped pairing must deliver` / `positive control: permissioned pairing must deliver` / `expected the positive control (rule enabled) to succeed` / `expected the positive control (correct ARN) to succeed`. No API response reports a failure: the publish is answered 200 and the rule reads back as it was created.
Why: a client gets a rule that the control plane says exists and is enabled while the data plane routes nothing, so the core IoT ingestion shape (device publish -> rule -> Lambda) is dead with no error anywhere to diagnose it. Worse for the negatives: because the positive control is also silent, every guardrail these checks exist to prove — ruleDisabled suppression, deleted-rule suppression, a wrong functionArn, a wrong SourceArn, a missing lambda:InvokeFunction grant, a wrong Principal, and an action role that does not trust iot.amazonaws.com — passes vacuously. An under-permissioned or disabled deployment is indistinguishable from a correctly wired one, so IoT->Lambda authorization regressions cannot be caught at all.
Fix: the topic-rule matching and action-dispatch path of the iot service reached from the IoT data plane's Publish handler, plus the authorization gate it must consult on the lambda crate's stored function resource policy (Principal and SourceArn) and on the rule's own role trust, so that a permitted action invokes and an unpermitted or disabled one deliberately does not.
Traces: the twelve check ids above (all verdict mismatch).

=== Cause 2 of 7: a rule's `errorAction` Lambda is never executed when the primary action fails ===
Failing check ids: iot__lambda.iot-rule-error-action-lambda-positive, iot__lambda.cfn-deploy-iot-rule-error-action-lambda-positive.
AWS: Smithy models TopicRulePayload.errorAction as an `Action`, documented "The action to take when an error occurs". When a matched rule's primary action cannot be executed — here a `lambda` action whose functionArn names a function that does not exist — IoT executes the rule's errorAction instead and invokes the fallback function with a rule-failure event. Recorded behavior only for that event's shape (neither the iot nor the lambda model describes it): it carries `ruleName` (the rule's name as created), `topic` (the topic published to), `base64OriginalPayload` (base64 of the exact published payload bytes) and a non-empty `failures` list whose first element has a non-empty `errorMessage`. All of the variable parts come from the request and the rule's stored definition; none of them is fixed text.
Emulator: nothing is dispatched. The publish is answered 200 and the fallback function's sink stays empty until the poll window closes: `AssertionError: expected the errorAction to forward an error report to SQS` and `AssertionError: fallback errorAction invocation delivered not met within 90.0s. Last result: []`.
Why: a client that uses errorAction as its dead-letter path for rule failures gets total silence — the primary action's failure is reported neither in any API response nor through the one channel AWS provides for it, so IoT error handling cannot be exercised at all.
Fix: the same rule-action dispatcher as Cause 1 — when an action's execution fails it must build the rule-failure event above and execute the rule's stored `errorAction` instead of discarding the failure.
Traces: the two check ids above (both verdict mismatch).

=== Cause 3 of 7: a `republish` action does not re-inject the message, so a two-hop rule chain never reaches the second rule ===
Failing check id: iot__lambda.iot-rule-republish-chain-lambda-positive.
AWS: Smithy models Action.republish as RepublishAction with required `roleArn` and required `topic` and optional `qos` (range 0..1, default 0), documented "Publish to another MQTT topic". A message matched by rule A is therefore republished to rule A's configured topic as a new broker message, which rule B's own SQL FROM clause then matches, running rule B's `lambda` action with the republished document.
Emulator: the chain never completes — `AssertionError: expected the republished message to reach rule B's lambda action`. Both rules are created successfully and the publish to topic A answers 200, but nothing appears on topic B and rule B never fires.
Why: a client that fans out or normalizes traffic with a republish hop (the standard IoT pattern for staging a topic before a downstream rule) loses every message silently; no API call reports the drop.
Fix: the rule-action dispatcher must treat a `republish` action as a new publish into the same broker/matching path (honouring the action's `topic` and `qos`) so downstream rules match it, rather than terminating the message at the first rule.
Traces: iot__lambda.iot-rule-republish-chain-lambda-positive (verdict mismatch).

=== Cause 4 of 7: the rule SQL projection and WHERE filter are never applied, because no event is ever produced to carry them ===
Failing check ids: iot__lambda.iot-rule-lambda-payload-data-format, iot__lambda.iot-rule-sql-filter-lambda-positive.
AWS: TopicRulePayload.sql is @required and is an IoT SQL statement. A SELECT list with computed expressions and aliases, and the `topic()` function, define EXACTLY the JSON document delivered to the action: only the selected/aliased keys are present, unselected members of the published payload are dropped, arithmetic is evaluated, and `topic()` resolves to the topic the message was published to. A WHERE clause selects which published messages run the action at all.
Emulator: no event is ever delivered, so neither the projection nor the filter is observable: `AssertionError: expected the transformed event to be forwarded to SQS` and `AssertionError: matching queue message not met within 90s. Last result: []`. The SQL is accepted by CreateTopicRule and read back unchanged, so the control plane asserts a projection the data plane never performs.
Why: a client relying on rule SQL to shape and filter payloads cannot tell a correct projection from no projection at all; a rule that would over- or under-select in AWS looks identical here, so payload-contract regressions in downstream consumers are undetectable.
Fix: once Cause 1's dispatcher invokes actions, the rules engine's SQL evaluation in the iot service must project the published payload through the SELECT list (expressions, aliases, and the `topic()` builtin) and gate dispatch on the WHERE clause, and pass that projected document as the action's event.
Traces: the two check ids above (both verdict mismatch).

Fix: Cause 1's dispatcher plus the CloudFormation resource handlers for AWS::IoT::TopicRule and AWS::Lambda::Permission, which must materialize the rule and the function resource-policy statement into the iot and lambda crates' state so the dispatcher's authorization gate sees them.

=== Cause 6 of 7: an UpdateStack that changes an AWS::Lambda::Function's Environment is never reflected in a later invocation ===

=== Cause 7 of 7: the in-Lambda AWS SDK shim knows no `iot` / `iot-data` service, so any handler that calls IoT dies with UnknownServiceError ===
