# AppConfigData GetLatestConfiguration re-resolves the configuration profile on every poll, so deleting the profile retroactively kills an already-active session token with ResourceNotFoundException

> _Note: this issue was identified against the code base at commit `c4171394ecd9e8acdff90bddf637ffaae1174b81`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetLatestConfiguration

## Description
One net-new root cause in the bootstrapped appconfigdata data plane, grounded in the replayed behavioral check appconfigdata.profile-deletion-does-not-immediately-break-active-session-token. Cause 1 of 1: GetLatestConfiguration treats the continued existence of the session's AppConfig control-plane resources as a precondition of EVERY poll, so a control-plane deletion made after the session was started retroactively invalidates a token that was already minted and already served.

AWS: GetLatestConfiguration (Smithy sdkId AppConfigData, restJson1, GET /configuration, success 200) takes exactly one input member, ConfigurationToken (@required, @httpQuery configuration_token, target Token, pattern ^\S{1,8192}$). The model's own documentation for ConfigurationToken/NextPollConfigurationToken states the only time bound on a token: "To support long poll use cases, the token is valid for up to 24 hours. If a GetLatestConfiguration call uses an expired token, the system returns BadRequestException." Nothing in the model makes a poll conditional on re-resolving the application / environment / configuration profile the session named; resource resolution is StartConfigurationSession's job (that is where ResourceNotFoundException with ResourceType/ReferencedBy belongs). Recorded behavior: with a session already started and already polled once, the check deletes the victim's hosted configuration version and then its configuration profile via the appconfig control plane, and the next poll on the session's NextPollConfigurationToken still SUCCEEDS with HTTP 200 and an empty Configuration payload (nothing new was deployed, so this is the modelled no-change answer: Configuration empty, ContentType/@httpHeader Content-Type and NextPollConfigurationToken/@httpHeader Next-Poll-Configuration-Token still present, VersionLabel empty per its own doc "If the client already has the latest version of the configuration data, this value is empty"). The profile's deletion is not re-checked on the poll path within the token's lifetime.

Emulator: the post-deletion poll is REFUSED with error code ResourceNotFoundException, HTTP 404, instead of answering 200 with an empty body. The refusal comes from the per-poll control-plane re-resolution: services/service-com-amazonaws-appconfigdata-appconfigdata/src/ops/get_latest_configuration.rs STEP 2 (lines 336-361) calls crate::state::served_configuration(engine, session.application_identifier, session.environment_identifier, session.configuration_profile_identifier, now) on every single poll and maps any unresolved level straight to GetLatestConfigurationErrorModeled::ResourceNotFoundException, with the message, ResourceType and ReferencedBy of whichever level no longer resolves. The message is the resolver's fixed per-level text naming the missing resource level (the sibling environment-deletion path in the same run produced "Environment not found"; the profile-deletion path names the configuration-profile level the same way) — its fixed part is the resource-level sentence and its variable parts are the identifiers taken from the stored session. The session's own STEP 1 checks (token known, not expired, poll floor satisfied) all pass, so the token is live: only the resource re-resolution refuses it.

Why: a client that is polling correctly loses its poll chain because of an UNRELATED control-plane edit. AWS's contract is that a configuration client holds one long-lived poll loop and only ever has to handle BadRequestException (restart the session) or a no-change 200; here a profile (or environment) deletion makes the loop raise a 404 that the client has no documented recovery for, and because no NextPollConfigurationToken is returned the chain cannot continue even once the resource is recreated. It also inverts the blast radius of a control-plane delete: in AWS an in-flight fleet keeps serving its last configuration, in the emulator every poller fails immediately. Negative/resilience tests asserting that a delete does not break live sessions pass against AWS and fail here.

Fix: the GetLatestConfiguration handler's STEP 2 resource-resolution path and the session state it reads — a token that resolves to a live, unexpired session must be served from what that session was last bound to, without making the continued existence of the application/environment/profile a per-poll precondition. Resolve the triple at StartConfigurationSession (where ResourceNotFoundException is the right refusal) and have the poll path answer the no-change 200 (empty Configuration, ContentType, rotated NextPollConfigurationToken, NextPollIntervalInSeconds) when the session's bound configuration can no longer be re-resolved but the session itself is valid; reserve ResourceNotFoundException on this operation for the case where a session was never bound to a deployed configuration at all.

Relationship to filed issues (neither covers this): open 20261024T112615Z-appconfigdata-data-plane-deployed-configuration-never-served-sessions.md owns a DIFFERENT refusal class on this operation — "No deployed configuration found for application ... environment ... and configuration profile ..." when nothing was ever served — and it owns the sibling check appconfigdata.environment-deletion-does-not-immediately-break-active-session-or-new-session via its replay key, so that check is skipped here. In this run the first polls of this very check SUCCEEDED and returned the deployed bytes, so the unreachable-configuration cause is not what refuses this call; the per-poll re-resolution of a DELETED resource is. Fixed 20261023T163610Z-appconfigdata-session-and-poll-surface-errors-lack-modeled.md and fixed 20261025T105131Z-appconfigdata-getlatestconfiguration-an-empty-configurationtoken-is-answered-with.md concern serving the deployed configuration and empty/reused-token verdicts respectively, not resource re-resolution on an active session.

## Steps to Reproduce
Boot the emulator and point an appconfig client and an appconfigdata client at its data listener (region and credentials are irrelevant).

1. Build two independent deployed hierarchies, 'control' and 'victim'. For each: create_application -> create_environment -> create_configuration_profile(LocationUri='hosted', Type='AWS.Freeform') -> create_hosted_configuration_version(Content=b'{"victim":true}' / b'{"control":true}', ContentType='application/json') -> create_deployment_strategy(DeploymentDurationInMinutes=0, GrowthFactor=100.0, FinalBakeTimeInMinutes=0, ReplicateTo='NONE') -> start_deployment and poll get_deployment until State == 'COMPLETE'.
2. appconfigdata.start_configuration_session(ApplicationIdentifier=..., EnvironmentIdentifier=..., ConfigurationProfileIdentifier=...) for both, and call get_latest_configuration once with each InitialConfigurationToken. Both must return the deployed bytes and a NextPollConfigurationToken (they do today).
3. Break exactly one thing on the victim, via the appconfig control plane: delete_hosted_configuration_version(ApplicationId, ConfigurationProfileId, VersionNumber) then delete_configuration_profile(ApplicationId, ConfigurationProfileId).
4. Call appconfigdata.get_latest_configuration(ConfigurationToken=<victim's NextPollConfigurationToken from step 2>). Expected: HTTP 200, Configuration payload empty (no new deployment since the last poll), a fresh Next-Poll-Configuration-Token header and Next-Poll-Interval-In-Seconds. Actual: refused with error code ResourceNotFoundException, HTTP 404, naming the configuration-profile level that no longer resolves.
5. Positive control: the untouched control session's next poll with its own NextPollConfigurationToken must still return HTTP 200 with an empty body — it does, which isolates the failure to the deleted resource's re-resolution.
6. Same shape with the environment instead of the profile (appconfig.delete_environment, then poll the victim's token) produces the same 404 with message 'Environment not found'; that variant's check is OWNED by 20261024T112615Z-appconfigdata-data-plane-deployed-configuration-never-served-sessions.md, so re-replay only appconfigdata.profile-deletion-does-not-immediately-break-active-session-token to confirm this fix.
