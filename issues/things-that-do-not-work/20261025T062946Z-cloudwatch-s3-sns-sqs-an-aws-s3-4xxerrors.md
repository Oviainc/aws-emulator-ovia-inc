# cloudwatch__s3__sns__sqs: an AWS/S3 4xxErrors alarm per FilterId never leaves INSUFFICIENT_DATA because the request metric never flows, so the alarm-to-SNS-to-SQS chain hangs to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `cfbb9a1e24eec7d8c98af7d6e9e62a0e8013f018`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlarms

## Description
Cause 1 of 1 — a CloudWatch metric alarm over AWS/S3 4xxErrors dimensioned [BucketName, FilterId] never reaches OK, so the real-404-driven OK->ALARM transition and its SNS->SQS notification are unobservable.
AWS: recorded behavior only for the metric emission (the Smithy model describes only the read/alarm surface: PutMetricAlarm with Namespace/MetricName/Dimensions/Statistic/Period/EvaluationPeriods/Threshold/ComparisonOperator/TreatMissingData, DescribeAlarms -> MetricAlarms[].StateValue, GetMetricStatistics -> Datapoints). The recording shows that once two prefix-filtered metrics configurations exist on a bucket and both prefixes receive successful GETs, both filters publish real AWS/S3 4xxErrors datapoints with Sum=0.0, so both alarms (TreatMissingData=notBreaching, Threshold=2.0, GreaterThanOrEqualToThreshold, Period=60, EvaluationPeriods=1) settle in OK; GETs of a missing key under the loud prefix only then drive that alarm OK->ALARM, which is recorded in DescribeAlarmHistory and published through the AlarmActions topic into the subscribed queue, while the control alarm on the other FilterId stays OK and its queue stays empty.
Emulator: the check's phase-1 barrier — `_poll_until(..., interval_s=60.0)` whose predicate is evaluated immediately on entry and requires DescribeAlarms to report both alarms OK AND GetMetricStatistics to return real 4xxErrors datapoints under BOTH FilterIds — is never satisfied on any pass, and the check is killed by the harness at 60s ('Error: Check timed out after 60.0s'). Every preceding call (CreateBucket, PutBucketTagging, PutBucketMetricsConfiguration x2, PutObject x2, CreateTopic, CreateQueue, GetQueueAttributes, SetQueueAttributes, Subscribe, PutMetricAlarm x2) succeeded, so the stall is at the metric/alarm-state stage, not at setup. Consistent with the sibling cloudwatch__s3 checks, which show that no AWS/S3 request metric is published at all.
Why: a client whose runbook is 'S3 4xx rate per prefix filter alarms into a queue' gets an alarm pinned in INSUFFICIENT_DATA, no notification on a real breach, and no way to distinguish a quiet prefix from an unimplemented metric — and a negative control built on the same mechanism can never be shown to be a true negative.
Fix: emit AWS/S3 request metrics (including a zero-valued 4xxErrors datapoint for an ACTIVE filter) from the S3 request path into the CloudWatch metric store (services/service-com-amazonaws-s3-amazons3 + services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801), and make the alarm evaluator grade those datapoints. Note for the fixer: once the barrier is satisfiable this check still needs more than one 60s period to drive a breach, so re-replay it with the check's own declared budget (timeout_s=1500) rather than the 60s cap.
Related open issues that do NOT carry this check's replay key: 20261025T020208Z-cloudwatch-alarms-never-evaluate-published-metric-data-no.md and 20261025T020208Z-cloudwatch-sns-sqs-cloudwatch-alarm-actions-never-fire-to-sns-so.md cover alarm evaluation/actions over caller-published PutMetricData metrics; neither names the AWS/S3 request-metric source this check's barrier waits on.

## Evidence
Expected (real-AWS recording): DescribeAlarms(AlarmNames=[loud, quiet], AlarmTypes=['MetricAlarm']) reports StateValue='OK' for both alarms, and GetMetricStatistics(Namespace='AWS/S3', MetricName='4xxErrors', Dimensions=[BucketName=<bucket>, FilterId=<loud|quiet>], Statistics=['Sum']) returns datapoints (Sum=0.0) for both FilterIds; then 404 GETs under the loud prefix move that alarm to ALARM and one notification arrives in the SQS queue, with the control alarm never in ALARM. Actual: the phase-1 barrier is never satisfied on any pass — the alarms do not report OK and no 4xxErrors datapoint exists under either FilterId — and the check is terminated: 'Error: Check timed out after 60.0s'.
