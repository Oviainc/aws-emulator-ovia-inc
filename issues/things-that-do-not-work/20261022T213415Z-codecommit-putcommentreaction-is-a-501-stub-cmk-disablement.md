# CodeCommit: PutCommentReaction is a 501 stub, CMK disablement is not enforced, and two error-message templates diverge (4 causes)

## Description
Four net-new root causes in the codecommit crate, all grounded in failing behavioral checks that the replay report left unmarked (not ALREADY FILED, not OWNED). Related-but-not-covering open issues are named per cause.

Cause 1 of 4: PutCommentReaction answers 501 NotImplemented where AWS returns a modeled 400 rejection for an unsupported reaction value.
AWS: Smithy PutCommentReaction takes commentId (@required, CommentId) and reactionValue (@required, ReactionValue) and models InvalidReactionValueException (client, httpError 400) among its errors; the operation doc states 'The value of the reaction is not valid.' A reactionValue that is not a supported emoji shortcode is refused with InvalidReactionValueException (HTTP 400), no reaction is recorded, and a later valid value (e.g. ':thumbsup:') succeeds and shows up in GetCommentReactions. Recorded message example: 'Unrecognized Reaction Value: <reactionValue>'.
Emulator: the call comes back with error code 'NotImplemented' (HTTP 501, 'operation PutCommentReaction is scaffolded but not implemented in this emulator'); services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/put_comment_reaction.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and its handle() returns Scaffolded::not_implemented. No per-operation stub issue exists for PutCommentReaction (the filed stub issues name BatchGetRepositories, CreateApprovalRuleTemplate, CreateBranch, CreateCommit, GetDifferences, GetRepositoryTriggers, PostCommentForComparedCommit, PutRepositoryTriggers, TagResource, UpdateRepositoryDescription), and the open issue '20261022T171422Z-codecommit-answers-501-notimplemented-where-aws-returns-a.md' does not list this check or this operation.
Why: a review/annotation client cannot distinguish a bad reaction value from an absent API, and the whole comment-reaction surface (PutCommentReaction/GetCommentReactions) is unusable.
Fix: implement the handler and its reaction-value validation in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/put_comment_reaction.rs (returning InvalidReactionValueException for an unrecognized shortcode), plus the reaction state it reads back.
Traces: codecommit.put-comment-reaction-invalid-value-rejected.

Cause 2 of 4: a repository's customer-managed KMS key is stored but never enforced — reads and writes are served while the key is Disabled.
AWS: Smithy models EncryptionKeyDisabledException (client, httpError 400) on GetBlob, GetFile, GetBranch, GetCommit and PutFile. With the CMK a repository was created under moved to KeyState 'Disabled', those paths are refused with EncryptionKeyDisabledException and serve no content; after enable_key the identical GetBlob hands back the original bytes and GetFile resolves the same blobId. (AWS does not enforce it on every individual request, which is why the check polls each path within a bounded window rather than sampling once.)
Emulator: the check never observes a refusal and runs past the harness budget — verdict 'mismatch', detail 'Check timed out after 60.0s'. The emulator accepts kmsKeyId on CreateRepository and echoes it back, but no read or write path consults the key's state. Hypothesis: GetBlob keeps succeeding, so the check's refusal poll (180 s deadline, 5 s sleeps) runs until the harness 60 s cap — a correctly-refusing implementation returns on the first poll iteration and the check completes well inside the budget.
Why: the entire point of pointing a repository at your own CMK is being able to cut access to its contents; an emulator that treats kmsKeyId as inert metadata lets key-revocation runbooks and break-glass tests pass against data that is still readable, and clients that handle EncryptionKeyDisabledException never see that path exercised.
Fix: the repository-level encryption-key check shared by the codecommit crate's read/write handlers (src/ops/get_blob.rs, get_file.rs, get_branch.rs, get_commit.rs, put_file.rs) and the repository state that records kmsKeyId, resolving the key's state against the kms service state.
Traces: codecommit.reads-blocked-when-the-repository-kms-key-is-disabled.

Cause 3 of 4: GetCommit's CommitIdDoesNotExistException message is not the request-derived template 'Could not retrieve <commitId>'.
AWS: Smithy models CommitIdDoesNotExistException (client, httpError 400) on GetCommit (commitId @required, target ObjectId). Recorded behavior: the message is the word 'Could not retrieve' followed by the commitId from the request, and names no repository — built from the request, so the template is the requirement, not the recorded literal.
Emulator: the code and the 400 status are now correct, but the message is 'the commit ID <commitId> does not exist in the repository <repositoryName>' — a different template that also leaks the repository name.
Why: tools and samples that match on this message (and differential clients comparing emulator output against AWS) flag every unknown-commit path; the emulator is also more informative than AWS, hiding the ambiguity real clients are written against.
Note: codecommit.get-commit-unknown-id-rejected appears on the open issue '20261022T171422Z-codecommit-answers-501-notimplemented-where-aws-returns-a.md' (Cause 5, 'GetCommit does not reject an unknown commit id'), whose replay key is the `assert code ==` line. That cause is now satisfied — the code assertion passes — and the check fails one assertion later on the message, so this is a distinct residual cause of the same check.
Fix: the message construction for CommitIdDoesNotExistException in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/get_commit.rs (and the commit-lookup helper it shares).
Traces: codecommit.get-commit-unknown-id-rejected.

Cause 4 of 4: the RepositoryDoesNotExistException message template is still the emulator's own prose on the post-rename GetRepository path.
AWS: Smithy models RepositoryDoesNotExistException (client, httpError 400) on GetRepository and UpdateRepositoryName. Recorded behavior: the message is exactly the requested repository name, a space, 'for', a space, and the 12-digit account id of the caller ('<repositoryName> for <accountId>') — a fixed template built from the request and the caller's account.
Emulator: 'the repository <repositoryName> does not exist'; status 400 and the code are correct. Observed here after a successful UpdateRepositoryName, where the check reads the OLD name back to prove the rename moved the resource.
Why: callers that verify a rename by confirming the old name is gone, and any tool matching this message, cannot tell which account the lookup happened in; every not-found path diverges.
Note: the same template is Cause 1 of the open issue '20261022T171422Z-codecommit-client-error-messages-do-not-follow-aws.md', but neither of these two check ids is on that issue's replay list, so they are recorded here. Fixing that cause may close these; both ids must be re-replayed to confirm.
Fix: the shared repository-lookup rejection in the codecommit crate (src/ops/get_repository.rs and the helper used by src/ops/update_repository_name.rs).
Traces: codecommit.update-repository-name-reflected, codecommit.update-repository-name-conflict.
