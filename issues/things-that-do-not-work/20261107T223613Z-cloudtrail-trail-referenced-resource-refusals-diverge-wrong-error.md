# CloudTrail trail referenced-resource refusals diverge: wrong error class for an absent KMS key, re-worded log-group/SNS/KMS refusal texts, KmsKeyId echoed un-normalized, and InsufficientS3BucketPolicyException served 403 instead of 400 (5 causes)

> _Note: this issue was identified against the code base at commit `9cfb70c8dd865d3301250e334464bd408152814b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateTrail

## Description
FIVE distinct causes in this issue; all five must be closed before submitting. They all live on the ONE shared pre-flight that CreateTrail and UpdateTrail run over the resources a trail references (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/state/referenced_resources.rs, reached from create_trail.rs::resolve_referenced_resources and its UpdateTrail twin), plus the KmsKeyId echo and the status mapping of one of its errors. Context, not coverage: the open issue 20261024T145209Z-cloudtrail-accepts-three-calls-real-aws-refuses-createeventdatastore.md describes bucket-policy OVER-ACCEPTANCE on PutInsightSelectors/UpdateTrail (and quotes the model's 403 for InsufficientS3BucketPolicyException); none of the five causes below is carried by it, and the replay report marked none of these checks as owned or already filed.

Cause 1 of 5 — a well-formed KmsKeyId that names no key in the trail's own Region is refused with the WRONG error class.
AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) binds to UpdateTrail/CreateTrail both InsufficientEncryptionPolicyException (errorKind client, httpError 400, awsQueryError InsufficientEncryptionPolicy — documented 'For the CreateTrail, PutInsightSelectors, UpdateTrail, StartQuery, and StartImport operations, this exception is thrown when the policy on the S3 bucket or KMS key does not have sufficient permissions') and KmsKeyNotFoundException (client, 400, KmsKeyNotFound — 'thrown when the KMS key does not exist, when the S3 bucket and the KMS key are not in the same Region'). Recorded AWS behavior splits the two: a syntactically valid SAME-REGION, same-account key identifier that resolves to nothing — a key ARN, a bare key UUID, or an `alias/<name>` — is refused InsufficientEncryptionPolicyException, HTTP 400, message `Insufficient permissions to access S3 bucket <s3-bucket-of-the-trail> or KMS key <expanded-key-arn>.` (fixed text 'Insufficient permissions to access S3 bucket ' + ' or KMS key ' + '.'; the two variable slots are the trail's stored S3BucketName and the identifier expanded to a fully-specified same-region key/alias ARN). Only a MALFORMED identifier (e.g. `not-a-key-id`) or a key ARN in ANOTHER Region is KmsKeyNotFoundException, HTTP 400, message `KMS key ID <key-arn> does not exist, or s3 bucket <s3-bucket-of-the-trail> and key are not in the same region.` (same two kinds of variable slot).
Emulator: every unresolvable-but-well-formed identifier is answered KmsKeyNotFoundException, and a malformed one is answered InvalidKmsKeyIdException. encryption_key_verdict (referenced_resources.rs:235-257) maps KMS's KeyRef::NotFound -> EncryptionKeyVerdict::NotFound -> KmsKeyNotFoundException and KeyRef::MalformedArn/UnauthorizedAccount -> InvalidKmsKeyIdException; there is no InsufficientEncryptionPolicyException branch at all. Its message templates also diverge: kms_key_not_found_message (referenced_resources.rs:322-324) emits 'KMS key <id> does not exist, or is not in the same Region as the trail' — it neither names the trail's S3 bucket nor expands a bare id/alias into a same-region ARN — and invalid_kms_key_id_message (:328-330) emits a sentence AWS never sends for this member.
Why: a client cannot tell 'the key policy does not let CloudTrail use this key / the key is not there' (InsufficientEncryptionPolicyException, remediated by fixing the key or its policy) from 'you gave me an identifier for another Region' (KmsKeyNotFoundException, remediated by changing Region); error-class branching in CDK/Terraform providers and in retry logic takes the wrong arm, and InvalidKmsKeyIdException is a class AWS does not use here at all.
Emulator traces for this cause: cloudtrail.create-trail-unknown-kms-key-rejected — observed at the FIRST assertion (code), so the class split is measured; the message templates above come from the same check's later assertions, which were never reached.

Cause 2 of 5 — the CloudWatch Logs log-group refusals share one emulator-authored sentence instead of AWS's three fixed texts.
AWS: Smithy binds InvalidCloudWatchLogsLogGroupArnException (client, httpError 400, awsQueryError InvalidCloudWatchLogsLogGroupArn, 'thrown when the provided CloudWatch Logs log group is not valid') and InvalidCloudWatchLogsRoleArnException (client, 400, InvalidCloudWatchLogsRoleArn). Recorded AWS behavior distinguishes the cases by MESSAGE, each entirely fixed text with no request-derived slot: a well-formed in-account, in-region log-group ARN naming a group that does not exist -> InvalidCloudWatchLogsLogGroupArnException / `You must specify an existing log group.`; a syntactically malformed group ARN ('not-an-arn') -> InvalidCloudWatchLogsLogGroupArnException / `CloudTrail cannot validate the specified log group ARN.`; either half of the pair sent alone -> `You must specify a log group and a role ARN.` (as InvalidCloudWatchLogsRoleArnException when the role is the absent half, as InvalidCloudWatchLogsLogGroupArnException when the group is).
Emulator: log_group_is_valid (referenced_resources.rs:268-295) collapses all of these into one boolean and invalid_log_group_arn_message (:335-340) renders a single self-authored sentence that interpolates the ARN: `CloudWatch Logs log group ARN <arn> is not valid: it must name a log group that exists in your account`.
Why: the three messages are the only thing that tells a caller WHICH half of the CloudWatch Logs configuration is wrong and how to fix it; one merged sentence makes the remediation ambiguous and makes emulator failures non-comparable with AWS ones.
Emulator traces for this cause: cloudtrail.create-trail-cloudwatch-logs-arn-validation — the absent-group case is observed; the malformed-ARN and lone-half texts are the same check's later, unreached assertions.

Cause 3 of 5 — the insufficient-SNS-topic-policy refusal message is re-worded from the S3 one.
AWS: Smithy binds InsufficientSnsTopicPolicyException (client, httpError 403, awsQueryError InsufficientSnsTopicPolicy, 'thrown when the policy on the Amazon SNS topic is not sufficient'). Recorded AWS behavior: pointing a trail at an existing topic whose access policy does not grant cloudtrail.amazonaws.com sns:Publish is refused with code InsufficientSnsTopicPolicyException and the ENTIRELY FIXED message `SNS Topic does not exist or the topic policy is incorrect!` — no part of it is derived from the request (notably it does NOT name the topic). A malformed topic name is the separate InvalidSnsTopicNameException with `Invalid SNS topic name: <name> is found!`, whose one slot is the request's SnsTopicName.
Emulator: the code is right, but insufficient_sns_topic_policy_message (referenced_resources.rs:313-315) invents `Incorrect SNS topic policy is detected for topic: <topic-arn>` — the S3 bucket template with the resolved topic ARN substituted. Its own doc comment states that no recorded refusal pins the sentence; one does.
Why: callers and provisioning tools match CloudTrail's fixed refusal text to distinguish a topic-policy problem from a topic-name problem; a re-worded message breaks that match and leaks a resolved ARN AWS does not include.
Emulator traces for this cause: cloudtrail.create-trail-sns-topic-without-policy-fails.

Cause 4 of 5 — CreateTrail (and GetTrail after it) echoes KmsKeyId exactly as sent instead of the fully-specified key ARN.
AWS: Smithy documents CreateTrailResponse$KmsKeyId / Trail$KmsKeyId as 'the KMS key ID that encrypts the events delivered by CloudTrail. The value is a fully specified ARN to a KMS key in the following format. arn:aws:kms:<region>:<account>:key/<uuid>', while the request member accepts 'an alias name prefixed by alias/, a fully specified ARN to an alias, a fully specified ARN to a key, or a globally unique identifier'. Recorded AWS behavior matches: CreateTrail called with a bare key UUID answers with the fully-specified key ARN, and GetTrail reports the same ARN.
Emulator: the request value is stored and echoed verbatim — create_trail.rs:512 persists `kms_key_id: input.kms_key_id` and :549 echoes `record.kms_key_id.clone()` — so a bare UUID request comes back as that bare UUID on CreateTrail and on GetTrail.
Why: a client that stores or compares the trail's KmsKeyId (drift detection, policy generation that needs the key ARN, CloudFormation/Terraform state) gets an identifier in the wrong form and a spurious diff against AWS; the input-form-independent output contract is broken.
Emulator traces for this cause: cloudtrail.put-insight-selectors-rejects-insufficient-kms-policy.

Cause 5 of 5 — InsufficientS3BucketPolicyException is served with HTTP 403 where AWS answers HTTP 400.
AWS: the recorded response for CreateTrail against an existing, same-account bucket that carries no CloudTrail delivery policy is HTTP 400 with Error.Code InsufficientS3BucketPolicyException and message `Incorrect S3 bucket policy is detected for bucket: <bucket>` (fixed text plus the request's S3BucketName). Note the model's @httpError on this shape is 403; the recorded wire status for this refusal is 400, and the recording is what the behavioral check measures, so 400 is the requirement here.
Emulator: the code and the message are right, but the response status is 403 — the modeled @httpError(403) is used as the wire status.
Why: clients and SDK retry/classification layers branch on the HTTP status before the payload (403 reads as an authentication/authorization failure worth re-signing or surfacing as AccessDenied, 400 as a malformed-request/validation failure); a 403 for a bucket-policy misconfiguration sends callers down the credentials path instead of the 'attach the CloudTrail delivery policy and retry' path.
Emulator traces for this cause: cloudtrail.trail-creation-on-unpolicied-bucket-rejected-and-succeeds-once-policied.

Fix (all five): the shared referenced-resource resolution and its refusal texts in src/state/referenced_resources.rs (encryption_key_verdict and the kms/log-group/sns message builders), the KmsKeyId normalization on the CreateTrail/UpdateTrail handlers' store-and-echo path, and the status mapping used when InsufficientS3BucketPolicyException is serialized.
