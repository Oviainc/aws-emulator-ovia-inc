# ACM PCA certificate path: IssueCertificate issues leaves that outlive the CA, does not dedupe identical requests, the CA CSR/issued key material is unparseable, CA templates are not applied, mismatched CA-certificate import is accepted and two InvalidStateException messages are emulator-authored

> _Note: this issue was identified against the code base at commit `8d5a4f803a514b21e009b483e221bcf8b3c8087d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
IssueCertificate

## Description
SEVEN net-new root causes on the acm-pca certificate path, all reached now that CAs can be activated. None of the ten failing checks below is marked ALREADY FILED or OWNED in this replay. The open issue 20261022T143159Z-acm-pca-private-ca-lifecycle-is-unusable-issuecertificate.md names neighbouring symptoms (its cause 2 is the placeholder CSR, its cause 3 is mismatched import) but it does not carry these checks' replay keys and its evidence was taken when activation still deadlocked; causes 4 and 6 below are the same surfaces re-grounded in checks it does not own, and causes 1, 2, 3, 5, 7 are not in it at all.

Cause 1 of 7: IssueCertificate does not enforce that the requested validity fits inside the issuing CA certificate's own validity.
AWS: Smithy models IssueCertificate input {CertificateAuthorityArn @required, Csr @required (CsrBlob @length 1..32768), SigningAlgorithm @required, TemplateArn, Validity @required, ValidityNotBefore, IdempotencyToken} -> output CertificateArn, errors InvalidArgsException, InvalidArnException, InvalidStateException, LimitExceededException, MalformedCSRException, ResourceNotFoundException (all 400). The rule and its text are recorded behavior: a leaf validity that runs past the CA certificate's NotAfter is refused with HTTP 400 ValidationException and the message "The certificate validity specified exceeds the certificate authority validity." — the whole sentence is fixed text, nothing is taken from the request — and no certificate is minted. The checks exercise it two ways: a 365-day leaf against a CA activated with a 90-day certificate, and a 7-day leaf against a CA whose certificate expires in 2 days (the second deliberately stays inside the SHORT_LIVED_CERTIFICATE 7-day ceiling so the CA's NotAfter is the only rule broken).
Emulator: answers HTTP 200 with a CertificateArn in both cases and signs the certificate.
Why: the emulator mints certificates that outlive their issuer, which every RFC 5280 path validator rejects; a client's chain-validation and renewal logic is validated against material production would never produce, and since ACM PCA has no DeleteCertificate the caller cannot even undo it. It is also an over-permissive answer: the refusal branch is never exercised.
Fix: IssueCertificate's validity validation — compute the requested NotAfter (Validity/ValidityNotBefore, all period types) and refuse with ValidationException and AWS's sentence when it exceeds the issuing CA certificate's NotAfter, before any signing or state mutation.
Traces: acm-pca.issue-certificate-validity-exceeds-ca-rejected (check line 27), acm-pca.leaf-issued-past-ca-notafter-rejected (check line 358); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs.

Cause 2 of 7: IssueCertificate's MalformedCSRException message is emulator-authored wording instead of AWS's.
AWS: MalformedCSRException is modeled on IssueCertificate (400). The text is recorded behavior: a PEM CERTIFICATE REQUEST block whose body is not a valid PKCS#10 DER structure is refused with HTTP 400 MalformedCSRException and the message "Malformed CSR." — fixed text in full, with no request-derived part.
Emulator: same status and same error class, but the message is "Csr must be a PEM-encoded CERTIFICATE REQUEST block carrying a DER PKCS#10 certification request" — a self-authored explanation that appears nowhere in AWS.
Why: the message is part of the contract; any client or test that asserts on, logs or matches the refusal text sees something production never returns, and the wording implies a shape rule rather than the semantic decode failure that actually occurred.
Fix: the MalformedCSRException construction in IssueCertificate's CSR decode path — emit AWS's fixed sentence.
Traces: acm-pca.issue-certificate-malformed-csr-rejected (check line 43); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs.

Cause 3 of 7: IssueCertificate mints a second certificate for a repeated, byte-identical request instead of replaying the first one.
AWS: Smithy marks IssueCertificate @idempotent and models IdempotencyToken (@length 1..36). Recorded behavior (REAL-AWS verified in the check): re-issuing from the identical CertificateAuthorityArn, Csr, SigningAlgorithm, TemplateArn and Validity on the same CA returns the SAME CertificateArn as the earlier call rather than a new serial — the request is deduplicated, so an interval in which the CA was DISABLED cannot leave a second certificate under the same identity.
Emulator: returns a fresh CertificateArn (a new random serial segment) for the identical repeated request, so the CA accumulates duplicate certificates for one logical request.
Why: a client that retries IssueCertificate after a timeout or a transient error double-issues, is double-billed, and ends up with two live certificates for one key/subject that it can only wait out — there is no DeleteCertificate. Any code that treats CertificateArn as the identity of a request breaks.
Fix: IssueCertificate's handler and certificate state — key the issued certificate on the request's identity (CA ARN, CSR, signing algorithm, template, validity, and IdempotencyToken when supplied) and return the existing CertificateArn for a repeat instead of signing again.
Traces: acm-pca.issue-certificate-on-disabled-ca-rejected (check line 94; its DISABLED-state refusal half passes, only the dedupe assertion fails); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs.

Cause 4 of 7: the CA's PKCS#10 CSR, and the public key inside the certificate issued from it, are not parseable ASN.1.
AWS: GetCertificateAuthorityCsr returns Csr (CsrBody) holding a PEM-armoured PKCS#10 CertificationRequest over the CA's generated key pair, carrying the configured ASN1Subject and a SubjectPublicKeyInfo for the configured KeyAlgorithm; an RSA_2048 request parses with any X.509 tooling and its public key loads. The certificate IssueCertificate then produces must carry that same SubjectPublicKeyInfo, so the leaf it signs verifies against the CA public key.
Emulator: cryptography's load_pem_x509_csr(...).public_key() raises ValueError "Could not deserialize key data ... ASN.1 parsing error: short data (needed at least 75 additional bytes)" on the CSR, and loading the CA public key out of the issued CA certificate raises "... ASN.1 parsing error: invalid length", so the issued leaf's signature cannot be verified at all. The DER is a placeholder, not a real key structure.
Why: every real consumer of this API parses these PEMs — to sign a subordinate CSR with a parent CA, to pin a key, or to verify a chain. With unparseable key material no chain can be built or verified, and a client cannot distinguish the emulator's placeholder from corrupt data.
Fix: the CA key-pair/CSR generation in the service's CA state plus the certificate assembly in IssueCertificate — mint a real key pair of the configured KeyAlgorithm, emit a real PKCS#10 request over it, and copy that SubjectPublicKeyInfo into every certificate issued from it. Same surface as cause 2 of the open lifecycle issue, which only names three now-OWNED checks.
Traces: acm-pca.csr-to-issued-certificate-pem-preserved (check line 71), acm-pca.e2e-root-ca-issue-revoke-audit-delete (check line 113); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/get_certificate_authority_csr.rs, src/ops/issue_certificate.rs, src/state.rs.

Cause 5 of 7: a certificate issued under a CA-certificate template carries no BasicConstraints extension, so the template's CA/pathLen semantics are absent.
AWS: TemplateArn selects the certificate definition. Recorded behavior plus the published template definitions: a certificate issued under arn:aws:acm-pca:::template/SubordinateCACertificate_PathLen0/V1 contains a critical BasicConstraints extension with CA=TRUE and pathLenConstraint=0 (and the root template's certificate likewise carries CA=TRUE); that extension is what makes the subordinate usable as an issuer and what bounds the chain.
Emulator: the issued subordinate-CA certificate has no BasicConstraints extension at all — cryptography raises ExtensionNotFound for x509.BasicConstraints — so a two-level hierarchy cannot be validated and nothing distinguishes a CA certificate from an end-entity one.
Why: a client building or validating a subordinate hierarchy (the documented use of the Subordinate* templates) sees certificates that no path validator will accept as issuers, and the pathLen=0 restriction the template exists to express is unobservable.
Fix: the certificate-assembly/template application in IssueCertificate — populate the extensions each TemplateArn's definition mandates (BasicConstraints with the template's CA flag and pathLenConstraint, marked critical) rather than emitting a bare certificate.
Traces: acm-pca.subordinate-ca-chain-validates-two-levels-deep (check line 364); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs.

Cause 6 of 7: ImportCertificateAuthorityCertificate accepts a certificate that belongs to a different CA's key and subject.
AWS: Smithy models ImportCertificateAuthorityCertificate {CertificateAuthorityArn @required, Certificate @required (CertificateBodyBlob @length 1..32768), CertificateChain} -> Unit with CertificateMismatchException among its errors ("The certificate authority certificate you are importing does not comply with conditions specified in the certificate that signed it"). Recorded behavior: importing CA-B's well-formed self-signed certificate onto CA-A is refused with HTTP 400 CertificateMismatchException and the message "The certificate subject contains a different subject than the CA certificate signing request." — fixed text in full — and CA-A stays PENDING_CERTIFICATE.
Emulator: answers HTTP 200 with an empty body (content-length 2) and installs the foreign certificate.
Why: the CA is activated with a certificate whose private key the service does not hold, so everything it then signs is unverifiable, and the client's mismatch-handling branch is never exercised. Same surface as cause 3 of the open lifecycle issue, whose named traces are OWNED while this check is not.
Fix: ImportCertificateAuthorityCertificate's validation — compare the submitted certificate's subject and SubjectPublicKeyInfo against the CA's outstanding CSR and refuse with CertificateMismatchException before any state change.
Traces: acm-pca.import-certificate-csr-key-mismatch-rejected (check line 31/75); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/import_certificate_authority_certificate.rs.

Cause 7 of 7: two InvalidStateException messages are emulator-authored prose instead of AWS's fixed sentences (DeleteCertificateAuthority on an ACTIVE CA, ImportCertificateAuthorityCertificate on a DELETED CA).
AWS: Smithy models InvalidStateException (400) on both DeleteCertificateAuthority (input CertificateAuthorityArn @required, PermanentDeletionTimeInDays @range 7..30) and ImportCertificateAuthorityCertificate. The texts are recorded behavior: deleting a CA while it is ACTIVE is refused with "The certificate authority is not in a valid state for deletion."; importing a CA certificate onto a soft-deleted CA is refused with "The certificate authority is in the DELETED state and must be restored to complete this action." Both sentences are fixed text in full — no ARN, state name or other request/state value appears in either.
Emulator: right status and right error class, wrong text. It answers 'A private CA can be deleted only if it is in the PENDING_CERTIFICATE, CREATING, EXPIRED, DISABLED, or FAILED state. To delete a CA in the ACTIVE state, you must first disable it.' for the first, and 'the certificate authority <ca-arn> is in state DELETED, which cannot import a certificate authority certificate' for the second — the latter also interpolates the CA ARN and the state name, which AWS's message does not contain.
Why: these are the refusals a client asserts on when driving a CA through its lifecycle; messages that differ (and that carry per-run values AWS never includes) break message matching and make a recorded emulator response non-comparable with production.
Fix: the InvalidStateException message construction in those two handlers — emit AWS's fixed sentence for each state refusal, with no interpolated ARN or state token.
Traces: acm-pca.delete-active-ca-without-disable-rejected (check line 49), acm-pca.import-certificate-on-deleted-ca-rejected (check line 51); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/delete_certificate_authority.rs, src/ops/import_certificate_authority_certificate.rs.
