## Description
This bundle has 2 causes; BOTH must be closed before submitting. Both are grounded in failing checks of this run and both live in the pipe's FILTER stage, which now runs (the pipes data plane does poll and deliver in this run — see the Evidence: a target queue received two records) but evaluates a record's `body` as the raw string the envelope carries.

Related, not covering: the open issue 20261023T235727Z-pipes-eventbridge-pipes-has-no-runtime-a-running-pipe.md lists these five check ids among its trace ids, but its causes are "a RUNNING pipe never polls or delivers", terminal create/start failure states, ConflictException, the CFN resource provider and metrics. Neither 20261027T030720Z-pipes-the-data-plane-never-authorizes-against-the.md nor 20261027T213600Z-pipes-updatepipe-desiredstate-toggling-is-write-only-a.md touches pattern matching.

Cause 1 of 2: a filter pattern with a STRUCTURED `body` clause (an object, or a clause using a comparison operator under `body`) never matches an SQS record whose body is valid JSON, so a pipe that should deliver the matching record delivers nothing at all.
AWS: Smithy (com.amazonaws.pipes): CreatePipe/UpdatePipe take SourceParameters.FilterCriteria -> FilterCriteria{Filters: FilterList @length 0..5}, each Filter.Pattern an EventPattern (@length 0..4096, @sensitive), documented as "The collection of event patterns used to filter events" and pointing at Events and Event Patterns in the EventBridge user guide. Recorded behavior for the data plane (the model describes only the control plane): EventBridge Pipes builds the SQS record envelope (messageId/receiptHandle/body/attributes/messageAttributes/md5OfBody/eventSource/eventSourceARN/awsRegion) and, when the message body is valid JSON, matches `body` as the PARSED JSON document — which is what makes `{"body": {"kind": ["alpha"]}}`, `{"body": {"severity": [{"numeric": [">=", 500]}], "stage": [{"prefix": "prod-"}], "team": [{"anything-but": ["ignore-me"]}], "suppress": [{"exists": false}]}}` and the documented clause-level AND / Filters-level OR semantics meaningful at all. A record that satisfies the pattern is delivered to the target exactly once.
Emulator: every check whose pattern constrains `body` structurally hangs on its own positive control and is cut at the harness cap ("Check timed out after 60.0s") — the record that MUST be delivered is never delivered, so the pipe behaves as if the pattern matched nothing. services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs:1372 `admitted()` hands the envelope straight to `service_common::event_pattern::matches_within`, and the envelope built at data_plane.rs:1415-1425 sets `"body": message.body` — the raw string. A string value can never satisfy an object-shaped or operator-shaped clause, so the match fails for every JSON message. (Hypothesis, not establishable from this run because no record ever got through the body clause: whether the shared matcher `service_common::event_pattern` also lacks `numeric`/`prefix`/`anything-but`/`exists`; after the body is parsed, pipes.filter-comparison-operators-gate-delivery-one-clause-at-a-time additionally requires all four of those operators, ANDed within one pattern, and pipes.filter-criteria-multiple-filters-are-ored-not-anded requires the two entries of Filters to be ORed — `admitted()` does OR them with `.any()`, so the OR wiring itself looks right.)
Why: the normal way to use Pipes — JSON messages on a queue, filtered on fields of the body — silently delivers NOTHING. A client sees the pipe report RUNNING, sees DescribePipe echo its FilterCriteria, sees its source drained, and never receives the records that match. It is indistinguishable from a filter that is correct and an empty source, and it is the exact inverse of the defect in Cause 2, so neither direction of the filter can be trusted.
Fix: the filter stage of the pipes data plane — the match view of a record in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs (`admitted()` and the envelope builder `queue_record_envelope()`): the value matched at `body` must be the parsed JSON document when the body is valid JSON, while the payload handed to the enrichment and the target stays the record envelope with the body as sent. If the shared matcher lacks the content-based operators, extend `service_common::event_pattern` too.
Traces: pipes.filter-criteria-multiple-filters-are-ored-not-anded (positive control for Filters[0], body.kind=alpha, never arrives), pipes.filter-comparison-operators-gate-delivery-one-clause-at-a-time (the fully-matching control record never arrives), pipes.update-pipe-filter-criteria-takes-effect-on-a-running-pipe-and-reverts (the v1-admitted control record under `{"body": {"kind": ["alpha", "beta"]}}` never arrives, so the UpdatePipe re-install can never even be reached), pipes.filter-json-body-pattern-drops-plain-string-message-metadata-pattern-delivers-it (the JSON record that must match `{"body": {"kind": ["order"]}}` never arrives).

Cause 2 of 2: the format-mismatch drop rule is not applied — a plain-string `body` pattern admits a message whose body is valid JSON (and, symmetrically, a JSON-structured `body` clause is expected to drop a non-JSON body).
AWS: recorded behavior only (the Smithy model constrains Pattern's length, not its semantics). EventBridge event filtering decides the FORMAT of a `body` clause first: a pattern whose `body` clause lists plain-string literals matches only messages whose body is NOT JSON, and a pattern whose `body` clause is a JSON document matches only messages whose body IS valid JSON. A format mismatch is a DROP regardless of content — so a message whose raw body is byte-identical to a literal listed in a plain-string pattern is still dropped when that body happens to be valid JSON, and a plain-string message is dropped by a pattern with a JSON `body` clause. A pattern with no `body` clause at all (e.g. `{"messageAttributes": {"tier": {"stringValue": ["gold"]}}}`) skips the format check and matches both formats.
Emulator: with `FilterCriteria.Filters=[{"Pattern": {"body": ["PLAINMATCH-<marker>-PLAIN", "{\"k\": \"<marker>-JSON\"}"]}}]`, BOTH messages are delivered to the target. The replay reports: "pipe '...' delivered the valid-JSON record '{\"k\": \"<marker>-JSON\"}' even though its filter is a PLAIN-STRING body pattern", with the target holding both envelopes (the second one's `body` being the JSON text). Same root site as Cause 1: `body` is compared as text, so a string equality against a JSON-text literal succeeds where AWS refuses on format.
Why: the filter leaks. Records a client excluded by format reach the enrichment and the target, so a pipe used to separate JSON traffic from plain-text traffic (a very common Pipes shape) delivers both to whichever branch it is wired into, and the client's downstream parser receives payloads it was built to never see. Combined with Cause 1, a pipe can simultaneously withhold what it must deliver and deliver what it must drop.
Fix: the same filter stage in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs — classify the body's format once per record, compare it to the format the pattern's `body` clause demands, and drop on mismatch before any value comparison; patterns with no `body` clause must bypass the check entirely (the messageAttributes envelope at data_plane.rs:1400-1414 already renders dataType/stringValue/binaryValue, so metadata-only patterns should keep matching both formats).
Traces: pipes.filter-plain-string-body-pattern-drops-a-valid-json-body-of-identical-text (the leak, asserted directly), pipes.filter-json-body-pattern-drops-plain-string-message-metadata-pattern-delivers-it (the mirror leg: a JSON `body` clause must drop the plain-string record while the metadata-only twin pipe delivers it).
