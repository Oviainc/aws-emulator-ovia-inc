## Description
Three net-new root causes in the apigateway service. None of the four failing checks below is marked ALREADY FILED, and none carries a replay key held by an open issue. Related open/fixed issues describe the same FAMILIES of symptom but do not carry these keys and do not name these conditions: 20261024T043741Z-apigateway-api-gateway-6-control-plane-convergence-causes-updateaccount.md (open) cause 4 covered UpdateStage answering 404 NotFoundException for a bogus /deploymentId — that classification is now correct (the emulator returns 400 BadRequestException) and the failure has moved to the message, which is cause 3 here; 20261025T014422Z-apigateway-api-gateway-control-plane-10-causes-of-invented.md (fixed) enumerates ten invented-message families but neither DeleteVpcLink's in-use refusal nor UpdateStage's /deploymentId refusal is among them, so neither cause below is a reopen. Each cause is numbered with its own failing check ids; all three must be closed before this issue is submitted.

Cause 1 of 3: a VpcLink created against a well-formed but NON-EXISTENT network load balancer settles AVAILABLE instead of FAILED.
AWS: Smithy: CreateVpcLink (POST /vpclinks, success 202) takes name (required) and targetArns: ListOfString (required) and returns the VpcLink shape, whose status member targets enum VpcLinkStatus with values AVAILABLE | PENDING | DELETING | FAILED; VpcLink$targetArns is documented as "The ARN of the network load balancer of the VPC targeted by the VPC link. The network load balancer must be owned by the same Amazon Web Services account of the API owner", and VpcLink$status as "The status of the VPC link... Deploying an API will wait if the status is PENDING and will fail if the status is DELETING", with statusMessage "A description about the VPC link status". Recorded behavior: the create is ACCEPTED (status PENDING, or occasionally an immediate FAILED) because provisioning is asynchronous, and the asynchronous provisioning then SETTLES on status FAILED — never AVAILABLE — when the targetArn names a load balancer that does not exist in the account; GetVpcLink and GetVpcLinks both report that terminal FAILED, with statusMessage describing why. The target's EXISTENCE (and, per the check's own setup note, its having at least one listener) is what decides the terminal state, not the ARN's syntax.
Emulator: the create is accepted and the link converges to status AVAILABLE. GetVpcLink polled for up to 220 s returns AVAILABLE, so the terminal state is a usable link pointing at nothing. The handler decides the settled outcome purely from ARN SHAPE: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_vpc_link.rs provisioning_failure() -> names_a_network_load_balancer() only parses the ARN and checks vendor == "elasticloadbalancing" and resource prefix "loadbalancer/net/", so an ARN that is well formed but resolves to no load balancer passes and the link is marked AVAILABLE.
Why: a client that uses VpcLink status as its readiness/validation gate is told a link is usable when its backend does not exist. Deployments that "wait for PENDING then proceed on AVAILABLE" proceed, and the misconfiguration surfaces later as unexplained integration failures (or never surfaces at all), instead of at the resource whose status AWS marks FAILED. Negative tests that assert a bad target is rejected cannot pass, and the FAILED branch of the VpcLink state machine is unreachable.
Fix: the CreateVpcLink handler's asynchronous provisioning outcome (create_vpc_link.rs provisioning_failure / the VpcLinkEntry failure it settles into) must resolve each targetArn against Elastic Load Balancing state and settle the link in FAILED, with a statusMessage, when the named network load balancer does not exist; ARN syntax alone is not sufficient.

Cause 2 of 3: DeleteVpcLink's refusal for a link still referenced by an Integration returns an emulator-authored message that identifies the link by NAME and does not use AWS's reference format.
AWS: Smithy: DeleteVpcLink (DELETE /vpclinks/{vpcLinkId}, success 202, output Unit) models BadRequestException 400, ConflictException 409, NotFoundException 404, TooManyRequestsException 429, UnauthorizedException 401. Recorded behavior: while an Integration still names the link through connectionType=VPC_LINK / connectionId, the delete is refused with BadRequestException 400 whose message is "Cannot delete vpc link. Vpc link '<vpcLinkId>', is referenced in [<restApiId>:<httpMethod>:<resourceId>] in format of [RESTApiId:Method:Resource]." The FIXED text is "Cannot delete vpc link. Vpc link '", "', is referenced in [", and "] in format of [RESTApiId:Method:Resource]."; the VARIABLE parts are the vpcLinkId taken from the request path and the restApiId, HTTP method and resource ID of each referencing integration taken from service state — i.e. AWS identifies the link by its ID, and the reference by the triple restApiId:method:resourceId, and it says so in the message by naming that format. The positive control in the same check confirms the identical delete succeeds once the integration is removed, and that a later GetVpcLink then answers NotFoundException "Invalid Vpc Link identifier specified".
Emulator: the status and error code are right (400 BadRequestException), the message is not: "Cannot delete VPC link '<vpcLinkName>', is referenced in integration: <method>//". It diverges three ways — the leading sentence "Cannot delete vpc link." is dropped and the remaining prefix is recased ("VPC link"); the quoted identifier is the link's NAME, not its id (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/delete_vpc_link.rs takes link.name from the resolved record and passes it to crate::state::vpc_link_in_use(&name, &referencing)); and the reference is rendered as "integration: GET//" (method plus resource PATH) rather than "[<restApiId>:GET:<resourceId>] in format of [RESTApiId:Method:Resource]".
Why: the message is the only place AWS reports WHICH integration blocks the delete, and it reports it in ids a client can act on. A caller parsing the refusal to find and clear the blocking integration gets a resource path instead of a restApiId/resourceId pair, and gets a link name where it expects the id it just passed — so automated cleanup cannot locate the blocker, and log/assertion tooling keyed on AWS's wording does not match.
Fix: the DeleteVpcLink handler's in-use refusal construction — crate::state::vpc_link_in_use() and its call site in src/ops/delete_vpc_link.rs: emit AWS's fixed text, substitute the request's vpcLinkId (not the stored name), and format each referencing integration as <restApiId>:<httpMethod>:<resourceId>.
Checks: apigateway.delete-vpc-link-in-use-by-integration-conflict

Cause 3 of 3: UpdateStage's refusal of a /deploymentId patch naming a deployment that does not exist carries the GetDeployment NOT-FOUND message instead of AWS's bad-request message.
AWS: Smithy: UpdateStage (PATCH /restapis/{restApiId}/stages/{stageName}) takes patchOperations: ListOfPatchOperation, returns Stage, and models BadRequestException 400, ConflictException 409, LimitExceededException 429, NotFoundException 404, TooManyRequestsException 429, UnauthorizedException 401. Recorded behavior: a replace of /deploymentId with an id that does not exist — whether it was never created or has since been deleted — is refused with BadRequestException 400 and the message "Deployment id does not exist". That message is a CONSTANT: it has no variable part, and in particular it does not echo the offending id. It is distinct from the NotFoundException message AWS returns from GetDeployment for a missing deployment, "Invalid Deployment identifier specified" (the same checks assert that text on GetDeployment and it matches). Both checks run a positive control first — the same stage is repointed at a second REAL deployment successfully — so the refusal is attributable to the unknown id, and after the rejected patch the stage still points at the previously set deployment.
Emulator: status 400 and code BadRequestException are right; the message is "Invalid Deployment identifier specified" — the not-found text, reused on the bad-request path. Both of AWS's two distinct messages for the two distinct refusals of an unknown deployment id collapse onto one string.
Why: the two conditions are deliberately distinguishable in AWS — "this stage patch value is invalid" (400, "Deployment id does not exist") versus "the deployment resource you read is gone" (404, "Invalid Deployment identifier specified"). A client or test harness that branches on the message to decide whether to pick a different deployment id or to treat the deployment as deleted cannot tell them apart, and assertions on AWS's wording fail even though the status and code are correct.
Fix: the UpdateStage handler's /deploymentId patch-value resolution (services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/update_stage.rs) must build its BadRequestException with its own constant "Deployment id does not exist" rather than reusing the shared deployment not-found message constant.
Checks: apigateway.stage-repoint-unblocks-old-deployment-delete, apigateway.update-stage-conflict-during-deployment
