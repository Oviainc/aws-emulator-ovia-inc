# EC2: CreateVpc from an IPAM pool is a stub (12 checks), 5 IPAM refusal/representation causes, 3 message-fidelity causes, and no instance ever presents a guest (37 checks hang)

> _Note: this issue was identified against the code base at commit `620c90c23a321396910fd66a692ef2fcecf33f7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateVpc

## Description
Six net-new root causes behind the remaining surviving ec2 failures.

Cause 1 of 6: CreateVpc with an IPAM-allocated CIDR is an unimplemented scaffold variant, so the whole IPAM-to-VPC path answers 501 NotImplemented.
AWS: CreateVpc with Ipv4IpamPoolId (optionally Ipv4NetmaskLength) allocates a CIDR from the pool and returns the VPC with that CidrBlock; the pool records the allocation, sequential VPCs get disjoint blocks, an explicit CIDR inside the pool is honoured exactly, and the modelled refusals apply — a locale-less pool is refused InvalidParameterValue ("The resource type vpc is not valid for pool <pool> with None locale."), a netmask wider than the pool's allocation rules is refused InvalidParameterValue ("The requested netmask length /19 is larger than allowed by pool <pool>. Largest netmask length allowed is /20"), a request with neither CIDR nor netmask against a pool with no default is refused InvalidParameterCombination ("The request cannot contain empty CIDR and Netmask Length for a pool with no default allocation netmask length set. Exactly one of them should be provided."), and an untagged VPC against a pool with required resource tags is refused InvalidParameterValue.
Emulator: every such call answers ('NotImplemented', 'operation CreateVpc with an IPAM-allocated CIDR block is scaffolded but not implemented in this emulator') — the allocations never happen and none of the modelled refusals is reachable.
Why: IPAM is unusable end to end: no VPC can be allocated from a pool, no allocation/deprovision/address-history can be observed, and every negative branch returns the wrong code and a 501-class status.
Fix: the CreateVpc handler's IPAM-allocated-CIDR path (and the ipam pool allocation state it must update).
Traces: ec2.ipam-cli-create-vpc-from-ipam-pool-matches-sdk-allocation, .ipam-deprovision-cidr-under-live-vpc-accepted-then-rejected-as-failed-deprovision, .ipam-pool-default-netmask-sizes-vpc-when-length-omitted, .ipam-release-of-vpc-owned-allocation-frees-the-cidr-for-reuse, .ipam-sequential-vpcs-from-one-pool-receive-disjoint-blocks, .ipam-vpc-explicit-cidr-inside-pool-is-honoured-exactly, .ipam-vpc-from-localeless-top-pool-rejected, .ipam-vpc-from-regional-child-pool-found-by-recursive-allocation-walk, .ipam-vpc-missing-pool-required-resource-tag-rejected, .ipam-vpc-netmask-outside-pool-allocation-rules-rejected, .ipam-vpc-without-length-on-pool-without-default-rejected, .concurrent-modify-ipam-resource-cidr-conflicting-updates, .op-contract-get-ipam-address-history.

Cause 2 of 6: IPAM pool/scope operations refuse or represent wrongly outside the CreateVpc path.
AWS: ProvisionIpamPoolCidr with a netmask larger than the source pool's free space is ACCEPTED and settles as a failed provision (the refusal is asynchronous, not an InvalidParameterValue at request time); a provision naming neither Cidr nor NetmaskLength is refused with the modelled combination error rather than MissingParameter; a cross-scope source pool and a dependent delete each carry their own modelled code (DeleteIpamScope answers NotImplemented today, so "scope with pools" and "default scope" report NotImplemented instead of the dependency/immutability refusals); and a top-level pool reports Locale ("None"), PoolDepth 1 and omits allocation rules.
Emulator: ProvisionIpamPoolCidr refuses synchronously with InvalidParameterValue ("Invalid value '7' for netmaskLength. The source IPAM pool '...' has no free CIDR of that size"); the size-less provision answers MissingParameter; the cross-scope source answers InvalidParameterValue; the delete-order refusals read {'scope with pools': 'NotImplemented', 'default scope': 'NotImplemented'}; and GetIpamPools omits Locale (KeyError).
Why: a client cannot read a pool's shape, and every negative IPAM branch returns a different code (or a 501) than AWS, so ordering/cleanup logic keyed on them breaks.
Fix: the IPAM pool handlers (provision/allocate validation and its async failure state), the IPAM scope delete handler, and the IpamPool serializer (Locale/PoolDepth/AllocationResourceTags).
Traces: ec2.ipam-provision-beyond-parent-space-accepted-then-rejected-as-failed-provision, .ipam-provision-pool-cidr-without-cidr-or-netmask-rejected, .ipam-child-pool-sourced-across-scopes-rejected, .ipam-delete-with-dependents-rejected-until-removed-in-order, .ipam-top-pool-reports-none-locale-depth-one-and-omits-allocation-rules.

Cause 3 of 6: StateTransitionReason is not formatted the way EC2 formats it.
AWS: after StopInstances the instance's StateTransitionReason reads exactly "User initiated (YYYY-MM-DD HH:MM:SS GMT)" — fixed text "User initiated (" + a space-separated UTC timestamp with the literal suffix " GMT)".
Emulator: "User initiated (2026-11-07T07:26:37.693718Z)" — an ISO-8601 instant inside the parentheses.
Why: clients parse this field to recover when and by whom an instance was stopped; the format is part of the contract, not the particular timestamp.
Fix: the instance state-transition writer / DescribeInstances serializer for StateTransitionReason.
Traces: ec2.stop-start-transitions-are-monotone-and-reads-do-not-advance-them.

Cause 4 of 6: the termination-protection refusal message loses its final period.
AWS: OperationNotPermitted with exactly "The instance '<id>' may not be terminated. Modify its 'disableApiTermination' instance attribute and try again." — fixed text, terminated by a period; the only variable part is the instance id.
Emulator: the identical sentence without the trailing period.
Why: a client comparing the documented message (or a runbook grepping it) fails on an exact-match assertion.
Fix: TerminateInstances' disableApiTermination refusal message.
Traces: ec2.terminate-termination-protected-instance-rejected.

Cause 5 of 6: the cross-VPC security-group-reference refusal names the group and VPC instead of AWS's generic sentence.
AWS: authorizing a rule that references a group in another VPC is refused with the generic different-networks text, which names neither the group id nor either VPC.
Emulator: "The security group 'sg-...' does not exist in VPC 'vpc-...'".
Why: the emulator's message reads like a not-found error, so a client classifies a topology error as a missing resource.
Fix: AuthorizeSecurityGroupIngress/Egress cross-VPC validation message.
Traces: ec2.ec2mr-usg-cross-vpc-group-reference-rejected.

Cause 6 of 6: an EC2 instance never presents a guest or converges to the state a waiter needs, so 37 checks spin to the 60s budget.
AWS: a launched instance boots, runs its UserData, serves IMDS (hop limit and token TTL enforced), registers an SSM agent that comes Online, exposes its attached volumes as block devices whose bytes survive detach/reattach, stop/start and snapshot/restore, reports instance-store volumes as NVMe namespaces, answers on its security-group-admitted ports, honours source/dest check, and advances through stop/start/terminate — and the identity document, hibernate-resume, capacity-reservation consumption and shutdown-behavior paths each settle to an observable state (recorded behavior).
Emulator: none of this converges: every check below ends "Check timed out after 60.0s" (two of them as an explicit assertion that the SSM agent never came Online within the wait).
Why: the entire guest-observable half of EC2 — UserData, IMDS, EBS/instance-store data, in-guest networking, shutdown behaviour, identity documents — is unobservable, and a client cannot distinguish "the behaviour is wrong" from "nothing ever happened".
Fix: the EC2 instance runtime and state convergence (guest boot/UserData, IMDS service, volume data plane, instance state machine) behind these waits.
