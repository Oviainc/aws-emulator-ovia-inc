# es reference catalogs diverge from AWS: upgrade matrix, instance-type limits and reserved-instance offerings

> _Note: this issue was identified against the code base at commit `60b375bfe55c4c11c191fcd8cd6edcaa1ac7cf89`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCompatibleVersions

## Description
3 net-new root causes on the es service token: three static reference catalogs this service serves are emulator-authored and differ from the ones AWS publishes. All three must be closed before this issue is resubmitted. Recorded behavior only in each case - the model constrains the shape of these responses, not their contents.

Cause 1 of 3: GetCompatibleVersions returns the wrong upgrade-compatibility matrix.
AWS: Smithy GetCompatibleVersions = GET /2021-01-01/opensearch/compatibleVersions, optional domainName query filter, output CompatibleVersions: CompatibleVersionsList of {SourceVersion, TargetVersions}. Unfiltered, AWS returns one entry per upgradable source engine version, and each entry's TargetVersions is exactly the set of versions that source version may upgrade to - e.g. source Elasticsearch_6.8 offers Elasticsearch_7.1, 7.4, 7.7, 7.8, 7.9, 7.10 and OpenSearch_1.0-1.3, and nothing later. The entries appear in AWS's own order.
Emulator: the matrix is a different list in a different order - 24 of the ~33 recorded entries do not match the recording at their index. At the index where AWS reports source Elasticsearch_6.8 the emulator reports Elasticsearch_7.8, and the emulator's target sets are generated by enumerating later versions rather than by AWS's upgrade rules (its OpenSearch_2.3 entry, for instance, offers targets up to OpenSearch_3.7 where AWS stops at OpenSearch_2.19).
Why: this matrix is how a client decides whether an in-place upgrade is possible and which target to pick. A client reading the emulator's answer picks an upgrade path AWS does not offer (and is refused when it tries), or concludes a path AWS does offer does not exist.
Fix: the static upgrade-compatibility table behind the GetCompatibleVersions reader in the es/opensearch service crate, including the order the entries are emitted in.
Traces: es-engine-version-and-instance-catalog#task#2.

Cause 2 of 3: DescribeInstanceTypeLimits serves one generic storage-limit table instead of the limits of the requested instance type and engine version.
AWS: Smithy DescribeInstanceTypeLimits = GET /2021-01-01/opensearch/instanceTypeLimits/{EngineVersion}/{InstanceType}, both path members required, output LimitsByRole: map of role -> Limits. Per role, StorageTypes lists only the storage types that the requested instance type actually supports, and the StorageTypeLimits values (MaximumVolumeSize, MinimumVolumeSize, MaximumIops, MinimumIops) are the limits for THAT instance type - for the small burstable type the fixtures request, MaximumVolumeSize 100 GiB, MaximumIops 11800 and MinimumIops 260, with no io1 and no standard (magnetic) sub-type offered.
Emulator: the data role reports MaximumVolumeSize 512, MaximumIops 16000 and MinimumIops 1000, and adds two storage types the recording does not contain at all (StorageSubTypeName io1 and StorageSubTypeName standard). The values do not vary with the requested instance type, i.e. a fixed table is returned regardless of the {EngineVersion}/{InstanceType} path.
Why: these limits are the bounds a client validates an EBSOptions block against before calling CreateDomain/UpdateDomainConfig. A client sizing a volume or an IOPS value from the emulator's table builds a domain request AWS refuses (512 GiB / 16000 IOPS on a type capped at 100 GiB / 11800 IOPS), and it believes io1 and magnetic storage are available where AWS offers neither.
Fix: the per-instance-type, per-engine-version limit table behind the DescribeInstanceTypeLimits reader, and the selection of storage types by requested instance type.
Traces: es-engine-version-and-instance-catalog#task#4 (also reproduced by eserr-describe-instance-type-limits-t2-micro-invalid-type#task#1 and opensearch-domain-version-capacity-and-software-update-management#task#4, the other members of that cluster).

Cause 3 of 3: DescribeReservedInstanceOfferings serves a synthesized offering table.
AWS: Smithy DescribeReservedInstanceOfferings = GET /2021-01-01/opensearch/reservedInstanceOfferings (paginated, offeringId/maxResults/nextToken query members), output ReservedInstanceOfferings of {ReservedInstanceOfferingId, InstanceType, Duration, FixedPrice, UsagePrice, CurrencyCode, PaymentOption, RecurringCharges}. AWS returns its published offering table in its own order; the recording's first page begins with a NO_UPFRONT offering whose RecurringCharges is a single Hourly charge of 2.61.
Emulator: the first offering is a PARTIAL_UPFRONT offering on a previous-generation instance type (d2.8xlarge.search) with its own fixed price and an Hourly recurring charge of 0.83067 - a different offering set in a different order, so the page the client receives is not a page of AWS's catalog. The same mismatch appears on the paginated walks of the same reader.
Why: reserved-instance purchasing starts from this catalog: the client picks an offering id, a payment option and a price from it and passes it to PurchaseReservedInstanceOffering. Every offering id and price the emulator hands out is one AWS does not sell, and AWS's actual offerings (payment options and instance types included) are invisible.
Fix: the static reserved-instance offering table behind the DescribeReservedInstanceOfferings reader and the order/pagination it emits.
Traces: opensearch-describe-reserved-instance-offerings-paginated#task#2 (also reproduced by opensearch-list-and-paginate-reserved-instance-offerings#task#1, #task#2 and opensearch-paginate-reserved-instance-offerings#task#2, the other members of that cluster).

Prior art: open issue 20261029T190009Z-opensearch-the-package-offering-version-and-instance-type.md files the same class of fault for the OPENSEARCH service token (its Issue-Keys are all opensearch|...) and does not carry any of the three es replay keys above, so none of these three clusters is exercised or closed by it.
