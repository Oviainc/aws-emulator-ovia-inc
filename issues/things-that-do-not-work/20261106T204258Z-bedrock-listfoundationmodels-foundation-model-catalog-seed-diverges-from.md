# bedrock ListFoundationModels foundation-model catalog seed diverges from AWS across converse metadata, capability-flag shapes and membership

> _Note: this issue was identified against the code base at commit `f321e401751560d87b6bbb5351bddaf8182a3d98`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListFoundationModels

## Description
The emulator's built-in read-only Bedrock foundation-model catalog is seeded with its own invented content and serialised with capability sub-objects of the wrong SHAPE. GET /foundation-models answers 200 with a well-formed ListFoundationModelsResponse, so the handler's control flow and HTTP contract are right; what diverges is the catalog CONTENT (which models are listed, and every per-model metadata field) and the TYPE of several capability members. There is 1 cause in this bundle; it must be closed before submitting.

Cause 1 of 1: ListFoundationModels serves a foundation-model catalog whose membership, per-model `converse` metadata, capability-flag member types and lifecycle timestamps all diverge from AWS (fixture bedrock-catalog-list-foundation-models, step task#1).

AWS: Smithy bedrock#ListFoundationModels -> GET /foundation-models, http code 200, readonly; input is query-bound only (byProvider @pattern ^[A-Za-z0-9- ]{1,63}$, byCustomizationType, byOutputModality, byInferenceType); output member modelSummaries targets FoundationModelSummaryList. The on-disk model's FoundationModelSummary declares modelArn (required, @pattern ^arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}::foundation-model/...$), modelId (required, BedrockModelId @length max 140), modelName and providerName (BrandedName @length 1..20), inputModalities / outputModalities (ModelModalityList), responseStreamingSupported (Boolean), customizationsSupported (ModelCustomizationList), inferenceTypesSupported (InferenceTypeList) and modelLifecycle (FoundationModelLifecycle). Modeled errors: ValidationException 400, AccessDeniedException 403, ThrottlingException 429, InternalServerException 500. The on-disk model declares NO `converse`, `featuresSupported`, `explicitPromptCaching`, `intelligentPromptRouting`, `batchSupported`, `guardrailsSupported`, `latencyOptimizationSupported`, `modelFamily` or `description` member on FoundationModelSummary, and it says nothing about WHICH models the catalog contains, so for all of those: recorded behavior only. The recording shows AWS serving (a) a specific set of model ids, (b) for each model a `converse` block carrying additionalRequestFieldsSchema, maxTokensDefault, maxTokensMaximum, reasoningSupported.embedded, stopSequencesDefault and the user*TypesSupported lists in a specific order, and (c) capability members whose values are STRUCTURES, not booleans — e.g. featuresSupported.batchInference is the object {"crossRegion": <bool>, "inRegion": <bool>}, and explicitPromptCaching / intelligentPromptRouting are objects with an isSupported member.

Emulator: the response is 200/200 but a large share of $.modelSummaries diverges, in four distinct ways. (1) CAPABILITY-FLAG SHAPE: featuresSupported.batchInference is emitted as a bare boolean where AWS emits the two-member object — recorded example for modelId openai.gpt-6-astra: expected {'crossRegion': False, 'inRegion': False}, got False; the same collapse-to-boolean affects featuresSupported.*, explicitPromptCaching and intelligentPromptRouting on many entries, which is a type_mismatch, not a value difference. (2) CONVERSE METADATA: converse.additionalRequestFieldsSchema, converse.maxTokensMaximum, converse.maxTokensDefault, converse.reasoningSupported.embedded and converse.stopSequencesDefault are absent where AWS reports them (openai.gpt-6-astra: expected additionalRequestFieldsSchema '{"reasoning_config":{"type":"enum","default":"medium","enum":["low","medium","high","xhigh","max"]}}', maxTokensMaximum 131072, reasoningSupported.embedded false — all got None), while converse.userDocumentTypesSupported and converse.userVideoTypesSupported are populated on models for which AWS reports no such list (openai.gpt-6-astra: emulator emits pdf, csv, doc, docx, xls, xlsx, html, txt, md as extras), and converse.userImageTypesSupported is emitted in a different ORDER than AWS's (expected ['jpeg','png'], got ['png','jpeg']). (3) CATALOG MEMBERSHIP: whole summary objects diverge with no sub-path — the catalog does not agree with AWS on whether these model ids are listed at all: ai21.jamba-1-5-mini-v1:0, amazon.nova-canvas-v1:0, amazon.titan-image-generator-v1, amazon.titan-text-lite-v1, amazon.titan-text-premier-v1:0, anthropic.claude-3-5-sonnet-20241022-v2:0, anthropic.claude-3-haiku-20240307-v1:0, anthropic.claude-3-sonnet-20240229-v1:0. (4) SEED FIELD VALUES: modelName, description, modelFamily, inputModalities/outputModalities, inferenceAPIsSupported, inferenceTypesSupported, customizationsSupported, batchSupported, responseStreamingSupported, guardrailsSupported, latencyOptimizationSupported and modelLifecycle.startOfLifeTime / endOfLifeTime / legacyTime / publicExtendedAccessTime / status diverge across dozens of entries (modelLifecycle.startOfLifeTime in particular is absent on nearly every model AWS reports it for).

Why: ListFoundationModels is the discovery call every Bedrock client makes before it invokes anything. A client that decodes featuresSupported.batchInference into a struct fails to deserialize a bare boolean (and vice versa for an SDK expecting the struct), so the call errors outright rather than returning a usable catalog. A client that filters on converse.maxTokensMaximum, reasoningSupported.embedded or additionalRequestFieldsSchema to size a request sees those fields as unset and either skips the model or sends a request AWS would reject; one that reads userDocumentTypesSupported / userVideoTypesSupported believes a model accepts attachment types AWS does not advertise for it. A client that picks a model id out of the catalog may pick one AWS does not list in the region, or may not find one AWS does list, so model selection and any lifecycle/deprecation check diverge from AWS.

Fix: the bedrock service's built-in foundation-model catalog seed (the static table the ListFoundationModels handler serves) for the membership, per-model converse metadata, modelLifecycle timestamps and the remaining descriptive fields; and the ListFoundationModels output serializer for the capability members whose structured form is being flattened to a boolean (featuresSupported.*, explicitPromptCaching, intelligentPromptRouting) and for the ordering of the converse user*TypesSupported lists.
