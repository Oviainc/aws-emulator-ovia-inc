# AppSync tagging operations are not gated by identity-based IAM: a zero-policy principal's TagResource/UntagResource/ListTagsForResource succeed with 200 instead of AccessDeniedException/403

> _Note: this issue was identified against the code base at commit `ecf253bb3fa1c909a3ed3f4957712769073c494c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
1 cause in this issue; it must be closed before submitting.

=== Cause 1 of 1: no identity-based authorization decision is applied to the AppSync resource-tagging operations, so an unauthorized principal is served (and allowed to MUTATE tags) instead of denied ===

AWS: Smithy (com.amazonaws.appsync#AWSDeepdishControlPlaneService) models AccessDeniedException with errorKind=client and httpError=403 on all three tagging operations: TagResource (POST /v1/tags/{resourceArn}), UntagResource (DELETE /v1/tags/{resourceArn}) and ListTagsForResource (GET /v1/tags/{resourceArn}). Each carries the error set {AccessDeniedException 403, BadRequestException 400, LimitExceededException 429, NotFoundException 404, UnauthorizedException 401, InternalFailureException 500}. A SigV4-signed request whose IAM principal has no identity-based policy granting the corresponding appsync:<Action> is refused by implicit default deny with AccessDeniedException / HTTP 403 BEFORE the tag store is read or written, so a denied TagResource/UntagResource leaves the resource's tag map exactly as it was. The denial message is rule-derived from the request (principal ARN, action, resource ARN) and has the documented implicit-deny form: "User: <principal-arn> is not authorized to perform: appsync:<Action> on resource: <resource-arn> because no identity-based policy allows the appsync:<Action> action". The fixed text is "User: ", " is not authorized to perform: appsync:", " on resource: " and " because no identity-based policy allows the appsync:" + " action"; the variable parts are the calling principal's ARN (taken from the signing credentials), the action name (TagResource / UntagResource / ListTagsForResource) and the resourceArn from the request (the GraphQL API ARN, which the modelled ResourceArn pattern constrains to ^arn:aws:appsync:[A-Za-z0-9_/.-]{0,63}:\d{12}:apis/[0-9A-Za-z_-]{26}$). That derivation rule is the requirement — no single recorded ARN, user name or account id from one run is part of it.

Emulator: with credentials of a freshly created IAM user that has ZERO attached policies, the first denied-principal probe, TagResource(resourceArn=<api arn>, tags={<key>: "v"}), is ACCEPTED: HTTP 200 with an empty JSON body (content-type application/json, content-length 2). No AccessDeniedException is produced, so the check fails at the first probe with "expected the call to be rejected, but it succeeded". The remaining two probes (UntagResource, ListTagsForResource) are never reached, but they are served by the same un-gated dispatch path. Because the accepted call is a MUTATION, the emulator additionally persists a tag an unauthorized caller must never have been able to write, so the later assertion that the denied TagResource "must not have taken effect" is also unsatisfiable. The same three calls with the runner's own permissioned credentials (the check's positive control before and after) all succeed, so the operations are implemented and only the caller-authorization decision is absent — this is not a scaffold stub.

Why: this is an overly-permissive security boundary, and for tagging it is also an ABAC amplifier. A client, test or CI gate that verifies least privilege against the emulator ("a role without appsync:TagResource cannot retag my API", "an unprivileged principal cannot enumerate my API's tags") passes against the emulator while real AWS refuses the same call, so IAM-policy regressions are invisible. Code written to catch appsync.exceptions.AccessDeniedException and fall back (assume a role, re-sign, surface a permissions error) never takes that branch. Worse, because AppSync tags are commonly the subject of aws:ResourceTag conditions, an unauthorized principal that can write tags here can grant itself tag-conditioned access elsewhere, and the emulator's tag state diverges from what AWS would hold. ListTagsForResource additionally leaks the API's tag map (often containing cost-allocation and environment metadata) to any signed caller.

Note: the open issues 20261025T022306Z-appsync-graphql-api-control-plane-operations-are-not.md (GetGraphqlApi/UpdateGraphqlApi/DeleteGraphqlApi/Get+PutGraphqlApiEnvironmentVariables), 20261026T233737Z-appsync-channel-namespace-control-plane-get-update-deletechannelnamespace.md (Get/Update/DeleteChannelNamespace), 20261027T010308Z-appsync-listapis-and-listgraphqlapis-are-not-gated-by.md (ListApis/ListGraphqlApis) and 20261025T041655Z-appsync-event-api-domain-control-plane-no-identity.md (Event-API/domain operations) each describe a missing IAM default-deny gate on a DIFFERENT set of AppSync operations and none of them carries this check's replay key or names TagResource/UntagResource/ListTagsForResource. They do not cover this divergence; if the gate is implemented as one shared pre-dispatch layer, closing them may also close this one, but it must be verified against appsync.access-denied-tagging.

Fix: the request authorization layer in front of AppSync operation dispatch (the same pre-dispatch gate the other appsync IAM issues name), extended to cover the generic tagging operations — resolve the SigV4 principal, evaluate identity-based policy for appsync:TagResource / appsync:UntagResource / appsync:ListTagsForResource against the request's resourceArn, and refuse with the modelled AccessDeniedException (HTTP 403) carrying the implicit-deny message built from principal/action/resource BEFORE the TagResource/UntagResource/ListTagsForResource handlers touch the tag store, so a denied call neither reads nor writes tags.

Traces: appsync.access-denied-tagging.

## Evidence
Cause 1 — expected: each of TagResource(resourceArn=<api arn>, tags={k:"v"}), UntagResource(resourceArn=<api arn>, tagKeys=[k]) and ListTagsForResource(resourceArn=<api arn>), made with an access key of an IAM user created with no attached policies, is refused with error code `AccessDeniedException` / HTTP 403 and a message of the implicit-deny form `User: <user-arn> is not authorized to perform: appsync:<Action> on resource: <api-arn> because no identity-based policy allows the appsync:<Action> action`; afterwards the API's tag map does not contain the key the denied TagResource tried to write.

Actual (appsync.access-denied-tagging, check_appsync_access_denied_tagging.py line 92 -> _error line 28): `AssertionError: expected the call to be rejected, but it succeeded and returned {'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'application/json', 'content-length': '2', ...}, 'RetryAttempts': 0}}` — i.e. the unauthorized TagResource got HTTP 200 with an empty body `{}` instead of a 403 AccessDeniedException, and the tag write took effect. The check's positive control (TagResource -> ListTagsForResource -> UntagResource with the runner's permissioned credentials, both before the denial probes and in the post-denial restore) succeeded, so the three operations are implemented and only the caller-authorization decision is missing.

Smithy citation used: TagResource (POST /v1/tags/{resourceArn}), UntagResource (DELETE /v1/tags/{resourceArn}) and ListTagsForResource (GET /v1/tags/{resourceArn}) each list `AccessDeniedException` (errorKind client, httpError 403) in their error sets; input member `resourceArn` is an @httpLabel required ResourceArn with @length min 70 max 75 and pattern `^arn:aws:appsync:[A-Za-z0-9_/.-]{0,63}:\d{12}:apis/[0-9A-Za-z_-]{26}$`.
