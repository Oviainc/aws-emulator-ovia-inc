=== Cause 1 of 3: a control-plane operation sent to a discovered data endpoint is refused with a bare HTTP 404 carrying no error code on the wire, so an AWS client cannot classify it as UnknownOperationException ===
AWS: recorded behavior only — UnknownOperationException is not a modeled kinesisvideo shape; the model binds the control operations (Smithy com.amazonaws.kinesisvideo#DescribeStream, POST /describeStream -> 200, errors ClientLimitExceededException 400 / InvalidArgumentException 400 / NotAuthorizedException 401 / ResourceNotFoundException 404) to the control endpoint only, and Kinesis Video Media (com.amazonaws.kinesisvideomedia, restJson1) binds only its media routes to a data host. A data host therefore refuses a control-plane call, and the recording shows the refusal is classifiable by a restJson1 client: the error CODE is UnknownOperationException (the fixed, whole content of the identification — restJson1 carries it in the x-amzn-ErrorType response header, since there is no modeled body shape to put a __type in) and the refusal carries NO message member at all, so there is no variable part and no stream name or ARN appears anywhere in it.
Emulator: DescribeStream addressed to the DataEndpoint returned for APIName=PUT_MEDIA is answered HTTP 404 whose whole body is the framework's unrouted-path element and which sets no x-amzn-ErrorType header (services/.../src/service/data_plane_address.rs: unrouted_address_response builds RtResponse 404 with smithy_server_runtime::UNRECOGNISED_PROTOCOL_BODY and no error-type header, as its own doc comment states). A botocore kinesisvideo client therefore finds no error code to parse and reports the bare status: replay shows `AssertionError: the media host must not answer control-plane calls; DescribeStream against 'http://127.0.0.1:<port>' failed with '404' instead of UnknownOperationException` (the host and port are per-run values; the divergence is the absent error code). The 404 status itself is right; what is missing is the code the client branches on.
Why: a client cannot tell a wrong-plane call from any other 404. The documented re-discovery loop a KVS producer/consumer runs — catch the endpoint's refusal, call GetDataEndpoint again, retry — never fires, because botocore raises a generic ClientError whose Error.Code is '404' instead of UnknownOperationException, and error_code-based retry/branch logic in every SDK sees an unrecognised failure. Endpoint discovery becomes unverifiable from the client side.
Fix: the refusal rendering of the unrouted-on-a-data-plane-address answer in this service's routing seam — it must carry the UnknownOperationException code where a restJson1 client reads it (the x-amzn-ErrorType header) while keeping status 404 and carrying no message member.

=== Cause 2 of 3: the ingest DataEndpoint is one address shared by every stream, so PutMedia naming a stream other than the one the endpoint was discovered for is accepted with 200 and its fragments are persisted, instead of being refused 404 ResourceNotFoundException ===
AWS: recorded behavior only (PutMedia is in no SDK model; kinesisvideomedia declares GetMedia only, with common errors ResourceNotFoundException, InvalidEndpointException, NotAuthorizedException). A DataEndpoint is discovered PER STREAM — GetDataEndpoint takes StreamName/StreamARN precisely so the endpoint it hands back belongs to that stream — and the recording shows an ingest host serves ONLY the stream it was announced for: POST /putMedia whose x-amzn-stream-name names any other stream (an ACTIVE stream of the same account, or a name that exists nowhere) is refused with HTTP 404, response header x-amzn-ErrorType: ResourceNotFoundException, and an error acknowledgement whose Message states that the named stream is "not found or not active" — that clause is the fixed text; the stream name in the message is taken from the request's x-amzn-stream-name header (Smithy com.amazonaws.kinesisvideo#ResourceNotFoundException is documented "Amazon Kinesis Video Streams can't find the stream that you specified" and is httpError 404, which is the class this refusal belongs to). Nothing is persisted: neither the named stream nor the host's own stream gains a fragment.
Emulator: the ingest address is opened once per PLANE and keyed by plane alone, not per stream (services/.../src/state/data_endpoint.rs: ensure_data_endpoint stores one DataPlaneEndpoint per DataPlane in state.data_endpoints and its own doc says "the plane resolves to the same address for every stream"), so the ingest host has no stream identity to check a request against. PutMedia naming another ACTIVE stream of the account on this stream's ingest host is served normally: replay shows `AssertionError: PutMedia naming another ACTIVE stream of this account (<other stream name>) on <this stream name>'s ingest host expected HTTP 404, got 200` with a full acknowledgement stream (BUFFERING/RECEIVED/PERSISTED for each cluster) — the names, fragment numbers and timecodes in that output are per-run values; the divergence is the 200 and the persistence.
Why: cross-stream writes succeed silently. A producer that reuses a cached ingest endpoint for a different stream — or that has the wrong stream name in its configuration — gets 200 and believes its media landed where it asked, and a consumer of the intended stream sees fragments it never should, while the wrong-endpoint feedback (404 ResourceNotFoundException) that tells a producer to re-discover never arrives. The per-stream scoping of a DataEndpoint, which is the reason the discovery call takes a stream at all, is not emulated.
Fix: the PutMedia ingest handler's request admission together with the data-endpoint projection that owns the announced addresses — an announced ingest address has to be bound to the stream it was discovered for (or the handler has to check the request's stream against the endpoint's), and a request naming any other stream must be refused 404 ResourceNotFoundException with the "not found or not active" acknowledgement and no state change.

=== Cause 3 of 3: PutMedia is served without verifying the request's SigV4 signature, so a request signed without the x-amz-content-sha256 header is accepted with 200 and persists fragments instead of being refused 403 InvalidSignatureException ===
AWS: recorded behavior only (PutMedia is unmodeled; the kinesisvideomedia service declares authSchemes [sigv4]). The ingest front end verifies SigV4 over the request as signed, and because it never buffers the stream it is handed, the payload hash it requires is the x-amz-content-sha256 header with the value UNSIGNED-PAYLOAD; the recording shows the SAME bytes signed WITHOUT that header are refused with HTTP 403 and response header x-amzn-ErrorType: InvalidSignatureException, with nothing persisted — the status and the error code are the whole of the graded refusal, and they carry no value from the request.
Emulator: the request missing x-amz-content-sha256 is accepted and ingested exactly like the signed control: replay shows `AssertionError: the same bytes signed without x-amz-content-sha256 expected HTTP 403, got 200` followed by a full BUFFERING/RECEIVED/PERSISTED acknowledgement stream (the fragment numbers and timecodes there are per-run values). The data-plane front door applies only transport-safety predicates (Host allowlist, WebSocket refusal, browser check, size/deadline caps — services/.../src/state/data_plane_serving.rs refused_before_dispatch) and then forwards the request to the router unchanged, so no signature or signed-header requirement is enforced on the ingest path at all.
Why: an unauthenticated or mis-signed producer is indistinguishable from a correctly signed one. A client whose signing is broken — the single most common PutMedia integration failure, since the endpoint requires UNSIGNED-PAYLOAD rather than a body hash — is told 200 and that its media persisted, so the emulator cannot be used to develop or regression-test a producer's signing, and a 403-driven credential-refresh path in a producer never exercises.
Fix: the PutMedia ingest handler's authentication/validation stage on the announced data plane — verify the SigV4 signature over the request as presented, require the x-amz-content-sha256 header the signature must cover, and refuse a request that fails with HTTP 403 and x-amzn-ErrorType InvalidSignatureException, persisting nothing.
