# UpdateRoutingControlState safety-rule refusal message is non-AWS wording: it omits the quoted rule condition and the AllowSafetyRulesOverride remediation sentence, and reports internal counters instead

> _Note: this issue was identified against the code base at commit `334866e49a2e1dd36c287c2dd48bc4975a5ca561`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateRoutingControlState

## Description
One net-new root cause (Cause 1 of 1) for route53-recovery-control-config: the safety-rule enforcement stage on the Route 53 ARC cluster (data-plane) state-change path now REFUSES correctly (right error class, right status, state not moved), but words the refusal with its own sentence instead of the sentence AWS states, so the message a failover operator and a message-matching client read is wrong.

Cause 1 of 1: the ValidationException produced when a deployed safety rule blocks a routing-control state change carries an emulator-authored diagnostic sentence that (a) does not quote the rule's human-readable condition, (b) omits AWS's remediation sentence pointing at AllowSafetyRulesOverride in the Route 53 ARC Developer Guide, (c) omits the two labelled lines `Routing control: [<arn>]` and `Safety rule: <arn>`, and (d) instead leaks internal evaluation counters and the raw RuleConfig fields. Failing check: route53-recovery-control-config.safety-rule-threshold-exceeds-controls-rejected.

AWS: Smithy (route53-recovery-cluster / ToggleCustomerAPI, awsJson1_0) models UpdateRoutingControlState with errors AccessDeniedException (403), ConflictException (409), EndpointTemporarilyUnavailableException (503), InternalServerException (500), ResourceNotFoundException (404), ThrottlingException (429) and ValidationException (client, httpError 400), and models the input member SafetyRulesToOverride (list Arns) — the break-glass override the refusal must point the caller at. The model does not state the message text; for that this is recorded behavior only. The recording shows code ValidationException (HTTP 400) with a message whose FIXED text is, in order: `Can't update the routing control state because of a configured safety rule: "` … `." To override the rule and change the state, see the guidance for AllowSafetyRulesOverride in the Route 53 ARC Developer Guide. ` then a newline, `Routing control: [`, `] `, a newline, `Safety rule: `. Its VARIABLE parts, all taken from the request and from stored control-plane state, are exactly three: (1) inside the double quotes, the human-readable rendering of the blocking rule's condition derived from its stored RuleConfig — for an ATLEAST rule with Threshold N that is `At least N routing controls must be On` (N is the stored Threshold; the recording's `3` is this run's value, not part of the template); (2) inside the square brackets, the RoutingControlArn echoed verbatim from the request; (3) after `Safety rule: `, the SafetyRuleArn of the rule that blocked the request. Nothing else appears: no rule NAME, no count of controls, no raw Type/Threshold/Inverted triple.

Emulator: the same call is refused with code ValidationException (correct) but message `Routing control state update would violate the assertion safety rule '<rule name>' (<safety rule arn>): <k> of its <n> asserted routing controls would be On, which does not satisfy its rule configuration (Type <TYPE>, Threshold <N>, Inverted <bool>).` — in the replay: "Routing control state update would violate the assertion safety rule 'sim2real-r53arc-badthresh-…' (arn:…:safetyrule/…): 1 of its 2 asserted routing controls would be On, which does not satisfy its rule configuration (Type ATLEAST, Threshold 3, Inverted false)." None of AWS's fixed text is present. This is authored in one place: services/service-com-amazonaws-route53recoverycluster-togglecustomerapi/src/state.rs, fn safety_rule_violation_message (lines 391-411), whose format! string is the diverging sentence; it is reached from DataPlane::safety_rule_violation (lines 282-334, the message is built at line 328) and surfaced by services/service-com-amazonaws-route53recoverycluster-togglecustomerapi/src/ops/update_routing_control_state.rs lines 233-245, which copies violation.message straight into ValidationException.Message. The batch operation UpdateRoutingControlStates shares the same helper, so both operations state the same wrong sentence.

Why: this is the refusal an operator hits mid-failover, and AWS's wording is the only thing that tells them the way out — the `To override the rule and change the state, see the guidance for AllowSafetyRulesOverride` sentence, plus the two labelled lines giving the exact RoutingControlArn and SafetyRuleArn to retry with in SafetyRulesToOverride. Against the emulator that remediation text is absent, so a runbook or operator console that surfaces the message loses the break-glass instruction, and tooling that matches on the fixed prefix `Can't update the routing control state because of a configured safety rule:` (or parses the `Safety rule: ` line to populate SafetyRulesToOverride automatically) matches nothing and falls through to a generic failure path. Clients also cannot rely on the quoted condition being the rule's semantics (`At least N routing controls must be On`), because the emulator substitutes raw internal field values instead.

Fix: the message construction for this refusal — fn safety_rule_violation_message in this service's state module, the single place both UpdateRoutingControlState and UpdateRoutingControlStates word the refusal. It must emit AWS's template: the fixed prose above, with the condition rendered from the stored RuleConfig (ATLEAST -> `At least <Threshold> routing controls must be On`, with the AND/OR and Inverted forms rendered to their equivalent sentence), the request's RoutingControlArn in the brackets, and the blocking rule's SafetyRuleArn on the `Safety rule: ` line; drop the rule name, the would-be-On/evaluated counts and the raw Type/Threshold/Inverted triple, which AWS does not state. The ValidationException's status (400), code and the no-write behavior are already right and must not change. Note this is the wording-only remainder of the enforcement work filed as 20261030T111431Z-route53-recovery-cluster-data-plane-ignores-safety-rules.md (now fixed: the rule IS evaluated and the state no longer moves) and previously described, pre-enforcement, in the still-open 20261030T111123Z-route53-recovery-control-config-configured-safety-rules-are-never-evaluated-an-unsatisfiable.md; neither covers this failure, which the suite reports as a live unowned mismatch on the message assertion rather than on the refusal itself.

Traces: check route53-recovery-control-config.safety-rule-threshold-exceeds-controls-rejected (verdict mismatch).
