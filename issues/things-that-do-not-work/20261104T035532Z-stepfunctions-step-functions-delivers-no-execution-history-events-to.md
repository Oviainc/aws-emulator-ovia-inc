# Step Functions delivers no execution-history events to the loggingConfiguration CloudWatch Logs group, so every log-delivery check hangs to the 60 s cap

> _Note: this issue was identified against the code base at commit `c083bea380b29cc5238d586af0774e0d5864cbe3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStateMachine

## Description
Cause 1 of 1: a state machine created (or updated) with a loggingConfiguration naming a CloudWatch Logs vended log group never emits a single log event — or even a log stream — into that group, so execution logging is entirely inert.

AWS: Smithy (services/service-com-amazonaws-sfn-awsstepfunctions): CreateStateMachine.loggingConfiguration and UpdateStateMachine.loggingConfiguration target LoggingConfiguration{level: LogLevel enum [ALL, ERROR, FATAL, OFF], includeExecutionData: boolean (default false), destinations: LogDestinationList "Limited to size 1. Required, if your log level is not set to OFF"}; LogDestination.cloudWatchLogsLogGroup.logGroupArn is documented as "The ARN of the the CloudWatch log group to which you want your logs emitted to. The ARN must end with :*". LoggingConfiguration.level is documented as "Defines which category of execution history events are logged" and includeExecutionData as "Determines whether execution data is included in your log. When set to false, data is excluded." Beyond the model this is recorded behavior only, and the recordings show: once logging is configured at a non-OFF level, Step Functions creates a log stream under the named log group and writes one JSON log event per execution-history event, carrying at least the members `type` (the history event type, e.g. ExecutionStarted, TaskStateEntered, FailStateEntered, ExecutionSucceeded, ExecutionFailed), `id` (the history event id — the delivered ids form the contiguous sequence 1..N of that execution's history with no gaps or duplicates), and `execution_arn` (the ARN of the execution that produced it); with includeExecutionData=true the event also carries the execution input/output payload, and with includeExecutionData=false the same event types are delivered with the payload absent. The level selects which event types are delivered: ALL delivers every type; ERROR delivers the error-tier types (e.g. FailStateEntered, ExecutionFailed) and suppresses ExecutionStarted; FATAL delivers only the execution-terminal failure type (ExecutionFailed) and suppresses FailStateEntered and ExecutionStarted. A level whose events are all 'Not logged' for a given execution creates no log stream at all. Delivery becomes live a short time after the logging configuration is written, which is why each check runs a warm-up execution first and waits for it to land before grading.

Emulator: CreateStateMachine and UpdateStateMachine accept the loggingConfiguration without error and the executions themselves reach a terminal status, but the destination log group receives nothing: no log stream is created and FilterLogEvents/GetLogEvents on the group stay empty for the warm-up execution and for every graded execution afterwards. Every one of the seven checks below therefore blocks in its delivery barrier and is killed by the harness with the identical verdict `Check timed out after 60.0s`. Because the barrier is reached before the per-level, redaction, history-agreement and update-refusal assertions, none of those later assertions was even exercised — in particular `log-sfn-apigw-agreement-update-to-unqualified-log-group-arn-rejected-and-delivery-unchanged` requires UpdateStateMachine with a logGroupArn stripped of its trailing ':*' to be refused 400 InvalidLoggingConfiguration (a modeled error of UpdateStateMachine) with the message "Invalid Logging Configuration: Log Group ARN must be provided with '*' qualifier." — fixed text with no variable part — and that refusal can only be graded once delivery works.

Why: a client that relies on vended execution logs gets a silently empty audit trail. Operators who read execution history from CloudWatch Logs (the only record for EXPRESS workflows, and the usual record for standard ones) see nothing; metric filters, subscription filters and Logs Insights queries built on these events count zero; and tooling that distinguishes ALL/ERROR/FATAL tiers or relies on includeExecutionData redaction cannot observe any difference, so a misconfigured or over-sharing logging setup looks identical to a correct one.

Fix: the Step Functions service's execution-logging path — the component that turns a state machine's stored loggingConfiguration into CloudWatch Logs delivery (log-stream creation plus a per-history-event PutLogEvents emitter, with the level filter and the includeExecutionData redaction applied), in the sfn crate's execution engine/state rather than in the CreateStateMachine/UpdateStateMachine request validators, which already accept the configuration.

Traces: the seven failing checks listed under `### stepfunctions` in trace_ids, all with detail `Check timed out after 60.0s`; `stepfunctions.log-level-selects-which-history-events-reach-cloudwatch-logs` is the clearest example (four one-definition arms differing only in level/includeExecutionData, each with its own group). No open issue covers Step Functions vended log delivery; the nearby open issues 20261023T114649Z-sfn-step-functions-never-executes-task-states-every-execution.md and 20261024T043150Z-sfn-5-of-the-6-interpreter-causes-remain-open.md are about Task-state execution, not about logging, and do not cover this.

## Evidence
Expected (AWS, per the recordings): after a warm-up execution on a state machine whose loggingConfiguration is {level: ALL, includeExecutionData: true, destinations:[{cloudWatchLogsLogGroup:{logGroupArn: "<group ARN>:*"}}]}, the named log group holds a log stream whose events include {"type":"ExecutionStarted", "id":1, "execution_arn":"<the execution ARN>", ...input payload...} and {"type":"ExecutionSucceeded", ...}, with ids forming 1..N; an ERROR-level twin holds FailStateEntered/ExecutionFailed but no ExecutionStarted; a FATAL-level twin holds only ExecutionFailed; a purely successful execution on an ERROR/FATAL twin leaves the group with zero events and zero log streams; and an includeExecutionData=false twin holds the same event types with the input marker absent.

Actual (emulator): CreateStateMachine/UpdateStateMachine return success for the same loggingConfiguration, executions reach a terminal status, but the destination group never receives any log stream or log event. Every check blocks in its delivery barrier (_await_delivery_live / _warm_up / _await_log_types) and the harness reports `Check timed out after 60.0s` for all seven checks. One consequence of the same cause: `log-sfn-apigw-agreement-update-to-unqualified-log-group-arn-rejected-and-delivery-unchanged` never reaches its assertion that UpdateStateMachine with an unqualified log group ARN is refused 400 InvalidLoggingConfiguration / "Invalid Logging Configuration: Log Group ARN must be provided with '*' qualifier."

## Steps to Reproduce
1. Create an IAM role trusted by states.amazonaws.com with the documented log-delivery actions (logs:CreateLogDelivery, logs:GetLogDelivery, logs:UpdateLogDelivery, logs:DeleteLogDelivery, logs:ListLogDeliveries, logs:PutResourcePolicy, logs:DescribeResourcePolicies, logs:DescribeLogGroups, logs:CreateLogStream, logs:PutLogEvents on Resource "*").
2. logs.CreateLogGroup for a group under /aws/vendedlogs/states/.
3. sfn.CreateStateMachine with a trivial definition (Choice -> Pass / Fail), the role above, and loggingConfiguration={level:"ALL", includeExecutionData:true, destinations:[{cloudWatchLogsLogGroup:{logGroupArn:"arn:aws:logs:<region>:<account>:log-group:<group>:*"}}]}.
4. sfn.StartExecution with input {"mode":"ok","marker":"<marker>"} and wait for the execution to reach SUCCEEDED.
5. Poll logs.DescribeLogStreams / logs.FilterLogEvents on the group. Expected: a log stream containing ExecutionStarted and ExecutionSucceeded events naming the execution ARN and carrying the marker. Observed: no streams and no events, indefinitely.
6. Repeat step 3 with level="ERROR" and level="FATAL" twins and a failing execution (input {"mode":"boom"}): expected FailStateEntered/ExecutionFailed (ERROR) and ExecutionFailed only (FATAL); observed nothing in either group.
