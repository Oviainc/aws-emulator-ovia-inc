# autoscaling__ec2__elbv2: 2 net-new causes — an ASG-registered EC2 target never reaches healthy/HTTP-200 through its ALB and never feeds an ELB verdict back into the group, and an NLB target never produces any health verdict (no unhealthy on a security group that blocks :4000, no healthy after the CIDR is admitted)

> _Note: this issue was identified against the code base at commit `f1f9f5b66979f27b8680cd8e6119d18c6179a071`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTargetHealth

## Description
Two net-new root causes in the Auto Scaling -> ELBv2 target-health feedback path. Both surface as the harness's hard 180 s cap being reached: every convergence poll in these checks (420-600 s budgets, 10-15 s intervals) keeps reading the same non-converging value, so the check never gets past its first wait. Neither check is claimed by an open issue; the closest open items are 20261107T075601Z-autoscaling-ec2-elbv2-auto-scaling-elbv2-asg-instances-never-register-with.md and 20261107T173527Z-autoscaling-ec2-elbv2-auto-scaling-elbv2-asg-instances-are-never-registered.md, which cover registration appearing in DescribeTargetHealth at all; these two causes are about the health VERDICT and the data plane behind it, and the report did not mark either check as owned by them.

Cause 1 of 2: an instance an ASG registers into a target group never becomes healthy, the ALB never serves its body, and HealthCheckType=ELB never feeds back into the group.
AWS: Smithy (elasticloadbalancingv2) — DescribeTargetHealth returns TargetHealthDescriptions[].TargetHealth{State,Reason,Description}; TargetHealthStateEnum = initial|healthy|unhealthy|unhealthy.draining|unused|draining|unavailable, and TargetHealthReasonEnum documents that while a newly registered target is coming up the State is `initial` with Reason `Elb.RegistrationInProgress` then `Elb.InitialHealthChecking`, and that once the configured HealthyThresholdCount of probes pass the State becomes `healthy` with NO Reason and NO Description ("If the target state is healthy, a reason code is not provided"). AWS's documented ASG contract (attach-load-balancer-asg) is that CreateAutoScalingGroup with TargetGroupARNs registers each launched instance into every listed target group, and with HealthCheckType=ELB the load balancer's verdict is the instance's health: Smithy (autoscaling) Instance.LifecycleState (enum, includes `InService`) and Instance.HealthStatus ("The last reported health status of the instance. Healthy means that the instance is healthy and should remain in service"). An ALB listener forwarding to that group must then answer the request from the registered instance (HTTP 200 carrying that instance's own body).
Emulator: the check registers one instance through the ASG, then polls DescribeTargetHealth for `healthy` (600 s), an HTTP GET through the ALB DNS name for a 200 whose body carries the instance's marker (420 s), and DescribeAutoScalingGroups for Instances[0].LifecycleState==InService with HealthStatus==Healthy (600 s). None of those predicates is ever satisfied — the check is killed at the harness's 180 s cap with no intervening assertion failure, i.e. the polled values never move to the AWS-documented terminal ones.
Why: a client that waits for a target to go healthy before shifting traffic (every blue/green cutover, every CodeDeploy/CFN wait condition, every `aws elbv2 wait target-in-service`) waits forever, and a client that reads ASG instance health to decide whether its fleet is serving sees a group that never reports a healthy, in-service instance even though the ALB was created and the instance launched. Capacity decisions driven off HealthCheckType=ELB are therefore unmakeable.
Fix: the ELBv2 target-health evaluator for instance-type target groups (it must drive registered targets out of `initial` to `healthy`/`unhealthy` instead of parking them) plus the ALB listener's forwarding path to instance targets, and the Auto Scaling health-check ingestion that copies the ELB verdict onto Instance.HealthStatus/LifecycleState.
Traces: autoscaling__ec2__elbv2.asg-target-group-registration-serves-http-and-feeds-back-health.

Cause 2 of 2: an NLB produces no health verdict at all for an ASG instance — not the unhealthy verdict a security group with no :4000 ingress rule requires, and not the healthy verdict after the NLB subnet's CIDR is admitted.
AWS: Smithy (elasticloadbalancingv2) — TargetHealthReasonEnum documents `Target.FailedHealthChecks` as "The load balancer received an error while establishing a connection to the target or the target response was malformed". AWS evaluates NLB health probes against the target instance's security groups, so with a cluster security group whose only ingress rules are self-references (TCP 988 from self, all traffic from self, TCP 1018-1023 from self) and NO rule admitting the health-check port from any IP range, the TCP connect to the target's :4000 responder is dropped and DescribeTargetHealth must report State=`unhealthy` with Reason=`Target.FailedHealthChecks` once UnhealthyThresholdCount consecutive probes fail. After AuthorizeSecurityGroupIngress admits tcp/4000 from the NLB subnet's CIDR, the same target must transition to State=`healthy` with no Reason. The check deliberately polls for the FIRST non-`initial` verdict so that a wrong verdict fails immediately rather than timing out.
Emulator: the target never leaves `initial` — the poll for "any verdict other than initial" never fires, so the emulator is killed at the 180 s cap before even the negative half can be graded. The emulator therefore neither honours security-group evaluation for NLB health probes nor converges an NLB target group's health state. Hypothesis: the NLB health-check evaluator is absent entirely, which is why no verdict (right or wrong) is produced in either half.
Why: security-group misconfiguration is the single most common cause of an unreachable NLB target in production, and the whole diagnostic loop depends on DescribeTargetHealth saying `unhealthy`/`Target.FailedHealthChecks` before the rule is added and `healthy` after it. Against this emulator the same target reads `initial` forever, so a client cannot distinguish "blocked by the security group" from "still registering", and a remediation that actually fixed the path is indistinguishable from one that did nothing.
Fix: the ELBv2 NLB target-health evaluator (it must probe the target's health-check port and apply the target's security-group ingress rules when deciding reachability) and its transition out of `initial` into `healthy`/`unhealthy` with the modelled Reason.
Traces: autoscaling__ec2__elbv2.asghc-nlb-target-stays-unhealthy-on-the-cluster-sg-until-the-subnet-cidr-is-admitted.

## Evidence
Check autoscaling__ec2__elbv2.asg-target-group-registration-serves-http-and-feeds-back-health — verdict [mismatch], detail "Error: Check timed out after 180.0s".
Expected (AWS): after CreateAutoScalingGroup(TargetGroupARNs=[tg], HealthCheckType=ELB, DesiredCapacity=1) and the instance launching, DescribeTargetHealth(tg) reports {<instance-id>: State=healthy, no Reason}; GET http://<alb-dns-name>/ answers 200 with the instance's own body; DescribeAutoScalingGroups(<asg>).Instances[0] reports LifecycleState=InService, HealthStatus=Healthy, DesiredCapacity=1.
Actual (emulator): none of those three predicates is ever reached — the health state never becomes healthy, no 200 is served through the load balancer, and the group's instance never reports InService/Healthy; the check is cut off at the harness cap with no assertion ever firing.

Check autoscaling__ec2__elbv2.asghc-nlb-target-stays-unhealthy-on-the-cluster-sg-until-the-subnet-cidr-is-admitted — verdict [mismatch], detail "Error: Check timed out after 180.0s".
Expected (AWS): with the instance's security group admitting nothing from any IP range (self-references only) and the target group configured HealthCheckProtocol=HTTP, HealthCheckPort=4000, HealthCheckPath=/health-check, HealthCheckIntervalSeconds=10, HealthCheckTimeoutSeconds=5, UnhealthyThresholdCount=2, DescribeTargetHealth(tg) == {<instance-id>: (State="unhealthy", Reason="Target.FailedHealthChecks")}; after AuthorizeSecurityGroupIngress(tcp/4000 from the NLB subnet CIDR), DescribeTargetHealth(tg) == {<instance-id>: (State="healthy", Reason=None)} and the EC2-health-check group still reports its one instance as HealthStatus=Healthy.
Actual (emulator): DescribeTargetHealth never reports any state other than "initial" for that target, in either half; the first-verdict poll never fires and the check is cut off at the harness cap.

The fixed text of the diverging values is the enum vocabulary itself — the State strings "initial"/"healthy"/"unhealthy" and the Reason string "Target.FailedHealthChecks"; the instance id, target-group ARN, load-balancer DNS name, subnet CIDR and body marker are per-run values taken from the request and the emulator's own state, not part of the requirement.

## Steps to Reproduce
Cause 1: in the shared VPC, create an instance-type target group and an internet-facing ALB with a listener forwarding to it; create a launch template running a trivial HTTP server on :80; CreateAutoScalingGroup with TargetGroupARNs=[that group], HealthCheckType=ELB, Min=Max=Desired=1. Then poll DescribeTargetHealth for the launched instance reaching State=healthy, GET http://<alb-dns>/ for a 200 carrying the instance's body, and DescribeAutoScalingGroups for Instances[0].LifecycleState=InService with HealthStatus=Healthy. Observe all three never converge.

Cause 2: create an isolated VPC (172.25.0.0/16) with one /23 subnet, a security group whose ingress is self-references only (no IP-range rule for tcp/4000) and whose egress is self plus the region's S3 prefix list; create a launch template whose user data serves 200 on :4000/health-check; create an HTTP:4000 target group (interval 10, timeout 5, unhealthy threshold 2), an internal NLB in that subnet and a listener onto the group; CreateAutoScalingGroup with HealthCheckType=EC2, Min=Max=Desired=1 and that target group. Poll DescribeTargetHealth for the first non-"initial" verdict: expect ("unhealthy","Target.FailedHealthChecks"). Then AuthorizeSecurityGroupIngress tcp/4000 from the subnet CIDR and poll again: expect ("healthy", None). Observe the target stays "initial" in both halves.
