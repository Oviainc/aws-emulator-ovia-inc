# bedrock-agent__lambda__opensearchserverless: the RetrieveAndGenerate end-to-end path never completes — the knowledge-base build stalls on the AOSS collectionEndpoint index create and the check burns its whole budget instead of answering

> _Note: this issue was identified against the code base at commit `256a0363d1d84a79f79b1b2146ae7b4a065def33`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RetrieveAndGenerate

## Description
Cause 1 of 1: the only RetrieveAndGenerate end-to-end check in this suite never reaches an answer — it exhausts its time budget with no response at all. Failing check id: bedrock-agent__lambda__opensearchserverless.lambda-bedrock-agent-retrieve-and-generate-positive.

AWS: recorded behavior only for the stalling leg. An OpenSearch Serverless collection's published `collectionEndpoint` (the value BatchGetCollection returns in collectionDetails[].collectionEndpoint) is the OpenSearch REST data plane, signed SigV4 with service name `aoss`; `PUT <collectionEndpoint>/<index-name>` with a knn_vector mapping body creates the vector index and answers 200/201 with the OpenSearch index-create body, and it is the step a Bedrock vector knowledge base is built on. The recording shows that PUT succeeding and then the knowledge base ingesting and serving a grounded answer. For the operation the check is actually about, Smithy (bedrock-agent-runtime, services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice): RetrieveAndGenerate is POST /retrieveAndGenerate -> 200 with required members `sessionId` and `output` (output.text), plus `citations` (list of Citation, each with retrievedReferences[].content.text). Its modeled refusals are AccessDeniedException 403, BadGatewayException 502, ConflictException 409, DependencyFailedException 424, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 400, ThrottlingException 429, ValidationException 400. Every outcome AWS can produce here is therefore a bounded one: either a 200 carrying output.text and at least one citation whose retrievedReferences[].content.text contains the ingested document text, or one of those modeled errors with its code and message. AWS never leaves the call hanging.

Emulator: the check produces no response of any kind — the replay verdict is a mismatch whose entire detail is `Check timed out after 60.0s`. The check's knowledge-base build (_build_ready_knowledge_base) creates the encryption/network/data-access policies and a VECTORSEARCH collection, waits for ACTIVE, then retries `PUT <collectionEndpoint>/sim2real-vectors` in a 2-second loop against its own 180s deadline, and only after that does it create the knowledge base, ingest and invoke RetrieveAndGenerate through a Lambda. The emulator never gets past that retry loop within the harness budget, so RetrieveAndGenerate is never answered and no status, error code or body is ever emitted. Hypothesis: the stall is the same data-plane front-door defect the sibling checks in this service report as a 400 SerializationException 'missing required header x-amz-target' from the published collectionEndpoint (open issues 20261104T034157Z-bedrock-agent-lambda-opensearchserverles-...-the-published-vectorsearch-collection.md, 20261102T091854Z-bedrock-agent-lambda-opensearchserverles-...-a-vectorsearch-collection-endpoint.md and 20261104T072704Z-opensearchserverless-the-published-collectionendpoint-serves-the-aws-json.md); none of those issues carries this check's replay key, and the suite did not mark this check as owned by any of them, so it is filed here. Whatever the refused leg turns out to be, the emulator-visible divergence asserted by this check is that the whole path produces nothing within the budget rather than either the modeled 200 or one of the modeled refusals.

Why: a client doing retrieval-augmented generation against the emulator cannot complete the documented build-ingest-answer sequence and cannot even discover why. A bounded refusal (AccessDeniedException, DependencyFailedException, ValidationException) would let a client branch; an unbounded stall makes every caller and every CI job hang until its own timeout, and it hides which leg is unimplemented. Nothing a client writes against AWS's RetrieveAndGenerate contract — reading output.text, counting citations, checking that a retrievedReferences[].content.text contains the ingested fact — can be exercised at all.

Fix: the OpenSearch Serverless data-plane front door reached at the collectionEndpoint published by BatchGetCollection (the opensearchserverless crate's endpoint routing/serializer, which must dispatch the SigV4 `aoss` OpenSearch REST verbs — PUT /<index>, POST /<index>/_search, POST /<index>/_doc — rather than the AWS-JSON RPC front door), and then the bedrock-agent-runtime RetrieveAndGenerate handler plus its citation serializer so the knowledge-base path returns the modeled RetrieveAndGenerateResponse. Any leg that is not implemented must answer the modeled error for its class promptly instead of leaving the request open.

Traces: bedrock-agent__lambda__opensearchserverless.lambda-bedrock-agent-retrieve-and-generate-positive (verdict mismatch, detail `Check timed out after 60.0s`).

Any failure instead arrives as one of the modeled errors with its code and message: AccessDeniedException 403, BadGatewayException 502, ConflictException 409, DependencyFailedException 424, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 400, ThrottlingException 429, ValidationException 400.

Actual (emulator): no response at all. The suite reports
  [mismatch] bedrock-agent__lambda__opensearchserverless.lambda-bedrock-agent-retrieve-and-generate-positive

No HTTP status, no error code and no body are ever produced for RetrieveAndGenerate: the run does not get past the knowledge-base build's AOSS index-create retry loop. Message-shape note: the fixed text required here is the modeled error codes above; the only variable parts of a correct response are the generated sessionId, the generated answer text and the retrieved reference text (which must contain the ingested document's wording). The 60.0s figure is this harness's budget, not a requirement.
