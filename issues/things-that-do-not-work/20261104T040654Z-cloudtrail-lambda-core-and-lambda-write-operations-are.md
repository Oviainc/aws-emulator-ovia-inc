# cloudtrail: lambda-core and lambda write operations are never recorded as CloudTrail management events, so LookupEvents never returns them and audit-trail workflows never converge

> _Note: this issue was identified against the code base at commit `b4ead8169e48e6047949699a772a41fd75a6bc4d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
One net-new root cause on the CloudTrail event-history path shared by lambda-core (com.amazonaws.lambdacore#LambdaCoreApiService) and classic Lambda (com.amazonaws.lambda), grounded in the one failing behavioral check under this heading that is neither ALREADY FILED nor OWNED.

Cause 1 of 1 - a successful control-plane WRITE in lambda-core (CreateNetworkConnector) and in lambda (PublishLayerVersion) produces no CloudTrail management-event record at all, so CloudTrail LookupEvents answers 200 with an empty Events list for those event names forever and a client that polls event history for its own write never sees it.

AWS: CloudTrail LookupEvents (cloudtrail 2013-11-01, awsQuery/JSON RPC, `LookupEvents`) "looks up management events or CloudTrail Insights events that are captured by CloudTrail" for the Region the request is made in, filtered by a single LookupAttribute (here AttributeKey=EventName). Each returned Event carries EventSource plus a CloudTrailEvent string holding the audit record, whose contents are the documented record format (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-event-reference-record-contents.html): eventSource, eventName, eventID, eventCategory, awsRegion, recipientAccountId, readOnly, requestParameters, and errorCode only on a failed call. lambda-core's own Smithy model declares `cloudTrailEventSource` = "lambda.amazonaws.com" - the SAME source classic Lambda declares - and CreateNetworkConnector (POST /2026-04-04/network-connectors, success 202) carries no @readonly trait, so it is a write. The requirement is therefore: after a successful CreateNetworkConnector, event history holds a Management record with eventSource="lambda.amazonaws.com", eventName="CreateNetworkConnector", readOnly=false, no errorCode, awsRegion = the request's Region, recipientAccountId = the caller's account, a unique eventID, and requestParameters naming that connector; after a successful PublishLayerVersion, a second, distinct record under the same source with eventName="PublishLayerVersion20181031" (classic Lambda's eventName carries its per-operation REST URI version suffix) naming only the layer. Recorded behavior: the check polls LookupEvents until each record appears and the recording returns both inside the indexing budget. The identifying members (eventSource/eventName/eventCategory/readOnly) are the requirement; eventID values, timestamps and generated resource names are per-run values.

Emulator: LookupEvents itself is implemented and reads a shared management-event store (`::service_common::management_events::ManagementEvent`, imported at services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/lookup_events.rs lines 120-122), but nothing in lambda-core or lambda ever WRITES into that store: services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/ops/create_network_connector.rs and services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/publish_layer_version.rs reference no management-event recorder at all. So LookupEvents(LookupAttributes=[{EventName: CreateNetworkConnector}]) answers HTTP 200 with Events=[] and no NextToken after a connector was successfully created, and the check's poll loop (2 s interval, 255 s budget) can never satisfy its predicate; the replay reports it as "Check timed out after 60.0s". Hypothesis (the replay emits no traceback, so the exact stalled call is not stated by the report): the stall is in the first `_await_record` poll over LookupEvents, because that is the only unbounded wait reached before the assertions and the two producing operations demonstrably record nothing. The two other waits in the check cannot stall it: the create retry only loops on an operator-role propagation message the emulator does not emit, and `_await_not_pending` runs only AFTER all the assertions.

Why a client gets this wrong: every audit, compliance and "who changed this" workflow reads a write back out of CloudTrail event history. Against the emulator such a workflow blocks until its own deadline and then reports that the operation was never audited, which is indistinguishable from a real missing-trail defect. Worse for the contract this check exists to pin: because NO record exists, the separability guarantees of a shared cloudTrailEventSource - two different services (lambda-core and lambda) auditing under one eventSource yet keeping distinct eventName and eventID and never naming each other's resource - are entirely unverifiable, and nothing stops a later implementation from keying the source on the service or crate name (emitting "lambdacore.amazonaws.com") or collapsing the two services into one audit entry.

Fix: the write path, not the reader. lambda-core's CreateNetworkConnector handler (and the other non-readonly lambda-core operations) and classic Lambda's PublishLayerVersion handler must record a ManagementEvent into the shared `service_common::management_events` store that CloudTrail's LookupEvents already reads, using each service's modeled cloudTrailEventSource ("lambda.amazonaws.com" for BOTH services, taken from the Smithy trait rather than from the service or crate name), the operation's own eventName (with classic Lambda's version suffix), eventCategory=Management, readOnly=false for a write, the request's Region and the caller's account, a freshly minted unique eventID per call, and requestParameters holding only that call's own input members. CloudTrail's LookupEvents handler needs no change.

## Evidence
Behavioral suite simparity-behavioral-aws-v1 replayed against the emulator built from this checkout: 23/29 passed (79.3%), 5 mismatched, 1 errored, bootstrap_signal false (the emulator answered calls in this check - EC2, IAM, STS, lambda-core and lambda all responded).

[mismatch] cloudtrail__lambda-core.two-services-sharing-one-event-source-stay-distinguishable-in-the-audit-record
  Error: Check timed out after 60.0s

The check (GROUP=eventing, SERVICES=[cloudtrail, lambda-core]) does, in order: resolve a subnet and the default security group in the shared network, create an IAM operator role trusting lambda.amazonaws.com and wait for the attached AWSLambdaNetworkConnectorOperatorPolicy to be visible, CreateNetworkConnector (asserting a non-empty Id, which it got), PublishLayerVersion for a tiny layer zip (asserting the layer ARN prefix), and THEN its two terminal reads:
    core_record, core_event = _await_record(ct, "CreateNetworkConnector", connector_name)
    lambda_record, lambda_event = _await_record(ct, "PublishLayerVersion20181031", layer_name)
where `_await_record` pages ct.lookup_events(LookupAttributes=[{"AttributeKey": "EventName", "AttributeValue": <eventName>}]) every 2 s for up to 255 s and fails with "DATAPLANE_UNIMPLEMENTED: no <eventName> record naming <resource> within <budget>s; expected 1, actual 0 of N <eventName> records examined" if none appears.

Expected (AWS): the first poll iteration (or one shortly after) returns an Event whose CloudTrailEvent parses to eventSource='lambda.amazonaws.com', eventName='CreateNetworkConnector', eventCategory='Management', readOnly=false, errorCode absent, awsRegion = the request Region, recipientAccountId = the caller's account, requestParameters containing the connector name; and a second, distinct Event (different eventID) for eventName='PublishLayerVersion20181031' naming the layer, under the same eventSource.
Actual (emulator): LookupEvents answers HTTP 200 with an empty Events list for both event names - no record is ever produced, because neither producing handler writes into the management-event store CloudTrail's LookupEvents reads - so the poll loop cannot terminate and the harness cuts the check at its 60 s budget. None of the eventSource / eventName / eventID / requestParameters assertions is ever evaluated.
(The generated connector name, layer name, account id and timestamps in the recording are per-run values and are not part of the requirement; the diverging fact is that zero management-event records exist for these two writes.)

## Steps to Reproduce
1. git_clone, then run_behavioral_suite() and look at check cloudtrail__lambda-core.two-services-sharing-one-event-source-stay-distinguishable-in-the-audit-record.
2. Or by hand against the booted emulator (region us-west-2):
   a. Create (or resolve) a VPC with a subnet and its default security group in EC2, and an IAM role whose trust policy names lambda.amazonaws.com with AWSLambdaNetworkConnectorOperatorPolicy attached.
   b. POST /2026-04-04/network-connectors with Name=<unique>, Configuration={"VpcEgressConfiguration":{"SubnetIds":[<subnetId>],"SecurityGroupIds":[<sgId>],"NetworkProtocol":"IPv4","AssociatedComputeResourceTypes":["MicroVm"]}}, OperatorRole=<roleArn>. Observe 202 with an Id (succeeds).
   c. Call lambda PublishLayerVersion with a small zip. Observe success.
3. Call CloudTrail LookupEvents with LookupAttributes=[{"AttributeKey":"EventName","AttributeValue":"CreateNetworkConnector"}], paging NextToken to exhaustion. Expect at least one Event whose CloudTrailEvent names the connector created in 2b, with eventSource='lambda.amazonaws.com', eventName='CreateNetworkConnector', eventCategory='Management', readOnly=false and no errorCode. Observe HTTP 200 with Events=[] - no record at all, however long you poll.
4. Repeat step 3 with AttributeValue="PublishLayerVersion20181031" and expect a second, distinct record (different eventID, same eventSource) naming the layer from 2c. Observe Events=[] again.
5. Because no record is ever indexed, the audit-separability assertions (shared eventSource, distinct eventName/eventID, each record naming only its own resource and never the other's) cannot be evaluated at all.
