=== Cause 1 of 2: an HTTP API route backed by an AWS_PROXY integration answers 500 {"message":"Internal Server Error"} instead of the function's proxy response, so eight distinct data-plane behaviours never reach their own verdict. ===
Failing checks: apigatewayv2.deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore, apigatewayv2.delete-route-stops-delivery-on-autodeploy, apigatewayv2.e2e-custom-domain-mapping-invoke, apigatewayv2.http-api-path-without-stage-prefix-not-delivered, apigatewayv2.http-api-stage-requires-deployment-before-serving, apigatewayv2.http-api-unmatched-route-key-not-delivered, apigatewayv2.lambda-authorizer-context-propagates-to-integration-event, apigatewayv2.lambda-payload-format-1-0-and-2-0-envelopes-differ.

AWS: recorded behavior only for the data plane — execute-api carries no Smithy model. Smithy grounds the control-plane setup these checks build: CreateIntegration.IntegrationType (enum IntegrationType, required) with PayloadFormatVersion (StringWithLengthBetween1And64) and TimeoutInMillis @range 50..30000 (POST /v2/apis/{ApiId}/integrations, 201); CreateDeployment (POST /v2/apis/{ApiId}/deployments, 201) whose output carries DeploymentId/DeploymentStatus/AutoDeployed; UpdateApi.DisableExecuteApiEndpoint (boolean, jsonName disableExecuteApiEndpoint, PATCH /v2/apis/{ApiId}); CreateAuthorizer.AuthorizerType/IdentitySource/EnableSimpleResponses/AuthorizerPayloadFormatVersion. The recordings show that a deployed HTTP API route whose AWS_PROXY integration targets a Lambda returning {"statusCode":200, "headers":{...}, "body":<marker>} serves HTTP 200 with that body verbatim on the FIRST probe of the stage invoke URL. On top of that positive control the recordings pin these eight behaviours, every one of which the gateway (not the backend) decides:
  (a) UpdateApi(DisableExecuteApiEndpoint=true) stops the default https://{api-id}.execute-api.{region}.amazonaws.com endpoint routing: every request answers 404 with body {"message":"Not Found"} and the backend never runs; a twin API left enabled keeps serving in the same instant; flipping the flag back restores 200 and the backend body. Fixed text: the status 404 and the exact body {"message":"Not Found"} — there are no request- or state-derived parts in it. Note AWS uses 404 here, NOT the 403 a REST API's disabled endpoint returns.
  (b) DeleteRoute on an AutoDeploy stage takes the route off the data plane: the deleted route's path converges on 404 {"message":"Not Found"} and never reaches the integration again, while a sibling route on the same integration keeps serving.
  (c) An API whose only stage is a NAMED stage serves nothing at the bare host: a request without the stage prefix, and a request under a stage name that does not exist, both answer 404 {"message":"Not Found"}.
  (d) A stage created with AutoDeploy=false and no DeploymentId does not serve its routes: 404 {"message":"Not Found"} even though route and integration exist; CreateDeployment(StageName=<stage>) lifts the gate, the same URL then serves the backend body with requestContext.stage equal to that stage, and GetStage.DeploymentId is the new deployment id.
  (e) A request matching no route key is not delivered: a non-matching path and a non-matching method on a method-scoped route key both answer 404 {"message":"Not Found"}, never the integration's body.
  (f) A payload-format-2.0 REQUEST authorizer's simple-response `context` map reaches the downstream AWS_PROXY event as requestContext.authorizer.lambda with each value's ORIGINAL JSON type preserved (string stays string, number stays number, boolean stays boolean) and no extra keys. The HTTP-API (v2) behaviour is NOT the REST-API (v1) stringification the developer guide describes.
  (g) Two integrations on one function differing only in PayloadFormatVersion deliver structurally different events for the same HTTP request: 1.0 carries httpMethod/path/resource/multiValueHeaders/multiValueQueryStringParameters and no rawPath or cookies; 2.0 carries rawPath/rawQueryString/cookies, no multi-value maps, and comma-joins a repeated query key.
  (h) A custom domain name mapped to an HTTP API stage routes real HTTPS invokes to the mapped integration.
Emulator: the stage invoke URL accepts the request and then answers HTTP 500 with body {"message":"Internal Server Error"}. deep-apigatewayv2-2-enforce-disable-execute-api-endpoint-404-and-restore asserts its precondition and reports it directly: "precondition: the target API must serve GET /hit with marker '<marker>' while its execute-api endpoint is enabled; got 500: '{"message":"Internal Server Error"}'". The other seven poll the same positive control for 200-plus-marker (90 s / 120 s poll budgets) and never observe it, so the runner kills them at its 60 s cap with "Check timed out after 60.0s" before any of (a)-(h) is asserted. So the listener resolves a route and then fails internally instead of invoking the integration and translating its proxy response.
Why: a client gets an unconditional 5xx from every HTTP API backed by a Lambda proxy integration, which is the normal shape of an HTTP API. No application can be run against the emulator; worse, 500 is indistinguishable from a genuine backend fault, so callers retry requests AWS would have served. And because the whole 404 non-delivery family above is unobservable, an emulator that quietly delivers traffic AWS drops (a deleted route, a disabled endpoint, an undeployed stage, an unmatched route key, a missing stage prefix) would not be caught: those are the exact surprises users hit in production.
Fix: the execute-api HTTP data-plane request handler for AWS_PROXY integrations — route resolution, proxy-event construction per PayloadFormatVersion, Lambda invocation, and the translation of the function's return value back into an HTTP response — together with its error mapping, which must not collapse an internal failure into 500 for a well-formed request. The non-delivery legs additionally need the stage/deployment gate (a stage serves only the routes of the deployment it names; $default + AutoDeploy republishes on route create/delete), the DisableExecuteApiEndpoint edge gate, and the REQUEST-authorizer context propagation into the integration event.
Traces: the eight check ids listed at the head of this cause. Handler area: services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ (data plane) and services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs for the invocation it depends on.

=== Cause 2 of 2: a WEBSOCKET route's integration response is never gated on a RouteResponse, because the deployed WEBSOCKET stage never serves a client socket at all. ===
Failing check: apigatewayv2.websocket-two-way-route-needs-a-route-response-to-reach-the-client.
AWS: recorded behavior only for the socket; Smithy models the gate's control plane — CreateRouteResponse (POST /v2/apis/{ApiId}/routes/{RouteId}/routeresponses, 201) with RouteResponseKey required, and CreateDeployment/CreateStage for the deployment. The recording shows: a WEBSOCKET route declared two-way but with NO RouteResponse runs its integration, yet the client's socket stays silent — the integration's response is not delivered as a frame; after CreateRouteResponse the identical message arrives at the client as a text frame.
Emulator: the check is killed at the 60 s cap ("Check timed out after 60.0s") before either leg is asserted: the deployed WEBSOCKET stage never completes the RFC 6455 upgrade, so no socket exists on which to observe either the silence or the post-CreateRouteResponse delivery.
Why: a client cannot distinguish "the integration ran and the gateway withheld the reply" from "the integration never ran". An emulator that pushes the integration result to the socket whether or not a RouteResponse exists lets a two-way route appear to work in the emulator and go silent on real AWS, which is the single most common WebSocket API surprise.
Fix: the execute-api WEBSOCKET data plane — the RFC 6455 upgrade on a deployed stage, frame dispatch to the selected route, and the RouteResponse gate in front of delivering an integration response back to the client.
Traces: apigatewayv2.websocket-two-way-route-needs-a-route-response-to-reach-the-client. Handler area: services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ (WebSocket data plane) and the vendored listener's upgrade path.
