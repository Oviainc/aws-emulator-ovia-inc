# Redshift resource-policy and namespace-registration semantics diverge: unsupported resource types accepted, InvalidPolicyFault wording, policy canonicalization, and register/deregister preconditions (5 causes)

> _Note: this issue was identified against the code base at commit `f099a2d3bf6bcdb075a9bf115e0dc86bb75f03d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutResourcePolicy

## Description
Five net-new root causes on the Redshift resource-policy and namespace-registration surface. All five were observed against the behavioral suite; the open issues 20261029T192501Z-redshift-resource-policy-idc-application-and-event-subscription.md and 20261029T200555Z-redshift-request-validation-answers-a-generic-validationexception-or.md describe neighbouring defects but do not carry any of the failing checks listed below.

Cause 1 of 5 — PutResourcePolicy/GetResourcePolicy accept resource types AWS does not support. AWS: a resource policy can only be attached to a namespace ARN; a provisioned-cluster ARN or a cluster-snapshot ARN is refused with HTTP 400, Error.Code 'InvalidParameterValue' and the message "Resource type <type> isn't supported for the resource policy. Choose another resource type." — fixed text "Resource type " + the resource type parsed from the supplied ResourceArn ('cluster', 'snapshot') + " isn't supported for the resource policy. Choose another resource type." (Smithy: PutResourcePolicy errors are ConflictPolicyUpdateFault, InvalidPolicyFault, ResourceNotFoundFault, UnsupportedOperationFault; the InvalidParameterValue classification and the wording are recorded behavior). The same refusal holds for GetResourcePolicy on those ARNs. Emulator: HTTP 200, the policy is stored against the cluster/snapshot ARN and echoed back in ResourcePolicy.{ResourceArn,Policy}. Why: a client is told that a cluster or a snapshot is share-able by resource policy; it builds a cross-account sharing flow that silently grants nothing, and never learns it must use the namespace ARN. Fix: ResourceArn type validation in the PutResourcePolicy and GetResourcePolicy handlers, before any state write. Traces: redshift.e2e-resource-policy-access-enforcement-flow, redshift.e2e-resource-policy-cross-account-snapshot-share-flow, redshift.resource-policy-put-get-delete-round-trip.

Cause 2 of 5 — the InvalidPolicyFault message for an unparseable policy document is emulator-authored. AWS: a Policy body that is not valid JSON is refused 400 InvalidPolicyFault with the exact message "The resource policy can't be parsed." (Smithy: InvalidPolicyFault, @error client, httpError 400, awsQueryError InvalidPolicyFault, doc "The resource policy isn't valid."); the message has no variable part. Emulator: the code is right, the message is "The resource policy must be a JSON policy document." Why: clients and operators that match on the refusal text (and the AWS-documented wording in runbooks) do not recognise the error. Fix: the PutResourcePolicy validation's InvalidPolicyFault message text. Traces: redshift.put-resource-policy-invalid-json-rejected, redshift.put-resource-policy-malformed-policy-rejected. Related: 20261029T200555Z-redshift-request-validation-answers-a-generic-validationexception-or.md names the same wording for resource-policy-malformed-json-rejected but does not carry these two checks.

Cause 3 of 5 — a stored resource policy is not canonicalized on read-back. AWS: the service canonicalizes the policy document it returns — a single-element Principal/Action/Resource array is collapsed to a scalar string (and multi-element lists are kept as arrays), so GetResourcePolicy returns Principal {"AWS": "<arn>"} and Resource "<arn>" for a policy submitted with one-element arrays; Condition values, including non-ASCII keys and values, round-trip byte-for-byte (recorded behavior only). Emulator: the document is stored and returned verbatim — Principal {"AWS": ["<arn>"]} and Resource ["<arn>"] stay arrays. Why: a client that diffs the policy it submitted against the policy AWS reports, or that reads Principal.AWS as a string, mis-parses or loops re-putting the policy. Fix: the resource-policy serializer/state must canonicalize single-element Principal/Action/Resource arrays to scalars on read. Traces: redshift.resource-policy-unicode-round-trip.

Cause 4 of 5 — RegisterNamespace against a cluster that is not yet available is refused with the wrong error class and message. AWS: HTTP 400, Error.Code 'InvalidParameterValue', message "This cluster version doesn't support Register Namespace operation. Please upgrade to the latest cluster version." — entirely fixed text, no values from the request (Smithy: RegisterNamespace models ClusterNotFoundFault, InvalidClusterStateFault and InvalidNamespaceFault; the InvalidParameterValue classification and wording are recorded behavior). Emulator: HTTP 400 'InvalidClusterState' with "Cluster <ClusterIdentifier> is not in available state." Why: a client that distinguishes a retryable state precondition (InvalidClusterState) from a permanent capability refusal (InvalidParameterValue) retries forever against a cluster that will never accept the call for this reason. Fix: the RegisterNamespace handler's precondition check and its refusal classification/message. Traces: redshift.namespace-invalid-state-and-namespace-errors, redshift.namespace-register-wrong-state-blocked, redshift.register-namespace-invalid-state-rejected.

Cause 5 of 5 — DeregisterNamespace refuses a namespace that was never registered. AWS: DeregisterNamespace on an available cluster is accepted whatever the prior registration state — HTTP 200 with Status 'Deregistering' — and repeating it is identically accepted; there is no registration precondition (Smithy: DeregisterNamespace output member Status of NamespaceRegistrationStatus; InvalidNamespaceFault exists for a namespace that does not exist, documented "The namespace isn't valid because the namespace doesn't exist", not for an unregistered consumer). Emulator: HTTP 400 InvalidNamespaceFault "The namespace of cluster <ClusterIdentifier> is not registered to consumer account <account-id>." Why: idempotent teardown and register/deregister toggling break — a client cleaning up fails on a namespace that is already in the desired state, and the error names a precondition AWS does not have. Fix: the DeregisterNamespace handler must drop the registration precondition and answer Status 'Deregistering' for an existing, available cluster. Traces: redshift.deregister-namespace-unregistered-accepted-nonexistent-cluster-rejected, redshift.namespace-deregister-invalid-namespace-blocked, redshift.namespace-register-deregister-lifecycle.
