# CreateDataSource never runs the connection test: an ATHENA data source against a nonexistent workgroup reports CREATION_SUCCESSFUL with no ErrorInfo, and CreateDataSet accepts a reference to a CREATION_FAILED data source

> _Note: this issue was identified against the code base at commit `04a5c1cce1738afed3911d32859c10309860f34e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDataSource

## Description
Two causes, both in the QuickSight data-source/data-set creation path. Both are grounded in the single failing check quicksight.dataset-spice-ingestion-fails-deterministically-on-invalid-source; the check fails on Cause 1 and therefore never reaches Cause 2, which is the same check's final assertion.

Cause 1 of 2: CreateDataSource reports success unconditionally and never records a connection-test failure.
AWS: Smithy model (services/service-com-amazonaws-quicksight-quicksight-20180401/smithy-model/com-amazonaws-quicksight-quicksight-20180401.json) models CreateDataSource.CreationStatus as ResourceStatus (CREATION_FAILED | CREATION_IN_PROGRESS | CREATION_SUCCESSFUL | DELETED | UPDATE_FAILED | UPDATE_IN_PROGRESS | UPDATE_SUCCESSFUL) and DescribeDataSource returns a DataSource carrying ErrorInfo of shape DataSourceErrorInfo {Type: DataSourceErrorInfoType, Message: String}, documented as "Error information for the data source creation or update". DataSourceErrorInfoType values are ACCESS_DENIED, COPY_SOURCE_NOT_FOUND, TIMEOUT, ENGINE_VERSION_NOT_SUPPORTED, UNKNOWN_HOST, GENERIC_SQL_FAILURE, CONFLICT, UNKNOWN. Real AWS asynchronously tests the connection described by DataSourceParameters; when that test fails because the underlying source does not exist — here AthenaParameters.WorkGroup names a workgroup that does not exist in the account/region — the data source settles in the TERMINAL status CREATION_FAILED, and DescribeDataSource returns ErrorInfo.Type = GENERIC_SQL_FAILURE with a Message whose subject is the missing workgroup (the message names the workgroup from the request and embeds the per-call Athena request id, so only the fixed subject "workgroup" plus the request-supplied workgroup name is a requirement; the request id is a per-run value and is not). CREATION_SUCCESSFUL is reserved for a connection test that actually passed. A data source against a workgroup that DOES exist ("primary") settles CREATION_SUCCESSFUL with no ErrorInfo — that is the check's positive control, and it is what distinguishes this from a credentials/role problem.
Emulator: CreateDataSource validates only that Type is a member of DataSourceType and that DataSourceId is non-empty, then inserts the record with status = RESOURCE_STATUS_CREATION_SUCCESSFUL and error_info = None and answers CreationStatus = CREATION_SUCCESSFUL for ANY DataSourceParameters whatsoever. DataSourceParameters is stored verbatim and never inspected, so no workgroup, host, database or role is ever checked and no data source can ever reach CREATION_FAILED. The replay shows DescribeDataSource returning Status 'CREATION_SUCCESSFUL' and no ErrorInfo member at all for an ATHENA data source whose AthenaParameters.WorkGroup names a workgroup that does not exist.
Why: a client that provisions a data source and polls DescribeDataSource to a terminal status — the documented way to learn whether the connection works — is told every data source is healthy. Misconfigured sources (wrong workgroup, wrong host, wrong database) are indistinguishable from working ones, so error-handling and remediation paths are never exercised against the emulator and ship untested; downstream dataset/ingestion creation is then attempted against a source that cannot serve queries.
Fix: CreateDataSource's handler/validation plus the data-source status model in the service state — the creation path must decide the terminal status from DataSourceParameters rather than hard-coding success, and must be able to persist a CREATION_FAILED record with a populated DataSourceErrorInfo (Type GENERIC_SQL_FAILURE, Message naming the offending workgroup) that DescribeDataSource then serializes as ErrorInfo. The emulator has no real Athena to probe, so the rule it needs is one consistent with what it does know about the referenced resource; whatever rule is chosen, CREATION_FAILED and ErrorInfo must be reachable. Hypothesis: resolving AthenaParameters.WorkGroup against the emulator's own Athena workgroups (treating "primary" as existing) reproduces both the positive control and the negative case.
Traces: quicksight.dataset-spice-ingestion-fails-deterministically-on-invalid-source (AssertionError on `assert bad["Status"] == "CREATION_FAILED"`, observed DataSource with 'Status': 'CREATION_SUCCESSFUL' and no 'ErrorInfo'). Handler: services/service-com-amazonaws-quicksight-quicksight-20180401/src/ops/create_data_source.rs lines 277-308 (status hard-coded to RESOURCE_STATUS_CREATION_SUCCESSFUL, error_info: None).

Cause 2 of 2: CreateDataSet does not refuse a PhysicalTableMap entry that references a data source in status CREATION_FAILED.
AWS: Smithy model declares InvalidParameterValueException (HTTP 400, "One or more parameters has a value that isn't valid") on CreateDataSet. Recorded behavior (the check asserts it directly against real AWS): CreateDataSet whose CustomSql.DataSourceArn points at a data source in status CREATION_FAILED is refused with error code InvalidParameterValueException and message `DataSource <arn> is in status CREATION_FAILED` — fixed text "DataSource " ... " is in status " ... with the variable parts being the data source ARN taken from the request's DataSourceArn and the data source's current status taken from emulator state. A data source that never passed its connection test can never back a dataset, in SPICE or DIRECT_QUERY.
Emulator: CreateDataSet validates only ImportMode membership, non-empty DataSetId, id collision and the store's size ceilings; it never resolves PhysicalTableMap's DataSourceArn, so it neither checks that the data source exists nor what status it is in, and the call succeeds with HTTP 200. NOTE: this cause was NOT reached in this replay — the check fails earlier on Cause 1, because the emulator cannot produce a CREATION_FAILED data source at all. It is filed as the second half of the same contract and must be closed together with Cause 1, otherwise the check still fails on this assertion once Cause 1 is fixed.
Why: a client gets a dataset built on a data source that cannot serve queries, and the failure surfaces later (or never) instead of at the call that introduced it; code that handles InvalidParameterValueException here is never exercised.
Fix: CreateDataSet's validation — resolve each PhysicalTableMap entry's DataSourceArn in the service state and refuse with InvalidParameterValueException (HTTP 400) and the message above when the referenced data source's status is not a successful terminal one.
Traces: quicksight.dataset-spice-ingestion-fails-deterministically-on-invalid-source (final assertions `error.get("Code") == "InvalidParameterValueException"` and `error.get("Message") == f"DataSource {bad['Arn']} is in status CREATION_FAILED"`, currently unreached). Handler: services/service-com-amazonaws-quicksight-quicksight-20180401/src/ops/create_data_set.rs lines 205-300 (no DataSourceArn resolution).

## Evidence
Cause 1 — expected (real AWS): after creating an ATHENA data source with DataSourceParameters.AthenaParameters.WorkGroup set to a workgroup that does not exist, DescribeDataSource settles at DataSource.Status == "CREATION_FAILED" with DataSource.ErrorInfo == {"Type": "GENERIC_SQL_FAILURE", "Message": <text naming the missing workgroup>}; the same call against the existing "primary" workgroup settles CREATION_SUCCESSFUL with no ErrorInfo.
Cause 1 — actual (emulator): CreateDataSource returns 200 with CreationStatus "CREATION_SUCCESSFUL", and DescribeDataSource returns
  {'Arn': 'arn:aws:quicksight:<region>:<account>:datasource/<DataSourceId>', 'DataSourceId': '<DataSourceId>', 'Name': '<Name>', 'Type': 'ATHENA', 'Status': 'CREATION_SUCCESSFUL', 'CreatedTime': ..., 'LastUpdatedTime': ..., 'DataSourceParameters': {'AthenaParameters': {'WorkGroup': '<nonexistent workgroup>', 'RoleArn': '<role arn>'}}}
with NO 'ErrorInfo' member. Replay assertion: `AssertionError: assert bad["Status"] == "CREATION_FAILED"`. Source-grounded: create_data_source.rs sets `status: crate::state::RESOURCE_STATUS_CREATION_SUCCESSFUL.to_string()` and `error_info: None` on every insert, with the comment "Creation succeeded, so the data source carries no error."

Cause 2 — expected (real AWS): CreateDataSet(ImportMode="SPICE", PhysicalTableMap={"tbl1": {"CustomSql": {"DataSourceArn": <arn of a CREATION_FAILED data source\>, ...}}}) is refused with HTTP 400, Error.Code "InvalidParameterValueException", Error.Message "DataSource <that arn> is in status CREATION_FAILED".
Cause 2 — actual (emulator): the call is accepted with HTTP 200 and a dataset is created; the emulator never resolves DataSourceArn (create_data_set.rs performs no lookup of store.data_sources). Not directly observed in this replay because the emulator cannot produce a CREATION_FAILED data source (Cause 1).

1. Boot the emulator and point a boto3 quicksight client at it; ensure the account subscription exists (CreateAccountSubscription / DescribeAccountSubscription) and an execution role ARN is available.
2. This passes today.

Expect a ClientError with Code "InvalidParameterValueException" and Message "DataSource <arn> is in status CREATION_FAILED". Observed: HTTP 200, dataset created.
