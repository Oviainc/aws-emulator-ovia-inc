# bedrock-agent__lambda__opensearchserverless: 5 net-new causes — Retrieve answers NotImplemented, the Lambda runtime's botocore has no 'bedrock-agent-runtime' client, CreateKnowledgeBase accepts a storage config with no AOSS data-access grant, and a COMPLETE ingestion job writes no documents into the collection

> _Note: this issue was identified against the code base at commit `f392f82803b1854878505550560cb55ee4e9c61d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve, CreateKnowledgeBase, StartIngestionJob

## Description
Five distinct root causes in the Bedrock knowledge base / OpenSearch Serverless / Lambda paths of this service. Each cause must be closed before submitting.

Cause 1 of 5: bedrock-agent-runtime Retrieve is a scaffold stub, so every CloudFormation-deployed knowledge-base retrieval check is refused with an unmodeled error. Failing check ids: bedrock-agent__lambda__opensearchserverless.deploy-opensearchserverless-collection-data-access-policy-positive, bedrock-agent__lambda__opensearchserverless.deploy-stack-missing-opensearchserverless-data-access-negative.
AWS: Smithy (bedrock-agent-runtime): Retrieve is POST /knowledgebases/{knowledgeBaseId}/retrieve -> 200 with required `retrievalResults` (each result carrying content.text), @readonly, @paginated on nextToken/retrievalResults; the only other modeled outcomes are AccessDeniedException 403, BadGatewayException 502, ConflictException 409, DependencyFailedException 424, InternalServerException 500, ResourceNotFoundException 404, ServiceQuotaExceededException 400, ThrottlingException 429, ValidationException 400. There is no NotImplemented code and no 501 in that set.
Emulator: `An error occurred (NotImplemented) when calling the Retrieve operation: operation Retrieve is scaffolded but not implemented in this emulator`. The code `NotImplemented` and that sentence are emulator-authored fixed text with no request- or state-derived parts.
Why: a client cannot read anything back out of a knowledge base, and the error it does get is outside the modeled error set, so SDK exception handling and retry/fallback branches never match. Both the positive data-access case and the negative (grant-missing) case are undecidable.
Fix: the Retrieve handler in the bedrock-agent-runtime crate (ops/retrieve.rs) and the knowledge-base retrieval state it reads. Related open issues describe this stub elsewhere but none carries these checks' replay keys: 20261029T171944Z-bedrock-agent-runtime-retrieve-stub.md, 20261025T173258Z-bedrock-agent-runtime-retrieve-is-a-scaffold-stub.md.
Traces: the two deploy-* checks above (verdict error, ClientError NotImplemented on Retrieve).

Cause 2 of 5: the Lambda Python runtime's bundled botocore has no 'bedrock-agent-runtime' service model, so a handler can never call Retrieve or RetrieveAndGenerate at all. Failing check ids: bedrock-agent__lambda__opensearchserverless.lambda-bedrock-agent-retrieve-knowledge-base-positive, bedrock-agent__lambda__opensearchserverless.lambda-bedrock-agent-retrieve-and-generate-positive.
AWS: recorded behavior only. On AWS, the managed python3.12 runtime ships an AWS SDK whose client factory resolves `boto3.client('bedrock-agent-runtime', region_name=...)` and the handler's call is then answered by the service (200 with retrievalResults / output.text+citations, or one of the modeled errors). Client construction itself never fails.
Emulator: the handler's own exception path reports `{'ok': False, 'code': 'UnknownServiceError'}` — botocore raised UnknownServiceError when constructing the client, i.e. the runtime image has no service data for 'bedrock-agent-runtime'. The failure is at client construction, before any request leaves the sandbox: no HTTP status, no AWS error code.
Why: no in-function Bedrock retrieval code can run on this emulator, so IAM-boundary behavior, retrieval results and generated answers are all unobservable from inside Lambda; a client sees a botocore-level exception name instead of an AWS error it can branch on.
Fix: the Lambda runtime image / bundled SDK used by the lambda crate's python runtime — its botocore service-model set must include bedrock-agent-runtime (and generally the services the emulator serves). Sibling open issues report the same missing-model defect for other clients and do not cover this one: 20261108T072100Z-bedrock-agent-lambda-opensearchserverles-...-the-lambda-python-runtime-60d1ec.md ('opensearchserverless'), 20261105T090020Z-bedrock-agent-runtime-lambda-s3vectors-the-python-lambda.md.
Traces: the two lambda-bedrock-agent-retrieve* checks above (verdict mismatch, body {'ok': False, 'code': 'UnknownServiceError'}).

Cause 3 of 5: CreateKnowledgeBase accepts an OPENSEARCH_SERVERLESS storage configuration naming an index the knowledge-base role has no AOSS data-access grant for, instead of refusing it. Failing check id: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-data-access-policy-missing-negative.
AWS: Smithy (bedrock-agent): CreateKnowledgeBase is PUT /knowledgebases/ -> 202 with required `knowledgeBase`; modeled errors AccessDeniedException 403, ConflictException 409, InternalServerException 500, ServiceQuotaExceededException 402, ThrottlingException 429, ValidationException 400. Per the recording, when the role named in roleArn has no OpenSearch Serverless data access policy grant for the collection/index in storageConfiguration.opensearchServerlessConfiguration, AWS validates the storage configuration synchronously and refuses with ValidationException (HTTP 400) whose message is 'The knowledge base storage configuration provided is invalid... Dependency error document status code: 403, error message: Bad Authorization'. That whole sentence is fixed text for this error class (the embedded dependency status 403 and 'Bad Authorization' come from the AOSS authorization failure, not from the request); the request-derived parts of this class are only which configuration was rejected. Adding the missing grant and re-issuing the identical request then succeeds.
Emulator: the call is accepted — it answers success with a knowledgeBase body (status CREATING, the requested roleArn, knowledgeBaseConfiguration and storageConfiguration echoed back). No AOSS data-access evaluation happens at all, so the negative case cannot be distinguished from the positive one.
Why: the emulator silently permits a knowledge base whose role cannot read its own index. A client that relies on CreateKnowledgeBase to pre-validate its storage wiring gets a KB that is broken only later (or never detectably), and infrastructure tests asserting the documented refusal pass vacuously.
Fix: CreateKnowledgeBase's validation in the bedrock-agent crate — before accepting the request it must resolve storageConfiguration.opensearchServerlessConfiguration.collectionArn/vectorIndexName against the opensearchserverless data-access policies for the principal in roleArn and, when no grant covers the index, return ValidationException 400 with the storage-configuration message above.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-data-access-policy-missing-negative (verdict mismatch, 'CreateKnowledgeBase accepted an index its role has no data access grant for: {...status CREATING...}').

Cause 4 of 5: an ingestion job reports COMPLETE but no document is ever written into the target OpenSearch Serverless index, so the configured field mapping is unobservable. Failing check id: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-field-mapping-positive.
AWS: Smithy (bedrock-agent): StartIngestionJob is PUT /knowledgebases/{knowledgeBaseId}/datasources/{dataSourceId}/ingestionjobs/ -> 202 with required `ingestionJob`; GetIngestionJob reports status COMPLETE and statistics (numberOfNewDocumentsIndexed, numberOfDocumentsFailed). Per the recording, COMPLETE means the source S3 object has actually been embedded and written into the collection: a match_all search on the index returns at least one hit whose _source carries the three fields named in the KB's fieldMapping — the vectorField holding a numeric array of the embedding model's dimension (1536 for amazon.titan-embed-text-v1), the textField holding the source document's content, and the metadataField referencing the source S3 bucket/key. The field names honored are the CONFIGURED ones, not hardcoded 'vector'/'text'/'metadata'.
Emulator: the job settles COMPLETE, but the collection stays empty: the data-plane search answers {'took': 0, 'timed_out': False, '_shards': {'total': 1, 'successful': 1, 'failed': 0}, 'hits': {'total': {'value': 0, 'relation': 'eq'}, 'hits': []}} for the whole 120s window. Status is reported without the work behind it.
Why: a COMPLETE ingestion job is the client's signal that its corpus is queryable; here it is false. Retrieval returns nothing, the configured field mapping can never be validated, and a client cannot tell an empty corpus from a broken ingestion because no failure is reported anywhere.
Fix: the ingestion pipeline behind StartIngestionJob in the bedrock-agent crate — it must read the S3 data source, produce embeddings of the configured dimension and write documents into the collection/index named in the KB's storageConfiguration under the configured vector/text/metadata field names; a job that cannot write must report numberOfDocumentsFailed and a FAILED status rather than COMPLETE.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-opensearchserverless-field-mapping-positive (verdict mismatch, 'condition never became true within 120s; last observed: ... hits.total.value 0').

Cause 5 of 5: the end-to-end 'ingestion writes to the collection' path produces no verdict at all — it exhausts the harness budget with no answer. Failing check id: bedrock-agent__lambda__opensearchserverless.bedrock-kb-ingestion-job-writes-to-collection-positive.
AWS: recorded behavior only for the stalling legs. Every step the check performs is a bounded call on AWS: opensearchserverless CreateCollection + BatchGetCollection reach ACTIVE and publish collectionEndpoint, the SigV4 'aoss' OpenSearch REST index create answers 200/201, bedrock-agent CreateKnowledgeBase answers 202, StartIngestionJob answers 202 and GetIngestionJob eventually reports COMPLETE with numberOfNewDocumentsIndexed=1 / numberOfDocumentsFailed=0, and a data-plane search then returns the indexed document. AWS answers each of these promptly or refuses with the operation's modeled error; it never leaves a request open.
Emulator: the replay verdict's entire detail is `Check timed out after 180.0s` — no status, no error code and no body is produced for any leg, so the emulator never reaches a decision point. Hypothesis: the stall is one of the AOSS data-plane front-door defects sibling checks of this service report (the published collectionEndpoint answering the OpenSearch REST verbs with 400 SerializationException 'missing required header x-amz-target'), compounded by cause 4; the 180.0s figure is this harness's budget, not a requirement.
Why: a client gets no outcome at all — not success, not a modeled refusal — so it and its CI hang until their own timeouts and cannot discover which leg is unsupported. A prompt modeled error (DependencyFailedException 424, AccessDeniedException 403, ValidationException 400) would at least be branchable.
Fix: whichever leg does not answer must answer — the opensearchserverless collection-endpoint data-plane router (it must dispatch SigV4 'aoss' OpenSearch REST verbs PUT /<index>, POST /<index>/_search, POST /<index>/_doc rather than the AWS-JSON RPC front door) and the bedrock-agent ingestion pipeline; any unimplemented leg must return its modeled error promptly instead of leaving the request open. A similar unbounded stall is filed for a different check in 20261105T040349Z-bedrock-agent-lambda-opensearchserverles-...-the-retrieveandgenerate-end-to.md, which does not carry this check's replay key.
Traces: bedrock-agent__lambda__opensearchserverless.bedrock-kb-ingestion-job-writes-to-collection-positive (verdict mismatch, detail 'Check timed out after 180.0s').
