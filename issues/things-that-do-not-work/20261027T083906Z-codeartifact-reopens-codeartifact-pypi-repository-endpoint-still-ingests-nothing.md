# REOPENS: CodeArtifact pypi repository endpoint still ingests nothing through an external connection, so package-origin upstream=BLOCK remains unverifiable (1 cause)

> _Note: this issue was identified against the code base at commit `9cf2ebd925d1a1f6505c9155fdd17f25927ece5d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
REOPENS 20261026T235849Z-codeartifact-listpackageversions-accepts-status-deleted-as-an-input.md: its fix left the call refused. That issue's Cause 2 named exactly this check and exactly this cause (the pypi Simple Repository API data plane plus external-connection pull-through ingestion) and is now marked fixed, but the check still fails with the identical verdict and the identical failure point (Check timed out after 60.0s, inside the ingestion poll's time.sleep(10)). This is not a new defect; it is the same cause unclosed. Cause 1 of 1.

Cause 1 of 1: a repository with public:pypi as an external connection never ingests any version, so upstream ingestion — and the package origin restriction that is meant to block it — is unobservable.

AWS: AssociateExternalConnection (Smithy: POST /v1/repository/external-connection, required domain + repository + externalConnection, errors AccessDeniedException 403 / ConflictException 409 / ResourceNotFoundException 404 / ServiceQuotaExceededException 402 / ThrottlingException 429 / ValidationException 400) attaches a public upstream to a repository. PutPackageOriginConfiguration (Smithy: POST /v1/package, required domain + repository + format:PackageFormat + package + restrictions:PackageOriginRestrictions) sets that package's restrictions; the model documents `upstream` as "The package origin configuration that determines if new versions of the package can be added to the repository from an external connection or upstream source." Data-plane behavior is recorded behavior only (the Smithy model describes only the control plane): the endpoint returned by GetRepositoryEndpoint(format='pypi') speaks the PyPI Simple Repository API, so GET <endpoint>/simple/<project>/ with Accept: application/vnd.pypi.simple.v1+json and the CodeArtifact token as HTTP Basic (user `aws`, password the authorization token) answers a JSON index whose files[].url entries are downloadable, and downloading one causes the service to INGEST that version into the repository, after which ListPackageVersions (Smithy: POST /v1/package/versions, output versions + originType member PackageVersionOriginType) reports it with originType EXTERNAL. For a package carrying restrictions {publish: BLOCK, upstream: BLOCK} the same fetch must ingest nothing: the package keeps zero versions and GetPackageVersionAsset (Smithy: GET /v1/package/version/asset, errors include ResourceNotFoundException httpError 404) is refused ResourceNotFoundException / HTTP 404 with the package-version-not-found message built from the addressed coordinate.

Emulator: nothing is ever ingested, and the pypi endpoint serves no data plane. Every control-plane step of the check answers (CreateDomain, CreateRepository, AssociateExternalConnection with public:pypi, PutPackageOriginConfiguration with {publish: BLOCK, upstream: BLOCK}, GetRepositoryEndpoint(format='pypi'), GetAuthorizationToken all return 200), but the index/file fetches against the handed-out endpoint do not succeed — consistent with the already-open 20261025T024237Z-codeartifact-repository-endpoints-serve-nothing-npm-registry-404.md, whose Cause 1 reports the same endpoint host answering HTTP 404 {"__type":"UnknownService",...} for the npm registry protocol; that issue is about npm host/protocol routing and does not carry this check or the pypi + ingestion semantics. The check's ingestion trigger is therefore a no-op, its bounded poll of ListPackageVersions(format='pypi', package='toml') for the UNRESTRICTED control package never sees a version, and the harness kills the check at its 60s ceiling. The timeout is the permanent absence of ingestion, not a slow response: the blocked-package legs ahead of it pass only vacuously, because a store that ingests nothing at all satisfies "the blocked package has no versions" for the wrong reason.

Why: external connections are the main reason to run CodeArtifact, and with no ingestion path every upstream behavior is a silent no-op that looks correct — a blocked package has no versions, an ALLOWED package also has no versions, and a client cannot tell the difference. Any client or test asserting that origin restrictions keep a package out of a repository is validated green against an emulator that would equally "block" a package it was told to allow, so the restriction is never actually enforced. The final leg, which grades the ResourceNotFoundException (404) coordinate-derived refusal of GetPackageVersionAsset for the blocked package, is never reached at all.

Fix: in the CodeArtifact service, (a) the pypi package-format data-plane handlers on the repository endpoint (Simple Repository API index + file download, with the bearer/Basic token auth the npm endpoint uses), backed by the same package/asset state the control-plane PublishPackageVersion and GetPackageVersionAsset handlers read; and (b) the upstream/external-connection resolution in that data plane, which on a fetch miss must fetch from the associated external connection, persist the version as an EXTERNAL-origin version visible to ListPackageVersions, and consult the package's origin configuration FIRST so an upstream: BLOCK package is never ingested while an unrestricted sibling is. PutPackageOriginConfiguration must keep pre-creating the package record for a package with no versions yet, so the restriction exists before the first fetch. Since the prior fix was recorded as landed, the regression surface to re-examine is whichever of (a)/(b) was left out: a served index that still never persists an ingested version fails this check exactly as an unserved endpoint does.
