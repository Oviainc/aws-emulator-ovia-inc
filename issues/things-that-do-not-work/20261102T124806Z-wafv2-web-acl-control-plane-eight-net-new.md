# wafv2 web-ACL control plane: eight net-new causes — union/required-field preconditions unenforced, scope and identifier refusals wrong, and WebACL state is not region-partitioned

> _Note: this issue was identified against the code base at commit `afb41014a6bc1e75e8336e677aedbec1633a6643`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateWebACL

## Description
EIGHT distinct net-new root causes in the wafv2 web-ACL control plane (CreateWebACL / UpdateWebACL / GetWebACL / ListWebACLs and the WebACL state store). This is ONE issue with EIGHT causes; every cause below must be closed before the fix is submitted. None of these eight is marked ALREADY FILED or OWNED in the behavioral replay report. Related but NON-covering open issues, named for the fixer: `20261030T002309Z-wafv2-write-path-validation-is-over-permissive-seven.md` (its cause 3 is the CreateWebACL duplicate-priority leg; cause 4 below is the UpdateWebACL leg, which carries a distinct replay key) and `20261102T094456Z-wafv2-scope-and-identifier-validation-refusals-carry-the.md` (a wire issue covering Get/UpdateWebACL with Scope=CLOUDFRONT misclassified, and ListWebACLs with Scope omitted or Scope=GLOBAL; it does NOT cover ListWebACLs with Scope=CLOUDFRONT answering 200, nor GetWebACL by a foreign-account ARN, nor GetWebACL with every identifier omitted).

Cause 1 of 8: CreateWebACL accepts a RateBasedStatement whose AggregateKeyType requires a companion member that is absent.
AWS: Smithy: RateBasedStatement.AggregateKeyType is @required (enum RateBasedStatementAggregateKeyType) and its documentation states that with FORWARDED_IP "you must specify the header to use in the ForwardedIPConfig property" and with CUSTOM_KEYS "you must specify the aggregate keys in the CustomKeys property"; CreateWebACL models WAFInvalidParameterException (client, httpError 400) whose Field member targets ParameterExceptionField, which contains both FORWARDED_IP_CONFIG and CUSTOM_KEYS. Each such request is refused with HTTP 400, error code WAFInvalidParameterException, and the message AWS words as: for the missing ForwardedIPConfig, "Error reason: A required field is missing from the parameter., field: FORWARDED_IP_CONFIG, parameter: RateBasedStatement"; for the missing CustomKeys, "Error reason: You are missing at-least one of condition between some parameters or all parameters of object., field: CUSTOM_KEYS, parameter: RateBasedStatement". In both messages the fixed text is "Error reason: ", the reason sentence, ", field: ", ", parameter: "; the variable parts are the field token naming the absent member and the parameter token naming the statement shape. No web ACL may be left behind (ListWebACLs must not show the name afterwards).
Emulator: HTTP 200 with a normal CreateWebACL Summary (Name/Id/Description/LockToken/ARN) for AggregateKeyType=FORWARDED_IP with no ForwardedIPConfig; the web ACL is created.
Why: a rate-based rule aggregating on a forwarded IP with no header configured, or on CUSTOM_KEYS with no keys, is not an evaluable rule. The client believes it shipped a rate limit that AWS will refuse at deploy time, and until then the emulator evaluates a rule whose aggregation key is undefined.
Fix: the RateBasedStatement precondition in the shared rule-statement validation that the CreateWebACL/UpdateWebACL handlers run before state is written, plus the WAFInvalidParameterException serializer so Field/Parameter/Reason are emitted.
Traces: wafv2.dsw-aggregate-key-type-without-its-config-rejected.

Cause 2 of 8: CreateWebACL accepts a DefaultAction naming zero or two members.
AWS: Smithy: CreateWebACL.DefaultAction is @required and targets DefaultAction, a structure with exactly the members Block and Allow, documented as "the action that you want WAF to perform when a web request doesn't match any of the rules" and "The default action must be a terminating action" — i.e. a one-of. ParameterExceptionField contains DEFAULT_ACTION. Both an empty DefaultAction ({}) and one naming both Allow and Block are refused identically with HTTP 400, code WAFInvalidParameterException, message "Error reason: You have used none or multiple values for a field that requires exactly one value., field: DEFAULT_ACTION, parameter: DefaultAction" (fixed text throughout; no per-request variable part). Nothing is created.
Emulator: HTTP 200 with a Summary for DefaultAction={} (and the same for Allow+Block); the web ACL is created with no determinate default action.
Why: the default action decides every request that matches no rule. A web ACL the emulator accepts with no (or an ambiguous) default action is unrepresentable on AWS and its fail-open/fail-closed behavior is undefined — a security-relevant divergence with no configure-time signal.
Fix: the exactly-one-member check on DefaultAction in CreateWebACL's (and UpdateWebACL's shared) input validation, before the web ACL is written to state.
Traces: wafv2.dsw-default-action-without-exactly-one-member-rejected.

Cause 3 of 8: CreateWebACL accepts a Rule that sets neither Action nor OverrideAction, or sets both.
AWS: Smithy: Rule.Action (RuleAction) and Rule.OverrideAction (OverrideAction) are a union by documentation — "You must specify either this Action setting or the rule OverrideAction setting, but not both"; CreateWebACL models WAFInvalidParameterException (client, 400) and ParameterExceptionField contains RULE. Both the neither-set and the both-set request are refused with HTTP 400, code WAFInvalidParameterException, message "Error reason: You have used none or multiple values for a field that requires exactly one value., field: RULE, parameter: Rule" (all fixed text). No web ACL is created.
Emulator: HTTP 200 with a Summary for a rule whose Action was removed, and the web ACL is created.
Why: without exactly one of Action/OverrideAction, what WAF does on a match is undefined; a rule-group-less rule with only an OverrideAction (or no action at all) silently evaluates to nothing in the emulator while AWS refuses the configuration outright.
Fix: the Action/OverrideAction union check per rule in the shared Rules validation used by the CreateWebACL and UpdateWebACL handlers.
Traces: wafv2.dsw-rule-without-exactly-one-action-rejected.

Cause 4 of 8: UpdateWebACL accepts two rules sharing one Priority, commits them and rotates the LockToken.
AWS: Smithy: Rule.Priority is a @required integer (@range min 0) documented as "The priorities don't need to be consecutive, but they must all be different"; UpdateWebACL models WAFInvalidParameterException (client, 400). An update introducing a duplicate priority is refused with HTTP 400, code WAFInvalidParameterException, message "Error reason: You have a duplicate priority. Priorities must be unique., field: RULE, parameter: <priority>" — fixed text through ", field: RULE, parameter: ", the variable part being the duplicated Priority value taken from the request. Because the write is refused, the stored Rules AND the LockToken must be unchanged, and a later update with distinct priorities must succeed and rotate the token.
Emulator: HTTP 200 with a fresh NextLockToken; the clashing rule set is committed and the LockToken rotates.
Why: Priority is the only thing ordering rule evaluation, so an accepted duplicate makes evaluation order non-deterministic; worse, the rotated LockToken makes a client believe its refused update landed, and its optimistic-concurrency bookkeeping desynchronizes from AWS.
Fix: the duplicate-Priority check must run in UpdateWebACL's validation (shared with CreateWebACL) before the handler mutates state or mints a new LockToken. The CreateWebACL leg is cause 3 of 20261030T002309Z-wafv2-write-path-validation-is-over-permissive-seven.md; this cause is the UpdateWebACL leg including the must-not-rotate-LockToken requirement.
Traces: wafv2.dsw-update-duplicate-rule-priority-rejected.

Cause 5 of 8: ListWebACLs with Scope=CLOUDFRONT against a non-us-east-1 endpoint is answered 200.
AWS: Smithy: Scope is an enum [CLOUDFRONT, REGIONAL]; ListWebACLs.Scope is @required and the operation models WAFInvalidParameterException (client, 400) with Field/Parameter/Reason; CLOUDFRONT scope is usable only at the us-east-1 endpoint. Outside us-east-1 the call is refused with HTTP 400, code WAFInvalidParameterException, message "Error reason: The scope is not valid., field: SCOPE_VALUE, parameter: CLOUDFRONT" — fixed text "Error reason: ", ", field: ", ", parameter: "; variable parts the reason sentence, the SCOPE_VALUE field token and the offending scope value from the request. The same refusal precedes any lock-token or existence check on GetWebACL, UpdateWebACL and DeleteWebACL in that region, and REGIONAL scope in the same region still reaches the real web ACL.
Emulator: HTTP 200 with {"WebACLs": []} — the invalid scope is treated as an empty result set, so no refusal happens at all. (The check stopped at this first leg, so the Get/Update/DeleteWebACL CLOUDFRONT legs in the same region were not reached and remain unverified here; the open wire issue 20261102T094456Z reports those two as misclassified WAFNonexistentItemException rather than not refused.)
Why: an empty list is indistinguishable from "you have no CloudFront web ACLs". A client pointed at the wrong region concludes its global web ACLs were deleted and recreates them, instead of correcting the endpoint.
Fix: the scope/endpoint precondition in ListWebACLs' input validation, before any state lookup, emitting the WAFInvalidParameterException with its Field/Parameter/Reason members; share the validator with Get/Update/DeleteWebACL.
Traces: wafv2.dsw-cloudfront-scope-outside-us-east-1-rejected.

Cause 6 of 8: GetWebACL by an ARN whose account segment names another account is refused as a nonexistent item.
AWS: Smithy: GetWebACL.ARN targets ResourceArn (@length 20..2048, @pattern \\S); the operation's modeled errors are WAFInternalErrorException, WAFInvalidOperationException, WAFInvalidParameterException and WAFNonexistentItemException. Recorded behavior only for this class: an ARN whose account id WAF cannot resolve for the caller is refused with error code UnrecognizedClientException and the message "No account found for the given parameters" (entirely fixed text, no variable part) — the class is NOT in the operation's modeled error list, so this is recorded behavior, not a model requirement. The same ARN must still resolve for its real owner.
Emulator: error code WAFNonexistentItemException with message "AWS WAF couldn\u2019t perform the operation because your resource doesn\u2019t exist." — a not-found, not a credential/account refusal.
Why: a client that catches UnrecognizedClientException to re-target credentials or an account instead sees "your resource doesn't exist" and concludes the web ACL was deleted, so cross-account misconfiguration is reported as data loss. This is a different cause from cause 3 of the open wire issue 20261102T094456Z, which concerns an ARN naming the wrong resource TYPE (expected AccessDeniedException "Invalid ARN provided for GetWebACLRequest <arn>").
Fix: GetWebACL's ARN identifier validation must compare the ARN's account segment against the caller's account and raise the account-unresolvable refusal before state lookup; the error serializer must select that class.
Traces: wafv2.dsw-get-web-acl-by-arn-for-another-account-rejected.

Cause 7 of 8: GetWebACL carrying only Scope — no Name, Id or ARN — is refused with the wrong class and a message that is not AWS's.
AWS: Smithy: GetWebACL's input members Name, Scope, Id and ARN are all optional in the model; a web ACL must be addressed either by ARN or by Name+Scope+Id. Recorded behavior only for this class: the request is refused with error code AccessDeniedException and the message "Critical information is missing in your request: GetWebACLRequest(name=null, scope=REGIONAL, id=null, aRN=null)." — fixed text is "Critical information is missing in your request: " followed by the request shape name and its member=value rendering with absent members rendered as null and the trailing period; the only variable parts are the values actually supplied (here the scope token from the request). AccessDeniedException is not in GetWebACL's modeled error list, so this class is recorded behavior only.
Emulator: error code WAFInvalidParameterException with the message "Error reason: a web ACL is addressed by its ARN or by its name, scope and id, field: WEB_ACL, parameter: ARN" — a hand-written sentence in WAF's message shape but not WAF's wording, and the wrong exception class.
Why: the class is what SDK error handling branches on (AccessDeniedException is handled as a request/identity failure, WAFInvalidParameterException as a retry-with-corrected-parameter), and a message no AWS deployment emits breaks any client or test asserting on it. The open wire issue 20261102T094456Z carries the ListWebACLs missing-Scope analogue (cause 5), not this GetWebACL identifier-omission case.
Fix: GetWebACL's missing-identifier handling must emit the critical-information-missing refusal with the request-shape rendering, in the operation's input validation and the error serializer that picks the class.
Traces: wafv2.dsw-get-web-acl-omitting-every-identifier-rejected.

Cause 8 of 8: WebACL state is not partitioned by region — a REGIONAL web ACL created at one regional endpoint is visible at another region's endpoint.
AWS: Smithy/WAF semantics: a REGIONAL web ACL is a regional resource, and its ARN embeds the region (arn:aws:wafv2:<region>:<account>:regional/webacl/<name>/<id>). Another region's ListWebACLs does not list it; that region's GetWebACL for the same Name+Scope+Id is refused with code WAFNonexistentItemException and WAF's fixed not-found sentence "AWS WAF couldn\u2019t perform the operation because your resource doesn\u2019t exist." (no variable parts); and the same name is free to reuse in that other region for an unrelated web ACL, which gets its own distinct Id and an ARN naming that region.
Emulator: the other region's ListWebACLs returns the web ACL created in the home region — the entity leaked across regions, so the store is keyed without the region.
Why: every multi-region deployment relies on regional isolation: name reuse per region, per-region inventory, and per-region not-found. A shared store makes cross-region name collisions appear as DuplicateItem, makes inventory/cleanup tooling delete or report resources belonging to another region, and hides region misconfiguration entirely.
Fix: the WebACL state store (and the list/get lookups over it) must key entities by region as well as scope and account; the ARN region segment must be derived from the serving endpoint's region.
Traces: wafv2.dsw-webacl-is-region-scoped.
