## Description

=== Cause 1 of 2: a Lambda-invoke action's job result is never published, so the action never reaches a terminal status and its outputVariables are never readable ===
AWS: Smithy (com.amazonaws.codepipeline#CodePipeline_20150709) models PutJobSuccessResult with outputVariables (target OutputVariablesMap, a string->string map) and ListActionExecutions returning ActionExecutionDetail whose output carries outputVariables. AWS drives an Invoke/Lambda action by handing the function a CodePipeline.job with data.actionConfiguration.configuration (including UserParameters); when the worker calls PutJobSuccessResult(jobId, outputVariables=...), the action moves to a terminal ActionExecutionStatus ('Succeeded'), GetPipelineState reports the stage's latestExecution.pipelineExecutionId, and ListActionExecutions reports that action's output.outputVariables with the values byte-identical to what was submitted — map values are opaque strings, so a long integer literal, a 36-digit decimal literal and non-ASCII (UTF-8) text all round-trip with no numeric coercion, no precision loss and no re-encoding.
Emulator: the check never gets that far. It creates the artifact bucket, the Lambda function (waits for it Active), the pipeline role and a two-stage Source(S3)+InvokeStage(Lambda) pipeline, then StartPipelineExecution and polls GetPipelineState for InvokeStage.latestExecution and ListActionExecutions for the InvokeLambda action to reach 'Succeeded' or 'Failed' — the check stops at the suite's per-check ceiling, 'Error: Check timed out after 60.0s', with no terminal action status and therefore no output.outputVariables ever observed. Against an emulator each of those probes should resolve on the first poll. Hypothesis (neither the model nor the recording states the mechanism): the execution driver never dispatches the Invoke/Lambda action as a job, so no PutJobSuccessResult is ever made and the action is left non-terminal; it is also possible the result is accepted but never projected onto the action's output.
Why: a client that uses the documented Lambda-invoke integration to publish output variables for a downstream action (the standard way to pass values between stages) hangs forever and reads no variables; worse, any precision/encoding defect in the outputVariables round-trip is masked because the field is never populated at all.
Fix: the codepipeline crate's execution plane — the driver that materialises an Invoke/Lambda action as a dispatched job and the PutJobSuccessResult path that must store outputVariables and project them onto the action's terminal ActionExecutionDetail read by ListActionExecutions/GetPipelineState.
Traces: codepipeline.job-output-variables-precision-preserved.

=== Cause 2 of 2: a PARALLEL-mode pipeline's active-execution ceiling is never reached, so ConcurrentPipelineExecutionsLimitExceededException is unobservable and the execution history cannot be reconciled ===
AWS: Smithy models ConcurrentPipelineExecutionsLimitExceededException on StartPipelineExecution (errorKind=client, httpError 400). AWS documents a fixed, non-adjustable quota of 50 active executions per pipeline (AWS General Reference, CodePipeline endpoints and quotas, 'Active executions per pipeline'), which applies to a V2 pipeline in executionMode PARALLEL where every started execution stays active concurrently. Behaviour required: sequential StartPipelineExecution calls are accepted while fewer than 50 executions are active, each returning a distinct pipelineExecutionId and each independently visible through ListPipelineExecutions; the call that would exceed the ceiling is refused 400 ConcurrentPipelineExecutionsLimitExceededException with the fixed message 'The limit for concurrent pipeline executions has been exceeded. Please try again later.' (no variable parts), and the refused call creates no execution — ListPipelineExecutions must report no entry for it. The number of accepted executions must never exceed 50.
Emulator: the check — a PARALLEL V2 pipeline with an S3 Source stage and an Invoke/Lambda stage whose function sleeps, so executions stay active — stops at the suite's per-check ceiling, 'Error: Check timed out after 60.0s', before any refusal is observed, so neither the ceiling, the refusal nor the 'rejected start created nothing' reconciliation through ListPipelineExecutions is reachable. Hypothesis (the recording states only the quota and the refusal, not the mechanism): with the Invoke action never driven to a terminal state (Cause 1) and/or executions not counted as active per pipeline in PARALLEL mode, the emulator accepts every start and never refuses one, so the probe runs its whole search range. NOTE for the fixer: part of this check's elapsed time is its own deliberate ~1s pacing between the sequential starts, so the budget is tight by construction — reproduce it directly (steps below) and judge the ceiling behaviour, not only the timeout.
Why: a client that fills a PARALLEL pipeline and relies on the documented quota refusal to back off instead sees unbounded acceptance; with more than 50 executions admitted, the pipeline's own concurrency guarantee and anything that reads the execution history become wrong.
Fix: the active-execution accounting behind StartPipelineExecution in the codepipeline crate (per-pipeline count of non-terminal executions, honouring executionMode PARALLEL) plus the execution driver that must retire an execution so the count can fall again, and the refusal's message in the StartPipelineExecution handler.
Traces: codepipeline.concurrent-pipeline-executions-limit-exceeded.
