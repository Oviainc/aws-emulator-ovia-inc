# events__glue: glue CreateTrigger is an unimplemented 501 scaffold stub, so a Glue EVENT trigger's EventBatchingCondition (BatchSize/BatchWindow) governing the EventBridge->Glue-workflow ingress can never be created or graded

> _Note: this issue was identified against the code base at commit `b76b7166d3d256a1ac9f503358a3b66c42be670e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTrigger

## Description
One root cause. Cause count: 1.

=== Cause 1 of 1: glue CreateTrigger answers HTTP 501 NotImplemented, so an EVENT-type trigger carrying EventBatchingCondition cannot be created and the whole EventBridge -> Glue-workflow ingress (and the batch-size suppression that governs it) is unreachable ===

AWS: Smithy (services/service-com-amazonaws-glue-awsglue/smithy-model/com-amazonaws-glue-awsglue.json) models glue CreateTrigger with required input members Name (NameString, @length 1..255, pattern ^[\u0020-\uD7FF\uE000-\uFFFD\uD800\uDC00-\uDBFF\uDFFF\t]*$), Type (TriggerType enum: SCHEDULED | CONDITIONAL | ON_DEMAND | EVENT) and Actions (ActionList), plus optional WorkflowName, Schedule, Predicate, Description, StartOnCreation (default false), Tags and EventBatchingCondition; output is CreateTriggerResponse { Name } on HTTP 200. com.amazonaws.glue#EventBatchingCondition has required BatchSize (@range 1..100, documented "Number of events that must be received from Amazon EventBridge before EventBridge event trigger fires") and optional BatchWindow (@range 1..900, "Window of time in seconds after which EventBridge event trigger fires. Window starts when first event is received"). The operation's modeled error set is AlreadyExistsException, ConcurrentModificationException, EntityNotFoundException, IdempotentParameterMismatchException, InvalidInputException, OperationTimeoutException, ResourceNumberLimitExceededException (all HTTP 400) and InternalServiceException (HTTP 500); `NotImplemented` is not a member of it. For a well-formed EVENT trigger naming an existing workflow and an existing job action, the correct answer is 200 with the trigger name, GetTrigger must then report Type EVENT, State CREATED and the EventBatchingCondition as submitted, and each subsequent EventBridge delivery to the workflow target must be counted against BatchSize so that a workflow run starts only once BatchSize deliveries have arrived (or BatchWindow has expired), while a BatchSize=1 trigger on identical wiring runs on the first delivery.

Emulator: `botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the CreateTrigger operation: operation CreateTrigger is scaffolded but not implemented in this emulator` — HTTP 501, error code `NotImplemented`, and a message that is entirely fixed stub text parameterised only by the operation name; it carries no value from the request or from state, where every legitimate refusal AWS has here (EntityNotFoundException, InvalidInputException, AlreadyExistsException) is that error class's fixed text with the trigger/workflow/job name taken from the request — and for this request no refusal is legitimate at all. The handler is still the generated scaffold: services/service-com-amazonaws-glue-awsglue/src/ops/create_trigger.rs carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker (line 4). The check gets through sts:GetCallerIdentity, the IAM role creation/attachment, glue CreateJob and glue CreateWorkflow and fails on the FIRST CreateTrigger, so nothing downstream — GetTrigger's State/Type/EventBatchingCondition echo, PutTargets on the glue workflow ARN, PutEvents, GetWorkflowRuns — is exercised.

Why: a client relying on AWS's behavior cannot build the documented EventBridge-driven Glue workflow at all: the only way to make a workflow start from an event is an EVENT trigger, and it cannot be created. The error it receives (`NotImplemented`, HTTP 501) is outside the SDK's modeled error set for the operation, so no except/retry clause keyed on InvalidInputException, EntityNotFoundException or AlreadyExistsException matches it and generic retry logic retries a permanent failure. Beyond the refusal, EventBatchingCondition exists purely to SUPPRESS work: a client that sets BatchSize=3 to coalesce three events into one workflow run has no way to verify that, and an emulator that later accepts the trigger but ignores the condition (one run per delivery) or never starts a run at all is indistinguishable from a correct one today.

Fix: implement the operation in its own handler, services/service-com-amazonaws-glue-awsglue/src/ops/create_trigger.rs, over the glue crate's trigger/workflow state (validate Type against TriggerType, require a Schedule for SCHEDULED and a Predicate for CONDITIONAL, validate EventBatchingCondition's BatchSize 1..100 and BatchWindow 1..900, refuse an unknown WorkflowName or Actions job with the modeled 400 EntityNotFoundException and a duplicate Name with AlreadyExistsException, return 200 with Name, and record the trigger so GetTrigger reports Type/State/EventBatchingCondition), and delete the SCAFFOLDED marker. The behaviour the check grades afterwards belongs to the EventBridge target-delivery path for glue workflow ARNs (glue:notifyEvent) and to the glue trigger's batch accounting that turns the BatchSize-th delivery into exactly one workflow run, so this needs a re-replay after the stub lands.
