# API Gateway control plane: 8 net-new refusal/validation causes — duplicate access associations answer the wrong error class, a non-existent VPC endpoint is accepted, four refusal messages are emulator-authored, and control-plane IAM authorization is not enforced

> _Note: this issue was identified against the code base at commit `2d2373ac96719fb51b225d122133a9d558f5af51`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomainNameAccessAssociation

## Description
Eight independent control-plane defects, all grounded in failing behavioral checks. The status code is already right in causes 2, 4, 5, 6 and 7 — only the message text diverges, and an error message is a requirement. Causes 1, 3 and 8 are wrong error class / missing refusal. Ids, names and ARNs quoted below are one run's instances of each template, never part of the requirement.

Cause 1 of 8 — CreateDomainNameAccessAssociation for a domain/VPCE pair that is already associated. AWS: 400 BadRequestException with the fixed message `The domain name access association between this VPC endpoint and domain name already exists.` (entirely fixed text — no variable part). Smithy: CreateDomainNameAccessAssociation models BadRequestException @httpError 400 and ConflictException @httpError 409; ConflictException is modeled for the operation but is not what a same-pair duplicate returns. Emulator: 409 ConflictException with an emulator-authored sentence `The access association source <vpceId> is already associated with the domain name <domainNameArn>: <associationArn>`. Why: a client that distinguishes a malformed/duplicate request (400, do not retry, surface to the user) from a resource conflict (409, often retried) takes the wrong branch, and no client can match on AWS's sentence. Fix: the CreateDomainNameAccessAssociation handler's duplicate-pair check — it must raise BadRequestException with AWS's fixed sentence, not ConflictException. Traces: apigateway.concurrent-create-domain-name-access-association-race, apigateway.concurrent-domain-name-access-association-duplicate.

Cause 2 of 8 — CreateDomainNameAccessAssociation naming a well-formed but non-existent domainNameArn. AWS: 400 BadRequestException with the fixed message `Domain not found` (entirely fixed text). Emulator: 400 BadRequestException `Invalid domain name identifier specified`. Why: the code and status are right, so the divergence is invisible to a status check but breaks every client, test or operator runbook that matches the message. Fix: the CreateDomainNameAccessAssociation handler's domain-resolution error message. Traces: apigateway.concurrent-create-domain-name-access-association-duplicate-race.

Cause 3 of 8 — CreateDomainNameAccessAssociation with accessAssociationSourceType=VPCE and an accessAssociationSource that is not an existing VPC endpoint. AWS: 400 BadRequestException whose message is `<accessAssociationSource> is not a valid VPC endpoint id` — fixed text `is not a valid VPC endpoint id` with the VPC endpoint id taken verbatim from the request — and no association is created. Emulator: 201 Created, returning a full DomainNameAccessAssociation (domainNameAccessAssociationArn, domainNameArn, accessAssociationSourceType, accessAssociationSource) for an endpoint that does not exist, and the dangling association is then visible from GetDomainNameAccessAssociations. Why: the emulator is over-permissive — a client provisioning private custom domains believes a VPC endpoint is wired up when it is not, and the dangling association pollutes the account's state irrecoverably. Fix: the CreateDomainNameAccessAssociation handler's validation must resolve accessAssociationSource against the EC2 VPC-endpoint state before creating anything. Traces: apigateway.create-domain-name-access-association-without-vpce-fails.

Cause 4 of 8 — CreateUsagePlanKey for a key already subscribed to the plan. AWS: 409 ConflictException with the fixed message `API Key is already subscribed to Usage Plan` (entirely fixed text — it names neither the key nor the plan). Smithy: CreateUsagePlanKey models ConflictException @httpError 409. Emulator: the right code (409 ConflictException) with an emulator-authored, id-interpolating sentence `API Key <keyId> already in Usage Plan <usagePlanId>`. Why: a client matching AWS's sentence to de-duplicate a racing subscription never matches. Fix: the CreateUsagePlanKey handler's duplicate-subscription message. Note the resolved issue 20261029T200808Z-apigateway-api-gateway-usage-plans-and-api-keys-deletes.md fixed CreateUsagePlanKey's invalid-keyType message (its cause 7); this duplicate-subscription message is a different refusal and was not covered. Traces: apigateway.concurrent-create-usage-plan-key-same-key-dedup, apigateway.concurrent-usage-plan-key-association-race, apigateway.concurrent-usage-plan-key-duplicate-conflict.

Cause 5 of 8 — PutMethodResponse for a statusCode that already has a method response. AWS: 409 ConflictException with the fixed message `Response already exists for this resource` (entirely fixed text). Smithy: PutMethodResponse models ConflictException @httpError 409. Emulator: 409 ConflictException `Method response already exists for this method`. Why: message-only divergence on an otherwise correct refusal; a client that treats AWS's sentence as the idempotency signal for a re-applied method response does not recognise it. Fix: the PutMethodResponse handler's already-exists message. Traces: apigateway.concurrent-put-method-response-conflicting-updates.

Cause 6 of 8 — CreateVpcLink with targetArns present but empty. AWS: 400 BadRequestException with the fixed message `Need at least one target arn to create a vpc link` (entirely fixed text). Smithy: CreateVpcLink.targetArns is a required ListOfString and the operation models BadRequestException @httpError 400. Emulator: 400 BadRequestException `targetArns must name at least one target`. Why: the refusal is correct in class but unmatchable by text; CLI/console surfaces and client retries keyed on AWS's sentence diverge. Fix: the CreateVpcLink handler's targetArns validation message. Traces: apigateway.create-vpc-link-empty-target-arns-rejected, apigateway.create-vpc-link-missing-target-arns-rejected.

Cause 7 of 8 — UpdateDomainName with a patchOperation targeting the immutable `/domainName` path. AWS: 400 BadRequestException whose message is `<path> Invalid request input` — fixed suffix `Invalid request input` prefixed by the offending patch path taken verbatim from the request, i.e. `/domainName Invalid request input`. Smithy: UpdateDomainName takes ListOfPatchOperation and models BadRequestException @httpError 400. Emulator: 400 BadRequestException `Invalid patch path /domainName`. Why: UpdateDomainName does not use the generic unsupported-patch-path template; a client cannot tell an immutable-field rejection from an unknown-path rejection. Fix: the UpdateDomainName handler's patch-path validation message (its own template, distinct from the shared one). Note the resolved issue 20261029T200808Z-apigateway-api-gateway-patch-path-refusals-omit-the-op.md fixed the shared template for UpdateAccount/Stage/Deployment/DocumentationPart/DocumentationVersion/Model/RequestValidator/Authorizer/Resource/UsagePlan — UpdateDomainName was not among them and needs the different sentence above. Traces: apigateway.update-domain-name-immutable-field-rejected.

Cause 8 of 8 — the API Gateway control plane does not enforce caller IAM authorization. A session for an assumed role carrying an explicit deny on apigateway:* calls GetMethodResponse for an existing method response. AWS: 403 AccessDeniedException whose message is `User: <assumedRoleArn> is not authorized to perform: apigateway:GET on resource: arn:<partition>:apigateway:<region>::/restapis/<restApiId>/resources/<resourceId>/methods/<httpMethod>/responses/<statusCode> with an explicit deny in an identity-based policy` — fixed text around four variable parts taken from the caller's identity and the request (the assumed-role ARN, the partition/region, the resource path, the method/status). Smithy: GetMethodResponse models only NotFoundException 404, TooManyRequestsException 429 and UnauthorizedException 401, so the authorization refusal is the SigV4/IAM layer's AccessDeniedException and must be distinct from NotFoundException. Emulator: 200 with the method-response body `{"statusCode": "200"}` — the deny is ignored entirely. Why: any check of least-privilege policy on the API Gateway control plane silently passes against the emulator, so a client cannot test that its roles are scoped correctly, and the emulator cannot distinguish 'no permission' from 'does not exist'. Fix: the apigateway control-plane request pipeline's IAM authorization step (shared, not just GetMethodResponse's handler). Related open issues 20261023T210711Z-apigateway-api-gateway-control-plane-10-fidelity-causes-context.md and 20261023T125454Z-apigateway-api-gateway-control-plane-accepts-inputs-real-aws.md carry other unauthorized-vs-not-found checks but do not own this one. Traces: apigateway.resource-method-get-lacks-badrequest-error.
