Cause 1 of 2: ListComponents omits the `billable` member from every componentVersionList entry. Fixtures imagebuilder-ibp-traj-component-listing-and-paging, steps task#8 and task#9.
AWS: recorded behavior only — this checkout's on-disk Smithy model (services/service-com-amazonaws-imagebuilder-imagebuilder/smithy-model/com-amazonaws-imagebuilder-imagebuilder.json) declares ComponentVersion with arn, name, version, description, platform, supportedOsVersions, type, owner, dateCreated, status and productCodes, and does NOT declare `billable`. The recordings show AWS's ListComponents HTTP 200 body carrying componentVersionList[*].billable as a boolean, false for a customer-owned (non-Marketplace) component. This is the same undocumented member AWS also returns as component.billable on GetComponent.
Emulator: the member is absent from each entry of the 200 body (status 200 matches, and every other asserted entry member matches). Replay detail at both steps: "$.componentVersionList[0].billable: missing (expected False, got None)".
Why: a client that reads billable off a listing to decide whether a component version incurs Amazon Web Services Marketplace charges gets a missing/None value instead of the boolean AWS sends, so billing-sensitive branches take the wrong path, and a strict decoder that requires the member fails to deserialize the page at all. The value is per-component (false for self-owned components, true for billable Marketplace components), so a client cannot substitute a constant.
Fix: the ComponentVersion view ListComponents builds and its response serializer — emit `billable` on every entry, from the component record's billable flag (false for self-owned components). Because the bundled model omits the member, the ComponentVersion shape must carry it before the serializer can emit it; the same flag feeds GetComponent's Component view (Cause 4 of the issue named above), so fix it on the record, not per operation.
Traces: imagebuilder-ibp-traj-component-listing-and-paging#task#8 and #task#9; the entry is built at services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/list_components.rs lines 332-336 (`latest.version_entry(input.by_name)`), whose ComponentVersion is assembled in services/service-com-amazonaws-imagebuilder-imagebuilder/src/state.rs (ComponentRecord::version_entry).

Cause 2 of 2: the nextToken ListComponents returns for a truncated page is not an opaque token of the form AWS emits — it is the emulator's page cursor in recoverable plaintext. Fixture imagebuilder-ibp-traj-component-listing-and-paging, step task#8.
AWS: recorded behavior only — Smithy types both the input and output nextToken as PaginationToken, a string @length 1..65535 with no pattern, and documents it only as "the next token used for paginated responses ... use this token with the next request"; ListComponents is @paginated with inputToken/outputToken nextToken. The recording asserts the token's SHAPE and not its value (expected '<shaped-not-asserted>'): AWS's token is an opaque service-issued string that does not expose the request, and the fixture's shape assertion is over that form.
Emulator: returns a token of a different shape, which the shape assertion rejects — a 32-character hex digest, a literal '.', then a hex encoding of the cursor's ASCII plaintext, so the operation name, region, the owner/byName/filters fingerprint and the last ARN of the page are all readable straight out of the token (the replayed token decodes to "ListComponents", "us-west-2", "owner=4:Self;byName=false;filters=[[4:name,[32:<name>]]]" and the trailing component ARN). Replay detail: "$.nextToken: value_mismatch (expected '<shaped-not-asserted>', got '3e51f769...4c697374436f6d706f6e656e7473...')".
Why: a client that stores, logs or round-trips the token sees service-internal query state and the caller's resource names embedded in what AWS treats as an opaque handle, and any client or test that asserts the token's form against AWS's (length, alphabet, base64-ness) rejects the emulator's page token and cannot continue the pagination.
Hypothesis: the cursor is encoded for debuggability rather than to match AWS's token form; the page position itself is correct (the following page at task#9 returns the right entries), so only the encoding is at fault.
Fix: the pagination-token encoding in the imagebuilder service state — `encode_page_token`/`decode_page_token` and PageCursor in services/service-com-amazonaws-imagebuilder-imagebuilder/src/state.rs — emit an opaque token of AWS's form while keeping it decodable server-side and still refusing a token issued for a different listing (the InvalidPaginationTokenException path must keep working). ListComponents itself only calls the helper, so no per-operation change is needed.
Traces: imagebuilder-ibp-traj-component-listing-and-paging#task#8; the token is produced at services/service-com-amazonaws-imagebuilder-imagebuilder/src/ops/list_components.rs lines 337-346 and consumed at lines 248-261.
