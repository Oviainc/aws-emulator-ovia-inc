# dynamodb: 2 net-new root causes — the Kinesis streaming-destination state refusals for Disable (never-enabled) and Update (DISABLED) both answer a generic "no streaming destination found" message instead of AWS's state-specific ValidationException wording

> _Note: this issue was identified against the code base at commit `7c633d33488c8b4a2fced706e99f4ae2731b2252`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DisableKinesisStreamingDestination

## Description
Two net-new root causes on DynamoDB's Kinesis streaming-destination control plane, both grounded in failing behavioral checks the replay report marked neither ALREADY FILED nor OWNED. The emulator is serving (224/451 checks pass, bootstrap_signal false), so these are fidelity divergences, not a bootstrap gap. Both operations are DynamoDB control-plane operations (the Kinesis stream in the second check is only a prerequisite resource), so both causes share service `dynamodb`. Both causes must be closed before this issue is submitted.

Shared mechanism (Hypothesis): both handlers resolve the destination with the same helper and word every miss with the same lookup-miss text, so the two DISTINCT state refusals AWS words differently collapse into one message. In the checkout, services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/disable_kinesis_streaming_destination.rs (lines 202-209) and .../src/ops/update_kinesis_streaming_destination.rs (lines 205-212) both call `crate::state::replicating_kinesis_destination_mut(...)` and, on None, `crate::state::kinesis_destination_not_found(&table_name, &input.stream_arn)`. A DISABLED destination that still EXISTS is therefore reported as if no destination had ever been registered.

=== Cause 1 of 2: DisableKinesisStreamingDestination on a never-enabled stream is refused with the wrong message ===
AWS: Smithy (services/service-com-amazonaws-dynamodb-dynamodb-20120810/smithy-model/com-amazonaws-dynamodb-dynamodb-20120810.json) models DisableKinesisStreamingDestination with required TableName (TableArn, len 1..1024) and StreamArn (len 37..1024) and the errors InternalServerError/InvalidEndpointException/LimitExceededException/ResourceInUseException/ResourceNotFoundException; it does NOT model this refusal, so the error class is recorded behavior only: HTTP 400 with error code `ValidationException`. Recorded message, which is ENTIRELY FIXED TEXT with no request- or state-derived values: "Table is not in a valid state to enable Kinesis Streaming Destination: KinesisStreamingDestination must be ACTIVE to perform DISABLE operation." AWS states the refusal in terms of the destination's required STATE (it must be ACTIVE to be disabled), not in terms of a lookup miss, and it does not name the table or the stream. The recording also shows the call leaves no destination behind (DescribeKinesisStreamingDestination answers an empty KinesisDataStreamDestinations list) and that the positive control — Enable, wait for ACTIVE, then Disable — is accepted and reaches DISABLING/DISABLED.
Emulator: the status (400) and the code (ValidationException) are right, but the message is "Table is not in a valid state to enable Kinesis Streaming Destination: No streaming destination with streamArn: <StreamArn from the request> found for table with tableName: <table name from the request>" — the fixed prefix matches, and the remainder is an invented lookup-miss sentence that interpolates the request's StreamArn and TableName where AWS emits the fixed sentence "KinesisStreamingDestination must be ACTIVE to perform DISABLE operation." and interpolates nothing.
Why: a client or operator that distinguishes AWS's refusal classes by message — retry/backoff logic that waits for a destination to become ACTIVE, test suites and CLI wrappers that assert on the state sentence, log-based alarms — reads the wrong cause. It is told the destination does not exist (terminal, nothing to wait for) when AWS tells it the destination is not in the ACTIVE state required for DISABLE.
Fix: the refusal wording in DisableKinesisStreamingDestination's handler/validation path — the refusal must be stated over the destination's required state, not over the lookup result, and must carry no table or stream values.
Traces: dynamodb.disable-kinesis-streaming-destination-not-enabled-rejected.

=== Cause 2 of 2: UpdateKinesisStreamingDestination on an existing but DISABLED destination is refused as a lookup miss instead of as a state violation ===
AWS: Smithy models UpdateKinesisStreamingDestination with required TableName/StreamArn plus UpdateKinesisStreamingConfiguration, and the same five modeled errors; this refusal is likewise not modeled, so it is recorded behavior only: HTTP 400 with error code `ValidationException`. Recorded message: "Table is not in a valid state to enable Kinesis Streaming Destination: Kinesis streaming is not in ACTIVE state. Updates are only allowed in ACTIVE state. TableName: <TableName>, kdsArn: <StreamArn>". Its FIXED text is "Table is not in a valid state to enable Kinesis Streaming Destination: Kinesis streaming is not in ACTIVE state. Updates are only allowed in ACTIVE state. TableName: " ... ", kdsArn: "; its VARIABLE parts are exactly two values taken from the request — the table name and the Kinesis stream ARN. The recording also shows the state contract around it: the identical Update IS accepted while the destination is ACTIVE (DestinationStatus UPDATING, settling back to ACTIVE), and the refused Update must leave the destination DISABLED and the table out of the streaming inventory.
Emulator: status 400 and code ValidationException are right, but the message is "Table is not in a valid state to enable Kinesis Streaming Destination: No streaming destination with streamArn: <StreamArn> found for table with tableName: <TableName>" — i.e. the emulator reports a destination that does not exist, even though the destination record exists and is DISABLED. The state sentence AWS requires ("Kinesis streaming is not in ACTIVE state. Updates are only allowed in ACTIVE state.") and its TableName/kdsArn labelling are never emitted.
Why: the emulator erases the difference between "this table never had that destination" and "that destination exists but is DISABLED". A client that re-enables a destination on a not-found message, or that treats not-found as unrecoverable while treating a non-ACTIVE state as retryable after Enable, branches the wrong way; and the message never names the table/stream pair in AWS's TableName/kdsArn form that tooling parses.
Fix: the state check and refusal wording in UpdateKinesisStreamingDestination's handler — a destination that exists in a non-ACTIVE state must be refused on its state (naming the request's table name and stream ARN in AWS's form), which requires the destination lookup used for the refusal to see non-replicating (DISABLED/DISABLING) records instead of collapsing them into the not-found path shared with Disable.
Traces: dynamodb__kinesis.ddbkds-update-on-disabled-destination-rejected.

Related but NOT covering: the open issue 20261027T001720Z-dynamodb-kinesis-enablekinesisstreamingdestination-omits-enablekinesisstreamingconfiguration-from-its-response.md is keyed to Enable's missing EnableKinesisStreamingConfiguration member and to the absent change-record data plane; neither cause above is its refusal wording. 20261025T024002Z-dynamodb-enablekinesisstreamingdestination-stub.md is keyed to Enable answering NotImplemented; Enable now answers with real behavior (both checks' positive controls get past it).
