# partnercentral-channel is unusable: every operation is refused 403 AccessDenied "Sign the request with the emulator credentials", so no validation, no entitlement denial and no read ever happens (4 causes)

> _Note: this issue was identified against the code base at commit `1a0d537a6f45d8cc06f79b3c3e7692a297108dcd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListChannelHandshakes

## Description
Four net-new root causes in the partnercentral-channel service. All 21 behavioral checks of this service fail, and every one of them gets the same emulator answer: HTTP 403 with awsJson1_0 error code `AccessDenied` and message `Sign the request with the emulator credentials`, for every operation the checks call (ListChannelHandshakes, CreateChannelHandshake, AcceptChannelHandshake, RejectChannelHandshake, CancelChannelHandshake, CreateProgramManagementAccount, DeleteProgramManagementAccount, UpdateProgramManagementAccount, ListProgramManagementAccounts, CreateRelationship, GetRelationship, UpdateRelationship, DeleteRelationship, ListRelationships, ListTagsForResource, UntagResource). The SigV4 request the harness sends is the same one every other bootstrapped service in this emulator accepts, and the same botocore session reaches STS successfully in the same check run (partnercentral-channel.relationship-create-duplicate-submission-access-denied-without-partner-benefit asserts sts:GetCallerIdentity returns an Account before its first channel call), so the refusal is this service's own pre-dispatch credential gate, not the caller.

The open issue 20261022T040845Z-partnercentral-channel-listchannelhandshakes-rejects-a-valid-request-with-403-instead.md reports the wire side of Cause 1 only (ListChannelHandshakes 200->403 from the wire corpus); it does not cover the error code and message of the refusal, nor causes 2-4, and it carries no behavioral replay key.

Cause 1 of 4 — the service refuses a well-formed, authorized request before any handler runs.
AWS: ListChannelHandshakes is a read-only paginated list (Smithy: PartnerCentralChannel, protocol awsJson1_0, authSchemes sigv4/sigv4a; ListChannelHandshakes -> ListChannelHandshakesResponse{items, nextToken}; input requires handshakeType, catalog (@length 1..64, @pattern ^[a-zA-Z]*$) and participantType, with maxResults @range 1..100 default 20). A request that satisfies those constraints from a SigV4-signed caller is answered HTTP 200 with `items` present — empty when nothing matches. This list is reachable without any AWS Partner benefit: it is how a prospective partner sees incoming invitations.
Emulator: HTTP 403, body `{"__type":"AccessDenied","message":"Sign the request with the emulator credentials"}` (botocore: `An error occurred (AccessDenied) when calling the ListChannelHandshakes operation: Sign the request with the emulator credentials`), with no `items` member. Nine checks never get past this: it is the positive control eight of them open with, and it is the whole subject of the ninth.
Why: the service is inert. A client cannot list, create, read or tag anything; the SDK maps the answer to a non-retryable authorization failure, so paginators abort on page one and any flow that reads "no handshakes" from an empty page breaks outright. Worse, `AccessDenied` is not a code this service models at all, so a client catching the modeled AccessDeniedException does not even catch it.
Fix: the pre-dispatch request-authentication/credential gate the router applies to this service (it must accept the emulator's standard SigV4 credentials for partnercentral-channel exactly as for the other bootstrapped services) and then the ListChannelHandshakes success path in services/service-com-amazonaws-partnercentralchannel-partnercentralchannel/src/ops/ — which must serialize ListChannelHandshakesResponse with `items` always present (empty list when nothing matches) and `nextToken` omitted on the last page.
Traces: partnercentral-channel.list-channel-handshakes-succeeds-without-partner-benefit, .accept-channel-handshake-already-accepted-rejected, .cancel-channel-handshake-nonexistent-error, .concurrent-create-program-management-account-all-denied, .create-channel-handshake-access-denied-without-partner-benefit, .create-program-management-account-access-denied-without-partner-benefit, .list-tags-for-resource-well-formed-arn-access-denied-vs-malformed-validation, .reject-channel-handshake-nonexistent-error.

Cause 2 of 4 — the entitlement denial is served with an unmodeled code and the wrong message.
AWS: the write and relationship-read plane of this service is gated on the caller account holding an active AWS Partner benefit, and the refusal is the modeled AccessDeniedException (Smithy: service-common error AccessDeniedException, errorKind client, httpError 403, member `message` @required, optional `reason`), i.e. awsJson1_0 `__type` AccessDeniedException. Its message for this class is fixed text with no variable part: `This action requires an active AWS Partner benefit. Register as an AWS Partner if you haven't already, or contact AWS Partner Central Support.` (recorded behavior; the model documents only "request was denied due to insufficient permissions"). It is returned identically for CreateRelationship, GetRelationship, UpdateRelationship, DeleteRelationship, ListRelationships, ListProgramManagementAccounts, CreateChannelHandshake, CreateProgramManagementAccount and UpdateProgramManagementAccount — including for a syntactically well-formed but nonexistent pma-/rs- identifier, because the entitlement gate fires before any existence check, and identically on an immediate retry of the same request.
Emulator: code `AccessDenied` with message `Sign the request with the emulator credentials` instead of code `AccessDeniedException` with the partner-benefit text (observed verbatim as `expected AccessDeniedException, got AccessDenied: Sign the request with the emulator credentials`).
Why: a client cannot classify the failure. `AccessDenied` is outside this service's modeled error set, so typed `except AccessDeniedException` handlers miss it, and the message tells a partner-onboarding flow to re-sign its request rather than to register as an AWS Partner. The emulator also leaks a signing-layer concern into a business-entitlement answer.
Fix: the entitlement/authorization decision in the partnercentral-channel handlers and the error serializer that builds the 403 body — the modeled AccessDeniedException shape with the fixed partner-benefit message, raised before any resource-existence lookup and deterministic across retries.
Traces: partnercentral-channel.create-relationship-access-denied-for-nonexistent-pma, .get-relationship-nonexistent-access-denied, .delete-relationship-nonexistent-error, .update-relationship-nonexistent-error, .list-relationships-access-denied-without-partner-benefit, .relationship-create-duplicate-submission-access-denied-without-partner-benefit.

Cause 3 of 4 — input-shape validation never runs, so a request AWS rejects for its FORM is answered as an authorization failure.
AWS: constraint validation precedes authorization. Smithy constraints that fire here: ListChannelHandshakesRequest.maxResults / ListRelationshipsRequest.maxResults / ListProgramManagementAccountsRequest.maxResults @range min 1 max 100; UpdateProgramManagementAccountRequest.identifier and DeleteProgramManagementAccountRequest.identifier @pattern ^(arn:[a-z-]+:partnercentral:[a-z0-9-]+:[0-9]{12}:catalog/[a-zA-Z]+/program-management-account/)?pma-[a-z0-9]{13}$ (@length 17..1011); UntagResourceRequest.resourceArn / ListTagsForResourceRequest.resourceArn @pattern ^arn:[a-z-]+:partnercentral:...$; CreateRelationshipRequest.sector enum. The refusal is ValidationException (errorKind client, httpError 400, members message @required, reason @required, fieldList). Its message is the fixed text `N validation error detected.` where N is the number of offending members (one here), plus a `fieldList` entry per offending member whose `name` is the request member that failed, `code` is the violation class, and `message` is `Value at '<member>' failed to satisfy constraint: <the rule>` — e.g. name `maxResults`, code `INVALID_VALUE`, message `Value at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 100`; name `resourceArn`, code `INVALID_STRING_FORMAT`, message `Value at 'resourceArn' failed to satisfy constraint: Member must satisfy regular expression pattern: a full resource ARN`; name `identifier`, code `INVALID_STRING_FORMAT`, message `Value at 'identifier' failed to satisfy constraint: Member must satisfy regular expression pattern: either a resource ID starting with pma- followed by 13 alphanumeric characters or a full ARN`; name `sector`, code `INVALID_ENUM_VALUE`, message `Value at 'sector' failed to satisfy constraint: Member must satisfy enum value set: [GOVERNMENT_EXCEPTION, COMMERCIAL, GOVERNMENT]`. The member names, the offending value's rule text and the limit come from the request and the model; the count and the wrapper sentence are fixed.
Emulator: every one of these is answered 403 `AccessDenied` / `Sign the request with the emulator credentials` (observed verbatim as `expected ValidationException, got AccessDenied` for maxResults=1000, maxResults=101, maxResults=500, resourceArn='not-a-arn' forms, identifier='not-a-valid-pma-identifier', identifier='not-a-pma-identifier' and sector='NOT_A_REAL_SECTOR_VALUE'). No `fieldList` is produced anywhere, and the 400/403 boundary between "your request is malformed" and "you may not do this" disappears.
Why: a client cannot tell a bug in its own request from a missing permission. Code that retries on authorization failures retries a permanently malformed request forever, and code that surfaces `fieldList` to a user shows nothing. It also means the emulator accepts-or-denies without ever inspecting the request, so out-of-range paging and malformed identifiers would silently pass once the gate of Cause 1 is opened.
Fix: the request-validation stage of the partnercentral-channel handlers (services/service-com-amazonaws-partnercentralchannel-partnercentralchannel/src/ops/) must run the modeled @range/@pattern/@length/enum constraints before the authorization decision, and the error serializer must emit ValidationException 400 with `message` = "<N> validation error detected." and the per-member `fieldList`.
Traces: partnercentral-channel.list-channel-handshakes-maxresults-out-of-range-rejected, .list-program-management-accounts-validation-precedes-access-denied, .list-relationships-validation-precedes-access-denied, .untag-resource-malformed-arn-validation-error, .update-program-management-account-nonexistent-error, .delete-program-management-account-nonexistent-error, .create-relationship-invalid-sector-enum-validation-order.

Cause 4 of 4 — the resource-scoped IAM denial for the tagging and handshake planes is never produced.
AWS: for a resourceArn / handshake identifier that is well formed but names a resource in another account that no resource-based policy opens to this caller, the refusal is AccessDeniedException (403) carrying the standard IAM authorization sentence, whose fixed text is `User: <caller principal ARN> is not authorized to perform: partnercentral:<ActionName> on resource: <the resource ARN from the request> because no resource-based policy allows the partnercentral:<ActionName> action` — the caller ARN comes from the signing identity (sts:GetCallerIdentity), the action name from the operation, the resource ARN from the request; everything else is fixed. This is a different code path from Cause 3's shape refusal and from Cause 2's entitlement refusal, and it is deterministic across retries.
Emulator: these operations are refused at the signing gate with 403 `AccessDenied` / `Sign the request with the emulator credentials`; no IAM-worded message naming the principal, the action or the resource is ever produced, so the tagging plane and the handshake accept/reject/cancel plane have no authorization semantics at all.
Why: a caller cannot learn which action on which resource was denied — the one thing the message exists to say — and cannot distinguish "not mine / not visible to me" from "malformed request" or from "not an AWS Partner".
Fix: the authorization layer for the tagging operations (ListTagsForResource, UntagResource) and the handshake transition operations (AcceptChannelHandshake, RejectChannelHandshake, CancelChannelHandshake) in the partnercentral-channel handlers — it must build the modeled AccessDeniedException with the IAM-worded message templated on the caller principal, the partnercentral:<Action> name and the request's resource ARN, after shape validation and without disclosing resource existence.
Traces: partnercentral-channel.list-tags-for-resource-well-formed-arn-access-denied-vs-malformed-validation, .untag-resource-malformed-arn-validation-error, .reject-channel-handshake-nonexistent-error, .cancel-channel-handshake-nonexistent-error, .accept-channel-handshake-already-accepted-rejected.
