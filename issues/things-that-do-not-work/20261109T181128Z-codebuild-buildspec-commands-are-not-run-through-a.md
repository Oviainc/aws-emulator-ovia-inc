# CodeBuild: buildspec commands are not run through a shell (every shell construct exits 127), the YAML-parse context loses the parser diagnostic, RetryBuild ignores concurrentBuildLimit, and no build is ever observable in its BUILD phase (4 causes)

> _Note: this issue was identified against the code base at commit `17c4643c966c9683f16ddaee3534ae6f6497ef31`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartBuild

## Description
FOUR net-new root causes in the codebuild crate (services/service-com-amazonaws-codebuild-codebuild-20161006). ALL FOUR must be closed before this issue is resolved. The open issues about builds FAULTing at PROVISIONING (e.g. 20261107T225801Z-codebuild-6-net-new-causes-builds-and-sandbox.md) and about an unparseable buildspec FAULTing at PROVISIONING (20261029T091648Z-codebuild-a-build-with-an-unparseable-buildspec-faults.md) describe earlier stages: on this checkout these builds DO reach a BUILD/DOWNLOAD_SOURCE verdict, and none of those issues carries a replay key for the checks below.

Cause 1 of 4: buildspec commands are executed without a shell, so every command using shell syntax fails with exit status 127 instead of the status the command computes.
AWS: recorded behavior only for the execution mechanism; AWS runs each entry of a phase's `commands` list through a POSIX shell in the build container, so parameter expansion, arithmetic expansion, command substitution and redirection all work. A command that terminates non-zero fails the phase and CodeBuild records a PhaseContext (Smithy BuildPhase.contexts -> PhaseContext{statusCode, message}) of the form statusCode 'COMMAND_EXECUTION_ERROR', message 'Error while executing command: <the command as written>. Reason: exit status <N>' — fixed text 'Error while executing command: ' and '. Reason: exit status ', with the command text taken from the buildspec and N the status the container actually produced.
Emulator: the command string is not given to a shell. `exit $(( SIM2REAL_EXIT_A + SIM2REAL_EXIT_B ))` reports 'COMMAND_EXECUTION_ERROR Error while executing command: exit $(( SIM2REAL_EXIT_A + SIM2REAL_EXIT_B )). Reason: exit status 127' — 127 is 'command not found', i.e. the literal string was looked up as an executable. The same shape appears for redirection (`printf '%s' "$VAR" > file`) and command substitution (`export X="$(cat f)"`).
Why: no realistic buildspec survives. Variable expansion, redirection and substitution are how builds produce files and exit codes, so phases fail that must succeed, the exit status a client reads back is always 127 rather than the one its command computed, and declared artifacts are never created.
Fix: the build command runner in the codebuild build-execution component — execute each buildspec command through a shell (sh -c) with the build's environment variables exported, and record the real wait status in the phase's PhaseContext message.
Traces: codebuild.failing-pre-build-phase-skips-later-phases-and-reports-the-exit-code (expected exit status 90 from 45+45, got 127), codebuild.on-failure-continue-runs-the-next-phase-while-the-failed-phase-stays-failed (expected 64 from 32+32, got 127).

Cause 2 of 4: a build whose buildspec cannot be parsed fails in DOWNLOAD_SOURCE with a generic one-liner instead of the YAML parser's own diagnostic.
AWS: recorded behavior only (PhaseContext.message is free text, Smithy PhaseContext{statusCode, message}). For a buildspec that is not valid YAML (tab indentation), AWS fails DOWNLOAD_SOURCE and the phase context carries the parser's message, which names the offending construct and its position — e.g. 'found character that cannot start any token at line <N>'. The fixed part is the parser diagnostic class ('... cannot start any token ...'); the variable parts are the character/construct and the line taken from the submitted buildspec.
Emulator: the DOWNLOAD_SOURCE context message is exactly 'Unable to parse YAML file' — a fixed generic sentence with no position and no parser detail.
Why: the whole purpose of this context is to tell a build author where the buildspec is malformed; a caller gets no line, no character, and no way to distinguish a tab-indentation error from any other parse failure.
Fix: the buildspec parsing path in the codebuild build-execution component — propagate the YAML parser's error text (including its position) into the DOWNLOAD_SOURCE PhaseContext message instead of replacing it with a fixed string.
Traces: codebuild.codebuild-invalid-buildspec-yaml-rejected-before-the-build-phase-runs.

Cause 3 of 4: RetryBuild does not enforce the project's concurrentBuildLimit — it mints an extra build where AWS refuses.
AWS: Smithy RetryBuild(id NonEmptyString, idempotencyToken) -> {build}; modeled errors AccountLimitExceededException, InvalidInputException, ResourceNotFoundException (all client, httpError 400). With the project's concurrentBuildLimit already saturated by a running build, AWS answers 400 AccountLimitExceededException with the message 'Concurrent build limit exceeded. This build project has a limit of <limit> concurrent build(s). Start the build again after other builds are complete, or edit project configuration.' — the fixed text is that sentence pair, and <limit> is the project's configured concurrentBuildLimit; no new build is created, so ListBuildsForProject still shows only the pre-existing builds.
Emulator: RetryBuild returns HTTP 200 with a brand-new build (buildStatus IN_PROGRESS, currentPhase QUEUED, the next buildNumber) while another build of that project is IN_PROGRESS and concurrentBuildLimit is 1. The modeled AccountLimitExceededException path is unreachable on this seam.
Why: a client that relies on the refusal to back off instead exceeds its own configured concurrency, and the limit a project advertises is not enforced on the retry path at all — the build set a caller reconciles against gains a build AWS would never have created.
Fix: the RetryBuild handler's precondition checks in the codebuild crate — apply the same concurrent-build accounting StartBuild uses before minting the retried build, emitting AccountLimitExceededException with CodeBuild's wording. Open issue 20261107T225801Z-codebuild-6-net-new-causes-builds-and-sandbox.md owns the StartBuild concurrency check and carries no key for this RetryBuild path.
Traces: codebuild.retry-build-account-limit-exceeded-blocked.

Cause 4 of 4: a running build is never observable in its BUILD phase — a long-running command completes instantly, so queueing and queuedTimeoutInMinutes are never exercised.
AWS: recorded behavior only for the phase timeline; a build whose buildspec runs `sleep 600` stays with currentPhase 'BUILD' and buildStatus IN_PROGRESS for the duration of that command (Smithy Build.currentPhase/phases, BuildPhaseType includes QUEUED and BUILD; StatusType includes IN_PROGRESS). While it holds the only slot of a reserved-capacity fleet, a second build sits with currentPhase 'QUEUED', and when queuedTimeoutInMinutes(Override) elapses the build completes with buildStatus FAILED, currentPhase COMPLETED, and the QUEUED phase's phaseStatus TIMED_OUT.
Emulator: the holder build reports currentPhase 'COMPLETED' within seconds of StartBuild — a 600-second command does not keep the build in BUILD — so no build ever occupies fleet capacity, no second build is ever QUEUED, and the queued-timeout transition cannot occur. Checks that poll for currentPhase == 'BUILD' never see it and exhaust their budget.
Why: every client behavior that depends on a build being in flight is unobservable: waiting for BUILD before stopping it, queue-depth and fleet-capacity behavior, and the queuedTimeoutInMinutes contract. Build durations are reported as effectively zero, so a caller cannot distinguish a build that ran from one that did nothing.
Fix: the build lifecycle/phase scheduler in the codebuild build-execution component — keep the build in its BUILD phase for as long as its commands run, hold the project's/fleet's capacity while it does, and enforce queuedTimeoutInMinutes on a build held in QUEUED (QUEUED phaseStatus TIMED_OUT, build FAILED, currentPhase COMPLETED).
Traces: codebuild.build-queue-timeout-in-minutes-enforced (poll for currentPhase == 'BUILD' on a `sleep 600` build gave up after 600 s with last observed 'COMPLETED'), codebuild.stop-build-on-completed-build-is-an-idempotent-no-op (its positive control polls the same condition and the check exhausted its 180 s budget).
