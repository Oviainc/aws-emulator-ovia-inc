# cloudwatch__ecs__ssm__xray: a launched Fargate task's container never produces its side effects — no CloudWatch metric data and no X-Ray segments from the task, so the task-role permission contrast yields no verdict

> _Note: this issue was identified against the code base at commit `c083bea380b29cc5238d586af0774e0d5864cbe3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
ONE root cause, grounded in the single failing check listed under the cloudwatch__ecs__ssm__xray heading. Per-service bootstrap gate: this heading is a multi-service one; each of its constituent services is bootstrapped (service-com-amazonaws-cloudwatch-graniteserviceversion20100801, service-com-amazonaws-ecs-amazonec2containerservicev20141113, service-com-amazonaws-ssm-amazonssm, service-com-amazonaws-xray-awsxray are all in the bootstrapped set; only athena and iot are pending), so this is filed as a fidelity finding, not deferred. The check is not marked ALREADY FILED or OWNED, and no open or fixed issue names it (no issue mentions a Fargate task's container side effects; the ECS issues cover control-plane validation, representation and task-state reporting).

Cause 1 of 1: ECS accepts RunTask for a Fargate task definition, but the task's container never runs, so nothing the container would publish ever appears — the dependent CloudWatch metric data and X-Ray segments never materialise and an IAM-permission contrast that is only observable through a running container cannot be graded at all.
AWS: recorded behavior only (no Smithy member describes container execution; ECS RunTask is modelled as a control-plane call that returns tasks/failures). On real AWS a Fargate task registered with requiresCompatibilities=[FARGATE], networkMode=awsvpc and a taskRoleArn reaches RUNNING and its container executes with the TASK ROLE's credentials: the check's container loops calling ssm:GetParameter on a flag parameter, xray:PutTraceSegments with one root segment plus two subsegments, and cloudwatch:PutMetricData publishing TraceWrites with Dimension Result=ok on an accepted trace and Result=denied on a refused one, writing its refusal text to the awslogs log group. The contrast the check grades is that the task whose role carries xray:PutTraceSegments/xray:PutTelemetryRecords gets its frames INDEXED in X-Ray (and root-causing to the slow subsegment), while the task whose role omits exactly that statement publishes TraceWrites{Result=denied} and leaves no trace — and that adding the statement to the live role repairs the same running task.
Emulator: every control-plane call of the setup succeeded (ssm.put_parameter, iam role creation, logs.create_log_group, ecs.create_cluster, two ecs.register_task_definition, two ecs.run_task), but the first differential barrier — cloudwatch.get_metric_statistics for TraceWrites{Result=ok} in the allowed task's namespace >= 3 AND TraceWrites{Result=denied} in the denied task's namespace >= 3 AND >= 3 indexed X-Ray traces for the allowed service — never advanced, and the check ended with TimeoutError 'the control tracing its frames and the denied task reporting refusals: the run budget ended first; not graded'. Hypothesis (the check's own message says the run budget, not its 420 s task deadline, ended the poll, so the emulator is not proven to never converge): ECS RunTask records task state without executing the container image, so none of the container's SSM/X-Ray/CloudWatch calls is ever made and none of the three counters can move; the same shape is already filed for Lambda, whose Invoke refuses every real invocation (20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md).
Why: a client cannot exercise anything that depends on a task doing work — task-role credential scoping, instrumented traces from a task, container metrics or container logs. Every such scenario silently produces no data rather than an error, which is the direction that hides breakage: the emulator reports a launched task and then nothing ever happens, so an IAM least-privilege contrast on a task role (the whole point of this check) is unverifiable in either direction.
Fix: the ECS RunTask/task-lifecycle component (the ecs crate's run_task handler and the task state it drives) must make a launched task's declared work observable — either by executing the container workload or by driving the task through its lifecycle with the side effects its definition declares (awslogs log stream, and the task-role-signed data-plane calls the container makes) — so that cloudwatch:PutMetricData and xray:PutTraceSegments from a task are reachable, and so that a task role missing xray:PutTraceSegments is refused where a role carrying it is not.
