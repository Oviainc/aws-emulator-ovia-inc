# Service Quotas default-quota catalog covers only five services and is incomplete for those

## Operation
ListAWSDefaultServiceQuotas

## Description
The emulator's Service Quotas static catalog (the table behind ListServices / ListAWSDefaultServiceQuotas) only knows five service codes (dynamodb, ec2, lambda, s3, vpc) and, even for those, holds a small subset of each service's AWS default quotas with several ServiceQuota members unpopulated. Five distinct causes, all rooted in that one catalog plus the handlers that read it.

Cause 1 of 5 — ListAWSDefaultServiceQuotas 404s for every service code outside the five-entry stub.
AWS: ListAWSDefaultServiceQuotas takes a required ServiceCode (Smithy: ListAWSDefaultServiceQuotasRequest.ServiceCode @required, @length 1-63, @pattern ^[a-zA-Z][a-zA-Z0-9-]{1,63}$) and returns HTTP 200 with Quotas (ServiceQuotaListDefinition) for any service code that ListServices enumerates; NoSuchResourceException is reserved for codes that are not AWS service codes at all. The recording shows 200 with a populated Quotas list for ordinary service codes such as access-analyzer, acm, apigateway, athena, autoscaling (e.g. QuotaCode L-96F55078 'Policy generation CloudTrail time range').
Emulator: HTTP 404 with no Quotas member for every such service code. This cluster covers 239 recorded steps — effectively every service in the catalog corpus except the five hardcoded ones.
Why: a client enumerating AWS default quotas (console-style quota browsers, drift checkers, Terraform/CDK quota lookups) gets a hard NoSuchResourceException for virtually every AWS service, so it concludes the service code does not exist rather than reading its defaults.
Fix: the Service Quotas default-quota catalog data set, and the ListAWSDefaultServiceQuotas handler that resolves ServiceCode against it.
Traces: service-quotas-catalog-list-aws-default-service-quotas-access-analyzer#task#1 (238 further affected fixtures in the same cluster, one per service code).

Cause 2 of 5 — the dynamodb default-quota set is missing most of its quotas and several members of the one it does return.
AWS: ListAWSDefaultServiceQuotas('dynamodb') returns 200 with the full default quota set for DynamoDB; each element is a ServiceQuota carrying Description, QuotaArn, Unit, Value, Adjustable, GlobalQuota and, where DynamoDB publishes a CloudWatch usage metric, UsageMetric (MetricInfo: MetricNamespace/MetricName/MetricDimensions/MetricStatisticRecommendation). Recorded behavior shows at least L-AB614373, L-34F8CCC8, L-1BB77E89, L-2A593B99, L-34F6A552, L-6F30DCE1, L-923BEB7A, L-C2098644, L-CF0CBE56, L-D98E8184, L-F3CA5463, L-F7858A77 present, and L-F98FE922 carrying Description, QuotaArn and UsageMetric.
Emulator: 200, but all twelve of those QuotaCodes are absent from Quotas and L-F98FE922 is returned without Description, QuotaArn or UsageMetric.
Why: a client that looks up a specific DynamoDB quota by code finds it missing from the list and treats the quota as nonexistent; one that drives CloudWatch usage alarms off UsageMetric has no metric to subscribe to.
Fix: the dynamodb rows of the default-quota catalog data set (quota coverage and per-quota member population).
Traces: service-quotas-catalog-list-aws-default-service-quotas-dynamodb#task#1.

Cause 3 of 5 — the s3 default-quota set is missing most of its quotas.
AWS: ListAWSDefaultServiceQuotas('s3') returns 200 with S3's full default quota set. Recorded behavior shows 21 QuotaCodes the emulator does not return, including L-B461D596 ('Replication rules'), L-1A9B467F, L-89BABEE8 (Unit 'Terabytes'), L-349AD9CA (which carries Period {PeriodUnit SECOND, PeriodValue 1} and Unit 'Gigabits'), L-146D5F0C, L-1923B91D, L-2431D3AF, L-2A85EAC1, L-3E24E5F9, L-55BA2C6C, L-6AF88990, L-748707F3, L-775A314D, L-881EA1F4, L-9CD4D118, L-BB883139, L-CD1053C4, L-DC2B2D3D, L-DEBF781C, L-DEDCCF9D, L-FAABEEBA.
Emulator: 200 with those entries absent from Quotas.
Why: same class of failure as cause 2 — rate-shaped quotas (the ones carrying Period) are exactly what throughput-planning clients read, and they are not there at all.
Fix: the s3 rows of the default-quota catalog data set.
Traces: service-quotas-catalog-list-aws-default-service-quotas-s3#task#1.

Cause 4 of 5 — the vpc default-quota set is missing most of its quotas, and the AWS-default QuotaArn is built with an account id in it.
AWS: ListAWSDefaultServiceQuotas('vpc') returns 200 with VPC's full default quota set. Two separate defects show here. (a) Roughly 35 QuotaCodes are absent (L-5F53652F, L-45FE3B85, L-42B9C2CA, L-045E6E9C, L-0EA8095F, L-12E49864, L-1B52E74A, L-29B6F2EB, L-2AEEBF1A, L-2AFB9258, L-2C462E13, L-3248932A, L-3B4E38D2, L-407747CB, L-44499CD2, L-589F43AA, L-7E9ECCDB, L-8312C5BB, L-83CA0A9D, L-93826ACB, L-A272D574, L-B4A6D682, L-BB24F6E5, L-CA6CC422, L-CD17FD4B, L-DC9F7029, L-DF5E4CA3, L-DFA99DE7, L-E79EC296, L-FE5A380F), and the ones returned (L-F678F1CE, L-085A6257, L-A4707A72) lack Description, Period and UsageMetric and carry wrong Adjustable/Value. (b) The QuotaArn of an AWS *default* quota has an EMPTY account-id segment — recorded form arn:aws:servicequotas:<region>::<serviceCode>/<quotaCode> — whereas the emulator emits arn:aws:servicequotas:<region>:<accountId>:<serviceCode>/<quotaCode>. (Applied quotas, returned by ListServiceQuotas/GetServiceQuota, DO carry the account id; the distinction is default-vs-applied, not a formatting accident.)
Why: ARN-keyed clients (tagging, policy conditions, cross-referencing a default quota against an applied one) build or match the wrong ARN, and the missing Period/UsageMetric strips the rate semantics off the quota.
Fix: the vpc rows of the default-quota catalog, and the QuotaArn construction used by the AWS-default code path (it must omit the account id).
Traces: service-quotas-catalog-list-aws-default-service-quotas-vpc#task#1.

Cause 5 of 5 — ListServices returns five services instead of the whole AWS service catalog.
AWS: ListServices returns 200 with Services (ServiceInfoListDefinition of ServiceInfo{ServiceCode, ServiceName}) enumerating every service that publishes quotas, paginated via NextToken/MaxResults (Smithy: ListServices @paginated inputToken NextToken, outputToken NextToken, items Services, pageSize MaxResults). The recording returns on the order of 283 entries, ordered by ServiceCode (AWSCloudMap, access-analyzer, account-access, acm, acm-pca, aco-automation, agent-registry, ...).
Emulator: 200 with exactly five entries (dynamodb, ec2, lambda, s3, vpc), in that order, and nothing else.
Why: ListServices is the documented discovery entry point for the whole API — a client enumerates it and then calls ListServiceQuotas/ListAWSDefaultServiceQuotas per code. With five entries it never discovers the other services, and it also never exercises pagination.
Fix: the Service Quotas service catalog data set, and the ListServices handler's ordering/pagination.
Traces: service-quotas-catalog-list-services#task#1.
