# Type-filtered ListGroupResources never reflects real membership: the accepted resource-type filter (positive control) answers an empty 200 forever

> _Note: this issue was identified against the code base at commit `a28b00726e6917844828701198c7c2f9a84a8d63`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListGroupResources

## Description
This issue carries 1 cause (Cause 1 of 1). Related but NOT covering it: open issue 20261029T195549Z-resource-groups-resolves-no-real-resources-searchresources-and.md (its cause 2 describes the same handler gap but is grounded in six OTHER check ids and does not carry this check's replay key) and open issue 20261024T072908Z-resource-groups-listgroupresources-wrong-behavior (static-pass description of the same handler). If either is fixed first this may close with it — confirm only by re-replaying the check id in trace_ids.

Cause 1 of 1: ListGroupResources accepts a resource-type filter that IS part of the group's own query (that leg is correct) but then resolves membership only from statically recorded members, so the filtered listing answers 200 with an empty Resources list forever and the group's stored TAG_FILTERS_1_0 query is never evaluated. Failing check: resource-groups.list-group-resources-type-filter-mismatch-rejected.
AWS: Smithy: ListGroupResources (POST /list-group-resources), output Resources (ListGroupResourcesItemList, each Identifier.ResourceArn + Identifier.ResourceType), ResourceIdentifiers, QueryErrors, NextToken; errors BadRequestException (400), NotFoundException (404), ForbiddenException (403), MethodNotAllowedException (405), TooManyRequestsException (429), InternalServerErrorException (500), UnauthorizedException (401). Documented as "Returns a list of Amazon resource names (ARNs) of the resources that are members of a specified resource group", with required permissions resource-groups:ListGroupResources, cloudformation:DescribeStacks, cloudformation:ListStackResources, tag:GetResources — i.e. membership of a query-based group is DERIVED by running the group's stored ResourceQuery against the account's tagged resources / stack resources. Smithy doc for ListGroupResourcesInput$Filters: a resource-type filter "Filters the results to include only those of the specified resource types" and is validated against "the types that are defined in the query associated with the group". So for a group whose query is {ResourceTypeFilters:["AWS::SQS::Queue"], TagFilters:[{Key:K, Values:[V]}]} and a queue carrying tag K=V, ListGroupResources with Filters=[{Name:"resource-type", Values:["AWS::SQS::Queue"]}] must eventually return that queue's ARN with Identifier.ResourceType "AWS::SQS::Queue" — the filter narrows a derived membership, it does not substitute for it.
Emulator: the refusal leg is right — a filter value the group's query does not admit is refused 400 BadRequestException with the expected message, whose fixed text is "Filters not valid: The resource types specified as filters in the request are incompatible with the group query:" followed by the unadmitted type values taken from the request (services/service-com-amazonaws-resourcegroups-ardi/src/ops/list_group_resources.rs:259-270, :343-344). The ACCEPTED leg then diverges: the handler builds the page from group.members only (list_group_resources.rs:289-297), the list written exclusively by GroupResources (static membership), and hardcodes query_errors: None (:326-328) with the comment "listing recorded memberships runs none". The group's stored ResourceQuery is write-only state; nothing evaluates it. The emulator therefore answers every poll immediately with HTTP 200 and Resources: [] (and ResourceIdentifiers: []), with no QueryErrors to explain the gap, so the check's predicate can never become true and the harness reports "Check timed out after 60.0s". The divergence is the empty 200, not slowness.
Why: a client that creates a tag-query group and then narrows its listing by a resource type the query admits — the normal way this operation is used by inventory, dashboard and bulk-tagging tooling — receives a silent empty set with a 200 and no QueryErrors, indistinguishable from "the group genuinely has no members". Worse, the rejection half of the contract passes while the acceptance half cannot, so a target that refuses everything incompatible and resolves nothing at all looks correct to any check that only asserts the refusal.
Fix: the ListGroupResources handler's membership resolution — for a group that stores a ResourceQuery, evaluate that query against the emulator's cross-service resource/tag inventory (sharing the evaluator with SearchResources) instead of reading only GroupRecord::members, derive Identifier.ResourceType from the matched resource, apply the request's resource-type Filters to that derived set, and report QueryErrors for anything the query could not resolve. The existing filter-validation and pagination code paths are correct and should be preserved.
Traces: resource-groups.list-group-resources-type-filter-mismatch-rejected (the refusal leg passes; the positive-control leg times out).
