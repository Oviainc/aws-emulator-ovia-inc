# AppConfig experiment-run lifecycle: UpdateExperimentRun records no EXPOSURE_UPDATED event, ListExperimentRunEvents returns oldest-first, and updating a terminal run is refused as ConflictException instead of BadRequestException (3 causes)

> _Note: this issue was identified against the code base at commit `21d30b53374928fd663edcc8ae486344ab510a4e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListExperimentRunEvents

## Description
Three distinct root causes in the AppConfig experiment-run lifecycle, all grounded in replayed behavioral checks. Causes 1 and 2 are in the experiment-run event log (what gets recorded, and in what order it is returned); cause 3 is the refusal CLASS for a forward-only state-machine violation. They are bundled because they all belong to the appconfig experiment-run state and its event projection. Numbered; close ALL THREE before submitting.

NOTE on an adjacent open issue: 20261024T131534Z-appconfig-refusal-messages-on-the-tagging-pagination-hosted.md covers AppConfig refusal MESSAGE wording for TagResource/UntagResource, pagination tokens, CreateHostedConfigurationVersion and CreateExperimentDefinition. It does NOT cover UpdateExperimentRun, and cause 3 below is not a message-wording nit: the emulator returns the WRONG error shape and HTTP status (409 ConflictException where AWS returns 400 BadRequestException), so it is a separate work item. This is not a REOPEN of any fixed issue.

=== Cause 1 of 3: UpdateExperimentRun does not record an EXPOSURE_UPDATED event ===
AWS: an experiment run's event log is a timeline of every action and state change on that run. Smithy: ListExperimentRunEvents GET /applications/{ApplicationIdentifier}/experimentdefinitions/{ExperimentDefinitionIdentifier}/experimentruns/{Run}/events, output ExperimentRunEvents.Items of ExperimentRunEvent; ExperimentRunEvent.EventType targets enum ExperimentRunEventType with values RUN_STARTED, EXPOSURE_UPDATED, OVERRIDES_UPDATED, RUN_STOPPED, and its own documentation states "The type of event. Valid values: RUN_STARTED, EXPOSURE_UPDATED, OVERRIDES_UPDATED, RUN_STOPPED"; the operation doc states it "Lists the events for a specified experiment run. Events provide a timeline of actions and state changes that occurred during the run." So a successful UpdateExperimentRun that changes ExposurePercentage must append an EXPOSURE_UPDATED event (and one that changes TreatmentOverrides an OVERRIDES_UPDATED event), each carrying the OccurredAt of the change and the ExposurePercentage/TreatmentOverrides in force at that moment.
Emulator: UpdateExperimentRun applies the new ExposurePercentage to the run's state but appends nothing to the event log. After StartExperimentRun(ExposurePercentage=5.0) -> UpdateExperimentRun(ExposurePercentage=25.0) -> StopExperimentRun, ListExperimentRunEvents returns exactly two items, EventType RUN_STARTED and RUN_STOPPED. EXPOSURE_UPDATED is never emitted for any update, so the enum value is unreachable; the update is visible only as the exposure value carried on the later RUN_STOPPED event.
Why: the event log is the audit timeline a client uses to reconstruct what an experiment was exposed to and when. Against the emulator every mid-run exposure (or override) change is invisible: a consumer that correlates exposure windows, bills or attributes metrics per exposure level, or alerts on operator changes to a running experiment, sees a run that was started at one exposure and stopped, with no record that it ever changed. Pagination is affected too, since Items is short by one entry per update.
Fix: the UpdateExperimentRun handler's state mutation must append an ExperimentRunEvent to the run's event log (EventType EXPOSURE_UPDATED when ExposurePercentage changes, OVERRIDES_UPDATED when TreatmentOverrides change), with OccurredAt at the mutation and the post-update ExposurePercentage/TreatmentOverrides, so ListExperimentRunEvents projects it.
Traces: appconfig.experiment-run-events-chronological-ordering.

=== Cause 2 of 3: ListExperimentRunEvents returns the timeline oldest-first instead of most-recent-first ===
AWS: AppConfig returns run events most-recent-first — the same convention AppConfig documents for deployment events ("The most recent events are displayed first"). The first element of Items is the newest event and OccurredAt descends down the page. Recorded behavior only for the ordering itself (the Smithy model declares Items as a list and does not state the sort), but the check asserts the ordering directly: Items[0].EventType == RUN_STOPPED, Items[-1].EventType == RUN_STARTED, and OccurredAt sorted descending.
Emulator: Items comes back in ascending (oldest-first) OccurredAt order — the replay shows Items[0] = RUN_STARTED (earlier OccurredAt) and Items[1] = RUN_STOPPED (later OccurredAt), i.e. the reverse of AWS's order. This is independent of cause 1: even with only two events the order is already inverted, and it would still be inverted once EXPOSURE_UPDATED is emitted.
Why: a client that reads the head of the first page to get the run's current/latest state (the normal use of a most-recent-first feed, and the only cheap one under pagination with MaxResults) gets the run's OLDEST event instead. With paging, the newest events land on the LAST page rather than the first, so a consumer that fetches one page sees a stale view and never observes the stop.
Fix: the ListExperimentRunEvents handler/projection must order the run's event log by OccurredAt descending before pagination (newest first), not insertion order.
Traces: appconfig.experiment-run-events-chronological-ordering.

=== Cause 3 of 3: UpdateExperimentRun on a terminal (DONE) run is refused with ConflictException 409 instead of BadRequestException 400 ===
AWS: experiment runs are a forward-only state machine over ExperimentRunStatus (Smithy enum values RUNNING, DONE). Once a run has reached the terminal DONE status, UpdateExperimentRun is refused with BadRequestException — HTTP 400, error code BadRequestException (Smithy: UpdateExperimentRun PATCH /applications/{ApplicationIdentifier}/experimentdefinitions/{ExperimentDefinitionIdentifier}/experimentruns/{Run}/update, success code 200, modeled errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / InternalServerException 500; BadRequestException is documented as "The input fails to satisfy the constraints specified by an Amazon Web Services service", ConflictException as "The request could not be processed because of conflict in the current state of the resource"). The message is the request-derived template "Cannot update experiment run <Run> for experiment definition <ExperimentDefinitionId> because it is already terminal." — fixed text "Cannot update experiment run ", " for experiment definition " and " because it is already terminal.", with <Run> taken from the request's Run member and <ExperimentDefinitionId> from the request's ExperimentDefinitionIdentifier. The refusal must leave no effect: the DONE run's ExposurePercentage stays at the value it had when it stopped. Updating a still-RUNNING run must still succeed and persist (Status RUNNING, the new ExposurePercentage readable via GetExperimentRun).
Emulator: the call IS refused and has no effect, but with the wrong error shape and status — error code 'ConflictException' (HTTP 409) rather than 'BadRequestException' (HTTP 400). Replay: AssertionError: got='ConflictException'. Because the code diverges, the check stopped before comparing the Message, so the message template above must be verified as part of the fix.
Why: the two errors mean different things and clients branch on exactly that. ConflictException/409 denotes a transient conflict with the resource's current state and is the retry-after-settling signal — the harness's own StartExperimentRun helper, like real client code, retries precisely on ConflictException. A terminal run never leaves DONE, so a client that treats the emulator's 409 as retryable spins until its deadline instead of failing fast on a permanent input error; a client that classifies 4xx by code records a conflict where AWS reports invalid input, and 409-vs-400 also changes generic HTTP retry policy in the SDKs.
Fix: the terminal-status guard in the UpdateExperimentRun handler's validation must raise BadRequestException (400) instead of ConflictException (409), rendering AWS's message template from the request's Run and experiment-definition id. Keep ConflictException for genuine current-state conflicts, and keep the existing no-effect behavior and the RUNNING-run success path.
Traces: appconfig.update-experiment-run-invalid-state-transition-rejected.
