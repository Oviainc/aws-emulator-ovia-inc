# ListPurchaseOptions returns an empty page for filtered and drilldown queries

> _Note: this issue was identified against the code base at commit `a49d8a631972e5e3f3c68d65033d44ad0fc63f2b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 2 net-new root causes, both in marketplace-discovery and both on ListPurchaseOptions, found by replaying the wire corpus simparity-wire-aws-v1 against the emulator built from this checkout (28 steps, 13 passed, 12 mismatched, 3 blocked; 46.4%). Neither is grounded in a per-run value: the assertions that fail are on the presence and the shape of the modelled PurchaseOptionSummary items the operation must return, not on a request id, a clock reading or an account-specific id.

The shared fault: ListPurchaseOptions answers HTTP 200 with an EMPTY purchaseOptions page for every query in the corpus that narrows purchase options down to a concrete product/seller or drills into an offer set, where the recorded service returns at least one fully populated purchase option. The operation is reachable and well-formed (status, content type and envelope all match) but its match set is always empty, so the whole purchase-options half of the discovery flow is a dead end.

Two already-open marketplace-discovery issues are adjacent but cover NEITHER of these replay keys (the replay report marks both clusters as un-owned), so they do not cover these causes: 20261029T201942Z-marketplace-discovery-getlisting-getproduct-and-listfulfillmentoptions-serve-synthesized-placeholder-records.md is about GetListing/GetProduct/ListFulfillmentOptions serving synthesized CONTENT for records they do find, and 20261030T005652Z-marketplace-discovery-iam-authorization-never-evaluated-on-getlisting.md Cause 4 is about the ORDER of the PurchaseOptionFilterType value set inside a ValidationException message. Here the operation succeeds and returns nothing at all; both causes below must be closed on their own.

=== Cause 1 of 2: a ListPurchaseOptions query filtered by PRODUCT_ID and SELLER_OF_RECORD_PROFILE_ID returns no purchase options at all ===
AWS: Smithy: ListPurchaseOptions (POST /2026-02-05/listPurchaseOptions, http 200, @readonly, @paginated{inputToken: nextToken, outputToken: nextToken, items: purchaseOptions}); input filters -> PurchaseOptionFilterList @length(1..10) of PurchaseOptionFilter{filterType: PurchaseOptionFilterType (required), filterValues: PurchaseOptionFilterValueList @length(1..10) (required)}; output purchaseOptions -> PurchaseOptionSummaryList @length(..100) plus nextToken. The operation doc: "Returns the purchase options (offers and offer sets) available to the buyer. You can filter results by product, seller, purchase option type, visibility scope, and availability status." PurchaseOptionFilter$filterValues doc: PRODUCT_ID takes "One or more product identifiers to filter by", SELLER_OF_RECORD_PROFILE_ID "One or more seller profile identifiers to filter by"; multiple filters are AND-combined, multiple values within one filter are OR-combined. So a request naming a product that exists in the catalog together with that product's own seller profile must return the purchase options covering that product, each a PurchaseOptionSummary carrying the required purchaseOptionId, catalog, purchaseOptionType (OFFER or OFFERSET), sellerOfRecord and associatedEntities, plus the optional purchaseOptionName/availableFromTime/expirationTime/badges. Recorded behavior: 200 with purchaseOptions[0] present — purchaseOptionType OFFER, catalog AWSMarketplace, a sellerOfRecord{sellerProfileId, displayName}, badges[{badgeType AUTO_RENEW, displayName "Auto-renew"}], and associatedEntities[0] carrying both the product{productId, productName, manufacturer{sellerProfileId, displayName}} and the offer{offerId, sellerOfRecord{...}}. The concrete ids, names and the seller profile id in that recording are values of the recorded catalog, not literals the emulator must reproduce; the requirement is that a product-and-seller scoped query returns the matching purchase option(s) with those members populated.
Emulator: 200 with an EMPTY page — purchaseOptions[0] is missing (the list is empty), so a client sees "no purchase options for this product" for a product the same emulator serves through its own listing graph. The status, the code path and the envelope are right; only the match set is empty. Hypothesis: the seeded catalog's offers/offer sets carry product ids and seller profile ids drawn from a different population than the ones a product-scoped drilldown reaches, so no PurchaseOptionEntry can satisfy a PRODUCT_ID or SELLER_OF_RECORD_PROFILE_ID filter — matches_every_filter compares the filter values against entry.product_ids and entry.seller_profile_id by exact string equality, which can never hold if the catalog never contains the queried id.
Why: a client that discovers a product and then asks for its purchase options — the normal buy-path in this API — concludes the product has none, and never reaches GetOffer/GetOfferSet. Because the operation returns 200 rather than an error, the client has no signal that anything is wrong: a procurement UI renders an empty "pricing options" panel, and an automated test asserting "every product has at least one purchase option" passes against AWS and fails only in the emulator (or, written the other way round, passes in the emulator while asserting nothing). Pagination is unreachable for the same reason: an always-empty match set never emits nextToken.
Fix: the operation's state/match layer — the catalog projection ListPurchaseOptions pages over, so that the offers and offer sets it projects are keyed by the SAME product ids and seller profile ids the rest of the catalog exposes, and the PRODUCT_ID / SELLER_OF_RECORD_PROFILE_ID filter predicates then match. The filter semantics themselves (AND across filters, OR within one) belong in the handler's filter predicate; the ids they compare against belong in the seeded catalog. Traces: services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/list_purchase_options.rs (handle + matches_every_filter) and the catalog seed and purchase_options() projection in services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs.
Traces: fixture marketplace-discovery-purchase-options-filter-by-product-and-seller step task#1 (representative; the cluster also covers marketplace-discovery-purchase-options-offer-drilldown step task#1).

=== Cause 2 of 2: drilling into an offer set with ListPurchaseOptions returns an empty list instead of the offer set's purchase options ===
AWS: Smithy: same operation and shapes as Cause 1; PurchaseOptionType enumerates OFFER ("a single-product offer") and OFFERSET ("a bundled offer set"), and PurchaseOptionSummary$associatedEntities (required) is documented as "The products, offers, and offer sets associated with this purchase option", each PurchaseOptionAssociatedEntity carrying the product, the offer and optionally the offer set. So an offer-set drilldown — a filtered ListPurchaseOptions issued after an offer set has been resolved — returns the purchase options belonging to that set, each with its associatedEntities populated. Recorded behavior: 200 with purchaseOptions a NON-empty list whose first element is an OFFER purchase option carrying catalog AWSMarketplace, sellerOfRecord{sellerProfileId, displayName}, badges[{badgeType AUTO_RENEW, displayName "Auto-renew"}] and associatedEntities[0]{product{productId, productName, manufacturer{...}}, offer{offerId, sellerOfRecord{...}}}. Again the recorded ids/names are that catalog's values, not a requirement.
Emulator: 200 with purchaseOptions = [] — the whole list is empty, so the drilldown yields nothing. Hypothesis: the offer-set projection in purchase_options() builds its OFFERSET entries only from offers reachable via offer_set.offer_ids and skips any id it cannot resolve (`let Some(offer) = self.offers.get(offer_id) else { continue }`), and the filtered query's values do not match the seeded ids, so the AND of the filters eliminates every candidate.
Why: the offer-set path is the multi-product procurement flow; a client that has an offer set in hand cannot enumerate what it contains, so it cannot price or subscribe to the bundle. As in Cause 1 the response is a success, so the failure is silent and a test built on the emulator certifies a flow that does not work.
Fix: same component as Cause 1 — the catalog projection and the filter predicate for OFFERSET entries in ListPurchaseOptions, so an offer set that exists in the catalog is reachable by a filtered ListPurchaseOptions and reports its member purchase options with associatedEntities (product + offer + offerSet) populated. Traces: services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/list_purchase_options.rs and the offer-set branch of purchase_options() in services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs.
Traces: fixture marketplace-discovery-purchase-options-offerset-drilldown step task#2.
