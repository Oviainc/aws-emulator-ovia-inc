# bedrock: 2 net-new causes — no-commitment CreateProvisionedModelThroughput refuses every PROVISIONED-catalogued model as unsupported instead of reaching the model-unit quota refusal, and CreateModelInvocationJob accepts a pass-role the recording denies

> _Note: this issue was identified against the code base at commit `9d2e170c3a479b68290b0c2532ee0534a60c9186`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateProvisionedModelThroughput

## Description
TWO net-new root causes in the bedrock control plane, both on the create path of a billable resource. Numbered below; each must be closed before this issue is submitted.

Cause 1 of 2: a no-commitment CreateProvisionedModelThroughput (no `commitmentDuration`) on a base model that this same emulator's ListFoundationModels reports as PROVISIONED-capable and ACTIVE is refused 400 ValidationException 'The provided model is not supported for provisioned throughput.' — the eligibility gate short-circuits before the model-unit quota gate is ever reached.
Failing checks: bedrock.create-provisioned-throughput-zero-units-rejected, bedrock.provisioned-throughput-create-delete-404, bedrock.provisioned-throughput-lifecycle, bedrock.numeric-precision-provisioned-throughput-model-units-preserved.
AWS: the purchase is classified against the ACCOUNT'S GRANTED no-commitment model-unit quota, not against a blanket per-model 'PT unsupported' wall, for any model the account's own catalogue returns from ListFoundationModels(byInferenceType=PROVISIONED) with modelLifecycle.status ACTIVE. With the default quota (zero no-commitment model units, the default for every account until AWS Support raises it) the call is refused 400 ServiceQuotaExceededException whose message is the fixed sentence 'Your account does not currently have any no commitment model units reserved for <modelId>. Please see https://support.console.aws.amazon.com/support/home?region=<region>#/case/create?issueType=service-limit-increase to request a service quota increase.' — fixed text everywhere except two variable parts taken from the request and the caller's endpoint: <modelId> is the BARE model id of the modelId the request names (the short id, not the ARN) and <region> is the request's region. No resource is created. Smithy (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice): CreateProvisionedModelThroughput POST /provisioned-model-throughput, success 201, modelUnits @required PositiveInteger @range min 1, modelId @required ModelIdentifier, commitmentDuration optional enum (OneMonth|SixMonths, omitted = no-commitment); modeled errors ValidationException httpError 400, ServiceQuotaExceededException httpError 400 ('The number of requests exceeds the service quota'), ResourceNotFoundException 404, AccessDeniedException 403, TooManyTagsException 400, ThrottlingException 429, InternalServerException 500. The modelId doc states Provisioned Throughput is purchasable only for the published PT model list, and the modelUnits doc states the account holds no model units until it requests them via support — i.e. the account-quota refusal is the documented outcome. The exact quota sentence above is recorded behavior only (the model gives the error class, not its text); it is what the recorded responses carry for every candidate model, and the emulator already composes the same sentence elsewhere (see Traces).
Emulator: 400 ValidationException with message 'The provided model is not supported for provisioned throughput.' for every candidate. Concretely, with amazon.nova-lite-v1:0 (returned by this emulator's own ListFoundationModels(byInferenceType=PROVISIONED) as ACTIVE, addressed as arn:aws:bedrock:<region>::foundation-model/amazon.nova-lite-v1:0) and modelUnits=1 the reply is ValidationException, not ServiceQuotaExceededException. The ValidationException for modelUnits=0 is correct and does pass, so the divergence is specifically the well-formed request's classification. The emulator is also self-inconsistent: a model it advertises as PROVISIONED-eligible in the catalogue is rejected as not eligible on purchase.
Why: a client cannot tell 'ask AWS Support for model-unit quota' (a 400 ServiceQuotaExceededException, the one actionable outcome, routed to a quota owner) from 'this model can never be provisioned' (a ValidationException, which tells the caller to pick another model — advice that is wrong for every model in the catalogue). Every Provisioned Throughput flow built on this API therefore mis-branches: capacity-planning tooling drops the model from its candidate list, quota-request automation never fires, and any test or runbook that distinguishes a malformed request (modelUnits=0 -> ValidationException) from a quota-gated one (modelUnits=1 -> ServiceQuotaExceededException) sees both collapse into one code. It also makes the whole create->Creating->InService->delete->404 lifecycle unreachable, since no model can be purchased at all.
Fix: the CreateProvisionedModelThroughput handler's validation ordering and the no-commitment eligibility data it consults — the no-commitment-eligible base-model set and the gate that precedes the granted-model-unit check in that handler must admit the models the service's own foundation-model catalogue returns for byInferenceType=PROVISIONED, so a well-formed no-commitment purchase reaches the granted-model-unit refusal and is answered 400 ServiceQuotaExceededException with AWS's sentence (the emulator's existing no-commitment quota message helper), while the not-supported ValidationException stays reserved for models the catalogue genuinely does not offer PT for (and the retired set).
Traces: bedrock.create-provisioned-throughput-zero-units-rejected (expected ('ServiceQuotaExceededException', 'Your account does not currently have any no commitment model units reserved for amazon.nova-lite-v1:0. Please see ...'), got ('ValidationException', 'The provided model is not supported for provisioned throughput.')); bedrock.provisioned-throughput-create-delete-404 (same, asserted for two eligible models); bedrock.provisioned-throughput-lifecycle (expected one of ServiceQuotaExceededException/AccessDeniedException, got ValidationException); bedrock.numeric-precision-provisioned-throughput-model-units-preserved (raised ValidationException out of the candidate loop, which only tolerates ServiceQuotaExceededException). Code sites for the fixer: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_provisioned_model_throughput.rs lines 297-306 (the no-commitment eligibility short-circuit returning `not_provisionable()`) versus lines 308-329 (the granted-model-unit gate that composes the correct ServiceQuotaExceededException via `crate::state::no_commitment_model_units_message`), with the eligibility predicate `crate::state::supports_no_commitment_provisioned_throughput` and the message constant `crate::state::MODEL_NOT_SUPPORTED_FOR_PROVISIONED_THROUGHPUT` in that crate's state module. Related open issue that does NOT cover this: 20261101T064404Z-bedrock-listfoundationmodels-serves-an-incomplete-foundation-model-catalogue-with.md is about ListFoundationModels' catalogue content and carries no CreateProvisionedModelThroughput key, so this refusal stays wrong when it is closed; 20261029T211357Z-bedrock-answers-resourcenotfoundexception-or-accessdeniedexception-where-aws-answers.md names CreateProvisionedModelThroughput for a different, not-found/denied-vs-validation ordering, not for the quota classification of a well-formed no-commitment purchase.

Cause 2 of 2: CreateModelInvocationJob accepts a batch-inference submission that the recorded service refuses, returning a jobArn instead of an authorization refusal.
Failing check: bedrock.model-invocation-job-stop-transitions.
AWS: recorded behavior only — in the recorded environment the caller's session is itself a nested (doubly-assumed) role chain, and Bedrock refuses the submission before any job validation with 403 AccessDeniedException whose message is the fixed sentence 'Cross-account pass role is not allowed.' (no variable part), for ANY roleArn passed, including a freshly created same-account role carrying a bedrock.amazonaws.com trust statement and an S3 policy for the input/output bucket. The recording shows the refusal reproducing across a 90s retry loop (so it is not IAM propagation lag) and no model-invocation job existing afterwards: ListModelInvocationJobs(nameContains=<jobName>) returns an empty invocationJobSummaries. Smithy: CreateModelInvocationJob POST /model-invocation-job, success 200, roleArn @required (pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$), modelId @required, inputDataConfig/outputDataConfig @required; AccessDeniedException is modeled with httpError 403.
Emulator: HTTP 200 with a jobArn — no error at all (the check's error-capture helper reports code None, message None) — for the same request shape (valid same-account roleArn from IAM CreateRole/GetRole, modelId arn:aws:bedrock:<region>::foundation-model/amazon.titan-text-express-v1, s3 input/output URIs in a bucket the same run created). The pass-role/authorization gate never runs on this path, so a job is created where the recording has none.
Why: this is the over-permissive direction, the worst kind for a negative-path client: code that expects the submission to be denied (and that asserts no job was created) instead gets a live job id, so cleanup, cost control and 'does this environment allow batch inference at all' probes all take the wrong branch. Anything that treats an accepted CreateModelInvocationJob as proof that the role is passable will then fail later, in a place with no link to the pass-role decision.
Fix: CreateModelInvocationJob's authorization stage in its handler — the pass-role/role-chain gate must be evaluated for every submission and answer 403 AccessDeniedException with AWS's fixed sentence when the calling session cannot pass the role, with no job written to state. Note the ordering requirement already filed in 20261030T063647Z-bedrock-batch-job-creation-runs-its-pass-role.md (that issue says the gate must not run BEFORE model-identifier validation, and must not refuse a role AWS admits); it carries no key for this check and does not cover a submission being accepted outright, so both must hold together: validate the model identifier first, then apply the pass-role gate, which here must deny.
Traces: bedrock.model-invocation-job-stop-transitions — 'expected AccessDeniedException, got None (None)' at the assertion on CreateModelInvocationJob's error code.
