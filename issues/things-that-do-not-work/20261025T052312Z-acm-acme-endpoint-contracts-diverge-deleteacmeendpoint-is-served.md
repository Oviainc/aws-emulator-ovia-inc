# ACM ACME-endpoint contracts diverge: DeleteAcmeEndpoint is served for a principal with no permissions, and UntagResource's ResourceNotFoundException message does not name the resource type (2 causes)

> _Note: this issue was identified against the code base at commit `9736c84da1ff98c2027d891c67e5be6441f006f6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteAcmeEndpoint

## Description
Two distinct net-new root causes in the ACM emulator, both grounded in failing behavioral checks whose positive legs reach the emulator and are served (CreateAcmeEndpoint/DescribeAcmeEndpoint/TagResource/ListTagsForResource all work), so neither is a scaffold stub.

Cause 1 of 2: identity-based authorization is not enforced on DeleteAcmeEndpoint — a session with zero permissions deletes the endpoint.
AWS: Smithy (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) models DeleteAcmeEndpoint(AcmeEndpointArn required, @length 1..200, @pattern ^arn:aws[a-z-]*:acm:[a-z0-9-]+:[0-9]{12}:acme-endpoint/[a-zA-Z0-9-]+$) -> Unit, @idempotent, errors [AccessDeniedException (client, httpError 403, awsQueryError AccessDenied), ConflictException 400, ThrottlingException 400, ValidationException 400, InternalServerException 500]. A role created with no policies attached hits IAM's implicit deny, so the call signed with that assumed-role session is refused with HTTP 403 and Error.Code 'AccessDeniedException'; the endpoint is untouched and still describable with Status ACTIVE, and the caller's own (permitted) credentials can still delete it. The model does not fix the message text; the recording shows the IAM-standard template built from the request's principal, action and resource, e.g. 'User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: acm:DeleteAcmeEndpoint on resource: <endpoint arn> because no identity-based policy allows the acm:DeleteAcmeEndpoint action' — that template is the rule; the concrete arns/role names are environment-dependent examples.
Emulator: the same DeleteAcmeEndpoint call, signed with credentials returned by sts:AssumeRole on a freshly created role carrying no policies, SUCCEEDS — HTTP 200 with an empty JSON body (content-type application/x-amz-json-1.1, content-length 2). No denial is produced; every signed request is served as if it were the account's root principal.
Why: overly permissive. The negative authorization contract is unobservable, so a deployment whose role lacks acm:DeleteAcmeEndpoint passes against the emulator and is denied in production (false green), and the effect is destructive: the endpoint is actually deleted by a principal AWS would have refused. Least-privilege policy work cannot be validated at all.
Fix: the request-authorization layer the ACM handlers are dispatched through (evaluate the signing principal's IAM identity-based policies before dispatch and raise the modeled AccessDeniedException); services/service-com-amazonaws-acm-certificatemanager/src/ops/delete_acme_endpoint.rs only needs to surface the denial, its business logic is correct. NOTE: open issue 20261023T004835Z-acm-serves-calls-from-a-principal-with-no.md records the same missing authorization layer for GetAccountConfiguration/PutAccountConfiguration; it does not carry this check's replay key, and this cause shows the gap is service-wide and has destructive effects, so the fix belongs in the shared layer rather than per-operation.
Traces: acm.delete-acme-endpoint-without-permission-denied.

Cause 2 of 2: UntagResource's ResourceNotFoundException message does not name the resource type parsed from the ARN.
AWS: Smithy models UntagResource(ResourceArn required @length 20..2048 @pattern ^arn:[\w+=/,.@-]+:acm:[\w+=/,.@-]*:[0-9]+:[\w+=,.@-]+(/[\w+=,.@-]+)*$, TagKeys required @length 1..50) -> Unit, errors [ResourceNotFoundException (client, 400), ValidationException (400, awsQueryError ValidationError)]. Against an AcmeEndpoint ARN that has already been deleted the call is refused with HTTP 400 and Error.Code 'ResourceNotFoundException' — the emulator gets the status and code right. The message is built from the request: it names the resource TYPE taken from the ARN's resource segment plus the ARN itself, 'Could not find acme-endpoint <ResourceArn>.' So the rule is: the type token from the ARN, not a generic noun. (Compare the already-fixed 20261022T122353Z-acm-certificate-not-found-message-drops-the-trailing.md, which pinned the same family of not-found message for certificates.)
Emulator: code ResourceNotFoundException (correct) but the message substitutes the literal word 'resource' for the ARN's type token: 'Could not find resource arn:aws:acm:<region>:<account>:acme-endpoint/<id>.' The positive control passes (untagging a live, tagged endpoint removes the tag).
Why: the message is request-derived by a known rule, so the rule is the requirement. A client that parses ACM's not-found envelope to recover which KIND of resource was missing (routing a retry/cleanup differently for a certificate vs an acme-endpoint) cannot distinguish them, and any byte-comparison against ACM's envelope diverges for every non-certificate ARN.
Fix: the ResourceNotFoundException construction in the UntagResource handler's ARN resolution (shared with the other tag-writing operations) in services/service-com-amazonaws-acm-certificatemanager/src/ops/ — interpolate the resource-type token parsed from the ARN instead of the constant 'resource'. Related open issue 20261025T011324Z-acm-error-message-envelopes-diverge-validation-errors-never.md covers other ACM message envelopes (ValidationException value echo, InvalidTagException, tag quota) but not this one.
Traces: acm.untag-resource-on-deleted-acme-resource-rejected.

## Evidence
Cause 1 — acm.delete-acme-endpoint-without-permission-denied [mismatch]: the check creates an ACTIVE AcmeEndpoint, creates an IAM role with NO policies attached, assumes it (RoleSessionName 'sim2real-acme-noperm-session'), builds an ACM client from those temporary credentials and calls delete_acme_endpoint(AcmeEndpointArn=<arn>). AssertionError: "expected the call to be rejected, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'application/x-amz-json-1.1', 'content-length': '2', ...}}}". Expected: HTTP 403, Error.Code 'AccessDeniedException', endpoint still describable with Status ACTIVE, and deletion with the caller's own credentials still succeeding. Smithy: DeleteAcmeEndpoint errors [AccessDeniedException httpError 403 / awsQueryError AccessDenied, ConflictException 400, ThrottlingException 400, ValidationException 400, InternalServerException 500]; the quoted IAM message is an example of the request-derived template, the requirement is the 403 + code.

Cause 2 — acm.untag-resource-on-deleted-acme-resource-rejected [mismatch]: the check creates an ACTIVE AcmeEndpoint, deletes it, polls until DescribeAcmeEndpoint answers ResourceNotFoundException, then calls untag_resource(ResourceArn=<deleted acme-endpoint arn>, TagKeys=['foo']). Code is ResourceNotFoundException (as expected). AssertionError: expected message 'Could not find acme-endpoint arn:aws:acm:us-west-2:000000000000:acme-endpoint/9ab9de00-8816-4d29-a36f-1c1c216e098a.', got 'Could not find resource arn:aws:acm:us-west-2:000000000000:acme-endpoint/9ab9de00-8816-4d29-a36f-1c1c216e098a.' — identical apart from the resource-type token, which the emulator replaces with the constant 'resource'. The positive control (tag then untag a live endpoint, ListTagsForResource no longer shows the key) passes. Smithy: UntagResource errors [ResourceNotFoundException 400, ValidationException 400].
