# stepfunctions: 5 net-new causes — activity-backed Task states never hand out a token (so the task/heartbeat clocks and their Catchers are unreachable), a tolerated-failure Distributed Map never terminates, StartSyncExecution never settles on StateMachineDeleting, a qualified StartExecution scenario never completes, and the 1000-version cap is never enforced

> _Note: this issue was identified against the code base at commit `5598dd881b8e225c34bc5a9814ddc1ff981b448f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetActivityTask

## Description
Five net-new root causes, grounded in seven failing behavioral checks the replay report left unmarked (no ALREADY-FILED marker and no OWNED marker). Every one of the seven is killed by the harness with "Error: Check timed out after 60.0s": the emulator never produces the condition the check polls for, so the check cannot proceed past it. Smithy model used throughout: services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json.

Cause 1 of 5 — a RUNNING execution whose Task state names an activity ARN never enqueues a task, so GetActivityTask hands out no taskToken, and with it the Task-level TimeoutSeconds / HeartbeatSeconds clocks and the Catchers that must match States.Timeout / States.HeartbeatTimeout are unreachable.
Failing check ids: stepfunctions.activity-heartbeat-timeout-catcher-order-decides-winner, stepfunctions.catch-timeout-empty-cause, stepfunctions.jsonata-task-error-two-levels-deep-propagates-through-map-and-parallel.
AWS: Smithy models GetActivityTask with input {activityArn (required, @length 1..256), workerName (@length 1..80)} and output {taskToken (@length 1..2048, @sensitive), input (@length 0..1048576, @sensitive)}; modeled errors ActivityDoesNotExist, ActivityWorkerLimitExceeded, InvalidArn, KmsAccessDeniedException, KmsInvalidStateException, KmsThrottlingException, all HTTP 400. In AWS, as soon as an execution enters a Task whose Resource is an activity ARN the task is enqueued on that activity and the next long-poll returns a non-empty taskToken plus the state input. Recorded behavior for the clocks: if the claiming worker then sends neither SendTaskHeartbeat nor SendTaskSuccess/SendTaskFailure, (a) the Task's HeartbeatSeconds lapse raises an error that matches BOTH a States.HeartbeatTimeout Catcher and a States.Timeout Catcher, and the winner is the FIRST-listed Catcher in the Catch array — never the more specific error name; (b) the Task's TimeoutSeconds lapse raises States.Timeout, and a Catcher on it with a ResultPath writes exactly the two keys Error and Cause at that path, with Error the fixed text "States.Timeout" and Cause present as the empty string "" (not an absent key, not null); (c) a JSONata Task error raised two containers deep (a Map inside a Parallel branch) climbs as EvaluationFailed, MapIterationFailed, TaskStateAborted for the sibling branch's in-flight Task, MapStateFailed, ExecutionFailed, and the cause names the failing Task's own entered-event id.
Emulator: all three checks are killed at the 60 s harness cap inside their first activity claim — the GetActivityTask poll loop never returns a taskToken, the executions never leave RUNNING, and neither the timeout/heartbeat transition nor the Catch result nor the history-event chain is ever produced.
Why: a client implementing the first-class activity-worker pattern (CreateActivity -> Task on the activity ARN -> long-poll GetActivityTask -> SendTaskSuccess/SendTaskFailure) is handed no work and no error explaining why; its executions hang in RUNNING forever. Any workflow that relies on a Task clock lapsing (the standard way to bound a human/worker step) never fails over to its Catcher, so retry and compensation branches are dead code against this emulator.
Fix: the activity task scheduling path shared by the interpreter's Task-state handler and the GetActivityTask handler/state (entering a Task whose Resource is an activity ARN must enqueue a task; GetActivityTask must dequeue it and mint a token carrying the state input), then the Task timer component that lapses HeartbeatSeconds/TimeoutSeconds and the Catch matcher that resolves which Catcher wins by array order and writes Error/Cause at the ResultPath.
Related but NOT covering these checks (the replay report marked none of the three as owned): open issue 20261025T100143Z-cloudwatch-sfn-activity-backed-task-states-never-enqueue.md covers only two cloudwatch__stepfunctions checks.
Traces: stepfunctions.activity-heartbeat-timeout-catcher-order-decides-winner, stepfunctions.catch-timeout-empty-cause, stepfunctions.jsonata-task-error-two-levels-deep-propagates-through-map-and-parallel.

Cause 2 of 5 — a Distributed Map run with ToleratedFailurePercentage never reaches a terminal execution status.
Failing check id: stepfunctions.conc-distributed-map-tolerated-failure-percentage-succeeds-and-names-failed-items.
AWS: recorded behavior only (the Smithy model does not describe Map-run semantics). A DISTRIBUTED Map over N items whose failing fraction is at or below ToleratedFailurePercentage ends the parent execution SUCCEEDED; DescribeMapRun, the child-execution listing and the ResultWriter FAILED manifest each name exactly the items that failed, and every tolerated-failure item produces none of its side effects while every successful item produces exactly one.
Emulator: the check is killed at the 60 s harness cap while polling the parent execution for a terminal status (its own internal budget is 220 s), so no DescribeMapRun, child listing or ResultWriter output is ever read.
Why: a client cannot use Distributed Map at all — the execution never finishes, so partial-failure tolerance, the failed-item manifest and the per-item effects can never be relied on.
Fix: the Distributed Map run driver (item-reader fan-out, child-execution bookkeeping and the tolerated-failure accounting that decides the parent's terminal status) and the ResultWriter/DescribeMapRun projections it feeds.
Traces: stepfunctions.conc-distributed-map-tolerated-failure-percentage-succeeds-and-names-failed-items.

Cause 3 of 5 — StartSyncExecution against a state machine that is being deleted never settles on a stable refusal.
Failing check id: stepfunctions.start-sync-execution-on-deleting-state-machine-rejected.
AWS: Smithy models StartSyncExecution (host prefix "sync-") with StateMachineDeleting among its errors (HTTP 400, error code StateMachineDeleting), alongside StateMachineDoesNotExist, StateMachineTypeNotSupported, InvalidArn, InvalidName, InvalidExecutionInput and the Kms* family. After DeleteStateMachine on an EXPRESS machine, StartSyncExecution is refused; the deletion race may let a call through or answer a different code briefly, but the refusal must become stable (the check only requires three consecutive reads of the same code within 120 s).
Emulator: the check is killed at the 60 s harness cap inside that stable-refusal poll — the emulator never produces three consecutive reads of the expected code, so it neither rejects the call stably nor converges to the post-deletion steady state.
Why: a client that deletes an EXPRESS state machine and keeps invoking it gets no stable, classifiable answer, so it cannot distinguish "still deleting" from "gone" and cannot write a safe teardown sequence.
Fix: DeleteStateMachine's state transition (a DELETING marker that outlives the request) and the StartSyncExecution handler's pre-dispatch lookup, which must map a DELETING state machine to HTTP 400 StateMachineDeleting and a deleted one to StateMachineDoesNotExist.
Traces: stepfunctions.start-sync-execution-on-deleting-state-machine-rejected.

Cause 4 of 5 — the states:StateMachineQualifier condition scenario never completes: a qualifier-scoped caller's calls against version- and alias-qualified ARNs never resolve.
Failing check id: stepfunctions.statemachinequalifier-condition-restricts-qualifier-value-not-its-absence.
AWS: recorded behavior only for the IAM condition semantics. A ForAllValues:StringEquals condition on states:StateMachineQualifier, attached to an identity policy whose Resource is the UNQUALIFIED state-machine ARN, allows StartExecution/DescribeStateMachine for a qualifier in the allowed set, denies one outside it, and — because an unqualified call carries no states:StateMachineQualifier key at all — vacuously ALLOWS the unqualified call. The denial is HTTP 400 AccessDeniedException whose message is the standard template "User: <caller-arn> is not authorized to perform: states:StartExecution on resource: <unqualified state-machine ARN> because no identity-based policy allows the states:StartExecution action" — fixed text apart from the assumed-role ARN of the caller and the unqualified state-machine ARN, which come from the request and the emulator's state; note the resource named is the UNQUALIFIED ARN even though the call carried a qualifier. DescribeStateMachine on a version-qualified ARN must report that qualified ARN back in stateMachineArn.
Emulator: the check is killed at the 60 s harness cap before any of those assertions; it never gets past publishing/aliasing plus the assumed-role caller's first calls, so neither the allowed qualified call, the denied wrong-qualifier call, nor the vacuously-allowed unqualified call is ever answered.
Why: a client cannot validate qualifier-scoped least-privilege policies: a policy that should pin a caller to one alias/version either blocks nothing or blocks everything, and the denial message a caller parses to diagnose it never appears.
Fix: the IAM authorization path for the states actions — population of the states:StateMachineQualifier request-context key from a qualified ARN (and its ABSENCE for an unqualified one), the ForAllValues set-operator evaluation, and the AccessDeniedException message builder that must name the unqualified resource ARN.
Traces: stepfunctions.statemachinequalifier-condition-restricts-qualifier-value-not-its-absence.

Cause 5 of 5 — the 1000-versions-per-state-machine quota is never enforced, so UpdateStateMachine(publish=true) never reaches ServiceQuotaExceededException and a client driving the cap loops without end.
Failing check id: stepfunctions.update-state-machine-publish-at-version-cap-quota-exceeded.
AWS: Smithy models UpdateStateMachine with input {stateMachineArn (required), definition, roleArn, publish (default false), versionDescription (@length 0..256), loggingConfiguration, tracingConfiguration, encryptionConfiguration} and output {updateDate (required), revisionId, stateMachineVersionArn}; ServiceQuotaExceededException is a modeled error with HTTP status 402 (the same error is modeled on PublishStateMachineVersion). Once a state machine holds the documented maximum of 1000 versions, a further publish is refused with error code ServiceQuotaExceededException and creates no new version; the message is AWS's fixed text for that error class with the state-machine ARN and the limit taken from the request and from the service quota, never from one recording.
Emulator: the check publishes versions in a loop that ends only when a ServiceQuotaExceededException arrives (its own loop deadline is 2400 s) and is killed at the 60 s harness cap, with no quota refusal ever observed. Hypothesis: the version counter is unbounded, so the cap is never hit and the refusal is unreachable; a per-publish latency high enough to miss the cap inside the budget would produce the same symptom and the same fix location.
Why: a client that uses version publishing as part of every deploy gets no backpressure and no 402 to handle; emulator-based tests of quota handling pass vacuously, and nothing stops unbounded version accumulation.
Fix: the UpdateStateMachine/PublishStateMachineVersion handler and the state machine's version store — enforce the 1000-version cap before minting a version and return HTTP 402 ServiceQuotaExceededException, leaving the version list unchanged.
Traces: stepfunctions.update-state-machine-publish-at-version-cap-quota-exceeded.

## Evidence
All seven checks: verdict mismatch, detail "Error: Check timed out after 60.0s".

1) stepfunctions.activity-heartbeat-timeout-catcher-order-decides-winner — Expected: StartExecution on a machine whose single Task names the activity ARN with HeartbeatSeconds=5 and TimeoutSeconds=120 and a two-entry Catch; GetActivityTask returns a non-empty taskToken; the worker then sends nothing, the heartbeat clock lapses, and the FIRST-listed Catcher wins — output "heartbeat-timeout-catcher-won" when States.HeartbeatTimeout is listed first and "timeout-catcher-won" when States.Timeout is listed first, with the execution SUCCEEDED both times. Actual: killed at 60 s inside the GetActivityTask poll; no token, execution never terminal.

2) stepfunctions.catch-timeout-empty-cause — Expected: the claimed-then-abandoned activity Task with TimeoutSeconds=5 and a Catch on States.Timeout with ResultPath "$.error-info" lets the execution end SUCCEEDED, and the output at that path is exactly {"Error": "States.Timeout", "Cause": ""} — the Cause key PRESENT and the empty string, and no other keys. Actual: killed at 60 s inside the GetActivityTask poll; the Catch result is never produced.

3) stepfunctions.jsonata-task-error-two-levels-deep-propagates-through-map-and-parallel — Expected: a QueryLanguage=JSONata Task error inside a Map inside a Parallel branch produces the history chain EvaluationFailed -> MapIterationFailed -> TaskStateAborted (sibling branch's in-flight Task) -> MapStateFailed -> ExecutionFailed with error States.QueryEvaluationError, the cause naming the failing Task's own entered-event id. Actual: killed at 60 s; the branch's activity Task is never claimed, so the chain is never emitted.

4) stepfunctions.conc-distributed-map-tolerated-failure-percentage-succeeds-and-names-failed-items — Expected: ToleratedFailurePercentage=10 over 40 items with 2 failing (5%) ends the execution SUCCEEDED; DescribeMapRun, the child listing and the ResultWriter FAILED output each name exactly those 2; the other 38 each write one row and the failed 2 write none. Actual: killed at 60 s while polling for a terminal status (internal budget 220 s); status never left RUNNING.

5) stepfunctions.start-sync-execution-on-deleting-state-machine-rejected — Expected: after DeleteStateMachine on an EXPRESS machine, StartSyncExecution settles on a stable HTTP 400 StateMachineDeleting (three consecutive reads of that code within 120 s). Actual: killed at 60 s inside the stable-refusal poll; the expected code never streaked.

6) stepfunctions.statemachinequalifier-condition-restricts-qualifier-value-not-its-absence — Expected: under ForAllValues:StringEquals on states:StateMachineQualifier with the alias name and the version qualifier allowed, StartExecution on the alias ARN is accepted; StartExecution on "<sm_arn>:<unlisted-qualifier>" is refused HTTP 400 AccessDeniedException with message "User: <assumed-role-arn> is not authorized to perform: states:StartExecution on resource: <sm_arn> because no identity-based policy allows the states:StartExecution action" (the UNQUALIFIED ARN); the unqualified StartExecution is ALLOWED and ends SUCCEEDED; DescribeStateMachine on "<sm_arn>:<version-qualifier>" returns stateMachineArn = the version ARN. Actual: killed at 60 s before any of these outcomes was observed.

7) stepfunctions.update-state-machine-publish-at-version-cap-quota-exceeded — Expected: once the state machine holds 1000 versions, UpdateStateMachine(publish=true) is refused with error code ServiceQuotaExceededException (modeled HTTP 402) and creates no version; the loop therefore terminates. Actual: killed at 60 s with no quota refusal ever returned — the publish loop (own deadline 2400 s) never ends.
