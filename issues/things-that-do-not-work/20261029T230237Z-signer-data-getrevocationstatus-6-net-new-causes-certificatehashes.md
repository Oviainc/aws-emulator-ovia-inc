# signer-data GetRevocationStatus: 6 net-new causes — certificateHashes and signatureTimestamp are never validated, the call is never authorized, and three refusals are misworded

> _Note: this issue was identified against the code base at commit `712591afcbaa8fe04acc2e16b4d0dd73e216350b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRevocationStatus

## Description
Six net-new root causes on ONE operation of ONE service (signer-data / GetRevocationStatus, GET /revocations, served by the signer crate's ops/get_revocation_status.rs). They are independent and ALL SIX must be closed before this issue is submitted. Three of them are over-permissiveness (the emulator answers 200 where AWS refuses), one is an authorization bypass, and two are refusal wording. No open issue covers any of them: the only open issue touching this operation, 20261029T123510Z-signer-getrevocationstatus-error-response.md, is about the platform-not-found refusal echoing an UNBOUNDED platformId and does not touch the wording, the missing validations, or authorization.

Cause 1 of 6: certificateHashes entries are never validated — a hash outside the service's 128..256 hexadecimal-character band is accepted, and the per-request cardinality cap is absent.
AWS: 400 ValidationException (Smithy, signer-data model com.amazonaws.signerdata#GetRevocationStatus: error ValidationException errorKind client httpError 400, members {message, code}; certificateHashes targets CertificateHashes, a list whose member CertificateHash is a bare string with @length 1..2048 and NO pattern, and the list itself carries no @length — so the real rule is recorded behavior only, not modelled). Recorded behavior: an entry must be hexadecimal and between 128 and 256 characters long, and the refusal is worded "Certificate hash <entry> must be hexadecimal and between 128 and 256 bits long". Fixed text: "Certificate hash " … " must be hexadecimal and between 128 and 256 bits long"; the single variable part is the rejected entry, taken verbatim from the request. The rule is applied to EVERY entry, not just the first: a well-formed batch of four followed by a malformed fifth is refused on the fifth. Recorded behavior also caps the list at five entries, refused with the entirely fixed message "certificateHashes must not contain more than 5 hashes" (no request value in it).
Emulator: answers HTTP 200 with {"revokedEntities": []} for a 127-character entry, for a 257-character entry, and for a four-good-plus-one-malformed batch. ops/get_revocation_status.rs inspects certificateHashes exactly once — `if input.certificate_hashes.is_empty()` (lines 207-211) — and then states in its own header comment that "Nothing in AWS Signer revokes a CERTIFICATE" and never reads the entries again, so no entry is ever checked for hexadecimality, for length, and no count ceiling exists.
Why: a client that sends a truncated, non-hex or oversized certificate identifier — the single most likely way to get this parameter wrong, since the hash is built by concatenating two TBS digests — is told the artifact is NOT revoked instead of being told its identifier is malformed. That is a fail-open answer on a revocation check: the caller trusts a signature whose revocation status was never actually evaluated. The absent cardinality cap has the same shape: a 6-entry batch is silently accepted rather than refused, so a caller cannot learn the batch limit.
Fix: GetRevocationStatus' input validation in the signer crate (ops/get_revocation_status.rs, alongside the existing platformId and empty-list gates, before any state is read) — validate each certificateHashes entry for the hex character class and the 128..256 length band in the model's member order and refuse the FIRST offending entry with the message above, and refuse a list of more than five entries. The per-entry predicate and the two message templates belong next to the other shared refusal wording in src/state.rs so one rule words all of them.
Traces: signer-data.certificate-hash-entry-too-short-rejected, signer-data.certificate-hash-length-boundaries-accepted, signer-data.multiple-certificate-hashes-batch.

Cause 2 of 6: a signatureTimestamp in the future is accepted instead of refused.
AWS: 400 ValidationException (Smithy: signatureTimestamp targets Timestamp, @httpQuery "signatureTimestamp", @required; errors include ValidationException httpError 400). Recorded behavior: signatureTimestamp names when an artifact was actually signed, so a timestamp later than the service's present time is refused with "Invalid signatureTimestamp: <timestamp> must be earlier than present time". Fixed text: "Invalid signatureTimestamp: " … " must be earlier than present time"; the variable part is the rejected timestamp from the request, rendered as ISO-8601 UTC with a trailing Z and second precision (the recording's 2066-01-02T03:04:05Z is one value filling that template, not part of it). A timestamp decades in the PAST is accepted — signatures do not expire from this API's perspective — so the rule is one-sided.
Emulator: answers 200 with {"revokedEntities": []} for a timestamp decades in the future. ops/get_revocation_status.rs only ever passes input.signature_timestamp into version_revoked_at as a comparison operand (line 274); it is never bounded against the present.
Why: the timestamp is the input that decides the answer (a profile revocation covers only signatures made at or after its effectiveTime), so a caller that computes or parses it wrongly and lands in the future gets a confident "not revoked" for a signature that cannot exist, instead of the refusal that would surface the bug.
Fix: GetRevocationStatus' input validation in the signer crate — reject a signatureTimestamp after the service's current time, with the message template above, before any revocation record is consulted.
Traces: signer-data.signature-timestamp-future-rejected.

Cause 3 of 6: the unregistered-platformId refusal is worded as a missing resource instead of as an invalid input.
AWS: 400 ValidationException with message "Invalid platformId: <platformId>". Fixed text: "Invalid platformId: "; the variable part is the request's platformId query value. The refusal fires for an id that satisfies the published character class (Smithy, signerdata model: PlatformId @pattern ^[a-zA-Z0-9_-]+$) but names no registered signing platform, so the check is against the platform catalog and the ANSWER is still an invalid-input refusal, not a not-found one. A registered id (e.g. Notation-OCI-SHA384-ECDSA) on an otherwise identical request succeeds.
Emulator: right status and error class, but message "Platform with id MyMadeUpPlatform-123_x does not exist" — crate::state::platform_not_found_message (src/state.rs:1498-1500), reached from ops/get_revocation_status.rs:217-221. That is the wording AWS uses for GetSigningPlatform's 404, reused here for a 400.
Why: the message text is part of the error contract; a wording-sensitive client or test never matches, and the "does not exist" phrasing tells the caller a resource is missing when AWS is telling it the request value is invalid, so it retries the same call expecting the platform to appear.
Fix: the platform-catalog gate in ops/get_revocation_status.rs must compose this operation's own ValidationException text rather than calling the shared not-found prose; keep crate::state::platform_not_found_message for the operations whose refusal AWS really does word that way. (Note: open issue 20261029T123510Z-signer-getrevocationstatus-error-response.md asks that the echoed platformId on this same path be bounded the way the sibling pattern refusal bounds it — that bound applies to the variable part of the NEW template too.)
Traces: signer-data.unknown-platform-id-rejected.

Cause 4 of 6: the malformed-profileVersionArn refusal is worded by the emulator instead of by the service.
AWS: 400 ValidationException with message "Invalid profileVersionArn: <value>". Fixed text: "Invalid profileVersionArn: "; the variable part is the request's profileVersionArn query value, echoed as supplied. The refusal is about ARN SHAPE, not length: a non-ARN string inside the modelled band (Smithy: profileVersionArn targets Arn, @length 20..2048) is refused, while a syntactically valid but non-existent profile version ARN of the same length succeeds with an empty revokedEntities list.
Emulator: right status and class, message "<value> is not a valid signing profile version ARN" — ops/get_revocation_status.rs:229-234, `format!("{} is not a valid signing profile version ARN", input.profile_version_arn)`: emulator-authored prose that opens with the caller's bytes instead of the service's "Invalid <member>: " opener.
Why: same contract break as cause 3 — the wording is the part of a 400 a client branches or asserts on, and the member name is not stated in the form AWS states it, so a caller cannot key the refusal to the member it must fix.
Fix: the ARN-shape gate in ops/get_revocation_status.rs — emit "Invalid profileVersionArn: <value>". The sibling jobArn gate at lines 235-240 is written the same way ("<value> is not a valid signing job ARN") and should be corrected to the same "Invalid <member>: <value>" template at the same time; only the profileVersionArn half is witnessed by a failing check.
Traces: signer-data.profile-version-arn-format-rejected.

Cause 5 of 6: the over-length jobArn refusal does not reproduce AWS's constraint sentence.
AWS: 400 ValidationException for a jobArn one character past the modelled maximum (Smithy: jobArn targets Arn, @length min 20 max 2048, @httpQuery "jobArn", @required), worded with the service's standard constraint sentence "1 validation error detected: Value '<the rejected jobArn>' at 'jobArn' failed to satisfy constraint: Member must have length less than or equal to 2048". Fixed text: "1 validation error detected: Value '" … "' at 'jobArn' failed to satisfy constraint: Member must have length less than or equal to 2048"; the variable parts are the rejected value, echoed whole, the wire member name, and the modelled maximum. A jobArn at exactly 2048 characters is accepted and answers a revokedEntities list.
Emulator: refuses with the right status and the right error code (ValidationException) — the check's code assertion passes — but the message differs from that sentence. The emulator keeps the framework's own constraint rendering for every length violation (src/service.rs override_refusal rewords ONE class only, the query-bound-list "supplied nothing" case, and its own test every_other_refusal_keeps_the_framework_wording pins that a jobArn length violation falls through to the framework), so the divergence is in that shared rendering rather than in the handler. The replay report truncated the emulator's actual message past the 2049-character echo, so the exact differing bytes around the echo are not quoted here; re-replaying the named check prints both sides in full.
Why: the message of a 400 is a requirement, and this is the only signal a caller gets that it exceeded a length bound; a client or test matching AWS's constraint sentence does not match.
Fix: the shared framework constraint-violation rendering that this service lets answer for length violations (src/service.rs's override_refusal seam and the violation-to-message renderer it defers to) must produce AWS's sentence for a MaxLength violation on a string member, including the "1 validation error detected: " opener and the whole echoed value.
Traces: signer-data.job-arn-too-long-rejected.

Cause 6 of 6: GetRevocationStatus is never authorized — an identity carrying an explicit Deny on signer:GetRevocationStatus is served a 200, and the modelled AccessDeniedException is unreachable.
AWS: 403 AccessDeniedException (Smithy: GetRevocationStatus errors include AccessDeniedException, errorKind client, httpError 403, members {message, code}) with message "User: arn:aws:sts::<accountId>:assumed-role/<roleName>/<sessionName> is not authorized to perform: signer:GetRevocationStatus on resource: <the signing-profile ARN the request's profileVersionArn names, with its version segment dropped> with an explicit deny in an identity-based policy". Fixed text: "User: " … " is not authorized to perform: signer:GetRevocationStatus on resource: " … " with an explicit deny in an identity-based policy"; variable parts: the caller's assumed-role session ARN, and the profile ARN derived from the request's profileVersionArn. The same request made with an unrestricted identity succeeds, so the refusal is driven by the identity's policy and nothing else.
Emulator: the call succeeds for the denied session exactly as it does for the unrestricted one. ops/get_revocation_status.rs reads only the request region from ctx and never consults the caller's identity or any policy, so AccessDeniedException is declared in GetRevocationStatusErrorModeled (lines 123-128) and never constructed. The check polls for the denial for up to 90s and is consumed by its 60s budget ("Check timed out after 60.0s") because the denial never arrives.
Why: a revocation check is a security decision, and here it is answered for a principal AWS refuses outright. Any client or test that relies on an explicit Deny to fence this data-plane read off — and any negative-path test that asserts the 403 — sees the call succeed, so a least-privilege configuration is validated by the emulator and rejected by AWS.
Fix: an authorization gate for this operation in the signer crate (ahead of the handler body, where the request's credential scope is already resolved), evaluating the caller's identity-based policy for signer:GetRevocationStatus on the profile ARN and answering the modelled AccessDeniedException with the message template above; the role, its inline Deny and the assumed-role session are all created through the already-bootstrapped iam and sts services in the same run, so the policy to evaluate is present in state.
Traces: signer-data.access-denied-rejected.
