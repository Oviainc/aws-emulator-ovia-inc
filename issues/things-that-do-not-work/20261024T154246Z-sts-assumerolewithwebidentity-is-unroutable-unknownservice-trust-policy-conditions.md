# STS: AssumeRoleWithWebIdentity is unroutable (UnknownService), trust-policy Conditions are never evaluated, session identity is a constant, and two refusal messages diverge (6 causes)

> _Note: this issue was identified against the code base at commit `d0704f2fe7a69fbeda61cd50377e188330130aec`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRole

## Description
This issue bundles SIX distinct net-new root causes in the STS service (service token `sts`). A fixer must close all six before submitting; each cause names its own failing check ids. None of these six is covered by the open issues 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md or 20261024T065715Z-sts-sessions-carry-no-policy-scoping-packedpolicysize-oversized.md, which are named below where they are adjacent.

Cause 1 of 6: AssumeRoleWithWebIdentity cannot be dispatched at all, because the request router only resolves a target service from a SigV4 credential scope, an X-Amz-Target header or the Host header.
AWS: Smithy: AssumeRoleWithWebIdentity carries `auth: []` with `optionalAuth: true` — it is an ANONYMOUS operation, so a conforming client sends it unsigned (no Authorization header, hence no SigV4 credential scope), and the awsQuery protocol sends no X-Amz-Target. Its modeled errors are InvalidIdentityTokenException (awsQueryError code InvalidIdentityToken, HTTP 400), ExpiredTokenException (ExpiredTokenException, 400), IDPRejectedClaimException (IDPRejectedClaim, 403), IDPCommunicationErrorException (IDPCommunicationError, 400), MalformedPolicyDocumentException (MalformedPolicyDocument, 400), PackedPolicyTooLargeException (PackedPolicyTooLarge, 400), RegionDisabledException (RegionDisabledException, 403). Every one of those is serialized as an awsQuery XML ErrorResponse.
Emulator: the unsigned call is answered with a JSON body `{"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}`, which is not even the right protocol: botocore fails before it can read an error, raising `botocore.parsers.ResponseParserError: Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received`.
Why: the whole web-identity federation surface is unreachable. A client gets a parser crash instead of a modeled error, so it cannot distinguish an expired token, a forged token and a non-JWT token, and no OIDC/web-identity flow can be exercised against the emulator. This is the same routing defect already filed for Cognito Identity (20261024T065715Z-cloudtrail-cognito-identity-sts-unsigned-cognito-identity-requests-are-answered-unknownservice-so.md), here on STS's own anonymous operation.
Why it is the emulator's: the request reaches the emulator and the emulator answers; it simply refuses to attribute an unsigned request to STS.
Fix: the request-routing/service-resolution layer must resolve an anonymous awsQuery request to STS (e.g. from the Action parameter and the endpoint/Host it is reached on) and then the AssumeRoleWithWebIdentity handler must classify the token (not-a-JWT / expired / unsigned-or-forged) into InvalidIdentityToken (400) and ExpiredTokenException (400) and serialize them as awsQuery XML.
Traces: sts.assume-role-with-web-identity-invalid-token-format-rejected, sts.assume-role-with-web-identity-expired-token-rejected, sts.assume-role-with-web-identity-forged-token-rejected.

Cause 2 of 6: AssumeRole never evaluates the Condition element of a role's trust policy, and never observes a trust document that was tightened after the role was created, so a principal the trust policy gates out keeps receiving credentials and AccessDenied is never reached.
AWS: a role's trust policy is the assumption-time gate. A statement whose Condition is not satisfied by the caller does not authorize the assume, and the call is refused with the service-common client error AccessDenied, HTTP 403 (the Smithy model lists only ExpiredTokenException / MalformedPolicyDocumentException / PackedPolicyTooLargeException / RegionDisabledException for AssumeRole, so the denial is the common AccessDenied — recorded behavior for the condition keys exercised here: aws:MultiFactorAuthPresent, aws:PrincipalArn and sts:RoleSessionName). AWS serves a cached ALLOW for a (role, principal) pair for roughly 300s after UpdateAssumeRolePolicy tightens the document, and then refuses with exactly AccessDenied; tightening the document does NOT invalidate sessions already vended, which keep working until their own Expiration.
Emulator: the gate is simply absent. The concurrency check proves it directly: against a role whose only Allow is gated by a Condition the ambient caller does not satisfy, AssumeRole returned success — `AssertionError: ambient caller unexpectedly assumed the gated-only role: {'success': True, 'error_code': None}`. The four polling checks corroborate it: each tightens a trust policy and then polls for the eventual AccessDenied (their own budgets are 600s, far above the suite's 60s cap), and each spends its whole budget without ever seeing a refusal — `Error: Check timed out after 60.0s`. A faithful emulator need not reproduce AWS's ~300s decision cache; enforcing immediately would make the first poll return and the checks complete well inside the cap, so a budget-long run of uninterrupted ALLOWs is the emulator never denying, not the cap being short.
Why: this is an overly-permissive authorization hole. Every least-privilege trust-policy design validated against the emulator — MFA-required assume, assume restricted to one principal ARN, assume restricted to one session name — is unenforced, and a developer is told their role boundary works when in AWS it does not. Negative tests of a trust policy pass here and fail against AWS. It is adjacent to but distinct from cause 1 of 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md (which covers role existence, cross-account and sts:ExternalId): this is the general Condition-element evaluation and the re-read of an updated trust document.
Fix: the AssumeRole handler's authorization step — evaluate the resolved role's trust-policy statements including their Condition block against the request context (MFA present, caller principal ARN, requested RoleSessionName), read the CURRENT stored AssumeRolePolicyDocument on every assume rather than a value captured at role creation, and emit AccessDenied / HTTP 403 when no statement authorizes the caller. Already-vended sessions must remain valid.
Traces: sts.concurrent-role-trust-policy-update-and-assume-role-race-consistent, sts.assume-role-trust-policy-mfa-condition-refuses-non-mfa-assume, sts.assume-role-trust-policy-principal-arn-condition-enforced, sts.assume-role-trust-policy-session-name-condition-enforced, sts.tightening-the-trust-policy-does-not-invalidate-an-already-vended-session.

Cause 3 of 6: credentials minted by GetSessionToken from an IAM user's own access key do not carry that user's identity — they resolve to one fixed placeholder principal.
AWS: GetSessionToken returns temporary credentials for the IAM user whose long-term access key signed the call; GetCallerIdentity under those credentials reports that user (Arn `arn:aws:iam::<account>:user/<that user>`). Deleting the access key that minted the session does not change whose identity the already-issued session carries.
Emulator: GetCallerIdentity under those session credentials answers `arn:aws:iam::000000000000:user/emulator` instead of the user under test — `AssertionError: expected session-token credentials minted before key deletion to still resolve to user/<created user>, got 'arn:aws:iam::000000000000:user/emulator'`.
Why: every per-principal assertion is wrong and two different IAM users are indistinguishable, so nothing keyed on the caller (policy conditions, audit joins, multi-tenant isolation tests) can be exercised. This is the same underlying defect as cause 9 of the open issue 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md, which the suite did not mark as owning this check; it is recorded here so it is replayed, and a fixer should close the two together.
Fix: the GetSessionToken handler must bind the minted session to the signing IAM user in STS/IAM state, and the GetCallerIdentity handler must resolve the identity from the presented credential instead of returning a constant.
Traces: sts.e2e-access-key-lifecycle-independent-of-session-token-validity.

Cause 4 of 6: the SignatureDoesNotMatch refusal does not carry the message AWS builds for a signature mismatch.
AWS: a real access key id paired with the wrong secret is refused with error code SignatureDoesNotMatch and the fixed, AWS-documented SigV4 message "The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method. Consult the service documentation for details." The message is a constant produced by the signing layer for this condition, so it is a requirement rather than an example.
Emulator: the code is correct (SignatureDoesNotMatch) but the message is "The request signature does not match".
Why: the message is the only part of this refusal that tells an operator WHICH half of the credential pair is wrong; tooling and docs that match on the documented text do not recognise the emulator's refusal.
Fix: the request authentication layer's signature-mismatch error construction.
Traces: sts.get-caller-identity-rejects-wrong-secret-key.

Cause 5 of 6: the PackedPolicyTooLarge refusal reports a percentage instead of the measured token size and the byte limit.
AWS: Smithy: AssumeRole error PackedPolicyTooLargeException, awsQueryError code PackedPolicyTooLarge, HTTP 400. The message is built from the request and names the constraint it violated: the serialized token's size in bytes and the maximum allowed size in bytes (recorded form: "Serialized token too large for session. Token size of <N> bytes exceeds the maximum allowed limit of 4096 bytes."; the 4096 ceiling is also the modeled @range max of MinimumSessionTokenSize). Because the rule — measured byte size versus the 4096-byte limit — is what produces the text, that rule is the requirement; the particular N is not.
Emulator: the code is correct but the message is phrased as a percentage with no byte figures and no limit: "Serialized token too large for session: the session policies and session tags pack to 928 percent of the allowed size".
Why: a caller trimming session tags or session policy to fit has no way to compute how much to remove, because neither the actual size nor the limit is reported.
Fix: the AssumeRole handler's packed-size validation must report the computed token size in bytes and the 4096-byte limit in the PackedPolicyTooLarge message.
Traces: sts.e2e-assume-role-oversized-session-policy-rejected.

Cause 6 of 6: SourceIdentity set on AssumeRole is not observable on the resulting session's own later activity, so the check cannot complete within its budget.
AWS: Smithy: AssumeRoleRequest.SourceIdentity and AssumeRoleResponse.SourceIdentity (target sourceIdentityType, @length 2..64, @pattern ^[\w+=,.@-]*$). SourceIdentity is recorded server-side against the session, and an independent later call made with that session's credentials reports it on its own audit record under userIdentity.sessionContext.sourceIdentity (recorded behavior).
Emulator: the check never reaches an assertion — `Error: Check timed out after 60.0s`. It first polls up to 120s for the SourceIdentity-carrying AssumeRole to succeed and then polls up to 255s for the session's own GetCallerIdentity audit record, so the budget is consumed by one of those two emulator-served polls never converging: either AssumeRole with SourceIdentity against a trust policy allowing sts:SetSourceIdentity never succeeds, or the session's subsequent activity is never retrievable with the session identity attached. Hypothesis: the second, since cause 6 of 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md records that the AssumeRole response omits SourceIdentity entirely, so nothing is persisted to surface later.
Why: SourceIdentity exists precisely so that an identity a session cannot alter is attributable on everything the session subsequently does; with it unpersisted, that audit guarantee cannot be relied on and any flow built on it is untestable.
Fix: the AssumeRole handler must persist SourceIdentity on the issued session (and echo it in the response), and the identity the audit path records for a call must carry the session's sourceIdentity in its session context.
Traces: sts.assume-role-source-identity-echoed.
