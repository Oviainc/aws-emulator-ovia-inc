# route53-recovery-control-config safety-rule error paths answer the wrong refusal class: no front-door 401 authorization gate and no ARN-format validation

> _Note: this issue was identified against the code base at commit `f5df567e1e8a9531fafde50d7cd95a16d29857a0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSafetyRule

## Description
Two net-new causes, both on Route 53 Application Recovery Controller recovery-control-config SAFETY RULE error paths. In each one the emulator does refuse the request, but it refuses it as the wrong class of error, with the wrong HTTP status and the wrong message, because a gate AWS applies BEFORE the handler's own input checks does not exist in the emulator: the front-door authorization gate (cause 1) and the ARN-format gate on a caller-supplied resource ARN (cause 2). A client therefore reads an auth failure as a malformed-body failure, and a malformed ARN as a missing resource.

Cause 1 of 2: CreateSafetyRule applies no front-door authorization gate, so a request AWS refuses with HTTP 401 / UnauthorizedException is instead run through the handler's exactly-one-of body check and refused with HTTP 400 / ValidationException. (fixture route53-recovery-control-config-validation-error-paths, step task#4)

AWS: recorded behavior only for this refusal — the Smithy model cannot express it. Smithy: CreateSafetyRule is POST /safetyrule (restJson1, sigv4 name route53-recovery-control-config) and declares exactly two errors, ValidationException (client, httpError 400) and InternalServerException (server, 500); the service model contains NO UnauthorizedException shape at all (nearest modeled shapes are AccessDeniedException httpError 403 and ValidationException httpError 400). The recording shows the request refused at the service's front door, ahead of any operation-level input validation, with HTTP 401, response header x-amzn-errortype: UnauthorizedException and a body whose message member is the single word 'Unauthorized'. That message is entirely FIXED text: no part of it is taken from the request or from service state — no rule name, no control-panel ARN, no member name, no principal and no request id appear in it. Because the status/error type sit outside the operation's modeled error set, this is a refusal the request pipeline must produce, not a modeled operation error. Hypothesis: the recorded request is one the API-Gateway-fronted recovery-control-config endpoint declines to authorize, so AWS never reaches CreateSafetyRule's body validation at all; the recording states only the 401/UnauthorizedException/'Unauthorized' triple, not the reason it was declined.

Emulator: the request is admitted past authorization unconditionally and evaluated by the handler's body check, which answers HTTP 400 with x-amzn-errortype: ValidationException and message 'Invalid Rule provided.' — the exactly-one-of refusal for a CreateSafetyRule request carrying both AssertionRule and GatingRule or neither. Replay reports: status: expected 401, got 400; $.message: expected 'Unauthorized', got 'Invalid Rule provided.'; $headers.x-amzn-errortype: expected 'UnauthorizedException', got 'ValidationException'. There is no authorization decision anywhere on this path: the only authorization check this service owns is state::authorize_resource_arn, which (a) is a per-ARN cross-account ownership check that yields AccessDeniedException/403 rather than the front door's UnauthorizedException/401, and (b) is not consulted by CreateSafetyRule before its exactly-one-of match.

Why: a client cannot tell a request it is not authorized to make from a request it built wrongly. Botocore maps HTTP 401 with x-amzn-errortype UnauthorizedException to an auth failure, which is what drives credential refresh, role re-assumption and the operator-facing 'not authorized' report; handlers that branch on that never fire, while a 400 ValidationException tells the caller its request body is malformed and that retrying with the same credentials is pointless. Worse, the absence of the gate is not confined to this refusal: every other operation of the service likewise admits requests the real endpoint declines, so any authorization-dependent flow a client tests against the emulator passes and then fails against AWS.

Fix: the service's request pipeline — the authorization stage of the centralized request walk that runs ahead of each operation's handle(), for the service mounted from services/service-com-amazonaws-route53recoverycontrolconfig-route53recoverycontrolconfig. It must decline the request before deserialized input reaches CreateSafetyRule's exactly-one-of match, emitting HTTP 401 with header x-amzn-errortype: UnauthorizedException and body member message set to the fixed string 'Unauthorized'. This is not a change to the exactly-one-of rule itself, which is correct and must keep answering 400 ValidationException 'Invalid Rule provided.' for an authorized request carrying both rules or neither.

Cause 2 of 2: DescribeSafetyRule performs no ARN-format validation on SafetyRuleArn, so a value that is not a well-formed ARN falls through to the store lookup and is refused as a missing resource (404 ResourceNotFoundException) instead of as a malformed input (400 ValidationException). (fixture route53-recovery-control-config-validation-error-paths, step task#5)

AWS: Smithy: DescribeSafetyRule is GET /safetyrule/{SafetyRuleArn} with SafetyRuleArn bound as a required @httpLabel of type __string, and declares both ValidationException (client, httpError 400 — documented '400 response - Multiple causes. For example, you might have a malformed query string and input parameter might be out of range, or you might have used parameters together incorrectly.') and ResourceNotFoundException (client, httpError 404 — documented '404 response - MalformedQueryString. The query string contains a syntax error or resource not found.'). The model puts no pattern on the label, so the ordering is recorded behavior only: the recording shows a SafetyRuleArn that is not a syntactically valid ARN refused with HTTP 400, x-amzn-errortype: ValidationException and message 'ARN format is invalid: <value>.' — the fixed text is 'ARN format is invalid: ' followed by the offending ARN value echoed from the request's path label, closed by a full stop. The only variable part is that echoed value; the 404 class is reserved for a WELL-FORMED ARN that addresses no stored safety rule. (The recorded instance echoed the value the step sent, which is just what filled that slot.)

Emulator: the handler skips straight to the store, so an unparseable ARN is reported as an absent resource: HTTP 404 with x-amzn-errortype: ResourceNotFoundException and message 'No record corresponding to safety rule Arn(<value>)' (state::not_found_message with SAFETY_RULE_NOUN). Replay reports: status: expected 400, got 404; $.message: expected 'ARN format is invalid: not a valid arn!!.', got 'No record corresponding to safety rule Arn(not a valid arn!!)'; $headers.x-amzn-errortype: expected 'ValidationException', got 'ResourceNotFoundException'. This is deliberate in the current design: state::authorize_resource_arn documents that a value no account can be read out of — one that is not a well-formed ARN — is returned Ok and 'left to the lookup the handler goes on to do, which is what refuses them', and DescribeSafetyRule's handle() does exactly one safety_rules.get() on the raw label with the 404 as its only refusal.

Why: the two classes mean opposite things to a caller. 400 ValidationException is permanent and caller-fixable (the identifier it built is syntactically wrong); 404 ResourceNotFoundException is a statement about the account's state, and is routinely treated as 'not created yet' — so poll-until-present loops, waiters and reconcilers retry a request that can never succeed until they time out, and bug reports blame a missing safety rule rather than the malformed ARN the client actually sent. It also leaks the wrong contract to clients that validate identifiers by probing, and it makes the emulator unable to distinguish a garbled ARN from a deleted rule.

Fix: the operation's validation, in the DescribeSafetyRule handler — services/service-com-amazonaws-route53recoverycontrolconfig-route53recoverycontrolconfig/src/ops/describe_safety_rule.rs (handle(), which currently goes straight to guard.safety_rules.get(&input.safety_rule_arn) around lines 153-164). Parse the supplied SafetyRuleArn first and, when it is not a well-formed ARN, refuse with ValidationException/400 and the message 'ARN format is invalid: ' + the supplied value + '.', reserving ResourceNotFoundException/404 and state::not_found_message for a well-formed ARN that holds no rule. The same ordering belongs in the shared ARN gate (state::authorize_resource_arn / state.rs, whose doc comment currently delegates unparseable values to the lookup) so sibling operations taking a caller-supplied ARN agree.

Related but not covering either cause: the open issue 20261029T194945Z-route53-recovery-control-config-createsafetyrule-does-not-enforce-the-exactly-one-of.md is a behavioral finding about the exactly-one-of rule itself (it carries only the check id route53-recovery-control-config.create-safety-rule-both-rule-types-rejected, and the emulator now answers that path with 400 'Invalid Rule provided.'); it carries neither wire replay key here and gates neither the missing 401 front-door gate nor the missing ARN-format gate. The five open 'unimplemented scaffold stub' issues for this service cover GetResourcePolicy, ListAssociatedRoute53HealthChecks, TagResource, UpdateControlPanel and UpdateRoutingControl, none of which is CreateSafetyRule or DescribeSafetyRule.

Traces: route53-recovery-control-config-validation-error-paths#task#4 (cause 1, CreateSafetyRule), route53-recovery-control-config-validation-error-paths#task#5 (cause 2, DescribeSafetyRule).
