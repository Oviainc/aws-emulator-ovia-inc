# CloudTrail event history is empty for everything but CloudTrail's own writes: no other service records management events, trails deliver no S3 log files, and there is no EventBridge fan-out

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
THREE distinct causes in this issue; all 3 must be closed before submitting. They are the three delivery paths CloudTrail has for a served API call, and none of them carries anything today.

Cause 1 of 3 - LookupEvents returns no record for any call except CloudTrail's own mutating operations.
AWS: every management call of every service is recorded in the Region's event history and readable through LookupEvents (Smithy: LookupEvents, input LookupAttributes/StartTime/EndTime/EventCategory/MaxResults, output Events with CloudTrailEvent; the model's own doc for the operation lists the supported lookup attributes - Event ID, Event name, Event source, Read only, Resource name, Resource type, User name, access key). Read-only calls are recorded too, with readOnly 'true', and FAILED calls are recorded with errorCode/errorMessage. The per-record field semantics each of these checks grades (redaction literals, errorCode carrying the fault-shape name rather than the wire code, requestParameters/responseElements content, requestID equal to the caller's own request id) are recorded behavior measured by the checks against real AWS.
Emulator: event history is empty for these calls. LookupEvents itself is implemented and reads the shared log (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/lookup_events.rs reads service_common::management_events via crate::state::management_event_log), but that log is only ever written by CloudTrail's own mutating handlers - state.rs documents record_management_event as 'reached from each mutating handler'. So no dynamodb, s3, iam, lambda, elbv2, cloudformation, codepipeline, cognito-idp or read-only CloudTrail call is ever recorded. Each of these checks issues its calls and then polls LookupEvents under its own budget (255-1200 s) and never sees a single matching record, so it is still polling when the harness's 60 s cap kills it ('Check timed out after 60.0s') and never reaches its field assertions. Note: the two cloudtrail__cloudformation checks also wait on stack transitions before their poll, so their timeout may be in that earlier wait (Hypothesis) - the LookupEvents gap is certain for the other fourteen, which poll only after their subject calls have returned.
Why: the emulator cannot answer 'who did this'. Every detective control a client builds on event history - incident reconstruction, compliance evidence, redaction proofs that a secret was never persisted, reconciliation of failed calls - reads an empty trail and silently passes; a client cannot distinguish 'nothing happened' from 'nothing is recorded'.
Fix: the shared management-event recording seam (service_common::management_events, the one CloudTrail's state.rs::record_management_event already uses) must be driven from every service's served operations, not just CloudTrail's mutating ones, and for read-only and failed calls as well, populating eventSource/eventName/readOnly/requestParameters/responseElements/errorCode/requestID and the sensitive-member redaction.

Cause 2 of 3 - a logging trail never delivers a log file to its S3 bucket.
AWS: recorded behavior only (measured by the check against real AWS): after StartLogging on a trail whose bucket carries the CloudTrail policy, CloudTrail writes gzipped log files under the documented key layout AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/, each object being a gzip stream whose JSON holds the account's records.
Emulator: no object ever appears in the trail's bucket. The check drives logging and then lists the bucket until the harness cap ends it ('Check timed out after 60.0s'); the check carries the suite's DATAPLANE_UNIMPLEMENTED marker for exactly this case.
Why: the S3 delivery path is the one most audit pipelines actually consume (Athena/Glue over the log prefix, digest validation, SIEM ingestion). A client that reads logs from the bucket rather than through LookupEvents sees a permanently empty prefix, and log-file validation cannot be exercised at all.
Fix: trail log-file delivery - the trail's logging state must write the account's recorded events as gzipped objects into the configured S3 bucket under the documented key layout (and the digest objects when LogFileValidationEnabled is set).
Traces: cloudtrail.trail-delivers-a-gzipped-log-file-to-the-documented-s3-key-layout.

Cause 3 of 3 - no CloudTrail-sourced events reach EventBridge, so the 'AWS API Call via CloudTrail' fan-out delivers nothing.
AWS: recorded behavior only (the CloudTrail integration these checks name and measure): while a trail is logging management events, each served call is also published to the default EventBridge bus as detail-type 'AWS API Call via CloudTrail' with source 'aws.<service>' and detail.eventSource/detail.eventName carrying the record, so a rule matching {"source":["aws.dynamodb"],"detail-type":["AWS API Call via CloudTrail"],"detail":{"eventName":["CreateTable"]}} delivers to its target; IAM's events are published in us-east-1 only.
Emulator: nothing is ever delivered. Each check first proves the channel live with an unrelated control write (sqs:TagQueue through its own rule and sink) and long-polls its SQS sink; no envelope arrives, so the check is still draining the queue when the harness cap ends it ('Check timed out after 60.0s'). All three carry the DATAPLANE_UNIMPLEMENTED marker.
Why: this hop is the ONLY path from a control-plane call of a service with no native EventBridge source (DynamoDB, IAM, Cognito) to an event-driven consumer. Every rule, near-miss pattern and target wired to API-call events is dead, and an application whose automation is triggered by a control-plane change never fires.
Fix: the management-event recording seam from Cause 1 must also publish each recorded call onto the EventBridge default bus as 'AWS API Call via CloudTrail' (source aws.<service>, the record under detail, IAM in the partition leader Region) while a trail is logging, so EventBridge rule matching and target delivery can run.
