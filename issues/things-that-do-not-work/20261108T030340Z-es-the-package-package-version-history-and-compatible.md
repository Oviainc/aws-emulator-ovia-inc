# es: the package, package-version-history and compatible-version catalogs are synthetic

> _Note: this issue was identified against the code base at commit `09ea2d6b5347c41b77d17c7337847f8c3ab13f71`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribePackages

## Description
3 net-new root causes on the es (Elasticsearch Service, 2015-01-01) service token, sharing one fault: the static reference catalogs this service reads out of are emulator-invented placeholder data rather than the catalogs AWS publishes, so every read over them answers content AWS does not serve — and for one of them, refuses the read outright. The Smithy model constrains only the shapes of these responses, not their contents, so the AWS side of each cause is recorded behavior only except where stated. This is the es-side counterpart of the already-open opensearch issue 20261029T190009Z-opensearch-the-package-offering-version-and-instance-type (same fault, different service token, so it does not cover these), and it is distinct from the open refusal-wording issue 20261029T190009Z-es-package-vpc-endpoint-tagging-and-reserved-instance, which is about message text on es package refusals and not about catalog contents.

Cause 1 of 3 — DescribePackages serves an invented package catalog. AWS: 200 with PackageDetailsList holding the AWS-published package catalog (92 entries in the recording), each entry carrying PackageID (a pkg-<hex> id), PackageName, PackageType (e.g. ZIP-PLUGIN), PackageDescription, PackageStatus (AVAILABLE), AvailablePackageVersion, ErrorDetails and distinct CreatedAt / LastUpdatedAt timestamps per package and per version. Smithy: DescribePackages -> DescribePackagesResponse.PackageDetailsList (PackageDetailsList), http POST /2015-01-01/packages/describe, code 200. Emulator: 200 but with a small, hardcoded, locally generated catalog — entries such as analysis-kuromoji and analysis-phonetic under emulator-generated PackageIDs, every entry stamped with the same fixed CreatedAt and LastUpdatedAt and with no ErrorDetails member at all — and none of AWS's catalog entries. Trace: es-catalog-describe-packages#task#1.

Cause 2 of 3 — GetCompatibleElasticsearchVersions returns the wrong upgrade matrix. AWS: 200 with CompatibleElasticsearchVersions covering both the legacy Elasticsearch 5.x/6.x lines (e.g. source 5.1 -> [5.6]; source 6.0 -> [6.3, 6.4, 6.5, 6.7, 6.8]; sources 5.3, 6.2, 6.3, 6.4 likewise) and the current OpenSearch lines (e.g. source OpenSearch_3.3 -> [OpenSearch_3.5, OpenSearch_3.7]; OpenSearch_2.19 -> [OpenSearch_3.1, OpenSearch_3.3, OpenSearch_3.5, OpenSearch_3.7]), with each entry's TargetVersions limited to the versions that source may actually upgrade to. Smithy: GetCompatibleElasticsearchVersions, http GET /2015-01-01/es/compatibleVersions, output CompatibleElasticsearchVersions (CompatibleElasticsearchVersionsList); contents unmodelled, so recorded behavior only. Emulator: 200 with a different, stale matrix — it omits whole source versions AWS lists (the 5.x and 6.0-6.4 rows come back absent) and over-enumerates targets on the rows it does serve (e.g. a 7.9 row fanning out to the whole OpenSearch_1.x line), so source/target pairs do not line up with AWS's at any index. Trace: es-catalog-get-compatible-elasticsearch-versions#task#1.

Cause 3 of 3 — GetPackageVersionHistory refuses every AWS catalog package. AWS: 200 with the requested PackageID echoed and PackageVersionHistoryList holding one entry per package version (CommitMessage, CreatedAt, PackageVersion), newest version first. Smithy: GetPackageVersionHistory, http GET /2015-01-01/packages/{PackageID}/history, required PackageID @httpLabel, output PackageID + PackageVersionHistoryList; ResourceNotFoundException is a modelled error for this operation. Emulator: 404 with x-amzn-errortype ResourceNotFoundException and a 'Package not found: <packageID>' body, with no PackageID and no PackageVersionHistoryList — for every one of the AWS package ids the fixture walks (91 affected steps), because those packages are absent from the emulator's invented catalog. The fixed text here is the not-found refusal; the only variable part is the packageID taken from the request path. The defect is not the refusal's wording but that a package AWS publishes is unknown to the emulator, so the whole package-version surface is unreadable.

Why: these catalogs are the menus a client chooses from. A client that lists packages gets package names and PackageIDs that exist nowhere in AWS and misses every package AWS does publish, so a subsequent AssociatePackage or GetPackageVersionHistory on a legitimately discovered id fails; a client that plans an upgrade reads a compatibility matrix that both hides supported upgrade paths (every 5.x/6.0-6.4 source) and offers targets AWS will reject; and a client that reads version history for any AWS-published package is told the package does not exist, so version pinning and plugin-version discovery are impossible.

Fix: the static reference data behind these three readers and the lookups over it — the es package catalog (with per-package version history records, per-package CreatedAt/LastUpdatedAt and the ErrorDetails member on each PackageDetails) in the service's state/seed data, and the Elasticsearch/OpenSearch upgrade-compatibility table behind GetCompatibleElasticsearchVersions. GetPackageVersionHistory's handler needs no new refusal logic; it needs the catalog it reads to contain AWS's packages.

Traces: es-catalog-describe-packages#task#1 (cause 1), es-catalog-get-compatible-elasticsearch-versions#task#1 (cause 2), es-catalog-get-package-version-history#task#1 and its 90 sibling steps task#2..task#25+ (cause 3).
