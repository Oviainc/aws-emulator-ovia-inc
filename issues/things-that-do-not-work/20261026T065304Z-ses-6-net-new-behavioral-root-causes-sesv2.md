# ses: 6 net-new behavioral root causes — SESv2 PutConfigurationSetSendingOptions and TagResource answer 501 NotImplemented, the two identity-notification setters invent an SNS-topic prerequisite, SetIdentityNotificationTopic stores a nonexistent topic ARN, and CFN-deployed AWS::SES::* resources do not exist after CREATE_COMPLETE

## Operation
PutConfigurationSetSendingOptions

## Description
Six net-new behavioral root causes on the SES surface. None of the seven failing checks below was marked ALREADY FILED or OWNED by the replay report. Open issues that are related but do NOT cover them are named per cause.

Cause 1 of 6: SESv2 PutConfigurationSetSendingOptions is an unimplemented scaffold stub, so a configuration set's sending pause can never be written and the v2 data-plane SendingPaused refusal is unreachable.
AWS: Smithy (com.amazonaws.sesv2#PutConfigurationSetSendingOptions) binds PUT /v2/email/configuration-sets/{ConfigurationSetName}/sending with success status 200 and an empty body; input {ConfigurationSetName @httpLabel required, SendingEnabled boolean default false}; modeled errors BadRequestException 400, NotFoundException 404, TooManyRequestsException 429. A fresh configuration set defaults to SendingEnabled=true, so SendEmail through it succeeds; after SendingEnabled=false the v2 send is refused with SendingPausedException whose message is "Sending is paused for configuration set <ConfigurationSetName>" — fixed text "Sending is paused for configuration set " plus the configuration-set name taken from the request — and re-enabling restores sending, each accepted send minting its own MessageId. 501/NotImplemented is a status no SESv2 operation models.
Emulator: every call is refused. HTTP 501, code `NotImplemented`, message `operation PutConfigurationSetSendingOptions is scaffolded but not implemented in this emulator`. The preceding sesv2.create_configuration_set and the first SendEmail through the set both succeed, so the check aborts exactly on this call.
Why: a client cannot pause sending for a configuration set at all; the account- vs set-scoped pause distinction, the SendingPausedException class and its message, and the restore path are all unreachable, and the caller sees an unmodeled error class it cannot branch on.
Fix: implement the handler at services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/put_configuration_set_sending_options.rs (persist the flag on the named configuration set in that crate's state, refuse an unknown set with NotFoundException 404, remove the file's `//! SCAFFOLDED, NOT IMPLEMENTED:` marker) and gate the v2 send path on it with SendingPausedException and AWS's sentence.
Traces: ses.configuration-set-sending-disabled-blocks-v2-send-email-then-restored.

Cause 2 of 6: SESv2 TagResource is an unimplemented scaffold stub, so the SES tagging write path and its two distinct refusal classes are unreachable.
AWS: Smithy (com.amazonaws.sesv2#TagResource) binds POST /v2/email/tags, success 200 empty body; input {ResourceArn required @length min 1, Tags required TagList}; modeled errors BadRequestException 400, NotFoundException 404, ConcurrentModificationException 500, TooManyRequestsException 429. Recorded behavior (us-west-2) shows two different layers refusing two different conditions: a tag key using the reserved `aws:` prefix is refused BadRequestException with the fixed message "Failed to tag resource" (no interpolated value), while a tag key longer than the modeled TagKey maximum (129 characters) trips the shape constraint and is refused ValidationException with an EMPTY Message; a batch containing one bad key applies none of the batch, and an already-stored legitimate tag survives every refusal untouched.
Emulator: every call is refused. HTTP 501, code `NotImplemented`, message `operation TagResource is scaffolded but not implemented in this emulator` — raised on the very first (valid) tag_resource call, so neither the happy path nor either refusal class exists. Related but not covering: the open issue 20261026T044445Z-sesv2-tagresource-stub.md names this same operation and handler file but does not carry this check's replay key, and it asks only for the operation to exist — the two-class refusal taxonomy and the batch atomicity above are the additional fidelity requirement recorded here.
Why: tags are read by cost-control and attribution tooling, so a caller cannot tag any SES resource; and once implemented, collapsing the reserved-prefix and over-length conditions into one code/message (or applying a batch partially) leaves a half-tagged resource and a diagnosis real AWS never produces.
Fix: implement the handler at services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/tag_resource.rs — validate the whole batch before writing anything, refuse a reserved `aws:` key with BadRequestException/"Failed to tag resource", let the modeled TagKey length constraint surface as ValidationException with an empty Message, and remove that file's scaffold header.
Traces: ses.tag-resource-reserved-prefix-and-key-limit-rejected.

Cause 3 of 6: SetIdentityFeedbackForwardingEnabled invents an SNS-topic precondition and refuses a disable that AWS accepts.
AWS: Smithy (com.amazonaws.ses#SetIdentityFeedbackForwardingEnabled) models NO errors at all; input {Identity required, ForwardingEnabled boolean required}. The operation's prose says feedback forwarding "can only be disabled when Amazon SNS topics are specified for both bounces and complaints", but that guidance is NOT enforced at the API boundary: recorded behavior is that ForwardingEnabled=false on an identity with no Bounce/Complaint topic is ACCEPTED (200, empty body) and GetIdentityNotificationAttributes then reports ForwardingEnabled=false; setting it back to true restores it.
Emulator: the call is refused with HTTP 400, code `InvalidParameterValue`, message "ForwardingEnabled can only be set to false when Amazon SNS topics are set for both Bounce and Complaint notification types; <identity> has no topic for both of them" — an emulator-authored sentence built from the member's documentation, with the identity interpolated. The gate is services/service-com-amazonaws-ses-simpleemailservice/src/ops/set_identity_feedback_forwarding_enabled.rs lines 166-174 (`if !input.forwarding_enabled && !record.notifications.publishes_bounces_and_complaints()`).
Why: over-strictness. The default state of every identity is ForwardingEnabled=true with no topics, so the ONLY way a client turns email feedback forwarding off is exactly the call the emulator refuses; the flag is unreachable, and the caller gets an InvalidParameterValue for a request AWS answers 200. InvalidParameterValue is also not among this operation's modeled errors.
Fix: the validation in that handler — drop the both-topics precondition and write the flag unconditionally (the identity-exists check stays).
Traces: ses.feedback-forwarding-toggle.

Cause 4 of 6: SetIdentityHeadersInNotificationsEnabled invents the same kind of topic precondition.
AWS: Smithy (com.amazonaws.ses#SetIdentityHeadersInNotificationsEnabled) models NO errors; input {Identity required, NotificationType enum required, Enabled boolean required}. Recorded behavior: on a freshly verified identity with no SNS topic attached, Enabled=true for NotificationType=Bounce is ACCEPTED (200) and GetIdentityNotificationAttributes reports HeadersInBounceNotificationsEnabled=true while HeadersInComplaintNotificationsEnabled stays false (the flag is scoped to the named notification type); setting it back to false is accepted too. The "can only be set when NotificationType is already set to use a particular Amazon SNS topic" sentence in the member's docs is not an API-boundary rule.
Emulator: refused with HTTP 400, code `InvalidParameterValue`, message "Enabled can only be set when NotificationType is already set to use a particular Amazon SNS topic; <identity> has no Bounce topic" — handler-authored from the doc prose, with the identity and the notification type interpolated. The gate is services/service-com-amazonaws-ses-simpleemailservice/src/ops/set_identity_headers_in_notifications_enabled.rs lines 184-192 (`if record.notifications.topic(notification_type).is_none()`).
Why: the per-notification-type header flags can never be set on an identity that has no topic, which is every identity until a topic is attached, so the whole attribute group is unreachable and a client that sets headers before wiring SNS gets an unmodeled refusal where AWS answers 200.
Fix: the validation in that handler — remove the topic-existence precondition and write the per-type flag.
Traces: ses.identity-headers-in-notifications-toggle.

Cause 5 of 6: SetIdentityNotificationTopic accepts and stores an SNS topic ARN that names no existing topic.
AWS: Smithy (com.amazonaws.ses#SetIdentityNotificationTopic) models no operation-specific errors; SnsTopic is documented as "The Amazon Resource Name (ARN) of the Amazon SNS topic" and omitting/clearing it disables publishing. Recorded behavior: a well-formed ARN in the caller's own account and region that names no existing topic is refused 400 `InvalidParameterValue` with the message "SNS topic <arn> is invalid." — fixed text "SNS topic " + the submitted ARN copied verbatim from the request + " is invalid." — and the refusal leaves the topic already attached to that notification type unchanged (the positive control, a real SES-publishable topic, is accepted and read back by GetIdentityNotificationAttributes).
Emulator: the call SUCCEEDS — HTTP 200, empty SetIdentityNotificationTopicResponse — and the nonexistent ARN is stored on the identity. The handler (services/service-com-amazonaws-ses-simpleemailservice/src/ops/set_identity_notification_topic.rs lines 168-181) only runs `crate::state::resolve_sns_topic`, an ARN-shape/region parse; nothing checks that the topic exists in the SNS service, so no refusal is ever raised for a dangling ARN.
Why: over-permissiveness. The emulator blesses a notification configuration real AWS refuses, so a typo'd or cross-account topic ARN is stored and the bounce/complaint notifications it is supposed to carry silently go nowhere; code that catches InvalidParameterValue to surface the misconfiguration never runs.
Fix: the topic validation in that handler — resolve the ARN against the SNS service's topic store for the request's account+region and refuse an unknown topic with InvalidParameterValue carrying AWS's "SNS topic <arn> is invalid." text before anything is written.
Traces: ses.identity-notification-topic-bogus-arn-rejected.

Cause 6 of 6: a CloudFormation stack declaring AWS::SES::ConfigurationSet / AWS::SES::ReceiptRuleSet / AWS::SES::ReceiptRule reaches CREATE_COMPLETE without creating the SES resource — the stack record exists, the resource does not.
AWS: recorded behavior only (CloudFormation resource types are not in the SES Smithy model). A stack whose template declares `AWS::SES::ConfigurationSet` with Name=<n> reaches CREATE_COMPLETE and the resource is then a fully functional configuration set: v1 DescribeConfigurationSet(ConfigurationSetName=<n>) answers with ConfigurationSet.Name=<n>, SESv2 GetConfigurationSet reports SendingOptions.SendingEnabled=true, UpdateConfigurationSetSendingEnabled toggles are durably reflected, and deleting the stack removes the underlying set (GetConfigurationSet then answers NotFoundException). Likewise a stack declaring `AWS::SES::ReceiptRuleSet` with RuleSetName=<r> plus a dependent `AWS::SES::ReceiptRule` reaches CREATE_COMPLETE and v1 DescribeReceiptRuleSet(RuleSetName=<r>) answers with Metadata.Name=<r> and the declared rule present and Enabled=true, and SetActiveReceiptRuleSet/DescribeActiveReceiptRuleSet then report it active.
Emulator: both stacks are created and the `stack_create_complete` waiter returns, but the SES resources were never provisioned. The first read after the deploy is refused: DescribeConfigurationSet answers 400 `ConfigurationSetDoesNotExist` "Configuration set <name> does not exist." and DescribeReceiptRuleSet answers 400 `RuleSetDoesNotExist` "Rule set does not exist: <name>" — both naming the exact name the template created, so the stack succeeded while its resource is absent.
Why: a CREATE_COMPLETE that provisions nothing is the most misleading outcome available: every infrastructure-as-code workflow that deploys SES resources and then uses them through the SES API breaks one call later, with a not-found error that points at the resource rather than at the deployment, and stack deletion cannot be verified to remove anything. Related but not covering: the open issue 20261026T062103Z-codecommit-2-net-new-behavioral-root-causes-a.md records the same class for AWS::CodeCommit::Repository, and 20261026T023803Z-apigatewayv2-cloudformation-stack-outputs-carry-no-outputvalue-and.md for AWS::ApiGatewayV2::DomainName; neither covers the AWS::SES::* resource types or carries these checks' replay keys.
Fix: the CloudFormation resource-provisioning layer (the cloudformation crate's resource-type provider registry) must materialise AWS::SES::ConfigurationSet, AWS::SES::ReceiptRuleSet and AWS::SES::ReceiptRule into the ses crate's state on create — and delete them on stack delete — rather than recording only stack resources; the SES-side state writers those resources need are the same ones CreateConfigurationSet / CreateReceiptRuleSet use.
Traces: ses.deploy-ses-configuration-set-cfn-usable, ses.deploy-ses-receipt-rule-set-cfn-activatable.
