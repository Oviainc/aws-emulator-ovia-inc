# Step Functions: JSONata definitions are never evaluated at run time (whole-machine and per-state override), and the InvalidDefinition message orders diagnostics lexicographically instead of in definition order (3 causes)

> _Note: this issue was identified against the code base at commit `11987c6da263e982c4d9dc23065f7f10f256112a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
Three net-new root causes in the Step Functions service, all reached through the `sfn.deep-sfn-2-sfn-jsonata-*` checks. They are NOT the causes already carried by the open issue 20261024T043150Z-sfn-step-functions-interpreter-does-not-run-the-workflow.md (Task states / Distributed Map / callbacks / Retry-Catch) nor by 20261027T000406Z-sfn-step-functions-states-startexecution-sync-is-never-executed.md (a JSONata state inside a Parallel branch): the failures below are plain Pass-state JSONata machines with no Task, no Parallel and no service integration in the data path, and one is a control-plane message-composition defect. The suite did not mark any of these three checks as owned by an existing issue.

Cause 1 of 3 — a state machine whose top-level `QueryLanguage` is `JSONata` is refused at run time instead of being interpreted.
AWS: Smithy: CreateStateMachine.definition (@length 1..1048576) is accepted for either query language; `QueryLanguage` is a definition-level field of the Amazon States Language and a definition declaring `"QueryLanguage": "JSONata"` with Pass states carrying `Output` JSONata expressions (`{% ... %}`) is a valid, runnable machine — ValidateStateMachineDefinition returns result `OK` with no diagnostics for it (the check's own positive control asserts that, and the emulator agreed). Running it evaluates each `Output` expression against `$states.input` and the execution reaches `status` SUCCEEDED with the evaluated object as `output` (here `{"x": 50}` from input `{"n": 4}` through `Seed`/`P`).
Emulator: StartExecution accepts the machine, then the execution ends `status` `FAILED` with `error` `States.Runtime` and `cause` "the definition is written in 'JSONata', and this emulator evaluates only 'JSONPath' definitions, so nothing was run for it" — emulator-local wording that AWS never emits, on a definition AWS runs to success.
Why: every JSONata-mode workflow is unrunnable. A client cannot test any JSONata machine at all: output assembly, variable assignment and choice evaluation in JSONata mode all come back as a bogus `States.Runtime` failure, and a test suite that expects SUCCEEDED sees a failed execution with a cause string it cannot map to any AWS error class.
Fix: the state-machine interpreter — the query-language dispatch in the execution evaluator (services/service-com-amazonaws-sfn-awsstepfunctions/src/...; the evaluator currently hard-refuses any definition whose `QueryLanguage` is not `JSONPath`) must evaluate JSONata expressions (`{% %}`) for state `Output`/`Arguments`/`Assign` rather than failing the execution.
Traces: sfn.deep-sfn-2-sfn-jsonata-pass-states-result-rejected (positive control, after the create-time rejection asserts passed).

Cause 2 of 3 — a per-state `QueryLanguage: JSONata` override inside a JSONPath machine is refused at run time: the state's `Output` member is not interpreted.
AWS: recorded behavior only for the mixed-language direction (the ASL permits a per-state `QueryLanguage` override to JSONata inside a `"QueryLanguage": "JSONPath"` machine; the reverse override is rejected, which the emulator already reports correctly). AWS validates such a definition (`result` `OK`, no diagnostics), stores it so DescribeStateMachine round-trips the definition verbatim, and runs it: the JSONPath state applies its `Parameters` and the JSONata state evaluates its `Output` expression, giving SUCCEEDED with output `{"v": "x-nata"}` for input `{"v": "x", "drop": 1}`.
Emulator: the execution ends `status` `FAILED` with `error` `States.Runtime` and `cause` "state 'Q' carries the member 'Output', which this emulator does not interpret, so nothing was run for it" — the fixed text is emulator-local; the variable parts are the state name (`Q` here, taken from the definition) and the member name (`Output`). AWS emits no such error for a modelled ASL member.
Why: mixed-language machines — the documented migration path from JSONPath to JSONata, one state at a time — cannot be exercised. A client migrating a workflow sees every converted state fail the whole execution, and the refusal is attributed to a legal ASL member rather than to anything in its request.
Fix: the state evaluator's per-state member handling (the same interpreter component as Cause 1): honour a state-level `QueryLanguage` override and implement the `Output` member for JSONata states instead of failing the execution on an uninterpreted member.
Traces: sfn.deep-sfn-2-sfn-jsonata-jsonpath-state-under-jsonata-machine-rejected (positive control; the create-time SCHEMA_VALIDATION_FAILED rejection and its message matched).

Cause 3 of 3 — CreateStateMachine's InvalidDefinition message lists multiple diagnostics in the wrong order.
AWS: Smithy: CreateStateMachine error `InvalidDefinition` (client, HTTP 400). When several JSONata diagnostics are raised for one definition, the message is the fixed prefix `Invalid State Machine Definition: '` followed by the diagnostics joined with `, ` and a closing `'`, each rendered as `<CODE>: <message> at <location>`, in the order the offending fields appear in the submitted definition — not sorted by location. For a Task whose own `Output` is `{"error": "{% $states.errorOutput.Error %}", "cause": "{% $states.errorOutput.Cause %}"}` AWS answers: `Invalid State Machine Definition: 'UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Error' does not exist. at /States/T/Output/error, UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Cause' does not exist. at /States/T/Output/cause'`. Fixed text: `Invalid State Machine Definition: '`, the code `UNSUPPORTED_JSONATA_EXPRESSION: `, the phrase `does not exist.` and ` at `. Variable parts: the offending field reference (`$states.errorOutput.Error`) and the JSON pointer location, both taken from the submitted definition; the state name `T` and member names `error`/`cause` are this request's values, not part of the template.
Emulator: same code (`InvalidDefinition`) but the two diagnostics are emitted lexicographically by location, i.e. `...'$states.errorOutput.Cause' does not exist. at /States/T/Output/cause, UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Error' does not exist. at /States/T/Output/error'` — cause before error. ValidateStateMachineDefinition's own diagnostics list, codes, locations and per-diagnostic messages all matched; only the aggregated create-time message order diverges.
Why: a client that asserts on, logs or diffs the InvalidDefinition message (the usual way an ASL authoring tool surfaces which field broke first) gets a different string from the emulator than from AWS, so definition-validation tests pass against AWS and fail against the emulator for a definition whose rejection is otherwise correct.
Fix: the CreateStateMachine handler's definition-validation diagnostic aggregation — the component that composes the InvalidDefinition message must preserve the definition's member order when joining diagnostics instead of sorting them by location (services/service-com-amazonaws-sfn-awsstepfunctions/src/ops/create_state_machine.rs and the shared definition validator it calls).
Traces: sfn.deep-sfn-2-sfn-jsonata-error-output-outside-catch-rejected.

  Actual: status FAILED, error 'States.Runtime', cause "state 'Q' carries the member 'Output', which this emulator does not interpret, so nothing was run for it".

Cause 3 (sfn.deep-sfn-2-sfn-jsonata-error-output-outside-catch-rejected):
  Expected CreateStateMachine refusal: code InvalidDefinition (HTTP 400), message "Invalid State Machine Definition: 'UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Error' does not exist. at /States/T/Output/error, UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Cause' does not exist. at /States/T/Output/cause'".
  Actual: code InvalidDefinition, message "Invalid State Machine Definition: 'UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Cause' does not exist. at /States/T/Output/cause, UNSUPPORTED_JSONATA_EXPRESSION: Field '$states.errorOutput.Error' does not exist. at /States/T/Output/error'" — the two diagnostics are in the opposite (location-sorted) order.
  The preceding ValidateStateMachineDefinition assertions (result FAIL, one ERROR/UNSUPPORTED_JSONATA_EXPRESSION diagnostic per Output field, per-diagnostic messages, and OK for the same expression inside a Catch Output) all passed.
