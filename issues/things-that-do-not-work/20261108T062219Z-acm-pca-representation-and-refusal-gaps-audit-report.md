Cause 1 of 5: the JSON audit report writes each row's `serial` as unseparated lowercase hex instead of colon-delimited octet pairs, so no client can join an audit-report row to the certificate it describes.
AWS: Smithy models CreateCertificateAuthorityAuditReport {CertificateAuthorityArn @required, S3BucketName @required, AuditReportResponseFormat @required} -> {AuditReportId, S3Key} and DescribeCertificateAuthorityAuditReport -> {AuditReportStatus, S3BucketName, S3Key, CreatedAt}; the model says nothing about the report body, so the body format is recorded behavior only. The recordings show the report object is a JSON array of rows {awsAccountId, certificateArn, serial, subject, notBefore, notAfter, issuedAt, revokedAt, revocationReason, templateArn}, and `serial` is the certificate's serial number rendered as lowercase hex octets separated by colons -- the same rendering `openssl x509 -serial`/X.509 tooling produce and the form a client obtains from the certificate PEM it already holds. The `certificateArn` tail keeps the unseparated hex form; `serial` does not.
Emulator: emits `serial` as unseparated lowercase hex, e.g. a row with serial 'c85cfc5c68f90d55ac9d3909a49aed4f' for a certificate whose serial is 'c8:5c:fc:5c:68:f9:0d:55:ac:9d:39:09:a4:9a:ed:4f' -- identical to the value it already puts in the certificateArn tail. The particular serial is a per-run value; the requirement is the colon-delimited rendering.
Why: the audit report exists to be correlated with issued certificates, and the serial is the only field that correlates a row with a certificate a client parsed itself. With the separators dropped, every lookup of a known serial in the report returns no row, so clients cannot confirm an issuance, cannot confirm a revocation (revokedAt/revocationReason are unreachable), and silently conclude a certificate was never issued.
Emulator rows also show the leaf's `templateArn` as the empty string where the root's row carries arn:aws:acm-pca:::template/RootCACertificate/V1; that is visible in the same evidence but is not what any check asserts, so it is noted only.
Fix: the audit-report row serialization in the CreateCertificateAuthorityAuditReport handler (the component that renders certificate state into the report object) -- render `serial` as colon-separated lowercase hex octet pairs.
Traces: acm-pca.audit-report-async-completion-managed (check line 61), acm-pca.e2e-issue-and-revoke-certificate-reflected-in-audit-report (check line 49), acm-pca.revoke-already-revoked-certificate-rejected (check line 62), acm-pca.revoke-certificate-duplicate-revoke-already-processed (check line 86); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/create_certificate_authority_audit_report.rs.

Cause 2 of 5: DescribeCertificateAuthorityAuditReport's ResourceNotFoundException message is miscased relative to AWS's fixed sentence.
AWS: Smithy models ResourceNotFoundException on DescribeCertificateAuthorityAuditReport as a client error with httpError 400 (doc: 'A resource such as a private CA, S3 bucket, certificate, audit report, or policy cannot be found.'). The text is recorded behavior: an AuditReportId that is well-formed (@length 36..36, pattern ^[a-z0-9]{8}-[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{4}-[a-z0-9]{12}$) but names no report on that CA is refused with HTTP 400, Error.Code 'ResourceNotFoundException' and Error.Message 'Could not find specified Audit Report.' -- the whole sentence is fixed text, including the capitalised 'Audit Report'; no part of it comes from the request or from state.
Emulator: right status and right error code, but the message is 'Could not find specified audit report.' -- the same sentence with 'Audit Report' lower-cased.
Why: the message is part of the contract. A client, test or log matcher that compares the refusal text exactly (as this check does) sees a string production never returns, so a recorded emulator response is not comparable with production.
Fix: the ResourceNotFoundException message construction in DescribeCertificateAuthorityAuditReport's lookup path -- emit AWS's fixed sentence verbatim.
Traces: acm-pca.describe-audit-report-not-found (check line 227); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/describe_certificate_authority_audit_report.rs.

Cause 3 of 5: ImportCertificateAuthorityCertificate accepts a correctly-signed subordinate certificate paired with a CertificateChain that did not sign it, instead of refusing the chain mismatch.
AWS: Smithy models ImportCertificateAuthorityCertificate {CertificateAuthorityArn @required (Arn, @length 5..200), Certificate @required (CertificateBodyBlob, @length 1..32768), CertificateChain (CertificateChainBlob, @length 0..2097152)} -> Unit, with CertificateMismatchException among its errors (doc: 'The certificate authority certificate you are importing does not comply with conditions specified in the certificate that signed it'), httpError 400. The specific diagnostic is recorded behavior: when the submitted Certificate is a valid signature over the CA's own outstanding CSR but the supplied CertificateChain does not contain the issuer that signed it, the call is refused with HTTP 400, Error.Code 'CertificateMismatchException' and Error.Message 'Certificate does not chain up to certificate chain provided.' -- that sentence is fixed text in full, with no part taken from the request or state -- and the CA stays PENDING_CERTIFICATE (GetCertificateAuthorityCertificate still refuses with InvalidStateException 'The certificate authority <CertificateAuthorityArn> is not in the correct state to have a certificate signing request.', whose only variable part is the request's CA ARN). The SAME certificate paired with the correct chain must then activate the CA, which is what proves the refusal was about the chain. This is a THIRD, distinct classification from the subject-mismatch and public-key-mismatch diagnostics the two related open issues describe: the three are told apart by which input diverges.
Emulator: answers HTTP 200 with an empty JSON body (content-type application/x-amz-json-1.1, content-length 2) and installs the certificate -- CertificateChain is not validated at all.
Why: the CA is activated with a certificate whose chain the service cannot build, so nothing it subsequently signs can be path-validated by a client that trusts the advertised chain, and ACM PCA offers no way to undo an import. The client's mismatch-handling branch never runs, and because the emulator never distinguishes a chain mismatch from a subject or key mismatch, a caller cannot tell which input it got wrong.
Fix: ImportCertificateAuthorityCertificate's validation -- before any state mutation, verify the submitted Certificate's signature against the issuer in the supplied CertificateChain and refuse with CertificateMismatchException carrying the chain sentence when it does not chain up.
Traces: acm-pca.certificate-mismatch-import-rejected (check lines 42/89); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/import_certificate_authority_certificate.rs.

Cause 4 of 5: the CA's generated PKCS#10 CSR carries no KeyUsage extension, so CreateCertificateAuthority's CsrExtensions.KeyUsage is silently dropped.
AWS: Smithy models CertificateAuthorityConfiguration.CsrExtensions as CsrExtensions {KeyUsage, SubjectInformationAccess} (doc: 'Describes the certificate extensions to be added to the certificate signing request (CSR)'), and KeyUsage as nine booleans (DigitalSignature, NonRepudiation, KeyEncipherment, DataEncipherment, KeyAgreement, KeyCertSign, CRLSign, EncipherOnly, DecipherOnly), each @default false (doc: 'Default value for each option is false'). GetCertificateAuthorityCsr -> Csr (CsrBody). The content requirement is recorded behavior: the returned PEM CERTIFICATE REQUEST carries a KeyUsage extension in its requested-extensions attribute whose bits are EXACTLY the ones set true in CsrExtensions.KeyUsage and no others -- for CsrExtensions={'KeyUsage': {'DigitalSignature': true, 'KeyCertSign': true, 'CRLSign': true}} the CSR's KeyUsage has digitalSignature, keyCertSign and cRLSign asserted and nonRepudiation, keyEncipherment, dataEncipherment and keyAgreement clear.
Emulator: the CSR parses, its subject matches, its RSA-2048 key loads and its self-signature verifies, but it has NO KeyUsage extension at all -- cryptography raises 'cryptography.x509.extensions.ExtensionNotFound: No <class \'cryptography.x509.extensions.KeyUsage\'> extension was found'. The configured CsrExtensions have no observable effect on the CSR.
Why: CsrExtensions exists solely to shape the CSR a parent CA will sign. With the extension absent, the parent signs a request that declares no key purposes, so the resulting CA certificate cannot be constrained to keyCertSign/cRLSign and the caller's configuration is accepted-and-ignored: the client gets a silent downgrade, not an error.
Fix: the CA key-pair/CSR generation that backs GetCertificateAuthorityCsr (and the CA state that must retain CsrExtensions from CreateCertificateAuthority) -- encode a KeyUsage extension into the PKCS#10 requested-extensions attribute with exactly the configured bits set.
Traces: acm-pca.ca-csr-pem-structure-matches-requested-configuration (check line 270); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/get_certificate_authority_csr.rs, src/ops/create_certificate_authority.rs, src/state.rs.

Cause 5 of 5: a certificate issued under the RootCACertificate/V1 template carries no BasicConstraints extension, so nothing marks it as a CA certificate.
AWS: Smithy models IssueCertificate {CertificateAuthorityArn @required, Csr @required, SigningAlgorithm @required, TemplateArn, Validity @required, ValidityNotBefore, IdempotencyToken} -> CertificateArn; the model does not describe template contents, so the extension set is recorded behavior plus the published template definitions. A certificate issued with TemplateArn arn:aws:acm-pca:::template/RootCACertificate/V1 contains a critical BasicConstraints extension with CA=TRUE; that extension is what makes the certificate usable as an issuer and what distinguishes a CA certificate from an end-entity one.
Emulator: the issued root certificate has no BasicConstraints extension -- 'cryptography.x509.extensions.ExtensionNotFound: No <class \'cryptography.x509.extensions.BasicConstraints\'> extension was found'. (The CSR-to-certificate key identity this check also asserts now passes, so this is the remaining divergence; the unparseable-SPKI cause named by 20261102T094958Z-acm-pca-key-material-identity-the-ca-s.md no longer reproduces.)
Why: an RFC 5280 path validator rejects a certificate without CA=TRUE as an issuer, so the root the emulator activates a CA with can never anchor a chain; a client validating anything that CA signs fails, and nothing in the response tells it the template's semantics were not applied.
Fix: the template application in IssueCertificate's certificate assembly -- populate the extensions each TemplateArn's definition mandates, including a critical BasicConstraints with that template's CA flag and pathLenConstraint. Same surface as cause 5 of 20261029T193511Z-acm-pca-certificate-path-issuecertificate-issues-leaves-that.md, which grounds it only in the SubordinateCACertificate_PathLen0 template and does not carry this check's replay key.
Traces: acm-pca.csr-to-issued-certificate-pem-preserved (check line 73); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/issue_certificate.rs.
