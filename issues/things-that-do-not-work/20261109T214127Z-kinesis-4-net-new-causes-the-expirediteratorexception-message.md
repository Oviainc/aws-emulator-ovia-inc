# kinesis: 4 net-new causes — the ExpiredIteratorException message is emulator-authored (wrong phrase and wrong timestamp format), the ListStreamConsumers ExpiredNextTokenException message is invented, no AWS/Kinesis stream- or shard-level metric series is published, and the HTTPS front door refuses h2 in ALPN so hand-signed HTTP/2 PutRecord/GetRecords cannot connect

> _Note: this issue was identified against the code base at commit `19c62db1539bfab1a25075fa0f8ae1a77a215876`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRecords

## Description
Four net-new root causes in the Kinesis Data Streams surface. All ten failing checks below are listed under `### kinesis` in the replay report and marked NEITHER "ALREADY FILED" nor "OWNED by"; every other kinesis failure in this replay is owned by an existing issue.

=== Cause 1 of 4: the ExpiredIteratorException message uses the wrong fixed phrase and the wrong timestamp format ===
AWS: Smithy (com-amazonaws-kinesis-kinesis-20131202) binds ExpiredIteratorException to GetRecords — a client error, HTTP 400, doc "The provided iterator exceeds the maximum age allowed" — with a single `message` member; the message text itself is recorded behavior only. AWS serves exactly this sentence: `Iterator expired. The iterator was created at time <created> while right now it is <now> which is further in the future than the tolerated delay of 300000 milliseconds.` Fixed text: `Iterator expired. The iterator was created at time `, ` while right now it is `, ` which is further in the future than the tolerated delay of 300000 milliseconds.` — including the 300000 ms figure. Variable parts: <created>, the instant GetShardIterator minted the iterator, and <now>, the server's current instant, BOTH rendered in Java's `Date.toString` layout `EEE MMM dd HH:mm:ss UTC yyyy` (e.g. three-letter weekday, three-letter month, zero-padded day, 24-hour time, the literal `UTC`, four-digit year). The instants themselves are per-run values and are not part of the requirement; the layout is.
Emulator: the error code and the 400 are right, but the message is `Iterator expired. The iterator was created at time 2026-11-09T20:49:40.236Z while right now it is 2026-11-09T20:54:42.268Z which is further in the past than the tolerated delay of 300000 milliseconds.` Two divergences in one sentence: the fixed phrase reads `further in the past than` where AWS says `further in the future than`, and both instants are rendered as ISO-8601 with a `Z` suffix and fractional seconds instead of the `EEE MMM dd HH:mm:ss UTC yyyy` layout — the fraction is not even fixed-width (one sample renders `2026-11-09T20:31:49.1Z`), so the rendering is not self-consistent either.
Why: the message is part of the contract. Consumer libraries and operators that parse or match this sentence (KCL-style log scrapers, retry wrappers keyed on the creation instant, tests pinned to AWS's text) see text AWS never serves, and a client that extracts the two instants cannot parse them with AWS's format.
Fix: the ExpiredIteratorException message construction on the GetRecords handler's iterator-age path — emit AWS's fixed sentence and format both instants in the `EEE MMM dd HH:mm:ss UTC yyyy` layout.
Traces: kinesis.expired-shard-iterator-rejected-after-retention-window, kinesis.get-shard-iterator-ttl-expires-after-inactivity, kinesis.shard-iterator-expires-after-ttl, kinesis.shard-iterator-expires-after-ttl-window.

=== Cause 2 of 4: the ListStreamConsumers ExpiredNextTokenException message is emulator-authored prose ===
AWS: Smithy binds ExpiredNextTokenException to ListStreamConsumers (client error, HTTP 400, doc "The pagination token passed to the operation is expired"), and models ListStreamConsumers as @paginated with NextToken in and out; the message text is recorded behavior only. AWS serves `NextToken expired at time <expiry>. Invoke ListStreamConsumers again to get a new pagination token.` Fixed text: `NextToken expired at time `, and the whole sentence `Invoke ListStreamConsumers again to get a new pagination token.` Variable part: <expiry>, the instant the token lapsed, in the `EEE MMM dd HH:mm:ss UTC yyyy` layout. The token TTL is about 300 s, but the message names an INSTANT, never the TTL.
Emulator: the code is right but the message is `the pagination token is expired or was not issued by this service; a NextToken is usable for 300 seconds after the page that returned it` — entirely emulator-authored lowercase prose: it names no expiry instant, states a duration AWS does not put in this message, and conflates "expired" with "not issued by this service" (two distinct error classes — a token that was never minted is a ValidationException, as already filed for the sibling misclassification in 20261029T140704Z-kinesis-liststreamconsumers-misclassifies-a-malformed-nexttoken-as-expirednexttokenexception.md, which covers the CLASSIFICATION and carries neither check id below).
Why: a paginating client that surfaces or matches the service's message gets text AWS never serves, and loses the expiry instant it needs to tell an expired page from a corrupt token.
Fix: the ExpiredNextTokenException message construction in the ListStreamConsumers handler's NextToken-decode path — emit AWS's sentence with the token's recorded expiry instant in the `EEE MMM dd HH:mm:ss UTC yyyy` layout.
Traces: kinesis.list-stream-consumers-expired-token-rejected, kinesis.list-stream-consumers-expired-token-unreachable.

=== Cause 3 of 4: no AWS/Kinesis metric series is published, so neither stream-level nor ShardId-dimensioned datapoints ever appear, with or without enhanced monitoring ===
AWS: Smithy models EnableEnhancedMonitoring (ShardLevelMetrics required, MetricsNameList @length 1..7) returning CurrentShardLevelMetrics/DesiredShardLevelMetrics; what the metrics mean is recorded behavior (https://docs.aws.amazon.com/streams/latest/dev/monitoring-with-cloudwatch.html). Recorded behavior: every stream publishes stream-level AWS/Kinesis series dimensioned by StreamName (IncomingRecords, IncomingBytes, PutRecord.* / PutRecords.*, GetRecords.IteratorAgeMilliseconds) without any opt-in, and once EnableEnhancedMonitoring names a shard-level metric the SAME metric names are additionally published dimensioned by StreamName+ShardId. The sums are exact: N separate PutRecord calls of equal-length payloads yield IncomingRecords Sum == N and IncomingBytes Sum == N * payload length on both the stream-level and the shard-level series, and a stream whose enhanced monitoring was never enabled publishes NO ShardId-dimensioned series at all until it is.
Emulator: GetMetricStatistics/GetMetricData for AWS/Kinesis return nothing. Polling for up to 240 s after 7 PutRecord calls leaves every series unobserved — `{'stream_incoming_records': None, 'shard_incoming_records': None, 'shard_incoming_bytes': None, 'shard_outgoing_records': None, 'shard_incoming_samples': None}` — and the twin-stream check that waits up to 420 s for the ARMED twin's ShardId-dimensioned IncomingRecords Sum to reach 6 observes `None`. Because nothing is ever published, the "absent until enabled" half of the contract passes only vacuously.
Why: Kinesis is operated through these metrics — autoscaling on IncomingRecords, alarms on GetRecords.IteratorAgeMilliseconds, hot-shard diagnosis on the ShardId dimension. A client sees a healthy stream with no telemetry at all, and an EnableEnhancedMonitoring call that reports success while changing nothing observable.
Fix: metric emission in the Kinesis service crate's data-plane handlers (PutRecord/PutRecords/GetRecords) into the CloudWatch store — publish the stream-level AWS/Kinesis series unconditionally and, for each metric named by the stream's enhanced-monitoring setting, the StreamName+ShardId series as well. Open issue 20261109T183935Z-cloudwatch-kinesis-no-aws-kinesis-stream-metric-series.md describes the same missing series but carries only `cloudwatch__kinesis` replay keys; neither of the two check ids below appears in it, so a fixer closing it would never re-replay the shard-dimensioned leg.
Traces: kinesis.enhanced-shard-level-metrics-land-in-cloudwatch-with-shard-dimension, kinesis.shard-dimensioned-metrics-absent-until-enhanced-monitoring-is-enabled.

=== Cause 4 of 4: the HTTPS front door does not advertise h2 in ALPN, so an HTTP/2 client cannot reach PutRecord or GetRecords at all ===
AWS: recorded behavior only (the protocol is wire identity, not a modeled trait): the Kinesis HTTPS endpoint advertises `h2` in the TLS ALPN extension, and a hand-signed HTTP/2 POST carrying `X-Amz-Target: Kinesis_20131202.PutRecord` / `.GetRecords` with an `application/x-amz-json-1.1` body is answered `:status 200` with the operation's JSON output; a request whose SigV4 signature was computed over one host but sent with a different `:authority` REACHES the service and is refused by it with a signature/authorization error, not dropped by the transport.
Emulator: the TLS handshake is aborted during ALPN with a fatal no_application_protocol alert — `error:0A000460:SSL routines:ssl3_read_bytes:tlsv1 alert no application protocol ... SSL alert number 120` — when an HTTP/2 client connects to the emulator's OWN announced HTTPS endpoint. No HTTP/2 session is established, no `:status` is ever seen and zero response bytes arrive, so neither the HTTP/2 round trip nor the `:authority`-mismatch refusal can be graded: the mismatch check fails at the transport instead of reaching the service, which hides whether the authority is bound into signature verification at all. The address is the one the emulator announced for itself, so this refusal is the emulator's and not the runner's network.
Why: HTTP/2 is the normal transport for AWS SDK Kinesis clients and the only transport for enhanced fan-out; an endpoint that refuses h2 by ALPN makes every h2-only client fail at connect time with a TLS alert that looks like a certificate or network problem, and leaves the authority-binding half of SigV4 verification unexercised.
Fix: the HTTPS front door's TLS configuration — advertise `h2` alongside `http/1.1` in ALPN and serve HTTP/2 on the Kinesis endpoint. Open issue 20261103T091152Z-kinesis-4-net-new-root-causes-listchannels-classifies.md describes the same ALPN gap as its Cause 4 but carries only kinesis.subscribe-to-shard-event-stream-framing-over-a-hand-signed-http2-request as a replay key; neither check id below appears there, so a fixer closing it would leave the PutRecord/GetRecords h2 path and the authority-mismatch refusal unrun. 20261101T034628Z-kinesis-the-https-front-door-aborts-the-tls.md reports a different alert (decode_error) under concurrent PutRecords.
Traces: kinesis.put-record-then-get-records-round-trip-over-a-hand-signed-http2-request, kinesis.put-record-signed-for-a-different-authority-host-rejected.
