# cloudformation__ec2__ssm: CFN-deployed EC2+SSM estates never converge (17 checks reach no verdict), and the emulator hands out guest IPs it does not serve

> _Note: this issue was identified against the code base at commit `6596661b7bed7b2c68eacfc83c0e7a703969540b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two net-new root causes in the CloudFormation + EC2 + SSM group. Both are grounded in the failing checks listed per cause; neither is covered by an existing open issue (the nearest, 20261103T200742Z-ec2-ssm-cloudformation-deployed-ec2-ssm-estates-are-unusable-instance.md, is filed under a different service heading and carries other checks' replay keys, and 20261107T075601Z-cloudformation-ec2-ssm-cloudformation-ssm-aws-ssm-maintenancewindowtarget-unrecognised-ec2-ref.md owns only the MaintenanceWindowTarget/sdk-ssm checks).

Cause 1 of 2: a CloudFormation stack that deploys an EC2 instance with an SSM-enabled instance profile never reaches the state the scenario waits on, so 17 checks exhaust the harness cap without ever producing an assertion.
AWS: CreateStack of a VPC + subnet + security group + IAM role/instance profile + AWS::EC2::Instance stack reaches CREATE_COMPLETE, DescribeStacks then exposes the declared Outputs, the launched instance's SSM Agent registers, and ssm:DescribeInstanceInformation lists exactly that instance with PingStatus 'Online' and ResourceType 'EC2Instance'. The same estate then deregisters from SSM on DeleteStack, and AWS::SSM::Association / AWS::SSM::PatchBaseline resources in the stack become describable through ssm:DescribeAssociation / ssm:DescribeAvailablePatches. Each of these checks polls those reads with its own multi-minute budget (e.g. 420 s for the registration poll, 600 s for the stack poll), so a converging estate answers well inside the suite's per-check cap. Recorded behavior only for the registration timing; the CFN and SSM models state the shapes, not the latency.
Emulator: every one of these 17 checks ends with 'Check timed out after 180.0s' — the check reaches no verdict at all, because the stack deploy plus the first SSM read never settle inside the harness cap. Nothing is asserted, so the operation that hangs is not narrowed by the report; the group-wide pattern (17 of 18 checks under this heading, all of them deploy-then-read-SSM shapes) is that the deploy/registration path does not converge. Hypothesis: the stack never reaches a terminal CREATE state, or the instance it creates never registers as an SSM managed node, so the poll loops run to their own deadline.
Why: a client cannot use CloudFormation to stand up an SSM-managed fleet at all — the stack never reports success and the node never appears in DescribeInstanceInformation, so every downstream operation (SendCommand, associations, patch baselines, inventory) is unreachable. Worse, the failure mode is a hang rather than a refusal, so callers and CI block instead of erroring.
Fix: the CloudFormation stack-execution path for EC2/IAM/SSM resource types and the SSM managed-node registration that an instance-profile-carrying instance must trigger (the stack executor's resource provisioners plus the SSM instance-information state). The registration must reach PingStatus 'Online' for an instance whose profile grants AmazonSSMManagedInstanceCore, and the stack must reach a terminal status.

Cause 2 of 2: the emulator announces an instance address that is not the endpoint it serves, so a scenario that follows the address it was handed is refused egress.
AWS: an address EC2 reports for an instance (PrivateIpAddress / PublicIpAddress / PrivateDnsName) is an address that actually carries traffic for that instance, so a scenario that reads an address out of a DescribeInstances/DescribeNetworkInterfaces answer and then connects to it reaches the instance. Recorded behavior only — the EC2 model types these members as strings and states no reachability rule.
Emulator: the replay is refused before any connect: 'simparity.egress.EgressRefused: egress refused: "10.43.1.4" is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on'. The 10.43.1.4 host is a guest address the emulator itself produced for the stack's instance; nothing the emulator serves answers on it.
Why: any client that uses a returned instance address — a security-group reachability probe, a peer-to-peer connectivity test, a userdata script that targets a sibling instance by private IP — is sent to an address the emulator does not serve, so the data-plane claim can never be exercised and the address is misleading rather than merely synthetic.
Fix: the instance/network-interface address representation and the data-plane that must back it (the RunInstances/DescribeInstances address assignment and the emulator's guest networking). An address the emulator reports must be an address it serves, or the operation must not report one.
