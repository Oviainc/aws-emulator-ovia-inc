# AppSync channel-namespace control plane: Get/Update/DeleteChannelNamespace are not gated by identity-based IAM (zero-policy principal succeeds with 200), and CreateChannelNamespace's auth-mode BadRequestException carries the wrong message

> _Note: this issue was identified against the code base at commit `281440c6fd2fb349634dcc135fbec4e15edad452`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetChannelNamespace

## Description
Two distinct root causes on the AppSync Event-API channel-namespace control plane (/v2/apis/{apiId}/channelNamespaces). 2 causes in this issue; BOTH must be closed before submitting. Neither failing check is marked ALREADY FILED or OWNED in the replay report. Related open issues are named per cause below but neither carries these contracts: 20261025T041655Z-appsync-event-api-domain-control-plane-no-identity.md records the missing deny gate for the Api/domain-association operations (its Cause 1) and the CreateChannelNamespace rejection as a NotImplemented stub (its Cause 2) — the channel-namespace read/mutate operations and the message contract below are not recorded anywhere, and the CreateChannelNamespace call now reaches a real handler, so its recorded replay key no longer matches.

=== Cause 1 of 2: no identity-based IAM authorization gate in front of GetChannelNamespace / UpdateChannelNamespace / DeleteChannelNamespace, so an authenticated-but-unauthorized principal is never denied ===
AWS: a principal whose IAM user has NO attached policy is refused by implicit default deny BEFORE the namespace is read or mutated. Smithy (appsync) models AccessDeniedException with httpError 403 on all three operations: GetChannelNamespace (GET /v2/apis/{apiId}/channelNamespaces/{name}), UpdateChannelNamespace (POST same URI) and DeleteChannelNamespace (DELETE same URI). The denial message is rule-derived, not a recorded literal — its fixed text is `User: ` ... ` is not authorized to perform: appsync:` ... ` on resource: ` ... ` because no identity-based policy allows the appsync:` ... ` action`, and its variable parts are taken from the request and from state: the calling principal's ARN, the operation name as the IAM action (`GetChannelNamespace` / `UpdateChannelNamespace` / `DeleteChannelNamespace`), and the channel-namespace ARN `<api apiArn>/channelNamespace/<name>`. A denied UpdateChannelNamespace must also have NO effect on stored state, and the same three calls made with permissioned credentials must still reach the service layer — that is what distinguishes a real gate from a blanket 403.
Emulator: the zero-policy principal's GetChannelNamespace SUCCEEDS with HTTP 200 and returns the full channelNamespace body (apiId, name, subscribeAuthModes, publishAuthModes, tags, channelNamespaceArn, created, lastModified) instead of AccessDeniedException/403; the check aborts on that first unexpected success, and UpdateChannelNamespace/DeleteChannelNamespace are equally ungated. The emulator applies no identity-based authorization decision to these operations at all.
Why: this is an overly-permissive boundary — the most dangerous class of divergence. Any caller holding any credential can read, reconfigure (change publish/subscribe auth modes) or delete another principal's channel namespace. A client built against AWS catches AccessDeniedException to distinguish "you lack permission" from success; here it gets a 200 and silently proceeds, so least-privilege regressions and denial-path code can never be exercised or detected against this emulator.
Fix: the request authorization layer in front of AppSync operation dispatch (sigv4 principal -> IAM policy evaluation -> AccessDeniedException/403 carrying the implicit-deny message shape), which must fire before the channel-namespace handlers run, plus wiring those three handlers into it. This is the same missing component as Cause 1 of 20261025T041655Z-appsync-event-api-domain-control-plane-no-identity.md, but there the stub answered 501 first; here the handlers are implemented and simply ungated, so closing that issue does not close this.
Traces: appsync.access-denied-channel-namespace.

=== Cause 2 of 2: CreateChannelNamespace rejects a mismatched auth mode with the right code but the wrong error message ===
AWS: Smithy CreateChannelNamespace (POST /v2/apis/{apiId}/channelNamespaces) takes subscribeAuthModes/publishAuthModes (AuthModes) and models BadRequestException httpError 400 (plus ConcurrentModificationException 409, ConflictException 409, NotFoundException 404, ServiceQuotaExceededException 402, UnauthorizedException 401, InternalFailureException 500); success is 200. When a requested auth mode is not among the parent Api's eventConfig.authProviders, AWS refuses with 400 BadRequestException and the recorded message `Channel namespace auth type must be present in the API's auth providers.` — that string is entirely FIXED text: it names neither the offending member, nor the auth type, nor the apiId, so nothing in it is interpolated from the request or from state. No namespace is created, and the identical call with an auth mode the parent DOES offer succeeds with 200.
Emulator: the status and error code are now correct (BadRequestException/400), but the message is `subscribeAuthModes specifies authorization mode AWS_IAM, which is not configured as an authorization provider for this API.` — emulator-invented prose that additionally interpolates the member name and the auth type, neither of which AWS includes. The check fails on the message assertion.
Why: the error message is part of the contract. Clients, CDK/CFN error surfacing, and operator tooling match on or log this text; a caller that string-matches AWS's wording to classify a mis-specified auth mode fails to recognize the refusal, and test suites or runbooks written against AWS diverge on an error that is otherwise correctly classified.
Fix: the message construction in the CreateChannelNamespace handler's cross-validation of requested auth modes against the parent Api's eventConfig.authProviders in the appsync service crate (ops/create_channel_namespace.rs) — emit AWS's fixed string verbatim rather than a per-member templated sentence. Cause 2 of the open issue 20261025T041655Z-appsync-event-api-domain-control-plane-no-identity.md asked only that this call stop answering NotImplemented and start refusing with BadRequestException; that part now holds, and this cause is the remaining divergence on the same call.
Traces: appsync.create-channel-namespace-invalid-auth-mode-rejected.
