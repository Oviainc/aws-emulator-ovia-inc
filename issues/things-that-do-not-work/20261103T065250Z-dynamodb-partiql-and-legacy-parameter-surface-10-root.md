# DynamoDB PartiQL and legacy-parameter surface: 10 root causes in statement parsing, missing validation, legacy filters, numbers and sets

> _Note: this issue was identified against the code base at commit `ce4f28f15b4841beefbad6c596b9d2158570753e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ExecuteStatement

## Description
Ten net-new root causes in the PartiQL front end and the legacy (non-expression) parameter surface. All ten must be closed before submitting.

Cause 1 of 10: every malformed PartiQL statement collapses to one generic message. AWS: the PartiQL parser reports the DEFECT -- "Statement wasn't well formed, can't be processed: Unexpected token after expression", "Statement wasn't well formed, can't be processed: Expected data manipulation", "Statement wasn't well formed, can't be processed: Expected identifier for simple path", 'Unrecognized function: <name> at <line:col:len>', 'A path may contain at most 2 components in the FROM clause', 'FROM clause may only contain a single table name in data manipulation statements at <line:col:len>', 'Operator or function requires a document path; operator or function: attribute_exists', and inside ExecuteTransaction 'Validation failed in TransactStatements[<i>]: ...' (Smithy: ExecuteStatement.Statement is PartiQLStatement @length 1..8192; refusals are ValidationException, 400). The fixed text is the AWS sentence for that defect class; the variable parts are the offending token/function name, the statement index and the source position taken from the request. Emulator: every one of them is "Invalid Statement: statement wasn't well formed, could not be parsed" (or, for a write through an index qualifier, 'This operation is not supported on an index'). Why: a client cannot tell a quoting mistake from an unknown function, and the ExecuteTransaction form loses the statement index. Fix: the PartiQL parser's diagnostics in the ExecuteStatement/BatchExecuteStatement/ExecuteTransaction handlers. Checks: dynamodb.batch-execute-statement-malformed-slot-siblings-execute, dynamodb.execute-statement-extra-token-after-complete-statement-rejected, dynamodb.execute-statement-malformed-literal-rejected, dynamodb.execute-statement-missing-clause-rejected, dynamodb.execute-statement-quoting-rules, dynamodb.execute-statement-undefined-function-and-projection-function-rejected, dynamodb.execute-statement-function-requires-document-path-or-operand-count-rejected, dynamodb.execute-transaction-malformed-statement-rejects-whole-call, dynamodb.partiql-from-clause-path-arity-rejected, dynamodb.partiql-unknown-index-qualifier-rejected, dynamodb.partiql-write-through-index-qualifier-rejected.

Cause 2 of 10: PartiQL statements AWS refuses are ACCEPTED with HTTP 200. AWS refuses: a relational operator over a complex-type operand; a WHERE filter on an attribute the named GSI (INCLUDE) or LSI (KEYS_ONLY) does not project; a SELECT through an LSI qualifier whose filter is unprojected; size()/attribute_type over an incompatible type; and a parameter whose N value is non-numeric or out of range. Emulator: all return 200, some with Items. Why: a query that AWS rejects silently returns an empty or wrong result set, so the caller reads absence of data as absence of rows. Fix: PartiQL planner/validation (index projection and operand typing) in the ExecuteStatement handler. Checks: dynamodb.partiql-relational-operators-reject-complex-type-operands, dynamodb.partiql-select-gsi-include-projection-nonprojected-filter-rejected, dynamodb.partiql-select-lsi-keys-only-nonprojected-filter-and-in-between-key-forms, dynamodb.partiql-select-through-lsi-qualifier, dynamodb.partiql-size-and-attribute-type-select-exact-sets-and-reject-incompatible-size, dynamodb.execute-statement-rejects-non-numeric-n-parameter, dynamodb.execute-statement-rejects-out-of-range-n-parameter.

Cause 3 of 10: PartiQL semantic-validation messages diverge. AWS has specific texts for a number over 38 significant digits, a parameter-count/key-type mismatch, and a transaction read statement that does not address exactly one item. Emulator: '1 validation error detected: Attempting to store more than 38 significant digits in a Number', 'Invalid Statement: the number of parameters in the request and in the statement do not match', and 'a read statement in a transaction must address one item of the table: its WHERE clause states an equality on every key attribute, and its source is the table rather than an index' -- prose the service does not emit. Fix: the PartiQL validation messages. Checks: dynamodb.execute-statement-number-precision-in-update-set-and-key-equality, dynamodb.execute-statement-parameter-count-and-key-type-mismatch-rejected, dynamodb.execute-transaction-index-select-top-level-validation-not-cancellation.

Cause 4 of 10: PartiQL projection and NULL semantics. AWS: projecting a list element returns it keyed by the PATH ('l[1]'), and 'IS NULL' is true only for a NULL-typed attribute -- a MISSING attribute is not NULL. Emulator: returns the element keyed by the bare attribute name ('l'), and 'IS NOT NULL' counts items that lack the attribute (returned user-004, website-001..003 where only user-004 is NULL-typed). Why: readers get a differently shaped item and a wrong row set. Fix: PartiQL projection/predicate evaluation. Checks: dynamodb.partiql-select-projects-nested-map-and-list-paths, dynamodb.ddb-sfa-partiql-is-not-null-counts-a-missing-attribute-as-not-null.

Cause 5 of 10: BatchExecuteStatement response slots do not carry the per-slot envelope. AWS: each successful slot echoes TableName alongside the item/returned values. Emulator: the UPDATE slot returned only {'Item': {...}} with no TableName. Fix: BatchExecuteStatement's response serializer. Check: dynamodb.batch-execute-statement-returning-update-vs-delete-rejected.

Cause 6 of 10: legacy ConditionalOperator/Expected/ScanFilter refusal messages diverge. AWS: 'ConditionalOperator can only be used together with ScanFilter' is NOT the message when ScanFilter is present but under-populated -- AWS requires two conditions and says so; 'One or more parameter values were invalid: Invalid number of argument(s) for the NOT_NULL ComparisonOperator'; the mixing error names EVERY legacy parameter in the request ('Non-expression parameters: {ScanFilter, ConditionalOperator}'); and a ConditionalOperator enum violation is reported where the emulator reports the generic enum text. Emulator: 'ConditionalOperator can only be used together with ScanFilter' / 'ConditionalOperator can only be used together with Expected' for the two-condition cases, 'One or more parameter values were invalid: NOT_NULL takes 0 value(s) in AttributeValueList, got 1', and names only {ScanFilter} in the mixing error. Fix: legacy-parameter validation in Scan/Query/PutItem/UpdateItem. Checks: dynamodb.conditionaloperator-enum-error-precedes-nesting-depth-in-legacy-expected, dynamodb.ddb-sfa-legacy-not-null-with-a-value-list-rejected, dynamodb.scan-query-conditional-operator-needs-two-filter-conditions-rejected, dynamodb.write-conditional-operator-needs-two-expected-conditions-rejected, dynamodb.scan-filter-conditional-operator-document-value-equality, dynamodb.legacy-expected-exists-value-comparator-matrix, dynamodb.ddb-ss-scan-filter-mixed-with-filter-expression-rejected, dynamodb.scan-query-legacy-and-expression-mixing-names-every-parameter-rejected.

Cause 7 of 10: legacy filter SEMANTICS on missing attributes and binary values are wrong. AWS: NOT_CONTAINS and NOT_NULL exclude every item that lacks the attribute (unlike NE), and CONTAINS over a B value compares unsigned bytes, so 0x00 is found as a subsequence. Emulator: NOT_CONTAINS returned the items missing 'status' (user-001, user-003, website-001..003 where only user-001 and user-003 qualify), NOT_CONTAINS on a missing attribute returned ['no-attr'], and CONTAINS 0x00 returned []. Why: filters silently return the wrong rows -- no error surfaces. Fix: legacy ScanFilter/QueryFilter evaluation. Checks: dynamodb.ddb-sfa-legacy-scan-filter-not-null-and-null-match-the-expression-functions, dynamodb.scan-filter-ne-and-not-contains-on-missing-attribute, dynamodb.scan-filter-binary-attribute-unsigned-byte-order.

Cause 8 of 10: several legacy/expression defects are not validated at all. AWS refuses: begins_with with a non-string operand in a ScanFilter; a BatchGetItem mixing ProjectionExpression with legacy projection plus Query KeyConditions with expressions; a non-numeric N operand; a bare reserved word as a sort key in a key condition; attribute_type with an unknown type name; and IN with 101 operands. Emulator: all succeed (HTTP 200). Fix: the legacy-parameter and expression operand validation. Checks: dynamodb.scan-filter-begins-with-non-string-operand-rejected, dynamodb.null-false-batchget-mixed-projection-and-query-keyconditions-with-expressions, dynamodb.ddb-frc-non-numeric-number-operand-rejected, dynamodb.ddb-sfa-bare-reserved-sort-key-timestamp-in-key-condition-rejected, dynamodb.ddb-ss-attribute-type-with-an-unknown-type-name-rejected, dynamodb.ddb-ss-in-operator-with-101-operands-rejected.

Cause 9 of 10: N-value limits are not enforced, and the overflow message diverges. AWS: a Number carries at most 38 significant digits with a bounded exponent and is canonicalised on write; out-of-range values are refused with ValidationException. Emulator: accepts the out-of-range canonicalisation/precision/zero-exponent cases with HTTP 200, and for the overflow path answers '1 validation error detected: Number overflow. Attempting to store a number with magnitude larger than supported range' rather than AWS's text. Why: a value AWS would never store round-trips, then diverges once AWS is in the loop. Fix: the AttributeValue N parser/validator in the item write path. Checks: dynamodb.number-canonicalization-boundaries, dynamodb.number-precision-limited-to-38-digits, dynamodb.zero-with-out-of-range-exponent-rejected, dynamodb.update-item-malformed-or-overflowing-number-rejected.

Cause 10 of 10: set validation is missing. AWS refuses a set (SS/NS/BS) containing a duplicate or empty member -- in an item, in a condition value and inside a transaction. Emulator: accepts the duplicate-member condition value (HTTP 200) and, where it does refuse, answers '1 validation error detected: Invalid ConditionExpression: Attribute name is a reserved keyword; reserved keyword: other' -- an unrelated defect. Fix: AttributeValue set validation shared by the item and condition paths. Checks: dynamodb.empty-and-duplicate-set-members-rejected-for-ss-ns-and-bs, dynamodb.duplicate-set-members-in-condition-key-and-transact-rejected.
