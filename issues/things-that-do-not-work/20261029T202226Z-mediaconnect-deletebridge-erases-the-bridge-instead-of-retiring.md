# MediaConnect: DeleteBridge erases the bridge instead of retiring it DELETED, DescribeFlowSourceMetadata answers 200 on a non-ACTIVE flow, RemoveFlowSource's last-source refusal uses non-AWS prose, and no UDP ingest listener exists

> _Note: this issue was identified against the code base at commit `0d251cb15d5c6a3e8a766cb6c72620a30f43ef7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteBridge

## Description
Four distinct root causes found replaying the behavioral suite against the MediaConnect emulator (15/28 checks pass). All four belong to service `mediaconnect`. Checks the replay report marked OWNED by the open issue 20261022T132818Z-mediaconnect-router-interface-union-payload-rejected-no-flow.md (router-input-lifecycle, router-output-lifecycle, take-router-input-routes-and-unroutes, take-router-input-routing-scope-mismatch-rejected, the three flow-state-change/EventBridge checks, start-flow-missing-source-rejected, batch-get-router-input-arn-limit-exceeded-rejected) are NOT included here.

=== Cause 1 of 4: DeleteBridge removes the bridge record, so DescribeBridge answers 404 afterwards instead of reporting the bridge in terminal BridgeState DELETED ===
AWS: Smithy model `services/service-com-amazonaws-mediaconnect-mediaconnect/smithy-model/com-amazonaws-mediaconnect-mediaconnect.json` — DeleteBridge (DELETE /v1/bridges/{BridgeArn}, success 200, output {bridgeArn}); DescribeBridge (GET /v1/bridges/{BridgeArn}, success 200, output {bridge: Bridge}), modelled errors include NotFoundException (404) and BadRequestException (400). Recorded behavior: a deleted bridge is a persistent tombstone, not a removed resource — after DeleteBridge, DescribeBridge keeps answering HTTP 200 with `Bridge.BridgeState == "DELETED"`, and that terminal state does not revert across repeated reads. The bridge is nevertheless unusable: the same UpdateBridge call that succeeded while the bridge was STANDBY is then refused HTTP 400 `BadRequestException` with the message `Validation failed:\nYou cannot update a bridge unless it is in STANDBY.` (that whole string is fixed text for this error class — it carries no value taken from the request or from state).
Emulator: `src/ops/delete_bridge.rs` drops the record outright — `store.bridges.remove(&input.bridge_arn)` at line 228, with a comment asserting "nothing in the model asks a deleted bridge to stay describable". The following DescribeBridge therefore takes the not-found branch of `src/ops/describe_bridge.rs` (lines 169-174) and answers HTTP 404 `NotFoundException` with message `Not found: <the requested bridge ARN>`. The bridge-lifecycle check dies there (`botocore.errorfactory.NotFoundException: An error occurred (NotFoundException) when calling the DescribeBridge operation: Not found: arn:aws:mediaconnect:<region>:<account>:bridge:<id>:<name>`), so the post-delete UpdateBridge refusal and its message are never reached either.
Why: a client that reads a bridge's lifecycle after deletion — to confirm the delete settled, to tell a deleted bridge apart from one that never existed, or to show the terminal state in an inventory — gets a 404 where AWS gives it 200/DELETED, and must special-case NotFound as "probably deleted". It is also inconsistent inside this very service: a gateway's terminal GatewayState DELETED stays readable, as does the DELETED bridge state the crate's own UpdateBridgeState calls irreversible, so delete semantics differ per resource.
Fix: the DeleteBridge handler and the bridge record in state — retire the bridge into the terminal `DELETED` bridge state (the same way DeleteGateway settles a gateway) and keep it resolvable by DescribeBridge, instead of removing it from the store; UpdateBridge must then refuse a DELETED bridge with the STANDBY-precondition BadRequestException.
Traces: mediaconnect.bridge-create-and-delete-lifecycle.

=== Cause 2 of 4: DescribeFlowSourceMetadata succeeds with HTTP 200 on a flow that is not ACTIVE, instead of refusing it with BadRequestException ===
AWS: Smithy model — DescribeFlowSourceMetadata, GET /v1/flows/{FlowArn}/source-metadata, success 200, output {flowArn, messages, timestamp, transportMediaInfo, ndiInfo}; modelled client errors include BadRequestException (400), whose documentation says it "is thrown if the request contains a semantic error. The precise meaning depends on the API, and is documented in the error message". Recorded behavior: the call is gated on the flow's own Status, not on real ingest traffic — on a freshly created STANDBY flow it is refused with HTTP 400 `BadRequestException` and the message `Bad request: The flow must be in ACTIVE state to perform this action` (fixed text for this error class; no request- or state-derived values in it), while DescribeFlow for the same flow succeeds. The IDENTICAL call then succeeds with HTTP 200 once the flow reaches ACTIVE, returning `TransportMediaInfo` (with an empty Programs list) even though no media was ever sent.
Emulator: `src/ops/describe_flow_source_metadata.rs` applies no status gate at all. It resolves the flow and returns HTTP 200 with `Messages=[{Code: "FLOW_NOT_RUNNING", Message: "The flow is STANDBY; source metadata is reported only while the flow is ACTIVE and receiving content.", ResourceName: "source1"}]` (built by `source_metadata_messages`, lines 265-292). The same handler hard-codes `transport_media_info: None` (line 235), so the ACTIVE half of the contract diverges too: once the flow is ACTIVE the response is a 200 with `Code: NO_SOURCE_METADATA` and NO `TransportMediaInfo` member, where AWS returns TransportMediaInfo with an empty Programs list.
Why: the refusal is laundered into a success. A client cannot branch on BadRequestException to learn "start the flow first" — it gets a 200 and must parse free-form `Messages[].Code` prose that AWS does not use this way — and a client that reads `TransportMediaInfo` off an ACTIVE flow finds the member absent and sees a KeyError/None where AWS always supplies the structure.
Fix: the DescribeFlowSourceMetadata handler — refuse with the modelled BadRequestException while the stored flow's status is not ACTIVE, and project a TransportMediaInfo (empty Programs) from state for an ACTIVE flow.
Traces: mediaconnect.describe-flow-source-metadata-not-yet-available.

=== Cause 3 of 4: RemoveFlowSource's last-source refusal carries emulator-authored prose, not AWS's message for that error class ===
AWS: Smithy model — RemoveFlowSource, DELETE /v1/flows/{FlowArn}/source/{SourceArn}, success 202, output {flowArn, sourceArn}; modelled errors include BadRequestException (400) and NotFoundException (404). Recorded behavior: removing a flow's ONLY source is refused with HTTP 400 `BadRequestException` and the message `Validation failed:\nYour request removes the only source that is assigned to this flow. Each flow must have at least one source. Review the existing source and make changes as needed. Your request removes all sources that are assigned to this flow.` Every word of that message is FIXED text for this error class — it interpolates nothing from the request or from state (notably, no ARN and no source name). The flow keeps its source, and once a second source exists the identical call succeeds.
Emulator: the status and the error code already match, and the `Validation failed:\n` envelope is now rendered, but the detail is the crate's own sentence: `Validation failed:\nFlow <flow ARN> has only one source. A source can be removed only from a flow that has more than one.` — see `src/ops/remove_flow_source.rs` lines 206-215, which formats `input.flow_arn` into the detail. So the emulator both uses different wording and injects a request-derived ARN into a message AWS states without one.
Why: operators and tooling that match MediaConnect's documented refusal text (log greps, runbook assertions, user-facing error surfacing, tests written against real AWS) do not recognise this refusal; and because the message is the only place AWS documents what a BadRequestException means for this operation, a client cannot tell the last-source rule apart from the other BadRequestException cases this operation can return. Note this cause is the residue of Cause 6 of open issue 20261022T132818Z-mediaconnect-router-interface-union-payload-rejected-no-flow.md: the envelope prefix it asked for is now emitted, but the message body still diverges from AWS's fixed text for this class.
Fix: the RemoveFlowSource handler's last-source guard — emit AWS's message for that error class verbatim through the service's shared error-message helper, with no ARN interpolated.
Traces: mediaconnect.remove-only-flow-source-rejected.

=== Cause 4 of 4: an ACTIVE flow advertises an ingest endpoint that nothing listens on, and Source.PeerIpAddress never populates ===
AWS: recorded behavior only — MediaConnect's data plane is raw UDP, not an API call, so the Smithy model describes none of it. Once a flow is ACTIVE, MediaConnect binds the endpoint it advertises on DescribeFlow as `Source.IngestIp`:`Source.IngestPort`, and on observing real inbound UDP packets from a sender it records that sender's address on the flow's `Source.PeerIpAddress`. No conformant RTP/MPEG-TS payload is required — only that something is actually listening on the wire.
Emulator: UDP datagrams sent from a plain socket to the ACTIVE flow's own advertised IngestIp:IngestPort are never observed; DescribeFlow's `Source.PeerIpAddress` never appears, and the check spins until the harness timeout (`Check timed out after 60.0s`). The harness verified up front that it can open a UDP socket and that it egresses from a single CIDR, so this is not a runner limitation: the emulator announced an endpoint it does not serve. The check's trailing assertion — that CreateFlow with `Source.Protocol='udp'` is refused with BadRequestException naming the protocol invalid — is unverified here because the run never gets past the ingest poll.
Why: the emulator accepts every control-plane call and advertises an ingest endpoint that does not exist, so any client doing a real ingest round trip (or asserting the peer address it observes) hangs indefinitely instead of failing fast; there is no way to distinguish "nothing is sending" from "nothing is listening". This cause is the same defect described as Cause 5 of open issue 20261022T132818Z-mediaconnect-router-interface-union-payload-rejected-no-flow.md; the replay report did not mark this check as owned by it (its recorded replay key no longer matches the current failure frame), so it is re-filed here with the current evidence rather than dropped.
Fix: the flow data plane — bind the advertised ingest endpoint when a flow becomes ACTIVE and record the observed sender on `Source.PeerIpAddress` in the flow store, driven from the flow-start path.
Traces: mediaconnect.native-media-ingest-udp-round-trip.
