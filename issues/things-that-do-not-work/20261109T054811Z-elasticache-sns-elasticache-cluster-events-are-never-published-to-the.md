# ElastiCache cluster events are never published to the configured SNS topic, and NotificationTopicStatus='inactive' deletes the topic binding instead of deactivating it (2 causes)

> _Note: this issue was identified against the code base at commit `37c80e55e89881237cfb2c32173143a5950fe67d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCacheCluster

## Description
Two independent root causes on the IMPLEMENTED ElastiCache cache-cluster surface, both exercised by the single failing check elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber. Together they mean the documented ElastiCache -> SNS event integration does not exist in this emulator.

Note on existing issues: open issue 20261108T102114Z-elasticache-sns-elasticache-cluster-event-notifications-are-never-published-to.md describes these same two causes and carries this same check id, but the replay did NOT mark this check OWNED or ALREADY FILED, so it is re-filed here as instructed; whoever fixes either issue should close both together. Open issue 20261023T155010Z-elasticache-control-plane-is-unusable-end-to-end.md also lists this check id, but its cause is CreateCacheSubnetGroup refusing real EC2 subnet ids — a different operation, and the replay no longer dies there (the check now provisions an available cluster and hangs on notification delivery).

Cause 1 of 2: a cache cluster carrying a NotificationTopicArn publishes NOTHING to that SNS topic; the event only reaches the local event log.
AWS: Smithy (com.amazonaws.elasticache#AmazonElastiCacheV9): CreateCacheCluster$NotificationTopicArn — "The Amazon Resource Name (ARN) of the Amazon Simple Notification Service (SNS) topic to which notifications are sent. The Amazon SNS topic owner must be the same as the cluster owner"; ModifyCacheCluster$NotificationTopicStatus — "The status of the Amazon SNS notification topic. Notifications are sent only if the status is active. Valid values: active | inactive"; DescribeCacheClusters projects CacheCluster$NotificationConfiguration as {TopicArn, TopicStatus}. The publish itself is recorded behavior only: while NotificationConfiguration.TopicStatus is 'active', each cluster event ElastiCache records for that cluster is ALSO published to the named topic, so an SQS subscriber of that topic receives an SNS Notification envelope (Type='Notification', TopicArn = the configured topic) whose Message carries the documented `ElastiCache:<Event>` event name together with the cluster id (a node reboot produces the ElastiCache:CacheNodeReboot* events). Fixed parts: the envelope shape, Type='Notification', the `ElastiCache:` prefix. Variable parts taken from the request/state: the topic ARN, the cluster id, the event name and timestamps.
Emulator: the ARN is stored and nothing else happens. create_cache_cluster.rs copies input.notification_topic_arn onto the cluster record and calls store.record_event(..); reboot_cache_cluster.rs only drives the node/cluster transition and states that the reboot's event "belongs to DescribeEvents"; there is no SNS Publish anywhere on the elasticache event path, and state.rs says so beside the hardcoded topic status ("The emulator models no SNS subscription lifecycle"). DescribeEvents does record the event, so the producer side is observable while the delivery side is permanently silent and the subscriber queue's ApproximateNumberOfMessages stays 0 forever.
Why: a client wiring cluster events to SNS (the documented ECEvents.SNS pattern, usually SNS -> SQS or SNS -> Lambda for alerting) is told the configuration is active and then never receives a single message — no error, just silence; it never learns a node was rebooted, replaced, or that provisioning finished.
Fix: the elasticache cluster event path — where a cluster event becomes real (crate::state record_event / the cluster record's settle, and the create / modify / reboot / delete handlers that drive it) must publish the event to the cluster's configured topic whenever that topic's status is active, not merely append to the event log.
Traces: elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber (arm A: after RebootCacheCluster the check waits for a matching notification through its own topic while DescribeEvents already shows the reboot).

Cause 2 of 2: ModifyCacheCluster with NotificationTopicStatus='inactive' CLEARS the stored topic ARN, and NotificationConfiguration.TopicStatus is a hardcoded constant 'active', so an inactive notification configuration is unrepresentable and the binding is destroyed.
AWS: Smithy: ModifyCacheCluster$NotificationTopicStatus — "The status of the Amazon SNS notification topic. Notifications are sent only if the status is active. Valid values: active | inactive"; CacheCluster$NotificationConfiguration carries BOTH TopicArn and TopicStatus. Recorded behavior: after ModifyCacheCluster(NotificationTopicStatus='inactive', ApplyImmediately=true) the cluster STILL reports NotificationConfiguration.TopicArn = the same topic with TopicStatus='inactive' (deactivated, not detached); events keep being recorded and are not delivered; a later ModifyCacheCluster(NotificationTopicStatus='active') flips the same configuration back to 'active' and delivery resumes without the caller re-supplying the ARN.
Emulator: modify_cache_cluster.rs (lines 626-633 of this checkout) does `if input.notification_topic_status.as_deref() == Some("inactive") { cluster.notification_topic_arn = None; }` — the binding is deleted — and state.rs (lines 856-859) defines `NOTIFICATION_TOPIC_STATUS: &str = "active"` as the only status a configured topic is ever reported in, so TopicStatus can never read back 'inactive'. A client polling DescribeCacheClusters for TopicStatus='inactive' therefore never converges (it sees 'active' or no NotificationConfiguration at all), and re-activation is impossible because the ARN is gone.
Why: pausing notifications is the documented way to silence a cluster temporarily; here it silently unbinds the topic and loses the configuration, so the state the client waits for never appears and the resume step has nothing to resume. Two observable requirements are broken: the readback of TopicStatus, and the persistence of TopicArn across a deactivate/reactivate cycle.
Fix: the cache-cluster record and its projection — store the notification topic STATUS beside the ARN on the cluster record and project it into NotificationConfiguration.TopicStatus (replacing the fixed NOTIFICATION_TOPIC_STATUS constant), and make the ModifyCacheCluster handler set that status instead of clearing notification_topic_arn; Cause 1's publish gate then reads this status.
Traces: elasticache__sns.cache-cluster-event-notification-reaches-the-sns-subscriber (arm B sets NotificationTopicStatus='inactive' and polls NotificationConfiguration.TopicStatus for 'inactive'; arm C sets it back to 'active' and demands delivery resume on the same topic).

- The check builds a VPC/subnets/security group/cache subnet group, an SNS topic with an SQS subscriber (policy scoped to that topic), then CreateCacheCluster(..., NotificationTopicArn=<topic>), waits for CacheClusterStatus='available' and asserts NotificationConfiguration.TopicStatus='active' with TopicArn = its topic — which the emulator satisfies from the hardcoded constant.
- Arm A reboots the node (RebootCacheCluster with the node ids DescribeCacheClusters(ShowCacheNodeInfo=true) reports) and waits up to 600s for a notification carrying the cluster id through its own topic, while asserting the reboot IS in ElastiCache's own DescribeEvents log. The emulator records the event and publishes nothing, so this wait cannot terminate: the queue's ApproximateNumberOfMessages stays 0. The harness kills the check at its 180s ceiling inside that wait.
- Arm B would then set NotificationTopicStatus='inactive' and poll NotificationConfiguration.TopicStatus for 'inactive'. modify_cache_cluster.rs clears notification_topic_arn and state.rs reports TopicStatus as the constant 'active', so that poll also cannot terminate, and arm C's re-activation has no ARN left to re-activate.
