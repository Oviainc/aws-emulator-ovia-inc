# Answer ChoiceAnswers projection, improvement-plan details and two lens-alias refusal messages diverge in wellarchitected

> _Note: this issue was identified against the code base at commit `98c28633a50c37c08c8640cea9cea1eb68cf9263`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateAnswer

## Description
This bundle has 4 net-new causes, all in service wellarchitected, grounded in 4 failing behavioral checks of suite simparity-behavioral-aws-v1. Cause 1 is the per-choice answer projection on UpdateAnswer, cause 2 the DisassociateLenses default-lens refusal message, cause 3 the missing per-choice improvement-plan detail on ListLensReviewImprovements, cause 4 the AssociateLenses refusal message for an unpublished custom lens. These four checks now get PAST the custom-lens publish path that open issue 20261029T223409Z-wellarchitected-custom-lens-publish-path-empty-selection-risk-derivation.md (cause 1) and fixed issue 20261029T192731Z-wellarchitected-custom-lens-import-publish-version-and-export-chain.md describe, so none of the divergences below is covered by an existing issue; each is a new, deeper failure point on the same checks.

Cause 1 of 4: UpdateAnswer's Answer$ChoiceAnswers reports EVERY choice of the question, including the unselected ones, and omits Reason and Notes from each entry.
AWS: Smithy: Answer$ChoiceAnswers -> list<ChoiceAnswer>, documented as 'A list of selected choices to a question in your workload'; ChoiceAnswer{ChoiceId (@length 1..64), Status -> ChoiceStatus enum [SELECTED, NOT_APPLICABLE, UNSELECTED], Reason -> ChoiceReason enum [OUT_OF_SCOPE, BUSINESS_PRIORITIES, ARCHITECTURE_CONSTRAINTS, OTHER, NONE], Notes (@length max 250)}; UpdateAnswer PATCH /workloads/{WorkloadId}/lensReviews/{LensAlias}/answers/{QuestionId}, code 200, output UpdateAnswerOutput{WorkloadId, LensAlias, LensArn, Answer}. Recorded behavior: after UpdateAnswer selects a strict subset of a question's choices, the 200 response's Answer.ChoiceAnswers holds one entry PER ANSWERED (selected) choice only — for a two-choice question with one choice selected, exactly one entry, whose ChoiceId is the selected choice, Status is SELECTED, and whose Reason and Notes members are both present and empty. The choices that were not selected are reported only through Answer$Choices/Answer$SelectedChoices, never as ChoiceAnswers entries.
Emulator: returns one ChoiceAnswers entry per choice DEFINED on the question — the unselected ones carried as Status 'UNSELECTED' — and each entry carries only ChoiceId and Status, with Reason and Notes absent.
Why: a client that reads Answer.ChoiceAnswers as the set of answered choices (its documented meaning) counts every choice as answered, so per-choice progress, 'answered' badges and choice-level notes/reason displays are wrong; a client that reads entry['Reason'] or entry['Notes'] raises a KeyError on every entry.
Fix: the ChoiceAnswers projection shared by the UpdateAnswer handler and the answer serializer (GetAnswer/ListAnswers read the same projection) — build it from the recorded per-choice answers, not from the question's full choice set, and emit Reason and Notes on each entry. Related FIXED issue 20261028T195937Z-wellarchitected-getanswer-wrong-behavior.md changed which choice set this projection walks; it did not make the projection selection-only, and this check is not a refusal of that operation, so this is a new defect rather than a reopen.
Traces: wellarchitected.custom-lens-risk-rules-derive-answer-risk.

Cause 2 of 4: DisassociateLenses refuses the default 'wellarchitected' lens with the crate's generic constraint wording instead of AWS's default-lens message.
AWS: DisassociateLenses (Smithy: PATCH /workloads/{WorkloadId}/disassociateLenses, code 200, LensAliases required @length min 1; errors include ValidationException httpError 400) refuses an attempt to detach the Well-Architected Framework lens with 400 ValidationException. Recorded behavior: the message's fixed text is '[Validation] Cannot disassociate default lens: ' ... '.' — its single variable part is the lens alias taken from the request's LensAliases entry (the default lens alias, 'wellarchitected'). The refusal is specific: the same call removes a custom lens successfully.
Emulator: returns the right code (ValidationException) and status (400) but the message '[Validation] Value at LensAliases failed to satisfy constraint: must not name the Well-Architected Framework lens (wellarchitected), which cannot be removed from a workload'.
Why: a client that matches AWS's text to distinguish 'you may not remove the default lens' from any other LensAliases validation failure never matches, and an operator shown the message verbatim sees text AWS never emits.
Fix: the DisassociateLenses handler's default-lens guard — render AWS's message from the submitted alias instead of delegating to the shared 'Value at <member> failed to satisfy constraint' renderer. Related open issue 20261029T192731Z-wellarchitected-validationexception-envelopes-use-generic-framework-text-and-omit.md reports that shared renderer on other members and does NOT carry this check.
Traces: wellarchitected.disassociate-default-lens-rejected.

Cause 3 of 4: ListLensReviewImprovements omits ImprovementSummary$ImprovementPlans entirely for a custom lens review.
AWS: ListLensReviewImprovements (Smithy: GET /workloads/{WorkloadId}/lensReviews/{LensAlias}/improvements, code 200, output ListLensReviewImprovementsOutput{WorkloadId, MilestoneNumber, LensAlias, LensArn, ImprovementSummaries, NextToken}) returns for each at-risk question an ImprovementSummary{QuestionId, PillarId, QuestionTitle, Risk, ImprovementPlanUrl, ImprovementPlans, JiraConfiguration}, where ImprovementPlans -> list<ChoiceImprovementPlan{ChoiceId, DisplayText (@length 1..64), ImprovementPlanUrl}> is documented 'The improvement plan details. This value is only applicable to custom lenses.' Recorded behavior: for an at-risk answer on an imported custom lens, the summary carries ImprovementPlans with one entry per choice of that question that is NOT selected, each entry's ChoiceId being that unselected choice's id and DisplayText being the improvementPlan.displayText the imported lens document declares for that choice.
Emulator: the ImprovementSummary member is absent from the response, so the client's `summary['ImprovementPlans']` raises KeyError: 'ImprovementPlans'. The same summary's QuestionId, PillarId and Risk are correct, so only the per-choice plan detail is missing.
Why: a custom lens's improvement plan is the per-choice remediation text the lens author wrote; a consumer building a remediation list from a custom-lens review gets nothing to show, and any client that dereferences the member (rather than defaulting it) crashes outright.
Fix: the ListLensReviewImprovements handler's improvement-summary construction and its serializer — carry the question's unselected choices and their improvementPlan display text from the stored custom lens document into ImprovementPlans. Related FIXED issue 20261028T163409Z-wellarchitected-listlensreviewimprovements-wrong-behavior.md concerned the ORDER of the improvement list only; the member is still never emitted.
Traces: wellarchitected.improvements-track-at-risk-answers.

Cause 4 of 4: AssociateLenses refuses an imported-but-unpublished (DRAFT) custom lens with the crate's generic constraint wording instead of AWS's lens-resolution message.
AWS: AssociateLenses (Smithy: PATCH /workloads/{WorkloadId}/associateLenses, code 200, LensAliases required @length min 1; errors include ValidationException httpError 400 and ResourceNotFoundException 404) refuses an alias naming a custom lens that has no published version with 400 ValidationException. Recorded behavior: AWS does not distinguish 'not published' from 'not visible to you' — the message's fixed text is '[Validation] Failed to get lenses ' ... '. User might be not authorized to access lens.', its variable part being the lens alias(es) from the request's LensAliases. The refusal must leave the workload untouched (the draft lens must not appear among its lens reviews), and the identical call succeeds once CreateLensVersion publishes a version.
Emulator: returns the right code (ValidationException) and status (400) but the message '[Validation] Value at LensAliases failed to satisfy constraint: member must name a lens with a published version; lens <lensArn> has none until one is published with CreateLensVersion'.
Why: a client branching on AWS's text (to retry, to prompt for permissions, or to publish) never matches, and the emulator discloses a lens-state distinction AWS deliberately does not make, so clients written against the emulator behave differently against AWS.
Fix: the AssociateLenses handler's lens-alias resolution/refusal path — emit AWS's 'Failed to get lenses <aliases>. User might be not authorized to access lens.' message for an unresolvable or unpublished alias instead of the shared 'Value at <member> failed to satisfy constraint' renderer.
Traces: wellarchitected.unpublished-lens-rejected.
