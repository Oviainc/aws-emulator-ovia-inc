# cloudformation: 4 net-new behavioral root causes — custom-resource providers are never invoked, the change-set execute lifecycle never reaches a terminal status, SetTypeConfiguration never accepts an activated Hook's configuration, and a WaitCondition-barriered update is unobservable

> _Note: this issue was identified against the code base at commit `8fdd90c15790d38aa3c5d0088f99b03c79823121`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Four distinct CloudFormation root causes, all surfaced as checks that cannot complete: every wait in each of them is a BOUNDED poll for a CloudFormation status or a provider request, so a check that runs out its window means the awaited thing never arrives. None of these is covered by an already-filed issue; the nearest open issues are named per cause.

=== Cause 1 of 4: a template's custom resource is never invoked — no provider request is ever delivered to its ServiceToken ===
AWS: a resource of type `Custom::<Name>` / `AWS::CloudFormation::CustomResource` names a provider in its `ServiceToken` property (an SNS topic ARN or a Lambda ARN). On every stack operation touching the resource, CloudFormation PUBLISHES a provider request to that token and holds the stack in `CREATE_IN_PROGRESS` / `UPDATE_IN_PROGRESS` until the provider PUTs a response to the request's pre-signed `ResponseURL`. The request carries `RequestType` (`Create`|`Update`|`Delete`), `RequestId`, `StackId`, `LogicalResourceId`, `ResponseURL`, `ResourceProperties`, plus `PhysicalResourceId` and `OldResourceProperties` on an Update/Delete. A provider that answers an Update with a NEW `PhysicalResourceId` makes the resource a replacement: the stack goes to `UPDATE_COMPLETE_CLEANUP_IN_PROGRESS` and a cleanup `Delete` request for the OLD id with the OLD properties is sent; the same id means an in-place update and NO Delete. `Fn::GetAtt` on the resource resolves from the response's `Data`. The custom-resource protocol is not in the Smithy model (recorded behavior only; it is template/provider-protocol behavior, not a modeled operation shape).
Emulator: the provider mailbox is never written. Each of these checks subscribes an SQS queue to the SNS topic it passes as `ServiceToken`, creates the stack, and then blocks reading the queue for the `Create` request; no request ever arrives, so the check runs out its window on the first `_next_request` / mailbox `get`. Consequently no custom resource ever settles, no Update/cleanup-Delete sequence happens, and `Fn::GetAtt` on response data never resolves.
Why: a client cannot use custom resources at all. Every CDK/SAM construct backed by a custom resource (bucket auto-delete, config writers, Lambda-backed lookups) hangs forever instead of completing, and a stack driven by a provider's `FAILED` response never reaches the failure/rollback path clients script against.
Fix: the CloudFormation provisioning path — `services/service-com-amazonaws-cloudformation-cloudformation/src/state.rs` (the `provisioning` module and the pending-status clock, `STATUS_TRANSITION_DELAY` at line 204) needs a provisioner for `Custom::*` / `AWS::CloudFormation::CustomResource` that publishes the provider request to the `ServiceToken` and keeps the stack's transition pending until a response is PUT back, plus the replacement/cleanup-Delete rule on a changed `PhysicalResourceId`.
Traces: cloudformation.continue-update-rollback-on-stable-stack-fails, cloudformation.stack-continue-update-rollback-lifecycle, cloudformation.stack-update-cancel-then-continue-rollback, cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-new-physical-id-on-update-triggers-cleanup-delete-of-old, cloudformation__sns__sqs.xsvc-cloudformation-3-sns-custom-resource-request-roundtrip-and-getatt-returns-response-data

=== Cause 2 of 4: the change-set create/execute lifecycle never reaches the terminal status a client polls for ===
AWS: `CreateChangeSet` answers while the change set is still being computed; `DescribeChangeSet` then reports `Status` settling to `CREATE_COMPLETE`, or to `FAILED` with `StatusReason` exactly "The submitted information didn't contain changes. Submit different information to create a change set." when the submitted revision changes nothing (fixed text; no request-derived parts). `ExecuteChangeSet` on an executable set drives the stack `UPDATE_IN_PROGRESS` -> `UPDATE_COMPLETE`; on a change set in `FAILED` it is refused with HTTP 400 `InvalidChangeSetStatus` (Smithy: `ExecuteChangeSet` errors include `InvalidChangeSetStatusException`, httpError 400, awsQueryError code `InvalidChangeSetStatus`) and the message "ChangeSet [<change-set-ARN>] cannot be executed in its current status of [FAILED]" — fixed text with the change set's own ARN (the `Id` `CreateChangeSet` answered) and its current status substituted in. The refused execute leaves the stack exactly where it was.
Emulator: neither check completes. Their only waits are bounded polls of `DescribeChangeSet` for `{CREATE_COMPLETE, FAILED}` and of `DescribeStacks` for `{CREATE_COMPLETE}` and `{UPDATE_COMPLETE, UPDATE_ROLLBACK_COMPLETE}`, so one of those statuses is never reported: the change set and/or the executed stack is left in a non-terminal status (`CREATE_PENDING` / `*_IN_PROGRESS`) indefinitely. `ops/create_change_set.rs` and `ops/execute_change_set.rs` both claim the settle-on-clock behavior and `state.rs` sets that delay to 500ms, so the status that never arrives is a defect in that settle/transition path, not a slow clock. Nothing beyond the status is gradeable from this run, so the `FAILED` `StatusReason` and the `InvalidChangeSetStatus` refusal above are the contract the fix must also satisfy.
Why: the whole change-set workflow (`aws cloudformation deploy`, CDK, any review-then-execute pipeline) never converges: a client polls `DescribeChangeSet`/`DescribeStacks` forever instead of seeing an executable set, an applied update, or the documented refusal of a no-op set.
Fix: `services/service-com-amazonaws-cloudformation-cloudformation/src/ops/create_change_set.rs` (the pending change-set status it records), `ops/execute_change_set.rs` (the stack transition it opens and its `InvalidChangeSetStatus` refusal) and the `settle` path in `src/state.rs`.
Traces: cloudformation.execute-changeset-rejects-non-executable-status, cloudformation.execute-failed-changeset-rejected

=== Cause 3 of 4: SetTypeConfiguration never accepts a configuration for a Hook type ActivateType has just returned ===
AWS: `SetTypeConfiguration` persists account-level configuration for an ACTIVATED extension and answers a `ConfigurationArn` (Smithy: `SetTypeConfiguration` input `TypeArn` pattern `^arn:aws[A-Za-z0-9-]{0,64}:cloudformation:[A-Za-z0-9-]{1,64}:([0-9]{12})?:type/.+$`, output `ConfigurationArn` of the `type-configuration/` form; modeled errors `TypeNotFoundException` HTTP 404 and `CFNRegistryException` HTTP 400). `BatchDescribeTypeConfigurations` then reads that exact `Configuration`, `Alias` and `Arn` back (Smithy: output `TypeConfigurations`, plus `Errors`/`UnprocessedTypeConfigurations` for identifiers that do not resolve, errors `TypeConfigurationNotFoundException` 404, `CFNRegistryException` 400), and a concurrent write is observed as a whole pre- or post-image, never torn.
Emulator: both checks activate a Guard Hook and then spend their entire window inside a 60-second `SetTypeConfiguration` retry loop that swallows the refusal, i.e. `SetTypeConfiguration` keeps refusing the `TypeArn` that `ActivateType` has just answered for the whole retry window, so the configuration is never written and neither the read-back nor the concurrency assertions are ever reached. Hypothesis: the activated Hook type is not resolvable by the ARN `ActivateType` minted, so `SetTypeConfiguration` answers its `TypeNotFoundException`/`CFNRegistryException` path forever. Related but NOT the same cause, and it does not cover this: 20261025T115133Z-cloudformation-registry-registerpublisher-accepts-a-non-marketplace-seller.md (the public registry's activatable third-party extensions).
Why: a client cannot configure an activated extension at all — Hook configuration (`HookInvocationStatus`, `TargetOperations`, `FailureMode`, `Properties`) can never be set, so no Hook can be turned on and every configuration read-back is empty.
Fix: `services/service-com-amazonaws-cloudformation-cloudformation/src/ops/set_type_configuration.rs` and the registry store it resolves the type through (`src/state.rs`, `registry` module), so the ARN `ActivateType` answers resolves there.
Traces: cloudformation.type-configuration-set-and-batch-describe, cloudformation.concurrent-batch-describe-type-configurations-consistent-snapshot

=== Cause 4 of 4: an update held open by an unsignalled WaitCondition is not observable, so the single-flight refusal cannot be reached ===
AWS: while one `UpdateStack` is in flight — including one whose `AWS::CloudFormation::WaitCondition` with `CreationPolicy.ResourceSignal` has not been signalled — the stack reports `UPDATE_IN_PROGRESS`, the gate resource reports `ResourceStatus` `CREATE_IN_PROGRESS` through `DescribeStackResource`, and a second `UpdateStack` is refused HTTP 400 `ValidationError` with the message "Stack:<stack-ARN> is in UPDATE_IN_PROGRESS state and can not be updated." (fixed text; the stack id and the current status come from the request and state). `UpdateStack` models no state error of its own (Smithy: `UpdateStack` errors are `InsufficientCapabilitiesException`, `TokenAlreadyExistsException`), so this refusal is the service's `ValidationError`. After `SignalResource(Status=SUCCESS)` the held update reaches `UPDATE_COMPLETE` and the previously refused update is accepted.
Emulator: the check never gets past waiting for the gate resource to report `CREATE_IN_PROGRESS` inside an `UPDATE_IN_PROGRESS` stack — that state is never reported, so the competing-update refusal, the "refusal did not disturb the in-flight update" reads and the post-signal completion are all unreachable. Related open issues that do not cover this check: 20261025T150742Z-cloudformation-3-net-new-behavioral-root-causes-an.md (an unsignalled WaitCondition never times out) and 20261025T015306Z-cloudformation-stack-events-and-resource-views-are-incomplete.md (an in-progress stack omits resources).
Why: a client cannot see which resource an operation is blocked on, and cannot rely on CloudFormation serialising stack operations — the usual "is another update running?" guard based on `UPDATE_IN_PROGRESS` plus the per-resource status is unusable.
Fix: the in-progress resource view and the wait-condition barrier in `services/service-com-amazonaws-cloudformation-cloudformation/src/state.rs` (`opening_barriers` / `waiting_for_signals` / `release_wait_conditions`, lines ~1458-1608) and `ops/describe_stack_resource.rs`.
Traces: cloudformation.deep-cloudformation-3-cfn-flight-update-while-wait-condition-barriered-rejected-then-succeeds

## Evidence
Suite: simparity-behavioral-ga-prod-v1, 107/411 passed. All ten checks below are reported as failures with `Error: Check timed out after 60.0s`; every wait inside them is a bounded poll, so the awaited status/request never arrived.

Cause 1 (custom resources never invoked):
- Expected: after `CreateStack`, a provider request with `RequestType="Create"` for the `Custom::*` resource is published to the `ServiceToken` SNS topic (and so into the subscribed SQS queue); on an Update, a request with `RequestType="Update"`, `PhysicalResourceId` = the previous id, `ResourceProperties` = the new properties and `OldResourceProperties` = the previous ones; on a replacement, a cleanup `Delete` for the OLD id with the OLD properties while the stack reports `UPDATE_COMPLETE_CLEANUP_IN_PROGRESS`.
- Actual: the queue stays empty for the whole window — the checks block in `_next_request(sqs, queue_url, timeout_s=90.0)` / `box.get(..., why="Create")` and never observe any request, so no assertion past it is reached.

Cause 2 (change-set lifecycle):
- Expected: `DescribeChangeSet` -> `Status="CREATE_COMPLETE"` for a real diff; for a no-op revision `Status="FAILED"` with `StatusReason="The submitted information didn't contain changes. Submit different information to create a change set."`; `ExecuteChangeSet` of the real diff -> stack `UPDATE_COMPLETE`; `ExecuteChangeSet` of the FAILED set -> HTTP 400, `Code="InvalidChangeSetStatus"`, `Message="ChangeSet [<change-set ARN>] cannot be executed in its current status of [FAILED]"`, stack still `UPDATE_COMPLETE`.
- Actual: neither check gets to the refusal: the polls `_wait_changeset_status(..., {"CREATE_COMPLETE","FAILED"})` (120s budget) and `_wait_stack(..., {"UPDATE_COMPLETE","UPDATE_ROLLBACK_COMPLETE"})` (180s budget) never see a terminal value within the window.

Cause 3 (SetTypeConfiguration):
- Expected: `SetTypeConfiguration(TypeArn=<ARN from ActivateType>, Configuration=<Hook config JSON>, ConfigurationAlias="default")` returns a `ConfigurationArn`, and `BatchDescribeTypeConfigurations` reads back the same `Configuration`, `Alias="default"` and `Arn` = that `ConfigurationArn`, with the unresolvable identifier reported once under `Errors` (`ErrorCode` "404") or `UnprocessedTypeConfigurations`.
- Actual: the whole window is consumed by `_set_type_configuration_with_retry` (a 60s loop that retries on every `ClientError`), so `SetTypeConfiguration` refuses the just-activated type for the entire loop and the read-back is never performed.

Cause 4 (WaitCondition-barriered update):
- Expected: `DescribeStackResource(LogicalResourceId="Gate")` -> `ResourceStatus="CREATE_IN_PROGRESS"` while `DescribeStacks` -> `StackStatus="UPDATE_IN_PROGRESS"`; a competing `UpdateStack` -> HTTP 400 `ValidationError` "Stack:<stack-ARN> is in UPDATE_IN_PROGRESS state and can not be updated." with no effect; after `SignalResource(Status="SUCCESS")` the stack -> `UPDATE_COMPLETE` and `Gate` -> `CREATE_COMPLETE`.
- Actual: `_wait_resource_status(cf, stack_id, "Gate", "CREATE_IN_PROGRESS")` (300s budget) never converges, so the refusal is never exercised.
