# ElastiCache control plane is unusable end to end: subnet groups reject real subnets, cluster-mode parameter groups are missing, and five lifecycle operations never answer (8 causes)

> _Note: this issue was identified against the code base at commit `6d7833292dd9d4a45d8e52e2aa7ee7e5a822f7f5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCacheSubnetGroup

## Description
Eight independent root causes on the IMPLEMENTED ElastiCache control-plane surface. Together they stop a client from building the normal VPC cache topology at all: the subnet group a cluster is placed in cannot be created from the account's own subnets, a cluster-mode replication group cannot be created, and the reshard/migration/serverless lifecycles never answer. Each cause is separate and must be closed separately.

Cause 1 of 8: CreateCacheSubnetGroup refuses every subnet the account actually has, because the handler resolves subnet ids against a synthetic derived catalog instead of the EC2 subnet store.
AWS: Smithy: CreateCacheSubnetGroup takes SubnetIds (SubnetIdentifierList, required) and models InvalidSubnet / SubnetNotAllowedFault / CacheSubnetGroupAlreadyExistsFault (all HTTP 400); recorded behavior is that ids returned by EC2 CreateSubnet in the caller's VPC are ACCEPTED with HTTP 200 and the group is created carrying those subnets and their zones. An id that names nothing is the only case refused (recorded: HTTP 400 InvalidParameterValue, example message "Some input subnets in :[subnet-00000000deadbeef] are invalid.").
Emulator: every freshly created EC2 subnet is refused with HTTP 400 InvalidParameterValue and the recorded example message "Some input subnets in :[subnet-00000000000000020, subnet-00000000000000021] are invalid." The cause is visible in the handler: it calls crate::state::resolve_subnet(&region, id), and that function only matches the three sha256-derived default-VPC subnet ids that crate::state::region_subnets(region) mints for the Region; it never consults the EC2 service's subnet store. The doc comment on resolve_subnet states the assumption explicitly ("EC2's own subnet operations still answer 501 in this emulator; when they are implemented, this is the one place that has to start consulting the stored subnets") — EC2 CreateSubnet is now implemented and mints subnet-00000000000000NN ids, so the assumption is stale.
Why: this is the first call of every VPC cache topology. A client that creates a VPC, subnets and then a cache subnet group is blocked before it ever reaches a cluster, and 19 checks across five service combinations die on this single call. It is also a REGRESSION risk marker: open issue 20261022T193451Z-elasticache-cache-cluster-subnet-group-validation-is-over.md asked for this validation to exist (its Cause 1), and the validation that was added now rejects valid input.
Fix: the subnet resolution used by the CreateCacheSubnetGroup handler — crate::state::resolve_subnet / region_subnets in the elasticache crate — must resolve a subnet id against the subnets EC2 holds (and keep refusing ids that name nothing), not against a derived per-Region list.

Cause 2 of 8: the cluster-mode default cache parameter groups (default.<family>.cluster.on) are not in the seeded catalog, so no cluster-mode-enabled replication group can be created.
AWS: Smithy: CreateReplicationGroup takes CacheParameterGroupName and models CacheParameterGroupNotFoundFault (code CacheParameterGroupNotFound, HTTP 404). Recorded behavior: the service publishes BOTH a plain default and a cluster-mode-on default for every Redis/Valkey family (default.redis7 AND default.redis7.cluster.on), and naming the .cluster.on group on CreateReplicationGroup succeeds with HTTP 200.
Emulator: HTTP 404 CacheParameterGroupNotFound, recorded example message "CacheParameterGroup default.redis7.cluster.on not found." The group simply does not exist in the seeded catalog.
Why: cluster mode is selected AT CREATION through this parameter group; without it a client cannot create a sharded replication group, and every reshard, global-datastore and shard-state-machine flow is unreachable.
Fix: the seeded default-parameter-group catalog in the elasticache state bootstrap (add the .cluster.on default per family and the description/ARN convention). NOTE: this is the behavioral manifestation of Cause 4 of the still-open wire issue 20261023T062907Z-elasticache-catalog-describes-serve-synthesized-data-instead-of.md, which carries no behavioral replay keys; closing one should close both, and the check ids below are the behavioral keys that issue lacks.
Traces: elasticache.global-replication-group-lifecycle-full, elasticache.increase-node-groups-below-current-rejected, elasticache.shard-reconfiguration-state-machine.

Cause 3 of 8: CreateReplicationGroup refuses AutomaticFailoverEnabled=true whenever ReplicasPerNodeGroup is omitted.
AWS: Smithy: CreateReplicationGroup models InvalidParameterCombinationException (code InvalidParameterCombination, HTTP 400); NumNodeGroups, ReplicasPerNodeGroup and AutomaticFailoverEnabled are all optional (IntegerOptional/BooleanOptional). Recorded behavior: CreateReplicationGroup(Engine=redis, CacheNodeType=cache.t3.micro, NumNodeGroups=2, AutomaticFailoverEnabled=true) with NO ReplicasPerNodeGroup is ACCEPTED with HTTP 200 — the service applies the mode-appropriate replica default and the group settles available with 2 shards.
Emulator: HTTP 400 InvalidParameterCombination with the recorded example message "AutomaticFailoverEnabled requires at least one replica in every node group (shard) to promote.", so the create never happens.
Why: this is the documented way to ask for a cluster-mode group with failover; a client that omits a replica count (as the AWS CLI examples do) is refused input the service accepts, and the whole shard-configuration surface behind it is unreachable.
Fix: the CreateReplicationGroup handler's AutomaticFailover/replica defaulting — derive the default ReplicasPerNodeGroup for the requested topology before the combination check, instead of validating against an absent member.
Traces: elasticache.modify-replication-group-shard-configuration-invalid-rejected, elasticache.shard-configuration-resize-transitions.

Cause 4 of 8: DeleteCacheSubnetGroup (and ModifyCacheSubnetGroup) are unimplemented and answer the scaffold's NotImplemented.
AWS: Smithy: DeleteCacheSubnetGroup models CacheSubnetGroupNotFoundFault (code CacheSubnetGroupNotFoundFault, HTTP 400) and CacheSubnetGroupInUse; recorded behavior for a name that does not exist is that fault, example message "Cache Subnet Group <name> does not exist.", and for a name that does exist an empty 200 that removes the group.
Emulator: answers code NotImplemented ("operation ... is scaffolded but not implemented in this emulator") for both the delete and the modify.
Why: a subnet group can be created but never removed or re-described, so a client cannot clean up or reconfigure its cache network, and the not-found contract on the delete path is absent.
Fix: implement the DeleteCacheSubnetGroup and ModifyCacheSubnetGroup handlers over the existing cache_subnet_groups store.
Traces: elasticache.cache-subnet-group-invalid-subnet.

Cause 5 of 8: ModifyReplicationGroupShardConfiguration is unimplemented and answers NotImplemented.
AWS: Smithy: ModifyReplicationGroupShardConfiguration takes ReplicationGroupId/NodeGroupCount/ApplyImmediately (all required) and models InvalidParameterValueException (code InvalidParameterValue, HTTP 400), InvalidParameterCombinationException, InvalidReplicationGroupStateFault and ReplicationGroupNotFoundFault (404). Recorded behavior: a scale-in that names neither NodeGroupsToRemove nor NodeGroupsToRetain is refused with HTTP 400 (example message "Node groups to remove or node groups to retain must be specified for a scale-in call but not both."), a cluster-mode-disabled group is refused with InvalidParameterValue, and a consistent scale-out is accepted with 200.
Emulator: every call answers code NotImplemented, so neither the refusals nor the accepted reshard exist.
Why: resharding is the only way to change a replication group's shard count; a client cannot scale a cluster, and two concurrent reshard calls both fail instead of exactly one winning.
Fix: implement the ModifyReplicationGroupShardConfiguration handler (its validation ordering and the node-group state transition).
Traces: elasticache.concurrent-shard-config-modification-conflict, elasticache.modify-shard-configuration-disabled-cluster-mode-rejected.

Cause 6 of 8: CompleteMigration is unimplemented and answers NotImplemented instead of the modeled migration refusal.
AWS: Smithy: CompleteMigration models InvalidParameterValueException (code InvalidParameterValue, HTTP 400), ReplicationGroupNotUnderMigrationFault, InvalidReplicationGroupStateFault and ReplicationGroupNotFoundFault (404). Recorded behavior on an available group with no migration in flight is HTTP 400 InvalidParameterValue, example message "The replication group must be in migrating state to complete the migration. Please retry later.", with the group left available — and the same refusal with Force=True.
Emulator: code NotImplemented for every CompleteMigration call, including with Force.
Why: the online-migration state machine cannot be driven or even probed; a client cannot tell "no migration is in flight" from "this service does not implement migration", and the ordering contract (StartMigration before CompleteMigration) is unenforced.
Fix: implement the CompleteMigration handler over the replication-group migration state (see also the separately filed StartMigration scaffold issue, which covers that operation only).
Traces: elasticache.migration-complete-without-active-migration-rejected, elasticache.online-migration-lifecycle, elasticache.replication-group-migration-lifecycle.

Cause 7 of 8: serverless cache/snapshot Status is reported in UPPER case, so the resource never reads as creating or available and every serverless waiter hangs.
AWS: recorded behavior — CreateServerlessCache answers HTTP 200 with ServerlessCache.Status 'creating' and the cache then reports 'available' (lower case), and a serverless snapshot likewise moves creating -> available; the suite's waiters compare against those exact lower-case values. (The model's prose for ServerlessCache$Status says "The allowed values are CREATING, AVAILABLE, DELETING, CREATE-FAILED and MODIFYING", but the recorded wire value is lower case, so the recording governs.)
Emulator: returns Status 'CREATING' and never reports a lower-case lifecycle value, so a client polling for 'available' never converges.
Why: every serverless flow is unreachable in practice — two checks fail the status assertion outright and five more are killed by the 60s harness ceiling while polling for a state that can never appear. A client's own waiter (the SDK's documented pattern) hangs rather than failing fast.
Fix: the ServerlessCache / ServerlessCacheSnapshot status values in the elasticache state projection (and their transition), so the serialized Status matches the recorded lower-case lifecycle.
Traces: elasticache.serverless-cache-lifecycle, elasticache.serverless-cache-usage-limits-inverted-rejected, elasticache.create-serverless-cache-conflicting-name-rejected, elasticache.serverless-cache-snapshot-full-lifecycle, elasticache.serverless-cache-snapshot-retention-limit-out-of-range-rejected, elasticache.serverless-cache-snapshot-retention-window-enforced, elasticache.serverless-cache-usage-limits-numeric-precision-persists, elasticache.serverless-snapshot-not-found-semantics. (Hypothesis: the five checks whose detail is only "Check timed out after 60.0s" block on the first wait for 'available'; the two status assertions above are the direct evidence for the casing.)

Cause 8 of 8: a subnet EC2 CreateSubnet just returned is not yet selectable, because the emulator holds it in 'pending' for an artificial delay.
AWS: recorded behavior — immediately after CreateSubnet, DescribeSubnets with Filters=[vpc-id, state=available] returns the new subnet, so the recorded cache topology builds its network and proceeds with no wait.
Emulator: ec2 CreateSubnet stores the subnet with state SUBNET_STATE_PENDING and records subnet_available_at = now + TRANSITION_DELAY, so the immediately following DescribeSubnets(state=available) selects nothing and the caller concludes it has no usable subnet (recorded assertion: "created no usable subnet in vpc-0000000000000001c").
Why: any client that creates a subnet and then selects it by state — the normal way to pick subnets for a cache subnet group — gets an empty list and fails, where against AWS it succeeds.
Fix: the EC2 CreateSubnet handler's pending-state delay (services/service-com-amazonaws-ec2-amazonec2/src/ops/create_subnet.rs) — a created subnet must be selectable as available on the next call, as the recording shows.
Traces: elasticache.elasticache-revoked-security-group-ingress-blocked-from-cache-data-plane, elasticache.elasticache-streams-consumer-group-pending-and-autoclaim, elasticache.transit-encryption-endpoint-refuses-plaintext-resp-in-vpc.
