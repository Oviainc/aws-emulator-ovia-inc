# EBS direct APIs: EC2 DescribeSnapshots stub blocks 23 checks, checksum-mismatch misclassified, open snapshots are readable, and four refusal-message templates are emulator-authored (6 causes)

> _Note: this issue was identified against the code base at commit `ead37dd00922f5e8ae35cfd4d29cc6e26f23d78c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSnapshots

## Description
Six distinct root causes found replaying the EBS direct-API behavioral suite (1/30 checks passed). All six belong to the ebs behavioral surface; cause 1's code lives in the EC2 crate but is reported here because every failing check id is an `ebs.*` check.

=== Cause 1 of 6: ec2 DescribeSnapshots answers NotImplemented, so no EBS snapshot lifecycle check can observe snapshot state ===
AWS: EC2 DescribeSnapshots is the only way a caller learns that a snapshot started with the EBS direct API StartSnapshot has moved pending -> completed, and its Progress ('100%') and State fields are what every EBS direct-API workflow polls. Smithy (com.amazonaws.ebs): StartSnapshot http POST /snapshots code 201 returns Status 'pending'; CompleteSnapshot http POST /snapshots/completion/{SnapshotId} code 202 returns Status; the model itself exposes no read of snapshot state, so the EC2 DescribeSnapshots read is the required companion. Recorded behavior only for the EC2 response shape.
Emulator: every call answers `An error occurred (NotImplemented) when calling the DescribeSnapshots operation: operation DescribeSnapshots is scaffolded but not implemented in this emulator`. 22 checks abort on the first poll. A 23rd, ebs.missing-permission-put-snapshot-block-rejected, polls DescribeSnapshots through a restricted role in a retry loop and is killed by the 60s check timeout instead of raising, because the stub reply is never a success and never the expected rejection.
Why: a client that writes blocks and then waits for the snapshot to become usable never completes. Every EBS direct-API workflow — StartSnapshot/PutSnapshotBlock/CompleteSnapshot then read — is unusable end to end even though the EBS operations themselves answer.
Fix: implement the EC2 DescribeSnapshots handler (the scaffold stub in the ec2 service crate) and back it with the snapshot state the EBS direct-API handlers mutate, so StartSnapshot creates a pending snapshot, CompleteSnapshot drives it to completed with Progress '100%', and ec2:DeleteSnapshot (used by every check's cleanup) removes it. No open issue covers this: the open ec2 stub issues name CreateSubnet, DeleteVpc, DescribeNetworkInterfaces, ModifyVpcAttribute, DescribeVpcAttribute and CreateInternetGateway, and the two filed DescribeSnapshots stub issues are for `ds` and `elasticache`, not ec2.
Traces: ebs.complete-snapshot-transitions-to-completed-state, ebs.complete-snapshot-twice-is-idempotent, ebs.complete-snapshot-wrong-changed-blocks-count-is-accepted, ebs.concurrent-put-snapshot-block-distinct-indices, ebs.full-snapshot-round-trip-write-read-complete, ebs.get-snapshot-block-invalid-token-rejected, ebs.incremental-child-lists-and-serves-inherited-parent-blocks, ebs.incremental-parent-not-yet-complete-rejected, ebs.incremental-snapshot-list-changed-blocks, ebs.list-changed-blocks-token-presence-distinguishes-new-from-rewritten-block, ebs.list-changed-blocks-unrelated-snapshots-rejected, ebs.list-snapshot-blocks-expiry-time-in-future, ebs.list-snapshot-blocks-maxresults-out-of-range-rejected, ebs.list-snapshot-blocks-reflects-written-blocks, ebs.list-snapshot-blocks-starting-block-index-windows-the-listing, ebs.put-snapshot-block-after-completion-rejected, ebs.put-snapshot-block-response-returns-checksum-and-algorithm, ebs.start-snapshot-client-token-idempotent-same-payload, ebs.start-snapshot-description-and-tags-persist, ebs.start-snapshot-encrypted-with-parent-rejected, ebs.start-snapshot-nonexistent-parent-rejected, ebs.start-snapshot-returns-pending-status, ebs.missing-permission-put-snapshot-block-rejected.

=== Cause 2 of 6: PutSnapshotBlock with a Checksum that does not match the payload is refused as ValidationException instead of InvalidSignatureException ===
AWS: the x-amz-Checksum header is part of the SigV4 signing process for PutSnapshotBlock (Smithy: PutSnapshotBlockRequest.BlockData is @streaming/@httpPayload and is NOT signed, so Checksum is the integrity binding; Checksum is @required, httpHeader x-amz-Checksum). A checksum that does not match the transmitted bytes is therefore a signing-integrity failure: the recorded response is error code `InvalidSignatureException` (HTTP 403), with a message built from the request — the computed and the supplied checksum ('The value passed in as x-amz-Checksum does not match the computed checksum. Computed checksum: <sha256 of sent bytes> expected checksum: <value sent>').
Emulator: answers code `ValidationException` (HTTP 400, per the modeled @httpError on com.amazonaws.ebs#ValidationException) with the emulator-authored message, e.g. 'Checksum lIk9pF1EQI/XfDEZ5HybQO5TDy4dPudKwRGnDbAP/uU= does not match the SHA256 checksum of the block data'.
Why: the two classes are retried differently. InvalidSignatureException is an auth/signing failure a client resigns or fails fast on; ValidationException is a non-retryable input error. A client (or SDK retry policy) keyed on the signing class never sees it, and anything that distinguishes 403 from 400 takes the wrong branch.
Fix: the PutSnapshotBlock handler's checksum verification — classify the mismatch as the signing-integrity error (403 InvalidSignatureException) and render the message from the computed vs supplied checksum rather than from a local template.
Traces: ebs.put-snapshot-block-checksum-mismatch-rejected.

=== Cause 3 of 6: an open (pending) snapshot is readable — ListSnapshotBlocks/GetSnapshotBlock answer 200 where AWS answers 404 ResourceNotFoundException ===
AWS: a snapshot that has not been completed does not exist to the read path, even for the writer that is filling it. The recorded behavior: after a successful PutSnapshotBlock on a pending snapshot, ListSnapshotBlocks answers error code `ResourceNotFoundException` (Smithy com.amazonaws.ebs#ResourceNotFoundException, @httpError 404) with Reason `SNAPSHOT_NOT_FOUND` (Smithy ResourceNotFoundExceptionReason enum) and a request-derived message "The snapshot '<snapshot-id>' does not exist."; GetSnapshotBlock on the same open snapshot answers the same not-found error even when the BlockToken supplied is invalid — the absent snapshot is reported ahead of token validation. The same snapshot id answers 200 after CompleteSnapshot.
Emulator: ListSnapshotBlocks on the still-open snapshot SUCCEEDS (returns a listing rather than raising), so the check fails with 'the call SUCCEEDED where real AWS rejects it'. Note that cause 6's foreign-token check shows GetSnapshotBlock on an open snapshot reaching token validation (it answered a BlockToken error), which is the same precedence defect.
Why: a client treats readability as the completion signal — it can read back blocks out of a half-written snapshot and will conclude a snapshot is usable before CompleteSnapshot has sealed it, and sees an empty/partial listing where AWS refuses the resource outright.
Fix: the read-path state lookup shared by the ListSnapshotBlocks and GetSnapshotBlock handlers — gate it on the snapshot being completed, raise the 404 not-found error with Reason SNAPSHOT_NOT_FOUND, and evaluate that gate BEFORE BlockToken validation.
Traces: ebs.read-from-incomplete-snapshot-rejected.

=== Cause 4 of 6: PutSnapshotBlock ValidationException messages are emulator-authored instead of the AWS request-derived templates ===
AWS: both of these rejections carry the correct code (`ValidationException`, 400) but a message AWS builds from the request, so the template is the requirement, not the recorded text. For an unsupported DataLength the message names the rejected value and the only supported block size: 'Block data length <DataLength> is not valid, expected 524288' (Smithy: PutSnapshotBlockRequest.DataLength httpHeader x-amz-Data-Length, doc 'Currently, the only supported size is 524288 bytes'). For a BlockIndex beyond the volume extent it names the rejected index: 'Block index <BlockIndex> is beyond the volume size extent' (Smithy: BlockIndex @range min 0, a logical index in 512 KiB units).
Emulator: answers 'DataLength 1000 is not supported; the only supported block size is 524288 bytes' and 'BlockIndex 99999 is outside a 1 GiB volume, which addresses block indexes 0..2048' respectively — the right class, locally worded templates, and the second one leaks a derived upper bound (2048) that is not the inclusive last valid index.
Why: callers and tooling that match on the validation text to attribute which input was rejected (and test suites pinned to AWS wording) diverge, and the emulator's extra 'addresses block indexes 0..2048' phrasing is not something AWS ever returns.
Fix: the PutSnapshotBlock validation layer's message rendering for the DataLength and BlockIndex rejections. Also populate the modeled ValidationException.Reason member (Smithy ValidationExceptionReason) on these refusals; the emulator's envelope carries no Reason on the related token refusal (cause 5), so the same omission is likely here.
Traces: ebs.put-snapshot-block-datalength-mismatch-rejected, ebs.put-snapshot-block-index-exceeds-volume-rejected.

=== Cause 5 of 6: GetSnapshotBlock with a well-formed but never-issued BlockToken refuses with an emulator-authored message (and the modeled Reason is unverified/absent) ===
AWS: the code is right (`ValidationException`, 400) and the message is built from the request — it names the rejected token: 'The block token <BlockToken> is invalid.' The refusal also carries Reason `INVALID_BLOCK_TOKEN` (Smithy com.amazonaws.ebs#ValidationExceptionReason includes INVALID_BLOCK_TOKEN; ValidationException.Reason is a modeled member). The point under test is that only the token the service minted authorises a read — the BlockIndex alone must not.
Emulator: message is 'BlockToken does not name block 0 of snapshot snap-<id>' — it is keyed on the index/snapshot pair rather than reporting the token as the thing refused. The check asserted the message before the Reason assertion, so whether Reason=INVALID_BLOCK_TOKEN is emitted was not reached; populate it as part of this fix.
Why: a client cannot tell from the refusal that the TOKEN was rejected (rather than the index or the snapshot), which is exactly the distinction the Reason enum and the AWS message carry.
Fix: the GetSnapshotBlock handler's BlockToken validation — render the request-derived 'The block token <token> is invalid.' message and set ValidationException.Reason to INVALID_BLOCK_TOKEN.
Traces: ebs.get-snapshot-block-foreign-token-rejected.

=== Cause 6 of 6: StartSnapshot ClientToken reuse with a different payload returns a locally worded ConflictException message ===
AWS: recorded behavior only — the model documents the condition but not the text (Smithy com.amazonaws.ebs#ConflictException, @httpError 409, doc 'The request uses the same client token as a previous, but non-identical request'; StartSnapshot declares ConflictException). The recording shows AWS answering a FIXED, request-independent message for this condition: 'Current request does not match request stored with this token.' Because it does not vary with the request, the constant string is the rule, not an example.
Emulator: code and status are right but the message embeds the token and the operation: 'ClientToken sim2real-ebs-tok-<...> was already used for a different StartSnapshot request'.
Why: idempotency handling is one of the few places clients branch on the refusal text, and a token-embedding message also echoes a caller-supplied value AWS deliberately does not echo here.
Fix: the StartSnapshot handler's client-token conflict path — emit the fixed ConflictException message.
Traces: ebs.start-snapshot-client-token-conflict-rejected.
