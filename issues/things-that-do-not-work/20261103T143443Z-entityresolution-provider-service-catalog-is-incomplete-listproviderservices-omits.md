# entityresolution provider-service catalog is incomplete: ListProviderServices omits entries and GetProviderService returns stripped definition documents

> _Note: this issue was identified against the code base at commit `7bc0c82e0fb09c9b6063106544a9c7b54c672996`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListProviderServices

## Description
The entityresolution emulator serves the AWS-managed provider-service catalog (the read-only /providerservices surface) as a thin placeholder rather than the real catalog. Both read operations answer HTTP 200 with a body whose shape is right but whose catalog content is wrong: the summary list is missing members, and the per-service detail document is stripped of the definition documents clients need. There are 2 distinct causes in this issue and BOTH must be closed.

Cause 1 of 2 - ListProviderServices returns a provider-service list that is missing catalog entries (and therefore mis-aligned past the point where the first one is dropped).
AWS: GET /providerservices (ListProviderServices, @readonly, @paginated items=providerServiceSummaries, inputToken/outputToken=nextToken, pageSize=maxResults range 15..25) returns one ProviderServiceSummary per provider service registered in the AWS-managed catalog, for every provider and every service type. Smithy (services/service-com-amazonaws-entityresolution-awsveniceservice/smithy-model/com-amazonaws-entityresolution-awsveniceservice.json): ListProviderServices output providerServiceSummaries -> ProviderServiceList; ProviderServiceSummary members providerServiceArn (@required, ProviderServiceArn, @length 20..255, pattern ^arn:(aws|aws-us-gov|aws-cn):(entityresolution):([a-z]{2}-[a-z]{1,10}-[0-9])::providerservice/([a-zA-Z0-9_-]{1,255})/([a-zA-Z0-9_-]{1,255})$), providerName (@required), providerServiceName (@required), providerServiceDisplayName (@required), providerServiceType (@required, ServiceType enum); errors AccessDeniedException(403), ValidationException(400), ThrottlingException(429), InternalServerException(500). Which providers populate the catalog is recorded behavior only: the recording shows the catalog carrying more entries than the emulator holds, including ASSIGNMENT-type services whose providers also offer other service types, so a provider's presence in the list does not imply all of its services are present.
Emulator: answers 200 but its catalog is short. At the index where the expected catalog carries the next ASSIGNMENT entry, the emulator's list carries an unrelated ID_MAPPING entry instead, and the expected tail entry has no counterpart at all (reported as `missing ... got None`) - i.e. the emulator's list is a strict subset of the catalog, so every position after the first dropped entry is occupied by the wrong summary. The ServiceType mix is skewed the same way: ASSIGNMENT-type services are under-represented relative to ID_MAPPING.
Why: ListProviderServices is the only discovery path a client has for provider-based matching. A client that enumerates the catalog to choose a provider never sees the omitted services, so a provider/service pair that exists on AWS looks unavailable; a client that indexes into the list positionally, or that filters by providerServiceType to offer only ASSIGNMENT services, gets a different provider than it would on AWS and then builds a provider-based workflow against the wrong providerServiceArn. Pagination makes it worse: with fewer entries than AWS the page boundary and nextToken fall in a different place.
Fix: the provider-service catalog seed data backing the entityresolution service crate's state, read by the ListProviderServices handler - the catalog must enumerate the full set of provider services (every provider x every service type it offers), not a subset, and the handler must return them in the catalog's own stable order so positional and paginated reads line up with AWS.
Traces: entityresolution-catalog-list-provider-services#task#1 (cluster also covers entityresolution-provider-services-catalog#task#1).

Cause 2 of 2 - GetProviderService returns the provider detail with its Document members emptied and a fabricated Data Exchange listingId.
AWS: GET /providerservices/{providerName}/{providerServiceName} (GetProviderService, @readonly) returns the provider service's full definition. Smithy: output members providerConfigurationDefinition (Document), providerJobConfiguration (Document), providerEntityOutputDefinition (@required, Document), providerEndpointConfiguration (@required, ProviderEndpointConfiguration union with member marketplaceConfiguration -> ProviderMarketplaceConfiguration whose dataSetId/revisionId/assetId/listingId are ALL @required, doc 'The listing ID on Data Exchange'); errors AccessDeniedException(403), ResourceNotFoundException(404), ValidationException(400), ThrottlingException(429), InternalServerException(500). The Document members are JSON-schema-shaped descriptors: each property carries its own metadata - description, pattern, minLength/maxLength, value, and required lists on nested objects - and that metadata is what tells a caller how to fill the provider configuration in. Content of these documents is recorded behavior only; the recording shows, per property, a full descriptor (e.g. secret-ARN-typed credential properties carrying description plus a secretsmanager ARN pattern and min/max length bounds, and provider output entity properties carrying a `required` list naming the provider's identifier plus that identifier's description and length bounds).
Emulator: answers 200 with the top-level members present but hollow. Inside providerConfigurationDefinition.properties every per-property attribute is absent (`missing ... got None`) for description, pattern, minLength, maxLength and value - only bare property names survive; providerEntityOutputDefinition.properties.entity is missing its `required` list and each output property's description/minLength/maxLength/pattern; providerJobConfiguration.properties entries are likewise reduced. providerEndpointConfiguration.marketplaceConfiguration.listingId is a value_mismatch: the emulator emits a 32-character lowercase hex string where AWS emits the Data Exchange listing identifier, which is a catalog constant of the form `prodview-<listing-id>` (the `prodview-` prefix is fixed text; the suffix is that provider service's own listing id from the catalog, not a per-run value).
Why: a client reads providerConfigurationDefinition to learn which fields a provider needs and how to validate them (secret ARN pattern, length bounds) before calling CreateMatchingWorkflow/CreateIdMappingWorkflow with a providerProperties payload; with the metadata stripped it cannot validate or render those inputs, and any client-side schema check over the document fails outright. providerEntityOutputDefinition's missing `required` list means the caller cannot tell which identifier the provider guarantees in its output. The hex listingId is not a Data Exchange listing id at all, so a client that follows it to look up or subscribe to the provider's Data Exchange listing resolves nothing - and because the value changes shape rather than just content, code matching the `prodview-` prefix breaks.
Fix: the entityresolution service crate's GetProviderService handler and the provider-catalog seed data it reads - serve the stored provider definition documents verbatim with all per-property metadata (description/pattern/minLength/maxLength/value and nested `required` lists) instead of emitting name-only property stubs, and populate ProviderMarketplaceConfiguration.listingId (with dataSetId/revisionId/assetId) from the catalog's Data Exchange identifiers rather than generating an opaque id.
Traces: entityresolution-provider-services-catalog#task#2.
