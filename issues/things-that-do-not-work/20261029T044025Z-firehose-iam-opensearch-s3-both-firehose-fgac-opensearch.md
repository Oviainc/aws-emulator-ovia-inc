# firehose__iam__opensearch__s3: both Firehose→FGAC-OpenSearch delivery checks never complete — the domain REST data plane is never reachable, so the AmazonopensearchserviceDestination path (indexed documents and the AmazonOpenSearchService-failed/ S3 backup) can never be observed

> _Note: this issue was identified against the code base at commit `96b9d79b1b8395723cfce0b7aa8e9f6fed8726ec`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeliveryStream

## Description
One root cause (Cause 1 of 1), grounded in two failing checks.

Cause 1 of 1: a Firehose DirectPut delivery stream whose destination is a fine-grained-access-control (FGAC) OpenSearch domain can never be exercised end to end, because the scenario blocks before any delivery assertion is reached and both checks run to the harness cap.

AWS: Smithy (services/service-com-amazonaws-firehose-firehose-20150804) models CreateDeliveryStream.AmazonopensearchserviceDestinationConfiguration with required RoleARN (pattern ^arn:.*:iam::\d{12}:role/...), required IndexName (@length 1..80), required S3Configuration (S3DestinationConfiguration), optional DomainARN (pattern ^arn:.*:es:[a-zA-Z0-9\-]+:\d{12}:domain/[a-z][-0-9a-z]{2,27}$), IndexRotationPeriod (enum NoRotation|OneHour|OneDay|OneWeek|OneMonth) and S3BackupMode (enum FailedDocumentsOnly|AllDocuments, documented "When it is set to FailedDocumentsOnly, Firehose writes any documents that could not be indexed to the configured Amazon S3 destination"). AWS's documented end-to-end behavior for this configuration: the OpenSearch domain created with AdvancedSecurityOptions publishes an HTTPS REST endpoint in DescribeDomain's DomainStatus.Endpoint once Processing is false; SigV4-signed requests to that endpoint (service name `es`) are answered by the domain (200 for a mapped/master principal, 403 security_exception for an unmapped one); the delivery stream reaches DeliveryStreamStatus ACTIVE; records put with PutRecordBatch are indexed into IndexName suffixed by the OneDay rotation date (IndexName-YYYY-MM-DD), and each document Firehose could not index is written to the backup bucket under the prefix "AmazonOpenSearchService-failed/" as a JSON envelope carrying errorCode in the "OS." namespace, osIndexName naming the target index, and rawData holding the base64 of the original record byte-for-byte. The index name, the date suffix, the "AmazonOpenSearchService-failed/" prefix and the "OS." errorCode namespace are the fixed parts of that contract; the concrete domain name, bucket name, stream name, role ARNs, the date value and the specific OS.* code are values taken from the request, the account state and the run.

Emulator: both checks produce no response at all for the behavior under test — the replay reports "Error: Check timed out after 60.0s" for each. The first observable call that cannot be satisfied is the wait for the created FGAC domain to become usable: _wait_domain polls opensearch.describe_domain for Processing=false with an Endpoint, and _wait_master then polls a SigV4-signed GET /_cluster/health against the published endpoint for HTTP 200. Neither predicate is ever met, so the check never gets as far as creating the delivery stream, putting records, or reading the index and the S3 failed prefix. Hypothesis: the same emulator gap the already-open opensearch issues describe — the domain REST data plane is not registered in the request router, so signed requests to the published domain host are answered HTTP 404 {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"} — and, behind it, the Firehose AmazonopensearchserviceDestination delivery path is inert, so even a reachable domain would receive no document and no "AmazonOpenSearchService-failed/" object would be written.

Related open issues that do NOT cover these two checks: 20261024T055421Z-opensearch-domain-data-plane-is-not-served-and.md and 20261024T055421Z-iam-opensearch-sts-iam-role-to-fgac-search-authorization-check-never.md describe the opensearch-side data-plane gap, and 20261024T005347Z-firehose-never-delivers-buffered-records-to-the-s3.md describes the S3-destination flush gap; none of them carries the replay key of either firehose__iam__opensearch__s3 check, and none of them covers the Firehose→OpenSearch destination (index rotation, FGAC-driven document failure, the AmazonOpenSearchService-failed/ envelope).

Why: a client relying on AWS's behavior gets two things wrong. First, it cannot observe that Firehose indexes what fits and quarantines what does not: a pipeline that silently drops conflicting documents instead of writing them under AmazonOpenSearchService-failed/ with an OS.* errorCode looks identical to a healthy one, so data loss is undetectable. Second, FGAC is the authorization boundary for OpenSearch writes — an unmapped Firehose role must index nothing and have every record land in the failed prefix. Against this emulator neither the allow nor the deny side produces any result, so an estate behaves as though OpenSearch write authorization and Firehose error routing did not exist.

Fix: the OpenSearch domain data plane belongs in the emulator's request router / endpoint resolution (serve the published DomainStatus.Endpoint host as the `es` data plane and enforce FGAC role mappings on signed requests), and the Firehose OpenSearch destination belongs in the firehose delivery/flush component that owns AmazonopensearchserviceDestinationConfiguration — it must index to IndexName plus the IndexRotationPeriod suffix and write non-indexable documents to the S3Configuration bucket under the AmazonOpenSearchService-failed/ prefix when S3BackupMode is FailedDocumentsOnly.

## Evidence
Expected (real AWS):
- opensearch.DescribeDomain on the FGAC domain eventually reports Processing=false with a non-empty DomainStatus.Endpoint, and a SigV4-signed (service `es`) GET /_cluster/health against that endpoint as the IAM master role returns HTTP 200.
- firehose.CreateDeliveryStream(DeliveryStreamType="DirectPut", AmazonopensearchserviceDestinationConfiguration={RoleARN, DomainARN, IndexName, IndexRotationPeriod: "OneDay", S3BackupMode: "FailedDocumentsOnly", S3Configuration: {...}}) reaches DeliveryStreamStatus ACTIVE.
- After PutRecordBatch of 7 records (5 that fit a strict index template, 2 that conflict) exactly one index named <IndexName>-YYYY-MM-DD exists, its _count is 5, and the backup bucket holds objects only under "AmazonOpenSearchService-failed/" containing exactly 2 JSON records, each with one errorCode in the "OS." namespace, osIndexName equal to that index, and rawData whose base64 decodes to the original record.
- For the unmapped-role case: the stream whose role is allowed es:ESHttp* by IAM but has no FGAC role mapping creates no index and all 5 records land under "AmazonOpenSearchService-failed/" intact; the mapped control stream on the same domain indexes its 5 documents and backs up nothing; adding the role to the FGAC rolesmapping makes the same stream deliver.

Actual (emulator): no response is ever obtained for any of the above. The suite reports for both checks:
  Error: Check timed out after 60.0s
The checks block in _wait_domain / _wait_master, i.e. before CreateDeliveryStream is even called, so the delivery-path assertions are never reached. Sibling opensearch checks already recorded the underlying data-plane answer for signed requests to the published domain endpoint: HTTP 404 {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"}.

## Steps to Reproduce
1. sts.GetCallerIdentity to get the account id.
2. iam.CreateRole for an OpenSearch master role trusted by the account root, with an inline policy allowing es:ESHttp* on arn:aws:es:<region>:<account>:domain/<domain-prefix>-*/*; assume it via sts.AssumeRole.
3. opensearch.CreateDomain with EngineVersion OpenSearch_2.11, a single t3.small.search node, EBS gp3 10 GiB, and AdvancedSecurityOptions naming the assumed master role as the IAM master user.
4. Poll opensearch.DescribeDomain until Processing=false and DomainStatus.Endpoint is set, then send a SigV4-signed (service `es`) GET /_cluster/health to that endpoint with the master role credentials and expect HTTP 200. On this emulator neither step ever succeeds and the check is killed at the 60 s harness cap.
5. (Blocked by step 4, the remainder of the recorded scenario:) s3.CreateBucket for the backup bucket; iam.CreateRole for the Firehose delivery role granting the s3:PutObject/ListBucket set on that bucket and es:DescribeDomain*/es:ESHttpPost|Put|Get on the domain ARN; PUT an index template with dynamic:"strict" and a non-coercing integer field; PUT an FGAC role and rolesmapping binding the Firehose role ARN as a backend_role.
6. firehose.CreateDeliveryStream(DeliveryStreamName=<stream>, DeliveryStreamType="DirectPut", AmazonopensearchserviceDestinationConfiguration={RoleARN: <fh-role>, DomainARN: <domain-arn>, IndexName: <index>, IndexRotationPeriod: "OneDay", BufferingHints: {IntervalInSeconds: 0, SizeInMBs: 1}, RetryOptions: {DurationInSeconds: 0}, S3BackupMode: "FailedDocumentsOnly", S3Configuration: {RoleARN: <fh-role>, BucketARN: arn:aws:s3:::<bucket>, CompressionFormat: "UNCOMPRESSED"}}) and poll DescribeDeliveryStream for ACTIVE.
7. firehose.PutRecordBatch with 5 conforming and 2 conflicting JSON documents; then read back the <index>-YYYY-MM-DD index via signed _count/_search and list the backup bucket, expecting only "AmazonOpenSearchService-failed/" keys holding the 2 conflicting records with OS.* errorCodes.
8. Replay firehose__iam__opensearch__s3.xsvc-opensearch-1-firehose-fgac-strict-mapping-routes-conflicts-to-s3 and firehose__iam__opensearch__s3.xsvc-opensearch-1-firehose-unmapped-role-denied-all-records-to-s3.
