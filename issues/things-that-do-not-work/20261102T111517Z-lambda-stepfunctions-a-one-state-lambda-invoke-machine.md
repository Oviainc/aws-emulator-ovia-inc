# lambda__stepfunctions: a one-state lambda:invoke machine never reaches SUCCEEDED, so all eight Lambda-task scenarios hang to the 60 s harness cap (1 cause)

> _Note: this issue was identified against the code base at commit `fbef683f21970efb4631f2658975dd3b2c5af139`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExecution

## Description
One net-new root cause in this service group.

Cause 1 of 1: a STANDARD state machine with a single Task state `{"Resource": "arn:aws:states:::lambda:invoke", "Parameters": {"FunctionName": <arn>, "Payload.$": "$"}, "End": true}` never produces a SUCCEEDED execution. Every one of these eight checks opens with a positive-control barrier that starts that machine and polls DescribeExecution until it reports SUCCEEDED (the barrier exists because a fresh states.amazonaws.com trust relationship needs to propagate on AWS); because the emulator's execution never becomes SUCCEEDED, the barrier re-starts executions until the harness kills the check at 60 s, and no check in the group reaches a single subject assertion.
Failing checks: lambda__stepfunctions.cli-derives-failed-state-and-cause-like-the-sdk, lambda__stepfunctions.definition-naming-absent-function-accepted-then-execution-fails, lambda__stepfunctions.describe-state-machine-for-execution-keeps-the-role-an-execution-ran-under-after-a-role-update, lambda__stepfunctions.execution-input-array-reaches-lambda-unchanged-bare-number-rejected-at-payload, lambda__stepfunctions.execution-name-taken-on-one-state-machine-is-free-on-another, lambda__stepfunctions.handler-exception-fails-execution-with-structured-cause, lambda__stepfunctions.list-executions-status-filtered-pages-walk-only-matching-runs-of-a-mixed-machine, lambda__stepfunctions.state-machine-role-without-invoke-permission-denied.

AWS: the Task invokes the function and the execution advances to its end, so DescribeExecution reports `status="SUCCEEDED"` with the function's result (wrapped in the optimized integration's envelope: `Payload`, `StatusCode`, `ExecutedVersion`) as the execution output and no `error`/`cause`. A genuine failure is classified by its real cause: an unhandled handler exception gives `error` = the Python exception class (e.g. `RuntimeError`) with `cause` the function's structured error document `{"errorType", "errorMessage", "trace"}`; a role without `lambda:InvokeFunction` gives `Lambda.AWSLambdaException`; a `Payload.$` that resolves to a bare number is refused at the Task because the Payload parameter requires a string, object or array. `States.Runtime` is reserved for interpreter-level faults. Smithy (sfn): DescribeExecution models `status`, `error` and `cause`, and ListExecutions models `statusFilter`, so these are the modeled carriers these checks read; Smithy (lambda): `Invoke` is a modeled data-plane operation returning `Payload`/`StatusCode`/`FunctionError`/`ExecutedVersion`.
Emulator: no such execution ever reports SUCCEEDED; each check reports `Check timed out after 60.0s` inside its `_await_role_assumable` barrier (the barrier's own diagnosis is "the control state machine never reached SUCCEEDED"). Consistently across this suite the emulator answers a Lambda-invoking Task with `status='FAILED'`, `error='States.Runtime'` and `cause="the 'Invoke' operation of Lambda is not implemented by this emulator, so nothing was run for this task"` — fixed text that is entirely emulator-authored (AWS never emits "is not implemented by this emulator"), with the operation name (`Invoke`) and service (`Lambda`) as its variable parts.
Why: the whole Lambda-task surface of Step Functions is unusable and unobservable for a client: no successful invocation, no structured failure `cause` to parse, no AWS-matchable `error` name for Retry/Catch `ErrorEquals`, and every derived behaviour these checks cover — CLI/SDK parity of `error` and `cause`, `ExecutedVersion` in the invoke envelope, Payload type refusal, per-state-machine execution-name uniqueness, `ListExecutions` status-filtered paging over a mixed machine, DescribeStateMachineForExecution pinning the role an execution ran under, and the denied-invoke verdict — cannot be reached at all.
Fix: the Lambda `Invoke` data-plane handler in the lambda crate (it must execute the function package rather than answer NotImplemented) and the Step Functions interpreter's Task dispatch and failure classification in the sfn crate (run the optimized `lambda:invoke` integration, return its `Payload`/`StatusCode`/`ExecutedVersion` envelope as the state result, map a real task failure to the AWS error name with the function's structured document as `cause`, and reserve `States.Runtime` for interpreter faults).

Traces: the eight failing check ids listed above.

## Evidence
Cause 1 — Expected: StartExecution on a one-state `arn:aws:states:::lambda:invoke` machine whose role grants `lambda:InvokeFunction` reaches `status="SUCCEEDED"`, which is the precondition all eight checks wait on; the failing twin then reports `error="RuntimeError"` and a `cause` that parses as `{"errorType": "RuntimeError", "errorMessage": "<the handler's message>", ...}`.
Actual, identically in all eight checks: `Check timed out after 60.0s` — the control execution never reports SUCCEEDED, so the barrier loop never exits and no subject assertion runs. The emulator's recorded answer for such a Task in this suite is `status='FAILED'`, `error='States.Runtime'`, `cause="the 'Invoke' operation of Lambda is not implemented by this emulator, so nothing was run for this task"` — not an AWS error name and not a parseable structured cause document.

## Steps to Reproduce
1. Create an IAM role trusted by lambda.amazonaws.com with the basic logs permissions, and create two python3.12 inline functions with it: one returning `{'ok': True, 'echo': event}` and one raising `RuntimeError("<message>")`.
2. Create an IAM role trusted by states.amazonaws.com granting `lambda:InvokeFunction` on both function ARNs.
3. CreateStateMachine (STANDARD) twice with `{"StartAt": "InvokeProcessingLambda", "States": {"InvokeProcessingLambda": {"Type": "Task", "Resource": "arn:aws:states:::lambda:invoke", "Parameters": {"FunctionName": "<fn arn>", "Payload.$": "$"}, "End": true}}}` — once per function, with no Retry block.
4. StartExecution on the OK machine and poll DescribeExecution until the status is not RUNNING.
On AWS it reaches SUCCEEDED (this is the barrier every check in the group waits on). On the emulator it reaches FAILED with error `States.Runtime` and the emulator-authored cause, so the barrier never completes.
5. Then StartExecution on the raising machine: AWS reports `error="RuntimeError"` with a structured JSON `cause`; the emulator again reports `States.Runtime`.
