# CodeCommit/CodePipeline/Glue/IAM/Lambda refarch: CFN leaves AWS::Lambda::Function declared-only, Glue CreateJob misclassifies a config mismatch and applies no defaults, and UpdatePipeline versions a no-op (4 causes)

> _Note: this issue was identified against the code base at commit `86c9f1e4438a61fbe37b19dfcd3d77efce3d0679`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
FOUR net-new root causes across this reference architecture's surface, all grounded in failing behavioral checks the replay report left unmarked (neither ALREADY FILED nor OWNED). A fixer must close ALL FOUR before submitting.

=== Cause 1 of 4: a CloudFormation stack's AWS::Lambda::Function is never created in Lambda, so the function the stack reports does not exist ===
AWS: a stack that reaches CREATE_COMPLETE has really created every resource it declares. For AWS::Lambda::Function, CloudFormation calls lambda:CreateFunction and the generated physical resource id IS the function's name, so lambda:GetFunction on it answers 200 with Code.Location and Configuration. The lambda model's GetFunction.FunctionName accepts all three documented forms ('The name or ARN of the Lambda function... Function name - my-function... Function ARN... Partial ARN'), and ResourceNotFoundException (httpError 404) is reserved for a function that does not exist.
Emulator: the stack reaches CREATE_COMPLETE, DescribeStacks reports the function's physical id, and CodePipeline's Deploy action carries it as its FunctionName — but lambda:GetFunction on that identity answers 404 ResourceNotFoundException 'Function not found: arn:aws:lambda:<region>:<account>:function:<physical id>'. The cause is in CloudFormation, not in Lambda: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs carries one arm per resource type the emulator REALLY creates (S3::Bucket, IAM::Role/InstanceProfile/User/ManagedPolicy, CodePipeline::Pipeline, Glue::Job, the RDS types, BedrockAgentCore::WorkloadIdentity) and has NO arm for AWS::Lambda::Function, so that type is left 'declared-only' as the module's own doc comment describes: it gets a physical id and attributes from CloudFormation's naming rules and nothing is created in the owning service. Lambda's own resolver is fine — crate::state::resolve_function parses names, qualified names and full/partial ARNs and formats the 404 message by expanding the requested name to an ARN, which is why the message shows an ARN for a name-form request.
Why: every serverless estate deployed through CloudFormation is a shell. A stack says the launcher exists, the pipeline's Deploy action names it, and the first call that touches it — GetFunction, GetFunctionConfiguration, Invoke, AddPermission, or anything reading /aws/lambda/<name> — fails 404. Diagnosis replays and deploy-then-exercise workflows cannot get past the deploy they just 'succeeded'.
Fix: add the AWS::Lambda::Function arm to services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs (create via lambda CreateFunction from the evaluated properties — Runtime, Handler, Role, Timeout, Code.ZipFile, Environment.Variables, Tags — with the generated name as the function name, delete via DeleteFunction, and the update path through UpdateFunctionCode/UpdateFunctionConfiguration), so Ref resolves to a function that exists and Fn::GetAtt Arn to its real ARN.
Traces: codecommit__codepipeline__glue__iam__lambda.e2e-diagnose-glue-pipeline-not-running-lifecycle (phase 2/4 'solve').

=== Cause 2 of 4: Glue CreateJob answers AlreadyExistsException where AWS answers IdempotentParameterMismatchException for a same-name create with a DIFFERENT configuration ===
AWS: Smithy CreateJob (Name @required, Role @required, Command @required) models BOTH AlreadyExistsException and IdempotentParameterMismatchException (both client, httpError 400 [defaulted]); IdempotentParameterMismatchException documents 'The same unique identifier was associated with two different records.' Recorded behavior: a second CreateJob under a name that already exists, differing from the first only in Role, is refused HTTP 400 with code IdempotentParameterMismatchException and the fixed message 'Job already submitted with different configuration.' — Glue's idempotency check covers the whole job definition, so the name collision is reported as a parameter mismatch, and the original job keeps its original Role.
Emulator: HTTP 400 with code AlreadyExistsException and message 'Job already exists: <Name>' — the other error the operation declares, with the requested job name interpolated.
Why: the two codes imply different client behavior. A caller that recreates its execution role between runs treats IdempotentParameterMismatchException as 'your definition drifted, reconcile it' and AlreadyExistsException as 'this name is taken, pick another'; retry and infrastructure-convergence loops branch on exactly this distinction and take the wrong branch.
Fix: the duplicate-name branch of glue CreateJob in services/service-com-amazonaws-glue-awsglue/src/ops/create_job.rs — compare the submitted job definition against the stored one and answer IdempotentParameterMismatchException with AWS's fixed sentence when it differs (leaving the stored job untouched).
Traces: codecommit__codepipeline__glue__iam__lambda.refarch-glue-create-job-duplicate-name-rejected.

=== Cause 3 of 4: Glue CreateJob stores the submitted document verbatim and applies none of the Job defaults, starting with the nested Command.PythonVersion ===
AWS: Smithy JobCommand carries a PythonVersion member ('The Python version being used to run a Python shell job', pattern ^([2-3]|3[.]9)$), and the Job shape documents the defaults the service APPLIES when the create omits them: Timeout 'When the value is left blank, the timeout is defaulted to 2,880 minutes for Glue version 4.0 and earlier', JobMode 'When the JobMode field is missing or null, SCRIPT is assigned as the default value', MaxRetries @default 0, JobRunQueuingEnabled ('If false or not populated...'), and ExecutionProperty's MaxConcurrentRuns. Recorded behavior for a CreateJob sending only Name/Role/Command{Name,ScriptLocation}/GlueVersion 4.0/NumberOfWorkers 2/WorkerType G.1X: GetJob returns the sent values verbatim AND Command.PythonVersion '3' added INSIDE the caller's structure, MaxRetries 0, Timeout 2880, ExecutionProperty {'MaxConcurrentRuns': 1}, JobMode 'SCRIPT', JobRunQueuingEnabled false, MaxCapacity 2.0 and AllocatedCapacity 2 derived from NumberOfWorkers/WorkerType, CreatedOn and LastModifiedOn present — while the members nothing was sent for (DefaultArguments, Description, Connections, SecurityConfiguration, NonOverridableArguments) stay ABSENT rather than becoming empty values.
Emulator: the sent members round-trip correctly (Command.Name, Command.ScriptLocation, Role, GlueVersion '4.0', WorkerType, NumberOfWorkers all pass), but Command.PythonVersion comes back absent (None) — the Command structure is echoed through verbatim, so no default is injected into it. The check stops at that first default, so the remaining applied defaults listed above and the 'omissions stay omissions' assertions are UNVERIFIED behind it and must be made to hold by the same fix.
Why: a job document that is missing its applied defaults is not the document AWS stores. An operator asking 'will a failed run be retried' reads absent instead of 0, a launcher reading Command.PythonVersion to decide how to invoke gets nothing, and anything that re-submits the read-back document (UpdateJob, drift comparison, IaC convergence) diffs against AWS forever.
Fix: glue CreateJob's default application in services/service-com-amazonaws-glue-awsglue/src/ops/create_job.rs and the job record in that crate's state (write the documented defaults into the stored Job — including nested ones inside Command and ExecutionProperty, and the capacity values derived from WorkerType/NumberOfWorkers — while leaving undeclared members unset), so GetJob/GetJobs report them.
Traces: codecommit__codepipeline__glue__iam__lambda.refarch-glue-job-command-and-defaults-round-trip.

=== Cause 4 of 4: CodePipeline UpdatePipeline advances `version` on an unmodified re-submission ===
AWS: Smithy PipelineDeclaration$version documents 'The version number of the pipeline. A new pipeline always has a version number of 1. This number is incremented when a pipeline is updated.' Recorded behavior (what 'updated' means on the wire): UpdatePipeline DIFFS the submitted declaration against the stored one, so re-submitting exactly what GetPipeline returned is accepted, returns version 1 unchanged, leaves every stage and artifactStore byte-identical, and a following GetPipeline still reports 1; only a declaration that really differs advances the version, and then by exactly one.
Emulator: a byte-identical re-submission of the declaration just read back returns version 2 — the version is incremented per accepted call rather than per real change.
Why: the pipeline version is what an operator and an IaC tool use to confirm a change landed. An emulator that bumps it on every write tells them their fix shipped when nothing changed, and makes idempotent re-apply (the normal mode of every deploy tool) indistinguishable from a real edit.
Fix: the version-assignment path of codepipeline UpdatePipeline in services/service-com-amazonaws-codepipeline-codepipeline-20150709/src/ops/update_pipeline.rs — compare the submitted PipelineDeclaration with the stored one and advance the stored version only when they differ, returning the stored version otherwise.
Traces: codecommit__codepipeline__glue__iam__lambda.refarch-glue-pipeline-declaration-survives-update-and-bumps-version.
