# sustainability: every operation refused 403 AccessDeniedException before dispatch, and IAM identity-based denial is never evaluated or worded

> _Note: this issue was identified against the code base at commit `78295efc92da5c3ab6dc723b39af1e4944870efd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetEstimatedCarbonEmissions

## Description
2 causes, both in the sustainability service's pre-dispatch authentication/authorization path. ALL 33 behavioral checks of this service fail; 0/33 pass. Related open issue 20261029T184222Z-sustainability-getestimatedwaterallocation-refused-403-accessdeniedexception-before-dispatch-so.md reports the same pre-dispatch refusal from the WIRE corpus for GetEstimatedWaterAllocation only; it does not cover the behavioral checks listed here, nor Cause 2 (IAM denial wording), which no filed issue describes.

Cause 1 of 4 is not used; the bundle has exactly 2 causes, numbered below.

Cause 1 of 2 - every request to every sustainability operation is answered 403 AccessDeniedException before any operation handler runs, so neither a success response nor a modelled validation refusal is reachable.
AWS: all four modelled operations (Smithy: AwsSustainabilityApiService, sdkId Sustainability, protocol restJson1, authSchemes [sigv4, sigv4a]; GetEstimatedCarbonEmissions POST /v1/estimated-carbon-emissions, GetEstimatedCarbonEmissionsDimensionValues POST /v1/estimated-carbon-emissions-dimension-values, GetEstimatedWaterAllocation POST /v1/estimated-water-allocation, GetEstimatedWaterAllocationDimensionValues POST /v1/estimated-water-allocation-dimension-values) answer HTTP 200 with their modelled output (Results list, optional NextToken) to a correctly SigV4-signed request made by a principal that is allowed the action, and refuse a malformed input with ValidationException (@error("client"), @httpError(400), required Message with jsonName "message"; it is one of this service's common errors together with AccessDeniedException, InternalServerException, ThrottlingException). For an out-of-enum list member AWS words the constraint envelope: fixed text "<n> validation error(s) detected: Value '" ... "' at '" ... "' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [" ... "]]", with the violation count, the rejected value list from the request, the input member path (dimensions / groupBy / emissionsTypes / allocationTypes) and the enum value set from the model as the variable parts. AccessDeniedException (@httpError(403)) is reserved for an authorization failure of the caller, not for a well-signed call by an authorized principal.
Emulator: every call - including calls made with the harness's own default emulator credentials, the same credentials with which the SAME checks successfully call iam.CreateRole, iam.PutRolePolicy, sts.GetCallerIdentity and sts.AssumeRole - is answered 403 with x-amzn-errortype AccessDeniedException and the fixed message "You do not have sufficient access to perform this action. Sign the request with the emulator credentials, using SigV4 (AWS4-HMAC-SHA256)." The request is claimed by the service (can_handle widens the claim to any SigV4-family credential scope and to the api.<service>. host form) and is then classified Refusal::Unauthenticated, which override_refusal words as the modelled AccessDeniedException code with that fixed sentence. Hypothesis: the framework's signature/credential verification still depends on the route key that resolve_route_key could not derive for this service (SigV4A scope with no region segment, restJson1 so no X-Amz-Target, and an api.sustainability.<region>... host whose first label is "api"), so authentication fails for a request can_handle nevertheless accepted; the checks pin region us-east-1 on the sustainability client only, which is the only thing that distinguishes these calls from the iam/sts calls that succeed.
Why: a client gets 403 AccessDeniedException for a correctly signed, authorized call, so the whole sustainability read surface is unusable: no Results list is ever returned (Results is a REQUIRED output member, so an SDK cannot even distinguish "no data" from "denied"), pagination/NextToken behavior and group-by/dimension echoing cannot be exercised, and every negative class (bad enum member, end-before-start TimePeriod, out-of-range MaxResults, unsupported granularity) is laundered from 400 ValidationException into 403 AccessDeniedException, so a client retries credentials instead of fixing its request.
Fix: the service's request-authentication gate ahead of dispatch - services/service-com-amazonaws-sustainability-awssustainabilityapiservice/src/service.rs can_handle / override_refusal and the framework authentication it feeds - must authenticate the same SigV4 (AWS4-HMAC-SHA256) and SigV4A (AWS4-ECDSA-P256-SHA256) emulator credentials it already accepts for other services, for a client whose region is pinned to us-east-1, so the request reaches the generated routing table, the operations' constrained-input validation, and the handlers over src/state.rs (which is already implemented and seeds the carbon/water dataset).

Cause 2 of 2 - when a caller genuinely is not authorized, the AccessDeniedException message is the emulator's fixed signing sentence instead of AWS's IAM authorization-failure wording, and identity-based authorization is not evaluated at all (explicit Deny vs no Allow are indistinguishable).
AWS: a sustainability call by a principal with no identity-based policy allowing the action is refused 403 AccessDeniedException whose Message follows AWS's implicit-deny template - fixed text "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action" - with the caller's principal ARN, the action name (sustainability:GetEstimatedCarbonEmissions), and the resource ARN arn:aws:sustainability:<region>:<account>:<operation http uri> taken from the request and the caller's identity. When the principal's policy carries an explicit Deny for the same action, Deny wins over any Allow and the Message uses the explicit-deny template instead: fixed text "User: ", " is not authorized to perform: ", " on resource: ", " with an explicit deny in an identity-based policy". (Smithy: AccessDeniedException @error("client") @httpError(403), required Message jsonName "message", documented as the caller lacking sufficient access; the message templates are AWS's documented IAM authorization-failure wording - recorded behavior for the exact text.)
Emulator: both an unprivileged assumed role with zero policies and a role whose single policy is Allow sustainability:Get* plus Deny sustainability:Get* receive the correct CODE AccessDeniedException but the message "You do not have sufficient access to perform this action. Sign the request with the emulator credentials, using SigV4 (AWS4-HMAC-SHA256)." - identical to the message every authorized caller gets (Cause 1), i.e. no identity-based policy evaluation happens for this service and the two denial classes cannot be told apart.
Why: a client or test that asserts on the denial reason - and any operator reading the message to learn WHICH principal lacked WHICH action on WHICH resource, or whether an explicit Deny was responsible - gets a signing instruction instead; an authorization regression in a caller's policy is indistinguishable from a credential problem, and after Cause 1 is fixed these calls would instead be wrongly ACCEPTED, which is worse (an over-permissive surface).
Fix: the sustainability request-authorization step that runs after authentication (services/service-com-amazonaws-sustainability-awssustainabilityapiservice/src/service.rs override_refusal for the wording, plus the IAM policy evaluation the framework exposes for the caller's principal), so a denied call renders AccessDeniedException with the implicit-deny or explicit-deny template above, filled from the request's action, the resolved principal ARN and the operation's resource ARN.
Traces: 3 checks - sustainability.get-carbon-emissions-denied-without-permission-rejected, sustainability.explicit-deny-policy-overrides-allow-rejected, sustainability.carbon-emissions-missing-permission-access-denied-rejected.
