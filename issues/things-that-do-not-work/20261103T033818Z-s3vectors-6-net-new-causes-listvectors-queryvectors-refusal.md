=== Cause 1 of 6: the @length framework sentence drops AWS's "with length <n>" clause ===
AWS: Smithy models ListVectorsInput.indexName -> IndexName (string, @length min 3 max 63). A name longer than 63 characters leaves the SDK and is refused by the SERVICE with HTTP 400 ValidationException. The sentence AWS uses for a length-constraint violation names the length of the rejected value: top-level `message` = "1 validation error detected. Value with length <actualLength> at '/<memberPath>' failed to satisfy constraint: Member must have length between <min> and <max>, inclusive", and `fieldList[0].message` = the same sentence without the leading "1 validation error detected. " count clause. Fixed text: "1 validation error detected. ", "Value with length ", " at '/", "' failed to satisfy constraint: Member must have length between ", " and ", ", inclusive". Variable parts, all taken from the request and the model: the LENGTH of the submitted value, the member path, and the member's modeled min/max (3 and 63 for IndexName).
Emulator: HTTP 400 ValidationException with the "with length <n>" clause missing from both members — "1 validation error detected. Value at '/indexName' failed to satisfy constraint: Member must have length between 3 and 63, inclusive" and the matching `fieldList[0].message`. Status, code, error path and the member path are all correct; only the length clause is absent.
Why: this is the framework sentence shared by every @length-constrained member of the service, so the defect is service-wide, not specific to indexName. The length of the rejected value is what tells a caller BY HOW MUCH it overran — the clause a client surfaces or asserts to distinguish "name too long" from "name too short" without re-measuring its own input. A client asserting AWS's wording diverges on every length violation this service can report.
Fix: the shared constraint-violation message builder for the s3vectors crate's generated/framework input validation (the @length formatter that renders both the top-level `message` and the `fieldList` entry) — emit the "Value with length <n>" form.
Traces: s3vectors-vbi-list-vectors-addressing-mistakes#task#4 (representative) and #task#5, the two steps of this cluster.

=== Cause 2 of 6: a syntactically invalid index name is answered 404 NotFoundException instead of 400 ValidationException "Invalid index name" ===
AWS: an index name that satisfies IndexName's @length 3..63 but violates the service's index-name grammar (the modeled IndexArn pattern shows the admissible name form: ^[a-z0-9][a-z0-9-.]{1,61}[a-z0-9]$ — lower-case letters, digits, hyphen and dot only) is refused on NAME GROUNDS, before any resource lookup: HTTP 400 ValidationException with `message` exactly "Invalid index name" and the error type header x-amzn-errortype naming ValidationException. That sentence is entirely FIXED text — the rejected name is not interpolated.
Emulator: HTTP 404 NotFoundException with `message` "The specified index could not be found" and x-amzn-errortype: NotFoundException. The malformed name is carried into the lookup and reported as a missing resource.
Why: this inverts the refusal taxonomy a client branches on. 400/ValidationException means "fix the request" and is not retryable; 404/NotFoundException means "the resource is absent", which provisioning code treats as create-if-absent. A caller that mistypes or mis-cases an index name is told by this emulator that the index does not exist, so it goes on to CREATE it (or reports a missing resource to its user) where AWS would have told it the name itself is inadmissible. It also diverges in HTTP status, so retry/alarm policies keyed on 4xx class detail behave differently.
Fix: ListVectors' input validation in the s3vectors crate (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/list_vectors.rs and the index-selector resolution it calls in crate::state) — validate the index name's grammar and refuse with ValidationException BEFORE the index lookup that produces NotFoundException.
Traces: s3vectors-vbi-list-vectors-addressing-mistakes#task#9.

=== Cause 3 of 6: ListVectors' segmentIndex-out-of-range refusal is emulator-worded AND uses the wrong fieldList path ===
AWS: Smithy models ListVectorsInput.segmentCount (integer, default 1, @range 1..16) and segmentIndex (integer, default 0, @range 0..15). segmentIndex == segmentCount is inside BOTH shape ranges, so the request leaves the SDK and the SERVICE refuses it: HTTP 400 ValidationException with top-level `message` exactly "Segment index is zero-indexed and must be smaller than segment count", `fieldList[0].message` the same sentence, and `fieldList[0].path` = "segment_index" — the snake_case field name the service uses in fieldList for this cross-field rule, not the wire member name. All fixed text; neither submitted number is interpolated.
Emulator: HTTP 400 ValidationException (correct status and code) with `fieldList[0].path` = "segmentIndex" and both messages set to "`segmentIndex` (<i>) must be less than `segmentCount` (<n>)" — the emulator's own sentence, quoting the wire member names in backticks and echoing both submitted values, which are request values and not part of any AWS template.
Why: a parallel-listing worker pool derives its segment assignment from its own worker count, and this refusal is how a mis-derived assignment is reported; ValidationException covers every input defect on ListVectors, so the sentence and the fieldList path are the only discriminators. A client that keys remediation off fieldList[].path never matches "segment_index", and one that asserts or surfaces AWS's wording diverges.
Fix: ListVectors' input validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/list_vectors.rs and the segment cross-field check it calls in crate::state) — emit AWS's fixed sentence with no submitted values and the snake_case fieldList path. Shared root cause with Cause 8 of the open issue 20261029T195812Z-...-8-further.md and Cause 3 of 20261102T105452Z-s3vectors-3-net-new-causes-putvectors-accepts-a.md; this WIRE step must be re-replayed on top of that fix because neither of those issues carries its replay key.
Traces: s3vectors-vbi-list-vectors-segment-mistakes#task#6.

=== Cause 4 of 6: QueryVectors' wrong-width query vector reports the write path's record sentence, the wrong fieldList path and drops the 'Invalid input: ' prefix ===
AWS: Smithy models QueryVectorsInput.queryVector (VectorData, required) and topK (required, @range min 1); the bound index's own `dimension` (@range 1..4096) fixes the admissible query width. A query whose vector width disagrees with the index dimension is refused with HTTP 400 ValidationException carrying a two-level body: top-level `message` exactly "Query vector contains invalid values or is invalid for this index" — all FIXED text, deliberately opaque because it also covers NaN/infinite values — and `fieldList[0]` = {path: "vector", message: "Invalid input: vector must have length <indexDimension>, but has length <submittedLength>"}. In the fieldList entry the fixed text is "Invalid input: vector must have length ", ", but has length "; the two numbers are the index's configured dimension and the submitted width, and the path is the service's field name "vector", not the wire member name.
Emulator: HTTP 400 ValidationException (correct status and code) with `fieldList[0].path` = "queryVector", `fieldList[0].message` = "vector must have length <d>, but has length <n>" (the "Invalid input: " prefix dropped) and the top-level `message` set to that SAME record-level sentence instead of AWS's opaque query-vector sentence — i.e. the PutVectors write-path message re-used on the read path, with no top-level/field-level distinction.
Why: the top-level sentence is what other AWS services forward verbatim when they probe an index (Bedrock's knowledge-base storage validation does exactly this), so consumers match on it; the fieldList entry is where the dimension detail belongs. Collapsing the two means a client cannot tell a malformed query vector from any other QueryVectors input defect, and clients keyed on fieldList[].path never match "vector".
Fix: QueryVectors' input validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/query_vectors.rs and the query-vector check it calls in crate::state) — emit the opaque query-vector sentence at the top level and the prefixed record detail under fieldList path "vector", keeping PutVectors' record-level sentence on the write path. Shares its top-level sentence with Cause 2 of the open issue 20261102T105452Z-s3vectors-3-net-new-causes-putvectors-accepts-a.md, which carries no wire replay key for this step and does not cover the fieldList divergence.
Traces: s3vectors-vbi-query-vectors-mistakes#task#4.

=== Cause 5 of 6: a QueryVectors request with no queryVector gets the generic framework null-check sentence instead of the service's own ===
AWS: Smithy marks QueryVectorsInput.queryVector required. A request that reaches the service without it is refused with HTTP 400 ValidationException whose `message` is exactly "Query must provide a queryVector" — all FIXED text, naming no member path and interpolating nothing. The service does NOT use the generic Smithy framework null-constraint sentence for this member.
Emulator: HTTP 400 ValidationException (correct status and code) with "1 validation error detected. Value at '/queryVector' failed to satisfy constraint: Member must not be null" — the framework's generic missing-member sentence.
Why: an SDK normally refuses this client-side, so the requests that reach the wire are hand-built or cross-service relays — exactly the callers that read the sentence to learn what the far side objected to. ValidationException is the only code available here, so the text is the whole signal; a client asserting or forwarding AWS's wording diverges.
Fix: QueryVectors' input validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/query_vectors.rs) — raise the service's own fixed sentence for an absent queryVector before the generic required-member check reports it.
Traces: s3vectors-vbi-query-vectors-mistakes#task#6.

=== Cause 6 of 6: an unsupported metadata filter operator is refused with the emulator's diagnostic instead of "Invalid filter" ===
AWS: Smithy models QueryVectorsInput.filter as a Document (free-form metadata filter) and ValidationException (400, required `message`, optional `fieldList`) on QueryVectors. A filter using an operator the service does not support is refused with HTTP 400 ValidationException whose top-level `message` and `fieldList[0].message` are both exactly "Invalid filter" — all fixed text, deliberately disclosing nothing about which operator or which clause failed.
Emulator: HTTP 400 ValidationException (correct status and code) with both members set to "unsupported metadata filter operator `<operator>`" — the emulator's own diagnostic, which additionally echoes the offending operator token back from the request.
Why: every filter defect (unknown operator, wrong operand type, malformed nesting) collapses to AWS's one opaque sentence, which is what a client matches on to report "your filter is not valid" and what a cross-service relay forwards. The emulator teaches callers a per-defect diagnostic shape AWS never emits, so filter-error handling written against it breaks against AWS, and no assertion on AWS's sentence can hold.
Fix: QueryVectors' metadata-filter validation (services/service-com-amazonaws-s3vectors-s3vectors/src/ops/query_vectors.rs and the filter parser/validator it calls in crate::state) — collapse every filter-grammar failure to the single fixed sentence with no echoed operator.
Traces: s3vectors-vbi-query-vectors-mistakes#task#7.
