# DeleteVolume ignores Recycle Bin retention rules, so a matched volume is destroyed instead of binned and RestoreVolumeFromRecycleBin can never give it back

> _Note: this issue was identified against the code base at commit `611eef386f1100e1b77f5a1515bab52b7a7a6aeb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteVolume

## Description
One net-new root cause in the ec2 Recycle Bin path.

Cause 1 of 1: a deleted, rule-matched EBS volume never enters the account's Recycle Bin, so every downstream Recycle Bin observable stays empty.
Failing check id: ec2.op-contract-restore-volume-from-recycle-bin

AWS: With an active Recycle Bin retention rule covering EBS_VOLUME (either Region-level or matching at least one of the volume's tag key/value pairs), EC2 DeleteVolume does NOT destroy the volume — it retains it. Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json): `ListVolumesInRecycleBin` — "Lists one or more volumes that are currently in the Recycle Bin", output member `Volumes` (`VolumeRecycleBinInfoList`, xmlName `volumeSet`) whose entries carry `VolumeId`, `RecycleBinEnterTime` and `RecycleBinExitTime`; `RestoreVolumeFromRecycleBin` takes the required `VolumeId` and answers `Return: true`, after which the volume is describable again in state `available`. Neither operation models any error, so the only AWS-defined refusals on these paths are the common EC2 id/permission ones. The rbin side of the contract is modelled in the Recycle Bin service: CreateRule documents "Resources (of the specified type) that have at least one of these tag key and value pairs are automatically retained in the Recycle Bin upon deletion", and a Region-level rule "retains all deleted resources of the specified resource type in the Region in which the rule is created, even if the resources are not tagged". So the general requirement is: rule active -> DeleteVolume on a covered volume moves it to the bin; a VolumeIds-filtered DescribeVolumes on it then answers `InvalidVolume.NotFound` with the message `The volume '<volume-id>' does not exist.` (fixed text plus the requested id); ListVolumesInRecycleBin lists exactly that id with an enter time of the deletion instant and an exit time of enter time + the rule's retention period; RestoreVolumeFromRecycleBin on that id succeeds and the volume returns to `available` and leaves the bin.

Emulator: DeleteVolume consults no retention rule at all. services/service-com-amazonaws-ec2-amazonec2/src/ops/delete_volume.rs validates the id, materialises due detachments, refuses an attached volume, honours DryRun, and then calls `store.remove_volume(&input.volume_id)` — an unconditional, permanent removal. It never calls `crate::state::ComAmazonawsEc2Amazonec2State::move_volume_to_recycle_bin`, and nothing else does either, so `volumes_in_recycle_bin` is only ever empty in a live emulator. ListVolumesInRecycleBin is itself implemented and reads that map (list_volumes_in_recycle_bin.rs), so it correctly reports an empty `volumeSet` for a bin nothing populates; RestoreVolumeFromRecycleBin consequently has no entry to restore. The check reaches this: its fast assertions pass (RestoreVolumeFromRecycleBin on `vol-1234567890abcdef0` is refused `InvalidVolumeID.Malformed` with `The volume 'vol-1234567890abcdef0' is malformed` as AWS does), then it creates an EBS_VOLUME retention rule, creates a tagged 1 GiB gp3 volume, deletes it, and polls ListVolumesInRecycleBin for that id. The bin never lists it, so the bounded 90 s poll (and the preceding 120 s rule-availability poll) never satisfies its predicate and the check is killed by the harness ceiling: `Error: Check timed out after 60.0s`. The failure mode is a never-reached observable, not a wrong status code — no Recycle Bin call ever returns anything but an empty set.

Why: a client that relies on Recycle Bin as its safety net loses data irrecoverably. Against AWS, deleting a covered volume is reversible for the whole retention period; against the emulator the same DeleteVolume is a hard, silent destroy — DescribeVolumes answers NotFound, ListVolumesInRecycleBin answers an empty `volumeSet`, and RestoreVolumeFromRecycleBin can never return the bytes. Any backup/retention or accidental-deletion-recovery workflow validated against the emulator reports success while exercising none of the protection it is testing, and a restore runbook rehearsed on the emulator cannot work.

Fix: the ec2 DeleteVolume handler's state transition (services/service-com-amazonaws-ec2-amazonec2/src/ops/delete_volume.rs — replace the unconditional `store.remove_volume` with a retention decision) plus the cross-service lookup it needs: the Recycle Bin rule store must expose a "which active rules cover resource type EBS_VOLUME and these tags" query that the ec2 crate can consult, and the matching branch must call the already-present `crate::state::ComAmazonawsEc2Amazonec2State::move_volume_to_recycle_bin` so the entry carries `RecycleBinEnterTime` = the deletion instant and `RecycleBinExitTime` = that instant plus the rule's retention period. `RestoreVolumeFromRecycleBin` must then take the entry back out and return the volume to `available`, and a VolumeIds-filtered DescribeVolumes on a binned id must answer `InvalidVolume.NotFound` rather than reporting it as a normal volume.

Related open issue (does NOT cover this check; it is filed against service `rbin`/`CreateRule` and carries no replay key for any ec2 behavioral check): 20261024T155459Z-rbin-createrule-event-propagation.md, "A retention rule has no effect on resource deletion". It describes the same inert-rule root cause from the rbin side and notes that ec2 DeleteVolume/DeleteSnapshot were scaffolded stubs at the time; DeleteVolume is now implemented and still consults no rule, which is what this check now proves from the ec2 side. Fixing the ec2 deletion path is the work this issue names.

Traces: ec2.op-contract-restore-volume-from-recycle-bin (the grounding check; replay it to confirm). The sibling check ec2.op-contract-list-volumes-in-recycle-bin fails on the same cause but is NOT usable as a pass gate — its own body blocks on a fixed 300-second rule-enforcement grace before deleting, which exceeds the suite's 60 s per-check ceiling no matter how the emulator behaves.

## Evidence
Expected (AWS): with an active EBS_VOLUME retention rule whose ResourceTags match the volume's tags, DeleteVolume retains the volume; ListVolumesInRecycleBin then returns a `volumeSet` containing one entry for that VolumeId with RecycleBinEnterTime set and RecycleBinExitTime = enter time + the rule's retention period; a VolumeIds-filtered DescribeVolumes on it is refused with code InvalidVolume.NotFound and message "The volume '<volume-id>' does not exist." (fixed text, with the requested id substituted); RestoreVolumeFromRecycleBin on that VolumeId returns Return=true and the volume is describable again in state `available` and no longer listed in the bin.

Actual (emulator): ListVolumesInRecycleBin returns HTTP 200 with an empty `volumeSet` for the just-deleted, rule-matched volume, forever. DeleteVolume returned 200 and permanently removed the volume (services/service-com-amazonaws-ec2-amazonec2/src/ops/delete_volume.rs calls `store.remove_volume(&input.volume_id)` unconditionally and never calls `move_volume_to_recycle_bin`), so the bin the implemented ListVolumesInRecycleBin reads (`store.volumes_in_recycle_bin`) is never written by any handler. RestoreVolumeFromRecycleBin therefore has no entry to restore. Replay verdict for ec2.op-contract-restore-volume-from-recycle-bin: `Error: Check timed out after 60.0s` — the check's bounded polls for the bin entry never see it, so the observable is never reached rather than a wrong code being returned. The check's fast error-boundary assertion passed, confirming the emulator got as far as the retention path: RestoreVolumeFromRecycleBin(VolumeId="vol-1234567890abcdef0") was refused with code InvalidVolumeID.Malformed and message "The volume 'vol-1234567890abcdef0' is malformed", matching AWS.

## Steps to Reproduce
1. Create a Recycle Bin retention rule on the rbin endpoint: CreateRule with ResourceType="EBS_VOLUME", RetentionPeriod={RetentionPeriodValue:1, RetentionPeriodUnit:"DAYS"}, ResourceTags=[{ResourceTagKey:"<tag-key>", ResourceTagValue:"<tag-value>"}]. Poll GetRule until Status is "available".
2. On the ec2 endpoint, CreateVolume with Size=1, VolumeType="gp3", AvailabilityZone=<any zone DescribeAvailabilityZones reports as available>, and TagSpecifications=[{ResourceType:"volume", Tags:[{Key:"<tag-key>", Value:"<tag-value>"}]}]. Wait for the volume to reach state `available`.
3. Call DeleteVolume on that VolumeId. It answers 200.
4. Call ListVolumesInRecycleBin (no VolumeIds filter). Expected: a `volumeSet` with one entry for that VolumeId carrying RecycleBinEnterTime and RecycleBinExitTime. Actual: an empty `volumeSet`, and it stays empty however long you poll.
5. Call DescribeVolumes(VolumeIds=[that id]). Expected: InvalidVolume.NotFound, "The volume '<volume-id>' does not exist." because the volume now exists only as a bin entry. Actual: the same NotFound, but because the volume was destroyed, not retained.
6. Call RestoreVolumeFromRecycleBin(VolumeId=that id). Expected: Return=true, and the volume is describable again in state `available`. Actual: nothing can be restored — the bin holds no entry for it.
7. Replay the suite check ec2.op-contract-restore-volume-from-recycle-bin: it times out at the 60 s ceiling waiting for the bin entry instead of completing.
