# DynamoDB replica auto scaling is table-scoped, not global-table-scoped: DescribeTableReplicaAutoScaling invents a replica for a non-replicated table, and UpdateTableReplicaAutoScaling's iam:PassRole refusal is mis-worded (2 causes)

> _Note: this issue was identified against the code base at commit `ac0eea33c4f4a66a7179f256fe88fefcc3a441e0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTableReplicaAutoScaling

## Description
Two net-new root causes in the DynamoDB replica-auto-scaling surface. Both are grounded in failing behavioral checks listed under `### dynamodb`. The open issue 20261029T180026Z-dynamodb-global-tables-replica-auto-scaling-indexed-query.md covers replica-auto-scaling calls that answer 501 NotImplemented; it does NOT cover either cause below — these calls are implemented and answer, they just answer wrongly.

=== Cause 1 of 2: DescribeTableReplicaAutoScaling answers 200 with a fabricated local replica for a table that is not part of a global table ===
AWS: Smithy: DescribeTableReplicaAutoScaling input `TableName` (target TableArn, required, @length 1..1024); output `TableAutoScalingDescription`; modeled errors `InternalServerError` (HTTP 500) and `ResourceNotFoundException` (HTTP 400, "The operation tried to access a nonexistent table or index"). The operation's own doc is "Describes auto scaling settings across replicas of the global table at once" — the addressed resource is the GLOBAL TABLE, not the table. Recorded behavior: for an existing single-region table that has no replicas, real AWS refuses the call with HTTP 400 `ResourceNotFoundException` and the message `Global table with name: '<TableName>' does not exist.` — fixed text `Global table with name: '` + `' does not exist.`, with `<TableName>` taken verbatim from the request's TableName. Replica auto scaling is a global-table-only concept, so a plain table is reported as a non-existent global table.
Emulator: answers HTTP 200 with `{"TableAutoScalingDescription": {"TableName": "<table>", "TableStatus": "ACTIVE", "Replicas": [{"RegionName": "<request region>", "ReplicaStatus": "ACTIVE"}]}}` — it resolves the plain table by name and reports the request's own region as a replica of a replication group that does not exist.
Why: this is an over-permissive boundary. A client that uses DescribeTableReplicaAutoScaling to decide whether a table is a global table (or to enumerate the regions it is replicated into) is told every table is a one-region global table, so no caller can ever discover the not-found condition AWS reports, and code that branches on ResourceNotFoundException takes the wrong branch. Any 2xx where AWS returns a 400 also silently passes error-handling tests that should fail.
Fix: the DescribeTableReplicaAutoScaling handler's state read — it must refuse a table that is not a member of a replication group with the modeled ResourceNotFoundException and the global-table wording, instead of synthesizing a single-region description.
Traces: check `dynamodb.autoscaling-and-kinesis-destination-defaults`. Handler: services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/describe_table_replica_auto_scaling.rs lines 138-156 (`crate::state::resolve_table_name_in` then `store.described_replica_auto_scaling(&region, &name, now)`), with the state function `described_replica_auto_scaling` in services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state.rs. The same check then asserts DescribeKinesisStreamingDestination echoes TableName with an empty `KinesisDataStreamDestinations` on a fresh table; that assertion was never reached because the describe-autoscaling call succeeded first.

=== Cause 2 of 2: UpdateTableReplicaAutoScaling's ValidationException wrapping the iam:PassRole denial has the wrong principal and drops the wrapped-service trailer ===
AWS: Smithy: UpdateTableReplicaAutoScaling input `TableName` (required), `ProvisionedWriteCapacityAutoScalingUpdate` (AutoScalingSettingsUpdate, which carries `AutoScalingRoleArn`), `ReplicaUpdates`, `GlobalSecondaryIndexUpdates`; modeled errors InternalServerError, LimitExceededException, ResourceInUseException, ResourceNotFoundException. ValidationException is not modeled for this operation, so the refusal class and its text are recorded behavior only. Recorded behavior: when the update names a customer `AutoScalingRoleArn`, DynamoDB passes that role to Application Auto Scaling through its own replication service-linked role, which is never authorized for iam:PassRole on a customer role, and answers HTTP 400 `ValidationException` whose Message is the Application Auto Scaling `AccessDeniedException` quoted verbatim: it BEGINS with `User: arn:aws:sts::<account>:assumed-role/<role>/<session>`, continues with the fixed text ` is not authorized to perform: iam:PassRole on resource: <AutoScalingRoleArn> because no identity-based policy allows the iam:PassRole action (Service: `, and ENDS with `; Proxy: null)`. Fixed text: `User: `, ` is not authorized to perform: iam:PassRole on resource: `, ` because no identity-based policy allows the iam:PassRole action (Service: `, `; Proxy: null)`. Variable parts: the account id and the assumed-role session path (from the calling service-linked role), the role ARN from the request's AutoScalingRoleArn, and the wrapped service/status/error-code/request-id values in the trailer (the request id is per-run and is not a requirement).
Emulator: returns ValidationException whose Message is `AccessDeniedException: User: arn:aws:iam::<account>:user/emulator is not authorized to perform: iam:PassRole on resource: <AutoScalingRoleArn> because no identity-based policy allows the iam:PassRole action`. Three divergences: (a) it prefixes the message with the literal `AccessDeniedException: ` where AWS's message starts at `User: `; (b) it renders the principal as the caller's own IAM user ARN (`arn:aws:iam::<account>:user/...`) instead of the STS assumed-role ARN of the role actually attempting the pass (`arn:aws:sts::<account>:assumed-role/...`); (c) it omits the wrapped-service trailer entirely — no `(Service: ...; Status Code: ...; Error Code: AccessDeniedException; Request ID: ...; Proxy: null)`.
Why: the error code and status are right but the message is not AWS's. Clients and SDK error-parsing helpers that read the embedded denial to learn WHICH principal needs iam:PassRole are told it is the caller's own user, so operators grant the permission to the wrong identity; tooling that parses the `(Service: ...; Proxy: null)` trailer to recover the nested service and error code finds nothing to parse.
Fix: the UpdateTableReplicaAutoScaling handler's refusal path and its message builder — the caller resolution and the pass-denial text, not the handler's control flow.
Traces: check `dynamodb.table-replica-auto-scaling-update-reflected` (the check's positive control — update without AutoScalingRoleArn binding the AWSServiceRoleForApplicationAutoScaling service-linked role and the settings reading back at MinimumUnits=5/MaximumUnits=12 — passed; only the wrapped-denial message assertion failed). Handler: services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/update_table_replica_auto_scaling.rs lines 166-177 (`crate::state::unpassable_auto_scaling_role`, `crate::state::request_caller`, `crate::state::auto_scaling_role_pass_denied`), with those functions in services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state.rs.

## Steps to Reproduce
Cause 1:
1. CreateTable with a composite key (pk S HASH, sk S RANGE), BillingMode=PAY_PER_REQUEST; wait until DescribeTable reports TableStatus=ACTIVE. Add no replicas.
2. Call DescribeTableReplicaAutoScaling(TableName=<that table>).
3. AWS: HTTP 400 ResourceNotFoundException, Message "Global table with name: '<TableName>' does not exist." Emulator: HTTP 200 with a TableAutoScalingDescription listing the request region as an ACTIVE replica.

Cause 2:
1. Create an IAM role trusted by application-autoscaling.amazonaws.com (any role ARN the caller is not authorized to pass).
2. CreateTable with BillingMode=PROVISIONED (RCU/WCU 5/5) and a stream enabled; wait ACTIVE. RegisterScalableTarget + PutScalingPolicy on dynamodb:table:WriteCapacityUnits, then UpdateTable with ReplicaUpdates=[{Create:{RegionName:<second region>}}] and wait for the replica to be ACTIVE.
3. Call UpdateTableReplicaAutoScaling(TableName=<table>, ProvisionedWriteCapacityAutoScalingUpdate={MinimumUnits:5, MaximumUnits:15, AutoScalingRoleArn:<the customer role ARN>, ScalingPolicyUpdate:{...}}).
4. Inspect Error.Code and Error.Message. AWS: ValidationException whose message begins "User: arn:aws:sts::<account>:assumed-role/..." and ends "; Proxy: null)". Emulator: ValidationException whose message begins "AccessDeniedException: User: arn:aws:iam::<account>:user/emulator ..." and has no trailer.
