# ds-data serves a directory whose data access is Disabled (no DATA_DISABLED gate), mis-words the duplicate-user ConflictException, and still echoes a constant Realm / Enabled=true (4 causes)

> _Note: this issue was identified against the code base at commit `b64c3d45927e2833db57dde0eaeae2a33a5b497f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateUser

## Description
Four distinct root causes, all grounded in failing behavioral checks the suite lists under service `ds` (every one of them drives the ds control plane to build a live Managed Microsoft AD and then exercises the ds-data data plane against it). All four are in one service, so they are bundled: a fixer must close ALL FOUR and re-replay every check id in trace_ids before submitting.

=== Cause 1 of 4: ds-data has no data-access gate — every operation against a directory whose DataAccessStatus is 'Disabled' is served instead of refused with AccessDeniedException / Reason DATA_DISABLED ===
Failing check: ds.ds-data-access-must-be-enabled-before-the-data-plane-answers
AWS: the ds-data endpoint answers NOTHING for a directory until the ds control plane has turned the feature on. Smithy (com.amazonaws.directoryservicedata): CreateUser declares AccessDeniedException @error client, httpError 403 (POST /Users/CreateUser), ListUsers declares the same error, and AccessDeniedException carries member Reason -> AccessDeniedReason enum [IAM_AUTH, DIRECTORY_AUTH, DATA_DISABLED]; its doc states "You don't have permission to perform the request or access the directory." The DATA_DISABLED value exists for exactly this predicate. Recorded behavior: for an Active directory on which EnableDirectoryDataAccess has never been called (ds DescribeDirectoryDataAccess reports DataAccessStatus 'Disabled'), every ds-data operation — reads and writes alike, because the gate is on the DIRECTORY and not on the operation — is refused with AccessDeniedException, HTTP 403, Reason 'DATA_DISABLED', and this message, which is fixed text in full with no variable parts: "DS Data feature is not enabled on this directory. This feature must first be enabled by calling the EnableDirectoryDataAccess API." The refused write leaves nothing behind: after EnableDirectoryDataAccess the paginated ListUsers inventory does not contain the name the refused CreateUser used.
Emulator: the refusal never happens and the write lands. CreateUser against that same directory answered HTTP 200 with {'DirectoryId': <id>, 'SAMAccountName': <name>, 'SID': 'S-1-5-21-…'} — i.e. the check's `_refusal()` helper raised because the call SUCCEEDED. The handler never consults the data-access toggle at all: services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/ops/create_user.rs:227 calls `store.directory_for_write(&input.directory_id)`, whose comment states "A create is a write, so it is what materialises the directory record: the `ds` control plane that creates a directory is not part of this API" — so the ds-data store invents its own directory record and no AccessDeniedException variant is constructible for a switched-off directory on any operation.
Why: EnableDirectoryDataAccess is the only switch that makes the Directory Service Data API usable, and against the emulator it is a no-op: a client that provisions a directory and forgets to enable data access is told by the emulator that its users were created, and discovers in production that all seventeen ds-data operations were 403ing. Code that branches on Reason=DATA_DISABLED (retry after enabling, or surface "turn on DS Data") is dead code in the emulator, and a write that AWS discards is persisted, so the emulator's and AWS's object inventories diverge permanently from that point.
Fix: a shared data-access gate in the ds-data crate, applied ahead of every operation handler (and ahead of ClientToken/NextToken handling), that reads the directory's data-access state from the ds control plane's directory record rather than materialising a directory locally — the same cross-plane state seam Cause 3 needs. `directory_for_write` must stop creating directories.
Relation to open issues: 20261022T085720Z-ds-data-no-directory-authorization-gate-absent-directoryid.md and 20261022T085720Z-ds-ds-data-cross-plane-contract-broken-ds.md both concern an ABSENT DirectoryId and the IAM_AUTH reason. This cause is a different predicate and a different modeled Reason: the directory EXISTS, is Active and is owned by the caller, and the refusal AWS gives is DATA_DISABLED with its own fixed message. Neither open issue carries this check's replay key.

=== Cause 2 of 4: the duplicate-sAMAccountName ConflictException message is the emulator's own wording and discloses the account name AWS withholds ===
Failing check: ds.ds-data-duplicate-sam-account-name-rejected-and-original-untouched
AWS: Smithy declares ConflictException @error client, httpError 409 on CreateUser, doc "This error will occur when you try to create a resource that conflicts with an existing object." Recorded behavior for a second CreateUser carrying an existing SAMAccountName: ConflictException, HTTP 409, message "User already exists in directory <DirectoryId>." — the fixed text is "User already exists in directory " plus the trailing period; the only variable part is the DirectoryId taken from the request. The object kind ("User") is named and the sAMAccountName is NOT disclosed.
Emulator: the code and status are right (ConflictException/409 — the check's Code assertion passed) and the original user is left untouched, but the message is a different template: "<SAMAccountName> already names an object in directory <DirectoryId>" (recorded: "sim2realOrig already names an object in directory d-003ba5fe5a") — it leads with the account name AWS withholds, calls the thing a generic "object" instead of naming the User kind, and omits the trailing period.
Why: the error message is part of the contract for this error class and its rule is known (it is composed from the request's DirectoryId). A client or test that matches on AWS's wording does not match, and the emulator discloses the existing account's name in a refusal AWS deliberately keeps resource-free.
Fix: the conflict-message builder of the duplicate-object path — services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/ops/create_user.rs:229-236 — and its siblings for the group/member conflict paths, which must use the per-object-kind template ("User already exists in directory <id>.", "Group already exists in directory <id>.") rather than one generic "already names an object" string. The ClientToken-reuse ConflictException at create_user.rs:213-221 is a different refusal and is not covered here.

=== Cause 3 of 4: every ds-data page/record echoes the constant realm 'corp.example.com' instead of the directory's own domain name ===
Failing check: ds.ds-data-list-users-pagination-is-exact-and-reaches-the-token-layer
AWS: ListUsersResult$Realm (Smithy: target Realm, length 1..255, pattern ^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+[.]?$) reports the AD domain the data plane resolved the listing in — the name the ds control plane was given at CreateMicrosoftAD (DirectoryDescription$Name). Recorded behavior: EVERY page of ListUsers for a directory created with Name=<fqdn> carries Realm=<fqdn>.
Emulator: every page carries the build-time constant. The check aborted with "expected every page to echo the directory's own realm, expected 'sim2real-behav-5fce8c920388.example.com', got 'corp.example.com' on page 1" — i.e. the realm is independent of the directory's actual domain name, so it is wrong for every directory.
Why: the realm is what a client uses to build an LDAP/Kerberos principal against the directory it just created, and it is also the value ds-data's own Realm request members are matched against — so a caller that correctly passes its own fqdn is treated as naming a foreign domain. It also blocks the pagination assertions behind it (the check never reaches the exact-page-size and fabricated-NextToken legs, which assert ValidationException / Reason INVALID_NEXT_TOKEN / "Invalid parameter: NextToken.").
Fix: the ds-data state must take the domain name from the ds control-plane directory record when it materialises a Directory, instead of a module constant: services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/state.rs (`DEFAULT_REALM` constant and `Directory::new`), with the DN/UPN builders and the realm matcher following. This is the SAME root cause as Cause 2 of open issue 20261023T134711Z-ds-data-user-objects-are-not-real-active.md, which was grounded only in ds.ds-data-user-create-describe-search-roundtrip; it is restated here because this failing check is a second, independent witness (the ListUsers projection, not DescribeUser) and its replay key is not carried by that issue, so fixing that issue alone will not get this check re-replayed.

=== Cause 4 of 4: a ds-data-created user comes back Enabled=true, so nothing can be enabled afterwards ===
Failing check: ds.reset-user-password-enables-the-ds-data-user-it-names
AWS: Smithy CreateUser's input is {DirectoryId, SAMAccountName, EmailAddress, GivenName, Surname, OtherAttributes, ClientToken} — there is NO password member, and Active Directory does not activate a password-less account. Recorded behavior only: DescribeUser/UserSummary report Enabled=false for an account created this way, and ds ResetUserPassword (the control-plane call that sets the first password) is what flips it to true.
Emulator: the created user is Enabled=true immediately — "expected a ds-data CreateUser to land DISABLED (Enabled is False) so the reset below has something to flip, got Enabled=True for 's2rRstb57fc703f4bc'" — set unconditionally at services/service-com-amazonaws-directoryservicedata-directoryservicedata/src/ops/create_user.rs:250 (`enabled: true`).
Why: the cross-plane effect that ResetUserPassword has on the ds-data object is unobservable, so a provisioning flow that asserts "account created, not yet usable → set password → account usable" passes against the emulator with the middle step doing nothing, and the ds-data Enabled flag can never be used to tell a half-provisioned account from a live one. It also blocks the rest of this check, whose later legs assert the UserDoesNotExistException and complexity refusals of ResetUserPassword.
Fix: CreateUser's handler (create_user.rs:250) must create the account inactive, and the ds ResetUserPassword / ds-data EnableUser-DisableUser transitions must be the only things that move the flag — which for ResetUserPassword means the same cross-plane seam as Causes 1 and 3. This is the SAME root cause as Cause 1 of open issue 20261023T134711Z-ds-data-user-objects-are-not-real-active.md; it is restated because this check is a second witness of it (through ds ResetUserPassword rather than DescribeUser) and that issue does not carry this check's replay key.
