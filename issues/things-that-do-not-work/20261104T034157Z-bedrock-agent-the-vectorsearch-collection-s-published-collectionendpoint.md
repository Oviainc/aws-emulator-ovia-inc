=== Cause 1 of 1: a collection's published data-plane endpoint serves the AWS-JSON RPC dispatcher instead of the OpenSearch REST data plane ===
AWS: recorded behavior only for the collection data plane — the opensearchserverless Smithy model covers only the control plane (BatchGetCollection input {ids,names}, output collectionDetails[] carrying the collection's published endpoint; errors InternalServerException 500 / ValidationException 400); a collection's data plane is the OpenSearch REST API and is not modeled. Smithy consulted on the Bedrock side: bedrock-agent CreateKnowledgeBase (PUT /knowledgebases/, success 202; required name/roleArn/knowledgeBaseConfiguration plus storageConfiguration; errors AccessDeniedException 403, ConflictException 409, ValidationException 400, ThrottlingException 429, ServiceQuotaExceededException 402) takes an OPENSEARCH_SERVERLESS storageConfiguration naming collectionArn + vectorIndexName + fieldMapping, i.e. the index must ALREADY exist in the collection before the knowledge base is created. Recorded behavior: once a VECTORSEARCH collection is ACTIVE and its endpoint is published, a SigV4-signed (signing name `aoss`) `PUT https://<collectionEndpoint>/<indexName>` carrying a knn_vector mapping — exactly what opensearch-py's indices.create issues, and which carries NO x-amz-target header because the OpenSearch REST API has no RPC target — is accepted (200/201).
Emulator: that request is answered HTTP 400 with body {"__type":"SerializationException","message":"missing required header `x-amz-target`"}. Every part of that response is fixed text emitted by the JSON-protocol front door — the status 400, the __type SerializationException and that message contain nothing derived from the request — which is exactly what shows the request was never routed to a data-plane handler. No OpenSearch REST verb is servable on a collection endpoint for any principal.
Why: a client that provisions a Bedrock vector knowledge base the documented way is stopped at step one, and everything downstream is unobservable: knowledge-base lifecycle status transitions, a deleted knowledge base answering GetKnowledgeBase with 404 ResourceNotFoundException rather than a 500, ingestion-job lifecycle progression STARTING/IN_PROGRESS->COMPLETE and its appearance in ListIngestionJobs, ingestion-job timestamp precision, document blob round-tripping, and resource-policy round-trip enforcement are all unverified.
Fix: the opensearchserverless collection data plane plus the emulator's host/endpoint routing table — route the published collection endpoint host to an OpenSearch REST handler (index create/get/delete, document index/search/count) that authorises SigV4 `aoss` requests against the collection's data-access and network policies, instead of letting that host fall through to the AWS-JSON x-amz-target dispatcher.
Traces: 3 checks surface the 400 directly as opensearchpy.exceptions.RequestError(400, '{"__type":"SerializationException",...}') — bedrock-agent.get-deleted-resource-returns-404-not-500, bedrock-agent.ingestion-job-lifecycle, bedrock-agent.knowledge-base-lifecycle. 3 more surface it wrapped by their own retry helper as AssertionError 'could not create AOSS vector index <name>: RequestError(400, ...)' — bedrock-agent.ingestion-job-timestamp-precision-preserved, bedrock-agent.knowledge-base-document-blob-round-trip, bedrock-agent.resource-policy-round-trip-enforced.
