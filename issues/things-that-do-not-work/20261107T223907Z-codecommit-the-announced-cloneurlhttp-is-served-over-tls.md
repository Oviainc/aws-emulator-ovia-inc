=== Cause 1 of 1: the address GetRepository/CreateRepository announce in repositoryMetadata.cloneUrlHttp presents a certificate no default git client trusts, so `git clone` fails at the TLS handshake and nothing behind the git transport can be exercised ===

AWS: Smithy com.amazonaws.codecommit#CodeCommit_20150413 — GetRepository/CreateRepository return RepositoryMetadata whose member cloneUrlHttp is documented as "The URL to use for cloning the repository over HTTPS" (and cloneUrlSsh for SSH). Beyond the shape this is recorded behavior only: the announced origin is an address the service answers git smart-HTTP on (`<cloneUrlHttp>/info/refs?service=git-upload-pack`, `git-upload-pack`, `git-receive-pack`) over TLS with a certificate the caller's default trust store accepts. With CodeCommit credentials (either `aws codecommit credential-helper` for an assumed role, or an IAM service-specific credential pair for ServiceName=codecommit.amazonaws.com embedded in the URL), an UNMODIFIED git client — no extra CA material, no http.sslVerify=false — completes `git clone <cloneUrlHttp>`, and then: a fast-forward `git push` lands and the control plane (GetBranch/GetCommit/GetFile) reports the pushed objects; a push that is not a fast-forward is refused by receive-pack with a non-zero exit and git's "! [rejected] ... (non-fast-forward)"/"fetch first" stderr while the remote ref is unchanged; a `git push origin <tag>` creates a ref that CodeCommit then treats as a tag — which is the ONLY way to create one, since no CodeCommit API operation creates a tag, and it is what makes MergeBranchesByFastForward's BranchNameIsTagNameException reachable; and an IAM Deny on codecommit:GitPush conditioned on codecommit:References (with the documented mandatory `Null: {"codecommit:References": "false"}` guard) is evaluated inside the receive-pack negotiation, refusing the named ref while other refs still land. Hosts, ports and generated repository names are per-environment and are not the requirement; the requirement is that the address the emulator itself announces be dialable, as-is, by the same stock git client that just read the metadata.

Emulator: the announced cloneUrlHttp is published as `https://<loopback-host>:<ephemeral-port>/v1/repos/<repositoryName>` on a listener that terminates TLS itself with a certificate generated at run time and chained to no trusted root, so the handshake is rejected before any git protocol byte is exchanged. Every one of the five checks below fails on it, with git exiting 128 and stderr exactly of the form `fatal: unable to access '<cloneUrlHttp>/': SSL certificate OpenSSL verify result: self-signed certificate (18)`. The fixed text of that message is git's ("fatal: unable to access ... : SSL certificate OpenSSL verify result: self-signed certificate (18)"); its variable part is the URL the emulator itself announced. This is not the runner's trust configuration and not a missing tool: the same checks call require_tools("git", "aws"), their SigV4 control-plane calls to the same emulator (CreateRepository, PutFile, CreateBranch, GetRepository, IAM CreateRole/PutRolePolicy/CreateServiceSpecificCredential, STS AssumeRole) all succeed from the same process, and only the origin the emulator announces for git is undiallable. No status code or error code is produced at all — the refusal happens below HTTP.

Why: cloning cloneUrlHttp is the documented way to use a CodeCommit repository, so a client that reads repository metadata and hands it to git cannot reach the repository at all, and cannot work around it without disabling TLS verification, which no stock git/credential-helper configuration does. Everything reachable only through that transport is consequently unverifiable in this emulator: per-ref IAM authorization of codecommit:GitPush (CodeCommit's only branch-protection mechanism, including the well-known Null-guard footgun where a Deny missing the guard widens from one ref to every ref), the server-side non-fast-forward refusal, read-back of git-pushed commits through the API, and the existence of git tags — so MergeBranchesByFastForward's BranchNameIsTagNameException can never be exercised. An emulator that silently authorizes every push, or that never serves one, is indistinguishable from a correct one; a user who protects main here and verifies it here gets no protection.

Fix: the git smart-HTTP transport of the codecommit crate and the clone-URL projection that advertises it — the cloneUrlHttp/cloneUrlSsh construction in the repository-metadata serializer and the listener `services/service-com-amazonaws-codecommit-codecommit-20150413/src/service/git_http.rs` is served on, together with whatever seam the core offers for serving a plane on a transport a default client already trusts (the core's listeners terminate TLS with self-signed material: vendor/server/src/listeners.rs — `Listeners::tcp` ~:239 and `Listeners::http` ~:334, from the generated certificate ~:211). Announce git smart-HTTP on a scheme/trust the caller can dial unmodified — the same move that closed the kinesisvideo DataEndpoint cause — keeping the `/v1/repos/<repositoryName>` path form; and once the transport serves, the receive-pack authorization hook must evaluate the caller's IAM policy on every authorization step, including the keyless step that carries no codecommit:References key.
