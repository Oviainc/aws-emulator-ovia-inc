# lambda__s3__s3control: a Lambda role's read through an access point whose policy Denies it never settles — the AP-ARN data path and its policy are not enforced, so the two-arm outcome never appears (1 cause)

> _Note: this issue was identified against the code base at commit `664a72bba61e2c00bac218cc260309c5c90c944d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject (via S3 access point ARN; chain: s3control CreateAccessPoint/PutAccessPointPolicy/GetAccessPointPolicy + lambda Invoke)

## Description
One net-new root cause found by replaying the behavioral suite. The failing check is listed under the composite suite heading `### lambda__s3__s3control`; its three constituent services (lambda, s3, s3control) are all bootstrapped, so the finding is filed rather than deferred. The service token is taken verbatim from that heading.

--- Cause 1 of 1: an access-point policy Deny is never applied on the data path, so the 'denied through the AP / served through the bucket' outcome never settles and the invocation poll runs out its budget ---

AWS: an S3 access point is a named data path onto one bucket (Smithy: s3control CreateAccessPoint PUT /v20180820/accesspoint/{Name}, returning AccessPointArn; PutAccessPointPolicy PUT /v20180820/accesspoint/{Name}/policy with Policy required; GetAccessPointPolicy GET the same URI returning Policy; DeleteAccessPointPolicy DELETE it — all host-prefixed `{AccountId}.` with AccountId @hostLabel/x-amz-account-id pattern ^\d{12}$). S3 accepts that access point ARN in the Bucket field of a data-plane call and resolves it to the underlying bucket. Authorization on that path is the identity policy AND the access point policy AND (because the bucket policy delegates via the s3:DataAccessPointAccount condition) the bucket policy; an explicit Deny in the ACCESS POINT policy wins over the identity Allow, and it governs ONLY the access point path — the same key read by bucket name is unaffected. So with an AP policy that Denies s3:GetObject for a principal selected by `ArnEquals aws:PrincipalArn <role-arn>`, the same Lambda invocation must come back with two different outcomes in one payload: the access-point arm refused with HTTP 403, Code `AccessDenied`, and the bucket arm returning the object bytes. The refusal message's fixed text is `User: <caller-arn> is not authorized to perform: s3:GetObject on resource: "<access-point-arn>/object/<key>" with an explicit deny in a resource-based policy`; its variable parts are the caller ARN (here the assumed-role session ARN arn:aws:sts::<account>:assumed-role/<role-name>/<function-name>, all three taken from the invoking identity), the access point ARN, and the object key from the request. Removing the Deny with DeleteAccessPointPolicy must then let the SAME invocation read the bytes through the access point too, and GetAccessPointPolicy must afterwards refuse with the no-policy error rather than return the deleted document. Recorded behavior only for the settling timing: the check tolerates propagation by polling the observable outcome rather than sleeping.

Emulator: the outcome never settles. The check exhausts its budget — `Check timed out after 60.0s` — while polling the Lambda invocation for 'AP arm AccessDenied while the bucket arm serves the object'. Neither arm of the expected payload is ever produced, so no 403/AccessDenied is observed on the access-point arm and the repair arm (delete the AP policy, read through the AP) is never reached. This is the data-plane access-point gap seen directly by the s3control-only check in open issue 20261103T080052Z-s3control-s3-policy-enforcement-and-batch-operations-diverge.md (its Cause 3: a read addressed by access point ARN answers `NoSuchBucket` and the stored AP policy is never evaluated) and by 20261030T064829Z-s3control-an-internet-borne-read-of-a-vpc.md; neither of those issues carries this cross-service check's replay key, and neither covers the Lambda-identity arm (a Deny selected by `aws:PrincipalArn` against an assumed-role session) or the bucket-delegation arm that must keep serving.

Why: a client that fronts a bucket with access points to carve up access gets no enforcement and no usable answer at all — a role an access point policy explicitly denies is not refused with AccessDenied, so least-privilege boundaries built on access point policies are silently absent, while the caller instead hangs or sees a 404-class error for an object that exists. Error-handling branches keyed on AccessDenied are never taken, and the central access-point invariant (an AP Deny governs only the AP path, never the direct bucket path) cannot be observed, so a client cannot distinguish 'denied by the access point' from 'bucket missing' from 'not yet propagated'.

Fix: the S3 data-plane Bucket-field resolver must parse an access point ARN and route the call to that access point's bucket, and the GetObject authorization path must evaluate the stored access point policy — Deny wins, condition keys including aws:PrincipalArn resolved against the caller's assumed-role session ARN — combined with the identity policy and the bucket policy's s3:DataAccessPointAccount delegation, emitting 403 AccessDenied with the explicit-deny message on the access-point path only, and leaving the direct bucket path unaffected. DeleteAccessPointPolicy must make that decision revert for subsequent reads.

## Steps to Reproduce
1. Create a bucket and PutObject a key (e.g. data/report.txt) with known bytes.
2. s3control CreateAccessPoint(AccountId, Name, Bucket=<bucket>) and keep the returned AccessPointArn.
3. s3 PutBucketPolicy on <bucket> delegating to access points: Allow Principal {"AWS":"*"} Action "*" on arn:aws:s3:::<bucket> and arn:aws:s3:::<bucket>/* with Condition StringEquals s3:DataAccessPointAccount = <account>.
4. iam CreateRole trusting lambda.amazonaws.com and put_role_policy allowing s3:GetObject on arn:aws:s3:::<bucket>/* and <ap-arn>/object/*; lambda CreateFunction (python3.12) with a handler that, for each of {"access_point": <ap-arn>, "bucket": <bucket>}, calls s3.get_object(Bucket=<that value>, Key=<key>) and returns either the body or the error Code/Message; wait for State=Active.
5. s3control PutAccessPointPolicy(AccountId, Name, Policy=Deny s3:GetObject on <ap-arn>/object/* with Condition ArnEquals aws:PrincipalArn = <role-arn>); confirm GetAccessPointPolicy reads Effect "Deny" back.
6. lambda Invoke the function with {"key": <key>, "paths": {"access_point": <ap-arn>, "bucket": <bucket>}}. On AWS the payload is {"bucket": {"body": <bytes>}, "access_point": {"code": "AccessDenied", "message": "User: arn:aws:sts::<account>:assumed-role/<role-name>/<function-name> is not authorized to perform: s3:GetObject on resource: \"<ap-arn>/object/<key>\" with an explicit deny in a resource-based policy"}}. On the emulator that pair never appears — polling it exhausts the check budget (the access-point arm does not answer 403 AccessDenied; the s3control-only companion check shows NoSuchBucket on that path).
7. s3control DeleteAccessPointPolicy(AccountId, Name) and Invoke again: on AWS both arms now return the bytes, and GetAccessPointPolicy refuses with the no-such-policy error.
