# pricing catalog metadata diverges from the published Price List API across DescribeServices, GetAttributeValues and GetProducts (4 causes)

> _Note: this issue was identified against the code base at commit `3a2a2ae2b1ffef990857b0544f1895e5cc0c5b77`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeServices

## Description
The Price List API is served entirely out of one seeded, read-only catalog (services/service-com-amazonaws-pricing-awspricelistservice/src/state.rs documents this: DescribeServices.AttributeNames is ServiceCatalog::attribute_names, GetAttributeValues is the distinct values those attributes take on the SAME products GetProducts returns). That catalog does not match the catalog AWS publishes, so three different operations answer 200 with the wrong content. FOUR net-new causes, all on service `pricing`, all distinct divergence clusters in this replay. Two further pricing clusters in the same replay are already owned and are NOT part of this issue: the GetProducts 400-with-no-Message cluster (20261102T121014Z-pricing-getproducts-400-validation-refusals-carry-no-error.md) and the incomplete Compute Instance offer cluster (20261106T202905Z-pricing-getproducts-serves-an-incomplete-compute-instance-offer.md).

Cause 1 of 4: GetAttributeValues publishes the wrong value set for an EC2 attribute, so every page after the first lands on different values.
AWS: Smithy — GetAttributeValues(ServiceCode required, AttributeName required, NextToken, MaxResults @range 1..10000) returns AttributeValues (AttributeValueList of AttributeValue{Value}) plus NextToken, @paginated{inputToken:NextToken, outputToken:NextToken, items:AttributeValues, pageSize:MaxResults}. The model does not enumerate the values themselves, so for the value SET this is recorded behavior only: the recording of GetAttributeValues over the AmazonEC2 instance-type vocabulary continues the page with the value `a1` where the emulator serves `c1.medium` — i.e. AWS publishes family-level instance-type values alongside the per-size ones, and the emulator's vocabulary does not contain them. Status 200 in both cases; this is purely a body divergence.
Emulator: at the same offset of the same paginated walk, `$.AttributeValues[1]` is `{"Value": "c1.medium"}` instead of `{"Value": "a1"}`. ServiceCatalog::attribute_values (state.rs:176-183) derives the vocabulary as the distinct values of that attribute over the SEEDED products only, and the EC2 seed (EC2_INSTANCE_TYPES, state.rs:1607ff) carries only per-size instance types, so values AWS publishes are absent and every subsequent page is shifted onto different entries.
Why: a client enumerating an attribute's vocabulary (the documented way to discover legal GetProducts filter values) gets a value list that is both incomplete and mis-paged. A value AWS accepts as a TERM_MATCH filter value cannot be discovered, and a client that pages through the vocabulary and keys later requests off page N gets a different slice than against AWS.
Emulator fix: the catalog seed and the vocabulary derivation for this service — ServiceCatalog::attribute_values / the EC2 product seed in the pricing service's state, not the GetAttributeValues handler's paging arithmetic (the page boundaries follow from the vocabulary).
Traces: pricing-attribute-values-pagination#task#2 (representative); pricing-ecc-traj-service-code-and-filter-value-discovery#task#6.

Cause 2 of 4: DescribeServices reports a derived attribute-name list instead of the service's published one — it omits names AWS publishes and adds names AWS does not.
AWS: Smithy — DescribeServices returns Services (ServiceList of Service{ServiceCode, AttributeNames}) plus FormatVersion/NextToken. The membership of AttributeNames is not modelled, so recorded behavior only: for ServiceCode AmazonEC2 the recording publishes AttributeNames as [termType, productFamily, servicecode, location, instanceType, usagetype] — note it includes `termType` and `productFamily`, and it is NOT in alphabetical order.
Emulator: the same step answers 200 with a 25-name alphabetically sorted list (capacitystatus, currentGeneration, group, groupDescription, instanceFamily, instanceType, licenseModel, location, locationType, maxIopsvolume, maxThroughputvolume, memory, normalizationSizeFactor, operatingSystem, operation, physicalProcessor, preInstalledSw, regionCode, servicecode, servicename, storageMedia, tenancy, usagetype, vcpu, volumeApiName, volumeType) — `termType` and `productFamily` are MISSING. ServiceCatalog::new (state.rs:162-172) builds attribute_names as the BTreeSet union of the seeded products' attribute keys, so (a) the order is alphabetical rather than the service's published order and (b) any published attribute that is not a product-attribute key of a seeded product (termType, productFamily) can never appear.
Why: DescribeServices is the documented discovery entry point — a client reads AttributeNames and then calls GetAttributeValues/GetProducts for each. Because `termType` and `productFamily` are absent, a client cannot discover the two attributes that select a term type and a product family, and a client that iterates AttributeNames issues calls for attribute names AWS never advertises.
Emulator fix: the catalog's attribute-name list for a service (ServiceCatalog::attribute_names, seeded in the pricing service's state) must be the published list in its published order, independent of which keys the seeded products happen to carry.
Traces: pricing-discover-services-and-attributes#task#1.

Cause 3 of 4: GetProducts over an EC2 filter set returns a different first offer AND a different page token, so a filtered price query returns a different result set than AWS.
AWS: Smithy — GetProducts(ServiceCode required, Filters @length 0..50, FormatVersion, NextToken, MaxResults @range 1..100) returns FormatVersion, PriceList (PriceListJsonItems — each item an aws_v1 offer document) and NextToken, @paginated{items:PriceList, pageSize:MaxResults}. The documents' content is recorded behavior only: the recording's first PriceList entry is the t3.nano Compute Instance offer whose product.attributes carry the full published EC2 attribute set (clockSpeed, ecu, networkPerformance, processorArchitecture, processorFeatures, dedicatedEbsThroughput, dedicatedEbsThroughputDescription, enhancedNetworkingSupported, intelAvxAvailable, intelAvx2Available, intelTurboAvailable, classicnetworkingsupport, vpcnetworkingsupport, instanceFamilyCategory, gpuMemory, marketoption, availabilityzone, storage, tenancy, capacitystatus, ...), and the response carries a NextToken continuing that filtered set.
Emulator: the same request answers 200 but both `$.PriceList[0]` and `$.NextToken` diverge — the emulator's filtered set is ordered/populated differently and its offer document is not the recorded one (its attributes come straight from the product seed via offer_document, state.rs:1134-1162, which writes only the seeded attribute keys), and its continuation token does not describe the same remaining set.
Why: a client prices a workload off PriceList[0] and then pages with NextToken. A different first offer means a different price for the same filter set, and a divergent NextToken means the rest of the result set is a different population — so a cost estimate built by paging GetProducts is wrong in both the figure it reports and the products it covers.
Emulator fix: the GetProducts handler's filtered-selection and paging (its result ordering and NextToken encoding) together with the EC2 product seed/offer-document builder in the pricing service's state. Overlaps with, but is not covered by, open issue 20261106T202905Z-pricing-getproducts-serves-an-incomplete-compute-instance-offer.md (that issue owns a different cluster and does not carry this cluster's replay key, and says nothing about NextToken).
Traces: pricing-ecc-traj-ec2-vocabulary-in-price-filters#task#4 (representative); pricing-ecc-traj-get-products-request-mistakes#task#7; pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#1; pricing-ecc-traj-upstream-lookup-page-token-and-os-split#task#4.

Cause 4 of 4: GetAttributeValues answers 200 with an EMPTY AttributeValues list for an attribute AWS publishes values for (the EC2 operating-system vocabulary).
AWS: Smithy — GetAttributeValues returns AttributeValues (list of AttributeValue{Value}); modelled errors for an unusable request are InvalidParameterException / NotFoundException (both httpError 400), so a published attribute of a published service answers 200 with a NON-empty list. Recorded behavior for the value set: the recording's first two entries are {"Value": "Linux"} and {"Value": "Windows"}.
Emulator: the step answers 200 with nothing at `$.AttributeValues[0]` or `$.AttributeValues[1]` — the list is empty (detail: "expected {'Value': 'Linux'}, got None" and "expected {'Value': 'Windows'}, got None"). The vocabulary is derived on read from the seeded products (ServiceCatalog::attribute_values, state.rs:176-183), so an attribute no seeded product carries a value for yields an empty page rather than the published vocabulary. It also means the emulator cannot report the platform split (Linux vs Windows) at all.
Why: an empty 200 is indistinguishable from "this attribute has no values", so a client doing filter-value discovery concludes the service prices no operating systems and either skips the platform dimension or builds a single-platform estimate — a mixed-OS estimate is then silently wrong. Related, but not the same cluster and not covering it: open issues 20261103T043017Z-pricing-getproducts-5-net-new-root-causes-ec2.md and 20261108T114447Z-ec2-pricing-pricing-getproducts-publishes-no-windows-sku-for-the.md (both about GetProducts SKUs, neither carries this GetAttributeValues cluster's replay key).
Emulator fix: the pricing service's catalog seed plus the vocabulary derivation — a published attribute name must resolve to the published value set, and an operation must never answer a published attribute with an empty page.
Traces: pricing-ecc-traj-service-code-and-filter-value-discovery#task#4.
