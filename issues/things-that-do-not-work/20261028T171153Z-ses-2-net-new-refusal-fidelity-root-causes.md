# ses: 2 net-new refusal-fidelity root causes — the SESv2 TagResource reserved-prefix refusal carries an emulator-authored message instead of AWS's 'Failed to tag resource', and CreateReceiptRule's S3Action pre-flight never evaluates the KmsKeyArn key policy

> _Note: this issue was identified against the code base at commit `e09687ccd784c01fa8090fa7f40964051dd69a6c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
Two net-new behavioral root causes on the SES surface, both about a refusal the emulator gets wrong in a different way. Neither failing check is marked ALREADY FILED or OWNED in the replay report.

Cause 1 of 2: SESv2 TagResource refuses a reserved `aws:` tag key with the right class but an emulator-authored sentence instead of AWS's message.
AWS: Smithy com.amazonaws.sesv2#TagResource binds POST /v2/email/tags (input ResourceArn required @length min 1, Tags required TagList; errors BadRequestException 400, NotFoundException 404, ConcurrentModificationException 500, TooManyRequestsException 429). Recorded behavior shows two distinct layers refusing two distinct conditions: a tag key using the reserved `aws:` prefix is refused BadRequestException with the FIXED, value-free message "Failed to tag resource" (no key, value or ARN is interpolated — the whole sentence is fixed text), while a key longer than the modeled TagKey maximum trips the shape constraint and is refused ValidationException with an EMPTY Message; the two must not collapse into one code or one byte-identical message. A batch containing one reserved key applies NONE of the batch and leaves the already-stored tags exactly as they were.
Emulator: the class is now right — HTTP 400 `BadRequestException` — but the message is the emulator's own explanation, "The aws: prefix is reserved and cannot be used in a tag key or value.", so the replay fails on the message assertion (the code assertion before it passes). Related but NOT covering: the open issue 20261026T065304Z-ses-6-net-new-behavioral-root-causes-sesv2.md Cause 2 recorded this same operation answering 501 NotImplemented; the operation now exists and that replay key no longer matches, so the remaining wording defect is filed here.
Why: an error message is part of the contract. Log scrapers, support runbooks and tests that assert AWS's "Failed to tag resource" never match, and a message that explains the rule in the emulator's own words cannot be told apart from a genuinely different refusal by a client that classifies by text. The value-free wording is itself the requirement here: AWS deliberately does not echo the offending key.
Fix: the reserved-prefix branch of the tag validation in services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/tag_resource.rs — emit BadRequestException with exactly "Failed to tag resource", keep the modeled TagKey length violation on the separate ValidationException/empty-Message path, and validate the whole batch before writing anything.
Traces: ses.tag-resource-reserved-prefix-and-key-limit-rejected.

Cause 2 of 2: CreateReceiptRule accepts an S3Action whose KmsKeyArn names a KMS key whose key policy grants SES nothing — the KMS leg of the S3 destination pre-flight does not exist.
AWS: Smithy com.amazonaws.ses#CreateReceiptRule declares InvalidS3ConfigurationException (awsQueryError code InvalidS3Configuration, httpResponseCode 400). SES pre-flights the whole S3 destination at rule-creation time, and the KMS key is part of it: when S3Action.KmsKeyArn names a customer master key whose key policy does NOT allow ses.amazonaws.com (kms:Encrypt/GenerateDataKey*), the call is refused 400 InvalidS3Configuration with the message "Could not write to bucket: <BucketName>" — fixed text "Could not write to bucket: " plus the BucketName taken from the request's S3Action (the message names the bucket, not the key). This is a SEPARATE condition from the bucket's own grant: the identical rule WITHOUT KmsKeyArn is accepted once the bucket policy allows ses.amazonaws.com s3:PutObject, and a nonexistent bucket is refused InvalidS3Configuration "No such bucket: <BucketName>"; nothing is persisted on refusal.
Emulator: the call with the root-only-policy KmsKeyArn is ACCEPTED — HTTP 200 with an empty CreateReceiptRuleResponse (replay: "real AWS refuses this call, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}") — even though the check has already proved, through KMS itself, that the key policy names no SES principal (GetKeyPolicy shows only the account root). Related but NOT covering: the open issue 20261027T223106Z-ses-7-net-new-behavioral-root-causes-in.md Cause 2 covers the bucket-existence and bucket-policy legs of this same pre-flight and carries the sibling check ses.receipt-rule-s3-action-requires-a-live-bucket-policy-grant; it says nothing about KMS, and it does not carry this check's replay key — the KMS key policy is evaluated apart from the bucket grant and is a third, independent condition.
Why: over-permissiveness at exactly the point SES exists to protect the customer. A rule created against a key SES cannot use looks healthy and then silently drops every received message, because the delivery-time encryption fails where no caller is listening; the client never learns at creation time that its SSE-KMS inbound bucket is misconfigured, and cannot tell this fault from a missing bucket or an ungranted bucket since none of the three is reported.
Fix: the S3Action branch of the pre-flight in services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_receipt_rule.rs (and the shared validation that ops/update_receipt_rule.rs must reuse) — when KmsKeyArn is present, resolve the key in the emulator's KMS state for the request's account+region and evaluate its key policy for ses.amazonaws.com; refuse with InvalidS3Configuration/"Could not write to bucket: <BucketName>" and persist nothing, keeping the absent-bucket message ("No such bucket: <BucketName>") distinct.
Traces: ses.receipt-rule-s3-action-kms-key-policy-is-evaluated-apart-from-the-bucket-grant.
