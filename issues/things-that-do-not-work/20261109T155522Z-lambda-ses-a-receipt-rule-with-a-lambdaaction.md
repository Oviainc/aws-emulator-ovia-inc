# lambda__ses: a receipt rule with a LambdaAction never completes the documented SES event invocation — the check stalls for its whole budget at the rule/invocation stage

> _Note: this issue was identified against the code base at commit `5b2a9eedb8fa287cac2318fd09ae07f52de03ab6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRule

## Description
One net-new root cause, grounded in the single failing lambda__ses check. The replay marks it neither "ALREADY FILED" nor "OWNED by", so it is filed here. Related open issues describe neighbouring stages of the same inbound pipeline but carry different replay keys (and a different service heading), so they do not cover this check: 20261101T195358Z-s3-ses-sesv2-ses-inbound-mail-receiving-never.md (accepted inbound mail is never run through the ACTIVE rule set, so an S3Action never writes its object) and 20261027T223106Z-ses-7-net-new-behavioral-root-causes-in.md (which owns the ses-only check receipt-rule-lambda-action-requires-a-rule-scoped-invoke-permission).

Cause 1 of 1: the SES LambdaAction path never reaches the documented outcome — a receipt rule carrying `{"LambdaAction": {"FunctionArn": <fn>, "InvocationType": "Event"}}`, created against a function that already holds the rule-scoped invoke grant, does not get through to an asynchronous invocation delivering the documented SES event, and the check is killed by the harness at its 180 s cap without ever producing an assertion.
Failing check id: lambda__ses.lambda-receipt-action-event-invocation-delivers-documented-ses-event.
Hypothesis (location): the harness cap is 180.0 s and the ONLY 180 s wait in the check body is `_poll_call(lambda: ses.create_receipt_rule(... LambdaAction ...), timeout_s=180, interval_s=10, description="CreateReceiptRule accepts the LambdaAction once the scoped invoke grant exists")`, which retries on every ClientError; the earlier waits are shorter (function-Active poll) and the later one is 300 s. So the stall is most likely CreateReceiptRule refusing the LambdaAction for the whole window despite the grant, with the delivery poll as the alternative. The report gives no traceback for a harness timeout, so the exact line is not stated.
AWS: the envelopes are modelled, the invocation effect and the event payload are recorded behavior/published documentation. Smithy (com.amazonaws.ses): CreateReceiptRule — input {RuleSetName @required (ReceiptRuleSetName), After, Rule @required (ReceiptRule)}, empty output, 200; modeled refusals AlreadyExistsException/AlreadyExists(400), InvalidLambdaFunctionException/InvalidLambdaFunction(400), InvalidS3ConfigurationException/InvalidS3Configuration(400), InvalidSnsTopicException/InvalidSnsTopic(400), LimitExceededException/LimitExceeded(400), RuleDoesNotExistException/RuleDoesNotExist(400), RuleSetDoesNotExistException/RuleSetDoesNotExist(400). Recorded behavior: once the target function carries a lambda AddPermission grant with Action=lambda:InvokeFunction, Principal=ses.amazonaws.com, SourceAccount=<account> and SourceArn=arn:aws:ses:<region>:<account>:receipt-rule-set/<set>:receipt-rule/<rule>, CreateReceiptRule ACCEPTS the LambdaAction with 200 and does not refuse with InvalidLambdaFunction; DescribeReceiptRule then round-trips the action with InvocationType 'Event'; and after the rule set is made active and a message is sent to a matched recipient, SES asynchronously invokes the function once with the documented event: Records[0].eventSource == 'aws:ses', Records[0].ses.mail.destination containing the matched recipient and ses.mail.commonHeaders.subject equal to the sent subject, Records[0].ses.receipt.recipients containing the matched recipient, ses.receipt.action.type == 'Lambda' with functionArn == the configured function ARN and invocationType == 'Event', and ses.receipt.{spamVerdict,virusVerdict,spfVerdict,dkimVerdict,dmarcVerdict} each an object carrying a `status`.
Emulator: the check never produces a verdict — it is killed with "Check timed out after 180.0s", i.e. the LambdaAction stage does not settle within the 180 s the check allows it. Consequently none of the documented event's structure is ever observable on this emulator: no eventSource, no mail/receipt envelope, no action.invocationType round-trip and no verdict objects. No status, error code or error message is returned to diverge on at the point of failure; the divergence is a stage that never completes where AWS completes it in seconds.
Why: Lambda-backed inbound mail processing — the documented pattern for parsing or routing received email — cannot be built or tested on this emulator at all. A client either never gets its receipt rule accepted (and sees only a retried refusal), or gets it accepted and then never sees its function invoked, with no error distinguishing the two; everything downstream of the invocation (the SES event schema its handler parses) is untestable and would pass review unimplemented.
Fix: the SES receipt-rule LambdaAction path — the CreateReceiptRule handler's LambdaAction pre-flight in the ses crate (services/service-com-amazonaws-ses-simpleemailservice), which must accept the action once a matching rule-scoped lambda:InvokeFunction grant exists instead of refusing it; and the receiving pipeline's LambdaAction executor, which must, for a message accepted for a recipient matched by an Enabled rule in the ACTIVE rule set, invoke the configured function with InvocationType Event and the documented aws:ses event payload (mail + receipt + the five verdict objects).
Traces: lambda__ses.lambda-receipt-action-event-invocation-delivers-documented-ses-event.

2. Obtain a verified receiving domain <domain> (sesv2 GetEmailIdentity reports VerifiedForSendingStatus true for it). Create an S3 proof bucket <bucket>.

6. ses CreateReceiptRule RuleSetName=<set>, Rule={"Name":"lambda-event","Enabled":true,"ScanEnabled":false,"Recipients":["<local>@<domain>"],"Actions":[{"LambdaAction":{"FunctionArn":<fn arn>,"InvocationType":"Event"}}]}, retrying on ClientError for up to 180 s.
