=== Cause 1 of 1: WithEvent=true emits no EventBridge statement-status-change event ===
Failing check: redshift__sqs.data-api-with-event-emits-a-real-statement-event-and-the-default-emits-none

AWS: Smithy (redshift-data) ExecuteStatement input member WithEvent, target Boolean, documented verbatim as "A value that indicates whether to send an event to the Amazon EventBridge event bus after the SQL statement runs." (ExecuteStatementInput$WithEvent). When WithEvent is true and the statement reaches a terminal status, the Data API publishes one envelope on the account's default EventBridge bus with source "aws.redshift-data" and detail-type "Redshift Data Statement Status Change"; the envelope's `account` is the calling account, `region` is the request region, `resources` names the cluster ARN the statement ran on (arn:aws:redshift:<region>:<account>:cluster:<clusterIdentifier> — the region, account and cluster identifier are all taken from the request and caller, none of them fixed text), and `detail` carries `statementId` equal to the ExecuteStatement response Id and `state` equal to the terminal status ("FINISHED" here). WithEvent is not required and has no modeled default, and AWS treats its absence as false, so an otherwise identical statement submitted without the member publishes nothing. An EventBridge rule whose pattern matches only on source + detail-type therefore forwards exactly the WithEvent=true statements' envelopes to its target (an SQS queue in this check).

Emulator: no event is ever delivered. The check makes no progress past its first delivery window and is killed by the harness: 'Check timed out after 60.0s'. The check's positive leg submits a WithEvent=True 'SELECT 1', polls DescribeStatement to a terminal status, then drains the SQS target (ReceiveMessage with WaitTimeSeconds=20, up to 3 windows) looking for an envelope keyed by that statementId; because nothing arrives it long-polls to the cap. Recorded behavior only for the exact stall point — the replay output carries no stack frame, just the timeout. Hypothesis: redshift-data's statement state machine never publishes to EventBridge at all, so the rule has nothing to match and the queue is never written. The negative half of the contract (the WithEvent-less twin must emit nothing) is consequently ungradeable: an emulator that emits nothing for every statement satisfies it trivially while still being wrong.

Why: a client that uses WithEvent to drive asynchronous completion handling — an EventBridge rule fanning statement-status changes to a queue, a Lambda or a Step Functions execution — receives nothing and waits indefinitely, with no error and no other signal that distinguishes 'WithEvent was honoured' from 'WithEvent was silently ignored'. Any pipeline built on Data API completion events deadlocks against this emulator, and a test suite that asserts the WithEvent-less twin emits nothing passes for the wrong reason.

Fix: the redshift-data ExecuteStatement handler and the statement state machine that transitions a statement to a terminal status. On terminal transition, and only when the request set WithEvent=true, publish one envelope to the default EventBridge bus with source "aws.redshift-data", detail-type "Redshift Data Statement Status Change", account/region from the caller and request, resources containing the cluster ARN resolved from ClusterIdentifier (or the workgroup ARN for the serverless form), and detail.statementId / detail.state set from the statement record, so existing rule-to-SQS routing delivers it. Statements submitted without WithEvent must publish nothing.

## Evidence
Expected: after redshift-data ExecuteStatement(ClusterIdentifier=<cluster>, Database=devdb, DbUser=adminuser, Sql='SELECT 1', WithEvent=True) on an available single-node cluster reaches Status=FINISHED, an EventBridge envelope with source='aws.redshift-data', detail-type='Redshift Data Statement Status Change', account=<caller account>, region=<request region>, resources containing arn:aws:redshift:<region>:<account>:cluster:<clusterIdentifier>, detail.statementId=<the ExecuteStatement Id> and detail.state='FINISHED' is delivered to the SQS queue targeted by a rule matching that source and detail-type; the twin statement submitted with WithEvent omitted produces no message; a later WithEvent=True statement restores delivery on the same wiring; and GetQueueAttributes reports ApproximateNumberOfMessages='0' after draining.

Actual: 'Check timed out after 60.0s'. No envelope for the WithEvent=True statement ever arrives on the queue, so the check stalls in its first long-poll drain window and is killed by the harness before any delivery assertion is evaluated. ## Steps to Reproduce
