# kms__secretsmanager: a KMS authorization refusal is relayed as DecryptionFailure instead of AccessDeniedException, and kms:ViaService is never populated for the Secrets Manager forward access session (2 causes)

> _Note: this issue was identified against the code base at commit `eae7f7f16b684f1a8712c1e61a1eea233e8e7a22`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
REOPENS 20261029T175759Z-kms-secretsmanager-getsecretvalue-and-putsecretvalue-never-consult-the.md: its fix left the call refused. That fix wired the Secrets Manager envelope path to KMS and mapped every KMS refusal onto DecryptionFailure/EncryptionFailure. Both causes below are consequences of how that mapping and the KMS request context are now built: the read path can no longer express an authorization denial, and the write path is refused on a route AWS permits. TWO root causes, both in the Secrets Manager <-> KMS envelope path; a fixer must close BOTH before submitting.

Related OPEN issue, named for context only, which does NOT carry either replay key below: 20261024T102105Z-kms-secretsmanager-secrets-manager-getsecretvalue-keeps-succeeding-after-the-caller.md (it describes GetSecretValue still SUCCEEDING after kms:Decrypt is removed; the emulator now refuses, so what is left is the refusal's identity and wording, which is Cause 1).

Cause 1 of 2 - GetSecretValue collapses a KMS AUTHORIZATION refusal onto the crypto-failure code DecryptionFailure.
AWS: GetSecretValue decrypts the requested version under the secret's KmsKeyId on the caller's behalf. When that KMS call is refused for authorization reasons (an explicit Deny on kms:Decrypt in the key policy, or the permission simply absent), Secrets Manager refuses the read with HTTP 400, Error.Code AccessDeniedException and the message 'Access to KMS is not allowed'. That message is entirely FIXED text - it has no variable part, and in particular it does not relay the wrapped KMS denial text, the caller ARN, the key ARN or a KMS request id. Smithy: GetSecretValue's modeled error set is DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException - AccessDeniedException is NOT among them, i.e. it is the service-common denial, while DecryptionFailure is the modeled code reserved for the key-state / crypto-failure class (recorded behavior for the code split; the Secrets Manager model carries no key-state or authorization semantics). Secret METADATA is not enveloped under the CMK, so DescribeSecret and ListSecrets must keep working and must keep enumerating the secret while the deny is live.
Emulator: the read is refused, but with Error.Code 'DecryptionFailure' and the relayed KMS text, of the form "Secrets Manager can't decrypt the secret value: User: <caller-arn> is not authorized to perform: kms:Decrypt on resource: <key-arn> with an explicit deny in a resource-based policy (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <request-id>; Proxy: null)". In that string the caller ARN, key ARN and request id are per-run values filling the template; the defect is the CODE and the template itself - AWS emits neither.
Why: the two codes mean different remediations to a client. AccessDeniedException means 'the principal lost access to the CMK - fix the key policy or the IAM policy'; DecryptionFailure means 'the key cannot decrypt - re-enable or restore the key material'. A client that branches on AccessDeniedException (break-glass tooling, permission-boundary tests, retry/alarm logic) takes the wrong branch, and the relayed message leaks the internal KMS call shape, so error-text matching against AWS fails too.
Fix: the GetSecretValue handler's KMS error-mapping step in the envelope path. Classify the KMS refusal before mapping it: an AccessDenied-class KMS refusal must become AccessDeniedException with the fixed message 'Access to KMS is not allowed'; only the key-state / crypto-failure class may become DecryptionFailure with the relayed KMS message. The same split applies to the PutSecretValue write path (AccessDeniedException vs EncryptionFailure).
Traces: kms__secretsmanager.get-secret-value-denied-when-the-cmk-decrypt-permission-is-removed.

Cause 2 of 2 - the KMS request Secrets Manager makes on the caller's behalf carries no kms:ViaService condition value, so a key-policy Deny conditioned on StringNotEquals kms:ViaService refuses the SERVICE route as well as the direct one.
AWS: kms:ViaService discriminates by HOW the KMS request arrived, not by who made it (AWS KMS Developer Guide, conditions-kms.html: 'The kms:ViaService condition key limits use of an KMS key to requests from specified AWS services. This condition key only applies for Forward access sessions.'). A KMS request that Secrets Manager issues through a forward access session on the caller's behalf carries kms:ViaService = secretsmanager.<region>.amazonaws.com; the same principal's OWN direct KMS call carries no value for that key at all, so a Deny with StringNotEquals on it fires for the direct call and not for the service route. Consequently, with such a Deny live: a direct kms:GenerateDataKey and a direct kms:Encrypt are refused HTTP 400 AccessDeniedException with the message 'User: <caller-arn> is not authorized to perform: <kms-action> on resource: <key-arn> with an explicit deny in a resource-based policy' (fixed text; caller ARN, action and key ARN taken from the request), while PutSecretValue answers 200 with a NEW VersionId and GetSecretValue returns the byte-identical plaintext for both the new and the baseline version. This check carries no recorded ground truth (its body is marked DRAFT/unblessed), so the AWS side above is the documented ViaService rule plus the modeled refusal shape, not a recording; the direct-leg behaviour below IS observed in this replay. Hypothesis: the emulator's KMS builds its policy-evaluation request context from the HTTP caller only, so no caller can ever present a kms:ViaService value.
Emulator: KMS does evaluate the condition - the direct leg is refused exactly as AWS would be, which proves the Deny is live and parsed - but the Secrets Manager -> KMS call presents no kms:ViaService value either, so StringNotEquals fires on it too and the service route is denied. PutSecretValue answers HTTP 400 EncryptionFailure "Secrets Manager can't encrypt the secret value: User: <caller-arn> is not authorized to perform: kms:GenerateDataKey on resource: <key-arn> with an explicit deny in a resource-based policy (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <request-id>; Proxy: null)" where AWS returns 200 and a new version. (The code/message of that refusal is itself Cause 1's mapping defect; Cause 2 is that the call is refused at all.)
Why: restricting a CMK to one service route with kms:ViaService is a standard, widely deployed KMS control. Under the emulator it is indistinguishable from revoking the key outright: every secret read and write through the service is refused, so a client whose production key policy uses this condition cannot run against the emulator at all, and nobody can verify that the control permits the service while blocking direct use.
Fix: the KMS policy-evaluation request context must be populated with kms:ViaService = <service-endpoint-prefix>.<region>.amazonaws.com whenever a cryptographic call arrives as a service forward access session rather than from the principal directly, and the Secrets Manager envelope path (GetSecretValue / PutSecretValue / CreateSecret / UpdateSecret) must mark the KMS calls it makes on the caller's behalf as arriving via secretsmanager.<region>.amazonaws.com. A direct call must continue to present NO value for the key, so negated conditions keep firing on it.
Traces: kms__secretsmanager.via-service-condition-permits-the-secrets-manager-read-and-denies-the-direct-call.
