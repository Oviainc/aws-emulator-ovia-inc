# Data export table catalog returns paraphrased column metadata and wrong column sets

> _Note: this issue was identified against the code base at commit `8beaefc9c507e60dc8fbd7bca4267c7f5166e2dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
The emulator serves its own hand-written version of the Billing and Cost Management Data Exports table catalog instead of the catalog AWS publishes. The catalog is response DATA, not documentation: GetTable returns Schema as a list of Column{Name,Type,Description} and ListTables returns Table{TableName,Description,TableProperties[]} with ValidValues/DefaultValue, and clients read those values to decide which columns and table properties exist and what type each column has. Across every table in the catalog the emulator's Column.Description text is a paraphrase of AWS's published column description, several Column.Type values differ, and for some tables the column set and the property set themselves differ (whole columns and whole table properties present on one side only). 7 causes, one per recorded catalog step; they share one root cause (the built-in catalog fixture data) but each is a distinct recorded table whose contents must be corrected and re-replayed separately.

Cause 1 of 7: GetTable for the carbon-footprint table returns paraphrased column descriptions and diverging column types.
AWS: Smithy GetTable output = {TableName, Description, TableProperties, Schema: ColumnList}; Column = {Name, Type, Description}, Description documented as "The description for a column" and Type as "The kind of data a column stores" — the model constrains the shape, so the VALUES are recorded behavior only. The recording shows AWS's published per-column text, e.g. usage_account_id => 'The account ID of the account associated with the carbon footprint value. For organizations, this can be either the management account or a member account.', usage_period_start => 'The start date of the period that is covered by this report, in UTC. The format is YYYY-MM-DDTHH:mm:ssZ.', region_code => the long 'A Region is a physical location around the world where data centers are clustered...' paragraph.
Emulator: HTTP 200 with its own shorter prose for the same columns ('The account ID of the account whose usage the emissions are estimated for.', 'The inclusive start of the usage period that the estimate covers, in UTC.', 'The Region code of the usage that the emissions are estimated for.'), and the Type value also diverges on the numeric emission columns (the replay reports Type keys for total_lbm_emissions_value, total_mbm_emissions_value, total_scope_1_emissions_value, total_scope_2_lbm_emissions_value, total_scope_2_mbm_emissions_value, total_scope_3_lbm_emissions_value and total_scope_3_mbm_emissions_value; the concrete values are beyond the truncated detail string, so re-replay the step to read them).
Why: a client that introspects the catalog to build or validate an export reads a column Type AWS never reports for that column, so generated schemas/casts for the emission value columns are wrong; UI and docs generated from the catalog show text AWS does not serve.
Fix: the GetTable handler's built-in table-catalog data for this table (column Type and Description values must match the published catalog, not be re-worded).
Traces: bcm-data-exports-catalog-get-table#task#1.

Cause 2 of 7: GetTable for the legacy cost-and-usage table returns a different column SET as well as paraphrased descriptions.
AWS: same GetTable/Column contract; recorded catalog for this table carries the legacy CUR column names with AWS's text, e.g. usage_date => 'The start date for the line item in UTC, inclusive. The format is YYYY-MM-DDTHH:mm:ssZ.', invoice_id => 'The ID associated with a specific line item. Until the report is final, the InvoiceId is blank.', charge_category => 'The category of charge covered by this line item possible values are Running_Usage and non_usage.'
Emulator: paraphrased text for those columns ('The date of the usage that this row aggregates, in UTC.', 'The ID of the invoice that includes the usage in this row.', 'The classification of the charge that this row covers, based on the nature of how it is billed.') AND a different column set: the replay reports bare $.Schema[Name=...] keys (no .Description suffix) for ~100 columns such as bill_bill_type, bill_payer_account_id, line_item_usage_start_date, pricing_rate_code, product_sku, reservation_effective_cost, savings_plan_savings_plan_a_r_n and resource_tags, i.e. columns that exist on only one of the two sides for this table name.
Why: the published schema is the contract a client uses to write the export's query statement. Columns the emulator invents are accepted locally and rejected by AWS; columns it omits make a valid AWS query look unsupported.
Fix: same built-in catalog data — this table's column list must match the published one, column for column.
Traces: bcm-data-exports-catalog-get-table#task#2.

Cause 3 of 7: GetTable for the CUR 2.0 table returns paraphrased descriptions for the whole bill_/line_item_/pricing_/product_/reservation_/savings_plan_ column families.
AWS: recorded catalog text, e.g. identity_line_item_id => "This field is generated for each line item and is unique in a given partition. This does not guarantee that the field will be unique across an entire delivery (that is, all partitions in an update) of the AWS CUR. The line item ID isn't consistent between different Cost and Usage Reports and can't be used to identify the same line item across different reports.", bill_billing_entity => 'Helps you identify whether your invoices or transactions are for AWS Marketplace or for purchases of other AWS services.', bill_bill_type => 'The type of bill that this report covers.'
Emulator: one-sentence rewrites ('A unique identifier for every line item in a single delivery of the export.', 'The Amazon Web Services organization that the charge in this line item was made through, which identifies an AWS Marketplace purchase.', 'The type of bill that this line item covers.') across ~120 columns of this table.
Why: as cause 1 — catalog content a client renders or diffs against AWS does not match.
Fix: same built-in catalog data for this table.
Traces: bcm-data-exports-catalog-get-table#task#3 (cluster also covers bcm-data-exports-table-catalog-inspection#task#2).

Cause 4 of 7: GetTable for the cost-optimization-recommendations table returns paraphrased descriptions and diverging types.
AWS: recorded catalog text, e.g. resource_arn => 'The Amazon Resource Name (ARN) of the resource.', region => 'The AWS Region of the resource.', estimated_monthly_cost_before_discount => 'The estimated monthly cost of the current resource before discounts. For Reserved Instances and Savings Plans, it refers to the cost for eligible usage.'

Why: the type of the lookback-period and tags columns is what a consumer casts on; and a description that swaps current for recommended misleads a reader about which cost the column holds.

Cause 5 of 7: GetTable for the FOCUS 1.0 tables returns paraphrased descriptions.
AWS: recorded catalog text, e.g. AvailabilityZone => 'A provider-assigned identifier for a physically separated and isolated area within a Region that provides high availability and fault tolerance.', BillingCurrency => 'Represents the currency that a charge was billed in.', ChargeDescription => "Self-contained summary of the charge's purpose and price.", CommitmentDiscountCategory => 'Indicates whether the commitment-based discount identified in the CommitmentDiscountId column is based on usage quantity or cost (aka "spend").'

Why: as cause 1; FOCUS column descriptions are the spec text consumers display next to each column.
Fix: same built-in catalog data for the FOCUS 1.0 tables.
Traces: bcm-data-exports-catalog-get-table#task#5 (cluster also covers bcm-data-exports-catalog-get-table#task#6).

Cause 6 of 7: GetTable for the FOCUS 1.2 table returns paraphrased descriptions.
AWS: recorded catalog text, e.g. ChargeCategory => 'Represents the highest-level classification of a charge based on the nature of how it is billed.', ChargeClass => 'Indicates whether the row represents a correction to a previously invoiced billing period.', CapacityReservationStatus => 'Indicates whether the charge represents either the consumption of a capacity reservation or when a capacity reservation is unused.'
Emulator: different prose for those same columns, including a ChargeCategory description that instead enumerates fee/usage/adjustment/tax and a ChargeClass description that adds refund-vs-usage wording. ~48 columns affected.
Why: as cause 5.
Fix: same built-in catalog data for the FOCUS 1.2 table.
Traces: bcm-data-exports-catalog-get-table#task#7.

Cause 7 of 7: ListTables returns the wrong TableProperties for several tables — a missing ValidValues entry, a wrong property Description, and an extra property AWS does not publish.
AWS: Smithy ListTables output Tables: TableList of Table{TableName, Description, TableProperties: TablePropertyDescriptionList}, TablePropertyDescription = {Name, ValidValues, DefaultValue, Description}. The recording shows, for COST_OPTIMIZATION_RECOMMENDATIONS, a property whose Description is "The constraints that you want all returned recommendations to match. Expressed as a json of AWS Cost Optimization Hub's Filter SDK object. See COST_OPTIMIZATION_RECOMMENDATIONS table documentation for further details." and whose ValidValues contains '*'; for FOCUS_1_0_AWS_PREVIEW a single property whose Description is 'This table has been deprecated. New exports for this table are no longer supported.'
Emulator: that property's Description is 'The filter that the rows in the table are restricted to.' and its ValidValues list is EMPTY (the '*' entry is absent); FOCUS_1_0_AWS_PREVIEW's property description is 'Whether the table is deprecated.'; and both FOCUS_1_0_AWS_PREVIEW and FOCUS_1_2_AWS carry an EXTRA property {Name: 'BILLING_VIEW_ARN', ValidValues: [], DefaultValue: '', Description: 'The arn of the billing conductor group that this CUR2.0/ FOCUS Data Export is for.'} that the recording does not contain.
Why: ValidValues is what a client validates a TableConfigurations value against before calling CreateExport, so an empty ValidValues makes a legal value look illegal, and an extra published property invites a client to send a table configuration AWS rejects.
Fix: the ListTables handler's built-in table-property catalog (property list, ValidValues and Description per table).
Traces: bcm-data-exports-catalog-list-tables#task#1.
