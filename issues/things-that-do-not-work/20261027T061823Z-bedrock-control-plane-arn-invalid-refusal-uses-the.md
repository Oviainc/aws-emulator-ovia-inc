# bedrock control plane: ARN-invalid refusal uses the constraint envelope, deleted-guardrail not-found message rewritten, no default prompt routers or SYSTEM_DEFINED inference profiles in the catalogue, and GetResourcePolicy does not canonicalize the stored document

> _Note: this issue was identified against the code base at commit `01d2c61316e604fc562e841d03e580212f748c20`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateModelCopyJob, GetGuardrail/UpdateGuardrail, ListPromptRouters, GetInferenceProfile, GetResourcePolicy

## Description
REOPENS 20261022T174904Z-bedrock-arn-inputs-rejected-with-constraint-violation-envelope.md (Cause 1 below): its fix left the call refused with the generic Smithy constraint-violation envelope instead of Bedrock's own ARN message. The remaining four causes are net-new.

Five distinct root causes found on the Bedrock control plane by the behavioral suite. All five are in the same service (bedrock) and are bundled here; a fixer must close ALL FIVE before submitting. Related open issue 20261024T025841Z-bedrock-control-plane-no-iam-authorization-gate-guardrail.md covers the value-interpolation inside the constraint envelope for CreateModelInvocationJob — it does NOT cover any of the five causes below (a different refusal rule, a different message, three different operations and a different serializer).

=== Cause 1 of 5: CreateModelCopyJob answers the generic constraint-violation envelope for a malformed sourceModelArn, where Bedrock answers its own short ARN message ===
AWS: Smithy (com.amazonaws.bedrock) CreateModelCopyJob.sourceModelArn targets ModelArn, required, @length 20..1011, @pattern ^arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}:(([0-9]{12}:custom-model/...)|(:foundation-model/...))$; HTTP POST /model-copy-jobs, success 201; the operation models AccessDeniedException (403), ResourceNotFoundException (404), TooManyTagsException (400), InternalServerException (500), and the service-common ValidationException (400). Recorded behavior: Bedrock does not run the member @pattern for this ARN member — it performs its own ARN check and refuses with HTTP 400 / ValidationException whose message is the fixed text "Provided ARN is invalid." with NO variable part at all (no member path, no rejected value, no quoted regex). The same rule, with the ARN-class message varying, was already recorded on the wire corpus for this very member (fixed issue 20261022T174904Z, Cause 3). For a sourceModelArn that DOES match the pattern but names a made-up base model, AWS still answers 400 ValidationException, message template "The foundation model '<base-model-id>' for custom model is not a valid foundation model" — fixed text with the base-model id taken from the submitted ARN.
Emulator: status 400 and code ValidationException agree, but the message is the generic constraint envelope with the rejected value interpolated: "1 validation error detected: Value 'not-an-arn-at-all-0123456789' at 'sourceModelArn' failed to satisfy constraint: Member must satisfy regular expression pattern: arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}:(([0-9]{12}:custom-model/((imported)|([a-z0-9-]{1,63}[.]{1}[a-z0-9-]{1,63}))(([:][a-z0-9-]{1,63}){0,2})?/[a-z0-9]{12})|(:foundation-model/[a-z0-9-]{1,63}[.]{1}([a-z0-9-]{1,63}[.]){0,2}[a-z0-9-]{1,63}([:][a-z0-9-]{1,63}){0,2}))". The check never reaches the second probe, so whether the "not a valid foundation model" message is produced at all is unverified.
Why: the two envelopes are produced by different rules, and clients branch on them. A caller that reads Bedrock's message learns the ARN itself is unusable; a caller matching on "validation error detected" takes a branch AWS never puts it on. The emulator also reflects the caller-submitted ARN (and the model regex) back into an error string that AWS deliberately keeps value-free for this API, so log scrapers and negative tests written against AWS text do not match.
Fix: the ARN-bearing input handling in CreateModelCopyJob's handler/validation — an ARN check that runs before, and in place of, generic @pattern validation — plus the ValidationException message rendered there.
Traces: bedrock.create-model-copy-job-nonexistent-source-model-rejected; handler services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_copy_job.rs.

=== Cause 2 of 5: the guardrail not-found refusal uses the emulator's own wording instead of Bedrock's message ===
AWS: Smithy GetGuardrail (GET /guardrails/{guardrailIdentifier}, success 200) and UpdateGuardrail both model ResourceNotFoundException at httpError 404. Recorded behavior: for an identifier that does not resolve (here, a guardrail that was deleted), both answer HTTP 404 / ResourceNotFoundException with the message "This guardrail does not exist." — the message is entirely fixed text; it contains NO variable part, in particular no guardrail id and no account reference.
Emulator: status 404 and code ResourceNotFoundException agree, but the message is the emulator's own sentence with the id interpolated: "no guardrail 00000105ljl0 exists in this account" (the 12-char id is a per-run value from the emulator's own state; the diverging part is the whole template). The replay shows: AssertionError: expected the message 'This guardrail does not exist.', got 'no guardrail 00000105ljl0 exists in this account'.
Why: a client, SDK retry/branch logic or test suite that matches Bedrock's not-found text does not match; the emulator-authored sentence also leaks a resource identifier into a message AWS keeps identifier-free, and it is lower-case/unpunctuated where every AWS guardrail message is a sentence. Because the same wording is reused for UpdateGuardrail on a deleted guardrail, the divergence is in the shared refusal, not in one read.
Fix: the not-found refusal for the guardrail resource — the guardrail lookup/state helper shared by get_guardrail.rs and update_guardrail.rs (and any other guardrail-identifier resolver) — so the modelled ResourceNotFoundException carries exactly "This guardrail does not exist."
Traces: bedrock.guardrail-create-get-roundtrip; handlers services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/get_guardrail.rs and .../update_guardrail.rs.

=== Cause 3 of 5: ListPromptRouters returns no default prompt routers — the service-managed router catalogue is empty ===
AWS: Smithy ListPromptRouters (GET /prompt-routers, success 200) has input member type targeting the PromptRouterType enum with @default "default", and output promptRouterSummaries (paginated on nextToken/maxResults). AWS publishes its OWN default (service-managed) prompt routers in every region where intelligent prompt routing is available, so ListPromptRouters(type="default") returns a non-empty promptRouterSummaries list, each summary carrying models and fallbackModel that are guaranteed routable in that account/region. Recorded behavior: the check reads models/fallbackModel out of the first default router precisely because they are account-independent.
Emulator: ListPromptRouters(type="default") answers 200 with an empty promptRouterSummaries list, so nothing in the default catalogue exists. The replay shows: AssertionError: expected at least one default prompt router in this account/region. The duplicate-name refusal under test is therefore never exercised: on AWS, CreatePromptRouter reusing an existing router name answers 400 ValidationException with the message template "Failed to create the resource because the prompt router with name <promptRouterName> already exists." (fixed text; the name is taken from the request) — unverified here.
Why: every prompt-routing workflow begins by discovering the default routers; against the emulator that discovery returns nothing, so a client cannot build a custom router from a supported model set, and the whole CreatePromptRouter/GetPromptRouter/DeletePromptRouter surface is unreachable for any caller that does not hard-code model ids. It is the same class of gap as an empty foundation-model catalogue.
Fix: the prompt-router state/catalogue behind ListPromptRouters — seed the service-managed (type=default) routers, with models and fallbackModel drawn from the emulator's own foundation-model catalogue — and have list_prompt_routers.rs serve them for type=default while keeping caller-created routers under type=custom.
Traces: bedrock.create-prompt-router-duplicate-name-conflict-rejected; handler services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/list_prompt_routers.rs.

=== Cause 4 of 5: GetInferenceProfile cannot resolve a SYSTEM_DEFINED cross-region inference profile — the service-managed profile catalogue is empty ===
AWS: Smithy GetInferenceProfile (GET /inference-profiles/{inferenceProfileIdentifier}, success 200) accepts either an inference-profile ARN or a bare profile id ([a-zA-Z0-9-:.]+), and its output type targets the InferenceProfileType enum, whose SYSTEM_DEFINED value denotes the profiles AWS itself publishes. AWS provisions those cross-region profiles (ids of the form <region-prefix>.<model-id>, e.g. a us.* Nova profile) in every supported region independently of the caller's account, so GetInferenceProfile on such an id answers 200 with type="SYSTEM_DEFINED", status="ACTIVE" and the profile's own inference-profile ARN. CreateInferenceProfile then copies one via modelSource.copyFrom.
Emulator: GetInferenceProfile on the pinned SYSTEM_DEFINED id answers 404 ResourceNotFoundException "Inference profile not found." — no system-defined profile exists at all, so no APPLICATION profile can be created from one. The replay shows: botocore.errorfactory.ResourceNotFoundException: An error occurred (ResourceNotFoundException) when calling the GetInferenceProfile operation: Inference profile not found. Consequently the behavior under test is unverified: on AWS, CreateInferenceProfile with more than 50 tags answers 400 TooManyTagsException with the message "You can assign a maximum of 50 tags to a resource" (fixed text) and creates nothing, while a request with an acceptable tag count returns status=ACTIVE and its tags are readable via ListTagsForResource.
Why: cross-region inference profiles are the documented way to invoke most current foundation models, and application inference profiles can only be created by copying one. With the catalogue empty, every profile-based invocation and every cost-allocation (tagged application-profile) workflow is impossible against the emulator, and the failure arrives as a not-found on a resource the caller never created and cannot create.
Fix: the inference-profile state/catalogue behind GetInferenceProfile/ListInferenceProfiles — seed the SYSTEM_DEFINED cross-region profiles for the emulator's region from the same foundation-model catalogue the service already serves — so a bare system-defined profile id resolves with type=SYSTEM_DEFINED and can be named in CreateInferenceProfile.modelSource.copyFrom.
Traces: bedrock.inference-profile-too-many-tags-rejected; handlers services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/get_inference_profile.rs, .../list_inference_profiles.rs, .../create_inference_profile.rs.

=== Cause 5 of 5: GetResourcePolicy returns the stored bytes verbatim instead of the canonicalized policy document ===
AWS: Smithy GetResourcePolicy (GET /resource-policy/{resourceArn}, success 200) returns resourcePolicy targeting ResourcePolicyDocument, @length 1..20480, @pattern ^[\t\n\r -\xff]+$ — a JSON string. Recorded behavior: Bedrock stores a resource policy as a parsed document and re-serializes it on read, so GetResourcePolicy returns MINIFIED JSON (no whitespace between tokens) that is semantically identical to what PutResourcePolicy accepted; a document submitted with non-canonical (but valid) whitespace comes back canonicalized, i.e. byte-equal to json.dumps(doc, separators=(",",":")) of the same document.
Emulator: the response is the request's raw bytes — the submitted whitespace is preserved — so the returned document is longer than the canonical form and not byte-equal to it. The replay shows: AssertionError: resourcePolicy[11]: sent='"2012-10-17"' got=' "2012-10-17' (lens 244/256), i.e. the emulator's document still carries the space after the "Version" key's colon that AWS strips. Status 200 and semantic equality agree; the serialization is the divergence.
Why: a client that stores, diffs, hashes or signs the policy it reads back (a drift detector comparing GetResourcePolicy output against a canonical rendering of its intended policy, or an IaC provider computing a checksum) sees a spurious difference on the emulator and none on AWS, and the round-trip contract "what you read back is the canonical form of what you wrote" does not hold.
Fix: PutResourcePolicy's state (store the parsed document, not the request bytes) and GetResourcePolicy's serializer (emit the minified canonical JSON rendering on read).
Traces: bedrock.resource-policy-json-round-trip-byte-equal; handlers services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/get_resource_policy.rs and .../put_resource_policy.rs.
