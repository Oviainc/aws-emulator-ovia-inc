# acm__apigatewayv2: a REGIONAL custom domain never presents its ACM certificate on the wire, so certificate presentation and UpdateDomainName rotation are unverifiable (1 cause)

> _Note: this issue was identified against the code base at commit `edda120f5b31e63091be2c3166cb69bdc8220f1a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomainName

## Description
Cause 1 of 1: a REGIONAL apigatewayv2 custom domain has no TLS data plane, so the end-to-end flow "ImportCertificate -> CreateDomainName(REGIONAL, CertificateArn) -> verified TLS handshake against ApiGatewayDomainName with SNI = the custom domain -> UpdateDomainName rotates the presented leaf" never completes; the check is killed at the harness's 60.0 s cap. Failing check: acm__apigatewayv2.regional-custom-domain-presents-the-imported-certificate-and-rotation-swaps-it.

AWS: a REGIONAL custom domain is a real TLS terminator. Smithy (com.amazonaws.apigatewayv2): DomainNameConfiguration$CertificateArn — "An AWS-managed certificate that will be used by the ... endpoint for this domain name. AWS Certificate Manager is the only supported source"; DomainNameConfiguration$ApiGatewayDomainName — "A domain name for the API", the dedicated regional target host the caller points DNS at; DomainNameConfiguration$DomainNameStatus — AVAILABLE | UPDATING | PENDING_CERTIFICATE_REIMPORT | PENDING_OWNERSHIP_VERIFICATION; DomainNameConfiguration$SecurityPolicy — TLS_1_0 | TLS_1_2. Beyond the model, recorded behavior only: the host returned in ApiGatewayDomainName completes a TLS handshake in which the server presents, byte for byte, the leaf whose ARN was given in CertificateArn (selection is driven by the ClientHello SNI per RFC 6066 §3, so no DNS delegation is needed); the HTTP layer behind that terminator answers HTTP 403 for a custom domain with no API mapping; the negotiated TLS version is >= 1.2 when SecurityPolicy is TLS_1_2; and UpdateDomainName with a different CertificateArn swaps which leaf is presented on subsequent handshakes while GetDomainName converges on the new CertificateArn with DomainNameStatus=AVAILABLE.

Emulator: the check makes no progress and is terminated — "Error: Check timed out after 60.0s" — against a flow whose own declared waits (ISSUED poll, AVAILABLE poll, first-handshake poll, rotation poll) are all minutes long, so the failure is a stalled readiness/handshake loop, not a wrong field value. The control plane itself is implemented and returns immediately: services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/ops/create_domain_name.rs stores the configurations and mints api_gateway_domain_host(domain_id, region), and get_domain_name.rs reports the stored record; nothing in the emulator binds that minted host to a TLS listener that presents the ACM certificate. Hypothesis: the blocking loop is the first verified handshake — the minted d-xxxxxxxxxx.execute-api.<region>.amazonaws.com host is served by the same execute-api data plane that open issue 20261024T120951Z-apigatewayv2-the-execute-api-data-plane-never-serves.md reports as never serving, so every handshake attempt fails as a transport error and the retry loop spins until the cap. That issue is about HTTP invoke and the WebSocket upgrade and does not cover custom-domain TLS termination or certificate selection, which is what this check exercises; the other two candidate stalls (ACM DescribeCertificate on an imported certificate never reaching ISSUED, or GetDomainName never reporting DomainNameStatus=AVAILABLE) are covered for other checks by 20261025T172549Z-acm-certificate-representation-and-state-gating-diverge-in.md and are not asserted here.

Why: a client relying on AWS's behavior cannot serve or test TLS on a custom domain at all. CreateDomainName and UpdateDomainName become stored-but-unproven config writes: the CertificateArn is echoed back, but no client is ever presented that certificate, a certificate rotation has no observable effect, the SecurityPolicy floor is unenforced, and the documented 403-for-unmapped-domain response never arrives. Any test or deployment that validates a certificate rotation, pins a leaf, or probes a custom domain's TLS endpoint hangs instead of failing or passing.

Fix: the apigatewayv2 custom-domain data plane — the listener behind the host minted by crate::state::api_gateway_domain_host must terminate TLS using the leaf referenced by the domain's DomainNameConfigurations[].CertificateArn (resolved from ACM state), select it by ClientHello SNI, honour SecurityPolicy as a minimum-version floor, answer HTTP 403 when no API mapping matches the Host, and re-resolve the certificate after UpdateDomainName so a rotation takes effect; CreateDomainName/GetDomainName state in create_domain_name.rs and get_domain_name.rs already carry the needed fields.

Traces: acm__apigatewayv2.regional-custom-domain-presents-the-imported-certificate-and-rotation-swaps-it (mismatch, "Check timed out after 60.0s").

## Evidence
Expected (AWS): after ImportCertificate returns an ARN and the certificate reaches ISSUED, CreateDomainName(DomainName=<domain>, DomainNameConfigurations=[{CertificateArn=<old-arn>, EndpointType=REGIONAL, SecurityPolicy=TLS_1_2}]) yields a domain that reaches DomainNameStatus=AVAILABLE with a non-empty ApiGatewayDomainName; a TLS handshake to that host with server_hostname/Host = the custom domain verifies against the importing chain and presents exactly the imported leaf DER; the negotiated version is TLSv1.2 or TLSv1.3; the tunnel carries a well-formed 'HTTP/1.1 403 ...' status line because no API mapping exists; UpdateDomainName with CertificateArn=<new-arn> makes subsequent handshakes present the new leaf DER stably across three attempts while still answering 403, and GetDomainName reports CertificateArn=<new-arn> with DomainNameStatus=AVAILABLE and SecurityPolicy=TLS_1_2.

Actual (emulator): the check never reaches a terminal assertion. Replay verdict: mismatch, 'Error: Check timed out after 60.0s'. No TLS handshake to the ApiGatewayDomainName host ever completes, so neither the presented-certificate assertion, the TLS-version floor, the 403 from the unmapped domain, nor the rotation swap is ever observed. The control-plane handlers return promptly (create_domain_name.rs lines 228-260 mint and store the record including api_gateway_domain_name; get_domain_name.rs lines 149-171 report it), which is why the failure manifests as a hang in the data-plane retry loop rather than as an API error. Note on the 60 s cap: it is the harness ceiling, not an AWS requirement — the divergence being reported is the absent custom-domain TLS endpoint, not the specific wall-clock number.

## Steps to Reproduce
1. Mint a private RSA-2048 root CA and two leaves signed by it, both carrying DNS SAN = <domain> and distinct serials.
2. acm:ImportCertificate the first leaf (Certificate/PrivateKey/CertificateChain) -> old_arn; poll acm:DescribeCertificate until Status=ISSUED. Repeat for the second leaf -> new_arn.
3. apigatewayv2:CreateDomainName(DomainName=<domain>, DomainNameConfigurations=[{CertificateArn=old_arn, EndpointType=REGIONAL, SecurityPolicy=TLS_1_2}]).
4. Poll apigatewayv2:GetDomainName until DomainNameConfigurations[0].DomainNameStatus=AVAILABLE; read ApiGatewayDomainName.
5. Open a TCP connection to that host on port 443 and wrap it in a TLS client context that trusts ONLY the private root, with check_hostname=True and server_hostname=<domain>; send 'GET / HTTP/1.1' with Host: <domain>. Expect a completed handshake, peer DER == the first leaf's DER, negotiated version in {TLSv1.2, TLSv1.3}, and an 'HTTP/1.1 403' status line. Observed: the handshake never completes; the flow is still retrying when the harness cap fires.
6. apigatewayv2:UpdateDomainName(DomainName=<domain>, DomainNameConfigurations=[{CertificateArn=new_arn, EndpointType=REGIONAL, SecurityPolicy=TLS_1_2}]) and repeat step 5. Expect the presented DER to become the second leaf's and stay there across three handshakes, and GetDomainName to report CertificateArn=new_arn with DomainNameStatus=AVAILABLE.
