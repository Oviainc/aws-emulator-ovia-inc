# Personalize provisioning never reaches an ACTIVE campaign inside the check budget: every create holds its resource in a transient status, so each Describe* after a create costs the client a full poll interval

> _Note: this issue was identified against the code base at commit `0c065617979d1ee76fa77b423bd58183fc04c861`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSolutionVersion

## Description
Cause 1 of 1: the Amazon Personalize provisioning pipeline (CreateDatasetGroup -> CreateDataset -> CreateDatasetImportJob -> CreateSolution -> CreateSolutionVersion -> CreateCampaign) can no longer be completed inside the behavioral budget, so no campaign ever exists and both end-to-end personalize-runtime inference checks abort with "Check timed out after 60.0s" before they ever call the runtime plane. Failing checks: personalize-runtime.get-personalized-ranking-round-trip, personalize-runtime.recommendations-recipe-type-mismatch-rejected.

AWS: a client provisions a recommender by creating each stage and polling the matching Describe* until it reports ACTIVE. Smithy (com.amazonaws.personalize): SolutionVersion$status is documented as "CREATE PENDING | CREATE IN_PROGRESS | ACTIVE | CREATE FAILED | CREATE STOPPING | CREATE STOPPED"; DatasetGroup$status, Dataset$status, DatasetImportJob$status and Campaign$status document the same "CREATE PENDING > CREATE IN_PROGRESS > ACTIVE -or- CREATE FAILED" progression, and CreateDatasetImportJob's own documentation says "Importing takes time. You must wait until the status shows as ACTIVE before training a model using the dataset". AWS neither models nor documents any duration for those transitions, and a client therefore chooses AWS-sized poll cadences (the two checks use 5s for the dataset group, 20s for the import job, 60s for the solution version and 20s for the campaign, with AWS-sized overall waits of 300s/1800s/7200s/1800s). Recorded behavior only for the budget: the suite gives the whole check 60s of wall clock, i.e. the emulator is expected to make a stage's completion visible to the FIRST Describe* that follows its create, since the work itself is in-process and takes milliseconds.

Emulator: each create deliberately holds its resource in a transient status for a fixed wall-clock span before the derived status flips. The create-status clock stamps active_at = created_at + CREATE_SPAN with CREATE_SPAN = 500ms, and the status is derived from that instant on every read (CREATE PENDING for the first half of the span, CREATE IN_PROGRESS for the second, ACTIVE afterwards); a dependent stage is chained with due_after, so it is due 500ms after the stage below it. The consequence is not a wrong field on any single response: it is that the Describe* a client issues immediately after a create ALWAYS reports a transient status, after which the client sleeps its full poll interval before asking again. The pipeline therefore costs at least 5s + 20s + 60s + 20s = 105s of client sleeping for work the emulator finished in under 3s, which exceeds the 60s the check has. Both checks are killed during the 60s sleep that follows the first DescribeSolutionVersion, so GetPersonalizedRanking / GetRecommendations / GetActionRecommendations are never reached, the recipe-type refusal that requires a real ACTIVE campaign is never observable, and the ranking round trip never gets a response to assert on.

Why: a client of this emulator has no sequence of SDK calls that brings a campaign into existence in a bounded, useful time. Code written against AWS polls at AWS cadences (tens of seconds), and against this emulator every such poll loop pays one full interval per stage even though the underlying work is instantaneous, so an application or test that provisions a Personalize pipeline and then performs inference stalls for minutes or is killed by its own timeout. Every personalize-runtime success path, and every refusal that presupposes an ACTIVE campaign, stays unreachable over the wire.

Fix: the create-status clock shared by the control plane - services/service-com-amazonaws-personalize-amazonpersonalize/src/state.rs (CREATE_SPAN, active_at, creation_status, terminal_status) and the dependency chaining in services/service-com-amazonaws-personalize-amazonpersonalize/src/state/pipeline.rs (due_after) - together with the DescribeDatasetGroup / DescribeDatasetImportJob / DescribeSolutionVersion / DescribeCampaign handlers that report the derived status. A stage whose in-process work has already completed must be reported ACTIVE by the first Describe* following its create (the transient states may still be served while work is genuinely outstanding, e.g. a job whose import is still running), rather than being withheld for a wall-clock span a client can only discover by sleeping its next poll interval. Related open issue 20261107T171146Z-personalize-runtime-personalize-provisioning-pipeline-is-unreachable-createdatasetimportjob-answers-501 is keyed to the earlier cause of the same two checks (CreateDatasetImportJob answering 501 NotImplemented); that handler is now implemented, and this clock behavior is the remaining reason the same two checks still fail, so that issue's replay key no longer covers them.

Traces: personalize-runtime.get-personalized-ranking-round-trip (times out during the first DescribeSolutionVersion poll interval, never reaching GetPersonalizedRanking), personalize-runtime.recommendations-recipe-type-mismatch-rejected (same, so the InvalidInputException for a wrong-recipe-type campaign is never reachable).

## Evidence
Both failing checks report, with no botocore error at all:
  Check timed out after 60.0s

Where the time goes (each stage's first Describe* follows its create immediately and is answered with a transient status, so the client sleeps its whole interval):
  - CreateDatasetGroup  -> DescribeDatasetGroup #1 = "CREATE PENDING"  -> sleep 5s  -> "ACTIVE"   (~5s)
  - CreateDatasetImportJob -> DescribeDatasetImportJob #1 = "CREATE PENDING" -> sleep 20s -> "ACTIVE" (~25s cumulative)
  - CreateSolutionVersion -> DescribeSolutionVersion #1 = "CREATE PENDING" -> sleep 60s ... the check is killed at 60s wall clock here
  - CreateCampaign would add a further 20s interval
  Floor for the pipeline: 5 + 20 + 60 + 20 = 105s of client sleep, against a 60s check budget, for work the emulator completes in under 3s.

Expected (AWS semantics plus the emulator's own in-process work): the create answers, the work completes in milliseconds, and the first DescribeSolutionVersion / DescribeDatasetImportJob / DescribeDatasetGroup / DescribeCampaign after it reports status "ACTIVE", so each poll loop exits on its first iteration and the pipeline reaches an ACTIVE campaign in a couple of seconds. GetPersonalizedRanking then returns 200 with personalizedRanking a same-set permutation of the 10-item inputList carrying float scores in descending order plus a non-empty recommendationId; GetRecommendations on a USER_PERSONALIZATION campaign returns 200 with a non-empty itemList while GetPersonalizedRanking / GetActionRecommendations against that same campaign are refused with InvalidInputException (HTTP 400).
Actual: every Describe* issued immediately after its create reports a transient status ("CREATE PENDING", then "CREATE IN_PROGRESS" within the same 500ms span), because the status is derived from active_at = created_at + CREATE_SPAN; the resource does become ACTIVE 500ms later, but only a client that polls again learns it, and both checks are killed mid-interval before reaching the runtime plane.

Code: services/service-com-amazonaws-personalize-amazonpersonalize/src/state.rs lines 347-378 (CREATE_SPAN = Duration::from_millis(500), active_at, creation_status); services/service-com-amazonaws-personalize-amazonpersonalize/src/state/pipeline.rs lines 233-242 (due_after chains a stage 500ms after the stage it depends on); services/service-com-amazonaws-personalize-amazonpersonalize/src/ops/create_dataset_import_job.rs line 327 and the other create handlers stamp those due instants.

## Steps to Reproduce
1. Boot the emulator.
2. personalize.CreateSchema(name=<name>, schema=<interactions schema JSON>) -> 200.
3. personalize.CreateDatasetGroup(name=<name>) -> 200, then immediately personalize.DescribeDatasetGroup(datasetGroupArn=<arn>) -> status "CREATE PENDING". Expected: "ACTIVE" (the group's creation work is already done). Poll again after 5s -> "ACTIVE".
4. personalize.CreateDataset(datasetType="Interactions", ...) -> 200; personalize.CreateDatasetImportJob(jobName=<name>, datasetArn=<arn>, dataSource={"dataLocation": "s3://<bucket>/interactions.csv"}, roleArn=<role arn>) -> 200, then immediately personalize.DescribeDatasetImportJob(datasetImportJobArn=<arn>) -> status "CREATE PENDING". Expected: "ACTIVE" (the import already read the object and stored the rows). A client polling at the AWS cadence waits 20s.
5. personalize.CreateSolution(recipeArn="arn:aws:personalize:::recipe/aws-personalized-ranking", datasetGroupArn=<arn>) -> 200; personalize.CreateSolutionVersion(solutionArn=<arn>) -> 200, then immediately personalize.DescribeSolutionVersion(solutionVersionArn=<arn>) -> status "CREATE PENDING". Expected: "ACTIVE" (training already ran against the imported rows). A client polling at the AWS cadence now sleeps 60s and the 60s check budget is exhausted here.
6. Because step 5 cannot complete in budget, CreateCampaign and its ACTIVE wait are never reached, so personalize-runtime.GetPersonalizedRanking(campaignArn=<the campaign that was never created>, userId=<user>, inputList=[...]) is never issued. Expected after the fix: steps 3-5 each exit their poll loop on the FIRST Describe*, the campaign reaches ACTIVE within a couple of seconds, GetPersonalizedRanking returns 200 with a descending-scored permutation of inputList and a non-empty recommendationId, and GetPersonalizedRanking / GetActionRecommendations against a USER_PERSONALIZATION campaign return InvalidInputException (400).
