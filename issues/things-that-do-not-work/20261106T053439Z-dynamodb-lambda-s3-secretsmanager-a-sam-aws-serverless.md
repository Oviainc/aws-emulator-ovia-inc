# dynamodb__lambda__s3__secretsmanager: a SAM (AWS::Serverless-2016-10-31) stack's S3-upload -> Lambda -> Secrets Manager -> DynamoDB pipeline never produces an effect, so the check cannot reach a verdict within the suite cap (1 cause)

> _Note: this issue was identified against the code base at commit `aea0025a0a2ae3cf9a8e66b6bbaaa1ced2731beb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutObject (S3 bucket notification dispatch to an AWS::Serverless::Function) — reached through CloudFormation CreateStack of an AWS::Serverless-2016-10-31 template; the effect is read back with dynamodb GetItem

## Description
Cause 1 of 1: a stack built from a SAM template (Transform: AWS::Serverless-2016-10-31, deployed with Capabilities=[CAPABILITY_IAM, CAPABILITY_NAMED_IAM, CAPABILITY_AUTO_EXPAND]) that declares an AWS::SecretsManager::Secret, an AWS::DynamoDB::Table, an AWS::IAM::Role, an AWS::Serverless::Function with InlineCode, an AWS::Lambda::Permission for s3.amazonaws.com and an AWS::S3::Bucket carrying a NotificationConfiguration.LambdaConfigurations entry for s3:ObjectCreated:* never produces the end-to-end effect. Uploading an object to the stack's bucket is accepted, but the row the handler is supposed to write never appears, so the check wedges on its poll and is killed at the suite's 60 s cap (`Error: Check timed out after 60.0s`). No verdict is reachable for any of the behaviours the recording exercises.

AWS: recorded behavior only for the notification delivery and the SAM macro expansion (neither S3 event-notification dispatch nor the AWS::Serverless-2016-10-31 transform is in any Smithy model); the read-back leg is modelled. The recording requires, in order: (1) CreateStack of the SAM template settles at CREATE_COMPLETE and DescribeStacks returns the Outputs BucketName (!Ref MyBucket), TableName (!Ref MyTable) and SecretArn (!Ref MySecret), each WITH an OutputValue; (2) the AWS::Serverless::Function is expanded into a concrete, invocable function whose Environment.Variables SECRET_ARN and TABLE_NAME resolve to the stack's secret ARN and table name; (3) an s3 PutObject into the bucket causes S3 to invoke that function once per created object with an S3 event whose Records[].s3.object.key is the uploaded key and Records[].s3.bucket.name is the bucket name; (4) the handler's secretsmanager GetSecretValue(SecretId=$SECRET_ARN) answers 200 with SecretString byte-identical to the SecretString the template declared (the handler then writes it verbatim); (5) dynamodb GetItem(TableName=$TABLE_NAME, Key={pk:{S:<uploaded key>}}) answers 200 with an Item present (Smithy: GetItem input TableName target TableArn @required @length 1..1024, Key target Key @required; output member Item target AttributeMap; errors ResourceNotFoundException 400, ProvisionedThroughputExceededException 400, InternalServerError 500) whose attributes are secret.S == the template's SecretString and bucket.S == the bucket name. The key, bucket name and secret value are all values taken from the request and the stack's own state, not literals of one run; the requirement is that they round-trip unchanged.

Emulator: none of that is observable. The GetItem poll never sees a non-absent Item and the check is terminated at the 60 s harness cap; no status, item, secret value or bucket name from this flow is observable, and the emulator produced no refusal either — the flow hangs rather than answering an error a caller could act on. Hypothesis (neither the model nor the recording states which leg stalls, and the replay reports only the timeout): the S3 ObjectCreated notification is never dispatched to its Lambda destination, the same shape already filed for neighbouring service groups in 20261025T022656Z-dynamodb-lambda-s3-an-s3-putobject-never-invokes.md, 20261103T101621Z-dynamodb-lambda-s3-after-lambda-addpermission-grants-s3-amazonaws-com-an.md and 20261104T044826Z-lambda-s3-sqs-s3-bucket-notifications-never-invoke-their-lambda-target.md; none of those is keyed to this check or to this service group, and none covers the extra leg this recording needs — the AWS::Serverless-2016-10-31 macro expansion of AWS::Serverless::Function with InlineCode into an invocable function with its resolved Environment.Variables, which is the SAM-specific requirement also noted for other resource types in 20261105T111951Z-cloudformation-lambda-s3-a-sam-aws-serverless-layerversion.md. A second candidate leg is the in-process Lambda python runtime's ability to run a handler that calls secretsmanager and dynamodb, the subject of the open 20261105T081139Z-dynamodb-lambda-s3-secretsmanager-the-in-process-lambda.md; that issue does not carry this check's replay key.

Why: a client that deploys this ordinary SAM template against the emulator gets a stack that reports CREATE_COMPLETE (or never settles) but is inert: uploading an object produces no invocation, the handler never reads the stack's secret, and the table stays empty. Because the pipeline hangs instead of refusing, the client has no error to react to and must infer the failure from a missing row — exactly the silent-success failure mode an emulator must not have.

Fix: the components the flow needs, in order — (a) the CloudFormation AWS::Serverless-2016-10-31 transform expansion step that feeds the stack provisioner, so AWS::Serverless::Function with InlineCode becomes a concrete AWS::Lambda::Function with its Environment.Variables resolved from !Ref of the sibling secret and table, and the Outputs resolve to OutputValues; (b) the S3 bucket-notification dispatch path that must invoke a LambdaConfigurations destination on ObjectCreated, in the S3 object-write handler's notification-publication component (shared with the neighbouring issues named above); (c) the lambda Invoke path that must actually execute the expanded handler's secretsmanager GetSecretValue and dynamodb PutItem calls. File and line citations for the known-missing notification dispatch and provisioner arms are in the open issues cited above.

## Evidence
Failing check `dynamodb__lambda__s3__secretsmanager.deploy-sam-lambda-secret-s3-dynamodb-full-stack` — verdict [mismatch], detail: `Error: Check timed out after 60.0s`.

Expected (AWS):
- cloudformation CreateStack(TemplateBody = the SAM template below, Capabilities=[CAPABILITY_IAM, CAPABILITY_NAMED_IAM, CAPABILITY_AUTO_EXPAND]) settles CREATE_COMPLETE; DescribeStacks returns Outputs BucketName / TableName / SecretArn each with an OutputValue.
- s3 PutObject(Bucket=<BucketName output>, Key="incoming/file1.txt", Body=b"hello-sam") -> 200, and S3 invokes the expanded AWS::Serverless::Function with an event whose Records[0].s3.object.key == the uploaded key and Records[0].s3.bucket.name == the bucket name.
- The handler's secretsmanager GetSecretValue(SecretId=$SECRET_ARN) -> 200 with SecretString equal to the template's declared SecretString, and its dynamodb PutItem writes Item {pk:{S:<key>}, secret:{S:<SecretString>}, bucket:{S:<bucket>}}.
- dynamodb GetItem(TableName=<TableName output>, Key={pk:{S:"incoming/file1.txt"}}) -> 200 with Item present, Item["secret"]["S"] == the template's SecretString and Item["bucket"]["S"] == the bucket name.

Actual (emulator): the GetItem poll never observes an Item; the check is killed at the suite's 60 s cap. No invocation, no secret read, no table row and no refusal are observable — the flow hangs. The emulator returned no HTTP status or error code for this path at all, so there is no diverging status/code/message to quote; the divergence is the absent effect.
