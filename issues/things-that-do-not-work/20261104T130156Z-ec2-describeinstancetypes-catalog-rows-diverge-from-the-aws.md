# EC2 DescribeInstanceTypes catalog rows diverge from the AWS instance-type facts

> _Note: this issue was identified against the code base at commit `30059ba7efbea1c9406793a7f2ccf8806d86986b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers 200 but the per-instance-type rows it serves are computed/defaulted by the emulator instead of being the fixed AWS catalog facts for that instance type. This bundle carries 3 causes (3 of the 124 replay clusters that share this root cause across the ec2-catalog-describe-instance-types-* fixtures; every cluster is the same wrong catalog table read for a different instance family).

Cause 1 of 3: Nitro/EBS/network attributes are wrong for the c7gn family (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#20).
AWS: Smithy: DescribeInstanceTypes -> InstanceTypeInfo carries per-type hardware facts that are constant for a given instanceType: ebsInfo.ebsOptimizedInfo (shape EbsOptimizedInfo, members baselineBandwidthInMbps:int, baselineIops:int, baselineThroughputInMBps:double, maximumBandwidthInMbps:int, maximumIops:int, maximumThroughputInMBps:double), ebsInfo.maximumEbsAttachments, autoRecoverySupported, cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.networkCards (shape NetworkCardInfo), networkInfo.maximumNetworkCards, networkInfo.networkPerformance, networkInfo.secondaryNetworkSupported, networkInfo.trafficMirroringSupport, nitroEnclavesSupport, nitroTpmSupport, phcSupport, rebootMigrationSupport, processorInfo.sustainedClockSpeedInGhz. The recorded AWS response for c7gn.metal gives autoRecoverySupported=true, cpuBurstModel=none, ebsOptimizedInfo baseline 33333 Mbps / 133333 IOPS / 4166.625 MB/s, maximum 40000 Mbps / 160000 IOPS / 5000.0 MB/s, maximumEbsAttachments=31, networkInfo.defaultNetworkCardIndex=0, enaSrdSupported=true, flexibleEnaQueuesSupport=unsupported.
Emulator: returns autoRecoverySupported=false, omits cpuBurstModel, defaultNetworkCardIndex, enaSrdSupported and flexibleEnaQueuesSupport entirely, and reports generically derived EBS numbers (13600 Mbps / 60000 IOPS / 1700 MB/s baseline and maximum alike, maximumEbsAttachments=28) for every size in the family.
Why: a client that sizes EBS throughput, counts ENIs/network cards, or gates on ENA-SRD / Nitro-TPM / PHC / reboot-migration support reads values that no real instance type has, so capacity planning, scheduler placement and feature gating all decide wrongly against a service that answers 200.
Fix: the DescribeInstanceTypes handler's instance-type catalog table (per-type static data) in the ec2 service crate, not the serializer: the values must come from a per-instanceType table rather than being derived from vCPU/memory.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#20.

Cause 2 of 3: the same omission/derivation for the c7i family, plus wrong classification members (fixture ec2-catalog-describe-instance-types-a1-c9g, step task#21).
AWS: recorded AWS values for c7i.48xlarge: dedicatedHostsSupported=false, ebsInfo.attachmentLimitType=dedicated, ebsOptimizedInfo baseline/maximum 40000 Mbps, 240000 IOPS, 5000.0 MB/s, maximumEbsAttachments=128, networkInfo.defaultNetworkCardIndex=0, networkInfo.efaInfo.maximumEfaInterfaces=1 with efaSupported set; vCpuInfo.validCores enumerates every valid core count.
