# Glue: StartJobRun is an unimplemented 501 scaffold, and GetDatabase ignores Lake Formation permissions after IAM_ALLOWED_PRINCIPALS is revoked

> _Note: this issue was identified against the code base at commit `001920e7906d433f041aca694d32f13b44f642fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun

## Description
Two distinct root causes in the Glue emulator, found by replaying the behavioral suite. Both must be closed before this issue is done. Neither is covered by the open issue 20261022T131025Z-glue-createjob-is-a-501-stub-gettable-ignores.md: that issue's Cause 1 is CreateJob (which now succeeds — these checks get past it and die one call later on StartJobRun) and its Cause 2 is GetTable, a different operation and a different read path from the one in Cause 2 below.

Cause 1 of 2: StartJobRun answers HTTP 501 NotImplemented (unimplemented scaffold stub).
AWS: Smithy com.amazonaws.glue#StartJobRun takes JobName (NameString, required, len 1..255) plus Arguments (GenericMap), Timeout (range min 1), MaxCapacity, WorkerType (enum), NumberOfWorkers, ExecutionClass, NotificationProperty, and returns HTTP 200 with output member JobRunId (IdString, len 1..255). Its modeled errors are ConcurrentRunsExceededException, EntityNotFoundException, InternalServiceException (500), InvalidInputException, OperationTimeoutException and ResourceNumberLimitExceededException — all HTTP 400 except InternalServiceException. HTTP 501 / error code NotImplemented is not a modeled outcome of this operation. The run started this way must then be observable through GetJobRun (output member JobRun) until it reaches a terminal JobRunState.
Emulator: every StartJobRun call fails with HTTP 501, error code NotImplemented, message 'operation StartJobRun is scaffolded but not implemented in this emulator'. The handler is an untouched scaffold — services/service-com-amazonaws-glue-awsglue/src/ops/start_job_run.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker at line 4 and its handle() body returns Err(crate::scaffolded::Scaffolded::not_implemented("StartJobRun")).
Why: a client can define a Glue job but can never run one, so nothing that depends on a run exists: no JobRunId, no GetJobRun/GetJobRuns state machine, no terminal JobRunState, no ErrorMessage on a failed run, and no data-plane effect of a job. Every end-to-end flow whose only observables are a run's terminal state and the object it writes is unreachable.
Fix: implement the handler in services/service-com-amazonaws-glue-awsglue/src/ops/start_job_run.rs — resolve JobName against the stored job definitions (EntityNotFoundException when absent), persist a run record in crate::state keyed by a generated JobRunId, return that JobRunId, and let the run progress to a terminal JobRunState readable by GetJobRun/GetJobRuns with an ErrorMessage when it fails. Then delete the SCAFFOLDED marker line.
Traces: glue__iam__lakeformation__s3.glue-job-catalog-read-denied-until-lf-grant, glue__iam__lakeformation__s3.glue-job-denied-on-governed-table-without-lf-data-admin-until-lf-grant.

Cause 2 of 2: GetDatabase is not gated on Lake Formation permissions — revoking IAM_ALLOWED_PRINCIPALS on a database does not make the database unreadable.
AWS: recorded behavior only — com.amazonaws.glue#GetDatabase does not model AccessDeniedException (its modeled errors are EntityNotFoundException, FederationSourceException, FederationSourceRetryableException, GlueEncryptionException, InternalServiceException, InvalidInputException, OperationTimeoutException), but the recording shows the catalog read being refused by Lake Formation. A reader role whose inline IAM policy allows glue:GetDatabase and glue:GetTable reads the database successfully while it still carries the IAM_ALLOWED_PRINCIPALS grant; after lakeformation:RevokePermissions of ALL for principal IAM_ALLOWED_PRINCIPALS on that Database resource, the same GetDatabase is refused with error code AccessDeniedException; and after a DESCRIBE grant on ONE TABLE inside the database — with no database-level grant at all, which ListPermissions on the Database resource confirms stays empty — GetDatabase succeeds again. The requirement is the decision and its error code, plus the implicit parent-database visibility a table-level grant confers; the recorded message is an example only.
Emulator: GetDatabase keeps returning the database after the revoke. The check polls the outcome waiting for it to settle on AccessDeniedException and never sees it, so the check is killed by the harness ('Check timed out after 60.0s'). Glue's database read path consults no Lake Formation state, so a database with and without IAM_ALLOWED_PRINCIPALS are indistinguishable to a non-admin principal.
Why: a client cannot test or reproduce Lake Formation governance of the catalog at database granularity. Metadata that AWS withholds is disclosed, code that expects AccessDeniedException until a grant exists never sees the refusal, and the revoke-then-table-grant transition — including the implicit database visibility derived from a table-level DESCRIBE — can never be observed.
Fix: the Glue database read path (services/service-com-amazonaws-glue-awsglue/src/ops/get_database.rs, and the sibling GetDatabases listing) must consult the Lake Formation permission state for the request's resolved caller principal: allow when IAM_ALLOWED_PRINCIPALS is granted on the database, when the principal holds a database permission, or when the principal holds any permission on a table inside it; otherwise refuse with AccessDeniedException naming the missing Lake Formation permission.
Traces: glue__iam__lakeformation__s3.lf-database-iap-revoked-get-database-denied-until-a-table-grant.

Cause 2 — expected sequence on a governed database with a parquet table: (a) GetDatabase as the reader role => OK; (b) lakeformation:RevokePermissions(Principal=IAM_ALLOWED_PRINCIPALS, Resource={Database:{Name:db}}, Permissions=[ALL]) then GetDatabase => error code AccessDeniedException; (c) lakeformation:GrantPermissions(DESCRIBE) on {Table:{DatabaseName:db,Name:usage_events}} then GetDatabase => OK, with ListPermissions on the Database resource still returning an empty PrincipalResourcePermissions. Actual: step (b) never produces an error — GetDatabase keeps returning the database, the check's bounded poll for AccessDeniedException never settles, and the harness reports 'Check timed out after 60.0s' (verdict: mismatch).
