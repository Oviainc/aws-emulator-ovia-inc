# EC2 describe projections serve synthesized catalog data and omit members

> _Note: this issue was identified against the code base at commit `b64c3d45927e2833db57dde0eaeae2a33a5b497f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
Three net-new causes: two static catalogs are generated rather than served as AWS's published metadata, and one describe projection drops members AWS returns. All three must be closed before this issue is submitted.

Cause 1 of 3: DescribeInstanceTypes attribute values are derived, not AWS's published per-type values, and modeled optional members are omitted.
AWS: DescribeInstanceTypes returns, per instance type, the published hardware description — ebsInfo.ebsOptimizedInfo baseline/maximum bandwidth, IOPS and throughput, ebsInfo.maximumEbsAttachments and attachmentLimitType, instanceStorageInfo disk count/size and totalSizeInGB, networkInfo (defaultNetworkCardIndex, maximumNetworkCards, networkCards, networkPerformance, ipv4/ipv6 addresses per interface, enaSrdSupported, flexibleEnaQueuesSupport, bandwidthWeightings, connectionTrackingConfiguration timeouts, efaInfo.maximumEfaInterfaces, secondaryNetworkSupported, trafficMirroringSupport), processorInfo.sustainedClockSpeedInGhz, vCpuInfo.validCores, cpuBurstModel, dedicatedHostsSupported, nitroEnclavesSupport, nitroTpmSupport, phcSupport, rebootMigrationSupport and supportedBootModes. These are catalog facts, not request-derived values; the recordings carry them per type.
Emulator: the values are synthesized from a formula keyed on size (e.g. for c7gd.medium baselineBandwidthInMbps 287 vs AWS's 315, baselineIops 1500 vs 2500, maximumThroughputInMBps 593.75 vs 1250.0, maximumEbsAttachments 28 vs 26, instanceStorageInfo totalSizeInGB 25 vs 59; for r9g.medium attachmentLimitType 'shared' vs 'dedicated', connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 vs 350) and a long list of modeled members is simply absent (cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.bandwidthWeightings, networkInfo.maximumNetworkCards, ... reported as missing/got None). The same pattern recurs for every step of every ec2-catalog-describe-instance-types-* fixture.
Why: any client that sizes workloads, validates EBS/ENA limits or filters instance types by a described attribute gets wrong answers that look authoritative, and code reading an omitted member sees it as unset.
Fix: the DescribeInstanceTypes static catalog (data) plus its response projection — serve AWS's per-type catalog rows verbatim and emit every member the recording carries, instead of deriving values from the type's size.
Traces: ec2-catalog-describe-instance-types-r9g-z1d#task#1, #task#10, #task#11; ec2-catalog-describe-instance-types-a1-c9g#task#19. Related open issues 20261103T154947Z-ec2-describeinstancetypes-instance-type-catalog-diverges-from-aws.md, 20261104T022117Z-ec2-describeinstancetypes-catalog-sweep-serves-derived-hardware-attributes.md and 20261103T123451Z-ec2-static-catalogs-serve-emulator-authored-instance-type.md describe the same family but do not carry these replay keys.

Cause 2 of 3: DescribeFpgaImages serves emulator-invented AFIs instead of the Amazon-published catalog.
AWS: DescribeFpgaImages with no owner filter returns the Amazon-published AFIs — each with its own fpgaImageId, fpgaImageGlobalId, name, description, shellVersion, pciId (DeviceId/VendorId/SubsystemId/SubsystemVendorId), state.code, createTime/updateTime, ownerId, ownerAlias 'amazon', public 'true' and dataRetentionSupport 'false'. The identities and attributes are catalog facts, not per-run values.
Emulator: a different, invented set of images is returned: ids, names, descriptions, shell versions, pciId values, owner account and timestamps all differ from the recorded catalog (e.g. a 'cl_hello_world' row with ownerId 137112412989 and createTime 2025-11-04T00:00:00Z in place of the recorded rows), and the emulator's rows carry an instanceTypes member the recorded rows do not.
Why: a client that looks up an AFI by id or name (the normal way an FPGA workload selects an image) finds nothing, and an operator comparing the catalog against AWS sees unrelated images.
Fix: the DescribeFpgaImages static catalog (data) and its projection — serve the recorded Amazon-published rows and only the members AWS returns.
Traces: ec2-catalog-describe-fpga-images#task#1.

Cause 3 of 3: DescribeSubnets omits the subnet's DHCP options members.
AWS: recorded behavior only — the on-disk Smithy com.amazonaws.ec2#Subnet shape in this checkout does not model them, but the recorded 200 response carries dhcpOptionsId (the VPC's DHCP options set id) and dhcpOptionsSource 'vpc' on every subnet of the VPC.
Emulator: both members are missing from every subnet in the response (got None), while the rest of the subnet projection matches.
Why: a client that reads a subnet's effective DHCP configuration (or distinguishes a VPC-inherited set from a subnet-level one) gets no value at all and cannot tell an unset field from an unimplemented one.
Fix: the DescribeSubnets response projection — emit dhcpOptionsId and dhcpOptionsSource, resolved from the subnet's VPC association.
Traces: ec2-madl-traj-vpc-subnet-discovery-filters#task#8.
