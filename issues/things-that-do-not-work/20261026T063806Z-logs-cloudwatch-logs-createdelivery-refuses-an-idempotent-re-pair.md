=== Cause 1 of 2: CreateDelivery refuses a repeat of the same source+destination pair with ConflictException instead of upserting ===
AWS: Smithy (com.amazonaws.cloudwatchlogs#Logs_20140328) CreateDelivery takes deliverySourceName (@required, @length 1..60, @pattern ^[\w-]*$) and deliveryDestinationArn (@required), plus optional recordFields/fieldDelimiter/s3DeliveryConfiguration/tags, and returns {delivery}. Its modeled errors are AccessDeniedException, ConflictException, ResourceNotFoundException, ServiceQuotaExceededException, ThrottlingException, ValidationException (all HTTP 400) and ServiceUnavailableException (500) — so ConflictException exists on the operation, but the recording shows it is NOT the response to this request class. Recorded behavior: a second CreateDelivery naming the SAME deliverySourceName and the SAME deliveryDestinationArn as an existing delivery is ACCEPTED (HTTP 200) and idempotently returns the EXISTING delivery — delivery.id is byte-identical to the first call's id — and an independent read (DescribeDeliveries, paged) still lists exactly ONE delivery for that source+destination pair. CreateDelivery is an upsert on the (source, destination) pair: it neither errors nor mints a duplicate.
Emulator: the second call is refused HTTP 400 ConflictException with the message "A delivery already exists between delivery source <deliverySourceName> and delivery destination <deliveryDestinationArn>: <existingDeliveryId>". Message rule, for the record: the fixed text is "A delivery already exists between delivery source " … " and delivery destination " … ": "; the three variable parts are the deliverySourceName and deliveryDestinationArn taken from the request and the existing delivery id taken from emulator state (this run's values — source `sim2real-behav-dlvsrc-53ee261d4ff2`, destination `arn:aws:logs:us-west-2:000000000000:delivery-destination:sim2real-behav-dlvdst-173f361281a7`, id `0000000000000000` — merely fill that template and are not part of any requirement). No message is correct here, because AWS does not refuse this call at all: the required response is 200 with the existing delivery.
Why: re-issuing CreateDelivery is the normal way a client converges desired state — a CloudFormation/CDK/Terraform re-apply, a retried provisioning step, or any idempotent "ensure this delivery exists" helper. Against AWS that is a no-op that returns the same id; against the emulator it is a hard 400 that aborts the caller, so a second deploy of an unchanged vended-log pipeline fails where AWS succeeds. Because the exception propagates, every later leg of the same flow is also left unexercised: UpdateDeliveryConfiguration's recordFields round-trip, the DeleteDeliveryDestination-while-in-use ConflictException, the duplicate-name CreateScheduledQuery ConflictException and the CreateImportTask invalid-event-data-store-ARN refusal.
Fix: the CreateDelivery handler in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/create_delivery.rs — the branch that currently detects an existing (deliverySourceName, deliveryDestinationArn) pair and raises ConflictException must instead return the stored Delivery with its existing id at HTTP 200, leaving the delivery state unchanged and the pair's cardinality at one. ConflictException stays reserved for the genuinely conflicting cases the model lists it for.
Traces: logs.conflict-exception-concurrent-state.

=== Cause 2 of 2: an EC2 interface VPC endpoint never reports State "available", so the whole logs syslog-configuration lifecycle is ungradeable ===
AWS: Smithy (cloudwatchlogs) PutSyslogConfiguration takes logGroupIdentifier (@required, @length 1..2048, @pattern ^[\w#+=/:,.@-]*$) and vpcEndpointId (@pattern ^vpce-[0-9a-f]{1,64}$) and returns an empty body; ListSyslogConfigurations returns syslogConfigurations (each carrying vpcEndpointId and logGroupArn) with nextToken/maxResults (0..50); DeleteSyslogConfiguration takes logGroupIdentifier (@required) and vpcEndpointId. All three model AccessDeniedException, InvalidOperationException, InvalidParameterException, ResourceNotFoundException, ThrottlingException (400) and ServiceUnavailableException (500). Recorded behavior: PutSyslogConfiguration requires a real EC2 interface endpoint to the dedicated regional PrivateLink service com.amazonaws.<region>.syslog-logs, so the check provisions a VPC, a subnet, a security group and that endpoint, and then waits for ec2 DescribeVpcEndpoints to report VpcEndpoints[0].State == "available" (budgeted 240 s against AWS) before touching the logs syslog surface at all.
Emulator: ec2 CreateVpcEndpoint is accepted and returns a VpcEndpointId, but DescribeVpcEndpoints never reports State "available" for that endpoint, so the availability wait spins until the harness kills the check at its 60 s cap. PutSyslogConfiguration, ListSyslogConfigurations and DeleteSyslogConfiguration are never called, so the emulator is never asked whether a listing reflects a put and a delete. Hypothesis: the created endpoint is persisted in its initial non-terminal state with no transition to "available" (or is not returned by DescribeVpcEndpoints at all — the poll helper swallows exceptions, so a failing describe is indistinguishable from a never-advancing state).
Why: the endpoint-state machine is the gate in front of an entire CloudWatch Logs feature. A client that provisions a syslog ingestion endpoint waits forever instead of getting "available", and because the gate never opens, nothing about the logs syslog-configuration contract (a put becoming visible in ListSyslogConfigurations, the logGroupArn it reports, and a delete removing exactly the configuration for that vpcEndpointId) can be observed or regression-tested.
Fix: the EC2 VPC-endpoint state machine — services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs must record an endpoint that services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_vpc_endpoints.rs reports with State "available" (immediately, or after a bounded synthetic transition), for an Interface endpoint whose ServiceName is com.amazonaws.<region>.syslog-logs; once the gate opens, the PutSyslogConfiguration / ListSyslogConfigurations / DeleteSyslogConfiguration handlers in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/ must round-trip the configuration keyed on (logGroupIdentifier, vpcEndpointId). Note: the replay report's ALREADY-FILED stub issue for ec2 DescribeVpcEndpointServices blocks the sibling check logs.syslog-configuration-delete-nonexistent-rejected; that is a different operation and does not carry this check id.
Traces: logs.list-syslog-configurations-reflects-put-and-delete.
