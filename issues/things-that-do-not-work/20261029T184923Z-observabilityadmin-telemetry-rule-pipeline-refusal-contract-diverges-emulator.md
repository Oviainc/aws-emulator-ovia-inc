# observabilityadmin telemetry-rule/pipeline refusal contract diverges: emulator-authored not-found, conflict and mutual-exclusion messages, UpdateTelemetryPipeline unserved (501), and ValidateTelemetryPipelineConfiguration FieldMap keyed by member instead of 'path'

> _Note: this issue was identified against the code base at commit `92c3b140342b1bc1fab2a232b8cee3f25ea78ff5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTelemetryRule

## Description
The behavioral suite exercised observabilityadmin's telemetry-rule and telemetry-pipeline surface and found that the emulator serves its own refusal prose instead of AWS's error messages, leaves one update operation entirely unserved, and reports pipeline-configuration validation errors with a FieldMap shape AWS does not use. This issue bundles 5 distinct root causes; ALL FIVE must be closed before submitting.

Related open issues (neither covers these behavioral checks; they carry WIRE replay keys for the same service and should be fixed consistently with this one): '20261029T174915Z-observabilityadmin-refusal-contract-diverges-not-found-conflict-and.md' (refusal messages observed on the wire corpus) and '20261029T174915Z-observabilityadmin-success-response-projection-diverges-minted-arns-omitted.md' (ValidateTelemetryPipelineConfiguration error vocabulary for other bodies). Cause 4 below (UpdateTelemetryPipeline) is named by neither, and the only other open issue '20261029T064523Z-observabilityadmin-lists3tableintegrations-stub.md' covers a different operation.

Cause 1 of 5 — GetTelemetryRule's ResourceNotFoundException message is emulator prose that interpolates the identifier and the region.
AWS: Smithy: GetTelemetryRule input RuleIdentifier (required, @length 1..1011); modeled error ResourceNotFoundException (errorKind client, httpError 404) with members Message/ResourceId/ResourceType. Recorded behavior: a well-formed RuleIdentifier naming no rule — whether never created, or created and then deleted, and whether supplied as a bare rule name or as the rule's full ARN — is answered HTTP 404, code ResourceNotFoundException, Message exactly 'Rule not found.' The whole message is FIXED text (including the trailing period); there is NO variable part, and in particular the requested identifier and the region are NOT interpolated.
Emulator: the correct 404/ResourceNotFoundException, but Message is "no telemetry rule '<RuleIdentifier as submitted>' in <region>" — emulator wording whose variable parts are the request's identifier and the region. Observed both for a bare name ("no telemetry rule 'sim2real-oa-notfound-...' in us-west-2") and for a full ARN ("no telemetry rule 'arn:aws:observabilityadmin:<region>:<account>:telemetry-rule/...' in us-west-2").
Why: the message text is part of the error contract. A client, log matcher or test keyed on AWS's fixed sentence never matches, and the emulator leaks an internal phrasing (plus the caller's identifier) AWS never emits.
Fix: the not-found path of the GetTelemetryRule handler in services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/ — raise ResourceNotFoundException with AWS's fixed text rather than the shared emulator error helper's interpolated sentence.
Traces: observabilityadmin.get-telemetry-rule-not-found, observabilityadmin.telemetry-rule-create-get-delete-lifecycle, observabilityadmin.telemetry-rule-invalid-resource-type-enum-rejected (in the last two the preceding assertions — nested DestinationConfiguration round-trip and the ResourceType enum-constraint refusal — passed; only this message diverged).

Cause 2 of 5 — CreateTelemetryRule's duplicate-name ConflictException message is emulator prose that interpolates the rule name and region.
AWS: Smithy: CreateTelemetryRule input RuleName (required, @length 1..100, @pattern ^[0-9A-Za-z-_.#/]+$); modeled error ConflictException (errorKind client, httpError 409). Recorded behavior: creating a rule whose RuleName already exists is refused HTTP 409 / ConflictException with Message exactly 'Telemetry Rule already exists.' — entirely fixed text including the trailing period, with the rule name NOT interpolated.
Emulator: 409/ConflictException (status and code correct) with Message "a telemetry rule named '<RuleName>' already exists in <region>" — the fixed part is the emulator's own sentence and the variable parts are the submitted RuleName and the region.
Why: a client that branches on, surfaces or matches the conflict message sees text AWS never produces; the duplicate-detection contract is observable only through this message.
Fix: the duplicate-name branch of the CreateTelemetryRule handler.
Traces: observabilityadmin.telemetry-rule-duplicate-name-conflict-rejected.

Cause 3 of 5 — CreateTelemetryRule's Regions/AllRegions mutual-exclusion ValidationException message names the members by shape path instead of AWS's wire parameter names.
AWS: Smithy: TelemetryRule.Regions and TelemetryRule.AllRegions are each documented as mutually exclusive with the other; CreateTelemetryRule models ValidationException (errorKind client, httpError 400). Recorded behavior: supplying both is refused HTTP 400 / ValidationException with Message exactly "Parameters 'regions' and 'allRegions' are mutually exclusive. Provide one or the other, not both." — entirely fixed text, naming the parameters in lowerCamel WIRE form ('regions', 'allRegions'), with no request value interpolated.
Emulator: 400/ValidationException (status and code correct) with Message 'Rule.Regions and Rule.AllRegions are mutually exclusive; supply one of them' — the emulator's own sentence, naming the members by internal shape path ('Rule.Regions'/'Rule.AllRegions') rather than the names present in the client's own wire payload.
Why: a client that surfaces the validation message to a user, or matches on it, gets text AWS never produces and member names that do not correspond to its request body.
Fix: the request-validation step of the CreateTelemetryRule handler (the mutual-exclusion check), using AWS's message template verbatim.
Traces: observabilityadmin.telemetry-rule-regions-allregions-mutually-exclusive-rejected.

Cause 4 of 5 — UpdateTelemetryPipeline is an unimplemented scaffold stub, so the immutable-source-type rule is unenforced and every update is refused 501 NotImplemented.
AWS: Smithy: UpdateTelemetryPipeline input PipelineIdentifier (required, @length 1..512) and Configuration (required); modeled errors AccessDeniedException(400), InternalServerException(500), ResourceNotFoundException(404), TooManyRequestsException(429), ValidationException(400) — NotImplemented is not among them. The operation's own model documentation states the source type is immutable: 'Once a pipeline is created with a specific source type (such as S3, CloudWatch Logs, GitHub, or third-party sources), it cannot be changed to a different source type', while processors may be added, removed or modified. Recorded behavior: an UpdateTelemetryPipeline whose Configuration.Body swaps the pipeline's source from cloudwatch_logs to s3 is refused HTTP 400 / ValidationException with Message exactly 'Validation errors found' (fixed text; the per-field detail travels in ValidationException.Errors), the stored Configuration is left untouched (the original cloudwatch_logs source survives and no s3 source is persisted), and an update that changes only the processor list at the same source type SUCCEEDS and persists.
Emulator: answers HTTP 501 with code 'NotImplemented' and message 'operation UpdateTelemetryPipeline is scaffolded but not implemented in this emulator' for every UpdateTelemetryPipeline call, so neither the immutability refusal nor the accepted same-source-type update is served. Note this check was NOT marked ALREADY FILED by the suite — the auto-filed stub issues name ListTelemetryPipelines and DeleteTelemetryPipeline, not UpdateTelemetryPipeline.
Why: a client cannot modify a pipeline at all, and a client relying on the refusal to learn that the source type is immutable instead receives an unmodeled 501 with an error code no SDK retry/branching logic recognizes; configuration drift is silently impossible rather than selectively rejected.
Fix: implement the handler in services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/update_telemetry_pipeline.rs (currently returns crate::scaffolded::Scaffolded::not_implemented("UpdateTelemetryPipeline") at line 186 and still carries the SCAFFOLDED marker at line 4): validate the new Configuration against the stored pipeline, reject a source-type change with ValidationException, persist an accepted same-source-type change in the pipeline state, and leave state unchanged on rejection.
Traces: observabilityadmin.telemetry-pipeline-source-type-immutable-update-rejected.

Cause 5 of 5 — ValidateTelemetryPipelineConfiguration's INVALID_PATTERN error keys FieldMap by the offending member name instead of carrying the field's 'path'.
AWS: Smithy: ValidateTelemetryPipelineConfiguration returns HTTP 200 with Errors -> list of ValidationError { Message, Reason, FieldMap }, FieldMap documented as 'A mapping of field names to specific validation issues within the configuration'. Recorded behavior: a content-level defect inside Configuration.Body is reported in that Errors list (never as a synchronous exception), and a schema error pinned to a specific field carries its location under the FieldMap key 'path', whose value is the full dotted document path of the offending field (here ending in 'sts_role_arn', i.e. 'pipeline.source.cloudwatch_logs.aws.sts_role_arn'). The fixed part of the contract is the FieldMap key name 'path' and the Reason vocabulary; the dotted path itself is derived from the submitted document.
Emulator: for a non-IAM-shaped sts_role_arn it returns 200 with Reason 'INVALID_PATTERN' (correct) and a plausible constraint Message, but FieldMap is keyed by the bare member name — {'sts_role_arn': '<message>'} — with no 'path' entry at all, so the error cannot be located in the document by the documented key.
Why: the FieldMap 'path' entry is what a console, CLI or client uses to point the user at the offending line of the pipeline document; keying by bare member name makes the location unreadable by any client following AWS's contract and ambiguous whenever the same member name appears under more than one source.
Fix: the configuration validator behind the ValidateTelemetryPipelineConfiguration handler — emit each field-pinned ValidationError with FieldMap carrying 'path' set to the field's full dotted document path (this is the same validator named by the related open issue's ValidateTelemetryPipelineConfiguration causes; fix the FieldMap key shape there once for all Reason codes).
Traces: observabilityadmin.validate-telemetry-pipeline-configuration-malformed-yaml-rejected (the PIPELINE_CONFIGURATION_PARSE_ERROR assertion for unparseable YAML passed; the failure is the FieldMap key).
