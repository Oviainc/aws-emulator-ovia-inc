## Description
Two net-new root causes in the WAFv2 logging surface reached through an API Gateway REST stage. Cause 1 of 2: PutLoggingConfiguration accepts a LogDestinationConfigs entry whose CloudWatch Logs log group name does not start with `aws-waf-logs-`.
Failing check: apigateway__logs__wafv2.wafv2-put-logging-configuration-log-group-without-the-waf-prefix-rejected
AWS: WAF validates the destination's NAME, not only its ARN syntax. The WAFv2 operation documentation for PutLoggingConfiguration states the rule plainly — the name you give the destination must start with `aws-waf-logs-` — and a CloudWatch Logs group that does not carry that prefix is refused as a client error. Smithy (services/service-com-amazonaws-wafv2-awswaf-20190729/smithy-model/com-amazonaws-wafv2-awswaf-20190729.json): PutLoggingConfiguration input `LoggingConfiguration` (required), member `LogDestinationConfigs` ("The logging destination configuration that you want to associate with the web ACL... You can associate one logging destination to a web ACL"); modeled errors WAFInvalidParameterException (httpError 400), WAFLogDestinationPermissionIssueException (400), WAFNonexistentItemException (400), WAFOptimisticLockException (400), WAFLimitsExceededException (400), WAFInvalidOperationException (400), WAFServiceLinkedRoleErrorException (400), WAFInternalErrorException (500). So the required answer for an unacceptable LoggingConfiguration member is HTTP 400 with error code `WAFInvalidParameterException`; message text for this path is not stated by the model or by the recording, so only the status and code are asserted requirements here. GetLoggingConfiguration for a web ACL with no stored configuration must answer HTTP 400 `WAFNonexistentItemException`.
Emulator: the call is ACCEPTED. The replay reports `AssertionError: the call was ACCEPTED where a refusal was expected`, from the check's `_error_code(lambda: w.put_logging_configuration(...bad_arn...))` wrapper. The check builds two log groups moments apart from the SAME random suffix, differing only in the eleven-character `aws-waf-logs-` prefix, and the unprefixed one is taken. Because the call did not raise, the emulator never produced the 400/`WAFInvalidParameterException` pair at all, and the downstream effect-absent legs (GetLoggingConfiguration must then answer WAFNonexistentItemException; the wrongly named group must receive no log streams) were never reached.
Why: the `aws-waf-logs-` prefix is the contract that lets CloudWatch Logs subscription filters, metric filters and log-delivery IAM policies be written against a known name space. A client that typos or omits the prefix is told at PutLoggingConfiguration time by AWS; against the emulator it is told nothing, stores a configuration AWS would never have stored, and then sees no records arrive — a silent, undiagnosable logging outage instead of a 400 at configuration time. Negative tests asserting the refusal pass against a permissive target.
Fix: the wafv2 PutLoggingConfiguration handler's validation of `LoggingConfiguration.LogDestinationConfigs` — parse each destination ARN, and for a CloudWatch Logs `log-group` destination require the group name to begin with `aws-waf-logs-`, refusing with HTTP 400 `WAFInvalidParameterException` BEFORE anything is persisted, so GetLoggingConfiguration still answers WAFNonexistentItemException afterwards.
Traces: apigateway__logs__wafv2.wafv2-put-logging-configuration-log-group-without-the-waf-prefix-rejected (mismatch).

Cause 2 of 2: with logging accepted and a blocking web ACL associated with a deployed REST stage, no WAF log record is ever observable, so the check cannot complete and runs out at the 60 s cap.
Failing check: apigateway__logs__wafv2.wafv2-logging-configuration-delivers-a-blocked-request-record-with-redacted-fields
AWS: once PutLoggingConfiguration is in place, WAF asynchronously delivers one JSON record per inspected request to the destination log group. For a request terminated by a Block rule the record carries `action` = "BLOCK", `terminatingRuleId` = the rule's Name, `httpRequest.uri` containing the requested path, and `httpRequest.headers` with every header configured in `RedactedFields` replaced by the fixed literal `REDACTED` while all other headers appear verbatim. Recorded behavior only for the delivery itself (the check's own measurement against real AWS, us-west-2 2026-09-10: delivery is asynchronous and the poll is bounded on the record arriving, with the propagation of the rule to the API Gateway edge measured at 20-30 s and log delivery within the check's 480 s arrival budget); the record field names above are the documented WAF log format. GetLoggingConfiguration must round-trip `LogDestinationConfigs` and `RedactedFields` exactly as stored.
Emulator: the check never completes — the replay reports `Check timed out after 60.0s`. The deployed stage itself does serve: the sibling check in Cause 1 gets past the same `_wait_http(url, status==200, 180 s)` pre-flight on the execute-api URL, past CreateWebACL/AssociateWebACL, and all the way to its PutLoggingConfiguration assertion inside the same cap. What this check does in addition, and what therefore does not converge, is (a) the bounded wait for the marker path to settle on HTTP 403 once the Block rule is associated, and (b) the bounded poll for a WAF log record naming the marker path to arrive in the destination log group. Hypothesis: the stall is in one of those two bounded polls — the associated web ACL's Block rule never takes effect at the stage, and/or no record is ever delivered to CloudWatch Logs — rather than in anything before them. Either way the observable outcome is that WAF logging, after being accepted, produces nothing: no BLOCK record, no terminatingRuleId, and the `RedactedFields` redaction (and the non-redaction of other headers) has never been demonstrated by this emulator.
Why: WAF logs are the only audit trail of what a web ACL did to traffic in front of a REST stage. A client that enables logging and gets a 200 reasonably concludes logging is on; it then has no record of blocked requests, no way to attribute a block to a rule, and no evidence that a header it marked sensitive is actually redacted before it is written to CloudWatch Logs. An implementation that is silently a no-op here is strictly worse than one that refuses, because the client never learns.
Fix: the wafv2 log-delivery path and the web-ACL enforcement path at the API Gateway stage — an associated web ACL's terminating Block rule must answer the request at the stage with HTTP 403, and an enabled logging configuration must then write a record per inspected request into the configured destination log group with `action`, `terminatingRuleId`, `httpRequest.uri` and `httpRequest.headers`, substituting the fixed literal `REDACTED` for exactly the headers named in `RedactedFields` and leaving every other header's value verbatim.
Traces: apigateway__logs__wafv2.wafv2-logging-configuration-delivers-a-blocked-request-record-with-redacted-fields (mismatch, timed out at the 60 s cap). Sibling evidence that the stage pre-flight is not the stall: apigateway__logs__wafv2.wafv2-put-logging-configuration-log-group-without-the-waf-prefix-rejected reached its PutLoggingConfiguration assertion within the same cap.
