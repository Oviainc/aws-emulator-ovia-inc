# cognito-idp: a pool with an accepted userAuthEvents log delivery never emits any SignIn record to the destination CloudWatch Logs group

> _Note: this issue was identified against the code base at commit `eb1ede2cbce186d0b7cae6d474f923ddb0f91b8a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetLogDeliveryConfiguration

## Description
One net-new root cause, grounded in failing behavioral check cognito-idp__logs.obs-cognito-idp-1-security-audit-telemetry, which the replay report marks neither ALREADY FILED nor OWNED.

NOTE on the adjacent issue (named so a fixer does not conflate them): open issue 20261026T055019Z-logs-cognito-idp-cognito-idp-setlogdeliveryconfiguration-accepts-a-cloudwatch-logs-destination.md is about SetLogDeliveryConfiguration ACCEPTING a destination log group that does not resolve, and carries only the replay key of check cognito-idp__logs.obs-cognito-idp-1-log-delivery-config. It does not cover the behavior below, which is about a destination that DOES resolve and is accepted and read back correctly, yet never receives a record. The two are independent: fixing destination validation does not make records appear.

Cause 1 of 1: the userAuthEvents log-delivery pipeline produces no records at all — accepted configuration, zero emission.
AWS: Smithy (com.amazonaws.cognitoidentityprovider#AWSCognitoIdentityProviderService) models SetLogDeliveryConfiguration with input {UserPoolId (required, @length 1..55, pattern ^[\w-]+_[0-9a-zA-Z]+$), LogConfigurations (required, list, @length 0..2)} and errors FeatureUnavailableInTierException 403, InvalidParameterException 400, NotAuthorizedException 403, ResourceNotFoundException 404, TooManyRequestsException 429, InternalErrorException 500; the model says nothing about what is delivered, so for the record content: recorded behavior only. The recording shows that on a PLUS-tier pool with UserPoolAddOns.AdvancedSecurityMode=AUDIT and LogConfigurations=[{EventSource: userAuthEvents, LogLevel: INFO, CloudWatchLogsConfiguration: {LogGroupArn: <existing group>}}], every InitiateAuth sign-in attempt on that pool lands in the destination log group as ONE structured JSON event per attempt, carrying eventSource = 'USER_AUTH_EVENTS', logSourceId.userPoolId = the pool id, and a nested 'message' object with eventType = 'SignIn', eventResponse = 'Pass' for a correct password and 'Fail' for a wrong one, a distinct eventId per attempt, userName, userPoolId, clientId, and a 'challenges' list containing 'Password:Success' on a pass and 'Password:Failure' on a fail. Exactly one stream is exempt from this structure — 'log_stream_created_by_aws_to_validate_log_delivery_subscriptions', into which CloudWatch Logs' own vended-delivery machinery writes one plain-text validation line. Clearing the delivery (LogConfigurations=[]) must stop emission for subsequent sign-ins, and re-setting it must resume it.
Emulator: nothing is ever written. The pool is created PLUS/AUDIT, SetLogDeliveryConfiguration is accepted and GetLogDeliveryConfiguration reads the destination ARN back unchanged, the sign-ins themselves behave (correct password yields AccessToken+IdToken, wrong password yields NotAuthorizedException 'Incorrect username or password.'), but FilterLogEvents on the destination group never returns a userAuthEvents record. The check polls FilterLogEvents for the first pass/fail pair at 2s intervals and never resolves, so the replay ends in 'Check timed out after 60.0s' — the emulator answered every control-plane call and simply emitted no telemetry.
Why: the security-audit plane is silent. A client that wires Cognito threat-protection telemetry into CloudWatch Logs — a SIEM pipeline, a metric filter on eventResponse=Fail, an alarm on repeated 'Password:Failure' challenges, or a compliance assertion that sign-ins are audited — sees an empty log group and concludes no sign-ins occurred, while the configuration read-back says delivery is on. Because nothing is ever emitted, the complementary negative is also unverifiable: a sign-in made while delivery is cleared cannot be shown NOT to leak into the group, so both the positive and the negative control collapse to the same empty result and a delivery regression is undetectable.
Fix: the cognito-idp service's authentication path must emit a userAuthEvents record into each configured CloudWatch Logs destination. This belongs in the sign-in handlers' telemetry emission (InitiateAuth / AdminInitiateAuth / RespondToAuthChallenge in service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/ops/) reading the pool's stored LogDeliveryConfiguration out of src/state.rs and writing a PutLogEvents-equivalent structured event into the named log group in the CloudWatch Logs service state: one event per attempt, with eventSource USER_AUTH_EVENTS, logSourceId.userPoolId, and message {eventType: SignIn, eventResponse: Pass|Fail, eventId: unique per attempt, userName, userPoolId, clientId, challenges: ['Password:Success'|'Password:Failure']}; emission must be gated on the pool being PLUS tier with AdvancedSecurityMode AUDIT (or ENFORCED) and on a userAuthEvents configuration being present, so that clearing LogConfigurations stops it and re-setting it resumes it.
Traces: cognito-idp__logs.obs-cognito-idp-1-security-audit-telemetry (mismatch, 'Check timed out after 60.0s' while polling FilterLogEvents for the marker user's Pass and Fail sign-in records).

## Evidence
Failing check (behavioral suite, service heading '### cognito-idp__logs'): cognito-idp__logs.obs-cognito-idp-1-security-audit-telemetry — [mismatch].

Verbatim replay output:
  Error: Check timed out after 60.0s

Where it hangs: the check's first barrier, _await(logs, group, phase1_done, "the marker user's Pass and Fail sign-in records"), which repeatedly calls logs.filter_log_events(logGroupName=<group>) every 2s and returns only once the records for the marker user include both eventResponse 'Pass' and 'Fail'. Everything before that barrier is control-plane work the emulator completes: CreateLogGroup + DescribeLogGroups (the group is listed exactly once, so its ARN resolves), two CreateUserPool calls with UserPoolTier=PLUS and UserPoolAddOns={AdvancedSecurityMode: AUDIT} whose DescribeUserPool read-back is asserted to report PLUS/AUDIT, SetLogDeliveryConfiguration on both pools with EventSource=userAuthEvents / LogLevel=INFO / CloudWatchLogsConfiguration.LogGroupArn=<that group>, GetLogDeliveryConfiguration asserted to read the same ARN back, four AdminCreateUser + AdminSetUserPassword pairs, one successful InitiateAuth (USER_PASSWORD_AUTH) asserted to return AccessToken and IdToken, and one wrong-password InitiateAuth asserted to return ('NotAuthorizedException', 'Incorrect username or password.'). Those assertions did not fire, so the sign-ins happened and the delivery configuration was accepted and persisted.

Expected (AWS, recorded behavior): FilterLogEvents on the destination group returns, for each of those two attempts, one JSON event with eventSource='USER_AUTH_EVENTS', logSourceId.userPoolId=<pool id>, message.eventType='SignIn', message.userPoolId=<pool id>, message.clientId=<app client id>, message.userName=<the signing-in user>, message.eventResponse='Pass' for the correct password and 'Fail' for the wrong one, a distinct message.eventId per attempt, and message.challenges containing 'Password:Success' / 'Password:Failure' respectively. Only the stream 'log_stream_created_by_aws_to_validate_log_delivery_subscriptions' is exempt from that structure.
Actual (emulator): FilterLogEvents on that group yields no userAuthEvents record at any point in the poll, so the barrier never resolves and the check is killed at the harness ceiling. The later legs — clearing delivery, confirming the control pool's record still arrives, restoring delivery and confirming the 'quiet' sign-in made while cleared never leaked — are never reached.

Note on the ids above: pool ids, client ids, user names, group names and eventIds are per-run values that fill the record template; the required parts are the field names, the fixed values 'USER_AUTH_EVENTS' / 'SignIn' / 'Pass' / 'Fail' / 'Password:Success' / 'Password:Failure', and one event per sign-in attempt.

## Steps to Reproduce
1. logs: CreateLogGroup(logGroupName='/<name>'); DescribeLogGroups(logGroupNamePrefix='/<name>') and take the group ARN with any trailing ':*' stripped.
2. cognito-idp: CreateUserPool(PoolName=<name>, UserPoolTier='PLUS', UserPoolAddOns={'AdvancedSecurityMode': 'AUDIT'}); DescribeUserPool confirms UserPoolTier=PLUS and AdvancedSecurityMode=AUDIT.
3. CreateUserPoolClient(UserPoolId=<pool>, ExplicitAuthFlows=['ALLOW_USER_PASSWORD_AUTH','ALLOW_REFRESH_TOKEN_AUTH']).
4. SetLogDeliveryConfiguration(UserPoolId=<pool>, LogConfigurations=[{'EventSource':'userAuthEvents','LogLevel':'INFO','CloudWatchLogsConfiguration':{'LogGroupArn':<group ARN>}}]); GetLogDeliveryConfiguration reads the same ARN back.
5. AdminCreateUser(MessageAction='SUPPRESS') + AdminSetUserPassword(Permanent=True) for one user.
6. InitiateAuth(ClientId=<client>, AuthFlow='USER_PASSWORD_AUTH', AuthParameters={'USERNAME':<user>,'PASSWORD':<correct>}) -> tokens; then InitiateAuth with the password plus a stray character -> NotAuthorizedException 'Incorrect username or password.'
7. Poll logs.FilterLogEvents(logGroupName='/<name>') and JSON-decode each event outside the stream 'log_stream_created_by_aws_to_validate_log_delivery_subscriptions'.
   Expected: two structured records as described above — one eventResponse='Pass' with challenges containing 'Password:Success', one eventResponse='Fail' with challenges containing 'Password:Failure', both naming the pool and client.
   Observed: no record ever appears; the poll never terminates.
8. Negative/positive loop that is blocked by the same cause: SetLogDeliveryConfiguration(UserPoolId=<pool>, LogConfigurations=[]) (GetLogDeliveryConfiguration shows []), sign in as a second user, then re-set the delivery and sign in as a third user — AWS delivers the third user's record and never the second user's.
