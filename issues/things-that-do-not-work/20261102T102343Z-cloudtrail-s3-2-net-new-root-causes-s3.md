# cloudtrail__s3: 2 net-new root causes — S3 object data events are never delivered to the trail's bucket (so ARN-prefix and ReadWriteType selector scoping are inert), and a bucket-policy explicit Deny is not evaluated for a role session

> _Note: this issue was identified against the code base at commit `699db40da250628f4cc12f3dc175d789bc27ad1e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
TWO distinct causes in this issue; both must be closed before submitting.

Cause 1 of 2 — no S3 object data event is ever delivered to a logging trail's bucket, so every scoping rule a basic/advanced selector expresses over object data events is unobservable.
AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) models the selectors these checks install — EventSelector.DataResources with Type AWS::S3::Object (the DataResource shape documents AWS::S3::Object as one of the three basic types) plus ReadWriteType, and AdvancedEventSelector field selectors on eventCategory / resources.type / resources.ARN with Equals, StartsWith and NotStartsWith. The delivery itself is recorded behavior only (measured by the checks against real AWS): while such a trail is logging, each matching S3 object-level call (PutObject/GetObject) is delivered as a gzipped log record under the trail's bucket prefix, with the object's ARN as the resource, readOnly true for GetObject and false for PutObject; records whose resource ARN is excluded by the selector (NotStartsWith on a key prefix) or whose read/write class is excluded by ReadWriteType=WriteOnly are NOT delivered, and the exclusion must still hold after an equal-length hold window.
Emulator: nothing is delivered. Both checks drive their object calls in repeated rounds and poll the log bucket for the expected records; no record ever lands, so each is still polling when the harness's 60s cap ends it ('Check timed out after 60.0s'). Both carry DATAPLANE_MARKER = 'DATAPLANE_UNIMPLEMENTED' for exactly this absence.
Why: S3 object data events are the highest-volume and most security-relevant audit stream AWS emits, and selector scoping over them is simultaneously a correctness and a billing control. With delivery absent, an over-broad selector that would collect (and bill) every object read in AWS is indistinguishable from a correctly scoped one, and a client's 'we log all access to this bucket' control silently logs nothing.
Fix: S3 object-level data-event capture plus trail log-file delivery — S3's object operations must feed the shared event-recording seam as eventCategory Data records carrying the AWS::S3::Object resource ARN and their readOnly class, and the trail's logging state must evaluate the stored event selectors (ReadWriteType, DataResources ARN prefixes, advanced StartsWith/NotStartsWith) against those records and write the matching ones as gzipped objects into the configured bucket/prefix while withholding the rest.
Traces: cloudtrail__s3.obs-s3-2-arn-prefix-exclusion-withholds-object-data-events, cloudtrail__s3.write-only-read-write-type-delivers-the-put-and-withholds-the-get. NOTE: the open issue 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md lists the first of those trace ids under its Cause 1/2, but the replay report did NOT mark either check as owned, so both replay keys are unclaimed and are filed here.

Cause 2 of 2 — an S3 bucket policy's explicit Deny is not evaluated: a role session's GetObject on an existing object under a denied key prefix SUCCEEDS instead of being refused.
AWS: recorded behavior only (measured by the check against real AWS): with a bucket policy containing an explicit Deny for s3:GetObject/s3:PutObject on arn:aws:s3:::<bucket>/denied/* for the assumed-role principal, the role session's GetObject on an object that EXISTS under that prefix is refused with HTTP 403, error code AccessDenied and message `User: <session-arn> is not authorized to perform: s3:GetObject on resource: "<object-arn>" with an explicit deny in a resource-based policy` — fixed text 'User: ', ' is not authorized to perform: ', ' on resource: ' (the resource ARN double-quoted) and ' with an explicit deny in a resource-based policy', with the variable parts taken from the request and state: the caller's assumed-role session ARN (arn:aws:sts::<account>:assumed-role/<role>/<session>), the action name (s3:GetObject / s3:PutObject), and the target object ARN. The denied PutObject must additionally leave no object behind (a later HeadObject answers 404 'Not Found').
Emulator: the call is accepted. The check's _error() helper raises 'expected the call to be rejected, but it succeeded' on the role session's GetObject of the existing denied-prefix object, i.e. the object's bytes are returned to a principal the resource policy explicitly denies; no 403/AccessDenied is produced. The emulator had already accepted the PutBucketPolicy that installed the Deny, so the policy is stored and then ignored at access time.
Why: this is a confidentiality failure, not a cosmetic one. An explicit Deny in a resource-based policy is the strongest control S3 offers and the one guardrails and data-perimeter designs rely on; an emulator that stores it and serves the object anyway lets a test suite certify a bucket as protected when the same configuration in AWS refuses the read. It also makes every downstream audit assertion about denied calls (errorCode/errorMessage on the data event) unreachable.
Fix: S3 request authorization — the bucket-policy evaluation seam for object operations must apply resource-based policy statements (explicit Deny first, then Allow) against the authenticated principal, the action and the object ARN, and refuse with 403 AccessDenied carrying AWS's explicit-deny message template; a refused PutObject must not mutate state.
Traces: cloudtrail__s3.obs-s3-2-object-data-events-record-success-missing-key-and-denied-calls (the surviving assertion is the role GetObject at check line 420). NOTE: the open issue 20261023T135552Z-cloudtrail-s3-s3-getobject-succeeds-for-a-role-whose-policy.md describes an object-level authorization gap that looks the same; the replay report did NOT mark this check as owned by it, so this check's replay key is unclaimed and the cause is filed here — if the fix is shared, close both and re-replay the trace above.
