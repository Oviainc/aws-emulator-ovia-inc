# ACM DescribeCertificate renders Subject/Issuer distinguished names in reversed RFC 4514 order instead of the certificate's DER order, and ExportCertificate's 501 stub blocks the imported-chain round-trip check (2 causes)

> _Note: this issue was identified against the code base at commit `df009dd79b3a670d3c0c53c12bb5e37a115b862c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCertificate

## Description
TWO distinct root causes in the ACM crate, grounded in two failing behavioral checks of this suite. A fixer must close BOTH before submitting.

Cause 1 of 2: DescribeCertificate's Subject (and, by the same code path, Issuer) is rendered with its relative distinguished names in reverse of the order the certificate encodes them, so a certificate whose subject DER is CN then OU is reported as 'OU=...,CN=...'.
AWS: Smithy CertificateDetail$Subject is a String, documented only as 'The name of the entity that is associated with the public key contained in the certificate.' (CertificateDetail$Issuer likewise: the name of the certificate authority that issued and signed the certificate), so the rendering is recorded behavior only. Measured: ACM renders the X.509 Name reading the RDNs in the order the certificate's DER carries them, so a leaf whose subject was encoded as CN=<common name> followed by OU=<organizational unit> is reported with the common name FIRST -- the Subject string begins with 'CN=<the certificate's own common name>'. The general rule is the requirement (DER order, 'Type=Value' components comma-separated); the common name itself is a value read from the imported certificate, not part of any fixed text.
Emulator: the Subject is the x509_cert crate's Display/RFC 4514 rendering of the Name (services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs stores subject: tbs.subject.to_string() and issuer: tbs.issuer.to_string(), and the field is documented in that file as 'The subject distinguished name, as RFC 4514 writes one'). RFC 4514 emits RDNs in REVERSE DER order, so the same certificate is reported as 'OU=sim2real-probe-acm-not-a-real-key,CN=<common name>' -- the common name last.
Why: Subject is the human- and tool-readable identity of the certificate, and callers substring-match or prefix-match it (most commonly on 'CN=') to pick a certificate, to display it, or to compare ACM's view against the certificate they imported or against openssl's output. With the components reversed, every such comparison fails against the emulator while passing on AWS, and a caller that splits on the first component reads the organizational unit where the common name belongs.
Fix: the Subject/Issuer rendering behind the imported certificate record and DescribeCertificate's projection -- services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs (imported_certificate(): render tbs.subject / tbs.issuer in DER order rather than taking the type's RFC 4514 Display) and any other producer of those fields in src/ops/ and src/state.rs, so DescribeCertificate and the list/search projections all agree.
Traces: acm.acm-imported-pem-round-trips-to-byte-identical-der.

Cause 2 of 2: ExportCertificate is still a scaffold stub answering HTTP 501 NotImplemented, which refuses the imported-certificate export contract asserted by a check no filed issue carries as a replay key.
AWS: Smithy ExportCertificate(CertificateArn required, Passphrase required @sensitive @length 4..128) -> {Certificate, CertificateChain, PrivateKey}, errors InvalidArnException, RequestInProgressException, ResourceNotFoundException, ThrottlingException, ValidationException (all HTTP 400). An existing IMPORTED certificate is not exportable and the call is refused with HTTP 400 ValidationException.
Emulator: HTTP 501 with Error.Code 'NotImplemented' and message 'operation ExportCertificate is scaffolded but not implemented in this emulator'; services/service-com-amazonaws-acm-certificatemanager/src/ops/export_certificate.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and ends handle() with Err(crate::scaffolded::Scaffolded::not_implemented(..)).
Why: 501 is a server fault to every SDK, so a client cannot distinguish 'this certificate may not be exported' from 'the service is down', and retry logic hammers a call that can never succeed.
Fix: services/service-com-amazonaws-acm-certificatemanager/src/ops/export_certificate.rs (replace the not_implemented Err and delete the SCAFFOLDED marker). This is the SAME stub that open issue 20261022T143245Z-acm-seven-modeled-operations-answer-http-501-notimplemented.md describes as its Cause 1 and open issue 20261025T172549Z-acm-certificate-representation-and-state-gating-diverge-in.md describes as its Cause 9; NEITHER carries acm.import-certificate-chain-byte-exact-round-trip as a replay key, so this cause records it and additionally gates the fix on the surrounding contract that check asserts (a two-certificate chain supplied at ImportCertificate is returned byte-for-byte identically by GetCertificate, and the export of that IMPORTED certificate is refused with ValidationException).
Traces: acm.import-certificate-chain-byte-exact-round-trip.
