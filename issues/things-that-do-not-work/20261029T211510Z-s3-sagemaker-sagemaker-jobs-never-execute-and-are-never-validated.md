> _Note: this issue was identified against the code base at commit `482573dd66a8fdd59e0387c95d89889e67d3b0e1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Cause 1 of 5: training jobs never run, so they end Failed and write no model artifact.
AWS: CreateTrainingJob accepted -> TrainingJobStatus walks InProgress -> Completed; the algorithm container reads every declared S3 input channel, and ModelArtifacts.S3ModelArtifacts names a real archive written under OutputDataConfig.S3OutputPath. A run that cannot read its input or write its output ends Failed with a FailureReason attributing the failure to the missing s3:GetObject / s3:PutObject grant. (Smithy: DescribeTrainingJob output TrainingJobStatus, FailureReason, ModelArtifacts.S3ModelArtifacts; status values are recorded behavior.)
Emulator: every training job reaches Failed with FailureReason "This emulator has no container runtime, so the training job's algorithm image was never started and no model artifacts were written to the output S3 location". Nothing is written under S3OutputPath, checkpoint config and input manifests are never exercised, and the permission-denied negatives get this same FailureReason instead of an access-denied one, so the negative and the positive are indistinguishable.
Why: a client that waits for Completed and then loads the artifact never gets one; a client that reads FailureReason to diagnose an IAM problem is told about a container runtime instead.
Fix: the CreateTrainingJob execution path -- the job state machine and the worker that must read the input channels and write the model artifact to S3 -- and the FailureReason it reports.

Cause 3 of 5: no inference runs, so batch transform writes nothing and InvokeEndpoint always errors.
AWS: CreateTransformJob transforms every record of its S3 input and writes the result under S3OutputPath; InvokeEndpoint returns the model's inference, and with DataCaptureConfig enabled the request/response is captured to the capture S3 destination (a missing write grant on that destination surfaces as the documented capture failure, not as a model error).

Why: no serving path produces a prediction, so nothing downstream of an endpoint or a transform job can be exercised, and the data-capture negative is masked by a ModelError.
Fix: the CreateTransformJob and InvokeEndpoint execution paths and the data-capture writer behind DataCaptureConfig.

Cause 4 of 5: CreateTrainingJob/CreateProcessingJob perform no synchronous validation of the execution role or the input URI.
AWS: these calls are refused synchronously -- with a ValidationException whose message names the specific problem -- when the execution role does not trust sagemaker.amazonaws.com, when its trust policy has no principal, when it holds no S3 permission (no s3:ListBucket / s3:GetObject) on the declared input bucket, or when the declared S3Uri prefix is malformed or has no objects under it. Nothing is created.
