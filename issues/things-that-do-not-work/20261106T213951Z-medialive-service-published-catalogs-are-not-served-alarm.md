# medialive service-published catalogs are not served: alarm template groups, alarm templates and reserved offerings omit every AWS-published entry

> _Note: this issue was identified against the code base at commit `3abf5fbf54017146c695171b75c1d278f497be4f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCloudWatchAlarmTemplateGroups

## Description
Three distinct causes, all in the medialive crate's seeded SERVICE-PUBLISHED read-only catalogs and the three list handlers that project them. Each catalog is a fixed, region-stable table that AWS reports identically to every account; the emulator serves either nothing at the published identities or rows minted from its own sequential resource-id counter. A fixer must close all three causes before submitting.

Cause 1 of 3 - ListCloudWatchAlarmTemplateGroups does not publish AWS's provided CloudWatch alarm template groups (fixture medialive-catalog-list-cloud-watch-alarm-template-groups, step task#1).
AWS: Smithy: ListCloudWatchAlarmTemplateGroups GET /prod/cloudwatch-alarm-template-groups, 200, output member CloudWatchAlarmTemplateGroups (jsonName cloudWatchAlarmTemplateGroups) targeting __listOfCloudWatchAlarmTemplateGroupSummary, paginated on NextToken/MaxResults with a `scope` query member. CloudWatchAlarmTemplateGroupSummary requires Arn (target __stringPatternArnMedialiveCloudwatchAlarmTemplateGroup), Id, Name, CreatedAt and TemplateCount, and documents Id as "A cloudwatch alarm template group's id. AWS provided template groups have ids that start with `aws-`" (target __stringMin7Max11PatternAws097). The AWS-provided rows are a published table, not per-account data: the same ids, names, templateCounts and createdAt instants are returned in a region to every caller, and their ARN has an EMPTY account field (arn:aws:medialive:<region>::cloudwatch-alarm-template-group:<id>). Recorded behavior shows that table, e.g. id aws-1160891 / AWS-CloudFrontGeneralWorkflows / templateCount 2, aws-1484347 / AWS-MediaLiveUdpAndRtmpWorkflows / templateCount 9, aws-2520023 / AWS-MediaPackageGeneralWorkflows / templateCount 3, aws-2587288 / AWS-MediaConnectCdiJpegxsWorkflows / 3, aws-3414886 / AWS-MediaConnectRtpWorkflows / 4, each with tags {}.
Emulator: 200, but the cloudWatchAlarmTemplateGroups list holds NO entry at any published ARN - every lookup by arn:aws:medialive:us-west-2::cloudwatch-alarm-template-group:aws-NNNNNNN resolves to None. The sibling lifecycle recording shows why: the groups of those NAMES are synthesized at seed time out of the crate's sequential id mint (AWS-CloudFrontGeneralWorkflows served as aws-1000001, AWS-MediaLiveUdpAndRtmpWorkflows as aws-1000008) with synthesized templateCounts. The minted values satisfy the `aws-` pattern but are not the catalog's identities; because they come from the per-run id mint they are also not stable, whereas AWS's are.
Why: the provided group id is the handle a client passes on as GroupIdentifier to ListCloudWatchAlarmTemplates or as the group of a signal map's monitor deployment. A client that holds or caches a real id (aws-1160891) gets a not-found from the emulator, and an id read back from the emulator is unusable against AWS; a "this group holds N templates" assertion is wrong too.
Fix: the crate's seeded alarm-template-group catalog state - the AWS-provided groups must be a fixed published table carrying AWS's own ids, names, templateCounts and createdAt, allocated OUTSIDE the resource id mint that serves caller-created groups - plus the ListCloudWatchAlarmTemplateGroups projection and its scope filter.
Traces: medialive-catalog-list-cloud-watch-alarm-template-groups#task#1.

Cause 2 of 3 - ListCloudWatchAlarmTemplates does not publish AWS's provided alarm templates (fixture medialive-catalog-list-cloud-watch-alarm-templates, step task#1).
AWS: Smithy: ListCloudWatchAlarmTemplates GET /prod/cloudwatch-alarm-templates, 200, output CloudWatchAlarmTemplates targeting __listOfCloudWatchAlarmTemplateSummary, paginated, with groupIdentifier/scope/signalMapIdentifier query filters. The provided templates are likewise a fixed published table whose GroupId cross-references the provided groups of cause 1. Recorded behavior shows e.g. id aws-0253256 in groupId aws-1484347, name AWS-ChannelInputErrorSecondsHigh-MediaLiveUdpAndRtmpWorkflows, targetResourceType MEDIALIVE_CHANNEL, metricName ChannelInputErrorSeconds, comparisonOperator GreaterThanThreshold, period 60, statistic Maximum, treatMissingData missing, threshold 0, evaluationPeriods 1, datapointsToAlarm 1; and id aws-0563153 in groupId aws-5775786, name AWS-InputLossSecondsHigh-MediaLiveToMediaPackageWorkflows, metricName InputLossSeconds.

Why: deploying AWS's recommended alarms is the normal use of this API - list the managed templates of a group, then deploy the group onto a signal map. Against the emulator there is nothing to deploy, and every assertion on a managed alarm's metric, statistic, period or threshold is unverifiable.
Fix: the same seeded catalog state extended with the AWS-provided template table (ids and groupIds fixed to AWS's published values, the full alarm definition stored rather than defaulted) plus the ListCloudWatchAlarmTemplates projection and its groupIdentifier/scope filters.
Traces: medialive-catalog-list-cloud-watch-alarm-templates#task#1.
