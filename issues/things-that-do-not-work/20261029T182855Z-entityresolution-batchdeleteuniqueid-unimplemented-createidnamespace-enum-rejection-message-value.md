# entityresolution: BatchDeleteUniqueId unimplemented, CreateIdNamespace enum-rejection message value-set order, PutPolicy stale-token conflict message text

BatchDeleteUniqueId

## Description
Three independent defects in the entityresolution emulator found by behavioral replay: one operation is not implemented at all, and two refusal messages are not the text AWS returns. There are 3 distinct causes in this issue and ALL THREE must be closed before submitting.

Related but different open issues (none of the three causes below is covered by them): 20261022T153803Z-entityresolution-control-plane-missing-reference-duplicate-validation-no.md owns the missing-reference / duplicate / authorization control-plane checks; 20261022T191952Z-entityresolution-rule-based-matching-jobs-never-succeed-no.md owns the matching-job lifecycle and AddPolicyStatement duplicate-statementId semantics; 20261029T172827Z-entityresolution-response-fidelity-wrong-tagging-success-status-wrong.md owns TagResource/UntagResource status, DeleteIdNamespace messages and the rendered policy DOCUMENT shape — it does not touch PutPolicy's revision-token conflict message.

Cause 1 of 3 — BatchDeleteUniqueId is an unimplemented scaffold stub, so every call is refused with 501 NotImplemented.
AWS: DELETE /matchingworkflows/{workflowName}/uniqueids (Smithy: BatchDeleteUniqueId, input workflowName @httpLabel @required EntityName @length 1..255 pattern ^[a-zA-Z_0-9-]*$, uniqueIds @httpHeader "uniqueIds" @required UniqueIdList of HeaderSafeUniqueId @length 1..780, optional inputSource @httpHeader; output status (DeleteUniqueIdStatus: COMPLETED|ACCEPTED) @required, errors @required, deleted @required, disconnectedUniqueIds @required; modeled errors ValidationException(400), ResourceNotFoundException(404), InternalServerException(500)). A call with an EMPTY uniqueIds list is refused with HTTP 400 ValidationException whose message is entirely fixed text with no variable parts: "1 validation error detected: Value null at 'uniqueIds' failed to satisfy constraint: Member must not be null" (the list is header-serialized, so an empty list arrives as an absent header, i.e. null). Hypothesis: that is why the message says "null" rather than naming a minimum length; the model puts no @length on UniqueIdList itself, so this refusal is recorded behavior. A rejected call must mutate nothing. A call with a non-empty uniqueIds list that names a record the workflow knows answers 200 with status COMPLETED or ACCEPTED, and the deletion is observable through an independent read (GetMatchId no longer resolves the record to its previous match id).
Emulator: BatchDeleteUniqueId returns HTTP 501 with error code 'NotImplemented' for every request, valid or not — the handler is still the generated stub whose body is Err(crate::scaffolded::Scaffolded::not_implemented("BatchDeleteUniqueId")).
Why: a client cannot delete unique ids from a matching workflow at all, and a client that probes the validation boundary gets 'NotImplemented' where AWS gives a 400 ValidationException, so negative-path handling and retry classification (501 is not a client error) both go wrong.
Fix: implement the operation in its own handler in the entityresolution service crate — services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/batch_delete_unique_id.rs (the handle body at lines 147-165, and delete the SCAFFOLDED marker at lines 4-6) — refusing an empty uniqueIds list with ValidationException carrying AWS's fixed text, and removing the named unique ids from the workflow's match state (crate::state) so GetMatchId reflects the deletion.
Traces: entityresolution.batch-delete-unique-id-empty-list-rejected.

Cause 2 of 3 — CreateIdNamespace's enum ValidationException lists the allowed value set in the wrong order.
AWS: POST /idnamespaces with type @required targeting IdNamespaceType. A value outside the enum is refused with HTTP 400 ValidationException. Message template (recorded behavior; the model states the value set but not the message): "1 validation error detected: Value '<supplied value>' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [TARGET, SOURCE]". Fixed text: "1 validation error detected: Value ", " at 'type' failed to satisfy constraint: Member must satisfy enum value set: [TARGET, SOURCE]" — including the value-set order AWS prints. Variable part: only the rejected value echoed from the request.
Emulator: right status, right error code, right structure, but renders the value set in the Smithy declaration order — "... enum value set: [SOURCE, TARGET]" (Smithy: IdNamespaceType values are declared SOURCE, TARGET).
Why: the message is part of the refusal contract; clients and tests that assert on the validation message, and humans diffing emulator logs against AWS, see a different string, and it shows the message is being composed from the model's member order rather than reproducing the service's text.
Fix: the enum-constraint validation message rendering applied before the CreateIdNamespace handler runs (the boundary validator in the shared smithy server runtime that formats "Member must satisfy enum value set: [...]", as reached for services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/create_id_namespace.rs) — emit the value set in the order AWS prints for this member instead of the model's declaration order.
Traces: entityresolution.create-id-namespace-invalid-type-enum-rejected.

Cause 3 of 3 — PutPolicy's stale-revision-token ConflictException message is a generated sentence that interpolates the token, not AWS's text.
AWS: PUT /policies/{arn} with an optional token (Smithy: PolicyToken @length 36..36, pattern ^[a-fA-F0-9]{8}-...; ConflictException is modeled on PutPolicy with httpError 400). When the supplied token is no longer the current revision (here because AddPolicyStatement bumped the revision after the token was issued), AWS refuses with HTTP 400 ConflictException whose message is entirely FIXED text with NO variable parts: "Policy put request failed. Incorrect token." The refused write must not apply (the attempted statement is absent and the statement that staled the token survives), and a PutPolicy with a freshly fetched token must succeed and replace the document.
Emulator: the status (400), the error code (ConflictException) and the no-op semantics are right, but the message is "The policy token <token> is not the current revision of this resource's policy" — invented wording that additionally interpolates the request's token value (AWS's message contains no token).
Why: clients and tests that match on the conflict message to distinguish a stale-token retry from other 400 ConflictExceptions (workflow already exists, resource in use) do not match, and echoing the caller's token back changes the message per request where AWS's is constant.
Fix: the stale-token conflict message construction in the entityresolution service crate's message module — crate::state::messages::stale_policy_token, called from services/service-com-amazonaws-entityresolution-awsveniceservice/src/ops/put_policy.rs:233-236 — return AWS's constant text instead of a formatted sentence.
Traces: entityresolution.put-policy-stale-revision-token-rejected.
