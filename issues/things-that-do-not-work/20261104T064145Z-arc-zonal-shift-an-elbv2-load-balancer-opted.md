## Description
One net-new root cause in the arc-zonal-shift emulator, found by replaying the behavioral suite (simparity-behavioral-aws-v1). This bundle has 1 cause; it must be closed before submitting.

RELATION TO OPEN ISSUES (none of them covers these checks): open issue 20261102T114957Z-arc-zonal-shift-an-elbv2-load-balancer-with.md describes the SAME defect but carries the replay key of only one check (arc-zonal-shift.update-zonal-shift-extends-expiry), and open issue 20261029T193235Z-arc-zonal-shift-accessdenied-message-on-unknown-shift.md names the registration gap as its "Cause 3 of 3" with a replay key that no longer binds. The remaining open arc-zonal-shift issues (20261029T170702Z-… 403 body shape, 20261102T015300Z-… CancelZonalShift ValidationException value interpolation) are different causes and do not cover these checks.

Cause 1 of 1 — a load balancer whose zonal-shift integration has been turned on never becomes an ARC managed resource, so the ARC control-plane surface that is reached THROUGH a managed resource (StartZonalShift / UpdateZonalShift / CancelZonalShift against a real resource, practice runs, zonal autoshift, and the managed-resource listings themselves) can never be exercised. Failing checks: arc-zonal-shift.cancel-practice-run-wrong-shift-type-rejected, arc-zonal-shift.cancel-zonal-shift-already-canceled-rejected, arc-zonal-shift.concurrent-start-zonal-shift-exactly-one-wins, arc-zonal-shift.create-practice-run-configuration-duplicate-conflict-rejected, arc-zonal-shift.delete-practice-run-configuration-removes-it, arc-zonal-shift.delete-practice-run-configuration-while-autoshift-enabled-rejected, arc-zonal-shift.list-managed-resources-practice-run-status-reflects-config, arc-zonal-shift.practice-run-lifecycle-start-and-cancel, arc-zonal-shift.start-zonal-shift-creates-active-shift-and-shifts-weight, arc-zonal-shift.start-zonal-shift-duplicate-active-conflict-rejected, arc-zonal-shift.start-zonal-shift-invalid-az-rejected, arc-zonal-shift.start-zonal-shift-invalid-expires-in-format-rejected, arc-zonal-shift.update-zonal-autoshift-enabled-without-practice-config-rejected, arc-zonal-shift.update-zonal-shift-after-cancel-rejected, arc-zonal-shift.zonal-autoshift-configuration-toggle-reflects-in-managed-resource.

AWS: Smithy (com.amazonaws.arczonalshift#PercDataPlane): GetManagedResource = GET /managedresources/{resourceIdentifier}, success 200; input member resourceIdentifier (@httpLabel, @required, @length 8..1024); output members appliedWeights (map of Availability Zone -> weight, @required) and zonalShifts (list, @required), plus arn, name, autoshifts, practiceRunConfiguration, zonalAutoshiftStatus; modeled errors AccessDeniedException (client, 403), ResourceNotFoundException (client, 404), ValidationException (client, 400), ThrottlingException (429), InternalServerException (500). ListManagedResources = GET /managedresources, 200, output items (@required list of ManagedResourceSummaries), paginated by nextToken/maxResults. StartZonalShift = POST /zonalshifts, success 201, requires resourceIdentifier/awayFrom/expiresIn (pattern ^([1-9][0-9]*)(m|h)$)/comment. AWS documents (Route 53 ARC developer guide, "Network Load Balancers" under zonal-shift resource types) that an ALB/NLB is NOT auto-discovered: it becomes an ARC managed resource once zonal-shift integration is turned on for it via elbv2 ModifyLoadBalancerAttributes with Key=zonal_shift.config.enabled, Value=true. Recorded behavior: after that call, GetManagedResource on the load balancer ARN answers 200 within well under a minute with a NON-EMPTY appliedWeights map holding one entry per Availability Zone the load balancer spans, the resource also appears in ListManagedResources.items, and shifts started on it are visible in GetManagedResource.zonalShifts.

Emulator: registration never happens. GetManagedResource resolves only out of the arc-zonal-shift service's own store: after the attributability gate it reads store.managed_resources for the request's identifier and, finding no entry, answers 404 ResourceNotFoundException with the fixed text "no managed resource is registered with ARC for resourceIdentifier " followed by the identifier copied from the request (the identifier is the request value; the surrounding text is the emulator's own, and AWS emits no such refusal for a resource whose integration was just enabled). Nothing on the ELBv2 side ever publishes an entry: ModifyLoadBalancerAttributes validates the key against the service's attribute table and stores the key/value onto its own load-balancer record, and has no cross-service registration step at all, so the map stays empty forever and ListManagedResources likewise reports the resource as absent. Each of the 15 checks provisions the documented prerequisite (two subnets in distinct AZs, an internal Type=network load balancer, wait for load_balancer_available, ModifyLoadBalancerAttributes(zonal_shift.config.enabled=true)) and then polls GetManagedResource until appliedWeights is non-empty, treating ResourceNotFoundException/AccessDeniedException as not-yet-registered. The poll never terminates and the harness kills every one of them with "Check timed out after 60.0s", so none of their ARC assertions (shift creation, weight shifting, duplicate/conflict refusals, practice-run lifecycle, autoshift toggling, managed-resource listing) is ever evaluated. No exception propagates out of the EC2/ELBv2 provisioning calls, which rules out a hard failure in the setup steps.

Why: a client that follows AWS's documented sequence — create a load balancer, enable zonal-shift integration, then read GetManagedResource — blocks indefinitely on a resource real ARC registers within seconds, instead of receiving 200 with a populated appliedWeights map; and every ARC operation that takes a resourceIdentifier (StartZonalShift, practice-run configuration, UpdateZonalAutoshiftConfiguration) is unreachable, because there is no managed resource to name. On the emulator the entire ARC zonal-shift feature is therefore unusable end to end, and a caller sees a 404 with a message AWS never emits for a registered resource.

Fix: the arc-zonal-shift managed-resource registration path. The service's state (services/service-com-amazonaws-arczonalshift-percdataplane/src/state.rs — the managed_resources map read by ops/get_managed_resource.rs and by the ListManagedResources handler) must gain an entry when zonal-shift integration is enabled for an ELBv2 load balancer, with appliedWeights seeded to the full weight for each Availability Zone the load balancer spans and an empty zonalShifts list; i.e. the elbv2 ModifyLoadBalancerAttributes handler (or an equivalent cross-service registration seam) must publish the resource to ARC, and removing the attribute / deleting the load balancer must withdraw it. Once registered, the existing StartZonalShift / UpdateZonalShift / CancelZonalShift / practice-run / autoshift handlers must be reachable and their effects visible through GetManagedResource.appliedWeights, GetManagedResource.zonalShifts and ListManagedResources.items.

Traces: the 15 failing check ids listed above, all reported as "Check timed out after 60.0s". Note for the fixer: one of them (arc-zonal-shift.start-zonal-shift-invalid-expires-in-format-rejected) additionally waits for an ALB target registered in a TCP target group to reach TargetHealth.State="healthy" before it reaches the ARC poll, so verify that elbv2 DescribeTargetHealth reports "healthy" for it as well when re-replaying that check.
