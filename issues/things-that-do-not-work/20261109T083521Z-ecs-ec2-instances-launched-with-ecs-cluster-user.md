# ecs: EC2 instances launched with ECS_CLUSTER user data never become ACTIVE agent-connected container instances, so DistinctInstance placement, DeregisterContainerInstance's force requirement and DiscoverPollEndpoint are all unreachable

> _Note: this issue was identified against the code base at commit `70f3a3a7604d630d6ba1835b99fbb61e8ce58784`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterContainerInstance

## Description
One root cause, grounded in three failing checks the suite lists under `### ecs` and marks neither ALREADY FILED nor OWNED by an open issue.

Cause 1 of 1: an EC2 instance launched from the ECS-optimized AMI with an ECS-capable instance profile and the standard `echo ECS_CLUSTER=<cluster> >> /etc/ecs/ecs.config` user data never shows up as a container instance of that cluster, so every check whose first step is "get real EC2 capacity into this cluster" burns its entire budget before it can assert anything.
  AWS: on such an instance the ECS agent calls RegisterContainerInstance with a genuine instance-identity document, and ListContainerInstances / DescribeContainerInstances then report that instance with `status: ACTIVE` and `agentConnected: true`, carrying registeredResources / remainingResources (CPU, MEMORY, PORTS) that the scheduler places against. Smithy (com.amazonaws.ecs#AmazonEC2ContainerServiceV20141113): RegisterContainerInstance input {cluster, instanceIdentityDocument, instanceIdentityDocumentSignature, totalResources, versionInfo, containerInstanceArn, attributes, platformDevices, tags} -> output {containerInstance: ContainerInstance}; modeled errors AccessDeniedException 403, ClientException / ClusterNotFoundException / InvalidParameterException 400, ServerException 500. Everything the three checks then exercise is defined only over such a registered instance: StartTask (input member `containerInstances` is @required), DeregisterContainerInstance {cluster, containerInstance @required, force} and DiscoverPollEndpoint {containerInstance, cluster} -> {endpoint, telemetryEndpoint, serviceConnectEndpoint}, plus RunTask's `placementConstraints` of type `distinctInstance`. The model states the shapes, not the timing; the timing is recorded behavior only — in the recording an instance reaches ACTIVE with its agent connected well inside each check's budget (the checks allow 180-480s).
  Emulator: the registration never happens. `ecs list_container_instances(cluster=...)` keeps returning an empty `containerInstanceArns`, so the polling loop in each check (`_launch_real_container_instance` / `_launch_hosts` / `_two_host_estate`) never converges and the check is cut with `Error: Check timed out after 180.0s`. No error code and no error response is produced — the call simply never settles.
  Why: the whole ECS-on-EC2 plane is unusable AND unfalsifiable for a client. Three distinct behaviors can be neither obtained nor refused: (a) RunTask with `placementConstraints=[{type: distinctInstance}]` and `launchType=EC2` on a two-host cluster must place count=2 on two different hosts and cap count=3 at two placed tasks, returning one `failures[]` entry per rejected host whose `arn` is that host's container-instance ARN and whose `reason` is the fixed text `DistinctInstance placement constraint unsatisfied.`; (b) DeregisterContainerInstance without `force` on a host that still has a task placed must be refused with HTTP 400 `InvalidParameterException` and the fixed message `Found running tasks on the instance.`, leaving the instance `ACTIVE`, and must succeed (instance -> `INACTIVE`, dropped from ListContainerInstances) once that task is STOPPED; (c) DiscoverPollEndpoint must return a non-empty `endpoint` and the SAME `endpoint`/`telemetryEndpoint` on repeated calls for one registered instance, and must refuse a malformed `containerInstance` identifier with HTTP 400 `ClientException` whose message is AWS's fixed text (`instanceId length should be one of [32,36]` or `Could not locate resources`). The host ids, ARNs and cluster names in those messages are values from the request and the emulator's state; the quoted sentences are the fixed text. A client gets neither success nor an error — it hangs.
  Fix: whatever stands an emulator-launched EC2 instance up as an ECS agent host, plus the ECS `register_container_instance` handler and the container-instance records in `crate::state` that ListContainerInstances / DescribeContainerInstances are served from — an instance launched into a cluster must become an ACTIVE, agentConnected container instance with registered/remaining resources, and the scheduler, DeregisterContainerInstance's force check and DiscoverPollEndpoint must all resolve against it.
  Related open issue, which the suite did NOT bind to these three checks this run: 20261109T013920Z-ecs-4-net-new-causes-ec2-launched-hosts.md describes the same plane as its cause 1 and names these three check ids in its prose, but the report lists them with no OWNED-by marker, so they are not gated by it. Fixing that issue's cause 1 will very likely close this one too — replay the three ids below to confirm, and do not close this without replaying them.
  Traces: ecs.deep-ecs-2-ec2place-distinct-instance-third-task-on-two-hosts-rejected, ecs.deregister-container-instance-requires-force, ecs.poll-endpoint-requires-registered-instance.

## Evidence
Expected (recorded AWS): after `ec2 run-instances` into the cluster, `ecs list-container-instances --cluster <c>` returns at least one ARN and `ecs describe-container-instances` reports that ARN with `status: ACTIVE`, `agentConnected: true` and registered/remaining CPU, MEMORY and PORTS — within the checks' 180-480s polling budgets.

Actual (emulator): `ecs list-container-instances --cluster <c>` returns `containerInstanceArns: []` for the whole budget, and all three checks are cut at their poll:
  Error: Check timed out after 180.0s   (ecs.deep-ecs-2-ec2place-distinct-instance-third-task-on-two-hosts-rejected — cut in `_poll_until` from `_launch_hosts`, description "EC2 instances [...] register as ACTIVE, connected container instances")
  Error: Check timed out after 180.0s   (ecs.deregister-container-instance-requires-force — cut in `_poll_until` from `_launch_real_container_instance`, description "EC2 instance registers as an ECS container instance")
  Error: Check timed out after 180.0s   (ecs.poll-endpoint-requires-registered-instance — cut in `_poll_until` from `_launch_real_container_instance`, same description)

Because the registration poll comes before every assertion in all three bodies, none of the following AWS behaviors is ever reached, and each is what the check would have graded:
  - RunTask(count=3, launchType=EC2, placementConstraints=[{type: distinctInstance}]) on a two-host cluster: exactly 2 entries in `tasks` on two different `containerInstanceArn`s, and `failures` = one entry per rejected host, each `{arn: <that host's container-instance ARN>, reason: "DistinctInstance placement constraint unsatisfied."}` (the ARNs are state values; the reason sentence is fixed text). ListTasks(startedBy=<tag>) must then show exactly the two placed tasks, which reach RUNNING.
  - DeregisterContainerInstance(cluster, containerInstance) with a live task and no `force`: HTTP 400, `Error.Code = InvalidParameterException`, `Error.Message = "Found running tasks on the instance."` (whole message is fixed text), instance still `ACTIVE`; after StopTask + STOPPED the identical call succeeds and the instance becomes `INACTIVE` and leaves ListContainerInstances.
  - DiscoverPollEndpoint(cluster, containerInstance): non-empty `endpoint`, identical `endpoint` and `telemetryEndpoint` across repeated calls for the same instance; DiscoverPollEndpoint(containerInstance="not a valid @@@ identifier") -> HTTP 400, `Error.Code = ClientException`, `Error.Message` exactly one of AWS's fixed sentences `instanceId length should be one of [32,36]` / `Could not locate resources`.

The EC2 instance ids, container-instance ARNs, cluster names and startedBy tags in these messages are per-run values from the request and the emulator's state; the never-registering instance is the divergence.

## Steps to Reproduce
1. `ecs create-cluster --cluster-name <c>`.
2. Create an IAM role trusting ec2.amazonaws.com with `arn:aws:iam::aws:policy/service-role/AmazonEC2ContainerServiceforEC2Role` attached, plus a same-named instance profile containing it.
3. `ssm get-parameter --name /aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id` for the AMI, and pick a subnet + default security group in the shared VPC.
4. `ec2 run-instances --image-id <ami> --instance-type t3.micro --iam-instance-profile Arn=<profile-arn> --subnet-id <subnet> --security-group-ids <sg> --user-data $(printf '#!/bin/bash\necho ECS_CLUSTER=<c> >> /etc/ecs/ecs.config\n' | base64)`.
5. Poll `ecs list-container-instances --cluster <c>` -> stays `[]` for the whole budget. On AWS one ARN appears and `ecs describe-container-instances --cluster <c> --container-instances <arn>` reports `status: ACTIVE`, `agentConnected: true`.
6. Everything downstream is therefore unreachable: (a) `ecs run-task --cluster <c> --launch-type EC2 --count 3 --placement-constraints type=distinctInstance --task-definition <td>` on a two-host cluster (expect 2 placed on distinct hosts + one `failures[]` entry per host with reason "DistinctInstance placement constraint unsatisfied."); (b) `ecs start-task --cluster <c> --container-instances <ci> --task-definition <td>` then `ecs deregister-container-instance --cluster <c> --container-instance <ci>` with no `--force` (expect 400 InvalidParameterException "Found running tasks on the instance.", instance still ACTIVE; after `ecs stop-task` + STOPPED the same call must succeed and the instance must become INACTIVE); (c) `ecs discover-poll-endpoint --cluster <c> --container-instance <ci>` twice (expect the same non-empty endpoint/telemetryEndpoint) and `ecs discover-poll-endpoint --container-instance 'not a valid @@@ identifier'` (expect 400 ClientException with AWS's fixed message).
