# autoscaling group round-trip: create skips min/max validation and describe omits group defaults

> _Note: this issue was identified against the code base at commit `6f223cb07d8f19a9e48b2b4f7aac2665ac919e98`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAutoScalingGroups

## Description
Four causes on the Auto Scaling group create/describe/delete round trip. All four must be closed before submitting.

Cause 1 of 4: DescribeAutoScalingGroups omits the members AWS always materialises on a group. AWS: a described group carries its server-side defaults even when the client never set them — the recording shows CapacityReservationSpecification {CapacityReservationPreference: default}, AvailabilityZoneDistribution {CapacityDistributionStrategy: balanced-best-effort}, InstanceLifecyclePolicy {RetentionTriggers: {TerminateHookAbandon: terminate}}, ServiceLinkedRoleARN (the AWSServiceRoleForAutoScaling SLR arn), AvailabilityZoneIds, LaunchTemplate.LaunchTemplateId, plus the empty-but-present collections EnabledMetrics, TargetGroupARNs, TrafficSources, LoadBalancerNames, SuspendedProcesses and VPCZoneIdentifier. Smithy: shape AutoScalingGroup declares every one of these members (and marks AvailabilityZones, DefaultCooldown, HealthCheckType, CreatedTime, MinSize, MaxSize, DesiredCapacity required). Emulator: each of those twelve paths is reported missing (got None) on the described group. Why: a client that reads a group's effective configuration — to display it, to diff it before UpdateAutoScalingGroup, or to find the launch template id it was created with — gets null where AWS gives a value, so round-tripping a described group back into an update silently drops settings. Fix: the DescribeAutoScalingGroups serializer plus the group's creation defaults in autoscaling state (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01) — populate the defaulted structures at create time and always emit the list members, empty element rather than absent. Traces: autoscaling-update-group-partial-merges-and-clamps-desired-capacity#task#6 (and #task#8).

Cause 2 of 4: CreateAutoScalingGroup never checks MinSize <= MaxSize. AWS: a create with MaxSize below MinSize is refused with 400 ValidationError whose message is built from the request and names both bounds (recorded example: 'Max bound, 1, must be greater than or equal to min bound, 5'); Smithy: MinSize and MaxSize are both required members of CreateAutoScalingGroupType (targets AutoScalingGroupMinSize / AutoScalingGroupMaxSize). Emulator: returns 400 but with the launch-source complaint instead ('Valid requests must contain either LaunchTemplate, LaunchConfigurationName, InstanceId or MixedInstancesPolicy'), i.e. the bound relation is never validated and an unrelated validation fires first. Why: a client probing its own capacity validation is told the wrong field is at fault; worse, a request with a valid launch source and inverted bounds would be accepted and produce a group AWS would have rejected. Fix: CreateAutoScalingGroup input validation — add the MinSize/MaxSize (and DesiredCapacity within bounds) relational check and order it as the recording shows. Traces: autoscaling-resource-creation-validation-errors#task#1 (and #task#2).

Cause 3 of 4: a created group is not visible to DescribeAutoScalingGroups. AWS: after CreateAutoScalingGroup, DescribeAutoScalingGroups returns the group with the capacity values as submitted (the fixture asserts MaxSize 999999999, MinSize 0, DesiredCapacity 0 round-tripped exactly). Emulator: 200 with an EMPTY AutoScalingGroups element — the group is absent entirely. Why: every create-then-read workflow sees no group, so capacity values can never be confirmed and dependent calls fail. Hypothesis: this fixture's prerequisite steps did not complete (its setup includes the EC2 CreateVpc stub, already filed, and an ssm GetParameter that answers 400), so the create may never have been issued; re-replay this binding once those prerequisites answer, and if the group is created and still not described, the defect is in autoscaling's group state/index. Fix: autoscaling group state and the DescribeAutoScalingGroups lookup (no name/filter supplied must list all groups). Traces: autoscaling-asg-capacity-large-numeric-precision-preserved#task#5.

Cause 4 of 4: DeleteAutoScalingGroup reports failure during teardown of nine fixtures. AWS: 200 for a delete of a group that exists. Emulator: 400. Why: teardown cannot converge, so a client's cleanup path reports an error and leaks resources. Hypothesis: same prerequisite chain as Cause 3 — in these nine fixtures the group was never successfully created, so delete legitimately finds nothing; in the fixture where the group DOES exist (autoscaling-update-group-partial-merges-...) the delete does not diverge. Verify after Cause 3 and the filed EC2/ssm prerequisite gaps are closed; if delete still answers 400 for an existing group, fix the DeleteAutoScalingGroup handler. Traces: autoscaling-asg-capacity-large-numeric-precision-preserved#teardown#6 (also autoscaling-batch-delete-scheduled-action-partial-failure-envelope#teardown#8, autoscaling-batch-put-scheduled-action-partial-failure-envelope#teardown#8, autoscaling-batch-put-scheduled-actions-creates-multiple#teardown#8, autoscaling-scheduled-actions-pagination-max-records#teardown#11, autoscaling-step-scaling-and-predictive-scaling-policy-defaults#teardown#11, autoscaling-tags-pagination-max-records#teardown#9, autoscaling-target-tracking-disable-scale-in-alarm-count#teardown#9, autoscaling-target-tracking-target-value-decimal-precision-preserved#teardown#8).
