# CodePipeline: CreatePipeline never triggers its own execution, and an execution with a CodeCommit Source action never reaches Deploy (2 causes)

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePipeline

## Description
Two net-new root causes in the codepipeline crate, each grounded in a failing behavioral check the replay report left unmarked (not ALREADY FILED, not OWNED). Both failing check ids lead with the multi-service suite token codecommit__codepipeline__glue__iam__lambda; the diverging calls are codepipeline's (CreatePipeline, ListPipelineExecutions, ListActionExecutions) and both checks' SERVICES lists name codepipeline first, so they are filed against codepipeline — the same attribution open issue '20261023T185908Z-codepipeline-getpipeline-omits-an-action-s-empty-inputartifacts.md' uses for a sibling check of this same suite. A fixer must close BOTH causes before submitting.

Cause 1 of 2: CreatePipeline stores the declaration but never starts the one execution AWS starts for it, so the pipeline has no execution history at all. Failing check: codecommit__codepipeline__glue__iam__lambda.refarch-glue-pipeline-creation-triggers-one-failed-source-execution.
AWS: Smithy (com.amazonaws.codepipeline#CodePipeline_20150709) models ExecutionTrigger$triggerType over PipelineExecutionSummary, whose values include CreatePipeline, StartPipelineExecution, PollForSourceChanges and others. Recorded behavior: creating a pipeline RUNS it once — ListPipelineExecutions reports exactly one summary whose trigger.triggerType is 'CreatePipeline'. Against a source repository that has no branches that execution reaches status 'Failed' with sourceRevisions == [], its Source action execution reports status Failed with output.executionResult.errorDetails.code == 'ConfigurationError' and a non-empty externalExecutionSummary, no Deploy action execution exists in the history, and GetPipelineState reports a Deploy action state carrying NO latestExecution member at all.
Emulator: ListPipelineExecutions stays empty after CreatePipeline, so the check's 600 s poll for a terminal execution never resolves and the harness cuts it off — verdict 'mismatch', detail 'Check timed out after 60.0s'. Confirmed in the handler: services/service-com-amazonaws-codepipeline-codepipeline-20150709/src/ops/create_pipeline.rs validates the declaration, checks the role, stores `state.pipelines.insert(name, pipeline)` and returns; it never builds a PipelineExecutionRecord and never calls crate::state::record_execution/advance, which only start_pipeline_execution.rs does (and that one records triggerType StartPipelineExecution).
Why: 'no execution in the history' is not the same answer as 'one execution that failed at Source'. An operator asking why a pipeline has produced nothing gets the CreatePipeline trigger and the ConfigurationError from AWS; from the emulator they get an empty history, which reads as 'nothing ever ran because nothing triggered it' and hides the configuration defect. Every CloudFormation-deployed pipeline depends on this initial run.
Fix: the codepipeline crate's CreatePipeline handler (src/ops/create_pipeline.rs) must mint and drive an execution through crate::state::execution with trigger.triggerType = 'CreatePipeline', reusing the execution plane start_pipeline_execution.rs already uses.
Traces: codecommit__codepipeline__glue__iam__lambda.refarch-glue-pipeline-creation-triggers-one-failed-source-execution.

Cause 2 of 2: the execution plane cannot run a CodeCommit Source action or a Lambda-invoke Deploy action, so a started execution of an ordinary CodeCommit-sourced pipeline never produces a Deploy action execution. Failing check: codecommit__codepipeline__glue__iam__lambda.refarch-glue-deploy-reports-success-before-the-glue-run-finishes.
AWS: recorded behavior. Smithy models ActionDeclaration.actionTypeId (category/owner/provider/version) and ActionExecutionDetail with output.executionResult.externalExecutionId and lastUpdateTime, which ListActionExecutions reports. Recorded: for a pipeline whose Source action is {category Source, owner AWS, provider CodeCommit} on branch main and whose Deploy action invokes a Lambda, StartPipelineExecution drives Source to 'Succeeded' with output.executionResult.externalExecutionId equal to the branch tip's commit id, then runs the Deploy action, which reports 'Succeeded' with externalExecutionId equal to the launcher function name, and the overall execution reaches 'Succeeded' — Deploy completing BEFORE the Glue run it started resolves (the action's lastUpdateTime is earlier than the run's CompletedOn) is precisely the behavior under test.
Emulator: no Deploy action execution ever reaches a terminal status, so the check's 900 s poll for one exhausts and the harness cuts it off — verdict 'mismatch', detail 'Check timed out after 60.0s'. The crate documents this limitation itself at services/service-com-amazonaws-codepipeline-codepipeline-20150709/src/state/execution.rs:28-41: only Approval actions and S3-provider Source/Deploy actions are performed; "every other provider (CodeBuild, CloudFormation, Lambda, a custom job worker …) is work this emulator cannot perform, so its action FAILS". A CodeCommit Source provider is not in the supported set either. Hypothesis: the Source action fails immediately, the stage never advances, and ListActionExecutions therefore never shows a Deploy entry at all (the preceding Lambda-launcher 180 s State poll is the only other candidate for the stall; GetFunctionConfiguration is implemented in the lambda crate, so the Deploy poll is the far more likely consumer of the budget).
Why: CodeCommit source plus a Lambda invoke action is the canonical CodePipeline shape; with neither provider runnable, no pipeline an emulator user deploys ever reaches its deploy stage, and every claim about stage ordering, artifacts or downstream effects is unobservable. Combined with Cause 1, the whole execution surface of a realistic pipeline is missing while CreatePipeline/GetPipeline answer 200.
Fix: the codepipeline crate's execution plane (src/state/execution.rs and the action-runner it dispatches on actionTypeId.provider) — resolve a CodeCommit Source action against the codecommit service over the framework's in-process callback (branch tip -> source artifact, externalExecutionId = commit id) and perform a Lambda invoke Deploy action through the lambda service, so the stage advances and the action executions ListActionExecutions reports reach terminal statuses.
Traces: codecommit__codepipeline__glue__iam__lambda.refarch-glue-deploy-reports-success-before-the-glue-run-finishes.
