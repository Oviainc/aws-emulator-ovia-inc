# AWS Backup: 2 net-new causes — AssociateBackupVaultMpaApprovalTeam accepts a nonexistent approval-team ARN (204), and StartRestoreJob accepts DynamoDB restore Metadata with no TargetTableName (200)

> _Note: this issue was identified against the code base at commit `eebab1fc03169ac9ede9275cc690165ff01e833c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateBackupVaultMpaApprovalTeam

## Description
Two distinct net-new root causes in the AWS Backup emulator, both of them the same class of defect — a request real AWS refuses with a 400 InvalidParameterValueException is accepted with a 2xx — but in two different handlers with two different validation rules. Each cause is numbered and carries its own failing check ids; both must be closed before this work item is submitted.

=== Cause 1 of 2: AssociateBackupVaultMpaApprovalTeam does not resolve MpaApprovalTeamArn, so a well-formed ARN naming no approval team is accepted ===
AWS: Smithy (services/service-com-amazonaws-backup-cryocontrollerusermanager/smithy-model/com-amazonaws-backup-cryocontrollerusermanager.json): AssociateBackupVaultMpaApprovalTeam is PUT /backup-vaults/{BackupVaultName}/mpaApprovalTeam with success code 204 and an empty output; its input requires BackupVaultName (@pattern ^[a-zA-Z0-9\-\_]{2,50}$, httpLabel) and MpaApprovalTeamArn (target ARN); its modeled errors are InvalidParameterValueException, InvalidRequestException, MissingParameterValueException, ResourceNotFoundException (all client, httpError 400) and ServiceUnavailableException (500). The ARN member being syntactically well-formed is therefore not sufficient — the service resolves it. Recorded behavior: associating a syntactically valid but nonexistent approval-team ARN (arn:aws:mpa:<region>:<account>:approval-team/<uuid>) with an AVAILABLE logically air-gapped vault is refused 400 InvalidParameterValueException with the message "Parameter MpaApprovalTeamArn is invalid." — that sentence is entirely FIXED text; its only name-like part, MpaApprovalTeamArn, is the request's own modeled member name, so nothing in the message comes from this run's region, account, vault name or generated team uuid. The refusal leaves no association behind: a subsequent DescribeBackupVault on the same vault reports NO MpaApprovalTeamArn member. Separately, DisassociateBackupVaultMpaApprovalTeam (POST /backup-vaults/{BackupVaultName}/mpaApprovalTeam?delete, success 204) on a vault that never had a team attached is an idempotent no-op success and likewise leaves DescribeBackupVault with no MpaApprovalTeamArn.
Emulator: the associate call SUCCEEDS — the replay recorded HTTP 204 with an empty body where a 400 refusal was required ("expected the call to be refused, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 204, ...}}"). The handler accepts any value that parses as an ARN without resolving it against the account's approval teams, so the InvalidParameterValueException branch is unreachable, and the check cannot go on to grade the post-refusal DescribeBackupVault state or the idempotent no-op disassociate. The check's positive control passed in the same run (TagResource/ListTags on the same vault ARN took effect), so the acceptance is not explained by an unhealthy vault or account.
Why: a client that wires multi-party approval onto a vault is told the association succeeded when no approval team exists, so the vault it believes is protected by an MPA quorum has no approval team at all; the client has no error to catch and no way to detect the gap, and a typo'd or stale team ARN is silently accepted. Code that branches on InvalidParameterValueException to re-prompt for a team never runs.
Fix: the AssociateBackupVaultMpaApprovalTeam handler's validation in the backup crate — resolve MpaApprovalTeamArn against the approval-team state before mutating the vault, and refuse 400 InvalidParameterValueException with AWS's fixed sentence when it does not resolve, persisting no association. Note for the fixer: fixed issue 20261031T121352Z-backup-aws-backup-restore-access-vault-and-mpa-association.md previously addressed the SHAPE of MPA-association refusals (missing Code member, emulator-authored sentence); this is a different defect — the refusal is now not produced at all for an unresolvable team ARN — and that resolved issue does not cover it.
Traces: backup.mpa-approval-team-association-server-side.

=== Cause 2 of 2: StartRestoreJob performs no restore-Metadata validation for the recovery point's resource type, so DynamoDB Metadata omitting TargetTableName mints a restore job ===
AWS: Smithy: StartRestoreJob is PUT /restore-jobs with success code 200, requires RecoveryPointArn (ARN) and Metadata (sensitive string map), optionally takes IamRoleArn/IdempotencyToken/ResourceType/CopySourceTagsToRestoredResource, returns RestoreJobId, and models InvalidParameterValueException (client, httpError 400) among its errors. The Metadata map's required keys are determined by the recovery point's resource type; for a DynamoDB recovery point the target table name is required. Recorded behavior: StartRestoreJob with Metadata that omits that key is refused 400 InvalidParameterValueException with a message whose FIXED text is "Invalid restore metadata. Target table name must be provided with restore metadata. Restore metadata validation failed for DynamoDB with recoveryPoint " followed by the RecoveryPointArn taken verbatim from the request and a trailing "." — i.e. "Invalid restore metadata. Target table name must be provided with restore metadata. Restore metadata validation failed for DynamoDB with recoveryPoint <the request's RecoveryPointArn>." The only variable part is that ARN; "DynamoDB" is the recovery point's resource type. The refused call creates NO restore job (ListRestoreJobs reports none whose RecoveryPointArn is that recovery point), and the same call with the target table name supplied is accepted (200 + RestoreJobId), runs to DescribeRestoreJob Status COMPLETED, is listed by ListRestoreJobs for that recovery point, and materializes the restored table.
Emulator: the malformed call SUCCEEDS — the replay recorded HTTP 200 with a minted RestoreJobId where a 400 refusal was required ("expected the call to be refused, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}, 'RestoreJobId': '<minted id>'}"). StartRestoreJob now mints a restore job for any accepted RecoveryPointArn without inspecting the Metadata map against the recovery point's resource type, so neither the InvalidParameterValueException class nor its message nor the "no restore job created" consequence exists.
Why: a client cannot discover a malformed restore request at submission time. It gets a RestoreJobId for a restore that can never produce a correctly-named target resource, so its polling loop and its validation/retry branches are driven off a job that should never have existed, and the account accumulates restore jobs AWS would have refused. A least-privilege/least-surprise regression in the caller's own request-building code passes silently.
Fix: restore-Metadata validation in the StartRestoreJob handler (services/service-com-amazonaws-backup-cryocontrollerusermanager/src/ops/start_restore_job.rs) — resolve the recovery point, determine its resource type, and refuse 400 InvalidParameterValueException with the message above when the Metadata map lacks the key that type requires, persisting no restore job; only on acceptance mint the job. Note for the fixer: open issue 20261110T013454Z-backup-aws-backup-2-net-new-causes-a-backup.md describes this same check when StartRestoreJob answered 501 NotImplemented; the operation is now implemented and the failure signature has changed from a NotImplemented refusal to an unconditional 200 acceptance, so that issue's replay key no longer matches this check and the check was marked neither ALREADY FILED nor OWNED. Open issues 20261029T175130Z-backup-startrestorejob-stub.md and 20261108T091930Z-backup-events-backup-startrestorejob-answers-notimplemented-501-instead-of-synchronously.md describe the earlier 501 state and likewise do not cover the missing validation.
Traces: backup.start-restore-job-invalid-metadata-rejected.

## Steps to Reproduce
Cause 1 (backup.mpa-approval-team-association-server-side):
1. backup.CreateLogicallyAirGappedBackupVault(BackupVaultName=<fresh name>, MinRetentionDays=7, MaxRetentionDays=30); poll DescribeBackupVault until VaultState=='AVAILABLE'.
2. Positive control: backup.TagResource(ResourceArn=<the vault's BackupVaultArn>, Tags={...}) then backup.ListTags on the same ARN and confirm the tag took effect.
3. backup.AssociateBackupVaultMpaApprovalTeam(BackupVaultName=<vault>, MpaApprovalTeamArn='arn:aws:mpa:<region>:<account>:approval-team/<a freshly generated uuid that names no approval team>'). Expect ClientError 400 InvalidParameterValueException with message 'Parameter MpaApprovalTeamArn is invalid.'; the emulator answers HTTP 204 success.
4. backup.DescribeBackupVault(BackupVaultName=<vault>) -> AWS reports no MpaApprovalTeamArn after the refusal.
5. backup.DisassociateBackupVaultMpaApprovalTeam(BackupVaultName=<vault>) on a vault with no team -> AWS answers 204 as an idempotent no-op, and DescribeBackupVault still reports no MpaApprovalTeamArn.

3. backup.StartBackupJob(BackupVaultName=<vault>, ResourceArn=<table arn>, IamRoleArn=<role>) and poll DescribeBackupJob to COMPLETED; take its RecoveryPointArn.
4. backup.StartRestoreJob(RecoveryPointArn=<rp>, Metadata={'NotARealKey': 'x'}, IamRoleArn=<role>). Expect 400 InvalidParameterValueException with the restore-metadata message above and NO restore job; the emulator answers HTTP 200 with a RestoreJobId.
5. backup.ListRestoreJobs across all pages and filter on RecoveryPointArn==<rp> -> AWS lists nothing after the refusal; the emulator lists the job it should not have created.
6. backup.StartRestoreJob(RecoveryPointArn=<rp>, Metadata={'TargetTableName': <new name>}, IamRoleArn=<role>) -> accepted, DescribeRestoreJob reaches COMPLETED, ListRestoreJobs lists exactly that job, and the target table exists.
