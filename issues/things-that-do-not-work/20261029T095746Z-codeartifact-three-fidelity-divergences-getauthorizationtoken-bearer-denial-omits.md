# CodeArtifact: three fidelity divergences — GetAuthorizationToken bearer denial omits the 'on resource:' clause, ListPackageVersions returns DescribePackage's not-found message, and the npm endpoint never pulls through an external connection (3 causes)

> _Note: this issue was identified against the code base at commit `d1b341c944550181b7ac630538402367c666ba11`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListPackageVersions

## Description
Three distinct, net-new CodeArtifact root causes, bundled because they share one service. Cause 1 of 3 and Cause 2 of 3 are error-message/refusal-shape defects on control-plane operations that DO answer; Cause 3 of 3 is the missing external-connection pull-through on the npm repository endpoint (which now routes, so this is no longer the 'endpoint unrouted' defect).

=== Cause 1 of 3: the sts:GetServiceBearerToken denial for GetAuthorizationToken omits the 'on resource: <session-arn>' clause ===
Failing check: codeartifact.authorization-token-needs-sts-bearer-permission-that-a-domain-policy-cannot-grant
AWS: Smithy GetAuthorizationToken (POST /v1/authorization-token; required `domain`, optional `domainOwner`, `durationSeconds` @range 0..43200; modeled errors AccessDeniedException httpError 403, ValidationException 400, ResourceNotFoundException 404, ThrottlingException 429, InternalServerException 500). Minting a token requires sts:GetServiceBearerToken in the CALLER'S IDENTITY policy (https://docs.aws.amazon.com/codeartifact/latest/ug/tokens-authentication.html); a domain resource policy cannot grant it. When only that permission is missing, AWS refuses with AccessDeniedException (HTTP 403) and the standard IAM implicit-deny message, whose fixed text is "User: <principal-arn> is not authorized to perform: sts:GetServiceBearerToken on resource: <resource-arn> because no identity-based policy allows the sts:GetServiceBearerToken action". The fixed parts are "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action"; the variable parts are the principal ARN and the resource ARN (both the caller's assumed-role session ARN for this call) and the action name, all derived from the request's signing identity — the specific role name/session name/account id in any single run fill the template and are not part of it.
Emulator: returns AccessDeniedException with the message "User: <session-arn> is not authorized to perform: sts:GetServiceBearerToken because no identity-based policy allows the sts:GetServiceBearerToken action" — the entire " on resource: <resource-arn>" clause is missing. The error code and the action naming are correct; only the message is truncated. The positive control (both permissions present -> token minted) and the enforcement itself both work.
Why: clients, SDK log scrapers and permission-diagnosing tooling parse the IAM implicit-deny message for the resource the call was evaluated against; a message with no 'on resource:' segment makes an automated parse fail or report 'no resource', so operators cannot tell which resource the deny applies to and the emulator's denial text is not interchangeable with AWS's.
Fix: the message formatter for the AccessDeniedException the CodeArtifact GetAuthorizationToken handler raises when the caller's identity policy lacks sts:GetServiceBearerToken — the implicit-deny message template must include the ' on resource: <arn>' clause, with the resource ARN taken from the evaluated request context (the caller's session ARN for this bearer-token check).

=== Cause 2 of 3: ListPackageVersions answers DescribePackage's not-found message instead of the npm-package-not-in-repository message ===
Failing check: codeartifact.codeartifact-upstream-chain-resolves-through-two-hops-and-caches-in-the-front-repository
AWS: Smithy ListPackageVersions (POST /v1/package/versions; required `domain`, `repository`, `format`, `package`; modeled errors ResourceNotFoundException httpError 404, AccessDeniedException 403, ValidationException 400, ThrottlingException 429, InternalServerException 500). For a package that does not exist in the addressed repository, AWS refuses with ResourceNotFoundException (HTTP 404) whose message's fixed text is "The <format> package '<package>' does not exist in repository '<repository>'." — the variable parts are the format, the package name and the repository name, all taken verbatim from the request. The same template is recorded for DescribePackageVersion (recorded behavior only for the exact wording; the model carries only the error shape). This is a DIFFERENT template from DescribePackage's, which the recordings show as "Package not found in repository. Package = {format=<format>, name=<package>}" — that DescribePackage wording is asserted and PASSES in another check, so the two operations genuinely use different messages.
Emulator: ListPackageVersions for a package absent from the repository answers ResourceNotFoundException with DescribePackage's message, "Package not found in repository. Package = {format=npm, name=<package>}". The repository name is absent entirely and the sentence form differs.
Why: the repository name is the only thing that distinguishes 'absent from THIS repository' from 'absent from the domain' in a multi-repository upstream chain. A client walking an upstream chain (front -> mid -> back) cannot tell from the emulator's message which hop reported the miss, and any assertion or log match on AWS's wording fails.
Fix: the ResourceNotFoundException construction in the CodeArtifact ListPackageVersions handler (and any shared package-lookup helper it reaches through) must use the per-operation message template, not DescribePackage's, formatting format/package/repository from the request.

=== Cause 3 of 3: the npm repository endpoint never resolves or ingests through an associated external connection ===
Failing checks: codeartifact.ingested-package-defaults-to-publish-block-and-origin-type-partitions-the-versions, codeartifact.e2e-external-connection-upstream-fetch-then-disassociate-blocks
AWS: AssociateExternalConnection (POST /v1/repository/external-connection) attaches a public upstream such as public:npmjs to a repository. The npm registry wire protocol on the endpoint from GetRepositoryEndpoint(format='npm') is recorded behavior only (not in the Smithy model): with the GetAuthorizationToken token as the bearer credential, GET <endpoint>/<package> for a package held only upstream answers HTTP 200 with the packument, with dist.tarball rewritten to the repository's own endpoint, and fetching that tarball ingests the version into the repository. After ingestion the control plane shows it: ListPackageVersions reports the version with originType EXTERNAL, and DescribePackage reports originConfiguration.restrictions {publish: BLOCK, upstream: ALLOW} (the documented default for a package whose first version arrived by ingestion, https://docs.aws.amazon.com/codeartifact/latest/ug/package-origin-controls.html). A publish into that publish=BLOCK package is then refused HTTP 400 with body {"success":false,"error":"This package is configured to block new versions from being published."} — fixed text, no per-run values. After DisassociateExternalConnection, an already-cached version stays downloadable while an upstream version never fetched while the connection was live can no longer be retrieved.
Emulator: the endpoint is reachable and answers in CodeArtifact's own envelope (so this is not the already-filed unrouted-host defect 20261025T024028Z, whose refusal was 404 {"__type":"UnknownService"}), but it serves nothing from the external connection: GET <endpoint>/left-pad on a repository with public:npmjs associated answers HTTP 404 with body {"error":"Package not found in repository. Package = {format=npm, name=left-pad}"}, and the same GET for lodash answers HTTP 404. Because no packument is ever served, nothing is ingested: no EXTERNAL-origin version appears, the ingestion-derived origin default is never produced, the publish=BLOCK refusal and the originType partition are never exercised, and the post-disassociation cached-vs-never-fetched distinction cannot be observed.
Why: external connections are the primary reason to run CodeArtifact. With no pull-through, every upstream behavior is a silent no-op that looks correct — a blocked package has no versions and an allowed package also has no versions — so a client or CI pipeline validating dependency-substitution protection, origin controls or upstream caching passes against an emulator that enforces nothing, and `npm install` of any public dependency simply 404s.
Fix: in the CodeArtifact service, the npm package-format data-plane handlers on the repository endpoint need external-connection resolution: on a packument/tarball miss, fetch from the associated external connection, rewrite dist.tarball to this repository's endpoint, persist the fetched version into package/asset state as an EXTERNAL-origin version visible to the control-plane ListPackageVersions/DescribePackage handlers, default a newly ingested package's origin restrictions to {publish: BLOCK, upstream: ALLOW}, consult the package's origin configuration before ingesting, and stop resolving upstream once the connection is disassociated while keeping already-cached versions readable. NOTE: the pypi side of this same gap is already carried by open issue 20261027T083906Z-codeartifact-reopens-codeartifact-pypi-repository-endpoint-still-ingests-nothing.md (it owns check codeartifact.package-origin-configuration-blocks-upstream-ingestion); this cause is the npm data plane and is not carried by it.

Traces: see each cause's failing check ids above; all are listed in trace_ids.

## Steps to Reproduce
Cause 1:
1. iam.create_role(R) with a trust policy allowing the account root to sts:AssumeRole; attach an inline policy granting codeartifact:GetAuthorizationToken AND sts:GetServiceBearerToken.
2. Assume R; codeartifact.get_authorization_token(domain=D, durationSeconds=900) -> 200 with an authorizationToken (positive control).
3. Rewrite the inline policy to grant ONLY codeartifact:GetAuthorizationToken (drop sts:GetServiceBearerToken); repeat the same call -> expect AccessDeniedException whose message contains ' on resource: <caller session ARN>'; observe the emulator's message with that clause absent.

Cause 2:
1. codeartifact.create_domain(domain=D); create three repositories BACK, MID (upstreams=[BACK]), FRONT (upstreams=[MID]).
2. codeartifact.list_package_versions(domain=D, repository=FRONT, format='npm', package=P) for a package FRONT holds nothing for -> expect ResourceNotFoundException with message "The npm package '<P>' does not exist in repository '<FRONT>'."; observe 'Package not found in repository. Package = {format=npm, name=<P>}' (no repository name).
3. For contrast, codeartifact.describe_package(domain=D, repository=FRONT, format='npm', package=P) -> the 'Package not found in repository. Package = {...}' wording is correct there.

Cause 3:
1. codeartifact.create_domain(domain=D); create_repository(domain=D, repository=R); associate_external_connection(domain=D, repository=R, externalConnection='public:npmjs') -> all 200.
2. token = get_authorization_token(domain=D)['authorizationToken']; ep = get_repository_endpoint(domain=D, repository=R, format='npm')['repositoryEndpoint'].
3. HTTP GET ep + 'left-pad' with the token as bearer credential -> expect HTTP 200 packument with dist.tarball rewritten to ep; observe HTTP 404 {"error":"Package not found in repository. Package = {format=npm, name=left-pad}"}.
4. GET the advertised tarball, then poll list_package_versions(domain=D, repository=R, format='npm', package='left-pad') -> expect the ingested version with originType EXTERNAL; observe nothing is ever ingested.
5. describe_package(...)['package']['originConfiguration']['restrictions'] -> expect {'publish': 'BLOCK', 'upstream': 'ALLOW'}; then PUT an npm publish envelope for the same package -> expect HTTP 400 {"success":false,"error":"This package is configured to block new versions from being published."}, then relax with put_package_origin_configuration(restrictions={'publish':'ALLOW','upstream':'ALLOW'}) and expect the identical PUT to return 200.
6. Separately: after caching one version through the connection, disassociate_external_connection(...) -> the cached version must stay downloadable via get_package_version_asset while a version never fetched while the connection was live must be refused.
