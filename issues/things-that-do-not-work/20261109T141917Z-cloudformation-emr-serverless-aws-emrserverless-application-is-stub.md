# cloudformation__emr-serverless: AWS::EMRServerless::Application is stub-provisioned — the stack reaches CREATE_COMPLETE but no application exists in EMR Serverless, and Ref/PhysicalResourceId/GetAtt ApplicationId are the template Name instead of a generated applicationId

> _Note: this issue was identified against the code base at commit `6bab9504f4457a639e729a9dc2b08c46f536304f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: a CloudFormation stack declaring a single `AWS::EMRServerless::Application` resource reaches CREATE_COMPLETE and records a CREATE_COMPLETE resource event, but the resource is never provisioned through EMR Serverless itself, and the identifier CloudFormation hands back is not an EMR Serverless application id. Failing checks: cloudformation__emr-serverless.deploy-cfn-emrserverless-application-reaches-created-and-terminated, cloudformation__emr-serverless.deploy-cfn-emrserverless-application-invalid-release-label-rejected. Both fail at the first point where the stack's resource is crossed with EMR Serverless' own API, from opposite directions: the first finds nothing in ListApplications, the second finds the physical id is not even a well-formed applicationId.

AWS: Smithy com.amazonaws.emrserverless (AWS Toledo Web Service) models CreateApplication (POST /applications) returning `applicationId` @required, @length 1..64, @pattern ^[0-9a-z]+$ and `arn` @pattern ^arn:(aws[a-zA-Z0-9-]*):emr-serverless:.+:(\d{12}):\/applications\/[0-9a-zA-Z]+$; GetApplication (GET /applications/{applicationId}) takes that same `applicationId` with @pattern ^[0-9a-z]+$ as an httpLabel and errors ValidationException (400) / ResourceNotFoundException (404); ListApplications (GET /applications) returns the paginated `applications` list whose rows carry `id` and `name`. CloudFormation provisions AWS::EMRServerless::Application by calling that CreateApplication, so for a CREATE_COMPLETE stack: (a) the resource's PhysicalResourceId, {"Ref": "<logical id>"} and {"Fn::GetAtt": ["<logical id>", "ApplicationId"]} are all the SERVICE-generated applicationId (lower-case alphanumeric, matching ^[0-9a-z]+$) — never the template's `Name` property; (b) {"Fn::GetAtt": [...,"Arn"]} is the application ARN built from that id; (c) EMR Serverless' own API sees the application — an unfiltered, fully paginated ListApplications contains exactly one row whose `name` equals the template's Name and whose `id` equals that Ref, and GetApplication on it returns `state` CREATED, `name` = the template Name, `releaseLabel` = the template ReleaseLabel, `type` "Spark" for a template Type of "SPARK", and `autoStartConfiguration.enabled` = the template's AutoStartConfiguration.Enabled; (d) after the stack is deleted, the application is soft-deleted, so GetApplication on the same id keeps answering 200 with `state` TERMINATED rather than a not-found error. The names, ids and ARNs above are variable parts taken from the request and from the id the service generates — no value from one run is part of the requirement.

Emulator: the stack's AWS::EMRServerless::Application is recorded only inside CloudFormation. The physical id is the template's `Name` property verbatim (a value containing '-' and upper/lower mixed run text, e.g. a name of the form sim2real-cfnemrs-app-<hex>), and Fn::GetAtt ApplicationId returns that same string, so the PhysicalResourceId == ApplicationId cross-check passes while both are wrong. (1) In deploy-cfn-emrserverless-application-reaches-created-and-terminated, the fully paginated emr-serverless ListApplications contains NO row with the templated name: `AssertionError: expected ListApplications to report exactly the Ref 'sim2real-cfnemrs-app-9cb73f6127fd' under 'sim2real-cfnemrs-app-9cb73f6127fd', got []`. (2) In deploy-cfn-emrserverless-application-invalid-release-label-rejected, passing that physical id to GetApplication is refused by emr-serverless' own input validation: `botocore.errorfactory.ValidationException: An error occurred (ValidationException) when calling the GetApplication operation: 1 validation error detected: Value 'sim2real-cfnemrsctl-app-5386234be90a' at 'applicationId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-z]+$` — i.e. CloudFormation handed out an identifier its own target service cannot accept. Because the application never exists, every downstream assertion of these scenarios is unreachable: GetApplication's name/releaseLabel/type/state/autoStartConfiguration read-back, the Arn output cross-check, the post-delete TERMINATED tombstone, and (in the second check) the whole release-label rejection comparison the check exists to grade.

Why: a client that deploys EMR Serverless applications as IaC and then drives emr-serverless with the stack's Ref/GetAtt gets a green stack over an empty account. Every follow-on call — GetApplication, StartApplication, StartJobRun with applicationId=<Ref>, tagging, ListApplications-based inventory or drift checks — either fails input validation on the synthesized id or silently addresses nothing, and the stack reports success so there is no signal to retry or fail. Deleting the stack likewise leaves no TERMINATED tombstone to observe.

Fix: CloudFormation's AWS::EMRServerless::Application resource provisioner must create, update and delete through EMR Serverless' own state — the CreateApplication / UpdateApplication / DeleteApplication paths and the application records they write — instead of recording a stack-local resource. The identifier it returns as PhysicalResourceId / Ref / Fn::GetAtt ApplicationId must be the applicationId that provisioning generated (matching the modeled ^[0-9a-z]+$), and Fn::GetAtt Arn the ARN of that same record, so CloudFormation and emr-serverless cannot disagree; template Name / ReleaseLabel / Type / AutoStartConfiguration must be carried into that record so GetApplication and ListApplications read them back, and stack deletion must drive the same soft-delete that leaves GetApplication answering state TERMINATED. This belongs in the cloudformation crate's stack-resource provisioning for this type (services/service-com-amazonaws-cloudformation-cloudformation/src, the resource-provisioning path backing CreateStack/DeleteStack) together with the emr-serverless application state it must write (services/service-com-amazonaws-emrserverless-awstoledowebservice/src).

Traces: cloudformation__emr-serverless.deploy-cfn-emrserverless-application-reaches-created-and-terminated (ListApplications sees nothing), cloudformation__emr-serverless.deploy-cfn-emrserverless-application-invalid-release-label-rejected (GetApplication refuses the synthesized physical id).

Related but NOT covering: the ten open emr-serverless issues (e.g. 20261030T093552Z-emr-serverless-job-run-lifecycle-diverges-runs-never.md, 20261102T083744Z-emr-serverless-application-lifecycle-refusals-carry-emulator-authored.md) all concern applications/job runs created directly through emr-serverless, not CloudFormation provisioning of AWS::EMRServerless::Application, and none carries these replay keys. ## Evidence
Expected (deploy-cfn-emrserverless-application-reaches-created-and-terminated): after CREATE_COMPLETE, emr-serverless ListApplications (unfiltered, all pages) contains exactly one row whose `name` is the templated Name and whose `id` equals the stack output for {"Ref": "Application"}; that id also equals DescribeStackResource's PhysicalResourceId and Fn::GetAtt ApplicationId, matches ^[0-9a-z]+$, and GetApplication on it returns state CREATED, type "Spark", releaseLabel "emr-7.9.0", autoStartConfiguration.enabled false and arn equal to the Fn::GetAtt Arn output; after DeleteStack, GetApplication on the same id returns state TERMINATED.
Actual: AssertionError: expected ListApplications to report exactly the Ref 'sim2real-cfnemrs-app-9cb73f6127fd' under 'sim2real-cfnemrs-app-9cb73f6127fd', got [] — the Ref/PhysicalResourceId is the template Name, and no application with that name exists in EMR Serverless.

Expected (deploy-cfn-emrserverless-application-invalid-release-label-rejected): the control stack's Application PhysicalResourceId is a generated applicationId, so emrs.get_application(applicationId=<physical id>) succeeds and reports state CREATED with (name, releaseLabel, type, autoStartConfiguration) == (<templated name>, "emr-7.9.0", "Spark", {"enabled": False}).
Actual: botocore.errorfactory.ValidationException: An error occurred (ValidationException) when calling the GetApplication operation: 1 validation error detected: Value 'sim2real-cfnemrsctl-app-5386234be90a' at 'applicationId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-z]+$. (Fixed text of that message is AWS's standard "<n> validation error(s) detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>"; the value is the request's applicationId, here the CloudFormation-synthesized physical id.) The check never reaches the release-label rejection it grades, so whether the bogus release label is refused is untested here.

## Steps to Reproduce
Replay the behavioral suite and re-run the check ids in trace_ids. Minimal repro: CreateStack with TemplateBody {"AWSTemplateFormatVersion": "2010-09-09", "Resources": {"Application": {"Type": "AWS::EMRServerless::Application", "Properties": {"Name": "<app-name>", "ReleaseLabel": "emr-7.9.0", "Type": "SPARK", "AutoStartConfiguration": {"Enabled": false}}}}, "Outputs": {"ApplicationRef": {"Value": {"Ref": "Application"}}, "ApplicationArn": {"Value": {"Fn::GetAtt": ["Application", "Arn"]}}, "ApplicationId": {"Value": {"Fn::GetAtt": ["Application", "ApplicationId"]}}}}. Poll DescribeStacks until CREATE_COMPLETE, then: (1) DescribeStackResource(StackName=<stack id>, LogicalResourceId="Application") — PhysicalResourceId is the template's Name, not a ^[0-9a-z]+$ applicationId; (2) emr-serverless ListApplications with no filter, paging every result — no row has name == "<app-name>"; (3) emr-serverless GetApplication(applicationId=<that PhysicalResourceId>) — 400 ValidationException on the applicationId pattern instead of the application. Then DeleteStack and call GetApplication again: there is no TERMINATED tombstone to read.
