# cloudwatch__s3: deleting one bucket metrics configuration cannot be observed — no AWS/S3 FilterId series is ever published, so neither the deleted nor the surviving filter reports a datapoint

> _Note: this issue was identified against the code base at commit `4ca728998286b7558a3f8204f86decdeb692036b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricStatistics

## Description
One net-new root cause, reached after the control plane answered: CreateBucket, PutBucketTagging, two PutBucketMetricsConfiguration calls and the subsequent DeleteBucketMetricsConfiguration/GetBucketMetricsConfiguration all succeeded, and S3 data-plane traffic was driven against both filters' prefixes. The failure is on the metric READ side, so this is not a bootstrap gap or an unimplemented-stub failure.

Cause 1 of 1 — a bucket metrics configuration publishes no AWS/S3 request-metric datapoints, so the 'deleted filter goes quiet while its sibling keeps reporting' behaviour cannot occur at all.
AWS: recorded behavior only — neither the S3 nor the CloudWatch Smithy model describes metric emission; CloudWatch models only the read surface (GetMetricStatistics requires Namespace, MetricName, StartTime, EndTime, Period and takes Dimensions @length 0..30, returning Datapoints; ListMetrics takes Namespace @length 1..255 and Dimensions @length 0..10). The recording shows that after PutBucketMetricsConfiguration, S3 accounts request traffic matching that configuration's filter into the AWS/S3 namespace under the dimension pair [BucketName, FilterId] where FilterId's value is the configuration's Id; those series are readable through GetMetricStatistics and indexed by ListMetrics. Once one configuration is DELETED, its FilterId series stops gaining datapoints while a sibling configuration over the same traffic keeps publishing, so the deleted filter's last datapoint is older than the surviving filter's by at least the quiet window the check measures — and an alarm left on the deleted filter goes INSUFFICIENT_DATA rather than tracking requests.
Emulator: no AWS/S3 datapoint is produced for either FilterId at any point. The check cannot even establish its baseline — it never observes a first datapoint for the surviving configuration, so the deleted-vs-kept comparison is never reached and the check is killed at the harness budget ('Error: Check timed out after 180.0s').
Why: a client that enables S3 request metrics to partition traffic per prefix or tag, and that alarms or dashboards on AWS/S3 GetRequests/AllRequests/4xxErrors/BytesDownloaded per FilterId, sees permanently empty series; crucially, deleting a configuration is indistinguishable from keeping it, so the lifecycle signal an operator relies on (an alarm on a removed filter going quiet) never appears, and automation that waits for its own FilterId to publish blocks forever with nothing distinguishing 'no traffic' from 'metrics not implemented'.
Fix: the S3 request path's metrics-configuration accounting must publish AWS/S3 series dimensioned on [BucketName, FilterId] into the CloudWatch metric store, must stop publishing a FilterId's series when its configuration is deleted while leaving sibling configurations publishing, and those series must be registered in CloudWatch's metric-discovery index (services/service-com-amazonaws-s3-amazons3 request handling and the AWS/S3 namespace writer, plus the metric store/ListMetrics index in services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801). Already-open issue that does NOT carry this check's replay key: 20261025T062946Z-cloudwatch-s3-s3-request-metrics-configurations-publish-no.md names the same emission gap for two OTHER checks (s3-request-metrics-filter-partitions-traffic-into-cloudwatch, obs-s3-1-request-metrics-filter-counts-each-verb-exactly) and for the DescribeAlarmHistory wording; it does not list cloudwatch__s3.s3-tagfilter-deleted-metrics-configuration-stops-its-filter-series, and the deletion-stops-publishing half of the behaviour described here is not covered by it. Note for the fixer: this check declares its own first-data budget of 1500s, so once a first datapoint becomes observable promptly (an emulator has no 15-minute enablement lag) it must also settle inside the suite's per-check cap.
Traces: cloudwatch__s3.s3-tagfilter-deleted-metrics-configuration-stops-its-filter-series.

## Evidence
Expected: with two metrics configurations on one bucket (Id 'EntireBucket' with no filter and Id 'ImportantPrefix' filtered to important/), traffic under both prefixes makes GetMetricStatistics(Namespace='AWS/S3', Dimensions=[{Name:'BucketName',Value:<bucket>},{Name:'FilterId',Value:<id>}], Statistics=['Sum'], Period=60) return datapoints for BOTH ids; after DeleteBucketMetricsConfiguration(Id='ImportantPrefix') the 'ImportantPrefix' series gains no further datapoints while 'EntireBucket' keeps reporting for at least the quiet window.

Actual: GetMetricStatistics returns no datapoints for either FilterId for the entire run, so the first-data barrier is never satisfied and the check is terminated — the suite reports 'Error: Check timed out after 180.0s' for cloudwatch__s3.s3-tagfilter-deleted-metrics-configuration-stops-its-filter-series. No AWS/S3 metric dimensioned on the bucket is indexed either.

## Steps to Reproduce
Create a bucket; PutBucketMetricsConfiguration(Bucket, Id='EntireBucket', MetricsConfiguration={Id:'EntireBucket'}) and PutBucketMetricsConfiguration(Bucket, Id='ImportantPrefix', MetricsConfiguration={Id:'ImportantPrefix', Filter:{Prefix:'important/'}}); drive S3 requests under important/ and other/; poll cloudwatch GetMetricStatistics(Namespace='AWS/S3', MetricName='AllRequests'/'GetRequests', Dimensions=[{BucketName:<bucket>},{FilterId:'EntireBucket'}] and [...,{FilterId:'ImportantPrefix'}], Statistics=['Sum'], Period=60) until datapoints appear; then DeleteBucketMetricsConfiguration(Bucket, Id='ImportantPrefix') and keep driving the same traffic, comparing the two series' last datapoint times. Observe that no datapoint ever appears for either id. Replay cloudwatch__s3.s3-tagfilter-deleted-metrics-configuration-stops-its-filter-series.
