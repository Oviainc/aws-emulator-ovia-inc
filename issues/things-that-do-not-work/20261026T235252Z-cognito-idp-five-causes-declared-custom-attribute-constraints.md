# cognito-idp: five causes — declared custom-attribute constraints unenforced, GetUICustomization performs no IAM resource-scope check, UpdateIdentityProvider's 404 message wording, UpdateProvisionedLimit accepts a no-op value, UpdateUserPoolReplica answers NotImplemented

> _Note: this issue was identified against the code base at commit `f2163892bf40cea6da7d1662f28c14ec75c797c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AdminUpdateUserAttributes

## Description
Five net-new root causes in the cognito-idp emulator, all grounded in failing behavioral checks that the replay report marked neither ALREADY FILED nor OWNED. Each cause is numbered and carries its own failing check ids; all five must be closed before this issue is submitted.

Cause 1 of 5: a custom attribute's declared StringAttributeConstraints / NumberAttributeConstraints are never enforced on a write.
AWS: AddCustomAttributes stores the per-attribute constraints in the pool schema (Smithy: AddCustomAttributes.CustomAttributes @length 1..25 of SchemaAttributeType, carrying StringAttributeConstraints{MinLength,MaxLength} and NumberAttributeConstraints{MinValue,MaxValue}), and AdminUpdateUserAttributes validates every supplied value against the schema entry before persisting it, refusing an out-of-bound value with InvalidParameterException (Smithy: AdminUpdateUserAttributes models InvalidParameterException, httpError 400; NotImplemented is not in its error set). The message is built per violated attribute, with fixed text and the member/attribute name and the declared bound taken from the request and the pool schema: for a Number above MaxValue it is "user.<attribute-name>: Number must be less than <MaxValue>\n" (recorded example: "user.custom:level: Number must be less than 10\n"), and for a String longer than MaxLength it is "user.<attribute-name>: String must be no longer than <MaxLength> characters\n" (recorded example: "user.custom:tenant: String must be no longer than 8 characters\n"). The fixed text is everything except the attribute name and the numeric bound, which come from the request and the schema.
Emulator: AdminUpdateUserAttributes answers HTTP 200 with an empty body for custom:level="99" against a schema that declares NumberAttributeConstraints MinValue=1/MaxValue=10, so the out-of-range value is persisted. (The over-length String leg, and the AddCustomAttributes redefinition-is-refused leg later in the same check, were never reached because the check stops at the first accepted call — they are not claimed to diverge here, only unverified.)
Why: a client that relies on the pool schema as its validation boundary gets values its own code treats as impossible; worse, a schema/validation design that AWS would refuse passes locally, so the failure only appears in production.
Fix: the AdminUpdateUserAttributes handler's validation step in the cognito-idp service — resolve each supplied attribute against the pool's SchemaAttributes and enforce the declared String/Number constraints (and the same shared validation used by UpdateUserAttributes/SignUp) before any value is written; a refused write must leave all prior values intact.
Traces: cognito-idp.custom-attribute-schema-is-append-only.

Cause 2 of 5: GetUICustomization performs no IAM resource-level authorization, so a principal scoped to one user pool reads another pool.
AWS: Amazon Cognito evaluates IAM policies for the user-pool API operations, and a resource-level condition on the identity policy is enforced before the operation's own logic. A caller whose only statement allows cognito-idp:GetUICustomization on pool A's ARN is refused when it names pool B, with AccessDeniedException (403) — not Cognito's own NotAuthorizedException, which is reserved for token/user-level failures (Smithy: GetUICustomization models InvalidParameterException 400, NotAuthorizedException 403, OperationNotEnabledException 400, ResourceNotFoundException 404, TooManyRequestsException 429). The message is the standard IAM denial template, fixed text with the caller ARN, the action and the resource ARN substituted from the request context: "User: <caller-arn> is not authorized to perform: cognito-idp:GetUICustomization on resource: <user-pool-arn> because no identity-based policy allows the cognito-idp:GetUICustomization action". Everything but <caller-arn> (the assumed-role ARN of the signing credentials) and <user-pool-arn> (the targeted pool) is fixed text.
Emulator: the cross-pool call answers HTTP 200 with {"UICustomization": {}} — no authorization decision is made at all, and the positive control against the granted pool also succeeds, so the emulator is simply allowing everything.
Why: branding/UI configuration of any pool in the account is readable by any principal, so per-pool isolation cannot be tested locally and a least-privilege policy that AWS would honour appears to grant nothing extra; a negative authorization test can never pass.
Note: open issue 20261024T114943Z-cognito-idp-five-modeled-error-paths-answer-notimplemented.md (Cause 1) names these same two checks from the earlier phase when GetUICustomization answered NotImplemented. That phase is over — the handler now answers 200 — and that issue does not carry the current replay keys, so this cause is filed separately; a fixer closing either must land the IAM resource-scope evaluation.
Fix: the GetUICustomization handler plus the shared request-authorization step of the cognito-idp service: evaluate the signing principal's identity-based policy against the targeted pool ARN and refuse with AccessDeniedException before reading UI-customization state.
Traces: cognito-idp.get-ui-customization-cross-pool-access-denied, cognito-idp.get-ui-customization-cross-pool-access-denied-rejected.

Cause 3 of 5: UpdateIdentityProvider's ResourceNotFoundException message uses the Describe wording instead of its own.
AWS: UpdateIdentityProvider on a provider that does not exist in the pool is refused with ResourceNotFoundException (Smithy: UpdateIdentityProvider models ResourceNotFoundException, httpError 404). Its message is "Identity provider <ProviderName> in User Pool <UserPoolId> does not exist." — fixed text, with the provider name and the pool id taken from the request. This differs deliberately from the read operations: DescribeIdentityProvider and GetIdentityProviderByIdentifier say "Identity provider <name> for tenantId <UserPoolId> does not exist.", and the emulator already gets both of those right in the same check.
Emulator: UpdateIdentityProvider refuses with the correct code but the read operations' wording: "Identity provider <name> for tenantId <pool-id> does not exist." (recorded instance: 'Identity provider sim2realidpb1646497a717 for tenantId us-west-2_0a8fc2af0 does not exist.').
Why: a client or test that matches on the documented message of the mutating path (the only way to distinguish which call 404'd when several are chained) never matches, and the message mis-states the identifier kind as a tenantId.
Fix: the UpdateIdentityProvider handler's not-found error construction in the cognito-idp service — give the mutating path its own message template instead of reusing the describe/lookup one.
Traces: cognito-idp.identity-provider-lifecycle.

Cause 4 of 5: UpdateProvisionedLimit accepts a RequestedLimitValue that equals the current provisioned value instead of refusing it as a no-op.
AWS: UpdateProvisionedLimit "sets the provisioned limit for a specific API category. The value must be between the default limit and your account-level maximum limit in Service Quotas" (Smithy doc) and models InvalidParameterException (400) and ServiceQuotaExceededException (400). Recorded behavior: the requested value is compared against the CURRENT persisted ProvisionedLimitValue before any ceiling check, and re-requesting the account's own current value is always refused with InvalidParameterException whose message states the value is the same as the current provisioned limit (the check matches the fixed fragment "same as the current provisioned limit"; the surrounding text and any value in it come from the request/account state). Separately, a value above the account ceiling is refused with ServiceQuotaExceededException naming the requested value and the Service Quota.
Emulator: UpdateProvisionedLimit answers HTTP 200 and echoes a Limit for LimitDefinition {LimitClass: API_CATEGORY, Attributes: {Category: UserCreation}} with RequestedLimitValue equal to the value GetProvisionedLimit just reported (recorded run: 50), i.e. no same-value comparison exists. Because the check stops there, the above-ceiling ServiceQuotaExceededException leg is unverified, not claimed divergent.
Why: a client cannot tell an applied quota change from a silently ignored one — every request looks successful, so code that branches on InvalidParameterException/ServiceQuotaExceededException is never exercised and a quota workflow that AWS refuses appears to work.
Fix: the UpdateProvisionedLimit handler in the cognito-idp service: compare RequestedLimitValue with the stored ProvisionedLimitValue for the LimitDefinition and refuse the equal case with InvalidParameterException ahead of the Service-Quotas ceiling check, leaving the persisted value untouched.
Traces: cognito-idp.provisioned-limit-numeric-precision-preserved, cognito-idp.provisioned-limit-numeric-value-precision-round-trip.

Cause 5 of 5: UpdateUserPoolReplica answers NotImplemented.
AWS: UpdateUserPoolReplica takes UserPoolId, RegionName and Status and models InvalidParameterException (400), NotAuthorizedException (403), OperationNotEnabledException (400), ResourceNotFoundException (404) and TooManyRequestsException (429) — 'NotImplemented' is not a member of its error set. For a RegionName that was never added as a replica of the pool, the call is refused with ResourceNotFoundException and the message "Replica not found in the requested region" (fixed text; no value is interpolated), and the pool's replica list is unchanged.
Emulator: the call is refused with error code 'NotImplemented' (the scaffold answer), so neither the refusal path nor the ACTIVE/INACTIVE transition on a real replica is reachable. This is a different operation from CreateUserPoolReplica, whose own stub issue the replay report filed.
Why: multi-Region user pools have no reachable status surface at all — a client cannot activate or deactivate a replica, and the one refusal it must handle (an unregistered region) arrives as an unmodelled code no SDK error handler maps.
Fix: implement the UpdateUserPoolReplica handler in the cognito-idp service (replica lookup by region over the pool's replica state, the unregistered-region ResourceNotFoundException, and the Status transition read back by ListUserPoolReplicas).
Traces: cognito-idp.update-user-pool-replica-region-list-server-enforced.
