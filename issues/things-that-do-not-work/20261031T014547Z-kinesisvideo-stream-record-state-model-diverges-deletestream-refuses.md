# kinesisvideo stream record state model diverges: DeleteStream refuses an acknowledged stream, DescribeStream projects a non-opaque Version

> _Note: this issue was identified against the code base at commit `01c7fcf3c0ea1f4059dc8385cf9ae11a0d4a6576`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteStream

## Description
This issue bundles 2 net-new root causes, both of them in the kinesisvideo STREAM RECORD's state model (the stored `Stream` record, the status the clock gives it, and the `Version` token the state layer mints for it) and both surfacing on the stream read/delete paths. A fixer must close BOTH causes - the DeleteStream state gate AND the minted Version token's form - and re-replay both replay keys named below, not just the representative.

Cause 1 of 2: DeleteStream refuses a stream CreateStream has already acknowledged, answering 400 ResourceInUseException where the recording shows 200.
AWS: Smithy `DeleteStream` (POST /deleteStream, success code 200, `DeleteStreamOutput` has no members, so the success body is the empty JSON object `{}`); its modeled errors are ClientLimitExceededException (400), InvalidArgumentException (400), NotAuthorizedException (401), ResourceInUseException (400), ResourceNotFoundException (404) and VersionMismatchException (400). `ResourceInUseException`'s own documentation scopes it to a resource that "is not in Active status" (and points the caller at DescribeStream to check), i.e. a stream that is still being created or is already being deleted. The recordings show the ordinary sequence - CreateStream, use the stream, then DeleteStream by StreamARN with no CurrentVersion - answering HTTP 200 with an empty body; no recorded step refuses the delete of a stream that the create call already returned and that nothing has mutated since.
Emulator: that same delete answers HTTP 400 with body `{"__type": "ResourceInUseException", "Message": "The requested stream is not active."}` (fixed text, no request values interpolated - it is the service's own STREAM_NOT_ACTIVE_MESSAGE). The refusal comes from DeleteStream's state gate, which admits a record only when `status == ACTIVE`; the record is still in `CREATING`, because CreateStream parks it in CREATING with an `activates_at` instant and only the per-request `settle_clock` walk promotes it to ACTIVE once a CHOSEN 500 ms activation span has elapsed. Hypothesis (the model states none of this, and the recording only shows the 200): because the promotion is owed by the wall clock rather than by the call sequence, acceptance of the delete depends on how much real time passed since the create - the same create-then-delete sequence is accepted in other fixtures of this corpus and refused in these two, which is why the failure looks intermittent rather than systematic. What is observed, not hypothesised, is the status (400 instead of 200), the error code (ResourceInUseException where the recording has no error at all) and the message sentence above.
Why: a client - or any test teardown - that creates a stream, uses it, and deletes it gets a refusal AWS never gives, so the stream is leaked and the cleanup step fails; retry logic keyed on ResourceInUseException sits and waits for a status change that the caller cannot influence. Worse, the outcome is not a function of the request sequence, so the same program succeeds or fails depending on how fast its calls run - behaviour AWS never exhibits for a stream its own CreateStream has returned.
Fix: DeleteStream's handler state gate together with the CREATING-span model in the service state (CreateStream's `activates_at` seeding, the chosen STREAM_ACTIVATION_SPAN and `settle_clock`'s promotion): a stream that CreateStream has acknowledged must be deletable, so either the create must not leave the record in a status that refuses deletion for a chosen span, or the gate must admit a CREATING record and reserve ResourceInUseException/400 for a stream that is already DELETING.
Traces: kinesisvideo-get-data-endpoint#teardown#9, kinesisvideo-stream-tags#teardown#14.

Cause 2 of 2: DescribeStream projects a Version token that is not an opaque per-record identifier.
AWS: Smithy `StreamInfo$Version` targets `com.amazonaws.kinesisvideo#Version` (string, @length min 1 max 64, @pattern ^[a-zA-Z0-9]+$), documented "The version of the stream"; it is the value a caller feeds back as `CurrentVersion` to UpdateDataRetention/DeleteStream, and the service re-mints it on every mutation of the record. Beyond that pattern and length the model says nothing about the token's FORM, so for the form this is recorded behavior only: the corpus does not pin any single run's literal token (the expectation is the member's recorded shape class, reported as '<shaped-not-asserted>') - it asserts that the member carries a token of the form the service emits, an opaque per-record identifier that encodes nothing a caller can read.
Emulator: DescribeStream answers 200 and every other StreamInfo member matches, but $.StreamInfo.Version carries the state layer's minted token - `mint_version` returns base36(version_seq) concatenated with base36(now_nanos()), where `version_seq` is a store-GLOBAL mutation counter shared by streams and signaling channels - i.e. a lowercase-only base36 string (13 characters in the run that produced this report) whose leading digits are the account-wide mutation count and whose remainder is the mint-time nanosecond clock. The replay rejects that token's form on 9 steps across 4 fixtures.
Why: Version stops being opaque. A client can read the account's mutation ordering out of the prefix and guess the next token a record will carry, and every record minted in the same run shares a long common clock suffix, so code that treats Version as an opaque concurrency token (caching it, comparing prefixes, storing it fixed-width, asserting it is unguessable) behaves differently against the emulator than against AWS, and any test that pins the member's form fails.
Fix: the state layer's version minter (`mint_version` and the per-record `version` field it fills) - mint an opaque per-record token in AWS's form instead of encoding a store-global sequence plus the clock. DescribeStream's projection itself needs no change beyond re-replaying.
Traces: kinesis-video-stream-data-retention-version-guard#task#2 (also #task#4, #task#8, kinesis-video-stream-lifecycle-create-describe-delete#task#2, #task#7, kinesisvideo-stream-data-retention#task#2, #task#4, #task#8, kinesisvideo-stream-lifecycle#task#2).

Related open issues that do NOT cover these two causes: 20261029T231444Z-kinesisvideo-version-tokens-are-minted-from-a-global.md reports the same minter on DescribeSignalingChannel, ListStreams and ListSignalingChannels but does not carry the DescribeStream cluster's replay key, so cause 2 is filed with its own key (fixing the minter should close both, but this cluster must be re-replayed to confirm); 20261029T194209Z-kinesisvideo-stream-state-transitions-are-not-modeled-deletestream.md reports the OPPOSITE delete-path fault (a delete that hard-removed the record, and a second delete mis-refused as 404) and does not carry the teardown DeleteStream key of cause 1, where a FIRST delete of an acknowledged stream is refused.
