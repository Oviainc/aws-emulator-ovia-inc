# Batch inference job performs no inference: nothing is read from the input S3 object, nothing is written to the output S3 location, and all four record counts are never reported (1 cause)

> _Note: this issue was identified against the code base at commit `d3024881b49e6a38960b221dd9fb71d2129efe77`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateModelInvocationJob

## Description
One root cause, in the bedrock control plane's model-invocation-job (batch inference) execution path. This is NOT the job-clock defect already filed as 20261026T015550Z-bedrock-batch-inference-job-collapses-submitted-inprogress-completed-inside.md (that issue is scoped to the status dwell/transition timing); the cause below is that the job has no work step at all, and it would still be wrong after any fix to the clock.

Cause 1 of 1: a submitted batch inference job is a status record and nothing else — it never reads its `inputDataConfig` object, never invokes the model over the records in it, never writes anything under its `outputDataConfig` S3 prefix, and never reports `totalRecordCount`/`processedRecordCount`/`successRecordCount`/`errorRecordCount`.

AWS: Smithy `com.amazonaws.bedrock#CreateModelInvocationJob` takes a required `inputDataConfig` ("Details about the location of the input to the batch inference job") and a required `outputDataConfig` ("Details about the location of the output of the batch inference job"), and `GetModelInvocationJob`/`ListModelInvocationJobs` report four `NonNegativeLong` (@range min 0) members documented as `totalRecordCount` "The total number of records in the batch inference job", `processedRecordCount` "The number of records that have been processed in the batch inference job", `successRecordCount` "The number of records that were successfully processed in the batch inference job" and `errorRecordCount` "The number of records that failed to process in the batch inference job". The `ModelInvocationJobStatus` documentation ties the statuses to actual work and actual output: `Validating` checks "Your files are .jsonl files and each individual record is a JSON object in the correct format" and "Your files fulfill the requirements for file size and number of records"; `InProgress` – "This job has begun. You can start viewing the results in the output S3 location"; `Completed` – "This job has successfully completed. View the output files in the output S3 location"; `PartiallyCompleted` – "Not all of your records could be processed in time. View the output files in the output S3 location". So on AWS a job that reports `Completed` has consumed every record of the input object, has written result objects under the output prefix, and reports record counts that account for them (`totalRecordCount` equal to the number of records in the input, `successRecordCount` + `errorRecordCount` accounting for the processed ones).

Emulator: `CreateModelInvocationJob` validates the request, mints an ARN, and stores a `ModelInvocationJobRecord` whose fields are only identity, the two data configs as opaque echoes, the timeout, tags, a status and two due-instants; the input S3 object is never opened, no per-record model invocation is performed, and no object is ever put under the output prefix. The struct carries no record-count fields at all, so the summary the two reads are built from can only report `totalRecordCount`/`processedRecordCount`/`successRecordCount`/`errorRecordCount` as absent — a caller is served a `Completed` job with all four members omitted. `ModelInvocationJobRecord::settle` only rewrites `status`/`last_modified_at`/`ended_at`; there is no step between `Submitted` and `Completed` that touches S3. Consequently the two observable consequences the replayed end-to-end check asserts can never hold: `successRecordCount` is never equal to the submitted record count (it is never present), and `ListObjectsV2` on the output prefix returns no objects for a job the emulator reports as `Completed`. Replay symptom for `bedrock.e2e-batch-inference-job-produces-output`: the check did not reach those asserts and reported `Check timed out after 60.0s` — its status poll runs at a 60s interval and the first read lands in the non-terminal window, so the harness budget expires before the output assertions run; the output/counts gap above is read off the handler and the stored record rather than off that timeout.

Why: a client that relies on AWS's batch-inference contract gets wrong answers in the two places that matter. Any consumer that waits for `Completed` and then reads its results out of the output S3 location finds an empty prefix, so every downstream step (parsing `*.jsonl.out` records, joining results back to `recordId`, moving the output elsewhere) silently processes zero rows instead of failing loudly. Any consumer that reconciles counts — comparing `totalRecordCount` to the records it uploaded, alerting on `errorRecordCount` > 0, showing progress from `processedRecordCount` — reads absent members, which botocore surfaces as missing keys (or 0 after a `.get(..., 0)`), so a job that did nothing is indistinguishable from a job that processed everything perfectly. Batch inference is the only API surface where the result is the S3 output rather than the response body, so an emulator that writes none of it makes the whole operation untestable end to end.

Fix: the model-invocation-job execution step in this crate — the create handler's job submission plus the job's state record and its settle path. The stored record needs the four record counts the model reports, populated from the input object actually read out of the `s3InputDataConfig.s3Uri` (its record count becoming `totalRecordCount`), and the transition into a terminal status needs to write per-record result objects under the `s3OutputDataConfig.s3Uri` prefix and advance `processedRecordCount`/`successRecordCount`/`errorRecordCount` to match them, so that a job reported `Completed` has output and counts that agree with its input. A job whose input cannot be read or parsed should take the modelled failure path with a `message` rather than reporting `Completed` with nothing done.

Traces: failing check `bedrock.e2e-batch-inference-job-produces-output` (GROUP state-machine, asserts `successRecordCount` equals the uploaded record count and that the output prefix holds at least one non-empty object). Code for the fixer: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/create_model_invocation_job.rs:290-332 (the stored record — no input read, no counts, no output write); services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/state.rs:1550-1613 (`ModelInvocationJobRecord`, which has no record-count members) and :1621-1634 (`settle`, which only moves the status); services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/get_model_invocation_job.rs:258-261 (the four counts served straight off the summary).

## Evidence
Expected (AWS / Smithy): after CreateModelInvocationJob against a batch-capable model with inputDataConfig.s3InputDataConfig.s3Uri pointing at an N-record .jsonl object and outputDataConfig.s3OutputDataConfig.s3Uri pointing at a prefix, a job that reports status "Completed" also reports totalRecordCount = N and successRecordCount = N (errorRecordCount accounting for any failures), and the output prefix holds at least one non-empty result object (ModelInvocationJobSummary$successRecordCount: "The number of records that were successfully processed in the batch inference job"; ModelInvocationJobStatus$Completed: "This job has successfully completed. View the output files in the output S3 location").

Actual (emulator): GetModelInvocationJob on the same job reports status "Completed" with totalRecordCount, processedRecordCount, successRecordCount and errorRecordCount all absent from the response, and ListObjectsV2 on the output prefix returns no Contents — no object is ever written there. The job record the create stores (create_model_invocation_job.rs:292-325) holds only arn/name/region/clientRequestToken/roleArn/modelId/inputDataConfig/outputDataConfig/vpcConfig/timeout/jobExpirationTime/modelInvocationType/tags/status/in_progress_due_at/completed_due_at/submit_time/last_modified_at/ended_at; ModelInvocationJobRecord (state.rs:1550-1613) declares no record-count field, and settle (state.rs:1621-1634) rewrites only status, last_modified_at and ended_at. Nothing on the path opens the s3InputDataConfig object or puts an object under s3OutputDataConfig.

Replay output for bedrock.e2e-batch-inference-job-produces-output:

  Error: Check timed out after 60.0s

The check uploads a 100-record .jsonl input, creates a Bedrock-assumable role, submits the job, polls GetModelInvocationJob until a terminal status (60s interval), then asserts `job.get("successRecordCount", 0) == 100` and that `list_objects_v2(Prefix="output/")` returns at least one object with Size > 0 ("batch inference job reported Completed but wrote no output objects"). Those two asserts are unsatisfiable against the emulator as written, independently of the poll timing.

## Steps to Reproduce
1. Create an S3 bucket and put an object `batch-input.jsonl` containing N (e.g. 100) JSON lines, each with a `recordId` and a `modelInput`.
2. Create an IAM role Bedrock can assume with s3:GetObject/s3:PutObject/s3:ListBucket on that bucket.
3. bedrock:CreateModelInvocationJob with jobName, that roleArn, a batch-capable modelId (e.g. meta.llama3-1-8b-instruct-v1:0), inputDataConfig.s3InputDataConfig.s3Uri = s3://<bucket>/batch-input.jsonl and outputDataConfig.s3OutputDataConfig.s3Uri = s3://<bucket>/output/.
4. Poll bedrock:GetModelInvocationJob with the returned jobArn until status is terminal (it reports "Completed").
5. Observe that the Completed response carries no totalRecordCount, processedRecordCount, successRecordCount or errorRecordCount member at all (AWS reports totalRecordCount = N and successRecordCount = N).
6. Call s3:ListObjectsV2 with Prefix="output/" on the same bucket. Observe no Contents: the job that reported Completed wrote no output objects, so there is nothing to read the inference results out of.
