# osis refuses implemented-path calls with NotImplemented: PutResourcePolicy, TagResource, CreatePipelineEndpoint lookup and the pipeline HTTP ingest data plane

> _Note: this issue was identified against the code base at commit `69bb2c4e0c47afe7ac06c67651974f0cf752730a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutResourcePolicy

## Description
Behavioral replay of the OSIS suite found FOUR distinct, independently fixable paths where the emulator answers a call AWS serves with a generic `NotImplemented` (HTTP 501) instead of the modeled behavior. This issue bundles all four; each must be closed before submitting. None of these four checks is marked "ALREADY FILED" or "OWNED by" in the suite report. Related open issues: 20261021T234042Z-osis-validatepipeline-stub.md covers only ValidatePipeline; the TagResource scaffold-stub issue filed for check osis.untag-resource-removes-tag names the TagResource operation and file but not the reserved-prefix validation contract in Cause 2 below (Cause 2 can be closed together with it); 20261029T174701Z-osis-control-plane-responses-diverge-from-aws-across.md covers none of the four.

--- Cause 1 of 4: PutResourcePolicy answers NotImplemented instead of validating and storing the resource policy ---
AWS: Smithy PutResourcePolicy (PUT /2022-01-01/osis/resourcePolicy/{ResourceArn}, @idempotent, http code 200) takes ResourceArn (@required httpLabel, PipelineArn @length 46..76, pattern ^arn:(aws|aws\-cn|aws\-us\-gov|aws\-iso|aws\-iso\-b):osis:.+:pipeline\/.+$) and Policy (@required ResourcePolicy, @length 2..204800), returns {ResourceArn, Policy}, and models ValidationException (httpError 400, member `message`), ResourceNotFoundException(404), AccessDeniedException(403), LimitExceededException(409), DisabledOperationException(409), InternalException(500). Recorded behavior: a Policy that is not valid JSON (e.g. `{this is not valid json`) is refused 400 ValidationException with message `Invalid resource policy.` — entirely FIXED text, no variable parts — and no policy is attached (a following GetResourcePolicy returns an empty document, since osis has no not-found contract for an absent policy); a syntactically valid IAM-style policy on the same pipeline is accepted 200 and is retrievable byte-equivalently via GetResourcePolicy.
Emulator: every PutResourcePolicy call is refused with error code `NotImplemented` (HTTP 501) regardless of the Policy contents, so neither the rejection nor the accept path exists.
Why: resource-policy wiring (cross-account CreatePipelineEndpoint grants) cannot be exercised at all. A caller testing its rejection handling gets a 501 that no SDK models for this operation — it is retried as a server fault or surfaced as an unknown error instead of ValidationException — and a caller attaching a valid policy silently has no policy, so later authorization-dependent flows diverge.
Fix: the PutResourcePolicy handler in the osis service crate (services/service-com-amazonaws-osis-amazonopensearchingestionservice/src/ops/put_resource_policy.rs) — parse/validate the Policy document, reject non-JSON with 400 ValidationException + `Invalid resource policy.` without mutating state, and otherwise persist it in the pipeline's state so GetResourcePolicy returns it.
Traces: osis.put-resource-policy-invalid-json-rejected.

--- Cause 2 of 4: TagResource answers NotImplemented instead of rejecting reserved `aws:` tag keys and attaching normal tags ---
AWS: Smithy TagResource (POST /2022-01-01/osis/tagResource, http code 200) takes Arn (@required httpQuery `arn`, PipelineArn) and Tags (@required TagList) and models ValidationException(400, member `message`), ResourceNotFoundException(404), LimitExceededException(409), DisabledOperationException(409), AccessDeniedException(403). Recorded behavior: a tag whose Key uses the reserved `aws:` prefix is refused 400 ValidationException with message `Invalid System Tag: <tagKey> is missing Vendor Id.` — fixed text `Invalid System Tag: ` ... ` is missing Vendor Id.`, with <tagKey> the offending Key taken verbatim from the request; the tag is NOT attached (ListTagsForResource does not show it), while a normal-key tag on the same pipeline is accepted 200 and is visible via ListTagsForResource.
Emulator: TagResource is refused with code `NotImplemented` for both the reserved-prefix tag and the normal tag, so neither the validation nor the tagging state exists.
Why: tag-driven workflows (cost allocation, IaC tag reconciliation, resource-group membership) cannot run, and a client probing the reserved-prefix guard sees a 501 unmodelled for this operation instead of ValidationException — so an invalid tag reads as a transient server failure rather than a permanent client error.
Fix: the TagResource handler and the pipeline tag state it writes (services/service-com-amazonaws-osis-amazonopensearchingestionservice/src/ops/tag_resource.rs plus the osis tag state) — validate tag keys (reject the reserved `aws:` prefix with the AWS message, rejecting without partial mutation) and persist accepted tags so ListTagsForResource reflects them.
Traces: osis.tag-resource-reserved-prefix-rejected.

--- Cause 3 of 4: CreatePipelineEndpoint answers NotImplemented once VpcOptions are well-formed, instead of failing the pipeline lookup with ResourceNotFoundException ---
AWS: Smithy CreatePipelineEndpoint (POST /2022-01-01/osis/createPipelineEndpoint, http code 200) takes PipelineArn (@required) and VpcOptions (@required PipelineEndpointVpcOptions) and models ValidationException(400) and ResourceNotFoundException (httpError 404, member `message`). Recorded behavior: the request is validated in two stages — structurally malformed subnet/security-group ids are refused 400 ValidationException (that leg passes against the emulator), and a request whose ids satisfy their patterns but whose PipelineArn names a pipeline that does not exist is refused 404 ResourceNotFoundException with message `The pipeline could not be found` — entirely FIXED text, no variable parts, no ARN echoed. In neither case is an endpoint left behind (ListPipelineEndpoints does not show one).
Emulator: with a real subnet id and security group id (so request-shape validation is cleared) the same call against the same nonexistent pipeline ARN is refused with code `NotImplemented` instead of ResourceNotFoundException — the handler implements only the input-shape validation and stubs out the pipeline lookup/creation path behind it.
Why: the error is the signal that distinguishes "your ids are malformed" from "that pipeline does not exist". A client creating a VPC endpoint for a pipeline it has not yet created (or has deleted) gets an unmodelled 501 that SDKs may retry as a server fault, and cannot tell a missing pipeline from a bad request; the happy path (an endpoint created for an existing pipeline) is unavailable for the same reason.
Fix: the CreatePipelineEndpoint handler (services/service-com-amazonaws-osis-amazonopensearchingestionservice/src/ops/create_pipeline_endpoint.rs) — after VpcOptions validation, look the PipelineArn up in the osis pipeline state and return 404 ResourceNotFoundException with `The pipeline could not be found` when absent, and create/record the endpoint (visible in ListPipelineEndpoints) when present.
Traces: osis.create-pipeline-endpoint-invalid-vpc-options-rejected.

--- Cause 4 of 4: the pipeline's HTTP ingest data plane returns 501 NotImplemented, so an ACTIVE pipeline drops every ingested document ---
AWS: recorded behavior only — the ingest endpoint is a Data Prepper http source, not an operation in the Smithy model; the model's link to it is GetPipeline's Pipeline.IngestEndpointUrls, which the emulator does populate. Recorded behavior: once CreatePipeline reaches ACTIVE, a SigV4-signed (service name `osis`) POST of a JSON document array to `https://<ingest-endpoint-url><source path>` (here the config's http source path `/ingest`) returns a 2xx, and the document flows through the pipeline to the configured sink — the S3 sink bucket in the pipeline configuration body receives an object containing the posted record.
Emulator: the POST is answered HTTP 501 with body {"__type":"NotImplemented","message":"operation POST /ingest is not implemented in this emulator"} — the ingest endpoint URL is advertised by GetPipeline but the data plane behind it is a stub, so nothing is ingested and nothing reaches the sink.
Why: this is the service's entire purpose. The emulator reports a pipeline as ACTIVE and hands out an ingest URL, so a client believes it has a working ingestion path, while every document is refused; data-plane tests (ingest-then-assert-in-sink) cannot pass, and the 501 is not an error any ingestion client models.
Fix: the osis data-plane route that serves the advertised IngestEndpointUrls (the ingest/http-source handler of the osis service crate, alongside the pipeline state that holds the parsed pipeline configuration body) — accept SigV4-signed POSTs on the source path declared in the pipeline configuration, return 2xx, and deliver the records to the configured sink (for an s3 sink, write an object into the configured bucket) so a read-back of the sink finds the ingested document.
Traces: osis.native-protocol-http-ingest-round-trip.
