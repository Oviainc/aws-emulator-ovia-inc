## Description
Two net-new root causes in the eks add-on install path. Neither is an unimplemented scaffold stub (CreateAddon, DescribeAddon, ListAddons, DeleteAddon and DescribeAddonVersions all answer 200) and neither is marked ALREADY FILED or OWNED in the replay report. The nearest open neighbour, 20261026T235448Z-eks-updateaddon-stub.md, is only the UpdateAddon stub and covers neither cause. The previously resolved 20261026T235448Z-eks-3-net-new-root-causes-the-add.md seeded the add-on catalog (cert-manager and amazon-sagemaker-hyperpod-training-operator now publish, and the version the emulator installs is already the catalog default), which is what lets the replay get PAST the catalog lookup and reach the two causes below; neither cause is a refusal of an operation that issue fixed, and neither is described by it. BOTH causes must be closed.

Cause 1 of 2: an installed add-on always settles ACTIVE with no health issues, so no add-on ever reports a failed or degraded install.
AWS: Smithy: eks#Addon.status -> AddonStatus, an enum whose values are CREATING | ACTIVE | CREATE_FAILED | UPDATING | DELETING | DELETE_FAILED | DEGRADED | UPDATE_FAILED; eks#Addon.health -> AddonHealth.issues -> list of AddonIssue {code: AddonIssueCode, message, resourceIds}, where AddonIssueCode is AccessDenied | InternalFailure | ClusterUnreachable | InsufficientNumberOfReplicas | ConfigurationConflict | AdmissionRequestDenied | UnsupportedAddonModification | K8sResourceNotFound | AddonSubscriptionNeeded | AddonPermissionFailure. The model does not state WHICH outcome a given install produces, so recorded behavior only for the outcomes themselves: an add-on install is asynchronous and leaves CREATING for a terminal state that reflects what actually happened in the cluster. Installing amazon-sagemaker-hyperpod-training-operator on a cluster where its cert-manager prerequisite is absent settles status CREATE_FAILED with health.issues == [{code: K8sResourceNotFound, ...}] — the Kubernetes resources the add-on needs are not there. On a NODELESS cluster cert-manager applies but cannot place a replica and settles DEGRADED with health.issues == [{code: InsufficientNumberOfReplicas, ...}], and the operator installed after it is refused at admission by cert-manager's replica-less validating webhook and settles CREATE_FAILED with [{code: AdmissionRequestDenied, ...}]. The requirement is that the terminal status and the issue code follow from the cluster's actual state (prerequisite add-ons present or not, nodes present or not), not that any single recording's code is returned unconditionally.
Emulator: every CreateAddon mints the record with status CREATING and an unconditional due instant crate::state::ADDON_ACTIVATION_DELAY later, after which the first read flips it to ACTIVE; health is never populated. DescribeAddon of amazon-sagemaker-hyperpod-training-operator installed on an ACTIVE cluster with no cert-manager and no nodes answers HTTP 200 with status 'ACTIVE' and no health.issues (the check reads 'got ACTIVE []'), where AWS answers CREATE_FAILED with ['K8sResourceNotFound']. CREATE_FAILED, DEGRADED and the whole AddonIssueCode vocabulary are unreachable on this emulator.
Why: a client that gates on the add-on's terminal status is told every install succeeded. Readiness waiters (`aws eks wait addon-active`, CDK/Terraform/eksctl install steps) pass on an add-on that is not running; a client that diagnoses a bad install by reading health.issues[].code finds nothing to act on, and a dependency-ordering bug (installing an add-on before its prerequisite) is silently reported as success instead of CREATE_FAILED/K8sResourceNotFound.
Fix: the add-on lifecycle in this service's state and the CreateAddon handler that schedules it (services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_addon.rs, the AddonRecord it writes with status ADDON_STATUS_CREATING + active_at = now + ADDON_ACTIVATION_DELAY, and the read path in describe_addon.rs/list_addons.rs that materialises it) must decide the terminal state from cluster state rather than always owing ACTIVE: unmet prerequisite add-ons -> CREATE_FAILED with an AddonIssue code K8sResourceNotFound; a cluster with no nodes -> DEGRADED with InsufficientNumberOfReplicas for an add-on that needs a replica, and AdmissionRequestDenied for one refused at admission by a replica-less webhook. The record must carry the health issues so DescribeAddon reads them back.
Traces: eks.mbes-addon-install-on-a-live-cluster-rejects-bad-requests-and-bad-order (CREATE_FAILED/K8sResourceNotFound expected, ACTIVE/[] served). The same cause also sits behind the status half of eks__s3.e2e-manage-buckets-eks-sagemaker-lifecycle, which stops at Cause 2 before reaching it.

Cause 2 of 2: CreateAddon with no namespaceConfig installs the add-on into a hardcoded 'kube-system' instead of the add-on's own catalog default namespace.
AWS: Smithy: eks#CreateAddon.namespaceConfig (AddonNamespaceConfigRequest, namespace len 1..63) — 'The namespace configuration for the addon. If specified, this will override the default namespace for the addon'; eks#Addon.namespaceConfig (AddonNamespaceConfigResponse) — 'The name of the Kubernetes namespace where the addon is installed'; and eks#AddonInfo.defaultNamespace (returned by DescribeAddonVersions) — 'The default Kubernetes namespace where this addon is typically installed if no custom namespace is specified'. So when the request omits namespaceConfig, the add-on is installed into the defaultNamespace the catalog publishes for THAT add-on, and DescribeAddon echoes it in namespaceConfig.namespace. For cert-manager the catalog's defaultNamespace is 'cert-manager', not the kube-system that the core networking add-ons use.
Emulator: the handler validates a caller-supplied namespaceConfig.namespace and then falls back to a single global constant for every add-on — `input.namespace_config...unwrap_or_else(|| ADDON_DEFAULT_NAMESPACE.to_string())` — so CreateAddon(clusterName, addonName='cert-manager', resolveConflicts='OVERWRITE') stores namespace 'kube-system' and DescribeAddon answers namespaceConfig.namespace == 'kube-system'. The catalog itself is right: the SAME emulator's DescribeAddonVersions(addonName='cert-manager', kubernetesVersion=<cluster version>) publishes defaultNamespace 'cert-manager' (the check's expected value is read from that response), and the installed addonVersion already matches the catalog default — only the namespace diverges. The defect is that the install path never consults the catalog entry's defaultNamespace.
Why: the emulator contradicts its own catalog. A client that reads defaultNamespace to find where the add-on landed (to patch the Deployment, scope an EKS Pod Identity association, or target a namespaced kubectl/Helm operation) is given the wrong namespace, and because the same value is also used as the namespace of the associations CreateAddon mints for podIdentityAssociations, those associations are created against kube-system as well — so the (namespace, serviceAccount) pair a later association or a pod-identity credential lookup resolves is wrong too.
Fix: services/service-com-amazonaws-eks-awswesleyfrontend/src/ops/create_addon.rs — the namespace fallback must resolve the installed add-on's catalog entry (the same seed DescribeAddonVersions serves, crate::state's add-on catalog) and use ITS defaultNamespace, keeping ADDON_DEFAULT_NAMESPACE only as the value for catalog entries that publish no default; a caller-supplied namespaceConfig.namespace keeps overriding it.
Traces: eks__s3.e2e-manage-buckets-eks-sagemaker-lifecycle (phase 4/7 solve).
