# autoscaling__ec2__elbv2: 4 net-new root causes — IAM authorization is never evaluated, TerminateInstanceInAutoScalingGroup answers 501, DescribeAutoScalingGroups omits TargetGroupARNs, and target-group registration never converges

> _Note: this issue was identified against the code base at commit `637c0a54c7e9b591effc4af895837fd7874d2d9c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAutoScalingGroups

## Description
Four independent root causes in the Auto Scaling / EC2 / ELBv2 surface. Each must be closed before submitting.

Cause 1 of 4: Auto Scaling control-plane calls are executed without evaluating the caller's IAM authorization, so a caller holding none of the required permissions gets HTTP 200. Failing check ids: autoscaling__ec2__elbv2.asg-launch-without-runinstances-permission-rejected, autoscaling__ec2__elbv2.cli-scale-in-via-cli-denied-without-autoscaling-permission.
  AWS: CreateAutoScalingGroup with a `LaunchTemplate` synchronously checks that the calling principal is authorized to launch from that template (which requires `ec2:RunInstances`) and refuses a principal without it; SetDesiredCapacity refuses a principal without `autoscaling:SetDesiredCapacity`. Both refusals are authorization failures, not validation: HTTP 403 with error code `AccessDenied` and AWS's standard authorization sentence `User: <caller-arn> is not authorized to perform: <action> on resource: <resource-arn> because no identity-based policy allows the <action> action` — the fixed text is that sentence, and the caller ARN, action name and resource ARN are taken from the request and the evaluated policy. Smithy models no authorization error for these operations (CreateAutoScalingGroup: AlreadyExists/LimitExceeded/ResourceContention/ServiceLinkedRoleFailure; SetDesiredCapacity: ScalingActivityInProgress/ResourceContention), so AccessDenied is the service-common authorization refusal the recordings show — recorded behavior for the exact wording.
  Emulator: the call SUCCEEDS. The replay shows CreateAutoScalingGroup returning `HTTPStatusCode: 200` with an empty body for a principal scoped to describe-only actions, and the CLI `aws autoscaling set-desired-capacity` run under a permission-less role exits 0. No error is raised at all.
  Why: every negative-path client contract built on IAM — least-privilege rollouts, permission-boundary tests, guard rails that expect a 403 before a group is created — silently takes the success path, and a group/capacity change that AWS would have refused is actually applied. The emulator reports a more permissive security model than AWS.
  Fix: the authorization step in front of the autoscaling operation handlers (CreateAutoScalingGroup's launch-template authorization probe and the generic per-operation action check), not the handlers' own validation.

Cause 2 of 4: TerminateInstanceInAutoScalingGroup answers 501 `NotImplemented` instead of refusing an instance that is not a member of the named group. Failing check id: autoscaling__ec2__elbv2.asg-terminate-instance-outside-group-rejected.
  AWS: TerminateInstanceInAutoScalingGroup takes `InstanceId` (XmlStringMaxLen19) and required `ShouldDecrementDesiredCapacity`, and returns an `Activity`. For an EC2 instance that belongs to no Auto Scaling group it refuses with HTTP 400 and awsQuery error code `ValidationError`, message `Instance <instance-id> is not part of Auto Scaling group <group-name>.` — the fixed text is `Instance ` / ` is not part of Auto Scaling group ` / `.`, with the instance id and group name taken from the request; the id in any one recording is a per-run value, not part of the template. Smithy models only `ScalingActivityInProgressFault` and `ResourceContentionFault` for this operation, so the membership refusal is the service-common `ValidationError` the recording shows (recorded behavior). `NotImplemented` is in neither the model nor the recording.
  Emulator: the SDK error code is `NotImplemented` (the scaffold's 501 channel) where the check asserts `ValidationError`, so the operation refuses every caller — including the positive control that terminates a genuine member with decrement.
  Why: a client cannot distinguish "this instance is not in the group" from "the emulator has not implemented terminate"; scale-in and instance-replacement flows that go through this operation cannot run at all.
  Fix: the TerminateInstanceInAutoScalingGroup handler (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/terminate_instance_in_auto_scaling_group.rs) — implement the terminate against group state and return the membership `ValidationError` for a non-member.

Cause 3 of 4: DescribeAutoScalingGroups omits the `TargetGroupARNs` member entirely, so the key is absent from the parsed AutoScalingGroup. Failing check ids: autoscaling__ec2__elbv2.cli-asg-attach-load-balancer-target-groups-command, autoscaling__ec2__elbv2.cli-target-group-attach-fails-with-invalid-arn.
  AWS: Smithy: `AutoScalingGroup.TargetGroupARNs` (target `TargetGroupARNs`, list) is part of every described group. AWS always serializes the element in the awsQuery response — as an empty `<TargetGroupARNs/>` when no target group is attached, and holding each attached target group's ARN after AttachLoadBalancerTargetGroups — so botocore always yields the `TargetGroupARNs` key (value `[]` or the ARN list).
  Emulator: the member is missing from the serialized group, so `describe_auto_scaling_groups(...)['AutoScalingGroups'][0]['TargetGroupARNs']` raises `KeyError: 'TargetGroupARNs'`.
  Why: any client that reads a group's attached target groups — the attach/detach workflows, drift detection, CLI `--query 'AutoScalingGroups[].TargetGroupARNs'` — crashes on a missing key rather than seeing an empty list, and cannot observe the result of an attach at all.
  Fix: the DescribeAutoScalingGroups serializer / the group projection it builds (the autoscaling crate's describe_auto_scaling_groups op and its group-to-wire mapping), which must always emit TargetGroupARNs, empty element included.

Cause 4 of 4: an ASG attached to an ELBv2 target group never converges — its instances never become registered targets, so every check that polls for that convergence exhausts its budget with no terminal result. Failing check ids: autoscaling__ec2__elbv2.cli-create-asg-with-target-group-and-verify-ec2-registration, autoscaling__ec2__elbv2.cli-describe-target-health-reflects-asg-instances, autoscaling__ec2__elbv2.cli-detach-instance-from-asg-decrements-target-group.
  AWS: an Auto Scaling group whose `TargetGroupARNs` names a target group registers each instance it launches into that target group; DescribeTargetHealth then reports exactly the instance ids the group manages, and DetachInstances deregisters exactly the detached instance while leaving the rest registered. The recordings reach that steady state well inside the checks' own deadlines. Recorded behavior only (the model states the representation, not the reconciliation).
  Emulator: none of these polls ever observes the expected registration/deregistration; all three checks end with `Check timed out after 60.0s`, i.e. the emulator produced no convergence at all in that window rather than a wrong answer.
  Why: a client waiting for `describe-target-health` to reflect its ASG's instances waits forever; nothing tells it the registration will never happen, so load-balanced ASG rollouts hang instead of failing.
  Fix: the Auto Scaling group reconciliation that propagates group membership into ELBv2 target-group registration (the autoscaling crate's group state/reconciler and its attach/detach of target groups), not the describe serializers.

Hypothesis (not asserted by model or recording): causes 3 and 4 may share one incomplete target-group attachment model in the group state; they are listed separately because the first is a serialization omission observable on a group with no instances, the second is a reconciliation that never runs.
