# apigateway__iam: AWS_IAM authorization at a deployed execute-api stage is not enforced at all — 6 net-new root causes (identity policy, explicit Deny, session policy, resource policy, principal attribution, decision ordering)

> _Note: this issue was identified against the code base at commit `024100b485faef6e8a7d69224b42c4d112173d44`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
All 21 failing checks under the `apigateway__iam` heading are net-new (none is marked ALREADY FILED or OWNED). They decompose into 6 distinct root causes, all in the execute-api data-plane authorization step that must run before integration dispatch for a method whose `authorizationType` is `AWS_IAM`. Open issues about API Gateway's IAM surface that do NOT cover these (they are about TestInvokeMethod never returning, or about control-plane calls) include 20261101T201430Z-apigateway-dynamodb-iam-lambda-apigateway-testinvokemethod-never-returns-its-response-envelope-and.md and 20261102T121914Z-apigateway-dynamodb-iam-lambda-the-iam-authorization-e2e.md; here the stage DOES answer — it answers 200 where AWS denies.

=== Cause 1 of 6: no identity-policy evaluation of execute-api:Invoke ===
AWS: a request to a deployed stage whose method is `authorizationType=AWS_IAM` is served only when the signing principal's effective identity policy contains an Allow for action `execute-api:Invoke` on the method ARN `arn:aws:execute-api:<region>:<account-id>:<rest-api-id>/<stage>/<HTTP-VERB>/<resource-path>`. ARN matching is literal: the verb is matched case-sensitively, a non-wildcard path segment does not cover its children, and a grant naming a different rest-api-id or a different stage does not apply. With no matching Allow AWS answers HTTP 403, header `x-amzn-ErrorType: AccessDeniedException`, body `{"Message":"User: <caller-arn> is not authorized to perform: execute-api:Invoke on resource: <method-arn>"}`. Fixed text: `User: ` / ` is not authorized to perform: execute-api:Invoke on resource: `; variable parts: the caller ARN (the assumed-role session ARN of the signer) and the method ARN assembled from the request's region, account, rest-api-id, stage, verb and resource path. recorded behavior only — the on-disk Smithy model (services/service-com-amazonaws-apigateway-backplanecontrolservice) models only the control plane and says nothing about the execute-api data plane.
Emulator: every signed request is served. A role with no execute-api policy at all gets 200 `{"served": "GET"}`; a POST-only grant serves GET; a grant for one agreement id serves a sibling agreement id; a grant naming another rest-api-id or another stage is honoured on this one; a lowercase verb in the grant ARN is honoured for the uppercase request; a literal parent-path grant is honoured for a child path; a grant naming a nonexistent api id admits the real one; detaching/rewriting the managed or inline policy changes nothing; and a `//` double-slash stage path is served rather than normalized and then denied.
Why: a client that relies on execute-api:Invoke scoping as its authorization boundary gets none. Every caller that can sign at all reads and writes every method of every stage of every API, and least-privilege grants, policy detachment and policy rewrites are all unobservable — a privilege-escalation-shaped divergence, not a cosmetic one.
Fix: the execute-api data-plane request authorizer in the apigateway service crate — the AWS_IAM authorization step that must resolve the SigV4 signing principal, build the method ARN for the matched route, evaluate its identity policies and refuse with 403 AccessDeniedException before any integration is dispatched.
Traces: apigateway__iam.xsvc-apigateway-3-iam-role-without-invoke-permission-denied ("attempt 0: unpermitted GET returned 200 '{\"served\": \"GET\"}'"), apigateway__iam.xsvc-apigateway-3-iam-identity-allow-invokes-only-the-granted-method ("ungranted POST returned 200"), apigateway__iam.post-scoped-invoke-grant-denies-the-get-only-agreement-endpoint, apigateway__iam.exact-agreement-grant-admits-that-agreement-and-denies-another, apigateway__iam.grant-scoped-to-another-api-id-is-denied-on-this-api, apigateway__iam.stage-scoped-grant-for-another-stage-is-denied, apigateway__iam.lowercase-verb-in-the-invoke-arn-is-denied-case-sensitively, apigateway__iam.parent-path-grant-without-a-wildcard-does-not-cover-the-child-denied, apigateway__iam.invoke-grant-naming-a-nonexistent-api-is-accepted-by-iam-and-denied-at-the-stage, apigateway__iam.managed-get-policy-attached-to-the-post-scoped-role-admits-it-until-detached, apigateway__iam.rewriting-the-post-grant-to-get-admits-a-fresh-session-and-reverting-denies-again, apigateway__iam.double-slash-in-the-stage-path-is-normalized-before-authorization.

=== Cause 2 of 6: an explicit Deny in the identity policy does not override a wildcard Allow ===
AWS: IAM evaluation is deny-overrides. A statement `Effect: Deny, Action: execute-api:Invoke, Resource: <one method arn>` alongside a wildcard Allow denies that one method: 403 with `x-amzn-ErrorType: AccessDeniedException`.
Emulator: the explicitly denied path is served 200 `{"agreementId": "blocked-001", "served": "GET"}`.
Why: a client that carves an exception out of a broad grant with an explicit Deny finds the exception has no effect, so data it deliberately fenced off is readable.
Fix: the same data-plane authorizer's policy evaluator — it must collect Deny statements and apply deny-overrides precedence, not stop at the first Allow (or at no evaluation at all).
Traces: apigateway__iam.explicit-deny-on-one-agreement-overrides-a-wildcard-allow.

=== Cause 3 of 6: the STS session policy is never part of the effective permissions ===
AWS: when AssumeRole carried an inline session `Policy`, the effective permission is the intersection of the role policy and the session policy. A session policy naming only POST denies a GET the role grants, with HTTP 403, `x-amzn-ErrorType: AccessDeniedException` and message `User: <assumed-role session arn> is not authorized to perform: execute-api:Invoke on resource: <method-arn> because no session policy allows the execute-api:Invoke action`. Fixed text includes the trailing clause ` because no session policy allows the execute-api:Invoke action`; the principal ARN, method ARN and the account/region in it are values from the request and the emulator's state.
Emulator: the POST-scoped session's GET returns `(200, None, None)` — no denial, no error type header, no message.
Why: a client that narrows a session's reach with a session policy at AssumeRole time keeps the role's full reach, so credential vending with a reduced scope is not a boundary at all.
Fix: the data-plane authorizer must read the session policy bound to the presented session credentials and intersect it with the identity policies, and the denial serializer must emit the `because no session policy allows the execute-api:Invoke action` clause for that denial class.
Traces: apigateway__iam.session-policy-naming-post-denies-get-that-the-role-grants.

=== Cause 4 of 6: the REST API resource policy is never evaluated at the stage ===
AWS: a REST API's resource policy (set through UpdateRestApi `/policy` and taking effect on a new deployment) is evaluated together with the identity policy. An Allow in the resource policy rescues a principal with no identity grant; an explicit Deny in it beats an identity Allow; `Condition` keys such as `IpAddress`/`NotIpAddress` on `aws:SourceIp` are honoured against the caller's address. A resource-policy explicit deny answers 403, `x-amzn-ErrorType: AccessDeniedException`, message `User: <assumed-role session arn> is not authorized to perform: execute-api:Invoke on resource: <method-arn> with an explicit deny in a resource-based policy` — the trailing clause ` with an explicit deny in a resource-based policy` is fixed text; principal and method ARN are values.
Emulator: the resource policy has no effect in either direction. Before any resource policy is attached the ungranted role is already served 200 (so the "rescue" transition is unobservable); a `NotIpAddress 192.0.2.0/24` Deny does produce a 403 but with the bare identity-style message `User: arn:aws:iam::000000000000:user/emulator is not authorized to perform: execute-api:Invoke on resource: arn:aws:execute-api:us-west-2:000000000000:<api>/test/GET/widgets` — missing the resource-based-policy clause; and the explicit-deny-beats-identity-allow scenario never reaches a verdict within the suite's 60 s cap.
Why: a client that protects an API with a resource policy — the only lever available for cross-account and source-IP restriction on REST APIs — gets neither its Allow nor its Deny nor its conditions, and cannot distinguish a resource-policy denial from an identity denial from the message.
Fix: the data-plane authorizer must load the deployed snapshot's REST API resource policy, evaluate it with the request condition context (at minimum `aws:SourceIp`), apply deny-overrides across identity and resource policies, and the denial serializer must append the resource-based-policy clause for that class.
Traces: apigateway__iam.xsvc-apigateway-3-iam-resource-policy-allow-rescues-unauthorized-role, apigateway__iam.xsvc-apigateway-3-iam-resource-policy-source-ip-any-cidr-allow-invokes, apigateway__iam.xsvc-apigateway-3-iam-resource-policy-explicit-deny-beats-identity-allow-denied, apigateway__iam.xsvc-apigateway-3-iam-resource-policy-not-ip-address-deny-blocked.

=== Cause 5 of 6: the SigV4 signature is not verified, so a forged signature is served ===
AWS: execute-api verifies the presented SigV4 signature against the secret of the named access key. A request signed with the wrong secret is refused 403 (`AccessDeniedException` / an invalid-signature refusal); the integration is never reached.
Emulator: the wrong-secret GET returns 200 `{"served": "GET"}` — the signature is parsed for identity but never checked.
Why: any party that learns an access key id, without the secret, can invoke every AWS_IAM-protected method. Signature verification is the whole point of SigV4 at the edge.
Fix: the execute-api data-plane SigV4 verifier — it must recompute the signature from the canonical request and the credential's secret and refuse a mismatch before authorization or dispatch.
Traces: apigateway__iam.xsvc-apigateway-3-iam-wrong-secret-signature-mismatch-rejected.

=== Cause 6 of 6: denial principal attribution and the authorization/route-matching order are wrong ===
AWS: (a) on a resource whose methods are AWS_IAM-protected, authorization is decided before route matching, so a verb the resource does not define is refused 403 with `x-amzn-ErrorType: AccessDeniedException` — not with `MissingAuthenticationTokenException`; (b) a signed, granted GET on a resource that exists but defines no method is 404; (c) the denial message names the principal that actually signed the request — for an assumed role, the session ARN `arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>`.
Emulator: (a) the GET-scoped role's POST returns 403 but with `x-amzn-errortype: MissingAuthenticationTokenException` and body `{"message":"Missing Authentication Token"}`; (b) a signed GET on the methodless parent returns 403 `{"message":"Missing Authentication Token"}` instead of 404; (c) the denial message names the ambient emulator principal `arn:aws:iam::000000000000:user/emulator` rather than the assumed-role session that signed the request.
Why: a client cannot tell an authorization failure from a signing failure from a routing failure — retry and alarm logic keyed on `x-amzn-ErrorType` or on the status/404 distinction behaves wrongly, and audit of "who was denied" names the wrong identity every time.
Fix: the execute-api request pipeline's ordering (authorize the matched-or-unmatched verb under the resource's authorizer before emitting the missing-token refusal; 404 for an existing methodless resource), and the denial message builder's principal resolution, which must use the request's signing principal rather than a default account identity.
Traces: apigateway__iam.authorization-is-decided-before-route-matching-for-an-undefined-verb, apigateway__iam.granted-get-on-the-methodless-parent-resource-is-rejected-not-found, apigateway__iam.xsvc-apigateway-3-iam-resource-policy-not-ip-address-deny-blocked (principal attribution evidence).
