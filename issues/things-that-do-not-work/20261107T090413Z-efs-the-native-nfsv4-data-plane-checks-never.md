# efs: the native NFSv4 data-plane checks never reach a verdict — an EFS mount target reported `available` is never mountable, and both NFS scenarios are killed at the 60s cap (2 causes)

> _Note: this issue was identified against the code base at commit `2d393b0b08d4e0faded23ebb784005e509785021`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMountTarget

## Description
Two net-new root causes in the EFS native (NFS) data plane. Both are grounded in checks that are cut off with "Check timed out after 60.0s" having reached no assertion at all, so the emulator returns no verdict for any claim either check makes. Neither check is covered by an open issue: 20261104T054216Z-efs-mount-target-file-system-refusals-use-emulator.md (mount-target refusal wording / invented CIDR for IpAddress) and 20261029T195311Z-elasticfilesystem-efs-mount-targets-ignore-ec2-subnet-state.md are control-plane findings and carry neither replay key; the three timeout issues of the same SHAPE (20261023T153329Z-efs-lambda-the-shared-efs-mount-check-never.md, 20261024T012650Z-efs-lambda-the-shared-efs-access-point-lambda.md, 20261104T054216Z-ecs-efs-logs-the-shared-efs-fargate-scenario.md) are Lambda/ECS compute flows, not the NFS mount path.

Cause 1 of 2: a mount target the control plane reports as LifeCycleState=available is not actually serving NFSv4 at its own IpAddress, so a single-node mount/write/read round trip never converges. Failing check: efs.efs-nfs-mount-write-read-round-trip.
AWS: Smithy: CreateMountTarget (POST /2015-02-01/mount-targets, 200) returns MountTargetDescription with required MountTargetId (^fsmt-[0-9a-f]{8,40}$), required LifeCycleState, plus IpAddress (^[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}$) and NetworkInterfaceId; DescribeMountTargets (GET /2015-02-01/mount-targets) reports the same description. What `available` MEANS on AWS is the data-plane promise behind those fields: the NFSv4.1 server is reachable at that IpAddress inside the VPC on TCP 2049, so `mount -t nfs4 -o nfsvers=4.1,...  <IpAddress>:/ /mnt/x` succeeds, a file written through the mount is read back byte-for-byte, and the mount is genuinely NFS — `findmnt -no FSTYPE` is exactly `nfs4` and `stat -f -c %T` is `nfs`. Recorded behavior only for the mount itself (no modelled operation describes it); the check's own retry loop allows six mount attempts 10s apart before giving up with exit 32.
Emulator: the check is killed at the suite's 60s cap with no assertion reached, so at least one of its bounded waits never converges: DescribeFileSystems LifeCycleState -> `available` (180s budget), DescribeMountTargets LifeCycleState -> `available` (180s budget), the EC2 instance_running waiter, SSM DescribeInstanceInformation PingStatus -> `Online` (300s budget), or SSM GetCommandInvocation reaching a terminal Status (240s budget) for the AWS-RunShellScript invocation that performs the mount. The emulator answers the EFS control-plane creates and hands back an fsmt- id with an IpAddress, but nothing behind that address ever completes the round trip, and no SSM command result carrying SIM2REAL_CONTENT/SIM2REAL_FSTYPE/SIM2REAL_MAGIC is ever produced.
Why: a client that provisions EFS the documented way — create file system, wait for available, create a mount target, wait for available, mount it from an instance — blocks forever instead of getting a filesystem. Every workload built on EFS (write a file, read it back, confirm the mount is nfs4) is unreachable, and an `available` LifeCycleState on this emulator cannot be trusted as a signal that the filesystem can be used at all.
Fix: the EFS native data plane: the NFSv4.1 listener the mount target's IpAddress must answer on, plus whatever binds a mount-target record in the efs service crate's state to that listener, and the lifecycle transition that is allowed to report `available` only once it answers. The convergence of the surrounding EC2 run/instance-running and SSM Online/GetCommandInvocation path this scenario drives is part of the same gap (see also the open EC2/SSM issue 20261103T200742Z-ec2-ssm-cloudformation-deployed-ec2-ssm-estates-are-unusable-instance.md).
Traces: efs.efs-nfs-mount-write-read-round-trip.

Cause 2 of 2: the two-node, cross-AZ POSIX coherence scenario over the same mount never reaches a verdict, so none of EFS's shared-filesystem POSIX semantics is observable. Failing check: efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.
AWS: recorded behavior only (POSIX/NFSv4 semantics, not a modelled operation). On AWS one EFS file system mounted from two instances in two availability zones behaves as one POSIX filesystem: a barrier file one node creates and fsyncs becomes visible to the peer; close-to-open consistency makes a file a peer wrote, fsynced and closed readable with identical bytes on the next open; concurrent O_APPEND writers never leave a TORN record (records stay whole and checksum-valid, though NFS may legitimately lose an interleaved record, which the check deliberately does not assert); `os.link` gives two paths one inode with st_nlink 2 as observed from the node that created neither, and unlinking one leaves the survivor with the data and st_nlink 1; `os.rename` over a live name is atomic, so a reader only ever sees one of the two whole contents; and `os.rmdir` on a non-empty directory fails with errno ENOTEMPTY and leaves the directory and its occupant untouched, while the same rmdir succeeds once the occupant is removed.
Emulator: the check is killed at the suite's 60s cap with no assertion reached. Its own budgets are far larger (_FS_TIMEOUT_S/_MT_TIMEOUT_S 300s, _SSM_ONLINE_TIMEOUT_S 600s, _SSM_COMMAND_TIMEOUT_S 900s, _NODE_BARRIER_TIMEOUT_S 420s), so the emulator produces none of the intermediate states those waits need: no pair of instances running the per-node script, and no SIM2REAL_JSON payload reporting fstype/fstype_magic, shared_all_valid, nlink_a/nlink_b/same_inode, rename_seen, or rmdir_errno. In particular the ENOTEMPTY refusal and the hard-link identity are never exercised.
Why: a client that treats EFS as a shared POSIX filesystem across nodes — lock/barrier files, atomic rename-into-place deploys, hard links, rmdir refusals — gets no behavior at all from the emulator, and code that depends on those semantics cannot be tested against it. A write-through object store or a per-node local directory would also satisfy the naive round trip, so the absent cross-node coherence is exactly the fidelity that is missing.
Fix: the EFS native data plane again (one shared filesystem backing store served over NFSv4.1 to every mount target of a file system, with POSIX link/rename/rmdir semantics and ENOTEMPTY on a non-empty rmdir), together with the EC2+SSM execution path that lets two instances run a command concurrently against it.
Traces: efs.efs-nfs-two-node-posix-coherence-and-a-nonempty-rmdir-is-rejected.
