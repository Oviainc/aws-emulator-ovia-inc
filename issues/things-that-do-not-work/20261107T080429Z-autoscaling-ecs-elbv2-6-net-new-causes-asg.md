# autoscaling__ecs__elbv2: 6 net-new causes — ASG instances never become target-group targets, no Auto Scaling lifecycle events reach EventBridge, DescribeScalingActivities is a 501 stub, a CFN-created ASG is invisible, and CreateCapacityProvider neither tags nor authorizes against the bound ASG

> _Note: this issue was identified against the code base at commit `620c90c23a321396910fd66a692ef2fcecf33f7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTargetHealth

## Description
Six independent root causes in the Auto Scaling / ECS / ELBv2 surface. Each must be closed before submitting. None of these six carries the replay key of an already-open issue: the closest open ones are 20261104T042502Z-autoscaling-ecs-elbv2-6-net-new-root-causes.md (which covered these two CFN checks in their PREVIOUS failure mode, a ROLLBACK_COMPLETE stack — the stack now deploys and the failure moved to the Auto Scaling read), 20261105T143800Z-autoscaling-ecs-elbv2-2-net-new-causes-an.md (ECS-task targets, not ASG-instance targets), 20261102T091623Z-autoscaling-an-auto-scaling-group-declared-by-a.md and 20261104T042502Z-autoscaling-ec2-elbv2-4-net-new-root-causes.md.

Cause 1 of 6: an Auto Scaling group that carries TargetGroupARNs (or has a target group attached afterwards) never produces an observable ELBv2 target, and target health never converges in either direction. Failing check ids: autoscaling__ecs__elbv2.asg-scale-out-adds-new-targets-to-target-group, autoscaling__ecs__elbv2.autoscaling-group-registers-instances-with-target-group, autoscaling__ecs__elbv2.autoscaling-group-without-elasticloadbalancing-permission-fails-attach, autoscaling__ecs__elbv2.asg-instance-health-status-derived-from-elb-health-check.
  AWS: Auto Scaling registers each instance it launches into every attached target group using its own service-linked role, so DescribeTargetHealth lists the instance id as a target; once a listener forwards to that target group the target transitions to healthy (serving instance) or unhealthy (nothing listening), and with HealthCheckType=ELB DescribeAutoScalingInstances then reports HealthStatus derived from that target health. Recorded behavior only — the Smithy model describes the shapes of DescribeTargetHealth/DescribeAutoScalingInstances, not the reconciliation; the recordings reach these states inside each check's own deadline.
  Emulator: every poll for a registered or state-changed target exhausts the budget — `Error: Check timed out after 60.0s` for the first three, and `TimeoutError: target <instance-id> reaching state unhealthy: the run budget ended first` for the fourth (the instance id there is a per-run value). No target is ever observed registered, healthy or unhealthy.
  Why: registering ASG instances behind a load balancer is the standard rollout gate; a client that waits for `describe-target-health` after creating or scaling an ASG hangs forever, and nothing built on ELB-derived instance health (ELB health-check type, instance replacement) can ever be exercised.
  Fix: the Auto Scaling group reconciliation that propagates launched instances into the attached ELBv2 target groups, and the ELBv2 target-health evaluation / its feedback into Auto Scaling instance HealthStatus — the Auto Scaling and ELBv2 crates' state machines, not the describe serializers.

Cause 2 of 6: Auto Scaling publishes no instance-lifecycle events to EventBridge, so neither the positive delivery nor the negative (pattern-mismatch) comparison can be observed. Failing check ids: autoscaling__ecs__elbv2.autoscaling-instance-launch-event-triggers-target-group-check, autoscaling__ecs__elbv2.autoscaling-event-rule-mismatched-pattern-no-delivery.
  AWS: a scale-out emits an event with source `aws.autoscaling` and detail-type `EC2 Instance Launch Successful` whose detail carries the AutoScalingGroupName; an EventBridge rule matching that pattern delivers it to its SQS target, and a rule matching only `EC2 Instance Terminate Successful` receives nothing until the pattern is corrected. Recorded behavior only (eventing is not in the Smithy model).
  Emulator: both checks exhaust the budget — `Error: Check timed out after 60.0s`; no message ever arrives on the target queue, so the negative case cannot be distinguished from a platform that publishes nothing at all.
  Why: a client that reacts to ASG launch/terminate events (registration hooks, inventory, alarms) never sees one, and a negative-delivery assertion silently 'passes' for the wrong reason.
  Fix: the Auto Scaling lifecycle-event publisher that must emit aws.autoscaling instance launch/terminate events onto the default event bus (the Auto Scaling crate's scaling activity path), plus whatever EventBridge wiring consumes it.

Cause 3 of 6: DescribeScalingActivities is an unimplemented scaffold stub, so no scaling activity can ever be read. Failing check id: autoscaling__ecs__elbv2.asg-target-group-mismatched-vpc-fails-registration.
  AWS: DescribeScalingActivities returns the group's Activities (StatusCode, StatusMessage, Cause) with HTTP 200, including the failure activity recorded when an attached target group cannot accept the launched instances. Smithy: autoscaling DescribeScalingActivities -> ActivitiesType; its modeled errors are InvalidNextToken and ResourceContextNotFound, so NotImplemented is not a modeled outcome.
  Emulator: `botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the DescribeScalingActivities operation: operation DescribeScalingActivities is scaffolded but not implemented in this emulator` — the fixed text is the scaffold sentence, the operation name is the request's.
  Why: scaling activities are the only place Auto Scaling surfaces WHY a launch or a registration failed; with the call refused, no client can diagnose a failed scale-out, and every check that reads activities aborts before reaching its subject.
  Fix: implement the DescribeScalingActivities handler in the autoscaling crate's ops module (it must read the recorded scaling activities from Auto Scaling state), not the client.

Cause 4 of 6: an Auto Scaling group created by a CloudFormation stack is absent from DescribeAutoScalingGroups, so the group cannot be read back by name. Failing check ids: autoscaling__ecs__elbv2.deploy-asg-with-elb-target-group-attachment-cfn, autoscaling__ecs__elbv2.deploy-asg-missing-trust-policy-fails-instance-registration.
  AWS: after a stack containing AWS::AutoScaling::AutoScalingGroup reaches CREATE_COMPLETE, `DescribeAutoScalingGroups(AutoScalingGroupNames=[<name>])` returns exactly that one group with its Instances list; an unknown name returns an empty AutoScalingGroups list rather than the group. Recorded behavior only.
  Emulator: the response's AutoScalingGroups list is EMPTY for the just-created group — the check fails with `IndexError: list index out of range` on `describe_auto_scaling_groups(AutoScalingGroupNames=[asg_name])['AutoScalingGroups'][0]`. Note this is a NEW failure mode: 20261104T042502Z-autoscaling-ecs-elbv2-6-net-new-root-causes.md recorded these two checks failing earlier, at stack ROLLBACK_COMPLETE; the stack now deploys and the group is simply never registered in Auto Scaling state.
  Why: a template-driven estate cannot be driven through the Auto Scaling API at all — waiters, instance inspection and attach/detach all see no group even though CloudFormation reported the resource created.
  Fix: the CloudFormation AWS::AutoScaling::AutoScalingGroup provisioner must register the group in Auto Scaling state (the same class of gap as the open 20261102T091623Z-autoscaling-an-auto-scaling-group-declared-by-a.md and 20261102T104402Z-autoscaling-ec2-kms-an-auto-scaling-group-created.md, neither of which carries these checks' replay keys).

Cause 5 of 6: ECS CreateCapacityProvider does not tag the Auto Scaling group it binds. Failing check id: autoscaling__ecs__elbv2.ecs-capacity-provider-associates-autoscaling-group.
  AWS: creating a capacity provider over an ASG mutates the ASG itself — ECS adds the tag key `AmazonECSManaged` to it (that tag is what scopes the ECS service-linked role's permission to manage the group's scaling), so DescribeAutoScalingGroups then lists `AmazonECSManaged` among the group's Tags. Recorded behavior only; Smithy models CreateCapacityProvider's AutoScalingGroupProvider but not this side effect.
  Emulator: the bound group's Tags contain only the tags the caller created it with — `AssertionError: expected ECS to tag the bound ASG AmazonECSManaged, got tags=[{... 'Key': 'sim2real:managed' ...}]` (the group name and the caller's own tag keys in that list are per-run values; the missing key `AmazonECSManaged` is the requirement).
  Why: anything that identifies ECS-managed groups by that tag (the service-linked role's policy, managed scaling, operator tooling) treats the group as unmanaged, and managed termination protection/scaling can never be authorized.
  Fix: the ECS CreateCapacityProvider handler's ASG-binding step must write the AmazonECSManaged tag through to Auto Scaling state (the ECS crate's capacity-provider op, plus the cross-service tag write).

Cause 6 of 6: ECS CreateCapacityProvider runs no authorization check for the Auto Scaling tagging it performs, so a principal explicitly denied it succeeds. Failing check id: autoscaling__ecs__elbv2.ecs-capacity-provider-without-autoscaling-permission-fails-association.
  AWS: because CreateCapacityProvider must tag the ASG, a caller without `autoscaling:CreateOrUpdateTags` (and UpdateAutoScalingGroup) is refused with HTTP 403, error code `AccessDeniedException` and the sentence "The capacity provider could not be created because you do not have autoscaling:CreateOrUpdateTags permissions to create tags on the Auto Scaling group." — entirely fixed text, no request values — and nothing is created, the ASG is left untagged. Smithy: CreateCapacityProvider lists AccessDeniedException with httpError 403.
  Emulator: the call SUCCEEDS with HTTP 200 and returns the capacity provider ACTIVE — `AssertionError: expected the call to be rejected for lacking autoscaling permissions, but it succeeded and returned {'capacityProvider': {... 'status': 'ACTIVE' ...}, 'ResponseMetadata': {'HTTPStatusCode': 200, ...}}` (the names, ARNs, date and content-length there are per-run values).
  Why: the emulator reports a more permissive authorization model than AWS; least-privilege rollouts that rely on this refusal instead create a capacity provider, and the negative half of every permission-boundary test is unobservable. Related open issue that does NOT carry this replay key: 20261024T081305Z-ecs-is-overly-permissive-ten-validations-authorizations-aws.md.
  Fix: the authorization evaluation in front of the ECS CreateCapacityProvider handler's Auto Scaling tagging step (the ECS crate's capacity-provider op and the shared IAM policy evaluation it must consult).

Traces: the eleven failing check ids listed under the six causes above, all reported by the suite under `### autoscaling__ecs__elbv2`.
