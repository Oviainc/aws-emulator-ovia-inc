# Auto Scaling group-scoped operations refuse an existing group as not found

> _Note: this issue was identified against the code base at commit `a4ef059b31cd49fc5529baf331c68065b4514ad5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SetDesiredCapacity

## Description
TEN net-new causes on the Auto Scaling (awsQuery, api version 2011-01-01) group-scoped paths. They share ONE fault: a group that the same fixture created is not resolvable afterwards, so every group-scoped operation answers the emulator's generic group-lookup refusal (HTTP 400, Code ValidationError, Message 'AutoScalingGroup name not found - AutoScalingGroup: <group-name> not found') where AWS either succeeds or refuses with a DIFFERENT, operation-specific modeled error. Each cause below is a distinct operation/verdict a fixer must close; a fixer must close ALL TEN before submitting.

Cause 1 of 10 - SetDesiredCapacity on a group that exists. AWS: HTTP 200 with an empty SetDesiredCapacityResponse carrying only ResponseMetadata.RequestId. Smithy: SetDesiredCapacity input SetDesiredCapacityType (AutoScalingGroupName, DesiredCapacity required), output Unit; its only modeled client error is ScalingActivityInProgressFault (awsQueryError ScalingActivityInProgress, 400) - a missing group is not a modeled outcome for a group that exists. Emulator: HTTP 400 and NO SetDesiredCapacityResponse element at all, reporting the group-not-found ValidationError. Why: a client scaling a group it just created is told the group does not exist, so every scale-out/scale-in workflow aborts; the group name in the message is a per-run value, the fault is that the group is unresolvable. Fix: the autoscaling group state/index lookup shared by the group-scoped handlers (the group must stay resolvable for the lifetime of the emulator state), then the SetDesiredCapacity handler. Traces: asglf-activity-arch-mismatch#task#9 (cluster of 12 steps across 6 fixtures).

Cause 2 of 10 - UpdateAutoScalingGroup on a group that exists. AWS: HTTP 200, UpdateAutoScalingGroupResponse with ResponseMetadata.RequestId only. Smithy: UpdateAutoScalingGroupType, output Unit, modeled client error only ScalingActivityInProgressFault. Emulator: HTTP 400, response element absent, group-not-found ValidationError. Why: a client cannot change min/max/desired or health-check settings on its own group. Fix: same group lookup, then the UpdateAutoScalingGroup handler. Traces: autoscaling-asgdx-traj-remove-instance-min-size-and-in-use-refusals#task#13 (3 steps).

Cause 3 of 10 - DeleteAutoScalingGroup on a group that exists. AWS: HTTP 200, DeleteAutoScalingGroupResponse with ResponseMetadata.RequestId. Smithy: DeleteAutoScalingGroupType, output Unit, modeled client errors ResourceInUseFault and ScalingActivityInProgressFault. Emulator: HTTP 400 with the group-not-found ValidationError. Why: cleanup paths report a failure and leak the group. Fix: same group lookup, then the DeleteAutoScalingGroup handler. Traces: autoscaling-asgdx-traj-remove-instance-min-size-and-in-use-refusals#task#20 (2 steps).

Cause 4 of 10 - DescribeInstanceRefreshes on a group that exists with no refresh ever started. AWS: HTTP 200 with DescribeInstanceRefreshesResult.InstanceRefreshes present but EMPTY (an empty element, not an absent one) plus ResponseMetadata.RequestId. Smithy: DescribeInstanceRefreshesType.AutoScalingGroupName required; output DescribeInstanceRefreshesAnswer.InstanceRefreshes; only modeled client error InvalidNextToken. Emulator: HTTP 400 and no DescribeInstanceRefreshesResponse at all. Why: a client polling refresh history on a healthy group cannot distinguish 'no refreshes' from 'no group'. Fix: same group lookup, then the DescribeInstanceRefreshes handler must emit the empty list. Traces: autoscaling-asgdx-traj-instance-refresh-refusals-and-in-progress-block#task#6.

Cause 5 of 10 - StartInstanceRefresh on a group that exists. AWS: HTTP 200, StartInstanceRefreshResult.InstanceRefreshId (a server-generated id; its value is per-run and not a requirement) plus ResponseMetadata.RequestId. Smithy: StartInstanceRefreshType.AutoScalingGroupName required, output StartInstanceRefreshAnswer.InstanceRefreshId; modeled client errors InstanceRefreshInProgressFault and LimitExceededFault. Emulator: HTTP 400, no response element. Why: instance-refresh rollouts cannot be started at all. Fix: same group lookup, then the StartInstanceRefresh handler plus the refresh record it must create in autoscaling state. Traces: autoscaling-asgdx-traj-instance-refresh-refusals-and-in-progress-block#task#13.

Cause 6 of 10 - CancelInstanceRefresh when the group exists but has no active refresh: wrong error identity. AWS: HTTP 400, Error.Code ActiveInstanceRefreshNotFound, Message 'No in progress, baking, pending, or cancelling Instance Refresh found for Auto Scaling group <group-name>.' - the sentence is fixed text and the only variable part is the requested AutoScalingGroupName. Smithy: CancelInstanceRefresh models ActiveInstanceRefreshNotFoundFault with awsQueryError code ActiveInstanceRefreshNotFound, httpError 400 - exactly this case. Emulator: HTTP 400 with Code ValidationError and the group-not-found message. Why: a client that distinguishes 'nothing to cancel' (benign, modeled) from 'no such group' sees the wrong code and treats a benign no-op as a configuration error. Fix: the CancelInstanceRefresh handler must resolve the group and then raise the modeled ActiveInstanceRefreshNotFoundFault. Traces: autoscaling-asgdx-traj-instance-refresh-refusals-and-in-progress-block#task#7 (2 steps).

Cause 7 of 10 - StartInstanceRefresh while a refresh is already running: wrong error identity. AWS: HTTP 400, Code InstanceRefreshInProgress, Message exactly 'An Instance Refresh is already in progress and blocks the execution of this Instance Refresh.' (entirely fixed text, nothing substituted). Smithy: StartInstanceRefresh models InstanceRefreshInProgressFault, awsQueryError InstanceRefreshInProgress, httpError 400. Emulator: HTTP 400 with Code ValidationError and the group-not-found message. Why: a client retrying on InstanceRefreshInProgress never sees that code, so it re-issues the start instead of waiting. Fix: the StartInstanceRefresh handler must track the group's active refresh and raise the modeled fault. Traces: autoscaling-asgdx-traj-instance-refresh-refusals-and-in-progress-block#task#14.

Cause 8 of 10 - an instance refresh never reaches a terminal state. AWS: polling DescribeInstanceRefreshes converges on HTTP 200 with InstanceRefreshes.member.Status 'Successful', PercentageComplete 100, Strategy 'Rolling' and the Preferences the start request set (MinHealthyPercentage, InstanceWarmup, AutoRollback, SkipMatching, AlarmSpecification); StartTime/EndTime/InstanceRefreshId are per-run values, the terminal Status is the requirement. Smithy: InstanceRefresh.Status (enum including Successful) on DescribeInstanceRefreshesAnswer. Emulator: the poll was capped at 60s after 13 attempts and every attempt answered HTTP 400 with the group-not-found ValidationError, so Status was never produced. Why: any client waiting for a refresh to finish hangs until its own timeout. Fix: autoscaling refresh state must advance a started refresh to Successful and the describe handler must project it. Traces: autoscaling-asgdx-traj-instance-refresh-refusals-and-in-progress-block#task#15.

Cause 9 of 10 - DeleteAutoScalingGroup on a group that still has instances: wrong error identity. AWS: HTTP 400, Code ResourceInUse, Message exactly 'You cannot delete an AutoScalingGroup while there are instances or pending Spot instance request(s) still in the group.' (entirely fixed text; the group name is NOT echoed). Smithy: DeleteAutoScalingGroup models ResourceInUseFault with awsQueryError code ResourceInUse, httpError 400. Emulator: HTTP 400 with Code ValidationError and the group-not-found message. Why: a client that force-deletes on ResourceInUse (ForceDelete=true) never takes that branch and reports a spurious configuration error instead. Fix: the DeleteAutoScalingGroup handler's in-use check must raise the modeled ResourceInUseFault. Traces: autoscaling-asgdx-traj-remove-instance-min-size-and-in-use-refusals#task#11.

Cause 10 of 10 - instances in a group never become InService, because the group itself is not described. AWS: after a create with DesiredCapacity>0, DescribeAutoScalingGroups returns the group with Instances.member.LifecycleState converging to 'InService'. Smithy: AutoScalingGroup.Instances (list of Instance) and Instance.LifecycleState. Emulator: the poll was capped at 60s after 13 attempts; every answer was HTTP 200 with DescribeAutoScalingGroupsResult.AutoScalingGroups EMPTY, so no instance and no LifecycleState existed to converge. Why: every workflow that waits for capacity to come into service hangs; this is the read-side face of the same missing-group fault. Fix: autoscaling group state must retain the created group and materialise its instances, and DescribeAutoScalingGroups with no name filter must list all groups. Traces: autoscaling-asgdx-traj-remove-instance-min-size-and-in-use-refusals#setup#6 (2 steps).
