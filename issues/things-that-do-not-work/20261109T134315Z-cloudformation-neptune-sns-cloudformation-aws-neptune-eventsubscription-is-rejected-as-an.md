# cloudformation: AWS::Neptune::EventSubscription is rejected as an unrecognized resource type, so neither the Neptune event-subscription round trip nor its SourceType rejection/rollback path can be deployed

> _Note: this issue was identified against the code base at commit `e0227173af353a179b5497df80ad91b1569c5be2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template resource-type registry does not know AWS::Neptune::EventSubscription, so CreateStack refuses at template validation every stack that declares a Neptune event subscription. Both failing checks under this heading die on their first CreateStack, so the entire event-subscription deploy surface — the happy-path round trip and the invalid-SourceType rollback path — is unreachable.

AWS: CloudFormation publishes AWS::Neptune::EventSubscription as a first-class resource type and provisions it through Neptune's CreateEventSubscription (Smithy, com-amazonaws-neptune-amazonrdsv19: SubscriptionName, SnsTopicArn, SourceType, SourceIds, EventCategories, Enabled, Tags). CreateStack therefore ACCEPTS a template that declares it alongside an AWS::SNS::Topic and returns a StackId; the stack reaches CREATE_COMPLETE, the resource's Ref is the subscription name, and the subscription reads back through Neptune DescribeEventSubscriptions with the declared SnsTopicArn, SourceType and Enabled, its ARN tag-readable via ListTagsForResource (the resource's own Tags plus the propagated stack tag). Deleting the stack removes both the subscription and the topic, after which SNS answers error code NotFound with message "Topic does not exist" for the deleted topic ARN. Conversely, when SourceType is not one of the service's accepted values, CloudFormation does NOT refuse at template validation: it accepts the stack, the Subscription resource goes CREATE_FAILED, the stack ends ROLLBACK_COMPLETE, the rollback removes the subscription and the topic, and the CREATE_FAILED StackEvent's ResourceStatusReason is the registry-handler envelope Resource handler returned message: "<service message>" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest). For this class the Neptune message is entirely fixed text apart from the per-run request id and attempt count: "Invalid event source type. Valid types are 'db-instance', 'db-security-group', 'db-parameter-group', 'db-snapshot', 'db-cluster', 'db-cluster-snapshot', 'custom-engine-version', 'db-proxy', 'blue-green-deployment', 'db-shard-group', 'zero-etl' (Service: Neptune, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)", with HandlerErrorCode InvalidRequest.

Emulator: CreateStack is refused synchronously with HTTP 400, error code ValidationError and message "Template format error: Unrecognized resource types: [AWS::Neptune::EventSubscription]" — for BOTH the valid-SourceType template and the invalid-SourceType one, so the type is rejected on its name alone, before any property is looked at. The fixed text is "Template format error: Unrecognized resource types: [" ... "]"; the bracketed list is the set of type names taken from the submitted template. That code and message shape is what AWS emits for a genuinely unknown type — the defect is that this type is classified as unknown at all. Consequently no stack id is minted, no topic or subscription is created, and there is no CREATE_FAILED / ROLLBACK_COMPLETE path and no handler reason to read.

Why: a client wiring Neptune event notifications through IaC cannot create the stack at all. The synchronous ValidationError makes a correct template look malformed, so the caller debugs a template bug that does not exist. And because the resource create is never attempted, Neptune's own SourceType refusal never surfaces as a resource-level failure, so a pipeline that relies on CloudFormation to report and roll back a bad SourceType gets neither a stack nor a handler reason.

Fix: the cloudformation service crate's template resource-type registry consulted during CreateStack validation, and the AWS::Neptune::EventSubscription provisioner it must route to — create/update/delete against Neptune's event-subscription state via CreateEventSubscription/DeleteEventSubscription, Ref = SubscriptionName, tag propagation to the subscription ARN, and the handler-error envelope that turns a Neptune refusal into a CREATE_FAILED resource with HandlerErrorCode InvalidRequest and a ROLLBACK_COMPLETE stack whose rollback also removes the SNS topic. Note: open issue 20261029T174713Z-neptune-parameter-group-and-event-subscription-handlers-skip.md reports gate gaps in the Neptune-side event-subscription handler and does not cover the CloudFormation type registry; open issues 20261109T115129Z-cloudformation-neptune-graph-cloudformation-aws-neptunegraph-graph-and-aws-neptunegraph-graphsnapshot.md and 20261109T115129Z-cloudformation-ec2-neptune-graph-cloudformation-aws-neptunegraph-graph-and-aws-neptunegraph-privategraphendpoint.md report the same class of gap for the AWS::NeptuneGraph::* types and do not cover AWS::Neptune::EventSubscription.
