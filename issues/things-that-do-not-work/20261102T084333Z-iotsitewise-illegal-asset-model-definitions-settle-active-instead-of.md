# Illegal asset-model definitions settle ACTIVE instead of FAILED, and DeleteAssetModel's state gating is inverted at both ends

> _Note: this issue was identified against the code base at commit `86ceea0f39fca17f15a7090d9d9227e10094079b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAssetModel

## Description
IoT SiteWise splits asset-model validation across two planes: a synchronous request-validation plane (400 InvalidRequestException) and an ASYNCHRONOUS plane that accepts the request, reports CREATING/UPDATING/DELETING, and then settles the model at FAILED with assetModelStatus.error = {code: VALIDATION_ERROR, message: <the rule that fired>}. The emulator implements no asynchronous failure path at all - every accepted transition settles ACTIVE - and its DeleteAssetModel gate is inverted on both ends: it refuses synchronously where AWS accepts-then-fails, and accepts where AWS refuses synchronously. Consequence: FAILED is unreachable, so nothing a client does can produce or observe a failed model. This issue bundles 5 causes; all five must be closed.

Cause 1 of 5: a parent metric referencing a CHILD model's raw (non-metric) measurement settles ACTIVE instead of FAILED.
AWS: Smithy: AssetModelStatus{state @required (AssetModelState), error (ErrorDetails)}; ErrorDetails{code @required = ErrorCode enum [VALIDATION_ERROR, INTERNAL_FAILURE], message @required}; Metric documented as consuming properties of type INTEGER or DOUBLE, with a cross-hierarchy variable having to name an aggregated (metric) property of the child. CreateAssetModel ACCEPTS such a definition (the synchronous response reports CREATING - nothing distinguishes it from a legal create) and the model then settles state=FAILED with error.code=VALIDATION_ERROR and a message naming the rule; the recorded message contains the fixed phrase 'non-metric property from a child model'.
Emulator: the create is accepted as CREATING and settles at ACTIVE; assetModelStatus.error is never populated.
Why: the client's own poll (or the asset-model-active waiter) reports success for a rollup that will never compute a value, and the diagnosis AWS puts in assetModelStatus.error is nowhere to be read.
Fix: the asset-model settle/transition machinery (the CreateAssetModel handler's deferred validation and the state it writes) must evaluate cross-hierarchy variable legality at settle time and write state=FAILED with ErrorDetails{VALIDATION_ERROR, message}.
Traces: iotsitewise.sitewise-create-asset-model-settles-failed-on-a-raw-child-measurement-reference.

Cause 2 of 5: a metric reaching OUTSIDE its hierarchy settles ACTIVE instead of FAILED, so no client can ever obtain a FAILED model to list, describe or repair.
AWS: same AssetModelStatus/ErrorDetails grounding. A metric whose variable carries a propertyId that the named hierarchy's child model does not expose is accepted as CREATING and settles FAILED with error.code=VALIDATION_ERROR and the message 'A formula property references a child asset model property that doesn't exist.' - entirely FIXED text including the trailing period, with no variable parts. A FAILED model then REMAINS in ListAssetModels with status.state=FAILED and remains fully describable (properties, hierarchies, assetModelVersion and eTag all present, assetModelStatus.error present), and an UpdateAssetModel that corrects the definition moves it back to ACTIVE.
Emulator: the model settles ACTIVE, so the FAILED state is unreachable; the two checks that observe a FAILED model (still listed + describable, and repaired to ACTIVE by an update) cannot even reach their subject and fail on the precondition 'the deliberately illegal model settled at ACTIVE'.
Why: FAILED is the state a client must handle for every async SiteWise write; with it unreachable, error handling, listing filters and repair flows are all untestable, and a never-armed rollup is reported as healthy.
Fix: the same settle-time validation as cause 1 for hierarchy-scoped property resolution, plus the FAILED model's survival in the listing/describe projections and the ACTIVE transition on a corrective UpdateAssetModel.
Traces: iotsitewise.sitewise-create-asset-model-settles-failed-when-a-metric-reaches-outside-its-hierarchy; iotsitewise.sitewise-a-failed-asset-model-is-still-listed-and-still-describable; iotsitewise.sitewise-update-asset-model-repairs-a-failed-model-to-active.

Cause 3 of 5: an UpdateAssetModel introducing a CYCLICAL hierarchy settles ACTIVE instead of FAILED.
AWS: same AssetModelStatus/ErrorDetails grounding; UpdateAssetModel input assetModelHierarchies (AssetModelHierarchies, each with childAssetModelId). Adding a hierarchy whose childAssetModelId is the model itself is ACCEPTED (not refused), the model goes UPDATING, and settles state=FAILED with error.code=VALIDATION_ERROR and the message 'A cyclical hierarchy definition exists. Asset models can''t contain cyclical hierarchy references.' - entirely fixed text, no variable parts.
Emulator: the update settles at ACTIVE and the self-referencing hierarchy is stored, so the model graph now contains a cycle that every downstream traversal (ListAssociatedAssets, path building, metric resolution) can loop on.
Why: a client gets a cyclic model AWS would have quarantined, and sees no error anywhere.
Fix: the UpdateAssetModel settle path - detect cycles over the childAssetModelId graph at settle time and write FAILED + VALIDATION_ERROR with AWS's fixed sentence.
Traces: iotsitewise.sitewise-update-asset-model-settles-failed-on-a-cyclical-hierarchy.

Cause 4 of 5: DeleteAssetModel on a child still referenced by a parent hierarchy is refused synchronously, where AWS accepts it and settles the model FAILED while the model survives.
AWS: Smithy: DeleteAssetModel output assetModelStatus @required; errors InvalidRequestException (400), ResourceNotFoundException (404), ConflictingOperationException (409). Deleting a child model a parent hierarchy still references is ACCEPTED: the synchronous response reports assetModelStatus.state=DELETING (which is why no synchronous response distinguishes it from a legal delete), and the model then settles state=FAILED with error.code=VALIDATION_ERROR and the message 'Attempted to delete an asset model that is referenced by a hierarchy in a parent asset model. You must remove hierarchy references before you can delete the asset model.' - entirely fixed text, no variable parts. The model is NOT deleted: it stays in ListAssetModels and stays describable under its original name.
Emulator: the call raises InvalidRequestException with the emulator-authored message 'Asset model <childAssetModelId> is referenced by a hierarchy of asset model <parentAssetModelId> when delete was called' - a sentence this service does not produce, carrying two interpolated ids AWS's message does not contain, and on the WRONG plane (synchronous refusal instead of accept-then-FAILED).
Why: a client that deletes in the wrong order must poll the model to learn the delete failed; against the emulator it instead gets an exception at call time, so the correct AWS-shaped code path (accept, poll, read assetModelStatus.error) is never exercised and the opposite code (catch-and-abort) is written instead.
Fix: the DeleteAssetModel handler - accept the delete, return DELETING, and let the settle path write FAILED + VALIDATION_ERROR with AWS's fixed sentence while leaving the model in place.
Traces: iotsitewise.sitewise-delete-asset-model-settles-failed-and-the-model-survives-under-a-parent.

Cause 5 of 5: DeleteAssetModel on a model still CREATING is accepted, where AWS refuses it synchronously.
AWS: Smithy: DeleteAssetModel error InvalidRequestException httpError 400, member message. A model that has not yet left CREATING may not be modified: the delete is refused 400 with the message 'This asset model must be ACTIVE or FAILED before you can modify it. AssetModelID: <assetModelId> AssetModelName: <assetModelName> AssetModelState: <state>' - fixed text 'This asset model must be ACTIVE or FAILED before you can modify it. AssetModelID: ', ' AssetModelName: ', ' AssetModelState: '; variable parts: the model's id and name and its current state from the emulator's own state (CREATING here). The model's in-flight transition is untouched (it must not move to DELETING) and the identical delete succeeds once the model settles ACTIVE.
Emulator: answers HTTP 202 with {assetModelId, assetModelStatus:{state: DELETING}} - it accepts the delete mid-create and moves the model to DELETING.
Why: this is the busy-state guard for every asset-model write; without it a delete racing a create tears down a half-created model instead of being refused, and a client never sees the state-gated refusal it must retry on.
Fix: the DeleteAssetModel handler's precondition - gate on the model's current state (only ACTIVE or FAILED may be modified) and refuse with the service's state message before any transition is written. Note causes 4 and 5 are opposite ends of the SAME gate: a referenced child must be accepted, a CREATING model must be refused.
Traces: iotsitewise.sitewise-delete-asset-model-is-refused-synchronously-while-still-creating.
