# inspector2: DeleteFilter is not idempotent for an already-deleted filter, and BatchGetAccountStatus reports a real status for a non-member account (2 causes)

> _Note: this issue was identified against the code base at commit `221dd3602e5d0e66d71e70da1fb8509b07c948c5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteFilter

## Description
TWO causes, both in inspector2 state/authorization logic rather than in serialization. Both are over-/under-permissive state decisions: one refuses a call AWS accepts, the other accepts an account AWS refuses per-entry.

Cause 1 of 2: DeleteFilter refuses a second delete of a filter the caller already deleted, instead of succeeding idempotently.
AWS: Smithy: DeleteFilter, POST /filters/delete, input {arn (required, FilterArn @length 1..128)}, output DeleteFilterResponse{arn (required, FilterArn)}; ResourceNotFoundException (httpError 404) is modeled but, per recorded behavior, is not used for an already-deleted filter the caller owns: deleting the same ARN again answers 200 and ECHOES the requested arn back in the response. The recorded concurrency run confirms it (5/5 real-AWS runs of two simultaneous DeleteFilter calls on one ARN returned ["ok", "ok"], never ResourceNotFoundException), so the idempotence holds both sequentially and under concurrency; the only `arn` value in the response is the one from the request. A syntactically INVALID arn is still refused, with 400 ValidationException and message "Invalid Filter Arn <arn>", whose fixed text is "Invalid Filter Arn " and whose variable part is the caller-supplied arn verbatim.
Emulator: the first DeleteFilter succeeds; the second call on the same ARN is refused 404 ResourceNotFoundException with message "The filter <filter-arn> does not exist." Under two concurrent deletes exactly one wins and the other gets ResourceNotFoundException (observed results ['ok', 'ResourceNotFoundException']).
Why: every client retry of DeleteFilter — an SDK-level retry after a timeout, a cleanup path that deletes defensively, or two workers racing on the same filter — turns a successful delete into a hard 404 error. Teardown code that treats ResourceNotFoundException as fatal breaks, and callers cannot rely on the documented echo of `arn` in the response.
Fix: the DeleteFilter handler's resolve step and the filter state it deletes from (services/service-com-amazonaws-inspector2-inspector2/src/ops/delete_filter.rs): a well-formed FilterArn in the caller's own namespace that resolves to nothing must answer 200 echoing the requested arn, and only a malformed arn may be refused (400 ValidationException). The deletion must be a single idempotent state transition so concurrent callers both observe success.

Cause 2 of 2: BatchGetAccountStatus returns a fabricated DISABLED status for an accountId that is not a member account, instead of reporting it in failedAccounts.
AWS: Smithy: BatchGetAccountStatus, POST /status/batch/get, input {accountIds (AccountIdSet, @length 0..100, uniqueItems)}, output {accounts (required, AccountStateList) and failedAccounts (FailedAccountList)}. FailedAccount declares accountId, errorCode (required, ErrorCode enum — ACCESS_DENIED is one of its values) and errorMessage (required, NonEmptyString) — the shape exists precisely so a per-account failure is reported per entry rather than as a whole-request error. Recorded behavior: a syntactically valid 12-digit account id that is not a member of the caller's organization does NOT appear in `accounts`; it appears in `failedAccounts` with errorCode "ACCESS_DENIED" and errorMessage "Invoking account does not have access to this account" (fixed text; the variable part of the entry is the accountId, echoed from the request). The caller's own account in the same request still succeeds in `accounts`.
Emulator: answers HTTP 200 with BOTH ids in `accounts` — the non-member id is given a complete, invented state ({'accountId': '<non-member id>', 'state': {'status': 'DISABLED'}, 'resourceState': {ec2/ecr/lambda/lambdaCode/codeRepository all 'DISABLED'}}) — and emits no `failedAccounts` entry at all.
Why: this is an authorization leak in the overly-permissive direction: a caller is told it can read the Inspector2 posture of an arbitrary account it has no access to, and is handed a plausible-looking DISABLED status for it. Multi-account tooling that pages account posture will treat non-member/unauthorized accounts as genuinely disabled members, report them as unprotected, and never surface the ACCESS_DENIED that AWS reports; nothing exercises the failedAccounts branch of the client.
Fix: the BatchGetAccountStatus handler's per-account membership/authorization decision and its response assembly (services/service-com-amazonaws-inspector2-inspector2/src/ops/batch_get_account_status.rs): for each requested accountId, only accounts the caller may read (its own account, and members of the organization it administers) go into `accounts`; every other id goes into `failedAccounts` with errorCode ACCESS_DENIED and AWS's errorMessage, and must never be given a synthesized state.
