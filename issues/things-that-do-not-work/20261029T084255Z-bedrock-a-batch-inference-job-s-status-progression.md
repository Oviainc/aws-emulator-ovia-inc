# bedrock: a batch inference job's status progression is gated on the NUMBER of polls, not elapsed time — GetModelInvocationJob advances at most one stage per call, so a job never reaches a terminal status for a coarse poller and no output is ever written

> _Note: this issue was identified against the code base at commit `ede2de3f7102f867619bb62880127888c08c3e6a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetModelInvocationJob

## Description
Cause 1 of 1: the batch inference job lifecycle (CreateModelInvocationJob -> GetModelInvocationJob) only moves forward when a caller READS the job, one stage per read, and the next stage's due instant is re-armed from the instant of that read. Elapsed wall-clock time alone never carries a job forward, so the number of GetModelInvocationJob calls — not the time since submission — decides whether the job ever finishes. Failing check: bedrock.e2e-batch-inference-job-produces-output.

AWS: ModelInvocationJobStatus is documented as the progression `Submitted` ('This job has been submitted to a queue for validation') -> `Validating` -> `Scheduled` -> `InProgress` ('this job has begun. You can start viewing the results in the output S3 location') -> a terminal status (`Completed` | `PartiallyCompleted` | `Failed` | `Stopped` | `Expired`) (Smithy: com.amazonaws.bedrock#ModelInvocationJobStatus, as reported by GetModelInvocationJob$status; GetModelInvocationJob also reports totalRecordCount / processedRecordCount / successRecordCount / errorRecordCount and endTime). That progression is driven by the SERVICE as the job runs: it happens whether or not anybody polls, and at what interval. A client that submits a job and then issues a SINGLE GetModelInvocationJob after enough time has passed is answered with the terminal status directly — intermediate statuses are observable, never mandatory waypoints a caller must poll through. Having reached `Completed`, the records are written under the outputDataConfig s3Uri prefix, so a ListObjectsV2 on that prefix returns non-empty objects, and successRecordCount equals the record count of the input .jsonl object.

Emulator: the submission arms the whole clock, but `ModelInvocationJobRecord::settle` materialises AT MOST ONE stage per call and then `return`s, and `owe_next_stage` re-counts the following stage's due instant from `now` — the instant of the read that just materialised a stage — rather than from the submission. The consequence is that a job needs four separate GetModelInvocationJob (or ListModelInvocationJobs) calls, spaced at least one span apart, to reach its terminal status, and the elapsed time between calls buys nothing beyond a single stage. In the replay the check submits the job, then polls GetModelInvocationJob with a 60-second interval (the interval a client uses for a job AWS documents as long-running): the first poll reports `Validating`, and because each later poll can only advance one more stage, the terminal status is unreachable inside the check's budget — the check is killed at the 60s harness limit with the job still non-terminal. Nothing therefore ever runs `run_batch_inference`, so no result records are stored under the `output/` prefix and successRecordCount stays 0.

Why: a client that polls a batch inference job at any realistic interval, or that sleeps once and polls once, hangs forever on a non-terminal status and never finds its output in S3 — the ordinary 'submit, wait, read result' shape of every batch-inference client. Worse, the behavior is non-deterministic from the client's point of view: the same job finishes quickly for a tight polling loop and never finishes for a patient one, which is the opposite of the real service, where a tight loop merely observes more intermediate statuses. Every downstream assertion a user can make (status == Completed, successRecordCount == totalRecordCount, endTime present, output objects present) is unreachable.

Fix: the batch inference job clock in the bedrock control-plane state — `ModelInvocationJobRecord::settle` and `owe_next_stage` — must settle EVERY stage whose armed instant has already elapsed on a single read (a loop, not an early `return` after one stage), and must keep each stage's due instant on the submission's own timeline (`ModelInvocationJobClock::armed_at`) instead of re-arming it from the instant of the observing call. The due run (`due_run` / `run_batch_inference`, taken by `ops/get_model_invocation_job.rs` and `ops/list_model_invocation_jobs.rs`) must then be performed as part of the same read that carries the job to `InProgress`-or-later, so the counts and the objects under the outputDataConfig prefix are there for the read that first reports a terminal status.

Traces: bedrock.e2e-batch-inference-job-produces-output (reported as 'Check timed out after 60.0s' — the poll loop never sees a terminal status). Code citations for the fixer: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/state.rs lines 2349-2426 (`settle` returning after one stage, `owe_next_stage` re-counting from `now`) and lines 2007-2039 (the spans), and services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/get_model_invocation_job.rs lines 242-269 (the single settle + due run per read).

## Evidence
Expected (AWS): after CreateModelInvocationJob returns a jobArn, a client polling GetModelInvocationJob — at ANY interval, including a single call after the job has had time to run — eventually reads status in {Completed, PartiallyCompleted, Failed, Stopped, Expired}; for a valid 100-record .jsonl input the terminal status is `Completed`, successRecordCount == 100 == totalRecordCount, endTime is set, and ListObjectsV2 on the outputDataConfig prefix returns at least one object of non-zero size.

Actual (emulator): the first GetModelInvocationJob reports `Validating`; each subsequent call advances exactly one stage and re-arms the next stage from that call's instant, so with a 60s poll interval the job is still non-terminal after the check's whole budget and the check is killed ('Error: Check timed out after 60.0s'). successRecordCount stays 0 and the output prefix stays empty because the job's run is only performed once a read has carried it to the begun state.

Mechanism in the emulator source: `ModelInvocationJobRecord::settle` (state.rs:2349) tests `validating_due_at`, then unconditionally `return`s — it never falls through to `scheduled_due_at` / `in_progress_due_at` / `completed_due_at` in the same call — and `owe_next_stage` (state.rs:2413) sets the next due instant to `now + <span>`, discarding the submission-relative instants `ModelInvocationJobClock::armed_at` (state.rs:2071) computed. Spans are 500ms/500ms/500ms/3s, so time is not the limiting factor: poll COUNT is.

## Steps to Reproduce
1. Put a valid 100-record batch-inference .jsonl object in an S3 bucket in the emulator and create an IAM role trusting bedrock.amazonaws.com.
2. bedrock CreateModelInvocationJob with modelId=meta.llama3-1-8b-instruct-v1:0, inputDataConfig.s3InputDataConfig.s3Uri pointing at that object and outputDataConfig.s3OutputDataConfig.s3Uri pointing at an `output/` prefix in the same bucket; keep the returned jobArn.
3. Sleep 30 seconds (far longer than every span the emulator arms), then call GetModelInvocationJob(jobIdentifier=<jobArn>) exactly ONCE. Observe status == `Validating` — a single stage — rather than the terminal status the elapsed time is owed.
4. Continue polling at a 60-second interval, as a client of a long-running job does. Each poll advances exactly one stage, so the job stays non-terminal for the whole of the check's 60s budget; the check bedrock.e2e-batch-inference-job-produces-output is killed by the harness timeout.
5. ListObjectsV2(Bucket=<bucket>, Prefix="output/") returns no non-zero-size objects, and GetModelInvocationJob reports successRecordCount 0, because the job's run is only performed by the read that carries it into the begun state.
