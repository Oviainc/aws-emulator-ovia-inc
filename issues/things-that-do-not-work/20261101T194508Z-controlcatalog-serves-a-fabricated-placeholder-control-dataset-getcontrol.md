# ControlCatalog serves a fabricated placeholder control dataset: GetControl 404s on real control ARNs and ListControls returns invented controls

> _Note: this issue was identified against the code base at commit `7f3f2187a2100f71560b62bea9ff35bd72db691b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetControl

## Description
The emulator's control dataset is not the AWS Control Catalog: it holds a small set of invented controls whose ARNs, names, descriptions, timestamps and parameter summaries are emulator-authored, so the catalog read path answers with content AWS never serves and the catalog lookup path cannot find any real control ARN. THREE divergence clusters, numbered as causes below; ALL THREE must be closed and re-replayed before this issue is done.

Related open issues do NOT cover any cause below: 20261030T021409Z-controlcatalog-listcommoncontrols-returns-an-empty-commoncontrols-list-for-every--r2.md (ListCommonControls empty), 20261029T195408Z-controlcatalog-listdomains-and-listobjectives-return-empty-catalog-taxonomy-lists.md, 20261029T195408Z-controlcatalog-listcontrolmappings-returns-an-empty-controlmappings-list-for-every.md (other list operations returning EMPTY lists), 20261029T152442Z-controlcatalog-getcontrol-validation.md (ARN partition parsing) and 20261029T183447Z-controlcatalog-getcontrol-ignores-caller-authorization-no-accessdeniedexception-and.md (authorization and refusal wording). The ListCommonControls issue even notes in passing that "ListControls ... emits placeholder entries"; that defect is filed here for the first time.

Cause 1 of 3: GetControl answers 404 for every control ARN in the recorded catalog (fixture controlcatalog-catalog-get-control, step task#1; 20 recorded steps in this cluster, task#1..task#20).
  AWS: Smithy GetControl (POST /get-control, @readonly, http code 200). Input ControlArn is @required, @length 34..2048, @pattern ^arn:(aws(?:[-a-z]*)?):(controlcatalog|controltower):[a-zA-Z0-9-]*::control/[0-9a-zA-Z_\-]+$. For an ARN that names a control in the catalog, AWS returns 200 and a GetControlResponse carrying the @required members Arn, Name, Description, Behavior and RegionConfiguration plus Aliases, Severity, Implementation{Type,Identifier}, ParameterRequirementSummary, Parameters, CreateTime, GovernedResources and GovernedProviders. Every control ARN the corpus requests is a catalog ARN, so the recorded response is a 200 success. ResourceNotFoundException (errorKind client, @httpError 404) is modeled, but it is the answer for an ARN that is NOT in the catalog — neither the model nor the recording states its message text, so no message is asserted here.
  Emulator: status 200 -> 404, and not one GetControlResponse member is serialized ($.Aliases, $.Arn, $.Behavior, $.CreateTime, $.Description, $.GovernedProviders, $.GovernedResources, $.Implementation, $.Name, $.ParameterRequirementSummary, $.Parameters, $.RegionConfiguration, $.Severity all reported missing, got None). Hypothesis: the lookup itself works but only over the emulator's invented ARN space — the behavioral evidence in 20261029T183447Z-... shows GetControl answering 200 for 'arn:aws:controlcatalog:::control/09f38e820aed77abaa51300ac', an emulator-minted id — while every real catalog ARN (e.g. control/1038h7d21e6g8i10g6v3xsssi) is absent from the seed and therefore not found.
  Why: a client that discovers a control ARN (from ListControls, from a Control Tower enabled-control record, or from its own configuration) and then reads the control's detail gets a hard not-found for every genuine AWS control. The whole discover-then-describe flow is unusable, and a caller cannot tell a mis-seeded emulator from a genuinely deleted control.
  Fix: the control-catalog seed state the service reads (services/service-com-amazonaws-controlcatalog-controlcatalog/src/state.rs) and the lookup in the GetControl handler (src/ops/get_control.rs), which must resolve the catalog's real control ARNs and project the full response.

Cause 2 of 3: ListControls returns an invented control in place of the catalog's control for the same alias (fixture controlcatalog-catalog-list-controls-aws-config-configrule, step task#1; 21 recorded steps, also spanning fixture controlcatalog-catalog-list-controls-aws-securityhub-securitycontrol).
  AWS: Smithy ListControls (POST /list-controls, @readonly, paginated inputToken/outputToken NextToken, pageSize MaxResults @range 1..100, items Controls; output member Controls is @required). Each ControlSummary carries the catalog's own identity for the control: the control ARN, its Aliases, the catalog's Name and Description text, Behavior, Severity, ParameterRequirementSummary, Implementation{Type,Identifier}, CreateTime, GovernedResources and GovernedProviders. The alias CONFIG.ACCOUNT.DT.1 belongs to control/4x11tie7h25sws4g7ilakhcb7, name 'Rule checks whether AWS account is part of AWS Organizations', ParameterRequirementSummary OPTIONAL, Severity HIGH, implementation AWS::Config::ConfigRule / ACCOUNT_PART_OF_ORGANIZATIONS.
  Emulator: status matches (200), but that summary is reported missing and an emulator-authored one is reported extra under the same alias: ARN control/0d316cbc7af46ffa3560a5c2b (an id of the emulator's own minting, not the catalog's), a paraphrased Name ('Checks whether an Amazon Web Services account is part of an organization') and Description, ParameterRequirementSummary NONE instead of OPTIONAL, and a CreateTime that is not the control's catalog creation time. Behavior, Severity, Implementation and GovernedProviders/GovernedResources do carry over, so the summary is shaped correctly and only its identity and metadata are fabricated.
  Why: the ARNs a client harvests here do not exist in AWS, so any ARN captured against the emulator is invalid against the real service (and, per cause 1, is the only thing GetControl can even resolve). ParameterRequirementSummary NONE where AWS says OPTIONAL also misleads a client into believing the control takes no parameters.
  Fix: the same seed state, plus the summary projection in the ListControls handler (src/ops/list_controls.rs) — the ARN and the Name/Description/ParameterRequirementSummary/CreateTime must come from the catalog record, not be synthesized.

Cause 3 of 3: ListControls pages do not contain the catalog's controls at all (fixture controlcatalog-catalog-list-controls-aws-config-configrule, step task#2; the largest cluster, 1285 recorded steps).
  AWS: as cause 2 — 200 with the @required Controls list paged by MaxResults/NextToken, the entries being the catalog's controls in the service's own order. The first expected entry of this page is control/6yl9xxuky13vzaxi3n6lm73k5, alias CONFIG.ACM-PCA.DT.2, name 'Checks if AWS Private CA certificate authorities have tags', Behavior DETECTIVE, Severity LOW, ParameterRequirementSummary OPTIONAL, implementation AWS::Config::ConfigRule / ACMPCA_CERTIFICATE_AUTHORITY_TAGGED, GovernedResources ['AWS::ACMPCA::CertificateAuthority'].
  Emulator: 200, but $.Controls[0] is missing (got None) on essentially every page of the fixture — the placeholder dataset is far smaller than the catalog and shares neither its contents nor its ordering, so paging through ListControls never yields the recorded controls.
  Why: a client enumerating the catalog (to build a picker, to reconcile its own control inventory, or to drive Control Tower enablement) sees a handful of invented controls instead of the catalog, and pagination over the real catalog size is never exercised.
  Fix: the control-catalog seed state (src/state.rs) must carry the catalog's controls, and the ListControls handler (src/ops/list_controls.rs) must page them in catalog order through the shared pagination seam.

Traces: controlcatalog-catalog-get-control#task#1 (cause 1, 20 steps); controlcatalog-catalog-list-controls-aws-config-configrule#task#1 (cause 2, 21 steps, incl. controlcatalog-catalog-list-controls-aws-securityhub-securitycontrol#task#66); controlcatalog-catalog-list-controls-aws-config-configrule#task#2 (cause 3, 1285 steps).
