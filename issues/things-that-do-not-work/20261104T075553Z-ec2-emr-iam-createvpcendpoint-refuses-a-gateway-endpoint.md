# ec2__emr__iam: CreateVpcEndpoint refuses a gateway endpoint that names RouteTableIds with 501 NotImplemented, and a CFN-deployed private estate exposes no route table for its subnet — every EMR private-network check is blocked

> _Note: this issue was identified against the code base at commit `6e4fa4ae0561cad796d7088ff8894510cc385391`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateVpcEndpoint

## Description
Two net-new root causes in the ec2__emr__iam group, both on the EC2 route-table / gateway-endpoint path that every multi-primary EMR check builds its private network with. All five failing checks of this group are grounded here; none is marked ALREADY FILED or OWNED in the replay report.

Cause 1 of 2: CreateVpcEndpoint answers 501 NotImplemented whenever the request carries RouteTableIds (a gateway endpoint).
AWS: Smithy com.amazonaws.ec2#CreateVpcEndpoint (model services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json) accepts VpcId (required), ServiceName, VpcEndpointType, RouteTableIds (list, xmlName RouteTableId — documented as "(Gateway endpoint) The route table IDs"), PolicyDocument, TagSpecifications, and returns CreateVpcEndpointResult{VpcEndpoint, ClientToken}; the operation models NO errors, so there is no modelled refusal for this member at all. AWS answers HTTP 200 with a vpcEndpoint whose vpcEndpointType is Gateway, whose routeTableIdSet echoes the ids the request named, and whose state moves pending -> available; each route table named gains a route whose DestinationPrefixListId is the endpoint service's prefix list and whose GatewayId is the new vpce- id. (A route table id that does not exist is InvalidRouteTableId.NotFound, not a 501.)
Emulator: HTTP 501, error code NotImplemented, message "operation CreateVpcEndpoint with route table associations is scaffolded but not implemented in this emulator" — fixed text "operation " + <operation name> + " ... is scaffolded but not implemented in this emulator", with the operation name and the qualifier "with route table associations" supplied by the handler, no part of it taken from the request. The guard is explicit in services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs (the route_table_ids non-empty branch returning Scaffolded::not_implemented), and its stated premise — "a VPC route table is a resource of its own and this crate holds no store of them (CreateRouteTable is still a scaffold)" — is stale: CreateRouteTable, AssociateRouteTable and DescribeRouteTables in the same crate are all IMPLEMENTED against a route_tables store. The same file also stores route_table_ids as an empty Vec for gateway endpoints that are accepted.
Why: a client building the standard private-subnet estate (S3 gateway endpoint attached to the subnet's route table) cannot create the endpoint at all, and on the error class: a 501/NotImplemented is not a client error, so SDKs and CDK/CFN providers surface it as an emulator gap rather than one of AWS's modelled outcomes, and no retry or validation path recovers. Every EMR cluster check that needs the private network dies before it reaches RunJobFlow, so EMR's own behaviour (service-role validation, unknown-role VALIDATION_ERROR, placement groups) is never exercised.
Fix: the CreateVpcEndpoint handler (services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs) — the gateway path must create the endpoint, associate it with each named, existing route table of the same VPC, add the prefix-list route to each of those tables, and report routeTableIds as stored; an unknown or cross-VPC route table id must be refused with EC2's modelled not-found error rather than a 501.
Traces: ec2__emr__iam.cluster-in-nonexistent-subnet-rejected, ec2__emr__iam.multi-master-nodes-spread-in-emr-placement-group, ec2__emr__iam.service-role-without-placement-group-policy-rejected, ec2__emr__iam.unknown-service-role-cluster-rejected (all four fail with the 501 above while building the private network).

Cause 2 of 2: after a CloudFormation stack declaring AWS::EC2::VPC, AWS::EC2::Subnet, AWS::EC2::RouteTable, AWS::EC2::SubnetRouteTableAssociation and a gateway AWS::EC2::VPCEndpoint is deployed, EC2 reports no route table associated with the stack's subnet.
AWS: an explicit SubnetRouteTableAssociation makes the subnet's association explicit, and DescribeRouteTables with Filters=[{Name: "association.subnet-id", Values: [<subnet>]}] returns that route table, carrying the VPC-local route plus exactly one route out of the VPC — the S3 gateway endpoint's route (DestinationPrefixListId set, GatewayId the vpce- id). The emulator's own DescribeRouteTables documents and implements the association.subnet-id filter (services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_route_tables.rs).
Emulator: the filtered DescribeRouteTables answers 200 with an EMPTY RouteTables list (the check's assertion reports "the subnet's only route out of the VPC should be the S3 gateway endpoint, got []", where [] is the whole RouteTables list), even though DescribeStackResources reports all five declared resource types for the stack. So neither the explicit subnet association nor the endpoint route is observable. Hypothesis: the CloudFormation providers for AWS::EC2::RouteTable / AWS::EC2::SubnetRouteTableAssociation / AWS::EC2::VPCEndpoint do not create the corresponding EC2 state (or the VPCEndpoint resource hits Cause 1 and the estate is rolled back), so the route-table store holds nothing for that subnet.
Why: a client that deploys the canonical private-subnet-plus-gateway-endpoint estate and then reads it back through EC2 sees a subnet with no explicit route table and no egress route, so any workload placed in it (here EMR) is configured against a network that the emulator does not actually hold. Note this cause may be downstream of Cause 1; it is called out separately so it is re-replayed and confirmed rather than assumed fixed.
Fix: the CloudFormation EC2 resource providers for RouteTable / SubnetRouteTableAssociation / VPCEndpoint (they must write the same EC2 state the corresponding EC2 operations write), together with the Cause 1 handler change.
Traces: ec2__emr__iam.e2e-create-emr-cluster-multi-master-lifecycle (phase 1/6 deploy).
