# MediaPackage HLS ingest endpoint: unauthenticated PUT returns no WWW-Authenticate Digest challenge, so the published ingest URL can never be authenticated

> _Note: this issue was identified against the code base at commit `54f388b9499ec3dd7b64bc533fb6b62161b4e3d7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One root cause (Cause 1 of 1), grounded in the single surviving failing check mediapackage.native-ingest-endpoint-requires-basic-auth.

NOTE ON OVERLAP: the open issue 20261022T213438Z-mediapackage-data-plane-hls-ingest-url-is-unrouted.md describes a comparable ingest-plane gap (its "Cause 2 of 4") and even lists this check id, but the replay report did NOT mark this check as OWNED by it or as ALREADY FILED, so it is filed here as a live, still-failing divergence. A fixer closing that issue must also re-replay the check id in trace_ids; if the two are the same work item, resolve them together.

Cause 1 of 1: a PUT to the HlsIngest ingest URL that CreateChannel publishes does not answer a 401 carrying a WWW-Authenticate Digest challenge, so no Digest round-trip is possible against the channel's generated credentials.
AWS: recorded behavior only — the ingest data plane is not modelled in Smithy. Smithy (services/service-com-amazonaws-mediapackage-mediapackage/smithy-model/com-amazonaws-mediapackage-mediapackage.json) only models the control-plane shape: CreateChannel POST /channels -> CreateChannelResponse.HlsIngest (jsonName "hlsIngest"), whose IngestEndpoints entries carry Id, Url, Username and Password; the wire protocol of that Url is not modelled. The recording shows the listener behind that Url challenging an unauthenticated PUT with HTTP 401 and a `WWW-Authenticate: Digest realm="WebDAV", ..., algorithm=MD5, qop="auth"` header (RFC 2617); the generated Username/Password then authenticate over Digest (non-401), and a Digest response computed with a wrong password is refused 401. Fixed text of the challenge: the scheme token `Digest`, `realm="WebDAV"`, `algorithm=MD5` and `qop="auth"`. Variable parts: `nonce` and `opaque` are per-response values generated by the listener and are NOT requirements; the realm value and scheme are. The requirement is: a 401 whose WWW-Authenticate advertises Digest with realm="WebDAV", credentials taken from the channel record the control plane created.
Emulator: the unauthenticated PUT comes back with NO WWW-Authenticate header at all — the check fails at `assert challenge, "expected a WWW-Authenticate challenge on the 401 probe"` in _digest_put, immediately after the no-credentials probe. Because the challenge is absent, the check can never compute a Digest response, so neither the positive control (correct credentials must not be 401) nor the wrong-password 401 arm is reachable. This is consistent with the published ingest Url not being routed to any credential-gating listener.
Why: a Digest client is driven entirely by the challenge. With no WWW-Authenticate on the 401, an encoder or any client that pushes to the Url CreateChannel handed it cannot derive an Authorization header and can never ingest content; it also cannot distinguish a credential-gated ingest endpoint from a closed/nonexistent one, which is the opposite branch in every real pusher.
Fix: the ingest data-plane listener for the published HlsIngest Url — the channel's ingest routing/handler plus its authentication layer, and the URL the CreateChannel handler publishes must point at it. It must emit 401 with `WWW-Authenticate: Digest realm="WebDAV", algorithm=MD5, qop="auth"` for a PUT with no Authorization header, validate the channel-record Username/Password over Digest, and answer 401 for a Digest response computed with a wrong password.
