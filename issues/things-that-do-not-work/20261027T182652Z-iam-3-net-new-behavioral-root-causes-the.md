# iam: 3 net-new behavioral root causes — the request authorizer still builds an EMPTY condition context (ABAC StringEquals on iam:ResourceTag vs ${aws:PrincipalTag} can never grant), policy variables such as ${aws:username} in a Resource element are never expanded per caller, and iam:GetUser reaches no authorization gate so a sibling user's GetUser is served outside the statement's Resource

## Description
THREE net-new root causes (Cause 1 of 3 .. Cause 3 of 3) in the bootstrapped `iam` service, each grounded in a failing behavioral check that the replay report marks neither ALREADY FILED nor OWNED. A fixer must close all three before submitting; closing any one of them leaves the other two checks still failing.

All three are the OPPOSITE-DIRECTION failure of divergences that were previously recorded against this service, which is why the replay keys no longer match any open issue: the authorization gate has since been wired into `iam:ListAccessKeys` (services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs now declares `LIST_ACCESS_KEYS`), so the two checks that used to fail because a call SUCCEEDED now fail because the same call is permanently REFUSED. The related open issues are named per cause below; none of them carries these replay keys and none of them can be closed by the work this issue describes without the other half also being done.

=== Cause 1 of 3: the IAM request authorizer builds its request with an EMPTY condition context and never expands a policy variable inside a Condition VALUE, so an ABAC statement comparing iam:ResourceTag/<key> to ${aws:PrincipalTag/<key>} can never grant a real signed call ===

AWS: IAM itself populates the request context and evaluates a statement's Condition against it — `iam:ResourceTag/<key>` from the tags stored on the TARGET IAM entity, `aws:PrincipalTag/<key>` from the SIGNING principal's stored tags — and a policy variable written as a Condition VALUE (`"iam:ResourceTag/project": "${aws:PrincipalTag/project}"`) is substituted from that same context at evaluation time, not at write time (IAM User Guide, "IAM policy elements: variables and tags"; "Determining whether a request is allowed or denied within an account"). So an identity policy containing {Allow iam:ListAccessKeys on [<match user arn>, <sibling arn>], Condition StringEquals {"iam:ResourceTag/project": "${aws:PrincipalTag/project}"}} permits the caller's real signed `ListAccessKeys(UserName=<match user>)` when the target's `project` tag equals the caller's `project` tag, and refuses `ListAccessKeys(UserName=<sibling>)` where the values differ — both target ARNs are named in the same Resource element, so the Condition is the only thing separating the two requests. Re-tagging the CALLER swaps both outcomes without a single request byte changing. Smithy com.amazonaws.iam#ListAccessKeys declares only NoSuchEntityException (httpError 404, awsQueryError code `NoSuchEntity`) and ServiceFailureException (500), so the authorization refusal is the service-common `AccessDenied` at HTTP 403 — recorded behavior rather than modeled. The refusal message is the one `authorize_named` already words (`User: <principal arn> is not authorized to perform: <action> on resource: <resource as the request named it> because no identity-based policy allows the <action> action` followed by the authorization-details pointer); its fixed text is everything outside those slots, and the variable parts are the caller ARN, the action, the resource naming from the request and the per-request authorization id.

Emulator: `iam:ListAccessKeys` IS gated now, but every conditioned Allow is undecidable, so the gate refuses the MATCHING combination too. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs::authorize_named line 269 builds `let request = iam::Request::new(action, resource, &principals);` — the constructor whose context is `&[]` — and `Request::with_context` appears nowhere in the file. services/common/src/iam_authorization.rs then applies its documented fail-closed reading (module docs lines 61-72: a clause over "a key the request context does not carry" makes the statement UNDECIDED, and "an `Allow` whose condition may not hold is not a grant"; "nothing here guesses a condition value"). Independently, nothing in that module substitutes a policy variable: the module documentation's complete statement of what it reads (lines 39-89) never mentions variables, so `${aws:PrincipalTag/project}` is compared as literal text even once the context carries the key. Replay: the check's unconditioned control leg passed (`iam:ListUserTags` on the matching target returned OK, so the minted key and the policy are both effective), and then the conditioned leg never converged — the bounded poll for the permitted call reported `AccessDenied` on every observation and raised `the ABAC Condition resolves to 'sim2real-alpha' on both sides and permits the real signed iam:ListAccessKeys did not happen within 54.8s; last observation 'AccessDenied'`. Expected: HTTP 200 with the target's access-key metadata. Actual: HTTP 403, code `AccessDenied`, permanently.

Why: every ABAC grant a client writes against this emulator is inert in the restrictive direction. A tag-based least-privilege design cannot be validated at all: the matching call is refused where AWS permits it, and because the non-matching call is refused with exactly the same code and message, the emulator cannot show that the refusal came from a failing condition rather than from an unmodelled key. A client that works around the refusal by deleting the Condition then ships something strictly MORE permissive than the policy it meant to test.

Fix: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs must assemble the request's condition context and pass it through `iam::Request::with_context` — `iam:ResourceTag/*` and `aws:ResourceTag/*` read from the target entity in src/state.rs, `aws:PrincipalTag/*` from the resolved signing principal's stored tags (declared as a family through `Request::published` so the empty-set and `Null` rules apply), `aws:RequestTag/*` and `aws:TagKeys` from the calling operation's tag input — and services/common/src/iam_authorization.rs must substitute policy variables into a Condition's VALUES from that context before comparing. Related open issues, named so a fixer can see the overlap and NOT treat this cause as closed by them: 20261025T170540Z-iam-4-net-new-root-causes-the-authorization.md (its Cause 2 describes the same empty context and explicitly predicted this flip, but its recorded key for this check is the over-permissive `_rejected_code` signature, which no longer occurs) and 20261025T121312Z-iam-request-time-authorization-supplies-no-condition-context.md (the aws:ResourceTag + aws:RequestTag case on TagUser). Neither names the `${aws:PrincipalTag/<key>}` variable appearing as a Condition value.

=== Cause 2 of 3: IAM policy variables are never expanded, so a Resource element written as `user/${aws:username}` matches nothing and each caller's own self-service read is refused ===

AWS: a policy variable is a placeholder substituted from the request context at EVALUATION time, legal inside a Resource ARN as well as inside a Condition value, and `${aws:username}` expands to the signing IAM user's friendly name without its path (IAM User Guide, "IAM policy elements: variables and tags"). The consequences that follow: the document is STORED verbatim, so GetPolicy/GetPolicyVersion return it still containing the literal `${aws:username}`; ONE managed policy whose Resource is `arn:aws:iam::<account>:user/${aws:username}`, attached to two users, permits EACH user's own `iam:ListAccessKeys` / `iam:ListUserTags` because the variable expands to a different value per signer; the SAME policy grants nothing on the OTHER user, so each user's `ListAccessKeys` addressed at its sibling is refused HTTP 403 `AccessDenied`; and attaching an inline policy that names the sibling's ARN literally lifts that refusal until it is deleted. Smithy com.amazonaws.iam#ListAccessKeys / #ListUserTags model no authorization error, so `AccessDenied` 403 is the service-common refusal — recorded behavior only.

Emulator: there is no variable substitution anywhere in the evaluator. services/common/src/iam_authorization.rs is the tree's single evaluation of policy documents against a request; its module documentation (lines 39-89) enumerates exactly what it reads — Action/NotAction, Resource/NotResource, Principal/NotPrincipal, the string, ARN, boolean and existence operators, the set qualifiers — and never mentions a variable, and its Resource comparison is `wildcard_match`, whose only metacharacters are `*` and `?`. `${aws:username}` is therefore compared as fifteen literal characters and can never equal a user name. Now that `iam:ListAccessKeys` is gated, the symptom is the under-permissive one: replay shows the check's two POSITIVE legs failing — `the shared policy's ${aws:username} expands to 'sim2real-pvar-a-<id>' and permits its own read did not happen within 54.8s; last observation 'AccessDenied'`. The legs that passed before it localise the defect precisely: GetPolicyVersion returned the default version's document still carrying the literal `arn:aws:iam::<account>:user/${aws:username}` with neither user name in it (the write path is correct), ListAttachedUserPolicies reported exactly the one shared policy ARN for each user and ListUserPolicies reported no inline policy, so that shared managed policy is the only possible source of a grant. Expected: HTTP 200 for each user's `ListAccessKeys(UserName=<itself>)`. Actual: HTTP 403 `AccessDenied` for both, forever.

Why: the single-policy self-service pattern — one shared managed policy that lets every user administer only itself — is the canonical use of `${aws:username}`, and against this emulator it is simply broken: every caller is refused on its OWN resource. A developer cannot distinguish "my variable is wrong" from "this emulator does not expand variables", and the obvious workaround — widening the Resource to `user/*` — ships a policy that grants every user access to every other user's credential metadata.

Fix: services/common/src/iam_authorization.rs must substitute policy variables into a statement's Resource/NotResource values (and Condition values, see Cause 1) from the request context before matching, using the resolved signing principal for `${aws:username}` / `${aws:userid}` and its stored tags for `${aws:PrincipalTag/<key>}`, honouring IAM's `${...}` grammar including the `${?}`, `${*}`, `${$}` literal escapes so a `$` that is not a variable still matches literally; and services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs must supply the caller's resolved identity on the request so the variable has a value to expand to. PREREQUISITE and related, NOT a duplicate: 20261026T004230Z-iam-3-net-new-behavioral-root-causes-iam.md Cause 1 describes this same missing expansion and explicitly predicted that wiring the gate would turn this check's positive legs into permanent refusals — which is what has now happened, so its recorded `_rejected_code` replay key for this check no longer matches and the check is unowned.

=== Cause 3 of 3: `iam:GetUser` reaches no authorization gate, so GetUser on a resource OUTSIDE the statement's Resource element is served HTTP 200 ===

AWS: IAM's own API is governed by IAM, for every `iam:` action. An `Allow` with `NotAction: [iam:ListAccessKeys]` and `Resource: <own user arn>` grants the set COMPLEMENT of the listed actions and ONLY within that Resource element — NotAction never widens the Resource (IAM User Guide, "IAM JSON policy elements: NotAction"). So under that one statement the caller's real signed `iam:GetUser` and `iam:ListUserTags` on its OWN ARN are permitted, `iam:ListAccessKeys` on its own ARN is refused `AccessDenied`, and `iam:GetUser` addressed at a SIBLING user is refused `AccessDenied` (HTTP 403) because the sibling's ARN is not in the Resource element — and the SimulatePrincipalPolicy view must agree, reporting `implicitDeny` for that same (action, resource) pair. Smithy com.amazonaws.iam#GetUser declares only NoSuchEntityException 404 / ServiceFailureException 500, so `AccessDenied` 403 is the service-common refusal — recorded behavior only.

Emulator: the gate is not reached for GetUser. services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/state/authorization.rs declares action constants for 24 actions (lines 101-171: ListGroups, ListRoles, ListUsers, ListPolicies, ListInstanceProfiles, ListPoliciesGrantingServiceAccess, ListOpenIDConnectProviders, CreateGroup, DeleteGroup, GetGroup, UpdateGroup, ListGroupsForUser, ListUserTags, ListAccessKeys, ListRoleTags, ListPolicyTags, ListInstanceProfileTags, TagPolicy, UntagPolicy, CreatePolicyVersion, DeletePolicyVersion, SetDefaultPolicyVersion, GetAccountAuthorizationDetails, GetDelegationRequest) and `iam:GetUser` is not one of them; src/ops/get_user.rs never calls `crate::state::authorization::authorize`/`authorize_named`. Replay: everything the check asserts about the gated actions passed — the own-ARN real calls came back exactly `{'iam:GetUser': 'OK', 'iam:ListUserTags': 'OK', 'iam:ListAccessKeys': 'AccessDenied'}`, and the simulator leg had already settled on allowed/allowed/implicitDeny plus `implicitDeny` for GetUser on the sibling — and the ONE divergence is the sibling real call: `AssertionError: GetUser on a sibling is outside the statement's Resource; got 'OK'`. Expected HTTP 403 code `AccessDenied`; actual HTTP 200 with the sibling user's record. The simulator and the authorizer therefore disagree about the same policy in the same run.

Why: a negative IAM test on an ungated operation passes vacuously, in the dangerous direction. GetUser is how a client reads another principal's identity, so a policy that was meant to confine a caller to its own user record reads as working while serving every user in the account; and because the simulator answers correctly for the same pair, a reviewer who checks the simulator sees a confinement the real call does not enforce.

Fix: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/get_user.rs must call `crate::state::authorization::authorize_named` with an `iam:GetUser` action constant and the ARN of the user the request addresses (naming the entity, `user <name>`, in the refusal) before reading the store — and the same wiring is owed by every other handler that still bypasses the gate. The decision itself already lives in src/state/authorization.rs and services/common/src/iam_authorization.rs, which already implement NotAction and NotResource as a set complement, so this cause is call-site wiring plus the action-name constant. Related open issue, named because it covers the general wiring gap but NOT this check's current replay key: 20261025T170540Z-iam-4-net-new-root-causes-the-authorization.md Cause 1 (recorded when the own-ARN ListAccessKeys leg also returned 200 — that leg is now correct, so only the sibling GetUser leg remains and the signature changed).
