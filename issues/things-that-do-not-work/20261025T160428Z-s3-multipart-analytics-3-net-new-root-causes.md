# S3 multipart/analytics: 3 net-new root causes — UploadPart omits its flexible-checksum response members, ListBucketAnalyticsConfigurations answers NotImplemented instead of NoSuchBucket, and CompleteMultipartUpload is a scaffold stub so no multipart-completion event exists

> _Note: this issue was identified against the code base at commit `bf4b5d75768eba06386b10826e7ace22b8c67a1e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UploadPart

## Description
Three distinct net-new root causes, all in the s3 service (the Amazon S3 emulator crate, services/service-com-amazonaws-s3-amazons3). Each is numbered with its own failing check ids; ALL THREE must be closed before this issue is submitted. The check ids are grouped under three suite directories (s3, lambda__s3__sqs, s3__sqs) but every divergence is a divergence of an S3 operation, so the owning service is s3 for all of them.

Cause 1 of 3: UploadPart answers 200 without the flexible-checksum members it is modeled to return, so a part's digest is never observable and a wrong part digest is never refused.
AWS: Smithy s3#UploadPart carries @httpChecksum{requestAlgorithmMember: ChecksumAlgorithm} and accepts the request headers x-amz-sdk-checksum-algorithm plus x-amz-checksum-crc32 / -crc32c / -crc64nvme / -sha1 / -sha256 / -sha512 / -md5 / -xxhash64 / -xxhash3 / -xxhash128. Its output shape UploadPartOutput declares the matching response members ChecksumCRC32 (header x-amz-checksum-crc32), ChecksumCRC32C, ChecksumCRC64NVME (x-amz-checksum-crc64nvme), ChecksumSHA1, ChecksumSHA256 (x-amz-checksum-sha256), ChecksumSHA512, ChecksumMD5 and the three XXHASH members, alongside ETag. AWS computes the digest over the part body, refuses a supplied digest that does not match the bytes with BadDigest / HTTP 400 (and leaves that part slot empty, so a later ListParts/CompleteMultipartUpload does not see the part), and on success echoes the part's OWN digest in the member matching the requested algorithm. A part-scoped digest is a per-part value and is never the object's composite digest; when the upload is a FULL_OBJECT CRC64NVME upload, UploadPart still returns that part's ChecksumCRC64NVME.
Emulator: UploadPart answers 200 with every checksum member absent from the response. The replay shows `AssertionError: part 1 echoed ChecksumSHA256 None, want its true sha256`, and three further checks blow up reading the member off the response dict: `KeyError: 'ChecksumSHA256'` and `KeyError: 'ChecksumCRC64NVME'` (twice). Because nothing is computed, the companion requirement — refusing a deliberately wrong part digest with BadDigest/400 and leaving the slot empty — is also not reached.
Why: flexible checksums exist to make corruption detectable. A client that uploads parts with x-amz-checksum-sha256 (the SDK default behaviour for many transfer managers) gets back no digest to compare, and a corrupted part is accepted silently; code that reads response['ChecksumSHA256'] or response['ChecksumCRC64NVME'] — which the model says is present — raises KeyError against the emulator and works against AWS, so the emulator cannot be used to test the integrity path at all.
Fix: the UploadPart handler's checksum computation and validation, and the UploadPart response serializer that must emit the x-amz-checksum-* header for the algorithm in force; the same computation feeds the part digests CompleteMultipartUpload composes.

Cause 2 of 3: ListBucketAnalyticsConfigurations refuses with the emulator's own NotImplemented code where AWS refuses NoSuchBucket, so a walk over a deleted or mistyped bucket cannot be told from a bucket with no analytics exports.
AWS: Smithy s3#ListBucketAnalyticsConfigurations is GET /{Bucket}?analytics with required httpLabel Bucket and output ListBucketAnalyticsConfigurationsOutput (IsTruncated, ContinuationToken, NextContinuationToken, AnalyticsConfigurationList). For a bucket that does not exist the recorded response is error code NoSuchBucket with HTTP 404 and the message 'The specified bucket does not exist' — that message text is fixed for this error class; the BucketName/Resource reported alongside it is a value taken from the request, never a literal. The model declares no operation-specific errors, so the code/status/message here are recorded behavior from the check's own oracle plus S3's common NoSuchBucket class.
Emulator: the call is refused with error code 'NotImplemented' and the message 'operation ListBucketAnalyticsConfigurations is scaffolded but not implemented in this emulator' (`AssertionError: listing analytics configurations on a bucket that was never created must be rejected NoSuchBucket; got 'NotImplemented'`).
Why: a client enumerating analytics exports across buckets cannot distinguish 'this bucket is gone' from 'this bucket has no exports', and the error code it must branch on (NoSuchBucket) never appears.
Fix: the ListBucketAnalyticsConfigurations handler — implement the operation and make its bucket-existence pre-condition answer NoSuchBucket/404 before any listing.
Related (does NOT cover this): 20261025T032458Z-s3-listbucketanalyticsconfigurations-stub.md names the operation as an unimplemented scaffold stub; it does not state the required refusal for an absent bucket, which is the requirement this check asserts.
Traces: s3.s3-analytics-xacct-list-rejected-for-a-bucket-that-does-not-exist

Cause 3 of 3: CompleteMultipartUpload is an unimplemented scaffold stub, so a multipart upload can never be completed and the ObjectCreated:CompleteMultipartUpload notification semantics do not exist.
AWS: Smithy s3#CompleteMultipartUpload is POST /{Bucket}/{Key+} with httpQuery uploadId and the CompletedMultipartUpload payload; it answers 200 with CompleteMultipartUploadResult carrying Location, Bucket, Key, ETag, the checksum members and ChecksumType, and x-amz-version-id on a versioned bucket. On a bucket carrying an s3:ObjectCreated:* notification (Lambda or SQS target), completing the upload emits exactly ONE record whose eventName is ObjectCreated:CompleteMultipartUpload and whose s3.object.size is the assembled byte count. CreateMultipartUpload, UploadPart and AbortMultipartUpload emit no notification record at all, and after an abort ListParts on that upload id answers NoSuchUpload while HeadObject on the key answers a not-found — the S3 event-type table documents this only by omission, so the no-event-on-create/part/abort half is recorded behavior only (the s3__sqs check states it as a hypothesis in its own header).
Emulator: `botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the CompleteMultipartUpload operation: operation CompleteMultipartUpload is scaffolded but not implemented in this emulator`. Both checks die on that call, before any notification can be observed.
Why: every multipart upload path — which is what the AWS CLI and SDK transfer managers use for anything above the multipart threshold — is unusable, and the event an S3-triggered pipeline is wired to (ObjectCreated:CompleteMultipartUpload) can never fire, so a pipeline that works on AWS produces nothing here and an aborted upload cannot be shown to produce nothing either.
Fix: the CompleteMultipartUpload handler (services/service-com-amazonaws-s3-amazons3/src/ops/complete_multipart_upload.rs) — assemble the parts into the object, then emit the single ObjectCreated:CompleteMultipartUpload notification from the object-write event emitter, and emit nothing from the create/upload-part/abort paths.
Related (does NOT cover this): the auto-filed scaffold-stub issue for s3 CompleteMultipartUpload names the operation and its handler file (the suite reports it blocking 6 checks); 20261025T032458Z-s3-sqs-s3-notification-destinations-are-never-validated.md and 20261025T032458Z-s3-request-auth-and-eventing-plane-10-root.md Cause 7 cover notification delivery in general. Neither states the multipart event rule above, and neither carries these two check ids.
