# s3__sqs: PutBucketNotificationConfiguration accepts an SQS destination it cannot deliver to, and a bucket whose CREATE_FAILED destination validation rolled the stack back survives the rollback (2 causes)

> _Note: this issue was identified against the code base at commit `ab8b9af343344bd9ec1c9404b5c1438075827ba1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutBucketNotificationConfiguration

## Description
Two net-new root causes in the s3__sqs notification/deploy surface. Both must be closed before this issue is submitted.

Cause 1 of 2 — PutBucketNotificationConfiguration performs no delivery-permission validation of an SQS destination (failing check: s3__sqs.s3-sequencer-is-the-only-total-order-over-one-key).
AWS: Smithy doc for PutBucketNotificationConfiguration states that after S3 receives the request it "first verifies that any Amazon Simple Notification Service (Amazon SNS) or Amazon Simple Queue Service (Amazon SQS) destination exists, and that the bucket owner has permission to publish to it by sending a test notification", and that "If the message fails, the entire PUT action will fail, and Amazon S3 will not add the configuration to your bucket". The model also binds PutBucketNotificationConfigurationRequest.SkipDestinationValidation to the header x-amz-skip-destination-validation, documented as "Skips validation of Amazon SQS, Amazon SNS, and Lambda destinations" — the opt-out exists precisely because validation is on by default. The refusal class is HTTP 400 with error code InvalidArgument and the message "Unable to validate the following destination configurations"; that sentence is the fixed text of this error class (the variable part is the destination(s) named in the detail, taken from the request's QueueConfigurations). S3 reuses InvalidArgument for an overlapping-prefix configuration, so the message, not the code alone, is what identifies this class.
Emulator: the PUT of a two-destination configuration whose second QueueConfiguration names an existing queue whose resource policy does NOT grant sqs:SendMessage to s3.amazonaws.com SUCCEEDS (HTTP 200) and installs the configuration. The replay fails on exactly that: "the call was expected to be rejected by the service but it SUCCEEDED". Note the emulator does produce this refusal for a destination queue that does not exist at all (the sibling check s3__sqs.deploy-s3-3-... sees the CREATE_FAILED reason "Unable to validate the following destination configurations"), so what is missing is the resource-policy/test-notification half of the validation, not the whole of it.
Why: a client that relies on configuration-time validation to tell it the pipeline is wired gets a 200 for a notification configuration that can never deliver; the failure then shows up only as permanent silence at the destination, with no error anywhere. Conversely, code that handles InvalidArgument to repair a queue policy never runs.
Fix: the destination-validation step of the PutBucketNotificationConfiguration handler in the s3 crate — for each TopicConfiguration/QueueConfiguration, resolve the destination and require that its resource policy admit the S3 service principal for the bucket (the 'send a test notification' step), refusing the WHOLE request with 400 InvalidArgument / "Unable to validate the following destination configurations" and leaving the previously stored configuration untouched; honour SkipDestinationValidation as the documented opt-out. A similar but distinct open issue, 20261025T025317Z-s3-sns-sqs-a-bucket-notification-to-a.md, reports the SNS-topic form of this gap; it does not carry this check's key and does not cover the SQS-queue destination.
Traces: s3__sqs.s3-sequencer-is-the-only-total-order-over-one-key (every ordering/sequencer/event-shape assertion before the negative arm passed; only the refusal is missing).

Cause 2 of 2 — a bucket whose AWS::S3::Bucket resource ended CREATE_FAILED still exists after the stack reaches ROLLBACK_COMPLETE (failing check: s3__sqs.deploy-s3-3-notification-nonexistent-queue-rollback-rejected).
AWS: recorded behavior only (CloudFormation's rollback contract, not a modelled error). A create that fails is rolled back, and every resource the create had physically provisioned is deleted; after ROLLBACK_COMPLETE a HeadBucket on such a bucket answers HTTP 404 with no body. The recording shows the emulator already gets the rest of this right: the stack ends ROLLBACK_COMPLETE, BucketB has exactly one CREATE_FAILED event whose ResourceStatusReason names the destination-validation failure, BucketB never reaches CREATE_COMPLETE, BucketA is CREATE_COMPLETE then DELETE_COMPLETE, and HeadBucket on BucketA answers 404 — all of those assertions passed.
Emulator: HeadBucket on the rolled-back BucketB answers HTTP 200, i.e. the bucket created for the resource whose creation then failed is left behind.
Why: the account is left holding a bucket no stack tracks, under a name the template owns; a retry of the same deploy, or any later CreateBucket of that name, is then refused as already existing, and a client that trusts ROLLBACK_COMPLETE to mean "nothing from this stack exists" leaks storage and S3's globally unique name.
Fix: the cloudformation crate's rollback/cleanup path — the set of resources the rollback deletes must include a resource that was physically created and then transitioned to CREATE_FAILED, not only those that reached CREATE_COMPLETE; for AWS::S3::Bucket that means deleting the bucket it had already created before notification-destination validation refused it. The open issue 20261025T015306Z-cloudformation-never-rolls-a-failed-stack-back-failed.md looks related but does not cover this: here the rollback does run and reports correctly, and only the failed resource's physical bucket survives.
Traces: s3__sqs.deploy-s3-3-notification-nonexistent-queue-rollback-rejected.

## Evidence
Cause 1 — expected: put_bucket_notification_configuration with QueueConfigurations=[granted queue (prefix 'ord/'), ungranted queue (prefix 'deny/')] is refused HTTP 400, Error.Code='InvalidArgument', Error.Message='Unable to validate the following destination configurations', the stored configuration still lists only the granted queue, and nothing is ever delivered to the ungranted queue. Actual: the call returned success (200) and the configuration was installed; replay assertion: "AssertionError: the call was expected to be rejected by the service but it SUCCEEDED -- a target that accepts this input is more broken than one that returns the wrong error code" (check_s3__sqs_s3_sequencer_is_the_only_total_order_over_one_key.py line 343). Smithy: PutBucketNotificationConfiguration doc — S3 'verifies that any ... SQS destination exists, and that the bucket owner has permission to publish to it by sending a test notification ... the entire PUT action will fail'; PutBucketNotificationConfigurationRequest.SkipDestinationValidation -> x-amz-skip-destination-validation.

Cause 2 — expected: after the stack ends ROLLBACK_COMPLETE, HeadBucket on BucketB answers 404. Actual: it answers 200. Replay assertion: "AssertionError: after ROLLBACK_COMPLETE, HeadBucket on BucketB 'sim2real-s3-3-b-<generated>' returned '200'; a bucket whose destination failed validation must not exist (expected 404)" (the bucket name is per-run and is not part of the requirement). The same replay shows BucketB's single CREATE_FAILED event with the 'Unable to validate the following destination configurations' reason, and BucketA correctly created, deleted and 404 on HeadBucket.

## Steps to Reproduce
Cause 1: create a bucket; create two SQS queues, one with a resource policy allowing sqs:SendMessage to s3.amazonaws.com for the bucket ARN and one with no such grant; PUT a notification configuration carrying both as QueueConfigurations with disjoint prefixes and s3:ObjectCreated:*; observe the call succeed instead of being refused 400 InvalidArgument / 'Unable to validate the following destination configurations'. Replay: s3__sqs.s3-sequencer-is-the-only-total-order-over-one-key.

Cause 2: CreateStack with a template declaring BucketA (plain AWS::S3::Bucket) and BucketB (AWS::S3::Bucket whose NotificationConfiguration names an SQS queue ARN that does not exist); wait for the terminal status ROLLBACK_COMPLETE; HeadBucket BucketA (404, correct) and HeadBucket BucketB — it answers 200 instead of 404. Replay: s3__sqs.deploy-s3-3-notification-nonexistent-queue-rollback-rejected.
