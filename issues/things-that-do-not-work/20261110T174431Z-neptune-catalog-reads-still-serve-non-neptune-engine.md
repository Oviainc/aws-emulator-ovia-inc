# Neptune catalog reads still serve non-Neptune engine-version, event-category and orderable-option reference data

> _Note: this issue was identified against the code base at commit `54b3fe10738e925f02de63999e233b2f22231166`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions

## Description
The three read-only reference catalogs the Neptune front door publishes (engine versions, event categories, orderable DB instance options) all answer the modelled HTTP 200, but the reference data in the body is still not the catalog the service serves: the engine-version list contains none of the graph engine's releases at any index, the event-category report is missing whole source types and alphabetises one entry's category list, and the orderable-option elements emit a member the model does not declare while reporting a short Availability-Zone set. Replay of simparity-wire-aws-v1 reports all three clusters with an EMPTY owned_by and an EMPTY stub_path, so no open issue carries their replay keys. The prior work item on these same three fixtures, 20261030T024450Z-neptune-3-net-new-catalog-causes-engine-version.md, is RESOLVED (it corrected the per-element capability flags in the orderable-option report and the category SETS of most event-category entries) and a resolved issue covers nothing; the open 20261103T175309Z-neptune-parameter-and-engine-version-catalogs-serve-rds.md covers only the engine-name/family VALIDATION and refusal wording on the neptune-npt-traj-* fixtures, not the catalog CONTENT clusters below. THIS ISSUE HAS 3 CAUSES — all three must be closed before submitting.

Cause 1 of 3: DescribeDBEngineVersions does not serve the Neptune engine-version catalog — not one recorded DBEngineVersion element is present at its index. AWS: the operation models no errors and returns com.amazonaws.neptune#DBEngineVersionMessage carrying DBEngineVersions, a list whose member is com.amazonaws.neptune#DBEngineVersion serialised under the xmlName DBEngineVersion, plus the pagination Marker (Smithy: DescribeDBEngineVersions errors=[], paginated inputToken/outputToken=Marker, items=DBEngineVersions, pageSize=MaxRecords). DBEngineVersion models Engine, EngineVersion, DBParameterGroupFamily, DBEngineDescription, DBEngineVersionDescription, ValidUpgradeTarget (list<UpgradeTarget>), ExportableLogTypes, SupportsLogExportsToCloudwatchLogs, SupportsReadReplica and SupportsGlobalDatabases. Recorded behavior only for the catalog's contents: an unfiltered DescribeDBEngineVersions against the Neptune front door enumerates every published release of the graph engine, each element naming Engine 'neptune', its own EngineVersion, the DB parameter group family that release belongs to (neptune1, neptune1.2, neptune1.3, neptune1.4 ...), a DBEngineVersionDescription naming the product and the release, and a ValidUpgradeTarget chain of the releases that release may be upgraded to (each target carrying EngineVersion, Description, AutoUpgrade and IsMajorVersionUpgrade), alongside the per-release capability flags the RDS-shared wire shape publishes. Emulator: the response is a 200 whose DBEngineVersions list presents none of those releases — every element the recording reports at DBEngineVersions.DBEngineVersion[0] through [28] is reported 'missing' at that index, so neither the release set, nor the family grouping, nor the upgrade-target chains are the engine's. Why: this is the discovery call a client makes before CreateDBCluster/CreateDBInstance to pick a version, and the call an upgrade planner walks to compute a path from the version it is on; reading a catalog whose entries are not the service's means it either finds no version it may create with or plans an upgrade to a release the service will refuse. Fix: the engine-version reference catalog read by the DescribeDBEngineVersions handler, and that handler's assembly of the DBEngineVersions list (which releases are enumerated, their family grouping and their ValidUpgradeTarget chains). Traces: neptune-catalog-describe-db-engine-versions#task#1.

Cause 2 of 3: DescribeEventCategories omits three published source types from EventCategoriesMapList and alphabetises the db-instance entry's category list. AWS: the operation returns com.amazonaws.neptune#EventCategoriesMessage carrying EventCategoriesMapList, a list whose member is com.amazonaws.neptune#EventCategoriesMap (xmlName EventCategoriesMap) pairing SourceType with that source type's EventCategories list (Smithy: DescribeEventCategories, errors=[], input SourceType/Filters both optional). Recorded behavior only, because neither the model nor AWS documentation states a sort rule or fixes the membership: with no SourceType filter the service reports an entry for every source type it raises events for — including blue-green-deployment (categories creation, failure, deletion, notification), db-shard-group (creation, deletion, availability, maintenance, failure, notification) and zero-etl (creation, deletion, failure, notification) — and reports each entry's EventCategories in the catalog's own published sequence, which for db-instance is backup, deletion, availability, creation, low storage, restoration, configuration change, failover, maintenance, failure, notification, read replica, recovery, security, backtrack, security patching. Emulator: the list it serves ends before those three source types — positions [8], [9] and [10] are absent entirely ('got None') — and the db-instance entry at position [2] carries the same 16 categories re-sorted alphabetically (availability, backtrack, backup, configuration change, creation, deletion, failover, failure, low storage, maintenance, notification, read replica, recovery, restoration, security, security patching). Why: a client that enumerates this catalog to decide which categories it may subscribe to with CreateEventSubscription cannot discover the blue-green-deployment, db-shard-group or zero-etl source types at all, and a client that indexes or diffs the report positionally (a console-style listing, a cached catalog diff, a test pinning an entry) reads a different category at a given position than the service reports. Fix: the event-category reference catalog read by the DescribeEventCategories handler — its source-type membership — and the ordering that handler applies when emitting each entry's EventCategories, which must be the catalog's published order rather than a sort imposed by the projection. Traces: neptune-catalog-describe-event-categories#task#1.

Cause 3 of 3: DescribeOrderableDBInstanceOption elements emit a SupportsStorageAutoscaling member the shape does not model and report a short Availability-Zone set, so no element matches the service's report at its index. AWS: com.amazonaws.neptune#OrderableDBInstanceOption models exactly Engine, EngineVersion, DBInstanceClass, LicenseModel, AvailabilityZones (list<AvailabilityZone>), MultiAZCapable, ReadReplicaCapable, Vpc, SupportsStorageEncryption, StorageType, SupportsIops, SupportsEnhancedMonitoring, SupportsIAMDatabaseAuthentication, SupportsPerformanceInsights, MinStorageSize, MaxStorageSize, MinIopsPerDbInstance, MaxIopsPerDbInstance, MinIopsPerGib, MaxIopsPerGib, SupportsGlobalDatabases and SupportedNetworkTypes — there is NO SupportsStorageAutoscaling member on this shape (Smithy: shape com.amazonaws.neptune#OrderableDBInstanceOption; Engine is a required input member of DescribeOrderableDBInstanceOptionsMessage and the operation models no errors). Recorded behavior only for the data: AvailabilityZones lists every zone of the endpoint's region in which that class/engine-version combination is orderable, which for the recorded region is four zones, and each element additionally carries the RDS-shared wire members the service emits (SupportsGlobalDatabases, SupportsClusters, SupportedNetworkTypes, SupportsHttpEndpoint, SupportsOptimizedReads/Writes, SupportsKerberosAuthentication, SupportsAdditionalStorageVolumes, SupportsDedicatedLogVolume, RequiresCustomProcessorFeatures, AvailableProcessorFeatures, SupportedActivityStreamModes, OutpostCapable). Emulator: every element at OrderableDBInstanceOption[0] through [147] is reported 'missing' at its index; the element it serves instead carries an extra SupportsStorageAutoscaling flag that neither the model declares nor the service emits, and its AvailabilityZones list is one zone short of the zone set the service reports as orderable for that class. Why: a client pre-flighting a CreateDBInstance against this report is told the class is unavailable in a zone in which it is in fact orderable, so it places the instance in the wrong zone or refuses a valid placement; and a strict SDK or schema validator that rejects unmodelled members fails to deserialise the catalog at all. Fix: the orderable-options reference catalog read by the DescribeOrderableDBInstanceOptions handler and that handler's projection of OrderableDBInstanceOption — the zone set per class must come from the region's orderable zones and the projection must emit only the members the shape declares. Traces: neptune-catalog-describe-orderable-db-instance-options#task#1.
