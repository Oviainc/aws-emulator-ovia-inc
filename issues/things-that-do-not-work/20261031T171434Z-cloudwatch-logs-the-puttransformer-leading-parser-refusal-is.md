# cloudwatch__logs: the PutTransformer leading-parser refusal is emulator-authored (and lists 9 fewer parsers than AWS), and applyOnTransformedLogs metric filters plus the AWS/Logs transformer metrics publish nothing (2 causes)

> _Note: this issue was identified against the code base at commit `74eb505d6f038f764bd1308b44906372fa72a184`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTransformer

## Description
Two independent root causes in the CloudWatch Logs transformer/metric-filter surface, both grounded in behavioral checks that the replay did not mark ALREADY FILED or OWNED. Cause count: 2. Each cause below carries its own failing check id; BOTH must be closed before submitting.

=== Cause 1 of 2: PutTransformer's 'must begin with a parser' refusal uses the emulator's own sentence and an incomplete parser catalogue ===
AWS: PutTransformer refuses a transformerConfig whose FIRST processor is not a parse-type processor. Smithy: PutTransformer input transformerConfig -> Processors (@required, @length min 1 max 20); modeled errors include InvalidParameterException (errorKind client, httpError 400, 'A parameter is specified incorrectly'). The model does NOT encode the leading-parser rule, so the message text is recorded behavior only. Recorded refusal: error code InvalidParameterException, HTTP 400, message 'Transformer config should begin with parser. Allowed parsers are parsePostgres, parseWAF, parseCloudfront, parseCloudfrontOCSF, parseRoute53, parseLambda, parseVPC, parseSyslog, parseRDS, parseCiscoFTD, parseF5BigIP, parseCiscoISE, parseForescoutNac, parseInfobloxDDI, parseToOCSF, parseJSON, grok, csv, parseKeyValue'. That string is ENTIRELY fixed text: there are no variable parts taken from the request or from state — AWS names neither the offending processor nor its position, and the 19 parser names are a fixed service-side catalogue in a fixed order.
Emulator: the status (400) and the code (InvalidParameterException) are already correct, but the message is 'The first processor in a transformer must be a parse-type processor, one of csv, grok, parseCloudfront, parseJSON, parseKeyValue, parsePostgres, parseRoute53, parseToOCSF, parseVPC, parseWAF; this transformer begins with addKeys.' Three divergences in one sentence: (a) the fixed lead-in is rewritten ('The first processor in a transformer must be a parse-type processor, one of ...' instead of 'Transformer config should begin with parser. Allowed parsers are ...'); (b) the catalogue is alphabetised and holds only 10 of AWS's 19 parsers — parseCloudfrontOCSF, parseLambda, parseSyslog, parseRDS, parseCiscoFTD, parseF5BigIP, parseCiscoISE, parseForescoutNac and parseInfobloxDDI are absent; (c) it appends a trailing clause derived from the request ('; this transformer begins with <firstProcessorName>.') that AWS never emits.
Why: a client that keys retry/repair logic on AWS's wording does not recognise the refusal and falls through to a generic failure, even though the code matched. Worse, a user who reads the allowed-parser list out of the message to repair a transformer is told that nine parsers real CloudWatch Logs accepts (including parseLambda, parseVPC-adjacent parseSyslog, parseRDS and the OCSF CloudFront parser) are not allowed, so they will rewrite a working transformer configuration into a different one.
Fix: the leading-parser refusal branch of the PutTransformer handler and the message builder it calls — `crate::state::transformer_leading_parser_message` as invoked at services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/put_transformer.rs lines 256-270. The fixed text and the full 19-name catalogue in AWS's order belong in that builder; the request-derived trailing clause must be dropped. Note the same catalogue constant (`crate::state::PARSE_TYPE_PROCESSORS`) is shared with the per-position check above it, so widening it must not change which configurations are ACCEPTED beyond AWS's set.
Traces: cloudwatch__logs.obs-logs-2-transformer-without-leading-parser-rejected.

=== Cause 2 of 2: a metric filter with applyOnTransformedLogs=true publishes no datapoint, and AWS/Logs TransformedLogEvents / TransformedBytes are never published at all ===
AWS: recorded behavior only for the emission; the model states only the inputs. Smithy: PutMetricFilter input carries applyOnTransformedLogs (ApplyOnTransformedLogs, boolean, @default false) alongside logGroupName/filterName/filterPattern/metricTransformations (@length min 1 max 1), and PutTransformer installs the log-group-level processor pipeline. The recording shows: with a transformer of [parseJSON, addKeys{sev: HIGH}] installed on a log group, two metric filters on that group sharing the pattern '{ $.sev = "HIGH" }' — one with applyOnTransformedLogs=true, one with it false — are evaluated against DIFFERENT events. For N ingested JSON lines that do NOT themselves carry `sev`, the applyOnTransformedLogs=true filter's metric reaches Sum = N (it sees the transformed event, which addKeys gave sev=HIGH) and stays at exactly N with no double counting, while the applyOnTransformedLogs=false twin publishes NO datapoint at all (GetMetricStatistics returns an empty Datapoints list, not a zero) because the raw event has no `sev`. Independently, AWS publishes the transformer's own series in the AWS/Logs namespace under exactly ONE per-log-group dimension whose name is LogGroupName and whose value is the group: TransformedLogEvents reaches Sum = N, and TransformedBytes publishes at least one datapoint whose Unit is 'Bytes' with a positive Sum.
Emulator: none of that materialises. The check never gets past its FIRST wait — the custom-namespace metric of the applyOnTransformedLogs=true filter never reaches Sum = N — and the harness kills the check at its 60 s ceiling ('Error: Check timed out after 60.0s'), so the emulator produced no transformed-side filter datapoint, no AWS/Logs TransformedLogEvents datapoint and no AWS/Logs TransformedBytes datapoint. PutTransformer/GetTransformer round-trip the pipeline and DescribeMetricFilters echoes applyOnTransformedLogs correctly (the check asserts both before the wait), so the control plane stores the configuration and only the ingest-time evaluation and emission are missing.
Why: the whole point of applyOnTransformedLogs is that a filter pattern can be written against the normalised event rather than the raw line. A client that installs a transformer and then alarms on a metric filter over the transformed shape gets a metric that never exists, so the alarm sits in INSUFFICIENT_DATA forever instead of breaching — and because the raw-event twin also publishes nothing, the emulator is indistinguishable from the correct 'raw filter matched nothing' outcome, which makes the bug silent. The missing AWS/Logs TransformedLogEvents/TransformedBytes series also removes the only way to observe that the transformer ran at all, and TransformedBytes is a billed dimension of the feature.
Fix: the ingest-time path, not the control plane. Metric-filter evaluation on PutLogEvents must run the group's installed transformer pipeline and evaluate each filter against the transformed event when applyOnTransformedLogs is true and against the raw message when it is false, publishing the configured metricTransformations into the declared namespace; and the ingest path must additionally publish AWS/Logs TransformedLogEvents (count of transformed events) and AWS/Logs TransformedBytes (Unit Bytes) under a single LogGroupName dimension. This belongs in the logs service's ingest/state component (services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/state.rs and the PutLogEvents handler under services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/), together with whatever bridges logs-derived metrics into the CloudWatch metric store. Related but NOT covering: the open issue 20261024T150703Z-logs-cloudwatch-logs-metric-filters-emit-no-cloudwatch-metric.md is filed against service `logs` and describes metric filters emitting no CloudWatch data generally; it does not carry this check's replay key and says nothing about applyOnTransformedLogs selection or the AWS/Logs transformer series, so this cause must be closed on its own evidence.

## Steps to Reproduce
Cause 1 (PutTransformer refusal message):
1. logs CreateLogGroup logGroupName=<group>.
2. logs PutTransformer logGroupIdentifier=<group> transformerConfig=[{"addKeys": {"entries": [{"key": "sev", "value": "HIGH"}]}}] — i.e. a pipeline whose first (and only) processor is a mutation step, not a parse-type processor.
3. The call is correctly refused with HTTP 400 / InvalidParameterException. Compare the message against AWS's fixed text 'Transformer config should begin with parser. Allowed parsers are parsePostgres, parseWAF, parseCloudfront, parseCloudfrontOCSF, parseRoute53, parseLambda, parseVPC, parseSyslog, parseRDS, parseCiscoFTD, parseF5BigIP, parseCiscoISE, parseForescoutNac, parseInfobloxDDI, parseToOCSF, parseJSON, grok, csv, parseKeyValue'. The emulator returns its own sentence, a 10-name catalogue and an extra request-derived trailing clause.
4. logs GetTransformer logGroupIdentifier=<group> must return an empty transformerConfig (nothing was installed) — this part already holds.

Cause 2 (applyOnTransformedLogs filters and AWS/Logs transformer metrics):
1. logs CreateLogGroup logGroupName=<group>; CreateLogStream logStreamName=events.
2. logs PutTransformer logGroupIdentifier=<group> transformerConfig=[{"parseJSON": {}}, {"addKeys": {"entries": [{"key": "sev", "value": "HIGH"}]}}].
3. logs PutMetricFilter logGroupName=<group> filterName=txmf-transformed filterPattern='{ $.sev = "HIGH" }' applyOnTransformedLogs=true metricTransformations=[{metricName: Transformed, metricNamespace: <ns>, metricValue: "1"}].
4. logs PutMetricFilter logGroupName=<group> filterName=txmf-raw, SAME filterPattern, applyOnTransformedLogs=false, metricName=Raw, same <ns>.
5. logs PutLogEvents 4 events whose messages are JSON objects that do NOT contain a `sev` key, e.g. {"msg": "order processed", "n": 0..3}.
6. cloudwatch GetMetricStatistics Namespace=<ns> MetricName=Transformed Period=60 Statistics=[Sum] over a window covering the write: expect Sum == 4.0. The emulator returns no datapoints.
7. cloudwatch GetMetricStatistics Namespace=<ns> MetricName=Raw: expect an EMPTY Datapoints list (the raw events lack sev).
8. cloudwatch ListMetrics Namespace=AWS/Logs MetricName=TransformedLogEvents: expect exactly one metric for <group> with exactly one dimension, LogGroupName=<group>. Then GetMetricStatistics on AWS/Logs TransformedLogEvents (expect Sum == 4.0) and on AWS/Logs TransformedBytes (expect >= 1 datapoint, Unit 'Bytes', Sum > 0). The emulator publishes neither series.
