# Configured safety rules are never evaluated: an unsatisfiable ATLEAST assertion rule does not block UpdateRoutingControlState, which answers 200 and moves the state

> _Note: this issue was identified against the code base at commit `bc82654c409a33f503ba5ef7384156730ff2d370`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateRoutingControlState

## Description
One net-new root cause (Cause 1 of 1) for route53-recovery-control-config: safety rules created through CreateSafetyRule are stored and reported as DEPLOYED but are never ENFORCED, so the routing-control state change they must block succeeds instead.

Cause 1 of 1: a routing control covered by an assertion rule whose condition the requested transition would violate is updated anyway — the emulator answers HTTP 200 with an empty body where AWS refuses with ValidationException (400) naming the offending safety rule. Failing check: route53-recovery-control-config.safety-rule-threshold-exceeds-controls-rejected.

AWS: CreateSafetyRule imposes no Threshold-vs-AssertedControls-count validation, so an ATLEAST assertion rule whose Threshold exceeds the number of asserted controls is accepted and reaches DEPLOYED (this part the emulator already matches, and the check asserts it). The consequence lives on the data plane: Smithy (route53-recovery-cluster / ToggleCustomerAPI, awsJson1_0) models UpdateRoutingControlState with errors AccessDeniedException (403), ConflictException (409), EndpointTemporarilyUnavailableException (503), InternalServerException (500), ResourceNotFoundException (404), ThrottlingException (429) and ValidationException (400, "There was a validation error on the request."), and models the input member SafetyRulesToOverride (list Arns) documented as "The Amazon Resource Names (ARNs) for the safety rules that you want to override when you're updating the state of a routing control" — i.e. the model states that configured safety rules DO block a state update unless the caller explicitly overrides them. Recorded behavior for the refusal itself: AWS returns code ValidationException with the message whose FIXED text is `Can't update the routing control state because of a configured safety rule: "` ... `." To override the rule and change the state, see the guidance for AllowSafetyRulesOverride in the Route 53 ARC Developer Guide. ` then a newline, `Routing control: [`, `] `, a newline, `Safety rule: `. Its VARIABLE parts, all taken from the request and from control-plane state, are: (a) the human-readable rendering of the blocking rule's condition, built from the rule's RuleConfig — for an ATLEAST rule with Threshold N that is `At least N routing controls must be On` (N is the stored Threshold, not a literal); (b) the RoutingControlArn echoed from the request, inside the square brackets; (c) the SafetyRuleArn of the rule that blocked the request. The state must not move: an immediately following GetRoutingControlState still reports the pre-call state. Deleting the rule must make the identical UpdateRoutingControlState call succeed, which is the check's restore step — so the refusal is rule-driven, not a blanket denial.

Emulator: safety rules are not consulted at all on the state-change path. The replay shows the blocked call answered HTTP 200 with content-type application/x-amz-json-1.0 and a 2-byte body (`{}`), so the check's `_error()` helper raised `AssertionError: expected a ClientError but call succeeded: {'ResponseMetadata': {'HTTPStatusCode': 200, ...}}` at the UpdateRoutingControlState step. This is explicit in the handler: services/service-com-amazonaws-route53recoverycluster-togglecustomerapi/src/ops/update_routing_control_state.rs states in its module header "`SafetyRulesToOverride` is accepted and IGNORED in this first slice: safety-rule assertion and gating is left to its own gap issue", and handle() does `let _ = &input.safety_rules_to_override;` (line 182) then goes straight from the enum re-parse to `plane.set_state(...)` (line 223). Its only refusals are the enum ValidationException and the not-found ResourceNotFoundException; there is no evaluation point for assertion or gating rules, and no read of the control plane's safety-rule store.

Why: safety rules are the entire point of Route 53 ARC's control-plane configuration — they exist to stop a fail-open or fail-both-cells state transition. Against the emulator every such transition is permitted, so a client cannot test that its safety rules work, cannot exercise the ValidationException branch that drives the break-glass path (retry with SafetyRulesToOverride set), and cannot distinguish a correctly configured safety rule from no rule at all. Misconfigurations such as this check's unsatisfiable ATLEAST rule (Threshold 3 over 2 asserted controls), which on AWS permanently wedge every transition on those controls, look harmless in the emulator and then wedge production. A failover runbook validated against the emulator succeeds and then is refused by AWS at the moment it is needed.

Fix: the state-change path of the data-plane operation handler — the missing safety-rule evaluation stage in UpdateRoutingControlState (and the batch UpdateRoutingControlStates, which shares it) must, before committing the transition, read the control panel's DEPLOYED safety rules that assert the target routing control, evaluate the proposed post-transition On/Off vector against each rule's RuleConfig (Type ATLEAST/AND/OR, Threshold, Inverted), and on violation leave the stored state untouched and return the modeled ValidationException (400) with the message template above, interpolating the rule's rendered condition, the request's RoutingControlArn and the blocking SafetyRuleArn. The same stage is what makes SafetyRulesToOverride meaningful: a rule whose ARN appears there must be skipped rather than ignored wholesale. This requires the cluster data plane to see the control plane's safety-rule state, so the shared store these two crates use is part of the fix; the control-plane side (CreateSafetyRule accepting the over-threshold rule) is already correct and must not start rejecting it.

## Steps to Reproduce
1. Clone the repo and boot the emulator built from it. route53-recovery-control-config is bootstrapped (get_bootstrap_status reports service-com-amazonaws-route53recoverycontrolconfig-route53recoverycontrolconfig in bootstrapped, and the suite's other 14 checks for it pass), as is the route53-recovery-cluster data plane it drives.
2. CreateCluster (or reuse a DEPLOYED one) and wait for Status DEPLOYED. DescribeCluster and build a route53-recovery-cluster client against the ClusterEndpoints entry for the current region (there is no generic regional endpoint for this data plane).
3. CreateControlPanel in that cluster; wait for DEPLOYED. CreateRoutingControl twice in that control panel (rc0, rc1); wait for both DEPLOYED.
4. Positive control: GetRoutingControlState(rc0), UpdateRoutingControlState(rc0, the opposite state), poll until GetRoutingControlState reports it, then set it back. Both toggles must succeed — this proves the data plane is live before any rule exists.
5. CreateSafetyRule with AssertionRule{Name:<any>, ControlPanelArn:<panel>, AssertedControls:[rc0, rc1], RuleConfig:{Type:"ATLEAST", Threshold:3, Inverted:false}, WaitPeriodMs:0}. It must be ACCEPTED (AWS does not validate Threshold against the asserted-control count) and DescribeSafetyRule must report Status DEPLOYED. The emulator already does this correctly.
6. Call UpdateRoutingControlState(RoutingControlArn=rc0, RoutingControlState=<the opposite of its current state>).
   Expected: ValidationException (400) with message 'Can\'t update the routing control state because of a configured safety rule: "At least 3 routing controls must be On." To override the rule and change the state, see the guidance for AllowSafetyRulesOverride in the Route 53 ARC Developer Guide. \nRouting control: [<rc0 arn>] \nSafety rule: <rule arn>'.
   Observed: HTTP 200 with an empty body `{}` and no error.
7. Effect check: GetRoutingControlState(rc0) must still report the pre-call state. Observed: the emulator has moved it, because set_state() ran.
8. Restore control: DeleteSafetyRule(rule), wait until ListSafetyRules for the control panel no longer lists it, then repeat the step-6 call. It must now succeed and the state must settle on the requested value — confirming the refusal is produced by the rule and only by the rule.
9. Override control (same stage, once implemented): with the rule DEPLOYED again, call UpdateRoutingControlState with SafetyRulesToOverride=[<rule arn>]; that call must succeed while the un-overridden one is still refused.
10. Re-replay to confirm a fix: route53-recovery-control-config.safety-rule-threshold-exceeds-controls-rejected.
