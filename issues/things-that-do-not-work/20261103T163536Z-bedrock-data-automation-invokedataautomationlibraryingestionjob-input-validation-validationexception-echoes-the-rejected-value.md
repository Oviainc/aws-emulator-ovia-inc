# InvokeDataAutomationLibraryIngestionJob input validation: ValidationException echoes the rejected value, and the entityType enum set is missing RECOGNIZED_PERSON

> _Note: this issue was identified against the code base at commit `6788b77349a4fc1e05cc03a6c90d9f4cfe03594a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Two net-new root causes in the input-validation refusals of InvokeDataAutomationLibraryIngestionJob (PUT /data-automation-libraries/{libraryArn}/library-ingestion-jobs/). Both are observed on the constrained-member refusal path that the centralized request walk (deserialize -> validate -> handle) runs BEFORE the operation handler, so they are independent of the fact that the handler itself is still a scaffold stub (that stub is already filed as the UNIMPLEMENTED `InvokeDataAutomationLibraryIngestionJob` issue and is NOT re-filed here; it is what keeps each check's positive-control leg from completing once the message wording is fixed).

Related open issue, named so a fixer can single-home the change and not because it covers these checks (neither failing check id appears in its replay keys): 20261029T211335Z-bedrock-data-automation-ten-net-new-causes-create.md, whose Cause 6 and Cause 8 describe the same value-echoing defect reached through CreateBlueprint/CreateDataAutomationProject/CreateDataAutomationLibrary name patterns and the TagResource tag-count limit. The two causes below are reached through DIFFERENT members (libraryArn's ARN pattern and entityType's enum) of a different operation, and Cause 2 is a constraint-set defect that issue does not mention at all.

=== Cause 1 of 2: the pattern/enum ValidationException message interpolates the rejected value where AWS renders no value ===
AWS: Smithy (services/service-com-amazonaws-bedrockdataautomation-amazonbedrockkeystonebuildtimeservice/smithy-model/com-amazonaws-bedrockdataautomation-amazonbedrockkeystonebuildtimeservice.json): InvokeDataAutomationLibraryIngestionJobRequest.libraryArn targets DataAutomationLibraryArn, @httpLabel, required, @length(max 128), pattern ^arn:aws(|-cn|-iso|-iso-[a-z]|-us-gov):bedrock:[a-zA-Z0-9-]*:[0-9]{12}:data-automation-library/[a-zA-Z0-9-]{12,36}$; entityType targets the EntityType enum, required; ValidationException is errorKind client, @httpError(400), members message + fieldList. Recorded behavior: a constrained-member violation on this operation is refused 400 ValidationException whose message is "1 validation error detected: Value at '<member>' failed to satisfy constraint: Member must satisfy <constraint phrase>". Its FIXED text is "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy " plus the constraint phrase ("regular expression pattern: " / "enum value set: "); its VARIABLE parts are the member path (libraryArn / entityType, from the request) and the constraint itself (the pattern, rendered WITHOUT the ^ and $ anchors, or the enum value list) taken from the model. There is deliberately NO rendering of the offending value between "Value" and "at".
Emulator: status 400 and code ValidationException are correct, and the pattern is correctly rendered unanchored, but the message inserts the rejected value: "1 validation error detected: Value '<the rejected ARN>' at 'libraryArn' failed to satisfy constraint: Member must satisfy regular expression pattern: arn:aws(|-cn|-iso|-iso-[a-z]|-us-gov):bedrock:[a-zA-Z0-9-]*:[0-9]{12}:data-automation-library/[a-zA-Z0-9-]{12,36}", and likewise "Value '<the rejected entityType>' at 'entityType' failed to satisfy constraint: Member must satisfy enum value set: [...]". The quoted values are whatever the request sent; the requirement is that no value is rendered at all.
Why: a client or conformance test comparing the refusal against AWS's value-suppressed message never matches, so the validation contract of this operation cannot be asserted; the message length also becomes a function of the request payload, where AWS's is bounded by the model, and any caller that logs the error body now records request content AWS deliberately withholds. The status and the code are right, so the defect is invisible until the text is compared.
Fix: the shared ValidationException message builder in the centralized validate phase that renders constraint violations for this service's INPUT_SCHEMAs (the same builder Cause 6/8 of the issue named above indicts) — emit "Value at '<member>'" with no offending value for pattern and enum violations.
Traces: bedrock-data-automation.invoke-ingestion-job-wrong-arn-type-rejected, bedrock-data-automation.ingestion-job-invalid-entity-type-rejected.

=== Cause 2 of 2: the EntityType enum set is [VOCABULARY] where AWS's is [VOCABULARY, RECOGNIZED_PERSON] ===
AWS: Recorded behavior only (the on-disk Smithy model is stale here): the enum-violation refusal for entityType reports "Member must satisfy enum value set: [VOCABULARY, RECOGNIZED_PERSON]", i.e. AWS admits BOTH VOCABULARY and RECOGNIZED_PERSON as library entity types. The checked-in model declares com.amazonaws.bedrockdataautomation#EntityType with values [VOCABULARY] only, which is what the emulator's generated input schema enforces.
Emulator: the refusal for an out-of-set entityType reports "Member must satisfy enum value set: [VOCABULARY]" — the advertised value set omits RECOGNIZED_PERSON, and because the same set drives admission, a well-formed request naming entityType=RECOGNIZED_PERSON is refused 400 ValidationException where AWS accepts it.
Why: this is an over-strict refusal on the admission axis, not just a wording difference: a client that ingests recognized-person entities (and the GetDataAutomationLibraryEntity / ListDataAutomationLibraryIngestionJobs reads scoped by that entityType) cannot use the service at all against the emulator, and the message it gets names a value set its own SDK model contradicts, so it concludes its request was malformed rather than that the service is wrong.
Fix: the EntityType enum value set used by this service's generated types/input schema (refresh it to the recorded AWS set) and the enum-violation rendering that reports it, in the same validate phase as Cause 1; the ingestion handler must then accept RECOGNIZED_PERSON alongside VOCABULARY.
Traces: bedrock-data-automation.ingestion-job-invalid-entity-type-rejected.
