# DocDB read-only catalog responses serve a hand-authored catalog instead of the RDS-shared one AWS returns

> _Note: this issue was identified against the code base at commit `30059ba7efbea1c9406793a7f2ccf8806d86986b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions

## Description
Amazon DocumentDB is served by the shared Amazon RDS query API (the docdb Smithy service is com.amazonaws.docdb, sdkId `docdb`, bound to the amazonrdsv19 wire). Its three read-only catalog operations — DescribeDBEngineVersions, DescribeEventCategories and DescribeOrderableDBInstanceOptions — return the catalog that RDS publishes for engine `docdb`. The emulator answers all three with HTTP 200 and a well-formed awsQuery envelope, but the catalog *inside* each envelope is an emulator-authored approximation: every element of the returned list diverges from the recorded AWS catalog, in membership, in per-element member set and in order. This is one fault — three catalog tables that were written by hand rather than derived from the published docdb catalog — with three causes, one per operation.

Cause 1 of 3: DescribeDBEngineVersions returns a different engine-version catalog.
  AWS: DescribeDBEngineVersions (Smithy: input DescribeDBEngineVersionsMessage, output DBEngineVersionMessage.DBEngineVersions -> DBEngineVersionList, no modeled errors) returns one DBEngineVersion per published docdb engine version. Recorded behavior only for the catalog contents (the model documents the members, not the rows): each row carries Engine=docdb, EngineVersion, MajorEngineVersion/MinorEngineVersion split out of it, DBParameterGroupFamily naming that version's family (a 3.6.x row carries docdb3.6), DBEngineVersionDescription "Amazon DocumentDB (with MongoDB compatibility)", SupportedCACertificateIdentifiers (rds-ca-rsa4096-g1, rds-ca-rsa2048-g1), SupportsCertificateRotationWithoutRestart, and the RDS-shared feature flags SupportsBabelfish, SupportsRDSProxy, SupportsGlobalDatabases, SupportsParallelQuery, SupportsDataGroups, SupportsReadReplica, SupportsCluster and SupportsLimitlessDatabase; plus a ValidUpgradeTarget list holding every higher version reachable from that row, each target carrying Engine, EngineVersion, MajorEngineVersion/MinorEngineVersion, Description, AutoUpgrade, IsMajorVersionUpgrade, SupportsSnapshotUpgrade and SupportsDataGroups. The row ordering is the catalog's own, oldest major first.
  Emulator: status matches (200 -> 200) but the body does not: the replay reports every one of the eight entries $.DescribeDBEngineVersionsResponse.DescribeDBEngineVersionsResult.DBEngineVersions.DBEngineVersion[0]..[7] as diverging, with index [0] (the docdb3.6/3.6.0 row with its ValidUpgradeTarget chain into 5.0.x and 8.0.x) absent from the emulator's list at that position. The emulator's list is a different set of rows carrying a different member set, not a reordering of the same rows.
  Why: version selection is driven off this call. A client that picks an EngineVersion, derives the matching DBParameterGroupFamily for CreateDBClusterParameterGroup, or plans an upgrade from ValidUpgradeTarget reads a version list that does not exist on AWS — it either offers an unavailable version or refuses an available one, and its upgrade plan targets versions AWS never advertised as reachable.
  Fix: the docdb DescribeDBEngineVersions handler's static catalog table (and the projection that serialises DBEngineVersion, which is missing the RDS-shared feature-flag members).
  Traces: docdb-catalog-describe-db-engine-versions#task#1.

Cause 2 of 3: DescribeEventCategories returns a different source-type/category catalog.
  AWS: DescribeEventCategories (Smithy: output EventCategoriesMessage.EventCategoriesMapList -> list of EventCategoriesMap{SourceType, EventCategories}, no modeled errors) returns one map per event source type the shared RDS catalog publishes, each with that source type's full category list. Recorded behavior only for the rows: the recorded catalog leads with SourceType `db-snapshot` carrying EventCategories notification, creation, deletion, restoration; `db-instance` carries sixteen categories (backup, deletion, availability, creation, low storage, restoration, configuration change, failover, maintenance, failure, notification, read replica, recovery, security, backtrack, security patching); `db-cluster` carries failover, migration, failure, notification, serverless, creation, deletion, maintenance, configuration change, global-failover; `db-proxy` carries creation, configuration change, deletion, failure. Both the order of the maps and the order of categories within a map are the catalog's own, not alphabetical.
  Emulator: status matches (200 -> 200) but nine of the eleven maps diverge — $.DescribeEventCategoriesResponse.DescribeEventCategoriesResult.EventCategoriesMapList.EventCategoriesMap[0],[1],[2],[4],[5],[7],[8],[9],[10]. The emulator leads with `db-instance` rather than `db-snapshot`; its `db-cluster` row omits the categories migration, serverless and global-failover; and it alphabetises the categories within each map, so even the row whose content matches (`db-proxy`: expected creation, configuration change, deletion, failure; got configuration change, creation, deletion, failure) diverges on order.
  Why: a client subscribing to events (CreateEventSubscription takes SourceType plus EventCategories validated against this catalog) cannot subscribe to a category the emulator does not publish — db-cluster `global-failover`, `migration` and `serverless` are unreachable — and a client that renders or diffs the catalog positionally sees a different table than AWS serves. Note the related, already-open issue "DocDB error responses use emulator-authored messages instead of AWS wording" (20261029T193448Z-docdb-error-responses-use-emulator-authored-messages-instead.md), which owns the *refusal* message that enumerates valid source types; it does not cover this success-path catalog.
  Fix: the docdb DescribeEventCategories handler's static source-type/category table, which must preserve the published order rather than sorting.
  Traces: docdb-catalog-describe-event-categories#task#1.

Cause 3 of 3: DescribeOrderableDBInstanceOptions returns a different orderable-option catalog.
  AWS: DescribeOrderableDBInstanceOptions (Smithy: input requires Engine, output OrderableDBInstanceOptionsMessage.OrderableDBInstanceOptions -> OrderableDBInstanceOptionsList, no modeled errors) returns one OrderableDBInstanceOption per (EngineVersion, DBInstanceClass, StorageType) the docdb catalog publishes. Recorded behavior only for the rows: each row carries Engine=docdb, EngineVersion, DBInstanceClass, LicenseModel=na, StorageType, Vpc, the AvailabilityZones the class is orderable in, and the RDS-shared capability flags — including SupportsClusters, SupportsGlobalDatabases, SupportsAdditionalStorageVolumes, SupportsHttpEndpoint, SupportsOptimizedReads, SupportsOptimizedWrites, SupportsKerberosAuthentication, SupportsDedicatedLogVolume, SupportedNetworkTypes (IPV4, DUAL), AvailableProcessorFeatures, RequiresCustomProcessorFeatures and OutpostCapable. For docdb rows the recording shows MultiAZCapable, ReadReplicaCapable and SupportsEnhancedMonitoring all false, and the AvailabilityZones list covering four zones in the region.
  Emulator: status matches (200 -> 200) but all sixty-six entries diverge, $.DescribeOrderableDBInstanceOptionsResponse.DescribeOrderableDBInstanceOptionsResult.OrderableDBInstanceOptions.OrderableDBInstanceOption[0]..[65]. For the db.r5.12xlarge/5.0.0 row the emulator reports MultiAZCapable=true, ReadReplicaCapable=true and SupportsEnhancedMonitoring=true where AWS reports false for all three; it lists one fewer Availability Zone than the region's catalog advertises; it emits a member AWS does not return for docdb (SupportsStorageAutoscaling); and it omits the capability members listed above (SupportsClusters, SupportsAdditionalStorageVolumes, SupportsHttpEndpoint, SupportsOptimizedReads, SupportsOptimizedWrites, SupportsKerberosAuthentication, SupportsDedicatedLogVolume, SupportedNetworkTypes, AvailableProcessorFeatures, RequiresCustomProcessorFeatures).
  Why: this is the call a client makes before CreateDBInstance to decide what it is allowed to order. Inverted capability flags make the emulator advertise read replicas and Multi-AZ for a docdb instance class that cannot have them, so a client builds a cluster topology AWS rejects; a short AvailabilityZones list makes it refuse to place an instance in a zone that is in fact orderable; and the missing capability members break any client that branches on them (they read as absent/false).
  Fix: the docdb DescribeOrderableDBInstanceOptions handler's static option catalog plus the OrderableDBInstanceOption projection/serializer that drops the RDS-shared capability members.
  Traces: docdb-catalog-describe-orderable-db-instance-options#task#1.
