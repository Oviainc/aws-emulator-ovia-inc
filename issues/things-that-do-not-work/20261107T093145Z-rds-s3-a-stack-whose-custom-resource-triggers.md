# rds__s3: a stack whose Custom:: resource triggers RDS StartExportTask never settles — the snapshot-export-via-custom-resource check hangs to its 60 s budget instead of reaching a terminal stack status

> _Note: this issue was identified against the code base at commit `1fc9adf30749f0c6ab9c43ee9fd19368a01a782d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartExportTask

## Description
One net-new root cause in the rds__s3 behavioral suite. Every other failing rds__s3 check is already owned by an open issue or blocked by an already-filed unimplemented-operation issue; this one is not covered by any of them.

Cause 1 of 1: a CloudFormation stack whose `Custom::RdsExportTrigger` resource is backed by a Lambda ServiceToken that calls RDS StartExportTask never reaches a terminal CREATE status, so the whole snapshot-export-driven-by-a-custom-resource path produces no answer at all.

AWS: CreateStack on a template containing a Lambda-backed `Custom::<Type>` resource always terminates. CloudFormation invokes the ServiceToken function with the Create provider request, the provider PUTs its `{"Status": "SUCCESS"|"FAILED", ...}` document to the presigned ResponseURL, and the stack settles — CREATE_COMPLETE when the provider answers SUCCESS, or CREATE_FAILED followed by ROLLBACK_COMPLETE when it answers FAILED or does not answer inside the resource's timeout. After CREATE_COMPLETE, `Fn::GetAtt` on the custom resource resolves the key the provider returned in its `Data` object (here `S3Arn`), and the stack's Outputs carry those resolved values. For the RDS leg, Smithy (com-amazonaws-rds-amazonrdsv19) models StartExportTask with required ExportTaskIdentifier, SourceArn, S3BucketName, IamRoleArn and KmsKeyId, and with the modeled refusals DBSnapshotNotFoundFault (404, awsQueryError code `DBSnapshotNotFound`), DBClusterSnapshotNotFoundFault (404), ExportTaskAlreadyExistsFault (400, `ExportTaskAlreadyExists`), IamRoleNotFoundFault (404, `IamRoleNotFound`), IamRoleMissingPermissionsFault (400, `IamRoleMissingPermissions`), InvalidS3BucketFault (400), InvalidExportOnlyFault (400), InvalidExportSourceStateFault (400) and KMSKeyNotAccessibleFault (400); on success it returns an ExportTask whose Status then progresses through STARTING / IN_PROGRESS to a terminal COMPLETE (or FAILED/CANCELED with FailureCause) as reported by DescribeExportTasks. Either way the caller gets an answer — a 200 with an ExportTask or one of those coded faults — so the custom resource can always report SUCCESS or FAILED and the stack can always settle.

Emulator: the check never reaches a single one of its assertions. The replayed result is only `Error: Check timed out after 60.0s`. The flow it exercises is CreateDBInstance -> poll DescribeDBInstances to `available` -> CreateDBSnapshot -> poll DescribeDBSnapshots to `available` -> CreateStack of a template containing an S3 bucket, a KMS key, two IAM roles, a python3.12 Lambda and the `Custom::RdsExportTrigger` resource -> poll DescribeStacks for a terminal status -> read Outputs `BucketName` and `ResolvedS3Arn` (`Fn::GetAtt [TriggerResource, S3Arn]`) -> poll DescribeExportTasks for a terminal export status -> ListObjectsV2. No terminal stack status, no resolved Output and no terminal export status is ever observed: the check is still polling when its budget expires. This is the ONLY rds__s3 check that carries a Custom:: resource and the only one that hangs rather than failing on an assertion or an error response, so the stall is specific to the custom-resource settling path rather than to the suite's budget. Hypothesis: the Lambda-backed Custom:: provider is never invoked (or its ResponseURL callback is never ingested), so the resource sits non-terminal forever and DescribeStacks keeps answering a non-terminal CREATE status; a secondary contributor is that RDS StartExportTask is an unimplemented scaffold stub in this build, which is what the provider would call. Note that even a refused StartExportTask must not produce a hang: the provider would then answer FAILED and AWS would roll the stack back to ROLLBACK_COMPLETE, which the check would report as an assertion failure rather than a timeout.

Why: a client that deploys a stack is entitled to a stack that finishes. Here CreateStack never resolves, so any caller — a CI pipeline, a CDK/CFN deploy, a wait-for-stack poller — blocks indefinitely rather than seeing either a completed stack or a rollback with a CREATE_FAILED ResourceStatusReason it can act on. Nothing downstream of the stack is reachable: `Fn::GetAtt` on the custom resource yields no S3 ARN, the export task is never started or observable through DescribeExportTasks, and no S3 objects are written. The failure mode is also the worst kind for an emulator — an unbounded wait instead of a diagnosable error.

Fix: the CloudFormation custom-resource provisioner that drives `Custom::<Type>` resources with a Lambda ServiceToken — the component that invokes the provider function with the Create request, accepts the provider's response document on the presigned ResponseURL, and transitions the resource to CREATE_COMPLETE (recording the provider's Data for Fn::GetAtt) or CREATE_FAILED with a rollback. It must bound the wait so a provider that never answers lands the stack in a terminal status instead of leaving the stack non-terminal. Paired with it, the RDS StartExportTask handler and its DescribeExportTasks state (the export-task state the provider's call creates and the status progression DescribeExportTasks reports) must answer — either a modeled ExportTask or one of the modeled faults above — so the provider has something to report.

Related already-open issues that do NOT cover this one (different services, different replay keys), named here only so the fixer can reuse their work: 20261105T152359Z-cloudformation-iam-lambda-s3-cloudformation-a-stack-whose-only-resource-is-a.md and 20261105T153010Z-apigateway-cloudformation-lambda-3-net-new-causes-a.md describe the same class of non-settling Lambda-backed Custom:: resource in other services; 20261029T072224Z-rds-s3-startexporttask-is-an-unimplemented-scaffold-stub.md and 20261103T040901Z-rds-s3-rds-startexporttask-answers-501-notimplemented-so.md cover the StartExportTask stub reached directly by SDK, not through a stack.

## Evidence
Failing check: rds__s3.deploy-cfn-rds-export-task-custom-resource-positive — verdict [mismatch].

Replay detail, verbatim and complete:
    Error: Check timed out after 60.0s

Expected (AWS): CreateStack on the check's template (AWS::S3::Bucket, AWS::KMS::Key, two AWS::IAM::Role, AWS::Lambda::Function runtime python3.12 handler index.handler, and Custom::RdsExportTrigger whose ServiceToken is Fn::GetAtt [TriggerFunction, Arn]) reaches a TERMINAL stack status. On the happy path DescribeStacks reports CREATE_COMPLETE; Outputs carry BucketName (Ref ExportBucket) and ResolvedS3Arn (Fn::GetAtt [TriggerResource, S3Arn]) equal to arn:aws:s3:::<that bucket>; DescribeExportTasks(ExportTaskIdentifier=<id>) then reports Status COMPLETE and ListObjectsV2(Bucket=<bucket>, Prefix=<id>) returns KeyCount > 0. If the provider answers FAILED instead, DescribeStacks reports CREATE_FAILED/ROLLBACK_COMPLETE and DescribeStackEvents carries the provider's Reason on the custom resource's CREATE_FAILED event. If StartExportTask is to be refused, it must be refused with one of its modeled faults — e.g. HTTP 404 DBSnapshotNotFound, HTTP 404 IamRoleNotFound, HTTP 400 IamRoleMissingPermissions, HTTP 400 InvalidS3BucketFault, HTTP 400 KMSKeyNotAccessibleFault — whose fixed text is the AWS sentence for that class and whose variable parts (the snapshot ARN, role ARN, bucket name, KMS key id) come from the request; the per-run snapshot/role/bucket/key identifiers in any single recording are template fillers, not part of the requirement.

Actual (emulator): no terminal stack status, no resolved Output, no export-task status and no S3 listing are ever observed. The check is still polling DescribeStacks / DescribeExportTasks when the harness budget of 60.0 s elapses, so not one of its assertions is reached. No HTTP status or error code is produced at all for the stack's terminal state — the divergence is the absence of any terminal answer, i.e. an unbounded wait where AWS always terminates.

Corroboration that this is not a generic budget problem: all 91 other failing rds__s3 checks in this replay reached an assertion or an error response (and are each already owned by an open issue or already filed as blocked by an unimplemented operation). This check is the only rds__s3 check that deploys a Lambda-backed Custom:: resource, and the only one whose failure is a timeout.

## Steps to Reproduce
1. Build and boot the emulator from this checkout and point an AWS SDK/CLI at it.
2. rds.create_db_subnet_group over the run's subnets; rds.create_db_instance(Engine="mysql", DBInstanceClass="db.t3.micro", AllocatedStorage=20, MasterUsername="admin", MasterUserPassword=<password>, BackupRetentionPeriod=1, DBSubnetGroupName=<that group>) and poll rds.describe_db_instances until DBInstanceStatus == "available".
3. rds.create_db_snapshot(DBInstanceIdentifier=<db>, DBSnapshotIdentifier=<snap>) and poll rds.describe_db_snapshots until Status == "available"; keep DBSnapshotArn.
4. cloudformation.create_stack with Capabilities [CAPABILITY_IAM, CAPABILITY_NAMED_IAM] and a template containing: AWS::S3::Bucket; AWS::KMS::Key with a root-allow KeyPolicy; an AWS::IAM::Role trusting export.rds.amazonaws.com with s3:PutObject*/GetObject*/ListBucket/DeleteObject*/GetBucketLocation on the bucket and kms:CreateGrant/DescribeKey/Encrypt/Decrypt/GenerateDataKey* on the key; an AWS::IAM::Role trusting lambda.amazonaws.com with rds:StartExportTask and iam:PassRole; an AWS::Lambda::Function (Runtime python3.12, Handler index.handler, inline ZipFile) whose handler calls rds.start_export_task(ExportTaskIdentifier, SourceArn=<snapshot ARN>, S3BucketName=Ref bucket, IamRoleArn=GetAtt export role Arn, KmsKeyId=Ref key) and then PUTs its SUCCESS/FAILED document to event['ResponseURL']; and a Custom::RdsExportTrigger whose ServiceToken is GetAtt [TriggerFunction, Arn] carrying those properties. Declare Outputs BucketName = Ref bucket and ResolvedS3Arn = Fn::GetAtt [TriggerResource, S3Arn].
5. Poll cloudformation.describe_stacks(StackName=<stack>) for StackStatus in {CREATE_COMPLETE, CREATE_FAILED, ROLLBACK_COMPLETE, ROLLBACK_FAILED}.
   Observed: no terminal status is ever reported; the poll never exits and the check is killed at its 60 s budget. Expected: a terminal status — CREATE_COMPLETE with both Outputs resolved, or CREATE_FAILED/ROLLBACK_COMPLETE with the provider's Reason on the custom resource's CREATE_FAILED stack event.
6. (Unreachable today) rds.describe_export_tasks(ExportTaskIdentifier=<id>) should report a terminal Status COMPLETE, and s3.list_objects_v2(Bucket=<Outputs.BucketName>, Prefix=<id>) should return KeyCount > 0.
