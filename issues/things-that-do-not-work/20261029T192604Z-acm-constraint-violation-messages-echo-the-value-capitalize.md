# ACM constraint-violation messages echo the value, capitalize the member path and sort enum value sets alphabetically (2 causes)

> _Note: this issue was identified against the code base at commit `8d5a4f803a514b21e009b483e221bcf8b3c8087d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchCertificates

## Description
Two root causes in the shared constraint-violation message builder behind ACM's ValidationException: the envelope is assembled differently from AWS's, and the enum value set inside it is rendered in a different order. HTTP 400 and the ValidationException code are correct in both; only the message text diverges. Related open filings, neither of which carries these fixture steps as a replay key: 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md cause 7 records the value-echoing/anchored-pattern half of this rule from the BEHAVIORAL suite (check ids only, and for RequestCertificate/ListTagsForResource members, not these two), and 20261029T190010Z-acm-pca-constraint-violation-messages-omit-aws-s.md records the analogous defect in the separate ACM PCA service.

Cause 1 of 2: a SearchCertificates enum violation echoes the submitted value and renders the member path in upper camel case.
AWS: Smithy SearchCertificates(FilterStatement: CertificateFilterStatement, ...) models ValidationException (client, 400) and CertificateType is an enum with values IMPORTED, AMAZON_ISSUED, PRIVATE. Recorded behavior: an unknown type in the metadata filter is refused 400 ValidationException with "1 validation error detected: Value of the input at '<memberPath>' failed to satisfy constraint: Member must satisfy enum value set: [PRIVATE, IMPORTED, AMAZON_ISSUED]". Three rules make up that template: (a) the offending value is NOT echoed — the phrase is the fixed 'Value of the input at'; (b) the member path is the wire/lower-camel path of the member, dot-joined from the input root ('filterStatement.filter.acmCertificateMetadataFilter.type'), not the shape-member names in upper camel; (c) the enum value set is rendered in a fixed service-side order which is neither alphabetical nor the Smithy declaration order. The member path is the variable part, taken from the request's offending member; everything around it is fixed text.
Emulator: "1 validation error detected: Value 'NOT_A_REAL_TYPE' at 'FilterStatement.Filter.AcmCertificateMetadataFilter.Type' failed to satisfy constraint: Member must satisfy enum value set: [AMAZON_ISSUED, IMPORTED, PRIVATE]" — it splices the submitted value in, upper-camel-cases every path segment, and sorts the enum set alphabetically.
Why: the message is produced by a known rule, so the rule is the requirement. A client or test that parses ACM's envelope to report which input member was wrong reads the path out of a fixed offset and gets a value instead of a member on the emulator; the upper-camel path does not match the member names a client sends on the wire, so a path-to-field mapping fails; and echoing the submitted value reflects request content back into error logs, which ACM never does.
Fix: the shared constraint-violation message builder for this service's ValidationException — emit the fixed 'Value of the input at' phrase, render the lower-camel wire member path, and render the enum value set in the service's fixed order rather than sorting it.
Traces: acm-certificate-list-and-search-error-paths#task#4 (cluster of 2, with acm-multi-certificate-listing-and-search#task#5).

Cause 2 of 2: a ListCertificates enum violation builds the correct envelope but still sorts the enum value set alphabetically.
AWS: Smithy ListCertificates(CertificateStatuses: CertificateStatuses, ...) models ValidationException (client, 400); CertificateStatus is an enum with values PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED. Recorded behavior: an unknown status in the list is refused 400 ValidationException with "1 validation error detected: Value of the input at 'certificateStatuses' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [VALIDATION_TIMED_OUT, PENDING_VALIDATION, EXPIRED, INACTIVE, ISSUED, FAILED, REVOKED], Member must not be null]" — the nested 'Member must satisfy constraint: [...]' form is used because the violation is on a list member, and the value set is again in a fixed service-side order that is neither alphabetical nor the declaration order.
Emulator: everything matches except the value set, which comes back as [PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED].
Why: the whole message is fixed text apart from the member path, so a client or fixture comparing ACM's refusal text byte-for-byte diverges on every bad status list even though code and status are right. That this leg gets the envelope right and only the ordering wrong shows the ordering is a separate defect from cause 1's envelope — fixing the envelope alone leaves this one failing. Hypothesis: the emulator derives the list from a sorted or Smithy-declaration iteration of the enum, while ACM renders a fixed per-enum order.
Fix: the enum-value-set rendering inside the same shared constraint-violation builder — carry the service's fixed order per enum instead of sorting or re-using declaration order.
Traces: acm-multi-certificate-listing-and-search#task#4.
