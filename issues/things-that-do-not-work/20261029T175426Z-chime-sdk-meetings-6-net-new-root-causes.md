# chime-sdk-meetings: 6 net-new root causes — MeetingArn encodes MediaRegion, CreateAttendee is not idempotent on ExternalUserId and admits the reserved 'aws:' prefix, three refusals use the wrong class/wording

> _Note: this issue was identified against the code base at commit `a1be48b455f77208774c140f08575194e8ab84c8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAttendee

## Description
This issue bundles 6 CAUSES, all in the chime-sdk-meetings emulator (crate services/service-com-amazonaws-chimesdkmeetings-chimemeetingssdkservice). Each cause is independent and each has its own failing behavioral check; a fixer must close ALL SIX before submitting. None of them is covered by the one open chime-sdk-meetings issue (20261029T170604Z-chime-sdk-meetings-meeting-projection-diverges-screenviewingurl-template-and-absent-tenantids.md), which is about MediaPlacement.ScreenViewingUrl's query string and the absent Meeting.TenantIds member only — neither the ARN's region label nor any of the attendee/tagging behaviour below.

Cause 1 of 6: Meeting.MeetingArn encodes the meeting's MediaRegion instead of the Region the control-plane endpoint serves.
AWS: Smithy says Meeting$MeetingArn targets AmazonResourceName @length(1..1011) @pattern(^arn:) and documents only "The ARN of the meeting", while Meeting$MediaRegion is documented as "The Region in which you create the meeting" (a media-placement parameter) — so the format requirement is recorded behavior only: the meeting's ARN is arn:aws:chime:<endpoint-region>:<account-id>:meeting/<MeetingId>, i.e. the fixed text `arn:aws:chime:`, then the Region of the endpoint/credentials the call was signed for, then the caller's account id, then the fixed text `:meeting/` and the minted MeetingId. MediaRegion is an independent request parameter and never appears in the ARN. Status 200, no error code.
Emulator: serves 200 with the ARN's Region field filled from the request's MediaRegion. With the endpoint Region us-west-2 and MediaRegion us-east-1 the check reports: expected MeetingArn 'arn:aws:chime:us-west-2:<account>:meeting/<meeting-guid>' (region+account+meeting-id encoded), got 'arn:aws:chime:us-east-1:<account>:meeting/<meeting-guid>'. (The concrete Region names, account id and GUID here are per-run values; the requirement is that the ARN's Region segment is the endpoint Region, not MediaRegion.)
Why: a client that derives the meeting's ARN from its own Region/account (for tagging, IAM resource conditions, cross-service references, or an equality check against a stored ARN) builds a different string from the one the emulator hands back, so every ARN comparison and every tagging call keyed on a client-built ARN diverges whenever MediaRegion differs from the endpoint Region.
Fix: the shared ARN derivation this service's state module exposes, which the create handler and every reader project from — it takes the media region as its region argument (see Traces for the citation). It must take the endpoint/signing Region instead.
Traces: chime-sdk-meetings.create-meeting-returns-full-meeting-fields

Cause 2 of 6: CreateAttendee is not idempotent on ExternalUserId — a repeat call mints a second attendee.
AWS: Smithy documents CreateAttendeeRequest$ExternalUserId (ExternalUserId, @length 2..64, @sensitive) as "The Amazon Chime SDK external user ID. An idempotency token. Links the attendee to an identity managed by a builder application." Two CreateAttendee calls with the same ExternalUserId in the same meeting therefore return the SAME attendee: the same AttendeeId and the same JoinToken, and ListAttendees shows exactly one attendee for that ExternalUserId. Status 200 on both calls, no error code.
Emulator: both calls answer 200 but each mints a fresh AttendeeId and a fresh JoinToken for the same ExternalUserId, so the meeting ends up with two attendees for one external identity. The check reports two Attendee objects with the same ExternalUserId and different AttendeeId/JoinToken values.
Why: a client that retries CreateAttendee (a timeout, an at-least-once job, a reconnecting participant) relies on the ExternalUserId idempotency token to get its existing attendee back. Against the emulator it silently creates duplicate attendees, double-counts against the meeting's attendee ceiling, and the JoinToken it already handed to the participant is no longer the one the newest record carries.
Fix: the CreateAttendee handler (services/.../src/ops/create_attendee.rs) plus the per-meeting attendee store it writes — resolve an existing attendee by ExternalUserId within the meeting and return it instead of minting, the same way CreateMeeting already resolves ClientRequestToken through meeting_by_client_request_token.
Traces: chime-sdk-meetings.create-attendee-duplicate-external-user-id-allowed

Cause 3 of 6: CreateAttendee accepts an ExternalUserId beginning with the reserved 'aws:' prefix.
AWS: the model's CreateAttendee documentation for ExternalUserId states "Values that begin with aws: are reserved. You can't configure a value that uses this prefix." (the same sentence the model carries on Meeting$ExternalMeetingId). AWS refuses such a request with BadRequestException (modeled errorKind client, httpError 400) and creates nothing; the message is the fixed text "Validation error for ExternalUserId, prefix 'aws:' is reserved." — fully fixed text, with the member name ExternalUserId naming the offending input member. No attendee appears in ListAttendees afterwards.
Emulator: answers 200 and mints an attendee whose ExternalUserId is the reserved value (observed: ExternalUserId 'aws:reserved-user' with a minted AttendeeId, JoinToken and default Capabilities). No validation of the reserved prefix exists in the handler's input checks.
Why: this is overly permissive — a client can create attendees in a namespace AWS reserves for itself. Code that is rejected in production passes against the emulator, so the reserved-prefix failure path is never exercised, and the emulator's store holds identities real AWS would never admit.
Fix: CreateAttendee's input validation (services/.../src/ops/create_attendee.rs, before anything is minted), raising the modeled BadRequestException with AWS's fixed message text; the reserved-prefix rule belongs beside the other request-level rules in this service's state module so CreateMeeting's ExternalMeetingId can share it.
Traces: chime-sdk-meetings.create-attendee-reserved-external-user-id-rejected

Cause 4 of 6: the capability-conflict BadRequestException carries bespoke emulator prose instead of AWS's message.
AWS: the model's AttendeeCapabilities documentation states "You can't set content capabilities to SendReceive or Receive unless you also set video capabilities to SendReceive or Receive. If you don't set the video capability to receive, the response will contain an HTTP 400 Bad Request status code." AWS refuses with BadRequestException (400) and the message "Attendee's video capability must be set to either SendReceive or Receive when setting content capability to SendReceive or Receive." — that is entirely FIXED text: it names the two capability members and the two admissible values generically and interpolates nothing from the request.
Emulator: the status (400) and the error code (BadRequestException) are right, but the message is generated prose that interpolates the request's values: "Capabilities.Content Receive requires Capabilities.Video to be SendReceive or Receive, not Send" (built in this service's state module's capability_problem; see Traces). Same divergence class applies to that function's other two messages for the Video:MaxResolution:None and Content:MaxResolution:None corner cases, which are likewise bespoke prose.
Why: a client (or a test, or a support runbook) that matches on the error message to distinguish the content/video capability conflict from the other two 400s this operation raises never matches against the emulator, and a message templated from request values is not the stable text AWS serves.
Fix: the capability validation's message construction in this service's state module (capability_problem) — serve AWS's fixed sentence for the content-requires-video rule rather than composing a per-request sentence.
Traces: chime-sdk-meetings.create-attendee-content-capability-without-video-rejected

Cause 5 of 6: reads and mutations of a DELETED attendee are refused as NotFoundException instead of ForbiddenException with AWS's wording.
AWS: after DeleteAttendee, GetAttendee (and a mutation such as UpdateAttendeeCapabilities) for that AttendeeId in the still-live meeting is refused with ForbiddenException — modeled errorKind client, httpError 403, documented "The client is permanently forbidden from making the request" — and both operations list it among their errors. The message is "Attendee <ATTENDEE_ID> is not in the meeting <MEETING_ID>": the fixed text `Attendee <`, `> is not in the meeting <`, `>` with the AttendeeId and MeetingId taken from the request. AWS classifies access to a deleted attendee's record as revoked, not as an unknown id.
Emulator: refuses with NotFoundException (HTTP 404, Code "NotFound") and the message "Attendee <ATTENDEE_ID> not found", built by the shared not_found()/attendee_not_found() helper in this service's state module. The check reports got code='NotFoundException' where ForbiddenException was required. (The removal from ListAttendees itself is correct.)
Why: a client branches on the error class — 404/NotFoundException reads as "wrong id, re-resolve and retry", while 403/ForbiddenException reads as "this attendee is gone for good, stop retrying and re-join". Against the emulator a deleted attendee drives retry loops that production would terminate, and any code keyed on ForbiddenException never runs.
Fix: the attendee-resolution path shared by GetAttendee/DeleteAttendee/UpdateAttendeeCapabilities (services/.../src/ops/*, resolving through attendee_not_found in this service's state module) — an AttendeeId that is absent from a LIVE meeting must raise the modeled ForbiddenException with AWS's wording, and a new ForbiddenException payload constructor belongs beside the existing not_found helpers.
Traces: chime-sdk-meetings.delete-attendee-invalidates-and-removes-from-list

Cause 6 of 6: tagging calls on a DELETED meeting's ARN succeed (or refuse with the wrong class) instead of BadRequestException "Invalid meeting id".
AWS: a meeting's tags live only as long as the meeting. Once DeleteMeeting has run, ListTagsForResource and TagResource on that same MeetingArn are refused with BadRequestException (modeled errorKind client, httpError 400, documented "The input parameters don't match the service's restrictions"; both operations declare it) and the message "Invalid meeting id" — entirely fixed text, interpolating nothing. Recorded behavior confirms BadRequestException here rather than ResourceNotFoundException.
Emulator: ListTagsForResource on the deleted meeting's ARN answers HTTP 200 with an empty list — observed body {"Tags": []} — so the dangling ARN is treated as a live, untagged resource and no refusal happens at all. The handler's taggable() gate in this service's state module compares the ARN against a STORED meeting's own MeetingArn and delegates the verdict to the family's shared addresses_taggable_resource rule, which admits this ARN; even when the gate does fire it raises ResourceNotFoundException (404), not the required BadRequestException (400). The sibling TagResource call on the same dead ARN is blocked from being observed by this same 200, and must be fixed with it.
Why: a client that uses a successful ListTagsForResource (or TagResource) as proof the meeting still exists is told the meeting is alive after it was deleted, and tags written against a dead ARN accumulate in the shared tag directory where AWS would have rejected the write — a silent state leak plus a wrong liveness signal.
Fix: the ARN-resolution gate shared by ListTagsForResource and TagResource — the taggable() check in this service's state module and the family's shared chime_tags rule it delegates to — must treat an ARN naming a meeting this store no longer holds (including one recorded as ended) as invalid, and the two tagging handlers must raise the modeled BadRequestException with the fixed message "Invalid meeting id".
Traces: chime-sdk-meetings.tag-resource-and-list-tags-roundtrip
