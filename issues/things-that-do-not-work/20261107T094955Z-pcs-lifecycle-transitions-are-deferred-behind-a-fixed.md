# pcs lifecycle transitions are deferred behind a fixed 500 ms wall-clock span, so every create/delete wait costs a client a full polling interval and a multi-stage cluster/node-group/queue teardown never converges in budget

> _Note: this issue was identified against the code base at commit `aadd2c1b1749c5dc18f73d53ca940ec47d9cbcaf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteComputeNodeGroup

## Description
One root cause, grounded in the single surviving failing behavioral check for pcs (the other six pcs failures in this run are marked OWNED by 20261023T123102Z-pcs-fidelity-bundle-5-divergences-not-found-message.md, 20261106T154605Z-pcs-2-net-new-root-causes-resourcenotfoundexception-resourcetype.md and 20261107T062642Z-pcs-createcomputenodegroup-never-enforces-the-iam-instance-profile.md and are skipped here).

Cause 1 of 1: a PCS resource is never settled on the request that immediately follows the call that created or deleted it — the emulator holds the transient status for a fixed 500 ms of WALL CLOCK time — so a client that polls at AWS-scale intervals burns one whole interval per lifecycle wait, and a scenario that sequences six waits (cluster ACTIVE, compute node group ACTIVE, queue ACTIVE, queue gone, node group DELETED, cluster gone) cannot complete. Failing check: pcs.delete-dependents-out-of-order-conflict-rejected (verdict mismatch, 'Check timed out after 60.0s').

AWS: Smithy: ClusterStatus, ComputeNodeGroupStatus and QueueStatus all declare CREATING/ACTIVE/DELETING (ComputeNodeGroupStatus alone declares DELETED), and CreateCluster/CreateComputeNodeGroup/CreateQueue return the resource in CREATING while DeleteQueue/DeleteComputeNodeGroup/DeleteCluster return an empty body and move the resource out of ACTIVE; ConflictException's modeled examples include "A cluster isn't in ACTIVE status" and "A cluster to delete is in an unstable state. For example, because it still has ACTIVE node groups or queues". The model states no timing at all, so: recorded behavior only — on AWS the transition is asynchronous and the caller polls Get* until the status settles. What is NOT part of AWS's contract is a service that has already decided the outcome synchronously and then withholds it from the next read for a span of its own choosing: AWS's delay is the real provisioning work, and a client's poll interval is sized against it. Note the behavior that IS correct here and must be preserved: the two refusals this check targets already match AWS — DeleteComputeNodeGroup while a queue of the cluster assigns jobs to the group answers ConflictException with the fixed sentence "AWS PCS can't delete the compute node group you specified because the cluster has associated queues.", and DeleteCluster with an ACTIVE queue/node group answers ConflictException with the fixed sentence "AWS PCS can't delete the cluster you specified because it has associated queues or compute node groups." (both sentences are entirely fixed text and echo no caller-supplied value; the resource is named by resourceId).

Emulator: every lifecycle change is recorded as a Pending whose due instant is `Instant::now() + TRANSITION_SPAN` with TRANSITION_SPAN = 500 ms, and handlers call state.settle() at entry, which only materialises a change whose wall-clock due instant has already passed. The outcome is already determined when the create/delete returns, but the very next Get* — issued a few milliseconds later over loopback — still reports CREATING / DELETING. A client whose probe-then-sleep loop therefore misses on its first probe pays one full sleep interval for every single transition. The failing check pays 20 s (cluster ACTIVE) + 15 s (node group ACTIVE) + 15 s (queue ACTIVE) + 10 s (queue removed) + 15 s (node group DELETED) + 15 s (cluster removed) = at least 90 s of pure client-side sleeping against an emulator that had each answer ready in half a second, and is killed by the suite's 60 s per-check budget before it finishes. No request in the check is refused and no operation on its path is a stub: the emulator simply never lets the scenario reach its end, so the ordered-teardown positive control (delete queue, then node group, then cluster) is left unverified even though the two ConflictException legs that precede it are correct.

Why: a client written against AWS sizes its polling interval to AWS's provisioning time (tens of seconds), because that is the only sane choice against the real service. Against this emulator that same client takes tens of seconds to observe a transition that already happened, so any workflow that chains more than two or three PCS lifecycle steps — a provisioning script, a CDK/Terraform-style converge loop, an integration test suite, a teardown routine — runs an order of magnitude slower than the work the emulator actually does and trips its own deadlines. The resource states are reported correctly; what is wrong is that observing them requires wall-clock time to pass, so correctness that depends on completing a sequence (here: that the out-of-order deletes are refused AND the in-order deletes then succeed) can never be demonstrated.

Fix: the lifecycle clock in this crate's state module (the TRANSITION_SPAN constant, Pending::in_a_span and the settle() paths on the cluster, compute-node-group and queue records that apply_pending drives, called from the top of every handler). A transition must be settled by the time the NEXT request observes the resource rather than after a wall-clock span — e.g. advance pending changes on request arrival/sequence rather than on Instant::now(), keeping the transient status in the response of the call that starts it (a create still answers CREATING, a delete still leaves DELETING/DELETED observable where the model declares it) so nothing that asserts on the create/delete response changes. The delete-ordering guards themselves (compute_node_group_still_referenced, cluster_still_has_children and the is_being_deleted exclusion they use) are correct and need no change.
