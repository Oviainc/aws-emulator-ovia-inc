# kinesis__lambda: a Kinesis-stream event source mapping never delivers a batch to its function, so all six Kinesis ESM delivery-semantics checks hang to the harness cap

> _Note: this issue was identified against the code base at commit `954781cef49baf7406aef764139782df619c6255`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEventSourceMapping

## Description
One root cause (Cause 1 of 1), grounded in six failing behavioral checks whose check ids lead with the `kinesis__lambda` service token: kinesis__lambda.kinesis-esm-record-envelope-matches-the-put-record, kinesis__lambda.kinesis-esm-filter-on-decoded-json-data-drops-non-matching, kinesis__lambda.kinesis-esm-explicit-hash-key-routes-and-each-shard-stays-ordered, kinesis__lambda.kinesis-esm-parallelization-factor-keeps-each-partition-key-in-order, kinesis__lambda.kinesis-esm-latest-mapping-never-sees-records-put-before-it, kinesis__lambda.esm-at-timestamp-starting-position-withholds-pre-boundary-records. All six are reported "Check timed out after 60.0s" and none is marked ALREADY FILED or OWNED.

=== Cause 1 of 1: the Kinesis event-source poller does not exist — an accepted mapping never invokes the function ===
Failing checks: all six listed above.
AWS: Smithy models CreateEventSourceMapping with EventSourceArn, FunctionName, Enabled, BatchSize, StartingPosition (TRIM_HORIZON | LATEST | AT_TIMESTAMP), StartingPositionTimestamp, MaximumBatchingWindowInSeconds, ParallelizationFactor and FilterCriteria, and reports the mapping's State through GetEventSourceMapping. Recorded behavior (the Kinesis ESM contract, https://docs.aws.amazon.com/lambda/latest/dg/with-kinesis.html): once the mapping reaches Enabled, Lambda polls each shard of the source stream and SYNCHRONOUSLY invokes the function with an event whose `Records` carry, per record, `kinesis.data` = base64 of the exact bytes put, `kinesis.partitionKey` = the PartitionKey of the PutRecord, `kinesis.sequenceNumber`, `kinesis.approximateArrivalTimestamp` (a number), `kinesis.kinesisSchemaVersion` = "1.0", and at record level `eventID` = "<ShardId>:<sequenceNumber>", `eventName` = "aws:kinesis:record", `eventSource` = "aws:kinesis", `eventVersion` = "1.0", `eventSourceARN` = the source stream ARN, `awsRegion` = the stream's region and `invokeIdentityArn` = the function's execution-role ARN. The StartingPosition is honoured: LATEST never delivers a record written before the mapping existed, AT_TIMESTAMP=T never delivers a record whose ApproximateArrivalTimestamp precedes T while delivering every record after it, and TRIM_HORIZON delivers from the oldest untrimmed record. FilterCriteria are applied to the decoded data so non-matching records are dropped without an invocation, ParallelizationFactor shards concurrency while keeping per-partition-key order within a shard, and ExplicitHashKey routing keeps each shard's order intact.
Emulator: nothing is ever delivered. Each check stands up a source stream (ACTIVE), an execution role, a function and an Enabled mapping, puts records, and then polls its observable sink — the second Kinesis stream the handler forwards to, or the S3 keys the handler writes — for the batch; the predicate is never satisfied and every one of the six is cut off at the 60 s harness cap, where a service that delivered promptly would satisfy it in seconds. Because not one batch arrives, NONE of the contracts above is graded: not the record envelope, not the StartingPosition gating (LATEST/AT_TIMESTAMP), not FilterCriteria, not ParallelizationFactor ordering, not ExplicitHashKey routing. Hypothesis: the emulator accepts and stores the mapping but has no poller that reads the source stream's shards and invokes the function, so the mapping is inert; the already-filed Lambda Invoke defect (20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md) would additionally block any invocation a poller did attempt.
Why: Kinesis -> Lambda is the canonical stream-processing wiring. A client gets an Enabled mapping and no error anywhere, while every record it puts is silently never processed; worse, the StartingPosition and FilterCriteria legs are the "nothing should arrive" assertions, so against an emulator that delivers nothing they would pass vacuously once the positive legs are repaired — they are only meaningful alongside a working delivery path.
Fix: a Kinesis event-source poller in the lambda service crate's event-source-mapping machinery — it must, for each Enabled Kinesis mapping, iterate the source stream's shards from the mapping's StartingPosition (honouring StartingPositionTimestamp), build the `aws:kinesis` record envelope above from the stream's stored records and the mapping's function/role, apply FilterCriteria to the decoded data, respect BatchSize / MaximumBatchingWindowInSeconds / ParallelizationFactor, and invoke the target function (which also requires the Invoke path named in the related issue to serve real invocations).
Relationship to already-filed issues: 20261027T001720Z-dynamodb-kinesis-lambda-a-kinesis-stream-event-source.md and 20261029T180026Z-dynamodb-kinesis-lambda-event-source-mappings-are-created-for-non-existent.md describe the same inert-mapping behavior for the `dynamodb__kinesis__lambda` service group and carry only that group's replay keys; 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md covers the Invoke leg. None of them carries any of the six `kinesis__lambda` check ids above, so a fixer closing them would never re-replay these six. This issue exists to carry those keys; if one poller fix serves both groups, close them together.
Traces: kinesis__lambda.kinesis-esm-record-envelope-matches-the-put-record, kinesis__lambda.kinesis-esm-filter-on-decoded-json-data-drops-non-matching, kinesis__lambda.kinesis-esm-explicit-hash-key-routes-and-each-shard-stays-ordered, kinesis__lambda.kinesis-esm-parallelization-factor-keeps-each-partition-key-in-order, kinesis__lambda.kinesis-esm-latest-mapping-never-sees-records-put-before-it, kinesis__lambda.esm-at-timestamp-starting-position-withholds-pre-boundary-records.

## Evidence
All evidence is from the replayed behavioral suite (simparity-behavioral-aws-v1): per-service pass rate kinesis__lambda 1/7 (14%), 6 failed, and every one of the six failures is reported as:
  Error: Check timed out after 60.0s

Expected, per check, within seconds of the PutRecord(s):
- kinesis-esm-record-envelope-matches-the-put-record: the function is invoked and forwards a record whose kinesis.data base64-decodes to the exact bytes put (including the non-UTF8 prefix b"\x00\xff\x80..."), kinesis.partitionKey equals the PartitionKey sent, kinesis.kinesisSchemaVersion == "1.0", kinesis.approximateArrivalTimestamp is numeric, eventID == "<ShardId>:<SequenceNumber>" of the PutRecord response, eventName == "aws:kinesis:record", eventSource == "aws:kinesis", eventVersion == "1.0", eventSourceARN == the source stream ARN, awsRegion == the stream's region, invokeIdentityArn == the execution-role ARN.
- kinesis-esm-filter-on-decoded-json-data-drops-non-matching: matching records are delivered, non-matching ones produce no invocation.
- kinesis-esm-explicit-hash-key-routes-and-each-shard-stays-ordered / kinesis-esm-parallelization-factor-keeps-each-partition-key-in-order: batches arrive and per-shard / per-partition-key order is preserved.
- kinesis-esm-latest-mapping-never-sees-records-put-before-it: post-mapping records are delivered while pre-mapping ones are not.
- esm-at-timestamp-starting-position-withholds-pre-boundary-records: every post-boundary payload is delivered while no pre-boundary payload is, with the boundary verified against each record's server-side ApproximateArrivalTimestamp.

Actual, in all six: the sink (a second Kinesis stream the handler writes to, or the S3 key set the handler writes) stays empty for the whole polling window and the check is cut off at the 60 s cap. The mapping itself was accepted and reported Enabled, and the source stream was ACTIVE with the records readable directly off it — so the records exist and the mapping exists; only the delivery never happens.

## Steps to Reproduce
1. kinesis.create_stream(StreamName=<src>, ShardCount=1) and a second stream <sink>; poll both to ACTIVE.
2. iam.create_role with a lambda.amazonaws.com trust policy and an inline policy allowing kinesis:GetRecords, GetShardIterator, DescribeStream, ListShards on <src> and kinesis:PutRecord on <sink>.
3. lambda.create_function with a handler that, for each event["Records"] entry, forwards the whole record JSON to <sink> (or writes an S3 key named after the decoded payload).
4. lambda.create_event_source_mapping(EventSourceArn=<src arn>, FunctionName=<fn>, StartingPosition='TRIM_HORIZON', BatchSize=10); poll get_event_source_mapping until State == 'Enabled'.
5. kinesis.put_record(StreamName=<src>, Data=b"\x00\xff\x80payload", PartitionKey='pk-1').
6. Poll <sink> (get_shard_iterator TRIM_HORIZON + get_records) for the forwarded record -> it never arrives; the records are still readable directly off <src>, and the mapping still reports Enabled, so neither the stream nor the mapping is the missing piece.
7. Repeat step 4 with StartingPosition='LATEST' (records put before the mapping must not arrive, records put after must), and with StartingPosition='AT_TIMESTAMP' + StartingPositionTimestamp=T between two groups of records (pre-T must not arrive, post-T must), and with FilterCriteria on the decoded JSON data, and with ParallelizationFactor > 1 — none of these can be distinguished from the universal non-delivery until step 6 works.
