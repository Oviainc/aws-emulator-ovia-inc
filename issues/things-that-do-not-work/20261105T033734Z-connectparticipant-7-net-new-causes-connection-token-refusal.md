# connectparticipant: 7 net-new causes — connection-token refusal wording, SendEvent ClientToken dedup ignores Content, typing events persist in the transcript, receipts never attach to their message, and CreateParticipantConnection fails open on an unissued ParticipantToken

> _Note: this issue was identified against the code base at commit `f788da56fca8042d5f8354f4ce9bfd6169341434`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEvent

## Description
Seven distinct root causes in the ConnectParticipant data plane, grounded in the five failing behavioral checks listed in trace_ids (the three checks the report marks ALREADY FILED — UpdateAttachedFilesConfiguration, GetAuthenticationUrl, DescribeView stubs — are excluded). Smithy model consulted: services/service-com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda/smithy-model/com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda.json (sdkId ConnectParticipant, restJson1).

Cause 1 of 7: every connection-token refusal carries emulator-authored message text instead of AWS's. AWS: after DisconnectParticipant, a subsequent SendMessage or GetTranscript on that ConnectionToken is refused AccessDeniedException (Smithy: AccessDeniedException, httpError 403, documented "You do not have sufficient access to perform this action") whose Message is the fixed text "Access denied" — no request- or state-derived parts at all. Emulator: same code and status, but Message "the connection token does not name a connected chat participant". Why: a client that classifies or surfaces the refusal text (or asserts on it, as the recorded behavior does) sees wording AWS never emits; the same wording is used for the unknown/expired-token path and for DescribeView, so every refusal on this service is mis-worded. Fix: the shared connection-token authentication refusal in the operation handlers (services/service-com-amazonaws-connectparticipant-amazonconnectparticipantservicelambda/src/ops/*.rs — e.g. send_event.rs builds AccessDeniedException with this message) must emit AWS's fixed "Access denied" text. Failing check: connectparticipant.disconnect-participant-invalidates-connection-token.

Cause 2 of 7: SendEvent's ClientToken idempotency key omits Content, so a reused ClientToken with DIFFERENT Content replays the first event. AWS (recorded behavior; Smithy marks SendEvent.ClientToken @idempotencyToken, length 0..500, and SendEvent.Content length 1..16384): the dedup key is the pair (ClientToken, Content) and does NOT include ContentType — reusing one ClientToken with the same Content but a different ContentType returns the first event's Id, while reusing it with different Content mints a new, distinct Id. Emulator: the key is "EVENT:<ClientToken>" only, so the third call (same ClientToken, different Content) returned the first call's Id and appended nothing. Why: a client sending a delivered receipt and then a read receipt for a DIFFERENT message under a retried/SDK-populated ClientToken silently loses the second event and is handed an Id belonging to another event. Fix: SendEvent's idempotency keying and its state helper. Failing check: connectparticipant.send-event-client-token-caches-on-content-not-contenttype.

Cause 3 of 7: typing events are persisted as transcript items. AWS (recorded behavior; SendEvent documents application/vnd.amazonaws.connect.event.typing as a supported ContentType but it is transient): SendEvent(typing) answers an Id and a yyyy-MM-ddThh:mm:ss.SSSZ AbsoluteTime, and GetTranscript afterwards holds NO item for it — no item with that Id, no item of Type TYPING, no item whose ContentType is the typing content type. Emulator: GetTranscript lists the typing event as a full item (Type EVENT, ContentType application/vnd.amazonaws.connect.event.typing, the Id SendEvent returned, with ParticipantId/DisplayName/ParticipantRole/ContactId filled in). Why: a client rendering a transcript shows transient typing indicators as permanent chat items, and transcript item counts/pagination diverge from AWS for every chat where typing was sent. Fix: SendEvent's handler must not append a transcript item for the typing ContentType (state append in src/state.rs is called unconditionally from src/ops/send_event.rs). Failing checks: connectparticipant.send-event-typing-appears-as-typing-item, connectparticipant.send-multiple-events-produce-distinct-transcript-ids.

Cause 4 of 7: message-receipt events answer a fresh Id instead of the referenced message's Id. AWS (recorded behavior; SendEvent.Content documents receipt content as a JSON string of the form {"messageId":"<chat item id>"}): SendEvent with ContentType application/vnd.amazonaws.connect.event.message.delivered or ...message.read answers Id equal to the messageId named in Content — the receipt is recorded against that existing message, not stored as a new chat item. Emulator: the delivered receipt answered a newly minted chat-item Id (an Id distinct from the message's), because the handler appends an EVENT item and reports its own new Id. Why: a client correlating a receipt response back to the message it acknowledged gets an Id that names nothing it sent, and the transcript grows one extra item per receipt. Fix: SendEvent's handler must parse the receipt Content, resolve the referenced transcript item and report that item's Id. Failing checks: connectparticipant.send-multiple-events-produce-distinct-transcript-ids, connectparticipant.send-event-client-token-caches-on-content-not-contenttype.

Cause 5 of 7: GetTranscript items carry no MessageMetadata/Receipts, so delivered/read state is unobservable. AWS (recorded behavior): after a delivered and then a read receipt for a message, that message's GetTranscript item carries MessageMetadata whose MessageId is the message's own Id and whose Receipts list holds exactly one entry, with a DeliveredTimestamp not after its ReadTimestamp; a message that only received a delivered receipt carries a receipt entry with DeliveredTimestamp and NO ReadTimestamp. Emulator: no transcript item carries MessageMetadata at all — the stored TranscriptItem (src/state.rs) has no receipt fields, so the poll for a receipt-bearing item never succeeds and the metadata assertions can never be reached. Why: message-receipt state is the whole point of the delivered/read event types; a chat UI can never show delivered/read ticks against this emulator. Fix: receipt state on the transcript item in src/state.rs plus its serialization in GetTranscript's handler. Failing checks: connectparticipant.send-multiple-events-produce-distinct-transcript-ids, connectparticipant.send-event-client-token-caches-on-content-not-contenttype.

Cause 6 of 7: CreateParticipantConnection's empty-Type refusal serves the framework's generic constraint text instead of AWS's message. AWS: an empty Type list is refused ValidationException (Smithy: common error ValidationException, httpError 400, "The input fails to satisfy the constraints specified by Amazon Connect"; Type targets ConnectionTypeList with @length min 1) with the fixed Message "Failed to create participant connection due to missing connection type" — entirely fixed text, no values from the request. Emulator: ValidationException with the boundary validator's generic rendering "1 validation error detected: Value '0 items' at 'type' failed to satisfy constraint: Member must have length greater than or equal to 1" (the '0 items', 'type' and bound are framework-derived, not AWS wording). Why: a client branching on the refusal text for a missing connection type never matches, and the message leaks the emulator's internal member casing ('type'). Fix: CreateParticipantConnection's own validation, ahead of/overriding the generic length check (src/ops/create_participant_connection.rs). Failing check: connectparticipant.create-participant-connection-rejected-inputs.

Cause 7 of 7: CreateParticipantConnection accepts a ParticipantToken the service never issued (fails open). AWS: a bogus ParticipantToken is refused AccessDeniedException (httpError 403) with the fixed text "User is not authorized to access this resource with an explicit deny in an identity-based policy". Emulator: src/ops/create_participant_connection.rs, on a participant token absent from state.participant_tokens, mints a brand-new contact id and session and returns live ConnectionCredentials — so any arbitrary string is a valid participant token. Why: this is an authentication bypass relative to AWS; a test or client that expects an unissued token to be rejected instead gets a working chat session, and negative-path coverage of the service's only credential is unreachable. Fix: CreateParticipantConnection's handler must refuse a participant token no started chat registered rather than creating a session for it. Failing check: connectparticipant.create-participant-connection-rejected-inputs (this assertion sits immediately after Cause 6's, which currently fails first).
