# global-accelerator: 4 net-new root causes — UpdateEndpointGroup is a 501 stub, and three refusal messages (duplicate endpoint group, traffic-dial constraint, DeleteListener conflict) use emulator-authored wording

> _Note: this issue was identified against the code base at commit `611eef386f1100e1b77f5a1515bab52b7a7a6aeb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

UpdateEndpointGroup

## Description
Four independent net-new root causes in the Global Accelerator emulator, all grounded in failing behavioral checks of this suite. They must all be closed before this issue is submitted. Related but NOT covering: open issue 20261029T171730Z-globalaccelerator-error-messages-diverge-from-aws-wording-across.md describes the same message-template family from the WIRE corpus (its Issue-Keys name CreateAccelerator/CreateEndpointGroup/UpdateEndpointGroup/DeleteListener/CreateListener $.Message); the behavioral checks below were not marked as owned by it, and Cause 2 and Cause 4 reach paths that issue does not key (CreateEndpointGroup's constraint formatter, and UpdateEndpointGroup not being implemented at all).

Cause 1 of 4: CreateEndpointGroup's already-exists refusal is emulator-authored prose with per-run ARNs interpolated.
AWS: Smithy (services/service-com-amazonaws-globalaccelerator-globalaccelerator-v20180706/smithy-model/com-amazonaws-globalaccelerator-globalaccelerator-v20180706.json) models EndpointGroupAlreadyExistsException on CreateEndpointGroup, errorKind client, httpError 400 ("The endpoint group that you specified already exists."). The message text itself is recorded behavior only: the recording shows HTTP 400, code EndpointGroupAlreadyExistsException, Message exactly 'Endpoint group already exists.' — the entire string is fixed text; no ARN, listener id or Region is interpolated.
Emulator: HTTP 400 EndpointGroupAlreadyExistsException with Message of the form 'endpoint group <endpointGroupArn> already covers Region <region> for listener <listenerArn>' (the run showed 'endpoint group arn:aws:globalaccelerator::000000000000:accelerator/.../endpoint-group/... already covers Region us-west-2 for listener arn:aws:globalaccelerator::.../listener/...' — those ARNs and the Region are per-run values, not part of the requirement).
Why: a client comparing, logging or pattern-matching AWS's constant sentence never matches; the emulator additionally leaks generated per-run identifiers into a message AWS keeps stable, so duplicate-Region handling keyed on that text does not fire.
Fix: CreateEndpointGroup's conflict path (the per-Region duplicate check in its handler) must raise EndpointGroupAlreadyExistsException with the fixed message and no interpolation.
Traces: global-accelerator.endpoint-group-rejects-duplicate-region.

Cause 2 of 4: the TrafficDialPercentage constraint-violation message on CreateEndpointGroup reports the wrong member path and renders the rejected float as an integer.
AWS: Smithy models CreateEndpointGroupRequest.TrafficDialPercentage as TrafficDialPercentage, type float, @range min 0 max 100, and CreateEndpointGroup throws InvalidArgumentException (httpError 400). The recording shows HTTP 400, code InvalidArgumentException, with AWS's standard constraint template: "1 validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must have value less than or equal to <max>". Fixed text: "1 validation error detected: Value '", "' at '", "' failed to satisfy constraint: Member must have value less than or equal to ". Variable parts: the rejected value as the service renders it (a float, rendered WITH its decimal part — the recording shows '150.0' for a request of 150.0), the member path the service reports for this input member (recorded as 'trafficRetentionPercentage'), and the limit from the member's @range max (100).
Emulator: same template but two wrong variable parts — "1 validation error detected: Value '150' at 'trafficDialPercentage' failed to satisfy constraint: Member must have value less than or equal to 100": the member path is the modeled member name instead of the path the service reports, and the float is rendered without its decimal part.
Why: a client that parses the standard validation template to learn which member to correct is pointed at a member name the service never reports in this error, and an exact-match assertion on the validation message fails even though status and code are right.
Fix: the shared constraint-violation formatter reached from CreateEndpointGroup's (and UpdateEndpointGroup's) input validation — the reported member path for this member and the float rendering of the rejected value.
Traces: global-accelerator.traffic-dial-rejects-percentage-above-hundred.

Cause 3 of 4: DeleteListener's associated-endpoint-group refusal uses a different sentence than AWS.
AWS: Smithy models AssociatedEndpointGroupFoundException on DeleteListener, errorKind client, httpError 400 ("The listener that you specified has an endpoint group associated with it. You must remove all dependent resources from a resource before you can delete it."); the wire message is recorded behavior only. The recording shows HTTP 400 with Message of the form 'Cannot delete listener <listenerArn> because an associated endpoint group was found.' — fixed text 'Cannot delete listener ' + ' because an associated endpoint group was found.', with the single variable part being the ListenerArn taken from the request.
Emulator: HTTP 400 with 'Listener <listenerArn> has an endpoint group associated with it; delete its endpoint groups before deleting it.' — a wholly different sentence (reversed clause order, added remediation advice) around the same request ARN.
Why: delete-ordering error handling that matches AWS's sentence does not fire, and tests pinned to AWS's text fail.
Fix: DeleteListener's handler error path — raise AssociatedEndpointGroupFoundException with the service's template, interpolating only the request's ListenerArn.
Traces: global-accelerator.listener-delete-rejects-associated-endpoint-group.

Cause 4 of 4: UpdateEndpointGroup is an unimplemented scaffold stub, so every update — including the unsupported-health-check-interval refusal — answers 501 NotImplemented.
AWS: Smithy models UpdateEndpointGroup with errors AccessDeniedException(403), EndpointGroupNotFoundException(404), InternalServiceErrorException(500), InvalidArgumentException(400), LimitExceededException(403); HealthCheckIntervalSeconds is @range 10..30, and the member doc states only two values are supported ("The time—10 seconds or 30 seconds—between each health check"). The recording shows an in-range-but-unsupported 20 refused with HTTP 400, code InvalidArgumentException, Message 'Invalid HealthCheck Interval Seconds: 20 expected values are: 10 or 30' — fixed text 'Invalid HealthCheck Interval Seconds: ' + ' expected values are: 10 or 30', with the rejected value taken from the request; the endpoint group is left unchanged, and the supported value (10) is then accepted and round-trips through DescribeEndpointGroup.
Emulator: UpdateEndpointGroup returns HTTP 501 with code 'NotImplemented' for every request — the handler body is still the scaffold's Err(crate::scaffolded::Scaffolded::not_implemented("UpdateEndpointGroup")). So neither the refusal, nor its no-mutation guarantee, nor any successful update of TrafficDialPercentage / HealthCheckIntervalSeconds / endpoints is observable.
Why: a client cannot modify an endpoint group at all, and code branching on InvalidArgumentException for an unsupported interval instead sees a 501 it has no handling for; the same stub also hides Cause 2 on the update path.
Fix: implement UpdateEndpointGroup's handler (services/service-com-amazonaws-globalaccelerator-globalaccelerator-v20180706/src/ops/update_endpoint_group.rs, handle() at line 176, 501 returned at line 193) against the existing store, reusing the create path's validation helpers (crate::state::validate_health_check_interval, SUPPORTED_HEALTH_CHECK_INTERVALS in src/state.rs line 76) and removing the SCAFFOLDED marker; the refusal must leave the stored endpoint group untouched.
Traces: global-accelerator.health-check-interval-rejects-unsupported-value.
