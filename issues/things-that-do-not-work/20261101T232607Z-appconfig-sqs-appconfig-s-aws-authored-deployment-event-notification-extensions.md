# AppConfig's AWS-authored deployment-event notification extensions never deliver anything: action dispatch skips every action with no Uri, so an association's queueArn is never sent to

> _Note: this issue was identified against the code base at commit `f80d17848b0354e4d278a13ef40d60fb16242eb6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartDeployment

## Description
One net-new root cause.

Cause 1 of 1: AppConfig's AWS-authored deployment-event notification extensions are now published in the catalogue, but an association of one produces no invocation at any ON_DEPLOYMENT_* action point, so no lifecycle notification is ever delivered to the queue the association names. Failing check: appconfig__sqs.deployment-events-to-sqs-extension-delivers-lifecycle-messages.

AWS: an AWS-authored notification extension (ARN with an EMPTY account field, e.g. arn:aws:appconfig:<region>::extension/AWS.AppConfig.DeploymentEventsToSqs/1) binds exactly the three deployment-lifecycle action points ON_DEPLOYMENT_START, ON_DEPLOYMENT_COMPLETE, ON_DEPLOYMENT_ROLLED_BACK and is not customizable. Its DESTINATION is not part of the extension: it is the value the ASSOCIATION supplies for the extension's own parameter — Smithy: Parameter is "A value such as an Amazon Resource Name (ARN) or an Amazon Simple Notification Service topic entered in an extension when invoked. Parameter values are specified in an extension association", with Required=true for the queue-ARN parameter; Action$Uri ("The extension URI associated to the action point in the extension definition") is OPTIONAL and an authored notification extension publishes none. So associating that extension to an environment ARN with Parameters={'queueArn': <queue arn>} makes AppConfig enqueue one message when a deployment starts and one when it completes. Recorded behavior only for the exact body keys (the check is marked DRAFT/unblessed and discovers the extension from ListExtensions rather than hardcoding it): each body carries Type in PascalCase ('OnDeploymentStart' / 'OnDeploymentComplete' — not the SCREAMING_SNAKE action-point keys), DeploymentNumber, ConfigurationVersion, Application.Id, Environment.Id, ConfigurationProfile.Id and the association's Parameters. Deleting the association stops delivery (GetExtensionAssociation then answers ResourceNotFoundException with Message "ExtensionAssociation could not be found for account <account>." — fixed text, with the account id taken from the caller's identity), and re-creating the association restores delivery for the NEXT deployment. Smithy: StartDeployment POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments; CreateExtensionAssociation POST /extensionassociations with Parameters (ParameterValueMap).

Emulator: the catalogue exists but the dispatch refuses to use it. services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs publishes AWS_AUTHORED_EXTENSIONS (AWS.AppConfig.DeploymentEventsToEventBridge / ...ToSns / ...ToSqs) with DEPLOYMENT_EVENT_ACTION_POINTS and the required queue-ARN parameter, and Extension::aws_authored builds each Action with only `name` set and NO `uri` (its own doc says the destination "is the value an association supplies for the extension's own parameter, not part of the extension"). But services/service-com-amazonaws-appconfig-amazonappconfig/src/state/extension_actions.rs targets_at() then drops exactly those actions: `let Some(uri) = action.uri.clone().filter(|uri| !uri.trim().is_empty()) else { continue; }`, with the comment "An action with no `Uri` names no target: AppConfig's own AWS-authored extensions are published without one, and there is nothing to invoke." So no ActionTarget is ever built for an authored notification extension, nothing is dispatched at ON_DEPLOYMENT_START / ON_DEPLOYMENT_COMPLETE / ON_DEPLOYMENT_ROLLED_BACK, and the association is pure metadata — even though the generic SQS delivery path right beside it works (TargetKind::Queue -> queue_url(arn) -> sqs_client(ctx, region).send_message()). The replay shows the check reaching no assertion at all: it is killed at the harness 60 s cap while waiting inside _deploy_and_wait_complete (poll GetDeployment to a terminal state for a 1-minute strategy) and _drain (long-poll for the two messages), so neither the positive, the absence, nor the restore beat is observable.

Why: this predefined extension is the supported, zero-code way to observe AppConfig releases from outside AppConfig. A consumer that drives release gating, change logging or paging off those SQS messages receives nothing and never learns that a deployment started, completed or rolled back — and because the delivery path does not exist at all, an "association deleted, therefore nothing arrives" expectation passes for the wrong reason, so a client can also never detect that its notification wiring is broken.

Fix: the authored-extension branch of extension-action dispatch (state/extension_actions.rs targets_at and the invoke path it feeds), plus the deployment state machine that reaches those action points. An action belonging to an AWS-authored notification extension must resolve its destination from the bound association's parameter value (queueArn for ...ToSqs, the topic ARN for ...ToSns, the account's default event bus for ...ToEventBridge) instead of from Action$Uri, and must send the deployment-lifecycle notification body (Type in PascalCase, DeploymentNumber, ConfigurationVersion, Application/Environment/ConfigurationProfile and the association's Parameters) at each of the extension's three action points — and send nothing once the association is deleted. Confirming the fix also needs a wall-clock budget larger than the current 60 s cap, since the check's strategy has DeploymentDurationInMinutes=1 and the emulator paces a rollout in real minutes (Deployment::rollout_duration = 60 * DeploymentDurationInMinutes seconds); the check declares _NOTIFICATION_BUDGET_S=900.

## Evidence
Behavioral replay, suite simparity-behavioral-aws-v1. appconfig__sqs.deployment-events-to-sqs-extension-delivers-lifecycle-messages [mismatch]: 'Error: Check timed out after 60.0s' — the check reached no assertion. Its only unbounded waits are _deploy_and_wait_complete (StartDeployment, then poll GetDeployment until State is one of COMPLETE/ROLLED_BACK/REVERTED, failing with "deployment <n> of version <v> did not reach COMPLETE within <timeout>s; last state <state>") and the queue drains, so nothing past the association was graded.

What the check would have asserted: after a completed deployment, exactly 2 messages on the queue whose Type set is {'OnDeploymentStart','OnDeploymentComplete'} (assertion message: "the two messages must be the start and complete notifications, PascalCase — NOT the SCREAMING_SNAKE action-point keys"), each naming the deployment number and the configuration version deployed and carrying Application.Id, Environment.Id, ConfigurationProfile.Id and Parameters['queueArn']; then an absence beat (association deleted -> GetExtensionAssociation ResourceNotFoundException with message "ExtensionAssociation could not be found for account <account>.", an empty queue over 3x the measured delivery latency, and ApproximateNumberOfMessages == '0'); then a restore beat (re-associate -> the same two notification types come back naming the NEW deployment).

Source of the cause: services/service-com-amazonaws-appconfig-amazonappconfig/src/state.rs AWS_AUTHORED_EXTENSIONS / DEPLOYMENT_EVENT_ACTION_POINTS / Extension::aws_authored (authored actions are built with `name` set and no `uri`; the required parameter is the queue ARN, "The ARN of the Amazon SQS queue deployment events are sent to"), against services/service-com-amazonaws-appconfig-amazonappconfig/src/state/extension_actions.rs targets_at, which `continue`s past any action whose Uri is absent or blank — so the authored notification extensions can never produce a target. The generic queue path in the same file (TargetKind::of -> TargetKind::Queue, queue_url(), sqs_client(...).send_message()) is reachable only for a custom extension action that carries a Uri.

Queue URLs/ARNs, account ids, generated names and the particular configuration bytes in the run are examples; the requirements are the authored extension's three action points, delivery of the documented notification body to the destination named by the association's parameter, the absence of delivery once the association is deleted, and restoration after re-association.

## Steps to Reproduce
1. sqs create_queue; read QueueArn via get_queue_attributes; set a queue Policy allowing appconfig.amazonaws.com SQS:SendMessage on it.
2. appconfig list_extensions and select the AWS-authored entry (ARN containing '::extension/') whose name mentions SQS; get_extension on it -> Actions == {ON_DEPLOYMENT_START, ON_DEPLOYMENT_COMPLETE, ON_DEPLOYMENT_ROLLED_BACK} (correct today) and a required queue-ARN parameter.
3. create_application / create_environment / create_configuration_profile(LocationUri='hosted'); create three hosted configuration versions with distinguishable bytes.
4. create_deployment_strategy with a NON-ZERO DeploymentDurationInMinutes (the check uses 1) — a zero-duration/zero-bake deployment invokes no action point.
5. create_extension_association(ExtensionIdentifier=<that authored extension ARN>, ResourceIdentifier=<environment ARN>, Parameters={'queueArn': <queue arn>}); get_extension_association -> Parameters['queueArn'] echoes the queue ARN.
6. start_deployment of version 1 and poll get_deployment to State COMPLETE; receive_message on the queue. Expected: two bodies with Type 'OnDeploymentStart' and 'OnDeploymentComplete', each naming that deployment number and configuration version, the application, environment and configuration profile, and echoing Parameters['queueArn']. Observed: nothing is ever enqueued — targets_at builds no target for the authored extension, so no ON_DEPLOYMENT_* invocation happens at all.
7. delete_extension_association, deploy version 2 -> the deployment must still complete and reach the data plane, and NOTHING must be enqueued (ApproximateNumberOfMessages '0'). This beat currently 'passes' only because no delivery path exists.
8. Re-associate and deploy version 3 -> the two notifications must come back naming the NEW deployment.
9. Re-replay appconfig__sqs.deployment-events-to-sqs-extension-delivers-lifecycle-messages with a wall-clock budget at least its declared _NOTIFICATION_BUDGET_S (900 s) to confirm the fix.
