# bedrock-runtime inference envelope: token usage is recomputed wrongly, usage.serverToolUsage omitted, and InvokeModel ignores max-token truncation

> _Note: this issue was identified against the code base at commit `7240e32f2500d20910730c71d4ad0714ff1f3217`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Converse

## Description
The synchronous inference envelope is wrong on both of this fixture's served turns: the token accounting does not match what the service reports for the same request, one usage member is never emitted at all, and the InvokeModel path reports the wrong stop reason because it does not truncate at the requested max tokens. Two net-new causes.

Cause 1 of 2 - Converse usage.inputTokens/totalTokens are miscounted and usage.serverToolUsage is missing (fixture bedrockruntime-converse-envelope-and-rejections, step task#1).
AWS: Smithy Converse output declares usage (TokenUsage, @required) whose inputTokens, outputTokens and totalTokens are all @required Integer @range min 0, documented as "The number of tokens sent in the request to the model", "...that the model generated", and "The total of input tokens and tokens generated by the model". So inputTokens is a deterministic function of the request's messages/system content under the model's tokenizer, and totalTokens must equal inputTokens + outputTokens. Recorded behavior for this request: inputTokens 8, outputTokens 8, totalTokens 16. The response also carries usage.serverToolUsage (an object, empty when no server-side tool ran); this member is not in the checked-in Smithy model, so for that member: recorded behavior only - the service emits it on every Converse response and the recording shows it as {}.
Emulator: inputTokens 11 and totalTokens 19 for the same request (outputTokens matches at 8, and 11+8=19, so the sum rule holds but the prompt-side count does not), and no serverToolUsage member at all.
Why: inputTokens is what callers meter, budget and bill against and what prompt-size regression tests assert on, so a prompt-token count that differs from the service's makes cost estimation and context-budget logic wrong by a fixed offset; an SDK or client that reads usage.serverToolUsage unconditionally gets a null where AWS always sends an object.
Fix: the Converse handler's token accounting (the prompt-side counter that feeds TokenUsage) and the response serializer, which must always emit the serverToolUsage member - empty when no server tool ran.

Cause 2 of 2 - InvokeModel ignores the request's max-token limit, so stopReason is 'end_turn' and the output token count overruns (same fixture, step task#2).
AWS: Smithy InvokeModel returns the model's body as the @required httpPayload; for the Converse-shaped bodies in this fixture the envelope carries stopReason (StopReason enum) and the same usage counters as Cause 1. The service generates at most the requested maximum number of output tokens and, when generation is cut off by that limit rather than by the model finishing, reports stopReason "max_tokens" - "end_turn" means the model completed its turn on its own. Recorded behavior for this request: stopReason "max_tokens", inputTokens 8, outputTokens 8, totalTokens 16 - output truncated exactly at the configured limit.
Emulator: stopReason "end_turn" with outputTokens 53 (and inputTokens 11, totalTokens 64) - generation ran past the requested limit and then reported a natural completion.
Why: the limit is a hard contract - a caller sizing a downstream buffer or a context window by it gets far more tokens than it allowed, and stopReason is how clients decide whether to continue the turn (on "max_tokens" they re-prompt to resume, on "end_turn" they stop), so a truncated completion is silently treated as complete and the continuation is lost. Note the inverse defect was previously filed and resolved for Converse/ConverseStream (20261024T085515Z, stopReason 'max_tokens' on a normal short turn); this is the InvokeModel path and the opposite direction, so that resolved issue does not cover it.
Fix: the InvokeModel handler's generation stage - enforce the request's max-token limit on the generated body, set stopReason from the actual cut-off cause, and count outputTokens from the truncated output; the prompt-side counter is the same one as Cause 1.
