# codedeploy: the minimumHealthyHosts concurrency check cannot start — the launched Server-platform fleet never becomes Online SSM managed nodes (1 cause)

> _Note: this issue was identified against the code base at commit `51ca4c2291cddeccaa5c76d2f3d0dac1588f79fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDeployment

## Description
Cause 1 of 1: the behavioral check codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability — the only check that measures a custom deployment config's minimumHealthyHosts bound as observable concurrency on a real EC2 fleet — makes no progress at all and is cut off by the harness cap. It launches a two-host tagged fleet (t3.micro, instance profile with AmazonSSMManagedInstanceCore plus read on the revision bucket, user-data installing SSM Agent and the CodeDeploy agent), then blocks in its fleet-readiness wait, which polls ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<ids>]}]) for PingStatus 'Online' (600 s budget) and then runs 'systemctl is-active codedeploy-agent' through ssm:SendCommand on each host. Nothing downstream is ever reached: no CreateDeploymentConfig-bounded deployment is created, so neither the per-target concurrency bound nor the deploymentOverview partition nor the service-clock elapsed comparison is exercised.

AWS: a running EC2 instance whose instance profile grants AmazonSSMManagedInstanceCore registers itself as a Systems Manager managed node within a minute or two, after which DescribeInstanceInformation returns one InstanceInformation entry for that instance id with PingStatus 'Online' (ssm Smithy: InstanceInformation.PingStatus, enum Online | ConnectionLost | Inactive), and ssm:SendCommand/GetCommandInvocation can run in-guest commands on it. On top of that host, CodeDeploy's Server compute platform honours the deployment config: Smithy (codedeploy) MinimumHealthyHosts.type = HOST_COUNT | FLEET_PERCENT with MinimumHealthyHostsValue, documented as "the minimum number of healthy instances as an absolute value" and, in the model's own example, "In an example of nine instances, if a HOST_COUNT of six is specified, deploy to up to three instances at a time" — i.e. at most (fleet size − value) instances are taken out of service at one instant, so an in-place rolling deployment shows an InProgress window bounded by that arithmetic in ListDeploymentTargets/BatchGetDeploymentTargets, a deploymentOverview (Pending/InProgress/Succeeded/Failed/Skipped, all InstanceCount) that partitions the fleet at every instant, and a createTime→completeTime span longer than the same revision deployed with CodeDeployDefault.AllAtOnce over the same hosts.

Emulator: the check never gets past host registration — it is reported as 'Error: Check timed out after 60.0s' with no assertion diagnostic, because the 60 s harness cap falls inside the DescribeInstanceInformation poll loop (InstanceInformationList stays empty for the launched instance ids, so the wait spins instead of failing fast). No codedeploy call under test is ever issued. Hypothesis: as in the related report below, a RunInstances-created instance is modelled only in EC2 state and never cross-registered into SSM's managed-node inventory, so no PingStatus is ever reported and the Server-platform deployment path has no host to drive.

Why: a client cannot observe or rely on minimumHealthyHosts at all on this emulator. The whole point of a custom deployment config — bounding how many instances a rolling in-place deployment takes out of service at once — is unobservable, and the blocking symptom is a silent empty list rather than an error, so a client's own readiness poll hangs to its own deadline instead of failing.

Note: open issue 20261107T094623Z-codedeploy-no-server-platform-ec2-agent-deployment-check.md reports the same root cause for eight other Server-platform checks, but it does not carry this check's replay key (it is absent from that issue's Issue-Trace-Ids and Issue-Key lines), so this check is not covered by it and must be re-replayed separately. Once hosts register, the minimumHealthyHosts arithmetic above (and the deploymentOverview partition) is the second thing this check grades; the instant-settling of deployments reported in 20261029T180825Z-codedeploy-deployments-settle-to-succeeded-instantly-no-inprogress.md is likely to surface next.

Fix: the EC2 instance lifecycle must cross-register a running instance into the SSM managed-node state that backs DescribeInstanceInformation (PingStatus 'Online' shortly after the instance reaches 'running'), and the in-guest command plane (SendCommand/GetCommandInvocation) must act on that host; on the CodeDeploy side, the Server-platform deployment execution path (the instance-target lifecycle driver) must then pace targets according to the deployment config's minimumHealthyHosts and report the per-instant buckets in GetDeployment's deploymentOverview.

Traces: codedeploy.minimum-healthy-hosts-bounds-observed-concurrent-unavailability (timed out inside _wait_fleet_ready, before CreateDeploymentConfig/CreateDeployment are graded).

## Evidence
Expected (AWS): after RunInstances of two tagged t3.micro hosts with an SSM-capable instance profile, ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<the two ids>]}]) returns an entry per instance with PingStatus 'Online'; SendCommand('systemctl is-active codedeploy-agent') returns 'active'; then a Server-platform CreateDeployment through a group using a HOST_COUNT=1 config over a 2-host fleet shows at most (2 − 1) = 1 instance InProgress at any sampled instant in BatchGetDeploymentTargets, a deploymentOverview whose Pending+InProgress+Succeeded+Failed+Skipped equals 2 at every sample, and completeTime − createTime greater than the same revision deployed with CodeDeployDefault.AllAtOnce over the same hosts.

Actual (emulator): 'Error: Check timed out after 60.0s' — the check is cut off inside its fleet-readiness wait (polling DescribeInstanceInformation for PingStatus 'Online', then SendCommand for the agent state); InstanceInformationList never reports the launched ids, and no CodeDeploy operation under test (CreateDeploymentConfig / CreateDeployment / ListDeploymentTargets / BatchGetDeploymentTargets / GetDeployment) is reached, so the minimumHealthyHosts bound is never exercised. Instance ids, host names and timings are per-run values and not part of the requirement; the requirement is that a running instance becomes an Online managed node at all, and that a HOST_COUNT config bounds concurrent out-of-service instances to (fleet size − value).

## Steps to Reproduce
1. Create a VPC with a public subnet and an internet gateway; create an IAM role with AmazonSSMManagedInstanceCore attached plus s3:GetObject/ListBucket on a revision bucket, and an instance profile holding it.
2. Upload a zip revision to S3 whose appspec.yml installs payload.txt and runs a BeforeInstall hook that sleeps ~45 s.
3. ec2:RunInstances two t3.micro instances in that subnet with the instance profile and a tag KEY_AND_VALUE the deployment group will filter on; wait for state 'running'.
4. Poll ssm:DescribeInstanceInformation(Filters=[{Key:'InstanceIds',Values:[<both ids>]}]) for PingStatus 'Online' — observe InstanceInformationList stays empty, so the check's readiness wait never returns and the run is cut off at the 60 s cap.
5. (Blocked by step 4, and what the check grades) codedeploy:CreateDeploymentConfig(computePlatform='Server', minimumHealthyHosts={type:'HOST_COUNT', value:1}); create one deployment group using it and one using CodeDeployDefault.AllAtOnce over the same ec2TagFilters; CreateDeployment the same revision through each with fileExistsBehavior='OVERWRITE'; sample BatchGetDeploymentTargets every 3 s and GetDeployment's deploymentOverview, and compare completeTime − createTime of the two legs.
