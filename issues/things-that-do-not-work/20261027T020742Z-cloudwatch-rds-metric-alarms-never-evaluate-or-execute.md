# cloudwatch__rds: metric alarms never evaluate or execute AlarmActions, so no Action history item, no SNS publish and no topic-policy authorization decision ever happen (1 cause)

> _Note: this issue was identified against the code base at commit `a04a6917251164fb3627e673f5d6322225de49e4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutMetricAlarm

## Description
One cause.

NOTE ON OVERLAP: the open issue `20261024T030130Z-cloudwatch-rds-cloudwatch-metric-alarms-never-evaluate-or-fire-their.md` describes the same alarm-evaluation gap and lists this same check in its Issue-Trace-Ids, but the replay report did NOT mark this failing check as OWNED by it (no `OWNED by` / `ALREADY FILED` line on the check), so it is filed here rather than dropped. A fixer should treat the two as the same work item if that issue is still open, and close them together.

Cause 1 of 1: a metric alarm is stored but never evaluated, so no state transition, no action execution, no Action history and no action-target authorization ever occur.

AWS: PutMetricAlarm (Smithy: PutMetricAlarm input members TreatMissingData (string, @length 1..255), EvaluationPeriods (@range min 1), Period (@range min 1), AlarmActions -> ResourceList @length 0..5; output Unit, only modeled error LimitExceededFault/LimitExceeded 400) creates a MetricAlarm that CloudWatch evaluates on its OWN clock, with no SetAlarmState call from the client. With TreatMissingData="breaching" on a metric/dimension combination that receives no datapoints (here Namespace AWS/RDS, MetricName DatabaseConnections, Dimensions [{DBInstanceIdentifier: <an identifier that names no DB instance>}], EvaluationPeriods 1), each missing period is treated as breaching and the alarm leaves INSUFFICIENT_DATA for ALARM. On that transition CloudWatch executes every entry of AlarmActions and records one history item per action, retrievable through DescribeAlarmHistory with HistoryItemType="Action" (Smithy: HistoryItemType enum values ConfigurationUpdate | StateUpdate | Action | AlarmContributorStateUpdate | AlarmContributorAction; AlarmHistoryItem.HistoryData is "Data about the alarm, in JSON format", @length 1..4095). Recorded behavior only for the HistoryData field names the check reads: each Action item's parsed HistoryData names `notificationResource` (the action's target ARN), an `actionState` of `Succeeded` or `Failed`, a `publishedMessage` only when the publish happened, and an `error` when it did not. CloudWatch evaluates the TARGET's resource policy when it executes an SNS action: publishing to a topic whose policy carries an explicit Deny of `sns:Publish` for Principal Service `cloudwatch.amazonaws.com` is refused, so that action's item is `actionState: Failed`, its `error` contains the fixed text `not authorized to perform: SNS:Publish` with the denied topic ARN as the variable part taken from the alarm's own AlarmActions entry, and it carries no `publishedMessage`; the sibling topic with the default policy gets `actionState: Succeeded` and its notification (Message body carrying AlarmName and NewStateValue=ALARM, Trigger.Namespace=AWS/RDS) reaches the SQS queue subscribed to it. Removing the Deny makes a fresh alarm aimed only at that topic deliver into the same queue.

Emulator: nothing at all happens after PutMetricAlarm. The alarm is accepted but never evaluated: it never leaves INSUFFICIENT_DATA, no AlarmActions entry is executed, DescribeAlarmHistory(HistoryItemType="Action", AlarmTypes=["MetricAlarm"]) returns no AlarmHistoryItems for the alarm, and the subscribed SQS queue receives no SNS envelope. The check's first barrier poll (budget 600 s, 15 s interval) for an Action item per topic therefore never satisfies, and the check is killed by the harness: verdict `mismatch`, `Check timed out after 60.0s`. Because no action ever fires, the authorization decision this check exists to grade is never made either — the "correct" emptiness at the denied topic is produced by the alarm being inert, not by the Deny statement, and an emulator that later fires actions without consulting the target topic's resource policy will publish to a topic AWS refuses.

Why: every alarm-driven workflow is inert for a client. A client that creates an alarm and waits for the state change, for the SNS/SQS notification, or for the Action history that tells it whether its notification was actually delivered, waits forever and eventually times out instead of observing ALARM, a Succeeded action and a notification. A client that relies on CloudWatch refusing a publish into a topic that denies cloudwatch.amazonaws.com gets no Failed Action item and no authorization error to key alerting or incident automation on, so a real misconfiguration is indistinguishable from a healthy pipeline.

Fix: the CloudWatch alarm evaluation path (the alarm state/evaluation component behind PutMetricAlarm, DescribeAlarms and DescribeAlarmHistory, and the action-execution path that reaches SNS). Alarms must be evaluated against their metric data on a timer honouring Period/EvaluationPeriods/DatapointsToAlarm and TreatMissingData ("breaching" on absent data must drive INSUFFICIENT_DATA -> ALARM), must record the StateUpdate item, must execute each AlarmActions entry through the target service while evaluating that target's resource policy, and must record one Action history item per action carrying notificationResource, actionState Succeeded/Failed, publishedMessage only on success and AWS's `not authorized to perform: SNS:Publish` error text on an explicit Deny.

## Evidence
Failing check cloudwatch__rds.rds-alarm-action-blocked-by-topic-policy-denying-cloudwatch — verdict `mismatch`, detail `Check timed out after 60.0s`, with no ALREADY FILED / OWNED marker in the suite report.

Expected (AWS): after PutMetricAlarm with TreatMissingData="breaching", EvaluationPeriods=1, AlarmActions=[allowedTopicArn, deniedTopicArn] on AWS/RDS DatabaseConnections for a non-existent DBInstanceIdentifier, DescribeAlarmHistory(AlarmName=<alarm>, HistoryItemType="Action", AlarmTypes=["MetricAlarm"]) yields one Action item per topic ARN; HistoryData for allowedTopicArn has actionState="Succeeded"; HistoryData for deniedTopicArn has actionState="Failed", error containing `not authorized to perform: SNS:Publish` plus the denied topic ARN, and publishedMessage absent. ReceiveMessage on the queue subscribed to both topics yields exactly one SNS envelope whose TopicArn is the allowed topic and whose parsed Message has AlarmName=<alarm>, NewStateValue="ALARM", Trigger.Namespace="AWS/RDS" — and nothing from the denied topic. After SetTopicAttributes restores the default policy, a fresh alarm with AlarmActions=[deniedTopicArn] records actionState="Succeeded" and its notification arrives in the same queue.

Actual (emulator): the alarm stays in its initial state; DescribeAlarmHistory returns no Action items for the alarm (the check's `_by_resource(_action_items(cw, alarm))` never contains either topic ARN); ReceiveMessage returns no messages. The first `_poll_until` barrier (timeout_s=600, interval_s=15) never satisfies and the run is cut off at the harness's 60 s cap, so steps 2-4 of the check (Succeeded positive control, Failed denied action, repair leg) are never reached.

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. rds: DescribeDBInstances(DBInstanceIdentifier=<ghost-id>) and confirm it answers DBInstanceNotFound — the alarm's dimension must name no instance.
3. sns: CreateTopic twice (an "allowed" and a "denied" topic). On the denied one, GetTopicAttributes to read the default Policy, append a statement {Sid: DenyCloudWatchPublish, Effect: Deny, Principal: {Service: cloudwatch.amazonaws.com}, Action: sns:Publish, Resource: <denied topic arn>} and SetTopicAttributes(AttributeName="Policy"). GetTopicAttributes confirms the Deny is stored.
4. sqs: CreateQueue, read its QueueArn, SetQueueAttributes with a Policy allowing sns.amazonaws.com sqs:SendMessage from both topic ARNs, then sns:Subscribe the queue ARN to BOTH topics (Protocol=sqs, ReturnSubscriptionArn=true).
5. cloudwatch: PutMetricAlarm(AlarmName=<alarm>, Namespace="AWS/RDS", MetricName="DatabaseConnections", Dimensions=[{Name: DBInstanceIdentifier, Value: <ghost-id>}], Statistic="Maximum", Period=60, EvaluationPeriods=1, Threshold=1.0, ComparisonOperator="GreaterThanOrEqualToThreshold", TreatMissingData="breaching", AlarmActions=[<allowed>, <denied>]).
6. Poll DescribeAlarms(AlarmNames=[<alarm>]) for StateValue, DescribeAlarmHistory(AlarmName=<alarm>, HistoryItemType="Action", AlarmTypes=["MetricAlarm"]) for Action items, and ReceiveMessage on the queue: the alarm never transitions to ALARM, no Action history item is ever recorded for either topic, and no notification is ever delivered — the poll runs until the harness cap.
