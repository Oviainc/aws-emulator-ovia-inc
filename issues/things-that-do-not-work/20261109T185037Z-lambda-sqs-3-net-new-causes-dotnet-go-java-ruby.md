# 3 net-new causes: dotnet/go/java/ruby functions never run, Node async destination records are never delivered, and a FIFO SQS mapping accepts MaximumBatchingWindowInSeconds

> _Note: this issue was identified against the code base at commit `b4090e4eff86c6645a745aa23fbd4b95671a37a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Three distinct root causes in the lambda__sqs suite. Each is listed with its own failing check ids; all three must be closed.

Cause 1 of 3 — functions on the .NET, Java, Ruby and custom (provided.al2023) runtimes are accepted by CreateFunction but never executed. AWS: Lambda runs every runtime it accepts. A dotnet8 handler, a java21 handler, a ruby3.x handler and a Go binary on provided.al2023 (Handler='bootstrap') all run: their async invocations produce OnSuccess/OnFailure destination records, and their SQS event source mappings honour batchItemFailures so only the reported message stays in the queue. Emulator: all eight checks end with 'the run budget ended first; not graded' (no destination record, queue depth never settles), while the emulator states its support explicitly elsewhere in this run — 'The runtime an image package is not supported by this emulator, which runs the Python and node runtimes.' CreateFunction accepts the runtime anyway and the function reports Active. Why: a client sees a healthy function and a wired mapping with no invocation, no error and no log — nothing distinguishes 'my handler is broken' from 'this runtime never runs'. Accepting a runtime that is never executed is the defect: an unsupported runtime must be refused at CreateFunction/UpdateFunctionConfiguration with Lambda's InvalidParameterValueException. Fix: the Lambda runtime-execution component (support the runtimes, or refuse them at create with the modeled error). Traces: lambda__sqs.dotnet-async-invoke-onsuccess-onfailure-destination-envelope, lambda__sqs.dotnet-sqs-batch-item-failures-deletes-only-successes, lambda__sqs.go-handler-async-invoke-destinations-route-onsuccess-and-onfailure, lambda__sqs.go-handler-sqs-batch-item-failures-deletes-only-the-successes, lambda__sqs.java-async-invoke-on-success-and-on-failure-destination-envelope, lambda__sqs.java-sqs-esm-partial-batch-response-deletes-only-the-successful-records, lambda__sqs.ruby-async-invoke-onsuccess-and-onfailure-destination-envelope, lambda__sqs.ruby-sqs-esm-partial-batch-response-deletes-only-successes.

Cause 2 of 3 — asynchronous invocation destination records are not delivered even for a supported (Node ESM / Python) runtime. AWS: an async Invoke (InvocationType='Event') of a function with an EventInvokeConfig DestinationConfig delivers an invocation record to OnSuccess on success and to OnFailure when the retry budget or MaximumEventAgeInSeconds is exhausted; the record carries requestContext (requestId, functionArn, condition, approximateInvokeCount) plus requestPayload/responsePayload. Emulator: nothing arrives — 'the OnSuccess record: the run budget ended first; not graded' for a Node ESM handler, and for the maximum-event-age check even the positive leg (the short-age function's first invocation and its OnSuccess record) never happens within 300s. Why: the entire async-destination plane is unobservable, so a client cannot confirm success, cannot capture failures, and MaximumEventAgeInSeconds has no visible effect. Fix: the asynchronous invoke queue/destination delivery path in the Lambda async plane. Related open issues filed for sibling checks: 20261107T212447Z-lambda-sqs-asynchronous-invocation-destinations-and-deadletterconfig-never-deliver-a.md, 20261107T014900Z-lambda-sqs-the-asynchronous-invocation-plane-is-inert.md. Traces: lambda__sqs.async-invoke-node-esm-handler-on-success-and-on-failure-destination-envelopes, lambda__sqs.maximum-event-age-discards-the-throttled-async-invocation-to-the-on-failure-destination.

Cause 3 of 3 — CreateEventSourceMapping accepts MaximumBatchingWindowInSeconds on a FIFO queue. AWS: a FIFO SQS event source does not support a batching window; the call is refused with InvalidParameterValueException (HTTP 400) naming the unsupported parameter for a FIFO queue. Emulator: 'expected a ClientError, the call unexpectedly succeeded' — the mapping is created. Why: the client ships a configuration AWS rejects, and the batching semantics it assumes silently do not apply. Fix: FIFO-source parameter validation in the CreateEventSourceMapping handler. Traces: lambda__sqs.sqs-esm-fifo-queue-rejects-maximum-batching-window-negative.
