Cause 1 of 6: a started build never executes — it FAULTs in PROVISIONING, so no INSTALL/PRE_BUILD/BUILD/POST_BUILD phase ever appears and no build ever reaches SUCCEEDED, FAILED, STOPPED or TIMED_OUT.
AWS: Smithy: StartBuild returns a Build (errors AccountLimitExceededException / InvalidInputException / ResourceNotFoundException, HTTP 400); StopBuild returns a Build. Recorded behavior for the lifecycle itself: a build on a NO_SOURCE project with an inline buildspec moves SUBMITTED -> QUEUED -> PROVISIONING -> DOWNLOAD_SOURCE -> INSTALL -> PRE_BUILD -> BUILD -> POST_BUILD -> ... -> COMPLETED, each phase carrying phaseStatus SUCCEEDED and its own startTime/endTime/durationInSeconds, and buildStatus settles on SUCCEEDED when every command exits zero, FAILED when a command exits non-zero (the failing phase is FAILED and later phases are skipped unless on-failure: CONTINUE is set), STOPPED after StopBuild, TIMED_OUT when timeoutInMinutes elapses. A build stays IN_PROGRESS for the duration of its commands, which is what makes concurrentBuildLimit, StopBuild, RetryBuild and BatchDeleteBuilds observable. FAULT is reserved for an internal CodeBuild fault, not for an ordinary build.
Emulator: every build ends buildStatus 'FAULT' within ~1s with phases [('SUBMITTED','SUCCEEDED'),('QUEUED','SUCCEEDED'),('PROVISIONING','FAULT'),('COMPLETED',None)] and a PROVISIONING context message "this emulator does not run CodeBuild build containers, so the build could not be provisioned and no buildspec was executed" — prose no AWS account ever returns. Consequences observed: a non-zero command yields FAULT instead of FAILED; natural completion yields FAULT instead of SUCCEEDED; StopBuild on a completed build reports FAULT instead of SUCCEEDED; the build is never IN_PROGRESS long enough to occupy a concurrency slot or to be stopped mid-PRE_BUILD (the stop-build race check is killed at the 180s cap while polling for currentPhase 'BUILD'); no phase durations exist to compare; environment-variable precedence, exported variables, on-failure: CONTINUE and timeoutInMinutes are all unobservable.
Why: the entire CodeBuild data plane is non-functional. A client that polls BatchGetBuilds for a terminal outcome gets a status AWS only emits for its own internal faults, so CI logic keyed on SUCCEEDED/FAILED/STOPPED/TIMED_OUT takes the wrong branch, and every per-phase, per-variable and concurrency behavior is invisible.
Fix: the build execution engine behind StartBuild/RetryBuild (phase state machine, buildspec execution, exported variables, on-failure handling, timeout enforcement, StopBuild transition) and the removal of the emulator-authored PROVISIONING fault context.
Traces: codebuild.batch-delete-builds-partial-failure-isolated, codebuild.build-executes-buildspec-and-exports-computed-variable, codebuild.build-failing-command-reaches-failed-terminal, codebuild.build-lifecycle-transitions-to-terminal-state, codebuild.cbnv-unknown-runtime-name-build-rejected-as-yaml-file-error, codebuild.codebuild-concurrent-build-limit-rejects-the-second-start-and-no-second-build-appears, codebuild.codebuild-environment-variable-precedence-resolves-inside-the-build, codebuild.failing-pre-build-phase-skips-later-phases-and-reports-the-exit-code, codebuild.on-failure-continue-runs-the-next-phase-while-the-failed-phase-stays-failed, codebuild.phase-durations-equal-their-own-windows-and-the-slow-phase-dominates, codebuild.retry-build-account-limit-exceeded-blocked, codebuild.stop-build-during-pre-build-stops-exactly-that-phase-and-leaves-the-rest-unrun, codebuild.stop-build-on-completed-build-is-an-idempotent-no-op, codebuild.stop-build-race-idempotent-single-transition, codebuild.timeout-in-minutes-kills-the-running-build-and-marks-that-phase-timed-out.

Cause 2 of 6: a sandbox command execution never executes — it ends status FAULT with emulator prose in standardErrContent, and the sandbox never becomes usable.
AWS: Smithy: StartCommandExecution takes sandboxId + command (+ type SHELL) and returns a CommandExecution (errors InvalidInputException / ResourceNotFoundException). Recorded behavior: the CommandExecution settles on status SUCCEEDED when the command exits zero (FAILED on non-zero), carries the command's real stdout in standardOutputContent and an exitCode, and the owning sandbox advances through its lifecycle (QUEUED -> PROVISIONING -> RUNNING/IDLE and on to a terminal state) so later executions and StopSandbox are observable.
Emulator: the CommandExecution ends status 'FAULT' with standardErrContent "this emulator does not execute sandbox commands, so nothing ran this command: it produced no output and no exit code", no standardOutputContent and no exitCode; polls for SUCCEEDED/FAILED exhaust at 120s with last value 'FAULT', and the sandbox-lifecycle checks never see a terminal command execution. FAULT is not an outcome AWS produces for a command that simply ran.
Why: the sandbox surface is unusable — a client cannot read a command's output, cannot distinguish a failing command from a succeeding one, and sees a status AWS reserves for internal faults.
Fix: the sandbox command execution runtime behind StartCommandExecution (execute the command, capture stdout/stderr and exit code, settle status SUCCEEDED/FAILED) plus the sandbox state machine that drives it.
Traces: codebuild.codebuild-sandbox-command-execution-returns-the-commands-real-stdout, codebuild.command-execution-lifecycle-in-sandbox, codebuild.sandbox-lifecycle-active-to-terminated, codebuild.sandbox-lifecycle-transitions.

Cause 3 of 6: a CodeBuild project created by a CloudFormation stack is never registered in CodeBuild's state, so the project the stack reports as created is not found by the CodeBuild API.
AWS: recorded behavior only. A stack declaring AWS::CodeBuild::Project creates a real project: BatchGetProjects(names=[<that project name>]) returns it in `projects` with an empty `projectsNotFound`, and StartBuild against the stack's project name or ARN is accepted (HTTP 200 with a build). Smithy: StartBuild's ResourceNotFoundException is for a project that does not exist.
Emulator: the stack reaches completion, but BatchGetProjects on the declared project returns projects=[] with the name in projectsNotFound, and StartBuild on the stack's project ARN is refused HTTP 400 ResourceNotFoundException — message fixed text "Project cannot be found: " plus the project ARN taken from the request. State and API disagree.
Why: infrastructure-as-code topologies are unusable: the template applies and the outputs look right, yet every CodeBuild call against the created project fails as not-found, which a client cannot distinguish from a template defect.
Fix: the CloudFormation AWS::CodeBuild::Project resource provider must create the project in CodeBuild's own state and mint its physical id/ARN from that record, so CodeBuild's read and start paths resolve it.
Traces: codebuild.deploy-project-start-build-succeeds, codebuild.e2e-cbnv-check-codebuild-project-nodejs-version-lifecycle.

Cause 4 of 6: the sts:AssumeRole refusal message for an unusable service role is rewritten, dropping AWS's second and third remediation clauses. Affects CreateProject(serviceRole=...) and StartBuild(serviceRoleOverride=...).
AWS: Smithy: CreateProject and StartBuild both model InvalidInputException (HTTP 400); serviceRole is required on CreateProject and serviceRoleOverride is a NonEmptyString on StartBuild. When the named role does not exist, or does not trust codebuild.amazonaws.com, AWS answers InvalidInputException whose message is entirely FIXED text with no request-derived parts: "CodeBuild is not authorized to perform: sts:AssumeRole on service role. Please verify that: 1) The provided service role exists, 2) The role name is case-sensitive and matches exactly, and 3) The role has the necessary trust policy configured."
Emulator: answers InvalidInputException (code and status correct) with its own two-clause rewrite: "CodeBuild is not authorized to perform: sts:AssumeRole on service role. Please verify that: 1) The provided service role exists, 2) The service role's trust policy allows codebuild.amazonaws.com to assume it." — clause 2 is reworded and clause 3 is dropped.
Why: the message is part of the contract; a client or operator matching on, or displaying, AWS's remediation text gets emulator prose and loses the case-sensitivity and trust-policy hints AWS gives.
Fix: the service-role validation refusal message shared by the CreateProject and StartBuild handlers.
Traces: codebuild.create-project-invalid-role-rejected, codebuild.start-build-unassumable-role-override-rejected.

Cause 5 of 6: CreateProject with an S3 source and no location is refused with the wrong message text.
AWS: Smithy: CreateProject.source is a required ProjectSource and the operation models InvalidInputException (HTTP 400). For source={"type":"S3"} with no location, AWS answers InvalidInputException with the fixed message "Project source location is required" (no request-derived parts).
Emulator: answers InvalidInputException with "Invalid source: location is required" — its own wording for the same refusal class.
Why: a client that matches the refusal message to tell a missing-location source from any other invalid-source refusal cannot do so, and surfaced text is not AWS's.
Fix: the CreateProject source validation message construction.
Traces: codebuild.create-project-s3-source-without-location-rejected.

Cause 6 of 6: InvalidateProjectCache's not-found message omits the project name and the trailing period.
AWS: Smithy: InvalidateProjectCache takes a required projectName and models ResourceNotFoundException (HTTP 400). For a project that has never existed, AWS answers ResourceNotFoundException with the message "Project does not exist: <projectName>." — fixed text "Project does not exist: ", the projectName copied from the request, then a '.'.
Emulator: answers ResourceNotFoundException (code correct) with the bare message "Project does not exist" — the request-derived project name and the terminating period are missing.
Why: the message no longer identifies which project was absent, so a client logging or parsing the refusal of a batch of names cannot tell them apart.
Fix: the InvalidateProjectCache handler's not-found message construction.
Traces: codebuild.invalidate-project-cache-absent-not-found.
