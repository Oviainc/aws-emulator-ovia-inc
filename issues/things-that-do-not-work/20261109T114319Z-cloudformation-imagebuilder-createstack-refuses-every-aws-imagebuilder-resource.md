# cloudformation__imagebuilder: CreateStack refuses every AWS::ImageBuilder::* resource type as an unrecognized type, so no Image Builder template can be deployed

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template validation does not know the AWS::ImageBuilder::* resource types, so CreateStack refuses any template that declares one and no Image Builder resource can ever be provisioned through IaC. Failing checks: cloudformation__imagebuilder.deploy-imagebuilder-component-round-trip-and-delete, cloudformation__imagebuilder.deploy-imagebuilder-component-invalid-action-rejected-and-rolled-back, cloudformation__imagebuilder.deploy-imagebuilder-distribution-configuration-round-trip-and-delete, cloudformation__imagebuilder.deploy-imagebuilder-image-recipe-round-trip-and-delete, cloudformation__imagebuilder.deploy-imagebuilder-workflow-round-trip-and-delete.

AWS: recorded behavior only for the registry contents — Smithy (services/service-com-amazonaws-cloudformation-cloudformation) models CreateStack(StackName, TemplateBody, ...) -> CreateStackOutput{StackId} and declares only AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException; which resource types are recognized is CloudFormation's own registry, not a modeled value. AWS's registry includes the Image Builder types AWS::ImageBuilder::Component, AWS::ImageBuilder::ContainerRecipe, AWS::ImageBuilder::DistributionConfiguration, AWS::ImageBuilder::Image, AWS::ImageBuilder::ImagePipeline, AWS::ImageBuilder::ImageRecipe, AWS::ImageBuilder::InfrastructureConfiguration, AWS::ImageBuilder::LifecyclePolicy and AWS::ImageBuilder::Workflow, so a template declaring any of them is ACCEPTED: CreateStack answers HTTP 200 with a StackId, the stack walks CREATE_IN_PROGRESS -> CREATE_COMPLETE (or, when the underlying Image Builder create is refused, CREATE_FAILED -> ROLLBACK_COMPLETE with the service's own refusal as the resource's ResourceStatusReason), and the created resources are then readable through the imagebuilder API. The 'Unrecognized resource types' refusal is reserved for types that are genuinely not in the registry: AWS words it 'Template format error: Unrecognized resource types: [<type>, <type>, ...]' with error code ValidationError at HTTP 400 — the sentence up to the colon is fixed text and the bracketed list is taken from the request's template.
Emulator: CreateStack answers HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [...]', listing exactly the AWS::ImageBuilder::* types the template declares (observed: [AWS::ImageBuilder::Component]; [AWS::ImageBuilder::Component, AWS::ImageBuilder::ImageRecipe]; [AWS::ImageBuilder::DistributionConfiguration]; [AWS::ImageBuilder::Workflow]). No stack is created, so every later step of each check — stack status, Outputs, the imagebuilder read-back, the rollback assertions and the delete — is unreachable.
Why: a client that provisions Image Builder through CloudFormation (or CDK, which emits exactly these types) cannot deploy at all: a template AWS accepts is rejected at submit time with a template-format error, which a caller reads as 'my template is malformed' rather than 'the emulator lacks this provider'. Negative scenarios are also unverifiable, because the emulator refuses before the resource-level failure and rollback AWS would report.
Fix: CloudFormation's supported-resource-type registry used by template validation in the CreateStack path, plus resource handlers (create/read/update/delete + Ref/Fn::GetAtt) for the AWS::ImageBuilder::* types so a validated template actually provisions through the imagebuilder service state.
Traces: the five cloudformation__imagebuilder.deploy-imagebuilder-* checks listed above; the same refusal shape recurs under the cloudformation__iam__imagebuilder and cloudformation__ecr__imagebuilder headings (filed separately, one issue per service heading).

## Evidence
Expected (AWS): CreateStack with a template whose Resources declare AWS::ImageBuilder::Component / ImageRecipe / DistributionConfiguration / Workflow -> HTTP 200 {"StackId": "arn:aws:cloudformation:<region>:<account>:stack/<name>/<uuid>"}, then DescribeStacks reports a terminal CREATE_COMPLETE (or ROLLBACK_COMPLETE for the invalid-action component case, with the Image Builder refusal carried as the resource's ResourceStatusReason).
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::ImageBuilder::Component] (deploy-imagebuilder-component-round-trip-and-delete and deploy-imagebuilder-component-invalid-action-rejected-and-rolled-back); ... [AWS::ImageBuilder::Component, AWS::ImageBuilder::ImageRecipe] (deploy-imagebuilder-image-recipe-round-trip-and-delete); ... [AWS::ImageBuilder::DistributionConfiguration] (deploy-imagebuilder-distribution-configuration-round-trip-and-delete); ... [AWS::ImageBuilder::Workflow] (deploy-imagebuilder-workflow-round-trip-and-delete). HTTP 400, no StackId returned, no stack created.
The fixed text is 'Template format error: Unrecognized resource types: ' with code ValidationError; the bracketed type list is derived from the submitted template. The divergence is that these types must not be in that list at all.

## Steps to Reproduce
1. Boot the emulator and replay the behavioral suite.
2. Run cloudformation__imagebuilder.deploy-imagebuilder-component-round-trip-and-delete: it calls CreateStack(StackName=<unique>, TemplateBody=<template declaring an AWS::ImageBuilder::Component>, Tags=[{sim2real:<name>}]).
3. Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::ImageBuilder::Component]' instead of a 200 with a StackId.
4. Repeat with the image-recipe, distribution-configuration and workflow templates (same refusal, with the respective type names) and with the component-invalid-action template, which should reach ROLLBACK_COMPLETE rather than being refused at submit.
