# Transfer: TestIdentityProvider never invokes an AWS_LAMBDA provider (StatusCode 0, no Response), and a connector-delivered upload fires no observable OnUpload CUSTOM-step callback (2 causes)

> _Note: this issue was identified against the code base at commit `f33722003a1ee8bc5c3b48db565875ccd278b623`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TestIdentityProvider

## Description
TWO distinct net-new root causes in the transfer emulator, each grounded in one failing behavioral check of this replay. BOTH must be closed before this issue is submitted. These are the only two failing checks in the whole report that were marked neither 'ALREADY FILED' nor 'OWNED by'.

=== Cause 1 of 2: TestIdentityProvider on an AWS_LAMBDA server never invokes the function, so it answers StatusCode 0 with no Response and an emulator-authored Message instead of the provider's own outcome ===
Failing check: transfer.test-identity-provider-wrong-server-type-error.
AWS: Smithy com.amazonaws.transfer#TestIdentityProvider input {ServerId @required len 19..19 pattern ^s-([0-9a-f]{17})$, UserName @required len 3..100, ServerProtocol (Protocol enum), SourceIp, UserPassword @sensitive}; output {StatusCode (integer, @required, default 0), Response, Message, Url (@required len 0..255)}; modeled errors InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503. The model documents StatusCode as 'The HTTP status code that is the response from your API Gateway or your Lambda function', Response as 'The response that is returned from your API Gateway or your Lambda function', and Url as 'The endpoint of the service used to authenticate a user'. So for a server whose IdentityProviderType is AWS_LAMBDA and whose IdentityProviderDetails.Function names a Lambda function, this operation's answer is the OUTCOME of an authentication request made against that function: StatusCode is the status that invocation answered (200 for a function that ran and returned), and Response carries that function's own response body. Recorded behavior: against an AWS_LAMBDA server whose Function names a function that exists and is Active, TestIdentityProvider answers HTTP 200 with StatusCode 200 and a Response containing the JSON the handler returned (in the check, the handler returns {'Role': <arn>, 'HomeDirectory': '/sim2real-idp-test/<marker>'} and the marker is found inside Response). The function name/ARN, the account, the region and the marker value are request- and environment-derived and are NOT requirements — the requirement is that StatusCode is the invoked provider's status and Response is the provider's body verbatim.
Emulator: the gate on SERVICE_MANAGED and the ResourceNotFoundException/InvalidRequestException refusals are correct (those two assertions of the check pass), but past the gate the handler never calls anything. For the AWS_LAMBDA server it answers HTTP 200 with StatusCode 0, Response absent, and Message = 'The stored identity provider configuration is complete, but the authentication request could not be made: this emulator opens no outbound connection and runs no customer identity provider, so the provider returned no response.' That claim is wrong for an AWS_LAMBDA provider in this emulator: the function the server names is held by this same emulator's Lambda emulation, so no outbound connection is needed — the transfer crate already invokes an emulated function in-process for a CUSTOM workflow step (state/connector_delivery.rs builds an aws_sdk_lambda client over the EmbeddedEmulator callback), and the same seam is available here.
Why: a client cannot test or exercise a Lambda-backed custom identity provider at all. StatusCode 0 is the modeled DEFAULT, i.e. 'no HTTP status', so a caller that branches on StatusCode == 200 (the documented way to tell a working provider from a broken one) always takes the failure branch, and a caller that parses Response to validate the Role/HomeDirectory/Policy its provider returns has nothing to parse. Every provisioning or troubleshooting flow built on the operation AWS 'highly recommend[s] you call ... as soon as you create your server' reports a healthy provider as broken.
Fix: the TestIdentityProvider handler (services/service-com-amazonaws-transfer-transferservice/src/ops/test_identity_provider.rs) must, for a server past the external-identity-provider gate whose provider is one this emulator serves, actually make the authentication request over the in-process callback — invoke the Lambda function named by IdentityProviderDetails.Function with the documented authentication event — and report that invocation's HTTP status in StatusCode and its response payload in Response, keeping the no-response answer (StatusCode = state::IDENTITY_PROVIDER_NO_RESPONSE_STATUS with the explanatory Message) only for a provider endpoint this emulator does not serve.
Traces: transfer.test-identity-provider-wrong-server-type-error.

=== Cause 2 of 2: a file delivered through a connector onto a server with WorkflowDetails.OnUpload produces no observable CUSTOM-step callback, so no callback token ever exists and the replayed-token refusal is unreachable ===
Failing check: transfer.workflow-step-state-out-of-order-rejected.
AWS: Smithy CreateWorkflow (Steps with Type CUSTOM and CustomStepDetails{Name, Target, TimeoutSeconds, SourceFileLocation}); UpdateServer (WorkflowDetails.OnUpload = [{WorkflowId, ExecutionRole}]); StartFileTransfer(ConnectorId @required, SendFilePaths, RemoteDirectoryPath) -> TransferId; ListFileTransferResults(ConnectorId, TransferId) -> FileTransferResults @required; SendWorkflowStepState(WorkflowId @required len 19..19 ^w-([a-z0-9]{17})$, ExecutionId @required len 36..36 UUID pattern, Token @required len 1..64 ^\w+$, Status @required CustomStepStatus) -> empty output, modeled errors AccessDeniedException 403, InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429, ServiceUnavailableException 503; DescribeExecution(WorkflowId, ExecutionId) -> {WorkflowId, Execution} with ResourceNotFoundException 404. Recorded behavior: a file that lands on a server whose WorkflowDetails.OnUpload names a workflow starts ONE execution of that workflow; the workflow's CUSTOM step invokes its Lambda Target with an event carrying token and serviceMetadata.executionDetails.{workflowId, executionId}; that function's side effects are observable (here, an object written under tokens/<token>.json and then tokens/<token>.done) and its in-order SendWorkflowStepState(Status='SUCCESS') succeeds. Replaying that SAME token after the step has completed is refused with HTTP 404, error code ResourceNotFoundException and the message exactly 'Unknown execution' — that message is entirely FIXED text with no request- or state-derived part — and DescribeExecution's answer for that ExecutionId is unchanged by the refused replay.
Emulator: the connector plane now gets much further than it did — TestConnection reports SftpConnectionDetails.HostKey and then Status 'OK' after the key is pinned, and ListFileTransferResults reaches StatusCode 'COMPLETED' for the pushed file (all of those assertions pass in this replay) — but the workflow the arrival makes due produces nothing observable: the check then polls for the CUSTOM step's marker object for 60s and sees none ('AssertionError: condition not met within 60s, last value=None'). No callback token is therefore ever obtainable, and the target behavior (the 404 ResourceNotFoundException 'Unknown execution' on a replayed token, with DescribeExecution unchanged) cannot be reached at all.
Hypothesis (neither the model nor the replay output states which link breaks; the replay only shows the step's effect never appears): the chain is state/connector_delivery.rs::deliver -> start_upload_executions -> invoke_custom_step, and it is skipped or silently dropped at one of its guards — the server's stored WorkflowDetails.OnUpload not being read back, `state.workflows` not holding the created workflow at delivery time (the same store that open wire issue 20261105T194233Z-transfer-listworkflows-reports-an-empty-workflows-list-while.md reports as empty for a workflow the account holds, which would make `if !state.workflows.contains_key(&workflow_id) { continue; }` start no execution), the execution-capacity guard, or the in-process Lambda invocation failing/timing out so the step is left pending with only a tracing::warn.
Related already-filed issues that do NOT cover this: fixed issue 20261103T012703Z-transfer-connector-gated-workflow-callback-path-never-runs.md claimed both halves of this path; its TestConnection/StartFileTransfer half did land (those assertions now pass), but the OnUpload-execution half did not, and the check still fails — this is not a refusal of a call that issue fixed, it is the missing side effect it declared. Fixed issue 20261102T102840Z-transfer-connector-plane-never-becomes-usable-testconnection-reports.md and open issue 20261024T042010Z-transfer-fidelity-gaps-api-gateway-createserver-always-refused.md (its cause 2) likewise cover only the connector/TestConnection half.
Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback token) sees its workflow never run on an upload that the service itself reports as COMPLETED, so the step's function is never invoked, and the at-most-once property of a callback token — the property that makes a token safe to retry against — cannot be exercised here at all. Retry/idempotency logic written against real Transfer Family is untestable, and a caller cannot distinguish 'my workflow is misconfigured' from 'this target never runs workflows'.
Fix: the server upload path and the workflow/execution state in the transfer crate (services/service-com-amazonaws-transfer-transferservice/src/state/connector_delivery.rs start_upload_executions/invoke_custom_step, the WorkflowDetails.OnUpload storage written by src/ops/update_server.rs, the `workflows` store written by src/ops/create_workflow.rs, and the SendWorkflowStepState / DescribeExecution / ListExecutions handlers) must start an execution for a file delivered to a server whose WorkflowDetails.OnUpload names a workflow, invoke each CUSTOM step's Target with its callback token so the function's own effects are observable, accept the in-order SendWorkflowStepState for that token exactly once, and refuse a replay of the same token with the modeled HTTP 404 ResourceNotFoundException whose message is exactly 'Unknown execution', leaving DescribeExecution's answer unchanged.
Traces: transfer.workflow-step-state-out-of-order-rejected.
