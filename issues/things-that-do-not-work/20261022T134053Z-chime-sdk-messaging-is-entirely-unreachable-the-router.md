# Chime SDK Messaging is entirely unreachable: the router resolves requests by sigv4 signing name, so all 5 'chime'-signed services collide and every request is refused with AmbiguousService

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAppInstance

## Description
Cause 1 of 1: the emulator's front-door request router resolves an inbound request to an emulated service by the sigv4 signing name (the credential-scope service field of the Authorization header) instead of by the request's endpoint prefix / Host and the restJson1 URI path. Chime is a service family in which several distinct AWS services deliberately share one signing name, so that key is not unique: the router finds 5 candidate services for every Chime-signed request and refuses to serve any of them. Every chime-sdk-messaging behavioral check therefore dies on its very first setup call (CreateAppInstance on a chime-sdk-identity client, signed with the same 'chime' name), and no messaging operation is ever reached.

AWS: Smithy (services/service-com-amazonaws-chimesdkmessaging-chimemessagingservice/smithy-model/com-amazonaws-chimesdkmessaging-chimemessagingservice.json) — service ChimeMessagingService, version 2021-05-15, protocol restJson1, aws.auth#sigv4 name = 'chime', aws.api#service endpointPrefix = 'messaging-chime', arnNamespace = 'chime'. The sibling Chime SDK services (Chime, Chime SDK Identity, Chime SDK Meetings, Chime SDK Voice, Chime SDK Media Pipelines) share the SAME sigv4 signing name 'chime' while each carries its OWN endpointPrefix ('chime', 'identity-chime', 'meetings-chime', 'voice-chime', 'media-pipelines-chime'). Real AWS therefore disambiguates by the endpoint host the client was pointed at and by each operation's @http URI, never by signing name alone: CreateAppInstance is restJson1 POST /app-instances returning 201 with an AppInstanceArn; CreateChannel is POST /channels -> 201 {ChannelArn}; SendChannelMessage is POST /channels/{ChannelArn}/messages -> 201 {ChannelArn, MessageId, Status}; CreateChannelBan is POST /channels/{ChannelArn}/bans -> 201 {ChannelArn, Member}. 'AmbiguousService' is not a modeled error of this service — its modeled/common errors are BadRequestException (400), ConflictException (409), ForbiddenException (403), ResourceLimitExceededException (400), ServiceFailureException (500), ServiceUnavailableException (503), ThrottledClientException (429), UnauthorizedClientException (401).

Emulator: every call made by a correctly configured botocore chime-sdk-identity / chime-sdk-messaging client is rejected with error code 'AmbiguousService' and a message whose recorded example text is "5 emulated services all claim requests for 'chime': chime, chime, chime, chime, chime; the request is rejected rather than served by an arbitrary one". botocore additionally exhausted its retry budget on it ("reached max retries: 3"), i.e. the refusal is delivered in a form the SDK classifies as retryable rather than as a terminal client error. Hypothesis: the refusal is emitted as a 5xx from the router layer, which is why it is retried; the replay output records only the parsed error code and message. The message also renders all 5 collided candidates with the same display name 'chime' instead of their distinct sdkIds, so the refusal does not even identify which services collided.

Why: a client relying on AWS behavior cannot reach Chime SDK Messaging at all. None of the 51 modeled operations is exercisable — channel CRUD, memberships, moderation (bans/moderators), message send/read/redact/delete, channel search and flow configuration — because the refusal happens before any handler runs. Worse, the refusal masquerades as a retryable server fault, so SDK and application retry loops spin to max attempts and then surface an error code AWS never returns, instead of failing fast or succeeding. No correctness signal for this service is obtainable while this holds.

Fix: the front-door service-resolution/routing layer (the component that maps an inbound request to an emulated service), not any chime-sdk-messaging handler. Resolution must key on the request's endpoint prefix / Host header — and, where absent, on the operation's restJson1 method+URI — with the sigv4 signing name used only as a weak hint; a shared signing name must not be treated as a service identity. A resolution failure must also be rendered as a terminal AWS error shape rather than a retryable one. The same router defect is already filed for other signing-name families, including the sibling Chime services: 20261022T042904Z-chime-sdk-identity-is-entirely-unreachable-the-router.md and 20261022T075458Z-chime-sdk-media-pipelines-is-entirely-unreachable-the.md (plus wisdom, lambda, lex, greengrassv2, migrationhub-config, docdb, bedrock-runtime variants). None of those carries chime-sdk-messaging's replay keys, so this issue is filed separately and must be re-replayed against the 12 chime-sdk-messaging checks listed below.

Traces: all 12 chime-sdk-messaging behavioral checks fail identically, each aborting on its first call (CreateAppInstance) with AmbiguousService: channel-ban-blocks-banned-member-rejected, concurrent-send-messages-all-persisted, delete-channel-message-by-moderator-rejected, list-private-channels-requires-app-instance-admin-rejected, non-persistent-message-read-back-rejected, private-channel-non-member-read-denied, redact-message-removes-content-keeps-message, restricted-channel-member-add-rejected, search-channels-by-membership-reflects-join, send-message-idempotent-client-request-token, send-message-read-back-in-order, send-message-token-reuse-new-content-rejected.
