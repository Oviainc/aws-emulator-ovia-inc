# dynamodb__kinesis__lambda: 2 net-new causes — in-function DynamoDB calls are served without an identity-based grant, and a Kinesis ESM with retry bounds / an OnFailure destination never invokes its function

> _Note: this issue was identified against the code base at commit `7fd503bab2d5afd1eb19742236a7b553a6c3348b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetItem

## Description
Two net-new root causes in the dynamodb__kinesis__lambda group. Neither is covered by an existing issue: the open issues 20261105T111951Z-dynamodb-kinesis-lambda-the-lambda-python-runtime-has.md (no AWS SDK in the python runtime), 20261106T011422Z-dynamodb-kinesis-lambda-a-trim-horizon-kinesis-event.md (TRIM_HORIZON Kinesis ESM never invokes), 20261029T180026Z-dynamodb-kinesis-lambda-event-source-mappings-are-created-for-non-existent.md and 20261101T210635Z-dynamodb-kinesis-lambda-an-event-source-mapping-s.md (OnFailure batch-info pointer) are named here for the fixer's benefit, but none of them carries the replay keys of the four checks below, so both causes are filed here. In this run the in-function SDK DID reach DynamoDB (the handlers' GetItem/PutItem both returned), so cause 1 is an authorization defect, not an SDK-availability one.

Cause 1 of 2: a DynamoDB data-plane call made from inside a Lambda function is served even though the function's execution role carries no identity-based statement allowing that action. Failing checks: dynamodb__kinesis__lambda.check-lambda-dynamodb-getitem-without-permission, dynamodb__kinesis__lambda.check-lambda-dynamodb-putitem-without-permission.
AWS: credentials injected into the execution environment are the role's assumed-role session, and every SDK call they sign is authorized against that role's identity-based policy. An action the policy does not allow is refused by implicit deny: HTTP 400 with error code AccessDeniedException (Smithy: dynamodb GetItem/PutItem do NOT model AccessDeniedException — it is the auth framework's error, served as DynamoDB's awsJson1_0 400 shape; the modeled errors are ResourceNotFoundException/ProvisionedThroughputExceededException/etc., none of which applies). The message AWS words for an implicit identity-based deny is, with its fixed text exactly as given here and its variable parts taken from the request and state: `User: arn:aws:sts::<account-id>:assumed-role/<execution-role-name>/<function-name> is not authorized to perform: <service>:<Action> on resource: <resource-arn> because no identity-based policy allows the <service>:<Action> action`. Variable parts: <account-id>, <execution-role-name>, <function-name> (the role session name Lambda uses), <resource-arn> (the table ARN from the request) and the action string; fixed text: `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no identity-based policy allows the `, ` action`. A refused PutItem must also leave no item behind.
Emulator: both calls are served successfully. In check-lambda-dynamodb-getitem-without-permission the role is granted only dynamodb:PutItem on the table, yet the handler's GetItem returns 200 — the invocation payload is `{'put_ok': True, 'get_ok': True, 'get_error': None}` where get_ok must be False and get_error must be the AccessDeniedException message above. In check-lambda-dynamodb-putitem-without-permission the role is granted only dynamodb:GetItem, yet PutItem returns 200 (`AssertionError: Lambda succeeded writing to DynamoDB without IAM permission`) and the item is written. No AccessDeniedException is produced for either action.
Why: a client cannot test or rely on least-privilege. Every negative IAM scenario passes vacuously, a role that was meant to be read-only writes, and code that catches AccessDeniedException to fall back or alarm never takes that branch — a policy regression that AWS would refuse is invisible here.
Fix: the request-authorization path for in-function SDK calls — the component that resolves the execution-role session from the injected credentials and evaluates the role's identity-based policy before the DynamoDB operation handler runs, plus the error serializer that must emit the 400 AccessDeniedException shape and the implicit-deny message template.
Traces: dynamodb__kinesis__lambda.check-lambda-dynamodb-getitem-without-permission, dynamodb__kinesis__lambda.check-lambda-dynamodb-putitem-without-permission.

Cause 2 of 2: a Kinesis-sourced event source mapping configured with MaximumRetryAttempts/MaximumRecordAgeInSeconds (and, in one check, DestinationConfig.OnFailure) is created and reports its bounds, but never invokes the mapped function at all, so neither the retry-then-discard behavior nor the OnFailure selectivity is ever exercised. Failing checks: dynamodb__kinesis__lambda.xsvc-lambda-2-kinesis-esm-retry-exhaustion-drops-poison-batch-after-two-attempts, dynamodb__kinesis__lambda.xsvc-lambda-2-kinesis-esm-healthy-record-sends-no-on-failure-message.
AWS: CreateEventSourceMapping (POST /2015-03-31/event-source-mappings, 202; Smithy: StartingPosition -> EventSourcePosition, MaximumRetryAttempts range -1..10000, MaximumRecordAgeInSeconds range -1..604800, BisectBatchOnFunctionError boolean, DestinationConfig.OnFailure.Destination; errors InvalidParameterValueException 400 / ResourceNotFoundException 404 / ResourceConflictException 409) is accepted, and an Enabled mapping then polls the stream from the configured position and invokes the function with the aws:kinesis event envelope. With MaximumRetryAttempts=N and BisectBatchOnFunctionError=false, a batch whose handler always throws is delivered exactly N+1 times with the IDENTICAL batch, then discarded together with its healthy siblings, and the poller moves past it in shard order and delivers the records written behind it exactly once. With DestinationConfig.OnFailure set, only the discarded batch yields a destination message (a KinesisBatchInfo pointer whose startSequenceNumber/endSequenceNumber/batchSize bound that batch); successfully processed records yield none. No error is involved on this path — the calls succeed and delivery is an asynchronous effect.
Emulator: no invocation ever occurs. Both checks block on their first effect poll — the retry check on `the first (failing) attempt on the poison batch` (the handler's DynamoDB UpdateItem into the audit sink never appears) and the healthy-record check on `the healthy records [0, 1, 2] processed successfully` — and each ends with `Error: Check timed out after 60.0s`. Every control-plane call (CreateStream, PutRecord, CreateEventSourceMapping, GetEventSourceMapping, CreateQueue) succeeds and returns the configured bounds; the data path is silently inert, with no refusal and no non-2xx anywhere.
Why: a client that wires Kinesis to Lambda gets a mapping that reports healthy and delivers nothing, so poison-pill handling (retry budget, batch discard, per-shard head-of-line unblocking) and the OnFailure dead-letter contract cannot be built or tested. Because there is no error, there is nothing to retry or alarm on — the failure shows up only as missing downstream data and, on AWS, as a permanently blocked shard.
Fix: the Lambda event-source-mapping poller for Kinesis sources — the component that drives an Enabled mapping to read shards from the configured StartingPosition, invoke the function with the aws:kinesis envelope, count attempts against MaximumRetryAttempts/MaximumRecordAgeInSeconds, discard the batch and advance the shard, and emit the OnFailure destination message for the discarded batch only.
Traces: dynamodb__kinesis__lambda.xsvc-lambda-2-kinesis-esm-retry-exhaustion-drops-poison-batch-after-two-attempts, dynamodb__kinesis__lambda.xsvc-lambda-2-kinesis-esm-healthy-record-sends-no-on-failure-message.
