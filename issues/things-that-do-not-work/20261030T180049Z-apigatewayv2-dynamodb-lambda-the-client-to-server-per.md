Cause 1 of 1: a deployed WEBSOCKET stage's execute-api data plane never completes the RFC 6455 opening handshake, so continuation-fragment reassembly and the per-reassembled-message size ceiling in the client-to-server direction are never exercised and never enforced. Failing check id: apigatewayv2__dynamodb__lambda.wsduplex-oversize-client-message-rejected-close-1009.

AWS: not modeled in Smithy — the WebSocket data plane is RFC 6455 framing on a long-lived socket, not a modeled operation. The apigatewayv2 model (services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json) describes only the control plane that stands the socket up: Smithy shape ProtocolType is an enum [WEBSOCKET, HTTP]; Api.ProtocolType and Api.RouteSelectionExpression are required; Api.ApiEndpoint doc: "The URI of the API, of the form {api-id}.execute-api.{region}.amazonaws.com. The stage name is typically appended to this URI to form a complete path to a deployed API stage." There is no modeled shape for a frame, an opcode or a close code. Recorded behavior only: a GET to the deployed stage URL carrying Upgrade: websocket / Connection: Upgrade / Sec-WebSocket-Key / Sec-WebSocket-Version: 13 is answered HTTP/1.1 101 Switching Protocols with Sec-WebSocket-Accept derived from the offered key; after that (a) a message sent as RFC 6455 continuation fragments is REASSEMBLED and delivered to the route matched by the route-selection expression as ONE body of the summed length (a target that forwarded each fragment separately would produce one body per fragment), and (b) a reassembled message past the per-message ceiling is refused at the PROTOCOL level — a CLOSE frame, opcode 0x8, whose first two payload bytes are close code 1009 and whose reason is the fixed text `Message too big` — the socket is then torn down and the route integration is never invoked for those bytes. Fixed text of that refusal: opcode 0x8, code 1009, reason exactly `Message too big`. The only request/state-derived parts are which connection is closed and which message bytes were refused; no name, id, length or timestamp from any single run belongs in it. The refusal is message-scoped, not API-scoped: other sockets on the same stage keep working and keep completing duplex round trips.

Emulator: the check never gets far enough to observe any of that. It polls the upgrade (its own budget is 150 s, interval 3 s, description "WebSocket handshake against stage <stage>") and the suite cap fires first: `Error: Check timed out after 60.0s`, verdict [mismatch]. No 101 is ever returned on the deployed stage, so there is no socket on which to send the accepted control message (7 continuation fragments of 16 KiB = 114688 bytes) or the refused one (10 fragments = 163840 bytes). Consequently none of these is observable: the one-body reassembly guarantee, the opcode-0x8 / 1009 / `Message too big` CLOSE, the tear-down of the refused socket, the 'integration never invoked for the refused bytes' guarantee (no msg# row for the refused digest), nor the surviving-twin-socket round trip afterwards. The control-plane legs preceding the handshake (DynamoDB table, Lambda function, CreateApi ProtocolType=WEBSOCKET, CreateIntegration AWS_PROXY, CreateRoute for $connect/$disconnect/$default, CreateDeployment, CreateStage) do succeed, so this is a data-plane gap, not a setup failure.

Why: a client relying on AWS's behavior gets no WebSocket data plane at all, and specifically no back-pressure contract. Instead of a 101 followed by a 1009 CLOSE carrying `Message too big` — which is the only signal telling the client to resize and retry — it sees an upgrade that never completes and hangs until its own deadline. Client code that handles 1009 by chunking never runs; and once the handshake is served, a reader with no per-reassembled-message gate would silently accept oversize bodies and invoke the integration for them, which is over-permissive in exactly the direction this check grades.

Fix: the apigatewayv2 WEBSOCKET execute-api data-plane listener and its frame layer. First the upgrade path for a deployed stage must answer 101 Switching Protocols with a correct Sec-WebSocket-Accept instead of leaving the request unanswered / falling through to the generic not-found handler; then the frame reader must reassemble continuation fragments into one message before dispatch, and a per-reassembled-message size gate must emit the opcode-0x8 CLOSE with code 1009 and reason `Message too big`, close that connection, and skip integration invocation for those bytes while leaving other connections on the stage untouched. Capability gap in the data-plane router / WebSocket session layer, not an error-shape bug in a control-plane handler.

Traces: apigatewayv2__dynamodb__lambda.wsduplex-oversize-client-message-rejected-close-1009.
