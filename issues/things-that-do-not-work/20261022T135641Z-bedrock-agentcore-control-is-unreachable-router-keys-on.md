# Bedrock AgentCore Control is unreachable: router keys on the shared 'bedrock-agentcore' sigv4 name (AmbiguousService 500), plus S3 tagged PutObject stub and valueless CloudFormation Outputs (3 causes)

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAgentRuntime

## Description
Three distinct root causes behind the bedrock-agentcore-control behavioral failures. A fixer must close ALL THREE before submitting.

=== Cause 1 of 3: every bedrock-agentcore-control request is refused 500 AmbiguousService because the router resolves an emulated service by its sigv4 signing name ===
AWS: Smithy (com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol): service AmazonBedrockAgentCoreControl, version 2023-06-05, protocol restJson1, awsService.endpointPrefix "bedrock-agentcore-control", awsService.arnNamespace "bedrock-agentcore", sigv4Name "bedrock-agentcore". Smithy (com-amazonaws-bedrockagentcore-amazonbedrockagentcore): service AmazonBedrockAgentCore, version 2024-02-28, protocol restJson1, awsService.endpointPrefix "bedrock-agentcore", sigv4Name "bedrock-agentcore". The two services therefore SHARE a sigv4 signing name while having DIFFERENT endpoint prefixes/hosts and disjoint restJson1 routes. On AWS the signing name is not a service identity: each request is dispatched by the endpoint it is sent to and by its HTTP method+path, and every modeled operation answers its own modeled status (2xx on success, the operation's modeled 4xx error otherwise, e.g. ValidationException, AccessDeniedException, ResourceNotFoundException, ConflictException).
Emulator: every control-plane call is answered with HTTP 500 and error code `AmbiguousService`; example recorded message: "2 emulated services all claim requests for 'bedrock-agentcore': bedrock-agentcore, bedrock-agentcore; the request is rejected rather than served by an arbitrary one". The client exhausts its retries ("reached max retries: 3") because the status is a 5xx. This hits every operation exercised by the suite, including CreateAgentRuntime, CreateAgentRuntimeEndpoint, CreateGateway, CreateGatewayTarget, CreateGatewayRule, BatchPutGatewayRateLimits, CreateMemory, CreateDataset, CreateDatasetVersion, AddDatasetExamples, CreateBrowser, CreateBrowserProfile, CreateCodeInterpreter, CreateConfigurationBundle, CreateApiKeyCredentialProvider, CreateOauth2CredentialProvider, CreatePaymentCredentialProvider, CreatePaymentManager, CreatePolicyEngine, CreateHarness, CreateEvaluator, CreateOnlineEvaluationConfig, CreateWorkloadIdentity, ListAgentRuntimes, ListGateways, GetBrowser, PutResourcePolicy and TagResource.
Why: the whole AgentCore control plane is unusable — no resource can be created, read, listed or tagged. Negative-class clients are hurt twice: a caller that expects a modeled 400-class rejection (ValidationException for a bad maxResults/scope/schema, AccessDeniedException without IAM permission, ResourceNotFoundException for a missing resource, ConflictException for a duplicate name or a concurrent writer) instead sees a retryable 500 with a code that is not in the model at all, so SDK error handling, waiters and retry policies all behave wrongly.
Fix: the request-routing / service-registration component that maps an inbound request to an emulated service — dispatch on the endpoint prefix (host) and the restJson1 method+URI route, not on the sigv4 signing name, so bedrock-agentcore-control and bedrock-agentcore can both be served. The same router shape is already filed for other services (20261022T032542Z-application-autoscaling-lambda-lambda-is-unreachable-four-emulated-services-all-claim.md, 20261022T092619Z-greengrassv2-every-request-rejected-with-ambiguousservice-because-greengrass.md, 20261022T110819Z-migrationhub-config-is-entirely-unreachable-router-resolves-by.md); none of them covers bedrock-agentcore.
Traces: 108 failing checks, all with the identical AmbiguousService detail — e.g. bedrock-agentcore-control.agent-runtime-create-returns-creating-status, bedrock-agentcore-control.gateway-create-lifecycle-ready, bedrock-agentcore-control.memory-lifecycle-and-delete, bedrock-agentcore-control.list-agent-runtimes-maxresults-range-rejected (mismatch: "expected ValidationException, got 'AmbiguousService'"), bedrock-agentcore-control.create-agent-runtime-without-iam-permission-denied (mismatch: "expected AccessDeniedException, got AmbiguousService"). Full list in trace_ids below.

=== Cause 2 of 3: S3 PutObject refuses any request that carries the x-amz-tagging header ===
AWS: Smithy (com-amazonaws-s3-amazons3): PutObject input member `Tagging` is bound to httpHeader "x-amz-tagging" (target TaggingHeader); PutObject is `PUT /{Bucket}/{Key+}` with success code 200, and its only modeled errors are EncryptionTypeMismatch, InvalidRequest, InvalidWriteOffset and TooManyParts (all 400). A PutObject that supplies object tags therefore succeeds with 200 and an ETag exactly as an untagged one does.
Emulator: the call fails with error code `NotImplemented`; recorded message example: "operation PutObject with x-amz-tagging is scaffolded but not implemented in this emulator". PutObject itself is implemented — only the tagged variant is refused, so this is a partially-implemented operation rather than a plain stub (the suite did not mark it as already filed).
Why: any client that uploads an object together with its tags (the normal way to stage a tagged deployment artifact) gets a non-modeled failure instead of a stored object, and every downstream step that reads that object fails.
Fix: the s3 PutObject handler/validation (services/service-com-amazonaws-s3-amazons3/src/ops/put_object.rs) — parse the Tagging header into the object's tag set and store it instead of rejecting the request.
Traces: bedrock-agentcore-control.agent-runtime-endpoint-pinned-version-survives-runtime-update.

=== Cause 3 of 3: CloudFormation stacks declaring AWS::BedrockAgentCore::* resources reach CREATE_COMPLETE but DescribeStacks returns Outputs entries with no OutputValue ===
AWS: Smithy (com-amazonaws-cloudformation): the `Output` structure carries OutputKey and OutputValue ("The value associated with the output"). After a stack reaches CREATE_COMPLETE, DescribeStacks returns every Output declared by the template with its resolved value — here `!GetAtt Memory.MemoryId`, and the equivalent GetAtt outputs of the agent-runtime, gateway and workload-identity templates.
Emulator: the stack_create_complete waiter succeeds, but `describe_stacks(...)["Stacks"][0]["Outputs"]` contains entries that have OutputKey and NO OutputValue member, so the checks raise `KeyError: 'OutputValue'` while building {OutputKey: OutputValue}. The resolved GetAtt value is never produced (Hypothesis: the AWS::BedrockAgentCore::* resource types are not provisioned by the CFN engine, so there is no attribute to resolve, yet the stack is still reported CREATE_COMPLETE).
Why: a client that deploys AgentCore resources with CloudFormation and reads the stack outputs to find the created resource id cannot proceed at all, and is additionally told the stack succeeded when nothing was created.
Fix: the CloudFormation stack-provisioning/outputs component — resolve declared Outputs (GetAtt/Ref) from provisioned resource state before reporting CREATE_COMPLETE, and provision the AWS::BedrockAgentCore::Memory / ::Runtime / ::Gateway / ::WorkloadIdentity resource types into the agentcore service state. Same shape already filed for other resource types: 20261022T043627Z-fis-describestacks-omits-the-outputs-member-for-a-stack.md, 20261022T064119Z-firehose-cloudformation-deployed-firehose-delivery-streams-are-never-provisioned.md, 20261022T031509Z-xray-cloudformation-never-provisions-aws-xray-group-aws-xray.md — none covers AWS::BedrockAgentCore::*.
Traces: bedrock-agentcore-control.deploy-memory-cfn-behaves, bedrock-agentcore-control.deploy-agent-runtime-cfn-behaves, bedrock-agentcore-control.deploy-gateway-cfn-behaves, bedrock-agentcore-control.deploy-workload-identity-cfn-behaves.
