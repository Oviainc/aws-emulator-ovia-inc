# EC2 DescribeInstanceTypes instance-type catalog returns wrong and missing attribute values

> _Note: this issue was identified against the code base at commit `ab92470025dd8eeb501814706ada4aa2b617e26c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
Cause 1 of 1 (one root cause, observed in 90 net-new divergence clusters). Every one of the 90 net-new DescribeInstanceTypes clusters in this replay is the same defect: the emulator's instance-type catalog is synthesised from a size/family heuristic instead of carrying AWS's per-instance-type attribute data, so for the instance types the corpus reads back (the ec2-catalog-describe-instance-types-* fixtures walk the catalog family by family) the answer is HTTP 200 with wrong or absent attribute values. The clusters are not blocked by a stub and are not owned by any open issue; no open issue mentions the instance-type catalog.

AWS: Smithy: DescribeInstanceTypes returns instanceTypeSet.item (InstanceTypeInfo) per instance type, with - among the members this replay flags - cpuBurstModel, dedicatedHostsSupported, hibernationSupported, ebsInfo.attachmentLimitType, ebsInfo.maximumEbsAttachments, ebsInfo.ebsOptimizedInfo (EbsOptimizedInfo{baselineBandwidthInMbps integer, baselineIops integer, baselineThroughputInMBps double, maximumBandwidthInMbps integer, maximumIops integer, maximumThroughputInMBps double}), memoryInfo.sizeInMiB, processorInfo.sustainedClockSpeedInGhz, vCpuInfo.validCores, networkInfo.* (bandwidthWeightings, connectionTrackingConfiguration.defaultTcpEstablishedTimeout, defaultNetworkCardIndex, enaSrdSupported, encryptionInTransitSupported, flexibleEnaQueuesSupport, ipv4AddressesPerInterface, ipv4AddressesPerSecondaryInterface, ipv6AddressesPerInterface, maximumNetworkCards, maximumNetworkInterfaces, networkCards, networkPerformance, secondaryNetworkSupported, trafficMirroringSupport), inferenceAcceleratorInfo, neuronInfo, phcSupport and rebootMigrationSupport. The values themselves are per-instance-type facts of the AWS catalog; the recording is the source for each (recorded behavior only for the individual numbers).
Emulator: for each instance type in these fixtures it returns 200 but (a) OMITS members it does not model at all (e.g. cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.bandwidthWeightings, inferenceAcceleratorInfo and neuronInfo for accelerated families), (b) returns values derived from a size heuristic rather than the real catalog (EBS baseline/maximum bandwidth, IOPS and throughput, maximumEbsAttachments, memoryInfo.sizeInMiB, processorInfo.sustainedClockSpeedInGhz, networkInfo address/interface/card counts, connection-tracking timeouts, vCpuInfo.validCores lists), and (c) reports capability booleans by blanket default rather than per type (dedicatedHostsSupported and hibernationSupported true where AWS says false, ebsInfo.attachmentLimitType "shared" where AWS says "dedicated"). The double-typed members are also serialized without their fractional form (e.g. an integer-looking '1275' where AWS emits '1875.0').
Why: DescribeInstanceTypes is the sizing/capability oracle. A client that filters instance types on these attributes (EBS bandwidth, ENA/EFA/SRD support, network cards, hibernation, dedicated-host support, accelerator presence, valid core counts) gets a different candidate set from the emulator than from AWS, and code that reads capacity numbers computes wrong limits - silently, because the call succeeds.
Fix: the DescribeInstanceTypes handler's catalog data source - back it with the real per-instance-type attribute table (and emit the double-typed EbsOptimizedInfo members in their modeled form) instead of deriving attributes from the type name; the member omissions belong in the same catalog/serializer.
Traces: representative ec2-catalog-describe-instance-types-a1-c9g#task#33 (c8ine.* sizes), plus ec2-catalog-describe-instance-types-a1-c9g#task#34 (c9g.* sizes) and ec2-catalog-describe-instance-types-c9gd-m6gd#task#28 (inf1.* sizes, where inferenceAcceleratorInfo/neuronInfo are missing entirely). 87 further clusters of this same cause are spread over the remaining steps of the ec2-catalog-describe-instance-types-* fixtures; re-replaying those fixtures in full is the check for this fix.
