# Translate rejection paths: wrong error class for oversize text, generic not-found and language-pair messages, unsorted-enum validation text, and no TagResource tag-limit check

> _Note: this issue was identified against the code base at commit `5b3f288c64c79f31818824eff80fa309a30ec0e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TranslateText

## Description
Five net-new causes in Amazon Translate's refusal paths. The shared fault is that the emulator does not reproduce AWS's refusal IDENTITY: it lets generic shape-constraint validation pre-empt a modeled business error, and where it does pick the right error class it fills `Message` with the Smithy shape's documentation sentence instead of the operation-specific message AWS emits. A fixer must close all FIVE before submitting.

Related open issue: `20261029T184304Z-translate-error-responses-use-wrong-status-and-message.md` already describes the not-found message templates (its Causes 1-3) and the ListLanguages enum ordering (its Cause 4) from WIRE fixtures. Causes 3 and 4 below are the same root causes reached from the behavioral suite and are carried here only so the check ids in `trace_ids` are re-replayable; close them together with that issue. Causes 1, 2 and 5 are NOT in that issue.

Cause 1 of 5 — TranslateText with `Text` over the 10,000-character limit is refused as a generic ValidationException instead of TextSizeLimitExceededException.
AWS: Smithy: TranslateText input `Text` targets `BoundedLengthString` @length 1..10000, @pattern `^[\P{M}\p{M}]{1,10000}$`; the operation models `TextSizeLimitExceededException` (httpError 400, doc "The size of the text you submitted exceeds the size limit. Reduce the size of the text or use a smaller document and then retry your request."). The model binds both the length constraint and that error, so the model alone does not pick one; the recorded behavior is that AWS answers HTTP 400 with error code `TextSizeLimitExceededException` and `Message` = the template `Input text size exceeds limit. Max length of request text allowed is 10000 bytes while in this request the text size is <n> bytes`. Fixed text: `Input text size exceeds limit. Max length of request text allowed is 10000 bytes while in this request the text size is `, ` bytes`; variable part: `<n>`, the UTF-8 byte length of the request's `Text` (10001 for a 10001-character ASCII input). The documented limit is a BYTE limit, so the oversize check belongs to the operation, not to a character-length shape constraint.
Emulator: refuses with error code `ValidationException`, i.e. the shared input-constraint validator rejects the request on `Text`'s @length before the handler runs, so the modeled `TextSizeLimitExceededException` is never reachable for an oversize request and the size-limit message is never emitted.
Why: a client branching on the error code sees `ValidationException`, which is not a modeled error of TranslateText at all, so SDK error-shape handling, retry classification and `except TextSizeLimitExceededException` paths never fire; the caller also loses the actual and allowed byte counts it needs to chunk the input.
Emulator component to fix: the TranslateText handler's own size validation and its ordering relative to the generic shape-constraint validator in the translate service crate — the oversize-text case must raise the modeled `TextSizeLimitExceededException` with AWS's message template before (or instead of) the @length constraint rejection.
Traces: translate.translate-text-size-limit-exceeded-rejected.

Cause 2 of 5 — UnsupportedLanguagePairException carries the Smithy doc sentence instead of AWS's message naming the pair.
AWS: Smithy: `UnsupportedLanguagePairException` (httpError 400) has members `Message`, `SourceLanguageCode`, `TargetLanguageCode`; the shape doc is "Amazon Translate does not support translation from the language of the source text into the requested target language." The recorded behavior is that `Message` is NOT that doc sentence but the template `Unsupported language pair: <source> to <target>.` Fixed text: `Unsupported language pair: `, ` to `, `.`; variable parts: the request's `SourceLanguageCode` and `TargetLanguageCode`. The error code (`UnsupportedLanguagePairException`) and status 400 are already correct in the emulator; only the message diverges.
Emulator: returns `Message` = `Amazon Translate does not support translation from the language of the source text into the requested target language.` — the shape documentation, with no language codes interpolated. The handler hardcodes this as the constant `UNSUPPORTED_LANGUAGE_PAIR` and uses it for every unsupported-pair refusal (same-language, unsupported source, unsupported target, and the auto-detect path).
Why: the message is the only place a caller sees WHICH pair was rejected when it batches translations across pairs; AWS's text names both codes, the emulator's names neither. Any client or conformance test matching AWS's message never matches, and log-based diagnosis of a rejected pair is impossible.
Emulator component to fix: the TranslateText handler's unsupported-pair refusal in the translate service crate — build `Message` from the resolved source and target codes using AWS's template rather than emitting the model's doc constant.
Traces: translate.translate-text-unsupported-language-pair-rejected.

Cause 3 of 5 — ResourceNotFoundException for a missing terminology carries the generic shape doc instead of the per-operation not-found template.
AWS: Smithy: `ResourceNotFoundException` has a single `Message` member; its shape doc is the generic sentence "The resource you are looking for has not been found. Review the resource you're looking for and see if a different resource will accomplish your needs before retrying the revised request." The recorded behavior is that AWS fills `Message` with an operation-specific template instead: GetTerminology and TranslateText (terminology named in `TerminologyNames`) use `The Terminology for <accountId> <name> was not found`; DeleteTerminology uses `The TerminologyMetadata for <accountId> <name> was not found` — note the different resource word. Fixed text: `The Terminology for ` / `The TerminologyMetadata for ` and ` was not found`; variable parts: the caller's 12-digit account id and the `Name` (or `TerminologyNames` entry) from the request, separated by a single space. The error code `ResourceNotFoundException` is already correct in the emulator.
Emulator: every one of these paths returns the generic shape-doc sentence with no account id and no resource name — the handler funnels them through a single shared `terminology_not_found()` constructor in the service state module, so all three operations emit one identical string.
Why: a caller cannot tell WHICH terminology was missing, and cannot tell a terminology-record miss from a terminology-metadata miss; any client or test matching AWS's per-operation wording never matches.
Emulator component to fix: the shared `terminology_not_found()` message constructor in the translate service crate's state module and its three call sites (the GetTerminology handler, the DeleteTerminology handler, and the terminology-resolution step inside the TranslateText handler) — each must format its own template from the account id and the requested name.
Traces: translate.delete-terminology-then-get-returns-not-found (covers both the GetTerminology-after-delete and the DeleteTerminology-on-a-dead-name templates), translate.translate-text-terminology-reference-not-found-rejected.

Cause 4 of 5 — ListLanguages' out-of-enum validation message renders the enum value set in the wrong order.
AWS: Smithy: `ListLanguages.DisplayLanguageCode` targets enum `DisplayLanguageCode` whose declared values are [de, en, es, fr, it, ja, ko, pt, zh, zh-TW]; the operation models `InvalidParameterValueException` 400 and `UnsupportedDisplayLanguageCodeException` 400. Status and message are recorded behavior only: HTTP 400 with the message `1 validation error detected: Value '<value>' at 'displayLanguageCode' failed to satisfy constraint: Member must satisfy enum value set: [de, zh-TW, pt, ko, en, it, fr, zh, es, ja]`. Fixed text: the frame `1 validation error detected: Value '` / `' at 'displayLanguageCode' failed to satisfy constraint: Member must satisfy enum value set: [` / `]`, the member path `displayLanguageCode`, AND the bracketed list itself — AWS emits those ten codes in that exact non-alphabetical order, which is neither sorted nor the model's declaration order. Variable part: only the rejected value from the request.
Emulator: emits the right frame and the right member path but sorts the value set alphabetically: `[de, en, es, fr, it, ja, ko, pt, zh, zh-TW]`.
Why: status and error class are right, but any client or conformance test asserting AWS's validation text never matches, and tooling that parses the accepted-value list out of the message reads a list AWS never emits.
Emulator component to fix: the shared constraint-violation message serializer used by the translate input validation — the enum value set must be emitted in AWS's fixed order for this message rather than sorted.
Traces: translate.list-languages-unsupported-display-language-code-rejected.

Cause 5 of 5 — TagResource does not enforce the 50-tag business limit, so TooManyTagsException is unreachable.
AWS: Smithy: `TagResource` input `Tags` targets `TagList` @length 0..200 and the operation models `TooManyTagsException` (httpError 400, members `message` and `ResourceArn`, doc "You have added too many tags to this resource. The maximum is 50 tags."). A 60-tag call therefore passes shape validation (60 <= 200) and must be refused by the business-rule check with HTTP 400, error code `TooManyTagsException` and `message` = `Allowable tag limit for resource exceeded` — fixed text with no variable part. The refusal must have no effect: the resource's existing tags are unchanged and none of the 60 are applied, while a subsequent in-limit single-tag call succeeds.
Emulator: answers `NotImplemented` ("operation TagResource is scaffolded but not implemented in this emulator"), so the 50-tag rule, its error class and its message do not exist. The unimplemented-stub issue already filed for `src/ops/tag_resource.rs` covers standing the operation up; it does NOT state this limit, its error class or its message, which is why the rule is recorded here.
Why: a client that relies on AWS refusing an over-limit tag set — the common pattern of merging tags and catching `TooManyTagsException` — will, once TagResource answers at all, either have the over-limit set silently accepted (state AWS would never hold) or get an unmodeled error code, and its limit-handling branch never runs.
Emulator component to fix: the TagResource handler's validation in the translate service crate (services/service-com-amazonaws-translate-awsshinefrontendservice-20170701/src/ops/tag_resource.rs) — after shape validation, refuse a request whose resulting user-defined tag count would exceed 50 with the modeled `TooManyTagsException`, atomically, before any tag is written.
Traces: translate.tag-resource-too-many-tags-rejected.
