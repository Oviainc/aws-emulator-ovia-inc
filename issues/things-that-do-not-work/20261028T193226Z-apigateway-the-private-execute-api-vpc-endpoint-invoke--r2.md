=== Cause 1 of 1: a created interface VPC endpoint never advances from `pending` to `available`, so the private-API readiness poll never converges and the check is killed at the harness cap before any API Gateway data-plane call is made ===
AWS: Smithy (com.amazonaws.ec2#AmazonEC2) CreateVpcEndpoint takes VpcId (required), ServiceName, VpcEndpointType, SubnetIds, SecurityGroupIds, PrivateDnsEnabled and answers CreateVpcEndpointResult.VpcEndpoint (shape com.amazonaws.ec2#VpcEndpoint). VpcEndpoint.State targets enum com.amazonaws.ec2#State = [PendingAcceptance, Pending, Available, Deleting, Deleted, Rejected, Failed, Expired, Partial] and is documented "The state of the endpoint"; VpcEndpoint.NetworkInterfaceIds is documented "(Interface, Gateway Load Balancer endpoints, Resource, ServiceNetwork, and Tunnel endpoints only) The network interfaces for the endpoint". DescribeVpcEndpoints (paginated, VpcEndpointIds/Filters) is the way that state is observed. On create, an interface endpoint to an AWS-provided service (here com.amazonaws.<region>.execute-api) is non-terminal: it is answered pending and then reaches available with NO further caller action, in bounded time. Recorded behavior (the model does not spell the wire casing): DescribeVpcEndpoints reports the member in its lowercase spelling (`pending`, then `available`), which this check compares against exactly, and once available the endpoint exposes one ENI per subnet whose PrivateIpAddress is the NLB target.
Emulator: ec2 CreateVpcEndpoint is accepted and returns a VpcEndpointId, but the endpoint's State never changes — DescribeVpcEndpoints keeps reporting the pending value the create stored, forever. The check's poll (`describe_vpc_endpoints(VpcEndpointIds=[E])['VpcEndpoints'][0]['State']` until it is `available` or `failed`, budget 600 s against real AWS) therefore never converges and the suite kills the check at its cap: the only detail reported is "Error: Check timed out after 60.0s". No status or error code diverges — the divergence is a response VALUE that never changes. The cause is still present in the checkout at the replayed commit: services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs stores the endpoint `pending` and records the owed move in `store.vpc_endpoint_moves`, but `vpc_endpoint_moves` in services/service-com-amazonaws-ec2-amazonec2/src/state.rs is mentioned exactly twice — its declaration ("CreateVpcEndpoint answers an endpoint in the non-terminal `pending` state, so the clock owes it `available` TRANSITION_DELAY later whether or not anybody calls again") and its empty initialisation — so `materialize_due_transitions()`, which describe_vpc_endpoints.rs calls before reading, never consumes it. The map is written by the create and read by nothing.
Why: the endpoint's readiness is the gate in front of API Gateway's whole PRIVATE REST-API data plane. A client that provisions an execute-api interface endpoint and waits for it (CloudFormation, CDK, Terraform, botocore's own vpc_endpoint waiters, or a hand-rolled poll) blocks indefinitely instead of either proceeding or getting a modeled refusal, and everything behind the gate is left unexercised: a PRIVATE RestApi reached through that endpoint via a VpcLink/NLB must serve its MOCK integration body while the API's resource policy allows execute-api:Invoke conditioned on StringEquals aws:SourceVpce == that endpoint id; re-pinning the policy to a different vpce- id must make the same path answer HTTP 403 with a JSON body whose "Message" is AWS's authorization-denial text — the fixed text "is not authorized to perform: execute-api:Invoke on resource: " with the principal and the execute-api resource ARN (api id, stage, method, path) taken from the request and the caller's identity, never the API's own body — and must not leak the integration's payload; restoring the original endpoint id must serve it again. None of those three claims has ever been graded against this emulator.
Fix: the EC2 VPC-endpoint state machine, not anything in the apigateway crate — `materialize_due_transitions` must apply the moves held in `vpc_endpoint_moves` (the same retain-and-apply shape the VPC, subnet and carrier-gateway moves beside it use, and the shape `vpc_endpoint_connection_moves` already gets), so an endpoint created by the create handler is reported `available` by the describe handler once the transition delay has passed, whether or not anyone called in between, in the lowercase wire spelling, and with the per-subnet ENIs resolvable by DescribeNetworkInterfaces; the same materialized value must be what the `vpc-endpoint-state` filter and the delete path see. Behind the gate, the API Gateway private data plane must then enforce the RestApi resource policy's aws:SourceVpce condition in the invoke path and produce the 403 denial envelope described above.
