# ssm: 3 net-new causes — a launched EC2 instance never becomes an Online managed node, an aws:ec2:image parameter that fails validation stays readable, and DescribeParameters describes no AWS public parameters

> _Note: this issue was identified against the code base at commit `145c20a94e0bd5c99471752c6f247be888f6ff73`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceInformation

## Description
Three net-new root causes grounded in failing checks the suite lists under '### ssm'. 3 CAUSES — all three must be closed before submitting.

Cause 1 of 3: an EC2 instance the emulator launches with an instance profile carrying AmazonSSMManagedInstanceCore never registers as a Systems Manager managed node, so DescribeInstanceInformation never reports it and every check that needs a managed node polls to its deadline and is killed.
AWS: an instance launched from an Amazon Linux/Windows AMI whose instance profile carries arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore registers with Systems Manager shortly after boot. DescribeInstanceInformation (Smithy, services/service-com-amazonaws-ssm-amazonssm: InstanceInformation$PingStatus -> enum PingStatus Online | ConnectionLost | Inactive, plus LastPingDateTime, AgentVersion, IsLatestVersion, PlatformType, PlatformName, IamRole, IPAddress, ComputerName) then returns one entry for that InstanceId with PingStatus 'Online', filterable by Filters Key=InstanceIds. Only after that do PutComplianceItems/ListComplianceItems/ListResourceComplianceSummaries accept the instance as a ManagedInstance ResourceId, PutInventory/GetInventory/DeleteInventory accept it as an InstanceId, StartSession/ResumeSession/DescribeSessions/GetConnectionStatus have a connected target, and SendCommand/GetCommandInvocation and CreateAssociation/UpdateAssociationStatus have a target the service will accept.
Emulator: no launched instance ever appears Online. The graded form is 'AssertionError: instance i-00000000000000001 never reached PingStatus=Online within 1s (SSM Agent never registered)' (ssm.compliance-summary-server-computed-aggregation); the rest are killed mid-poll with 'TimeoutError: instance(s) {...} reaching PingStatus=Online: the run budget ended first' or 'Error: Check timed out after 60.0s' with no response printed, because the check never gets an answer to assert on. Hypothesis: nothing in the emulator populates the ssm crate's managed-node inventory from an EC2 RunInstances, so describe_instance_information has nothing to project.
Why: the failure mode is a hang, not a refusal — a client that waits for PingStatus=='Online' (or uses `aws ssm wait`) before it does anything has no error code to branch on, and the whole of Compliance, Inventory, Session Manager, Run Command and State Manager against real instances is unreachable. The open issues 20261027T034339Z-ec2-ssm-a-launched-ec2-instance-never-becomes.md and cause 2 of 20261104T121102Z-ec2-ssm-the-duplicate-security-group-rule-refusal.md diagnose the same gate for ec2__ssm checks, but neither carries any of the 40 ssm check ids below.
Fix: SSM managed-node registration in the ssm crate's state (populate managed_nodes for an instance whose profile can reach Systems Manager and project it from describe_instance_information with PingStatus/LastPingDateTime/AgentVersion/PlatformType/IamRole on the emulator's owed-transition clock), then let the compliance, inventory, session and command handlers accept such a node as a target.

Cause 2 of 3: a String parameter created with DataType 'aws:ec2:image' whose value is not an AMI that exists is stored and served, instead of being discarded by the asynchronous validation.
AWS: Smithy, PutParameterRequest$DataType documentation: 'If you call PutParameter with aws:ec2:image data type, a successful HTTP 200 response does not guarantee that your parameter was successfully created or updated. The aws:ec2:image value is validated asynchronously, and the PutParameter call returns before the validation is complete. If you submit an invalid AMI value, the PutParameter operation will return success, but the asynchronous validation will fail and the parameter will not be created or updated.' So PutParameter answers 200 with a Version, and shortly afterwards GetParameter on that name is refused with ParameterNotFound (the parameter never lands); the name stays absent from GetParameter/DescribeParameters.
Emulator: PutParameter answers 200 and the parameter stays readable indefinitely. GetParameter returns the record verbatim — {'Name': '/<name>/param', 'Type': 'String', 'Value': 'ami-c72fca79873e45e5b', 'Version': 1, 'DataType': 'aws:ec2:image', ...} — 10 s after the write (3x the measured positive-path latency), i.e. the asynchronous AMI validation is not performed at all.
Why: a client that stores an AMI id in Parameter Store relies on aws:ec2:image to reject a bad id behind its back; against the emulator a typo'd or deleted AMI id silently becomes the fleet-wide 'current AMI', and launch templates and CloudFormation AWS::SSM::Parameter::Value<AWS::EC2::Image::Id> resolutions read a value AWS would never have published.
Fix: PutParameter's post-commit validation for DataType aws:ec2:image in the ssm parameter-store state — validate the value against the EC2 image catalogue after the 200 and remove (or never commit) the version when the AMI does not exist, so GetParameter answers ParameterNotFound.
Traces: ssm.ec2-image-datatype-validation-is-asynchronous-and-the-parameter-never-lands.

Cause 3 of 3: DescribeParameters over the AWS-owned public /aws/service hierarchy returns an empty list, so public parameters are readable one-by-one but not describable.
AWS: public parameters under /aws/service (e.g. /aws/service/ami-amazon-linux-latest/*) are visible to every account: DescribeParameters with ParameterFilters=[{Key:'Path',Option:'Recursive',Values:['/aws/service/ami-amazon-linux-latest']}] returns those parameters, each confined to the requested path, with Tier 'Standard', DataType 'text', Policies [] and Version >= 1, and an ARN whose account field is EMPTY (arn:aws:ssm:<region>::parameter<name>) because no account owns them; a Name/Equals filter on one of those names describes it too. Recorded behavior only for the list contents (measured on real AWS, us-west-2); the Smithy model does not enumerate the public hierarchy.
Emulator: GetParameter on a public name works (the checks resolve AMI ids through it), but DescribeParameters with that Path filter returns [] — 'AssertionError: asked for the public path explicitly, DescribeParameters describes AWS public parameters (measured on real AWS, us-west-2); it returned nothing'.
Why: a client that discovers which public AMI aliases exist (the normal way to pick an AMI family, and what CDK/console pickers do) sees an empty hierarchy and concludes the parameters do not exist, even though reading them by exact name succeeds. The open issue 20261103T215115Z-ssm-validationexception-constraint-text-documentalreadyexists-wording-the-cloudformation.md touches the public /aws/service hierarchy from another corpus but does not carry this check id.
Fix: DescribeParameters' filtering/projection in the ssm parameter-store state — include the seeded public /aws/service parameters in the Path/Name filter result with their public projection (Tier Standard, DataType text, empty Policies, account-less ARN).
Traces: ssm.public-parameter-reference-data-readable-not-owned.
