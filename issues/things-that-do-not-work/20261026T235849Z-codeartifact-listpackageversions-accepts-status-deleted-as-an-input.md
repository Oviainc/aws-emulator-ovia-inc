# CodeArtifact: ListPackageVersions accepts status=Deleted as an input filter instead of refusing it, and the pypi repository endpoint never ingests through an external connection so package-origin upstream=BLOCK is unverifiable (2 causes)

ListPackageVersions

## Description
Two distinct net-new root causes in the CodeArtifact emulator, both reached through the `codeartifact` service. Both operations ARE implemented and answer (neither is a scaffold stub). Numbered so each can be closed individually; a fixer must close BOTH before submitting.

Cause 1 of 2: ListPackageVersions accepts `status=Deleted` as a filter and returns a 200 listing, where AWS refuses that one enum value as an input.
AWS: Smithy, ListPackageVersions input member `status` targets `PackageVersionStatus`, whose declared values are Published | Unfinished | Unlisted | Archived | Disposed | Deleted (httpQuery `status`, POST /v1/package/versions); the operation models ValidationException with httpError 400 ("The operation did not succeed because a parameter in the request was sent with an invalid value"). The model therefore ACCEPTS `Deleted` at the enum level, but the service does not accept it as an INPUT filter: `DELETED` is an output-only lifecycle state, and a request carrying `status=Deleted` is refused with HTTP 400, error code `ValidationException`, message `Deleted is not a valid input status` (recorded behavior only — the divergence is exactly that the enum is wider than the set of filterable values). Message anatomy: the fixed text is `is not a valid input status`; the leading token is the request-supplied `status` value, rendered in the model's own casing as it arrived (`Deleted`). The positive control in the same check shows `status=Published` must keep working, so this is a per-value refusal, not a refusal of the filter.
Emulator: the request succeeds. `services/service-com-amazonaws-codeartifact-codeartifactcontrolplaneservice/src/ops/list_package_versions.rs` applies `status` as a generic exact string match over stored versions (`input.status.as_deref().is_none_or(|status| status == version.status)`), with no input-value allow-list anywhere ahead of it, so `status=Deleted` is treated as a legitimate filter and answers HTTP 200 with an empty `versions` list. The replay reports `AssertionError: the call SUCCEEDED where real AWS rejects it — there is no error code to compare`.
Why: a client cannot discover that DELETED is not queryable. Worse, the emulator's answer is indistinguishable from a successful query that found nothing, so code written to "list the deleted versions" looks supported here and gets a 400 ValidationException in production on the first call. It also hides the real semantic the check is grading — that DeletePackageVersions genuinely removes the version and frees the version number for re-publication, which cannot be graded because the check stops at this refusal.
Fix: the input validation for the `status` member in the ListPackageVersions handler (`src/ops/list_package_versions.rs`), ahead of the paging/filter call — reject the output-only lifecycle values with the modeled ValidationException (400) built from the supplied value, and keep the remaining values filtering as today. The same input-only/output-only split should be shared with any other operation that takes a PackageVersionStatus as input rather than re-derived per handler.
Traces: codeartifact.deleted-package-version-frees-the-version-number.

Cause 2 of 2: a repository with `public:pypi` as an external connection never ingests any version, so upstream ingestion (and the origin restriction that is supposed to block it) is unobservable.
AWS: AssociateExternalConnection + PutPackageOriginConfiguration (Smithy: POST /v1/package, required domain + repository + format + package + restrictions:PackageOriginRestrictions{publish:AllowPublish, upstream:AllowUpstream}, both required; `upstream` is documented as "the package origin configuration that determines if new versions of the package can be added to the repository from an external connection or upstream source"). Recorded behavior for the data plane: the pypi repository endpoint returned by GetRepositoryEndpoint speaks the PyPI Simple Repository API, so GET `<endpoint>/simple/<project>/` with `Accept: application/vnd.pypi.simple.v1+json` and the CodeArtifact bearer token as HTTP Basic (`aws:<token>`) answers a JSON index whose `files[].url` entries are downloadable; downloading one causes the service to INGEST that version into the repository, after which ListPackageVersions reports it with originType EXTERNAL. For a package carrying restrictions {publish: BLOCK, upstream: BLOCK} the same fetch must NOT ingest anything: the package keeps zero versions, and GetPackageVersionAsset for any version of it is refused `ResourceNotFoundException` (404) with the package-version-not-found message built from the request coordinate.
Emulator: nothing is ever ingested. The repository endpoint the emulator hands out serves no pypi data plane, so every index/file fetch fails and the check's ingestion trigger is a no-op; its bounded poll for the UNRESTRICTED control package (`toml`) therefore never sees a version and the harness kills the check at its 60s ceiling (reported verdict: `Check timed out after 60.0s`). The timeout is the permanent absence of ingestion, not a slow response — the blocked-package legs ahead of it pass only vacuously, because a store that ingests nothing at all satisfies "the blocked package has no versions" for the wrong reason.
Why: external connections are the main reason to run CodeArtifact, and with no ingestion path every upstream behavior is a silent no-op that *looks* correct: a blocked package has no versions, an allowed package also has no versions, and a client cannot tell the difference. Any test asserting that origin restrictions keep a package out of a repository passes here against an emulator that would equally "block" a package it was told to allow, so the restriction is validated green without ever being enforced.
Fix: in the CodeArtifact service, (a) the pypi package-format data-plane handlers on the repository endpoint (Simple Repository API index + file download, bearer/Basic auth as the npm endpoint does), backed by the same package/asset state the control-plane PublishPackageVersion and GetPackageVersionAsset handlers read; and (b) the upstream/external-connection resolution in that data plane, which on a fetch miss must fetch from the associated external connection, persist the version as an EXTERNAL-origin version visible to ListPackageVersions, and consult the package's origin configuration first so an `upstream: BLOCK` package is never ingested while an unrestricted sibling is. PutPackageOriginConfiguration must keep pre-creating the package record for a package that has no versions yet, so the restriction exists before the first fetch.
Traces: codeartifact.package-origin-configuration-blocks-upstream-ingestion.
