# ListSchemas serves a seeded AWS-managed catalog whose membership, ordering and VersionCount diverge from the published registry

> _Note: this issue was identified against the code base at commit `355c5d16add239c66c8799ffa26377be788e0f43`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSchemas

## Description
GET /v1/registries/name/aws.events/schemas (ListSchemas over the service-owned catalog) answers 200 with a Schemas list that does not match the catalog AWS publishes. The replay walked the catalog page by page and EVERY page diverged: 50 of the 63 divergence clusters in this sweep are ListSchemas on fixture schemas-catalog-list-schemas, covering 221 of the fixture's steps. The four causes below are independent and all four must be closed.

Cause 1 of 4 - catalog MEMBERSHIP. AWS: recorded behavior only (the model types Schemas as a list of SchemaSummary and says nothing about which entries the aws.events registry holds; Smithy: ListSchemas GET /v1/registries/name/{RegistryName}/schemas, output Schemas -> __listOfSchemaSummary, @paginated(items: Schemas)). The recording shows the published catalog holding entries the emulator's seed does not have at all, and holding both spellings where AWS has published a legacy and a current name for the same event type. Examples from the recording: aws.account@RegionOpt-InStatusChange, aws.appflow@AppFlowAutomaticFieldImportReport, aws.acm@ACMCertificateApproachingExpiration / ACMCertificateExpired / ACMCertificateRenewalActionRequired / ACMCertificateRevoked / ACMCertificateRevokedByCA / ACMCertificateRevokedbyCertificateAuthorityCA, aws.aidevops@Investigation* (Cancelled, Completed, Created, Failed, InProgress, Linked, PendingTriage), the whole aws.maester@ source (DocumentCreated, DocumentDeleted, DocumentUpdated), aws.labs@Lab* (LabAutoCancelled, LabCostAlert, LabCostUpdate, LabLaunchStatusChange, LabTerminationStatusChange), aws.autoscaling@AWSAPICallViaCloudTrail (capital V, published alongside the lower-case AWSAPICallviaCloudTrail) and aws.tag@TagChangeOnResource (capital O, published alongside TagChangeonResource). Emulator: the catalog is a compile-time constant list (aws_managed_event_types() -> aws_managed_schemas(), seeded by aws_managed_registries()), so a source or event type absent from that list is absent from every response; for aws.maester the emulator returned None for all three expected entries, and for aws.acm it returned one ACM* entry where the recording has seven. Why: because the catalog is @paginated and every page is a fixed-size window over one ordered sequence, a single missing or extra entry shifts every later page, so a client that pages the catalog gets wrong data on every page after the first divergence, not just at the missing entry. A client resolving a well-known event type by name (DescribeSchema/ExportSchema after ListSchemas) gets 404 for an event type AWS publishes. Fix: the seeded catalog data behind aws_managed_event_types()/aws_managed_schemas() in the service's state module.

Cause 2 of 4 - ORDERING of SchemaName. AWS: recorded behavior only. The recording orders the list by SchemaName in codepoint (byte) order, so an upper-case letter sorts before a lower-case one at the same position: aws.acm-pca@ACMPrivateCAAuditReportGeneration, ACMPrivateCACRLGeneration, ACMPrivateCACertificateIssuance, ACMPrivateCACertificateRevocation, ACMPrivateCACreation; likewise aws.autoscaling@AWSAPICallViaCloudTrail before aws.autoscaling@AWSAPICallviaCloudTrail. Emulator: orders case-insensitively - it returned ACMPrivateCAAuditReportGeneration, ACMPrivateCACertificateIssuance, ACMPrivateCACertificateRevocation, ACMPrivateCACreation, ACMPrivateCACRLGeneration, i.e. CRLGeneration after Creation, which only a case-folded comparator produces. Why: the order is also the pagination order, so a NextToken resumes at a different place than AWS would and a client that merges pages or binary-searches by name misreads the catalog. Fix: the comparator that orders the catalog's schemas for the ListSchemas handler (the seeded registry's schema map ordering in the service's state module).

Cause 3 of 4 - VersionCount. AWS: recorded behavior only; SchemaSummary.VersionCount is the number of versions the catalog publishes for that schema, a per-entry property. The recording shows per-entry values that differ between entries of the same source: aws.acm@ACMCertificateApproachingExpiration / ACMCertificateAvailable / ACMCertificateExpired / ACMCertificateRenewalActionRequired = 3, aws.acm@ACMCertificateRevoked = 2, aws.acm@ACMCertificateRevokedByCA = 1, aws.aidevops@Investigation* = 2, aws.tag@TagChangeOnResource = 4. Emulator: derives it with managed_version_count(&name) from a digest over the schema name, so the count it reports for a given name is unrelated to the number of versions AWS publishes - it returned VersionCount 1 for aws.acm@AWSAPICallviaCloudTrail where the aligned expected entry carries 3, and 1 for aws.tag entries the recording publishes with 4. Why: VersionCount is what a client uses to decide whether to enumerate versions at all and which version numbers are valid; a wrong count makes DescribeSchema/ExportSchema calls for versions that do not exist, or hides versions that do. Fix: carry the published version count as seed data per catalog entry instead of deriving it, in the same state module.

Cause 4 of 4 - LastModified of entries with a fixed publication instant. AWS: recorded behavior only; SchemaSummary.LastModified is the instant the PUBLISHED schema was last modified. Most entries in this recording report an instant equal to the recording instant, so those exact values are a per-run property of the recording and are NOT asserted here as a requirement. What the recording does establish is that some entries carry a fixed historical publication instant that is theirs alone - aws.autoscaling@AWSAPICallViaCloudTrail at 2019-12-01T00:59:43Z and aws.tag@TagChangeOnResource at 2022-03-24T16:40:20Z - and that these are not a function of the schema name. Emulator: managed_last_modified(schema_name) hashes the schema NAME with SHA-256 and maps the first 8 bytes into a six-year window starting at CATALOGUE_EPOCH 2019-12-01T00:00:00Z, so every entry reports an arbitrary instant in 2019-2025 (it returned 2021-04-08T22:56:53Z for aws.autoscaling@AWSAPICallviaCloudTrail, 2024-12-16T03:48:47Z for an aws.tag entry) that is unrelated to when the schema was published and cannot ever reproduce a published instant. Why: LastModified is exactly the value a client compares against its cached copy of a schema to decide whether the copy is stale, so a value unrelated to publication makes cache validation meaningless. Fix: carry the published instant as seed data per catalog entry (and keep the digest only as the fallback for entries with no published instant), in the same state module.
