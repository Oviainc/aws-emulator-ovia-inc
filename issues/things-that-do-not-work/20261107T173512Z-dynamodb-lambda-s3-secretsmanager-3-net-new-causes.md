# dynamodb__lambda__s3__secretsmanager: 3 net-new causes — in-function AWS calls are never authorized (IAM, resource policy, tag condition and KMS denials all succeed), S3 ObjectCreated notifications never invoke their Lambda, and a rotation Lambda never writes its backup

> _Note: this issue was identified against the code base at commit `edd8d27229a8bc99e308a4b32d393f13d6f32cb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
Three independent root causes in this scenario group; each is listed with its own failing check ids and all three must be closed before this issue is submitted.

Cause 1 of 3: an AWS call made from inside a Lambda handler is never authorized — every denial path returns data instead of a refusal.
AWS: Smithy: secretsmanager GetSecretValue (errors DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException) and DescribeSecret. Authorization is evaluated before any of those: a caller whose execution role does not grant secretsmanager:GetSecretValue (or whose grant is excluded by a tag condition such as aws:ResourceTag/<key>, or whose request is denied by the secret's resource policy) is refused `AccessDeniedException` with HTTP 400 and the message `User: <role-session ARN> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret ARN>` — the fixed text is `User: … is not authorized to perform: … on resource: …`, with the principal ARN, action and resource ARN taken from the request and the caller's identity, plus the clause `with an explicit deny in a resource-based policy` when a resource-policy Deny is what decided it. secretsmanager:DescribeSecret and secretsmanager:GetSecretValue are separate actions, so a role with only DescribeSecret must be refused the value read. When the secret is encrypted with a customer CMK and the caller lacks kms:Decrypt on that key, AWS refuses the read rather than returning plaintext. The same rule holds for a DynamoDB write that needs kms:Decrypt on the item-encryption key.
Emulator: every one of these calls succeeds and returns the protected material. The role lacking GetSecretValue reads the value (`{'ok': True, 'secret_string': 'top-secret-…'}`); a role with only DescribeSecret also gets the value (`{'describe_ok': True, …, 'get_ok': True, 'get_value': 'value-only-visible-with-getvalue-permission'}`); a tag-condition-excluded role gets it (`{'ok': True, 'secret_string': 'green-team-secret-value'}`); a secret whose resource policy denies the caller is still read, and the Deny never converges (`the resource-policy Deny to take effect on GetSecretValue for the denied secret not reached within 60.0s; last observation {'ok': True, …}`); a cross-account secret with NO grant at all is read (`expected ok=False for ungranted secret, got {'ok': True, …}`); a CMK-encrypted secret is read without kms:Decrypt; and a DynamoDB write that should be blocked without kms:Decrypt succeeds (`expected the write to be blocked without kms:Decrypt, got {'ok': True}`). No AccessDeniedException is produced on any path.
Why: least-privilege is unverifiable and silently absent. A client that scopes an execution role, attaches a resource-policy Deny, gates access by resource tag, or relies on CMK permissions as a second control gets none of those effects, and a negative test that should prove the boundary passes while reading secret material.
Fix: the authorization layer the in-process Lambda runtime's AWS client goes through — the in-function call must be evaluated against the execution role's identity policy, the target's resource policy (including explicit Deny), condition keys such as aws:ResourceTag/*, and the KMS grant on the resource's CMK, and refused AccessDeniedException with AWS's wording before the operation runs.

Cause 2 of 3: an S3 ObjectCreated notification never invokes its configured Lambda, so the downstream pipeline never runs.
AWS: s3 PutBucketNotificationConfiguration with a LambdaFunctionConfiguration for s3:ObjectCreated:* delivers an S3 event notification to the function on every matching PutObject, provided the function's resource policy allows s3.amazonaws.com. The handler then performs its work (here: read a secret, decrypt the object, write a DynamoDB item), so the item appears shortly after the upload.
Emulator: the upload is accepted but the function is never invoked and no item is ever written: `S3 upload never triggered a DynamoDB write via the Lambda notification` and `condition not met within 90s; last=None`.
Why: the canonical S3-triggered processing pipeline silently does nothing; a client sees a configured notification, a stored object, and no effect.
Fix: the s3 notification dispatcher — a matching ObjectCreated event must be delivered to the configured Lambda target.
Traces: dynamodb__lambda__s3__secretsmanager.cli-s3-upload-lambda-reads-config-secret-writes-dynamodb, .s3-notification-lambda-decrypts-object-with-secret-writes-dynamodb. Related open issue that does not carry these checks' replay keys: 20261107T015155Z-dynamodb-lambda-s3-secretsmanager-an-s3-objectcreated-notification.md.

Cause 3 of 3: a secret rotation never executes the rotation Lambda, so its S3 backup object is never written.
AWS: secretsmanager RotateSecret invokes the configured RotationLambdaARN through the createSecret/setSecret/testSecret/finishSecret steps; a rotation function that writes a backup copy of the old value to S3 therefore leaves an object under the configured prefix.
Emulator: the rotation is accepted but the function never runs — the backup prefix stays empty for the whole window: `rotation backup object written to S3 not met within 150.0s. Last result: … 'KeyCount': 0`.
Why: a client relying on rotation side effects (backups, audit records, downstream credential updates) gets none of them, and RotateSecret reporting success is misleading.
Fix: the secretsmanager rotation driver — RotateSecret must invoke the rotation Lambda for each step.
Traces: dynamodb__lambda__s3__secretsmanager.secretsmanager-rotation-lambda-s3-backup-positive. Related open issue that does not carry this check's replay key: 20261029T180026Z-dynamodb-lambda-s3-secretsmanager-secrets-manager-rotatesecret-is-accepted-for-an-un.md.
