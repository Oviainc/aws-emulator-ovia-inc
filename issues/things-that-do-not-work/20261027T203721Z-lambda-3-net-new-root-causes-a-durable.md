# lambda: 3 net-new root causes — a durable execution is accepted but never runs (no step, no callback, status stuck RUNNING), CreateFunction(Publish=true) answers the version-qualified ARN, and GetFunctionScalingConfig never drops RequestedFunctionScalingConfig once applied

> _Note: this issue was identified against the code base at commit `6ad1863e43f5664fac16df5e246702230b6849d0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Three net-new root causes in the `lambda` service, all grounded in failing behavioral checks of this suite. None of these eight checks is marked ALREADY FILED or OWNED in the replay report; the open lambda issues named below carry other replay keys and do not cover these.

=== Cause 1 of 3: a durable execution started through Invoke is recorded but never EXECUTES — no step runs, no callback is ever created, and the execution never leaves RUNNING except to time out ===
Failing checks (6): lambda.callback-heartbeat-extends-deadline, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors, lambda.send-callback-success-after-checkpoint-window.

AWS: Invoke is the entry point that STARTS a named durable execution — Smithy: Invoke input member DurableExecutionName @httpHeader("X-Amz-Durable-Execution-Name") (@length 1..64, pattern ^[a-zA-Z0-9-_]+$), output member DurableExecutionArn @httpHeader("X-Amz-Durable-Execution-Arn"), modeled error DurableExecutionAlreadyStartedException (409). Once started, AWS RUNS the handler: the durable SDK's steps execute, `context.wait_for_callback(notify, ...)` invokes the handler's own notify function (which in these checks publishes the CallbackId to an SQS queue), and the execution is then resolvable through SendDurableExecutionCallbackSuccess / SendDurableExecutionCallbackHeartbeat (Smithy: POST /2025-12-01/durable-execution-callbacks/{CallbackId}/succeed and /heartbeat, errors CallbackTimeoutException 400, ResourceNotFoundException 404). GetDurableExecution then reports Status moving out of RUNNING to one of ExecutionStatus's terminal values (SUCCEEDED | FAILED | TIMED_OUT | STOPPED) with Result/Error and EndTimestamp, and GetDurableExecutionHistory records the Callback* events. Recorded behavior (these checks' oracle): the CallbackId arrives on the handler-written queue within seconds, a heartbeat inside the window answers HTTP 200 and extends the deadline, and a success callback drives the execution to SUCCEEDED carrying the handler's own result.

Emulator: Invoke(InvocationType=Event, DurableExecutionName=<name>) answers 202 and the execution IS registered — ListDurableExecutionsByFunction reports it — but nothing ever runs it. The emulator's own state documents this: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (module docs, "The event is never executed here (this emulator has no in-process runtime for a deployment package)"; the durable slice: "it starts RUNNING, and the move to TIMED_OUT is owed by the CLOCK"), and DurableExecutionRecord::materialize applies exactly one transition, RUNNING -> TIMED_OUT. Consequently the handler's notify callback never fires, no CallbackId is ever minted or delivered, no checkpoint or history event is written, and Status can only ever be RUNNING or TIMED_OUT. Every one of the six checks blocks on the first service-driven signal (the CallbackId on SQS, or GetDurableExecution leaving RUNNING) and the runner reports `Check timed out after 60.0s` for all six.

Why: the whole durable-execution feature is inert while looking healthy. A client gets a 202, an execution ARN and a RUNNING status, so it believes work is in flight; it then waits forever for the callback id its own handler was supposed to publish, and every downstream API it would call (SendDurableExecutionCallbackSuccess/Failure/Heartbeat, GetDurableExecutionHistory, StopDurableExecution) has no callback or event to address. A workflow written against AWS neither completes nor fails — it hangs, and the only terminal state the emulator can ever reach is TIMED_OUT, which misreports a healthy workflow as a timeout.

Fix: the Invoke handler's durable path plus the durable-execution slice of the lambda service's state — a started execution must actually be driven (its steps executed, its wait_for_callback notify invoked, a CallbackId minted and resolvable, checkpoints and history events appended, and the status advanced to SUCCEEDED/FAILED on completion) rather than registered and left to the timeout clock. Related open issues: 20261026T070343Z-events-lambda-sqs-lambda-invoke-on-a-durable-execution-function-returns.md covers only the missing X-Amz-Durable-Execution-Arn response header on that Invoke, and 20261027T191349Z-events-lambda-sqs-lambda-durable-execution-status-change-events-are-never.md covers the missing status-change events; neither covers the execution never running at all. 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md covers synchronous Invoke being refused — these six checks are NOT refused, they are accepted with 202 and then never progress.

Traces: lambda.callback-heartbeat-extends-deadline, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors, lambda.send-callback-success-after-checkpoint-window. State: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (DurableExecutionRecord and its materialize; FunctionRecord::start_durable_execution).

=== Cause 2 of 3: CreateFunction with Publish=true reports the VERSION-QUALIFIED ARN in FunctionArn, where AWS reports the unqualified function ARN ===
Failing check: lambda.delete-capacity-provider-with-attached-function-rejected.

AWS: CreateFunction's output is FunctionConfiguration, whose FunctionArn is documented only as "The function's Amazon Resource Name (ARN)" and targets NameSpacedFunctionArn (a pattern that PERMITS a qualifier), so the model does not settle this — recorded behavior only: AWS answers CreateFunction with the UNQUALIFIED function ARN (arn:<partition>:lambda:<region>:<account>:function:<name>) and reports the published version separately in the Version member ("1"). The check's oracle depends on exactly that: it forms the version ARN as CreateFunction's FunctionArn with ":1" appended and compares it to the version ARN AWS names in DeleteCapacityProvider's ResourceConflictException message. The message itself is a requirement: HTTP 409, code `ResourceConflictException`, message `The capacity provider is currently in use by <N> function. To delete this capacity provider, first remove its association with <version-arn>.` — the fixed text is everything but <N> (the number of associated functions, from state) and <version-arn> (the qualified ARN of the associated function version, from state).

Emulator: CreateFunction(..., Publish=True) returns FunctionArn = `arn:aws:lambda:<region>:<account>:function:<name>:1` — the qualified ARN — because the handler answers `stored.configuration(&reported_version, &config)` and FunctionRecord::configuration sets function_arn to versioned_arn(version), which appends `:<version>` for anything but $LATEST. The DeleteCapacityProvider refusal itself is correct (409 ResourceConflictException with exactly the message text above, naming the version ARN `...:function:<name>:1`), but the client's notion of the function ARN is already one qualifier off, so the two cannot agree: the check computes the expected version ARN as `...:function:<name>:1:1` and reports `AssertionError: unexpected DeleteCapacityProvider message: 'The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with arn:aws:lambda:<region>:<account>:function:<name>:1.'`

Why: every client that creates a function with Publish=true and then uses the returned FunctionArn gets a version-pinned ARN where AWS gives it the function's own ARN. It writes that string into IAM and resource policies, event source mappings, API Gateway and EventBridge targets, CloudFormation outputs and CloudWatch dimensions — all of which then address `<fn>:1` instead of `<fn>`, or, when the client appends its own qualifier, a nonexistent `<fn>:1:<qualifier>`. The divergence is silent: nothing refuses the malformed ARN at the point of use.

Fix: the CreateFunction handler's response construction (and the shared FunctionRecord::configuration it reads through) — the ARN reported for a create must be the function's unqualified ARN with the published version carried only in Version, while PublishVersion and qualified reads keep reporting the qualified form.

Traces: lambda.delete-capacity-provider-with-attached-function-rejected. Handler: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/create_function.rs lines 609-646 (the Publish arm and the final `stored.configuration(&reported_version, &config)`); state: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (FunctionRecord::configuration -> versioned_arn).

=== Cause 3 of 3: GetFunctionScalingConfig always reports RequestedFunctionScalingConfig, so the "request fully applied" signal never appears and a Managed-Instances scaling request can never be observed to converge ===
Failing check: lambda.put-function-scaling-config-then-capacity-provider-list-reflects.

AWS: Smithy GetFunctionScalingConfig (GET /2025-11-30/functions/{FunctionName}/function-scaling-config, required FunctionName and Qualifier) has output members FunctionArn, AppliedFunctionScalingConfig and RequestedFunctionScalingConfig, both of type FunctionScalingConfig. Recorded behavior only (this check's oracle, stated in the check itself): once a PutFunctionScalingConfig request is FULLY APPLIED, `RequestedFunctionScalingConfig` is omitted from the response entirely — its ABSENCE, not its equality with the applied configuration, is the convergence signal a client polls on — while AppliedFunctionScalingConfig then reports the bounds in effect ({MinExecutionEnvironments: 1, MaxExecutionEnvironments: 2} for the request this check makes).

Emulator: the member is unconditionally present. FunctionScalingConfigRecord::reported builds `requested_function_scaling_config: Some(self.requested.clone())` with no dependence on whether the request has been applied, so after PutFunctionScalingConfig the response carries RequestedFunctionScalingConfig forever. The check's bounded poll for the member's absence can therefore never be satisfied and the runner reports `Check timed out after 60.0s`.

Why: a client that reconciles Lambda Managed Instances scaling bounds has no way to learn that its request landed. Code written against AWS polls GetFunctionScalingConfig until RequestedFunctionScalingConfig disappears and then reads AppliedFunctionScalingConfig; against the emulator that loop never terminates, so deployments and autoscaling reconcilers that gate on convergence hang or time out even though the bounds were in fact applied.

Fix: the GetFunctionScalingConfig response construction in the lambda service's scaling-config state (FunctionScalingConfigRecord::reported) — once the requested configuration has become the applied one, the response must omit RequestedFunctionScalingConfig and report only FunctionArn plus AppliedFunctionScalingConfig; it should be reported only while a request is still outstanding. Related open issue 20261025T100455Z-lambda-getfunctionscalingconfig-accepts-a-function-with-no-capacity.md covers two different causes of the same operation (a 200 for a function with no capacity-provider configuration, and the missing service-managed default for a never-configured version); it does not cover the member never being dropped after a request IS applied.

Traces: lambda.put-function-scaling-config-then-capacity-provider-list-reflects. State: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (FunctionScalingConfigRecord::request / ::materialize / ::reported); handler: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/get_function_scaling_config.rs.

## Evidence
Cause 1 — expected (AWS, recorded): after Invoke(FunctionName=<durable fn>, InvocationType='Event', DurableExecutionName=<name>) answers 202, the handler runs; `context.wait_for_callback(notify, ...)` fires `notify`, which sends the CallbackId to the check's SQS queue; SendDurableExecutionCallbackHeartbeat(CallbackId=...) answers HTTP 200 and extends the heartbeat deadline; SendDurableExecutionCallbackSuccess(CallbackId=..., Result=b'{"approved": true, ...}') drives the execution to Status=SUCCEEDED, GetDurableExecution(IncludeExecutionData=True) returns the handler's own Result, and GetDurableExecutionHistory contains at least one Callback* event.
Actual (emulator): the 202 and the registered execution are the last things that happen. No message ever reaches the queue the handler was given, GetDurableExecution reports Status=RUNNING until the function's DurableConfig ExecutionTimeout falls due (then TIMED_OUT), and all six checks are cut off by the runner: `Error: Check timed out after 60.0s` for lambda.callback-heartbeat-extends-deadline, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors and lambda.send-callback-success-after-checkpoint-window. The emulator's own state documentation states the cause in full: "this emulator has no in-process runtime for a deployment package" and, for a durable execution, "The ONLY transition it applies is the one the clock owed at `now`" — RUNNING -> TIMED_OUT. These checks are not blocked on an unimplemented operation and were not refused; every call they made was accepted.

Cause 2 — expected (AWS, recorded): CreateFunction(..., Publish=True) answers FunctionArn = `arn:aws:lambda:<region>:<account-id>:function:<function-name>` with Version = "1"; DeleteCapacityProvider on a provider that version runs on is refused HTTP 409 `ResourceConflictException` with message `The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with <CreateFunction FunctionArn>:1.` — so the ARN in the message equals the created function's ARN plus ":1".
Actual (emulator): the refusal's message is `The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with arn:aws:lambda:us-west-2:000000000000:function:sim2real-neg-cp-fn-7cb2dfc14610:1.` while CreateFunction had already returned that same qualified string as the function's FunctionArn, so the version ARN the client forms is `...:sim2real-neg-cp-fn-7cb2dfc14610:1:1`. Reported by the replay as:
  check_lambda_delete_capacity_provider_with_attached_function_rejected.py, line 110, in run

The region, account id and function name above are values this run filled in; the requirement is that CreateFunction's FunctionArn carry no version qualifier, and that the 409 message's fixed text be exactly as quoted with the association's version ARN taken from state.

Cause 3 — expected (AWS, recorded): after PutFunctionScalingConfig(FunctionName=<mi fn>, Qualifier="1", FunctionScalingConfig={MinExecutionEnvironments:1, MaxExecutionEnvironments:2}) has been fully applied, GetFunctionScalingConfig(FunctionName=<mi fn>, Qualifier="1") returns a response with NO RequestedFunctionScalingConfig member and AppliedFunctionScalingConfig == {"MinExecutionEnvironments": 1, "MaxExecutionEnvironments": 2}.
Actual (emulator): RequestedFunctionScalingConfig is present in every response for the rest of the record's life — `FunctionScalingConfigRecord::reported` sets it to `Some(self.requested.clone())` unconditionally — so the check's poll for its absence (600 s budget, 15 s interval) can never succeed and the runner cuts the check off: `Error: Check timed out after 60.0s` for lambda.put-function-scaling-config-then-capacity-provider-list-reflects. Every upstream call in that check succeeded (ec2 network, both IAM roles, CreateCapacityProvider reaching Active, CreateFunction with CapacityProviderConfig reporting State=ActiveNonInvocable, PublishVersion, PutFunctionScalingConfig).
