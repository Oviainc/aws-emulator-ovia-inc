# ses: CreateReceiptRule's SNSAction pre-flight never evaluates the target topic's policy — an explicit Deny of sns:Publish for ses.amazonaws.com is accepted 200 instead of refused InvalidSnsTopic

> _Note: this issue was identified against the code base at commit `2aa7499d3c3b76d99f0f951c53163fca54ec3d78`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRule

## Description
One net-new behavioral root cause on the SES v1 (awsQuery) receipt-rule surface. The failing check is marked neither ALREADY FILED nor OWNED in the replay report.

Related open issue that touches the same handler but does NOT carry this cause: 20261027T223106Z-ses-7-net-new-behavioral-root-causes-in.md. Its Cause 2 and Cause 3 cover the S3Action and LambdaAction pre-flights on CreateReceiptRule, and its Cause 4 covers UpdateReceiptRule's destination pre-flight (including an SNSAction naming a topic that does not exist). Neither covers the cause below: CreateReceiptRule's SNSAction branch failing to evaluate the policy of a topic that DOES exist. That issue's replay keys do not include this check's key, so this cause would be closed unrun under it.

Cause 1 of 1: CreateReceiptRule accepts an SNSAction whose target topic's resource policy explicitly denies sns:Publish to the SES service principal.
AWS: Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery) CreateReceiptRule declares InvalidSnsTopicException with awsQueryError code InvalidSnsTopic and httpResponseCode 400; SNSAction.TopicArn is required (target AmazonResourceName). The exception's own documentation states the scope of the check: "Indicates that the provided Amazon SNS topic is invalid, or that Amazon SES could not publish to the topic, possibly due to permissions issues." SES therefore pre-flights publishability at rule-creation time, not just topic existence: it evaluates the topic's resource policy for the ses.amazonaws.com service principal, and an explicit Deny of sns:Publish is terminal in AWS policy evaluation, so no other answer is reachable. Recorded behavior for the refusal: HTTP 400 with awsQuery Error.Code "InvalidSnsTopic" and Error.Message "Could not publish to SNS topic: <TopicArn>" — the fixed text is the sentence prefix "Could not publish to SNS topic: " and the single variable part is the TopicArn taken verbatim from the request's SNSAction (never a topic ARN from anywhere else). Nothing is persisted by the refused call, so DescribeReceiptRuleSet still lists no rules afterwards; and once the Deny statement is removed the byte-identical CreateReceiptRule succeeds. Two further requirements the same behavior implies, both read at SNS through operations SES never calls: SES must not edit the topic's policy to grant itself the permission (the API path leaves that to the caller, unlike the console), and creating a receipt rule must not subscribe anything to the topic. The deny is principal-scoped, so the topic stays healthy and the caller's own Publish must still succeed — that is what distinguishes "the deny blocked SES" from "the topic became unusable".
Emulator: the call is accepted. CreateReceiptRule answers HTTP 200 with an empty CreateReceiptRuleResponse (content-type text/xml, content-length 251) and persists the rule, although the check has already proved at the consumer, via GetTopicAttributes, that the Deny statement is observably stored on the topic's policy before anything is concluded from its effect. Replay: "AssertionError: real AWS refuses this call, but it SUCCEEDED and returned {... 'HTTPStatusCode': 200 ...}". The positive control in the same check passes (with the topic's default policy the identical rule is accepted and DescribeReceiptRule reports the TopicArn), so the divergence is isolated to the policy evaluation: the SNSAction branch does no authorization pre-flight at all.
Why: a client that validates its inbound-email configuration by attempting CreateReceiptRule and treats a 200 as proof that SES can reach the topic is told a broken configuration is good. It ships a receipt rule whose SNS notifications can never be published, and the failure surfaces only in production as silently missing notifications. The whole negative class — a topic that exists but withholds publish permission from SES — is unreachable against the emulator, so neither the InvalidSnsTopic code nor its message can be exercised, and "topic is unreachable" becomes indistinguishable from "topic is fine".
Fix: the SNSAction branch of the CreateReceiptRule handler's destination pre-flight in the ses v1 crate — resolve the TopicArn in the emulator's SNS state and evaluate the topic's resource policy for sns:Publish by the ses.amazonaws.com service principal (honouring explicit Deny as terminal), refusing with InvalidSnsTopic / "Could not publish to SNS topic: <TopicArn>" and persisting nothing. The same shared validation should back UpdateReceiptRule (Cause 4 of the related issue above). The handler must not mutate the topic policy or create a subscription as a side effect.
Traces: ses__sns.receipt-rule-sns-action-honours-an-explicit-topic-policy-deny.
