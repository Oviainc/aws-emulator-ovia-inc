## Description
One (1) net-new root cause. Cause 1 of 1 must be closed before this issue is submitted. The failing check was NOT marked ALREADY FILED or OWNED by the replay report, so no open issue carries its current replay key; it now fails as a check-level TIMEOUT inside its positive control.

=== Cause 1 of 1: the positive control of the Lake Formation revoke lifecycle never converges — a reader holding a Lake Formation SELECT grant never gets a SUCCEEDED Athena read of the granted table, so the revoke behaviour behind it can never be observed ===
AWS: Smithy (athena): StartQueryExecution -> QueryExecutionId; GetQueryExecution -> QueryExecution{Status{State: QueryExecutionState, StateChangeReason}}; (lakeformation): GrantPermissions/RevokePermissions(Principal, Resource, Permissions), ListPermissions; (glue): GetTable errors include AccessDeniedException. Recorded behavior: with the table's S3 location registered and the reader role granted DESCRIBE on the database and SELECT on the table, `SELECT ...` through Athena settles State == "SUCCEEDED" and the result rows are exactly the rows written to the table's location. After RevokePermissions withdraws SELECT, the identical query settles State == "FAILED" with StateChangeReason of the form "TABLE_NOT_FOUND: line 1:28: Table 'awsdatacatalog.<database>.<table>' does not exist" — fixed text "TABLE_NOT_FOUND: line ", the line:column prefix of the table reference in the submitted SQL, ": Table '", the catalog name "awsdatacatalog", and "' does not exist", with the database and table names taken from the request; the reader's glue GetTable is then refused AccessDeniedException whose message is "Insufficient Lake Formation permission(s): Required Describe on <table>" (fixed text "Insufficient Lake Formation permission(s): Required Describe on " plus the table name from the request); ListPermissions for that principal/table returns no entry; and re-granting SELECT makes the identical query SUCCEEDED again with the same rows.
Emulator: the check never gets past its first state — the poll of StartQueryExecution/GetQueryExecution for a SUCCEEDED read of the SELECT-granted table (and/or the reader's GetTable projecting the three columns) never converges, and the check ends as "Check timed out after 60.0s" before its first assertion. Hypothesis: the Athena data plane does not execute the query against the Glue-catalogued S3 location at all, so no terminal SUCCEEDED state is ever reached; the replay output records only the timeout, not which call stalled.
Why: Lake Formation's entire enforcement contract is unverifiable for a client. A grant that cannot be demonstrated to work means a later revoke cannot be distinguished from a read that never worked, so an application relying on Lake Formation to hide or expose a table — and on the specific TABLE_NOT_FOUND re-hiding rather than an authorization error — gets neither behaviour, and any code branching on those reasons/messages never runs.
Related but NOT covering: 20261108T073030Z-athena-glue-lakeformation-s3-athena-does-not-enforce-lake-formation-permissions-ungranted.md (Lake Formation permissions not enforced on ungranted reads) and 20261104T082656Z-athena-glue-s3-the-athena-data-plane-never.md (the Athena data plane never executes queries) describe neighbouring faults; the report left this check unowned, so neither carries its current replay key.
Fix: the Athena query-execution data plane for a Glue/Lake Formation-catalogued external table (the query must settle SUCCEEDED and return the rows at the table's registered S3 location) and, behind it, the Lake Formation permission evaluation consulted by Athena and by glue GetTable — including the FAILED/TABLE_NOT_FOUND StateChangeReason composition on a revoked table, the AccessDeniedException message on the reader's catalog read, and RevokePermissions removing the entry from ListPermissions.
