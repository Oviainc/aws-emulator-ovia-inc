# cloudwatch__ec2__elbv2: an ALB answers HTTP 502 at its DNS name for an EC2 instance target it has just reported 'healthy', so no ApplicationELB request/health metric scenario can start

> _Note: this issue was identified against the code base at commit `ac0eea33c4f4a66a7179f256fe88fefcc3a441e0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeTargetHealth

## Description
Cause 1 of 1: the Application Load Balancer data plane never proxies a request to an EC2 instance target that the emulator's own DescribeTargetHealth reports as 'healthy' — every request to the load balancer's DNSName is answered HTTP 502 instead of the target's response. All four failing checks in this service are blocked at the same warm-up step, before any CloudWatch assertion is reached, and they cover both routing shapes: the default listener action (obs-elbv2-1-...) and listener rules with an http-header condition (the three metrics-elbv2-apigw-alb-... checks).

AWS: the ELBv2 data plane is not described by the Smithy model, so for the forwarding behaviour itself this is recorded behavior only: in the recordings, once DescribeTargetHealth reports TargetHealth.State 'healthy' for a registered instance target, a GET through the listener (or through a matching listener rule) returns the target's own response — HTTP 200 with the target's body (the recorded target answers 200 "TARGET-200:<marker>") — and the load balancer generates a 5xx of its own only in the cases AWS documents: HTTP 503 with body "503 Service Temporarily Unavailable" and header Server: awselb/2.0 when the chosen target group has no registered target, and HTTP 502 "502 Bad Gateway" (Server: awselb/2.0) only when it cannot establish a connection to, or gets a malformed reply from, the target. The control plane that frames this IS modeled — Smithy: DescribeTargetHealth -> DescribeTargetHealthOutput.TargetHealthDescriptions, each TargetHealth carrying State and Reason; errors InvalidTarget (400), TargetGroupNotFound (400), HealthUnavailable (500). So the two observable facts AWS guarantees are coupled: a target reported 'healthy' is a target the load balancer has just connected to successfully on the health-check path, and it is therefore reachable for traffic; a target that is unreachable is reported unhealthy with Reason Target.FailedHealthChecks / Target.Timeout, not 'healthy'.

Emulator: the setup succeeds all the way through — RunInstances, CreateLoadBalancer, CreateTargetGroup, CreateListener/CreateRule, RegisterTargets, the load balancer reaching 'active', and DescribeTargetHealth reaching State 'healthy' for the registered instance id (the checks' _wait_healthy helper would have raised otherwise). Immediately afterwards, repeated GETs to http://<DNSName>/warm/ok through that same listener return status 502 for the whole 180 s budget: "AssertionError: the listener forwarding to the healthy targets not met within 180s. Last result: 502" (and, for the rule-based variants, "the live rule forwarding to the healthy target", "the run-header rule forwarding to the targets", "the header rule forwarding to the healthy targets" — same last result, 502). So the emulator reports a health verdict it cannot honour: either the health check is synthesized without being performed (in which case the state should be 'unhealthy' with Reason Target.FailedHealthChecks while nothing is listening in the guest), or the proxy path refuses to connect to a target it did probe. Either way the pair of answers is self-inconsistent.

Why: a client that does what every ALB runbook does — register targets, wait for DescribeTargetHealth to report 'healthy', then send traffic — gets a hard 502 on every request. Nothing downstream of the data path can be exercised: the AWS/ApplicationELB series these checks exist to measure (RequestCount, HTTPCode_Target_2XX/5XX_Count, HTTPCode_ELB_503_Count/5XX_Count, HealthyHostCount/UnHealthyHostCount, ClientTLSNegotiationErrorCount and the keep-alive/idle-timeout behaviours) are never fed, the load-balancer-generated 503 for an empty target group and 400/504 for malformed and slow requests are never reached, and an alarm built on those series can never leave INSUFFICIENT_DATA. A 502 is also the status AWS reserves for a genuinely broken target, so the emulator's answer actively misleads diagnosis.

Fix: the ELBv2 data-plane request path for instance targets — the listener/rule forwarding and target-connection component that serves the load balancer's DNSName — together with the target-group health-check evaluator that feeds DescribeTargetHealth, so that a target reported 'healthy' is proxied to and a target that cannot be connected to is reported unhealthy with the matching Reason instead. Related open issues describe the same shape for other service combinations but do not carry these checks' replay keys: 20261108T200221Z-elbv2-an-alb-never-forwards-a-successful-http.md, 20261107T080944Z-elbv2-2-net-new-data-plane-root-causes.md, 20261108T191814Z-cloudwatch-ecs-elbv2-logs-an-alb-answers-502.md (ECS ip targets) and 20261109T153103Z-elbv2-4-net-new-causes-the-published-dnsname.md (DNSName publication).

Traces: the four failing checks listed below, all under the cloudwatch__ec2__elbv2 heading of the behavioral suite.

## Evidence
Expected (AWS): after RegisterTargets and DescribeTargetHealth reporting TargetHealth.State='healthy' for the instance target, GET http://<lb-DNSName>/warm/ok through the listener (default action, or a rule whose http-header condition the request matches) returns HTTP 200 carrying the target's body (recorded: "TARGET-200:<marker>"). A load-balancer-generated 502 "502 Bad Gateway" with Server: awselb/2.0 is only produced when the target cannot be reached — and in that case DescribeTargetHealth reports State 'unhealthy' with Reason Target.FailedHealthChecks (or 'unused'/'initial' as applicable), never 'healthy'.

Actual (emulator): DescribeTargetHealth reports State='healthy' for the registered instance id, then every GET to http://<lb-DNSName>/warm/ok returns HTTP 502 for 180 s. Suite output, one line per failing check (the variable parts are the per-run rule/listener description; the status is invariant):
  * metrics-elbv2-apigw-alb-empty-target-group-503-counted-as-elb-5xx-not-target-5xx — "AssertionError: the live rule forwarding to the healthy target not met within 180s. Last result: 502"
  * metrics-elbv2-apigw-alb-failing-health-endpoint-flips-healthy-and-unhealthy-host-count — "AssertionError: the run-header rule forwarding to the targets not met within 180s. Last result: 502"
  * metrics-elbv2-apigw-alb-request-metrics-exact-counts-code-split-and-literal-dimensions — "AssertionError: the header rule forwarding to the healthy targets not met within 180s. Last result: 502"
  * obs-elbv2-1-alb-rejects-malformed-requests-elb-504-and-keepalive-connection-metrics — "AssertionError: the listener forwarding to the healthy targets not met within 180s. Last result: 502"
In all four the failure is the first data-plane request of the check; no CloudWatch GetMetricStatistics assertion is ever evaluated. Fixed text of the assertion is the harness's; the requirement being violated is the status: 200 (target's response) is expected, 502 is returned.

## Steps to Reproduce
1. ec2: create a VPC with two subnets in two AZs; create an ALB security group allowing tcp/80 from the caller's ingress CIDRs and a target security group allowing tcp/80 from the ALB security group.
2. ec2 RunInstances: launch one t3.micro from an AL2023 AMI into the first subnet with the target security group and user-data that starts an HTTP server on port 80 answering 200 for any path; wait for instance_running.
3. elbv2 CreateLoadBalancer (internet-facing, both subnets, ALB security group), CreateTargetGroup (HTTP/80 in that VPC), CreateListener on port 80 forwarding to the target group. Optionally add CreateRule with an http-header condition to exercise the rule path.
4. elbv2 RegisterTargets with {"Id": <instance-id>}; poll DescribeLoadBalancers until State.Code='active' and DescribeTargetHealth until TargetHealth.State='healthy' for that instance id — both succeed on the emulator.
5. GET http://<DNSName>/warm/ok (adding the rule's header when exercising a rule).
Observed: HTTP 502 on every attempt for 180 s. Expected: HTTP 200 with the target's body, consistent with the 'healthy' verdict just returned by DescribeTargetHealth.
