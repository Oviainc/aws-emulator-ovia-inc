# batch__events__sqs: a Batch job state change never reaches an EventBridge rule's SQS target, so the whole job-state-change eventing contract hangs to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `dae6e7ecbed2f75cbdde9154518aba02892291c8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SubmitJob

## Description
Cause 1 of 1: Batch job state transitions are never delivered to an EventBridge rule's SQS target, so no part of the Batch -> EventBridge -> SQS eventing contract can be observed. The check does not fail an assertion — it never gets far enough to make one, and is cut off by the suite's 60 s per-check cap while still inside its pre-evidence delivery stage (first the EventBridge->SQS warm-up loop that proves the wiring can deliver at all, then the wait for the job's first `Batch Job State Change` envelope). Failing check: batch__events__sqs.batch-job-state-change-event-delivered-to-matching-rule-and-withheld-from-other-queue.

AWS: not expressible in the Smithy model — EventBridge envelopes are not modelled, so this is recorded/documented behavior only. Batch publishes a job state change to the account's DEFAULT EventBridge bus on every transition a job makes AFTER submission (the Batch User Guide is explicit that no event is created for the initial SUBMITTED state, so the first event for a job parked on an UNMANAGED compute environment is RUNNABLE, and TerminateJob produces a further FAILED event). The envelope carries `source` = "aws.batch", `detail-type` = "Batch Job State Change", `account` = the caller's account id, `region` = the call's region, and `resources` = exactly one element, the job's ARN. The `detail` is a projection of the service's own job record as DescribeJobs reports it (Smithy: JobDetail.jobId, JobDetail.jobArn, JobDetail.jobQueue — "The Amazon Resource Name (ARN) of the job queue that the job is associated with", JobDetail.status (JobStatus enum, the state transitioned INTO), JobDetail.jobDefinition — "The Amazon Resource Name (ARN) of the job definition that this job uses", JobDetail.jobName, JobDetail.createdAt (Long, Unix timestamp in milliseconds), JobDetail.statusReason), so detail.jobName/detail.createdAt must equal what DescribeJobs reports for the same job, and a terminate's FAILED event must carry the TerminateJob `reason` inside detail.statusReason. An ENABLED default-bus rule whose EventPattern pins {"source":["aws.batch"],"detail-type":["Batch Job State Change"],"detail":{"jobQueue":[<that queue's ARN>]}} with an SQS target therefore receives those envelopes, and a sibling rule pinning a DIFFERENT job queue ARN receives none of them (0 visible / 0 in-flight) until a job is actually submitted to that sibling queue, at which point its own RUNNABLE event arrives there.

Emulator: nothing is delivered. The check exhausts the 60 s cap before its first assertion, with the verdict `Error: Check timed out after 60.0s`. Its pre-evidence stage is a bounded retry against an OBSERVABLE condition only (PutEvents returns FailedEntryCount 0 and the check then polls ReceiveMessage for the envelope), so a timeout there means messages were never produced at the consumer, not that the check waited on nothing. Both legs of that stage are paths this project already has open reports against: EventBridge target delivery not completing (20261025T002357Z-events-eventbridge-target-delivery-never-completes-for-sns-step.md, 20261023T140640Z-cloudfront-events-eventbridge-never-delivers-a-matched-event-to-any.md) and no service-emitted events at all reaching a rule's SQS target (20261024T030130Z-events-rds-sqs-rds-publishes-no-db-instance-events-to-the.md, 20261025T020208Z-cloudwatch-ecr-ecs-ecr-emits-no-image-action-events-to-eventbridge.md). None of those names Batch as an event SOURCE and none carries this check's replay key, so the Batch emission side is unreported: the service has no job-state-change publisher at all, and the two observable consequences (no envelope on the matching rule's queue, and the negative/absence and repair layers being ungradeable) both follow from that.

Why: a client that wires job orchestration to Batch events gets silence. Job completion/failure fan-out, alerting on FAILED transitions, and any state machine driven by `Batch Job State Change` never fire, and the failure is invisible — EventBridge reports FailedEntryCount 0 and the rule looks correctly configured, so the caller cannot distinguish "no transition yet" from "this service emits nothing". Negative tests are equally misled: a rule pinned to the wrong job queue appears correct because EVERY rule receives nothing.

Fix: the Batch job-state machine needs an event-emission step wherever a job's status is advanced (the SubmitJob/scheduler sweep that moves SUBMITTED -> RUNNABLE, and the TerminateJob/terminal transition path) in the batch service's job state, publishing an aws.batch "Batch Job State Change" envelope onto the default bus built by projecting the stored job record rather than authoring a fresh body; and the EventBridge rule-matching/target-dispatch component must carry that envelope to an SQS target so the default-bus delivery is observable at the consumer. The envelope's detail must be read from the same job record DescribeJobs serves, so the two views cannot disagree.

Traces: batch__events__sqs.batch-job-state-change-event-delivered-to-matching-rule-and-withheld-from-other-queue (verdict mismatch, `Check timed out after 60.0s`).

## Evidence
Expected (AWS): after SubmitJob to a job queue fronted by an UNMANAGED compute environment, an ENABLED default-bus rule with EventPattern {"source":["aws.batch"],"detail-type":["Batch Job State Change"],"detail":{"jobQueue":[<watched job queue ARN>]}} and an SQS target receives an envelope with source="aws.batch", detail-type="Batch Job State Change", account=<caller account>, region=<call region>, resources=[<job ARN>], detail.jobId=<the submitted job id>, detail.jobQueue=<watched queue ARN>, detail.status="RUNNABLE", detail.jobDefinition starting with "arn:", detail.createdAt an epoch-millis integer, and detail.jobName/detail.createdAt equal to the values DescribeJobs reports for the same job. No SUBMITTED event is ever produced. A second envelope with detail.status="FAILED" follows TerminateJob and carries the call's `reason` inside detail.statusReason. A sibling rule pinning a different job queue ARN receives nothing over a window of 3x the measured delivery latency (floor 180 s) and its queue reports ApproximateNumberOfMessages=0 and ApproximateNumberOfMessagesNotVisible=0, then receives its own RUNNABLE envelope once a job IS submitted to that sibling queue.

Actual (emulator): no envelope is ever observed at the SQS consumer. The check is terminated by the suite's per-check cap with `Error: Check timed out after 60.0s`, before its first assertion, while still inside the bounded delivery-proving stage (PutEvents is accepted with FailedEntryCount 0, but ReceiveMessage on the target queue returns nothing). Nothing in the Batch -> EventBridge -> SQS path produces an observable message, so the positive delivery, the latency-calibrated absence on the sibling wiring, the SUBMITTED-suppression rule, the FAILED/statusReason transition and the sibling repair are all ungradeable.

Note on values: the account id, region, job id, job ARN, queue ARNs, job/queue/rule names, createdAt timestamp and terminate reason above are per-run values filled in from the request and the emulator's state; the fixed requirements are the source "aws.batch", the detail-type "Batch Job State Change", the one-element `resources` list holding the job ARN, the detail member names and types, the RUNNABLE-then-FAILED transition sequence with no SUBMITTED event, and the agreement between the detail and DescribeJobs.

## Steps to Reproduce
1. Create an UNMANAGED, ENABLED Batch compute environment with a customer-managed service role and poll it to VALID (no container ever runs, so a job parks in RUNNABLE).
2. Create two ENABLED job queues on that compute environment and poll both to VALID; keep their distinct jobQueueArn values as <watched> and <sibling>.
3. Create two SQS queues and set a Policy on each allowing principal events.amazonaws.com to sqs:SendMessage.
4. For each SQS queue, prove the wiring can deliver: PutRule with a throwaway pattern on a custom source, PutTargets with that queue's ARN, then PutEvents on that source and ReceiveMessage until the envelope arrives. (In the emulator this loop never observes a message, and the suite's 60 s cap fires here.)
5. PutRule (ENABLED, default bus) with EventPattern {"source":["aws.batch"],"detail-type":["Batch Job State Change"],"detail":{"jobQueue":["<watched>"]}} and PutTargets to the watched SQS queue; repeat with "<sibling>" to the sibling queue. Drain both queues to empty.
6. RegisterJobDefinition (type=container), then SubmitJob to the WATCHED queue by name.
7. ReceiveMessage on the watched queue and look for an envelope with source "aws.batch", detail-type "Batch Job State Change" and detail.jobId = the submitted job id with detail.status "RUNNABLE". Expected: it arrives. Actual: nothing arrives.
8. TerminateJob with a reason and poll the watched queue for a second envelope with detail.status "FAILED" carrying that reason in detail.statusReason. Expected: it arrives; no envelope with detail.status "SUBMITTED" ever appears. Actual: nothing arrives.
9. GetQueueAttributes on the sibling queue, then SubmitJob to the SIBLING queue and poll it for its own RUNNABLE envelope naming "<sibling>" in detail.jobQueue. Expected: the sibling queue reported 0/0 before this submit and now receives exactly its own job's event, never the first job's. Actual: it receives nothing at any point.
