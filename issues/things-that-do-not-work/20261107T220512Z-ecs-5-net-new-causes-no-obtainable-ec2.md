# ecs: 5 net-new causes — no obtainable EC2 identity document (agent plane dead), a one-shot Fargate task never reaches STOPPED, ExecuteCommand stays InvalidParameterException after enableExecuteCommand, ListServicesByNamespace returns nothing, and an ecs:RunTask deny is not enforced

## Operation
RegisterContainerInstance

## Description
Five independent root causes in the ECS surface, all grounded in failing checks the suite lists under `### ecs` and none of them marked ALREADY FILED or OWNED. Each must be closed before submitting.

Cause 1 of 5: an emulator-launched EC2 instance never becomes an SSM-managed, Online instance, so no AWS-signed EC2 instance identity document can be obtained and RegisterContainerInstance can never be driven the way AWS requires.
  AWS: RegisterContainerInstance validates the (instanceIdentityDocument, instanceIdentityDocumentSignature) pair cryptographically and refuses a synthetic pair with InvalidParameterException (Smithy: ecs RegisterContainerInstance models InvalidParameterException/ClientException at 400 and AccessDeniedException at 403), so the only supported way to get the pair is from the instance itself: launch an EC2 instance with an SSM-capable instance profile, poll ssm DescribeInstanceInformation until that instance id reports PingStatus=Online, then read http://169.254.169.254/latest/dynamic/instance-identity/document and .../signature through an AWS-RunShellScript Run Command. Recorded behavior: that chain completes well inside each check's budget.
  Emulator: DescribeInstanceInformation never reports the launched instance at all — the poll's last observed value is None for the full 100-120s budget, so the identity document is never read and no container instance is ever registered. Failures read `AssertionError: identity-fetch EC2 instance never registered Online with SSM (status=None)` / `AssertionError: condition not met within 120.0s (last=None)`.
  Why: the whole ECS-on-EC2 agent plane is unreachable for a client following AWS's only supported registration path — container-instance attributes (PutAttributes/ListAttributes/DeleteAttributes against a container-instance target), DiscoverPollEndpoint, SubmitTaskStateChange / SubmitContainerStateChange, ExecuteCommand on an EC2-launched task and the container-instance register/deregister lifecycle can neither be exercised nor refused.
  Emulator component: the EC2 instance-identity-document source plus the SSM managed-instance registration and Run Command execution that exposes it, and downstream the ECS RegisterContainerInstance handler's acceptance of that pair.
  Fix: whatever makes an emulator-launched EC2 instance an Online SSM managed instance and serves its identity document, then the ECS register_container_instance op that must accept it.
  Note: the open 20261107T080429Z-ecs-2-net-new-causes-no-aws-signed.md records the same cause for these same checks under a DIFFERENT replay key (a 60s harness Timeout inside _poll_until); the current run fails earlier with explicit AssertionErrors, so none of these checks is owned by it — close them together.
  Failing check ids: ecs.attribute-put-list-delete-roundtrip, ecs.attributes-put-list-delete-lifecycle, ecs.container-instance-register-deregister-lifecycle, ecs.delete-attributes-missing-target-rejected, ecs.discover-poll-endpoint-returns-endpoint-for-registered-instance, ecs.execute-command-requires-enabled-flag, ecs.submit-container-state-change-updates-container-status, ecs.submit-task-state-change-updates-task-status.

Cause 2 of 5: a standalone one-shot Fargate task never leaves RUNNING, so it never exits to STOPPED.
  AWS: a RunTask task whose only essential container runs a command that terminates moves lastStatus RUNNING -> DEACTIVATING/STOPPING -> STOPPED with desiredStatus STOPPED, the container's exitCode set (0 for a clean exit) and stopCode EssentialContainerExited; the cluster's runningTasksCount then drops to zero and the empty cluster deletes cleanly. Recorded behavior for the timing; the Smithy model carries the Task lastStatus/stopCode/containers[].exitCode members but states no rule.
  Emulator: the task stays `lastStatus: RUNNING`, `desiredStatus: RUNNING` with its container `lastStatus: RUNNING` and NO exitCode for the whole 150s budget — `AssertionError: condition not met within 150.0s; last={... 'desiredStatus': 'RUNNING', 'lastStatus': 'RUNNING', 'containers': [{... 'lastStatus': 'RUNNING', 'healthStatus': 'UNKNOWN'}] ...}` (the ARNs, ids, IPs and timestamps in that payload are per-run values; the stuck RUNNING status and the missing exitCode are the divergence).
  Why: batch/one-shot workloads never complete for a client that waits on DescribeTasks, cluster cleanup is blocked by a task that will never stop, and no exit code is ever observable.
  Fix: the ECS task lifecycle in the task state machine — a container whose command terminates must drive the task through STOPPING to STOPPED with exitCode and stopCode, and the cluster's runningTasksCount must follow. Related open issue 20261104T062603Z-ecs-containers-never-execute-no-in-container-behaviour.md covers in-container execution and does not carry this replay key.
  Failing check id: ecs.e2e-run-task-to-completion-and-cluster-cleanup.

Cause 3 of 5: ExecuteCommand keeps refusing with InvalidParameterException after the task is launched WITH enableExecuteCommand.
  AWS: ExecuteCommand on a RUNNING task launched without enableExecuteCommand is refused with InvalidParameterException (Smithy: ExecuteCommand models InvalidParameterException, TargetNotConnectedException, ClientException, ClusterNotFoundException at 400 and AccessDeniedException at 403) because the launch-time gate is not satisfied; the identical call on the same task definition launched WITH the flag must no longer hit that gate — it either returns a session or, if the exec agent is not connected, the modeled TargetNotConnectedException. The launch-time gate is keyed on the task's enableExecuteCommand value.
  Emulator: both calls return the same InvalidParameterException — `AssertionError: enabling the flag must clear the launch-time gate; still got InvalidParameterException on the identical call after enabling it` — so the refusal is not keyed on the task's enableExecuteCommand at all.
  Why: a client can never distinguish "you forgot enableExecuteCommand" from "the exec agent is not connected", and an exec-enabled task is reported as unusable for the wrong reason; the negative test for the flag is indistinguishable from the positive one.
  Fix: the ExecuteCommand handler's precondition check — read the task's enableExecuteCommand and only raise InvalidParameterException when it is false, otherwise fall through to the session/TargetNotConnectedException path. Related open issue 20261104T062603Z-ecs-exec-the-executecommandagent-managed-agent-never-reaches.md covers the agent never reaching RUNNING and does not carry this replay key.
  Failing check id: ecs.execute-command-without-exec-enabled-rejected.

Cause 4 of 5: ListServicesByNamespace never returns a Service-Connect-enabled service.
  AWS: a service created with a serviceConnectConfiguration naming a Cloud Map namespace is listed by ListServicesByNamespace for that namespace (Smithy: input {namespace (required), nextToken, maxResults}, output {serviceArns, nextToken}, readonly+paginated, errors NamespaceNotFoundException/InvalidParameterException/ClientException at 400).
  Emulator: serviceArns stays empty for the whole poll — `AssertionError: timed out waiting for 'the Service-Connect-enabled service becomes visible via ListServicesByNamespace' (last=[])` — even though the service was created successfully.
  Why: a client enumerating the services in a Service Connect namespace (the documented way to find the members of a mesh) gets an empty list and concludes the namespace is unused.
  Fix: the ListServicesByNamespace handler and the service-state index it reads — services must be recorded against their serviceConnectConfiguration namespace at CreateService/UpdateService time. Related open issues 20261104T062603Z-ecs-refusal-messages-and-error-classes-diverge-from.md and 20261104T062603Z-ecs-resource-scoping-and-agent-only-apis-are.md carry other ListServicesByNamespace checks' keys, not this one.
  Failing check id: ecs.list-services-by-namespace.

Cause 5 of 5: an IAM policy denying ecs:RunTask is not enforced — RunTask still launches the task.
  AWS: once the caller's identity-based policy no longer allows (or explicitly denies) ecs:RunTask, RunTask is refused with HTTP 403 and error code AccessDeniedException (Smithy: RunTask models AccessDeniedException at httpError 403), whose message is AWS's fixed authorization sentence with the caller ARN, the action `ecs:RunTask` and the resource taken from the request ("User: <caller arn> is not authorized to perform: ecs:RunTask on resource: <task definition/cluster arn> because no identity-based policy allows the ecs:RunTask action"), and no task is created.
  Emulator: the call keeps succeeding for the whole poll after the inline policy update — `AssertionError: timed out waiting for 'ecs:RunTask denial to take effect after the inline policy update' (last=('launched', None, None))`: a task is launched and there is no error code and no message.
  Why: least-privilege regressions are invisible — a role that AWS would block can still start tasks, so an authorization test passes in the emulator and fails in AWS.
  Fix: caller authorization in the ECS RunTask handler (evaluate the caller's IAM policy for ecs:RunTask on the requested resource before placing the task) and the AccessDeniedException it must raise. Related open issue 20261024T081305Z-ecs-is-overly-permissive-ten-validations-authorizations-aws.md covers other permissiveness causes and does not carry this replay key.
  Failing check id: ecs.run-task-blocked-by-iam-policy-rejected.
