# apigateway: every private custom-domain / domain-name-access-association check hangs because an EC2 interface VPC endpoint never leaves `pending` (1 cause)

> _Note: this issue was identified against the code base at commit `b827135cf833dfec17047e08babbbec809d0cc25`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause, grounded in eight failing behavioral checks whose ids lead with `apigateway.`. None of the eight is marked ALREADY FILED or OWNED in the replay report. Cause count: 1 — it is numbered below with the full list of failing check ids it must be verified against before this issue is submitted.

=== Cause 1 of 1: a created interface VPC endpoint is reported `pending` forever, so every check that must wait for it to become `available` is killed at the harness cap ===
AWS: Smithy (com.amazonaws.ec2#AmazonEC2) CreateVpcEndpoint returns `VpcEndpoint`, whose `State` member ("The state of the endpoint", target enum com.amazonaws.ec2#State with members PendingAcceptance | Pending | Available | Deleting | Deleted | Rejected | Failed | Expired | Partial) is non-terminal on create: an interface endpoint to an AWS-provided service (here com.amazonaws.<region>.execute-api) is answered pending and then reaches available WITHOUT any further caller action, which is why DescribeVpcEndpoints is the documented way to observe it ("Describes your VPC endpoints"). Recorded behavior: every one of the eight checks provisions a VPC, a subnet, a security group and that interface endpoint, then polls ec2 DescribeVpcEndpoints(VpcEndpointIds=[E]) until VpcEndpoints[0].State is `available` (budgets of 240 s / 300 s against real AWS) before it issues a single API Gateway private-domain call. On the wire AWS reports this member in its lowercase spelling (`pending`, then `available`), which is what the checks compare against exactly.
Emulator: ec2 CreateVpcEndpoint is accepted and hands back a VpcEndpointId, but the endpoint's State never changes: DescribeVpcEndpoints keeps reporting the pending state the create stored, so the poll never converges and each check is killed by the suite at its 60.0 s cap ("Error: Check timed out after 60.0s"), with no apigateway operation under test ever issued. The cause is visible in the checkout: services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs stores the endpoint with `state: Some(state::VPC_ENDPOINT_STATE_PENDING)` and records the owed move with `store.vpc_endpoint_moves.insert(endpoint_id, PendingStateMove::starting_now(VPC_ENDPOINT_STATE_AVAILABLE))`, and services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_vpc_endpoints.rs calls `store.materialize_due_transitions()` before it reads — but `materialize_due_transitions` in services/service-com-amazonaws-ec2-amazonec2/src/state.rs never consumes `vpc_endpoint_moves` (it applies instances, VPCs, subnets, carrier gateways, IPAM pools/scopes, Verified Access endpoints, route-server endpoints, `vpc_endpoint_connection_moves` and others). The map is written by the create and read by nothing, so the owed Pending -> Available transition is never applied no matter how long a client waits. No status code or error code diverges here — the divergence is a response VALUE that never changes.
Why: the endpoint's readiness is the gate in front of API Gateway's whole v1 PRIVATE custom-domain surface. A private custom domain name, its base path mappings and every domain-name access association are defined in terms of an interface execute-api endpoint, so a client that provisions one (CloudFormation, CDK, Terraform or a hand-rolled waiter — botocore's own vpc_endpoint waiters included) blocks forever instead of proceeding, and nothing downstream of the gate can be observed at all: CreateBasePathMapping's duplicate ConflictException and its one-persisted-mapping invariant, DeleteBasePathMapping's NotFoundException ("Invalid base path mapping identifier specified"), CreateDomainNameAccessAssociation's BadRequestException for a non-existent endpoint id ("<vpce-id> is not a valid VPC endpoint id") and its positive control, GetDomainNameAccessAssociations' listing, and the reject/delete access-association lifecycle are all left unexercised.
Fix: the EC2 VPC-endpoint state machine, not anything in the apigateway crate — `ComAmazonawsEc2Amazonec2State::materialize_due_transitions` in services/service-com-amazonaws-ec2-amazonec2/src/state.rs must apply the moves held in `vpc_endpoint_moves` (the same retain-and-apply shape the VPC, subnet and carrier-gateway moves beside it use, and the same shape `vpc_endpoint_connection_moves` already gets), so that an endpoint created by services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs is reported `available` by services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_vpc_endpoints.rs once TRANSITION_DELAY has passed, whether or not anyone called in between. Two things must hold for the gate to actually open: the reported value has to be the spelling DescribeVpcEndpoints puts on the wire (lowercase `pending` / `available`), since the checks compare it exactly; and the same materialized state must be what the `vpc-endpoint-state` filter and the delete path see, so one endpoint is never reported two ways.
Traces: apigateway.concurrent-create-base-path-mapping-duplicate-race, apigateway.create-base-path-mapping-duplicate-rejected, apigateway.concurrent-domain-name-access-association-duplicate, apigateway.create-domain-name-access-association-without-vpce-fails, apigateway.domain-access-association-concurrent-reject-delete, apigateway.domain-name-access-association-lifecycle, apigateway.reject-domain-name-access-association-removes-pending, apigateway.reject-domain-name-access-association-wrong-state-fails.
