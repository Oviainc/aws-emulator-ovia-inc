# firehose: 3 net-new root causes — the ResourceNotFoundException message says "under accountId" and drops its terminal period, the InvalidKMSResourceException message is a KMS-shaped "does not exist" string, and StopDeliveryStreamEncryption words the already-disabled refusal wrongly

> _Note: this issue was identified against the code base at commit `8005689898fcaab18d59205649ae7b06565801fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDeliveryStream

## Description
Three distinct, net-new root causes in the firehose service, all of them error-MESSAGE fidelity defects on refusals that the emulator otherwise classifies correctly (right HTTP status, right error code, wrong message text). firehose is bootstrapped (get_bootstrap_status reports service-com-amazonaws-firehose-firehose-20150804), so these are fidelity findings, not bootstrap gaps.

Context for a fixer: the open issue 20261022T064119Z-firehose-createdeliverystream-putrecordbatch-are-overly-permissive-and-misclassify.md carries several of the same check ids, but it owns the EARLIER failures in those flows (calls that were accepted with 200, or refused with the wrong error code). Those checks now get past the code/status assertions and fail on the message assertion that follows, with a replay key that issue does not carry, and the replay report did not mark them OWNED. The causes below are the message-text defects only; none of them is the acceptance/classification defect that issue describes.

Cause 1 of 3: the ResourceNotFoundException message for an unknown delivery stream is misworded — "accountId" where AWS writes "account", and the terminal period is missing.
AWS: Smithy: ResourceNotFoundException (com.amazonaws.firehose#ResourceNotFoundException, errorKind client, HTTP 400, doc "The specified resource could not be found.") is the modeled not-found error of DescribeDeliveryStream, DeleteDeliveryStream, ListTagsForDeliveryStream, TagDeliveryStream and StopDeliveryStreamEncryption; its only member is `message`. The model does not fix the message text, so the message is recorded behavior: when the named DeliveryStreamName does not exist in the caller's account, AWS returns the message template `Firehose under account <accountId> not found.` — fixed text "Firehose under account " + " not found." (with the terminal period), and ONE variable part, <accountId>, which is the 12-digit account id of the calling credentials (the recorded runs show 000000000000 because that is the emulator's account; the account id is a per-environment value, not part of the requirement).
Emulator: the same refusal carries `Firehose under accountId 000000000000 not found` — the fixed text reads "under accountId" instead of "under account", and the sentence-final period is absent. Error code (ResourceNotFoundException) and status (400) are correct; only the message diverges.
Why: a client that branches on, logs or asserts the not-found message — or any test/monitoring rule that string-matches AWS's documented wording — behaves differently against the emulator than against AWS. Because this message is produced by the shared not-found path, EVERY control-plane operation that can answer not-found is affected at once, so the divergence is systemic rather than confined to one API.
Fix: the firehose service's shared ResourceNotFoundException construction (the not-found helper the delivery-stream operation handlers call from their state lookup — DescribeDeliveryStream, DeleteDeliveryStream, ListTagsForDeliveryStream, TagDeliveryStream, StopDeliveryStreamEncryption all reach it) must emit the AWS template "Firehose under account {account_id} not found." — the literal word "account", and the terminal period.
Traces: firehose.describe-nonexistent-stream-not-found, firehose.delete-nonexistent-stream-not-found, firehose.list-tags-nonexistent-stream-not-found, firehose.tag-delivery-stream-nonexistent-rejected, firehose.delete-transitions-to-deleting, firehose.delete-stream-transitions-to-deleting-then-gone, firehose.delete-stream-during-creating-rejected, firehose.delete-stream-while-update-in-progress-resource-in-use, firehose.create-delivery-stream-untrusted-role-rejected, firehose.create-kinesis-source-type-without-source-config, firehose.create-stream-buffering-interval-below-minimum-rejected, firehose.create-stream-buffering-interval-out-of-range-rejected, firehose.create-stream-buffering-size-above-maximum-rejected, firehose.create-stream-conflicting-destination-configs, firehose.create-stream-conflicting-destinations-rejected, firehose.create-stream-malformed-role-arn-rejected, firehose.create-stream-name-exceeds-length-limit-rejected, firehose.create-stream-nonexistent-role-arn-rejected, firehose.create-stream-role-arn-malformed-rejected, firehose.create-stream-role-missing-trust-policy-denied, firehose.create-stream-role-missing-trust-policy-rejected, firehose.splunk-retry-duration-out-of-range-rejected, firehose.deploy-cfn-stack-deletion-removes-delivery-stream, firehose.deploy-cfn-stream-tags-and-encryption-applied, firehose.e2e-create-put-deliver-to-s3-delete-and-confirm-gone, firehose.e2e-create-put-land-delete-full-flow, plus two checks whose suite ids are composite multi-service tokens (events__firehose__s3 and firehose__kinesis__s3) but whose divergence is this same firehose message: events__firehose__s3.firehose-role-without-trust-policy-rejected and firehose__kinesis__s3.cli-firehose-describe-nonexistent-delivery-stream-negative.

Cause 2 of 3: CreateDeliveryStream's InvalidKMSResourceException for an unusable CMK carries a KMS-style "key does not exist" string instead of Firehose's key-policy message.
AWS: Smithy: CreateDeliveryStream models InvalidKMSResourceException (client, HTTP 400), documented as "Firehose throws this exception when an attempt to put records or to start or stop Firehose stream encryption fails. This happens when the KMS service throws one of the following exception types: AccessDeniedException, InvalidStateException, DisabledException, or NotFoundException." The shape carries `code` and `message` members. Message text is recorded behavior: a DeliveryStreamEncryptionConfigurationInput with KeyType=CUSTOMER_MANAGED_CMK and a KeyARN the Firehose service cannot use is refused with the entirely fixed text `AccessDenied by KMS while using the CMK. Check the key policy to ensure that the KMS grant related apis are allowed. Try again after the key policy has the right permissions.` — Firehose reports the failure in terms of its own inability to use the key under the key policy, with NO variable part, and does not leak the KMS-side exception or echo the key ARN.
Emulator: the error code and status are now correct, but the message is `Key '<keyARN>' does not exist` (recorded instance: Key 'arn:aws:kms:us-west-2:111122223333:key/00000000-0000-0000-0000-000000000000' does not exist — the ARN is the request's KeyARN, i.e. a request value filling an emulator-invented template, not AWS wording).
Why: a client cannot distinguish the documented Firehose condition (the CMK exists but the key policy/grant does not permit Firehose) from a nonexistent key, and operators following AWS's remediation text (fix the key policy) get a message pointing them at the wrong problem. Any handling keyed on the documented string fails.
Fix: the CreateDeliveryStream handler's encryption-configuration validation must raise InvalidKMSResourceException with Firehose's fixed message text rather than surfacing the KMS state lookup's own "does not exist" string.
Traces: firehose.create-stream-invalid-kms-key-arn.

Cause 3 of 3: StopDeliveryStreamEncryption's refusal on an unencrypted stream words the state clause as "when encryption is in DISABLED status" instead of "when encryption is already disabled".
AWS: Smithy: StopDeliveryStreamEncryption models InvalidArgumentException (client, HTTP 400, doc "The specified input parameter has a value that is not valid."), ResourceInUseException, ResourceNotFoundException and LimitExceededException; the message text is recorded behavior. Calling StopDeliveryStreamEncryption on a stream whose encryption is already off is refused with the message template `Cannot disable encryption on firehose: <DeliveryStreamName> when encryption is already disabled` — fixed text "Cannot disable encryption on firehose: " and " when encryption is already disabled", with ONE variable part, the DeliveryStreamName taken verbatim from the request (the recorded run's generated stream name only fills that slot).
Emulator: the prefix and the stream-name substitution are right, but the trailing clause is rendered from the emulator's internal status enum: `... when encryption is already disabled` becomes `... when encryption is in DISABLED status`.
Why: the message is a requirement of the refusal; a client or operator matching AWS's wording to recognise the benign idempotent-stop case sees an unrecognised string, and the emulator leaks its internal encryption-status enum name into a customer-facing message.
Fix: the StopDeliveryStreamEncryption handler's already-disabled guard must format AWS's clause ("when encryption is already disabled") instead of interpolating the stored DeliveryStreamEncryptionStatus value.
Traces: firehose.stop-encryption-on-unencrypted-stream.
