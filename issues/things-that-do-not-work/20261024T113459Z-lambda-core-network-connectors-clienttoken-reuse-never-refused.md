# lambda-core network connectors: ClientToken reuse never refused, ARN names the connector by Name not Id, OperatorRole and SubnetIds are never validated, and state-conflict refusals diverge (6 causes)

> _Note: this issue was identified against the code base at commit `6b8dcd825499bdd91675cbbb3bc6eaac525bf5b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateNetworkConnector

## Description
Six net-new root causes in the lambda-core network-connector control plane, found by replaying the behavioral suite (lambda-core scored 5/23). Four of them make the emulator ACCEPT (HTTP 202) a request real AWS REFUSES, one mints an ARN that disagrees with the connector's own Id, and one states a modeled state-conflict refusal by a different rule than the service does. Related open issue: 20261023T022015Z-lambda-core-admits-requests-aws-refuses-and-misclassifies.md (a WIRE issue whose Cause 2/3 concern CreateNetworkConnector EC2-reference validation). It does NOT cover Causes 1, 2, 3, 5 or 6 below, and its Cause 3 is grounded in wire fixture keys, not in the behavioral check named in Cause 4 here.

--- Cause 1 of 6: a ClientToken reused with DIFFERENT parameters is served as an idempotent replay instead of being refused. ---
AWS: Smithy (com.amazonaws.lambdacore) CreateNetworkConnector.ClientToken -> ClientTokenString, @idempotencyToken, @length 1..64; the operation models ResourceConflictException (httpError 409). The operation's own model docs say idempotency holds only when "you retry a request that completed successfully using the same client token" — i.e. the token is bound to the parameter set it first carried. The recorded service refuses the same token presented with a different Name with HTTP 409 / ResourceConflictException; the recorded message, which is the service's fixed sentence for a token/parameter mismatch, is "A request with the same client token but different parameters was already submitted".
Emulator: accepts the call. services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/ops/create_network_connector.rs stores only (name, version) under the token (crate::state::TokenOutcome in src/state.rs), with no fingerprint of the request, so a token reused with a changed Name returns 202 carrying the ORIGINAL connector instead of refusing. The check's helper reports it as "the call unexpectedly SUCCEEDED; real AWS rejects it".
Why: a client that mutated its request but reused its retry token believes the new connector exists under the new Name. Nothing was created under that Name, and the client never learns its request was ignored — the classic silent-idempotency data loss that 409 exists to prevent.
Fix: CreateNetworkConnector's handler must remember the request fingerprint (Name, Configuration, OperatorRole, Tags) alongside the token and refuse ResourceConflictException when a known token arrives with a different fingerprint; replay only on an exact match.
Traces: lambda-core.client-token-replay-rejects-changed-parameters.

--- Cause 2 of 6: the connector ARN's resource segment is the connector's Name, not its Id, so Arn and Id disagree. ---
AWS: Smithy CreateNetworkConnector output carries both Arn (NetworkConnectorArn, pattern ^(arn:aws[a-zA-Z-]*:lambda:...:\d{12}:network-connector:[a-zA-Z0-9-_]+(:[1-9][0-9]*)?)$) and Id (NetworkConnectorId, @required, "assigned by the service at creation time"). Recorded behavior (two independent blessed checks assert it): the resource segment after "network-connector:" is the service-assigned Id, so Arn always ends in ":network-connector:<Id>" for the Id the same response returns. The requirement is the self-consistency of the response, not any particular id text.
Emulator: src/state.rs connector_arn(region, name) builds "network-connector:{Name}" and create_network_connector.rs calls it with input.name, while mint_connector_id() mints an unrelated "nc-%016x". Replay shows Arn 'arn:aws:lambda:us-west-2:000000000000:network-connector:sim2real-lnc-6a4e2e0920bf' alongside Id 'nc-0000000000000001'. Every downstream ARN inherits it: NetworkConnector.arn, version_arn ("{arn}:{version}"), VersionArn, LatestVersionArn, the List summaries, and the "Network connector not found: <arn>" message.
Why: a client that derives an ARN from the Id (for IAM resource policies, tagging, CloudTrail correlation or a version-qualified identifier) builds an ARN the emulator cannot resolve, and a client that parses the Id out of the ARN gets the Name. The two identity fields of the same resource contradict each other.
Fix: connector_arn in src/state.rs (and its one call site in create_network_connector.rs) must be built from the minted Id, with the Id minted before the ARN; name-based lookup stays available through parse_identifier/name_of.
Traces: lambda-core.create-get-network-connector-field-roundtrip, lambda-core.network-connector-lifecycle-round-trip.

--- Cause 3 of 6: CreateNetworkConnector never validates OperatorRole, so an unusable IAM role is accepted. ---
AWS: Smithy CreateNetworkConnector.OperatorRole -> NetworkConnectorRoleArn (pattern ^arn:(aws[a-zA-Z-]*)?:iam::\d{12}:role/?[a-zA-Z_0-9+=,.@\-_/]+$), documented as "the IAM role that Lambda assumes to manage elastic network interfaces in your VPC. This role must have permissions for ec2:CreateNetworkInterface, ec2:DeleteNetworkInterface, and related describe operations"; the operation models InvalidParameterValueException (httpError 400). Recorded behavior: the role is proved usable SYNCHRONOUSLY in two stages and each failure is HTTP 400 / InvalidParameterValueException — a trust policy that does not name lambda.amazonaws.com (recorded message example: "The service is unable to assume the provided NetworkConnectorOperatorRole. Please verify the trust policy on the role.") and a role lacking the ENI permissions (recorded message example: "Encountered unauthorized operation while calling EC2 due to invalid ConnectorOperatorRole permissions").
Emulator: create_network_connector.rs stores input.operator_role on the version verbatim and performs no IAM lookup at all — neither role existence, nor trust principal, nor attached permissions. Both refused creates are answered 202 PENDING.
Why: the single most common real-world misconfiguration of this API — a connector wired to a role Lambda cannot assume — is reported as a healthy connector, so a caller ships the broken wiring and negative tests of role validation pass against a service that validates nothing.
Fix: OperatorRole validation in CreateNetworkConnector's handler (and the same check on the UpdateNetworkConnector path, which also accepts the member): resolve the role in the IAM store, require lambda.amazonaws.com in its trust policy and the ENI permissions on its attached policies, and raise InvalidParameterValueException otherwise.
Traces: lambda-core.create-rejected-with-unusable-operator-role.

--- Cause 4 of 6: CreateNetworkConnector never validates that the SubnetIds exist, so a connector is created over a subnet that does not exist. ---
AWS: Smithy CreateNetworkConnector.Configuration -> NetworkConnectorConfiguration (@required), a VpcEgressConfiguration naming EC2 subnets; the operation models InvalidParameterValueException (httpError 400). Recorded behavior: a syntactically valid but non-existent subnet is refused synchronously at call time with HTTP 400 / InvalidParameterValueException whose message carries the downstream EC2 failure and names the missing subnet (recorded example: "Error occurred while DescribeSubnets. EC2 Error Code: InvalidSubnetID.NotFound. EC2 Error Message: The subnet ID '<id>' does not exist"). No connector is created and there is no PENDING-then-FAILED transition for this input. The status, the error class, and the fact that the message names the offending subnet and reports it as non-existent are the requirement.
Emulator: create_network_connector.rs reads nothing from the EC2 store; it validates only Name uniqueness and the connector quota, then returns 202 PENDING and persists the connector.
Why: a caller is told a connector is provisioning over a subnet that cannot exist; the connector then reports ACTIVE and is enumerated by List, so the misconfiguration is undetectable through the API.
Fix: validate every SubnetId (and SecurityGroupId) in the Configuration against the EC2 store in CreateNetworkConnector's handler, before any state is written, raising InvalidParameterValueException. Note: the open WIRE issue 20261023T022015Z-lambda-core-admits-requests-aws-refuses-and-misclassifies.md describes the same handler gap from its own fixtures; a fixer closing this cause must also re-replay the behavioral check below, which that issue does not carry.
Traces: lambda-core.network-connector-create-nonexistent-subnet-rejected.

--- Cause 5 of 6: UpdateNetworkConnector never validates that the SubnetIds exist, so a bad update is accepted and persisted onto a healthy connector. ---
AWS: Smithy UpdateNetworkConnector.Configuration -> NetworkConnectorConfiguration; the operation models InvalidParameterValueException (httpError 400) and returns LastUpdateStatus (NetworkConnectorLastUpdateStatus). Recorded behavior: subnet existence is validated SYNCHRONOUSLY, not through the asynchronous LastUpdateStatus machinery — an update naming a non-existent subnet is refused immediately with HTTP 400 / InvalidParameterValueException whose message embeds the EC2 DescribeSubnets failure (code InvalidSubnetID.NotFound) and names the subnet. The rejected call mutates nothing: Get keeps serving the PREVIOUS Configuration, State stays ACTIVE, and LastUpdateStatus stays ABSENT because the request never reached the async update path.
Emulator: src/ops/update_network_connector.rs checks only the identifier form, an idempotency replay, State == ACTIVE, whether anything changed, and the version cap; it then appends a new version carrying the caller's Configuration. The non-existent subnet is accepted with 202 and persisted, and LastUpdateStatus is set to InProgress.
Why: an update that AWS refuses outright takes a working connector's configuration to a subnet that does not exist, and a caller that correctly treats 202/InProgress as "accepted" never retries. This is distinct from Cause 4: Create and Update are separate handlers and the Update path is not covered by any open issue.
Fix: the same EC2-reference validation as Cause 4, in UpdateNetworkConnector's handler, ahead of the version append — and it must leave State, Configuration and LastUpdateStatus untouched when it refuses.
Traces: lambda-core.failed-update-keeps-connector-active-on-previous-config.

--- Cause 6 of 6: the state-conflict refusals for a PENDING connector are stated by the wrong rule — they name the connector by Name instead of by Id, and use different wording from the service. ---
AWS: Smithy ResourceConflictException (httpError 409) is modeled on both UpdateNetworkConnector and DeleteNetworkConnector ("for example, attempting to update a connector that is not in ACTIVE state"); DeleteNetworkConnector documents "You can delete connectors in ACTIVE or FAILED states". The message rule is known because it is built from the resource: for an update refused while the connector is PENDING the service states "Network connector <Id> is in state Pending and cannot be updated. Only ACTIVE connectors can be updated." — the connector's service-assigned Id, and the state capitalised as 'Pending'. For a delete refused while PENDING it states the fixed sentence "Network connector is in PENDING state and cannot be deleted". Two independent checks derive the update message from the Id the create response returned, so the identifier it must carry is the Id.
Emulator: the 409 status and the ResourceConflictException code are correct, but the message is built by a different rule. update_network_connector.rs formats "The network connector {name} is in {state} state; it must be ACTIVE to accept updates" (replay: 'The network connector sim2real-lnc-96f2011998ca is in PENDING state; it must be ACTIVE to accept updates'), and delete_network_connector.rs formats "The network connector {name} is in {state} state; it can be deleted once it is ACTIVE" — both naming the connector by Name through connector_conflict() in src/state.rs.
Why: the refusal does not name the resource by the identifier the service uses, so a client (or operator reading a log) cannot correlate the 409 with the Id it holds, and the Name it is given is not the field AWS reports here. This compounds Cause 2, where Name and Id are already conflated.
Fix: the two conflict call sites (update_network_connector.rs state gate, delete_network_connector.rs state gate) must state the service's sentences and identify the connector by its Id.
Traces: lambda-core.network-connector-update-pending-conflict-then-active-success, lambda-core.pending-connector-rejects-update-and-delete.
