# cognito-identity: 2 net-new root causes — GetCredentialsForIdentity never requests the mapped principal tags as session tags (so an aws:RequestTag-gated trust policy denies every identity), and ServerSideTokenCheck=true keeps vending for a globally-signed-out user

> _Note: this issue was identified against the code base at commit `cae7c7114b6b8b21c16a9367bb3638c681e12be0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCredentialsForIdentity

## Description
TWO net-new root causes, grounded in the only two failing checks under the suite heading `cognito-identity` in this replay that the report marks neither ALREADY FILED nor OWNED. Every other cognito-identity failure in this run is OWNED by an open issue and is not re-filed here. A fixer must close BOTH causes before submitting.

=== Cause 1 of 2: the vend's role assumption carries no requested session tags, so a role trust policy conditioned on aws:RequestTag/<key> refuses EVERY identity, including the one whose mapped tag satisfies it ===
Failing check id: cognito-identity.server-side-sts-role-session-tags-enforced-in-trust-policy.
AWS: when an identity pool has a PrincipalTagAttributeMap (SetPrincipalTagAttributeMap, e.g. PrincipalTags={"Department": "custom:dept"} over a cognito-idp provider), GetCredentialsForIdentity assumes the pool's authenticated role via sts:AssumeRoleWithWebIdentity AND sts:TagSession, passing the tag values derived from the presented token's claims as the REQUESTED session tags. A trust policy whose Condition contains StringEquals {"aws:RequestTag/Department": "eng"} is therefore satisfied for an identity whose mapped claim value is `eng`, and that call returns HTTP 200 with Credentials (AccessKeyId/SecretKey/SessionToken/Expiration). Only the identity whose mapped value is something else (here `finance`) fails the trust condition; STS refuses the assumption and Cognito Identity surfaces that as HTTP 400 `InvalidIdentityPoolConfigurationException` with the fixed sentence "Invalid identity pool configuration. Check assigned IAM roles for this pool." — entirely fixed text, with no request- or state-derived parts. Smithy (services/service-com-amazonaws-cognitoidentity-awscognitoidentityservice): GetCredentialsForIdentity errors include InvalidIdentityPoolConfigurationException @httpError 400, documented as "the identity pool has no authenticated role configured, or STS returned an error response to the request to assume the authenticated role from the identity pool" — i.e. this code is exactly how a trust-policy denial at assumption time is reported, and it must therefore be returned for the DENIED identity only. The tag-gating semantics themselves are recorded behavior.
Emulator: the refusal is returned for both identities. The matching-tag identity (mapped Department=eng, the check's positive control) is refused on every attempt for the whole 90 s retry window: `An error occurred (InvalidIdentityPoolConfigurationException) when calling the GetCredentialsForIdentity operation: Invalid identity pool configuration. Check assigned IAM roles for this pool.` The code and message are the right ones for a denial, but they are produced for a request that AWS allows, so the pool can never vend at all once its role trust policy mentions aws:RequestTag. Hypothesis: the emulator's assumption is made without any requested session tags (and without sts:TagSession), so aws:RequestTag/<key> is unpopulated and every StringEquals on it evaluates false.
Why: attribute-based access control at the TRUST-POLICY boundary is inoperative, and it fails closed in a way a client cannot distinguish from a genuinely misconfigured pool — the same code and message AWS uses for "your roles are wrong" is returned for a correct configuration. An application that gates role assumption on a mapped attribute (the documented Cognito "attributes for access control" pattern) gets zero working identities, and a caller retrying on InvalidIdentityPoolConfigurationException never terminates.
Fix: the role-assumption step of the GetCredentialsForIdentity handler in the cognito-identity service — derive the session tags from the pool's PrincipalTagAttributeMap and the presented token's claims, attach them to the AssumeRoleWithWebIdentity request as requested tags (with sts:TagSession), and let the trust-policy evaluator populate aws:RequestTag/<key> from them, so the InvalidIdentityPoolConfigurationException above is returned only when the condition genuinely fails.
Related open issue, named so it is not fixed twice: 20261106T123006Z-cognito-identity-5-net-new-root-causes-cfn.md, Cause 4, reports that principal tags never become session tags on the vended session (aws:PrincipalTag conditions in the role's PERMISSION policy never match). It does not carry this check id, and the symptom here is upstream of it and differently visible: the vend itself is refused, so the session is never minted.

=== Cause 2 of 2: ServerSideTokenCheck=true does not consult global sign-out, so a globally-signed-out user's outstanding ID token keeps vending credentials ===
Failing check id: cognito-identity.server-side-token-check-refuses-a-globally-signed-out-user.
AWS: an identity pool whose CognitoIdentityProviders[] entry carries ServerSideTokenCheck=true revalidates the presented user-pool ID token against the user pool on each GetId/GetCredentialsForIdentity. After cognito-idp AdminUserGlobalSignOut on the token's user, that same unchanged token (same bytes, same signature, unexpired `exp`) is refused with HTTP 403 `NotAuthorizedException`, message "Token is inactive" — fixed text, no variable parts. The refusal is a refusal to VEND only: DescribeIdentity still resolves the identity and still lists the provider among its Logins. A twin identity pool differing ONLY in ServerSideTokenCheck=false keeps vending for the very same token, and a freshly minted token vends again on the checked pool. Smithy: GetCredentialsForIdentity errors include NotAuthorizedException @httpError 403; the revalidation semantics and the message text are recorded behavior only.
Emulator: no refusal ever arrives. After AdminUserGlobalSignOut, GetCredentialsForIdentity on the ServerSideTokenCheck=true pool with the unchanged token keeps answering 200 with Credentials for the whole 120 s propagation budget the check allows (the last success returned an AccessKeyId; its value is per-run and not part of the requirement). The flag is stored and echoed — DescribeIdentityPool reports ServerSideTokenCheck=true, which the check asserts before the sign-out — but it is never consulted at vend time, so the checked pool behaves identically to its ServerSideTokenCheck=false twin.
Why: a client cannot revoke access by signing a user out. Any ID token minted before the global sign-out keeps exchanging for authenticated-role credentials until it expires, so offboarding and incident-response flows validate as working against the emulator and fail in production. Because the divergence is an unexpected SUCCESS rather than a wrong error, callers that poll for the revocation never terminate.
Fix: the login/token validation path shared by GetId and GetCredentialsForIdentity in the cognito-identity service — when the matched CognitoIdentityProviders entry has ServerSideTokenCheck=true, resolve the token's user/session in the named user pool and refuse a token invalidated by a global sign-out with the modeled 403 NotAuthorizedException above, leaving the identity and its linked login untouched.
Related open issues, named so they are not fixed twice: 20261026T054328Z-cognito-identity-cognito-idp-serversidetokencheck-is-not-enforced.md and 20261029T122617Z-cognito-identity-cognito-idp-serversidetokencheck-true-pool-keeps.md both describe ServerSideTokenCheck not being enforced for an AdminDisableUser'd user under the suite heading cognito-identity__cognito-idp. Neither carries this check id, and the revocation trigger here is AdminUserGlobalSignOut (session invalidation, user still enabled), so closing either of those can leave this check failing; a fixer that makes SSTC consult user-pool state should cover all three together.

Traces: the two failing check ids above, both under the suite heading `cognito-identity`. Login matching and the vend's role assumption live in services/service-com-amazonaws-cognitoidentity-awscognitoidentityservice/src/ops/get_credentials_for_identity.rs.
