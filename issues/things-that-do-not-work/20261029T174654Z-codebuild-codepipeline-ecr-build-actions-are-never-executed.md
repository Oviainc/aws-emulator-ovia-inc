# CodeBuild/CodePipeline/ECR: Build actions are never executed, ECR pushes never start a pipeline via EventBridge, and the CI CloudFormation stacks never settle (3 causes)

> _Note: this issue was identified against the code base at commit `b4c1cbd51f8bf527a5a2f5b1db6a86929ff8c5f7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartPipelineExecution

## Description
THREE net-new root causes in the CodeBuild/CodePipeline/ECR chain. Open issues 20261022T172625Z-codebuild-codepipeline-ecr-ci-chain-pipeline-executions-never.md, 20261024T014332Z-codebuild-codepipeline-ecr-codepipeline-build-stages-fail-and-record-no-action.md and 20261028T112857Z-codebuild-codepipeline-ecr-codebuild-in-codepipeline-3-net-new-root-causes.md describe neighbouring symptoms but none of them carries the twelve replay keys listed here; the checks below are reported by the suite as unowned.

Cause 1 of 3 — CodePipeline refuses to run a CodeBuild Build action at all, and says so in the wire response.
AWS: codepipeline executes a Build action of provider CodeBuild by calling codebuild StartBuild; the action execution then carries externalExecutionId (the build id) and the stage succeeds when the build succeeds. When the pipeline's service role lacks codebuild:StartBuild, AWS still attempts the invocation and fails the action with errorDetails.code "JobFailed" (measured in the check's own recording), never with a configuration error. Smithy (codepipeline) models ActionExecutionResult with externalExecutionId/externalExecutionSummary/errorDetails{code,message}.
Emulator: every Build action resolves to errorDetails {code: "ConfigurationError", message: "this emulator does not run Build actions provided by CodeBuild, so the action cannot be performed"} with the same text echoed in externalExecutionSummary; no build is started, no externalExecutionId is recorded, and the execution ends "Failed". The message is emulator self-description, not an AWS error message, and the code is wrong for the permission-denied case (AWS: JobFailed).
Why: no pipeline with a Build stage can ever succeed, source artifacts are never delivered to a build, build logs never exist, and every negative test of a CodeBuild-related permission passes for the wrong reason — the denial is indistinguishable from "the feature is absent".
Fix: the CodePipeline Build-action executor (its CodeBuild provider integration) plus the action-execution result it records; the permission-denied path must report AWS's errorDetails.code JobFailed with AWS's message rather than a ConfigurationError naming the emulator.
Traces: codebuild__codepipeline__ecr.pipeline-invokes-codebuild-project-on-build-stage, codebuild__codepipeline__ecr.pipeline-passes-source-artifact-location-to-codebuild, codebuild__codepipeline__ecr.cli-start-pipeline-execution-and-verify-codebuild-log-output, codebuild__codepipeline__ecr.cli-pipeline-execution-fails-when-codebuild-role-lacks-ecr-permissions, codebuild__codepipeline__ecr.pipeline-role-missing-codebuild-startbuild-permission-blocks-invocation-rejected.

Cause 2 of 3 — an ECR image push never starts a pipeline execution through an EventBridge rule.
AWS: recorded behavior — pushing an image to an ECR repository emits an "ECR Image Action" event (source aws.ecr, detail.action-type PUSH, detail.image-tag, detail.repository-name); an EventBridge rule targeting a pipeline ARN with a role holding codepipeline:StartPipelineExecution starts a NEW pipeline execution whose Source action's source revision is the digest of that very push. A rule whose pattern filters on a different image-tag, a push to a repository no rule references, or a target role without the permission start nothing.
Emulator: no new execution is ever observed after a push; the checks poll for the new executionId and are killed at the 60 s replay cap. Hypothesis: ECR emits no image-action event at all (open issue 20261025T020208Z-cloudwatch-ecr-ecs-ecr-emits-no-image-action-events-to-eventbridge.md reports the same absence for a delete event), so the EventBridge rule never fires and the positive controls inside the negative checks never converge either.
Why: the whole push-to-deploy trigger is dead, and — worse for a test consumer — the negative cases ("tag filter excludes this push", "untracked repository", "target role lacks permission") appear to hold vacuously, so an emulator user cannot tell a working filter from an absent event bus.
Fix: ECR's push path must publish the ECR Image Action event to EventBridge, and the EventBridge rule-target path must invoke codepipeline StartPipelineExecution under the target role.
Traces: codebuild__codepipeline__ecr.ecr-image-push-triggers-codepipeline-eventbridge-execution, codebuild__codepipeline__ecr.ecr-image-tag-filter-in-eventbridge-rule-controls-pipeline-trigger, codebuild__codepipeline__ecr.ecr-push-to-untracked-repository-does-not-trigger-pipeline, codebuild__codepipeline__ecr.missing-eventbridge-target-permission-blocks-pipeline-invocation, codebuild__codepipeline__ecr.codepipeline-execution-includes-ecr-image-digest-as-source-revision.

Cause 3 of 3 — the CloudFormation stack that declares the CI roles/pipeline never reaches a state the caller can observe.
AWS: recorded behavior — a stack declaring AWS::S3::Bucket + AWS::IAM::Role (trust policy for codebuild.amazonaws.com / codepipeline.amazonaws.com) + the CodeBuild project and pipeline reaches CREATE_COMPLETE, after which GetRole returns the declared AssumeRolePolicyDocument and the pipeline is usable.
Emulator: both stack-deploying checks run to the 60 s replay cap with no result. Hypothesis: the stack never settles (or settles without the declared resources, so the subsequent wait never ends) — consistent with the already-open 20261023T080113Z-codebuild-codepipeline-ecr-cloudformation-stack-reports-completion-but-provisions-no-codepipeline.md, which reports a completed stack provisioning no pipeline; neither of these two replay keys is carried by that issue.
Why: a client cannot provision this CI topology by template at all, so the IAM trust the stack declares can never be exercised.
Fix: the CloudFormation provisioners for the CodeBuild project / CodePipeline pipeline / IAM role in this template shape, and the stack's terminal-status reporting.
Traces: codebuild__codepipeline__ecr.deploy-stack-codebuild-role-trust-policy-allows-codebuild-service, codebuild__codepipeline__ecr.deploy-stack-pipeline-role-trust-policy-allows-codepipeline-service.

Repeat with a pipeline role holding no codebuild:* permissions: AWS reports errorDetails.code JobFailed.

Push an image to <repo> and poll ListPipelineExecutions for a new executionId — none appears.
Cause 3: CreateStack with a template declaring an artifact bucket, a CodeBuild role trusting codebuild.amazonaws.com, a pipeline role trusting codepipeline.amazonaws.com, a CodeBuild project and a pipeline; wait for a terminal stack status and then GetRole on the declared roles.
