# rds: 3 net-new causes — an aurora-postgresql cluster publishes Port as an ephemeral listener port, a REPEATABLE READ transaction gets no stable snapshot, and a lock-waiting statement is cancelled with a non-PostgreSQL QueryCanceled message instead of SERIALIZABLE 40001

## Operation
DescribeDBClusters

## Description
This issue bundles 3 net-new root causes in the rds service, each grounded in a failing behavioural check the suite report marked neither ALREADY FILED nor OWNED. A fixer must close all THREE causes below before submitting.

Cause 1 is the same defect class as open issue 20261108T051751Z-rds-7-net-new-causes-endpoint-port-is.md (its Cause 1) and 20261106T031005Z-rds-7-net-new-causes-endpoint-port-publishes.md (its Cause 1), but neither issue's Issue-Trace-Ids/replay keys include the check below, and both of those describe the INSTANCE-level Endpoint.Port; what is grounded here is the CLUSTER-level DBCluster.Port read from DescribeDBClusters.

=== Cause 1 of 3: DBCluster.Port on an aurora-postgresql cluster reports the emulator's internal listener port instead of the engine port ===
AWS: Smithy: DBCluster$Port — "The port that the database engine is listening on"; CreateDBClusterMessage$Port — "Valid Values: 1150-65535. Default: RDS for MySQL and Aurora MySQL - 3306; RDS for PostgreSQL and Aurora PostgreSQL - 5432". So DescribeDBClusters on an aurora-postgresql cluster created with Port omitted must report 5432, and when Port IS supplied it must echo the supplied value. The value is a property of the engine/request, never of the host the service runs on.
Emulator: DescribeDBClusters reports a port drawn from the host's dynamic/ephemeral range — observed 36315 for an aurora-postgresql cluster created with Port omitted. The concrete number differs per run and is not itself the requirement; the requirement is that the modelled engine default (5432 for Aurora PostgreSQL, 3306 for Aurora MySQL) or the requested Port is what is published, and that the emulator's own socket placement does not leak into the response.
Why: a client reads DBCluster.Port to build a connection string, a security-group ingress rule, a DB proxy target or a CloudFormation output. "Aurora PostgreSQL listens on 5432" is true of every real cluster and false here, so every such artefact is wrong, and any assertion or config pinned to the documented default fails against the emulator while passing against AWS.
Fix: the cluster endpoint projection in the DescribeDBClusters/CreateDBClusters serializers in the rds crate, and the cluster state that records Port — decouple the published Port from the local socket the engine data plane happens to bind, defaulting per engine family and echoing a supplied Port.
Traces: rds.deep-rds-1-rds-engine-truth-aurora-postgres-constraint-and-lock-violations-rejected.

=== Cause 2 of 3: a REPEATABLE READ transaction does not see a stable snapshot — it observes another session's later commit mid-transaction ===
AWS: recorded behavior only for the emulated engine; the contract is PostgreSQL's, which RDS for PostgreSQL / Aurora PostgreSQL serve unmodified. Under REPEATABLE READ a transaction takes its snapshot at the first non-transaction-control statement and every subsequent read in that SAME still-open transaction returns that snapshot: a row read as 'first' re-reads as 'first' even after a concurrent session COMMITs 'second'; the new value only becomes visible after the reading transaction ends. The recording shows exactly that: session A re-reads its row and still gets the pre-commit value.
Emulator: session A, inside its own still-open REPEATABLE READ transaction, re-reads the row and gets the OTHER session's post-commit value — the check reports "the REPEATABLE READ snapshot was not stable: session A re-read the row inside its own still-open transaction and got [('second',)] after another session committed 'second'". Reads are being served from current committed state rather than from the transaction's snapshot, i.e. the session behaves as READ COMMITTED regardless of the level it reports via SHOW transaction_isolation.
Why: a client that relies on repeatable reads — paging a result set, computing a consistent aggregate, or reading-then-writing based on an earlier read inside one transaction — silently reads torn, mutually inconsistent data. Worse, the engine still REPORTS 'repeatable read', so the application cannot detect that the isolation it asked for is not being provided; code validated against the emulator will behave differently on real RDS and vice versa.
Fix: the MVCC/snapshot layer of the emulated PostgreSQL engine's data plane in the rds crate — take and pin a snapshot per transaction when the level is REPEATABLE READ (and SERIALIZABLE) and serve all reads in that transaction from it, rather than from latest-committed state.
Traces: rds.repeatable-read-transaction-sees-a-stable-snapshot.

=== Cause 3 of 3: a statement that waits on a row lock is cancelled with an emulator-invented QueryCanceled error, so SERIALIZABLE never produces the 40001 serialization failure ===
AWS: recorded behavior only for the emulated engine; the contract is PostgreSQL's as served by RDS. A writing statement that meets a row version another uncommitted transaction holds BLOCKS until that transaction ends (statement_timeout defaults to 0 on RDS, so it is not cancelled on a timer); it then either proceeds or, at REPEATABLE READ/SERIALIZABLE, is refused with SQLSTATE 40001 (serialization_failure) in an ErrorResponse at severity ERROR. Where PostgreSQL does cancel on a timer, the message is its own fixed text — "canceling statement due to statement timeout" — at SQLSTATE 57014, with the timeout value coming from the session's statement_timeout setting; no PostgreSQL error mentions what "this endpoint serves".
Emulator: the statement is aborted with psycopg.errors.QueryCanceled and the message "canceling statement: it ran longer than this endpoint serves". Both parts diverge: the message is fixed text no PostgreSQL build emits (it describes an emulator-internal serving limit rather than a session setting or a conflict verdict), and because the statement dies this way the two-session write-skew interleaving never reaches a commit, so the SERIALIZABLE arm can never produce the required single 40001 refusal (with diag.sqlstate '40001' and diag.severity 'ERROR') and the REPEATABLE READ arm can never show both commits succeeding.
Why: a client cannot distinguish a lock wait, a serialization conflict and a cancelled query. PostgreSQL clients and ORMs retry 40001 automatically and treat 57014 as a tuning problem; an invented message at an unexpected SQLSTATE matches neither retry path, so a transaction that real RDS would retry successfully fails permanently, and SERIALIZABLE provides none of the guarantee it advertises.
Fix: the lock-wait and transaction-conflict handling of the emulated PostgreSQL engine's data plane in the rds crate — block a statement on a conflicting row lock until the holder commits or rolls back instead of cancelling it on an internal serving deadline, and emit a serialization conflict as SQLSTATE 40001 at severity ERROR (reserving 57014 with PostgreSQL's own "canceling statement due to statement timeout" text for an actual statement_timeout).
Traces: rds.serializable-write-skew-rejected-repeatable-read-permits.

## Evidence
Cause 1: AssertionError: aurora-postgresql must listen on 5432; cluster says 36315 — DescribeDBClusters on an aurora-postgresql cluster created with Port omitted. Expected DBCluster.Port == 5432 (Smithy-documented Aurora PostgreSQL default); got a host-ephemeral port (the specific number varies per run).

Cause 2: AssertionError: the REPEATABLE READ snapshot was not stable: session A re-read the row inside its own still-open transaction and got [('second',)] after another session committed 'second'. Expected the re-read inside the open REPEATABLE READ transaction to still return [('first',)].

Cause 3: psycopg.errors.QueryCanceled: canceling statement: it ran longer than this endpoint serves — raised while executing a statement of the two-session write-skew interleaving, before either arm could commit. Expected: the statement blocks on the conflicting row lock and then, under SERIALIZABLE, exactly one commit is refused with sqlstate '40001', diag.sqlstate '40001', diag.severity 'ERROR'; under REPEATABLE READ both commits succeed. The emulator's message text ("canceling statement: it ran longer than this endpoint serves") is not any PostgreSQL message; PostgreSQL's timeout text is the fixed "canceling statement due to statement timeout" at SQLSTATE 57014.

## Steps to Reproduce
Cause 1: CreateDBCluster(Engine='aurora-postgresql', DBSubnetGroupName=<private subnets>, VpcSecurityGroupIds=[<sg>]) with Port OMITTED, add a writer via CreateDBInstance, poll DescribeDBClusters until Status=='available', then read DBCluster['Port'] — it must be 5432. Repeat with Engine='aurora-mysql' (must be 3306) and with an explicit Port=5433 (must echo 5433).

Cause 2: CreateDBInstance(Engine='postgres'), wait available, connect natively to the published endpoint. CREATE TABLE t(id INT PRIMARY KEY, v TEXT); INSERT (1,'first'). Open session A with isolation_level REPEATABLE READ, SELECT v FROM t WHERE id=1 (returns 'first') and leave the transaction OPEN. From session B, UPDATE t SET v='second' WHERE id=1 and COMMIT. Back in session A's still-open transaction, SELECT v FROM t WHERE id=1 again — it must still return 'first'; only after A commits/rolls back may it read 'second'.

Cause 3: CreateDBInstance(Engine='postgres'), wait available, connect natively. Confirm SELECT current_setting('default_transaction_isolation') is 'read committed'. Seed t(id,colour) with (1,'black'),(2,'white'). Open two sessions at isolation_level 'REPEATABLE READ': A does SELECT count(*) FROM t WHERE colour='black', B does SELECT count(*) FROM t WHERE colour='white', then A does UPDATE t SET colour='white' WHERE colour='black' and B does UPDATE t SET colour='black' WHERE colour='white'; commit both — neither statement may be cancelled and both commits must succeed, leaving the rows swapped. Re-seed and repeat the byte-identical sequence at isolation_level 'SERIALIZABLE' — exactly one commit must be refused with SQLSTATE 40001 (diag.sqlstate '40001', diag.severity 'ERROR'), only the survivor's write visible to an independent session, and re-running the refused transaction with no concurrent conflict must then succeed.
