# Workload access-token minting is unserved: GetWorkloadAccessTokenForJWT and GetWorkloadAccessToken answer 501 NotImplemented, so the UnauthorizedException and AccessDeniedException refusal classes are unreachable (2 causes)

> _Note: this issue was identified against the code base at commit `80128cf5220e52d7fa07858b1a17d4e0aeba15d4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetWorkloadAccessTokenForJWT

## Description
Two net-new causes in the bedrock-agentcore (data-plane) workload-identity token surface. Both token-minting operations are still scaffold stubs that answer HTTP 501 with error code `NotImplemented`, so neither the success path nor any modeled refusal class is reachable. Note: these two failing checks are NOT covered by the auto-filed stub issues or by the open issue 20261029T215145Z-bedrock-agentcore-agentcore-data-plane-invocation-unserved-invokecodeinterpreter-and-invokeharness.md (that issue's Issue-Trace-Ids and Issue-Keys name InvokeCodeInterpreter, InvokeHarness, GetMemoryRecord, StopRuntimeSession, InvokeAgentRuntime and StartBatchEvaluation only — neither GetWorkloadAccessToken nor GetWorkloadAccessTokenForJWT appears in it), and no open issue names either operation. The suite did not mark these two checks ALREADY FILED/OWNED because each check captures the stub's ClientError through its own error helper and reports it as a code mismatch rather than letting the exception escape.

Cause 1 of 2: GetWorkloadAccessTokenForJWT does not validate the supplied userToken — it answers NotImplemented instead of rejecting an invalid/expired JWT with UnauthorizedException.
AWS: Smithy: GetWorkloadAccessTokenForJWT, POST /identities/GetWorkloadAccessTokenForJWT, success @http code 200; required input `workloadName` (WorkloadIdentityNameType, @length 3..255, @pattern ^[A-Za-z0-9_.-]+$) and `userToken` (UserTokenType, @length 1..131072, @pattern ^[A-Za-z0-9-_=]+.[A-Za-z0-9-_=]+.[A-Za-z0-9-_=]+$, @sensitive); required output `workloadAccessToken` (@length 1..131072, @sensitive). Modeled errors: AccessDeniedException(403), InternalServerException(500), ResourceNotFoundException(404), ThrottlingException(429), UnauthorizedException(401), ValidationException(400). The model documents UnauthorizedException as "This exception is thrown when the JWT bearer token is invalid or not found for OAuth bearer token based access" — i.e. a token that is structurally a three-segment JWT (so it passes the @pattern and never reaches ValidationException) but whose signature/issuer/expiry do not validate must be refused with UnauthorizedException(401), and no token may be minted. Recorded behavior for the expired-token case: error code `UnauthorizedException`, message `Token has expired` (that message is entirely fixed text for this error class — it carries no request- or state-derived values).
Emulator: the call returns the scaffold's 501 with error code `NotImplemented` and message `operation GetWorkloadAccessTokenForJWT is scaffolded but not implemented in this emulator` (services/.../src/ops/get_workload_access_token_for_jwt.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker and its handle() body is `Err(crate::scaffolded::Scaffolded::not_implemented(...))`). Replay observed: `AssertionError: expected UnauthorizedException, got NotImplemented`.
Why: a client doing on-behalf-of-user token exchange cannot obtain a workload access token at all, and — worse for correctness testing — an invalid or expired user JWT produces an unmodeled error code with HTTP 501. SDK/retry classification sees neither a 401 auth failure nor a 400 validation failure, so code that refreshes the user's IdP token on UnauthorizedException never triggers, and an application that tests its JWT-rejection path against the emulator silently passes with the wrong outcome.
Fix: implement the operation's handler and its token validation in services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/get_workload_access_token_for_jwt.rs — resolve `workloadName` against workload-identity state, validate the userToken's signature/issuer/expiry, return UnauthorizedException(401) with the fixed message `Token has expired` for an expired token (and the invalid-token wording for the other invalid cases), and otherwise mint the required `workloadAccessToken`; then delete the SCAFFOLDED marker.
Traces: bedrock-agentcore.workload-access-token-for-jwt-invalid-rejected.

Cause 2 of 2: GetWorkloadAccessToken makes no authorization decision — it answers NotImplemented both for an out-of-scope request (which AWS denies) and for the principal's own permitted identity (which AWS serves).
AWS: Smithy: GetWorkloadAccessToken, POST /identities/GetWorkloadAccessToken, success @http code 200; required input `workloadName` (@length 3..255, @pattern ^[A-Za-z0-9_.-]+$); required output `workloadAccessToken` (@length 1..131072, @sensitive). Modeled errors include AccessDeniedException @httpError 403, documented as "The exception that occurs when you do not have sufficient permissions to perform an action." A principal whose identity-based policy grants bedrock-agentcore:GetWorkloadAccessToken only on its own workload-identity ARN (plus the workload-identity-directory ARN) must be refused with AccessDeniedException(403) when it asks for a token scoped to a different, existing workload identity — the denial is an authorization decision taken before/independently of resource existence. AWS's message is the standard IAM identity-based denial template: the fixed text `User: ` + ` is not authorized to perform: ` + ` on resource: ` + ` because no identity-based policy allows the ` + ` action`, with the variable parts taken from the caller's signing credentials (the assumed-role principal ARN), the operation (`bedrock-agentcore:GetWorkloadAccessToken`) and the requested resource (the arn:aws:bedrock-agentcore:<region>:<account>:workload-identity-directory/<directory>/workload-identity/<workloadName> ARN derived from the request). The same principal asking for its OWN permitted identity must succeed with a non-empty workloadAccessToken.
Emulator: both calls return the scaffold's 501 `NotImplemented` (`operation GetWorkloadAccessToken is scaffolded but not implemented in this emulator`); services/.../src/ops/get_workload_access_token.rs is still a stub (SCAFFOLDED marker present, handle() returns Scaffolded::not_implemented). Replay observed: `AssertionError: expected AccessDeniedException, got NotImplemented`.
Why: the whole non-user workload token path is unavailable, and because the reply is an unmodeled code at HTTP 501 a client cannot distinguish "not permitted" (403) from "identity does not exist" (404) from a transient server fault; any least-privilege or cross-scope authorization test run against the emulator reports the wrong result, and the per-identity scoping guarantee (grant enforced per workload identity, not blanket-denied) is not observable.
Fix: implement the handler/authorization of GetWorkloadAccessToken in services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/get_workload_access_token.rs, together with the shared sigv4 principal/authorization layer, so that an identity-based-policy check runs against both the workload-identity-directory and the specific workload-identity resource before lookup, emitting AccessDeniedException(403) with the IAM template message, and otherwise minting the required token for an existing identity; delete the SCAFFOLDED marker.
Traces: bedrock-agentcore.workload-access-token-scope-overreach-denied.
