# cloudwatch__rds: an AWS/RDS DatabaseConnections alarm never evaluates, so its AlarmActions never execute, no Action history is recorded, and the SNS topic-policy Deny is never the thing that blocks delivery (1 cause)

> _Note: this issue was identified against the code base at commit `a2837dbdebef5b9a30be37f112a3c5b63a2de779`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAlarmHistory

## Description
Cause 1 of 1 — CloudWatch metric alarms on the AWS/RDS namespace never evaluate, never transition state, never execute AlarmActions, and never record an Action history item; consequently the SNS resource-policy authorization decision that gates an alarm's publish is never made at all. Failing check: cloudwatch__rds.rds-alarm-action-blocked-by-topic-policy-denying-cloudwatch.

NOTE ON EXISTING ISSUES: the open issue 20261024T030130Z-cloudwatch-rds-cloudwatch-metric-alarms-never-evaluate-or-fire-their.md ('CloudWatch metric alarms never evaluate or fire their actions...') describes the same area and names this same check, but the replay report did NOT mark this failing check as OWNED by it or as ALREADY FILED, so it is filed here as a surviving failure and that issue is named rather than assumed to cover it. The open issues 20261025T020208Z-cloudwatch-alarms-never-evaluate-published-metric-data-no.md, 20261025T053543Z-cloudwatch-alarm-evaluation-and-metric-read-fidelity-statereason.md and 20261025T174025Z-cloudwatch-sns-sqs-breaching-datapoints-move-neither-the.md cover neighbouring alarm-evaluation symptoms on other namespaces/paths; none of them was reported as owning this check either.

AWS: a MetricAlarm created by PutMetricAlarm with Namespace=AWS/RDS, MetricName=DatabaseConnections, Dimensions=[{DBInstanceIdentifier: <identifier that names no instance>}], EvaluationPeriods=1, Period=60, Threshold>=1, ComparisonOperator=GreaterThanOrEqualToThreshold and TreatMissingData='breaching' is evaluated by CloudWatch on CloudWatch's own clock, with no SetAlarmState call. Smithy: PutMetricAlarmInput.TreatMissingData documents 'Sets how this alarm is to handle missing data points ... Valid Values: breaching | notBreaching | ignore | missing', and only the AWS/DynamoDB namespace is excepted from it — AWS/RDS is not, so a metric with no datapoints makes the alarm breach and move to StateValue=ALARM (Smithy: StateValue enum = OK | ALARM | INSUFFICIENT_DATA). On that transition CloudWatch executes every entry of AlarmActions and records one history item per action, readable through DescribeAlarmHistory with HistoryItemType='Action' (Smithy: HistoryItemType enum includes 'Action'; AlarmHistoryItem.HistoryData is 'Data about the alarm, in JSON format', max length 4095). Recorded behavior only for the HistoryData field names the check reads: notificationResource (the action's target ARN), actionState ('Succeeded'/'Failed'), error, publishedMessage. For an SNS topic whose resource policy carries an explicit Deny of sns:Publish for Principal {"Service": "cloudwatch.amazonaws.com"}, the Action item is actionState='Failed' with an error naming the SNS:Publish authorization refusal (fixed text 'not authorized to perform: SNS:Publish'; the variable parts are the denied topic ARN and the principal, taken from the request/state) and NO publishedMessage, and nothing is delivered to that topic's subscribers; for the sibling topic with the default policy the item is actionState='Succeeded' and the notification (Message body with AlarmName, NewStateValue='ALARM', Trigger.Namespace='AWS/RDS') is delivered to the subscribed SQS queue.

Emulator: nothing happens on either leg. The alarm is accepted by PutMetricAlarm but is never evaluated: it never leaves INSUFFICIENT_DATA, no AlarmActions entry is ever executed, DescribeAlarmHistory returns no HistoryItemType='Action' item for either topic, and the subscribed queue receives no notification. The check's barrier poll for 'Action history items for both topics' (its own budget is 600 s, with a 300 s delivery budget) therefore never satisfies its predicate and the replay ends as verdict 'mismatch' with 'Check timed out after 60.0s'. Because no action ever fires, the denied topic's correct-looking absence of delivery is produced by the alarm never firing, not by the Deny — the resource policy is never consulted, so the emulator also has no authorization step that would refuse a publish to a topic AWS refuses.

Why: every alarm-driven RDS workflow is inert. A client that creates an alarm on an AWS/RDS metric and waits for the state change, for the SNS notification, or for the Action history that tells it whether the notification was delivered, waits forever and cannot distinguish 'not delivered because denied' from 'not delivered because nothing ran'. A monitoring or incident-response integration built against this emulator would also see no refusal when it targets a topic whose policy denies cloudwatch.amazonaws.com, so a misconfiguration AWS surfaces as a Failed action with an authorization error is silently invisible here.

Fix: the CloudWatch alarm evaluation path and its action executor — alarms must be evaluated against their metric data on a timer honouring TreatMissingData (including 'breaching' for a series with no datapoints in the AWS/RDS namespace), must transition StateValue and record the StateUpdate, must execute each AlarmActions entry through the target service while evaluating that target's resource policy, and must record one Action history item per action with notificationResource, the Succeeded/Failed actionState, the authorization error text on a refusal and no publishedMessage in that case. The SNS publish-authorization decision for a service principal belongs in the SNS topic-policy evaluation the alarm action calls into.

Traces: cloudwatch__rds.rds-alarm-action-blocked-by-topic-policy-denying-cloudwatch.

## Evidence
Failing check cloudwatch__rds.rds-alarm-action-blocked-by-topic-policy-denying-cloudwatch — verdict 'mismatch', detail 'Check timed out after 60.0s'.

Expected (real AWS): after PutMetricAlarm with TreatMissingData='breaching' and AlarmActions=[allowed topic, denied topic], DescribeAlarmHistory(AlarmName=<alarm>, HistoryItemType='Action', AlarmTypes=['MetricAlarm']) yields one item per topic ARN. The allowed topic's parsed HistoryData has actionState='Succeeded' and its notification arrives in the SQS queue subscribed to the topic, with the SNS envelope's Message decoding to a body whose AlarmName is the alarm, NewStateValue='ALARM' and Trigger.Namespace='AWS/RDS'. The denied topic's item has actionState='Failed', an error containing 'not authorized to perform: SNS:Publish' and the denied topic ARN, and publishedMessage absent; repeated ReceiveMessage drains show nothing from the denied topic.

Actual (emulator): no Action history item ever appears for either topic ARN and no notification ever reaches the queue; the alarm stays in INSUFFICIENT_DATA. The check's _poll_until barrier (description 'Action history items for both topics on alarm <name>', interval 15 s, budget 600 s) never becomes true and the replay is cut off by the harness cap at 60 s. Every assertion past that barrier (acts[allowed].actionState == 'Succeeded', acts[denied].actionState == 'Failed', the error naming SNS:Publish, publishedMessage is None, the empty denied-topic drain, and the post-repair delivery after the Deny statement is removed) is therefore unreachable. The run-specific values in the recording — the generated topic/queue/alarm names, the ghost DBInstanceIdentifier, ARNs and account id — are fillers for the template, not part of the requirement.

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. rds: DescribeDBInstances(DBInstanceIdentifier=<unused identifier>) and confirm it answers DBInstanceNotFound, so the alarm's dimension names no instance.
3. sns: CreateTopic twice ('allowed' and 'denied'). GetTopicAttributes on the denied topic, append to its Policy a statement {Sid: DenyCloudWatchPublish, Effect: Deny, Principal: {Service: cloudwatch.amazonaws.com}, Action: sns:Publish, Resource: <denied topic ARN>} and SetTopicAttributes(AttributeName='Policy'); confirm GetTopicAttributes reads the Deny back.
4. sqs: CreateQueue, read its QueueArn, SetQueueAttributes with a Policy allowing sns.amazonaws.com sqs:SendMessage from both topic ARNs, and sns:Subscribe the queue to BOTH topics (Protocol='sqs', ReturnSubscriptionArn=True).
5. cloudwatch: PutMetricAlarm(Namespace='AWS/RDS', MetricName='DatabaseConnections', Dimensions=[{Name:'DBInstanceIdentifier', Value:<the unused identifier>}], Statistic='Maximum', Period=60, EvaluationPeriods=1, Threshold=1.0, ComparisonOperator='GreaterThanOrEqualToThreshold', TreatMissingData='breaching', AlarmActions=[allowed ARN, denied ARN]).
6. Poll DescribeAlarms for StateValue and DescribeAlarmHistory(HistoryItemType='Action', AlarmTypes=['MetricAlarm']) and ReceiveMessage on the queue. Observed: the alarm never leaves INSUFFICIENT_DATA, no Action history item is recorded for either topic, and no message is delivered — the poll runs until the harness cap.
7. Remove the Deny statement (SetTopicAttributes back to the default policy) and PutMetricAlarm a fresh alarm aimed only at the formerly denied topic: its action is likewise never executed, so the repair leg cannot be observed either.
