# CloudWatch Contributor Insights batch failures are misclassified: Disable/EnableInsightRules report an unknown rule as InvalidParameterValue instead of ResourceNotFoundException/RULE_NAME, and PutManagedInsightRules never validates ResourceARN (2 causes)

> _Note: this issue was identified against the code base at commit `5df675e0ea220f5d7ca93176f138364900f5089e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DisableInsightRules

## Description
Two net-new root causes in the cloudwatch service, grounded in 2 failing behavioral checks that the replay report marks NEITHER "ALREADY FILED" nor "OWNED by". BOTH must be closed before this issue is submitted; each cause names its own failing check id. Both live in the same place — the per-entry (PartialFailure) path of CloudWatch's Contributor-Insights batch operations — but they are independent defects in different handlers and either can be fixed without the other.

==================================================================
Cause 1 of 2: DisableInsightRules and EnableInsightRules report a well-formed rule name that names no rule as an InvalidParameterValue PartialFailure instead of AWS's ResourceNotFoundException / RULE_NAME entry, and the description drops AWS's terminal period.
Failing check id: cloudwatch.managed-insight-rules-server-side-enforcement

AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) models DisableInsightRules and EnableInsightRules with input RuleNames (@required, target InsightRuleNames of InsightRuleName @length 1..128 @pattern ^[\x20-\x7E]+$) and output Failures -> BatchFailures, a list of PartialFailure{FailureResource, ExceptionType, FailureCode, FailureDescription}. The PartialFailure shape documentation is the contract: "This array is empty if the API operation was successful for all the rules specified in the request. If the operation could not process one of the rules, the following data is returned for each of those rules." Modeled top-level errors are InvalidParameterValueException (client, httpError 400, awsQueryError InvalidParameterValue) and MissingRequiredParameterException (400, MissingParameter), plus LimitExceededException on EnableInsightRules — i.e. per-item problems are REPORTED in Failures, never raised. Recorded behavior pins the entry for an unprovisioned rule identity on an HTTP 200: exactly one PartialFailure whose FailureResource is the rule name taken verbatim from the request, ExceptionType is "ResourceNotFoundException", FailureCode is "RULE_NAME", and FailureDescription is "Rule <ruleName> does not exist." — fixed text "Rule " + " does not exist." (with the terminal period) around the request's own rule name. The ExceptionType/FailureCode pair is the fixed vocabulary; only FailureResource and the name inside the sentence come from the request.

Emulator: the call does answer HTTP 200 with exactly one entry, and FailureResource is right, but the classification and the text are wrong: ExceptionType is "InvalidParameterValueException", FailureCode is "InvalidParameterValue", and FailureDescription is "Rule <ruleName> does not exist" with no terminal period. Observed for this run's generated name: {'FailureResource': 'sim2real-behav-cwprobe-managed-rule-missing-dd34fff5ace2', 'ExceptionType': 'InvalidParameterValueException', 'FailureCode': 'InvalidParameterValue', 'FailureDescription': 'Rule sim2real-behav-cwprobe-managed-rule-missing-dd34fff5ace2 does not exist'} (the name is this run's value, not part of the requirement). EnableInsightRules on the same never-provisioned name is graded immediately after the Disable assertion by the same check and must carry the identical entry. Everything around this leg is already correct, which localises the defect: ListManagedInsightRules on a DynamoDB table ARN and on an alarm ARN both resolve to an empty ManagedRules list, a structurally malformed ResourceARN is refused InvalidParameterValue "INVALID_RESOURCE_ARN: Invalid ARN.", the two bogus-TemplateName PutManagedInsightRules legs return their TEMPLATE_NAME entries, and the positive control — Disable then Enable of a rule actually created by PutInsightRule — returns an empty Failures list.

Why: FailureCode and ExceptionType are exactly what a batch caller branches on. "ResourceNotFoundException"/"RULE_NAME" means "this rule does not exist — create it"; "InvalidParameterValueException"/"InvalidParameterValue" means "this name is not a legal rule name — the request is a client bug". Collapsing the first into the second makes a console or IaC reconciler treat a missing rule as an unfixable bad request: it stops creating the rule it was supposed to create, and it can no longer distinguish an absent rule from an illegal name in the same batch. The dropped terminal period independently breaks any caller or test that matches the description text.

Fix: the per-item loop of the DisableInsightRules and EnableInsightRules handlers in the cloudwatch crate (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/disable_insight_rules.rs and .../enable_insight_rules.rs), and the shared insight-rule batch-failure builder they emit through — an unknown-but-well-formed rule name must produce ExceptionType "ResourceNotFoundException", FailureCode "RULE_NAME" and the description "Rule <ruleName> does not exist." with the name interpolated from the request. Related open issue 20261027T005601Z-cloudwatch-6-net-new-root-causes-putmetricdata-s.md (cause 2) covers a DIFFERENT leg of the same operation — EnableInsightRules refusing the whole batch with an unmodeled ValidationException for a name that violates the InsightRuleName pattern — and expects ExceptionType "InvalidParameterException"/FailureCode "INVALID_RULE_NAME" for that case; it does not carry this check id and does not describe the not-found classification, but the two share this per-item failure machinery and should be fixed together.

Traces: cloudwatch.managed-insight-rules-server-side-enforcement (assertion at check line 156).

Cause 2 of 2: PutManagedInsightRules never validates ManagedRule.ResourceARN, so an entry whose ARN names no supported resource is reported as a template problem instead of AWS's InvalidParameterException "Invalid ResourceArn." entry.
Failing check id: cloudwatch.put-managed-insight-rules-invalid-resource-arn-rejected

AWS: Smithy models PutManagedInsightRules with input ManagedRules (@required list of ManagedRule{TemplateName @required @length 1..128 @pattern ^[0-9A-Za-z][\-\.\_0-9A-Za-z]{0,126}[0-9A-Za-z]$, ResourceARN @required target AmazonResourceName @length 1..1024, Tags}) and output Failures -> BatchFailures of PartialFailure; modeled top-level errors are InvalidParameterValueException (400, awsQueryError InvalidParameterValue) and MissingRequiredParameterException (400). Recorded behavior pins two per-entry shapes on an HTTP 200, differing ONLY in the ResourceARN sent: (a) control — an unresolvable TemplateName against a real, existing DynamoDB table ARN yields exactly one PartialFailure {FailureResource: the submitted TemplateName, ExceptionType: "ResourceNotFoundException", FailureCode: "TEMPLATE_NAME", FailureDescription: "Could not find template with the specified templateName."}; (b) the SAME TemplateName paired with a ResourceARN that is well-formed as an ARN but names no supported resource (shape arn:aws:cloudwatch:<region>:<account>:not-a-real-resource/does-not-exist) yields exactly one PartialFailure {FailureResource: the submitted TemplateName, ExceptionType: "InvalidParameterException", FailureCode: "TEMPLATE_NAME", FailureDescription: "Invalid ResourceArn."}. So the ARN problem takes PRECEDENCE over the template problem; FailureCode stays "TEMPLATE_NAME" and FailureResource is still the TemplateName (not the ARN); "Invalid ResourceArn." is wholly fixed text with nothing interpolated. In both cases nothing is enabled — ListManagedInsightRules for the real table reports no rule carrying a RuleState.

Emulator: the control leg now behaves (that half was closed by fixed issue 20261025T192750Z-cloudwatch-2-net-new-root-causes-putmanagedinsightrules-accepts.md), but the ARN leg returns the control's answer: for the bogus ResourceARN the emulator still replies HTTP 200 with {'FailureResource': '<TemplateName>', 'ExceptionType': 'ResourceNotFoundException', 'FailureCode': 'TEMPLATE_NAME', 'FailureDescription': 'Could not find template with the specified templateName.'}. Because both calls carry the same unresolvable TemplateName and differ only in the ARN, this shows ManagedRule.ResourceARN is never parsed or resolved at all: template resolution runs first and unconditionally, and no ARN-validation path exists to take precedence over it. The emulator's own effect-absence leg (nothing enabled) is correct and must be preserved.

Why: the per-entry failure is the only diagnosis a batch caller gets. A tool enabling managed Contributor Insights across an estate computes a resource ARN and submits it with a catalog template name; when its ARN is wrong AWS says "Invalid ResourceArn." and the caller fixes the ARN, whereas the emulator says the template does not exist, so the caller retries with other template names forever and never discovers the real fault. It also loses the InvalidParameterException-vs-ResourceNotFoundException distinction it would branch on to decide whether to re-resolve the resource or re-read the template catalog.

Fix: the per-entry loop of the PutManagedInsightRules handler in the cloudwatch crate (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/put_managed_insight_rules.rs) — parse and resolve each ManagedRule.ResourceARN BEFORE resolving its TemplateName, and for an ARN that names no supported resource emit {FailureResource: the entry's TemplateName, ExceptionType: "InvalidParameterException", FailureCode: "TEMPLATE_NAME", FailureDescription: "Invalid ResourceArn."} and process no further entries' templates for that entry. Open issue 20261025T151319Z-cloudwatch-4-net-new-root-causes-cfn-deployed.md (cause 2) names this operation and lists this check id, but its registered replay key is that issue's control-leg assertion (assert control_failures == [...]), which PASSES now — the ARN-precedence leg is a separate, still-diverging behavior and the replay report marks this check neither ALREADY FILED nor OWNED, so it is filed here to keep it gated.

Traces: cloudwatch.put-managed-insight-rules-invalid-resource-arn-rejected (assertion at check line 55).
