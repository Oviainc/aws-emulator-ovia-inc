# sqs: 4 net-new behavioral root causes — SendMessage refuses MessageSystemAttributes (AWSTraceHeader) outright, and three refusal messages are not AWS's text (CreateQueue FIFO cross-attribute, ReceiveRequestAttemptId, StartMessageMoveTask non-DLQ)

> _Note: this issue was identified against the code base at commit `a2be7a3586c8a34d922aa1b24d2f445b80a06855`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendMessage

## Description
Four net-new root causes in the sqs suite. None of the six failing checks below is marked ALREADY FILED or OWNED in the replay report. Smithy references are to services/service-com-amazonaws-sqs-amazonsqs/smithy-model/com-amazonaws-sqs-amazonsqs.json (com.amazonaws.sqs#AmazonSQS).

Cause 1 of 4: SendMessage refuses ANY MessageSystemAttributes value instead of accepting AWSTraceHeader.
AWS: Smithy models SendMessage input member MessageSystemAttributes -> MessageBodySystemAttributeMap and output member MD5OfMessageSystemAttributes; the member's own documentation states "Currently, the only supported message system attribute is AWSTraceHeader. Its type must be String and its value must be a correctly formatted X-Ray trace header string" and "The size of a message system attribute doesn't count towards the total size of a message." So SendMessage with MessageSystemAttributes={'AWSTraceHeader': {'DataType':'String','StringValue':<X-Ray trace header>}} is ACCEPTED at 200, returns MD5OfMessageSystemAttributes computed over that separate map, excludes the system attribute from the queue's MaximumMessageSize accounting (a 1024-byte body on a MaximumMessageSize=1024 queue plus an AWSTraceHeader is accepted), and makes the attribute selectable on ReceiveMessage; a system-attribute key OTHER than AWSTraceHeader is the only refusal, with Code InvalidParameterValue at 400.
Emulator: every SendMessage carrying MessageSystemAttributes is refused with Code 'AWS.SimpleQueueService.UnsupportedOperation' and Message 'The request includes MessageSystemAttributes, which this emulator does not support yet: it carries the X-Ray trace header, which nothing here propagates.' UnsupportedOperation IS modeled on SendMessage (400) but is AWS's code for a structurally unsupported request, and the message is emulator-authored prose AWS never produces (it even names the emulator). Four distinct AWS behaviours — accept, digest, size exclusion, and the one genuinely invalid key — collapse into one refusal.
Why: a producer that propagates an X-Ray trace through a queue cannot send at all; the whole trace-header leg of a tracing deployment fails at the edge, and a client that reads MD5OfMessageSystemAttributes or relies on the system attribute not counting toward MaximumMessageSize gets a refusal where AWS returns 200.
Fix: implement MessageSystemAttributes in the SendMessage handler (accept AWSTraceHeader, refuse other keys with InvalidParameterValue, exclude the map from the size accounting, compute MD5OfMessageSystemAttributes) and project it on ReceiveMessage — services/service-com-amazonaws-sqs-amazonsqs/src/ops/send_message.rs and receive_message.rs.
Relation to an existing issue: open issue 20261025T065401Z-sqs-message-attributes-are-neither-validated-nor-selected.md (Cause 5) describes the same refusal, but recorded it with Code 'ValidationException'; the emulator now answers 'AWS.SimpleQueueService.UnsupportedOperation', so these three checks no longer match that issue's replay keys and the report leaves them unowned. The error CODE and MESSAGE stated here are the current ones.
Traces: sqs.message-digests-recomputed-from-the-documented-canonical-encoding, sqs.message-size-counts-attribute-name-type-and-value, sqs.receive-message-attribute-selectivity.

Cause 2 of 4: the CreateQueue FIFO cross-attribute refusal message drops its 'Reason:' clause.
AWS: Smithy models InvalidAttributeValue (400) on CreateQueue. Recorded behavior: CreateQueue with FifoThroughputLimit='perMessageGroupId' and DeduplicationScope != 'messageGroup' is refused with Code 'InvalidAttributeValue' and Message 'Invalid value for the parameter FifoThroughputLimit. Reason: To set FifoThroughputLimit to perMessageGroupId, the DeduplicationScope must be messageGroup.' — all fixed text; the only variable part is the offending attribute name taken from the request's Attributes map.
Emulator: the Code is right, but the Message is only 'Invalid value for the parameter FifoThroughputLimit.' — the entire 'Reason: ...' clause, which is the only part that tells the caller WHICH other attribute to change, is missing.
Why: IaC and SDK callers surface and match on the Reason clause to repair the attribute pair; without it the refusal is indistinguishable from any other bad FifoThroughputLimit value.
Fix: the cross-attribute validation message template in the CreateQueue / SetQueueAttributes handler's attribute validation (services/service-com-amazonaws-sqs-amazonsqs/src/ops/create_queue.rs). The classification is already correct and must not change. Context: the refusal itself only started happening after the fix recorded in 20261025T065401Z-sqs-fifo-receive-side-idempotency-is-absent-receiverequestattemptid.md (status fixed, Cause 3, where the call returned 200); what remains is the message text.
Traces: sqs.fifo-throughput-limit-per-message-group-requires-message-group-scope-rejected.

Cause 3 of 4: the ReceiveMessage 'attempt id no longer retryable' refusal message drops its 'Reason:' clause.
AWS: ReceiveMessage carries ReceiveRequestAttemptId (String). Recorded behavior: retrying a FIFO receive under an attempt id whose batch has since been modified (a message deleted or its visibility changed) is refused with Code 'InvalidParameterValue' and Message 'Value <ReceiveRequestAttemptId> for parameter ReceiveRequestAttemptId is invalid. Reason: The receiveRequestAttemptId is not valid anymore since the receive call is not retryable.' — fixed text, with the attempt id copied from the request.
Emulator: the Code is right and the refusal now happens, but the Message is 'Value <attempt id> for parameter ReceiveRequestAttemptId is invalid.' (observed with this run's value 'attempt-a-328c9599'; the id is request data, the missing sentence is the requirement) — the 'Reason: ...' clause is dropped.
Why: a FIFO consumer distinguishes 'this attempt id was never valid' from 'this batch was modified, re-receive instead of retrying' by that sentence; without it a retry loop cannot tell a permanent from a recoverable condition.
Fix: the refusal message template for a non-retryable attempt id in the ReceiveMessage handler (services/service-com-amazonaws-sqs-amazonsqs/src/ops/receive_message.rs).
Traces: sqs.receive-request-attempt-id-not-retryable-after-batch-modified-rejected.

Cause 4 of 4: StartMessageMoveTask on a non-DLQ source is refused with the wrong message.
AWS: Smithy models StartMessageMoveTask with InvalidAddress, InvalidSecurity, RequestThrottled, ResourceNotFoundException and UnsupportedOperation; InvalidParameterValue is the service's parameter-refusal code. Recorded behavior: a SourceArn that no other queue's RedrivePolicy names is refused with Code 'InvalidParameterValue' and Message exactly 'Source queue must be configured as a Dead Letter Queue.' — entirely fixed text, nothing interpolated — and no task is recorded for that source.
Emulator: the Code is right (and the surrounding legs pass: the positive control starts a task on a real DLQ, and the identical call succeeds once the candidate is wired as a DLQ), but the Message is 'This action is currently limited to supporting message redrive from queues that are configured as dead-letter queues (DLQs) of other Amazon SQS queues only.' — the service's UnsupportedOperation documentation sentence reused as a parameter-refusal message.
Why: callers log and match the message to tell a mis-wired source from a transient one; this wording corresponds to a different AWS error class, so operators reading it look for an unsupported-source limitation rather than a missing RedrivePolicy.
Fix: the refusal message for a source that is not a dead-letter queue, in the StartMessageMoveTask handler (services/service-com-amazonaws-sqs-amazonsqs/src/ops/start_message_move_task.rs). Open issue 20261025T182751Z-sqs-7-net-new-batch-message-move-root.md (Cause 7) covers only the BUSY-source refusal code and does not carry this check or this message.
Traces: sqs.op-message-move-task-on-non-dlq-rejected.
