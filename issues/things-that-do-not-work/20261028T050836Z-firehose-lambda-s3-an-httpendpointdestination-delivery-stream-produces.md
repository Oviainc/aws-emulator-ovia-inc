# firehose__lambda__s3: an HttpEndpointDestination delivery stream produces no request at its endpoint, so the documented HTTP-endpoint request envelope is never observable (1 cause)

> _Note: this issue was identified against the code base at commit `d80e8185b7256698d8601ca5718ff628d8333fc6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRecordBatch

## Description
One root cause. Cause count: 1.

=== Cause 1 of 1: records accepted by PutRecordBatch on an HttpEndpointDestination stream never reach the endpoint, so nothing about the delivery request can be read back ===

AWS: a delivery stream whose destination is `HttpEndpointDestinationConfiguration` POSTs each due buffer to `EndpointConfiguration.Url` (Smithy: HttpEndpointConfiguration.Url is required, `@pattern ^https://`, max length 1000, sensitive; AccessKey max 4096, sensitive; HttpEndpointRequestConfiguration carries ContentEncoding and CommonAttributes, 0..50 entries). Per the HTTP Endpoint Delivery Request and Response Specifications the request carries `X-Amz-Firehose-Protocol-Version: 1.0`, `X-Amz-Firehose-Request-Id` (an opaque 8-4-4-4-12 GUID, per request), `X-Amz-Firehose-Source-Arn` equal to the stream's own DeliveryStreamARN, `X-Amz-Firehose-Access-Key` equal to the configured AccessKey copied verbatim, `Content-Type: application/json`, no `Content-Encoding` header at all when RequestConfiguration.ContentEncoding is NONE, and `X-Amz-Firehose-Common-Attributes` holding `{"commonAttributes": {<name>: <value>}}` for the configured attributes; the body is `{"requestId": <the header's value>, "timestamp": <epoch ms>, "records": [{"data": <base64 of the record bytes>}, ...]}` with `data` the only member of each entry and no appended delimiter. A conforming 200 whose `requestId` matches ends the attempt: nothing is retried, nothing is written to ErrorOutputPrefix, and with S3BackupMode FailedDataOnly nothing is written to the backup prefix.
Emulator: the check is cut off — `Error: Check timed out after 60.0s` — with no capture object ever written. PutRecordBatch reports FailedPutCount 0, but the endpoint (which records every request it receives into S3 and answers the documented success envelope) is never called, so not one of the header or body requirements above can be graded. The delivery path itself exists in the crate (services/service-com-amazonaws-firehose-firehose-20150804/src/state/delivery.rs documents `post_to_endpoint`, the in-process connector from `OperationContext::callback`, and `backup_object` parking for unacknowledged buffers), so the records are accepted and buffered but nothing observable comes out of the HTTP-endpoint destination within the window.
Hypothesis: the endpoint under test is a Lambda function URL, and Lambda in this emulator cannot execute a deployment package at all — the open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md (and 20261024T055421Z-lambda-opensearch-s3-lambda-invoke-cannot-execute-a-deployment-package-so.md) record that Invoke answers NotImplemented. If the function-URL route is likewise not served or cannot run the handler, Firehose's POST would reach nothing even if it were sent; conversely, if the flush/POST never happens, the Lambda side is irrelevant. The replay cannot separate the two, and neither of those issues names this check or the Firehose HTTP-endpoint protocol, so neither covers it. Related but distinct: 20261024T005347Z-firehose-never-delivers-buffered-records-to-the-s3.md covers the S3 destination, not HttpEndpointDestination.
Why: a client building an HTTP-endpoint (third-party/Datadog-style) delivery pipeline gets a stream that reports ACTIVE, accepts records with FailedPutCount 0 and echoes the destination's Url, while its receiver is never invoked — indistinguishable from "data is still buffering", and no Firehose API reports what was put on the wire. Error-path behaviour is equally unobservable: a client cannot tell an acknowledged batch from one that silently never left, and cannot verify that a conforming 200 is not retried into ErrorOutputPrefix or the S3 backup prefix.
Fix: the Firehose delivery clock and HTTP-endpoint delivery path — services/service-com-amazonaws-firehose-firehose-20150804/src/state/delivery.rs (`deliver_due` / `post_to_endpoint`): the due buffer must actually be POSTed through the in-process connector to the host named by EndpointConfiguration.Url with the documented headers and body, and the route for that URL must be served (for a Lambda function URL, the Lambda invocation path that the issues above cover).
