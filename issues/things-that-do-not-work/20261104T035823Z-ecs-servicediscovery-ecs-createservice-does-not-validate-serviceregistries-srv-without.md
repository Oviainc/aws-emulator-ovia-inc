# ECS CreateService does not validate serviceRegistries: SRV without a port and an A record under bridge/host networkMode are accepted, and the bad-containerName message is emulator prose

> _Note: this issue was identified against the code base at commit `c083bea380b29cc5238d586af0774e0d5864cbe3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateService

## Description
THREE independent, net-new root causes in the ECS emulator's CreateService handling of the `serviceRegistries` triplet (registryArn / containerName / containerPort / port), all grounded in failing behavioral checks of the bootstrapped ecs service against a real Cloud Map registry. Each cause below must be closed before this issue is submitted. Model citations use services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/smithy-model/com-amazonaws-ecs-amazonec2containerservicev20141113.json.

Cause 1 of 3: CreateService ACCEPTS an SRV-record service registry that carries neither `port` nor a `containerName`+`containerPort` pair, where AWS refuses it.
AWS: Smithy ServiceRegistry{registryArn, port, containerName, containerPort}; containerName/containerPort are documented as 'If the task definition your service task specifies uses the awsvpc network mode and a type SRV DNS record is used, you must specify either a containerName and containerPort combination or a port value. However, you can't specify both.' The refusal is InvalidParameterException (Smithy com.amazonaws.ecs#InvalidParameterException, HTTP 400) and its recorded message template is: fixed text "When specifying a value for serviceRegistries that is configured to use a type 'SRV' DNS record, you must also enter a value for either 'port' or the 'containerName' and 'containerPort' combination, but not both. Registry: " followed by one variable part — the Cloud Map service ARN taken verbatim from the request's registryArn.
Emulator: HTTP 200. The service is created ACTIVE with serviceRegistries=[{registryArn: <the Cloud Map SRV service ARN>}] (no port, no containerName), desiredCount honoured and a PRIMARY deployment started.
Why: an incomplete SRV registration can never produce a usable SRV record (no port to publish), so a client validating its deployment templates against the emulator ships a configuration real AWS rejects at create time; negative tests of the refusal pass vacuously here and fail against AWS.
Fix: the serviceRegistries validation in ECS CreateService's handler (the same validation UpdateService shares), before any service row is persisted — the rejected call must leave no ECS service and no Cloud Map instance behind.
Traces: ecs__servicediscovery.ecs-srv-service-registry-without-a-port-rejected.

Cause 2 of 3: CreateService ACCEPTS a service registry whose Cloud Map service publishes an A record while the task definition uses the `bridge` network mode, where AWS refuses it.
AWS: ServiceRegistry.containerName/containerPort are documented as 'If the task definition that your service task specifies uses the bridge or host network mode, you must specify a containerName and containerPort combination from the task definition' — a type 'A' DNS record is not supported for those network modes. The refusal is InvalidParameterException (HTTP 400) with the recorded message template: fixed text "The specified serviceRegistries value is configured to use a type 'A' DNS record, which is not supported when specifying 'host' or 'bridge' for networkMode. Change to 'SRV' record, which is the supported DNS record type. Registry: " plus one variable part — the registryArn from the request.
Emulator: every attempt is accepted. The check retries the create for up to 80 s precisely because a very fresh Cloud Map service can momentarily pass this check on real AWS, and it only leaves that loop when a rejection arrives; against the emulator no rejection ever arrives, so the check burns its whole budget and is reported as 'Check timed out after 60.0s'. The positive control in the same check (the identical SRV registry triplet, stored and read back by DescribeServices) passes, so the registry path itself works — only the record-type/networkMode rule is missing.
Why: bridge/host-mode services registered against an A-record Cloud Map service are silently created and never resolve; the emulator gives no signal of a misconfiguration AWS catches synchronously.
Fix: the same serviceRegistries validation in ECS CreateService's handler — resolve the registryArn's Cloud Map DnsConfig record type and reject 'A'/'AAAA' when the task definition's networkMode is bridge or host.
Traces: ecs__servicediscovery.ecs-create-service-rejects-an-a-record-registry-under-bridge-networking.

Cause 3 of 3: the InvalidParameterException message for a containerName that is absent from the task definition is the emulator's own prose instead of AWS's template.
AWS: ServiceRegistry.containerName is documented as 'The container name value to be used for your service discovery service. It's already specified in the task definition.' ECS resolves the name against the task definition's containerDefinitions and refuses an unknown one with InvalidParameterException whose message template is: fixed text "The container ", then the containerName value taken from the request, then fixed text " is not valid. The value for 'containerName' must already be specified in the task definition. Registry: ", then the registryArn value taken from the request.
Emulator: InvalidParameterException with "The container <containerName> does not exist in the task definition." — the error code and 400 status are right, the message is a different sentence and it drops the 'Registry: <registryArn>' suffix entirely.
Why: the Registry suffix is the only part of the refusal that says WHICH of a service's registries was rejected; clients and tests matching the documented text diverge, and multi-registry diagnostics lose the correlation.
Fix: the InvalidParameterException construction in ECS CreateService's serviceRegistries validation (per-rule template, not a generic 'does not exist' helper).
Traces: ecs__servicediscovery.ecs-create-service-rejects-a-container-name-absent-from-the-task-definition.
