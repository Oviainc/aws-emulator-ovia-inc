# events: UpdateConnection's "AuthParameters without AuthorizationType" refusal uses an emulator-authored message, and an API_KEY connection's API destination never delivers (2 causes)

> _Note: this issue was identified against the code base at commit `6e4639cd3b0eb321e74af4094a3461ae2de27150`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateConnection

## Description
Two net-new root causes in the events service. Both surfaced from behavioral checks the replay report did NOT mark OWNED or ALREADY FILED.

Cause 1 of 2: UpdateConnection refuses an update that names AuthParameters without AuthorizationType with the right error code but an emulator-authored message.
Failing check: events.api-destination-state-follows-connection-deauthorize-and-reauthorize.
AWS: Smithy (eventbridge) UpdateConnection models only `Name` as required (@length 1-64, pattern ^[\.\-_A-Za-z0-9]+$); `Description`, `AuthorizationType`, `AuthParameters` (UpdateConnectionAuthRequestParameters), `InvocationConnectivityParameters` and `KmsKeyIdentifier` are all optional, and the operation's modeled errors are AccessDeniedException, ConcurrentModificationException, InternalException, LimitExceededException, ResourceNotFoundException and ThrottlingException — ValidationException is NOT modeled, so this code/message pairing is recorded behavior only. Recorded: the call is refused with HTTP 400, Error.Code `ValidationException` and Error.Message `Failed to update the connection(s). At least one of the following is required: Description, KmsKeyIdentifier, AuthorizationType with BasicAuthParameters, ApiKeyAuthParameters, or OAuthParameters.` The whole message is FIXED text for this error class: AWS interpolates nothing from the request — no connection name, no member name, no supplied value. The refusal is also a no-op on state: the connection is still DEAUTHORIZED afterwards (Smithy ConnectionState enum: CREATING/UPDATING/DELETING/AUTHORIZED/DEAUTHORIZED/AUTHORIZING/DEAUTHORIZING/ACTIVE/FAILED_CONNECTIVITY).
Emulator: same code, wholly different fixed text — `('ValidationException', 'Failed to update the connection(s). Parameter AuthParameters is not valid. Reason: AuthorizationType must be provided when AuthParameters is provided.')`. It reports a per-parameter "Parameter <X> is not valid. Reason: ..." diagnosis (with the member name `AuthParameters` taken from the request) where AWS reports the "At least one of the following is required: ..." alternatives list and names no request value at all.
Why: a client or CLI wrapper that matches on the refusal text to distinguish "you must also pass AuthorizationType / one of these fields" from other validation failures takes the wrong branch, and any recorded-response comparison fails on a message the service never produces. The parenthetical "(s)" prefix matching makes the divergence easy to miss while the actionable remainder is wrong.
Fix: the UpdateConnection handler's validation/refusal construction in the events crate — emit the fixed AWS message for this error class instead of formatting the offending member name and a synthesized reason into it. Fixed issue 20261029T235600Z-events-client-error-messages-are-emulator-authored-instead.md covered other events refusals; this UpdateConnection message is still emulator-authored.
Traces: events.api-destination-state-follows-connection-deauthorize-and-reauthorize (assertion at check line 48).

Cause 2 of 2: an API_KEY connection's API destination target never issues the HTTP request, so neither the API-key header nor the connection/target parameter merge can be observed.
Failing check: events.api-destination-api-key-connection-adds-its-key-and-parameters-and-its-values-win-over-the-targets.
AWS: Smithy (eventbridge) models CreateConnection AuthParameters.ApiKeyAuthParameters{ApiKeyName (required, @length 1-512), ApiKeyValue (required, @sensitive)} and ConnectionHttpParameters{HeaderParameters, QueryStringParameters, BodyParameters} (each a list, @length 0-100), and Target.HttpParameters{PathParameterValues, HeaderParameters, QueryStringParameters}. HttpParameters' own model documentation states the rule: "These are custom parameter to be used when the target is an API Gateway APIs or EventBridge ApiDestinations. In the latter case, these are merged with any InvocationParameters specified on the Connection, with any values from the Connection taking precedence." Recorded behavior for the wire details: a matched event on a rule whose target is the API destination causes one request to the destination's InvocationEndpoint using the destination's HttpMethod (POST), with each `*` path wildcard filled from the target's PathParameterValues; the connection's ApiKeyName header carries the ApiKeyValue; connection and target header and query parameters are both present and the connection's value wins on a clashing key; the connection's BodyParameters are added as members of the JSON body alongside the bare EventBridge envelope (keys account, detail, detail-type, id, region, resources, source, time, version) whose `id` is the EventId PutEvents returned; content-type is `application/json; charset=utf-8` and user-agent is `Amazon/EventBridge/ApiDestinations`.
Emulator: nothing is delivered. The check ends `Check timed out after 60.0s` — no request ever reaches the capture endpoint, so every assertion above is unreachable. Note the capture endpoint in this check is a Lambda function URL, and Lambda invocation is itself refused in this emulator (open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md), so both the API-destination dispatch path and that endpoint path are emulator-side; neither is a runner defect.
Why: a client that fans events to an HTTP endpoint through an API_KEY connection receives no calls at all — the credential it configured is never sent and the connection-over-target precedence it relies on is unobservable, so a misconfiguration is indistinguishable from correct operation.
Fix: the API-destination target dispatch path in the events crate — resolve the destination and its connection, build the HTTP request (method, endpoint with PathParameterValues substituted into `*`, api-key header from ApiKeyAuthParameters, EventBridge content-type and user-agent, bare envelope plus connection BodyParameters as body) and merge the connection's InvocationHttpParameters with the target's HttpParameters giving the connection precedence.
Ownership note: open issue 20261102T091831Z-events-api-destinations-never-deliver-or-dead-letter.md describes API-destination non-delivery as its Cause 1, and 20261029T092208Z-events-eventbridge-api-destination-targets-never-deliver-so-the.md and 20261027T200000Z-events-eventbridge-an-oauth-client-credentials-connection-never-fetches-a-token-so-its-api-destination-never-delivers.md cover neighbouring checks — none of them carries this check's replay key, which is why the report leaves it unowned; the API_KEY auth-header and parameter-merge contract is not described by any of them.
Traces: events.api-destination-api-key-connection-adds-its-key-and-parameters-and-its-values-win-over-the-targets.

## Evidence
Cause 1 — Expected: UpdateConnection(Name=<conn>, AuthParameters={BasicAuthParameters:{...}}) with no AuthorizationType is refused HTTP 400 with Error.Code 'ValidationException' and Error.Message "Failed to update the connection(s). At least one of the following is required: Description, KmsKeyIdentifier, AuthorizationType with BasicAuthParameters, ApiKeyAuthParameters, or OAuthParameters." (entirely fixed text), and DescribeConnection still reports ConnectionState 'DEAUTHORIZED'. Actual: AssertionError: auth parameters without AuthorizationType must be refused, got 'ValidationException' 'Failed to update the connection(s). Parameter AuthParameters is not valid. Reason: AuthorizationType must be provided when AuthParameters is provided.' — same code, different fixed text, and the message names the request member 'AuthParameters' which AWS does not mention.

Cause 2 — Expected: one POST to /orders/o-42 at the destination's endpoint, query string exactly cq=from-conn&tq=from-target (connection's cq wins over the target's), header x-sim2real-key carrying the connection's ApiKeyValue, headers x-conn-h=conn, x-target-h=tgt, x-both=from-conn (connection wins), content-type 'application/json; charset=utf-8', user-agent 'Amazon/EventBridge/ApiDestinations', and a JSON body carrying the connection body parameter conn_body=b1 plus the bare envelope keys [account, detail, detail-type, id, region, resources, source, time, version] whose id equals the PutEvents EventId and whose detail is the published detail. Actual: 'Check timed out after 60.0s' — PutTargets reported FailedEntryCount 0 and PutEvents accepted every entry, but no HTTP request was ever captured, so the destination was never invoked.
