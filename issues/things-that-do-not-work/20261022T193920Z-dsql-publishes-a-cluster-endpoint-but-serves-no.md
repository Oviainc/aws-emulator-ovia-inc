# dsql publishes a cluster endpoint but serves no PostgreSQL wire data plane, so every native-SQL check hangs until the harness kills it

> _Note: this issue was identified against the code base at commit `17f16131651e3a76635c083c093a8581359ec045`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCluster

## Description
Cause 1 of 1: the cluster endpoint the control plane publishes accepts no PostgreSQL wire connection, so the entire Aurora DSQL data plane is unreachable.

AWS: recorded behavior only — the Smithy model (services/service-com-amazonaws-dsql-dsql/smithy-model/com-amazonaws-dsql-dsql.json) is control-plane only: it binds no operation that carries SQL, and it models the endpoint merely as CreateCluster/GetCluster's `endpoint` member (Endpoint, pattern ^[a-zA-Z0-9.-]+$). What the recordings show is that this published endpoint is a live PostgreSQL server: once a cluster reports status ACTIVE, a libpq client connects to it on TCP 5432, database `postgres`, user `admin`, with a DSQL IAM auth token as the password (the SDK's GenerateDbConnectAdminAuthToken / GenerateDbConnectAuthToken presigners are client-side, so they need no server support), and gets a working session. The recordings further show the endpoint enforces specific data-plane behavior: TLS is mandatory (a plaintext connection is refused FATAL "unable to accept connection, SSL is mandatory. AWS Authentication is required."), the token's action and host are validated (a DbConnect token presented for `admin`, a non-token password, and an admin token signed for another cluster's host are each refused FATAL "unable to accept connection, access denied"), sessions run at REPEATABLE READ with optimistic concurrency that rejects the losing commit, and the documented-unsupported PostgreSQL features (TRUNCATE, TEMP tables, triggers, PL/pgSQL, extensions, synchronous CREATE INDEX, other isolation levels, locking clauses other than FOR UPDATE / FOR KEY SHARE, LOCK, advisory locks, PARTITION BY, VACUUM) are refused with SQLSTATE 0A000.

Emulator: the control plane mints and publishes an endpoint — services/service-com-amazonaws-dsql-dsql/src/state.rs `cluster_endpoint` (around line 699) renders `{identifier}.dsql.{region}.on.aws` and services/service-com-amazonaws-dsql-dsql/src/ops/create_cluster.rs line 279 stores it on the cluster — but nothing in the service answers the PostgreSQL wire protocol at it: services/service-com-amazonaws-dsql-dsql/src/lib.rs declares only `ops`, `scaffolded`, `service` and `state`, with no data-plane listener module. Every check that resolves the published endpoint and opens a libpq connection therefore retries a connection that is never accepted and is killed by the harness: all nine `dp:native` / `plane:data` checks report "Check timed out after 60.0s" and none of their data-plane assertions is ever reached. (This is not a missing runner tool: the harness has psycopg available — the native-SQL check would have reported RequiredToolMissing rather than timing out — and no assertion here depends on a real account or a live-only value.)

Why: a cluster that reports ACTIVE and advertises an endpoint but accepts no connection is "provisioned but unconnectable" — the single most misleading state for a client. Any application that does the normal thing (CreateCluster, wait for ACTIVE, generate an auth token, connect, run SQL) hangs on connect rather than failing fast, and every behavior a DSQL client depends on — mandatory TLS, auth-token validation scoped to action and host, REPEATABLE READ with OCC commit rejection, the 0A000 refusal of unsupported PostgreSQL statements, the sequence/identity CACHE rule, and the transaction constraints on mixing DDL with DML — is unverifiable and unimplemented. A target that answers the control plane correctly while silently having no data plane also looks healthy to anything that only grades control-plane envelopes.

Fix: the service needs a data-plane component — a PostgreSQL wire-protocol listener reached at the endpoint `crate::state::cluster_endpoint` publishes (port 5432), mounted alongside the control-plane `service` module, that requires TLS, authenticates the password as a DSQL auth token validated against the connecting cluster's host and the requested action/user, and executes SQL under DSQL's documented semantics. Until a listener exists at all, none of the per-statement semantics above can be reached.

Traces: failing checks dsql.native-sql-round-trip-create-insert-select, dsql.connection-without-tls-or-admin-token-rejected, dsql.expired-auth-token-rejected-open-session-survives, dsql.iam-mapped-database-role-privileges-denied, dsql.dsql-occ-write-conflict-rejects-the-losing-commit, dsql.locking-read-conflicts-rejected-at-commit, dsql.transaction-constraints-rejected, dsql.unsupported-postgres-statements-rejected, dsql.sequence-and-identity-cache-rule-rejected — every one of them times out at the connect step. File citations: services/service-com-amazonaws-dsql-dsql/src/lib.rs lines 10-17 (module list, no data plane); services/service-com-amazonaws-dsql-dsql/src/state.rs around line 699; services/service-com-amazonaws-dsql-dsql/src/ops/create_cluster.rs line 279.

## Evidence
Expected (recorded AWS): after GetCluster reports status=ACTIVE and an `endpoint`, `psycopg.connect(host=<endpoint>, port=5432, dbname="postgres", user="admin", password=<admin auth token>, sslmode="require")` opens a session in which `SELECT current_user, 1 + 1` returns ('admin', 2); a plaintext (sslmode=disable) attempt is refused with FATAL "unable to accept connection, SSL is mandatory. AWS Authentication is required."; a DbConnect token for user admin, a non-token password, and an admin token signed for a different cluster host are each refused with FATAL "unable to accept connection, access denied" (the DbConnect-for-admin case additionally carrying HINT "Wrong user to action mapping. user: admin, action: DbConnect"); unsupported statements are refused with SQLSTATE 0A000.

Actual (emulator): the control plane answers — CreateCluster returns an identifier and an endpoint of the form <identifier>.dsql.<region>.on.aws and GetCluster settles the cluster to ACTIVE — but no connection to that endpoint on 5432 is ever accepted. All nine data-plane checks report exactly:
  Error: Check timed out after 60.0s
They time out inside their connect-retry loops (`_connect_ready` / `_connect_with_retry`, which retry psycopg.OperationalError to a 180 s / 120 s budget), so none of the SQL-level assertions above is reached. The crate itself confirms the absence: services/service-com-amazonaws-dsql-dsql/src/lib.rs exposes only `ops`, `scaffolded`, `service`, `state` — there is no PostgreSQL listener to accept the connection the published endpoint advertises.

## Steps to Reproduce
1. CreateCluster(deletionProtectionEnabled=false).
2. Poll GetCluster(identifier=<id>) until status == "ACTIVE" and note the `endpoint` it returns.
3. GenerateDbConnectAdminAuthToken(Hostname=<endpoint>, Region=<region>, ExpiresIn=900) (client-side presigner).
4. Connect a PostgreSQL client to that endpoint: psycopg.connect(host=<endpoint>, port=5432, dbname="postgres", user="admin", password=<token>, sslmode="require", connect_timeout=20).
5. The connection is never accepted — it fails/retries indefinitely instead of opening a session; against AWS the same sequence yields a working session where `SELECT current_user, 1 + 1` returns ('admin', 2).
6. Consequently none of the data-plane behaviors can be probed: plaintext refusal, auth-token action/host validation, REPEATABLE READ + OCC commit rejection, SQLSTATE 0A000 refusals of unsupported statements, the sequence/identity CACHE rule, and the DDL/DML transaction constraints all remain unreachable.
