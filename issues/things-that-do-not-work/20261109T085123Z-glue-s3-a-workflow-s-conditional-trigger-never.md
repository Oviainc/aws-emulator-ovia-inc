# glue__s3: a workflow's CONDITIONAL trigger never fires after its predicate job succeeds — the workflow run settles ERROR with one action and the downstream job never runs

> _Note: this issue was identified against the code base at commit `4ca728998286b7558a3f8204f86decdeb692036b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetWorkflowRun

## Description
One net-new root cause, reached after glue CreateJob, CreateWorkflow, CreateTrigger (ON_DEMAND and CONDITIONAL) and the standalone producer job run all succeeded — the warm-up producer run reached SUCCEEDED and wrote its object, so this is not a bootstrap gap or an unimplemented stub.

Cause 1 of 1 — a CONDITIONAL trigger inside a workflow is never evaluated when its predicate job reaches SUCCEEDED, and the workflow run is reported ERROR even though no action errored.
AWS: Smithy models Trigger.Type as a TriggerType enum with Trigger.Predicate (Predicate{Logical: Logical enum, Conditions: ConditionList @length 0..500}) and Condition{LogicalOperator, JobName — 'the name of the job whose JobRuns this condition applies to, and on which this trigger waits', State: JobRunState — 'the only job states that a trigger can listen for are SUCCEEDED, STOPPED, FAILED, and TIMEOUT'}; WorkflowRun.Status is a WorkflowRunStatus enum and WorkflowRun.Statistics is WorkflowRunStatistics{TotalActions, SucceededActions, FailedActions, ErroredActions, …}, with ErroredActions documented as 'the count of job runs in the ERROR state in the workflow run'. Recorded behavior: starting the workflow runs the ON_DEMAND trigger's action (the producer job); when that run reaches SUCCEEDED the CONDITIONAL trigger whose predicate is {Logical: ANY, Conditions:[{LogicalOperator: EQUALS, JobName: <producer>, State: SUCCEEDED}]} fires and runs its own action (the consumer job); the run then settles Status 'COMPLETED' with Statistics.TotalActions 2 and SucceededActions 2, the run Graph holds a JOB node for both the producer and the consumer each with one SUCCEEDED JobRun, and both objects exist in S3 (the consumer's value is computable only by reading the producer's object).
Emulator: only the entry trigger's action runs. The workflow run settles Status 'ERROR' with Statistics {TotalActions: 1, SucceededActions: 1, FailedActions: 0, StoppedActions: 0, ErroredActions: 0, TimeoutActions: 0, RunningActions: 0, WaitingActions: 0} — i.e. ERROR is reported while every counter says the single action succeeded and nothing errored, which is self-contradictory, and the consumer job is never started so its object is never written.
Why: Glue workflows are the dependency primitive for multi-job ETL. A client that gates a consumer job on its producer's SUCCEEDED state gets a workflow that stops after the first job yet reports a terminal status its own statistics contradict: orchestration code polling for COMPLETED fails, code branching on ErroredActions/FailedActions sees zero failures and cannot explain the ERROR, and downstream data is silently never produced.
Fix: the Glue workflow engine must evaluate CONDITIONAL triggers against job-run state transitions within the run and dispatch their Actions (services/service-com-amazonaws-glue-awsglue — the workflow-run/trigger evaluation path behind StartWorkflowRun/CreateTrigger/GetWorkflowRun), and the workflow run's terminal Status must be derived from its action outcomes so that an all-succeeded run is COMPLETED, with Statistics.TotalActions counting every dispatched action and the run Graph carrying a JOB node per action. Open issues that do NOT cover this: 20261027T003436Z-glue-sqs-an-on-demand-trigger-that-starts.md is about an ON_DEMAND trigger initiating NO job run (here the entry trigger's action does run and succeed), and 20261025T040843Z-glue-sqs-glue-createworkflow-answers-notimplemented-so-the.md (resolved) was CreateWorkflow answering NotImplemented, which it no longer does.
Traces: glue__s3.glue-workflow-runs-its-second-trigger-only-after-the-first-job-succeeds.

## Evidence
Expected: GetWorkflowRun after the run reaches a terminal state reports Status 'COMPLETED', Statistics.SucceededActions == 2, Graph.Nodes containing JOB nodes for exactly {<producer>, <consumer>} each with JobDetails.JobRuns == ['SUCCEEDED'], and both S3 objects present (producer value = seed*3, consumer value = seed*3+7, the latter obtainable only by reading the producer's object).

Actual (replay): AssertionError at check line 127 — "workflow run ended 'ERROR', statistics {'TotalActions': 1, 'TimeoutActions': 0, 'FailedActions': 0, 'StoppedActions': 0, 'SucceededActions': 1, 'RunningActions': 0, 'ErroredActions': 0, 'WaitingActions': 0}". The CONDITIONAL trigger created with StartOnCreation=True and Predicate {Logical:'ANY', Conditions:[{LogicalOperator:'EQUALS', JobName:<producer>, State:'SUCCEEDED'}]} never fired, so the consumer action is absent from TotalActions and its object was never written; the status is ERROR while ErroredActions and FailedActions are both 0.

## Steps to Reproduce
Create a bucket holding producer.py and consumer.py (the consumer reads the producer's object and writes a derived value); create a Glue role with read/write on the bucket; glue CreateJob for the producer and the consumer (pythonshell, MaxCapacity 0.0625, ExecutionProperty.MaxConcurrentRuns 5, DefaultArguments naming --IN/--OUT); run the producer standalone once and confirm SUCCEEDED; glue CreateWorkflow; CreateTrigger(Type='ON_DEMAND', WorkflowName=<wf>, Actions=[{JobName: producer}]); CreateTrigger(Type='CONDITIONAL', WorkflowName=<wf>, StartOnCreation=True, Predicate={Logical:'ANY', Conditions:[{LogicalOperator:'EQUALS', JobName: producer, State:'SUCCEEDED'}]}, Actions=[{JobName: consumer}]); start the workflow and poll GetWorkflowRun to a terminal Status. Observe Status 'ERROR' with TotalActions 1 and no consumer node or consumer object. Replay glue__s3.glue-workflow-runs-its-second-trigger-only-after-the-first-job-succeeds.
