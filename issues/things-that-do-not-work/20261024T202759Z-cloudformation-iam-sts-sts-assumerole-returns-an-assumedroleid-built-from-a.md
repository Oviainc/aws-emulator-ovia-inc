# STS AssumeRole returns an AssumedRoleId built from a freshly generated role ID, not the assumed role's RoleId, so a CFN-deployed role cannot be correlated to its session (1 cause)

> _Note: this issue was identified against the code base at commit `6b1652c669c36440eab65de28fac2314531b273d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRole

## Description
This issue carries ONE net-new root cause, observed on the cloudformation/iam/sts cross-service deploy scenario (service token `cloudformation__iam__sts`). A fixer must close one cause before submitting.

Cause 1 of 1: AssumeRole's AssumedRoleUser.AssumedRoleId does not embed the RoleId of the role named by RoleArn; a fresh, unrelated AROA identifier is minted per call.

AWS: Smithy: AssumeRole (service com.amazonaws.sts#AWSSecurityTokenServiceV20110615) returns AssumeRoleResponse.AssumedRoleUser; the AssumedRoleUser.AssumedRoleId member is documented as "A unique identifier that contains the role ID and the role session name of the role that is being assumed. The role ID is generated by Amazon Web Services when the role is created." So the value is the pair `<RoleId>:<RoleSessionName>`, where `<RoleId>` is exactly the RoleId that iam:CreateRole / iam:GetRole report for that role and `<RoleSessionName>` is the value supplied in the request (Smithy: AssumeRoleRequest.RoleSessionName, @length 2..64, @pattern ^[\w+=,.@-]*$). Here the role is created by CloudFormation (AWS::IAM::Role with a pinned RoleName) and read back with iam:GetRole, so the RoleId the role actually has is observable before the assume.

Emulator: the assume succeeds (HTTP 200) and the session name half is correct, but the role-ID half names a role identifier that exists nowhere in IAM state. Replay: iam:GetRole reported RoleId 'AROAOWVOJOY3VBWOJCSHY' for the CFN-deployed role, while sts:AssumeRole against that same role's ARN answered AssumedRoleUser.AssumedRoleId 'AROAD5ELEHRAVLI5FPML5:sim2real-trusted'. The identifier also differs between calls on one role (a second STS check in the same run shows 'AROAZHWIQD7HK6GMQKDNG:<session>'), which confirms it is generated per request rather than read from state.

Why: a client cannot correlate a session back to the role it came from. Audit joins (CloudTrail userIdentity.sessionContext), policy conditions keyed on the role id, and any UserId/AssumedRoleId comparison against the RoleId returned by CreateRole/GetRole all fail to match, and two assumes of the same role disagree with each other. In this scenario it also breaks the CloudFormation-driven IAM lifecycle: the stack's deployed role cannot be shown to be the role the session belongs to, so the subsequent in-place trust flip and replacing-rename transitions cannot be verified against the sessions they affect.

Fix: the AssumeRole handler/serializer must resolve RoleArn in IAM state and compose AssumedRoleId from that role's stored RoleId plus the request's RoleSessionName, instead of generating a new AROA id; the same resolved RoleId must be what GetCallerIdentity reports as UserId for the resulting session.

Related already-open issue: this is the same underlying defect as cause 5 of the open issue 20261024T065715Z-sts-assumerole-getsessiontoken-admit-requests-aws-refuses-no.md ("AssumedRoleUser.AssumedRoleId is not built from the assumed role's RoleId"). The suite did NOT mark this check as owned by that issue, so it is recorded here to make sure this cross-service check is re-replayed; a fixer should close the two together.

Traces: cloudformation__iam__sts.deploy-iam-1-cfn-rollback-and-trust-flip-assume-denied.
