# s3: 2 root causes — an ABAC tag-matched session is refused GetObject (the policy variable is never interpolated), and a bucket policy Allow naming a role ARN never admits that role's session

=== Cause 1 of 2: with bucket ABAC enabled, a policy variable in a condition value is never interpolated, so the TAG-MATCHED session is refused the object ===
AWS: Smithy models com.amazonaws.s3#PutBucketAbac (PUT /{Bucket}?abac, required httpPayload member AbacStatus) and GetBucketAbac; GetObject (GET /{Bucket}/{Key+}) declares only NoSuchKey and InvalidObjectState, so an authorization refusal rides S3's REST-XML error document — recorded behavior for the outcome. Recorded behavior: a bucket tagged `Team=Finance` with AbacStatus `Status=Enabled`, and a role whose only permission statement is Allow s3:GetObject on `arn:aws:s3:::<bucket>/*` with Condition `StringEquals {"aws:ResourceTag/Team": "${aws:PrincipalTag/Team}"}`: a session assumed with session tag `Team=Marketing` is REFUSED 403 `AccessDenied` with `User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:GetObject action`, and a session assumed with the MATCHING session tag `Team=Finance` is ALLOWED and returns the object's bytes. Both legs are the oracle: the allow is what proves the condition was evaluated rather than simply failing closed.
Emulator: the mismatched leg now matches AWS exactly (same code, same message). The MATCHED session is ALSO refused: GetObject raises `AccessDenied` with `... because no identity-based policy allows the s3:GetObject action` for a principal whose session tag equals the bucket's tag value. The condition is therefore not being evaluated at all — it is being treated as unsatisfiable — so either `aws:PrincipalTag/Team` is not populated from the assumed-role session tags, or `aws:ResourceTag/Team` is not populated from the bucket's tag set, or the `${aws:PrincipalTag/Team}` policy variable on the right-hand side of StringEquals is compared literally instead of being interpolated.
Why: ABAC is the mechanism customers use for tenant/team isolation — one role, many tag-scoped sessions. Failing closed is less dangerous than failing open but it is just as wrong: the legitimate, correctly tagged principal is locked out, so a client validating an ABAC design against this emulator concludes its policy is broken and widens it (typically by dropping the condition), shipping a grant that is far more permissive than the one it meant. The two directions are also indistinguishable from the message alone, since the emulator returns the no-grant message in both.
Fix: the GetObject authorization path and the shared IAM condition evaluator it calls — populate `aws:PrincipalTag/<k>` from the session tags carried by the assumed-role credential, populate `aws:ResourceTag/<k>` from the addressed bucket's tag set when the bucket's AbacStatus is Enabled, and interpolate `${aws:PrincipalTag/<k>}` inside condition VALUES before comparing. A matching pair must be admitted (HTTP 200 with the bytes); only a non-matching pair may be refused, with the implicit-deny message form above.
Traces: s3.abac-policy-enforcement.

=== Cause 2 of 2: a bucket policy whose Allow names a role ARN as Principal does not admit a session assumed from that role ===
AWS: recorded behavior only for the outcome (GetObject models no authorization error; the code rides the REST-XML body with HTTP 403). Recorded behavior: for a bucket whose policy carries `{Sid ReaderGetObject, Effect: Allow, Principal: {AWS: "<role arn>"}, Action: s3:GetObject, Resource: <bucket>/*}` — here deployed by CloudFormation as an `AWS::S3::BucketPolicy` with `Effect: !Ref ReaderEffect` set to `Allow` and `Principal` from `!GetAtt ReaderRole.Arn` — a session assumed from that role reads the object: GetObject returns 200 and the current bytes. The same stack updated to `Effect: Deny` then refuses that session with 403 `AccessDenied` and the message `User: <assumed-role session arn> is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" with an explicit deny in a resource-based policy`, while the bucket owner, not named by the Deny, still reads.
Emulator: the Allow never admits the role session. The check assumes the reader role and polls GetObject until it is allowed; it is refused for the whole window and the check ends with `TimeoutError: reader role to read <bucket>/<key> under the Allow policy: the run budget ended first; not graded`. The stack itself reached CREATE_COMPLETE and the owner's own PutObject/GetObject work, so the bucket, the object and the role all exist — only the resource-policy grant to the role principal is not honoured.
Why: a bucket policy naming a role ARN is the standard way to grant cross-principal and cross-account S3 access, and it is how a CloudFormation-managed bucket hands read access to an application role. With the Allow inert, every such deployment is unusable against the emulator, and — because the subsequent Deny leg can never be reached — a client also cannot verify that flipping the Effect actually blocks the reader. Everything the check would go on to verify (versioning Suspended in place, the explicit-deny message form, UpdateReplacePolicy Retain keeping the old bucket and its versions readable after a rename) is lost behind this one grant.
Fix: S3's resource-policy evaluation — a Principal entry of the form `arn:aws:iam::<account>:role/<name>` must match a caller whose credentials are a session assumed from that role (the session's `arn:aws:sts::<account>:assumed-role/<name>/<session>` identity resolves to that role principal), and an Allow so matched must admit GetObject.
Traces: s3.deploy-s3-1-bucket-update-versioning-policy-rename.
