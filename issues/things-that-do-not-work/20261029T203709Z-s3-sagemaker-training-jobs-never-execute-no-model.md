# s3__sagemaker: training jobs never execute (no model.tar.gz written to the S3 output path) and InvokeEndpoint on an InService endpoint refuses with 424 ModelError instead of serving inference (2 causes)

> _Note: this issue was identified against the code base at commit `355c5d16add239c66c8799ffa26377be788e0f43`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTrainingJob

## Description
Two distinct root causes block every cross-service S3+SageMaker model-serving flow. Both must be closed before submitting. Related open issues that do NOT cover these checks: 20261025T095709Z-s3-sagemaker-cross-service-s3-sagemaker-flows-blocked-an-accepted.md and 20261025T095709Z-sagemaker-training-jobs-never-run-an-accepted-createtrainingjob.md (they own other replay keys; the five checks listed here are unowned).

Cause 1 of 2: an accepted CreateTrainingJob never runs, so it terminates Failed and writes no model artifact to the caller's S3 output path. Failing checks: s3__sagemaker.sagemaker-endpoint-config-model-data-url-resolution, s3__sagemaker.sagemaker-endpoint-config-s3-model-data-resolution-positive, s3__sagemaker.sagemaker-endpoint-invocation-output-captured-to-s3.
AWS: CreateTrainingJob is accepted and the job runs the AlgorithmSpecification.TrainingImage over the InputDataConfig channels; DescribeTrainingJob then reports TrainingJobStatus moving InProgress -> Completed (Smithy com.amazonaws.sagemaker#TrainingJobStatus = InProgress|Completed|Failed|Stopping|Stopped|Deleting) and the response carries ModelArtifacts.S3ModelArtifacts, a required S3Uri documented as "The path of the S3 object that contains the model artifacts. For example, s3://bucket-name/keynameprefix/model.tar.gz" — i.e. a real object exists under the OutputDataConfig.S3OutputPath that a later CreateModel/CreateEndpointConfig can resolve. A Completed job sets no FailureReason.
Emulator: the job is accepted, then settles in TrainingJobStatus=Failed with FailureReason "This emulator has no container runtime, so the training job's algorithm image was never started and no model artifacts were written to the output S3 location" (emulator-authored prose that AWS never emits), and nothing is written under the S3 output prefix.
Why: every downstream step a client builds on training is unreachable — CreateModel cannot reference a ModelDataUrl that exists, EndpointConfig cannot resolve it at deployment time, and the endpoint can never load weights. A client that validates its train->deploy->infer pipeline against this emulator cannot distinguish "my pipeline is wrong" from "the backend ran nothing", and the Failed/FailureReason pair is itself a wire-visible divergence a caller may branch on.
Fix: the training-job execution/state machine behind CreateTrainingJob (the job runner that advances TrainingJobStatus and materializes the output artifact into the S3 service's object store), plus DescribeTrainingJob's ModelArtifacts projection. A synthesized, deterministic model.tar.gz placed at OutputDataConfig.S3OutputPath/<job>/output/model.tar.gz satisfies the contract; the requirement is that the status reaches Completed with no FailureReason and the artifact object is readable through S3.

Cause 2 of 2: an endpoint that the emulator itself reports InService serves no inference — InvokeEndpoint refuses with 424 ModelError — so DataCaptureConfig never writes capture records to S3 either. Failing checks: s3__sagemaker.sagemaker-endpoint-data-capture-s3-positive, s3__sagemaker.sagemaker-endpoint-data-capture-missing-s3-write-permission-negative.
AWS: once DescribeEndpoint reports EndpointStatus=InService, InvokeEndpoint returns HTTP 200 with the model's response Body plus the x-Amzn-Invoked-Production-Variant header (Smithy com.amazonaws.sagemakerruntime#InvokeEndpoint, http 200). ModelError is modeled httpError 424 and documented as "Model (owned by the customer in the container) returned 4xx or 5xx error code" — it is the container's OWN failure, not a statement that no container exists, and it is not raised for a healthy variant. With DataCaptureConfig enabled and InitialSamplingPercentage=100, the request/response is additionally written as JSON-lines objects under DestinationS3Uri; when the execution role lacks s3:PutObject on that destination, capture silently fails but the inference still succeeds with 200 (capture is best-effort).
Emulator: InvokeEndpoint against the InService endpoint answers 424 ModelError with the message "This emulator runs no model inference container, so endpoint <endpoint-name> returned no inference for this request." (fixed text is emulator-authored; the only request-derived part is the endpoint name). No capture object ever appears under DestinationS3Uri, and the negative control cannot be exercised at all because the happy path it depends on is refused.
Why: the data plane is a dead end. A client cannot verify a deployed model answers, cannot verify capture-to-S3 wiring, and cannot distinguish a genuine container-side 4xx/5xx (the real meaning of ModelError, which callers retry or alert on differently) from "this backend serves nothing". Permission-boundary tests invert: a flow that AWS completes with 200 fails here, so a client reads a broken deployment as a policy problem.
Fix: the InvokeEndpoint handler of the runtime data plane plus the endpoint state it reads — an endpoint in InService must serve a deterministic response derived from the referenced model's artifact instead of short-circuiting to ModelError, and the DataCaptureConfig writer must emit the capture records into the S3 object store (best-effort: a capture write failure must not change the 200 inference result).

Traces: see trace_ids; the three Cause-1 checks fail on `assert train_desc["TrainingJobStatus"] == "Completed"`, the two Cause-2 checks error out of botocore with ModelError on InvokeEndpoint.

Actual (emulator): TrainingJobStatus "Failed", FailureReason "This emulator has no container runtime, so the training job's algorithm image was never started and no model artifacts were written to the output S3 location"; no object under the S3OutputPath prefix.

## Steps to Reproduce
1. Boot the emulator and replay s3__sagemaker.sagemaker-endpoint-config-s3-model-data-resolution-positive.
2. Create an S3 bucket, upload a small CSV to train/train.csv, and create an IAM role trusted by sagemaker.amazonaws.com with S3 access to it.
3. Call sagemaker CreateTrainingJob with AlgorithmSpecification.TrainingImage set to the region's built-in XGBoost image, InputDataConfig pointing at s3://<bucket>/train/ and OutputDataConfig.S3OutputPath = s3://<bucket>/output/.
4. Poll DescribeTrainingJob: observe TrainingJobStatus "Failed" with the no-container-runtime FailureReason instead of "Completed", and ListObjectsV2 on s3://<bucket>/output/ returns no model.tar.gz. (Cause 1)
5. For Cause 2, replay s3__sagemaker.sagemaker-endpoint-data-capture-s3-positive: upload a hand-built model.tar.gz to S3, CreateModel referencing it, CreateEndpointConfig with a ProductionVariant plus DataCaptureConfig(EnableCapture=true, InitialSamplingPercentage=100, DestinationS3Uri=s3://<bucket>/capture/), CreateEndpoint and wait for DescribeEndpoint EndpointStatus=InService.
6. Call sagemaker-runtime InvokeEndpoint on that endpoint with a CSV row: observe HTTP 424 ModelError ("This emulator runs no model inference container, ...") instead of HTTP 200 with an inference body, and no capture object under s3://<bucket>/capture/.
7. Repeat step 5-6 with an execution role lacking s3:PutObject on the capture bucket: AWS still returns 200 (capture best-effort); the emulator refuses identically with 424.
