# oam: 8 behavioral divergences across CreateLink, GetSink, ListAttachedLinks and the tagging APIs (same-account gate missing, wrong rejection codes/messages)

> _Note: this issue was identified against the code base at commit `92c3b140342b1bc1fab2a232b8cee3f25ea78ff5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLink (bundle also covers GetSink, ListAttachedLinks, ListTagsForResource, TagResource, UntagResource)

## Description
The oam emulator (crate services/service-com-amazonaws-oam-oamservice) diverges from real AWS CloudWatch Observability Access Manager in 8 distinct root causes found by the behavioral suite. This issue bundles 8 causes; ALL EIGHT must be closed before submitting. Each cause below names its own failing check ids.

Note on scope: the open issue `20261029T174714Z-oam-createlink-accepts-a-same-account-sink-corrupting.md` describes the same missing same-account gate from the WIRE corpus (fixture oam-sink-crud-and-same-account-link-rejection); it does not carry the behavioral check keys below, so Cause 1 is recorded here and the two should be closed together. The behavioral check `oam.list-tags-for-resource-reflects-tag-and-untag` is NOT included: it is already filed as blocked by the unimplemented `UntagResource` scaffold stub (services/service-com-amazonaws-oam-oamservice/src/ops/untag_resource.rs). That same stub also sits behind the second half of Cause 7, so Cause 7 cannot be fully verified until that filed issue is fixed.

--- Cause 1 of 8: CreateLink accepts a sink in the CALLER'S OWN account ---
AWS: a monitoring link may never point at a sink owned by the calling account (cross-account sharing is the entire purpose of OAM). CreateLink with a SinkIdentifier that resolves to a same-account sink is refused with HTTP 400 and error code InvalidParameterException (Smithy: CreateLink errors = ConflictException 409, InternalServiceFault 500, InvalidParameterException 400, MissingRequiredParameterException 400, ServiceQuotaExceededException 429). The message is entirely FIXED text with no variable parts: "Cannot create a link to a sink in the same account". The gate is UNCONDITIONAL and fires before any content of the request is distinguished: it fires for a well-formed LinkConfiguration, for a LinkConfiguration that structurally mismatches ResourceTypes (e.g. LogGroupConfiguration supplied while ResourceTypes lists only AWS::CloudWatch::Metric), for every ResourceTypes combination, and on every repeated attempt — and it fires even when the sink carries a permissive sink policy naming the caller's own account as principal. Nothing is created: ListAttachedLinks for that sink stays empty and ListLinks reports no link with that SinkArn.
Emulator: CreateLink returns HTTP 200 with a fully populated CreateLinkOutput (Arn/Id/Label/LabelTemplate/ResourceTypes/SinkArn, plus LinkConfiguration when supplied) and PERSISTS the link. services/service-com-amazonaws-oam-oamservice/src/ops/create_link.rs has no account-ownership check at all: it goes from `require_resource_kind` and the resource-type catalog check straight to `store.sink(...)` and `store.insert_link(...)`. The repeat-attempt check also shows the follow-on effect: the second same-account attempt then hits the emulator's own ConflictException ("this source account is already linked to this sink by link ..."), a code AWS never reaches here.
Why: a client that mis-configures monitoring account == source account sees the call succeed, so it believes a cross-account observability link exists where AWS would have refused and created none. Every downstream read (ListAttachedLinks, ListLinks, GetLink) then reports a phantom link, and DeleteSink is permanently blocked by it.
Fix: an account-ownership gate in the CreateLink handler's validation, evaluated BEFORE the sink is looked up in state and before LinkConfiguration/ResourceTypes content is examined, raising InvalidParameterException (400) with the fixed message above and writing nothing to the link store.
Traces: oam.create-link-same-account-sink-rejected-regardless-of-link-configuration, oam.create-link-duplicate-already-linked-conflict-rejected, oam.create-link-invalid-sink-identifier-effect-absent (this last one's malformed-identifier half already passes; it fails only on the same-account positive control).

--- Cause 2 of 8: CreateLink with an unsupported ResourceTypes value uses the wrong error code and message ---
AWS: a ResourceTypes element outside the modeled enum is refused by request-body validation as error code BadRequestException (recorded behavior only — BadRequestException is NOT in the Smithy model for CreateLink; it is a frontend request-body rejection that precedes the modeled errors). The message template is: `Invalid request body: [instance value ("<value>") not found in enum (possible values: [<quoted enum values>])]`. Fixed text: `Invalid request body: [instance value (`, `) not found in enum (possible values: [`, and the trailing `])]`. Variable parts: the offending value echoed from the request, and the list of currently supported ResourceType values (Smithy ResourceType enum: AWS::CloudWatch::Metric, AWS::Logs::LogGroup, AWS::XRay::Trace, AWS::ApplicationInsights::Application, AWS::InternetMonitor::Monitor, AWS::ApplicationSignals::Service, AWS::ApplicationSignals::ServiceLevelObjective) — the list grows as OAM adds types, so it is state/model-derived, not fixed text.
Emulator: returns error code InvalidParameterException with its own prose message `ResourceTypes contains '<value>', which is not one of [<values>]` (create_link.rs, the `unmodelled_resource_type` branch).
Why: a client branching on the error code cannot distinguish a malformed request body from a semantically invalid parameter, and any client parsing the enum-membership message to discover the supported resource types gets nothing it can parse.
Fix: the ResourceTypes enum-membership refusal in the CreateLink handler's validation must emit error code BadRequestException with the message template above, instead of the handler's InvalidParameterException branch.
Traces: oam.create-link-invalid-resource-type-effect-absent.

--- Cause 3 of 8: GetSink with IncludeTags OMITTED drops Tags from the response ---
AWS: GetSink for the sink's owner returns the sink's tag set in Tags both when IncludeTags=true AND when IncludeTags is omitted, and that set is identical to ListTagsForResource for the same ARN after every mutation (CreateSink-time tags, TagResource, UntagResource, down to an empty set). Only IncludeTags=false omits the Tags member entirely. Recorded behavior for the omitted case: the Smithy doc for GetSinkInput.IncludeTags states "The default value is false", but the recording shows AWS returning Tags when the member is absent, so the recorded behavior is the requirement and the model doc is stale for this path. (Smithy: GetSinkOutput members Arn, Id, Name, Tags:TagMapOutput.)
Emulator: GetSink(Identifier=arn, IncludeTags=True) returns Tags correctly, but GetSink(Identifier=arn) with IncludeTags absent returns NO Tags member. Observed right after CreateSink(Tags={"origin":"create"}): {'include_true': {'origin': 'create'}, 'include_omitted': None, 'list_tags': {'origin': 'create'}}.
Why: a client that reads sink tags with a plain GetSink (the common call, with no IncludeTags passed) sees an untagged sink and concludes the tags were never applied — while ListTagsForResource contradicts it.
Fix: the IncludeTags handling in the GetSink handler/serializer must treat an ABSENT IncludeTags the same as true (tags projected from the single tagging store), and only suppress Tags for an explicit false.
Traces: oam.get-sink-include-tags-tracks-tag-and-untag.

--- Cause 4 of 8: ListTagsForResource on a deleted resource returns the wrong error code and message ---
AWS: after DeleteSink, GetSink and GetSinkPolicy for the dead identifier are ResourceNotFoundException (404) with the fixed message "Resource not found." — the emulator already matches those — but ListTagsForResource for the same ARN comes back on the TAGGING path with a DIFFERENT code and a DIFFERENT message: error code NotFoundException and the fixed message "Resource was not found" (no trailing period, no variable parts). Recorded behavior only: the Smithy model lists ListTagsForResource errors as ResourceNotFoundException 404 and ValidationException 400 and does not model NotFoundException, so the model does not describe this path.
Emulator: returns error code ResourceNotFoundException (the service-wide `crate::state::RESOURCE_NOT_FOUND_MESSAGE` path used by every other op), so the tagging-path distinction is lost.
Why: a client that keys cleanup/teardown logic on the tagging API's own NotFoundException never matches, so it treats a gone resource as an unexpected failure rather than as deleted.
Fix: the not-found refusal in the ListTagsForResource handler (and the tagging-path error mapping it shares) must emit code NotFoundException with the message "Resource was not found", distinct from the control-plane ops' ResourceNotFoundException / "Resource not found.".
Traces: oam.link-create-with-sink-policy-full-lifecycle.

--- Cause 5 of 8: ListAttachedLinks with a malformed SinkIdentifier returns BadRequestException instead of AccessDeniedException ---
AWS: ListAttachedLinks is authorized against the sink resource ARN BEFORE the service's own input validation runs, so a SinkIdentifier that cannot match the resource pattern (e.g. "not!a!valid!identifier") is refused by the IAM resource-matching path as error code AccessDeniedException, with the standard explicit-deny message template: `User: <caller-arn> is not authorized to perform: oam:ListAttachedLinks on resource: <sink-resource-arn-pattern> with an explicit deny in a resource-based policy`. Fixed text: `User: `, ` is not authorized to perform: oam:`, ` on resource: `, ` with an explicit deny in a resource-based policy`. Variable parts: the caller's own principal ARN, the action name, and the resource ARN scope (arn:aws:oam:<region>:<account>:sink/*) — all derived from the request/caller, never literal values from one run. Recorded behavior only: AccessDeniedException is not modeled for ListAttachedLinks (Smithy errors: InternalServiceFault 500, InvalidParameterException 400, MissingRequiredParameterException 400, ResourceNotFoundException 404). The neighbouring cases the same check asserts DO pass: a well-formed but absent sink ARN is ResourceNotFoundException with "Resource not found.", and a real empty sink returns a well-formed empty Items page.
Emulator: returns error code BadRequestException from the centralized request-shape/pattern validation, so the authorization boundary is never reached.
Why: a client cannot tell "you are not permitted to read this sink" from "your request was malformed"; permission-diagnostic and retry logic branches the wrong way, and the three "nothing here" shapes (empty page / absent sink / not permitted) collapse into two.
Fix: authorization/resource-matching for ListAttachedLinks must be evaluated ahead of the SinkIdentifier pattern validation in that operation's request walk, emitting AccessDeniedException with the explicit-deny message template above.
Traces: oam.link-visible-in-attached-links-and-removed-after-delete.

--- Cause 6 of 8: TagResource with a malformed (non-oam) ARN returns ValidationException instead of BadRequestException ---
AWS: TagResource with a ResourceArn that is not an oam ARN at all (e.g. "not-an-oam-arn") is refused with error code BadRequestException and the fixed message "Invalid input resource arn: bad syntax" (no variable parts — the offending ARN is NOT echoed). Nothing is mutated: a real sink's tag set is unchanged, and the identical Tags payload against the real sink's ARN still succeeds. Recorded behavior only: the Smithy model binds ResourceArn with pattern ^arn:(\w|-)+:oam:.+:.+:.+ and models TagResource errors as ResourceNotFoundException 404, TooManyTagsException 400, ValidationException 400 — BadRequestException is not modeled, so the recording is the requirement for this path.
Emulator: the centralized pattern validation refuses it as error code ValidationException (with a message from the generic validation walk, not AWS's text).
Why: a client distinguishing "this ARN is syntactically not an OAM ARN" from "this parameter value is invalid" mis-routes the failure, and any assertion on the documented message text fails.
Fix: the ResourceArn syntax refusal for the tagging operations must map to code BadRequestException with the message "Invalid input resource arn: bad syntax" rather than the generic ValidationException produced by the shared pattern validation.
Traces: oam.tag-resource-invalid-arn-effect-absent.

--- Cause 7 of 8: TagResource/UntagResource do not reject keys in the reserved aws: namespace ---
AWS: tag keys in the reserved `aws:` namespace are not customer-settable, matched CASE-INSENSITIVELY (so "AWS:...", "Aws:..." and "aws:..." are all refused). TagResource with such a key is refused with error code BadRequestException and the fixed message "Invalid tag key. Customers cannot set tag keys starting with aws: (case insensitive)"; UntagResource of such a key is refused with BadRequestException and the DISTINCT fixed message "Invalid tag key. Customers cannot remove tag keys starting with aws: (case insensitive)" (set vs remove — both messages are entirely fixed text, no variable parts). Neither refusal changes the resource's tag set as seen by GetSink(IncludeTags=True) or ListTagsForResource, and an ordinary key is accepted immediately afterwards. Recorded behavior only: the model has no reserved-prefix constraint on TagMapInput keys.
Emulator: TagResource(ResourceArn=<sink arn>, Tags={"AWS:sim2real": "v"}) returns HTTP 200 with an empty body and STORES the reserved key — services/service-com-amazonaws-oam-oamservice/src/ops/tag_resource.rs validates only the resulting tag COUNT and then upserts every key unconditionally. The UntagResource half of this rule cannot be observed at all because that operation is still an unimplemented scaffold stub (see the already-filed issue referenced above).
Why: a client (or an emulated AWS-managed-tag flow) can plant keys in a namespace AWS reserves, so tag-based access control and any aws:-prefixed system tags become forgeable, and a client expecting the refusal treats the write as accepted.
Fix: a reserved-prefix key check in the tagging validation shared by the TagResource and UntagResource handlers, case-insensitive on the `aws:` prefix, raising BadRequestException with the set/remove message above before any key is written or removed.
Traces: oam.tag-resource-reserved-aws-prefix-rejected.

--- Cause 8 of 8: TagResource past the 50-tag ceiling returns TooManyTagsException instead of BadRequestException, with the wrong message ---
AWS: pushing a resource's resulting tag set past 50 user tags is refused with error code BadRequestException and the fixed message "The resultant tag set must not have more than 50 user tags." (no variable parts — neither the resulting count nor the limit is interpolated). The refusal leaves the existing 50 tags exactly as they were, and freeing a slot with UntagResource lets the new key be added. Recorded behavior only for the CODE: the Smithy model does model TooManyTagsException (400, "A resource can have no more than 50 tags") for TagResource, but the recording shows AWS answering this path with BadRequestException, so the recorded code/message is the requirement.
Emulator: returns error code TooManyTagsException with its own prose message `these tags would leave the resource holding <n> tags, and a resource can have no more than 50 tags` (tag_resource.rs, the MAX_TAGS_PER_RESOURCE branch) — a different code and a message whose count is interpolated from state where AWS's text is fixed. The effect-absence and the 50-tag fill themselves behave correctly.
Why: a client that catches the tag-quota refusal by code never matches, so a predictable quota rejection surfaces as an unhandled error instead of a retry-after-untag path.
Fix: the resulting-tag-count ceiling check in the TagResource handler must emit BadRequestException with the exact fixed message above instead of TooManyTagsException with interpolated prose.
Traces: oam.tag-resource-too-many-tags-rejected.
