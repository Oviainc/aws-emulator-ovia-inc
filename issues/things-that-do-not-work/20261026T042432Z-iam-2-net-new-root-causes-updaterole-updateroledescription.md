# iam: 2 net-new root causes — UpdateRole/UpdateRoleDescription refuse a legal description change on a service-linked role, and maxSessionDuration/description ValidationError messages echo the rejected value

> _Note: this issue was identified against the code base at commit `ceb741ee79af2c0788f14c9e582177f56ff0f4dd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateRole

## Description
Two distinct net-new root causes in the bootstrapped `iam` service. Neither failing check is marked ALREADY FILED or OWNED in the replay report. A fixer must close BOTH before submitting.

Cause 1 of 2: UpdateRole (and UpdateRoleDescription) refuse a Description-only change on a service-linked role with UnmodifiableEntity, and the refusal text is generated prose.
AWS: Smithy UpdateRole input is RoleName (roleNameType, required, length 1-64, pattern ^[\w+=,.@-]+$), Description (roleDescriptionType, string length 0-1000) and MaxSessionDuration (roleMaxSessionDurationType, integer range 3600-43200); UpdateRoleDescription takes RoleName + Description, both required. Both operations model UnmodifiableEntityException (awsQueryError code `UnmodifiableEntity`, HTTP 400), whose model documentation reads "The request was rejected because service-linked roles are protected Amazon Web Services resources. Only the service that depends on the service-linked role can modify or delete the role on your behalf." That protection covers the service-linked role's permissions and its lifecycle, NOT its Description: the description is the documented, deliberately mutable field on an SLR, so UpdateRole(RoleName=<slr>, Description=...) and UpdateRoleDescription(RoleName=<slr>, Description=...) both return a 2xx and GetRole reads the new Description back. Recorded behavior: the check creates a real service-linked role via CreateServiceLinkedRole(AWSServiceName=autoscaling.amazonaws.com, CustomSuffix=<suffix>), sets its description through UpdateRole and then through UpdateRoleDescription, asserting GetRole echoes each value, and only AFTER that asserts the genuinely protected paths (DeleteRolePermissionsBoundary and a plain DeleteRole) are refused UnmodifiableEntity 400 with AWS's fixed text "Cannot perform the operation on the protected role '<roleName>' - this role is only modifiable by AWS" — fixed text apart from <roleName>, which comes from the request.
Emulator: the very first UpdateRole is refused. HTTP 400, code `UnmodifiableEntity`, message "Service role AWSServiceRoleForAutoScaling_<customSuffix> cannot be modified: it is a service-linked role, so the change must be requested through autoscaling.amazonaws.com". Two things diverge: (a) a call AWS accepts is refused, so the check never reaches the protected-path legs at all; (b) the message is synthesized prose — the fixed text AWS uses for this error class on a protected role is "Cannot perform the operation on the protected role '<roleName>' - this role is only modifiable by AWS" (only the quoted role name is request-derived), whereas the emulator invents a sentence that additionally interpolates the owning service principal (autoscaling.amazonaws.com), which AWS does not put in this message.
Why: a client cannot label or re-document a service-linked role at all — every console/IaC description edit on an SLR fails with a 400 that looks like a permanent protection error, so retry/branch logic treats a legal field as immutable. Clients and runbooks that match AWS's exact protected-role text to decide "this role is AWS-managed, skip it" also never match, and the emulator's wording leaks the owning service into an error surface AWS keeps generic.
Fix: the iam role-update handlers — services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/update_role.rs and src/ops/update_role_description.rs — must permit a Description change on a role recognised as service-linked (path /aws-service-role/<servicePrincipal>/) while continuing to refuse MaxSessionDuration and permission/lifecycle changes, and the UnmodifiableEntity message must be AWS's constant. The same constant is used by src/ops/delete_role.rs and src/ops/delete_role_permissions_boundary.rs for the protected-role refusal; the check never reached those legs, so their text is unverified by this replay and should be aligned with the same constant rather than assumed correct. Note: the open issue 20261025T000319Z-iam-updaterole-stub.md ("Implement iam UpdateRole: unimplemented scaffold stub") is stale — UpdateRole now answers (it validated MaxSessionDuration and refused this SLR call), so this is a behavioral defect in a live handler, not a stub.
Traces: iam.service-linked-role-unmodifiable-enforced.

Cause 2 of 2: the ValidationError message for an out-of-range MaxSessionDuration (and an over-length Description) interpolates the rejected value where AWS omits it.
AWS: roleMaxSessionDurationType is `integer` with @range min 3600, max 43200; roleDescriptionType is `string` with @length min 0, max 1000. A request that reaches IAM with a value outside those bounds is refused with error code `ValidationError` / HTTP 400, and the message is built from the request by a fixed rule: "N validation error(s) detected: Value at '<member>' failed to satisfy constraint: Member must <constraint>". For these members AWS does NOT interpolate the offending value, and the constraint clause is taken from the model's bound. So the required messages are "1 validation error detected: Value at 'maxSessionDuration' failed to satisfy constraint: Member must have value greater than or equal to 3600" (under the minimum, including 0), "... Value at 'maxSessionDuration' failed to satisfy constraint: Member must have value less than or equal to 43200" (over the maximum) and "... Value at 'description' failed to satisfy constraint: Member must have length less than or equal to 1000". The fixed text is everything except the member name ('maxSessionDuration' / 'description') and the numeric bound (3600 / 43200 / 1000), which come from the model; the error count comes from how many members failed.
Emulator: the same code and status, but the message inserts the rejected value: "1 validation error detected: Value '3599' at 'maxSessionDuration' failed to satisfy constraint: Member must have value greater than or equal to 3600". The under-bound and over-bound variants and the stored-value-unchanged legs are otherwise correct, so this is purely the message template.
Why: the member name plus the constraint clause is the part clients parse to map a refusal onto a form field; a message carrying an extra synthesized `Value '<x>' ` segment does not match AWS's rule, breaks exact-match assertions and echoes caller input straight back into an error surface AWS deliberately keeps value-free.
Fix: the shared constraint-violation message builder used by the role handlers in services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/ (reached from update_role.rs and create_role.rs — the check asserts the same message on CreateRole with MaxSessionDuration=43201). This is the same root cause the open issue 20261025T000319Z-iam-9-net-new-behavioral-root-causes-cloudformation.md records as its cause 7 for the 'tags' and 'sessionDuration' members; the replay report did not attribute this check to that issue, so it is filed here — fixing the one shared builder closes both.
Traces: iam.role-session-duration-and-description-bounds-rejected.
