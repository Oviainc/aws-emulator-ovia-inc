# ACM ACME surface: newAccount still 501 for 12 more contracts, newNonce casing blocks a 13th, and four conflict-refusal messages are hand-written instead of ACM's (6 causes)

> _Note: this issue was identified against the code base at commit `c8d80ea15f1454d07f388eb2b932b3a5430349f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAcmeEndpoint

## Description
Six distinct root causes in ACM's ACME surface (control plane + the ACME data plane it fronts), each grounded in failing behavioral checks of this suite that are NOT carried as replay keys by any open issue.

Cause 1 of 6: every ACME JWS POST to an endpoint's newAccount resource is answered HTTP 501 with problem type urn:ietf:params:acme:error:serverInternal, so no ACME account can be registered and twelve FURTHER account-lifecycle contracts are unreachable.
AWS: recorded behavior only for the ACME wire (the ACME data plane is not a modelled Smithy operation; RFC 8555 §7.3). A correctly-signed JWS POST to directory['newAccount'] with payload {"termsOfServiceAgreed": true, "contact": [...]} is answered 200/201 with a Location header carrying the new account URL, preceded on an endpoint that requires an external account binding by HTTP 400 type urn:ietf:params:acme:error:externalAccountRequired until the HS256 externalAccountBinding JWS built from GetAcmeExternalAccountBindingCredentials' KeyId/MacKey is attached. The control-plane operations that read the resulting state ARE modelled: DescribeAcmeAccount(AcmeEndpointArn, AccountUrl) -> AcmeAccount @readonly, RevokeAcmeAccount(AcmeEndpointArn, AccountUrl) -> Unit @idempotent, ListAcmeAccounts @paginated(items=AcmeAccounts), all with errors AccessDeniedException(403)/ConflictException(400)/InternalServerException(500)/ResourceNotFoundException(400)/ThrottlingException(400)/ValidationException(400).
Emulator: the POST is answered HTTP 501 {"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501} and no Location header; only the directory (GET) and newNonce (HEAD/GET) resources are served, and no JWS signature, nonce or external-account binding is ever verified.
Why: 501/serverInternal tells an ACME client (certbot, lego, acme.sh) the CA itself is broken, so it retries or aborts instead of branching on the problem type. Because no account URL can be minted, a caller cannot observe any of the twelve contracts these checks pin: DescribeAcmeAccount returning Status=VALID with the right AcmeExternalAccountBindingArn linkage and the account appearing in ListAcmeAccounts; RevokeAcmeAccount moving an account to the terminal REVOKED state, being idempotent on a second call (no ConflictException) and single-winner/idempotent under two concurrent racers; DescribeAcmeAccount on a REVOKED account answering with Status=REVOKED rather than ResourceNotFoundException; the account identity being the ACME account key rather than the external-account binding (a second newAccount with the same key must return the SAME account URL); a contact-less registration being accepted by a Contact=NOT_REQUIRED endpoint and refused by a Contact=REQUIRED one; and a newAccount whose externalAccountBinding MAC is forged being rejected while the genuine MacKey is accepted — a security boundary that currently cannot be shown to exist at all.
Fix: the ACME data-plane handler, services/service-com-amazonaws-acm-certificatemanager/src/service/acme_http.rs — the ("POST", AcmeResource::Jws) arm of AcmeHttpSurface::serve routes to not_implemented(). Implement newAccount there (JWS verification, single-use nonce store, EAB HS256 verification keyed by the binding's KeyId/MacKey, externalAccountRequired(400) when the endpoint demands a binding, account record minted with a Location URL), and back the control-plane handlers in services/service-com-amazonaws-acm-certificatemanager/src/ops/ (describe_acme_account.rs, revoke_acme_account.rs, list_acme_accounts.rs) with that account state. Related open issues record the SAME 501 arm but gate only four other checks, so neither closes these twelve: 20261027T001842Z-acm-acme-data-plane-newaccount-answers-http-501.md (3 replay keys) and 20261026T043337Z-acm-acme-account-surface-diverges-in-two-places.md (its Cause 2, 1 replay key).
Traces: acm.acme-account-describe-list, acm.acme-account-double-revoke-is-idempotent, acm.acme-account-identity-is-the-account-key-not-the-binding, acm.acme-account-revoke-lifecycle, acm.acme-account-revoke-terminal-transition, acm.acme-account-revoke-transitions-state, acm.acme-contact-required-endpoint-refuses-a-registration-without-contact, acm.acme-new-account-with-a-forged-eab-mac-rejected, acm.concurrent-revoke-acme-account-idempotent-terminal, acm.concurrent-revoke-acme-account-single-winner, acm.describe-acme-account-revoked-status-not-notfound, acm.revoke-already-revoked-acme-account-is-idempotent.

Cause 2 of 6: the newNonce answer's nonce field reaches the client lower-cased, so a client that reads field names as received never gets a nonce and cannot sign a single JWS.
AWS: recorded behavior only (not a modelled operation). RFC 8555 §7.2 spells the field Replay-Nonce and requires it on the 200 answer to HEAD <newNonce> and the 204 answer to GET <newNonce>; AWS's ACM ACME endpoints serve that exact spelling.
Emulator: statuses are right (200 for HEAD, 204 for GET) and the nonce is fresh per request, but the field arrives spelled replay-nonce, so this check's registration helper — which does NOT lower-case the names it reads — finds nothing and fails with "no Replay-Nonce returned from newNonce (status=204)" before any POST.
Why: an ACME client takes its first nonce from newNonce and can send no JWS without it; against the emulator it wedges before the first POST, so every downstream ACME contract is unreachable for a reason unrelated to the implementation behind it.
Fix: the response-writing seam for this surface must preserve the canonical field spelling; services/service-com-amazonaws-acm-certificatemanager/src/service/acme_http.rs already states the canonical name. Open issue 20261027T102721Z-acm-acme-newnonce-emits-a-lower-cased-replay-nonce-field-name.md describes this same cause (with a vendor blocker) but carries only acm.update-acme-endpoint-on-revoked-account-succeeds as a replay key, so it does not gate the check below.
Traces: acm.revoke-acme-account-sets-terminal-state.

Cause 3 of 6: the ConflictException raised when an idempotency token is reused with different request parameters carries a hand-written, resource-naming message instead of ACM's fixed text.
AWS: Smithy CreateAcmeEndpoint(IdempotencyToken @idempotencyToken, AuthorizationBehavior required, Contact default REQUIRED, CertificateAuthority required, Tags) and CreateAcmeExternalAccountBinding(IdempotencyToken @idempotencyToken, AcmeEndpointArn required, RoleArn required) both model ConflictException (client, HTTP 400). Recorded behavior: replaying a token with identical parameters is a no-op returning the SAME ARN, while replaying it with DIFFERENT parameters is refused 400 ConflictException with the message exactly 'Idempotency token was already used with different request parameters' — the whole message is fixed text, with no resource id, ARN or parameter name interpolated.
Emulator: code ConflictException and status 400 are correct, but the message is 'the idempotency token of this request already created ACME endpoint <endpoint-arn>, with different parameters' (and, for the binding, 'the idempotency token of this request already created ACME external account binding <eab-arn>, with different parameters') — lower-cased prose with the created resource's ARN interpolated, where AWS interpolates nothing.
Why: the text is produced by a fixed rule, so the rule is the requirement; a client or test that matches ACM's idempotency-conflict message (the only way to distinguish token reuse from any other ConflictException, since the code is shared) never matches, and the emulator additionally leaks the identifier of a resource the caller's mismatched request did not create.
Fix: the ConflictException construction in the idempotency-token path of the ACME create handlers, services/service-com-amazonaws-acm-certificatemanager/src/ops/create_acme_endpoint.rs and .../create_acme_external_account_binding.rs (or the shared idempotency helper they call).
Traces: acm.acme-endpoint-duplicate-create-conflicts, acm.create-acme-endpoint-duplicate-name-conflict, acm.create-acme-external-account-binding-duplicate-key-conflict, acm.delete-acme-endpoint-with-active-validations-conflict.

Cause 4 of 6: the duplicate-domain ConflictException from CreateAcmeDomainValidation is worded as an endpoint/validation-ARN report instead of ACM's domain-named sentence.
AWS: Smithy CreateAcmeDomainValidation(AcmeEndpointArn required, DomainName required @pattern ^([a-z0-9]([a-z0-9-]*[a-z0-9])?\.)*[a-z0-9]([a-z0-9-]*[a-z0-9])?$, PrevalidationOptions required) models ConflictException (client, 400). Recorded behavior: a second validation for a domain that already has one on the same endpoint is refused 400 ConflictException with 'An ACME domain validation for <DomainName> already exists.' — fixed text around one variable part, the DomainName taken from the request, terminated by a period.
Emulator: code and status are right, message is 'ACME endpoint <endpoint-arn> already has domain validation <domain-validation-arn> for domain <DomainName>' — different fixed text, two extra interpolated ARNs from state, and no terminating period.
Why: a client branching on ACM's duplicate-validation text cannot recognise the refusal, and the emulator exposes the pre-existing validation's ARN in a refusal where AWS names only the domain the caller submitted.
Fix: the duplicate-detection refusal in services/service-com-amazonaws-acm-certificatemanager/src/ops/create_acme_domain_validation.rs.
Traces: acm.create-acme-domain-validation-duplicate-domain-rejected, acm.create-acme-domain-validation-duplicate-rejected, acm.duplicate-domain-validation-rejected.

Cause 5 of 6: the ValidationException that guards UpdateAcmeDomainValidation while the record is VALIDATING carries the wrong message.
AWS: Smithy UpdateAcmeDomainValidation(AcmeDomainValidationArn required, PrevalidationOptions) @idempotent models ValidationException (client, 400). Recorded behavior: updating a validation whose Status is still VALIDATING is refused 400 ValidationException with exactly 'Cannot update ACME domain validation in VALIDATING status.' — all fixed text except the status name, which comes from the resource's state.
Emulator: code ValidationException and status 400 are correct; the message is 'An ACME domain validation that is VALIDATING cannot be updated. Wait for the previous operation to finish and try again.'
Why: the message is generated by a known rule from the resource's state, so the rule is the requirement; retry logic and tests that key on ACM's sentence do not match, and the two texts are not interchangeable for a client that classifies by message because ValidationException is ACM's catch-all code here.
Fix: the VALIDATING-state guard's error construction in services/service-com-amazonaws-acm-certificatemanager/src/ops/update_acme_domain_validation.rs.
Traces: acm.acme-domain-validation-full-lifecycle.

Cause 6 of 6: two UpdateAcmeDomainValidation calls racing a SETTLED validation make the loser fail with the VALIDATING ValidationException instead of ACM's concurrency ConflictException.
AWS: Smithy UpdateAcmeDomainValidation models both ConflictException and ValidationException (client, 400). Recorded behavior: with the record already in a terminal status (VALID/INVALID), two concurrent updates each either succeed or lose with ConflictException whose message is 'Concurrent modification of ACME domain validation <AcmeDomainValidationArn>. Please try again.' — fixed text around the request's ARN; at least one racer succeeds and the final DomainScope equals one winner's scope in full.
Emulator: the losing racer is refused with code ValidationException and message 'An ACME domain validation that is VALIDATING cannot be updated. Wait for the previous operation to finish and try again.', i.e. the wrong error class entirely, reported for a record the check had already polled into VALID/INVALID before racing.
Why: ConflictException is the retryable optimistic-concurrency signal; ValidationException is a terminal request defect, so a client that retries on conflict and gives up on validation errors abandons an update AWS would have let it retry — and the message asserts a state the resource is not in.
Fix: the concurrency/locking path of services/service-com-amazonaws-acm-certificatemanager/src/ops/update_acme_domain_validation.rs: distinguish a concurrent in-flight update (ConflictException with the concurrent-modification text) from the VALIDATING precondition (Cause 5), instead of collapsing both onto the status guard.
Traces: acm.concurrent-update-acme-domain-validation-conflict.
