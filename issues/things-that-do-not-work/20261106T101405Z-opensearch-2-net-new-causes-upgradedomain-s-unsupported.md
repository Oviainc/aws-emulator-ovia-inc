# opensearch: 2 net-new causes — UpgradeDomain's unsupported-path refusal strips the OpenSearch_ prefix from TargetVersion, and CreateDomain accepts FGAC with InternalUserDatabaseEnabled=true and no MasterUserOptions (2 causes)

> _Note: this issue was identified against the code base at commit `dac07326602f9aba95bf6def628915eb769a9227`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpgradeDomain

## Description
Two net-new root causes in the opensearch service crate, each with its own failing check ids. Cause 1 is a refusal-wording divergence (status and error code are right, the sentence is not); cause 2 is missing request validation, where the emulator ACCEPTS a CreateDomain request AWS refuses.

Cause 1 of 2 — UpgradeDomain: the unsupported-upgrade-path refusal renders an OpenSearch_X.Y target with its engine prefix stripped.
AWS: Smithy: UpgradeDomain (POST /2021-01-01/opensearch/upgradeDomain) input TargetVersion is a required VersionString, length 14..18, pattern ^Elasticsearch_[0-9]{1}\.[0-9]{1,2}$|^OpenSearch_[0-9]{1,2}\.[0-9]{1,2}$; the operation declares BaseException (errorKind client, httpError 400, defaulted) alongside ValidationException. Recorded behavior: a TargetVersion that is not an advertised forward target of the domain's current engine (GetCompatibleVersions does not list it) is refused with error code BaseException, HTTP 400, no state change (DescribeDomain still reports the original EngineVersion), and the message "Failed to submit upgrade. Upgrade from <source> to <target> not supported." Fixed text: "Failed to submit upgrade. Upgrade from ", " to ", " not supported.". Variable parts, both taken from the request and the domain's state: <source> is the domain's current EngineVersion as declared (OpenSearch_2.11 / OpenSearch_2.13 in the two recordings) and <target> is the requested TargetVersion rendered in AWS's legacy engine-version form — an OpenSearch engine keeps its OpenSearch_ prefix (TargetVersion=OpenSearch_1.0 renders as OpenSearch_1.0), while an Elasticsearch engine is rendered bare (TargetVersion=Elasticsearch_7.10 renders as 7.10, as recorded on the earlier check opensearch.domain-upgrade-lifecycle). The version values themselves are per-run inputs, not part of the template; the PREFIX RULE is the requirement.
Emulator: the same calls answer the right code (BaseException) but render the target with every engine prefix removed: "Failed to submit upgrade. Upgrade from OpenSearch_2.11 to 1.0 not supported." and "Failed to submit upgrade. Upgrade from OpenSearch_2.13 to 1.0 not supported." — the OpenSearch_ prefix is stripped, so the sentence names a version string AWS never emits and that does not even match the VersionString pattern.
Why: a client or operator that matches the documented refusal sentence for an unsupported upgrade path (log matching, alarm rules, test assertions distinguishing "unsupported target" from the other BaseException classes of this operation, such as the background-tasks refusal) never matches, and a caller reading the message cannot tell which engine family it asked for.
Note: the resolved issue 20261103T073642Z-opensearch-ten-control-plane-divergences-six-refusal-messages.md (cause 4) covered the Elasticsearch_7.10 recording of this message and does not carry these two replay keys, so it does not cover them: its fix generalised prefix-stripping to ALL targets instead of only the Elasticsearch_ form, which is what these two checks now observe.
Fix: the message rendering on the unsupported-path branch of UpgradeDomain — the helper crate::state::incompatible_target_version used at services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/upgrade_domain.rs lines 217-228, defined in that crate's src/state.rs: render the target in AWS's legacy engine-version form (strip only a leading "Elasticsearch_", keep "OpenSearch_" intact) and leave the source version as declared.
Traces: opensearch.domain-upgrade-invalid-target-version-rejected, opensearch.upgrade-domain-incompatible-version-rejected

Cause 2 of 2 — CreateDomain accepts fine-grained access control with the internal user database enabled but no master user supplied.
AWS: Smithy: CreateDomain.AdvancedSecurityOptions (AdvancedSecurityOptionsInput) carries Enabled, InternalUserDatabaseEnabled and MasterUserOptions; MasterUserOptions.MasterUserName ("Only specify if InternalUserDatabaseEnabled is true") and MasterUserPassword ("Only specify if InternalUserDatabaseEnabled is true") are the internal-database master credentials, and CreateDomain declares ValidationException (errorKind client, httpError 400). Recorded behavior: CreateDomain with AdvancedSecurityOptions {Enabled: true, InternalUserDatabaseEnabled: true} and NO MasterUserOptions — all three FGAC prerequisites satisfied (EncryptionAtRestOptions.Enabled=true, NodeToNodeEncryptionOptions.Enabled=true, DomainEndpointOptions.EnforceHTTPS=true), so nothing else is in question — is refused with ValidationException / HTTP 400, and the effect is absent: no domain is provisioned, and DescribeDomain on that name answers ResourceNotFoundException. The refusal names the missing master-user credentials; the check asserts the code and the absent effect, not the sentence. Hypothesis: AWS words it as a "you must provide master user credentials when the internal user database is enabled" sentence — treat the exact wording as unverified here, but it must be a ValidationException that names the missing MasterUserOptions.
Emulator: the request is ACCEPTED — CreateDomain returns a 200 DomainStatus (observed DomainId 000000000000/sim2real-behav-os-ebf470d656) and the domain exists, so no refusal is produced at all. The sibling negatives of the same check (FGAC without encryption at rest / without node-to-node encryption / without EnforceHTTPS) ARE refused, so only this prerequisite of AdvancedSecurityOptions is unvalidated.
Why: a caller gets a domain AWS would never create — FGAC with the internal user database on and no administrator, i.e. a domain whose security plugin has no master credential to authenticate against. Infrastructure validation, policy-as-code tests and CloudFormation rollbacks that rely on this refusal pass against the emulator and fail against AWS, and the emulated domain's stored AdvancedSecurityOptions describe a configuration that cannot exist.
Fix: the AdvancedSecurityOptions validator in the CreateDomain handler, services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/create_domain.rs — require MasterUserOptions (MasterUserName + MasterUserPassword) whenever Enabled=true and InternalUserDatabaseEnabled=true, refuse with ValidationException before any domain record is written, and share the rule with UpdateDomainConfig.
Traces: opensearch.overly-permissive-fgac-requires-encryption-and-https
