# cloudformation__mailmanager: CreateStack refuses every AWS::SES::MailManager* resource type as unrecognized, so no MailManager estate can be deployed from a template

> _Note: this issue was identified against the code base at commit `2061b56961bdd6ee54cec665a2a7c785cb8cb220`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template resource-type registry does not know the AWS::SES::MailManager* resource types, so template validation rejects the stack before any resource is provisioned. The five types the behavioral checks declare are AWS::SES::MailManagerAddressList, AWS::SES::MailManagerArchive, AWS::SES::MailManagerRelay, AWS::SES::MailManagerRuleSet and AWS::SES::MailManagerTrafficPolicy. Failing checks: cloudformation__mailmanager.deploy-mailmanager-addresslist-archive-relay-functional, cloudformation__mailmanager.deploy-mailmanager-duplicate-address-list-name-rejected, cloudformation__mailmanager.deploy-mailmanager-ruleset-and-trafficpolicy-functional.

AWS: CloudFormation accepts all five AWS::SES::MailManager* types (documented at https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/aws-resource-ses-mailmanageraddresslist.html and the sibling archive/relay/ruleset/trafficpolicy pages). CreateStack returns a StackId, the stack settles CREATE_COMPLETE, and each resource is created through the MailManager control plane: AWS::SES::MailManagerAddressList -> CreateAddressList (Smithy: input AddressListName required, @length 1-255, @pattern ^[a-zA-Z0-9_.-]+$; output AddressListId required), AWS::SES::MailManagerArchive -> CreateArchive (ArchiveName required @length 1-64; Retention ArchiveRetention; output ArchiveId), AWS::SES::MailManagerRelay -> CreateRelay (RelayName, ServerName, ServerPort @range 1-65535 and Authentication all required; output RelayId), AWS::SES::MailManagerRuleSet -> CreateRuleSet (RuleSetName and Rules required, Rules @length 0-40; output RuleSetId), AWS::SES::MailManagerTrafficPolicy -> CreateTrafficPolicy (TrafficPolicyName @length 3-63, PolicyStatements and DefaultAction required; output TrafficPolicyId). Ref on each resource yields the service id returned by the matching Create call, and the documented GetAtt attributes (AddressList.AddressListArn, Archive.ArchiveArn, Archive.ArchiveState, Relay.RelayArn, RuleSet.RuleSetArn, TrafficPolicy.TrafficPolicyArn) resolve to the values the matching MailManager Get* / List* operations report, so the stack Outputs and the MailManager reads agree. Stack-level tags propagate to each taggable MailManager resource and are visible through ListTagsForResource. On DeleteStack each resource is removed via its Delete* operation: the address list, relay, rule set and traffic policy then answer their modeled ResourceNotFoundException refusals, while a deleted archive still reads back with ArchiveState PENDING_DELETION. Where a create is refused by MailManager, CloudFormation fails that logical resource and rolls the stack back to ROLLBACK_COMPLETE, carrying the service refusal verbatim in the CREATE_FAILED event's ResourceStatusReason (for a repeated address-list name, MailManager's ConflictException — Smithy: CreateAddressList error ConflictException, httpError 409 — surfaced as 'SimpleAddressList name <AddressListName> already exists in account <accountId> (Service: MailManager, Status Code: 409, Request ID: <id>) (SDK Attempt Count: <n>)' with error code AlreadyExists; the fixed text is everything but <AddressListName>, <accountId>, <id> and <n>, which come from the request, the caller's account and the per-call attempt). Rollback deletes the resources the stack had already created, so nothing is left under the shared name.

Emulator: CreateStack never reaches provisioning. It answers 400 ValidationError with message 'Template format error: Unrecognized resource types: [<type>, ...]' listing exactly the MailManager types in the template — '[AWS::SES::MailManagerAddressList, AWS::SES::MailManagerArchive, AWS::SES::MailManagerRelay]' for the address-list/archive/relay template, '[AWS::SES::MailManagerAddressList]' for the duplicate-name template, and '[AWS::SES::MailManagerRuleSet, AWS::SES::MailManagerTrafficPolicy]' for the rule-set/traffic-policy template. No StackId is minted, so neither the happy-path reads, the GetAtt/Ref identities, the tag propagation, the delete semantics, nor the duplicate-name rollback path can be exercised at all.

Why: a client that provisions MailManager through CloudFormation (console, CDK, or any template-driven deployment) cannot deploy anything — every stack containing an address list, archive, relay, rule set or traffic policy fails at CreateStack with a template-format error, which a client reads as 'my template is malformed' rather than 'the provider is missing'. Rollback and drift behavior for these resources is likewise unreachable, so no deployment-time negative class (duplicate name conflict) can be observed either.

Fix: register the five AWS::SES::MailManager* types in CloudFormation's resource-type registry / template validator and add their provisioning handlers, mapping create/read/delete to the MailManager control plane operations above, wiring Ref to the service-minted id and the documented GetAtt attributes to the corresponding Get* fields, propagating stack tags to each resource, and surfacing a MailManager create refusal as the logical resource's CREATE_FAILED ResourceStatusReason so the stack rolls back and the rollback deletes the already-created siblings.

Traces: the three cloudformation__mailmanager deploy checks listed above; all three fail on the same CreateStack ValidationError.

## Evidence
Expected (AWS): CreateStack returns a StackId; DescribeStacks settles CREATE_COMPLETE; Outputs Ref/GetAtt match MailManager's GetAddressList/GetArchive/GetRelay/GetRuleSet/GetTrafficPolicy; stack tag sim2real propagates; DeleteStack removes each resource (archive reads back ArchiveState=PENDING_DELETION); a duplicate AddressListName fails 'Second' with code AlreadyExists and reason 'SimpleAddressList name <name> already exists in account <accountId> (Service: MailManager, Status Code: 409, Request ID: <id>) (SDK Attempt Count: <n>)' and the stack ends ROLLBACK_COMPLETE with no list left under that name.

Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::SES::MailManagerAddressList, AWS::SES::MailManagerArchive, AWS::SES::MailManagerRelay]
... Unrecognized resource types: [AWS::SES::MailManagerAddressList]
... Unrecognized resource types: [AWS::SES::MailManagerRuleSet, AWS::SES::MailManagerTrafficPolicy]
No stack is created in any of the three cases.

## Steps to Reproduce
1. cfn.create_stack(StackName=<name>, TemplateBody=<template declaring Resources of Type AWS::SES::MailManagerAddressList, AWS::SES::MailManagerArchive and AWS::SES::MailManagerRelay with Outputs using !Ref and !GetAtt AddressList.AddressListArn / Archive.ArchiveArn / Archive.ArchiveState / Relay.RelayArn>, Parameters=[names], Tags=[{Key: sim2real, Value: <name>}]).
2. Observe 400 ValidationError 'Template format error: Unrecognized resource types: [...]' instead of a StackId.
3. Repeat with a template declaring two AWS::SES::MailManagerAddressList resources that share one AddressListName (expect ROLLBACK_COMPLETE with the AlreadyExists CREATE_FAILED reason) and with a template declaring AWS::SES::MailManagerRuleSet + AWS::SES::MailManagerTrafficPolicy (expect CREATE_COMPLETE and MailManager reads matching the template); both are refused the same way.
