# secretsmanager: 5 net-new causes — CloudFormation stack delete only schedules the secret, {{resolve:secretsmanager:...}} is stored literally, ReplicaRegions stacks end DELETE_FAILED, AWS::SecretsManager::ResourcePolicy attaches nothing, and a Lambda-driven RotateSecret never promotes AWSCURRENT

> _Note: this issue was identified against the code base at commit `264726cd210189fc14dd0f74a077b22d6a361cf8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSecret

## Description
Bundle of 5 net-new root causes, all of service `secretsmanager`, grounded in behavioral checks that the replay report does not mark ALREADY FILED or OWNED. A fixer MUST close all five before submitting.

Cause 1 of 5: deleting the CloudFormation stack that owns an AWS::SecretsManager::Secret leaves the secret merely SCHEDULED for deletion instead of removing it.
AWS: Smithy (secretsmanager): DescribeSecret and GetSecretValue both model ResourceNotFoundException (client, httpError 400); DescribeSecret's output carries the optional DeletedDate member used for a secret that is only scheduled for deletion. Recorded behavior: CloudFormation's delete of an AWS::SecretsManager::Secret removes the secret outright (a force delete, no recovery window), so once the stack reaches DELETE_COMPLETE both DescribeSecret and GetSecretValue on that secret answer HTTP 400 with error code ResourceNotFoundException and message "Secrets Manager can't find the specified secret." — the whole message is fixed text with no variable parts. The contrast is part of the requirement: a direct DeleteSecret (no ForceDeleteWithoutRecovery) only SCHEDULES, leaving the secret describable with DeletedDate set; the CFN stack-delete path does not.
Emulator: after the owning stack reaches DELETE_COMPLETE, DescribeSecret still answers HTTP 200 for the secret, and GetSecretValue answers InvalidRequestException with message "You can't perform this operation on the secret because it was marked for deletion." — i.e. the stack delete was routed through the recovery-window scheduling path rather than a force delete.
Why: a client cannot tell a torn-down secret from a live one. Teardown waiters and polls for a not-found never finish, and re-deploying the same template collides with a secret name the emulator still reports as existing (within the recovery window the name cannot be reused).
Fix: the CloudFormation resource provider's delete path for AWS::SecretsManager::Secret must force-delete the secret without a recovery window, and the DescribeSecret/GetSecretValue lookups must then answer ResourceNotFoundException for it.
Note: the open issue 20261108T215449Z-secretsmanager-2-net-new-causes-a-stack-created.md describes the same behavior from the wire corpus (its Cause 2); it does not carry these behavioral check keys, so they are recorded here.
Traces: secretsmanager.deploy-cfn-delete-stack-schedules-deletion, secretsmanager.deploy-cfn-secret-generates-and-serves-value, secretsmanager.deploy-secret-cfn-stack-behaves.

Cause 2 of 5: a {{resolve:secretsmanager:...}} dynamic reference in a template property is never resolved — the literal reference text is stored as the property value.
AWS: recorded behavior only (the secretsmanager Smithy model does not describe CloudFormation dynamic references). CloudFormation resolves {{resolve:secretsmanager:<secret-arn-or-name>:SecretString:<json-key>[:<version-stage>][:<version-id>]}} at deploy time by reading the named secret version and substituting the named JSON key's value; the default (no stage, no id) is AWSCURRENT, a 5th field names a staging label, and a 6th field names a VersionId. The resolved plaintext is what the created resource holds, and it is frozen at deploy time — a later PutSecretValue on the source does not change it.
Emulator: each created secret's SecretString is the reference STRING itself, verbatim: GetSecretValue returns e.g. '{{resolve:secretsmanager:<source-arn>:SecretString:password}}', '{{resolve:secretsmanager:<source-arn>:SecretString:password:AWSPREVIOUS}}' and '{{resolve:secretsmanager:<source-arn>:SecretString:password::<version-id>}}' instead of the three referenced passwords (the arn and version id are per-run values; the defect is that no substitution happened at all, for the default, the stage selector and the version-id selector alike).
Why: every consumer of a template that injects a secret by dynamic reference receives the placeholder text instead of the credential. Nothing fails loudly: the stack reaches CREATE_COMPLETE, so the broken value is only discovered when the consumer tries to authenticate with it.
Fix: the CloudFormation template-processing stage must resolve secretsmanager dynamic references (all of default / :<stage> / ::<version-id> forms) against the Secrets Manager state before the resource provider is invoked.
Traces: secretsmanager.deploy-cfn-dynamic-reference-resolves-the-json-key-of-the-named-version.

Cause 3 of 5: a stack whose AWS::SecretsManager::Secret declares ReplicaRegions cannot be deleted — the stack ends DELETE_FAILED.
AWS: recorded behavior only for the CloudFormation side; Smithy (secretsmanager) models the replication surface this depends on (DescribeSecret output ReplicationStatus/PrimaryRegion, ReplicateSecretToRegions/RemoveRegionsFromReplication). A secret deployed with ReplicaRegions settles to replication Status 'InSync' in the named Region, serves the primary's plaintext under the same name there, receives later primary writes, and deleting the stack removes the secret from BOTH Regions, reaching DELETE_COMPLETE; DescribeSecret in either Region then answers 400 ResourceNotFoundException with "Secrets Manager can't find the specified secret."
Emulator: the stack delete reaches the terminal state DELETE_FAILED (the botocore StackDeleteComplete waiter reports: matched expected path "DELETE_FAILED"), so neither the stack nor its replicated secret is ever removed.
Why: a replicated secret becomes undeletable through its owning stack. The stack is stuck in DELETE_FAILED, the secret and its replica leak, and the name stays taken, so redeploys of the same template fail.
Fix: the CloudFormation delete path for AWS::SecretsManager::Secret must de-replicate (remove the replica Regions) and then force-delete the primary, rather than faulting the resource delete; the stack must reach DELETE_COMPLETE.
Traces: secretsmanager.deploy-cfn-replica-regions-serve-the-value-in-the-second-region-and-stack-delete-removes-both.

Cause 4 of 5: an AWS::SecretsManager::ResourcePolicy resource attaches no policy — GetResourcePolicy comes back without the policy.
AWS: Smithy: GetResourcePolicy output members are ARN, Name and ResourcePolicy (NonEmptyResourcePolicyType, @length 1..20480); its modeled errors are InvalidParameterException, InvalidRequestException and ResourceNotFoundException (all client, httpError 400). Recorded behavior: once a stack containing an AWS::SecretsManager::ResourcePolicy (SecretId + ResourcePolicy, BlockPublicPolicy true) reaches CREATE_COMPLETE, GetResourcePolicy on that secret answers HTTP 200 with ResourcePolicy present, holding the policy document the template declared, and that policy is then enforced exactly as the same document attached via PutResourcePolicy.
Emulator: GetResourcePolicy answers 200 but with NO ResourcePolicy member at all (the client raises KeyError: 'ResourcePolicy'), so the CFN-declared resource policy was silently not attached.
Why: a policy a template declares as a deny/scoping guard is absent at runtime while the stack reports success — access a client believes is denied is in fact allowed, and the policy is invisible to any audit that reads it back.
Fix: the CloudFormation resource provider for AWS::SecretsManager::ResourcePolicy must store the document on the referenced secret through the same state the PutResourcePolicy handler writes and the GetResourcePolicy serializer reads.
Note: the open issue 20261025T031105Z-secretsmanager-secrets-manager-resource-based-policies-and-the-blockpublicpolicy.md covers resource-policy EVALUATION; it does not carry this check's key, and this cause is the CFN attachment path.
Traces: secretsmanager.deploy-cfn-resource-policy-attached-enforced.

Cause 5 of 5: RotateSecret with a real, invokable Lambda rotation function never promotes a new AWSCURRENT version.
AWS: Smithy: RotateSecret takes SecretId (required), RotationLambdaARN and RotationRules, returns ARN/Name/VersionId, and models InvalidParameterException/InvalidRequestException/ResourceNotFoundException (client, 400). Recorded behavior: with a function that Secrets Manager is permitted to invoke (lambda:InvokeFunction granted to secretsmanager.amazonaws.com for the secret's ARN), RotateSecret drives the four rotation steps (createSecret, setSecret, testSecret, finishSecret) against that function; the version the function staged as AWSPENDING becomes AWSCURRENT and the pre-rotation version becomes AWSPREVIOUS, so DescribeSecret's VersionIdsToStages shows the new version under AWSCURRENT and GetSecretValue(VersionStage=AWSCURRENT) returns the rotated value while AWSPREVIOUS returns the original.
Emulator: AWSCURRENT never moves off the pre-rotation version. The check repeatedly calls RotateSecret and polls DescribeSecret and burns its whole 180 s budget without the rotation ever completing ('Check timed out after 180.0s'), i.e. the rotation function is never driven to completion and no promotion occurs.
Why: every credential-rotation flow silently never rotates. A client that rotates and then reads AWSCURRENT keeps getting the old credential, and any poll for the new version hangs until the caller's own timeout.
Fix: the RotateSecret handler must execute the rotation state machine — invoke the configured rotation Lambda for each step with SecretId/ClientRequestToken/Step and, on finishSecret, move AWSCURRENT to the token's version and AWSPREVIOUS to the old one — rather than accepting the call and leaving the staging map unchanged.
Note: several open issues describe RotateSecret not rotating in other scenarios (e.g. 20261108T035337Z-secretsmanager-5-net-new-causes-a-deferred-rotateimmediately.md for RotateImmediately=false, 20261027T052624Z-dynamodb-lambda-s3-secretsmanager-secretsmanager-rotatesecret-never-drives-a-rotation-so-awspending.md); none carries this check's key.
Traces: secretsmanager.e2e-rotate-secret-lambda-invocation-flow.
