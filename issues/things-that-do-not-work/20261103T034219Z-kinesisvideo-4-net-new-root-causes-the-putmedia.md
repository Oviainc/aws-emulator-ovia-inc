=== Cause 1 of 4: there is no /putMedia route anywhere, so every ingest session is refused 404 UnknownService instead of being acknowledged ===
AWS: recorded behavior only — PutMedia is in no SDK model (com.amazonaws.kinesisvideo#KinesisVideo_20170930 binds 32 operations, none of them PutMedia; com.amazonaws.kinesisvideomedia binds GetMedia only), and the GetDataEndpoint documentation states the returned endpoint is used to "write to it (using the PutMedia operation)". The recording shows the ingest front end as: POST /putMedia to the host GetDataEndpoint(APIName=PUT_MEDIA) minted for that stream, SigV4-signed over the literal string UNSIGNED-PAYLOAD (x-amz-content-sha256: UNSIGNED-PAYLOAD, present and signed), body sent Transfer-Encoding: chunked, request headers x-amzn-stream-name (or x-amzn-stream-arn), x-amzn-fragment-timecode-type (RELATIVE|ABSOLUTE) and x-amzn-producer-start-timestamp, and a Matroska body in which ONE Cluster is ONE fragment. The response is HTTP 200 whose body is a stream of JSON Acknowledgement objects with EventType values BUFFERING, RECEIVED and PERSISTED — one PERSISTED per accepted Cluster, carrying the service-minted FragmentNumber and that Cluster's FragmentTimecode — and no ERROR acknowledgement for an accepted container. Fixed text is the JSON member names and the EventType tokens; the variable parts are the stream name taken from the request headers, the FragmentNumber the service mints and the FragmentTimecode read from the submitted Cluster. The ingested fragments then become visible to the read plane: ListFragments, which answers an empty Fragments list before ingestion, must afterwards report exactly the ingested fragments (one per Cluster, with the span implied by the SimpleBlock spacing and the producer timestamps implied by the timecode type), GetMedia must return a Matroska document carrying the exact frame bytes written (and must honour StartSelectorType EARLIEST and FRAGMENT_NUMBER/AfterFragmentNumber), GetMediaForFragmentList must return only the named fragment, successive PutMedia sessions on the same stream must extend it monotonically, and a container-level fault (malformed EBML, a SimpleBlock on an undeclared track number, a Cluster timecode that regresses) is reported as an ERROR Acknowledgement INSIDE a 200 response rather than as an HTTP error.
Emulator: no /putMedia route exists on any host. The ingest POST is answered HTTP 404 with header x-amzn-ErrorType: UnknownService and body {"__type":"UnknownService","message":"no emulated service is registered for 'kinesisvideo'"}. Replay, from ten checks: AssertionError: PutMedia answered HTTP 404 (x-amzn-ErrorType 'UnknownService'): b'{"__type":"UnknownService","message":"no emulated service is registered for \'kinesisvideo\'"}'. Because nothing can write the fragment log, the read side stays permanently empty — the empty-stream half of list-fragments-reflects-ingestion-transition-from-empty passes (GetMedia on an empty ACTIVE stream answers 200 video/webm with zero bytes) and the post-ingestion half is never reached.
Why: the entire producer half of Kinesis Video Streams is unavailable. A client gets UnknownService, an error code Kinesis Video Streams never returns, instead of either the 200 acknowledgement stream or a modeled refusal; no fragment can ever exist, so ListFragments can only ever report an empty archive and GetMedia/GetMediaForFragmentList can only ever serve zero bytes. The create -> ingest -> read round trip that every producer SDK performs (KVS C/Java producer, GStreamer kvssink) cannot complete, and every producer-side container validation contract is silently absent rather than enforced.
Fix: the ingest data plane needs an implementation — a /putMedia route bound on the PUT_MEDIA data host, with a handler that parses the Matroska container Cluster by Cluster, appends each Cluster to the stream's fragment log in the same registry the archived-media and media read paths read from, derives each fragment's producer timestamp from the timecode type (RELATIVE = x-amzn-producer-start-timestamp plus the Cluster timecode; ABSOLUTE = the Cluster timecode as epoch milliseconds), and streams back BUFFERING/RECEIVED/PERSISTED acknowledgements; container-level faults belong in that handler's validation as ERROR acknowledgements inside the 200 stream, not as HTTP errors.

=== Cause 2 of 4: PutMedia naming a stream that does not exist must be refused 404 ResourceNotFoundException with the documented message, not UnknownService ===
AWS: recorded behavior only for the ingest front end (PutMedia is unmodeled), but the refusal identity is the control plane's modeled one: ResourceNotFoundException, httpError 404 on every kinesisvideo operation that resolves a stream (GetDataEndpoint/DescribeStream both list it). The recording shows POST /putMedia whose x-amzn-stream-name names a stream that does not exist answered HTTP 404 with header x-amzn-ErrorType: ResourceNotFoundException (optionally suffixed after a ':') and a JSON body whose Message member is exactly "The requested stream is not found or not active." — that whole sentence is fixed text with no variable part, and the stream name appears only in the request, not in the message. Nothing is archived: the stream whose discovered endpoint carried the bytes must still report an empty archive.
Emulator: the request never reaches any stream resolution, because the route does not exist; it is answered HTTP 404 with x-amzn-ErrorType: UnknownService and body {"__type":"UnknownService","message":"no emulated service is registered for 'kinesisvideo'"}. Replay: AssertionError: the refusal must be a ResourceNotFoundException, got x-amzn-ErrorType 'UnknownService'. The status happens to match (404), so a client sees the right status with the wrong error code and the wrong message.
Why: a producer that addresses a deleted or misspelled stream cannot distinguish "this stream does not exist" from "this service does not exist": UnknownService is not in kinesisvideo's error set, is not retried or branched on by any SDK, and carries no Message member, so error handling keyed on ResourceNotFoundException (re-create the stream, re-discover the endpoint) never fires.
Fix: the /putMedia handler's stream resolution — resolve x-amzn-stream-name/x-amzn-stream-arn against the kinesisvideo stream registry before accepting any container bytes and emit the 404 ResourceNotFoundException envelope with the fixed message when it does not resolve to an active stream.

=== Cause 3 of 4: an unrouted path on the control-plane host is answered with a JSON UnknownService envelope and an x-amzn-ErrorType header instead of a bare <UnknownOperationException/> body with no error-type header ===
AWS: recorded behavior only. POST /putMedia addressed to the CONTROL-plane host (which routes only the modeled control operations, each at its own path such as /getDataEndpoint and /describeStream) is refused before any operation is identified: HTTP 404, NO x-amzn-ErrorType response header at all, and a body that is exactly the bare XML element <UnknownOperationException/> — all fixed text, no variable part. Nothing is archived, so the stream's archive stays empty.
Emulator: the status is right but the envelope is not: the refusal carries x-amzn-ErrorType: UnknownService and the JSON body {"__type":"UnknownService","message":"no emulated service is registered for 'kinesisvideo'"}. Replay: AssertionError: an unrouted path is refused before any operation is identified, so no x-amzn-ErrorType header is returned; got 'UnknownService'.
Why: the front door announces a service-level fault ("no emulated service is registered for 'kinesisvideo'") for what is really an unrouted path on a service that IS serving. A client probing which host serves which plane — the exact thing endpoint discovery makes it do — reads that as "Kinesis Video is unavailable here" instead of "this operation is not on this host", and anything parsing the documented UnknownOperationException refusal shape fails to parse the JSON envelope at all. This differs from open issue 20261029T173603Z (unknown operation NAME on the control plane); here the path itself is unrouted.
Fix: the front door's unrouted-path fallback for the kinesisvideo endpoint family — it must emit the bare <UnknownOperationException/> body with no x-amzn-ErrorType header rather than falling through to the generic "no emulated service is registered" JSON envelope.

=== Cause 4 of 4: GetDataEndpoint returns the control-plane host for every APIName instead of a distinct data-plane host ===
AWS: Smithy: GetDataEndpoint (POST /getDataEndpoint, 200) takes required APIName and returns DataEndpoint; its documentation states "Gets an endpoint for a specified stream for either reading or writing. Use this endpoint in your application to read from the specified stream (using the GetMedia or GetMediaForFragmentList operations) or write to it (using the PutMedia operation)" and "The returned endpoint does not have the API name appended". The recording shows a bare http(s) origin with a host and an empty path, and that host is NOT the control-plane host the GetDataEndpoint call itself was made against — a per-stream ingest host for PUT_MEDIA and a per-stream archive host for the read APIs. Because that host serves the media APIs only, a control-plane operation is unknown there: DescribeStream against the returned endpoint is refused with error code UnknownOperationException and, as recorded, no message member at all.
Emulator: GetDataEndpoint(PUT_MEDIA) (and GET_MEDIA / LIST_FRAGMENTS) returns the same host:port the control-plane client is already talking to. Replay: AssertionError: GetDataEndpoint(PUT_MEDIA) handed back the control-plane host '<control host:port>'; the reason the call exists is that this stream's data plane lives on a different host. (The host and port in the replay output are per-run values and are not part of the requirement — the requirement is that the returned host differs from the control host and that the ingest and archive planes resolve to their own hosts.) The later assertions of this check — that a control-plane call on the data host is refused UnknownOperationException with no message, and that the discovered PUT_MEDIA endpoint actually accepts media — are not reached.
Why: endpoint discovery becomes a no-op, so a client can never be pointed at the plane that serves its call; collapsing all planes onto the control host also means a request addressed to the wrong plane is never refused, hiding the very misrouting (Cause 3) that producers rely on being told about, and any client that caches a per-API data endpoint caches a host that cannot serve it.
Fix: the GetDataEndpoint handler/serializer — mint and return a per-stream, per-plane data endpoint (one host for the ingest APIs, one for the archive/read APIs), bare origin with no path, distinct from the control-plane listener, and bind the media/archived-media routes on those hosts only.
