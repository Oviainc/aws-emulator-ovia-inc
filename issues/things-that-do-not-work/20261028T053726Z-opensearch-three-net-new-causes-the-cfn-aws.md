=== Cause 1 of 3: CloudFormation cannot provision an AWS::OpenSearchService::Domain that carries AccessPolicies, because the resource provisioner forwards the policy document as a JSON object where CreateDomain models a JSON string ===
AWS: Smithy com.amazonaws.opensearch#CreateDomain — POST /2021-01-01/opensearch/domain, success 200, output DomainStatus. Member `AccessPolicies` targets com.amazonaws.opensearch#PolicyDocument, a STRING with @length {min 0, max 102400} and @pattern '.*'. Modeled client errors: ValidationException (400), BaseException (400, defaulted), InvalidTypeException/LimitExceededException/ResourceAlreadyExistsException/DisabledOperationException (409). On AWS, the AWS::OpenSearchService::Domain resource handler accepts AccessPolicies written the normal CloudFormation way — a nested policy-document OBJECT, with intrinsics (!Sub / !Ref / !GetAtt / Fn::Sub) inside it — resolves those intrinsics, serializes the document to a JSON string and calls CreateDomain with that string. A stack declaring ClusterConfig + EBSOptions (+ optionally VPCOptions, DomainEndpointOptions, AdvancedSecurityOptions) plus an object AccessPolicies therefore reaches CREATE_COMPLETE, its Outputs are published, and DescribeDomain returns AccessPolicies as a JSON string. For a request that genuinely IS ill-typed, AWS answers one of the modeled client errors with a message naming the offending member and the expected type; it never surfaces a deserializer's internal parser text as the service message. Recorded behavior only for CloudFormation's wrapper, which the recordings show in AWS's documented resource-failure shape: `Resource handler returned message: "<service message> (Service: OpenSearch, Status Code: <status>, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: <code>)` — that frame is fixed text; <service message>, <status>, <id>, <token> and <code> are per-request values.
Emulator: the Domain resource fails at create. The resource-level reason is `Resource handler returned message: "Invalid request provided: expected string, got object start (Service: OpenSearch, Status Code: 400, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)` and the stack-level reason is `The following resource(s) failed to create: [Domain]. `. In that message, `Invalid request provided: expected string, got object start` is entirely FIXED text — it carries no value from the request and names no member; only the Request ID and RequestToken vary per run, so this is a template-level divergence and not a per-run value difference. Two things diverge: (a) a CreateDomain request real AWS accepts is refused HTTP 400, and (b) the refusal is reported with the request deserializer's internal parser text instead of a modeled client error (ValidationException/BaseException, 400) whose message names `AccessPolicies` and the expected type. Depending on the stack's OnFailure setting the consequence differs but the cause is identical: with OnFailure=DELETE the stack is removed and the follow-up DescribeStacks raises `ValidationError: Stack with id <name> does not exist` (deploy-vpc-endpoint-cfn-policy-enforced) or the StackCreateComplete waiter dies with `Matched expected service error code: ValidationError` (deploy-domain-cfn-index-operations-behave); with rollback it ends ROLLBACK_COMPLETE (vpc-endpoint-list-and-delete-lifecycle-observed).
Why: a client relying on AWS's behavior cannot deploy an OpenSearch domain through infrastructure-as-code whenever the domain has a resource policy — the normal case, since AccessPolicies is how a domain is made reachable. The stack rolls back, so no Outputs (DomainArn, DomainEndpoint, SecretArn, SubnetId, SecurityGroupId) are ever published and nothing downstream is reachable: the access-policy enforcement verdicts at the domain endpoint, the control-plane index CRUD on a deployed domain, the FGAC/Secrets-Manager dynamic-reference master credential flow, and the VPC-endpoint grant/revoke and list/delete lifecycles are all never exercised. Because the failure surfaces as a resource-handler InvalidRequest with raw parser text, an IaC user reads it as a fault in their own template and cannot tell which property is wrong.
Fix: the CloudFormation AWS::OpenSearchService::Domain resource provisioner's property-to-request mapping — after resolving intrinsics, a policy-document property must be serialized to a JSON string before it is placed in the CreateDomain body, so every forwarded member matches its modeled type. Secondarily, the OpenSearch CreateDomain input deserializer/handler must report a genuine type mismatch through a modeled client error whose message names the member and the expected type, rather than emitting its internal parser text as the service message.
Traces: opensearch.deploy-domain-cfn-access-policy-enforced, opensearch.deploy-domain-cfn-index-operations-behave, opensearch.deploy-opensearch-3-fgac-secret-master-basic-auth, opensearch.deploy-vpc-endpoint-cfn-policy-enforced, opensearch.vpc-endpoint-list-and-delete-lifecycle-observed.

=== Cause 2 of 3: a CloudFormation domain deploy that carries NO AccessPolicies produces no response at all — the chained stack-readiness and domain-readiness reads are never observed settled by a poll sized for AWS ===
AWS: recorded behavior for the latency, modeled for the shapes — CreateStack over a single AWS::OpenSearchService::Domain resource reaches CREATE_COMPLETE (DescribeStacks StackStatus), after which DescribeDomain's DomainStatus reports Created=true / Processing=false and the control-plane index APIs (CreateIndex/GetIndex, Smithy com.amazonaws.opensearch#CreateIndex -> Status 'CREATED', GetIndex -> IndexSchema) answer on that domain. Because AWS takes minutes, a client polls with AWS-sized intervals: here the CFN StackCreateComplete waiter at Delay=30/MaxAttempts=120 and then DescribeDomain at a 30 s interval with a 1200 s deadline. The contract a client depends on is simply that each terminal state is OBSERVABLE to such a poll.
Emulator: the check produces no gradeable response whatsoever — it is killed at the suite's 60 s budget with `Check timed out after 60.0s`, reporting no HTTP status, no error code and no body. This template declares only DomainName, EngineVersion OpenSearch_2.19, ClusterConfig, EBSOptions and Tags — no AccessPolicies — so cause 1 does not apply to it, and the emulator never answers either CREATE_COMPLETE+Active or an error. Hypothesis (the replay output states only the timeout, so the mechanism is inferred from the two AWS-sized waits the check chains and from the settling behaviour recorded in 20261027T004336Z-opensearch-ten-checks-never-produce-a-response-freshly.md cause 1): the stack status and/or the domain's Created/Processing transition is not reported settled on the read that immediately follows the create and then lands inside a sub-second span, so each 30 s poll interval is burned by a sample taken before the transition and two chained waits exhaust the 60 s budget before the first graded call (CreateIndex) is ever issued.
Why: a client that waits for a documented terminal state neither proceeds nor receives an error — there is no success and no failure to handle, only a hang. Everything behind the wait (that a CFN-deployed domain really accepts CreateIndex with Status=CREATED and that GetIndex reflects the requested settings/mappings) is unverifiable.
Fix: the CloudFormation stack-status progression for AWS::OpenSearchService::Domain together with the domain settling model in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs (PROVISIONING / Domain::settle), so that a resource's settled state is observable to a caller polling at AWS-sized intervals — either reported ready on the read that follows the create, or resting in its transient state long enough for one poll to sample it.
Traces: opensearch.deploy-opensearch-domain-cfn-behavioral.

=== Cause 3 of 3: DescribeDryRunProgress answers HTTP 501 NotImplemented, an error class the operation does not model ===
AWS: Smithy com.amazonaws.opensearch#DescribeDryRunProgress — GET /2021-01-01/opensearch/domain/{DomainName}/dryRun, success 200, output members DryRunProgressStatus, DryRunConfig (DomainStatus) and DryRunResults; input DomainName (@required, httpLabel, len 3..28, pattern ^[a-z][a-z0-9\-]+$), DryRunId (httpQuery dryRunId, GUID) and LoadDryRunConfig (httpQuery). Its modeled errors are ValidationException (400), BaseException (400, defaulted), DisabledOperationException (409), ResourceNotFoundException (409) and InternalException (500) — there is no 501 and no NotImplemented in that set. For a domain on which no dry run was ever started, AWS either refuses with ResourceNotFoundException/DisabledOperationException or answers 200 with a progress record that does NOT claim DryRunStatus PENDING/IN_PROGRESS/COMPLETED; it never fabricates a dry run that was not requested (recorded behavior for which of the two answers an account gets).
Emulator: the call fails with error code `NotImplemented` (HTTP 501). The handler is still a scaffold stub: services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/describe_dry_run_progress.rs carries the `//! SCAFFOLDED, NOT IMPLEMENTED` marker and its handle body returns `Err(crate::scaffolded::Scaffolded::not_implemented("DescribeDryRunProgress"))`. The replay report does NOT mark this check ALREADY FILED, and no open stub issue exists for this operation (the filed opensearch stub issues cover DeleteOutboundConnection, InsightFeedback, ListApplications, RegisterCapability, StartMigration, UpdateApplication, DeleteDirectQueryDataSource, ListDirectQueryDataSources, UpdateDirectQueryDataSource and ListMigrations only).
Why: a client cannot tell "no dry run exists here" from "this service is broken": 501/NotImplemented is outside the modeled error set, so SDK error handling written against the API (catching ResourceNotFoundException, or reading DryRunProgressStatus) never matches, and the pre-update dry-run inspection path is unusable. It also breaks the broader guarantee the check grades — that reads of never-created resources fail as genuine not-founds rather than fabricating records — for this one operation while the rest of the family (StartDomainMaintenance, GetDomainMaintenanceStatus, DescribeDataSourceAttachment, ListVpcEndpointsForDomain) behaves.
Fix: implement DescribeDryRunProgress in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/describe_dry_run_progress.rs against the domain's dry-run state (and delete the SCAFFOLDED marker): return 200 with DryRunProgressStatus for a tracked dry run, and a modeled ResourceNotFoundException (409) for a domain/DryRunId with no dry run, never 501.
