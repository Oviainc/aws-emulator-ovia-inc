# ses: 3 net-new root causes in the v1/v2 identity plane — v1 ListIdentityPolicies cannot see a SESv2-created identity policy, v1 GetIdentityDkimAttributes reports NotStarted for a v2 identity whose DKIM is PENDING, and v1 VerifyDomainIdentity starts Easy DKIM by itself

## Operation
ListIdentityPolicies

## Description
Three net-new behavioral root causes in the shared SES v1 (awsQuery) / SESv2 identity plane. None of the three failing checks below is marked ALREADY FILED or OWNED in the replay report. Related but NOT covering: the open issue 20261027T223106Z-ses-7-net-new-behavioral-root-causes-in.md (Cause 7) and 20261028T091851Z-ses-2-net-new-behavioral-root-causes-v1.md record other cross-API identity-read defects (an identity missing from v1 GetIdentityVerificationAttributes / from the v1 DkimAttributes map) and carry neither of these checks' replay keys; the *existence* side of the shared identity store now works in all three checks below (every read resolves the identity), so what remains are these three distinct state/mapping defects.

Cause 1 of 3: the identity AUTHORIZATION-POLICY store is not shared between the two APIs — a policy written with SESv2 CreateEmailIdentityPolicy is invisible to v1 ListIdentityPolicies.
AWS: SES v1 and SESv2 are two APIs over ONE set of account identities and one set of identity authorization policies. Smithy com.amazonaws.sesv2#CreateEmailIdentityPolicy binds POST /v2/email/identities/{EmailIdentity}/policies/{PolicyName} (input EmailIdentity/PolicyName @httpLabel required, Policy required; errors AlreadyExistsException 400, BadRequestException 400, LimitExceededException 400, NotFoundException 404, TooManyRequestsException 429) and success 200 with an empty body; Smithy com.amazonaws.ses#ListIdentityPolicies (input Identity required, output PolicyNames required list, NO modeled errors) therefore reports exactly the policy names attached to that identity, whichever API attached them — the v1 name list and the v2 GetEmailIdentityPolicies map are two views of one store. After the identity is deleted, v1 lists an EMPTY PolicyNames (the operation models no not-found error), and re-creating the same identity name must not resurrect the deleted policies.
Emulator: v2 CreateEmailIdentityPolicy is accepted and v2 GetEmailIdentityPolicies reports the policy, but v1 ListIdentityPolicies(Identity=<the same domain>) answers HTTP 200 with an EMPTY PolicyNames list for an identity that demonstrably carries that policy. The replay fails on the check's setup precondition ("v1 must see the v2-created policy on one shared store, got []"), so the cascade-on-delete and no-resurrection legs are never reached.
Why: a client that attaches sending authorization with the modern API and audits or reconciles it with the legacy one is told the identity has no policy at all, so a cross-account send grant looks absent (and tooling that removes "orphan" policies, or that verifies a grant before using it, takes the wrong action). The two surfaces report contradictory authorization state for one resource.
Fix: the identity-policy state the two crates read and write — SESv2 ops/create_email_identity_policy.rs (and delete/get/put siblings) in services/service-com-amazonaws-sesv2-simpleemailservice-v2 must write into the same per-account/region identity record that the ses v1 ops/list_identity_policies.rs handler reads via services/service-com-amazonaws-ses-simpleemailservice/src/state.rs, exactly as the identity records themselves are now shared; deleting an identity must drop its policies from both views.
Traces: ses.delete-email-identity-cascades-policies-and-tags.

Cause 2 of 3: v1 GetIdentityDkimAttributes reports DkimVerificationStatus 'NotStarted' for an identity whose SESv2 DKIM Status is 'PENDING' — the v1<->v2 DKIM status spelling/mapping is wrong.
AWS: Smithy com.amazonaws.ses#GetIdentityDkimAttributes (input Identities required, output DkimAttributes required map of IdentityDkimAttributes{DkimEnabled required bool, DkimVerificationStatus required enum VerificationStatus [Pending, Success, Failed, TemporaryFailure, NotStarted], DkimTokens list}) is v1's view of the SAME DKIM state SESv2 GetEmailIdentity exposes as DkimAttributes{Status: DkimStatus [PENDING, SUCCESS, FAILED, TEMPORARY_FAILURE, NOT_STARTED]}. A fresh domain identity created with SESv2 CreateEmailIdentity defaults to Easy DKIM (SigningAttributesOrigin AWS_SES, SigningEnabled true, three 32-character CNAME tokens) and Status PENDING — "the verification process was initiated, but Amazon SES hasn't yet detected the DKIM records" — so v1 must report the TitleCase mirror of it, DkimVerificationStatus 'Pending'. 'NotStarted' is v1's spelling of NOT_STARTED, which means the DKIM process was never initiated for the domain — a different state entirely.
Emulator: v1 answers 200 and the identity IS present with DkimEnabled=true and the same three tokens, but DkimVerificationStatus is 'NotStarted' while the v2 read of the same identity says Status 'PENDING' (replay: "v1 DkimVerificationStatus must mirror v2 PENDING as 'Pending', got 'NotStarted'").
Why: every Easy DKIM setup workflow polls one of the two APIs for the Pending -> Success transition. A caller polling v1 sees a state that says "nothing is in progress", so it either never starts waiting, or re-initiates DKIM, while v2 says the CNAMEs are already expected; the two APIs report mutually exclusive states for one identity.
Fix: the v1 read mapping in services/service-com-amazonaws-ses-simpleemailservice/src/ops/get_identity_dkim_attributes.rs (and the shared identity state it reads) — project the stored DKIM status onto v1's VerificationStatus enum by value (PENDING->Pending, SUCCESS->Success, FAILED->Failed, TEMPORARY_FAILURE->TemporaryFailure, NOT_STARTED->NotStarted) instead of defaulting to NotStarted.
Traces: ses.dkim-cname-token-shape-and-cross-api-identity.

Cause 3 of 3: v1 VerifyDomainIdentity by itself starts Easy DKIM — the identity it creates reads back through SESv2 with DkimAttributes.SigningEnabled=true instead of DKIM not started.
AWS: Smithy com.amazonaws.ses#VerifyDomainIdentity (input Domain required, output VerificationToken required, no modeled errors) only adds the domain identity and mints its TXT verification token; Easy DKIM is the SEPARATE VerifyDomainDkim call (output DkimTokens, three distinct tokens). A domain added with VerifyDomainIdentity alone therefore reads back through SESv2 GetEmailIdentity as IdentityType DOMAIN, VerificationStatus PENDING, VerifiedForSendingStatus false and DkimAttributes{SigningEnabled: false, Status: NOT_STARTED, Tokens: absent/empty} — "NOT_STARTED – the DKIM verification process hasn't been initiated for the domain" (sesv2 DkimStatus docs). Only after v1 VerifyDomainDkim does v2 report the three minted tokens and SigningEnabled true.
Emulator: v2 GetEmailIdentity of the v1-created domain reports DkimAttributes.SigningEnabled=true immediately after VerifyDomainIdentity, with no VerifyDomainDkim call having been made (replay: "VerifyDomainIdentity alone does not start Easy DKIM, got SigningEnabled=True"); the preceding assertions (DOMAIN, PENDING, VerifiedForSendingStatus false, and both directions of the identity read) all pass, so the single divergence is the DKIM sub-state the v1 writer stamps onto a new identity.
Why: the emulator fabricates a DKIM configuration the caller never asked for. A client that branches on SigningEnabled/Status to decide whether it still has to call VerifyDomainDkim and publish CNAMEs skips that step entirely, and then waits forever for a DKIM verification that was never initiated; auditing tooling reports domains as DKIM-signing when they are not.
Fix: the identity writer behind services/service-com-amazonaws-ses-simpleemailservice/src/ops/verify_domain_identity.rs (in that crate's shared identity state) — create the identity with its DKIM sub-state at SigningEnabled=false / NOT_STARTED and no tokens, and let only verify_domain_dkim.rs (and the SESv2 Easy-DKIM path) flip it to enabled/PENDING with the minted tokens.
Traces: ses.email-identity-v1-v2-shared-store.
