# cloudformation__emr-containers: 2 net-new root causes — AWS::EMRContainers::JobTemplate and AWS::EMRContainers::SecurityConfiguration are unregistered resource types, so CreateStack refuses the template with ValidationError

> _Note: this issue was identified against the code base at commit `71f7d99b59a9a708e54faa827e942cfeab25846d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
The emulator's CloudFormation template parser recognises no AWS::EMRContainers::* resource type beyond what is already filed, so every stack that declares one is refused outright at CreateStack time and the EMR-on-EKS resource behind it is never provisioned. Two distinct resource types are missing from the registry; each needs its own registration and its own resource handler routed at emr-containers, so each is its own cause.

Cause 1 of 2: AWS::EMRContainers::JobTemplate is not a known resource type.
AWS: recorded behavior only — resource-type registration is not expressed in the Smithy model. Real CloudFormation supports AWS::EMRContainers::JobTemplate: CreateStack accepts the template (HTTP 200 with a StackId), the stack provisions the template through emr-containers CreateJobTemplate, and Ref / Fn::GetAtt Id / Fn::GetAtt CreatedBy resolve against the created template so an independent ListJobTemplates by name reads back the declared arn and jobTemplateData.releaseLabel. When one property breaks the type's schema — JobTemplateData.ReleaseLabel against pattern ^([\.\-_/A-Za-z0-9]+|\$\{[a-zA-Z]\w*\})$ — CloudFormation's early property validation fails the resource and the stack reaches ROLLBACK_COMPLETE, emitting a VALIDATION_ERROR operation event with ValidationName=PROPERTY_VALIDATION, ValidationStatus=FAILED, ValidationFailureMode=FAIL, ValidationPath=/Resources/<logical id>/Properties/JobTemplateData/ReleaseLabel and reason 'Property value [<the supplied value>] does not match pattern: <the type's pattern>' — fixed text 'Property value [' + the rejected value from the request + '] does not match pattern: ' + the schema pattern — and no job template exists in EMR Containers afterwards. 'Template format error: Unrecognized resource types: [...]' (ValidationError, HTTP 400) is AWS's answer only for a type it genuinely does not support.
Emulator: CreateStack answers HTTP 400, error code ValidationError, message 'Template format error: Unrecognized resource types: [AWS::EMRContainers::JobTemplate]' — fixed text 'Template format error: Unrecognized resource types: [' + the unrecognised type names from the template + ']'. The stack is never created, so neither the happy-path round trip nor the property-validation rollback path is reachable.
Why: a client that deploys an EMR-on-EKS job template by template cannot create the stack at all, and a genuine property error is reported as a template-format error, so a caller cannot distinguish an unsupported resource type from a bad property value and no rollback/validation-event path can be exercised.
Fix: CloudFormation's resource-type registry and template validation must register AWS::EMRContainers::JobTemplate with its property schema (including the ReleaseLabel pattern) and route it to an emr-containers CreateJobTemplate/DeleteJobTemplate resource handler, with Ref -> arn and GetAtt Id/CreatedBy wired to the created template.
Traces: cloudformation__emr-containers.deploy-emrcontainers-jobtemplate-round-trip-and-delete, cloudformation__emr-containers.deploy-emrcontainers-jobtemplate-invalid-releaselabel-rejected-and-rolled-back.

Cause 2 of 2: AWS::EMRContainers::SecurityConfiguration is not a known resource type.
AWS: recorded behavior only. Real CloudFormation supports AWS::EMRContainers::SecurityConfiguration: CreateStack accepts the template, the resource is provisioned through emr-containers CreateSecurityConfiguration, Ref resolves to the configuration's arn and Fn::GetAtt Id to its id, and an independent ListSecurityConfigurations/DescribeSecurityConfiguration reads back the declared name, the in-transit TLS certificate configuration (certificateProviderType plus the public/private certificate secret ARNs) and the Lake Formation configuration (authorizedSessionTagValue, queryEngineRoleArn, secureNamespaceInfo), together with the template's tags. After DeleteStack and the configuration's own delete, DescribeSecurityConfiguration refuses with ResourceNotFoundException and message 'Security Configuration <id> doesn't exist.' — fixed text 'Security Configuration ' + the requested id + " doesn't exist."
Emulator: CreateStack answers HTTP 400, error code ValidationError, message 'Template format error: Unrecognized resource types: [AWS::EMRContainers::SecurityConfiguration]'. No stack and no security configuration are ever created, so the whole read-back and delete-absence path is unreachable.
Why: a client cannot declare an EMR-on-EKS security configuration in a template at all, and templates that mix it with IAM roles and Secrets Manager secrets fail at submission rather than at the resource, hiding which resource is unsupported.
Fix: CloudFormation's resource-type registry and template validation must register AWS::EMRContainers::SecurityConfiguration and route it to an emr-containers CreateSecurityConfiguration/DeleteSecurityConfiguration resource handler, with Ref -> arn and GetAtt Id wired to the created configuration.
Traces: cloudformation__emr-containers.deploy-emrcontainers-securityconfiguration-round-trip-and-delete.

Related but not covering: the open issue 20261109T160052Z-cloudformation-eks-emr-containers-aws-emrcontainers-virtualcluster-is.md files the same defect shape for AWS::EMRContainers::VirtualCluster only; it names neither of these two resource types nor any of these three checks. The open cloudformation__emr-serverless and cloudformation__emr issues likewise cover other types.
