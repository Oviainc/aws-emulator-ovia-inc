# iam query responses omit or mis-encode modeled response members (4 causes: instance-profile Role policy document, OIDC provider Tags, simulation result details)

> _Note: this issue was identified against the code base at commit `01e7e7e4d8371571a5c4b5afb30bf8b87d00507b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListInstanceProfiles

## Description
Four net-new wire divergences on IAM's query/XML response surface share one fault family: a modeled member is dropped from the response, or is serialized in the wrong encoding, by the response projection of the operation that owns it. Every status line is correct (200 on both sides in all four) — the defect is purely in what the body carries. All four causes must be closed before this issue is submitted.

Cause 1 of 4: the Role embedded in an instance-profile listing carries its AssumeRolePolicyDocument as raw JSON instead of URL-encoded.
AWS: Smithy — ListInstanceProfiles output ListInstanceProfilesResponse.InstanceProfiles is a list of instanceProfileListType entries, each carrying Roles, a list of com.amazonaws.iam#Role, whose AssumeRolePolicyDocument member targets policyDocumentType (length 1..131072, pattern ^[\u0009\u000A\u000D\u0020-\u00FF]+$). The same nesting exists on ListInstanceProfilesForRole. The model does not state the transfer encoding, so this is recorded behavior plus AWS's documented rule for IAM policy-document response members: IAM returns the policy document URL-encoded (percent-encoded, RFC 3986), so a caller must URL-decode it before parsing it as JSON. The recording shows exactly that: every Roles.member.AssumeRolePolicyDocument is the percent-encoded form of the trust policy (e.g. %7B%22Version%22%3A%222012-10-17%22%2C%22Statement%22%3A... for {"Version":"2012-10-17","Statement":[...]}). The requirement is the encoding, not any particular document: whatever trust policy the role was created with is returned percent-encoded.
Emulator: the member is emitted as the literal JSON text of the trust policy, unencoded — '{"Version": "2012-10-17", "Statement": [{"Effect": "Allow", "Principal": {"Service": "ec2.amazonaws.com"}, "Action": "sts:AssumeRole"}]}' where AWS returns its percent-encoded form. It affects every Roles entry of every instance profile in the page, on both ListInstanceProfiles (unpaginated and paginated pages) and ListInstanceProfilesForRole, so the fault is in the shared embedded-Role projection used by the instance-profile listings, not in a single handler. Role-level operations in this corpus (GetRole/ListRoles) do not diverge on this member, so the encoding step exists elsewhere and is simply not applied here.
Why: a client that follows AWS's contract URL-decodes the member before json.loads(). Decoding the emulator's raw JSON leaves it unchanged only while it happens to contain no '%' and no '+' character; a trust policy containing either (any percent in a condition value, any '+' in a principal or ARN) is silently corrupted on decode — '+' becomes a space and a stray '%xx' becomes a different byte — so the parse either fails or yields a policy the caller never wrote. Code that compares a round-tripped document against the encoded form it submitted never matches.
Fix: the instance-profile response serializers (the embedded Role projection shared by ListInstanceProfiles and ListInstanceProfilesForRole) must apply the same percent-encoding to AssumeRolePolicyDocument that the role-level serializers already apply.
Traces: iam-instance-profile-listing-pagination#task#10 (ListInstanceProfiles, positional page), #task#11 (ListInstanceProfiles, four profiles matched by Arn), #task#12 and #task#13 (ListInstanceProfilesForRole).

Cause 2 of 4: GetOpenIDConnectProvider omits the Tags member entirely instead of returning it present-but-empty.
AWS: Smithy — GetOpenIDConnectProvider output GetOpenIDConnectProviderResponse models Url, ClientIDList, ThumbprintList, CreateDate and Tags (target tagListType, list, length 0..50). AWS returns Tags for a provider that carries no tags as the empty-list serialization of the query/XML protocol, which the fixture records as '' (an empty <Tags/> element) — the member is present, its list is empty.
Emulator: the response has no Tags element at all; the replay reports $.GetOpenIDConnectProviderResponse.GetOpenIDConnectProviderResult.Tags: missing (expected '', got None) on an otherwise-correct 200.
Why: a caller cannot distinguish "this provider has no tags" from "this response did not report tags". SDK models surface an absent list as null/None rather than an empty collection, so client code that iterates response.Tags raises instead of looping zero times, and tag-reconciliation logic that treats None as unknown skips the provider instead of concluding it needs its tags applied.
Fix: the GetOpenIDConnectProvider handler's response serializer — emit Tags unconditionally, as an empty list when the provider carries no tags. (The same step's replay also flags Url with verdict host_not_own while expected and actual are the identical string the provider was registered with; that is a host-ownership annotation of the recording, not an emulator difference, and is NOT part of this cause.)
Traces: iam-add-client-id-to-openid-connect-provider#task#4.

Cause 3 of 4: a SimulateCustomPolicy EvaluationResult omits the matched statements' Position members and MissingContextValues.
AWS: Smithy — SimulateCustomPolicy returns SimulatePolicyResponse.EvaluationResults, a list of com.amazonaws.iam#EvaluationResult. EvaluationResult.MatchedStatements targets StatementListType of com.amazonaws.iam#Statement, whose members are SourcePolicyId, SourcePolicyType, StartPosition ("The row and column of the beginning of the Statement in an IAM policy") and EndPosition ("The row and column of the end of a Statement in an IAM policy"), each a Position structure of Line and Column. EvaluationResult.MissingContextValues targets ContextKeyNamesResultListType and is returned present-but-empty (recorded as '') when the simulation lacked no context key. So each matched statement is returned with the Line/Column span it occupies in the submitted document, and MissingContextValues is always present.
Emulator: every EvaluationResults member comes back carrying only EvalActionName, EvalResourceName, EvalDecision and a MatchedStatements entry with SourcePolicyId and SourcePolicyType — StartPosition, EndPosition and MissingContextValues are absent from all five results of the simulated action list.
Why: StartPosition/EndPosition are the only way a caller can point a user at the statement in the submitted document that produced the decision, which is the entire purpose of MatchedStatements; a linter or console cannot highlight the deciding statement. And because MissingContextValues is absent rather than empty, a caller cannot tell "no condition key was missing" from "the field was not reported", so the documented discrimination between an unsatisfied condition and an unsupplied condition key is lost.
Fix: the SimulateCustomPolicy policy-evaluation path and its EvaluationResult/Statement projection — record the line/column span of each matching statement within the submitted document and always emit MissingContextValues, empty when nothing is missing. Related: the OPEN issue 20261107T005227Z-iam-simulatecustompolicy-responses-omit-modeled-statement-positions-and.md describes the same omission, but its replay keys name only fixtures iam-permissions-boundary-and-policy-simulation and iam-policy-simulation-and-context-keys; it does not own the pagination/resource-ARN fixture steps below, which must be re-replayed here after the fix.
Traces: iam-simulate-custom-policy-pagination-and-resource-arns#task#2.

Cause 4 of 4: with ResourceArns supplied, the same simulation additionally omits EvalDecisionDetails and the Position members inside ResourceSpecificResults.MatchedStatements.
AWS: Smithy — EvaluationResult.EvalDecisionDetails targets EvalDecisionDetailsType (map) and is documented: "If the simulation evaluates policies within the same account and includes a resource ARN, then the parameter is present but the response is empty" — so a same-account simulation that names resource ARNs returns EvalDecisionDetails present and empty (recorded as ''). EvaluationResult.ResourceSpecificResults is a list of com.amazonaws.iam#ResourceSpecificResult, whose MatchedStatements is the same StatementListType, so each per-resource matched statement likewise carries StartPosition and EndPosition with Line and Column, and each ResourceSpecificResult carries its own MissingContextValues.
Emulator: on the resource-ARN simulation both EvaluationResults members omit EvalDecisionDetails and MissingContextValues, and the matched statements omit StartPosition/EndPosition both at the top level and inside ResourceSpecificResults — i.e. the elision is in the shared per-result projection and reaches the per-resource branch too.
Why: a caller that followed AWS's guidance to read per-resource decisions from ResourceSpecificResults gets results it cannot attribute to a statement, and an absent EvalDecisionDetails map reads as "cross-account details unknown" rather than AWS's "same-account, nothing to report", so cross-account detection logic branches the wrong way.
Fix: same component as Cause 3, extended to the ResourceSpecificResult projection — emit EvalDecisionDetails (empty for a same-account simulation naming resource ARNs) and populate the statement Position members on both the top-level and per-resource MatchedStatements.
Traces: iam-simulate-custom-policy-pagination-and-resource-arns#task#3.
