# lambda: a durable execution is accepted but never runs — no step, no callback, status stuck RUNNING

> _Note: this is cause 1 of 3 of `20261027T203721Z-lambda-3-net-new-root-causes-a-durable.md`, re-filed on its own with its own six replay keys. The other two causes of that bundle (CreateFunction's version-qualified ARN, and GetFunctionScalingConfig never dropping RequestedFunctionScalingConfig) are fixed and that report now lives under `issues/things-that-now-work/`. Both were identified against commit `6ad1863e43f5664fac16df5e246702230b6849d0`, so trace this back to the current code base._

## Operation
Invoke

## Description
A durable execution started through Invoke is recorded but never EXECUTES — no step runs, no callback is ever created, and the execution never leaves RUNNING except to time out.

Failing checks (6): lambda.callback-heartbeat-extends-deadline, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors, lambda.send-callback-success-after-checkpoint-window.

AWS: Invoke is the entry point that STARTS a named durable execution — Smithy: Invoke input member DurableExecutionName @httpHeader("X-Amz-Durable-Execution-Name") (@length 1..64, pattern ^[a-zA-Z0-9-_]+$), output member DurableExecutionArn @httpHeader("X-Amz-Durable-Execution-Arn"), modeled error DurableExecutionAlreadyStartedException (409). Once started, AWS RUNS the handler: the durable SDK's steps execute, `context.wait_for_callback(notify, ...)` invokes the handler's own notify function (which in these checks publishes the CallbackId to an SQS queue), and the execution is then resolvable through SendDurableExecutionCallbackSuccess / SendDurableExecutionCallbackHeartbeat (Smithy: POST /2025-12-01/durable-execution-callbacks/{CallbackId}/succeed and /heartbeat, errors CallbackTimeoutException 400, ResourceNotFoundException 404). GetDurableExecution then reports Status moving out of RUNNING to one of ExecutionStatus's terminal values (SUCCEEDED | FAILED | TIMED_OUT | STOPPED) with Result/Error and EndTimestamp, and GetDurableExecutionHistory records the Callback* events. Recorded behavior (these checks' oracle): the CallbackId arrives on the handler-written queue within seconds, a heartbeat inside the window answers HTTP 200 and extends the deadline, and a success callback drives the execution to SUCCEEDED carrying the handler's own result.

Emulator: Invoke(InvocationType=Event, DurableExecutionName=<name>) answers 202 and the execution IS registered — ListDurableExecutionsByFunction reports it — but nothing ever runs it. The emulator's own state documents this: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (module docs, "The event is never executed here (this emulator has no in-process runtime for a deployment package)"; the durable slice: "it starts RUNNING, and the move to TIMED_OUT is owed by the CLOCK"), and DurableExecutionRecord::materialize applies exactly one transition, RUNNING -> TIMED_OUT. Consequently the handler's notify callback never fires, no CallbackId is ever minted or delivered, no checkpoint or history event is written, and Status can only ever be RUNNING or TIMED_OUT. Every one of the six checks blocks on the first service-driven signal (the CallbackId on SQS, or GetDurableExecution leaving RUNNING) and the runner reports `Check timed out after 60.0s` for all six.

Why: the whole durable-execution feature is inert while looking healthy. A client gets a 202, an execution ARN and a RUNNING status, so it believes work is in flight; it then waits forever for the callback id its own handler was supposed to publish, and every downstream API it would call (SendDurableExecutionCallbackSuccess/Failure/Heartbeat, GetDurableExecutionHistory, StopDurableExecution) has no callback or event to address. A workflow written against AWS neither completes nor fails — it hangs, and the only terminal state the emulator can ever reach is TIMED_OUT, which misreports a healthy workflow as a timeout.

Fix: the Invoke handler's durable path plus the durable-execution slice of the lambda service's state — a started execution must actually be driven (its steps executed, its wait_for_callback notify invoked, a CallbackId minted and resolvable, checkpoints and history events appended, and the status advanced to SUCCEEDED/FAILED on completion) rather than registered and left to the timeout clock.

### What blocks this today (read before picking it up)
The six checks cannot be served without RUNNING the function's own deployment package: `context.wait_for_callback(notify, ...)` invokes the handler's own `notify`, and that user code is the only thing that can put the CallbackId on the queue each check polls; the result a success callback carries is the handler's own return value. This emulator has no in-process runtime for a deployment package at all — synchronous Invoke is still refused `NotImplemented` (`issues/things-that-do-not-work/20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md` is the prerequisite). Serving these faithfully needs a Python 3.13 interpreter, bounded in steps, memory and output, with boto3 (routed to the emulator's own in-process services) and the Lambda durable-functions SDK reachable from the handler; containers and external processes are not available to this emulator, and no interpreter crate is in Cargo.lock yet. Nothing short of that is a fix: minting a CallbackId nothing asked for, appending a checkpoint or history event nothing wrote, or advancing an execution to SUCCEEDED with a result nothing produced would all report an outcome no engine produced.

The service-owned half of the feature is separate, still 501, and tracked by its own stub issues: CheckpointDurableExecution, GetDurableExecutionState, GetDurableExecutionHistory, SendDurableExecutionCallbackSuccess/Failure/Heartbeat and StopDurableExecution.

Related open issues: 20261026T070343Z-events-lambda-sqs-lambda-invoke-on-a-durable-execution-function-returns.md covers only the missing X-Amz-Durable-Execution-Arn response header on that Invoke, and 20261027T191349Z-events-lambda-sqs-lambda-durable-execution-status-change-events-are-never.md covers the missing status-change events; neither covers the execution never running at all. 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md covers synchronous Invoke being refused — these six checks are NOT refused, they are accepted with 202 and then never progress.

## Evidence
Expected (AWS, recorded): after Invoke(FunctionName=<durable fn>, InvocationType='Event', DurableExecutionName=<name>) answers 202, the handler runs; `context.wait_for_callback(notify, ...)` fires `notify`, which sends the CallbackId to the check's SQS queue; SendDurableExecutionCallbackHeartbeat(CallbackId=...) answers HTTP 200 and extends the heartbeat deadline; SendDurableExecutionCallbackSuccess(CallbackId=..., Result=b'{"approved": true, ...}') drives the execution to Status=SUCCEEDED, GetDurableExecution(IncludeExecutionData=True) returns the handler's own Result, and GetDurableExecutionHistory contains at least one Callback* event.
Actual (emulator): the 202 and the registered execution are the last things that happen. No message ever reaches the queue the handler was given, GetDurableExecution reports Status=RUNNING until the function's DurableConfig ExecutionTimeout falls due (then TIMED_OUT), and all six checks are cut off by the runner: `Error: Check timed out after 60.0s` for lambda.callback-heartbeat-extends-deadline, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors and lambda.send-callback-success-after-checkpoint-window. The emulator's own state documentation states the cause in full: "this emulator has no in-process runtime for a deployment package" and, for a durable execution, "The ONLY transition it applies is the one the clock owed at `now`" — RUNNING -> TIMED_OUT. These checks are not blocked on an unimplemented operation and were not refused; every call they made was accepted.

## Steps to Reproduce
Any of the six durable checks; this is the heartbeat one: 1) sqs:CreateQueue and read its QueueArn. 2) iam:CreateRole trusted by lambda.amazonaws.com with AWSLambdaBasicExecutionRole plus sqs:SendMessage on that queue. 3) lambda:CreateFunction (python3.13) whose handler uses the durable SDK — @durable_execution, and `context.wait_for_callback(notify, name=..., config=WaitForCallbackConfig(timeout=..., heartbeat_timeout=...))` where `notify` sends the CallbackId to the queue — with a DurableConfig; wait for State=Active. 4) lambda:Invoke(FunctionName=<fn>, Qualifier='$LATEST', InvocationType='Event', DurableExecutionName=<unique>, Payload={queueUrl, timeoutSeconds, heartbeatTimeoutSeconds}); observe StatusCode 202 and resolve the execution ARN (from X-Amz-Durable-Execution-Arn, or via lambda:ListDurableExecutionsByFunction). 5) sqs:ReceiveMessage on the queue. On AWS the CallbackId arrives; on the emulator nothing ever arrives. 6) lambda:GetDurableExecution(DurableExecutionArn=<arn>) repeatedly: on the emulator Status stays RUNNING and no SendDurableExecutionCallbackHeartbeat/Success is possible because no CallbackId exists.
