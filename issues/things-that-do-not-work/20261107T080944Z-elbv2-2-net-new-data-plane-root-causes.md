# elbv2: 2 net-new data-plane root causes — an ALB with registered instance targets answers 502/never answers at its DNS name, and an NLB gets no network interfaces so its TCP listener never serves

> _Note: this issue was identified against the code base at commit `228033d439b60358a40317f8e8a680bd7ef66315`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterTargets

## Description
Two distinct root causes covering the elbv2 data-plane checks that no open issue owns (the report marks none of these OWNED/ALREADY FILED). Related open issues that do NOT cover these checks: 20261104T094656Z-elbv2-seven-target-health-routing-and-data-plane-causes-still-open.md, 20261105T093535Z-elbv2-4-net-new-data-plane-causes-desync.md, 20261104T165357Z-elbv2-an-https-listener-never-terminates-tls-so.md.

Cause 1 of 2: an ALB whose target group holds registered, reachable instance targets never serves their response at the load balancer's DNS name.
AWS: a request to an internet-facing ALB's DNSName on a listener port is forwarded to a healthy target of the listener's forward action and the client receives the target's own status and body (HTTP 200 and the target's bytes here); a load-balancer-generated 502 only appears when the target cannot be reached or breaks the response contract, and a 504 only after the configured idle timeout elapses. The per-request behaviours these checks then assert (lb_cookie/app_cookie stickiness pinning via AWSALB, least-outstanding-requests vs round-robin spread, slow_start, min-healthy-count routing to an unhealthy target, deregistration_delay serving in-flight requests while draining, oversize request line/headers refused by the ALB with its own 4xx) are all layered on top of that forwarding.
Emulator: the data path never produces the target's response. Observed: HTTP 502 with an empty body on the very first request ('request 1/30 to http://…/ (headers=None) returned HTTP 502, expected 200; body=""'), or the endpoint never answers at all so the poll records nothing ('http://…/ping answering 200 (observed: [])', "load balancer serving 'SIM2REAL-TARGET-BODY' at http://…/?s=0 (observed: [])"), and the remaining checks are cut at 60s with 'Check timed out after 60.0s' before any routing behaviour can be sampled.
Why: every client that goes through the load balancer instead of to the target directly gets a 502 (or a hang) for a healthy deployment; stickiness, load-balancing algorithm, slow start, draining and the ALB's own request-size refusals are all unobservable, and a 502 is indistinguishable from a genuinely broken target.
Fix: the ELBv2 data-plane listener/forward path — the listener must accept a connection on the load balancer's address, select a target of the forward action's target group and proxy the request/response — plus the target-health state it selects from.
Traces: elbv2.lb-cookie-stickiness-pins-a-client-to-one-target-in-the-group, elbv2.elbv2shape-deep-elbv2-3-oversize-request-line-and-headers-rejected-by-alb, elbv2.target-response-exceeding-idle-timeout-yields-504, elbv2.e2e-alb-traffic-lifecycle-flow, elbv2.deregistration-delay-serves-in-flight-requests-while-draining, elbv2.elbv2attr-deep-elbv2-1-unhealthy-state-routing-min-healthy-count-serves-unhealthy-target, elbv2.elbv2shape-deep-elbv2-3-app-cookie-stickiness-pins-with-cookie-spreads-without, elbv2.elbv2shape-deep-elbv2-3-least-outstanding-requests-starves-slow-backend-vs-round-robin, elbv2.elbv2shape-deep-elbv2-3-slow-start-with-least-outstanding-requests-rejected.

Cause 2 of 2: a Network Load Balancer is never represented by network interfaces, so its TCP listener has no address that serves.
AWS: creating an NLB places one elastic network interface per enabled subnet, each carrying the node's private address (and, for an internet-facing NLB, an associated public address); EC2 DescribeNetworkInterfaces filtered on the load balancer therefore returns one interface per zone, and a TCP listener on those addresses forwards to the target group — preserving the client source IP to an instance target, prefixing PROXY protocol v2 when proxy_protocol_v2.enabled is true, honouring the target group's cross-zone override, and refusing a port no security group rule admits.
Emulator: no NLB interface with an address is ever found — 'TimeoutError: 1 NLB interfaces with public addresses: the run budget ended first; not graded' — so the wire-level checks never get an address to connect to, and the source-IP/cross-zone checks are cut at 60s with 'Check timed out after 60.0s'.
Why: an NLB is unusable from a client's point of view: nothing can connect to it, and PROXY protocol, source-IP preservation, cross-zone behaviour and security-group enforcement on an NLB cannot be exercised at all.
Fix: NLB creation state must materialise per-subnet network interfaces (private and, when internet-facing, public addresses) visible to EC2 DescribeNetworkInterfaces, and the NLB data-plane listener must serve TCP on those addresses.
Traces: elbv2.deep-elbv2-2-nlbwire-proxy-protocol-v2-signature-and-address-block, elbv2.deep-elbv2-2-nlbwire-security-group-unlisted-listener-port-blocked, elbv2.deep-elbv2-2-nlbwire-cross-zone-target-group-override, elbv2.nlb-tcp-listener-preserves-client-source-ip-to-instance-target.
