# Marketplace Discovery router refuses every request as AmbiguousService, making the whole service unreachable

> _Note: this issue was identified against the code base at commit `ace69a9d3348e9c8c81d3eff309bd15ea7c6e8c3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchListings

## Description
This bundle has 1 cause. Every one of the 78 behavioral checks for Marketplace Discovery fails with the SAME emulator response, produced before any Marketplace Discovery handler runs, so there is exactly one root cause to close.

Cause 1 of 1: the shared request router resolves an incoming request to an emulated service by its SigV4 signing name alone, and the AWS Marketplace family shares one signing name.

AWS: Smithy (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/smithy-model/com-amazonaws-marketplacediscovery-awsmarketplacediscovery.json, query=service_info) gives AWSMarketplaceDiscovery sdkId "Marketplace Discovery", protocol restJson1, sigv4Name "aws-marketplace", arnNamespace "aws-marketplace" and endpointPrefix "discovery-marketplace". Its nine operations are POST-bound under a dated prefix: GetListing POST /2026-02-05/getListing, GetOffer POST /2026-02-05/getOffer, GetOfferSet POST /2026-02-05/getOfferSet, GetOfferTerms POST /2026-02-05/getOfferTerms, GetProduct POST /2026-02-05/getProduct, ListFulfillmentOptions POST /2026-02-05/listFulfillmentOptions, ListPurchaseOptions POST /2026-02-05/listPurchaseOptions, SearchFacets POST /2026-02-05/searchFacets, SearchListings POST /2026-02-05/searchListings. Sibling services in the family share the signing name but NOT the endpoint prefix or the URIs: Marketplace Reporting has sigv4Name "aws-marketplace" with endpointPrefix "reporting-marketplace" (query=service_info on services/service-com-amazonaws-marketplacereporting-awsmarketplacereporting/...). AWS therefore serves each of these distinct services correctly; the signing name is not a service identity. No AWS model anywhere defines an error named AmbiguousService — it is not a code a client can ever observe from AWS. In particular AWS answers each exercised surface with a modeled result: SearchListings/SearchFacets/ListPurchaseOptions/ListFulfillmentOptions/GetOfferTerms return 200 with their modeled output documents (SearchListingsOutput carries listingSummaries and totalResults; maxResults @range 1..100 default 25, searchText @length 1..512, filters @length 1..30); GetListing returns 200 GetListingOutput for an existing listingId; a listingId violating GetListingInput.listingId (@required, @length 1..255, @pattern ^[\w\-]+$) or a maxResults/rating filter outside its modeled range is rejected with ValidationException (errorKind client, @httpError 400); a well-formed but unknown listingId is rejected with ResourceNotFoundException (errorKind client, @httpError 404).

Emulator: every call — SearchListings, SearchFacets and the GetListing calls the checks reach — is answered by the router with error code AmbiguousService and the message "7 emulated services all claim requests for 'aws-marketplace': aws-marketplace, aws-marketplace, aws-marketplace, aws-marketplace, aws-marketplace, aws-marketplace, aws-marketplace; the request is rejected rather than served by an arbitrary one" (recorded example of the message; the AmbiguousService code is the requirement that diverges). botocore classifies it as retryable and the SDK exhausts its retries ("reached max retries: 3") before surfacing it. No handler, no input validation, no state lookup and no serializer for Marketplace Discovery is ever invoked. The five checks reported as [mismatch] rather than [error] show the same substitution at the error-code level: get-listing-id-length-exceeded-rejected expected ValidationException and got 'AmbiguousService'; get-listing-not-found-rejected and get-listing-nonexistent-id-not-found expected ResourceNotFoundException and got 'AmbiguousService'; search-listings-rating-filter-out-of-range-rejected and search-listings-max-results-exceeds-limit-rejected expected ValidationException and got 'AmbiguousService'.

Why: a client relying on AWS behavior cannot use the service at all. Discovery workloads begin with SearchListings, so the first call of every workflow fails; the pass rate is 0/78 (0%). Because the refusal is a server-fault-shaped code, SDKs retry requests that can never succeed, turning each call into 4 round trips plus backoff. Negative-path clients are mis-taught too: code that catches ValidationException or ResourceNotFoundException to branch on bad input or a missing listing instead sees an unmodeled AmbiguousService, so input validation and not-found handling appear broken rather than enforced.

Fix: the shared request router / service-registry claim resolution. Claims must be disambiguated by the request's endpoint (Host header / endpointPrefix "discovery-marketplace") and by the operation's HTTP binding — the dated restJson1 URIs above are unique to this service — rather than by the SigV4 signing name, which is shared across the whole aws-marketplace family. Secondarily, the refusal itself must never be emitted for a request that does resolve, and no synthetic AmbiguousService code should reach a client. Once routing lands, the nine operations' handlers, their input validation (GetListingInput.listingId length/pattern, SearchListingsInput.maxResults/searchText/filters ranges, the rating and facet filter enums) and their restJson1 serializers must produce the modeled 200/400/404 responses the checks assert.

Related open issues (they do NOT cover these checks): '20261022T000249Z-marketplace-catalog-entity-read-and-list-operations-refused', '20261022T000249Z-marketplace-catalog-change-set-and-assessment-operations-refused' and '20261022T000249Z-marketplace-catalog-tagging-and-resource-policy-operations-refused' report the same router defect for the marketplace-catalog service from the wire corpus and carry no replay key for any marketplace-discovery behavioral check.

Traces: all 78 failing behavioral checks of this service, listed in trace_ids — 73 reported as [error] (the ClientError propagates out of the check) and 5 as [mismatch] (the check caught the error and asserted on its Code). Representative examples: marketplace-discovery.search-listings-basic-success, marketplace-discovery.get-listing-not-found-rejected, marketplace-discovery.search-facets-category-present-with-counts, marketplace-discovery.list-purchase-options-filter-by-product-id, marketplace-discovery.get-offer-terms-for-discovered-offer.
