# cloudtrail__lambda__s3: a trail whose advanced event selector names one Lambda function's ARN never delivers an Invoke data-event log file to its S3 bucket

> _Note: this issue was identified against the code base at commit `f3ca7ead92e65d3eb9c80914c7f5792563c2115c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEventSelectors

## Description
ONE net-new root cause in this issue; it must be closed before submitting.

Cause 1 of 1: a trail that accepts and echoes an advanced event selector for the Lambda data-event class (eventCategory=Data / resources.type=AWS::Lambda::Function / resources.ARN=<function arn>) and is then started with StartLogging never writes a single log file to its S3 bucket, so no Invoke data event is ever delivered and neither the per-record shape nor the selector's scoping (one function included, a second withheld) is observable at all. Failing check: cloudtrail__lambda__s3.obs-lambda-3-data-events-s3.

AWS: PutEventSelectors takes TrailName (required) plus EventSelectors / AdvancedEventSelectors and echoes TrailARN + the stored selectors (Smithy, cloudtrail: PutEventSelectors input TrailName/EventSelectors/AdvancedEventSelectors, output TrailARN/EventSelectors/AdvancedEventSelectors; errors InvalidEventSelectorsException 400, InvalidTrailNameException 400, TrailNotFoundException 404, UnsupportedOperationException 400, ConflictException 409). StartLogging has an empty output (Smithy: StartLogging input Name required, output {}), and GetTrailStatus then reports IsLogging plus the LatestDelivery*/LatestDigestDelivery* members that describe delivery (Smithy: GetTrailStatus output IsLogging, LatestDeliveryTime, LatestDeliveryError, ...). What the selector then CAUSES is recorded behavior only, as the check's reference (https://docs.aws.amazon.com/awscloudtrail/latest/userguide/logging-data-events-with-cloudtrail.html) and its own header state: CloudTrail writes gzipped objects under the documented key layout AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/, whose body is a JSON object with a Records list, and each Invoke of the function named by resources.ARN appears there as one record with eventSource "lambda.amazonaws.com", eventName "Invoke", eventCategory "Data", managementEvent false, readOnly false, requestParameters == {"functionName": <the function's UNQUALIFIED ARN>}, additionalEventData.functionVersion == "<that same ARN>:$LATEST" (the QUALIFIED name), resources containing {"accountId": <account>, "type": "AWS::Lambda::Function", "ARN": <the function arn>}, recipientAccountId == the caller's account and awsRegion == the request's region, and requestID equal to the Invoke response's ResponseMetadata.RequestId. The function named by the selector is delivered; a second function invoked in the same window produces NO record with eventName Invoke or eventCategory Data. Those literals (the event source, event name, "Data", the resource type "AWS::Lambda::Function", the ":$LATEST" suffix and the AWSLogs/<account>/CloudTrail/<region>/YYYY/MM/DD/ prefix shape) are the requirement; the per-run function names, bucket name, account id, request ids and timestamps that fill them are not.

Emulator: the whole setup leg is accepted — bucket + CloudTrail bucket policy, CreateTrail, PutEventSelectors (its echo assertion, which compares the three stored FieldSelectors against the three sent, runs BEFORE the wait and did not fire, so the selector round-trips unchanged), StartLogging — the Invokes genuinely run (each returns 200 echoing its marker payload, and the request-id gap filed as 20261105T112044Z-cloudtrail-lambda-s3-the-lambda-invoke-response-carries.md no longer stops the check), and then nothing is ever written. The check re-invokes both functions every 20 s and re-lists AWSLogs/<account>/CloudTrail/ after every poll; it is still inside that delivery loop when the run budget ends, so the verdict is 'error' with TimeoutError: "an Invoke data event for fnA (arn:aws:lambda:<region>:<account>:function:<name>) in s3://<bucket>: the run budget ended first; not graded". No per-record assertion, no withholding assertion for the second function and no LookupEvents leg is ever reached. Hypothesis (neither the model nor the replay states it): the emulator has no trail delivery writer at all, so the gap is not specific to the Lambda data class.

Why: a client that configures the advanced event selector AWS publishes for Lambda function invocations gets a trail that looks healthy (the selector is echoed back byte-identically and the trail reports it is logging) and an S3 prefix that stays permanently empty. Every detective control over who invoked which function — SIEM/Athena ingestion of the log prefix, incident reconstruction by requestID, proof that only the selected function's invocations are captured — reads nothing and cannot distinguish "no invocations happened" from "invocations are not recorded". The management/data split is also unobservable: without delivery there is no evidence that Invoke is a data event rather than a management event.

Fix: CloudTrail's trail log-file delivery path and its event-selector evaluation (the trail-logging state machine plus the S3 writer it feeds), together with the Lambda Invoke handler's hook into that seam: a logging trail must evaluate its stored AdvancedEventSelectors against each served call, including the Data category matched on eventCategory / resources.type / resources.ARN, and write the matching records as gzipped JSON objects into the configured bucket under AWSLogs/<account-id>/CloudTrail/<region>/YYYY/MM/DD/, each populated with eventSource, eventName, eventCategory "Data", managementEvent false, readOnly false, requestParameters.functionName (unqualified ARN), additionalEventData.functionVersion (qualified), the resources entry, recipientAccountId/awsRegion and requestID equal to the caller's request id. Neighbouring OPEN issues, named because they do not carry this failure's replay key and do not cover it: 20261105T111951Z-cloudtrail-lambda-s3-s3-data-events-are-not.md (S3 object data events, same check id but keyed on the earlier Invoke request-id frame), 20261105T112044Z-cloudtrail-lambda-s3-the-lambda-invoke-response-carries.md (the Invoke request-id header), 20261027T003725Z-cloudtrail-delivers-no-data-event-log-files-for.md (the Cognito identity-pool data class), 20261102T102343Z-cloudtrail-s3-2-net-new-root-causes-s3.md and 20261024T114720Z-cloudtrail-event-history-is-empty-for-everything-but.md (management-event history and basic selectors).
