=== Cause 1 of 2: an aws:RequestedRegion condition in the ROLE's OWN permissions policy is not evaluated, so one session reaches every region ===
AWS: `aws:RequestedRegion` is a global condition key DERIVED from the region the request is actually sent to; Smithy (com.amazonaws.s3#PutObject, PUT /{Bucket}/{Key+}) models EncryptionTypeMismatch/InvalidRequest/InvalidWriteOffset/TooManyParts only, so an authorization refusal rides S3's REST-XML error document — recorded behavior for the outcome. Recorded behavior: a role whose own identity-based permissions policy Allows s3:PutObject only under `StringEquals {"aws:RequestedRegion": "<region A>"}` yields a session whose PutObject SUCCEEDS against a bucket in region A and is REFUSED with error code `AccessDenied` (HTTP 403) against an equivalent bucket in a second region — same credentials, no session policy involved. A control session assumed from the same role with its permissions policy temporarily replaced by an unconditional Allow reaches BOTH regions, which is what proves the refusal belongs to the condition and not to the bucket or the region.
Emulator: the refusal never arrives. The check establishes the positive control, then polls for the AccessDenied in the second region and the harness budget expires first — `Error: Check timed out after 60.0s`. No divergent response body is captured because none is produced: PutObject keeps answering 200 in both regions.
Why: every region-fencing policy is inert. A data-residency guardrail written as aws:RequestedRegion validates clean against the emulator and then does nothing, and no test can observe that a cross-region write was meant to be refused. Note this is a different code path from a session policy passed in AssumeRole's `Policy=`: here the condition lives in the role's own identity-based document with no session policy at all, so the key must be derived identically on that path.
Fix: the S3 request-authorization gate — the PutObject handler must derive the request's `aws:RequestedRegion` from the region it is serving and ask the shared IAM evaluation for a decision against the role's identity-based documents, refusing with HTTP 403 / `AccessDenied` when the condition does not hold.
Traces: iam__s3__sts.assumed-role-permissions-policy-requestedregion-condition-gates-put-object-by-region.

=== Cause 2 of 2: a request refused by a matched explicit Deny is reported with the implicit-deny message, mis-stating why it was refused ===
AWS: recorded behavior only for the framing (no modelled error member carries it; the code is carried in S3's REST-XML body as `<Code>AccessDenied</Code>` with HTTP 403). An IAM user whose only inline policy is {Allow s3:PutObject/s3:GetObject on the bucket's objects} + {Allow the MFA bootstrap actions} + {Deny NotAction <those bootstrap actions> on * when `BoolIfExists aws:MultiFactorAuthPresent` is "false"} has its long-term, non-MFA PutObject refused by the explicit Deny, and AWS words that refusal as `User: <caller-arn> is not authorized to perform: <action> on resource: "<resource-arn>" with an explicit deny in an identity-based policy`. The FIXED text is `User: `, ` is not authorized to perform: `, ` on resource: `, the surrounding double quotes and ` with an explicit deny in an identity-based policy`; `<caller-arn>` is the signing identity, `<action>` is the request's action (s3:PutObject) and `<resource-arn>` is the object ARN built from the request. The trailing clause is the DIAGNOSIS: AWS uses ` with an explicit deny in an identity-based policy` when a Deny statement matched, and ` because no identity-based policy allows the <action> action` only when nothing granted the action.
Emulator: the status and code are now right — HTTP 403 `AccessDenied` — but the message ends `because no identity-based policy allows the s3:PutObject action` for a request that WAS matched by an explicit Deny while an Allow for the same action exists in the same document. The principal ARN, action and quoted resource ARN all match; only the deny-classification clause diverges.
Why: that clause is the whole remediation signal. Told "no identity-based policy allows" the action, a caller or its tooling goes looking for a missing Allow that is in fact already present, and never finds the Deny-with-condition it actually has to satisfy (here: sign with an MFA-bearing session). Any policy-troubleshooting flow, support runbook or log-scraping alert keyed on AWS's two message forms draws the opposite conclusion from the truth, and a client can no longer tell an explicit deny from an un-granted action.
Fix: the S3 request-authorization gate's refusal-message construction — the evaluation already distinguishes an explicit Deny from an absent Allow, and the message must carry that distinction: emit ` with an explicit deny in an identity-based policy` when a Deny statement (including one matched via NotAction plus a Bool/BoolIfExists condition over `aws:MultiFactorAuthPresent`) decided the request, reserving the `because no identity-based policy allows the <action> action` form for the no-grant case.
Traces: iam__s3__sts.deny-unless-mfa-present-blocks-plain-session-but-allows-mfa-session.
