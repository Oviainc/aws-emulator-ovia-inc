# chime-sdk-media-pipelines: 7 net-new root causes — NotFoundException messages are bespoke prose instead of AWS's fixed text, duplicate PoolName misclassified ConflictException, name-pattern refusal misclassified BadRequestException, and four refusals AWS makes are not made at all (GetSpeakerSearchTask still 501)

> _Note: this issue was identified against the code base at commit `d7c92a359e65b119da339df847b0735e9ef403e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMediaInsightsPipelineConfiguration

## Description
Seven distinct root causes in the chime-sdk-media-pipelines emulator, all grounded in failing behavioral checks of this one service. No existing open issue covers any of them (list_existing_issues query='chime' returns none); the three failures the report marks ALREADY FILED (ListMediaInsightsPipelineConfigurations, UpdateMediaInsightsPipelineConfiguration, StartSpeakerSearchTask scaffold stubs) are excluded here.

=== Cause 1 of 7: every NotFoundException carries a bespoke per-resource message instead of this service's one fixed text ===
AWS: Smithy: NotFoundException (HTTP 404) is modeled on GetMediaPipeline, GetMediaCapturePipeline, GetMediaInsightsPipelineConfiguration, DeleteMediaInsightsPipelineConfiguration, GetMediaPipelineKinesisVideoStreamPool and UpdateMediaInsightsPipelineStatus, documented "One or more of the resources in the request does not exist in the system." The model does not state the message text, so: recorded behavior only — in every recording of this service, for every one of those operations and every resource kind, the 404 body's message is the FIXED string "Unable to find the requested identifier". It has no variable parts at all: no resource name, no id, no ARN, no resource-kind noun.
Emulator: each handler composes its own sentence and interpolates the requested identifier, e.g. GetMediaPipeline answers NotFoundException 'No media pipeline with the ID 00000000-0000-0000-0000-000000000000 exists.'; DeleteMediaInsightsPipelineConfiguration answers 'No media insights pipeline configuration identified by <name-or-ARN> exists.'; GetMediaInsightsPipelineConfiguration after delete answers 'No media insights pipeline configuration identified by <ARN> exists.'; GetMediaPipelineKinesisVideoStreamPool after delete answers 'No Kinesis Video Stream pool identified by <pool ARN> exists.'; GetMediaCapturePipeline after delete answers 'No media capture pipeline with the ID <uuid> exists.'; UpdateMediaInsightsPipelineStatus answers 'No media insights pipeline identified by <uuid> exists.' The 404 status and the NotFoundException code are right in all six; only the message diverges, and the pattern is identical in each: the emulator substitutes the request's identifier into prose AWS never emits.
Why: a client that branches on, logs, or asserts against the service's not-found wording — and anything that redacts error bodies, since AWS's text deliberately echoes NO caller-supplied identifier while the emulator's echoes it in full — behaves differently against the emulator than against AWS. The emulator also leaks the requested identifier (a configuration name or ARN, up to the 1024-character NonEmptyString bound) into an error body AWS keeps identifier-free.
Fix: the service's not-found refusal wording. crate::state::not_found is already the single home for building this error, but every handler passes it a format!-composed string (e.g. services/service-com-amazonaws-chimesdkmediapipelines-chimesdkmediapipelinesservice/src/ops/get_media_pipeline.rs lines 191-197); the fixed text belongs in that one helper so no handler words it or interpolates an identifier into it.
Traces: chime-sdk-media-pipelines.get-media-pipeline-not-found, chime-sdk-media-pipelines.delete-media-insights-pipeline-configuration-not-found, chime-sdk-media-pipelines.media-insights-pipeline-configuration-delete-lifecycle, chime-sdk-media-pipelines.kinesis-video-stream-pool-delete-removes-from-list, chime-sdk-media-pipelines.media-capture-pipeline-lifecycle-with-chime-meeting, chime-sdk-media-pipelines.update-media-insights-pipeline-status-not-found.

=== Cause 2 of 7: a duplicate PoolName is refused 409 ConflictException instead of 400 BadRequestException ===
AWS: Smithy: CreateMediaPipelineKinesisVideoStreamPool models BOTH BadRequestException (400) and ConflictException (409), so the model alone does not pick one. Recorded behavior: a second create whose PoolName is already in use is refused 400 BadRequestException with the message "Media Pipeline Kinesis Video Stream Pool already exists with <PoolName> name" — fixed text "Media Pipeline Kinesis Video Stream Pool already exists with" + the PoolName taken verbatim from the request + fixed text "name". The refusal is uniform: under concurrent creates of ONE name, every loser gets the same 400 BadRequestException, not a different class from the serial case.
Emulator: answers ConflictException with the message "A Kinesis Video Stream pool with that name already exists." — a different error code, a different HTTP status (409 vs 400), and a message that names no PoolName at all. Both the serial duplicate and all four losers of the concurrent race get ConflictException.
Why: retry middleware and client code classify 409 Conflict as a retryable/raceable condition and 400 as a permanent input error, so a client that would fail fast against AWS retries against the emulator (and vice versa); a client that parses the PoolName out of the message to report which name collided gets nothing.
Fix: the CreateMediaPipelineKinesisVideoStreamPool handler's name-in-use refusal — the StreamPoolRefused::NameInUse arm in services/service-com-amazonaws-chimesdkmediapipelines-chimesdkmediapipelinesservice/src/ops/create_media_pipeline_kinesis_video_stream_pool.rs lines 247-256 — must raise the modeled BadRequestException with AWS's wording rather than crate::state::conflict.
Traces: chime-sdk-media-pipelines.kinesis-video-stream-pool-duplicate-name-rejected, chime-sdk-media-pipelines.kinesis-video-stream-pool-duplicate-name-concurrent-create-race.

=== Cause 3 of 7: a MediaInsightsPipelineConfigurationName pattern violation is refused BadRequestException, and the message drops AWS's "N validation error(s) detected" preamble ===
AWS: Smithy: CreateMediaInsightsPipelineConfiguration.MediaInsightsPipelineConfigurationName is required, @length 2..64 and @pattern ^[0-9a-zA-Z._-]+$. The operation's modeled error list is BadRequestException/ForbiddenException/NotFoundException/ResourceLimitExceeded/ServiceFailure/ServiceUnavailable/ThrottledClient/UnauthorizedClient — ValidationException is NOT modeled, so this is recorded behavior only: the constraint is enforced at the request boundary, which answers 400 ValidationException with the message "1 validation error detected: Value '<name>' at 'mediaInsightsPipelineConfigurationName' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-zA-Z._-]+$". Fixed text: "<N> validation error detected: Value '", "' at '", "' failed to satisfy constraint: Member must satisfy regular expression pattern: "; variable parts: the error count, the rejected value and the member's lowerCamel wire name and pattern, all from the request and the model.
Emulator: answers code BadRequestException with message "Value 'sim2real-invalid@name-suffix<id>' at 'mediaInsightsPipelineConfigurationName' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-zA-Z._-]+$" — the right clause, but the wrong error code and without the leading "1 validation error detected: " preamble. The crate states this intentionally: create_media_insights_pipeline_configuration.rs lines 172-176 record that service.rs words every boundary constraint failure as this service's BadRequestException.
Why: a client that catches ValidationException to distinguish malformed input from a service-level bad request sees an unmatched exception type against the emulator, and anything that counts or splits on the "N validation error(s) detected:" preamble to enumerate per-member failures finds no preamble to split on.
Fix: the service's boundary-constraint refusal mapping (service.rs) for this service, plus the preamble in the message builder it uses — not the handler, which never sees the request.
Traces: chime-sdk-media-pipelines.create-media-insights-pipeline-configuration-invalid-name-pattern-rejected.

=== Cause 4 of 7: an Elements list holding BOTH Transcribe processor types is accepted and stored ===
AWS: Smithy: Elements targets MediaInsightsPipelineConfigurationElements, whose members include AmazonTranscribeProcessor and AmazonTranscribeCallAnalyticsProcessor; the list carries no constraint expressing the exclusion, so recorded behavior only: a create whose Elements contains an AmazonTranscribeProcessor element AND an AmazonTranscribeCallAnalyticsProcessor element is refused 400 BadRequestException with the fixed message "Duplicate Transcribe processors are not allowed" (no variable parts), and no configuration is created — the name does not appear in a following ListMediaInsightsPipelineConfigurations.
Emulator: accepts the request, answers 201, and persists both elements; the created configuration echoes the AmazonTranscribeProcessorConfiguration and the AmazonTranscribeCallAnalyticsProcessorConfiguration side by side and is then listable. No refusal of any kind is made.
Why: a configuration real AWS would never create exists in the emulator, so a client's negative-path handling for this documented element rule is never exercised, and a pipeline built on that configuration would succeed in test and fail at the real service.
Fix: CreateMediaInsightsPipelineConfiguration's validation — the Elements check that already exists in services/service-com-amazonaws-chimesdkmediapipelines-chimesdkmediapipelinesservice/src/ops/create_media_insights_pipeline_configuration.rs lines 184-193 bounds only the element COUNT; the mutually-exclusive-processor rule belongs beside it, before the record is built.
Traces: chime-sdk-media-pipelines.create-media-insights-pipeline-configuration-duplicate-processor-elements-rejected.

=== Cause 5 of 7: a ResourceAccessRoleArn naming no existing IAM role is accepted instead of refused ForbiddenException ===
AWS: Smithy: ResourceAccessRoleArn is required and @pattern ^arn[\\/\\:\\-\\_\\.a-zA-Z0-9]+$ — syntax only; ForbiddenException (HTTP 403, "The client is permanently forbidden from making the request.") IS modeled on this operation. Recorded behavior: when the ARN is well-formed but no such IAM role exists, the create is refused 403 ForbiddenException with the message "Service does not have permission to invoke role: <ResourceAccessRoleArn>" — fixed text "Service does not have permission to invoke role: " plus the role ARN copied from the request — and no configuration is created (the name is absent from a following list). Hypothesis: the service attempts the AssumeRole at create time and reports the failure as a permissions error rather than NotFoundException.
Emulator: accepts the create, answers 201, and stores the configuration with ResourceAccessRoleArn echoed back as the nonexistent role. An otherwise-identical request naming a real role also succeeds, so the emulator makes no distinction at all. The handler never consults the IAM role directory.
Why: the most common real-world misconfiguration for this API — a role that was deleted, misspelled, or never created — is silently accepted, so a client never learns at create time what AWS tells it immediately, and discovers it only when the pipeline fails to start.
Fix: CreateMediaInsightsPipelineConfiguration's validation: resolve ResourceAccessRoleArn against the account's IAM role state before the record is built (alongside the existing pre-lock checks in create_media_insights_pipeline_configuration.rs) and raise the modeled ForbiddenException with AWS's wording.
Traces: chime-sdk-media-pipelines.create-media-insights-pipeline-configuration-role-not-found.

=== Cause 6 of 7: CreateMediaPipelineKinesisVideoStreamPool is not authorized against the caller's identity-based policy ===
AWS: Smithy: the operation models ForbiddenException/UnauthorizedClientException; AccessDeniedException is the standard sigv4 authorization refusal applied before the operation. Recorded behavior: a caller holding credentials for an assumed role with NO attached identity-based policy is refused AccessDeniedException with the message "User: <caller principal ARN> is not authorized to perform: chime:CreateMediaPipelineKinesisVideoStreamPool on resource: <media-pipeline-kinesis-video-stream-pool ARN pattern> because no identity-based policy allows the chime:CreateMediaPipelineKinesisVideoStreamPool action" — fixed text "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action"; variable parts are the caller's assumed-role principal ARN (from the credentials), the action name (service prefix + operation) and the resource ARN the action is authorized against. No pool is created under the denied attempt, while the same call with permissioned credentials succeeds.
Emulator: accepts the call from the unpermissioned assumed-role credentials and answers 201, minting and persisting a pool (PoolStatus CREATING) that AWS would never have created. No authorization decision is made for these credentials at all.
Why: least-privilege tests pass against the emulator and fail against AWS; code paths that handle AccessDeniedException (surfacing a permissions remediation message, refreshing credentials, failing the deploy) are unreachable, and state the real service would have refused accumulates in the emulator.
Fix: the request-authorization layer this service mounts (the authorization decision that runs before the operation handler), not the CreateMediaPipelineKinesisVideoStreamPool handler body — it must evaluate the caller's identity-based policy for chime:CreateMediaPipelineKinesisVideoStreamPool and refuse with AWS's AccessDeniedException wording.
Traces: chime-sdk-media-pipelines.create-media-pipeline-kinesis-video-stream-pool-missing-permission-rejected.
