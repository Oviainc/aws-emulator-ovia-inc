# EC2 DescribeInstanceTypes catalog rows omit modeled members and report generically derived performance values

> _Note: this issue was identified against the code base at commit `25868398053db3fb9f24c4ac75ab683f5b2a8f47`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
DescribeInstanceTypes answers HTTP 200 but the InstanceTypeInfo rows it serves are a narrower and partly fabricated projection of AWS's instance-type catalog: a set of modeled members is never emitted at all, and several numeric members are produced by one generic formula instead of carrying the per-instance-type value AWS publishes. This issue bundles 3 causes; all 3 must be closed. The same catalogue fault is visible on every step of the ec2-catalog-describe-instance-types-* fixtures (141 net-new clusters in this replay, one per catalog page); the three steps named below are its representatives and no open issue carries their replay keys (list_existing_issues finds no DescribeInstanceTypes issue at all).

Cause 1 of 3: modeled InstanceTypeInfo / NetworkInfo / EbsInfo members are omitted from every row.
AWS: Smithy: InstanceTypeInfo carries CpuBurstModel (xmlName 'cpuBurstModel'), PhcSupport ('phcSupport'), RebootMigrationSupport ('rebootMigrationSupport') and NetworkInfo ('networkInfo') whose NetworkInfo structure carries DefaultNetworkCardIndex, EnaSrdSupported, FlexibleEnaQueuesSupport, MaximumNetworkCards, NetworkCards, NetworkPerformance, SecondaryNetworkSupported, TrafficMirroringSupport, BandwidthWeightings, EfaSupported/EfaInfo and Ipv4AddressesPerSecondaryInterface; EbsInfo carries AttachmentLimitType ('attachmentLimitType'). The recordings show each of these present on each instanceTypeSet.item, with the value AWS publishes for that instance type (for example 'none' for cpuBurstModel on a general-purpose type, '0' for defaultNetworkCardIndex, '1' for maximumNetworkCards, and the bandwidthWeightings list ['default','ebs-1','vpc-1'] on r8g types).
Emulator: the members are absent from the serialized row entirely (reported as 'missing ... got None'), for every instance type in the page.
Why: a client that reads the catalogue to pick an instance type - a scheduler checking maximumNetworkCards or enaSrdSupported, a capacity planner reading networkPerformance, a sizing tool reading cpuBurstModel - gets a null where AWS always supplies a value, so the choice is made on absent data or the deserializer rejects the row.
Fix: the per-instance-type catalogue data behind the DescribeInstanceTypes handler and its InstanceTypeInfo projection - each modeled member must be populated per type rather than skipped.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#10 (c6a.* page), ec2-catalog-describe-instance-types-r5-r8in#task#21 (r8g.* page).

Cause 2 of 3: ebsOptimizedInfo, maximumEbsAttachments and attachmentLimitType are derived generically instead of per instance type.
AWS: Smithy: EbsOptimizedInfo.BaselineBandwidthInMbps/BaselineIops/BaselineThroughputInMBps/MaximumBandwidthInMbps/MaximumIops/MaximumThroughputInMBps and EbsInfo.MaximumEbsAttachments / EbsInfo.AttachmentLimitType ('Indicates whether the instance type features a shared or dedicated Amazon EBS volume attachment limit'). These are per-instance-type constants published by AWS; the recordings show them differing by type and size in a way no single size-scaling rule reproduces.
Emulator: every value is off, and consistently so, as if computed from vCPU count: on a c6a.32xlarge it answers baselineBandwidthInMbps 27200 / baselineIops 120000 / baselineThroughputInMBps 3400 / maximumBandwidthInMbps 27200 / maximumIops 120000 / maximumThroughputInMBps 3400 and maximumEbsAttachments 28 where AWS answers 40000 / 160000 / 5000.0 / 40000 / 160000 / 5000.0 and 27; on an r8g.medium it answers 287 / 1500 / 35.875 / 4750 / 18750 / 593.75 and maximumEbsAttachments 28 and attachmentLimitType 'shared' where AWS answers 315 / 2500 / 39.375 / 10000 / 40000 / 1250.0 and 32 and 'dedicated'.
Why: these numbers are exactly what EBS throughput planning and volume-attachment limit checks are read for, so a client sizing a workload or deciding how many volumes it may attach is given wrong figures that look authoritative, and a dedicated-limit type is reported as sharing its limit with the network.
Fix: the instance-type catalogue data - EbsInfo/EbsOptimizedInfo must be table values per instance type, not a formula in the DescribeInstanceTypes handler.
Traces: ec2-catalog-describe-instance-types-r5-r8in#task#21, ec2-catalog-describe-instance-types-a1-c9g#task#10, ec2-catalog-describe-instance-types-a1-c9g#task#11.

Cause 3 of 3: capability flags, sustained clock speed and the vCPU validCores list are wrong per type.
AWS: Smithy: InstanceTypeInfo.AutoRecoverySupported, HibernationSupported, NitroEnclavesSupport, NitroTpmSupport, ProcessorInfo.SustainedClockSpeedInGhz, NetworkInfo.EncryptionInTransitSupported and VCpuInfo.ValidCores (the set of core counts the type can be launched with). The recordings carry the published per-type values, and validCores enumerates one entry per supported core count for that type (for example 64 entries on a c6a.32xlarge, 192 on an r8g.48xlarge).
Emulator: the flags are inverted or defaulted per type (c6g.metal autoRecoverySupported 'false' where AWS says 'true'; c6g.metal networkInfo.encryptionInTransitSupported 'true' where AWS says 'false'), sustainedClockSpeedInGhz differs, and the validCores list is short - the trailing entries AWS returns are missing.
Why: a client that gates a feature on autoRecoverySupported, nitroTpmSupport or encryptionInTransitSupported takes the opposite branch from production, and a CPU-options caller that validates a requested core count against validCores has valid counts rejected.
Fix: the same catalogue data plus the VCpuInfo projection, which must enumerate the type's full validCores set.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#11 (c6g.* page), ec2-catalog-describe-instance-types-a1-c9g#task#10.
