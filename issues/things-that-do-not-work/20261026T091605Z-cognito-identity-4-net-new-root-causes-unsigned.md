# cognito-identity: 4 net-new root causes — unsigned sts:AssumeRoleWithWebIdentity answers UnknownService (as JSON on an XML client), AllowClassicFlow=False does not gate GetOpenIdToken, and the amr trust condition is never evaluated

> _Note: this issue was identified against the code base at commit `653181f0b0e0e3e935b382b574b4ea320d44c436`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetOpenIdToken

## Description
This issue bundles FOUR distinct root causes reached through cognito-identity behavioral checks that no open issue claims (none of the four checks is marked ALREADY FILED or OWNED in this replay). All four must be fixed and re-replayed before closing.

=== Cause 1 of 4: an unsigned (anonymous) sts AssumeRoleWithWebIdentity request is never routed to a service — the emulator answers UnknownService ===
AWS: Smithy: sts#AssumeRoleWithWebIdentity is modeled with "auth": [] and "optionalAuth": true, so SDKs send it with NO SigV4 signature even when the client holds credentials (botocore does exactly this for ctx.client("sts").assume_role_with_web_identity). AWS resolves the target service from the endpoint/Host and answers with the operation's own semantics: HTTP 200 carrying Credentials / AssumedRoleUser / SubjectFromWebIdentityToken / Provider / Audience, or one of its modeled awsQuery errors (InvalidIdentityToken 400, IDPRejectedClaim 403, ExpiredTokenException 400, MalformedPolicyDocument 400, RegionDisabledException 403). This call is the only way to redeem a Cognito basic/classic-flow OpenID token for credentials.
Emulator: the request is never dispatched to any service. The response body is {"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}. The whole message is fixed text — it interpolates nothing from the request. The cause is visible in the message itself: an unsigned request has no SigV4 credential scope, awsQuery carries no X-Amz-Target, and the router does not map the Host/endpoint it is reached on to sts, so routing falls through for every anonymous-capable query-protocol operation.
Why: the entire Cognito basic/classic flow (GetOpenIdToken -> sts:AssumeRoleWithWebIdentity -> temporary credentials) is dead end-to-end, and so is every other anonymous-capable query-protocol operation. A client gets an error code no SDK models instead of either credentials or a modeled refusal, so it cannot distinguish "token rejected" from "service missing".
Fix: the request router / front-door auth layer — resolve the target service for an unsigned request (from the endpoint/Host binding, or from the operation's optionalAuth / empty-auth binding) instead of requiring a SigV4 credential scope or an X-Amz-Target header to select the service.

This is a different router path, a different message, and a different target service (sts); neither check below is marked as owned by them.

=== Cause 2 of 4: the router's refusal is serialized as a JSON __type body for an awsQuery (XML) client, so the SDK cannot parse it into an error at all ===
AWS: sts speaks awsQuery. Every sts error — including a service-level/unroutable refusal — is an XML document of the form <ErrorResponse><Error><Type>..</Type><Code>..</Code><Message>..</Message></Error><RequestId>..</RequestId></ErrorResponse>, which is why the Smithy model gives each AssumeRoleWithWebIdentity error an awsQueryError code and httpResponseCode (e.g. InvalidIdentityToken/400, IDPRejectedClaim/403). The SDK therefore always surfaces a ClientError with a code and a message.
Emulator: it emits the awsJson error encoding {"__type":"UnknownService","message":"..."} regardless of the resolved client's protocol. botocore's query error parser raises botocore.parsers.ResponseParserError: Unable to parse response (not well-formed (invalid token): line 1, column 0), invalid XML received — so the call yields NO error code at all; it is not a ClientError.
Why: a client cannot classify, log, or branch on the failure, and retry logic treats it as a transient parse failure and loops ("Further retries may succeed"). Any check or application error handler that catches ClientError is bypassed entirely. This defect is independent of Cause 1: any unroutable or service-level refusal on sts/iam/cloudformation (awsQuery/restXml) is unparseable today.
Fix: the shared error serializer in the front-door/router — select the error encoding from the protocol of the resolved (or defaulted) service, emitting the awsQuery/restXml ErrorResponse document for XML protocols and the __type JSON body only for awsJson protocols.
Traces: cognito-identity.basic-flow-get-open-id-token-refused-while-role-mappings-are-configured, cognito-identity.classic-flow-open-id-token-assume-role-with-web-identity.

=== Cause 3 of 4: AllowClassicFlow=False does not gate GetOpenIdToken — the basic flow is served on a pool that forbids it ===
AWS: Smithy: CreateIdentityPoolInput.AllowClassicFlow is documented "Enables or disables the Basic (Classic) authentication flow", and GetOpenIdToken is the entry point of exactly that flow. On a pool whose AllowClassicFlow is false the call is refused, not served; GetOpenIdToken models InvalidParameterException (HTTP 400) and NotAuthorizedException (HTTP 403). Hypothesis: the refusal is HTTP 400 InvalidParameterException with the message "Basic (classic) flow is not enabled, please use enhanced flow." — the whole message is fixed text with no variable part. Neither the Smithy model nor a recording in this run quotes the code/message, and the check that asserts them is marked DRAFT/unblessed by its author; what is NOT hypothetical is that the emulator applies no gate whatsoever, which diverges from the documented meaning of the flag either way.
Emulator: GetOpenIdToken on a pool created with AllowClassicFlow=False returns HTTP 200 with a Token (388 characters observed) and the identity id. The flag round-trips correctly through CreateIdentityPool/DescribeIdentityPool (the check re-reads it as False after the call) but gates nothing.
Why: the basic flow lets the client pick its own IAM role, which is why AWS advises leaving the flag off; a pool deliberately configured to forbid it still mints tokens for it. A security-relevant pool setting is inert, and an application that relies on the refusal to prove the flow is shut off gets a false pass.
Fix: the GetOpenIdToken handler (and its validation) — read AllowClassicFlow from the identity pool's state and refuse the call when it is false, before minting a token; the refusal must mutate nothing (the pool's flag and the identity must survive it).
Traces: cognito-identity.allow-classic-flow-disabled-refuses-get-open-id-token.

=== Cause 4 of 4: the cognito-identity.amazonaws.com:amr trust condition is never evaluated and no assumed-role session is produced, so the amr check hangs to the harness cap ===
AWS: a role whose trust policy names Principal {"Federated": "cognito-identity.amazonaws.com"} for sts:AssumeRoleWithWebIdentity with Condition StringEquals cognito-identity.amazonaws.com:aud = <identity pool id> and ForAnyValue:StringLike cognito-identity.amazonaws.com:amr = <value> is assumable only by a login whose OpenID token amr list contains that value. A developer-authenticated login's token carries amr ["authenticated", <developer provider name>, ...] and a user-pool login's does not carry the developer provider, so the two are discriminated by the condition: the matching login gets credentials whose sts:GetCallerIdentity Arn is arn:aws:sts::<account>:assumed-role/<role name>/CognitoIdentityCredentials, and the non-matching login is refused by GetCredentialsForIdentity. Smithy: GetCredentialsForIdentity declares InvalidIdentityPoolConfigurationException with httpError 400. Hypothesis: that refusal's message is "Invalid identity pool configuration. Check assigned IAM roles for this pool." (fixed text, no variable part) — the model does not quote it and this run never produced it.
Emulator: the check never gets as far as the negative leg. Its positive control polls (240 s budget) for the developer-provider login to come back as a session of the amr-scoped role and never observes one, so the harness kills the check: "Error: Check timed out after 60.0s". Hypothesis for the exact hang point: the poll is the first blocking step after the amr-claim assertions, and the emulator's GetCredentialsForIdentity performs no trust-policy evaluation and returns no assumed-role session, so the predicate can never become true.
Why: amr-scoped trust policies are the standard way to separate a developer-authenticated backend from user-pool logins inside one identity pool. Against the emulator neither the condition nor the role session exists, so both logins are treated identically: an over-permissive pool configuration looks correct, and no tenant-isolation design on this mechanism can be validated. The failure also presents as a 60 s hang rather than an error, so it burns the whole harness budget.
Fix: the GetCredentialsForIdentity credential-vending path — resolve the pool's role, evaluate the role's trust policy against the minted token's claims (the cognito-identity.amazonaws.com:aud and :amr condition keys), return a genuine assumed-role session for a trusted match, and refuse with InvalidIdentityPoolConfigurationException when no role trusts the login.
