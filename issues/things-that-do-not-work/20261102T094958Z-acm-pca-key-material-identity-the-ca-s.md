# ACM PCA key-material identity: the CA's PKCS#10 CSR carries an unparseable SubjectPublicKeyInfo, and ImportCertificateAuthorityCertificate accepts a certificate whose public key differs from that CSR

> _Note: this issue was identified against the code base at commit `5ba72cc05e802971fb04990ddf25d58f3354550b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportCertificateAuthorityCertificate

## Description
TWO net-new root causes on the acm-pca CA-activation path. Neither failing check below is marked ALREADY FILED or OWNED in this replay. Two open issues name neighbouring surfaces and are called out per cause: 20261022T143159Z-acm-pca-private-ca-lifecycle-is-unusable-issuecertificate.md (its cause 2 is the placeholder CSR, its cause 3 is mismatched import) and 20261029T193511Z-acm-pca-certificate-path-issuecertificate-issues-leaves-that.md (its cause 4 is unparseable CA key material, its cause 6 is a mismatched-SUBJECT import). Neither carries these two checks' replay keys in this replay, and cause 2 below is a different diagnostic class than any of them.

Cause 1 of 2: GetCertificateAuthorityCsr returns a PEM CERTIFICATE REQUEST whose embedded public key is not valid DER, so the CA's key material cannot be read out of the CSR at all.
AWS: Smithy models GetCertificateAuthorityCsr {CertificateAuthorityArn @required (Arn, @length 5..200, pattern ^arn:[\w+=/,.@-]+:acm-pca:...)} -> output Csr (CsrBody), errors InvalidArnException, InvalidStateException, RequestFailedException, RequestInProgressException, ResourceNotFoundException (all 400). The content requirement is recorded behavior: Csr is a PEM-armoured PKCS#10 CertificationRequest over the key pair the service generated for the CA, carrying the configured ASN1Subject and a SubjectPublicKeyInfo for the CA's configured KeyAlgorithm; for KeyAlgorithm=RSA_2048 that SPKI loads as a 2048-bit RSA public key with any X.509 tooling, and the certificate IssueCertificate then mints from that CSR (TemplateArn arn:aws:acm-pca:::template/RootCACertificate/V1) must carry the SAME SubjectPublicKeyInfo, which is what makes the CSR-to-certificate identity verifiable.
Emulator: the PEM armour and the outer CertificationRequest structure parse (cryptography's load_pem_x509_csr succeeds and the Subject compares equal to the issued certificate's Subject), but reading the key out of it raises ValueError 'Could not deserialize key data. The data may be in an incorrect format, it may be encrypted with an unsupported algorithm, or it may be an unsupported key type (e.g. EC curves with explicit parameters). Details: ASN.1 parsing error: short data (needed at least N additional bytes)'. The byte count in that message is a per-run value; the requirement is only that the SPKI is a complete, well-formed RSA key of the configured algorithm. So the CSR's SubjectPublicKeyInfo is a truncated placeholder rather than a real key structure, and the public-key-preservation property between CSR and issued certificate is unobservable.
Why: every real consumer of this API parses this PEM — to have a parent CA sign a subordinate's CSR, to pin the CA key, or to verify that an issued certificate really encodes the CSR's key. With an unparseable SPKI no chain can be built or verified and a client cannot tell the emulator's placeholder from corrupt data; it also hides whether IssueCertificate re-generated key material server-side.
Fix: the CA key-pair and CSR generation in the service's CA state, plus the certificate assembly in IssueCertificate that must copy that SPKI into the issued certificate — mint a real key pair of the configured KeyAlgorithm and encode a real SubjectPublicKeyInfo. Same surface as cause 4 of 20261029T193511Z-acm-pca-certificate-path-issuecertificate-issues-leaves-that.md, which this replay does not report as owning this check.
Traces: acm-pca.csr-to-issued-certificate-pem-preserved (fails at csr_obj.public_key().public_numbers(), check line 63); services/service-com-amazonaws-acmpca-acmprivateca/src/ops/get_certificate_authority_csr.rs, src/ops/issue_certificate.rs, src/state.rs.

Cause 2 of 2: ImportCertificateAuthorityCertificate accepts a self-signed certificate that carries the CA's own subject but a DIFFERENT public key, instead of refusing it as a public-key mismatch.
AWS: Smithy models ImportCertificateAuthorityCertificate {CertificateAuthorityArn @required, Certificate @required (CertificateBodyBlob @length 1..32768), CertificateChain (@length 0..2097152)} -> Unit, with CertificateMismatchException among its errors (modelled doc: 'The certificate authority certificate you are importing does not comply with conditions specified in the certificate that signed it'), httpError 400. The specific diagnostic is recorded behavior: when the submitted certificate's subject MATCHES the CA's outstanding CSR but its SubjectPublicKeyInfo does not, the call is refused with HTTP 400, error code CertificateMismatchException and the message 'The certificate subject public key info field contains a different public key or key algorithm than the CA certificate signing request.' — that sentence is fixed text in full, with no part taken from the request or from state — and the CA stays in PENDING_CERTIFICATE with no certificate installed (GetCertificateAuthorityCertificate still refuses). This is a DISTINCT classification from the subject-mismatch message AWS uses when the subject itself differs: the two are told apart by which field diverges.
Emulator: answers HTTP 200 with an empty JSON body (content-type application/x-amz-json-1.1, content-length 2) and installs the foreign certificate — no error is raised at all.
Why: the CA is activated with a certificate whose private key the service does not hold, so every certificate it subsequently signs is unverifiable against the installed CA certificate, and ACM PCA offers no way to undo an import. The client's mismatch-handling branch is never exercised, and because the emulator never distinguishes a key mismatch from a subject mismatch, a client cannot tell which field it got wrong.
Fix: ImportCertificateAuthorityCertificate's validation — before any state mutation, compare the submitted certificate's subject AND its SubjectPublicKeyInfo against the CA's outstanding CSR, and refuse with CertificateMismatchException carrying the public-key-info sentence when the subject matches but the key or key algorithm does not (and the subject sentence when the subject differs). Related: cause 6 of 20261029T193511Z-acm-pca-certificate-path-issuecertificate-issues-leaves-that.md covers the subject-mismatch message only, and cause 3 of 20261022T143159Z-acm-pca-private-ca-lifecycle-is-unusable-issuecertificate.md names the import surface generally; neither carries this check or this diagnostic.
Traces: acm-pca.import-certificate-mismatch-rejected (check lines 53/100); handler services/service-com-amazonaws-acmpca-acmprivateca/src/ops/import_certificate_authority_certificate.rs.

## Steps to Reproduce
Common setup: acmpca.create_certificate_authority(CertificateAuthorityConfiguration={'KeyAlgorithm':'RSA_2048','SigningAlgorithm':'SHA256WITHRSA','Subject':{...}}, CertificateAuthorityType='ROOT'), then poll DescribeCertificateAuthority until Status == 'PENDING_CERTIFICATE'.

Cause 1: csr = acmpca.get_certificate_authority_csr(CertificateAuthorityArn=arn)['Csr']; cryptography.x509.load_pem_x509_csr(csr.encode('ascii')).public_key().public_numbers() must succeed and yield a 2048-bit RSA key. Then issue_certificate(CertificateAuthorityArn=arn, Csr=csr, SigningAlgorithm='SHA256WITHRSA', TemplateArn='arn:aws:acm-pca:::template/RootCACertificate/V1', Validity={'Value':10,'Type':'YEARS'}), get_certificate(...) and load the PEM: the certificate's public-key (n, e) must equal the CSR's, and its BasicConstraints must be CA=TRUE.

Cause 2: build a self-signed certificate with x509.CertificateBuilder whose subject_name and issuer_name are exactly the CA's configured Subject (so only the key differs) and whose public_key() is a freshly generated, unrelated RSA-2048 key, signed by that same unrelated key with SHA256, add BasicConstraints(ca=True) critical, serialise to PEM. Call acmpca.import_certificate_authority_certificate(CertificateAuthorityArn=<the PENDING_CERTIFICATE CA>, Certificate=<that PEM>) -> must be HTTP 400 CertificateMismatchException with message 'The certificate subject public key info field contains a different public key or key algorithm than the CA certificate signing request.'; DescribeCertificateAuthority must still report PENDING_CERTIFICATE and GetCertificateAuthorityCertificate must still refuse. Then activate the SAME CA with its own CSR (GetCertificateAuthorityCsr -> IssueCertificate with RootCACertificate/V1 -> GetCertificate -> ImportCertificateAuthorityCertificate): it must reach ACTIVE, proving the earlier refusal was about the key mismatch and not a blanket refusal.
