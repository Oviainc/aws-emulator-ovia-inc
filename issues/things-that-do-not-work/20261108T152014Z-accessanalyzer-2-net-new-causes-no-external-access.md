# accessanalyzer: 2 net-new causes — no external-access finding is ever derived for an SQS queue policy (ListFindings stays empty forever), and ApplyArchiveRule is still a 501 scaffold so no finding can be archived

> _Note: this issue was identified against the code base at commit `32a26f18a0fb4dc356c9d3ce1ecec069a0aff304`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
Two net-new root causes, both grounded in the single failing check accessanalyzer.apply-archive-rule-archives-real-finding-end-to-end, which the suite reports as [mismatch] 'Check timed out after 180.0s'. The check is NOT marked ALREADY FILED or OWNED by the report. Note on neighbouring issues: the open issue 20261029T194301Z-accessanalyzer-listfindings-stub.md carries this check's replay key, but it describes ListFindings as an unimplemented 501 scaffold and ListFindings is now implemented (services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/ops/list_findings.rs has a real handler and no SCAFFOLDED marker) — it does not cover either cause below. The fixed issue 20261022T015008Z-accessanalyzer-applyarchiverule-end-to-end-finding-archival-path.md deferred this same check to SQS CreateQueue; SQS now answers, the check no longer fails on a refusal, and (as that issue itself anticipated) the residual divergence is in accessanalyzer's finding derivation and in ApplyArchiveRule.

Cause 1 of 2: an external-access analyzer never reports a finding for an Amazon SQS queue whose queue policy grants access to every principal, so ListFindings answers an empty findings list for that queue forever. Failing check ids: accessanalyzer.apply-archive-rule-archives-real-finding-end-to-end.
AWS: Smithy (services/service-com-amazonaws-accessanalyzer-accessanalyzer/smithy-model/com-amazonaws-accessanalyzer-accessanalyzer.json): com.amazonaws.accessanalyzer#ResourceType enumerates 'AWS::SQS::Queue' alongside 'AWS::S3::Bucket' and 'AWS::IAM::Role', so an SQS queue is a resource type an external-access analyzer reports on; FindingStatus = ACTIVE | ARCHIVED | RESOLVED; StartResourceScan takes analyzerArn + resourceArn and immediately scans the named resource. AWS behaviour: an ACCOUNT external-access analyzer monitoring an account that holds a queue whose resource policy has an Allow statement with Principal '*' (no caller-binding Condition) reports one ACTIVE finding for that queue, with resource = the queue ARN, resourceType = 'AWS::SQS::Queue', isPublic = true, action = the statement's Action list, and ListFindings(filter={resource:{eq:[queueArn]}}) returns it.
Emulator: ListFindings derives findings only from the resource-based policies the emulator holds for two resource types — crate::state::monitored_resources() calls iam_roles() and s3_buckets() and nothing else (its own doc says so: 'AWS::IAM::Role — the role's trust policy; AWS::S3::Bucket — the bucket policy', and 'A resource type whose policy no service of this emulator holds yet contributes nothing'). The SQS store's queue Policy attribute is never read, so no AWS::SQS::Queue finding can exist: after CreateQueue + SetQueueAttributes(Policy=public) + StartResourceScan, ListFindings for the queue ARN keeps answering 200 with findings = [] indefinitely. The check's bounded poll for an ACTIVE finding therefore never terminates and the check is killed at the 180 s budget without ever reaching the archive-rule legs.
Why: a client that provisions a publicly-shared queue and relies on Access Analyzer to detect it sees a clean account — the very detection the service exists for silently reports nothing, with no error to distinguish 'no external access' from 'this resource type is not analyzed'. Every workflow keyed on a queue finding (triage, archive rules, ListFindings/GetFinding) is unreachable.
Fix: the external-access analysis's monitored-resource providers — add an SQS provider to crate::state::monitored_resources alongside iam_roles/s3_buckets that reads each queue's Policy attribute out of the SQS service's store and contributes a MonitoredResource with resource_type 'AWS::SQS::Queue' and the queue ARN, so the shared external_access_findings analysis (used by both ListFindings and the access-preview path) produces the ACTIVE finding. StartResourceScan on a queue ARN must make that resource analyzed rather than only recording a ResourceScan.
Traces: accessanalyzer.apply-archive-rule-archives-real-finding-end-to-end (hangs in its list_findings poll for the queue ARN; code citation: services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/state/external_access.rs lines 20-32 and 217-228).

Cause 2 of 2: ApplyArchiveRule is an unimplemented scaffold, so an existing ACTIVE finding can never be retroactively flipped to ARCHIVED. Failing check ids: accessanalyzer.apply-archive-rule-archives-real-finding-end-to-end.
AWS: Smithy: ApplyArchiveRule is PUT /archive-rule with required analyzerArn (pattern ^[^:]*:[^:]*:[^:]*:[^:]*:[^:]*:analyzer/.{1,255}$) and required ruleName, an optional idempotencyToken clientToken, an empty (Unit) output answered 200, and modeled errors AccessDeniedException (403), InternalServerException (500), ResourceNotFoundException (404), ThrottlingException (429), ValidationException (400). Documented behaviour: 'Retroactively applies the archive rule to existing findings that meet the archive rule criteria' — so after ApplyArchiveRule(analyzerArn, ruleName) for a rule whose filter matches an existing ACTIVE finding, GetFinding for that finding id reports status 'ARCHIVED' (the same finding id, retained, not deleted).
Emulator: services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/ops/apply_archive_rule.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED:' marker and its handle() returns Err(crate::scaffolded::Scaffolded::not_implemented("ApplyArchiveRule")), i.e. HTTP 501 with error code 'NotImplemented' and message 'operation ApplyArchiveRule is scaffolded but not implemented in this emulator', instead of 200 with an empty body. The crate acknowledges the gap in state/external_access.rs ('ARCHIVED is what an archive rule produces (ApplyArchiveRule is itself still scaffolded, with an issue of its own)') but the only such issue, 20261022T015008Z-..., is RESOLVED and covered the SQS CreateQueue refusal, not this stub. The analysis is also purely derived with status hard-coded to ACTIVE (FINDING_STATUS_ACTIVE), so there is no place for an archived status to live even once the call is accepted.
Why: a client cannot complete the findings lifecycle (derive -> ACTIVE -> ApplyArchiveRule -> ARCHIVED). A 501 is not a modeled error for this operation, so SDK retry/error handling has no branch for it, and the archive-rule feature is inert: rules can be created and listed but never suppress anything.
Fix: implement the handler in services/service-com-amazonaws-accessanalyzer-accessanalyzer/src/ops/apply_archive_rule.rs (resolve analyzerArn to a stored analyzer — 404 ResourceNotFoundException otherwise — and the ruleName to one of its archive_rules, then record that the matching derived findings are archived so GetFinding/ListFindings report status ARCHIVED for the same finding ids), extend the shared finding derivation in src/state/external_access.rs so a finding's status is not hard-coded ACTIVE, and delete that file's SCAFFOLDED marker line once implemented.
Traces: accessanalyzer.apply-archive-rule-archives-real-finding-end-to-end (never reaches the ApplyArchiveRule leg today because Cause 1 blocks it first; apply_archive_rule.rs lines 4 and 183).
