# lambda: a durable execution's wait_for_callback never starts, so no CallbackStartedDetails/CallbackTimedOutDetails is ever recorded and the late-callback CallbackTimeoutException refusal (400, "The callback is either timed out or already completed") can never be observed

> _Note: this issue was identified against the code base at commit `0568eb97aa29b2749d69ef4a06e4ccfaa6de4f80`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
One net-new root cause in the `lambda` service, grounded in a failing behavioral check of this suite that the replay report marks neither ALREADY FILED nor OWNED.

=== Cause 1 of 1: a durable execution started through Invoke never reaches its wait_for_callback checkpoint, so no callback is ever minted, no callback timeout is ever recorded, and the three late-callback refusals cannot be reached ===
Failing check (1): lambda.callback-timeout-exceeded-rejected.

AWS: Invoke starts a named durable execution (Smithy: Invoke input member DurableExecutionName @httpHeader("X-Amz-Durable-Execution-Name"), output member DurableExecutionArn @httpHeader("X-Amz-Durable-Execution-Arn")) and then RUNS the handler. When the durable SDK handler calls `context.wait_for_callback(notify, name=..., config=WaitForCallbackConfig(timeout=Duration.from_seconds(N)))`, Lambda mints a CallbackId and records it in the execution history as a `CallbackStartedDetails` event (readable through GetDurableExecutionHistory). When the configured callback timeout elapses without a callback, Lambda records a `CallbackTimedOutDetails` event for that callback and closes it. Every subsequent callback API on that closed CallbackId is then refused: Smithy models `SendDurableExecutionCallbackSuccess` (POST /2025-12-01/durable-execution-callbacks/{CallbackId}/succeed), `SendDurableExecutionCallbackHeartbeat` (.../heartbeat) and `SendDurableExecutionCallbackFailure` (.../fail) each with the error `CallbackTimeoutException` @httpError(400), documented as "The callback ID token has either expired or the callback associated with the token has already been closed". The refusal is a requirement: HTTP 400, error code `CallbackTimeoutException`, and the message `The callback is either timed out or already completed` — that text is entirely FIXED, it carries no values from the request or from state. In the same check an in-window callback on a second, long-timeout execution on the same function must be ACCEPTED (HTTP 200), so the distinction between an open and a timed-out callback is what is under test.

Emulator: the durable execution is accepted and registered but never executed, so the handler's `wait_for_callback` never runs. GetDurableExecutionHistory never yields a `CallbackStartedDetails` event, so no CallbackId exists for the positive control or for the timeout case, and no `CallbackTimedOutDetails` event is ever appended either (the only transition the durable slice applies is the clock-owed RUNNING -> TIMED_OUT of the whole execution, not a per-callback timeout). The check blocks in its bounded poll for the first CallbackId and the runner cuts it off: `Error: Check timed out after 60.0s`. Nothing in the check was refused and no unimplemented operation was reached — every call it made was accepted. Downstream of that block the three callback operations are also still 501 `NotImplemented` scaffolds (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/send_durable_execution_callback_success.rs, .../send_durable_execution_callback_heartbeat.rs, .../send_durable_execution_callback_failure.rs, each carrying the `//! SCAFFOLDED, NOT IMPLEMENTED` marker), so even with a CallbackId the check could only ever see 501/NotImplemented where AWS answers 200 for an in-window callback and 400 CallbackTimeoutException for a late one.

Why: a client that implements the documented external-callback pattern cannot distinguish an open callback from an expired one. It never receives the CallbackId its own handler was asked to publish, so it hangs; and the refusal taxonomy it codes against — treat `CallbackTimeoutException` as "too late, stop retrying" and anything else as retryable — is unreachable, so retry/compensation logic written against AWS is never exercised and a late success/heartbeat/failure is never rejected the way AWS rejects it.

Fix: the Invoke handler's durable path plus the durable-execution slice of the lambda service's state — a started execution must actually be driven so that `wait_for_callback` mints a CallbackId, appends a `CallbackStartedDetails` history event, and appends a `CallbackTimedOutDetails` event and closes the callback when the configured callback timeout falls due; and the three `SendDurableExecutionCallback*` handlers must resolve a CallbackId against that state, answering 200 for an open callback and the modeled 400 `CallbackTimeoutException` with the fixed message above for one that has timed out or already completed. Related open issue 20261027T203721Z-lambda-3-net-new-root-causes-a-durable.md describes the same inert durable runtime for six OTHER checks but does not carry this check's replay key, and its callback coverage stops at success/heartbeat on a still-open callback — the per-callback TIMEOUT recording and the late-callback refusal taxonomy on all three callback operations are not covered there. 20261026T070343Z-events-lambda-sqs-lambda-invoke-on-a-durable-execution-function-returns.md covers only the missing X-Amz-Durable-Execution-Arn header (this check works around it via ListDurableExecutionsByFunction), and 20261027T191349Z-events-lambda-sqs-lambda-durable-execution-status-change-events-are-never.md covers only the missing status-change events.

Traces: lambda.callback-timeout-exceeded-rejected. Handler: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs (durable path) and .../src/ops/send_durable_execution_callback_{success,heartbeat,failure}.rs; state: services/service-com-amazonaws-lambda-awsgirapiservice/src/state.rs (the durable-execution records and their materialize).

## Evidence
Expected (AWS, and the behavior this check's oracle asserts):
1) CreateFunction(Runtime='python3.13', Handler='lambda_function.lambda_handler', DurableConfig={ExecutionTimeout:300, RetentionPeriodInDays:1}) reaches State=Active.
2) Invoke(FunctionName=<fn>, Qualifier='$LATEST', InvocationType='Event', DurableExecutionName=<name>, Payload={"timeoutSeconds":120,"heartbeatTimeoutSeconds":0}) answers StatusCode 202, and the handler runs: GetDurableExecutionHistory(DurableExecutionArn=<arn>) contains an event with CallbackStartedDetails.CallbackId.
3) SendDurableExecutionCallbackSuccess(CallbackId=<that id>, Result=b'{}') on that in-window callback is ACCEPTED (HTTP 200).
4) A second execution with Payload={"timeoutSeconds":8,"heartbeatTimeoutSeconds":0} reaches its own CallbackStartedDetails, and after ~8s the history contains an event with CallbackTimedOutDetails.
5) Each of SendDurableExecutionCallbackSuccess(CallbackId=<expired>, Result=b'{}'), SendDurableExecutionCallbackHeartbeat(CallbackId=<expired>) and SendDurableExecutionCallbackFailure(CallbackId=<expired>, Error={ErrorMessage:'too-late', ErrorType:'TestError'}) is refused with HTTP 400, Error.Code == 'CallbackTimeoutException' and Error.Message == 'The callback is either timed out or already completed' (fixed text; no request- or state-derived parts).

Actual (emulator): the 202 and the registered execution are the last things that happen. GetDurableExecutionHistory never produces a CallbackStartedDetails event for either execution, so the check's bounded poll for the first CallbackId never completes and the replay reports, for lambda.callback-timeout-exceeded-rejected:
  Error: Check timed out after 60.0s
No CallbackTimedOutDetails event is ever recorded either. The three late-callback refusals are therefore never exercised; the handlers that would have to produce them are still scaffolds that answer HTTP 501 `NotImplemented` ("operation SendDurableExecutionCallbackSuccess is scaffolded but not implemented in this emulator"), i.e. neither the accepted in-window callback (200) nor the 400 `CallbackTimeoutException` is reachable. Function names and execution names in this run are generated per run and are not part of the requirement; the requirement is the history events, the 200 for an open callback, and the 400 + `CallbackTimeoutException` + the exact message text for a closed one.

Wait for State=Active.
3) Positive control: lambda:Invoke(FunctionName=<fn>, Qualifier='$LATEST', InvocationType='Event', DurableExecutionName=<name-a>, Payload={"timeoutSeconds":120,"heartbeatTimeoutSeconds":0}); resolve the execution ARN from the response's DurableExecutionArn or via lambda:ListDurableExecutionsByFunction; poll lambda:GetDurableExecutionHistory(DurableExecutionArn=<arn-a>) for an event carrying CallbackStartedDetails.
