# rds-data: 4 net-new root causes — an empty transactionId is refused instead of treated as absent, a MONEY result column is returned instead of refused, a non-finite float8 cast evaluates to 0.0 instead of being refused, and a typeHint'ed/non-string parameter is not checked against the target column's type

## Description
Four net-new root causes in the rds-data Data API, all reached through ExecuteStatement. A fixer must close all four before submitting. Related but NOT covering any of them: the open issue 20261108T050629Z-rds-data-5-net-new-root-causes-an.md (its cause 4 describes the NaN sibling of cause 3 below, measured on a different check and carrying a different replay key), 20261023T045849Z-rds-data-skips-resource-secret-and-transaction-preconditions.md and 20261107T062403Z-rds-data-a-terminated-transaction-is-forgotten-so.md (both about transaction-id lookup classes, neither about an EMPTY id).

Cause 1 of 4: an empty `transactionId` is refused as a validation fault instead of being treated as absent.
AWS: Smithy rdsdataservice ExecuteStatement$transactionId targets `Id` (@length max 192, no minimum), so an empty string passes the model's own constraints; its doc says "If the SQL statement is not part of a transaction, don't set this parameter." Recorded behavior: ExecuteStatement with transactionId="" and sql="SELECT 1" is ACCEPTED with HTTP 200 and answers exactly {"records": [[{"longValue": 1}]], "numberOfRecordsUpdated": 0} — the empty value is read as no transaction at all and the statement runs standalone and auto-commits. ValidationException is reserved for a value that could not be an id of the resource.
Emulator: HTTP 400 ValidationException with the message "Invalid transaction ID" (entirely fixed text), raised before the statement runs, so the call never reaches the engine. The chain's last leg short-circuits on `Some("")`: services/service-com-amazonaws-rdsdata-rdsdataservice/src/state/preconditions.rs, `require_a_transaction_id_of_the_resource` returns Ok only for `None`, and `super::transaction_id_names_resource("", resource_arn)` is false for the empty string.
Why: SDK and ORM layers that always populate the member and leave it empty when there is no transaction (the common "pass the field through" pattern) have every single statement refused against the emulator while the identical code works on AWS; the whole check beyond that point is unreachable. A second, latent consequence of the same read: execute_statement.rs drops the request's `database` whenever `transaction_id` is `Some(_)` (lines 270-273), so an empty id would also silently discard the database the call selected.
Fix: the transaction-id leg of the precondition chain (state/preconditions.rs `require_a_transaction_id_of_the_resource`) and the `transaction_id` reads in ops/execute_statement.rs and ops/batch_execute_statement.rs — an empty `transactionId` must be normalised to "absent" before the chain and before the database-selection decision.
Traces: rds-data.rds-data-concurrent-transactions-independent-and-dead-transaction-ids-refuse-apart (the uncaught ClientError on `ExecuteStatement("SELECT 1", transactionId="")`; every earlier leg of that check — two concurrently open transactions, READ COMMITTED visibility, commit/rollback bodies, terminated- and aborted-id refusals — had already passed).

Cause 2 of 4: a result column of PostgreSQL's `money` type is returned as a double instead of being refused as an unsupported result type.
AWS: Smithy models UnsupportedResultException as errorKind client @httpError(400), documented "There was a problem with the result because of one of the following conditions: It contained an unsupported data type …". Recorded behavior: `SELECT <money column> FROM <table>` is refused with HTTP 400 UnsupportedResultException and the message "The result contains the unsupported data type MONEY." — fixed text "The result contains the unsupported data type " + the offending type's name upper-cased + "." — and the refusal is identical in the column form and under formatRecordsAs=JSON. The same cell IS readable once cast (`SELECT mny::numeric` answers stringValue, typeName "numeric", precision 0, tableName ""), which is what makes the refusal a property of the type and not of the row.
Emulator: the call is ACCEPTED with HTTP 200 and returns {'records': [[{'doubleValue': 12.34}]], 'numberOfRecordsUpdated': 0}. The type catalog has no `money` entry, so state/postgres.rs `pg_type` falls through to its default arm (`PgType::of(&name, TypeClass::Other, jdbc::OTHER, UNLIMITED_LENGTH, 0).takes_text()`), which leaves `refusal: None`; `require_returnable` in state.rs therefore finds nothing to refuse, exactly where the sibling `interval` arm calls `.unreturnable()`.
Why: a client is handed a doubleValue for a currency column whose exact value AWS refuses to transport, so money amounts silently lose exactness (and carry no currency), and the UnsupportedResultException branch the client is written to handle never fires. Because the default arm also sets `takes_text`, the same gap makes money columns silently writable from unhinted strings.
Fix: the PostgreSQL type catalog in state/postgres.rs `pg_type` — give `money` (and the other types with no `Field` member) a catalog entry marked unreturnable so state.rs `require_returnable` refuses the result in both the records and the formattedRecords forms.
Traces: rds-data.rds-data-column-metadata-members-and-result-set-options-under-json (its 14-member ColumnMetadata and self-join legs passed; it fails on the first money read).

Cause 3 of 4: a non-finite float8 produced by a cast is evaluated to 0.0, so it is neither returned nor refused.
AWS: recorded behavior — `SELECT 'inf'::float8 AS inf` is refused with HTTP 400 UnsupportedResultException and the fixed message "NaN and Infinity values are not supported", which must stay distinguishable from the unsupported-type sentence of cause 2 (the same check grades `SELECT '1 day'::interval` separately and that leg passes today).
Emulator: the call is ACCEPTED with HTTP 200 and returns {'records': [[{'doubleValue': 0.0}]], 'numberOfRecordsUpdated': 0}. The non-finite guards exist (state.rs `field_for`/`json_for` return SqlError::UnsupportedResult(postgres::NON_FINITE_FLOAT) for `SqlValue::Real(n) if !n.is_finite()`), but they never see a non-finite value: the PostgreSQL front end renders `'inf'::float8` as a cast the backing engine evaluates to 0.0, so the infinity is lost before the result is shaped.
Why: the caller gets 0.0 where the database holds +Infinity, with no error anywhere — totals, comparisons and averages computed from that cell are wrong, and the modelled refusal class never appears. The value is also wrong for any client that merely stores it.
Fix: the cast/literal rendering in state/postgres.rs (a cast of 'inf'/'-inf'/'NaN' to a floating type must produce the non-finite value, not 0.0) so the existing non-finite guard in state.rs `field_for`/`json_for` refuses the result with UnsupportedResultException(400, "NaN and Infinity values are not supported").
Traces: rds-data.typed-value-round-trip (the INTERVAL refusal leg immediately above it passes, so the two UnsupportedResultException classes are not collapsed — only the non-finite one is missing).

Cause 4 of 4: a parameter is checked for assignability to its target column ONLY when it is an unhinted stringValue, so a typeHint'ed value or a non-string Field bound into an incompatible column is accepted and the row lands.
AWS: Smithy SqlParameter$typeHint is an enum of JSON | UUID | TIMESTAMP | DATE | TIME | DECIMAL, each documented as the object type "the corresponding String parameter value is sent as … to the database" — so a JSON-hinted string reaches the engine as jsonb, and the engine applies its ordinary assignment rules. Recorded behavior: `INSERT INTO <t> (id, i) VALUES (2, :p)` with parameter p = stringValue '{"a":1}' and typeHint JSON, where column `i` is `integer`, is refused with HTTP 400 DatabaseErrorException carrying the engine's SQLSTATE 42804 diagnostic: fixed text 'ERROR: column "' … '" is of type ' … ' but expression is of type ' … '; Hint: You will need to rewrite or cast the expression.; Position: ' … '; SQLState: 42804', whose variable parts are the column name and its declared type from state, the sent expression's type from the parameter (jsonb here) and the character offset of the value in the submitted statement. The same refusal class covers a UUID hint carried on a longValue (expression type bigint) and a booleanValue written into an integer column, and nothing may be written.
Emulator: the call is ACCEPTED with HTTP 200 and returns {'numberOfRecordsUpdated': 1, 'generatedFields': []} — the row lands. state.rs `require_assignable_values` only considers parameters where `parameter.type_hint.is_none() && matches!(value, Some(Field::stringValue(_)))`, and `hinted_text` then binds all six hints as TEXT, which the backing engine stores into an integer column without complaint; non-string Field members are never checked against the column at all.
Why: writes AWS rejects are persisted with a wrong-typed value, so a client that relies on the database to police its column types silently corrupts rows (an integer column holding a JSON document), and the DatabaseErrorException/42804 branch it handles never fires. The unhinted-string legs of the same check pass, so the gap is specifically the hinted and non-string paths.
Fix: state.rs `require_assignable_values` / `sql_value_for` — derive the type each parameter is SENT AS (the hint's type for a hinted string, the Field member's type otherwise) and check it against the assigned column's declared type, refusing with the engine's 42804 assignment diagnostic before the statement is applied; the same path serves BatchExecuteStatement.
Traces: rds-data.rds-data-type-hint-is-required-for-engine-typed-parameters (its unhinted-string 42804 legs and its unparseable-hint legs pass; it fails on the first hinted/mismatched-member leg, so the UUID-on-longValue and booleanValue-into-integer legs after it were never reached).
