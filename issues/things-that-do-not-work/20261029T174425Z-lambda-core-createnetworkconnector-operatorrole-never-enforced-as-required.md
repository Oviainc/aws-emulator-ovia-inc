# lambda-core CreateNetworkConnector: OperatorRole never enforced as required for VPC_EGRESS, ClientToken replay ignores a changed Configuration, and the duplicate-name 409 message uses the wrong sentence (3 causes)

> _Note: this issue was identified against the code base at commit `42eb24959c6a4eb33ac3ba3d48b702ee83f6032d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateNetworkConnector

## Description
Three net-new root causes in the lambda-core network-connector control plane, found by replaying the behavioral suite (lambda-core scored 5/26 overall; 21 lambda-core checks failed, of which the ALREADY-FILED EC2/microvm scaffold blocks and the checks OWNED by 20261024T113459Z-lambda-core-network-connectors-clienttoken-reuse-never-refused.md and 20261029T071743Z-lambda-core-updatenetworkconnector-s-pending-state-resourceconflictexception-message.md are excluded here). Two of the three make CreateNetworkConnector ACCEPT (HTTP 202) a request real AWS REFUSES; the third states a refusal AWS does make by a different rule than the service uses.

Related open issues, neither of which covers the causes below: 20261024T113459Z-lambda-core-network-connectors-clienttoken-reuse-never-refused.md (its Cause 1 is the ClientToken fingerprint for a changed *Name*, grounded in lambda-core.client-token-replay-rejects-changed-parameters; its Cause 3 is an *unusable* OperatorRole, grounded in lambda-core.create-rejected-with-unusable-operator-role) and 20261023T022015Z-lambda-core-admits-requests-aws-refuses-and-misclassifies.md (a WIRE issue about EC2-reference validation and identifier classification). Cause 1 below is the OMITTED-role conditional requirement, not an unusable role; Cause 2 is the changed-Configuration replay, whose replay keys no open issue carries; Cause 3 is the duplicate-name message, which no open issue mentions.

--- Cause 1 of 3: CreateNetworkConnector accepts a VPC_EGRESS connector with NO OperatorRole at all. ---
AWS: Smithy (com.amazonaws.lambdacore) CreateNetworkConnector.OperatorRole -> NetworkConnectorRoleArn (@length 0..10000, pattern ^arn:(aws[a-zA-Z-]*)?:iam::\d{12}:role/?[a-zA-Z_0-9+=,.@\-_/]+$) carries NO @required trait, and the operation models InvalidParameterValueException (httpError 400). The member's model doc states it is "the IAM role that Lambda assumes to manage elastic network interfaces in your VPC" — i.e. the connector cannot exist without one. Recorded behavior: the requirement is CONDITIONAL on the connector type the Configuration selects, and a request whose Configuration is a VpcEgressConfiguration but which omits OperatorRole is refused synchronously with HTTP 400 / InvalidParameterValueException and the service's fixed sentence for this error class, "NetworkConnectorOperatorRole is required for VPC_EGRESS connector type" (fixed text throughout; the connector type token is the type implied by the request's Configuration — VPC_EGRESS for a VpcEgressConfiguration). The refusal creates nothing: ListNetworkConnectors shows no connector under that Name. The byte-identical payload WITH a usable OperatorRole is accepted (202, State PENDING).
Emulator: services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/ops/create_network_connector.rs never looks at input.operator_role before persisting. The handler checks, in order, the idempotency token, Name uniqueness and the connector quota, then mints the connector and stores operator_role verbatim as None on the version. The request is answered 202 PENDING and the connector is enumerated by List. Both checks report it as "the call unexpectedly SUCCEEDED; real AWS rejects it".
Why: a client that forgot the role — or whose template never set it — is told its connector is provisioning. The connector then reports ACTIVE, so the caller ships a connector that in real AWS could never have been created, and every negative test of this conditional requirement passes against a service that enforces nothing. Because the member is not @required in the model, no amount of schema-driven validation catches it; it must be a handler rule.
Fix: CreateNetworkConnector's input validation in its handler (services/service-com-amazonaws-lambdacore-lambdacoreapiservice/src/ops/create_network_connector.rs, ahead of the name/quota checks and before any state is written) must require OperatorRole whenever the Configuration is a VpcEgressConfiguration and raise InvalidParameterValueException with the service's sentence. This is distinct from the unusable-role validation of 20261024T113459Z Cause 3: that cause validates a role that IS supplied; this one is the presence rule, and it must fire before any role resolution.
Traces: lambda-core.create-network-connector-operator-role-required-rejected, lambda-core.create-rejected-without-operator-role.

--- Cause 2 of 3: a ClientToken replayed with the SAME Name but a DIFFERENT Configuration is served as an idempotent replay instead of being refused. ---
AWS: Smithy CreateNetworkConnector.ClientToken -> ClientTokenString (@idempotencyToken, @length 1..64); the operation models ResourceConflictException (httpError 409). The operation's model doc scopes idempotency to "if you retry a request that completed successfully using the same client token, the operation returns the existing connector without creating a duplicate" — the token is bound to the whole parameter set it first carried, not to the Name alone. Recorded behavior: the same token presented with the same Name but a Configuration naming a different subnet is refused with HTTP 409 / ResourceConflictException and the service's fixed sentence for a token/parameter mismatch, "A request with the same client token but different parameters was already submitted" (entirely fixed text — no request or state values interpolated). The rejected attempt mutates nothing: the original connector's Configuration.VpcEgressConfiguration.SubnetIds still serve the ORIGINAL subnet, and the account still holds exactly one connector by that Name. A replay with the token AND identical parameters still returns the original Id/Arn.
Emulator: create_network_connector.rs keys idempotency on the token alone — store.idempotency maps the token to a crate::state::TokenOutcome of (name, version) only (src/state.rs, written by store.remember_token at the end of handle), with no fingerprint of Configuration, OperatorRole or Tags. The replay branch (the `if let Some(outcome) = replayed` block) therefore returns 202 carrying the ORIGINAL connector for a request whose Configuration differs. The check reports "the mismatched-token create unexpectedly SUCCEEDED; real AWS rejects it".
Why: a client that corrected its Configuration but reused its retry token is handed back the OLD connector as if the new configuration had been applied. The connector keeps routing over the old subnets, the client never learns its request was discarded, and the 409 that exists to surface exactly this silent-idempotency data loss never fires. Note for the fixer: 20261024T113459Z Cause 1 names the same handler gap from a changed-*Name* replay, but does not carry this check's replay key, and a fingerprint that covers only Name would still pass that cause's check while failing this one — the fingerprint must span Configuration (and OperatorRole and Tags) too.
Fix: CreateNetworkConnector's handler must store a fingerprint of the full request (Name, Configuration, OperatorRole, Tags) alongside the token in crate::state::TokenOutcome / remember_token (src/state.rs) and, in the replay branch, refuse with ResourceConflictException when a known token arrives with a different fingerprint, replaying only on an exact match.
Traces: lambda-core.create-network-connector-token-reuse-mismatch-rejected.

--- Cause 3 of 3: the duplicate-Name 409's message is a different sentence from the service's. ---
AWS: Smithy CreateNetworkConnector.Name -> NetworkConnectorName (@required), documented as "a unique name for the network connector within your account and Region", and the operation models ResourceConflictException (httpError 409). Recorded behavior: a second create under a Name already held in the account is refused with HTTP 409 / ResourceConflictException and the message "A network connector with name '<Name>' already exists in this account". Its fixed text is "A network connector with name '" ... "' already exists in this account" — the quoting is part of the sentence and the trailing clause stops at "account"; the only variable part is <Name>, taken verbatim from the request's Name member. The refusal creates nothing (the account still holds exactly one connector under that Name, with the original Id) and the identical payload under a different Name is accepted with a newly minted Id.
Emulator: the status 409 and the code ResourceConflictException are correct, but create_network_connector.rs:234-242 formats a different sentence — "A network connector named {} already exists in this account and Region" (replay: 'A network connector named sim2real-behav-lc-dup-a2721208e04a already exists in this account and Region'): "named <Name>" unquoted instead of "with name '<Name>'", and an extra " and Region" clause the service does not emit. The same string is also the message the wire issue 20261023T022015Z observed on its Cause 3, so one string literal is the whole defect.
Why: the error message is part of the contract. A client or operator that matches on the service's sentence (log scraping, an error-classification table, a test asserting the collision reason) does not match the emulator's, so a genuine name collision reads as an unrecognised conflict and is handled by the wrong branch.
Fix: the duplicate-name conflict call site in create_network_connector.rs (the store.connectors.contains_key branch feeding crate::state::connector_conflict) must emit the service's sentence with the request's Name interpolated into its quoted slot.
Traces: lambda-core.duplicate-connector-name-rejected.
