Cause 1 of 4: CreateProject with a service role that does not trust codebuild.amazonaws.com is refused with the right class but the wrong message text.
AWS: Smithy: CreateProject errors include InvalidInputException (HTTP 400); serviceRole is a required member. For a role whose trust policy does not allow codebuild.amazonaws.com to assume it, AWS answers InvalidInputException whose message is entirely FIXED text with no request-derived parts: "CodeBuild is not authorized to perform: sts:AssumeRole on service role. Please verify that: 1) The provided service role exists, 2) The role name is case-sensitive and matches exactly, and 3) The role has the necessary trust policy configured."
Emulator: answers InvalidInputException (correct code and status) with its own two-clause rewrite: "CodeBuild is not authorized to perform: sts:AssumeRole on service role. Please verify that: 1) The provided service role exists, 2) The service role's trust policy allows codebuild.amazonaws.com to assume it." — the third numbered clause and the case-sensitivity clause are dropped and clause 2 is reworded.
Why: the error message is part of the contract; a client (or an operator reading a CI failure) that matches on or displays AWS's remediation text gets emulator prose, and the case-sensitivity hint AWS gives is lost.
Fix: the CreateProject handler's service-role trust validation message construction.
Traces: codebuild__codepipeline__ecr.codebuild-role-missing-trust-policy-blocks-assume-role-during-build-rejected.

Cause 2 of 4: a CodePipeline Build action is refused by the emulator instead of being executed, and the refusal text announces the emulator.
AWS: recorded behavior only. A pipeline whose Build stage has an ActionTypeId of category Build / provider CodeBuild invokes the project, and when the build succeeds the action and the pipeline execution reach status Succeeded; GetPipelineExecution reports 'Succeeded' with the action's executionResult naming the build.
Emulator: the pipeline execution ends 'Failed' with action detail "Build/Build=Failed: this emulator does not run Build actions provided by CodeBuild, so the action cannot be performed". That is not an AWS status detail at all — no AWS error code, and prose naming the emulator.
Why: no CI pipeline can ever reach Succeeded, so nothing downstream of a Build stage (artifact promotion, ECR push, deployment) is testable; and a client that surfaces action failure details shows text no AWS account produces.
Fix: the CodePipeline Build-action execution path (dispatch to the CodeBuild project and settle the action from the build's terminal status), plus removal of the emulator-authored refusal detail.
Traces: codebuild__codepipeline__ecr.deploy-stack-codebuild-role-trust-policy-allows-codebuild-service, codebuild__codepipeline__ecr.deploy-stack-pipeline-role-trust-policy-allows-codepipeline-service.

Cause 3 of 4: a CodeBuild project created by a CloudFormation stack is unknown to the CodeBuild API, so StartBuild on the stack's own project ARN is refused.
AWS: recorded behavior only. A stack declaring AWS::CodeBuild::Project creates a real project; the physical id/ARN the stack reports resolves in CodeBuild, and StartBuild(projectName=<that ARN>) is accepted (HTTP 200 with a build).
Emulator: StartBuild on the ARN the deployed stack produced is refused HTTP 400 ResourceNotFoundException with message "Project cannot be found: <project ARN>" (fixed text "Project cannot be found: " plus the ARN taken from the request). The stack reported the resource as created, so state and API disagree.
Why: infrastructure-as-code CI topologies are unusable — the template applies, the outputs look right, and every call against the created project fails as not-found, which a client cannot distinguish from a template defect.
Fix: the CloudFormation AWS::CodeBuild::Project resource provider must register the project in CodeBuild's state (and mint its physical id from that record), so CodeBuild read/start paths resolve it.
Traces: codebuild__codepipeline__ecr.deploy-stack-missing-ecr-repository-policy-blocks-codebuild-push.

Cause 4 of 4: an ECR image push never starts the pipeline its EventBridge rule targets, so neither the source-revision contract nor the two negative-delivery controls can be observed.
AWS: recorded behavior only. A push to an ECR repository publishes an 'ECR Image Action' event (source aws.ecr, detail carrying repository-name, action-type PUSH, image-tag, image-digest); an EventBridge rule matching it with a CodePipeline target and a role granting codepipeline:StartPipelineExecution starts a new pipeline execution, whose Source action records the pushed image's digest as its source revision. A rule whose image-tag filter does not match the push starts nothing, and a target role without codepipeline:StartPipelineExecution starts nothing while a correctly permissioned sibling rule still does (the positive control).
Emulator: no execution outside the baseline ever appears — ListPipelineExecutions shows only the baseline id after repeated pushes (170 s of retried pushes in one check, 120 s in another) and the third check is killed at the 180 s cap. Hypothesis: the push publishes no event (see the companion cloudwatch__ecr__ecs issue filed in this sweep), so the rule never fires and the permission/filter distinctions are unobservable.
Why: the whole push-to-pipeline trigger is dead, and because the positive control never fires either, the emulator cannot tell a correctly filtered or correctly permissioned rule from a broken one — a user validating least-privilege EventBridge wiring gets a false 'blocked' verdict for every configuration.
Fix: ECR's push path event publication plus EventBridge rule matching/target invocation for a CodePipeline target (including the target role's codepipeline:StartPipelineExecution authorization and the detail.image-tag filter), and CodePipeline's recording of the triggering image digest as the Source action's source revision.
Traces: codebuild__codepipeline__ecr.codepipeline-execution-includes-ecr-image-digest-as-source-revision, codebuild__codepipeline__ecr.ecr-image-tag-filter-in-eventbridge-rule-controls-pipeline-trigger, codebuild__codepipeline__ecr.missing-eventbridge-target-permission-blocks-pipeline-invocation.
