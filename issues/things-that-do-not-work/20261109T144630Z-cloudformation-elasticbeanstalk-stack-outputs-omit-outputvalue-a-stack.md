# cloudformation__elasticbeanstalk: stack Outputs omit OutputValue, a stack-created ConfigurationTemplate is not registered on its application, and an unknown SolutionStackName does not fail the stack (3 causes)

> _Note: this issue was identified against the code base at commit `6bab9504f4457a639e729a9dc2b08c46f536304f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
THREE distinct root causes in the CloudFormation/Elastic Beanstalk deployment path, all under the same suite service heading, each grounded in failing behavioral checks of this suite that the replay marked neither ALREADY FILED nor OWNED. THREE causes must be closed before submitting. All four checks under this heading fail (0/4).

Adjacent issues describe neighbouring ground but do NOT carry these checks: the FIXED 20261023T205650Z-elasticbeanstalk-elastic-beanstalk-deployment-substrate-is-missing-createstoragelocation-s.md claimed 'CloudFormation EB environments are never created' — in THIS replay the stacks do reach CREATE_COMPLETE, and none of the failures below is a refusal, so these are new divergences and not a reopening of that fix.

Cause 1 of 3: DescribeStacks returns Output entries that carry OutputKey but no OutputValue member.
AWS: Smithy (cloudformation): Stack.Outputs -> list of Output{OutputKey, OutputValue ('The value associated with the output'), Description, ExportName}. Recorded behavior: for every Output a template declares, a CREATE_COMPLETE stack reports an entry with BOTH OutputKey and OutputValue, the resolved value of the output's Value expression ({"Ref": <logical id>} or {"Fn::GetAtt": [<logical id>, <attribute>]}); an attribute a resource type does not support fails the stack instead of yielding an output with no value.
Emulator: a CREATE_COMPLETE stack whose Outputs include Fn::GetAtt on an Elastic Beanstalk resource (Fn::GetAtt ["Environment", "EndpointURL"], Fn::GetAtt ["ConfigTemplate", "TemplateName"]) returns at least one Output entry with the OutputValue member absent, so building {o['OutputKey']: o['OutputValue']} over stack['Outputs'] raises KeyError: 'OutputValue'. Hypothesis: the resolver yields no value for that GetAtt (the attribute is unresolved or empty) and the serializer then omits the member rather than failing the stack or emitting the value.
Why: Outputs are the documented contract between a stack and its consumers. A client that reads a declared output by key — every CLI/CDK/pipeline consumer of stack outputs does — gets a response missing a modeled member and crashes, instead of either the value or a stack failure that explains the unsupported attribute. Nothing downstream of the stack can discover the environment's endpoint or the template's name.
Fix: the Output resolution and serialization in the stack-outputs path — resolve Ref/Fn::GetAtt for Elastic Beanstalk resource attributes (notably AWS::ElasticBeanstalk::Environment EndpointURL and AWS::ElasticBeanstalk::ConfigurationTemplate TemplateName) and always emit OutputValue for a declared output, failing the stack when the attribute cannot be resolved. Belongs in the CloudFormation DescribeStacks handler's Output serializer and the stack provisioning/attribute-resolution engine (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/describe_stacks.rs and the stack/resource-provisioning module).
Traces: cloudformation__elasticbeanstalk.deploy-elasticbeanstalk-application-version-and-configurationtemplate-round-trip-and-delete, cloudformation__elasticbeanstalk.deploy-elasticbeanstalk-environment-round-trip-and-delete.

Cause 2 of 3: an AWS::ElasticBeanstalk::ConfigurationTemplate a stack creates is not registered on its Elastic Beanstalk application.
AWS: recorded behavior only (CloudFormation resource provisioning, read back through elasticbeanstalk DescribeApplications -> ApplicationDescription.ConfigurationTemplates, 'The names of the configuration templates associated with this application'). Recorded behavior: once a stack containing an AWS::ElasticBeanstalk::Application and an AWS::ElasticBeanstalk::ConfigurationTemplate referencing it reaches CREATE_COMPLETE, DescribeApplications(ApplicationNames=[app]) reports ConfigurationTemplates == [<the template name the stack minted>], and DescribeConfigurationSettings(ApplicationName=app, TemplateName=<that name>) reports the template's SolutionStackName.
Emulator: the stack reaches CREATE_COMPLETE and its ConfigTemplateRef output resolves, but DescribeApplications for that application reports ConfigurationTemplates == [] — AssertionError 'control application templates [[]]'. The template the stack claims to have created does not exist in Elastic Beanstalk.
Why: the stack reports success for a resource that was never created, so the two services disagree about state. A client that deploys saved configurations through CloudFormation and then launches environments from TemplateName, or that reads the template's settings back, finds nothing — and the discrepancy is invisible from CloudFormation alone.
Fix: the AWS::ElasticBeanstalk::ConfigurationTemplate resource provisioner — creating that resource must create the configuration template in the Elastic Beanstalk service state (the same state DescribeApplications/DescribeConfigurationSettings read) and deleting it must remove it. Belongs in the CloudFormation resource-provisioning module for the Elastic Beanstalk resource types, wired to the elasticbeanstalk service's application/template state.
Traces: cloudformation__elasticbeanstalk.deploy-elasticbeanstalk-configurationtemplate-invalid-solutionstack-rejected-and-rolled-back.

Cause 3 of 3: a stack whose AWS::ElasticBeanstalk::Environment names an unknown SolutionStackName reaches CREATE_COMPLETE instead of failing and rolling back.
AWS: recorded behavior only. Recorded behavior: the Elastic Beanstalk CreateEnvironment the resource performs is refused, the Environment resource goes CREATE_FAILED with the handler reason relaying Elastic Beanstalk's own words — ResourceStatusReason carrying "No Solution Stack named '<SolutionStackName>' found. (Service: ElasticBeanstalk, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" under error code 'InvalidRequest' — the stack ends ROLLBACK_COMPLETE, and the rollback leaves no application and no environment behind (DescribeApplications and DescribeEnvironments both empty). The fixed text is "No Solution Stack named '" ... "' found. (Service: ElasticBeanstalk, Status Code: 400, Request ID: ...) (SDK Attempt Count: ...)"; the variable parts are the SolutionStackName from the template and the per-run request id / attempt count.
Emulator: the same stack ends 'CREATE_COMPLETE' — AssertionError "rejected stack ended 'CREATE_COMPLETE'". The bad property is accepted, no resource fails, no rollback occurs, and the application/environment the rollback should have removed are left in place.
Why: CloudFormation's contract is that a resource its handler cannot create fails the stack. A client deploying a template with a typo'd or retired solution stack is told the deployment succeeded and is left with an environment that cannot exist, instead of a ROLLBACK_COMPLETE stack whose event names the bad value. Every negative-path deployment gate built on stack status mis-reports.
Fix: the AWS::ElasticBeanstalk::Environment resource provisioner must perform the real CreateEnvironment against the elasticbeanstalk service state and propagate its refusal as a CREATE_FAILED resource event (relaying Elastic Beanstalk's message verbatim in ResourceStatusReason) so the stack rolls back. Belongs in the CloudFormation resource-provisioning module for the Elastic Beanstalk resource types and its failure/rollback path.
Traces: cloudformation__elasticbeanstalk.deploy-elasticbeanstalk-environment-invalid-solution-stack-rejected-and-rolled-back.
