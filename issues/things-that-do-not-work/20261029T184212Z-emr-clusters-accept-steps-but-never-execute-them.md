# EMR clusters accept steps but never execute them: no step reaches a terminal state, no cluster self-terminates, no step/bootstrap output or log is written to S3, and no "EMR Cluster State Change" event is published (4 causes)

> _Note: this issue was identified against the code base at commit `969cd59636329c2a8786028d0edb680658e5b91d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AddJobFlowSteps

## Description
This issue bundles 4 net-new root causes in the EMR (elasticmapreduce) crate, all in the cluster/step execution path that runs AFTER a cluster has been provisioned. The emulator does drive a cluster to WAITING (the already-filed issue 20261029T175551Z-emr-accepts-two-requests-aws-refuses-unknown-releaselabel.md grades a WAITING cluster, so provisioning itself completes quickly), but from that point on nothing the submitted work is supposed to produce ever happens: every one of the eight checks below hangs on a bounded poll of the emulator's own API and is killed by the harness with `Check timed out after 60.0s`, never reaching its assertions. Related open issues cover OTHER services' execution gaps (20261029T175551Z-glue-job-runs-reached-through-the-emr-glue.md for Glue job runs, 20261022T154846Z-emr-serverless-job-runs-are-recorded-but-never-executed.md and 20261029T174551Z-emr-serverless-job-run-lifecycle-and-interactive-session.md for EMR Serverless); none of them carries EMR-classic steps, EMR log delivery or the EMR cluster-state event, and none carries these check ids.

--- Cause 1 of 4: a submitted step never reaches a terminal StepState and the cluster never self-terminates ---
AWS: Smithy: `StepState` is PENDING | CANCEL_PENDING | RUNNING | COMPLETED | CANCELLED | FAILED | INTERRUPTED, and `StepTimeline` carries CreationDateTime, StartDateTime ("when the cluster step execution started") and EndDateTime ("when the cluster step execution completed or failed"); `ClusterState` is STARTING | BOOTSTRAPPING | RUNNING | WAITING | TERMINATING | TERMINATED | TERMINATED_WITH_ERRORS and `ClusterStateChangeReasonCode` includes ALL_STEPS_COMPLETED and STEP_FAILURE. Real EMR dispatches each step, moves it PENDING -> RUNNING -> COMPLETED/FAILED with a full Timeline; with KeepJobFlowAliveWhenNoSteps=false the cluster then goes TERMINATING -> TERMINATED with StateChangeReason.Code=ALL_STEPS_COMPLETED, and a step whose ActionOnFailure is TERMINATE_CLUSTER ends the cluster TERMINATED_WITH_ERRORS with StateChangeReason.Code=STEP_FAILURE while a still-pending later step becomes CANCELLED with no Start/EndDateTime. At StepConcurrencyLevel=1 step N ends before step N+1 starts.
Emulator: DescribeStep/DescribeCluster are answered, but the state never advances to any of those terminal values inside the harness window: every check that polls `DescribeStep(...).Step.Status.State in {COMPLETED,FAILED,CANCELLED,INTERRUPTED}` or `DescribeCluster(...).Cluster.Status.State in {TERMINATED,TERMINATED_WITH_ERRORS}` runs until the 60 s harness ceiling and is reported as `Check timed out after 60.0s` (the checks' own budgets are far larger — 2400 s for the cluster, 300-900 s for the steps — so they never give up on their own). Hypothesis: steps are recorded by AddJobFlowSteps/RunJobFlow but no step scheduler or cluster shutdown path consumes them, so ActionOnFailure (CONTINUE / TERMINATE_CLUSTER) is never interpreted either.
Why: every client that submits a step and waits for it — the standard EMR usage — blocks forever; `ALL_STEPS_COMPLETED` / `STEP_FAILURE` shutdown, step cancellation semantics, sequential execution at StepConcurrencyLevel=1 and the "cluster cannot be modified once terminated" rule are all unreachable, and negative tests gated on a positive control can never be graded.
Fix: the EMR crate's step scheduler / cluster state machine (services/service-com-amazonaws-emr-elasticmapreduce — the state that backs add_job_flow_steps.rs, describe_step.rs, list_steps.rs and describe_cluster.rs): drive each submitted step through PENDING -> RUNNING -> a terminal state with a populated StepTimeline, honour ActionOnFailure, and terminate the cluster with the matching ClusterStateChangeReasonCode.
Traces: emr.action-on-failure-continue-then-terminate-cluster, emr.emr-run-step-spark, emr.step-writes-real-output-to-s3, emr__glue__s3.cfn-deploy-emr-cluster-glue-catalog-permission-missing-negative, emr__glue__s3.eventbridge-emr-cluster-state-change-rule-positive.

--- Cause 2 of 4: a step's work is never executed, so the artifacts it writes to S3 never appear ---
AWS: recorded behavior only (the step payload is opaque to the model): a step submitted with command-runner.jar / spark-submit actually runs on the cluster's nodes, so the object the step writes (`s3://<bucket>/<key>` holding exactly the bytes the step was told to write, a Spark job's `part-*` output, or the rc/stderr files a node-side AWS CLI call redirects to S3) exists once the step is COMPLETED. The checks assert the exact content the job computes (a nonce, a closed-form sum), so a fabricated COMPLETED status without execution is detectable.
Emulator: no such object is ever created — the polls for `GetObject`/`ListObjectsV2` on the step's output key never see a key and the checks time out (`Check timed out after 60.0s`). Nothing in the replay output indicates any node-side execution occurs.
Why: the EMR data plane is inert: a client gets no computed result, so any pipeline whose next stage reads the step's output (and every permission-boundary check that distinguishes allowed from denied node-side calls by the rc/stderr files the step writes) cannot work at all.
Fix: the EMR crate's step execution path — the component that should run a dispatched step's command and produce its side effects (the step runner behind add_job_flow_steps.rs / the cluster's instance state), rather than only recording the step definition.
Traces: emr.step-writes-real-output-to-s3, emr.emr-run-step-spark, emr__glue__s3.cfn-deploy-emr-cluster-glue-catalog-config-positive, emr__glue__s3.cfn-deploy-emr-cluster-glue-catalog-permission-missing-negative.

--- Cause 3 of 4: no cluster, step or bootstrap-action logs are delivered under the cluster's LogUri ---
AWS: recorded behavior only: when RunJobFlow (or a CloudFormation AWS::EMR::Cluster) sets LogUri to an S3 location, EMR delivers node and application logs under `<LogUri>/<cluster-id>/`, with step logs under `<cluster-id>/steps/<step-id>/` and bootstrap-action stdout under `<cluster-id>/node/<instance-id>/bootstrap-actions/...` (gzip-compressed), so a client can list a non-zero key count there after the step/bootstrap action has run.
Emulator: those prefixes stay empty — the polls on `ListObjectsV2(Bucket=<log bucket>, Prefix=logs/<cluster-id>/steps/<step-id>/)` and on the bootstrap stdout keys under `logs/<cluster-id>/node/` never return a key, and the checks are killed at 60 s. Bootstrap actions equally show no evidence of having run (their marker never appears in any log).
Why: log-based debugging and every workflow that reads EMR logs out of S3 (including CloudFormation-deployed logging stacks whose entire purpose is that delivery) observe an empty bucket while the control plane reports the cluster healthy.
Fix: the EMR crate's log-delivery path and bootstrap-action execution (the cluster state machine that should write step/node logs to the configured LogUri through the S3 service state).
Traces: emr__glue__s3.cfn-deploy-emr-cluster-s3-logging-stack-positive, emr__glue__s3.cfn-deploy-emr-step-s3-bootstrap-positive, emr.step-writes-real-output-to-s3.

--- Cause 4 of 4: no "EMR Cluster State Change" event is published to EventBridge ---
AWS: recorded behavior only: every EMR cluster state transition publishes an EventBridge event with `source` = `aws.emr`, `detail-type` = `EMR Cluster State Change` and `detail.clusterId` / `detail.state` (e.g. state TERMINATED), which a rule matching that pattern delivers to its target (here an SQS queue).
Emulator: the check never gets that far because the transient cluster (KeepJobFlowAliveWhenNoSteps=false) never reaches TERMINATED (Cause 1), and no message is observed on the rule's SQS target; the check is killed at 60 s with `Check timed out after 60.0s`. Hypothesis: the EMR state machine has no EventBridge publication hook at all, so even a cluster that did terminate would deliver nothing.
Why: event-driven EMR automation (alarms, reaper lambdas, step functions waiting on cluster termination) never fires, and a rule that is correctly configured looks broken.
Fix: the EMR crate's cluster state machine — publish an `aws.emr` / `EMR Cluster State Change` event carrying clusterId, state, and the state-change reason to the EventBridge service state on every transition.
Traces: emr__glue__s3.eventbridge-emr-cluster-state-change-rule-positive.

## Evidence
Replay of suite simparity-behavioral-aws-v1 against the emulator. Per-service pass rates: emr 35/201 (17%), emr__glue__s3 1/46 (2%). Each of the eight checks below reports exactly one detail — `Error: Check timed out after 60.0s` — i.e. the check was still polling an emulator API for a state/artifact that never arrived when the harness killed it; none of them raised an assertion, so the emulator answered every call but never changed the answer.

Cause 1 (step/cluster never settles):
- emr.action-on-failure-continue-then-terminate-cluster — after RunJobFlow + 4 steps (ActionOnFailure CONTINUE, CONTINUE, TERMINATE_CLUSTER, CONTINUE) at StepConcurrencyLevel=1, polls `_cluster_state` for TERMINATED/TERMINATED_WITH_ERRORS with timeout_s=2400, then all 4 steps for a terminal StepState with timeout_s=300. Expected: step1 FAILED, step2 COMPLETED, step3 FAILED, step4 CANCELLED (no Start/EndDateTime), cluster TERMINATED_WITH_ERRORS with StateChangeReason.Code=STEP_FAILURE. Actual: timed out at 60 s with no terminal state.
- emr.emr-run-step-spark — polls DescribeStep for a terminal state, then expects cluster TERMINATED with StateChangeReason.Code=ALL_STEPS_COMPLETED and, finally, AddJobFlowSteps on the terminated cluster refused with HTTP 400 / ValidationException / "A job flow that is shutting down, terminated, or finished may not be modified." Actual: timed out at 60 s.
- emr.step-writes-real-output-to-s3, emr__glue__s3.cfn-deploy-emr-cluster-glue-catalog-permission-missing-negative, emr__glue__s3.eventbridge-emr-cluster-state-change-rule-positive — same timeout while polling DescribeStep / DescribeCluster.

Cause 2 (no step output in S3):
- emr.step-writes-real-output-to-s3 — the step runs `printf %s '<nonce>' > /tmp/result.txt && aws s3 cp /tmp/result.txt s3://<bucket>/<key>`; the check polls GetObject on that key (timeout_s=120) and asserts the body equals the nonce exactly. No object ever appears.
- emr.emr-run-step-spark — polls for the Spark job's `part-*` object under the output prefix and asserts the exact closed-form sum; no object appears.
- emr__glue__s3.cfn-deploy-emr-cluster-glue-catalog-config-positive / ...-glue-catalog-permission-missing-negative — poll for the node-side rc.txt/err.txt (`glue-check/rc.txt`) the step redirects to S3 to prove the Hive/Glue call ran (and that an explicit Deny on glue:* yields AccessDenied); neither file is ever written.

Cause 3 (no logs under LogUri):
- emr__glue__s3.cfn-deploy-emr-step-s3-bootstrap-positive — polls for bootstrap stdout keys under `logs/<cluster-id>/node/` in the stack's log bucket and then for the marker `sim2real-bootstrap-ran-ok`; nothing is delivered.
- emr__glue__s3.cfn-deploy-emr-cluster-s3-logging-stack-positive — expects node/application logs under the stack-created bucket's `<cluster-id>` prefix; the prefix stays empty.
- emr.step-writes-real-output-to-s3 — also polls `ListObjectsV2(Prefix=logs/<cluster-id>/steps/<step-id>/)` for KeyCount > 0.

Cause 4 (no EMR state-change event):
- emr__glue__s3.eventbridge-emr-cluster-state-change-rule-positive — EventBridge rule on detail-type "EMR Cluster State Change" with state TERMINATED targeting an SQS queue; after the transient cluster is expected to self-terminate the check polls ReceiveMessage for a body with source=aws.emr, detail-type="EMR Cluster State Change", detail.clusterId=<cluster id>, detail.state=TERMINATED. No message is received; timed out at 60 s.
