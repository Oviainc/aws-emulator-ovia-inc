## Description
TWO net-new root causes in the Config (StarlingDoveService) emulator, each grounded in failing behavioral checks of simparity-behavioral-ga-prod-v1 that are marked neither ALREADY FILED nor OWNED. TWO CAUSES must be closed before submitting.

Cause 1 of 2: a CUSTOM_LAMBDA Config rule's evaluator is never invoked, so no evaluation result from PutEvaluations ever lands and no rule's compliance ever leaves its initial state.

AWS: recorded behavior only, with model grounding. Smithy (configservice): PutEvaluations{Evaluations @length 0..100, ResultToken required, TestMode default false} -> {FailedEvaluations}, errors InvalidParameterValueException / InvalidResultTokenException / NoSuchConfigRuleException (all errorKind client, httpError 400); GetComplianceDetailsByConfigRule{ConfigRuleName required} -> {EvaluationResults, NextToken}, paginated, errors InvalidNextTokenException / InvalidParameterValueException / NoSuchConfigRuleException (client, 400); GetAggregateComplianceDetailsByConfigRule{ConfigurationAggregatorName, ConfigRuleName, AccountId (^\d{12}$), AwsRegion required} -> {AggregateEvaluationResults, NextToken}. None of these models a server error, so a healthy rule and aggregator never answer a request about an existing rule with a permanently empty result set. Recorded flow: after PutConfigRule with Source{Owner: CUSTOM_LAMBDA, SourceIdentifier: <function arn>} (plus lambda:AddPermission for config.amazonaws.com) and, for the periodic shape, StartConfigRulesEvaluation, Config INVOKES the function with a genuine ResultToken; the function spends that token on PutEvaluations; the submitted verdict then becomes readable through GetComplianceDetailsByConfigRule with the same ComplianceResourceType / ComplianceResourceId / ComplianceType, and through the aggregator surfaces GetAggregateComplianceDetailsByConfigRule and GetAggregateConfigRuleComplianceSummary (NonCompliantResourceCount.CappedCount rises by one for Filters={AccountId, AwsRegion}). The checks use ComplianceResourceType "AWS::::Account" (Config's account-wide pseudo-resource type, ResourceId = the account id).

Emulator: nothing in that pipeline moves. Five checks each block in their first wait for a verdict and are killed when their own in-check budget expires; none of them is refused anything, so this is not a refusal defect but a missing invocation. The verdict never appears in GetComplianceDetailsByConfigRule, so it also never appears in either aggregate surface, and a rule that gates remediation never becomes NON_COMPLIANT:
  - config.aggregate-compliance-details-reflect-source-rule-evaluation — TimeoutError: "the Lambda-backed rule's PutEvaluations result: the run budget ended first; not graded" (check line 68).
  - config.aggregate-compliance-summary-reflects-source-evaluations — TimeoutError in _poll_until on `_has_non_compliant_result()` (check line 154, 120 s budget).
  - config.concurrent-start-remediation-execution-dedup — TimeoutError: "compliance for account <account-id> reaching 'NON_COMPLIANT'" (check line 60; the account id is a value from the caller's identity, not part of the template).
  - config.e2e-remediation-execution-resolves-noncompliant-resource — TimeoutError: "compliance 'NON_COMPLIANT' for account <account-id>" (check line 46, 180 s budget).
  - config.overly-permissive-put-evaluations-invalid-result-token — TimeoutError: "a genuine ResultToken is accepted for rule <rule name>" (check line 318). This check's POSITIVE control never passes: the evaluator Config is supposed to invoke with a real ResultToken is never invoked, so the forged-token refusal it wants to contrast against can never be graded.

Why: Config's whole custom-rule plane is inert while reporting success at every control-plane call. A client cannot distinguish 'nothing is non-compliant' from 'evaluation is not implemented' — no call fails, the EvaluationResults list is simply always empty and the aggregate counts never move. A CUSTOM_LAMBDA guardrail that would mark a resource NON_COMPLIANT silently never runs, so an account looks permanently green; auto-remediation that is gated on a NON_COMPLIANT verdict never triggers; and every negative assertion about PutEvaluations (forged/expired ResultToken) becomes vacuous because the positive control cannot be established.

Fix: the custom-rule evaluation pipeline of the Config service — the rule-evaluation trigger behind services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/put_config_rule.rs and src/ops/start_config_rules_evaluation.rs must actually invoke the rule's CUSTOM_LAMBDA function with a genuine ResultToken; src/ops/put_evaluations.rs must accept that token and write the verdict into the compliance state that src/ops/get_compliance_details_by_config_rule.rs, src/ops/get_aggregate_compliance_details_by_config_rule.rs and src/ops/get_aggregate_config_rule_compliance_summary.rs project.

Cause 2 of 2: DeliverConfigSnapshot is accepted but the delivery channel's configSnapshotDeliveryInfo is never stamped — lastAttemptTime stays absent, so the snapshot-frequency horizon can never be observed.

AWS: recorded behavior only, with model grounding. Smithy (configservice): DescribeDeliveryChannelStatus{DeliveryChannelNames} -> {DeliveryChannelsStatus: [DeliveryChannelStatus{name, configSnapshotDeliveryInfo, configHistoryDeliveryInfo, configStreamDeliveryInfo}]}, only modelled error NoSuchDeliveryChannelException (client, 400); ConfigExportDeliveryInfo{lastStatus: DeliveryStatus(Success|Failure|Not_Applicable), lastErrorCode, lastErrorMessage, lastAttemptTime, lastSuccessfulTime, nextDeliveryTime} with lastAttemptTime documented as "The time of the last attempted delivery" and nextDeliveryTime as "The time that the next delivery occurs". DeliverConfigSnapshot's only modelled errors are NoSuchDeliveryChannelException / NoAvailableConfigurationRecorderException / NoRunningConfigurationRecorderException, so once it is accepted the ATTEMPT must be recorded in configSnapshotDeliveryInfo. Recorded behavior: each accepted DeliverConfigSnapshot stamps configSnapshotDeliveryInfo.lastAttemptTime strictly later than the previous reading, and nextDeliveryTime is bounded by the channel's configSnapshotDeliveryProperties.deliveryFrequency (MaximumExecutionFrequency = One_Hour | Three_Hours | Six_Hours | Twelve_Hours | TwentyFour_Hours — the check exercises the One_Hour and the TwentyFour_Hours legs and bounds the horizon with a clock-skew tolerance, so the concrete timestamps are state values, not part of the requirement).

Emulator: the One_Hour leg never settles. TimeoutError: "snapshot delivery for <channel name> settles with a lastAttemptTime strictly after the prior reading (None) (One_Hour leg): the run budget ended first; not graded" (check line 526, helper at line 131). The parenthesised `(None)` is the prior reading: configSnapshotDeliveryInfo.lastAttemptTime is ABSENT before and stays absent after an accepted DeliverConfigSnapshot, so the field is never written at all and the frequency-derived nextDeliveryTime assertions downstream are unreachable. Nothing is refused.

Why: a client that drives on-demand delivery and then waits on configSnapshotDeliveryInfo to learn whether and when the snapshot was attempted — the only place Config reports that outcome, since DeliverConfigSnapshot itself returns only a configSnapshotId — waits forever on an absent lastAttemptTime, and cannot compute or validate the next delivery window from nextDeliveryTime/deliveryFrequency. Delivery looks unattempted even though the call was accepted.

Fix: the delivery-channel status state of the Config service — src/ops/deliver_config_snapshot.rs must record the attempt on the named channel's state, and src/ops/describe_delivery_channel_status.rs must project configSnapshotDeliveryInfo with lastAttemptTime (and lastStatus, lastSuccessfulTime or lastErrorCode/lastErrorMessage) plus a nextDeliveryTime derived from the channel's configSnapshotDeliveryProperties.deliveryFrequency.

Traces: config.delivery-channel-snapshot-frequency-bounds-the-next-delivery-time (check line 526, helper _poll_until at line 131).
