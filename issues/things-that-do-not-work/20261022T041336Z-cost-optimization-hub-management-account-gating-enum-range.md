# Cost Optimization Hub: management-account gating, enum/range validation envelope and enrollment singleton diverge (6 causes)

> _Note: this issue was identified against the code base at commit `6d3a954d57304c873e4e6a3ccc977c1ac1664bbd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdatePreferences

## Description
Six distinct root causes in the Cost Optimization Hub emulator, all grounded in failing behavioral checks of the simparity-behavioral-aws-v1 suite. Causes 1-3 are over-permissive: the emulator answers 200 to calls real AWS refuses. Cause 4 is the error envelope of input validation, cause 5 a wrong numeric constraint bound, cause 6 the initial enrollment state. A fixer must close all six before submitting.

Cause 1 of 6: UpdatePreferences accepts memberAccountDiscountVisibility from a non-management caller.
AWS: Smithy: UpdatePreferences input member memberAccountDiscountVisibility targets enum MemberAccountDiscountVisibility ([All, None]); modeled errors include ValidationException (client, httpError 400) and AccessDeniedException (403). Recorded behavior: this field is settable only by the organization's management account; for any other caller an otherwise well-formed call is refused with HTTP 400 ValidationException and the field stays unreported by GetPreferences (message example: 'Only management accounts can update member account discount visibility.'). The rule that produces that text is the management-account restriction, so the requirement is the 400/ValidationException refusal plus no state change; the text is an example.
Emulator: HTTP 200 and the value is stored and echoed - the replay shows UpdatePreferences(memberAccountDiscountVisibility=...) returning {'savingsEstimationMode': 'BeforeDiscounts', 'memberAccountDiscountVisibility': 'None'} with HTTPStatusCode 200.
Why: a client that probes which preference fields it may write concludes it is the management account, writes member-account discount visibility, and then reads back a value real AWS would never have stored; the 'restricted field' error path is never exercised, and code distinguishing the restriction error from a plain input error cannot be tested.
Fix: the UpdatePreferences handler's authorization/validation step (plus the preference state it writes, which must stay untouched on refusal), and the GetPreferences serializer, which must not report memberAccountDiscountVisibility for a non-management caller.
Traces: cost-optimization-hub.preferences-member-account-discount-visibility-roundtrip, cost-optimization-hub.update-preferences-invalid-discount-visibility-rejected (its second rejection, the within-enum value 'All').

Cause 2 of 6: UpdatePreferences accepts savingsEstimationMode=AfterDiscounts although member account discount visibility is not enabled.
AWS: Smithy: UpdatePreferences.savingsEstimationMode targets enum SavingsEstimationMode; modeled error ValidationException (400). Recorded behavior: AfterDiscounts is only reachable once discount visibility is enabled (a management-account-only act), so for a caller without it the call is refused with HTTP 400 ValidationException and savingsEstimationMode keeps its previous value (message example: 'Invalid permission to update preferences. To use AfterDiscounts savings estimation mode, the management account must either enable member account discount visibility in Cost Optimization Hub, or enable linked account discount visibility in Cost Management Preferences.'). BeforeDiscounts is accepted and is the positive control.
Emulator: HTTP 200, returning {'savingsEstimationMode': 'AfterDiscounts'}; the value is accepted and stored.
Why: savings figures a client then renders are attributed to a discount mode the account is not entitled to, and the dependency between the two preferences is invisible - a client never learns it must enable discount visibility first.
Fix: the UpdatePreferences handler - gate AfterDiscounts on the stored memberAccountDiscountVisibility/caller entitlement and raise the modeled ValidationException, leaving state unchanged.
Traces: cost-optimization-hub.preferences-savings-estimation-mode-roundtrip.

Cause 3 of 6: ListRecommendations accepts an accountIds filter from a caller that is not the organization's management account.
AWS: Smithy: ListRecommendations.filter -> Filter.accountIds -> AccountIdList of AccountId (@pattern ^[0-9]{12}$); modeled errors include AccessDeniedException (client, httpError 403). Recorded behavior: the accountIds filter is an organization-view feature - a non-management caller is refused with HTTP 403 AccessDeniedException for ANY accountIds value, while the identical call with no filter succeeds (message example: 'Cannot get enrollment statuses for member accounts of the organization. This is because your account is not the management account of the organization.').
Emulator: HTTP 200 - the filtered call succeeds; the check fails with 'expected the call to be rejected, but it succeeded'.
Why: a client can enumerate other accounts' recommendations through an emulated account that has no organization entitlement, so the entire org-permission branch of a cost tool (prompting for delegated-admin setup, degrading to single-account mode) is unreachable and untested.
Fix: the ListRecommendations handler's authorization step, before filtering/pagination: when filter.accountIds is populated and the caller is not the management account, return the modeled AccessDeniedException. Note the open issue 'Cost Optimization Hub reads return canned data, ignoring request filters and stored preferences' covers a different defect in the same handler (filter members not applied to the result set) and does not cover this authorization gate.
Traces: cost-optimization-hub.list-recommendations-filter-nonexistent-account-returns-empty.

Cause 4 of 6: input-constraint failures carry the framework's generic prose message instead of this service's fixed summary plus a per-field detail.
AWS: Smithy: ValidationException (client, httpError 400) has members message (required), reason -> ValidationExceptionReason, fields -> list<ValidationExceptionDetail{fieldName required, message required}>, documented as 'The list of fields that are invalid'. Recorded behavior, identical across operations and constraint kinds: the top-level message is the fixed, request-independent summary 'Input validation failed. Please check the field list for more details.' and the per-member diagnosis is carried in fields, e.g. [{fieldName: 'maxResults', message: 'Member must have value less than or equal to 1000'}] and [{fieldName: 'memberAccountDiscountVisibility', message: 'Member must satisfy enum value set: [All, None]'}]. Because the summary is fixed and the detail is built from the request member and its modeled constraint, both are requirements here, not example text.
Emulator: HTTP 400 with the right error code but the whole diagnosis inlined in message, e.g. "1 validation error detected: Value 'not-an-account-id' at 'accountId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9]{12}$", "1 validation error detected: Value '1001' at 'maxResults' failed to satisfy constraint: Member must have value less than or equal to 100", "1 validation error detected: Value 'Suspended' at 'status' failed to satisfy constraint: Member must satisfy enum value set: [Active, Inactive]", "1 validation error detected: Value 'Everyone' at 'memberAccountDiscountVisibility' failed to satisfy constraint: Member must satisfy enum value set: [All, None]".
Why: a client that maps ValidationException.fields back onto form members gets nothing and must scrape prose; code switching on reason never matches FieldValidationFailed.
Fix: the shared input-validation/ValidationException serialization path of this service, applied to ListEnrollmentStatuses.accountId (pattern), UpdateEnrollmentStatus.status (enum), ListRecommendations.maxResults (range) and UpdatePreferences.memberAccountDiscountVisibility (enum). The open issue 'ValidationException body omits reason and fields members' (20261022T032312Z-cost-optimization-hub-validationexception-body-omits-reason-and-fields-members.md) is the same root cause seen from the wire corpus and names ListEnrollmentStatuses/UpdateEnrollmentStatus/ListRecommendations; net-new here are the behavioral checks below and the UpdatePreferences enum path, which that issue does not name.
Traces: cost-optimization-hub.list-enrollment-statuses-account-id-pattern-rejected, cost-optimization-hub.update-enrollment-status-invalid-value-rejected, cost-optimization-hub.list-recommendations-max-results-out-of-range-rejected, cost-optimization-hub.update-preferences-invalid-discount-visibility-rejected.

Cause 5 of 6: ListRecommendations enforces maxResults <= 100 instead of the modeled <= 1000.
AWS: Smithy: ListRecommendations.maxResults targets MaxResults with @range min 0, max 1000 for this operation (ListEnrollmentStatuses' own maxResults is 0..100). So maxResults=1000 must be accepted and only values above 1000 are refused with ValidationException, whose field detail reads 'Member must have value less than or equal to 1000'.
Emulator: the rejection of maxResults=1001 states the bound as 100 ('Member must have value less than or equal to 100'), i.e. the validation uses the 0..100 bound; every request with 101..1000 - including the modeled maximum - is therefore refused where AWS answers 200.
Why: a client paging recommendations at the documented maximum page size gets a 400 on every call and cannot list at all; the apparent constraint contradicts the service model the SDK is generated from.
Fix: the ListRecommendations input validation - bind maxResults to this operation's own range (0..1000) rather than the narrower shape/other-operation bound.
Traces: cost-optimization-hub.list-recommendations-max-results-out-of-range-rejected (the emulator's own rejection message is the evidence of the wrong bound; the check's positive control at maxResults=1000 is never reached).

Cause 6 of 6: ListEnrollmentStatuses reports no record for the caller account until UpdateEnrollmentStatus has been called.
AWS: recorded behavior only - the recorded happy-path run reads the caller's enrollment singleton directly as items[0] before performing any write, i.e. ListEnrollmentStatuses answers with one AccountEnrollmentStatus for the calling account (accountId/status/createdTimestamp/lastUpdatedTimestamp), so the account's status is readable before any enrollment write. Hypothesis: the leased account already carried an enrollment record (status Inactive) because the account is known to Cost Optimization Hub.
Emulator: on fresh state items is an empty list - the handler reports only records UpdateEnrollmentStatus wrote (see the handler's own doc comment), so the check dies with IndexError on items[0] before it can transition anything. After an UpdateEnrollmentStatus call the record does appear, so only the initial state diverges.
Why: a client that reads the account's enrollment status before deciding whether to enroll sees no record at all and cannot distinguish 'not enrolled' from 'no such account/unsupported'; every read-before-write flow against a fresh emulator fails rather than reporting Inactive.
Fix: the service state's initial contents (seed the caller account's enrollment record, status Inactive, with timestamps) or the ListEnrollmentStatuses handler, which should materialise the caller's singleton when no record was written yet.
Traces: cost-optimization-hub.enrollment-status-active-transition.
