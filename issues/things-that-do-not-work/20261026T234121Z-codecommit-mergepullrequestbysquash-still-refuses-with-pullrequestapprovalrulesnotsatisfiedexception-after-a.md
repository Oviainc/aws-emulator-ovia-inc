# CodeCommit MergePullRequestBySquash still refuses with PullRequestApprovalRulesNotSatisfiedException after a valid non-author approval, so an approval-gated merge can never complete

> _Note: this issue was identified against the code base at commit `f2163892bf40cea6da7d1662f28c14ec75c797c6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
MergePullRequestBySquash

## Description
REOPENS 20261025T013318Z-codecommit-mergepullrequestbysquash-stub.md: its fix left the call refused.

The operation is no longer a 501 stub and its NEGATIVE leg is now correct — merging while an Approvers rule is unmet is refused with HTTP 400 / PullRequestApprovalRulesNotSatisfiedException, the exact AWS message, the pull request stays OPEN and the destination reference does not move (all of those assertions pass). What that fix left behind is the POSITIVE side of the same gate: once the rule is genuinely satisfied, the identical call is STILL refused with the same error, so no approval-gated merge can ever complete. This is one net-new root cause.

Cause 1 of 1: an approval recorded by UpdatePullRequestApprovalState is not counted when MergePullRequestBySquash re-evaluates the pull request's approval rules, so a satisfied rule is still reported unsatisfied.

AWS: Smithy models MergePullRequestBySquash with input pullRequestId (@required, PullRequestId) and repositoryName (@required, RepositoryName, @length 1..100, @pattern ^[\w\.-]+$), output pullRequest (PullRequest), and among its errors PullRequestApprovalRulesNotSatisfiedException (errorKind client, httpError 400 [defaulted]). Smithy models UpdatePullRequestApprovalState with input pullRequestId (@required), revisionId (@required, RevisionId) and approvalState (@required, enum ApprovalState: APPROVE | REVOKE) and a Unit output; its doc states 'Updates the state of a user's approval on a pull request. The user is derived from the signed-in account when the request is made.' PullRequestApprovalRulesNotSatisfiedException's modelled documentation is the error message itself and is entirely FIXED text — it interpolates nothing from the request or state: 'You cannot merge the pull request because the requirements for one or more approval rules have not been met. For details about the approval rules that still have requirements, use EvaluatePullRequestApprovalRules.' The rule under test is an Approvers statement with NumberOfApprovalsNeeded 1 whose ApprovalPoolMembers is the assumed-role pool pattern 'arn:aws:sts::<account>:assumed-role/<roleName>/*' (the account id and role name come from the request/environment; the fixed parts are the arn:aws:sts:: prefix, ':assumed-role/' and the trailing '/*'). AWS's rule is: after a principal that is NOT the pull request's author and that MATCHES that pool calls UpdatePullRequestApprovalState with approvalState APPROVE for the pull request's CURRENT revisionId, the rule is satisfied — EvaluatePullRequestApprovalRules reports approved true with the rule in approvalRulesSatisfied — and the very same MergePullRequestBySquash call then succeeds with HTTP 200, returns pullRequest.pullRequestStatus 'CLOSED', and advances the destination branch head past its pre-merge commit.
Emulator: UpdatePullRequestApprovalState is accepted (it no longer answers 501 — the check's _retry_until_propagated only retries UnrecognizedClientException/InvalidClientTokenId and it did not raise), yet the subsequent MergePullRequestBySquash on the same pullRequestId/repositoryName answers HTTP 400 PullRequestApprovalRulesNotSatisfiedException with that same fixed message. The replay ends on the uncaught botocore.errorfactory.PullRequestApprovalRulesNotSatisfiedException raised by the post-approval merge at check line 1786 (the pre-approval merge at line 1752 is the one deliberately caught, and it asserted clean). So the gate is permanently closed: the recorded approval either is not persisted where the merge's rule evaluation reads it, or the caller's assumed-role principal is not matched against the rule's ApprovalPoolMembers pattern, or the approval is keyed to a revisionId the merge no longer considers current.
Why: approval-gated merge is the whole point of CodeCommit approval rules. A client sees a pull request that can be approved but never merged: review tooling that catches PullRequestApprovalRulesNotSatisfiedException to re-request review loops forever, and a release pipeline's 'merge only once approved' step can never go green, so the guard is untestable in the emulator even though its refusal path looks correct. Because the refusal is indistinguishable from the legitimate pre-approval refusal, a caller cannot tell 'not approved yet' from 'approvals are never counted'.
Fix: the approval-rule evaluation MergePullRequestBySquash performs before merging, and the state it reads — services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/merge_pull_request_by_squash.rs together with the approval records written by src/ops/update_pull_request_approval_state.rs and the pull-request approval state in src/state.rs. The same evaluation is what EvaluatePullRequestApprovalRules and GetPullRequestApprovalStates must read, so it belongs in one shared helper in src/state.rs rather than per-handler. Related but NOT covering: open issue 20261025T123952Z-codecommit-pull-request-approval-surface-updatepullrequestapprovalstate-answers-501.md (its Cause 2 asserts only that the squash merge answers 501 and does not gate at all, and its replay list is codecommit.e2e-pull-request-approval-and-merge-flow / codecommit.author-cannot-approve-own-pull-request-rejected / codecommit.concurrent-put-file-same-parent-single-winner — it does not carry this check's key and the behaviour it describes has since changed).
