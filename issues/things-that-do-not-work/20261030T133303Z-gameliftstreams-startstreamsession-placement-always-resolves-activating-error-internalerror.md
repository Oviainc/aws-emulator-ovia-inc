# gameliftstreams StartStreamSession placement always resolves ACTIVATING -> ERROR/internalError, so a session never reaches ACTIVE and no successful-stream path can be exercised

> _Note: this issue was identified against the code base at commit `eb57128e1f47424b0ae342c00c568765199d6d29`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartStreamSession

## Description
Cause 1 of 1: a stream session started against an ACTIVE stream group with free capacity and an associated READY application never reaches an eligible (non-terminal) status — the emulator unconditionally resolves placement into the modelled failure state.

Failing check: gameliftstreams.create-stream-session-admin-shell-not-ready-rejected

AWS: StartStreamSession (Smithy: StartStreamSession, POST /streamgroups/{Identifier}/streamsessions, 201; output members Status -> StreamSessionStatus, StatusReason -> StreamSessionStatusReason, SignalResponse) documents the placement lifecycle explicitly: "Amazon GameLift Streams creates the stream session resource, assigns an Amazon Resource Name (ARN) value, and begins searching for available stream capacity ... Session transitions to ACTIVATING status. Placement completion: If Amazon GameLift Streams is successful in finding capacity for the stream, the stream session status changes to ACTIVE status and StartStreamSession returns stream connection information. If Amazon GameLift Streams was not successful in finding capacity within the placement timeout period ..., the stream session status changes to ERROR status and StartStreamSession returns a StatusReason of placementTimeout." So, given the prerequisites the model lists (stream group in ACTIVE status, idle/on-demand capacity in the requested location, at least one associated application), the terminal outcome of placement is ACTIVE (then CONNECTED / PENDING_CLIENT_RECONNECTION / RECONNECTING as the client connects), and the modelled ERROR reasons are specific causes: placementTimeout when capacity could not be found, invalidSignalRequest for a bad WebRTC offer, applicationLogS3DestinationError, assumeRoleFailed; internalError is documented as "An internal service error occurred. Start a new stream session to continue streaming" — a fault, not the normal result of a healthy placement. StreamSessionStatus enum: ACTIVATING | ACTIVE | CONNECTED | PENDING_CLIENT_RECONNECTION | RECONNECTING | TERMINATING | TERMINATED | ERROR.

Emulator: every session resolves ACTIVATING -> ERROR with StatusReason internalError after the fixed TRANSITION span, regardless of the request, the group's capacity, the location's status or the SignalRequest. GetStreamSession then reports Status="ERROR", StatusReason="internalError" for a session whose group was ACTIVE with MaximumCapacity 12 in the requested location and whose application was READY and associated, and whose SignalRequest was a complete WebRTC offer (video+audio recvonly transceivers, ICE gathering complete). The replayed check observes exactly that: "stream session reached terminal status ERROR before becoming admin-shell-eligible: internalError". Note the emulator's own handler doc states this is deliberate ("the placement resolves into the modelled failure state (ERROR with StatusReason internalError) rather than reporting a stream that never started") — but that choice is itself the divergence: it makes a documented success outcome unreachable, and it reports a service-fault reason for a request that AWS would place successfully.

Why: a client relying on AWS's behavior cannot complete any stream workflow against the emulator. Every operation gated on a live session is unreachable — CreateStreamSessionAdminShell (eligible statuses ACTIVE, CONNECTED, PENDING_CLIENT_RECONNECTION, RECONNECTING), CreateStreamUrl, the connect/reconnect and ConnectionTimeoutSeconds paths, and TerminateStreamSession's TERMINATING -> TERMINATED path from a live session. Worse, the failure is reported as internalError, which AWS documents as a retryable service fault: SDK/client logic that retries or alarms on internalError will loop or page, where a genuine capacity problem would have been the client-actionable placementTimeout, and a bad offer invalidSignalRequest. It also makes negative tests unverifiable: a rejection that depends on session status cannot be distinguished from this blanket failure.

Fix: the stream-session placement state machine, not the request handler's validation. StreamSession::advance must resolve ACTIVATING to ACTIVE (setting the modelled connection information, including a SignalResponse — the WebRTC answer string — and leaving StatusReason unset) whenever the group is ACTIVE, the requested/first-available location is ACTIVE and has capacity, and the application is associated and READY; the ERROR outcome must be reserved for the modelled causes and must carry the matching StatusReason (placementTimeout when no capacity is available in the requested location, invalidSignalRequest for a SignalRequest that is not a usable WebRTC offer). internalError must not be the default resolution of a healthy placement. Status/StatusReason belong to the session record in state; StartStreamSession's and GetStreamSession's serializers then report them unchanged.

## Evidence
Expected (AWS, per the StartStreamSession model documentation): with a stream group in ACTIVE status, capacity in the requested location, an associated READY application and a valid WebRTC SignalRequest, the session leaves ACTIVATING for ACTIVE (then CONNECTED/PENDING_CLIENT_RECONNECTION/RECONNECTING on client activity). GetStreamSession reports Status=ACTIVE with no StatusReason and a SignalResponse. ERROR occurs only for a modelled cause and then carries the matching StatusReason (placementTimeout for no capacity, invalidSignalRequest for an unusable offer).

Actual (emulator): GetStreamSession reports Status="ERROR", StatusReason="internalError" for every started session once the fixed transition span elapses. Replay output for gameliftstreams.create-stream-session-admin-shell-not-ready-rejected:
  AssertionError: stream session reached terminal status ERROR before becoming admin-shell-eligible: internalError
  (raised from _wait_session_admin_shell_eligible, whose eligible set is {ACTIVE, CONNECTED, PENDING_CLIENT_RECONNECTION, RECONNECTING} and failed set is {TERMINATED, ERROR})
The earlier beat of the same check passed: before the session settles, CreateStreamSessionAdminShell is correctly refused with ValidationException naming the eligible-status set. The divergence is only that the session never reaches that set, so the positive control (the identical admin-shell call succeeding on an eligible session, returning SessionId/StreamUrl/TokenValue) can never run.

Requirement vs per-run values: the requirement is the status/reason pair as a class — ACTIVE with StatusReason absent for a successful placement, and an ERROR StatusReason drawn from the enum cause that actually applies (placementTimeout / invalidSignalRequest / applicationLogS3DestinationError / assumeRoleFailed). The session ARN, stream group id, application id, timestamps and the "(Internal ID: <uuid>)" suffix on any error message are per-run values and are not part of the requirement.

## Steps to Reproduce
1. Create an S3 bucket and put an executable object under a prefix; call CreateApplication (RuntimeEnvironment UBUNTU/22_04_LTS, ExecutablePath run.sh, ApplicationSourceUri s3://<bucket>/app/) and poll GetApplication until READY.
2. Call CreateStreamGroup (StreamClass gen6n_small, LocationConfigurations [{LocationName: <region>, MaximumCapacity: 12}]) and poll GetStreamGroup until Status=ACTIVE and the location's LocationStates entry is ACTIVE.
3. Call AssociateApplications on the group with the application id.
4. Build a complete WebRTC offer (video+audio recvonly, ICE gathering complete) and call StartStreamSession(Identifier=<groupArn>, ApplicationIdentifier=<appId>, Protocol=WebRTC, SignalRequest=<offer JSON>). It returns 201 with Status=ACTIVATING.
5. Poll GetStreamSession(Identifier=<groupArn>, StreamSessionIdentifier=<sessionArn>).
   Observed: Status becomes "ERROR" with StatusReason "internalError" and never ACTIVE/CONNECTED.
   Expected: Status becomes "ACTIVE" (no StatusReason, SignalResponse present), after which CreateStreamSessionAdminShell succeeds and returns SessionId, StreamUrl and TokenValue.
