# cognito-idp__kms__lambda__sqs: the CustomEmailSender Lambda trigger is never invoked, so no verification/OTP code is ever produced and all seven real-code checks hang to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `f04105fb2faf5f6bd82b29a86b394ae1fc089f7b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SignUp

## Description
Cause 1 of 1: a user pool configured with LambdaConfig.CustomEmailSender never invokes that function, so the real verification/OTP code is never produced and every flow that needs it stalls until the harness kills the check.

AWS: CreateUserPool accepts LambdaConfig.CustomEmailSender = {LambdaVersion: 'V1_0', LambdaArn: <fn>} together with LambdaConfig.KMSKeyID. Smithy (cognito-idp): LambdaConfigType.CustomEmailSender targets CustomEmailLambdaVersionConfigType with required LambdaVersion (documented 'You must use a LambdaVersion of V1_0 with a custom sender function') and required LambdaArn; LambdaConfigType.KMSKeyID is documented 'The ARN of an KMS key. Amazon Cognito uses the key to encrypt codes and temporary passwords sent to …'. With that configuration Cognito stops delivering email itself and instead invokes the named function exactly once per code-producing operation, passing the code in request.code as an AWS Encryption SDK message encrypted under that CMK, plus event.triggerSource / event.userName / event.userPoolId. Recorded behavior (these checks' oracle, 2026-10-01): sign_up yields one invocation with triggerSource 'CustomEmailSender_SignUp', ResendConfirmationCode another, ForgotPassword 'CustomEmailSender_ForgotPassword', GetUserAttributeVerificationCode / UpdateUserAttributes(email) the attribute-verification source, and an InitiateAuth USER_AUTH EMAIL_OTP challenge 'CustomEmailSender_Authentication' with an 8-digit code; the code the trigger decrypts is exactly the code the matching ConfirmSignUp / ConfirmForgotPassword / VerifyUserAttribute / RespondToAuthChallenge call accepts, and the superseded or wrong code is refused.

Emulator: no invocation ever happens. The whole estate is accepted — kms:CreateKey, sqs:CreateQueue, iam:CreateRole, lambda:CreateFunction reaching State='Active', cognito-idp:CreateUserPool carrying the CustomEmailSender LambdaConfig and KMSKeyID, lambda:AddPermission for principal cognito-idp.amazonaws.com, CreateUserPoolClient — and then the code-producing call returns normally while nothing is delivered to the trigger's sink. All seven checks consequently block in their inbox poll (a 120 s deadline inside the check) and are killed by the harness at 60 s; the report shows them only as 'Check timed out after 60.0s'. Hypothesis: the configured trigger is stored and echoed but the code-producing handlers never dispatch it (the same dispatch path reported for other triggers in open issue 20261023T114649Z-cognito-idp-cognito-user-pool-lambda-triggers-are-not-invoked.md, which covers PreSignUp / PreTokenGeneration V2_0 / non-invokable trigger ARNs, does not mention CustomEmailSender or the KMS code encryption and does not carry these checks' replay keys). Open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md reports that lambda:Invoke itself answers NotImplemented, which would also have to be fixed for a dispatched invocation to run the function.

Why: a client cannot exercise any code-based Cognito flow against the emulator — sign-up confirmation, ResendConfirmationCode, ForgotPassword/ConfirmForgotPassword, email-attribute verification and passwordless EMAIL_OTP sign-in all require the delivered code, and with a custom sender configured there is no other channel to obtain it. Worse, the configuration is accepted silently, so an application whose only code channel is a CustomEmailSender trigger appears correctly wired while every user is permanently stuck at the 'enter the code we emailed you' step, and the single-use / superseded-code / wrong-code refusal rules that depend on a real outstanding code cannot be observed at all.

Fix: the user-pool Lambda-trigger dispatch path in cognito-idp — the code-producing handlers (SignUp, ResendConfirmationCode, ForgotPassword, GetUserAttributeVerificationCode, UpdateUserAttributes on a verified-attribute change, and the EMAIL_OTP challenge of InitiateAuth/RespondToAuthChallenge) must, when LambdaConfig.CustomEmailSender is set, encrypt the generated code under LambdaConfig.KMSKeyID and invoke the configured function with the V1_0 event shape instead of self-delivering or silently skipping it.

Traces: cognito-idp__kms__lambda__sqs.deep-cognito-idp-1-real-code-email-otp-wrong-code-rejected, .deep-cognito-idp-1-real-code-forgot-password-code-reuse-rejected, .deep-cognito-idp-1-real-code-forgot-password-confirm, .deep-cognito-idp-1-real-code-reissued-reset-code-invalidates-first-rejected, .deep-cognito-idp-1-real-code-resent-signup-code-invalidates-first-rejected, .deep-cognito-idp-1-real-code-verify-email-wrong-code-rejected, .deep-cognito-idp-1-real-code-verify-updated-email. (The eighth sibling, .deep-cognito-idp-1-real-code-email-otp-session-expiry-rejected, also times out but is deliberately excluded: its own design sleeps 150 s + 210 s of genuine elapsed time, which no 60 s harness budget can accommodate, so its timeout is not attributable to the emulator.)

## Evidence
All seven checks fail identically with 'Error: Check timed out after 60.0s' and no frame, each blocked in the same inlined helper: _CodeInbox.next_code(username, trigger_source, timeout_s=120.0), which long-polls the trigger's SQS sink and would otherwise raise "no <trigger_source> code for <user> reached the trigger's queue within 120.0s; deliveries seen but unmatched: []". Expected (AWS): one CustomEmailSender invocation per code-producing call, carrying triggerSource CustomEmailSender_SignUp / CustomEmailSender_ForgotPassword / CustomEmailSender_Authentication (8-digit code) / the attribute-verification source for the matching user, with request.code decryptable under LambdaConfig.KMSKeyID. Actual (emulator): zero invocations — nothing is ever delivered, so the sink stays empty and the check is killed at the 60 s cap. Everything upstream succeeds (CreateFunction -> State='Active', CreateUserPool with LambdaConfig.CustomEmailSender + KMSKeyID, AddPermission for cognito-idp.amazonaws.com, CreateUserPoolClient), and none of these checks was reported as blocked by an unimplemented scaffold stub.

## Steps to Reproduce
1. kms:CreateKey with a key policy allowing kms:Encrypt/kms:CreateGrant to Service principal cognito-idp.amazonaws.com. 2. sqs:CreateQueue as a sink; iam:CreateRole for Lambda with kms:Decrypt on the key and sqs:SendMessage on the queue. 3. lambda:CreateFunction (nodejs22.x) whose handler forwards the event (triggerSource, userName, decrypted request.code) to that queue; wait for State='Active'; lambda:AddPermission(Action='lambda:InvokeFunction', Principal='cognito-idp.amazonaws.com', SourceArn=<pool ARN>). 4. cognito-idp:CreateUserPool with LambdaConfig={'CustomEmailSender': {'LambdaVersion': 'V1_0', 'LambdaArn': <fn>}, 'KMSKeyID': <key ARN>} and AutoVerifiedAttributes=['email']; CreateUserPoolClient. 5. cognito-idp:SignUp a user with an email attribute. 6. sqs:ReceiveMessage on the sink — AWS delivers one message with triggerSource 'CustomEmailSender_SignUp' within seconds; the emulator delivers nothing, so ConfirmSignUp can never be given a real code. 7. Repeat with ForgotPassword, ResendConfirmationCode, UpdateUserAttributes(email) and InitiateAuth(AuthFlow='USER_AUTH', PREFERRED_CHALLENGE='EMAIL_OTP') — no invocation for any of them.
