# ec2 transit gateway: 4 net-new behavioral root causes — IncorrectState refusal prose on Accept/RejectTransitGatewayVpcAttachment, DeleteTransitGatewayConnect answers 501, propagation reports 'enabling' instead of a settled state, and a VPC attachment never auto-associates with the default route table

> _Note: this issue was identified against the code base at commit `ea226a61fd4fc055bb456ff32cf72ea13892c65d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AcceptTransitGatewayVpcAttachment, RejectTransitGatewayVpcAttachment, DeleteTransitGatewayConnect, EnableTransitGatewayRouteTablePropagation, CreateTransitGatewayVpcAttachment

## Description
Four net-new root causes in the EC2 transit-gateway family, all of them ec2-only (Causes 1 of 4 .. 4 of 4). Each cause has its own failing check ids; a fixer must close all four before submitting.

--- Cause 1 of 4: the IncorrectState refusal of AcceptTransitGatewayVpcAttachment and RejectTransitGatewayVpcAttachment is emulator-authored prose, not AWS's sentence. ---
AWS: both operations require the attachment to be in `pendingAcceptance`; an attachment in any other state is refused with HTTP 400, error code `IncorrectState`, and the message template `<TransitGatewayAttachmentId> is in invalid state` — fixed text ` is in invalid state`, with the attachment id taken verbatim from the request as its only variable part. Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json): AcceptTransitGatewayVpcAttachment / RejectTransitGatewayVpcAttachment each take only `TransitGatewayAttachmentId` (@required) + `DryRun` and declare NO error shapes (EC2 returns every documented code through the generic error channel), so the code and the sentence are recorded behavior only — the checks measured `IncorrectState` plus that exact sentence against real AWS.
Emulator: the code is right and the status is right, but the sentence is the emulator's own: `The transit gateway attachment 'tgw-attach-...' is in state 'available'; only an attachment in state 'pendingAcceptance' can be accepted` (and the `... can be rejected` twin). The attachment id, the two state words and the trailing clause are all emulator-chosen prose; none of that shape exists in AWS's message.
Why: a client that matches on the refusal message (log scrapers, retry classifiers, test assertions that pin AWS's wording, and SDK-level error-message comparisons) sees a sentence AWS never emits, so a refusal that is semantically correct still reads as an unknown failure.
Fix: the refusal construction in the two handlers (services/service-com-amazonaws-ec2-amazonec2/src/ops/accept_transit_gateway_vpc_attachment.rs and .../src/ops/reject_transit_gateway_vpc_attachment.rs) — or the shared helper they build the IncorrectState refusal through — must emit `{attachment_id} is in invalid state` and nothing else.
Traces: ec2.op-contract-acceptTransitGatewayVpcAttachment, ec2.op-contract-reject-transit-gateway-vpc-attachment-rejected.

--- Cause 2 of 4: DeleteTransitGatewayConnect is an unimplemented scaffold, so deleting a Connect attachment answers 501 NotImplemented instead of the state/dependency refusal or a deletion. ---
AWS: `Deletes the specified Connect attachment. You must first delete any Connect peers for the attachment.` (Smithy doc for DeleteTransitGatewayConnect; input `TransitGatewayAttachmentId` @required + `DryRun`; output `TransitGatewayConnect`; no modeled error shapes). A Connect attachment that still carries Connect peers is therefore refused with a client 400 — the recorded behavior the check accepts is error code `IncorrectState` or `DependencyViolation` — and a clean Connect attachment is deleted and answered with the attachment in its `deleting` state.
Emulator: HTTP 501 with code `NotImplemented` and the message `operation DeleteTransitGatewayConnect is scaffolded but not implemented in this emulator`. services/service-com-amazonaws-ec2-amazonec2/src/ops/delete_transit_gateway_connect.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker and its `handle` body is `Err(crate::scaffolded::Scaffolded::not_implemented("DeleteTransitGatewayConnect"))`. No open issue names this operation (CreateTransitGatewayConnect and CreateTransitGatewayConnectPeer are both filed and fixed; there is no DeleteTransitGatewayConnect issue), and the replay did not mark this check as blocked because the check converts the error into an assertion rather than letting it escape.
Why: a Connect attachment can be created but never torn down, so the quota it holds is never released and the documented 'delete the peers first' precondition is unobservable; a client cannot distinguish 'refused because peers remain' from 'this emulator has no such operation', and a 501 is not retryable or classifiable as a client error.
Fix: implement `handle` in services/service-com-amazonaws-ec2-amazonec2/src/ops/delete_transit_gateway_connect.rs — resolve the attachment, refuse with the client 400 code above while Connect peers remain, otherwise move it to `deleting` with the crate's clock-owed `deleted` transition and answer the stored `TransitGatewayConnect`; then drop the SCAFFOLDED marker line.
Traces: ec2.op-contract-deleteTransitGatewayConnect.

--- Cause 3 of 4: EnableTransitGatewayRouteTablePropagation answers Propagation.State 'enabling', a transient state real AWS does not hand back from this call. ---
AWS: the call's own response carries `Propagation` (Smithy: EnableTransitGatewayRouteTablePropagationResult$Propagation -> TransitGatewayPropagation, member `State` -> TransitGatewayPropagationState, enum values `enabling`,`enabled`,`disabling`,`disabled`). Recorded behavior: the propagation in the ENABLE response is already settled — two independent checks assert `State` in (`pending`, `enabled`) for the response of that call, i.e. a settled `enabled` (`pending` is not even a member of the modeled enum, so the only value satisfying both the model and the recordings is `enabled`); neither recording shows `enabling`.
Emulator: returns `enabling`. This is deliberate in the handler: services/service-com-amazonaws-ec2-amazonec2/src/ops/enable_transit_gateway_route_table_propagation.rs documents itself as `leaving the propagation in the transient state of an enable with the clock owing it 'enabled'`, and crate::state's `TRANSITION_DELAY` (500 ms) settles it only on a LATER call.
Why: a client that reads the enable response and proceeds (or asserts on the state it got) sees a word AWS never returns here, so every state-machine assertion or wait that keys off this response's State is wrong; a caller that treats `enabling` as 'not usable yet' sleeps for a state change the response should already have reported.
Fix: the enable handler's response projection — answer the propagation already in `enabled` for the enable path (the clock-owed REMOVAL of the record after a disable is a separate, unaffected move).
Traces: ec2.op-contract-enableTransitGatewayRouteTablePropagation, ec2.transit-gateway-route-table-propagation-produces-route-duplicate-enable-rejected.

--- Cause 4 of 4: a new transit gateway VPC attachment never becomes observable on the gateway's default association route table, so the association lifecycle cannot be read at all. ---
AWS: a transit gateway whose `DefaultRouteTableAssociation` is `enable` auto-associates each new attachment with its default association route table — no Associate call is made — and that association is reported by GetTransitGatewayRouteTableAssociations with `State` walking `associating` -> `associated`, `ResourceType` `vpc`, the gateway reporting the table as `Options.AssociationDefaultRouteTableId`; a second AssociateTransitGatewayRouteTable against a different table while that association stands is refused `Resource.AlreadyAssociated` (recorded behavior only — EC2 models no error shapes; Smithy gives only the shapes: TransitGatewayAssociationState enum `associating`,`associated`,`disassociating`,`disassociated`).
Emulator: the check never observes that chain and spends its whole budget polling (verdict `mismatch`, detail `Check timed out after 60.0s`, with no assertion reached). services/service-com-amazonaws-ec2-amazonec2/src/ops/create_transit_gateway_vpc_attachment.rs writes ONLY the attachment record (`store.insert_transit_gateway_vpc_attachment(view)`) and answers it; nothing in that handler records a route-table association, and the attachment's own state/`available` move and the gateway's `AssociationDefaultRouteTableId` are the other two gates the check waits on. Hypothesis: the missing auto-association is what the poll never satisfies (its budget for that gate is 180 s, the attachment-available gate 240 s, both far above the 60 s the run allowed), since every clock-owed move in this crate settles after TRANSITION_DELAY = 500 ms and so cannot explain a 60 s stall on its own.
Why: a client cannot see which route table its attachment landed on, cannot move it (disassociate-then-associate), and the documented 'only one route table per attachment' refusal is unreachable — the whole default-association contract of a transit gateway is invisible.
Fix: CreateTransitGatewayVpcAttachment must record the default-table association as part of creating the attachment (the association store crate::state documents per (route table, attachment) pair, answered `associating` with `associated` owed to the clock), and GetTransitGatewayRouteTableAssociations must report it; note 20261029T175114Z-ec2-gettransitgatewayroutetableassociations-stub.md (open) covers only that read operation's stub and does not name this check, and 20261023T155030Z-ec2-transit-gateway-omits-encryptionsupport-and-never-reaches.md covers the gateway record's own members — neither covers the missing auto-association.
Traces: ec2.transit-gateway-route-table-association-moves-between-tables.
