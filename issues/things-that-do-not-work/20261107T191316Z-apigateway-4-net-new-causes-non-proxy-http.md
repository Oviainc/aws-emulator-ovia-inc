# apigateway: 4 net-new causes — non-proxy HTTP integrations and VTL mapping templates answer 500 at a deployed stage, CFN-provisioned stage URLs answer 404 UnknownService, and FlushStageAuthorizersCache never invalidates the authorizer cache

> _Note: this issue was identified against the code base at commit `c3a6f169c346304d6b4c388bf8378b1c143b9d70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke (execute-api data plane)

## Description
Four distinct net-new root causes in the API Gateway REST emulator, all grounded in failing behavioral checks of this suite. None of these checks is marked ALREADY FILED or OWNED by an open issue.

=== Cause 1 of 4: a deployed stage answers 500 for every non-proxy HTTP integration ===
AWS: Smithy: PutIntegration.type -> IntegrationType enum [HTTP, AWS, MOCK, HTTP_PROXY, AWS_PROXY]; `HTTP` is documented as "integrating an API method with an HTTP backend". For type=HTTP, API Gateway calls the configured `uri` with `integrationHttpMethod`, applies the request mapping template, then selects an integration response by selectionPattern and applies the response template, and serves the resulting method response (200 in these recordings). Recorded behavior only for the marker bodies the checks assert.
Emulator: every request through a type=HTTP (non-proxy) integration is answered HTTP 500 with the DEFAULT_5XX body `{"message":"Internal server error"}`. The same checks' type=HTTP_PROXY and type=MOCK legs are served correctly — check `apigw-http-proxy-passes-cors-header-plain-http-integration-drops-it` proves the split: the HTTP_PROXY route is served and the plain-HTTP route is 500. The front API in `apigw-cache-key-parameters-...` and `apigw-extended-request-id-...` points at a second, healthy stage of the same emulator, so the backend being unreachable is not the explanation.
Why: a client that models an existing HTTP backend behind a REST API — the canonical non-proxy integration with request/response mapping — gets a 500 for every call. Request/response transformation, caching keyed on declared cache-key parameters, per-stage backend selection via stage variables, and passthrough (415) behavior are all unobservable because no call ever reaches the backend.
Fix: the execute-api data-plane integration dispatcher for IntegrationType HTTP in the apigateway service crate (the outbound HTTP integration client and its response-mapping path), not the control plane — PutIntegration itself accepts the configuration.
Traces: apigateway.apigw-cache-key-parameters-index-the-stage-cache-per-declared-key-only, apigateway.apigw-extended-request-id-is-minted-per-api-per-request-not-echoed, apigateway.apigw-http-proxy-passes-cors-header-plain-http-integration-drops-it, apigateway.apigw-stage-variable-selects-a-different-backend-per-stage-from-one-deployment, apigateway.apigw-strict-passthrough-rejects-an-unmapped-content-type-with-415, apigateway.apigw-vtl-request-and-response-templates-transform-a-real-body (this last one wires both a MOCK backend and an HTTP front, so it also exercises Cause 2).

=== Cause 2 of 4: VTL mapping-template evaluation beyond a literal body answers 500 ===
AWS: Smithy: PutIntegration.requestTemplates / PutIntegrationResponse.responseTemplates are MapOfStringToString of VTL templates. API Gateway's template language supports `$input.params(name)`, `$input.params().header.get(name)`, `$input.path('$.x')`, `$util.escapeJavaScript(...)`, `$stageVariables.<name>`, `$context.requestId` / `$context.extendedRequestId`, the `#if` directive, and `#set($context.responseOverride.status = <int>)` / `#set($context.responseOverride.header.<Name> = ...)`. A template using them renders and the stage serves the mapped status/headers/body; `$context.responseOverride.status` set to a numeric literal becomes the served status (201 here), and a MOCK request template's `#if` chooses the integration status that selectionPattern then routes.
Emulator: any MOCK integration whose request or response template uses one of those constructs makes the deployed stage answer 500 `{"message":"Internal server error"}`. MOCK methods whose only template is the literal `{"statusCode": 200}` are served fine in the same runs, so the failure is in template evaluation, not in MOCK dispatch. Observed with: `$input.params('id')` + `$input.params().header.get('X-Req')` + `$context.requestId`; `#set($context.responseOverride.status = 201)`; `$util.escapeJavaScript($stageVariables.release)`; `#if($input.params('scope') == "internal")`.
Why: mapping templates are the primary way a REST API shapes requests and responses. A client gets a blanket 500 instead of the mapped body, and cannot observe selectionPattern routing, response status/header overrides, stage-variable substitution or per-request `$context` identity at all.
Fix: the VTL mapping-template evaluator used by the execute-api data plane (the `$input`/`$util`/`$stageVariables`/`$context` bindings and the `#if`/`#set` directive handling), plus the `$context.responseOverride` sink that feeds the response serializer.
Traces: apigateway.apigw-concurrent-invocations-through-one-stage-keep-per-request-identity, apigateway.apigw-response-override-status-requires-numeric-value, apigateway.canary-deployment-traffic-shift-and-promotion, apigateway.mock-selection-pattern-selects-status-and-headers.

=== Cause 3 of 4: a CloudFormation-provisioned REST API's stage invoke URL is not routed ===
AWS: a REST API created by a CloudFormation stack is an ordinary RestApi: its deployed stage serves the method's integration response at the execute-api invoke URL exactly as an SDK-created API does. There is no AWS error code `UnknownService` on the execute-api data plane; an unmatched route is 403 `{"message":"Forbidden"}` and a matched one is the mapped status.
Emulator: the invoke URL of a stack-provisioned stage answers HTTP 404 with the emulator-invented body `{"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}`. The same URL shape is served for an API created directly through the apigateway API in the same run, so the CFN-created RestApi is never registered with the execute-api router. The fixed text here is the emulator's own; nothing of it is AWS wording.
Why: every template-deployed API is dead on arrival — a client cannot invoke, negatively test, or roll forward a stack-managed REST API.
Fix: the CloudFormation resource provider for AWS::ApiGateway::RestApi/Deployment/Stage must register the created API and stage with the same execute-api route table the control-plane handlers populate. Related but NOT covering these checks: open issues 20261103T000000Z-apigateway-cloudformation-a-template-deployed-rest-api-stage-url-answers-404-unknownservice.md and 20261107T070300Z-apigateway-dynamodb-lambda-logs-cloudformation-deployed-rest-api-stages-are-unservable-the.md — neither carries these two replay keys.
Traces: apigateway.deploy-apigateway-1-cfn-deployment-without-method-rejected, apigateway.deploy-rest-api-cfn-behaves.

=== Cause 4 of 4: FlushStageAuthorizersCache is accepted but does not invalidate the authorizer cache ===
AWS: Smithy: FlushStageAuthorizersCache — DELETE /restapis/{restApiId}/stages/{stageName}/cache/authorizers, success code 202, empty output. Accepting it means the stage's authorizer-result cache is dropped, so the next request re-invokes the TOKEN authorizer even though `authorizerResultTtlInSeconds` (300 here) has not elapsed.
Emulator: the call is accepted with 202, but subsequent requests with the same identity-source value keep being served the cached authorizer result — the authorizer's invocation counter stays at its pre-flush value for the whole 120 s poll window (`{'count': '1'}`).
Why: a client that rotates authorizer state (revoked token, changed group membership) and flushes the cache to make it effective keeps being authorized off the stale decision for up to the full TTL; the flush is a no-op that reports success.
Fix: the FlushStageAuthorizersCache handler must clear the data-plane authorizer-result cache keyed by (stage, identity source), in the execute-api authorizer cache rather than only acknowledging the control-plane call.
Traces: apigateway.flush-stage-authorizers-cache-bypasses-ttl.

## Evidence
Cause 1 — expected: the deployed stage serves the HTTP integration's mapped response (200 plus the marker body the backend returns). Actual, e.g. apigw-http-proxy-passes-cors-header-plain-http-integration-drops-it: `AssertionError: plain HTTP route not observed within 90.0s; last=(500, '{"message":"Internal server error"}')`; apigw-cache-key-parameters-...: `GET .../_aws/execute-api/<apiId>/<stage>/vary?k=alpha&other=1 to be served by the cached front stage not observed within 150.0s; last=(status=500, body='{"message":"Internal server error"}')`; apigw-strict-passthrough-...: `POST .../strict with a MATCHING application/json Content-Type to be served 200 ... last=(status=500, body='{"message":"Internal server error"}')`. In all of them the HTTP_PROXY and MOCK legs of the same API are served.

Cause 2 — expected: 200 (or the overridden 201) with the rendered template body. Actual: 500 `{"message":"Internal server error"}` from the stage. apigw-response-override-status-requires-numeric-value (MOCK + `#set($context.responseOverride.status = 201)`): `GET to be served not observed within 150.0s; last=(500, '{"message":"Internal server error"}')`. mock-selection-pattern-selects-status-and-headers (MOCK request template using `#if($input.params('scope') == "internal")`): `GET .../select?scope=internal to be served the 200 branch not observed within 120.0s; last=(500, ...)`. canary-deployment-traffic-shift-and-promotion (response template `$util.escapeJavaScript($stageVariables.release)`): `... to serve the base deployment (snapshot v1, release=base) not observed within 120.0s; last=(500, ...)`. apigw-concurrent-invocations-... (`$input.params(...)`, `$input.params().header.get(...)`, `$context.requestId`): `... to be served by the deployed stage not observed within 150.0s; last=(500, ...)`.

Cause 3 — expected: 200 from the stack's deployed stage (and, for the negative leg, 500 for a method-less deployment). Actual: `404, '{"__type":"UnknownService","message":"could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"}'` at `https://<host>/_aws/execute-api/<apiId>/<stage>/<path>`. Variable parts: apiId, stage, path, host/port. Fixed text: the whole `UnknownService` sentence, which AWS never emits.

Cause 4 — expected: after a 202 from FlushStageAuthorizersCache, the next request re-invokes the TOKEN authorizer, so its returned `context.count` rises above the pre-flush value. Actual: `AssertionError: authorizer count never advanced past baseline 1 within 120.0s (last observed: {'count': '1'})` with `authorizerResultTtlInSeconds=300`.
