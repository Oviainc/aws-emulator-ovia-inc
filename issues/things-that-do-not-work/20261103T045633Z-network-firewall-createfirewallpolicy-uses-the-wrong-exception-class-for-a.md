# CreateFirewallPolicy uses the wrong exception class for a duplicate policy name and accepts an unknown stateless default action (2 root causes)

> _Note: this issue was identified against the code base at commit `981c4cbbb98c58ce8ac9493ce56831a4fdef61bb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFirewallPolicy

## Description
CreateFirewallPolicy's request validation diverges from AWS in two independent ways: a name that is already taken is refused with the wrong (unmodeled-for-this-case) exception class, and a StatelessDefaultActions value outside the supported action vocabulary is accepted and stored instead of being refused. This bundle has 2 causes.

Cause 1 of 2 - a duplicate FirewallPolicyName is refused as InvalidOperationException instead of InvalidRequestException (failing check: network-firewall.nfwr-policy-duplicate-name-rejected).
AWS: a second CreateFirewallPolicy under a FirewallPolicyName that already exists is refused with HTTP 400 and error code InvalidRequestException, message "A resource with the specified name already exists". Smithy: CreateFirewallPolicy models both InvalidRequestException and InvalidOperationException (both client errors, httpError 400); InvalidRequestException is documented as "The operation failed because of a problem with your request. Examples include: You specified an unsupported parameter name or value...", while InvalidOperationException is documented as "The operation failed because it's not valid. For example, you might have tried to delete a rule group or firewall policy that's in use" - i.e. an in-use/state conflict, not a name clash. The name-clash code and message are recorded behavior. Message template: the fixed text "A resource with the specified name already exists" with no variable part.
Emulator: returns HTTP 400 with code InvalidOperationException and the right message text. The surviving state is correct (the original policy still resolves to its original ARN with its original document) - only the error class diverges.

Cause 2 of 2 - an unsupported StatelessDefaultActions value is accepted with HTTP 200 instead of being refused (failing check: network-firewall.nfwr-policy-unknown-stateless-action-rejected).
AWS: FirewallPolicy.StatelessDefaultActions is required and must contain one of the standard actions aws:pass, aws:drop or aws:forward_to_sfe (plus named custom actions declared in StatelessCustomActions) - Smithy: FirewallPolicy.StatelessDefaultActions -> StatelessActions (a list of string, so the vocabulary is prose/recorded behavior, not an enum), documented "You must specify one of the standard actions: aws:pass, aws:drop, or aws:forward_to_sfe. In addition, you can specify custom actions that are compatible with your standard section choice." A value outside that set is refused with HTTP 400, code InvalidRequestException and message "StatelessDefaultActions is invalid, parameter: [<action>], context: StatelessDefaultActions". Fixed text: "StatelessDefaultActions is invalid, parameter: [", "], context: StatelessDefaultActions"; variable part: the rejected action string taken verbatim from the request (the check sends aws:forward_to_stateful). Because the request is refused, no policy is created: the name stays free and DescribeFirewallPolicy on it answers ResourceNotFoundException with message "No object with the provided name or resource identifier was found".
Emulator: returns HTTP 200 and creates the policy (FirewallPolicyStatus ACTIVE, an UpdateToken and a full FirewallPolicyResponse), so the unsupported action is stored and the name is consumed.

Why: for Cause 1 a client that distinguishes AWS's error classes - retrying or renaming on InvalidRequestException but treating InvalidOperationException as a resource-in-use/state conflict that it must drain before retrying - takes the wrong branch and either loops or aborts an idempotent create path that works against real AWS. For Cause 2 a client gets a false success for a policy AWS would never store: its firewall policy silently differs from production (a packet that matches no stateless rule is handled by an action the engine does not implement), the modeled InvalidRequestException path is never exercised, and the name the client expected to remain free is now taken, so the corrected retry under the same name fails with a name clash that cannot happen on AWS.

Fix: CreateFirewallPolicy's request validation and handler in the network-firewall service crate - raise InvalidRequestException (not InvalidOperationException) for the existing-name conflict, and validate every StatelessDefaultActions / StatelessFragmentDefaultActions entry against the standard action set plus the request's declared StatelessCustomActions before any state mutation, raising InvalidRequestException with the message template above so the name is not consumed. Related but distinct open issues on this operation: 20261102T120026Z-network-firewall-createfirewallpolicy-does-not-validate-statefuldefaultactions-against-the-policy.md (StatefulDefaultActions rule-order/action validation; it records the same wrong InvalidOperationException class as a side effect but does not own the duplicate-name refusal) and 20261102T120026Z-network-firewall-describe-responses-omit-the-empty-tags-list-and.md (canonical casing of a stored stateless action on read, not refusal of an unsupported one).

Traces: network-firewall.nfwr-policy-duplicate-name-rejected, network-firewall.nfwr-policy-unknown-stateless-action-rejected.

## Evidence
Cause 1 - check network-firewall.nfwr-policy-duplicate-name-rejected: after creating a policy, a second CreateFirewallPolicy with the same FirewallPolicyName was expected to fail with Code 'InvalidRequestException' and Message 'A resource with the specified name already exists'; the emulator answered Code 'InvalidOperationException' (assertion: "a duplicate policy name returned 'InvalidOperationException', expected InvalidRequestException").

Cause 2 - check network-firewall.nfwr-policy-unknown-stateless-action-rejected: CreateFirewallPolicy with StatelessDefaultActions=['aws:forward_to_stateful'] and StatelessFragmentDefaultActions=['aws:forward_to_sfe'] was expected to fail with ('InvalidRequestException', 'StatelessDefaultActions is invalid, parameter: [aws:forward_to_stateful], context: StatelessDefaultActions'); the emulator returned HTTP 200 with UpdateToken + FirewallPolicyResponse {FirewallPolicyStatus: 'ACTIVE', ConsumedStatelessRuleCapacity: 0, ...} (assertion: "expected a rejection, but it succeeded"). The policy name is then consumed, so the check's follow-up DescribeFirewallPolicy on that name, which AWS answers with ResourceNotFoundException / 'No object with the provided name or resource identifier was found', would also diverge.
