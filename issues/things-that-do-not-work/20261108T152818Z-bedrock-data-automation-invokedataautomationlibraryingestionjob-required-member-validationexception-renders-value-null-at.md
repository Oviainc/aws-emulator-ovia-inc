=== Cause 1 of 2: the required-member ValidationException message renders "Value null at" where AWS renders "Value at" ===
AWS: Smithy (services/service-com-amazonaws-bedrockdataautomation-amazonbedrockkeystonebuildtimeservice/smithy-model/com-amazonaws-bedrockdataautomation-amazonbedrockkeystonebuildtimeservice.json): VocabularyEntityInfo.phrases targets PhraseList, @required, @length(min 1); ValidationException is errorKind client, @httpError(400), members message + fieldList. Recorded behavior: omitting a @required member is refused 400 ValidationException whose message is "1 validation error detected: Value at '<member path>' failed to satisfy constraint: Member must not be null". Its FIXED text is "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must not be null"; its only VARIABLE part is the member path, derived from the request's shape traversal. AWS renders NO value token between "Value" and "at" for this constraint class — in particular not the literal "null".
Emulator: status 400 and code ValidationException are correct, but the message is "1 validation error detected: Value null at '<path>' failed to satisfy constraint: Member must not be null" — the builder splices a rendered value (here the literal "null", the same slot where the sibling pattern/enum path splices the rejected value) into a message AWS leaves value-free.
Why: a client or conformance test that compares the refusal text against AWS never matches, so the required-member contract of this operation cannot be asserted; SDK-level error-message matching and any log-scraping on "Value at '<field>'" silently fails to classify the error. The status and code are right, so the defect is invisible until the text is compared.
Fix: the shared ValidationException message builder in the centralized validate phase for this service's generated INPUT_SCHEMAs — emit "Value at '<path>'" with no value token for the required/not-null violation class (the same builder the related issue above indicts for pattern/enum).
Traces: bedrock-data-automation.ingestion-job-missing-required-phrases-validation-rejected.

=== Cause 2 of 2: the member path omits the union and list member-name segments of the nested payload ===
AWS: Smithy, same model: InvokeDataAutomationLibraryIngestionJobRequest.inputConfiguration -> InputConfiguration; InputConfiguration.inlinePayload -> InlinePayload, a UNION whose member upsertEntitiesInfo targets UpsertEntitiesInfo (list, @length min 1 max 10) whose member targets UpsertEntityInfo, itself a UNION whose member vocabulary targets VocabularyEntityInfo, which declares the @required member phrases. Recorded behavior: the refusal names the full traversal, with each structure/union member name and each list index rendered as "<1-based index>.member": 'inputConfiguration.inlinePayload.upsertEntitiesInfo.1.member.vocabulary.phrases'. The path segments are FIXED by the model's shape graph; only the index comes from the request (the position of the offending list element, 1-based).
Emulator: the refusal names 'inputConfiguration.inlinePayload.1.member.phrases' — the union member names that select the payload variant and the entity variant ('upsertEntitiesInfo' after inlinePayload, 'vocabulary' after the list member) are both dropped, so the path descends from a union straight into a list and from a list member straight into the structure's member. The emitted path does not exist in the request shape.
Why: the member path is the only machine-usable part of a ValidationException message (and the same string AWS puts in ValidationExceptionField.name), so a client that maps the refusal back onto its own request payload to highlight the offending field, or that asserts on the field path, resolves a path that does not exist and cannot locate the bad element — and a payload with several union variants in flight becomes ambiguous about which variant was rejected. It also makes the emulator's refusal indistinguishable between an InlinePayload variant and a sibling variant.
Fix: the member-path construction in the centralized validate phase's shape walk for this service — push a path segment for UNION members and for the list member's enclosing member name as well as for structure members, so the rendered path matches the model traversal (and use the same path in ValidationExceptionField.name).
Traces: bedrock-data-automation.ingestion-job-missing-required-phrases-validation-rejected.
