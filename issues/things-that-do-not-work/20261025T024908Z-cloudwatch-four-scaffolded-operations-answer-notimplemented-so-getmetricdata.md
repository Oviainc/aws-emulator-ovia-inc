# CloudWatch: four scaffolded operations answer NotImplemented, so GetMetricData query validation, PutDashboard body validation, GetMetricWidgetImage rendering/limits and AssociateDatasetKmsKey KMS preconditions all diverge (4 causes)

> _Note: this issue was identified against the code base at commit `e0255819ca3e503154d6ac924edd987da058b9b5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetMetricData

## Description
Four distinct causes, each a scaffolded CloudWatch operation that answers the unmodeled error code `NotImplemented` for every request, and each with request-shaped behavior that must come with the implementation. These checks were NOT marked ALREADY FILED/OWNED by the replay report because they catch the ClientError and assert on its code, so they land as `mismatch` rather than `error` and carry no stub marker. The bare stub existence is tracked by open issues 20261025T020208Z-cloudwatch-getmetricdata-stub.md, 20261025T020208Z-cloudwatch-putdashboard-stub.md, 20261025T020208Z-cloudwatch-getmetricwidgetimage-stub.md and 20261025T020208Z-cloudwatch-associatedatasetkmskey-stub.md; none of those carries these checks' replay keys, and none of them states the validation semantics below, which is what these checks grade. Fixing the stubs alone will not close these checks.

Cause 1 of 4: GetMetricData performs no request validation. Failing checks: cloudwatch.get-metric-data-duplicate-query-id-rejected, cloudwatch.get-metric-data-metric-math-invalid-expression-rejected.
AWS: Smithy: GetMetricData.MetricDataQueries (@required, list of MetricDataQuery), StartTime/EndTime @required timestamps; the only modeled error is InvalidNextToken, so query-shape refusals are the service-common validation class. Recorded behavior: two MetricDataQueries sharing the same `Id` are refused synchronously with error code `ValidationError` (HTTP 400); a metric-math query whose `Expression` has unbalanced parentheses (`SUM(`) is likewise refused with `ValidationError` at request time and the refusal names the offending query id (recorded example message: "Error in expression 'e1': Invalid syntax") rather than returning 200 with a per-result StatusCode. A syntactically valid ordinary metric query over the same window is a 200 with data.
Emulator: every GetMetricData call answers error code `NotImplemented` ("operation GetMetricData is scaffolded but not implemented in this emulator"); the checks read `NotImplemented` where they expect `ValidationError`.
Why: GetMetricData is the primary metric read path. A client gets no data at all, and the two distinct outcomes AWS separates — a malformed query rejected up front vs. a valid query returning datapoints — collapse into one failure, so query-builder code (dashboards, alarm previews, metric-math editors) cannot distinguish a client bug from a server fault and never sees its own syntax errors reported.
Fix: the GetMetricData handler plus its input validation (duplicate `Id` across MetricDataQueries; metric-math `Expression` parse) in the cloudwatch service crate's ops layer, and the metric read path it must serve from.

Cause 2 of 4: PutDashboard does not validate DashboardBody, and the CloudFormation dashboard resource inherits that. Failing checks: cloudwatch.deploy-cloudformation-invalid-dashboard-body-rejected, cloudwatch.put-dashboard-with-a-metric-widget-missing-metrics-rejected.
AWS: Smithy: PutDashboard.DashboardName and .DashboardBody are both @required; modeled error DashboardInvalidInputError, errorKind client, httpError 400, awsQueryError code `InvalidParameterInput`. Recorded behavior: a DashboardBody that is not valid JSON is refused `InvalidParameterInput` (400) with a message built from the offending field (recorded example: "The field DashboardBody must be a valid JSON object"); a body that IS valid JSON but whose metric widget omits `metrics` is also refused `InvalidParameterInput`, with a message built from the widget-schema validation results (recorded example enumerates per-dataPath problems under "/widgets/0/properties"). In both cases nothing is stored: a subsequent GetDashboard on the refused name answers `ResourceNotFound`. Driven through CloudFormation, an `AWS::CloudWatch::Dashboard` carrying the same invalid body must fail the resource and the stack must not reach CREATE_COMPLETE.
Emulator: PutDashboard answers error code `NotImplemented` for both bodies, so no dashboard is ever validated or stored, and the CloudFormation leg cannot be graded either.
Why: a client that relies on CloudWatch to validate a dashboard document gets a non-modeled `NotImplemented` instead of the schema diagnosis it parses, and infrastructure-as-code pipelines cannot tell a bad template from a working one; nothing in the dashboard surface is usable.
Fix: the PutDashboard handler, a DashboardBody JSON + widget-schema validator that emits DashboardInvalidInputError/`InvalidParameterInput`, the dashboard state store, and the CloudFormation resource provider for AWS::CloudWatch::Dashboard so that a refused Put fails the resource. The `ResourceNotFound` read-back leg also needs GetDashboard (open issue 20261025T020208Z-cloudwatch-getdashboard-stub.md).

Cause 3 of 4: GetMetricWidgetImage renders nothing and enforces neither of its two request limits. Failing checks: cloudwatch.get-metric-widget-image-cross-account-metric-denied, cloudwatch.get-metric-widget-image-payload-exceeds-limit-rejected.
AWS: Smithy: GetMetricWidgetImage.MetricWidget @required, output member MetricWidgetImage is a blob; the operation models NO errors, so its refusals are service-common classes. Recorded behavior: a well-formed widget returns 200 with non-empty image bytes whose first 8 bytes are the PNG signature, and a widget naming an unlinked FOREIGN `accountId` is likewise ACCEPTED (200, PNG) rather than denied; a MetricWidget that is not valid JSON is refused with code `ValidationError` (recorded example message: "MetricWidget property 'metricWidget' has a bad JSON content"); an uncompressed payload over the documented 100 KB per-call limit is refused at the transport layer with code `RequestEntityTooLarge`, whose message is built from the request body size the client actually sent and the 102400-byte limit.
Emulator: every GetMetricWidgetImage call answers `NotImplemented`, so neither refusal class appears and no image is produced.
Why: consumers embed these PNGs in notifications and reports; they get a non-modeled error instead of bytes, they never learn that their widget JSON is malformed, and an oversized payload is indistinguishable from any other failure. The cross-account leg is also a permissiveness question clients depend on: AWS accepts the foreign accountId, so an emulator must not later start denying it.
Fix: the GetMetricWidgetImage handler — MetricWidget JSON parse producing `ValidationError`, a request-body size gate producing `RequestEntityTooLarge` before handling, and an image serializer returning real PNG bytes.

Cause 4 of 4: AssociateDatasetKmsKey never checks the KMS preconditions. Failing check: cloudwatch.kms-key-access-errors.
AWS: Smithy: AssociateDatasetKmsKey.DatasetIdentifier @required (pattern `^(default|arn:...:dataset/default)$`) and .KmsKeyArn @required (pattern `^arn:[a-zA-Z0-9-]+:kms:...:key/[a-f0-9-]+$`); modeled errors include KmsAccessDeniedException, KmsKeyDisabledException, KmsKeyNotFoundException (all client, 400) and ConflictException (409). Recorded behavior resolves an ambiguity in that model: BOTH usability failures — a key whose policy does not grant the `cloudwatch.amazonaws.com` service principal kms:DescribeKey/GenerateDataKey/Encrypt/Decrypt, and a correctly-permissioned key that is Disabled — surface as the SAME wire error code `AccessDenied` (400), not as two distinct codes. In both cases the association does not take effect (a following GetDataset still does not report that KmsKeyArn), and after the precondition is repaired (key policy updated, or the key re-enabled) the identical call succeeds and GetDataset reports the KmsKeyArn.
Emulator: AssociateDatasetKmsKey answers `NotImplemented`, so no KMS precondition is evaluated, the dataset association never happens, and the check reads `NotImplemented` where it expects `AccessDenied`.
Why: a client cannot encrypt a CloudWatch dataset at all, and the refusal it must handle (fix the key policy / enable the key) is replaced by an unmodeled code its SDK error handling has no branch for — it cannot distinguish "your key is unusable" from "this service is broken".
Fix: the AssociateDatasetKmsKey handler, its KMS key-state and key-policy precondition checks against the kms service state (both mapped to the `AccessDenied` code), and the dataset state that GetDataset reads back. The read-back leg also needs GetDataset (open issue 20261025T020208Z-cloudwatch-getdataset-stub.md).

Traces: the seven failing check ids listed in trace_ids are the examples; each exercises exactly one of the four operations above.
