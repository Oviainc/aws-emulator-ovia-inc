# opensearchserverless: the published collectionEndpoint serves the AWS-JSON RPC front door, so every data-plane check (SigV4 aoss REST, per-permission data-access enforcement, network-policy enforcement) hangs until the check budget expires

> _Note: this issue was identified against the code base at commit `2b503955bb0e5c53465d42867d341986b9868a3b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetCollection

## Description
ONE net-new root cause, grounded in three failing behavioral checks of the opensearchserverless service token. Overlap note: the open issue 20261029T191222Z-opensearchserverless-5-net-new-causes-in-the-state.md describes this same wall as its 'Cause 5 of 5' and lists these three check ids, but the replay suite did NOT mark any of these three as OWNED by it (only opensearchserverless.collection-endpoint-requires-aoss-sigv4-service-name was marked owned), so they are re-filed here with their current failing keys so they are replayed and closed; if that issue's Cause 5 is fixed first, this closes with it. Open issues 20261029T171944Z-bedrock-agent-runtime-2-net-new-causes-the.md and 20261104T034157Z-bedrock-agent-lambda-opensearchserverles-...-the-published-vectorsearch-collection.md describe the same wall under OTHER service tokens.

=== Cause 1 of 1: a collection's published collectionEndpoint is routed to the AWS-JSON protocol dispatcher instead of an OpenSearch REST data plane, so no index/search/document request can be served and no network- or data-access-policy decision is observable ===
AWS: Smithy (com.amazonaws.opensearchserverless) models only the control plane; CollectionDetail.collectionEndpoint is documented as the 'Collection-specific endpoint used to submit index, search, and data upload requests to an OpenSearch Serverless collection', and the protocol spoken there is the OpenSearch REST API, which is not Smithy-modeled — so for the data plane this is recorded behavior only. Recorded behavior: with an ACTIVE collection, an encryption policy, a network policy admitting the caller, a data-access policy naming the signing principal, and the IAM grant aoss:APIAccessAll, a SigV4-signed request with signing service name `aoss` (and x-amz-content-sha256 on body-bearing requests) and NO x-amz-target header is served by OpenSearch at https://<collectionEndpoint>/...: PUT /<index>, PUT /<index>/_doc/<id>, GET /<index>/_doc/<id>, GET/POST /<index>/_search, GET /<index>/_mapping and HEAD /<index> are accepted (200/201); a permission withheld by the data-access policy (e.g. aoss:ReadDocument granted but aoss:WriteDocument withdrawn) is refused HTTP 403 with an OpenSearch error body whose error.type is 'forbidden'; a caller outside every SourceVPCEs entry of the only network policy, or a collection with the network policy deleted, is refused HTTP 401/403 by the service. Those statuses and their fixed error type are the requirement; the index names, document ids and vpce- ids in any one run are request/state values that fill the template.
Emulator: every one of those requests is answered HTTP 400 with the body {"__type":"SerializationException","message":"missing required header `x-amz-target`"} — fixed text, nothing derived from the request. The collectionEndpoint host reaches the emulator's AWS-JSON `x-amz-target` dispatcher, which is the control-plane front door; the OpenSearch REST verbs carry no RPC target header by design, so none of them can ever be served. Because each of these checks treats a failed probe as policy-propagation latency and re-probes on a bounded poll, the failure surfaces to the suite as 'Check timed out after 60.0s' rather than as the 400 itself (the identical 400 is surfaced directly by the sibling bedrock-agent-runtime check, which uses opensearch-py and reports opensearchpy.exceptions.RequestError(400, ...)).
Why: a client cannot use an OpenSearch Serverless collection for anything at all — it can create the collection and read its endpoint, but no index can be created, no document written or read, no search run. Worse, allow and deny become indistinguishable: SigV4 scope validation (aoss vs es), per-permission data-access-policy enforcement, VPC-only network-policy enforcement and the effect of deleting the only network policy on a live endpoint all produce the same 400 whether the service should have allowed or denied, so a client that depends on a 403/401 refusal as a security boundary sees a 400 serialization error and can conclude nothing.
Fix: the opensearchserverless collection data plane plus the emulator's host/endpoint routing table — the host published as collectionEndpoint must route to an OpenSearch REST handler (index create/get/head/delete, document index/get, _search, _mapping) that authorises SigV4 `aoss` requests against the collection's network policy and data-access policy and refuses with 401/403 and an OpenSearch error body, instead of falling through to the AWS-JSON x-amz-target dispatcher in services/service-com-amazonaws-opensearchserverless-opensearchserverless.
Traces: opensearchserverless.data-access-policy-read-permission-without-write-blocks-indexing, opensearchserverless.deleting-network-policy-stops-the-live-collection-endpoint-serving, opensearchserverless.server-side-network-policy-enforces-vpc-only-access.

## Evidence
All three checks are reported by the suite as 'Error: Check timed out after 60.0s' ([mismatch] verdict), with no probe ever succeeding and no probe ever being refused with a service status.

Expected (recorded AWS): 
- data-access-policy-read-permission-without-write-blocks-indexing: with only aoss:ReadDocument on index/<collection>/*, GET /<index>/_doc/<id> and GET/POST /<index>/_search return 200, while PUT /<index>/_doc/<id> and GET /<index>/_mapping are refused HTTP 403 (error.type 'forbidden') and the document never lands.
- deleting-network-policy-stops-the-live-collection-endpoint-serving: a signed, data-access-authorised request succeeds while the network policy exists, and after DeleteSecurityPolicy(type='network') the identical request is refused by the endpoint (401/403).
- server-side-network-policy-enforces-vpc-only-access: HEAD /<probe-index> succeeds under a policy whose SourceVPCEs admits the caller's endpoint, is refused with a TransportError whose status_code is 401 or 403 once the policy is narrowed to a different VPC endpoint, and succeeds again when the original policy is restored.

Actual (emulator): every signed request to https://<collectionEndpoint>/... — regardless of verb, principal, data-access policy or network policy — is answered HTTP 400 with the body {"__type":"SerializationException","message":"missing required header `x-amz-target`"}. The probe loops therefore never observe either the success or the refusal they poll for and are killed by the check budget (60s).

## Steps to Reproduce
1. opensearchserverless.create_security_policy(type='encryption', policy matching collection/<name>); create_security_policy(type='network', policy with Rules=[{ResourceType:'collection', Resource:['collection/<name>']}], AllowFromPublic=false, SourceVPCEs=[<an ACTIVE vpce id>]); create_access_policy(type='data', granting aoss:CreateIndex/DescribeIndex/UpdateIndex/DeleteIndex/ReadDocument/WriteDocument on index/<name>/* and the collection-item permissions on collection/<name>, Principal=[<the calling role ARN>]).
2. create_collection(name=<name>, type='SEARCH', encryptionConfig={'aWSOwnedKey': True}); poll batch_get_collection(ids=[<id>]) until status ACTIVE and read collectionDetails[0].collectionEndpoint.
3. SigV4-sign with signing service name 'aoss' (region of the run), adding x-amz-content-sha256 for body-bearing requests, and send against https://<collectionEndpoint>/: HEAD /<index>, PUT /<index>, PUT /<index>/_doc/<id> with a JSON body, GET /<index>/_doc/<id>, POST /<index>/_search, GET /<index>/_mapping.
   -> every call returns HTTP 400 {"__type":"SerializationException","message":"missing required header `x-amz-target`"} instead of being served/authorised.
4. Narrow the network policy with update_security_policy to a SourceVPCEs that does not admit the caller, or delete it entirely, and repeat step 3: the response is the identical 400, so the enforcement change is unobservable.
