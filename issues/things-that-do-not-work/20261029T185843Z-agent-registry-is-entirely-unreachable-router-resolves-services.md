# Agent Registry is entirely unreachable: router resolves services by SigV4 signing name, so AgentRegistry and AgentRegistryControl both claim 'agent-registry' and every request is refused with a non-AWS 'AmbiguousService' code

> _Note: this issue was identified against the code base at commit `600bb9247975905af81e2aa2cda8a015f9396423`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDiscoverableRegistryRecords

## Description
Cause 1 of 1: the emulator's request router keys emulated services by their SigV4 signing name instead of by the endpoint the request was addressed to, so the two Agent Registry crates collide and NEITHER is reachable. Every single request signed for 'agent-registry' is rejected pre-dispatch.

AWS: Smithy, services/service-com-amazonaws-agentregistry-agentregistry/smithy-model/com-amazonaws-agentregistry-agentregistry.json — service AgentRegistry (sdkId 'Agent Registry', version 2025-12-01, restJson1, sigv4Name 'agent-registry', awsService.endpointPrefix 'agent-registry', arnNamespace 'agent-registry'); and services/service-com-amazonaws-agentregistrycontrol-agentregistrycontrol/... — service AgentRegistryControl (sdkId 'Agent Registry Control', restJson1, sigv4Name 'agent-registry', awsService.endpointPrefix 'agent-registry-control', arnNamespace 'agent-registry', cloudTrailEventSource 'agent-registry.amazonaws.com'). Sharing a sigv4 signing name across two services is normal and deliberate in AWS: the two services are distinguished by the ENDPOINT (agent-registry.<region>.amazonaws.com vs agent-registry-control.<region>.amazonaws.com) and by their disjoint HTTP routes, never by the signing name. On real AWS a SigV4-'agent-registry'-signed POST /registries/{registryId}/discoverable-records-list is dispatched to AgentRegistry.ListDiscoverableRegistryRecords and answered by that operation. For the three AgentRegistry operations the modeled errors are the service-common set — ResourceNotFoundException (errorKind client, httpError 404), AccessDeniedException (403), ValidationException (400, required members message + reason), UnauthorizedException, ThrottlingException, InternalServerException — and the recorded behavior the checks assert is: a well-formed but nonexistent registryId yields 404 ResourceNotFoundException with message 'Registry not found: <registryId>' (fixed text 'Registry not found: ', variable part the registryId value taken verbatim from the request); a registryId that violates RegistryIdentifier's pattern ^(arn:aws(-[^:]+)?:agent-registry:[a-z0-9-]+:[0-9]{12}:registry/)?[a-zA-Z0-9]{12,16}$ yields 400 ValidationException; and an unpermissioned caller naming the registry by ID or ARN yields 403 AccessDeniedException with the standard IAM no-allow message 'User: <caller principal ARN> is not authorized to perform: agent-registry:<OperationName> on resource: <canonical registry ARN> because no identity-based policy allows the agent-registry:<OperationName> action' (fixed text as quoted; the principal ARN comes from the signing credentials, the operation name from the dispatched operation, and the resource ARN is the registryId normalized to its canonical arn:aws:agent-registry:<region>:<account>:registry/<id> form regardless of whether the caller passed the ID or the ARN).

Emulator: no AgentRegistry operation is ever dispatched. Every call — including the fully-permissioned positive-control call that is the FIRST request each check makes — comes back as the error code 'AmbiguousService' with message '2 emulated services all claim requests for \'agent-registry\': agent-registry, agent-registry; the request is rejected rather than served by an arbitrary one'. 'AmbiguousService' is not a code in either Smithy model nor anywhere in AWS's error vocabulary, and the message's duplicated 'agent-registry, agent-registry' shows the router is listing the two crates' shared SIGNING NAME rather than their distinct endpoint prefixes, which is exactly why it cannot tell them apart. So instead of 404/ResourceNotFoundException + 'Registry not found: sim2realnotfnd1' the caller gets AmbiguousService; instead of 400/ValidationException for a malformed registryId it gets AmbiguousService; instead of 403/AccessDeniedException for an unpermissioned caller it gets AmbiguousService.

Why: Agent Registry (and, symmetrically, Agent Registry Control) is 100% unusable — not degraded, unreachable. An SDK client gets a ClientError whose code is not in the service's error set, so no client's error handling matches it: retry classification is wrong (an unmodeled code is treated as non-retryable generic failure rather than a client 400/403/404), not-found handling never fires, and IAM-denial handling never fires. Any caller that branches on ResourceNotFoundException to create-if-missing, or on AccessDeniedException to re-auth, silently takes its fallback path. Because the refusal happens before dispatch, it also masks the whole authorization and validation surface of these operations: ordering of shape validation vs authorization, ID-vs-ARN resource normalization in the denial message, and the per-entry not-found semantics of BatchGetDiscoverableRegistryRecord are all untested until the router can route.

Fix: the shared request router / service-resolution layer, not any Agent Registry handler. Resolve the target emulated service from the request's addressed endpoint (Host / endpointPrefix — 'agent-registry' vs 'agent-registry-control'), falling back to the HTTP method+URI route table of each candidate (the two services' restJson1 routes are disjoint: AgentRegistry owns POST /discoverable-records-batch, POST /registries/{registryId}/discoverable-records-list, POST /discoverable-records-search), and treat a shared sigv4Name as expected rather than as a conflict. The 'AmbiguousService' refusal path must not be reachable for two services that differ in endpointPrefix. This is the same router root cause already filed for other signing-name-colliding pairs — see open issues 20261022T110819Z-migrationhub-config-is-entirely-unreachable-router-resolves-by.md, 20261022T145747Z-connectcampaigns-is-entirely-unreachable-router-resolves-services-by.md and 20261029T174910Z-payment-cryptography-control-plane-is-entirely-unreachable-the.md — but none of those issues names agent-registry or carries these replay keys, so this pair is not covered by them.

Traces: agent-registry.list-discoverable-registry-records-unauthorized, agent-registry.search-discoverable-registry-records-unauthorized, agent-registry.batch-get-discoverable-registry-record-id-form-bypasses-authorization — all three fail on their first, fully-permissioned positive-control call.

## Evidence
Expected (AWS / recorded): ar.list_discoverable_registry_records(registryId='sim2realnotfnd1') -> HTTP 404, Error.Code 'ResourceNotFoundException', Error.Message 'Registry not found: sim2realnotfnd1' (fixed text 'Registry not found: ' + the registryId from the request). Malformed registryId 'bad id!' -> HTTP 400 'ValidationException'. Unpermissioned assumed-role caller -> HTTP 403 'AccessDeniedException', message 'User: <assumed-role principal ARN> is not authorized to perform: agent-registry:ListDiscoverableRegistryRecords on resource: <canonical registry ARN> because no identity-based policy allows the agent-registry:ListDiscoverableRegistryRecords action' (same message whether the registry is named by ID or ARN). Same shape for SearchDiscoverableRegistryRecords and BatchGetDiscoverableRegistryRecord.

Actual (emulator): every call, including the first fully-permissioned one, is refused pre-dispatch with Error.Code 'AmbiguousService' and Error.Message '2 emulated services all claim requests for \'agent-registry\': agent-registry, agent-registry; the request is rejected rather than served by an arbitrary one'.

Model evidence for the collision: AgentRegistry sigv4Name='agent-registry', endpointPrefix='agent-registry'; AgentRegistryControl sigv4Name='agent-registry', endpointPrefix='agent-registry-control'. Both are in the bootstrapped set (service-com-amazonaws-agentregistry-agentregistry, service-com-amazonaws-agentregistrycontrol-agentregistrycontrol), so both stood up and then collided at routing time. ## Steps to Reproduce
1. Build and boot the emulator with both Agent Registry crates present (service-com-amazonaws-agentregistry-agentregistry and service-com-amazonaws-agentregistrycontrol-agentregistrycontrol); both are bootstrapped on mainline, so the default build reproduces it.
2. Create a botocore client for sdkId 'Agent Registry' against the emulator endpoint, with fully-permissioned credentials.
3. Call list_discoverable_registry_records(registryId='sim2realnotfnd1') — a well-formed RegistryIdentifier (matches ^[a-zA-Z0-9]{12,16}$) that does not exist.
4. Observe the ClientError: Code 'AmbiguousService', message '2 emulated services all claim requests for ...agent-registry...: agent-registry, agent-registry; the request is rejected rather than served by an arbitrary one'. Expected: HTTP 404, Code 'ResourceNotFoundException', Message 'Registry not found: sim2realnotfnd1'.
5. Repeat with search_discoverable_registry_records(searchQuery='smoke-test', registryIds=['sim2realnotfnd1']) and batch_get_discoverable_registry_record(entries=[{'registryId':'sim2realnotfnd1','recordIds':['sim2real0001']}]) — identical AmbiguousService refusal, so no AgentRegistry operation is reachable at all.
6. Also call list_discoverable_registry_records(registryId='bad id!') (pattern violation, expect 400 ValidationException) and the same calls through an assumed IAM role with no permissions policy (expect 403 AccessDeniedException with the no-allow message) — both are refused with AmbiguousService before any validation or authorization runs.
7. Confirm the cause: both services declare sigv4Name 'agent-registry' while their endpointPrefixes differ ('agent-registry' vs 'agent-registry-control'); routing on the endpoint/route table instead of the signing name makes both reachable.
