# dynamodb: the CreateBackup -> RestoreTableFromBackup name-collision flow never converges, so TableAlreadyExistsException is never reached (check killed at the 60 s budget)

> _Note: this issue was identified against the code base at commit `d1f488ff5b87ae19d202e4a045e598018e7d1458`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RestoreTableFromBackup

## Description
One cause.

Cause 1 of 1: the backup/restore control-plane sequence (CreateTable -> CreateBackup -> RestoreTableFromBackup -> DescribeTable/TagResource -> colliding RestoreTableFromBackup) never settles inside the replay budget, so RestoreTableFromBackup's name-collision rejection is never exercised. Failing check: dynamodb.restore-backup-name-conflict.

AWS: the graded behavior is RestoreTableFromBackup's overly-permissive boundary. Smithy (com.amazonaws.dynamodb#RestoreTableFromBackup): input TargetTableName (TableName, required, @length 3..255, @pattern ^[a-zA-Z0-9_.-]+$) + BackupArn (required, @length 37..1024); output TableDescription; modeled errors BackupInUseException, BackupNotFoundException, LimitExceededException, TableAlreadyExistsException, TableInUseException (all HTTP 400), InvalidEndpointException (421), InternalServerError (500). A restore whose TargetTableName names a table that already exists and is settled (ACTIVE) must be refused with HTTP 400, error code TableAlreadyExistsException, message of the form 'Table already exists: <TargetTableName>' - the fixed text is 'Table already exists: ' and the only variable part is the TargetTableName taken from the request - and the colliding table must be provably unaffected (same TableArn, same CreationDateTime, still ACTIVE, its own items intact and no item from the backup leaked into it). The recording also establishes the positive control on the way there: the same backup restored to a free name succeeds and the restored table carries the source items (ConsistentRead GetItem on the seeded key returns it), and the whole sequence completes inside the harness's 60 s per-check budget. Supporting modeled facts the sequence depends on: DescribeContinuousBackups reports ContinuousBackupsStatus = ENABLED ('Continuous backups are ENABLED on all tables at table creation'), and CreateBackup is asynchronous so its backup reaches BackupStatus = AVAILABLE ('the backup is created asynchronously').

Emulator: the check never finishes. The replay verdict is a mismatch whose entire detail is 'Check timed out after 60.0s' - the harness killed the check on its 60 s budget, so NO assertion past the polling/waiting stage was ever evaluated: neither the positive control (restore to a free name carries the source data), nor the collision rejection (code/message), nor the effect-absent assertions on the colliding table. The sequence has exactly four blocking waits - DescribeContinuousBackups polled until ENABLED, DescribeBackup polled until AVAILABLE, and three SDK 'table_exists' waiters (DescribeTable polled until TableStatus == ACTIVE) for the two source tables and the restored table - and one of them does not reach its terminal state fast enough for the sequence to complete, so the client is left waiting instead of being answered. Hypothesis (neither the model nor the recording states this, so it is offered only as a starting point for the fixer, not as the requirement): the emulator keeps a created/restored table in CREATING for a fixed 500 ms span (state.rs STATUS_TRANSITION) which is short enough that nothing observes the transition usefully but long enough that it always lands AFTER the SDK waiter's immediate first DescribeTable probe, so every one of the three table_exists waits costs the client a full waiter polling interval and three of them alone exhaust the budget; the per-call handlers themselves (restore_table_from_backup.rs, describe_continuous_backups.rs, create_backup.rs) do compute the right terminal values.

Why: a client driving the documented backup-and-restore flow with the standard SDK waiters hangs instead of completing. Every downstream behavior of this flow is unobservable: a caller cannot confirm that restoring onto an occupied name is refused (it never gets an answer), so an application that relies on that refusal as its 'name already taken' signal - rather than on a prior DescribeTable - stalls, and an operator cannot tell a slow restore apart from one that will never finish. Because the collision path is never reached, nothing proves the emulator does not instead clobber or partially overwrite the existing table; the guarantee the check exists to grade is simply ungraded.

Fix: the DynamoDB backup/restore control-plane path and the table-status clock it shares - the RestoreTableFromBackup handler and the CREATING-span/status derivation in the crate's table state - must let this sequence converge: each create/restore must reach the status an SDK waiter accepts within the time the recorded run met, and once it does, the collision branch must answer 400 TableAlreadyExistsException with the message template above and leave the existing table's identity, status and items untouched. Note: the auto-filed scaffold-stub issues 20261025T123639Z-dynamodb-restoretablefrombackup-stub.md (fixed) and 20261025T024002Z-dynamodb-createbackup-stub.md (open) cover only the existence of the two handlers; this non-convergence of the combined flow is not covered by either, nor by 20261025T084647Z-dynamodb-describeendpoints-returns-an-address-that-names-neither.md, which records CreateBackup's concurrency/uniqueness requirement instead. File and line citations for the handlers involved: services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/restore_table_from_backup.rs (handle, collision branch at the TableAlreadyExistsException construction), services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state.rs (STATUS_TRANSITION, Table::status).

Traces: dynamodb.restore-backup-name-conflict (mismatch; 'Check timed out after 60.0s').

## Evidence
Expected (recorded AWS behavior): the whole sequence completes within the 60 s per-check budget, and the final call ddb.restore_table_from_backup(TargetTableName=<an existing ACTIVE table>, BackupArn=<AVAILABLE backup of another table>) is refused with HTTP 400, Error.Code = 'TableAlreadyExistsException' and Error.Message = 'Table already exists: <TargetTableName>' (fixed text 'Table already exists: ' plus the TargetTableName from the request); the positive control restore to an unused name succeeds and ConsistentRead GetItem on the restored table returns the seeded item (v = the source value); afterwards the collision target still reports TableStatus ACTIVE with an unchanged TableArn and CreationDateTime, its own item is intact and the backup's item is absent from it.

Actual (emulator): the check is terminated by the harness with the single detail 'Check timed out after 60.0s'. No response assertion was reached - not the positive-control GetItem, not the collision error code or message, not the effect-absent assertions. The blocking stage is one of the sequence's polling waits (DescribeContinuousBackups until ContinuousBackupsStatus == ENABLED, DescribeBackup until BackupStatus == AVAILABLE, or any of the three SDK table_exists waits on DescribeTable until TableStatus == ACTIVE): the client keeps polling instead of observing the terminal state, and the remainder of the flow never runs. No error code and no HTTP status is produced for the collision call at all, where AWS produces 400 / TableAlreadyExistsException.

## Steps to Reproduce
1. CreateTable table A (single HASH key 'pk' of type S, BillingMode PAY_PER_REQUEST, with one tag) and wait for TableStatus ACTIVE; PutItem {pk: 'seed', v: 'seed-data'}.
2. CreateTable table B the same way and wait for ACTIVE; PutItem {pk: 'sentinel', v: 'untouched'}.
3. Poll DescribeContinuousBackups(TableName=A) until ContinuousBackupsDescription.ContinuousBackupsStatus == 'ENABLED'.
4. CreateBackup(TableName=A, BackupName=<name>) and poll DescribeBackup(BackupArn=...) until BackupDetails.BackupStatus == 'AVAILABLE'.
5. RestoreTableFromBackup(TargetTableName=<unused name>, BackupArn=...) and wait for that table to be ACTIVE; TagResource on its TableArn; GetItem(pk='seed', ConsistentRead=True) and confirm it carries 'seed-data' (positive control).
6. RestoreTableFromBackup(TargetTableName=B, BackupArn=...) and observe the error code and message.
7. Observe instead that the run never gets to step 6: the sequence is still inside one of the waits of steps 1-5 when the 60 s budget expires ('Check timed out after 60.0s'), so the TableAlreadyExistsException refusal and the effect-absent assertions on B are never exercised.
8. Or replay the check id in trace_ids: dynamodb.restore-backup-name-conflict.
