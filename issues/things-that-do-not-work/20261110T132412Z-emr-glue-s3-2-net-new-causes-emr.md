# emr__glue__s3: 2 net-new causes — EMR clusters never execute their steps, auto-terminate or upload logs to the log URI, and a completed Glue job run publishes no Glue Job State Change event to an EventBridge rule's SQS target

## Operation
RunJobFlow

## Description
Two (2) net-new root causes behind four failing checks in this service group. Each is independent and BOTH must be closed before this issue is submitted. None of the four checks was marked ALREADY FILED or OWNED by the replay report, so no open issue carries their current replay keys; all four now fail as check-level TIMEOUTS because the asynchronous progression they poll for never happens. Where an open issue describes the same area it is named inside the cause.

=== Cause 1 of 2: an EMR cluster accepts its steps but never runs them, never auto-terminates, and never writes logs under its LogUri ===
AWS: recorded behavior only for the asynchronous progression (the Smithy model fixes only the shapes: RunJobFlow(Name, Instances, Steps, ServiceRole, JobFlowRole, LogUri) -> JobFlowId; DescribeCluster -> Cluster{Status{State: ClusterState}}; ListSteps -> Steps{Status}). Recorded behavior: a cluster submitted with Instances.KeepJobFlowAliveWhenNoSteps=false (the CLI's --auto-terminate) runs each submitted step and then settles DescribeCluster.Cluster.Status.State == "TERMINATED" (or TERMINATED_WITH_ERRORS when a step fails); the side effects of the step are real — a CUSTOM_JAR/command-runner.jar step that writes an object to S3 leaves that object readable by HeadObject with ContentLength > 0 — and the cluster's logs are uploaded under <LogUri>/<cluster-id>/, so a ListObjectsV2 on that prefix returns objects, subject to the instance profile's s3:PutObject permission on the prefix.
Emulator: the cluster is created and its steps are accepted, but the state never leaves its initial/running state, so every poll for a terminal state runs to the check deadline; no step side effect ever lands in S3 and no log object ever appears under the log prefix. The four observable symptoms: "Check timed out after 60.0s" while polling DescribeCluster for TERMINATED after an --auto-terminate create, and "Check timed out after 600.0s" in the log-permission check whose positive-control cluster never terminates and never gets its logs to S3.
Why: every EMR workflow is unobservable end-to-end — a client that submits a step and waits on DescribeCluster for a terminal state hangs forever, the data its step was supposed to write never exists, and the log-based permission boundary cannot be distinguished from the absence of logs altogether (a negative assertion "the denied cluster got no logs" passes vacuously because NO cluster gets logs).
Related but NOT covering: 20261108T104909Z-emr-glue-s3-2-net-new-causes-cluster.md, 20261105T074335Z-emr-glue-s3-emr-cluster-steps-never-reach.md and 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md describe this area, but the report left these checks unowned, so none carries their current replay keys.
Fix: the EMR cluster/step execution and lifecycle in the RunJobFlow (and AddJobFlowSteps) handler and the cluster state it drives — steps must execute with their real S3 side effects, an auto-terminating cluster must settle TERMINATED, and the cluster's log upload must write under <LogUri>/<cluster-id>/ through the instance profile's S3 permissions.
Traces: emr__glue__s3.cli-emr-create-cluster-submit-step-s3-workflow, emr__glue__s3.emr-cluster-missing-s3-logs-permission-negative.

=== Cause 2 of 2: a Glue job run that completes publishes no "Glue Job State Change" event, so an EventBridge rule's SQS target never receives it ===
AWS: recorded behavior only (EventBridge/Glue do not model the event payload in Smithy; Glue models StartJobRun -> JobRunId and GetJobRun -> JobRun{JobRunState}). Recorded behavior: StartJobRun's run progresses to JobRunState == "SUCCEEDED", and Glue publishes an event onto the default event bus with source == "aws.glue", detail-type == "Glue Job State Change" and a detail object carrying at least jobName (the job started), state ("SUCCEEDED") and jobRunId (the id returned by StartJobRun). A rule whose EventPattern matches that source/detail-type/detail and whose SQS target queue policy allows events.amazonaws.com sqs:SendMessage receives exactly that event as a message body; a sibling queue with no such resource policy receives nothing and holds 0 messages.
Emulator: the Glue job run never reaches SUCCEEDED and/or no Glue Job State Change event is ever delivered, so the poll for the matching message on the permissioned queue never converges and both checks end as "Check timed out after 60.0s" before their first assertion. The negative half (the unpermissioned queue must stay empty) is never reached, and would in any case be vacuous.
Why: a client driving Glue from events — an EventBridge rule fanning job completions out to a queue, a Lambda, or a Step Functions state machine — never fires at all, and a rule's permission boundary cannot be validated because no event flows on either side of it.
Related but NOT covering: 20261029T175551Z-glue-job-runs-reached-through-the-emr-glue.md and 20261109T085123Z-athena-glue-s3-3-net-new-causes-glue.md touch Glue job runs and job-state events; the report left these checks unowned, so neither carries their current replay keys.
Fix: the Glue job-run execution path (the run must reach a terminal JobRunState) and the event publication hooked to that transition — Glue must put a "Glue Job State Change" event with source aws.glue and detail{jobName, state, jobRunId} onto the default bus, and the EventBridge rule-matching/target-delivery path must deliver it to the SQS target whose queue policy grants events.amazonaws.com.
Traces: emr__glue__s3.eventbridge-glue-job-state-change-triggers-rule-positive, emr__glue__s3.eventbridge-rule-missing-target-permission-negative.
