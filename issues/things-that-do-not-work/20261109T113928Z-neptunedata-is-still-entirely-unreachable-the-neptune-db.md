# neptunedata is still entirely unreachable: the Neptune DB cluster publishes a *.neptune.amazonaws.com Endpoint the emulator does not serve, so no data-plane client can be addressed

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetEngineStatus

## Description
THIS ISSUE HAS 1 CAUSE — it must be closed before submitting.

Cause 1 of 1: the Neptune control plane announces a DB cluster connection endpoint on a host the emulator does not serve, so every neptunedata data-plane call is unreachable and all 19 neptunedata behavioral checks die before a single neptunedata request is issued. Failing check ids for this cause: all 19 ids listed in trace_ids (representatives: neptunedata.engine-status-reports-query-language-endpoints, neptunedata.opencypher-create-and-match-roundtrip, neptunedata.gremlin-addv-and-traverse-roundtrip).

AWS: neptunedata has no regional, account-wide front door that a client can be pointed at generically — every one of its operations is addressed at the owning cluster's own connection endpoint on the Neptune engine port. Smithy (services/service-com-amazonaws-neptunedata-amazonneptunedataplane): service AmazonNeptuneDataplane, version 2023-08-01, sdkId `neptunedata`, protocol restJson1, sigv4Name/arnNamespace `neptune-db`, 43 bound operations; its endpoint rule set only ever resolves host names (`https://neptune-db.{Region}.{PartitionResult#dnsSuffix}` and the fips/dualstack variants), never a host:port pair. Smithy (services/service-com-amazonaws-neptune-amazonrdsv19): com.amazonaws.neptune#DBCluster member `Endpoint` is documented as "Specifies the connection endpoint for the primary instance of the DB cluster", i.e. a bare host name with no scheme and no port, with the port reported separately in the sibling member `Port` (8182 for the neptune engine). The general requirement that follows: `Endpoint` is a host name, and `https://<Endpoint>:<Port>` must be an address that actually answers the restJson1 neptunedata API of that cluster. For an emulator, "actually answers" means an address the emulator is reachable on — its own host and port, or a per-resource listener it owns.

Emulator: `Endpoint` is now port-less and DNS-shaped, but it names a real-AWS hostname that the emulator does not and cannot serve. Observed published value, general form: `<cluster-identifier>.cluster-<12-hex-resource-id>.<region>.neptune.amazonaws.com`, with `Port` 8182. Each check reads DBCluster.Endpoint and DBCluster.Port and builds its client as `ctx.client("neptunedata", endpoint_url=ctx.endpoint_url(f"{endpoint}:{cluster['Port']}"))`; all 19 are then refused identically by the harness with `simparity.published.PublishedUrlRejected: endpoint_url was given https://<cluster-id>.cluster-<resource-id>.<region>.neptune.amazonaws.com:8182 (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener` (raised from context.py `endpoint_route` -> `_published_target`). The cluster identifier and the 12-hex resource id vary per check and the emulator port varies per run; neither is part of the requirement — the requirement is that the announced host be one the emulator answers on. Zero neptunedata requests reach the emulator, so not one of the 43 modelled operations is exercised.

This is a NEW, distinct state of the same reachability surface as open issue 20261104T102956Z-neptunedata-is-entirely-unreachable-the-neptune-db-cluster.md, which is still open and describes the PREVIOUS form of the defect: there `Endpoint` resolved to an address that already pinned the emulator's port, so appending `:8182` produced a URL with two ports and the harness refused it as malformed. That half is gone — `Endpoint` is now port-less and `Port` is 8182, which is the shape the model asks for. What remains, and what this issue reports, is the other half: the port-less host that is now published is a fabricated `*.neptune.amazonaws.com` name that resolves nowhere the emulator is listening, so the publish-side refusal is now "host is not one of the emulator's own hosts" instead of "not a http/https URL with a host". Also related but NOT the same defect: open issue 20261103T175309Z-neptune-db-cluster-and-cluster-snapshot-reports-omit.md covers other missing/inverted DBCluster members and says nothing about the reachability of `Endpoint`.

Why: `Endpoint` is the ONLY way a client finds a Neptune cluster, so a client doing exactly the documented thing — read `Endpoint`, read `Port`, connect to `Endpoint:Port` — is sent to an address that does not exist in the emulator's world. Every Gremlin query, every openCypher query, every explain/profile, every bulk-loader job, every statistics and summary call, every ML endpoint call and fast reset is unusable, and a client that hardcodes a workaround against the emulator will not work against AWS. Because the emulator announces an address other than the one it is reached on, the whole 43-operation neptunedata surface is ungradable (0/19) and no fidelity statement about neptunedata can be made until this is fixed.

Fix: the Neptune control plane's DBCluster projection — the `Endpoint` (and, for consistency, `ReaderEndpoint` and any custom cluster endpoint) value written to cluster state and rendered by the CreateDBCluster / DescribeDBClusters / ModifyDBCluster handlers — must publish a host the emulator actually serves, and the neptunedata data plane must be served at `<that host>:<Port>` so that `https://<Endpoint>:<Port>` routes to this crate's restJson1 front door for that cluster. Keep the port-less `Endpoint` + `Port`=8182 split that is already correct; what must change is the host's provenance (the emulator's own host / a per-resource listener it owns) and the existence of a data-plane route bound to it that dispatches to the owning cluster's graph state.

Traces: the 19 failing checks in trace_ids, each refused at client construction with the PublishedUrlRejected message quoted above.
