# IoT SiteWise: 7 divergences — alias ingestion never creates a time series, AssociateAssets/CreateGateway/TagResource conflicts misclassified, DeleteAsset ignores child associations, UpdateAssetModel and ExecuteQuery refuse with NotImplemented

> _Note: this issue was identified against the code base at commit `9979b14c0e509985792db6dac0171a1eff5d6a10`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateAssets

## Description
Seven independent root causes in the iotsitewise emulator, each grounded in failing behavioral checks of this suite and each net-new relative to the already-filed issues. All seven must be closed before this issue is resolved.

=== Cause 1 of 7: AssociateAssets answers a duplicate/raced association with ResourceAlreadyExistsException ===
AWS: Smithy: AssociateAssets, POST /assets/{assetId}/associate (host prefix api.), required members assetId/hierarchyId/childAssetId; modeled errors ConflictingOperationException (httpError 409), InvalidRequestException (httpError 400), LimitExceededException (410), ResourceAlreadyExistsException (409), ResourceNotFoundException (404), ThrottlingException (429). Recorded behavior: for N simultaneous, identical AssociateAssets calls on one (assetId, hierarchyId, childAssetId) triple exactly one call wins and every other racer is refused — with ConflictingOperationException (409) while the association operation is still in progress (the in-progress-association lock), and with InvalidRequestException (400) once the association is already established. In both recordings the child ends up associated exactly once.
Emulator: every loser is refused with ResourceAlreadyExistsException. Observed: 5 of 5 losers returned 'ResourceAlreadyExistsException' where ConflictingOperationException was recorded, and 5 of 6 racers returned 'ResourceAlreadyExistsException' where InvalidRequestException was recorded (one SUCCESS).
Why: the three classes mean different things to the caller. ConflictingOperationException (409) says "the same association is mid-flight, retry"; InvalidRequestException (400) says "this association already exists, stop"; ResourceAlreadyExistsException is used by this service for a distinct resource-identity collision. A client's `except ConflictingOperationException: retry` never fires, so a benign concurrent association is surfaced as a terminal resource-collision, and conversely an already-established association is not reported as a terminal request error.
Fix: the duplicate/in-flight association check in the AssociateAssets handler and its error mapping, plus the hierarchy-association state that records whether an association is in progress or already established.
Traces: iotsitewise.associate-assets-concurrent-duplicate-race, iotsitewise.concurrent-associate-assets-race.

=== Cause 2 of 7: DeleteAsset deletes a parent asset that still has an associated child ===
AWS: Smithy: DeleteAsset, DELETE /assets/{assetId}, success code 202 with required assetStatus; modeled errors ConflictingOperationException (409), InvalidRequestException (httpError 400), ResourceNotFoundException (404), ThrottlingException (429). Recorded behavior: DeleteAsset on a parent asset that still has a child associated under one of its hierarchies is refused with InvalidRequestException (400) and the parent survives; after DisassociateAssets removes the child, the identical DeleteAsset succeeds (202, state DELETING).
Emulator: the call is accepted — HTTP 202 with {assetId, assetStatus: {state: 'DELETING'}} — i.e. the hierarchy-dependency precondition is never evaluated.
Why: the delete is destructive and unrecoverable. A client relying on AWS refusing a parent delete while children are attached loses the parent asset and is left with children pointing at a hierarchy whose parent no longer exists; there is no error for the caller to react to.
Fix: the dependency (child-association) precondition check in the DeleteAsset handler and its InvalidRequestException mapping, reading the hierarchy-association state.
Traces: iotsitewise.delete-asset-conflict-when-hierarchy-associated-rejected.

=== Cause 3 of 7: CreateGateway with an already-registered coreDeviceThingName returns ResourceAlreadyExistsException ===
AWS: Smithy: CreateGateway, POST /20200301/gateways, success code 201; modeled errors InternalFailureException (500), InvalidRequestException (httpError 400), LimitExceededException (410), ResourceAlreadyExistsException (409), ThrottlingException (429). Recorded behavior: CreateGateway whose gatewayPlatform names a coreDeviceThingName already registered to another gateway is refused with InvalidRequestException; the pre-existing gateway is untouched, a different thing name still succeeds, and once the conflicting gateway is deleted the identical CreateGateway call succeeds and the freed coreDeviceThingName is readable on the new gateway.
Emulator: refuses with ResourceAlreadyExistsException (recorded message example: "The gateway <id> already exists.").
Why: the emulator reports the collision as a gateway-identity collision rather than as an invalid request about the core-device thing name, so `except InvalidRequestException` handlers never match; worse, the message names a gateway id the caller never supplied instead of the colliding coreDeviceThingName, pointing diagnosis at the wrong dimension.
Fix: the coreDeviceThingName uniqueness check in the CreateGateway handler and its error mapping (it must not reuse the gateway-identity already-exists path).
Traces: iotsitewise.gateway-duplicate-core-device-rejected.

=== Cause 4 of 7: TagResource at the 50-tag resource limit returns TooManyTagsException instead of LimitExceededException ===
AWS: Smithy: TagResource, POST /tags, TagResourceRequest.tags required with @length min 1 / max 50; modeled errors include BOTH LimitExceededException (httpError 410) and TooManyTagsException (httpError 400). Recorded behavior: when a resource already carries the maximum of 50 tags, a further TagResource adding one NEW key (a request that itself violates no @length constraint — it carries a single tag) is refused with LimitExceededException, the resource keeps exactly 50 tags and the new key is not added; freeing a slot lets a new tag land.
Emulator: refuses with TooManyTagsException.
Why: these are two different modeled errors with different HTTP statuses (410 vs 400) and different SDK exception classes. A client that catches LimitExceededException to trigger its "prune a tag and retry" path never sees it, and the 400 reads as a malformed request rather than an account/resource limit. Note this is NOT the request-shape violation already filed as Cause 5 of 20261022T070208Z-iotsitewise-iot-sitewise-control-plane-6-divergences-disassociateassets-answers.md (a single TagResource carrying 51 tags, where the @length max 50 on the request is violated); here the request is well-formed and the limit is the resource's accumulated tag count, which is a separate check and a separate code path.
Fix: the resource-level tag-count limit check in the TagResource handler (count existing tags on the target resource) and its LimitExceededException mapping.
Traces: iotsitewise.tag-resource-too-many-tags-rejected.

=== Cause 5 of 7: BatchPutAssetPropertyValue with propertyAlias never creates a disassociated time series ===
AWS: Smithy: BatchPutAssetPropertyValue, POST /properties (host prefix data.), entries may address a property by propertyAlias instead of assetId/propertyId. DescribeTimeSeries (GET /timeseries/describe, query member alias) returns required timeSeriesId/dataType/timeSeriesCreationDate/timeSeriesLastUpdateDate/timeSeriesArn, and ListTimeSeries (GET /timeseries, query members aliasPrefix and timeSeriesType) returns required TimeSeriesSummaries; both model ResourceNotFoundException (404). Recorded behavior: alias-only ingestion implicitly creates a DISASSOCIATED (orphan) time series, which then becomes visible on DescribeTimeSeries(alias=...) and appears in ListTimeSeries(aliasPrefix=..., timeSeriesType='DISASSOCIATED'); from there it can be associated to an asset property, deleted by alias, and after deletion DescribeTimeSeries answers ResourceNotFoundException.
Emulator: the time series is never created. DescribeTimeSeries(alias=...) keeps answering ResourceNotFoundException indefinitely, so every check that polls for the orphan to appear hangs until the 60s harness timeout ("Check timed out after 60.0s") — none of the downstream behavior (ListTimeSeries filtering, AssociateTimeSeriesToAssetProperty, DeleteTimeSeries argument validation, alias/direct history merge) is reachable at all.
Why: the whole alias-addressed ingestion model is unusable. Industrial clients ingest by property alias before any asset exists and then bind the alias to an asset property; against this emulator that flow never progresses past the first read, and a caller polling for the time series to appear blocks forever instead of succeeding.
Fix: the BatchPutAssetPropertyValue handler must register a disassociated time series in the time-series state when an entry carries propertyAlias (allocating timeSeriesId/ARN/dataType/creation+update timestamps), and the DescribeTimeSeries / ListTimeSeries handlers must read it, including the aliasPrefix and timeSeriesType='DISASSOCIATED' filters.
Traces: iotsitewise.associate-time-series-to-asset-property-lifecycle, iotsitewise.list-time-series-and-delete-time-series-lifecycle, iotsitewise.time-series-alias-and-direct-ingestion-merge-into-one-history, iotsitewise.delete-time-series-missing-identifier-rejected.

=== Cause 6 of 7: UpdateAssetModel refuses with NotImplemented, so the ETag precondition is never enforced ===
AWS: Smithy: UpdateAssetModel, PUT /asset-models/{assetModelId}, success code 202 with required assetModelStatus; ifMatch bound to httpHeader If-Match (ETag, pattern ^[\w-]{43}$), matchForVersionType bound to httpHeader Match-For-Version-Type; modeled errors include PreconditionFailedException (httpError 412) and ConflictingOperationException (409). Recorded behavior: UpdateAssetModel with the current ETag succeeds and advances the ETag; the same call replayed with the now-stale ETag is refused 412 PreconditionFailedException, the rejected update does not take effect (name and ETag both unchanged) and the retry against the current ETag succeeds. For two concurrent updates sharing one stale ETag, exactly one wins (the other gets PreconditionFailedException or ConflictingOperationException) and the model carries the winner's name, never a merge. Recorded message example: "Provided If-Match value does not match the current latest version ETag."
Emulator: every UpdateAssetModel call returns the scaffold refusal — error code `NotImplemented`, message "operation UpdateAssetModel is scaffolded but not implemented in this emulator" — so neither the positive control nor the precondition path exists. Observed: "expected PreconditionFailedException, got NotImplemented" and both concurrency racers returning ('error', 'NotImplemented').
Why: an asset model can never be renamed or re-shaped, and because `NotImplemented` is not in the operation's modeled error set no generated SDK exception class matches it — both `except PreconditionFailedException` and `except ConflictingOperationException` miss, and lost-update protection for asset models is entirely absent.
Fix: implement the UpdateAssetModel handler (services/service-com-amazonaws-iotsitewise-awsiotsitewise/src/ops/update_asset_model.rs) including If-Match / Match-For-Version-Type evaluation against the asset-model state's ETag and 412 PreconditionFailedException serialization. Note: the suite auto-filed a scaffold-stub issue naming this operation and file against the check iotsitewise.update-asset-model-precondition-etag-mismatch-rejected; this cause is the SAME root cause, recorded here because the two checks below are not carried by that issue's replay keys — close them together.
Traces: iotsitewise.update-asset-model-etag-precondition-mismatch-rejected, iotsitewise.concurrent-asset-model-updates-etag-race.

=== Cause 7 of 7: ExecuteQuery refuses with NotImplemented, so malformed SQL is not rejected with InvalidRequestException ===
AWS: Smithy: ExecuteQuery, POST /queries/execution (host prefix data.), queryStatement required (@length 1..10000, sensitive); modeled errors AccessDeniedException (403), InternalFailureException (500), InvalidRequestException (httpError 400), QueryTimeoutException (400), ServiceUnavailableException (503), ThrottlingException (429), ValidationException (400). Recorded behavior: a syntactically invalid queryStatement is refused with InvalidRequestException, while a syntactically valid statement against the same asset succeeds.
Emulator: returns error code `NotImplemented` ("operation ExecuteQuery is scaffolded but not implemented in this emulator") for the malformed statement — and therefore for every statement, valid or not.
Why: `NotImplemented` is not in the operation's modeled error set, so an SDK caller's `except InvalidRequestException` never fires and a malformed query is indistinguishable from a healthy query against an unsupported endpoint; the negative path cannot be distinguished from the positive one.
Fix: implement the ExecuteQuery handler (services/service-com-amazonaws-iotsitewise-awsiotsitewise/src/ops/execute_query.rs), including SQL parse/validation that raises the service's InvalidRequestException (400) on a syntax error. The open issue 20261022T070208Z-iotsitewise-executequery-stub.md covers the stub itself but does not carry this check's replay key or the rejection requirement; close them together.
Traces: iotsitewise.execute-query-malformed-sql-rejected.
