# EC2 DescribeInstanceTypes serves a synthesized instance-type catalog instead of the real one

> _Note: this issue was identified against the code base at commit `68ec0c9cae77cfbc133f0186a4c923306bef5402`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
Shared fault: DescribeInstanceTypes answers 200 but the instance-type catalog behind it is synthesized from formulas and defaults rather than carrying AWS's per-type facts, so for every family the same classes of divergence appear: whole members AWS always returns are absent, booleans are guessed, and the EBS/storage/memory/processor numbers are computed instead of looked up. This is one root cause with wide blast radius — the replay reports 112 net-new DescribeInstanceTypes divergence clusters across the ec2-catalog-describe-instance-types-* fixture family, every one of them this same catalog. Five representative causes are named below with their exact bindings; a fixer must re-replay the whole ec2-catalog-describe-instance-types-* family, not only these five, because the remaining clusters differ only in which instance types the page covers.
AWS (applies to all five causes): Smithy: DescribeInstanceTypes returns InstanceTypes (instanceTypeSet) of InstanceTypeInfo. The recorded responses show, for every type, cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.networkCards, networkInfo.secondaryNetworkSupported, networkInfo.trafficMirroringSupport, phcSupport and rebootMigrationSupport present, plus networkInfo.bandwidthWeightings and networkInfo.connectionTrackingConfiguration where the family supports them, and per-type values for ebsInfo.attachmentLimitType, ebsInfo.ebsOptimizedSupport, ebsInfo.maximumEbsAttachments, ebsInfo.ebsOptimizedInfo.*, instanceStorageInfo.*, memoryInfo.sizeInMiB, processorInfo.sustainedClockSpeedInGhz/supportedFeatures, placementGroupInfo.supportedStrategies, supportedRootDeviceTypes, vCpuInfo.validCores, autoRecoverySupported and dedicatedHostsSupported. Values are per instance type, never derived from the type's size.
Emulator (applies to all five): the newer members are omitted entirely; the EBS throughput/IOPS/bandwidth figures, instance-store disk counts and sizes, memory size, clock speed and attachment limits come out as scaled-by-size approximations; and the booleans (autoRecoverySupported, dedicatedHostsSupported, ebsOptimizedSupport, attachmentLimitType) are a single default rather than per-type facts.
Why: callers that size instances from this catalog — schedulers, cost/capacity planners, Terraform/CDK instance selection, anything filtering on ena-srd, EFA, network cards or EBS limits — get answers that are wrong in both directions, and code reading a member AWS always returns gets a null.
Fix: the DescribeInstanceTypes handler's catalog data source (the static instance-type table) and the InstanceTypeInfo serializer, which has no slot for the newer members.
