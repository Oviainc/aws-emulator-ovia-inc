# pca-connector-scep: 7 net-new causes — CreateConnector admits an absent/non-ACTIVE CA, FAILED provisioning is unreachable, not-found and pattern messages are re-worded, TagResource's tag ceiling uses the wrong error class, and the SCEP data plane is unserved

> _Note: this issue was identified against the code base at commit `ff83c0933c8ed1531136a633c3dbb3195f533006`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConnector

## Description
Behavioral replay of suite simparity-behavioral-aws-v1 against the pca-connector-scep emulator failed 10 of 21 checks; one (untag-resource-removes-tag) is already filed as an unimplemented-stub issue and is excluded here. The remaining nine failures cluster into 7 distinct root causes, all in pca-connector-scep. A fixer must close all 7 before submitting.

Cause 1 of 7: CreateConnector admits a CertificateAuthorityArn that names no certificate authority.
  AWS: 404 ResourceNotFoundException. Message is "CertificateAuthorityArn was not found: <caArn>." — fixed text "CertificateAuthorityArn was not found: " plus a terminating ".", with the CA ARN taken verbatim from the request; ResourceId = that ARN, ResourceType = the input member name "CertificateAuthorityArn". No connector is created (ListConnectors shows none for that CA). Smithy: CreateConnector (POST /connectors, success code 202) models ResourceNotFoundException (errorKind=client, httpError=404; required Message, ResourceId, ResourceType); CreateConnectorRequest.CertificateAuthorityArn is required with @length 5..200 and @pattern ^arn:aws(-[a-z]+)*:acm-pca:...$ — the model constrains only ARN syntax, so the existence check itself is recorded behavior only.
  Emulator: HTTP 202 with a ConnectorArn body for a well-formed but nonexistent CA ARN; the connector is registered.
  Why: a stale or typo'd CA ARN silently "succeeds", so a client proceeds to mint challenges against a connector that could never work on AWS, and its error branch is untestable.
  Fix: CreateConnector's handler/validation — resolve CertificateAuthorityArn against acm-pca state before admitting the connector, and raise the modeled 404 naming the input member as ResourceType.
  Traces: pca-connector-scep.create-connector-ca-not-found-rejected. Related, and NOT a substitute: open issue 20261029T190804Z-pca-connector-scep-missing-resource-handling-returns-the-wrong-status-class.md (its cause 5) describes the same defect from a wire fixture step but carries no replay key for this behavioral check; fixed issue 20261024T020831Z-pca-connector-scep-createconnector-validation.md claimed to make CreateConnector report a nonexistent CA, and the call is still accepted (a success, not a refusal, so this is not a refusal regression).

Cause 2 of 7: CreateConnector admits a CA that exists but is not ACTIVE.
  AWS: 400 ValidationException with Message "Validation error detected: Resource(s) are not active: <caArn>." — fixed text "Validation error detected: Resource(s) are not active: " plus a terminating ".", with the CA ARN from the request. The precondition is enforced synchronously at request time (a CA still in PENDING_CERTIFICATE), no connector resource is left behind, and the identical call succeeds once that same CA reaches ACTIVE. Smithy: ValidationException is modeled on CreateConnector (errorKind=client, httpError=400, required Message, optional Reason); the active-state precondition and its message are recorded behavior only.
  Emulator: 202 with a ConnectorArn for a CA in PENDING_CERTIFICATE, and the connector is subsequently listed by ListConnectors.
  Why: callers that rely on create-time rejection to detect an unfinished CA get a connector handle that AWS would never have issued, and the "wait for the CA, then create" workflow cannot be exercised.
  Fix: CreateConnector's handler/validation — read the referenced CA's Status from acm-pca state and refuse anything other than ACTIVE with the modeled 400.
  Traces: pca-connector-scep.connector-failed-transition-invalid-ca-state.

Cause 3 of 7: provisioning ignores the caller's acm-pca authorization, so a FAILED connector is unreachable and the non-ACTIVE guards on CreateChallenge / ListChallengeMetadata never fire.
  AWS: Connector for SCEP issues the connector's internal certificate with the caller's own acm-pca permissions. With an explicit IAM Deny on acm-pca:IssueCertificate scoped to the connector's CA, asynchronous provisioning settles the connector at Status FAILED with StatusReason PRIVATECA_ACCESS_DENIED (Smithy: ConnectorStatusReason enum = INTERNAL_FAILURE, PRIVATECA_ACCESS_DENIED, PRIVATECA_INVALID_STATE, PRIVATECA_RESOURCE_NOT_FOUND, VPC_ENDPOINT_RESOURCE_NOT_FOUND, VPC_ENDPOINT_DNS_ENTRIES_NOT_FOUND; Connector$StatusReason doc: "Information about why connector creation failed, if status is FAILED"). On such a connector, CreateChallenge is refused 400 ValidationException with Message "Validation error detected: Resource(s) are not active: <connectorArn>." and ListChallengeMetadata 400 ValidationException with Message "Validation error detected: Resource cannot be in state FAILED: <connectorArn>." — fixed sentence text in both cases, with the connector ARN from the request; those two message forms are recorded behavior only.
  Emulator: the connector settles at Status ACTIVE with StatusReason absent, so neither refusal is reachable at all.
  Why: a client cannot observe or test the service's documented failure mode; code that branches on FAILED/PRIVATECA_ACCESS_DENIED, or that expects challenge creation to be blocked on an unhealthy connector, is validated against behavior AWS never produces and will mint challenges against a connector AWS would have failed.
  Fix: CreateConnector's async settle path and the connector state machine (the pending-outcome/settle logic) must resolve CA usability and the caller's acm-pca authorization and admit the FAILED status with a reason; the CreateChallenge and ListChallengeMetadata handlers need the corresponding non-ACTIVE / FAILED guards.
  Traces: pca-connector-scep.create-challenge-on-inactive-connector-rejected. Related, and NOT a substitute: open issue 20261024T071525Z-pca-connector-scep-createconnector-wrong-behavior.md records that FAILED is unreachable for an absent CA/VPC endpoint; it carries no replay key for this check and does not state the two ValidationException messages required on the FAILED connector.

Cause 4 of 7: the ResourceNotFoundException message template is the emulator's own sentence, not AWS's.
  AWS: this error class reads "<ResourceType> was not found: <ResourceId>." — fixed text " was not found: " and a terminating ".", with the resource-type word ("Connector" or "Challenge", per the modeled ResourceType doc) and the ARN taken from the request/state. Observed on GetConnector after DeleteConnector ("Connector was not found: <connectorArn>."), and on GetChallengePassword / GetChallengeMetadata after DeleteChallenge or a cascading DeleteConnector ("Challenge was not found: <challengeArn>."). Smithy: ResourceNotFoundException is errorKind=client, httpError=404, required Message/ResourceId/ResourceType.
  Emulator: the 404 status and the error code are right, but Message is "<Type> <arn> could not be found" — the ARN is interpolated mid-sentence, the fixed words differ and the terminating period is missing.
  Why: any client or test that reads the not-found message (log scraping, snapshot assertions, branch logic keyed on text) sees wording AWS never emits, so code validated against the emulator diverges from the real service.
  Fix: the shared ResourceNotFoundException constructor/error renderer for this service, not the individual handlers.
  Traces: pca-connector-scep.delete-challenge-removes-password, pca-connector-scep.delete-connector-cascades-challenges, pca-connector-scep.delete-connector-twice-rejected. Related, and NOT a substitute: open issue 20261029T190804Z-pca-connector-scep-resourcenotfoundexception-message-text-and-resourcetype-diverge-from-aws.md describes this template from wire fixture steps; it carries no replay key for these three behavioral checks.

Cause 5 of 7: a pattern-constraint ValidationException message emits the @pattern with its ^ and $ anchors.
  AWS: for the path-bound ChallengeArn of GetChallengeMetadata, a value that fails the member's @pattern is refused 400 ValidationException with Message "1 validation error detected: Value '<value>' at 'challengeArn' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>" where <pattern> is the modeled regex with its leading ^ and trailing $ removed. Fixed text is the whole sentence scaffold; the variable parts are the rejected value from the request, the lowerCamel member name, and the anchor-stripped pattern. Smithy: GetChallengeMetadataRequest.ChallengeArn is an httpLabel, required, @length 5..200, @pattern ^arn:aws(-[a-z]+)*:pca-connector-scep:...:connector\/...\/challenge\/...$ — distinct from a plain Connector ARN, so passing a Connector-shaped ARN must be refused by input validation rather than treated as a lookup miss.
  Emulator: the correct code and sentence, but the pattern is emitted verbatim including the ^ prefix and $ suffix, so the message text diverges on every pattern-validated member.
  Why: a client that echoes the server-supplied pattern to a user, or compares it against the documented constraint, mismatches on every such refusal.
  Fix: the shared validation message builder — strip a leading ^ and trailing $ from the member's @pattern before interpolation.
  Traces: pca-connector-scep.challenge-arn-wrong-resource-type-rejected. Related, and NOT a substitute: open issue 20261029T190804Z-pca-connector-scep-pattern-constraint-validationexception-messages-use-the-wrong-form.md (its cause 4) names the same anchor leak for an httpLabel ARN from a wire fixture; it carries no replay key for this behavioral check.

Cause 6 of 7: TagResource over the per-resource tag ceiling is refused with the wrong error class.
  AWS: 400 with x-amzn-errortype BadRequestException and Message "The resultant tag set must not have more than 50 user tags." — entirely fixed text with nothing interpolated; the rejected batch is not partially applied (none of its keys appear in ListTagsForResource) and an in-limit TagResource on the same resource still succeeds. Smithy: BadRequestException exists on this service as errorKind=client, httpError=400 with a required Message ("The request is malformed or contains an error such as an invalid parameter value or a missing required parameter"); TagResource itself models only AccessDenied/Internal/ResourceNotFound/Throttling/ValidationException, so which class AWS picks for the tag ceiling, and the 50-tag limit, are recorded behavior only.
  Emulator: 400 with error code ValidationException.
  Why: a client's catch/branch on BadRequestException never fires, so an over-limit tagging call is indistinguishable from a modeled input-constraint violation.
  Fix: the TagResource handler's tag-count validation — raise BadRequestException with the fixed message, leaving the existing tag set untouched.
  Traces: pca-connector-scep.tag-resource-exceeds-max-tags-rejected.

Cause 7 of 7: the connector's announced Endpoint serves no SCEP (RFC 8894) data plane.
  AWS: Connector$Endpoint is documented as "The connector's HTTPS public SCEP URL" and speaks the SCEP wire protocol: a plain HTTP GET of "<Endpoint>?operation=GetCACert" answers 200 with a non-empty body that is either the CA certificate in DER or an application/x-x509-ca-ra-cert PKCS#7 bundle, and it contains the certificate of the private CA that CreateConnector was pointed at (matching subject and serial). Recorded behavior only — the Smithy model covers the control plane and does not model the SCEP endpoint.
  Emulator: the check never observes a 200 from the connector's Endpoint and exhausts its 60s budget in the GetCACert poll loop. Other checks in this suite that run the same preamble (create CA, activate it, create connector, wait for ACTIVE, create a challenge — e.g. delete-challenge-removes-password) reach their assertions well inside that budget, so the budget is not consumed by the control-plane setup. Hypothesis: no SCEP responder is bound to the Endpoint URL the emulator hands out, so the data plane is unreachable while the control plane answers normally.
  Why: a connector that accepts CreateConnector/CreateChallenge but cannot serve SCEP is a control-plane stub — no device-enrolment flow (the service's entire purpose) can be exercised against it.
  Fix: a SCEP data-plane responder routed at the Endpoint the connector advertises, backed by the connector's configured CA certificate from acm-pca state.
  Traces: pca-connector-scep.scep-get-cacert-native-protocol-roundtrip.
