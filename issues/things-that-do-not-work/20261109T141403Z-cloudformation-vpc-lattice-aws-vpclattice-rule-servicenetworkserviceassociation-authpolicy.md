# cloudformation__vpc-lattice: AWS::VpcLattice::Rule, ::ServiceNetworkServiceAssociation, ::AuthPolicy and ::ResourcePolicy are refused as unrecognized resource types, so no VPC Lattice rule, association or policy can be deployed from a template

> _Note: this issue was identified against the code base at commit `22941ee6d43df66d29bcadd7a62b7906e5868e84`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template resource-type registry does not carry the AWS::VpcLattice::Rule, AWS::VpcLattice::ServiceNetworkServiceAssociation, AWS::VpcLattice::AuthPolicy or AWS::VpcLattice::ResourcePolicy resource types, so CreateStack refuses at template-format validation any stack that declares one of them. Failing check ids: cloudformation__vpc-lattice.deploy-vpclattice-rule-fixedresponse-statuscode-rejected, cloudformation__vpc-lattice.deploy-vpclattice-targetgroup-listener-rule-round-trip-and-delete, cloudformation__vpc-lattice.deploy-vpclattice-service-network-association-round-trip-and-delete, cloudformation__vpc-lattice.deploy-vpclattice-servicenetwork-authpolicy-resourcepolicy-round-trip-and-delete.

AWS: AWS CloudFormation registers AWS::VpcLattice::Rule, AWS::VpcLattice::ServiceNetworkServiceAssociation, AWS::VpcLattice::AuthPolicy and AWS::VpcLattice::ResourcePolicy as supported resource types (documented at https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/AWS_VpcLattice.html), so CreateStack ACCEPTS a template declaring them and answers 200 with a StackId; whether each resource is provisioned or refused is then decided by its registry handler DURING the stack operation, not by template-format validation. Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): CreateStack input TemplateBody (@length min 1), output StackId; its only modeled errors are AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException — none of which is the refusal seen here. The 'Template format error: Unrecognized resource types: [...]' ValidationError is recorded behavior only: AWS returns HTTP 400 with Code ValidationError and a message whose FIXED text is 'Template format error: Unrecognized resource types: [' ... ']' and whose VARIABLE part is the comma-separated list of the submitted template's genuinely unregistered type names. AWS raises it only for a type name it does not register, which does not include the four above. Downstream of acceptance the recordings show what AWS does with these types: (a) a VPC Lattice rule whose FixedResponse StatusCode is unsupported is refused by the VPC Lattice handler, not by early validation (DescribeEvents carries no VALIDATION_ERROR row), driving the stack to ROLLBACK_COMPLETE with a CREATE_FAILED ResourceStatusReason of the form 'Resource handler returned message: "Provided status code is not supported. (Service: VpcLattice, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)' — the fixed text is 'Provided status code is not supported.' and the envelope, while request id, token and attempt count are per-run values; (b) a service + target group + listener + rule stack reaches CREATE_COMPLETE, Ref yields each resource's ARN in the documented formats (arn:<partition>:vpc-lattice:<region>:<account>:service/<svc-id>, :targetgroup/<tg-id>, <service-arn>/listener/<listener-id>, <service-arn>/listener/<listener-id>/rule/<rule-id>), GetRule reads back the declared priority, HttpMatch PathMatch exact and fixedResponse action, each resource carries the template Tags plus the stack's propagated tags, and UpdateStack dropping the rule and then the listener removes each child while its parent still answers; (c) a service network + service + ServiceNetworkServiceAssociation stack reaches CREATE_COMPLETE, the association's Ref is arn:<partition>:vpc-lattice:<region>:<account>:servicenetworkserviceassociation/<assoc-id> and reads status ACTIVE with serviceId/serviceNetworkId/serviceArn/serviceNetworkArn matching its parents, and an update dropping it leaves both parents' createdAt unchanged; (d) an AWS::VpcLattice::AuthPolicy and an AWS::VpcLattice::ResourcePolicy attached to a service network both have Ref equal to the SERVICE NETWORK's ARN, GetAtt State on the auth policy is 'Active', GetAuthPolicy/GetResourcePolicy return the declared documents, and after the stack is deleted all three reads answer ResourceNotFoundException 'ServiceNetwork <id> cannot be found.'

Emulator: CreateStack is refused outright with HTTP 400 ValidationError. The two rule checks get 'Template format error: Unrecognized resource types: [AWS::VpcLattice::Rule]'; the association check gets '...: [AWS::VpcLattice::ServiceNetworkServiceAssociation]'; the policy check gets '...: [AWS::VpcLattice::AuthPolicy, AWS::VpcLattice::ResourcePolicy]'. AWS::VpcLattice::ServiceNetwork, ::Service, ::Listener and ::TargetGroup are NOT named in any of those lists, so those four types are registered and the gap is exactly the four types above. Because the call raises at CreateStack, no stack is ever created and every downstream assertion of all four checks (CREATE_COMPLETE/ROLLBACK_COMPLETE, the handler CREATE_FAILED reason and HandlerErrorCode, Ref/GetAtt ARN formats, the VPC Lattice read-backs and tag propagation, the child-dropping updates and the post-delete not-found tombstones) is unreachable.

Why: a client that provisions VPC Lattice declaratively — any CloudFormation, SAM or CDK stack containing a listener rule, a service-network/service association, an auth policy or a resource policy — cannot deploy at all against the emulator. The refusal arrives as a template-format ValidationError at submit time, which a client reads as 'my template is malformed' and will neither retry nor poll, instead of as a stack operation whose outcome it can observe. The emulator also cannot reproduce AWS's rejection path for a bad rule property, which is supposed to surface as a resource-handler CREATE_FAILED reason with HandlerErrorCode InvalidRequest followed by a rollback, not as an up-front template error; code that distinguishes 'bad template' from 'resource refused by the service' takes the wrong branch.

Fix: CloudFormation's template resource-type registry and the VPC Lattice resource-type handlers it dispatches to. Register the four types so template-format validation accepts them, and implement their create/update/delete handlers against VPC Lattice state so Ref/GetAtt return the documented identifiers, template Tags propagate alongside the aws:cloudformation:* tags, VPC Lattice's own refusals (unsupported fixed-response status code) surface as handler CREATE_FAILED reasons that roll the stack back, and stack delete removes each resource so VPC Lattice reads answer ResourceNotFoundException.

Traces: cloudformation__vpc-lattice.deploy-vpclattice-rule-fixedresponse-statuscode-rejected and cloudformation__vpc-lattice.deploy-vpclattice-targetgroup-listener-rule-round-trip-and-delete (both refused with '[AWS::VpcLattice::Rule]'), cloudformation__vpc-lattice.deploy-vpclattice-service-network-association-round-trip-and-delete ('[AWS::VpcLattice::ServiceNetworkServiceAssociation]'), cloudformation__vpc-lattice.deploy-vpclattice-servicenetwork-authpolicy-resourcepolicy-round-trip-and-delete ('[AWS::VpcLattice::AuthPolicy, AWS::VpcLattice::ResourcePolicy]').

## Steps to Reproduce
1. Point a boto3/botocore cloudformation client at the emulator.
2. Submit a template declaring a VPC Lattice service, listener and rule:
   cf.create_stack(StackName='t1', TemplateBody=json.dumps({'AWSTemplateFormatVersion':'2010-09-09','Resources':{
     'Svc':{'Type':'AWS::VpcLattice::Service','Properties':{'Name':'svc1'}},
     'Listener':{'Type':'AWS::VpcLattice::Listener','Properties':{'ServiceIdentifier':{'Ref':'Svc'},'Protocol':'HTTP','DefaultAction':{'FixedResponse':{'StatusCode':404}}}},
     'Rule':{'Type':'AWS::VpcLattice::Rule','Properties':{'ServiceIdentifier':{'Ref':'Svc'},'ListenerIdentifier':{'Ref':'Listener'},'Priority':5,'Match':{'HttpMatch':{'PathMatch':{'Match':{'Exact':'/x'}}}},'Action':{'FixedResponse':{'StatusCode':404}}}}}}))
   Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::VpcLattice::Rule]' instead of a 200 with a StackId.
3. Repeat with an AWS::VpcLattice::ServiceNetworkServiceAssociation, and again with an AWS::VpcLattice::AuthPolicy plus AWS::VpcLattice::ResourcePolicy on a service network; each is refused naming only those types, confirming ::ServiceNetwork/::Service/::Listener/::TargetGroup are registered and the four above are not.
4. Replay the four behavioral checks listed in Issue-Trace-Ids; all four abort at their first create_stack call.
