# Lake Formation GrantPermissions stores a table grant verbatim instead of normalising it into Table/TableWithColumns entries, and accepts grants on tables and databases that do not exist

> _Note: this issue was identified against the code base at commit `001920e7906d433f041aca694d32f13b44f642fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GrantPermissions

## Description
Two distinct root causes in the Lake Formation emulator's GrantPermissions/ListPermissions path, found by replaying the behavioral suite. Both must be closed before this issue is done. The open issue 20261022T131025Z-lakeformation-grantpermissions-stub.md does NOT cover either one: it asks only that the GrantPermissions scaffold stop answering 501, and the call now returns 200 and persists a grant. These are the fidelity defects of the implemented handler that the replay reaches afterwards, and the three checks it lists now fail on assertions about what was stored, not on a NotImplemented refusal.

Cause 1 of 2: a single GrantPermissions call of SELECT + DESCRIBE on a Table resource is stored as one verbatim entry instead of being normalised into two entries.
AWS: Smithy com.amazonaws.lakeformation#GrantPermissions takes Principal (DataLakePrincipal, required), Resource (Resource, required) and Permissions (PermissionList, required) and returns HTTP 200 with an empty body; what it stored is observable only through ListPermissions, whose output member PrincipalResourcePermissions is a list of PrincipalResourcePermissions (Principal, Resource, Permissions, PermissionsWithGrantOption). The Resource union models Table (TableResource) and TableWithColumns (TableWithColumnsResource) as distinct members, and TableWithColumnsResource documents ColumnNames/ColumnWildcard — 'This object is only used when granting a SELECT permission'. Recorded behavior: granting ['SELECT','DESCRIBE'] on {Table:{DatabaseName:db,Name:usage_events}} is recorded as exactly TWO entries for that principal — one with Resource.Table and Permissions ['DESCRIBE'], and one with Resource.TableWithColumns carrying ColumnWildcard {} (and no ColumnNames), DatabaseName/Name of the same table, and Permissions ['SELECT'] — with PermissionsWithGrantOption [] on both. The same two entries are what the Principal-filtered ListPermissions returns for that role.
Emulator: ListPermissions returns a single entry: Resource {'Table': {'CatalogId': ..., 'DatabaseName': ..., 'Name': 'usage_events'}} with Permissions ['SELECT','DESCRIBE'] and PermissionsWithGrantOption []. The handler persists the request's Resource and Permissions as given and performs no SELECT-to-column-wildcard normalisation, so the Table/TableWithColumns split never exists in state and both the unfiltered and the Principal-filtered listing report one wrong-shaped entry.
Why: any client that reads back what a principal holds sees a grant shape AWS never produces. Column-level reasoning is impossible (a table-wide SELECT is indistinguishable from no column scope at all), audit/diff tooling that keys on the resource kind mis-attributes the SELECT, and a revoke aimed at the TableWithColumns entry AWS records matches nothing.
Fix: the normalisation belongs in the GrantPermissions handler and the state it writes — services/service-com-amazonaws-lakeformation-awslakeformation/src/ops/grant_permissions.rs plus the permission store in crate::state — splitting a Table-resource grant that contains SELECT into a Table entry holding the non-SELECT permissions and a TableWithColumns entry holding SELECT with ColumnWildcard; ListPermissions (list_permissions.rs) must then project those stored entries unchanged.
Traces: glue__iam__lakeformation__s3.lf-select-describe-grant-splits-into-table-and-column-wildcard-entries, glue__iam__lakeformation__s3.lf-list-permissions-principal-filter-attributes-iam-allowed-principals-grant-to-the-principal.

Cause 2 of 2: GrantPermissions succeeds on a table or a database that does not exist.
AWS: Smithy com.amazonaws.lakeformation#GrantPermissions models InvalidInputException (HTTP 400, 'The input provided was not valid') alongside EntityNotFoundException and ConcurrentModificationException; the operation otherwise returns HTTP 200 with an empty body. Recorded behavior: granting ['SELECT','DESCRIBE'] on {Table:{DatabaseName:<existing db>,Name:<absent table>}} is refused with error code InvalidInputException (example message 'Table not found.'), and granting ['DESCRIBE'] on {Database:{Name:<absent db>}} is refused with error code InvalidInputException (example message 'Database not found.'). Lake Formation resolves the resource against the Glue catalog at grant time, and the refusal leaves the principal's real grant on the existing table untouched. The requirement is the HTTP 400 and the InvalidInputException code; the two messages are recorded examples.
Emulator: both calls return HTTP 200 and record a grant on a resource with no catalog entry — the check's error helper raises 'the call succeeded; real AWS refuses it, so there is no error'. The handler performs no cross-service existence check of Resource.Table / Resource.Database against the Glue catalog.
Why: a client gets silent success for a grant aimed at the wrong name — the single most common operator mistake in this area. The grant it believes it made has no effect on the real table, troubleshooting flows that use the refusal to detect a typo lose their signal, and the permission store accumulates entries for resources that do not exist.
Fix: add resource resolution to the GrantPermissions handler's validation in services/service-com-amazonaws-lakeformation-awslakeformation/src/ops/grant_permissions.rs (and the matching path in revoke_permissions.rs) — look the Database/Table up in the Glue catalog state before writing, and reject an unresolvable one with InvalidInputException (HTTP 400) naming the missing database or table, persisting nothing.
Traces: glue__iam__lakeformation__s3.lf-grant-on-missing-table-or-database-rejected.
