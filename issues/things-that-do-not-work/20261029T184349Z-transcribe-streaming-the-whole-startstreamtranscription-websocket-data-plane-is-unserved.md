# The whole StartStreamTranscription WebSocket data plane is unserved: the upgrade is answered with 503, and the refusals that should arrive as eventstream exceptions on the open stream are answered as HTTP 4xx at the handshake

> _Note: this issue was identified against the code base at commit `f20bf72de740b5a2b8804db1d8ff681c13106e79`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartStreamTranscription

## Description
Four distinct root causes in the transcribe-streaming data plane, all reached through the documented WebSocket endpoint GET /stream-transcription-websocket with the SigV4 query-signed upgrade. Every one of the 14 behavioral checks for this service fails before a single audio byte is transcribed. Smithy (services/service-com-amazonaws-transcribestreaming-transcribe/smithy-model/com-amazonaws-transcribestreaming-transcribe.json): StartStreamTranscription, restJson1, sigv4, POST /stream-transcription, input AudioStream @streaming @httpPayload, output TranscriptResultStream @streaming, and its own doc sentence reads "Starts a bidirectional HTTP/2 or WebSocket stream where audio is streamed to Amazon Transcribe and the transcription results are streamed to your application" — the WebSocket transport is part of the modeled operation, not an extra.

=== Cause 1 of 4: the WebSocket upgrade is refused outright, so no session can ever be opened ===
AWS: a SigV4 query-signed GET of /stream-transcription-websocket is answered with 'HTTP/1.1 101 Switching Protocols' (Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Accept = base64(sha1(Sec-WebSocket-Key + 258EAFA5-E914-47DA-95CA-C5AB0DC85B11))) and mints a session, reported in the x-amzn-SessionId response header; audio then flows up as vnd.amazon.eventstream AudioEvent messages and TranscriptEvent messages flow down, and the session ends with WebSocket close 1000 "Streaming completed successfully.". Smithy: the operation's doc states the WebSocket transport; the modeled ServiceUnavailableException is httpError 503, errorKind server, and means the service is temporarily unable to serve the request — not that a transport is unimplemented.
Emulator: the upgrade is answered 'HTTP/1.1 503 Service Unavailable', content-type application/json, x-amzn-errortype: ServiceUnavailableException, body {"__type":"ServiceUnavailableException","Message":"This emulator cannot serve the WebSocket transport of this operation: its HTTP front door answers one buffered request per call and cannot switch a connection to the WebSocket protocol, so no 101 Switching Protocols handshake is possible. ..."}. The message is emulator self-description: no AWS error message mentions an emulator, a front door or a buffered request, so both the status (503 where AWS sends 101) and the whole message body are divergent.
Why: a client that speaks this service's documented streaming transport — every browser/JS client, and every SDK configured for the WebSocket data plane — can never open a stream. Nothing about transcription (partials, finals, ResultId identity, channel identification, language identification, stabilization, speaker labels, vocabulary filtering) is reachable, and a server-class 503 tells the client to retry forever against a condition that never clears.
Fix: the transcribe-streaming front door / transport layer for StartStreamTranscription must implement the 101 handshake and a bidirectional eventstream session (hijack the connection, compute Sec-WebSocket-Accept, mint and return x-amzn-SessionId, read AudioEvent frames, emit TranscriptEvent frames, close 1000 with "Streaming completed successfully."), then the StartStreamTranscription handler's transcription behavior behind it.
Traces: transcribe-streaming.stream-transcription-event-stream-framing-and-session-identity, transcribe-streaming.stream-transcription-partial-then-final-transcript, transcribe-streaming.stream-transcription-channel-identification-separates-two-channels, transcribe-streaming.stream-transcription-identifies-the-spoken-language, transcribe-streaming.stream-transcription-partial-results-stabilization-adds-stable-flag, transcribe-streaming.stream-transcription-speaker-label-annotates-final-items, transcribe-streaming.stream-transcription-vocabulary-filter-masks-filtered-words, transcribe-streaming.stream-transcription-rejects-corrupted-event-stream-message, transcribe-streaming.stream-transcription-rejects-oversized-audio-frame.

=== Cause 2 of 4: request-parameter refusals are delivered at the handshake instead of as an exception on the open stream ===
AWS: on the WebSocket transport the handshake does not carry the modeled per-request error. The upgrade is accepted with 101, a session id is minted, and the refusal is delivered as an eventstream message with :message-type = exception and :exception-type naming the error, after which the socket closes with the reason "Your request completed with an exception." and no TranscriptEvent is ever sent. The parameters in question are modeled as @httpHeader-bound members of StartStreamTranscriptionRequest (MediaEncoding, MediaSampleRateHertz, NumberOfChannels, EnableChannelIdentification, PartialResultsStability, EnablePartialResultsStabilization), carried as query parameters on the WebSocket endpoint; recorded behavior only for where the refusal lands (the model binds errors to the HTTP response and says nothing about the WebSocket framing).
Emulator: each of these requests is refused before the upgrade with 'HTTP/1.1 400 Bad Request', x-amzn-errortype: BadRequestException and a JSON body, so status 400 appears where AWS sends 101 and the client never sees an exception event, never gets a session id, and never observes the 1009/1000 close contract.
Why: a client written against the WebSocket data plane reads refusals off the stream; getting them as a failed handshake makes an ordinary parameter mistake indistinguishable from an endpoint/credential/transport failure, and code that waits for "Your request completed with an exception." to classify the outcome hangs or mis-reports.
Fix: the StartStreamTranscription WebSocket transport must complete the handshake first and route request-validation failures into the outbound eventstream as exception messages, with the close reason, rather than returning them from the upgrade's HTTP response.
Traces: transcribe-streaming.stream-transcription-rejects-unsupported-media-encoding, transcribe-streaming.stream-transcription-rejects-unsupported-sample-rate, transcribe-streaming.stream-transcription-rejects-channel-count-without-channel-identification, transcribe-streaming.stream-transcription-rejects-partial-results-stability-without-stabilization.

=== Cause 3 of 4: wrong error code for constraint violations, and wrong message text for the cross-parameter co-requirements ===
AWS: a member that violates its own modeled constraint is refused as ValidationException whose message is the standard constraint template — fixed text "N validation error(s) detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy enum value set: [<values>]" for an enum, and "... Member must have value greater than or equal to <min>" for a range — where the value, the member name (mediaEncoding, mediaSampleRateHertz) and the limit come from the request and from the model (Smithy: MediaSampleRateHertz @range min 8000 max 48000; MediaEncoding enum; NumberOfChannels @range min 2). The two co-requirement rules are refused as BadRequestException (Smithy: BadRequestException, errorKind client, httpError 400, a common error of this service) with AWS's own fixed wording, which carries no value from the request at all: "You need to be enable Channel Identification while specifying number of channels in the request. Please enable Channel Identification and try again." and "Partial Results Stabilization must be enabled while specifying partial results stability in the request. Please enable Partial Results Stabilization and try again." ValidationException itself is not in this model's error list — recorded behavior only for that code.
Emulator: all four are classified BadRequestException, and the two constraint violations therefore carry the wrong error code (BadRequestException where AWS raises ValidationException), while the two co-requirement messages are locally invented prose that interpolates request values AWS's text does not contain: "NumberOfChannels was set to 2 without EnableChannelIdentification: if you include NumberOfChannels in your request, you must also include EnableChannelIdentification" and "PartialResultsStability was set to 'high' without EnablePartialResultsStabilization: a stability level applies only when you enable partial results stabilization". (The '2' and 'high' here are this run's request values; the defect is that AWS's message for these two classes is fixed text with no interpolation.)
Why: clients branch on the exception type and SDKs map it to a typed error, so a ValidationException surfaced as BadRequestException defeats retry/branching logic, and tests or support tooling that match AWS's documented message text never match.
Fix: the StartStreamTranscription request validation must classify modeled-constraint failures as ValidationException with the standard constraint message template, and emit AWS's fixed wording for the NumberOfChannels/EnableChannelIdentification and PartialResultsStability/EnablePartialResultsStabilization co-requirements.
Traces: transcribe-streaming.stream-transcription-rejects-unsupported-media-encoding, transcribe-streaming.stream-transcription-rejects-unsupported-sample-rate, transcribe-streaming.stream-transcription-rejects-channel-count-without-channel-identification, transcribe-streaming.stream-transcription-rejects-partial-results-stability-without-stabilization.

=== Cause 4 of 4: a bad stream signature fails the handshake instead of being raised on the open stream ===
AWS: on this WebSocket endpoint the presigned-query signature is NOT verified as a precondition of the upgrade. A request whose X-Amz-Signature has been tampered with is still answered 101 and still mints a session id; the refusal arrives only once audio is written to the open stream, as an eventstream exception of type InvalidSignatureException whose message begins with the fixed text "The request signature we calculated does not match the signature you provided." (the remainder names the canonical request/string-to-sign derived from the request), and no TranscriptEvent is produced. Recorded behavior only for the deferral point; the message is AWS's standard SigV4 mismatch text.
Emulator: the tampered upgrade is refused at the handshake with 'HTTP/1.1 403 Forbidden', x-amzn-errortype: SignatureDoesNotMatch, body {"__type":"SignatureDoesNotMatch","message":"The request signature does not match"} — wrong status (403 where AWS sends 101), wrong error code (SignatureDoesNotMatch where AWS raises InvalidSignatureException on the stream), and a truncated message that is not AWS's text for this class.
Why: a client cannot distinguish a credential problem from an unreachable endpoint, gets no session id to correlate, and SDK/stream error handlers that expect InvalidSignatureException as a stream exception never fire. It also diverges on where auth is enforced, so an emulator-based test cannot reproduce the real service's deferred-auth behavior at all.
Fix: the transcribe-streaming WebSocket upgrade path for StartStreamTranscription must accept the presigned upgrade without gating on signature validity, and raise InvalidSignatureException with AWS's SigV4 mismatch message as an eventstream exception on the first audio write.
Traces: transcribe-streaming.stream-transcription-rejects-invalid-signature-on-the-stream-not-the-upgrade.

No open issue covers any of these; the six open transcribe-family issues (e.g. 20261029T093654Z-transcribe-starttranscriptionjob-wrong-behavior--r2.md) are all batch-transcribe control-plane findings for the separate `transcribe` service and none touches the streaming data plane.
