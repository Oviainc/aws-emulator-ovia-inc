=== Cause 1 of 3: PutMetricAlarm stores DatapointsToAlarm but the evaluator never produces an evaluated OK over an M-of-N window ===
Failing check: cloudwatch.alarm-m-of-n-holds-at-m-minus-one-and-fires-at-m

AWS: Smithy (com.amazonaws.cloudwatch) — PutMetricAlarm.DatapointsToAlarm (target DatapointsToAlarm, range min 1) is documented "The number of data points that must be breaching to trigger the alarm"; PutMetricAlarm.EvaluationPeriods (range min 1) is "The number of periods over which data is compared to the specified threshold"; MetricAlarm.StateReason (StateReason, @length max 1023) is "An explanation for the alarm state, in text format" and MetricAlarm.StateReasonData (@length max 4000) is "An explanation for the alarm state, in JSON format"; MetricAlarm.StateValue targets the StateValue enum. The model says nothing about the M-of-N predicate itself, so for that part: recorded behavior only. The recording shows that with EvaluationPeriods=5, DatapointsToAlarm=3, Statistic=Maximum, Period=60, ComparisonOperator=GreaterThanThreshold, TreatMissingData=notBreaching and a hole-free 5-period window holding exactly 2 breaching datapoints, the alarm reaches an EVALUATED OK (not INSUFFICIENT_DATA), and only once a 3rd breaching datapoint enters the window does it reach ALARM. The recording also pins the response content: StateReasonData carries `recentDatapoints` — the full EvaluationPeriods-long window, oldest first — and `evaluatedDatapoints`, which is NOT the window but exactly the datapoints that justified the verdict, newest first, each `{timestamp, sampleCount, value}` and no per-item breaching flag; `threshold` echoes the alarm's configured Threshold. StateReason is a template whose FIXED text is "Threshold Crossed: " / " out of the last " / " datapoints [" / "] were greater than the threshold (" / ") (minimum " / " datapoints for " / " transition)." and whose VARIABLE parts come from the request and from state: the counted datapoints and the window length (DatapointsToAlarm and EvaluationPeriods as the request set them), the datapoint values and their timestamps (from the stored series), the threshold (from the alarm's configuration), the direction ("OK -> ALARM" / "ALARM -> OK") and the direction's minimum — which is DatapointsToAlarm for OK->ALARM and EvaluationPeriods - DatapointsToAlarm + 1 for ALARM->OK. Never copy one run's literals (99.0/1.0/10.0, the 5/3 pair, the run's timestamps) as the requirement: those are this recording's filling of that template.

Emulator: the alarm is created and the two configuration integers round-trip, but the alarm never reaches OK. The check's DescribeAlarms poll for StateValue == "OK" (its own budget 300 s, republishing a non-breaching newest datapoint each pass) is never satisfied, and the check is killed at the suite's 60 s harness cap ("Error: Check timed out after 60.0s"). Nothing downstream of that poll — the recentDatapoints window, the evaluatedDatapoints justification, the StateReason wording, the history StateUpdate item — is ever produced.

Why: a client that configures DatapointsToAlarm != EvaluationPeriods gets an alarm that never settles into an evaluated non-breaching state. Autoscaling, deployment-rollback and paging logic that waits for OK before proceeding, and anything that reads StateReason/StateReasonData to explain a verdict, hangs or reads nothing. An emulator that instead graded only the newest datapoint would fire during the 2-of-5 phase and could not recover — the same configuration silently means something different than on AWS.

Fix: the alarm evaluator and the state-reason rendering it drives — services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_evaluation.rs (the M-of-N count over the EvaluationPeriods sliding window, and the INSUFFICIENT_DATA -> OK -> ALARM progression driven by the stored series), plus the StateReason/StateReasonData serialization on the DescribeAlarms read path.

Traces: cloudwatch.alarm-m-of-n-holds-at-m-minus-one-and-fires-at-m. The open issue 20261025T020208Z-cloudwatch-alarms-never-evaluate-published-metric-data-no.md describes a neighbouring symptom but does not carry this check's replay key, and it does not cover the M-of-N predicate or the direction-specific minimum wording.

=== Cause 2 of 3: an ANOMALY_DETECTION_BAND alarm is accepted but never evaluated — it stays INSUFFICIENT_DATA forever ===
Failing check: cloudwatch.alarm-math-and-anomaly-band-alarm-survives-detector-delete-and-fires-out-of-band

AWS: Smithy — PutMetricAlarm.ThresholdMetricId (target MetricId, @length 1..255) is documented "In an alarm based on an anomaly detection model, this is the ID of the ANOMALY_DETECTION_BAND function used as the threshold for the alarm"; ComparisonOperator carries GreaterThanUpperThreshold; AnomalyDetector.StateValue targets AnomalyDetectorStateValue with values PENDING_TRAINING, TRAINED_INSUFFICIENT_DATA, TRAINED. Beyond that: recorded behavior only. The recording shows (a) a steady in-band value drives the band alarm to OK — not merely "not ALARM" — and the upper threshold the evaluator cites in StateReasonData.evaluatedDatapoints[0].threshold equals the "High" series GetMetricData returns for the ANOMALY_DETECTION_BAND expression at the evaluated timestamp, with the published value inside [Low, High]; (b) DeleteAnomalyDetector on a detector a live alarm references succeeds and the detector disappears from DescribeAnomalyDetectors, and then the still-live alarm RE-CREATES it (it reappears PENDING_TRAINING or TRAINED*) while the alarm stays OK, whereas an identically created-and-deleted detector that NO alarm references stays absent; (c) a far out-of-band value drives the SAME alarm to ALARM, with a DescribeAlarmHistory StateUpdate item whose cited datapoint is above the cited upper threshold and whose oldState is the earlier OK.

Emulator: PutMetricAlarm ACCEPTS the band alarm (Metrics=[the metric query, {Id: ad1, Expression: ANOMALY_DETECTION_BAND(m1, 2)}], ThresholdMetricId="ad1", ComparisonOperator=GreaterThanUpperThreshold) and the detector does settle out of PENDING_TRAINING (PutAnomalyDetector stores TRAINING_DELAY_SECS = 0.5 and settle_anomaly_detector_training materialises it), but the alarm then never leaves INSUFFICIENT_DATA: the check's DescribeAlarms poll for StateValue != "INSUFFICIENT_DATA" (its own budget 600 s, republishing the in-band value each pass) is never satisfied and the check is killed at the 60 s harness cap. So neither the band-as-threshold evaluation, nor the alarm-driven re-creation of the deleted detector, nor the out-of-band ALARM is ever reached.

Why: anomaly-detection alarms are inert. A client that builds a band alarm gets a permanently INSUFFICIENT_DATA alarm, so nothing it gates ever runs, and a client that deletes a detector under a live alarm sees the model stay gone instead of being rebuilt by the alarm reference — the opposite of AWS's documented guidance to delete the alarm first.

Fix: the alarm evaluator's threshold resolution — services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_evaluation.rs must resolve ThresholdMetricId to the band series instead of a scalar Threshold; the band function belongs in src/state/metric_math.rs (ANOMALY_DETECTION_BAND must yield the Low/High pair GetMetricData returns, labelled so the "High"/"Low" suffix is readable); and the anomaly-detector store (src/state.rs, anomaly_detectors) must re-create a deleted detector that a live alarm still references.

Traces: cloudwatch.alarm-math-and-anomaly-band-alarm-survives-detector-delete-and-fires-out-of-band. The open issue 20261026T031713Z-cloudwatch-2-net-new-root-causes-putmetricalarm-refuses.md reports PutMetricAlarm REFUSING band alarms; here the alarm is accepted and then never evaluated, and that issue does not carry this check's replay key.

=== Cause 3 of 3: a CloudFormation-deployed two-stream metric-stream estate never becomes readable, so the whole deploy/solve/cleanup/destroy lifecycle stalls ===
Failing check: cloudwatch.mstrx-e2e-find-metric-streams-excluding-namespace-lifecycle

AWS: Smithy — GetMetricStream output carries IncludeFilters, ExcludeFilters (MetricStreamFilters), FirehoseArn, RoleArn, State (MetricStreamState), OutputFormat, StatisticsConfigurations, IncludeLinkedAccountsMetrics, and models ResourceNotFoundException with httpError 404 (awsQueryError code ResourceNotFoundException). Everything else here is recorded behavior only: a stack declaring two AWS::CloudWatch::MetricStream resources over one Firehose/S3 destination reaches CREATE_COMPLETE; GetMetricStream then reports the exclude stream's ExcludeFilters as a single filter whose MetricNames are in TEMPLATE order, its FirehoseArn equal to the stack's Firehose ARN, and both streams' State as "running"; the include stream carries only its IncludeFilters and NO ExcludeFilters member at all (absent, not empty). StopMetricStreams then leaves both States "stopped" and quiesces delivery so the destination bucket can be emptied; after the stack is deleted, GetMetricStream answers ResourceNotFoundException with an EMPTY message, and CloudFormation DescribeStackResources answers ValidationError whose message is the fixed text "Stack with id " + the stack name from the request + " does not exist".

Emulator: the check never gets past its deploy phase. It is killed at the 60 s harness cap ("Error: Check timed out after 60.0s") before the first GetMetricStream assertion runs, so the stack's MetricStream resources never become readable through the CloudWatch API within any usable time, and none of the solve/cleanup/destroy stages (ListMetricStreams walk, StopMetricStreams quiescing, destroy-then-not-found) is exercised.

Why: an infrastructure-as-code client cannot stand up metric streams at all in this emulator — the stack it deploys never yields streams it can read, stop or tear down, so every tool that provisions observability through CloudFormation is blocked rather than merely inaccurate.

Fix: the CloudFormation resource provisioner for AWS::CloudWatch::MetricStream and the CloudWatch metric-stream store it must write into (services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state.rs, metric_streams, read by src/ops/get_metric_stream.rs and src/ops/list_metric_streams.rs), including preserving MetricNames order and omitting the ExcludeFilters member entirely on an include-only stream, and the not-found path of GetMetricStream.

Traces: cloudwatch.mstrx-e2e-find-metric-streams-excluding-namespace-lifecycle. The open issue 20261025T002604Z-cloudwatch-firehose-s3-cloudformation-deployed-metric-stream-pipeline-the-stack-reports.md is filed against the cloudwatch__firehose__s3 service token and does not carry this check's replay key.
