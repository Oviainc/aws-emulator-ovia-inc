# EC2: a minted cancellation quote is never usable, well-formed unknown capacity-reservation ids are reported Malformed, and an identical CreateNetworkAclEntry re-create is refused (3 causes)

> _Note: this issue was identified against the code base at commit `86d4487805fae2c305c5dd9de933831005de30fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelCapacityReservation

## Description
Three independent net-new fidelity defects in EC2 operations that DO answer (no scaffold stub is involved — none of these four checks was reported as blocked by an unimplemented operation, and none is carried by an open issue). This issue bundles 3 causes; ALL THREE must be closed before submitting.

Background shared by causes 1 and 2: EC2 models no error shapes (Smithy com-amazonaws-ec2-amazonec2: CancelCapacityReservation, CreateCapacityReservationCancellationQuote, UpdateInterruptibleCapacityReservationAllocation and CreateNetworkAclEntry all report errors: []), so the ec2Query error CODE and message on the wire are the whole contract a client can branch on; a wrong code is a wrong response.

Cause 1 of 3: CancelCapacityReservation refuses the cancellation quote the emulator itself just minted, because the quote never leaves QuoteState 'pending'.
AWS: CreateCapacityReservationCancellationQuote on a future-dated, commitment-bearing reservation that has settled out of 'assessing' (state scheduled / payment-pending / active / delayed) mints a quote that is then USABLE: CancelCapacityReservation(CapacityReservationId=<id>, QuoteId=<quoteId>, ApplyCancellationCharges='commitment-wind-down') returns 200 with Return=true and the reservation settles into 'cancelling' then 'cancelled'. Smithy: CancelCapacityReservation input carries QuoteId -> CapacityReservationCancellationQuoteId and ApplyCancellationCharges -> enum ApplyCancellationCharges with the single value 'commitment-wind-down'; CapacityReservationCancellationQuote.QuoteState -> CapacityReservationCancellationQuoteState, enum values pending | active | expired, documented as 'The state of the cancellation quote'. The quote minting is a success path (recorded behavior only for the transition timing): a quote minted for an eligible reservation becomes usable rather than staying pending forever.
Emulator: the cancel is refused — HTTP 4xx, code IncorrectState, message "The cancellation quote '<quoteId>' is in state 'pending', not 'active', so it cannot be used for a cancellation" (fixed text "The cancellation quote '" ... "' is in state '" <current QuoteState> "', not 'active', so it cannot be used for a cancellation"; the quote id is the one just returned by CreateCapacityReservationCancellationQuote and the state comes from emulator state). The quote is minted in 'pending' and nothing ever advances it to 'active', so the refusal is unreachable in AWS and the whole quote-then-cancel workflow is a dead end.
Why: a client that follows AWS's documented quote-then-cancel flow for a future-dated commitment reservation can never cancel it; the reservation stays scheduled/active and keeps billing, and there is no state the client can poll to make the quote usable.
Fix: the cancellation-quote state machine (the quote record in EC2 state plus the CreateCapacityReservationCancellationQuote handler, services/service-com-amazonaws-ec2-amazonec2/src/ops/create_capacity_reservation_cancellation_quote.rs) must take the quote to QuoteState 'active' when its target reservation is eligible, and the precondition check in the CancelCapacityReservation handler (src/ops/cancel_capacity_reservation.rs) must then accept it and drive the reservation to cancelling/cancelled. Related open issue 20261029T200817Z-ec2-capacity-reservations-never-reach-cancelled-lose-their.md covers the cancel-state projection and the no-commitment quote refusal class; it does NOT carry this quote-stuck-in-pending cause or this check.
Traces: ec2.capacity-reservation-cancellation-quote-then-cancel-consistency.

Cause 2 of 3: a syntactically valid but never-allocated capacity-reservation id is classified as Malformed instead of NotFound, on two different operations.
AWS: an id of the real shape ('cr-' followed by the same number of hex characters an allocated reservation id uses) that was never allocated is refused with code InvalidCapacityReservationId.NotFound and message "The capacity-reservation ID '<id>' does not exist" — fixed text "The capacity-reservation ID '" ... "' does not exist", with the id taken verbatim from the request (recorded behavior only; EC2 models no error shapes). InvalidCapacityReservationId.Malformed is reserved for ids whose SYNTAX is wrong. Smithy: CapacityReservationId is a plain string shape with no length or pattern constraint, so the model imposes no syntax the probe ids violate; both CancelCapacityReservation.CapacityReservationId and UpdateInterruptibleCapacityReservationAllocation.CapacityReservationId target it and are required.
Emulator: both operations answer code InvalidCapacityReservationId.Malformed with message "Capacity Reservation ID '<id>' is malformed". ec2.op-contract-cancel-capacity-reservation draws up to ten random, syntactically valid 'cr-' + hex candidates of the real id's length and every one is reported Malformed, so no well-formed id the emulator did not itself mint is ever reported NotFound; ec2.op-contract-update-interruptible-capacity-reservation-allocation shows the same for the all-zero placeholder cr-00000000000000000 (expected ('InvalidCapacityReservationId.NotFound', "The capacity-reservation ID 'cr-00000000000000000' does not exist"), got ('InvalidCapacityReservationId.Malformed', "Capacity Reservation ID 'cr-00000000000000000' is malformed")).
Why: a client cannot tell a typo from a reservation that no longer exists, so repair/retry logic takes the wrong branch — and cleanup code that tolerates InvalidCapacityReservationId.NotFound (the pattern both checks' teardown uses) raises instead.
Fix: the capacity-reservation id validation/lookup ordering shared by these handlers (services/service-com-amazonaws-ec2-amazonec2/src/ops/cancel_capacity_reservation.rs and src/ops/update_interruptible_capacity_reservation_allocation.rs): validate SYNTAX only, then classify an unknown-but-well-formed id as NotFound with AWS's wording. Note: open issue 20261022T235108Z-ec2-misclassifies-rejections-and-skips-validation-malformed-ids.md covers the opposite direction (malformed ids answered as NotFound on DescribeImages/TerminateInstances/etc.) and does not carry either of these checks or the capacity-reservation id path; open issue 20261023T102725Z-ec2-updateinterruptiblecapacityreservationallocation-stub.md names that operation as a stub, but the operation now answers and reaches this error boundary, so neither covers this cause.
Traces: ec2.op-contract-cancel-capacity-reservation, ec2.op-contract-update-interruptible-capacity-reservation-allocation.

Cause 3 of 3: CreateNetworkAclEntry is not idempotent — an identical re-create of an existing entry is refused instead of accepted.
AWS: CreateNetworkAclEntry for a (NetworkAclId, RuleNumber, Egress) triple that already exists with IDENTICAL contents succeeds (empty 200 body — Smithy: output_shape Unit) and leaves exactly one entry for that rule number and direction; only a re-create with the SAME rule number and direction but DIFFERENT contents is refused with code NetworkAclEntryAlreadyExists and message "The network acl entry identified by <ruleNumber> already exists." (fixed text "The network acl entry identified by " <RuleNumber from the request> " already exists."). Recorded behavior only for the idempotency rule; Smithy: CreateNetworkAclEntry requires NetworkAclId, RuleNumber, Protocol, RuleAction and Egress, with optional CidrBlock/Ipv6CidrBlock/IcmpTypeCode/PortRange, and declares errors: [].
Emulator: the conflict path is right (the differing-CidrBlock re-create is correctly refused NetworkAclEntryAlreadyExists with exactly that message), but the IDENTICAL re-create is refused with the same code and message — the check dies on an uncaught ClientError "An error occurred (NetworkAclEntryAlreadyExists) when calling the CreateNetworkAclEntry operation: The network acl entry identified by 100 already exists." So the handler keys the conflict on rule number + direction alone and never compares the entry's contents.
Why: every converging/retrying client breaks — a re-applied Terraform/CloudFormation-style configuration, or any retry after a timed-out-but-applied create, turns a no-op into a hard failure, and a client cannot distinguish 'already exactly as you asked' from 'a different rule occupies this number'.
Fix: the duplicate detection in the CreateNetworkAclEntry handler (services/service-com-amazonaws-ec2-amazonec2/src/ops/create_network_acl_entry.rs): compare the full entry (protocol, rule action, cidr/ipv6 cidr, icmp type-code, port range) and return success when it matches, reserving NetworkAclEntryAlreadyExists for a genuine content conflict. Related open issue 20261030T063325Z-ec2-network-acl-entries-are-wrong-egress-flag.md covers the entrySet projection/ordering, not this write-path idempotency, and does not carry this check.
Traces: ec2.network-acl-entry-create-duplicate-delete.
