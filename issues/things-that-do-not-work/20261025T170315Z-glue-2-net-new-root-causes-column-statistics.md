# Glue: 2 net-new root causes — column statistics task runs always settle to FAILED and compute no statistics, and CreateColumnStatisticsTaskSettings is a NotImplemented stub so the running-task conflict is never raised

> _Note: this issue was identified against the code base at commit `3a5777642c2144d422034a2df8d16fbd36d2448f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartColumnStatisticsTaskRun

## Description
Two distinct root causes in the Glue Data Catalog's column-statistics surface. Both are net-new: neither is marked ALREADY FILED nor OWNED by an open issue in the replay report. Cause 2 is adjacent to the open issue `20261025T022820Z-glue-createcolumnstatisticstasksettings-stub.md` ("Implement glue CreateColumnStatisticsTaskSettings: unimplemented scaffold stub"), which records only that the operation is a stub; the behavioural requirements below (the in-flight conflict refusal, its exact message, and the absence-of-effect on GetColumnStatisticsTaskSettings) are what the replayed check grades and are not stated there.

=== Cause 1 of 2: a column statistics task run never computes statistics and always ends FAILED ===
AWS: Smithy (com.amazonaws.glue) — `StartColumnStatisticsTaskRun` takes DatabaseName/TableName/Role (@required) plus ColumnNameList, and returns a ColumnStatisticsTaskRunId. `GetColumnStatisticsTaskRun` returns a `ColumnStatisticsTaskRun` whose `Status` is a `ColumnStatisticsState` enum with values STARTING | RUNNING | SUCCEEDED | FAILED | STOPPED. The run is a Glue-managed computation over the objects behind the table's StorageDescriptor.Location: for a well-formed EXTERNAL_TABLE whose Role grants s3:GetObject/s3:ListBucket on that location, the run transitions STARTING -> RUNNING -> SUCCEEDED, `ErrorMessage` is absent, and the computed statistics then become readable through `GetColumnStatisticsForTable` (`ColumnStatisticsList[].StatisticsData.LongColumnStatisticsData` with `MinimumValue`, `MaximumValue`, and the @required `NumberOfNulls` and `NumberOfDistinctValues`, with `ColumnType` "long" for a bigint column, and `Errors` empty). FAILED with an ErrorMessage is reserved for a run that genuinely could not compute — a missing location, an unreadable object, a role without access. Recorded behaviour confirms SUCCEEDED and exact statistics for a 9-row CSV (5 distinct ids, 2 null rows).
Emulator: the run is recorded, but the handler deliberately owes it the modelled FAILURE status: `services/service-com-amazonaws-glue-awsglue/src/ops/start_column_statistics_task_run.rs` (module doc, lines 10-17) settles the run after `crate::state::COLUMN_STATISTICS_TASK_RUN_SETTLES_AFTER` into FAILED carrying `crate::state::COLUMN_STATISTICS_TASK_RUN_NOT_EXECUTED_MESSAGE`. GetColumnStatisticsTaskRun therefore reports `'Status': 'FAILED'` with `'ErrorMessage': "This emulator records column statistics task runs but reads none of the table's underlying data, so the run ended without generating statistics."`, and `'SampleSize': 0.0`, `'NumberOfWorkers': 0`, `'DPUSeconds': 0.0`. No statistics are ever produced, so GetColumnStatisticsForTable has nothing to return. The ErrorMessage text is itself a divergence: it is emulator-authored prose, not any message AWS emits for this operation.
Why: a client that starts a statistics task and waits for a terminal state sees a terminal FAILED and concludes its table or its role is broken, when neither is. Anything that gates on statistics — cost-based planning, Athena/Spark optimiser input, data-quality pipelines, operator dashboards — either aborts or silently proceeds without statistics. A caller that retries on FAILED retries forever. Because the FAILED verdict is unconditional, no test of the genuine failure classes (unreadable location, denied role) can ever be distinguished from the healthy path.
Fix: the StartColumnStatisticsTaskRun / GetColumnStatisticsTaskRun state machine and the catalog's column-statistics state. The run must read the objects under the table's StorageDescriptor.Location, aggregate the requested columns, persist the resulting ColumnStatistics so GetColumnStatisticsForTable returns them, and settle the run to SUCCEEDED with no ErrorMessage; FAILED must be reserved for a real computation failure and must carry a message AWS actually emits.
Traces: glue.column-statistics-task-run-reaches-terminal-state (mismatch: assertion `final["Status"] == "SUCCEEDED"` saw Status FAILED); glue__s3.glue-column-statistics-computed-from-real-data-match-the-known-distribution (mismatch: `the statistics task ended 'FAILED'`, so the check never reached its assertions on MinimumValue/MaximumValue/NumberOfNulls/NumberOfDistinctValues/ColumnType). Handler: services/service-com-amazonaws-glue-awsglue/src/ops/start_column_statistics_task_run.rs lines 10-17 and 240-259.

=== Cause 2 of 2: CreateColumnStatisticsTaskSettings answers NotImplemented, so the in-flight-run conflict is never refused ===
AWS: Smithy (com.amazonaws.glue) — `CreateColumnStatisticsTaskSettings` (input DatabaseName/TableName/Role @required, plus Schedule, ColumnNameList, SampleSize, CatalogID, SecurityConfiguration, Tags; empty output) models `ColumnStatisticsTaskRunningException`, documented as "An exception thrown when you try to start another job while running a column stats generation job" (client error, HTTP 400). When a column-statistics task run for that same table is in flight, the call is refused with error code `ColumnStatisticsTaskRunningException`; the recorded message is the fixed text "Column statistics task for input table has already started" (no variable parts). The refusal persists nothing, so a following `GetColumnStatisticsTaskSettings` for that DatabaseName/TableName is refused with `EntityNotFoundException` and the fixed message "ColumnStatisticsTaskSettings entry for input DatabaseName and TableName does not exist". Once the run has drained to a terminal state, the same create (with a Schedule) succeeds and GetColumnStatisticsTaskSettings round-trips the submitted `Role`.
Emulator: the call is refused with error code `NotImplemented` and the message "operation CreateColumnStatisticsTaskSettings is scaffolded but not implemented in this emulator" — an unmodelled code for this operation. The replayed check's assertion `code == "ColumnStatisticsTaskRunningException"` failed with `NotImplemented`.
Why: `NotImplemented` is not in this operation's modelled error set, so SDK error handling never dispatches to the ColumnStatisticsTaskRunningException branch and a client cannot tell a transient conflict (retry after the run drains) from an unsupported API (give up). The whole settings surface — scheduled statistics refresh — is unreachable, and the conflict invariant that stops a schedule being written over an active run is unenforced in either direction.
Fix: the CreateColumnStatisticsTaskSettings handler and its validation — reject with ColumnStatisticsTaskRunningException and its fixed message while a run for that catalog/database/table is in flight, persist nothing on that refusal, and on success store the settings so GetColumnStatisticsTaskSettings returns them (and 404s with its own fixed message when absent).
Traces: glue.create-column-statistics-task-settings-while-running-rejected (mismatch: AssertionError NotImplemented at the `code == "ColumnStatisticsTaskRunningException"` assertion). Handler: services/service-com-amazonaws-glue-awsglue/src/ops/create_column_statistics_task_settings.rs.

## Evidence
Cause 1 of 2 — glue.column-statistics-task-run-reaches-terminal-state

Actual (emulator): AssertionError: column statistics task run on a well-formed table with a correctly-scoped role should succeed, not merely reach a terminal state: {... 'ColumnNameList': ['id'], 'SampleSize': 0.0, 'NumberOfWorkers': 0, 'ComputationType': 'FULL', 'Status': 'FAILED', ... (The ids, names, role ARN and timestamps in that dict are per-run values; the requirement is Status == SUCCEEDED and no ErrorMessage.)

Cause 1 of 2 — glue__s3.glue-column-statistics-computed-from-real-data-match-the-known-distribution

## Steps to Reproduce
Cause 1 of 2:
1. s3.create_bucket and put_object a small CSV under a prefix, e.g. key "stats/rows.csv" with a header row and a bigint-valued column containing both repeated values and empty (null) cells.
2. iam.create_role with a glue.amazonaws.com trust policy and an inline policy allowing s3:GetObject/s3:PutObject/s3:ListBucket on that bucket and its objects.
3. glue.create_database, then glue.create_table with TableType EXTERNAL_TABLE, StorageDescriptor.Location s3://<bucket>/stats/, TextInputFormat/LazySimpleSerDe and Parameters {"skip.header.line.count": "1"}.
4. glue.start_column_statistics_task_run(DatabaseName, TableName, Role=<role arn>, ColumnNameList=["id"]) and capture ColumnStatisticsTaskRunId.
5. Poll glue.get_column_statistics_task_run(ColumnStatisticsTaskRunId) until Status is not STARTING/RUNNING.
   -> Emulator: Status "FAILED" with the emulator-authored ErrorMessage. AWS: "SUCCEEDED", no ErrorMessage.
6. glue.get_column_statistics_for_table(DatabaseName, TableName, ColumnNames=["id"]).
   -> AWS: Errors empty and one LongColumnStatisticsData entry whose MinimumValue/MaximumValue/NumberOfNulls/NumberOfDistinctValues equal the uploaded distribution, ColumnType "long". Emulator: no statistics were ever computed.
Replay: glue.column-statistics-task-run-reaches-terminal-state, glue__s3.glue-column-statistics-computed-from-real-data-match-the-known-distribution

Cause 2 of 2:
1. Same bucket/role/database/table setup (a single string column suffices).
2. glue.start_column_statistics_task_run(DatabaseName, TableName, Role, ColumnNameList=["col1"]) and confirm via get_column_statistics_task_run that the run is STARTING/RUNNING.
3. While that run is in flight, call glue.create_column_statistics_task_settings(DatabaseName, TableName, Role) with no Schedule.
