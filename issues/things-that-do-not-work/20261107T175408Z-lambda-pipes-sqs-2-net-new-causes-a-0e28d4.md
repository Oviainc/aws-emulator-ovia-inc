# lambda__pipes__sqs: 2 net-new causes — a RUNNING SQS-sourced pipe never invokes its Lambda target (11 checks), and a pipe whose role cannot read the source settles RUNNING with an empty StateReason

> _Note: this issue was identified against the code base at commit `c98f49a3ab045fe250f88b9f8f7e4420d8205746`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePipe

## Description
Two distinct root causes in the EventBridge Pipes data plane as exercised with an SQS source and a Lambda target. This issue carries 2 causes; both must be closed before submitting.

Cause 1 of 2: a pipe in CurrentState RUNNING with an SQS source and a Lambda target never consumes from the source queue and never invokes the target function.
AWS: Smithy (services/service-com-amazonaws-pipes-pipes/smithy-model/com-amazonaws-pipes-pipes.json) models CreatePipe with required Source (ArnOrUrl), Target (Arn), RoleArn, plus SourceParameters.SqsQueueParameters (BatchSize) and TargetParameters.LambdaFunctionParameters (InvocationType), and DescribePipe.CurrentState of the PipeState enum [RUNNING, STOPPED, CREATING, UPDATING, DELETING, STARTING, STOPPING, CREATE_FAILED, UPDATE_FAILED, START_FAILED, STOP_FAILED, DELETE_FAILED, CREATE_ROLLBACK_FAILED, DELETE_ROLLBACK_FAILED, UPDATE_ROLLBACK_FAILED]. The model describes no runtime, so this is recorded behavior only: on AWS, once DescribePipe reports CurrentState=RUNNING the pipe polls the SQS source, hands each batch (sized by SqsQueueParameters.BatchSize) to the Lambda target as a list of SQS record envelopes, and deletes the successfully handled source messages, so GetQueueAttributes ApproximateNumberOfMessages on the source returns to "0". FilterCriteria admit the matching records and drop the rest; a FIFO source preserves per-MessageGroupId order; BatchSize caps how many records arrive per invocation.
Emulator: CreatePipe/StartPipe succeed and DescribePipe reports CurrentState=RUNNING, but nothing is ever consumed and the target function is never invoked. Every delivery probe observes the empty set for the whole poll window: "expected message body 'payload-<pipe-name>' to be delivered to the Lambda target via the pipe"; "positive control: pipe must deliver while RUNNING"; "delivery of pre-update message to target A not met within 90s; last observed: []"; "matching message was never delivered to the target"; "positive-control pipe delivery not met within 150.0s. Last result: None"; "delivery of marker <marker> to result queue not met within 150.0s. Last result: None"; "all 5 bodies delivered to results queue for pipe <name> not met within 90s. Last result: set()"; "matching message was never delivered to the Lambda target"; "positive control delivery of 'ok-<name>' to results queue not met within 60s. Last result: []"; "condition not met within 60s (last=0)" (FIFO ordering probe); "poll timed out after 60s without satisfying predicate; last observed: []". The names, markers and ids in those strings are per-run values; the requirement is that the poll observes the delivered record, not those literals.
Why: a client that wires SQS -> Pipe -> Lambda — by SDK, by `aws pipes create-pipe`, or by a CloudFormation stack — sees a healthy RUNNING pipe and never receives an event. Nothing surfaces the fault: no state change, no StateReason, no error on any call. Source messages also pile up instead of being deleted, so a consumer reading ApproximateNumberOfMessages concludes the backlog is never drained. Batch sizing, filter criteria and FIFO ordering are all unverifiable because the zeroth record never arrives.
Fix: the pipes crate's pipe runtime — the component that must poll an SQS source for a pipe in RUNNING, apply SourceParameters.FilterCriteria, build the SQS record envelope batch per SqsQueueParameters.BatchSize, invoke the Lambda target with TargetParameters.LambdaFunctionParameters.InvocationType, and delete the consumed source messages on success. Cause 2 of 2: a pipe whose execution role grants no read on its SQS source stays in CurrentState RUNNING with StateReason empty, instead of settling in a failed/stopped state carrying a reason.
AWS: Smithy models DescribePipe.StateReason as PipeStateReason (@length min 0 max 512) alongside CurrentState of the PipeState enum, which includes CREATE_FAILED, START_FAILED and STOPPED precisely so an unstartable pipe is observable. Recorded behavior: when the RoleArn cannot perform sqs:ReceiveMessage/sqs:DeleteMessage/sqs:GetQueueAttributes on the source, the pipe does not remain healthy — it settles in one of STOPPED / START_FAILED / CREATE_FAILED and DescribePipe returns a non-empty StateReason naming the denied source access. The fixed text is the reason AWS emits for a source-permission failure; the variable parts are the source ARN and the role ARN taken from the request.
Emulator: DescribePipe keeps reporting CurrentState='RUNNING' with StateReason='' indefinitely — "expected the pipe to self-disable due to missing source permissions, got state='RUNNING' reason=''".
Why: a client cannot detect a misconfigured execution role. The pipe advertises itself as healthy forever, so deployment gates and operators that poll DescribePipe for CREATE_FAILED/START_FAILED plus StateReason wait out their timeout and then treat a permanently dead pipe as working.
Fix: the pipes crate's pipe lifecycle/state component — it must validate the execution role's source-read grant when a pipe starts, drive CurrentState into the failed/stopped state and populate StateReason. The open issue 20261104T213346Z-lambda-pipes-sqs-5-net-new-causes-an.md mentions source-permission failures not being reported; this check is not carried by it and is filed here.

## Steps to Reproduce
Cause 1: create an SQS queue and a Lambda function; create an IAM role granting sqs:ReceiveMessage/DeleteMessage/GetQueueAttributes on the queue and lambda:InvokeFunction on the function; CreatePipe (SDK, `aws pipes create-pipe`, or CloudFormation AWS::Pipes::Pipe) with Source=<queue arn>, SourceParameters={SqsQueueParameters:{BatchSize:1}}, Target=<function arn>, TargetParameters={LambdaFunctionParameters:{InvocationType:REQUEST_RESPONSE}}, DesiredState=RUNNING; poll DescribePipe until CurrentState=RUNNING; SendMessage to the source queue; observe the function is never invoked and GetQueueAttributes ApproximateNumberOfMessages on the source never returns to "0".

Cause 2: create the same pipe but with an execution role that grants NO sqs:* on the source queue; poll DescribePipe; observe CurrentState stays 'RUNNING' with StateReason '' instead of settling in STOPPED/START_FAILED/CREATE_FAILED with a reason.
