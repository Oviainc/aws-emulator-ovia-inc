# GuardDuty: IAM authorization is not enforced on CreateCustomDetectionRuleAssociation, and GetFilter/GetMalwareProtectionPlan not-found refusals use an invented ownership message

> _Note: this issue was identified against the code base at commit `0b9721afe99d360c98ec9e05a46069ffbe923470`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCustomDetectionRuleAssociation

## Description
This issue bundles 3 distinct root causes, all in the guardduty crate. Fix all 3 before submitting. None of the three failing checks below is marked owned by an existing open issue; where an open issue addresses a neighbouring operation it is named inline so the fixer can land the change in the shared code path rather than duplicating it.

Cause 1 of 3: CreateCustomDetectionRuleAssociation applies no authorization check, so a zero-permission principal reaches the handler.
AWS: Smithy CreateCustomDetectionRuleAssociation (POST /custom-detection-rule/association; RuleId required, pattern ^[a-z0-9]+(-[a-z0-9]+)*$, Mode required) models AccessDeniedException with httpError 403 alongside ResourceNotFoundException 404. Recorded behavior: when the call is signed with freshly-minted IAM user credentials that have NO attached policy, GuardDuty refuses it with AccessDeniedException BEFORE any resource lookup, using IAM's standard no-identity-based-policy template: fixed text 'User: ', then the caller's principal ARN (arn:aws:iam::<account>:user/<user-name>), then ' is not authorized to perform: ', then the action ('guardduty:CreateCustomDetectionRuleAssociation'), then ' on resource: ', then the target resource ARN (arn:aws:guardduty:<region>:<account>:detection-rule/custom/<RuleId>/association/*), then ' because no identity-based policy allows the ' + action + ' action'. Every variable part (account, user name, region, RuleId) comes from the request's credentials and parameters; only the connective text is fixed. The authorization decision precedes existence checking: the identical call made by a fully-permissioned caller is refused ResourceNotFoundException with 'Rule not found: <RuleId>' instead, and the emulator already matches that permissioned path (that assertion passed).
Emulator: the unauthenticated-to-anything caller gets the SAME answer as the admin — ResourceNotFoundException ('Rule not found: <RuleId>'), i.e. the request was evaluated on resource existence only and no permission check ran at all.
Why: a client that asserts a least-privilege boundary ('this principal must NOT be able to associate a detection rule') passes against the emulator and fails against AWS; and because the refusal is 404 rather than 403, error-handling code routes the caller into a create-the-rule retry instead of surfacing an entitlement failure. Clients and audits cannot distinguish 'you may not do this' from 'that rule does not exist'.
Fix: the per-operation permission check that must run before the CreateCustomDetectionRuleAssociation handler performs its RuleId lookup, in the guardduty crate (services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/create_custom_detection_rule_association.rs and the shared auth layer it must call). Open issue 20261029T183757Z-guardduty-performs-no-authorization-identity-policy-deny-is.md reports the same absent authorization for CreateInvestigation/UpdateIPSet/GetCustomDetectionRule and for the org-configuration delegated-admin gate; it does NOT list this operation, and the zero-permission (no-policy) path and its distinct message template are additional to that issue's explicit-Deny template, so this operation must be covered too — ideally by the same shared auth layer.
Traces: guardduty.create-custom-detection-rule-association-without-permission-denied.

Cause 2 of 3: GetFilter on a filter name that does not exist reports an account-ownership error instead of AWS's not-found text.
AWS: Smithy GetFilter (GET /detector/{DetectorId}/filter/{FilterName}; both httpLabel and required; modeled errors BadRequestException httpError 400, InternalServerErrorException 500). Recorded behavior: reading a FilterName that does not exist under the detector — here a name whose CreateFilter was correctly rejected for an out-of-range Rank, so no filter was ever created — is refused HTTP 400 BadRequestException with the wholly fixed text 'The request is rejected since no such resource found.' There is no variable part: the filter name is NOT interpolated.
Emulator: HTTP 400 / BadRequestException matches, but the message is 'The request is rejected because the input filterName is not owned by the current account.' — a message AWS never emits, which additionally asserts an ownership distinction AWS does not make here.
Why: the effect-absent probe every client uses after a rejected or deleted create ('is there a filter under this name?') is answered with a claim that the name belongs to another account, so callers that branch on the documented not-found wording mis-classify their own absent filters and cross-account diagnosis fires spuriously.
Fix: the not-found path of the GetFilter handler / the shared error constructor it calls in the guardduty crate (services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/get_filter.rs). Open issue 20261029T183757Z-guardduty-resource-not-found-rejections-across-guardduty-are-reported.md describes this same wording defect for the filter family (its Cause 2) from other checks; this check is a further, unowned instance that the same correction must cover — re-replay it after fixing.
Traces: guardduty.filter-rank-out-of-range-rejected.

Cause 3 of 3: GetMalwareProtectionPlan on a deleted plan id reports an account-ownership error instead of AWS's not-found text.
AWS: Smithy GetMalwareProtectionPlan (GET /malware-protection-plan/{MalwareProtectionPlanId}; MalwareProtectionPlanId httpLabel, required; modeled errors ResourceNotFoundException httpError 404, BadRequestException 400, AccessDeniedException 403, InternalServerErrorException 500). Recorded behavior: after DeleteMalwareProtectionPlan, reading the same id is refused ResourceNotFoundException with the fixed text 'The request was rejected because the specified malware protection plan was not found.' — no variable part; the plan id is not interpolated, and AWS deliberately collapses absent and foreign plans into this one wording so plan ids are not probeable.
Emulator: the error CODE ResourceNotFoundException matches, but the message is 'The request is rejected because the input malwareProtectionPlanId is not owned by the current account.' — discloses an ownership distinction AWS hides and does not match the documented text.
Why: a client confirming that a delete took effect (and then re-creating the plan for the same bucket, as the conflict-tracking lifecycle requires) gets wording AWS never emits, so parity assertions and operator runbooks keyed to the real text fail, and the message implies someone else's account owns an id the caller just deleted.
Fix: the not-found path of the GetMalwareProtectionPlan handler / the shared error constructor it calls in the guardduty crate (services/service-com-amazonaws-guardduty-guarddutyapiservice/src/ops/get_malware_protection_plan.rs). The same open issue 20261029T183757Z-guardduty-resource-not-found-rejections-across-guardduty-are-reported.md reports this wording for the malware-protection-plan family (its Cause 4) from the lifecycle and cross-account checks; this check is a further, unowned instance reached through the duplicate-conflict/restore path.
Traces: guardduty.create-malware-protection-plan-duplicate-conflict.
