Five net-new DescribeInstanceTypes divergence clusters, all driven by the same defect: the instance-type catalog the emulator serves is synthesized (values derived from the type's family/size, with optional sub-structures simply absent) rather than carrying AWS's per-type attribute data. Each cause below is a distinct replay cluster with its own fixture and step and must be re-replayed separately.

Scope note for the fixer: this replay reports 82 net-new (unowned, non-stub) DescribeInstanceTypes clusters spread over the ec2-catalog-describe-instance-types-* fixtures; the five named here are the bindings this issue carries. Open issues 20261107T204938Z-ec2-describeinstancetypes-pages-c9gd-m6gd-m6i-r4-r5.md, 20261107T184734Z-ec2-describeinstancetypes-instance-type-catalog-returns-wrong-and.md, 20261106T142039Z-ec2-describeinstancetypes-catalog-pages-still-diverge-per-instance-type.md, 20261106T122956Z-ec2-instance-type-catalog-pages-a1-c9g-through.md and 20261106T072955Z-ec2-describeinstancetypes-serves-an-emulator-authored-instance-type.md describe the same area but do not carry these replay keys, so these clusters are still failing and unowned. A fix that only makes these five green will leave the rest of that family red: the table has to be sourced from AWS per-type data, not patched per failing step.

AWS: Smithy: DescribeInstanceTypes returns one InstanceTypeInfo per requested type (ebsInfo with ebsOptimizedInfo, gpuInfo, networkInfo with networkCards / efaInfo / connectionTrackingConfiguration, processorInfo, vCpuInfo with validCores, instanceStorageInfo, and the per-type flags). The model fixes the shape but not the values, so each type's attribute values are recorded behavior only and the recording is the authority: every attribute AWS publishes for a type must be present with AWS's value, and a sub-structure a type has (gpuInfo for a GPU type, efaInfo for an EFA type, instanceStorageInfo for an instance-store type) must be emitted.
Emulator: for each requested type it returns a record whose numbers are derived from the type name rather than looked up (identical ebsOptimizedInfo baselines across unrelated families, a size-scaled memoryInfo.sizeInMiB, a fixed maximumEbsAttachments), inverts per-type flags (currentGeneration, dedicatedHostsSupported, instanceStorageSupported, autoRecoverySupported, encryptionInTransitSupported, ebsInfo.attachmentLimitType, ebsInfo.encryptionSupport), and omits whole sub-structures and members (gpuInfo, networkInfo.efaInfo, networkInfo.networkCards, networkInfo.connectionTrackingConfiguration, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.secondaryNetworkSupported, networkInfo.trafficMirroringSupport, cpuBurstModel, phcSupport, rebootMigrationSupport, vCpuInfo.validCores).
Why: DescribeInstanceTypes is the authority clients use to choose an instance type and to size things off it. Against the emulator a capacity planner sees no GPUs on a GPU type, wrong memory for a type whose memory it budgets against, wrong EBS bandwidth/IOPS baselines, a current-generation flag inverted, and absent capability flags — so selection logic, EFA/GPU gating and attachment-limit arithmetic all come out wrong, silently, with a 200 response.
Fix: the static instance-type catalog data that backs the DescribeInstanceTypes handler (the emulator's instance-type table and the projection that serializes it) — populate it from AWS's per-type attribute data instead of deriving values from the type name, and emit the optional sub-structures and per-type flags for the types that have them.

Cause 1 of 5: fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#8 — the g5 family. gpuInfo absent for every g5 size (AWS publishes gpus with count/manufacturer/memoryInfo/name plus totalGpuMemoryInMiB), cpuBurstModel absent, currentGeneration and dedicatedHostsSupported inverted, every ebsOptimizedInfo baseline/maximum bandwidth-IOPS-throughput wrong, maximumEbsAttachments wrong, networkInfo.efaInfo / efaSupported / enaSrdSupported / flexibleEnaQueuesSupport / networkCards / networkPerformance / maximumNetworkCards absent or wrong, processorInfo.manufacturer and sustainedClockSpeedInGhz wrong, instanceStorageInfo disk count/size wrong.
Cause 2 of 5: fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#9 — the g5g family. autoRecoverySupported and instanceStorageSupported inverted, memoryInfo.sizeInMiB roughly doubled, gpuInfo (T4g) absent, dedicatedHostsSupported inverted, ebsOptimizedInfo values and maximumEbsAttachments wrong.
Cause 3 of 5: fixture ec2-catalog-describe-instance-types-c9gd-m6gd, step task#34 — the m4 family. ebsInfo.attachmentLimitType reported dedicated where AWS reports shared, networkInfo.connectionTrackingConfiguration absent, vCpuInfo.validCores entries absent, currentGeneration inverted, ebsOptimizedInfo baselines and maximumEbsAttachments wrong.
Cause 4 of 5: fixture ec2-catalog-describe-instance-types-m6i-r4, step task#44 — the r4 family. memoryInfo.sizeInMiB wrong, currentGeneration inverted, attachmentLimitType wrong, ebsOptimizedInfo bandwidth/throughput wrong, maximumEbsAttachments wrong, networkInfo.connectionTrackingConfiguration / defaultNetworkCardIndex / enaSrdSupported absent.
Cause 5 of 5: fixture ec2-catalog-describe-instance-types-r5-r8in, step task#5 — the r5d family. networkInfo.networkCards, networkPerformance, maximumNetworkCards, defaultNetworkCardIndex, secondaryNetworkSupported, trafficMirroringSupport, enaSrdSupported and flexibleEnaQueuesSupport absent, phcSupport and cpuBurstModel absent, maximumEbsAttachments and processorInfo.sustainedClockSpeedInGhz wrong.

Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#8, ec2-catalog-describe-instance-types-c9gd-m6gd#task#9, ec2-catalog-describe-instance-types-c9gd-m6gd#task#34, ec2-catalog-describe-instance-types-m6i-r4#task#44, ec2-catalog-describe-instance-types-r5-r8in#task#5.
