=== Cause 1 of 5: credentials minted from a role that has since been DELETED still resolve to a live principal, and are refused at the AUTHORIZATION stage instead of at credential resolution ===
AWS: a temporary session's identity is the role's RoleId, not its name (Smithy: com.amazonaws.sts#AssumeRole -> AssumeRoleResponse.Credentials + AssumedRoleUser; the credential-resolution ordering itself is recorded behavior only — no modeled member carries it). Once the role is deleted, the AccessKeyId in that session resolves to no principal, so the called service refuses BEFORE any policy is consulted: S3 answers HTTP 403, error code `InvalidAccessKeyId`, message `The AWS Access Key Id you provided does not exist in our records.` — that sentence is entirely FIXED text and carries no request or state values. Recreating the role under the same name with byte-identical trust and inline policies does NOT revive the old session (new RoleId, identical ARN), while a session assumed from the recreated role reads normally.
Emulator: the call is refused, but with code `AccessDenied` — the authorization-stage verdict — so the dead key is still being resolved to a live principal and only the grant is judged missing. The check's own words: "a session issued from a role that has since been deleted must be rejected with InvalidAccessKeyId -- at credential resolution, before any policy is consulted; got 'AccessDenied'".
Why: the two codes mean opposite things to a client. `InvalidAccessKeyId` is terminal and tells an SDK credential provider to stop using and refresh the credential; `AccessDenied` reads as a policy problem on a credential still believed valid, so retry/refresh logic keeps a dead (possibly leaked) session in rotation and an operator hunting a permissions bug never learns the role is gone. It also hides the role-identity-is-the-RoleId guarantee: a by-name recreation would look like it restored access.
Fix: the credential-resolution step shared by the data-plane handlers (the resolve-the-signing-identity path for session credentials) — a session whose role no longer exists, or whose recorded RoleId no longer matches the role now at that ARN, must FAIL resolution, and the called service must serialize HTTP 403 / `InvalidAccessKeyId` / the fixed sentence above ahead of any policy evaluation. The revocation hook belongs on IAM's DeleteRole side of the shared session directory.

=== Cause 2 of 5: a refusal decided by a MATCHED explicit Deny is worded with the implicit-deny (no-grant) clause, and the deciding policy SOURCE is never named ===
AWS: recorded behavior only for the message framing (no modeled error member carries it; S3 serializes `AccessDenied` with HTTP 403). AWS words an authorization refusal with one of three mutually exclusive diagnoses, and the trailing clause IS the diagnosis: ` with an explicit deny in an identity-based policy` when a Deny statement in an inline/attached role or user document decided it; ` with an explicit deny in a session policy` when the deciding Deny came from the session policy passed in `Policy=` (Smithy: GetFederationToken.Policy -> sessionPolicyDocumentType @length 1..2048, AssumeRole.Policy -> unrestrictedSessionPolicyDocumentType); and ` because no identity-based policy allows the <action> action` ONLY when nothing granted the action. Fixed text: `User: `, ` is not authorized to perform: `, ` on resource: `, the double quotes around the resource ARN, and the chosen trailing clause. Variable parts, all taken from the request and state: the caller ARN (`arn:aws:sts::<account>:assumed-role/<role>/<session>` or `arn:aws:sts::<account>:federated-user/<name>`), the action (`s3:GetObject`), and the object ARN built from the request. Unicode in the resource is immaterial — a Deny whose Resource ARN carries accented-Latin/CJK key bytes must match that exact key and leave a sibling ASCII key readable.
Emulator: status (403) and code (`AccessDenied`) are right and the refusal does arrive, but the message ALWAYS ends `because no identity-based policy allows the s3:GetObject action`, for both deciding sources. Observed on (a) a GetFederationToken session policy of [Allow s3:GetObject on `arn:aws:s3:::<bucket>/*`, Deny s3:GetObject on `arn:aws:s3:::<bucket>/café/日本語/Zürich-résumé.txt`] — the expected tail is ` with an explicit deny in a session policy`; and (b) an inline ROLE policy Deny `*`/`*` under `DateLessThan {aws:TokenIssueTime: <cut-off>}` (the AWSRevokeOlderSessions shape) refusing an already-issued session — the expected tail is ` with an explicit deny in an identity-based policy`. Caller ARN, action and quoted resource ARN all match in both legs; only the diagnosis clause, and with it the policy source, diverges.
Why: that clause is the whole remediation signal. Told "no identity-based policy allows" the action, a caller hunts a missing Allow that is already present and never finds the Deny it must satisfy; policy-troubleshooting flows and log alerts keyed on AWS's three forms draw the opposite conclusion, and a client can no longer distinguish an explicit deny from an un-granted action, nor a session-policy deny from an identity-policy one.
Fix: the refusal-message construction in the request-authorization gate shared by the data-plane handlers — the evaluation already knows which statement decided the request and which document it came from, so the message must carry that: emit the explicit-deny clause (identity-based vs session-policy form) when a Deny decided it, and reserve the `because no identity-based policy allows the <action> action` form for the genuine no-grant case. Adjacent OPEN issue, which does not carry these ids: 20261106T072814Z-iam-s3-sts-2-root-causes-an-aws.md (same classification defect reported for the identity-policy form under the `iam__s3__sts` heading).
Traces: sts.get-federation-token-policy-document-unicode-round-trip (session-policy form), sts.in-flight-session-denied-after-a-revoke-older-sessions-policy-is-attached-to-the-role (identity-policy form).

=== Cause 3 of 5: a chained AssumeRole refused by an unsatisfied sts:SourceIdentity trust condition names sts:AssumeRole as the action instead of sts:SetSourceIdentity ===
AWS: SourceIdentity carries over a role chain (Smithy: AssumeRoleRequest.SourceIdentity -> sourceIdentityType @length 2..64 @pattern `^[\w+=,.@-]*$`, echoed back as AssumeRoleResponse.SourceIdentity). When the next role's trust policy conditions on `sts:SourceIdentity` and the calling session's carried value does not satisfy it, the refusal is `AccessDenied`/403 naming the SetSourceIdentity action, not AssumeRole: `User: <calling session ARN> is not authorized to perform: sts:SetSourceIdentity on resource: <target role ARN>` (ref: https://docs.aws.amazon.com/IAM/latest/UserGuide/id_credentials_temp_control-access_monitor.html). Fixed text: `User: `, ` is not authorized to perform: sts:SetSourceIdentity on resource: `; variable parts: the calling assumed-role session ARN and the target role ARN, both from the request/state. Recorded behavior for the exact sentence; the action name is what AWS uses because the condition gates the source-identity SET, not the assume itself.
Emulator: same status and code, but the message names the wrong action — `User: arn:aws:sts::<account>:assumed-role/<roleA>/<session> is not authorized to perform: sts:AssumeRole on resource: arn:aws:iam::<account>:role/<roleB>`. The neighbouring legs pass (a conflicting SourceIdentity mid-chain is ValidationError with `The source identity is already set for this assume role session`, and the code here is AccessDenied), so only the action token diverges.
Why: a caller debugging a source-identity guardrail is told the principal cannot assume the role at all and goes looking at the AssumeRole statement in the trust policy, when the blocked permission is the sts:SetSourceIdentity grant/condition; audit and log-scraping flows that key on the action in the refusal attribute the denial to the wrong permission entirely.
Fix: the AssumeRole handler's trust-policy evaluation and its refusal-message construction — when the deciding statement is the one gating `sts:SetSourceIdentity` (a trust-policy condition on `sts:SourceIdentity` the carried value fails), the message's action must be `sts:SetSourceIdentity`.
Traces: sts.role-chain-with-a-conflicting-source-identity-denied-and-the-matching-one-permitted.

=== Cause 4 of 5: aws:PrincipalArn is not published in the data-plane request context for an assumed-role session, so an Allow conditioned on the ROLE arn never grants and the check never converges ===
AWS: for an AssumeRole session, `aws:PrincipalArn` is the ROLE arn (`arn:aws:iam::<account>:role/<roleName>`), NOT the session arn GetCallerIdentity reports (`arn:aws:sts::<account>:assumed-role/<roleName>/<sessionName>`); the key is always present in the request context, so a StringEquals clause over it is always decided. Consequently: an inline role policy whose ONLY Allow of s3:GetObject is conditioned on `StringEquals {aws:PrincipalArn: <session arn>}` does not match, and both GetObject and HeadObject on the object are refused (GetObject: 403 `AccessDenied` with the no-grant form `User: <session arn> is not authorized to perform: s3:GetObject on resource: "<object arn>" because no identity-based policy allows the s3:GetObject action` — fixed text plus the session arn, action and object ARN from the request; HeadObject carries no body, so the refusal is bare HTTP 403). Switching the SAME condition's value to the role arn, changing nothing else, makes the identical GetObject succeed and return the object bytes. Recorded behavior only for the key's value (the Smithy model declares no condition keys).
Emulator: the check never completes — "Check timed out after 60.0s" — so one of its bounded polls never observed the transition. Hypothesis (the emulator's observable responses are what the report records; the mechanism is inferred): the data-plane authorizer for session credentials does not publish `aws:PrincipalArn` at all (or publishes the SESSION arn), and by this tree's documented rule a clause over an undetermined key is left undecided and withholds the grant — so the role-arn leg's poll for the read to become permitted (interval 3 s, cap 240 s) can never converge, and the run is cut at the 60 s harness cap. Either way the behavioral requirement is the one above: the role-arn form grants and the session-arn form does not.
Why: `aws:PrincipalArn` is the standard way to pin a permission to one role, and the role-arn-not-session-arn rule is exactly what makes such a policy stable across sessions. Here policies written that way never grant, so a correct least-privilege design is dead in the emulator — and a client cannot tell that from an outage, because no response ever arrives for the call.
Fix: the request-context construction in the data-plane authorization gate (the shared evaluator's input for a temporary-session principal) must publish `aws:PrincipalArn` for session credentials, valued with the ROLE arn, so StringEquals over it is decided in both directions.
Traces: sts.principal-arn-condition-resolves-to-the-role-arn-not-the-session-arn.

=== Cause 5 of 5: aws:TokenIssueTime is not published in the data-plane request context, so a `Null` clause over it is undecided and neither half of one identity gets its documented outcome ===
AWS: `aws:TokenIssueTime` is present in the request context ONLY for temporary credentials, so `Condition {"Null": {"aws:TokenIssueTime": "true"}}` (key absent) admits an IAM user's long-term access key and refuses that same user's GetSessionToken credentials, and flipping the value to `"false"` reverses both outcomes exactly. The refused call is 403 `AccessDenied` (GetObject) / bare 403 `Forbidden` (HeadObject), and the permitted call returns the object bytes; both callers are the SAME principal — identical GetCallerIdentity Arn, UserId and Account (Smithy: GetSessionToken returns Credentials with a SessionToken, which is what makes the temporary half temporary). Recorded behavior only for the key's presence rule (the model declares no condition keys).
Emulator: the check never completes — "Check timed out after 60.0s". Hypothesis (mechanism inferred; the recorded symptom is the absent transition): `aws:TokenIssueTime` is never published in the data-plane request context, and a clause over an undetermined key is left undecided and withholds the grant, so the `Null=true` leg's positive-control poll (the long-term key reading, interval 3 s, cap 240 s) and/or the `Null=false` leg's poll (the session credentials becoming permitted) never converge and the run is cut at the 60 s cap. The requirement is the symmetric pair of outcomes above, not one recording's values.
Why: this key is the documented way to distinguish long-term from temporary credentials, and the basis of the whole aws:TokenIssueTime family (including the AWSRevokeOlderSessions `DateLessThan` shape in Cause 2). With the key unpublished, such a policy is unsatisfiable in one direction and silently un-enforced in the other, and the caller sees no response at all rather than a verdict.
Fix: the same request-context construction as Cause 4 — publish `aws:TokenIssueTime` for temporary-session credentials (and leave it genuinely ABSENT for long-term IAM-user keys, which is what makes `Null` decidable), so `Null` and the date operators over it are evaluated by the shared evaluator instead of withholding the grant.
Traces: sts.token-issue-time-is-present-only-for-the-temporary-half-of-one-identity.
