## Description
Eight distinct net-new root causes in the SageMaker training/transform data plane, all observed against S3-backed jobs. None of them is covered by an open issue the report marks as OWNING these checks; the nearest open issues (20261029T211510Z-s3-sagemaker-sagemaker-jobs-never-execute-and-are-never-validated.md, 20261030T171442Z-sagemaker-server-side-job-execution-is-absent-training.md, 20261022T210606Z-sagemaker-accepts-requests-real-aws-refuses-no-s3.md, 20261029T203709Z-s3-sagemaker-training-jobs-never-execute-no-model.md) describe jobs that end Failed with a no-container-runtime reason; the checks below now observe jobs that COMPLETE and report fabricated results, which is a different defect and is what each cause describes. A fixer must close all eight before submitting.

=== Cause 1 of 8: CreateTrainingJob's missing-s3:ListBucket refusal message stops after the first sentence ===
AWS: Smithy (services/service-com-amazonaws-sagemaker-sagemaker/smithy-model/com-amazonaws-sagemaker-sagemaker.json) models CreateTrainingJob with client error ResourceNotFound/ResourceInUse/ResourceLimitExceeded only; the input-channel accessibility refusal is a 400 ValidationException whose text is recorded behavior. For a role that cannot list the input bucket, AWS answers HTTP 400, code ValidationException, with this message template — fixed text verbatim, variable parts taken from the request and from IAM/S3 state (the channel's S3Uri, the region, the bucket, the RoleArn, the role's bare name, the account id):
  No S3 objects found under S3 URL "<S3Uri>" given in input data source. Please ensure that the bucket exists in the selected region (<region>), that objects exist under that S3 prefix, and that the role "<RoleArn>" has "s3:ListBucket" permissions on bucket "<bucket>". Error message from S3: User: arn:aws:sts::<account>:assumed-role/<role-name>/SageMaker is not authorized to perform: s3:ListBucket on resource: "arn:aws:s3:::<bucket>" because no identity-based policy allows the s3:ListBucket action
The second sentence ("Error message from S3: …") is part of the template whenever the listing was refused by authorization rather than merely empty; seven independent checks assert it.
Emulator: answers 400 ValidationException with only the first sentence, truncating everything from " Error message from S3:" onward.
Why: a client that classifies the refusal by matching/parsing the S3 authorization clause (to tell "prefix is empty" from "role may not list the bucket") cannot distinguish the two, and the operator-facing cause of the failure is lost.
Fix: the CreateTrainingJob handler's input-data-config validation, where this ValidationException message is composed.
Traces: s3__sagemaker.cfn-deploy-sagemaker-missing-s3-bucket-policy-negative, s3__sagemaker.cfn-deploy-sagemaker-role-missing-s3-trust-negative, s3__sagemaker.cli-sagemaker-missing-role-permission-negative, s3__sagemaker.cli-sagemaker-training-job-missing-s3-permission-error, s3__sagemaker.cli-sagemaker-training-job-missing-s3-permission-negative, s3__sagemaker.deploy-cfn-sagemaker-role-missing-s3-permission-negative, s3__sagemaker.sagemaker-training-job-missing-s3-read-permission-negative.

=== Cause 2 of 8: batch transform jobs are accepted but never perform inference, and settle Failed with an emulator-authored FailureReason ===
AWS: CreateTransformJob (modeled errors ResourceInUse/ResourceLimitExceeded/ResourceNotFound) is accepted and the job runs the model container over TransformInput, writing one <object>.out per input object under TransformOutput.S3OutputPath; DescribeTransformJob then reports TransformJobStatus=Completed with TransformStartTime/TransformEndTime and no FailureReason (recorded behavior; DescribeTransformJob models FailureReason only for Failed).
Emulator: every accepted transform job reaches TransformJobStatus=Failed with FailureReason "This emulator runs no model inference container, so no records were transformed and no output object was written to the job's S3OutputPath." — including the positive controls of permission-boundary checks, so no transform negative is measurable either.
Why: any client that waits for Completed and then reads the per-record output sees a terminal failure and a message that is not an AWS failure reason, so batch scoring pipelines cannot run at all.
Fix: the CreateTransformJob handler and its job-execution/state machine (transform-job state and the writer of the output objects).
Traces: s3__sagemaker.sagemaker-batch-transform-missing-role-permission-negative, s3__sagemaker.sagemaker-batch-transform-missing-s3-read-permission-negative, s3__sagemaker.sagemaker-batch-transform-nonexistent-s3-input-negative, s3__sagemaker.sagemaker-batch-transform-output-missing-s3-write-permission-negative, s3__sagemaker.sagemaker-batch-transform-reads-s3-input, s3__sagemaker.sagemaker-batch-transform-s3-input-positive, s3__sagemaker.sagemaker-batch-transform-s3-output-positive, s3__sagemaker.sagemaker-batch-transform-writes-s3-output.

=== Cause 3 of 8: CreateModel never checks that PrimaryContainer.ModelDataUrl exists or is readable by ExecutionRoleArn ===
AWS: CreateModel validates the model data at ModelDataUrl synchronously and refuses with HTTP 400 ValidationException before the model is registered (recorded behavior; the model does not appear in ListModels/DescribeModel afterwards). Two distinct messages, fixed text verbatim with the URL/role/region taken from the request:
  - object does not exist: Could not find model data at <ModelDataUrl>.
  - role cannot read it: Could not access model data at <ModelDataUrl>. Please ensure that the role "<ExecutionRoleArn>" exists and that its trust relationship policy allows the action "sts:AssumeRole" for the service principal "sagemaker.amazonaws.com". Also ensure that the role has "s3:GetObject" permissions and that the object is located in <region>. If your Model uses multiple models or uncompressed models, please ensure that the role has "s3:ListBucket" permission.
Emulator: accepts both calls with 200 and registers the model (the checks' else-branches fire: "CreateModel with a ModelDataUrl pointing at a nonexistent S3 object was expected to be rejected synchronously, but it was accepted" and "CreateModel with a role lacking S3 read access unexpectedly succeeded").
Why: a broken deployment is detected only much later (or never), and a client relying on CreateModel as the gate deploys an endpoint whose container has no artifact to load.
Fix: the CreateModel handler's validation of PrimaryContainer/Containers ModelDataUrl against S3 state and the execution role's effective permissions. Related open issue 20261022T210606Z-sagemaker-accepts-requests-real-aws-refuses-no-s3.md covers other CreateModel S3 negatives but not these two replay keys.
Traces: s3__sagemaker.cfn-deploy-sagemaker-endpoint-missing-s3-policy-negative, s3__sagemaker.sagemaker-create-model-nonexistent-s3-artifact-negative.

=== Cause 4 of 8: an S3 bucket policy that explicitly Denies the execution role is ignored, so the training job Completes ===
AWS: when the input bucket's policy carries an explicit Deny of s3:GetObject (or the role is otherwise not authorized to read the objects) the job that was accepted runs and then ends TrainingJobStatus=Failed with a FailureReason naming the S3 access failure (recorded behavior; DescribeTrainingJob.FailureReason is modeled for the Failed state).
Emulator: the job reaches TrainingJobStatus=Completed with FailureReason absent — "a training job whose role is explicitly Denied s3:GetObject by the bucket policy was expected to fail, got status 'Completed'" and "expected Failed when the bucket policy denies the role, got Completed, failure_reason=None".
Why: an authorization regression in a customer's bucket policy is invisible — the emulator reports success for a job that could not have read a byte of its input, so IAM/bucket-policy tests pass against a configuration real AWS fails.
Fix: the training-job execution path's S3 reads must evaluate the bucket policy and the execution role's effective permissions, and the job state machine must settle Failed with the S3 failure reason.
Traces: s3__sagemaker.sagemaker-execution-role-s3-bucket-policy-denies-access-negative, s3__sagemaker.sagemaker-training-job-s3-bucket-policy-blocks-access-negative.

=== Cause 5 of 8: the model artifact at ModelArtifacts.S3ModelArtifacts is fabricated, not the container's /opt/ml/model ===
AWS: Smithy documents ModelArtifacts.S3ModelArtifacts as "The path of the S3 object that contains the model artifacts… A SageMaker container stores your trained model artifacts in the /opt/ml/model directory. After training has completed, by default, these artifacts are uploaded to your Amazon S3 bucket as compressed files." So model.tar.gz contains exactly what the job's container wrote: a custom entrypoint that writes /opt/ml/model/artifact.txt yields a tar containing artifact.txt; the built-in XGBoost algorithm yields a tar containing xgboost-model.
Emulator: model.tar.gz contains a canned payload independent of the job — extracting the member the container wrote raises KeyError: "filename 'artifact.txt' not found", and for XGBoost jobs the archive holds only ['model.json'] ("expected the trained xgboost-model file in the artifact, got ['model.json']").
Why: a client that loads the artifact (unpacks it, reads its own files, or hands it to the inference container) gets a file that cannot be loaded and that contains none of the training output, so the whole train→package→deploy chain is unverifiable.
Fix: the training-job execution path that produces and uploads the artifact — it must archive the container's model directory instead of emitting a synthesized tar.
Traces: s3__sagemaker.cli-sagemaker-create-training-job-s3-input-workflow, s3__sagemaker.cli-sagemaker-invalid-s3-input-uri-negative, s3__sagemaker.sagemaker-training-job-writes-model-artifact-to-s3, s3__sagemaker.sagemaker-training-job-writes-model-artifact-to-s3-positive.

=== Cause 6 of 8: SecondaryStatus jumps Starting → Completed, and the artifact is already in S3 while SecondaryStatus is Starting ===
AWS: Smithy's SecondaryStatus enum and SecondaryStatusTransition docs define the in-progress phases a training job passes through — Starting, Downloading (File input mode), Training, then Uploading ("Training is complete and the model artifacts are being uploaded to the S3 location") before Completed — each recorded as an element of DescribeTrainingJob.SecondaryStatusTransitions. The artifact therefore becomes visible under OutputDataConfig.S3OutputPath no earlier than the Uploading phase.
Emulator: the observed transition sequence is ['Starting', 'Completed'] ("a real training job must pass through Starting, Training and Uploading"), and model.tar.gz is already listable under <S3OutputPath>/<job>/output/ while SecondaryStatus is still 'Starting' ("artifact appeared while SecondaryStatus='Starting' (pre-upload)").
Why: a client that polls SecondaryStatus to decide when the artifact exists, or that renders the phase timeline, sees neither a Training nor an Uploading phase and observes the output before the job claims to have produced it — ordering a real client depends on is inverted.
Fix: the training-job state machine (secondary-status progression and the point at which the artifact is published) and DescribeTrainingJob's SecondaryStatus/SecondaryStatusTransitions projection.
Traces: s3__sagemaker.cli-sagemaker-describe-training-job-status-transitions, s3__sagemaker.sagemaker-trained-model-artifact-is-a-real-loadable-archive-at-the-uri-it-reports.

=== Cause 7 of 8: FinalMetricDataList is a fixed pair of metric names unrelated to the job's algorithm and objective ===
AWS: Smithy models FinalMetricDataList as up to 40 MetricData entries, each "The name, value, and date and time of a metric that was emitted to Amazon CloudWatch" — i.e. the metrics the training container actually emitted, named per the algorithm's metric definitions and per input channel. The built-in XGBoost algorithm with objective binary:logistic emits train:error and validation:error for the train/validation channels (recorded behavior).
Emulator: returns the same canned names for every job regardless of HyperParameters or channels — {'validation:rmse', 'train:rmse'} for a binary:logistic two-channel job, and a single [{'MetricName': 'train:rmse', …}] where a per-channel train:error was emitted.
Why: a client that selects a model, tunes, or gates deployment on a named final metric never finds the metric its algorithm emits, and the values it does read are not derived from the job's data.
Fix: the training-job execution/metrics path feeding DescribeTrainingJob.FinalMetricDataList — metrics must come from the job's own run and be named from the algorithm's metric definitions and channel names.
Traces: s3__sagemaker.sagemaker-training-job-multiple-channels-s3-positive, s3__sagemaker.sagemaker-training-job-reads-s3-input-positive.

=== Cause 8 of 8: CheckpointConfig.S3Uri receives no object ===
AWS: Smithy models CheckpointConfig.S3Uri as "the S3 path where you want SageMaker to store checkpoints" (LocalPath default /opt/ml/checkpoints). A completed job that was created with CheckpointConfig has at least one object under that prefix, each with a LastModified inside the job's own TrainingStartTime..TrainingEndTime window (recorded behavior).
Emulator: after the job reports Completed, ListObjectsV2 on the CheckpointConfig prefix returns no contents at all ("expected at least one checkpoint object under the CheckpointConfig S3Uri prefix").
Why: a client that resumes from, inspects, or archives checkpoints (spot-training resume being the main use) finds an empty prefix while the job claims success.
Fix: the training-job execution path must write the container's checkpoint directory to CheckpointConfig.S3Uri during the training phase.
Traces: s3__sagemaker.sagemaker-training-job-s3-checkpoint-config-positive.
