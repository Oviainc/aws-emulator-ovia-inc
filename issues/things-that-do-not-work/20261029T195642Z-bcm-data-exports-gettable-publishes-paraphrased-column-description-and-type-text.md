# GetTable publishes paraphrased column Description and Type text instead of the table dictionary's text

> _Note: this issue was identified against the code base at commit `3660361421cece15e150541af9cef0f01b201b94`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTable

## Description
GetTable answers HTTP 200 with the right table name, the right table properties and the right column SET, but the per-column metadata it publishes is a re-wording of the AWS Data Exports table dictionary rather than the dictionary's published text. Six distinct schemas in the emulator's table catalog are affected, each with its own fixture step; all six share the single root cause, so the fix is one pass over the catalog's column data (every Description string, plus the Type token where it diverges), not six unrelated edits.

GENERAL RULE (applies to every cause below). Smithy: GetTable output member Schema -> ColumnList -> Column{Name, Type, Description}; Column.Description is documented as "The description for a column" and Column.Type as "The kind of data a column stores" (smithy_query shape Column). The model does not enumerate the strings, so for the text itself this is RECORDED BEHAVIOR ONLY: the recorded AWS responses carry the Data Exports table dictionary's published sentence for each column, verbatim, including its examples and its trailing clauses. Column.Description/Column.Type are RESPONSE DATA that a client reads to decide what a column holds and what to cast it to -- the emulator's own catalog header states this requirement explicitly ("every string below is the dictionary's PUBLISHED text for that column or property, carried over as published, rather than a shorter re-wording of it: a paraphrase is a different value on the wire"). The emulator nonetheless serves shortened or re-worded sentences. There is no status or error-code divergence in any cause: expected 200, actual 200, and only Schema[*].Description / Schema[*].Type values differ.

Cause 1 of 6: carbon-emissions schema. AWS: each column carries the dictionary's full sentence, e.g. region_code is published with the whole Region/Availability-Zone explanation ending "...specifies where the AWS service is available. For example, us-east-1."; total_lbm_emissions_value is published as "The total estimated location-based method (LBM) emissions value associated with the account, including Scope 1, Scope 2, and Scope 3."; total_lbm_emissions_unit names the supported unit ("...The unit we currently support is metric tons of carbon dioxide-equivalent (MTCO2e)."); last_refresh_timestamp is published as "The time when the carbon footprint value was last generated, in UTC. The format is YYYY-MM-DDTHH:mm:ssZ.". Emulator: substitutes its own shorter sentences ("Describes the Region code where the usage originated from.", "The total carbon emissions associated with your AWS usage, calculated using the location-based method (LBM).", "The unit of measurement for the total location-based method (LBM) carbon emissions.", "The date and time that the data in this report was last refreshed, in UTC. ..."), and does the same for location, total_mbm_emissions_*, total_scope_*_emissions_*, model_version. Why: see shared Why below. Fix: the GetTable handler's table catalog data (src/state/catalog.rs), carbon-emissions column group. Trace: bcm-data-exports-catalog-get-table#task#1.

Cause 2 of 6: cost-and-usage (payer/linked-account) schema. AWS: payer_account_name is published as "...this is the name of the management account."; linked_account_id and linked_account_name both end with the dictionary's tracking clause "You can use this field to track costs or usage by account."; product_name ends "Use this column to filter AWS usage by AWS service."; service is published as "This identifies the specific AWS service to the customer as a unique short abbreviation."; region as "The geographical area that hosts your AWS services."; availability_zone as "The Availability Zone that hosts this line item." with no example appended. Emulator: publishes re-wordings that drop the tracking and filtering clauses, swap "name"/"account name", replace the service abbreviation sentence with "The AWS service that the line item applies to.", replace region with "The Region that the usage occurred in.", and append an example ("For example, us-east-1a or us-east-1b.") the dictionary does not publish for availability_zone; the same re-wording affects instance_type_family, platform, processor, processor_features, tenancy, current_generation, database_engine, legal_entity, pricing_unit, product_group, product_to_location, amortized_cost, unblended_cost, ri_sp_trueup, ri_sp_upfront_fees. Fix: same catalog module, cost-and-usage column group. Trace: bcm-data-exports-catalog-get-table#task#2.

Cause 3 of 6: CUR line-item schema (also reached through the table-catalog inspection fixture). AWS: bill_payer_account_name is published as "The account name of the paying account. For an organization in AWS Organizations, this is the name of the management account."; line_item_usage_account_id/_name end with "You can use this field to track costs or usage by account."; line_item_usage_end_date as "The end date and time for the line item in UTC, exclusive. The format is YYYY-MM-DDTHH:mm:ssZ."; line_item_unblended_rate carries the two-paragraph AWS Organizations text including "For Amazon EC2 and Amazon RDS line items that have an RI discount applied to them, the UnblendedRate is zero. Line items with an RI discount have a LineItemType of DiscountedUsage." Emulator: shortens all of these (e.g. "The name of the paying account.", "...track costs and usage.", the Reserved-Instances variant of the unblended-rate text), and diverges the same way across the product_*, pricing_*, reservation_*, savings_plan_*, cost_category, discount, resource_tags and tags columns; it also diverges on the line_item_user_identifier column entry itself. Fix: same catalog module, CUR line-item column group. Trace: bcm-data-exports-catalog-get-table#task#3.

Cause 4 of 6: cost-optimization recommendations schema, including a TYPE divergence. AWS: current_resource_type is "The type of resource.", recommended_resource_type "The resource type of the recommendation.", action_type "The type of action you can take by adopting the recommendation.", current/recommended_resource_summary "Describes the current resource."/"Describes the recommended resource.", the estimated_savings_percentage_before/after_discount sentences word the discount clause before the lookback clause, tags "A list of tags associated with the resource for which the recommendation exists."; and the recorded Type tokens are the parameterised ones -- tags has Type "Map<String, String>" and recommendation_lookback_period_in_days carries the dictionary's own numeric token. Emulator: substitutes re-worded descriptions for all of those and publishes the bare token "Map" for tags (and a diverging Type for recommendation_lookback_period_in_days). Why (type): a client that reads Column.Type to build a cast or a table DDL gets no key/value types at all from "Map", so it cannot reproduce the column it will actually receive. Fix: same catalog module, recommendations column group -- both the Description strings and the Type token constants it selects. Trace: bcm-data-exports-catalog-get-table#task#4.

Cause 5 of 6: FOCUS 1.0 schema (two recorded steps in the cluster). AWS: ChargePeriodStart is "The inclusive start date and time within a charge period."; ListCost "Cost calculated by multiplying List Unit Price and the corresponding Pricing Quantity."; ResourceType "The kind of resource the charge applies to."; ServiceName uses the specification's "(e.g., cloud virtual machine, ...)" form; Tags "The set of tags assigned to tag sources that account for potential provider-defined or user-defined tag evaluations."; x_CostCategories "Key-value pairs of the cost categories and their values for a given line item."; x_Discounts "Key-value pairs for any discounts you are receiving."; x_Operation carries the RunInstances example sentence. Emulator: substitutes its own wording for each ("...of a charge period.", "...the list unit price...", "The kind of resource for which you are being charged.", "(for example, cloud virtual machine, ...)", "The set of tags assigned to a resource or charge, ...", "A map column containing key-value pairs ..."), and likewise for x_ServiceCode and x_UsageType. Fix: same catalog module, FOCUS 1.0 column group. Trace: bcm-data-exports-catalog-get-table#task#5.

Cause 6 of 6: FOCUS 1.2 schema (the revised group that supersedes FOCUS 1.0). AWS: CommitmentDiscountQuantity ends "...that is denominated in Commitment Discount Units."; CommitmentDiscountUnit is "The provider-specified measurement unit indicating how a provider measures the Commitment Discount Quantity of a commitment discount."; ConsumedQuantity/ConsumedUnit say "a metered SKU"; InvoiceId is "The provider-assigned identifier for an invoice encapsulating some or all charges in the corresponding billing period for a given billing account."; PricingCurrency and the PricingCurrency* price columns, ServiceSubcategory, SkuId, SkuMeter, SkuPriceDetails, SkuPriceId, SubAccountType, ResourceType, ServiceName, ListCost, Tags, x_Discounts, x_Operation, x_ServiceCode all carry the 1.2 specification's text. Emulator: publishes re-worded sentences for all of them ("...a given SKU...", "The unique identifier assigned to an invoice by the invoice issuer.", etc.), i.e. the revised group repeats cause 5's defect with its own text. Fix: same catalog module, FOCUS 1.2 revised column group. Trace: bcm-data-exports-catalog-get-table#task#7.

Why (shared): GetTable is how a client discovers a table before writing a QueryStatement -- it reads Column.Description to pick the columns it needs and Column.Type to cast them. A paraphrased Description is a different value on the wire: documentation generators, schema catalogs and dictionary-diff tooling built on the real API see every column as changed against AWS, and any client that matches on the published text (or asserts a recorded GetTable response in its own tests) fails against the emulator while passing against AWS. The Type divergence is worse than cosmetic: "Map" in place of "Map<String, String>" loses the key and value types the client needs to materialise the column.

No open issue covers this: the six open bcm-data-exports issues concern CreateExport/UpdateExport validation and destination delivery, GetExecution status, and ListExports pagination -- none touches the table catalog read by GetTable/ListTables.

Note for the fixer: ListTables reports the same catalog entries out of the same module, so correcting the catalog data corrects both operations; re-replay all six steps named above (the cluster for task#3 also covers bcm-data-exports-table-catalog-inspection#task#2, and the cluster for task#5 also covers bcm-data-exports-catalog-get-table#task#6).
