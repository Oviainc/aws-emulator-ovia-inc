# athena__glue__s3: 3 net-new causes — Glue job runs publish no "Glue Job State Change" event, JobRun.ErrorMessage is re-worded with the wrong session identity, and StartJobRun never checks the role's trust policy

> _Note: this issue was identified against the code base at commit `4ca728998286b7558a3f8204f86decdeb692036b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun

## Description
Three net-new root causes in the athena__glue__s3 group, all reached AFTER the control plane answered: CreateBucket/PutObject, CreateRole, glue CreateJob and glue StartJobRun all succeeded and the positive-control job run reached SUCCEEDED and wrote its object, so none of these is a bootstrap gap or an unimplemented stub.

Cause 1 of 3 — a Glue job run that reaches a terminal state publishes no "Glue Job State Change" EventBridge event, so no rule ever delivers it.
AWS: recorded behavior only for the event itself (the Glue Smithy model describes the job-run surface — JobRun.JobRunState is a JobRunState enum, JobRun.JobName/Id are the run's identity — but not EventBridge emission). The recordings show that when a job run settles SUCCEEDED, Glue publishes an event with source "aws.glue", detail-type "Glue Job State Change" and a detail object carrying at least jobName (the job definition's name), state (the terminal JobRunState) and the run id; an EventBridge rule whose pattern matches that source/detail-type (optionally narrowed on detail.jobName) delivers it to its SQS target, and a rule whose pattern names a DIFFERENT jobName does not match.
Emulator: the job run reaches SUCCEEDED, but nothing is ever published. The subscribed SQS queue stays empty for the whole polling window and both checks are killed at the harness budget ('Error: Check timed out after 180.0s'), the inner poll having observed only the empty list.
Why: every Glue-driven event pipeline is silently inert. A client that chains post-job work off a "Glue Job State Change" rule (notify, start the next job, archive, alarm) never runs that work, and because the run itself reports SUCCEEDED the client has no signal at all that the notification was lost; code that waits on the queue blocks forever rather than failing.
Fix: the Glue job-run state machine must publish a "Glue Job State Change" event into the EventBridge default bus on every terminal transition (services/service-com-amazonaws-glue-awsglue — the job-run executor/state writer behind StartJobRun/GetJobRun — handing the envelope to the events crate, services/service-com-amazonaws-eventbridge-awsevents, for pattern matching and target delivery). Open issues that do NOT cover this one: 20261025T031335Z-glue-job-runs-never-execute-and-publish-no.md and 20261025T072821Z-glue-job-runs-are-terminated-failed-without-executing.md both premise the missing event on job runs never executing — here the run DOES execute and succeed and the event is still absent; 20261027T003436Z-glue-sqs-an-on-demand-trigger-that-starts.md is about an ON_DEMAND trigger starting no job run; 20261103T101621Z-athena-glue-s3-glue-publishes-no-glue-crawler-state-change-eventbridge.md is the CRAWLER event, not the job event.
Traces: athena__glue__s3.eventbridge-rule-filters-glue-job-name-positive, athena__glue__s3.glue-job-succeeded-event-triggers-eventbridge-rule-positive.

Cause 2 of 3 — when the job script's own S3 call is refused, JobRun.ErrorMessage is re-prefixed and the assumed-role session name is wrong.
AWS: Smithy models JobRun.ErrorMessage as ErrorString, 'An error message associated with this job run', so the text is recorded behavior. The recording shows Glue surfaces the script's unhandled botocore exception verbatim, prefixed with the Python exception class name, and signed by Glue's own runner session. The required template is: `ClientError: An error occurred (<ErrorCode>) when calling the <Operation> operation: User: arn:aws:sts::<account-id>:assumed-role/<job-role-name>/GlueJobRunnerSession is not authorized to perform: <action> on resource: "<resource-arn>" because no identity-based policy allows the <action> action`. Fixed text: the `ClientError: ` prefix, `An error occurred (`…`) when calling the `…` operation: User: `, the literal session name `GlueJobRunnerSession`, ` is not authorized to perform: `, ` on resource: `, and ` because no identity-based policy allows the ` / ` action` tail. Variable parts taken from the request and from state: the account id, the job role's name, the S3 action, the operation name and the resource ARN (bucket/key). No value from any single run is part of the template.
Emulator: the prefix is the S3 error CODE rather than the Python exception class, and the session name is the JOB RUN's own generated name instead of Glue's fixed runner session. Replayed ErrorMessage: `AccessDenied: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account-id>:assumed-role/<job-role-name>/<job-name> is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/out/bad/output.txt" because no identity-based policy allows the s3:PutObject action` — i.e. `ClientError: ` replaced by `AccessDenied: `, and `/GlueJobRunnerSession` replaced by the job name.
Why: the ErrorMessage is the only diagnostic a failed Glue job gives. Tooling that classifies failures by the leading exception class (ClientError vs ValueError vs ModuleNotFoundError) misclassifies every AWS-API failure, and the session identity in the message is what an operator uses to find the denied principal in CloudTrail/IAM — naming the job run instead of Glue's runner session points at a principal that does not exist.
Fix: the Glue job-run executor's error formatter and the session identity it signs in-job SDK calls with (services/service-com-amazonaws-glue-awsglue, the job-run execution/ErrorMessage path behind StartJobRun/GetJobRun).
Traces: athena__glue__s3.deploy-cfn-glue-job-role-missing-s3-write-permission-negative.

Cause 3 of 3 — StartJobRun never checks that the job's role can be assumed by Glue, so a job whose role does not trust glue.amazonaws.com runs and SUCCEEDS.
AWS: Smithy models Job.Role/JobRun as the execution role Glue assumes to run the job; recorded behavior shows that when the role's trust policy does not name glue.amazonaws.com, Glue cannot assume it, the run settles FAILED (JobRunState enum), and ErrorMessage names the assume-role failure (real-AWS wording recorded in the check itself: "…should be given assume role permissions for Glue Service."), and the job writes nothing.
Emulator: the run with the mistrusted role ends 'SUCCEEDED' — identical to the positive control whose role DOES trust glue.amazonaws.com. Replay: AssertionError: job with mistrusted role ended as 'SUCCEEDED', expected FAILED.
Why: the emulator reports a passing run for a configuration real AWS refuses, so a trust-policy misconfiguration is invisible: deployment tests that assert the negative case pass against the emulator and the same stack fails in AWS, and least-privilege review of a Glue role gets no feedback at all.
Fix: StartJobRun's run admission must resolve the job's Role and evaluate its AssumeRolePolicyDocument for the glue.amazonaws.com service principal before dispatching the script, failing the run with the assume-role ErrorMessage otherwise (services/service-com-amazonaws-glue-awsglue job-run executor, consulting the IAM crate services/service-com-amazonaws-iam-awsidentitymanagementv20100508). Open issue that does NOT cover this: 20261030T000623Z-glue-job-runs-never-execute-so-a-role.md describes the opposite emulator state (no run executed at all, so a mistrusted role was indistinguishable from a healthy run) — here runs DO execute and succeed, and the trust policy is simply never consulted.
Traces: athena__glue__s3.glue-job-role-missing-trust-policy-negative.

## Evidence
Cause 1 — expected: after a pythonshell job run settles SUCCEEDED, an EventBridge rule with pattern {"source":["aws.glue"],"detail-type":["Glue Job State Change"],"detail":{"jobName":[<job>]}} delivers one message to its SQS target carrying detail.jobName == the job and detail.state == "SUCCEEDED"; a sibling pattern naming another jobName does not match. Actual: the target queue never receives a message; the inner poll's last result is [] for the whole window and the suite reports 'Error: Check timed out after 180.0s' for both athena__glue__s3.eventbridge-rule-filters-glue-job-name-positive and athena__glue__s3.glue-job-succeeded-event-triggers-eventbridge-rule-positive.

Cause 2 — expected GetJobRun(...)['JobRun']['ErrorMessage'] == 'ClientError: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account-id>:assumed-role/<bad-role-name>/GlueJobRunnerSession is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/out/bad/output.txt" because no identity-based policy allows the s3:PutObject action'. Actual (replay): 'AccessDenied: An error occurred (AccessDenied) when calling the PutObject operation: User: arn:aws:sts::<account-id>:assumed-role/<bad-role-name>/<bad-job-name> is not authorized to perform: s3:PutObject on resource: "arn:aws:s3:::<bucket>/out/bad/output.txt" because no identity-based policy allows the s3:PutObject action'. Two divergences: the leading token (`ClientError:` vs `AccessDenied:`) and the assumed-role session name (`GlueJobRunnerSession` vs the job-run's job name). AssertionError raised at check line 199: 'bad job run failed for the wrong reason'.

Cause 3 — expected: GetJobRun for the job whose role trusts a non-Glue principal reports JobRunState 'FAILED' with an assume-role ErrorMessage and no output object. Actual: JobRunState 'SUCCEEDED' (ExecutionTime 1, GlueVersion 5.1, no ErrorMessage). AssertionError at check line 85: "job with mistrusted role ended as 'SUCCEEDED', expected FAILED".
