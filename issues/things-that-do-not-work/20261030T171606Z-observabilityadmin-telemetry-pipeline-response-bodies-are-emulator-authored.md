# observabilityadmin telemetry-pipeline response bodies are emulator-authored: validation error list and pipeline projection diverge

> _Note: this issue was identified against the code base at commit `fc9301cbb7aa4298b93d2091e6319dbea4fc7b10`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ValidateTelemetryPipelineConfiguration

## Description
Replaying the wire corpus against this checkout shows that observabilityadmin's telemetry-pipeline RESPONSE BODIES are composed by the emulator rather than reproduced from AWS: the ValidateTelemetryPipelineConfiguration error list uses the wrong reason codes, the wrong FieldMap key shape and reports only a fraction of the defects AWS reports, and the GetTelemetryPipeline projection drops a whole output member and substitutes the emulator's own status sentence. Every status line is correct (200 throughout); only the bodies diverge. This issue bundles 3 distinct root causes; ALL THREE must be closed before submitting.

Related open issues (neither covers these wire steps): '20261029T184923Z-observabilityadmin-telemetry-rule-pipeline-refusal-contract-diverges-emulator.md' names the ValidateTelemetryPipelineConfiguration FieldMap key shape for the INVALID_PATTERN reason from the behavioral suite — Cause 1 and Cause 2 below are the same validator and should be fixed consistently with it, but they are different reason codes and different recorded steps; and '20261030T012240Z-observabilityadmin-deletes3tableintegration-answers-an-unknown-integration-arn-with-400.md' covers a different operation. The two previously RESOLVED issues '20261029T174915Z-observabilityadmin-success-response-projection-diverges-minted-arns-omitted.md' and '...-refusal-contract-diverges-not-found-conflict-and.md' touched this surface but are fixed and cover none of the steps below.

Cause 1 of 3 — ValidateTelemetryPipelineConfiguration reports a document that declares no top-level 'pipeline' section as an UNKNOWN_PROPERTY at root instead of the required property being absent.
AWS: Smithy (services/service-com-amazonaws-observabilityadmin-observabilityadmin/smithy-model/com-amazonaws-observabilityadmin-observabilityadmin.json): ValidateTelemetryPipelineConfiguration input Configuration (required) -> TelemetryPipelineConfiguration.Body (required, @length 1..24000); output Errors -> list<ValidationError{Message,Reason,FieldMap}>; http POST /ValidateTelemetryPipelineConfiguration, code 200 (defaulted); modeled errors AccessDeniedException(400), InternalServerException(500), TooManyRequestsException(429), ValidationException(400). The model documents FieldMap only as 'A mapping of field names to specific validation issues within the configuration' and Reason only as 'The reason code or category for the validation error', so the reason vocabulary and the FieldMap key names are recorded behavior only. Recorded behavior: a body that parses but declares no 'pipeline' section is answered HTTP 200 with EXACTLY ONE error — Reason 'MISSING_FIELD', Message "required property 'pipeline' not found", FieldMap {"name": "pipeline"}. Fixed text: the sentence template "required property '<property>' not found", the reason token 'MISSING_FIELD' and the FieldMap KEY 'name'; the only variable part is the missing property's name, taken from the schema requirement the document failed (here 'pipeline').
Emulator: HTTP 200 with one error whose Reason is 'UNKNOWN_PROPERTY', whose Message is "property '<the submitted body text>' is not defined in the schema and the schema does not allow additional properties" and whose FieldMap is {"path": "root"}. It treats the document's own scalar as an undefined property at root rather than reporting the absent required section, and echoes the caller's body into the message.
Why: a client that branches on Reason to tell 'you forgot a required section' from 'you wrote a property we do not know' takes the wrong branch, and a console or CLI that reads FieldMap['name'] to point at the missing field finds no such key, so the actionable part of the validation result is lost. The echoed body text is emulator prose AWS never emits.
Fix: the schema-validation stage behind the ValidateTelemetryPipelineConfiguration handler — a parsed document that does not declare the required 'pipeline' section must yield the missing-required-property defect (reason MISSING_FIELD, FieldMap keyed 'name'), not an unknown-property defect at root.
Traces: observabilityadmin-telemetry-pipeline-error-paths#task#6.

Cause 2 of 3 — ValidateTelemetryPipelineConfiguration's error list for a defective pipeline document is truncated to the missing-field defects, those defects' FieldMap key/value are inverted, and the data-source/processor restriction reason is absent from the emulator's vocabulary.
AWS: Smithy as in Cause 1 (200 carrying Errors; Reason and FieldMap key names are recorded behavior only). Recorded behavior for one defective document: NINE ValidationError entries, in a stable order — five with Reason 'DATA_SOURCE_PROCESSOR_RESTRICTED', two with Reason 'UNKNOWN_PROPERTY' and two with Reason 'MISSING_FIELD'. A DATA_SOURCE_PROCESSOR_RESTRICTED entry carries a FieldMap keyed by the RESTRICTION's own descriptors — 'source_type', 'data_source_name', 'allowed_processor'/'allowed_processors' — with Messages of the forms 'must have at most <n> items but found <m>', "property '<name>' is not defined in the schema and the schema does not allow additional properties" and "required property '<name>' not found"; the fixed parts are the reason token, the descriptor key names and those sentence templates, while the source type, data-source name, allowed-processor list and the counts come from the submitted document and the service's per-source-type restriction table. An UNKNOWN_PROPERTY entry pinned to a processor position carries FieldMap {"path": "processor[<i>]"}. A MISSING_FIELD entry carries Message "required property '<property>' not found" with FieldMap {"name": "<property>"} — e.g. {"name": "source"} and {"name": "sink"}.
Emulator: HTTP 200 with only TWO errors, both MISSING_FIELD — "required property 'source' not found" and "required property 'sink' not found" — and each FieldMap INVERTED relative to AWS: the missing property name is used as the KEY and the enclosing path as its value ({"source": "pipeline"}, {"sink": "pipeline"}), with no 'name' key at all. None of AWS's five DATA_SOURCE_PROCESSOR_RESTRICTED entries and neither processor-position UNKNOWN_PROPERTY entry is produced: the emulator's reason vocabulary has no DATA_SOURCE_PROCESSOR_RESTRICTED token, so per-source-type processor restrictions (how many processors a data source admits, which processors a source type allows) are never validated at all.
Why: this operation exists so a caller can learn every defect of a configuration in one round trip. A client is told two fields are missing and nothing about the processor restrictions that will also stop the pipeline, so it fixes the document, re-submits, and is refused again — or, worse, CreateTelemetryPipeline accepts a configuration the real service rejects. The inverted FieldMap also makes the one defect it does report unreadable by any client following AWS's key contract, and ambiguous whenever the same property is missing from two sections.
Fix: the ValidateTelemetryPipelineConfiguration validator — correct the MISSING_FIELD error constructor to emit FieldMap {'name': <property>} (it currently builds {property: path} in services/service-com-amazonaws-observabilityadmin-observabilityadmin/src/ops/validate_telemetry_pipeline_configuration.rs:473-481), and add the data-source/processor restriction pass plus the processor-position unknown-property pass to the schema walk, emitting them under AWS's reason tokens ahead of the missing-field defects.
Traces: observabilityadmin-telemetry-pipeline-workflow#task#3; src/ops/validate_telemetry_pipeline_configuration.rs:251-262 (the REASON_* vocabulary, which has no DATA_SOURCE_PROCESSOR_RESTRICTED token) and :473-481 (missing_field's FieldMap).

Cause 3 of 3 — GetTelemetryPipeline omits Pipeline.ConfigurationSummary entirely and reports an emulator-authored StatusReason.Description.
AWS: Smithy: GetTelemetryPipeline input PipelineIdentifier (required, @length 1..512), output Pipeline -> TelemetryPipeline {CreatedTimeStamp, LastUpdateTimeStamp, Arn, Name, Configuration, Status, StatusReason, Tags}; http POST /GetTelemetryPipeline, 200 (defaulted); readonly. The on-disk model does NOT declare a ConfigurationSummary member, so this is recorded behavior only: a read of an ACTIVE pipeline answers 200 with Pipeline.ConfigurationSummary present, a summary DERIVED from the stored configuration body — Sources as a list of {Type: <each source type declared>}, DataSources as a list of {Name: <data-source name>, Type: <data-source type, 'default' when the document names none>}, Processors as the list of processor names in document order, ProcessorCount as that list's length, Sinks as the list of sink types. Pipeline.StatusReason.Description for an ACTIVE pipeline is exactly 'Pipeline is active and processing data' — wholly fixed text with no interpolation. (The recorded summary's pipeline name and the timestamps are per-run values and are not part of the requirement; the member set, the derivation rule and the status sentence are.)
Emulator: HTTP 200 with Pipeline.ConfigurationSummary absent from the body altogether, and StatusReason.Description set to the emulator's own sentence 'The pipeline is active.'.
Why: a client or console that renders the pipeline's shape (how many processors, which sources and sinks) from ConfigurationSummary — the whole point of the member, since the alternative is re-parsing the raw YAML body — gets nothing, and a caller keyed on AWS's status sentence never matches. Both make the read's body unusable as a substitute for the real service's.
Fix: the GetTelemetryPipeline response projection — add the ConfigurationSummary member to the TelemetryPipeline output type and its serializer in src/ops/types.rs, derive it from the stored configuration body in the record-to-output projection, and replace the status-reason sentence table with AWS's text.
Traces: observabilityadmin-telemetry-pipeline-workflow#task#5; src/state.rs:544-557 (as_pipeline, which emits no configuration_summary) and src/state.rs:516-526 (status_reason_at, which maps ACTIVE to "The pipeline is active."); the handler returns record.as_pipeline(now) at src/ops/get_telemetry_pipeline.rs:184-186.
