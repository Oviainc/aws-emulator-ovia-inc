# cloudtrail__stepfunctions: no states.amazonaws.com management event is recorded in event history, so LookupEvents can never audit StartExecution or a rejected/successful DescribeStateMachine made by an assumed-role session

> _Note: this issue was identified against the code base at commit `6211fb78e0841381478152dba6893fe342be7489`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
ONE net-new root cause in this issue (Cause 1 of 1).

Cause 1 of 1 — Step Functions management calls (StartExecution, a refused DescribeStateMachine and a successful DescribeStateMachine) are never recorded into the Region's CloudTrail event history, so CloudTrail LookupEvents returns no record for any of them and the audit trail of a Step Functions session does not exist. Failing check: cloudtrail__stepfunctions.obs-sfn-2-lookup-events-audits-start-execution-and-a-rejected-describe-state-machine.

AWS: Smithy (services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/smithy-model/com-amazonaws-cloudtrail-cloudtrail-20131101.json) models LookupEvents with LookupAttributes / StartTime / EndTime / EventCategory / MaxResults (@range min 1, max 50) / NextToken and an output Events list of envelopes whose CloudTrailEvent carries the JSON record; its modeled refusals are InvalidLookupAttributes, InvalidTimeRange, InvalidMaxResults, InvalidNextToken, InvalidEventCategory (all 400 client errors), and the operation is paginated on NextToken. In AWS, every management call of every service — reads as well as writes, successful as well as refused — is recorded in the Region's event history and is readable through LookupEvents by the EventName attribute. The per-record field semantics are recorded behavior only (as this check measured them against real AWS): eventSource "states.amazonaws.com"; eventCategory "Management"; awsRegion and recipientAccountId of the call; userIdentity.type "AssumedRole" with userIdentity.arn equal to the caller's assumed-role session ARN and sessionContext.sessionIssuer.arn equal to the role ARN, and envelope Username equal to the role session name; requestID equal to the ResponseMetadata.RequestId the SDK observed on that same call; envelope EventId equal to the record's eventID; readOnly false for StartExecution and true for DescribeStateMachine (true even when the DescribeStateMachine was refused, with envelope ReadOnly "true"); requestParameters holding the arguments actually sent (stateMachineArn and name for StartExecution, exactly {"stateMachineArn": <arn>} for DescribeStateMachine); responseElements.executionArn equal to the execution ARN StartExecution returned; no errorCode/errorMessage member at all on a successful call; and on the refused DescribeStateMachine errorCode "StateMachineDoesNotExist" (the Step Functions model declares StateMachineDoesNotExist as a client error of DescribeStateMachine) with errorMessage identical to the message the caller received — fixed text "State Machine Does Not Exist: '" followed by the stateMachineArn taken from the request and a closing "'". Those variable parts (the ARN, the session ARN, the role ARN, the session name, the request ids) come from the request and the emulator's state; no literal value from one run is part of the requirement.

Emulator: event history holds none of these calls. The check creates an execution role and a STANDARD one-Pass-state machine, creates a caller role with states:StartExecution/DescribeStateMachine/DescribeExecution, AssumeRoles it, then with the session credentials runs StartExecution (the execution reaches SUCCEEDED and echoes its input), gets StateMachineDoesNotExist from DescribeStateMachine on a never-created ARN, and DescribeStateMachine on the real machine — all of those assertions pass. It then polls ct.lookup_events(MaxResults=50, StartTime=<now-3min>, EndTime=<now+5min>, LookupAttributes=[{AttributeKey:'EventName', AttributeValue:'StartExecution'|'DescribeStateMachine'}]) to NextToken exhaustion, keeping records whose userIdentity.arn equals the session ARN, and exits only once 'start', 'missing' and 'control' are all seen. No record attributed to that session is ever returned, so the poll (budget 900 s, interval 2 s, stall detector 420 s) is still running when the harness cap fires: verdict 'mismatch', detail 'Check timed out after 180.0s'. Hypothesis for the placement: the lookup poll is the only wait that can reach the cap — every earlier wait is bounded at 90 s (IAM retry) or 120 s (execution terminal wait) and raises an AssertionError with a different detail instead of hanging.

Why: a client cannot answer "who started this execution, with what arguments, and which calls were refused". Every detective control built on event history — incident reconstruction, compliance evidence that a specific role session started an execution, reconciliation of refused calls, joining a record back to the SDK's request id — reads an empty history and cannot distinguish "nothing happened" from "nothing was recorded"; the refused call's errorCode/errorMessage, the readOnly classification and the recorded requestParameters are all unobservable.

Fix: the shared management-event recording seam that CloudTrail's LookupEvents handler reads (the CloudTrail service's event-history state) must be driven from the Step Functions service's served operations — for read-only and refused calls as well as writes — populating eventSource/eventName/eventCategory/readOnly/requestParameters/responseElements/requestID/eventID, the caller's assumed-role userIdentity with its sessionContext.sessionIssuer, and errorCode/errorMessage copied from the refusal actually returned to the caller. The LookupEvents handler itself must then match on the EventName lookup attribute and the time window.
