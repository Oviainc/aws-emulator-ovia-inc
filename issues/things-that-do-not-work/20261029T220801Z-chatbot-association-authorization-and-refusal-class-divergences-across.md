# Chatbot association, authorization and refusal-class divergences across five operations

> _Note: this issue was identified against the code base at commit `baf30d4927ba43bb30691a1e04213021d426cca6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateToConfiguration

## Description
Five distinct root causes in the chatbot emulator, all surfaced by the behavioral suite (simparity-behavioral-aws-v1). One operation is still a scaffold stub and four refusal paths pick the wrong error class, the wrong message, or no refusal at all. Each cause below is independent and must be closed separately.

NOTE on scope: the already-open issue `20261029T170844Z-chatbot-not-found-and-conflict-errors-use-wrong.md` covers the CreateCustomAction conflict message and the TagResource/ListTagsForResource/GetCustomAction NOT-FOUND paths. It does NOT cover any cause below: cause 3 here is a different operation (CreateChimeWebhookConfiguration) and cause 5 here is TagResource's TAG-CAP path, not its not-found path.

Cause 1 of 5: AssociateToConfiguration is a scaffolded stub, so it answers 501 NotImplemented instead of AWS's refusal for an unsupported target.
AWS: Smithy: AssociateToConfiguration input Resource (ResourceIdentifier, required, @length 1..1011, @pattern ^arn:aws:chatbot:[A-Za-z0-9_/.-]{0,63}:[A-Za-z0-9_/.-]{0,63}:custom-action/[a-zA-Z0-9_-]{1,64}$) and ChatConfiguration (ChatConfigurationArn, required); modeled errors InternalServiceError (errorKind server, httpError 500), InvalidRequestException (400), UnauthorizedException (403); success is HTTP 201 with an empty body. Recorded behavior: when the ChatConfiguration names a configuration kind that does not support custom-action associations (a Chime webhook configuration), AWS refuses the call with the modeled InternalServiceError, HTTP 500, error code `InternalServiceError`, message `Internal Server Error` — that message is entirely fixed text with no variable part. The refusal is deterministic: firing the identical Resource/ChatConfiguration pair concurrently refuses every caller and creates no association (ListAssociations shows nothing for the pair afterwards).
Emulator: every call returns HTTP 501 with error code `NotImplemented` and message `operation AssociateToConfiguration is scaffolded but not implemented in this emulator`, for both the single-call and the 8-way concurrent case. The handler body is still the generated `Err(crate::scaffolded::Scaffolded::not_implemented("AssociateToConfiguration"))`.
Why: a client cannot link a custom action to a channel configuration at all, so the whole association feature is unusable; and code that distinguishes "this configuration kind cannot take associations" (a 500 InternalServiceError it retries or reports) from "this API does not exist" (501) takes the wrong branch. A 501 is also not a modeled error of the operation, so SDK error-shape matching finds no modeled variant.
Fix: implement the AssociateToConfiguration handler, including its target-kind check that refuses an unsupported configuration kind with the modeled InternalServiceError and leaves no partial association behind, and remove the SCAFFOLDED marker.
Traces: chatbot.associate-concurrent-unsupported-target-fails-atomically, chatbot.disassociate-nonexistent-association-idempotent (both fail on this same stub; the second uses the refusal only to establish that the pair can never become associated). File: services/service-com-amazonaws-chatbot-wheatleyorchestration-20171011/src/ops/associate_to_configuration.rs lines 139-157.

Cause 2 of 5: DisassociateFromConfiguration rejects a malformed Resource with the wrong error class.
AWS: Smithy: DisassociateFromConfiguration models errors InternalServiceError (500), InvalidRequestException (400) and UnauthorizedException (errorKind client, httpError 403); Resource carries the custom-action ARN @pattern shown in cause 1. Recorded behavior: AWS evaluates the resource-scoped authorization check BEFORE ARN-shape validation, so a Resource that does not match the custom-action ARN pattern fails closed with HTTP 403, error code `UnauthorizedException`, message `Unauthorized` — all fixed text, no variable part. A well-formed custom-action ARN that was simply never associated is NOT an error: it succeeds as an idempotent no-op (HTTP 204).
Emulator: the malformed Resource is refused with error code `InvalidRequestException` (400) — the emulator validates the ARN shape first and never reaches the authorization decision.
Why: a client that branches on UnauthorizedException to surface a permissions problem (and on InvalidRequestException to surface a caller-side input bug) is sent down the wrong path; retry and alerting policy differs between a 403 and a 400, and the ordering of the two checks is itself part of the contract because it is what makes the operation fail closed.
Fix: the DisassociateFromConfiguration handler's validation ordering — the resource-scoped authorization check must run before the Resource ARN-shape check, and the shape-mismatch path must emit the modeled UnauthorizedException rather than InvalidRequestException.
Traces: chatbot.disassociate-from-configuration-malformed-resource-arn-rejected.

Cause 3 of 5: CreateChimeWebhookConfiguration's duplicate-name ConflictException carries the wrong message.
AWS: Smithy: CreateChimeWebhookConfiguration models ConflictException (errorKind client, httpError 409, member `message`), plus InvalidParameterException, InvalidRequestException, LimitExceededException and CreateChimeWebhookConfigurationException; input ConfigurationName (required, @length 1..128, @pattern ^[A-Za-z0-9-_]+$). Recorded behavior: creating a second Chime webhook configuration whose ConfigurationName already exists in the account is refused with HTTP 409, error code `ConflictException`, and message `Resource with arn <chatConfigurationArn> already exists.` — the fixed text is `Resource with arn ` + ` already exists.` and the single variable part is the ARN of the EXISTING colliding configuration, read from emulator state. The original configuration is untouched (DescribeChimeWebhookConfigurations still shows exactly one entry with the original WebhookDescription), and a differently-named create still succeeds.
Emulator: the status and error code are right (409 ConflictException) but the message is `a chat configuration named <ConfigurationName> already exists` — different wording, and it names the configuration name from the request rather than the existing resource's ARN.
Why: the message is part of the contract for this error class; operators and tests that match AWS's wording see a mismatch, and the emulator's text omits the ARN AWS gives callers to identify the colliding resource, so a client cannot resolve the collision from the error alone. This mirrors cause 4 of the open issue named above, which fixed only CreateCustomAction — the same defect exists on this operation.
Fix: the CreateChimeWebhookConfiguration handler's conflict branch — format the modeled ConflictException `message` from the existing configuration's ChatConfigurationArn.
Traces: chatbot.chime-webhook-duplicate-configuration-name-conflict-rejected.

Cause 4 of 5: CreateCustomAction is not authorized at all — an unpermitted principal's create SUCCEEDS.
AWS: Smithy: CreateCustomAction models UnauthorizedException (403) and returns 201 with CustomActionArn on success. Recorded behavior: an IAM principal with NO attached permissions (implicit deny, assumed via sts:AssumeRole) calling CreateCustomAction is refused with error code `AccessDeniedException` and message `User: arn:aws:sts::<accountId>:assumed-role/<roleName>/<sessionName> is not authorized to perform: chatbot:CreateCustomAction on resource: arn:aws:chatbot::<accountId>:custom-action/<actionName> because no identity-based policy allows the chatbot:CreateCustomAction action` — the fixed text is the standard IAM implicit-deny template (`User: ` / ` is not authorized to perform: ` / ` on resource: ` / ` because no identity-based policy allows the ` / ` action`), and the variable parts are the caller's assumed-role ARN (account id, role name and session name from the AssumeRole call), the action `chatbot:CreateCustomAction`, and the resource ARN built from the caller's account and the ActionName in the request. No custom action is created for the denied attempt. The same call with permitted credentials succeeds (positive control).
Emulator: the call from the unpermitted assumed-role principal returns HTTP 201 with a CustomActionArn (e.g. arn:aws:chatbot:<region>:<account>:custom-action/<actionName>) and the action really is created — no authorization decision is made for the request's principal.
Why: the emulator is overly permissive, so it cannot be used to test or demonstrate least-privilege behavior: a caller that should be denied silently mutates state, and any client or test that asserts a denial for an unauthorized role passes against AWS and fails (or, worse, leaks a created resource) against the emulator. Hypothesis: the request's signing identity is not resolved to a principal and no identity-policy evaluation exists on this code path.
Fix: the CreateCustomAction handler's authorization step (and the shared principal/identity-policy evaluation it should call) must deny a principal with no allowing identity-based policy, emitting AccessDeniedException with the IAM implicit-deny message template above, and must not create the action on the denied path.
Traces: chatbot.create-custom-action-missing-permission-denied.

Cause 5 of 5: TagResource's tag-cap refusal uses the wrong error class and adds a message AWS does not send.
AWS: Smithy: TagResource input Tags (TagList, required, @length 0..200) and ResourceARN (required); modeled errors InternalServiceError (500), ResourceNotFoundException (404), ServiceUnavailableException (429) and TooManyTagsException (errorKind client, httpError 400). Recorded behavior: when a tag-applying call would push a resource past its total tag cap, AWS refuses it with error code `InvalidRequestException` and NO message member at all (not an empty string — the member is absent). The refusal is clean: the rejected batch is not partially applied (the resource's tag count equals exactly what was accepted), a further single brand-new key is refused again, freeing one slot makes the identical call succeed, and replacing the VALUE of an existing key never grows the count and always succeeds.
Emulator: the cap itself is enforced and no partial application occurs, but the refusal is reported with error code `TooManyTagsException` instead of `InvalidRequestException`, and it carries a message.
Why: a client that distinguishes the tag-cap refusal from other tagging failures by error code takes the wrong branch — TooManyTagsException reads as a per-call tag-count problem (drop some tags and retry the same batch) where AWS's InvalidRequestException is the account/resource cap (free a slot first). Any assertion on the absent message also fails.
Fix: the TagResource handler's cap-check branch — emit InvalidRequestException for the total-tag-cap refusal and omit the message member entirely; leave the existing no-partial-application behavior as-is.
Traces: chatbot.tag-resource-exceeds-max-tags-rejected.
