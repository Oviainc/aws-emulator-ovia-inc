# cleanroomsml__cloudformation__s3: UpdateStack refuses AWS::CleanRoomsML::TrainingDataset as an unrecognized resource type, so no training dataset can be deployed or rolled back from a template

> _Note: this issue was identified against the code base at commit `86c25e3173c48b1c4d4a9173324e183693bfe876`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
Cause 1 of 1: CloudFormation's template validation does not know the AWS::CleanRoomsML::TrainingDataset resource type, so an UpdateStack that adds one to an already-deployed prerequisite stack (S3 bucket + IAM role + Glue database/table) is refused at submit time and no Clean Rooms ML training dataset can be provisioned through IaC. Failing checks: cleanroomsml__cloudformation.deploy-cfn-cleanroomsml-training-dataset-empty-s3-location-rejected, cleanroomsml__cloudformation.deploy-cfn-cleanroomsml-training-dataset-round-trip-and-delete.

AWS: recorded behavior only for the registry contents — the CloudFormation Smithy model declares UpdateStack(StackName, TemplateBody, Capabilities, ...) -> UpdateStackOutput{StackId} with only InsufficientCapabilitiesException and TokenAlreadyExistsException; which resource types are recognized is CloudFormation's own provider registry, not a modeled value. AWS's registry contains AWS::CleanRoomsML::TrainingDataset, so a template declaring one is ACCEPTED: UpdateStack answers HTTP 200 with the StackId and the stack walks UPDATE_IN_PROGRESS to a terminal status. When the referenced Glue table's S3 location holds no non-zero-sized object, the resource create is refused by Clean Rooms ML and the stack ends UPDATE_ROLLBACK_COMPLETE with the handler failure carried on the TrainingDataset resource's ResourceStatusReason, worded 'Failed to find any non-zero sized objects in this S3 location s3://<bucket>/<prefix>/. (Service: CleanRoomsMl, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)' with error code InvalidRequest — the sentences are fixed text, while the s3:// location comes from the template's Glue data source, and the request id and attempt count are per-run values; no dataset of that name is then listed by ListTrainingDatasets. With an object present the identical update reaches UPDATE_COMPLETE and the dataset reads back through cleanroomsml GetTrainingDataset/ListTrainingDatasets, Ref resolving to the trainingDatasetArn the model constrains (CreateTrainingDataset output pattern ^arn:aws[-a-z]*:cleanrooms-ml:[-a-z0-9]+:[0-9]{12}:training-dataset/[-a-zA-Z0-9_/.]+$), with name, roleArn, trainingData[].type and the glueDataSource database/table echoed from the template. The 'Unrecognized resource types' refusal is reserved for types genuinely absent from the registry: 'Template format error: Unrecognized resource types: [<type>, ...]', error code ValidationError, HTTP 400, fixed text up to the colon and the bracketed list taken from the request.
Emulator: UpdateStack answers HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::CleanRoomsML::TrainingDataset]'. The prerequisite stack is created fine, but the update is never applied, so the expected UPDATE_ROLLBACK_COMPLETE, the graded Clean Rooms ML handler reason/error code, the ListTrainingDatasets absence assertion, and the positive control (object present -> UPDATE_COMPLETE plus the dataset read-back) are all unreachable in both checks.
Why: a client that provisions Clean Rooms ML training datasets through CloudFormation or CDK cannot deploy at all, and the ValidationError tells it its template is malformed rather than that the emulator has no provider for the type. The rollback path is also unobservable, so a caller cannot see the service-level refusal AWS surfaces through stack events.
Fix: CloudFormation's supported-resource-type registry used by template validation on the UpdateStack (and CreateStack) path, plus a resource handler for AWS::CleanRoomsML::TrainingDataset (create/read/delete, Ref -> trainingDatasetArn) that calls through to the cleanroomsml service state, including propagating the service's create refusal into the resource's ResourceStatusReason so the stack rolls back instead of being refused at submit.
Traces: the two cleanroomsml__cloudformation.deploy-cfn-cleanroomsml-training-dataset-* checks listed above. The sibling registry gap for AWS::CleanRooms::* / AWS::CleanRoomsML::ConfiguredModelAlgorithm* on the CreateStack path is filed separately under the cleanrooms__cleanroomsml__cloudformation heading.

## Evidence
Expected (AWS): after the prerequisite stack reaches CREATE_COMPLETE, UpdateStack(StackName=<stack id>, TemplateBody=<same template plus an AWS::CleanRoomsML::TrainingDataset over the Glue table>, Capabilities=[CAPABILITY_IAM]) -> HTTP 200 {"StackId": ...}; with an empty S3 location the stack ends UPDATE_ROLLBACK_COMPLETE and the TrainingDataset event's reason is ('Failed to find any non-zero sized objects in this S3 location s3://<bucket>/data/. (Service: CleanRoomsMl, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)', 'InvalidRequest'); with an object present the same update ends UPDATE_COMPLETE and GetTrainingDataset echoes the templated name, roleArn, INTERACTIONS training data, the three-column schema and the Glue database/table.
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the UpdateStack operation: Template format error: Unrecognized resource types: [AWS::CleanRoomsML::TrainingDataset] — HTTP 400, the update is not applied. Identical for both failing checks.
Message anatomy: 'Template format error: Unrecognized resource types: ' is fixed text with code ValidationError at HTTP 400; the bracketed list is derived from the submitted template. The divergence is that AWS::CleanRoomsML::TrainingDataset must not be in that list at all.

## Steps to Reproduce
1. Boot the emulator and replay the behavioral suite.
2. Run cleanroomsml__cloudformation.deploy-cfn-cleanroomsml-training-dataset-round-trip-and-delete: it first CreateStacks the prerequisites (S3 bucket, IAM role trusted by cleanrooms-ml, Glue database and table) and waits for CREATE_COMPLETE.
3. It then calls UpdateStack with the same template plus a resource of Type AWS::CleanRoomsML::TrainingDataset (DependsOn GlueTable, TrainingData[0].InputConfig.DataSource.GlueDataSource referencing the Glue database/table) and Capabilities=[CAPABILITY_IAM].
4. Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::CleanRoomsML::TrainingDataset]' instead of a 200 StackId followed by a terminal UPDATE_COMPLETE.
5. Run cleanroomsml__cloudformation.deploy-cfn-cleanroomsml-training-dataset-empty-s3-location-rejected: the same UpdateStack refusal occurs where AWS instead applies the update and ends it UPDATE_ROLLBACK_COMPLETE with the Clean Rooms ML InvalidRequest reason on the TrainingDataset resource.
