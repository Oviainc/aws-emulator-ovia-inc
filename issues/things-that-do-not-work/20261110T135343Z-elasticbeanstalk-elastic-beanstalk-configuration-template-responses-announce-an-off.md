# Elastic Beanstalk configuration-template responses announce an off-emulator TemplateUrl host, and configuration-settings reads serve the wrong resolved option set (4 causes)

> _Note: this issue was identified against the code base at commit `8ffd4f499c6d6f6b1d86ee4455070f9416ebee70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConfigurationTemplate

## Description
Wire replay of the elasticbeanstalk corpus produced 22 divergence clusters; 18 are already carried by open issues (platform-branch/platform-version catalog, not-found paths, environment reads, the empty Windows branch list). The 4 causes below are net-new and share one area: the configuration-template / configuration-settings surface. Two of them publish a URL on a host the emulator does not serve; two of them serve a resolved configuration-option set whose membership, ordering and OptionSource labelling do not match the service's. Each cause must be closed and re-replayed separately.

Cause 1 of 4 — CreateConfigurationTemplate publishes TemplateUrl on a host the emulator does not serve (fixture elasticbeanstalk-configuration-template-lifecycle-and-validation, step task#5).
AWS: recorded behavior only. The Smithy model's CreateConfigurationTemplate output shape ConfigurationSettingsDescription declares only SolutionStackName, PlatformArn, ApplicationName, TemplateName, Description, EnvironmentName, DeploymentStatus, DateCreated, DateUpdated and OptionSettings — TemplateUrl is not modeled, so the requirement comes from the recording: the Query-protocol success body (HTTP 200) carries CreateConfigurationTemplateResult.TemplateUrl, an absolute https URL addressing the stored template document in the account's Elastic Beanstalk resources bucket, path-shaped <bucket>/resources/templates/<ApplicationName>/<TemplateName>. In AWS that URL is served by the account's S3 endpoint, i.e. the caller can fetch it.
Emulator: answers 200 with a TemplateUrl whose host is the real AWS S3 endpoint for the region (host form s3-<region>.amazonaws.com) rather than the address the emulator is reached on; replay classifies the member host_not_own. The bucket/key path is right, only the authority is off-emulator.
Why: a client that follows TemplateUrl to read or diff the template leaves the emulator entirely — it either hits real AWS (or an egress refusal / name-resolution failure) and never sees the template this emulator stored, so template round-tripping and any tooling that downloads the document are broken.
Fix: the CreateConfigurationTemplate handler's response projection — the member that builds TemplateUrl — must derive the authority from the emulator's own announced S3/data address instead of a hard-coded AWS host, keeping the bucket-and-key path shape unchanged. Host and port are environment-specific and are not themselves the requirement; being reachable on the emulator is.
Traces: elasticbeanstalk-configuration-template-lifecycle-and-validation#task#5.

Cause 2 of 4 — UpdateConfigurationTemplate publishes the same off-emulator TemplateUrl (fixture elasticbeanstalk-configuration-template-lifecycle-and-validation, step task#8).
AWS: recorded behavior only, same as cause 1 — UpdateConfigurationTemplate shares the ConfigurationSettingsDescription output shape, and the recorded 200 body carries UpdateConfigurationTemplateResult.TemplateUrl addressing the same stored document, fetchable from the service.
Emulator: 200 with TemplateUrl on the real AWS S3 host, flagged host_not_own, exactly as on create — so the defect is in a second handler, not only the create path.
Why: the same client-visible break after a template update: the URL the emulator hands back for the updated template points off-emulator.
Fix: the UpdateConfigurationTemplate handler's response projection must build TemplateUrl from the emulator's own announced address (ideally through the single shared helper that cause 1 fixes, so the two handlers cannot drift).
Traces: elasticbeanstalk-configuration-template-lifecycle-and-validation#task#8.

Cause 3 of 4 — DescribeConfigurationSettings on a configuration template serves a resolved option set with the wrong membership and ordering, and labels unsourced options as Service-sourced (fixture elasticbeanstalk-configuration-template-lifecycle-and-validation, step task#6; same cluster also at task#9).
AWS: recorded behavior only for the extra members. The model's DescribeConfigurationSettings output is ConfigurationSettingsDescriptions -> ConfigurationSettingsDescription, whose only option member is OptionSettings (ConfigurationOptionSetting = ResourceName, Namespace, OptionName, Value); the recorded Query body additionally carries OptionSettingDetails entries and an OptionSource sub-structure (Identifier, Origin) that the model does not declare. The recording shows the service returning the fully resolved option set for the template: entries in the service's own order, beginning with aws:cloudformation:template:parameter options (InstanceTypeFamily, StaticFiles, EnvironmentVariables) and aws:elasticbeanstalk:application:environment options (e.g. PYTHONPATH), where some entries carry OptionSource {Identifier: Service, Origin: Service} and others carry no OptionSource at all. HTTP status 200 both sides; no error is involved.
Emulator: answers 200 with a different resolved set — the aws:cloudformation:template:parameter and aws:elasticbeanstalk:application:environment families are absent, the list starts with aws:autoscaling:asg options (Availability Zones, MaxSize) and continues in a different order, and every entry is stamped with OptionSource {Identifier: Service, Origin: Service}, including entries the service leaves without an OptionSource. Replay reports missing/extra/type_mismatch across ~190 OptionSettingDetails and OptionSettings paths in the single response.
Why: a client that reads back a template's effective configuration (to diff it, to seed an UpdateConfigurationTemplate, or to assert a platform default) sees a set that neither contains the options AWS reports nor preserves the service's ordering, and cannot tell a service-defaulted option from one with no source at all.
Fix: the DescribeConfigurationSettings projection for template scope — the resolved-option-set builder and its OptionSource stamping — must assemble the platform's full default option families (including the aws:cloudformation:template:parameter and aws:elasticbeanstalk:application:environment namespaces) in the service's order and emit OptionSource only where the service does. The resolved-vs-written aspect was previously filed and resolved (20261025T042905Z-elasticbeanstalk-elastic-beanstalk-describeconfigurationsettings-echoes-only-the-written-option.md): the emulator now does resolve a set, but its content is wrong, which that resolved issue does not cover. The open issue 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-accepts-inputs-aws-refuses-and-publishes.md concerns the DescribeConfigurationOptions catalog, a different operation.
Traces: elasticbeanstalk-configuration-template-lifecycle-and-validation#task#6 (cluster member: #task#9).

Cause 4 of 4 — DescribeConfigurationSettings on an environment loses the API origin of caller-supplied options and serves the same wrong resolved set (fixture elasticbeanstalk-environment-create-option-setting-reflected, step task#5).
AWS: recorded behavior only (OptionSettingDetails/OptionSource are unmodeled, as above). The recording shows that for an environment created with explicit OptionSettings, the resolved set reports those caller-supplied options with OptionSource {Identifier: API, Origin: API} — in this recording the aws:elasticbeanstalk:application:environment and aws:elasticbeanstalk:container:python options the CreateEnvironment request carried — while platform-supplied entries carry Service or no OptionSource, and the whole list is in the service's order starting with the aws:cloudformation:template:parameter family. Status 200.
Emulator: answers 200 with every entry labelled OptionSource {Identifier: Service, Origin: Service}, the aws:autoscaling:asg family first, and the caller-supplied namespaces not at the positions the service reports; replay flags the Namespace/OptionName/OptionSource.Identifier/OptionSource.Origin members as value_mismatch and several OptionSource members as type_mismatch.
Why: the option set a client set through the API is indistinguishable from the platform defaults, so a client cannot determine which settings it owns (the usual basis for building OptionsToRemove or an idempotent UpdateEnvironment), and positional reads of the list resolve to the wrong option.
Fix: the DescribeConfigurationSettings projection for environment scope must record, per option, whether the value came from the request (OptionSource Origin/Identifier = API) or from the platform (Service / absent) in the environment's stored option state, and emit the resolved list in the service's order — the same builder cause 3 names, which serves both scopes.
Traces: elasticbeanstalk-environment-create-option-setting-reflected#task#5.
