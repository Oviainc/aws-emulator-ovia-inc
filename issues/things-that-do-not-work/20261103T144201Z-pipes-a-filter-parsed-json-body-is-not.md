# pipes: a filter-parsed JSON body is not re-emitted to the target stage, so an InputTemplate path into the body never renders and the record is never delivered; and TagResource tag-rule refusals double-wrap their validation message in a JSON document (2 causes)

> _Note: this issue was identified against the code base at commit `92fa21155a5f185bd35dca5c5e524f786e59267d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePipe

## Description
This bundle has 2 net-new root causes, both in the pipes service; BOTH must be closed before submitting. Each is grounded in a failing check of this run that the suite did NOT mark ALREADY FILED and did NOT mark OWNED by an open issue.

Cause 1 of 2: when a pipe's FilterCriteria pattern reads the SQS message `body` as a JSON document, the later stages must be handed that body PARSED, so a target `InputTemplate` placeholder that reaches into the body (`<$.body.id>`) selects the scalar inside it. The emulator keeps the body as the text the producer sent, so such a path selects nothing, the render fails, and the record is never delivered at all.
AWS: Smithy (com.amazonaws.pipes): CreatePipe accepts SourceParameters -> PipeSourceParameters.FilterCriteria (Filters[].Pattern, an EventBridge event pattern) and TargetParameters -> PipeTargetParameters.InputTemplate, documented as "Valid JSON text passed to the target. In this case, nothing from the event itself is passed to the target" — i.e. the template IS the payload and the only parts of the event that reach the target are the ones its placeholders select. The model says nothing about how the SQS record's `body` member is typed for those placeholders, so for that detail this is recorded behavior only: the recording shows that a pipe whose filter pattern is {"body":{"type":["match-me"]}} (a pattern that can only match if `body` is read as an object) subsequently resolves `<$.body.id>` against that same parsed object and delivers the scalar `id` value — the target message body is exactly the id string, unquoted. The non-matching twin is dropped and never reaches the target.
Emulator: the check reaches the harness cap ("Error: Check timed out after 60.0s"). The non-matching leg behaves (nothing leaks to the target within its 40 s window), but the positive control — a body the filter admits — never arrives at the target at all, so the poll for it never completes. Hypothesis (code in this checkout, cited under Traces): the data plane deliberately hands the later stages "the record envelope itself, with the body as sent" (module doc of src/state/data_plane.rs), so `$.body.id` selects no value; render_template treats a path that selects no value as a FAILED render and leaves the record on the source, which is exactly a silent never-delivers rather than a wrong payload.
Why: a client whose pipe filters on a JSON body and whose target template extracts a field out of that body — the single most common Pipes shape, and the one AWS's own documentation example uses — gets NOTHING at the target. The pipe reports CurrentState RUNNING, the source message is not deleted but is also never delivered, and there is no error anywhere: a working configuration looks like an idle source. A wrong payload would at least be visible; silence is not.
Fix: the target/enrichment stage input of the pipes data plane — services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs: when the filter stage read a record's body as a JSON document, carry that parsed body in the event handed to the enrichment/target stages (and therefore to render_template's path resolution) instead of re-emitting the body as raw text, so `<$.body.…>` resolves to the value inside the body and a scalar selection renders as its own text.
Traces: pipes.pipe-filter-blocks-nonmatching-events. Code citations: services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs lines 21-32 ("A record's message body travels as the text the producer sent … What the later stages are handed is the record envelope itself, with the body as sent.") and lines 2003-2059 (render_template / selected_value: "A path that selects no one value of the event is a FAILED render — the record stays on the source").

Cause 2 of 2: TagResource refuses a tag that breaks a published tag rule with the right status and error code but wraps the validation sentence in a second JSON document, so the error message a client reads is a JSON blob with backslash-escaped apostrophes instead of the sentence.
AWS: Smithy (com.amazonaws.pipes): TagResource input `tags` is a TagMap @length 1..50 whose KEY target TagKey is @length(min:1,max:128); a map key constraint is not one the boundary validator walks, so the refusal is the service's. Recorded behavior for the wording: HTTP 400, error code `BadRequestException`, and the error Message is the bare request-validation sentence
  1 validation error detected: Value '{<tags as the member carried them, k=v entries joined with ", " inside braces>}' at '<member>' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]
Fixed text: "1 validation error detected: Value '", "' at '", "' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]". Variable parts: the echoed member value (every tag key=value the request carried) and the member name, which for TagResource's merge is `addedTags`; the two bounds are TagKey's modeled @length values. No part of the message is a per-run id, host or timestamp.
Emulator: status 400 and code BadRequestException are correct, but the Message is
  {"message": "1 validation error detected: Value \'{kkk…=irrelevant}\' at \'addedTags\' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]"}
— the sentence is correct but it is nested inside a further `{"message": …}` document and every apostrophe is backslash-escaped. Because the restJson1 error envelope ALREADY carries the message under its own `message` member, the client's Error.Message ends up being that whole document rather than the sentence.
Why: every client that shows, logs or matches on the error message of a rejected tag gets a JSON document with non-JSON escapes (a backslash before an apostrophe is not a JSON escape) in place of the sentence; a caller cannot parse it as JSON reliably and cannot read it as prose either, and anything asserting on the AWS message text fails. The constraint violation itself is reported correctly, so this is purely the message the refusal is worded with.
Fix: the tag-refusal message builder in services/service-com-amazonaws-pipes-pipes/src/state.rs — `tag_validation_document` wraps `one_validation_error(...)` in an extra `{"message": …}` envelope (and then escapes apostrophes); the refusal should carry the validation sentence itself as the BadRequestException's `message`, letting the protocol's error envelope supply the only `message` member. The same builder serves UntagResource (`removedTagKeys`) and the CreatePipe tag path, so all three are fixed together. Note that the service's own modeled ValidationException legitimately DOES word its message as a JSON document (a `ValidationErrorFields` array) — that path is correct and this fix must not change it.
Traces: pipes.tag-resource-invalid-key-rejected. Code citations: services/service-com-amazonaws-pipes-pipes/src/state.rs lines 229-301 (one_validation_error / TAG_REFUSAL_DOCUMENT_MEMBER / tag_validation_document / tag_refusal) and services/service-com-amazonaws-pipes-pipes/src/ops/tag_resource.rs lines 185-200 (the refusal site).
