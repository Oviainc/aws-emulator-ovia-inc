# ds: 3 net-new causes — every @pattern ValidationException message drops the regex ^/$ anchors, DescribeDirectories never reports RegionsInfo, and ListSchemaExtensions refuses a deleted directory instead of answering an empty list

> _Note: this issue was identified against the code base at commit `eaa123f65a60b02b9ee1461dec055a780335fce9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDirectories

## Description
THREE net-new root causes in the Directory Service (ds) control plane, all grounded in failing checks the suite lists under `### ds` that are neither ALREADY FILED nor OWNED by an open issue. All three belong to the one service, so they are bundled here; a fixer must close ALL THREE before submitting. Each cause carries its own failing check ids.

Cause 1 of 3: the shared @pattern constraint-violation formatter publishes the modeled regular expression with its `^` and `$` anchors STRIPPED, so every ds ValidationException message for a pattern failure diverges from AWS's sentence.
AWS: the message template for this error class is `<n> validation error detected: Value '<value>' at '<memberPath>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>`. Fixed text is everything but three variable parts — `<n>` (the number of detected errors), `<value>` (the rejected value, taken from the request), `<memberPath>` (the lowercase input-member path, including the list index and `.member.` segment for a list member) — and `<pattern>`, which is the Smithy @pattern trait string VERBATIM, anchors included. Smithy (services/service-com-amazonaws-directoryservice-directoryservice-20150416/smithy-model/com-amazonaws-directoryservice-directoryservice-20150416.json): CidrIp @pattern `^(([0-9]|[1-9][0-9]|1[0-9]{2}|2[0-4][0-9]|25[0-5])\.){3}([0-9]|[1-9][0-9]|1[0-9]{2}|2[0-4][0-9]|25[0-5])(\/([1-9]|[1-2][0-9]|3[0-2]))$`; DirectoryName @pattern `^([a-zA-Z0-9]+[\\.-])+([a-zA-Z0-9])+$`; DirectoryId @pattern `^d-[0-9a-f]{10}$`; TagValue @pattern `^([\p{L}\p{Z}\p{N}_.:/=+\-@]*)$`. Each violation is refused 400 ValidationException with the template above carrying that pattern, anchors and all; the recorded ds responses in these four checks all show the anchored form.
Emulator: 400 ValidationException with the right error code, the right `<n>`, the right `<value>` and the right `<memberPath>`, but the trailing regular expression has its leading `^` and trailing `$` removed — e.g. `… Member must satisfy regular expression pattern: d-[0-9a-f]{10}` where AWS sends `… ^d-[0-9a-f]{10}$`. The same delta appears on all four member paths exercised (`ipRoutes.<i>.member.cidrIp`, `name`, `directoryId`, `tags.<i>.member.value`), which is what makes this one formatter-level cause rather than four operation bugs. Note the direction: most AWS services DO strip the anchors and this emulator's shared helper normalizes for that; Directory Service does NOT, so the generic unanchoring is wrong for this crate.
Why: the status, the error code and the message are all requirements of the error class. A client, SDK test or CLI user that asserts on AWS's sentence never matches, and the regular expression the refusal actually publishes is UNANCHORED — so anything regenerated from it (a client-side pre-validator, a doc or diagnostic surface) accepts substring matches AWS rejects (e.g. `xxd-0123456789yy` satisfies `d-[0-9a-f]{10}` but not `^d-[0-9a-f]{10}$`).
Fix: the single input-validation layer of this crate that formats a @pattern failure into the ValidationException message (the validate step feeding `crate::scaffolded::Scaffolded::validation`, and the pattern-rendering helper it calls — the crate must emit the @pattern trait value exactly as the model states it instead of calling the shared `unanchored` renderer).
Related-but-not-covering open issues: 20261109T072650Z-ds-validationexception-message-omits-regex-anchors-for-directoryid-pattern.md and 20261109T072650Z-ds-validationexception-message-omits-regex-anchors-for-certificateid-and.md report the identical defect from the WIRE corpus on DescribeSettings/DescribeCertificate/etc.; neither carries the replay key of any behavioral check listed here, and neither covers the CidrIp, DirectoryName or TagValue paths. One formatter fix closes all of them, but the four checks below must be re-replayed.
Traces: ds.add-ip-routes-malformed-cidr-rejected (CidrIp, path `ipRoutes.1.member.cidrIp`), ds.create-microsoft-ad-single-label-domain-name-rejected-validation (DirectoryName, path `name`), ds.describe-client-authentication-settings-nonexistent-directory (DirectoryId, path `directoryId`), ds.tags-unicode-value-round-trip (TagValue, path `tags.1.member.value`).

Cause 2 of 3: DescribeDirectories never reports the directory's RegionsInfo, so a Managed Microsoft AD directory has no primary Region.
AWS: Smithy — DirectoryDescription$RegionsInfo targets RegionsInfo{PrimaryRegion: RegionName (length 8..32), AdditionalRegions: list}, documented "Lists the Regions where the directory has replicated" / "The Region where the Managed Microsoft AD directory was originally created". Recorded behavior: DescribeDirectories reports RegionsInfo for a VPC-placed directory, with PrimaryRegion equal to the Region the create was issued in and AdditionalRegions absent/empty until AddRegion is called. The Region string itself is an environment value, not a requirement; the member's PRESENCE and the rule (PrimaryRegion == the creating Region, no AdditionalRegions without AddRegion) are.
Emulator: the member is simply absent from every DirectoryDescription — `Directory::to_description` builds the struct and leaves `regions_info` to `..DirectoryDescription::default()`, so a client reading `DirectoryDescriptions[0].RegionsInfo` gets nothing and `PrimaryRegion` is None. The same rendering point also leaves NetworkType unset for these directories (the replayed description shows no NetworkType key at all), which is the very next assertion of the same check.
Why: multi-Region replication is read through this member. A client that resolves which Region owns a directory before calling AddRegion/RemoveRegion, or that lists the replicated Regions to pick an endpoint, finds no data at all and cannot distinguish "not replicated" from "field not served"; any IaC or inventory tool that reconciles a directory's Regions sees a missing field instead of a modeled answer.
Fix: the one place a stored directory is rendered as DirectoryDescription in the ds service state (`Directory::to_description`), plus the create handlers that must persist the Region the directory was created in so the renderer can report it as PrimaryRegion with no AdditionalRegions until AddRegion adds one.
Traces: ds.simple-ad-small-lifecycle-to-active-then-deleted.

Cause 3 of 3: ListSchemaExtensions refuses a directory the account has deleted with EntityDoesNotExistException, where AWS answers 200 with an empty SchemaExtensionsInfo list.
AWS: Smithy — ListSchemaExtensions(DirectoryId required) returns SchemaExtensionsInfo + NextToken and models ClientException / EntityDoesNotExistException / InvalidNextTokenException / ServiceException. Recorded behavior: after a directory that has been through StartSchemaExtension is deleted and its teardown completes, ListSchemaExtensions(DirectoryId=<the deleted id>) answers 200 with SchemaExtensionsInfo == [] — the extension records go away with the directory and the read for the account's remembered-deleted id is an empty listing, not a refusal.
Emulator: 400 EntityDoesNotExistException with message "Directory: '<directory id>' does not exist. : RequestId: <this call's request id>" (fixed text "Directory: ", "' does not exist. : RequestId: "; the directory id comes from the request and the request id from the call). src/ops/list_schema_extensions.rs looks the id up in `store.directories` and maps a miss straight to EntityDoesNotExistException(no_such_directory), never consulting the store's `deleted_directories` memory, so the post-teardown read of the schema-extension inventory can only ever be refused.
Why: the documented teardown assertion — that deleting a directory removes its schema-extension records — is unreachable: a client cannot confirm the cascade, and code that reads a directory-scoped inventory after a delete gets a 400 where AWS gives it an empty answer, so it reports a failure for a normal, completed teardown.
Fix: ListSchemaExtensions' handler (services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/list_schema_extensions.rs, the `store.directories.get(...).ok_or_else(...)` lookup) together with the remembered-deleted-directory memory in src/state.rs: an id this account was issued and has since deleted must yield an empty page, with EntityDoesNotExistException reserved for an id the account never held.
Traces: ds.e2e-schema-extension-teardown-flow.
