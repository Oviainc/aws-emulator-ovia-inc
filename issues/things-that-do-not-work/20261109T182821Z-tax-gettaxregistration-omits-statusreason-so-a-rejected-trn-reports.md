# GetTaxRegistration omits statusReason, so a Rejected TRN reports no reason for the rejection

> _Note: this issue was identified against the code base at commit `41c5ae389f495755d1c1e47282b4b58fd25764aa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTaxRegistration

## Description
One root cause in the taxsettings emulator: the TaxRegistration projection GetTaxRegistration reports carries no `statusReason`, so a registration whose TRN validation FAILED is reported as terminally `Rejected` with nothing saying why.

Cause 1 of 1: GetTaxRegistration's 200 response omits `taxRegistration.statusReason` for a registration in the `Rejected` status.
  AWS: recorded behavior only — the TaxRegistration shape in this repo's checked-out Smithy model (services/service-com-amazonaws-taxsettings-taxsettings/smithy-model/com-amazonaws-taxsettings-taxsettings.json) declares registrationId, registrationType, legalName, status, sector, taxDocumentMetadatas, certifiedEmailId, additionalTaxInformation and legalAddress and declares NO statusReason member at all (smithy_query query="shape" shape="TaxRegistration"; smithy_query query="shape" shape="StatusReason" -> shape not found). The model documents only the status enum itself: TaxRegistration$status — "The status of your TRN. This can be either Verified, Pending, Deleted, or Rejected." (TaxRegistrationStatus values Verified|Pending|Deleted|Rejected). The recording shows AWS answering GetTaxRegistration with 200 and, alongside that status, a nested `taxRegistration.statusReason` structure of two members — a reason `code` and a human-readable `message` — explaining the outcome of the TRN validation. In the recorded response the code is "OTHER" and the message is "Your tax registration could not be verified. Please review your information and resubmit."; the whole message is FIXED text for this reason class — no account id, registration id, registration type, jurisdiction, timestamp or other per-run value appears anywhere in it, and the code is a closed reason token rather than a generated value. The requirement is therefore that a registration reported in a non-successful terminal status carries a statusReason whose code names the reason class and whose message is the fixed sentence AWS words for that class; a registration AWS does not attach a reason to carries no statusReason (the member is optional, not required).
  Emulator: the emulator answers 200 and every other member of the registration matches the recording, but `$.taxRegistration.statusReason` is absent (replay detail: "$.taxRegistration.statusReason: missing (expected {'code': 'OTHER', 'message': 'Your tax registration could not be verified. Please review your information and resubmit.'}, got None)"). This is structural, not conditional: the projection that builds every reported registration has no such field to fill. `StoredTaxRegistration::to_tax_registration` (services/service-com-amazonaws-taxsettings-taxsettings/src/state.rs, around lines 1552-1566) constructs TaxRegistration from exactly the nine modeled members and nothing else, and the sibling projection `to_tax_registration_with_jurisdiction` (same file, around lines 1572-1584) does the same; the stored record itself never records WHY `trn_validation_status` (src/state.rs, around lines 80-94) settled a record to STATUS_REJECTED — it returns only the status string, discarding the reason, so there is nothing for a projection to report even if the member existed. GetTaxRegistration's handler (src/ops/get_tax_registration.rs, handle, around lines 155-168) settles the due validation and hands the record straight to that projection, so no statusReason can appear on any code path and no Rejected registration ever carries one.
  Why: statusReason is the only channel by which a client learns why its tax registration was refused and what to do about it. A caller that submits a TRN, polls GetTaxRegistration until the status is terminal and then surfaces or branches on the rejection reason reads `taxRegistration['statusReason']['code']` / `['message']` — against AWS it gets a reason class and a remediation sentence, against the emulator it gets a KeyError (or a None that renders as a blank reason in operator tooling). Code that routes on the reason code (retry vs. ask the user to correct the submission vs. escalate) cannot route at all, and a console or support workflow that displays the reason shows an unexplained "Rejected". The emulator's registration therefore looks like a successfully-read record that happens to be rejected for no stated cause, which is a strictly weaker contract than the one AWS serves.
  Fix: the registration's reported shape and the state that backs it. The TaxRegistration shape served by this crate must carry the optional nested statusReason (reason `code` + `message`) that AWS's response has and the checked-out model omits; `StoredTaxRegistration` must RECORD the reason the TRN validation settled on — the rejection reason belongs beside the status that `trn_validation_status` decides in src/state.rs, not re-derived per reader — and both `to_tax_registration` and `to_tax_registration_with_jurisdiction` must project it so GetTaxRegistration and ListTaxRegistrations report one record the same way. The message must be the fixed text AWS words for the reason class, emitted from a single constructor in src/state.rs rather than inlined in the handler, with statusReason left absent for a registration that has no reason to report (e.g. Verified/Pending). Note the open issue 20261030T005839Z-taxsettings-batchgettaxexemptions-omits-an-accessible-account-from-taxexemptiondetailsmap-when.md also touches PutTaxRegistration/state.rs wording, and 20261029T100532Z-taxsettings-puttaxinheritance-event-propagation.md touches this service, but neither covers the missing statusReason member on the reported registration — this is net-new.
  Traces: taxsettings-tax-registration-lifecycle#task#2 (GetTaxRegistration, expected 200 / actual 200, diverging key $.taxRegistration.statusReason).

Fixed vs variable parts of that message: the ENTIRE sentence "Your tax registration could not be verified. ## Steps to Reproduce
1. Replay fixture taxsettings-tax-registration-lifecycle against the emulator and stop at step task#2, or reproduce by hand:
2. POST /DeleteTaxRegistration for the caller's account (tolerating ResourceNotFoundException) so the account holds no primary TRN.
3. POST /PutTaxRegistration with a taxRegistrationEntry whose registrationId is written the way its jurisdiction's numbers are written but is NOT one the jurisdiction's authority confirms (i.e. a well-formed number whose check rule fails), so the TRN validation settles to the terminal `Rejected` status. Observe 200 with status "Pending".
4. Wait for the validation the write owes to fall due, then POST /GetTaxRegistration with {"accountId": "<caller account id>"}.
5. Observe HTTP 200 whose taxRegistration reports status "Rejected" with NO `statusReason` member. AWS returns the same 200 and status with a nested statusReason {"code": "<reason class, e.g. OTHER>", "message": "Your tax registration could not be verified. Please review your information and resubmit."}, so a client reading taxRegistration['statusReason']['message'] succeeds against AWS and fails against the emulator.
