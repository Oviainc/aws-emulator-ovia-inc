# Elastic Beanstalk state-guard refusals use the wrong error code and non-AWS message text on three rejection paths (3 causes)

> _Note: this issue was identified against the code base at commit `a57dea262f41459244daf18c6d5b4cdf00e6a648`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteApplication

## Description
THREE distinct root causes in the elasticbeanstalk emulator, all in the same service, each grounded in a failing behavioral check of this suite that the replay marked neither ALREADY FILED nor OWNED. THREE causes must be closed before submitting.

Adjacent open issues cover neighbouring ground but do NOT carry these checks (the suite marked none of these three failures OWNED, so those issues' recorded replay keys no longer match them): 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-refusal-messages-use-non-aws-templates.md (other rejection paths of the same service), 20261102T085012Z-elasticbeanstalk-elastic-beanstalk-managed-action-and-platform-quota-refusals.md (its Cause 1 reads the SAME ApplyEnvironmentManagedAction wording fault from a DIFFERENT check, apply-environment-managed-action-invalid-state-rejected; the check below is a separate, still-unowned grounding of it and must be re-replayed with it), and 20261023T205650Z-elasticbeanstalk-elastic-beanstalk-control-plane-guards-are-not-enforced.md (guard enforcement, not refusal wording).

Cause 1 of 3: AbortEnvironmentUpdate against a Ready environment with no update in progress is refused with the emulator's own sentence instead of AWS's invalid-state sentence.
AWS: Smithy: AbortEnvironmentUpdate(EnvironmentId, EnvironmentName @length 4..40) -> Unit; the only modelled operation error is InsufficientPrivilegesException (HTTP 403), so this refusal is the service-common InvalidParameterValue. Recorded behavior: a Ready environment that reports no abortable operation refuses the call with Error.Code 'InvalidParameterValue' / HTTP 400 and Error.Message "Environment named <EnvironmentName> is in an invalid state for this operation. Must be pending deployment." The fixed text is "Environment named " ... " is in an invalid state for this operation. Must be pending deployment."; the ONLY variable part is the environment name taken from the request (the recording's 'sim2real-eb-env-eb73883d5d36' is that run's generated name filling the template, not a requirement).
Emulator: the code and status match, but Error.Message is the emulator's own wording: "Environment <EnvironmentName> is not in a state from which an update can be aborted. No abortable operation is in progress." — a different sentence, missing the "named" form and the "Must be pending deployment." clause.
Why: a client that keys on AWS's invalid-state sentence (or on the 'Must be pending deployment' clause, which is how AWS tells an idle environment apart from a missing one) does not recognise the refusal and cannot distinguish 'nothing to abort' from any other InvalidParameterValue on this operation.
Fix: the no-abortable-operation refusal construction in the AbortEnvironmentUpdate handler's validation (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/abort_environment_update.rs, the `!environment.abortable_operation_in_progress` branch) — emit AWS's invalid-state template with only the environment name substituted.
Traces: elasticbeanstalk.abort-environment-update-unknown-env-fails (its earlier leg, the unknown-environment InvalidParameterValue "No Environment found for EnvironmentName = '<name>'.", already matches; the later positive-control leg that aborts a real in-progress update is never reached, so it is unverified).

Cause 2 of 3: ApplyEnvironmentManagedAction's unresolvable-ActionId refusal is worded from the request instead of AWS's fixed sentence.
AWS: Smithy: ApplyEnvironmentManagedAction(EnvironmentName, EnvironmentId optional; ActionId required) -> ApplyEnvironmentManagedActionResult, modelled errors ElasticBeanstalkServiceException (client, HTTP 400) and ManagedActionInvalidStateException (client, HTTP 400, awsQueryError ManagedActionInvalidStateException). Recorded behavior: an ActionId that never existed, against an environment with no managed-update data, is refused with Error.Code 'ElasticBeanstalkServiceException' / HTTP 400 and Error.Message 'Managed update data not found for this environment.' — the WHOLE sentence is fixed text with NO variable part: neither the ActionId nor the environment name appears in it.
Emulator: the Error.Code and status match, but Error.Message is built from the request and state: "No managed action with ActionId = '<ActionId>' exists for environment <EnvironmentName>." (the recording's uuid '50760014-55e5-4885-8d88-d96abf5d72c3' and name 'sim2real-env-2793910303ac' are that run's generated inputs filling the emulator's template, not part of any requirement).
Why: AWS reports this class as 'this environment has no managed-update data at all', while the emulator reports 'that one action id is unknown'. A client keying on AWS's fixed sentence to decide whether managed updates are configured cannot recognise the refusal, and one parsing the emulator's text gets an ActionId-scoped diagnosis AWS never gives. Distinguishing this class from ManagedActionInvalidStateException is also lost.
Fix: the unknown/unresolvable-ActionId error construction in the ApplyEnvironmentManagedAction handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/apply_environment_managed_action.rs) — emit the fixed sentence with no request-derived substitution.
Traces: elasticbeanstalk.apply-environment-managed-action-unknown-action-id-rejected (the check's terminal reads, that the pending-action set and the completed/failed history are unchanged, are never reached and so are unverified).

Cause 3 of 3: DeleteApplication on an application with a running environment and TerminateEnvByForce unset is refused with the WRONG error code and a non-AWS message.
AWS: Smithy: DeleteApplication(ApplicationName required @length 1..100, TerminateEnvByForce boolean) -> Unit, modelling OperationInProgressException (HTTP 400, awsQueryError code 'OperationInProgressFailure'); the documentation states 'You cannot delete an application that has a running environment.' Recorded behavior: this particular refusal is NOT that modelled error — it is Error.Code 'InvalidParameterValue' / HTTP 400 with Error.Message "Unable to delete application <ApplicationName> because it has a version that is deployed to a running environment." The fixed text is "Unable to delete application " ... " because it has a version that is deployed to a running environment."; the only variable part is the application name from the request (OperationInProgressFailure is reserved for a concurrent operation on the same element, not for this state guard). Recorded behavior governs here, since the model lists only the operation's declared error set and not the common errors.
Emulator: refuses with Error.Code 'OperationInProgressFailure' (OperationInProgressException) and Error.Message "Cannot delete application <ApplicationName> because it still has running environments: <env names>. Terminate them, or set TerminateEnvByForce." — wrong error code, wrong message template, and it leaks the environment-name list AWS does not include.
Why: the guard is reported under a code that means something else, so a client retrying OperationInProgressFailure (a transient, concurrency class) retries forever instead of terminating the environment or setting TerminateEnvByForce, and a client branching on InvalidParameterValue never sees the refusal. Error-code-keyed teardown and CI cleanup logic mis-route.
Fix: the running-environment guard's error construction in the DeleteApplication handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/delete_application.rs, the `terminate_env_by_force != Some(true)` branch that returns OperationInProgressException) — raise the service-common InvalidParameterValue with AWS's 'Unable to delete application ... because it has a version that is deployed to a running environment.' text.
Traces: elasticbeanstalk.delete-application-with-running-environment-must-fail (its later legs — the application and environment surviving the refused delete, and the identical call succeeding once TerminateEnvByForce is set — are never reached and so are unverified).
