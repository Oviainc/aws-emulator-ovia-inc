# ACM certificate control plane: ImportCertificate and UpdateCertificateOptions refuse with the wrong error code, and GetCertificate/ResendValidationEmail carry the wrong refusal message (4 causes)

> _Note: this issue was identified against the code base at commit `c8d80ea15f1454d07f388eb2b932b3a5430349f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportCertificate

## Description
Four distinct root causes in ACM's certificate control-plane refusals, each grounded in failing behavioral checks of this suite that are NOT carried as replay keys by any open issue. Related filing: open issue 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md covers the DescribeCertificate projection, the DNS-validation engine, the constraint-violation envelope and the not-found text; none of its eight causes is any of the four below, and its Issue-Trace-Ids do not carry these six checks.

Cause 1 of 4: a certificate-material defect at ImportCertificate is classified InvalidParameterException instead of ValidationException, with a different message.
AWS: Smithy ImportCertificate(Certificate required @length 1..32768 blob, PrivateKey required @length 1..5120 sensitive blob, CertificateChain, Tags @length 1..50) models BOTH InvalidParameterException and ValidationException as distinct client errors at HTTP 400. Recorded behavior (both legs verified against real ACM): a Certificate blob whose body can no longer be base64-decoded is refused 400 ValidationException 'The certificate is not PEM-encoded or is not valid.', and an already-expired certificate is refused 400 ValidationException 'The certificate is expired. You can Import a certificate only during its validity period.' Both messages are entirely fixed text — nothing from the request is interpolated. ValidationException is the request-shape/blob-format layer; InvalidParameterException is reserved for structurally-decodable but semantically-invalid certificate content.
Emulator: both refusals come back with code InvalidParameterException (status 400), so the check never reaches the message assertion.
Why: the two codes are modelled separately and clients branch on them — a caller that treats ValidationException as 'fix the material you submitted' and InvalidParameterException as a different class takes the wrong branch, and retry/alarm logic keyed on ACM's code mis-files every bad-import. Since ACM uses one code for every material defect, the message is what identifies expiry versus a malformed PEM, so the code AND the text both have to match.
Fix: the refusal classification and message construction in the import path, services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs (the certificate-decode and validity-window checks).
Traces: acm.import-certificate-expired-rejected, acm.op-contract-import-certificate.

Cause 2 of 4: UpdateCertificateOptions on a certificate that is not yet ISSUED is refused with InvalidStateException instead of ValidationException.
AWS: Smithy UpdateCertificateOptions(CertificateArn required, Options required) models ConflictException, InvalidArnException, InvalidStateException, LimitExceededException, ResourceNotFoundException and ValidationException, all client errors at 400. Recorded behavior: changing any Options field on a certificate still in PENDING_VALIDATION is refused 400 ValidationException with the fixed message 'Certificate is not issued' when migrating the renewal ValidationMethod, and 'Export option for certificates cannot be updated' when toggling Export; the certificate's Status and Options are left unchanged.
Emulator: the first leg is refused with code InvalidStateException, so the modelled class a client catches for this precondition never arrives (the second leg and the unchanged-state assertions are unreached).
Why: ACM deliberately returns the request-validation class, not the state class, for this precondition; a client catching ValidationException (as the API's own contract directs) sees an unhandled InvalidStateException instead and aborts, while a client catching InvalidStateException retries a call that will never succeed for this reason.
Fix: the precondition check in services/service-com-amazonaws-acm-certificatemanager/src/ops/update_certificate_options.rs — raise ValidationException with the fixed texts above instead of InvalidStateException.
Traces: acm.op-contract-update-certificate-options.

Cause 3 of 4: the RequestInProgressException from GetCertificate on a not-yet-issued certificate carries a generic sentence instead of ACM's ARN- and account-naming message.
AWS: Smithy GetCertificate(CertificateArn required) models RequestInProgressException (client, 400). Recorded behavior: calling it on a certificate still in PENDING_VALIDATION is refused 400 RequestInProgressException with 'Certificate <CertificateArn> in account <account-id> not yet issued' — fixed text around two variable parts, the ARN taken from the request and the account id taken from that ARN, with no terminating period.
Emulator: code RequestInProgressException and status 400 are correct; the message is 'The certificate request is in process and the certificate in your account has not yet been issued.' — different fixed text that names neither the certificate nor the account.
Why: the message is produced by a known rule from the request, so the rule is the requirement. A caller polling many certificates uses the ARN in this message to attribute the refusal; the emulator's text is unattributable, and fixtures matching ACM's wording diverge on every pending GetCertificate.
Fix: the not-yet-issued refusal in services/service-com-amazonaws-acm-certificatemanager/src/ops/get_certificate.rs.
Traces: acm.get-certificate-pending-validation-fails, acm.op-contract-get-certificate.

Cause 4 of 4: the InvalidStateException from ResendValidationEmail before the initial validation email has been dispatched carries an invented, ARN-interpolating message.
AWS: Smithy ResendValidationEmail(CertificateArn required, Domain required, ValidationDomain required) models InvalidStateException (client, 400). Recorded behavior: calling it immediately after RequestCertificate(ValidationMethod='EMAIL') returns, for the certificate's own validation domain, is refused 400 InvalidStateException with exactly 'The certificate request is still in progress. Try again later' — all fixed text, no identifier interpolated, no terminating period; the gate is short-lived and the identical call then succeeds.
Emulator: code InvalidStateException is correct; the message is 'The request for certificate <CertificateArn> is still in progress: its initial domain validation email has not been sent yet. Try again later.' — different fixed text, the request's ARN spliced in and a trailing period added.
Why: the text is generated by a fixed rule, so the rule is the requirement; a client that distinguishes this short-lived gate (retry) from the other InvalidStateException ResendValidationEmail returns (the certificate is not EMAIL-validated for that domain — do not retry) can only do so by the message, and matches neither against the emulator.
Fix: the initial-dispatch gate's error construction in services/service-com-amazonaws-acm-certificatemanager/src/ops/resend_validation_email.rs.
Traces: acm.op-contract-resend-validation-email.
