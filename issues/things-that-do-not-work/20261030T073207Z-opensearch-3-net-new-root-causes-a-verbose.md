# opensearch: 3 net-new root causes — a Verbose dry run never reaches 'succeeded' (reports 'COMPLETED'), the unknown-DryRunId refusal is emulator-worded, and a CFN secretsmanager dynamic reference reaches CreateDomain unresolved

> _Note: this issue was identified against the code base at commit `117833b2d4a5a382d56cda01f3bfd00f436cea08`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDryRunProgress

## Description
Three distinct net-new root causes in the opensearch service grouping. All three must be closed before this issue is resubmitted.

Note on prior art: open issue 20261024T055421Z-opensearch-domain-data-plane-is-not-served-and.md lists these same check ids, but for causes that are now past — its Cause 4 was "UpdateDomainConfig with a dry run returns no DryRunProgressStatus" and its Cause 3 was "CFN Outputs carry no OutputValue". The emulator now DOES return DryRunProgressStatus (with a UUID-shaped DryRunId) and the FGAC stack now fails earlier, at resource create. The three causes below are the divergences that surfaced behind that issue; none of them carries that issue's replay keys.

Cause 1 of 3: a Verbose dry run's DryRunStatus is reported as 'COMPLETED' and never takes a terminal value in AWS's vocabulary.
AWS: Smithy: opensearch#UpdateDomainConfig output members are DomainConfig (required), DryRunResults and DryRunProgressStatus; opensearch#DryRunProgressStatus = {DryRunId (required, GUID), DryRunStatus (required, String), CreationDate (required, String), UpdateDate (required, String), ValidationFailures, AcceptedWarnings}. DryRunStatus is a free String with no modelled enum, so the value set is recorded behavior only: AWS reports the LOWERCASE statuses, with the terminal values 'succeeded' and 'failed' (the recordings poll DescribeDryRunProgress until DryRunStatus is in ('succeeded','failed') and then assert equality with 'succeeded').
Emulator: UpdateDomainConfig(DryRun=true, DryRunMode='Verbose') and the subsequent DescribeDryRunProgress report DryRunStatus 'COMPLETED' — an uppercase value AWS does not use — alongside DryRunResults {'DeploymentType': 'Blue/Green'} and ValidationFailures []. The record never changes to 'succeeded'/'failed', so no AWS-shaped terminal state is ever observable.
Why: the documented way to validate a configuration change before applying it is to trigger a Verbose dry run and poll its DryRunId to a terminal status. A client doing exactly that never observes a terminal status and polls until its own deadline, then reports the change as unvalidated. Two of the failing checks do not even get an assertion message out of it: their bounded polls burn the whole run budget waiting for a status that cannot arrive.
Fix: the dry-run state machine behind UpdateDomainConfig's DryRun path and the DescribeDryRunProgress response projection in the opensearch service crate — settle a Verbose dry run through AWS's lowercase status vocabulary to a terminal 'succeeded' (or 'failed' when ValidationFailures is non-empty), and emit that value from both the UpdateDomainConfig dry-run response and DescribeDryRunProgress.
Traces: opensearch.dry-run-progress-ttl-expiration-requires-retrigger (hard assertion, carries the observed body), opensearch.dry-run-progress-ttl-expiry-after-completion (poll for a terminal status never returns), opensearch.visibility-timeout-ttl-dry-run-progress-expiry (same poll; the check is cut off at the harness ceiling while waiting for 'succeeded'/'failed').

Cause 2 of 3: DescribeDryRunProgress's unknown-DryRunId refusal carries emulator-authored wording that names the domain.
AWS: Smithy: DescribeDryRunProgress (GET /2021-01-01/opensearch/domain/{DomainName}/dryRun, DryRunId in the dryRunId query string) models ResourceNotFoundException for a DryRunId that does not exist. The refusal Message is 'No Dry Run found for the provided DryRunId: <DryRunId>' — the fixed text is 'No Dry Run found for the provided DryRunId: ' and the only variable part is the DryRunId taken verbatim from the request; the domain name is not part of the message.
Emulator: the error code is right (ResourceNotFoundException) but the Message reads 'Dry run not found for domain <DomainName>: <DryRunId>' — emulator wording, a different sentence, and it leaks the domain name into a message AWS builds from the DryRunId alone.
Why: a client that matches or surfaces the service's not-found text (log scraping, error classification, user-facing passthrough) sees a sentence AWS never emits, and the parts it would parse out (the id) sit in a different position than AWS puts them.
Fix: the not-found refusal in the DescribeDryRunProgress handler of the opensearch service crate — build the message from the fixed AWS text plus the request's DryRunId only.
Traces: opensearch.dry-run-progress-reporting.

Cause 3 of 3: a CloudFormation secretsmanager dynamic reference is handed to OpenSearch CreateDomain unresolved, so no FGAC domain can be deployed with secret-sourced master credentials.
AWS: CloudFormation resolves a '{{resolve:secretsmanager:<secret-arn-or-name>:SecretString:<json-key>}}' dynamic reference at provisioning time and passes the RESOLVED value to the resource provider, so AWS::OpenSearchService::Domain's AdvancedSecurityOptions.MasterUserOptions receives a real user name and password and the stack reaches CREATE_COMPLETE. Smithy: opensearch#MasterUserOptions.MasterUserName -> Username (@length min 1 max 64, @sensitive) and MasterUserPassword -> Password (@length min 8 max 128, @sensitive) — so a literal dynamic-reference placeholder, which is far longer than 64 characters, is CORRECTLY refused by CreateDomain; the defect is that it was never resolved.
Emulator: the stack goes CREATE_FAILED with 'The following resource(s) failed to create: [Domain].' and the Domain resource status reason 'Resource handler returned message: "Invalid request provided: 2 validation errors detected: Value \'{{resolve:secretsmanager:<secret-arn>:SecretString:username}}\' at \'advancedSecurityOptions.masterUserOptions.masterUserName\' failed to satisfy constraint: Member must have length less than or equal to 64; Value \'{{resolve:secretsmanager:<secret-arn>:SecretString:password}}\' at \'advancedSecurityOptions.masterUserOptions.masterUserPassword\' failed to satisfy constraint: Member must have length less than or equal to 128 (Service: OpenSearch, Status Code: 400, ...)" (HandlerErrorCode: InvalidRequest)'. The quoted values are the unresolved '{{resolve:secretsmanager:...:SecretString:<key>}}' template placeholders themselves — their fixed text is the whole '{{resolve:secretsmanager:' ... ':SecretString:' ... '}}' form, with the secret ARN and the JSON key coming from the template; the 400 and the two length sentences are the correct OpenSearch refusal for the string the provider was given.
Why: the documented, credential-safe way to deploy an FGAC domain — generate the master credentials into a Secrets Manager secret in the same stack and reference them, never putting them in the template — cannot be deployed at all. Every such stack fails, and the failure is reported as an OpenSearch validation error, pointing a user at their own (valid) template instead of at the unresolved reference.
Fix: CloudFormation's dynamic-reference resolution for the '{{resolve:secretsmanager:...:SecretString:<key>}}' form, applied to resource properties before the resource provider is invoked (and, for Fn::Sub-composed references, after the Sub is expanded). This cause is filed under the opensearch service because the failing check belongs to the opensearch suite grouping; the component it belongs in is the CloudFormation crate. Related open issues, neither of which carries this check's replay key: 20261023T114649Z-cloudformation-outputs-carry-no-outputvalue-failed-resources-never.md (states dynamic references are ignored) and 20261024T190718Z-secretsmanager-cloudformation-managed-secrets-aws-secretsmanager-secret-deploys-but.md.
Traces: opensearch.deploy-opensearch-3-fgac-secret-master-basic-auth.
