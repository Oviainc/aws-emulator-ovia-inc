=== Cause 1 of 3: an AWS::ApiGatewayV2::Api declared by a BodyS3Location whose object does not exist must fail the stack on that resource; the emulator reports a stack with no resources at all. ===
Failing check: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-bodys3location-missing-object-fails-stack.
AWS: recorded behavior only for the CloudFormation wrapping; Smithy grounds the underlying refusal — ImportApi (PUT /v2/apis, 201) takes Body (required) and declares BadRequestException @httpError 400 among its errors, and AWS::ApiGatewayV2::Api's BodyS3Location is resolved through that operation. The recording shows the stack reaching CREATE_FAILED with EXACTLY ONE failed resource, the Api resource (logical id S3Api in the check), whose ResourceStatus is CREATE_FAILED and whose ResourceStatusReason is the fixed text: Resource handler returned message: "Unable to parse BodyS3Location (Service: null; Status Code: 0; Error Code: null; Request ID: null; Proxy: null) (Service: null; Status Code: 404; Error Code: BadRequestException; Request ID: null; Proxy: null)" (RequestToken: <token>, HandlerErrorCode: GeneralServiceException). Every part of that string is fixed for this failure class except the RequestToken, which is the per-call CloudFormation request token taken from the request; the HandlerErrorCode is GeneralServiceException and the inner error code is BadRequestException with status 404.
Emulator: DescribeStackResources/DescribeStackEvents for the stack report NO resources: the check fails with "AssertionError: the S3Api resource must be the one that failed, stack resources report []". So the provisioner neither created nor failed the Api resource — the failure is not attributed to any resource, and a caller cannot tell which resource of the template is at fault.
Why: the whole point of a CREATE_FAILED resource is that the reason names the one resource and the one refusal. A client that reads stack resources to diagnose a bad BodyS3Location gets an empty list, so an unreadable S3 body is indistinguishable from a template that declared nothing; automation that keys off the failed logical id or on HandlerErrorCode cannot work.
Fix: the AWS::ApiGatewayV2::Api provisioner's BodyS3Location path (resolve the S3 object, map the ImportApi/S3 refusal into a CREATE_FAILED on that resource with the reason text above) plus the CloudFormation resource-status recording so failed resources appear in DescribeStackResources/DescribeStackEvents.
Traces: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-bodys3location-missing-object-fails-stack.

=== Cause 2 of 3: FailOnWarnings=true against a Body that produces import warnings does not fail the stack. ===
Failing check: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-failonwarnings-true-fails-create-on-import-warning.
AWS: Smithy — ImportApi.FailOnWarnings is an @httpQuery("failOnWarnings") boolean and ImportApi's output carries Warnings (__listOf__string); ImportApi declares BadRequestException @httpError 400. The recording shows that with FailOnWarnings=true and an OpenAPI Body containing an unsupported `http`-scheme security definition, import refuses 400 BadRequestException and CloudFormation turns it into CREATE_FAILED, with ResourceStatusReason wrapping API Gateway's own warning text verbatim: Resource handler returned message: "Warnings found during import:\n\tUnsupported Security Scheme type 'http' for '<schemeName>'. Ignoring.\n\tMethod '<METHOD>' on resource '<path>' specified security, but no custom authorizers were created and the extension x-amazon-apigateway-auth was not properly set. This method will be not be secured. (Service: AmazonApiGatewayV2; Status Code: 400; Error Code: BadRequestException; Request ID: <id>; Proxy: null) (Service: null; Status Code: 404; Error Code: BadRequestException; Request ID: null; Proxy: null)" (RequestToken: <token>, HandlerErrorCode: GeneralServiceException). The fixed text is the "Warnings found during import:" prefix, each warning sentence and the Service/Status Code/Error Code trailers; the variable parts are the security scheme name, the HTTP method and the resource path taken from the submitted Body, and the Request ID / RequestToken which are per-call.
Emulator: the stack reaches CREATE_COMPLETE — "AssertionError: FailOnWarnings=true against a Body that produces import warnings must fail the stack, got 'CREATE_COMPLETE'". The flag is accepted and ignored, and the warnings are never surfaced.
Why: FailOnWarnings exists so a deployment stops on a spec the gateway only partly understood — here, a method the import silently left UNSECURED. An emulator that completes the stack ships an API whose security definition was dropped, and the operator sees a green deploy.
Fix: the ImportApi handler's warning collection and the FailOnWarnings gate (emit the warnings, refuse 400 BadRequestException with the text above when the flag is set, and populate Warnings/ImportInfo when it is not), plus the AWS::ApiGatewayV2::Api provisioner's propagation of that refusal into CREATE_FAILED.
Traces: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-failonwarnings-true-fails-create-on-import-warning.

=== Cause 3 of 3: a WEBSOCKET API built ENTIRELY from CloudFormation resources dispatches no frame on a live socket. ===
Failing check: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-websocket-route-selection-expression-dispatches-by-action.
AWS: recorded behavior only for the socket; Smithy grounds the resources CloudFormation drives — CreateIntegration/CreateRoute/CreateRouteResponse (POST /v2/apis/{ApiId}/routes/{RouteId}/routeresponses, 201, RouteResponseKey required)/CreateDeployment/CreateStage, and UpdateApi.RouteSelectionExpression. The recording shows a stack declaring AWS::ApiGatewayV2::Api (ProtocolType WEBSOCKET, RouteSelectionExpression "$request.body.action"), three Route resources with their RouteResponses, an explicit Deployment and a Stage referencing it — with no direct CreateRoute/CreateDeployment call anywhere — serving a live RFC 6455 socket on which each frame is dispatched to the route whose key equals the frame's `action`, ping and sendMessage each replying with their own route's branch, and an action matching neither falling through to $default.
Emulator: the check is killed at the 60 s cap ("Error: Check timed out after 60.0s") — the CFN-declared WEBSOCKET stage never produces a socket that answers, so neither the per-route dispatch nor the $default fallback is observable.
Why: CloudFormation is how these APIs are actually built. An emulator in which CFN-declared Route/RouteResponse/Deployment/Stage resources return success but wire up no dispatch lets a stack deploy green and then answer nothing, and the deployment-snapshot/route-response ordering that only CFN exercises is left unverified.
Fix: the AWS::ApiGatewayV2::Route / ::RouteResponse / ::Deployment / ::Stage provisioners must produce the same state the direct control-plane calls do (including the deployment snapshot a Stage's DeploymentId names), and the execute-api WEBSOCKET data plane must complete the upgrade and evaluate RouteSelectionExpression against the frame body.
Traces: apigatewayv2__cloudformation.deploy-apigatewayv2-cfn-websocket-route-selection-expression-dispatches-by-action.
