# cloudformation__sns__sqs: a stack's DELETE phase records no per-resource DELETE_IN_PROGRESS events, so reverse-order teardown is unobservable (diamond stack)

> _Note: this issue was identified against the code base at commit `1aab6ad9a4dd8a2817d61de8022dab6fc1da2f9a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeStackEvents

## Description
One net-new behavioral root cause, grounded in the only cloudformation__sns__sqs check this replay left unattributed. The create-phase divergence previously filed for this very check (open issue 20261026T012701Z-cloudformation-never-provisions-a-dependency-graph-concurrently-and.md, whose replay key is the old 60 s timeout) no longer reproduces: the emulator now schedules the diamond's independent branches concurrently, holds each WaitCondition open until SignalResource, and emits the two create-phase CREATE_IN_PROGRESS events per resource (one with no ResourceStatusReason, one 'Resource creation Initiated'), reaching CREATE_COMPLETE. The failure has moved to the DELETE phase, which that issue does not state and whose key it does not carry.

Cause 1 of 1: DeleteStack settles the stack to DELETE_COMPLETE while DescribeStackEvents records no per-resource delete events — the resources the stack deleted get no DELETE_IN_PROGRESS (and therefore no observable delete interval) at all.
AWS: DeleteStack tears a stack's graph down in reverse topological order and records the teardown in the stack's event stream the same way it records the build. DescribeStackEvents (Smithy: @paginated on NextToken, items StackEvents; each StackEvent carries StackName, LogicalResourceId, PhysicalResourceId, ResourceType, Timestamp, ResourceStatus, ResourceStatusReason) returns, for every resource the stack owns, a DELETE_IN_PROGRESS event followed by a DELETE_COMPLETE event, alongside the stack-level DELETE_IN_PROGRESS ('User Initiated') and DELETE_COMPLETE. Those per-resource stamps are what make the ordering contract observable: a join resource's DELETE_COMPLETE precedes each predecessor branch's DELETE_IN_PROGRESS, a subscription finishes deleting before the queue it points at starts, and two independent branches' delete intervals overlap. This is recorded behavior for the delete phase and mirrors the create phase the emulator already reproduces.
Emulator: after DeleteStack the stack does reach StackStatus 'DELETE_COMPLETE' (the check's status assertion passes), but the event stream carries no DELETE_IN_PROGRESS event for the resources: looking up the stamp for logical id 'GateA' (an AWS::CloudFormation::WaitCondition) finds none, and the event list the check dumps runs from the stack-level CREATE_IN_PROGRESS 'User Initiated' through every per-resource create event and CREATE_COMPLETE to the stack-level DELETE_IN_PROGRESS 'User Initiated' with no per-resource delete event in it. Create-phase events are present and correctly reasoned (both 'picked off the ready set' and 'Resource creation Initiated' forms), so the gap is specific to the teardown path's event emission.
Why: a client cannot verify or debug any teardown. Nothing tells it which resource is being deleted, in what order, which one is slow, or which one failed — deletion is a black box between the stack-level DELETE_IN_PROGRESS and DELETE_COMPLETE. Deployment tooling that surfaces per-resource delete progress (the CLI/CDK event tails, CI gates that assert a dependant is gone before its dependency) shows nothing, and the reverse-topological-order and branch-concurrency guarantees are unobservable even when the engine honours them.
Fix: the delete path of the cloudformation provisioning engine (the teardown planner that walks the reverse topological order) must append a DELETE_IN_PROGRESS event per resource as it is picked and a DELETE_COMPLETE (or DELETE_FAILED) event when it settles, into the same per-stack event log DescribeStackEvents serves and that the create path already writes. Related open issues that record the CREATE-phase version of this gap and do NOT cover the delete phase or carry this check: 20261025T015306Z-cloudformation-stack-events-and-resource-views-are-incomplete.md, 20261025T050651Z-cloudformation-records-no-per-resource-stack-events-a.md, 20261025T053459Z-cloudformation-emits-no-per-resource-stack-events-and.md.
Traces: cloudformation__sns__sqs.cfn-independent-branches-provision-concurrently-and-tear-down-in-reverse (this check needs its own budget: it holds HOLD_S=20 s deliberately plus a create, a delete and absence polls).

## Evidence
Expected (AWS): after DeleteStack on the diamond stack, paging DescribeStackEvents yields, per logical id (GateA, GateB, QueueA, QueueB, Fanout, SubA, SubB, JoinPolicy), a DELETE_IN_PROGRESS event and a later DELETE_COMPLETE event, so that JoinPolicy's DELETE_COMPLETE timestamp precedes QueueA's and QueueB's DELETE_IN_PROGRESS, SubA/SubB finish before QueueA/QueueB start, and the two branches' delete intervals overlap.

Actual (emulator): verdict 'mismatch'. The stack reaches 'DELETE_COMPLETE', but the first delete-phase stamp lookup fails: "AssertionError: no DELETE_IN_PROGRESS event for 'GateA' with reason_initiated=None; the events recorded were [('<stack-name>', 'CREATE_IN_PROGRESS', 'User Initiated'), ('GateA', 'CREATE_IN_PROGRESS', ''), ('GateB', 'CREATE_IN_PROGRESS', ''), ('Fanout', 'CREATE_IN_PROGRESS', ''), ('Fanout', 'CREATE_IN_PROGRESS', 'Resource creation Initiated'), ('Fanout', 'CREATE_COMPLETE', ''), ('GateA', 'CREATE_IN_PROGRESS', 'Resource creation Initiated'), ('GateB', 'CREATE_IN_PROGRESS', 'Resource creation Initiated'), ('GateA', 'CREATE_IN_PROGRESS', 'Received SUCCESS signal with UniqueId si'), ('GateA', 'CREATE_COMPLETE', ''), … ('JoinPolicy', 'CREATE_COMPLETE', ''), ('<stack-name>', 'CREATE_COMPLETE', ''), ('<stack-name>', 'DELETE_IN_PROGRESS', 'User Initiated'), …]" — every create-phase per-resource event is present and correctly reasoned; no per-resource delete event appears. (The stack/queue/topic names in the dump are this run's generated ids and are not part of the requirement.)

## Steps to Reproduce
1. Boot the emulator. CreateStack with the diamond template: GateA and GateB as AWS::CloudFormation::WaitCondition with CreationPolicy {ResourceSignal: {Timeout: 'PT10M', Count: 1}}; QueueA/QueueB as AWS::SQS::Queue with DependsOn GateA/GateB; Fanout as AWS::SNS::Topic; SubA/SubB as AWS::SNS::Subscription (Protocol sqs, TopicArn Ref Fanout, Endpoint Fn::GetAtt [QueueX, 'Arn']); JoinPolicy as AWS::SQS::QueuePolicy DependsOn [SubA, SubB] over both queues.
2. SignalResource both gates (Status='SUCCESS') and wait for CREATE_COMPLETE.
3. DeleteStack(StackName=<stack id>) and poll DescribeStacks until DELETE_COMPLETE.
4. Page DescribeStackEvents(StackName=<stack id>) to the end and filter for ResourceStatus 'DELETE_IN_PROGRESS' / 'DELETE_COMPLETE' with a LogicalResourceId other than the stack itself. AWS returns one of each per resource; the emulator returns none, so no delete ordering can be computed.
5. Replay cloudformation__sns__sqs.cfn-independent-branches-provision-concurrently-and-tear-down-in-reverse with the check's own budget (not the 60 s cap).
