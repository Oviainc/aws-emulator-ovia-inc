# cloudformation DescribeType does not serve the public resource-type registry: unknown types 404 and known ones return emulator-authored schemas

> _Note: this issue was identified against the code base at commit `c52a7255ce2600c21f38f62abb43a8c83b37855a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeType

## Description
Seven distinct root causes in the CloudFormation registry behind DescribeType. Each is numbered with its own fixture and step; all seven must be closed before this issue is done. The replay clusters cover 2,029 recorded DescribeType steps, so this is the registry catalog as a whole, not a handful of types.

Cause 1 of 7: DescribeType refuses the vast majority of public AWS resource types.
AWS: DescribeType on a registered PUBLIC type answers HTTP 200 with the type's DescribeTypeResult (Schema, Description, ProvisioningType, Visibility=PUBLIC, DefaultVersionId, Arn, ...). Smithy: DescribeType input Type/TypeName (TypeName pattern ^[A-Za-z0-9]{2,64}::[A-Za-z0-9]{2,64}::[A-Za-z0-9]{2,64}(::MODULE){0,1}$), output member Schema -> TypeSchema @length 1..16777216; the only not-found refusal modelled is TypeNotFoundException (httpError 404), which AWS uses for a type that is NOT in the registry. Every AWS-published resource type IS in the registry.
Emulator: answers HTTP 404 with no DescribeTypeResponse body member at all for 1,939 recorded type lookups (Alexa::ASK::Skill, AWS::AccessAnalyzer::Analyzer, AWS::Amplify::*, AWS::ApiGateway::*, ... ). Expected status 200, actual 404; $.DescribeTypeResponse missing.
Why: a client that reads a resource type's schema before deploying (cfn-lint, CDK, Cloud Control, the console registry view, any tool doing `aws cloudformation describe-type --type RESOURCE --type-name ...`) concludes the type does not exist, so schema-driven validation and provisioning are impossible for nearly the whole catalog.
Fix: the DescribeType handler's registry lookup plus the bundled public-type catalog data it resolves against.
Traces: cloudformation-catalog-describe-type-alexa-ask-skill#task#1 (1,939 steps in the cluster).

Cause 2 of 7: for types the emulator does know, DescribeTypeResult.Schema is not the published resource-type schema, and Description/ProvisioningType/SourceUrl follow it.
AWS: Schema is the type's full provider definition JSON (typeName, description, sourceUrl, definitions, properties, required, createOnlyProperties, primaryIdentifier, readOnlyProperties, handlers...), Description is the schema's description text, SourceUrl is the type's published source URL, and ProvisioningType reflects the type (NON_PROVISIONABLE / IMMUTABLE / FULLY_MUTABLE).
Emulator: serves a synthesized stand-in schema whose body does not match the published definition, so Schema, Description, ProvisioningType and SourceUrl all diverge on 5 types (AWS::ACMPCA::Certificate, AWS::ApiGateway::UsagePlanKey, AWS::BedrockAgentCore::Browser, AWS::BedrockAgentCore::CodeInterpreter, AWS::MSK::ServerlessCluster).
Why: a client validating a template against the schema accepts properties AWS rejects and rejects properties AWS accepts.
Fix: the registry catalog data for those types (the DescribeType handler's schema store).
Traces: cloudformation-catalog-describe-type-aws-acmpca-certificate#task#1 (5 steps).

Cause 3 of 7: the same stand-in-schema fault with Schema, Description and SourceUrl diverging, over 63 types (AWS::ACMPCA::CertificateAuthority, AWS::AmazonMQ::Broker, AWS::ApiGateway::RestApi, AWS::CloudFront::Distribution, AWS::Batch::*, AWS::CodeBuild::Project, ...).
AWS: as Cause 2 — Schema is the published provider definition and SourceUrl/Description come from it.
Emulator: synthesized Schema with a mismatching Description and SourceUrl.
Why: as Cause 2; schema-driven tooling diverges for 63 of the most commonly deployed types.
Fix: the registry catalog data for those types.
Traces: cloudformation-catalog-describe-type-aws-acmpca-certificateauthority#task#1 (63 steps).

Cause 4 of 7: the same fault with Schema and Description diverging over 19 further types (AWS::ApiGateway::Authorizer, AWS::CloudWatch::Alarm, AWS::EC2::NetworkAcl, AWS::ECR::Repository, AWS::EKS::Cluster, AWS::IAM::Role, AWS::Logs::LogGroup, AWS::Route53::HostedZone, AWS::SecretsManager::Secret, AWS::SQS::Queue, ...).
AWS: as Cause 2.
Emulator: synthesized Schema plus a Description that is not the schema's description.
Why: as Cause 2.
Fix: the registry catalog data for those types.
Traces: cloudformation-catalog-describe-type-aws-apigateway-authorizer#task#1 (19 steps).

Cause 5 of 7: DescribeTypeResult carries NO Schema member at all for the AWS::CloudFormation::* pseudo resource types.
AWS: DescribeType for AWS::CloudFormation::CustomResource, ::WaitCondition and ::WaitConditionHandle returns a Schema (the provider definition JSON for the type, e.g. typeName AWS::CloudFormation::CustomResource with ServiceToken required). Smithy: output member Schema -> TypeSchema.
Emulator: Schema is absent (expected the schema document, got None).
Why: a client that reads Schema to learn the required properties of a custom resource gets nothing back and cannot validate or generate a template.
Fix: the registry catalog data for the AWS::CloudFormation::* types.
Traces: cloudformation-catalog-describe-type-aws-cloudformation-customresource#task#1 (3 steps).

Cause 6 of 7: AWS::ElasticLoadBalancingV2::LoadBalancer diverges on Schema, Description, SourceUrl and DocumentationUrl.
AWS: the published LoadBalancer provider definition, with its sourceUrl and documentationUrl members.
Emulator: a synthesized schema and mismatching Description/SourceUrl/DocumentationUrl.
Why: as Cause 2.
Fix: the registry catalog data for that type.
Traces: cloudformation-catalog-describe-type-aws-elasticloadbalancingv2-loadbalancer#task#1.

Cause 7 of 7: AWS::IAM::AccessKey is described as a mutable type with a one-property stub schema and an invented SourceUrl.
AWS: Schema is the published AWS::IAM::AccessKey definition (properties Id/SecretAccessKey/Serial/Status/UserName, required UserName, readOnlyProperties SecretAccessKey+Id, createOnlyProperties UserName+Serial, primaryIdentifier Id), ProvisioningType is NON_PROVISIONABLE (Smithy: ProvisioningType enum NON_PROVISIONABLE|IMMUTABLE|FULLY_MUTABLE) and no SourceUrl is returned.
Emulator: Schema is '{"$schema":"https://schema.cloudformation.us-east-1.amazonaws.com/provider.definition.schema.v1.json","typeName":"AWS::IAM::AccessKey","properties":{"SecretAccessKey":{"type":"string"}},"sourceUrl":"https://github.com/aws-cloudformation/aws-cloudformation-resource-providers-iam.git"}', ProvisioningType is 'FULLY_MUTABLE', and SourceUrl is populated with that github URL — a host the emulator does not serve — where AWS returns none.
Why: the type is advertised as fully mutable with one property, so a client believes an access key can be updated in place and that UserName is optional.
Fix: the registry catalog data and the ProvisioningType/SourceUrl population in the DescribeType handler.
Traces: cloudformation-catalog-describe-type-aws-iam-accesskey#task#1.
