=== Cause 1 of 1: AWS Batch emits no `aws.batch` / `Batch Job State Change` event when a job changes state ===
AWS: recorded behavior only for the event vocabulary — the EventBridge envelope is not described by any Smithy model. Smithy (batch, com-amazonaws-batch-awsbatchv20160810) does model the state the event projects: SubmitJob (POST /v1/submitjob, 200) returns jobArn/jobName/jobId; DescribeJobs (POST /v1/describejobs) returns JobDetailList carrying jobName, jobArn, jobQueue, jobDefinition, status and createdAt (epoch millis); TerminateJob (POST /v1/terminatejob) takes required jobId and reason. AWS Batch publishes one EventBridge event per job-state TRANSITION on the default bus with the fixed strings source = "aws.batch" and detail-type = "Batch Job State Change", account = the caller's account, region = the calling region, resources = exactly [the job ARN], and a detail that is a projection of the job record: detail.jobId, detail.jobArn, detail.jobQueue (the job queue ARN), detail.jobName, detail.jobDefinition (an ARN), detail.createdAt (epoch-millis integer) and detail.status = the state the job transitioned INTO. The documented rule is that the initial SUBMITTED state creates no event, so a job on a queue backed by an UNMANAGED compute environment first produces status RUNNABLE; a subsequent TerminateJob produces a second event with detail.status "FAILED" whose detail.statusReason carries the reason string the request passed. The events are routable by content: a rule with pattern {"source":["aws.batch"],"detail-type":["Batch Job State Change"],"detail":{"jobQueue":[<that queue's ARN>]}} receives only events of jobs submitted to that queue, and a sibling rule pinned to a different job queue ARN receives nothing. The ARNs, job ids, names and timestamps above are per-run values that fill the template; the fixed source/detail-type strings, resources == [job ARN] and the detail-to-DescribeJobs agreement are the requirement.
Emulator: nothing observable is ever produced for this pipeline. The check stands up the whole wiring (IAM role trusting batch.amazonaws.com, an UNMANAGED compute environment polled to VALID, two job queues polled to VALID, two SQS queues whose policies admit events.amazonaws.com sqs:SendMessage, two ENABLED default-bus rules each pinned to one job queue ARN, plus a per-queue warm-up rule on a source the check itself publishes to prove the EventBridge->SQS leg can deliver and to measure its latency), submits a job, waits until DescribeJobs reports a jobArn, then polls the watched SQS queue for the RUNNABLE envelope. No envelope with source "aws.batch" and detail-type "Batch Job State Change" ever arrives, the check reaches no verdict, and the suite reports [mismatch] with "Check timed out after 60.0s". Every later graded observation is therefore unreachable too: the envelope assertions (source, detail-type, account, region, resources == [jobArn]), the projection assertions (detail.jobName and detail.createdAt must equal what DescribeJobs reports for the same job), the absence leg on the sibling queue (no stray event; ApproximateNumberOfMessages and ApproximateNumberOfMessagesNotVisible both 0), the second transition after TerminateJob (status FAILED with detail.statusReason containing the reason), the "no SUBMITTED event is ever created" assertion, and the repair leg where a job submitted to the sibling queue does produce a RUNNABLE event there naming the sibling queue ARN.
Why: a client that drives Batch asynchronously is blind. Completion/failure fan-out (notify on FAILED, chain the next stage on SUCCEEDED, dead-letter a terminated job) is built on these events — they are the only push signal Batch offers — so any EventBridge rule, Lambda target, Step Functions callback or alarm wired to aws.batch silently never fires and the client must fall back to polling DescribeJobs. Because the emulator emits nothing at all rather than something wrong, a correctly scoped rule pattern and a mis-scoped one are indistinguishable, so routing and filtering logic cannot be validated against the emulator either.
Fix: the Batch job state machine — the SubmitJob / scheduler-sweep / TerminateJob transition path and the job record it owns in the batch service's state — must publish a `Batch Job State Change` event onto the default event bus on every transition after SUBMITTED, with source "aws.batch", resources = [the job ARN], and a detail projected from the SAME job record DescribeJobs serves (so the two can never disagree), including statusReason on a terminate-driven FAILED transition.

## Steps to Reproduce
1. Create an IAM role trusting batch.amazonaws.com with AWSBatchServiceRole attached; wait until GetRole resolves it.
2. batch CreateComputeEnvironment type=UNMANAGED state=ENABLED with that service role; poll DescribeComputeEnvironments until status == VALID.
3. batch CreateJobQueue twice (state=ENABLED, priority=10, computeEnvironmentOrder = [that CE]); poll DescribeJobQueues until each is VALID. Keep both jobQueueArns (WATCHED and SIBLING).
4. Create two SQS queues; set each queue's Policy to allow Principal {Service: events.amazonaws.com} sqs:SendMessage on its own ARN.
5. events PutRule (default bus, State=ENABLED) with EventPattern {"source":["aws.batch"],"detail-type":["Batch Job State Change"],"detail":{"jobQueue":[WATCHED]}} and PutTargets the first queue; repeat with SIBLING and the second queue. Both PutTargets must answer FailedEntryCount == 0.
6. (Control) PutRule a throwaway rule on a source you control, PutEvents one event, confirm it reaches each queue, then drain both queues to empty.
7. batch RegisterJobDefinition, then SubmitJob onto WATCHED; poll DescribeJobs until it reports a jobArn.
8. ReceiveMessage from the first queue.
   Expected: an envelope with source "aws.batch", detail-type "Batch Job State Change", resources == [the jobArn] and detail.status == "RUNNABLE", whose detail.jobName and detail.createdAt equal what DescribeJobs reports for that job.
   Actual: nothing with that source/detail-type ever arrives.
9. Hold the sibling queue for a window calibrated on the measured delivery latency: expected empty, with ApproximateNumberOfMessages == 0 and ApproximateNumberOfMessagesNotVisible == 0.
10. batch TerminateJob(jobId, reason=<reason>). Expected a second envelope for the same jobId with detail.status == "FAILED" and detail.statusReason containing <reason>; no envelope may ever carry detail.status == "SUBMITTED".
11. SubmitJob onto SIBLING. Expected its RUNNABLE event arrives on the second queue with detail.jobQueue == SIBLING, and the first job's events have still never appeared there.
