=== Cause 1 of 2: after CompleteSnapshot the snapshot is never readable, so every write-then-wait-then-read direct-API flow hangs instead of converging ===
AWS: the EBS direct API is write-then-wait-then-read. Smithy com.amazonaws.ebs#StartSnapshot creates a snapshot (POST /snapshots, code 201, Status from com.amazonaws.ebs#Status = completed|pending|error); CompleteSnapshot (POST /snapshots/completion/{SnapshotId}, code 202, output Status) drives it to a terminal state. The EBS model exposes no read of snapshot state, so a client observes the lifecycle through ec2:DescribeSnapshots (State pending -> completed, Progress '100%'; an unknown id is refused with error code `InvalidSnapshot.NotFound`) and then reads content back through ebs:ListSnapshotBlocks (which answers `ResourceNotFoundException`, HTTP 404, while the snapshot is not yet readable). Both reads MUST resolve within a bounded time after CompleteSnapshot. Recorded behavior only for the exact convergence latency.
Emulator: all three checks are killed by the harness with `Error: Check timed out after 60.0s`. In each, the hang is located after a synchronous leg that did not raise (the checks' `_error_code_msg` helper raises an AssertionError IMMEDIATELY when a call it expects to be refused instead succeeds, so an unexpected acceptance would not present as a timeout): the surviving loops are `_wait_for_snapshot_state`, which calls `ec2.describe_snapshots(SnapshotIds=[snap-...])` on a 3 s interval and swallows `InvalidSnapshot.NotFound`, and `_list_blocks_with_retry`, which calls `ebs.list_snapshot_blocks(SnapshotId=snap-...)` on a 3 s interval and swallows `ResourceNotFoundException`. Neither loop ever observes a terminal snapshot, so no check reaches its post-completion assertions (`State`/`Progress`, and the block-index set that must be exactly the blocks accepted).
Why: a client that writes blocks and then polls for completion is told forever that the snapshot does not exist (EC2) or is not found (ListSnapshotBlocks). It can never learn the snapshot is usable, can never read content back, and can never run its cleanup (ec2:DeleteSnapshot on an id EC2 denies). The individual EBS operations answer, but no end-to-end flow terminates, and these three checks additionally never get to grade the behaviour they exist for (that a rejected block never persisted, that an out-of-range block never persisted).
Fix: the snapshot state shared by the ebs and ec2 service crates, plus the ebs ListSnapshotBlocks read path — the StartSnapshot/CompleteSnapshot handlers must register and then terminally update a snapshot in the same state that ec2:DescribeSnapshots reads (pending -> completed with Progress '100%') and that ListSnapshotBlocks serves once completed, so a bounded poll converges.
Traces: ebs.put-snapshot-block-datalength-mismatch-rejected, ebs.put-snapshot-block-index-exceeds-volume-rejected, ebs.complete-snapshot-wrong-changed-blocks-count-is-accepted.

=== Cause 2 of 2: a CompleteSnapshot whose ChangedBlocksCount disagrees with the blocks actually written is accepted and then never enforced — the snapshot never converges to 'error' ===
AWS: ChangedBlocksCount is a required header member of CompleteSnapshot (Smithy com.amazonaws.ebs#CompleteSnapshot: `x-amz-ChangedBlocksCount`, @required, @range min 0) and is NOT validated synchronously against the blocks received: the call is accepted (HTTP 202) and returns a Status of `pending`/`completed`. The mismatch is enforced asynchronously — the snapshot converges to the terminal state `error` (com.amazonaws.ebs#Status value `error`; observable as ec2:DescribeSnapshots State 'error') rather than to `completed`, and the snapshot is unusable. Recorded behavior only for the asynchronous convergence (the recording shows it taking on the order of 150 s); the model states only the member, its constraints and the `error` status value.
Emulator: the asynchronous mismatch enforcement is absent. CompleteSnapshot(ChangedBlocksCount=5) against a snapshot with exactly one block written is accepted, and the snapshot then never reaches either terminal state within the check's window — `ebs.complete-snapshot-wrong-changed-blocks-count-is-accepted` is killed at the 60 s cap with the poll still running, having never seen `error`. There is no path in the emulator that distinguishes a correct ChangedBlocksCount from an incorrect one: a correct count and an incorrect count are treated identically.
Why: ChangedBlocksCount is the direct API's only integrity check that a producer uploaded everything it claimed. A client that mis-counts blocks (a crashed or partial uploader) is never told, so against the emulator a truncated snapshot looks indistinguishable from a complete one; a client that relies on the snapshot converging to `error` to detect and retry its own partial upload never sees that signal, and a test that asserts the mismatch is caught passes while the data is wrong.
Why this is a cause of its own and not cause 1: cause 1 is the read path failing to converge at all; this cause is the missing comparison between the declared ChangedBlocksCount and the blocks received, which decides WHICH terminal state the snapshot converges to. Fixing cause 1 alone would make this check converge to `completed` and still fail its `expected the snapshot to converge to 'error'` assertion. It is currently masked by cause 1.
Fix: the CompleteSnapshot handler and the snapshot state it finalises — record the declared ChangedBlocksCount, compare it to the number of distinct block indices PutSnapshotBlock accepted for that snapshot, and finalise the snapshot to Status/State `error` when they disagree (keeping the synchronous response a 202 with Status pending/completed, never a refusal).
Traces: ebs.complete-snapshot-wrong-changed-blocks-count-is-accepted.
