# bedrock: the account-enforced guardrail configuration is stored but never applied to inference, and ListFoundationModelAgreementOffers answers 501 NotImplemented

> _Note: this issue was identified against the code base at commit `0de7718ade8f368be0e47aca52d0dd18a585e082`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEnforcedGuardrailConfiguration

## Description
TWO CAUSES on the Bedrock control plane, both net-new. Each is a distinct contract a fixer must see answer correctly before submitting. Model read for both: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json. Neither cause is an assertion on generated model text.

Cause 1 of 2 — the account-level enforced guardrail is accepted, stored and listed, but inference never consults it (OVER-PERMISSIVE, safety-relevant).
AWS: Smithy PutEnforcedGuardrailConfiguration (PUT /enforcedGuardrailsConfiguration, 200) takes a required guardrailInferenceConfig -> AccountEnforcedGuardrailInferenceInputConfiguration whose required members are guardrailIdentifier and guardrailVersion, with optional selectiveContentGuarding and modelEnforcement; modelEnforcement is documented "Model-specific information for the enforced guardrail configuration. If not present, the configuration is enforced on all models". The point of the operation is that the guardrail is applied SERVER-SIDE to inference the caller did not opt in to: once a configuration is installed (and visible via ListEnforcedGuardrailsConfiguration, whose required guardrailsConfig list is @length 0..1, i.e. an account singleton), an InvokeModel/Converse request that carries NO guardrailConfig at all is still evaluated against it, and a request whose prompt matches the guardrail's word policy comes back with the service-injected response member amazon-bedrock-guardrailAction = INTERVENED (recorded behavior only — amazon-bedrock-guardrailAction is injected into the InvokeModel body by the service and is not a modeled member; a non-matching prompt under the same configuration carries amazon-bedrock-guardrailAction = NONE).
Emulator: PutEnforcedGuardrailConfiguration succeeds and persists the record (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/put_enforced_guardrail_configuration.rs resolves the guardrail revision and writes crate::state::EnforcedGuardrailConfiguration), and ListEnforcedGuardrailsConfiguration reports the minted configId — but a subsequent InvokeModel on a model named in modelEnforcement.includedModels, with a prompt containing the guardrail's blocked word, returns 200 with a plain body carrying only {output, stopReason:'end_turn', usage} and NO amazon-bedrock-guardrailAction member at all. Nothing on the inference path reads the stored singleton, so enforcement is unobservable in either direction (neither INTERVENED nor NONE is ever reported).
Why: an operator who relies on the account-enforced guardrail to apply a content policy to every model invocation in the account — the one control that cannot be bypassed by a client omitting guardrailConfig — gets no enforcement whatsoever while both the control plane (Put/List) and the data plane (200) report success. Forbidden content flows straight through, and a client cannot even detect the absence of enforcement because the guardrailAction member is missing rather than NONE.
Fix: the bedrock-runtime InvokeModel / Converse / ConverseStream handlers' guardrail evaluation stage must consult the control plane's account-enforced guardrail singleton (honouring modelEnforcement include/exclude and selectiveContentGuarding) in addition to any per-request guardrailConfig, and must emit the amazon-bedrock-guardrailAction member on the InvokeModel body. Related but NOT the same cause: open issue 20261023T232022Z-bedrock-runtime-synchronous-inference-guardrailconfig-and-toolconfig-silently.md cause 1 covers the per-request guardrailConfig member being ignored on Converse; this cause is the ACCOUNT-ENFORCED configuration installed through the control plane and applied to a request that names no guardrail, and it is not fixed by honouring the request member.
Traces: bedrock.put-enforced-guardrail-configuration-applies-to-invoke.

Cause 2 of 2 — ListFoundationModelAgreementOffers is an unimplemented scaffold stub, so no catalogued model ever exposes an offer and the whole EULA-agreement flow is unreachable.
AWS: Smithy ListFoundationModelAgreementOffers (GET /list-foundation-model-agreement-offers/{modelId}, 200) returns required modelId and required offers -> Offers, a list of Offer{offerId, offerToken (required), termDetails (required)}; the optional offerType query member is the enum OfferType [ALL, PUBLIC]. Its modeled errors are AccessDeniedException(403), InternalServerException(500), ResourceNotFoundException(404), ThrottlingException(429), ValidationException(400) — 501/NotImplemented is not among them and is not a modeled Bedrock error code. For a marketplace/third-party model in the account's ListFoundationModels catalog that still needs EULA acceptance, the call returns 200 with a non-empty offers list whose offerToken then feeds CreateFoundationModelAgreement (POST /create-foundation-model-agreement, 202).
Emulator: every call answers HTTP 501 with the unmodeled code NotImplemented ("operation ListFoundationModelAgreementOffers is scaffolded but not implemented in this emulator") — services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/list_foundation_model_agreement_offers.rs still returns crate::scaffolded::Scaffolded::not_implemented. Because the check's catalog probe treats any ClientError as "this model has no offer", the visible symptom is that NO model in the emulator's ListFoundationModels catalog exposes a purchasable offer, which strands CreateFoundationModelAgreement / GetFoundationModelAvailability as well: there is no offerToken to call them with. Note this failure was NOT auto-flagged as a scaffold stub by the suite, because the 501 is swallowed by the probe and surfaces as an assertion instead.
Why: a client that drives model access through the agreement APIs cannot run at all here — the discovery step returns an unmodeled 501 that its error handling does not know, and if it tolerates the error it concludes (wrongly) that every model in the region is already entitled, so the accept-EULA-then-invoke path is never exercised.
Fix: implement ListFoundationModelAgreementOffers in that handler file (back it with offers for the catalogued models that require agreement acceptance, honour offerType, and return the modeled 404/400 rather than 501), then delete the SCAFFOLDED marker at the top of the file.
Traces: bedrock.create-foundation-model-agreement-duplicate-rejected.
