# wafv2 logging: an accepted S3 logging destination never receives a delivered WAF log record — sampling now converges, delivery never does (1 cause)

> _Note: this issue was identified against the code base at commit `7bc4016e226ff2d9d25ecfef2fc219d914bce0ad`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
One net-new root cause in the wafv2 logging surface, grounded in the only failing behavioral check of this run that the suite marked neither ALREADY FILED nor OWNED.

Related open issues that do NOT cover it: 20261026T023047Z-wafv2-logging-surface-putloggingconfiguration-accepts-a-destination-whose.md lists this check id, but its recorded replay key for it is `wafv2.e2e-logging-configuration-capture-flow|_poll_for_samples#23|Timeout` — the GetSampledRequests leg — and that leg now PASSES: in this run the check gets past `GetSampledRequests` returning a SampledRequest with Action=="COUNT" and fails further down, inside `_poll_for_s3_log_records`, so the suite did not mark the check OWNED. The surviving failure is the S3 log-delivery leg alone, which is what this issue describes. 20261026T010229Z-apigateway-logs-wafv2-waf-logging-is-now-accepted.md describes the missing CloudWatch Logs delivery under the apigateway__logs__wafv2 token and an unprefixed-destination accept, not an S3 destination reached through plain wafv2 + s3 calls.

Cause 1 of 1: with an enabled logging configuration whose LogDestinationConfigs names an `aws-waf-logs-`-prefixed S3 bucket, and a REGIONAL web ACL (one Priority 0 Count rule) associated with a deployed API Gateway stage, no WAF log record is ever written to the configured bucket, while the same traffic IS observable through GetSampledRequests.
Failing check: wafv2.e2e-logging-configuration-capture-flow
AWS: PutLoggingConfiguration associates one logging destination with a web ACL and, on success, WAF provisions the permission needed to write to it (Smithy, services/service-com-amazonaws-wafv2-awswaf-20190729/smithy-model/com-amazonaws-wafv2-awswaf-20190729.json — shape LoggingConfiguration: required ResourceArn and LogDestinationConfigs (@length 1..100, "You can associate one logging destination to a web ACL"), and the shape doc states the destination may be a CloudWatch Logs log group, an Amazon S3 bucket or a Kinesis Data Firehose, that "The name that you give the destination must start with aws-waf-logs-", and that on a successful PutLoggingConfiguration "WAF creates an additional role or policy that is required to write logs to the logging destination... For an Amazon S3 bucket, WAF creates a bucket policy"). PutLoggingConfiguration/GetLoggingConfiguration/DeleteLoggingConfiguration are modelled with WAFInvalidParameterException, WAFNonexistentItemException and WAFLogDestinationPermissionIssueException, all errorKind client / httpError 400. For the delivery itself the model says nothing — recorded behavior only: the recording shows WAF writing, asynchronously (well over a minute on real AWS) and batched, gzip objects of newline-delimited JSON into the configured bucket, one record per inspected request, each record carrying `httpRequest.headers` reproducing the inspected request's headers (name/value pairs) and, for a request matched by a non-terminating Count rule, that rule listed under `nonTerminatingMatchingRules` with `ruleId` = the rule's Name and `action` = "COUNT". The number of objects, their keys, timestamps and the batching interval are per-run values and are not part of the requirement; the existence of a record per inspected request, and the two fields above, are.
Emulator: PutLoggingConfiguration answers 200 and GetLoggingConfiguration round-trips LogDestinationConfigs = [the S3 bucket ARN] (both legs pass), and the matched traffic is sampled — GetSampledRequests returns a SampledRequest with Action "COUNT", so the association and enforcement are live. But the configured bucket stays empty: the check drives fresh matching traffic through the associated stage on every poll iteration and lists/gets every object in the bucket, and no object — hence no record naming the marker header — ever appears, up to the 480 s poll cap (the run budget cut the poll short, reported as `TimeoutError: a WAF log record arriving in S3: the run budget ended first`; nothing was ever delivered in any iteration, and `len(seen_keys)` never grew). The later DeleteLoggingConfiguration → GetLoggingConfiguration leg, which must answer HTTP 400 WAFNonexistentItemException with WAF's sentence "AWS WAF couldn\u2019t perform the operation because your resource doesn\u2019t exist." (curly apostrophe; fixed text, no variable parts), is therefore never reached by this check.
Why: the delivered log record is the only durable, per-request audit trail WAF gives a client; sampling is a 3-hour best-effort window and is governed only by VisibilityConfig, so it cannot substitute. A client that configures logging gets a 200 and a round-tripping GetLoggingConfiguration, believes logging is on, and then finds its bucket permanently empty — indistinguishable from "no traffic matched". Any pipeline that reads WAF logs from S3 (Athena/Glue tables, SIEM ingestion, log-based alarming) silently produces nothing against the emulator, and a test that asserts a blocked/counted request was logged cannot pass.
Fix: the wafv2 log-delivery path — the web-ACL enforcement hook must, for every inspected request, emit a WAF log record to the enabled logging configuration's destination, and the S3 destination branch of that writer must be implemented: write gzip newline-delimited JSON objects into the bucket named by LogDestinationConfigs, each record carrying httpRequest.headers for the inspected request and nonTerminatingMatchingRules entries (ruleId = rule Name, action = "COUNT") for non-terminating matches. RedactedFields and LoggingFilter belong in the same writer. The configuration store itself (PutLoggingConfiguration/GetLoggingConfiguration) already behaves; only the emission is missing.
Traces: wafv2.e2e-logging-configuration-capture-flow (error, raised in _poll_for_s3_log_records after the PutLoggingConfiguration, GetLoggingConfiguration and GetSampledRequests legs passed).
