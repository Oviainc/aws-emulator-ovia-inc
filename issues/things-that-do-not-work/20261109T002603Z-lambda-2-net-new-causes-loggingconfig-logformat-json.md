# lambda: 2 net-new causes — LoggingConfig LogFormat=JSON is ignored for the records delivered to CloudWatch Logs, and the weighted-alias ladder never reaches a verdict

> _Note: this issue was identified against the code base at commit `7357c0aea0dc68ee0c6ea06203400d848de76641`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two net-new root causes in the Lambda service, both grounded in failing behavioral checks of this run.

Cause 1 of 2 — a function configured LoggingConfig.LogFormat=JSON has its application log lines delivered to CloudWatch Logs in the plain-text runtime framing, not as JSON records.
AWS: Smithy: CreateFunction/UpdateFunctionConfiguration carry LoggingConfig; LoggingConfig.LogFormat is documented as "The format in which Lambda sends your function's application and system logs to CloudWatch. Select between plain text and structured JSON", LoggingConfig.ApplicationLogLevel as "Lambda only sends application logs at the selected level of detail and lower", and LoggingConfig.LogGroup as the group that replaces the default "/aws/lambda/<function name>". Recorded behavior for LogFormat=JSON: every application line Lambda delivers into the group is one JSON object — a `level` member carrying the emitting logger's level NAME (for a Python `logging.warning` call that is `WARNING`, even though ApplicationLogLevel is spelled `WARN`), a `message` member carrying the formatted line, a `requestId` member equal to the invocation's request id, and a `timestamp`; platform records arrive as JSON objects with `type: platform.*`, so no free-text line is left in the group at all.
Emulator: the configuration round-trips (GetFunctionConfiguration returns LogFormat=JSON, ApplicationLogLevel=WARN) and the line is delivered to the correct group — including when LoggingConfig.LogGroup names a non-default group — but the delivered event is the runtime's plain-text framing `[<LEVEL>]\t<timestamp>\t<request id>\t<message>` rather than a JSON record. The two checks fail with `AssertionError: expected exactly one structured application record carrying 'sim2real-warn-<marker>', got []` (no delivered event parses as a JSON object with a `level` member) and `AssertionError: the function's LogFormat is JSON, but <log group> holds an unstructured line carrying '<marker>': '[INFO]\t<timestamp>\t<request id>\t<message>'`. In both messages the fixed text is the assertion wording and the `[LEVEL]`+tab framing of the delivered line; the marker, group name, timestamp and request id are per-run values taken from the request and the emulator's state.
Why: a client that selects LogFormat=JSON parses its function's logs as structured records — CloudWatch Logs Insights queries on `level`/`requestId`, metric filters over JSON fields, and any log shipper keyed on the JSON envelope. Against this emulator every such query returns nothing and every record is unattributable to its invocation, while the control plane reports the JSON format is in force, so the misconfiguration is invisible.
Fix: the Lambda log-delivery path that formats an invocation's application and system records before publishing them to CloudWatch Logs — it must honour the function's LoggingConfig.LogFormat (and emit the level/message/requestId/timestamp envelope) instead of always writing the text framing. The LogGroup routing on that path is NOT at fault: the override group does receive the line.
Traces: lambda.logging-config-json-format-filters-application-log-level, lambda.logging-config-log-group-override-routes-logs-and-leaves-the-default-group-absent. Open issue 20261107T091747Z-lambda-loggingconfig-is-ignored-by-the-invoke-log.md reports the same neglect on the Invoke *Tail* pipeline and carries neither of these checks' replay keys; here the Tail is fine (the DEBUG/INFO/WARN control assertions on LogResult pass) and only the delivered records diverge. Open issue 20261107T035448Z-lambda-logs-3-net-new-causes-loggingconfig-loggroup.md covers LogGroup routing, which now works.

Cause 2 of 2 — a weighted-alias invoke ladder never completes, so weighted routing cannot be observed at any rung.
AWS: Smithy: AliasRoutingConfiguration.AdditionalVersionWeights ("The second version, and the percentage of traffic that's routed to it") on CreateAlias/UpdateAlias; the model states no distribution guarantee, so recorded behavior only: four aliases over one function (one with no AdditionalVersionWeights, one at 0.10, one at 0.50, one at 1.00) coexist, each Invoke against each alias is answered promptly and reports the version that served it, and a 200-invoke sample per alias at 8-way concurrency completes in seconds — a freshly created weighted alias is already consistent on its first sample.
Emulator: the check never reaches a verdict — `Error: Check timed out after 180.0s`. Neither a distribution nor a refusal is produced for any rung, so the alias dispatcher's weight handling is unobservable.
Why: a client cannot run or verify a canary/linear deployment: the only evidence that traffic shifted is the per-invocation executed version, and it never arrives. Callers block for the whole budget instead of being served or refused.
Fix: the Invoke path's alias resolution and dispatch for an alias carrying AdditionalVersionWeights (selecting the version per rung and answering each invoke). Hypothesis: the stall is the invocations themselves failing rather than the weight arithmetic — open issue 20261108T003043Z-lambda-a-weighted-alias-s-invocations-are-almost.md reports weighted-alias invocations dying with Runtime.ExitError 'Runtime exited with error: signal: killed'; the replay output here identifies no stall point beyond the timeout.
Traces: lambda.alias-weight-ladder-observed-distribution. Open issue 20261101T210635Z-lambda-weighted-alias-traffic-is-never-observable-across.md names this same check, but its replay key does not match this failure (it recorded a `_poll` timeout against a 60 s budget; this run times out at 180 s with no probe frame), so the suite does not report the check as owned by it.

## Evidence
Cause 1: expected — with LoggingConfig {LogFormat: JSON, ApplicationLogLevel: WARN} the WARNING line delivered to the function's log group is a JSON object whose `level` is "WARNING", whose `message` carries the logged text, whose `requestId` equals the invocation's request id and which carries a `timestamp`, and no unstructured line remains in the group. Actual — the group holds the plain-text runtime framing only: FilterLogEvents returns '[INFO]\t2026-11-09T00:00:42.153Z\t<request id>\trouted-marker <marker>' (per-run timestamp/request id/marker), so the structured-record scan yields []: `AssertionError: expected exactly one structured application record carrying 'sim2real-warn-<marker>', got []` and `AssertionError: the function's LogFormat is JSON, but /sim2real/behav/logroute-<suffix> holds an unstructured line carrying '<marker>'`. The function's stored LoggingConfig did round-trip, and the LogGroup override did receive the line.
Cause 2: expected — four coexisting aliases (no weight, 0.10, 0.50, 1.00) each answer 200 concurrent Invokes reporting their executed version, with the 1.00 rung deterministically 200/200 on the weighted version and the unweighted rung 0/200. Actual — `Error: Check timed out after 180.0s`; no sample completes and no rung is measurable.

## Steps to Reproduce
Cause 1: CreateFunction (python3.12) with LoggingConfig={LogFormat: JSON, ApplicationLogLevel: WARN, SystemLogLevel: INFO} and a handler that emits logging.debug/info/warning plus a bare print; wait for State=Active; Invoke with LogType=Tail; then FilterLogEvents over /aws/lambda/<fn> (and, for the second check, over the group named by LoggingConfig.LogGroup) and parse each delivered message as JSON. Every delivered application event is '[LEVEL]\t<timestamp>\t<request id>\t<message>' text; none parses as a JSON record carrying `level`.
Cause 2: CreateFunction, PublishVersion twice (v1, v2), then CreateAlias four times over the same function with RoutingConfig.AdditionalVersionWeights {} / {v2: 0.10} / {v2: 0.50} / {v2: 1.00}; invoke each alias 200 times with 8 concurrent workers and tally the version each invocation reports. The run does not finish inside the 180 s budget.
