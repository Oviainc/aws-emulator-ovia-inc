# Interconnect: ListAttachPoints misclassifies unknown environmentId, UpdateConnection not-found/state-refusal messages are not AWS's form, and the DeleteConnection terminal-state flow does not complete

> _Note: this issue was identified against the code base at commit `ead37dd00922f5e8ae35cfd4d29cc6e26f23d78c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAttachPoints, UpdateConnection, DeleteConnection

## Description
Four net-new root causes in the Interconnect emulator, surfaced by behavioral checks that are NOT covered by the already-filed issue 20261022T145736Z-interconnect-error-semantics-three-operations-still-501-environment.md. That issue's Cause 4 names only the GetEnvironment and CreateConnection environment-resolution paths, and its Cause 5 names only the GetConnection and DeleteConnection not-found message; the operations and handlers below are different ones and are not named there. They are numbered Cause 1 of 4 .. Cause 4 of 4; each must be closed before this issue is submitted.

=== Cause 1 of 4: ListAttachPoints answers an unknown environmentId with ResourceNotFoundException(404) instead of InterconnectClientException(400) ===
AWS: Smithy (services/service-com-amazonaws-interconnect-interconnect/smithy-model/com-amazonaws-interconnect-interconnect.json): ListAttachPoints input environmentId (required, EnvironmentId @length 1..64), @readonly, @paginated; modeled errors include InterconnectClientException (httpError 400) and ResourceNotFoundException (httpError 404). Recorded behavior: for an environmentId that corresponds to no Environment, ListAttachPoints fails with error code InterconnectClientException (HTTP 400) — not ResourceNotFoundException — with a message built from the request, as an example: "Unable to process request: This environment model with id <environmentId> could not be found". The requirement is the code/status pair and that the message names the supplied environmentId in that form; the particular id in any recording is an example. This is the same classification rule AWS applies on GetEnvironment/CreateConnection, but it is a separate read path in the emulator and a separate handler.
Emulator: ListAttachPoints with an unknown environmentId returns error code ResourceNotFoundException (the check asserts the code and reports got 'ResourceNotFoundException'). The positive control in the same check — ListAttachPoints against a real Environment id taken from ListEnvironments — succeeds, so only the unresolvable-id classification diverges.
Why: a client that branches on InterconnectClientException for "unknown environment" and reserves ResourceNotFoundException for connection-scoped lookups takes the wrong branch; the HTTP status also differs (400 vs 404), so status-based retry, alarming and error-metric classification diverge.
Fix: the ListAttachPoints handler's environment-resolution step (the same classification the GetEnvironment/CreateConnection fix must apply) — classify an unresolvable environmentId as InterconnectClientException and build the message from the requested id.
Traces: interconnect.list-attach-points-nonexistent-environment-rejected.

=== Cause 2 of 4: UpdateConnection's connection-not-found message is not AWS's request-derived form ===
AWS: Smithy: UpdateConnection input identifier (required, ConnectionId @length 1..32, @pattern ^(mcc|lmcc)-[a-z0-9]{8}$), @idempotent; modeled errors include ResourceNotFoundException (404). Recorded behavior: for a pattern-valid but nonexistent connection id, UpdateConnection returns code ResourceNotFoundException — which the emulator already gets right — with a message built from the request: "Unable to process request: Connection does not exist for <identifier>". The rule is known (fixed prefix/suffix around the identifier taken from the request), so that FORM is the requirement; the particular id is an example. Note this is a DIFFERENT wording from the GetConnection/DeleteConnection not-found form ("Unable to process request: Unable to retrieve connection <identifier>, as it does not exist") that the already-filed issue's Cause 5 covers — fixing those two handlers does not fix this one.
Emulator: the message is "no connection with identifier '<identifier>'" (reported for identifier mcc-ffffffff), i.e. the right code with a message that does not use AWS's "Unable to process request: Connection does not exist for ..." construction. The check's earlier positive control (UpdateConnection on a live Connection persists the new description) passed, so only the not-found message diverges.
Why: operators and tests that read or compare AWS's wording for a correctly classified failure see a different string for every UpdateConnection against a missing connection; the service-wide "Unable to process request:" envelope is absent.
Fix: the UpdateConnection handler's not-found path (its own message construction, distinct from the shared GetConnection/DeleteConnection one).
Traces: interconnect.update-connection-nonexistent-id-rejected.

=== Cause 3 of 4: UpdateConnection's refusal on a deleted Connection carries a non-AWS message ===
AWS: Smithy: UpdateConnection models InterconnectClientException (400); Connection.state targets ConnectionState with values available, requested, pending, down, deleting, deleted, failed, updating. Recorded behavior: UpdateConnection against a Connection in the terminal 'deleted' state is refused with code InterconnectClientException (HTTP 400) — the emulator gets the code right — and the message "Unable to process request: Cannot update connection <identifier>: only connections in 'requested' or 'available' state can be updated". The rule is known: the message is built from the request's identifier plus the set of states AWS permits an update from, so that form (and the stated permitted-state rule) is the requirement; the particular id is an example.
Emulator: the message is "connection '<identifier>' is deleted and cannot be modified" (reported for mcc-f22a647d) — the right code, but a message that neither carries the "Unable to process request:" envelope nor states which states are updatable.
Why: a client surfacing the service's explanation to a user, or matching on the updatable-state rule, gets text that does not state the rule AWS states; a real/emulated comparison diverges on every state-refusal of an update.
Fix: the UpdateConnection handler's state-guard (the branch that refuses a non-updatable state) and its message construction.
Traces: interconnect.update-connection-after-deletion-rejected.

=== Cause 4 of 4: the DeleteConnection lifecycle check never reaches a terminal state within the check budget ===
AWS: Smithy: DeleteConnection input identifier (required, ConnectionId), @idempotent, output connection (required, Connection); Connection.state includes 'deleting' and 'deleted' (documented as "deleting: The connection is being deleted" / "deleted: The connection has been deleted"). Recorded behavior: DeleteConnection is accepted and echoes the Connection whose id equals the requested identifier, and the Connection subsequently converges to the terminal 'deleted' state (or becomes not-found) when polled with GetConnection. The requirement is that a deleted Connection converges to a terminal state observable through GetConnection within a bounded time, without the caller hanging.
Emulator: the check (provision an Environment attach point via a Direct Connect gateway, CreateConnection, DeleteConnection, then poll GetConnection) does not complete — verdict mismatch, "Check timed out after 60.0s". Hypothesis: one of the steps in that sequence stalls rather than converging — either the poll that waits for a newly created Direct Connect gateway to appear in ListAttachPoints, or the post-delete state convergence to 'deleting'/'deleted'. The sibling check interconnect.update-connection-after-deletion-rejected does observe state 'deleted' after a delete, so the convergence is at least sometimes reached; the stall is in this sequence as replayed and needs to be traced in the CreateConnection/DeleteConnection state machine and the attach-point listing path.
Why: a client (or an SDK waiter) that deletes a Connection and polls for its terminal state hangs instead of completing, so the delete lifecycle cannot be exercised against the emulator at all.
Fix: the DeleteConnection handler and the Connection state it writes (plus the ListAttachPoints/CreateConnection prerequisite path this sequence depends on) — make the post-delete state converge to a terminal 'deleted' (or not-found) promptly and ensure every step answers without blocking.
Traces: interconnect.delete-connection-transitions-to-deleting-then-gone.
