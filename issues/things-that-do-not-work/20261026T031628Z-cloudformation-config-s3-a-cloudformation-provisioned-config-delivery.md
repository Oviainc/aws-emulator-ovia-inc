# cloudformation__config__s3: a CloudFormation-provisioned Config delivery channel delivers no snapshot — the recorded bucket's configuration item and the snapshot object never appear (1 cause)

> _Note: this issue was identified against the code base at commit `ebfe4f059696b431f00c6abb397dd11b94b7073a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeliverConfigSnapshot

## Description
ONE root cause. ONE CAUSE must be closed.

Cause 1 of 1: With a delivery bucket, bucket policy and recorder role provisioned by a CloudFormation stack, Config's recording + on-demand snapshot-delivery pipeline produces nothing observable: no configuration item for a resource created while the recorder runs, and no delivered snapshot object in the delivery bucket.

AWS: recorded behavior only, with model grounding. Recorded flow on real AWS: a CREATE_COMPLETE stack exports the delivery bucket name and the recorder role ARN; PutConfigurationRecorder + PutDeliveryChannel + StartConfigurationRecorder then make the recorder report recording=true; an S3 bucket created afterwards becomes discoverable through GetResourceConfigHistory(resourceType="AWS::S3::Bucket", resourceId=<bucket>) with a configurationItems entry whose `arn` ends in the bucket name, whose `resourceId` is the bucket name and whose `awsRegion` is the request region; DeliverConfigSnapshot(deliveryChannelName=<channel>) returns a configSnapshotId and DescribeDeliveryChannelStatus's DeliveryChannelsStatus[0].configSnapshotDeliveryInfo then settles on lastStatus="SUCCESS"; an object then exists in the delivery bucket under the key prefix AWSLogs/<account-id>/Config/<region>/ whose key contains that configSnapshotId, is gzip-framed (first two bytes 0x1f 0x8b) and gunzips to JSON carrying a `configurationItems` array that includes the recorded bucket's item (ARN/resourceId/awsRegion as above). Smithy (services/service-com-amazonaws-configservice-starlingdoveservice/smithy-model/com-amazonaws-configservice-starlingdoveservice.json): DeliverConfigSnapshot -> DeliverConfigSnapshotResponse{configSnapshotId}, errors NoSuchDeliveryChannelException / NoAvailableConfigurationRecorderException / NoRunningConfigurationRecorderException (all errorKind client, httpError 400) — the delivery outcome is never raised to the caller, so configSnapshotDeliveryInfo plus the S3 object are the only places it is reported; GetResourceConfigHistory -> {configurationItems, nextToken}, paginated, with ResourceNotDiscoveredException (client, 400) for a resource Config has recorded nothing for. The account id, region, bucket/recorder/channel names and the snapshot id are values taken from the request and the emulator's state — only the AWSLogs/<account>/Config/<region>/ prefix shape, the gzip framing and the configurationItems payload are fixed requirements.

Emulator: the check is killed with 'Check timed out after 60.0s' and no stack frame. Everything up to the first stalling poll is reached (CreateStack of the bucket + bucket policy + recorder role, the stack reaching CREATE_COMPLETE, PutConfigurationRecorder with the stack's role ARN, PutDeliveryChannel at the stack's bucket — which does enforce the delivery policy — StartConfigurationRecorder reporting recording=true, and CreateBucket of the observed bucket). The emulator then never satisfies any of the downstream oracles, each of which the check gives a 420–500s budget of its own, so the emulator is not merely slower than this harness — nothing ever transitions: GetResourceConfigHistory for the just-created AWS::S3::Bucket stays empty (or answers ResourceNotDiscoveredException), configSnapshotDeliveryInfo.lastStatus never becomes SUCCESS, and ListObjectsV2 on the delivery bucket never shows a key containing the configSnapshotId that DeliverConfigSnapshot returned. Hypothesis (the timeout report names no frame): the first poll to stall is the configuration-item poll for the observed bucket, because the recorder has no recording side effects at all; the snapshot-delivery and delivered-object oracles are then unreachable in the same run.

Why: a client that wires up Config delivery through CloudFormation gets a pipeline that is accepted at every control-plane call and silently does nothing. Compliance/audit consumers that read configuration items for a newly created resource, or that fetch and gunzip the delivered snapshot from the delivery bucket to inventory their account, see an empty history and an empty bucket forever, with no error anywhere to distinguish 'not yet delivered' from 'never will be'. Anything built on the snapshot's ARN/resourceId/awsRegion fields cannot be exercised at all.

Fix: the Config recording and snapshot-delivery pipeline and their status surfaces — the recorder's resource-discovery/record path behind services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/start_configuration_recorder.rs and the state it feeds src/ops/get_resource_config_history.rs, plus src/ops/deliver_config_snapshot.rs, the delivery task behind src/ops/put_delivery_channel.rs's channel state (which must perform the gzip-framed S3 write under AWSLogs/<account>/Config/<region>/ with the snapshot id in the key) and src/ops/describe_delivery_channel_status.rs, which must report the resulting terminal lastStatus.
