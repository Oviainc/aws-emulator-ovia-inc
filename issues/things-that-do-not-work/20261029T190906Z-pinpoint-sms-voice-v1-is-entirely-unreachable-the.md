# Pinpoint SMS Voice (V1) is entirely unreachable: the router resolves services by SigV4 signing name, so PinpointSMSVoice and PinpointSMSVoiceV2 both claim 'sms-voice' and every request is refused pre-dispatch with a non-AWS 'AmbiguousService' code (HTTP 500)

> _Note: this issue was identified against the code base at commit `69bb2c4e0c47afe7ac06c67651974f0cf752730a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListConfigurationSets

## Description
Cause 1 of 1: the emulator's request router keys emulated services by their SigV4 signing name rather than by the endpoint the request was addressed to (or by the candidate services' HTTP route tables), so the two Pinpoint SMS/Voice crates collide and NEITHER is reachable. Every request signed for 'sms-voice' is rejected before dispatch, so all 8 PinpointSMSVoice V1 operations answer the same non-AWS error. All 17 pinpoint-sms-voice behavioral checks fail on this one refusal — 10 as mismatches on the error code they assert and 7 as hard errors on the very first call they make (the ListConfigurationSets positive control).

AWS: Smithy, services/service-com-amazonaws-pinpointsmsvoice-pinpointsmsvoice/smithy-model/com-amazonaws-pinpointsmsvoice-pinpointsmsvoice.json — service PinpointSMSVoice (sdkId 'Pinpoint SMS Voice', version 2018-09-05, protocol restJson1, sigv4Name 'sms-voice', awsService.endpointPrefix 'sms-voice.pinpoint', arnNamespace 'sms-voice', cloudTrailEventSource 'pinpointsmsvoice.amazonaws.com'); and services/service-com-amazonaws-pinpointsmsvoicev2-pinpointsmsvoicev2/smithy-model/com-amazonaws-pinpointsmsvoicev2-pinpointsmsvoicev2.json — service PinpointSMSVoiceV2 (sdkId 'Pinpoint SMS Voice V2', version 2022-03-31, protocol awsJson1_0, sigv4Name 'sms-voice', awsService.endpointPrefix 'sms-voice', arnNamespace 'sms-voice'). Sharing a sigv4 signing name across two service versions is normal and deliberate in AWS: the two are distinguished by the ENDPOINT they are addressed to (sms-voice.pinpoint.<region>.amazonaws.com for V1 vs sms-voice.<region>.amazonaws.com for V2) and by wholly disjoint wire shapes — V1 is restJson1 with /v1/sms-voice/... paths (GET /v1/sms-voice/configuration-sets, POST /v1/sms-voice/configuration-sets, DELETE/PUT/GET /v1/sms-voice/configuration-sets/{ConfigurationSetName}/event-destinations[/{EventDestinationName}], POST /v1/sms-voice/voice/message), V2 is awsJson1_0 dispatched by an X-Amz-Target header on POST / — never by the signing name. On real AWS a 'sms-voice'-signed GET /v1/sms-voice/configuration-sets is dispatched to PinpointSMSVoice.ListConfigurationSets and answered 200 with a ConfigurationSets member. The V1 model's error vocabulary is the service-common set BadRequestException (errorKind client, httpError 400, member Message, doc 'The input you provided is invalid.'), InternalServiceErrorException and TooManyRequestsException, plus per-operation AlreadyExistsException, LimitExceededException and NotFoundException (client, httpError 404, member Message, doc "The resource you attempted to access doesn't exist."). 'AmbiguousService' appears in neither model. Recorded behavior only (not in the model) for the gated account these checks were recorded against: the legacy V1 write path and the resource-scoped read are closed by an entitlement gate, so CreateConfigurationSet / CreateConfigurationSetEventDestination / UpdateConfigurationSetEventDestination / DeleteConfigurationSet / DeleteConfigurationSetEventDestination / GetConfigurationSetEventDestinations / SendVoiceMessage return HTTP 403 with Error.Code 'AccessDeniedException' and a non-empty Error.Message (recorded message text 'Access Denied' — fixed text, with no variable part), input-independently and before any shape or existence check; while ListConfigurationSets (no resource-scoped ARN) stays open and returns 200. Request-shape validation still precedes authorization where the request is malformed: a ConfigurationSetName containing spaces/punctuation returns 400 BadRequestException, an empty ConfigurationSetName returns 400 BadRequestException whose message names the member 'ConfigurationSetName' (fixed text is the missing/invalid-parameter wording, the variable part is the member name taken from the request), and a non-numeric PageSize (modeled as __string via httpQuery, so no client-side type check) returns 400 BadRequestException.

Emulator: no PinpointSMSVoice V1 operation is ever dispatched. Every call is refused pre-dispatch with HTTP status 500, Error.Code 'AmbiguousService' and Error.Message "2 emulated services all claim requests for 'sms-voice': sms-voice, sms-voice; the request is rejected rather than served by an arbitrary one". The duplicated 'sms-voice, sms-voice' in that message shows the router is listing the two crates' shared SIGNING NAME instead of their distinct endpoint prefixes ('sms-voice.pinpoint' vs 'sms-voice'), which is exactly why it cannot tell them apart. Concretely: ListConfigurationSets returns 500/AmbiguousService instead of 200 with ConfigurationSets (and botocore retries it to exhaustion — 'reached max retries: 3' — because a 500 is classified retryable, so the 7 [error] checks die on their positive control); CreateConfigurationSet returns 'AmbiguousService' instead of 403 'AccessDeniedException'; CreateConfigurationSet with an invalid name returns 'AmbiguousService' instead of 400 'BadRequestException'; GetConfigurationSetEventDestinations, DeleteConfigurationSet, DeleteConfigurationSetEventDestination, UpdateConfigurationSetEventDestination and SendVoiceMessage all return 'AmbiguousService' instead of 403 'AccessDeniedException'; ListConfigurationSets with a non-numeric PageSize or a garbage NextToken returns 'AmbiguousService' instead of 400 'BadRequestException'. Under concurrency the refusal is at least uniform: 8 racing CreateConfigurationSet calls all get the same 500/AmbiguousService, but none gets the 403/AccessDeniedException AWS gives.

Why: Pinpoint SMS Voice V1 is 100% unusable — not degraded, unreachable — and symmetrically any request a client signs for 'sms-voice' (i.e. the whole V2 surface too) is refused. An SDK client receives a ClientError whose code is in neither service's error set, so no client error handling matches it: 'AccessDeniedException' branches (re-auth, fall back to V2, surface a permissions message) never fire; 'BadRequestException' branches (fix and resubmit the input) never fire; 'NotFoundException' create-if-missing branches never fire. Worse, the refusal is a 500, which botocore classifies as a retryable server fault, so every call burns the full retry budget and latency before failing, and a caller's retry/circuit-breaker logic sees a transient outage rather than a permanent client error. Because the refusal happens before dispatch it also masks the entire validation/authorization surface of the service: the ordering of shape validation vs authorization on CreateConfigurationSet, the missing-parameter message that must name ConfigurationSetName, PageSize/NextToken validation on ListConfigurationSets, and the input-independence of the SendVoiceMessage denial are all untestable until the router can route.

Fix: the shared request router / service-resolution layer, not any Pinpoint SMS Voice handler. Resolve the target emulated service from the request's addressed endpoint (Host / awsService.endpointPrefix — 'sms-voice.pinpoint' for V1 vs 'sms-voice' for V2) and, failing that, from the candidates' protocol and route tables (V1 is restJson1 on /v1/sms-voice/* paths; V2 is awsJson1_0 dispatched by X-Amz-Target on POST /), and treat a shared sigv4Name as expected rather than as a conflict. The 'AmbiguousService' refusal path must not be reachable for two services that differ in endpointPrefix or in protocol, and must never be returned as an HTTP 500 with an error code outside the service's modeled vocabulary. This is the same router root cause already filed for other signing-name-colliding pairs — see open issues 20261022T110819Z-migrationhub-config-is-entirely-unreachable-router-resolves-by.md, 20261022T145747Z-connectcampaigns-is-entirely-unreachable-router-resolves-services-by.md, 20261029T174910Z-payment-cryptography-control-plane-is-entirely-unreachable-the.md and 20261029T185843Z-agent-registry-is-entirely-unreachable-router-resolves-services.md — but none of those issues names sms-voice / pinpoint-sms-voice or carries these replay keys, so this pair is not covered by them.

Traces: all 17 pinpoint-sms-voice checks, every one of them failing on this single pre-dispatch refusal — pinpoint-sms-voice.list-configuration-sets-returns-valid-shape, .list-configuration-sets-pagination-no-duplicates, .list-configuration-sets-invalid-page-size-rejected, .list-configuration-sets-garbage-next-token-rejected, .create-configuration-set-denied, .create-configuration-set-invalid-name-validated-before-denied, .concurrent-create-configuration-set-denied-consistently, .create-event-destination-denied-across-destination-types, .create-event-destination-on-nonexistent-configset-denied, .delete-configuration-set-nonexistent-denied, .delete-configuration-set-event-destination-nonexistent-denied, .get-configuration-set-event-destinations-empty-name-validation, .get-configuration-set-event-destinations-nonexistent-configset-error, .update-configuration-set-event-destination-invalid-payload-still-denied, .update-configuration-set-event-destination-nonexistent-denied, .send-voice-message-invalid-phone-number-format-rejected, .send-voice-message-mutually-exclusive-content-rejected.

## Steps to Reproduce
