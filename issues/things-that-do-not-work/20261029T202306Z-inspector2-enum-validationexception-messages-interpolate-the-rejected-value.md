# inspector2 enum ValidationException messages interpolate the rejected value, use the wrong member path and the wrong value-set ordering (2 causes, behavioral replay of an already-open wire issue)

> _Note: this issue was identified against the code base at commit `221dd3602e5d0e66d71e70da1fb8509b07c948c5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateFilter

## Description
SAME ROOT CAUSE as the already-open issue 20261029T171819Z-inspector2-constraint-violation-validationexception-messages-add-the-rejected.md, which carries only WIRE replay keys (inspector2|CreateFilter|4xx->4xx|$.message and inspector2|CreateCodeSecurityScanConfiguration|4xx->4xx|$.message); these two BEHAVIORAL checks were not marked OWNED by it in the replay report, so they are recorded here with their behavioral check ids so the fixer can re-replay them. A fixer should close the two together — one correction to the shared constraint-violation message builder satisfies both.

TWO causes, both the same defect in the inspector2 constraint-violation message builder for ValidationException (HTTP 400). In each case the status (400) and the error type (ValidationException) are already correct and only the `message` string diverges, in three consistent ways: (a) the emulator interpolates the REJECTED VALUE into the sentence ("Value 'X' at '<path>' ...") where AWS writes "Value at '<path>' ..." for these constraint classes; (b) for an enum member inside a list the emulator names the indexed `.member` path and a bare enum clause, where AWS names the LIST member and nests the member clause inside "Member must satisfy constraint: [ ... ]"; (c) the enum value set is reproduced in the model's declaration order rather than the order AWS uses. The fixed text of each sentence ("1 validation error detected: ", "Value at '", "' failed to satisfy constraint: Member must satisfy enum value set: [") is the requirement; the variable parts are the member path and the enum value list, which come from the request's shape and from the model — never from one recording's rejected value.

Cause 1 of 2: CreateFilter with an unmodelled StringComparison in filterCriteria.severity[].comparison.
AWS: Smithy: CreateFilter.filterCriteria (required, FilterCriteria) -> severity is a list of StringFilter; StringFilter.comparison (required) targets StringComparison, whose values are EQUALS, PREFIX, NOT_EQUALS; modeled error ValidationException (httpError 400). Recorded behavior: 400 ValidationException with message "1 validation error detected: Value at 'filterCriteria.severity.1.member.comparison' failed to satisfy constraint: Member must satisfy enum value set: [NOT_EQUALS, PREFIX, EQUALS]" — the rejected value is ABSENT and the value set is enumerated NOT_EQUALS, PREFIX, EQUALS. The effect must also be absent: no filter with the rejected name is created, while the same call with comparison=EQUALS succeeds.
Emulator: answers 400 ValidationException (correct status and code) with message "1 validation error detected: Value 'NOT_A_REAL_COMPARISON' at 'filterCriteria.severity.1.member.comparison' failed to satisfy constraint: Member must satisfy enum value set: [EQUALS, PREFIX, NOT_EQUALS]" — the member path is right, but the rejected value is interpolated and the value set is in model-declaration order.
Why: a client or assertion harness matching AWS's message for an invalid filter comparison never matches, and because the submitted value is echoed, the message changes for every distinct bad input — so the error text is not stable across requests the way AWS's is.
Fix: the shared constraint-violation message builder reached from CreateFilter's filterCriteria validation in the inspector2 crate (scalar-enum branch: omit the rejected value, emit AWS's value-set ordering).

Cause 2 of 2: CreateCodeSecurityScanConfiguration with an unmodelled string in configuration.ruleSetCategories.
AWS: Smithy: CreateCodeSecurityScanConfiguration.configuration -> CodeSecurityScanConfiguration.ruleSetCategories (required, list of RuleSetCategory, @length 1..3); RuleSetCategory is an enum with values SAST, IAC, SCA; modeled error ValidationException (httpError 400). Recorded behavior: 400 ValidationException with message "1 validation error detected: Value at 'configuration.ruleSetCategories' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [IAC, SAST, SCA]]" — AWS names the LIST member (no element index, no `.member` suffix), omits the rejected value, wraps the member constraint in "Member must satisfy constraint: [ ... ]", and enumerates the value set IAC, SAST, SCA.
Emulator: answers 400 ValidationException with message "1 validation error detected: Value 'NOT_A_REAL_RULE_SET_CATEGORY' at 'configuration.ruleSetCategories.1.member' failed to satisfy constraint: Member must satisfy enum value set: [SAST, IAC, SCA]" — rejected value interpolated, indexed `.member` path instead of the list member, no nested "Member must satisfy constraint: [...]" wrapper, and the value set in model-declaration order.
Why: same as cause 1 — a client matching AWS's wording for a bad rule-set category never matches, and the leaked request value makes the message request-dependent.
Fix: the same shared constraint-violation message builder, list-of-enum branch, reached from CreateCodeSecurityScanConfiguration's request validation (suppress the value, name the list member, emit the nested member-constraint wrapper, emit AWS's value-set ordering). Note this validation runs BEFORE the handler, which is itself still an unimplemented scaffold stub (covered by its own auto-filed issue); the message defect is independent of that stub.
