Cause 1 of 3: CreateConfigurationSet accepts a syntactically invalid ConfigurationSetName instead of refusing it with BadRequestException, so no name validation exists at all.
AWS: recorded behavior only, supported by the model's shape choice — Smithy: CreateConfigurationSet (POST /v1/sms-voice/configuration-sets) input member ConfigurationSetName targets `WordCharactersWithDelimiters` (a dedicated name shape, as opposed to the plain `__string` other members use), and CreateConfigurationSet models BadRequestException @error client @httpError 400 with a single member Message, doc "The input you provided is invalid.". A name containing spaces and punctuation (the recording sends a name of the form `<word> <word> <word> !!`) is refused with HTTP 400, Error.Code `BadRequestException` and Error.Message `The following parameter is null, empty or invalid: ['configurationSetName']`. Message template: the fixed text is `The following parameter is null, empty or invalid: ['` + `']`, and the single variable part is the offending member name rendered in the wire/lowerCamel spelling of the model member — here `configurationSetName`, taken from the request's rejected member. This validation runs BEFORE the account entitlement gate: the identical call with a name made only of word characters and delimiters is refused differently (HTTP 403 `AccessDeniedException`, Message `Access Denied` — entirely fixed text, no variable part), which is what makes the ordering observable. Neither name may ever appear in a subsequent ListConfigurationSets.
Emulator: the invalid name SUCCEEDS — HTTP 200 with an empty JSON body (`content-length: 2`), and a configuration set is materialised under that name. The handler validates only blankness: `services/service-com-amazonaws-pinpointsmsvoice-pinpointsmsvoice/src/ops/create_configuration_set.rs` filters on `!name.trim().is_empty()` and otherwise stores the name verbatim, so any character set is accepted. The check aborts on that unexpected 200, so the emulator's 403-vs-400 ORDERING is unverified behind it: after the validation is added, the valid-name leg of the same check must still answer 403 `AccessDeniedException` / `Access Denied`.
Why: a client that validates its naming inputs against this service ships names AWS will reject — the emulator reports the name as created, so the client records a configuration set id that does not exist and only discovers the 400 in production. Worse, the two refusal classes are collapsed: a caller cannot tell "fix your input" (400, deterministic, do not retry) from "you are not entitled" (403, escalate permissions), because the emulator answers neither.
Fix: the CreateConfigurationSet handler's input validation — reject a ConfigurationSetName that is not word characters with delimiters with the modelled BadRequestException (400) whose Message names the member `configurationSetName`, ahead of the state lookup and ahead of the entitlement denial.
Failing checks: pinpoint-sms-voice.create-configuration-set-invalid-name-validated-before-denied.

Cause 2 of 3: CreateConfigurationSetEventDestination runs the parent-existence lookup instead of the denial, and the denial's Message is destination-shape dependent.
AWS: recorded behavior only — POST /v1/sms-voice/configuration-sets/{ConfigurationSetName}/event-destinations against a never-created configuration set is refused HTTP 403 with Error.Code `AccessDeniedException` for every destination shape, but the MESSAGE is not uniform across shapes: a destination that carries no passed role (SnsDestination{TopicArn}) is refused with Message `Access Denied`, while a destination that passes an IAM role belonging to another account (CloudWatchLogsDestination{LogGroupArn,IamRoleArn} and KinesisFirehoseDestination{DeliveryStreamArn,IamRoleArn}, with an IamRoleArn in an account other than the caller's) is refused with Message `Cross-account pass role is not allowed.` Both messages are entirely fixed text — no ids, arns or names are interpolated into either. The refusal precedes any resource-existence lookup, so it does not depend on whether the named set exists; nothing is created, and the set never appears in ListConfigurationSets. Smithy: CreateConfigurationSetEventDestination models AlreadyExistsException 409, BadRequestException 400, LimitExceededException 412, NotFoundException 404 (doc "The resource you attempted to access doesn't exist."), TooManyRequestsException 429 — `AccessDeniedException` is absent from the model and must be served as a synthetic 403 envelope with Code `AccessDeniedException` and member Message.
Emulator: answers the modelled NotFoundException — HTTP 404, Code `NotFoundException` — on the first (sns) destination shape, so the per-shape message distinction is never reached. Replay: `sns destination: expected AccessDeniedException, got 'NotFoundException'`. The positive control in the same check passed (ListConfigurationSets answered 200 with a ConfigurationSets member and the name absent), so this is the write path being misclassified, not a credential or reachability problem.
Why: a client branches on 403 (stop, escalate permissions) versus 404 (create the parent and retry). The emulator steers every caller onto create-the-parent-and-retry, which on real AWS never terminates because the parent create is itself refused. And a caller that surfaces the refusal reason to an operator loses the actionable one: `Cross-account pass role is not allowed.` tells the operator the IamRoleArn is in the wrong account, which `NotFoundException` does not.
Fix: the CreateConfigurationSetEventDestination handler — apply the entitlement denial before the parent-existence lookup and before the EventDestination payload inspection, and select the Message by whether the destination passes a cross-account IamRoleArn (`Cross-account pass role is not allowed.`) or not (`Access Denied`).
Failing checks: pinpoint-sms-voice.create-event-destination-denied-across-destination-types.

Cause 3 of 3: the invalid-PageSize BadRequestException on ListConfigurationSets carries a Message AWS does not send.
AWS: recorded behavior only — Smithy: ListConfigurationSets (GET /v1/sms-voice/configuration-sets) models PageSize as `__string` bound to @httpQuery, so a non-numeric value is serialised by the SDK and reaches the service rather than being refused client-side. The service refuses it with HTTP 400 and Error.Code `BadRequestException`, and the error payload carries NO Message member at all (BadRequestException.Message is optional in the model — structure BadRequestException, @error client, @httpError 400, single optional member Message). The absence of the member is the requirement: `Error.Message` must be unset, not empty-string, not a reworded sentence. A syntactically valid PageSize (e.g. `"5"`) answers 200 with a ConfigurationSets member and needs no write permission, so this is the only refusal on this path.
Emulator: returns the right code and status but adds a message of its own: `The following parameter is null, empty or invalid: ['pageSize']`. Replay: `AssertionError: expected no message, got "The following parameter is null, empty or invalid: ['pageSize']"`. Source: `services/service-com-amazonaws-pinpointsmsvoice-pinpointsmsvoice/src/ops/list_configuration_sets.rs`, `parse_page_size` populates `BadRequestException { message: Some(refusal_wording::invalid_parameters(&["PageSize"])) }`. Note this is the SAME wording helper that Cause 1 shows is correctly required on CreateConfigurationSet's name refusal — the helper is right, it is applied on a path where AWS sends no message. Because the check aborts on this assertion, the valid-PageSize leg (`PageSize="5"` -> 200 with ConfigurationSets) is unverified behind it.
Why: a client that logs or matches on `Error.Message` sees a sentence that will never arrive from AWS; code that treats a present Message as "the service explained the problem" (and an absent one as "retry/inspect locally") takes the wrong branch, and message-equality assertions written against the emulator fail against AWS.
Fix: the ListConfigurationSets handler's PageSize validation — emit the BadRequestException for a non-positive/non-numeric PageSize with no Message member set, leaving the NextToken refusal and the name refusal in Cause 1 (which DO carry the sentence) unchanged.
Failing checks: pinpoint-sms-voice.list-configuration-sets-invalid-page-size-rejected.
