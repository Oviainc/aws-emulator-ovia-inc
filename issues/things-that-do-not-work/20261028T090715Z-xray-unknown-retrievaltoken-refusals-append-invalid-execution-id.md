# xray: unknown-RetrievalToken refusals append 'Invalid execution id provided: <token>' instead of AWS's fixed cause clause 'Invalid Execution Id' (CancelTraceRetrieval, ListRetrievedTraces, GetRetrievedTracesGraph)

> _Note: this issue was identified against the code base at commit `7ea740a9eddbcecb1c916c525a3425e0eb603db2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CancelTraceRetrieval

## Description
ONE root cause, shared by the three trace-retrieval readers that refuse a RetrievalToken this service never issued. The xray service is bootstrapped and answering (102/125 xray checks pass in this run), so this is a fidelity defect, not a bootstrap gap. None of the four failing checks below is marked ALREADY FILED or OWNED in the replay report.

RELATED, NOT COVERING: 20261025T043615Z-xray-3-net-new-behavioral-root-causes-getservicegraph.md covers GetServiceGraph projection, ResponseTimeRootCauses derivation and the missing IAM authorization gate; 20261022T045628Z-xray-x-ray-account-config-surfaces-are-overly-permissive.md covers PutEncryptionConfig/TagResource/UpdateTraceSegmentDestination permissiveness; 20261022T013648Z-xray-putresourcepolicy-stub.md covers the PutResourcePolicy stub. None of them names the retrieval-token refusal message, and the refusal here is not over-permissive: the status and error code are already correct and only the message text diverges.

Cause 1 of 1: the malformed/unissued-retrieval-token refusal message appends the emulator's own cause string instead of AWS's fixed cause clause.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models CancelTraceRetrieval (POST /CancelTraceRetrieval), ListRetrievedTraces (POST /ListRetrievedTraces) and GetRetrievedTracesGraph (POST /GetRetrievedTracesGraph), each taking a required RetrievalToken (@length 0..1020) and each declaring InvalidRequestException (400, "The request is missing required parameters or has invalid parameters"), ResourceNotFoundException (404) and ThrottledException (429). The model does not state the message text, so for the text this is recorded behavior only: real AWS refuses a token it never issued with HTTP 400, code InvalidRequestException, and a message of the form `Invalid retrieval token <RetrievalToken> passed: Invalid Execution Id` for CancelTraceRetrieval and `Invalid execution id <RetrievalToken> passed: Invalid Execution Id` for ListRetrievedTraces and GetRetrievedTracesGraph. Template parts: the leading phrase (`Invalid retrieval token ` / `Invalid execution id `), the separator ` passed: ` and the trailing cause clause `Invalid Execution Id` are FIXED text, capitalised exactly that way; the only variable part is the RetrievalToken value echoed from the request. The token values in the recordings (`sim2real-behav-not-a-real-token`, `sim2real-behav-unknown-retrieval-token-0000000000`) are request values filling that slot, not part of the requirement.
Emulator: the status (400) and the code (InvalidRequestException) match, and the leading phrase is per-operation correct, but the trailing cause clause is replaced by the emulator's own sentence, which also repeats the token: CancelTraceRetrieval answers `Invalid retrieval token <token> passed: Invalid execution id provided: <token>` where AWS answers `Invalid retrieval token <token> passed: Invalid Execution Id`; ListRetrievedTraces and GetRetrievedTracesGraph answer `Invalid execution id <token> passed: Invalid execution id provided: <token>` where AWS answers `Invalid execution id <token> passed: Invalid Execution Id`. All four checks reach their message assertion only after their positive control passed (a genuinely issued token was accepted, and for xray.list-retrieved-traces-status-progresses-over-time the retrieval also reached COMPLETE), so the divergence is isolated to the refusal message of an unissued token.
Why: the error message is part of the contract a client matches on. SDK/CLI users, log scrapers and test suites that assert the AWS wording (`... passed: Invalid Execution Id`) see a different sentence, and the emulator additionally leaks the submitted token a second time into the message, so a client that redacts or parses by position gets a different payload than production returns. Since the code is right, the mismatch is silent: nothing fails until a consumer compares the text.
Fix: the shared refusal-message builder used by all three handlers — `crate::state::malformed_retrieval_token_message(<subject>, <token>)` in services/service-com-amazonaws-xray-awsxray/src/state.rs, called from services/service-com-amazonaws-xray-awsxray/src/ops/cancel_trace_retrieval.rs (line 169), and from the equivalent token-form guard in services/service-com-amazonaws-xray-awsxray/src/ops/list_retrieved_traces.rs and services/service-com-amazonaws-xray-awsxray/src/ops/get_retrieved_traces_graph.rs. It must emit the per-operation leading phrase, the token from the request, then the fixed clause `Invalid Execution Id`, and must not append a second copy of the token or its own cause sentence.
Traces: xray.cancel-trace-retrieval-unknown-token-fails, xray.list-retrieved-traces-unknown-token-fails, xray.get-retrieved-traces-graph-unknown-token-fails, xray.list-retrieved-traces-status-progresses-over-time.
