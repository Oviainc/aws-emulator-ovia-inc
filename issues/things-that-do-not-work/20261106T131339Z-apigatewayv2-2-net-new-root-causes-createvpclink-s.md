# apigatewayv2: 2 net-new root causes — CreateVpcLink's subnet-not-found message drops the relayed EC2 error envelope, and the $default-stage invoke URL cannot be carried in a StageVariables value

> _Note: this issue was identified against the code base at commit `0d41ee472df788e58645875c19630e6a52d7394d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateVpcLink

## Description
Two independent, net-new root causes in the apigatewayv2 emulator, both grounded in failing behavioral checks of this suite. They are counted and must BOTH be closed before submitting: Cause 1 of 2 and Cause 2 of 2 below. Neither is covered by an open issue; the closest neighbours are 20261104T121154Z-apigatewayv2-3-net-new-root-causes-a-cfn.md (a CFN-created VpcLink unknown to GetVpcLink, and the HTTP_PROXY PayloadFormatVersion refusal text) and the resolved 20261025T113951Z-apigatewayv2-five-refusals-return-the-right-error-code.md (five OTHER refusal message sites: CreateModel, CreateStage duplicate name, CreateIntegration/UpdateIntegration PayloadFormatVersion, UpdateRoute JWT) — neither names the two sites below, and neither check here is a refusal of an operation a resolved issue claimed to fix.

Cause 1 of 2: CreateVpcLink with a well-formed but non-existent SubnetIds entry answers BadRequestException with only API Gateway's own half of the sentence; AWS relays EC2's whole error envelope.
AWS: Smithy: CreateVpcLink errors BadRequestException (client, httpError 400) and TooManyRequestsException (429); SubnetIds is required and targets SubnetIdList. Recorded behavior for the text: AWS resolves the subnet against Amazon EC2 and RELAYS that service's error into the message, so the message is 'The subnet ID '<subnet-id>' does not exist (Service: AmazonEC2; Status Code: 400; Error Code: InvalidSubnetID.NotFound; Request ID: <ec2-request-id>; Proxy: null)'. Fixed text: everything outside the angle brackets, including the parenthesised relay clause with its 'Service: AmazonEC2', 'Status Code: 400', 'Error Code: InvalidSubnetID.NotFound' and trailing 'Proxy: null'. Variable parts: <subnet-id>, taken verbatim from the request's SubnetIds entry, and <ec2-request-id>, the per-call request id of the EC2 lookup (the check masks only that id, so it is not itself a requirement). HTTP status 400 and error code BadRequestException already match.
Emulator: BadRequestException (400, correct) with the message 'The subnet ID 'subnet-0000000000bad0bad' does not exist' — API Gateway's clause only, with the entire relayed EC2 envelope missing, so a caller cannot see WHICH service refused, under which error code, or correlate the EC2 call.
Why: a client (or operator log scraper) that parses the relayed clause to learn the underlying EC2 error code (InvalidSubnetID.NotFound) or to correlate the EC2 request id finds none, and the message does not match the text AWS emits for this refusal class, so message-based branching on the refusal fails.
Fix: the subnet-not-found refusal message built for CreateVpcLink's subnet resolution — the message builder in this service's EC2 subnet-resolution state module, where the sentence is composed before the handler lifts it into BadRequestException (services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/state/ec2_subnets.rs:83-85, subnet_does_not_exist_message, reached from resolve_vpc_link_subnets at the same file's line 233, whose Err becomes the operation's BadRequestException). The relay clause has to be built from the answer the EC2 lookup actually produced (its error code, status and request id) rather than appended as literal text.
Traces: apigatewayv2.create-vpc-link-invalid-subnet-bad-request (the error CODE and the no-orphan-VpcLink effect both pass; only Error.Message diverges).

Cause 2 of 2: an HTTP api's $default-stage invoke URL, as this emulator serves it, cannot be used as a StageVariables value, so an HTTP_PROXY IntegrationUri parameterised by a stage variable cannot even be configured — CreateStage refuses the stage before any request is made.
AWS: Smithy: CreateStage errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429); StageVariables targets StageVariablesMap and is documented 'Variable names can have alphanumeric and underscore characters, and the values must match [A-Za-z0-9-._~:/?#&=,]+'. Api$ApiEndpoint documents the invoke URI as '{api-id}.execute-api.{region}.amazonaws.com' with 'the stage name … typically appended', and the reserved $default stage is served at the api's ROOT (no stage segment in the path), which the emulator's own data plane states too (services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/service/invoke.rs, step 2 of 'What it resolves, in order'). Consequence on AWS: the invoke URL of a $default stage contains no character outside the documented stage-variable value set, so CreateStage(StageVariables={'backendUrl': '<backend-$default-invoke-url without its scheme>'}) is ACCEPTED and the stage is created; the check then exercises substitution of that variable into an HTTP_PROXY IntegrationUri.
Emulator: CreateStage answers 400 BadRequestException "Invalid value for StageVariables: the value of 'backendUrl' must match [A-Za-z0-9-._~:/?#&=,]+." for the value derived from the backend api's own $default-stage invoke URL as this emulator is reached at it. The character allowlist itself matches the documented set (crate::state::validate_stage_variables / is_stage_variable_value_character, services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/state.rs:2872-2912, called from ops/create_stage.rs:201), so the offending character comes from the URL the emulator's own addressing produces. Hypothesis: it is the '$' of the literal '$default' stage segment that this emulator's local, path-carried execute-api addressing puts in the URL (crate::state::LOCAL_ENDPOINT_PREFIX, '/_aws/execute-api/{api-id}/{stage}/{path}'), a character AWS's $default invoke URL never contains because that stage is served at the api root. Nothing else in such a URL (letters, digits, '-', '.', '_', ':', '/') is outside the set.
Why: a client that parameterises a backend host through a stage variable — the documented way one integration serves a different backend per stage — cannot create the stage at all against the emulator, so the whole stage-variable substitution contract (and its negative leg, a stage that defines no such variable answering 500 {"message":"Internal Server Error"}) is unreachable. More generally, any value a caller derives from an api's $default-stage invoke URL is refused by this service's own validator, i.e. the address the emulator serves and the grammar it enforces disagree.
Fix: the $default stage's served/announced invoke address for a client that reaches the emulator at its own endpoint, so it carries no character outside the documented stage-variable grammar — the local path addressing in the HTTP data plane (services/service-com-amazonaws-apigatewayv2-apigatewayv2/src/service/invoke.rs, resolve) together with the endpoint the control plane announces (src/state.rs, execute_api_endpoint and the announced-endpoint helpers beside announced_portal_default_domain_name), serving the $default stage at the api root as Api$ApiEndpoint documents instead of behind a reserved-name segment. Do NOT widen validate_stage_variables: its allowlist is the documented one.
Traces: apigatewayv2.http-proxy-stage-variable-selects-backend-host (the check never reaches an invoke: it errors out on the CreateStage call that defines backendUrl).
