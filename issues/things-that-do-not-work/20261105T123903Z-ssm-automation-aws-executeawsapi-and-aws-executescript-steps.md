# ssm Automation: aws:executeAwsApi and aws:executeScript steps are never run (execution ends Failed with emulator prose), and SendAutomationSignal answers 501 NotImplemented instead of its modelled refusals (3 causes)

> _Note: this issue was identified against the code base at commit `e924affd30ac1a5870106526f18d5e4efb90f778`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartAutomationExecution, GetAutomationExecution, SendAutomationSignal

## Description
Three net-new root causes in the SSM Automation surface. All three are in the `ssm` service. A fixer must close ALL THREE before submitting.

Cause 1 of 3: an Automation whose steps use `aws:executeAwsApi` never performs the API call, and the execution ends Failed.
AWS: `StartAutomationExecution` on an Active `DocumentType=Automation` runbook runs the runbook's `mainSteps` in the declared order; an `aws:executeAwsApi` step calls the named `Service`/`Api` in the account with the substituted inputs (document parameters `{{Param}}` and earlier step outputs `{{step.Output}}`), extracts each declared `outputs[].Selector` into the step's `Outputs`, and the step reaches `StepStatus=Success`. The execution then reaches `AutomationExecutionStatus=Success` (Smithy: GetAutomationExecution -> AutomationExecution; StartAutomationExecution models only AutomationDefinitionNotFoundException / AutomationDefinitionVersionNotFoundException / AutomationExecutionLimitExceededException / IdempotentParameterMismatch / InvalidAutomationExecutionParametersException / InvalidTarget — no "action not supported" outcome exists), document-level `outputs` are projected as `"<step>.<output>": [<value>]`, `ExecutionEndTime >= ExecutionStartTime`, `DescribeAutomationStepExecutions` lists every declared step with its `Action`, sequential times and `IsEnd` on the terminal step, and the step's real side effect lands (here a `ssm:PutParameter` creating the target parameter at `Version=1`, `Type=String`).
Emulator: the execution reaches `AutomationExecutionStatus='Failed'` with `FailureMessage` 'The aws:executeAwsApi action of step <stepName> runs where this emulator does not reach, so nothing ran for this step' (the step name is taken from the document; the rest is emulator-authored prose that AWS never emits). No API call is made, so no step output, no document-level output and no side effect exists.
Why: any client that drives work through Automation runbooks — the single most common way to script SSM, and the path CloudFormation/CDK runbooks use — sees every API-driven runbook fail, with a failure message no AWS error vocabulary contains, so retry/branching logic keyed on Success/Failed or on FailureMessage is driven down the wrong path and the runbook's effects never happen.
Fix: the Automation step-action executor reached from the `StartAutomationExecution` handler and the execution state it writes (services/service-com-amazonaws-ssm-amazonssm/src/ops/start_automation_execution.rs and `crate::state::automation`, read back by get_automation_execution.rs / describe_automation_step_executions.rs): `aws:executeAwsApi` must dispatch the named service API in-emulator, substitute parameters and prior step outputs, and record per-step Outputs and Success.
Traces: ssm.automation-execute-aws-api-reaches-success.

Cause 2 of 3: an `aws:executeScript` step never runs its script, so the execution ends Failed and nothing is computed.
AWS: an `aws:executeScript` step runs the supplied `Script` in the declared managed `Runtime` (here `python3.11`), calls the declared `Handler` with the substituted `InputPayload`, and the handler's return value is selected through `$.Payload.*` into the step's typed `outputs` (String / StringList / Integer), which are then projected into the execution's document-level `Outputs`; `platform.python_version()` observed inside that runtime begins with the declared minor version. The step and the execution reach Success and the following `aws:executeAwsApi` step consumes `{{compute.value}}`.
Emulator: the execution reaches `AutomationExecutionStatus='Failed'` with `FailureMessage` 'The aws:executeScript action of step <stepName> runs where this emulator does not reach, so nothing ran for this step' — again emulator-authored prose, with no step outputs, no projected document outputs and no downstream step.
Why: runbooks that compute a value in SSM's managed runtime (the standard way to do arithmetic, JSON shaping or polling inside Automation) cannot run at all, and the dependent steps that reference their outputs never execute.
Fix: same component as Cause 1 — the step-action executor must implement `aws:executeScript` (run the script in the declared runtime, apply `$.Payload` selectors with the declared output Types) rather than failing the execution.
Traces: ssm.ssm-automation-execute-script-computes-its-output-in-the-managed-runtime.

Cause 3 of 3: `SendAutomationSignal` answers HTTP 501 `NotImplemented` for every signal, so neither its modelled refusals nor Resume work.
AWS: `SendAutomationSignal` models exactly AutomationExecutionNotFoundException (400), AutomationStepNotFoundException (400), InvalidAutomationSignalException (400) and InternalServerError (500) — `NotImplemented` is not in its error set, and a well-formed signal on a Waiting execution returns 200 with an empty body. Against an unknown but well-formed execution id the refusal is `AutomationExecutionNotFoundException` with the fixed message "The input automation execution does not exist." (no variable parts). For `SignalType=Resume` naming a step the runbook does not define, the refusal is `AutomationStepNotFoundException` with the message "Failed to process signal Resume. Step <StepName> is not defined in document: <documentName> (version <documentVersion>)." — the fixed text is "Failed to process signal ", ". Step ", " is not defined in document: " and " (version " ... ").", while the signal type, the step name (from `Payload.StepName`), and the document name and version come from the request and from the execution's own state. In both refusals the execution is untouched (still `Waiting`) and no execution is fabricated for a bogus id; a subsequent Resume naming the real paused step is accepted and drives the execution to Success.
Emulator: every call returns HTTP 501 with error code `NotImplemented` (services/service-com-amazonaws-ssm-amazonssm/src/ops/send_automation_signal.rs is still a SCAFFOLDED stub: `Err(crate::scaffolded::Scaffolded::not_implemented("SendAutomationSignal"))`), so clients see neither the not-found nor the step-not-found classification, and a paused execution can never be resumed.
Why: a caller cannot distinguish a bad execution id from a bad step name from a server fault, and `aws:pause`/approval runbooks can never be resumed or approved — the execution sits Waiting forever.
Fix: implement the handler in services/service-com-amazonaws-ssm-amazonssm/src/ops/send_automation_signal.rs against the automation execution state, returning the modelled errors with AWS's wording and applying Resume/StartStep/Approve/Reject/StopStep to the stored execution. NOTE: a companion scaffold-stub issue for this same operation is filed automatically for the check ssm.send-automation-signal-invalid-state-rejected (which the report marks ALREADY FILED and which is skipped here); that issue only asks for the operation to exist, so the four checks listed below — the refusal codes, the exact refusal messages, the untouched-execution effect and Resume reaching Success — are what this cause adds and must be re-replayed.
Traces: ssm.send-automation-signal-nonexistent-execution-rejected, ssm.send-automation-signal-unknown-execution-rejected, ssm.send-automation-signal-invalid-step-rejected, ssm.send-automation-signal-unknown-step-rejected.
