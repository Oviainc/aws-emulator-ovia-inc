> _Note: this issue was identified against the code base at commit `f4f32d8dc5909c3913c2a89e0f1799d782bc5a16`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

=== Cause 1 of 1: the announced archived-media DataEndpoint cannot be dialled by a standard SDK client — its TLS identity is a self-signed certificate, so every call to it fails CERTIFICATE_VERIFY_FAILED before the request is sent ===

AWS: Smithy com.amazonaws.kinesisvideo#GetDataEndpoint, POST /getDataEndpoint -> 200; input APIName (required enum GET_CLIP | GET_DASH_STREAMING_SESSION_URL | GET_HLS_STREAMING_SESSION_URL | GET_IMAGES | GET_MEDIA | GET_MEDIA_FOR_FRAGMENT_LIST | LIST_FRAGMENTS | PUT_MEDIA) plus StreamName or StreamARN; output DataEndpoint, documented 'The endpoint value. To read data from the stream or to write data to it, specify this endpoint in your application'; operation doc 'Gets an endpoint for a specified stream for either reading or writing ... The returned endpoint does not have the API name appended. The client needs to add the API name to the returned endpoint.' The contract is OPERATIONAL: the client constructs a client with endpoint_url=DataEndpoint and the archived-media operations then succeed over it. Smithy com.amazonaws.kinesisvideoarchivedmedia#AWSAcuityReader (sdkId 'Kinesis Video Archived Media', restJson1, sigv4) binds POST /listFragments, /getClip, /getImages, /getMediaForFragmentList, /getHLSStreamingSessionURL, /getDASHStreamingSessionURL on that endpoint, with common errors ClientLimitExceededException, InvalidArgumentException, NotAuthorizedException, ResourceNotFoundException. On AWS the announced origin is https with a publicly trusted certificate, so an SDK client built on it completes the handshake with default verification enabled; a client never has to disable certificate verification to use a discovered DataEndpoint. Host, port and certificate issuer are per-environment and are not themselves requirements — the requirement is that the announced origin, as announced (scheme included), is one a default-configured SDK client can connect to and that serves that plane's operations. For an emulator that means the announced scheme and TLS identity must match what the run's clients already validate successfully against the control-plane endpoint of the same emulator.

Emulator: GetDataEndpoint now opens a core listener per plane and announces it as `https://<listener authority>` — services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs:159-208, `ensure_data_endpoint` calling `shared_engine(engine).listeners().http(DataPlaneFrontDoor{..}, HttpPolicy::default())` and then `format!("https://{}", ::service_common::data_plane_addressing::listener_authority(&listener))` at :188-191. The address is reachable (loopback, same machine) and the socket does complete a TLS handshake, but the certificate it presents is self-signed and chains to no anchor the client trusts, while the SAME run's control-plane client reaches the emulator without any verification failure. Every archived-media call over the discovered endpoint therefore dies in the handshake: `botocore.exceptions.SSLError: SSL validation failed for https://127.0.0.1:<port>/listFragments [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate (_ssl.c:1010)` — identically for /getClip, /getImages, /getMediaForFragmentList, /getHLSStreamingSessionURL and /getDASHStreamingSessionURL (the 127.0.0.1 host and the ephemeral port differ per run and are not the divergence; the unverifiable https identity on the announced origin is). Note that the control-plane leg succeeds in every check — CreateStream, DescribeStream polling to ACTIVE, UpdateDataRetention and GetDataEndpoint all answer normally — so the emulator is up and only the endpoint it announces for itself is unusable. Hypothesis (not stated by the model or the recording): the per-plane `ResourceListener` opened here gets a default TLS identity that is not the one the run's clients were given for the primary front door, and/or the plane is announced as `https://` while the authority it opened is reached over plain HTTP for the control plane; either way the announcement and the served identity disagree.

Why: endpoint discovery is the only documented way to find the Kinesis Video archived-media plane, so a client that follows it is dead in the water. A boto3/botocore client (`boto3.client('kinesis-video-archived-media', endpoint_url=get_data_endpoint(...)['DataEndpoint'])`), the KVS Java/C++ consumer SDKs, HLS/DASH players handed the session URL, and any tool that honours the returned endpoint all fail at connect time with a certificate error and never send a request. Consequences: ListFragments, GetClip, GetImages, GetMediaForFragmentList and the HLS/DASH session URL operations are entirely unavailable; none of their success shapes (empty Fragments list on an ingest-free ACTIVE stream, StreamName/StreamARN addressing equivalence, WidthPixels/HeightPixels acceptance) and none of their refusal contracts (NoDataRetentionException 'The stream data retention is set to 0 hours.', ResourceNotFoundException 'No fragments found in the stream for the GetImages request.' / '... for the clip request.', reversed-range and >300s window refusals, mutual exclusivity of StreamName/StreamARN, NotAuthorizedException) can be observed or relied on; and the failure mode a client sees is a TLS error rather than any AWS error, so it has no way to tell a configuration problem from a service problem. Workarounds all require a client to disable certificate verification, which no AWS client does by default and which is not something an emulator may demand.

Fix: the data-plane endpoint publication in the kinesisvideo service crate — `ensure_data_endpoint` / `DataPlaneEndpoint` / `DataPlaneFrontDoor` in services/service-com-amazonaws-kinesisvideo-kinesisvideo-20170930/src/state/data_endpoint.rs (listener opened at :178-187, scheme composed at :188-191, module header's addressing contract at :29-53), together with the core listener/TLS facility it borrows (`::emulator_server::Listeners::http`, `HttpPolicy`, `::service_common::data_plane_addressing::listener_authority`). The announced origin must carry the scheme and TLS identity the listener actually serves verifiably — the same certificate/trust anchor the emulator's primary front door presents to the run's clients, or plain `http://` if that is what the plane serves — so that a default-configured SDK client connects without disabling verification, while keeping what is already right: a bare origin with an empty path, per-plane distinct, distinct from the control-plane address, stable for the life of the store, with the archived-media routes bound on it. Keep the per-plane listener; change only the scheme/credential agreement.
