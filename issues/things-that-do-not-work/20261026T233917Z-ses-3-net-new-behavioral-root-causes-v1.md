# ses: 3 net-new behavioral root causes — v1 ListConfigurationSets cannot see SESv2-created configuration sets, legacy VerifyEmailAddress marks an address verified instantly, and DeleteReceiptRuleSet never enforces the active-rule-set guard

> _Note: this issue was identified against the code base at commit `4bb3c01901698ef95426c2799d1398daad63aada`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListConfigurationSets

## Description
Three net-new behavioral root causes in the SES v1 surface. None of the three is one of the clusters the replay report marked ALREADY FILED or OWNED; each is named below with the open issue it is adjacent to, because none of those issues carries these checks' replay keys or these contracts.

Cause 1 of 3: configuration sets created through SESv2 are invisible to the SES v1 API — the two surfaces do not share one configuration-set store.
AWS: SES v1 and SESv2 are two APIs over ONE set of per-account, per-Region configuration sets. Smithy (com.amazonaws.sesv2#SimpleEmailService_v2): CreateConfigurationSet creates a set by name; Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery): ListConfigurationSets input {MaxItems, NextToken} / output {ConfigurationSets: list<ConfigurationSet{Name}>, NextToken}, documented as "Provides a list of the configuration sets associated with your Amazon SES account in the current Amazon Web Services Region", returning up to 1,000 per call plus a NextToken for the rest. A v1 page-walk at MaxItems=1 therefore visits EVERY set of the account exactly once — including the ones created through v2 — and the NextToken a v1 page hands back continues the same paged collection when it is passed to the v2 ListConfigurationSets.
Emulator: after three sesv2 CreateConfigurationSet calls that each answered 200, an exhaustive v1 ListConfigurationSets page-walk at MaxItems=1 never returns any of them: "AssertionError: v1 paginated walk dropped configuration sets that exist: ['sim2real-behav-cfgset0-...', 'sim2real-behav-cfgset1-...', 'sim2real-behav-cfgset2-...']" (the walk terminates with no NextToken, so the v1 listing is simply empty for this account). The two crates keep independent stores: the v1 handler pages over `state.configuration_sets` of the ses v1 crate's own state, while the v2 create writes its `ConfigurationSetRecord` into the sesv2 crate's state. Because the v1 list is empty, the cross-API leg (a v1 NextToken continuing a v2 page) is unreachable too.
Why: a client that creates configuration sets with the modern API and then reads, pages, or names them on a v1 operation sees an account that holds no configuration sets at all; migration code that straddles the two API versions, and any cursor handed from one version to the other, silently walks an empty collection instead of the account's real one.
Fix: the configuration-set state shared by the two crates — the sesv2 CreateConfigurationSet handler must write into the same per-account/per-Region configuration-set store that the ses v1 ListConfigurationSets / DescribeConfigurationSet handlers read (one store, with each version's projection applied on read), rather than a per-crate store; the v1 page cursor must then be a cursor over that one store so it stays valid across both versions.

Cause 2 of 3: the deprecated VerifyEmailAddress reports the address verified immediately, so the Pending state never exists and the ListVerifiedEmailAddresses filter is never exercised.
AWS: VerifyEmailAddress only REQUESTS verification — Smithy: input {EmailAddress: Address, required}, output empty (no status member at all), documented "Deprecated. Use the VerifyEmailIdentity operation to verify a new email address." The address stays unverified until its confirmation link is clicked, so GetIdentityVerificationAttributes (output VerificationAttributes -> IdentityVerificationAttributes{VerificationStatus required; enum values Pending, Success, Failed, TemporaryFailure, NotStarted}) reports "Pending" for a freshly requested address, and ListVerifiedEmailAddresses (output {VerifiedEmailAddresses: AddressList}) returns ONLY verified addresses — so a Pending address shows in ListIdentities but is absent from ListVerifiedEmailAddresses.
Emulator: GetIdentityVerificationAttributes called immediately after VerifyEmailAddress on a brand-new address, with no confirmation click possible, answers VerificationStatus 'Success' — "AssertionError: expected Pending for a freshly verified email, got 'Success'". Because nothing is ever Pending on this path, ListVerifiedEmailAddresses degenerates into a copy of the email-address identity list and its documented filter is vacuous.
Why: the legacy verification state machine has no Pending state, so a client that polls for verification to complete sees it complete before the identity could possibly have been confirmed, and the one thing ListVerifiedEmailAddresses exists for — telling verified addresses apart from requested ones — returns the wrong set. Every downstream unverified-source refusal on an address verified through this deprecated spelling disappears as well.
Fix: the VerifyEmailAddress handler and the identity record it writes in the ses v1 crate — the identity must be persisted with VerificationStatus=Pending (the same record the non-deprecated spelling writes), and ListVerifiedEmailAddresses must project only identities whose stored status is Success.

Cause 3 of 3: DeleteReceiptRuleSet does not implement the active-rule-set guard — it answers NotImplemented where AWS refuses CannotDelete.
AWS: Smithy: DeleteReceiptRuleSet input {RuleSetName: ReceiptRuleSetName, required} / output empty, with exactly one modelled error — CannotDeleteException, client error, awsQueryError code "CannotDelete", httpError 400, documented "Indicates that the delete operation could not be completed." Deleting the CURRENTLY ACTIVE receipt rule set is that refusal: HTTP 400, Error.Code "CannotDelete", and the message names the rule set from the request (fixed text plus the RuleSetName value), and the rule set is left in place and still returned by ListReceiptRuleSets. Once the set is no longer active the same delete succeeds; afterwards DescribeReceiptRuleSet and SetActiveReceiptRuleSet naming it are refused RuleSetDoesNotExistException (awsQueryError code "RuleSetDoesNotExist", httpError 400) with message "Rule set does not exist: <RuleSetName>" — fixed text "Rule set does not exist: " followed by the name taken verbatim from the request.
Emulator: with the rule set created and made active (both of those calls succeeded), DeleteReceiptRuleSet on it answers Error.Code 'NotImplemented' — "AssertionError: expected CannotDelete deleting the active rule set 'sim2real-ses-rrs-...', got 'NotImplemented'" — a code no SES model defines, so neither the refusal nor the positive-control delete nor the post-delete not-found reads can happen.
Why: a client cannot delete a receipt rule set at all, and the one protection on this operation — that the active rule set cannot be removed out from under inbound mail — is unobservable; code that handles CannotDelete by deactivating and retrying instead sees an unmodelled error class it cannot classify.
Fix: the DeleteReceiptRuleSet handler and the receipt-rule-set state it reads in the ses v1 crate — compare the named rule set against the stored active rule set and refuse with CannotDelete (400) naming it, leaving the store untouched; otherwise remove it so the subsequent DescribeReceiptRuleSet/SetActiveReceiptRuleSet answer RuleSetDoesNotExist with the message above.
Traces: ses.receipt-rule-set-delete-while-active-rejected. File/line citation: services/service-com-amazonaws-ses-simpleemailservice/src/ops/delete_receipt_rule_set.rs. Adjacent open issue: the ses DeleteReceiptRuleSet unimplemented-scaffold-stub issue the report filed for ses.delete-active-receipt-rule-set-fails covers only that the operation is unimplemented; it carries neither this check's replay key nor the CannotDelete / RuleSetDoesNotExist contract, so an implementation without the active-set guard still leaves this check failing.
