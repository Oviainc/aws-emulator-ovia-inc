# codestar-connections: every operation answers 501 NotImplemented, so no connection/tag/repository-link behavior is reachable (plus missing CreateConnection validation)

> _Note: this issue was identified against the code base at commit `048778663a26e363156c6db724999c4fb229af36`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateConnection

## Description
Replaying the behavioral suite against the emulator, the CodeStar Connections service passes 0/45 checks. Every check fails on its FIRST call to the service with HTTP 501 / error code `NotImplemented` (message example: `operation amazonaws.codestar.connections.CodeStar_connections_20191201.CreateConnection is not implemented in this emulator`), even for operations whose handler files in this checkout contain complete implementations. One cluster (the 12 checks blocked by the genuinely-unwritten `CreateHost`) is already filed and is NOT part of this issue.

This issue bundles 4 root causes for this one service.

=== Cause 1 of 4: CreateConnection answers 501 NotImplemented although its handler is implemented ===
AWS: CreateConnection is a modeled operation of this service (Smithy: CreateConnection input ConnectionName @required @length 1..32, optional ProviderType enum [Bitbucket|GitHub|GitHubEnterpriseServer|GitLab|GitLabSelfManaged], optional HostArn @pattern ^arn:aws(-[\w]+)*:codestar-connections:.+:[0-9]{12}:host\/.+$, optional Tags @length 0..200; output ConnectionArn @required @pattern ^arn:aws(-[\w]+)*:.+:.+:[0-9]{12}:.+$ plus Tags; modeled errors LimitExceededException 429, ResourceNotFoundException 404, ResourceUnavailableException 400 — there is no `NotImplemented` in the model). A successful call returns 200 with a freshly minted ConnectionArn; per the modeled docs the connection "is in pending status until the third-party connection handshake is completed from the console", so GetConnection must then report ConnectionStatus PENDING, ConnectionName/ProviderType as supplied, tags supplied at creation must round-trip, and ConnectionName is not a unique key (two connections may share a name and get distinct ARNs).
Emulator: every CreateConnection call returns HTTP 501 with error code `NotImplemented`. This is NOT a missing handler: services/service-com-amazonaws-codestarconnections-codestar-connections-20191201/src/ops/create_connection.rs is fully implemented (it mints a connection id/ARN, enforces MAX_CONNECTIONS -> LimitExceededException, stores CONNECTION_STATUS_PENDING, merges tags and returns them). The 501 wording also does not match this crate's own scaffold text (`src/scaffolded.rs` formats "... is scaffolded but not implemented in this emulator") and the operation is named by its wire target rather than its shape id. Hypothesis: the request is never dispatched to the implemented handler — the service's operation routing/mounting layer resolves the target to a not-implemented response instead of to `ops::create_connection::CreateConnection::handle`.
Why: the entire service is unusable for a client. Nothing can be created, so every downstream surface (GetConnection, ListConnections and its ProviderTypeFilter/pagination, DeleteConnection, TagResource/UntagResource/ListTagsForResource, repository links, sync configurations, sync status, sync blockers) is unreachable; an SDK client sees 501 NotImplemented — which SDK retry classifiers do not retry — where AWS returns 200 and a usable ConnectionArn.
Fix: the service's operation dispatch/mounting for this crate (the generated ServiceDefinition routing table consumed by src/service.rs / src/ops/mod.rs), not the operation handler body — the handler already exists.

=== Cause 2 of 4: TagResource answers 501 NotImplemented although its handler is implemented ===
AWS: Smithy: TagResource input ResourceArn @required @length 1..1011 @pattern ^arn:aws(-[\w]+)*:.+:.+:[0-9]{12}:.+$, Tags @required @length 0..200; modeled errors LimitExceededException 429 and ResourceNotFoundException 404 ("Resource not found. Verify the connection resource ARN and try again."). Tagging an ARN that names no resource in the caller's account is refused with HTTP 404 `ResourceNotFoundException`; a successful call returns 200 with an empty body.
Emulator: TagResource returns HTTP 501 with error code `NotImplemented` even for a syntactically valid ARN that names nothing — the check asserting ResourceNotFoundException got `{'Code': 'NotImplemented'}`. Again the handler exists and already implements exactly this rule: src/ops/tag_resource.rs returns ResourceNotFoundException when the ARN is absent from `store.connections`, and LimitExceededException past MAX_TAGS_PER_RESOURCE. Hypothesis: same dispatch gap as Cause 1 — the implemented handler is never invoked.
Why: a client cannot tag anything, and cannot distinguish "no such resource" (404, a caller error it must fix) from a 501 that claims the operation does not exist at all.
Fix: same dispatch/mounting layer; verify TagResource (and the other implemented tag operations) reach `ops::tag_resource`.
Traces: codestar-connections.tag-resource-nonexistent-arn-rejected (reaches TagResource directly with a fabricated ARN, so it is independent of Cause 1).

=== Cause 3 of 4: CreateConnection does not refuse a request that supplies neither ProviderType nor HostArn ===
AWS: ProviderType and HostArn are both optional in the model, but exactly one must effectively be supplied — a connection is either direct (ProviderType) or host-backed (HostArn). Recorded behavior only: the replayed check asserts error code `ValidationException` (HTTP 400) for CreateConnection with ConnectionName only; the model declares no ValidationException for this operation, so the refusal must be rendered as a 400 `ValidationException` naming the missing/conflicting members (the scaffold provides `Scaffolded::validation` for exactly this case).
Emulator: the call is answered with 501 `NotImplemented` today; and once dispatch is fixed it would be ACCEPTED, because create_connection.rs performs no ProviderType/HostArn presence check — it stores `provider_type: input.provider_type` (None) and returns a 200 with an ARN. That is over-permissive: a connection with neither provider nor host becomes addressable.
Why: a client that relies on AWS refusing a malformed CreateConnection instead gets a 501 (today) or a bogus successful connection (after Cause 1 is fixed), and GetConnection then reports a connection with no ProviderType at all.
Fix: input validation in the CreateConnection handler (src/ops/create_connection.rs), before any state mutation.
Traces: codestar-connections.create-connection-without-provider-type-or-host.

=== Cause 4 of 4: HostArn naming a host outside the caller's account is not authorization-checked by CreateConnection/ListConnections ===
AWS: Recorded behavior only (the model lists no AccessDeniedException for these operations): the replayed check asserts HTTP error code `AccessDeniedException` for both CreateConnection with a HostArn whose account differs from the caller's and ListConnections with that same ARN as HostArnFilter, with a message built from the request — "Account <caller-account> does not have access to host <host-arn>" — i.e. the cross-account authorization check runs BEFORE any resource-existence lookup, and no connection may be created. (A HostArn for a nonexistent host in the caller's OWN account is ResourceNotFoundException 404 instead; Smithy: ListConnections errors = ResourceNotFoundException 404, CreateConnection errors = LimitExceededException 429 / ResourceNotFoundException 404 / ResourceUnavailableException 400.)
Emulator: both calls return 501 `NotImplemented` today; create_connection.rs stores `host_arn: input.host_arn` with no ownership or existence check and ListConnections applies the filter without one, so after Cause 1 is fixed CreateConnection would succeed with a foreign-account HostArn.
Why: a client's authorization boundary disappears — a connection can be attached to a host in another account, and a client branching on AccessDeniedException vs ResourceNotFoundException cannot tell the two apart.
Fix: HostArn account/existence validation in the CreateConnection handler and in the ListConnections HostArnFilter path (src/ops/create_connection.rs, src/ops/list_connections.rs), using the emulator account id already available via `engine::emulator_account_id()`.
Traces: codestar-connections.create-connection-nonexistent-host-arn-rejected.
