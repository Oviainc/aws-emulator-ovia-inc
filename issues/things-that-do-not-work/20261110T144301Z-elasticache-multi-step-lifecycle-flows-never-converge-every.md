# ElastiCache multi-step lifecycle flows never converge: every status wait costs a client a full poll interval because a settled resource is only materialised on a later read (4 checks time out)

> _Note: this issue was identified against the code base at commit `8ffd4f499c6d6f6b1d86ee4455070f9416ebee70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCacheClusters

## Description
One root cause (Cause 1 of 1), grounded in four failing checks that all end with the identical detail "Check timed out after 60.0s" and all die inside a status poll rather than on an assertion.

Cause 1 of 1: a resource ElastiCache has finished provisioning is not reported settled to the first client poll, so every wait in a multi-step flow costs the client its whole poll interval and flows with several waits never finish.
AWS: Smithy/recorded behavior per surface in these four flows. (a) Snapshot$SnapshotStatus is documented "creating | available | restoring | copying | deleting"; recorded: CreateSnapshot of a single-node redis cluster reports creating then available with exactly one NodeSnapshot, CopySnapshot yields an independent snapshot that reaches available and records the SOURCE CacheClusterId, DeleteSnapshot of the source leaves the copy available, and DeleteCacheCluster removes the cluster (DescribeCacheClusters then 404 CacheClusterNotFound). (b) ServerlessCache$Status is documented "CREATING, AVAILABLE, DELETING, CREATE-FAILED and MODIFYING" while the recorded wire values are lower case (creating -> available); ModifyServerlessCache models InvalidParameterValueException (awsQueryError InvalidParameterValue, 400) and leaves a refused change with no effect, and a legal widening of CacheUsageLimits applies on a cache that stays available. (c) GlobalReplicationGroup$Status settles at primary-only for a datastore with only its primary; DisassociateGlobalReplicationGroup refuses the primary with 400 InvalidParameterValue and the fixed message "Cannot disassociate primary replication group. Primary Replication Group will be disassociated when you delete the Global Replication Group.", the primary stays a member, and after DeleteGlobalReplicationGroup(RetainPrimaryReplicationGroup=True) the primary's GlobalReplicationGroupInfo clears and the primary can itself be deleted. (d) ModifyUserGroup moves a group to modifying and back to active with the membership change applied, and ModifyReplicationGroup(UserGroupIdsToAdd=...) returns the group to available with the new UserGroupIds.
Emulator: none of the four flows reaches its first divergence or its end — each is killed by the suite's 60 s per-check budget inside a poll loop, with no assertion ever failing: snapshot-of-a-single-node-cluster-copies-and-deletes has six sequential waits (cluster available, snapshot available, copy available, source snapshot gone, copy gone, cluster gone) at interval_s=15; serverless-cache-usage-limits-inverted-rejected waits for Status available, then for the widened limits, then for the delete to disappear at interval_s=15; global-replication-group-topology-lifecycle waits for replication-group available (interval 15), global datastore available|primary-only twice (interval 20), the primary's GlobalReplicationGroupInfo to clear (interval 10) and the primary's deletion (interval 10); e2e-user-group-access-revocation-flow waits for replication-group available (interval 20), the user-group attach (interval 20) and then four more group/replication-group waits (interval 15). Hypothesis for the mechanism: the emulator deliberately keeps a just-created/just-changed resource in its transient status for a fixed non-zero span and only materialises the settled status when a LATER call reads the record (CLUSTER_TRANSITION / SNAPSHOT_TRANSITION = Duration::from_millis(500), see Traces for the file and lines). A client's first poll lands inside that span, so it always observes the transient value and then sleeps a full 10-20 s interval before the next probe; four to six such waits exhaust the budget even though the emulator itself settled in half a second. The alternative, that one specific status is never reached at all, is not distinguishable from the replay output, because no assertion in these checks fired. e2e-user-group-access-revocation-flow additionally drives an in-VPC RESP probe whose runtime is the subject of open issues 20261110T001859Z-elasticache-in-vpc-data-plane-still-unverifiable-the.md and 20261105T090541Z-elasticache-every-in-vpc-data-plane-check-is.md; those issues do not carry this check id, and this check never reaches its first ping, so it is clustered here.
Why: a client written against AWS polls a lifecycle status on an interval sized for AWS (tens of seconds). Against this emulator every such wait costs the client that whole interval instead of returning immediately, so any flow that chains several waits — snapshot then copy then two deletes, create-then-modify-then-delete of a serverless cache, the Global datastore topology sequence, a user-group revocation round trip — takes minutes of wall clock and is indistinguishable from a resource that never settles. SDK waiters and CI flows time out, and a client cannot tell "still provisioning" from "stuck".
Fix: the status-settling path of the elasticache crate's state — make a resource whose transition is already due read back settled to the FIRST call that observes it (or shrink the transient span so a client's next request sees the settled value), keeping the create/modify/delete RESPONSE reporting the transient status that other checks assert. The four flows above then converge in the handlers that project CacheCluster, Snapshot, ServerlessCache, GlobalReplicationGroup, UserGroup and ReplicationGroup status.
