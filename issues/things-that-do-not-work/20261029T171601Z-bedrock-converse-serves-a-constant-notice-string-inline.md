# bedrock: Converse serves a constant notice string, inline and account-enforced guardrails are never applied, a nonexistent guardrailVersion is accepted, invocation logging delivers no records, and CreateEvaluationJob admits a same-account pass role

> _Note: this issue was identified against the code base at commit `d7c92a359e65b119da339df847b0735e9ef403e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Converse

## Description
This issue bundles 6 DISTINCT root causes found by the behavioral suite under the `bedrock` service token. A fixer must close ALL SIX before submitting; each cause below names its own failing check ids. Models consulted: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/smithy-model/com-amazonaws-bedrock-amazonbedrockcontrolplaneservice.json and services/service-com-amazonaws-bedrockruntime-amazonbedrockfrontendservice/smithy-model/com-amazonaws-bedrockruntime-amazonbedrockfrontendservice.json. The emulator answered every one of these calls (200/202 responses were returned), so the services are up and answering wrongly, not unbootstrapped.

---
Cause 1 of 6: the generation stage returns one constant notice string for every prompt, so no answer is ever responsive to its own request — under 8-way concurrency all 8 calls get the same bytes and no answer can be correlated with its request.
AWS: Smithy Converse -> ConverseResponse with `output` (ConverseOutput), `stopReason` (StopReason enum) and `usage` (TokenUsage) all @required; generated text is not described by the model, so recorded behavior only: Converse on amazon.nova-lite-v1:0 with the prompt "Reply with exactly this token and nothing else, no punctuation and no commentary: <nonce>" returns an assistant text block containing that request's own nonce, and each of N concurrent calls returns ITS OWN nonce (the nonce is a per-request value, never a literal).
Emulator: every call returns HTTP 200, stopReason='end_turn' and the single text block 'No language model runs in this emulator.' (in other handlers extended with '<modelId> generated no text for this request. The request carried N message(s) and M input token(s).'). All 8 concurrent calls returned that identical string, so request/response correlation is unobservable.
Why: a client that reads the completion (echo/extraction/agent loops, and any correlation or isolation test under concurrency) cannot be exercised at all; the emulator cannot distinguish a correctly routed response from a cross-contaminated one.
Fix: the generation stage behind Converse/ConverseStream/InvokeModel in the bedrock-runtime frontend — it must produce prompt-derived text and return it to the request it belongs to. NOTE: the open issue 20261028T194707Z-bedrock-runtime-generation-stage-serves-a-constant-emulator.md describes this same defect for `bedrock-runtime` check ids but does NOT carry this check's replay key; this cause exists to add that key, not to describe a second defect.
Traces: bedrock.bedrock-concurrent-converse-calls-do-not-cross-contaminate-responses.

---
Cause 2 of 6: a guardrailConfig naming a guardrail version that does not exist is accepted and the inference is served unguarded, instead of being refused.
AWS: Smithy GuardrailConfiguration.guardrailVersion -> GuardrailVersion @pattern ^(|([1-9][0-9]{0,7})|(DRAFT))$, so a numeric version string such as '99' is SYNTACTICALLY valid and the refusal is a resolution failure, not a shape failure; Converse models ValidationException (errorKind client, httpError 400). Recorded behavior for the exact text: HTTP 400, Error.Code='ValidationException', Error.Message='The guardrail identifier or version provided in the request does not exist.' — the whole message is fixed text for this error class (it names no request value). Scoping controls in the same recording: guardrailVersion='DRAFT' and the account's actually published version are both ACCEPTED, and the refusal leaves the guardrail and its published version untouched (GetGuardrail status stays READY, no new version appears).
Emulator: the call SUCCEEDS with HTTP 200, stopReason='end_turn', usage={'inputTokens':13,'outputTokens':11,'totalTokens':24} and the Cause-1 notice text. No ValidationException is raised and the unresolvable guardrail is simply ignored.
Why: a caller that mis-pins a guardrail version (a stale/templated version number is the common case) is served an UNGUARDED completion here and a hard 400 in production — the emulator both hides the configuration error and silently drops the safety control the caller asked for.
Fix: guardrail resolution in the Converse/ConverseStream/InvokeModel handlers (and the guardrail-version lookup in the bedrock control plane store they resolve against) — resolve guardrailIdentifier+guardrailVersion BEFORE the inference stage and answer the 400 ValidationException above when it does not resolve.
Traces: bedrock.bedrock-converse-with-a-nonexistent-guardrail-version-rejected.

Cause 3 of 6: an inline guardrail whose topic policy DENYs the prompt does not intervene — the request is served as a normal completion.
AWS: Smithy StopReason enum includes `guardrail_intervened`. Recorded behavior: Converse with guardrailConfig naming a READY guardrail that carries a topicPolicyConfig DENY topic, and an on-topic prompt, returns HTTP 200 with stopReason='guardrail_intervened' and a single text block equal to the guardrail's configured `blockedInputMessaging` (that string is a value taken from the guardrail the request references, not a literal); the model is never invoked. The off-topic control prompt through the same guardrail returns stopReason='end_turn'.
Emulator: stopReason='end_turn' and the Cause-1 notice text ('No language model runs in this emulator. amazon.nova-lite-v1:0 generated no text for this request. The request carried 1 message(s) and 15 input token(s).'). `guardrail_intervened` is never produced and blockedInputMessaging is never served.
Why: this is a safety control that reports success and does nothing. A client built against the emulator cannot see or handle an intervention (no stopReason branch, no blocked-message surfacing), and a guardrail regression in that client is invisible until production.
Fix: the guardrail evaluation stage of the Converse/ConverseStream/InvokeModel handlers — evaluate the resolved guardrail's policies against the input before generation, short-circuit with stopReason='guardrail_intervened' and the guardrail's blockedInputMessaging, and apply the output policies to generated text with blockedOutputsMessaging.
Traces: bedrock.bedrock-guardrail-blocked-input-never-reaches-the-model.

Cause 4 of 6: model invocation logging stores its configuration but never delivers a single record — nothing is ever written to the configured S3 target.
AWS: Smithy PutModelInvocationLoggingConfiguration PUT /logging/modelinvocations -> 200, GetModelInvocationLoggingConfiguration GET -> 200 with `loggingConfig` (LoggingConfig). Delivery itself is not modeled, so recorded behavior only: with loggingConfig.s3Config={bucketName,keyPrefix} and textDataDeliveryEnabled=true, every inference writes a JSON-lines record under that prefix in that bucket, and the record carries `modelId` (the model invoked), `operation` ('Converse' for a Converse call), input.inputBodyJson (the request body verbatim, so the prompt text appears in it), output.outputBodyJson (the completion the API returned on that same call), input.inputTokenCount and output.outputTokenCount equal to the `usage` the API returned inline. All of those are per-request values, not literals.
Emulator: Get echoes the stored configuration correctly (those assertions passed — bucketName and textDataDeliveryEnabled are returned), but no object ever appears under the configured prefix: the check's bounded poll over ListObjectsV2/GetObject never finds a record and the check is killed at the suite's 60s budget ('Check timed out after 60.0s'), so its own assertion message is never reached. The divergence is the absent delivery, not the timeout.
Why: an emulator that stores the configuration and delivers nothing makes 'logging is enabled' and 'logging works' indistinguishable; every downstream observability consumer (log readers, token-accounting and audit pipelines) is untestable, and a caller cannot verify that the prompt/completion it will be billed and audited for is the one that ran.
Fix: an invocation-logging delivery path — a post-inference hook in the bedrock-runtime inference handlers that emits the record, plus the bedrock control plane's logging component that resolves the stored s3Config/keyPrefix and writes the JSON-lines object (and honours the textDataDeliveryEnabled/imageDataDeliveryEnabled/embeddingDataDeliveryEnabled switches).
Traces: bedrock.bedrock-model-invocation-logging-records-the-prompt-and-the-completion.

Cause 5 of 6: the account-enforced guardrail configuration is stored but never applied to inference, so enforcement can neither be observed nor lifted.
AWS: recorded behavior only (PutEnforcedGuardrailConfiguration returns a `configId`). While an enforced configuration naming a READY guardrail version is in effect, an InvokeModel/Converse call that references NO guardrail is intervened on account-wide and the returned text is the enforced guardrail's configured blockedOutputsMessaging (a value from the guardrail, not a literal); after DeleteEnforcedGuardrailConfiguration(configId) the byte-identical call returns a normal non-empty completion without that marker.
Emulator: Put returns a configId and the guardrail reaches READY, but the subsequent Converse calls keep returning an ordinary completion with no intervention — the check polls the identical call for 90s waiting for the blocked marker and is killed at the suite's 60s budget ('Check timed out after 60.0s'). Enforcement never takes effect, so the 'blocks' half never happens and the 'lifts' half cannot be reached.
Why: an account-wide safety control that is accepted and ignored is the worst failure mode for this feature: operators testing a blast-radius control against the emulator see it stored and conclude it is in force.
Fix: the enforced-guardrail store must be consulted by the bedrock-runtime inference path on every call (no guardrailConfig required in the request), and removing the configuration must lift the intervention. NOTE: the open issue 20261024T175106Z-bedrock-the-account-enforced-guardrail-configuration-is-stored.md reports this same defect but carries only the replay key of bedrock.put-enforced-guardrail-configuration-applies-to-invoke; this cause adds the end-to-end check's key (blocks-then-lifts), which also covers the delete/lift half.
Traces: bedrock.e2e-enforced-guardrail-blocks-then-lifts.

Cause 6 of 6: CreateEvaluationJob accepts a passed same-account IAM role that AWS refuses, so the operation's pass-role gate does not exist.
AWS: Smithy CreateEvaluationJob POST /evaluation-jobs -> 202 with required `jobArn`; modeled errors include AccessDeniedException (errorKind client, httpError 403). Recorded behavior: CreateEvaluationJob naming a same-account IAM role (trusted for bedrock.amazonaws.com, granted s3 + bedrock:InvokeModel) with a real ACTIVE on-demand model is deterministically refused with HTTP 403, Error.Code='AccessDeniedException' and a message whose fixed text is the cross-account-pass-role refusal ('Cross-account pass role is not allowed'); the refusal leaves no job behind (ListEvaluationJobs(nameContains=<jobName>) returns an empty jobSummaries, where <jobName> is the request's own value). The positive control in the same recording — Converse on the same model with the same credentials — succeeds, so this is an operation-specific refusal and not an account/connectivity condition.
Emulator: the call SUCCEEDS with HTTP 202 and returns a jobArn (arn:aws:bedrock:<region>:<account>:evaluation-job/<12-char id>), i.e. the role is passed with no authorization decision at all. (The minted id/ARN itself matches the modeled pattern and is NOT the defect.)
Why: the real refusal is what makes StopEvaluationJob's terminal-state behaviour unreachable in this account, so a client that gets a job id from the emulator is testing a path AWS never permits; more generally no iam:PassRole decision is made on this operation, so a caller cannot discover a mis-trusted role until production.
Fix: the CreateEvaluationJob handler's authorization/pass-role stage in the bedrock control plane — evaluate the passed roleArn before minting a job and answer 403 AccessDeniedException with the cross-account-pass-role message, creating nothing. The open issue 20261027T212745Z-bedrock-createmodelcustomizationjob-the-iam-passrole-gate-admits-a.md reports the same gap on the DIFFERENT operation CreateModelCustomizationJob; this cause is CreateEvaluationJob and is not covered by it.
Traces: bedrock.stop-evaluation-job-terminal-state-rejected.
