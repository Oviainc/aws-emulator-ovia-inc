# Redshift parameter-group validation and the parameter catalog diverge in code, wording, content and acceptance

> _Note: this issue was identified against the code base at commit `5e177a4f4d28f6dc4714f734dc35ed5ad192c177`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyClusterParameterGroup

## Description
Ten net-new root causes in the redshift service, all in the cluster-parameter-group family: the refusal codes and messages are emulator-authored rather than AWS's query-protocol ones, two valid modifies are refused, one invalid modify is accepted, and the parameter catalog the emulator serves from DescribeClusterParameters does not match AWS's (missing user-modified parameters; wrong Description and ApplyType). Each cause is a separate site and must be closed separately. Open issues 20261029T200555Z-redshift-request-validation-answers-a-generic-validationexception-or.md and 20261102T105531Z-redshift-refusal-codes-and-messages-are-emulator-authored.md describe neighbouring parameter-group families; neither carries the replay keys below.

Cause 1 of 10: a structurally invalid CreateClusterParameterGroup request is refused with the wrong code. AWS: a request whose required members are missing or unparsable is refused HTTP 400 with the query-protocol code ValidationError. Smithy: CreateClusterParameterGroup requires ParameterGroupName, ParameterGroupFamily and Description, and models only ClusterParameterGroupAlreadyExistsFault / ClusterParameterGroupQuotaExceededFault / InvalidTagFault / TagLimitExceededFault, so the structural refusal is the protocol-level ValidationError (recorded behavior; the fixture asserts the code only, not the message). Emulator: HTTP 400 with code MalformedInput, which is not in Redshift's query-protocol error vocabulary. Why: SDK error handling keyed on ValidationError (the code every AWS query service emits for a structurally invalid request) does not match, so the client surfaces an unknown-error path instead of a validation failure. Fix: the redshift query-protocol request deserializer's structural-refusal code. Traces: redshift-rshealth-parameter-group-value-mistakes#task#2.

Cause 2 of 10: an invalid ParameterGroupName is refused with the wrong code and emulator-authored text. AWS: a ParameterGroupName violating the identifier grammar is refused HTTP 400 with code InvalidParameterValue and the fixed message "The parameter DBParameterGroupName is not a valid identifier. Identifiers must begin with a letter; must contain only ASCII letters, digits, and hyphens; and must not end with a hyphen or contain two consecutive hyphens." — entirely fixed text (AWS names the parameter DBParameterGroupName, from the shared RDS-family validator) and the offending value is NOT echoed. Smithy: ParameterGroupName is an unconstrained String, so the grammar is a service rule (recorded behavior). Emulator: code ValidationException and a long self-authored message that echoes the supplied name and restates the allowed-character rule in its own words. Why: the caller gets a code outside the service's vocabulary and wording no AWS region emits, so both programmatic classification and log matching fail. Fix: the CreateClusterParameterGroup handler's name validation. Traces: redshift-rshealth-parameter-group-value-mistakes#task#3.

Cause 3 of 10: an out-of-domain parameter VALUE is refused with the wrong code and emulator-authored text. AWS: ModifyClusterParameterGroup handing a boolean parameter a non-boolean value is refused HTTP 400 with code InvalidParameterValue and the message template "parameter value is not a valid boolean:" + the supplied value (fixed lower-case prefix, no space after the colon, one variable part; the parameter name is NOT named). Smithy: ModifyClusterParameterGroup models only ClusterParameterGroupNotFoundFault (404) and InvalidClusterParameterGroupStateFault (400), so the value-domain refusal is the service's own InvalidParameterValue (recorded behavior). Emulator: code ValidationException with a message that names the indexed wire member, the parameter and its allowed values. Why: a config-management client that validates by submitting and reading the code cannot distinguish a bad value from a malformed request. Fix: the ModifyClusterParameterGroup handler's per-parameter value-domain validation. Traces: redshift-rshealth-parameter-group-value-mistakes#task#4 (cluster also covers #task#8 and #task#10).

Cause 4 of 10: a valid ModifyClusterParameterGroup is refused outright. AWS: the modify answers HTTP 200 with ModifyClusterParameterGroupResult carrying the ParameterGroupName from the request and the fixed ParameterGroupStatus text "Your parameter group has been updated. If you changed only dynamic parameters, associated clusters are being modified now. If you changed static parameters, all updates, including dynamic parameters, will be applied when you reboot the associated clusters." Smithy: output shape ClusterParameterGroupNameMessage = {ParameterGroupName, ParameterGroupStatus}. Emulator: HTTP 400 and no ModifyClusterParameterGroupResponse at all. Why: a legal parameter change is rejected, so the group can never be brought to the desired state through the emulator and every downstream read in the workflow is wrong. Fix: the ModifyClusterParameterGroup handler's validation (it is refusing a value/parameter combination AWS accepts) and its success serializer. Traces: redshift-rshealth-parameter-group-value-mistakes#task#5 (cluster also covers #task#6).

Cause 5 of 10: DescribeClusterParameters serves an empty Parameters collection after successful modifies. AWS: after the group's parameters have been modified, DescribeClusterParameters returns the modified parameters, each with ParameterName, ParameterValue, Description, Source 'user', DataType, AllowedValues, ApplyType and IsModifiable. Smithy: output ClusterParameterGroupDetails.Parameters targets ParametersList. Emulator: Parameters is serialized as the empty value (type_mismatch against the expected list). Why: a client cannot read back the configuration it just wrote, so drift detection and any "read-after-write" reconciliation sees an unconfigured group. Fix: the DescribeClusterParameters handler's read of parameter-group state (and the state write performed by ModifyClusterParameterGroup). Traces: redshift-rshealth-parameter-group-value-mistakes#task#7.

Cause 6 of 10: an invalid wlm_json_configuration value is ACCEPTED. AWS: ModifyClusterParameterGroup setting wlm_json_configuration to a value that is not valid WLM JSON is refused HTTP 400 with code InvalidParameterValue and the fixed message "Invalid JSON for wlm_json_configuration" (no variable parts, no trailing period), and nothing is stored. Emulator: HTTP 200, the modify succeeds. Why: the emulator stores a WLM configuration AWS rejects, so a client believes an unparsable queue configuration took effect and no validation feedback ever reaches the operator. Fix: the ModifyClusterParameterGroup handler's wlm_json_configuration value validation. Traces: redshift-rshealth-parameter-group-value-mistakes#task#9.

Cause 7 of 10: a structurally invalid ModifyClusterParameterGroup request is refused with the wrong code — the same defect as cause 1 on the modify path. AWS: HTTP 400 with the query-protocol code ValidationError (the fixture asserts the code only). Emulator: code MalformedInput. Why: as cause 1 — the code is outside the service's vocabulary, so SDK validation-error handling does not fire. Fix: the redshift query-protocol request deserializer / ModifyClusterParameterGroup structural refusal. Traces: redshift-rshealth-parameter-group-value-mistakes#task#11.

Cause 8 of 10: the DescribeClusterParameters Source filter domain is wrong in both code and content. AWS: a Source outside the allowed domain is refused HTTP 400 with code InvalidParameterValue and the message template "Invalid Source: " + the supplied value + ". Allowed values are: engine-default, system, user" (fixed prefix and fixed allowed-value list, one variable part) — note the domain includes 'system', which the emulator does not know about. Smithy: DescribeClusterParameters.Source is an unconstrained String and the only modeled error is ClusterParameterGroupNotFoundFault, so the domain is a service rule (recorded behavior). Emulator: code ValidationException and the message "Invalid value for Source: '<value>'. Valid Values: user | engine-default" — wrong code, different fixed text, and a domain missing 'system'. Why: a client that filters by Source='system' is refused a legal filter, and the refusal it does get carries an unclassifiable code. Fix: the DescribeClusterParameters handler's Source validation and its allowed-value set. Traces: redshift-rshealth-parameter-group-value-mistakes#task#13.

Cause 9 of 10: the parameter catalog's Description and ApplyType metadata diverge from AWS's. AWS: for the redshift-1.0 family, enable_user_activity_logging carries Description 'parameter for audit logging purpose' and wlm_json_configuration carries Description 'wlm json configuration' with ApplyType 'dynamic'. Smithy: Parameter = {ParameterName, ParameterValue, Description, Source, DataType, AllowedValues, ApplyType, IsModifiable, MinimumEngineVersion}; the values themselves are catalog data, so this is recorded behavior only. Emulator: Description 'Logs each query run against the database to the user activity log.' and 'The workload management configuration, as a JSON array of queues.' (emulator-authored prose), and wlm_json_configuration ApplyType 'static'. Why: ApplyType is the contract that tells a client whether a reboot is required — reporting the dynamic wlm_json_configuration as static makes automation reboot clusters AWS would not, and the Description text is surfaced directly in consoles and CLI output. Fix: the redshift parameter-group parameter catalog (the static per-family parameter definitions). Traces: redshift-rshealth-parameter-group-value-mistakes#task#14.

Cause 10 of 10: the same catalog divergence on the Source-filtered read, where the parameter list is shorter and the affected indices differ. AWS: same Description and ApplyType values as cause 9 regardless of which Source filter produced the list. Emulator: same emulator-authored Description texts and the same static/dynamic ApplyType error, now at the filtered list's positions. Why: as cause 9, and it confirms the divergence is in the catalog itself rather than in one read path, so fixing only the unfiltered read leaves this one wrong. Fix: same parameter catalog — verify both the unfiltered and the Source-filtered reads. Traces: redshift-rshealth-parameter-group-value-mistakes#task#16.
