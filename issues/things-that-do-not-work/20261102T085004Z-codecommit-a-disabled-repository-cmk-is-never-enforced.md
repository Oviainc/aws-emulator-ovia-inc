# CodeCommit: a disabled repository CMK is never enforced on reads or writes, and the duplicate-approval-rule message is not AWS's (2 causes)

> _Note: this issue was identified against the code base at commit `86c9f1e4438a61fbe37b19dfcd3d77efce3d0679`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
TWO root causes in the codecommit crate, both grounded in failing behavioral checks the replay report left unmarked (neither ALREADY FILED nor OWNED). A fixer must close BOTH before submitting.

=== Cause 1 of 2: a repository's customer-managed KMS key is stored but never consulted — every read and write is served while the key is Disabled ===
AWS: Smithy models EncryptionKeyDisabledException (client, httpError 400 [defaulted]) on the codecommit read and write surface — it is in the error list of GetBlob, GetFile, GetBranch, PutFile and CreatePullRequestApprovalRule alike (verified with smithy_query on com-amazonaws-codecommit-codecommit-20150413). Recorded behavior: with the CMK a repository was created under moved to KeyState 'Disabled' (kms:DisableKey), each of those paths answers HTTP 400 with code EncryptionKeyDisabledException and serves NO content; after kms:EnableKey the byte-identical GetBlob hands back the original bytes and GetFile resolves the same blobId. The recorded message is the fixed words 'KMS key ' + the key ARN from the repository's kmsKeyId + ' is disabled' — the ARN is the variable part, taken from state, and the rest is fixed text. AWS does not enforce this on every individual request, which is why the recording polls each path inside a bounded window instead of sampling once.
Emulator: no refusal is ever observed. CreateRepository accepts kmsKeyId and echoes it back, but no read or write path resolves that key's state against the kms service, so GetBlob/GetFile/GetBranch keep returning content and PutFile keeps landing commits with the key Disabled. The check's refusal poll (180 s deadline, 5 s sleeps) therefore never returns and the check is killed by the harness budget — verdict 'mismatch', detail 'Check timed out after 60.0s'. Hypothesis: a correctly-refusing implementation returns on the first poll iteration, so the timeout is the symptom of 'never refuses', not of slowness.
Why: the whole point of pointing a repository at your own CMK is being able to cut access to its contents. An emulator that treats kmsKeyId as inert metadata lets key-revocation runbooks and break-glass drills pass against data that is still fully readable and still accepting commits, and client code written to handle EncryptionKeyDisabledException never has that branch exercised.
Fix: the repository-level encryption-key gate shared by the codecommit crate's read/write handlers (services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/get_blob.rs, get_file.rs, get_branch.rs, put_file.rs) and the repository state that records kmsKeyId — it must resolve the key's state in the kms service and refuse with EncryptionKeyDisabledException while it is Disabled.
Overlap, declared: the OPEN issue 20261022T213415Z-codecommit-putcommentreaction-is-a-501-stub-cmk-disablement.md carries this same check id (its Cause 2, Issue-Key 'codecommit.reads-blocked-when-the-repository-kms-key-is-disabled|_poll_for_refusal#21|Timeout|time.sleep(5.0)'), but this replay did NOT mark the check as owned, so it is recorded here rather than dropped. Whoever fixes either must re-replay this check id; closing one may close the other.
Traces: codecommit.reads-blocked-when-the-repository-kms-key-is-disabled.

=== Cause 2 of 2: CreatePullRequestApprovalRule's ApprovalRuleNameAlreadyExistsException message is the emulator's own template and leaks the rule name ===
AWS: Smithy CreatePullRequestApprovalRule (pullRequestId @required, approvalRuleName @required @length 1..100, approvalRuleContent @required @length 1..3000) models ApprovalRuleNameAlreadyExistsException (client, httpError 400 [defaulted]); the exception's own documentation is 'An approval rule with that name already exists. Approval rule names must be unique within the scope of a pull request.' Recorded behavior for the losing call of two concurrent creates of the same name: HTTP 400, code ApprovalRuleNameAlreadyExistsException, message 'An approval rule already exists with that name. Approval rule names must be unique within the scope of a pull request.' — entirely FIXED text, with no variable parts at all: AWS names neither the rule nor the pull request.
Emulator: the status (400) and the code are right, but the message is 'An approval rule with the name <approvalRuleName> already exists for this pull request. Approval rule names must be unique within a pull request.' — a different template that interpolates the requested rule name and ends with 'within a pull request' instead of 'within the scope of a pull request'. The rule name in the observed text is a per-run value filling the emulator's template; the requirement is AWS's fixed sentence, which carries no name.
Why: the concurrency semantics are already correct here (exactly one winner, exactly one loser, one stored rule), so the only thing a client sees as wrong is the text. Tools, runbooks and differential clients that match this message on the exact AWS sentence flag every duplicate-rule path, and a message that echoes the rule name reads as a per-request diagnostic rather than the fixed class AWS defines.
Fix: the ApprovalRuleNameAlreadyExistsException message construction in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_pull_request_approval_rule.rs (the duplicate-name branch of the approval-rule state it writes).
Related but not covering: 20261029T222310Z-codecommit-approval-rule-and-template-validation-messages-use.md covers the INVALID-CONTENT and template-SHA messages of this surface; it neither names this check nor this error class.
Traces: codecommit.approval-rule-name-conflict-rejected.
