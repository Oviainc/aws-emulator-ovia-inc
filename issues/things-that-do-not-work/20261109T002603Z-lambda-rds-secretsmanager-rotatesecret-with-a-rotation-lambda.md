# lambda__rds__secretsmanager: RotateSecret with a rotation Lambda that Secrets Manager may not invoke still neither refuses nor rotates — the check burns its whole 180 s budget

> _Note: this issue was identified against the code base at commit `7357c0aea0dc68ee0c6ea06203400d848de76641`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RotateSecret

## Description
One net-new root cause (1 of 1). Note for the fixer: resolved issue 20261107T212447Z-lambda-rds-secretsmanager-4-net-new-causes-in-function-secrets-manager.md already described this exact symptom as its Cause 4 and is marked fixed, yet the same check still ends in `Error: Check timed out after 180.0s` — this is not a new defect class, it is that cause still unresolved on this build. It is filed because the check is in this run's failing list and no open issue carries its replay key.

Cause 1 of 1 — the rotation-without-an-invoke-grant scenario never reaches a terminal answer.
AWS: recorded behavior only (the Secrets Manager model states no precondition for this on RotateSecret). Recorded behavior: RotateSecret validates that the service principal secretsmanager.amazonaws.com may invoke the function named by RotationLambdaARN BEFORE any rotation step runs. With no such resource-policy grant on the function, the call is refused synchronously with HTTP 400 and error code `AccessDeniedException`, message — fixed text, no variable parts — "Secrets Manager cannot invoke the specified Lambda function. Ensure that the function policy grants access to the principal secretsmanager.amazonaws.com." Nothing moves as a consequence: DescribeSecret shows no version staged AWSPENDING, GetSecretValue(AWSCURRENT) still returns the pre-rotation password, and the rotation function is never invoked, so /aws/lambda/<function> does not exist and FilterLogEvents on it is refused `ResourceNotFoundException` with message "The specified log group does not exist." Granting lambda:InvokeFunction to secretsmanager.amazonaws.com and repeating the same RotateSecret then rotates: AWSCURRENT moves to a new version id, the previous version keeps the AWSPREVIOUS label, and the password changes.
Emulator: no verdict at all — `Error: Check timed out after 180.0s`. Neither the AccessDeniedException refusal nor a completed rotation is observed inside the harness budget. The replay output carries no traceback frame, so it does not say which call stalled; the scenario's sequence before the assertion is a default-VPC lookup, CreateDBSubnetGroup, CreateDBInstance (MySQL) waited to its ready state, CreateSecret, CreateRole/CreateFunction, then RotateSecret. Hypothesis: either the RDS instance never reaches its available state or RotateSecret itself never answers; the recording shows every one of those calls terminating.
Why: a client that mis-wires a rotation Lambda's resource policy gets no answer whatsoever — the secret silently stops rotating and the API call that should have told it why hangs, so the misconfiguration surfaces only as expired credentials later. A client that wires it correctly cannot confirm rotation either, because the positive control on the same secret/function pair is never reached.
Fix: the RotateSecret handler — resolve RotationLambdaARN, check that secretsmanager.amazonaws.com is granted invoke on it, and refuse promptly with AccessDeniedException and the message above when it is not; and whichever of the RDS instance-provisioning state machine or that handler fails to reach a terminal state, so the call answers at all.

## Evidence
Expected: RotateSecret(SecretId=<arn>, RotationLambdaARN=<fn arn>, RotationRules={AutomaticallyAfterDays:1}, RotateImmediately=true) with no secretsmanager.amazonaws.com invoke grant on the function is refused with error code AccessDeniedException and the message "Secrets Manager cannot invoke the specified Lambda function. Ensure that the function policy grants access to the principal secretsmanager.amazonaws.com."; afterwards no version is staged AWSPENDING, AWSCURRENT still holds the original password, and FilterLogEvents on /aws/lambda/<fn> is refused ResourceNotFoundException "The specified log group does not exist."; then, after AddPermission for the service principal, the same call rotates and AWSCURRENT moves to a new version with the old one labelled AWSPREVIOUS.
Actual: `Error: Check timed out after 180.0s` — no refusal, no rotation, no frame identifying the stalled call. Resolved issue 20261107T212447Z-lambda-rds-secretsmanager-4-net-new-causes-in-function-secrets-manager.md recorded the identical symptom for this check as its Cause 4.

## Steps to Reproduce
1. Create a DB subnet group in the default VPC and a MySQL DB instance; wait for it to become available. 2. CreateSecret holding that instance's host/user/password. 3. Create an execution role and a rotation Lambda (createSecret/setSecret/testSecret/finishSecret steps), and deliberately do NOT AddPermission lambda:InvokeFunction for principal secretsmanager.amazonaws.com. 4. Call RotateSecret with RotationLambdaARN=<that function>, RotationRules={AutomaticallyAfterDays:1}, RotateImmediately=true and read the error code/message. 5. Grant the permission and repeat the same RotateSecret, then poll DescribeSecret/GetSecretValue for the new AWSCURRENT version. Against the emulator the scenario never reaches step 4's verdict within 180 s.
