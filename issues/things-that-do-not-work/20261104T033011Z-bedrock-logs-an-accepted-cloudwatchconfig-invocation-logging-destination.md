# bedrock__logs: an accepted cloudWatchConfig invocation-logging destination never receives a ModelInvocationLog event, so the log-event-shape check hangs to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `c2d690adb5c99cf0fe6b339d9b4e7b6ccf196d09`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutModelInvocationLoggingConfiguration

## Description
This issue carries 1 net-new root cause for the bedrock/CloudWatch Logs pair; the service heading the suite report lists the failing check under is `bedrock__logs`. It is the ONLY failing check in this replay of simparity-behavioral-aws-v1 that the report marked neither "ALREADY FILED" nor "OWNED by" — all 112 other reported failures carry an owner.

Cause 1 of 1: with a CloudWatch Logs destination installed (loggingConfig.cloudWatchConfig + textDataDeliveryEnabled=true), model invocations produce no invocation log event in the configured log group at all. The configuration is accepted and read back, the subsequent Converse call returns 200, and the log group stays empty forever, so a caller polling for its own invocation's record polls until it is killed. Failing check: bedrock__logs.model-invocation-log-event-shape-at-cloudwatch-logs — "Error: Check timed out after 60.0s" (the check's own delivery deadline is 240 s, so it never reaches its own assertions).

AWS: Smithy (com.amazonaws.bedrock) models PutModelInvocationLoggingConfiguration as PUT /logging/modelinvocations, success code 200, @idempotent, output shape with no members, one required input member `loggingConfig` -> LoggingConfig; modeled errors AccessDeniedException (@httpError 403), ValidationException (@httpError 400), ThrottlingException (429), InternalServerException (500). LoggingConfig carries `cloudWatchConfig` -> CloudWatchConfig {logGroupName required @length 1..512, roleArn required @length max 2048 @pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$, largeDataDeliveryS3Config} alongside `s3Config` and the per-modality switches textDataDeliveryEnabled / imageDataDeliveryEnabled / embeddingDataDeliveryEnabled / videoDataDeliveryEnabled / audioDataDeliveryEnabled; GetModelInvocationLoggingConfiguration is GET on the same URI returning {loggingConfig}. The DELIVERY behavior is not in the model — recorded behavior only: once a cloudWatchConfig destination is in force for the account and region, Bedrock assumes the configured roleArn and writes one JSON log event per model invocation into a log stream of the named log group, promptly (seconds, not minutes). Each event's message is a JSON document with schemaType="ModelInvocationLog", `operation` equal to the API that ran ("Converse" for a Converse call), `modelId` equal to the model id the request named, `accountId` equal to the calling account and `region` equal to the request region, `input.inputBodyJson` holding the request body as submitted (so the prompt text appears verbatim), `output.outputBodyJson` holding the response body as returned, and `input.inputTokenCount` / `output.outputTokenCount` equal to the `usage.inputTokens` / `usage.outputTokens` the inline Converse response reported. Delivery is gated by the per-modality *DataDeliveryEnabled switches (text here).

Emulator: the setup all succeeds — logs.CreateLogGroup and logs.DescribeLogGroups return the group, iam.CreateRole/PutRolePolicy create the bedrock.amazonaws.com-trusted delivery role, PutModelInvocationLoggingConfiguration with that cloudWatchConfig is accepted on the first call (no "Failed to validate permissions" ValidationException is ever served, so the check's bounded propagation retry never engages), GetModelInvocationLoggingConfiguration reports the configuration back with the right logGroupName, and bedrock-runtime Converse against amazon.nova-lite-v1:0 answers 200. But logs.FilterLogEvents over the configured log group returns no event carrying the prompt nonce — in fact no invocation event at all — so the check's bounded poll never matches and the harness kills the run: "Error: Check timed out after 60.0s". Zero events delivered, not a malformed event: every downstream assertion (schemaType=="ModelInvocationLog", operation=="Converse", modelId, accountId, region, the prompt nonce inside input.inputBodyJson, and the two token-count equalities against the inline usage) is unreachable.

Why: a client that enables model invocation logging to a CloudWatch Logs destination to audit what was prompted and what was generated gets an account that reports logging as configured while producing no audit trail. There is no error to key off — the emulator's answer is silence — so compliance/observability code that waits for its invocation's record (the normal pattern, because the configuration is an account-and-region singleton shared with other invocations) blocks until its own timeout rather than finding the record, and code that reconciles the logged token counts against the inline usage can never run. Live monitoring built on a metric filter or subscription filter over that log group sees no data.

Fix: the delivery step for the cloudWatchConfig destination is missing. The control-plane handler for PutModelInvocationLoggingConfiguration only stores `loggingConfig` into account/region state and nothing on the inference path consumes it; the bedrock-runtime inference handlers (Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream) must, after a successful invocation, read that singleton and — when a cloudWatchConfig is installed and the relevant *DataDeliveryEnabled switch is on — emit one ModelInvocationLog JSON event into a log stream of the configured logGroupName, carrying schemaType, operation, modelId, accountId, region, input.inputBodyJson, output.outputBodyJson and the same token counts the inline response reported. This is the CloudWatch Logs sibling of the S3 delivery gap and must be fixed on the same path.

Related open issues, none of which the report reported as owning this check and none of which covers this cause: 20261102T125313Z-bedrock-model-invocation-logging-is-inert-an-accepted.md covers the SAME missing delivery step for the `s3Config` destination (different destination branch, different check); 20261030T100233Z-bedrock-logs-putmodelinvocationloggingconfiguration-accepts-a-cloudwatchconfig-the-recorded.md is grounded in this same check id but on the ACCEPT/REFUSE decision of the cloudWatchConfig branch (and its replay key is an AssertionError on a withdrawal assertion this check no longer makes — the check now asserts the delivered log event shape, and fails by timeout); 20261030T033702Z-bedrock-putmodelinvocationloggingconfiguration-refuses-an-unverifiable-cloudwatchconfig-with-403.md covers the 400-vs-403 error class for an unverifiable destination. Making the acceptance decision stricter does NOT fix this cause: whenever the destination is accepted 200, events must be delivered.
