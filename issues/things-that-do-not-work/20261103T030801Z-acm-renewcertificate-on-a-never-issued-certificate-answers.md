Cause 1 of 2: RenewCertificate on a certificate that was never issued (PENDING_VALIDATION) is refused RequestInProgressException instead of ResourceNotFoundException, with the wrong message, and every concurrent caller takes that same wrong branch.
AWS: Smithy RenewCertificate(CertificateArn required, Arn @length 20..2048 @pattern ^arn:[\w+=/,.@-]+:acm:[\w+=/,.@-]*:[0-9]+:[\w+=,.@-]+(/[\w+=,.@-]+)*$) -> Unit; modeled errors InvalidArnException (400), RequestInProgressException (400), ResourceNotFoundException (400), ValidationException (400). ACM's renewal target set is its ISSUED certificates, so an ARN that names a certificate which has not been issued is a lookup miss on that set: the call is refused HTTP 400 with Error.Code ResourceNotFoundException and Error.Message 'Could not find an issued certificate <CertificateArn>' — fixed text 'Could not find an issued certificate ' followed by the ARN taken verbatim from the request, and no terminating period. The refusal is per-call and stateless, so N simultaneous calls all get that same code and message, and the certificate's Status stays PENDING_VALIDATION throughout.
Emulator: all five concurrent calls are refused with Error.Code 'RequestInProgressException' and the generic message 'The certificate request is in process and the certificate in your account has not yet been issued.' (the RequestInProgressException doc sentence, reused verbatim), which names neither the certificate nor the account.
Why: the code is the branch a client takes. ResourceNotFoundException means 'this ARN is not a renewable certificate, stop'; RequestInProgressException means 'retry later'. A renewal client is therefore sent into an unbounded retry loop against a certificate that will never become renewable on this path, and because the message interpolates no ARN the loop cannot even report which certificate it is stuck on. A caller that catches ResourceNotFoundException (what the contract directs for a non-renewable ARN) sees an unhandled error instead.
Fix: the not-issued precondition in the RenewCertificate handler's state lookup (services/service-com-amazonaws-acm-certificatemanager/src/ops/renew_certificate.rs, the `certificate.status == crate::state::STATUS_PENDING_VALIDATION` arm around lines 232-241, which raises RequestInProgressException with crate::state::REQUEST_IN_PROGRESS_MESSAGE): a certificate that has never been issued must raise ResourceNotFoundException with the 'Could not find an issued certificate <arn>' text built from the request's ARN. The separate renewal-already-in-progress condition on the same arm (`certificate.renewal_in_progress()`) is the one that legitimately keeps RequestInProgressException.
Traces: acm.renew-certificate-concurrent-request-in-progress.

Cause 2 of 2: the ACME data plane is unreachable through the URL the service advertises — a standard ACME client that fetches AcmeEndpoint.EndpointUrl verbatim is sent to an address the emulator does not answer on.
AWS: recorded behavior only (the ACME wire is RFC 8555, not a modeled operation). Smithy DescribeAcmeEndpoint(AcmeEndpointArn required) -> {AcmeEndpoint}, @readonly, errors AccessDeniedException(403)/InternalServerException(500)/ResourceNotFoundException(400)/ThrottlingException(400)/ValidationException(400); AcmeEndpoint$EndpointUrl is server-managed (it is a member of no request shape). On AWS the contract is that this exact URL is what an ACME client (certbot, lego, acme.sh, the python `acme` library) is configured with: a plain GET of it returns the RFC 8555 §7.1.1 directory object, and the registration flow proceeds from the resource map that body carries.
Emulator: the emulator announces an EndpointUrl on host 'acm-acme-enroll.<region>.amazonaws.com' while being served on the endpoint under test. A client that connects to the announced URL as given never reaches the emulator — the run's egress guard refuses it with simparity.egress.EgressRefused: "'acm-acme-enroll.us-west-2.amazonaws.com' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator" — so the check dies before newAccount. The ACME surface itself IS implemented (services/service-com-amazonaws-acm-certificatemanager/src/service/acme_http.rs serves directory/new-nonce/new-account), but only for a request that is re-pointed at the emulator's own endpoint; the advertised address is not one the emulator can be reached on.
Why: EndpointUrl is the only handle a client has on the ACME data plane, and ACME clients are libraries that take the directory URL and dial it — they do not rewrite hosts. Announcing an address other than the one the service answers on makes the whole ACME account lifecycle (newNonce, newAccount with external account binding, the account's own URL, and therefore DescribeAcmeAccount/RevokeAcmeAccount's AccountUrl) unreachable for any client that is not written specially for this emulator, and the first symptom a caller sees is a connection failure rather than any modeled error.
Fix: the EndpointUrl projection and the front-door host routing must agree on an address the emulator answers on — the generator in the CreateAcmeEndpoint handler / the AcmeEndpoint projection used by DescribeAcmeEndpoint (services/service-com-amazonaws-acm-certificatemanager/src/ops/create_acme_endpoint.rs, src/ops/describe_acme_endpoint.rs, and crate::state::acme_resource_url, which also mints every URL inside the directory body), so that the host and port advertised in EndpointUrl (and in the directory's newNonce/newAccount URLs) resolve to the endpoint the emulator is reached on, while keeping the enrollment-host form the blessed EndpointUrl-shape checks require.
Traces: acm.revoke-acme-account-reaches-terminal-state.
