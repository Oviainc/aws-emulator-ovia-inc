# Redshift resource-policy ARN refusal reports an emulator-authored not-found message instead of AWS's unsupported-resource-type wording

> _Note: this issue was identified against the code base at commit `35b42028f3202d783cfd444fbd332c2960d24a7a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutResourcePolicy

## Description
Two net-new root causes, one shared fault: both resource-policy write paths refuse a ResourceArn whose resource type the resource-policy surface does not support with a message the emulator authored itself (a generic "the resource it names does not exist" sentence) rather than the sentence AWS emits from its ARN/tagging validation layer. HTTP status (400) and Error.Code already match on both steps; only Error.Message diverges. The open issues 20261104T045922Z-redshift-resource-policy-and-namespace-registration-semantics-diverge.md (unsupported resource TYPES accepted with HTTP 200, InvalidPolicyFault wording, policy canonicalization) and 20261029T192501Z-redshift-resource-policy-idc-application-and-event-subscription.md (resource-policy/IDC/event-subscription requests accepted where AWS refuses) describe neighbouring defects on the same surface but carry neither of the fixture steps below.

Cause 1 of 2 — PutResourcePolicy. AWS: a ResourceArn naming a resource type that the resource-policy path cannot resolve is refused at ARN validation with HTTP 400 and the message "Tagging is not supported for this type of resource: '<resource-type>' (the ARN is potentially malformed, please check the ARN documentation for more information)". The fixed text is "Tagging is not supported for this type of resource: '" ... "' (the ARN is potentially malformed, please check the ARN documentation for more information)"; the single variable part is the resource type parsed out of the supplied ResourceArn (the segment after the account id — 'datashare' in the recording). Smithy: PutResourcePolicy input member ResourceArn (String, required); modeled errors ConflictPolicyUpdateFault (400), InvalidPolicyFault (400), ResourceNotFoundFault (404), UnsupportedOperationFault (awsQueryError UnsupportedOperation, 400). The model does not state this wording or which fault class carries it — recorded behavior only: the recorded response is HTTP 400 and the replay flags only $.ErrorResponse.Error.Message, so the recorded Error.Code is the one the emulator already returns. Emulator: HTTP 400 with the right code but Error.Message "Invalid value for ResourceArn: '<arn>'. The resource it names does not exist." — fabricated wording that also asserts a different reason (the named resource is absent) from AWS's (the resource type is not supported / the ARN is malformed). Why: a client or operator matching the refusal text, or following the AWS-documented remediation of re-checking the ARN form, does not recognise the error; worse, it is told the resource is missing and will go create it, when no resource of that type can ever carry a resource policy through this call. Fix: the PutResourcePolicy handler's ResourceArn validation must emit AWS's unsupported-resource-type message, built from the resource type parsed from the request's ARN, instead of a generic not-found sentence. Traces: redshift-resource-policy-and-reserved-node-exchange-preconditions#task#2.

Cause 2 of 2 — DeleteResourcePolicy. AWS: the same ARN-validation refusal on the delete path — HTTP 400 with the identical message template "Tagging is not supported for this type of resource: '<resource-type>' (the ARN is potentially malformed, please check the ARN documentation for more information)", the resource type taken from the request's ResourceArn. Smithy: DeleteResourcePolicy input member ResourceArn (String, required); modeled errors ResourceNotFoundFault (404) and UnsupportedOperationFault (awsQueryError UnsupportedOperation, 400); the wording is recorded behavior only, and the recorded status is 400 with the code the emulator already matches. Emulator: HTTP 400 with the same emulator-authored text, "Invalid value for ResourceArn: '<arn>'. The resource it names does not exist." Why: a teardown path that distinguishes "this ARN can never hold a resource policy" from "this resource is gone" takes the wrong branch — it treats a permanent, unsupported-type refusal as a transient/benign missing-resource condition and reports cleanup as complete. Fix: the DeleteResourcePolicy handler's ResourceArn validation, sharing the one ARN-validation message builder with PutResourcePolicy so both paths word the refusal the same way. Traces: redshift-resource-policy-and-reserved-node-exchange-preconditions#task#3.
