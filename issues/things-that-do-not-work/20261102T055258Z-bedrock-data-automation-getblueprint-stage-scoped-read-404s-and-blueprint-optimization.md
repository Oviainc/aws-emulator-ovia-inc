# GetBlueprint stage-scoped read 404s and blueprint-optimization invoke skips S3 URI validation

> _Note: this issue was identified against the code base at commit `307ae70e1176afe8148743d9dbd874f3de53a94d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprint

## Description
Two net-new causes on the Bedrock Data Automation build-time service, both in the blueprint surface: a read of a blueprint that exists resolves to nothing, and an asynchronous blueprint-optimization submission is accepted without validating the S3 locations it carries. Neither is covered by the one open issue on this service (20261029T170936Z-bedrock-data-automation-tagging-operations-reject-every-bedrock-data-automation-resource.md, which is about resourceARN validation in the three tagging operations only). A fixer must close BOTH causes before submitting.

=== Cause 1 of 2: GetBlueprint answers 404 ResourceNotFoundException for a blueprint that exists ===
AWS: Smithy (services/service-com-amazonaws-bedrockdataautomation-amazonbedrockkeystonebuildtimeservice): GetBlueprint, http POST /blueprints/{blueprintArn}/ with success code 200; input GetBlueprintRequest{blueprintArn @required @httpLabel (BlueprintArn, len ..128), blueprintVersion (optional, pattern ^[0-9]*$, "Optional field to get a specific Blueprint version"), blueprintStage (optional enum BlueprintStage = DEVELOPMENT|LIVE, "Optional field to get a specific Blueprint stage")}; output GetBlueprintResponse.blueprint @required -> Blueprint{blueprintArn, blueprintName, schema, type, blueprintStage, creationTime, lastModifiedTime}; ResourceNotFoundException is modelled @httpError(404) and documented "This exception is thrown when a resource referenced by the operation does not exist". A read of a blueprint the same session created must therefore answer 200 with that blueprint. The recorded response for this step is HTTP 200 with the blueprint reported at blueprintStage DEVELOPMENT, type DOCUMENT, and the schema/name/ARN the create stored (the concrete ARN, name suffix, schema text and timestamps are this run's values, not requirements).
Emulator: HTTP 404 — the whole $.blueprint member is absent (replay: "status: expected 200, got 404; $.blueprint: missing"), i.e. the handler takes its ResourceNotFoundException path for a resource that is present in its own store.
Hypothesis: src/ops/get_blueprint.rs narrows the lookup by stage ("if let Some(stage) = input.blueprint_stage ... if stage != record.blueprint_stage { return Err(not_found()) }") and src/state.rs sets DEFAULT_BLUEPRINT_STAGE = "LIVE" for a create that names no stage, while the recording shows the blueprint at DEVELOPMENT — so a stage-scoped read of a blueprint created without an explicit stage resolves to nothing. The same handler also 404s when the request scopes the read to a version the record has no snapshot for. The model documents no default stage, so the stage a stage-silent create must report is the recorded behavior: DEVELOPMENT.
Why: a client that creates a blueprint and then reads it back — the normal author/promote loop, and what every SDK waiter and every Terraform-style read-after-write does — is told the resource does not exist. It then either retries forever or deletes its local record of a blueprint that is really there, and because the refusal is a modelled 404 rather than an error, nothing in the client flags it as an emulator fault.
Fix: GetBlueprint's handler and the blueprint record's stored stage in this service's state — the stage a stage-silent CreateBlueprint persists, and the stage/version narrowing the read applies before it concludes the resource is absent, must agree so that a read of a blueprint that exists cannot answer 404.
Traces: bedrock-data-automation-blueprint-lifecycle#task#8.

=== Cause 2 of 2: InvokeBlueprintOptimizationAsync accepts an invalid S3 URI and mints a job instead of refusing 400 ValidationException ===
AWS: Smithy: InvokeBlueprintOptimizationAsync, http POST /invokeBlueprintOptimizationAsync, @idempotent, success 200, output InvokeBlueprintOptimizationAsyncResponse.invocationArn @required; input requires blueprint (BlueprintOptimizationObject), samples (list of BlueprintOptimizationSample{assetS3Object @required, groundTruthS3Object @required}), outputConfiguration (BlueprintOptimizationOutputConfiguration{s3Object @required}) and dataAutomationProfileArn. Every one of those S3 members targets S3Object.s3Uri -> S3Uri, @length(1..1024) and pattern ^s3://[a-z0-9][\.\-a-z0-9]{1,61}[a-z0-9](/.*)?$. ValidationException is modelled @httpError(400), documented "This exception is thrown when the request's input validation fails". The recorded refusal for a submission carrying an S3 location the service cannot use is HTTP 400 with x-amzn-errortype naming ValidationException and the message "Request has invalid S3 URI" — that sentence is entirely FIXED text for this error class, with nothing interpolated from the request or from state (the recording's header value carries the coral suffix ":http://internal.amazon.com/coral/com.amazon.bedrock.keystone.build/"; the requirement is the ValidationException type name, not that per-build suffix).
Emulator: HTTP 200 with a freshly minted invocationArn. No $.message and no x-amzn-errortype header at all (replay: "status: expected 400, got 200; $.message: missing (expected 'Request has invalid S3 URI'); $headers.x-amzn-errortype: missing"). src/ops/invoke_blueprint_optimization_async.rs checks only that the referenced blueprint resolves and that the job quota is not exhausted, then stores input.samples and input.output_configuration verbatim — the S3 locations are never inspected.
Why: the operation is asynchronous, so the only moment a client can learn its input is unusable is this synchronous refusal. Accepting it returns a job ARN that can never produce output, so the caller polls GetBlueprintOptimizationStatus against a job that is doomed, and a bad bucket/key in a pipeline's configuration surfaces (if at all) as a mysterious later failure instead of a 400 at submit time. Code written against AWS, which asserts the 400/ValidationException pair to catch a mis-rendered S3 path, silently passes against the emulator.
Fix: InvokeBlueprintOptimizationAsync's input validation — validate the s3Uri of every samples[].assetS3Object, samples[].groundTruthS3Object and outputConfiguration.s3Object against the modelled S3Uri form before any job is minted, and refuse with ValidationException (HTTP 400, x-amzn-errortype ValidationException) carrying the fixed message "Request has invalid S3 URI"; a refused submission must leave no record behind.
Traces: bedrock-data-automation-blueprint-optimization-invoke#task#2.
