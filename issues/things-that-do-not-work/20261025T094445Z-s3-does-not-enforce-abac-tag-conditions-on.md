# S3 does not enforce ABAC tag conditions on GetObject, and lifecycle transition refusals carry non-AWS validation messages (3 causes)

> _Note: this issue was identified against the code base at commit `3bc9be6f406ac9203ca7b4af142bb62bbe4e14d6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject, PutBucketLifecycleConfiguration

## Description
Three net-new root causes in the bootstrapped `s3` service. None of the three failing checks is marked ALREADY FILED or OWNED in the replay report. A fixer must close ALL THREE causes before submitting.

Related open issues that do NOT cover these: 20261025T032458Z-s3-putbucketabac-stub.md (claims PutBucketAbac is an unimplemented stub — in this replay PutBucketAbac and GetBucketAbac both answered 200 and GetBucketAbac reported Status=Enabled, so the check got past them; the divergence below is in the AUTHORIZER, not in those two operations), 20261025T032458Z-s3-putbucketlifecycleconfiguration-stub.md (resolved; the operation is implemented and refuses with the right code — only the message text diverges), and the open s3 bundles 20261025T032458Z-s3-control-plane-10-root-causes-generic-validationexception.md / 20261025T032458Z-s3-object-plane-10-root-causes-conditional-requests.md / 20261025T053834Z-s3-object-plane-6-net-new-root-causes.md, none of which mentions bucket ABAC, aws:PrincipalTag/aws:ResourceTag evaluation, or lifecycle transition-ordering/minimum-duration message rules.

Cause 1 of 3 — with bucket ABAC Enabled, an identity policy whose grant is conditioned on a matching aws:ResourceTag/aws:PrincipalTag pair is not evaluated, so a tag-MISMATCHED session reads the object.
AWS: Smithy (com.amazonaws.s3) models PutBucketAbac (PUT /{Bucket}?abac, required member AbacStatus) and GetBucketAbac, and GetObject's authorization is the ordinary IAM request authorization; the model says nothing about condition-key evaluation, so this is recorded behavior only. Recorded behavior (this check's oracle): a bucket tagged Team=Finance with AbacStatus Status=Enabled, and an assumable role whose only permission statement is Allow s3:GetObject on arn:aws:s3:::<bucket>/* with Condition StringEquals {"aws:ResourceTag/Team": "${aws:PrincipalTag/Team}"}. A session assumed with session tag Team=Marketing is REFUSED — HTTP 403, error code AccessDenied, with the message AWS builds from the request: `User: arn:aws:sts::<account>:assumed-role/<role-name>/<session-name> is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:GetObject action`. A session assumed with session tag Team=Finance (the matching tag) is ALLOWED and returns the object bytes, which is what proves the refusal is attributable to the tag mismatch specifically.
Emulator: the tag-mismatched session's GetObject SUCCEEDS — HTTP 200 with the full body (17 bytes, ETag and x-amz-server-side-encryption: AES256 returned), no refusal at all. The condition block is effectively ignored: neither aws:PrincipalTag/<key> (from the assumed-role session tags) nor aws:ResourceTag/<key> (from the bucket's tag set) is resolved, and the policy variable `${aws:PrincipalTag/Team}` on the right-hand side of StringEquals is not interpolated.
Why: this is an over-permissive divergence and the worst class of one. ABAC is the mechanism customers use for tenant/team isolation: one role, many tag-scoped sessions. A client that validates its isolation design against this emulator sees cross-team reads succeed and concludes the deny works when the emulator never evaluated it; equally, a client testing the deny path gets a false pass and ships a policy whose enforcement it never exercised. Any check that asserts a tag-scoped refusal silently becomes a no-op.
Fix: the GetObject authorization path and the shared IAM condition evaluator it calls (the condition-key resolution and policy-variable interpolation used by s3 request authorization). It must populate aws:PrincipalTag/<k> from the session tags carried by the assumed-role credential, populate aws:ResourceTag/<k> from the addressed bucket's tag set when the bucket's AbacStatus is Enabled, interpolate ${aws:PrincipalTag/<k>} inside condition values, and refuse a non-matching request with 403 AccessDenied carrying the implicit-deny message form above (principal ARN, action, quoted resource ARN, "because no identity-based policy allows the s3:GetObject action").
Traces: s3.abac-policy-enforcement.

Cause 2 of 3 — PutBucketLifecycleConfiguration refuses a cold-before-warm transition order with the right code but its own message text instead of the Days-comparison message AWS builds from the request.
AWS: Smithy models no errors for PutBucketLifecycleConfiguration (errors: []); S3 publishes InvalidArgument at HTTP 400 for a rejected lifecycle document, and the message is built from the request — it names the member under constraint ('Days'), the action ('Transition'), both StorageClass values and the rule's filter description. Recorded behavior: for one rule over filter prefix `tiered/` with Transitions GLACIER@30 and STANDARD_IA@60, AWS answers code InvalidArgument with message `'Days' in the 'Transition' action for StorageClass 'GLACIER' for filter '(prefix=tiered/)' must be greater than 'Days' in the 'Transition' action for StorageClass 'STANDARD_IA' for filter '(prefix=tiered/)'`. The same two classes and day values in the order STANDARD_IA@30 -> GLACIER@60 are ACCEPTED (positive control, and the emulator accepts it too).
Emulator: same code (InvalidArgument) and status, but the message is the emulator's own prose: `Rule 1: transitions to "GLACIER" and then to the warmer class "STANDARD_IA"; transitions follow the order STANDARD_IA -> INTELLIGENT_TIERING -> ONEZONE_IA -> GLACIER_IR -> GLACIER -> DEEP_ARCHIVE`. It identifies the rule by ordinal rather than by its filter, never names the constrained member, and expresses the rule as a class ordering rather than as the Days comparison AWS states.
Why: the refusal is correctly classified, so a client that only branches on the code is fine; a client that surfaces or parses the message — the SDK's own error text, a CI policy linter, a CloudFormation/Terraform diagnostic, or an operator reading a deploy log — gets text that names neither the member nor the filter it must edit, and tooling keyed on AWS's template fails to extract the offending transition. The check's later leg (that the refused PUT leaves the previously stored warm->cold rule unchanged) was never reached, so it is still unverified.
Fix: the lifecycle-configuration validator's message construction — `crate::state::validate_lifecycle_configuration` and `LifecycleConfigurationRejection::message()` in the s3 service state (surfaced by services/service-com-amazonaws-s3-amazons3/src/ops/put_bucket_lifecycle_configuration.rs, which forwards rejection.code()/rejection.message() with HTTP 400). The ordering rule must be reported as the Days comparison between the two named StorageClasses, parameterized by the rule's filter description in AWS's `(prefix=<p>)` form.
Traces: s3.deep-s3-storage-class-lifecycle-transition-colder-before-warmer-rejected.

Cause 3 of 3 — the GLACIER 90-day minimum-storage-duration refusal likewise carries emulator prose instead of AWS's message rule.
AWS: same operation, same code/status channel (InvalidArgument, HTTP 400), message again built from the request. Recorded behavior: for one rule over filter prefix `archive/` with Transitions GLACIER@30 and DEEP_ARCHIVE@60, AWS answers InvalidArgument with message `'Days' in the 'Transition' action for StorageClass 'DEEP_ARCHIVE' for filter '(prefix=archive/)' must be 90 days more than 'filter '(prefix=archive/)'' in the 'Transition' action for StorageClass 'GLACIER'` (the doubled quoting of the filter clause is AWS's own text, reproduced here as the recorded template). The same pair at GLACIER@30 -> DEEP_ARCHIVE@120 is ACCEPTED, so only the gap differs. This is a SECOND, distinct rule from cause 2: the minimum gap is class-specific (90 days after GLACIER, not the 30 days STANDARD_IA carries), which is exactly what an implementation that hard-codes one minimum gets wrong.
Emulator: code InvalidArgument, message `Rule 1: transitions to "DEEP_ARCHIVE" 30 days after the transition to "GLACIER", which has a minimum storage duration of 90 days`.
Why: same client impact as cause 2 — the diagnosis a caller or its tooling reads does not name the member, the filter or the required value in the form AWS states, so message-driven remediation and parsers break. Filed as its own cause because it is a separate validation rule with its own message template; fixing the ordering message alone leaves this one diverging.
Fix: same component as cause 2 (`validate_lifecycle_configuration` / `LifecycleConfigurationRejection::message()`), with the per-class minimum storage duration carried into the message as the required number of days between the two named StorageClasses for the rule's filter.
Traces: s3.deep-s3-storage-class-lifecycle-transition-glacier-to-deep-archive-gap-rejected.
