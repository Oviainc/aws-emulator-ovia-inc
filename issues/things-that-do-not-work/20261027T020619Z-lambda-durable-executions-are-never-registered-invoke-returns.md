# lambda: durable executions are never registered (Invoke returns no DurableExecutionArn, ListDurableExecutionsByFunction stays empty) and three capacity-provider verdicts diverge (4 causes)

> _Note: this issue was identified against the code base at commit `9a356a0438a215c6e535efb212b208d427610e62`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Four net-new root causes in the Lambda emulator, grounded in ten failing behavioral checks. A fixer must close all four before submitting.

Cause 1 of 4: an async Invoke that names a DurableExecutionName starts no durable execution, so no durable execution can ever be addressed (7 checks).
AWS: Smithy (service-com-amazonaws-lambda-awsgirapiservice) models Invoke input member DurableExecutionName (httpHeader X-Amz-Durable-Execution-Name, @length 1-64, pattern ^[a-zA-Z0-9-_]+$) and Invoke output member DurableExecutionArn (httpHeader X-Amz-Durable-Execution-Arn, pattern ^arn:...:function:<name>:(\$LATEST(\.PUBLISHED)?|[0-9]+)/durable-execution/<name>/<id>$); Invoke also models DurableExecutionAlreadyStartedException (409). ListDurableExecutionsByFunction (GET /2025-12-01/functions/{FunctionName}/durable-executions, filterable by DurableExecutionName/Statuses) returns the DurableExecutions list, and the DurableExecution resource carries GetDurableExecution / CheckpointDurableExecution / GetDurableExecutionHistory / GetDurableExecutionState / StopDurableExecution. So an accepted `Invoke(InvocationType=Event, Qualifier=$LATEST, DurableExecutionName=<name>)` on a durable-execution function must either return the DurableExecutionArn header on the 202 or make the execution listable under that name within seconds.
Emulator: the Invoke is accepted with StatusCode 202 but carries NO DurableExecutionArn header, and ListDurableExecutionsByFunction then answers 200 with `{'DurableExecutions': []}` forever (observed for the full 30 s poll window of each check). The checks therefore abort with `durable execution named <name> not found in 30.0s`, `durable execution <name> to be listed not met within 30s. Last result: {... 'DurableExecutions': []}`, `durable execution never registered under ListDurableExecutionsByFunction; cannot validate KMS enforcement without a real execution ARN` and `could not resolve a DurableExecutionArn`. Nothing in the durable-execution surface (checkpointing, callbacks/heartbeats, callback timeouts, KMS enforcement on execution state) can be exercised because no execution ARN exists. The open issue 20261026T070343Z-events-lambda-sqs-lambda-invoke-on-a-durable-execution-function-returns.md describes the same missing-ARN symptom for an SQS status-change check but does not carry these seven replay keys; the fixed issue 20261026T070343Z-lambda-listdurableexecutionsbyfunction-stub.md implemented the list operation's envelope only — it now answers 200, but the registry it reads from is never populated.
Why: a client that starts a durable execution gets a 202 with no handle and an empty listing, so it can never checkpoint, send a callback/heartbeat, read execution state or history, or stop the execution. Every durable-execution workflow silently does nothing instead of running.
Fix: Invoke's handler must, when DurableExecutionName is present, create a durable-execution record in the function's durable-execution state, return its ARN in the X-Amz-Durable-Execution-Arn response header, and make it visible to ListDurableExecutionsByFunction (and to the DurableExecution read/checkpoint/stop operations); a second Invoke reusing a live name must raise DurableExecutionAlreadyStartedException (409). The work belongs in the Invoke handler plus the shared durable-execution state, not only in the list operation's serializer.
Traces: lambda.callback-heartbeat-extends-deadline, lambda.callback-timeout-exceeded-rejected, lambda.durable-execution-callback-timeout-enforced, lambda.durable-execution-checkpoint-sequence-monotonic, lambda.durable-execution-kms-enforcement-rejected, lambda.durable-execution-kms-errors, lambda.send-callback-success-after-checkpoint-window.

Cause 2 of 4: DeleteCapacityProvider's in-use refusal message is not AWS's sentence (1 check).
AWS: Smithy models DeleteCapacityProvider (DELETE /2025-11-30/capacity-providers/{CapacityProviderName}, success 202) with ResourceConflictException (409). Recorded behavior: when a function version is still associated with the provider, AWS refuses 409 ResourceConflictException with the message template `The capacity provider is currently in use by 1 function. To delete this capacity provider, first remove its association with <function-version-arn>.` Fixed text: "The capacity provider is currently in use by ", " function. To delete this capacity provider, first remove its association with ", trailing period. Variable parts: the count of associated functions, and the qualified function-version ARN taken from the emulator's own association state.
Emulator: the status and error code are right (409 ResourceConflictException) but the message is `The capacity provider <capacity-provider-arn> cannot be deleted while it is in use by 2 function version(s), including <function-arn>` — a different sentence, it leads with the provider ARN instead of the association, it counts 2 where one version is associated, it names the UNqualified function ARN instead of the `<fn-arn>:1` version ARN, and it has no terminating period.
Why: a client that matches on the refusal text, or that parses the sentence to learn which association to remove, is told the wrong thing: it is handed a provider ARN and an unqualified function ARN, and an association count that does not match the versions actually attached.
Fix: the DeleteCapacityProvider handler's refusal message construction, and the association-count it reads out of capacity-provider state (one associated version must count as 1).
Traces: lambda.delete-capacity-provider-with-attached-function-rejected.

Cause 3 of 4: UpdateCapacityProvider's mid-delete conflict message is not AWS's sentence (1 check).
AWS: Smithy models UpdateCapacityProvider (PUT /2025-11-30/capacity-providers/{CapacityProviderName}, success 202) with ResourceConflictException (409). Recorded behavior: an UpdateCapacityProvider issued while the provider is being deleted is refused 409 ResourceConflictException with the fixed text `The capacity provider can't be updated because it's currently processing another operation. Wait for the current operation to complete and try again.` — this template has no variable parts.
Emulator: status and code are right, the message is `The operation cannot be performed at this time. The capacity provider is currently in the following state: Deleting` — different wording, and it leaks the internal lifecycle state name into the diagnosis instead of telling the caller to wait and retry.
Why: callers that retry on AWS's wording, or that surface the refusal to an operator, get an unrecognized sentence; the state name in the emulator's text is not a contract AWS exposes here.
Fix: the UpdateCapacityProvider handler's conflict-refusal message construction.
Traces: lambda.update-capacity-provider-conflict-during-delete-rejected.

Cause 4 of 4: a function created with CapacityProviderConfig reports State "Active" instead of "ActiveNonInvocable" (1 check).
AWS: Smithy enum State = [Pending, Active, Inactive, Failed, Deactivating, Deactivated, ActiveNonInvocable, Deleting]; PutFunctionScalingConfig returns FunctionState of that same enum. Recorded behavior: a function created with a LambdaManagedInstancesCapacityProviderConfig settles its $LATEST configuration in State `ActiveNonInvocable` — $LATEST on such a function is never directly invocable, only a published version registered with the capacity provider is.
Emulator: GetFunctionConfiguration answers 200 with `'State': 'Active', 'LastUpdateStatus': 'Successful'` while the same document carries `CapacityProviderConfig.LambdaManagedInstancesCapacityProviderConfig.CapacityProviderArn`, so the capacity-provider-managed function is reported as a normally invocable function.
Why: a client reads State == Active and invokes $LATEST, which real AWS never allows for a capacity-provider-managed function; orchestration that waits for ActiveNonInvocable before publishing a version and putting a scaling config never sees that state at all. Related open issue 20261025T100455Z-lambda-getfunctionscalingconfig-accepts-a-function-with-no-capacity.md covers a different scaling-config read defect and does not cover this state projection.
Fix: the function-state computation behind CreateFunction/GetFunctionConfiguration (the $LATEST state must be ActiveNonInvocable whenever CapacityProviderConfig is present), and PutFunctionScalingConfig's returned FunctionState.
Traces: lambda.put-function-scaling-config-then-capacity-provider-list-reflects.
