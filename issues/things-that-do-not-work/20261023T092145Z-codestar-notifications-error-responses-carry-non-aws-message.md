# codestar-notifications error responses carry non-AWS message text

> _Note: this issue was identified against the code base at commit `aae04825aca42e5b620901be4ebc2f4e42bc7c15`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateNotificationRule

## Description
Every modeled error path of codestar-notifications returns the right HTTP status and the right error shape, but the Message member is generated by the emulator's own templates instead of following the rule AWS uses. One of them (the validation error) misstates the constraint it reports and echoes a @sensitive value back to the caller. This bundle has 5 causes; all five must be closed.

Cause 1 of 5: CreateNotificationRule with a name that already exists (fixture codestar-notifications-create-rule-error-paths, step task#5).
AWS: Smithy: CreateNotificationRule errors include ResourceAlreadyExistsException, httpError 409, member Message (string, length min 1), documented 'A resource with the same name or ID already exists. Notification rule names must be unique in your Amazon Web Services account.' The recorded response is 409 with the service's fixed explanatory text about the name already being in use and rule names having to be unique in the account; it names neither the submitted name nor the existing rule's ARN. CreateNotificationRuleRequest.Name targets NotificationRuleName, which is @sensitive.
Emulator: 409 ResourceAlreadyExistsException - status and code correct - with a message it builds from the request and from state: 'A notification rule with the name "<name>" already exists in this account and region: arn:aws:codestar-notifications:<region>:<account>:notificationrule/<id>'.
Why: AWS's message for this error is a service constant, so the emulator's request-derived text is a different rule, not a different wording of the same one; worse, it discloses the @sensitive rule name and the ARN/id of a rule the caller did not name, which AWS deliberately does not return. A client or log scrubber that treats a sensitive member as never echoed is wrong against this emulator.
Fix: the CreateNotificationRule handler's duplicate-name branch - emit the ResourceAlreadyExistsException message as the service's constant text and stop interpolating the submitted name and the conflicting rule's ARN into it.
Traces: codestar-notifications-create-rule-error-paths#task#5.

Cause 2 of 5: CreateNotificationRule with a name violating the name pattern (fixture codestar-notifications-create-rule-error-paths, step task#6).
AWS: Smithy: ValidationException is a service-common error, httpError 400, member Message; NotificationRuleName has length min 1 max 64, pattern ^[A-Za-z0-9\-_ ]+$ and is @sensitive. The message here IS built from the request by a known rule - AWS's standard constraint-violation format - and the recording shows that format precisely: '1 validation error detected: Value at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: [A-Za-z0-9\-_ ]+$'. Two properties of that rule matter: the offending value is NOT echoed (the member is sensitive, so AWS prints 'Value at <member>' rather than 'Value <value> at <member>'), and the pattern is reported without its leading ^ anchor.
Emulator: 400 ValidationException - status and code correct - with '1 validation error detected: Value 'bad name!' at 'name' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[A-Za-z0-9\-_ ]+$': it inserts the rejected value and reports the anchored form of the pattern.
Why: the emulator echoes a @sensitive member's value into an error message, which is exactly the redaction AWS's format exists to perform, and it reports a constraint string that differs from the one AWS reports, so a client that surfaces or parses the constraint text sees a different regex than AWS would ever send.
Fix: the shared validation-error formatter used by the codestar-notifications handlers - omit the value for @sensitive members and strip the anchors when rendering a pattern constraint.
Traces: codestar-notifications-create-rule-error-paths#task#6.

Cause 3 of 5: DescribeNotificationRule (and the other read/delete paths in the cluster) for a rule ARN that does not exist (fixture codestar-notifications-create-rule-error-paths, step task#8).
AWS: Smithy: DescribeNotificationRule errors ResourceNotFoundException, httpError 404, member Message, documented 'CodeStar Notifications can't find a resource that matches the provided ARN.' The recorded message is built from the request, but from the rule ID extracted out of the submitted ARN, not the ARN itself: 'A notification rule with the following ID cannot be found: <id>. Verify that the notification rule ID is correct, and then try again.'
Emulator: 404 ResourceNotFoundException - status and code correct - with a single generic text, 'No notification rule matches the ARN <arn>'.
Why: AWS's not-found text is request-derived and identifies the resource by ID with a remediation sentence; the emulator substitutes one of its own for every operation, so a client that extracts the offending ID from the message, or matches AWS's phrasing to classify a transient-vs-permanent miss, gets nothing to match.
Fix: the ResourceNotFoundException construction behind DescribeNotificationRule/DeleteNotificationRule - build the message from the ID parsed out of the request ARN in AWS's form.
Traces: codestar-notifications-create-rule-error-paths#task#8; the same cluster covers codestar-notifications-create-rule-error-paths#teardown#13, codestar-notifications-delete-notification-rule-idempotent#task#6, codestar-notifications-list-and-filter-rules#teardown#10, codestar-notifications-list-and-filter-rules#teardown#12, codestar-notifications-rule-lifecycle#teardown#9, codestar-notifications-target-subscribe-unsubscribe#teardown#13.

Cause 4 of 5: UpdateNotificationRule for a rule that does not exist (fixture codestar-notifications-create-rule-error-paths, step task#9).
AWS: Smithy: UpdateNotificationRule errors ResourceNotFoundException, httpError 404, member Message. Recorded message, built from the request's ARN by taking its rule ID: 'A notification rule with the Id <id> was not found.' - a different phrasing from the describe path, so the message is per-operation.
Emulator: 404 ResourceNotFoundException with the same generic 'No notification rule matches the ARN <arn>' as every other not-found path.
Why: the emulator collapses per-operation not-found text into one string, so a client cannot tell from the message which call failed and does not receive the ID-form AWS sends.
Fix: the UpdateNotificationRule handler's not-found branch - emit this operation's own ID-based message.
Traces: codestar-notifications-create-rule-error-paths#task#9.

Cause 5 of 5: Subscribe against a rule ARN that does not exist (fixture codestar-notifications-create-rule-error-paths, step task#11).
AWS: Smithy: Subscribe errors ConfigurationException and ResourceNotFoundException, httpError 404, member Message. Recorded message, built from the request: 'A notification rule with the Id <full ARN> was not found.' - here the Id slot carries the whole submitted ARN, unlike the describe and update paths.
Emulator: 404 ResourceNotFoundException with the generic 'No notification rule matches the ARN <arn>'.
Why: same as causes 3 and 4 - the status and code are right but the request-derived message AWS specifies for this operation is not produced.
Fix: the Subscribe handler's not-found branch.
Traces: codestar-notifications-create-rule-error-paths#task#11.
