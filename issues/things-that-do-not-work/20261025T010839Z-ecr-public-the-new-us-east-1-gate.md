# ECR Public: the new us-east-1 gate on PutRegistryCatalogData refuses the primary client, so the account-global registry catalog write is unreachable (1 cause)

> _Note: this issue was identified against the code base at commit `a0c9c8ccc8bc5abababeef7ae6993b0ce3338eb3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRegistryCatalogData

## Description
REOPENS 20261022T192707Z-ecr-public-putregistrycatalogdata-has-no-us-east-1.md: its fix left the call refused.

That issue's cause 1 asked for a Region gate on PutRegistryCatalogData, and a gate was added. The gate is now applied to the suite's PRIMARY ecr-public client as well, so the operation that previously answered 200 for that client now answers 400 UnsupportedCommandException and the round-trip check it also carried (ecr-public.registry-catalog-display-name-round-trip-and-limit, listed in that issue's Issue-Trace-Ids) can no longer reach its first assertion. ONE cause, below.

=== Cause 1 of 1: PutRegistryCatalogData from the suite's primary client is refused 400 UnsupportedCommandException, where the recording serves it 200 ===
AWS: Smithy PutRegistryCatalogData — input displayName -> RegistryDisplayName (@length min 0, max 100), output registryCatalogData (required); modeled errors InvalidParameterException (client, httpError 400), ServerException (server, 500) and UnsupportedCommandException (client, 400, documented "The action isn't supported in this Region"). UnsupportedCommandException is the refusal for a request addressed to a Region that does not serve the call; it is NOT the response to a well-formed call on the endpoint/Region that does serve it. Recorded behavior: the check's primary ecr-public client calls PutRegistryCatalogData(displayName=<100 chars>) and is served — HTTP 200 echoing registryCatalogData.displayName verbatim, readable back through GetRegistryCatalogData — and only a 101-character value is refused (400 InvalidParameterException). The separate check ecr-public.put-registry-catalog-data-unsupported-command-rejected, which builds an explicitly wrong-Region client, is the one that records the UnsupportedCommandException leg, and it passes in this replay.
Emulator: src/ops/put_registry_catalog_data.rs calls crate::state::unsupported_in_region(ctx.parts(), "PutRegistryCatalogData") before touching state; that helper (src/state.rs) parses the Region out of the request's SigV4 credential scope and refuses every scope that is not case-insensitively equal to the hardcoded constant API_REGION = "us-east-1". The suite's primary client does not sign for that literal Region, so the very first PutRegistryCatalogData of the round-trip check fails with botocore.errorfactory.UnsupportedCommandException: "An error occurred (UnsupportedCommandException) when calling the PutRegistryCatalogData operation: PutRegistryCatalogData command is only supported in us-east-1." The check errors out before any of its own assertions run. Hypothesis: the gate is keyed to a hardcoded Region string rather than to the Region the emulator is actually serving as, so it refuses the one client every other ecr-public check uses successfully.
Why: the write half of the only account-global, resource-less pair in ecr-public becomes unreachable. A client pointed at the emulator with the Region it is served on can never set a registry displayName, so GetRegistryCatalogData can never return anything a caller wrote, and every workflow that publishes a registry author name (Gallery setup, a deploy script, a conformance suite) fails with a client error AWS does not return for that request. The gate has also inverted the original defect instead of fixing it: over-permissive accept has become over-strict refusal, and the Region-refusal code path now fires on the happy path, so a caller handling UnsupportedCommandException cannot distinguish "wrong Region" from "correct Region".
Fix: the Region gate — crate::state::unsupported_in_region / the API_REGION constant in services/service-com-amazonaws-ecrpublic-spencerfrontendservice/src/state.rs, consulted by src/ops/put_registry_catalog_data.rs — must compare the request's SigV4 credential-scope Region against the Region this emulator instance is serving as (its configured/announced Region) rather than a hardcoded literal, so a request that reaches the emulator as its own Region is served 200 while a request signed for a different Region is still refused the modeled UnsupportedCommandException (400). Both legs must hold together: ecr-public.put-registry-catalog-data-unsupported-command-rejected must keep passing. Once the call is served again, the round-trip check continues into its 101-character rejection assertion, which is the still-open InvalidParameterException message-template divergence (cause 3 of that fixed issue, and cause 3 of the open 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md) — that cause is not re-filed here, but this check will only go green once it is also closed, so re-replay this check after both.
