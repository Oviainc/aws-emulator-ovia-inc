# Custom-lens publish path, empty-selection risk derivation, milestone conflict echo and enum-validation wording diverge in wellarchitected

> _Note: this issue was identified against the code base at commit `7f15003d0a907feeff2a5480102e15f01cf57628`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLensVersion

## Description
This bundle has 5 causes, all in service wellarchitected, grounded in the 8 failing checks of suite simparity-behavioral-aws-v1. Causes 1 and 5 concern the custom-lens DRAFT/PUBLISHED lifecycle, cause 2 the CreateMilestone conflict message, cause 3 the derivation of Answer$Risk, cause 4 the enum-violation wording on CreateWorkloadShare.

Cause 1 of 5: CreateLensVersion cannot resolve the custom lens ImportLens just created, so no custom lens can ever be published.
AWS: CreateLensVersion (Smithy: POST /lenses/{LensAlias}/versions, code 200, output CreateLensVersionOutput{LensArn, LensVersion}; errors include ResourceNotFoundException httpError 404, ConflictException httpError 409) accepts for LensAlias (@length 1..128, httpLabel) the very lens ARN that ImportLens returned in LensArn, and publishes the named version: 200 with LensArn = the account-scoped custom lens ARN and LensVersion = the version name taken from the request.
Emulator: answers 404 ResourceNotFoundException. The message's fixed text is '[ResourceNotFound] No custom lens with alias ' ... ' was found in account ' ... '.', with the lens ARN taken from the request and the account id from the caller's identity — i.e. the emulator never resolves a lens it has itself just stored, whatever the id values are.
Why: a client that imports a lens and publishes it — the only way to make a custom lens usable — is blocked at the publish step, so every downstream capability (AssociateLenses, GetLensReview, UpdateAnswer against a custom lens, UpgradeLensReview, GetLensVersionDifference, improvement tracking) is unreachable. Four independent behavioral checks all terminate on this one call.
Fix: the CreateLensVersion handler's lens-alias resolution against the lens store that ImportLens writes (ARN-form alias must resolve to the imported record), plus the DRAFT->PUBLISHED transition it performs.
Related open issue, which does NOT cover these checks: 20261029T192731Z-wellarchitected-custom-lens-import-publish-version-and-export-chain.md reports the same path from the WIRE corpus (its cause 3). These behavioral checks are independently grounded and are listed here so a fixer re-replays them; a fix to that wire issue must be confirmed against this cause's four check ids.
Traces: wellarchitected.custom-lens-risk-rules-derive-answer-risk, wellarchitected.disassociate-default-lens-rejected, wellarchitected.improvements-track-at-risk-answers, wellarchitected.lens-upgrade-preserves-recorded-answers.

Cause 2 of 5: the CreateMilestone duplicate-name ConflictException echoes the STORED milestone name instead of the name the request submitted.
AWS: CreateMilestone (Smithy: POST /workloads/{WorkloadId}/milestones; MilestoneName @length 3..100 required; errors include ConflictException httpError 409 with ConflictException{Message, ResourceId, ResourceType} all required) compares a milestone name against the workload's existing names ignoring capitalization and surrounding whitespace, and refuses a duplicate 409 ConflictException. Recorded behavior: the message's fixed text is '[Conflict] Milestone with name ' ... ' already exists under workload ' ... '. Capitalization and whitespace are ignored in milestone names.' Its variable parts are (a) the MilestoneName exactly AS SUBMITTED in the rejected request — not the trimmed/case-folded form and not the already-stored name — and (b) the WorkloadId from the request path.
Emulator: returns the right code (ConflictException) and the right fixed text, but substitutes the name of the milestone already on record. Replay: a request submitting the upper-cased name produced '[Conflict] Milestone with name sim2real-behav-ms-10526f21dc31 already exists under workload <workloadId>. Capitalization and whitespace are ignored in milestone names.' where AWS names the submitted 'SIM2REAL-BEHAV-MS-10526F21DC31'. The same substitution happens for the whitespace-padded form, where AWS preserves the submitted leading/trailing spaces.
Why: a client that surfaces or logs the refusal names a string the caller never sent, so an operator cannot tell which of several candidate names was rejected, and a client that string-matches the message against its own request input never matches.
Fix: the CreateMilestone handler's name-conflict path — render the message from the request's MilestoneName, and keep normalization confined to the comparison.
Traces: wellarchitected.duplicate-milestone-name-rejected.

Cause 3 of 5: UpdateAnswer with an empty SelectedChoices list does not re-derive Answer$Risk, leaving the risk computed from the previous selection.
AWS: UpdateAnswer (Smithy: PATCH /workloads/{WorkloadId}/lensReviews/{LensAlias}/answers/{QuestionId}, code 200, output UpdateAnswerOutput{WorkloadId, LensAlias, LensArn, Answer}; SelectedChoices is a list member) derives Answer$Risk (Smithy: Risk enum [UNANSWERED, HIGH, MEDIUM, NONE, NOT_APPLICABLE]) from the current selection. Clearing the selection makes the question unanswered, so the Answer in the 200 response reports Risk UNANSWERED, and the lens review's RiskCounts move that question back into the UNANSWERED bucket.
Emulator: the 200 response reports Risk 'HIGH' — the risk derived from the selection that was just removed; the empty selection is stored but no re-derivation runs.
Why: a client that unanswers a question (a normal review edit) still sees the question reported at its old risk level, so risk dashboards and the review's RiskCounts histogram over-report risk and never converge on the review's own answers.
Fix: the UpdateAnswer handler's risk-derivation step — an empty (or absent) selection must short-circuit to UNANSWERED before any risk rule is applied — and the lens review's RiskCounts aggregation that reads from it.
Traces: wellarchitected.milestone-freezes-answers-while-workload-moves.

Cause 4 of 5: CreateWorkloadShare's enum-violation ValidationException uses the generic framework wording instead of Well-Architected's enum wording.
AWS: CreateWorkloadShare (Smithy: POST /workloads/{WorkloadId}/shares; PermissionType required, target PermissionType enum with values [READONLY, CONTRIBUTOR]; errors include ValidationException httpError 400) refuses an out-of-range PermissionType 400 ValidationException with the JSON-schema style message whose fixed text is '[Validation] [instance value ("' ... '") not found in enum (possible values: ["READONLY","CONTRIBUTOR"])]' — the variable parts being the rejected value taken from the request and the modeled enum value list, rendered comma-separated in double quotes with no spaces.
Emulator: '[Validation] 1 validation error detected: Value <value> at \'permissionType\' failed to satisfy constraint: Member must satisfy enum value set: [READONLY, CONTRIBUTOR]' — the correct code and 400 status, but a message AWS never emits for this class.
Why: a client that matches on AWS's validation text, or shows it verbatim to an operator, sees framework-generated text; the two forms also differ in how the enum list is rendered, so any parse of the permitted values fails.
Fix: the enum-violation renderer in this crate's shared validation layer, on the CreateWorkloadShare input-validation path.

Traces: wellarchitected.share-with-own-account-rejected.

Cause 5 of 5: GetLens serves an imported-but-unpublished (DRAFT) custom lens with 200 instead of refusing it as not published.
AWS: GetLens (Smithy: GET /lenses/{LensAlias}, code 200, output GetLensOutput{Lens}; errors ResourceNotFoundException httpError 404, ValidationException 400) does not retrieve a custom lens that has been imported but never published: it answers 404 ResourceNotFoundException whose message's fixed text is '[ResourceNotFound] LENS with id ' ... ' not found. Lens is not published.', the variable part being the lens id from the request alias. The lens still exists and is still listed by ListLenses(CUSTOM_SELF) with LensStatus DRAFT and LensVersion 'DRAFT'; publishing a version is what makes GetLens succeed.
Emulator: the call succeeds (200 with the draft lens), so import is treated as publication.
Why: a client uses GetLens to decide whether a lens is published yet; a 200 makes an unpublished lens look usable and the publish step gets skipped, and a client that branches on the 404 to publish never does so.
Fix: a lens-status gate in the GetLens handler (refuse a lens whose only version is DRAFT) and the ResourceNotFoundException serialization on that path.
