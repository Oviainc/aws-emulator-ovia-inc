# apigatewayv2__lambda: three more WebSocket checks cannot run — $connect/$disconnect per-route Lambdas, the 401 missing-identity-source short-circuit and body-based route selection all hang on the RFC 6455 upgrade (1 cause)

> _Note: this issue was identified against the code base at commit `c8d80ea15f1454d07f388eb2b932b3a5430349f4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateRoute

## Description
Cause 1 of 1: on a deployed WEBSOCKET-protocol apigatewayv2 stage the client opening handshake never reaches 101 Switching Protocols, so three distinct WebSocket behaviours — per-route $connect/$disconnect Lambda dispatch, the authorizer identity-source short-circuit, and RouteSelectionExpression dispatch from the frame body — are all unobservable. All three checks are blocked at the same step; they are grouped as one root cause because one upgrade path fixes all three.

AWS: recorded behavior only for the handshake (the opening upgrade is the execute-api data plane, not a modelled operation). The modelled surface is apigatewayv2 2018-11-29: Api.ProtocolType=WEBSOCKET with a required RouteSelectionExpression, Route/RouteKey ($connect, $disconnect, $default and custom keys), AWS_PROXY integrations targeting Lambda, Authorizer of type REQUEST with IdentitySource, and Stage. Recorded: (a) the upgrade to the deployed stage answers HTTP/1.1 101 Switching Protocols with Sec-WebSocket-Accept, and the handshake invokes the $connect route's OWN integration with requestContext.eventType == "CONNECT", the handshake query string and the service-minted connectionId; a frame then reaches its route's own Lambda with the SAME connectionId and eventType == "MESSAGE"; a clean client CLOSE invokes the $disconnect route's own Lambda with eventType == "DISCONNECT". (b) With a $connect REQUEST authorizer whose IdentitySource is route.request.querystring.token, an upgrade that OMITS the token is refused with HTTP 401 WITHOUT invoking the authorizer Lambda and without running $connect (the gateway decides from the request alone); the same API with the token present runs the authorizer and upgrades (101). (c) RouteSelectionExpression=$request.body.action dispatches each frame on one socket to the route its action names and thus to that route's own integration, with unknown actions, a frame with no action member and a non-JSON frame all falling back to $default; requestContext.routeKey equals the selected route and the routed body is the frame verbatim.
Emulator: none of the three checks obtains a socket. Each blocks polling for a 101 upgrade against the deployed stage and is cut by the harness at "Check timed out after 60.0s"; the wire shape of that non-101 answer is visible in the same run's apigatewaymanagementapi checks as `b'HTTP/1.1 404 Not Found'`. All control-plane setup before the upgrade (sts, IAM roles, multiple Lambda functions reaching Active, create_api / create_integration / create_route / authorizer / create_deployment / create_stage) completes.
Why: a client relying on AWS behavior gets no WebSocket at all. It cannot verify that lifecycle routes run their own integrations (a wrong-integration dispatch would be silent), it cannot verify that a missing identity source is refused 401 before any Lambda is invoked — an emulator that instead called the authorizer and let it deny would answer 403 and bill/execute a Lambda AWS never invokes — and it cannot verify that body-based route selection reaches the right function, so a misrouted action is indistinguishable from a correct one.
Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer — complete the RFC 6455 handshake (101 + Sec-WebSocket-Accept) on a deployed WEBSOCKET API's stage path instead of falling through to the generic 404 path; then mint the connectionId, evaluate the $connect REQUEST authorizer's IdentitySource against the upgrade request and refuse 401 before invoking anything when it is absent, invoke the $connect/$disconnect routes' own integrations with eventType CONNECT/DISCONNECT, and evaluate RouteSelectionExpression per frame to dispatch to each route's own integration with $default as the fallback.
Related: 20261023T223918Z-apigatewayv2-lambda-all-three-websocket-authorizer-routing-checks.md owns three OTHER apigatewayv2__lambda checks on the same step and does not carry these three replay keys; 20261024T120951Z-apigatewayv2-lambda-an-unmatched-websocket-action-never-reaches.md and 20261025T030504Z-apigatewayv2-lambda-both-websocket-aws-integration-request-template.md likewise cover different checks. A single upgrade fix should close all of them, but none covers these three today.

## Steps to Reproduce
1. Boot the emulator and replay the three apigatewayv2__lambda checks listed in trace_ids from simparity-behavioral-aws-v1.
2. Create an apigatewayv2 API with ProtocolType=WEBSOCKET and RouteSelectionExpression=$request.body.action; create one AWS_PROXY integration per route pointing at its OWN Lambda function; create routes $connect, $disconnect, $default and the custom keys (ping, sendmsg, echo); for the authorizer check add a REQUEST authorizer with IdentitySource=route.request.querystring.token on $connect; create a deployment and a stage.
3. Open a TCP/TLS connection to the stage URL and send an RFC 6455 opening handshake (GET /<stage>[?token=...] with Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key, Sec-WebSocket-Version: 13).
4. Observe the handshake is never answered HTTP/1.1 101 Switching Protocols (the emulator answers 404 Not Found on this path), so each check's poll for a 101 runs out and the harness cuts it at 60 s.
5. Consequently: no $connect/$disconnect invocation with eventType CONNECT/DISCONNECT is ever recorded on a watcher connection; the token-less handshake is never refused 401 (and it cannot be shown that the authorizer Lambda was not invoked); and no frame is ever dispatched by RouteSelectionExpression to its own route's Lambda.
