# acm__elbv2: 3 net-new root causes — an ALB HTTPS listener never presents its ACM certificate on the wire, CreateListener accepts a FAILED certificate with HTTP 200, and the DeleteCertificate in-use message drops "in account <account-id>"

> _Note: this issue was identified against the code base at commit `d08bdc6421dd34ea7f486f80e752180a84c66a0c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateListener

## Description
Three distinct root causes in the ACM <-> ELBv2 integration. Related open filings that do NOT cover any of them: 20261025T210904Z-acm-apigatewayv2-a-regional-custom-domain-never-presents.md (same class of defect, but the API Gateway v2 custom-domain data plane, not an ALB listener), 20261104T055008Z-elbv2-s3-an-https-alb-writes-no-access.md (the ALB access-LOG writer, not TLS termination/certificate presentation), and 20261029T192604Z-acm-certificate-control-plane-refusals-a-valid-import.md (five other ACM refusal messages; the DeleteCertificate in-use message of cause 3 is not among them).

Cause 1 of 3: an ALB HTTPS listener holding an ACM certificate never terminates TLS, so the certificate is never presented on the wire.
AWS: recorded behavior only. An internet-facing application load balancer whose HTTPS:443 listener names an ISSUED ACM certificate and whose default action is a fixed-response reaches State.Code 'active' and then answers an HTTPS request on its DNSName: it completes a TLS handshake (default security policy negotiates TLSv1.2), presents exactly the leaf that was imported into ACM (same serial, same DER bytes, same DNS SANs), and returns the fixed-response status line and MessageBody. Rotating the listener's certificate (ModifyListener / AddListenerCertificates) then makes the newly named leaf the one presented, with no connection refused in between.
Emulator: no HTTPS response is ever produced for the load balancer's DNSName. The happy-path check exhausts its budget ('Check timed out after 60.0s') before any TLS handshake succeeds, and the rotation check fails inside its own wait helper with 'TimeoutError: the HTTPS listener beginning to serve with the pre-rotation certificate: the run budget ended first'. The control plane accepts CreateListener and DescribeListenerCertificates, but nothing listens on the data plane, so the pre-rotation leaf is never observed and the rotation can never be graded.
Why: a client cannot do the one thing an ACM certificate on an ALB exists for — serve TLS under its own name. Every end-to-end flow built on an HTTPS ALB (certificate presentation checks, SNI-based routing, certificate rotation with zero dropped requests, hostname verification against a private trust anchor) is unreachable: a provisioned-but-unconnectable listener is reported to the caller only as a hung connect, not as an error it can branch on.
Fix: the ELBv2 data plane in the elbv2 service crate — the HTTPS listener path that must accept a TCP connection on the listener's port, complete the TLS handshake presenting the leaf (and chain) stored in ACM for the listener's CertificateArn, and run the listener's default action (fixed-response here) — plus the ACM->ELBv2 key-material lookup it needs.
Traces: acm__elbv2.acm-alb-https-listener-serves-the-imported-certificate, acm__elbv2.live-listener-certificate-rotation-swaps-the-presented-leaf-with-no-dropped-request

Cause 2 of 3: CreateListener attaches an ACM certificate in FAILED status (no key material) to an HTTPS listener and answers HTTP 200 instead of refusing it.
AWS: Smithy CreateListener(LoadBalancerArn required, Protocol, Port, Certificates: CertificateList, DefaultActions required) -> CreateListenerOutput models CertificateNotFoundException, UnsupportedProtocolException, InvalidConfigurationRequestException and others, every one a client error at HTTP 400; no success path is modeled for an unusable certificate. Recorded behavior: naming an ACM certificate that never issued (Status FAILED, so it holds no private key) in Certificates is refused with HTTP 400, Error.Code 'UnsupportedCertificate' and Error.Message "The certificate '<CertificateArn>' must have a fully-qualified domain name, a supported signature, and a supported key size." — the fixed text is "The certificate '" / "' must have a fully-qualified domain name, a supported signature, and a supported key size." and the only variable part is the certificate ARN taken verbatim from the request. No listener is created, and the certificate's Status stays FAILED with InUseBy empty.
Emulator: the identical call succeeds with HTTP 200 and returns a Listeners[0] entry (Protocol HTTPS, Port 443, Certificates naming the FAILED certificate), so a listener that can never serve TLS is created and recorded.
Why: this is the gate that tells a deployment its certificate is not usable, at the moment it is attached. Accepting it turns a 400 the caller handles into an ALB that answers HTTPS requests with nothing, diagnosable only from the data plane; infrastructure tooling (CloudFormation, CDK, Terraform) treats the 200 as a successful rollout and proceeds. It also lets a FAILED certificate be marked in use, corrupting ACM's InUseBy accounting and the delete gate of cause 3.
Fix: the certificate-resolution/validation step of the CreateListener handler in the elbv2 service crate — resolve each Certificates[].CertificateArn against ACM and refuse a certificate that is not ISSUED (no usable key material) with HTTP 400 'UnsupportedCertificate' and the message template above, creating no listener and leaving the certificate untouched.
Traces: acm__elbv2.acm-never-issued-certificate-refused-by-an-https-listener-rejected

Cause 3 of 3: the DeleteCertificate ResourceInUseException message omits AWS's " in account <account-id>" clause.
AWS: Smithy DeleteCertificate(CertificateArn required, @length 20..2048, ACM ARN pattern) -> Unit models ResourceInUseException as a client error at HTTP 400. Recorded behavior: deleting a certificate a live HTTPS listener is serving is refused 400 ResourceInUseException with 'Certificate <CertificateArn> in account <account-id> is in use.' — the fixed text is 'Certificate ' / ' in account ' / ' is in use.' around two variable parts: the ARN taken from the request and the account id taken from that ARN's 5th field; the terminating period is part of the fixed text.
Emulator: the status 400 and the code ResourceInUseException are right, but the message is 'Certificate <CertificateArn> is in use.' — the ' in account <account-id>' clause is dropped from the template.
Why: the message is produced from the request by a fixed rule, so the rule is the requirement. ACM's wording names the account that owns the in-use certificate, which is what a caller cleaning up across accounts/regions keys its diagnostics and log-matching on; the emulator's shorter sentence matches no ACM message, so an exact-match assertion or a parser extracting the account from the refusal fails even though the refusal itself is correct.
Fix: the in-use refusal construction in the ACM DeleteCertificate handler — build the message with the ' in account <account-id>' clause from the certificate ARN's account field.
Traces: acm__elbv2.acm-certificate-in-use-by-a-listener-cannot-be-deleted-rejected
