# opensearch: 2 net-new causes — AttachDataSource performs no IAM authorization (permissionless callers get 200), and a non-domain data-source ARN (the account's Glue Data Catalog) settles FAILED

> _Note: this issue was identified against the code base at commit `3bac9b013a04c7643864c8c3bd11f9ae19258a78`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AttachDataSource

## Description
Two independent root causes in the OpenSearch emulator's AttachDataSource implementation, both grounded in failing behavioral checks of service `opensearch`. They are numbered below; a fixer must close BOTH before submitting.

=== Cause 1 of 2: AttachDataSource never authorizes the caller — a principal with no es:* permissions is served HTTP 200 instead of AccessDeniedException ===
Failing checks: opensearch.overly-permissive-attach-data-source-missing-role-rejected, opensearch.overly-permissive-data-source-attach-unauthorized-role-rejected

AWS: Smithy model com.amazonaws.opensearch#AttachDataSource models AccessDeniedException with @httpError 403, documented as "An error occurred because you don't have permissions to access the resource." (same error is modeled on DetachDataSource and ListDataSourceAttachments). Recorded behavior: when the request is signed by a principal that no identity-based policy grants `es:AttachDataSource`, the call is refused HTTP 403 `AccessDeniedException` and no attachment record is created (proved by an independent ListDataSourceAttachments read, not by the refused call's own response). The message is AWS's standard identity-based-denial template; its fixed text is `User: `, ` is not authorized to perform: `, ` on resource: `, and ` because no identity-based policy allows the ` + `<action>` + ` action`, and its variable parts come from the request's signing identity and the targeted resource: the caller principal ARN (`arn:aws:iam::<account>:user/<user-name>` for an IAM user, `arn:aws:sts::<account>:assumed-role/<role-name>/<session-name>` for an assumed role), the action `es:AttachDataSource`, and the resource `arn:aws:es:<region>:<account>:domain/*`. The authorization decision precedes any resource lookup, so it is returned even when the named data source does not exist.

Emulator: the call SUCCEEDS. Both a brand-new IAM user with no attached policies and an assumed role whose only policy is its trust policy receive HTTP 200 with a minted `attachmentId`, the application `id`/`arn`, the submitted `dataSourceArn` and `status` = `PENDING`. services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/attach_data_source.rs never reads the request's signing identity at all (`let _ = ctx;` on the first line of `handle`), so the `AccessDeniedException` variant declared in `AttachDataSourceErrorModeled` is never constructed on any path. The mutation also lands: the unauthorized attempt leaves a real attachment record behind.

Why: a client relying on AWS's behavior gets no authorization boundary at all. Negative tests that assert an unprivileged principal is denied pass vacuously against the emulator and then fail against real AWS; worse, code paths that deliberately probe with reduced credentials to discover whether an action is permitted are told "yes" and go on to mutate state that real AWS would have protected. The 403/AccessDeniedException class is simply unreachable, so no SDK error handler for it can ever be exercised.

Fix: authorization in the AttachDataSource handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/attach_data_source.rs) — the handler must resolve the caller principal from the request context/SigV4 credential, evaluate it against the identity-based policies the IAM emulator holds, and return the modeled AccessDeniedException (403) with the template above BEFORE the application lookup or any store mutation. If the emulator has a shared authorization seam, this operation must be wired into it rather than growing a private check.

Traces: see Traces section.

=== Cause 2 of 2: an attachment whose data-source ARN is not an OpenSearch domain ARN (e.g. the account's Glue Data Catalog) settles to FAILED instead of PENDING/ATTACHED ===
Failing check: opensearch.attach-detach-data-source-race-converges-consistent

AWS: Smithy model com.amazonaws.opensearch#AttachDataSource documents the lifecycle: "If both the application and the data source are active, the attachment completes immediately with a status of ATTACHED. Otherwise, the operation returns PENDING and completes the attachment automatically once both become active. If the attachment cannot be completed, its status becomes FAILED." `DataSourceAttachmentStatus` is the enum PENDING | ATTACHED | FAILED, and the output member documents FAILED as "attachment timed out or encountered a non-retryable error". Recorded behavior: attaching the caller's own Glue Data Catalog ARN `arn:aws:glue:<region>:<account>:catalog` — a resource that always exists for an account — to an ACTIVE application yields an attachment that is PENDING and completes to ATTACHED; it is never reported FAILED. Racing two AttachDataSource and two DetachDataSource calls on the same (application, dataSourceArn) pair converges to AT MOST ONE attachment entry, and any surviving entry reads PENDING or ATTACHED.

Emulator: the race converges to exactly one entry — the arity contract holds — but that entry settles to `{'attachmentId': 'dsa-...', 'dataSourceArn': 'arn:aws:glue:<region>:<account>:catalog', 'status': 'FAILED'}`. The cause is visible in the handler: `store.domain_of_arn(&input.data_source_arn)` only resolves `arn:aws:es:...:domain/<name>` ARNs, and every other ARN takes the `None` branch, which schedules the attachment to settle as the non-retryable FAILED a provisioning span later. Any data-source ARN that is not an OpenSearch domain of this account is therefore condemned to FAILED regardless of whether the resource exists.

Why: a client that attaches a Glue Data Catalog (the direct-query data-source case) to an OpenSearch application sees the attachment go FAILED and, per the handler's own idempotency rule, a FAILED attachment is "neither attached nor pending", so a retry mints a fresh record that fails again — an unbreakable loop. Application/data-source flows built on non-domain data sources can never reach ATTACHED, and a caller polling for the documented PENDING→ATTACHED transition times out on a status AWS would not have produced.

Fix: the data-source resolution in the AttachDataSource handler and the attachment settlement it feeds (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/attach_data_source.rs — the `domain_of_arn(...)` / `attachment_outcome(active_at)` decision, and `settle_for_attachments` in src/state.rs). Resolution must recognize the data-source kinds AWS accepts, not domain ARNs alone: an ARN naming a resource that exists for the account (the account's Glue Data Catalog among them) must be treated as an active data source so the attachment completes to ATTACHED, with FAILED reserved for an attachment that genuinely cannot complete.

Traces: see Traces section.
