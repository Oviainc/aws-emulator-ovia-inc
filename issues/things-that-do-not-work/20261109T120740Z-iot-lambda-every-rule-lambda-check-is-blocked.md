# iot__lambda: every rule→Lambda check is blocked by the AWS-shaped data-plane address DescribeEndpoint publishes, and CFN-deployed rules never invoke their Lambda even on the positive control (2 causes)

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEndpoint

## Description
Two net-new root causes under the iot__lambda heading.

Cause 1 of 2: iot DescribeEndpoint(endpointType="iot:Data-ATS") publishes an AWS public ATS hostname the emulator does not serve, so the message that is supposed to trigger each rule can never be published.
AWS: Smithy (service-com-amazonaws-iot-awsiotservice): DescribeEndpoint — GET /endpoint, input endpointType (httpQuery, @length 0..128), output endpointAddress : EndpointAddress, modeled errors InternalFailureException (500), InvalidRequestException (400), ThrottlingException (400), UnauthorizedException (401). The returned address is the caller's own data-plane host, served by AWS on 443 for the HTTPS Publish/shadow API; every iot-data client is expected to be pointed at it because the control-plane host refuses data-plane operations with UnknownOperationException.
Emulator: DescribeEndpoint answers 200 with a hostname of AWS's public form ("<prefix>-ats.iot.<region>.amazonaws.com"), which is not one of the emulator's own hosts and which it does not listen on. Replay refuses to follow it — "endpoint_url was given https://<prefix>-ats.iot.<region>.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://<own host>:<port>/<path>" — so all 25 checks below stop at endpoint discovery: no Publish, no rule evaluation, no Lambda invoke, no shadow read, and the negative cases (missing lambda:InvokeFunction permission, wrong ARN, wrong SourceArn, untrusted role, disabled rule) are never exercised either.
Why: the rules-engine → Lambda contract is only observable by publishing to a topic through the data-plane endpoint discovered via DescribeEndpoint. A client doing exactly that is sent off the emulator, so an entire integration surface (rule action dispatch, error actions, republish chains, SQL projection, per-action permission enforcement) is unverifiable through the supported discovery path.
Fix: the iot DescribeEndpoint handler's endpoint-address construction in the iot service crate — serve the emulator's own host (and port) for the requested endpointType instead of a synthesized amazonaws.com name.

Cause 2 of 2: a CloudFormation-deployed AWS::IoT::TopicRule with a Lambda action and a matching AWS::Lambda::Permission never invokes its function, so even the in-template positive control produces no invocation.
AWS: recorded behavior only — the model carries no dispatch semantics. The recording shows one stack declaring two identical rule→function wirings that differ only in whether the AWS::Lambda::Permission granting lambda:InvokeFunction to iot.amazonaws.com is present; on AWS the granted wiring (the control) invokes its function and the function records its marker, while the ungranted one does not. The discriminating behavior is that the rules engine evaluates the rule's SQL on a published message and calls lambda:Invoke for the action's FunctionArn when, and only when, a resource policy permits iot.amazonaws.com.
Emulator: neither wiring invokes anything. The control asserts first and fails with AssertionError "control rule (with permission) never invoked its lambda" (and, in the wrong-ARN check, AssertionError "control rule (valid arn + permission) never invoked"), so the emulator cannot tell a permitted action from a denied one — the negative result is indistinguishable from a rules engine that never dispatches at all.
Why: a client that deploys rule→Lambda wiring by template sees the stack reach CREATE_COMPLETE and then no message is ever delivered to the function; a missing or wrong permission produces the same silence as a correct one, so permission-boundary behavior cannot be developed or tested against the emulator.
Fix: the iot rules-engine dispatch path (topic-rule action execution for the lambda action, including the resource-policy check against the function's permissions) and its wiring to resources created by the CloudFormation AWS::IoT::TopicRule / AWS::Lambda::Permission providers.
Related but not covering: 20261107T185434Z-iot-lambda-the-iot-rules-engine-never-dispatches.md describes the rules engine never dispatching lambda/republish actions; it does not carry these two replay keys (the report leaves them unowned), so they are filed here.

## Evidence
Cause 1 — expected: DescribeEndpoint(endpointType='iot:Data-ATS') -> 200 endpointAddress = a host the emulator serves, then iot-data Publish to the rule's topic -> 200 and the Lambda records its marker. Actual: 200 with the AWS public ATS form and simparity.published.PublishedUrlRejected: "endpoint_url was given https://<prefix>-ats.iot.<region>.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". 25 checks abort at that point.

Cause 2 — expected: for the stack's granted wiring, the published message reaches FnB and its marker is observable; for the ungranted/wrong-ARN wiring, no invocation. Actual: AssertionError "control rule (with permission) never invoked its lambda" (cfn-deploy-iot-rule-lambda-missing-permission-negative, line 172) and AssertionError "control rule (valid arn + permission) never invoked" (cfn-deploy-iot-rule-wrong-lambda-arn-negative, line 152) — no invocation on either side of the comparison.
