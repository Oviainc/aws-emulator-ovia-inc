# S3 Object Lock is not enforced: retained and legal-held versions are deleted with 204, BypassGovernanceRetention is never authorized, and GetObject reports no lock state (4 causes)

> _Note: this issue was identified against the code base at commit `d9d92e1bb4d26644359d4701433c452d79a4d930`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteObject

## Description
Four distinct net-new root causes in S3's Object Lock (WORM) enforcement path. Each is numbered with its own failing check ids; all four must be closed before this issue is submitted.

These eight checks were previously listed as examples of Cause 4 of the open issue 20261025T032458Z-s3-object-plane-10-root-causes-conditional-requests.md ("writes to a versioning-enabled bucket return no version id", signature `KeyError: 'VersionId'`). That signature is gone: PutObject now returns `x-amz-version-id` and the checks get past the version-id step, so they now fail further downstream on object-lock ENFORCEMENT, which that issue does not describe. This issue carries those net-new causes; it does not reopen or replace that issue, which remains open for its other causes.

Cause 1 of 4: Object Lock retention is stored but never consulted by DeleteObject — a version-scoped delete of a version under an active retention period succeeds.
AWS: Smithy s3#PutObjectRetention (PUT /{Bucket}/{Key+}?retention, httpError code 200) takes an ObjectLockRetention payload with Mode (GOVERNANCE|COMPLIANCE) and RetainUntilDate, and s3#DeleteObject (DELETE /{Bucket}/{Key+}, success code 204) takes VersionId (@httpQuery versionId) and BypassGovernanceRetention (@httpHeader x-amz-bypass-governance-retention). While now < RetainUntilDate, AWS refuses a version-scoped DeleteObject of that version with HTTP 403 and S3's authorization error: code `AccessDenied`, message `Access Denied` (that message is entirely fixed text for this class — S3 does not interpolate the bucket, key, version id, mode or expiry into it). DeleteObject models no operation-specific errors, so this generic authorization refusal is the only shape AWS can use. The delete only succeeds once the window has lapsed, or (GOVERNANCE only) with x-amz-bypass-governance-retention: true held by a caller allowed s3:BypassGovernanceRetention.
Emulator: the delete is accepted. The response is HTTP 204 carrying x-amz-version-id for the version that was supposed to be protected, e.g. `{'ResponseMetadata': {'HTTPStatusCode': 204, 'HTTPHeaders': {'x-amz-version-id': ...}}, 'VersionId': ...}` — so the retention record is written by PutObjectRetention and then ignored on the delete path, and the protected version is really removed.
Why: a client that uses Object Lock for immutability/compliance gets a silent no-op. Code written to handle the 403 never sees it, and data the caller believes is undeletable for the length of the retention window is destroyed by an ordinary version-scoped delete — the single guarantee the feature exists to provide.
Fix: the DeleteObject handler's object-lock pre-check and the per-version retention state it must read (the state PutObjectRetention writes), including the now < RetainUntilDate comparison and the GOVERNANCE-vs-COMPLIANCE distinction.
Traces: s3.delete-object-under-retention-rejected, s3.object-retention-governance-blocks-delete, s3.object-retention-governance-bypass-delete, s3.object-retention-until-date-enforces-window

Cause 2 of 4: an Object Lock legal hold is not enforced on DeleteObject at all, with or without a governance bypass.
AWS: Smithy s3#PutObjectLegalHold sets ObjectLockLegalHoldStatus ON|OFF on a specific version; a legal hold has no expiry and is INDEPENDENT of any retention period. While the hold is ON, AWS refuses the version-scoped DeleteObject of that version with HTTP 403, code `AccessDenied`, message `Access Denied` (fixed text, no variable parts), and keeps refusing it even when x-amz-bypass-governance-retention: true is sent, because the bypass applies only to GOVERNANCE retention and never to a legal hold. The delete succeeds only after PutObjectLegalHold sets the status OFF.
Emulator: both legs are accepted. A plain version-scoped delete of a held version answers HTTP 204 with the version id (`expected a ClientError, but the call succeeded and returned {... 'HTTPStatusCode': 204 ...}`), and a bypass delete of a version that is under a GOVERNANCE retention AND a legal hold also answers HTTP 204 (`a bypass DeleteObject of a GOVERNANCE-retained version that is also under legal hold unexpectedly SUCCEEDED (HTTP 204) where real AWS refuses it`). The legal-hold flag is never read on the delete path.
Why: the one protection AWS documents as un-bypassable is bypassable here, so a litigation/regulatory hold protects nothing and an operator with only the governance-bypass permission can erase held evidence.
Fix: the DeleteObject handler's object-lock pre-check — the legal-hold flag must be evaluated separately from retention, and must be evaluated AFTER and independently of the BypassGovernanceRetention branch so a bypass cannot clear it.
Traces: s3.delete-object-under-legal-hold-rejected, s3.deep-s3-immutability-legal-hold-blocks-bypass-independent-of-retention-rejected

Cause 3 of 4: BypassGovernanceRetention is honoured without authorizing the caller for s3:BypassGovernanceRetention.
AWS: s3#DeleteObject's BypassGovernanceRetention header is a privileged request, not a self-service override: AWS evaluates s3:BypassGovernanceRetention for the caller and, when the caller is denied it (explicitly or by absence of an allow), refuses the delete with HTTP 403, code `AccessDenied`, message `Access Denied` (fixed text), leaving the GOVERNANCE-retained version in place.
Emulator: the header alone is sufficient. A caller carrying an explicit Deny on s3:BypassGovernanceRetention gets HTTP 204 and the retained version is removed — `a bypass DeleteObject by a caller explicitly denied s3:BypassGovernanceRetention unexpectedly SUCCEEDED (HTTP 204) where real AWS refuses it`. No authorization decision is taken for the bypass at all.
Why: the privilege separation between "may delete objects" and "may override governance retention" does not exist, so every principal with DeleteObject is effectively a compliance administrator and the two-person-control posture AWS supports cannot be modelled.
Fix: the DeleteObject handler's BypassGovernanceRetention branch must run the request through the authorization layer for the s3:BypassGovernanceRetention action before it is allowed to clear GOVERNANCE retention.
Traces: s3.deep-s3-immutability-governance-bypass-without-permission-denied

Cause 4 of 4: GetObject reports no Object Lock state for a locked version.
AWS: Smithy s3#GetObject output declares ObjectLockMode (@httpHeader x-amz-object-lock-mode, enum), ObjectLockRetainUntilDate (@httpHeader x-amz-object-lock-retain-until-date, timestampFormat date-time) and ObjectLockLegalHoldStatus (@httpHeader x-amz-object-lock-legal-hold, enum). After PutObjectRetention sets Mode=COMPLIANCE on a version, a GetObject of that version reports ObjectLockMode COMPLIANCE and echoes the stored RetainUntilDate.
Emulator: the response omits those headers, so the client reads nothing back — `GetObject on the locked version reported ObjectLockMode None`.
Why: a client cannot discover whether an object is locked, under which mode, or until when, so it cannot decide whether a delete or a weakening re-put will be refused, and audit tooling that reads lock posture off the object sees an unlocked object.
Fix: the GetObject (and HeadObject) response serializer must emit the three object-lock headers from the per-version lock state, and that state must be the record PutObjectRetention/PutObjectLegalHold write.
Traces: s3.deep-s3-immutability-compliance-lock-extends-and-overwrites-but-weakening-rejected

## Steps to Reproduce
Boot the emulator and replay exactly the check ids in trace_ids. Minimal manual repros:
(1) Cause 1 — CreateBucket with ObjectLockEnabledForBucket=true; PutObject a key and keep its VersionId; PutObjectRetention(VersionId, Retention={Mode: GOVERNANCE, RetainUntilDate: now+1h}); DeleteObject(Bucket, Key, VersionId=that version) with no bypass header. Emulator: 204 and the version is gone. AWS: 403 AccessDenied / `Access Denied`, version intact. Repeat with Mode=COMPLIANCE for the same result.
(2) Cause 2 — same setup, but PutObjectLegalHold(VersionId, LegalHold={Status: ON}); then DeleteObject(VersionId) and again DeleteObject(VersionId, BypassGovernanceRetention=True). Both must be 403 AccessDenied; both are 204.
(3) Cause 3 — put GOVERNANCE retention on a version, then issue DeleteObject(VersionId, BypassGovernanceRetention=True) as a principal carrying an explicit Deny on s3:BypassGovernanceRetention. Must be 403 AccessDenied; is 204.
(4) Cause 4 — put COMPLIANCE retention on a version, then GetObject(Bucket, Key, VersionId=that version) and read ObjectLockMode / ObjectLockRetainUntilDate from the response. Must report COMPLIANCE and the stored date; both are absent.
