# AppSync: no IAM deny gate on FlushApiCache/ListDomainNames, ListDomainNames still a NotImplemented stub, CreateDomainName accepts refused certificates, Event API realtime endpoint 404s, UpdateApi event-config message, and valueless CFN stack Outputs

> _Note: this issue was identified against the code base at commit `910698ab7b22be6d08fbb15c4abd76821047ddd2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FlushApiCache

## Description
Six distinct net-new root causes outside the error-wording family. 6 causes in this issue; all six must be closed before submitting. Open issues that look adjacent but carry none of the replay keys below are named per cause.

=== Cause 1 of 6: FlushApiCache and ListDomainNames are not gated by identity-based IAM, so an explicit Deny is never enforced ===
AWS: Smithy (appsync) FlushApiCache — DELETE /v1/apis/{apiId}/FlushCache — and ListDomainNames — GET /v1/domainnames, which models AccessDeniedException|403 explicitly. Recorded behavior: a principal whose identity policy carries an explicit Deny on appsync:FlushApiCache (resp. appsync:ListDomainNames) is refused 403 AccessDeniedException with the IAM-standard message 'User: <principal arn> is not authorized to perform: <appsync action> on resource: <resource arn> with an explicit deny in an identity-based policy' — fixed text is 'User: ', ' is not authorized to perform: ', ' on resource: ', ' with an explicit deny in an identity-based policy'; the variable parts are the caller's session ARN, the action, and the resource ARN derived from the request (arn:aws:appsync:<region>:<account>:/v1/apis/<apiId>/FlushCache for FlushApiCache, arn:aws:appsync:<region>:<account>:* for ListDomainNames).
Emulator: no AccessDeniedException is ever produced. Both checks poll for up to 60s for the deny to take effect and time out, so the denied principal is served exactly like the unrestricted one. This is the same class as the open issues 20261027T222245Z-appsync-tagging-operations-are-not-gated-by-identity.md, 20261027T010308Z-appsync-listapis-and-listgraphqlapis-are-not-gated-by.md and 20261025T022306Z-appsync-graphql-api-control-plane-operations-are-not.md, but those name other operations and do not carry these two replay keys.
Why: an explicit Deny is the strongest authorization control AWS offers; a cache flush (data-visibility-affecting) and the account's domain-name inventory are served to a principal the account has explicitly forbidden. Any policy test or least-privilege gate run against the emulator passes while the real deployment would refuse.
Fix: the request authorization layer must evaluate identity-based policies for these operations' actions before the FlushApiCache and ListDomainNames handlers run, and produce 403 AccessDeniedException with the IAM explicit-deny message.
Traces: appsync.access-denied-flush-api-cache, appsync.access-denied-list-domain-names.

=== Cause 2 of 6: ListDomainNames answers NotImplemented, so its pagination-token validation is unreachable ===
AWS: Smithy (appsync) ListDomainNames — GET /v1/domainnames, nextToken @length 1-65536 @pattern ^[\\S]+$, maxResults 0-25, output domainNameConfigs + nextToken; modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. Recorded behavior: a nextToken that is not a token this service issued is refused 400 BadRequestException.
Emulator: the call returns the scaffold error 'NotImplemented' ('operation ListDomainNames is scaffolded but not implemented in this emulator'), an error code AppSync does not model, so no pagination behavior exists at all. The suite's auto-filed stub issue for ListDomainNames (and the open issue 20261024T032443Z-appsync-control-plane-fidelity-domain-name-operations-unimplemented.md) describe the stub, but neither carries these two replay keys, so the token-validation contract they pin stays unverified.
Why: callers enumerating custom domain names get an unmodeled error instead of a page, and no client can detect an invalid continuation token.
Fix: the ListDomainNames handler (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/list_domain_names.rs) — implement listing plus nextToken validation refusing unknown tokens with BadRequestException.
Traces: appsync.list-domain-names-invalid-next-token-rejected, appsync.list-domain-names-invalid-pagination-token-rejected.

=== Cause 3 of 6: CreateDomainName accepts certificates AWS refuses on provenance ===
AWS: Smithy (appsync) CreateDomainName — POST /v1/domainnames, required domainName (@pattern ^(\\*[\\w\\d-]*\\.)?([\\w\\d-]+\\.)+[\\w\\d-]+$) and certificateArn (@pattern ^arn:[a-z-]*:(acm|iam):...:(certificate|server-certificate)/...$); modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. Recorded behavior: a certificate that is not Amazon-issued for that domain (a self-signed or ImportCertificate-sourced certificate) is refused 400 BadRequestException; only an ACM-issued certificate covering the domain is accepted.
Emulator: CreateDomainName SUCCEEDS with 200 and returns a domainNameConfig for both a self-signed-provenance certificate and a CA-signed-but-not-Amazon-issued one. The open issue 20261027T212657Z-appsync-custom-domain-names-createdomainname-performs-no-certificate.md describes this defect for other checks and does not carry these two replay keys.
Why: an overly-permissive boundary — a client believes it has provisioned a working custom domain whose certificate real AppSync would never accept, and the failure only appears at deploy time against AWS.
Fix: certificate-provenance validation in the CreateDomainName handler (resolve certificateArn against the ACM/IAM certificate state and refuse non-Amazon-issued or non-matching certificates with BadRequestException).
Traces: appsync.concurrent-update-domain-name, appsync.disassociate-api-without-prior-association-rejected.

=== Cause 4 of 6: UpdateApi's invalid event-config auth-mode refusal uses non-AWS wording ===
AWS: Smithy (appsync) UpdateApi — POST /v2/apis/{apiId}, required apiId/name/eventConfig, models BadRequestException|400. Recorded behavior: an eventConfig whose connectionAuthModes names an auth type that is not among the api's configured authProviders is refused 400 BadRequestException with the fixed message 'Event API configuration connect auth contains an invalid auth type.'
Emulator: 400 BadRequestException with 'connectionAuthModes specifies authorization mode AWS_LAMBDA, which is not configured as an authorization provider for this API.' — a different sentence that also echoes the submitted auth type.
Why: the refusal class is right but its message is not AWS's; Event-API configuration tooling that distinguishes the connect-auth error from the publish/subscribe-auth error by message cannot.
Fix: the eventConfig auth-mode validation in the UpdateApi handler (message text per auth-mode slot).
Traces: appsync.update-api-invalid-event-config-rejected.

=== Cause 5 of 6: the Event API realtime WebSocket endpoint rejects the handshake with 404 ===
AWS: recorded behavior only (the realtime protocol is not in the Smithy model). An Event API's Api$dns REALTIME host serves a WebSocket upgrade for the graphql-ws/appsync-event protocol: the handshake returns 101 Switching Protocols, the client receives connection_ack, can subscribe to a channel of a created ChannelNamespace, and events published over the HTTP data plane are delivered on that subscription.
Emulator: the WebSocket handshake against the advertised REALTIME endpoint answers 'HTTP/1.1 404 Not Found', so no connection, subscription or delivery is possible even though CreateApi advertised the dns.REALTIME host. The open issue 20261027T015425Z-appsync-event-api-has-no-data-plane-behind.md describes the missing Event-API data plane for other checks and does not carry this replay key.
Why: the control plane hands the client a realtime endpoint that does not exist; pub/sub applications cannot run at all, and the 404 (rather than a protocol error) gives no diagnosis.
Fix: the Event API realtime data-plane listener and its routing from the advertised Api$dns REALTIME host, plus channel subscribe/publish delivery.
Traces: appsync.e2e-event-api-publish-subscribe-flow.

=== Cause 6 of 6: DescribeStacks returns Outputs entries without OutputValue for AppSync deploys ===
AWS: recorded behavior only (the CFN resource registry is not in the Smithy model). For a stack reporting StackStatus=CREATE_COMPLETE, DescribeStacks returns every template Output with both OutputKey and OutputValue populated, with Ref/Fn::GetAtt (e.g. AWS::AppSync::GraphQLApi GraphQLUrl/ApiId, AWS::Cognito::UserPool ids) already resolved.
Emulator: the stack reaches CREATE_COMPLETE but Outputs entries carry OutputKey and no OutputValue, so every client building {o['OutputKey']: o['OutputValue']} dies with KeyError: 'OutputValue'. This is the same root cause as Cause 1 of the open issue 20261024T032443Z-appsync-cloudformation-deploys-of-appsync-templates-diverge-valueless-stack.md, but that issue's replay keys cover a different set of checks; the eleven checks listed below still fail and are not re-run by it.
Why: no deployed endpoint or id can be retrieved from a stack, so every downstream data-plane step (query the GraphQL URL, authenticate against the user pool, invoke a resolver) is unreachable, and a stack that reports CREATE_COMPLETE while handing back valueless outputs hides the problem from the caller.
Fix: the CloudFormation output/intrinsic-resolution step of stack creation and the DescribeStacks output serializer — an Output must not be emitted without a resolved value, and an unresolvable resource attribute must fail the stack.
Traces: appsync.deploy-api-key-cfn-grants-access, appsync.deploy-api-key-cfn-grants-data-plane-access, appsync.deploy-function-cfn-pipeline-resolver-invocable, appsync.deploy-graphql-api-cfn-behavioral, appsync.deploy-resolver-cfn-insufficient-iam-permission-rejected, appsync.deploy-resolver-cfn-pipeline-executes, appsync__cognito-idp__dynamodb.deploy-appsync-ddb-cognito-stack-positive, appsync__cognito-idp__dynamodb.deploy-appsync-ddb-missing-datasource-role-negative, appsync__cognito-idp__dynamodb.deploy-appsync-multi-datasource-pipeline-positive, appsync__cognito-idp__dynamodb.deploy-appsync-schema-resolver-mapping-positive, appsync__cognito-idp__dynamodb.deploy-cognito-userpool-client-appsync-auth-config-negative.
