# CloudTrail page-size and query-id refusals diverge: LookupEvents refuses an over-maximum MaxResults instead of clamping, GetQueryResults answers the wrong error class, CancelQuery/DescribeQuery resolve the store before the QueryId, and AddTags' tag-limit message is not the service's

> _Note: this issue was identified against the code base at commit `27d60cb41c89860474fb4eac178b022e94c750b0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
LookupEvents

## Description
FOUR distinct causes in this issue; all 4 must be closed before submitting. They are independent control-plane refusal divergences in cloudtrail, each with its own failing check.

Cause 1 of 4 - LookupEvents refuses a MaxResults above the modelled maximum instead of accepting it and clamping the page.
AWS: Smithy LookupEvents.MaxResults targets MaxResults with @range {min 1, max 50}; the operation is @paginated (inputToken/outputToken NextToken, items Events, pageSize MaxResults) and models InvalidMaxResultsException (client, httpError 400, awsQueryError InvalidMaxResults). Recorded behavior (measured by the check against real AWS, us-west-2 2026-09-07): MaxResults=51, 52, 100, 1000 and 1001 were ALL accepted with HTTP 200, each returning at most 50 events plus a NextToken; InvalidMaxResultsException was not returned for any of them. The ceiling is enforced on the RESPONSE (a clamp), not on the request.
Emulator: the call is refused 400 InvalidMaxResultsException, message (example) "The limit at 'maxResults' is not valid: it must have value less than or equal to 50." The refusal is produced before the handler runs by the service's pre-dispatch validation seam, which treats every page-size member as a range-checked input.
Why: SDK paginators and clients send whatever page size the caller configured; against the emulator any value above 50 is a hard 400 where AWS pages normally, so pagination and NextToken stability are unreachable and audit history cannot be walked at all by such a client.
Fix: the request-validation seam must not enforce LookupEvents' MaxResults upper bound - LookupEvents must answer 200 and clamp the page to 50 with a NextToken (the handler already clamps). Related open issue 20261024T114720Z-cloudtrail-control-plane-fidelity-gettrailstatus-omits-its-deprecated.md records this check under its Cause 3 for the earlier form of the bug (the refusal was ValidationException then; it is now the modelled InvalidMaxResultsException), so its recorded replay key no longer matches this failure - the refusal itself is unchanged and must be removed, not re-coded.
Traces: cloudtrail.lookup-events-max-results-bound-and-token-stability.

Cause 2 of 4 - GetQueryResults refuses an out-of-range MaxQueryResults with InvalidMaxResultsException where AWS answers ValidationException.
AWS: Smithy GetQueryResults.MaxQueryResults targets MaxQueryResults with @range {min 1, max 1000}, and the operation DOES model InvalidMaxResultsException (client, httpError 400). Recorded behavior (measured by the check against real AWS): the service nonetheless answers the generic ValidationException/400 for this field - MaxQueryResults=1001 gives "1 validation error detected: Value at 'maxQueryResults' failed to satisfy constraint: Member must have value less than or equal to 1000" and MaxQueryResults=0 the matching greater-than-or-equal-to-1 clause; the modelled exception was not observed. The message is built from the request (member + violated bound), so that construction is the requirement, and the refusal precedes the QueryId existence check (an in-range call on a nonexistent QueryId correctly yields QueryIdNotFoundException, which the emulator already matches).
Emulator: 400 InvalidMaxResultsException for MaxQueryResults=1001.
Why: a client that branches on ValidationException to repair a bad page size never takes that branch, and generic AWS parameter-validation handling (which keys on ValidationException for every service) does not fire.
Fix: the page-size validation seam must classify an out-of-range MaxQueryResults on GetQueryResults as the generic ValidationException envelope with the member/bound clause, i.e. the page-size member must not be routed to the modelled InvalidMaxResults refusal for this operation (file citation: services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/service.rs, PAGE_SIZE_MEMBERS / max_results_refusal / ModelledRefusal::InvalidMaxResults).
Traces: cloudtrail.get-query-results-max-results-out-of-range-rejected.

Cause 3 of 4 - CancelQuery and DescribeQuery answer EventDataStoreNotFoundException for an unknown QueryId even when the request names no event data store at all.
AWS: Smithy marks CancelQueryRequest.EventDataStore and DescribeQueryRequest.EventDataStore deprecated ("EventDataStore is no longer required by CancelQueryRequest" / "... DescribeQueryRequest"); QueryId is required on CancelQuery. Both operations model QueryIdNotFoundException (client, httpError 404, awsQueryError QueryIdNotFound) and EventDataStoreNotFoundException (404). Recorded behavior (measured by the check against real AWS): with only a well-formed but never-issued QueryId supplied, CancelQuery is refused QueryIdNotFoundException - and so is DescribeQuery on the same id; two CancelQuery calls fired concurrently at that id both resolve to that same rejection. The query id is what these operations resolve on; the deprecated store member is not.
Emulator: both answer EventDataStoreNotFoundException (message, as an example, "The event data store was not found."). The handler resolves a store before the query id and, with no EventDataStore member given, falls back to "does this Region hold any event data store at all" - since CreateEventDataStore cannot be provisioned, that is always false, so a QueryId can never be reported as not found (file citation: services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/cancel_query.rs, the store_resolved / has_event_data_store_in branch ahead of store.query(...), and the same precedence in ops/describe_query.rs).
Why: a client polling or cancelling a query id it holds cannot distinguish "no such query" from "no such store", and retry/cleanup logic keyed on QueryIdNotFoundException never fires.
Fix: CancelQuery's and DescribeQuery's handlers must resolve QueryId first and refuse with QueryIdNotFoundException when it names no query, and must not require any event data store to exist when the deprecated EventDataStore member is absent. Related open issue 20261024T114720Z-cloudtrail-control-plane-fidelity-gettrailstatus-omits-its-deprecated.md covers the same inversion under its Cause 5 for a DIFFERENT check (cloudtrail.query-ops-reject-unknown-event-data-store, which passes an explicit nonexistent store ARN); it does not carry this check's key, and this failure shows the inversion also applies when no store member is sent at all.
Traces: cloudtrail.cancel-query-conflict-when-already-finished.

Cause 4 of 4 - AddTags' tag-limit refusal carries a message the service does not use.
AWS: Smithy AddTags models TagsLimitExceededException (client, httpError 400, awsQueryError TagsLimitExceeded), documented as "The number of tags per trail, event data store, dashboard, or channel has exceeded the permitted amount. Currently, the limit is 50." Recorded behavior (measured by the check against real AWS): adding 51 tags to a trail already carrying one is refused TagsLimitExceededException/400 with the service's fixed sentence for that rule - "The resultant tag set must not have more than 50 user tags." - and the resource's existing tags are left unchanged. The rule producing the text is known (resultant tag set above 50 user tags), so the constant sentence is the requirement; the status and code the emulator already matches.
Emulator: the code and status are right but the message is built locally from the request: "TagsList carries 51 tags; the limit is 50 tags per resource" (file citation: services/service-com-amazonaws-cloudtrail-cloudtrail-20131101/src/ops/add_tags.rs, the TAGS_PER_RESOURCE_LIMIT request-size check and the post-merge check below it).
Why: consumers that surface or assert the service's refusal text (operator runbooks, tag reapers, test suites pinned to AWS messages) see a different sentence, and the emulator's wording also claims the request size rather than the resultant set is what AWS limits.
Fix: the AddTags handler's tag-limit refusal (both the request-size and the post-merge path) must word TagsLimitExceededException as the service does for this rule, independent of the submitted count.
Traces: cloudtrail.op-contract-add-tags.

Count, stated plainly: FOUR causes - 1 LookupEvents MaxResults clamp, 2 GetQueryResults error class for MaxQueryResults, 3 CancelQuery/DescribeQuery QueryId precedence, 4 AddTags tag-limit message. All four must be closed.
