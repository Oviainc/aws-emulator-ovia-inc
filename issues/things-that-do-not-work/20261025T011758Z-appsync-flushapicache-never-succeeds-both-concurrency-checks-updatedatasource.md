# AppSync: FlushApiCache never succeeds (both concurrency checks), UpdateDataSource diagnoses the wrong missing member for a lambdaConfig-less retype, and an AppSync+Cognito+DynamoDB CFN stack ends CREATE_FAILED

> _Note: this issue was identified against the code base at commit `2c888af5aa33aca2a1e4835e22187ff259bac9bc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FlushApiCache

## Description
Three distinct net-new root causes surfaced by the behavioral replay against the AppSync emulator. 3 causes in this issue; all three must be closed before submitting.

=== Cause 1 of 3: FlushApiCache never returns success, so neither of its concurrency semantics can be exercised ===
AWS: Smithy (appsync) `FlushApiCache` — DELETE /v1/apis/{apiId}/FlushCache, input `apiId` (required, httpLabel), EMPTY output shape, HTTP success code 200; modeled errors BadRequestException|400, ConcurrentModificationException|409, InternalFailureException|500, NotFoundException|404, UnauthorizedException|401. Recorded behavior (the two checks' own docstrings, measured against real AWS): FlushApiCache has no state to arbitrate, so (a) two simultaneous FlushApiCache calls on the same api BOTH succeed with 200 — neither is refused with ConcurrentModificationException — and (b) a FlushApiCache racing an UpdateApiCache on the same api also succeeds alongside it, the update's new `ttl` persists, and the cache settles back to status AVAILABLE with a further flush still succeeding.
Emulator: every FlushApiCache call fails. In the flush-vs-flush race both racers come back `error` (`got {'flush_a': 'error', 'flush_b': 'error'}`); in the flush-vs-update race the UpdateApiCache succeeds and only the flush fails (`got {'flush': 'error', 'update': 'ok'}`). Hypothesis: the handler is still the unimplemented scaffold at services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/flush_api_cache.rs, which the suite reports as UNIMPLEMENTED and which an auto-filed stub issue covers for the single check `appsync.flush-api-cache-clears-state`. These two checks are NOT covered by that stub report (the suite did not mark them) because they swallow the per-racer exception, and they assert more than that the call returns 200: they pin the concurrency contract.
Why: a client can never invalidate an API cache, and any client that relies on flushes being safe to issue concurrently (or concurrently with a cache reconfiguration) sees failures AWS never produces. Once the operation is implemented it must additionally NOT be put behind the api-cache modification lock, otherwise these two checks still fail with ConcurrentModificationException/409 where AWS returns 200.
Fix: the FlushApiCache handler (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/flush_api_cache.rs) must return the empty 200 body, and the api-cache state component must not serialize flush-vs-flush or flush-vs-update into a winner/loser.
Traces: appsync.flush-api-cache-concurrent-double-flush-single-winner, appsync.flush-api-cache-concurrent-modification-accepted.

=== Cause 2 of 3: UpdateDataSource retyped to AWS_LAMBDA with no lambdaConfig is refused for the wrong missing member ===
AWS: Smithy (appsync) `UpdateDataSource` — POST /v1/apis/{apiId}/datasources/{name}, required `apiId`, `name`, `type`; `lambdaConfig` (LambdaDataSourceConfig) and `serviceRoleArn` are both optional at the wire level, so the per-type requirement is enforced in the handler; modeled error BadRequestException|400. Recorded behavior: retyping an existing data source to `type=AWS_LAMBDA` with NO `lambdaConfig` is refused with 400 BadRequestException whose message names the missing type-specific config block (recorded example: `Missing Lambda data source config`), and the data source keeps its prior type/config. The requirement is the refusal (400 BadRequestException) AND that the diagnosed member is the missing `lambdaConfig` for the requested type — the message is derived from the request's own missing member, so which member it names is behavior, not cosmetics; the exact recorded wording is an example.
Emulator: the call IS refused with BadRequestException, but the validation diagnoses a different member: message `Service role arn not specified.`. The handler evidently checks `serviceRoleArn` before (or instead of) the type-specific config block, so a caller who supplies a serviceRoleArn but forgets lambdaConfig is told to fix the wrong field, and a caller who omits both is pointed at the wrong one. Earlier steps of the same check pass, so UpdateDataSource itself is implemented (NONE -> HTTP retype and the GetDataSource read-back both succeeded) — the open issue 20261024T231224Z-appsync-updatedatasource-stub.md (UpdateDataSource scaffold stub) no longer describes what happens here, and 20261024T231224Z-appsync-createdatasource-accepts-a-role-requiring-data-source.md is about CreateDataSource accepting such a request with 200, a different operation and a different outcome.
Why: a client correcting its request from the error message adds a serviceRoleArn, retries, and is refused again — the actual missing input (lambdaConfig) is never named. Validation-order divergence like this makes AppSync's per-type required-config contract untestable and breaks tooling that branches on which member the control plane reports as missing.
Fix: the UpdateDataSource validation in the operation's handler — the type-specific config block required by `type` (lambdaConfig for AWS_LAMBDA, dynamodbConfig for AMAZON_DYNAMODB, etc.) must be checked and reported before/instead of the generic serviceRoleArn check.
Traces: appsync.op-contract-updateDataSource-missing-lambda-config-rejected.

=== Cause 3 of 3: a CloudFormation stack combining AWS::AppSync::*, AWS::Cognito::* , AWS::DynamoDB::Table and AWS::IAM::Role ends in CREATE_FAILED ===
AWS: recorded behavior only (the CFN resource registry is not in the Smithy model). Real CloudFormation provisions the whole template — AWS::DynamoDB::Table, AWS::IAM::Role, AWS::Cognito::UserPool, AWS::Cognito::UserPoolGroup, AWS::Cognito::UserPoolClient, AWS::AppSync::GraphQLApi (AuthenticationType AMAZON_COGNITO_USER_POOLS with UserPoolConfig.UserPoolId from `Ref`), AWS::AppSync::GraphQLSchema, AWS::AppSync::DataSource (AMAZON_DYNAMODB, ServiceRoleArn via Fn::GetAtt) and AWS::AppSync::Resolver with DependsOn — and reaches StackStatus=CREATE_COMPLETE with the Outputs resolved.
Emulator: the stack create terminates in StackStatus=CREATE_FAILED (`AssertionError: Stack sim2real-xsvc-stk-... ended in CREATE_FAILED`), so the deploy never completes and no downstream auth/data-plane step runs. This is a MOVED failure, not the one already on file: the open issue 20261024T032443Z-appsync-cloudformation-deploys-of-appsync-templates-diverge-valueless-stack.md lists this same check under Cause 1 with the stack reaching CREATE_COMPLETE and DescribeStacks handing back Outputs entries lacking OutputValue (KeyError: 'OutputValue'); the stack now fails outright at creation instead, which that issue's Cause 1 does not describe and its fix does not address. Hypothesis: one of the resource provisioning handlers in this template (the Cognito user-pool group/client, or the AppSync resolver/data-source whose ApiId comes from Fn::GetAtt) reports resource-create failure.
Why: the single most common AppSync deployment shape — Cognito-authenticated GraphQL API writing to DynamoDB via an IAM-role data source — cannot be deployed at all; the stack fails and the client gets no endpoint, no user pool and no table. DescribeStackEvents should name the failing resource, so the fix should start there.
Fix: the CloudFormation stack-creation engine and the per-resource provisioning handlers for the types in this template (AWS::Cognito::UserPoolGroup / UserPoolClient, AWS::AppSync::DataSource, AWS::AppSync::Resolver, AWS::AppSync::GraphQLSchema) — the resource that fails must be identified and made to provision, and the stack must reach CREATE_COMPLETE with resolved Outputs.
Traces: appsync__cognito-idp__dynamodb.deploy-appsync-cognito-groups-field-authorization-positive.
