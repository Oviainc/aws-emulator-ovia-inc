# gameliftstreams: 7 control-plane fidelity defects — CreateApplication skips S3 existence/access validation and URI normalization, empty ReplicationStatuses, wrong DeleteApplication/UpdateStreamGroup refusals, DisassociateApplications unimplemented

> _Note: this issue was identified against the code base at commit `611eef386f1100e1b77f5a1515bab52b7a7a6aeb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateApplication

## Description
Seven net-new root causes in the gameliftstreams application/stream-group control plane. ALL SEVEN must be closed before this issue is submitted; each cause names its own failing checks.

Cause 1 of 7: CreateApplication does not validate that ApplicationSourceUri resolves to real S3 content, so a URI naming a bucket that does not exist is accepted.
AWS: recorded behavior only (the Smithy model gives ApplicationSourceUri @required, @length 1..1024 and NO @pattern, and models ValidationException httpError 400 for the operation; the object-existence precondition is not modeled). The replayed check, measured against real AWS, shows CreateApplication synchronously refusing the request: 400 ValidationException, message "No S3 objects were found at the specified source URI" (entirely fixed text, followed by this service's per-request " (Internal ID: <uuid>)" suffix), no Arn/Id allocated, and the description absent from ListApplications. The identical call succeeds once the bucket and object exist.
Emulator: answers HTTP 201 with a full application body (Arn, Id, Status INITIALIZED) for a bucket that was never created. src/ops/create_application.rs only checks the URI's SYNTAX (crate::state::is_s3_uri, state.rs lines 335-343) and never consults the S3 store, so no object-existence precondition exists.
Why: this is overly permissive — a caller that mistypes a bucket or races bucket creation gets a success and an application id, instead of the 400 that tells it to correct the request. Code that keys on the rejection (prompting for a fix, creating the bucket, retrying) never runs, and the emulator accumulates applications AWS would never have created.
Fix: CreateApplication's input validation in its handler, before any record is allocated — resolve ApplicationSourceUri against the emulator's S3 state and refuse with the modeled ValidationException (400) and AWS's fixed message when the prefix matches no object.
Traces: gameliftstreams.application-lifecycle-reaches-error-on-missing-bucket.

Cause 2 of 7: CreateApplication does not check read access to the source, so a source covered by an explicit S3 Deny is accepted instead of refused with AccessDeniedException.
AWS: recorded behavior only for the access precondition; the model does declare AccessDeniedException (errorKind client, httpError 403) for CreateApplication. Both replayed checks, measured against real AWS, show the call itself failing: 403 AccessDeniedException with message "Access was denied for s3:ListBucket and s3:GetObject actions on the specified source URI" (entirely fixed text plus the " (Internal ID: <uuid>)" suffix), no Arn/Id returned and nothing in ListApplications; an identical call against a sibling prefix that no Deny covers succeeds and reaches READY, and removing the Deny statement makes the refused call succeed.
Emulator: answers HTTP 201 and allocates the application (Status INITIALIZED) even though a bucket policy explicitly Denies s3:GetObject (and s3:ListBucket) on the named source. The handler never consults the bucket policy at all.
Why: a permission mistake is reported as success, so the application is created and only ever fails later (or never); callers relying on the 403 to surface "fix the bucket policy" see nothing. It also makes the emulator unusable for testing least-privilege/deny-policy behavior, which is the whole point of these checks.
Fix: CreateApplication's source-access validation in its handler — evaluate the source bucket/prefix against the S3 bucket policy in the emulator's state and refuse with the modeled AccessDeniedException (403) and AWS's fixed message when ListBucket/GetObject on that source is denied.
Traces: gameliftstreams.application-source-access-denied-via-s3-deny-policy, gameliftstreams.create-application-source-access-denied-rejected.

Cause 3 of 7: a prefix-style ApplicationSourceUri is not normalized with a trailing slash on echo or on read.
AWS: recorded behavior only (the model gives ApplicationSourceUri @length 1..1024 and no @pattern, and documents the output member as "The original Amazon S3 location of uploaded stream content"). The replayed check, measured against real AWS, shows AWS treating the value as a PREFIX and normalizing it: a submitted "s3://<bucket>/<prefix>" comes back as "s3://<bucket>/<prefix>/" both in the CreateApplication response and in GetApplication. The variable parts are the bucket and key prefix from the request; the normalization rule (append exactly one "/" when the prefix does not already end in one) is the requirement.
Emulator: stores and echoes the submitted string verbatim — CreateApplication returned "s3://sim2real-behav-glsbkt-a6e4c55544d7/build" where AWS returns "s3://sim2real-behav-glsbkt-a6e4c55544d7/build/". src/ops/create_application.rs assigns input.application_source_uri straight into the stored Application and reads it back unchanged.
Why: a client that compares the echoed/read-back ApplicationSourceUri with what it submitted, or that derives a prefix for its own S3 calls from the response, sees a different value than AWS produces, so idempotency/drift checks and prefix concatenation diverge.
Fix: CreateApplication's state write (the single place the application's source URI is stored) must normalize the prefix form, so both the CreateApplication response and GetApplication/ListApplications report the normalized value.
Traces: gameliftstreams.create-application-reflects-input-fields.

Cause 4 of 7: a READY application reports an EMPTY ReplicationStatuses unless some stream group happens to reference it.
AWS: recorded behavior only (the model declares ReplicationStatuses on the application outputs, documented as "A set of replication statuses for each location"; ReplicationStatus carries Location and Status). The replayed check, measured against real AWS, shows that once an application reaches READY it reports AT LEAST ONE location in ReplicationStatuses and EVERY entry's Status is COMPLETED — content that is not replicated anywhere is not usable for streaming, and no stream group association is involved in the check.
Emulator: returns ReplicationStatuses == [] for an application that has reached READY. By construction (state.rs Application::replication_statuses, documented "Empty for an application no stream group references"), rows are only ever appended when a stream group adds a location (src/ops/add_stream_group_locations.rs), so an unassociated application never reports any location.
Why: a caller that waits for replication to complete before deploying content (the documented way to know the content is usable) has nothing to wait on; code iterating ReplicationStatuses silently treats "no locations" as "nothing to check" or fails its own assertion, and the member documented as reporting each location reports none.
Fix: the application's state model/read path — an application that reaches READY must carry at least its own (home-region) replication row, reported COMPLETED, independent of any stream-group association, and the ReplicationStatuses projection used by CreateApplication/GetApplication/ListApplications must surface it.
Traces: gameliftstreams.create-application-content-lifecycle-ready.

Cause 5 of 7: DeleteApplication's "still associated" refusal uses emulator-authored message text instead of AWS's wording.
AWS: the model declares ValidationException (400) for DeleteApplication (DELETE /applications/{Identifier}, success 204). The replayed check, measured against real AWS (us-west-2), shows the refusal message "Application '<application ARN>' has an active association with stream group '<stream group ARN>" — note AWS emits NO closing quote after the stream group ARN — followed by the " (Internal ID: <uuid>)" suffix. Fixed text: "Application '", "' has an active association with stream group '"; variable parts: the application's full ARN and the stream group's full ARN, taken from the request and the emulator's state.
Emulator: answers 400 ValidationException with "application <bare id> is still associated with <n> stream group(s): <comma-joined ARNs>" — wording AWS never emits, naming the application by bare id, adding a count, and joining a list. Built in src/ops/delete_application.rs lines 231-243.
Why: the error class and status are right, but any client or test asserting on the message (the only place the conflicting association is named) sees text that does not match AWS, and the application is identified by id rather than by the ARN AWS reports.
Fix: the DeleteApplication handler's association-conflict refusal — emit AWS's message template with the application ARN and the (first) associated stream group ARN.
Traces: gameliftstreams.delete-application-while-associated-conflict-rejected.

Cause 6 of 7: DisassociateApplications is an unimplemented scaffold stub — it answers 501 NotImplemented for every request.
AWS: the model binds DisassociateApplications to POST /streamgroups/{Identifier}/disassociations with success status 200, @required Identifier (httpLabel) and ApplicationIdentifiers (len 1..50), output {Arn, ApplicationArns}, and errors ResourceNotFoundException (404) and ValidationException (400). The replayed check, measured against real AWS, pins three behaviors: (a) an ApplicationIdentifier that resolves to no application is refused 404 ResourceNotFoundException with message "Resource '<application ARN>' does not exist" + the " (Internal ID: <uuid>)" suffix — fixed text "Resource '" / "' does not exist", with the ARN resolved from the supplied identifier; (b) a real application that was simply never associated with the group is an idempotent no-op SUCCESS (200), whose ApplicationArns reflects the applications still associated after the call (empty here), not the ones removed; (c) after a real association, the call removes it and the link is gone from both GetStreamGroup.AssociatedApplications and GetApplication.AssociatedStreamGroups.
Emulator: every call answers HTTP 501 with error code NotImplemented, "operation DisassociateApplications is scaffolded but not implemented in this emulator" (services/service-com-amazonaws-gameliftstreams-gameliftstreams/src/ops/disassociate_applications.rs still returns crate::scaffolded::Scaffolded::not_implemented and carries the SCAFFOLDED marker).
Why: the whole unlink half of the application/stream-group association lifecycle is unreachable — a caller cannot undo AssociateApplications, cannot clean up before DeleteApplication (which refuses an associated application, cause 5), and sees a status code that is not in the operation's modeled error set, so SDK error handling cannot classify it.
Fix: implement the DisassociateApplications handler in that file — resolve each ApplicationIdentifier (404 ResourceNotFoundException with the resolved-ARN message for one that does not exist), remove the links that exist, treat a never-associated existing application as a no-op success, and answer 200 with Arn and the still-associated ApplicationArns.
Traces: gameliftstreams.disassociate-application-not-associated-rejected.

Cause 7 of 7: UpdateStreamGroup classifies an unknown DefaultApplicationIdentifier as a not-found lookup (404 ResourceNotFoundException) instead of the 400 ValidationException AWS answers.
AWS: the model gives UpdateStreamGroup PATCH /streamgroups/{Identifier} with DefaultApplicationIdentifier (Identifier shape, @length 1..128, the id-or-ARN pattern) and declares BOTH ValidationException (400) and ResourceNotFoundException (404). The replayed check, measured against real AWS, shows AWS NOT resolving this member as a lookup: an identifier that names no application is refused 400 ValidationException with "Application '<application ARN>' cannot be set as default because it is not currently associated with the stream group" + the " (Internal ID: <uuid>)" suffix. Fixed text: "Application '" / "' cannot be set as default because it is not currently associated with the stream group"; the one variable part is the application ARN resolved from the supplied identifier. The group's DefaultApplication is left unset, and a Description-only update still succeeds.
Emulator: answers 404 ResourceNotFoundException with "Resource '<arn>' does not exist (Internal ID: ...)" — src/ops/update_stream_group.rs lines 404-418 looks the application up and returns resource_not_found before it ever applies the association rule, so the "not associated" ValidationException the same handler already words (lines 439-450, and itself in emulator wording: "application <id> is not associated with stream group <group id>; use AssociateApplications to associate it first") is unreachable for a nonexistent identifier.
Why: 404 ResourceNotFoundException and 400 ValidationException mean different things to a caller: the first says the stream group URI/resource was not found and invites create-or-retry logic, the second says this particular member value is not usable for this group. Error-class-driven branches and retry policies take the wrong path, and the message names a missing resource rather than the association rule AWS reports. Note the separate open issue 20261029T182642Z-gameliftstreams-refusals-validationexception-omits-required-message-and-arn.md covers the same misclassification family for AssociateApplications' Identifier label; it does NOT cover UpdateStreamGroup's DefaultApplicationIdentifier.
Fix: the UpdateStreamGroup handler's default-application resolution — an identifier that resolves to no application must take the same ValidationException path as an application that exists but is not associated, with AWS's wording (and that wording, for both cases, must be AWS's "Application '<arn>' cannot be set as default because it is not currently associated with the stream group").
Traces: gameliftstreams.update-stream-group-default-application-not-found-rejected.
