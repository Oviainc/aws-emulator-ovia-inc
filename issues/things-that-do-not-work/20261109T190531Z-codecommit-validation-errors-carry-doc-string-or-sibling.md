# CodeCommit validation errors carry doc-string or sibling-operation messages and one wrong exception code (5 causes)

> _Note: this issue was identified against the code base at commit `ad50bb76edcdd86b23b984a2eb82fa03f07ee77a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetFolder

## Description
FIVE net-new causes sharing one fault: on the codecommit content-read and write validation paths the emulator answers with the correct HTTP status but substitutes a sentence that is not AWS's wire message for that error class — in three cases the Smithy error shape's own DOCUMENTATION string, in two cases a sibling operation's message template — and in one case it also selects the sibling exception code, reporting a malformed value as a missing one. A fixer must close ALL FIVE causes before submitting.

=== Cause 1 of 5: GetFolder's CommitDoesNotExistException uses the commit-SPECIFIER template instead of its own wording ===
AWS: Smithy com.amazonaws.codecommit#GetFolder takes repositoryName (@required RepositoryName, @length 1..100, @pattern ^[\w\.-]+$), folderPath (@required Path) and an optional commitSpecifier (CommitName), and models CommitDoesNotExistException (errorKind client, httpError 400 [defaulted]) with a single `message` member. The shape's doc is only 'The specified commit does not exist or no commit was specified, and the specified repository has no default branch.', so the model does not state the wire text; recorded behavior supplies it. For a repository that has no commits and no default branch, GetFolder is refused 400 CommitDoesNotExistException with 'Could not find commit HEAD'. In that template 'Could not find commit ' is FIXED text and the single variable part is the commit specifier the request resolved to — the request's commitSpecifier when it names one, the literal HEAD when it names none. No repository name, folder path or commit id appears.
Emulator: the same status (400) and the same error code, but the message 'AWS CodeCommit could not find the commit specifier HEAD. Either the specifier does not exist, or the commit has not yet been pushed to the remote repository.' — the two-sentence template AWS uses for the comparison/merge operations (GetDifferences, GetMergeOptions), obtained from the crate-shared commit-specifier helper, so GetFolder inherits a sibling operation's text.
Why: this refusal is the first thing a client meets when it reads a freshly created repository, and it is the one it must recognize to tell 'repository is empty' from 'folder is missing'. A caller matching AWS's sentence never matches, and the emulator's variant asserts something AWS does not say here — that the commit may merely be unpushed — which is false for a repository that never had a commit. It also collapses two distinct AWS templates for one error code into one.
Fix: the CommitDoesNotExistException construction on the GetFolder handler's commit-resolution path, and the shared message helper it calls: GetFolder must word this refusal itself (fixed prefix plus the resolved specifier) while the specifier wording stays available to the comparison/merge operations. Related: behavioral issue 20261109T063854Z-codecommit-codepipeline-glue-iam-lambda-reopens-codecommit-getfolder-s-commitdoesnotexistexception-uses-the-shared.md describes this same wording for GetFolder, but it is a BEHAVIORAL report carrying no wire replay key, so this fixture step is unexercised by its pointer; open issue 20261102T130134Z-codecommit-content-read-and-commit-write-errors-carry.md Cause 1 requires the two-sentence specifier wording for GetDifferences, so the two templates must coexist rather than one replacing the other.
Traces: codecommit-fresh-repository-has-no-branches-or-default#task#3 (representative; cluster also covers codecommit-gpn-traj-empty-repository-content-reads#task#4).

=== Cause 2 of 5: GetFile's CommitDoesNotExistException uses the same commit-SPECIFIER template ===
AWS: Smithy GetFile takes repositoryName (@required), filePath (@required Path) and an optional commitSpecifier (CommitName), and models CommitDoesNotExistException (client, httpError 400 [defaulted]). Recorded behavior: reading any path in a repository with no commits is refused 400 CommitDoesNotExistException with 'Could not find commit HEAD' — fixed text 'Could not find commit ' plus the one variable part, the resolved commit specifier (HEAD when the request names none).
Emulator: 400 with the correct error code but the message 'AWS CodeCommit could not find the commit specifier HEAD. Either the specifier does not exist, or the commit has not yet been pushed to the remote repository.' — again the comparison/merge template.
Why: same client consequence as Cause 1 on the single-file read path, which is the most common first read of a new repository; this is a separate handler, so fixing GetFolder alone leaves GetFile diverging.
Fix: the CommitDoesNotExistException construction in the GetFile handler's commit-resolution path (same shared helper as Cause 1).
Traces: codecommit-gpn-traj-empty-repository-content-reads#task#2 (representative; cluster also covers the same fixture's task#3).

=== Cause 3 of 5: CreateBranch's InvalidCommitIdException message is the Smithy doc string and names no value ===
AWS: Smithy CreateBranch takes repositoryName (@required), branchName (@required BranchName, @length 1..256) and commitId (@required CommitId), and models InvalidCommitIdException (client, httpError 400 [defaulted]) whose doc string is 'The specified commit ID is not valid.' Recorded behavior supplies the wire text: when commitId is not a git object id (here the ref name HEAD passed where a commit id is required) AWS answers 400 InvalidCommitIdException with 'The specified commit ID is not a valid Git object ID: HEAD' — fixed prefix 'The specified commit ID is not a valid Git object ID: ' plus the rejected id copied verbatim from the request.
Emulator: 400 with the right code but the message 'The specified commit ID is not valid.' — verbatim the shape's documentation sentence, naming nothing.
Why: AWS's message states WHY the value was rejected (it is not a Git object ID — pass a commit id, not a ref) and WHICH value was rejected; the emulator conveys neither, so a caller that passed a branch name or HEAD cannot tell a malformed id from an unknown one. Open issue 20261102T130134Z-codecommit-content-read-and-commit-write-errors-carry.md Cause 2 requires this template for GetCommit only and does not carry this step's replay key or cover CreateBranch.
Fix: the commitId validation in the CreateBranch handler — build the message from the rejected id instead of returning the shape doc; ideally share one git-object-id validator across the operations that take a CommitId.
Traces: codecommit-gpn-traj-seeding-main-on-an-empty-repository#task#3.

=== Cause 4 of 5: PutFile's BranchNameRequiredException message is the Smithy doc string ===
AWS: Smithy PutFile models branchName as @required (BranchName, @length 1..256) and declares BranchNameRequiredException (client, httpError 400 [defaulted]), whose doc string is 'A branch name is required, but was not specified.' Recorded behavior: a PutFile whose branchName is empty is refused 400 BranchNameRequiredException with 'You must provide a branch name. The branch name cannot be empty.' — entirely FIXED text, two sentences, no request values interpolated.
Emulator: the correct status and error code, but the message 'A branch name is required, but was not specified.' — verbatim the Smithy documentation sentence rather than AWS's wire text.
Why: a value-free message is pure wording, so every client or test asserting AWS's sentence for the empty-branch-name case fails, and the rule AWS states ('the branch name cannot be empty') is not conveyed. It also confirms the handler's refusal path reaches for shape docs, which is the fault this bundle shares.
Fix: the branchName validation in the PutFile handler — emit AWS's fixed two-sentence text verbatim instead of the error shape's documentation.
Traces: codecommit-gpn-traj-seeding-main-on-an-empty-repository#task#4.

=== Cause 5 of 5: PutFile still classifies a malformed parentCommitId as a missing one (wrong exception code AND message) ===
AWS: Smithy PutFile models InvalidParentCommitIdException and ParentCommitDoesNotExistException as two DISTINCT errors (both client, httpError 400 [defaulted]). InvalidParentCommitIdException is documented 'The parent commit ID is not valid. The commit ID cannot be empty, and must match the head commit ID for the branch of the repository where you want to add or update a file.' — a FORMAT/consistency rejection; ParentCommitDoesNotExistException is documented 'The parent commit ID is not valid because it does not exist. The specified parent commit ID does not exist in the specified branch of the repository.' — an EXISTENCE rejection. Recorded behavior: a parentCommitId that is not a git object id at all (here the literal HEAD, not a 40-hex id) is rejected on FORM, before any lookup: 400 with $.__type 'InvalidParentCommitIdException' and message 'The parent commit ID is not valid. The commit ID is not a valid length for commit IDs in Git.' — entirely fixed text; AWS echoes neither the id nor the repository name.
Emulator: 400 with $.__type 'ParentCommitDoesNotExistException' and message 'The parent commit ID is not valid. The specified parent commit ID does not exist.' — the sibling error code, with a sentence assembled from that sibling shape's documentation.
Why: the error code is what clients dispatch on. A write path that treats a parent-commit existence error as 'refetch the branch head and retry' retries forever against the emulator on input AWS rejects as permanently malformed, while a client catching InvalidParentCommitIdException to report a bad argument never sees it. Ordering is the rule: form validation must precede the existence lookup, otherwise a syntactically invalid id can only ever be reported as missing. Open issue 20261102T130134Z-codecommit-content-read-and-commit-write-errors-carry.md Cause 3 describes this same step, but its replay pointer names only fixture ids without steps, so the replay reports this cluster as unowned and its prior fix only replaced the lowercase prose — the wrong code and the wrong sentence both remain.
Fix: the PutFile input validation — validate parentCommitId's git-object-id form first and raise InvalidParentCommitIdException with AWS's fixed sentence, reserving ParentCommitDoesNotExistException for a well-formed id that is absent.
Traces: codecommit-gpn-traj-seeding-main-on-an-empty-repository#task#5.
