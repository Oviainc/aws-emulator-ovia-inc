# ACM PCA: GetPolicy misreports a missing CA, CreateCertificateAuthority ignores IdempotencyToken, CFN CertificateAuthorityActivation never activates, and ListTags omits the Tags member

> _Note: this issue was identified against the code base at commit `20ab55bd9317ee9a3c91528cd79e8ca342e82eb9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateCertificateAuthority

## Description
Four distinct net-new root causes in the acm-pca surface. All four are grounded in failing behavioral checks that the replay marked NEITHER "ALREADY FILED" NOR "OWNED by" (the other 39 acm-pca failures in this run are owned by 20261022T143159Z-acm-pca-private-ca-lifecycle-is-unusable-issuecertificate.md and 20261025T011542Z-acm-pca-resource-policy-contract-diverges-putpolicy-rejection.md and are skipped here). Smithy citations are from services/service-com-amazonaws-acmpca-acmprivateca/smithy-model/com-amazonaws-acmpca-acmprivateca.json.

Cause 1 of 4: GetPolicy returns the policy-not-found diagnostic when it is the CERTIFICATE AUTHORITY that does not exist, so the two ResourceNotFoundException branches are indistinguishable.
AWS: Smithy models GetPolicy with ResourceArn (target Arn, required, @length 5..200, pattern ^arn:[\w+=/,.@-]+:acm-pca:[\w+=/,.@-]*:[0-9]*:[\w+=,.@-]+(/[\w+=,.@-]+)*$) and the errors InvalidArnException, InvalidStateException, RequestFailedException, ResourceNotFoundException (all errorKind client, httpError 400). The model does not state diagnostic text, so for the message this is recorded behavior only: across the five ARN-taking operations (DescribeCertificateAuthority, ListTags, ListPermissions, GetPolicy, DeletePolicy) ARN shape validation runs BEFORE resource lookup, so a malformed CA ARN is 400 InvalidArnException with the fixed message "Not a valid arn." (no variable part), and a well-formed ARN naming a never-minted CA is 400 ResourceNotFoundException with the fixed message "Could not find specified CA" (no variable part). "Could not find policy for specified resource." is AWS's message for GetPolicy's OTHER ResourceNotFoundException branch — an authority that EXISTS but carries no resource policy. The requirement is the two-stage resolution rule (authority first, then the attached policy) and the distinct message per stage.
Emulator: DescribeCertificateAuthority, ListTags and ListPermissions get both branches right (both assertions pass for them). GetPolicy on a well-formed, never-minted CA ARN returns ResourceNotFoundException with message 'Could not find policy for specified resource.' — it only looks the policy up and never resolves the authority, so an absent CA and an absent policy on a live CA produce the identical code AND the identical message.
Why: a client cannot tell "this CA is gone" from "this CA has no resource policy" — the first is a fatal, non-retryable condition that should abort a workflow, the second is the normal pre-PutPolicy state that a caller treats as "nothing to read". Teardown and least-privilege flows that branch on the GetPolicy diagnostic take the wrong branch, and an operator debugging a typo'd/stale CA ARN is told the policy is missing rather than the authority.
Fix: GetPolicy's handler in the acm-pca service crate — resolve the authority from ResourceArn first (ResourceNotFoundException "Could not find specified CA" when absent) and only then the attached policy (ResourceNotFoundException "Could not find policy for specified resource."). The same two-stage resolution belongs in DeletePolicy. Related but not covering: cause 2 of the open 20261025T011542Z-acm-pca-resource-policy-contract-diverges-putpolicy-rejection.md reports DeletePolicy resolving the policy instead of the authority; that issue does not carry this check and says nothing about GetPolicy's missing-CA message.
Traces: acm-pca.ca-arn-validation-precedes-resource-lookup (assertion at check line 67).

Cause 2 of 4: CreateCertificateAuthority ignores IdempotencyToken — replaying the same token with the identical configuration mints a second billable CA instead of returning the first CA's ARN.
AWS: Smithy marks CreateCertificateAuthority @idempotent and models IdempotencyToken (@length 1..36, pattern ^[\u0009\u000A\u000D\u0020-\u00FF]*$) alongside CertificateAuthorityConfiguration (required), CertificateAuthorityType (required), UsageMode and Tags; errors InvalidArgsException, InvalidPolicyException, InvalidTagException, LimitExceededException. The model does not state the replay semantics, so recorded behavior only: a CreateCertificateAuthority whose IdempotencyToken AND configuration match a recent create returns HTTP 200 carrying the ARN of the ALREADY-created authority, creates nothing, and leaves that authority untouched (CreatedAt unchanged, exactly one CA with that subject CommonName); reusing the same token with a materially different configuration is NOT IdempotencyParameterMismatchException — it creates a second, independent CA, and the first CA keeps its own configuration.
Emulator: every call creates a fresh authority and a fresh ARN; the token is accepted and discarded. The third call, with the token and configuration byte-identical to the first, returned a different certificate-authority ARN than the first call did (two distinct uuid resource ids for one token+config pair). The "different configuration, same token" half of the contract passes only incidentally, because nothing is ever deduplicated.
Why: a private CA bills hourly from creation. Any retry of CreateCertificateAuthority — an SDK retry after a socket timeout, a replayed CloudFormation/Terraform create, a re-run deploy job — silently provisions a duplicate billable CA, and the caller keeps the ARN of the duplicate while the first CA is orphaned and never cleaned up. The IdempotencyToken is precisely the mechanism clients use to make creation exactly-once; a backend that accepts and ignores it validates unsafe client code as safe.
Fix: CreateCertificateAuthority's handler/state in the acm-pca service crate — key created authorities by (account, region, IdempotencyToken) together with the normalized request configuration, return the stored CertificateAuthorityArn without mutating state when both match within the idempotency window, and fall through to a new authority when the configuration differs for the same token.
Traces: acm-pca.create-certificate-authority-idempotency-token-mismatch (assertion `same_arn == arn` at check line 91).

Cause 3 of 4: a CloudFormation stack carrying AWS::ACMPCA::Certificate + AWS::ACMPCA::CertificateAuthorityActivation reaches CREATE_COMPLETE while the CA is still PENDING_CERTIFICATE — the activation resources are provisioned as no-ops.
AWS: recorded behavior only (CloudFormation resource types are not part of the acm-pca Smithy model): for a stack whose resources are AWS::ACMPCA::CertificateAuthority (Type ROOT, RSA_2048/SHA256WITHRSA), AWS::ACMPCA::Certificate (CertificateSigningRequest = Fn::GetAtt Ca.CertificateSigningRequest, TemplateArn arn:aws:acm-pca:::template/RootCACertificate/V1, Validity 3650 DAYS) and AWS::ACMPCA::CertificateAuthorityActivation (Certificate = Fn::GetAtt CaCert.Certificate, Status ACTIVE), CREATE_COMPLETE is only reported once the CA's own CSR has actually been signed and imported: DescribeCertificateAuthority on the ARN from the stack output then reports Status ACTIVE, and that CA signs a leaf, with GetCertificate returning a PEM delimited by -----BEGIN CERTIFICATE----- / -----END CERTIFICATE-----.
Emulator: CreateStack is accepted and the stack does reach CREATE_COMPLETE, but DescribeCertificateAuthority on Outputs.CaArn reports Status PENDING_CERTIFICATE ("CFN-deployed CA is not ACTIVE, got PENDING_CERTIFICATE"). The Certificate and/or CertificateAuthorityActivation resources are created without driving IssueCertificate on the CA's CSR and ImportCertificateAuthorityCertificate + Status=ACTIVE, so the stack reports success for an activation that never happened and everything downstream (IssueCertificate/GetCertificate against the deployed CA) is unreachable.
The open issue 20261025T011542Z-acm-pca-cloudformation-rejects-every-aws-acmpca-resource-type-as.md names this same check, but describes a DIFFERENT failure — CreateStack refused with 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::ACMPCA::...]'. That refusal no longer occurs in this replay (the stack now reaches CREATE_COMPLETE), which is why the suite did not mark this check owned; the remaining divergence is the silent no-op activation described here.
Why: CREATE_COMPLETE is the signal every IaC pipeline gates on. A stack that reports success while leaving its root CA unsigned hands the caller an ARN that cannot sign anything, and the failure surfaces far away as an InvalidStateException from IssueCertificate rather than at deploy time. A refusal at least stops the pipeline; a false success does not.
Fix: the AWS::ACMPCA::Certificate and AWS::ACMPCA::CertificateAuthorityActivation provisioning handlers in the emulator's cloudformation service — Certificate must resolve Fn::GetAtt <Ca>.CertificateSigningRequest and sign it via IssueCertificate with the RootCACertificate/V1 template, exposing the signed PEM as its Certificate attribute; CertificateAuthorityActivation must call ImportCertificateAuthorityCertificate with that PEM and apply the requested Status (ACTIVE), and both must fail the stack rather than report CREATE_COMPLETE when they cannot.
Traces: acm-pca.deploy-cloudformation-ca-issues-certificate (assertion at check line 40).

Cause 4 of 4: ListTags omits the Tags member for an authority that currently has no tags, instead of returning it empty.
AWS: Smithy models ListTagsResponse with NextToken and Tags (target TagList, @length 1..50) and marks the operation paginated with inputToken/outputToken NextToken and items "Tags". Tags is not marked required, so for its PRESENCE this is recorded behavior only: ListTags against an existing certificate authority that carries no tags returns HTTP 200 with the Tags member PRESENT and empty, so a client may index response["Tags"] unconditionally; the member is absent only in the sense of carrying no elements. (Hypothesis: the @length min 1 on TagList constrains supplied tag lists, not the empty-collection response.) Note the earlier assertions of this same check PASS, so TagCertificateAuthority's refusal of a disallowed tag key is already correct: 400 ValidationException with message "1 validation error detected: Value at 'tags.1.member.key' failed to satisfy constraint: Member must satisfy regular expression pattern: ([\p{L}\p{Z}\p{N}_.:/=+\-@]*)" — fixed text, with the member path index and the pattern as its variable parts. Nothing in that part needs changing.
Emulator: the ListTags response for a tagless authority omits the Tags key entirely, so the SDK's parsed response has no 'Tags' entry and the client raises KeyError: 'Tags' when it dereferences it.
Why: every SDK models Tags as a list, and idiomatic client code (and the "did my rejected tag get persisted?" check pattern) reads it directly. Omitting the member turns the normal, successful "no tags yet" answer into a hard client-side crash in Python, a nil-list dereference in Go/Java consumers that iterate it, and it is a plain shape divergence: the same operation returns a different response shape depending on whether any tags happen to exist.
Fix: ListTags' handler/serializer in the acm-pca service crate — always emit the Tags member, as an empty list when the resolved authority carries no tags (and keep NextToken omitted when there is no next page).
Traces: acm-pca.tag-certificate-authority-invalid-tag-key-rejected (KeyError: 'Tags' at check line 36, after the ValidationException assertions passed).
