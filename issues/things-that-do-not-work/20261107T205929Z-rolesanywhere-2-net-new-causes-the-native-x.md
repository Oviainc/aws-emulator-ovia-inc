# rolesanywhere: 2 net-new causes — the native X.509 CreateSession data plane is answered 'UnknownService' by the request router, and an explicit IAM Deny on rolesanywhere:CreateProfile is not enforced

> _Note: this issue was identified against the code base at commit `9af3ef1be99c27ea1cc985f2aa8eae4c07398a66`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSession

## Description
Two net-new root causes on the rolesanywhere request-acceptance surface, numbered below. A fixer must close BOTH before submitting. Related open issue: 20261029T195344Z-rolesanywhere-does-not-serve-the-native-createsession-data.md describes the same two surfaces, but the suite did not mark either of these checks as covered by it (its replay keys record the old failure signature, a 60s poll timeout); the emulator's observed behavior has since changed to an immediate routing refusal, so the behavior described here is what the current build does and it is filed separately rather than assumed covered.

Cause 1 of 2 — CreateSession (POST /sessions, AWS4-X509-RSA-SHA256) is not routed to the rolesanywhere service at all:
AWS: CreateSession is IAM Roles Anywhere's native data plane and is NOT present in this checkout's Smithy model (smithy_query query=operation operation=CreateSession on services/service-com-amazonaws-rolesanywhere-rolesanywhere/smithy-model/com-amazonaws-rolesanywhere-rolesanywhere.json answers "operation 'CreateSession' not found", did_you_mean CreateProfile/CreateTrustAnchor), so this is recorded behavior only. AWS serves it as POST /sessions on the rolesanywhere endpoint, hand-signed with the SigV4-derived algorithm AWS4-X509-RSA-SHA256: the Authorization header carries Credential=<client-certificate serial number>/<date>/<region>/rolesanywhere/aws4_request (note the credential scope's first element is a certificate serial number, NOT an AWS access key id), SignedHeaders and an RSA PKCS#1 v1.5 SHA-256 Signature over the standard string-to-sign, and the DER client certificate base64-encoded in X-Amz-X509. With an enabled profile whose roleArns name a role trusting rolesanywhere.amazonaws.com and a trust anchor holding the signing certificate's CA, AWS answers HTTP 201 with a body carrying exactly one credentialSet entry: roleArn echoing the requested role, assumedRoleUser.arn ending in '/<session name>' where the default session name is the signing certificate's serial number hex-encoded, and credentials {accessKeyId, secretAccessKey, sessionToken, expiration} usable for sts:GetCallerIdentity, which then resolves to an ':assumed-role/<role name>/' identity. The same signed request against a profile with enabled=false is refused HTTP 403 with error code AccessDeniedException (the x-amzn-ErrorType header's part before ':' is AccessDeniedException) and a body containing no credentialSet; re-enabling the profile makes the identical request succeed with 201 again.
Emulator: the request never reaches any rolesanywhere handler. The emulator's front-door router answers the signed POST /sessions with the emulator-authored error body {"__type": "UnknownService", "message": "could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)"} on a non-201 status — i.e. the router only resolves a target service from a SigV4 credential scope, an X-Amz-Target header or the Host header, and an AWS4-X509-RSA-SHA256 Authorization header (whose credential scope element 4 is still 'rolesanywhere') is not recognised as naming a service. Neither __type 'UnknownService' nor that message text is an AWS error class. Corroboration: services/service-com-amazonaws-rolesanywhere-rolesanywhere/src/ops/create_session.rs does not exist in the checkout, and the operation is absent from the model the handlers are generated from, so even a routed request would have no handler. Because the positive-control leg never yields 201, the disabled-profile refusal (403 AccessDeniedException, no credentialSet) is never exercised either.
Why: exchanging an X.509 identity for temporary AWS credentials is the entire purpose of IAM Roles Anywhere. A client built against this emulator can create trust anchors and profiles but can never obtain credentials; instead of a modelled AWS error it receives an unknown '__type: UnknownService' envelope that no AWS SDK can classify, so retry/error handling written for AWS misbehaves, and the 'disabled profile vends no credentials' kill switch operators depend on cannot be expressed or tested at all.
Fix: the front-door request router's service-resolution step must recognise the AWS4-X509-RSA-SHA256 authorization scheme and resolve the service from its credential scope (and from the /sessions path on the rolesanywhere endpoint), and a CreateSession handler must be added to the rolesanywhere service crate alongside the generated ops, with its route registration and state wiring: verify the X-Amz-X509 certificate chains to a registered, enabled trust anchor, resolve the profile and role, consult the profile's (and trust anchor's) enabled flag — refusing 403 AccessDeniedException with the matching x-amzn-ErrorType header and no credentialSet when disabled — and otherwise vend one credentialSet whose default session name is the certificate's hex serial.
Traces: rolesanywhere.create-session-native-x509-round-trip, rolesanywhere.create-session-disabled-profile-rejected.

Cause 2 of 2 — CreateProfile ignores an explicit IAM Deny on the calling identity:
AWS: CreateProfile models AccessDeniedException with httpError 403 (Smithy: CreateProfile POST /profiles code 201; errors AccessDeniedException httpError 403, ValidationException httpError 400). A CreateProfile request signed with an IAM user's own access key, where that user carries an inline policy with Effect Deny for Action rolesanywhere:CreateProfile, is refused with HTTP 403 at the authorization layer and creates nothing: the submitted profile name is absent from ListProfiles afterwards. Deleting the Deny statement makes the identical call succeed and the profile becomes visible via ListProfiles. (The error code string for an IAM-layer deny varies by call path; the stable requirement is the 403 status and that no state is mutated.)
Emulator: the call signed with the explicitly-denied identity keeps succeeding. The check polls CreateProfile with those credentials for 60s, deleting each unexpectedly created profile, and never observes any non-success answer — it fails with AssertionError 'the deny policy never took effect within the timeout'. The request's signing identity and its attached identity policies are never consulted on the rolesanywhere control plane, so no 403 is ever produced.
Why: every negative authorization assertion is silently inverted. A caller validating least-privilege or break-glass Deny policies against the emulator sees every scoped-down or explicitly denied identity succeed, so a policy that actually blocks the workload in production looks correct here, and the 403 AccessDeniedException the client is written to handle never arrives.
Fix: the service's per-operation request-authorization step, applied before the CreateProfile handler's state write, must evaluate the caller's identity policies (including explicit Deny) and refuse with 403 AccessDeniedException without mutating state.
Traces: rolesanywhere.access-denied-without-permission-rejected.

2. Then POST {profileArn, roleArn, trustAnchorArn} to <rolesanywhere endpoint>/sessions with X-Amz-Date, X-Amz-X509=<base64 DER leaf cert> and Authorization 'AWS4-X509-RSA-SHA256 Credential=<leaf serial>/<date>/<region>/rolesanywhere/aws4_request, SignedHeaders=content-type;host;x-amz-date;x-amz-x509, Signature=<RSA PKCS#1v1.5 SHA-256 over the SigV4 string-to-sign>'.
