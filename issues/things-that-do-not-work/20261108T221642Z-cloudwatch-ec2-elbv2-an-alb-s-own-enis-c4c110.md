# cloudwatch__ec2__elbv2: an ALB's own ENIs are never materialised in EC2 and its AWS/ApplicationELB host-count alarm never leaves INSUFFICIENT_DATA, so the CLI address-level diagnosis reaches no verdict

> _Note: this issue was identified against the code base at commit `6211fb78e0841381478152dba6893fe342be7489`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeNetworkInterfaces

## Description
One root cause, grounded in the only failing cloudwatch__ec2__elbv2 check that the replay report marks neither ALREADY FILED nor OWNED. Two open issues describe the same family of behaviour but do NOT own this check in this replay (their stored replay keys for it no longer match what the replay produces — one records a 60 s-era poll index, the other an `aws#17` subprocess frame, while the check now simply ends 'Check timed out after 180.0s'): 20261102T085002Z-cloudwatch-ec2-elbv2-2-net-new-root-causes.md and 20261108T002731Z-cloudwatch-ec2-elbv2-an-alb-s-own-enis.md. Reconcile with those rather than assuming this check is covered by them.

Cause 1 of 1: an Application Load Balancer's service-managed elastic network interfaces are never written into EC2 network-interface state, and no AWS/ApplicationELB host-count datapoints are published for its target groups, so the two unbounded waits in this check are predicates the emulator can never satisfy.
AWS: creating an ALB attaches one service-managed ENI per configured subnet, and those interfaces are ordinary describable EC2 network interfaces. Smithy (EC2 DescribeNetworkInterfacesRequest.Filters) documents the 'vpc-id' filter — 'The ID of the VPC for the network interface' — and the 'requester-id' filter — 'The alias or Amazon Web Services account ID of the principal or service that created the network interface'; the same member's 'interface-type' filter enumerates 'load_balancer' and 'network_load_balancer', i.e. the model itself models load-balancer-owned interfaces, and 'requester-managed' marks a service-managed one. So DescribeNetworkInterfaces with Filters=[{Name:'vpc-id',Values:[<the ALB's VPC>]}] lists at least one interface per ALB subnet, each with a PrivateIpAddress drawn from that subnet and never equal to a registered-but-dead ip target address, and the same query additionally filtered Name=requester-id,Values=amazon-elb returns that identical set when the ALB is the only load balancer in the VPC. For the derived observability leg (recorded behavior only — these are service-published metrics, not modeled shapes): an ALB publishes per-minute AWS/ApplicationELB UnHealthyHostCount under the dimension pair TargetGroup=targetgroup/<name>/<id> + LoadBalancer=app/<name>/<id>, so an alarm over that series with Statistic=Maximum, Period=60, EvaluationPeriods=2, Threshold=0, ComparisonOperator=GreaterThanThreshold and TreatMissingData=breaching leaves INSUFFICIENT_DATA and reads StateValue 'ALARM'.
Emulator: the check's earlier control-plane reads are all made through the aws CLI and are reached — DescribeLoadBalancers filtered client-side on DNSName, LoadBalancers[0].VpcId, DescribeTargetGroups --load-balancer-arn, DescribeTargetHealth per group — so the emulator was serving and the CLI was present. It then never gets past its waits: the poll for at least two network interfaces in the ALB's VPC (the check's own budget 600 s, 10 s interval) and the following poll for the unhealthy-hosts alarm to leave INSUFFICIENT_DATA (budget 600 s, 15 s interval) never satisfy, so the check ends with no assertion failure and no traceback, only 'Check timed out after 180.0s'. Hypothesis: ELBv2 load-balancer provisioning never writes into EC2 network-interface state and there is no ALB metric publisher, so both predicates are unreachable rather than merely slow.
Why: a client can perform no address-level diagnosis of a load balancer — which interface is the ALB, which addresses in the VPC are stale targets, whether an address belongs to amazon-elb — because the load balancer is invisible in EC2. An unhealthy-host alarm configured exactly as AWS documents stays in its initial state forever, so alarm-driven remediation never triggers. Because these reads answer successfully-but-empty instead of refusing, a caller cannot distinguish 'not provisioned yet' from 'never will be' and burns its own deadline.
Fix: ELBv2 load-balancer provisioning (the CreateLoadBalancer handler and its state) must materialise one service-managed ENI per configured subnet into EC2 network-interface state — InterfaceType 'load_balancer' for an ALB / 'network_load_balancer' for an NLB, requester-id 'amazon-elb', requester-managed true, a PrivateIpAddress from the respective subnet — and release them on DeleteLoadBalancer; the EC2 DescribeNetworkInterfaces handler's filter evaluation must match those interfaces on both 'vpc-id' and 'requester-id'. The ELBv2 target-group health evaluation must publish the AWS/ApplicationELB HealthyHostCount/UnHealthyHostCount series into CloudWatch metric state, and CloudWatch alarm evaluation must grade the alarm from those stored datapoints rather than leaving it at its initial state.

Or build the estate by hand: a VPC with three /22 subnets across two AZs plus a security group allowing TCP 80 from the VPC CIDR; an internal, ipv4, application-type load balancer across two of the private subnets; three ip-type HTTPS:443 target groups in that VPC, each registering the same pair of unreachable in-VPC addresses on port 443; an HTTP:80 listener whose default action forwards to the first group and a priority-10 path-pattern rule forwarding to the second; the third group left unrouted.
