# DynamoDB data-plane ignores the session policy's dynamodb:Select / dynamodb:Attributes conditions, so a projection-scoped session reads the whole item including the withheld attribute

> _Note: this issue was identified against the code base at commit `089026a1c9416fdeaf52bd064325368a385b884c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
ONE net-new root cause in the DynamoDB data-plane authorization gate as reached by an assumed-role session. The failing check is neither ALREADY FILED nor OWNED in the replay report.

Nearest open neighbours, named so they are not re-fixed and are not mistaken for coverage of this replay key: 20261031T102348Z-dynamodb-iam-sts-dynamodb-data-plane-authorization-ignores-session-policies-and.md (its Cause 1 is the same missing session-policy evaluation reached through an explicit session-policy Deny, and its Cause 2's Fix paragraph mentions `dynamodb:Attributes` in passing; it carries neither this check id nor the Select/Attributes/projection behaviour as a graded requirement, so this cause supplies the additional replay key and the two should be closed together) and 20261024T065715Z-dynamodb-iam-sts-dynamodb-data-plane-reads-are-never-authorized-identity.md (the earlier state in which no authorization happened at all).

Cause 1 of 1: a session policy that allows reads only when the request projects a fixed attribute set is not applied, so an unprojected full-item read is served instead of refused.
AWS: an assumed-role session's request is authorized against the role's identity policies INTERSECT the inline session policy passed to sts:AssumeRole, and DynamoDB derives the condition keys dynamodb:Select, dynamodb:Attributes and dynamodb:LeadingKeys from the request itself (a ProjectionExpression with no explicit Select yields Select=SPECIFIC_ATTRIBUTES and Attributes = the projected names). A session policy of the form {"Effect":"Allow","Action":["dynamodb:GetItem","dynamodb:Query","dynamodb:BatchGetItem"],"Resource":<table ARN>,"Condition":{"ForAllValues:StringEquals":{"dynamodb:LeadingKeys":[<allowed pk>],"dynamodb:Attributes":[<visible attribute names>]},"StringEquals":{"dynamodb:Select":"SPECIFIC_ATTRIBUTES"}}} therefore admits only projected reads of the allowed partition. Every request outside that envelope — GetItem with no ProjectionExpression, GetItem projecting a non-listed attribute, GetItem on another partition, Query with Select=ALL_ATTRIBUTES, Query with no projection, BatchGetItem with no ProjectionExpression — is refused AccessDeniedException with the message "User: <session principal ARN> is not authorized to perform: dynamodb:<Action> on resource: <table ARN> because no session policy allows the dynamodb:<Action> action". The fixed text is "User: ", " is not authorized to perform: dynamodb:", " on resource: ", " because no session policy allows the dynamodb:" and " action"; the variable parts are the AssumedRoleUser ARN STS returned for that session, the table ARN from the request, and the action name of the operation actually called (GetItem / Query / BatchGetItem), repeated in the trailing attribution clause. The stored item is unchanged by a refused read: the hidden attribute is hidden, never removed. Recorded behavior only for the refusal shape: the Smithy model for GetItem, Query and BatchGetItem declares errors InternalServerError, InvalidEndpointException, ProvisionedThroughputExceededException, RequestLimitExceeded, ResourceNotFoundException and ThrottlingException and NO AccessDeniedException, and carries no authorization trait, so the oracle for the code and message is the recorded AWS response.
Emulator: the role's own inline identity policy (Allow dynamodb:* on the table) is the only thing evaluated, so the session policy neither scopes nor denies. GetItem(TableName=<table>, Key=<allowed pk>) with NO ProjectionExpression returns HTTP 200 and the complete item, including the attribute the session policy withholds — replay output: "call was expected to be DENIED but succeeded: {'Item': {'pub': {'S': 'public-value'}, 'pk': {'S': 'tenant-allowed'}, 'sk': {'S': '1'}, 'secret': {'S': 'hidden-value'}}}". The projected positive control passes only because ProjectionExpression filtering happens in the read path, not because any condition was evaluated; the later legs (hidden-attribute projection, other partition, Query Select=ALL_ATTRIBUTES, Query with no projection, BatchGetItem full item) are downstream of the first failed assertion and were not reached, but all are the same envelope.
Why: this is the over-permissive class and it leaks data. A session policy on dynamodb:Attributes/Select is the documented way to hand out a read credential that can see only a projection of an item (field-level tenancy, PII withholding). Against the emulator such a credential returns the whole item, so a control that proves "this credential cannot see `secret`" passes here and is false on AWS, and the AccessDeniedException the client must handle never occurs.
Fix: the DynamoDB data-plane authorization path — the handlers for GetItem, Query and BatchGetItem must (a) include the STS session's inline session policy as a separate scoping document in the evaluation (an Allow is required from both the identity set and the session policy; an explicit Deny in either wins) and (b) build the request condition context the evaluator needs: dynamodb:Select derived from the request (explicit Select, or SPECIFIC_ATTRIBUTES when a ProjectionExpression/AttributesToGet is present), dynamodb:Attributes from the projected attribute names (including the key attributes the request addresses), and dynamodb:LeadingKeys from the partition-key value(s) addressed, so a conditioned clause is decided instead of left undecided. The refusal must be rendered with AWS's session-policy attribution wording above.
