# cloudformation: DeletionPolicy=Snapshot on AWS::EC2::Volume takes NO EBS snapshot — the stack deletes the volume and leaves nothing behind (1 cause)

> _Note: this issue was identified against the code base at commit `6c1a210febfdea66ca602e6cad55ded855ffc229`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Cause 1 of 1: CloudFormation honours `DeletionPolicy: Snapshot` on AWS::EC2::Volume as if it were `Delete` — the volume is deleted and no EBS snapshot of it is ever created. Failing check: cloudformation.deep-cloudformation-2-snapshot-volume.

AWS: `DeletionPolicy` is documented "With the DeletionPolicy attribute you can preserve, and in some cases, backup a resource when its stack is deleted", and for the `Snapshot` value: "For resources that support snapshots, CloudFormation creates a snapshot for the resource before deleting it." AWS::EC2::Volume is one of the published snapshot-supporting types, and the snapshot CloudFormation takes for it is an ordinary ec2:CreateSnapshot call against the volume, not a member of the delete call. Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json): CreateSnapshot input {VolumeId (required), Description, TagSpecifications, OutpostArn, Location, DryRun}, output shape `Snapshot` {SnapshotId, VolumeId, VolumeSize, State (SnapshotState), Progress, StartTime, OwnerId, Encrypted, Description, Tags, …}, `errors: []`; DeleteVolume takes only VolumeId and models no final-snapshot member, so the snapshot cannot be a parameter of the delete. DescribeSnapshots is modelled paginated with `errors: []`, so a listing that matches nothing is an empty list, never a refusal. Recorded behavior for the end-to-end contract: after DeleteStack on a stack whose AWS::EC2::Volume carries `DeletionPolicy: Snapshot` reaches DELETE_COMPLETE, ec2:DescribeVolumes on the volume id is refused `InvalidVolume.NotFound` AND ec2:DescribeSnapshots with OwnerIds=["self"], Filters=[{Name:"volume-id",Values:[<volume id>]}] returns exactly ONE snapshot whose VolumeId is the deleted volume id, whose VolumeSize equals the volume's size and whose State is not `error`; that same snapshot is addressable directly by SnapshotIds=[<snapshot id>] and reports the same VolumeId.

Emulator: the stack reaches CREATE_COMPLETE, the volume is created and reported by DescribeVolumes at the requested size, DeleteStack reaches DELETE_COMPLETE and the volume is really gone (DescribeVolumes settles on `InvalidVolume.NotFound`, so that half of the policy is right) — but DescribeSnapshots filtered on that volume id returns an EMPTY list, both before and after the delete. No snapshot is created at any point, and no error is raised: the deletion silently behaves as the default `Delete` policy. The cause is in the per-type delete arm: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs computes the snapshot identifier for a `Snapshot` policy (`final_snapshot = (policy == deletion_policy::SNAPSHOT).then(|| final_snapshot_identifier(resource))`) and passes it to `Provisioner::delete`, but services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs routes `Self::Ec2Volume => delete_ec2_volume(ctx, region, physical_resource_id)` — the arm drops `final_snapshot` entirely, and the doc comment on `Provisioner::delete` states the design limit outright: `final_snapshot` "reaches the arms of the types whose owning service takes a snapshot ON THE WAY OUT, as a member of the delete call itself (Amazon RDS's FinalDBSnapshotIdentifier, Amazon Redshift's FinalClusterSnapshotIdentifier) — the published list of types Snapshot supports is wider than that, and a type whose snapshot is a call of its own is not one of these arms yet, so it is deleted with no snapshot taken". AWS::EC2::Volume is exactly such a type.

Why: a client that relies on `DeletionPolicy: Snapshot` to back up an EBS volume before the stack is torn down loses the volume's data with no indication anything went wrong — the stack reports DELETE_COMPLETE, the volume reports `InvalidVolume.NotFound`, and the backup it promised simply does not exist. Any restore flow (CreateVolume from SnapshotId), any `snapshot_completed` waiter, any `aws ec2 describe-snapshots --filters Name=volume-id,...` poll and any disaster-recovery runbook written against AWS reads an empty list where AWS has one completed snapshot, and cannot distinguish `Snapshot` from plain `Delete` at all.

Fix: the owning component is CloudFormation's per-type delete arm — `Provisioner::delete`'s `Self::Ec2Volume` branch in services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs must, when `final_snapshot` is `Some(..)`, call the owning service's ec2:CreateSnapshot for the volume (tagging it with the stack provenance and the derived identifier as its Description) and wait for the snapshot to be recorded before issuing DeleteVolume, so the snapshot survives the volume. That requires EC2's CreateSnapshot handler (services/service-com-amazonaws-ec2-amazonec2/src/ops/create_snapshot.rs, still carrying `//! SCAFFOLDED, NOT IMPLEMENTED:`) to write the snapshot into the same EC2 snapshot state the now-implemented DescribeSnapshots reads.
