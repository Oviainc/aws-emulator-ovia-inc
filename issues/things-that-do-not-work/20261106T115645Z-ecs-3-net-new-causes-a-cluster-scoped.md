# ecs: 3 net-new causes — a cluster-scoped Managed Instances capacity provider never blocks DeleteCluster, circuit-breaker rollback never happens, and ExecuteCommand's not-enabled refusal is unreachable

> _Note: this issue was identified against the code base at commit `20004884b35d4e30d0a51c1edcbd16198ad55508`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteCluster, UpdateService, ExecuteCommand

## Description
Three net-new root causes in the ECS emulator, each grounded in a behavioral check that the suite kills at its 60s ceiling because the emulator never produces any of the states the check polls for. All three are bounded-retry checks: a timeout here means the emulator answered, but never with the state AWS reaches, so the scenario never gets to its assertion.

Cause 1 of 3: DeleteCluster is never refused for an attached cluster-scoped (Managed Instances) capacity provider.
AWS: DeleteCluster models ClusterContainsCapacityProviderException and ClientException, both HTTP 400 (Smithy: DeleteCluster errors = AccessDeniedException, ClientException, ClusterContainsCapacityProviderException, ClusterContainsContainerInstancesException, ClusterContainsServicesException, ClusterContainsTasksException, ClusterNotFoundException, InvalidParameterException, ServerException, UpdateInProgressException). On a cluster that has a cluster-scoped Managed Instances capacity provider attached, DeleteCluster is refused with error code ClientException and the message "The Cluster cannot be deleted while Cluster Scoped Capacity Providers are attached to the cluster." — that message is entirely fixed text, it carries no request- or state-derived value — and the cluster stays non-INACTIVE with its capacityProviders association intact. The supporting path AWS offers: CreateCapacityProvider accepts a cluster-scoped provider (Smithy: CreateCapacityProvider.name required, optional cluster, managedInstancesProvider -> CreateManagedInstancesProviderConfiguration with infrastructureRoleArn and instanceLaunchTemplate), that provider settles asynchronously to a terminal status readable via DescribeCapacityProviders (status ACTIVE, or updateStatus CREATE_FAILED / status INACTIVE on failure), PutClusterCapacityProviders then attaches it, and DescribeClusters lists its name in cluster.capacityProviders.
Emulator: the check never reaches its DeleteCluster assertion. It is killed at the suite's 60s ceiling ("Check timed out after 60.0s") inside the bounded poll chain between CreateCapacityProvider and the DeleteCluster probe — the managed-instances provider never settles to a terminal status, and/or the attachment never shows up in DescribeClusters.capacityProviders, and/or DeleteCluster never returns a response other than UpdateInProgressException. No terminal state for the scenario is ever observable.
Why: a client that relies on ECS refusing to delete a cluster that still owns cluster-scoped capacity (the guard that keeps Managed Instances capacity from being orphaned) gets no guard at all here, and tooling that waits for a created capacity provider to become ACTIVE before attaching it waits forever.
Fix: the CreateCapacityProvider handler and the capacity-provider lifecycle in the ecs crate's state (a cluster-scoped managedInstancesProvider must reach a terminal status and be attachable), and the DeleteCluster handler's refusal path, which must raise ClientException with the fixed message above while a cluster-scoped capacity provider is attached and leave the cluster and its association untouched. Open issues 20261104T062603Z-ecs-daemon-scheduling-never-progresses-and-createcapacityprovider-rejects.md (CreateCapacityProvider rejects a valid Managed Instances monitoring value) and 20261104T062603Z-ecs-reads-hang-or-mis-resolve-on-clusters.md (capacity-provider reads time out) are adjacent but neither carries this check or this refusal contract.
Traces: ecs.delete-cluster-with-capacity-provider-rejected.

Cause 2 of 3: the deployment circuit breaker never fails a bad deployment and never rolls a service back.
AWS: a service created with deploymentConfiguration.deploymentCircuitBreaker {enable: true, rollback: true} (Smithy: UpdateService.deploymentConfiguration -> DeploymentConfiguration) that is updated to a revision whose image cannot be pulled ends THAT deployment with rolloutState FAILED and a rolloutStateReason that attributes the failure to the circuit breaker (AWS's text names the deployment circuit breaker, e.g. "ECS deployment circuit breaker: task failed to start."), then rolls back: running tasks settle on the prior stable revision, no task of the rejected revision survives, and the PRIMARY deployment references the prior revision with runningCount == desiredCount (1 here). ListServiceDeployments/DescribeServiceDeployments surface a record for that rollout whose serviceArn matches the service.
Emulator: the check is killed at the 60s ceiling before any of that is observable — the service's own first milestone (exactly one RUNNING task on the good revision, via ListTasks+DescribeTasks) and then the FAILED deployment for the bad revision never appear. Neither the rolloutState/rolloutStateReason bookkeeping nor the rollback effect is ever produced.
Why: a client that deploys behind the circuit breaker relies on ECS detecting an unlaunchable revision and restoring the last good one; against the emulator a bad deployment neither fails nor rolls back, so a deploy pipeline reports success (or hangs) on a revision that can never run.
Fix: the UpdateService handler and the service deployment state machine in the ecs crate (deployment records with rolloutState/rolloutStateReason, circuit-breaker evaluation and rollback to the prior stable revision, and the task lifecycle that must fail a task whose image cannot be pulled). Open issue 20261104T062603Z-ecs-rolling-deployment-controls-are-not-enforced-the.md reports the rolling-deployment controls for other checks but does not carry this check's replay key.
Traces: ecs.e2e-service-deployment-rollback-on-failed-taskdef.

Cause 3 of 3: ExecuteCommand's "not enabled at launch" refusal and its exec-enabled control are both unreachable.
AWS: ExecuteCommand models InvalidParameterException and TargetNotConnectedException at HTTP 400 (Smithy: ExecuteCommand errors = AccessDeniedException, ClientException, ClusterNotFoundException, InvalidParameterException, ServerException, TargetNotConnectedException). On a RUNNING task launched WITHOUT enableExecuteCommand, ExecuteCommand is refused with error code InvalidParameterException and the message "The execute command failed because execute command was not enabled when the task was run or the execute command agent isn't running. Wait and try again or run a new task with execute command enabled and try again." — entirely fixed text, no request- or state-derived parts. The refusal has no effect: DescribeTasks still reports enableExecuteCommand false, lastStatus unchanged (not STOPPED), and no ExecuteCommandAgent entry in containers[].managedAgents. For the contrasting case, a task launched WITH enableExecuteCommand and a task role reaches lastStatus RUNNING, its container's managedAgents gains an ExecuteCommandAgent whose lastStatus becomes RUNNING, and ExecuteCommand then succeeds with a session.
Emulator: the check is killed at the 60s ceiling before either side is exercised — the RunTask'd Fargate task never reaches lastStatus RUNNING (the check only proceeds on RUNNING/STOPPED/DEPROVISIONING) and the ExecuteCommandAgent managed agent never reaches RUNNING, so neither the success control nor the InvalidParameterException refusal is ever observed.
Why: a client cannot distinguish "exec is not enabled on this task" from "the agent is still connecting" — it gets a hang instead of the documented InvalidParameterException, and an exec-enabled task never becomes exec-able at all.
Fix: the task lifecycle in the ecs crate (a Fargate task must reach RUNNING and an exec-enabled task must publish an ExecuteCommandAgent managed agent that reaches RUNNING) and the ExecuteCommand handler's gate, which must refuse with InvalidParameterException and the fixed message above when the task was run without enableExecuteCommand, leaving the task record untouched. Open issue 20261104T062603Z-ecs-exec-the-executecommandagent-managed-agent-never-reaches.md names the agent cause for other exec checks but does not carry this check's replay key.
Traces: ecs.execute-command-without-enable-flag-rejected.
