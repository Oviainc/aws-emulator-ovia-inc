# ListCommonControls: the invalid-filter ValidationException message omits AWS's downstream-exception envelope suffix "(Service: …; Status Code: …; Request ID: …)"

> _Note: this issue was identified against the code base at commit `e968c00e41b0d1403a091108575069722ed2efa8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCommonControls

## Description
One net-new root cause in the controlcatalog emulator, grounded in two failing behavioral checks.

The open issue 20261029T183447Z-controlcatalog-getcontrol-ignores-caller-authorization-no-accessdeniedexception-and.md is in the same family (emulator-authored refusal wording) but names only the list-member constraint envelope and the invalid-NextToken sentence; it does not mention the invalid-filter sentence or ListCommonControls, so it does not cover this cause. The open issue 20261030T021409Z-controlcatalog-listcommoncontrols-returns-an-empty-commoncontrols-list-for-every--r2.md covers the SEPARATE defect that a single-objective filter returns no common controls — that is the later positive-control assertion of controlcatalog.common-control-filter-multiple-objectives-rejected and must be fixed there, not here.

Cause 1 of 1: the refusal of a multi-ARN CommonControlFilter.Objectives carries only the bare invalid-filter sentence, dropping the downstream-exception envelope AWS appends to that message.
  AWS: CommonControlFilter.Objectives is a list whose member documentation states the constraint directly (Smithy: com.amazonaws.controlcatalog#CommonControlFilter member Objectives -> ObjectiveResourceFilterList, doc "You can use this parameter to specify one objective ARN at a time. Passing multiple ARNs in the CommonControlFilter isn't supported."). ListCommonControls declares ValidationException (Smithy: com.amazonaws.controlcatalog#ValidationException, errorKind client, @httpError 400, doc "The request has invalid or missing parameters."). Recorded behavior only for the message: the Message value on the wire is the invalid-filter sentence FOLLOWED by the envelope of the downstream exception ControlCatalog surfaces, i.e. "The provided filter is not valid. Ensure that each part of the filter is valid, and try again. (Service: <downstream service name>; Status Code: <status>; Request ID: <request id>; …)". Fixed text: the sentence "The provided filter is not valid. Ensure that each part of the filter is valid, and try again." then a single space then the literal "(Service: ", and the "; Status Code: " / "; Request ID: " separators that follow. Variable parts, all per-request / per-deployment and NOT part of the requirement as literal values: the downstream service name, the numeric status code (400 for this class) and the request id, which must be the id of the request being refused rather than any value copied from a recording. The behavioral checks therefore assert only the stable prefix up to and including "(Service: ".
  Emulator: HTTP 400 and code ValidationException are correct, but the Message is exactly "The provided filter is not valid. Ensure that each part of the filter is valid, and try again." with no envelope at all — the string ends at the period, so the prefix match on "… try again. (Service: " fails. Observed for ListCommonControls called with CommonControlFilter={"Objectives": [{"Arn": <arn A>}, {"Arn": <arn B>}]}, both with and without MaxResults.
  Why: a client (or a test, or a log parser) that reads AWS's ValidationException Message for this class sees the service/status/request-id envelope AWS always appends and keys on it — to pull out the request id for a support case, or to match the full documented message text. Against the emulator that envelope is never present, so the parse yields nothing and the match never fires; a request-id-based correlation path that works against AWS is silently dead.
  Fix: this service's invalid-filter refusal wording — INVALID_FILTER_MESSAGE in services/service-com-amazonaws-controlcatalog-controlcatalog/src/service.rs:74-75, the single fixed sentence that crate::state::single_resource_filter_arn returns (src/state.rs:459-476, reached from SingleResourceFilter::read at src/state.rs:512-521) and that ListCommonControls lifts into its modeled ValidationException (src/ops/list_common_controls.rs:210-222). The sentence must be completed with the downstream-exception envelope, with the request id taken from the request currently being served; since the envelope is per-request it cannot be a compile-time constant and has to be assembled where the ValidationException is built. Every other list operation that funnels through single_resource_filter_arn (ListObjectives' ObjectiveFilter) shares the sentence and so shares the fix.
  Traces: controlcatalog.common-control-filter-multiple-objectives-rejected, controlcatalog.list-common-controls-multiple-objectives-filter-rejected.

## Evidence
controlcatalog.common-control-filter-multiple-objectives-rejected — ListObjectives(MaxResults=2) yielded two objective ARNs; cc.list_common_controls(MaxResults=10, CommonControlFilter={'Objectives': [{'Arn': arn_a}, {'Arn': arn_b}]}) raised ValidationException (code and HTTP 400 both as expected), but the harness asserted: "expected a message starting 'The provided filter is not valid. Ensure that each part of the filter is valid, and try again. (Service: ', got 'The provided filter is not valid. Ensure that each part of the filter is valid, and try again.'" (check line 43).

controlcatalog.list-common-controls-multiple-objectives-filter-rejected — cc.list_common_controls(CommonControlFilter={'Objectives': [{'Arn': arn1}, {'Arn': arn2}]}) (no MaxResults) produced the identical divergence: "expected a message starting 'The provided filter is not valid. Ensure that each part of the filter is valid, and try again. (Service: ', got 'The provided filter is not valid. Ensure that each part of the filter is valid, and try again.'" (check line 36).

Expected (AWS): Code ValidationException, HTTP 400, Message = "The provided filter is not valid. Ensure that each part of the filter is valid, and try again. (Service: <downstream service>; Status Code: 400; Request ID: <this request's id>; …)". Actual (emulator): Code ValidationException, HTTP 400, Message = "The provided filter is not valid. Ensure that each part of the filter is valid, and try again." — the envelope is absent. The refusal decision itself (reject a 2-element Objectives filter) is correct in both checks; only the message text diverges.
