# AppConfigData StartConfigurationSession misreports identifier refusals: wrong unresolved tier and 404 instead of 400 for a malformed identifier

> _Note: this issue was identified against the code base at commit `2d2373ac96719fb51b225d122133a9d558f5af51`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartConfigurationSession

## Description
Two root causes in the bootstrapped appconfigdata data plane, both in how StartConfigurationSession refuses an identifier it will not serve a session for. Both were replayed from the wire corpus simparity-wire-aws-v1 and both are CAUSES OF THIS ISSUE: a fixer must close BOTH before submitting. Cause 1 of 2 and Cause 2 of 2 below.

Cause 1 of 2 — when more than one tier of the triple is unresolvable, the WRONG tier is reported (fixture appconfigdata-lacs-traj-session-logical-ids-rejected-per-tier-then-names, step task#8).
AWS: Smithy StartConfigurationSession — POST /configurationsessions, success 201; ApplicationIdentifier, EnvironmentIdentifier and ConfigurationProfileIdentifier all target Identifier (@length 1..128, @required) and each is documented as "the ID or the name" of its level; ResourceNotFoundException (httpError 404) carries Message, ResourceType (enum: Application | ConfigurationProfile | Deployment | Environment | Configuration) and ReferencedBy, documented as "a map indicating which parameters in the request reference the resource that was not found". The model states no resolution ORDER, so the precedence is recorded behavior only: for a session request in which the configuration-profile tier is named by an identifier that is neither an id nor a name of an existing profile (the recording uses a CloudFormation logical id) and the environment tier is likewise not resolvable by the identifier given, AWS answers 404 reporting the CONFIGURATION PROFILE: Message "ConfigurationProfile not found", ResourceType "ConfigurationProfile", ReferencedBy {"ConfigurationProfileIdentifier": <the identifier the request carried>}. Message rule: the whole message is fixed text of the form "<ResourceType> not found" — here exactly "ConfigurationProfile not found" — and interpolates nothing; the only request-derived parts of the response are the ReferencedBy entry's KEY (the input member name that referenced the missing resource) and its VALUE (the identifier that member carried). The logical id in the recording is a per-run value that fills that slot and is not part of the requirement. Hypothesis: AWS resolves the configuration profile — a direct child of the application, and the thing that identifies the configuration a session is over — before it resolves the environment, so the profile tier wins the report when both are unresolvable.
Emulator: the same request is refused 404 but reports the ENVIRONMENT tier: Message "Environment not found", ResourceType "Environment", and ReferencedBy carries no ConfigurationProfileIdentifier key at all (the replay reports $.Message value_mismatch expected 'ConfigurationProfile not found' got 'Environment not found'; $.ResourceType value_mismatch expected 'ConfigurationProfile' got 'Environment'; $.ReferencedBy.ConfigurationProfileIdentifier missing). The resolution helper walks the hierarchy strictly outermost-first (application, then environment, then configuration profile) and returns on the first level that fails, so the environment always pre-empts the profile.
Why: a client reads ResourceType and ReferencedBy to learn WHICH of its three parameters is wrong — that is the documented purpose of ReferencedBy. Against this emulator an operator whose configuration-profile identifier is wrong is told to fix the environment instead, and tooling that keys off ResourceType (or looks up ReferencedBy["ConfigurationProfileIdentifier"]) finds nothing and mis-reports the failure; the emulator teaches a diagnostic precedence AWS does not have.
Fix: the appconfigdata session-resolution layer — the tier precedence in the shared triple-resolution helper that StartConfigurationSession consults before minting (and that GetLatestConfiguration re-uses) must match AWS's order, reporting the configuration profile ahead of the environment, with ReferencedBy keyed by that tier's own input member.

Cause 2 of 2 — an ARN-form identifier is looked up and missed (404) instead of being refused as malformed input (400) (fixture appconfigdata-lacs-traj-session-logical-ids-rejected-per-tier-then-names, step task#10).
AWS: the operation models BadRequestException (httpError 400, "The input fails to satisfy the constraints specified by the service", members Message, Reason -> BadRequestReason with the single value "InvalidParameters", Details -> union BadRequestDetails{InvalidParameters: map of parameter name -> InvalidParameterDetail}) alongside ResourceNotFoundException (404), ThrottlingException (429) and InternalServerException (500). Identifier carries only @length 1..128, so the rule that a full resource ARN is NOT an acceptable value for ApplicationIdentifier is recorded behavior only: for a StartConfigurationSession whose ApplicationIdentifier is an AppConfig application ARN (arn:aws:appconfig:<region>:<account>:application/<applicationId>) instead of the id or the name, AWS answers HTTP 400 with a modeled error type in x-amzn-errortype — it treats the value as input that fails the service's constraints rather than as an identifier that resolved to nothing. Message rule: the recording asserts the 400 status and the PRESENCE of x-amzn-errortype (its value is shaped-not-asserted) and asserts no body members, so the requirement here is the status class and the modeled client-error type; no message text is claimed for it. Hypothesis (neither the model nor the recording states it): the error is BadRequestException with Reason "InvalidParameters" and Details.InvalidParameters keyed by the offending member name "ApplicationIdentifier".
Emulator: answers 404 with x-amzn-errortype: ResourceNotFoundException and body {"__type": "ResourceNotFoundException", "Message": "Application not found", "ResourceType": "Application", "ReferencedBy": {"ApplicationIdentifier": <the ARN from the request, echoed verbatim>}} — it passes the ARN straight into the control-plane id-or-name lookup, misses, and reports a missing application. The replay reports status expected 400 got 404 and $headers.x-amzn-errortype shape_mismatch.
Why: the status class is the client's branch point. An SDK caller that passed an ARN (the form CloudFormation/CDK outputs hand out, so a very common mistake) is told the application does not exist instead of that its parameter is malformed: a bootstrapping poller that reads 404 as "nothing deployed yet" waits forever, retry/error classification differs from AWS, and the caller never learns the value itself is unacceptable.
Fix: StartConfigurationSession's input validation — the identifier form must be validated (an id or a name, not an ARN) and refused with the modeled BadRequestException BEFORE the triple is resolved against the control plane, so a malformed identifier never becomes a ResourceNotFoundException.
