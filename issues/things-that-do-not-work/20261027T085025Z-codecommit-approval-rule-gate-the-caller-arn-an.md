# CodeCommit approval-rule gate: the caller ARN an approval is recorded under can never match an ApprovalPoolMembers assumed-role entry, and the author guard on UpdatePullRequestApprovalState skips REVOKE (2 causes)

> _Note: this issue was identified against the code base at commit `9cf2ebd925d1a1f6505c9155fdd17f25927ece5d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
EvaluatePullRequestApprovalRules

## Description
Two net-new behavioral root causes on the CodeCommit pull-request approval surface. Both are reached only now that UpdatePullRequestApprovalState is implemented (it no longer answers 501), so neither is the 501 that open issue 20261025T123952Z-codecommit-pull-request-approval-surface-updatepullrequestapprovalstate-answers-501.md describes. Cause 1 is the SHARED evaluation that open issue 20261026T234121Z-codecommit-mergepullrequestbysquash-still-refuses-with-pullrequestapprovalrulesnotsatisfiedexception-after-a.md names as one of three candidate explanations for MergePullRequestBySquash; that issue carries only the replay key codecommit.e2e-merge-pull-request-approval-rules-not-satisfied-rejected and is scoped to the merge operation, so it does not cover EvaluatePullRequestApprovalRules' own wrong answer and does not carry either check listed here. Neither open issue covers Cause 2 at all.

Cause 1 of 2: EvaluatePullRequestApprovalRules reports approved=false and leaves the rule in approvalRulesNotSatisfied after a genuine non-author APPROVE, because the principal ARN an approval is recorded under is always synthesized as an IAM user ARN and so can never match an Approvers statement's ApprovalPoolMembers entry written as an assumed-role ARN. Failing check: codecommit.e2e-pull-request-approval-and-merge-flow.

AWS: Smithy models EvaluatePullRequestApprovalRules with input pullRequestId (@required, PullRequestId) and revisionId (@required, RevisionId) and output evaluation (@required, Evaluation). Evaluation carries approved (Boolean, default false) documented 'Whether the state of the pull request is approved', overridden (Boolean, default false), approvalRulesSatisfied (ApprovalRulesSatisfiedList) documented 'The names of the approval rules that have had their conditions met', and approvalRulesNotSatisfied (ApprovalRulesNotSatisfiedList) documented 'The names of the approval rules that have not had their conditions met'. Smithy models UpdatePullRequestApprovalState with input pullRequestId (@required), revisionId (@required) and approvalState (@required, enum ApprovalState: APPROVE | REVOKE) and a Unit output, documented 'Updates the state of a user's approval on a pull request. The user is derived from the signed-in account when the request is made.' Smithy's Approval shape documents approvalState as 'The state of the approval, APPROVE or REVOKE. REVOKE states are not stored.' The rule document under test is an Approvers statement with NumberOfApprovalsNeeded 1 whose ApprovalPoolMembers holds one entry of the fixed form 'arn:aws:sts::<account-id>:assumed-role/<role-name>/*' — the fixed parts are the 'arn:aws:sts::' prefix, the ':assumed-role/' separator and the trailing '/*' wildcard; the account id and role name come from the request/environment. AWS's rule: when a principal that is NOT the pull request's author calls UpdatePullRequestApprovalState with approvalState APPROVE on the pull request's current revisionId, and that principal's own caller ARN is matched by the statement's pool, the statement is met; once every statement of every applied rule is met, EvaluatePullRequestApprovalRules answers HTTP 200 with evaluation.approved true, the rule name in approvalRulesSatisfied and approvalRulesNotSatisfied empty. For a session created by sts:AssumeRole, the caller ARN AWS matches against the pool is the assumed-role session ARN 'arn:aws:sts::<account-id>:assumed-role/<role-name>/<session-name>', which is exactly what the '/*' entry exists to cover; it is never an 'arn:aws:iam::<account-id>:user/...' ARN.
Emulator: the approval IS accepted and IS stored — the replay's GetPullRequestApprovalStates immediately after the approver's call returns exactly one entry with approvalState 'APPROVE' (that assertion passes) — but the very next EvaluatePullRequestApprovalRules on the same pullRequestId/revisionId answers HTTP 200 with evaluation {'approved': False, 'overridden': False, 'approvalRulesSatisfied': [], 'approvalRulesNotSatisfied': ['<the rule name>']}. The rule is therefore counted against an approver set that does not contain the approval that was just stored. The identity the approval is keyed by is derived with no notion of a role session at all: it is built from the request's SigV4 access key id and always rendered as an IAM user ARN of the emulator account, so it is structurally incapable of being matched by a pool entry of the 'arn:aws:sts::...:assumed-role/<role>/*' form no matter how the wildcard matcher behaves. The pool filter then counts 0 approvers against NumberOfApprovalsNeeded 1 and reports the rule unmet.
Why: approval-gated review is unusable. A client that approves a pull request as the second identity its own rule names sees the approval come back from GetPullRequestApprovalStates yet sees EvaluatePullRequestApprovalRules keep saying approved=false, and because MergePullRequestBySquash asks the same question the merge is then refused forever. Review tooling that polls EvaluatePullRequestApprovalRules until approved=true never terminates, and a release pipeline's 'merge only once approved' gate can never go green. Worse, the answer is indistinguishable from the legitimate 'not approved yet' answer, so a caller cannot tell an unmet rule from an uncountable one. Any rule whose pool is written as an assumed-role ARN — the form AWS's own console and docs produce for role-based review pools — can never be satisfied.
Fix: the caller-identity derivation and the approval-pool matching that the one shared rule evaluation reads. The caller ARN must reflect an assumed-role session when the request is signed with session credentials (an 'arn:aws:sts::<account>:assumed-role/<role>/<session>' ARN) rather than always an IAM user ARN, and the approver set the rule is counted against must be those ARNs; it belongs in the shared state helper both EvaluatePullRequestApprovalRules and the merge operations read, not per handler. See Traces for the file and line citations.

Code citations: services/service-com-amazonaws-codecommit-codecommit-20150413/src/state.rs:3861-3873 (caller_identity_arn builds ::engine::emulator_arn("iam", "", "user/<akid>") from the SigV4 access key id and nothing else); src/state.rs:3308-3343 (approval_rule_satisfied filters the approver set through ApprovalPoolMembers via approval_pool_includes and compares the count to NumberOfApprovalsNeeded); src/state.rs:2658-2691 (approval_rules_by_condition / approval_rules_satisfied, the one split evaluation and merge share); src/ops/update_pull_request_approval_state.rs:266 (the reviewer key is that same caller_identity_arn); src/ops/evaluate_pull_request_approval_rules.rs:253-265 (the response is built straight from that split).

Cause 2 of 2: UpdatePullRequestApprovalState accepts approvalState=REVOKE from the pull request's own author with HTTP 200 instead of refusing it with PullRequestCannotBeApprovedByAuthorException. Failing check: codecommit.pull-request-approval-states-reflect-rule-evaluation.

AWS: Smithy models UpdatePullRequestApprovalState's approvalState as @required enum ApprovalState with values APPROVE | REVOKE, and lists PullRequestCannotBeApprovedByAuthorException among its errors (errorKind client, httpError 400 [defaulted]). The model places NO condition on approvalState for that error — it is declared for the operation, not for one enum value. The exception's modelled documentation is the error message itself and is entirely FIXED text, interpolating nothing from the request or state: 'The approval cannot be applied because the user approving the pull request matches the user who created the pull request. You cannot approve a pull request that you created.' Recorded behavior shows the rule AWS applies: the author of a pull request calling UpdatePullRequestApprovalState is refused with HTTP 400 / PullRequestCannotBeApprovedByAuthorException and that exact message for BOTH approvalState values, and nothing is recorded — a following GetPullRequestApprovalStates returns approvals == [] and EvaluatePullRequestApprovalRules still reports approved false. The emulator already gets the APPROVE leg of this exactly right: the same check's earlier author-APPROVE assertions on the code and the full message both pass, as does the 'no approval recorded as a side effect' read after it. Only the REVOKE leg diverges.
Emulator: the author guard is gated on the requested state, so an author's REVOKE never reaches it. UpdatePullRequestApprovalState returns HTTP 200 with an empty body for pullRequestId=<the author's own PR>, revisionId=<its current revision>, approvalState='REVOKE'; the replay's _client_error helper raises AssertionError('expected the call to be rejected, but it succeeded') at check line 166. Expected HTTP 400 with code PullRequestCannotBeApprovedByAuthorException and the fixed message above; observed HTTP 200 and no error at all.
Why: the author-cannot-self-review invariant is only half enforced, and the half that is missing is the one a client cannot detect any other way. A caller that treats a 200 from UpdatePullRequestApprovalState as 'my approval state is now what I asked for' is told the author's REVOKE took effect; a tool that discovers whether an identity may touch a pull request's approval state by probing REVOKE (the harmless direction) concludes the author may, then fails on APPROVE. Error-handling paths written against the real service — catch PullRequestCannotBeApprovedByAuthorException, fall back to requesting review from someone else — are never exercised in the emulator for REVOKE, so the guard looks present and is not. It also makes the two enum values of one @required member behave under different authorization rules, which AWS does not do.
Fix: the author check in the UpdatePullRequestApprovalState handler must apply to the operation, not to a single approvalState value — the identity comparison has to run before the requested state is considered. See Traces for the file and line citation.
Traces: codecommit.pull-request-approval-states-reflect-rule-evaluation, failing at check line 166. Code citation: services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/update_pull_request_approval_state.rs:312-329 — the guard reads `if requested == crate::state::APPROVAL_STATE_APPROVE && pull_request.author_arn == reviewer`, with an in-file comment asserting that 'Revoking is not approving, and an author holds no approval to revoke, so it is only an approval that is refused here'; the recording contradicts that premise. The subsequent no-op path at lines 335-369 is why the call then returns 200 having changed nothing.
