# bedrock__logs: PutModelInvocationLoggingConfiguration performs no PassRole decision on cloudWatchConfig — every CloudWatch Logs destination is accepted 200, so the environment's AccessDeniedException "Cross-account pass role is not allowed." refusal is never produced (1 cause)

> _Note: this issue was identified against the code base at commit `02f6d4f25c27220a14c0924662b79788aefc3700`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutModelInvocationLoggingConfiguration

## Description
Related open issue: 20261027T044413Z-bedrock-reopens-bedrock-putmodelinvocationloggingconfiguration-a-same-account-cloudwatchconfig-role.md describes the OPPOSITE symptom (every cloudWatchConfig refused 403) and does NOT carry this check's replay key, so this failure is not covered by it; it is filed here so the check id below gets re-replayed. Both symptoms share one underlying fact: the cloudWatchConfig branch makes no decision at all, it is hard-wired — previously to refuse, now to accept.

=== Cause 1 of 1: the cloudWatchConfig branch of PutModelInvocationLoggingConfiguration is unconditionally accepting, so the modeled AccessDeniedException can never be reached ===

AWS: Smithy (com.amazonaws.bedrock) models PutModelInvocationLoggingConfiguration as PUT /logging/modelinvocations, success code 200 with an empty output shape, one required input member `loggingConfig` (LoggingConfig), and errors AccessDeniedException (httpError 403), ValidationException (400), ThrottlingException (429), InternalServerException (500). LoggingConfig.cloudWatchConfig targets CloudWatchConfig, whose `logGroupName` (@length 1..512) and `roleArn` (@length max 2048, @pattern ^arn:aws(-[^:]+)?:iam::([0-9]{12})?:role/.+$) are both required. The model does not state the outcome of the PassRole step that enabling a CloudWatch Logs destination requires, so for the OUTCOME: recorded behavior only. The grounding recording (behavioral check below, measured against the corpus's AWS environment) shows the REFUSAL path: a cloudWatchConfig naming a log group created moments earlier and a roleArn for a role created moments earlier with trust policy {Effect Allow, Principal {Service bedrock.amazonaws.com}, Action sts:AssumeRole} and an inline policy granting logs:CreateLogStream / logs:PutLogEvents / logs:DescribeLogStreams scoped to that group's ARN is refused on the FIRST call with HTTP 403, error code AccessDeniedException, message "Cross-account pass role is not allowed." — the recording also establishes that the only transient AWS uses while IAM propagates is ValidationException whose message contains "Failed to validate permissions", never AccessDeniedException, and that the refused call leaves the account singleton unchanged (an independent GetModelInvocationLoggingConfiguration returns exactly the prior loggingConfig). Message anatomy for this error class: "Cross-account pass role is not allowed." is entirely FIXED text — it has no variable part, it names neither the roleArn nor either account id. The refusal is therefore a decision over the submitted roleArn (the role's account vs. the caller's account, and whether the role's trust policy admits the bedrock.amazonaws.com service principal), not a property of the particular ARN string in any one run.

Emulator: the PUT is ACCEPTED. The emulator answers the success code (HTTP 200, empty body) for the cloudWatchConfig above on the first attempt, so no AccessDeniedException is ever produced for the cloudWatchConfig branch. Replay output: `AssertionError: PutModelInvocationLoggingConfiguration accepted a CloudWatch Logs destination in this environment; the withdrawal this check asserts no longer holds and it needs rewriting back to the log event shape its name promises.` The positive control in the same check succeeded (GetFoundationModel for amazon.nova-lite-v1:0 returned modelDetails with modelLifecycle.status=ACTIVE), so the caller does reach Bedrock's own logic and the acceptance is this operation's behavior, not a credential/front-door artifact. Note the contradictory sibling recording cited by the related issue above, in which a same-account correctly-trusted role is ACCEPTED 200: taken together the two recordings mean the branch must DECIDE per role rather than be constant in either direction — a constant-accept branch cannot satisfy the refusal recording and a constant-refuse branch cannot satisfy the acceptance recording.

Why: a client relying on AWS's behavior sees a CloudWatch Logs invocation-logging destination reported as configured when the account's PassRole boundary would have rejected it. Audit/compliance wiring (console-equivalent setup, Terraform/CloudFormation convergence, a CI bootstrap that Puts then Gets) reports success and the operator believes model-invocation records are being delivered into the log group, when on AWS the configuration was refused and nothing is delivered. Negative-path clients that catch AccessDeniedException to fall back to an S3 destination, or to surface a PassRole remediation message, never take that branch at all; and because nothing is refused, the "refused call leaves no partial state" guarantee is untested in the emulator.

Fix: the cloudWatchConfig branch of PutModelInvocationLoggingConfiguration's handler/validation. It must perform an actual PassRole decision over cloudWatchConfig.roleArn — parse the account id out of the ARN and compare it with the caller's account, and consult the referenced role's trust policy for a statement allowing sts:AssumeRole to Principal Service bedrock.amazonaws.com — and on a negative decision refuse with the modeled AccessDeniedException (HTTP 403) carrying the fixed message "Cross-account pass role is not allowed.", committing nothing to the account-singleton logging state so an independent GetModelInvocationLoggingConfiguration still returns the prior loggingConfig. On a positive decision it keeps today's 200/empty-body behavior and commits the loggingConfig. Any propagation transient belongs on ValidationException with the "Failed to validate permissions" wording, not on AccessDeniedException.

Traces: bedrock__logs.model-invocation-log-event-shape-at-cloudwatch-logs. Handler: services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/src/ops/put_model_invocation_logging_configuration.rs.
