# apigatewayv2__dynamodb__lambda: the binary-frame refusal check hangs to the 60 s cap — a deployed WEBSOCKET stage never completes the RFC 6455 upgrade, so the CLOSE 1003 frame-opcode policy is unreachable (1 cause)

> _Note: this issue was identified against the code base at commit `feb204971e0c529b59922c31c571e9b68abdb6f7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
$default (WebSocket data plane / execute-api upgrade)

## Description
Cause 1 of 1: the WebSocket duplex check that grades the binary-frame refusal builds its whole stack successfully (DynamoDB table, Lambda handler, apigatewayv2 API with ProtocolType=WEBSOCKET and $connect/$disconnect/$default routes, an AWS_PROXY integration, a deployment and a stage) and then never obtains a 101 upgrade on the deployed stage. It blocks in the handshake poll (`_poll_until(lambda: _try_ws_connect(ctx, api['api_id'], api['stage']), lambda s: s is not None, timeout_s=150.0, interval_s=3.0, description=f"WebSocket handshake against stage {api['stage']}")`) and is cut by the harness cap, reporting `Check timed out after 60.0s`. Because no socket is ever upgraded, every leg this check grades — the text-frame positive control, the binary-frame refusal, and the absence assertion — is unreachable. Failing check id: apigatewayv2__dynamodb__lambda.wsduplex-client-binary-frame-rejected-close-1003.

AWS: recorded behavior only for the opening handshake and the frame policy — neither is a modeled operation; the upgrade is the execute-api data plane. Smithy (apigatewayv2, com-amazonaws-apigatewayv2-apigatewayv2.json): shape ProtocolType is an enum with values [WEBSOCKET, HTTP]; Api.ProtocolType is required; Api.RouteSelectionExpression is required and documented as "The route selection expression for the API" (for WebSocket APIs it selects the route from the frame); Api.ApiEndpoint is documented as "The URI of the API, of the form {api-id}.execute-api.{region}.amazonaws.com. The stage name is typically appended to this URI to form a complete path to a deployed API stage." On real AWS, an RFC 6455 opening handshake against that stage URL is answered `HTTP/1.1 101 Switching Protocols` with a `Sec-WebSocket-Accept` derived from the client's `Sec-WebSocket-Key`; $connect then runs with requestContext.connectionId/domainName/stage; a client TEXT frame (opcode 0x1) is routed by the route-selection expression to $default and the integration can push back through ApiGatewayManagementApi PostToConnection; a client BINARY frame (opcode 0x2) on a WebSocket API is refused at the edge with an RFC 6455 CLOSE frame (opcode 0x8) whose 2-byte status code is 1003 and whose reason is the fixed text `Binary is not supported`, after which the service tears the socket down and $default is never invoked for that frame. In that close payload the status code (1003) and the reason text (`Binary is not supported`) are both FIXED — nothing in it is taken from the request or from state.

Emulator: no 101 is ever returned for the upgrade on the deployed WEBSOCKET stage, so the handshake poll never yields a socket and the check hangs until the harness cuts it (`Check timed out after 60.0s`). No frame can therefore be sent at all, and consequently the frame-opcode policy is never exercised: the emulator never emits a CLOSE frame, never emits close code 1003, and never emits the reason `Binary is not supported`.

Why: a client relying on AWS behavior gets no WebSocket data plane. wss:// connects fail rather than upgrading, so $connect/$default/$disconnect never fire, nothing is written to or removed from DynamoDB, PostToConnection push-back never happens, and a client that sends a binary frame to a text-only WebSocket API receives neither the 1003 close nor a socket teardown — it simply waits. A client cannot distinguish "refused" from "hung", and an over-permissive relay of binary frames to the integration would be equally undetectable.

Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer. Recognise the RFC 6455 upgrade on a deployed WEBSOCKET API's stage path and answer 101 with a correct Sec-WebSocket-Accept instead of falling through to the generic not-found handler; then mint a connection id, invoke $connect, route frames through the route-selection expression, and add the frame-opcode policy that answers a client BINARY frame with CLOSE 1003 + reason `Binary is not supported` and closes the socket without invoking $default. This is a capability gap in the data-plane router and session layer, not an error-shape bug in a modeled operation.

Expected (real AWS):
- Opening handshake on the deployed stage URL -> `HTTP/1.1 101 Switching Protocols` + `Sec-WebSocket-Accept` derived from the client key.
- Client TEXT frame (opcode 0x1) carrying a marker -> $default invoked; a `msg#<sha256(marker)>` row appears in the DynamoDB table with `len` = the marker's byte length and `b64` = false; the integration's PostToConnection delivers `{"sha": <digest>, "len": <length>}` back on the same socket.
- Client BINARY frame (opcode 0x2) with the same payload shape -> one RFC 6455 CLOSE frame, opcode 0x8, first two payload bytes = close code 1003, remaining payload = the fixed reason text `Binary is not supported`; then the socket is torn down (next recv returns b""); and no `msg#<sha256(bin marker)>` row ever appears, proving $default was not invoked for the refused frame.

Actual (emulator): the check never gets past the handshake. It blocks in `_poll_until(lambda: _try_ws_connect(ctx, api['api_id'], api['stage']), lambda s: s is not None, timeout_s=150.0, interval_s=3.0, description=f"WebSocket handshake against stage {api['stage']}")` — `_try_ws_connect` returns None for every attempt because the response's first line does not contain ` 101 ` — and the harness reports `Check timed out after 60.0s`. No CLOSE frame, no close code 1003 and no `Binary is not supported` reason are ever produced, and no DynamoDB row (neither the text-control `msg#` row nor its absence counterpart) can be observed.
