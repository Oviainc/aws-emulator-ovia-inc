# events: API destinations never deliver or dead-letter, and PutRule accepts ScheduleExpressions and reports a DeleteRule refusal message AWS does not use (3 causes)

> _Note: this issue was identified against the code base at commit `b1a4a993822b0574a1f24a3d622a9d42702ca481`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRule

## Description
Three net-new root causes in the events service.

Cause 1 of 3: an EventBridge API destination target neither issues the HTTP request nor dead-letters on failure, so no API-destination contract (auth header, method, body, retry/dead-letter classification, invocation rate limiting) can be observed.
Failing checks: events.api-destination-4xx-dead-letters-without-retry-while-5xx-is-retried-until-its-retry-attempts-are-used-up, events.api-destination-basic-connection-sends-the-basic-authorization-header-with-the-destinations-method-and-the-bare-envelope, events.api-destination-rate-limit-defers-a-burst-it-cannot-absorb-and-still-delivers-every-event.
AWS: a matched event whose target is an API destination is sent to the destination's InvocationEndpoint using the destination's HttpMethod, carrying the connection's auth material (for a BASIC connection, `Authorization: Basic <base64(user:password)>`), no query string unless configured, and the bare EventBridge envelope as the body; an input transformer on a second rule sends the rendered template instead. A 4xx response (400) is a non-retryable failure: the event is dead-lettered immediately, with the dead-letter attributes recording the failure (ERROR_CODE `INVALID_PARAMETER`) and no retry; a 5xx (500) is retried until the target's RetryPolicy.MaximumRetryAttempts is used up and only then dead-lettered, with the dead letter recording the exhausted retry count. A destination limited to InvocationRateLimitPerSecond = 1 defers a 60-event burst and still delivers each event exactly once, none dead-lettered, spread over time rather than dropped. Recorded behavior only for the wire details; Smithy (eventbridge) models Target.RetryPolicy{MaximumRetryAttempts, MaximumEventAgeInSeconds}, Target.DeadLetterConfig.Arn and ApiDestination{HttpMethod, InvocationEndpoint, InvocationRateLimitPerSecond}, so all of these knobs are modeled inputs the emulator accepts and then ignores.
Emulator: nothing is delivered and nothing is dead-lettered. The 4xx/5xx check fails with `TimeoutError: an event dead-lettered by both targets: the run budget ended first; not graded`; the BASIC-connection and rate-limit checks end `Check timed out after 60.0s`. The capture endpoint sees no request and the DLQ stays empty.
Why: a client that fans events to an HTTP endpoint through an API destination gets no calls and no dead letters — failures are silent, so neither delivery nor loss is detectable, and the retry/rate-limit configuration it set has no effect.
Fix: the API-destination target dispatch path in the events crate — resolve the destination and its connection, build and sign/authorize the HTTP request (method, headers, body, connection auth parameters), apply InvocationRateLimitPerSecond, classify the response (4xx non-retryable vs 5xx retryable), honour the target RetryPolicy and write the AWS dead-letter attributes to DeadLetterConfig.Arn. Open issues 20261025T084539Z-events-eventbridge-api-destinations-and-connections-diverge-no-http.md, 20261027T052336Z-events-4-net-new-behavioral-root-causes-api.md and 20261027T200000Z-events-eventbridge-an-oauth-client-credentials-connection-never-fetches-a-token-so-its-api-destination-never-delivers.md own neighbouring checks in this group; none carries these three replay keys.

Cause 2 of 3: PutRule performs no ScheduleExpression grammar validation — malformed rate()/cron() expressions are accepted and the rule is created (or an existing rule's schedule is replaced), where AWS refuses them.
Failing checks: events.put-rule-schedule-expression-grammar-rejection, events.put-rule-update-to-a-cron-with-both-day-fields-rejected-keeping-the-old-schedule.
AWS: PutRule parses ScheduleExpression and refuses an invalid one with HTTP 400 and Error.Code `ValidationException`, creating no rule and — on an update — leaving the existing rule's schedule untouched. The refused forms include a singular rate value with a plural unit (`rate(1 minutes)`), a plural value with a singular unit (`rate(5 minute)`), a zero value (`rate(0 minutes)`), a unit finer than a minute (`rate(30 seconds)`), a unit outside minute/hour/day (`rate(1 fortnight)`), a five-field cron (`cron(0 12 * * ?)` — the AWS dialect requires six fields) and a cron naming BOTH day-of-month and day-of-week concretely or with `*` in both (`cron(0 12 * * * *)`, `cron(05 23 27 * * *)`). The message's fixed text is AWS's per-form validation wording and its variable part is the caller's own expression. Smithy (eventbridge): PutRule.ScheduleExpression is `@length(min:0,max:256)` with no pattern and PutRule's modeled errors do not include ValidationException, so the grammar and its ValidationException refusal are recorded behavior only; the AWS schedule-expression reference documents the rule.
Emulator: every one of those expressions is ACCEPTED. The grammar check fails with `AssertionError: expected a ClientError, but the call SUCCEEDED`, and the update check with `AssertionError: the call succeeded; real AWS refuses it` for `cron(05 23 27 * * *)` — so a live rule's schedule is also silently replaced with an invalid one.
Why: a typo in a schedule is accepted and the rule then never fires (or fires on an unintended cadence) with no error anywhere; worse, an update that AWS would reject destroys a working schedule here.
Fix: input validation for PutRule — parse and validate ScheduleExpression (rate unit/value agreement and allowed units; six-field cron with exactly one of day-of-month/day-of-week specified) in the operation's validation layer, before any state change, and refuse with 400 ValidationException so the prior rule is left intact.

Cause 3 of 3: DeleteRule's refusal for a rule that still has targets uses an emulator-authored message instead of AWS's wording.
Failing check: events.disabled-rule-keeps-its-ecs-target-and-delete-is-still-rejected-until-removed.
AWS: DeleteRule without Force on a rule that still has targets is refused with HTTP 400, Error.Code `ValidationException` and the message `Rule can't be deleted since it has targets.` — the whole message is fixed text, with no rule name, no target count and no remediation clause; the refusal applies equally whether the rule is ENABLED or DISABLED, and the targets survive. Smithy (eventbridge): DeleteRule models Name, EventBusName and `Force` (default false) and its modeled errors do not include ValidationException, so the code/message pairing is recorded behavior only.
Emulator: the code is right but the message is rewritten: `('ValidationException', 'Rule sim2real-ebecs-6068968410a3 cannot be deleted since it still has 1 target(s). Remove them with RemoveTargets first.')`. The fixed text differs entirely and the message interpolates two values AWS never includes — the rule name taken from the request and the target count taken from emulator state.
Why: clients and CLI wrappers that match on the refusal text to distinguish "remove targets first" from other validation failures take the wrong branch, and recorded-response comparisons fail on a message the service never produces.
Fix: the DeleteRule handler's refusal construction in the events crate — emit the fixed AWS message for this error class rather than formatting the rule name and target count into it. Fixed issue 20261029T235600Z-events-client-error-messages-are-emulator-authored-instead.md covered nine other events refusals; this DeleteRule message is still emulator-authored.
Traces: the six failing check ids listed above.

## Evidence
Cause 1 — Expected: the 400 endpoint's event is dead-lettered immediately with ERROR_CODE INVALID_PARAMETER and no retry while the 500 endpoint's event is retried until MaximumRetryAttempts (1) is exhausted and then dead-lettered recording the exhausted retries; a BASIC connection's destination receives a PUT carrying `Authorization: Basic <base64(user:password)>`, no query string and the bare envelope as body; a 60-event burst at a 1/s destination is delivered once each, none dead-lettered, spread over at least 10 s. Actual: `TimeoutError: an event dead-lettered by both targets: the run budget ended first; not graded` and `Check timed out after 60.0s` (x2) — no HTTP request reaches the capture endpoint and the DLQ stays empty.

Actual: `AssertionError: expected a ClientError, but the call SUCCEEDED` and `AssertionError: the call succeeded; real AWS refuses it`.

Remove them with RemoveTargets first.') — same code, wholly different fixed text plus a request-derived rule name and a state-derived target count AWS never emits.

## Steps to Reproduce
Cause 1: create an API_KEY (or BASIC) connection and two API destinations pointing at an HTTPS endpoint that answers 400 and 500 respectively; put both as targets of one rule with DeadLetterConfig and RetryPolicy{MaximumRetryAttempts:1, MaximumEventAgeInSeconds:900} and a RoleArn allowing events:InvokeApiDestination; PutEvents one matching event and poll the DLQ and the capture endpoint. Repeat with a BASIC connection and with a destination whose InvocationRateLimitPerSecond is 1 and a 60-event burst.
Cause 2: call PutRule with each malformed expression above and then DescribeRule/ListRules for that name — AWS answers 400 ValidationException and no rule exists. Then PutRule a valid schedule, PutRule the same Name with `cron(05 23 27 * * *)` and DescribeRule — AWS refuses and the old schedule is intact.
Cause 3: PutRule a rule, PutTargets one target, DisableRule, then DeleteRule without Force and read Error.Code and Error.Message.
