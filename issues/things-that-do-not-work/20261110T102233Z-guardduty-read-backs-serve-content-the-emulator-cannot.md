# GuardDuty read-backs serve content the emulator cannot back: investigation analysis absent and IPSet location points off-emulator

> _Note: this issue was identified against the code base at commit `4c5ed4b9d036a2e1417b0b3c05fbe59e6fe27101`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetInvestigation

## Description
This issue bundles 2 distinct net-new replay clusters, both in the guardduty service and both on a GET read-back projection. Fix BOTH causes and re-replay both fixture#steps (the representative in Issue-Trace/Issue-Step plus the one in Issue-Trace-Ids) before submitting; closing one leaves the other unexercised. Neither cluster is blocked by a stub (stub_path="") and neither is marked owned by an open issue (owned_by=[]).

SHARED FAULT: a GuardDuty read-back answers 200 with a body the emulator cannot actually back - it either reports a resource member it never produced (the investigation's analysis result, replaced by a FAILED status and an emulator-self-describing error) or advertises a URL on a host the emulator does not serve (the IPSet's `location`). In both cases the status line is correct and the divergence is entirely in the served content, so a client that believes the 200 and follows the body is sent somewhere the emulator cannot answer.

Cause 1 of 2: GetInvestigation never reports a completed investigation - it answers status FAILED with a fixed emulator-specific error and omits the whole analysis result. Fixture guardduty-tagging-created-with-tags, step setup#4.
AWS: Smithy GetInvestigation - GET /detector/{DetectorId}/investigation/{InvestigationId}, success code 200; input DetectorId and InvestigationId both required @httpLabel (InvestigationId @length 1..64, @pattern ^[a-fA-F0-9\-]+$); output Investigation (jsonName `investigation`, required); errors AccessDeniedException 403, BadRequestException 400, ResourceNotFoundException 404, InternalServerErrorException 500. Smithy Investigation: `status` -> InvestigationStatus, required, enum RUNNING|COMPLETED|FAILED ("The current status of the investigation"); `metadata` -> InvestigationMetadata ("Metadata about the product and version that produced the investigation"); `cloud` -> CloudDetails ("Details about the cloud environment in which the investigation was performed, including the provider, region, and account"); `riskLevel` -> RiskLevel enum Info|Low|Medium|High|Critical; `risk` -> RiskDetails @length 0..1024; `confidence` -> Confidence enum Unknown|Low|Medium|High; `summary` -> String ("A structured summary of the investigation findings..."); `error` -> InvestigationErrorDetails @length 0..2048, documented as "Details about the error if the investigation status is FAILED" - i.e. `error` is present ONLY on a genuinely failed investigation. Recorded behavior for the values: an investigation created in the fixture polls to `status` 'COMPLETED' (the replay's poll treats 'FAILED' as a fail_on terminal value) and the body then carries `metadata` = {product: {name: 'Amazon GuardDuty AI Analyst', feature: 'Investigation'}, version: '1.0.0'} (fixed product/feature/version text, no per-run part), `cloud` = {provider: 'AWS', region: <the detector's region>, account: <the caller's account>} (provider is fixed text; region and account are values taken from the request context, never literals), and `summary`, `risk`, `riskLevel` and `confidence` all PRESENT (their contents are shaped-not-asserted), with NO `error` member.
Emulator: HTTP 200, but `$.investigation.status` is 'FAILED' (the replay's poll gives up: "'FAILED' is in fail_on after 2 attempt(s)"), `$.investigation.error` is the fixed string 'The investigation analysis engine is not available in this emulator, so no investigation summary was produced.', and `$.investigation.cloud`, `$.investigation.metadata`, `$.investigation.summary`, `$.investigation.risk`, `$.investigation.riskLevel` and `$.investigation.confidence` are all absent. That error text is wholly an emulator self-reference: no part of it is AWS wording, and AWS populates `error` only when an investigation actually failed, so neither its fixed text nor any variable part of it is a requirement - the requirement is that a completed investigation carries no `error` at all.
Why: every client of the Investigation (AI Analyst) API is handed a permanently failed investigation. A caller cannot distinguish 'this emulator has no analysis engine' from a real analysis failure, so retry and alerting logic keyed on FAILED fires forever; and because `summary`, `risk`, `riskLevel`, `confidence`, `metadata` and `cloud` are never emitted, any consumer that reads the finding narrative, routes on riskLevel, or joins on the investigation's cloud account/region gets nothing to read. The fixture's own later steps (tagging a completed investigation) cannot proceed from a FAILED one.
Fix: the GetInvestigation handler's Investigation projection together with the investigation state machine in the guardduty crate's investigation state - a created investigation must progress RUNNING -> COMPLETED, and the completed view must populate `metadata` (fixed product name/feature and version), `cloud` (provider 'AWS' plus the request's region and account), `riskLevel`, `risk`, `confidence` and `summary`, and must NOT emit `error`.
Related open issues that do not cover this cluster (the replay reports owned_by=[]): 20261029T202111Z-guardduty-getinvestigation-fabricates-investigation-cloud-from-endpoint-context.md asserts the opposite direction for `cloud` (that it is fabricated from endpoint context and should be omitted), whereas this recording REQUIRES `cloud` on a completed investigation and the emulator omits it entirely - the two must be reconciled in favour of the recording; 20261029T190006Z-guardduty-investigation-and-publishing-destination-calls-answer-the-wrong.md owns this run's GetInvestigation 404-wording and CreateInvestigation status clusters but not this completed-investigation projection; 20261107T113312Z-guardduty-startmalwarescan-never-conflicts-on-a-resource-scanned.md describes the same 'everything ends FAILED' pattern for malware scans, a sibling symptom in a different operation.
Traces: guardduty-tagging-created-with-tags#setup#4 (cluster affected_count 2; also covers guardduty-tagging-round-trip#setup#4).

Cause 2 of 2: GetIPSet advertises the IPSet's `location` on a host the emulator does not serve, so the advertised list is unfetchable from the emulator. Fixture guardduty-ipset-tags-unicode-value-round-trip, step task#3.
AWS: Smithy GetIPSet - GET /detector/{DetectorId}/ipset/{IpSetId}, success code 200; output `name`, `format`, `location` and `status` all required, plus optional `tags` and `expectedBucketOwner`; `location` targets Location, a string @length 1..300; errors BadRequestException 400, InternalServerErrorException 500. CreateIPSet takes the same `location` member (required) as input. Recorded behavior only for the VALUE: the recording does not pin the location's literal text (the replay renders the expectation as '<shaped-not-asserted>'), and its host assertion requires the URL the serving endpoint hands back to name a host that endpoint actually serves - against real AWS the recorded location is a bucket the recording account owns and can be fetched; against the emulator the advertised location must resolve to the emulator itself.
Emulator: HTTP 200, but `$.location` is verdict host_not_own - the emulator echoes 'https://s3.amazonaws.com/<bucket>/list.txt' back verbatim from the CreateIPSet input, naming the public AWS S3 endpoint rather than the address the emulator is reached on. The bucket name and its uuid suffix are per-run values and are not the requirement; the requirement is the host.
Why: a client (or the emulator's own list-ingestion path) that resolves the advertised location leaves the emulator for the public internet. In a sealed environment the fetch fails on name resolution or egress refusal; in a connected one it reads a foreign object that has nothing to do with the emulator's stored IPSet. Either way the IPSet the emulator claims to serve cannot be retrieved from it, and CloudFormation/automation that round-trips IPSet locations breaks.
Fix: the IPSet view the GetIPSet handler (and the matching ThreatIntelSet read-back) serializes, in the guardduty crate's IPSet state projection - the stored list object must be re-announced through the emulator's own endpoint instead of the create-time input URL being echoed verbatim.
Related open issue that does not cover this cluster (owned_by=[]): 20261031T120647Z-guardduty-refuses-every-uploaded-list-location-that-is.md is the validation-side inverse (it refuses every Location that is not an amazonaws.com S3 URL); this cause is about the Location the emulator SERVES on read-back, and a fix for one must not re-break the other.
Traces: guardduty-ipset-tags-unicode-value-round-trip#task#3 (cluster affected_count 1).
