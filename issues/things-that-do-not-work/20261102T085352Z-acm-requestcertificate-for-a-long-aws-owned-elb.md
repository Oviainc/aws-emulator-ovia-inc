# ACM RequestCertificate for a long AWS-owned ELB name: the 64-octet first-domain refusal is missing and the certificate never reaches FAILED/ADDITIONAL_VERIFICATION_REQUIRED (2 causes)

> _Note: this issue was identified against the code base at commit `fec48c0e4a4ef614c94c9aeb73915e609cba5726`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RequestCertificate

## Description
Two root causes on the ACM public-certificate request path, both exercised by the acm-osc-public-cert-for-alb-dns-name fixture (requesting a public certificate for an Elastic Load Balancing DNS name). Both must be closed before this issue is submitted.

=== Cause 1 of 2: RequestCertificate accepts a first DomainName longer than 64 octets instead of refusing it (fixture acm-osc-public-cert-for-alb-dns-name, step task#1) ===

AWS: Smithy (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) RequestCertificateRequest.DomainName -> DomainNameString, required, @length min 1 max 253, pattern ^(\*\.)?(((?!-)[A-Za-z0-9-]{0,62}[A-Za-z0-9])\.)+((?!-)[A-Za-z0-9-]{1,62}[A-Za-z0-9])$, documented verbatim: "In compliance with RFC 5280, the length of the domain name (technically, the Common Name) that you provide cannot exceed 64 octets (characters), including periods. To add a longer domain name, specify it in the Subject Alternative Name field, which supports names up to 253 octets in length." So the model states the rule directly: the FIRST domain name (the one that becomes the certificate's Common Name, i.e. the DomainName member) is capped at 64 octets even though the member's own @length allows 253, and a longer name belongs in SubjectAlternativeNames. RequestCertificate models InvalidDomainValidationOptionsException (errorKind client, httpError 400). Recorded response for a DomainName longer than 64 octets: HTTP 400, __type 'InvalidDomainValidationOptionsException', message 'The first domain name can be no longer than 64 characters.' — that message is entirely fixed text for this error class (it embeds no name, id, value or limit taken from the request), so it is reproducible exactly; only the enclosing __type/message envelope is wire structure.

Emulator: the emulator accepts the request. It answers HTTP 200 with a CertificateArn and no error body at all: $.__type missing (expected 'InvalidDomainValidationOptionsException', got None) and $.message missing (expected 'The first domain name can be no longer than 64 characters.', got None). Hypothesis: RequestCertificate input validation only enforces the modelled @length max 253 and the hostname pattern on DomainName, and never applies the 64-octet Common Name cap that distinguishes DomainName from a SubjectAlternativeNames entry.

Why: a client relying on AWS's behavior gets a certificate request that cannot exist on AWS. Tooling that requests a certificate for a long generated hostname (an ELB DNS name, an internal load-balancer name, any long service-generated FQDN) is told by the emulator that the request succeeded and is handed a CertificateArn, so it proceeds to the validation and attachment steps; against AWS the same call fails fast with a 400 that tells the caller to move the long name into SubjectAlternativeNames. Code that catches InvalidDomainValidationOptionsException to implement exactly that fallback is never exercised and silently looks dead, and the emulator's phantom certificate goes on to diverge for the rest of the workflow (see Cause 2, which is the continuation of this same fixture).

Fix: RequestCertificate's input validation in the ACM service crate (the operation's handler, before the certificate is created in state) must reject a DomainName whose length exceeds 64 octets with HTTP 400 InvalidDomainValidationOptionsException and the message above, while continuing to allow names up to 253 octets in SubjectAlternativeNames / DomainValidationOptions.

Traces: acm-osc-public-cert-for-alb-dns-name#task#1 (sole member of this cluster; divergence_key service=acm|RequestCertificate|status=400->200|keys=$.__type,$.message,status).

=== Cause 2 of 2: a certificate requested for a name ACM cannot validate stays PENDING_VALIDATION forever, with no FailureReason and a truncated ValidationDomain (fixture acm-osc-public-cert-for-alb-dns-name, step task#3) ===

AWS: Smithy CertificateDetail.Status -> CertificateStatus [PENDING_VALIDATION, ISSUED, INACTIVE, EXPIRED, VALIDATION_TIMED_OUT, REVOKED, FAILED]; CertificateDetail.FailureReason -> FailureReason enum [NO_AVAILABLE_CONTACTS, ADDITIONAL_VERIFICATION_REQUIRED, DOMAIN_NOT_ALLOWED, INVALID_PUBLIC_DOMAIN, DOMAIN_VALIDATION_DENIED, CAA_ERROR, PCA_*, SLR_NOT_FOUND, OTHER], documented as existing only when the certificate status is FAILED; DomainValidation.ValidationStatus -> DomainStatus [PENDING_VALIDATION, SUCCESS, FAILED]; DomainValidation.ValidationDomain -> DomainNameString (@length 1..253, same hostname pattern as DomainName). The recording shows the terminal outcome for a public certificate requested for a name ACM will not issue for (here an AWS-owned elb.amazonaws.com wildcard plus the account's load-balancer hostname): the request leaves PENDING_VALIDATION and DescribeCertificate reports Certificate.Status 'FAILED' with Certificate.FailureReason 'ADDITIONAL_VERIFICATION_REQUIRED', the entry for the non-validatable name carrying ValidationStatus 'FAILED' while the other entry stays 'PENDING_VALIDATION'. Recorded behavior only for ValidationDomain on a DNS-validated certificate: each DomainValidationOptions entry's ValidationDomain equals that entry's own DomainName, character for character, INCLUDING a leading '*.' wildcard label — it is not reduced to a registrable parent domain. All four of these are modelled enum tokens or an echo of the request's own domain name; the certificate ARN, account id, generated load-balancer hostname and CreatedAt in this fixture are per-run values and are not part of the requirement.

Emulator: the certificate never leaves the pending state. The fixture polls DescribeCertificate for the terminal status and the replay reports '$: poll capped at 60s' — i.e. the expected state is never reached within the poll window — with Certificate.Status 'PENDING_VALIDATION' (expected 'FAILED'), Certificate.FailureReason absent (expected 'ADDITIONAL_VERIFICATION_REQUIRED'), DomainValidationOptions[0].ValidationStatus 'PENDING_VALIDATION' (expected 'FAILED'), and DomainValidationOptions[0].ValidationDomain 'us-west-2.elb.amazonaws.com' where AWS echoes the entry's own DomainName '*.us-west-2.elb.amazonaws.com' — the emulator strips the wildcard label when it derives ValidationDomain. Hypothesis: the ACM state machine has no request-failure path at all: every requested AMAZON_ISSUED certificate is parked in PENDING_VALIDATION regardless of whether the requested names are validatable by this account, so no modelled FailureReason is ever produced.

Why: a client relying on AWS's behavior hangs. The standard pattern — and the certificate-issued waiter — polls DescribeCertificate until the status is terminal; against AWS this request reaches FAILED with ADDITIONAL_VERIFICATION_REQUIRED, which tells the caller the names need manual verification and that it must stop. Against the emulator the status is PENDING_VALIDATION forever, so the waiter spins to its own timeout and the caller cannot distinguish "still validating" from "will never issue"; code that branches on FailureReason to explain or classify the failure reads None for a field AWS guarantees once the status is FAILED. The truncated ValidationDomain additionally misidentifies which name the challenge belongs to, so a client that matches validation entries by ValidationDomain to decide where to publish a record (or which SAN failed) matches nothing for a wildcard name.

Fix: the ACM certificate state machine and the CertificateDetail projection in the ACM service crate — the stored certificate state that DescribeCertificate reads. A requested certificate whose names ACM cannot validate for the account must settle into Status 'FAILED' with a populated FailureReason ('ADDITIONAL_VERIFICATION_REQUIRED' for a name requiring manual verification) and ValidationStatus 'FAILED' on the offending DomainValidationOptions entry; ValidationDomain must be the entry's own DomainName verbatim, wildcard label included.

Traces: acm-osc-public-cert-for-alb-dns-name#task#3 (sole member of this cluster; divergence_key service=acm|DescribeCertificate|status=200->200|keys=$,$.Certificate.DomainValidationOptions[0].ValidationDomain,$.Certificate.DomainValidationOptions[0].ValidationStatus,$.Certificate.FailureReason,$.Certificate.Status).
