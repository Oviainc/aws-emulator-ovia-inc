# cloudwatch__ec2__elbv2: an ALB's own ENIs never appear in its VPC (and its AWS/ApplicationELB host-count alarm never leaves INSUFFICIENT_DATA), so the CLI diagnosis check reaches no verdict

> _Note: this issue was identified against the code base at commit `b53c97f357326d3fde109a0e36eac1a0cf3c82af`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeNetworkInterfaces

## Description
One net-new-to-this-replay root cause, grounded in the single failing cloudwatch__ec2__elbv2 check that the replay report does NOT mark ALREADY FILED or OWNED. Note for the fixer: the open issue 20261102T085002Z-cloudwatch-ec2-elbv2-2-net-new-root-causes.md describes the same family of behavior and even lists this check in its Issue-Trace-Ids, but its stored replay key for this check no longer matches what the replay produces (that key was recorded at a 60 s harness ceiling and the poll index it names; the check now ends 'Check timed out after 180.0s'), so the report left this check unowned. Treat this issue as the live work item for this check and reconcile with that issue rather than assuming it is covered.

Cause 1 of 1: a load balancer's own elastic network interfaces are never materialised in EC2, so no EC2 network-interface query can ever attribute addresses to the ALB, and the check hangs on that unsatisfiable poll until the harness cap.
AWS: creating an Application Load Balancer attaches one service-managed ENI per subnet the load balancer is given. Those ENIs are ordinary describable EC2 network interfaces: EC2 DescribeNetworkInterfaces with Filters=[{Name:'vpc-id',Values:[<the ALB's VPC>]}] lists them (Smithy: DescribeNetworkInterfacesRequest.Filters documents the 'vpc-id' filter — 'The ID of the VPC for the network interface' — and the 'requester-id' filter — 'The alias or Amazon Web Services account ID of the principal or service that created the network interface'; NetworkInterface.InterfaceType enumerates 'load_balancer' and 'network_load_balancer', i.e. the model itself models load-balancer-owned interfaces). Each carries a PrivateIpAddress drawn from the ALB's subnets, and a requester-id of 'amazon-elb', so a diagnosis filtered Name=requester-id,Values=amazon-elb returns exactly the same interfaces as the unfiltered vpc-id query when the only load balancer in that VPC is the ALB. None of those addresses is ever one of the registered-but-dead ip targets. For the derived observability leg: an ALB publishes per-minute AWS/ApplicationELB UnHealthyHostCount under the dimension pair TargetGroup=targetgroup/<name>/<id> + LoadBalancer=app/<name>/<id>, so a PutMetricAlarm over that series with Statistic=Maximum, Period=60, EvaluationPeriods=2, Threshold=0, ComparisonOperator=GreaterThanThreshold, TreatMissingData=breaching reaches DescribeAlarms StateValue 'ALARM' and leaves INSUFFICIENT_DATA. Recorded behavior only for the ENI materialisation and the metric publication themselves (these are service side effects, not modeled response shapes); the filter names and the interface types above are from the EC2 Smithy model.
Emulator: the check's earlier control-plane assertions are made through the aws CLI and are reached (DescribeLoadBalancers filtered client-side on DNSName, LoadBalancers[0].VpcId, DescribeTargetGroups --load-balancer-arn, DescribeTargetHealth per group), so the emulator was serving and the CLI was present. The check then never gets past its waits: the poll for at least two network interfaces in the ALB's VPC (its own budget 600 s, 10 s interval) and the subsequent poll for the unhealthy-hosts alarm to leave INSUFFICIENT_DATA (budget 600 s, 15 s interval) are predicates the emulator can never satisfy, because the ALB owns no ENI in EC2 state and publishes no AWS/ApplicationELB host-count datapoints. The check therefore produces no assertion failure at all — it ends 'Check timed out after 180.0s' with no traceback. Hypothesis: ELBv2 load-balancer provisioning never writes into EC2 network-interface state and there is no ALB metric publisher, so both predicates are unreachable rather than merely slow.
Why: a client cannot perform any address-level diagnosis of a load balancer — which interface is the ALB, which addresses in the VPC are stale targets, whether an address belongs to amazon-elb — because the load balancer is invisible in EC2. Every unhealthy-host alarm built the way AWS documents stays in INSUFFICIENT_DATA forever, so alarm-driven remediation never triggers. And because the emulator answers these reads successfully-but-empty rather than refusing, a caller cannot distinguish 'not provisioned yet' from 'never will be' and waits out its own deadline.
Fix: ELBv2 load-balancer provisioning must materialise one service-managed ENI per configured subnet into EC2 network-interface state (InterfaceType 'load_balancer' for an ALB / 'network_load_balancer' for an NLB, requester-id 'amazon-elb', a PrivateIpAddress from the respective subnet, requester-managed true) and release them on DeleteLoadBalancer; the EC2 DescribeNetworkInterfaces handler's filter evaluation must match those interfaces on both 'vpc-id' and 'requester-id'. The ELBv2 target-group health evaluation must publish the AWS/ApplicationELB HealthyHostCount/UnHealthyHostCount series into CloudWatch metric state, and CloudWatch alarm evaluation must grade an alarm from those stored datapoints rather than leaving it at its initial state.
