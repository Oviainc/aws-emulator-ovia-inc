# cloudfront__dynamodb__lambda: a deployed distribution's edge data plane never answers a viewer request, so spoofed CloudFront-generated viewer headers are never stripped or rejected at the edge

Cause 1 of 1: a viewer request to a deployed distribution's domain never completes, so the edge's handling of client-supplied CloudFront-* headers cannot be observed.
AWS: recorded behavior only (the viewer-to-edge exchange is not expressed in the CloudFront Smithy model, which covers only the control plane). Once a distribution created by CreateDistribution is Deployed, a GET to its DomainName is answered by the edge; headers CloudFront generates itself — CloudFront-Viewer-Country, CloudFront-Forwarded-Proto and the rest of the CloudFront-* family — are regenerated by the edge from the connection, so a viewer that sets them itself cannot influence what the origin sees: the origin receives the edge's own values, never the client's spoofed ones.
Emulator: the request to the distribution's domain never returns; the check is killed by the harness — "Check timed out after 60.0s" — so no response, no origin invocation and no forwarded-header set is produced. The check is written to report the distinguishable case (its DATAPLANE_UNIMPLEMENTED marker) when the endpoint serves no edge at all, and it did not even get that far.
Why: a client cannot use the emulator to exercise anything behind a distribution — cache behaviour, origin request policies, or the security property that edge-generated headers are not viewer-controllable. A hanging request is worse than a refusal: SDK and browser clients block instead of failing fast.
Fix: the CloudFront edge data plane — a Deployed distribution's DomainName must accept viewer requests, strip/overwrite the CloudFront-* request headers with edge-computed values before forwarding to the configured origin, and return the origin's response; if the data plane is not implemented it must answer with a definite status rather than never responding.
