# SageMaker rejection fidelity: cluster-node/algorithm/model-package-group not-found & conflict message templates diverge, hyperparameter-tuning range and quota rejections are rendered with the wrong rule, and CreateTrainingJob answers NotImplemented instead of rejecting a conflicting AlgorithmSpecification (6 causes)

> _Note: this issue was identified against the code base at commit `ee21bdc0559bb252101e2375a2c132d26bd8f920`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateHyperParameterTuningJob (bundle also covers AttachClusterNodeVolume, DescribeClusterNode, DescribeAlgorithm, DeleteModelPackageGroup, CreateTrainingJob)

## Description
Six independent divergences on SageMaker's rejection path, all reached by replayed behavioral checks against the running emulator. Each is its own root cause and its own work item; this issue bundles SIX causes and all six must be closed before submitting.

Cause 1 of 6: the unknown-cluster-node refusal uses the emulator's own sentence instead of the one SageMaker's HyperPod node lookup produces.
AWS: Smithy: AttachClusterNodeVolume (input ClusterArn/NodeId/VolumeId, all required) and DescribeClusterNode both model exactly one error, ResourceNotFound (HTTP 400). Recorded AWS: a NodeId that does not exist on an existing cluster is rejected 400 ResourceNotFound with the fixed message "Specified cluster node not found", while a nonexistent ClusterArn is rejected 400 ResourceNotFound with a DIFFERENT message, "ClusterNotExistsException: Specified cluster not found" — the two unknown-identifier cases are distinguishable by message. The code/status are the requirement; the two message forms are the recorded ones.
Emulator: same 400/ResourceNotFound, but the message is built from the synthesized cluster ARN and the node id, e.g. 'Cluster arn:aws:sagemaker:<region>:<account>:cluster/<id> has no node i-00000000.'
Why: a client (or operator) that tells "this cluster does not exist" from "this node is not in the cluster" by the refusal text sees neither recorded form, and the emulator's text leaks an ARN the caller never supplied.
Fix: the not-found error construction in the cluster-node lookup shared by AttachClusterNodeVolume and DescribeClusterNode (the cluster handlers / shared cluster-state lookup helper), not the volume path.
Traces: sagemaker.attach-cluster-node-volume-unknown-node-not-found.

Cause 2 of 6: the invalid ContinuousParameterRange rejection is rendered with the emulator's own template rather than AWS's hyperparameter-ranges template.
AWS: Smithy: CreateHyperParameterTuningJob.HyperParameterTuningJobConfig.ParameterRanges.ContinuousParameterRanges carries MinValue/MaxValue as strings with no modeled cross-member constraint (the operation models only ResourceInUse and ResourceLimitExceeded), so the refusal is recorded behavior: 400 ValidationException whose message is built from the request, naming the offending range(s) as a bracketed list of hyperparameter names and then stating the constraint — "The hyperparameter ranges [<name>,...] are not valid. For continuous parameter ranges, the value of MinValue must be smaller than the value of MaxValue. Specify a value for MinValue that is smaller than the value of MaxValue." (recorded example for Name='eta', MinValue='1.0', MaxValue='0.5').
Emulator: same 400/ValidationException, but the message is per-range prose quoting the parsed numbers, e.g. 'The continuous parameter range for hyperparameter "eta" has MinValue 1, which is greater than its MaxValue 0.5.'
Why: the message rule here is known (it is built from the request: a bracketed list of the invalid range names plus the fixed constraint sentence), so a client that extracts the invalid range names from the bracketed list gets nothing, and the emulator additionally re-renders '1.0' as '1', losing the value the caller sent.
Fix: the ParameterRanges validation of CreateHyperParameterTuningJob (its validation layer / handler), services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_hyper_parameter_tuning_job.rs.
Traces: sagemaker.create-hyper-parameter-tuning-job-out-of-range-rejected.

Cause 3 of 6: the tuning-job ResourceLimits rejection evaluates a per-job cap instead of the account-level parallel-training-jobs quota, and reports no quota/utilization/delta.
AWS: Smithy: CreateHyperParameterTuningJob models ResourceLimitExceeded (HTTP 400). Recorded AWS, for ResourceLimits={MaxParallelTrainingJobs: 999999999, MaxNumberOfTrainingJobs: 999999999}: 400 ResourceLimitExceeded whose message is built from the request and the account's quota, in the form "The account-level service limit '<quota name>' is <limit> TrainingJobs, with current utilization of <used> TrainingJobs and a request delta of <requested> TrainingJobs. Please use AWS Service Quotas to request an increase for this quota. If AWS Service Quotas is not available, contact AWS support to request an increase for this quota." — the quota evaluated first is 'Maximum number of training jobs each hyper parameter tuning job can run in parallel at once' (the recorded limit value 10 and utilization 0 are account-specific examples, the rule is: the parallel-training-jobs quota, with limit, current utilization and request delta all reported).
Emulator: same 400/ResourceLimitExceeded, but it checks MaxNumberOfTrainingJobs against a fixed per-job cap and says "The service limit 'Maximum number of training jobs per hyperparameter tuning job' is 750, and MaxNumberOfTrainingJobs requested 999999999." — a different quota, and the message carries no utilization or delta and no Service Quotas guidance.
Why: the message rule is known (quota name + limit + utilization + delta) and the quota actually evaluated differs, so a client that parses the limit/utilization to decide whether to lower MaxParallelTrainingJobs or request an increase reads a limit about a different dimension; a request that is legal for MaxNumberOfTrainingJobs but illegal for MaxParallelTrainingJobs is classified against the wrong quota.
Fix: the ResourceLimits quota check in CreateHyperParameterTuningJob's handler/validation (evaluate the account-level parallel-training-jobs quota and build the account-level-limit message), services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_hyper_parameter_tuning_job.rs.
Traces: sagemaker.create-hyperparameter-tuning-job-resource-limit-exceeded-rejected.

Cause 4 of 6: the deleted/unknown-algorithm refusal uses the 'Could not find ...' template instead of AWS's '<Entity> <arn> does not exist.' form.
AWS: Smithy: DescribeAlgorithm declares no operation errors and takes AlgorithmName as an ArnOrName. Recorded AWS: looking up an algorithm that does not exist (here, right after DeleteAlgorithm) is rejected 400 ValidationException — not ResourceNotFound — with the message built from the resolved algorithm ARN in the fixed form "Algorithm <algorithm-arn> does not exist."
Emulator: same 400/ValidationException, but the message is 'Could not find algorithm "<algorithm-arn>".'
Why: the message rule is known (resolved ARN followed by "does not exist."), and it is the same sentence-shape divergence already filed for the lineage entities and the pipeline (Cause 2/Cause 4 of 20261022T210606Z-sagemaker-rejection-fidelity-duplicate-model-packages-get-conflictexception.md, now closed) — that issue's replay keys do not include this check, so the algorithm path was never verified. Consumers that match on the recorded sentence see an unrecognised refusal.
Fix: the not-found error construction in the algorithm handlers / the shared algorithm-state lookup helper (DescribeAlgorithm and the other Algorithm readers).
Traces: sagemaker.delete-algorithm-conflict-while-referenced.

Cause 5 of 6: the non-empty model-package-group delete conflict message diverges from the recorded template.
AWS: Smithy: DeleteModelPackageGroup models ConflictException (HTTP 400), but recorded AWS rejects the delete of a group that still contains a model package version with 400 ValidationException whose message is built from the resolved group ARN: "Model Package Group <group-arn> cannot be deleted because it still contains Model Packages." The group survives the refused delete and the same call succeeds once the packages are deleted.
Emulator: same 400/ValidationException (the code is right), but the message quotes the ARN and adds a count and remediation sentence: 'Model Package Group "<group-arn>" cannot be deleted because it contains 1 model package version(s). Delete the model packages in the group first.'
Why: the message rule is known (ARN unquoted, the fixed "still contains Model Packages." clause); clients and suites that compare the recorded refusal see a different string, and the added count is a value real AWS never reports here.
Fix: the referenced-children conflict error construction in DeleteModelPackageGroup's handler, services/service-com-amazonaws-sagemaker-sagemaker/src/ops/delete_model_package_group.rs.
Traces: sagemaker.delete-model-package-group-with-packages-rejected.

Cause 6 of 6: a CreateTrainingJob AlgorithmSpecification that sets both AlgorithmName and TrainingImage is answered NotImplemented instead of being rejected with ValidationException.
AWS: Smithy: CreateTrainingJob.AlgorithmSpecification models AlgorithmName and TrainingImage as independent optional members (the mutual exclusion is not expressible in the model) and the operation models ResourceInUse, ResourceLimitExceeded and ResourceNotFound. Recorded AWS: a spec carrying BOTH is rejected synchronously with 400 ValidationException, and because AWS resolves AlgorithmName before weighing the conflict the message names the algorithm it could not find — "Algorithm arn:aws:sagemaker:<region>:<account>:algorithm/<AlgorithmName> does not exist." No training job is created: DescribeTrainingJob on that name is then 400 ValidationException "Requested resource not found."
Emulator: the call is answered with error code NotImplemented (the operation is still an unimplemented scaffold stub), so no mutual-exclusion validation exists and the refusal class is wrong.
Why: a client validating its training-job request against the server cannot distinguish "your spec is invalid" from "this emulator cannot do it", and every negative-path test of AlgorithmSpecification passes/fails for the wrong reason. The stub itself is already filed as open issue 20261022T120642Z-sagemaker-createtrainingjob-stub.md, but that issue's replay keys do not include this check, so implementing the operation without this validation would leave the conflicting-spec rejection unverified — this cause is the validation requirement, not a second request to implement the stub.
Fix: the AlgorithmSpecification validation in CreateTrainingJob's handler (reject AlgorithmName+TrainingImage together, resolving AlgorithmName first), services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_training_job.rs.
Traces: sagemaker.training-job-conflicting-algorithm-spec-rejected.
