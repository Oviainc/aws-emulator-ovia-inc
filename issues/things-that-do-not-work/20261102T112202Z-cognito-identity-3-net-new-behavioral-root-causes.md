# cognito-identity: 3 net-new behavioral root causes — foreign-pool token refused with the logins-mismatch message, unsigned control-plane calls answer AccessDenied instead of MissingAuthenticationTokenException, and the default principal-tag map uses the key 'clientID' instead of 'client'

> _Note: this issue was identified against the code base at commit `7923db9e5c097e7a9eee0c015b735053c707d1d4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCredentialsForIdentity

## Description
This issue bundles THREE distinct net-new root causes reached through cognito-identity behavioral checks. All three must be fixed and re-replayed before closing.

=== Cause 1 of 3: GetCredentialsForIdentity refuses a Cognito OpenID token minted by ANOTHER identity pool with the logins-mismatch message instead of the invalid-token message ===
AWS: GetCredentialsForIdentity is modeled with Logins (LoginsMap, @length 0..10) and NotAuthorizedException (HTTP 403 in the model; Smithy: NotAuthorizedException — "Thrown when a user is not authorized to access the requested resource"). A Logins entry under the reserved key `cognito-identity.amazonaws.com` carrying an OpenID token that this pool did not mint is refused as an INVALID TOKEN, not as a logins/identity mismatch: error code NotAuthorizedException with the fixed message text "Invalid login token. Not a Cognito token." (the message has no variable parts — it is fixed text for this refusal class). The call vends nothing and leaves the target identity's Logins unchanged.
Emulator: the refusal code is right (NotAuthorizedException) but the message is "Logins don't match. Please include at least one valid login for this identity or identity pool." — the message AWS reserves for the DIFFERENT class where supplied logins do not match the named identity (see the fixed issue 20261029T230931Z-cognito-identity-refusals-for-invalid-or-mismatched-logins.md, causes 2 and 9, which is where that text belongs). The emulator therefore classifies a cross-pool Cognito token as a logins mismatch rather than as a token that is not this pool's Cognito token at all.
Why: a client (or an operator reading logs) cannot distinguish "you presented a token from the wrong pool" from "you presented no login valid for this identity" — the two have different remediations (re-authenticate against the right pool vs. supply the identity's own login), and SDK/retry logic keyed on the message text takes the wrong branch.
Fix: the login-token validation and its error-message selection in the GetCredentialsForIdentity handler — the pool-binding (audience) check on a `cognito-identity.amazonaws.com` token must select the invalid-Cognito-token refusal, before/instead of the generic logins-vs-identity mismatch refusal.
Traces: cognito-identity.a-token-minted-by-another-pool-is-refused-and-vends-nothing.

=== Cause 2 of 3: UNSIGNED requests to non-anonymous cognito-identity operations answer AccessDenied "Sign the request with the emulator credentials" instead of MissingAuthenticationTokenException "Missing Authentication Token" ===
AWS: only part of this API is anonymous-capable — the model binds GetCredentialsForIdentity (and GetId/GetOpenIdToken) with an empty auth list and @optionalAuth, while CreateIdentityPool, DescribeIdentityPool, DeleteIdentityPool and DeleteIdentities carry NO such override, so they require SigV4. Recorded behavior only (the model declares no such error on these operations): an UNSIGNED request to one of those operations is refused with HTTP 400, error code `MissingAuthenticationTokenException`, message fixed text "Missing Authentication Token" — fixed text with no variable parts — and nothing is created or deleted.
Emulator: every such unsigned call is refused with error code `AccessDenied` and the message "Sign the request with the emulator credentials" — an emulator-authored code and an emulator-authored, self-referential message that no AWS SDK models for this API. Observed on unsigned CreateIdentityPool, unsigned DescribeIdentityPool, unsigned DeleteIdentities and unsigned DeleteIdentityPool; the signed controls and the unsigned anonymous legs (GetId, GetCredentialsForIdentity, GetOpenIdToken) in the same checks succeed, so routing of anonymous requests now works (the previously filed UnknownService behavior is gone — cf. the open 20261023T185902Z-cognito-identity-unsigned-anonymous-requests-answer-unknownservice-and.md cause 1 and the fixed 20261024T065715Z-cloudtrail-cognito-identity-sts-unsigned-cognito-identity-requests-are-answered-unknownservice-so.md; neither covers the error code/message this refusal now carries, and neither carries these checks' replay keys). The refusal direction is correct — the calls ARE refused and leave no effect behind — only the classification diverges.
Why: a client that distinguishes "request was not signed" (retry after acquiring credentials) from "principal is denied this action" (a policy problem) is told the wrong thing; code keyed on MissingAuthenticationTokenException never fires, and the message leaks emulator vocabulary into an AWS error envelope.
Fix: the request authentication/SigV4 middleware that gates non-anonymous operations (the layer that currently emits AccessDenied "Sign the request with the emulator credentials") — when a request carries no SigV4 Authorization header at all and the target operation is not @optionalAuth, answer HTTP 400 with __type/x-amzn-errortype MissingAuthenticationTokenException and the message "Missing Authentication Token".
Traces: cognito-identity.deep-cognito-identity-1-unsigned-public-api-control-plane-rejected-while-credentials-vend, cognito-identity.deep-cognito-identity-1-unsigned-public-api-delete-identities-rejected.

=== Cause 3 of 3: the default principal-tag attribute map is served with the tag key 'clientID' instead of 'client' ===
AWS: SetPrincipalTagAttributeMap with UseDefaults=true configures the default attribute mappings (Smithy doc for SetPrincipalTagAttributeMapInput.UseDefaults: "You can use this operation to use default (username and clientID) attribute mappings"), and the Set echo and the GetPrincipalTagAttributeMap read-back then report UseDefaults=true together with the default map itself — PrincipalTags with exactly two entries, `username` -> `sub` and `client` -> `aud`. The principal tag KEY is `client` (the prose names the concept "clientID", the wire key is `client`); the same `client` -> `aud` entry is what the recorded wire corpus asserts for both Set and Get (see the open 20261029T230931Z-cognito-identity-identity-pool-and-principal-tag-responses.md, causes 7 and 8, which carries wire replay keys `cognito-identity|SetPrincipalTagAttributeMap|2xx->2xx|$.PrincipalTags.client` and the Get equivalent and does NOT carry this behavioral check's key).
Emulator: after SetPrincipalTagAttributeMap(UseDefaults=true, PrincipalTags={}), GetPrincipalTagAttributeMap answers HTTP 200 with UseDefaults=true and PrincipalTags={"username": "sub", "clientID": "aud"} — the second key is spelled `clientID` (the documentation prose) rather than the wire key `client`. The custom-map legs of the same check (set a custom map, read it back, the custom entries cleared on switching to defaults) all pass, so the divergence is confined to the default map's key name.
Why: these keys become the IAM session-tag names of the federated principal, so every policy written against AWS (`aws:PrincipalTag/client`, or a bucket/table condition keyed on it) silently never matches here, while a policy written against the emulator's `clientID` never matches in AWS — multi-tenant authorization built on the default mapping is wrong in both directions, and a client reading the map back cannot round-trip it.
Fix: the default principal-tag map in cognito-identity state — `crate::state::default_principal_tags()` (consumed by services/service-com-amazonaws-cognitoidentity-awscognitoidentityservice/src/ops/set_principal_tag_attribute_map.rs:245-249 and served by .../src/ops/get_principal_tag_attribute_map.rs:241-246) must name the tag key `client` mapped to the `aud` claim, alongside `username` -> `sub`.
Traces: cognito-identity.principal-tag-attribute-map-lifecycle.
