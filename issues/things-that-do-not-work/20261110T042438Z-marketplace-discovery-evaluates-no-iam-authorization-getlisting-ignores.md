# marketplace-discovery evaluates no IAM authorization: GetListing ignores an explicit Deny layered over an Allow, and GetOffer serves a principal with no policy at all

> _Note: this issue was identified against the code base at commit `795c74e692207bc8fa0a6278ad393ecb317bba54`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetListing

## Description
This issue bundles 2 net-new root causes, both in marketplace-discovery, grounded in the two behavioral checks of the 9 marketplace-discovery failures that are NOT marked OWNED by an open issue. Both are in the overly-permissive direction: the emulator answers 200 to a signed call that AWS refuses on an identity-based policy decision.

Naming adjacent open issues so this is not read as a duplicate: 20261030T005652Z-marketplace-discovery-iam-authorization-never-evaluated-on-getlisting.md is open and its Cause 1 describes the same class of defect, but it carries DIFFERENT replay keys for these two checks (it recorded both as harness `Timeout` observations: `get-listing-denied-without-permission-rejected|_poll#22|Timeout` and `get-offer-access-denied-without-permission-rejected|_poll_for_denial#15|Timeout`). Both checks now fail as in-body `AssertionError`s at different sites, so neither replay key is carried by that issue and neither check is owned by it. The two causes below are stated against the current observations so they can be closed on their own; a fix to the shared authorization hook may well close that issue's Cause 1 too, but these keys must be re-replayed to confirm it. No assertion here is on a per-run value: the account id, user name, listing id and offer id that appear in the expected message are variable parts filled from the request and from the emulator's own state, not literals from one run.

=== Cause 1 of 2: GetListing ignores an explicit Deny on aws-marketplace:GetListing layered over an explicit Allow for the same principal ===
AWS: Smithy: GetListing (POST /2026-02-05/getListing) models AccessDeniedException with errorKind client and httpError 403, member `message` -> ExceptionMessage, doc "You don't have sufficient access to perform this action." GetListing is the aws-marketplace:GetListing action, so ordinary IAM evaluation applies and an explicit Deny in an identity-based policy overrides any Allow, unconditionally. Recorded behavior for the message: the standard IAM explicit-deny sentence. Its FIXED text is "User: ", " is not authorized to perform: ", " on resource: " and " with an explicit deny in an identity-based policy". Its VARIABLE parts are taken from the request and from state: the signing principal's user ARN (arn:aws:iam::<account>:user/<user-name>), the action name (aws-marketplace:GetListing), and the target resource ARN (arn:aws:aws-marketplace:::catalog/<catalog>/listing/<listingId>, catalog and listingId as resolved for the request).
Emulator: no authorization decision is taken. The check first confirms the explicit Allow grants the real signed call (that leg passes), then layers an inline Deny for the same action on the same user and polls the identical GetListing call for 90s. Every single attempt keeps answering HTTP 200 with the full GetListingOutput body — the poll's last observation is the harness's success sentinel, {'Code': 'UNEXPECTED_SUCCESS'} — so no 403 and no AccessDeniedException is ever produced. Because the Allow leg passes and the Deny leg does not change anything, the emulator is not "allowing by policy"; it is not consulting policy at all.
Why: a client, policy test or least-privilege CI gate that asserts a scoped-down principal CANNOT read a listing passes against the emulator and then fails against AWS. Worse, a tenant-isolation guard built on an explicit Deny appears to hold while the emulator serves the listing body to every caller, so the isolation bug ships. Symmetrically, a client's AccessDeniedException handling path for this operation is unreachable and therefore untestable.
Fix: the service crate's request-authorization layer — a pre-handler authorization hook that resolves the signing principal from the sigv4 credential, evaluates that principal's identity-based policies against the operation's aws-marketplace action and the resolved resource ARN, and raises the modelled AccessDeniedException (403) with the explicit-deny sentence when a Deny matches. The decision belongs in that shared hook rather than in each handler; GetListing's handler only needs to surface the resource ARN it resolves. Traces: the handler currently runs its body unconditionally in services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/get_listing.rs.
Traces: marketplace-discovery.get-listing-denied-without-permission-rejected.

=== Cause 2 of 2: GetOffer serves a brand-new IAM principal that has NO policy attached, instead of refusing it by implicit deny ===
AWS: Smithy: GetOffer (POST /2026-02-05/getOffer) models AccessDeniedException with errorKind client and httpError 403, member `message` -> ExceptionMessage. GetOffer is the aws-marketplace:GetOffer action; a freshly created IAM user with no attached policy is refused by IAM implicit deny, so the call returns 403 with error code AccessDeniedException. Recorded behavior: the refusal carries code AccessDeniedException and a message that is NOT the credential-propagation message "The security token included in the request is invalid." — the check explicitly polls past that one, so an invalid-token answer does not satisfy it either. Granting that same principal an explicit Allow for aws-marketplace:GetOffer must then make the identical call succeed.
Emulator: the unprivileged, policy-less principal's GetOffer calls keep succeeding. The poll observes no ClientError at all for the whole window, so the captured error code is None and the check fails with "expected AccessDeniedException for a principal with no attached policy, got None". The positive control with the ambient credentials also succeeds, which confirms the offerId is readable and that the divergence is the missing authorization decision, not a missing record.
Why: the emulator cannot distinguish an authorized caller from an unauthorized one on this operation, so any least-privilege or multi-tenant assertion built on GetOffer is vacuous — it passes locally and the real refusal only appears in production. A caller that must handle 403 on offer reads has no way to exercise that branch.
Fix: the same shared pre-handler authorization hook described in Cause 1, extended to GetOffer's aws-marketplace:GetOffer action and the offer resource it resolves, with the implicit-deny decision (no matching Allow) producing the modelled AccessDeniedException at 403. Traces: services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/get_offer.rs runs its handle body unconditionally.
Traces: marketplace-discovery.get-offer-access-denied-without-permission-rejected.
