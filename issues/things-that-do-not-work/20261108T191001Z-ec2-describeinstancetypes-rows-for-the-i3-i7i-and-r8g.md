# DescribeInstanceTypes rows for the i3, i7i and r8g families omit modeled members and derive EBS, storage and vCPU facts

> _Note: this issue was identified against the code base at commit `e96438ac8652a0a4da19e4ddf11cb276239c17b7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
This issue bundles 3 root causes, all in the ec2 DescribeInstanceTypes instance-type catalog. They are the net-new part of 69 replay clusters (all DescribeInstanceTypes, all status 200 -> 200, bodies differing per instance type) that no open issue carries the replay key for. Related open issues exist for OTHER instance-type pages and do NOT cover these steps: 20261108T044413Z-ec2-describeinstancetypes-per-type-attributes-still-diverge-on-the.md, 20261106T142039Z-ec2-describeinstancetypes-catalog-pages-still-diverge-per-instance-type.md and 20261103T123451Z-ec2-static-catalogs-serve-emulator-authored-instance-type.md. All three causes below must be closed, and the fix must be catalog-wide (the 69 clusters span the ec2-catalog-describe-instance-types-* fixtures; the three replay keys bound to this issue are examples of the same table).

Cause 1 of 3: modeled InstanceTypeInfo members are omitted from every row.
AWS: Smithy (ec2, DescribeInstanceTypes -> InstanceTypeInfo) models cpuBurstModel, phcSupport, rebootMigrationSupport, processorInfo.supportedFeatures and the NetworkInfo members connectionTrackingConfiguration, defaultNetworkCardIndex, enaSrdSupported, flexibleEnaQueuesSupport, maximumNetworkCards, networkCards, secondaryNetworkSupported, trafficMirroringSupport, bandwidthWeightings, ipv4AddressesPerSecondaryInterface, efaSupported/efaInfo. AWS populates them for every instance type it returns; the recording shows them present (e.g. cpuBurstModel 'none', networkInfo.defaultNetworkCardIndex '0', networkInfo.enaSrdSupported 'false', networkInfo.connectionTrackingConfiguration with defaultTcpEstablishedTimeout/defaultUdpStreamTimeout/defaultUdpTimeout, networkInfo.bandwidthWeightings with the default/ebs-1/vpc-1 items).
Emulator: those elements are absent from each instanceTypeSet.item (replay reports them as 'missing (expected ..., got None)').
Why: a client that selects instance types on network-card count, ENA-SRD/EFA support, connection-tracking defaults or burst model sees unset optionals and either rejects every candidate or silently treats the capability as unsupported.
Fix: the DescribeInstanceTypes response projection/serializer in the ec2 service crate must emit these members from the instance-type catalog rather than leaving them unset.

Cause 2 of 3: EBS attributes are computed from a per-size formula instead of the per-type catalog.
AWS: Smithy EbsInfo{ebsOptimizedSupport, maximumEbsAttachments, attachmentLimitType, ebsOptimizedInfo} and EbsOptimizedInfo{baselineBandwidthInMbps, baselineThroughputInMBps, baselineIops, maximumBandwidthInMbps, maximumThroughputInMBps, maximumIops} carry the published per-instance-type numbers, and attachmentLimitType is the per-type enum ('shared' or 'dedicated'). The recordings show per-type values that do not follow any uniform size scaling (an i3 row expects baseline/maximum 850 Mbps and 106.25 MB/s with ebsOptimizedSupport 'default', attachmentLimitType 'shared' and maximumEbsAttachments 40; an r8g row expects baseline 315 Mbps / 2500 IOPS and maximum 10000 Mbps / 40000 IOPS with attachmentLimitType 'dedicated').
Emulator: it answers derived numbers for the same rows (1150 Mbps and 143.75 MB/s, ebsOptimizedSupport 'supported', attachmentLimitType 'dedicated', maximumEbsAttachments 27 for the i3 row; 287 Mbps / 1500 IOPS, maximum 4750 Mbps / 18750 IOPS and attachmentLimitType 'shared' for the r8g row).
Why: capacity planning and volume-limit checks read these fields; a client sizing EBS throughput or counting attachable volumes gets numbers AWS never publishes for that type, and the shared/dedicated attachment-limit decision is inverted.
Fix: the instance-type catalog data (state/seed table) behind DescribeInstanceTypes must hold the recorded per-type EBS facts; the handler must read them instead of computing them from vCPU/size.

Cause 3 of 3: other per-type hardware facts are synthesized.
AWS: instanceStorageInfo.disks.item.count/sizeInGB and instanceStorageInfo.totalSizeInGB, hibernationSupported, networkInfo.networkPerformance, processorInfo.sustainedClockSpeedInGhz and vCpuInfo.validCores are per-instance-type facts in AWS's catalog (recorded behavior: an i7i.metal-24xl row expects 6 disks of 3750 GB totalling 22500 GB; an i3 row expects hibernationSupported 'true'; validCores enumerates the type's real core counts).
Emulator: it reports different values for the same rows (12 disks of 1900 GB totalling 22800 GB; hibernationSupported 'false') and a validCores list whose entries do not match the recorded one.
Why: a client that filters on instance-store capacity, hibernation support, clock speed or valid core counts picks the wrong instance type, and CPU-options validation built on validCores accepts or rejects the wrong core counts.
Fix: same catalog table as cause 2 — storage, hibernation, network-performance, clock-speed and validCores entries must come from the recorded AWS catalog rows, not from a generator.
