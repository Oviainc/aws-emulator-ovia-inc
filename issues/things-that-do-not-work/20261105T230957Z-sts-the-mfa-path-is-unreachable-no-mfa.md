Cause 1 of 2: STS never authenticates an MFA challenge — a correct TOTP code from a virtual MFA device is refused exactly like a wrong one, so no MFA-bearing session can ever be minted.
AWS: Smithy sts#GetSessionToken takes SerialNumber (serialNumberType, @length 9-256, pattern ^[\w+=/:,.@-]*$) and TokenCode (tokenCodeType, @length 6-6, pattern ^[\d]*$), and its documentation states "MFA-enabled IAM users must call GetSessionToken and submit an MFA code that is associated with their MFA device … An incorrect MFA code causes the API to return an access denied error". A CORRECT code — RFC 6238, SHA-1, 30 s step, 6 digits, computed from the Base32StringSeed that iam#CreateVirtualMFADevice returned for a device enrolled against the calling user — must therefore NOT be refused: GetSessionToken answers 200 with Credentials whose AccessKeyId is in the ASIA class, and the session it mints is one that was authenticated with MFA. sts#AssumeRole states the same contract for its own SerialNumber/TokenCode members: "if the role being assumed requires MFA and if the TokenCode value is missing or expired, the AssumeRole call returns an 'access denied' error" (AssumeRoleRequest$TokenCode) — a present, live code must be accepted. The refusal class for a bad challenge is AccessDenied / HTTP 403 with AWS's fixed sentences "MultiFactorAuthentication failed, unable to validate MFA code.  Please verify your MFA serial number is valid and associated with this user." (wrong/unassociated serial) and "MultiFactorAuthentication failed with invalid MFA one time pass code." (wrong code) — both wholly fixed text, neither echoing the serial or the code.
Emulator: there is no code verification anywhere. `crate::state::mfa_challenge_failure` (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs) returns `Some(..)` on EVERY path once both SerialNumber and TokenCode are present: there is no branch that answers `None` for a valid challenge. The serial is resolved by `crate::state::held_mfa_device`, which reads only IAM's FIDO security-key registry (`iam.fido_security_key(serial)`) and never the virtual MFA devices that iam#CreateVirtualMFADevice stores (`store.virtual_mfa_devices`, keyed by the device's `mfa` ARN), so a virtual device's serial number resolves to `None` and every such call is refused AccessDenied with the unassociated-serial sentence; when a serial does resolve, the function unconditionally returns `InvalidPassCode`. The handler's own comment records this ("A COMPLETE challenge is never authenticated today"). Both call sites behave this way: GetSessionToken (src/ops/get_session_token.rs, the `mfa_challenge_failure` gate before any mint) and AssumeRole (src/ops/assume_role.rs). The error code and the two messages are AWS's own — the defect is that a legitimate challenge receives them too.
Why: a client cannot complete the standard MFA flow at all. Every MFA-gated control — "this action requires MFA", break-glass roles, the whole aws:MultiFactorAuthPresent pattern — is untestable, and a caller that holds a correctly enrolled device and computes a live code is told its serial is not associated with the user, which is false. Worse, the refusal is indistinguishable from the genuine wrong-code refusal, so an operator debugging an MFA integration is pointed at the device instead of the service.
Fix: `state::held_mfa_device` must resolve a serial number against the IAM store's virtual MFA devices (and the user binding iam#EnableMFADevice establishes), not only its FIDO key registry; `state::mfa_challenge_failure` must verify the presented six digits as an RFC 6238 TOTP against that device's stored Base32 seed, accepting the previous and current 30 s windows and returning `None` on a match; and the session `state::mint_session` creates for a validated challenge must record that MFA authenticated it (the fact Cause 2 needs). Enrolment itself stays with the already-filed iam EnableMFADevice stub issues.

Cause 2 of 2: AssumeRole never publishes aws:MultiFactorAuthPresent, so a trust policy conditioned on MFA is unsatisfiable and refuses every caller, MFA-bearing or not.
AWS: a role trust policy whose statement carries "Condition": {"Bool": {"aws:MultiFactorAuthPresent": "true"}} is satisfied by an sts:AssumeRole request signed with credentials that were themselves obtained with MFA (e.g. a GetSessionToken session minted with a validated device code): the assume succeeds with 200 and the AssumedRoleUser ARN arn:aws:sts::<account>:assumed-role/<roleName>/<roleSessionName>. The same request signed with the same user's long-term access key does not satisfy the condition and is refused AccessDenied / HTTP 403 with "User: <caller ARN> is not authorized to perform: sts:AssumeRole on resource: <role ARN>" — fixed text around two variable parts taken from the caller's identity and the request's RoleArn. The Smithy model declares no condition keys (recorded/AWS-documented behavior only: IAM User Guide id_credentials_mfa_configure-api-require), and AWS's rule is that the key is ALWAYS present in the request context for an STS request, valued true or false, so a Bool clause over it is always decided.
Emulator: the key is never in the context and the session registry holds no MFA flag at all. `ASSUME_ROLE_PUBLISHED_CONDITION_KEYS` lists only sts:RoleSessionName, sts:ExternalId, sts:SourceIdentity, sts:TransitiveTagKeys, aws:PrincipalArn, aws:PrincipalAccount, aws:PrincipalType, aws:userid, aws:TagKeys (plus the aws:RequestTag/ and aws:PrincipalTag/ families), and `assume_role_condition_context` builds exactly those; aws:MultiFactorAuthPresent appears in neither. By the crate's own documented rule — "a key the request does not determine is left out, so a clause over it stays undecided and withholds the grant" — `role.trust_policy_admits(ASSUME_ROLE_ACTION, ..)` refuses EVERY principal for such a role. src/ops/assume_role.rs states this outright at the MFA gate: "A trust policy's MFA condition is not a string condition, so the shared evaluator leaves such a statement undecided and withholds the grant." So the no-MFA leg returns the right code for the wrong reason, and the MFA leg — the one AWS allows — can never succeed no matter how the credential was obtained.
Why: the role is permanently un-assumable, which is a fidelity failure in the restrictive direction and silently converts a working least-privilege design into a dead one: an account that gates its admin role on MFA gets AccessDenied for its correctly MFA-authenticated operators, with a message asserting they are not authorized to assume the role. It also makes the MFA condition untestable in either direction, since a client cannot distinguish "MFA missing" from "this condition can never be satisfied".
Fix: carry an "authenticated with MFA" fact on a minted session in src/state.rs (set by GetSessionToken when Cause 1's validation passes, and propagated across role chaining the way the session's other inherited facts are), then publish aws:MultiFactorAuthPresent in both `assume_role_condition_context` (valued "true"/"false" for every request, never omitted) and `ASSUME_ROLE_PUBLISHED_CONDITION_KEYS`, and let the shared Bool operator in ::service_common::iam_authorization decide the clause instead of leaving it undecided. The same published key is what the S3/data-plane Deny leg in 20261029T065036Z needs, but that issue's fix is in its own service's authorizer and does not add the key here.
