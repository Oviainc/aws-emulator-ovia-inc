# CodeArtifact repository endpoints and authorization: pypi data plane unrouted, external-connection ingestion absent, 401 body missing success=false, GetRepositoryEndpoint not authorized, and npm-published readme never returned

> _Note: this issue was identified against the code base at commit `ec258a82c643322f3f1b10a7ea424abc4c176038`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetRepositoryEndpoint

## Description
This issue bundles FIVE distinct net-new root causes on the CodeArtifact data plane and its authorization, all grounded in failing behavioral checks of this replay. A fixer must close all five before submitting; each cause below names its own failing check ids.

=== Cause 1 of 5: GetRepositoryEndpoint is served to a principal with no identity-based grant (authorization not enforced) ===
AWS: Smithy GetRepositoryEndpoint models AccessDeniedException (httpError 403). A principal that holds NO identity-based policy for the action — here a freshly created IAM role with no attached permissions, assumed via sts:AssumeRole, while the domain's resource policy allows only codeartifact:DescribeDomain to another principal — is refused: AccessDeniedException, HTTP 403, message "User: <caller arn> is not authorized to perform: codeartifact:GetRepositoryEndpoint on resource: <repository arn> because no identity-based policy allows the codeartifact:GetRepositoryEndpoint action". Fixed text: "User: ", " is not authorized to perform: ", " on resource: ", " because no identity-based policy allows the ", " action"; the caller ARN (arn:aws:sts::<account>:assumed-role/<role>/<session>), the action name and the repository ARN (arn:aws:codeartifact:<region>:<account>:repository/<domain>/<repository>) all come from the request and the caller's credentials. The domain owner's own credentials must still succeed (positive control).
Emulator: the unprivileged call SUCCEEDS — HTTP 200 with {'repositoryEndpoint': 'https://<domain>-<account>.d.codeartifact.<region>.amazonaws.com/generic/<repo>/'}.
Why: this is an authorization bypass. Any client, test or pipeline validating least-privilege IAM for CodeArtifact is green against an emulator that grants every principal the repository endpoint — and the endpoint is the handle to the whole data plane, so the bypass is not cosmetic.
Fix: identity-policy evaluation in the GetRepositoryEndpoint handler (services/service-com-amazonaws-codeartifact-codeartifactcontrolplaneservice/src/ops/get_repository_endpoint.rs) over the shared authorization component the service already uses for token minting (src/service/token_authorization.rs), producing the modeled AccessDeniedException sentence above. Related open issues that do NOT carry this check: 20261029T063047Z-codeartifact-getrepositoryendpoint-is-not-authorized-a-role-named.md (same operation, the repository-permissions-policy path) and 20261022T171312Z-codeartifact-no-iam-authorization-on-reads-publishpackageversion-digest.md (reads generally); this check fails on the identity-policy implicit-deny path and is unowned.
Traces: codeartifact.cross-domain-unauthorized-access-denied.

=== Cause 2 of 5: the pypi repository endpoint host is not routed at all, so no PyPI data plane exists even for locally published distributions ===
AWS: recorded behavior only (the Smithy model describes the control plane). The host GetRepositoryEndpoint(format='pypi') hands out speaks the PyPI upload + Simple Repository API, authenticated with HTTP Basic (user `aws`, password the GetAuthorizationToken token): a twine-style multipart/form-data POST of a wheel to the endpoint root answers HTTP 201; GET <endpoint>simple/<normalized-name>/ then answers HTTP 200 with a PEP 503 index titled "Links for <normalized-name>" holding exactly one href to the wheel filename with a #sha256=<digest> fragment; GETting that href returns the uploaded bytes byte-identically; and the control plane agrees — ListPackageVersionAssets reports that asset name with hashes['SHA-256'] equal to the uploaded digest. PEP 503 normalisation is part of it: the wheel filename keeps underscores while the index path uses the hyphen/lowercase form. The JSON variant (Accept: application/vnd.pypi.simple.v1+json) must likewise answer 200 with a non-empty `files` list for a project the repository holds.
Emulator: the pypi endpoint host is not registered with the emulator's router at all — the upload POST answers HTTP 404 with {"__type":"UnknownService","message":"no emulated service is registered for '<domain>-<account>'"} — so neither upload, index nor download exists. The npm endpoint host, by contrast, IS routed (it answers CodeArtifact's own package-not-found JSON), so this is a missing pypi data plane rather than a general endpoint-routing gap.
Why: pip/twine against the emulator cannot publish or resolve anything; every pypi client flow 404s with an envelope that is not even CodeArtifact's, and the origin/upstream checks that need a served pypi index cannot reach their graded legs.
Fix: a pypi data-plane module beside the existing src/service/npm_registry.rs (upload handler + PEP 503/PEP 691 index + file download, with the Basic-token authentication the npm endpoint already performs), backed by the same package/asset state the PublishPackageVersion / GetPackageVersionAsset / ListPackageVersionAssets handlers read, plus registration of the pypi repository-endpoint host in the emulator's endpoint router.
Traces: codeartifact.codeartifact-pypi-simple-index-serves-a-published-wheel, codeartifact.codeartifact-package-origin-configuration-blocks-upstream-ingestion.

=== Cause 3 of 5: an associated external connection ingests nothing, so no EXTERNAL-origin version is ever created ===
AWS: recorded behavior only. With AssociateExternalConnection('public:npmjs' / 'public:pypi') in place, a package-manager fetch through the repository endpoint for a package only the public registry holds resolves: the npm packument answers HTTP 200 with dist.tarball rewritten to this repository's own endpoint, and fetching that tarball CACHES the version — ListPackageVersions then reports it with origin.originType == 'EXTERNAL' and origin.domainEntryPoint.externalConnectionName == 'public:npmjs'; DescribePackage before any fetch still answers ResourceNotFoundException "Package not found in repository. Package = {format=npm, name=<package>}" (an external connection does not pre-populate). After DisassociateExternalConnection the cached version SURVIVES and stays downloadable, while a version never fetched while the connection was live can no longer be retrieved. A package carrying restrictions {publish: BLOCK, upstream: BLOCK} must ingest nothing while an unrestricted sibling in the same run does, and GetPackageVersionAsset for the blocked coordinate is refused ResourceNotFoundException/404 "Package version not found in repo. repoId = '<id>', packageCoordinate = 'PackageVersionCoordinateEntity{name=<package>, type=<FORMAT>, version=<version>, displayName=<package>==<version>}'." (repoId is service-internal state; the coordinate parts come from the request).
Emulator: nothing is ever ingested. The npm packument GET through a live connection answers HTTP 404 {"error":"Package not found in repository. Package = {format=npm, name=<package>}"}, the pypi legs have no index at all (Cause 2), and the bounded ingestion polls never see a version, so the originType partition, the post-disassociation cached-vs-never-fetched distinction and the blocked-coordinate refusal are all unreachable. The upstream=BLOCK assertions pass only VACUOUSLY — a store that ingests nothing "blocks" a package it was told to allow just as well.
Why: external connections are the main reason to run CodeArtifact. With no pull-through, every upstream behavior is a silent no-op that looks correct, so a client validating dependency-substitution protection or origin controls passes against an emulator that enforces nothing, and installing any public dependency simply 404s.
Fix: upstream/external-connection resolution in the repository data plane (src/service/npm_registry.rs and the pypi module of Cause 2): on a local miss, resolve through the associated external connection, persist the fetched version as an EXTERNAL-origin version with its domainEntryPoint, consult the package's origin configuration FIRST so an upstream=BLOCK package is never ingested, and retain cached versions across disassociation. NOTE the known platform blocker already recorded in the open issues 20261029T095746Z-codeartifact-npm-external-connection-ingests-nothing.md (npm) and 20261027T083906Z-codeartifact-reopens-codeartifact-pypi-repository-endpoint-still-ingests-nothing.md (pypi): reaching a third-party registry needs outbound egress this emulator does not have, and fabricated per-package content is not an acceptable fix — so this cause may have to end in an honest wont-fix naming that rule. Those two issues do not carry the three checks listed below, which fail on this cause in this replay.
Traces: codeartifact.external-connection-caches-fetched-package, codeartifact.codeartifact-external-connection-upstream-fetch-then-disassociate-blocks, codeartifact.package-origin-configuration-blocks-upstream-ingestion.

=== Cause 4 of 5: the repository endpoint's 401 body is not CodeArtifact's refusal envelope ===
AWS: recorded behavior only. A GET to the repository endpoint with NO Authorization header answers HTTP 401 with a JSON body carrying success == false and an `error` sentence naming the missing header (it states that the request did not include an Authorization header); a GET with a BAD bearer token answers HTTP 401 with a DIFFERENT `error` sentence, naming invalid credentials rather than reusing the missing-header wording; and the same URL with a real GetAuthorizationToken token gets past authentication to HTTP 404 whose `error` is a package-not-found sentence — which is what proves the 401s were about the credential and not the path.
Emulator: the status is 401, but the body has no `success` member at all (the check dies with KeyError: 'success' after json.loads), so the two 401 bodies cannot be told apart in the shape AWS serves them.
Why: package managers and CI wrappers branch on this body (success=false plus the error sentence) to decide whether to re-login; a body of another shape makes a token-expiry refusal indistinguishable from any other 401.
Fix: the unauthenticated/invalid-credential refusal bodies of the repository endpoint handler (src/service/npm_registry.rs, and the pypi module of Cause 2): emit {"success": false, "error": "<sentence>"} with two DISTINCT sentences — one naming the absent Authorization header, one naming invalid credentials.
Traces: codeartifact.repository-endpoint-unauthenticated-fetch-rejected.

=== Cause 5 of 5: GetPackageVersionReadme never returns the readme of a version published through the npm registry endpoint ===
AWS: Smithy GetPackageVersionReadme (GET /v1/package/version/readme) returns `readme` (String) beside format/namespace/package/version/versionRevision. For an npm version published through the repository's npm endpoint with the PUT registry protocol (PublishPackageVersion itself accepts only the generic format), the README embedded in the published manifest is extracted and returned, decoded byte-for-byte — multi-byte UTF-8 (CJK, Cyrillic, accents, emoji) round-trips unchanged.
Emulator: the readme is never populated. The npm PUT publish is accepted (it does not raise the check's publish failure, and a published npm version is otherwise visible to the control plane), but a bounded poll of GetPackageVersionReadme never yields a non-empty `readme`, so the check is killed at the harness ceiling (Check timed out after 60.0s). The timeout is the permanent absence of a readme, not a slow response.
Why: a client that reads package documentation through the API gets nothing for every npm version in the repository, and a UTF-8 round-trip regression would be invisible because there is no value to compare.
Fix: extract the manifest's readme (and the package/README.md in the published tarball) during npm registry ingestion in src/service/npm_registry.rs, persist it on the stored version in src/state.rs, and return it from the GetPackageVersionReadme handler (src/ops/get_package_version_readme.rs) as UTF-8 text.
Traces: codeartifact.package-version-readme-unicode-round-trip.
