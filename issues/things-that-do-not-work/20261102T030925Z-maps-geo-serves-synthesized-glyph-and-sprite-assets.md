# maps.geo serves synthesized glyph and sprite assets instead of the published basemap asset bytes

> _Note: this issue was identified against the code base at commit `7ae6661e06a7b508bcb27fb3544e971eb802ec55`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetGlyphs, GetSprites

## Description
FOUR net-new wire-divergence causes in the geo-maps (maps.geo) emulator, all of them 200-OK responses whose asset payload is synthesized by the emulator rather than being the published, environment-independent basemap asset AWS serves for the same path. The emulator answers every one of these calls, so these are fidelity defects, not a bootstrap gap. A fixer must close all FOUR before submitting.

Scope note on what is NOT this issue: the three GetStyleDescriptor clusters in the same replay are already owned by the open issue "maps.geo GetStyleDescriptor serves a synthesized style document instead of the published basemap style release" (20261030T062941Z-maps-geo-getstyledescriptor-serves-a-synthesized-style-document.md) and are deliberately excluded here. The open issue "geo-maps: four fidelity divergences in GetTile/GetStaticMap/GetGlyphs refusals and GetTile Content-Type" (20261030T093746Z) covers GetGlyphs/GetTile/GetStaticMap *refusal* wording and GetTile's Content-Type; it says nothing about the bytes a successful GetGlyphs or GetSprites returns, so none of the four causes below are covered by it.

=== Cause 1 of 4: GetGlyphs returns a synthesized glyph PBF instead of the published glyph range for the font stack ===
AWS: Smithy (services/service-com-amazonaws-geomaps-mapsservice/smithy-model/com-amazonaws-geomaps-mapsservice.json) binds GetGlyphs to GET /v2/glyphs/{FontStack}/{FontUnicodeRange} with FontUnicodeRange @pattern ^[0-9]+-[0-9]+\.pbf$, and GetGlyphsResponse$Blob is the @httpPayload; GetGlyphs models no errors. Recorded behavior: for a given (FontStack, FontUnicodeRange) pair the service returns 200 with ONE fixed, published glyph-range protobuf — the same bytes on every call, in every region and account, because it is a static published font asset keyed only by the two URI labels. The recorded payload for the replayed range is 74786 bytes (sha256 73b6ca0b7819f2dc763c75c5798d6fcb8527e74105de50744dbe32138c26ac18).
Emulator: returns 200 with a payload it generates itself: 139609 bytes, sha256 93b5b015200340cdd49f52bc5c9ef34bb8d0054e168311726b3385b3d20ee6b6 — nearly twice the recorded length and a different digest. The divergence reproduces on three different unicode ranges of the same font stack and again inside the vector-basemap workflow, i.e. it is the whole glyph source, not one range.
Why: a renderer feeds this blob straight into its glyph atlas. Synthetic SDF glyph data of a different size yields wrong advance/bearing metrics, missing codepoints and garbled or blank labels; any client that caches or ETags/validates glyph assets, or that checksums them before use, sees an asset that is not the one AWS publishes.
Fix: the GetGlyphs handler and the glyph-asset source in this service's state — the handler must serve the recorded published glyph-range bytes for the (FontStack, FontUnicodeRange) key rather than generating a PBF at request time.
Traces: geo-maps-glyphs-fontstack-unicode-ranges#task#1 (representative), plus geo-maps-glyphs-fontstack-unicode-ranges#task#2, geo-maps-glyphs-fontstack-unicode-ranges#task#3 and geo-maps-vector-basemap-style-workflow#task#4 in the same cluster. Component: services/service-com-amazonaws-geomaps-mapsservice/src/ops/get_glyphs.rs and the asset catalog it reads from services/service-com-amazonaws-geomaps-mapsservice/src/state.

=== Cause 2 of 4: GetSprites returns a synthesized sprite image instead of the published sprite sheet for the style/colour-scheme/variant ===
AWS: Smithy binds GetSprites to GET /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName} with FileName @pattern ^sprites(@2x)?\.(png|json)$ and GetSpritesResponse$Blob as the @httpPayload; GetSprites models no errors. Recorded behavior: the .png (and @2x.png) form returns 200 with the published sprite-sheet raster for that (Style, ColorScheme, Variant) — again a static asset fully determined by the URI labels, identical on every call. The recorded sheet for the replayed combination is 121655 bytes (sha256 f0d727b230e676e2a204c4f7ec0ab50ff2c73ead3945df40d2532ae0d4746b54).
Emulator: returns 200 with a self-generated image of 21822 bytes, sha256 1b9d66699cbd1b79d450b1ea6f09aaa15543f01eea7ea5ddbcd03e398cd7e180 — roughly one sixth of the published asset, so the sheet cannot be carrying the published icon artwork. Reproduces for two sprite variants of the same style and again inside the vector-basemap workflow.
Why: the sheet is sampled using the pixel rectangles from the companion sprites.json; a differently sized, differently drawn sheet means every icon a map draws (POI markers, shields, one-way arrows) is cropped from the wrong pixels — blank, clipped or wrong-icon rendering — and asset-integrity checks against the published sprite sheet fail.
Fix: the GetSprites handler and the sprite-asset source in this service's state — serve the recorded published raster bytes keyed by (Style, ColorScheme, Variant, FileName) instead of drawing a sheet at request time.
Traces: geo-maps-sprites-style-color-variants#task#1 (cluster representative; also geo-maps-sprites-style-color-variants#task#2 and geo-maps-vector-basemap-style-workflow#task#2). Component: services/service-com-amazonaws-geomaps-mapsservice/src/ops/get_sprites.rs plus services/service-com-amazonaws-geomaps-mapsservice/src/state.

=== Cause 3 of 4: GetSprites sprites.json index carries a synthesized atlas layout — wrong icon sizes, wrong positions, wrong icon name set ===
AWS: same GetSprites binding; with FileName=sprites.json the @httpPayload Blob is the sprite index document, a flat JSON object whose keys are the published icon names and whose values carry that icon's width, height, x, y (and pixelRatio) within the published sheet. Recorded behavior: the geometry is the published atlas's own packing — per-icon natural sizes and a packing in which these icons all sit on the first row (y=0): e.g. bicycle 22x20, bus 20x20 at x=138, citydot 5x5 at x=317, citydot-open 6x6 at x=305, citydot_lowrank 5x5 at x=322, book at x=117, education at x=475, entrance 20x20 at x=496, facilities at x=516, fast-food at x=537, ferry at x=558. Each icon's width/height/x/y is a published value of the asset, not a per-run value.

Why: the index is the only thing telling a renderer where an icon lives in the sheet. Fix: the GetSprites handler's sprites.json path and the sprite index in this service's state — serve the published index document verbatim (names and per-icon geometry) instead of synthesizing a uniform-grid atlas.
