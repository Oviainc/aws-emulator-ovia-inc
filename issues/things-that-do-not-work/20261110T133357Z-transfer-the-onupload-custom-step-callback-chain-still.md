# Transfer: the OnUpload CUSTOM-step callback chain still never completes — the step target's in-order SendWorkflowStepState never returns, and the whole check now exceeds the replay budget

> _Note: this issue was identified against the code base at commit `26d32bcad27715ea017c47668e9d99e84ae7a2e0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendWorkflowStepState

## Description
ONE net-new root cause in the transfer emulator, grounded in the single failing behavioral check of this replay that the report marked neither 'ALREADY FILED' nor 'OWNED by'.

=== Cause 1 of 1: the managed-workflow callback leg (OnUpload execution -> CUSTOM step invoked with a Token -> the target's own in-order SendWorkflowStepState(Status='SUCCESS')) never reaches a completed execution, and the chain is now slow enough that the whole check is killed at the replay harness' 60 s budget before any assertion is evaluated ===
Failing check: transfer.workflow-step-state-out-of-order-rejected.

AWS: Smithy com.amazonaws.transfer#SendWorkflowStepState input {WorkflowId @required len 19..19 pattern ^w-([a-z0-9]{17})$, ExecutionId @required len 36..36 UUID pattern, Token @required CallbackToken len 1..64 pattern ^\w+$, Status @required CustomStepStatus enum (SUCCESS|FAILURE)}; output shape is EMPTY; modeled errors AccessDeniedException (client, 403), InternalServiceError (server, 503), InvalidRequestException (client, 400), ResourceNotFoundException (client, 404), ServiceUnavailableException (server, 503), ThrottlingException (client, 429). The model documents the operation as sending 'a callback for asynchronous custom steps. The ExecutionId, WorkflowId, and Token are passed to the target resource during execution of a custom step of a workflow.' So the FIRST callback a step's target makes with the token it was handed succeeds: HTTP 200 with an empty body, recording that step's outcome and completing a single-step execution. Smithy DescribeExecution input {WorkflowId, ExecutionId} @required, output {WorkflowId @required, Execution @required}, errors incl. ResourceNotFoundException 404. Only a REPLAY of the same, already-consumed token is refused — HTTP 404, error code ResourceNotFoundException, message exactly 'Unknown execution' (entirely fixed text; the execution identifier travels in the error's Resource member with ResourceType='Execution', never interpolated into the message) — and DescribeExecution(WorkflowId, ExecutionId) must answer identically before and after that refused replay. Recorded behavior only, for the surrounding chain: a file landing on a server whose WorkflowDetails.OnUpload names a workflow starts one execution; the CUSTOM step invokes its Lambda Target with an event carrying 'token' and serviceMetadata.executionDetails.{workflowId, executionId}; the target's side effects become observable in order (here: write tokens/<token>.json, then call SendWorkflowStepState, then write tokens/<token>.done). Bucket/function/token/execution ids and object keys are request- and environment-derived and are NOT requirements; the requirement is the ORDER, the success of the in-order callback, and that the recorded run completes inside the replay budget AWS itself met.

Emulator: the check is killed outright — the replay reports 'Error: Check timed out after 60.0s' for transfer.workflow-step-state-out-of-order-rejected, with no exception and no assertion reached. Every wait in this check is a poll that probes FIRST and only sleeps when the predicate is false (DescribeServer State=='ONLINE' at 5 s intervals, TestConnection for SftpConnectionDetails.HostKey then Status=='OK' at 10 s intervals, ListFileTransferResults for a terminal StatusCode at 5 s intervals, then the tokens/<token>.json marker and the tokens/<token>.done positive control at 3 s intervals), so an emulator that answered each of these conditions as the recording does would finish well inside the budget: this service's own clock-due spans are short by construction (state.rs SERVER_START_SPAN = 3 s, CONNECTOR_TRANSFER_SPAN = 3 s). The harness kill therefore means at least one of those polled conditions never became true and the check burned the budget sleeping. The last recorded position of this same chain (see the related issue below) was the positive control: tokens/<token>.json appears — so the execution is started and the CUSTOM step IS invoked with a token — while tokens/<token>.done, written by the very next statement after the target's transfer.send_workflow_step_state(..., Status='SUCCESS'), never appears, i.e. the in-order callback for a token the execution is still holding as pending does not return 200. Hypothesis (neither the model nor this replay output says which link breaks; the replay now yields only the whole-check timeout): the live-token path of ops/send_workflow_step_state.rs refuses or does not answer the first callback (its gates answer 403 AccessDeniedException for an unknown workflow, 404 ResourceNotFoundException for an unresolved (WorkflowId, ExecutionId), 400 InvalidRequestException for a token not held as pending), or the nested in-process callback cannot complete while the delivery task holds this service's state lock — state/connector_delivery.rs discards the step invocation's outcome (warn only) and deliberately leaves the step pending, so nothing about the failure is observable through the API, and state/workflow_runs.rs derives ExecutionStatus purely from step_states, which stay None, leaving the run IN_PROGRESS forever.

Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback token) sees its step target invoked and then nothing: the step's success report is lost, the execution never leaves IN_PROGRESS, DescribeExecution/ListExecutions keep reporting a run that in fact finished, and the at-most-once property of a callback token — the property that makes a token safe to retry against, and the whole reason the replay of a consumed token answers 404 'Unknown execution' — cannot be observed at all. Retry/idempotency logic written against real Transfer Family is untestable here, and because the chain now also exhausts the replay budget, every downstream assertion of this flow is unreachable rather than merely wrong.

Fix: the SendWorkflowStepState handler and the workflow-execution state it resolves against must accept the FIRST callback for a token a started execution still holds as pending (HTTP 200, empty body, the reported Status recorded on that step, derived execution status moving to COMPLETED for SUCCESS / EXCEPTION for FAILURE), resolve the callback under exactly the values the step's event carried, never release an execution while a step of it is pending, and refuse only an already-reported token with the modeled 404 ResourceNotFoundException whose message is the fixed text 'Unknown execution', leaving DescribeExecution's answer unchanged. The callback leg must also stop swallowing the step invocation's outcome, and the whole delivery -> execution -> callback path must settle promptly rather than consuming the replay budget. Components: the SendWorkflowStepState operation handler, the workflow-execution state, and the connector-delivery writer that starts the run, mints the token and invokes the step (file citations under Traces).
