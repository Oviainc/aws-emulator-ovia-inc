# cognito-identity: 5 net-new root causes — CFN UserPoolClient Ref rolls identity-pool stacks back, a stack-level CREATE_FAILED event is invented, the provider-less GetId refusal is re-worded, principal tags never become STS session tags, and Rules role mapping never selects a rule's role

GetCredentialsForIdentity

## Description
FIVE net-new root causes, grounded in the nine failing checks under the suite heading `cognito-identity` that the replay report marks neither ALREADY FILED nor OWNED. All other cognito-identity failures in this run are OWNED by open issues and are not re-filed here. A fixer must close all five before submitting.

=== Cause 1 of 5: an AWS::Cognito::UserPoolClient's Ref is a hyphenated CFN physical name, so every stack feeding it into an identity pool rolls back ===
Failing check ids: cognito-identity.deploy-cognito-identity-3-cfn-principal-tag-governs-tenant-access, cognito-identity.deploy-cognito-identity-3-cfn-principal-tag-without-tag-session-rejected.
AWS: a Cognito app client id is service-minted and opaque — Smithy com.amazonaws.cognitoidentityprovider#ClientIdType: @length 1..128, @pattern ^[\w+]+$, @sensitive — and `Ref` on AWS::Cognito::UserPoolClient returns that ClientId. Smithy com.amazonaws.cognitoidentity#CognitoIdentityProvider.ClientId targets CognitoIdentityProviderClientId, @length 1..128, @pattern ^[\w_]+$, so a real client id satisfies it by construction and the stack reaches CREATE_COMPLETE.
Emulator: the physical id / Ref is the generic synthesized <stack-name>-<logical-id>-<hex suffix>, which contains hyphens. CreateIdentityPool then correctly refuses it, the IdentityPool (here logical ids `IdentityPool` and `MappedPool`) ends CREATE_FAILED with reason `Resource handler returned message: "1 validation error detected: Value '<stack>-UserPoolClient-<hex>' at 'cognitoIdentityProviders.1.member.clientId' failed to satisfy constraint: Member must satisfy regular expression pattern: [\w_]+" (RequestToken: <per-run id>, HandlerErrorCode: InvalidRequest)` and the stack settles ROLLBACK_COMPLETE. The fixed text of that message, its member path and its pattern are AWS's; the quoted value, stack name, hex suffix and RequestToken are per-run values. The refusal is right — its input is wrong.
Why: no template that creates an app client and hands its id to an identity pool, a principal-tag mapping or anything else can deploy; the user gets no estate at all and is pointed at the wrong resource for the diagnosis, and any client storing the Ref as a client id stores a value Cognito would never issue.
Fix: the CloudFormation resource provider for AWS::Cognito::UserPoolClient — its PhysicalResourceId (hence Ref) must be the ClientId that cognito-idp CreateUserPoolClient returns, and that id generator must emit ^[\w+]+$; not the generic physical-name generator. Nothing changes in cognito-identity's CreateIdentityPool validation.
Related open issues, named as required: 20261106T081405Z-cloudformation-cognito-identity-sts-aws-cognito-userpoolclient-s.md and 20261106T090935Z-cloudformation-cognito-identity-sts-an-aws-cognito-userpoolclient.md describe this behaviour under the suite heading cloudformation__cognito-identity__sts and do not carry these two check ids as replay keys; closing them would leave both of these checks failing.

=== Cause 2 of 5: a rolled-back stack emits a CREATE_FAILED event for the stack resource itself, in addition to the resource that failed ===
Failing check id: cognito-identity.deploy-cognito-identity-2-cfn-rollback-identity-pool-rejected.
AWS: recorded behavior only (CloudFormation event semantics; no Smithy constraint states it). When one resource fails during create, the only CREATE_FAILED event is the failing resource's — here ('RoleAttachment', 'AWS::Cognito::IdentityPoolRoleAttachment') with reason naming the missing rules configuration (`RuleConfiguration is required for Rules`) — and the summary text `The following resource(s) failed to create: [<logical ids>]. ` is attached to the STACK's ROLLBACK_IN_PROGRESS event, of which there is exactly one. Variable parts are the logical ids and the stack name.
Emulator: DescribeStackEvents additionally contains an event whose LogicalResourceId is the stack name, ResourceType `AWS::CloudFormation::Stack` and ResourceStatus `CREATE_FAILED`, carrying the reason `The following resource(s) failed to create: [RoleAttachment]. `. So the CREATE_FAILED set is [(<stack name>, 'AWS::CloudFormation::Stack'), ('RoleAttachment', 'AWS::Cognito::IdentityPoolRoleAttachment')] instead of just the latter.
Why: a client that locates the failing resource by filtering events on ResourceStatus == CREATE_FAILED (the documented way to find why a stack rolled back) gets the stack itself as a failed resource and cannot tell which resource is at fault; any tooling that asserts one failure per rollback, or that reads failed[0], picks the synthetic stack event and the wrong reason.
Fix: the CloudFormation stack-event recorder for a create-failure rollback — the stack-level transition must be recorded as ROLLBACK_IN_PROGRESS carrying the `The following resource(s) failed to create: [...]` reason, not as a second CREATE_FAILED event.

=== Cause 3 of 5: GetId against a pool with NO identity providers configured answers the wrong message ===
Failing check id: cognito-identity.deploy-cfn-stack-update-changes-provider-config-live.
AWS: GetId with a Logins entry on an identity pool that has no CognitoIdentityProviders and no SupportedLoginProviders at all is refused with NotAuthorizedException (Smithy: GetId errors include NotAuthorizedException, httpError 403) and the message `Identity pool - <IdentityPoolId> does not have identity providers configured.` — fixed text `Identity pool - ` / ` does not have identity providers configured.` with the pool id taken from the request. The refusal is about the pool's CONFIGURATION being empty, which is distinct from a token whose provider is not among the configured ones.
Emulator: same code, wrong message — `Token is not from a supported provider of this identity pool.` (recorded expected vs actual: expected ('NotAuthorizedException', 'Identity pool - <pool id> does not have identity providers configured.'), got ('NotAuthorizedException', 'Token is not from a supported provider of this identity pool.')).
Why: the two messages mean different things to an operator and to error-matching client code — one says "configure a provider on this pool", the other says "this token came from the wrong provider". A deploy-time check that a pool is still unconfigured (the shape of this check: refused before a CFN stack update adds the provider, accepted after) cannot distinguish the states.
Fix: GetId's provider-resolution/validation path in the cognito-identity handler — select the provider-less-pool message when the pool's provider configuration is empty, and keep the unsupported-provider message only when providers exist but none matches the login key.
Related open issue, named as required: 20261102T112202Z-cognito-identity-3-net-new-behavioral-root-causes.md covers a FOREIGN-pool token being refused with the logins-mismatch message; it is a different precondition (providers exist) and does not carry this check id.

=== Cause 4 of 5: principal tags never reach the STS session, so every aws:PrincipalTag condition/policy variable fails ===
Failing check ids: cognito-identity.e2e-principal-tags-federation-to-sts-session-tags, cognito-identity.e2e-principal-tags-flow-into-sts-session-tags, cognito-identity.principal-tag-condition-denies-the-other-tenants-object.
AWS: PrincipalTags supplied to GetOpenIdTokenForDeveloperIdentity (Smithy: PrincipalTags, map, @length 0..50, key PrincipalTagID 1..128, value PrincipalTagValue 1..256) are baked into the returned OpenID token, and a PrincipalTags mapping set with SetPrincipalTagAttributeMap maps a provider claim onto a tag; when that token is presented to sts:AssumeRoleWithWebIdentity (role trust granting sts:AssumeRoleWithWebIdentity AND sts:TagSession) the tags become session tags, so IAM conditions `StringEquals aws:PrincipalTag/<key>` match and the policy variable `${aws:PrincipalTag/<key>}` resolves inside a Resource ARN. The documented behaviour: the session CAN perform the action gated on the tag value it carries, and is refused with AccessDenied (message: `User: <assumed-role arn> is not authorized to perform: <action> on resource: <resource> because no identity-based policy allows the <action> action` — fixed text with the caller arn, action and resource taken from the request) only for a tag value it does not carry.
Emulator: the gated action is refused for the session that DOES carry the tag. iam:GetRole allowed only under `aws:PrincipalTag/department == engineering`, for a session minted from a token carrying department=engineering, is refused: `AccessDenied: User: arn:aws:sts::<acct>:assumed-role/<role>/<session> is not authorized to perform: iam:GetRole on resource: role <role> because no identity-based policy allows the iam:GetRole action`; likewise s3:GetObject on the session's own prefix is refused with `...is not authorized to perform: s3:GetObject on resource: "arn:aws:s3:::<bucket>/<key>" because no identity-based policy allows the s3:GetObject action`. Hypothesis: the AssumeRoleWithWebIdentity session minted from the Cognito token carries no session tags at all, so every aws:PrincipalTag condition evaluates false and `${aws:PrincipalTag/...}` in a Resource ARN resolves to nothing — both conditioned statements therefore grant nothing. For cognito-identity.principal-tag-condition-denies-the-other-tenants-object the replay output is only the 60 s harness cap, so which poll stalled is not stated; that check polls until the tenant's session may read its OWN `${aws:PrincipalTag/tenant}/`-scoped object, which never becomes allowed, consistent with the same cause.
Why: attribute-based access control for Cognito identities is inoperative in the refusing direction: every ABAC policy written per the Cognito "attributes for access control" guide denies its own principal, so multi-tenant applications are wholly broken rather than mis-scoped, and no client can validate a tag-scoped policy against the emulator.
Fix: the credential-vending path's session-tag propagation — the principal tags carried in the OpenID token / derived from the pool's PrincipalTagAttributeMap must be attached as session tags on the STS session minted by AssumeRoleWithWebIdentity (and by GetCredentialsForIdentity), and the policy evaluator must populate aws:PrincipalTag/<key> from them for both condition keys and policy variables.
Related open issues, named as required: 20261029T173827Z-cognito-identity-10-net-new-token-credential-refusal.md (owns server-side-principal-tag-attribute-map-enforced) and 20261026T054328Z-cognito-identity-4-net-new-root-causes-a.md (a vended session being authorization-UNBOUNDED) describe neighbouring defects; neither carries these three check ids, and this is the opposite symptom — a tag-gated grant that never applies.

=== Cause 5 of 5: a Rules role mapping never vends the role its matching rule names ===
Failing check ids: cognito-identity.role-mapping-rules-first-match-wins-in-order, cognito-identity.role-mapping-rules-match-types-evaluated.
AWS: Smithy com.amazonaws.cognitoidentity#RulesConfigurationType.Rules is required and documented "Rules are evaluated in order. The first one to match specifies the role."; MappingRule requires Claim, MatchType, Value and RoleARN, and MappingRuleMatchType has exactly Equals, Contains, StartsWith, NotEqual. So GetCredentialsForIdentity for a login whose claim satisfies a rule vends credentials for THAT rule's RoleARN (sts:GetCallerIdentity on them shows `arn:aws:sts::<acct>:assumed-role/<rule role>/<session>`); with two matching rules the first in the submitted list wins and reversing the list flips the vended role; a login matching no rule falls back per AmbiguousRoleResolution/the authenticated role.
Emulator: the vended session never names the rule's role. Both checks poll GetCredentialsForIdentity + sts:GetCallerIdentity until the caller arn contains `:assumed-role/<rule role>/` and never see it, exhausting the 60 s harness cap (`Check timed out after 60.0s`); the per-rule state they assert first (GetIdentityPoolRoles preserving rule order and MatchType) is reached, so the divergence is in evaluation at vend time, not in storage. The replay output gives only the cap, so whether the emulator vends the fallback role or keeps failing the vend is not stated. Hypothesis: the Rules mapping is not evaluated against the token's claims at vend time, so the authenticated/fallback role is always used.
Why: rules-based role mapping — the documented way to give different users different roles from one identity pool — has no effect; every identity is vended the same role, so an application that relies on claim-driven role selection gets either over-broad or under-broad permissions with no way to detect it, and no rule ordering or MatchType semantics can be validated.
Fix: the GetCredentialsForIdentity role-resolution path in the cognito-identity handler — evaluate the pool's RoleMappings of Type=Rules against the login token's claims in submitted order, select the first matching rule's RoleARN, apply Equals/Contains/StartsWith/NotEqual with their own semantics, and fall back only when no rule matches.
Related open issues, named as required: 20261026T054328Z-cognito-identity-4-net-new-root-causes-a.md ("rules-based role mapping ignores declared order") and 20261028T221339Z-cognito-identity-3-net-new-getcredentialsforidentity-root-causes.md (Rules mapping with AmbiguousRoleResolution) describe neighbouring causes but carry neither of these check ids; the observed symptom here is now a vend that never resolves to the rule role at all.
