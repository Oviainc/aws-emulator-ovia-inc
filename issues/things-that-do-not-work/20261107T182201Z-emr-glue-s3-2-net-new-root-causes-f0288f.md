# emr__glue__s3: 2 net-new root causes — an S3 Batch Operations job never leaves 'Ready' (never Active/Complete/Failed, nothing tagged), and a Glue job run never executes its script so an S3 GetObject denial is indistinguishable from any other failure

> _Note: this issue was identified against the code base at commit `e0dc03155a79e3340fd5a6f413ff0e6f3f485ded`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeJob

## Description
Two independent defects reached by the emr__glue__s3 cross-service checks, each with its own failing checks. THIS ISSUE BUNDLES 2 CAUSES. Both must be closed.

Cause 1 of 2: an S3 Control Batch Operations job is created and then parked in 'Ready' forever — it is never dispatched, never reaches a terminal status, and never performs its operation on the manifest's objects.
  AWS: s3control CreateJob with ConfirmationRequired=false returns a JobId, and the job then advances through the modeled status machine (Smithy: com.amazonaws.s3control#JobStatus = Active, Cancelled, Cancelling, Complete, Completing, Failed, Failing, New, Paused, Pausing, Preparing, Ready, Suspended) from New/Preparing through Ready and Active to the terminal Complete — assuming the RoleArn's trust policy names batchoperations.s3.amazonaws.com and its permissions allow the operation — applying Operation.S3PutObjectTagging to every object the manifest lists and writing the completion report under Report.Prefix. A job whose role cannot be assumed by Batch Operations (for example a role that trusts only ec2.amazonaws.com) instead settles terminal Failed with a FailureReason naming the unassumable role, and tags nothing. Recorded behavior: both checks poll s3control DescribeJob until Status is one of Complete/Failed/Cancelled and the recordings reach one.
  Emulator: DescribeJob keeps answering Status 'Ready' for the whole budget — e.g. last observed JobDescriptor {'JobId': <uuid>, 'Status': 'Ready', 'Operation': {'S3PutObjectTagging': {...}}, 'Priority': 1, 'Manifest': {...}, 'Report': {...}, 'RoleArn': 'arn:aws:iam::<account>:role/<role>'} — with no FailureReasons member and no ProgressSummary. 'Ready' is a legal JobStatus, so nothing is malformed; the job simply never runs. The target object's tag set stays empty and no report object is written. Both the positive path (good trust principal → Complete + object tagged) and the negative path (bad trust principal → Failed + nothing tagged) are therefore unobservable: the two outcomes are identical.
  Why: a client that submits a Batch Operations job and waits on it hangs indefinitely; no bulk tagging/copy/restore side effect ever lands, no completion report appears, and the trust/permission contract of the job role is never enforced, so a misconfigured role looks exactly like a healthy one.
  Fix: the s3control Batch Operations job runner behind CreateJob/DescribeJob (the job state machine in the s3control service state, which must move a ConfirmationRequired=false job Ready -> Active -> Complete, apply Operation to each manifest entry, write the report, and settle Failed with FailureReasons when the RoleArn cannot be assumed by batchoperations.s3.amazonaws.com).
  Note: open issues 20261102T121736Z-s3control-s3-control-batch-job-s3putobjecttagging-never-reaches-a.md, 20261029T192817Z-s3control-batch-operations-jobs-never-settle-and-refuse.md, 20261029T195302Z-s3control-batch-operations-a-confirmationrequired-false-s3putobjecttagging-job.md and 20261029T184212Z-s3control-an-s3-batch-operations-job-created-with-an.md describe the same non-settling Batch Operations job under the s3control service; none of them carries the two emr__glue__s3 check ids below, and the replay report did not mark these failures as owned, so they are filed here with those issues named.
  Traces: emr__glue__s3.iam-role-trust-s3-service-assumed-for-batch-op-positive, emr__glue__s3.s3-batch-operation-role-missing-s3-trust-rejected.

Cause 2 of 2: a Glue job run is recorded and immediately settled FAILED without the job script ever executing, so the run's ErrorMessage is an emulator sentence instead of the S3 access denial the script would have hit.
  AWS: glue StartJobRun returns a JobRunId and the run advances through the modeled states (Smithy: com.amazonaws.glue#JobRunState = STARTING, RUNNING, STOPPING, STOPPED, SUCCEEDED, FAILED, TIMEOUT, ERROR, WAITING, EXPIRED) while the script named by the job's Command.ScriptLocation actually runs under the job's Role. When that role is explicitly denied s3:GetObject on the source prefix, the Spark/Glue read of the source path fails and GetJobRun reports JobRunState FAILED with JobRun.ErrorMessage (Smithy: JobRun.ErrorMessage -> ErrorString, 'An error message associated with this job run') carrying the engine's own text for that failure — the S3 403/AccessDenied surfaced as an unreadable source path, naming the denied s3://<bucket>/<prefix> from the request and the role that was denied — and no output object is written. A sibling job whose role does hold s3:GetObject on the same prefix reaches SUCCEEDED and writes its output. Recorded behavior: the check asserts the FAILED run's error identifies the denied S3 read as a missing/unreadable source.
  Emulator: every run settles FAILED with the fixed emulator-authored ErrorMessage 'This emulator records job runs but executes no job script, so the job run ended without running.' — entirely emulator text, with no variable part taken from the request (no bucket, no source path, no role, no S3 error code), because the script is never executed and the role's S3 permissions are never evaluated.
  Why: a client cannot distinguish a permission defect from any other failure — every Glue run fails with the same sentence — so the in-file positive control also fails, and IAM/S3 permission boundaries around Glue ETL are unverifiable.
  Fix: the Glue job-run execution path behind StartJobRun/GetJobRun (the job-run state machine and script execution in the glue service), which must run the script, evaluate the run role's S3 permissions on the paths it touches, and report the resulting engine error in JobRun.ErrorMessage.
  Note: open issues 20261029T175551Z-glue-job-runs-reached-through-the-emr-glue.md and 20261029T185330Z-glue-job-runs-are-recorded-but-never-executed-e42472.md describe the same never-executed Glue run and own other checks' replay keys; neither carries the check id below, which the replay report left unowned.
  Traces: emr__glue__s3.glue-job-missing-s3-getobject-source-rejected.
