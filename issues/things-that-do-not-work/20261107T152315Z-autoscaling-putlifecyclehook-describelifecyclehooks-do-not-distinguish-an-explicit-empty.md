# PutLifecycleHook/DescribeLifecycleHooks do not distinguish an explicit empty NotificationTargetARN from an omitted one, and the 501 stub makes the check burn its whole 60s deadline (1 cause)

> _Note: this issue was identified against the code base at commit `5847d0581bcf2b9ad6cfaa8c900ea79fc46bdf96`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutLifecycleHook

## Description
Cause 1 of 1: a lifecycle hook's NotificationTargetARN has override semantics that the emulator serves nothing for, because PutLifecycleHook is still a 501 scaffold stub and the check's AWS-shaped retry loop therefore spins to the harness deadline instead of reaching a verdict. Failing check id: autoscaling.notification-config-empty-vs-absent-field-preserved.

AWS: PutLifecycleHook creates OR updates a hook. Smithy (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/smithy-model/com-amazonaws-autoscaling-autoscaling-2011-01-01.json): PutLifecycleHookType.LifecycleHookName (AsciiStringMaxLen255, len 1..255, required), AutoScalingGroupName (XmlStringMaxLen255, len 1..255, required), NotificationTargetARN (NotificationTargetResourceName, @length min 0 max 255 — so the empty string is a MODEL-VALID value), RoleARN, NotificationMetadata, HeartbeatTimeout (30..7200, default 3600), DefaultResult (CONTINUE|ABANDON, default ABANDON); modeled errors only LimitExceededFault (HTTP 400, awsQueryError code LimitExceeded) and ResourceContentionFault (HTTP 500, awsQueryError code ResourceContention); output PutLifecycleHookAnswer is empty, HTTP 200. The model's documentation for NotificationTargetARN states the override rule verbatim: "If you specify an empty string, this overrides the current ARN." and that LifecycleTransition and RoleARN are "Required for new lifecycle hooks, but optional when updating existing hooks." So three behaviors are required: (a) PutLifecycleHook naming an EXISTING hook is a partial update — members the request omits keep their previously stored values; (b) NotificationTargetARN="" is NOT "omitted": it clears the stored ARN, and DescribeLifecycleHooks then reports the member as empty/absent rather than the old ARN; (c) an update that carries only HeartbeatTimeout=120 must store 120 and leave NotificationTargetARN untouched. DescribeLifecycleHooks (Smithy: input AutoScalingGroupName required, LifecycleHookNames list 0..50; output LifecycleHooks; only ResourceContentionFault modeled) must project whichever of the two states the hook is in. Also per the model, specifying a notification target makes Auto Scaling send a test message to it, so a PutLifecycleHook with a freshly created RoleARN may legitimately be refused until IAM converges — AWS clients retry it, which is what this check does.

Emulator: PutLifecycleHook is an unimplemented scaffold — services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/put_lifecycle_hook.rs returns Err(crate::scaffolded::Scaffolded::not_implemented("PutLifecycleHook")), i.e. HTTP 501 with code NotImplemented and the emulator-authored message "operation PutLifecycleHook is scaffolded but not implemented in this emulator" (a code/status/message AWS never serves for this operation: the only modeled refusals are LimitExceeded 400 and ResourceContention 500). Because 501 arrives as a botocore ClientError, the check's AWS-correct "retry until IAM consistency closes" loop treats it as a transient refusal and retries for 60s; the replay verdict is therefore "Error: Check timed out after 60.0s" and NOTHING about the empty-vs-absent round-trip is ever observed. The companion read path DescribeLifecycleHooks is a stub as well.

Why: a client that manages lifecycle-hook notification targets cannot work at all. It cannot create a hook; worse, once the stub is replaced by a naive implementation, the natural shortcut of treating "" and absent alike silently corrupts configuration in both directions — clearing a target by sending "" would leave the old SNS/SQS ARN in place (notifications keep flowing to a target the operator believes they detached), and a narrow update that only changes HeartbeatTimeout would wipe the stored NotificationTargetARN (notifications stop silently and instances sit in the wait state until DefaultResult fires). Additionally, any client that retries refusals of this operation — the documented pattern, because of the test-message/IAM race — does not fail fast against the emulator, it hangs for its whole retry budget.

Fix: implement PutLifecycleHook in its handler (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/put_lifecycle_hook.rs) as an upsert over the group's hook collection in the service state, with per-member three-valued update semantics: member absent => keep stored value; member present (including the empty string for NotificationTargetARN) => overwrite, with "" clearing the target; require LifecycleTransition and RoleARN only when the named hook does not yet exist; default HeartbeatTimeout 3600 and DefaultResult ABANDON on create only. The matching projection belongs in the DescribeLifecycleHooks handler/serializer so a cleared target is reported as empty and an untouched one is reported unchanged. Related open stub issues that do NOT cover this check (it is reported as a 60s timeout, not as a NotImplemented failure, and neither of them states the empty-vs-absent override rule): 20261104T042502Z-autoscaling-putlifecyclehook-stub.md and 20261107T081710Z-auto-scaling-describelifecyclehooks-stub.md.

Traces: autoscaling.notification-config-empty-vs-absent-field-preserved (the only failing check in this suite not already marked ALREADY FILED or OWNED).

## Evidence
Expected (AWS): PutLifecycleHook(LifecycleHookName=H, AutoScalingGroupName=G, LifecycleTransition=autoscaling:EC2_INSTANCE_LAUNCHING, NotificationTargetARN=<topic arn>, RoleARN=<role arn>) -> HTTP 200, empty body; DescribeLifecycleHooks(G,[H]).LifecycleHooks[0].NotificationTargetARN == <topic arn>. Then PutLifecycleHook(LifecycleHookName=H, AutoScalingGroupName=G, NotificationTargetARN="") -> HTTP 200 and DescribeLifecycleHooks reports NotificationTargetARN as empty/absent (the empty string overrides the current ARN). On a second hook H2 set to <topic arn>, PutLifecycleHook(LifecycleHookName=H2, AutoScalingGroupName=G, HeartbeatTimeout=120) -> HTTP 200 and DescribeLifecycleHooks reports NotificationTargetARN == <topic arn> (unchanged) AND HeartbeatTimeout == 120. Variable parts above (G, H, H2, the topic ARN, the role ARN) come from the request/state; the required behavior is the three-valued update rule, not any one run's ARNs.

Actual (emulator): every PutLifecycleHook call answers HTTP 501 with error code NotImplemented and message "operation PutLifecycleHook is scaffolded but not implemented in this emulator" (handler: services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/put_lifecycle_hook.rs line 204, Scaffolded::not_implemented("PutLifecycleHook"); the SCAFFOLDED marker is at lines 4-6). The check's documented retry-on-ClientError loop (60s budget, 3s sleep) therefore never breaks out, and the suite records: "[mismatch] autoscaling.notification-config-empty-vs-absent-field-preserved / Error: Check timed out after 60.0s". No assertion about NotificationTargetARN is ever evaluated, so the empty-vs-absent round-trip is entirely unserved.

## Steps to Reproduce
1. Create an Auto Scaling group G with a launch template (MinSize 0, MaxSize 1, DesiredCapacity 0), an SNS topic T and an IAM role R trusted by autoscaling.amazonaws.com with sns:Publish on T.
2. autoscaling PutLifecycleHook LifecycleHookName=H AutoScalingGroupName=G LifecycleTransition=autoscaling:EC2_INSTANCE_LAUNCHING NotificationTargetARN=<T> RoleARN=<R>  -> emulator answers HTTP 501 NotImplemented instead of HTTP 200.
3. autoscaling DescribeLifecycleHooks AutoScalingGroupName=G LifecycleHookNames=[H] -> expect LifecycleHooks[0].NotificationTargetARN == <T>.
4. autoscaling PutLifecycleHook LifecycleHookName=H AutoScalingGroupName=G NotificationTargetARN=""  -> expect 200, then DescribeLifecycleHooks must report NotificationTargetARN empty/absent.
5. Repeat step 2 for a second hook H2, then autoscaling PutLifecycleHook LifecycleHookName=H2 AutoScalingGroupName=G HeartbeatTimeout=120 -> expect 200, then DescribeLifecycleHooks must report NotificationTargetARN still == <T> and HeartbeatTimeout == 120.
6. Replay the behavioral check autoscaling.notification-config-empty-vs-absent-field-preserved: against the emulator it does not fail at step 2, it retries the 501 and times out after 60s.
