# dynamodb__iam__sts: a conditioned Allow in an AssumeRole inline session policy never grants, so every DynamoDB read under that session is refused AccessDeniedException "because no session policy allows the <action> action" — including the requests the policy admits

> _Note: this issue was identified against the code base at commit `77172d4b913d3cd289b60abc3e2fa4659d3ee8a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetItem

## Description
ONE net-new root cause in the DynamoDB data-plane authorization gate as reached by an assumed-role session carrying an inline session policy. Neither failing check is marked ALREADY FILED or OWNED in the replay report.

Nearest open neighbour, named so it is not re-fixed and is not mistaken for coverage of these replay keys: 20261105T054223Z-dynamodb-iam-sts-dynamodb-data-plane-ignores-the-session-policy-s.md. That issue records the OPPOSITE failure of the same evaluation path — the session policy was not applied at all, so an unprojected read was SERVED. The emulator now refuses instead, and refuses the whole envelope including the projected read that policy explicitly allows, so its replay key no longer matches and the behaviour has crossed from over-permissive to over-restrictive. Fix them together: the requirement is that the conditioned Allow be DECIDED, not that it be denied.

Cause 1 of 1: a session-policy statement whose Allow carries DynamoDB request condition keys is treated as granting nothing.
AWS: an assumed-role session's request is authorized against the role's identity policies INTERSECT the inline session policy passed to sts:AssumeRole (Policy parameter); DynamoDB derives the condition keys dynamodb:LeadingKeys, dynamodb:Attributes and dynamodb:Select from the request itself (a ProjectionExpression with no explicit Select yields Select=SPECIFIC_ATTRIBUTES and Attributes = the projected names, including the key attributes the request addresses). A session policy of the form {"Effect":"Allow","Action":[...],"Resource":<table ARN>,"Condition":{"ForAllValues:StringEquals":{"dynamodb:LeadingKeys":[<allowed pk>], ...}}} therefore ADMITS every request inside that envelope — the matching-partition, correctly-projected read — and refuses only requests outside it. A refusal is AccessDeniedException with the message "User: <session principal ARN> is not authorized to perform: dynamodb:<Action> on resource: <table ARN> because no session policy allows the dynamodb:<Action> action"; the fixed text is "User: ", " is not authorized to perform: dynamodb:", " on resource: ", " because no session policy allows the dynamodb:", " action" and the variable parts are the AssumedRoleUser ARN STS returned, the table ARN from the request and the action actually called. Recorded behavior only for the refusal shape: Smithy declares no AccessDeniedException and no authorization trait on GetItem/Query/Scan/BatchGetItem, so the oracle for the code and message is the recorded AWS response.
Emulator: every call made with those session credentials is refused AccessDeniedException with exactly that "no session policy allows the dynamodb:<Action> action" message — including the requests the Allow covers. Replay: a GetItem on the allowed partition with ProjectionExpression='pk, sk, pub' (the positive control the session policy admits via dynamodb:Attributes/dynamodb:Select) stayed refused for the full 51.8 s retry budget with "User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: dynamodb:GetItem on resource: arn:aws:dynamodb:<region>:<account>:table/<table> because no session policy allows the dynamodb:GetItem action"; and a Scan under a session policy allowing dynamodb:Scan on the same table ARN with only a ForAllValues:StringEquals dynamodb:LeadingKeys condition is refused the same way for dynamodb:Scan. The conditioned statement is evidently skipped rather than evaluated, so the session is left with no grant at all.
Why: this is a false-negative authorization. A session policy is the documented way to hand out a narrowed read credential (per-tenant partitions, field-level withholding); against the emulator such a credential can do NOTHING, so a client that mints scoped sessions is dead in the water, and the per-request condition semantics the policy encodes can never be observed — neither the allow inside the envelope nor a correct deny outside it is distinguishable.
Fix: the DynamoDB data-plane authorization path shared by GetItem, Query, Scan, BatchGetItem and PartiQL reads: it must (a) evaluate the STS session's inline session policy as a scoping document alongside the identity policies (an Allow required from both; an explicit Deny in either wins) and (b) build the request condition context those statements need — dynamodb:Select from the request (explicit Select, or SPECIFIC_ATTRIBUTES when a ProjectionExpression/AttributesToGet is present), dynamodb:Attributes from the projected attribute names plus the addressed key attributes, dynamodb:LeadingKeys from the partition-key value(s) addressed — so a conditioned clause resolves to allow or deny instead of being discarded. The refusal wording above must be kept for the requests that genuinely fall outside the envelope.
