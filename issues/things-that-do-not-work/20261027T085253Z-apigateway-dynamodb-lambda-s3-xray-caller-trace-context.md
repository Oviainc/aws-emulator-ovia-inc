# apigateway__dynamodb__lambda__s3__xray: caller trace-context continuation and the Sampled=0 decision are unobservable — the traced REST API stage never yields a trace, so the check runs out the harness budget (1 cause)

> _Note: this issue was identified against the code base at commit `d566282976cd3ecbd638dcfb7eabea66136f946a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetTraces

## Description
Cause 1 of 1: the producer side of the distributed-tracing path (an AWS_PROXY REST API stage with tracingEnabled=true in front of a Mode=Active Lambda, feeding X-Ray) never produces an observable result, so the check that grades X-Amzn-Trace-Id continuation and the Sampled flag is terminated at the 60 s harness cap instead of reaching any assertion. Failing check: apigateway__dynamodb__lambda__s3__xray.apigw-trace-header-continuation-and-sampled-zero-rejects-recording.

AWS: recorded behavior only for the producer side (no Smithy model describes edge trace-context stamping); the query side is modeled — Smithy xray BatchGetTraces POST /Traces -> 200 {Traces[].Segments[].Document, UnprocessedTraceIds}, GetTraceSummaries POST /TraceSummaries -> 200 {TraceSummaries[].Id}. A GET on the invoke URL of a deployed REST API stage whose AWS_PROXY integration targets a Lambda answers HTTP 200 with the handler's response, and the edge stamps the invocation environment's _X_AMZN_TRACE_ID. Four behaviors are required of that stamping: (a) an inbound X-Amzn-Trace-Id: Root=<id>;Sampled=1 is CONTINUED — the handler observes the caller's Root byte-for-byte plus a freshly minted 16-hex Parent= and Sampled=1, the resulting trace is filed under the caller's id (BatchGetTraces([that id]) returns that id, not a shadow id), it carries segments from the API Gateway stage (origin AWS::ApiGateway::Stage) and the Lambda function (origins AWS::Lambda and AWS::Lambda::Function) plus any subsegment the handler delivered to the daemon at AWS_XRAY_DAEMON_ADDRESS, and it is indexed by GetTraceSummaries over a window covering the request; (b) an inbound Sampled=0 reaches the invocation unchanged (handler observes Sampled=0 under the caller's Root) and the request still does its work — the handler's DynamoDB PutItem lands — while NOTHING is recorded for that id: BatchGetTraces returns no Segments for it and it never appears in GetTraceSummaries over a window in which a Sampled=1 id from the same batch is already indexed; (c) a request with no X-Amzn-Trace-Id header gets a server-generated id of the form 1-<8 hex epoch>-<24 hex>, whose epoch prefix decodes to approximately now, distinct from any other request's id; (d) a syntactically invalid Root= (e.g. Root=not-a-trace-id) is IGNORED and replaced with such a server-generated id with Sampled=1 — it is neither propagated nor fatal to the request.

Emulator: the check never reaches an assertion — it is killed with 'Check timed out after 60.0s'. Nothing in its setup-and-exercise sequence (create a PAY_PER_REQUEST DynamoDB table, create an S3 bucket, create a python3.12 function with TracingConfig Mode=Active on a role granting xray:PutTraceSegments, deploy a GET /x AWS_PROXY REST API to a tracingEnabled stage, then GET the stage four times with different X-Amzn-Trace-Id headers) returns a usable result inside the budget. The stage GET is wrapped in a 90 s bounded retry that only loops on 403/429/5xx, and the trace reads are 240 s polls that exit only when the expected origins appear, so both a stage that does not serve 200 and a trace store that never receives a document present as this hang. A sibling check in the same group (apigw-lambda-ddb-s3-trace-tree-shape) times out identically and is reported OWNED, which localises the fault to the shared producer path rather than to this check's own assertions. Adjacent recordings of the same path show the concrete refusals behind it: open issue 20261024T043741Z-apigateway-dynamodb-lambda-s3-xray-both-x-ray-9c23a5.md recorded the stage GET answering HTTP 404 'UnknownService', and open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md records Lambda Invoke answering NotImplemented, so no handler ever runs and no segment is ever emitted. As a result none of (a)-(d) above is observable: no continued Root, no minted Parent, no AWS::ApiGateway::Stage / AWS::Lambda / AWS::Lambda::Function segment, no GetTraceSummaries entry, and the Sampled=0 arm — including the requirement that an unsampled request still performs its DynamoDB write — is never reached.

Why: a client cannot observe or trust distributed tracing through an API-fronted Lambda. Trace-context continuation is what joins a caller's trace to the ones its downstream services record; without it a client's own root id is lost at the edge, correlation across hops breaks, and sampling cannot be reasoned about at all — an unsampled request must still do its work and still record nothing, and a client that cannot distinguish 'not sampled' from 'not executed' makes wrong conclusions about data loss. Worse, the failure presents as an indefinite hang (the stage neither serving 200 nor refusing in a way the retry stops on), so client code and CI pipelines block rather than receiving an error they can handle.

Fix: the execute-api stage data plane — the emulator's front-door routing for a deployed REST API stage endpoint and its AWS_PROXY integration dispatch — must serve the stage GET and stamp/propagate the X-Amzn-Trace-Id context into the invocation environment (continue a valid caller Root with a fresh Parent, generate an epoch-prefixed id when the header is absent or malformed, and pass the Sampled decision through); the Lambda invoke path must actually run the handler; and the X-Ray ingestion state must accept segments from the API Gateway edge and the Lambda service as well as daemon datagrams, stitch them into one trace by trace_id/parent_id, index sampled traces for GetTraceSummaries, and record nothing for an unsampled id. Related open issue 20261025T080135Z-apigateway-dynamodb-lambda-s3-xray-both-end-to.md names this same check id in its trace list but is keyed on the other check's frame, which is why this failure was not reported as owned by it — the two should be reconciled rather than fixed twice.
