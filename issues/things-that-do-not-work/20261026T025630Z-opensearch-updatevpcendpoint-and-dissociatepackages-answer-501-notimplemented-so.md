# opensearch: UpdateVpcEndpoint and DissociatePackages answer 501 NotImplemented so in-flight-modification conflicts never serialize, and the package-association e2e flows never converge (3 causes)

> _Note: this issue was identified against the code base at commit `d5b444aa1a2c0b78901c8918371b89e5e61348ae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateVpcEndpoint

## Description
Three distinct root causes in the opensearch service. All three must be closed before this issue is resubmitted. None of the five grounding checks is marked ALREADY FILED or OWNED in the replay report; related open issues are named per cause below, and none of them carries these checks' replay keys.

Cause 1 of 3: UpdateVpcEndpoint is not served at all, so an endpoint that is already being modified cannot refuse a second writer and no writer ever wins.
AWS: UpdateVpcEndpoint (Smithy: POST /2021-01-01/opensearch/vpcEndpoints/update; required input VpcEndpointId (pattern ^aos-[a-zA-Z0-9]*$, len 5..256) and VpcOptions; required output VpcEndpoint) applies the requested VpcOptions to the named OpenSearch-managed VPC endpoint and returns 200 with the endpoint in UPDATING, settling ACTIVE with exactly the winner's SecurityGroupIds. A second update that lands while the first is still in flight is refused with the modeled ConflictException, HTTP 409 — documented as "An error occurred because the client attempts to remove a resource that is currently in use." The requirement graded here is the pair: exactly one winner (200) and exactly one loser (409 ConflictException), with the endpoint's final VpcOptions being the winner's and never a merge of both; once the endpoint is idle again, the loser's identical request must succeed. AWS publishes no fixed text for this refusal's message, so the requirement is the 409 status and the ConflictException code, with the message's variable part being the VpcEndpointId taken from the request; the recordings assert only the code.
Emulator: both calls answer the scaffold's 501 with Error.Code 'NotImplemented' — outcomes=[('error', 'NotImplemented'), ('error', 'NotImplemented')] for the sequential in-flight pair and [('a', ('err', 'NotImplemented')), ('b', ('err', 'NotImplemented'))] for the concurrent pair. 'NotImplemented' is not a modeled error of this operation at all, so there is no winner to settle and no 409 loser.
Why: a client cannot change the subnets or security groups of a VPC endpoint it created, and a client that relies on the service serializing concurrent writers (retry on ConflictException, then re-read) gets an unmodeled 501 it cannot classify as retryable or terminal, and an endpoint whose configuration never changes.
Fix: implement the UpdateVpcEndpoint handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/update_vpc_endpoint.rs) over the VPC-endpoint records in src/state.rs: apply VpcOptions, move the endpoint through UPDATING to ACTIVE, and refuse a write that arrives while the record is still in flight with the modeled ConflictException. A separate scaffold-stub issue exists for this operation (the report filed one for the check opensearch.update-vpc-endpoint-conflict-on-concurrent-modify-rejected, which it says it blocks); that issue covers only standing the operation up — the serialization/conflict behavior and the final-state requirement graded by the two checks below are the net-new cause recorded here.
Traces: opensearch.concurrency-update-vpc-endpoint-optimistic-lock, opensearch.update-vpc-endpoint-concurrent-modification-conflict.

Cause 2 of 3: DissociatePackages answers 501 NotImplemented, so an Associate/Dissociate race on one domain/package pair cannot converge to a deterministic state.
AWS: DissociatePackages (Smithy: POST /2021-01-01/packages/dissociateMultiple; required PackageList and DomainName; output DomainPackageDetailsList) removes the named associations and reports them in DISSOCIATING. Concurrent AssociatePackages and DissociatePackages on the same domain/package pair serialize: one applies (200) and the one that arrives against a pair already in transition is refused with the modeled ConflictException, HTTP 409 (both operations declare it), after which the pair settles either at exactly one ACTIVE association or at none — never both, never a duplicate, never stuck mid-transition. No fixed message text is published for that refusal; the requirement is the 409 status and the ConflictException code, with the domain name and package id from the request as its variable parts.
Emulator: the dissociating racer fails with Error.Code 'NotImplemented' ('dissociate racer failed with unexpected code NotImplemented'), an error the operation does not model, so the race has no modeled outcome and the association can never be removed.
Why: a client cannot detach a package from a domain, and a client that treats ConflictException as "retry after the transition settles" instead receives a 501 that it must treat as a permanent service fault; package lifecycle automation (associate, use, dissociate, delete) dead-ends.
Fix: implement the DissociatePackages handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/dissociate_packages.rs) against the same association state and shared association decision that src/ops/associate_package.rs already uses (crate::state plan_package_association / put_package_association), and make an in-transition pair refuse with ConflictException from that one shared decision so the two directions cannot disagree. The open issue 20261025T080923Z-opensearch-dissociatepackages-and-updatescheduledaction-answer-501-notimplemented-instead.md describes the same 501 for other checks but does not carry this check's replay key or its race-convergence requirement.
Traces: opensearch.concurrent-associate-dissociate-packages-race-consistency.

Cause 3 of 3: the two end-to-end package-association flows never complete — a bounded readiness poll never observes its terminal state, so each check is killed at the suite's 60s budget instead of finishing or being refused.
AWS: recorded behavior only. In AWS both flows run to completion: CreatePackage settles AVAILABLE, AssociatePackage/AssociatePackages settles the domain package at DomainPackageStatus=ACTIVE (observable through ListPackagesForDomain, Smithy: GET /2021-01-01/domain/{DomainName}/packages), the domain publishes an Endpoint that serves the engine (so a signed GET / answers 200 and the package's file is mounted at analyzers/<PackageID> and genuinely drives the analyzer), and the flow then tears the index and association down. Every state a client polls for reaches a terminal value.
Emulator: both checks produce no response assertion at all — 'Check timed out after 60.0s'. Nothing in the run reports a status, code or message, because the emulator's answers keep the checks' bounded poll loops retrying rather than settling or refusing. Hypothesis: the loops that spin are the readiness/convergence waits these two flows share — _wait_data_plane_ready (a signed GET / on DomainStatus.Endpoint, which this emulator answers 404 {'__type': 'UnknownService', 'message': "no emulated service is registered for 'es'"}) and the DomainPackageStatus==ACTIVE poll over ListPackagesForDomain; a readiness loop sized for AWS's minutes never exits because the condition is never satisfiable, so the budget expires. The emulator's own provisioning span is not the cause: src/state.rs PROVISIONING is 500ms.
Why: a client that waits for a documented terminal state (package AVAILABLE, association ACTIVE, endpoint serving) hangs instead of either proceeding or receiving an error, which is the worst of both: no success, no failure to handle, and a wedged caller. The whole custom-package-drives-search capability is unreachable.
Fix: make every polled lifecycle state reach a terminal value and make an unsupported step refuse rather than stay pending — the package/association settling in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs (settle_packages and the association records it owes a status to), the ListPackagesForDomain handler that reports it, and the domain endpoint router that must serve the published Endpoint. Related open issues: 20261024T055421Z-opensearch-domain-data-plane-is-not-served-and.md (data plane answers 404 UnknownService) and 20261025T080923Z-opensearch-listpackagesfordomain-stub.md; neither carries these two checks' replay keys, and neither covers the no-response-at-all outcome recorded here.
Traces: opensearch.e2e-package-association-enables-index-analyzer, opensearch.e2e-package-association-search-flow.
