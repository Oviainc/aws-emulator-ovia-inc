## Description

=== Cause 1 of 2: MergePullRequestByFastForward refuses a repeat merge of a pull request it already merged, instead of answering idempotently ===
Failing check: codecommit.merge-pull-request-refused-when-approval-rules-not-satisfied

AWS: Smithy MergePullRequestByFastForward — input pullRequestId (PullRequestId, @required), repositoryName (RepositoryName, @required, @length 1..100, @pattern ^[\w\.-]+$), sourceCommitId (ObjectId, optional); output pullRequest (PullRequest). The operation doc is "Attempts to merge the source commit of a pull request into the specified destination branch for that pull request at the specified commit using the fast-forward merge strategy. If the merge is successful, it closes the pull request." The model does bind PullRequestAlreadyClosedException (client, HTTP 400, "The pull request status cannot be updated because it is already closed.") to this operation, but the model does not say WHICH closed pull requests it applies to, and the recorded behavior settles it: recorded behavior only — calling MergePullRequestByFastForward a second time on the pull request THIS SAME operation just merged returns HTTP 200 with the pull request still CLOSED and the SAME mergeMetadata as the first call (same isMerged=true, same mergeOption=FAST_FORWARD_MERGE, same mergedBy, and critically the same mergeCommitId), and the destination branch does not advance a second time. The merge is the idempotent re-read of a merge that already happened, not a state transition that can be attempted twice; PullRequestAlreadyClosedException is the answer AWS gives for mutating a closed pull request's own fields (UpdatePullRequestTitle / UpdatePullRequestDescription / OverridePullRequestApprovalRules), which the same check confirms separately and which the emulator gets right.

Emulator: the second MergePullRequestByFastForward call is rejected with HTTP 400 PullRequestAlreadyClosedException and the message "The pull request status cannot be updated because it is already closed." The refusal is unconditional on status: the handler tests only `pull_request.status != PULL_REQUEST_STATUS_OPEN` and errors out, so it cannot distinguish a pull request closed BY this merge (whose mergeMetadata it should echo) from one closed without ever being merged. The botocore client surfaces it as an uncaught botocore.errorfactory.PullRequestAlreadyClosedException, aborting the check. Everything up to that point passes: the approval-rule gate correctly refuses the unapproved merge with PullRequestApprovalRulesNotSatisfiedException and the documented message, leaves main at the base commit, and the post-override merge succeeds and reports CLOSED with correct mergeMetadata.

Why: merge is the one CodeCommit call a client is most likely to retry — a timed-out or network-interrupted MergePullRequestByFastForward gives the caller no way to know whether the merge landed. Against real AWS the safe recovery is to simply call it again and read mergeMetadata.mergeCommitId from the 200. Against this emulator that retry turns a SUCCESSFUL merge into a 400 error, so CI/CD merge-bots, retrying SDK wrappers and any at-least-once orchestrator report a merge failure for a pull request that is in fact merged, and then take compensating action (re-open, re-push, alarm) on a branch that already carries the change.

Fix: the already-closed guard in the MergePullRequestByFastForward handler (services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/merge_pull_request_by_fast_forward.rs) must not be a blanket status test. When the stored pull-request target already records a completed merge (mergeMetadata.isMerged true), the handler must return 200 with the STORED pull request and its existing mergeMetadata unchanged — no new mergeCommitId, no second reference move, no re-stamp of mergedBy — and reserve PullRequestAlreadyClosedException for a closed pull request that was never merged. The same reading belongs in the squash and three-way merge handlers, which share this precondition.

=== Cause 2 of 2: GetPullRequestOverrideState.overrider is an identity synthesized from the access key id, not the principal the request authenticates as ===
Failing check: codecommit.pull-request-override-state-reflects-override

AWS: Smithy OverridePullRequestApprovalRules — input pullRequestId (@required), revisionId (@required), overrideStatus (OverrideStatus enum, @required); output Unit. GetPullRequestOverrideState — input pullRequestId (@required), revisionId (@required); output overridden (Overridden boolean, @default false) and overrider (Arn). overrider is documented as "The Amazon Resource Name (ARN) of the user or identity that overrode the rules and their requirements for the pull request." The requirement is an identity EQUALITY, not a literal string: after exactly one OverridePullRequestApprovalRules(overrideStatus="OVERRIDE") by one caller, GetPullRequestOverrideState.overrider is exactly the principal ARN that same signing credential resolves to — i.e. the Arn sts:GetCallerIdentity returns for the same request signer.

Emulator: the override itself works (overridden flips false -> true, and the post-override EvaluatePullRequestApprovalRules correctly keeps approved=false with the rule still in approvalRulesNotSatisfied), but overrider comes back as arn:aws:iam::<accountId>:user/<ACCESS-KEY-ID> — built from the access key id the request was signed with — while sts:GetCallerIdentity for that very same credential answers arn:aws:iam::<accountId>:user/emulator. The replayed check observed overrider='arn:aws:iam::000000000000:user/EMULATOR6F9C4A204985' against a caller identity of 'arn:aws:iam::000000000000:user/emulator'. The account id and the key-id text are per-run values; the DIVERGENCE is that the user-path segment is derived from the key id's text instead of from the resolved principal, so the two answers disagree for one credential. This is the same stand-in-identity path that open issue 20261028T080155Z-codecommit-comment-reaction-attribution-uses-an-access-key.md reports for GetCommentReactions.reactionUsers; that issue does NOT cover this check (its replay list names only the two comment-reaction check ids, and its operation is GetCommentReactions), so it is filed separately here — if the shared resolution is fixed centrally, both close together. Open issue 20261027T073300Z-codecommit-getpullrequestoverridestate-stub.md is also related but NOT covering: that operation is no longer a 501 stub — it answers — this is a fidelity defect in the ARN it reports.

Why: overrider is the audit field of a privilege bypass. A reviewer UI or compliance job reads its own identity once from sts:GetCallerIdentity and then renders/attests "approval rules were overridden by <principal>", or tests whether the override was its own; against this emulator that ARN names no principal any IAM or STS surface knows, so the attribution is uncorrelatable and every per-identity override policy check silently fails to match.

Fix: the shared caller-identity resolution in the codecommit crate's state module must report the principal the credential resolves to (the identity STS answers for the same access key id) rather than an identity invented from the key id's text, so the stand-in path cannot disagree with sts:GetCallerIdentity. The OverridePullRequestApprovalRules handler must store that principal, and the GetPullRequestOverrideState serializer project it into overrider.
