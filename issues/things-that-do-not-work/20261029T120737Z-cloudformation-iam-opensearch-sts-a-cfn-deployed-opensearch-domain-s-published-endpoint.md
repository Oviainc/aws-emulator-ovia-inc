Fix them together if they share one router; this issue exists so the check id below is re-replayed. Note this check uses NO fine-grained access control at all — authorization here is the domain's IAM resource policy (AccessPolicies) plus the roles' identity policies — so it exercises a path those FGAC-shaped issues do not.

Cause 1 of 1: the emulator's CloudFormation + OpenSearch control plane successfully provisions the stack (two IAM roles plus an AWS::OpenSearchService::Domain whose AccessPolicies name each role via !GetAtt RoleX.Arn, one Allow and one Deny), DescribeDomain reports Processing=false with a non-empty Endpoint whose value matches the stack's !GetAtt Domain.DomainEndpoint output, the deployed AccessPolicies document round-trips with both role ARNs resolved and the right Effects, and both roles are assumable via sts:AssumeRole. Everything up to the data plane passes. But SigV4-signed ('es') HTTPS requests to that published endpoint never return HTTP 200 — not even GET /_cluster/health issued as the role the domain's own resource policy explicitly Allows with Action 'es:*'. The check polls that URL every 2 s until the run budget is spent and therefore never reaches the behavior under test (the allowed role's PUT /<index>/_doc/1 returning 201, the denied role's GET returning 403 with the explicit-deny refusal body, and those two verdicts reversing in place after a change set swaps the Allow and the Deny).

AWS: the OpenSearch domain native REST surface is not a Smithy API — recorded behavior only for the data plane itself. The modelled half is com.amazonaws.opensearch#DomainStatus.Endpoint ("Domain-specific endpoint used to submit index, search, and data upload requests to the domain") and DomainStatus.AccessPolicies (target PolicyDocument, @length 0..102400, "IAM policy document specifying the access policies for the domain"), together with DomainStatus.Processing ("False if the configuration is active") and DomainEndpointOptions.EnforceHTTPS. The contract AWS honours around them: once a domain publishes an Endpoint and Processing is false, a SigV4-signed (service 'es', domain region) HTTPS request to https://<Endpoint>/_cluster/health from a principal the domain's AccessPolicies Allow is answered HTTP 200 with the cluster-health document; a PUT of a new document to https://<Endpoint>/<index>/_doc/<id> by that principal is answered HTTP 201 with a body whose "result" field is the fixed string "created"; and an identical request by a principal the same AccessPolicies explicitly Deny is answered HTTP 403 whose JSON body carries a "Message" field holding the explicit-deny refusal naming that principal's role ARN and the refused action (here es:ESHttpGet) — the action name and the principal ARN are values taken from the request and the stored policy, the surrounding refusal wording is fixed text. After an AccessPolicies-only update the domain keeps the same DomainId, ARN and Endpoint (an in-place Modify, Replacement=False) and the two principals' verdicts swap.

Emulator: the published endpoint (the host the emulator itself put in DomainStatus.Endpoint and in the stack output) never answers 200 to the Allowed role. The check exhausts its run budget inside _wait_data_plane_allows and reports `TimeoutError: allowed role getting 200 from https://<published-endpoint>/_cluster/health: the run budget ended first; not graded`, so this report does not carry the last observed status code. Sibling opensearch checks in the already-open issues above record signed requests to the same kind of endpoint being answered HTTP 404 with body {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"} — Hypothesis: the same unrouted data plane is what this check is waiting on. Either way the divergence is the emulator's: it published that endpoint and it serves that host.

Why: a client relying on AWS's behavior cannot index, read or search against an emulated domain at all, and can observe no domain-level authorization verdict. Specifically, a stack that encodes its security boundary in the domain's resource policy (Allow one role, Deny another) appears to deploy perfectly — outputs, ARNs, endpoint and the stored policy document all look right — while nothing enforces or even serves that boundary, so a 'the denied role is refused 403' expectation and the in-place allow/deny swap after a change set are silently unvalidated.

Fix: the emulator's request router / OpenSearch domain data plane — serve the domain host published in DomainStatus.Endpoint as the native 'es' REST surface (/_cluster/health, /<index>/_doc/<id>, /<index>/_search) over SigV4 with service name 'es', and evaluate the domain's stored AccessPolicies together with the caller's identity policy on each signed request so an Allowed principal gets 200/201 and an explicitly Denied principal gets 403 with the explicit-deny Message body. The endpoint the control plane publishes must be the host that is actually served, and an AccessPolicies-only UpdateDomainConfig (as executed by a CloudFormation change set) must re-point authorization without changing DomainId/ARN/Endpoint.

Traces: cloudformation__iam__opensearch__sts.deploy-opensearch-1-changeset-swaps-allowed-and-denied-roles-in-place (fails in _wait_data_plane_allows at the first data-plane call, after CreateStack, the stack Outputs assertions, _wait_domain_settled, the AccessPolicies round-trip assertion and both sts:AssumeRole calls had all succeeded).
