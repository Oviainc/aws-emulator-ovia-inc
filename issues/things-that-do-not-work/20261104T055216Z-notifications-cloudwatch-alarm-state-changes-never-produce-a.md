# notifications: CloudWatch alarm state changes never produce a NotificationEvent, and the duplicate-EventRule ConflictException is worded differently from AWS (2 causes)

> _Note: this issue was identified against the code base at commit `e8571d025aeac7270f8ce9c804fecdb89f8ea73b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListNotificationEvents

## Description
Two net-new root causes in the notifications (AWS User Notifications) service crate, both grounded in failing behavioral checks of this run. Neither is marked ALREADY FILED or OWNED by an open issue, and no open issue listed for this service covers them: the two open notifications issues cover the `AWS-MP-Buyer` managed-catalog description text and the bodyless-204 `content-length` framing, which are unrelated to the event data plane and to the EventRule conflict wording.

Cause 1 of 2: no source event ever becomes a NotificationEvent, so the whole event data plane of this service is empty forever.
AWS: Smithy: `CreateEventRule` (POST /event-rules, 201) binds a NotificationConfiguration to a `(source, eventType)` pair — `source` @pattern `^aws.([a-z0-9\-])+$`, `eventType` @pattern `^([a-zA-Z0-9 \-\(\)])+$`, documented as "Must match one of the valid Amazon EventBridge event types. For example, EC2 Instance State-change Notification and Amazon CloudWatch Alarm State Change" — and once that rule's Regions report `ACTIVE` in `GetEventRule.statusSummaryByRegion`, a matching source event delivered in those Regions is stored by the service as a NotificationEvent. No modeled operation creates one (there is no Create/PutNotificationEvent in the model); the events are produced by delivery and are only READ, by `ListNotificationEvents` (GET /notification-events, 200, `notificationEvents` @required, filters `source`/`startTime`/`endTime`) and `GetNotificationEvent`. So for a configuration whose rule matches `source=aws.cloudwatch`, `eventType=CloudWatch Alarm State Change` with `eventPattern {"detail":{"state":{"value":["ALARM"]}}}`, a real CloudWatch metric-alarm transition into ALARM (here forced with `SetAlarmState`) makes `ListNotificationEvents(source="aws.cloudwatch", startTime=...)` report an event whose `notificationConfigurationArn` is that configuration, and `GetNotificationEvent` on its arn returns a non-empty `content`. This delivery is independent of the alarm's own actions: the check's alarm is created with `ActionsEnabled=False` and carries no AlarmActions, and AWS still delivers the notification, because User Notifications consumes the service event, not the alarm action.
Emulator: `ListNotificationEvents` never reports anything, for any source, because nothing ever records an event. `services/service-com-amazonaws-notifications-notifications/src/state.rs` holds `notification_events: BTreeMap<..>` / `notification_events_recorded`, a `NotificationEventDelivery` input struct and `record_notification_event()` + `mint_notification_event_arn()` to write one, and its own doc comments state the store "Empty until a delivery records one" — but no delivery path in the emulator calls it. The producing side has no fan-out either: the CloudWatch crate's transition path (`services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/ops/set_alarm_state.rs` -> `state::alarm_actions::settle_alarms`) delivers a transition ONLY to SNS topic ARNs named in the alarm's actions, and its module header says so explicitly ("Only an SNS topic ARN is delivered to here"); there is no EventBridge-style event emission and no in-process callback into the notifications service. The rest of the path does work: the hub registers and settles ACTIVE, `CreateNotificationConfiguration` and `CreateEventRule` succeed, and the rule's Regions settle from `CREATING` to `ACTIVE` within `EVENT_RULE_TRANSITION_SPAN` (500 ms), so the check gets past its rule-ACTIVE poll and then spends its whole remaining budget polling an eternally empty listing (the check polls every 10 s for up to 300 s; the harness cut it at 60 s, which is why the verdict is a timeout rather than an assertion).
Why: a client that configures User Notifications and then waits for the notification its rule subscribes to waits forever — no event is ever listed, so no `GetNotificationEvent` arn ever exists, `content` can never be read, and any application or test that gates on "the notification arrived" hangs or fails by timeout instead of being told anything. Because the gap is in the delivery seam, not in one source, EVERY `(source, eventType)` pair is equally dead, not just CloudWatch alarms.
Fix: the missing delivery seam. The notifications crate needs a delivery entry point that matches a source event against the stored EventRules of each configuration — the `(source, eventType)` pair, the rule's `regions`, the rule's `eventPattern`, and the rule's per-Region `ACTIVE` status — and then calls the existing `record_notification_event` with a populated `NotificationEventDelivery` (headline/content, `eventStatus`, `notificationType`, `aggregationEventType`, region-bearing arn), so `ListNotificationEvents` and `GetNotificationEvent` report it. The producing side needs to emit an alarm-state-change event into that seam from the CloudWatch transition path over the in-process callback, independently of `ActionsEnabled` and of any SNS action. Code: services/service-com-amazonaws-notifications-notifications/src/state.rs (`record_notification_event`, `notification_events`), src/ops/list_notification_events.rs and src/ops/get_notification_event.rs on the reading side; services/service-com-amazonaws-cloudwatch-graniteserviceversion20100801/src/state/alarm_actions.rs (`settle_alarms`/`drive_alarm_clock`) and src/ops/set_alarm_state.rs on the producing side.
Traces: notifications.cloudwatch-alarm-state-change-delivers-notification-event.

Cause 2 of 2: the duplicate-`(source, eventType)` refusal of `CreateEventRule` carries a message AWS does not word that way.
AWS: Smithy: `CreateEventRule` declares `ConflictException` (@httpError 409, "Updating or deleting a resource can cause an inconsistent state"); the model does not spell the sentence, so the text is recorded behavior. The recorded refusal of a second create for a pair one of the configuration's rules already covers reads, as a template whose fixed text is exact: `EventRule with source <source> and eventType <eventType> already exists in NotificationConfiguration with arn <notificationConfigurationArn>.` — the fixed parts being `EventRule with source `, ` and eventType `, ` already exists in NotificationConfiguration with arn ` and the trailing `.`; the three variable parts are the request's own `source`, its `eventType`, and the `notificationConfigurationArn` it named (the arn in the check's output, `arn:aws:notifications::000000000000:configuration/e8pcqadt47nggujywyenpd6cqhc`, is one run's value filling that slot, not part of the template). The status (409) and the code (`ConflictException`) are correct in the emulator; only the message diverges.
Emulator: `crate::state::event_rule_pair_conflict_message` renders all-lower-case prose in a different shape — observed `an event rule with source aws.ec2 and event type EC2 Instance State-change Notification already exists for notification configuration arn:aws:notifications::000000000000:configuration/e8pcqadt47nggujywyenpd6cqhc`: `EventRule` spelled `an event rule`, the member spelled `event type` instead of `eventType`, `already exists for notification configuration` instead of `already exists in NotificationConfiguration with arn`, and no terminating period. The crate's own doc comment on that function records that the wording is the emulator's own invention and that an observation of AWS supersedes it; this check is that observation. Everything else the check asserts about the race holds: exactly one of 5 concurrent creates wins, the other 4 are refused with `ConflictException`, and `ListEventRules` holds only the winner's rule.
Why: a client that branches on the refusal text — matching the sentence, or parsing the arn/source/eventType out of it to report which rule is in the way — takes the wrong branch or extracts nothing against the emulator while working against AWS, and any assertion on the refusal wording fails.
Fix: the conflict message builder, so the one place that words this refusal states AWS's sentence with the request's `source`, `eventType` and `notificationConfigurationArn` substituted. Code: services/service-com-amazonaws-notifications-notifications/src/state.rs, `event_rule_pair_conflict_message` (its sole caller is the conflict arm of src/ops/create_event_rule.rs, so the fix is in one place and covers `UpdateEventRule`-style callers if any are added).
Traces: notifications.concurrent-event-rule-creation-yields-distinct-rules.

## Steps to Reproduce
Prerequisite for both: build and boot the emulator from this checkout; the notifications service answers on the data listener (AWS User Notifications' control plane is us-east-1-only, which the emulator serves from its single endpoint).

Cause 1 (NotificationEvent never delivered):
1. `notifications:RegisterNotificationHub` for the region, and poll `ListNotificationHubs` until one hub reports `statusSummary.status == ACTIVE`.
2. `CreateNotificationConfiguration(name=..., description=..., aggregationDuration="NONE")` and keep the returned `arn`.
3. `CreateEventRule(notificationConfigurationArn=<that arn>, source="aws.cloudwatch", eventType="CloudWatch Alarm State Change", eventPattern='{"detail":{"state":{"value":["ALARM"]}}}', regions=[<region>])`; poll `GetEventRule(arn=<rule arn>)` until `statusSummaryByRegion[<region>].status == "ACTIVE"` (reached in well under a second).
4. `cloudwatch:PutMetricAlarm` for a fresh alarm (`ComparisonOperator=GreaterThanThreshold`, `EvaluationPeriods=1`, `Period=60`, `Statistic=Average`, `Threshold=1.0`, `ActionsEnabled=False`), then `cloudwatch:SetAlarmState(AlarmName=..., StateValue="ALARM", StateReason=...)`.
5. Poll `notifications:ListNotificationEvents(source="aws.cloudwatch", startTime=<just before step 4>, maxResults=50)`. Observe `notificationEvents` is empty on every poll, so no event with `notificationConfigurationArn == <configuration arn>` ever appears and `GetNotificationEvent` can never be called. Expected: an event for the ALARM transition, whose `GetNotificationEvent` response names that configuration and carries non-empty `content`.

Cause 2 (ConflictException wording):
1. Register/confirm an ACTIVE hub and `CreateNotificationConfiguration` as above; keep its `arn`.
2. Call `CreateEventRule(notificationConfigurationArn=<arn>, source="aws.ec2", eventType="EC2 Instance State-change Notification", regions=[<region>])` TWICE (or 5 times concurrently, as the check does).
3. The second/losing calls answer 409 `ConflictException`. Compare the `Error.Message` with AWS's sentence `EventRule with source aws.ec2 and eventType EC2 Instance State-change Notification already exists in NotificationConfiguration with arn <arn>.` and observe the emulator's lower-case `an event rule ... already exists for notification configuration <arn>` instead.
