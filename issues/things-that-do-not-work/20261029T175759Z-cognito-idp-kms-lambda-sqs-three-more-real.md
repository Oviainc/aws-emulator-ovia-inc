# cognito-idp__kms__lambda__sqs: three more real-verification-code flows never get a code — the CustomEmailSender trigger produces nothing, so sign-up confirmation and the wrong-code refusals are ungraded (1 cause)

> _Note: this issue was identified against the code base at commit `2e707008848158ee4bc91f1419f4a05920706f3a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ConfirmSignUp

## Description
ONE cause, reached by three checks that the report marked neither ALREADY FILED nor OWNED. They are the same mechanism as the seven checks already owned by 20261025T015335Z-cognito-idp-kms-lambda-sqs-the-customemailsender-lambda.md and the EMAIL_OTP variant in 20261025T182751Z-cognito-idp-kms-lambda-sqs-the-email-otp.md (and the earlier, now-fixed 20261025T022656Z-cognito-idp-kms-lambda-sqs-every-real-verification.md), but those issues do not carry these three replay keys, so they are filed here.

Cause 1 of 1 — a user pool with a CustomEmailSender Lambda trigger never invokes it, so no verification code is ever observable and no code-dependent flow can run.
AWS (recorded behavior; the model only declares the trigger's shape): a pool configured with LambdaConfig.CustomEmailSender (LambdaVersion V1_0 + LambdaArn) and LambdaConfig.KMSKeyID has every code-bearing message handed to that function instead of being emailed: SignUp, ResendConfirmationCode, ForgotPassword, GetUserAttributeVerificationCode and the EMAIL_OTP challenge each invoke it with triggerSource='CustomEmailSender_<flow>', userName and request.code — an AWS Encryption SDK message the function KMS-decrypts under the pool's CMK with the message's own encryption context. The decrypted code is six digits, and it is the real credential: ConfirmSignUp/ConfirmForgotPassword with it succeeds (and InitiateAuth then issues tokens whose ID token reports email_verified), while a WRONG code is refused CodeMismatchException.
Emulator: the trigger function is never invoked. No delivery ever reaches the function's SQS sink, so each check's inbox poll (next_code, 120 s budget, SQS ReceiveMessage with WaitTimeSeconds=5) never returns and the harness kills the check at its 60 s cap. The whole estate builds correctly first — the CMK, the queue, the execution role, the Node.js function reaching State=Active, the pool with the trigger, and SignUp/ForgotPassword themselves all succeed — so the gap is specifically the trigger invocation (and, behind it, the lack of any in-process Lambda runtime: see the open 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md).
Why: with a CustomEmailSender configured, this trigger is the ONLY place a code exists — there is no email and no API that returns it. An emulator that never calls it makes every confirmation, password-reset and attribute-verification flow unreachable, and the negative half (CodeMismatchException for a wrong code, which these two checks grade) can never be demonstrated because there is no correct code to contrast it with.
Fix: the Cognito IDP user-pool trigger dispatch — invoke the configured CustomEmailSender function (with the code encrypted under the pool's KMSKeyID and the AWS Encryption SDK encryption context) on every code-bearing flow, which requires the Lambda invoke path to actually run the deployment package.
Traces: cognito-idp__kms__lambda__sqs.deep-cognito-idp-1-real-code-signup-confirm, cognito-idp__kms__lambda__sqs.deep-cognito-idp-1-real-code-signup-wrong-code-rejected, cognito-idp__kms__lambda__sqs.deep-cognito-idp-1-real-code-forgot-password-wrong-code-rejected.

## Evidence
All three report "Error: Check timed out after 60.0s". The surviving probe in each is estate['inbox'].next_code(username, 'CustomEmailSender_<flow>') — a loop of sqs.receive_message(QueueUrl=<the trigger's sink>, MaxNumberOfMessages=10, WaitTimeSeconds=5) with a 120 s budget that raises "no <triggerSource> code for <user> reached the trigger's queue within 120.0s; deliveries seen but unmatched: []" only if nothing arrives. Everything before that poll succeeded: CreateKey, CreateQueue, the execution role with kms:Decrypt + sqs:SendMessage, CreateFunction (nodejs, polled to State='Active'), CreateUserPool with LambdaConfig={'CustomEmailSender': {'LambdaVersion': 'V1_0', 'LambdaArn': <fn>}, 'KMSKeyID': <key ARN>}, the app client, and the SignUp/ForgotPassword call itself. The function is written to send its own failure to the queue if it cannot decrypt request.code, so an empty queue means it never ran at all. The checks' assertions on the code are re.fullmatch(r'\\d{6}', code) and delivered['keyArn'] == the pool's CMK; the wrong-code legs expect CodeMismatchException.

## Steps to Reproduce
Replay the three check ids in trace_ids (each is killed at the 60 s cap). By hand: CreateKey; CreateQueue; create an execution role allowing kms:Decrypt on the key and sqs:SendMessage on the queue; CreateFunction (any runtime) that KMS-decrypts request.code and SendMessages the result; CreateUserPool with LambdaConfig.CustomEmailSender (LambdaVersion V1_0, that LambdaArn) and LambdaConfig.KMSKeyID = the key; CreateUserPoolClient; SignUp a user (and separately ForgotPassword) — then poll the queue: no message ever arrives, so no code exists to pass to ConfirmSignUp/ConfirmForgotPassword and no CodeMismatchException can be elicited for a wrong one.
