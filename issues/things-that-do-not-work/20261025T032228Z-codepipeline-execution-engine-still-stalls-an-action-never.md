# CodePipeline execution engine still stalls: an action never leaves InProgress once a stage transition is disabled, and 18 further checks exhaust their poll budget (2 causes)

> _Note: this issue was identified against the code base at commit `afc21d5623f1a8f7411b21bbb87a0dff6c2e7024`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartPipelineExecution

## Description
TWO net-new root causes in the codepipeline execution plane. A fixer must close BOTH before submitting; the two causes have DIFFERENT failing-check lists, named per cause below.

Related but NOT covering: the resolved issue 20261023T080113Z-codepipeline-execution-engine-41-further-behavioral-checks-exhaust.md claimed the engine gap fixed, and the engine now demonstrably does some work (an S3 Source action succeeds and an S3 Deploy action runs in a two-stage pipeline — see the sibling issue filed in this same sweep — and PollForJobs does dispatch a custom-action job). The checks below are still failing after that fix, and none of them is marked ALREADY FILED or OWNED in this replay, so no open issue carries their replay keys. The open issue 20261024T114145Z-codepipeline-createpipeline-never-triggers-its-own-execution-and.md records that CreatePipeline still starts no execution of its own; several checks under Cause 2 wait on that auto-triggered execution first, so that issue is a likely contributor but it carries none of these check ids.

=== Cause 1 of 2: an action never leaves InProgress while a stage transition on the pipeline is DISABLED, so the stage it is in never completes ===
AWS: Smithy (com.amazonaws.codepipeline#CodePipeline_20150709) models DisableStageTransition/EnableStageTransition over StageTransitionType Inbound|Outbound and publishes the hold through GetPipelineState's StageState$inboundTransitionState. A disabled INBOUND transition on stage N withholds the execution AT THAT BOUNDARY: every action of the preceding stages still runs to completion and ListActionExecutions/GetPipelineState report them Succeeded, the pipeline execution stays InProgress, and only entry into stage N is withheld. Disabling a transition never suspends work already running in an earlier stage.
Emulator: with Inbound into the second stage disabled and StartPipelineExecution issued, the FIRST stage's S3 Source action is created and then never progresses. ListActionExecutions reports it with status 'InProgress' and startTime == lastUpdateTime for the whole 30 s poll, so the check's wait for 'Source Succeeded' never resolves. Hypothesis (neither the model nor the recording states the mechanism): the planner consults the downstream transition hold and stops the walk before materialising the in-flight action of the current stage, leaving it claimed/InProgress for ever instead of finishing it and parking the execution at the boundary.
Why: a client that uses DisableStageTransition — the documented way to gate a deploy — hangs the whole pipeline instead of gating one boundary, and the gate itself becomes unobservable: the withhold cannot be distinguished from a dead execution, EnableStageTransition has nothing to release, and no artifact is ever handed to the next stage.
Fix: the execution planner/driver in the codepipeline crate's execution plane — the step walk that decides which action's work is due, and the point at which it applies a transition hold (it must apply the hold only to ENTERING the held stage, after the preceding stage's actions have been run to a terminal status).
Traces: codepipeline.e2e-pipeline-create-execute-approve-observe-teardown (concrete, non-timeout evidence), codepipeline.list-action-executions-order-matches-stage-sequence (same disable-then-start settling helper), codepipeline.disable-enable-stage-transition-persists-state, codepipeline.disable-stage-transition-holds-execution, codepipeline.disabled-transition-withhold-is-bounded-by-a-concurrent-enabled-twin, codepipeline.stopping-an-execution-leaves-no-deploy-artifact-and-a-restop-is-rejected.

=== Cause 2 of 2: an execution never reaches the next state 18 further checks wait for, so each exhausts its poll budget ===
AWS: Smithy models StartPipelineExecution -> pipelineExecutionId and the service then DRIVES the execution: actions run in runOrder, parallel actions of one run order each deliver their own artifact, artifacts are written to and read from the artifactStore (including a CMK-encrypted store, where losing the key fails the execution), a manual-approval action reaches InProgress and issues the token PutApprovalResult consumes, a custom-action job is claimed and completed through AcknowledgeJob/PutJobSuccessResult/PutJobFailureResult, StopPipelineExecution moves the execution to Stopping/Stopped and a second stop is refused, a missing source object fails the execution, condition rules produce RuleExecutionDetails for ListRuleExecutions, and the execution reaches a terminal PipelineExecutionStatus that GetPipelineExecution/ListPipelineExecutions/ListActionExecutions report.
Emulator: each of the 18 checks below stops at the suite's 60 s per-check ceiling ('Error: Check timed out after 60.0s') while polling for that next state — a terminal execution status, an approval token, a job in the state the Put*Result rejection classes need, an ordered action/rule-execution history, a delivered or withheld artifact, or a CMK failure. Against an emulator none of these waits should take seconds. What DOES work narrows the gap rather than closing it: the sibling issue from this sweep shows an S3 Source action succeeding and an S3 Deploy action running to a Failed verdict in a CFN-deployed two-stage pipeline, and codepipeline.poll-for-jobs-lease-expires-and-job-becomes-available-again shows PollForJobs dispatching a job with a nonce — so the stall is in advancing PAST those points (second stage, approval, job completion, stop, and the per-execution reporting those checks read), not in starting an execution at all.
Why: every CodePipeline workflow stays unusable for a client: starting a pipeline and waiting for it hangs, and because the state the rejection paths act on is never reached, even the negative classes (PipelineExecutionNotStoppableException, InvalidJobStateException, DuplicatedStopRequestException, condition-override conflicts) are unreachable. CloudFormation-deployed pipelines inherit all of it.
Fix: the codepipeline crate's execution plane (the driver behind StartPipelineExecution and the state it publishes to GetPipelineState/GetPipelineExecution/ListPipelineExecutions/ListActionExecutions/ListRuleExecutions), the approval-token and job lifecycles the PutApprovalResult/Put*Result handlers read, and the stop path.
Traces: codepipeline.approval-rejection-records-the-reviewer-and-withholds-the-downstream-stage, codepipeline.artifact-store-cmk-encrypts-the-delivered-artifact-object, codepipeline.disabling-the-artifact-store-cmk-fails-the-execution-and-reenabling-restores-it, codepipeline.deploy-codepipeline-cfn-execution-behaves, codepipeline.deploy-pipeline-cloudformation-executes-on-start, codepipeline.duplicate-stop-request-rejected, codepipeline.e2e-pipeline-create-run-approve-complete-teardown, codepipeline.job-claim-nonce-single-use-after-acknowledgement-rejected, codepipeline.job-output-variables-precision-preserved, codepipeline.list-rule-executions-matches-condition-evaluation-order, codepipeline.missing-source-object-fails-the-execution-and-no-artifact-is-deployed, codepipeline.override-stage-condition-conflict-rejected, codepipeline.parallel-actions-in-one-stage-both-deliver-their-own-artifact, codepipeline.put-job-success-invalid-job-state-rejected, codepipeline.put-job-success-result-wrong-job-state-rejected, codepipeline.run-order-two-starts-only-after-run-order-one-finishes, codepipeline.source-output-variable-resolves-into-the-downstream-object-key, codepipeline.webhook-url-rejects-a-wrong-hmac-signature-and-starts-no-execution.
