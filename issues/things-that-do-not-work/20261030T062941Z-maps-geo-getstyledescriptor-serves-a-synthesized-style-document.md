# maps.geo GetStyleDescriptor serves a synthesized style document instead of the published basemap style release

> _Note: this issue was identified against the code base at commit `cb1771c3c2a1df51218899fe99979bb9da68f0b3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetStyleDescriptor

## Description
GetStyleDescriptor answers 200 with a style document the emulator builds itself rather than the published Amazon Location basemap style release for the requested Style/ColorScheme/Variant. The HTTP envelope is right (200, blob payload) but the body's layer list, layer filter/layout/paint contents, the style id and the metadata block all diverge from the recorded descriptor. THIS ISSUE BUNDLES 3 NET-NEW CAUSES; all three must be closed before submitting. The already-open issue 20261029T182815Z-maps-geo-serves-synthetic-glyph-and-sprite-assets.md covers GetGlyphs/GetSprites asset bytes and the sprite-sheet JSON only — it carries no GetStyleDescriptor replay key and does not cover any cause below.

Cause 1 of 3: Standard/Dark descriptor with the rich option set (terrain/traffic/poi/travel-mode query options) — fixture geo-maps-style-descriptor-rich-options, step task#1.
AWS: recorded behavior only. Smithy: GetStyleDescriptor GET /v2/styles/{Style}/descriptor, output is an opaque Blob @httpPayload with Content-Type/Cache-Control/ETag headers and no modelled errors, so the body contract is entirely the recorded MapLibre style document. The recording shows (a) metadata."aws:virtual-variant"[0].variants carrying one entry per virtual variant the requested options enable (the recorded entry is an object with an `id` member, e.g. the terrain variant id), and (b) every vector layer carrying the published layer definition: an `all`-rooted filter whose clauses are full expressions (`match` over `['get', <attribute>]` with its value list and true/false arms, `has`, a negated `has`, a `case` expression, and an `['==', ['geometry-type'], <type>]` clause), a `layout` object where the published layer has one (e.g. a line layer's `{"line-join": "round"}`), and `paint` values whose colors and whose complete zoom-interpolation stop list match the release.
Emulator: metadata."aws:virtual-variant"[0].variants is empty, so variants[0] is absent. Every layer's filter is collapsed to a short fixed-arity form rooted at a comparison operator instead of `all` (e.g. for layer rail_tunnel the first element is '==' where the release has 'all', element[1][0] is 'get' where the release has 'match', element[1][1] is the bare string 'role' where the release has the expression ['get','kind'], and clauses 2..5 of the release filter are simply missing). Layer `layout` objects are dropped entirely. Paint values are invented: rail_tunnel line-color is served as hsl(213, 7%, 25%) where the release serves hsl(196, 10%, 18%), and its line-width interpolation list is both wrong at existing stops and truncated (stop values at indexes 7 and 8 absent). The same class of divergence repeats across the whole layer list (hundreds of paths, including admin_*, airport_*, bridge_*, rail_* layers).
Why: a MapLibre/MapBox GL client renders from this document. Collapsed filters select the wrong features per layer, missing `layout` drops join/placement behavior, and wrong paint colors plus truncated interpolation stops give wrong colors and line widths at every zoom — so the rendered map does not match AWS, and a client that reads metadata."aws:virtual-variant" to discover enabled variants (3-D terrain and similar) finds none and silently disables the feature it requested.
Fix: the GetStyleDescriptor handler's style-document source in the geo-maps service crate — it must serve the published style release document for the requested Style/ColorScheme/Variant (and apply the request's option query parameters to it) instead of synthesizing layers, and must populate metadata."aws:virtual-variant"[].variants for the variants the request enables.
Traces: geo-maps-style-descriptor-rich-options#task#1.

Cause 2 of 3: the same descriptor surface for a different style/color-scheme pair (Monochrome/Light) — fixture geo-maps-style-descriptor-rich-options, step task#2.
AWS: recorded behavior only; same opaque-Blob contract as above. The recording shows that each Style+ColorScheme pair has its own published palette, so a layer's paint colors differ per pair while the layer structure stays that of the release.
Emulator: identical structural faults (missing metadata virtual-variant entry, '=='-rooted collapsed filters in place of the release's `all`/`match`/`has`/`case`/geometry-type clauses, dropped `layout` objects, truncated line-width stop lists) and a per-pair palette that is also wrong: for Monochrome/Light the rail_tunnel line-color is served as hsl(228, 0%, 100%) where the release serves hsl(228, 0%, 91%). This is not a repeat of cause 1's values: it shows the colour table is wrong for every color scheme, not only for Dark, so fixing one palette does not fix the other.
Why: clients selecting any non-default style or color scheme get a map whose palette and feature selection are both wrong, and the divergence cannot be dismissed as one style's data being stale.
Fix: same component as cause 1 — the per-Style/ColorScheme/Variant style-document source behind GetStyleDescriptor, keyed on all three path/query inputs.
Traces: geo-maps-style-descriptor-rich-options#task#2.

Cause 3 of 3: the descriptor's style identity members report the base style version and drop the release's pre-release qualifier — fixture geo-maps-vector-basemap-style-workflow, step task#1 (Standard/Light).
AWS: recorded behavior only. The recorded descriptor's `id` is the style release identifier built as <style>-<coverage>-<color-scheme>-<variant>-<full release version>, where the full release version includes any pre-release qualifier the published release carries (the recorded value ends in a '-beta.N' qualifier after the three-part version). metadata.version carries that same full release version.
Emulator: `id` is minted from the three-part version only, dropping the pre-release qualifier (recorded 'standard-global-light-default-4.1.0-beta.1' vs served 'standard-global-light-default-4.1.0'), and metadata.version likewise reports the bare three-part version. The same step also omits the metadata."aws:virtual-variant"[0].variants entry described in cause 1.
Why: the descriptor `id`/metadata.version is how a client pins, caches and diffs a style release. Reporting a different identifier than the release it claims to serve makes cache keys collide across releases and makes version-pinning checks pass against the wrong document.
Fix: the GetStyleDescriptor response projection in the geo-maps service crate — carry the style release's full version string (including any pre-release qualifier) into both the descriptor `id` and metadata.version instead of reconstructing a three-part version.
Traces: geo-maps-vector-basemap-style-workflow#task#1.

Not filed as causes: the descriptor's `sprite` member resolves to the emulator's own host:port (and the replay records it as a shaped, non-asserted value) — the host and port are per-run values and its path matches the modelled GetSprites URI /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName}, so it is not treated as a divergence here.
