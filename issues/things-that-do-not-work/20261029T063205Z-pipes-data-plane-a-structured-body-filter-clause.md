Cause 1 of 2: a FilterCriteria pattern whose `body` clause is STRUCTURED never matches an SQS message whose body is valid JSON, so the pipe drops — and consumes — the very record it must deliver.
AWS: Smithy (com.amazonaws.pipes): CreatePipe takes SourceParameters -> PipeSourceParameters.FilterCriteria -> FilterCriteria{Filters: FilterList}, each Filter.Pattern an EventPattern, documented as "The collection of event patterns used to filter events" and pointing at EventBridge event patterns; CreatePipe is POST /v1/pipes/{Name} and models ValidationException (400). Recorded behavior for the data plane (the model describes only the control plane): EventBridge Pipes builds the SQS record envelope (messageId/receiptHandle/body/attributes/messageAttributes/md5OfBody/eventSource/eventSourceARN/awsRegion) and, when the message body is valid JSON, matches `body` as the PARSED JSON document — which is what makes a pattern such as {"body": {"type": ["match-me"]}} meaningful at all. A record that satisfies the pattern is delivered to the target exactly once; a record that does not is dropped (and consumed). Because the body was parsed for the match, Pipes re-emits nested-object paths unquoted, so a TargetParameters.InputTemplate of "<$.body.id>" renders the scalar `id` field of the body.
Emulator: the pipe admits nothing. data_plane.rs `admitted()` (line ~1410) hands the envelope straight to ::service_common::event_pattern::matches_within, and `queue_record_envelope()` (line ~1456) sets "body": message.body — the RAW string. A string value can never satisfy an object-shaped clause, so the JSON record that must match is not admitted; worse, move_one_batch then treats the emptied batch as moved ("let batch = admitted(...); if batch.is_empty() { finish_batch(...); return Batch::Moved }", lines ~667-671), so the record is DELETED from the source as a non-match. The check is cut at the harness cap ("Check timed out after 60.0s") waiting for its positive control at the target. Hypothesis, not establishable from this run because no record ever got through the body clause: once the body is parsed, the target InputTemplate "<$.body.id>" must resolve against the parsed document and render the bare id — with the body held as a raw string that path cannot resolve at all, so the same missing parse is expected to fail the delivered payload as well.
Why: the normal way to use Pipes — JSON messages on a queue, filtered on a field of the body — delivers NOTHING, and the records are destroyed on the way: the source is drained, the pipe reports RUNNING, DescribePipe echoes the FilterCriteria, and the matching message is gone without ever reaching the target. A client cannot tell this from a correct filter over an empty source, and it has no retry: the message was consumed.
Fix: the filter stage of the pipes data plane in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs — the value matched at `body` must be the parsed JSON document when the body is valid JSON, while the payload handed to the enrichment and the target keeps the body as sent; and the target InputTemplate renderer must resolve `$.body.<member>` against that parsed document. If the shared matcher lacks the content-based operators, extend ::service_common::event_pattern too.
Traces: pipes.pipe-filter-blocks-nonmatching-events (pattern {"body": {"type": ["match-me"]}}, TargetParameters.InputTemplate "<$.body.id>": the non-matching leg is satisfied vacuously because nothing is ever delivered, and the positive control with body {"type":"match-me","id":<uuid>} never arrives). The malformed-pattern leg of that same check — CreatePipe with Pattern "{not-valid-json" answering 400 ValidationException whose message is the JSON document {"ValidationErrorFields":[{"Name":"Pattern","Message":"Invalid Event Pattern. Reason: Unexpected character ('n' (code 110)): was expecting double-quote to start field name."}]} — did NOT fail in this run and is not part of this issue.

Cause 2 of 2: a pipe whose target delivery its execution role forbids never presents the in-flight / release / redelivery cycle an independent consumer of its SQS source must be able to observe.
AWS: recorded behavior only for the data plane. EventBridge Pipes receives the source message as its execution role and holds it for the queue's VisibilityTimeout while it attempts the target; an SQS receive is an atomic checkout, so for that span GetQueueAttributes on the source reports ApproximateNumberOfMessagesNotVisible >= 1 and no other ReceiveMessage can return the message. A delivery the role may not make leaves the message undeleted, so when the timeout lapses the message returns to the visible set and any consumer that then receives it reads ApproximateReceiveCount > 1 (Smithy, com.amazonaws.sqs: the ApproximateReceiveCount message system attribute is "the number of times a message has been received across all queues but not deleted"), while the target queue stays at ApproximateNumberOfMessages 0.
Emulator: the check never reaches that final assertion — it is cut at the harness cap ("Check timed out after 60.0s") inside the sequence of waits that observe the hide/release cycle on the source (first ApproximateNumberOfMessagesNotVisible >= 1 within its own 120 s budget, then a receive showing ApproximateReceiveCount > 1 within 90 s). Every call in the lead-up answers: CreateQueue with Attributes{VisibilityTimeout:"20"}, SendMessage, CreatePipe (DesiredState STOPPED), StartPipe and DescribePipe (CurrentState RUNNING) all succeed, and the refusal path itself is implemented (data_plane.rs asks execution_role::call_refusal(run.target.delivery_action(), target_arn) before the target call and returns Batch::Failed without calling finish_batch), so the message is not deleted. Hypothesis for the mechanism, which this run cannot settle between: (a) the poller's own cadence hides the cycle from any other consumer — POLL_INTERVAL is 100 ms and MAX_RETRY_BACKOFF 5 s (data_plane.rs:103-115), so the instant the visibility timeout lapses this poller re-claims the message and hides it again, leaving no window in which an independent ReceiveMessage can see it and read ApproximateReceiveCount > 1; or (b) the checkout is not observable at all, i.e. the batch the poller holds does not read as ApproximateNumberOfMessagesNotVisible >= 1 on the source for the queue's configured VisibilityTimeout. SQS's own accounting is in place (Queue::hand_over sets invisible_until and Queue::reported_attributes derives the three ApproximateNumberOfMessages* counters from it), which points at the pipes source stage rather than at sqs.
Why: a client cannot observe, or share, the source of a pipe. The one guarantee it relies on while a pipe is retrying a refused delivery — the message is checked out, exactly once, for the visibility timeout, and comes back with its receive count raised — is unobservable, so a dead-letter policy on the source, a monitoring probe on ApproximateNumberOfMessagesNotVisible, and any second consumer of that queue all behave differently against the emulator than against AWS, and a refused delivery cannot be distinguished from a pipe that is not consuming.
Fix: the SQS source stage of the pipes data plane in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs (`collect_batch`/`receive`, and the retry cadence in `poll` / `retry_backoff`): a polled batch must hold its messages in flight for the queue's configured VisibilityTimeout and the poller must not re-claim a released message so tightly that the release is unobservable to another consumer — a refused delivery is retried at a service-like interval, not at 100 ms.
Traces: pipes.sqs-source-visibility-timeout-enforced (source queue VisibilityTimeout=20, role granted sqs:ReceiveMessage/DeleteMessage/GetQueueAttributes on the source only, no sqs:SendMessage on the target; the message is sent while the pipe is STOPPED and StartPipe then starts it).
