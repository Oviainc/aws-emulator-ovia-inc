--- Cause 1 of 1: TerminateJobFlows does not refuse a termination-protected cluster; it returns success and silently drops the request ---
Failing check ids for this cause: emr.termination-protection-blocks-terminate-job-flows.

AWS: Smithy (services/service-com-amazonaws-emr-elasticmapreduce/smithy-model/com-amazonaws-emr-elasticmapreduce.json): TerminateJobFlows takes JobFlowIds (XmlStringList) @required and models exactly ONE error, InternalServerError (HTTP 500, server kind), so any client-side refusal of this operation travels on EMR's generic 400 client-error channel rather than a modelled shape. The protection contract itself is documented on the neighbouring operation and member: SetTerminationProtection 'locks a cluster (job flow) so the Amazon EC2 instances in the cluster cannot be terminated by user intervention, an API call, or in the event of a job-flow error', and 'to terminate a cluster that has been locked ... you must first unlock the job flow by a subsequent call to SetTerminationProtection in which you set the value to false'; Cluster$TerminationProtected is 'Indicates whether Amazon EMR will lock the cluster to prevent the Amazon EC2 instances from being terminated by an API call or user intervention'. For the SHAPE of the answer this is recorded behavior only: the behavioral check pins real EMR's refusal as a 4xx carrying one of the two error codes EMR uses across its cluster-validation surface — ValidationException or InvalidRequestException (the corpus shows both on the same surface, wire/emr/cluster-mutations-on-unknown-cluster.json) — with the message `Could not shut down one or more job flows since they are termination protected.` That message is ENTIRELY fixed text: it has no variable part at all — no job-flow id, no cluster name, no count, no timestamp is interpolated — which is why the sentence is plural and id-free. Hypothesis: EMR evaluates the protection flag for every named job flow before starting any shutdown and fails the whole request, so one protected id in a batch terminates none of them.
Emulator: the request is ACCEPTED. TerminateJobFlows answers HTTP 200 with an empty body for a protected cluster. The flag itself is stored and its EFFECT is honoured (SetTerminationProtection writes it, DescribeCluster reports TerminationProtected=true, the cluster stays WAITING and records no USER_REQUEST state-change reason), but the state-transition helper's refusal is discarded instead of being turned into an error, so NO status, NO error code and NO message ever reach the client. The emulator therefore has no wording for this error class at all — this is a missing refusal, not merely diverging wording.
Why: a client that asks to terminate a protected cluster is told the shutdown started. Cost-control and teardown code that terminates and moves on believes it reclaimed the fleet while a protected, per-second-billed EMR cluster plus its EC2 instances keep running; the documented unlock-then-terminate sequence is never forced on the caller, because the step that must fail reports success; and no negative test of termination protection can be graded, since the only observable difference from a real terminate is the absence of the state change.
Fix: the TerminateJobFlows handler and its validation in the EMR crate. The handler already resolves every named id in a pre-pass before mutating anything, then calls the cluster record's begin-termination helper in a second pass and ignores the boolean that helper returns; the helper already decides the protected case. Decide protection in the SAME pre-pass that resolves the ids and return the refusal on EMR's 400 client-error channel with the constant sentence above, so a request naming one protected cluster terminates none of the clusters it names. Keep the existing idempotent 200 no-op for a cluster that is already TERMINATING or terminal — that is not protection and must stay a success. Related open issues that do NOT cover this path: 20261031T093431Z-elasticmapreduce-emr-setterminationprotection-appends-the-job-flow-id-to.md concerns SetTerminationProtection's unknown-job-flow message, and 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md concerns step execution and cluster self-termination.
