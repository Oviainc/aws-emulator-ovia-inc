# schemas ListSchemas serves a synthetic AWS-managed schema catalog: wrong schema set and wrong result ordering

> _Note: this issue was identified against the code base at commit `b27510b4d97b7d3408c23fe8ccf3618e6d5ed1db`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListSchemas

## Description
EventBridge Schemas' ListSchemas over the AWS-managed registry (`aws.events`/discoverer-published `aws.*` schemas) returns a catalog that is not the one AWS serves: the page members are different SchemaNames, and where the same name families are present they come back in a different order. 51 of the 55 replayed divergence clusters are this one operation, which is what drives the corpus score down to 19%.

This bundle has TWO causes. Both must be closed before submitting.

Cause 1 of 2: the seeded AWS-managed schema set is wrong (missing names AWS publishes, extra names it does not).
- AWS: recorded behavior only. Smithy (schemas) models ListSchemas as GET /v1/registries/name/{RegistryName}/schemas, output Schemas:__listOfSchemaSummary, paginated {inputToken NextToken, outputToken NextToken, items Schemas, pageSize Limit}; it says nothing about which schemas the AWS-managed registry contains, so the recording is the only source. The recording enumerates a concrete per-event-source catalog: e.g. `aws.access-analyzer` exposes exactly AccessAnalyzerFinding and UnusedAccessFindingforIAMentities; `aws.acm-pca` exposes ACMPrivateCAAuditReportGeneration, ACMPrivateCACRLGeneration, ACMPrivateCACertificateIssuance, ACMPrivateCACertificateRevocation, ACMPrivateCACreation alongside the generic CloudTrail schemas; `aws.cleanrooms` and `aws.deadline` expose full event families (AnalysisTemplateCreated/Deleted/Updated, CollaborationChangeRequest*, BudgetThresholdReached, FleetSizeRecommendationChange, JobLifecycleStatusChange, JobRunStatusChange, StepLifecycleStatusChange, StepRunStatusChange, ...); the `aws.events` registry exposes ConnectionAuthorized, ConnectionCreationStarted, ConnectionDeauthorized, ConnectionDeletionStarted, ConnectionFailedConnectivity, ConnectionUpdateStarted and ScheduledJson. All responses are status 200.
- Emulator: status 200 (so this is a body-fidelity gap, not a status gap) but a different set. Whole event-source families are absent — for schemas-catalog-list-schemas task#39 every expected `aws.cleanrooms@*` entry reports `got None`, and for task#52 every expected `aws.deadline@*` entry reports `got None`; the same for the `aws.events@Connection*` and `aws.events@ScheduledJson` entries in schemas-export-aws-managed-schema task#1. Conversely the emulator manufactures a uniform six-schema CloudTrail block (`@AWSAPICallviaCloudTrail`, `@AWSConsoleActionviaCloudTrail`, `@AWSConsoleSignInviaCloudTrail`, `@AWSInsightviaCloudTrail`, `@AWSNetworkActivityEventviaCloudTrail`, `@AWSServiceEventviaCloudTrail`) for event sources where the recording does not list them (task#3: the expected page is aws.access-analyzer@AccessAnalyzerFinding / @UnusedAccessFindingforIAMentities / aws.access-insights@..., while the emulator returns six aws.access-analyzer@AWS*viaCloudTrail rows instead). Because the member set differs, every page boundary shifts and the divergence repeats across the whole paginated walk.
- Why: the AWS-managed registry is a discovery surface. A client that lists it to find the schema for an event type it must bind to (CloudFormation/CDK codegen, `aws schemas list-schemas`, SDK code bindings, an integration test that asserts a schema exists before DescribeSchema/ExportSchema) either cannot find a schema that exists on AWS (aws.cleanrooms@*, aws.deadline@*, aws.events@ConnectionDeauthorized) or binds to one that does not (aws.access-analyzer@AWSInsightviaCloudTrail), and a paging client gets pages whose contents it cannot reproduce against AWS.
- Fix: the schemas service's AWS-managed registry seed/state — the fixture data that populates the `aws.*` SchemaSummary catalog ListSchemas reads — not the serializer: the envelope, status and SchemaSummary shape (SchemaName/VersionCount/tags) already match. Do not derive the catalog from a per-service template; it must be the recorded per-event-source set.
- Note: the clusters also report LastModified differences (recording shows 2026-07-08T18:xx:xxZ, emulator shows assorted 2019-2025 values). That is a recording timestamp, not a requirement, and is NOT part of this issue.
- Traces: schemas-catalog-list-schemas#task#1 (representative, aws.a4b page), plus #task#3, #task#39, #task#52 (whole families absent), #task#2, #task#4, #task#5, #task#6, #task#10, #task#14, #task#21, #task#31, #task#33, #task#38, #task#40, #task#42, #task#50, #task#56, and schemas-export-aws-managed-schema#task#1.

Cause 2 of 2: ListSchemas orders results by a different collation than AWS, so pages are composed of different items even where both sides hold the same names.
- AWS: recorded behavior only (the model states no sort order). The recording's ordering is not a raw byte sort of SchemaName: it places `aws.application-autoscaling@ApplicationAutoScalingScalingActivityStateChange` BEFORE `aws.application-autoscaling@AWSAPICallviaCloudTrail` (case-insensitive: "applicationautoscaling..." < "awsapicall..."), and it places `aws.autoscaling@AWSAPICallViaCloudTrail` BEFORE `aws.autoscaling-plans@AWSAPICallviaCloudTrail` (a raw byte sort would put '-' (0x2D) ahead of '@' (0x40) and emit autoscaling-plans first). Status 200.
- Emulator: status 200, ordered by raw byte comparison of SchemaName. task#22 returns aws.application-autoscaling@AWSAPICallviaCloudTrail at $.Schemas[0] where the recording has @ApplicationAutoScalingScalingActivityStateChange; task#32 returns aws.autoscaling-plans@AWSAPICallviaCloudTrail at $.Schemas[0] where the recording has aws.autoscaling@AWSAPICallViaCloudTrail. The uppercase/lowercase pair `aws.autoscaling@AWSAPICallViaCloudTrail` and `aws.autoscaling@AWSAPICallviaCloudTrail` are also adjacent in the recording, which a byte sort cannot produce.
- Why: ListSchemas is paginated with Limit/NextToken, so the sort order decides page membership. A client that pages the registry, or that asserts the first N schemas, gets items in an order it cannot reproduce against AWS, and a resumed walk with a NextToken skips or repeats schemas relative to AWS.
- Fix: the ListSchemas handler's ordering/pagination step in the schemas service — sort SchemaName with the recording's collation (case-insensitive, with '@' ordering ahead of '-') before applying Limit/NextToken, rather than comparing the raw strings.
- Traces: schemas-catalog-list-schemas#task#22 (representative for this cause), schemas-catalog-list-schemas#task#32.

Not covered by any existing issue: the only open schemas issue, 20261023T142626Z-schemas-empty-result-responses-use-the-wrong-status.md, is about empty-result status codes and Content-Length on DeleteResourcePolicy/DeleteSchema and carries neither of these replay keys (the two clusters it owns were skipped here).
