# geo-routes route synthesis ignores the road network: wrong metrics, geometry and snapped positions

> _Note: this issue was identified against the code base at commit `4988eaf067dbbfdfac9330bbeed709d39fc37f35`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CalculateRoutes

## Description
The geo-routes emulator answers CalculateRoutes, OptimizeWaypoints and SnapToRoads with HTTP 200 and a structurally valid body, but every quantitative field in that body is generated by a placeholder computation instead of being derived from the road network the recordings were captured against. Positions are emitted at reduced precision rather than snapped to a road, waypoint sequencing is not optimized, travel metrics are synthesized from straight-line/heuristic math, and encoded geometry is not the road polyline. This bundle has FIVE causes; all five must be closed.

Cause 1 of 5 - CalculateRoutes: leg places are not snapped and the second major-road label is the wrong label kind (fixture geo-routes-calculate-routes-truck-travel-mode-options-wiring-success, step task#1).
AWS: Smithy georoutes#CalculateRoutes -> CalculateRoutesResponse.Routes (required, RouteList); RouteVehicleLegDetails.Departure/Arrival carry a place whose OriginalPosition is the position as supplied in the request and whose Position is the road-snapped position, both `Position` lists of length 2 (full geodetic precision, 7 decimal places in the recordings); Route.MajorRoadLabels is a list of RouteMajorRoadLabel, a union-like structure with EITHER RoadName (LocalizedString) OR RouteNumber (RouteNumber) - "Important labels including names and route numbers that differentiate the current route from the alternatives presented". The recording shows the second label as a RouteNumber (a signed highway designation, e.g. a state route) and the places' Position values differing from OriginalPosition because the request coordinates were snapped onto the carriageway.
Emulator: OriginalPosition is the request coordinate ROUNDED to 4 decimal places rather than echoed verbatim; Position is set equal to that rounded OriginalPosition (no snapping is performed at all, so the departure/arrival place sits off the road); and MajorRoadLabels[1] is a RoadName whose Value is a generated street-name string with a numeric suffix, in language tag "en-us", where the recording has a RouteNumber label with Language "en".
Why: a client that renders a route draws the first/last leg endpoints off the road geometry, and round-tripping OriginalPosition back into a follow-up request silently moves the waypoint by up to ~10 m per coordinate. A client that labels alternatives by RouteNumber finds no route number on any route and cannot distinguish alternatives, and a client keyed on label language sees "en-us" where AWS sends "en".
Fix: the CalculateRoutes handler's response synthesis - echo the request Position verbatim (no rounding) into OriginalPosition, snap Position onto the road graph, and select MajorRoadLabels entries by label kind (RouteNumber for numbered roads) instead of always emitting a generated RoadName.

Cause 2 of 5 - OptimizeWaypoints: the waypoint sequence is not optimized, so Connections are emitted in request order (fixture geo-routes-optimize-waypoints-basic-success, step task#1).
AWS: Smithy georoutes#OptimizeWaypoints -> OptimizeWaypointsResponse.Connections (required, WaypointOptimizationConnectionList); each WaypointOptimizationConnection has required From and To (WaypointId, length 1..100, pattern ^[^,;!]+$) which "contains the ID of the starting waypoint in this connection" / "the ID of the ending waypoint". The operation's purpose is to resequence waypoints, so Connections follow the OPTIMIZED order, not the submitted order. The recording's first connection runs to the waypoint the optimizer visits first, which is not the first waypoint in the request array.
Emulator: Connections preserve the order the waypoints appear in the request: connection[0].To and connection[1].From/To carry the request-order waypoint ids, so the two legs are transposed relative to the optimized sequence the recording shows.
Why: the entire value of OptimizeWaypoints is the ordering; a dispatch client reading Connections (or OptimizedWaypoints) drives the waypoints in submission order and the "optimized" plan is indistinguishable from no optimization.
Fix: the OptimizeWaypoints handler - run the sequencing objective over the waypoint set and emit Connections (and OptimizedWaypoints) in the resulting order.

Cause 3 of 5 - OptimizeWaypoints: Distance/TravelDuration/Duration/TimeBreakdown.TravelDuration are synthesized, not road-network values (fixture geo-routes-optimize-waypoints-basic-success, step task#1).
AWS: Smithy WaypointOptimizationConnection.Distance (DistanceMeters, long, required, range 0..4294967295) and .TravelDuration (DurationSeconds, long, required, same range); OptimizeWaypointsResponse.Distance and .Duration are required totals and WaypointOptimizationTimeBreakdown.TravelDuration is the travelling share of Duration. The recorded values are road-network distances with a travel duration consistent with urban road speeds, and the response totals equal the sum over Connections.
Emulator: per-connection Distance is close to but not the road distance (it tracks a straight-line/heuristic estimate), and TravelDuration is roughly a third of the recorded value - i.e. the implied speed is far above any street speed. The response-level Duration and TimeBreakdown.TravelDuration inherit the same understatement.
Why: an ETA-driven client (delivery windows, driver shift planning) is told a multi-stop tour takes a fraction of its real time, so every downstream scheduling decision is wrong even though the call succeeded.
Fix: the OptimizeWaypoints handler's metric computation - derive Distance/TravelDuration per connection from the same road-graph traversal CalculateRoutes uses and recompute Duration/TimeBreakdown as the sum of the connection values.

Cause 4 of 5 - OptimizeWaypoints, single-connection case: the same metric defect with no ordering component (fixture geo-routes-optimize-waypoints-origin-only-rejected, step task#2).
AWS: as Cause 3 - Connections[0].Distance/TravelDuration and the response Distance/Duration/TimeBreakdown.TravelDuration are road-network values and the totals equal the single connection's values.
Emulator: with one connection the ids are correct but Distance is off by tens of metres and TravelDuration (hence Duration and TimeBreakdown.TravelDuration) is understated by roughly a factor of 2.5, confirming the metrics come from a generated estimate rather than the road graph and that the defect is independent of the sequencing defect in Cause 2.
Why: even the degenerate one-leg tour returns an unusable duration, so a client cannot trust OptimizeWaypoints metrics in any shape.
Fix: the OptimizeWaypoints handler's metric computation (same component as Cause 3); this trace is the ordering-free regression case for it.

Cause 5 of 5 - SnapToRoads: trace points are not snapped, Confidence is random, and SnappedGeometry.Polyline is not the road polyline (fixture geo-routes-snap-to-roads-basic-success, step task#1; also fixture geo-routes-snap-to-roads-invalid-coordinate-rejected, step task#3).
AWS: Smithy georoutes#SnapToRoads -> SnapToRoadsResponse.SnappedTracePoints (required) of RoadSnapSnappedTracePoint, whose SnappedPosition (required, Position len 2) is "Snapped position of the TracePoint provided within the request, at the same index" and whose Confidence (required, SensitiveDouble, range min 0 max 1) is "Confidence value for the correctness of this point match"; SnappedGeometry.Polyline (Polyline, length min 1) is "an ordered list of positions used to plot a route on a map in a lossy compression format" - the interpolated geometry along the snapped road, mutually exclusive with LineString. In the recordings SnappedPosition is a full-precision point on the carriageway that differs from the submitted trace point, Confidence is a match quality that varies with how far the point lay from the road (including the extreme values 1 for an on-road point and values near 0 for a far one), and the polyline encodes the whole interpolated road path.
Emulator: SnappedPosition is the submitted trace point rounded to 4 decimals - no lateral snap onto the road is applied; Confidence is a pseudo-random double in the mid-range (full 17-digit precision) that bears no relation to the point's distance from the road, so a point AWS matches with confidence 1 and a point AWS matches with confidence 0.05 both come back around 0.4-0.6; and SnappedGeometry.Polyline is a much shorter encoded string - the request points re-encoded, not the interpolated road geometry (AWS's polyline for the same trace has many more vertices).
Why: SnapToRoads exists to move noisy GPS traces onto roads and to report how much to trust each match. A telematics client gets its own unsnapped (and truncated) coordinates back, so map-matching is a no-op; it cannot threshold on Confidence because the value is noise; and drawing SnappedGeometry.Polyline yields a straight-line sketch between trace points instead of the road path.
Fix: the SnapToRoads handler's snapping and geometry serialization - snap each trace point to the nearest road segment at full precision, derive Confidence from the match (and clamp to the modeled 0..1 range), and encode the interpolated road path into SnappedGeometry.Polyline.
