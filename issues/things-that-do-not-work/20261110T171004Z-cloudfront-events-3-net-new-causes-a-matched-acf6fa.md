# cloudfront__events: 3 net-new causes — a matched EventBridge rule delivers to no target (SQS, Lambda via target RoleArn, Step Functions StartExecution), so every CloudFront-invalidation eventing check runs to its cap

> _Note: this issue was identified against the code base at commit `0c065617979d1ee76fa77b423bd58183fc04c861`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents

## Description
Three net-new root causes in EventBridge rule-to-target delivery, grounded in five failing behavioural checks that no open issue carries the replay key for. Open issues describe neighbouring symptoms for OTHER checks and do not cover these: 20261102T091831Z-cloudfront-events-a-matched-rule-never-invokes-its.md, 20261024T182555Z-cloudfront-events-a-matched-eventbridge-rule-never-produces.md, 20261107T192835Z-cloudfront-events-3-net-new-causes-a-matched.md, 20261029T175823Z-cloudfront-events-13-more-cloudfront-eventbridge-checks-fail.md. All three causes must be closed before submitting.

Every one of the five checks accepts PutEvents (FailedEntryCount is 0, so entry ingestion itself is fine) and then waits, on its own bounded budget, for the effect of the matched rule. None of those effects ever appears, so each check is killed at the harness cap instead of reaching a verdict.

Cause 1 of 3: a matched rule never delivers the event to an SQS target.
AWS: recorded behavior only for the delivery itself; the API surface is modeled (eventbridge PutRule, PutTargets, PutEvents — PutEvents answers FailedEntryCount 0 with one EventId per accepted entry). The recording shows: a rule on the default bus with EventPattern {"source":["sim2real.cloudfront"],"detail-type":["CloudFront Distribution State Change"],"detail":{"state":["Deployed"]}}, State ENABLED, and a single SQS target whose queue policy allows Principal Service events.amazonaws.com to sqs:SendMessage with Condition ArnEquals aws:SourceArn = the rule ARN. PutEvents with two entries, one Detail having state 'InProgress' and one having state 'Deployed', results in EXACTLY ONE message on the queue: the event envelope for the Deployed entry (its detail is carried in the message body). The InProgress entry does not match detail.state=["Deployed"] and is silently dropped — no message, no error.
Emulator: no message is ever enqueued. The check's drain loop (ReceiveMessage with WaitTimeSeconds=5 on a 90 s budget) collects nothing, so the positive control ('the Deployed event was never delivered') can never be satisfied and the check is killed at the 60 s harness cap. Because nothing is delivered, the pattern-filtering claim is also unobservable — the absence of the InProgress message proves nothing while the matching message is absent too.
Why: a client that fans CloudFront state-change events out to a queue receives nothing; the whole event-driven path (invalidate on Deployed, alarm on failure) is silently inert, and a developer cannot tell a non-matching pattern from a broken bus, because both look like an empty queue.
Fix: the EventBridge rule-matching and target-dispatch path — after PutEvents matches a rule, dispatch to each configured target; for an SQS target that means a SendMessage of the full event envelope, gated on the queue's resource policy.
Traces: cloudfront__events.cloudfront-distribution-inprogress-event-filtered-by-pattern.

Cause 2 of 3: a matched rule never invokes a Lambda target through the target's RoleArn, so neither the delivery nor the role-trust gate can be observed.
AWS: recorded behavior only for the delivery; PutTargets' RoleArn member is modeled. The recording shows: PutTargets with Targets=[{Id, Arn: <function ARN>, RoleArn: <role>}]. When that role's trust policy allows sts:AssumeRole for Principal Service events.amazonaws.com and its inline policy allows lambda:InvokeFunction on the function, a matching PutEvents event causes EventBridge to assume the role and invoke the function asynchronously with the event envelope as payload (the function's own side effects — here an SQS SendMessage carrying detail.requestId — become observable). When the RoleArn's trust policy OMITS events.amazonaws.com, PutTargets still ACCEPTS the target, but EventBridge cannot assume the role, so the target is never invoked and the failure is silent to the caller (it surfaces only as a FailedInvocations metric); a sibling rule whose role does trust events.amazonaws.com delivers normally in the same account. Separately, when the invoked function's EXECUTION role lacks the CloudFront permission it calls with, the in-function CreateInvalidation call is refused with AccessDenied and the function reports that outcome.
Emulator: the Lambda target is never invoked at all, with or without a correctly-trusted RoleArn. Every one of these three checks re-fires its event on a bounded retry loop and then waits for the function's observable effect; none appears, so each is killed at the 60 s harness cap. The role-trust contrast is therefore vacuous (the correctly-trusted positive control is as silent as the untrusted negative), and the 'denied CloudFront permission' contrast never runs because the function never executes.
Why: a client wiring an EventBridge rule to a Lambda through a target execution role gets no invocation, so an IAM misconfiguration and a correct configuration are indistinguishable — the emulator reports success for a wiring that delivers nothing, and an authorization boundary AWS enforces (an untrusted RoleArn must not deliver) is enforced only by accident of total inertness.
Fix: the EventBridge target-dispatch path for Lambda targets — assume the target's RoleArn (honouring its trust policy, and refusing to deliver when the trust policy does not allow events.amazonaws.com), then invoke the function with the event envelope; and the Lambda invocation's own IAM context, so an in-function AWS call is authorized against the function's execution role.
Traces: cloudfront__events.eventbridge-role-without-events-trust-rejected, cloudfront__events.events-role-trust-policy-allows-assume-for-cloudfront-target, cloudfront__events.lambda-role-missing-cloudfront-permission-denied-invalidation.

Cause 3 of 3: a matched rule never starts a Step Functions execution through the target's RoleArn.
AWS: recorded behavior only for the delivery. The recording shows: a rule with a state-machine ARN as its target and a RoleArn. With a role whose trust policy allows sts:AssumeRole for Principal Service events.amazonaws.com and whose inline policy allows states:StartExecution on that state machine, a matching event starts an execution whose input carries the event (the check finds it by a marker in the execution input) and it reaches SUCCEEDED. With a RoleArn trusting only lambda.amazonaws.com, PutTargets is accepted but NO execution is ever started.
Emulator: no execution is started in either case. The negative half (a bounded 75 s absence check) passes vacuously and the positive control never produces an execution, so the check is killed at the 60 s harness cap.
Why: a client that drives a workflow from an event sees nothing start, and the distinction AWS draws between a correctly-trusted and an untrusted target role is unobservable — a broken role reads exactly like a working one.
Fix: the EventBridge target-dispatch path for Step Functions targets — assume the target's RoleArn and call StartExecution with the event as input, refusing to deliver when the role's trust policy does not allow events.amazonaws.com.
Traces: cloudfront__events.eventbridge-rule-role-arn-wrong-trust-execution-not-started.

## Evidence
All five checks report the same terminal symptom from the suite: 'Error: Check timed out after 60.0s' with verdict mismatch.

Cause 1 — cloudfront__events.cloudfront-distribution-inprogress-event-filtered-by-pattern:
Expected (check body): after PutEvents with FailedEntryCount == 0 for two entries, draining the target queue for up to 90 s yields a message whose body contains the Deployed entry's distributionId marker ('positive control failed: the Deployed event was never delivered') and NO message containing the InProgress marker.
Actual: the drain loop collects zero messages for the whole budget; the check is killed at the 60 s cap before any assertion is reached.

Cause 2 — cloudfront__events.events-role-trust-policy-allows-assume-for-cloudfront-target: PutTargets is accepted with Targets=[{Id:'invalidation-target', Arn:<fn arn>, RoleArn:<role trusting events.amazonaws.com>}]; the check then re-fires a fresh event id up to 4 times and waits for the function's SQS message carrying detail.requestId. No invocation and no message ever occur. The same silence is what cloudfront__events.eventbridge-role-without-events-trust-rejected and cloudfront__events.lambda-role-missing-cloudfront-permission-denied-invalidation hit, so their negative/positive contrast never resolves.

Cause 3 — cloudfront__events.eventbridge-rule-role-arn-wrong-trust-execution-not-started: PutTargets accepted with Arn=<state machine arn>, RoleArn=<role trusting only lambda.amazonaws.com>; the bounded 75 s absence check finds no execution (vacuously correct), and the positive control with a role trusting events.amazonaws.com also starts no execution, so the check never reaches 'execution must not start when the target RoleArn's trust policy omits events.amazonaws.com' as a meaningful verdict and is killed at the 60 s cap.
