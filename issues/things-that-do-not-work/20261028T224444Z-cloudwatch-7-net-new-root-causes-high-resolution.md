=== Cause 1 of 7: a high-resolution (Period=10) metric alarm never leaves INSUFFICIENT_DATA on published data ===
Failing check id: cloudwatch.alarm-evaluation-engine-state-machine-advances-only-from-published-data

AWS: Smithy (com.amazonaws.cloudwatch#GraniteServiceVersion20100801) models PutMetricAlarm.Period as target Period with @range min 1 — a sub-minute (high-resolution) period such as 10 is a legal value, not a special case — together with EvaluationPeriods (@range min 1), DatapointsToAlarm (@range min 1), Statistic (enum), Threshold (double), ComparisonOperator (enum) and TreatMissingData (@length 1..255); MetricAlarm.StateValue targets the StateValue enum, StateReason is @length max 1023 ('An explanation for the alarm state, in text format') and StateReasonData @length max 4000 ('An explanation for the alarm state, in JSON format'). The state-machine behavior itself is recorded behavior only: a new alarm reports StateValue INSUFFICIENT_DATA with StateReason exactly 'Unchecked: Initial alarm creation' (fixed text, no variable parts) and NO StateUpdate history item; published datapoints ALONE — no SetAlarmState — then drive it INSUFFICIENT_DATA -> OK -> ALARM -> OK, one 10-second bucket at a time. DescribeAlarmHistory records exactly three StateUpdate items whose HistorySummary is the template 'Alarm updated from ' + oldState + ' to ' + newState (the two state names are the variable parts), each HistoryData version '1.0', each item's oldState equal to the previous item's newState. In each decision StateReasonData.statistic echoes the alarm's Statistic, .period echoes Period, .threshold echoes Threshold, .recentDatapoints is exactly EvaluationPeriods values long, and .evaluatedDatapoints holds only the datapoints that justified the verdict, in the same order the StateReason's bracketed list names them.

Emulator: the alarm is created, but it never leaves INSUFFICIENT_DATA. The check republishes in-range datapoints into fresh 10-second buckets and polls DescribeAlarms for StateValue != 'INSUFFICIENT_DATA'; that predicate is never satisfied and the check is killed at the suite's 60 s harness cap ('Error: Check timed out after 60.0s'). Nothing downstream — the OK verdict, the ALARM verdict, the recovery OK, the three StateUpdate history items, the StateReason/StateReasonData shape — is ever produced for a sub-minute period.

Why: a client that configures high-resolution alarming (the documented 10/30-second alarm) gets an alarm that is permanently INSUFFICIENT_DATA. Anything gated on it — autoscaling, rollback, paging — never runs, and because the alarm reports no state it cannot even be distinguished from a metric that has no data.

Fix: the CloudWatch alarm evaluation engine in the cloudwatch service crate (the evaluator that buckets the stored series by the alarm's Period and advances StateValue), plus the StateReason/StateReasonData rendering it drives on the DescribeAlarms and DescribeAlarmHistory read paths. The fixed issue 20261025T100455Z-cloudwatch-alarm-evaluator-a-period-10-high-resolution.md claimed a fix in this exact area (a Period=10 high-resolution alarm's decision window) — this check shows a sub-minute alarm still never reaches any evaluated state, so the evaluation tick/bucketing for sub-minute periods needs re-tracing rather than treating that issue as settled.

=== Cause 2 of 7: a SetAlarmState-forced ALARM is never reclaimed by the evaluator, because the alarm never reaches an evaluated OK from published data ===
Failing check id: cloudwatch.alarm-forced-state-is-transient-real-evaluation-reclaims-it

AWS: Smithy models SetAlarmState with required AlarmName (@length 1..255), required StateValue (StateValue enum), required StateReason (@length 0..1023), optional StateReasonData (@length 0..4000), and errors InvalidFormatFault (httpError 400, awsQueryError InvalidFormat) and ResourceNotFound (httpError 404). Beyond that, recorded behavior only: SetAlarmState is a TRANSIENT override. The recording shows (a) a Period=60, EvaluationPeriods=1, DatapointsToAlarm=1, Maximum/GreaterThanThreshold alarm over a published in-band datapoint first reaches an EVALUATED OK whose StateReason is prefixed 'Threshold Crossed' and names '1 out of the last 1 datapoints'; (b) SetAlarmState(ALARM) takes effect immediately and stores the client's StateReason verbatim; (c) with no further control-plane call, the evaluator RECLAIMS the alarm back to OK (measured on AWS at ~30 s) and REWRITES StateReason to its own 'Threshold Crossed: ...' template, advancing StateUpdatedTimestamp; (d) the reclaiming StateUpdate's stateReasonData.recentDatapoints contains the published value, .threshold echoes the alarm's Threshold, and .evaluatedDatapoints holds exactly the one datapoint; (e) the FORCED transition's history item carries the client's stateReason and NO stateReasonData member at all, because no evaluation produced it; (f) TreatMissingData='ignore' over a never-written metric KEEPS the forced state. In the StateReason template the fixed text is 'Threshold Crossed: ' / ' out of the last ' / ' datapoints [' / '] was not greater than the threshold (' / ') (minimum ' / ' datapoint for ' / ' transition).'; the counts, values, timestamps, threshold and direction are taken from the request and from the alarm's stored state.

Emulator: the check never gets as far as the SetAlarmState override. Its first step — poll DescribeAlarms until the alarm reaches StateValue 'OK' from the published in-band datapoint, republishing each pass (own budget 300 s, 15 s interval) — is never satisfied, and the check is killed at the 60 s harness cap. So the evaluated OK baseline, the forced override, the reclaim, the rewritten StateReason, the history-item shape and the 'ignore' hold arm are all unreachable.

Why: SetAlarmState is permanent here instead of transient. A client that forces a state for a drill, a test or a manual mute sees the alarm stay forced forever, so the real signal is masked indefinitely; and a client that waits for an evaluated OK baseline before forcing anything hangs. The forced-vs-evaluated distinction (whose only machine-readable marker is the presence of stateReasonData on the history item) cannot be observed at all.

Fix: the alarm evaluation engine must keep evaluating an alarm whose state was set by SetAlarmState and overwrite it with the next evaluated verdict (except under TreatMissingData='ignore'), and the SetAlarmState handler must record a history item with the caller's reason and no stateReasonData. The fixed issue 20261025T084321Z-cloudwatch-setalarmstate-s-forced-alarm-state-is-never-reclaimed.md claimed exactly this behavior; its symptom is back in the same shape (the alarm never reaches the evaluated baseline the reclaim is measured from), so that fix needs re-tracing.

=== Cause 3 of 7: StateReasonData.recentDatapoints is shorter than the alarm's EvaluationPeriods, so the M-of-N decision window is not the configured width ===
Failing check id: cloudwatch.alarm-m-of-n-holds-at-m-minus-one-and-fires-at-m

AWS: Smithy — PutMetricAlarm.EvaluationPeriods (@range min 1) is 'The number of periods over which data is compared to the specified threshold'; DatapointsToAlarm (@range min 1) is 'The number of data points that must be breaching to trigger the alarm'; MetricAlarm.StateReasonData is @length max 4000. The M-of-N predicate and the StateReasonData shape are recorded behavior only: for an alarm with EvaluationPeriods=N and DatapointsToAlarm=M over a hole-free window, StateReasonData.recentDatapoints is the FULL N-period window of per-period aggregated values (oldest first) regardless of the verdict, while .evaluatedDatapoints is NOT the window but exactly the datapoints that justified the verdict (N-M+1 non-breaching ones for ALARM->OK, M breaching ones for OK->ALARM). The StateReason names the same two integers: fixed text 'Threshold Crossed: ' / ' out of the last ' / ' datapoints [' / '] were not greater than the threshold (' / ') (minimum ' / ' datapoints for ' / ' transition).', with the counted datapoints, the window length N, the values and timestamps, the threshold, the direction and the direction's minimum (M for OK->ALARM, N-M+1 for ALARM->OK) all taken from the request and the stored series. The recorded run's 5/3 pair and its 1.0/99.0/10.0 values are that recording's filling of the template, not the requirement.

Emulator: with EvaluationPeriods=5, DatapointsToAlarm=3, Statistic=Maximum, Period=60, Threshold=10.0, GreaterThanThreshold, TreatMissingData=notBreaching over a hole-free 5-period window seeded with 3 clear and 2 breaching datapoints, the alarm DOES now reach OK, but its decision window is one period short: StateReasonData.recentDatapoints holds only 4 values where the alarm's EvaluationPeriods is 5. The check fails with 'AssertionError: the engine''s recentDatapoints hold 4 values [1.0, 1.0, 1.0, 99.0]; a 5-period alarm evaluates a 5-period window, so a shorter list means the window is not being tracked'. Because the window is short, the breach count it grades is also computed over the wrong number of periods, so the M-of-N predicate and the subsequent 'minimum N-M+1 datapoints for ALARM -> OK transition' wording cannot be right either.

Why: an alarm configured M-of-N grades a different window than AWS does. With a window one period short, a client's alarm can fire (or decline to fire) on data AWS would not have considered, and every consumer that reads recentDatapoints to explain or audit a verdict sees an incomplete window — the two configuration integers silently mean something else than on AWS.

Fix: the alarm evaluator's window construction (the sliding window must always materialise exactly EvaluationPeriods per-period aggregates, filling missing periods per TreatMissingData rather than shortening the list) and the StateReasonData serialization that renders recentDatapoints/evaluatedDatapoints. The open issue 20261027T035003Z-cloudwatch-3-net-new-root-causes-m-of.md names this check for an EARLIER symptom (the alarm never reaching OK at all); the alarm now reaches OK, so this short-window symptom is a different observation and that issue no longer carries this check's replay key.

Traces: cloudwatch.alarm-m-of-n-holds-at-m-minus-one-and-fires-at-m (mismatch, at the recentDatapoints length assertion after the evaluated OK was reached).

=== Cause 4 of 7: a metric-math (Metrics[]) alarm over IF() is never evaluated — it stays INSUFFICIENT_DATA with 'Unchecked: Initial alarm creation' forever ===
Failing check id: cloudwatch.alarm-math-and-anomaly-if-expression-alarm-grades-transformed-value

AWS: Smithy — PutMetricAlarm.Metrics targets MetricDataQueries, the same list GetMetricData takes, so an alarm may be defined over an expression member with ReturnData=true instead of a MetricName/Statistic pair; MetricAlarm.StateValue/StateReason/StateReasonData are as above. The grading of the expression is recorded behavior only: an alarm whose Metrics[] holds a MetricStat with ReturnData=false plus an expression member 'IF(m1 > 100, 0, 1000)' with ReturnData=true grades the TRANSFORMED value, not the raw input — so a raw input below the IF() predicate yields the 1000 branch and breaches a Threshold of 500, and the alarm leaves INSUFFICIENT_DATA on its first real evaluation and reports the expression's value in its StateReason/StateReasonData.

Emulator: PutMetricAlarm accepts the alarm and DescribeAlarms echoes Metrics[] correctly (m1 MetricStat with ReturnData False, e1 Expression 'IF(m1 > 100, 0, 1000)' Label 'Inverted' ReturnData True, Threshold 500.0, GreaterThanThreshold, EvaluationPeriods 1, DatapointsToAlarm 1, TreatMissingData 'missing'), but the alarm is never evaluated: the poll for the alarm leaving INSUFFICIENT_DATA fails with 'AssertionError: alarm ... left INSUFFICIENT_DATA on its first real evaluation did not happen within 39.9s', and the last observation still reports StateValue 'INSUFFICIENT_DATA' with StateReason 'Unchecked: Initial alarm creation' and StateUpdatedTimestamp still equal to AlarmConfigurationUpdatedTimestamp — i.e. no evaluation has ever run against this alarm.

Why: every metric-math alarm is inert. Expression alarms are the standard way to alarm on ratios, error rates and transformed signals; against this emulator they are accepted and then never fire or clear, so nothing they gate ever runs and no error-rate or ratio alarm can be tested.

Fix: the alarm evaluator must take the Metrics[]/expression path — resolve the MetricDataQueries closure through the metric-math engine, grade the ReturnData=true series against Threshold, and write StateValue/StateReason/StateReasonData from that series instead of leaving the initial 'Unchecked: Initial alarm creation' state in place. The fixed issue 20261027T060308Z-cloudwatch-metric-math-alarm-over-if-never-evaluates-a.md claimed exactly this fix and this check still reproduces its described symptom verbatim (INSUFFICIENT_DATA + 'Unchecked: Initial alarm creation'), so that fix did not take effect for this alarm shape and must be re-traced in the current code base.

Traces: cloudwatch.alarm-math-and-anomaly-if-expression-alarm-grades-transformed-value (mismatch).

=== Cause 5 of 7: EvaluationWindow.WallClockWindow is not honoured, and the wall-clock check can no longer even reach its assertion within the harness cap ===
Failing check id: cloudwatch.deep-cloudwatch-1-cw-warmup-wall-clock-window-gates-evaluation-and-rejects-period-120

AWS: Smithy — PutMetricAlarm.EvaluationWindow targets the EvaluationWindow union (members SlidingWindow and WallClockWindow); SlidingWindow is documented as a rolling window that advances on each evaluation, WallClockWindow aligns the evaluated range to fixed clock boundaries matching the alarm's period, and a wall-clock alarm's Period must be 1 minute, 5 minutes, 1 hour, 1 day or 1 week. The behavioral consequence, recorded: for Period P a wall-clock alarm evaluates only CLOSED aligned periods — it stays INSUFFICIENT_DATA until floor(t/P)*P + P has passed, then its StateReasonData.startDate equals that boundary, evaluatedDatapoints holds exactly the boundary timestamp, and queryDate/StateUpdatedTimestamp are at or after the close — while an identical SlidingWindow twin on the same series alarms inside the still-open period from a minute-aligned start that reaches back before the boundary. Neither alarm shape reports an EvaluationState member. The validation arm is separately pinned: Period=120 with a WallClockWindow is refused with HTTP 400, error code 'ValidationError' and the message 'Wall Clock evaluation period must be 1 minute, 5 minutes, 1 hour, 1 day or 1 week.' (that fixed text is the entire message; it has no variable parts), leaving no alarm behind, while Period=120 with a SlidingWindow is accepted and reads back Period=120.

Emulator: the check no longer reaches any of those assertions — it is killed at the suite's 60 s harness cap ('Error: Check timed out after 60.0s') inside its pre-assertion phase, after the Period=120 refusal/control arms, while it waits for the UTC clock to reach 5-150 s past a 300 s boundary and then polls the SlidingWindow twin to ALARM. On the previous replay of the same check the emulator moved BOTH twins to ALARM while the aligned 300 s window was still open, reporting the generic sliding-window StateReason for the wall-clock twin — the stored EvaluationWindow union is echoed back but never branched on by the evaluator.

Why: a client that selects WallClockWindow is asking for calendar-aligned alerting (daily batches, backups, dashboard-aligned periods). Here the alarm fires on partial, unaligned data, so it notifies early and over a different dataset than production, and StateReasonData.startDate/evaluatedDatapoints point at the wrong instants. The two evaluation windows are indistinguishable.

Fix: the alarm evaluator must branch on the stored EvaluationWindow union when it selects the evaluated range — for WallClockWindow, align the range start to floor(now/Period)*Period in the window's Timezone (default UTC), refuse to evaluate until that period has closed, and stamp startDate/evaluatedDatapoints/queryDate/StateUpdatedTimestamp accordingly; SlidingWindow keeps the rolling behaviour; neither path emits EvaluationState. The PutMetricAlarm handler already persists and echoes EvaluationWindow, so no input-side change is needed. NOTE: the open issue 20261028T085300Z-cloudwatch-ignores-evaluationwindow-wallclockwindow-a-wall-clock-alarm.md describes this same defect and names this check, but it is keyed on the old assertion-site replay key and this replay therefore did not mark the check as OWNED; close them together. A fixer should also confirm whether the new cap timeout is purely the check's own boundary-alignment wait (which can legitimately exceed 60 s) or an evaluation stall in front of the SlidingWindow twin's ALARM.

=== Cause 6 of 7: no AWS/Usage CallCount metric is ever published for CloudWatch API calls ===
Failing check id: cloudwatch.obs-cloudwatch-1-usage-callcount-tracks-calls-against-never-called-control

AWS: the Smithy model says nothing about service-usage metrics, so this is recorded behavior only (documented under CloudWatch's service-quota integration). The recording shows that every CloudWatch API call — including a call that FAILS, e.g. a GetDashboard that answers 404 ResourceNotFound with message 'Dashboard ' + the requested dashboard name + ' does not exist' — is counted into the reserved AWS/Usage namespace as the metric CallCount with exactly the four dimensions {Class, Resource, Service, Type}: Service='CloudWatch', Class='None', Type='API', Resource=the operation name. Over a closed 60-second window, the Sum for Resource=ListMetrics is at least the number of ListMetrics calls made, the Sum for a never-called operation (Resource=DeleteDashboards) is exactly 0, and the failed GetDashboard contributes at least 1 to Resource=GetDashboard. The series' Unit is 'None'. ListMetrics discovers the series, and every AWS/Usage CallCount/API metric carries exactly those four dimension NAMES. AWS/ is reserved for writes: PutMetricData into AWS/Usage is refused with HTTP 400, error code 'InvalidParameterValue' and message 'The value AWS/ for parameter Namespace is invalid.' (fixed text; the 'AWS/' prefix is the offending value from the request), while the identical payload into a custom namespace is accepted and reads back.

Emulator: no AWS/Usage CallCount datapoint is ever produced. After 8 ListMetrics calls and one 404 GetDashboard inside one 60-second window, GetMetricData over the three CallCount queries never reaches ListMetrics>=8 and GetDashboard>=1; the check's 600 s ceiling poll never satisfies and it is killed at the 60 s harness cap ('Error: Check timed out after 60.0s'). Because the series never exists, the never-called control (which must read exactly 0), the Unit='None' assertion, the four-dimension schema assertion on ListMetrics discovery and the reserved-namespace write refusal arm are all unreachable.

Why: service-usage metering is the basis of quota dashboards and quota alarms (CallCount vs. the account's request-rate limit). A client that builds a usage alarm or a quota dashboard gets an empty series, which is indistinguishable from 'no traffic' — so quota pressure is invisible and the usage-based alarms it would configure never evaluate.

Fix: the CloudWatch service's own request path must meter each served operation into the AWS/Usage metric store — one CallCount datum per call (successful AND refused) with dimensions Service='CloudWatch', Class='None', Type='API', Resource=<operation name> and Unit='None' — written into the same metric storage the GetMetricData/GetMetricStatistics/ListMetrics read paths serve, while PutMetricData keeps refusing client writes into the reserved AWS/ namespace.

=== Cause 7 of 7: unit-selected datapoint reads never resolve a stable per-unit series ===
Failing check id: cloudwatch.unit-is-part-of-a-datapoints-read-identity

AWS: Smithy — GetMetricStatistics.Unit targets the StandardUnit enum, and GetMetricStatistics models InvalidParameterValueException (httpError 400, awsQueryError InvalidParameterValue); ListMetrics returns Metrics entries that carry only Namespace/MetricName/Dimensions, with NO unit member. The storage semantics are recorded behavior only: Unit is part of a DATAPOINT's read identity but not of a metric's catalogue identity. Three datapoints published at ONE timestamp for one metric under three different units read back as three separate, unconverted series — a Unit-selected GetMetricStatistics returns exactly one datapoint carrying that unit and only the value published under it (no conversion: Kilobytes are never normalised into the Bytes series), omitting Unit returns one datapoint PER published unit at that one timestamp (never a single aggregate), GetMetricData with MetricStat.Unit makes the same selection over the same storage, and a valid-but-never-published unit (Terabytes/Percent/Count) is an EMPTY successful result on both read paths. ListMetrics still lists exactly ONE metric entry for the namespace. A string that is not a unit is refused differently per read path: GetMetricStatistics answers code 'InvalidParameterValue' with the message 'The parameter Unit must be a value in the set [ ' + the StandardUnit value list + ' ].', while GetMetricData answers code 'ValidationError' with the constraint-violation message '1 validation error detected: Value at ''metricDataQueries.<n>.member.metricStat.unit'' failed to satisfy constraint: Member must satisfy enum value set: [' + the enum values + ']' — the member path index comes from the request, the enum values from the model.

Emulator: the check cannot get past its first beat. It polls the three unit-selected GetMetricStatistics reads until all three are non-empty and hold one value for 30 s (own budget 180 s) and is killed at the 60 s harness cap ('Error: Check timed out after 60.0s'), so at least one of the three Unit-selected reads does not resolve to its own datapoint, or the reads do not settle. Everything after it — the no-conversion assertions, the unitless three-datapoint read, the GetMetricData agreement, the single ListMetrics catalogue entry, the empty never-published-unit reads and the two per-path refusal messages — is never exercised.

Why: a client that publishes the same metric under several units (a very common EMF/agent pattern) reads back values that are either missing or merged, so dashboards and alarms built on a unit-selected read see the wrong number or nothing at all; and because omitting Unit must return one datapoint per unit rather than an aggregate, a merged implementation silently sums incomparable quantities.

Fix: the metric store's datapoint key must include Unit (so each unit is its own bucket) while the ListMetrics catalogue key must NOT, and the GetMetricStatistics / GetMetricData read paths must select by Unit over that key — returning one datapoint per published unit when Unit is omitted and an empty successful result for a valid never-published unit. The fixed issue 20261027T100939Z-cloudwatch-unit-is-not-part-of-a-datapoint.md claimed exactly this fix ('Unit is not part of a datapoint''s storage/read identity — unit-selected GetMetricStatistics/GetMetricData reads never resolve the per-unit series'); the check still cannot resolve the three per-unit series, so that fix must be re-traced rather than treated as settled.

Traces: cloudwatch.unit-is-part-of-a-datapoints-read-identity (mismatch).
