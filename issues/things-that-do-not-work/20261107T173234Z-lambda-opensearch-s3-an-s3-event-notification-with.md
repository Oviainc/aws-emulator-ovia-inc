# lambda__opensearch__s3: an S3 event notification with a Lambda destination produces no observable effect, and the domain data plane refuses a caller its IAM identity policy allows (2 causes)

> _Note: this issue was identified against the code base at commit `edd8d27229a8bc99e308a4b32d393f13d6f32cb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutBucketNotificationConfiguration

## Description
This issue bundles 2 net-new root causes, both grounded in failing checks of the lambda__opensearch__s3 suite. Each cause must be closed before submitting.

Cause 1 of 2: an S3 ObjectCreated/ObjectRemoved notification whose destination is a Lambda function never produces the function's side effect — no OpenSearch document is indexed, and no marker/error object is written back to S3.
AWS: recorded behavior only (S3 event notification delivery is not modelled in the Smithy API). The recordings show the documented pipeline: PutBucketNotificationConfiguration with a LambdaFunctionConfiguration for `s3:ObjectCreated:*` (optionally with a `.json`/suffix Filter) and a `lambda:InvokeFunction` permission for principal `s3.amazonaws.com`; a subsequent PutObject then invokes the function asynchronously, and within seconds the function's effect is observable — a signed `GET /<index>/_doc/<id>` on the domain endpoint answers 200 with the indexed `_source`, a `HeadObject`/`GetObject` of the `<key>.marker` or `<key>.err` object answers 200, and after DeleteObject the ObjectRemoved handler removes the document so the same GET answers 404 with `found: false`. A suffix-filtered configuration fires for matching keys only.
Emulator: the effect never appears inside the checks' 90–120 s windows. The verifying GET answers HTTP 404 with the engine-shaped body `{'error': {'root_cause': [{'type': 'index_not_found_exception', 'reason': 'no such index [objects]', 'index': 'objects', 'resource.type': 'index_or_alias', 'resource.id': 'objects'}], 'type': 'index_not_found_exception', 'reason': 'no such index [objects]', ...}, 'status': 404}` — i.e. the target index was never even created — and the marker-object probes stay False for the whole window. Here the fixed text is `no such index [<index>]` / `index_not_found_exception` with status 404; `objects` is the index name the request carried, so only that name varies. The CLI variant reports the same thing as `document never indexed within 90s (last status=404)`.
Why: every S3-driven ingestion pipeline is silently dead. A client gets a successful PutObject and a successful notification configuration, then waits forever for a side effect that never happens; the negative checks are equally broken, because a pipeline that never fires cannot demonstrate that an ungranted function is NOT invoked and that a granted one IS.
Fix: the S3 event-notification dispatcher that turns an object mutation into an asynchronous Lambda invocation (S3's notification delivery path plus the Lambda async invoke path it calls). Hypothesis: the dispatch may be firing and the handler faulting instead — the open issue issues/things-that-do-not-work/20261105T111951Z-lambda-opensearch-s3-the-lambda-python-runtime-has.md records that the Lambda python runtime ships no AWS SDK, which would make every one of these boto3-importing handlers fault before doing anything; whichever of the two it is, the fixer should confirm by asserting a delivery/invocation record for the PutObject before concluding. Open issues 20261025T121424Z-lambda-opensearch-s3-an-s3-objectcreated-notification.md, 20261103T101621Z-lambda-opensearch-s3-s3-objectcreated-notification-to-a-granted-lambda-destination.md and 20261104T232822Z-lambda-opensearch-s3-a-cloudformation-deployed-s3-lambda.md describe the same symptom but carry none of the replay keys listed here.

Cause 2 of 2: the OpenSearch domain's data-plane authorizer decides es:ESHttp* on the domain's resource-based AccessPolicies alone and refuses a signed request from a principal that policy does not name, even when the caller's IAM identity-based permissions allow the action.
AWS: recorded behavior only for the authorization union (the domain access policy is an opaque `PolicyDocument` string in the Smithy model; AWS documents es:ESHttp* access as granted by the domain access policy OR by an identity-based IAM policy attached to the caller). In both recordings the domain is created by CloudFormation with an AccessPolicies document whose single statement allows `es:ESHttp*` on `<domainArn>/*` for the indexer role ONLY, and the test principal — which that document does not name — still gets 200 from a SigV4-signed `GET /<index>/_doc/<docId>` against the published endpoint, returning the document's `_source`.
Emulator: the same signed GET is refused HTTP 403 with `{'error': {'root_cause': [{'type': 'security_exception', 'reason': 'User: <callerArn> is not authorized to perform: es:ESHttpGet on resource: <domainArn>/<index>/_doc/<docId> because no resource-based policy allows the es:ESHttpGet action'}], 'type': 'security_exception', 'reason': '<same>'}, 'status': 403}`. The fixed text is `User: … is not authorized to perform: <action> on resource: <resource> because no resource-based policy allows the <action> action` with type `security_exception` and status 403; the caller ARN, the action, the domain/index/document resource and the generated domain name are request/state values, not part of the requirement.
Why: a client whose access is granted by its IAM identity policy (the normal console/CLI-admin case, and the case these CFN templates rely on) is locked out of its own domain. Automation that verifies an ingestion pipeline by reading a document back cannot distinguish "the pipeline did not run" from "I am not allowed to read", and a refusal is returned where AWS returns data.
Fix: the es data-plane authorizer for the published domain endpoint — the authorization decision must be the union of the domain's resource-based AccessPolicies and the signing principal's identity-based permissions, not the resource policy alone. Hypothesis: the handler evaluates only the stored AccessPolicies document, which is why its message hard-codes `because no resource-based policy allows …` for every denial.
Traces: lambda__opensearch__s3.deploy-lambda-opensearch-s3-stack-positive, lambda__opensearch__s3.deploy-s3-notification-lambda-opensearch-pipeline-positive.

## Steps to Reproduce
Cause 1: create a bucket and an execution role; CreateFunction with a handler that indexes the object into an OpenSearch domain (or writes a `<key>.marker` object back to S3); AddPermission(Action=lambda:InvokeFunction, Principal=s3.amazonaws.com, SourceArn=<bucketArn>); PutBucketNotificationConfiguration with a LambdaFunctionConfiguration for `s3:ObjectCreated:*` (optionally Filter suffix `.json`); PutObject a key -> poll a signed `GET /<index>/_doc/<id>` on the domain endpoint, or HeadObject the marker key. Observed: 404 index_not_found_exception / no marker for the whole window. Repeat with DeleteObject and an `s3:ObjectRemoved:*` configuration for the removal half.
Cause 2: deploy a CloudFormation stack with an AWS::OpenSearchService::Domain whose AccessPolicies allows `es:ESHttp*` on `<domainArn>/*` for the indexer role ONLY, then issue a SigV4-signed (service `es`) GET to `https://<DomainStatus.Endpoint>/<index>/_doc/<id>` using the stack deployer's own credentials, which the access policy does not name. Observed: 403 security_exception `…because no resource-based policy allows the es:ESHttpGet action`; AWS answers 200.
