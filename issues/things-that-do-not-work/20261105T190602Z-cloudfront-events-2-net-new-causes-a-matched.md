# cloudfront__events: 2 net-new causes — a matched event never reaches an InputPath/InputTransformer Lambda target, and a permission-denied Lambda target never dead-letters NO_PERMISSIONS

> _Note: this issue was identified against the code base at commit `04def8971989cc2c0cf0cb3f2a0f2f1403eb68f2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTargets

## Description
Two net-new root causes in the EventBridge rule-dispatch path, grounded in the only three failing cloudfront__events checks the replay report does not mark OWNED or ALREADY FILED. Both must be closed before submitting.

Related open issues (none of them carries any of the three replay keys below, so this is filed separately and should be de-duplicated against them if one dispatch fix closes them all): 20261105T172430Z-cloudfront-events-an-eventbridge-rule-whose-lambda-target.md (same symptom, but its only trace id is eventbridge-cloudfront-distribution-arn-resolution-in-target-input), 20261102T091831Z-cloudfront-events-a-matched-rule-never-invokes-its.md (its dead-letter cause is FAILED_TO_ASSUME_ROLE on a target ROLE, not NO_PERMISSIONS on a Lambda resource policy), 20261104T051153Z-cloudfront-events-a-matching-putevents-entry-never-invokes.md, 20261029T175823Z-cloudfront-events-13-more-cloudfront-eventbridge-checks-fail.md, 20261101T214154Z-cloudfront-events-two-more-root-causes-a-matched.md.

Cause 1 of 2: a matched PutEvents entry is never dispatched to a Lambda target, so neither the target's InputPath extraction nor its InputTransformer rendering is ever observable. Failing checks: cloudfront__events.eventbridge-rule-input-path-extracts-distribution-id, cloudfront__events.eventbridge-target-arn-resolves-to-specific-cloudfront-distribution.
AWS: Smithy (services/service-com-amazonaws-eventbridge-awsevents): PutTargets input Rule (@required, @length 1..64, @pattern ^[\.\-_A-Za-z0-9]+$) + Targets (@required, @length 1..100); Target carries Id/Arn (@required) and the optional input-shaping members InputPath -> TargetInputPath (@length 0..256) and InputTransformer (InputPathsMap -> TransformerPaths, map 0..100 of JSON paths; InputTemplate -> TransformerInput @required @length 1..8192). The modeled docs state InputPath is "the value of the JSONPath that is used for extracting part of the matched event when passing it to the target", and that each InputPathsMap key is referenced in InputTemplate enclosed in angle brackets (<value>) and substituted to form the input actually sent to the target. PutEvents (Entries @required @length 1..10) models only InternalException, i.e. an accepted entry (FailedEntryCount 0) is a promise of asynchronous delivery. On AWS, an entry matching an ENABLED rule's EventPattern invokes each target once with the shaped input — with InputPath the target receives ONLY the extracted node (here a bare JSON string, the distribution id), and with InputTransformer it receives the rendered template. A Lambda target is invoked provided its resource policy admits events.amazonaws.com for that rule ARN (lambda:AddPermission Principal events.amazonaws.com, SourceArn arn:aws:events:<region>:<account>:rule/<ruleName>). Recorded behavior only for timing: the recording shows the shaped payload reaching the target well inside the checks' 90 s poll windows.
Emulator: every setup call is accepted — sqs.CreateQueue/GetQueueAttributes, iam.CreateRole/AttachRolePolicy/PutRolePolicy, lambda.CreateFunction (the function reaches Active and the checks' direct RequestResponse warm-up Invoke succeeds, so function and role work), events.PutRule(State=ENABLED), lambda.AddPermission, events.PutTargets with InputPath or InputTransformer, and events.PutEvents — and then nothing happens. No invocation ever occurs, so nothing is ever enqueued on the observation queue; both checks exhaust their poll loops and are killed by the harness at "Check timed out after 60.0s" before reaching their assertions. Nothing is refused: there is no status, error code or message to compare, the divergence is silent non-delivery.
Why: a client that wires a rule to a Lambda target to hand it a reshaped payload (lift $.detail.requestParameters.distributionId with InputPath, or compose arn:aws:cloudfront::<account>:distribution/<distributionId> with an InputTransformer) sees PutEvents report success and then loses every event. Each downstream effect the target would have produced (an invalidation, a write, a notification, the SQS relay these checks observe) is missing, and no DLQ record or FailedInvocations signal distinguishes "did not match" from "matched but not delivered". Such automation looks correct at configuration time and drops 100% of traffic at run time, and the InputPath/InputTransformer shaping rules cannot be verified at all.
Fix: the EventBridge PutEvents -> rule-matching -> target-dispatch component for rules on the default bus: after an entry is accepted it must be matched against each ENABLED rule's EventPattern and each matching target invoked under its permission check, applying the target's input shaping (Input / InputPath JSONPath extraction / InputTransformer InputPathsMap extraction + angle-bracket InputTemplate substitution) to build the payload. The shapers cannot be exercised until dispatch exists, so both the dispatcher and the input-shaping renderer are in scope.
Traces: cloudfront__events.eventbridge-rule-input-path-extracts-distribution-id (group data-format), cloudfront__events.eventbridge-target-arn-resolves-to-specific-cloudfront-distribution (group arn-resolution).

Cause 2 of 2: a target whose Lambda has no events.amazonaws.com invoke grant produces no failed-delivery record on the target's DeadLetterConfig queue. Failing check: cloudfront__events.eventbridge-lambda-target-missing-permission-blocks-delivery.
AWS: Smithy: Target.DeadLetterConfig -> DeadLetterConfig{Arn -> ResourceArn @length 1..1600} is documented as "the target queue to send dead-letter queue events to", and Target.RetryPolicy -> RetryPolicy{MaximumRetryAttempts range 0..185, MaximumEventAgeInSeconds range 60..86400} bounds the attempts before an event is dead-lettered. AWS documents that when EventBridge cannot deliver a matched event to a target it sends the event to that target's DLQ and attaches the delivery metadata as SQS message attributes, among them ERROR_CODE and TARGET_ARN; the error code for a target the rule is not permitted to invoke is NO_PERMISSIONS, and the dead-lettered message BODY is the original event envelope (so $.detail of the dead-lettered message equals the detail published by PutEvents). With MaximumRetryAttempts=0 that record appears after the single failed attempt. The target itself must NOT run: no invocation and no downstream effect. Recorded behavior only for the pairing: granting lambda:AddPermission afterwards makes the identical wiring deliver.
Emulator: PutTargets with DeadLetterConfig + RetryPolicy and PutEvents are both accepted, but no message is ever written to the DLQ — the check republishes the matching event on a 180 s budget while polling the DLQ with ReceiveMessage(MessageAttributeNames=["All"]) and is killed by the harness at "Check timed out after 60.0s" before the first DLQ record arrives, so neither ERROR_CODE=NO_PERMISSIONS nor TARGET_ARN=<the function ARN> nor the republished detail.marker is ever observable. The positive-control leg (AddPermission, then delivery) is never reached.
Why: a DLQ is the only way a client learns that a matched event was lost; with no record, a permission gap is indistinguishable from a non-matching pattern, alarms on DLQ depth never fire, and the ERROR_CODE a remediation routine branches on (NO_PERMISSIONS -> add the resource policy) never exists. Note that this cause is separate from Cause 1: even after dispatch works, a delivery refused for want of permission must still produce the DLQ record with that error code.
Fix: the target-dispatch failure path — when a matched delivery is refused because the target's resource policy does not admit events.amazonaws.com for the rule ARN, exhaust RetryPolicy (MaximumRetryAttempts=0 means one attempt) and then write the original event envelope to Target.DeadLetterConfig.Arn with the delivery-metadata message attributes (ERROR_CODE, ERROR_MESSAGE, RULE_ARN, TARGET_ARN), ERROR_CODE being NO_PERMISSIONS; the target must remain uninvoked.
Traces: cloudfront__events.eventbridge-lambda-target-missing-permission-blocks-delivery (group overly-permissive).

## Evidence
Replay of suite simparity-behavioral-aws-v1: 302/584 passed (51.7%). Service cloudfront__events: 11/55 (20%), 44 failed; 41 of those are marked OWNED by an open issue or ALREADY FILED (stub-blocked) and were skipped. The three remaining failures cluster into the two causes above.

Cause 1 — [mismatch] cloudfront__events.eventbridge-rule-input-path-extracts-distribution-id: "Error: Check timed out after 60.0s".
Setup, all accepted by the emulator: CreateQueue + GetQueueAttributes(QueueArn); CreateRole (trust lambda.amazonaws.com) + AttachRolePolicy(AWSLambdaBasicExecutionRole) + PutRolePolicy(sqs:SendMessage on the queue); CreateFunction whose handler relays its event to that queue; a warm-up RequestResponse Invoke that succeeds; PutRule(EventPattern {"source":["sim2real.cloudfront"],"detail-type":["AWS API Call via CloudTrail"],"detail":{"eventName":["CreateInvalidation"],"requestParameters":{"distributionId":[<generated id>]}}}, State=ENABLED); lambda.AddPermission(Principal events.amazonaws.com, SourceArn the rule ARN); PutTargets with one Lambda target InputPath="$.detail.requestParameters.distributionId"; PutEvents with one matching CloudTrail-shaped entry.
Expected (AWS): the target is invoked with just the extracted scalar, so the relayed SQS body is the JSON string of the distribution id from the request (`assert payload == dist_id`).
Actual (emulator): no message ever arrives on the observation queue; _poll_for_message(timeout_s=90) never returns and the harness kills the check at 60 s. No refusal, no error code, no DLQ record.

Cause 1 — [mismatch] cloudfront__events.eventbridge-target-arn-resolves-to-specific-cloudfront-distribution: "Error: Check timed out after 60.0s".
Same wiring, but the target carries InputTransformer InputPathsMap {"acct":"$.account","did":"$.detail.requestParameters.distributionId"} and InputTemplate '{"resolvedArn": "arn:aws:cloudfront::<acct>:distribution/<did>", "distributionId": "<did>"}'.
Expected (AWS): the relayed body has resolvedArn == arn:aws:cloudfront::<account>:distribution/<distributionId> and distributionId == the id published in the event. Fixed text of that rendering: the literal "arn:aws:cloudfront::", ":distribution/" and the member names resolvedArn/distributionId; variable parts: the account id from GetCallerIdentity and the distribution id from the request's detail.
Actual (emulator): nothing is ever enqueued; killed at the 60 s cap before the assertion.

Cause 2 — [mismatch] cloudfront__events.eventbridge-lambda-target-missing-permission-blocks-delivery: "Error: Check timed out after 60.0s".
Setup: an observation queue and a DLQ (both created, ARNs read); a relay Lambda (warm-up Invoke succeeds); PutRule with pattern {"source":[<generated source>],"detail-type":["AWS API Call via CloudTrail"],"detail":{"requestParameters":{"distributionId":[<generated id>]}}}; an SQS policy granting events.amazonaws.com SendMessage on the DLQ for that rule ARN; PutTargets with DeadLetterConfig.Arn=<DLQ arn> and RetryPolicy{MaximumRetryAttempts:0, MaximumEventAgeInSeconds:60} and deliberately NO lambda.AddPermission.
Expected (AWS): the matched event is not delivered (the observation queue stays empty) and EventBridge writes the event to the DLQ with MessageAttributes ERROR_CODE == "NO_PERMISSIONS" and TARGET_ARN == the function ARN, body $.detail.marker == the published marker; then, after lambda.AddPermission, the identical wiring delivers and the relayed body carries the second marker.
Actual (emulator): the DLQ never receives anything. The check's _put_until_dlq loop (budget 180 s, each iteration PutEvents asserted FailedEntryCount==0 then a 30 s ReceiveMessage with MessageAttributeNames=["All"]) is still looping when the harness kills the check at 60 s, so the DLQ assertions and the positive control are never reached.

Not environment-dependent: the generated queue/role/function/rule names, the account id, the distribution id, the markers and the host/port differ per run and are not part of the requirement. The requirements are (1) a matched entry reaches the Lambda target with Input/InputPath/InputTransformer applied, and (2) a delivery refused for lack of an invoke grant yields a DLQ record carrying ERROR_CODE NO_PERMISSIONS and TARGET_ARN.
