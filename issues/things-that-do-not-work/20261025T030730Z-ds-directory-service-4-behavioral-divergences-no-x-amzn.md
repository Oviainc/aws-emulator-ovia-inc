Cause 1 of 4: ds responses carry no x-amzn-RequestId HTTP header, so an SDK's ResponseMetadata.RequestId does not exist.
AWS: recorded behavior only for the transport header (the Smithy model describes the body: every ds error structure declares Message plus a UUID-shaped RequestId, @pattern ^([A-Fa-f0-9]{8}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{4}-[A-Fa-f0-9]{12})$, CreateComputer errors all HTTP 400). Every AWS response — success or refusal — also carries the request id in the x-amzn-RequestId response header, which is where botocore populates response['ResponseMetadata']['RequestId'] from for this JSON protocol. The requirement is the PRESENCE of that header carrying the call's id; the particular id is an example.
Emulator: the refusal of CreateComputer on a directory that is not yet Active raises a ClientError whose ResponseMetadata has no RequestId key at all — the check dies with KeyError: 'RequestId' reading exc.response['ResponseMetadata']['RequestId'] — so the header is absent even though the body member is now populated. Secondary observation from the checkout (the check crashed before it could assert it): the recorded AWS diagnostic for this path is DirectoryUnavailableException with the request-derived template "Directory: '<DirectoryId>' does not exist. : RequestId: <id>", while services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/create_computer.rs words it "Directory <id> is in stage <stage> and is not available for computer account changes".
Why: every client, SDK retry log and support workflow correlates a ds call by ResponseMetadata.RequestId; against this emulator that field is missing, so request-id logging raises KeyError/None instead of yielding a handle, and any caller that echoes the id (as ds's own message format does) cannot build it.
Fix: the shared response/error serialization seam for this service (the runtime's response construction used by services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/*, which already mints the id in crate::state::refusal) — emit the same id as the x-amzn-RequestId header on every response, and align the CreateComputer not-in-service diagnostic with ds's request-derived template.
Traces: ds.create-computer-authentication-failed-rejected.

Cause 2 of 4: AddIpRoutes refuses an already-routed CIDR with the wrong error class.
AWS: recorded behavior (stated by the check as measured on real AWS, us-west-2): re-adding a CIDR the directory already routes is refused 400 ClientException with 'The IP route(s) [<cidr>] already exist. If you want to recreate them, please delete the existing routes first.' (plus ds's ' : RequestId: <id>' suffix) — explicitly NOT EntityAlreadyExistsException. Smithy: AddIpRoutes models BOTH ClientException and EntityAlreadyExistsException (client, HTTP 400), so the model does not disambiguate; the recording does.
Emulator: 400 with code EntityAlreadyExistsException and message 'Directory d-003ba5fe5a already routes the address block 198.51.102.0/24 : RequestId: <id>' (src/ops/add_ip_routes.rs duplicate-block branch). The status matches; the error code an SDK maps to an exception class does not.
Why: the error code is what SDKs turn into a typed exception, so a caller's duplicate-route branch keyed on ClientException never runs and a benign duplicate surfaces as an unexpected entity conflict.
Fix: the duplicate-block branch of the AddIpRoutes handler (src/ops/add_ip_routes.rs) — refuse with ClientException carrying the route-already-exists diagnostic.
Traces: ds.ip-route-duplicate-cidr-rejected.

Cause 3 of 4: DescribeDirectories never reports DnsIpAddrs, so the member is absent on a Managed Microsoft AD that is Active.
AWS: Smithy: DirectoryDescription.DnsIpAddrs (list) — 'The IP addresses of the DNS servers for the directory. For a Simple AD or Microsoft AD directory, these are the IP addresses of the Simple AD or Microsoft AD directory servers.' Recorded behavior: once the directory is Active the list holds one address per chosen subnet, each contained in that subnet's CIDR; the addresses are derived by the service, so the particular values are examples.
Emulator: the key is absent entirely — the check dies with KeyError: 'DnsIpAddrs' on describe_directories(...)['DirectoryDescriptions'][0]['DnsIpAddrs'] for a directory it has already waited into Active. Confirmed in the checkout: Directory::to_description in src/state.rs never fills dns_ip_addrs (the only dns_ip_addrs field in the module belongs to ConditionalForwarderRecord).
Why: DnsIpAddrs is the only way a client learns where to point resolvers or what to put in a peer directory's conditional forwarder; a caller reading it gets a KeyError/None, and every trust/forwarder flow that feeds the peer's DnsIpAddrs cannot be built at all.
Fix: the directory record's controller placement/address derivation in src/state.rs feeding DescribeDirectories (src/ops/describe_directories.rs) — allocate one address from each requested subnet CIDR and report them in DnsIpAddrs.
Traces: ds.state-machine-trust-create-verify-delete-404.

Cause 4 of 4: the trust state machine ignores the remote domain — CreateTrust always settles Created, so Failed is unreachable, and VerifyTrust is guarded only against Deleting.
AWS: Smithy: TrustState enumerates Creating, Created, Verifying, VerifyFailed, Verified, Updating, UpdateFailed, Updated, Deleting, Deleted, Failed, and Trust carries TrustStateReason ('The reason for the TrustState'); VerifyTrust models InvalidParameterException (client, 400). Recorded behavior (measured by the check, us-west-2): CreateTrust to an unresolvable remote domain (<unique>.invalid with ConditionalForwarderIpAddrs 203.0.113.5) goes Creating -> Failed within seconds with a non-empty TrustStateReason, VerifyTrust on that trust is then refused InvalidParameterException whose message names the state it refused from ('Cannot verify trust in state: Failed'), and DeleteTrust then removes it so DescribeTrusts answers EntityDoesNotExistException.
Emulator: src/ops/create_trust.rs stores every new trust as Creating with a clock transition, and src/state.rs advance_clock maps Creating -> Created unconditionally (TRUST_STATE_CREATING => TRUST_STATE_CREATED) — the remote domain is never resolved or contacted, so Failed/VerifyFailed and TrustStateReason are unreachable for any input. The check's wait for TrustState=Failed therefore never converges and the harness kills it at its 60 s budget ('Check timed out after 60.0s', no exception frame). Same file set: src/ops/verify_trust.rs refuses only a trust in Deleting, so a Failed trust would be ACCEPTED and driven to Verifying instead of refused InvalidParameterException. Hypothesis (neither the model nor a recording states it): part of this check's budget may also be consumed by the shared VPC/directory fixture wait that 20261024T081601Z's Cause 7 describes; the unreachable Failed state is the defect this check's assertions pin, and that is what re-replay must show.
Why: a client cannot observe or handle a trust that failed to establish — the only outcome this emulator can produce is success — so every trust error path (diagnose via TrustStateReason, refuse a verify from a bad state, tear the trust down) is unreachable, and a caller polling for a terminal failure hangs forever.
Fix: the trust state machine — src/ops/create_trust.rs plus the trust branch of advance_clock in src/state.rs must settle a trust whose remote domain cannot be resolved into Failed with a TrustStateReason, and src/ops/verify_trust.rs must refuse a verify from a non-verifiable state (Failed included) with InvalidParameterException naming that state.
Traces: ds.trust-create-verify-delete-lifecycle.
