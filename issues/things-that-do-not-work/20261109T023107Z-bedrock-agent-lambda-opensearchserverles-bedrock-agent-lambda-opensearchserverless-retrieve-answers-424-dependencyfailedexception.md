# bedrock-agent__lambda__opensearchserverless: Retrieve answers 424 DependencyFailedException for an AOSS-backed knowledge base, so a deployed data-access-policy grant can neither be confirmed nor denied end to end (1 cause, 2 checks)

> _Note: this issue was identified against the code base at commit `e944e72389a9c803ebf7fc7f022f4184a07cd9ff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve

## Description
REOPENS 20261025T173258Z-bedrock-agent-runtime-retrieve-is-a-scaffold-stub.md: its fix left the call refused. Retrieve is implemented now, but only for a knowledge base bound to an S3 Vectors index; a knowledge base backed by an OpenSearch Serverless collection — what these deployment checks build — is refused with 424 instead of served. Open issues 20261108T202701Z-bedrock-agent-lambda-opensearchserverles-bedrock-agent-lambda-opensearchserverless-retrieve-answers-501-notimplemented.md and 20261105T040349Z-bedrock-agent-lambda-opensearchserverles-bedrock-agent-lambda-opensearchserverless-the-retrieveandgenerate-end-to.md describe the older 501/stalled-build symptoms for other checks and do not carry these checks' replay keys or this refusal.

=== Cause 1 of 1: Retrieve refuses an OPENSEARCH_SERVERLESS-backed knowledge base with 424 DependencyFailedException, so the AOSS data-access-policy grant/denial boundary is never reached ===
AWS: Smithy: Retrieve = POST /knowledgebases/{knowledgeBaseId}/retrieve, @readonly, success HTTP 200, output retrievalResults (@required). Modeled errors include DependencyFailedException (424, "There was an issue with a dependency. Check the resource configurations and retry the request."), AccessDeniedException (403) and ResourceNotFoundException (404). On real AWS the two outcomes these checks separate are: (a) when the deployed AOSS data access policy grants the knowledge-base role aoss:APIAccessAll on the collection, the ingestion job completes and Retrieve answers 200 with the ingested content in content.text; (b) when that data-access grant is missing, the failure surfaces earlier and specifically — CreateKnowledgeBase refuses the storage configuration with the dependency detail AWS words as "The knowledge base storage configuration provided is invalid... Dependency error document status code: 403, error message: Bad Authorization" (fixed cause clause; the status code and the authorization message are the dependency's own, not values invented per run). In neither case is a supported store type itself reported as a failed dependency on Retrieve.
Emulator: both the granted and the missing-grant deployments end at the same refusal: HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." Fixed text is "The vector store the knowledge base is backed by could not be queried: " + <resource> + ". Check the resource configurations and retry the request." (runtime plane state/knowledge_base_retrieval.rs, unreachable_store_message); <resource> is the only variable part and is filled with the knowledge base's storageConfiguration.type, i.e. the store-type token "OPENSEARCH_SERVERLESS" rather than a collection ARN or index name. The cause is store-type blindness, not authorization: nearest_chunks resolves storage exclusively via agent_state::s3_vectors_binding and returns RetrievalRefusal::UnreachableVectorStore for an opensearchServerlessConfiguration, so neither the collection, its data access policy, nor the index the ingestion wrote is ever consulted.
Why: the permission boundary a client deploys the stack to verify is erased. A correct CloudFormation/Lambda deployment that grants aoss:APIAccessAll looks broken (424 on every retrieval), and an intentionally incomplete deployment that AWS rejects at CreateKnowledgeBase with a 403 Bad Authorization dependency detail reaches Retrieve and fails with the identical 424 — so a client cannot tell a policy mistake from a healthy stack, and cannot tell either from an unsupported store. Any infrastructure test or runbook keyed on these outcomes passes or fails for the wrong reason.
Fix: the runtime plane's retrieval state and the build-time plane's ingestion/storage validation. nearest_chunks (services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/state/knowledge_base_retrieval.rs) must resolve an opensearchServerlessConfiguration to the opensearchserverless collection/index it names, honour that collection's data access policy for the knowledge-base role (denial -> the modeled AccessDenied/dependency path, not store-type UnreachableVectorStore), and rank the chunks the ingestion wrote; the Bedrock Agent ingestion writer (service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/state/ingestion.rs, ingestion_index.rs) must write into that index; and CreateKnowledgeBase's storage validation in the same crate must refuse a knowledge base whose role cannot read the named index with AWS's invalid-storage-configuration wording carrying the dependency's 403/Bad Authorization detail instead of letting the call succeed.

## Evidence
Expected (positive check): with the deployed AOSS data access policy granting the knowledge-base role aoss:APIAccessAll on the collection, the ingestion job completes and Retrieve answers HTTP 200 with retrievalResults whose content.text contains the ingested document text.
Expected (negative check): with the data-access grant absent from the deployed stack, the failure appears at CreateKnowledgeBase as an invalid-storage-configuration refusal whose dependency detail reads "Dependency error document status code: 403, error message: Bad Authorization" — not as a Retrieve-time dependency failure.
Actual (both checks): HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." (botocore.errorfactory.DependencyFailedException raised on the Retrieve call). The trailing token is the knowledge base's storageConfiguration.type, the only variable part of the emulator's fixed message template; no collection, policy or index is consulted, so the granted and the ungranted deployments are indistinguishable.

## Steps to Reproduce
1. Deploy the stack: an IAM knowledge-base role, an opensearchserverless VECTORSEARCH collection with encryption/network policies, and a data access policy granting that role aoss:APIAccessAll on the collection; create the vector index on the collection endpoint.
2. Call bedrock-agent CreateKnowledgeBase with storageConfiguration.type = "OPENSEARCH_SERVERLESS" naming that collection and index, create a data source over an S3 object containing a known phrase, and run the ingestion job to completion.
3. Call bedrock-agent-runtime Retrieve(knowledgeBaseId=<kb id>, retrievalQuery={'text': <question about the phrase>}).
4. Observe HTTP 424 DependencyFailedException "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." instead of 200 with the ingested content.
5. Repeat the deployment with the aoss:APIAccessAll data-access grant omitted: CreateKnowledgeBase succeeds instead of refusing with the invalid-storage-configuration / 403 Bad Authorization dependency detail, and Retrieve returns the identical 424, so the two deployments cannot be told apart.
