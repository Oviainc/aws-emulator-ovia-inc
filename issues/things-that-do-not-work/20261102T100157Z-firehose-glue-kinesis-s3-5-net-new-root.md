# firehose__glue__kinesis__s3: 5 net-new root causes — Glue IcebergInput writes no metadata.json object, Iceberg and KDS-sourced delivery are inert, IcebergDestinationDescription omits BufferingHints, and the KDS-source encryption refusal is misworded

> _Note: this issue was identified against the code base at commit `ebea418ed7238d7557ed4699ab6be023240b4505`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateTable

## Description
Five net-new root causes on the Glue Iceberg catalog and the Firehose Iceberg / Kinesis-sourced delivery paths. The open issue 20261028T122732Z-firehose-glue-kinesis-s3-the-apache-iceberg-path.md names the same families from a single check each (its replay keys are kds-iceberg-input-mints-a-metadata-json-and-a-metadata-location, kds-records-put-to-kds-land-as-iceberg-data-and-a-committed-snapshot, kds-create-delivery-stream-* and kds-encryption-configuration-*) and does NOT carry the checks listed below; causes 1, 4 and 5 here are the same defect families seen through additional, independently failing checks that add requirements that issue does not state (the format-version default, the Glue→Iceberg type mapping, delete/recreate semantics, the parameter-only marker route, DirectPut Iceberg error routing, and KDS fan-out / LATEST start). Causes 2 and 3 are new defects not described anywhere.

Cause 1 of 5: Glue CreateTable with OpenTableFormatInput.IcebergInput back-fills Parameters['metadata_location'] but never writes the metadata.json object it points at.
AWS: recorded behavior only (the Smithy model declares OpenTableFormatInput.IcebergInput{MetadataOperation, Version} on CreateTable, not its side effect): real Glue sets Parameters['table_type']='ICEBERG' and Parameters['metadata_location'] to an s3:// URI under <StorageDescriptor.Location>metadata/ AND writes exactly that object. Its body carries format-version equal to IcebergInput.Version (2 when Version is omitted — the documented default), a table-uuid, 'snapshots': [], and schemas[0].fields numbered 1..n in declared column order with required=false, each Glue (Hive) type mapped to its Iceberg primitive (string→string, int→int, bigint→long, float→float, double→double, boolean→boolean, date→date) while GetTable keeps the Glue type names in StorageDescriptor.Columns. DeleteTable removes only the catalog row: the metadata object stays in S3, and re-creating the same name mints a NEW metadata object with a new table-uuid and empty snapshots. The parameter-only route (Parameters['table_type']='ICEBERG' plus the Hive-Iceberg SerDe/InputFormat/OutputFormat triple, no OpenTableFormatInput) labels the row only: no metadata_location and no S3 object at all.
Emulator: the catalog half works (GetTable returns table_type=ICEBERG and a well-formed metadata_location under the table Location), but the object is never written: GetObject on exactly the key named by metadata_location fails with NoSuchKey ('The specified key does not exist.'), and every check that polls the <Location>metadata/ prefix for that key exhausts its budget with the prefix empty.
Why: catalog and storage disagree — every Iceberg reader that resolves metadata_location (Athena, Spark, Firehose's own commit step) fails on a pointer to a nonexistent object, and the differential claims above (format-version default, type mapping, delete/recreate, parameter-only route) cannot be exercised at all because the control route never materialises.
Fix: the Glue CreateTable handler's OpenTableFormatInput/IcebergInput branch (services/service-com-amazonaws-glue-awsglue/src/ops/create_table.rs) must materialise the metadata.json into S3 at the location it records, with the format version, table-uuid, empty snapshot list and mapped schema above, and must leave the parameter-only route writing nothing.
Traces: firehose__glue__kinesis__s3.e2e-kds-firehose-iceberg-athena-lifecycle (phase 3/6 solve, GetObject NoSuchKey), firehose__glue__kinesis__s3.kds-glue-iceberg-input-without-a-version-writes-format-version-2, firehose__glue__kinesis__s3.kds-glue-iceberg-input-maps-glue-column-types-to-iceberg-types, firehose__glue__kinesis__s3.kds-glue-deleted-iceberg-table-keeps-its-metadata-and-a-recreate-mints-a-new-table, firehose__glue__kinesis__s3.kds-table-type-parameter-alone-materialises-no-iceberg-metadata.

Cause 2 of 5: DescribeDeliveryStream's IcebergDestinationDescription omits BufferingHints entirely when the create omitted them, instead of reporting the defaults.
AWS: Smithy: IcebergDestinationDescription has a BufferingHints member targeting BufferingHints{SizeInMBs (range 1..128, 'The default value is 5'), IntervalInSeconds (range 0..900, 'The default value is 300')}. A CreateDeliveryStream that supplies IcebergDestinationConfiguration with no BufferingHints is described with BufferingHints present and defaulted: {'SizeInMBs': 5, 'IntervalInSeconds': 300}.
Emulator: the key is absent from the description — reading Destinations[0].IcebergDestinationDescription['BufferingHints'] raises KeyError, so the member was never serialized.
Why: a client reading back the stream cannot learn the buffer the destination actually uses, and code that reads the hints to size its producer or to re-apply them in an Update call fails on a missing key rather than seeing the documented 5 MiB / 300 s.
Fix: the delivery-stream state that records an Iceberg destination plus the DescribeDeliveryStream serializer (services/service-com-amazonaws-firehose-firehose-20150804/src/ops/create_delivery_stream.rs and .../describe_delivery_stream.rs) must default omitted Iceberg BufferingHints to SizeInMBs 5 / IntervalInSeconds 300 and always emit the member.
Traces: firehose__glue__kinesis__s3.kds-omitted-iceberg-buffering-hints-default-to-5-mib-and-300-seconds (check line 256, KeyError: 'BufferingHints').

Cause 3 of 5: StartDeliveryStreamEncryption's refusal on a KinesisStreamAsSource stream carries the wrong message text.
AWS: Smithy: StartDeliveryStreamEncryption is modeled with InvalidArgumentException (client, HTTP 400). Server-side encryption is a direct-put-only feature, so for a stream whose DeliveryStreamType is KinesisStreamAsSource real Firehose refuses with InvalidArgumentException (HTTP 400) and the message `Cannot enable encryption for a delivery stream <name> with delivery stream type <type>` — fixed text with two variable parts: the delivery stream name from the request and the stream's DeliveryStreamType from state.
Emulator: the code is right (InvalidArgumentException) but the message is its own invention: 'server-side encryption cannot be enabled for Firehose stream <name> because its type is KinesisStreamAsSource; only a stream that uses DirectPut as its source supports it'.
Why: clients and tests that match on AWS's sentence (and log scrapers that key on it) do not recognise the refusal, even though the code matches.
Fix: the StartDeliveryStreamEncryption handler's source-type refusal (services/service-com-amazonaws-firehose-firehose-20150804/src/ops/start_delivery_stream_encryption.rs) must emit AWS's sentence with the request's stream name and the stored DeliveryStreamType.
Traces: firehose__glue__kinesis__s3.kds-start-delivery-stream-encryption-rejected-on-a-kinesis-sourced-stream (check line 298).

Cause 4 of 5: a DirectPut Iceberg-destination stream delivers nothing — no Parquet under <table Location>data/, no snapshot commit, and no per-record failure object under the ErrorOutputPrefix.
AWS: recorded behavior only: with an ACTIVE Iceberg-destination stream (BufferingHints{SizeInMBs:1, IntervalInSeconds:60}), records accepted by PutRecord (each returning a RecordId) are written as .parquet objects under <Location>data/, committed by a snap-*.avro manifest list plus a *-m0.avro manifest and a new NNNNN.metadata.json whose snapshot summary['added-records'] counts exactly the accepted records. Per-record validation failures are NOT dropped: a record whose timestamp column uses the space-separated SQL spelling 'YYYY-MM-DD HH:MM:SS' (while ISO-8601 with and without a zone offset and epoch milliseconds are accepted) is written under an iceberg-failed/ segment of the ErrorOutputPrefix as one JSON envelope per line with errorCode 'Iceberg.MalformedFieldWithinRecord', attemptsMade >= 1 and the original bytes base64-encoded in rawData. A stream pointed at a Glue table with no Iceberg marker also reaches ACTIVE and accepts records, but writes nothing under that table's prefix and must not retro-fit a metadata_location onto it.
Emulator: nothing is ever written. Both checks were killed at the suite's 60 s budget while polling S3: no data/ object, no .avro, no new metadata.json and no object under the error prefix appeared for the marked/valid cases, so neither the commit nor the discrimination against the malformed record is observable. This is the DirectPut face of the inert Iceberg writer (the open issue above records the KinesisStreamAsSource face from one check).
Why: an Iceberg lakehouse pipeline silently loses every record — producers get a RecordId, the table never commits, and a malformed record is indistinguishable from a delivered one because the documented failure envelope and its errorCode never appear.
Fix: the Firehose delivery engine's Iceberg destination writer and Glue commit step (services/service-com-amazonaws-firehose-firehose-20150804/src/ — the IcebergDestinationConfiguration delivery path) must buffer accepted records, write Parquet data objects, commit manifest + manifest list + metadata.json, advance the catalog's metadata_location, and route per-record field-validation failures to <ErrorOutputPrefix>iceberg-failed/ with the Iceberg.MalformedFieldWithinRecord envelope.
Traces: firehose__glue__kinesis__s3.kds-an-iceberg-timestamp-column-rejects-the-space-separated-sql-spelling, firehose__glue__kinesis__s3.kds-an-unmarked-destination-table-swallows-records-a-marked-one-commits.

Cause 5 of 5: a KinesisStreamAsSource stream with an ExtendedS3 destination never ingests its source stream, so neither fan-out nor the LATEST start position is observable.
AWS: recorded behavior only: a KinesisStreamAsSource delivery stream polls its source shard and writes the records under its ExtendedS3 Prefix (one JSON record per line). Two delivery streams may name the SAME Kinesis stream and each receives EVERY record (they are not competing consumers), and a stream starts reading at LATEST — records put to the source before the delivery stream was created are never delivered, while records put after it is ACTIVE are.
Emulator: no object is ever written under either destination prefix. Both checks reached ACTIVE and kinesis:PutRecords/PutRecord succeeded (FailedRecordCount 0, a SequenceNumber returned), then exhausted their budget with the destination prefixes empty, so both claims (fan-out completeness and the LATEST start) are ungradeable. Related open issues record the same ingestion gap under other service headings (20261026T074043Z-firehose-kinesis-s3-a-kinesisstreamassource-delivery-stream-never.md, 20261026T235333Z-firehose-2-net-new-root-causes-a-kinesisstreamassource.md); neither carries these two checks or the fan-out / start-position requirements.
Why: every Kinesis→Firehose→S3 pipeline silently loses all data, and a client cannot observe either documented property of the source binding.
Fix: the Firehose source ingestion loop for KinesisStreamSourceConfiguration (services/service-com-amazonaws-firehose-firehose-20150804/src/ — the KinesisStreamAsSource consumer feeding the destination writer) must consume the source shards from LATEST at stream creation, deliver every record to each subscribed delivery stream independently, and write them under the destination Prefix.
Traces: firehose__glue__kinesis__s3.kds-one-kinesis-stream-feeds-two-delivery-streams-each-with-every-record, firehose__glue__kinesis__s3.kds-sourced-delivery-stream-starts-at-latest-and-skips-earlier-records.
