# DescribeScalingPlanResources refuses a ScalingPlanVersion other than 1 with ValidationException instead of answering 200 with an empty ScalingPlanResources list

> _Note: this issue was identified against the code base at commit `c8d2895969da39fca153e18dbf6e2a36d41fd98d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeScalingPlanResources

## Description
The Auto Scaling Plans crate gates DescribeScalingPlanResources on its ScalingPlanVersion member and refuses any value other than 1 before it ever looks the plan up. AWS treats that member as a selector, not a constrained enum: a version the named plan does not have is simply a read that selects nothing. This issue has 1 cause.

Cause 1 of 1: a read for a plan version that does not exist is turned into a client error instead of an empty result.
AWS: Smithy (services/service-com-amazonaws-autoscalingplans-anyscalescalingplannerfrontendservice/smithy-model/com-amazonaws-autoscalingplans-anyscalescalingplannerfrontendservice.json): DescribeScalingPlanResources.ScalingPlanVersion -> ScalingPlanVersion, @required, type long, with NO @range and NO enum — the only statement about the value is prose on the member ("The version number of the scaling plan. Currently, the only valid value is 1."), which is documentation of what versions exist today, not a modeled input constraint. The operation binds ConcurrentUpdateException(500), InternalServiceException(500), InvalidNextTokenException(400) and ValidationException(400), and binds NO not-found shape, which is why a selector that matches nothing cannot be an error on this operation at all. Recorded behavior: a DescribeScalingPlanResources for a (ScalingPlanName, ScalingPlanVersion) pair the service does not hold — an absent plan name, or version 2 of a live plan that only has version 1 — answers HTTP 200 with ScalingPlanResources = [] and no NextToken. The write operations over the same absent coordinate are the ones that refuse: DeleteScalingPlan/UpdateScalingPlan answer HTTP 400 ObjectNotFoundException with the message "No scaling plan found for scaling plan name: <ScalingPlanName>, version: <ScalingPlanVersion>" — the fixed text is "No scaling plan found for scaling plan name: " + ", version: ", and the two variable parts are the plan name and the version number echoed from the request.
Emulator: the request is refused HTTP 400 ValidationException with Message "ScalingPlanVersion 2 is not valid: the only valid value is 1" (fixed text "ScalingPlanVersion " + " is not valid: the only valid value is 1", with the request's own version number interpolated; the recorded 2 is the request's value filling that template, not part of it). The refusal is raised before the lookup, so it fires for every version != 1 regardless of what the store holds. The emulator's own handler documents the opposite rule for the sibling case: an unknown ScalingPlanName reads back as 200 + empty list (ops/describe_scaling_plan_resources.rs lines 18-23 and 199-208), so the two halves of "absent coordinate" are handled inconsistently — absent name is empty, absent version is a 400.
Why: this read is the poll primitive for the whole plan lifecycle. A client that walks or probes versions (a caller that does not yet know which version is current, an upgrade path that checks version N+1, or any poll-until-visible loop keyed on a version) gets a thrown ValidationException from botocore where AWS hands back an empty list, so the loop aborts instead of continuing; and because the code is ValidationException rather than ObjectNotFoundException, generic not-found handling does not catch it either. It also inverts the read/write contract this API relies on: on AWS an absent plan coordinate is safe to READ and only refused on WRITE.
Fix: DescribeScalingPlanResources' request validation — the ScalingPlanVersion gate at services/service-com-amazonaws-autoscalingplans-anyscalescalingplannerfrontendservice/src/ops/describe_scaling_plan_resources.rs:180 (crate::state::validate_plan_version, in src/state.rs) must not reject a version the model does not constrain; the existing state.plan(name, version) lookup two lines later already yields the correct empty answer when no such plan/version is held. Note the same helper is invoked from the forecast read's copy of this member (per the comment at lines 177-179), so the fix belongs in the shared gate rather than in one handler.
Traces: auto-scaling-plans.asp-absent-plan-reads-are-empty-but-writes-are-rejected (errored at the version-2 read of a live plan). The check aborts on that call, so its remaining assertions — DeleteScalingPlan for version 2 answering ObjectNotFoundException "No scaling plan found for scaling plan name: <name>, version: 2", and DescribeScalingPlans refusing ScalingPlanNames together with ApplicationSources with ValidationException "Application sources cannot be provided with scaling plan names or version" — were never reached and are unverified; replaying the whole check after the fix is required.

Related but not covering this: open issue 20261030T033853Z-autoscaling-plans-auto-scaling-plans-client-error-refusals-diverge-no.md covers this operation's invalid-NextToken message wording and CreateScalingPlan's name pattern, not the ScalingPlanVersion gate; open issue 20261022T175157Z-auto-scaling-plans-plan-lifecycle-has-no-application.md covers the lifecycle/Application Auto Scaling side effects. Neither owns this replay key.

Not asserted as requirements: the generated plan/table names the check mints, and any request id or clock value in the envelope.
