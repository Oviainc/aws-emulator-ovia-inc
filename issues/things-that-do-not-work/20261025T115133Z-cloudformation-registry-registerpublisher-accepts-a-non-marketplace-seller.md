# CloudFormation registry: RegisterPublisher accepts a non-Marketplace-seller account, and the PUBLIC extension registry exposes no activatable THIRD_PARTY types (2 causes)

> _Note: this issue was identified against the code base at commit `7ec46f8e53e7b4a82f0a526dc76e942bfb70fd11`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterPublisher

## Description
This issue bundles 2 net-new root causes in the CloudFormation extension-registry surface. Related open issues do NOT cover them: 20261025T015306Z-cloudformation-is-not-region-scoped-stack-names-and.md (its Cause 5 records RegisterPublisher answering NotImplemented, keyed on cloudformation.type-publishing-lifecycle — the handler is now implemented, and the defect below is that it now ACCEPTS what AWS refuses, which is a different behaviour and a different replay key), 20261025T015306Z-cloudformation-describepublisher-stub.md (DescribePublisher; in this replay DescribePublisher already refuses correctly with CFNRegistryException), and the already-filed ListTypes scaffold-stub issue (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/list_types.rs) which Cause 2 sits downstream of but is not closed by.

Cause 1 of 2: RegisterPublisher registers a publisher for an account that is not an enrolled AWS Marketplace seller.
AWS: Smithy: RegisterPublisher(AcceptTermsAndConditions: boolean, ConnectionArn) -> RegisterPublisherOutput{PublisherId}; the single modeled error is CFNRegistryException, errorKind client, httpError 400 (awsQueryError code CFNRegistryException / 400). Publisher registration additionally requires the caller account to already be enrolled as an AWS Marketplace seller — an out-of-band, console-only step no API call can perform. Recorded behavior: on an account that is not enrolled, RegisterPublisher(AcceptTermsAndConditions=true) is refused with HTTP 400, Error.Code "CFNRegistryException" and Error.Message exactly "You must be a valid AWS Marketplace Seller to be registered as a publisher" — that message is entirely fixed text, with no part taken from the request or from state. Until a publisher exists, DescribePublisher stays refused with CFNRegistryException and the message "The account [<AccountId>] is not registered as a publisher, if you want to describe a specific publisher, please specify the publisherID" (fixed text; the only variable part is the caller's 12-digit account id in the square brackets, taken from the signed credentials). Downstream of the same gate, TestType on a type that was never registered is refused with CFNRegistryException "You must register as a publisher with CloudFormation to call test-type." and PublishType against a versioned type ARN with CFNRegistryException "Only default version can be published. Please remove versionId from Arn" (both entirely fixed text).
Emulator: RegisterPublisher(AcceptTermsAndConditions=true) returns HTTP 200 with a minted PublisherId and writes an account-wide publisher record. The handler (services/service-com-amazonaws-cloudformation-cloudformation/src/ops/register_publisher.rs) gates only on AcceptTermsAndConditions and then calls state.lock().register_publisher(...) unconditionally; there is no Marketplace-seller eligibility gate at all. Because the call succeeds, both publisher checks abort before they can reach the DescribePublisher / TestType / PublishType refusals that follow the same gate, so those messages are untested here.
Why: a client cannot distinguish an eligible publisher account from an ineligible one. Code that branches on the Marketplace-seller refusal (the only signal AWS gives that enrollment is missing) takes the success path against the emulator and then breaks against AWS; and the whole publish/test-type refusal taxonomy that hangs off "is this account a publisher" becomes unreachable, since the emulator reports every account as a registered publisher immediately.
Fix: the RegisterPublisher handler and the publisher state it writes (ops/register_publisher.rs plus crate::state::publisher) need an account-eligibility gate that refuses with the modeled 400 CFNRegistryException and the Marketplace-seller message, and writes nothing, unless the account is explicitly configured as an enrolled seller; the same gate must then be the one DescribePublisher/TestType/PublishType read.
Traces: cloudformation.publisher-registration-lifecycle, cloudformation.publisher-and-type-testing-lifecycle.

Cause 2 of 2: the PUBLIC extension registry holds no activatable THIRD_PARTY resource type that exposes a ConfigurationSchema, so no extension configuration can ever be set.
AWS: ListTypes(Visibility=PUBLIC, Type=RESOURCE, Filters={Category: THIRD_PARTY}) enumerates third-party public extensions; DescribeType on one of them returns a ConfigurationSchema, ActivateType(PublicTypeArn, ExecutionRoleArn) activates it in the account/Region, and SetTypeConfiguration -> BatchDescribeTypeConfigurations then round-trips a configuration document for it. Recorded behavior (from the check's own replay notes): every candidate's activation requires an ExecutionRoleArn and is otherwise refused with CFNRegistryException "Please provide execution role to activate the Resource type", and a configuration document that is set comes back with its structure intact and every non-ASCII codepoint replaced one-for-one by a literal "?".
Emulator: the registry search finds nothing usable — the bounded ListTypes walk over Visibility=PUBLIC / Category=THIRD_PARTY yields no type whose DescribeType carries a ConfigurationSchema, so the check fails with "no publicly-activatable THIRD_PARTY resource type exposing a ConfigurationSchema was found in this account/Region within the search budget". ListTypes itself is an unimplemented scaffold stub (already filed separately), but implementing it over an empty public registry still leaves this cause open: the whole ActivateType -> SetTypeConfiguration -> BatchDescribeTypeConfigurations path has no subject.
Why: no client can exercise third-party extension activation or extension configuration against the emulator; SetTypeConfiguration/BatchDescribeTypeConfigurations fidelity (including the ASCII-coercion rule AWS applies to configuration string values) is untestable and silently absent.
Fix: the cloudformation registry state needs a seeded PUBLIC/THIRD_PARTY type catalogue whose entries carry a ConfigurationSchema, reachable from the ListTypes and DescribeType handlers, with ActivateType enforcing the execution-role requirement.
Traces: cloudformation.type-configuration-nested-json-structure-preserved.
