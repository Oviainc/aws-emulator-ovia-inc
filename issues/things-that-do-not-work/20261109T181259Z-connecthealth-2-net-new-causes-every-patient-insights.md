## Description
Two distinct root causes under the suite heading '### connecthealth' (15/24 passed, 9 failed; connecthealth.delete-domain-not-found and connecthealth.domain-tags-visible-via-resourcegroupstaggingapi are marked OWNED by existing issues and are excluded). They are bundled because they share one service; each is numbered and carries its own failing check ids. A fixer must close BOTH before submitting.

=== Cause 1 of 2: the HealthLake data-store endpoint that connecthealth's patient-insights surface requires is published on a real-AWS host, so six patient-insights checks never reach a single connecthealth assertion ===
Failing checks: connecthealth.get-patient-insights-job-not-found, connecthealth.start-patient-insights-job-conflicting-client-token-rejected, connecthealth.start-patient-insights-job-malformed-s3-uri-rejected, connecthealth.start-patient-insights-job-nonexistent-domain-not-found, connecthealth.start-patient-insights-job-succeeds-and-produces-summary, connecthealth.start-patient-insights-job-unseeded-patient-rejected.
AWS: Smithy (services/service-com-amazonaws-connecthealth-connecthealth/smithy-model/com-amazonaws-connecthealth-connecthealth.json) models StartPatientInsightsJob as POST /domain/{domainId}/patient-insights-job (hostPrefix 'runtime.', 200) with required inputDataConfig; its fhirServer.fhirEndpoint must name a REAL, existing HealthLake FHIR data store ('Only HealthLake FHIR datastore is currently supported'; 'HealthLake datastore not found' for one that does not exist) and patientContext.patientId must resolve to a Patient that data store actually holds ('Patient could not be found in datastore' for an unseeded id). The model does not describe the FHIR REST data plane — recorded behavior only: healthlake DescribeFHIRDatastore/CreateFHIRDatastore hand the caller DatastoreProperties.DatastoreEndpoint (required, 'The Amazon Web Services endpoint for the data store'), and a SigV4-signed (service name 'healthlake', Content-Type application/fhir+json) PUT <DatastoreEndpoint>/Patient/<id>, GET <DatastoreEndpoint>/Patient/<id> and GET <DatastoreEndpoint>/Patient?identifier=<id> against it create, read and search that resource. The contract of that member is that it is a ROUTABLE base address of the service answering those interactions — nothing else in the API tells a client where the data plane is — so on an emulator it must be an address the emulator itself serves.
Emulator: the endpoint is published on the real AWS production host, https://healthlake.<region>.amazonaws.com/datastore/<32-hex datastore id>/r4/. The suite's harness refuses that egress before a byte is sent: 'endpoint_url was given https://healthlake.<region>.amazonaws.com/datastore/<id>/r4/Patient/<patient-id> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://<emulator host>:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener'. The region, the ports, the 32-hex data-store ids and the generated patient ids in that text are per-run values; the defect is the CLASS of host announced. All six checks fail identically in the shared _seed_patient/_signed_request helper at ctx.endpoint_route(url), i.e. on the first interaction against the published endpoint, before any connecthealth call under test is made. This is the same root cause already filed for healthlake's OWN checks in open issue 20261109T135225Z-healthlake-3-net-new-causes-datastoreendpoint-is-published.md (its Cause 1, trace ids healthlake.fhir-rest-api-native-protocol-roundtrip and healthlake.fhir-import-job-delivers-resource-to-datastore); the suite does not report these six connecthealth checks as owned by it, so they are filed here with their own replay keys — if that issue's Cause 1 is fixed, re-replay the six checks listed above to confirm. Note also that the two earlier connecthealth issues whose Cause 2 describes this setup failing later, at the FHIR type-level search (20261102T101414Z-connecthealth-createsubscription-words-a-malformed-domainid-with-the.md and 20261107T174733Z-connecthealth-behavioral-surface-2-divergences-tagged-domains-are.md), no longer match the symptom: the setup now dies one step earlier, at the endpoint's host.
Why: a client follows the published DatastoreEndpoint to establish the precondition the patient-insights API documents (a Patient resolvable in a real FHIR data store) and then to verify what a job consumed. Pointed at an amazonaws.com host, that request either leaves for the public internet or fails as a DNS/connection error, and the failure looks like the client's own networking rather than an emulator gap. Downstream, the entire connecthealth patient-insights slice is unobservable: starting a job for a seeded patient and reading its summary, the not-found job refusal, clientToken conflict handling, s3OutputPath validation, the nonexistent-domain refusal and the unseeded-patient refusal are all unverified rather than merely wrong.
Fix: the projection of DatastoreProperties.DatastoreEndpoint in the healthlake crate's data-store state/serializer — the single place CreateFHIRDatastore / DescribeFHIRDatastore / ListFHIRDatastores (and CloudFormation GetAtt DatastoreEndpoint) read — must build the value from the address the emulator is reached on (scheme/host/port of the serving listener, keeping the /datastore/<id>/r4/ path prefix the FHIR router already accepts, or the per-resource listener's host:port) instead of a hard-coded healthlake.<region>.amazonaws.com template; connecthealth's patient-insights handlers that resolve inputDataConfig.fhirServer.fhirEndpoint must accept that same self-served address.
Traces: the six checks named above; all six fail at context.py _published_target via the checks' _signed_request helper.

=== Cause 2 of 2: CreateSubscription refuses a malformed domainId with the framework's generic constraint sentence instead of the service's own domain-id refusal ===
Failing check: connecthealth.create-subscription-malformed-domain-id-rejected.
AWS: Smithy models CreateSubscription as POST /domains/{domainId}/subscriptions (201); input member domainId -> DomainId with @httpLabel, @required, @length(min 20, max 25) and @pattern '^(hai-|dom-)[a-z0-9]+$'; ValidationException is a modelled error with httpError 400. The model states the pattern but NOT how the service words a value that violates it — recorded behavior: a value that satisfies the length bound but carries a foreign prefix is not stopped by a framework constraint walk; it reaches the service, which answers HTTP 400 ValidationException whose message is the service's own sentence. Its FIXED text is ' is not a valid domain id.' preceded by the rejected domainId exactly as the request supplied it, followed by the backend's SDK-style suffix '(Service: <service>, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)' whose three values are per-request and not part of the requirement.
Emulator: the status and code are right (400 ValidationException) but the message is the generic modelled-input-validation sentence: "1 validation error detected: Value '<value>' at 'domainId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(hai-|dom-)[a-z0-9]+$". That is the service-level constraint gate rendering the modelled @pattern, so the request is refused before the operation's handler can word it and the 'is not a valid domain id.' sentence is unreachable for every malformed domainId.
Why: a client (or a human reading a CLI error) that matches on, logs or surfaces AWS's domain-id refusal sees a completely different sentence, and tooling that distinguishes 'this id is not a valid domain id' from a generic member-constraint violation cannot. The check's positive control (CreateSubscription with a well-formed domainId, then ListSubscriptions == 1) passes, so only the wording of the refusal diverges — exactly the part a caller reads. Open issue 20261102T101414Z-connecthealth-createsubscription-words-a-malformed-domainid-with-the.md describes this same divergence as its Cause 1, but is keyed on a replay key this check no longer produces (that key is an `assert message.startswith(expected)`; the check now asserts full equality of the message), so the suite does not report it as owned; if that issue's Cause 1 is being fixed, re-replay this check to confirm.
Fix: the domainId refusal belongs in CreateSubscription's own per-operation validation/handler path (currently preempted by the crate's service-level modelled-input-validation gate): the httpLabel domainId must be refused by the operation with the service's own sentence rather than by the generic constraint gate.
Traces: connecthealth.create-subscription-malformed-domain-id-rejected.
