# route53profiles association lifecycle is not reported: status messages, timestamps and a disassociated resource association that never goes away

> _Note: this issue was identified against the code base at commit `4d9e3fb251011fe781d884d5ecb8db5bb1e34e6b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateResourceToProfile

## Description
FIVE net-new wire causes in the route53profiles ASSOCIATION plane (Profile<->VPC associations and Profile<->DNS-resource associations), found by replaying the wire corpus (trace set simparity-wire-aws-v1). They share one root shape: the emulator records an association but does not report its LIFECYCLE the way AWS does - it never attaches the StatusMessage AWS pairs with each association status, it never varies that wording by the resource kind being associated, it reports both lifecycle timestamps in a form the recorded responses do not carry and never advances ModificationTime when the record changes, and a resource association that was disassociated stays readable forever. ALL FIVE must be closed before this issue is submitted.

Related but NOT covering: the open issue 'route53profiles Profile status reporting, not-found refusal wording and CreateProfile Name validation diverge' (20261029T194643Z-route53profiles-profile-status-reporting-not-found-refusal-wording.md) covers the same missing-StatusMessage fault on the PROFILE shape only (GetProfile/DeleteProfile); Causes 3 and 4 below are the ProfileAssociation shape and Causes 1, 2 and 5 the ProfileResourceAssociation shape, which that issue does not mention and which the replay reports as unowned clusters. The open stub issue 'Implement route53profiles DisassociateResourceFromProfile' (20261104T144248Z-route53profiles-disassociateresourcefromprofile-stub.md) covers that operation answering 501; Cause 5 is the STATE consequence observed on GetProfileResourceAssociation and is reported by the replay as its own unowned cluster, so implementing the stub is necessary but the read path must be re-replayed here to confirm it.

Cause 1 of 5 - AssociateResourceToProfile reports a DNS Firewall rule-group association with the generic 'Profile resource association' status wording instead of the DNS-Firewall-specific one. AWS: the response member is ProfileResourceAssociation (Smithy: AssociateResourceToProfile, HTTP POST /profileresourceassociation, success 200, output member ProfileResourceAssociation; shape ProfileResourceAssociation members Status -> ProfileStatus enum [COMPLETE, DELETING, UPDATING, CREATING, DELETED, FAILED] and StatusMessage -> String, documented 'Additional information about the Profile resource association'). The exact strings are recorded behavior only - the model does not enumerate them - and what the recording shows is that AWS names the RESOURCE KIND in both the status and the message when a DNS Firewall rule group is associated: Status 'UPDATING' with StatusMessage whose fixed text is 'Updating the Profile to DNS Firewall rule group association'. The message has no variable part; the resource kind in it comes from the type of the ResourceArn the request named. Emulator: answers 200 with Status 'CREATING' and StatusMessage 'Creating the Profile resource association' - a single kind-agnostic pair, because state.rs builds the message from the status alone (resource_association_status_message matches only on CREATING/COMPLETE and knows nothing about the record's resource_type). Why: a client watching a DNS Firewall rule group being attached to a Profile branches on the association status and surfaces its message; it sees a status AWS does not report at that point and prose that never mentions the rule group, so progress UIs and any wait-for-state loop keyed on the Firewall wording never match. Fix: the resource-association status/message projection in this service's state module, plus the status AssociateResourceToProfile mints - the message builder must take the record's ResourceType as well as its status so a FIREWALL_RULE_GROUP association reports the DNS-Firewall lifecycle wording, and the associate handler must mint the status AWS reports for that kind rather than always CREATING. Traces: route53profiles-profile-shares-dns-firewall-with-vpc#task#19.

Cause 2 of 5 - GetProfileResourceAssociation reports the settled DNS Firewall association with the generic completion message. AWS: GetProfileResourceAssociation returns the same ProfileResourceAssociation shape (Smithy: HTTP GET /profileresourceassociation/{ProfileResourceAssociationId}, success 200, readonly). Recorded behavior only for the string: once the DNS Firewall rule-group association has settled, AWS reports Status COMPLETE with StatusMessage whose fixed text is 'Completed creation of Profile to DNS Firewall rule group association' - again naming the resource kind, with no variable part. Emulator: 200 with the right COMPLETE status but StatusMessage 'Completed creation of Profile resource association'. Why: the completion message is how a client confirms the rule group is actually in force on the Profile; prose that never names the rule group makes a Firewall-specific readiness assertion fail against the emulator while passing against AWS. Why it is not Cause 1: a different status (COMPLETE, after the transition) reported by a different operation - fixing only the create-time wording leaves every read of a settled association diverging. Fix: same resource-association message projection as Cause 1, on its COMPLETE arm. Traces: route53profiles-profile-shares-dns-firewall-with-vpc#task#20.

Cause 3 of 5 - AssociateProfile omits ProfileAssociation.StatusMessage entirely. AWS: AssociateProfile returns the association it just created (Smithy: AssociateProfile, HTTP POST /profileassociation, success 200, output member ProfileAssociation; shape ProfileAssociation members Status -> ProfileStatus and StatusMessage -> String, documented 'Additional information about the Profile association'). Recorded behavior only for the string: AWS populates it on the associate response with the fixed text 'Creating Profile Association' - no variable part. Emulator: answers 200 with no StatusMessage member at all ($.ProfileAssociation.StatusMessage: missing, expected 'Creating Profile Association', got None), because the handler stores status_message: None for every association it mints and state's projection passes that None straight through. Hypothesis: AWS pairs that message with a non-terminal status for the new VPC association, where the emulator jumps straight to COMPLETE at insert time; the replay flagged only the message, so the message is the requirement this issue states. Why: StatusMessage is the only place this service explains a VPC association's state, so a client that renders or branches on it sees nothing and cannot distinguish 'association accepted, being applied' from an unexplained status. Fix: AssociateProfile's handler must set the association's status message when it mints the record (the field exists on the stored struct and in the wire shape and is simply never filled), and the state projection must carry it through. Traces: route53profiles-profile-shares-dns-firewall-with-vpc#task#21.

Cause 4 of 5 - GetProfileAssociation omits ProfileAssociation.StatusMessage for an established VPC association. AWS: GetProfileAssociation returns the same shape (Smithy: HTTP GET /profileassociation/{ProfileAssociationId}, success 200, readonly). Recorded behavior only for the string: a VPC association that finished being created is reported with the fixed text 'Created Profile Association' - note it differs from the associate-time message in Cause 3, so the two are not one constant. Emulator: 200 with the correct identity members but StatusMessage absent ($.ProfileAssociation.StatusMessage: missing, expected 'Created Profile Association', got None). Why: 'the VPC is attached to the Profile' is confirmed through this read; with no message a client cannot tell an established association from one it has no information about, and teardown/readiness assertions on the message fail. Why it is not Cause 3: a different operation and a different message for the settled state - filling only the create-time message leaves every read diverging. Fix: the association's stored status message must advance with its status, and GetProfileAssociation's projection must report it. Traces: route53profiles-profile-shares-dns-firewall-with-vpc#task#22.

Cause 5 of 5 - a disassociated Profile resource association stays readable: GetProfileResourceAssociation keeps answering 200 COMPLETE where AWS refuses with ResourceNotFoundException. AWS: once the resource association is removed, the id names nothing and the lookup is refused with ResourceNotFoundException at HTTP 400 (Smithy: GetProfileResourceAssociation errors include ResourceNotFoundException, errorKind client, httpError 400 defaulted; this service reports its sub-error code inside the message, Error.Code staying ResourceNotFoundException). The recorded teardown polls the id until that refusal arrives, i.e. the terminal state of a removed association is 'not found', never a readable record. Emulator: answers 200 for 13 poll attempts across the 60s cap, still reporting the full record with Status 'COMPLETE' and StatusMessage 'Completed creation of Profile resource association' - the association is never removed from the store and never enters DELETING/DELETED. The proximate reason is that DisassociateResourceFromProfile is an unimplemented scaffold stub (answers 501, filed separately), so nothing ever mutates or drops the record. Why: this is the over-permissive class - the emulator holds state AWS would not, so every later step (re-associating the same resource, deleting the Profile, which AWS refuses only while an association exists) runs against a resource that should be gone, and teardown never converges. Fix: the resource-association delete path - DisassociateResourceFromProfile's handler must remove (or transition to DELETING and then drop) the stored record and its tags, and GetProfileResourceAssociation's lookup must then take its modeled not-found branch for that id. Traces: route53profiles-profile-shares-dns-firewall-with-vpc#teardown#28.

Shared sub-fault present in Causes 1-4 - ProfileResourceAssociation and ProfileAssociation CreationTime/ModificationTime are reported in a form the recorded responses do not carry, and ModificationTime never advances. AWS: both shapes carry CreationTime and ModificationTime (Smithy: target Rfc3339Timestamp, documented 'The date and time that the Profile [resource] association was created/modified'). Modification time is by definition the instant the record last changed, so a status transition (CREATING -> COMPLETE, or the UPDATING of Cause 1) advances it past the creation time. Emulator: every one of the four clusters above flags both members - the association shapes serialize them as a bare epoch number with sub-microsecond fractional precision (e.g. 1794240283.7330902), which does not match the shape the recorded response carries, while the Profile shape's timestamps on the same code path pass the identical check; and because the store sets modification_time = creation_time at insert and the CREATING -> COMPLETE transition is computed from a settle deadline without touching it, the two members are always byte-identical however the record's status changes. Hypothesis: the shape check rejects the wire form rather than the value (the values themselves are not asserted - the corpus marks them shaped-not-asserted, and a per-run clock reading is never a requirement). Fix: the two association shapes' timestamp serialization must match the form the Profile shape's timestamps already serialize correctly in, and the state module must advance a record's modification_time whenever its status or properties change. This is not a separate cause to close - it is why Causes 1-4's steps will still fail if only their StatusMessage is fixed.
