# batch__logs: a placed Batch job ends FAILED with an emulator-authored no-container-runtime reason, and array children all fail with no reason at all, so no job ever runs or writes an awslogs stream (2 causes)

> _Note: this issue was identified against the code base at commit `afd9c28cd10d0281c7cc3c2a5c51ef0c1f3c612b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SubmitJob

## Description
Two net-new behavioral root causes grounded in the simparity-behavioral-aws-v1 replay against this checkout (batch__logs 0/10 passed). Both must be closed before submitting.

Related open issue, named for the fixer: 20261104T041055Z-batch-logs-array-job-submission-is-unimplemented-and.md. Its cause 1 (SubmitJob with arrayProperties refused NotImplemented) no longer reproduces — SubmitJob now accepts arrayProperties and creates children — and its cause 2 described jobs that never settle, whereas jobs now DO settle, as FAILED with a fixed emulator-authored reason. Neither check in this sweep is marked OWNED by it, so the current behavior is recorded here. See also open 20261106T090000Z-batch-s3-a-placed-job-s-container-is-never-run.md for the same defect family under service heading batch__s3.

Cause 1 of 2 — a placed single-container job ends FAILED with a fixed emulator-authored statusReason instead of running its container.
AWS: Smithy com.amazonaws.batch#SubmitJob answers 200 {jobArn,jobName,jobId}; DescribeJobs then reports JobDetail. JobDetail.status (JobStatus) walks SUBMITTED -> PENDING -> RUNNABLE -> STARTING -> RUNNING -> SUCCEEDED for a job whose container exits 0, and JobDetail.startedAt/stoppedAt are the transitions into RUNNING and into the terminal status. JobDetail.statusReason is modeled as "A short, human-readable string to provide more details for the current status of the job" and its documented values are the MISCONFIGURATION:* / CAPACITY:* family (MISCONFIGURATION:COMPUTE_ENVIRONMENT_MAX_RESOURCE, MISCONFIGURATION:JOB_RESOURCE_REQUIREMENT, MISCONFIGURATION:SERVICE_ROLE_PERMISSIONS, CAPACITY:INSUFFICIENT_INSTANCE_CAPACITY) — it is never prose about the server that answered. JobDetail.attempts carries AttemptDetail{startedAt,stoppedAt,statusReason,container:AttemptContainerDetail{taskArn,exitCode,reason,logStreamName}}; AttemptContainerDetail.logStreamName is documented as "The name of the CloudWatch Logs log stream that's associated with the container". For a FARGATE job definition carrying an awslogs logConfiguration, the container's stdout arrives as events in the configured log group, one event per printed line, in a stream whose name is derived from awslogs-stream-prefix, the container name and the ECS task id. A terminate, an elapsed timeout.attemptDurationSeconds and an exceeded container memory limit each stop the container before its completion marker is written; a maxvCpus cap holds a second job in RUNNABLE and then runs it; a retryStrategy/evaluateOnExit RETRY makes the next attempt see an incremented AWS_BATCH_JOB_ATTEMPT.
Emulator: every job the queue can place reaches FAILED one clock span after RUNNABLE, with JobDetail.statusReason AND the container reason both set to the fixed string "This emulator does not run containers, so the job's container was never started". No job is ever advanced to STARTING or RUNNING, no exitCode/startedAt/stoppedAt is reported, and no log stream or log event is ever created in the job definition's awslogs group. The whole string is fixed text — nothing in it comes from the request or from state.
Why: every observable output of Batch is wrong or absent. A client that submits work and waits for SUCCEEDED waits for a status that can never arrive; a client that tails the job's awslogs group gets no stream and no bytes; and the diagnosis it is handed is prose about the emulator, which is not a value AWS's statusReason can take, so a client matching the documented MISCONFIGURATION:*/CAPACITY:* reasons matches nothing. Timeout, memory-limit, terminate, maxVcpus-queueing and retry-attempt semantics are all unreachable because the container never starts.
Fix: the job placement/lifecycle state machine in the batch crate (advance a placed job through STARTING/RUNNING to a real terminal status, record the attempt and its exit code) and the awslogs wiring that must create the derived stream in the configured CloudWatch Logs group and deliver the container's stdout to it.
Traces: batch__logs.batch-attempt-timeout-kills-container-before-completion-marker, batch__logs.batch-awslogs-stream-prefix-derives-stream-name-from-prefix-and-ecs-task-id, batch__logs.batch-container-memory-limit-kills-job-before-completion-marker, batch__logs.batch-job-stdout-matches-computed-output, batch__logs.batch-maxvcpus-cap-holds-second-job-runnable-then-runs-it, batch__logs.batch-retry-attempt-number-visible-to-container-and-second-attempt-succeeds, batch__logs.batch-sequential-array-child-failure-leaves-remaining-children-blocked, batch__logs.batch-terminate-running-job-stops-container-before-completion-marker.

Cause 2 of 2 — an array job's children all end FAILED and the parent reports NO statusReason at all, so a size-N array job can never succeed and its children are never enumerable as SUCCEEDED.
AWS: Smithy com.amazonaws.batch#ArrayPropertiesDetail.statusSummary is "A summary of the number of array job children in each available job status" and is returned for the parent; .size is the array size and .index the child's position. For a size-3 array whose children all exit 0, the parent ends SUCCEEDED with statusSummary SUCCEEDED=3 and FAILED=0, ListJobs(arrayJobId=...) enumerates the 3 children, each child exports its own AWS_BATCH_JOB_ARRAY_INDEX into its container, and each child writes its own awslogs stream. A parent that does end FAILED carries a statusReason, because statusReason is the only diagnosis member JobDetail has.
Emulator: the parent ends FAILED with arrayProperties.statusSummary {'SUCCEEDED': 0, 'FAILED': 3, 'RUNNABLE': 0, 'RUNNING': 0, 'PENDING': 0, 'STARTING': 0, 'SUBMITTED': 0} and size 3 — every child failed — and the parent's statusReason is absent (None). So the array path diverges twice over: the children cannot run (cause 1 applies to each child), and unlike the single-job path the parent's terminal failure carries no reason at all. The child-index check never finishes at all, because it waits for statusSummary SUCCEEDED == size, which this path can never reach.
Why: a client running a fan-out array job sees a whole array fail and is given nothing to diagnose it with: no parent statusReason, no per-index output, and no per-child log stream. Sequential (index-ordered) execution and the "a failed child blocks the remaining children" contract are unobservable.
Fix: the array-parent aggregation in the batch crate's job state machine (propagate a reason onto the parent's statusReason when children fail) together with the child placement path from cause 1.
Traces: batch__logs.batch-sequential-array-children-run-one-at-a-time-in-index-order, batch__logs.batch-array-child-index-drives-distinct-stdout.
