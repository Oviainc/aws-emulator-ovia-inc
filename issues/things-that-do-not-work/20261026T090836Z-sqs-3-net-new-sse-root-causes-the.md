# sqs: 3 net-new SSE root causes — the both-SSE-modes refusal message is emulator-authored, an explicit Deny in a CMK key policy is never applied to the account's own credential, and a CFN-created KMS key is unresolvable so SendMessage answers KMS.NotFoundException

## Operation
SendMessage

## Description
Three independent net-new root causes in the SQS server-side-encryption surface, all grounded in failing behavioral checks the replay report marked neither ALREADY FILED nor OWNED. None is covered by the open sqs issues: 20261025T225310Z-sqs-5-net-new-behavioral-root-causes-sendmessagebatch.md and 20261026T013602Z-sqs-4-net-new-behavioral-root-causes-sendmessage.md claim other refusal-message templates (tags, MaxResults, batch entry codes, MessageSystemAttributes) and never touch SSE; 20261025T065401Z-sqs-queue-resource-policies-are-stored-but-never.md claims the QUEUE resource policy, not the KMS key policy; 20261025T055445Z-kms-sns-sqs-sns-sqs-delivery-ignores-the-destination-queue-s.md claims the SNS->SQS delivery path, not a direct caller's SendMessage/ReceiveMessage. Fix all three before submitting.

=== Cause 1 of 3: the "both SSE modes at once" refusal carries an emulator-authored message ===
AWS: Smithy models InvalidAttributeName on both CreateQueue and SetQueueAttributes (errorKind client, HTTP 400, httpErrorDefaulted); the message text is not in the model, so this is recorded behavior only. Recorded against real SQS: a request naming BOTH SqsManagedSseEnabled="true" and KmsMasterKeyId is refused HTTP 400 / InvalidAttributeName with the message "You can use one type of server-side encryption (SSE) at one time. You can either enable KMS SSE or SQS SSE." That sentence is entirely FIXED text — it contains no attribute name, key id, queue name or other value taken from the request or from state. A refused CreateQueue creates no queue (a following GetQueueUrl answers AWS.SimpleQueueService.NonExistentQueue) and a refused SetQueueAttributes leaves the queue's encryption unchanged; both of those halves are already correct in the emulator.
Emulator: the same refusal is answered with 'You can specify either KmsMasterKeyId or SqsManagedSseEnabled, but not both.' — the emulator's own sentence, built by interpolating the two attribute-name constants. The HTTP status and the InvalidAttributeName code are correct; only the message diverges.
Why: a client that distinguishes the SSE-exclusivity refusal from the other InvalidAttributeName causes (an unknown attribute name, an attribute not valid for the queue type) can only do so on the message, because they all share one code. IaC drift tooling and test harnesses that assert the documented sentence do not match, and an operator reading the emulator's text is told a different rule than the one AWS states.
Fix: the refusal message in the SQS state module's encryption component — the message produced for a request that names both encryption options must be AWS's fixed sentence rather than one interpolated from the attribute-name constants. The same helper serves CreateQueue and SetQueueAttributes, so one fix covers both.
Traces: services/service-com-amazonaws-sqs-amazonsqs/src/state/encryption.rs lines 177-192 (fn encryption_choice_refusal; the format! at lines 187-190 builds the diverging text). Failing check: sqs.sse-sqs-is-the-default-and-exclusive-with-sse-kms.

=== Cause 2 of 3: an explicit Deny in a CMK key policy is never applied to the account's own credential, so SendMessage/ReceiveMessage on an SSE-KMS queue are never refused ===
AWS: Smithy models KmsAccessDenied on SendMessage, SendMessageBatch and ReceiveMessage with awsQueryError code "KMS.AccessDeniedException" and HTTP 400 (alongside KmsDisabled, KmsInvalidState, KmsInvalidKeyUsage, KmsNotFound, KmsThrottled, KmsOptInRequired). KMS's documented policy-evaluation rule is that an explicit Deny in a key policy overrides every Allow and applies to EVERY principal the statement matches, including the account root — a key policy statement with Effect "Deny", Principal "*" and Action ["kms:GenerateDataKey","kms:Decrypt"] therefore denies the key's own account. Recorded behavior: SendMessage to a queue whose KmsMasterKeyId names such a key is refused HTTP 400 with code KMS.AccessDeniedException and KMS's own relayed sentence (fixed text "User: <caller> is not authorized to perform: <kms action> on resource: <key arn> ..." with the metadata block "(Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <uuid>; Proxy: null)"); the variable parts are the caller ARN, the kms action, the key ARN and the per-request id, and nothing is enqueued. Removing the Deny from the same key makes the identical call on the identical queue succeed.
Emulator: the decision short-circuits before the key policy is read at all. In the SQS encryption component's withheld_by, a caller identified as the account's own published credential (or one with an unreadable policy attachment) returns None — "allowed" — ahead of any resource_decision over the key policy. So a queue on a customer managed key whose policy explicitly Denies kms:GenerateDataKey still accepts SendMessage with a 200 and enqueues the message: the check polls for a refusal for its full 60s budget and never observes one (the suite reports the 60s cap). The exemption is only defensible for a caller about whom no document exists; an explicit Deny in the key's OWN policy is evidence that does exist and that AWS applies to the account root, so skipping the resource-policy evaluation for this caller class is the divergence. The same path governs the receive side (kms:Decrypt before handing a message over).
Why: this is a security-relevant bypass in the direction that hides risk. A key policy's Deny is the standard way to quarantine a CMK or to prove a blast-radius containment, and an emulator that accepts every send and receive reports the containment as ineffective-but-silent: a test that asserts "traffic stops when the key is denied" passes while the emulator in fact kept accepting and storing the traffic. Clients that branch on KMS.AccessDeniedException (back off, alarm, route to a fallback queue) never take that branch.
Fix: the KMS access decision in the SQS state module's encryption component — the account-credential/unreadable-attachment exemption must not skip evaluation of the key's own resource policy; an explicit Deny stated there has to refuse, with the existing relayed KMS.AccessDeniedException channel, before the message plane is touched on both the send and the receive path.
Traces: services/service-com-amazonaws-sqs-amazonsqs/src/state/encryption.rs lines 445-491 (fn withheld_by; the early return at lines 456-458 precedes the iam::resource_decision over key.policy at line 459) reached from authorize_master_key (lines 317-441) via authorize_queue_key (lines 279-303). Failing checks: sqs.kms-key-permission-gates-send-message (the primary grounding: its poll for a KMS refusal on an explicitly-denied key never sees one), sqs.sse-kms-consumer-without-decrypt-drives-message-to-dlq (exercises the same authorize path for kms:Decrypt on the receive side; note its terminal assertion ALSO needs the dead-letter move that 20261025T065401Z-sqs-never-redrives-to-a-dead-letter-queue.md owns, so re-replay it after both are fixed).

=== Cause 3 of 3: a KMS key created through CloudFormation is not resolvable by KMS, so SendMessage to a queue keyed by it is refused KMS.NotFoundException ===
AWS: Smithy models KmsNotFound on SendMessage with awsQueryError code "KMS.NotFoundException" and HTTP 400 — the refusal for a KmsMasterKeyId that names no key. On real AWS this path is NOT taken for a key the same stack created: AWS::KMS::Key's physical resource id is the key's own key id and Fn::GetAtt "Arn" yields that key's real ARN, so a queue whose KmsMasterKeyId is that GetAtt value sends and receives normally, and messages written before an SSE-SQS -> SSE-KMS update stay readable after it.
Emulator: after the stack update puts the CFN-created key's ARN on the queue, SendMessage is refused HTTP 400 / KMS.NotFoundException with the relayed message "Key '<arn>' does not exist (Service: AWSKMS; Status Code: 400; Error Code: NotFoundException; Request ID: <uuid>; Proxy: null)". The ARN in that refusal has a CloudFormation physical-resource-id in its key-id position (the "<stack-name>-<logical-id>-<suffix>" shape) rather than a KMS key identifier, and KMS's own store resolves it to KeyRef::NotFound. Hypothesis: CloudFormation's AWS::KMS::Key resource provider mints a generic physical id instead of creating a key in the KMS store and adopting its key id, so GetAtt "Arn" composes an ARN no key answers to. The code, status and message shape SQS relays are all correct — it is the key that does not exist.
Why: every stack that encrypts a queue with a key it declares itself (the canonical SSE-KMS template) is dead on the data plane: the queue reads back the expected KmsMasterKeyId, so a control-plane/drift check passes, and then every producer's SendMessage is refused. A client cannot work around it, because the key id it was handed is the only one the stack exports.
Fix: the AWS::KMS::Key resource provider in the CloudFormation resource surface must create the key in the KMS service's own store and use that key's identifier as the resource's physical id, so Fn::GetAtt "Arn" resolves through the same lookup SQS's authorize_master_key uses. (If the key IS created, the defect is instead in the physical-id/ARN it exports; either way the fix is in that provider, not in SQS, whose relay of KMS's NotFoundException is faithful.) Not claimed by 20261025T015306Z-cloudformation-cannot-deploy-large-parts-of-the-resource.md, which lists GuardHook/LambdaHook, AWS::IoT::Authorizer and TemplateURL/change-set gaps.
Traces: resolution path services/service-com-amazonaws-sqs-amazonsqs/src/state/encryption.rs lines 335-378 (kms_store::resolve -> KeyRef::NotFound -> KeyRefusal::NotFound). Failing check: sqs.deploy-cfn-encryption-update-keeps-earlier-messages-readable.
