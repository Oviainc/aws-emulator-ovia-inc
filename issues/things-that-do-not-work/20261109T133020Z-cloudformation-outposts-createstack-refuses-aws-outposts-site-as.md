# cloudformation__outposts: CreateStack refuses AWS::Outposts::Site as an unrecognized resource type, so no Outposts site can be deployed or rejected by a template

> _Note: this issue was identified against the code base at commit `f1d315614d2491eea3b7c6e4236ba64fe2dea133`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause in the CloudFormation emulator's template resource-type registry, grounded in the two failing behavioral checks listed under the cloudformation__outposts heading. Both fail on the very first call (CreateStack) with the identical refusal, so nothing downstream of template validation is exercised in either check.

No open issue covers AWS::Outposts::Site. The open outposts issues are all about the Outposts control plane itself (20261024T020944Z-outposts-getoutpostbillinginformation-stub.md, 20261024T172832Z-outposts-listassetinstances-wrong-behavior.md, 20261028T100620Z-outposts-createoutpost-wrong-behavior.md, 20261028T213649Z-outposts-updateoutpost-validation.md, 20261029T191039Z-outposts-lifecycle-and-precondition-gates-diverge-across-capacity.md, 20261029T191039Z-outposts-success-responses-omit-server-set-fields-and.md, 20261104T094407Z-outposts-catalog-reads-publish-a-synthesized-hardware-catalog.md), none of them about CloudFormation. The many open "Unrecognized resource types" issues name other types (AWS::Rbin::Rule, AWS::MWAA::Environment, AWS::MediaTailor::*, AWS::ImageBuilder::*, AWS::NeptuneGraph::*, AWS::IoTSiteWise::*, AWS::DeviceFarm::*, AWS::Omics::*, ...); none registers AWS::Outposts::Site.

=== Cause 1 of 1: the template resource-type registry does not recognize AWS::Outposts::Site, so every Outposts site template is refused at template validation ===

AWS:      recorded behavior only for the registry itself — CloudFormation's Smithy model carries no resource-type list, the set of supported types is the service's own data. AWS::Outposts::Site is a supported CloudFormation resource type. Its Properties are Name, Description, Notes, OperatingAddress, ShippingAddress, RackPhysicalProperties and Tags; Ref returns the site ARN and Fn::GetAtt publishes SiteId and SiteArn. A CreateStack whose template declares one is ACCEPTED: the call answers HTTP 200 with a StackId and the stack settles on its own terms. The refusal "Template format error: Unrecognized resource types: [<types>]" (ValidationError, HTTP 400) — fixed text "Template format error: Unrecognized resource types: [" ... "]", with the bracketed list taken verbatim from the submitted template — is what AWS reserves for types it genuinely does not support, and AWS::Outposts::Site is not one of them.
          The backing control plane is modelled and served: Smithy com.amazonaws.outposts CreateSite (POST /sites; Name required, OperatingAddress/ShippingAddress of shape Address, RackPhysicalProperties, Tags), GetSite (GET /sites/{SiteId}), GetSiteAddress (GET /sites/{SiteId}/address?AddressType=...) and ListSites (GET /sites, paginated on NextToken/Sites). The Site shape carries SiteId, SiteArn, Name, Description, Tags, OperatingAddressCountryCode, OperatingAddressStateOrRegion, OperatingAddressCity and RackPhysicalProperties, which is exactly the read-back surface both checks assert.
          Downstream of the registry, the two checks assert further AWS contracts this refusal makes unreachable. (a) Happy path: the stack reaches CREATE_COMPLETE; Ref equals Fn::GetAtt SiteArn and equals the SiteArn that outposts ListSites/GetSite report for the declared Name; the Site stack resource's PhysicalResourceId equals that same ARN; GetSite echoes Name, Description, the operating address's CountryCode/StateOrRegion/City and every RackPhysicalProperties member from the template; GetSiteAddress returns the full OPERATING_ADDRESS and SHIPPING_ADDRESS as declared; the site's Tags are the template tag plus the propagated stack tag with CloudFormation's aws:* tags excluded; after DeleteStack the site is gone, cf DescribeStacks answers ValidationError "Stack with id <name> does not exist" (fixed text "Stack with id " ... " does not exist", name from the request) and outposts GetSite answers NotFoundException (Smithy com.amazonaws.outposts#NotFoundException, HTTP 404) with message "siteId=<id>" — fixed text "siteId=", the id taken from the request. (b) Negative class: an OperatingAddress.CountryCode of three letters violates Address.CountryCode's Smithy constraints (@length min 2 max 2, @pattern ^[A-Z]{2}$) and is caught by CloudFormation's own pre-deployment property validation, not by the Outposts handler: CreateStack is still ACCEPTED, the stack settles ROLLBACK_COMPLETE, no Site resource exists under the rolled-back stack, no site carries the rejected Name, the stack-level CREATE_FAILED reason is the fixed text "Validation failed with 2 error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.", and DescribeEvents emits exactly two EventType=VALIDATION_ERROR rows for LogicalResourceId "Site" with ValidationName PROPERTY_VALIDATION, ValidationStatus FAILED, ValidationFailureMode FAIL and ValidationPath "/Resources/Site/Properties/OperatingAddress/CountryCode" — one reason "#/OperatingAddress/CountryCode: expected maxLength: 2, actual: 3" and one "Property value [USA] does not match pattern: ^[A-Z]{2}$". In those reasons the fixed text is "#/<property path>: expected maxLength: ", ", actual: " and "Property value [", "] does not match pattern: "; the limit (2), the actual length (3), the offending value and the pattern are variable parts taken from the schema and the submitted template.
Emulator: CreateStack is refused outright with HTTP 400 ValidationError and the message "Template format error: Unrecognized resource types: [AWS::Outposts::Site]". It is the only resource type in either template, so the refusal happens before any resource is created, no StackId is ever issued, and neither the round-trip contract nor the property-validation/rollback contract above is reached at all.
Why:      no Outposts site can be provisioned as infrastructure-as-code against this emulator. A site is the prerequisite for every Outpost — racks, Outposts, capacity tasks and S3-on-Outposts all hang off a site id — so a client's whole Outposts estate template is rejected at submit time with a ValidationError that tells the author their template is malformed. There is no recovery path: the failure is template validation, so there is no StackId to poll, no stack event, no partial stack and nothing to roll back or delete. The type's Ref/GetAtt contract (site ARN, SiteId) becomes unreachable, and the negative class is hidden entirely: a template with a malformed ISO country code must be accepted and then rolled back with two PROPERTY_VALIDATION rows naming the length and the pattern, and instead it is refused for a completely unrelated reason, so a client cannot distinguish a bad property value from an unsupported type.
Fix:      CloudFormation's template resource-type registry and the provisioning handler behind it, in the cloudformation service crate: register AWS::Outposts::Site with its property schema (including Address.CountryCode's maxLength 2 and ^[A-Z]{2}$ pattern so pre-deployment PROPERTY_VALIDATION produces the two DescribeEvents VALIDATION_ERROR rows and the stack-level "Validation failed with 2 error(s). ..." reason), its Ref (the site ARN) and its GetAtt attributes (SiteId, SiteArn), and back its create/delete lifecycle with the Outposts state the outposts crate already owns (CreateSite / GetSite / GetSiteAddress / ListSites), propagating the stack's tags onto the site and deleting the site on DeleteStack so GetSite then answers NotFoundException "siteId=<id>". The "Unrecognized resource types" refusal path itself is correct and must stay for types AWS really does not support.
Traces:   cloudformation__outposts.deploy-outposts-site-round-trip-and-delete, cloudformation__outposts.deploy-outposts-site-invalid-country-code-rejected-and-rolled-back.
