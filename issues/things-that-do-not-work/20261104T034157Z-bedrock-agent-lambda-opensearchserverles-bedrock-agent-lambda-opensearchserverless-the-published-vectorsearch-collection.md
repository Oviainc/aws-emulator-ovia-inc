=== Cause 1 of 1: the collection endpoint published for a VECTORSEARCH collection serves the AWS-JSON RPC dispatcher, not the OpenSearch REST data plane, and therefore also enforces neither the network policy nor the data access policy on data-plane requests ===
AWS: recorded behavior only for the collection data plane — the opensearchserverless Smithy model covers only the control plane (BatchGetCollection output collectionDetails[] publishes the collection endpoint; errors InternalServerException 500 / ValidationException 400), while a collection's data plane is the unmodeled OpenSearch REST API. Smithy consulted on the Bedrock side: bedrock-agent CreateKnowledgeBase (PUT /knowledgebases/, 202; errors ValidationException 400 / AccessDeniedException 403 / ConflictException 409 / ThrottlingException 429 / ServiceQuotaExceededException 402) requires an OPENSEARCH_SERVERLESS storageConfiguration naming collectionArn + vectorIndexName + fieldMapping, so the index must exist in the collection first. Recorded behavior: (a) a SigV4-'aoss'-signed `PUT https://<collectionEndpoint>/<indexName>` with a knn_vector mapping — no x-amz-target header, because OpenSearch REST has no RPC target — is accepted 200/201 when a data access policy grants the caller; (b) with NO matching network policy the same signed request is refused by the endpoint with an HTTP 401 (opensearch-py AuthenticationException); (c) with no data-access grant for the knowledge base role, bedrock-agent CreateKnowledgeBase refuses the storage configuration with 400 ValidationException.
Emulator: every OpenSearch REST request to the published endpoint is answered HTTP 400 with body {"__type":"SerializationException","message":"missing required header `x-amz-target`"} — all fixed front-door text, with no part derived from the request, showing the host never reached a data-plane handler. Consequently the negative cases are wrong too: the missing-network-policy case gets that 400 instead of a 401 (check asserts: 'expected opensearchpy AuthenticationException(401) without a matching network policy, got RequestError(400, {"__type":"SerializationException","message":"missing required header `x-amz-target`"}, None)'), and the missing-data-access and missing-encryption-policy walks never get far enough to observe their refusal.
Why: a client cannot create the vector index a Bedrock knowledge base requires, so nothing beyond it is observable — collection-ARN resolution into a knowledge base, fieldMapping honouring, an ingestion job actually writing vectors into the collection, a Lambda calling RetrieveAndGenerate against an ingested knowledge base, and the CloudFormation-deployed stack variant all stop at the index create. Equally important, the data-plane permission boundary reports the wrong refusal: a caller with no network policy sees a serialization error instead of a 401 authentication failure, so an application cannot distinguish a missing policy from a malformed request.
Fix: the opensearchserverless collection data plane plus the emulator's host/endpoint routing table — route the published collection endpoint host to an OpenSearch REST handler (index create/get/delete/count, document index and search) that authorises SigV4 `aoss` requests against the collection's network policy (401 when no policy admits the caller's network path) and its data access policy (403 when the principal is not granted), instead of letting the host fall through to the AWS-JSON x-amz-target dispatcher.
Traces: direct 400s — bedrock-agent__lambda__opensearchserverless.bedrock-kb-ingestion-job-writes-to-collection-positive ('PUT /<index> -> 400: {"__type":"SerializationException","message":"missing required header `x-amz-target`"}'), .bedrock-kb-opensearchserverless-collection-arn-resolution-positive, .bedrock-kb-opensearchserverless-encryption-policy-missing-negative, .bedrock-kb-opensearchserverless-field-mapping-positive ('could not create vector index after retries: RequestError(400, ...)'), .deploy-stack-missing-opensearchserverless-data-access-negative ('vector index creation failed: 400 {...}'); wrong refusal class — .bedrock-kb-opensearchserverless-network-policy-missing-negative; and two reported as 'Check timed out after 60.0s' because the same failing PUT is retried in a sleep loop before any assertion — .bedrock-kb-opensearchserverless-data-access-policy-missing-negative and .lambda-bedrock-agent-retrieve-and-generate-positive (Hypothesis for these two: the report gives only the timeout, and the first data-plane action in both is the same retrying index-create helper).
