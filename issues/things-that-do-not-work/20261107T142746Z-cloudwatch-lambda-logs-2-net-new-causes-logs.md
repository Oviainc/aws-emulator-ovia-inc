# cloudwatch__lambda__logs: 2 net-new causes — Logs Insights GetQueryResults answers 501 NotImplemented, and a metric filter's matching log line never produces a CloudWatch datapoint

> _Note: this issue was identified against the code base at commit `117dc8980bd60242192cfb0322b38a4da9ec7838`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetQueryResults

## Description
Two distinct root causes, both reached by behavioral checks the suite lists under `### cloudwatch__lambda__logs` and marks neither ALREADY FILED nor OWNED.

Cause 1 of 2: GetQueryResults is a scaffold stub, so no CloudWatch Logs Insights query can ever be read.
Failing checks: cloudwatch__lambda__logs.metrics-from-logs-insights-parse-named-capture-agrees-with-extracted-metric, cloudwatch__lambda__logs.metrics-from-logs-insights-stats-by-agrees-with-dimensioned-metric-filter, cloudwatch__lambda__logs.metrics-from-logs-no-matching-line-emits-no-datapoint-and-an-empty-complete-query, cloudwatch__lambda__logs.metrics-from-logs-regex-pattern-agrees-across-metric-filter-insights-and-filter-log-events.
AWS: Smithy (com-amazonaws-cloudwatchlogs-logs-20140328, GetQueryResults): input `queryId` (QueryId, @length 1..256, required), `nextToken` (0..1024), `maxItems` (@range 0..10000); output `status` (QueryStatus, one of Scheduled|Running|Complete|Failed|Cancelled|Timeout|Unknown), `results` (QueryResults — a list of rows, each a list of field/value pairs), `statistics` (QueryStatistics: recordsMatched, recordsScanned, bytesScanned, resultCount, ...), `queryLanguage`, `nextToken`; modeled errors InvalidParameterException (HTTP 400), ResourceNotFoundException (HTTP 400), ServiceUnavailableException (HTTP 500). For a queryId that StartQuery returned, AWS answers HTTP 200 and, once the query finishes, `status` "Complete" with the rows the query selected (an empty `results` list when nothing matched); an unknown/expired queryId is refused ResourceNotFoundException. The model declares no NotImplemented condition, so 501 is not a response AWS can give.
Emulator: every call is refused with HTTP 501 and botocore reports `An error occurred (NotImplemented) when calling the GetQueryResults operation: operation GetQueryResults is scaffolded but not implemented in this emulator`. Of that message only the error code `NotImplemented` and the operation name come from the request; the rest is emulator-authored text with no AWS counterpart.
Why: the standard Insights consumer loop — StartQuery, then poll GetQueryResults until status is Complete — raises a client error on its first poll, so no client can read an Insights result at all, and no workload can cross-check an Insights `stats ... by`/`parse` aggregation against the metric filter or FilterLogEvents view of the same lines.
Fix: implement the handler body of this operation (the logs crate's GetQueryResults operation handler, which currently returns the scaffold's not_implemented error), resolving the queryId against the query state StartQuery records and serializing results/statistics/status per the model. The pre-existing open issue 20261025T192833Z-logs-getqueryresults-stub.md files the same stub under the service token `logs`; the suite does not record it as owning these four checks, so they are filed here and that issue is named rather than duplicated. Related open issues that do NOT cover this: 20261025T192833Z-logs-cloudwatch-logs-7-net-new-root-causes-startquery.md, 20261102T090835Z-logs-cloudwatch-logs-insights-query-refusal-messages-diverge-missing.md.
Traces: the four check ids above; stub marker and refusal site at services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/get_query_results.rs lines 4-6 (SCAFFOLDED marker) and line 198 (`Err(crate::scaffolded::Scaffolded::not_implemented("GetQueryResults"))`).

Cause 2 of 2: a metric filter fed a MATCHING log line publishes no CloudWatch datapoint, so the negative-delivery check never reaches a verdict.
Failing check: cloudwatch__lambda__logs.logs-metric-filter-non-matching-pattern-no-metric-negative.
AWS: PutMetricFilter on a log group with `filterPattern` '"ERROR"' and one metricTransformation {metricName, metricNamespace, metricValue "1"} makes CloudWatch Logs publish one datapoint of value 1 into that namespace/metric for every ingested log event that matches the pattern, and publish nothing for an event that does not match. A GetMetricStatistics Sum over a window containing the matching line therefore returns >= 1, while the same read before any matching line returns no datapoint. The transformation contract is modeled (PutMetricFilter.metricTransformations metricName/metricNamespace/metricValue, filterPattern); the propagation delay is recorded behavior only — in the recording both polls resolve well inside the check's own 90s/180s budgets.
Emulator: neither arm ever resolves. The check publishes a non-matching line, polls for the absence of the datapoint, then publishes a matching line and polls for the positive control; it is killed with `Check timed out after 60.0s` before either poll converges, so the emulator produced no datapoint for the matching line within the harness budget. Hypothesis: the extraction is not wired — either the Lambda's stdout never reaches /aws/lambda/<function> or the metric filter is stored but never evaluated against ingested events into CloudWatch metric state.
Why: a client that builds alarms or dashboards on log-derived metrics sees an empty series forever, and cannot distinguish "my pattern did not match" (a real AWS outcome a client must be able to rely on) from "extraction does not run" — every negative-delivery assertion over log metrics is inconclusive.
Fix: the logs crate's metric-filter evaluation on the log-event ingestion path (PutMetricFilter's stored transformations applied at PutLogEvents time, publishing into CloudWatch's metric state), plus the Lambda stdout -> log group delivery it depends on. Adjacent open issues describe the same family but are not recorded as owning this check: 20261024T150703Z-logs-cloudwatch-logs-metric-filters-emit-no-cloudwatch-metric.md and 20261105T111951Z-cloudwatch-lambda-logs-5-net-new-root-causes.md.
Traces: cloudwatch__lambda__logs.logs-metric-filter-non-matching-pattern-no-metric-negative (suite report: `Error: Check timed out after 60.0s`).

## Evidence
Cause 1 — expected: HTTP 200 from GetQueryResults for a StartQuery-issued queryId, with `status` eventually "Complete", `results` carrying the selected rows (empty list when nothing matched) and `statistics` populated; or a modeled refusal (InvalidParameterException / ResourceNotFoundException, HTTP 400). Actual: HTTP 501, error code `NotImplemented`, message "operation GetQueryResults is scaffolded but not implemented in this emulator" — raised identically in all four checks:
  botocore.exceptions.ClientError: An error occurred (NotImplemented) when calling the GetQueryResults operation: operation GetQueryResults is scaffolded but not implemented in this emulator
Source of the refusal: services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/get_query_results.rs:198 returns Scaffolded::not_implemented("GetQueryResults"); the file still carries the `//! SCAFFOLDED, NOT IMPLEMENTED:` marker on line 4.

Cause 2 — expected: after PutMetricFilter(filterPattern='"ERROR"', metricTransformations=[{metricName, metricNamespace, metricValue "1"}]), a log line containing ERROR yields a GetMetricStatistics Sum >= 1 for that namespace/metric (the check allows 180s), and a line without ERROR yields no datapoint. Actual: no datapoint for either arm; the check is terminated with `Check timed out after 60.0s`, i.e. the emulator never published the positive-control datapoint and the preceding absence is therefore unverifiable (the check itself states: "positive-control metric <namespace>/<metricName> did not appear ... so the earlier absence is inconclusive").

## Steps to Reproduce
Cause 1: create a log group with some events, call logs.StartQuery(logGroupName=<group>, startTime/endTime over the events, queryString='parse @message /XFER (?<user>[a-z]+) (?<nbytes>[0-9]+)/ | stats sum(nbytes) as total, count(*) as n by user'), take the returned queryId and call logs.GetQueryResults(queryId=<that id>). AWS answers 200 and converges to status Complete with the aggregated rows; the emulator answers 501 NotImplemented. Replay: cloudwatch__lambda__logs.metrics-from-logs-insights-parse-named-capture-agrees-with-extracted-metric (and the three sibling insights/metric-filter checks listed in trace_ids).

Cause 2: create an IAM role trusting lambda.amazonaws.com with AWSLambdaBasicExecutionRole, create a python3.12 function whose handler prints event["message"], invoke it once to materialise /aws/lambda/<fn>, then logs.PutMetricFilter(logGroupName='/aws/lambda/<fn>', filterName=<name>, filterPattern='"ERROR"', metricTransformations=[{metricName:'ErrorLineCount', metricNamespace:<ns>, metricValue:'1'}]). Invoke with {"message": "INFO all good, nothing to see here"} and poll cloudwatch.GetMetricStatistics(Namespace=<ns>, MetricName='ErrorLineCount', Statistics=['Sum']) — expect no datapoint. Then invoke with {"message": "ERROR something failed"} and poll the same read — AWS returns Sum >= 1; the emulator returns nothing and the check is killed at 60s. Replay: cloudwatch__lambda__logs.logs-metric-filter-non-matching-pattern-no-metric-negative.
