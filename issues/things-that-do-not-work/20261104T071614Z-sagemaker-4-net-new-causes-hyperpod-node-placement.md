# sagemaker: 4 net-new causes — HyperPod node Placement is never reported, BatchAddClusterNodes ignores the account instance quota, CreateDomain 501s, and a CFN-deployed Domain's DomainId is the domain name

> _Note: this issue was identified against the code base at commit `7bce35011e06a27791111295606361de5e667ce7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeClusterNode, BatchAddClusterNodes, CreateDomain, CloudFormation AWS::SageMaker::Domain

## Description
Four independent root causes in the emulated SageMaker control plane, all grounded in failing behavioral checks the suite report lists under `### sagemaker`. They are numbered; each must be closed before this issue is submitted.

=== Cause 1 of 4: DescribeClusterNode never reports NodeDetails.Placement for a node CreateCluster provisioned ===
AWS: Smithy — DescribeClusterNode output `NodeDetails` (ClusterNodeDetails) **required**; member `Placement` targets `ClusterInstancePlacement` { `AvailabilityZone` (pattern ^[a-z]{2}-[a-z]+-\d[a-z]$), `AvailabilityZoneId` (pattern ^[a-z]{3,5}\d-az\d$) }, documented as "The placement details of the SageMaker HyperPod cluster node". A HyperPod node is launched into a subnet of its instance group's VpcConfig, so AWS reports the zone that subnet lives in — the zone is a property of the provisioned node, not of the request that read it. The same zone is what `BatchAddClusterNodes`'s `NodeAdditionResult.AvailabilityZones` reports.
Emulator: `Placement` is omitted entirely, so a client reading `["NodeDetails"]["Placement"]` gets `KeyError: 'Placement'`. The cause is in state: nodes minted for a cluster's declared instance groups are stored with `availability_zone: None` ("A group's zones follow from the subnets of its VPC configuration, which this emulator does not resolve"), and the reader maps that `None` to an absent `Placement` member rather than resolving the group's subnet. The `Successful` entries of BatchAddClusterNodes carry no `AvailabilityZones` for the same reason (visible in the Cause-2 evidence below).
Why: a client cannot learn where a HyperPod node runs. Anything that must co-locate a resource with a node — an EBS volume for AttachClusterNodeVolume must be created in the node's AZ — has no zone to use, and a required output member being absent breaks typed and untyped SDK consumers alike.
Fix: the DescribeClusterNode handler's projection of `ClusterNodeDetails` plus the cluster-node state that provisions a node, which must resolve the instance group's VpcConfig subnet to an Availability Zone (and its AZ id) at provisioning time so every reader reports the same placement.
Traces: sagemaker.attach-cluster-node-volume-nonexistent-node-rejected, sagemaker.attach-cluster-node-volume-unknown-node-rejected. Code: services/service-com-amazonaws-sagemaker-sagemaker/src/ops/describe_cluster_node.rs:213-219 (placement built only when `node.availability_zone` is Some) and services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs:2626-2628 and :6488-6490 (`availability_zone: None` at provisioning).

=== Cause 2 of 4: BatchAddClusterNodes does not enforce the account-level HyperPod instance quota, and the refusal it does have is emulator-worded ===
AWS: Smithy — BatchAddClusterNodes models `ResourceLimitExceeded` (HTTP 400, "You have exceeded an SageMaker resource limit"). The bound AWS applies is the ACCOUNT-level Service Quotas limit "Total number of instances allowed across SageMaker Clusters" (sagemaker quota code L-3308CCC7) measured against the instances every live cluster in the account currently holds, so a single request for 50 extra nodes on a small account is refused and adds nothing. Recorded message template (fixed text exact; the variable parts are the account's applied quota, the account's live utilization and the request's own delta): "The account-level service limit 'Total number of instances allowed across SageMaker Clusters' is <quota> Instances, with current utilization of <usage> Instances and a request delta of <delta> Instances. Please use AWS Service Quotas to request an increase for this quota. If AWS Service Quotas is not available, contact AWS support to request an increase for this quota."
Emulator: the request succeeds with HTTP 200. `BatchAddClusterNodes(NodesToAdd=[{InstanceGroupName: "controller", IncrementTargetCountBy: 50}])` returns 50 `Successful` entries (each `{NodeLogicalId, InstanceGroupName, Status: "Pending", InstanceTypes: [...]}`, with no `AvailabilityZones`) and raises the group's TargetCount. The only bound the handler applies is a per-CLUSTER constant of 1,000 nodes — a different quota, on a different subject, with an emulator-authored message: "The service limit for nodes in cluster <cluster ARN> is 1000, with current utilization of <n> and a request delta of <n>." — which no real request in this suite can reach.
Why: a client that provisions against its real quota sees an over-quota scale-out accepted, so capacity it will never get is reported as `Pending` and the group's TargetCount is permanently inflated. Code that keys on the AWS error code/message (to back off, or to raise a quota-increase request) never runs, and the wrong wording hides which quota was hit.
Fix: the BatchAddClusterNodes handler's pre-add bound check and its `ResourceLimitExceeded` message construction, which must size the whole batch against the account-level instance quota (summed over every live cluster's instance groups' CurrentCount, excluding Deleting/Failed clusters) and refuse before any node is added, leaving TargetCount and the node list untouched.
Traces: sagemaker.batch-add-cluster-nodes-exceeding-limit-rejected, sagemaker.batch-add-cluster-nodes-exceeds-limit-blocked, sagemaker.batch-add-cluster-nodes-limit-exceeded-blocked, sagemaker.batch-add-cluster-nodes-limit-exceeded-rejected. Code: services/service-com-amazonaws-sagemaker-sagemaker/src/ops/batch_add_cluster_nodes.rs:254-274 and services/service-com-amazonaws-sagemaker-sagemaker/src/state.rs:218-219 (`CLUSTER_NODE_QUOTA = 1_000`, per cluster).

=== Cause 3 of 4: CreateDomain answers 501 NotImplemented, so no Studio domain exists and its documented input validation never runs ===
AWS: Smithy — CreateDomain is a modeled operation returning `DomainArn`, `DomainId` (pattern ^d-(-*[a-z0-9]){1,61}$) and `Url`, and modeling only `ResourceInUse` / `ResourceLimitExceeded`; `NotImplemented` is not in its error set. A malformed network identifier is refused up front with `ValidationException` (HTTP 400) naming every failing member, recorded wording (fixed text exact; the quoted values and member names come from the request): "2 validation errors detected: Value 'not-a-real-vpc-id' at 'vpcId' failed to satisfy constraint: Member must satisfy regular expression pattern: vpc-[a-z0-9]{8,}; Value '[not-a-real-subnet-id]' at 'subnetIds' failed to satisfy constraint: Member must satisfy constraint: [Member must have length less than or equal to 32, Member must have length greater than or equal to 0, Member must satisfy regular expression pattern: subnet-[a-z0-9]{8,}]". A valid request mints a server-assigned `d-…` DomainId and the domain settles to `InService`.
Emulator: CreateDomain is a scaffold stub — `services/service-com-amazonaws-sagemaker-sagemaker/src/ops/create_domain.rs` is marked "SCAFFOLDED, NOT IMPLEMENTED: this operation answers HTTP 501 NotImplemented" — so the malformed-network request comes back with error code 'NotImplemented' instead of `ValidationException`, and every domain-dependent flow (CreateUserProfile -> CreateApp -> DeleteApp) never starts: the double-delete check burns its whole budget in a bounded create-retry loop and is killed at 60 s.
Why: Studio is unusable and a client cannot distinguish "my VpcId/SubnetIds are malformed" from "this call does not exist": a negative test that expects a 400 ValidationException sees a 501, and the per-member validation text AWS returns (which tells the caller WHICH members are wrong and why) is never produced. This cause is gated by the already-open stub issue 20261029T222441Z-sagemaker-createdomain-stub.md, which names the operation and file but states none of the behaviour above; the requirements recorded here (the exact ValidationException wording for vpcId/subnetIds, the `d-…` DomainId, settling to InService) are what the implementation must satisfy, and they are also what Cause 4 depends on.
Fix: the CreateDomain handler plus its input validation and the domain store it writes (DomainId minting and the Creating -> InService settle the Describe path reads).
Traces: sagemaker.create-domain-malformed-subnet-rejected (mismatch: expected ValidationException, got 'NotImplemented'), sagemaker.delete-app-double-delete-rejected (check timed out after 60.0s inside the CreateDomain retry loop).

=== Cause 4 of 4: a CloudFormation-deployed AWS::SageMaker::Domain reports the domain NAME as its DomainId, and SageMaker holds no domain for it ===
AWS: Smithy — `DomainId` (in CreateDomain/DescribeDomain, and in CloudFormation as `!GetAtt Domain.DomainId`) is constrained to pattern ^d-(-*[a-z0-9]){1,61}$, length 0..63: it is the service-assigned identifier, never the DomainName (DomainName has its own, different pattern ^[a-zA-Z0-9](-*[a-zA-Z0-9]){0,62}$). After a stack containing AWS::SageMaker::Domain plus AWS::SageMaker::UserProfile reaches CREATE_COMPLETE, `DescribeDomain(DomainId=<that GetAtt>)` describes the domain and it settles to `InService`, and `CreatePresignedDomainUrl` for it returns an AuthorizedUrl whose redirect chain lands on that domain's own Studio host.
Emulator: the stack reaches CREATE_COMPLETE and the stack output for `!GetAtt Domain.DomainId` is the domain's NAME (a value of the form the DomainName parameter carried, e.g. "sim2real-domain-<suffix>"), not a `d-…` id. Feeding that value straight back to the same emulator is then refused by SageMaker's own input validation: HTTP 400 `ValidationException` "1 validation error detected: Value '<domain name>' at 'domainId' failed to satisfy constraint: Member must satisfy regular expression pattern: d-(-*[a-z0-9]){1,61}". So CREATE_COMPLETE is reported for a domain no SageMaker read can reach.
Why: a template that wires any resource to a Domain by `!GetAtt Domain.DomainId` — UserProfile, Space, App, or any client reading the stack output — propagates a value SageMaker rejects, so an apparently successful deployment is unusable and the failure surfaces far from its cause, as a confusing pattern-constraint error on a caller's own input.
Fix: the CloudFormation resource provider for AWS::SageMaker::Domain — it must provision the domain through the SageMaker domain store (see Cause 3), use the service-assigned `d-…` id as the resource's physical id and as the value of the `DomainId` attribute, and fail the resource rather than report CREATE_COMPLETE when no domain was created. Related but distinct open issue: 20261022T210606Z-sagemaker-cloudformation-declared-sagemaker-resources-are-never-provisioned-and.md (other SageMaker resource types); neither it nor the CreateDomain stub issue states the DomainId-attribute requirement above.
Traces: sagemaker.deploy-domain-cfn-presigned-url-works.
