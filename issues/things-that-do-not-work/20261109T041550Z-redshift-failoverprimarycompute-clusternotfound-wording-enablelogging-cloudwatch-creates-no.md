# Redshift: FailoverPrimaryCompute ClusterNotFound wording, EnableLogging(cloudwatch) creates no log groups, cluster endpoint serves no SQL and CreateIntegration never reaches a terminal refusal (4 causes)

> _Note: this issue was identified against the code base at commit `7e037278676d8663d04d150221a10f1a7428ea64`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FailoverPrimaryCompute

## Description
Four net-new root causes in the redshift (query-protocol) control plane, each grounded in failing behavioral checks the suite did not mark already-filed or owned. All four are in one service, so they are bundled here; a fixer must close all FOUR before submitting.

=== Cause 1 of 4: FailoverPrimaryCompute's ClusterNotFoundFault message uses the wrong per-operation wording ===
Failing checks: redshift.failover-primary-compute-unauthorized-blocked, redshift.failover-primary-compute-unauthorized-denied
AWS: FailoverPrimaryCompute naming a ClusterIdentifier the account does not have is refused with HTTP 404, error code ClusterNotFound (Smithy: ClusterNotFoundFault, httpError 404, awsQueryError code ClusterNotFound) and the message `Cluster not found: <ClusterIdentifier>` — fixed text `Cluster not found: ` plus the ClusterIdentifier taken verbatim from the request. This is the wording the operations that ACT on a cluster they name answer with; recorded behavior fixes the message text (the model fixes only status and code).
Emulator: answers the right status and code but the message `Cluster <ClusterIdentifier> not found.` — the DescribeClusters/DeleteCluster wording, i.e. the handler selects the wrong wording variant (`ClusterNotFoundWording::IdentifierThenNotFound` instead of `NotFoundThenIdentifier`).
Why: the refusal's fixed text is a requirement of this error class. CLI transcript tests, log scrapers and error-mapping layers that match the documented sentence diverge, and the per-operation wording difference AWS actually exhibits (act-on vs. describe) is lost — a caller cannot tell from the text which family answered.
Fix: the FailoverPrimaryCompute handler's not-found path — pick the act-on-a-named-cluster wording for its ClusterNotFoundFault message instead of the read wording.
Traces: redshift.failover-primary-compute-unauthorized-blocked, redshift.failover-primary-compute-unauthorized-denied (both checks' positive control reached business logic, i.e. the operation itself is served; only the message text diverges). Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/failover_primary_compute.rs (the ClusterNotFoundFault construction around line 182) and the wording enum in src/state.rs (around lines 800-896). Related open issue 20261102T105531Z-redshift-refusal-codes-and-messages-are-emulator-authored.md covers OTHER redshift refusal messages; it does not carry these checks' replay keys and the suite did not mark these failures owned, so they are filed here and that issue is named for context.

=== Cause 2 of 4: EnableLogging with LogDestinationType=cloudwatch records the configuration but creates no CloudWatch Logs log groups ===
Failing check: redshift.enable-logging-server-side-delivery-enforced
AWS: a single EnableLogging(ClusterIdentifier=<id>, LogDestinationType=cloudwatch, LogExports=[connectionlog,userlog]) call makes Redshift itself create the CloudWatch Logs log groups that back the exported log types, with NO further client action: DescribeLogGroups(logGroupNamePrefix=`/aws/redshift/cluster/<ClusterIdentifier>/`) then lists a group per exported log type, named `/aws/redshift/cluster/<ClusterIdentifier>/<logtype>` (the cluster identifier from the request and the log type from LogExports are the variable parts). Recorded behavior only: the Smithy model of EnableLogging (errors BucketNotFoundFault/ClusterNotFoundFault/InsufficientS3BucketPolicyFault/InvalidClusterStateFault/InvalidS3BucketNameFault/InvalidS3KeyPrefixFault/UnsupportedOperationFault) says nothing about the server-side log-group creation; the recording shows the groups existing after the single call.
Emulator: EnableLogging stores a ClusterLogging record and answers 200 with LoggingEnabled=true/LogDestinationType=cloudwatch (DescribeLoggingStatus reports it back), but it performs no cross-service write at all for the cloudwatch destination — the handler only resolves a BUCKET for the S3 destination and otherwise just records the request. No log group ever appears under the prefix, so the check's bounded DescribeLogGroups poll never satisfies and the check is killed at the suite's 180 s budget with no assertion reached.
Why: a client that enables cloudwatch audit-log delivery and then reads/subscribes to the log group (log-group based alarms, metric filters, subscription filters, CLI `logs tail`) finds nothing to attach to; the configuration is reported as enabled while no delivery target exists, so the emulator claims a server-side effect it never performs.
Fix: the EnableLogging handler's cloudwatch-destination branch — it must create the backing log groups in the CloudWatch Logs service (and DisableLogging's counterpart behavior) rather than only recording the destination in redshift state. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/enable_logging.rs (the destination branch, around lines 256-321, where only LOG_DESTINATION_S3 performs a cross-service resolution).
Traces: redshift.enable-logging-server-side-delivery-enforced (the EnableLogging/DescribeLoggingStatus assertions that precede the poll pass).

=== Cause 3 of 4: a CloudFormation-deployed cluster publishes an endpoint that accepts no SQL connection, so the data-plane check never completes ===
Failing check: redshift.deploy-redshift-cluster-cfn-behavioral-connectivity
AWS: a cluster created through a CloudFormation AWS::Redshift::Cluster resource reaches CREATE_COMPLETE, DescribeClusters reports ClusterStatus=available with an Endpoint{Address,Port}, and that address/port accepts a TLS PostgreSQL-wire connection authenticated with the DbUser/DbPassword GetClusterCredentials just issued; `SELECT 1` returns (1,) and a CREATE TEMP TABLE / INSERT / SELECT round-trip returns the inserted row. Recorded behavior only (the Smithy model describes the control-plane shapes, not the wire protocol).
Emulator: the check is killed at the suite's 180 s budget with no assertion reached — every stage is a bounded poll (stack status, cluster available, then a connect-retry loop with connect_timeout=15 s over a 240 s budget), so the run burns its whole budget without producing a terminal outcome. Hypothesis: the stall is the SQL connect loop — the emulator publishes a cluster Endpoint.Address/Port but serves no Redshift/PostgreSQL wire protocol on it, so every psycopg.connect attempt hangs to its connect timeout and is retried until the harness kills the check.
Why: a client treats CREATE_COMPLETE plus a published endpoint as a usable warehouse. Instead of a fast, diagnosable refusal it gets an indefinitely hanging connect, so every deploy-then-query workflow (IaC smoke tests, JDBC/psql clients, ETL jobs) stalls rather than failing, and no data-plane behavior can be exercised at all.
Fix: the cluster data plane — the endpoint a cluster publishes must either serve the SQL wire protocol or the endpoint must not be published; the GetClusterCredentials-issued credentials must authenticate against it. Component: the cluster endpoint/data-plane serving path (src/state.rs cluster_endpoint / refresh_endpoint and whatever listener backs it), not the CreateCluster control-plane handler.
Traces: redshift.deploy-redshift-cluster-cfn-behavioral-connectivity. Related open issue 20261104T045922Z-redshift-publishes-a-cluster-endpoint-but-serves-no.md describes the same missing SQL endpoint for OTHER checks; it does not carry this check's replay key and the suite did not mark this failure owned, so it is filed here and that issue is named for context.

=== Cause 4 of 4: CreateIntegration with a nonexistent target namespace answers a retryable IntegrationTargetNotFoundFault, so the error-semantics check never reaches a terminal refusal ===
Failing check: redshift.integration-error-semantics
AWS: CreateIntegration whose TargetArn is well-formed but names a namespace that was never created is refused SYNCHRONOUSLY and terminally with HTTP 400, error code InvalidParameterValue and the fixed text `You don't have access to zero-ETL integrations because the Amazon Redshift data warehouse doesn't exist or you don't have the required permissions. Check the resource policy of the data warehouse and make sure your user or role is specified as an authorized principal.` (no variable part); the mirror case, a nonexistent DynamoDB SourceArn, is refused 400 InvalidParameterValue with the corresponding source-table sentence. Recorded behavior for the classification and wording: the Smithy model does list IntegrationTargetNotFoundFault (httpError 404) on CreateIntegration, but AWS does not use it for a namespace that does not exist.
Emulator: answers IntegrationTargetNotFoundFault (404) for the absent namespace. Because that fault class means "not there yet" to a client, the check treats it as a propagation-transient and re-creates the integration on a bounded retry loop; no terminal outcome is ever produced and the check is killed at the suite's 180 s budget.
Why: the two refusals mean different things — a target-not-found is retried while an existence/permissions refusal is surfaced to the operator with remediation text. A provisioning flow therefore retries a call that can never succeed until its own timeout, instead of failing fast with the actionable message, and the operator never sees the resource-policy guidance.
Fix: the CreateIntegration target-resolution branch's error classification and message — an absent namespace must raise the query-protocol InvalidParameterValue with the data-warehouse-access text instead of IntegrationTargetNotFoundFault. Component: services/service-com-amazonaws-redshift-redshiftserviceversion20121201/src/ops/create_integration.rs (the serverless Absent arm around lines 296-310 and the provisioned arm around lines 397-409).
Traces: redshift.integration-error-semantics. Related open issue 20261104T045922Z-redshift-zero-etl-integration-refusals-and-state-machine.md describes this same classification for redshift.integration-create-delete-lifecycle; it does not carry this check's replay key and the suite did not mark this failure owned, so it is filed here and that issue is named for context.
