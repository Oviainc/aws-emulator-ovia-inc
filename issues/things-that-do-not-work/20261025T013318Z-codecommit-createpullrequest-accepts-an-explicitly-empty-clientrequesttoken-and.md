# CodeCommit: CreatePullRequest accepts an explicitly empty clientRequestToken, and DeletePullRequestApprovalRule answers 501 NotImplemented (2 causes)

> _Note: this issue was identified against the code base at commit `d6e9bd85505b2fcf81ff15dd47c3206271b87270`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePullRequest

## Description
Two net-new root causes in the codecommit crate, each grounded in a failing behavioral check the replay report left unmarked (not ALREADY FILED, not OWNED). A fixer must close BOTH before submitting.

Cause 1 of 2: CreatePullRequest accepts an explicitly empty clientRequestToken and creates the pull request, where AWS refuses the call. Failing check: codecommit.client-request-token-required-rejected.
AWS: Smithy (com.amazonaws.codecommit#CodeCommit_20150413) CreatePullRequest input member clientRequestToken targets ClientRequestToken and carries @idempotencyToken; the operation models both ClientRequestTokenRequiredException and InvalidClientRequestTokenException as client errors with httpError 400. Recorded behavior: an explicitly supplied empty string is treated as a MALFORMED token, not as an absent one — the call is refused with HTTP 400 / InvalidClientRequestTokenException and NO pull request is created (recorded message example, from the earlier filing of this check id: 'The client request token is not valid. Client request tokens must be between 1 and 256 alphanumeric characters.'). The requirement here is the status and the error code plus the absence of the effect; the message text is an example.
Emulator: the call SUCCEEDS with HTTP 200 and returns a fully populated pullRequest (pullRequestStatus 'OPEN', a pullRequestId, a revisionId, resolved source/destination/mergeBase commits), i.e. the empty token is silently treated as 'generate one for me' and a pull request is created.
Why: this is an over-permissiveness defect on an idempotency parameter. A client that passes a token it computed and that came out empty (an unset variable, a trimmed string) is told by AWS that its request is malformed and retries with a real token; against the emulator the same bug creates a real pull request, and because the token is empty the idempotency key is meaningless, so a retry creates a SECOND pull request instead of being deduplicated or refused with IdempotencyParameterMismatchException. Negative-class coverage for the whole client-request-token family is lost.
Note: open issue '20261023T072048Z-codecommit-10-behavioral-root-causes-three-operations-answer.md' carries this check id on its replay list, but only as an explicit NON-cause ('Note (NOT a net-new cause, listed so its id is re-replayed)') — at that time CreatePullRequest was an unimplemented 501 scaffold and the check never reached this assertion. CreatePullRequest now answers, so the token validation gap is observable for the first time and is recorded here as a cause.
Fix: the clientRequestToken validation in the CreatePullRequest handler of the codecommit crate (services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_pull_request.rs) — a present-but-empty token must be refused with the modeled InvalidClientRequestTokenException (400) before any pull-request state is written, rather than being normalized into a generated token.
Traces: codecommit.client-request-token-required-rejected.

Cause 2 of 2: DeletePullRequestApprovalRule is an unimplemented scaffold and answers HTTP 501 NotImplemented for every input, so neither its success path nor its template-derived refusal exists. Failing checks: codecommit.delete-template-derived-approval-rule-rejected, codecommit.delete-template-derived-pr-approval-rule-blocked.
AWS: Smithy DeletePullRequestApprovalRule takes pullRequestId (@required) and approvalRuleName (@required, ApprovalRuleName, @length min 1 max 100) and returns approvalRuleId (@required). It models CannotDeleteApprovalRuleFromTemplateException as a client error with httpError 400, documented as 'The approval rule cannot be deleted from the pull request because it was created by an approval rule template and applied to the pull request automatically.' So: deleting a rule that a repository-associated approval rule template generated is refused with HTTP 400 / CannotDeleteApprovalRuleFromTemplateException and the rule stays attached to the pull request, while deleting a rule created directly on the pull request answers HTTP 200 with approvalRuleId and the rule disappears from GetPullRequest.approvalRules. Recorded refusal message example: 'The approval rule cannot be deleted from the pull request because it was created by an approval rule template and automatically applied to the pull request.'
Emulator: the operation returns HTTP 501 with error code 'NotImplemented' ('operation DeletePullRequestApprovalRule is scaffolded but not implemented in this emulator'). Confirmed stub in the checkout: services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/delete_pull_request_approval_rule.rs line 4 carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and handle() ends in Err(crate::scaffolded::Scaffolded::not_implemented("DeletePullRequestApprovalRule")). Both checks get this far only because the rest of the chain already works: CreateApprovalRuleTemplate, AssociateApprovalRuleTemplateWithRepository, CreateCommit/CreateBranch, CreatePullRequest and GetPullRequest all succeed, and GetPullRequest correctly reports exactly one approval rule carrying originApprovalRuleTemplate.approvalRuleTemplateName — so only the delete leg is missing.
Why: 501 is not a status AWS ever produces for this operation, so a client sees a transport-level failure where AWS sends either a success or a modeled 400. Concretely, template-governed approval rules are the mechanism that makes repository-wide approval policy un-bypassable; with the delete leg absent an emulator cannot show that a template-derived rule is protected, and tooling that cleans up its own per-pull-request rules (the legal, documented case) cannot run at all.
Note: no open issue names this operation — the stub-issue set filed for this crate covers GetRepositoryTriggers, PutRepositoryTriggers, DescribeMergeConflicts, GetBlobDifferences, GetMergeConflicts, ListPullRequests, GetCommentReactions, MergeBranchesByThreeWay and UpdatePullRequestStatus, and the replay report did not mark these two checks ALREADY FILED because each check's _error() helper converts the 501 into an error-code comparison, hiding the stub from the report's detector.
Fix: implement the handler in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/delete_pull_request_approval_rule.rs (the only file to touch for this operation) against the approval-rule state the pull-request store already holds: refuse a rule whose origin is an approval rule template with CannotDeleteApprovalRuleFromTemplateException and leave it attached, delete a pull-request-local rule and answer its approvalRuleId, and remove the SCAFFOLDED marker line.
Traces: codecommit.delete-template-derived-approval-rule-rejected, codecommit.delete-template-derived-pr-approval-rule-blocked.
