# service-quotas template-operation organization gate unreachable: the emulator reports the caller as its AWS Organization's management account, so NoAvailableOrganizationException is never raised

> _Note: this issue was identified against the code base at commit `e9aa8ba1fdfe417f19b3a603b17e06ccf1308d5b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutServiceQuotaIncreaseRequestIntoTemplate

## Description
One net-new root cause in the service-quotas (com.amazonaws.servicequotas#ServiceQuotasV20190624, awsJson1_1) emulator, surfaced by 1 failing behavioral check. The check is tagged identity:standalone / phase:standalone, i.e. it was recorded against an account that belongs to NO AWS Organization, and it grades the organization-membership gate on the Service Quotas request-template operations. Against the emulator it cannot reach that gate at all, because the emulator first answers the identity probe as if the caller were its organization's management account.

Cause 1 of 1 — the account identity the emulator presents makes the template-operations organization gate unreachable, and with it the NoAvailableOrganizationException refusal path.
AWS: Service Quotas request templates are an AWS Organizations feature available only to the organization's management account, from the single template home Region. Smithy (services/service-com-amazonaws-servicequotas-servicequotasv20190624/smithy-model/com-amazonaws-servicequotas-servicequotasv20190624.json): PutServiceQuotaIncreaseRequestIntoTemplate and GetServiceQuotaIncreaseRequestFromTemplate both declare NoAvailableOrganizationException (errorKind client, httpError 403), AccessDeniedException (403), AWSServiceAccessNotEnabledException (403) and TemplatesNotAvailableInRegionException (404) — so a caller that is in no organization is refused 403/NoAvailableOrganizationException, and a member account that is not the management account is refused 403/AccessDeniedException with the fixed message 'The request was called by a member account. To make this request, you must use the organization's master account.' (entirely fixed text, no request values interpolated). For the standalone identity this check records, the probe it uses to establish that topology is organizations:DescribeOrganization, which AWS answers with 404/AWSOrganizationsNotInUseException when the caller is in no organization (Smithy: services/service-com-amazonaws-organizations-awsorganizationsv20161128/..., DescribeOrganization errors include AWSOrganizationsNotInUseException, errorKind client, httpError 404).
Emulator: DescribeOrganization SUCCEEDS and returns an Organization whose MasterAccountId is the very account sts:GetCallerIdentity reports for the same caller (the two values are equal — the concrete account id is a per-run value and is no part of the requirement). The emulator therefore presents every caller as the management account of a pre-existing organization, where the recorded standalone identity has no organization at all. The check stops there with 'this account is its AWS Organization's management account; the rejection this check proves ... does not reproduce from the management account itself', so the Service Quotas template calls are never issued and their refusal (status, error code and message) is unverified. Hypothesis: because the emulator can never be in the standalone or non-management-member topology, no code path in the service-quotas template handlers can ever emit NoAvailableOrganizationException or the AccessDeniedException member-account refusal, i.e. the template operations are reachable by any caller — the overly-permissive direction this check exists to rule out.
Why: a client that relies on AWS's topology boundary gets the opposite answer in both services. Code that probes DescribeOrganization to decide whether request templates are usable is told 'yes, you are the management account' and then proceeds down a path real AWS refuses with 403, so the standalone/member error handling (NoAvailableOrganizationException -> 'enable Organizations / use the management account', AccessDeniedException -> 'call from the master account') is never exercised and silently regresses; conversely nothing in the emulator can ever surface the standalone 404/AWSOrganizationsNotInUseException that real standalone accounts return.
Fix: the emulator's account-identity/Organizations topology state (the seeded organization the organizations DescribeOrganization handler serves, and whatever makes its MasterAccountId equal the sts caller account) must model the recorded identity — a caller in no organization — so DescribeOrganization refuses with AWSOrganizationsNotInUseException; and the service-quotas request-template handlers (PutServiceQuotaIncreaseRequestIntoTemplate, GetServiceQuotaIncreaseRequestFromTemplate, and the sibling List/Delete template operations that share the gate) must consult that topology and refuse a non-management caller with 403/NoAvailableOrganizationException (standalone) or 403/AccessDeniedException carrying AWS's fixed member-account sentence, before any template state is read or written. Unrelated non-template Service Quotas reads (the check's positive control, GetAWSDefaultServiceQuota) must keep succeeding.
