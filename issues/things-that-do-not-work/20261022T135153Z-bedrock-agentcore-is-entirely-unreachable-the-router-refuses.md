# Bedrock AgentCore is entirely unreachable: the router refuses every 'bedrock-agentcore'-signed request with AmbiguousService, and a CFN-deployed AgentCore stack publishes Outputs with no OutputValue (2 causes)

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartCodeInterpreterSession

## Description
Two independent causes, both grounded in bedrock-agentcore behavioral checks. A fixer must close BOTH before submitting.

=== Cause 1 of 2: every bedrock-agentcore request is refused by the router with AmbiguousService ===
AWS: both the AgentCore data plane and the AgentCore control plane are real, separately addressed services. Smithy (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore): service AmazonBedrockAgentCore, protocol restJson1, awsService.endpointPrefix = "bedrock-agentcore", sigv4Name = "bedrock-agentcore", arnNamespace = "bedrock-agentcore". Smithy (services/service-com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol): service AmazonBedrockAgentCoreControl, protocol restJson1, awsService.endpointPrefix = "bedrock-agentcore-control", sigv4Name = "bedrock-agentcore", arnNamespace = "bedrock-agentcore". So the two share a SIGNING name but have DISTINCT endpoint prefixes and disjoint restJson1 route spaces (data plane: PUT /code-interpreters/{codeInterpreterIdentifier}/sessions/start, PUT /browsers/{browserIdentifier}/sessions/start, POST /memories/{memoryId}/events, GET /memories/{memoryId}/actor/{actorId}/sessions/{sessionId}/events/{eventId}, POST /runtimes/{agentRuntimeArn}/invocations, POST /identities/GetWorkloadAccessToken; control plane: POST /memories/create, PUT /runtimes/, ...). Each operation answers either a modeled success envelope or one of its modeled errors — e.g. StartCodeInterpreterSession -> 200 {codeInterpreterIdentifier, sessionId, createdAt}, errors AccessDeniedException 403 / ConflictException 409 / ResourceNotFoundException 404 / ServiceQuotaExceededException 402 / ThrottlingException 429 / ValidationException 400 / InternalServerException 500; CreateMemory -> 202 {memory}; CreateAgentRuntime -> 202 {agentRuntimeArn, agentRuntimeId, agentRuntimeVersion, createdAt, status}; CreateEvent -> 201 {event}, errors include InvalidInputException 400 and ValidationException 400. "AmbiguousService" is not an AWS error code and appears in no AgentCore operation's modeled error list.
Emulator: every AgentCore call — data plane and control plane alike — is refused before dispatch with error code AmbiguousService and the message "2 emulated services all claim requests for 'bedrock-agentcore': bedrock-agentcore, bedrock-agentcore; the request is rejected rather than served by an arbitrary one", retried to exhaustion by botocore ("reached max retries: 3"), which shows it is served with a retryable 5xx-class status rather than any modeled client error. The router resolves a request to a service by its sigv4 signing name alone, so the data plane and the control plane collide on 'bedrock-agentcore' and both are dropped; both claimants are even printed under the same token, so the message cannot distinguish them. Checks that assert a specific rejection code therefore read AmbiguousService where a modeled error belongs: "expected ValidationException, got AmbiguousService" (create-event-malformed-payload-rejected, delete-memory-record-invalid-input-malformed-id, get-event-malformed-id-invalid-input, evaluate-duplicate-id-rejected), "expected ResourceNotFoundException, got AmbiguousService" (get-event-missing-resource-not-found), "expected AccessDeniedException, got AmbiguousService" (get-memory-record-cross-tenant-read-denied, invoke-agent-runtime-cross-tenant-denied, invoke-agent-runtime-missing-permission-denied, stop-runtime-session-unauthorized-denied). abtest-lifecycle-transitions does not even return a verdict: the retried refusals on its setup calls consume the whole 60s check budget and it times out.
Why: no part of Bedrock AgentCore is usable through the emulator. No memory, runtime, browser, code-interpreter, gateway, A/B test, batch-evaluation, payment or workload-identity resource can be created, read, mutated or deleted, so neither happy paths nor negative/error-semantics paths can be exercised. Worse, a client receives a retryable server-class refusal rather than a modeled client error, so every caller burns its full retry budget and surfaces a transient-looking failure for a request that can never succeed.
Fix: the request router's service-resolution step — disambiguate a signing name shared by several modeled services (by endpoint prefix / request host, or by matching the request's method+URI against each candidate service's bound restJson1 operations) instead of refusing the request. This is the same defect class as the already-open issues "Kinesis Analytics V2 is entirely unreachable: router refuses every request with AmbiguousService ...", "Chime SDK Identity is entirely unreachable: the router resolves requests by sigv4 signing name ...", "All Wisdom requests rejected with AmbiguousService ...", "GreengrassV2: every request rejected with AmbiguousService ..." and "MigrationHub Config is entirely unreachable ..."; none of those names the 'bedrock-agentcore' claimants or carries any AgentCore replay key, so this instance is net-new. Note the AgentCore pair is the harder sub-case: the two claimants differ in endpointPrefix ('bedrock-agentcore' vs 'bedrock-agentcore-control') while sharing sigv4Name, so keying resolution on endpointPrefix/route rather than signing name resolves it exactly.

=== Cause 2 of 2: a CloudFormation stack that deploys AgentCore resources returns Output entries that carry an OutputKey but no OutputValue ===
AWS: recorded behavior only (no Smithy statement governs stack Output resolution). On AWS, a stack that reaches CREATE_COMPLETE exposes each declared Output through DescribeStacks as a complete member — an OutputKey AND its resolved OutputValue — so a client can map OutputKey -> OutputValue and read back the identifiers of what the template just created (here the agent runtime's ARN under OutputKey "RuntimeArn", and the code-interpreter custom resource's outputs).
Emulator: DescribeStacks returns a non-empty Outputs list whose entries lack the OutputValue member entirely, so both checks die with KeyError: 'OutputValue' while reading the stack they just deployed — one on `next(o["OutputValue"] for o in final["Outputs"] if o["OutputKey"] == "RuntimeArn")`, the other on `{o["OutputKey"]: o["OutputValue"] for o in stack.get("Outputs", [])}`. The Output is thus declared/echoed but never resolved to a value. Hypothesis: the stack's Outputs are recorded from the template at creation time without ever evaluating their Value expressions (Ref/Fn::GetAtt against the provisioned resources), which cause 1 would also contribute to if the AgentCore resources inside the stack are provisioned through the same router and therefore never came up.
Why: a client that deploys infrastructure and then consumes stack Outputs — the normal contract between a template and whatever runs after it — gets entries it cannot read. Naively mapping Outputs raises a KeyError instead of yielding the created resource's ARN, so every post-deploy step fails even though the stack reports success.
Fix: the CloudFormation stack-creation path — Output Value evaluation and the DescribeStacks Output serializer that must emit OutputValue alongside OutputKey — plus the AgentCore resource provisioning the stack drives. A related cause is already open as "Lambda is unreachable (router AmbiguousService across four 'lambda'-signing services), and a CloudFormation-deployed Lambda stack exposes no Outputs (2 causes)", whose cause 2 reports an EMPTY Outputs map for a different service's stack and carries none of these replay keys; this AgentCore instance differs (entries present but value-less) and is filed separately, though a shared Outputs-evaluation fix may close both.
Traces: deploy-agent-runtime-invokable-via-cfn, deploy-code-interpreter-custom-resource-executes.
