# lexv2-runtime RecognizeText has no NLU or dialog engine: every turn answers FallbackIntent/Close, no slot is ever elicited, resolved or stored, and a never-built locale is accepted (4 causes)

> _Note: this issue was identified against the code base at commit `881a3a65036f8f2ff03f484d3b78fc6be96d2a14`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RecognizeText

## Description
The Lex V2 runtime data plane answers every RecognizeText turn from a canned, bot-independent session turn. `services/service-com-amazonaws-lexruntimev2-awsdeepsenseruntimeserviceapi2-0/src/ops/recognize_text.rs` never reads `input.text` and never reaches the bot locale built through lexv2-models: it calls `state.lock().advance_turn(key, now, input.session_state, input.request_attributes)` only, and `src/state.rs` documents that choice (`FALLBACK_INTENT`, `DIALOG_ACTION_CLOSE`, and the `advance_turn` doc comment "this emulator holds no bot locale to match it against ... so it is not interpreted into an intent of its own and is not passed here"). That one gap is observable as four distinct behavioral divergences, each of which must be closed before this issue is submitted. All four were exercised on a bot whose en_US locale was created, given a TopResolution custom slot type (PizzaSize with sample values large/small and synonyms big/little), an OrderPizza intent with the sample utterances "I want to order a pizza" and "I want a {PizzaSize} pizza", and a Required PizzaSize slot with an authored elicitation prompt and priority 1, then built with BuildBotLocale to botLocaleStatus Built.

Cause 1 of 4 — the authored intents of the built locale are never matched; every utterance is the fallback intent.
AWS: RecognizeText "interprets the user input using the machine learning model that it build for the bot" (Smithy: lexruntimev2#RecognizeText doc). The 200 response carries `interpretations` (Interpretations, len 0..5) ordered by confidence, each an `Interpretation` with `intent` (Intent, required member `name`) and `nluConfidence` (ConfidenceScore.score, Double 0.00..1.00). An utterance matching an authored sample utterance of a built locale returns that intent as the top interpretation with a score at or above the locale's own nluIntentConfidenceThreshold (0.40 here); AMAZON.FallbackIntent is what AWS returns only when no intent of the locale matches.
Emulator: the top (and only) interpretation is always `FallbackIntent` — "the top interpretation was 'FallbackIntent', expected the authored 'OrderPizza'; all interpretations were ['FallbackIntent']" — for the exact sample utterances "I want a large pizza" and "I want to order a pizza".
Why: a client cannot test any conversation it authored. Every turn is misrouted to the fallback path, so intent-driven application code (fulfillment dispatch, analytics on intent name, confidence gating against nluIntentConfidenceThreshold) is exercised against an intent the bot does not declare and never against its own.
Fix: the RecognizeText/RecognizeUtterance turn in the runtime crate's state (`advance_turn`) must take the utterance text and resolve the bot locale built by lexv2-models (bot id + alias id + localeId), then match the locale's intents by their sample utterances and report the match as the top interpretation with a score, falling back to FallbackIntent only when nothing matches.

Cause 2 of 4 — a Required slot with an authored prompt is never elicited; the dialog action is always Close and carries no slotToElicit or prompt message.
AWS: Smithy lexruntimev2#DialogAction.type is required and enumerates Close/ConfirmIntent/Delegate/ElicitIntent/ElicitSlot/None; `slotToElicit` is "the name of the slot that should be elicited from the user", and Intent.state enumerates InProgress ("the bot is in the middle of eliciting the slot values that are necessary to fulfill the intent") and ReadyForFulfillment ("the bot has elicited all the slot values for the intent and is ready to fulfill the intent"). An utterance that matches an intent but names no value for its Required slot returns dialogAction.type = ElicitSlot with slotToElicit = that slot's name, intent.state = InProgress, and `messages` holding the prompt authored on the slot's valueElicitationSetting.promptSpecification; once the last Required slot is filled the same turn returns intent.state = ReadyForFulfillment and dialogAction.type = Close.
Emulator: the first turn of the conversation returns dialogAction.type 'Close' — "the first turn returned dialog action 'Close', expected 'ElicitSlot' — the required slot is unfilled" — and the DialogAction it serializes has no `slotToElicit` member at all, so reading it raises KeyError: 'slotToElicit'. No authored prompt is ever returned in `messages`.
Why: the conversation is one turn long and always terminal. A client that drives a multi-turn dialog off dialogAction.type/slotToElicit (the documented way to know what to ask next) sees a closed dialog on turn one and never collects the slot; the prompt text authored on the slot is unverifiable.
Fix: the same turn component must run the intent's slot-priority dialog loop — emit ElicitSlot with slotToElicit and the slot's promptSpecification messages while a Required slot is unfilled, hold intent.state at InProgress, and only move to ReadyForFulfillment/Close once every Required slot is filled.

Cause 3 of 4 — no slot value is ever filled or resolved, so TopResolution synonym mapping and the session's slot state do not exist.
AWS: Smithy lexruntimev2#Slot.value is a `Value` whose `interpretedValue` is required, with `originalValue` = "the part of the user's response to the slot elicitation that Amazon Lex V2 determines is relevant to the slot value" and `resolvedValues` = "a list of values that Amazon Lex V2 determines are possible resolutions for the user input. The first value matches the interpretedValue". For a slot type created with valueSelectionSetting.resolutionStrategy = TopResolution, an utterance naming a declared synonym resolves to the canonical sample value: saying "big" yields originalValue = the said word, interpretedValue = the canonical value, resolvedValues = [that canonical value]; a word the slot type declares neither as a sample value nor as a synonym resolves to nothing, leaving the slot unfilled, intent.state InProgress and the dialog still eliciting that slot. The fill is session state: GetSession on the same four labels reports the same sessionState.intent.slots entry.
Emulator: sessionState.intent carries no `slots` entry for PizzaSize on any turn — the checks' `_resolved()` helper (which reads sessionState.intent.slots[name].value.resolvedValues) finds nothing, and the turn in `advance_turn` is built without reference to the utterance, so neither the in-vocabulary sample value "large", nor the synonym "big", nor the out-of-vocabulary "gigantic" changes the response. There is consequently no distinction between a resolvable and an unresolvable answer, and GetSession holds no slot value.
Why: slot resolution is the substance of a Lex bot. A client cannot verify that its slot type's synonyms map onto canonical values, cannot verify that out-of-vocabulary input is rejected rather than accepted verbatim, and cannot read a filled slot back from the session on the following turn — the three things application code consumes from the runtime.
Fix: slot filling belongs in the same turn component and in the runtime's session state — extract candidate values from the utterance against the resolved locale's slot types, apply the slot type's resolutionStrategy (TopResolution maps a synonym to its sample value) to produce Value{originalValue, interpretedValue, resolvedValues}, store it on the session's intent.slots so GetSession returns it, and leave the slot unfilled when nothing resolves.

Cause 4 of 4 — RecognizeText against a locale that was never built is accepted 200 and creates a session, instead of being refused 404 ResourceNotFoundException.
AWS: Smithy lexruntimev2#RecognizeText models ResourceNotFoundException (httpError 404). A bot locale whose botLocaleStatus is NotBuilt has no runtime model, so AWS refuses the call with HTTP 404, error code ResourceNotFoundException and the message (fixed text, no variable parts) "The provided BotId/BotLocale combination is not valid. Please update the BotId/BotLocale combination and retry your request." The refusal has no effect: no session comes into existence, so a following GetSession for the same four labels is itself 404 ResourceNotFoundException whose message is "The session for user <sessionId> doesn\u2019t exist or has expired." — fixed text around the sessionId taken from the request, with a typographic apostrophe U+2019.
Emulator: the call succeeds. "AssertionError: the call was expected to fail but returned successfully" — a 200 RecognizeText for a locale DescribeBotLocale reports as NotBuilt, which also inserts the session (`advance_turn` creates the session on a first turn), so the absence-of-effect property is lost too.
Why: this fails open. A client testing its build gate — or its error handling for "bot not built yet" — gets a successful turn where AWS refuses, so a deployment that forgot BuildBotLocale looks healthy against the emulator and 404s in production; and the stray session the accepted call leaves behind makes a subsequent GetSession answer 200 where AWS answers 404.
Fix: RecognizeText's handler needs a pre-condition check on the addressed bot/alias/locale before any session is created or written — resolve the locale's build state from lexv2-models state and return the modeled ResourceNotFoundException with AWS's wording when it is not Built, ordering the check ahead of the session insert so a refused turn leaves no session.
