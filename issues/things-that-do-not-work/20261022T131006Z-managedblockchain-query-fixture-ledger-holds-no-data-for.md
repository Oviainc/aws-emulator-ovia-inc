# ManagedBlockchain Query fixture ledger holds no data for real mainnet identifiers: token-balance and transaction reads return empty/not-found

> _Note: this issue was identified against the code base at commit `6f82ed95aacdd57d8c8c0220ec6b50c75b2537e1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListTransactions

## Description
The emulator serves every read of this service out of a synthetic fixture ledger built in `crate::state` (`seed_networks` -> `seed_ethereum_ledger`/`seed_bitcoin_ledger`), whose addresses and contracts are SHA-256 digests of labels (`ethereum_address(network,"wallet-a")`, `bitcoin_address(...)`, `contract-erc20`) and whose transactions are anchored at `LEDGER_EPOCH` = 2024-01-01T00:00:00Z with `BLOCK_INTERVAL` 600s. Real AWS answers these same operations out of an index of the actual public chains, so every read keyed by a REAL, publicly-known mainnet identifier returns data on AWS and nothing on the emulator. Three distinct read surfaces are affected; each needs its own fix (ledger coverage for the identifiers the suite queries, and a ledger time span that covers the queried windows).

--- Cause 1 of 3: GetTokenBalance for a native token of a real mainnet wallet returns ResourceNotFoundException instead of a balance ---
AWS: Smithy `GetTokenBalance` (POST /get-token-balance) takes `tokenIdentifier` (required) + `ownerIdentifier` (required) + optional `atBlockchainInstant`, and returns `balance` (required String) and `atBlockchainInstant` (required). `TokenIdentifier$tokenId` doc: "For native tokens, use the 3 character abbreviation that best matches your token. For example, btc for Bitcoin, eth for Ether". For a long-lived, continuously active Ethereum mainnet wallet AWS returns HTTP 200 with a non-zero base-10 integer `balance`, echoes back the requested `ownerIdentifier`/`tokenIdentifier`, and — when no `atBlockchainInstant` is supplied — resolves `atBlockchainInstant` to the live chain tip (an instant inside the call's own wall-clock window), not to a fixed epoch. ResourceNotFoundException (404) is modeled for this op but applies to a token/owner the service holds nothing for.
Emulator: HTTP 404 `ResourceNotFoundException`, e.g. message "No balance is recorded for owner 0x28c6c06298d514db089934071355e5743bf21d60 of that token on network ETHEREUM_MAINNET" (example text), for `tokenIdentifier={network:ETHEREUM_MAINNET, tokenId:eth}` on a real mainnet address — both unpinned and pinned to a 2023-01-01 instant. The ledger simply has no holding under that `HoldingKey`, and no holding exists at any instant before `LEDGER_EPOCH` (2024-01-01) even for the synthetic wallets.
Why: a client reading a native-token balance (the single most common use of this API) gets a 404 where AWS gives it a number, so balance dashboards, reconciliation jobs and any retry logic that treats 404 as "this wallet does not exist" draw the wrong conclusion. Pinning a historical instant that predates the fixture epoch compounds it: every historical read 404s.
Fix: the service's seeded state (`src/state.rs`: `seed_ethereum_ledger`/`seed_bitcoin_ledger` opening balances and `derive_holdings`, plus `LEDGER_EPOCH`) must cover the real mainnet identifiers and a chain history that extends back well before the queried windows; `src/ops/get_token_balance.rs` must also resolve an unpinned request to a live "now" instant rather than a fixed epoch.
Traces: managedblockchain-query.get-token-balance-native-eth-structural, managedblockchain-query.get-token-balance-batch-consistency, managedblockchain-query.concurrent-get-token-balance-consistent-reads (all three fail on the same 404 from GetTokenBalance).

--- Cause 2 of 3: ListTokenBalances returns an empty tokenBalances list for a real ERC-20 contract and for an owner-scoped, network-only filter ---
AWS: Smithy `ListTokenBalances` (POST /list-token-balances) takes required `tokenFilter`, optional `ownerFilter`, `maxResults` @range(1,250); output `tokenBalances` (required list, @length 0..250) + `nextToken`. HTTP 200. For a heavily-held mainnet ERC-20 contract AWS returns holder rows whose `tokenIdentifier.contractAddress` is the filtered contract and whose `ownerIdentifier.address` is a well-formed chain address with a base-10 integer `balance`. With `ownerFilter` set and a tokenFilter naming only `network`, AWS widens the result to every token standard that owner holds — including the native-currency row (a `tokenIdentifier` with `tokenId` and no `contractAddress`) alongside ERC-20/721 rows.
Emulator: HTTP 200 with `tokenBalances: []` for `tokenFilter={network:ETHEREUM_MAINNET, contractAddress:<real USDC contract>}`, and zero contract rows (and zero native rows) for `ownerFilter={address:<real mainnet wallet>}` + `tokenFilter={network:ETHEREUM_MAINNET}` across the single page it returns.
Why: an empty 200 is indistinguishable from "this contract has no holders"/"this wallet holds nothing", so a client enumerating holders or building a wallet portfolio silently sees nothing instead of the real set, and never exercises its paging path.
Fix: same seeded-state gap as Cause 1, surfaced through `src/ops/list_token_balances.rs`'s read of `NetworkLedger::holdings`.
Traces: managedblockchain-query.list-token-balances-known-contract-nonempty, managedblockchain-query.list-token-balances-owner-and-native-token-filter.

--- Cause 3 of 3: ListTransactions returns an empty transactions list for real mainnet addresses, starving GetTransaction / ListTransactionEvents ---
AWS: Smithy `ListTransactions` (POST /list-transactions) takes required `address` (ChainAddress, @pattern ^[-A-Za-z0-9]{13,74}$) + required `network`, optional `fromBlockchainInstant`/`toBlockchainInstant`, `sort`, `confirmationStatusFilter`, `maxResults` @range(1,250); output `transactions` (required list) + `nextToken`. For a high-volume mainnet wallet AWS returns non-empty pages (ascending `transactionTimestamp` by default, descending when `sort.sortOrder=DESCENDING`), a `nextToken` when more remain, and non-empty results inside a historical one-month window (recorded behavior: the 2023-01-01..2023-02-01 window is reliably non-empty for such an address). `ConfirmationStatusFilter` is documented as additive — transactions that have reached finality are always part of the response. For BITCOIN_MAINNET, summaries additionally carry `transactionId`, and `GetTransaction` resolves the same transaction by `transactionHash` or by `transactionId`.
Emulator: HTTP 200 with `transactions: []` for a real mainnet address on ETHEREUM_MAINNET (unfiltered with maxResults=5, and with the 2023-01/2023-02 window, with DESCENDING sort, and with confirmationStatusFilter) and on BITCOIN_MAINNET. The fixture holds six Ethereum and four Bitcoin transactions, all between synthetic digest addresses and all timestamped at `LEDGER_EPOCH + (block+1)*600` (2024-01-01), so a real address matches nothing and a pre-2024 window matches nothing. Downstream checks that chain off the first returned summary fail with IndexError because the list is empty — GetTransaction and ListTransactionEvents are never reached.
Why: every address-scoped history read — the entry point for this whole API — comes back empty, so a client cannot discover a transaction hash, cannot page, cannot observe sort order or window filtering, and the GetTransaction/ListTransactionEvents chain built on it is unreachable.
Fix: same seeded-state gap (`src/state.rs` fixture ledger: identifiers and ledger time span) as read by `src/ops/list_transactions.rs`; the fixture must also hold enough transactions for the requested address to produce a `nextToken` beyond `maxResults=5`.
Traces: managedblockchain-query.list-transactions-busy-address-pagination, managedblockchain-query.list-transactions-time-window-filter, managedblockchain-query.list-transactions-sort-order-descending, managedblockchain-query.list-transactions-confirmation-status-filter, managedblockchain-query.get-transaction-matches-list-transactions-summary, managedblockchain-query.get-transaction-bitcoin-fields, managedblockchain-query.list-transaction-events-for-known-transaction.

## Evidence
Cause 1 — expected: HTTP 200 with a non-zero integer `balance` and an `atBlockchainInstant` at the live chain tip. Actual: HTTP 404 `ResourceNotFoundException` ("No balance is recorded for owner <addr> of that token on network ETHEREUM_MAINNET" — example text) for tokenIdentifier {network:ETHEREUM_MAINNET, tokenId:eth}.
Cause 2 — expected: HTTP 200, non-empty `tokenBalances` with rows whose contractAddress equals the filtered contract; and, for ownerFilter + network-only tokenFilter, both contract rows and a native row. Actual: HTTP 200 with `tokenBalances: []` (assertion "USDC must have holders, got an empty tokenBalances list"; "an active exchange wallet must hold at least one ERC-20/721 balance row (scanned 1 page(s))").
Cause 3 — expected: HTTP 200 with non-empty `transactions` plus a `nextToken` for a busy address; non-empty results in the 2023-01-01..2023-02-01 window; DESCENDING order honoured. Actual: HTTP 200 with `transactions: []` (assertions "expected 1-5 transactions for a wallet with heavy history", "expected transactions in this one-month window for a busy wallet", "expected at least one transaction for a busy wallet after bounded paging") and `IndexError: list index out of range` in the three checks that index `["transactions"][0]`.
Root cause visible in the checkout: services/service-com-amazonaws-managedblockchainquery-tietonchainqueryservice/src/state.rs — `seed_networks()`/`seed_ethereum_ledger()`/`seed_bitcoin_ledger()` build addresses via `ethereum_address()`/`bitcoin_address()` (SHA-256 of a label) and timestamp every transaction at `LEDGER_EPOCH` (1_704_067_200 = 2024-01-01Z) + (block+1)*`BLOCK_INTERVAL`; services/.../src/ops/get_token_balance.rs lines 191-209 return `ResourceNotFoundException` whenever the ledger holds no holding for the requested key/instant.

## Steps to Reproduce
Point a botocore client at the emulator's managedblockchain-query endpoint (region us-east-1) and run:
1. `get_token_balance(tokenIdentifier={"network":"ETHEREUM_MAINNET","tokenId":"eth"}, ownerIdentifier={"address":"0x28c6c06298d514db089934071355e5743bf21d60"})` -> observe HTTP 404 ResourceNotFoundException instead of HTTP 200 with a balance. Repeat with `atBlockchainInstant={"time": 2023-01-01T00:00:00Z}` — same 404.
2. `list_token_balances(tokenFilter={"network":"ETHEREUM_MAINNET","contractAddress":"0xa0b86991c6218b36c1d19d4a2e9eb0ce3606eb48"}, maxResults=10)` -> observe `tokenBalances: []`. Then `list_token_balances(tokenFilter={"network":"ETHEREUM_MAINNET"}, ownerFilter={"address":"0x28c6c06298d514db089934071355e5743bf21d60"}, maxResults=50)` -> observe no contract rows and no native row.
3. `list_transactions(address="0x28c6c06298d514db089934071355e5743bf21d60", network="ETHEREUM_MAINNET", maxResults=5)` -> observe `transactions: []` and no `nextToken`. Repeat with `fromBlockchainInstant={"time":2023-01-01Z}`/`toBlockchainInstant={"time":2023-02-01Z}`, with `sort={"sortBy":"TRANSACTION_TIMESTAMP","sortOrder":"DESCENDING"}`, and with `confirmationStatusFilter={"include":["FINAL"]}` — all empty. Repeat step 3 with `address="1A1zP1eP5QGefi2DMPTfTL5SLmv7DivfNa", network="BITCOIN_MAINNET"` -> also empty, so no hash/transactionId is available to feed get_transaction / list_transaction_events.
