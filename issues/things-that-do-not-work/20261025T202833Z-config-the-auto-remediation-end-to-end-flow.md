# config: the auto-remediation end-to-end flow never starts — a running recorder never discovers an S3 bucket, so ListDiscoveredResources stays empty forever and the check hangs to the 60 s cap (1 cause)

> _Note: this issue was identified against the code base at commit `07569be71b553a95f2f3aaa6a23a9103793b0794`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDiscoveredResources

## Description
ONE CAUSE. The check's service token is `config`; configservice is bootstrapped and answering (61/103 config checks pass in this replay), so this is a fidelity defect, not a bootstrap gap.

Cause 1 of 1: with a customer-managed configuration recorder RUNNING and a delivery channel in place, Config never discovers a resource that was created through another emulated service, so ListDiscoveredResources answers an empty `resourceIdentifiers` list forever for a bucket that was just created, and every step of the auto-remediation flow that depends on the resource being in inventory is unreachable.

AWS: a customer-managed recorder whose recordingGroup has allSupported=true asynchronously discovers supported resource types and admits them to the account's discovered-resource inventory; ListDiscoveredResources then reports them. Smithy (configservice): ListDiscoveredResources — "Returns a list of resource identifiers for the specified resource types... The results consist of resources that Config has discovered, including those that Config is not currently recording. You can narrow the results to include only resources that have specific resource IDs or a resource name."; input resourceType (ResourceType enum, required — the enum includes AWS::S3::Bucket), resourceIds (ResourceIdList, 1..20); output resourceIdentifiers (ResourceIdentifierList), shape ResourceIdentifier documented as "The details that identify a resource that is discovered by Config, including the resource type, ID, and (if available) the custom resource name."; modeled errors InvalidLimitException / InvalidNextTokenException / NoAvailableConfigurationRecorderException / ValidationException, all client/HTTP 400 — i.e. for a healthy customer-managed recorder the modeled answer is a list that becomes non-empty once discovery has happened, never a permanently empty one. Recorded behavior (the check's own inline AWS measurement): after s3:CreateBucket under such a recorder, ListDiscoveredResources(resourceType='AWS::S3::Bucket', resourceIds=[<bucket>]) returns exactly one resourceIdentifier within the check's 600 s / 15 s poll budget, after which the rule S3_BUCKET_VERSIONING_ENABLED scoped to that bucket yields a NON_COMPLIANT evaluation result.

Emulator: nothing is ever discovered. PutConfigurationRecorder / PutDeliveryChannel / StartConfigurationRecorder all succeed, but the handler services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/list_discovered_resources.rs:256-326 pages over `store.discovered_resources`, and that map has exactly one growth point — `record_discovered_resource` in src/state.rs, reachable only from an explicit client PutResourceConfig. A bucket created through the S3 service therefore never enters it, the predicate `len(ids) == 1` never becomes true, and the harness kills the check at its 60 s ceiling. The timeout report carries no stack frame, so the blocking call is not pinned by the replay itself; it is pinned by the check's ordering — the only long wait reachable inside 60 s is that first ListDiscoveredResources poll (everything before it is the recorder lock, _ensure_recorder and s3:CreateBucket, all synchronous). Hypothesis: the poll never converges for the reason above; a fixer can confirm by calling ListDiscoveredResources directly per the reproduction steps.

This is NOT covered by the open issues on the same surface, neither of which carries this check's replay key: 20261025T144945Z-config-the-configuration-recorder-never-records-resources-from.md names the same missing recording loop but is grounded in AWS::SQS::Queue through GetResourceConfigHistory / BatchGetResourceConfig / SelectResourceConfig and lists only the six config__sqs / config__lambda__sqs checks; the ListDiscoveredResources read path and the AWS::S3::Bucket discovery this check needs appear in neither its trace ids nor its Fix. 20261024T114729Z-config-never-converges-on-an-evaluation-or-a.md covers evaluation/delivery-status convergence downstream of a resource already being in inventory. Fixing either without admitting other services' resources to the inventory leaves this check hanging in the same place.

Why: a client cannot use Config as an inventory or guardrail service for resources it did not hand Config itself. ListDiscoveredResources is indistinguishable from "the account owns nothing of this type" while DescribeConfigurationRecorderStatus reports recording=true, so a discovery sweep, a compliance dashboard or an auto-remediation control silently reads empty and reports the account green; and because the resource is never in inventory, nothing further in the flow can be reached — no rule ever marks the bucket NON_COMPLIANT, PutRemediationConfigurations has no resource to act on, StartRemediationExecution cannot drive DescribeRemediationExecutionStatus to SUCCEEDED, and the post-remediation COMPLIANT re-evaluation never happens. The call never fails, it just never answers differently, so "not discovered yet" cannot be told from "discovery is not implemented".

Fix: the configuration-recorder discovery/recording loop in configservice — while a customer-managed recorder is recording and its recordingGroup covers the type, resources created, changed and deleted in the other emulated services (here AWS::S3::Bucket from the S3 crate) must be admitted to the recorder's inventory through the single existing growth point, from which list_discovered_resources.rs and the sibling read paths already project. No change is needed in the ListDiscoveredResources handler's own paging, filtering or refusals; its input is simply always empty.

Traces: config.remediation-auto-remediation-flow (killed at the 60 s cap in its first ListDiscoveredResources poll). The downstream legs of that check — the initial NON_COMPLIANT verdict, the SSM-document remediation reaching SUCCEEDED through DescribeRemediationExecutionStatus, and the COMPLIANT re-evaluation — were never reached, so this issue claims nothing about them; they become observable only once discovery produces the resource. Note on confirming the fix: the check's own budgets (600 s discovery, 300 s first compliance, 180 s execution, 3x180 s re-evaluation) exceed the 60 s harness cap, so confirm the cause by driving ListDiscoveredResources directly as in the reproduction steps rather than by expecting this check to pass inside the cap.

## Evidence
Replay of simparity-behavioral-ga-prod-v1 against the emulator built from mainline (emulator serving; bootstrap_signal false — 64/117 checks passed, 40 mismatched / 13 errored). Of the 53 reported failures this is the only one neither blocked by an unimplemented scaffold stub nor owned by an open issue.

  [mismatch] config.remediation-auto-remediation-flow — Error: Check timed out after 60.0s   (no stack frame)

The check (GROUP=e2e, SERVICES=[config], tags axis:happy-path, resource:account-singleton:config-recorder) does, in order: acquire the recorder lock, _ensure_recorder, s3:CreateBucket(<unique name>), then
  _poll_until(lambda: cfg.list_discovered_resources(resourceType='AWS::S3::Bucket', resourceIds=[bucket_name])['resourceIdentifiers'], lambda ids: len(ids) == 1, timeout_s=600, interval_s=15)
Everything preceding that poll is synchronous, so the 60 s kill lands inside it (4 poll iterations at interval 15 s).

Expected (AWS, measured inline by the check): resourceIdentifiers contains exactly one entry for the created bucket (resourceType AWS::S3::Bucket, resourceId the bucket name), after which get_compliance_details_by_resource(ResourceType='AWS::S3::Bucket', ResourceId=<bucket>) yields EvaluationResults[0].ComplianceType == 'NON_COMPLIANT' for rule source S3_BUCKET_VERSIONING_ENABLED.
Actual (emulator): HTTP 200 with resourceIdentifiers == [] on every poll. The listing is served from `store.discovered_resources` (services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/list_discovered_resources.rs:301 iterates it; :262 only guards that a customer-managed recorder exists), and that map is written in exactly one place, `record_discovered_resource` in services/service-com-amazonaws-configservice-starlingdoveservice/src/state.rs, which is reached only from PutResourceConfig — there is no path by which an s3:CreateBucket enters it.

Status and error code are not in question here: the call returns 200 and no modeled error (NoAvailableConfigurationRecorderException is correctly withheld because a customer-managed recorder does exist). The divergence is the permanently empty resourceIdentifiers list.

2. Replay simparity-behavioral-ga-prod-v1 and re-replay config.remediation-auto-remediation-flow; it reports 'Check timed out after 60.0s'.
3. Directly, without the harness: iam:CreateRole trusting config.amazonaws.com with arn:aws:iam::aws:policy/service-role/AWS_ConfigRole attached; s3:CreateBucket for delivery carrying the three AWSConfigBucket* policy statements; config:PutConfigurationRecorder with ConfigurationRecorder={'name': 'default', 'roleARN': <role arn>, 'recordingGroup': {'allSupported': True}}; config:PutDeliveryChannel at that bucket; config:StartConfigurationRecorder.
