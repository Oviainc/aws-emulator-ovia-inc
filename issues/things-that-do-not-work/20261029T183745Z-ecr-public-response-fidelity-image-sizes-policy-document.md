# ECR Public response fidelity: image sizes, policy-document formatting, batch-delete failure ordering and a missing DescribeRepositories MaxResults refusal (4 causes)

> _Note: this issue was identified against the code base at commit `e5bbef2d2760924537f10016f55a30b12c0b7775`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeImages

## Description
Wire replay of simparity-wire-aws-v1 (12 fixtures, 165 steps, 151 passed, 14 mismatched, score 91.5%, emulator_up=true, bootstrap_signal=false) produced 9 divergence clusters, ALL of them on ecr-public (which is bootstrapped: service-com-amazonaws-ecrpublic-spencerfrontendservice is in the bootstrapped set, and implemented operations answer 200/400). None was marked blocked by a stub and none was marked owned by an open issue. They reduce to the FOUR independent root causes below. ALL FOUR must be closed before this issue is resolved.

=== Cause 1 of 4: imageSizeInBytes reports the byte length of the manifest document instead of the size of the image in the repository ===
AWS: Smithy ImageDetail.imageSizeInBytes -> ImageSizeInBytes (long), documented "The size, in bytes, of the image in the repository" and "If the image is a manifest list, this is the max size of all manifests in the list"; the same member appears nested as ImageTagDetail.imageDetail -> ReferencedImageDetail.imageSizeInBytes. The value is therefore derived from the CONTENT the manifest references -- the sum of the sizes declared for the manifest's config blob and its layer blobs -- not from the size of the manifest JSON itself. Operations affected: DescribeImages (output imageDetails -> ImageDetailList) and DescribeImageTags (output imageTagDetails -> ImageTagDetailList).
Emulator: for an image pushed through InitiateLayerUpload/UploadLayerPart/CompleteLayerUpload/PutImage, DescribeImages and DescribeImageTags report an imageSizeInBytes equal to the length of the pushed manifest document, which is far smaller than the referenced content: the recordings show 36 where the referenced config+layers total 209, and 31 where they total 204. Every other member of the element (imageDigest, imageTags, imageManifestMediaType, artifactMediaType, registryId, repositoryName) matches; the element is reported as missing/extra by the comparator only because this one scalar differs. imagePushedAt/createdAt differ per run and are NOT part of this cause.
Why: imageSizeInBytes is the only size a client can read without pulling blobs, so anything that budgets pull bandwidth or disk, enforces a repository size policy, sorts or reports on image size, or asserts that a push stored what it uploaded, reads a value one to two orders of magnitude too small against the emulator while AWS reports the real content size.
Fix: the image-record state written by PutImage (and the DescribeImages / DescribeImageTags serializers that read it) must compute imageSizeInBytes by summing the sizes declared in the stored manifest for its config and layer descriptors (max over the members for a manifest list), instead of storing the manifest blob's own length.
Traces: api-image-layer-upload-and-push-workflow#task#10 (DescribeImages, also api-repository-deletion-and-non-empty-error-paths#task#10 and ecr-public-image-push-idempotent-replay-and-layer-reupload#task#10), api-image-layer-upload-and-push-workflow#task#11 (DescribeImageTags), ecr-public-describe-image-tags-pagination-and-not-found#task#10 and #task#12.

=== Cause 2 of 4: the repository policy document is echoed back verbatim-compact instead of re-serialized in the service's pretty-printed form ===
AWS: Smithy SetRepositoryPolicy / GetRepositoryPolicy / DeleteRepositoryPolicy all return policyText -> RepositoryPolicyText (@length 0..10240). The service parses the submitted document with its policy engine and re-serializes it on every read and write, so policyText is returned in the service's own canonical layout rather than as the caller's bytes: a two-space-indented, newline-separated rendering with a space on BOTH sides of the name separator and inside array brackets -- e.g. a document whose statement list holds one statement comes back as `{\n  "Version" : "2012-10-17",\n  "Statement" : [ {\n    "Sid" : ...,\n    "Effect" : ...,\n    "Principal" : ...,\n    "Action" : [ "ecr-public:BatchGetImage", "ecr-public:GetDownloadUrlForLayer" ]\n  } ]\n}`. Recorded behavior for the exact layout (the model constrains the document only by length); member order, Sid/Effect/Principal values and Action element order are preserved from the request, and the indentation/separator style is the fixed part.
Emulator: all three operations answer 200 with the correct keys, but policyText is the caller's document re-emitted as single-line compact JSON with no indentation and no spaces around separators (`{"Version": "2012-10-17", "Statement": [{"Sid": ... }]}`). The same divergence appears on the Set leg, on the Get read-back, and on the DeleteRepositoryPolicy response that echoes the policy being removed, which shows the document is stored as opaque text and never round-tripped through a policy serializer.
Why: policy read-back is how drift detection, policy diffing and infrastructure-as-code reconciliation decide whether the deployed policy equals the intended one; a client that compares the string it gets from GetRepositoryPolicy against what AWS returns (or caches an AWS-rendered document and re-compares) reports permanent spurious drift. NOTE: cause 5 of the open issue 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md covers a DIFFERENT symptom of the same missing round-trip (numeric Condition values not coerced to strings) and does not carry these wire steps; if the policy document is actually routed through a parse-and-re-serialize step, re-replay these fixtures to confirm both close together.
Fix: the repository-policy state plus the SetRepositoryPolicy / GetRepositoryPolicy / DeleteRepositoryPolicy serializers must parse the document and re-serialize it in the service's pretty-printed layout on every response, rather than echoing the stored bytes.
Traces: api-repository-policy-management#task#3 (SetRepositoryPolicy, also #task#5), api-repository-policy-management#task#4 (GetRepositoryPolicy, also #task#6), api-repository-policy-management#task#8 (DeleteRepositoryPolicy).

=== Cause 3 of 4: BatchDeleteImage emits its failures out of request order and words MissingDigestAndTag differently ===
AWS: Smithy BatchDeleteImage input imageIds -> ImageIdentifierList (required, @length 1..100); output failures -> ImageFailureList of ImageFailure{imageId -> ImageIdentifier, failureCode -> ImageFailureCode enum [InvalidImageDigest, InvalidImageTag, ImageTagDoesNotMatchDigest, ImageNotFound, MissingDigestAndTag, ImageReferencedByManifestList, KmsError], failureReason -> ImageFailureReason}. Each unprocessable entry yields one failure POSITIONALLY ALIGNED with the request's imageIds, carrying back the identifying members the caller supplied in imageId. Recorded behavior for the reason strings, which are fixed per failure code with no request-derived parts: MissingDigestAndTag (an imageId with neither imageTag nor imageDigest) -> "Invalid request parameters: both tag and digest cannot be null"; ImageNotFound (a well-formed digest that names no image) -> "Requested image not found", with imageId.imageDigest echoed as submitted.
Emulator: the two failures come back in the opposite order from the request -- failures[0] is the ImageNotFound entry and failures[1] the MissingDigestAndTag entry, where the recording has MissingDigestAndTag first -- so a caller zipping failures against its own imageIds mis-attributes both. On top of that the MissingDigestAndTag reason is the emulator's own wording, "Invalid request parameters: at least one of imageTag or imageDigest must be specified", instead of "Invalid request parameters: both tag and digest cannot be null". The missing failures[1].imageId.imageDigest in the diff is a consequence of the swap (the MissingDigestAndTag entry correctly has no digest). failureCode values themselves are drawn from the right enum.
Why: BatchDeleteImage's whole contract is per-entry partial failure; both the ordering and the reason text are what a batch client uses to decide which of its inputs failed and why, so a caller retrying or reporting per-image either blames the wrong image or fails a reason-text match it passes against AWS.
Fix: the BatchDeleteImage handler must build failures in the order of the request's imageIds (one entry per rejected input, echoing the submitted imageId members) and must render the MissingDigestAndTag reason in the service's wording.
Traces: ecr-public-batch-delete-image-failure-detail#task#10.

=== Cause 4 of 4: DescribeRepositories accepts maxResults together with repositoryNames and returns 200 instead of refusing it ===
AWS: Smithy DescribeRepositories input carries repositoryNames -> RepositoryNameList (@length 1..100) and maxResults -> MaxResults (@range 1..1000), with @paginated{inputToken: nextToken, outputToken: nextToken, items: repositories, pageSize: maxResults}; the operation models InvalidParameterException (client, httpError 400). The two inputs are mutually exclusive -- an explicit name list is not a paginable scan -- so a request carrying both is REFUSED with HTTP 400, error code (__type) InvalidParameterException and the service's member-constraint message "Invalid parameter at 'MaxResults' failed to satisfy constraint: 'Cannot provide MaxResults if providing RepositoryNames'". That message is entirely fixed text for this rule: the member path 'MaxResults' and the rule clause are the template, and no value from the request is interpolated.
Emulator: the same request answers HTTP 200 with a normal repositories payload; no __type and no message are emitted at all, so the refusal does not exist in the handler.
Why: this is a wrong SUCCESS -- a client that sends both (for example a paginating wrapper that always sets maxResults and then narrows by name) is silently served results against the emulator while AWS rejects the call, so the bug is never surfaced in testing and the pagination/filter mutual-exclusion contract is never exercised. Any code that catches InvalidParameterException to fall back to an unpaginated by-name describe never takes that branch.
Fix: DescribeRepositories' input validation must reject the combination of repositoryNames and maxResults with InvalidParameterException (400) and the service's 'Invalid parameter at <member> failed to satisfy constraint: <rule>' rendering before the handler reads state.
Traces: ecr-public-describe-repositories-max-results-pagination#task#6.
