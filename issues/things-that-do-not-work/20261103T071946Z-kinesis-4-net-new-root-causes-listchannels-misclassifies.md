# kinesis: 4 net-new root causes — ListChannels misclassifies a malformed NextToken as ExpiredNextTokenException, the PROVISIONED-without-ShardCount message is invented, a retention change to the CURRENT value is refused instead of a no-op, and the front door does not negotiate h2 by ALPN so SubscribeToShard has no HTTP/2 data plane

> _Note: this issue was identified against the code base at commit `62084d168200d993886f3f9bcbdaeb992dfa6fb2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListChannels

## Description
Four root causes in the Kinesis Data Streams surface, all grounded in failing checks the replay report lists under `### kinesis` and marks NEITHER "ALREADY FILED" nor "OWNED by".

=== Cause 1 of 4: ListChannels classifies a syntactically-invalid NextToken as ExpiredNextTokenException ===
AWS: Smithy binds BOTH `ExpiredNextTokenException` and `ValidationException` to ListChannels (plus AccessDeniedException, InvalidArgumentException, LimitExceededException), and models ListChannels.NextToken as NextToken @length min 1 max 1048576 with the @paginated inputToken/outputToken NextToken. The two token error classes are not interchangeable: a well-formed token whose ~5-minute TTL has lapsed is ExpiredNextTokenException, whereas a token that is not a valid token at all is a request-shape defect — recorded behavior: HTTP 400 `ValidationException` with the message `Invalid NextToken.` (entirely fixed text; the offending token is NOT echoed).
Emulator: ListChannels(NextToken='<any string that is not a token the emulator minted>') answers `ExpiredNextTokenException`. ListChannels with no token succeeds before and after, so the misclassification is specific to the token-validation path.
Why: ExpiredNextTokenException is the signal a paginating client uses to RESTART the listing from the first page — a client that receives it for a corrupt or hand-written token loops forever re-listing instead of surfacing the caller's bug, and never sees the `Invalid NextToken.` diagnosis. Open issue 20261029T140704Z-kinesis-liststreamconsumers-misclassifies-a-malformed-nexttoken-as-expirednexttokenexception.md reports the same defect for ListStreamConsumers; it does not cover ListChannels and does not carry this replay key, so the two share a cause but need both call sites fixed.
Fix: the NextToken decode/validation step in the ListChannels handler — distinguish "undecodable/not one of ours" (ValidationException, `Invalid NextToken.`) from "decoded but past its TTL" (ExpiredNextTokenException).
Traces: list-channels-malformed-next-token-rejected.

=== Cause 2 of 4: CreateStream's PROVISIONED-without-ShardCount refusal uses an invented message ===
AWS: Smithy models CreateStream.ShardCount as optional (PositiveIntegerObject, @range min 1) and StreamModeDetails separately, so the pairing rule is enforced at runtime, not by the shape. Recorded behavior: CreateStream with StreamModeDetails.StreamMode=PROVISIONED and no ShardCount is refused HTTP 400 `InvalidArgumentException` with the fixed message `ShardCount cannot be null when creating stream in PROVISIONED StreamMode` (entirely fixed text — no stream name or value is interpolated), and no stream is created: DescribeStreamSummary for that name is then ResourceNotFoundException `Stream <name> under account <account> not found.`
Emulator: the correct code and the correct absence, but the message is `ShardCount is required for a PROVISIONED stream` — emulator-authored text.
Why: the error message is part of the contract; clients and operators that match or display AWS's sentence see text AWS never serves for this error class.
Fix: the PROVISIONED/ShardCount pairing check in the CreateStream handler's validation. Open issue 20261027T011654Z-kinesis-9-net-new-root-causes-dryrun-not.md covers the converse case (ON_DEMAND *with* ShardCount) and other invented CreateStream messages but does not carry this replay key.
Traces: provisioned-stream-created-without-a-shard-count-rejected.

=== Cause 3 of 4: a retention change naming the stream's CURRENT value is refused instead of accepted as a no-op ===
AWS: Smithy models IncreaseStreamRetentionPeriod and DecreaseStreamRetentionPeriod with required RetentionPeriodHours and errors AccessDeniedException, InvalidArgumentException, LimitExceededException, ResourceInUseException, ResourceNotFoundException; both return no output. Recorded behavior: on a stream whose retention is the 24-hour default, BOTH increase_stream_retention_period(RetentionPeriodHours=24) and decrease_stream_retention_period(RetentionPeriodHours=24) SUCCEED as no-ops, and the stream stays ACTIVE with RetentionPeriodHours 24 after each. The guards are strict: Increase refuses only a requested value SHORTER than the current one, Decrease only a value LONGER than it — the boundary (equal) is allowed on both.
Emulator: IncreaseStreamRetentionPeriod(24) on a 24-hour stream is refused HTTP 400 `InvalidArgumentException` with `Requested retention period (24 hours) for stream <stream name> can not be shorter than existing retention period (24 hours). Use DecreaseRetentionPeriod API.` — i.e. the comparison is `<=`/`>=` where AWS uses a strict `<`/`>`, so the equal case falls into the refusal branch. (The message's own text contradicts itself: 24 is not shorter than 24.)
Why: idempotent configuration appliers (Terraform/CDK/CloudFormation-style converge loops, retried control-plane calls) re-apply the desired retention on every run; AWS accepts that as a no-op while the emulator fails the apply, so a converged stack cannot be re-applied.
Fix: the boundary comparison in the IncreaseStreamRetentionPeriod and DecreaseStreamRetentionPeriod handlers (accept requested == current on both paths). Open issue 20261027T095220Z-kinesis-6-net-new-root-causes-startstreamencryption-accepts.md covers a retention-too-short refusal but not the equal-value no-op, and does not carry this replay key.
Traces: retention-change-to-current-value-is-accepted-no-op.

=== Cause 4 of 4: the HTTPS front door does not negotiate h2 by ALPN, so SubscribeToShard's enhanced fan-out data plane cannot be reached at all ===
AWS: Smithy models SubscribeToShard with an output member EventStream targeting SubscribeToShardEventStream marked @streaming (required), i.e. an `application/vnd.amazon.eventstream` response body; the operation is offered ONLY over HTTP/2, so the endpoint must advertise `h2` in the TLS ALPN extension. Recorded behavior: a hand-signed HTTP/2 request to the endpoint is answered with an event-stream whose frames are [total_length:4][headers_length:4][prelude_crc:4][headers][payload][message_crc:4] (both CRCs CRC-32 over the preceding bytes), an `initial-response` message precedes the first SubscribeToShardEvent, and each event's JSON payload carries :content-type `application/x-amz-json-1.1`.
Emulator: the TLS handshake is aborted by the server during ALPN with a fatal `no_application_protocol` alert (TLS alert number 120) — `SSL routines:ssl3_read_bytes:tlsv1 alert no application protocol` — when an HTTP/2 client connects to the emulator's HTTPS endpoint. The emulator's listener offers no `h2` protocol in ALPN, so no HTTP/2 session can be established and the enhanced fan-out data plane is unreachable regardless of the SubscribeToShard handler's state. (The address is the emulator's own announced endpoint, so this is the emulator's refusal, not the runner's network.)
Why: every enhanced fan-out consumer (the KCL 2.x default, every SDK `subscribeToShard` call) requires h2 on this endpoint; with ALPN refusing it, no EFO client can connect, and the event-stream framing/CRC contract above can never be exercised.
Fix: the HTTPS front door's TLS configuration — advertise `h2` (alongside `http/1.1`) in ALPN and serve HTTP/2 on the Kinesis endpoint, so the streaming SubscribeToShard response can be framed. Related but distinct open issues: 20261101T034628Z-kinesis-the-https-front-door-aborts-the-tls.md (the front door aborts TLS with decode_error under concurrent PutRecords connections — a different alert and a different trigger), 20261027T201859Z-kinesis-4-net-new-root-causes-subscribetoshard-is.md and 20261029T174012Z-kinesis-subscribetoshard-answers-501-notimplemented-on-the-wire.md (the SubscribeToShard HANDLER is unimplemented over HTTP/1). Neither carries this replay key, and the ALPN gap would still block EFO after the handler is implemented.
Traces: subscribe-to-shard-event-stream-framing-over-a-hand-signed-http2-request.

Use DecreaseRetentionPeriod API. Expected the call to succeed and the stream to read ('ACTIVE', 24) afterwards; the same is expected of DecreaseStreamRetentionPeriod(24).

Cause 4 — subscribe-to-shard-event-stream-framing-over-a-hand-signed-http2-request: AssertionError: the HTTP/2 client failed talking to https://<emulator-endpoint>: session: error:0A000460:SSL routines:ssl3_read_bytes:tlsv1 alert no application protocol:ssl/record/rec_layer_s3.c:918:SSL alert number 120. SubscribeToShard is only offered over HTTP/2, so a target that cannot serve h2 has no enhanced fan-out data plane. (node:http2 connect to the announced endpoint; no :status, zero bytes.)
