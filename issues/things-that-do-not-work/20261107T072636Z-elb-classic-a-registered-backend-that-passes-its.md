# ELB Classic: a registered backend that passes its health check never reaches InService, so every data-plane check stalls (1 cause)

> _Note: this issue was identified against the code base at commit `620c90c23a321396910fd66a692ef2fcecf33f7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceHealth

## Description
1 cause.

Cause 1 of 1: DescribeInstanceHealth never reports State=InService for an instance that is registered with a Classic load balancer and really is answering the configured health-check target, so every check that waits for the control plane's health verdict before exercising the load balancer's data plane never gets past that wait. Failing checks: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.

AWS: Smithy: DescribeInstanceHealth (input DescribeEndPointStateInput {LoadBalancerName (AccessPointName) required, Instances}, output DescribeEndPointStateOutput {InstanceStates: list of InstanceState}); modeled errors AccessPointNotFoundException (awsQueryError LoadBalancerNotFound, HTTP 400) and InvalidEndPointException (awsQueryError InvalidInstance, HTTP 400). InstanceState.State documents the valid values InService | OutOfService | Unknown; InstanceState.ReasonCode documents ELB | Instance | N/A; InstanceState.Description enumerates the exact permitted sentences, including 'Instance registration is still in progress.' and 'Instance has failed at least the UnhealthyThreshold number of health checks consecutively.' On AWS the reported state is the OUTCOME of the load balancer actually probing each registered instance on the load balancer's health-check Target (here HTTP:80/ping or HTTP:80/ok, Interval 5, Timeout 2, HealthyThreshold 2): an instance that answers 200 on that target for HealthyThreshold consecutive checks becomes State=InService with ReasonCode='N/A' and Description='N/A', and only an instance that fails UnhealthyThreshold consecutive checks becomes State=OutOfService / ReasonCode='Instance' / Description='Instance has failed at least the UnhealthyThreshold number of health checks consecutively.' Those Description strings are fixed AWS text; the only request/state-derived value in the member is InstanceId (and the load balancer named in the request). The transition is therefore a function of what the backend serves, not of elapsed time since registration.

Emulator: the health of a registered instance is a pure clock function of the registration instant and never a probe result, so InService is unreachable by construction. services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/state.rs states it outright on LoadBalancer::instance_health: 'No emulated instance serves a health-check target, so every check an instance owes fails' — before UnhealthyThreshold * HEALTH_CHECK_SPAN has elapsed it returns the registration-in-progress triple, and after it the failed-health-checks triple; there is no path to InService / 'N/A' / 'N/A'. The handler (src/ops/describe_instance_health.rs) faithfully projects that, so each of the five checks blocks in its DescribeInstanceHealth poll for State=='InService' (the checks' own deadlines are 420s) and the harness kills the check: 'Check timed out after 60.0s'. Because the wait is the first leg, the data-plane legs of these checks (an unsigned HTTP GET to the minted DNS name returning the backend's marker, AWSELB cookie pinning, cross-zone spreading across pinned node addresses) were never reached in this run and are not separately claimed here — but a fix that only flips the health verdict will expose them next.

Why: a client cannot tell a healthy backend from an unhealthy one. Every registration-verification loop, SDK waiter, deploy health gate and 'wait until InService before sending traffic' step built on DescribeInstanceHealth blocks until its own timeout or concludes the fleet is permanently out of service, and the emulated load balancer can never be in the one state in which AWS routes traffic to an instance.

Fix: the per-load-balancer instance-health state and the health-check evaluation that feeds it (LoadBalancer::instance_health / the health-check configuration in the ELB Classic crate's state, read by the DescribeInstanceHealth handler) — health must be derived from an actual probe of the registered instance on the load balancer's configured Target/Interval/Timeout thresholds, with HealthyThreshold consecutive successes yielding InService / 'N/A' / 'N/A' and UnhealthyThreshold consecutive failures yielding OutOfService / 'Instance' / 'Instance has failed at least the UnhealthyThreshold number of health checks consecutively.', instead of a registration-timestamp countdown that always ends in failure.

Related (not covering this): open issue 20261030T195633Z-elasticloadbalancing-elb-classic-describeinstancehealth-serializes-instancestates-as-an-empty concerns InstanceStates being serialized as an empty scalar and reaching the OutOfService triple; the handler now emits members, and this cause is the opposite verdict — a healthy backend never reaching InService.

Traces: elb.registered-instance-serves-real-http-through-elb-dns-name, elb.instance-health-decides-whether-real-http-reaches-the-backend, elb.lb-cookie-stickiness-pins-a-client-to-one-registered-instance, elb.lb-cookie-stickiness-pins-client-to-one-instance, elb.cross-zone-load-balancing-spreads-requests-beyond-the-node-zone.

## Evidence
Cause 1 — DescribeInstanceHealth.
Expected (AWS): after a backend serving the configured health-check target passes HealthyThreshold consecutive checks, DescribeInstanceHealth returns one InstanceState per described instance with InstanceId = the registered instance, State='InService', ReasonCode='N/A', Description='N/A'. 'InService', 'N/A' and the Description sentences are fixed AWS text; InstanceId and the load balancer name come from the request/state.
Actual (emulator): the state returned for a registered, healthy instance is only ever the registration-in-progress triple (State='OutOfService', ReasonCode='ELB', Description='Instance registration is still in progress.') and then the failed-checks triple (State='OutOfService', ReasonCode='Instance', Description='Instance has failed at least the UnhealthyThreshold number of health checks consecutively.'). InService is unreachable; HTTP status is 200 in both cases, so the divergence is the value, not the wire shape.
Replay verdict for all five checks: '[mismatch] Check timed out after 60.0s' — each blocks in its _wait_instance_state(..., 'InService') poll (checks' own deadline 420s) before any assertion runs.
Code evidence: services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/state.rs, LoadBalancer::instance_health (around lines 890-914) — doc comment 'No emulated instance serves a health-check target, so every check an instance owes fails' and a match that returns HEALTH_REGISTRATION_IN_PROGRESS or HEALTH_FAILED_HEALTH_CHECKS and nothing else; services/service-com-amazonaws-elasticloadbalancing-elasticloadbalancing-v7/src/ops/describe_instance_health.rs lines 207-218 project that triple into every InstanceState.
Model evidence: InstanceState.State 'Valid values: InService | OutOfService | Unknown'; InstanceState.ReasonCode 'Valid values: ELB | Instance | N/A'; InstanceState.Description enumerates 'N/A', 'Instance registration is still in progress.' and 'Instance has failed at least the UnhealthyThreshold number of health checks consecutively.' among its permitted sentences.
