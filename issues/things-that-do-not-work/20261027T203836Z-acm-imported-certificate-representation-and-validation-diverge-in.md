# ACM imported-certificate representation and validation diverge in three places: Issuer is a full DN instead of the issuer CN, an unsupported RSA key size is refused with the wrong error class, and certificates with no Extended Key Usage extension are never reported or selectable under the NONE sentinel (3 causes)

> _Note: this issue was identified against the code base at commit `5d5ee4285f9d2aaa876a013aeae04fab091110e5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportCertificate

## Description
THREE distinct net-new root causes in ACM's imported-certificate ingestion, projection and ListCertificates filtering. All three are grounded in failing behavioral checks of this suite and a fixer must close ALL THREE before submitting. None is covered by an open issue: 20261027T001842Z-acm-importcertificate-validation-diverges-in-two-places-a.md covers only the chain-to-leaf issuance refusal and the private-key/certificate correspondence refusal, and says nothing about key-size admissibility; 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md Cause 1 covers only Options, DomainValidationOptions[*].ValidationDomain and the KeyAlgorithm wire form, and nothing about Issuer or ExtendedKeyUsages.

Cause 1 of 3: DescribeCertificate reports Issuer as the certificate's full distinguished name instead of the issuing authority's common name.
AWS: Smithy CertificateDetail$Issuer (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json) documents the member as 'The name of the certificate authority that issued and signed the certificate.' Recorded behavior: for an IMPORTED, self-signed certificate whose issuer RDN sequence is CN=<domain>, OU=<organizational unit>, ACM reports Issuer as the issuer's common-name attribute VALUE ALONE -- no 'CN=' prefix, no other RDNs, no commas. The rule is the requirement: Issuer is the common name taken from the certificate's issuer field in the submitted DER; a self-signed import is therefore its own issuer and reports its own CN. The domain and OU in any one run are values from the request's certificate, not part of the contract.
Emulator: Issuer is the RFC 4514 distinguished name of the whole issuer field, e.g. 'CN=<domain>,OU=<organizational unit>' -- CN= prefix and every additional RDN included. services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs builds the stored record with `issuer: distinguished_name(&tbs.issuer)` in imported_certificate(), and DescribeCertificate projects that string unchanged.
Why: a client that compares DescribeCertificate.Issuer against a CA name it knows (to decide whether a certificate came from its own private CA, to group certificates by issuer, or to render the issuer in a console/report) never matches, because every value it sees carries DN syntax AWS does not emit. Renewal and trust-chain selection keyed on the issuer name silently take the wrong branch. Note this is about Issuer only; the form of CertificateDetail$Subject is not in this check's evidence and must not be changed on the strength of this cause.
Fix: the issuer projection of the imported certificate -- imported_certificate() in services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs (store the issuer common name rather than the full DN), or equivalently the CertificateDetail projection that serves DescribeCertificate/the list and search operations, so every reader agrees.
Traces: acm.import-certificate-san-extension-parsed-from-der.

Cause 2 of 3: ImportCertificate refuses a certificate whose RSA key size is outside the KeyAlgorithm enum with InvalidParameterException instead of ValidationException.
AWS: Smithy ImportCertificate models BOTH error classes at HTTP 400 -- ValidationException ('The supplied input failed to satisfy constraints of an Amazon Web Services service.', awsQueryError code ValidationError) and InvalidParameterException ('An input parameter was invalid.'). Smithy KeyAlgorithm admits exactly RSA_1024, RSA_2048, RSA_3072, RSA_4096, EC_prime256v1, EC_secp384r1, EC_secp521r1, so a 1536-bit RSA key has no KeyAlgorithm to be reported under. Recorded behavior: such an import is refused with HTTP 400 and Error.Code 'ValidationException' -- the class ACM uses for defective certificate material generally (the same class it uses for the key/certificate mismatch recorded in 20261027T001842Z-acm-importcertificate-validation-diverges-in-two-places-a.md Cause 2). The status and error code are what this check grades; AWS's message text for this particular refusal is not in evidence here, so the requirement captured is HTTP 400 + ValidationException, and the message must be ACM's wording for the unsupported-key-material class rather than an emulator paraphrase. Hypothesis: the message follows the same fixed-sentence pattern as ACM's other material refusals, with the unsupported algorithm/size as its only variable part.
Emulator: HTTP 400 with Error.Code 'InvalidParameterException' and the paraphrase 'the certificate\'s public key algorithm and size are not ones ACM supports'. In services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs, public_key() returns None for any RSA modulus whose bit length is not in [1024, 2048, 3072, 4096], and imported_certificate() turns that None into invalid_parameter(...), i.e. InvalidParameterException.
Why: clients branch on Error.Code. A caller that catches ValidationException to report 'this key is not an algorithm/size ACM supports' never sees it in the emulator, while the InvalidParameterException it does get is the class this handler also uses for unrelated defects (bad PEM, chain problems, empty issuer, validity window), so the refusal cannot be told apart and automated remediation picks the wrong path. The divergence is exactly the error class, so a test suite that passes against the emulator fails against ACM.
Fix: the key-algorithm admissibility refusal in ImportCertificate's validation -- services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs, the `public_key(&tbs.subject_public_key_info).ok_or_else(|| invalid_parameter(...))` arm in imported_certificate(): raise ValidationException with ACM's message for unsupported key material instead of InvalidParameterException.
Traces: acm.import-certificate-unsupported-key-size-rejected.

Cause 3 of 3: a certificate carrying no Extended Key Usage extension is recorded with an EMPTY ExtendedKeyUsages, so it is never reported or selected under ACM's NONE sentinel and ListCertificates with Includes.extendedKeyUsage=["NONE"] matches nothing.
AWS: Smithy ExtendedKeyUsageName is an enum whose members include the sentinel 'NONE' alongside the real purposes (TLS_WEB_SERVER_AUTHENTICATION, TLS_WEB_CLIENT_AUTHENTICATION, CODE_SIGNING, ..., ANY, CUSTOM); Smithy Filters$extendedKeyUsage ('Specify one or more ExtendedKeyUsage extension values') filters ListCertificates on those same values. Recorded behavior: ACM reports a certificate that carries NO extendedKeyUsage extension under the NONE sentinel, so ListCertificates with Includes.extendedKeyUsage=["NONE"] RETURNS those certificates, and a certificate that does carry TLS_WEB_SERVER_AUTHENTICATION is EXCLUDED from that page (and conversely is the only one returned under Includes.extendedKeyUsage=["TLS_WEB_SERVER_AUTHENTICATION"]). The rule, not any one run's ARNs, is the requirement: absence of the extension IS the value NONE, in both the projection and the filter. The OID ACM publishes alongside the NONE name is not in this check's evidence.
Emulator: extended_key_usages() in services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs returns `Vec::new()` when the DER carries no ExtendedKeyUsage extension (its own comment: 'A certificate carrying no such extension asserts no purpose, which is the empty list'), and matches_filters() in services/service-com-amazonaws-acm-certificatemanager/src/ops/list_certificates.rs keeps a certificate only when one of the REQUESTED names is present in cert.extended_key_usages. The NONE sentinel is produced nowhere in the crate, so Includes.extendedKeyUsage=["NONE"] excludes every certificate that has no EKU extension -- the exact set it is supposed to return -- and answers an empty page. The check consequently never satisfies its poll for those certificates and is killed by the harness: 'Check timed out after 60.0s'. Hypothesis: that poll is where the 60s is spent -- it is the only loop in the check whose predicate the code above can never satisfy, and the legs before it (the four Includes.keyTypes include/exclude cases and the parsed TLS_WEB_SERVER_AUTHENTICATION value on the EKU certificate) are satisfied by the implemented keyTypes filter and EKU parsing. Collateral: because the check dies there, its later assertions -- that the EKU-carrying certificate is returned under Includes.extendedKeyUsage=["TLS_WEB_SERVER_AUTHENTICATION"] and that the default (no Includes) key-type filter includes RSA_2048 while excluding RSA_4096 and EC -- were never exercised and are NOT claimed here as passing.
Why: a client enumerating 'certificates with no extended key usage' -- the documented way to find plain TLS material -- gets an empty page forever and concludes it owns no such certificates, while the same call on AWS returns them; inventory, compliance and rotation sweeps built on that filter silently do nothing. The same missing sentinel means DescribeCertificate reports an empty ExtendedKeyUsages where AWS reports the NONE entry, so a reader cannot distinguish 'no purposes asserted' from 'not parsed yet'.
Fix: the EKU projection and its filter -- synthesize the NONE sentinel for a certificate with no ExtendedKeyUsage extension in extended_key_usages() (services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs) and/or in the shared certificate state's EKU projection, and make the extended_key_usage arm of matches_filters() in services/service-com-amazonaws-acm-certificatemanager/src/ops/list_certificates.rs select those certificates for the requested name 'NONE'; the two must agree so DescribeCertificate and ListCertificates cannot disagree about the same certificate.
Traces: acm.list-certificates-key-type-filter-excludes-others.

## Steps to Reproduce
1. Boot the emulator and point botocore at it (region/account are irrelevant to all three causes).
2. Cause 1: mint a self-signed X.509 certificate whose subject (and therefore issuer) RDN sequence is CN=<some-domain>, OU=<some-org-unit>, with a DNS SAN for <some-domain>; call acm.import_certificate(Certificate=<pem>, PrivateKey=<pkcs8 pem>). Then acm.describe_certificate(CertificateArn=<arn>)['Certificate']['Issuer']. The emulator returns 'CN=<some-domain>,OU=<some-org-unit>'; AWS returns '<some-domain>' (the issuer common name alone).
3. Cause 2: generate a 1536-bit RSA key, self-sign a certificate with it, and call acm.import_certificate(Certificate=<pem>, PrivateKey=<pem>). The emulator answers HTTP 400 Error.Code 'InvalidParameterException' with message 'the certificate's public key algorithm and size are not ones ACM supports'; AWS answers HTTP 400 Error.Code 'ValidationException'. Repeat with any RSA size outside {1024, 2048, 3072, 4096} and with an EC curve outside {prime256v1, secp384r1, secp521r1} -- the same handler arm produces the same wrong class.
4. Cause 3: import three certificates with NO extendedKeyUsage extension (one RSA-2048, one RSA-4096, one EC_prime256v1) and one RSA-2048 certificate WITH ExtendedKeyUsage=[TLS web server authentication]. Call acm.list_certificates(Includes={'keyTypes': ['RSA_1024','RSA_2048','RSA_3072','RSA_4096','EC_prime256v1','EC_secp384r1','EC_secp521r1'], 'extendedKeyUsage': ['NONE']}) and page it fully. The emulator returns a page containing NONE of the three EKU-less certificates (an empty result for that filter); AWS returns exactly those three and excludes the TLS_WEB_SERVER_AUTHENTICATION one. Also call acm.describe_certificate on one of the three and read ExtendedKeyUsages: the emulator reports an empty list where AWS reports the NONE sentinel entry.
5. Re-replay the 3 checks in trace_ids.
