# bedrock-agentcore-control: 2 net-new causes — DeletePolicyEngine answers 501 NotImplemented (so the has-policies ConflictException is unreachable), and the payment-vendor enum ValidationException omits Stripe from the value set

> _Note: this issue was identified against the code base at commit `54eb3746d93e75af91f1e8aa724026a8d6dfba62`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeletePolicyEngine

## Description
This bundle has 2 net-new root causes in bedrock-agentcore-control. Both must be fixed before the issue is closed.

Cause 1 of 2: DeletePolicyEngine is an unimplemented scaffold stub, so the modeled delete contract and its dependency refusal are both unreachable.
AWS: Smithy DeletePolicyEngine — DELETE /policy-engines/{policyEngineId}, success HTTP 202, input {policyEngineId @required @httpLabel, ResourceId @length 12..59, @pattern ^[A-Za-z][A-Za-z0-9_]*-[a-z0-9_]{10}$}, output {policyEngineId, name, policyEngineArn, status (PolicyEngineStatus: ACTIVE|CREATING|UPDATING|DELETING|CREATE_FAILED|UPDATE_FAILED|DELETE_FAILED), statusReasons, createdAt, updatedAt} all @required; modeled errors AccessDeniedException 403, ConflictException 409, ResourceNotFoundException 404, ThrottlingException 429, ValidationException 400, InternalServerException 500. The model's own operation doc states the contract: "The policy engine must not have any associated policies before deletion. ... This is an asynchronous operation. Use the GetPolicyEngine operation to poll the status field to track completion." Recorded behavior: a DeletePolicyEngine issued while the engine still holds one policy is refused 409 ConflictException whose message is the fixed text "Policy engine still contains " + the number of policies still attached + " policy and cannot be deleted" (here the count is 1, taken from the emulator's/service's state, not a constant), and the blocked call has NO effect — the engine stays ACTIVE and the policy is still readable. Once the policy is deleted, the identical DeletePolicyEngine call is accepted and answers status DELETING; the engine then settles to not-found, GetPolicyEngine answering 404 ResourceNotFoundException with the fixed text "Policy engine with ID " + the requested policyEngineId + " not found".
Emulator: every DeletePolicyEngine answers HTTP 501 with Error.Code "NotImplemented" and Error.Message "operation DeletePolicyEngine is scaffolded but not implemented in this emulator". NotImplemented is in none of the operation's modeled error sets. Both checks fail at their first assertion with "expected ConflictException, got 'NotImplemented'" — the dependency refusal, the accepted-delete 202/DELETING response and the post-delete 404 are all unreachable. The suite did NOT mark these checks as blocked-by-a-stub (the 501 was swallowed by each check's own ClientError handler and reported as a code mismatch), so no auto-filed stub issue names this operation; a search of open issues for DeletePolicyEngine returns nothing.
Why: a client cannot delete a policy engine at all, so engine names are never freed and teardown/CloudFormation-style delete waiters never converge; and because 501/NotImplemented is not a modeled error class, SDK error handling sees an unknown failure instead of the ConflictException it is written to branch on.
Fix: implement the operation handler services/service-com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol/src/ops/delete_policy_engine.rs (currently returns Err(crate::scaffolded::Scaffolded::not_implemented("DeletePolicyEngine")) at line 197 and still carries the SCAFFOLDED marker at line 4) over the policy-engine state: refuse with the modeled ConflictException while the engine owns any policy, leaving engine and policies untouched; otherwise accept with 202 and status DELETING and retire the engine so GetPolicyEngine resolves nothing. Note the related open issue 20261108T204036Z-bedrock-agentcore-control-policy-policy-engine-and-api-key-provider-deletes.md: it was recorded against a build where DeletePolicyEngine was accepted but left the engine readable; it does not cover the operation answering 501, and its replay key does not carry either check below.
Traces: bedrock-agentcore-control.delete-policy-engine-with-active-policies-blocked, bedrock-agentcore-control.delete-policy-engine-with-policy-conflict-rejected.

Cause 2 of 2: CreatePaymentCredentialProvider's enum ValidationException enumerates an incomplete vendor value set — it omits Stripe.
AWS: Smithy CreatePaymentCredentialProvider — POST /identities/CreatePaymentCredentialProvider, success HTTP 201, input credentialProviderVendor @required targeting the enum PaymentCredentialProviderVendorType; a value outside the set is refused 400 ValidationException. Recorded behavior (the live service; the on-disk model is behind it): the message is AWS's standard constraint sentence — the fixed text "1 validation error detected: Value at 'credentialProviderVendor' failed to satisfy constraint: Member must satisfy enum value set: [" + the service's accepted vendor values in the service's own order + "]", with the member name taken from the request's offending member. The recorded value set is [Stripe, CoinbaseCDP, StripePrivy]; the count prefix ("1 validation error detected") and the member name are request-derived, the value list is the service's enum.
Emulator: refuses with the right status and the right code (400 ValidationException) but the wrong value list: "1 validation error detected: Value at 'credentialProviderVendor' failed to satisfy constraint: Member must satisfy enum value set: [CoinbaseCDP, StripePrivy]" — Stripe is missing. The on-disk PaymentCredentialProviderVendorType enum lists only [CoinbaseCDP, StripePrivy], so the message is rendered from a stale value set rather than the service's.
Why: the enumerated set in this message is how a client (and a human operator) discovers which vendors the service accepts; a caller told Stripe is not a legal value will never attempt the vendor AWS does accept, and tests that assert the refusal text fail against the emulator. It also masks whether Stripe itself is accepted on the success path.
Fix: the CreatePaymentCredentialProvider input validation / enum-constraint message rendering for PaymentCredentialProviderVendorType (handler services/service-com-amazonaws-bedrockagentcorecontrol-amazonbedrockagentcorecontrol/src/ops/create_payment_credential_provider.rs and the enum the shared validation layer reads) must enumerate the vendors the service accepts, Stripe included, in AWS's order. Downstream of the fix the same check then asserts the vendor-specific key-authenticity refusal, 400 ValidationException with the fixed text "Invalid apiKeySecret format: Expected base64-encoded Ed25519 private key" for a correctly shaped but non-genuine CoinbaseCDP key, and that neither rejected create leaves a provider behind (GetPaymentCredentialProvider must stay 404 ResourceNotFoundException with the fixed text "PaymentCredentialProvider not found").
Traces: bedrock-agentcore-control.delete-payment-credential-provider-nonexistent-not-found.
