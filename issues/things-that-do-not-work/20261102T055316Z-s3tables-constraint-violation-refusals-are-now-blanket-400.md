# s3tables constraint-violation refusals are now blanket 400 BadRequestException with the framework's generic validator text: ValidationException paths lost their code, and enum/pattern paths still miss AWS's fixed sentence (2 causes)

> _Note: this issue was identified against the code base at commit `307ae70e1176afe8148743d9dbd874f3de53a94d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutTableBucketReplication

## Description
REOPENS 20261101T230800Z-s3tables-rejects-invalid-input-with-unmodeled-validationexception-instead.md: its fix left the call refused. That issue's fix re-labelled the generic constraint validator's refusal from `ValidationException` to `BadRequestException` for EVERY s3tables member constraint, without giving each refusal path the identity AWS gives it. The result is two distinct net-new defects: the two paths where AWS genuinely answers `ValidationException` now answer `BadRequestException`, and the paths where AWS answers a service-authored sentence still carry the framework's generic constraint text. Both causes live in the s3tables request-validation layer, are produced BEFORE the operation handler runs, and are therefore independent of this run's scaffold-stub issues (implementing PutTableBucketReplication / PutTableRecordExpirationConfiguration / PutTableBucketEncryption does not close either). Related open issue 20261101T233620Z-s3tables-refusals-diverge-enum-pattern-violations-answer-validationexception.md describes the PRE-fix state of these same paths (it records the emulator answering ValidationException); it does not describe the post-fix state reported here and does not cover the lost ValidationException code, so it does not cover these causes. Both causes must be closed before this issue is submitted.

Cause 1 of 2: the two constraint paths on which AWS really does answer ValidationException now answer BadRequestException.
AWS: for PutTableBucketReplication whose `configuration.rules[0].destinations[0].destinationTableBucketARN` is not a well-formed table-bucket ARN, and for PutTableRecordExpirationConfiguration whose `value.settings.days` is below the modeled minimum, AWS refuses with HTTP 400 and error code `ValidationException`, message "1 validation error detected: Value at '<member path>' failed to satisfy constraint: <constraint>". Fixed text: "1 validation error detected: Value at '", "' failed to satisfy constraint: ", then either "Member must satisfy regular expression pattern: " or "Member must have value greater than or equal to "; variable parts: the member path, derived from the request's shape path (e.g. configuration.rules.1.member.destinations.1.member.destinationTableBucketARN, value.settings.days), and the constraint's own pattern/limit taken from the model, rendered WITHOUT the ^ and $ anchors and WITHOUT the offending value quoted. Smithy (services/service-com-amazonaws-s3tables-s3tablebuckets/smithy-model/com-amazonaws-s3tables-s3tablebuckets.json): PutTableBucketReplication models BadRequestException(400)/ConflictException(409)/NotFoundException(404)/AccessDeniedException(403)/ForbiddenException(403)/TooManyRequestsException(429)/InternalServerErrorException(500); PutTableRecordExpirationConfiguration models BadRequestException(400)/MethodNotAllowedException(405)/NotFoundException(404)/ForbiddenException(403)/TooManyRequestsException(429)/InternalServerErrorException(500) — no ValidationException shape exists in the service model, so this code is the framework-level (untyped) validation refusal: recorded behavior only for the code on these two paths.
Emulator: HTTP 400 with error code `BadRequestException` on both paths.
Why: `ValidationException` is the only code a client can branch on to distinguish a malformed-parameter refusal from the service's own semantic refusals (BadRequestException is also what the service uses for business-rule rejections such as an invalid open-table format or a non-empty namespace). A client that retries or reports differently for parameter errors than for service errors now takes the service-error branch for a plain parameter error, and a `catch ValidationException` arm never fires.
Fix: the s3tables request-validation layer's refusal classification — the generic member-constraint validator must keep answering `ValidationException` on these framework-validated member paths rather than being re-labelled BadRequestException wholesale; the per-operation, service-authored refusals (cause 2) are the ones that need BadRequestException.
Traces: s3tables.put-table-bucket-replication-malformed-config-rejected, s3tables.record-expiration-invalid-days-rejected.

Cause 2 of 2: enum/pattern violations that AWS refuses with a service-authored fixed sentence still carry the framework's generic constraint text.
AWS: three paths answer HTTP 400 BadRequestException with a sentence that is entirely fixed text and contains no value from the request:
  - CreateTable with a `format` outside the OpenTableFormat enum: "The specified open table format is not valid" — and no table is created, so a following GetTable on that name answers 404 NotFoundException "The specified table does not exist.".
  - PutTableBucketEncryption with an `encryptionConfiguration.sseAlgorithm` outside the SSEAlgorithm enum: "The specified SSE algorithm is invalid."
  - PutTableBucketEncryption with a malformed `encryptionConfiguration.kmsKeyArn` under sseAlgorithm=aws:kms: "The specified KMS key ARN is invalid. Only key ARN format 'arn:<partition>:kms:<region>:<account-id>:key/<key-id>' is supported." — the <partition>/<region>/<account-id>/<key-id> placeholders are literal in AWS's message, not substituted from the request.
Smithy: CreateTableRequest.format targets OpenTableFormat (@enum, sole value ICEBERG), required; EncryptionConfiguration.sseAlgorithm targets SSEAlgorithm (@enum values AES256, aws:kms), required; EncryptionConfiguration.kmsKeyArn @length(1,2048) @pattern ^(arn:aws[-a-z0-9]*:kms:[-a-z0-9]*:[0-9]{12}:key/.+)$; both operations model BadRequestException(400). The message wording itself is recorded behavior only (the model does not carry it).
Emulator: the error code is now BadRequestException (so the code assertion passes), but the message is the framework's generic constraint report, which quotes the supplied value, names the member path and recites the model constraint — "1 validation error detected: Value 'PARQUET' at 'format' failed to satisfy constraint: Member must satisfy enum value set: [ICEBERG]", "1 validation error detected: Value 'des-not-a-real-algorithm' at 'encryptionConfiguration.sseAlgorithm' failed to satisfy constraint: Member must satisfy enum value set: [AES256, aws:kms]", "1 validation error detected: Value 'not-a-valid-kms-key-arn' at 'encryptionConfiguration.kmsKeyArn' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(arn:aws[-a-z0-9]*:kms:[-a-z0-9]*:[0-9]{12}:key/.+)$". (The quoted values above are the ones the checks send; they are the request's values filling the emulator's template, not part of the requirement.)
Why: BadRequestException carries no sub-code, so its message is the only discriminator a client has for WHY the request was refused — a client that matches "The specified SSE algorithm is invalid." or "The specified open table format is not valid" to pick a remediation, surface a field-level error, or decide not to retry never matches, and the emulator's message additionally varies per request where AWS's does not.
Fix: per-operation input validation for CreateTable (format) and PutTableBucketEncryption (sseAlgorithm, kmsKeyArn) — refuse with BadRequestException carrying the service's fixed sentence instead of delegating to the generic member-constraint validator's text.
Traces: s3tables.create-table-invalid-format-rejected, s3tables.put-table-bucket-encryption-invalid-algorithm-rejected, s3tables.put-table-bucket-encryption-invalid-kms-key-rejected.
