# bedrock-agent-runtime__lambda__s3vectors: 2 net-new root causes — the Python Lambda runtime provides no AWS SDK (boto3), and its CPython stdlib has no _socket extension so even a vendored SDK cannot do network I/O (29 checks blocked)

> _Note: this issue was identified against the code base at commit `c1082b91874a267e16e5e882b92de2a31503a88d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two distinct defects in the emulator's managed Python Lambda execution environment block every cross-service check in this group that drives s3vectors / bedrock-agent-runtime from inside a deployed function. Both surface on lambda Invoke as a 200 with FunctionError set and the runtime's own fault document as the Payload, instead of the handler's return value.

Note on related work: 20261105T090020Z-bedrock-agent-runtime-lambda-s3vectors-the-python-lambda.md (open) describes the missing-boto3 symptom for this same service heading but carries only the replay key for lambda-bedrock-retrieve-and-generate-positive; the suite did not mark any of the 29 checks below as owned, so they are not covered by it. Many other open issues record the same two environment defects under other service pairings and likewise do not cover these checks: 20261105T074953Z-lambda-scheduler-the-python3-12-invoke-runtime-provides.md, 20261105T081139Z-lambda-rds-secretsmanager-2-net-new-root-causes-e2a51e.md, 20261105T095706Z-lambda-xray-the-lambda-python-runtime-has-no.md, 20261105T083215Z-ec2-lambda-route53-the-lambda-python-runtime-has-no-socket-extension.md. If the runtime is repaired centrally, re-replay the 29 check ids listed here to confirm.

=== Cause 1 of 2: the managed Python runtime ships no AWS SDK, so `import boto3` in a handler faults at module load ===
Failing check ids (19): bedrock-agent-runtime__lambda__s3vectors.cfn-deploy-lambda-bedrock-s3vectors-full-stack-positive, .cfn-deploy-wrong-execution-role-mismatch-negative, .cfn-lambda-role-bedrock-agent-permission-positive, .cfn-lambda-role-missing-bedrock-permission-negative, .cfn-lambda-role-missing-s3vectors-permission-negative, .cfn-lambda-role-s3vectors-permission-positive, .cfn-lambda-s3vectors-policy-wrong-resource-arn-negative, .cfn-stack-update-add-bedrock-agent-permission-positive, .cfn-stack-update-add-s3vectors-permission-positive, .cli-lambda-deploy-role-with-s3vectors-bedrock-policies, .cli-lambda-invoke-missing-s3vectors-permission-negative, .cli-s3vectors-bucket-index-put-query-workflow, .cli-s3vectors-query-vectors-cli-put-sdk-verify, .lambda-bedrock-agent-missing-invokeagent-permission-negative, .lambda-bedrock-agent-missing-retrieve-permission-negative, .lambda-bedrock-retrieve-positive, .pipeline-missing-s3vectors-permission-negative, .pipeline-vector-query-result-count-limit-positive, .pipeline-wrong-vector-index-negative.

AWS: recorded behavior only for the contents of the managed runtime — the Smithy model describes the Invoke wire shape, not the execution environment. AWS's managed Python runtimes (here Runtime=python3.12, Handler=index.handler or lambda_function.lambda_handler, Code.ZipFile containing only the handler module) ship boto3 and botocore preinstalled on the handler's import path, so `import boto3` succeeds with no layer and no vendored dependency. Smithy (lambda Invoke -> InvocationResponse): StatusCode is httpResponseCode, FunctionError is header X-Amz-Function-Error, Payload is the httpPayload blob; http {method: POST, uri: /2015-03-31/functions/{FunctionName}/invocations, code: 200}. On a successful RequestResponse invocation AWS answers 200 with X-Amz-Function-Error ABSENT and Payload equal to exactly the JSON the handler returned. FunctionError is set ("Unhandled" for an uncaught fault, "Handled" for a raised exception) only when the handler itself failed, so a module-load ImportError for boto3 is not an outcome AWS produces for python3.12.

Emulator: Invoke answers HTTP 200 with X-Amz-Function-Error: Unhandled and ExecutedVersion $LATEST, and the Payload is the runtime's fault document rather than the handler's value:
  {"errorMessage": "Unable to import module '<handler module>': No module named 'boto3'", "errorType": "Runtime.ImportModuleError", "requestId": "<per-invocation id>", "stackTrace": []}
Fixed text of that message: errorType "Runtime.ImportModuleError" and the sentence "Unable to import module '<handler module>': No module named '<module>'". Variable parts: the handler module name taken from the function's Handler setting (observed as both `index` and `lambda_function`) and the name of the module that could not be imported (`boto3`). requestId is a per-invocation value and is not part of the requirement. In the three cli-* checks the same fault is observed only as FunctionError=Unhandled with a 182-byte JSON payload, because those harnesses do not decode the body before asserting.

Why: a client gets a Lambda that cannot call any AWS service. Every function whose code reaches another AWS API through the standard SDK — the dominant Lambda shape, and the entire subject of these checks (Lambda -> s3vectors CreateVectorBucket/CreateIndex/PutVectors/QueryVectors/ListVectors, Lambda -> bedrock-agent-runtime Retrieve/InvokeAgent) — dies before the handler body runs. Positive checks never observe the intended effect, and the negative/permission checks are worse than failed: a missing-permission arm that should return an s3vectors or bedrock AccessDeniedException instead returns an import fault, so an emulator user cannot tell a denied call from a broken package and concludes their own deployment zip is wrong — on real AWS vendoring boto3 is unnecessary. Every CFN-deployed and CLI-deployed scenario that fans out through Lambda glue is unreachable.

Fix: the Lambda service's invoke / execution-environment component — the in-process Python runtime that loads the handler module for Invoke must expose boto3 and botocore (configured against the emulator's endpoints and credentials) on the handler's sys.path the way the managed python3.12 runtime does. Not the Invoke serializer: the response wire shape is correct; the environment the handler loads in is missing the SDK.

=== Cause 2 of 2: the runtime's CPython has no `_socket` extension module, so a function that vendors its own boto3/botocore still faults at module load ===
Failing check ids (10): bedrock-agent-runtime__lambda__s3vectors.lambda-s3vectors-createindex-positive, .lambda-s3vectors-createvectorbucket-positive, .lambda-s3vectors-deletevectors-positive, .lambda-s3vectors-dimension-mismatch-negative, .lambda-s3vectors-listvectors-positive, .lambda-s3vectors-missing-putvectors-permission-negative, .lambda-s3vectors-missing-queryvectors-permission-negative, .lambda-s3vectors-putvectors-positive, .lambda-s3vectors-queryvectors-positive, .lambda-s3vectors-wrong-vector-bucket-arn-negative.

AWS: recorded behavior only (the model says nothing about the runtime image). These checks work around Cause 1 by packaging boto3 and botocore themselves — _build_deployment_zip writes index.py plus the whole `boto3` and `botocore` package trees into Code.ZipFile — so on AWS they do not depend on the runtime's SDK at all. They do depend on the managed runtime being a complete CPython: the standard library's `socket` module (imported transitively by botocore's HTTP stack) is backed by the built-in C extension `_socket`, which is present in every AWS-managed Python runtime. A self-contained deployment package therefore imports and runs normally on AWS, and Invoke answers 200 with no X-Amz-Function-Error and the handler's JSON as Payload.

Emulator: Invoke answers HTTP 200 with FunctionError set and this fault document:
  {"errorMessage": "Unable to import module '<handler module>': No module named '_socket'", "errorType": "Runtime.ImportModuleError", "requestId": "<per-invocation id>", "stackTrace": []}
Fixed text: errorType "Runtime.ImportModuleError" and "Unable to import module '<handler module>': No module named '<module>'". Variable parts: the handler module from the Handler setting (`index`) and the missing module (`_socket`). This is a SEPARATE defect from Cause 1 and is not fixed by adding boto3: here `boto3` resolves (it is in the zip) and the import chain dies deeper, on a missing CPython stdlib extension module. It means the runtime offers no socket layer, so no vendored SDK, HTTP client or DNS lookup can work either.

Why: a client cannot work around the missing SDK by bundling it, which is the standard remedy, and cannot run any handler that does network I/O at all (`import socket`, http.client, urllib, requests, a third-party driver). Every in-function s3vectors data-plane assertion in this group — index ARN self-resolution, PutVectors/GetVectors round trips, ListVectors paging, the dimension-mismatch and wrong-bucket-ARN refusals, and the two missing-permission arms that should surface AccessDeniedException — is replaced by an import fault, so none of them observes s3vectors behavior at all.

Fix: the Lambda service's execution-environment component that assembles the Python interpreter/filesystem for the sandbox — it must provide a complete CPython stdlib including the built-in extension modules (`_socket`, and the rest of the set `socket`/`ssl`/`select` depend on), so a handler and any vendored dependency can import `socket`. Again not the Invoke serializer.

Traces: the 29 failing check ids enumerated under the two causes above; see trace_ids.
