# events__logs: an EventBridge CloudWatch Logs target never writes the event, and bus LogConfig logging emits no records (2 causes)

> _Note: this issue was identified against the code base at commit `a57dea262f41459244daf18c6d5b4cdf00e6a648`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents

## Description
Two independent root causes, both of which make every EventBridge-to-CloudWatch-Logs path silent. No refusal is involved in either: the emulator accepts every control-plane call with a 2xx and then never produces the log data AWS produces, so all eight checks are killed at the harness ceiling with `Check timed out after 60.0s`. No open issue covers either cause: the nearest neighbours (20261104T062603Z-ecs-events-logs-an-eventbridge-ecs-target-never.md, 20261104T062603Z-ecs-events-logs-sqs-a-container-oom-kill.md) are about EventBridge *ECS* targets, and the logs-side issues (e.g. 20261029T222444Z-logs-vended-delivery-pipeline-delivery-records-and-destination.md) are about the delivery records' own shape and validation, not about EventBridge writing into a log group.

Cause 1 of 2: a rule target whose ARN is a CloudWatch Logs log group never writes any log event.
AWS: Smithy (eventbridge): PutTargets.Targets is a required TargetList (1-100) whose Target.Arn is required; an accepted target yields FailedEntryCount=0. The delivery semantics are recorded behavior only: when a matched event is put on the bus, EventBridge calls logs:CreateLogStream/logs:PutLogEvents on the target group (authorized by a resource policy on that one group granting principal events.amazonaws.com with Condition ArnEquals aws:SourceArn = the rule ARN) and writes exactly ONE log event per matched event. Its `message` is the event envelope verbatim — version "0", id = the EventId PutEvents returned for that entry, detail-type, source, account = the caller account, time = the entry's Time rendered as %Y-%m-%dT%H:%M:%SZ, region, resources, detail — and the log event's `timestamp` is that envelope time in epoch milliseconds. With an InputTransformer the record's timestamp and message are taken from the rendered template, and a template that renders neither `timestamp` nor `message` is not delivered at all; an event that does not match the rule's pattern (e.g. a detail-type differing only in letter case) is not delivered; and a group carrying no events.amazonaws.com policy is not written to while AWS/Events FailedInvocations counts the attempt. These variable parts (group name, rule ARN, account, region, event ids, timestamps) all come from the request and the emulator's state.
Emulator: CreateLogGroup, PutResourcePolicy, PutRule and PutTargets are all accepted (PutTargets answers FailedEntryCount=0), PutEvents is accepted with FailedEntryCount=0 and real EventIds, and then the target log group stays permanently empty: FilterLogEvents returns no events, and no log stream is created. The checks re-PutEvents up to eight times, polling for up to ~96 s, and still observe nothing before the harness kills them at 60 s. Because delivery never happens at all, the three negative companions (near-miss detail-type withheld, ungranted group withheld, timestamp/message-less template withheld) cannot be distinguished from this universal silence, so they are failures of the same cause rather than independent ones.
Why: a client that wires a rule to a log group — the standard way to observe an event bus — sees an empty log group and concludes no event was published, even though PutEvents reported success. Audit/observability pipelines built on log-group targets, and any assertion that a near-miss was *correctly* withheld, both become unverifiable against the emulator.
Fix: the EventBridge target-delivery dispatcher — add the CloudWatch Logs target kind (envelope serialization, event-time to log-event-timestamp mapping, InputTransformer rendering, and the logs resource-policy authorization check with its FailedInvocations accounting), and hook it into the matched-event delivery path.

Cause 2 of 2: an event bus LogConfig is stored and echoed but produces no bus log records in its vended-logs destination.
AWS: Smithy (eventbridge): CreateEventBus and UpdateEventBus both accept a LogConfig member (Level, IncludeDetail) and both echo it; DescribeEventBus returns it. The data-plane behavior is recorded behavior only: after the bus ARN is registered as a CloudWatch Logs DeliverySource (logType INFO_LOGS or ERROR_LOGS) and a Delivery joins that source to a DeliveryDestination over a /aws/vendedlogs/ log group whose resource policy grants delivery.logs.amazonaws.com, EventBridge writes one JSON record per event into that group — at Level=INFO an EVENT_INGEST_SUCCESS record naming the bus, the EventId, the caller account, log_level "INFO", source and detail_type, carrying event_detail when IncludeDetail=FULL and omitting event_detail entirely when IncludeDetail=NONE; at Level=ERROR an INVOCATION_FAILURE record whose error code is NO_PERMISSIONS, carrying the rule and target ARNs and the refused envelope, for each event a target refused. Before any Delivery exists, nothing is written at all. The bus name, EventId, account, rule/target ARNs and detail are all values from the request and state.
Emulator: UpdateEventBus/CreateEventBus accept LogConfig and DescribeEventBus echoes it back correctly, and PutDeliverySource, PutDeliveryDestination and CreateDelivery are all accepted — but the vended log group never receives a single record, for INFO or for ERROR, with FULL or with NONE. The checks poll FilterLogEvents on the destination group until the harness kills them at 60 s, so neither the INFO ingest record, nor the FULL-vs-NONE event_detail difference, nor the ERROR NO_PERMISSIONS invocation-failure record is ever observable; the "writes nothing before a delivery exists" half also cannot be told apart from the permanent silence.
Why: a client that turns on bus logging to diagnose why a target is not firing gets an empty log group and no signal at all — the very failure it is trying to see (NO_PERMISSIONS on a target) is invisible, and the IncludeDetail=NONE privacy guarantee cannot be shown to be honoured because there is no record either way.
Fix: the EventBridge event-bus logging emitter — on each PutEvents ingest and each target invocation outcome, render the bus log record for the bus's stored LogConfig Level/IncludeDetail and publish it through the registered logs DeliverySource/Delivery to its destination log group; bus-state LogConfig storage is already correct.
