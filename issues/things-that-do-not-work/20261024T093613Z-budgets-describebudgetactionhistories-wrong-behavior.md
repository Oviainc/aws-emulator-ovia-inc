# Action history never records the system-generated status change that completes an execution, so the newest record is permanently *_IN_PROGRESS

_Filed: 2026-10-24T09:36:13Z_
_Operation: DescribeBudgetActionHistories | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `a61b7e3a8f074f2acfd74e18fad3041c10471e17`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

An action's history is the audit log of its status changes: `ActionHistory$Status` is "The status of action at the time of the event" and `ActionHistory$EventType` "distinguishes between whether the events are triggered by the user or are generated by the system" — the `EventType` enum's `SYSTEM` value exists for exactly the transitions the service makes on its own.

The emulator records only caller-triggered events: `CREATE_ACTION` (create_budget_action.rs:284-289), `UPDATE_ACTION` (update_budget_action.rs:249-254) and `EXECUTE_ACTION` carrying the `*_IN_PROGRESS` status (execute_budget_action.rs:262-270). The transition that actually completes the work — `StoredAction::settle_due` moving the action from EXECUTION_IN_PROGRESS to EXECUTION_SUCCESS (or REVERSE_* / RESET_* to its settled status) in src/state.rs — changes `action.status` but appends nothing to `history`. `grep SYSTEM src/` finds no `EVENT_TYPE_SYSTEM` constant at all, so no `SYSTEM` event is ever produced by this service.

Expected: once an execution settles, DescribeBudgetActionHistories reports an additional record whose `Status` is the settled status (EXECUTION_SUCCESS, REVERSE_SUCCESS, STANDBY after a reset) and whose `EventType` is `SYSTEM`, so the history's newest record agrees with what DescribeBudgetAction reports. Actual: the history stops at the user-triggered `EXECUTE_ACTION` record with the `*_IN_PROGRESS` status, while DescribeBudgetAction reports the settled status — the two reads permanently disagree, and the `SYSTEM` EventType value never appears on the wire.

## Evidence

Spec: Smithy shapes `ActionHistory` (Status = "The status of action at the time of the event"; EventType = "This distinguishes between whether the events are triggered by the user or are generated by the system") and `EventType` enum = [SYSTEM, CREATE_ACTION, DELETE_ACTION, UPDATE_ACTION, EXECUTE_ACTION]; DescribeBudgetActionHistories returns those records.
Handler/state: src/ops/describe_budget_action_histories.rs:190-237 returns `stored.history` verbatim; src/state.rs `StoredAction::settle_due` (around line 116) assigns the settled status without calling `record_action_event`; the only event constants defined are EVENT_TYPE_CREATE_ACTION / EVENT_TYPE_UPDATE_ACTION / EVENT_TYPE_EXECUTE_ACTION (src/state.rs:1027-1033).
Tests: tests/all/budget_action_history.rs:592 (`executing_an_action_records_one_execute_action_event`) asserts exactly ONE record for an execution, i.e. the suite currently enshrines the missing settle record; tests/all/budget_action_execution.rs:750 (`the_clock_settles_an_execution_with_no_further_call`) checks the settled STATUS but never the history. No test asserts a SYSTEM event.

## Steps to Reproduce

1. CreateBudget "history-settle" for AccountId 123456789012, then CreateBudgetAction on it and keep the ActionId.
2. ExecuteBudgetAction with ExecutionType APPROVE_BUDGET_ACTION.
3. Wait for the settle to fall due (state.rs ACTION_SETTLES_AFTER) and call DescribeBudgetAction — Action.Status is EXECUTION_SUCCESS.
4. Call DescribeBudgetActionHistories for the same ActionId — the newest record is still {EventType: EXECUTE_ACTION, Status: EXECUTION_IN_PROGRESS}; no record with Status EXECUTION_SUCCESS and no EventType SYSTEM is ever returned, so the history contradicts the action read.
