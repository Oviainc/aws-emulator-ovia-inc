# cloudformation__ram: CreateStack refuses AWS::RAM::Permission and AWS::RAM::PermissionAssociation as unrecognized resource types, so no RAM permission can be deployed from a template

> _Note: this issue was identified against the code base at commit `ae5156e659812a6269d5e057615ff3791f30822e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template resource-type registry does not carry the AWS::RAM::Permission or AWS::RAM::PermissionAssociation resource types, so CreateStack refuses at template-format validation any stack that declares one. Failing check ids: cloudformation__ram.deploy-ram-permission-resource-type-rejected, cloudformation__ram.deploy-ram-resource-share-permission-round-trip-then-delete.

AWS: AWS CloudFormation registers AWS::RAM::Permission and AWS::RAM::PermissionAssociation as supported resource types, so CreateStack ACCEPTS a template declaring them and returns 200 with a StackId; the resource types are then provisioned (or refused) by their registry handlers during the stack operation, not by template-format validation. Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): CreateStack input TemplateBody (@length min 1), output StackId; its modeled errors are only AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException — none of which is the refusal observed here. The 'Template format error: Unrecognized resource types: [...]' ValidationError is recorded behavior only: AWS emits it with HTTP 400 and Code ValidationError, and its message is the fixed text 'Template format error: Unrecognized resource types: [' + the comma-separated list of the template's unregistered type names + ']'. AWS raises it only for a type name it genuinely does not register, which does not include the two RAM types above. Downstream of acceptance, the recordings show the expected behavior for these types: a supported ResourceType deploys to CREATE_COMPLETE and the permission reads back through RAM list_permissions as (ATTACHABLE, <declared resource type>, CUSTOMER_MANAGED), with Ref and Fn::GetAtt Arn both yielding the permission ARN; an unsupported ResourceType is refused by the RAM registry handler (NOT by early validation — DescribeEvents carries no VALIDATION_ERROR row), driving the stack to ROLLBACK_COMPLETE with a CREATE_FAILED ResourceStatusReason of the form 'Resource handler returned message: "<RAM refusal message> (Service: Ram, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)', where the inner RAM message is the service's own text for the rejected resource type (e.g. 'Customer managed permission is not supported for resource type <resourceType>') and the parenthesized ids/counts are per-run values, not part of the template.

Emulator: CreateStack is refused outright. The first check's template declares a single AWS::RAM::Permission and the emulator answers HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::RAM::Permission]'. The second check's template declares a resource share plus a permission plus a permission association and the emulator answers HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::RAM::Permission, AWS::RAM::PermissionAssociation]'. AWS::RAM::ResourceShare is NOT named in that second list, so it is registered and the gap is specifically the two permission types. Because the call raises at CreateStack, no stack is ever created and every downstream assertion of both checks (CREATE_COMPLETE, Ref/GetAtt Arn agreement, RAM read-back of the permission and its policy template and tags, the permission association row, the in-place allowExternalPrincipals update, the handler-level rejection and ROLLBACK_COMPLETE for an unsupported resource type, and the DELETED tombstones after stack delete) is unreachable.

Why: a client that provisions RAM customer-managed permissions declaratively — any CloudFormation, SAM or CDK stack containing an AWS::RAM::Permission or AWS::RAM::PermissionAssociation — cannot deploy at all against the emulator. The failure arrives as a template-format ValidationError at submit time, which a client reads as 'my template is malformed' and will not retry or poll, rather than as a stack operation whose outcome it can observe. The emulator also cannot reproduce AWS's rejection path for an unsupported RAM resource type, since that refusal is supposed to surface as a resource-handler CREATE_FAILED reason with HandlerErrorCode InvalidRequest followed by a rollback, not as an up-front template error; code under test that distinguishes 'bad template' from 'resource refused by the service' takes the wrong branch.

Fix: CloudFormation's template resource-type registry and the RAM resource-type handlers it dispatches to. Register AWS::RAM::Permission and AWS::RAM::PermissionAssociation so template-format validation accepts them, and implement their create/update/delete handlers against RAM state so the create path mints a customer-managed permission (Ref and Fn::GetAtt Arn both the permission ARN, Tags propagated alongside the stack's aws:cloudformation tags), the association path attaches the permission to the declared share, an unsupported ResourceType is refused by the handler and rolls the stack back with the handler-reason envelope, and stack delete tombstones both the share and the permission to status DELETED.

Traces: cloudformation__ram.deploy-ram-permission-resource-type-rejected (single AWS::RAM::Permission; refused with '[AWS::RAM::Permission]'), cloudformation__ram.deploy-ram-resource-share-permission-round-trip-then-delete (share + permission + association; refused with '[AWS::RAM::Permission, AWS::RAM::PermissionAssociation]').

## Evidence
Check cloudformation__ram.deploy-ram-permission-resource-type-rejected
Expected (AWS): CreateStack accepts the template and returns a StackId; the control stack with a supported ResourceType reaches CREATE_COMPLETE and RAM list_permissions reports (status, resourceType, permissionType) == ('ATTACHABLE', 'ssm:Document', 'CUSTOMER_MANAGED'); the stack with an unsupported ResourceType reaches ROLLBACK_COMPLETE with no VALIDATION_ERROR event and a CREATE_FAILED reason parsing to message 'Customer managed permission is not supported for resource type ec2:PrefixList (Service: Ram, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)' with HandlerErrorCode 'InvalidRequest'.
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::RAM::Permission]  (HTTP 400, Code ValidationError)

Check cloudformation__ram.deploy-ram-resource-share-permission-round-trip-then-delete
Expected (AWS): CreateStack accepts the template and returns a StackId; stack reaches CREATE_COMPLETE; Ref == Fn::GetAtt Arn for both the share and the permission; RAM get_resource_shares by name reports (status, allowExternalPrincipals) == ('ACTIVE', False); RAM get_permission reports (resourceType, permissionType) == ('ssm:Document', 'CUSTOMER_MANAGED') with the declared policy template; list_permission_associations reports (shareArn, 'ASSOCIATED'); UpdateStack flipping AllowExternalPrincipals reaches UPDATE_COMPLETE preserving the share ARN and creationTime; after delete_stack both the share and the permission read status 'DELETED'.
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::RAM::Permission, AWS::RAM::PermissionAssociation]  (HTTP 400, Code ValidationError). AWS::RAM::ResourceShare is absent from the unrecognized list, so only the two permission types are unregistered.

Fixed text of the diverging message: 'Template format error: Unrecognized resource types: [' ... ']'. The variable part is the comma-separated list of type names taken from the submitted template's Resources — here AWS::RAM::Permission and AWS::RAM::PermissionAssociation. In the expected handler reason, the fixed text is 'Resource handler returned message: "..." (RequestToken: <token>, HandlerErrorCode: InvalidRequest)' and 'Customer managed permission is not supported for resource type '; the resource type ('ec2:PrefixList' above) comes from the request, while Request ID, RequestToken and SDK Attempt Count are per-run values.

## Steps to Reproduce
1. Point a botocore/boto3 client at the emulator's cloudformation endpoint.
2. Submit a minimal template declaring only a RAM permission:
   cf.create_stack(StackName='t1', TemplateBody=json.dumps({
     'AWSTemplateFormatVersion': '2010-09-09',
     'Resources': {'Permission': {'Type': 'AWS::RAM::Permission', 'Properties': {
       'Name': 'p1', 'ResourceType': 'ssm:Document',
       'PolicyTemplate': {'Effect': 'Allow', 'Action': ['ssm:DescribeDocument','ssm:GetDocument']}}}}}))
   Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::RAM::Permission]' instead of a 200 with a StackId.
3. Add an AWS::RAM::ResourceShare and an AWS::RAM::PermissionAssociation to the same template and resubmit. Observe the refusal now lists '[AWS::RAM::Permission, AWS::RAM::PermissionAssociation]' while AWS::RAM::ResourceShare is accepted, confirming only the two permission types are unregistered.
4. Replay the behavioral checks cloudformation__ram.deploy-ram-permission-resource-type-rejected and cloudformation__ram.deploy-ram-resource-share-permission-round-trip-then-delete; both abort at the first create_stack call.
