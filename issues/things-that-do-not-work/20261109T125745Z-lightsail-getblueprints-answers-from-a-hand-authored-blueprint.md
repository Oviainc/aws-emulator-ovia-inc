# Lightsail GetBlueprints answers from a hand-authored blueprint table

> _Note: this issue was identified against the code base at commit `2061b56961bdd6ee54cec665a2a7c785cb8cb220`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBlueprints

## Description
Two net-new root causes, both in the static instance-blueprint catalog table behind Lightsail GetBlueprints. The operation answers 200 and the response is well formed and correctly shaped, so a client cannot detect either divergence from the envelope: the fault is entirely in the table's CONTENTS. Cause 1 is wrong column values on every row that is served; cause 2 is rows that are not served at all, which also shifts every later list position. Both causes must be closed before submitting.

Cause 1 of 2: every served blueprint row carries emulator-authored description prose, an OS-release `version` instead of the catalog date, and vendor product/licence URLs instead of AWS's marketplace ones.
AWS: Smithy com.amazonaws.lightsail#GetBlueprints is an awsJson RPC op (POST /ls/api/2016-11-28/GetBlueprints, success 200) whose output member `blueprints` is a BlueprintList of com.amazonaws.lightsail#Blueprint, with members blueprintId, name, group, type (BlueprintType enum os|app), description, isActive, minPower, version, versionCode, productUrl, licenseUrl, platform (InstancePlatform enum) and appCategory. Smithy documents `description` as "The description of the blueprint", `version` as "The version number of the operating system, application, or stack", `productUrl` as "The product URL to learn more about the image or blueprint" and `licenseUrl` as "The end-user license agreement URL for the image or blueprint", but fixes no values, so the catalog contents are recorded behavior only. The recording shows AWS serving, per row, its own full marketplace description paragraph, a `version` that is the catalog build date in YYYY.MM.DD form (shared by every row of a catalog generation), a productUrl under aws.amazon.com/marketplace/pp/<prodview-id>, and a licenseUrl under the AWS EULA host d7umqicpi7263.cloudfront.net/eula/product/<id>/<id>.txt. Only the Blueprint members are modelled; none of the quoted recorded strings, ids or dates is itself a requirement beyond being AWS's catalog text rather than the emulator's.
Emulator: blueprintId, name, group, type, isActive, minPower, versionCode and platform are served correctly, but `description` is a one-line emulator-generated sentence of the form "<name> operating system image for a Lightsail instance.", `version` is the OS release year instead of the catalog date, `productUrl` points at the upstream vendor's own site, and `licenseUrl` points at the vendor's licensing page instead of the AWS EULA host. The divergence covers every position the recordings assert.
Why: a client that renders or matches on a blueprint description, pins a blueprint by catalog `version`, or follows the product/licence link to present terms to a user gets emulator prose and a non-AWS link for every image in the catalog. Because blueprintId and name are right, the listing looks correct and the divergence only surfaces downstream, in UI text, licence presentation or version pinning.
Fix: the static instance-blueprint catalog table backing the GetBlueprints handler in the lightsail crate - the description, version, productUrl and licenseUrl columns, for all rows. Not handler or serializer logic: the member set, status and envelope are already right.
Traces: lightsail-catalog-get-blueprints#task#1.

Cause 2 of 2: the blueprint table omits whole blueprint tiers - the Windows SQL Server application blueprints and the tail of the catalog - so the list is short and positions shift.
AWS: recorded behavior only (the model constrains no row set). The recording shows the Windows SQL Server app blueprints following the plain Windows Server OS blueprints and preceding the first Linux entry: at the position after the Windows OS block AWS serves blueprintId 'windows_server_2022_sql_2022_express' (name 'SQL Server 2022 Express', group 'windows_2022_sql_exp_2022', type 'app', platform 'WINDOWS', minPower 2000). The recording also asserts 39 blueprint entries in total.
Emulator: that position holds 'amazon_linux_2023' (group 'amazon-linux', type 'os', platform 'LINUX_UNIX', minPower 0) - the Windows SQL app rows are absent entirely, so the Linux block starts one tier early and every subsequent index is off by the number of missing rows; and the tail of the list is missing too (replay reports the last eight asserted positions as entirely absent, i.e. the emulator serves 31 rows where AWS serves 39). Status 200 -> 200 in both fixtures.
Why: a blueprint that is not listed cannot be selected, so no SQL-Server (or other omitted-tier) instance workflow can be driven against the emulator at all. In addition, a client that reads the catalog by position gets a Linux OS image where AWS serves a Windows app image - including minPower 0 instead of the app blueprint's higher minimum - which silently permits pairing the blueprint with a bundle whose `power` AWS would reject. This is listed as a separate cause from cause 1 because it is a missing-row fault rather than a wrong-column fault, it is observed through a different fixture path, and correcting the columns of the served rows does not close it.
Fix: the same static instance-blueprint catalog table - add the missing Windows SQL Server app rows in AWS's order, and the omitted tail rows, with their type/group/platform/minPower values.
Traces: lightsail-catalog-and-operations-lifecycle#task#4 (and the same missing-tail positions in lightsail-catalog-get-blueprints#task#1).

Not covered by, and not a duplicate of, any open issue: replay reported stub_path empty and owned_by EMPTY for both clusters, so no open issue carries either replay key. The open issue 'Lightsail catalog tables still serve emulator-authored descriptions, prices and truncated tiers' (20261031T194833Z-lightsail-catalog-tables-still-serve-emulator-authored-descriptions.md) is the same family and describes the sibling tables (GetBundles, GetRegions, GetRelationalDatabaseBlueprints, GetRelationalDatabaseBundles) whose clusters replay DOES report as owned; it does not own these two GetBlueprints clusters and they are re-filed here so they are gated and re-replayed. The resolved issue 'Lightsail static catalog listings serve stale, reordered and incomplete entries' covers an earlier state of these tables and covers nothing now.
