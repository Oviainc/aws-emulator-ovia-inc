# ec2 instance-type catalog pages a1-c9g through r9g-z1d serve synthesized attributes

> _Note: this issue was identified against the code base at commit `c1a08d4a76589d569f176ed5dae8399fc2d0472d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
This issue bundles 5 causes — one per instance-family page of the recorded DescribeInstanceTypes catalog sweep. All five are the same defect seen on a different slice of the catalog: the emulator does not serve AWS's per-instance-type facts, it DERIVES them from the instance-type name (size multiplier x a family template) and OMITS the optional members AWS populates. A fixer must close all five before submitting.

Shared root cause: ec2 DescribeInstanceTypes answers 200 with a well-formed InstanceTypeInfo per requested type, but the member VALUES are emulator-computed rather than catalog facts, and several modeled members are absent entirely. Each cause below names the fixture page, its step, and the attribute groups that diverge there.

---
Cause 1 of 5 — page a1-c9g (6 diverging clusters; representative fixture ec2-catalog-describe-instance-types-a1-c9g step task#29, c8i-flex.* family)
AWS: Smithy com.amazonaws.ec2#InstanceTypeInfo binds EbsInfo (-> EbsInfo.ebsOptimizedInfo -> com.amazonaws.ec2#EbsOptimizedInfo with baselineBandwidthInMbps:integer, baselineIops:integer, baselineThroughputInMBps:double, maximumBandwidthInMbps:integer, maximumIops:integer, maximumThroughputInMBps:double), EbsInfo.maximumEbsAttachments, NetworkInfo, PlacementGroupInfo, ProcessorInfo, DedicatedHostsSupported, NitroEnclavesSupport, PhcSupport and RebootMigrationSupport. The model defines the SHAPE of these members only; the per-type VALUES are catalog facts the service returns and are not expressible in the model, so for the values this is recorded behavior only. The recording shows AWS returning, for c8i-flex sizes, distinct baseline and maximum EBS figures (baseline strictly below maximum), ebsInfo.attachmentLimitType 'dedicated', dedicatedHostsSupported false, a populated networkInfo.bandwidthWeightings list, a populated networkInfo.connectionTrackingConfiguration, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.networkCards, a three-entry placementGroupInfo.supportedStrategies, processorInfo.supportedFeatures and a cpuBurstModel member (cpuBurstModel is not in the checked-in model revision, so it is recorded behavior only).
Emulator: returns a single derived EBS figure for both baseline and maximum (baseline == maximum), e.g. 6800 Mbps / 30000 IOPS / 850 MB/s where the recording has 5000 and 10000 Mbps, 20000 and 40000 IOPS, 625.0 and 1250.0 MB/s; reports attachmentLimitType 'shared' instead of 'dedicated', dedicatedHostsSupported true instead of false, maximumEbsAttachments 28 instead of the per-type value (32 for c8i-flex.8xlarge); and omits cpuBurstModel, networkInfo.bandwidthWeightings, networkInfo.connectionTrackingConfiguration, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport and networkInfo.networkCards (reported as 'missing (expected ..., got None)').
Why: a client sizing EBS throughput, picking a dedicated-host-capable type, counting attachable volumes, or reading ENA/bandwidth-weighting capability gets fabricated hardware facts. Capacity planners and the DescribeInstanceTypes-driven selection logic in autoscaling/launch-template tooling branch on exactly these members, so they take the wrong branch, and absent optional members make typed SDK getters return null where AWS always supplies a value.
Fix: ec2's DescribeInstanceTypes handler and the instance-type catalog state it reads. The catalog must be a data table of AWS per-type facts keyed by instance type, not a size-multiplier derivation, and the serializer must emit every member the catalog carries instead of dropping the optional ones.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#29 (representative), ec2-catalog-describe-instance-types-a1-c9g#task#30 (c8ib.* family: baseline/maximum EBS figures, attachmentLimitType, maximumEbsAttachments 28 vs 128, networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout 432000 vs 350, missing networkInfo.efaInfo/efaSupported).

---
Cause 2 of 5 — page c9gd-m6gd (31 diverging clusters; representative fixture ec2-catalog-describe-instance-types-c9gd-m6gd step task#2, d2.* family)
AWS: same modeled members as Cause 1, plus InstanceTypeInfo.InstanceStorageInfo (disks.item.count, disks.item.sizeInGB, totalSizeInGB), InstanceTypeInfo.CurrentGeneration:boolean, EbsInfo.ebsOptimizedSupport and SupportedRootDeviceTypes. Values are recorded behavior only: for the previous-generation d2 family the recording has currentGeneration false, ebsOptimizedSupport 'default', a populated ebsInfo.ebsOptimizedInfo, attachmentLimitType 'shared', maximumEbsAttachments 40, instance storage of 3 disks x 2048 GB totalling 6144 GB, and populated networkInfo.connectionTrackingConfiguration / defaultNetworkCardIndex.
Emulator: reports currentGeneration true for a previous-generation family, ebsOptimizedSupport 'unsupported' with ebsInfo.ebsOptimizedInfo omitted entirely, attachmentLimitType 'dedicated' instead of 'shared', maximumEbsAttachments 27 instead of 40, and instance storage of 4 disks x 1500 GB totalling 6000 GB — a disk geometry and total that no AWS d2 size has.
Why: currentGeneration and ebsOptimizedSupport are what migration and cost tooling uses to flag legacy types and to decide whether EBS optimization must be requested explicitly; inverted values make the emulator recommend the opposite action. The fabricated disk geometry makes any instance-store capacity calculation wrong.
Fix: same component as Cause 1 — the ec2 instance-type catalog state must carry currentGeneration, ebsOptimizedSupport, attachmentLimitType, maximumEbsAttachments and the real disk geometry per type rather than deriving them, and must not drop ebsOptimizedInfo for types that have it.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#2, ec2-catalog-describe-instance-types-c9gd-m6gd#task#3 (d3.* family: maximumEbsAttachments 28 vs 3, 26x1846 GB vs 24x1980 GB instance storage, totalSizeInGB 47996 vs 47520, missing defaultNetworkCardIndex/enaSrdSupported).

---
