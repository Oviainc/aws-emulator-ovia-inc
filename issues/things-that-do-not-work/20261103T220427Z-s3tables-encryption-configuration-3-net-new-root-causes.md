# s3tables encryption configuration: 3 net-new root causes — DeleteTableBucketEncryption answers 501, and PutTableBucketEncryption's KMS-key access check and IAM authorization denial are unreachable

> _Note: this issue was identified against the code base at commit `2fe3407ad3a572d7c56bcafd231aa855d1c09ca1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteTableBucketEncryption

## Description
Three net-new root causes in the S3 Tables table-bucket encryption surface. None of them is carried by any open issue: `20261102T065133Z-s3tables-encryption-metrics-replication-put-operations-answer-501.md` states the PutTableBucketEncryption kmsKeyArn-required validation and the concurrent-put convergence rules and lists neither of the two Put checks below; `20261101T233620Z-s3tables-puttablebucketencryption-stub.md` and `20261101T233620Z-s3tables-six-replication-metrics-record-expiration-operations-are.md` only ask that handlers exist and state no authorization or KMS-access semantics; and NO open issue mentions DeleteTableBucketEncryption at all.

Cause 1 of 3: DeleteTableBucketEncryption is a scaffold stub, so neither its not-found refusal nor its revert-to-default effect exists.
AWS: Smithy models DeleteTableBucketEncryption as DELETE /buckets/{tableBucketARN}/encryption, @idempotent, success code 204 with an empty (Unit) output, input only `tableBucketARN` (TableBucketARN, @required, httpLabel, pattern ^(arn:aws[-a-z0-9]*:[a-z0-9]+:[-a-z0-9]*:[0-9]{12}:bucket/[a-z0-9_-]{3,63})$); modeled errors are BadRequestException 400, ConflictException 409, ForbiddenException 403, NotFoundException 404, InternalServerErrorException 500, TooManyRequestsException 429. `NotImplemented` is not among them, and 501 is not a modeled status. Recorded behavior: a table bucket that has only the IMPLICIT default encryption (GetTableBucketEncryption reports sseAlgorithm=AES256 with no kmsKeyArn and was never given an explicit configuration) refuses the delete with HTTP 404, error code `NotFoundException` and message `The specified encryption configuration does not exist.` — that message is entirely fixed text; nothing is interpolated from the request or state. The refusal has no effect: a following GetTableBucketEncryption returns exactly the same configuration as before. Once an EXPLICIT configuration has been put (either {sseAlgorithm: AES256} or {sseAlgorithm: aws:kms, kmsKeyArn: <a KMS key ARN of the caller's account>}), the delete succeeds (204, empty body) and reverts the bucket to the implicit default: GetTableBucketEncryption then reports sseAlgorithm=AES256 and NO kmsKeyArn.
Emulator: every DeleteTableBucketEncryption request answers HTTP 501 with error code `NotImplemented` and message `operation DeleteTableBucketEncryption is scaffolded but not implemented in this emulator`. services/service-com-amazonaws-s3tables-s3tablebuckets/src/ops/delete_table_bucket_encryption.rs still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker and its handle body is `Err(crate::scaffolded::Scaffolded::not_implemented("DeleteTableBucketEncryption"))` (line 186).
Why: a client cannot distinguish "this bucket has no explicit encryption configuration to remove" (a 404 it should treat as already-clean and move on) from a server-class 501 it will retry forever; and because the delete never runs, a bucket's explicit SSE-KMS configuration can never be removed, so the key stays bound to the bucket for the rest of its life.
Fix: implement the handler in services/service-com-amazonaws-s3tables-s3tablebuckets/src/ops/delete_table_bucket_encryption.rs together with the table-bucket encryption state it reads — the state must distinguish "no explicit configuration (implicit AES256 default)" from "explicitly configured", refuse the former with NotFoundException and that fixed message while writing nothing, and clear the stored configuration (including kmsKeyArn) for the latter, answering 204.
Traces: s3tables.delete-table-bucket-encryption-nonexistent-conflict, s3tables.delete-table-bucket-encryption-without-config-rejected.

Cause 2 of 3: PutTableBucketEncryption never checks access to the referenced KMS key, so the ForbiddenException for an inaccessible key ARN is unreachable and nothing refuses an unusable configuration.
AWS: Smithy models PutTableBucketEncryption as PUT /buckets/{tableBucketARN}/encryption, @idempotent, success code 200, input `tableBucketARN` (httpLabel, @required) + `encryptionConfiguration` (@required); ForbiddenException (403, "The caller isn't authorized to make the request.") is modeled. EncryptionConfiguration.sseAlgorithm is @required (enum AES256 | aws:kms) and its documentation states "If you choose SSE-KMS encryption you must grant the S3 Tables maintenance principal access to your KMS key"; kmsKeyArn has @length 1..2048 and pattern ^(arn:aws[-a-z0-9]*:kms:[-a-z0-9]*:[0-9]{12}:key/.+)$. Recorded behavior: a put of {sseAlgorithm: aws:kms, kmsKeyArn: <a syntactically valid key ARN naming a key the caller cannot access — e.g. one in a foreign account or absent from the request's Region>} is refused with HTTP 403 and error code `ForbiddenException`, message `User: <caller principal ARN> is not authorized to perform: kms:DescribeKey on this resource because the resource does not exist in this Region, no resource-based policies allow access, or a resource-based policy explicitly denies access`. Fixed text: `User: `, ` is not authorized to perform: kms:DescribeKey on this resource because the resource does not exist in this Region, no resource-based policies allow access, or a resource-based policy explicitly denies access`. The only variable part is the caller's own principal ARN, taken from the signing identity (what STS GetCallerIdentity reports for the caller) — never a literal from one recording. The refusal is effect-free: the bucket still reports sseAlgorithm=AES256 and no kmsKeyArn, and a following valid {sseAlgorithm: AES256} put succeeds.
Emulator: HTTP 501, error code `NotImplemented`, message `operation PutTableBucketEncryption is scaffolded but not implemented in this emulator` (services/service-com-amazonaws-s3tables-s3tablebuckets/src/ops/put_table_bucket_encryption.rs, handle body at line 191).
Why: a client that mis-types or mis-scopes its CMK gets a retryable server error instead of the 403 that names kms:DescribeKey as the missing permission, so it never learns to grant it; and an implementation added without this check would store an encryption configuration pointing at a key S3 Tables can never use, which later reads would report as valid while every write under it would fail.
Fix: PutTableBucketEncryption's handler in services/service-com-amazonaws-s3tables-s3tablebuckets/src/ops/put_table_bucket_encryption.rs — before any state write, resolve the supplied kmsKeyArn against the KMS key state for the request's account/Region and refuse an unresolvable or inaccessible key with ForbiddenException carrying the kms:DescribeKey message above, leaving the stored configuration untouched.
Traces: s3tables.put-table-bucket-encryption-with-unsupported-kms-key-rejected.

Cause 3 of 3: PutTableBucketEncryption applies no identity-based authorization, so the AccessDeniedException for an unprivileged caller is unreachable.
AWS: the operation's documentation states "You must have the s3tables:PutTableBucketEncryption permission to use this operation"; the model declares ForbiddenException 403 for it (AccessDeniedException 403 is modeled on the sibling GetTableBucketEncryption but not on the Put, so for the Put the code below is recorded behavior only). Recorded behavior: the same put issued by a principal with no s3tables permissions (a freshly assumed role with zero attached policies — implicit deny) is refused with HTTP 403 and error code `AccessDeniedException`, message `User: arn:<partition>:sts::<account-id>:assumed-role/<role-name>/<session-name> is not authorized to perform: s3tables:PutTableBucketEncryption on resource: <table bucket ARN> because no identity-based policy allows the s3tables:PutTableBucketEncryption action`. Fixed text: `User: `, ` is not authorized to perform: s3tables:PutTableBucketEncryption on resource: `, ` because no identity-based policy allows the s3tables:PutTableBucketEncryption action`. Variable parts, all taken from the request and state and never from one recording: the caller's assumed-role session ARN (partition from the target bucket's ARN, the account id, the role name and the role-session name of the signing credentials) and the `tableBucketARN` from the request. The denied call has no effect — the owner's own read still reports the bucket's prior configuration — and the identical put by the bucket owner succeeds, after which the bucket reads sseAlgorithm=AES256.
Emulator: HTTP 501, error code `NotImplemented`, message `operation PutTableBucketEncryption is scaffolded but not implemented in this emulator`; the restricted session is never evaluated at all.
Why: least-privilege testing is impossible — a caller with no permissions gets the same answer as a caller with every permission, so a client (or a policy test) cannot tell an authorization failure from an unavailable service, and an emulator that later implements the Put without this gate would let any principal rewrite another's bucket encryption.
Fix: PutTableBucketEncryption's handler in services/service-com-amazonaws-s3tables-s3tablebuckets/src/ops/put_table_bucket_encryption.rs — resolve the signing principal from the request context and evaluate s3tables:PutTableBucketEncryption against it before mutating state, answering AccessDeniedException with the message above when no identity-based policy allows the action.
Traces: s3tables.put-table-bucket-encryption-without-permission-denied.
