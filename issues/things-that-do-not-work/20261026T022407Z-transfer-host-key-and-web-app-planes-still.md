# Transfer host-key and web-app planes still refuse valid calls: ImportHostKey rejects PEM/PKCS#1 private keys, duplicate-import message is emulator prose, TestIdentityProvider never invokes an AWS_LAMBDA IdP, UpdateWebApp wedges on ConflictException (4 causes)

> _Note: this issue was identified against the code base at commit `13cd51356c86db6d039912819137db7f55e61de7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ImportHostKey

## Description
REOPENS 20261022T202037Z-transfer-host-key-plane-broken-importhostkey-refuses-valid.md: its fix left the call refused. That issue's Cause 1 claimed ImportHostKey would accept "the OpenSSH private-key container (and the PEM/PKCS#8 forms AWS accepts)", and its Cause 4 claimed TestIdentityProvider and UpdateWebApp would be implemented with their modeled behavior. The OpenSSH container form now imports, but a PEM/PKCS#1 private key is still refused (Cause 1 below), TestIdentityProvider still never succeeds against a Lambda-backed IdP (Cause 3), and UpdateWebApp now refuses even an uncontended call (Cause 4). Four distinct root causes, all in the transfer service, each grounded in a failing behavioral check of this suite.

=== Cause 1 of 4: ImportHostKey refuses a well-formed PEM/PKCS#1 private key ===
AWS: Smithy (com.amazonaws.transfer) ImportHostKey.HostKeyBody -> HostKey, @required, @length min 0 max 4096, @sensitive, documented as "The private key portion of an SSH key pair. Transfer Family accepts RSA, ECDSA, and ED25519 keys."; modeled errors InvalidRequestException (client, HTTP 400), ResourceExistsException (409), ResourceNotFoundException (404), ThrottlingException (429), InternalServiceError/ServiceUnavailableException (503). Output: ServerId @required plus HostKeyId @required, @length 25, pattern ^hostkey-[0-9a-f]{17}$. An RSA private key serialized as a PEM PKCS#1 / TraditionalOpenSSL document (armour "-----BEGIN RSA PRIVATE KEY-----" -- what ssh-keygen -m PEM and most key tooling emit) IS an RSA private key within the documented set, so the call succeeds with HTTP 200 and a HostKeyId.
Emulator: the call is refused with HTTP 400 InvalidRequestException, message "HostKeyBody must be a private key in OpenSSH format" (that whole string is fixed text; it interpolates nothing). The validator admits only the OpenSSH private-key container form -- an Ed25519 key in that container does import in another check in the same suite -- so every PEM PKCS#1 (and, by the same code path, PKCS#8) key is rejected regardless of algorithm.
Why: a client or IaC template that supplies an RSA host key in the standard PEM form cannot seed a server's host key at all, and gets a 400 that claims its valid key is malformed. Everything downstream of the import (DescribeHostKey/ListHostKeys fingerprint agreement, and the rule that DescribeServer's legacy top-level HostKeyFingerprint stays pinned to the server's original key) is unreachable for such a client.
Fix: the HostKeyBody validation in the ImportHostKey handler of the transfer service crate -- it must parse PEM PKCS#1 and PKCS#8 RSA/ECDSA/ED25519 private keys in addition to the OpenSSH container, and only then reject.
Traces: transfer.imported-host-key-active-without-downtime-window.

=== Cause 2 of 4: the duplicate-host-key refusal message is emulator-authored prose built from request and state values ===
AWS: recorded behavior only for the text (the model carries no message template). ImportHostKey called twice with identical key material on the same server is refused the second time with ResourceExistsException (modeled HTTP 409), and the Message is the fixed service text "Host key already exists" -- the message is ENTIRELY fixed text, with no variable parts: no server id, no host key id, no fingerprint.
Emulator: the error CODE is right (ResourceExistsException) but the Message is a different, emulator-invented sentence that interpolates request and state values: "Server <ServerId> already holds host key <HostKeyId> with fingerprint SHA256:<base64-digest>" (observed instance: "Server s-00000000000000001 already holds host key hostkey-00000000000000003 with fingerprint SHA256:VCY3mjAhnbGqGzqZnwadL6AbDRDW/crnDQk/kF/+o+E"). In that message "Server ", " already holds host key " and " with fingerprint " are the emulator's own fixed text, while the server id and host key id come from the request/state and the fingerprint is computed from the submitted key -- AWS supplies none of those.
Why: the message is part of the error contract. A client that matches on it (string equality, a regex, or a log assertion) does not recognise the duplicate-key condition, and a message leaking the colliding host key id and its fingerprint also discloses state AWS does not return on this path.
Fix: the ResourceExistsException message construction in the ImportHostKey handler's validation/error path in the transfer crate (fixed issue 20261024T171640Z-transfer-refusal-message-rules-diverge-on-createconnector-deleteaccess.md corrected this message-rule class for CreateConnector, DeleteAccess/DescribeAccess and ListProfiles, but not for ImportHostKey).
Traces: transfer.import-hostkey-duplicate-resource-exists-rejected.

=== Cause 3 of 4: TestIdentityProvider against an AWS_LAMBDA identity provider never returns StatusCode 200 ===
AWS: Smithy TestIdentityProvider input ServerId @required pattern ^s-([0-9a-f]{17})$ and UserName @required, plus ServerProtocol, SourceIp, UserPassword; output StatusCode @required (integer), Url @required, Response, Message; modeled errors InvalidRequestException (400), ResourceNotFoundException (404), InternalServiceError/ServiceUnavailableException (503). Against a server created with IdentityProviderType=AWS_LAMBDA and IdentityProviderDetails.Function=<function ARN>, the operation actually invokes that function and returns StatusCode 200 with Response carrying the function's own JSON response body (recorded behavior for the body relay). The two rejection paths the same check exercises do behave: SERVICE_MANAGED server -> InvalidRequestException "<ServerId> not configured for external auth" (fixed text " not configured for external auth" with the request's ServerId prefixed), and a well-formed but nonexistent ServerId -> ResourceNotFoundException "Unknown server" (wholly fixed text).
Emulator: the Lambda-backed call never produces StatusCode 200. The check polls TestIdentityProvider every 3 seconds against the AWS_LAMBDA server waiting for StatusCode 200 and never gets one, so the check is killed by the harness with "Check timed out after 60.0s" -- it is the only unbounded wait in the check, and the SERVICE_MANAGED/unknown-server assertions ahead of it had already passed. Hypothesis: the handler synthesizes a response without dispatching to the configured Lambda function, so it returns a non-200 StatusCode (and no function body in Response) for every AWS_LAMBDA server.
Why: TestIdentityProvider exists precisely so a client can verify a custom identity provider before putting it in front of users. A probe that can never succeed makes the AWS_LAMBDA IdP unverifiable, and a client that (correctly) retries until StatusCode 200 hangs instead of failing fast.
Fix: the TestIdentityProvider handler in the transfer crate -- it must resolve IdentityProviderDetails.Function, invoke that function through the lambda service's state, and map its result into StatusCode/Response/Message/Url.
Traces: transfer.test-identity-provider-wrong-server-type-error.

=== Cause 4 of 4: UpdateWebApp latches an "update in progress" state, so a later uncontended UpdateWebApp is refused forever ===
AWS: Smithy UpdateWebApp input WebAppId @required pattern ^webapp-[0-9a-f]{17}$ plus IdentityProviderDetails/AccessEndpoint/WebAppUnits/EndpointDetails; output WebAppId @required; modeled errors AccessDeniedException (403), ConflictException (409), InvalidRequestException (400), ResourceNotFoundException (404), ThrottlingException (429). Two UpdateWebApp calls fired simultaneously at one web app yield exactly one 200 winner and one 409 ConflictException loser; the conflict is transient, so once the in-flight update settles a subsequent uncontended UpdateWebApp(WebAppUnits={'Provisioned': 1}) succeeds with 200 and an independent DescribeWebApp then reports WebAppUnits.Provisioned == 1.
Emulator: after the contended pair, the following plain sequential UpdateWebApp on the same WebAppId is refused with HTTP 409 ConflictException, message "An update is already in progress for this web app; wait for it to complete and try again." -- raised uncaught out of the positive-control call, i.e. the in-progress marker / per-resource mutation lock taken by the concurrent writers is never released. The web app is left permanently un-updatable; waiting and retrying, which the message itself instructs, never clears it. (The message text is also emulator-authored prose that is not verified against AWS's wording for this class; the wedged state is the defect.)
Why: a client that handles 409 the documented way -- wait and retry -- loops forever, and the web app can never be resized or reconfigured again. A conflict that is supposed to be transient has become terminal, which is worse than no locking at all.
Fix: the UpdateWebApp handler and the web-app state in the transfer crate -- the in-progress/lock flag must be cleared on both the success and failure exits of an update so only genuinely overlapping calls conflict. Open issue 20261025T121006Z-transfer-web-app-plane-incomplete-updatewebapp-and-deletewebappcustomization.md describes UpdateWebApp answering 501 NotImplemented, a different and now-superseded failure mode, and does not cover this latched conflict.
Traces: transfer.update-webapp-concurrent-modification-conflict.

## Evidence
Cause 1 — expected: import_host_key(ServerId='s-...', HostKeyBody=<2048-bit RSA private key, PEM TraditionalOpenSSL/PKCS#1>) -> HTTP 200, {ServerId, HostKeyId ^hostkey-[0-9a-f]{17}$}. actual: botocore.errorfactory.InvalidRequestException — "An error occurred (InvalidRequestException) when calling the ImportHostKey operation: HostKeyBody must be a private key in OpenSSH format" (HTTP 400).

Cause 2 — expected: the second import_host_key with identical key material -> code 'ResourceExistsException', Message exactly 'Host key already exists' (no interpolated values). actual: code 'ResourceExistsException' (correct) with Message 'Server s-00000000000000001 already holds host key hostkey-00000000000000003 with fingerprint SHA256:VCY3mjAhnbGqGzqZnwadL6AbDRDW/crnDQk/kF/+o+E'; the assertion that failed was `assert message == "Host key already exists"`.

Cause 3 — expected: test_identity_provider(ServerId=<AWS_LAMBDA-backed server>, UserName='sim2real-probe-user', UserPassword=..., ServerProtocol='SFTP') -> StatusCode 200 with Response containing the invoked function's own body. actual: StatusCode never becomes 200; the check's 3-second poll loop runs to its 60s deadline and the harness reports "Check timed out after 60.0s". The preceding refusal assertions in the same check (SERVICE_MANAGED -> InvalidRequestException '<ServerId> not configured for external auth'; bogus 's-00000000000000000' -> ResourceNotFoundException 'Unknown server') had passed.

Cause 4 — expected: after two concurrent update_web_app calls (exactly one 200 winner, one 409 ConflictException loser), a subsequent uncontended update_web_app(WebAppId=..., WebAppUnits={'Provisioned': 1}) -> HTTP 200, and describe_web_app then reports WebAppUnits.Provisioned == 1. actual: botocore.errorfactory.ConflictException — "An error occurred (ConflictException) when calling the UpdateWebApp operation: An update is already in progress for this web app; wait for it to complete and try again." raised from the uncontended call, aborting the check.
