# bedrock-agent-runtime: the AOSS collection endpoint answers the OpenSearch REST index create with 400 SerializationException 'missing required header x-amz-target', so Retrieve's ResourceNotFoundException contract for an unknown knowledgeBaseId is never reached

> _Note: this issue was identified against the code base at commit `edd8d27229a8bc99e308a4b32d393f13d6f32cb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve

## Description
ONE net-new root cause, grounded in the single failing behavioral check listed under the `bedrock-agent-runtime` service heading that the replay report did NOT mark ALREADY FILED or OWNED. Overlap note: the open issues 20261104T072704Z-bedrock-agent-runtime-the-opensearch-serverless-vector-store.md and 20261029T171944Z-bedrock-agent-runtime-2-net-new-causes-the.md describe the same wall under this service token, but the suite bound neither of them to this check's replay key (the report lists this check with no OWNED marker), so it is filed here to carry that key; if either of those lands first this closes with it.

=== Cause 1 of 1: a VECTORSEARCH collection's published collectionEndpoint serves the AWS-JSON RPC front door instead of the OpenSearch REST data plane, so the vector index a knowledge base needs cannot be created and Retrieve is never called ===
AWS: the OpenSearch Serverless collection data plane is the OpenSearch REST API and is not Smithy-modeled, so for that leg this is recorded behavior only; the control-plane model does state the contract — Smithy (com.amazonaws.opensearchserverless) documents CollectionDetail.collectionEndpoint as the "Collection-specific endpoint used to submit index, search, and data upload requests to an OpenSearch Serverless collection". Recorded behavior: once a VECTORSEARCH collection is ACTIVE and a data-access policy names the signing principal, a SigV4-signed (service name `aoss`) HTTP PUT of an index body to https://<collectionEndpoint>/<indexName> — exactly what opensearch-py's `indices.create` issues, carrying NO `x-amz-target` header, because the OpenSearch REST API has no RPC target — is accepted and creates the knn_vector index. The knowledge base built on that index then reaches ACTIVE, Retrieve against it returns a `retrievalResults` field, and the identical Retrieve against a well-formed but never-provisioned knowledgeBaseId is refused with HTTP 404 ResourceNotFoundException (Smithy: Retrieve errors include ResourceNotFoundException, httpError 404; knowledgeBaseId is an httpLabel matching ^[0-9a-zA-Z]{10}$) whose message is "Knowledge Base with id <knowledgeBaseId> does not exist" — fixed text "Knowledge Base with id " + " does not exist", with the id taken verbatim from the request path, never from a recorded run.
Emulator: the index-create PUT against the host the emulator itself published as collectionEndpoint is answered HTTP 400 with body {"__type":"SerializationException","message":"missing required header `x-amz-target`"} — fixed emulator text, nothing in it derived from the request — surfaced to the client as opensearchpy.exceptions.RequestError(400, ...). The published endpoint host therefore lands on the AWS-JSON `x-amz-target` dispatcher rather than an OpenSearch REST handler. The check retries the create for 60 s and then asserts "vector index sim2real-kb-index could not be created", so no knowledge base exists, no Retrieve call is ever issued, and neither the positive control nor the ResourceNotFoundException refusal is observed.
Why: a client building the standard Bedrock knowledge-base vector store against this emulator cannot get past setup: the collection endpoint the emulator advertised for index/search/data-upload requests rejects every OpenSearch REST request, and it does so as a serialization error about a header the OpenSearch protocol does not define — so the client is told its request is malformed rather than that the endpoint does not speak that protocol. Every retrieval-augmented flow (index create, ingestion, Retrieve, and Retrieve's own not-found semantics) is unreachable.
Fix: the opensearchserverless collection data plane together with the emulator's host/endpoint routing table — route the host published as CollectionDetail.collectionEndpoint to an OpenSearch REST handler (index create/get/head/delete, document index and search) that authorises SigV4 `aoss` requests against the collection's data-access policy, instead of letting that host fall through to the AWS-JSON target dispatcher. Once an index can exist, the bedrock-agent-runtime Retrieve handler's not-found path (404 ResourceNotFoundException with the message template above) is what the check then measures.
