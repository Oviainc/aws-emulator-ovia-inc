# bedrock-agent-runtime: Retrieve refuses every OPENSEARCH_SERVERLESS-backed knowledge base with 424 DependencyFailedException, hiding both the success path and the 404 not-found path (1 cause, 2 checks)

> _Note: this issue was identified against the code base at commit `e944e72389a9c803ebf7fc7f022f4184a07cd9ff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve

## Description
REOPENS 20261025T173258Z-bedrock-agent-runtime-retrieve-is-a-scaffold-stub.md: its fix left the call refused. The Retrieve handler now exists, but it serves only a knowledge base bound to an S3 Vectors index (the configuration that issue's check used); a knowledge base backed by an OpenSearch Serverless collection is refused with 424 rather than served. Open issue 20261023T004328Z-bedrock-agent-runtime-retrieve-optimizeprompt-getagentmemory-deleteagentmemory-and.md describes the earlier NotImplemented symptom and does not cover this refusal.

=== Cause 1 of 1: Retrieve answers 424 DependencyFailedException for an OPENSEARCH_SERVERLESS-backed knowledge base instead of 200 with ranked chunks, which also makes the unknown-knowledge-base refusal unobservable ===
AWS: Smithy: Retrieve = POST /knowledgebases/{knowledgeBaseId}/retrieve, @readonly, success HTTP 200; output retrievalResults (@required), each KnowledgeBaseRetrievalResult carrying content (@required), location, score and metadata. Modeled errors include DependencyFailedException (HTTP 424, "There was an issue with a dependency. Check the resource configurations and retry the request."), ResourceNotFoundException (HTTP 404, "The specified resource Amazon Resource Name (ARN) was not found. Check the Amazon Resource Name (ARN) and try your request again.") and ValidationException (400). On real AWS an ACTIVE knowledge base whose storageConfiguration.type is OPENSEARCH_SERVERLESS and whose ingestion job has COMPLETEd is retrieved with 200: the results are ordered by descending score, and two identical Retrieve calls agree on the per-result scores to float32 precision because score is the index's own similarity for the query vector. A well-formed but never-provisioned knowledgeBaseId (matching ^[0-9a-zA-Z]{10}$) is refused with 404 ResourceNotFoundException and with no other rejection class. DependencyFailedException is for a dependency that really failed, not for the store type being unsupported.
Emulator: every Retrieve against an OPENSEARCH_SERVERLESS-backed knowledge base is refused with HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." Fixed text is "The vector store the knowledge base is backed by could not be queried: " + <resource> + ". Check the resource configurations and retry the request." (state/knowledge_base_retrieval.rs, unreachable_store_message); the sole variable part, <resource>, is filled with the knowledge base's storageConfiguration.type — the store-type token "OPENSEARCH_SERVERLESS", not a collection or index name. state::knowledge_base_retrieval::nearest_chunks resolves storage only through agent_state::s3_vectors_binding and returns RetrievalRefusal::UnreachableVectorStore for anything else, so no scoring is ever computed and the ResourceNotFoundException branch for an unknown knowledgeBaseId is never reached either: the positive leg a not-found check must first establish fails, so a caller cannot tell a missing knowledge base (404) from an unreadable store (424).
Why: a client that uses the AWS-documented vector store for Bedrock Knowledge Bases gets a dependency-failure error for a correct setup. Retry-on-424 logic loops or the client tears down and rebuilds a healthy collection, policy set and index; RAG code that ranks or thresholds on score has no scores at all; and error-handling branches keyed on ResourceNotFoundException never fire, because a bad knowledgeBaseId and a good one both produce 424.
Fix: the runtime plane's retrieval state — services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice/src/state/knowledge_base_retrieval.rs (nearest_chunks) must resolve an opensearchServerlessConfiguration to the collection/index it names and rank the chunks the Bedrock Agent ingestion wrote there, with score computed from the index's own distance metric so repeated identical queries agree bit-for-bit; and the build-time plane's ingestion writer (service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/state/ingestion.rs, ingestion_index.rs) must write chunk vectors and the published kb metadata fields into that collection's index. Keep UnknownKnowledgeBase -> 404 ahead of any store resolution so a nonexistent knowledgeBaseId is refused with ResourceNotFoundException regardless of the store type.
Traces: bedrock-agent-runtime.knowledge-base-retrieval-scoring-deterministic, bedrock-agent-runtime.retrieve-nonexistent-knowledge-base-not-found.

## Evidence
Expected (scoring check): two identical Retrieve calls against an ACTIVE OPENSEARCH_SERVERLESS-backed knowledge base each answer HTTP 200 with retrievalResults ordered by descending score, scores agreeing within float32 tolerance between the calls.
Expected (not-found check): the same Retrieve against the real knowledge base answers 200, and the identical call with a well-formed but never-provisioned knowledgeBaseId answers HTTP 404 with error code ResourceNotFoundException.
Actual (both checks): HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." (botocore.errorfactory.DependencyFailedException on the Retrieve call). In that message only the trailing store token is variable (it is the knowledge base's storageConfiguration.type); the surrounding sentence is fixed template text. No score is returned and the 404 path is never exercised.

## Steps to Reproduce
1. Create an opensearchserverless VECTORSEARCH collection (encryption, network and data-access policies granting the knowledge-base role aoss:APIAccessAll), wait for ACTIVE, and create the vector index with the vector/text/metadata field mapping on its endpoint.
2. Call bedrock-agent CreateKnowledgeBase with storageConfiguration.type = "OPENSEARCH_SERVERLESS" and opensearchServerlessConfiguration naming that collection ARN and index; create an S3 data source and run StartIngestionJob to completion.
3. Call bedrock-agent-runtime Retrieve(knowledgeBaseId=<kb id>, retrievalQuery={'text': 'What is the refund policy?'}) twice.
4. Observe HTTP 424 DependencyFailedException "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." instead of 200 with ranked, reproducibly scored results.
5. Call Retrieve with a well-formed 10-character knowledgeBaseId that was never created and observe the same 424 rather than 404 ResourceNotFoundException.
