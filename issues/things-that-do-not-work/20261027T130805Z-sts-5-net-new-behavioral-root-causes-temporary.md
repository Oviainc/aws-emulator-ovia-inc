# sts: 5 net-new behavioral root causes — temporary credentials are not ASIA-class, session tags never reach aws:PrincipalTag, role-chain transitive-tag and SourceIdentity legs never converge, and presigned GetCallerIdentity is expired with SignatureDoesNotMatch

> _Note: this issue was identified against the code base at commit `16c20ea7d22d9314dc8611d90389344009516a2f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRole

## Description
Five distinct net-new root causes in the STS credential vendor, all grounded in failing behavioral checks of the `sts` suite. They are bundled because they share one service; each must be closed separately.

Note on scope: the already-open issues 20261024T065715Z-sts-sessions-carry-no-policy-scoping-packedpolicysize-oversized.md, 20261025T131636Z-sts-session-revocation-is-a-no-op-an.md, 20261025T022928Z-sts-assumerolewithsaml-is-unroutable-unknownservice-assumerole-parses-the.md and 20261027T001707Z-sts-3-net-new-behavioral-root-causes-assumerolewithwebidentity.md own the replay keys of the other failing sts checks; none of them carries the five checks/causes below.

=== Cause 1 of 5: every temporary credential STS mints carries an AccessKeyId outside the ASIA class ===
AWS: AWS mints temporary security credentials — AssumeRole, GetSessionToken, GetFederationToken, AssumeRoleWith* — with an AccessKeyId in the `ASIA` class, while long-term IAM user keys are in the `AKIA` class (AWS IAM User Guide, "IAM identifiers" → unique identifier prefixes: `ASIA` = temporary (AWS STS) access key id, `AKIA` = IAM user access key id). Smithy: `Credentials$AccessKeyId` targets `accessKeyIdType`, @required, @length(min 16, max 128), @pattern "^[\\w]*$", doc "The access key ID that identifies the temporary security credentials." The model therefore constrains only the shape and says nothing about the class — the prefix rule is recorded behavior plus AWS's documented identifier prefixes. The requirement is the leading four-character class token `ASIA`; the remaining characters are a per-mint random id and are NOT part of the requirement (no recorded key id's body is a requirement).
Emulator: every STS mint answers an AccessKeyId in an `EMULATOR…` class. Observed prefixes `'EMUL'` from AssumeRole, GetSessionToken and GetFederationToken; one full observed value from AssumeRole is `'EMULATORASFE2YG2FJHD'` (that exact value is a per-run id, not a requirement — the diverging part is the class token). The class is identical for temporary and long-term keys, so a long-term IAM user key and an STS session key are indistinguishable by prefix.
Why: clients branch on the key-id class. Tooling decides from the prefix whether a credential needs an accompanying session token, whether it is a rotatable long-term key, and whether it is safe to persist; credential scanners, policy linters and the GetAccessKeyInfo contract (the owning account is encoded in the key id itself, not only in persisted IAM keys) all read it. Against the emulator, any code path that tests for `ASIA` concludes no STS session was ever issued and treats a short-lived session key as a long-term user key.
Fix: the temporary-credential key-id minting that the STS session minter asks the shared credential store for — `crate::state::mint_session` (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs:1568) delegating to `emulator_server::CredentialStore`. The session mint must request an `ASIA`-class key id while IAM long-term keys keep `AKIA`.
Traces: sts.assume-role-external-id-success-with-correct-id, sts.assume-role-packed-policy-too-large-rejected, sts.get-access-key-info-resolves-temporary-asia-key, sts.get-access-key-info-returns-correct-account, sts.get-caller-identity-userid-matches-created-role-id, sts.get-federation-token-policy-caps-caller-permissions.

=== Cause 2 of 5: session tags are never projected into aws:PrincipalTag, so a PrincipalTag-conditioned policy never denies ===
AWS: session tags passed to AssumeRole become principal tags on the resulting session. Smithy: `AssumeRoleRequest$Tags` targets `tagListType` @length(0..50); `Tag$Key` @length(1..128) @pattern "^[\\p{L}\\p{Z}\\p{N}_.:/=+\\-@]+$"; `Tag$Value` @length(0..256) @pattern "^[\\p{L}\\p{Z}\\p{N}_.:/=+\\-@]*$"; the `Tag` shape documents "These are called session tags. You can then use the session tags to control access to resources." A policy statement whose Condition is an exact `StringEquals` on `aws:PrincipalTag/<key>` must therefore allow a session carrying exactly that tag value and refuse one carrying no such tag or a different value — the refusal being that service's own denial for an unauthorized principal (IAM: 403 AccessDenied; S3 ListObjectsV2: 403 AccessDenied). Recorded behavior: the two checks assert exactly those deny legs, including that a unicode tag value (letters with diacritics and CJK code points, matched by the `\\p{L}` class in the modelled pattern) round-trips byte-exact so a diacritics-stripped value does NOT satisfy the condition.
Emulator: both deny legs succeed with HTTP 200. `iam.list_roles()` under a session carrying no tag returns 200 — "expected the call to be refused, but it succeeded". `s3.list_objects_v2` under the chained session whose carried tag value does not match the bucket policy's condition returns 200 — the poll's last observation is `('ok', 'ListObjectsV2 succeeded')` after 30 s. Because the deny leg never fires, exact unicode preservation of the tag value is also unverifiable through the condition.
Why: overly permissive. A tag-based access-control design (ABAC) validated against the emulator reports as working while every negative case is served, so a policy that is supposed to isolate one team/tenant isolates nothing.
Fix: the session-tag → condition-key projection on the STS session record and the IAM/S3 condition evaluation that consumes `aws:PrincipalTag/<key>` — the tag set recorded by the mint in the STS session registry (services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/state.rs, `NewSession`/`mint_session` and `assume_role_published_condition_keys`) must be published as principal tags to the authorization decision of the called service.
Traces: sts.assume-role-session-tags-unicode-value-round-trip, sts.e2e-session-tag-propagation-through-role-chain.

=== Cause 3 of 5: the transitive-session-tag role-chaining path never converges — the check hangs to the 60 s harness cap ===
AWS: a tag named in `AssumeRoleRequest$TransitiveTagKeys` survives role chaining: the chained session inherits it and it decides a condition in the chained session, while a non-transitive tag does not survive. Smithy/AssumeRole doc: "if you used temporary credentials to perform this operation, the new session inherits any transitive session tags from the calling session. If you pass a session tag with the same key as an inherited tag, the operation fails" (`AssumeRoleRequest$Tags`), and carrying tags onto the chained role needs `sts:TagSession` on the TARGET role's trust policy. So the chained assume that lacks `sts:TagSession` must be refused AccessDenied, and a condition keyed on the inherited transitive tag must deny the session that does not carry it.
Emulator: the check produces no verdict at all — `Error: Check timed out after 60.0s`. Its only unbounded waits are bounded polls for an expected refusal (`_poll_denied`, waiting for a specific error code) and for a positive control; a poll that never observes its expected code spins until the cap. Hypothesis: the same missing principal-tag/trust-condition evaluation as Cause 2 means the expected refusal never arrives on the transitive-tag leg, so the check cannot finish; it is reported separately because it exercises the transitive carry-forward and the `sts:TagSession` grant on the chained hop, levers Cause 2's checks never reach.
Why: the whole transitive-session-tag contract is unverifiable, and a chained session silently gains tag-derived permissions (or keeps tags it should have dropped) with no refusal anywhere.
Fix: AssumeRole's transitive-tag carry-forward and the `sts:TagSession`/trust-policy decision on a chained mint — services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/assume_role.rs (the `TAG_SESSION_ACTION` leg and the effective-tag computation around the `mint_session` call) together with the condition evaluation of Cause 2.
Traces: sts.assume-role-transitive-tag-survives-role-chaining.

=== Cause 4 of 5: the SourceIdentity role-chaining path never converges — the check hangs to the 60 s harness cap ===
AWS: `SourceIdentity` persists across chained role sessions and satisfies the next role's `sts:SourceIdentity` trust condition. Smithy: `AssumeRoleRequest$SourceIdentity` — "the source identity value persists across chained role sessions"; setting it needs `sts:SetSourceIdentity` on the target trust policy. Recorded behavior for the three legs: a chained assume that names a DIFFERENT SourceIdentity than the one the calling session carries is a ValidationError; a chained assume against a role whose trust condition requires a different value is AccessDenied; and a role-chained session is capped at one hour (`ROLE_CHAINING_MAX_DURATION_SECONDS` = 3600).
Emulator: no verdict — `Error: Check timed out after 60.0s`. Hypothesis: as in Cause 3, the check's bounded polls wait for an expected refusal code that never arrives, so it exhausts the harness cap instead of producing a comparison. Reported separately from Cause 3 because the lever is the `sts:SourceIdentity` trust condition and the conflicting-value refusal on a chained mint, not session tags.
Why: SourceIdentity exists so an action in a chained session is attributable to one original human identity and so a downstream role can require that identity. If neither the conflicting-value refusal nor the condition denial is observable, a chain can be continued under a substituted identity and the audit guarantee is void.
Fix: the SourceIdentity legs of AssumeRole — services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/assume_role.rs (the carried-vs-named SourceIdentity conflict refusal and the `SET_SOURCE_IDENTITY_ACTION` leg) and the `sts:SourceIdentity` trust-condition evaluation.
Traces: sts.role-chain-with-a-conflicting-source-identity-denied-and-the-matching-one-permitted.

=== Cause 5 of 5: a presigned (query-string SigV4) GetCallerIdentity URL is refused once X-Amz-Expires elapses, with SignatureDoesNotMatch ===
AWS: STS honours query-string-SigV4 presigned GetCallerIdentity and does not enforce `X-Amz-Expires` on it — a URL presigned with a 30-second expiry still answers HTTP 200 with the signer's identity long after that window, which is why a presigned GetCallerIdentity URL is usable as a bearer identity token. Model: recorded behavior only — the Smithy model binds no presign/expiry semantics to the operation. The signature-tampering leg is a real requirement and the emulator already matches it: one corrupted hex digit of `X-Amz-Signature` yields HTTP 403 with an XML `ErrorResponse` carrying `<Type>Sender</Type>`, `<Code>SignatureDoesNotMatch</Code>` and the fixed message "The request signature we calculated does not match the signature you provided. Check your AWS Secret Access Key and signing method." — that message has no variable part taken from the request, and no identity field leaks into the body.
Emulator: the positive control, the tampered-signature refusal and the restore all pass. Then two URLs minted at the same instant differing ONLY in `X-Amz-Expires` (30 s vs 900 s) diverge: the 30 s URL answers 200 while inside its window but is answered HTTP 403 with that same `SignatureDoesNotMatch` body when re-read inside a 150 s hold window, while the 900 s twin keeps answering 200. So the emulator applies an S3-style `X-Amz-Expires` check on this operation, and expresses the expiry as a signature mismatch — a message whose fixed text asserts a calculated-signature mismatch that did not occur (the signature bytes are unchanged from the request that returned 200).
Why: the standard pattern of minting a presigned GetCallerIdentity URL and handing it to a verifier (the aws-iam-authenticator / EKS webhook token flow, and any service-to-service identity proof) breaks against the emulator the moment the stated window passes, where real STS keeps answering 200. A client that distinguishes "my signing credentials are wrong" from "my token aged out" is also told the wrong thing, because the refusal it gets names a signature mismatch.
Fix: the query-string SigV4 verification path serving the STS endpoint — the presign expiry enforcement must not be applied to GetCallerIdentity, and that path's refusal classification must not report an elapsed `X-Amz-Expires` as SignatureDoesNotMatch.
Traces: sts.presigned-get-caller-identity-url-is-authenticated-by-query-string-sigv4.
