# bedrock-agent: Retrieve refuses every OPENSEARCH_SERVERLESS-backed knowledge base with 424 DependencyFailedException, so an ingested document can never be read back (1 cause, 1 check)

> _Note: this issue was identified against the code base at commit `e944e72389a9c803ebf7fc7f022f4184a07cd9ff`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Retrieve

## Description
REOPENS 20261025T173258Z-bedrock-agent-runtime-retrieve-is-a-scaffold-stub.md: its fix left the call refused. That issue's fix replaced the Retrieve 501 stub with a real handler, but the handler only serves a knowledge base bound to an S3 Vectors index; a knowledge base whose storageConfiguration.type is OPENSEARCH_SERVERLESS — the vector store Bedrock Knowledge Bases are normally built on, and the one this check builds — is now refused with a 424 instead of served. Open issue 20261108T202701Z-bedrock-agent-retrieve-answers-501-notimplemented-so-an.md describes the OLD symptom for this same check (501 NotImplemented) and does not cover the refusal reported here.

=== Cause 1 of 1: Retrieve answers 424 DependencyFailedException for an OPENSEARCH_SERVERLESS-backed knowledge base instead of 200 with the ingested chunks ===
AWS: Smithy (services/service-com-amazonaws-bedrockagentruntime-amazonbedrockagentruntimeservice): Retrieve = POST /knowledgebases/{knowledgeBaseId}/retrieve, @readonly, success HTTP 200; input knowledgeBaseId (@httpLabel @required @length 10..2048 @pattern ^[0-9a-zA-Z]{10}$|^arn:aws(-[^:]+)?:bedrock:[a-z0-9-]{1,20}:[0-9]{12}:knowledge-base/[0-9a-zA-Z]{10}$), retrievalQuery (@required); output retrievalResults (@required). Modeled errors include DependencyFailedException (HTTP 424, "There was an issue with a dependency. Check the resource configurations and retry the request.") and ResourceNotFoundException (404). On real AWS, OPENSEARCH_SERVERLESS is the standard KnowledgeBaseStorageType for a vector knowledge base: once such a knowledge base is ACTIVE and an ingestion job has reached COMPLETE, Retrieve answers 200 and reports one KnowledgeBaseRetrievalResult per matching chunk with content.text byte-identical to the ingested text (multi-byte UTF-8 included), location.type = "S3" / location.s3Location.uri naming the ingested object, and metadata carrying x-amz-bedrock-kb-chunk-id, x-amz-bedrock-kb-data-source-id and x-amz-bedrock-kb-source-file-modality. DependencyFailedException is reserved for a dependency that actually failed (a deleted index, a collection whose policies deny the knowledge-base role), not for the store type itself being supported.
Emulator: the call is refused with HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." Fixed text of that message is "The vector store the knowledge base is backed by could not be queried: " + <resource> + ". Check the resource configurations and retry the request." (see state::knowledge_base_retrieval::unreachable_store_message); the only variable part is <resource>, taken from the knowledge base's own storageConfiguration.type — here the literal store type "OPENSEARCH_SERVERLESS" rather than any resource name. The refusal is unconditional for that store type: state::knowledge_base_retrieval::nearest_chunks resolves the knowledge base's storage through agent_state::s3_vectors_binding and, when that returns None, returns RetrievalRefusal::UnreachableVectorStore(storage.type), which the handler maps to DependencyFailedException. No AOSS collection or index is consulted, and the content the Bedrock Agent ingestion took in is never read, so the result does not depend on the collection's state, its data access policy, or whether the ingestion succeeded.
Why: the whole knowledge-base data path is unusable for the canonical AWS configuration. A client that creates an AOSS vector collection + index, builds a knowledge base over it, ingests documents (IngestKnowledgeBaseDocuments / StartIngestionJob) and then retrieves gets a 424 for a configuration AWS serves with 200 — and 424 is the error AWS uses for a genuinely broken dependency, so the client's retry/repair branch fires and it starts "fixing" a correct collection, policy set and index. It also cannot distinguish "this emulator does not read that store" from "your collection is misconfigured", and round-trip fidelity of the ingested bytes (unicode text, custom document identifiers) is unverifiable because no success is ever produced.
Fix: the retrieval state of the runtime plane and the ingestion state of the build-time plane. nearest_chunks (services/.../bedrockagentruntime.../src/state/knowledge_base_retrieval.rs) must resolve an OPENSEARCH_SERVERLESS storageConfiguration to the opensearchserverless collection/index the knowledge base names and rank the chunks the Bedrock Agent ingestion wrote there, the same way it does for an S3 Vectors binding; correspondingly the ingestion writer (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/state/ingestion.rs + state/ingestion_index.rs) must write its chunk vectors and the published metadata fields into that collection's index. UnreachableVectorStore must then be reached only for a store type this emulator genuinely does not serve, and MissingVectorIndex only when the named index is really absent.
Traces: bedrock-agent.knowledge-base-document-blob-round-trip.

## Evidence
Expected: HTTP 200 from POST /knowledgebases/{knowledgeBaseId}/retrieve for a knowledge base whose storageConfiguration.type is OPENSEARCH_SERVERLESS and which has an ingestion job in COMPLETE, with retrievalResults non-empty and the document's multi-byte unicode text returned byte-identical under content.text, plus the custom document identifier tracked as INDEXED.
Actual: HTTP 424, error code DependencyFailedException, message "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." — raised by botocore as botocore.errorfactory.DependencyFailedException on the Retrieve call, before any of the round-trip assertions run. The variable part of that message is the storageConfiguration.type value; the rest is fixed template text. No AOSS index is read: the refusal is produced by agent_state::s3_vectors_binding returning None for a non-S3-Vectors store.

## Steps to Reproduce
1. Create an opensearchserverless VECTORSEARCH collection with encryption/network/data-access policies granting the knowledge-base role aoss:APIAccessAll, wait for ACTIVE, and create the vector index on its endpoint.
2. Create an IAM role for the knowledge base and call bedrock-agent CreateKnowledgeBase with storageConfiguration.type = "OPENSEARCH_SERVERLESS" and opensearchServerlessConfiguration naming that collection ARN, vector index and field mapping; wait for ACTIVE.
3. Create a CUSTOM data source and call IngestKnowledgeBaseDocuments with an inline byte blob whose text contains multi-byte UTF-8, under a custom document identifier; wait for the document to reach INDEXED.
4. Call bedrock-agent-runtime Retrieve(knowledgeBaseId=<kb id>, retrievalQuery={'text': <marker text>}).
5. Observe HTTP 424 DependencyFailedException "The vector store the knowledge base is backed by could not be queried: OPENSEARCH_SERVERLESS. Check the resource configurations and retry the request." instead of a 200 carrying the ingested chunk.
