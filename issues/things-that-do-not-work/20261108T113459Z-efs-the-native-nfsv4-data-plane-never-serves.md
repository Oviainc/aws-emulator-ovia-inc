# efs: the native NFSv4 data plane never serves a mount target reported `available` — the single-node mount/write/read round trip never reaches a verdict (1 cause)

> _Note: this issue was identified against the code base at commit `6596661b7bed7b2c68eacfc83c0e7a703969540b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMountTarget

## Description
1 net-new root cause in the EFS native (NFS) data plane, grounded in a check that is cut off with "Check timed out after 180.0s" having reached no assertion at all, so the emulator returns no verdict for any claim the check makes.

Related open issues that do NOT cover this check as the replay report scores it: 20261107T090413Z-efs-the-native-nfsv4-data-plane-checks-never.md describes the same family of data-plane gaps but the replay report does not mark efs.efs-nfs-mount-write-read-round-trip as owned by it (its recorded replay key was taken at the old 60s cap / a different _poll_until frame, and no longer matches the key this check now produces at the 180s cap), so this check is currently un-gated and is filed here; a fixer should close both together if they share the same backing gap. 20261104T054216Z-efs-mount-target-file-system-refusals-use-emulator.md (refusal wording / invented CIDR for IpAddress) and 20261029T195311Z-elasticfilesystem-efs-mount-targets-ignore-ec2-subnet-state.md are control-plane findings; 20261023T153329Z-efs-lambda-the-shared-efs-mount-check-never.md, 20261024T012650Z-efs-lambda-the-shared-efs-access-point-lambda.md and 20261104T054216Z-ecs-efs-logs-the-shared-efs-fargate-scenario.md are Lambda/ECS compute flows, not the NFS mount path.

Cause 1 of 1: a mount target the control plane reports as LifeCycleState=available is not actually serving NFSv4.1 at its own IpAddress, so a single-node mount/write/read round trip never converges. Failing check: efs.efs-nfs-mount-write-read-round-trip.
AWS: Smithy: CreateMountTarget (POST /2015-02-01/mount-targets, 200) returns MountTargetDescription with required MountTargetId (^fsmt-[0-9a-f]{8,40}$), required FileSystemId, required SubnetId, required LifeCycleState, plus IpAddress (^[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}$), NetworkInterfaceId, AvailabilityZoneName and VpcId; DescribeMountTargets (GET /2015-02-01/mount-targets, 200, paginated Marker/NextMarker over MountTargets) reports the same description and is the documented way to read LifeCycleState and IpAddress back. The modelled refusals of CreateMountTarget are AvailabilityZonesMismatch/BadRequest/FileSystemNotFound 404/IncorrectFileSystemLifeCycleState 409/IpAddressInUse 409/MountTargetConflict 409/NetworkInterfaceLimitExceeded 409/NoFreeAddressesInSubnet 409/SecurityGroupLimitExceeded/SecurityGroupNotFound/SubnetNotFound/UnsupportedAvailabilityZone — none of them describes what `available` promises. That promise is recorded behavior only: on AWS, once DescribeMountTargets reports LifeCycleState `available`, the NFSv4.1 server is reachable at that IpAddress from inside the VPC on TCP 2049, `mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport <IpAddress>:/ <dir>` succeeds, a file written through the mount is read back byte-for-byte, and the mount is genuinely NFS — `findmnt -no FSTYPE <dir>` is exactly `nfs4` and `stat -f -c %T <dir>` is exactly `nfs`. Those two independent probes exist precisely so a local/tmpfs stand-in cannot satisfy the round trip for the wrong reason.
Emulator: the check is killed at the suite's 180s cap with no assertion reached, so at least one of its bounded waits never converges: DescribeFileSystems LifeCycleState -> `available` (180s budget, 5s interval), DescribeMountTargets LifeCycleState -> `available` (180s budget, 5s interval), the EC2 instance_running waiter (Delay=2, MaxAttempts=150), SSM DescribeInstanceInformation PingStatus -> `Online` (300s budget), or SSM GetCommandInvocation reaching a terminal Status (240s budget) for the AWS-RunShellScript invocation that performs the mount. The emulator answers the EFS control-plane creates and hands back an fsmt- id with an IpAddress, but nothing behind that address ever completes the round trip: no SSM invocation result carrying SIM2REAL_CONTENT / SIM2REAL_FSTYPE / SIM2REAL_MAGIC is ever produced, and the script's own six mount attempts 10s apart (exit 32 on exhaustion) never report a success either.
Why: a client that provisions EFS the documented way — CreateFileSystem, wait for `available`, CreateMountTarget, wait for `available`, read IpAddress, mount it from an instance — blocks forever instead of getting a filesystem. An `available` LifeCycleState on this emulator cannot be trusted as a signal that the filesystem is usable at all, and every workload layered on EFS (write a file, read it back, confirm the mount is nfs4) is unreachable. A client cannot even distinguish "still provisioning" from "will never serve", because the control plane reports the terminal success state while the data plane is absent.
Fix: the EFS native data plane — the NFSv4.1 listener that a mount target's IpAddress must answer on, whatever binds a mount-target record in the efs service crate's state to that listener, and the lifecycle transition that may report `available` only once that listener answers. The convergence of the surrounding EC2 RunInstances/instance-running and SSM Online/SendCommand/GetCommandInvocation path this scenario drives is part of the same gap (see also the open EC2/SSM issue 20261103T200742Z-ec2-ssm-cloudformation-deployed-ec2-ssm-estates-are-unusable-instance.md).
Traces: efs.efs-nfs-mount-write-read-round-trip.

[mismatch] efs.efs-nfs-mount-write-read-round-trip — Error: Check timed out after 180.0s. No assertion in the body was reached. The check's blocking waits, from its source as the suite report prints it: _wait_fs_state(efs, fs_id, "available", timeout_s=180.0) polling DescribeFileSystems(FileSystemId=...)["FileSystems"][0]["LifeCycleState"] every 5s; _wait_mt_state(efs, mt_id, "available", timeout_s=180.0) polling DescribeMountTargets(MountTargetId=...)["MountTargets"][0]["LifeCycleState"] every 5s; ec2.get_waiter("instance_running").wait(InstanceIds=[...], WaiterConfig={"Delay": 2, "MaxAttempts": 150}); _wait_ssm_online(ssm, instance_id, timeout_s=300.0) polling DescribeInstanceInformation for PingStatus == "Online"; _wait_ssm_command(ssm, command_id, instance_id, timeout_s=240.0) polling GetCommandInvocation for a terminal Status. _poll_until raises AssertionError("condition not met within <timeout>s (last=<value>)") only after its own budget, which is larger than the cap, so the kill arrives first and the report shows the timeout rather than a named unmet condition.

The first assertion the check would have reached is invocation["Status"] == "Success" for the AWS-RunShellScript invocation that runs `sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport <mt_ip>:/ /mnt/sim2real-efs-test` (six attempts, 10s apart, else `exit 32` with 'mount never succeeded within the retry window'), then `marker in SIM2REAL_CONTENT` (the marker is a per-run unique name, so only its byte-for-byte echo is the requirement, not its value), then `SIM2REAL_FSTYPE == "nfs4"` from `findmnt -no FSTYPE` and `SIM2REAL_MAGIC == "nfs"` from `stat -f -c %T`. None of those values was ever produced. The mount target is addressed by its own IpAddress (from DescribeMountTargets), deliberately not by its Amazon-managed DNS name, so EFS private DNS delivery is not in the path.

The check is tagged axis:happy-path / concern:data-plane / dp:native / plane:data and declares SERVICES = ["efs"]; the suite lists it under the `efs` heading. Hosts, ports, generated ids (fs-/fsmt-/i-/subnet-), the mount target's IP and the unique marker differ per run and are not requirements; the requirement is that an `available` mount target answers NFSv4.1 at whatever IpAddress it reports.

## Steps to Reproduce
1. git clone the repo; build and boot the emulator from this checkout.
2. Replay simparity-behavioral-aws-v1 check efs.efs-nfs-mount-write-read-round-trip. Observe "Check timed out after 180.0s" with no assertion outcome.
3. Minimal repro: CreateFileSystem(CreationToken=<token>, Tags=[...]) and poll DescribeFileSystems(FileSystemId=...) until LifeCycleState == "available".
4. Create a dedicated VPC (10.91.0.0/24) with EnableDnsSupport and EnableDnsHostnames true, one public subnet with MapPublicIpOnLaunch, an internet gateway and a default route; create a security group allowing TCP 2049 ingress from itself.
5. CreateMountTarget(FileSystemId=..., SubnetId=..., SecurityGroups=[sg]); poll DescribeMountTargets(MountTargetId=...) until LifeCycleState == "available" and read its IpAddress.
6. Launch an EC2 instance in that subnet with an SSM-enabled instance profile (AmazonSSMManagedInstanceCore); wait for the instance_running waiter and for DescribeInstanceInformation PingStatus == "Online".
7. SendCommand(DocumentName="AWS-RunShellScript", TimeoutSeconds=180) with: `mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport <IpAddress>:/ /mnt/x` (retrying up to six times, 10s apart); write a marker through the mount with `tee`; `cat` it back; `findmnt -no FSTYPE /mnt/x`; `stat -f -c %T /mnt/x`; `umount /mnt/x`.
8. Expect GetCommandInvocation to reach Status "Success", the marker read back byte-for-byte, FSTYPE exactly `nfs4` and statfs magic exactly `nfs`. Observe instead that the invocation never reaches a terminal status / the mount never succeeds, so none of those three values is ever produced even though DescribeMountTargets already reported LifeCycleState "available".
