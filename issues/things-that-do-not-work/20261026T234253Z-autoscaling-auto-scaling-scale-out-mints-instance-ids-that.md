# Auto Scaling: scale-out mints instance ids that exist in no EC2 state, and the DeleteAutoScalingGroup ResourceInUse message appends the group name AWS does not

> _Note: this issue was identified against the code base at commit `281440c6fd2fb349634dcc135fbec4e15edad452`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

SetDesiredCapacity

## Description
TWO distinct net-new root causes on Auto Scaling paths the emulator answers (the service is up and serving — 8 autoscaling checks pass). A fixer must close BOTH before submitting. Neither failing check was marked ALREADY FILED or OWNED by the replay report. Open issues that do NOT cover them: 20261024T032514Z-autoscaling-setdesiredcapacity-answers-501-notimplemented-for-a-vpczoneidentifier-only.md (SetDesiredCapacity now answers and applies the capacity change — the divergence below is what the applied change does NOT do), 20261022T175547Z-autoscaling-auto-scaling-4-fidelity-divergences-cloudformation-asg-never.md (CloudFormation never provisioning an ASG into Auto Scaling at all; here the group DOES exist and reports instances), and 20261022T112459Z-autoscaling-group-round-trip-create-skips-min-max.md (CreateAutoScalingGroup validation / describe defaults, not a refusal message text).

Cause 1 of 2: a capacity change launches nothing in EC2 — the group reports synthetic instance ids that resolve in no EC2 state.
AWS: SetDesiredCapacity (Smithy: SetDesiredCapacityType, required AutoScalingGroupName + DesiredCapacity; errors ScalingActivityInProgressFault/ResourceContentionFault) starts a scaling activity that actually launches EC2 instances from the group's launch template: the instance ids DescribeAutoScalingGroups then reports under AutoScalingGroups[].Instances[].InstanceId are real EC2 instance ids, so ec2 DescribeInstances(InstanceIds=[those ids]) returns them in Reservations with State.Name running, the launch template's ImageId and InstanceType, the group's propagate-at-launch tags and a SubnetId drawn from the group's VPCZoneIdentifier; scaling back in moves the same ids to State.Name terminated (recorded behavior only for the id text — the requirement is that an instance id Auto Scaling reports for a group is resolvable in EC2, not any particular id format).
Emulator: SetDesiredCapacity(DesiredCapacity=2) is accepted, the group converges to 2 Instances with LifecycleState InService, but their ids are a per-process counter — observed 'i-00000000000000001' — and no EC2 instance is ever created, so ec2 DescribeInstances(InstanceIds=['i-00000000000000001']) is refused HTTP 400 InvalidInstanceID.NotFound with message "The instance ID 'i-00000000000000001' does not exist" (fixed text "The instance ID '" + the requested id + "' does not exist"; the id is taken from the request). The instances exist only in the Auto Scaling store.
Why: a client that scales a group and then inspects, tags, connects to, attaches volumes to or terminates the instances it was told about gets a not-found for every one of them; Auto Scaling's own view is internally consistent while the account's EC2 view is empty, so every scale-out/scale-in workflow and every ASG-plus-EC2 test passes vacuously up to the first EC2 read and then fails irrecoverably.
Fix: the Auto Scaling group capacity path — crate::state::AutoScalingState::apply_capacity in services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/state.rs (the launched StoredInstance is built with mint_instance_id() at state.rs:505, minted by mint_instance_id at state.rs:329) must launch the instances through the emulated EC2 RunInstances path (the crate already depends on service-com-amazonaws-ec2-amazonec2 and reads subnets via state::ec2_subnets), store the ids EC2 returns, and terminate those same EC2 instances when capacity drops or the group is force-deleted; the same applies to the Pending/Terminating materialisation in materialize_due.
Traces: autoscaling.set-desired-capacity-launches-instances

Cause 2 of 2: the DeleteAutoScalingGroup ResourceInUse refusal message appends the group name, which is not part of AWS's text.
AWS: DeleteAutoScalingGroup without ForceDelete on a group that still holds instances is refused with awsQueryError code ResourceInUse, HTTP 400 (Smithy: DeleteAutoScalingGroup error ResourceInUseFault, errorKind client, httpError 400, awsQueryError {code: ResourceInUse, httpResponseCode: 400}; documented as "The operation can't be performed because the resource is in use"). The message for this error class is entirely FIXED text with no variable parts: "You cannot delete an AutoScalingGroup while there are instances or pending Spot instance request(s) still in the group." — it names neither the group nor any id.
Emulator: the status (400) and the code (ResourceInUse) are right, but the message is "You cannot delete an AutoScalingGroup while there are instances or pending Spot instance request(s) still in the group: <AutoScalingGroupName>" — the trailing full stop is replaced by ": " plus the group name from the request (observed with a group named sim2real-behav-as-grp-61ff47712dde; the name is request-derived and is NOT part of AWS's template).
Why: the error message is part of the contract — clients, CLI output comparisons and operator runbooks that match on AWS's exact ResourceInUse sentence do not recognise the emulator's variant, and a client that parses the sentence's tail reads a group name where AWS puts nothing.
Fix: the DeleteAutoScalingGroup handler's refusal — services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/delete_auto_scaling_group.rs:232-240 builds the ResourceInUseFault message with a format! that interpolates {name}; it must emit the fixed sentence ending in '.' with no interpolation.
Traces: autoscaling.delete-asg-in-use-without-force-fails
