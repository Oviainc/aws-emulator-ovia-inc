=== Cause 1 of 1: ValidateConfiguration reports a successful verdict for content that violates the profile's JSON_SCHEMA validator ===
AWS: ValidateConfiguration is POST /applications/{ApplicationId}/configurationprofiles/{ConfigurationProfileId}/validators, success 204 with an empty body; input ApplicationId (@httpLabel, @required, length 1..64), ConfigurationProfileId (@httpLabel, @required, length 1..128), ConfigurationVersion (@httpQuery configuration_version, @required, length 1..1024); modeled errors BadRequestException httpError 400, ResourceNotFoundException httpError 404, InternalServerException httpError 500 (Smithy: services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json). The operation exists to run the profile's Validators (ValidatorList @length 0..2, member Validator{Type @required -> ValidatorType [JSON_SCHEMA, LAMBDA], Content @required}) against the named configuration version: the model documents a validator as "a syntactic or semantic check to ensure the configuration that you want to deploy functions as intended" and states the deployment or update "can only proceed when the configuration data is valid". So a version that violates a JSON_SCHEMA validator attached to the profile is refused with BadRequestException / HTTP 400 while a conforming version answers 204. The model carries no message text, so the message template is recorded behavior only: `Could not build JSON schema from invalid input:\n <validatorContent>.\n Original error message:\n[message: "instance type (string) does not match any allowed primitive type (allowed: [\"boolean\"])" - parent node: /enabled]`. Its FIXED text is `Could not build JSON schema from invalid input:` and ` Original error message:` plus the bracketing/punctuation; its VARIABLE parts are the validator's own schema document echoed verbatim from the profile and the violation report derived from the stored content and that schema — the offending node path (here `/enabled`, i.e. the member that violated the schema), the actual primitive type of the value and the list of types the schema allows for it. Hypothesis: the bracketed inner report is produced by AWS's JSON-schema library, so the firm requirement is the 400 BadRequestException whose message names the violating node and the type mismatch; the exact punctuation is draft-level evidence from the recording the check pins.
Emulator: ValidateConfiguration answers an ordinary success for the violating version — the replay recorded `{'ResponseMetadata': {'HTTPStatusCode': 204, ...}}` with no error at all, where AWS answers 400 BadRequestException. The positive control in the same check passed (a schema-conforming version answers 204), and the profile was created with Validators=[{Type: JSON_SCHEMA, Content: <draft-07 schema requiring a boolean `enabled`>}], so the validator is attached and simply never evaluated. The reason is in the checkout: the shared evaluation seam services/service-com-amazonaws-appconfig-amazonappconfig/src/state/validators.rs documents (lines 30-41) that "a `JSON_SCHEMA` validator ... this emulator produces NO verdict for one" and its `first_rejection` match (lines 103-116) returns `None` for every non-LAMBDA validator type, so the handler's refusal branch in src/ops/validate_configuration.rs (lines 216-243) is unreachable for a JSON_SCHEMA validator and the handler falls through to the empty 204.
Why: this is a safety inversion on the one operation whose entire purpose is to give a verdict. A release pipeline that calls ValidateConfiguration before deploying is told its configuration is valid, then AWS refuses the same content at validation/deployment time in production; conversely a negative test that asserts BadRequestException for malformed content passes against AWS and fails here, and no client code path that handles the 400 is ever exercised. Because the verdict is silent rather than wrong-shaped, the failure is invisible until production.
Fix: the shared validator evaluation (src/state/validators.rs — give `first_rejection` a JSON_SCHEMA arm that evaluates the validator's schema document against the candidate bytes and returns the violation report as the refusal message) and, through it, the ValidateConfiguration handler's refusal path (src/ops/validate_configuration.rs), which already resolves the profile, the version and the content and already lifts a rejection into BadwRequestException/400 — only the JSON_SCHEMA verdict is missing. Nothing may be written either way: this operation reports a verdict and must not mutate state.

The open issue 20261023T032202Z-appconfig-validateconfiguration-stub.md is stale for this surface: ValidateConfiguration is no longer a 501 stub, it answers 204.
