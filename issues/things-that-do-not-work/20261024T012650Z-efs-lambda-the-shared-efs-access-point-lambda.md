# efs__lambda: the shared-EFS-access-point Lambda flow never terminates — CreateFunction/GetFunctionConfiguration/Invoke poll loops never converge and the check is killed at the 60s harness cap (1 cause)

> _Note: this issue was identified against the code base at commit `1f316ce023d643c000ad0b8fb7b5799232d706fd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Replay of behavioral suite simparity-behavioral-ga-prod-v1 against the emulator built from this checkout (14/16 passed, bootstrap_signal=false — the emulator was serving; efs alone passed 14/14) found ONE surviving, unowned root cause in the cross-service efs+lambda group (check-id service token `efs__lambda`). THIS ISSUE HAS 1 CAUSE.

NOTE ON OVERLAP: the open issue 20261023T153329Z-efs-lambda-the-shared-efs-mount-check-never.md describes the same stall and names the same check in its Traces, but the replay report did NOT mark this failure as OWNED, so its replay key is not registered against that issue. This issue is filed to carry that key; a fixer should merge the two rather than do the work twice. Two further open issues describe answers that would produce exactly this stall and should be merged into the same fix: 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md (Invoke answers NotImplemented instead of running the function) and 20261023T114649Z-lambda-function-urls-unrouted-configuration-blocks-dropped-from.md (CreateFunction skips validation / configuration blocks dropped from reads). Neither of those names this cross-service flow or this check.

Cause 1 of 1 — the EFS-access-point-mounted Lambda flow produces no terminal answer at all. The flow is: EC2 VPC + two subnets + an SG admitting TCP 2049 from itself; EFS CreateFileSystem, one CreateMountTarget per subnet, PutFileSystemPolicy delegating the client actions to the account root, CreateAccessPoint with PosixUser Uid/Gid 1001 and RootDirectory /export/lambda; two IAM roles each granted elasticfilesystem:ClientMount+ClientWrite; two Lambda functions created with VpcConfig and FileSystemConfigs=[{Arn: <access-point ARN>, LocalMountPath: '/mnt/shared'}]; then RequestResponse Invokes that write from A and read from B, a cold-start re-mount after ClientMount is dropped from B's role, and a heal after it is restored. The replay reports exactly `Check timed out after 60.0s` — no AssertionError and no ClientError — so the check was still inside one of its bounded poll loops when the harness cap fired. Failing check: efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied.

AWS: the wire contract is modelled; the data-plane claim is recorded behavior only. Smithy (services/service-com-amazonaws-lambda-awsgirapiservice/smithy-model/com-amazonaws-lambda-awsgirapiservice.json): CreateFunction input carries FileSystemConfigs (target FileSystemConfigList, @length min 0 max 1) and VpcConfig; CreateFunction/GetFunctionConfiguration both return the FunctionConfiguration shape carrying State (enum), StateReason, LastUpdateStatus (enum) and FileSystemConfigs; GetFunctionConfiguration is @readonly, http GET /2015-03-31/functions/{FunctionName}/configuration, code 200. Invoke is http POST /2015-03-31/functions/{FunctionName}/invocations, code 200, output StatusCode (@httpResponseCode), FunctionError (@httpHeader X-Amz-Function-Error), Payload (@httpPayload, sensitive); among its modeled errors are EFSMountFailureException (errorKind client, httpError 403), EFSMountConnectivityException (408), EFSMountTimeoutException (408) and EFSIOException (410). Smithy (services/service-com-amazonaws-efs-magnolioapiservice-v20150201/...): FileSystemDescription / MountTargetDescription / AccessPointDescription each expose LifeCycleState, which settles at `available`. Recorded behavior for the rest: the file system, both mount targets and the access point all settle at LifeCycleState=available; CreateFunction with VpcConfig+FileSystemConfigs is accepted and GetFunctionConfiguration leaves State=Pending for State=Active while echoing FileSystemConfigs verbatim; a RequestResponse Invoke returns StatusCode 200 with no FunctionError and a payload in which the LocalMountPath is a real mount, bytes written by function A are read back byte-identical by a DIFFERENT function B with both files stamped with the access point's PosixUser uid/gid, and A's /tmp copy is NOT visible to B; after elasticfilesystem:ClientMount is removed from B's execution role, B's next cold Invoke is refused with error code EFSMountFailureException at HTTP 403 while A (ClientMount intact, also cold) still mounts and reads; restoring the grant heals B. Every one of those steps is reached through a bounded poll whose budget exceeds the harness cap (file system available 180s, both mount targets available 420s, access point available 120s, CreateFunction role-propagation retry 180s, State leaving Pending 600s, first successful Invoke 180s, refusal-after-cold-start 300s, heal 300s), so on AWS each poll converges and the check terminates well inside them.

Emulator: nothing that satisfies the awaited condition is ever produced, and nothing that fails an assertion is produced either — the replay output is the single line `Error: Check timed out after 60.0s`. Because every poll predicate swallows the per-call outcome (a ClientError from Invoke is converted to a non-ok tuple and retried; a LifeCycleState or State is compared for equality and retried), a permanently-wrong or permanently-refusing answer from any step on this path presents as an unterminating wait rather than a classifiable failure. Hypothesis: the stall is the first loop whose predicate the emulator cannot satisfy — either an EFS file-system / mount-target / access-point LifeCycleState that never reaches `available`, a Lambda function State that never leaves Pending for a VpcConfig+FileSystemConfigs function, or the first poll over Invoke, whose per-attempt refusal (NotImplemented, per the open Invoke issue named above) is retried until the budget is gone. The report's single line does not say which, so that attribution is a hypothesis and not a measurement.

Why: a client gets no answer at all rather than a wrong one, which is the worst failure mode because there is no error code to branch on. A caller that waits on DescribeFileSystems/DescribeMountTargets/DescribeAccessPoints or GetFunctionConfiguration for a settled lifecycle state, or that retries Invoke until it succeeds, hangs until its own timeout instead of either succeeding or receiving a refusal it can classify. The capability under test is also absent in both directions: an emulator that gives each function a private directory would pass CreateFunction and the FileSystemConfigs echo and then silently diverge on the shared bytes, while one that ignores IAM on the mount would admit B with no ClientMount (over-permissive) instead of refusing with EFSMountFailureException at 403.

Fix: three components, in the order the flow reaches them. (1) The EFS lifecycle state machine behind CreateFileSystem / CreateMountTarget / CreateAccessPoint and their Describe readers, so every created resource converges to LifeCycleState=available. (2) The Lambda CreateFunction and GetFunctionConfiguration handlers and the function state they share, so a VpcConfig+FileSystemConfigs function leaves State=Pending for Active, reports LastUpdateStatus after UpdateFunctionConfiguration, and echoes FileSystemConfigs verbatim. (3) The Invoke handler and the EFS mount it stands on: a function configured with a FileSystemConfig must see the access point's root directory at LocalMountPath as ONE shared store across functions (not a per-function private directory), stamped with the access point's PosixUser identity, and the mount must be authorized at execution-environment build time against that function's own execution role, refusing with error code EFSMountFailureException at HTTP 403 when elasticfilesystem:ClientMount is absent. Whichever loop is stalling must first be made to ANSWER: an unimplemented step on this path has to return its modeled error rather than a value a retry loop reads as 'not yet'.

Traces: efs__lambda.deep-lambda-2-efs-mount-shared-between-two-functions-and-clientmount-denied.

There is no AssertionError and no ClientError traceback, so the check produced no assertion verdict: it was still inside a poll loop when the 60s cap fired. The loops it can have been inside, in order, with their own budgets (all > 60s, so none had expired):

  1. ec2.get_waiter('vpc_available').wait(VpcIds=[vpc_id])
  2. _poll(describe_file_systems(...)['FileSystems'][0]['LifeCycleState'] == 'available', timeout_s=180)
  3. _poll(describe_mount_targets(...) states all == 'available', timeout_s=420, interval_s=10)
  4. _poll(describe_access_points(...)[0]['LifeCycleState'] == 'available', timeout_s=120)
  5. lam.create_function(... VpcConfig, FileSystemConfigs ...) role-propagation retry, deadline 180s
  6. _poll(get_function_configuration(...)['State'] in ('Active','Failed'), timeout_s=600, interval_s=5)
  7. _poll(_invoke(fn_a, {'op':'write',...})[0] == 'ok', timeout_s=180, interval_s=10)

Loop 7 is the first whose predicate a refusing emulator can never satisfy, because the check's _invoke() converts a ClientError into an ('error', code, status, message) tuple that _poll treats as 'not yet' and retries — which is exactly what the open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md would produce. That localisation is a hypothesis: the report's single line does not say which loop stalled.

Expected (AWS, as the check encodes it): A's Invoke returns StatusCode=200 with no FunctionError and a payload reporting the LocalMountPath is a mount, uid=gid equal to the access point's PosixUser, and the sha256 of the bytes written; B's Invoke returns those exact bytes with the /tmp copy absent; after ClientMount is dropped from B's role, B's cold Invoke raises error code 'EFSMountFailureException' with HTTPStatusCode 403 (Smithy: EFSMountFailureException, errorKind client, httpError 403); A still reads the bytes in the same window; restoring the grant makes B read them again. Actual (emulator): the check reaches none of those assertions and is killed at 60s.
