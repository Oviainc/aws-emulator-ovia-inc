# Glue: 2 net-new causes — CreateColumnStatisticsTaskSettings starts no task run, and a CloudFormation-deployed AWS::Glue::Crawler never completes a crawl or populates the catalog (both exhaust the check budget)

CreateColumnStatisticsTaskSettings

## Description
Two (2) net-new root causes in the Glue service. Each is independent and BOTH must be closed before this issue is submitted. Neither failing check was marked ALREADY FILED or OWNED by the replay report, so no open issue carries their current replay keys; both now fail as a check-level TIMEOUT (the previous assertion is never reached because the asynchronous state the check polls for never appears), and where an open issue describes the same area it is named inside the cause. === Cause 1 of 2: CreateColumnStatisticsTaskSettings answers 200 but starts no column-statistics task run, so GetColumnStatisticsTaskRuns never lists anything and the whole state machine behind it is unreachable ===
AWS: Smithy: CreateColumnStatisticsTaskSettings(DatabaseName, TableName, Role @required; Schedule optional), errors AccessDeniedException / AlreadyExistsException / ColumnStatisticsTaskRunningException / EntityNotFoundException / InvalidInputException (client, httpError 400). GetColumnStatisticsTaskRuns(DatabaseName, TableName @required) -> ColumnStatisticsTaskRuns (list of ColumnStatisticsTaskRun{ColumnStatisticsTaskRunId, Role, Status}). Recorded behavior: a Create with NO Schedule immediately starts a run, so GetColumnStatisticsTaskRuns for that (DatabaseName, TableName) lists one run whose Role is the Role submitted to Create and whose Status is still in flight (STARTING or RUNNING) when read right after. That in-flight run is the precondition for everything after it: a second Create for the same table with a different Role is refused HTTP 400 ColumnStatisticsTaskRunningException with the message "Column statistics task for input table has already started" (entirely fixed text, no variable part) and starts no run, StopColumnStatisticsTaskRun drives the run to STOPPED, and the identical Create then succeeds.
Emulator: Create answers 200, but GetColumnStatisticsTaskRuns(DatabaseName=<db>, TableName=<tbl>) stays EMPTY. The check polls it every 3 s and never sees a run, and because that poll consumes the whole check budget the check now ends as "Check timed out after 60.0s" instead of reaching its first assertion. Nothing downstream is reachable: the duplicate-Create refusal, the no-side-effect assertion over the run-id set, Stop -> STOPPED, and the re-Create.
Why: a client that registers column-statistics settings and then waits on GetColumnStatisticsTaskRuns for its statistics job waits forever and can never obtain a ColumnStatisticsTaskRunId; and with no run ever in flight, a second Create for the same table is accepted where AWS refuses it, so two conflicting Roles can be registered for one table.
Related but NOT covering: open issues 20261110T023747Z-glue-4-net-new-root-causes-createcolumnstatisticstasksettings-starts.md (Cause 1) and 20261108T041805Z-glue-5-net-new-root-causes-createcolumnstatisticstasksettings-starts.md (Cause 1) describe this same fault, but the report left this check unowned, so no open issue carries its current replay key.
Fix: the CreateColumnStatisticsTaskSettings handler and the column-statistics task state it writes — a Create with no Schedule must register the settings AND enqueue a task run for that table so GetColumnStatisticsTaskRuns lists it with the submitted Role and an in-flight Status, and so StopColumnStatisticsTaskRun has a run to drive to STOPPED.
Traces: glue.column-statistics-task-settings-duplicate-create-rejected.

=== Cause 2 of 2: a CloudFormation-deployed AWS::Glue::Crawler is created and startable, but no crawl ever finishes, no crawler metrics are produced and the Data Catalog is never populated ===
AWS: Smithy: StartCrawler(Name @required) -> empty output, errors CrawlerRunningException / EntityNotFoundException / OperationTimeoutException (client, httpError 400); GetCrawler(Name) -> Crawler; GetCrawlerMetrics(CrawlerNameList) -> CrawlerMetricsList (each carrying TablesCreated / TablesUpdated); GetTables(DatabaseName) -> TableList. The progression itself is recorded behavior: after StartCrawler the crawler leaves State RUNNING/STOPPING and settles with Crawler.State == "READY" and Crawler.LastCrawl.Status == "SUCCEEDED"; GetCrawlerMetrics for that crawler then reports TablesCreated + TablesUpdated >= 1, and GetTables on the crawler's target database lists at least one table whose StorageDescriptor.Location is under the crawled s3:// prefix.
Emulator: the stack reaches CREATE_COMPLETE and GetCrawler/GetDatabase resolve, but the crawl never reaches a terminal SUCCEEDED LastCrawl — the check's wait-for-finish poll never converges and the check ends as "Check timed out after 60.0s", so the metrics and the crawler-created table are never observable.
Why: a client that deploys a crawler as infrastructure-as-code and then waits for LastCrawl.Status == SUCCEEDED before querying the catalog hangs forever; every downstream consumer (Athena, a Glue job, a workflow trigger) sees an empty database, and crawler metrics never move off zero.
Related but NOT covering: 20261101T211008Z-glue-a-cloudformation-deployed-aws-glue-crawler-can.md and 20261030T063753Z-glue-startcrawler-refuses-every-crawl-501-notimplemented-so.md describe the crawler-run area; the report left this check unowned, so neither carries its current replay key.
Fix: the StartCrawler handler and the crawler-run execution in Glue's crawler state (it must advance the crawl to a terminal LastCrawl.Status, accumulate CrawlerMetrics, and write the discovered table into the catalog database), plus the CloudFormation provisioning of AWS::Glue::Crawler that feeds it.
Traces: glue.deploy-crawler-via-cloudformation.
