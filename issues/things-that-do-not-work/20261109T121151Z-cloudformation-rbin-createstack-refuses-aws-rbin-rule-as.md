# cloudformation__rbin: CreateStack refuses AWS::Rbin::Rule as an unrecognized resource type, so no Recycle Bin retention rule can be deployed from a template

> _Note: this issue was identified against the code base at commit `ae5156e659812a6269d5e057615ff3791f30822e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new root cause in the CloudFormation emulator's template resource-type registry, grounded in the two failing behavioural checks under the cloudformation__rbin heading: cloudformation__rbin.deploy-rbin-rule-round-trip-then-stack-delete-confirms-removal and cloudformation__rbin.deploy-rbin-rule-retention-period-over-one-year-rejected. Both fail at the very first call with the identical refusal.

No open issue covers AWS::Rbin::Rule. The existing rbin issues are about the data-plane retention path (20261024T155459Z-rbin-createrule-event-propagation.md, 20261029T194803Z-rbin-retention-rules-do-not-retain-deleted-ebs.md, 20261104T205546Z-rbin-ebs-snapshot-retention-is-still-unserved-end.md) and rbin error wording (20261029T230739Z-rbin-error-messages-are-emulator-rendered-rather-than.md); the existing "Unrecognized resource types" issues name other types (AWS::MWAA::Environment, AWS::MediaTailor::*, AWS::ImageBuilder::*, AWS::NeptuneGraph::*, AWS::IoTSiteWise::*, AWS::Chatbot::CustomAction, …). None of them registers AWS::Rbin::Rule.

=== Cause 1 of 1: the template resource-type registry does not recognize AWS::Rbin::Rule, so every Recycle Bin template is refused at template validation ===
AWS:      recorded behavior only for the registry itself (CloudFormation's Smithy model carries no resource-type list; the supported types are the service's own data). AWS::Rbin::Rule is a supported CloudFormation resource type: its Properties are ResourceType, RetentionPeriod {RetentionPeriodValue, RetentionPeriodUnit}, ResourceTags [{ResourceTagKey, ResourceTagValue}], Description, LockConfiguration, ExcludeResourceTags and Tags; Ref returns the rule ARN (the primary identifier) and Fn::GetAtt publishes Arn, Identifier and LockState. A CreateStack whose template declares one is ACCEPTED — the call answers HTTP 200 with a StackId, the resource is provisioned through the Recycle Bin control plane the emulator already serves (Smithy com.amazonaws.rbin#AmazonRecycleBin: CreateRule / GetRule / ListRules / DeleteRule / ListTagsForResource), and the stack reaches CREATE_COMPLETE. CloudFormation's "Template format error: Unrecognized resource types: [<types>]" ValidationError — fixed text "Template format error: Unrecognized resource types: [" … "]", with the bracketed list taken verbatim from the submitted template — is the refusal AWS reserves for types it genuinely does not support, and AWS::Rbin::Rule is not one of them.
          Downstream of the registry, the two checks assert contracts that are also AWS's and that this refusal makes unreachable: (a) a rule created from a template reads back through rbin GetRule with Status "available", the declared ResourceType/RetentionPeriod/ResourceTags, no LockState member at all for a never-locked rule, and the template tag plus the propagated stack tag (CloudFormation's aws:* tags dropped), while GetAtt LockState normalizes that same null state to the string "unlocked"; after DeleteStack, GetRule answers ResourceNotFoundException with the message "Recycle Bin Rule '<identifier>' does not exist." (fixed text "Recycle Bin Rule '" … "' does not exist.", the identifier taken from the request) and ListRules with the rule's own tag filter answers an empty Rules list. (b) a RetentionPeriodValue of 366 is inside the Smithy range (com.amazonaws.rbin#RetentionPeriodValue @range min 1 max 3650, required member RetentionPeriod.RetentionPeriodValue) and inside the CloudFormation schema bound, so it is NOT refused by CloudFormation's own early validation — it is refused by the Rbin resource handler, and the stack settles ROLLBACK_COMPLETE with a CREATE_FAILED resource whose ResourceStatusReason is the handler envelope 'Resource handler returned message: "Retention period value must be between 1 day and 1 year inclusive (Service: Rbin, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)'. The fixed text there is "Retention period value must be between 1 day and 1 year inclusive", the service name Rbin, the status code 400 and HandlerErrorCode InvalidRequest; the request id, request token and attempt count are per-run values and not part of the requirement. No DescribeEvents VALIDATION_ERROR row is emitted for that stack, and no rule is left behind after the rollback.
Emulator: CreateStack is refused outright with HTTP 400 ValidationError and the message "Template format error: Unrecognized resource types: [AWS::Rbin::Rule]". It is the only type in either template, so the refusal happens before any resource is created and no StackId is ever issued — neither check gets past its first call, so none of the read-back, rollback or handler-refusal behavior above is exercised at all.
Why:      no Recycle Bin retention rule can be provisioned as infrastructure-as-code against this emulator. Every CloudFormation/SAM/CDK stack that declares a tag-level or region-level retention rule — the normal way these rules are managed, since they are account-wide guardrails deployed alongside the resources they protect — is rejected at submit time with a ValidationError that tells the author their template is malformed. A client cannot work around it or recover from it: the failure is template validation, not a resource create, so there is no StackId to poll, no stack event, no partial stack and nothing to roll back. It also makes the type's Ref/GetAtt contract (rule ARN, Identifier, LockState) completely unreachable, and it hides the negative class entirely: a template whose retention period exceeds the real one-year maximum must be refused by the Rbin handler with a rollback, and instead it is refused by CloudFormation for an unrelated reason, so a client cannot distinguish a bad retention period from an unsupported type.
Fix:      CloudFormation's template resource-type registry and the provisioning handler behind it, in the cloudformation service crate: register AWS::Rbin::Rule with its property schema, its Ref (the rule ARN) and its GetAtt attributes (Arn, Identifier, LockState, with the never-locked rule normalized to "unlocked"), and back its create/update/delete lifecycle with the Recycle Bin state the rbin crate already owns (CreateRule / GetRule / ListRules / DeleteRule / ListTagsForResource), including propagation of the stack's tags onto the rule and surfacing the Rbin handler's 400 InvalidRequest refusal as a CREATE_FAILED resource reason inside the standard resource-handler envelope so the stack rolls back instead of being refused by early validation. The "Unrecognized resource types" refusal path itself is correct and should stay for types AWS really does not support.
Traces:   cloudformation__rbin.deploy-rbin-rule-round-trip-then-stack-delete-confirms-removal, cloudformation__rbin.deploy-rbin-rule-retention-period-over-one-year-rejected.

2. Build a JSON template whose only resource is:
