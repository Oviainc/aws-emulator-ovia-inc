# Neptune cluster reports still invert AutoMinorVersionUpgrade, synthesise HostedZoneId and drop CustomEndpoints

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBCluster

## Description
Every Neptune operation that projects a DBCluster renders it from an RDS-generic projection whose residual defects are the same on all three paths: a boolean the Neptune front door always reports false is reported true, the Route 53 hosted-zone id is synthesised per deployment instead of being the engine's published per-region constant, and a custom endpoint the emulator itself created against the cluster is not reflected in the cluster's own report. Related open issue 20261103T175309Z-neptune-db-cluster-and-cluster-snapshot-reports-omit covers the same fixture steps for the members that are now served (DocdbAnalyticsEnabled, CustomDataGroupPresent, DBActivityStreamStatus, the snapshot members); it does NOT cover these clusters, which this replay reports with owned_by=[] and stub_path="" because their divergence keys changed, so they are filed here. THIS ISSUE HAS 3 CAUSES — all three must be closed before submitting.

Cause 1 of 3: CreateDBCluster's DBCluster reports AutoMinorVersionUpgrade true and a synthesised HostedZoneId. AWS: CreateDBCluster returns CreateDBClusterResult.DBCluster (Smithy: CreateDBCluster, output shape CreateDBClusterResult, member DBCluster -> com.amazonaws.neptune#DBCluster). DBCluster.HostedZoneId is documented as 'Specifies the ID that Amazon Route 53 assigns when you create a hosted zone' — for this engine that id is a FIXED constant shared by every cluster in a region (the region's Neptune hosted zone), not a value derived per deployment, per account or per cluster. AutoMinorVersionUpgrade is NOT a modeled member of neptune#DBCluster and is not a member of CreateDBClusterMessage either (the model has no way to request it at create), so recorded behavior only: the RDS front door that serves Neptune reports the created cluster with AutoMinorVersionUpgrade 'false' — the cluster does not take minor-version upgrades automatically unless it is later asked to. Emulator: AutoMinorVersionUpgrade comes back 'true', and HostedZoneId comes back a per-deployment synthesised id instead of the region's published Neptune hosted zone. Why: a client reading AutoMinorVersionUpgrade concludes the cluster will be upgraded automatically when the service would never have said so, and a client that builds a Route 53 alias record or a DNS-failover record from HostedZoneId builds it against a zone that does not exist in the region. Fix: the CreateDBCluster handler's DBCluster projection and the per-region hosted-zone constant / AutoMinorVersionUpgrade default it writes into cluster state. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#1.

Cause 2 of 3: DescribeDBClusters repeats cause 1's two defects on the read-back path. AWS: DescribeDBClusters returns DBClusterMessage.DBClusters, a list of the same neptune#DBCluster (Smithy: DescribeDBClusters, output shape DBClusterMessage, paginated items=DBClusters). The same rules hold: HostedZoneId is the region's fixed Neptune hosted-zone id, and (recorded behavior only) AutoMinorVersionUpgrade is 'false' for a cluster that was never asked to auto-upgrade. Emulator: the describe echoes the same wrong pair — AutoMinorVersionUpgrade 'true' and the synthesised HostedZoneId. Why: describe is the call a client polls after create/modify to confirm what the service actually stored, so the wrong values are not merely echoed once, they are confirmed; a client that reconciles its own record of the cluster against the service never converges on AWS's values. Fix: the shared DBCluster projection used by the DescribeDBClusters handler (the same projection as causes 1 and 3), and the cluster state it reads. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#2.

Cause 3 of 3: ModifyDBCluster loses the cluster's custom endpoints in addition to repeating the two defects above. AWS: ModifyDBCluster returns the modified cluster as a neptune#DBCluster (Smithy: ModifyDBCluster, output shape ModifyDBClusterResult, member DBCluster). CustomEndpoints is not a modeled member of neptune#DBCluster, so recorded behavior only: once a custom endpoint has been created against the cluster, the cluster report carries CustomEndpoints as a LIST with one member per custom endpoint, each member that endpoint's DNS name. The endpoint hostname is derived from the endpoint identifier, the cluster's resource token and the region, so only the member's PRESENCE and count are the requirement — never the recorded hostname. Emulator: CustomEndpoints comes back as an empty scalar rather than a list (type_mismatch: expected a one-member list, got ''), while AutoMinorVersionUpgrade is 'true' and HostedZoneId is synthesised as in causes 1 and 2. Why: this is a loss of state the emulator created itself — a client that creates a custom endpoint and then reads the cluster back to confirm it, or that enumerates a cluster's endpoints to pick one to connect through, is told the cluster has no custom endpoints at all. Fix: the ModifyDBCluster handler's DBCluster projection and the cluster state that records custom endpoints created against the cluster. Traces: neptune-db-cluster-lifecycle-and-custom-endpoint#task#9.

Not filed as a requirement: all three clusters also report Endpoint/ReaderEndpoint differing only in the cluster-resource token embedded in the hostname (AWS emits a per-cluster token, the emulator substitutes the account number). That is a generated per-environment id, so it is excluded from the causes above and from the fix.
