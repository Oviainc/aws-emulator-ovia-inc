=== Cause 1 of 5: CreateKnowledgeBase's refusal for a VECTOR knowledge base submitted with no storageConfiguration names the wrong missing member, with the emulator's own wording ===
AWS: Smithy (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/smithy-model/com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda.json): CreateKnowledgeBase requires `name`, `roleArn` and `knowledgeBaseConfiguration`; `knowledgeBaseConfiguration.type` is the required enum member and `vectorKnowledgeBaseConfiguration` is OPTIONAL inside it, `storageConfiguration` is an optional top-level member, and the operation models ValidationException (httpError 400). The model therefore does not state which of the two absent members is reported, and the recording settles it. Recorded behavior: `create_knowledge_base(name=…, roleArn=…, knowledgeBaseConfiguration={"type": "VECTOR"})` — neither nested vector config nor storageConfiguration — is refused ValidationException 400 with the message `You must provide a storage configuration if you create a VECTOR knowledge base.` That message is entirely FIXED text: nothing in it is derived from the request or from state. AWS checks the missing STORAGE configuration first and names it; it does not name the nested vector configuration.
Emulator: ValidationException (the code matches) with the message `knowledgeBaseConfiguration.vectorKnowledgeBaseConfiguration is required for a knowledgeBaseConfiguration.type of VECTOR` — a member-path sentence the service never emits, naming the other member.
Why: for a generic ValidationException the message is the only machine-usable discriminator, so a client or deployment tool that branches on AWS's text ("provision the vector store first") does not recognise the refusal and cannot tell a missing storage configuration from a malformed embedding-model configuration. It also sends an operator to fix the wrong field.
Fix: the CreateKnowledgeBase handler's input validation in the bedrock-agent crate (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/create_knowledge_base.rs) — order the storage-configuration pre-condition ahead of the nested vector-configuration check and emit AWS's fixed sentence.
Traces: bedrock-agent.create-knowledge-base-malformed-vector-config-rejected.

=== Cause 2 of 5: pattern-constraint ValidationException messages quote the Smithy @pattern verbatim, including the ^ and $ anchors AWS strips ===
AWS: Smithy: `CreatePrompt.name` targets PromptName with @pattern `^([0-9a-zA-Z][_-]?){1,100}$`, and `GetKnowledgeBase.knowledgeBaseId` targets Id with @pattern `^[0-9a-zA-Z]{10}$`; both operations model ValidationException (400). Recorded behavior: AWS's constraint message is the standard template `1 validation error detected: Value '<value>' at '<memberName>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>` where `1 validation error detected: Value '`, `' at '`, `' failed to satisfy constraint: Member must satisfy regular expression pattern: ` are fixed text, `<value>` is the rejected value from the request, `<memberName>` is the input member's name, and `<pattern>` is the modeled pattern with its leading `^` and trailing `$` ANCHORS REMOVED — i.e. `([0-9a-zA-Z][_-]?){1,100}` for a prompt name.
Emulator: the same template, but `<pattern>` is reproduced with the anchors still attached: `… Member must satisfy regular expression pattern: ^([0-9a-zA-Z][_-]?){1,100}$`. The same anchored form appears on the Id constraint (`^[0-9a-zA-Z]{10}$`), so this is the shared message builder, not one operation.
Why: a client that matches AWS's constraint message (the only discriminator within the generic ValidationException) fails to match, and a tool that echoes the quoted pattern to a user or feeds it to its own regex engine gets a different expression than the service publishes.
Fix: the shared pattern-constraint message formatter used by the bedrock-agent request validators — strip the anchors from the modeled @pattern when composing the message, instead of interpolating the trait value as-is. NOTE: open issue 20261029T214059Z-bedrock-agent-runtime-validationexception-constraint-messages-quote-the.md records the same class of defect for the SEPARATE bedrock-agent-runtime service; it does not cover these checks.
Traces: bedrock-agent.create-prompt-invalid-name-pattern-validation-error (the prompt-name pattern); also observable in the GetKnowledgeBase refusal quoted under Cause 5.

=== Cause 3 of 5: CreatePrompt has no defaultVariant-membership pre-condition, so a request AWS refuses falls through to the unimplemented handler and answers NotImplemented ===
AWS: Smithy: CreatePrompt takes `defaultVariant` (PromptVariantName) and `variants` (PromptVariantList, @length max 1) as optional members and models ValidationException (400); the model does not express the cross-member rule, so the recording supplies it. Recorded behavior: `create_prompt(name=…, defaultVariant="a_name_not_in_variants", variants=[{name: "actual_variant", …}])` is refused ValidationException with the message `Default variant must be present in the variants list. Retry your request with the correct default variant.` — entirely FIXED text, with no value from the request interpolated — and the rejected prompt never appears in ListPrompts.
Emulator: the request is not validated against the supplied variants at all; it reaches the scaffold and is answered `NotImplemented` (`operation CreatePrompt is scaffolded but not implemented in this emulator`), so the caller gets a 501-class refusal with the wrong code and a message that says nothing about the defect in the request. Cause 2 proves the handler DOES run a name-pattern validator first, so the gap is specifically the cross-member rule, not a wholly absent validation stage.
Why: a client cannot distinguish "your defaultVariant is wrong" (retryable after fixing the request) from "this operation is unavailable" (retry later / unsupported region), so a mis-wired prompt definition is reported as a service outage, and no error-handling path that keys on ValidationException is ever taken.
Fix: the CreatePrompt handler's validation in the bedrock-agent crate (services/service-com-amazonaws-bedrockagent-amazonbedrockagentbuildtimelambda/src/ops/create_prompt.rs) — reject with ValidationException and AWS's fixed sentence when `defaultVariant` names no entry of `variants`, before any state is touched, and leave no prompt behind. NOTE: open issue 20261029T171944Z … CreatePrompt scaffold-stub issue (filed for this suite as `Implement bedrock-agent CreatePrompt: unimplemented scaffold stub`, representative check bedrock-agent.prompt-empty-vs-absent-field-preserved) owns the missing happy path; this cause records the REFUSAL semantics that must hold once it is implemented, and this check's replay key is not carried there.
Traces: bedrock-agent.create-prompt-variant-mismatch-validation-error.

=== Cause 4 of 5: CloudFormation does not recognize the AWS::Bedrock::Flow resource type, so a flow cannot be deployed through a stack ===
AWS: recorded behavior only (CloudFormation resource-type coverage is not expressed in the bedrock-agent Smithy model). Recorded behavior: a template declaring `AWS::Bedrock::Flow` with Name / ExecutionRoleArn / Definition (Nodes + Connections) is accepted by CreateStack, the stack reaches CREATE_COMPLETE, `!Ref` on the resource yields the flow ARN and `!GetAtt …Id` the flow id, and the flow is already `Prepared` at CREATE_COMPLETE (unlike the raw API, where a new flow is NotPrepared until PrepareFlow).
Emulator: CreateStack is refused at template-parse time with HTTP 400 `ValidationError` and the message `Template format error: Unrecognized resource types: [AWS::Bedrock::Flow]`. The fixed text there is `Template format error: Unrecognized resource types: [` + `]`; the bracketed list is the set of unknown types from the submitted template — so the message itself is well formed, but AWS does not produce it for this type.
Why: the entire infrastructure-as-code path for Bedrock flows is unavailable — a stack that deploys a flow alongside its execution role cannot be created at all, so nothing downstream (flow outputs consumed by other resources, alias/version snapshotting at deploy time) is reachable, and a CDK/CFN user gets a template-format error for a template real CloudFormation accepts.
Fix: the CloudFormation resource-type registry and its bedrock provisioner (services/service-com-amazonaws-cloudformation-cloudformation — the resource-type table consulted during template validation, plus a provisioner that creates the flow, prepares it, and exposes Ref = flow ARN and GetAtt Id = flow id).
Traces: bedrock-agent.deploy-flow-cfn-behaves.

=== Cause 5 of 5: a CloudFormation-created AWS::Bedrock::KnowledgeBase is given its NAME as the physical resource id, so Ref yields a value no bedrock-agent read accepts ===
AWS: Smithy: every bedrock-agent knowledge-base read takes `knowledgeBaseId` with @pattern `^[0-9a-zA-Z]{10}$` (a 10-character opaque id), and GetKnowledgeBase models ValidationException (400) and ResourceNotFoundException (404). Recorded behavior: `!Ref` on an `AWS::Bedrock::KnowledgeBase` resource returns that 10-character KnowledgeBaseId, which GetKnowledgeBase / StartIngestionJob then accept; and after the stack is deleted, GetKnowledgeBase on it is refused ResourceNotFoundException with `KnowledgeBase with id <knowledgeBaseId> is not found.` (fixed text around the id taken from the request).
Emulator: the stack reaches CREATE_COMPLETE, but `!Ref KnowledgeBaseResource` resolves to the knowledge base's NAME as given in the template (a stack-derived name, e.g. a `sim2real-kb-…` style name, not a 10-character id). The very next read is therefore refused ValidationException 400 `1 validation error detected: Value '<name>' at 'knowledgeBaseId' failed to satisfy constraint: Member must satisfy regular expression pattern: ^[0-9a-zA-Z]{10}$` (also showing Cause 2's anchor defect).
Why: nothing deployed by CloudFormation can be addressed afterwards — stack Outputs, Fn::Ref/Fn::GetAtt wiring into other resources, and every client that reads the output and calls GetKnowledgeBase / CreateDataSource / StartIngestionJob all carry a value the API rejects outright. The failure also masquerades as a client input error rather than a provisioning defect.
Fix: the CloudFormation provisioner for AWS::Bedrock::KnowledgeBase (services/service-com-amazonaws-cloudformation-cloudformation resource provisioners) — set the physical resource id to the KnowledgeBaseId returned by CreateKnowledgeBase, not the template's Name, and resolve Ref from it. NOTE: open issue 20261029T214321Z-bedrock-agent-cloudformation-ssm-a-cloudformation-created-aws.md records this same physical-id defect under the composite `bedrock-agent__cloudformation__ssm` token; it does not carry this check's replay key, so this check must be re-replayed and this cause should close with that issue if its fix lands first.
Traces: bedrock-agent.deploy-knowledge-base-cfn-behaves.

=== Additional cause bundled: ingestion-job statistics report numberOfDocumentsScanned = 0 for a data source holding documents ===
Treat this as Cause 5b of the bundle (it shares Cause 5's service and is a distinct root cause a fixer must close separately).
AWS: Smithy: IngestionJobStatistics members are PrimitiveLong with default 0 — `numberOfDocumentsScanned` is documented as "The total number of source documents that were scanned. Includes new, updated, and unchanged documents.", `numberOfNewDocumentsIndexed` as "The number of new source documents in the data source that were successfully indexed.", alongside numberOfModifiedDocumentsIndexed / numberOfDocumentsDeleted / numberOfDocumentsFailed / numberOfDocumentsSkipped; the structure is returned on the ingestion job by StartIngestionJob, GetIngestionJob and ListIngestionJobs. Recorded behavior: for a first ingestion over N previously-unseen objects in the bound S3 prefix, the COMPLETE job reports numberOfDocumentsScanned == N and numberOfNewDocumentsIndexed == N with modified/deleted/failed/skipped all 0; re-running with the bytes unchanged still reports scanned == N with every other counter 0; after exactly one object's bytes change, scanned == N and new+modified == 1. The requirement is that the counters are measured work, and that scanned equals the number of source documents the data source holds.
Emulator: the job is accepted and advances, but the statistics come back with numberOfDocumentsScanned = 0 for a data source holding 4 documents that an independent S3 ListObjectsV2 in the same check confirms are present — the counters are the modeled zero defaults, so no source enumeration is happening.
Why: numberOfDocumentsScanned / numberOfNewDocumentsIndexed are what every knowledge-base sync pipeline polls to decide whether the sync did anything — they gate "retry the sync", "alert on an empty or mis-prefixed bucket" and "proceed to query the KB". Against the emulator a successful ingestion is indistinguishable from one that silently indexed nothing, and a genuinely empty data source is never caught.
Fix: the ingestion-job execution and statistics accounting in the bedrock-agent crate — the component StartIngestionJob advances and GetIngestionJob reads back must enumerate the data source's source objects and populate IngestionJobStatistics from that count instead of leaving the Smithy defaults in place. NOTE: open issue 20261029T195812Z-bedrock-agent-s3vectors-bedrock-agent-ingestion-into-an-s3-vectors-store.md records the same accounting gap under the composite `bedrock-agent__s3vectors` token (numberOfNewDocumentsIndexed=0); it does not carry this check's replay key, so this check must be re-replayed and this cause should close with that issue if its fix lands first.
Traces: bedrock-agent.ingestion-job-statistics-account-for-every-source-document.
