# EC2 DescribeInstanceTypes serves placeholder hardware attributes for whole instance families

> _Note: this issue was identified against the code base at commit `b3b51bdc06920507036cd31ba091b78449e90c00`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
One root cause with a very wide blast radius: the emulator's static instance-type catalog does not carry the real per-instance-type attributes, so DescribeInstanceTypes answers 200 with a well-formed instanceTypeSet whose numbers and flags are derived/placeholder values rather than the family's actual hardware. The wire replay reports this as 63 divergence clusters - every one of them a DescribeInstanceTypes step of an ec2-catalog-describe-instance-types-* fixture, all with status 200 -> 200 and only value_mismatch/missing keys inside instanceTypeSet.item[instanceType="..."]. The two clusters named in the linkage below are representatives of that family of clusters; the remaining clusters of the same cause are the other steps of the ec2-catalog-describe-instance-types-* fixtures (families observed in the report include i7ie, i8g, c9gd and m6gd) and a fixer must re-replay the whole ec2-catalog-describe-instance-types-* set, not just the two named steps, to confirm the fix. (The replay payload could not be enumerated step-by-step here: each of those clusters carries hundreds of mismatching keys, so the report lines exceed what can be transcribed - this is stated plainly so the pointer is not read as covering only two steps.)

Cause 1 of 1: the per-instance-type attributes returned by DescribeInstanceTypes are wrong or absent for whole families.
AWS: Smithy com.amazonaws.ec2#DescribeInstanceTypes returns InstanceTypeInfo per type; the members the replay diverges on are modeled: EbsInfo$AttachmentLimitType (xmlName attachmentLimitType, enum, doc "Indicates whether the instance type features a shared or dedicated Amazon EBS volume attachment limit"), EbsInfo$MaximumEbsAttachments (maximumEbsAttachments), EbsOptimizedInfo$BaselineBandwidthInMbps / BaselineIops / BaselineThroughputInMBps / MaximumBandwidthInMbps / MaximumIops / MaximumThroughputInMBps, InstanceStorageInfo$TotalSizeInGB (totalSizeInGB) and $Disks (disks.item.count / disks.item.sizeInGB), plus NetworkInfo (networkCards, maximumNetworkCards, defaultNetworkCardIndex, networkPerformance, ipv4AddressesPerInterface, ipv4AddressesPerSecondaryInterface, ipv6AddressesPerInterface, enaSrdSupported, efaSupported/efaInfo, flexibleEnaQueuesSupport, secondaryNetworkSupported, trafficMirroringSupport), ProcessorInfo (sustainedClockSpeedInGhz, supportedFeatures), VCpuInfo$ValidCores, cpuBurstModel, phcSupport, rebootMigrationSupport and hibernationSupported. The values themselves are AWS's published hardware facts for each instance type, not something the model states: this is recorded behavior, and the recording is the authority for each type (for example the recorded i7ie.6xlarge carries ebsInfo.attachmentLimitType 'dedicated', maximumEbsAttachments 32, ebsOptimizedInfo baseline 7500 Mbps / 30000 IOPS / 937.5 MB/s and maximum 10000 Mbps / 40000 IOPS / 1250.0 MB/s, instanceStorageInfo 2 disks of 7500 GB totalling 15000 GB, and cpuBurstModel 'none'; the recorded i8g.24xlarge carries attachmentLimitType 'dedicated', maximumEbsAttachments 64, baseline = maximum = 30000 Mbps / 120000 IOPS / 3750.0 MB/s and 6 disks of 3750 GB totalling 22500 GB).
Emulator: the same types come back with attachmentLimitType 'shared' for types AWS reports as 'dedicated', maximumEbsAttachments pinned at 28, EBS-optimized baseline/maximum figures scaled from a generic model (i7ie.6xlarge: 5100 Mbps / 22500 IOPS / 637.5 MB/s for both baseline and maximum; i8g.24xlarge: 20400 Mbps / 90000 IOPS / 2550.0 MB/s), instance-store disk geometry taken from a different disk size (i7ie.6xlarge: 3 disks of 1900 GB = 5700 GB instead of 2 x 7500 GB; i8g.24xlarge: 12 x 1900 GB = 22800 GB instead of 6 x 3750 GB), cpuBurstModel absent entirely, and the networkInfo / processorInfo / vCpuInfo.validCores / phcSupport / rebootMigrationSupport members likewise absent or carrying generic values.
Why: DescribeInstanceTypes is the authority clients use to CHOOSE an instance type and to size what they attach to it. A client that reads maximumEbsAttachments or attachmentLimitType plans the wrong number of volumes; one that reads ebsOptimizedInfo or networkPerformance sizes throughput wrongly; one that reads instanceStorageInfo provisions the wrong local-disk capacity; and one that reads a member the emulator omits (cpuBurstModel, phcSupport, rebootMigrationSupport, enaSrdSupported, vCpuInfo.validCores) gets a None where AWS always returns a value for these types, so selectors and capacity planners silently exclude or mis-rank types. Nothing fails loudly - the status is 200 - so the wrong answer propagates into the client's plan.
Fix: the instance-type catalog data behind the DescribeInstanceTypes handler (the static per-instance-type attribute table and its projection), which must carry each type's real attributes instead of deriving them from a family-generic template, and must emit the members it currently omits.
Traces: ec2-catalog-describe-instance-types-c9gd-m6gd#task#24 and #task#25, plus the remaining ec2-catalog-describe-instance-types-* DescribeInstanceTypes steps in the same replay (63 clusters in total for this cause).
