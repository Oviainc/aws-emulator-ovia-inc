# X-Ray account-config surfaces are overly permissive: PutEncryptionConfig accepts a nonexistent KMS key, enum/length violations answer InvalidRequestException instead of ValidationException, UpdateTraceSegmentDestination accepts a no-op and an unauthorized CloudWatchLogs switch, PutTraceSegments ErrorCode and TagResource not-found message diverge

> _Note: this issue was identified against the code base at commit `38b62e174af309db3e46216fa3b3f7ac7f6f5b84`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEncryptionConfig

## Description
Seven distinct root causes in the X-Ray account-singleton control surfaces (PutEncryptionConfig / UpdateTraceSegmentDestination), the PutTelemetryRecords and PutTraceSegments data paths, and TagResource of services/service-com-amazonaws-xray-awsxray. All are grounded in failing behavioral checks of the `xray` suite that the replay report marked neither ALREADY FILED nor OWNED. The open issue 20261022T013648Z-xray-x-ray-trace-data-plane-batchgettraces-id-limit.md covers neighbouring trace-data-plane defects (BatchGetTraces limits, FilterExpression, and the MissingName/ParseError per-segment codes) and the open issue 20261022T013648Z-xray-x-ray-group-control-plane-no-implicit-default.md covers the group control plane; neither carries any of the replay keys below (Cause 4 is the same family as that issue's Cause 6 but a different, unowned member value).

Cause 1 of 7: PutEncryptionConfig accepts a KMS key that does not exist.
AWS: PutEncryptionConfig(Type=KMS, KeyId=<well-formed ARN of a nonexistent/inaccessible key>) is refused with InvalidRequestException at HTTP 400 before the account config changes, because X-Ray must create a grant on the CMK first; recorded response message example: "Failed to create grant for customer master key. KMSKeyNotFound". Smithy: PutEncryptionConfig models only InvalidRequestException (client, 400) and ThrottledException (429); KeyId is EncryptionKeyId @length 1..3000, so key existence is a service-side check, recorded behavior only. Emulator: answers HTTP 200 with EncryptionConfig {KeyId: 'arn:aws:kms:us-west-2:000000000000:key/00000000-0000-0000-0000-000000000000', Status: 'UPDATING', Type: 'KMS'} — the account is pointed at a key that cannot exist. Why: a client that mistypes or references a deleted CMK believes account-wide trace encryption is configured; on real AWS the call fails and the config is left alone, so the emulator hides a misconfiguration that would break ingestion. Fix: KeyId resolution/validation in the PutEncryptionConfig handler (reject when the key cannot be resolved, and leave the stored singleton untouched). Traces: xray.put-encryption-config-invalid-kms-key-rejected.

Cause 2 of 7: an out-of-enum PutEncryptionConfig Type is reported as InvalidRequestException instead of ValidationException.
AWS: Type is a modeled enum, so a value outside it is refused by the protocol/constraint layer with error code ValidationException at HTTP 400; recorded message example: "1 validation error detected: Value 'NOT_A_TYPE' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [KMS, NONE]" (the rule is the standard AWS constraint-violation format naming the member and its enum set). Smithy: PutEncryptionConfig.Type -> EncryptionType enum, values [NONE, KMS], @required. Emulator: answers code InvalidRequestException. Why: a client (or SDK error-typed handler) that distinguishes a malformed request from a service-state rejection takes the wrong branch, and the InvalidRequestException retry/settling logic real callers use for "a previous change is still being applied" now also catches plain typos. Fix: the enum constraint check for PutEncryptionConfig must raise the shared ValidationException used for modeled-constraint violations, not the operation's InvalidRequestException. Traces: xray.put-get-encryption-config-transitions.

Cause 3 of 7: an over-length PutTelemetryRecords EC2InstanceId is reported as InvalidRequestException instead of ValidationException.
AWS: EC2InstanceId longer than its modeled maximum is refused with error code ValidationException at HTTP 400; recorded message example: "1 validation error detected: Value '<value>' at 'eC2InstanceId' failed to satisfy constraint: Member must have length less than or equal to 20". Smithy: PutTelemetryRecords.EC2InstanceId @length min 0 max 20 (Hostname 0..255, ResourceARN 0..500 are the same class); the operation models InvalidRequestException (400) / ThrottledException (429), so a length violation is the protocol-level constraint error. Emulator: answers code InvalidRequestException for the over-length value. Why: same mis-branching as Cause 2 — a constraint violation the SDK should surface as a validation error looks like a service-state error, so clients retry an input that can never succeed. Fix: the @length constraint enforcement for PutTelemetryRecords input members must map to ValidationException. Traces: xray.put-telemetry-records-malformed-resource-arn-rejected.

Cause 4 of 7: the per-segment UnprocessedTraceSegments ErrorCode for a document missing `trace_id` is the emulator's own value.
AWS: a segment document missing the required `trace_id` field is reported per-document in UnprocessedTraceSegments (HTTP 200, batch not rejected wholesale) with ErrorCode `MissingTraceId` and a Message that restates the code (recorded form: "Invalid segment. ErrorCode: MissingTraceId"); recorded behavior only — Smithy documents UnprocessedTraceSegment.ErrorCode merely as "The error that caused processing to fail" and publishes no value set. Emulator: {'Id': '<segment id>', 'ErrorCode': 'MissingRequiredField', 'Message': 'segment document is missing the required field `trace_id`'}. An ErrorCode is an error code, so its value is a requirement; the Id was correct. Why: a client switching on ErrorCode to decide whether to repair and resend a segment never matches AWS's codes and treats every structural rejection as one bucket. Fix: the error-code constants used by the PutTraceSegments ingest path (the same table as the already-filed MissingName/ParseError divergence — fix all members together). Traces: xray.put-trace-segments-missing-trace-id-rejected.

Cause 5 of 7: UpdateTraceSegmentDestination accepts a same-value (no-op) update.
AWS: re-issuing UpdateTraceSegmentDestination with the destination the account is already on is refused with InvalidRequestException at HTTP 400; recorded message example: "The destination is already set to XRay". Smithy: UpdateTraceSegmentDestination models InvalidRequestException (client, 400) / ThrottledException (429); Destination -> TraceSegmentDestination enum, Status -> TraceSegmentDestinationStatus [PENDING, ACTIVE]. Emulator: answers HTTP 200 with {'Destination': 'XRay', 'Status': 'ACTIVE'}. Why: the destination is an account-global singleton whose switch is asynchronous; a client that relies on the rejection to detect "already there" (instead of starting a second transition) cannot tell a real switch from a no-op, and a suite/automation that toggles the singleton loses its idempotency guard. Note this cause also masks the enum check in the same check: the out-of-enum value 'NotARealDestination' is never reached, so after fixing this, confirm that case answers ValidationException with the member-and-enum-set message (same class as Cause 2). Fix: a current-value comparison in the UpdateTraceSegmentDestination handler before it stores the new value. Traces: xray.update-trace-segment-destination-invalid-value-fails.

Cause 6 of 7: UpdateTraceSegmentDestination switches to CloudWatchLogs with no CloudWatch Logs resource policy granting X-Ray PutLogEvents.
AWS: the switch to CloudWatchLogs (Transaction Search) is refused with AccessDeniedException while no CloudWatch Logs resource policy allows the xray.amazonaws.com service principal logs:PutLogEvents on the aws/spans log group, and the destination is left unchanged; recorded message example: "XRay does not have permission to call PutLogEvents on the aws/spans Log Group. Please verify that your CloudWatch Logs Resource Policies are configured correctly". Smithy: AccessDeniedException is not in UpdateTraceSegmentDestination's modeled error list (only InvalidRequestException/ThrottledException), so this is recorded behavior only. Once the policy is created, the identical call succeeds. Emulator: answers HTTP 200 with {'Destination': 'CloudWatchLogs', 'Status': 'PENDING'} with no policy present. Why: a client following the "enable transaction search" flow gets a success and then sees no spans delivered, instead of the actionable permission error; the emulator reports a delivery path it cannot have. Fix: a precondition check in the UpdateTraceSegmentDestination handler against the CloudWatch Logs resource-policy state before accepting Destination=CloudWatchLogs. Traces: xray.update-trace-segment-destination-without-logs-policy-fails.

Cause 7 of 7: TagResource's ResourceNotFoundException message does not follow AWS's request-derived format.
AWS: tagging a syntactically valid but nonexistent X-Ray group ARN fails with ResourceNotFoundException at HTTP 404 and a message built from the request's ResourceARN in the form "Resource <ResourceARN> not found". Smithy: TagResource models ResourceNotFoundException (client, 404); ResourceARN is @required AmazonResourceName @length 1..1011. Emulator: the code and status are correct, but the message is the emulator's own prose, e.g. "no X-Ray resource is named by ARN `arn:aws:xray:us-west-2:000000000000:group/<name>/<id>`". The requirement here is the format rule (AWS's message is composed from the submitted ARN), not the recorded text. Why: clients and operators that pattern-match AWS's standard not-found wording (log scrapers, error-mapping layers) do not match, and the emulator-specific prose with Rust-style backticks leaks the implementation. Fix: the message construction in the TagResource handler's not-found branch. Traces: xray.tag-resource-unknown-arn-fails.
