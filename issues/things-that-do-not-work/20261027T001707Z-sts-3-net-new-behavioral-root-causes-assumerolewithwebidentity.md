## Description
This issue bundles THREE distinct net-new root causes in the STS service (service token `sts`). A fixer must close all three before submitting; each cause names its own failing check ids below. None of these is covered by the open STS issues: 20261024T065715Z-sts-sessions-carry-no-policy-scoping-packedpolicysize-oversized.md (its cause 3 is the over-length inline `Policy` misclassification and its cause 6 is unsigned-request ROUTING for AssumeRoleWithWebIdentity — neither is token verification nor the packed byte count), 20261025T022928Z-sts-assumerolewithsaml-is-unroutable-unknownservice-assumerole-parses-the.md and 20261025T222710Z-sts-assumerolewithsaml-an-expired-saml-assertion-is-answered.md (both AssumeRoleWithSAML), 20261025T123916Z-sts-9-fidelity-divergences-temporary-accesskeyids-are-not.md (access-key class, session-tag/SourceIdentity authorization) and 20261025T131636Z-sts-session-revocation-is-a-no-op-an.md (revocation).

Cause 1 of 3: AssumeRoleWithWebIdentity performs no OIDC verification-key resolution at all, so every web identity token is refused with one generic key-retrieval message — a genuine, provider-issued token is never accepted, and an unsigned JWT is not diagnosed as such.
AWS: Smithy binds `AssumeRoleWithWebIdentity` (input WebIdentityToken required/sensitive, @length 4..20000; errors InvalidIdentityTokenException awsQueryError code InvalidIdentityToken HTTP 400, IDPCommunicationErrorException code IDPCommunicationError HTTP 400, IDPRejectedClaimException code IDPRejectedClaim HTTP 403, ExpiredTokenException HTTP 400). STS fetches the provider's signing keys from the issuer registered in the IAM OIDC provider / Cognito user pool, verifies the JWT signature and then evaluates the trust policy. A token the registered provider genuinely signed is ACCEPTED and yields Credentials + AssumedRoleUser (recorded behavior: the check's positive control asserts an `arn:aws:sts::…` AssumedRoleUser ARN for the untampered Cognito ID token). AWS distinguishes the failure classes by message within InvalidIdentityToken/400: an unsigned JWT (JOSE header alg="none") is refused with the fixed text "We don't accept unsigned JWTs"; a signature-tampered-but-signed token is refused with the fixed text "The web identity token provided could not be validated. See the AssumeRoleWithWebIdentity documentation for requirements."; the message "Couldn't retrieve verification key from your identity provider, please reference AssumeRoleWithWebIdentity documentation for requirements" is reserved for the case where the issuer's key endpoint could not be read. None of these messages has a variable part — each is fixed text for its class.
Emulator: every AssumeRoleWithWebIdentity call is answered with code InvalidIdentityToken and the single message "Couldn't retrieve verification key from your identity provider, please reference AssumeRoleWithWebIdentity documentation for requirements", regardless of the token. Replay shows that message returned for an unsigned self-minted JWT whose iss/aud/sub satisfy the role's Federated trust statement (expected "We don't accept unsigned JWTs"), and the companion check — which first needs a genuine Cognito ID token from a pool created in the same run to be ACCEPTED as its positive control, retrying for up to 90 s — never gets an acceptance and is killed at the 60 s harness cap. Hypothesis: the handler has no key-resolution step for the registered provider, so it short-circuits to the key-retrieval refusal before it ever inspects the JOSE header or verifies a signature.
Why: the whole web-identity federation path is unusable — a client that exchanges a real Cognito/OIDC token for role credentials (the standard mobile/web and IRSA pattern) can never obtain a session, so its success path is untestable; and because every failure collapses into the key-retrieval message, a developer cannot tell "your IdP is unreachable" (retryable, operational) from "your token is unsigned/forged" (never retryable, a security event). An integration keyed on the message or on the IDPCommunicationError-vs-InvalidIdentityToken distinction takes the wrong branch.
Fix: the AssumeRoleWithWebIdentity handler's token-verification step in the STS service crate — resolve the signing keys for the issuer registered via IAM CreateOpenIDConnectProvider (and for a Cognito user pool issuer served by this emulator), verify the JWT, and classify refusals per class (alg=none -> "We don't accept unsigned JWTs"; bad signature -> "The web identity token provided could not be validated. See the AssumeRoleWithWebIdentity documentation for requirements."; unreachable key endpoint -> IDPCommunicationError / the key-retrieval message) instead of emitting one message for all of them.
Traces: sts.assume-role-with-web-identity-forged-token-rejected, sts.assume-role-with-web-identity-expired-token-rejected.

Cause 2 of 3: AssumeRole's PackedPolicyTooLarge message reports a serialized session-token size that the emulator computes differently from AWS, so the size in the refusal does not match the one AWS reports for the same request.
AWS: Smithy binds PackedPolicyTooLargeException on `AssumeRole` (awsQueryError code PackedPolicyTooLarge, HTTP 400) and `AssumeRole.Tags` @length 0..50. When the packed (compressed binary) session state exceeds the token limit, the refusal message is "Serialized token too large for session. Token size of <N> bytes exceeds the maximum allowed limit of <LIMIT> bytes." — fixed text with two variable parts: N, the packed size AWS computed for THIS request's session state, and LIMIT, the service's packed-token quota (4096). The size is a deterministic function of the request: for the recorded request of 50 tags, each with a 124-character key and a 256-character value (every field inside its own limit), AWS reported N=26092 against LIMIT=4096.
Emulator: the code (PackedPolicyTooLarge) and LIMIT (4096) are right, but the reported size is "Token size of 19000 bytes", i.e. the emulator's packing of the identical, fully deterministic tag set yields a different N than AWS's. Hypothesis: the handler estimates the size from a fixed per-tag cost rather than from the serialized session token (19000 = 50 x 380 exactly), so N diverges for any tag set and would not track a change in tag contents at all.
Why: the message is the only place a client learns how far over the quota its session state is; tooling that parses N to decide how many tags to drop, or a test asserting the refusal AWS produces for a known tag set, gets a number that is wrong by thousands of bytes. It also means the admission boundary itself is computed from the wrong quantity, so requests near the limit can be admitted or refused differently than in AWS.
Fix: the AssumeRole handler's session-packing/validation step — compute the packed size from the actual serialized session token (the same encoding whose length the quota applies to) and render it into the PackedPolicyTooLarge message, rather than from a per-tag constant.
Traces: sts.e2e-assume-role-oversized-session-policy-rejected.

Cause 3 of 3: a SourceIdentity-carrying AssumeRole session leaves no CloudTrail audit record attributable to that session, so SourceIdentity is never observable on the session's own later activity.
AWS: `AssumeRole.SourceIdentity` (@length 2..64, @pattern [\w+=,.@-]*) is not merely echoed in AssumeRoleResponse.SourceIdentity — it is recorded server-side against the resulting session and appears on CloudTrail's record of every LATER call made with that session's credentials, nested as userIdentity.sessionContext.sourceIdentity (recorded behavior, us-west-2: userIdentity={"type":"AssumedRole",…,"sessionContext":{"sessionIssuer":{…},"attributes":{…},"sourceIdentity":"<the value passed to AssumeRole>"}}), and the record's userIdentity/ARN names the RoleSessionName. So a GetCallerIdentity issued with those credentials is findable through CloudTrail LookupEvents (EventName=GetCallerIdentity) and carries the source identity.
Emulator: the check mints the session (its trust policy allows both sts:AssumeRole and sts:SetSourceIdentity), makes the independent GetCallerIdentity with the session credentials, then polls LookupEvents every 10 s for a GetCallerIdentity event whose CloudTrailEvent body contains the RoleSessionName. No such record is ever produced and the check is killed at the 60 s harness cap with no response captured. Hypothesis (the stall is a non-arriving record, not a refusal): the sibling check sts.server-side-source-identity-missing-permission-rejected shows AssumeRole+SourceIdentity is served, and the cloudtrail LookupEvents checks pass, so what is missing is the session attribution on the emitted event — either no event is emitted for a call made with assumed-role session credentials, or the event's userIdentity does not name the session and carries no sessionContext.sourceIdentity.
Why: SourceIdentity exists so that an administrator can attribute a session's activity to the human or workload behind it, and it cannot be changed for the life of the session. An emulator that accepts the field, echoes it, and then drops it tells a developer their audit/attribution design works when in AWS it is the only thing their compliance control reads; the aws:SourceIdentity condition key and any downstream audit query see nothing.
Fix: the assumed-role session state plus the CloudTrail event emission for calls authenticated by session credentials — persist SourceIdentity on the session and render userIdentity.sessionContext.sourceIdentity (and the session-named ARN) on every event produced by that session, in the STS session state and the CloudTrail record builder.
Traces: sts.assume-role-source-identity-echoed.
