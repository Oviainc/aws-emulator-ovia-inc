# Transfer: the in-order SendWorkflowStepState a CUSTOM workflow step's own target makes never succeeds, so an OnUpload execution never completes and a consumed callback token is unreachable

> _Note: this issue was identified against the code base at commit `a9d97d81503b3005fc8c3c6f350451e3d0a3f288`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendWorkflowStepState

## Description
ONE net-new root cause in the transfer emulator, grounded in the single failing behavioral check of this replay that the report marked neither 'ALREADY FILED' nor 'OWNED by'.

=== Cause 1 of 1: a CUSTOM workflow step is now invoked with a callback token, but the step target's own in-order SendWorkflowStepState(Status='SUCCESS') for that live token never completes, so the step never reports and the at-most-once token rule cannot be exercised ===
Failing check: transfer.workflow-step-state-out-of-order-rejected.

AWS: Smithy com.amazonaws.transfer#SendWorkflowStepState input {WorkflowId @required len 19..19 pattern ^w-([a-z0-9]{17})$, ExecutionId @required len 36..36 UUID pattern, Token @required len 1..64 pattern ^\w+$, Status @required CustomStepStatus (FAILURE|SUCCESS)}; output is EMPTY; modeled errors AccessDeniedException 403, InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503, ThrottlingException 429. The model documents the operation as 'Sends a callback for asynchronous custom steps. The ExecutionId, WorkflowId, and Token are passed to the target resource during execution of a custom step of a workflow.' So the FIRST callback a step's target makes with the token it was handed — the in-order one — SUCCEEDS with HTTP 200 and an empty body, and it is what records that step's outcome and completes the single-step execution. Only a REPLAY of that same, now consumed, token is refused: HTTP 404, error code ResourceNotFoundException, message exactly 'Unknown execution' (entirely fixed text — no request- or state-derived part; the ExecutionId travels in the error's Resource member, the type in ResourceType='Execution'), and DescribeExecution(WorkflowId, ExecutionId) must answer identically before and after the refused replay. Recorded behavior for the surrounding chain: a file landing on a server whose WorkflowDetails.OnUpload names a workflow starts one execution; the workflow's CUSTOM step invokes its Lambda Target with an event carrying token and serviceMetadata.executionDetails.{workflowId, executionId}; that function's side effects are observable in order (here it writes tokens/<token>.json, then calls SendWorkflowStepState, then writes tokens/<token>.done). The bucket name, function name, token, execution id and object keys are all request/environment-derived and are NOT requirements; the requirement is the ORDER and the fact that the in-order callback returns success.

Emulator: the chain now gets one step further than the last sweep did — the OnUpload execution IS started and the CUSTOM step IS invoked, shown by the pre-callback marker object tokens/<token>.json now appearing (the check reads it and gets a well-formed marker whose workflowId matches the created workflow, so the event's token/workflowId/executionId are all present). What never happens is the step's report: the '.done' object the same handler writes on the line immediately AFTER its transfer.send_workflow_step_state(..., Status='SUCCESS') call never appears, and the check fails after 60s with 'AssertionError: condition not met within 60s, last value=False'. The in-order callback therefore did not return 200 — it either raised a modeled refusal inside the step's function or did not answer at all within the function's 30s timeout. Because the function's outcome is swallowed (src/state/connector_delivery.rs::invoke_custom_step only emits a tracing::warn for an invoke that errors or times out, and the step is deliberately 'left pending'), nothing surfaces to the caller: the execution stays IN_PROGRESS forever (WorkflowExecution::reported_status in src/state/workflow_runs.rs derives status purely from step_states, which stay None), and no consumed token is ever obtainable.
Hypothesis (neither the model nor the replay output says which link breaks — the replay shows only that the pre-call marker appears and the post-call marker never does): the live-token path through src/ops/send_workflow_step_state.rs is where the in-order callback is decided, and each of its three gates answers a modeled refusal for a token that should be accepted — guard.workflows.contains_key(workflow_id) -> 403 AccessDeniedException, workflow_executions.get_mut((workflow_id, execution_id)) -> 404 ResourceNotFoundException, step_states.get_mut(token) -> 400 InvalidRequestException 'Token does not address a pending custom step of this execution' — so a mismatch between what connector_delivery mints into the event (state.rs mint_execution_id/mint_callback_token, connector_delivery::custom_step_event) and the keys the handler looks the callback up under, or an execution released by take_execution_capacity/release_executions_of before the callback arrives, produces exactly the observed outcome. A nested in-process call that cannot complete while the delivery task is in flight would produce the same symptom (the handler's state.lock() blocking the callback until the function's own 30s timeout) — note the same handler's S3 calls from inside that function DO complete, so the stall, if any, is specific to this service's own state.

Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback token) sees its step's target invoked and then sees nothing ever happen: the step's own success report is lost, the execution never leaves IN_PROGRESS, ListExecutions/DescribeExecution keep reporting a run that finished, and the at-most-once property of a callback token — the property that makes a token safe to retry against, and the whole point of the 404 'Unknown execution' refusal on a replay — cannot be observed at all. Retry and idempotency logic written against real Transfer Family is untestable here, and a caller cannot tell 'my function failed to call back' from 'this target refuses the callback my function made'.

Fix: the SendWorkflowStepState handler and the workflow-execution state it resolves against — services/service-com-amazonaws-transfer-transferservice/src/ops/send_workflow_step_state.rs together with src/state/workflow_runs.rs and the writer that starts the run and mints the token, src/state/connector_delivery.rs (start_upload_executions / custom_step_event / invoke_custom_step) — must accept the FIRST callback for a token a started execution is still holding as pending: HTTP 200, empty body, the reported Status recorded on that step, and the execution's derived status moving to COMPLETED (or EXCEPTION for FAILURE). The keys the callback is resolved under must be exactly the values the step's event carried, and an execution must not be released while any of its steps is still pending. Only a token already reported must answer the modeled 404 ResourceNotFoundException with the fixed message 'Unknown execution' and leave DescribeExecution's answer unchanged. The callback leg should also stop being silent: an invocation that errors or times out leaves a step pending with only a tracing::warn, which is why this failure is invisible from the API.
