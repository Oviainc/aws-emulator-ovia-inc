# glue: 2 net-new causes — BACKWARD schema compatibility is never evaluated (every registered version settles AVAILABLE) and BatchDeleteTableVersion's per-entry ErrorMessage is emulator-authored

> _Note: this issue was identified against the code base at commit `4a9463f06c8da54961be1caf9572b353149b691e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterSchemaVersion

## Description
Two net-new root causes in the Glue service, both found by the behavioral suite. Cause 1 is in the Schema Registry version-registration path (RegisterSchemaVersion / GetSchemaVersion / GetSchemaByDefinition); Cause 2 is in the Data Catalog table-version delete path (BatchDeleteTableVersion). They are bundled because both are glue and both are small, localized handler/state defects. A fixer must close BOTH causes before submitting.

Cause 1 of 2: a schema version that breaks the schema set's compatibility mode is registered and reported AVAILABLE; the emulator has no FAILURE outcome at all.
  AWS: Smithy (services/service-com-amazonaws-glue-awsglue/smithy-model/com-amazonaws-glue-awsglue.json): RegisterSchemaVersion input {SchemaId @required, SchemaDefinition @required, SchemaDefinitionString @length 1..170000 pattern \S}; output {SchemaVersionId, VersionNumber, Status}; Status targets the enum SchemaVersionStatus = [AVAILABLE, PENDING, FAILURE, DELETING]. GetSchemaVersion output likewise carries Status: SchemaVersionStatus, so the status is a persisted property of the version, not a function of the read. RegisterSchemaVersion's own documentation states it "Returns an error if new version of schema does not meet the compatibility requirements of the schema set" and that "this call has the potential to run longer than other operations due to compatibility modes. You can call the GetSchemaVersion API with the SchemaVersionId to check compatibility modes." CreateSchema's Compatibility targets the enum Compatibility = [NONE, DISABLED, BACKWARD, BACKWARD_ALL, FORWARD, FORWARD_ALL, FULL, FULL_ALL]. Recorded behavior: for a schema created with Compatibility=BACKWARD and an AVRO v1 record, registering a version that only ADDS a field carrying a default is compatible and settles with Status=AVAILABLE; registering a version that adds a REQUIRED field with NO default breaks BACKWARD compatibility, is still stored (it still consumes a VersionNumber, LatestSchemaVersion still advances to it, and GetSchemaByDefinition still resolves its exact bytes back to its SchemaVersionId) but settles with Status=FAILURE. The outcome is reported in the version's Status, not as a client error — i.e. HTTP 200 either way.
  Emulator: the incompatible version is accepted and settles AVAILABLE. GetSchemaVersion on that version id answers HTTP 200 with Status='AVAILABLE' where AWS answers Status='FAILURE' (replay detail: "AssertionError: expected incompatible version FAILURE, got AVAILABLE"). Because no version ever reaches FAILURE, the downstream reads this check makes are unreachable in the emulator too: GetSchemaByDefinition for the incompatible bytes must resolve with Status='FAILURE', and LatestSchemaVersion must have advanced to that FAILURE version — a fix must make those hold as well, not just the single asserted value. The compatible control version settling AVAILABLE is correct and must not regress.
  Why: the version Status is the ONLY channel AWS uses to report a failed evolution (the call itself is a 200), and Glue's own docs tell clients to poll GetSchemaVersion to learn the compatibility verdict. A CI pipeline or producer that registers a candidate definition and gates deployment on Status reaching AVAILABLE sees every candidate accepted, so a definition real Glue would mark FAILURE is promoted to production and breaks every existing consumer of that schema. Conversely a client can never observe the FAILURE state it must handle.
  Fix: the RegisterSchemaVersion handler plus the schema-registry state in the glue crate — a stored version record must carry its own SchemaVersionStatus, set by an actual compatibility evaluation of the submitted definition against the schema set under the schema's Compatibility mode, instead of a constant AVAILABLE; GetSchemaVersion's and GetSchemaByDefinition's projections must then serialize that stored status. Registration must remain a 200 and must still store the version, advance LatestSchemaVersion and keep the definition resolvable by GetSchemaByDefinition when the verdict is FAILURE.
  Nearest open issue, which does NOT cover this: 20261108T174217Z-glue-schema-registry-version-registration-never-validates-or.md describes the same constant-AVAILABLE defect from the wire corpus, but it is keyed to the wire fixture glue-schema-registry-versioning and carries none of this behavioral check's keys; it also does not state the BACKWARD-mode rule this check exercises (added-field-with-default compatible vs added-required-field-without-default incompatible) nor the GetSchemaByDefinition/LatestSchemaVersion consequences above. 20261025T170315Z-glue-registerschemaversion-stub.md and 20261025T022820Z-glue-checkschemaversionvalidity-stub.md are about operations being stubs; RegisterSchemaVersion and GetSchemaVersion both answer 200 here, so neither covers this.
  Traces: glue.e2e-schema-registry-compatibility-enforced-across-versions.

Cause 2 of 2: BatchDeleteTableVersion's per-version ErrorDetail.ErrorMessage is an emulator-authored, id-interpolated sentence instead of AWS's fixed text.
  AWS: Smithy: BatchDeleteTableVersion input {CatalogId, DatabaseName @required, TableName @required, VersionIds @required (list, @length 0..100)}; output {Errors: TableVersionErrors}. A TableVersionError carries TableName, VersionId and ErrorDetail; ErrorDetail carries ErrorCode (NameString) and ErrorMessage (DescriptionString, @length 0..2048). The version id and table name therefore travel in their OWN modeled members and are not part of the message. Recorded behavior: a VersionIds entry that names no stored version is reported in band at HTTP 200 with ErrorDetail.ErrorCode='EntityNotFoundException' and ErrorDetail.ErrorMessage='Version not found.' — the whole sentence is FIXED text, with NO variable part and a terminating period. Beyond that the model says nothing about the wording: recorded behavior only.
  Emulator: the status (200), the per-entry keying by VersionId and the ErrorCode ('EntityNotFoundException') all match, but ErrorMessage is 'Table version (<VersionId>) not found' — different words, the requested version id interpolated into the message (duplicating the structured TableVersionError.VersionId member) and the trailing period dropped (replay detail: "{'9999': {'ErrorCode': 'EntityNotFoundException', 'ErrorMessage': 'Table version (9999) not found'}}" where 'Version not found.' was required; the 9999 is this run's requested version id filling the emulator's template and is not part of the requirement).
  Why: BatchDeleteTableVersion reports partial failure IN BAND at 200, so this record is a client's only signal about which versions were skipped. Code that matches ErrorDetail.ErrorMessage to classify a partial batch never matches, so a partially failed prune is treated as wholly successful (or wholly failed) and history is pruned incorrectly. The redundant interpolation also makes the text vary per request where AWS's is constant, breaking exact-match assertions and message-keyed metrics.
  Fix: the BatchDeleteTableVersion handler's per-version error construction in the glue crate — emit the fixed ErrorDetail.ErrorMessage for a missing version and let TableVersionError.VersionId/.TableName carry the identity, instead of formatting the requested id into the sentence.
  Nearest open issue, which does NOT cover this: 20261108T101230Z-glue-table-version-not-found-refusals-carry-emulator.md describes the same wording defect from the wire corpus (keyed to fixture glue-database-update-and-table#task#13) and carries none of this behavioral check's keys, so this check is still unowned by it.
  Traces: glue.table-version-deletion.
