# migrationhubstrategy import loop broken end to end: the MigrationHubStrategy service-linked role is minted under a derived name GetRole cannot resolve, and StartImportFileTask never ingests the import file (numberOfRecordsSuccess always 0) — 2 causes

> _Note: this issue was identified against the code base at commit `bd3308b0c8d992d57414e8fe0564c68280e702c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartImportFileTask

## Description
The behavioral suite drove MigrationHubStrategy's documented import-then-assess loop and every check failed. Clustering the 9 failures that are not already covered by a filed scaffold-stub issue (ListServers, ListImportFileTask, GetPortfolioPreferences, IAM ListRoles) leaves exactly TWO root causes. Both must be closed before re-submitting.

=== Cause 1 of 2: the service-linked role for migrationhub-strategy.amazonaws.com is created under a mechanically derived name, so GetRole on the AWS role name answers NoSuchEntity forever ===
AWS: IAM CreateServiceLinkedRole(AWSServiceName="migrationhub-strategy.amazonaws.com") creates the service's documented service-linked role and returns it in CreateServiceLinkedRoleResponse$Role; that role's RoleName is the per-service name AWS publishes — AWSServiceRoleForMigrationHubStrategy — and a subsequent GetRole(RoleName="AWSServiceRoleForMigrationHubStrategy") resolves it (HTTP 200) instead of answering NoSuchEntity (HTTP 404). Smithy: com.amazonaws.iam#CreateServiceLinkedRole.AWSServiceName is documented as "The service principal ... Service principals are unique and case-sensitive. To find the exact service principal for your service-linked role, see Amazon Web Services services that work with IAM" — i.e. the principal is the lookup key for a per-service role whose name the API model does not carry. The exact SLR name is recorded/documented behavior only; the requirement the checks exercise is that the role created for this principal is readable under the name AWS assigns it.
Emulator: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/create_service_linked_role.rs derives the role name from the principal's FIRST DOT-LABEL with only its initial letter upper-cased (fn service_linked_role_name: split('.').next(), capitalise first char, prepend AWSServiceRoleFor). For "migrationhub-strategy.amazonaws.com" that yields AWSServiceRoleForMigrationhub-strategy. The create call therefore succeeds, but GetRole(RoleName="AWSServiceRoleForMigrationHubStrategy") keeps answering NoSuchEntityException (404), so every check that creates the role and then waits for it to become visible spins until its budget is gone ("Check timed out after 60.0s"). Seven checks never reach a single MigrationHubStrategy assertion because of this.
Why: a client follows the service's documented prerequisite — create AWSServiceRoleForMigrationHubStrategy, then confirm/attach/inspect it by that name (GetRole, AttachRolePolicy, iam:PassRole, CloudFormation and Terraform SLR resources all key on the published name). Against the emulator every such read 404s, so the prerequisite can never be established and the whole import/assessment workflow is unreachable; no hyphenated-label service (migrationhub-strategy, migrationhub-orchestrator, etc.) can be bootstrapped at all.
Fix: IAM's CreateServiceLinkedRole handler/name derivation — the principal→role-name mapping must yield the name AWS assigns for that principal (and the role record filed under it) rather than a mechanical capitalisation of the first label; the role returned in CreateServiceLinkedRoleResponse$Role and the role GetRole resolves must agree on that name.
Traces: migrationhubstrategy.import-file-task-server-lifecycle-and-record-creation, migrationhubstrategy.import-file-task-invalid-name-pattern-rejected, migrationhubstrategy.import-file-task-partial-failure-records-failed-count, migrationhubstrategy.import-process-links-application-component-to-server, migrationhubstrategy.recommendation-report-generation-lifecycle-reaches-success, migrationhubstrategy.concurrent-recommendation-report-generation-exactly-one-succeeds, migrationhubstrategy.update-server-config-not-found-effect-absent. Each of these calls iam.create_service_linked_role(AWSServiceName="migrationhub-strategy.amazonaws.com") and then polls iam.get_role(RoleName="AWSServiceRoleForMigrationHubStrategy") with a 60s deadline; the two surviving checks that do NOT poll get_role (see Cause 2) are the only ones that get past the prerequisite, which is what isolates this cause. Code: services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/ops/create_service_linked_role.rs:143-159.

=== Cause 2 of 2: StartImportFileTask reaches ImportSuccess having ingested nothing — numberOfRecordsSuccess/numberOfRecordsFailed are always 0 and no SERVER/PROCESS records are created ===
AWS: StartImportFileTask reads the import file at (S3Bucket, s3key) and ingests the Resources it declares; GetImportFileTask then reports the outcome of that ingestion — Smithy: GetImportFileTaskResponse$numberOfRecordsSuccess is documented "The number of records successfully imported." and numberOfRecordsFailed the number that failed — and the imported resources become visible through the service's read path (ListServers/GetServerDetails, ListApplicationComponents/GetApplicationComponentDetails). An import file declaring N well-formed SERVER resources therefore terminates ImportSuccess with numberOfRecordsSuccess == N and numberOfRecordsFailed == 0.
Emulator: the task is minted with number_of_records_success: 0 / number_of_records_failed: 0 and the S3 object is never read; settle() flips the status to ImportSuccess after a fixed span without touching the counters, so GetImportFileTask reports status ImportSuccess with numberOfRecordsSuccess == 0 for any import file. Replay: an import of 3 SERVER resources gave "expected 3 records imported, got 0"; an import of one SERVER plus one PROCESS gave "expected both SERVER and PROCESS records imported, got numberOfRecordsSuccess=0". Consequently no server or application-component record ever enters the store either (state.rs::imported_server_count sums those zero counters), so the whole downstream read path has nothing to return.
Why: a client uses the record counts as the import's success signal and then reads the imported inventory; against the emulator the import claims success while reporting zero records and the inventory stays empty, so import validation, partial-failure handling, group filtering, per-server/per-component config updates and assessments all operate on an empty account while the API says the import succeeded. This is a silent wrong answer, not an error a client can detect.
Fix: the StartImportFileTask/GetImportFileTask state machine — the import must parse the referenced import-file object, count ingested vs failed records onto the task record, and materialise the SERVER/PROCESS/application-component entities into service state so the service's read operations can see them. (The read operations themselves, ListServers and ListImportFileTask, are separately filed as unimplemented stubs; this cause is the ingestion and the counters behind them.)
Traces: migrationhubstrategy.import-pagination-across-multiple-servers (AssertionError: expected 3 records imported, got 0), migrationhubstrategy.update-application-component-config-inclusion-status-transitions (AssertionError: expected both SERVER and PROCESS records imported, got numberOfRecordsSuccess=0). Code: services/service-com-amazonaws-migrationhubstrategy-awsmigrationhubstrategyrecommendation/src/ops/start_import_file_task.rs:219-223 and src/state.rs:29-35,106-116,326-333.
