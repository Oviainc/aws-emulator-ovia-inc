# CloudFormation never provisions a dependency graph concurrently and never gates a WaitCondition on SignalResource: a diamond stack's two independent branch heads are never both CREATE_IN_PROGRESS

> _Note: this issue was identified against the code base at commit `a2be7a3586c8a34d922aa1b24d2f445b80a06855`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
One net-new behavioral root cause in CloudFormation's provisioning engine, grounded in the only cloudformation__sns__sqs check the replay report left unattributed.

Cause 1 of 1: the provisioning engine exposes no concurrent scheduling of independent graph branches, and an AWS::CloudFormation::WaitCondition with CreationPolicy.ResourceSignal is never held open waiting for SignalResource.

AWS: CreateStack builds a dependency graph from DependsOn plus the implicit Ref/Fn::GetAtt edges and provisions every resource whose dependencies are satisfied CONCURRENTLY — two independent branches of a diamond are in flight at the same time, a branch's tail may complete while the other branch's head is still open, and a join resource is scheduled only after ALL of its predecessors complete. A resource carrying CreationPolicy.ResourceSignal (Count/Timeout, e.g. PT10M) stays in ResourceStatus CREATE_IN_PROGRESS until the required number of signals arrives; Smithy: SignalResource input = {StackName (required, length min 1, pattern ^([a-zA-Z][-a-zA-Z0-9]*)|(arn:\b(aws|aws-us-gov|aws-cn)\b:[-a-zA-Z0-9:/._+]*)$), LogicalResourceId (required), UniqueId (required, @length 1..64), Status (required, enum ResourceSignalStatus)}, output empty, no modeled errors. While the condition is unsignalled the stack does not advance; DescribeStackResource reports that logical id's ResourceStatus as CREATE_IN_PROGRESS (Smithy: DescribeStackResource -> StackResourceDetail), and DescribeStackEvents (Smithy: paginated on NextToken, items StackEvents) records TWO CREATE_IN_PROGRESS events per resource — the first with no ResourceStatusReason (the scheduler's pick off the ready set) and a second reading 'Resource creation Initiated'. DeleteStack then tears the graph down in REVERSE topological order: the join reaches DELETE_COMPLETE before either branch's delete begins, and the two independent branches delete concurrently.

Emulator: the check never gets past its FIRST observable. It polls DescribeStackResource for GateA and GateB until one single poll reports both as CREATE_IN_PROGRESS (the check's own 300 s budget) and that state is never reported; the check is cut by the harness with 'Error: Check timed out after 60.0s'. Nothing downstream of that poll (SignalResource on either gate, the branch-tail overlap, the join's predecessor gating, the reverse-order teardown, the fan-out data plane through the stack-created topic and queues, the post-delete absence probes) is ever reached. Hypothesis: the resource-level status the poll depends on is simply not produced — the already-filed 20261025T015306Z-cloudformation-stack-events-and-resource-views-are-incomplete.md records that this engine emits no per-resource events at all and that DescribeStackResource answers ValidationError for ids it does not track, so each gate reads as absent rather than as an open wait condition, and a WaitCondition is never a blocking node in the graph (see also 20261025T150742Z-cloudformation-3-net-new-behavioral-root-causes-an.md, 'an unsignalled WaitCondition never times out', and 20261025T231252Z-cloudformation-2-net-new-root-causes-a-disablerollback). None of those issues carries this check's replay key and none of them states the concurrency property, so this cause is not covered by them.

Why: a client cannot deploy or reason about any real template whose shape is not a single chain. Templates that gate provisioning on an out-of-band signal (WaitCondition/WaitConditionHandle, cfn-signal from an instance or a bootstrap job) never make progress, so the deploy either hangs or completes without ever having waited. Templates with independent branches get no parallelism, so deploy wall-clock and ordering differ from AWS, and a client that relies on a join resource (here an AWS::SQS::QueuePolicy DependsOn both branch tails) being scheduled after ALL predecessors, or on reverse-order teardown, cannot verify either against the emulator. Downstream, a fan-out the stack is supposed to have wired (SNS topic + two SQS subscriptions + the queue policy that authorizes sns.amazonaws.com) is never observable as working.

Fix: the CloudFormation provisioning engine — the ready-set scheduler that walks the resource graph (it must dispatch every dependency-satisfied resource concurrently rather than serially in template or sorted order), the CreationPolicy.ResourceSignal handling that must keep such a resource CREATE_IN_PROGRESS until SignalResource satisfies Count or the Timeout fires, the SignalResource handler that releases it, the per-resource status/event records DescribeStackResource and DescribeStackEvents serve, and the delete planner that must reverse the same topological order.

Traces: cloudformation__sns__sqs.cfn-independent-branches-provision-concurrently-and-tear-down-in-reverse. Note for the fixer: this check holds 20 s deliberately (HOLD_S) after it observes both gates open, so confirming the fix needs the check's own budget, not the 60 s cap that cut it.

## Evidence
Expected (AWS): a single DescribeStackResource poll over the diamond's two WaitCondition heads reports {'GateA': 'CREATE_IN_PROGRESS', 'GateB': 'CREATE_IN_PROGRESS'}; SignalResource(StackName, LogicalResourceId='GateA', UniqueId=..., Status='SUCCESS') releases only branch A, QueueA reaches CREATE_COMPLETE while GateB is still CREATE_IN_PROGRESS, JoinPolicy is scheduled only after SubA, SubB, QueueA and QueueB have all completed and is the last resource to reach CREATE_COMPLETE, the stack ends CREATE_COMPLETE, and after DeleteStack the join's DELETE_COMPLETE precedes both branches' DELETE_IN_PROGRESS while the two branches' delete intervals overlap.

Actual (emulator): cloudformation__sns__sqs.cfn-independent-branches-provision-concurrently-and-tear-down-in-reverse — verdict 'mismatch', 'Error: Check timed out after 60.0s'. The check's first blocking observation is the both-gates-CREATE_IN_PROGRESS poll (its own timeout_s=300.0, interval_s=2.0 over DescribeStackResource); it never returns, so no SignalResource call, no event-timestamp comparison, no fan-out publish and no teardown ordering assertion is ever executed. Consistent with the already-filed finding that this engine records no per-resource events and does not track resource-level status (20261025T015306Z-cloudformation-stack-events-and-resource-views-are-incomplete.md).

5. After CREATE_COMPLETE, page DescribeStackEvents and check for two CREATE_IN_PROGRESS events per logical id (one with no ResourceStatusReason, one reading 'Resource creation Initiated'), then DeleteStack and compare the join's DELETE_COMPLETE stamp against each branch's DELETE_IN_PROGRESS stamp.
