Cause 1 of 1: a message SQS moved to a dead-letter queue by a RedrivePolicy carries no DeadLetterQueueSourceArn message system attribute, so a consumer of the DLQ cannot tell which source queue the message came from.
AWS: Smithy (com.amazonaws.sqs) publishes DeadLetterQueueSourceArn as a value of the MessageSystemAttributeName enum (values: All, SenderId, SentTimestamp, ApproximateReceiveCount, ApproximateFirstReceiveTimestamp, SequenceNumber, MessageDeduplicationId, MessageGroupId, AWSTraceHeader, DeadLetterQueueSourceArn), and ReceiveMessage$MessageSystemAttributeNames (and the discontinued AttributeNames) documents "All – Returns all values". The attribute's meaning is recorded behavior only (the model carries no prose for this enum value): when SQS moves a message to a dead-letter queue because the source queue's RedrivePolicy maxReceiveCount was exceeded, it stamps the moved message with DeadLetterQueueSourceArn whose value is the ARN of the queue the message was moved FROM, and a ReceiveMessage on the DLQ asking for All reports it alongside ApproximateReceiveCount, SentTimestamp and SenderId. The whole value is taken from state (the source queue's ARN: arn:aws:sqs:<region>:<account>:<source queue name>); nothing in it is fixed text.
Emulator: the attribute is never reported, for two reasons that sit in one path. (1) services/service-com-amazonaws-sqs-amazonsqs/src/state.rs, ComAmazonawsSqsAmazonsqsState::dead_letter_due (the automatic redrive a receive applies before deciding what to deliver) rebuilds the moved record as `StoredMessage { available_at: now, invisible_until: None, queue_receive_count: 0, retention_from: …, ..message }` — it re-homes the message into the target queue without recording the source queue it came from anywhere on the record, and StoredMessage has no field for it. (2) services/service-com-amazonaws-sqs-amazonsqs/src/ops/receive_message.rs, fn system_attributes, deliberately offers only SenderId, SentTimestamp, ApproximateReceiveCount, ApproximateFirstReceiveTimestamp, AWSTraceHeader, MessageGroupId, MessageDeduplicationId and SequenceNumber ("The rest of the MessageSystemAttributeName set belongs to behaviour that is not implemented, so it is omitted rather than invented"), so even a request naming DeadLetterQueueSourceArn or All gets nothing back. The replay shows the dead-lettered message arriving on the DLQ with the right MessageId and then `attrs.get("DeadLetterQueueSourceArn")` being None.
Why: the DLQ is the inspection point for every record a pipe (or any consumer) could not process, and a dead-letter queue is routinely shared by several source queues. A client that triages or re-drives by origin reads DeadLetterQueueSourceArn to decide where a message came from and where it must go back; with the attribute absent, every dead-lettered message looks source-less, fan-in DLQ topologies become unattributable, and code that keys a dict on that attribute raises a KeyError or silently drops the record instead. It also hides the one piece of evidence that distinguishes "SQS redrove this message" from "somebody sent it here directly".
Fix: the SQS dead-letter redrive path — ComAmazonawsSqsAmazonsqsState::dead_letter_due in services/service-com-amazonaws-sqs-amazonsqs/src/state.rs must record the source queue's ARN on the message it hands to the target queue (a field on StoredMessage alongside sender_id/sent_at, set from the source queue's own arn, and preserved by the message-movement task path that drives such a message back), and fn system_attributes in services/service-com-amazonaws-sqs-amazonsqs/src/ops/receive_message.rs must offer "DeadLetterQueueSourceArn" from that field for the messages that carry one (and only those), so a receive asking for All or for that name reports it.
