# dynamodb__kinesis__lambda: a DynamoDB-Streams event source mapping that exhausts MaximumRetryAttempts delivers no DDBStreamBatchInfo OnFailure record to its SQS destination (1 cause)

> _Note: this issue was identified against the code base at commit `d1f488ff5b87ae19d202e4a045e598018e7d1458`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateEventSourceMapping

## Description
This issue has 1 cause.

Cause 1 of 1: a DynamoDB-Streams -> Lambda event source mapping configured with MaximumRetryAttempts and DestinationConfig.OnFailure pointing at an SQS queue never produces the on-failure record, so the retry-exhaustion path of a stream ESM has no observable effect at all.

AWS: Smithy (com.amazonaws.lambda#AWSGirApiService): CreateEventSourceMapping (POST /2015-03-31/event-source-mappings, success 202) takes EventSourceArn (Arn), StartingPosition (EventSourcePosition enum), BatchSize (range 1..10000), MaximumBatchingWindowInSeconds (0..300), BisectBatchOnFunctionError (boolean), MaximumRetryAttempts (MaximumRetryAttemptsEventSourceMapping, range -1..10000), MaximumRecordAgeInSeconds (-1..604800) and DestinationConfig (with OnFailure.Destination); its modeled client errors are InvalidParameterValueException 400, ResourceConflictException 409, ResourceNotFoundException 404, TooManyRequestsException 429. The record the poller writes to the OnFailure destination is not in the Smithy model, so for its shape this is recorded behavior only: for a DynamoDB-Streams source, once the function has been invoked MaximumRetryAttempts+1 times with the identical batch and still failed, the poller sends ONE message to the OnFailure queue whose JSON body is a POINTER, never the stream records. Its fixed members are the top-level key DDBStreamBatchInfo (source-specific: a Kinesis source uses KinesisBatchInfo and a DynamoDB source must never be described as Kinesis) carrying shardId, startSequenceNumber, endSequenceNumber, batchSize and streamArn; requestContext with condition == "RetryAttemptsExhausted", approximateInvokeCount == MaximumRetryAttempts+1 and functionArn naming the failing function; and responseContext.functionError == "Unhandled" for a raised exception. The variable parts are taken from the request and state: the shard id and sequence numbers are the source stream's own, batchSize is the size of the failed batch, streamArn is the EventSourceArn, and the function ARN is the configured function's. The pointer must dereference: DynamoDB Streams GetShardIterator(ShardIteratorType=AT_SEQUENCE_NUMBER, SequenceNumber=startSequenceNumber) followed by GetRecords must return exactly the batchSize records the function failed on, ending at endSequenceNumber. The item images must NOT appear anywhere in the SQS body.

Emulator: the check is killed at the harness 60 s cap with no assertion reached and no API error raised, so the run was still inside its long-poll for the OnFailure message (the check's own budget for that wait is 200 s). Nothing was ever delivered to the SQS OnFailure queue, so neither the retry accounting (two invocations with the identical batch), nor the DDBStreamBatchInfo pointer, nor requestContext.condition == "RetryAttemptsExhausted" is observable. Because the verdict is a timeout rather than an assertion failure, the replay output does not name the exact blocking call; Hypothesis: the DynamoDB-Streams event-source poller does not invoke the function at all, which is the same blocking point already filed for the sibling check in open issue 20261025T192630Z-dynamodb-lambda-s3-a-dynamodb-streams-event-source.md (service token dynamodb__lambda__s3, so it does not carry this check's replay key). That hypothesis must be confirmed by re-running this check; if the function IS invoked and retried, the defect is the OnFailure destination writer alone. Related-but-not-covering open issues, named per instructions: 20261025T192630Z-dynamodb-lambda-s3-a-dynamodb-streams-event-source.md, 20261025T011017Z-dynamodb-lambda-stream-enabled-createtable-never-becomes-visible-to-describetable.md, 20261024T150703Z-apigateway-dynamodb-lambda-logs-a-dynamodb-streams-event.md, 20261023T110802Z-dynamodb-stream-enablement-is-unimplemented-createtable-with-streamspecification.md (CreateTable now answers 200 and 7 of 11 dynamodbstreams checks pass in this run, so that refusal is no longer the blocker). None of them carries this check's replay key; the suite reported it unowned.

Why: a client relying on AWS's behavior loses its entire poison-pill story. A stream batch the function cannot process is supposed to be parked as a pointer on the configured destination so an operator can dereference it, replay exactly those records, and alert on condition == RetryAttemptsExhausted. Against the emulator the failure is silent: no message, no counter, no error anywhere, so code that treats the OnFailure queue as the dead-letter of record sees a healthy, empty queue while records are dropped. A client also cannot tell a DynamoDB source from a Kinesis one, because neither pointer key is ever emitted.

Fix: the DynamoDB-Streams event-source poller behind lambda CreateEventSourceMapping (the component that opens shard iterators on the source stream ARN, invokes the function with the batch, counts attempts against MaximumRetryAttempts, and writes the terminal record to DestinationConfig.OnFailure), plus its on-failure record serializer, which must choose the source-specific DDBStreamBatchInfo key for a DynamoDB stream ARN and emit the pointer members only, never the record images.
