# apigateway__cloudformation__lambda: a Custom:: resource whose Lambda provider answers SUCCESS still fails the stack — the no-forced-failure control ends ROLLBACK_COMPLETE instead of CREATE_COMPLETE

> _Note: this issue was identified against the code base at commit `cb4018749ce62725bb0d8ace7cfa8a8c0d6da7be`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
One net-new behavioral root cause of this service group, grounded in one failing behavioral check of this replay. The check is NOT marked OWNED or ALREADY FILED in the replay report: the open issue 20261105T153010Z-apigateway-cloudformation-lambda-3-net-new-causes-a.md does list this check id, but its replay key for it is an earlier failure point (`run#13|AssertionError|assert topic_event is not None`), i.e. the missing sibling CREATE_COMPLETE event. That assertion — and the whole negative half of the check (rollback to ROLLBACK_COMPLETE, the custom resource's CREATE_FAILED event, the sibling topic's CREATE_COMPLETE event with its PhysicalResourceId, and SNS answering NotFound/'Topic does not exist' for the rolled-back topic) — now passes. What fails is the positive control that follows it, a different key and a different observable, so it is filed here rather than silently closed with the older key. Cause 1 of that issue (a Lambda-backed Custom:: resource never settles) is the nearest neighbour and may well share this root cause; it is named here so a fixer can see that, not because it carries this key.

Cause 1 of 1: the identical template deployed with the provider's forced failure switched OFF — so the provider handler answers cfnresponse.SUCCESS — still fails the stack and rolls it back.
AWS: recorded behavior only for the custom-resource protocol; the shapes are modelled (Smithy com.amazonaws.cloudformation#StackStatus includes CREATE_IN_PROGRESS, CREATE_COMPLETE, ROLLBACK_IN_PROGRESS, ROLLBACK_COMPLETE; com.amazonaws.cloudformation#ResourceStatus likewise; DescribeStacks' Stack carries Outputs). CloudFormation sends the function named by the custom resource's ServiceToken a Create request carrying a pre-signed ResponseURL; the handler PUTs Status SUCCESS with a PhysicalResourceId and a Data object; the resource becomes CREATE_COMPLETE, Fn::GetAtt on the resource resolves against that Data (here Fn::GetAtt [MyResource, 'RequestType'] -> 'Create'), the stack settles CREATE_COMPLETE, and every resource it created — here a sibling AWS::SNS::Topic published as an output — remains, so sns:GetTopicAttributes on it answers 200. For a function with inline Code.ZipFile, AWS makes the cfnresponse module importable in the python runtime alongside the runtime's bundled boto3, which is what the documented `import cfnresponse` / `cfnresponse.send(event, context, cfnresponse.SUCCESS, data, id)` idiom relies on.
Emulator: the create of that same template reaches the terminal status ROLLBACK_COMPLETE, so no custom-resource Data is ever published, the stack has no Outputs, and the sibling topic is torn down. The provider's SUCCESS answer never arrives — the emulator fails a resource whose provider was supposed to succeed, i.e. it cannot distinguish 'provider answered FAILED' (the negative half, which now behaves correctly) from 'provider answered SUCCESS'. Hypothesis: the provider handler never runs or never PUTs to the ResponseURL (no in-process python runtime / no injected cfnresponse module), so the resource's stabilisation barrier always fails.
Why: a client cannot deploy any template that uses the custom-resource extension point — the only mechanism by which a template provisions anything CloudFormation does not model natively. A deploy that AWS completes becomes a rollback: every resource the stack did create is deleted, Fn::GetAtt on provider Data resolves to nothing, and the stack is left in ROLLBACK_COMPLETE, a state no CreateStack retry can leave. Worse, the emulator is now self-contradictory as an oracle: the same template fails whether the provider succeeds or fails, so a client cannot use the stack status to tell a broken provider from a working one.
Fix: the cloudformation crate's custom-resource provisioning and stabilising path — the delivery of the Create/Update/Delete request to the ServiceToken function, the recording of the provider's SUCCESS response (PhysicalResourceId + Data) and the resource's transition to CREATE_COMPLETE — together with the lambda Invoke execution path and the python module set (boto3 + the CloudFormation-injected cfnresponse) an inline-ZipFile function is given.
Traces: apigateway__cloudformation__lambda.cfn-stack-rollback-on-custom-resource-failure (positive-control half). Relevant components: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/custom_resource.rs, services/service-com-amazonaws-cloudformation-cloudformation/src/state/stabilising.rs, services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs.
