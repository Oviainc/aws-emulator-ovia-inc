# ec2__iam__kms__secretsmanager: a KMS authorization refusal is relayed verbatim to the caller instead of Secrets Manager's fixed message 'Access to KMS is not allowed' (1 cause, 11 checks)

> _Note: this issue was identified against the code base at commit `46d4bc769d688157e8bc6d12ab890b12b1627210`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
ONE root cause, in the Secrets Manager <-> KMS envelope error-mapping step. It is reached by eleven checks across GetSecretValue, PutSecretValue and BatchGetSecretValue.

Related OPEN issues, named for context only; NEITHER carries any of the replay keys below, so neither covers this: 20261031T125106Z-kms-secretsmanager-a-kms-authorization-refusal-is-relayed.md (its Cause 1 asked for code AccessDeniedException AND the fixed message; the code is now right in this replay, the message template is still the relayed KMS text, which is what remains) and 20261102T091623Z-secretsmanager-getsecretvalue-putsecretvalue-never-check-the-caller-s.md (that one describes the calls not checking KMS permission at all; the emulator now does check and refuses, so what is left is the refusal's WORDING).

Cause 1 of 1 - every KMS authorization refusal taken on the caller's behalf is relayed to the client verbatim, including the KMS-SDK diagnostic envelope, instead of being replaced by Secrets Manager's own fixed message.
AWS: Secrets Manager calls KMS on the caller's behalf to wrap/unwrap a secret's version under the secret's KmsKeyId. When that KMS call is refused for AUTHORIZATION reasons - the identity policy does not allow the action, the key policy explicitly denies it, the grant was revoked, the allowed resource is a different key or the key's alias ARN rather than the key ARN, or a kms:EncryptionContext condition does not match the secret's ARN - Secrets Manager refuses with HTTP 400, Error.Code AccessDeniedException and the message exactly 'Access to KMS is not allowed'. That message is ENTIRELY FIXED TEXT: it has no variable part at all. In particular it does not contain the caller ARN, the KMS action, the key ARN, the policy-evaluation reason, '(Service: AWSKMS; Status Code: ...; Error Code: ...; Request ID: ...; Proxy: null)' or any KMS request id. The same substitution applies on the write path (kms:GenerateDataKey denied on PutSecretValue) and per entry on BatchGetSecretValue, whose Errors[] element carries SecretId=<the secret ARN from the request>, ErrorCode='AccessDeniedException' and Message='Access to KMS is not allowed' while the other requested secrets still return their plaintext in SecretValues[]. Smithy (com-amazonaws-secretsmanager-secretsmanager): GetSecretValue's modeled errors are DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException; PutSecretValue adds EncryptionFailure, LimitExceededException, ResourceExistsException; BatchGetSecretValue adds InvalidNextTokenException and returns Errors: APIErrorListType - AccessDeniedException is in none of those sets, i.e. it is the service-common denial, and the fixed wording is recorded behavior only (the model carries no authorization semantics).
Emulator: the refusal has the right code (AccessDeniedException, HTTP 400) but the wrong message: the raw KMS denial is passed through unchanged, of the form 'User: <caller-arn> is not authorized to perform: <kms-action> on resource: <key-arn> because no identity-based policy allows the <kms-action> action (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <request-id>; Proxy: null)' - and, when the refusal comes from an explicit Deny, '... with an explicit deny in an identity-based policy (Service: AWSKMS; ...)'. Only the fixed scaffolding of that string is the defect; the caller ARN, action, key ARN and request id inside it are per-run values filling the emulator's own template. BatchGetSecretValue puts the same relayed string into Errors[].Message.
Why: 'Access to KMS is not allowed' is what distinguishes 'the principal cannot use the secret's CMK' from a Secrets Manager-level denial, and clients match on it: break-glass and permission-boundary tooling, CI assertions, log scrapers and operator runbooks branch on that exact text. Against the emulator they see a KMS-shaped string instead, so they take the wrong branch. Worse, the relayed text leaks the internal call shape - the exact KMS action Secrets Manager used, the resolved key ARN, the policy-evaluation reason and a KMS request id - which AWS deliberately does not disclose through the Secrets Manager front door; anyone probing a secret they may read but whose key they may not now learns the key's identity.
Fix: the KMS error-mapping step of the Secrets Manager envelope path (the GetSecretValue, PutSecretValue, CreateSecret/UpdateSecret and BatchGetSecretValue handlers' shared relay). Classify the KMS refusal: an AccessDenied-class refusal must be replaced by AccessDeniedException with the fixed message 'Access to KMS is not allowed' and nothing from the wrapped KMS response; only the key-state / crypto-failure class may keep a relayed message, under DecryptionFailure / EncryptionFailure. BatchGetSecretValue must emit it as a per-entry Errors[] element rather than failing the batch.
Traces: the eleven checks in trace_ids; representative failures are ecsm-get-secret-value-as-role-without-kms-decrypt-denied (missing identity permission), ecsm-identity-deny-on-decrypt-overrides-key-policy-allow-denied (explicit deny), ecsm-put-secret-value-with-decrypt-only-denied (kms:GenerateDataKey on the write path) and ecsm-batch-get-secret-value-reports-the-kms-denied-secret-as-a-per-secret-error (per-entry form).

## Steps to Reproduce
1. kms:CreateKey (SYMMETRIC_DEFAULT, ENCRYPT_DECRYPT) with the DEFAULT key policy (account root delegated kms:*), so identity policies alone decide KMS use.
2. secretsmanager:CreateSecret(Name=<n>, SecretString=<v>, KmsKeyId=<key ARN>).
3. iam:CreateRole trusting the account root; iam:PutRolePolicy granting ONLY ['secretsmanager:GetSecretValue','secretsmanager:DescribeSecret'] on '*' and nothing on KMS. sts:AssumeRole it.
4. As that session, secretsmanager:GetSecretValue(SecretId=<secret ARN>). Observe HTTP 400 AccessDeniedException whose Message is the relayed KMS string 'User: <session-arn> is not authorized to perform: kms:Decrypt on resource: <key-arn> because no identity-based policy allows the kms:Decrypt action (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <rid>; Proxy: null)'. AWS returns HTTP 400 AccessDeniedException with the Message exactly 'Access to KMS is not allowed' and nothing else.
5. Explicit-deny variant: put an identity policy that Allows secretsmanager read and the key policy that Allows kms:Decrypt to the role, plus an identity statement {Effect: Deny, Action: 'kms:Decrypt', Resource: '*'}. GetSecretValue again - the emulator relays '... with an explicit deny in an identity-based policy (Service: AWSKMS; ...)'; AWS still answers exactly 'Access to KMS is not allowed'.
6. Write path: grant the role kms:Decrypt but NOT kms:GenerateDataKey, then secretsmanager:PutSecretValue(SecretId=<arn>, SecretString=<new>) - the emulator relays the kms:GenerateDataKey denial; AWS answers AccessDeniedException 'Access to KMS is not allowed'.
7. Batch path: create a second secret under aws/secretsmanager, then as the no-KMS role call secretsmanager:BatchGetSecretValue(SecretIdList=[<managed secret arn>, <cmk secret arn>]) - the managed secret must come back in SecretValues[] with its plaintext and the CMK secret as ONE Errors[] entry {SecretId: <cmk secret arn>, ErrorCode: 'AccessDeniedException', Message: 'Access to KMS is not allowed'}. The emulator puts the relayed KMS string in Message.
8. Scoping variants that must all produce the same fixed message: grant kms:Decrypt on a DIFFERENT key ARN; grant it on the key's ALIAS ARN instead of the key ARN; grant it with Condition StringEquals 'kms:EncryptionContext:SecretARN' = another secret's ARN. Each is refused AccessDeniedException 'Access to KMS is not allowed'.
