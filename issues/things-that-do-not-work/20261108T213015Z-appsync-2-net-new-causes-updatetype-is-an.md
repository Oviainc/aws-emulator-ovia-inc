# appsync: 2 net-new causes — UpdateType is an unimplemented 501 stub (so its malformed-SDL BadRequestException never happens), and an Event API's Api$dns publishes bare host:port records with no distinguishable real-time endpoint

> _Note: this issue was identified against the code base at commit `2233db37534078619f28c37e0e1db9dccbe7de65`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateType

## Description
Two independent net-new appsync defects, both grounded in behavioral checks that are neither stub-blocked-and-auto-filed nor owned by an open issue. Both are service=appsync and BOTH must be closed before this issue is submitted.

Cause 1 of 2: UpdateType answers 501 NotImplemented, so no UpdateType behavior — neither its refusals nor its success path — exists. Failing check: appsync.update-type-invalid-sdl-rejected.
AWS: Smithy: UpdateType = POST /v1/apis/{apiId}/types/{typeName}, http code 200, input apiId (httpLabel, required), typeName (ResourceName, httpLabel, required, @length 1..65536, @pattern ^[_A-Za-z][_0-9A-Za-z]*$), definition (String), format (TypeDefinitionFormat = SDL|JSON, required); output type (Type); modeled errors BadRequestException (client, httpError 400), ConcurrentModificationException (409), NotFoundException (404), UnauthorizedException (401), InternalFailureException (500). A definition that cannot be parsed for the declared format is refused 400 BadRequestException with the message "Unable to parse provided type definition." — that sentence is entirely fixed text with no variable parts (recorded behavior for the exact wording; the status and error class are modeled, and the identical wording is already established for CreateType in open issue 20261108T071728Z-appsync-type-operations-diverge-deleted-types-stay-readable.md, Cause 4). The refusal has no effect: a subsequent GetType still returns the type's prior, valid definition. A well-formed UpdateType on the same typeName is accepted 200 and persisted, so the next GetType returns the new definition.
Emulator: the call is refused with error code 'NotImplemented' ("operation UpdateType is scaffolded but not implemented in this emulator") instead of BadRequestException — the check asserted BadRequestException and got 'NotImplemented'. The handler is a scaffold whose handle() returns scaffolded::not_implemented("UpdateType"), so every UpdateType request — valid or malformed — gets the same 501, and the operation's positive control (a valid update persisting) is unreachable too. No existing open issue covers this operation: the suite's auto-filed stub issues name StartSchemaCreation, ListTypes, DeleteType, ListTypesByAssociation, ListResolvers, StartDataSourceIntrospection, EvaluateCode, EvaluateMappingTemplate and GetSchemaCreationStatus, and open 20261108T071728Z (type operations) covers CreateType/GetType/DeleteType only.
Why: a client that updates a GraphQL type — schema-management tooling, CDK/CFN-adjacent type editors, any migration that evolves a type definition — cannot update a type at all, and a client that tests its own error handling sees an unmodelled 501 'NotImplemented' where AWS returns a modeled 400 BadRequestException. Because the 501 is returned before any validation, a malformed definition is indistinguishable from a well-formed one, and nothing proves the rejected update left prior state untouched.
Fix: the UpdateType operation handler (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/update_type.rs) — implement the operation: resolve the API and typeName (404 NotFoundException when either is unknown), parse definition for the declared format and on any parse failure refuse 400 BadRequestException with the fixed message "Unable to parse provided type definition." leaving the stored type unchanged, otherwise replace the stored definition and return the Type projection; then delete the SCAFFOLDED marker line in that file.
Traces: appsync.update-type-invalid-sdl-rejected.

Cause 2 of 2: CreateApi returns an Api whose dns map holds bare host:port strings, so the API publishes no identifiable real-time endpoint. Failing check: appsync.e2e-event-api-publish-subscribe-flow.
AWS: Smithy: CreateApi = POST /v2/apis, output api (Api); Api$dns is a MapOfStringToString documented as "The DNS records for the API. This will include an HTTP and a real-time endpoint." The two records are DNS host names of distinct kinds: the HTTP record is the API's HTTP endpoint host (AWS form <apiId>.appsync-api.<region>.amazonaws.com, carrying the api label) and the REALTIME record is the API's real-time/WebSocket endpoint host (AWS form <apiId>.appsync-realtime-api.<region>.amazonaws.com, carrying the realtime label); clients publish to https://<HTTP record>/event and subscribe over wss://<REALTIME record>/event/realtime. The requirement is the KIND of value: each record is a DNS host name whose real-time entry is identifiable as the real-time endpoint and is not the same host as the HTTP entry — the concrete api id, region and account in those names are per-run values, not part of the template.
Emulator: the created Event API's api.dns is {'REALTIME': '127.0.0.1:40315', 'HTTP': '127.0.0.1:39025'} — bare address:port literals with no DNS host name and no realtime label, so the two records are indistinguishable by kind and cannot be classified: the check failed with AssertionError "could not identify HTTP/realtime endpoints from dns={'REALTIME': '127.0.0.1:40315', 'HTTP': '127.0.0.1:39025'}". (The harness rewrites an announced AWS-shaped host to the emulator's actual listener via ctx.endpoint_route, so announcing a raw loopback address:port is not needed for reachability.)
Why: any client that derives its endpoints from the create response — the AppSync Events JS/amplify clients, which select the real-time endpoint by its host form, and any code that builds wss://<realtime>/event/realtime — cannot tell which record to dial, so publish/subscribe over an Event API cannot be wired up from the API's own response. It also means everything downstream of endpoint discovery in this flow (API-key-authenticated WebSocket connect/ack, subscribe on <namespace>/room1, POST /event publish returning successful/failed, and delivery of the event to the independent subscriber) is still completely unverified by this run.
Fix: the CreateApi/GetApi/UpdateApi Api response projection and the Event API endpoint naming in appsync state — mint and store two distinct DNS host names per Api (an HTTP endpoint host and a real-time endpoint host carrying the realtime label, in AWS's <apiId>.appsync-api.<region>.amazonaws.com / <apiId>.appsync-realtime-api.<region>.amazonaws.com form) and publish those as Api$dns['HTTP'] and Api$dns['REALTIME'], leaving address:port routing to the endpoint layer rather than the response body.
Traces: appsync.e2e-event-api-publish-subscribe-flow.
