# config: the configuration recorder never records resources from other services, so no configuration item is ever produced (6 checks hang to the 60 s cap), and the ResourceNotDiscoveredException message is emulator-authored (2 causes)

> _Note: this issue was identified against the code base at commit `5ed22e125380c04fb8121d8e25f405dce5415572`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartConfigurationRecorder

## Description
TWO CAUSES. The checks' service tokens are the composite suite tokens `config__sqs` and `config__lambda__sqs`; the services involved (configservice, lambda, sqs) are all bootstrapped, and the defect belongs to configservice.

Cause 1 of 2: a RUNNING customer-managed configuration recorder never discovers or records a resource that lives in another service, so no configuration item is ever produced for an AWS::SQS::Queue and every path that reads recorded inventory is permanently empty.

AWS: with a customer-managed recorder whose recordingGroup has allSupported=true and a delivery channel in place, Config asynchronously discovers supported resources and writes a configuration item per state. Smithy (configservice): RecordingGroup.allSupported — "Specifies whether Config records configuration changes for all supported resource types" and "when Config adds support for a new resource type, Config starts recording resources of that type automatically"; ConfigurationItem carries configurationItemCaptureTime, configurationItemStatus (enum OK | ResourceDiscovered | ResourceNotRecorded | ResourceDeleted | ResourceDeletedNotRecorded), arn, resourceType, resourceId, resourceName, awsRegion and configuration ("A JSON-encoded string that contains the contents for the resource configuration"). The first item for a newly created queue is the DISCOVERY item (configurationItemStatus = ResourceDiscovered). Recorded behavior (the checks' own inline AWS measurements, us-west-2, 2026-09-13): a fresh recorder with allSupported=true produced a created queue's first configuration item in 60 s / 76 s / 136 s on three runs; GetResourceConfigHistory then returns it, BatchGetResourceConfig returns it in baseConfigurationItems, SelectResourceConfig returns one row for it, and a CUSTOM_LAMBDA rule whose SourceDetails is [{EventSource: aws.config, MessageType: ConfigurationItemChangeNotification}] is PUSH-invoked by Config ~20 s after PutConfigRule with that item in invokingEvent.configurationItem (no StartConfigRulesEvaluation involved).

Emulator: nothing is ever recorded. PutConfigurationRecorder / PutDeliveryChannel / StartConfigurationRecorder all succeed and DescribeConfigurationRecorderStatus reports recording, but Config's inventory only ever grows from an explicit client write: the store's `discovered_resources` map has exactly ONE growth point, `record_discovered_resource`, whose own doc says each entry is bounded by "what `PutResourceConfig` records" — there is no path by which a queue created through the SQS service enters it. GetResourceConfigHistory consequently answers ResourceNotDiscoveredException forever for a queue that was just created under a running recorder, BatchGetResourceConfig returns an empty baseConfigurationItems, SelectResourceConfig returns zero rows, and the change-triggered rule is never push-invoked. All six checks block in their first wait for a configuration item (helpers `_await_history_items`, budget 300–1200 s inside the check) and are killed by the harness at 60 s; the report shows them only as "Check timed out after 60.0s". This is NOT the already-filed notification gap: open issue 20261022T190340Z-config-sns-sqs-config-publishes-no-configurationitemchangenotification-to-the-delivery-channel.md covers publishing ConfigurationItemChangeNotification to the channel's SNS topic and explicitly says it "Depends on the recorder actually producing configuration items" — this issue is that dependency. Open issue 20261025T014224Z-cloudformation-config-s3-snapshot-delivery-never-reaches-a.md (snapshot delivery lastStatus) and 20261025T133755Z-config-aggregate-compliance-summary-still-never-converges-deleteevaluationresults.md (aggregate compliance / remediation) are different surfaces and carry none of these checks' replay keys.

Why: a client cannot use Config for what Config exists for. Resource inventory reads (GetResourceConfigHistory, BatchGetResourceConfig, SelectResourceConfig, the aggregate reads) are indistinguishable from "the account has nothing", so a compliance dashboard or inventory query reads empty forever while reporting recording=true and lastStatus=Success; and because no configuration item exists, no change-triggered (ConfigurationItemChangeNotification) Config rule can ever be evaluated, so a CUSTOM_LAMBDA guardrail that would mark a resource NON_COMPLIANT silently never runs and the account looks green. Every negative Config assertion also becomes vacuous: ResourceNotDiscoveredException is the answer to every query, so a stub cannot be told apart from a working recorder.

Fix: the configuration-recorder recording loop in configservice — while a customer-managed recorder is recording and its recordingGroup covers a type, resources created/changed/deleted in the other emulated services must be captured into the recorder's inventory (`discovered_resources` via `record_discovered_resource`, today reachable only from PutResourceConfig) as configuration items with configurationItemStatus ResourceDiscovered on first capture and OK on subsequent states, from which the existing read paths and the change-triggered rule evaluation already project.

Traces: config__sqs.config-batch-get-resource-config-returns-only-the-recorded-key-of-a-mixed-batch, config__sqs.config-history-rejects-unrecorded-queue-while-batch-get-omits-it, config__sqs.config-select-resource-config-returns-the-recorded-queue-row, config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted, config__lambda__sqs.change-triggered-custom-rule-is-push-invoked-with-a-real-configuration-item, config__lambda__sqs.change-triggered-rule-creation-is-denied-when-config-cannot-invoke-the-evaluator. Note on confirming the fix: the two config__lambda__sqs checks additionally require Config to push-invoke a CUSTOM_LAMBDA evaluator and to refuse PutConfigRule with InsufficientPermissionsException when the evaluator is not invokable — neither was reached, so this issue claims nothing about those; they are expected to become observable once a configuration item exists. config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted will still not fit the 60 s harness cap after the fix: by design it watches an absence window of at least 180 s, so confirm Cause 1 on the other five.

Cause 2 of 2: GetResourceConfigHistory's ResourceNotDiscoveredException carries an emulator-authored message instead of Config's not-discovered template.

AWS: the refusal for a well-formed resource key the recorder never discovered is ResourceNotDiscoveredException (Smithy: client error, HTTP 400, doc "You have specified a resource that is either unknown or has not been discovered") whose message is Config's fixed template "Resource " + <resourceId> + " of resourceType:" + <resourceType> + " is unknown or has not been discovered" — the fixed text is everything but the two variable parts, and both variable parts are the resourceId and resourceType taken verbatim from the request (recorded behavior: config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted asserts exactly that string, built from the request's own resourceId and resourceType).

Emulator: the same refusal is produced with the message "Resource of type " + <resourceType> + " with id " + <resourceId> + " has not been discovered" — different fixed text, different member order, and it drops the "is unknown or" clause (services/service-com-amazonaws-configservice-starlingdoveservice/src/ops/get_resource_config_history.rs:294-307). The HTTP status (400) and the error code (ResourceNotDiscoveredException) are correct; only the message diverges.

Why: clients and test suites that match Config's not-discovered message — the only text that tells a human which resource and which type were unknown, in the order Config words it — mis-parse or fail to match it, and a user reading the emulator's error sees wording no AWS runbook or log search contains.

Fix: the ResourceNotDiscoveredException construction in the GetResourceConfigHistory handler's validation (and any sibling read path that raises it) must use Config's template with the request's resourceId and resourceType substituted.

Traces: config__sqs.config-stopped-recorder-records-no-configuration-item-until-restarted (asserts the exact message), config__sqs.config-history-rejects-unrecorded-queue-while-batch-get-omits-it (asserts the code on the same path). Both were killed at the 60 s cap by Cause 1 before reaching the assertion, so this cause is established from the handler source plus the check's AWS-measured expected message rather than from an observed assertion failure; it will surface as a plain mismatch once Cause 1 is fixed.
