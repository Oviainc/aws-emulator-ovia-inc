=== Cause 1 of 1: a PRIVATE REST API reached through its execute-api interface VPC endpoint can never be exercised — the check hangs to the harness cap because the created interface endpoint is reported `pending` forever, and the aws:SourceVpce resource-policy allow/deny/restore behavior behind that gate is never reached ===

AWS: the gating call is ec2 DescribeVpcEndpoints ("Describes your VPC endpoints"), whose VpcEndpoint.State member targets the EC2 `State` enum (PendingAcceptance | Pending | Available | Deleting | Deleted | Rejected | Failed | Expired | Partial) and is NON-TERMINAL on create: an interface endpoint to an AWS-provided service (here com.amazonaws.<region>.execute-api) is answered pending and reaches available with NO further caller action, which is why DescribeVpcEndpoints is the documented way to observe it. Behind that gate, Smithy (com.amazonaws.apigateway#BackplaneControlService): GetVpcLink is GET /vpclinks/{vpcLinkId}, 200 -> VpcLink{id,name,targetArns,status,statusMessage,tags} with status targeting enum VpcLinkStatus = [AVAILABLE, PENDING, DELETING, FAILED] — i.e. a created link's state machine terminates at AVAILABLE; UpdateRestApi is PATCH /restapis/{restApiId} with patchOperations, 200 -> RestApi carrying the `policy` member (modeled errors BadRequestException 400, ConflictException 409, NotFoundException 404, LimitExceededException 429, TooManyRequestsException 429, UnauthorizedException 401), so a `replace` of /policy with an execute-api:Invoke statement conditioned on StringEquals aws:SourceVpce is the documented way to pin a PRIVATE API to one endpoint. Recorded behavior for the data plane (the model says nothing about data-plane invoke responses): a GET to the stage URL arriving through the endpoint named in the policy returns 200 with the integration's own body; after the policy is re-pinned to a DIFFERENT vpce id and redeployed, the same GET returns HTTP 403 with a JSON body whose `Message` contains the fixed text "is not authorized to perform: execute-api:Invoke" and MUST NOT contain the integration's body; re-pinning the original endpoint id and redeploying returns 200 with that body again. Hypothesis (beyond the substring the check asserts): AWS words the full message "User: <principal> is not authorized to perform: execute-api:Invoke on resource: <method ARN>", where the fixed text is "User: ", " is not authorized to perform: execute-api:Invoke on resource: " and the variable parts are the caller's principal (`anonymous` for an unsigned request) and the method ARN built from the request's Region, account, rest-api id, stage, HTTP method and resource path.

Emulator: no terminal answer at all — the check is killed by the runner at its cap ("Error: Check timed out after 60.0s") with no response recorded for any operation under test. The blocking step is the first unbounded wait the check reaches, its poll of ec2 DescribeVpcEndpoints(VpcEndpointIds=[E]) for State in (available, failed) with a 600 s budget. The cause is visible in the checkout at the replayed commit: services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs stores the endpoint with `state: Some(state::VPC_ENDPOINT_STATE_PENDING.to_string())` and records the owed move with `store.vpc_endpoint_moves.insert(endpoint_id.clone(), state::PendingStateMove::starting_now(state::VPC_ENDPOINT_STATE_AVAILABLE))`, but in services/service-com-amazonaws-ec2-amazonec2/src/state.rs the field `pub vpc_endpoint_moves: BTreeMap<String, PendingStateMove>` has exactly TWO mentions in the whole file — its declaration (line ~3135) and its empty initialisation (line ~3591). `materialize_due_transitions`, which describe_vpc_endpoints.rs calls before reading, never consumes it, so the owed Pending -> Available transition is never applied however long a client waits. No status code or error code diverges here: the divergence is a response VALUE that never changes. Everything the check asserts after that gate — VpcLink status reaching AVAILABLE, the 200-with-nonce in-VPC invoke, the 403 "not authorized to perform: execute-api:Invoke" for a non-matching aws:SourceVpce, and the restored 200 — is therefore entirely unexercised, so its fidelity is unknown rather than confirmed.

Why: a client gets neither a converged resource nor a modeled refusal — it blocks. Every waiter in front of the PRIVATE API surface (botocore's own vpc_endpoint waiters, CloudFormation/CDK/Terraform readiness polls, hand-rolled loops) spins to its own timeout, so no private REST API can be stood up against the emulator at all. Worse for correctness work: because the gate never opens, the emulator's resource-policy evaluation is never consulted, so a PRIVATE API that admits a caller whose aws:SourceVpce does NOT match (serving the integration body where AWS returns 403) would pass silently — an authorization regression hidden behind a hang.

Fix: the EC2 VPC-endpoint state machine, not anything in the apigateway crate — `materialize_due_transitions` must apply the moves held in `vpc_endpoint_moves` using the same retain-and-apply shape the VPC, subnet and carrier-gateway moves beside it use (and that `vpc_endpoint_connection_moves` already gets), so an endpoint created by the create handler is reported available by the describe handler once the transition delay has passed, whether or not anyone called in between, and so the `vpc-endpoint-state` filter and the delete path see that same materialized value. Once the gate opens, the behavior behind it must then hold in the apigateway crate: the VpcLink state machine must advance PENDING -> AVAILABLE in its create/get handlers, and the REST API resource-policy evaluation on the execute-api data plane must evaluate the StringEquals aws:SourceVpce condition against the endpoint the request actually arrived through — allowing with the integration's body on a match and refusing 403 with the execute-api:Invoke authorization message (and never the integration body) on a mismatch, re-evaluated after each redeploy.

Traces: apigateway.deep-apigateway-3-apigw-private-vpce-invoke-policy-gated. File and line citations: services/service-com-amazonaws-ec2-amazonec2/src/ops/create_vpc_endpoint.rs (lines ~777 and ~831), services/service-com-amazonaws-ec2-amazonec2/src/state.rs (lines ~3135 and ~3591).
