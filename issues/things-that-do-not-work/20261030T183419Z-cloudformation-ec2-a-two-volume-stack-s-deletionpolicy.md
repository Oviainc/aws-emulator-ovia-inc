# cloudformation__ec2: a two-volume stack's DeletionPolicy=Snapshot sibling is deleted with no snapshot, so the Snapshot-vs-Retain check never settles (1 cause)

> _Note: this issue was identified against the code base at commit `6c1a210febfdea66ca602e6cad55ded855ffc229`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Cause 1 of 1: CloudFormation's AWS::EC2::Volume teardown ignores `DeletionPolicy: Snapshot` (the volume is deleted with no EBS snapshot taken), so a stack that declares a `Snapshot` volume beside a `Retain` sibling never produces the one snapshot that distinguishes the two policies; the check exhausts its wait for it and the harness kills the check at its 60 s budget. Failing check: cloudformation__ec2.deploy-ec2-1-volume-deletion-policy-snapshot-vs-retain.

AWS: `DeletionPolicy: Snapshot` is documented "For resources that support snapshots, CloudFormation creates a snapshot for the resource before deleting it", and `Retain` "CloudFormation keeps the resource without deleting the resource or its contents when its stack is deleted". AWS::EC2::Volume supports snapshots, and the snapshot CloudFormation takes for it is a standalone ec2:CreateSnapshot against the volume — Smithy (services/service-com-amazonaws-ec2-amazonec2/smithy-model/com-amazonaws-ec2-amazonec2.json): CreateSnapshot input {VolumeId (required), Description, TagSpecifications, OutpostArn, Location, DryRun}, output shape `Snapshot` {SnapshotId, VolumeId, VolumeSize, State (SnapshotState, reaching `completed`), Progress, StartTime, OwnerId, …}, `errors: []`; DeleteVolume models only VolumeId, so the snapshot is not a member of the delete. Recorded behavior for the two policies in one stack: DeleteStack reports ( SnapVol, DELETE_COMPLETE ) and ( KeepVol, DELETE_SKIPPED ) and never ( KeepVol, DELETE_COMPLETE ); the Snapshot volume answers DescribeVolumes with `InvalidVolume.NotFound` and leaves exactly one snapshot of itself that reaches State `completed` with VolumeSize equal to the volume's size; the Retain volume is still present, still `available`, still carrying its template tags; and no snapshot of the Retain volume exists.

Emulator: the first three contract halves hold — the stack reaches CREATE_COMPLETE, both volumes are `available` at the requested size and zone, and the delete trail carries ( SnapVol, DELETE_COMPLETE ) and ( KeepVol, DELETE_SKIPPED ) without ( KeepVol, DELETE_COMPLETE ) — and the check only stops once it reaches the step that waits for the Snapshot policy's snapshot, where DescribeSnapshots(OwnerIds=["self"], Filters=[{Name:"volume-id",Values:[<SnapVol id>]}]) never stops returning an EMPTY list; the check's 600 s poll for it outlives the suite's 60 s per-check budget and the replay records `Check timed out after 60.0s`. The directly observed form of the same cause is the sibling check cloudformation.deep-cloudformation-2-snapshot-volume, which asserts rather than times out: `DeletionPolicy:Snapshot must leave exactly one snapshot of vol-…; got []`. The code is the shared CloudFormation teardown: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs computes `final_snapshot` for a `Snapshot` policy and hands it to `Provisioner::delete`, but services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs routes `Self::Ec2Volume => delete_ec2_volume(ctx, region, physical_resource_id)` and drops it; that file's own doc comment says a type "whose snapshot is a call of its own is not one of these arms yet, so it is deleted with no snapshot taken".

Why: a client that uses `DeletionPolicy: Snapshot` to keep a backup of an EBS volume while tearing down its stack loses the data silently — CloudFormation reports the resource DELETE_COMPLETE and the volume is gone, but the snapshot it promised does not exist, and the response is indistinguishable from the default `Delete` policy. Any code that waits for the snapshot to reach `completed`, or restores a volume from it, hangs or fails against the emulator where it succeeds against AWS; here that hang is also what consumes the whole check budget, hiding the rest of this scenario's assertions behind a timeout.

Fix: the owning component is CloudFormation's per-type delete arm — `Provisioner::delete`'s `Self::Ec2Volume` branch in services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs must honour its `final_snapshot` argument by calling the owning service's ec2:CreateSnapshot for the volume before DeleteVolume and holding the teardown open until that snapshot is recorded (so it reaches `completed` and outlives the volume), while leaving the `Retain` sibling untouched as it already does. That requires EC2's CreateSnapshot handler (services/service-com-amazonaws-ec2-amazonec2/src/ops/create_snapshot.rs, still carrying `//! SCAFFOLDED, NOT IMPLEMENTED:`) to write the snapshot into the same EC2 snapshot state the implemented DescribeSnapshots reads.

Traces: cloudformation__ec2.deploy-ec2-1-volume-deletion-policy-snapshot-vs-retain (verdict mismatch, recorded as `Check timed out after 60.0s`); the same cause observed as a direct assertion in cloudformation.deep-cloudformation-2-snapshot-volume. Code citations: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs lines 1389-1393 and 1559-1564; services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs lines 1614-1622 and line 1652; services/service-com-amazonaws-ec2-amazonec2/src/ops/create_snapshot.rs line 4.

## Evidence
Expected (AWS): for a stack declaring two 1 GiB gp3 AWS::EC2::Volume resources in one zone — `SnapVol` with DeletionPolicy=Snapshot and `KeepVol` with DeletionPolicy=Retain — after cloudformation:DeleteStack reaches DELETE_COMPLETE:
  * describe_stack_events carries (SnapVol, DELETE_COMPLETE) and (KeepVol, DELETE_SKIPPED), and NOT (KeepVol, DELETE_COMPLETE);
  * ec2:DescribeSnapshots(OwnerIds=["self"], Filters=[{Name:"volume-id",Values:[<SnapVol id>]}]) -> HTTP 200 with exactly one entry whose (VolumeId, State, VolumeSize) is (<SnapVol id>, "completed", 1);
  * ec2:DescribeVolumes(VolumeIds=[<SnapVol id>]) -> HTTP 400 InvalidVolume.NotFound;
  * ec2:DescribeVolumes(VolumeIds=[<KeepVol id>]) -> HTTP 200, State "available", tags as declared;
  * the same filtered DescribeSnapshots for <KeepVol id> -> empty list.

Actual (emulator): the event-trail and both volumes' pre-delete state match, and the Retain/Snapshot event distinction is reported correctly, but the snapshot of <SnapVol id> never appears: DescribeSnapshots filtered on that volume id keeps answering HTTP 200 with an empty Snapshots list, so the check's 600 s wait for `len(snaps) == 1 and snaps[0]["State"] == "completed"` never satisfies and the suite records `Error: Check timed out after 60.0s` (60 s is the harness budget, not an AWS value). The same divergence in its asserting form, from the sibling check on the same code path: `AssertionError: DeletionPolicy:Snapshot must leave exactly one snapshot of vol-00000000000000024; got []` — the `vol-…` id is that run's value; the requirement is one snapshot per Snapshot-policy volume, with VolumeId = that volume and VolumeSize = its size. There is no diverging HTTP status, error code or message: the delete is accepted and reported complete, and the backup is simply missing.

Supporting source: services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs:1652 sends the AWS::EC2::Volume teardown to `delete_ec2_volume(ctx, region, physical_resource_id)`, discarding `final_snapshot: Option<&str>` (computed at provisioning.rs:1559 for `deletion_policy::SNAPSHOT`); provisioner.rs:1614-1622 documents that only types whose owning service takes a final snapshot as a member of its delete call (RDS `FinalDBSnapshotIdentifier`, Redshift `FinalClusterSnapshotIdentifier`) receive it, and that other types are "deleted with no snapshot taken". ec2:CreateSnapshot is modelled with `errors: []` and output shape `Snapshot`, and its handler create_snapshot.rs:4 is still `//! SCAFFOLDED, NOT IMPLEMENTED:`.

## Steps to Reproduce
1. Boot the emulator. ec2:DescribeAvailabilityZones(Filters=[{Name:"state",Values:["available"]}]) and take the first zone as parameter `Az`.
2. cloudformation:CreateStack with a template declaring Parameters {Az} and two resources, each Type AWS::EC2::Volume with Properties {AvailabilityZone: {Ref: Az}, Size: 1, VolumeType: "gp3", Tags: [...]}: `SnapVol` with "DeletionPolicy": "Snapshot" and `KeepVol` with "DeletionPolicy": "Retain"; Outputs SnapVolId/KeepVolId as {Ref} of each. Poll DescribeStacks by StackId to CREATE_COMPLETE and read both volume ids from Outputs.
3. ec2:DescribeVolumes(VolumeIds=[both]) — each is (available, 1, <zone>). ec2:DescribeSnapshots(OwnerIds=["self"], Filters=[{Name:"volume-id",Values:[<id>]}]) is empty for both (correct baseline).
4. cloudformation:DeleteStack, poll to DELETE_COMPLETE, then describe_stack_events: (SnapVol, DELETE_COMPLETE) and (KeepVol, DELETE_SKIPPED) are present and (KeepVol, DELETE_COMPLETE) is absent (all correct today).
5. Poll ec2:DescribeSnapshots(OwnerIds=["self"], Filters=[{Name:"volume-id",Values:[<SnapVol id>]}]). Expected (AWS): exactly one snapshot reaching State "completed" with VolumeId = <SnapVol id> and VolumeSize 1. Actual: an empty list forever — the poll never settles, which is what exhausts the check's time budget.
6. ec2:DescribeVolumes(VolumeIds=[<KeepVol id>]) still reports it "available" with its tags, and no snapshot of it exists (both correct) — so the only divergence is the missing Snapshot-policy snapshot.
7. Re-replay check cloudformation__ec2.deploy-ec2-1-volume-deletion-policy-snapshot-vs-retain (and, for the directly-asserting form of the same cause, cloudformation.deep-cloudformation-2-snapshot-volume) to confirm the fix.
