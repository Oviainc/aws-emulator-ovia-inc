# events__s3__sqs: S3 notification payloads copy the QUOTED ETag into detail.object.etag, and a successful PutObjectAcl carries no x-amz-request-id (so no event can name the request) (2 causes)

> _Note: this issue was identified against the code base at commit `69ed905f5c9274a78049f2399e34029eda6e3b1b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutObjectAcl

## Description
Two net-new root causes, both in S3's event-notification plane. S3 now DOES publish on both notification paths (the previously filed blockers 20261025T002357Z-events-s3-sqs-s3-produces-no-aws-s3-events-on-either.md and 20261025T171339Z-events-s3-sqs-a-rejected-putobjectacl-s-emits.md describe the earlier silence; the barriers in these checks prove delivery now happens), so what these checks now expose is the CONTENT of what is published and of the ACL response. Neither cause is covered by an open issue; the closest ones are named above and 20261028T004439Z-events-s3-sqs-s3-tagging-notifications-are-never-published-so-the.md.

Cause 1 of 2: the EventBridge 'Object Created' detail reports object.etag with the surrounding double quotes of the HTTP ETag header.
AWS: recorded behavior only for the event payload (the event is not in the Smithy model) — an aws.s3 event's detail.object.etag is the BARE entity tag, e.g. "etag": "b1946ac92492d2347c6235b4d2611184" (https://docs.aws.amazon.com/AmazonS3/latest/userguide/EventBridge.html), and the classic Records envelope's s3.object.eTag is likewise unquoted. The quoting belongs to the HTTP header only: Smithy: PutObject output member ETag is bound to the `ETag` HTTP header (httpHeader: "ETag"), which is why PutObject's response value is '"<hex>"'. Fixed text: none — the value is entirely derived from the object (its entity tag); the only requirement is that the notification carries the bare tag, not the header's quoted form.
Emulator: the event detail carries the quoted header value verbatim. The check compares detail.object.etag to PutObject's ETag with the quotes stripped and reports: AssertionError: expected detail.object.etag to be the ETag PutObject returned ('dfe6b404cdf63b0f6c0d46fa69705878'), got '"dfe6b404cdf63b0f6c0d46fa69705878"'. The same stored value is rendered into the classic record's s3.object.eTag, so that path has the same defect.
Why: a consumer that correlates an event to an object by ETag (or computes it from the body) never matches, and an EventBridge rule pattern on detail.object.etag never fires; the mismatch is silent because the event itself is delivered.
Fix: S3's notification emitter — the EventBridge detail builder and the Records-envelope builder, or the stored ObjectEvent.etag, which should hold the bare entity tag with quoting applied only when the ETag response header is serialized.
Traces: events__s3__sqs.object-restore-initiated-and-tags-added-carry-their-own-detail-types; emitter code at services/service-com-amazonaws-s3-amazons3/src/state/notifications.rs:583-593 (event_bridge_detail) and :545-547 (records_envelope).

Cause 2 of 2: a SUCCESSFUL PutObjectAcl answers 200 with no x-amz-request-id, and the notifications it produces name no request id either.
AWS: every S3 response — success or failure — carries the x-amz-request-id (and x-amz-id-2) response header; botocore surfaces it as ResponseMetadata.RequestId. Smithy: PutObjectAclOutput models only RequestCharged (httpHeader x-amz-request-charged) with http {method: PUT, uri: /{Bucket}/{Key+}?acl, code: 200} and error NoSuchKey/404, i.e. the response has no body and the request id is purely the protocol header, so it must be emitted by the serializer. Recorded behavior for the notification side: the classic record carries responseElements with "x-amz-request-id" and "x-amz-id-2", and the aws.s3 EventBridge detail carries "request-id" — in both cases the id of the request that made the change, so a client can tie an event to its own call.
Emulator: the 200 response omits the header entirely, so ResponseMetadata has no RequestId and both checks die on KeyError: 'RequestId' at `s3.put_object_acl(...)["ResponseMetadata"]["RequestId"]`. The ERROR path of the same operation does return one (the same checks read e.response["ResponseMetadata"]["RequestId"] successfully for the AccessControlListNotSupported refusal), so this is the success path only. Consistently, the emitter deliberately omits the request id from what it publishes (notifications.rs:575-582 states a request id "belong[s] to the request that made the change, which no part of this emulator records, so they are omitted"), and the Records envelope it builds has no responseElements/userIdentity/requestParameters at all — so even with the header fixed, both checks' closing assertions (every ACL event must name the successful request id) cannot hold.
Why: a client cannot report or log the request id of a successful S3 call (SDK retry/trace tooling and support workflows all read ResponseMetadata.RequestId), and nothing can correlate a delivered ObjectAcl:Put / 'Object ACL Updated' event with the call that caused it.
Fix: S3's response serializer / the common response-header layer for PutObjectAcl's success path (emit x-amz-request-id and x-amz-id-2 as on the error path), plus S3's notification emitter and the ObjectEvent it records, which must carry the originating request id so responseElements["x-amz-request-id"] and detail["request-id"] can be filled.
Traces: events__s3__sqs.obs-s3-3-acl-rejected-under-bucket-owner-enforced-emits-no-event (line 305), events__s3__sqs.obs-s3-3-object-acl-put-reaches-both-paths (line 253); emitter code at services/service-com-amazonaws-s3-amazons3/src/state/notifications.rs:532-608.
