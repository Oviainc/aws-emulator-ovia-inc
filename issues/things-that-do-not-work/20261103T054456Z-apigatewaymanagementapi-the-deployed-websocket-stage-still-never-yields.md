# ApiGatewayManagementApi: the deployed WEBSOCKET stage still never yields a 101 upgrade (4 checks), and an undeployed-stage @connections endpoint answers 410 GoneException instead of 403 ForbiddenException 'Forbidden' (2 causes)

## Operation
PostToConnection

## Description
TWO net-new root causes on the apigatewaymanagementapi service token, from checks the replay reports as neither ALREADY FILED nor OWNED. They are numbered below and each carries its own failing check ids; BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: a client RFC 6455 opening handshake against a deployed apigatewayv2 WEBSOCKET stage never reaches '101 Switching Protocols', so four @connections checks reach no verdict at all ===
AWS: the opening handshake is the execute-api data plane and is not a modelled operation, so this is recorded behavior only. Recorded: a GET on the deployed stage path carrying Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key and Sec-WebSocket-Version: 13 is answered HTTP/1.1 101 Switching Protocols with a Sec-WebSocket-Accept derived from the client key; $connect runs, the service mints the connection id, and that id is what the modelled @connections surface then addresses (Smithy ApiGatewayManagementApi, restJson1/sigv4: GetConnection GET /@connections/{ConnectionId} -> GetConnectionResponse{ConnectedAt/LastActiveAt __timestampIso8601 date-time, Identity{SourceIp,UserAgent}}; PostToConnection POST /@connections/{ConnectionId} with Data @httpPayload blob @length 0..131072, error PayloadTooLargeException @httpError 413; DeleteConnection DELETE /@connections/{ConnectionId} code 204; service common errors ForbiddenException @httpError 403 and GoneException @httpError 410, both memberless).
Emulator: every poll for a status line containing ' 101 ' fails for the whole budget. All four checks complete their control-plane setup (sts, iam role, lambda create + Active, create_api/create_integration/create_route/create_deployment/create_stage) and then block in their _poll_until helper on the upgrade, which raises `TimeoutError: a 101 WebSocket upgrade against stage dev for the <...> socket: the run budget ended first; not graded` (reported for the user-agent control socket, the byte-boundary socket, the minting-stage socket and the live socket respectively). No 101, no Sec-WebSocket-Accept, no socket, therefore no connection id.
Why: with no connection id minted, the entire server-push surface is unobservable against this emulator: GetConnection's Identity members and response envelope, PostToConnection's byte-exact 131072 ceiling on a LIVE connection and its behaviour against a socket whose peer never reads, resolution of one connection id across sibling deployed stages of the same API, and the ordering of the execute-api:ManageConnections authorization denial ahead of the connection lookup. A developer pointing a WebSocket client at the stage cannot distinguish a missing data plane from a misconfigured stage, and server-push application code cannot be exercised at all.
Fix: the execute-api data-plane front door / request router plus the apigatewayv2 WebSocket session layer — recognise an upgrade request on a deployed WEBSOCKET-protocol API's stage path, complete the handshake (101 + Sec-WebSocket-Accept) instead of falling through to the generic not-found path, mint a connection id, dispatch $connect/$disconnect/route selection, and register the connection in the store the @connections handlers read. This is a capability gap, not an error-shape bug.

=== Cause 2 of 2: the @connections endpoint's STAGE segment is ignored — a stage that is not deployed for that API reaches the connection store and all three operations answer 410 GoneException with an empty message instead of 403 ForbiddenException with the message 'Forbidden' ===
AWS: stage routing is the execute-api data plane and is not a modelled operation, so the refusal itself is recorded behavior; the modelled surface carries the error AWS uses — Smithy ForbiddenException, errorKind client, @httpError 403, NO members, doc 'The caller is not authorized to invoke this operation.' Recorded: when the management endpoint's path segment names a stage that is not a deployed stage of that API, GetConnection, PostToConnection and DeleteConnection are each answered HTTP 403 with error code ForbiddenException and the message 'Forbidden' — 'Forbidden' is fixed text with no variable parts — and the connection store is never consulted; the identical request against the SAME API's deployed stage still answers 410 GoneException (memberless, empty message) for a well-formed unknown id.
Emulator: all three operations on the undeployed-stage endpoint answer error code GoneException with an empty message. Replay detail: `AssertionError: the undeployed-stage endpoint returned {'GetConnection': ('GoneException', ''), 'PostToConnection': ('GoneException', ''), 'DeleteConnection': ('GoneException', '')}; real AWS returns ForbiddenException (HTTP 403 'Forbidden') for all three operations. A GoneException means the stage segment was ignored and the request reached the connection store anyway.`
Why: the endpoint's stage is the only thing scoping a @connections call to a deployment, so ignoring it makes the emulator over-permissive — a client pointed at a stage that was never deployed (a typo, a stale name, a stage deleted under it) is told the connection is gone rather than that it may not invoke that endpoint. Applications that prune their own connection table on GoneException (the documented signal that the peer went away) will silently delete LIVE connections whenever they are misconfigured, and a per-stage authorization boundary that exists on AWS does not exist here.
Fix: the @connections request router / endpoint resolution in front of the three handlers — resolve {api-id, stage} from the request path against the API's deployed stages and return the 403 ForbiddenException envelope (status 403, error code ForbiddenException, message 'Forbidden') before dispatching to the connection store.

The open wire issue 20261029T214905Z-apigatewaymanagementapi-connections-error-layer-every-failure-answers-410.md covers the same fault from the wire corpus and carries fixture/step keys, not this check id.
