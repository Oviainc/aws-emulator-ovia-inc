# EC2 DescribeInstanceTypes serves an emulator-authored instance-type catalog instead of AWS per-type attributes

> _Note: this issue was identified against the code base at commit `77172d4b913d3cd289b60abc3e2fa4659d3ee8a2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeInstanceTypes

## Description
This issue bundles 6 causes; all 6 must be closed. Every cause is one DescribeInstanceTypes catalog page that diverges because the emulator answers the instance-type catalog from a table it authored itself and from per-type formulas it computes, rather than from AWS's catalog values, and because its InstanceTypeInfo projection never emits a group of modelled members at all. The same defect is the dominant family in this replay: 107 unowned DescribeInstanceTypes clusters across the five ec2-catalog-describe-instance-types-* fixtures (a1-c9g, c9gd-m6gd, m6i-r4, r5-r8in, r9g-z1d) are the same root cause, one cluster per probed instance-type page; the 6 causes below are the per-fixture representatives, and fixing the catalog seed plus the omitted-member projection fixes them together. The open issue '20261030T063325Z-ec2-static-catalogs-diverge-from-aws-instance-type.md' describes this family on other steps and the open issues '20261029T200817Z-ec2-read-paths-omit-modeled-members-and-serve.md' and '20261029T215142Z-ec2-describe-projections-omit-modeled-members-and-seed.md' describe the omitted-member habit, but none of them carries the replay keys named here.

General shape of the fault, shared by all 6 causes:
AWS: recorded behavior only for the values - a per-instance-type attribute is catalog data, not a modelled constraint - but the MEMBERS are modelled on the DescribeInstanceTypes response's InstanceTypeInfo structure, and the recordings show them present on every entry: cpuBurstModel, phcSupport, rebootMigrationSupport, autoRecoverySupported, currentGeneration, dedicatedHostsSupported, freeTierEligible, hibernationSupported, ebsInfo.attachmentLimitType, ebsInfo.encryptionSupport, ebsInfo.maximumEbsAttachments, the six ebsInfo.ebsOptimizedInfo baseline/maximum bandwidth-IOPS-throughput numbers, instanceStorageInfo.disks.item.count/sizeInGB and instanceStorageInfo.totalSizeInGB, networkInfo.bandwidthWeightings, networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.ipv4AddressesPerInterface, networkInfo.ipv4AddressesPerSecondaryInterface, networkInfo.ipv6AddressesPerInterface, networkInfo.maximumNetworkCards, networkInfo.maximumNetworkInterfaces, networkInfo.networkCards, networkInfo.networkPerformance, networkInfo.secondaryNetworkSupported, networkInfo.trafficMirroringSupport, networkInfo.efaInfo/efaSupported, nitroEnclavesSupport, nitroTpmSupport, processorInfo.supportedFeatures, processorInfo.sustainedClockSpeedInGhz and vCpuInfo.validCores.
Emulator: a fixed subset of those members is never serialized (returned as absent), and the members it does serialize carry numbers produced by its own derivation rather than the per-type values AWS publishes, so they differ for the same instance type. A representative constant it emits regardless of type is networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout = 432000 where AWS reports 350, and ebsInfo.attachmentLimitType = 'shared' where AWS reports 'dedicated' for types that have a dedicated EBS attachment limit.
Why: clients size and select instances off exactly these numbers. A caller reading maximumEbsAttachments, baselineThroughputInMBps or networkPerformance gets a figure no real instance has, so capacity planning, volume-attachment limits and bandwidth budgeting are all computed from fiction; a caller reading cpuBurstModel, phcSupport, networkCards, bandwidthWeightings or validCores gets nothing at all and cannot tell 'unsupported' from 'not reported'. Strict deserializers that require the modelled members fail outright.
Fix: the DescribeInstanceTypes handler's instance-type catalog - the seeded catalog data and the derivation that synthesizes EBS/network figures must carry AWS's per-type values - together with the operation's InstanceTypeInfo serializer/projection, which must emit every modelled member it currently drops.
