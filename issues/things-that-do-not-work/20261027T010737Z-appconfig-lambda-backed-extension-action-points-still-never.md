# AppConfig Lambda-backed extension action points still never fire: PRE_START_DEPLOYMENT, AT_DEPLOYMENT_TICK and PRE_CREATE_HOSTED_CONFIGURATION_VERSION remain unobservable (3 causes)

## Description

=== Cause 1 of 3: a PRE_START_DEPLOYMENT extension action is never invoked and never gates StartDeployment ===
AWS: StartDeployment is POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / InternalServerException 500 (Smithy, services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json). With an extension whose Actions declare PRE_START_DEPLOYMENT [{Name, Uri=<lambda function ARN>, RoleArn}] and an extension association bound to the environment ARN, StartDeployment synchronously invokes that target BEFORE creating the deployment. Recorded behavior (the check states it was MEASURED against real AWS): the event carries Application{Id,Name}, Environment{Id,Name}, ConfigurationProfile{Id,Name}, Content (base64 of the exact candidate configuration bytes), ContentType, ContentVersion as a STRING, DeploymentNumber, PreviousDeploymentNumber, InvocationId, Parameters and Type='PreStartDeployment' — PascalCase, not the SCREAMING_SNAKE action-point key. When the target raises, StartDeployment is refused with BadRequestException / HTTP 400 and the request-derived message `Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <requestId>` (fixed text: `Error invoking extension `, `: Unhandled error, Lambda Request ID: `; variable parts: the associated extension's name from state and the invocation's own request id), NO deployment record is created, and the data plane keeps serving the previously deployed version. When the target returns normally the deployment proceeds and reaches State=COMPLETE.
Emulator: the check never reaches a verdict — killed at the harness cap with 'Check timed out after 60.0s'. Nothing ever arrives at the observation sink the target forwards its event to, and the deployment never reaches a terminal state, so neither the invocation, nor the event shape, nor the veto refusal is observable. Hypothesis: extension associations are still stored as metadata only, with no action-point dispatch in the StartDeployment path.
Why: PRE_START_DEPLOYMENT is the hook customers use to VETO a release. Against this emulator a configuration production would have blocked deploys anyway (over-permissive on the safety hook), and any client that waits for the deployment to settle waits forever.
Traces: appconfig__lambda.extension-action-point-invokes-lambda-during-deployment.

=== Cause 2 of 3: AT_DEPLOYMENT_TICK is never invoked during an in-flight deployment, so a ROLL_BACK directive cannot revert it, and the deployment never leaves its transitional state ===
AWS: per the replayed check's own DRAFT/unblessed header (so Hypothesis, drawn from AppConfig's custom-Lambda extension documentation rather than a recording), an extension action bound to AT_DEPLOYMENT_TICK is invoked repeatedly while a deployment is in flight, and a target response of {"Directive": "ROLL_BACK", "Description": "<text>"} makes AppConfig roll the deployment back; the deployment then settles in a terminal state (ROLLED_BACK/REVERTED) and the environment leaves its transitional Deploying/RollingBack state. Independently of the directive, a non-zero-duration deployment must progress to a terminal state on its own (DeploymentState is a modeled enum on GetDeployment/StartDeployment output; GetEnvironment's State is served CamelCase).
Emulator: killed at the 60 s cap. The deployment is never ticked, the directive is never read, and neither the deployment nor the environment leaves its transitional state, so no rollback is observable and teardown of the environment is blocked.
Why: AT_DEPLOYMENT_TICK plus ROLL_BACK is AppConfig's programmable abort. Here a deployment production would have rolled back stays in flight indefinitely with its configuration in service, and a client polling for a terminal state never returns.
Traces: appconfig__lambda.at-deployment-tick-directive-rollback-reverts-the-deployment.

=== Cause 3 of 3: PRE_CREATE_HOSTED_CONFIGURATION_VERSION is never invoked, so the action's replacement Content never changes the stored bytes ===
AWS: per the same check's DRAFT header (Hypothesis, from the same documentation), an extension action bound to PRE_CREATE_HOSTED_CONFIGURATION_VERSION is consulted synchronously by CreateHostedConfigurationVersion (POST /applications/{ApplicationId}/configurationprofiles/{ConfigurationProfileId}/hostedconfigurationversions, Content as the @httpPayload, success 201). The event carries Type='PreCreateHostedConfigurationVersion', ContentType, ContentVersion (the version being created, as a STRING), Content (base64 of the unmodified request bytes) and, from the second version on, PreviousContent{ContentType,ContentVersion,Content} carrying the previously STORED bytes. A response of {"Content": "<base64>"} REPLACES what is stored: both CreateHostedConfigurationVersion's own response body and a later GetHostedConfigurationVersion return the transformed bytes. Removing the association restores byte-faithful storage.
Emulator: killed at the 60 s cap before it can grade the transform; nothing reaches the observation sink, so the action point is never consulted. Hypothesis: CreateHostedConfigurationVersion stores the request bytes verbatim with no PRE_* dispatch — byte-faithful by default, which is exactly the plausible-but-wrong behavior the check exists to catch.
Why: this is one of only two places where customer code may rewrite the configuration payload itself. A client relying on it (stamping, normalizing, redacting) silently gets its untransformed document stored and later served.
Fix (shared component): AppConfig extension action-point dispatch — the extension/extension-association state plus the invocation seam called from the StartDeployment handler (PRE_START_DEPLOYMENT and the deployment state machine's tick loop) and from the CreateHostedConfigurationVersion handler (PRE_CREATE_HOSTED_CONFIGURATION_VERSION). Each site must resolve the associations bound to the target resource ARN, build the documented event (PascalCase Type, base64 Content, string ContentVersion, PreviousContent where applicable), invoke the action's Uri through the lambda data plane, and interpret the response: a raising target refuses the calling operation with BadRequestException/400 and leaves no record, a {"Content": ...} response replaces the stored payload, and a {"Directive":"ROLL_BACK"} response drives the deployment state machine to a terminal rolled-back state. The deployment state machine for non-zero-duration strategies must also progress to a terminal state on its own.
Traces: appconfig__lambda.pre-create-hosted-configuration-version-extension-transforms-stored-content.
