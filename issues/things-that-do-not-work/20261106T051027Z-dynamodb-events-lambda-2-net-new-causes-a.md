## Description
Two net-new root causes, grounded in the only two failing dynamodb__events__lambda checks the replay report marks neither OWNED nor ALREADY FILED (42 of the 44 failures in this service are marked and were skipped). Both must be closed before submitting.

Related open issues — none of them carries either replay key below, so this is filed separately and should be de-duplicated against them if one fix closes several: 20261106T015127Z-cloudwatch-dynamodb-lambda-a-cfn-stack-wiring-a.md (the SAME stack-rollback symptom, but filed for service cloudwatch__dynamodb__lambda and carrying only that service's three check ids), 20261105T022225Z-cloudwatch-dynamodb-lambda-2-net-new-causes-a.md (a CFN-deployed AWS::Lambda::EventSourceMapping invisible to ListEventSourceMappings), 20261105T094343Z-dynamodb-events-lambda-the-lambda-python-runtime-provides.md (the python runtime provides no AWS SDK, for a different 16-check set), 20261029T180026Z-dynamodb-events-lambda-eventbridge-rules-never-invoke-their-lambda-targets-ddb.md, 20261104T044826Z-dynamodb-events-lambda-cli-driven-eventbridge-rules-and-dynamodb-stream-event.md.

Cause 1 of 1-and-2: a CloudFormation stack declaring a DynamoDB table with StreamSpecification, an IAM role, a python Lambda and an AWS::Lambda::EventSourceMapping from the table's StreamArn to that function settles in ROLLBACK_COMPLETE instead of CREATE_COMPLETE. Failing check: dynamodb__events__lambda.cfn-ddb-stream-esm-lambda-deployment.
AWS: Smithy cloudformation CreateStack accepts the template, and DescribeStacks reports StackStatus from the StackStatus enum (values include CREATE_IN_PROGRESS, CREATE_COMPLETE, ROLLBACK_IN_PROGRESS, ROLLBACK_COMPLETE); ROLLBACK_COMPLETE is reached only after a resource create FAILED and the stack was rolled back. Every resource type in this template is a supported AWS type: two AWS::DynamoDB::Table (PAY_PER_REQUEST; the source one with StreamSpecification NEW_AND_OLD_IMAGES), an AWS::IAM::Role assumable by lambda.amazonaws.com with the managed AWSLambdaDynamoDBExecutionRole plus an inline dynamodb:PutItem statement scoped by !GetAtt SinkTable.Arn, an AWS::Lambda::Function (Runtime python3.12, Handler index.handler, inline Code.ZipFile, Role !GetAtt FunctionRole.Arn) and an AWS::Lambda::EventSourceMapping with EventSourceArn !GetAtt SourceTable.StreamArn, FunctionName !Ref StreamFunction, StartingPosition TRIM_HORIZON, BatchSize 5. Submitted with Capabilities CAPABILITY_IAM/CAPABILITY_NAMED_IAM, the stack settles CREATE_COMPLETE on AWS, its Outputs (SourceTableName, SinkTableName, EsmId, FunctionName) resolve, GetEventSourceMapping(UUID=EsmId) reaches State "Enabled", and a PutItem on the source table drives the function so the sink item appears with event_name == "INSERT". Recorded behavior: the check's deploy phase succeeded against real AWS and went on to inspect the mapping and the stream-driven write.
Emulator: the stack settles in ROLLBACK_COMPLETE, so the check's deploy helper raises `AssertionError: Stack <stack-name> ended in ROLLBACK_COMPLETE` (raised from _deploy_cfn, line 175, after create_stack) and the scenario stops at its first step. CreateStack itself returns no error code or message — the refusal is visible only as the terminal stack status, and the replay output shows no resource-level CREATE_FAILED reason.
Why: a client provisioning the standard DynamoDB-Streams-to-Lambda pipeline declaratively gets no stack at all: tables, role, function and mapping are rolled back and deleted, DescribeStacks reports a failed stack, and every downstream read (GetEventSourceMapping, the sink write, Invoke) has nothing to address. Nothing in the template can be adjusted to work around it, and with no CREATE_FAILED event carrying a ResourceStatusReason the cause is not diagnosable from the API.
Fix: the CloudFormation create path for this resource set — the providers for AWS::Lambda::EventSourceMapping, AWS::Lambda::Function and the AWS::DynamoDB::Table stream attribute (Fn::GetAtt StreamArn) must create successfully so the stack reaches CREATE_COMPLETE; and whichever resource fails must record a stack event with ResourceStatus CREATE_FAILED and a ResourceStatusReason rather than only a bare terminal ROLLBACK_COMPLETE.
Traces: dynamodb__events__lambda.cfn-ddb-stream-esm-lambda-deployment (group deployment-order).

Cause 2 of 2: a CLI-driven Lambda whose execution role carries dynamodb:PutItem from creation never reports a successful write, so neither the positive control nor the AccessDeniedException negative can be observed. Failing check: dynamodb__events__lambda.cli-lambda-role-policy-missing-dynamodb-negative-workflow.
AWS: Smithy lambda Invoke (POST /2015-03-31/functions/{FunctionName}/invocations) returns StatusCode, Payload (the handler's return value) and FunctionError only when the handler faulted. Smithy dynamodb PutItem input TableName (@required, @length 1..1024) + Item (@required) models ConditionalCheckFailedException, ResourceNotFoundException, ProvisionedThroughputExceededException, ThrottlingException, InternalServerError and friends — authorization failures are not modeled per-operation; AWS answers an unauthorized caller with HTTP 400 and error code AccessDeniedException whose message is "User: arn:aws:sts::<account-id>:assumed-role/<role-name>/<function-name> is not authorized to perform: dynamodb:PutItem on resource: <table-arn> because no identity-based policy allows the dynamodb:PutItem action" (fixed text: "User: ", " is not authorized to perform: dynamodb:PutItem on resource: ", " because no identity-based policy allows the dynamodb:PutItem action"; variable parts: the assumed-role ARN built from the account, role and function names, and the table ARN from the request). On AWS the check therefore observes: the function whose role has the inline dynamodb:PutItem statement returns {"status": "ok"} and the item is readable with GetItem; the sibling function whose role has only AWSLambdaBasicExecutionRole returns {"status": "error", "code": "AccessDeniedException"} and writes nothing.
Emulator: the setup is accepted — CreateTable (+ table_exists waiter), two CreateRole/AttachRolePolicy calls, PutRolePolicy for the allowed role, two CreateFunction calls (python3.12, Publish=true) — and then the positive control never succeeds: the retrying RequestResponse Invoke of the allowed function (budget 90 s, interval 5 s) never returns a payload with status == "ok", and the harness kills the check with "Error: Check timed out after 60.0s" before the GetItem assertion and before the denied-invoke leg runs at all. No refusal is produced on the path, so there is no status, error code or message to compare for the positive leg; the AccessDeniedException code and message the negative leg requires are never exercised.
Hypothesis: the handler imports boto3 and calls dynamodb:PutItem, so the observable is consistent with the runtime not providing an AWS SDK (the handler faults instead of returning its payload) or with the invoke never running the handler. Open issue 20261105T094343Z-dynamodb-events-lambda-the-lambda-python-runtime-provides.md reports that runtime defect for a different check set and does not carry this check's replay key, so this check is still unaccounted for.
Why: a client cannot tell a granted role from a denied one. The grant path returns no success, and the denial path — the only way an operator learns that a function's role is missing dynamodb:PutItem — never yields the AccessDeniedException code or its message, so least-privilege configuration cannot be validated: an under-privileged role and a correctly privileged role are indistinguishable at run time.
Fix: the Lambda invoke/runtime path (run the handler with an AWS SDK available and return its payload, setting FunctionError only on a genuine fault) together with the DynamoDB PutItem authorization path, which must answer a caller whose assumed execution role lacks dynamodb:PutItem with HTTP 400 AccessDeniedException and the message above, and must not write the item.
Traces: dynamodb__events__lambda.cli-lambda-role-policy-missing-dynamodb-negative-workflow (group overly-permissive).
