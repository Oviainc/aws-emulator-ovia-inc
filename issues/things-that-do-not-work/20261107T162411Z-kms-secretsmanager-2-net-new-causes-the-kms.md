# kms__secretsmanager: 2 net-new causes — the KMS authorization refusal is relayed verbatim instead of 'Access to KMS is not allowed', and kms:ViaService is still never populated for the Secrets Manager forward access session

> _Note: this issue was identified against the code base at commit `46d4bc769d688157e8bc6d12ab890b12b1627210`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSecretValue

## Description
TWO root causes, both in the Secrets Manager <-> KMS envelope path; a fixer must close BOTH before submitting.

Related OPEN issue, named for context only, which does NOT carry either replay key below (both checks now fail at a different assertion than the one its Issue-Key records, so it does not cover them): 20261031T125106Z-kms-secretsmanager-a-kms-authorization-refusal-is-relayed.md. Its Cause 1 asked for BOTH the code AccessDeniedException and the fixed message; the CODE now matches in this replay and the MESSAGE does not, which is Cause 1 here. Its Cause 2 asked for kms:ViaService to be populated for the service route; that is still unpopulated, and the refusal it produces has merely changed code (EncryptionFailure -> AccessDeniedException), which is Cause 2 here.

Cause 1 of 2 - GetSecretValue relays the raw KMS authorization denial, including the KMS-SDK diagnostic envelope, instead of Secrets Manager's own fixed message.
AWS: GetSecretValue unwraps the requested version under the secret's KmsKeyId on the caller's behalf. When that KMS call is refused for AUTHORIZATION reasons - here an explicit Deny on kms:Decrypt in the key policy - Secrets Manager refuses with HTTP 400, Error.Code AccessDeniedException and the message exactly 'Access to KMS is not allowed'. That message is ENTIRELY FIXED TEXT with no variable part: it does not carry the caller ARN, the KMS action, the key ARN, the policy-evaluation reason or '(Service: AWSKMS; Status Code: ...; Error Code: ...; Request ID: ...; Proxy: null)'. Secret METADATA is not wrapped under the CMK, so DescribeSecret must keep resolving (KmsKeyId = the key ARN) and ListSecrets must keep enumerating the secret while the Deny is live, and restoring the key policy must make the SAME VersionId readable again with no new version. Smithy (com-amazonaws-secretsmanager-secretsmanager): GetSecretValue's modeled errors are DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException - AccessDeniedException is the service-common denial and is not among them; the fixed wording is recorded behavior only.
Emulator: the code and status are now right (HTTP 400 AccessDeniedException) but the message is the relayed KMS string 'User: <caller-arn> is not authorized to perform: kms:Decrypt on resource: <key-arn> with an explicit deny in a resource-based policy (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <request-id>; Proxy: null)'. The caller ARN, key ARN and request id in it are per-run values filling the emulator's template; the defect is the template, which AWS never emits for this class.
Why: clients match on that exact text to tell 'the principal lost access to the CMK' from a Secrets Manager-level denial, so error-text assertions, runbooks and log scrapers take the wrong branch. The relayed string also discloses through the Secrets Manager front door what AWS deliberately withholds: the internal KMS action, the resolved key ARN, the policy-evaluation reason and a KMS request id.
Fix: the GetSecretValue handler's KMS error-mapping step in the envelope path (shared with PutSecretValue / CreateSecret / UpdateSecret). An AccessDenied-class KMS refusal must be replaced by AccessDeniedException with the fixed message and nothing from the wrapped response; only the key-state / crypto-failure class may keep a relayed message under DecryptionFailure / EncryptionFailure.
Traces: kms__secretsmanager.get-secret-value-denied-when-the-cmk-decrypt-permission-is-removed.

Cause 2 of 2 - the KMS request Secrets Manager makes on the caller's behalf still carries no kms:ViaService condition value, so a key-policy Deny conditioned on StringNotEquals kms:ViaService refuses the SERVICE route as well as the direct one.
AWS: kms:ViaService discriminates by HOW the KMS request arrived, not by who made it (AWS KMS Developer Guide, conditions-kms.html: the kms:ViaService condition key limits use of a KMS key to requests from specified AWS services, and applies only to forward access sessions). A KMS request Secrets Manager issues through a forward access session on the caller's behalf carries kms:ViaService = secretsmanager.<region>.amazonaws.com; the same principal's OWN direct KMS call carries no value for that key at all. So with a key-policy statement {Effect: Deny, Principal: {AWS: '*'}, Action: [kms:Encrypt, kms:Decrypt, kms:GenerateDataKey, kms:GenerateDataKey*, kms:ReEncrypt*], Resource: '*', Condition: {StringNotEquals: {'kms:ViaService': ['secretsmanager.<region>.amazonaws.com']}}} live: a DIRECT kms:GenerateDataKey and a DIRECT kms:Encrypt are refused HTTP 400 AccessDeniedException with the message 'User: <caller-arn> is not authorized to perform: <kms-action> on resource: <key-arn> with an explicit deny in a resource-based policy' (fixed text; caller ARN, KMS action and key ARN taken from the request), while PutSecretValue answers HTTP 200 with a NEW VersionId and GetSecretValue returns byte-identical plaintext for both the new and the baseline version. recorded behavior only for the service leg (this check carries no blessed recording for it); the AWS side above is the documented ViaService rule plus the modeled refusal shape, and the direct-leg behaviour IS observed in this replay.
Emulator: the key policy and its condition ARE evaluated correctly on the direct route - the direct kms:GenerateDataKey starts being refused exactly as AWS would refuse it - but the Secrets Manager -> KMS call presents no kms:ViaService value either, so StringNotEquals fires on it too. PutSecretValue is refused HTTP 400 AccessDeniedException 'User: <caller-arn> is not authorized to perform: kms:GenerateDataKey on resource: <key-arn> with an explicit deny in a resource-based policy (Service: AWSKMS; Status Code: 400; Error Code: AccessDeniedException; Request ID: <request-id>; Proxy: null)' where AWS answers 200 and a new version. (The code is now AccessDeniedException rather than EncryptionFailure; the wording is Cause 1's defect. Cause 2 is that the call is REFUSED at all.)
Why: restricting a CMK to one service route with kms:ViaService is a standard, widely deployed KMS control. Under the emulator it is indistinguishable from revoking the key: every secret read and write through the service is refused, so a client whose production key policy uses this condition cannot run against the emulator at all, and nobody can verify that the control permits the service while blocking direct use.
Fix: the KMS policy-evaluation request context must be populated with kms:ViaService = <service endpoint prefix>.<region>.amazonaws.com whenever a cryptographic call arrives as a service forward access session rather than from the principal directly, and the Secrets Manager envelope path (GetSecretValue / PutSecretValue / CreateSecret / UpdateSecret) must mark the KMS calls it makes on the caller's behalf as arriving via secretsmanager.<region>.amazonaws.com. A direct call must continue to present NO value for that key, so negated conditions keep firing on it.
Traces: kms__secretsmanager.via-service-condition-permits-the-secrets-manager-read-and-denies-the-direct-call.
