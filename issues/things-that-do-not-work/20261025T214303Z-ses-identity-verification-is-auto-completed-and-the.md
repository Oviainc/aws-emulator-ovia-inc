# SES identity verification is auto-completed and the v1/v2 identity store is not shared: 5 net-new root causes (instant 'Success', 33-byte VerificationToken, v2-created identities invisible to v1, forged v1 NextToken accepted, ListEmailIdentities unrouted)

> _Note: this issue was identified against the code base at commit `ca265ed85df5a1b6b7b5ff6c2c813551ab1096d8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
VerifyEmailIdentity

## Description
Five net-new behavioral root causes in the SES identity plane. Related open issue 20261023T120410Z-ses-v1-and-v2-is-entirely-unreachable-the.md (router AmbiguousService) no longer carries these replay keys — requests are now dispatched and these are the fidelity defects behind the dispatcher. None of the causes below is one of the scaffold-stub clusters the report marked ALREADY FILED.

Cause 1 of 5: a newly requested identity is reported verified immediately, so the identity gate on sending is never armed.
AWS: VerifyEmailIdentity and VerifyDomainIdentity only *request* verification; the identity stays unverified until the confirmation link is clicked (email address) or the TXT record is published and detected (domain). Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery): VerifyEmailIdentity input {EmailAddress} / output {} (no status at all); VerifyDomainIdentity output {VerificationToken required}; GetIdentityVerificationAttributes output VerificationAttributes -> IdentityVerificationAttributes{VerificationStatus required, enum VerificationStatus values [Pending, Success, Failed, TemporaryFailure, NotStarted], documented as "The verification status of the identity: 'Pending', 'Success', 'Failed', or 'TemporaryFailure'"}. A freshly requested identity therefore reads 'Pending', and SendEmail/SendRawEmail/SendTemplatedEmail/SendBulkTemplatedEmail from it are refused MessageRejected (Smithy: SendEmail error MessageRejected, awsQueryError code MessageRejected, httpError 400).
Emulator: GetIdentityVerificationAttributes reports VerificationStatus 'Success' for an identity created a moment earlier with no DNS record published and no confirmation click — replay shows "expected Pending status, got 'Success'", "a freshly verified domain with no published DNS records must be Pending, not 'Success'" and "precondition: a freshly requested email identity should be Pending, got 'Success'". Because the identity is already Success, every send-refusal check downstream cannot even arm its gate (ses.send-fault-precedence-is-a-stable-total-order: "the sender must be a real identity that is simply not verified ... got {'VerificationStatus': 'Success'}"). Note the v2 surface does NOT do this: a v2 CreateEmailIdentity domain correctly reads PENDING, so the defect is in the v1 verify path / the state it writes.
Why: the whole unverified-source refusal class disappears. A client that relies on AWS to refuse sending from an unverified address gets its mail accepted (MessageId returned) by the emulator, so sandbox/identity enforcement, the Pending->Success transition, and any polling loop that waits for verification are all unfaithful; code that waits for 'Pending' to clear sees a state machine with no Pending state.
Fix: the VerifyEmailIdentity / VerifyDomainIdentity handlers in the ses v1 crate (services/service-com-amazonaws-ses-simpleemailservice/src/ops/verify_email_identity.rs, verify_domain_identity.rs) and the identity record they write in that crate's state: a newly created identity must persist VerificationStatus=Pending, and the send-path identity gate must read it.
Traces: ses.verify-email-identity-lifecycle, ses.verify-domain-identity-and-dkim-tokens, ses.concurrent-verify-email-identity-is-idempotent, ses.send-email-unverified-source-rejected, ses.send-email-pending-identity-still-rejected, ses.send-raw-email-unverified-source-rejected, ses.send-bulk-templated-email-unverified-source-rejected, ses.send-templated-email-validation-order, ses.send-fault-precedence-is-a-stable-total-order.

Cause 2 of 5: the domain VerificationToken is not a 32-byte base64 value.
AWS: VerifyDomainIdentity returns the TXT value the customer publishes at _amazonses.<domain>; Smithy types it as VerificationToken (string) and documents it only as the verification token, so this is recorded behavior: real AWS tokens are base64 that decodes to exactly 32 bytes, and the same token must come back from GetIdentityVerificationAttributes (stored state, not minted per read).
Emulator: the token it mints is valid base64 but decodes to 33 bytes — "VerificationToken decoded to 33 bytes, expected 32".
Why: a client that round-trips the token through DNS tooling with a fixed-width expectation, or that compares it against the shape AWS emits, sees a token no real SES account would issue; token length is the only structural property a caller can validate before publishing the record.
Fix: the VerifyDomainIdentity handler's token minting in the ses v1 crate — generate 32 random bytes and base64-encode them (the length of the decoded value, not of the encoded string, is the requirement).
Traces: ses.domain-identity-dkim-tokens-stay-consistent-across-reads.

Cause 3 of 5: identities created through SESv2 are invisible to the SES v1 API — the two surfaces do not share one identity store.
AWS: v1 and v2 are two APIs over one set of account identities. Smithy: sesv2 CreateEmailIdentity (POST /v2/email/identities) creates an identity; v1 GetIdentityVerificationAttributes and ListIdentities then report it, with the status spelled in v1's TitleCase (Pending) for v2's SCREAMING_CASE (PENDING), and a domain identity exposes its TXT VerificationToken through v1.
Emulator: after sesv2 CreateEmailIdentity on a domain (which itself returns 200 and reads PENDING through v2), the v1 reads never see it: GetIdentityVerificationAttributes has no entry for that domain at all, so the check's poll never converges and the check is killed at the harness cap ("Check timed out after 60.0s"), and v1 ListIdentities(MaxItems=1) returns 0 identities for an account that holds three v2-created domains ("v1 ListIdentities(MaxItems=1) returned 0 items, expected exactly 1: []").
Why: any workflow that creates identities with the modern API and reads or waits on them with the legacy one (or vice versa) sees an empty account; cross-API cursors and status polling are impossible, and v1 pagination cannot even be exercised because the list is empty.
Fix: the identity state shared by the two crates — the sesv2 CreateEmailIdentity handler must write into the same identity store that the ses v1 ListIdentities / GetIdentityVerificationAttributes handlers read (one store per account+region, with the v1<->v2 status spelling mapped on read), rather than a per-crate store.
Traces: ses.email-identity-v1-v2-shared-store, ses.list-identities-v1-token-continues-v2-list.

Cause 4 of 5: a forged v1 ListIdentities NextToken is accepted and served as page one.
AWS: ListIdentities is paginated (Smithy: inputToken NextToken, outputToken NextToken, items Identities, pageSize MaxItems) and a cursor it never minted is refused, not honoured: code InvalidParameterValue with message "Invalid NextToken <TOKEN>." — fixed text "Invalid NextToken <" + the rejected token verbatim from the request + ">." — and the account's identity list is left untouched.
Emulator: v1 ListIdentities(NextToken='c2ltMnJlYWwtZm9yZ2VkLXYxLXRva2Vu') answers HTTP 200 with a full Identities page ("expected the call to be refused, but it succeeded with {'Identities': [...], 'HTTPStatusCode': 200}"), i.e. the cursor is not validated at all.
Why: an over-permissive pagination surface hides client bugs that real AWS surfaces, and a caller that reuses a stale or hand-built cursor silently restarts the walk from page one instead of being told the cursor is invalid — producing duplicate processing with no error.
Fix: NextToken validation in the ses v1 ListIdentities handler (services/service-com-amazonaws-ses-simpleemailservice/src/ops/list_identities.rs): decode and authenticate the cursor against the listing it was minted for and refuse an unknown one with InvalidParameterValue and the message above.
Traces: ses.v1-list-identities-forged-next-token-rejected.

Cause 5 of 5: SESv2 ListEmailIdentities is not reachable on the route the AWS SDKs use.
AWS: ListEmailIdentities returns the account's email identities; the AWS SDKs address it as GET /v2/email/identities (that is the request botocore issued in the recording) and it answers 200 with {EmailIdentities[], NextToken} (modeled errors BadRequestException 400, TooManyRequestsException 429).
Emulator: the call is answered 501 NotImplemented with the non-AWS message "operation GET /v2/email/identities is not implemented in this emulator" — a route miss rather than a scaffold-stub refusal (so it is not one of the ALREADY FILED stub clusters). The in-repo model binds the operation to POST /v2/email/list-identities (Smithy, service-com-amazonaws-sesv2-simpleemailservice-v2: ListEmailIdentities http POST /v2/email/list-identities code 200), so the method+URI every SDK actually sends is unbound. Hypothesis: the restJson1 route table was built from that binding only.
Why: no SDK client can list SESv2 identities at all — pagination exactness, filters and cross-API cursor continuation are unreachable, and the caller gets a 501 with a code no AWS model defines.
Fix: the sesv2 crate's restJson1 route table plus the handler at services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/list_email_identities.rs — bind GET /v2/email/identities (the SDK-visible route) to ListEmailIdentities and implement the listing.
Traces: ses.list-identities-pagination-exactness-v1-and-v2.
