# scheduler: 2 net-new behavioral causes — an EndDate-bounded rate() schedule delivers NO occurrence at all, and the refusal of a past EndDate with no StartDate is worded by the emulator

> _Note: this issue was identified against the code base at commit `58511c6cfb9f29f34cba9f5bd79b625dce957a70`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSchedule

## Description
This issue carries 2 root causes, both in the `scheduler` service. Each must be closed before this issue is submitted; each cause below lists the failing check ids it is grounded in. Neither check is marked ALREADY FILED or OWNED in the replay report. Related but NOT covering: open issue 20261109T141116Z-scheduler-occurrence-timing-and-lifecycle-7-causes-schedules.md describes early firing, ignored StartDate, un-paced rate() and ActionAfterCompletion, but carries no EndDate-suppression check and not this check id; open issue 20261108T032912Z-scheduler-5-net-new-behavioral-causes-three-refusal.md Cause 3 covers the reversed-pair branch of the SAME validator (both StartDate and EndDate present) and does not carry the no-StartDate branch or this check id.

=== Cause 1 of 2: a recurring rate() schedule bounded by a near-future EndDate delivers NO occurrence at all — the pre-EndDate tick is lost together with the post-EndDate ones ===
Failing check: scheduler.schedule-end-date-stops-future-invocations
AWS: Smithy (com.amazonaws.scheduler) — CreateSchedule.ScheduleExpression is required, @length 1..256, and accepts the rate(value unit) form; StartDate is "The date, in UTC, after which the schedule can begin invoking its target" and EndDate is "The date, in UTC, before which the schedule can invoke its target" (both optional plain timestamps; no error is modelled for an EndDate merely bounding the series). A rate() schedule carrying NO StartDate fires its first occurrence immediately on creation (t=0) and then every cadence interval; EndDate only closes the window, so the occurrences at or before EndDate are delivered and the ones after it are suppressed. For rate(2 minutes) in State=ENABLED with FlexibleTimeWindow Mode=OFF and EndDate placed 60 s after creation (i.e. 60 s after the t=0 tick and 60 s before the t=120 tick) the target receives EXACTLY ONE invocation.
Emulator: the target receives ZERO invocations across 200 s of continuous receive_message polling — the t=0 occurrence, which precedes EndDate, never arrives either. Supplying an EndDate therefore silences the schedule completely rather than bounding it. Hypothesis: the dispatcher derives the first due instant as creation + interval (t=120) instead of firing immediately, so the only occurrence it ever considers already lies beyond EndDate and is dropped; nothing in the model or the recording states this, so it is a hypothesis about the cause, not the observation.
Why: EndDate is how a client bounds a recurring schedule (a migration that must stop at a cut-over, a campaign that must stop at a deadline). On the emulator every occurrence inside the window is lost silently: GetSchedule keeps reporting State=ENABLED with the configured expression and EndDate, so there is no API surface that reveals the work was never done, and a client waiting on the in-window occurrence hangs. It is the inverse of a missed suppression and equally invisible.
Fix: the occurrence computation in the dispatch component of services/service-com-amazonaws-scheduler-awschronosservice/src/ (the arming/settle path that materialises due occurrences) must treat the window as [StartDate or the creation instant, EndDate]: emit the immediate first occurrence of a rate() expression that carries no StartDate, keep emitting at the cadence, and suppress only occurrences strictly after EndDate.
Traces: scheduler.schedule-end-date-stops-future-invocations.

=== Cause 2 of 2: UpdateSchedule refusing an already-past EndDate given with NO StartDate uses an emulator-authored message instead of AWS's StartDate/EndDate sentence ===
Failing check: scheduler.events-scheduler-semantics-update-to-a-past-end-date-rejected-and-the-series-keeps-firing
AWS: Smithy — UpdateSchedule (PUT /schedules/{Name}) declares ValidationException with httpError 400; StartDate/EndDate are the plain timestamps documented above. When EndDate is already behind the clock and the request carries no StartDate, AWS compares EndDate against an implicit start of "now" and refuses with HTTP 400 ValidationException whose Message is the fixed sentence 'The StartDate you specify must come before the EndDate.' — entirely fixed text, with no part taken from the request or from state. This is the same sentence AWS uses for an explicitly reversed pair, so the service has ONE message for an empty invocation window.
Emulator: the status and code are right (400 ValidationException) but the Message is 'EndDate must be in the future.' — a second, emulator-authored message class for the same refusal, produced by the no-StartDate arm of the window validator.
Why: the message is the whole diagnostic payload of the refusal. A client or test that matches AWS's documented wording to recognise an empty-window rejection sees an unrecognised error here, and a client that branches on the two AWS message classes it knows is told about a condition ('EndDate must be in the future') that this API never reports — while the same logical defect given with an explicit StartDate yields a different text, so the refusal is not even self-consistent.
Fix: the window-violation message in the schedule-definition validation module must be the one START_DATE_BEFORE_END_DATE sentence on BOTH arms — the explicitly reversed pair and the past EndDate with no StartDate — so the emulator-only END_DATE_IN_THE_FUTURE text disappears; both writing handlers reach it, so UpdateSchedule and CreateSchedule change together. The rest of the check's expectations (ValidationException code, the refused update storing no EndDate, State staying ENABLED, the series continuing to deliver afterwards) are unaffected by this cause.
Traces: scheduler.events-scheduler-semantics-update-to-a-past-end-date-rejected-and-the-series-keeps-firing. Code: services/service-com-amazonaws-scheduler-awschronosservice/src/state/schedule_definition.rs:246 (START_DATE_BEFORE_END_DATE), :249 (END_DATE_IN_THE_FUTURE) and :260-273 (schedule_window_violation, the `None` arm).
