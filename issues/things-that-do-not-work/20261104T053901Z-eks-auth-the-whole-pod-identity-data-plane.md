# eks-auth: the whole pod-identity data plane is unreachable — the cluster's certificateAuthority.data is not a certificate and no Kubernetes API is served at cluster.endpoint, so AssumeRoleForPodIdentity can never be reached with a pod-bound token (2 causes)

> _Note: this issue was identified against the code base at commit `b64c3d45927e2833db57dde0eaeae2a33a5b497f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssumeRoleForPodIdentity

## Description
Replaying simparity-behavioral-aws-v1 against this checkout, 11 of the 21 eks-auth checks never reach AssumeRoleForPodIdentity at all. Every one of them follows the only path AWS offers for a usable pod-identity token: create an EKS cluster, read `cluster.endpoint` and `cluster.certificateAuthority.data`, open TLS to that endpoint with that CA, create a Pod object and then mint a ServiceAccount TokenRequest bound to that Pod (boundObjectRef), because AssumeRoleForPodIdentity only accepts a token carrying the `kubernetes.io/pod` claim. The emulator breaks that path in two distinct places. TWO root causes; both must be closed before this issue is complete, and each carries its own failing check ids.

Cause 1 of 2 — `cluster.certificateAuthority.data` is not base64-encoded certificate data.
AWS: Smithy (com.amazonaws.eks#Certificate.data): "The Base64-encoded certificate data required to communicate with your cluster. Add this to the certificate-authority-data section of the kubeconfig file for your cluster." So for a cluster that has reached ACTIVE, `certificateAuthority.data` is the base64 encoding of one or more PEM-encoded X.509 certificates (`-----BEGIN CERTIFICATE-----` ... `-----END CERTIFICATE-----`) that validate the TLS certificate presented at `cluster.endpoint`. Any TLS client — kubectl, client-go, or `ssl.create_default_context(cadata=...)` — must be able to load it as a trust anchor. (The PEM bytes themselves are per-environment; what is required is that the member decodes to a parseable certificate chain that verifies the endpoint it is paired with.)
Emulator: the value base64-decodes to text that contains no certificate at all, so loading it as a trust anchor fails before any connection is attempted: `ssl.SSLError: no start line: cadata does not contain a certificate (_ssl.c:3977)`. The already-filed wire issue 20261102T083656Z-eks-cluster-response-payload-omits-modeled-members-and.md records the value the emulator substitutes here — base64 of the literal note "EMULATOR PLACEHOLDER: this emulator runs no certificate authority"; that issue is marked fixed and only concerned itself with whether the member is present while the cluster is CREATING, so it does not cover serving a loadable certificate once the cluster is usable. 10 of the 11 checks die exactly here.
Why: a client that builds a kubeconfig or any TLS context from DescribeCluster — which is the documented use of this member — cannot talk to the cluster at all. It does not get a verification failure it could diagnose as a trust problem; it gets a malformed-trust-store error, so every pod-identity, kubelet and CSI-driver flow that depends on reaching the cluster's API server is dead in the emulator while the control-plane calls all answer 200 and report the cluster ACTIVE.
Fix: the eks crate's Cluster projection / serializer — the code that fills `certificateAuthority.data` for CreateCluster and DescribeCluster must emit base64 of a real PEM certificate (e.g. the emulator's own cluster-API serving CA) rather than a prose placeholder, and that CA must be the one whose key signs the certificate served at `cluster.endpoint` (see Cause 2).
Traces: eks-auth.pod-identity-association-policy-intersects-the-role-permissions, eks-auth.pod-identity-association-role-update-takes-effect, eks-auth.pod-identity-concurrent-valid-token-all-succeed, eks-auth.pod-identity-credentials-scoped-to-role-permissions-rejected, eks-auth.pod-identity-native-round-trip-success, eks-auth.pod-identity-no-matching-association-rejected, eks-auth.pod-identity-repeated-calls-issue-fresh-credentials, eks-auth.pod-identity-session-tags-gate-an-abac-scoped-s3-read, eks-auth.pod-identity-target-role-chain-binds-to-the-generated-external-id, eks-auth.pod-identity-wrong-audience-token-rejected, eks-auth.pod-identity-association-deleted-rejected.

Cause 2 of 2 — nothing answers the Kubernetes API at the endpoint the cluster advertises, so a pod-bound projected token can never be minted.
AWS: recorded behavior only (the Kubernetes API is not in the AWS Smithy surface). An ACTIVE EKS cluster serves the Kubernetes API at `cluster.endpoint`; the two calls this whole family of checks needs are POST /api/v1/namespaces/{namespace}/pods (create the Pod object whose UID boundObjectRef refers to — it never has to be scheduled) and POST /api/v1/namespaces/{namespace}/serviceaccounts/{serviceAccount}/token with a TokenRequest whose audiences is ["pods.eks.amazonaws.com"] and whose boundObjectRef names that Pod. That is the only way to obtain a token carrying the `kubernetes.io/pod` claim, and AssumeRoleForPodIdentity (Smithy: POST /clusters/{clusterName}/assume-role-for-pod-identity, token: JwtToken required, modeled errors AccessDeniedException/ExpiredTokenException/InvalidParameterException/InvalidRequestException/InvalidTokenException 400, ResourceNotFoundException 404) refuses every other token as InvalidTokenException before it ever consults an association.
Emulator: the checks' own diagnosis is DATAPLANE_UNIMPLEMENTED — "the cluster's Kubernetes API at https://<id>.<x>.<region>.eks.amazonaws.com could not be reached for POST /api/v1/namespaces/default/pods". The harness routes that advertised URL back to the emulator (it builds the request through ctx.endpoint_route), so this is the emulator announcing an endpoint and then serving no Kubernetes API behind it, not an outbound egress problem. Note Cause 1 masks Cause 2 in the current run: the TLS trust store fails to load before any request is sent, so fixing Cause 1 alone will move these checks from an SSLError onto this unreachable-API failure rather than making them pass.
Why: the entire positive side of eks-auth is unverifiable and, worse, unusable: a client cannot obtain the one token shape the operation accepts, so AssumeRoleForPodIdentity can only ever be exercised with tokens it must refuse. Pod-identity credential issuance, the association lookup, session tags, target-role chaining and the external-id binding all sit behind this and are silently never executed, while the control plane reports a healthy cluster with pod-identity associations attached.
Fix: the eks crate's cluster data plane — stand up a minimal Kubernetes API surface on the host/port that `cluster.endpoint` resolves to, serving at least Pod create (returning a metadata.uid) and the ServiceAccount TokenRequest subresource, minting tokens whose claims include `kubernetes.io/pod` (name + uid), `kubernetes.io/serviceaccount`, `kubernetes.io/namespace` and the requested audience, signed by a key whose JWKS the eks-auth AssumeRoleForPodIdentity handler validates against; and serve that endpoint under a TLS certificate issued by the CA whose PEM Cause 1 publishes.
Traces: eks-auth.pod-identity-association-deleted-rejected (the explicit DATAPLANE_UNIMPLEMENTED assertion), and the same ten checks listed under Cause 1, all of which must complete this leg before their eks-auth assertions run.

4. Cause 2: with a trust store that does load, issue POST <cluster['endpoint']>/api/v1/namespaces/default/pods with a minimal Pod manifest, then POST <endpoint>/api/v1/namespaces/default/serviceaccounts/default/token with a TokenRequest whose audiences=['pods.eks.amazonaws.com'] and boundObjectRef names that Pod.
