# Elastic Beanstalk: managed-action and platform-quota refusals use non-AWS message shapes, the PlatformOwner='self' filter never matches the account's own custom platforms, and the RetrieveEnvironmentInfo tail bundle carries no application log (4 causes)

> _Note: this issue was identified against the code base at commit `b1a4a993822b0574a1f24a3d622a9d42702ca481`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePlatformVersion

## Description
FOUR distinct root causes in the elasticbeanstalk emulator, all in the same service, each grounded in a failing behavioral check of this suite that the replay did NOT mark ALREADY FILED or OWNED. FOUR causes must be closed before submitting.

Adjacent open issues cover neighbouring ground but do not carry these checks (the suite marked none of them OWNED, so their recorded replay keys no longer match these failures): 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-refusal-messages-use-non-aws-templates.md (other rejection paths of the same service), 20261024T015947Z-elasticbeanstalk-elastic-beanstalk-custom-platform-versions-are-not-registered.md (describes the custom-platform registration/quota area for a different, no-longer-matching failure shape — the emulator now DOES persist the platform version, so cause 3 below is a filter-resolution fault, not a persistence fault), and 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-lifecycle-and-log-retrieval-operations-are.md (names RetrieveEnvironmentInfo among five other causes).

Cause 1 of 4: ApplyEnvironmentManagedAction's unknown-ActionId refusal is worded the emulator's way.
AWS: Smithy: ApplyEnvironmentManagedAction(EnvironmentName, EnvironmentId optional; ActionId required) -> ApplyEnvironmentManagedActionResult, modelled errors ElasticBeanstalkServiceException (client, HTTP 400) and ManagedActionInvalidStateException (client, HTTP 400, awsQueryError ManagedActionInvalidStateException). Recorded behavior: against a LIVE (Ready) environment that has no managed-update data, an ActionId the service cannot resolve is refused with Error.Code 'ElasticBeanstalkServiceException' / HTTP 400 and the message 'Managed update data not found for this environment.' — the WHOLE sentence is fixed text, with NO variable part: neither the requested ActionId nor the environment name appears in it.
Emulator: the same Error.Code and status, but Error.Message is built from the request and state: "No managed action with ActionId = '<ActionId>' exists for environment <EnvironmentName>." (one run showed ActionId 'd44bb399-1451-4b6a-8573-a687ddf835f3' and environment 'sim2real-env-c1b2d9b65f74' — those two values are this run's generated inputs filling the emulator's template, not part of any requirement).
Why: AWS reports this class as 'the environment has no managed-update data at all', while the emulator reports 'that one action id is unknown'. A client that keys on AWS's fixed sentence to decide whether managed updates are configured at all does not recognise the refusal, and a client that parses the emulator's text gets an ActionId-scoped diagnosis real AWS never gives.
Fix: the unknown/unresolvable-ActionId error construction in the ApplyEnvironmentManagedAction handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/apply_environment_managed_action.rs) — emit the fixed 'Managed update data not found for this environment.' text with no request-derived substitution.
Traces: elasticbeanstalk.apply-environment-managed-action-invalid-state-rejected (the check's later leg — the same ActionId on a Terminated environment, which must become InvalidParameterValue "No Environment found for EnvironmentName = '<name>'." — is never reached, so it is unverified).

Cause 2 of 4: the over-quota CreatePlatformVersion rejection carries a Message element AWS's does not.
AWS: Smithy: CreatePlatformVersion models TooManyPlatformsException (client error, HTTP 400, awsQueryError code 'TooManyPlatformsException'), documented as 'You have exceeded the maximum number of allowed platforms associated with the account.' Recorded behavior: once the account sits at DescribeAccountAttributes.ResourceQuotas.CustomPlatformQuota.Maximum, one more CreatePlatformVersion is refused with that code and HTTP 400 and the Error element carries NO Message member at all (the SDK reads the message as empty).
Emulator: the code and status match, but Error.Message is populated — 'The number of custom platform versions in this account has reached the limit of 50.' (the 50 is the emulator's MAX_PLATFORM_VERSIONS rendered into the sentence). The divergence is the PRESENCE of the Message member, not its wording.
Why: clients and SDK error-shape assertions that key on the absence of Message for this error, or that surface whatever Message holds, see a response shape AWS never emits.
Fix: the quota-rejection construction/serialization in the CreatePlatformVersion handler (src/ops/create_platform_version.rs) — construct TooManyPlatformsException with no message member.
Traces: elasticbeanstalk.create-platform-version-too-many-fails.

Cause 3 of 4: ListPlatformVersions does not resolve the PlatformOwner filter keyword for the calling account, so an account's own custom platform versions are invisible to the owner filter.
AWS: Smithy: ListPlatformVersions(Filters: PlatformFilters{Type, Operator, Values}) -> PlatformSummaryList, with PlatformFilter$Type including 'PlatformOwner' and the filter evaluated as 'Type Operator Values[1]'. Recorded behavior: the PlatformArn returned by CreatePlatformVersion is immediately returned by ListPlatformVersions filtered on PlatformOwner = self (the keyword that selects the caller's own platforms, spelled either 'self' or 'Self'), so the custom-platform count an account reads back equals the number it created.
Emulator: the check creates CustomPlatformQuota platform versions, then polls ListPlatformVersions(Filters=[{Type:'PlatformOwner',Operator:'=',Values:['self']}]) until the count equals the quota; the count never converges and the check is killed at the harness's 60s per-check budget ('Error: Check timed out after 60.0s'), with no assertion frame. Hypothesis: the handler compares the filter value literally against PlatformSummary.PlatformOwner, which CreatePlatformVersion sets to the emulator account id, so neither 'self' nor 'Self' ever matches any custom platform version (PlatformOwner is not in the handler's case-insensitive/keyword set — only PlatformLifecycleState is folded).
Why: an account that creates custom platforms can never enumerate them the way every AWS client and the CLI does (owner=self), so it cannot poll build status, count against its quota, tag or delete them; the quota boundary is also unobservable.
Fix: the PlatformOwner filter term resolution in the ListPlatformVersions handler (src/ops/list_platform_versions.rs, Attribute::PlatformOwner / FilterTerm::matches) — the self keyword must resolve to the calling account's platform versions, independent of case, while an explicit account id keeps matching exactly.
Traces: elasticbeanstalk.create-platform-version-too-many-platforms-rejected.

Cause 4 of 4: the RetrieveEnvironmentInfo 'tail' bundle never carries the deployed application's own log output.
AWS: Smithy: RequestEnvironmentInfo(InfoType required) then RetrieveEnvironmentInfo(InfoType required) -> EnvironmentInfoDescriptionList of EnvironmentInfoDescription{InfoType, Ec2InstanceId, SampleTimestamp, Message}, where Message is the (pre-signed S3) URL of the compiled information; the model declares no operation errors. Recorded behavior: for an environment running a deployed application, the compiled tail bundle contains that application's own stdout lines byte-identically, including non-ASCII text — no truncation and no mojibake.
Emulator: the application's marker log line never appears in any downloaded tail bundle across the check's six request/retrieve attempts, and the check is killed at the 60s budget ('Error: Check timed out after 60.0s') with no assertion frame. Hypothesis: the compiled information is synthesized from service-side state only, so it can never contain application output; the open lifecycle/log-retrieval issue above records the same reading for a non-matching replay key.
Why: anything diagnosing a deployment from the tail bundle (operators, log shippers, CI gates) gets a bundle that cannot hold what it is looking for, and an encoding regression anywhere in that path would be undetectable.
Fix: the environment-information compile that RequestEnvironmentInfo starts and RetrieveEnvironmentInfo reports (src/ops/request_environment_info.rs, src/ops/retrieve_environment_info.rs and the environment-information state they build), which must include the deployed application's log lines verbatim as UTF-8.
Traces: elasticbeanstalk.environment-info-log-payload-preserved.
