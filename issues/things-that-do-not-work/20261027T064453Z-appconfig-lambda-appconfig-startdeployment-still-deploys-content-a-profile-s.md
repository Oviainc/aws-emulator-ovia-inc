=== Cause 1 of 1: a configuration version a LAMBDA validator reports non-compliant is deployed with HTTP 201 instead of being refused with BadRequestException/400 ===
AWS: StartDeployment is POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, modeled errors BadRequestException httpError 400, ConflictException 409, ResourceNotFoundException 404, InternalServerException 500 (Smithy: services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json). A configuration profile carries Validators (ValidatorList @length 0..2; Validator{Type @required -> ValidatorType [JSON_SCHEMA, LAMBDA], Content @required, sensitive, length 0..32768}) and the model documents them as the gate: "a validator provides a syntactic or semantic check to ensure the configuration that you want to deploy functions as intended", and the deployment "can only proceed when the configuration data is valid". For Type=LAMBDA the Content names a function that AppConfig invokes SYNCHRONOUSLY with the candidate configuration (the configuration bytes base64 in the event's `content` key); a function that answers an error has reported the content non-compliant, and StartDeployment is then refused with BadRequestException / HTTP 400. Recorded behavior for the refusal's effects: no deployment record is created (the environment's deployment history is unchanged and the per-environment deployment number is not consumed), the environment is not put into Deploying, the data plane keeps serving the previously deployed version's bytes, the non-compliant hosted version stays STORED, and a later version the same validator accepts deploys normally. The relayed message embeds the Lambda invocation's runtime request id, which is a per-run value, so the requirements here are the 400 status, the BadRequestException code and the absent effects — not a literal sentence.
Emulator: the identical StartDeployment of the non-compliant version is ACCEPTED (HTTP 201 with a DeploymentNumber). Replay: `AssertionError: the call under test SUCCEEDED where real AWS refuses it — this is an over-permissiveness failure, not an error-code mismatch`. The gate is now wired but inert, and the checkout says why: services/service-com-amazonaws-appconfig-amazonappconfig/src/state/validators.rs runs a LAMBDA validator by invoking the function through the in-process Lambda seam (lines 121-156) and classifies an invocation that "did not happen at all" as NO verdict, returning `None` and letting the gated call proceed (lines 36-41 and 145-146); the invocation cannot happen because lambda's synchronous Invoke is not implemented — services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs lines 13-20 state that running the deployment package is NOT implemented and that `RequestResponse` answers HTTP 501. So every LAMBDA validator silently passes, for any content.
Why: this is AppConfig's only customer-code safety gate, and it is a safety inversion. A client that relies on a LAMBDA validator to stop a bad configuration from reaching production watches the bad configuration deploy and be served; a negative test asserting BadRequestException passes against AWS and fails here; and the downstream invariants (no deployment record, no consumed deployment number, previous bytes still served, version still stored) are never exercised. A deployment pipeline proved against this emulator ships configuration AWS would have blocked at StartDeployment. 'No verdict' being treated as 'valid' is the specific inversion: AWS never puts a configuration into service that its validator did not pass.
Fix: the validator evaluation seam services/service-com-amazonaws-appconfig-amazonappconfig/src/state/validators.rs (the LAMBDA arm's classification of a non-answering invocation) together with the StartDeployment handler's pre-flight stage in src/ops/start_deployment.rs that consumes it — a LAMBDA validator that cannot be run must not be reported as a pass on the gating path; either the invocation has to reach a function that actually runs (which depends on lambda's synchronous Invoke, open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md, whose 501 for RequestResponse is the blocking dependency here), or the gate must refuse with BadRequestException/400 rather than deploy unvalidated content, in both cases leaving the deployment counter, the environment state, the data plane and the stored version untouched.
Related, not the same cause: 20261027T010737Z-appconfig-lambda-backed-extension-action-points-still-never.md covers EXTENSION action points (PRE_START_DEPLOYMENT / AT_DEPLOYMENT_TICK / PRE_CREATE_HOSTED_CONFIGURATION_VERSION), a different mechanism from a configuration profile's Validators, and owns different check ids; 20261027T010737Z-appconfig-getdeployment-not-found-message-wording-deleteapplication-is.md Cause 3 is the JSON_SCHEMA validator type at deployment time, a different validator engine on the same gate.
