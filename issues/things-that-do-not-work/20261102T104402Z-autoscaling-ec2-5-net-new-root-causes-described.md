# autoscaling__ec2: 5 net-new root causes — described groups lose the launch-template name and tag PropagateAtLaunch, a deleted launch template is accepted, and four capacity refusals are emulator-authored

> _Note: this issue was identified against the code base at commit `fb0a9c1858b32d12ecab08653c5d3b6198801bbb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAutoScalingGroups

## Description
FIVE net-new root causes on the Auto Scaling group-representation and capacity-validation paths, all reached with the EC2 side of the scenario working (VPC, subnet and launch template all created successfully). A fixer must close ALL FIVE before submitting; the failing check ids for each cause are named under its Traces line.

Cause 1 of 5 — DescribeAutoScalingGroups echoes the stored LaunchTemplate reference instead of resolving it.
AWS: AutoScalingGroup.LaunchTemplate is com.amazonaws.autoscaling#LaunchTemplateSpecification, whose members are LaunchTemplateId, LaunchTemplateName and Version; the model states 'Conditional: You must specify either a LaunchTemplateId or a LaunchTemplateName' on both identifier members, i.e. a request supplies ONE and the service resolves the other. Recorded behavior: a group created with LaunchTemplate={LaunchTemplateId: <id>} and no Version reads back BOTH {LaunchTemplateId: <id>, LaunchTemplateName: <that template's name>} with NO Version member, and a group created with {LaunchTemplateName: <name>, Version: '$Latest'} reads back id + name + Version kept literally '$Latest'.
Emulator: the response carries only the member the request supplied — the described group's LaunchTemplate is {'LaunchTemplateId': '<lt-id>'}, with no LaunchTemplateName at all.
Why: every consumer that reads the pair off a described group — the documented CLI query LaunchTemplate.[LaunchTemplateName,Version], CloudFormation/CDK drift detection, any diagnosis that walks group -> template -> version — reads an absent name and cannot resolve the template, although the group launches from it.
Fix: the DescribeAutoScalingGroups group projection must fill both identifiers from the EC2 launch-template store rather than passing the stored reference through; the stored reference is kept verbatim by the create handler and copied out by the projection (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/create_auto_scaling_group.rs line 585; services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/describe_auto_scaling_groups.rs line 313, fn group_view).
Traces: autoscaling__ec2.asgeni-asg-config-round-trips-template-reference-and-defaults.

Cause 2 of 5 — CreateAutoScalingGroup accepts a LaunchTemplate that names a template which does not exist.
AWS: HTTP 400, Error.Code ValidationError, Error.Message 'The specified launch template, with template name <launch-template-name>, does not exist.' when the reference is by name and 'The specified launch template, with template ID <launch-template-id>, does not exist.' when it is by id — the two sentences are fixed text and the only variable part is the identifier copied from the request. Smithy: CreateAutoScalingGroup models only AlreadyExistsFault, LimitExceededFault, ResourceContentionFault and ServiceLinkedRoleFailure, so a dangling launch-template reference is reported through the service-common ValidationError (the sentence is recorded behavior only). No group is created.
Emulator: the call SUCCEEDS (HTTP 200) for both reference forms and a group is created around a launch template that was deleted before the call.
Why: this is the dangerous direction — the caller is told the group exists, DescribeAutoScalingGroups lists it, and the dangling reference only surfaces later as a group that can never launch an instance; against AWS the create fails loudly and nothing is left behind.
Fix: the CreateAutoScalingGroup handler must resolve input.launch_template (and the LaunchTemplateSpecification inside MixedInstancesPolicy) against the account's EC2 launch templates before anything is stored, exactly as it already resolves IAM instance profiles and launch configuration names (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/create_auto_scaling_group.rs lines 515 and 553).
Traces: autoscaling__ec2.asgeni-asg-with-unknown-launch-template-rejected.

Cause 3 of 5 — a described group's Tags omit PropagateAtLaunch when the request omitted it.
AWS: Smithy com.amazonaws.autoscaling#TagDescription carries ResourceId ('The name of the group'), ResourceType ('The only supported value is auto-scaling-group'), Key, Value and PropagateAtLaunch (boolean, 'Determines whether the tag is added to new instances as they are launched in the group'). Recorded behavior: a tag passed to CreateAutoScalingGroup WITHOUT PropagateAtLaunch reads back with PropagateAtLaunch present and true; the member is present on every TagDescription a describe returns, and DescribeTags can then narrow on the propagate-at-launch filter.
Emulator: the member is absent from the TagDescription for any tag created without it — the check fails with KeyError: 'PropagateAtLaunch' while reading group['Tags']. The create handler stores the request's Option verbatim and the projection passes the None straight out (create_auto_scaling_group.rs line 575; describe_auto_scaling_groups.rs line 342).
Why: any client that reads tag['PropagateAtLaunch'] off a described group raises instead of reading a boolean, and the group's launch-time tag propagation is unknowable; a propagate-at-launch=false DescribeTags filter also cannot separate the tags.
Fix: apply the service default when the tag is stored (or when it is projected) so PropagateAtLaunch is always present on a TagDescription — in the CreateAutoScalingGroup/CreateOrUpdateTags tag-store path, not in the serializer.
Traces: autoscaling__ec2.asgeni-asg-tags-hold-unvalidated-ids-and-default-propagation.

Cause 4 of 5 — UpdateAutoScalingGroup's capacity-bound refusals use emulator-authored sentences.
AWS: HTTP 400, Error.Code ValidationError in both cases. MinSize above the effective MaxSize: Message 'Max bound, <max-size>, must be greater than or equal to min bound, <min-size>' — fixed text with the effective max and min (from the request, falling back to the stored group). DesiredCapacity outside [MinSize, MaxSize]: Message 'Desired capacity:<desired> must be between the specified min size:<min> and max size:<max>' — fixed text with the three numbers from the request/stored group, with no space after the colons. Smithy: UpdateAutoScalingGroup models only ResourceContentionFault, ScalingActivityInProgressFault and ServiceLinkedRoleFailure, so both refusals are the service-common ValidationError (sentences are recorded behavior only). Neither field is applied.
Emulator: the right status and Code but its own wording — 'The MinSize must be less than or equal to the MaxSize, but MinSize is <min> and MaxSize is <max>' and 'The DesiredCapacity must be between the MinSize and the MaxSize, but DesiredCapacity is <desired> and the range is [<min>, <max>]' (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/update_auto_scaling_group.rs lines 444-455).
Why: ValidationError is generic, so the message is the only machine-visible explanation of which bound was violated; a client or test matching AWS's sentence treats the refusal as an unknown failure, and the numbers appear in a different layout.
Traces: autoscaling__ec2.asgeni-asg-min-above-max-rejected, autoscaling__ec2.asgeni-asg-desired-above-max-rejected.

Cause 5 of 5 — SetDesiredCapacity's refusals echo the group name AWS does not echo.
AWS: HTTP 400, Code ValidationError. Unknown group: Message exactly 'AutoScalingGroup name not found - null' — entirely fixed text, the requested AutoScalingGroupName is NOT substituted (UpdateAutoScalingGroup on the same unknown group uses this same no-detail form, and the emulator gets that one right). DesiredCapacity above the group's MaxSize: Message 'New SetDesiredCapacity value <desired> is above max value <max> for the AutoScalingGroup.' — fixed text plus the two numbers, the sentence ending in a full stop with no group name appended. Smithy: SetDesiredCapacity models only ScalingActivityInProgressFault and ResourceContentionFault, so both are the common ValidationError (messages recorded behavior only).
Emulator: for the unknown group it reuses the shared echoing builder crate::state::absent_group_message and answers 'AutoScalingGroup name not found - AutoScalingGroup: <name> not found' (services/service-com-amazonaws-autoscaling-autoscaling-2011-01-01/src/ops/set_desired_capacity.rs line 189); for the above-max case it appends ': <name>' in place of AWS's full stop (same file, lines 202-206).
Why: a client cannot tell the two refusal shapes AWS actually serves apart, and an exact-match assertion or log scraper keyed to AWS's sentence never matches on a write path.
Related but not covering: open issue 20261029T211352Z-autoscaling-auto-scaling-client-error-refusals-diverge-emulator-authored.md records the same SetDesiredCapacity group-not-found wording as Cause 7 of 8 from the wire corpus; it carries none of the behavioral check ids above and its fix has not landed, so this cause is still open on the behavioral replay.
Traces: autoscaling__ec2.asgeni-unknown-asg-describes-empty-and-update-rejected (the above-max wording is additionally asserted by autoscaling__ec2.asgeni-asg-desired-above-max-rejected, which fails earlier in Cause 4).
