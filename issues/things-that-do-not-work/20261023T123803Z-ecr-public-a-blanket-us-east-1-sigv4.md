=== Cause 1 of 7: the us-east-1 Region gate is applied to EVERY operation and refuses the suite's default-region client, so 36 checks never reach the behavior they test ===
AWS: UnsupportedCommandException is a SERVICE-COMMON error in this model (smithy_query query="service_info" -> common_errors: [ServerException, UnsupportedCommandException]; errorKind client, httpError 400, documented "The action isn't supported in this Region"), and endpointResolution is an endpointRuleSet - so the model says any operation CAN be refused for a Region but says nothing about which Regions serve which operation. Recorded behavior is what fixes the scope, and it is asymmetric: exactly ONE check records a Region refusal - ecr-public.put-registry-catalog-data-unsupported-command-rejected, where PutRegistryCatalogData signed for us-west-2 is refused 400 UnsupportedCommandException, message example "PutRegistryCatalogData command is only supported in us-east-1." (that check PASSES against this emulator today, and the cause that produced it is the now-fixed issue 20261022T192707Z-ecr-public-putregistrycatalogdata-has-no-us-east-1.md). Against the same recorded account, 36 OTHER checks drive CreateRepository, DescribeRepositories, DeleteRepository, GetAuthorizationToken, InitiateLayerUpload, UploadLayerPart, CompleteLayerUpload, BatchCheckLayerAvailability, PutImage, DescribeImages, BatchDeleteImage, TagResource, ListTagsForResource, DescribeRegistries, GetRegistryCatalogData, PutRegistryCatalogData, PutRepositoryCatalogData, SetRepositoryPolicy and GetRepositoryPolicy through the suite's DEFAULT-region client (ctx.client("ecr-public") with no region= argument) and require them to SUCCEED (recorded behavior only). So the Region rule AWS enforces is NOT "every one of the 23 operations is refused outside us-east-1": the gate is narrower than the emulator's, and ecr-public.registry-catalog-display-name-round-trip-and-limit pins the contrast sharply - it round-trips PutRegistryCatalogData -> GetRegistryCatalogData through the DEFAULT-region client and must succeed, while the explicitly us-west-2-signed client in put-registry-catalog-data-unsupported-command-rejected must be refused.
Emulator: a single shared gate refuses ANY request whose SigV4 credential-scope Region is not exactly us-east-1, and every implemented handler calls it as its first statement before reading or writing anything. Through the suite's default-region client every one of those operations answers 400 UnsupportedCommandException with "<Operation> command is only supported in us-east-1."; the identical calls through a client pinned region="us-east-1" against the same endpoint and the same credentials are served normally. The 36 checks therefore abort on their first call (usually CreateRepository) and the behavior each one exists to grade - repository lifecycle, tagging, catalog data, policy, layer upload, image push, registry alias and response-shape fidelity - is never exercised at all.
Why: a client that targets ECR Public from any Region the service really does serve gets a blanket 400 on every call, i.e. the emulator is unusable for the whole ecr-public surface unless the caller hard-codes us-east-1; and because the refusal is a modeled client error, SDK retry/error handling treats it as a permanent caller fault. It also masks every other ecr-public defect behind one error, which is why this is CRITICAL rather than HIGH. Hypothesis: the gate was introduced to close the PutRegistryCatalogData Region cause and was then applied uniformly to all 23 operations instead of to the registry-catalog operation(s) the recording actually refuses.
Fix: the shared Region gate in the ecr-public state module (crate::state::unsupported_in_region) and the per-handler calls to it - it must be scoped to the operations/Regions the recordings refuse (the registry-catalog-data path) rather than run as the first statement of every handler, so the operations the suite's default-region client exercises are served.

=== Cause 2 of 7: PutImage accepts a manifest that references a layer digest never uploaded, instead of refusing with LayersNotFoundException ===
AWS: Smithy PutImage (input repositoryName required, imageManifest required @length 1..4194304, imageManifestMediaType, imageTag @length 1..300) models LayersNotFoundException (errorKind client, httpError 400) among its errors. A manifest whose layers[] names a digest that is not a completed layer of that repository is refused 400 LayersNotFoundException, NO image and NO tag is created, and the identical manifest pushed after the layer really is uploaded succeeds 200 (both checks carry that positive control in-file). Recorded behavior for the message, which is a fixed template built from the request - the missing digest list, the repository name and the registry id: an example is "Layers with digests '[sha256:<digest>]' required for pushing image into repository with name '<repo>' in the registry with id '<account>' do not exist".
Emulator: the push is ACCEPTED. PutImage answers HTTP 200 with a full image object (registryId, repositoryName, imageId.imageDigest, imageId.imageTag, imageManifest echoed, imageManifestMediaType) for a manifest whose single layer digest was confirmed NOT AVAILABLE by BatchCheckLayerAvailability immediately before the call, so the image and its tag are created over a dangling layer reference. No layer-existence check is performed at the push.
Why: this is an over-permissive accept at the commit point of the image data plane. A client pushing with a broken or partially failed layer upload sees success against the emulator and a 400 LayersNotFoundException against AWS, so the repair path (re-upload the missing blob, retry the manifest) is never exercised; worse, the registry ends up advertising an image that cannot be pulled, which for ECR Public is a world-visible broken image on the Gallery.
Fix: the PutImage handler must resolve every digest referenced by the submitted manifest (config and layers) against the repository's completed-layer state and return the modeled LayersNotFoundException, creating neither the image nor the tag, when any is absent. The now-fixed issue 20261022T154435Z-ecr-public-cfn-publicrepository-creates-nothing-putimage-accepts.md covered a different PutImage accept (malformed manifests) and does not carry the dangling-layer requirement.
Traces: ecr-public.put-image-missing-layer-rejected, ecr-public.e2e-put-image-missing-layers-rejected.

=== Cause 3 of 7: PutImage does not validate a manifest's embedded mediaType against the manifest's actual structure ===
AWS: Smithy PutImage models InvalidParameterException (errorKind client, httpError 400). A manifest whose own embedded "mediaType" declares it a manifest LIST (application/vnd.docker.distribution.manifest.list.v2+json, a schema that requires a "manifests" array) while the document structurally carries single-image members ("config" and "layers", no "manifests" at all) is refused 400 InvalidParameterException, and nothing is created under the requested tag (a following DescribeImages for that tag answers ImageNotFoundException). The same structural content declared consistently as application/vnd.docker.distribution.manifest.v2+json is accepted 200 (in-file positive control). Recorded behavior for the message; the recorded example is "Invalid parameter at 'ImageManifest' failed to satisfy constraint: 'Invalid JSON syntax'".
Emulator: the self-inconsistent manifest is ACCEPTED - HTTP 200 with the image stored under the requested tag and imageManifestMediaType echoed back as the manifest-list type, even though the stored document has no "manifests" member. No server-side schema validation of the manifest against its declared media type is performed.
Why: the registry is the only place this consistency can be enforced, and a client that relies on the rejection (a build pipeline that mislabels a single-image manifest as a multi-arch index) publishes an image that no runtime can resolve; against AWS the same push fails 400 and the pipeline stops.
Fix: the PutImage handler's manifest parsing/validation step must check the manifest's embedded mediaType against the members the document actually carries and return the modeled InvalidParameterException (400) for the mismatch, storing no image and no tag.
Traces: ecr-public.server-side-manifest-schema-validation-enforced.

=== Cause 4 of 7: UploadLayerPart's InvalidLayerPartException message does not use AWS's two-offset template (offset-gap leg, byte-exact ledger check) ===
AWS: Smithy UploadLayerPart's partFirstByte/partLastByte target PartSize (long, @range min 0, required) and the operation models InvalidLayerPartException (errorKind client, httpError 400), documented "The layer part size isn't valid, or the first byte specified isn't consecutive to the last byte of a previous layer part upload". A part whose partFirstByte is not the next byte after the last byte received is refused 400 InvalidLayerPartException; the message is built from the request and the upload's ledger as a fixed template over exactly the two offsets - observed first byte, then expected first byte. Recorded example: "First byte of the layer part is 1001 instead of 1000".
Emulator: the status 400 and the code InvalidLayerPartException are correct, and the byte-exact ledger legs that precede it (three contiguous parts reporting running lastByteReceived totals, CompleteLayerUpload hashing the concatenation, layerSize) all pass - but the message is a different template naming the upload id instead of rendering the two offsets in AWS's form, e.g. "The layer part beginning at byte '1001' is not consecutive to the last byte received for the upload with ID '<uuid>': the next layer part must begin at byte '1000'".
Why: the expected offset is what a resumable push client parses out of this message to continue; push logic written against the AWS template extracts nothing from the emulator's wording.
Fix: the UploadLayerPart handler's consecutiveness check must render the AWS template over the observed and expected first byte. This is the same root cause as cause 6 of the OPEN issue 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md; that issue does not carry this check's replay key (this check exercises it through the full three-part ledger), so it is recorded here and should close together with that cause.

=== Cause 5 of 7: CompleteLayerUpload's UploadNotFoundException message does not use AWS's template ===
AWS: Smithy CompleteLayerUpload (repositoryName, uploadId pattern ^[0-9a-fA-F]{8}-...-[0-9a-fA-F]{12}$ and layerDigests @length 1..100, all required) models UploadNotFoundException and LayerAlreadyExistsException (both errorKind client, httpError 400). When two completions race on one uploadId, at least one succeeds and every loser is refused as either UploadNotFoundException (the winner consumed the id) or LayerAlreadyExistsException; a sequential replay of the winning call answers UploadNotFoundException. Recorded behavior for the messages, both fixed templates built from the request - upload id, repository name, registry id: "The upload with id '<uploadId>' in the repository with name '<repo>' in registry with id '<account>' does not exist" and "Layer with upload id '<uploadId>' already exists in the repository with name '<repo>' in registry with id '<account>'".
Emulator: the loser is refused with the right code (UploadNotFoundException, 400) but a re-ordered, re-worded message - "The upload with ID '<uploadId>' does not exist for the repository with name '<repo>' in the registry with id '<account>'" - so the check's set-membership assertion over (code, message) fails and the convergence invariants after it (the blob stored exactly once, at exactly the uploaded size, and the uploadId consumed) are left unverified.
Why: a conformance or log-matching consumer pinned to the AWS wording of the registry clause does not match, and because the check aborts here the far more important property - that two concurrent completions converge on one stored blob - is still ungraded.
Fix: the CompleteLayerUpload handler's not-found (and already-exists) error construction must render the AWS templates. Cause 7 of the OPEN issue 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md records the same wording defect on UploadLayerPart's UploadNotFoundException; it does not carry the CompleteLayerUpload leg or this check's key.
