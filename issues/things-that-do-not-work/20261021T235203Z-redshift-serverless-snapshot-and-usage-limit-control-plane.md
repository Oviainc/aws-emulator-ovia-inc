# Redshift Serverless snapshot and usage-limit control plane: unimplemented operations and wrong ConflictException message on DeleteNamespace

> _Note: this issue was identified against the code base at commit `5939f31bbed4b1d4ad1ad30abce57388bc2dc3a9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSnapshot

## Description
Behavioral replay of trace set simparity-behavioral-aws-v1 against the booted emulator produced three distinct root causes in the redshift-serverless service (awsJson1_1, API version 2021-04-21, sdkId redshift-serverless). All THREE must be closed before this issue is resolved.

Cause 1 of 3 — CreateSnapshot (and the snapshot read path it feeds) is not implemented, so the namespace/compute coupling it must enforce is never evaluated. Failing check: redshift-serverless.snapshot-of-workgroupless-namespace-rejected.
AWS: Smithy com.amazonaws.redshiftserverless#CreateSnapshot takes namespaceName (@required) and snapshotName (@required) plus retentionPeriod and tags (TagList @length 0..200), returns CreateSnapshotResponse.snapshot (Snapshot), and models ConflictException(409), ResourceNotFoundException(404), ServiceQuotaExceededException(402), TooManyTagsException(400), ValidationException(400), InternalServerException(500). Recorded behavior: a snapshot is taken through the compute attached to a namespace, so CreateSnapshot against an AVAILABLE namespace that has NO workgroup is REJECTED with error code ResourceNotFoundException (the 404-status modeled error), the rejection creates nothing (ListSnapshots scoped to that namespaceName returns an empty snapshots list), and the identical CreateSnapshot call then SUCCEEDS once a workgroup on that namespace reaches AVAILABLE, returning snapshot.namespaceName equal to the namespace and appearing in ListSnapshots(namespaceName=...). The message observed on the rejection is an example: "You can't create a snapshot because there isn't a workgroup created for the namespace."
Emulator: CreateSnapshot answers with error code 'NotImplemented' ("operation ... is scaffolded but not implemented in this emulator") for every input, so neither the workgroupless rejection nor the positive control is reachable, and no snapshot state exists to list.
Why: a client cannot snapshot a namespace at all, and a client that relies on the rejection to discover that a namespace has no compute sees an unmodeled error code that no SDK error-matching branch handles (it is not in the operation's modeled error set), so backup/restore orchestration against the emulator neither succeeds nor fails in a way it can interpret.
Fix: the CreateSnapshot handler in the redshift-serverless service crate, plus the snapshot state it must keep and the ListSnapshots/GetSnapshot read path over it — implement the operation, raise the 404-status ResourceNotFoundException when the named namespace has no attached workgroup, persist nothing on that path, and record a Snapshot bound to the namespace on the accepted path.
Traces: redshift-serverless.snapshot-of-workgroupless-namespace-rejected.

Cause 2 of 3 — CreateUsageLimit does not resolve the workgroup ARN it is given (the operation answers NotImplemented), so a well-formed ARN naming no workgroup is not rejected. Failing check: redshift-serverless.usage-limit-on-absent-workgroup-arn-rejected.
AWS: Smithy CreateUsageLimit takes resourceArn (@required), usageType (UsageLimitUsageType, @required), amount (Long, @required), period (UsageLimitPeriod), breachAction, returns CreateUsageLimitResponse.usageLimit, and models ConflictException(409), ResourceNotFoundException(404), ServiceQuotaExceededException(402), ValidationException(400), InternalServerException(500). Recorded behavior: given a resourceArn that is structurally correct for this account/region/partition but whose workgroup id does not exist, the service answers error code ValidationException (400) — NOT the ResourceNotFoundException the model also declares for this operation — creates nothing (ListUsageLimits on the real workgroup ARN stays empty), and accepts the same request against an ARN that does resolve, returning usageLimit.resourceArn equal to the ARN and a usageLimitId that then appears in ListUsageLimits. Recorded message, as an example: "The Resource ARN is not valid as the workgroup ID <workgroup-uuid>."
Emulator: CreateUsageLimit answers error code 'NotImplemented' for both the absent-ARN request and the positive control, so no ARN resolution is performed and no usage-limit state is kept.
Why: a client that provisions spend guardrails gets an unmodeled failure for every request; worse, code written against AWS branches on ValidationException to detect a stale/incorrect workgroup ARN and on success to confirm the guardrail is in place, and neither branch is ever taken.
Note on overlap: the replay report already filed a scaffold issue naming the unimplemented operation CreateUsageLimit and its handler file services/service-com-amazonaws-redshiftserverless-redshiftserverless/src/ops/create_usage_limit.rs (it blocks redshift-serverless.usage-limit-survives-workgroup-provisioning, which is NOT re-filed here). That issue covers standing the operation up; this cause additionally fixes the behavior the check asserts — ARN existence resolution answering the 400-status ValidationException and creating nothing on that path. Close it together with that scaffold issue, not instead of it.
Fix: the CreateUsageLimit handler and its input validation in the redshift-serverless service crate, plus the usage-limit state ListUsageLimits reads — resolve resourceArn against workgroup state and raise the 400-status ValidationException when it names no workgroup, leaving usage-limit state unchanged.
Traces: redshift-serverless.usage-limit-on-absent-workgroup-arn-rejected.

Cause 3 of 3 — DeleteNamespace blocked by an attached workgroup returns the right status and error code but not the message AWS builds for it. Failing check: redshift-serverless.namespace-delete-rejected-while-workgroup-attached.
AWS: Smithy DeleteNamespace takes namespaceName (NamespaceName, @required, @length 3..64, @pattern "^[a-z0-9-]+$") and models ConflictException(409), ResourceNotFoundException(404), ValidationException(400), InternalServerException(500). Recorded behavior: deleting a namespace while a workgroup is attached is rejected with error code ConflictException, and the message is a fixed template interpolating the blocking workgroup's name: "Delete the associated workgroup <workgroupName> before you delete the namespace." The rule — ConflictException whose message instructs the caller to delete the named attached workgroup first — is what is recorded; it is state-derived and deterministic, not an opaque server string.
Emulator: the error code and status are correct (ConflictException), but the message is a different sentence, observed as "namespace <ns> still has workgroups attached: <wg>".
Why: this is the narrowest cause in the bundle (code and status already match), but the dependency-ordering rejection is the one every teardown of this service depends on, and callers/tests that assert the AWS-documented remediation sentence — or surface it to an operator — see different text. It also blocks the rest of this check (the rejected delete leaving the namespace and workgroup AVAILABLE, and the positive control where the same DeleteNamespace succeeds once the workgroup is gone) from ever being exercised, so those behaviors are unverified until the message matches.
Fix: the DeleteNamespace handler's attached-workgroup conflict path in the redshift-serverless service crate — emit the ConflictException message in the recorded form, naming the attached workgroup.
Traces: redshift-serverless.namespace-delete-rejected-while-workgroup-attached.

Exising-issue survey: the only open redshift-adjacent issues are the bootstrap issues for the separate 'redshift' and 'redshift-data' services (different services), the scaffold issue for CreateUsageLimit noted in Cause 2, and "Redshift Serverless namespace responses and error mapping diverge from AWS" (20261021T233729Z-redshift-serverless-namespace-responses-and-error-mapping-diverge.md), which is a WIRE issue scoped to CreateNamespace/GetNamespace response shape, creationDate format and the duplicate-name / absent-namespace status mapping. It names none of the three causes above (CreateSnapshot, CreateUsageLimit, DeleteNamespace conflict message) and does not cover them.
