# elbv2: 4 net-new data-plane causes — desync_mitigation_mode is inert, weighted/zero-weight forwarding and AWSALBTG stickiness never route, and the ALB→Lambda request/response contract is never produced

> _Note: this issue was identified against the code base at commit `6da489cbc4c2969d809761cd42ffd786edefa992`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyListener

## Description
Four net-new ELBv2 data-plane root causes, all exercised with `lambda`-type target groups (the one target type this process can serve in-process, so none of them needs egress to a foreign address). Each is independent and must be closed separately. None of the four failing checks is marked ALREADY FILED or OWNED by the replay report. The adjacent open issue 20261104T094656Z-elbv2-seven-target-health-routing-and-data-plane-causes-still-open.md (cause 9) records that the forward path answers nothing for instance/ip targets and names `src/service/data_plane.rs` as the serving seam; it does NOT carry any of the four replay keys below and does not cover the attribute-, weight-, stickiness- or Lambda-contract semantics described here.

Cause 1 of 4 — routing.http.desync_mitigation_mode is not enforced on the request path (ModifyLoadBalancerAttributes + the HTTP listener).
AWS: Smithy: LoadBalancerAttribute.Key documents `routing.http.desync_mitigation_mode` — "Determines how the load balancer handles requests that might pose a security risk to your application. The possible values are monitor, defensive, and strictest. The default is defensive." Recorded behavior: with the attribute set to `monitor`, a POST whose framing is ambiguous (both Content-Length and Transfer-Encoding present) is FORWARDED and the target's own response is returned (200 with the target body); with the attribute set to `strictest`, the identical request is answered by the load balancer itself with the status line `HTTP/1.1 400 Bad Request` and the target is NOT invoked, while a compliant POST on the same listener in the same instant still returns 200 with the target body. Restoring `monitor` makes the identical ambiguous request succeed again. The 400 body is generated by the load balancer, not proxied from the target.
Emulator: the check never observes any of the three legs — it exhausts the harness budget ("Check timed out after 60.0s") while polling for the first leg (the load balancer forwarding a compliant raw POST to its Lambda target). Nothing on the request path distinguishes ambiguous from compliant framing, and the stored attribute has no effect on what the listener answers.
Why: a client relying on AWS's desync mitigation sees request smuggling/desync protection as configured-but-inert: a request AWS refuses with 400 before the target runs is either forwarded or never answered at all, so security tests of `strictest` pass or hang instead of observing the refusal, and the mode is indistinguishable from `monitor`.
Fix: the ELBv2 HTTP data plane — request framing validation on the serving seam (services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10/src/service/data_plane.rs), reading the load balancer's stored `routing.http.desync_mitigation_mode` and answering 400 Bad Request from the load balancer for ambiguously framed requests under `strictest` without invoking the target.
Traces: elbv2.desync-mitigation-strictest-blocks-ambiguous-framing-before-the-target.

Cause 2 of 4 — a weighted forward never reaches both target groups and TargetGroupStickinessConfig never mints an AWSALBTG cookie.
AWS: Smithy: ForwardActionConfig carries `TargetGroups` (list of TargetGroupTuple{TargetGroupArn, Weight}, "The weight. The range is 0 to 999") and `TargetGroupStickinessConfig{Enabled, DurationSeconds}` ("[Application Load Balancers] The time period, in seconds, during which requests from a client should be routed to the same target group"). Recorded behavior: a 1:1 weighted forward over two target groups round-trips through DescribeListeners with both weights intact and, sampled over many requests, reaches BOTH groups; with stickiness disabled no `AWSALBTG` Set-Cookie is emitted; with `TargetGroupStickinessConfig{Enabled: true, DurationSeconds: 3600}` the ALB mints an `AWSALBTG` cookie and replaying that cookie pins every subsequent request to the one group that answered first.
Emulator: the check exhausts the harness budget ("Check timed out after 60.0s") before any of those observations: the weighted forward never serves a response from either Lambda target, so neither the 1:1 spread, the absence of AWSALBTG when stickiness is off, nor the minting/pinning of AWSALBTG when it is on is ever produced.
Why: blue/green and canary clients that shift traffic by target-group weight, and any client that depends on target-group stickiness, get no traffic distribution at all and no stickiness cookie — a weighted forward is accepted by the control plane but means nothing on the wire.
Fix: the forward action in the ELBv2 data plane — weighted selection across ForwardConfig.TargetGroups and the AWSALBTG target-group stickiness cookie (mint on response, honor on request) in the same serving seam.
Traces: elbv2.forward-weighted-and-sticky-target-groups-data-plane.

Cause 3 of 4 — a zero-weight target group is not excluded, and ModifyListener with every weight 0 is not refused.
AWS: Smithy: TargetGroupTuple.Weight range 0-999. Recorded behavior: with weights 1/0 every request is served by the weight-1 group (20 of 20 responses carry only that group's body) and the weight-0 group is never selected; with 0/1 the mirror holds. ModifyListener whose forward action sets EVERY target group's weight to 0 is refused with error code `ValidationError`, and the refused change does not reach the listener — DescribeListeners still reports the previous weights and the listener keeps serving the surviving configuration.
Emulator: the check exhausts the harness budget ("Check timed out after 60.0s") while waiting for the 1/0 configuration to serve a body, so neither the exclusion of the zero-weight group, the `ValidationError` refusal of the all-zero weighting, nor the effect-absent check on the stored weights is ever reached.
Why: a client that disables a target group by zeroing its weight cannot verify the group is drained, and an all-zero forward — a configuration AWS refuses outright with ValidationError — is not refused, so a listener can be left with no selectable target group.
Fix: weighted target-group selection in the data plane (weight 0 excluded from selection) and ModifyListener/CreateRule request validation refusing a forward action whose target-group weights are all 0 with `ValidationError`, leaving the stored action unchanged.
Traces: elbv2.zero-weight-target-group-is-never-selected.

Cause 4 of 4 — the ALB→Lambda request/response contract is never produced (event shape, response mapping, lambda.multi_value_headers.enabled).
AWS: Smithy: TargetGroupAttribute.Key includes `lambda.multi_value_headers.enabled`; RegisterTargets accepts a Lambda function ARN for a `lambda`-type target group. Recorded behavior: the ALB invokes the Lambda target with the ALB event shape — `httpMethod`, `path`, `queryStringParameters`, `headers` with request header names LOWER-CASED, `isBase64Encoded: false`, and `requestContext.elb.targetGroupArn` equal to the target group's ARN — and maps the function's returned object onto the HTTP response: `statusCode` becomes the HTTP status (e.g. 201 surfaces as 201), returned `headers` are emitted as response headers (including Content-Type), and a body returned with `isBase64Encoded: true` is base64-DECODED onto the wire. With the target group attribute `lambda.multi_value_headers.enabled` = `true`, the event switches to the multi-value key shape: `multiValueQueryStringParameters` and `multiValueHeaders` are present with list values and the single-value `queryStringParameters`/`headers` keys are ABSENT.
Emulator: the check exhausts the harness budget ("Check timed out after 60.0s") while polling for the ALB to return the handler's JSON echo, so no event is ever delivered to the function through the listener and none of the response mapping or the multi-value switch is observable.
Why: every client that fronts a Lambda function with an ALB — the whole serverless-behind-ALB pattern — gets no invocation at all: the function never sees the ALB event, the returned statusCode/headers/base64 body never reach the client, and the multi_value_headers attribute is stored but changes nothing.
Fix: the `forward`-to-`lambda`-target path of the ELBv2 data plane — build the ALB event from the request (lower-cased header names, query parsing, requestContext.elb), invoke the registered function in-process through the Lambda service, validate and map the returned statusCode/headers/body/isBase64Encoded onto the HTTP response, and select the single- vs multi-value event shape from the target group's stored `lambda.multi_value_headers.enabled`.
Traces: elbv2.lambda-target-request-response-contract.
