# ACM certificate read projections omit and mis-name modeled response fields (4 causes)

> _Note: this issue was identified against the code base at commit `8d5a4f803a514b21e009b483e221bcf8b3c8087d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCertificate

## Description
Four distinct root causes in how the ACM emulator projects certificate state onto the read operations (ListCertificateDomainValidations, DescribeCertificate, SearchCertificates). Every leg below answered HTTP 200 — the status and envelope are right and only the body diverges, so no client sees an error; it silently reads the wrong fields. Related open filings, neither of which carries any of these fixture steps as a replay key: 20261022T143245Z-acm-certificate-representation-dns-validation-and-error-message.md (behavioral corpus; its cause 1 covers the DescribeCertificate projection of Options/ValidationDomain/KeyAlgorithm for AMAZON_ISSUED certificates, not the four causes here) and 20261022T122353Z-acm-describecertificate-omits-modeled-certificate-metadata-and-mis-forms.

Cause 1 of 4: ListCertificateDomainValidations populates ActiveValidationConfiguration instead of RequestedValidationConfiguration, and fills in a DNS challenge record that is not served by this operation.
AWS: Smithy DomainValidationSummary{DomainName required, ActiveValidationConfiguration: ValidationConfiguration, RequestedValidationConfiguration: ValidationConfiguration}; ValidationChallenge is a union{EmailValidationChallenge, DnsValidationChallenge} and DnsValidationChallenge{ResourceRecord}. Recorded behavior: for a certificate requested with ValidationMethod DNS and still PENDING_VALIDATION, every element of DomainValidationSummaryList carries exactly DomainName plus RequestedValidationConfiguration{ValidationMethod: 'DNS', ValidationStatus: 'PENDING_VALIDATION', ValidationChallenge: {DnsValidationChallenge: {}}} — the DnsValidationChallenge is an EMPTY structure (no ResourceRecord) and ActiveValidationConfiguration is absent. One summary per name in the certificate (apex plus each SAN), in the order the names were requested.
Emulator: each summary carries ActiveValidationConfiguration instead, with the same ValidationMethod/ValidationStatus but with DnsValidationChallenge.ResourceRecord populated ({Name, Type: 'CNAME', Value}).
Why: a client that reads summary['RequestedValidationConfiguration'] — the member AWS populates while a request is pending — gets None/KeyError, so the per-domain validation method and status are invisible through this operation; and a client that takes the CNAME from here publishes a record real ACM never serves at this member (the authoritative record is DescribeCertificate's DomainValidationOptions[*].ResourceRecord), so validation automation keyed on this operation diverges in both directions.
Fix: the ListCertificateDomainValidations response projection in the ACM service crate — the DomainValidationSummary serializer must emit RequestedValidationConfiguration for a pending request and emit DnsValidationChallenge with no ResourceRecord member.
Traces: acm-certificate-dns-lifecycle#task#2, acm-certificate-domain-validation-and-tagging#task#3, acm-multi-domain-certificate-validations#task#2 (16 further steps in those three clusters, including the paginated fixture acm-domain-validations-pagination).

Cause 2 of 4: DescribeCertificate synthesizes ValidationEmails for an EMAIL-validated certificate that ACM has not mailed.
AWS: Smithy DomainValidation.ValidationEmails (ValidationEmailList) is documented as 'A list of email addresses that ACM used to send domain validation emails.' Recorded behavior: immediately after RequestCertificate(ValidationMethod='EMAIL') the DescribeCertificate projection's DomainValidationOptions[0] carries NO ValidationEmails member at all — nothing has been mailed yet, so the member is omitted rather than pre-filled.
Emulator: DomainValidationOptions[0].ValidationEmails is present with the five canonical administrative local-parts (admin@, administrator@, hostmaster@, postmaster@, webmaster@) at the certificate's validation domain, generated from the domain name rather than recorded from any dispatch.
Why: the member's meaning is 'addresses ACM used', so a client that shows the operator who was contacted lists five addresses that were never contacted, and a client that waits for the member to appear before offering ResendValidationEmail treats an undispatched request as dispatched — the same gate whose refusal is bundled as cause 4 of the control-plane refusal issue.
Fix: the DescribeCertificate / CertificateDetail projection for EMAIL validation — populate ValidationEmails only from recorded dispatch state, do not derive it from the domain.
Traces: acm-certificate-email-with-inline-tags#task#2.

Cause 3 of 4: the IMPORTED-certificate projection drops CreatedAt and DomainValidationOptions and defaults certificate-transparency logging to ENABLED.
AWS: Smithy CertificateDetail declares CreatedAt (TStamp, 'The time at which the certificate was requested'), DomainValidationOptions (DomainValidationList) and Options (CertificateOptions{CertificateTransparencyLoggingPreference, Export, ValidationMethod}). Recorded behavior: after ImportCertificate, DescribeCertificate returns CreatedAt set to the import time (epoch seconds with millisecond precision), a DomainValidationOptions list with one entry carrying ONLY DomainName (the certificate's subject common name — no ValidationStatus, no ResourceRecord, since an imported certificate is never validated by ACM), and Options.CertificateTransparencyLoggingPreference 'DISABLED' — ACM does not CT-log a certificate it did not issue.
Emulator: CreatedAt is absent, DomainValidationOptions is absent entirely, and Options.CertificateTransparencyLoggingPreference is 'ENABLED'.
Why: a client that ages, sorts or reconciles certificates by CreatedAt sees None for every imported certificate (sorting it arbitrarily or raising on the comparison); a client that iterates DomainValidationOptions to learn the names on a certificate gets nothing for imported certificates; and a CT-logging audit reports an imported certificate as publicly logged when ACM reports it as not logged — the inverted value is worse than a missing one because it reads as a definite answer.
Fix: the CertificateDetail projection plus the ImportCertificate state it reads — record the import timestamp as CreatedAt, derive the single DomainValidationOptions entry from the imported subject, and default the CT preference to DISABLED when Type is IMPORTED.
Traces: acm-certificate-list-and-search-error-paths#task#2 (an 11-step cluster spanning the import, re-import, tag-lifecycle, options-toggle and revoke fixtures).

Cause 4 of 4: SearchCertificates omits AcmCertificateMetadata.CreatedAt from every result.
AWS: Smithy AcmCertificateMetadata.CreatedAt (TStamp, 'The time at which the certificate was requested'); SearchCertificatesRequest.SortBy defaults to CREATED_AT and SortOrder to ASCENDING. Recorded behavior: each Results[*].CertificateMetadata.AcmCertificateMetadata carries CreatedAt as epoch seconds.
Emulator: that member is absent (None) while the rest of the metadata matches.
Why: CREATED_AT is the operation's own default sort key, so a client cannot read, render or verify the value the page is ordered by, and cannot implement its own stable tie-breaking or 'created since' filtering on the search path even though the same value is required on the describe path (cause 3).
Fix: the SearchCertificates result projection (the AcmCertificateMetadata serializer) reading the same certificate creation timestamp cause 3 needs stored.
Traces: acm-search-certificates-workflow#task#2.
