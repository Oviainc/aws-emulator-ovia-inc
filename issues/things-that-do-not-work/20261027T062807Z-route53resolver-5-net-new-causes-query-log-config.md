Cause 1 of 5: AssociateResolverQueryLogConfig re-associating the SAME config with the SAME VPC is refused with the wrong error code and wrong message.
AWS: Smithy: AssociateResolverQueryLogConfig(ResolverQueryLogConfigId: ResourceId @length 1..64 required, ResourceId: ResourceId @length 1..64 required) models both InvalidRequestException and ResourceExistsException at HTTP 400; the model states no message text. Recorded behavior: associating a (config, VPC) pair that is already associated answers HTTP 400 with error code InvalidRequestException and message '[RSLVR-01303] The specified resource is already associated with the specified query logging configuration.' — that message is ENTIRELY fixed text: it interpolates neither the config id, nor the VPC id, nor the association id. Route 53 Resolver appends its per-request ' Trace Id: "..."' suffix, which is a per-run value and not part of the requirement.
Emulator: HTTP 400 with code ResourceExistsException and message 'Resolver query log config "<config-id>" is already associated with VPC "<vpc-id>" by association "<assoc-id>"' — a different modeled error shape, no [RSLVR-nnnnn] code, service-invented prose, and three interpolated ids AWS never includes.
Why: Resolver answers HTTP 400 for every modeled error, so the error code plus the bracketed RSLVR code are the only discriminators available. A client that catches InvalidRequestException (or matches '[RSLVR-01303]') to treat a duplicate associate as already-done instead sees ResourceExistsException, so its idempotency branch never fires and the call surfaces as an unhandled failure; botocore's r53r.exceptions.InvalidRequestException handler is dead against the emulator.
Fix: the duplicate-pair branch of the operation's handler — services/service-com-amazonaws-route53resolver-route53resolver/src/ops/associate_resolver_query_log_config.rs:199-215 — must raise the InvalidRequestException variant with the RSLVR-01303-coded fixed sentence built through the existing crate::state::rslvr_message helper, and stop interpolating the ids. The rest of the branch (nothing written, association count unchanged) is already correct.
Traces: route53resolver.associate-resolver-query-log-config-duplicate-rejected.

Cause 2 of 5: AssociateResolverQueryLogConfig does not refuse a VPC that is already associated with a DIFFERENT query logging configuration of the same destination type — it accepts the call and creates a second association.
AWS: Smithy: same operation as Cause 1; InvalidRequestException at HTTP 400 ('The request is invalid.'). Recorded behavior: a VPC can have at most one active query logging configuration per destination type, so associating a second config (destination type CloudWatch Logs, when the VPC already has an active CloudWatch Logs association) is refused with HTTP 400, code InvalidRequestException and the fixed-text message '[RSLVR-01306] The resource is already associated with a query logging configuration that is sending query logs to the specified destination type.' No association is created; after the first association is removed, the identical call succeeds.
Emulator: the call returns HTTP 200 with a newly minted ResolverQueryLogConfigAssociation in status CREATING for the second config, so the VPC ends up carrying two associations. The handler validates only that the config exists and that THAT config does not already hold the VPC (associate_resolver_query_log_config.rs:180-215); there is no cross-config, per-VPC, per-destination-type check anywhere.
Why: this is an overly-permissive accept. A client that provisions query logging for a VPC relies on AWS to reject the conflicting second config; against the emulator it silently ends up with two configs claiming the same VPC, so logging-ownership logic, migration flows (which expect to have to disassociate first) and anything listing a VPC's associations diverge, and no error is ever surfaced.
Fix: the same handler needs a pre-write validation step that, before minting a record, scans all configs for an existing non-deleting association on input.resource_id whose destination type matches the requested config's (the destination type is derivable from the stored DestinationArn in crate::state), and refuses with InvalidRequestException carrying the RSLVR-01306 fixed sentence.
Traces: route53resolver.associate-resolver-query-log-config-vpc-already-associated-rejected.

Cause 3 of 5: CreateResolverQueryLogConfig accepts a DestinationArn naming a CloudWatch Logs log group that does not exist.
AWS: Smithy: CreateResolverQueryLogConfig(Name required, DestinationArn: DestinationArn @length 1..600 required, CreatorRequestId required) models AccessDeniedException at HTTP 400 ('The current account doesn't have the IAM permissions required to perform the specified Resolver operation.'); the model bounds DestinationArn's length only. Recorded behavior (wire/route53resolver/query-log-config-missing-resource-errors.json step 3): a well-formed log-group ARN for a log group that was never created is refused with HTTP 400, code AccessDeniedException and the fixed-text message '[RSLVR-01600] Access denied' — no part of it is variable. No configuration is stored in any status, so a subsequent ListResolverQueryLogConfigs filtered on that Name returns an empty list with TotalFilteredCount 0.
Emulator: HTTP 200, a config is created and stored (Status CREATING, DestinationArn canonicalised correctly) for a log group that does not exist. src/ops/create_resolver_query_log_config.rs:206-213 checks only crate::state::query_log_destination_is_wellformed — the ARN's SHAPE — and never asks CloudWatch Logs whether the named log group exists.
Why: another overly-permissive accept. Customers rely on this call failing fast when the destination is missing or unreadable; against the emulator a typo'd or not-yet-created log group yields a config that looks healthy forever, so the whole negative path (and the resources it should not have left behind) is untested and client remediation code never runs.
Fix: the destination validation in that handler must, for an arn:aws:logs:...:log-group:<name>[:*] destination, resolve <name> against the emulator's CloudWatch Logs state and refuse a missing one with AccessDeniedException carrying the RSLVR-01600 fixed sentence, before anything is written. The existing wildcard-stripping canonicalisation (crate::state::canonical_query_log_destination) is correct and must not change.
Traces: route53resolver.resolver-query-log-config-bad-destination-rejected.

Cause 4 of 5: PutResolverQueryLogConfigPolicy is an unimplemented scaffold stub, so it answers 501 NotImplemented instead of validating the policy and storing it.
AWS: Smithy: PutResolverQueryLogConfigPolicy(Arn @length 1..255 required, ResolverQueryLogConfigPolicy @length 0..30000 required) -> ReturnValue: Boolean required; models InvalidRequestException, InvalidPolicyDocument, AccessDeniedException, InvalidParameterException, UnknownResourceException, InternalServiceErrorException, all at HTTP 400. Recorded behavior: a policy document that is not parseable JSON (e.g. '{not valid json') is refused with HTTP 400, code InvalidRequestException and the fixed-text message '[RSLVR-00312] The specified IAM policy for sharing a query logging configuration with another AWS account is invalid.'; no policy is attached afterwards, so GetResolverQueryLogConfigPolicy for that ARN answers 400 AccessDeniedException '[RSLVR-01600] Access denied'. A well-formed policy is accepted with ReturnValue true and round-trips through Get with its Statement[].Resource preserved.
Emulator: HTTP 501 with code NotImplemented for every call. services/service-com-amazonaws-route53resolver-route53resolver/src/ops/put_resolver_query_log_config_policy.rs still carries the '//! SCAFFOLDED, NOT IMPLEMENTED' marker and its handle body is the generated Err(crate::scaffolded::Scaffolded::not_implemented("PutResolverQueryLogConfigPolicy")).
Why: cross-account sharing of a query logging configuration cannot be exercised at all, and the 501 is not a modeled error, so SDK clients see an unmodeled failure rather than any of the six errors they are written to handle.
Fix: implement the handler in that one file — parse and validate the policy document, refuse a non-JSON document with InvalidRequestException/RSLVR-00312, store the policy on the configuration named by Arn in crate::state, return ReturnValue true, and delete the SCAFFOLDED marker line. The companion read path (GetResolverQueryLogConfigPolicy, which must answer AccessDeniedException '[RSLVR-01600] Access denied' when no policy is attached) is covered by its own auto-filed stub issue and must agree with whatever this handler stores.
Traces: route53resolver.put-resolver-query-log-config-policy-invalid-policy-rejected.

Cause 5 of 5: AssociateResolverRule's duplicate-association refusal message omits '[RSLVR-00704] ' and adds text AWS does not produce.
AWS: Smithy: AssociateResolverRule(ResolverRuleId required, Name, VPCId required) models ResourceExistsException at HTTP 400. Recorded behavior: re-associating a rule with a VPC it is already associated with answers HTTP 400, code ResourceExistsException (which the emulator already gets right) and message '[RSLVR-00704] Resolver rule "<rule-id>" is already associated with VPC "<vpc-id>".' Fixed text: '[RSLVR-00704] Resolver rule "' ... '" is already associated with VPC "' ... '".'; the two variable parts are ResolverRuleId and VPCId taken verbatim from the request. AWS does NOT name the existing association id and the sentence ends with a period.
Emulator: 'Resolver rule "<rule-id>" is already associated with VPC "<vpc-id>" by association "<assoc-id>"' — no RSLVR code, an extra ' by association "<id>"' clause carrying an emulator-minted id, and no terminating period. Built inline at src/ops/associate_resolver_rule.rs:190-203.
Why: same discriminator problem as the already-fixed rule bodies — with every Resolver fault at HTTP 400, the bracketed RSLVR code inside Error.Message is what clients, log pipelines and operators key on; a matcher anchored on '[RSLVR-00704]' or on the message as a whole never matches, and the surfaced text mentions an association id AWS never returns here.
Fix: route that message through the existing crate::state::rslvr_message helper with a new RSLVR-00704 constant beside the existing RSLVR_CODE_* ones (state.rs), interpolating only the rule id and the VPC id, and drop the ' by association ...' clause. The status, the ResourceExistsException variant, resource_type: ResolverRuleAssociation and the write-nothing behaviour are already correct.
Traces: route53resolver.associate-resolver-rule-duplicate.
