# sesv2__sns__sqs: SES publishes no events to an SNS event destination (Enabled is never consulted, no Send event is ever emitted), and CreateEmailTemplate is an unimplemented 501 stub

> _Note: this issue was identified against the code base at commit `2e41c53f62212c879ccde9aca1b2ab6c6cf6a645`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SendEmail, CreateEmailTemplate

## Description
Two distinct root causes in the SESv2 -> SNS -> SQS event-publication slice. BOTH must be closed before submitting; each is numbered with its own grounding checks.

=== Cause 1 of 2: SendEmail never publishes an SES event to the configuration set's SNS destination ===
AWS: Smithy (services/service-com-amazonaws-sesv2-simpleemailservice-v2/smithy-model/com-amazonaws-sesv2-simpleemailservice-v2.json) models SendEmail (POST /v2/email/outbound-emails) returning 200 with MessageId, and EventDestinationDefinition.SnsDestination -> SnsDestination {TopicArn (required)}, "An object that defines an Amazon SNS destination for email events. You can use Amazon SNS to send notifications when certain email events occur"; EventDestinationDefinition.Enabled is documented as the switch that turns the destination on and off. Recorded behavior: for a send through a configuration set holding an Enabled=true SnsDestination whose MatchingEventTypes include SEND, SES publishes one JSON event per matching event to the topic — the object carries eventType "Send", mail.messageId equal to the MessageId SendEmail returned, mail.source equal to the sender, and mail.headers / mail.commonHeaders describing the message as sent (for a Content.Raw send, the caller's headers appear in the order and casing written, with their values byte-exact, among whatever headers SES adds). With Enabled=false SES publishes NOTHING for a send that would otherwise produce events, and flipping the SAME destination back to Enabled=true (UpdateConfigurationSetEventDestination) makes the next send publish its Send event again.
Emulator: nothing is ever published, so neither the positive nor the negative leg can be observed. CreateConfigurationSetEventDestination only stores the destination record (src/ops/create_configuration_set_event_destination.rs lines 211-214) and SendEmail (src/ops/send_email.rs lines 290-345) settles the clock, gates on the sender identity and the 24h quota and appends a SentMessage to the in-memory outbound log — it never reads the configuration set's event_destinations, never looks at Enabled or MatchingEventTypes, and emits no event anywhere. Both grounding checks therefore sit in a bounded SQS drain (ReceiveMessage with WaitTimeSeconds=10, own budgets 120s) that never sees a message, and the suite reports "Check timed out after 60.0s" for each instead of a value comparison.
Why: SES event publication is the only way a client learns what happened to a message (Send, Delivery, Bounce, Complaint, Rendering Failure). Against the emulator every topic and queue stays empty forever while the control plane reports a healthy Enabled destination, so no bounce/complaint handling, no delivery accounting and no header-fidelity assertion can be exercised; worse, because the Enabled flag is never read, an emulator that later starts publishing unconditionally would also be wrong in the opposite direction (the negative leg of the disabled check is the one that catches it).
Fix: SendEmail's handler plus the event-destination state it must read (src/ops/send_email.rs and the configuration_sets / EventDestinationRecord store in src/state.rs) — on an accepted send, for each event destination of the named configuration set whose Enabled is true and whose MatchingEventTypes select the event, build the SES event object (eventType, mail.messageId from the minted MessageId, mail.source, mail.headers and mail.commonHeaders derived from the message actually sent, including the raw MIME document's headers for a Content.Raw send) and deliver it to the destination (here, publish to the SNS topic through the emulator's sns slice); publish nothing when Enabled is false.
Traces: sesv2__sns__sqs.event-destination-disabled-publishes-no-events, sesv2__sns__sqs.send-raw-email-preserves-custom-headers-exactly-in-the-published-event.

=== Cause 2 of 2: CreateEmailTemplate is an unimplemented scaffold stub, so templated sends cannot be set up at all ===
AWS: Smithy binds CreateEmailTemplate to POST /v2/email/templates with input {TemplateName (required), TemplateContent (required), Tags} and modelled errors AlreadyExistsException (400), BadRequestException (400), LimitExceededException (400), TooManyRequestsException (429) — no 501 in the contract; a successful create answers 200 with an empty body and the template becomes usable by SendEmail's Content.Template.
Emulator: every call is refused with Code 'NotImplemented' and the message "operation CreateEmailTemplate is scaffolded but not implemented in this emulator". The check dies on its first setup call, so the behavior it exists to grade (a templated send whose rendering data omits a variable the template references is accepted synchronously with a MessageId and fails later as an asynchronous Rendering Failure event on the configuration set's SNS destination, never as a synchronous error) is never reached.
Why: no client can create an email template, so the entire templated-send surface — and the asynchronous rendering-failure contract that is the only signal a bad template/data pair produces — is unreachable, and the client gets a status outside the operation's modelled error set that SDK error handling cannot act on.
Fix: implement the handler in services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/create_email_template.rs over the template state in src/state.rs (AlreadyExistsException on a duplicate TemplateName, BadRequestException on invalid TemplateContent, otherwise store and answer 200) and drop the SCAFFOLDED marker. Note for the fixer: this is the same unimplemented operation the auto-filed sesv2 CreateEmailTemplate scaffold-stub issue names (raised from sesv2.email-template-lifecycle); it is recorded here because the sesv2__sns__sqs check above carries its own replay key and is not covered by that issue. Confirming this cause needs the templated-send check re-replayed, which additionally depends on Cause 1.
Traces: sesv2__sns__sqs.templated-send-with-missing-variable-publishes-rendering-failure.

Neighbouring filed work: the open issues 20261026T024515Z-sesv2-sns-sqs-all-four-remaining-ses-event.md and 20261025T220900Z-sesv2-sns-sqs-the-whole-ses-configuration-set.md describe these scenarios aborting at setup because CreateConfigurationSet / GetAccount / CreateConfigurationSetEventDestination were 501 scaffold stubs.
