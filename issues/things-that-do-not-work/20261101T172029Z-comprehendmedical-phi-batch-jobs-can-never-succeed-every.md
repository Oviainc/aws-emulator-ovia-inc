# ComprehendMedical PHI batch jobs can never succeed: every job ends FAILED with no S3 output, unknown-JobId message is emulator-authored, and ClientRequestToken dedupes regardless of parameters (3 causes)

> _Note: this issue was identified against the code base at commit `3ce102081c5eb2c7e7b5721e0bb6bf7cb79dc6fe`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartPHIDetectionJob

## Description
Three net-new behavioral root causes in the ComprehendMedical asynchronous PHI-detection job family. The family is now IMPLEMENTED (StartPHIDetectionJob mints a JobId, DescribePHIDetectionJob/ListPHIDetectionJobs project the stored record, the modeled pattern validation and the ResourceNotFoundException error class are all correct), so these are fidelity gaps in the implemented handlers and their shared state machine, not stub gaps.

Cause 1 of 3: a started PHI job is driven unconditionally to FAILED, so no batch job can ever COMPLETE and no analysis output is ever written.
AWS: Smithy (services/service-com-amazonaws-comprehendmedical-comprehendmedical-20181030/smithy-model/com-amazonaws-comprehendmedical-comprehendmedical-20181030.json): StartPHIDetectionJob input InputDataConfig/OutputDataConfig/DataAccessRoleArn/LanguageCode required, optional JobName and ClientRequestToken; output JobId (@length 1..32). DescribePHIDetectionJob output ComprehendMedicalAsyncJobProperties, whose JobStatus is the modeled JobStatus enum (SUBMITTED, IN_PROGRESS, COMPLETED, PARTIAL_SUCCESS, FAILED, STOP_REQUESTED, STOPPED) and whose ManifestFilePath/EndTime describe a run that produced results. Recorded behavior: a job whose InputDataConfig.S3Key names a readable prefix containing a document, and whose role grants the bucket, advances SUBMITTED -> IN_PROGRESS -> COMPLETED and writes a real `.out` object under the OutputDataConfig prefix; that object is JSON carrying an `Entities` array holding the same PHI entities a synchronous DetectPHI call finds in the same text (for the recorded text, at least one entity with Category PROTECTED_HEALTH_INFORMATION and a NAME-typed entity whose Text covers the person name in the input). FAILED is reserved for a run that actually could not be performed.
Emulator: the job reaches FAILED every time. services/service-com-amazonaws-comprehendmedical-comprehendmedical-20181030/src/state.rs AsyncJob::advance moves SUBMITTED -> IN_PROGRESS after JOB_SUBMITTED_SPAN_SECS and then sets JobStatus::Failed unconditionally, attaching AsyncJob::unreadable_input_message() — the emulator's own sentence "Could not read the input documents from s3://<bucket>/<key>: this emulator does not serve object storage for asynchronous batch jobs, so no document was analyzed and no output was written to s3://<bucket>/<key>." (its fixed text is emulator-authored; the variable parts are the request's InputDataConfig/OutputDataConfig bucket and key). No object is written under the output prefix, so DescribePHIDetectionJob never reports COMPLETED and the output bucket stays empty. The premise of that message is also wrong in this deployment: the suite's S3 service is stood up and serving — the same check creates the bucket, puts input/doc.txt and lists/gets objects through it successfully.
Why: batch PHI analysis is the documented way to process more text than the synchronous limit allows. A client polling to completion is told its correctly-configured job failed, with a message naming no AWS-side fault it can act on; every downstream consumer of the `.out` output (the manifest, the entity extraction) has nothing to read, and code that branches on COMPLETED vs FAILED takes the error path for every job.
Fix: the job-run step of the PHI family's state machine (AsyncJob::advance in src/state.rs, plus whatever run step the family needs beside it) must read the input objects under InputDataConfig.S3Key from the emulator's own S3 state, apply the same PHI detection the synchronous detector applies, write the per-document `.out` JSON (with the `Entities` array) under OutputDataConfig.S3Key, set ManifestFilePath/EndTime, and only then report COMPLETED; FAILED must be reserved for an input that genuinely cannot be read. The sibling entities-detection family shares this advance() path and must move with it.
Traces: comprehendmedical.async-phi-job-completes-and-writes-output-to-s3 (last observed status=FAILED where COMPLETED is required; no `.out` object with Entities in the output prefix).

Cause 2 of 3: DescribePHIDetectionJob's unknown-JobId refusal carries an emulator-authored message that echoes the requested JobId.
AWS: Smithy: DescribePHIDetectionJob input JobId (required, @length 1..32, @pattern ^([\p{L}\p{Z}\p{N}_.:/=+\-%@]*)$); modeled errors InternalServerException/500, InvalidRequestException/400, ResourceNotFoundException/404, TooManyRequestsException/429. Recorded behavior for a JobId that satisfies the pattern and length but names no job: error code `ResourceNotFoundException` with Message `Could not find specified job.` — that message is ENTIRELY fixed text for this error class; it has no variable part, and in particular it does NOT echo the requested JobId. (The error code and status are already correct in the emulator: the check's `code2 == "ResourceNotFoundException"` assertion passes, as does the first-phase pattern-violation refusal with the constraint-report message.)
Emulator: the same code, but Message "No PHI detection job was found for JobId '<the requested jobId>'." — src/state.rs is not involved; src/ops/describe_phi_detection_job.rs:165-177 formats that sentence from input.job_id when the lookup misses.
Why: a client or operator matching on AWS's documented sentence never matches, and the emulator leaks the requested JobId into a message AWS keeps constant — so a test or log-scraper calibrated against AWS diverges, and the two negative classes (malformed id vs absent job) are told apart by text that does not exist on AWS.
Fix: the unknown/expired-job branch of DescribePHIDetectionJob's handler (src/ops/describe_phi_detection_job.rs) must emit the fixed message `Could not find specified job.` with no interpolation. The sibling PHI stop/list paths and the entities-detection family use the same interpolated pattern (already noted in the open wire issue 20261029T172356Z-comprehendmedical-asynchronous-job-error-contract-diverges-from-aws.md for the entities family); fix them together so the two cannot drift. Related open issue 20261029T175936Z-comprehendmedical-phi-job-handlers-answer-501-notimplemented-on.md described this path while the handler still answered 501 — the 501 is gone, the message is what still diverges, and that issue does not own this check's current failure.
Traces: comprehendmedical.describe-job-malformed-jobid-rejected (expected message 'Could not find specified job.', got "No PHI detection job was found for JobId '<32-char id>'.").

Cause 3 of 3: ClientRequestToken is treated as an unconditional dedupe key, so a reused token with DIFFERENT parameters returns the first job instead of starting a second one.
AWS: Smithy: StartPHIDetectionJob.ClientRequestToken (ClientRequestTokenString, @idempotencyToken, @length 1..64, @pattern ^[a-zA-Z0-9-]+$). Recorded behavior: reusing a token with IDENTICAL parameters is idempotent and returns the SAME JobId (the emulator already does this; that assertion passes). Reusing the same token with DIFFERENT parameters is NOT refused and NOT deduplicated — the service enforces no parameter-match guard on the token, so the call is simply a distinct request: HTTP 200 with a NEW, distinct JobId, the new job carries its own JobName, and the first job's own configuration is left untouched.
Emulator: HTTP 200 with the FIRST job's JobId. src/ops/start_phi_detection_job.rs:187-193 short-circuits on `state.phi_detection_jobs.job_for_token(token)` before looking at any other input member, and src/state.rs JobFamilyStore::idempotency_tokens stores only token -> JobId, keeping none of the submission it was created with — so the handler cannot tell a repeat of the same request from a different request that happens to reuse the token.
Why: a client that reuses a token across differently-parameterized submissions (a retry loop whose request body changed, or a token derived from something coarser than the request) silently loses the second job: it gets back an id for work it did not ask for, polls the first job's status and reads the first job's output, and the submission it believed it made never runs. No error tells it so.
Fix: StartPHIDetectionJob's handler (src/ops/start_phi_detection_job.rs) together with the token index in src/state.rs: record the submission the token created and short-circuit ONLY when the new request's parameters match it; otherwise mint a new JobId and record an independent job, leaving the existing job unmodified. The entities-detection family's start handler shares this token index and has the same defect.
Traces: comprehendmedical.start-job-idempotency-token-reuse (expected a distinct second JobId for a reused token with a changed JobName, got the first JobId back).

Neither of the two open PHI issues covers these three: 20261023T185154Z-comprehendmedical-the-phi-asynchronous-job-family-is-still.md and 20261029T175936Z-comprehendmedical-phi-job-handlers-answer-501-notimplemented-on.md both describe the family answering HTTP 501 NotImplemented, which it no longer does — the suite reported all three failures below as unowned, un-filed mismatches at new assertion sites.
