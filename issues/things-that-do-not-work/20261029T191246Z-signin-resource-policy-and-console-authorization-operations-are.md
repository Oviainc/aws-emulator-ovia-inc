# signin resource-policy and console-authorization operations are still unreachable: the SDK is directed to the public host signin.<region>.api.aws instead of the endpoint under test (2 causes)

> _Note: this issue was identified against the code base at commit `f04d881c92d4dd0b362060ab10db1f8e619a8cb7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetResourcePolicy, ListResourcePermissionStatements, PutResourcePermissionStatement, DeleteResourcePermissionStatement, PutConsoleAuthorizationConfiguration, GetConsoleAuthorizationConfiguration, DeleteConsoleAuthorizationConfiguration

## Description
REOPENS 20261022T011310Z-signin-resource-policy-and-console-authorization-operations-unreachable.md: its fix left the call refused.

That issue's Causes 3/4/5 are now closed — the router no longer refuses sigv4 'iam' with AmbiguousService (the IAM principal minting in signin.put-resource-permission-statement-concurrent-same-token-idempotent now succeeds), and the OAuth2 validation causes pass (signin now scores 8/19 instead of 0/19). Its Causes 1 and 2 are NOT closed: all 11 remaining signin failures are the same off-endpoint addressing defect, now described below as two causes. signin IS serving (the OAuth2 operations on an identically constructed ctx.client("signin") reach 127.0.0.1 in the same run), so this is a fidelity/routing defect of these two operation families, not a bootstrap gap. A fixer must close BOTH causes below before submitting.

=== Cause 1 of 2: the four resource-based-policy operations are addressed to the public regional host signin.<caller-region>.api.aws, so no request reaches the emulator ===
AWS: GetResourcePolicy (POST /get-resource-policy, @readonly), ListResourcePermissionStatements (POST /list-resource-permission-statements, @readonly, @paginated nextToken/maxResults), PutResourcePermissionStatement (POST /put-resource-permission-statement, @idempotent, clientToken is the @idempotencyToken) and DeleteResourcePermissionStatement (POST /delete-resource-permission-statement) are ordinary restJson1 operations bound to the signin service and served on the signin endpoint for the caller's own region (Smithy: service Signin 2023-01-01, protocol restJson1, awsService endpointPrefix/arnNamespace 'signin', sigv4Name 'signin', standardRegionalEndpoints). Each models the refusals the checks assert: GetResourcePolicy/ListResourcePermissionStatements/DeleteResourcePermissionStatement -> ResourceNotFoundException httpError 404, ListResourcePermissionStatements/DeleteResourcePermissionStatement -> ValidationException httpError 400, and all four carry the service-common AccessDeniedException. Recorded behavior for the asserted messages: a baseline account with no policy answers ResourceNotFoundException with the fixed message text "Requested resource not found" (no variable part), and a principal without the capability is refused AccessDeniedException whose message is the fixed template "No Access to <OperationName> API" — for PutResourcePermissionStatement, "No Access to PutResourcePermissionStatement API" (the operation name is the only variable part, taken from the request's target).
Emulator: the request for each of these four operations is addressed to the host 'signin.us-west-2.api.aws' (the caller's region in this run; the host is the public regional signin host for whatever region the client uses, not the endpoint under test), and the run's egress guard refuses it with botocore.exceptions.HTTPClientError: "An HTTP Client raised an unhandled exception: egress refused: 'signin.us-west-2.api.aws' is not the endpoint under test (127.0.0.1); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on". No HTTP status, error code or body is ever produced for these operations. Decisive evidence that the divergence tracks the OPERATION and not the client: in the very same run the OAuth2 operations on an identically built ctx.client("signin") (same region, same credentials path) do reach 127.0.0.1 and are answered, and in signin.put-resource-permission-statement-concurrent-same-token-idempotent the preceding iam.create_user / put_user_policy / create_access_key calls all succeed against the emulator before the first signin resource-policy call is refused. Hypothesis: these four routes are not registered on the served endpoint (so endpoint resolution falls back to the public signin ruleset host), or the emulator answers them with a redirect/Location carrying the public regional host.
Why: every client of signin's resource-based-policy surface is silently pointed at real AWS instead of the emulator. Nothing on that surface can be exercised: the ResourceNotFoundException "Requested resource not found" baseline, the AccessDeniedException "No Access to PutResourcePermissionStatement API" capability gate, the invalid-statementId ValidationException and the paginated empty-list shape are all unobservable; and in a network-permitted run the call would escape to the real service and mutate a real account.
Fix: the signin service's route/endpoint registration and any URL the emulator announces for these four operations (the signin crate's router/endpoint wiring plus the handlers for get_resource_policy, list_resource_permission_statements, put_resource_permission_statement and delete_resource_permission_statement under services/service-com-amazonaws-signin-signin). Every URL the emulator announces must be the endpoint it is reached on, and every region the service accepts must be served there.
Traces: signin.get-resource-policy-not-found-without-statements, signin.list-resource-permission-statements-baseline-empty-shape, signin.put-resource-permission-statement-access-denied-without-permission, signin.delete-resource-permission-statement-invalid-sid-rejected, signin.put-resource-permission-statement-concurrent-same-token-idempotent.

=== Cause 2 of 2: the three console-authorization operations are addressed to signin.us-east-1.api.aws, so a us-east-1 client never reaches the emulator ===
AWS: PutConsoleAuthorizationConfiguration (POST /put-console-authorization-configuration, @idempotent), GetConsoleAuthorizationConfiguration (POST /get-console-authorization-configuration, @readonly) and DeleteConsoleAuthorizationConfiguration (POST /delete-console-authorization-configuration, @idempotent) are restJson1 operations on the signin endpoint; all three return {targetId, scope, consoleAuthorizationEnabled} with all three members @required, and all three model ResourceNotFoundException httpError 404 and ValidationException httpError 400 (Put additionally models ConflictException httpError 409). Recorded behavior: the write operations are region-locked to us-east-1 (a write from another region is a ValidationException whose message is the fixed text "Write operations only supported in us-east"), so a conforming client legitimately builds a us-east-1 client for this surface; reading or deleting a configuration that does not exist answers ResourceNotFoundException with the fixed message text "Console authorization configuration not found" (no variable part).
Emulator: a signin client for region us-east-1 is addressed to 'signin.us-east-1.api.aws' and the egress guard refuses it with the same HTTPClientError message as Cause 1 ("egress refused: 'signin.us-east-1.api.aws' is not the endpoint under test (127.0.0.1) ..."). No console-authorization request reaches the emulator, so no status, error code or body exists for any of them.
Why: a client that follows AWS's own region-locking rule for this surface is pointed away from the emulator entirely — the emulated service appears to have no us-east-1 presence even though it is reached on one endpoint. The whole lifecycle contract is unverifiable: put -> get reports consoleAuthorizationEnabled=true; delete reports consoleAuthorizationEnabled=false in its OWN response and removes the record; a subsequent get and a second delete answer ResourceNotFoundException / "Console authorization configuration not found"; a double put conflicts; an unknown organization target is refused.
Fix: the signin service's region/endpoint routing so every region the service accepts (notably us-east-1, the only region that accepts these writes) is served on the endpoint under test, plus any URL announced by the console-authorization handlers (services/service-com-amazonaws-signin-signin, ops put/get/delete_console_authorization_configuration).
Traces: signin.put-get-console-authorization-configuration-enables, signin.get-console-authorization-configuration-not-found-when-unset, signin.console-authorization-configuration-disabled-after-delete, signin.console-authorization-configuration-full-lifecycle-workflow, signin.put-console-authorization-configuration-double-put-conflict-rejected, signin.put-console-authorization-configuration-nonexistent-org-rejected.
