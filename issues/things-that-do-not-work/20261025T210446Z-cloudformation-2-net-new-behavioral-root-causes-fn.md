# cloudformation: 2 net-new behavioral root causes — Fn::ForEach in Outputs fails the stack ('collection is not a list this service can resolve'), and a stack policy denying Update:Replace is stored but never enforced

> _Note: this issue was identified against the code base at commit `115ab0d71fd6f3de2d6e043b64ced071bfd8a5e5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateStack

## Description
This issue bundles 2 net-new behavioral root causes in the CloudFormation template/update engine. Neither is covered by an existing open issue's replay keys: 20261025T015306Z-cloudformation-template-transforms-and-intrinsics-are-not-processed.md carries the same check id for a DIFFERENT failure point (it recorded 'assert ids == expected_ids' — the Resources-section loop producing only ['Sentinel']); the stack now fails earlier and for a different reason, which is Cause 1 below. 20261025T015306Z-cloudformation-setstackpolicy-stub.md is titled as an unimplemented stub but SetStackPolicy is implemented and stores the body; what is missing is enforcement (Cause 2). 20261025T015306Z-cloudformation-never-rolls-a-failed-stack-back-failed.md covers the rollback family generally but does not carry this replay key.

Cause 1 of 2: Fn::ForEach in the Outputs section is not expanded — the collection `Ref <CommaDelimitedList parameter>` is rejected and the whole stack fails.
AWS: with `Transform: AWS::LanguageExtensions`, Fn::ForEach is valid in the Outputs section as well as in Resources, and its collection argument may be `{"Ref": "<param>"}` naming a CommaDelimitedList parameter; CloudFormation resolves that parameter (from the supplied Parameters, else its Default) during transform processing and emits one Output per element, named by substituting the loop identifier into the output key. The stack then reaches CREATE_COMPLETE and DescribeStacks reports one Output per element. Smithy: CreateStack.Capabilities (enum Capability, includes CAPABILITY_AUTO_EXPAND) and error InsufficientCapabilitiesException (client, httpError 400) gate transform processing; GetTemplate.TemplateStage = Original | Processed is where the expanded document is readable.
Emulator: the create ends CREATE_FAILED with StackStatusReason "Fn::ForEach::Urls: the collection is not a list this service can resolve from the template alone". The fixed text of that reason is the emulator's own prose — AWS has no such message; the variable part is the loop block's key (here `Fn::ForEach::Urls`, taken from the template). The Resources-section loop in the same template evidently gets further, so the Outputs-section expansion is a separate, unresolved code path, and because the whole create fails, none of the 24 queues, the Sentinel topic, the 24 Outputs, the Processed template stage or the delete-teardown assertions can be reached.
Why: any template written against the language extensions that loops in Outputs is undeployable — the client gets a terminal CREATE_FAILED for a template real CloudFormation deploys, and the failure reason is not one AWS can produce, so error handling keyed on CloudFormation's wording does not match either.
Fix: the AWS::LanguageExtensions / Fn::ForEach expansion pass in the cloudformation template pipeline: its collection resolver must resolve a `Ref` to a CommaDelimitedList parameter before expanding, and the pass must run over the Outputs section as well as Resources (and the expanded document must be what GetTemplate(TemplateStage=Processed) serves).
Traces: cloudformation__sns__sqs.cfn-foreach-language-extensions-expands-to-24-working-queues-and-rejects-missing-capability.

Cause 2 of 2: a stack policy is stored but never consulted during UpdateStack, so a Deny on Update:Replace does not stop the replacement and the update is not rolled back.
AWS: SetStackPolicy associates a policy with a live stack (Smithy: SetStackPolicy input StackName required, StackPolicyBody @length 1..16384, StackPolicyURL @length 1..5120, output Unit, no modeled errors). During a subsequent UpdateStack, CloudFormation evaluates that policy against each planned resource action; a statement `{"Effect":"Deny","Action":"Update:Replace","Principal":"*","Resource":"LogicalResourceId/<id>"}` makes the update of that logical id fail, and the stack rolls back: UpdateStack itself still answers 200 with StackId (Smithy: UpdateStack output {StackId, OperationId}; modeled errors only InsufficientCapabilitiesException and TokenAlreadyExistsException), and the verdict appears asynchronously as DescribeStacks StackStatus `UPDATE_ROLLBACK_COMPLETE`, a stack event whose ResourceStatusReason names the stack policy and the denied action `Update:Replace`, an UNCHANGED PhysicalResourceId for the protected resource, no resource created under the new create-only name, and the rollback reverting the sibling's allowed in-place change. Relaxing the policy to Allow Update:* and re-issuing the byte-identical update must then succeed (UPDATE_COMPLETE) and change the physical id.
Emulator: the policy body is stored and nothing reads it on the update path — services/service-com-amazonaws-cloudformation-cloudformation/src/ops/set_stack_policy.rs assigns `stack.stack_policy_body = Some(body)` and no update-engine code consults it. The update that changes the protected AWS::SQS::Queue's QueueName (a create-only property, hence a REPLACEMENT) runs to completion: DescribeStacks reports StackStatus 'UPDATE_COMPLETE' where 'UPDATE_ROLLBACK_COMPLETE' is owed, so the replacement the policy denies is actually performed and no stack-policy event exists to attribute it.
Why: stack policies are a protection mechanism — a client that sets one to guard a stateful resource (a queue, a table, a bucket) believes the resource cannot be replaced, and the emulator silently replaces it. Infrastructure-protection tests pass against the emulator and the resource is destroyed against real AWS semantics; worse, there is no rollback, so an update partially applied under a Deny is left in place.
Fix: the UpdateStack handler and the stack update engine in the cloudformation service — evaluate the stack's stored stack_policy_body (and the per-update StackPolicyDuringUpdateBody) against each planned resource action (Update:Replace / Update:Modify / Update:Delete / Update:*) before executing it, fail the update when a Deny matches, roll the stack back to UPDATE_ROLLBACK_COMPLETE, and record a stack event whose reason names the stack policy and the denied action.
Traces: cloudformation__sqs.cfn-stack-policy-protected-resource-replacement-rejected.
