AWS: Smithy (services/service-com-amazonaws-appconfigdata-appconfigdata/smithy-model/com-amazonaws-appconfigdata-appconfigdata.json) models StartConfigurationSession as POST /configurationsessions, success 201, input ApplicationIdentifier/EnvironmentIdentifier/ConfigurationProfileIdentifier (all @required, Identifier @length 1..128), output InitialConfigurationToken, errors BadRequestException 400 / ResourceNotFoundException 404 / ThrottlingException 429 / InternalServerException 500; and GetLatestConfiguration as GET /configuration?configuration_token=..., success 200, Configuration as the @httpPayload (sensitive) blob with ContentType/Next-Poll-Configuration-Token/Next-Poll-Interval-In-Seconds headers, same error set. lambda Invoke answers StatusCode 200 with the handler's own payload and no X-Amz-Function-Error when the handler returns normally; UpdateFunctionConfiguration(Environment.Variables=...) REPLACES the variable map, and after the update settles GetFunctionConfiguration returns exactly the submitted map. On AWS, the three legs are each reachable within seconds of the deployment reaching COMPLETE: (1) all three identifiers CloudFormation-logical-id-shaped (strings resolving to no application/environment/profile) => StartConfigurationSession is refused ResourceNotFoundException/404, so the handler reports its default; (2) application and configuration-profile repaired to the real ids but the ENVIRONMENT identifier still logical-id-shaped => STILL refused ResourceNotFoundException/404 (a session needs all three to resolve; a partially-resolved triple is not served), so the handler still reports its default; (3) all three repaired => the session is minted and GetLatestConfiguration serves the deployed document byte-exactly, so the handler reports source 'appconfig' with that document. Resolution is per-identifier and total: there is no fallback to a 'latest' or default configuration when one identifier is wrong. Per-run application/environment/profile ids, role, function and log-group names only fill these templates; the requirements are the 404 ResourceNotFoundException classification for the broken and partially-broken triples and the byte-exact deployed document for the correct one.

Emulator: the check reports exactly 'Error: Check timed out after 180.0s' with verdict [mismatch] — no assertion is reached. The check's first leg is an invoke-until loop (_INVOKE_TIMEOUT_S = 240, 5 s between invocations) whose predicate is the handler's self-reported Error.Code == 'ResourceNotFoundException'; the second leg is a single invoke asserting ('default', 'ResourceNotFoundException', {'useNewBackend': False}); the third is an invoke-until waiting for source == 'appconfig' and the deployed document. None of the predicates ever holds, so neither the identifier refusal nor the served bytes is observable. Hypothesis (the replay output shows only the timeout): the handler's in-process appconfigdata call never produces either outcome — the data plane never serves the deployed configuration (so leg 3's predicate never holds and the loop burns its full budget), and/or a session is minted for identifiers that resolve to nothing so no ResourceNotFoundException is ever reported (legs 1 and 2). Which leg stalls must be re-observed with the steps below.

Why: this is exactly how an operator repairs a misconfigured serverless client — fix one identifier at a time and re-invoke until the function reads real configuration. Against this emulator the function never reports either outcome, so (i) a caller polling in-process for its flags never returns and silently keeps its compiled-in default, and (ii) a half-repaired configuration cannot be distinguished from a repaired one: if the emulator serves (or mints a session for) a triple whose environment is still wrong, a least-privilege/wrong-identifier regression that AWS refuses with ResourceNotFoundException passes here.

Fix: the lambda Invoke execution path's in-process AWS SDK environment together with the appconfigdata data-plane handlers it calls (StartConfigurationSession identifier resolution and GetLatestConfiguration's served payload) and the Lambda UpdateFunctionConfiguration environment-variable state the handler reads — a handler's session must be refused 404 ResourceNotFoundException whenever ANY of the three identifiers resolves to nothing, and must be served the deployed bytes once all three resolve, promptly enough for a synchronous invoke to answer.
