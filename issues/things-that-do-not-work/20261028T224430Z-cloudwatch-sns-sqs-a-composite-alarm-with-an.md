# cloudwatch__sns__sqs: a composite alarm with an AND AlarmRule never completes its rule evaluation / notification cycle — the check hangs to the 60 s harness cap (1 cause)

> _Note: this issue was identified against the code base at commit `6dde6b5b59a4735e67d87b555115fcc549deec6e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
One net-new root cause. This is the residual of the fixed issue 20261025T020208Z-cloudwatch-sns-sqs-cloudwatch-alarm-actions-never-fire-to-sns-so.md, which listed this same check in its Issue-Trace-Ids: its two sibling arms (ActionsEnabled suppression, failed action to a deleted topic) now pass, so metric-alarm evaluation and the alarm -> SNS -> SQS delivery path do work; the composite AND-rule arm alone still never reaches a terminal result. The failure is a hang, not a refusal, so this is filed as the remaining divergence rather than a reopen. The open issues 20261025T020208Z-cloudwatch-alarms-never-evaluate-published-metric-data-no.md, 20261027T130355Z-cloudwatch-sns-sqs-a-metric-alarm-with-disablealarmactions.md and 20261028T010828Z-cloudwatch-events-sqs-cloudwatch-publishes-no-cloudwatch-alarm-configuration-change-event.md look adjacent but none of them carries this check's replay key.

Cause 1 of 1: a composite alarm whose AlarmRule is a conjunction of two real metric alarms never drives the full ALARM/OK cycle the rule defines, so the check is killed in its poll loop at the harness cap.
AWS: PutCompositeAlarm (Smithy: PutCompositeAlarm.AlarmRule @required, @length 1..10240; AlarmActions/OKActions/InsufficientDataActions ResourceList @length 0..5) creates an alarm whose state is derived from its children, and the derived state is observable through DescribeAlarms' CompositeAlarms entry (Smithy CompositeAlarm members StateValue, StateReason "An explanation for the alarm state, in text format", StateReasonData "An explanation for the alarm state, in JSON format", StateTransitionedTimestamp "The timestamp of the last change to the alarm's StateValue"). For a rule of the form ALARM("<child-a>") AND ALARM("<child-b>") AWS requires, in order: (a) with only child a in ALARM and child b still INSUFFICIENT_DATA the conjunction is false, so the composite stays OK and publishes no ALARM notification; (b) when the second child transitions to ALARM the composite transitions to ALARM exactly once, its StateReason begins with "<arn-of-the-child-that-completed-the-rule> transitioned to ALARM" (fixed text "<child ARN> transitioned to ALARM"; the ARN is the state value, taken from the alarm that completed the rule), and StateReasonData is JSON whose triggeringAlarms list names every child with its state value; (c) the AlarmActions fire once, publishing an SNS Notification envelope whose Subject is the documented fixed form 'ALARM: "<AlarmName>" in <Region>' (fixed text ALARM:, in; variable parts the alarm name from the request and the alarm's region) and whose Message is the composite alarm JSON carrying AlarmName, AlarmDescription, AlarmArn, AWSAccountId, NewStateValue, OldStateValue, NewStateReason, AlarmRule, AlarmActions, OKActions, InsufficientDataActions, Region, StateChangeTime equal to the alarm's StateTransitionedTimestamp, a TriggeringChildren list of the children with their states, and NO metric Trigger block (a composite alarm has no metric); (d) when a child returns to OK the conjunction is false again, the composite returns to OK with a StateReason beginning "<arn-of-that-child> transitioned to OK" and the OKActions notify once. Recorded behavior: all four stages are observed in sequence well inside the suite's polling budget.
Emulator: the check never reaches any of its assertions. It publishes real datapoints for child a and child b, polls DescribeAlarms for the children and the composite and drains the SNS-subscribed SQS queue, and is killed at the harness 60 s cap inside the poll loop ("Error: Check timed out after 60.0s"), with no assertion message. Because the run is cut off rather than answered, the composite never produces an observed ALARM state, no composite StateReason/StateReasonData is ever seen, and no composite notification reaches the queue; a composite that correctly holds OK on one child is indistinguishable from one whose rule is never evaluated at all, so the whole AND-rule contract is unobservable. Hypothesis: composite AlarmRule derivation is not re-evaluated when a referenced child alarm changes state (the sibling metric-alarm arms of this group now pass, which places the gap in the composite path rather than in metric evaluation or SNS publish).
Why: a client that models a page-worthy condition as a conjunction of alarms (the standard way to suppress single-signal noise) gets an alarm that never fires and never clears. Nothing pages, nothing auto-remediates, and DescribeAlarms reports no transition, so the absence is silent; a test suite built on the emulator will also certify composite-alarm logic that does not exist.
Fix: composite-alarm state derivation and its action dispatch in the cloudwatch alarm evaluator/state — re-evaluating each composite's AlarmRule when a referenced child alarm transitions, writing the composite's StateValue/StateReason/StateReasonData (triggeringAlarms)/StateTransitionedTimestamp, and invoking AlarmActions/OKActions once per composite transition through the SNS publish path (including the composite notification body: AlarmRule, TriggeringChildren, no Trigger block).

## Evidence

The other three checks in this group pass, so the metric-alarm evaluation and alarm->SNS->SQS delivery used by this same check are working — only the composite arm does not progress. 5.
