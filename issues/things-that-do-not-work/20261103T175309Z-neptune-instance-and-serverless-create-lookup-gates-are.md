# Neptune instance and serverless create/lookup gates are missing or evaluated in the wrong order

> _Note: this issue was identified against the code base at commit `c27f8675843924c63f0ee6aedd1be01f08149ed1`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDBInstance

## Description
The Neptune instance-create, instance-lookup and serverless cluster-create paths either skip the gate AWS applies or apply their gates in a different order, so requests AWS refuses succeed, requests AWS refuses for one reason are refused for another, and a lookup of a resource that does not exist succeeds. Five clusters, all reported with owned_by=[] and stub_path="". THIS ISSUE HAS 5 CAUSES — all five must be closed before submitting.

Cause 1 of 5: CreateDBInstance accepts an unacceptable master password and answers 200. AWS: CreateDBInstance takes MasterUserPassword and validates it before provisioning; the recording shows the request refused with HTTP 400, Error Type 'Sender', Code 'InvalidParameterValue' and Message 'Invalid master password' — the message is entirely fixed text and deliberately echoes no part of the (sensitive) value. Emulator: answers HTTP 200 with a created instance and no ErrorResponse at all. Why: the emulator creates state AWS would never have created, so a client's negative test passes against the emulator and its real deployment then fails at the same call; worse, the client proceeds as though an instance with that credential exists. Fix: the CreateDBInstance handler's master-password validation, which must run before any instance is written to state. Traces: neptune-npt-traj-create-instance-without-cluster#task#1.

Cause 2 of 5: CreateDBInstance's required-member check fires in place of the cluster-existence gate, so the refusal names the wrong problem. AWS: DBInstanceIdentifier, DBInstanceClass, Engine and DBClusterIdentifier are all required on CreateDBInstanceMessage, and DBClusterNotFoundFault is modelled with httpError 404 / awsQuery code 'DBClusterNotFoundFault' (Smithy: CreateDBInstance errors include DBClusterNotFoundFault). The recording shows that for this request the service answers HTTP 404 DBClusterNotFoundFault with Message 'The source cluster could not be found or cannot be accessed: ' + the DBClusterIdentifier from the request — i.e. the cluster the instance would join is resolved first. Emulator: answers HTTP 400 with Code 'MalformedInput' and Message "1 validation error detected: Value null at 'dBInstanceClass' failed to satisfy constraint: Member must not be null". Why: the caller is told its request shape is wrong when the actual obstacle is that the target cluster does not exist; it will keep correcting the wrong field, and a client branching on DBClusterNotFoundFault (to create the cluster first) never takes that branch. Fix: the CreateDBInstance handler's gate ordering — resolve DBClusterIdentifier against state and raise DBClusterNotFoundFault/404 ahead of the generic required-member report (and raise value-level rejections as InvalidParameterValue, not MalformedInput). Traces: neptune-npt-traj-create-instance-without-cluster#task#2.

Cause 3 of 5: DescribeDBInstances answers 200 for a DB instance that does not exist. AWS: the only error DescribeDBInstances models is DBInstanceNotFoundFault with httpError 404 and awsQuery code 'DBInstanceNotFound' (Smithy: DescribeDBInstances errors=[DBInstanceNotFoundFault]); a DBInstanceIdentifier naming no instance is refused with HTTP 404, Error Type 'Sender', Code 'DBInstanceNotFound' and Message 'DBInstance ' + the identifier from the request + ' not found.'. Emulator: answers HTTP 200 with no ErrorResponse. Why: an identifier-scoped describe is how a client confirms an instance's existence and polls its status; a 200 for a non-existent instance makes a deletion look incomplete, makes a failed create look successful, and makes any wait-until-exists loop return immediately. Fix: the DescribeDBInstances handler — when DBInstanceIdentifier is supplied it must resolve it in state and raise DBInstanceNotFoundFault/404 rather than returning a successful (empty) report. Traces: neptune-npt-traj-create-instance-without-cluster#task#4.

Cause 4 of 5: CreateDBCluster rejects a serverless request on engine support before it resolves the DB subnet group, so a missing subnet group is reported as an unsupported-configuration error. AWS: DBSubnetGroupNotFoundFault is modelled on CreateDBCluster with httpError 404 and awsQuery code 'DBSubnetGroupNotFoundFault' (Smithy: CreateDBCluster errors include DBSubnetGroupNotFoundFault), and the recording shows the subnet group resolved first: HTTP 404, Code 'DBSubnetGroupNotFoundFault', Message "DB subnet group '" + the DBSubnetGroupName from the request + "' does not exist." — fixed text "DB subnet group '" and "' does not exist." around the requested name. Emulator: HTTP 400 with Code 'InvalidParameterCombination' and Message 'ServerlessV2ScalingConfiguration is not supported by engine neptune version (default): that version runs no Aurora Serverless v2 capacity'. Why: the caller is told its serverless configuration is impossible when in fact the subnet group it named is missing, so it abandons a configuration that would have worked; and it never sees the 404 class it would branch on to create the subnet group. Fix: the CreateDBCluster handler's gate ordering — resolve DBSubnetGroupName and raise DBSubnetGroupNotFoundFault/404 before evaluating the serverless configuration. Traces: neptune-npt-traj-serverless-cluster-refusals-behind-subnet-group#task#1.

Cause 5 of 5: CreateDBCluster refuses Neptune Serverless wholesale instead of validating the scaling configuration's capacity range. AWS: ServerlessV2ScalingConfiguration is a modelled member of CreateDBClusterMessage for this service (Smithy: CreateDBCluster input ServerlessV2ScalingConfiguration -> com.amazonaws.neptune#ServerlessV2ScalingConfiguration with MinCapacity and MaxCapacity, documented as Neptune capacity units for a Neptune Serverless cluster), and neptune#DBCluster reports it back, so the engine DOES accept the configuration. What the service validates is the range: a MinCapacity greater than MaxCapacity is refused with HTTP 400, Code 'InvalidParameterValue' and Message 'Serverless v2 minimum capacity must be less than or equal to maximum capacity' — entirely fixed text. Emulator: HTTP 400 with Code 'InvalidParameterCombination' and Message 'ServerlessV2ScalingConfiguration is not supported by engine neptune version (default): that version runs no Aurora Serverless v2 capacity', i.e. it rejects every serverless request regardless of the capacities given. Why: Neptune Serverless is unusable — a client cannot create a serverless cluster at all, and when it does make the mistake the service would catch (min above max) it is given an error class and wording that point at engine support rather than at the two capacity values it must swap. Fix: the CreateDBCluster handler's ServerlessV2ScalingConfiguration handling — accept the member for the Neptune engine and validate MinCapacity <= MaxCapacity, raising InvalidParameterValue with AWS's message when it is not. Traces: neptune-npt-traj-serverless-cluster-refusals-behind-subnet-group#task#2.
