# eks: 5 net-new root causes in refusal class and wording — CA delete-in-use, DescribeAddonConfiguration not-found, StartInsightsRefresh in-progress, ListAssociatedAccessPolicies nextToken and CreateAddon validation order

> _Note: this issue was identified against the code base at commit `34977689197ee7e7ec3a117f2c4937da4e6f0436`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAddonConfiguration

## Description
Replaying simparity-behavioral-aws-v1 against the eks emulator (crate services/service-com-amazonaws-eks-awswesleyfrontend) leaves eight failing checks that no open issue carries the replay key of. They cluster into FIVE distinct root causes, all of them refusals whose HTTP class is right but whose error code, message text or evaluation ORDER diverges from AWS. All five must be closed before this issue is complete; each cause below names its own failing check ids.

Note on overlap: several of these causes are described in already-open issues against OTHER check ids / other corpora — named per cause below. None of those issues owns the replay keys of the checks listed here (the suite report marks neither ALREADY FILED nor OWNED for any of them), so they are filed here with the checks that still fail; a fixer may well close them together.

Cause 1 of 5 — DeleteCertificateAuthority on the IN_USE signer returns the wrong message.
AWS: Smithy: DeleteCertificateAuthority (DELETE /clusters/{clusterName}/certificate-authorities/{certificateAuthorityId}) models ResourceInUseException (httpError 409). Recorded behavior: deleting the certificate authority that currently signs for the cluster is refused ResourceInUseException with the sentence "Cannot delete the active certificate authority. Activate a different CA first." — that text is entirely FIXED; it has no variable parts and names neither the CA id nor the cluster.
Emulator: the code ResourceInUseException is right, but the message is "Certificate authority <certificateAuthorityId> is in IN_USE signing status; the certificate authority that signs for cluster <clusterName> cannot be deleted." — a different sentence that also injects the CA id and the cluster name into text AWS keeps constant, and drops the remediation ("Activate a different CA first.").
Why: the sentence is the operator- and test-visible contract for this refusal; a client asserting AWS's wording never matches, and the remediation step is lost.
Fix: the DeleteCertificateAuthority handler's in-use guard message in the eks crate's ops module.
Traces: eks.certificate-authority-active-signer-deletion-rejected, eks.certificate-authority-full-state-transitions. (Same cause as cause 3 of open issue 20261029T175608Z-eks-8-net-new-root-causes-in-certificate.md, which is grounded in a different check id, eks.delete-inuse-certificate-authority-rejected; these two checks still fail.)

Cause 2 of 5 — DescribeAddonConfiguration reports an unknown (addonName, addonVersion) pair with a generic not-found sentence.
AWS: Smithy: DescribeAddonConfiguration (GET /addons/configuration-schemas) takes required httpQuery members addonName and addonVersion and models ResourceNotFoundException (httpError 404). Recorded behavior: when the PAIR is not in the catalog — an unpublished version, a listed version with its "-eksbuild.N" suffix dropped, or a version that exists only under a different add-on — the refusal is ResourceNotFoundException with the message "Schema not found for requested addonName=[<addonName>] and addonVersion=[<addonVersion>]". Fixed text: "Schema not found for requested addonName=[", "] and addonVersion=[", "]"; the two variable parts are copied verbatim from the request, and there is no trailing period.
Emulator: answers ResourceNotFoundException with the generic framework sentence "The requested resource does not exist." for every miss, echoing neither the name nor the version.
Why: the message is the only place the lookup says WHICH of the name and the version failed; a client probing the catalog (the normal way a version is pinned) cannot tell a bad add-on name from a bad version, and exact-match assertions fail.
Fix: the DescribeAddonConfiguration handler's catalog lookup — build the not-found message from the request's addonName/addonVersion instead of returning the shared generic not-found.
Traces: eks.describe-addon-configuration-unknown-version-rejected, eks.efs-csi-driver-configuration-lookup-with-another-addons-version-not-found, eks.mbes-addon-configuration-for-an-unknown-version-not-found. (Same cause as cause 4 of open issue 20261029T175608Z-eks-5-net-new-root-causes-in-refusal.md, filed from two other check ids; these three still fail.)

Cause 3 of 5 — the refusal of a second StartInsightsRefresh while one is in flight uses the wrong sentence.
AWS: Smithy: StartInsightsRefresh (POST /clusters/{clusterName}/insights-refresh) models InvalidRequestException (httpError 400). Recorded behavior: a StartInsightsRefresh fired while the cluster's refresh is IN_PROGRESS is refused 400 InvalidRequestException and the message BEGINS with the fixed sentence "Another refresh operation is already in progress for the cluster. " followed by AWS's wrapped suffix "(Service: EksClusterInsights, Status Code: 409, Request ID: <uuid>) (SDK Attempt Count: 1)" — the uuid is a per-run value and is NOT part of the requirement; the sentence and the suffix's fixed text are. The in-flight refresh's startedAt must be unchanged.
Emulator: code InvalidRequestException and HTTP 400 are correct, but the message is "An insights refresh is already in progress for cluster <clusterName>; wait for it to complete before starting another." — a different sentence, with the cluster name injected into text AWS keeps constant and no wrapped service/status/request-id suffix.
Why: the fixed sentence is what clients and tests match on to distinguish 'a refresh is already running' from other 400s; the emulator's wording never appears in real EKS.
Fix: the in-progress guard message in the StartInsightsRefresh handler.
Traces: eks.insights-refresh-cooldown-throttle. (Same cause as cause 2 of open issue 20261029T175608Z-eks-3-net-new-root-causes-startinsightsrefresh-response.md; that issue's recorded replay key for this check no longer matches, and the check still fails on exactly this wording.)

Cause 4 of 5 — a corrupted nextToken on ListAssociatedAccessPolicies is refused with the wrong error code and message.
AWS: Smithy: ListAssociatedAccessPolicies models InvalidRequestException (400) and ResourceNotFoundException (404); InvalidParameterException is NOT in its modeled error list, so this is recorded behavior only. Recorded behavior: a nextToken that cannot be decoded is refused with error code InvalidParameterException and the message "The specified nextToken is invalid: unrecognized format." — all fixed text, no variable parts.
Emulator: answers error code InvalidRequestException (the assertion on the code fails before the message is reached).
Why: pagination wrappers branch on the code to tell 'your token is garbage, restart the enumeration' (InvalidParameterException) from 'the resource state forbids this' (InvalidRequestException); keying on the code takes the wrong recovery path and a resumable listing is treated as a state error.
Fix: the ListAssociatedAccessPolicies handler's nextToken decoding/validation — error selection plus the message.
Traces: eks.list-associated-access-policies-invalid-scope-rejected. (Cause 3 of open issue 20261029T175608Z-eks-5-net-new-root-causes-in-refusal.md describes the same code mismatch for this check id, but the suite does not report it as OWNED and the check still fails; the message requirement above is additional.)

Cause 5 of 5 — CreateAddon validates resolveConflicts BEFORE resolving the cluster, so a request against a missing cluster is refused for the wrong reason.
AWS: Smithy: CreateAddon (POST /clusters/{clusterName}/addons) models InvalidParameterException (400) and ResourceNotFoundException (404); resolveConflicts targets the ResolveConflicts enum. Recorded behavior: when the named cluster does not exist, CreateAddon is refused 404 ResourceNotFoundException with "No cluster found for name: <clusterName>." — fixed text "No cluster found for name: " plus the clusterName from the request plus a trailing period — REGARDLESS of other problems in the same request: an addonVersion that was never published and an out-of-enum resolveConflicts value both still give the 404. Cluster resolution precedes add-on and resolveConflicts validation.
Emulator: for clusterName=<absent> with a valid addonName, and for clusterName=<absent> with an unknown addonVersion, it correctly answers 404 ResourceNotFoundException "No cluster found for name: <clusterName>."; but for clusterName=<absent> with resolveConflicts=<not an enum value> it answers 400 InvalidParameterException "Resolve conflicts option <value> is not supported for operation CreateAddon" — the resolveConflicts check runs first and the absent cluster is never reported.
Why: the client is told to change a parameter while the actual blocker — the cluster does not exist — is never surfaced, so a provisioning retry loop fixes the wrong field and cannot terminate.
Fix: the CreateAddon handler's validation ordering — resolve the cluster before validating resolveConflicts (and the add-on/version).
Traces: eks.mbes-create-addon-on-a-missing-cluster-precedes-addon-and-resolveconflicts-validation. (Cause 6 of open WIRE issue 20261102T083656Z-eks-add-on-request-validation-runs-in-the.md describes the same ordering defect from a wire fixture step; it does not carry this behavioral check's replay key.)
