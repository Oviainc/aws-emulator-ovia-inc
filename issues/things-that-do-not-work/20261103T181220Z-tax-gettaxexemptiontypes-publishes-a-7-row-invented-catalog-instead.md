# GetTaxExemptionTypes publishes a 7-row invented catalog instead of the exemption types AWS reports

> _Note: this issue was identified against the code base at commit `d4f8ce799a785ffcb655def193d42db12684ea89`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetTaxExemptionTypes

## Description
Cause 1 of 1: GetTaxExemptionTypes answers 200 with a hand-written catalog whose entry set, per-entry wording and per-entry applicableJurisdictions are the emulator's own invention, so the response body diverges from the collection the real service publishes from the second entry onward. Fixture taxsettings-tax-exemption-workflow, step task#1.

AWS: Smithy: GetTaxExemptionTypes (POST /GetTaxExemptionTypes, success 200, empty input GetTaxExemptionTypesRequest) returns GetTaxExemptionTypesResponse$taxExemptionTypes, a TaxExemptionTypes list of TaxExemptionType{displayName @length 0..50, description @length 1..200, applicableJurisdictions: list<Authority{country required @length 2..2, state optional @length 1..50}>}; the operation doc is "Get supported tax exemption types." The model enumerates no fixed value set for those types, so the ENTRY SET, the ORDER, each entry's displayName/description text and each entry's list of Authority jurisdictions are recorded behavior only: the recorded response is the authority for them. The recording publishes a substantially larger catalog than the emulator's — at minimum indices 0 through 22 are populated — with the entries in displayName order, so index 1 is displayName "Agriculture Production" / description "Agriculture Production", and its applicableJurisdictions are one Authority per US jurisdiction that grants that category (the recorded list for it carries 42 entries and INCLUDES country US state PR while carrying NO entry for state CA or state DC). No HTTP status or error code diverges here: both sides answer 200, and the operation models no error on this path.

Emulator: the replayed step returns 200 but a body built from crate::state::TAX_EXEMPTION_TYPE_CATALOG, a 7-row const table ("501C", "Direct Pay Permit", "Educational Institution", "Federal Government", "Reseller", "State or Local Government", "Tribal Government"). Only index 0 matches the recording; the replay reports $.taxExemptionTypes[1] through $.taxExemptionTypes[22] as diverging — at index 1 the emulator sends {displayName: "Direct Pay Permit", description: "Holder of a direct pay permit that remits sales and use tax directly to the taxing authority", applicableJurisdictions: [...]} where the recording has the "Agriculture Production" entry, and the indices past the end of the 7-row table have no element at all. The jurisdictions are wrong independently of the entry set: every row but the first is given the shared const US_SALES_TAX_JURISDICTIONS, which carries country US state CA and state DC and carries NO state PR, so even an entry whose displayName did line up would publish the wrong Authority list. The table's own doc comment concedes the divergence in as many words ("What is NOT claimed: the displayName and description WORDING of every entry but the first, the per-state list of those entries, and the number and order of the entries").

Why: a client gets the wrong answer to the only question this operation exists to answer — which exemption types it may claim and where each one applies. A client that renders or iterates the catalog sees 7 categories instead of the published set and never sees "Agriculture Production" or any of the other missing entries. Worse, the catalog is the token vocabulary for PutTaxExemptionRequest$exemptionType ("Use the supported tax exemption type description"), and the same table drives the emulator's admission checks: find_exemption_type places a submitted token only among these 7 rows, and check_exemption_authority derives the jurisdictions a submission may name from US_SALES_TAX_JURISDICTIONS. So a submission naming a real published type in a real jurisdiction (for example a type claimed in PR) is refused 400 ValidationException by the emulator although AWS grants it, while a jurisdiction AWS does not publish for the type (CA, DC) is wrongly admitted — a client that works against the emulator is coded to a catalog that does not exist.

Fix: the operation's state — the published catalog table and its jurisdiction consts, which the handler only projects. Replace TAX_EXEMPTION_TYPE_CATALOG with the entry set, order and exact displayName/description text the GetTaxExemptionTypes recording publishes, give each entry its own recorded applicableJurisdictions instead of one shared country-wide const (so PR is present where it is published and CA/DC are absent where they are not), and keep PutTaxExemption's accepted exemptionType tokens and its authority admission derived from that same corrected table rather than from a second copy. Note the pinned-wire-form table in tests/all/tax_exemption_types.rs asserts the current invented body in, so it has to move with the catalog. An earlier issue on this catalog (20261024T200859Z-taxsettings-gettaxexemptiontypes-wrong-behavior.md) is marked FIXED but the replay still diverges on the same body, so it does not cover this.
