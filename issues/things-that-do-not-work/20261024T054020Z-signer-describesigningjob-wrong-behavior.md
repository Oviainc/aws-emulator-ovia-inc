# DescribeSigningJob never reports signatureExpiresAt and reports requestedBy as a raw access key id

_Filed: 2026-10-24T05:40:20Z_
_Operation: DescribeSigningJob | Class: wrong-behavior_

> _Note: this issue was identified against the code base at commit `a72a5132d94bd5cd1bb063d76c12b2ff9f8a44a7`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

Two defects in the DescribeSigningJob answer, both computed-from-state fields that the emulator hardcodes or mis-derives.

1) `signatureExpiresAt` is always absent. The handler returns `signature_expires_at: None` unconditionally (services/service-com-amazonaws-signer-wallabyservice/src/ops/describe_signing_job.rs, `signature_expires_at: None` with the comment "this emulator issues no certificate, so it reports no expiry"). AWS reports the expiry of the signature the job produced: DescribeSigningJobResponse models `signatureExpiresAt` ("Thr expiration timestamp for the signature generated by the signing job"), ListSigningJobs models `signatureExpiresBefore`/`signatureExpiresAfter` filters over it, and SigningJob carries it too — so every job has a signature expiry. The emulator already has everything needed to compute it: the signing profile persists `signature_validity_period` (defaulting to the documented 135 MONTHS, see crate::state::default_signature_validity_period) and the job record persists `created_at`. Expected: a job reports `signatureExpiresAt` derived from the job's creation/completion time plus the profile's signatureValidityPeriod that was snapshotted at StartSigningJob. Actual: the member is never serialized, so a client that reads signature expiry (or that will later filter ListSigningJobs by it) sees nothing.

2) `requestedBy` is not an IAM principal. The job record stores `requested_by = crate::state::request_principal(ctx.parts())` (src/ops/start_signing_job.rs), which is the SigV4 **access key id** of the signing request, and DescribeSigningJob echoes it verbatim. The model documents RequestedBy as "The IAM principal that requested the signing job", and AWS returns a principal ARN (e.g. arn:aws:iam::<account>:user/<name>, or an assumed-role ARN). The same crate already has `crate::state::request_principal_arn` and uses it for `revocationRecord.revokedBy`, so the two identity fields of the same service disagree in form. Expected: `requestedBy` is the resolved caller principal (ARN form), the same identity the service reports elsewhere for those credentials. Actual: a bare access-key string.

Not the same gap as the open issue 20261023T031331Z-signer-accepts-calls-aws-rejects-and-reports-signing.md (whose Cause 3 is that the signedObject advertised by a Succeeded job was never written to S3, filed under PutSigningProfile); neither signatureExpiresAt nor requestedBy is covered there.

## Evidence

Smithy model: DescribeSigningJobResponse$signatureExpiresAt (Timestamp, "Thr expiration timestamp for the signature generated by the signing job"), SigningJob$signatureExpiresAt, ListSigningJobsRequest$signatureExpiresBefore/$signatureExpiresAfter; DescribeSigningJobResponse$requestedBy targets RequestedBy, documented "The IAM principal that requested the signing job". Handler: src/ops/describe_signing_job.rs sets `signature_expires_at: None` and `requested_by: job.requested_by.clone()`; src/ops/start_signing_job.rs sets `requested_by` from `crate::state::request_principal` (access key id) while src/ops/revoke_signing_profile.rs uses `crate::state::request_principal_arn` for revokedBy. State: SigningProfileRecord.signature_validity_period (default 135 MONTHS) and SigningJobRecord.created_at/completed_at are persisted, so the expiry is derivable. Tests: tests/all/signing_profile_lifecycle.rs asserts requestedBy == ACCESS_KEY_ID (i.e. it pins the divergent form) and no test anywhere references signatureExpiresAt (grep for signature_expires/signatureExpires in tests/ returns no hits).

## Steps to Reproduce

1. PutSigningProfile PUT /signing-profiles/Job_Profile with platformId AWSLambda-SHA384-ECDSA (and signingMaterial) — note no signatureValidityPeriod is given, so the profile takes the documented 135-month default.
2. StartSigningJob POST /signing-jobs with a source/destination S3 pair, profileName Job_Profile and a fresh clientRequestToken, using SigV4-signed credentials.
3. Wait for the job to reach Succeeded, then GET /signing-jobs/{jobId}.
4. Observe the response body carries no `signatureExpiresAt` member at all, although the job completed and the profile has a signature validity period.
5. Observe `requestedBy` is the bare SigV4 access key id of the caller rather than an IAM principal ARN (compare with revocationRecord.revokedBy from GetSigningProfile after RevokeSigningProfile, which IS an ARN).
