# cloudformation__iam__imagebuilder: CreateStack refuses AWS::ImageBuilder::InfrastructureConfiguration / ImageRecipe / ImagePipeline / LifecyclePolicy as unrecognized resource types

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template validation does not know the AWS::ImageBuilder::* resource types, so every stack that wires an IAM role + instance profile to an Image Builder infrastructure configuration, image pipeline or lifecycle policy is refused at submit time. Failing checks: cloudformation__iam__imagebuilder.deploy-imagebuilder-infrastructure-configuration-round-trip-and-delete, cloudformation__iam__imagebuilder.deploy-imagebuilder-image-pipeline-round-trip-and-delete, cloudformation__iam__imagebuilder.deploy-imagebuilder-lifecycle-policy-round-trip-and-delete, cloudformation__iam__imagebuilder.deploy-imagebuilder-infra-config-unknown-instance-profile-rejected-and-rolled-back.

AWS: recorded behavior only for the registry contents — Smithy (services/service-com-amazonaws-cloudformation-cloudformation) models CreateStack -> CreateStackOutput{StackId} and declares only AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException; the set of recognized resource types is CloudFormation's registry. AWS's registry contains AWS::ImageBuilder::InfrastructureConfiguration, AWS::ImageBuilder::ImageRecipe, AWS::ImageBuilder::ImagePipeline, AWS::ImageBuilder::Component and AWS::ImageBuilder::LifecyclePolicy, so such a template is accepted (HTTP 200 + StackId) and provisions. In the negative case the refusal comes from Image Builder at resource-create time, not from template validation: the resource ends CREATE_FAILED and the stack ROLLBACK_COMPLETE, with the resource's ResourceStatusReason carrying Image Builder's own InvalidRequest sentence 'The value supplied for parameter 'instanceProfileName' is not valid. The provided instance profile does not exist. Please specify a different instance profile and try again.' (fixed text; the parameter name is the member that failed, and the service/status/request-id suffix CloudFormation appends is per-run). 'Template format error: Unrecognized resource types: [...]' (ValidationError, HTTP 400) is reserved for types not in the registry: fixed sentence, bracketed list taken from the template.
Emulator: CreateStack answers HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [...]' for these templates (observed [AWS::ImageBuilder::InfrastructureConfiguration]; [AWS::ImageBuilder::LifecyclePolicy]; [AWS::ImageBuilder::InfrastructureConfiguration, AWS::ImageBuilder::Component, AWS::ImageBuilder::ImageRecipe, AWS::ImageBuilder::ImagePipeline]). No stack exists, so the IAM-role/instance-profile wiring, the imagebuilder read-back, the rollback reason and the delete-and-verify phases are never exercised.
Why: a client cannot deploy Image Builder infrastructure through CloudFormation/CDK at all, and sees a template-format error for a template AWS accepts. The negative path is worse than unimplemented: instead of the resource-level InvalidRequest and a ROLLBACK_COMPLETE stack, the caller gets a validation error that attributes the problem to its template rather than to the bad instanceProfileName.
Fix: CloudFormation's supported-resource-type registry used by template validation in the CreateStack path, plus the AWS::ImageBuilder::* resource handlers (create/read/delete, Ref/Fn::GetAtt, and relaying the imagebuilder service refusal into the resource's ResourceStatusReason so rollback reports it).
Traces: the four cloudformation__iam__imagebuilder.deploy-imagebuilder-* checks listed above.

## Evidence
Expected (AWS): CreateStack with a template declaring AWS::IAM::Role + AWS::IAM::InstanceProfile + AWS::ImageBuilder::InfrastructureConfiguration (and, for the pipeline check, Component/ImageRecipe/ImagePipeline, or LifecyclePolicy) -> HTTP 200 with a StackId; DescribeStacks then reaches CREATE_COMPLETE, and for the unknown-instance-profile template the stack reaches ROLLBACK_COMPLETE with the resource reason 'The value supplied for parameter 'instanceProfileName' is not valid. The provided instance profile does not exist. Please specify a different instance profile and try again. (Service: Imagebuilder, Status Code: 400, Request ID: <id>) ...' and error code InvalidRequest.
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::ImageBuilder::InfrastructureConfiguration] (infrastructure-configuration-round-trip-and-delete and infra-config-unknown-instance-profile-rejected-and-rolled-back); ... [AWS::ImageBuilder::InfrastructureConfiguration, AWS::ImageBuilder::Component, AWS::ImageBuilder::ImageRecipe, AWS::ImageBuilder::ImagePipeline] (image-pipeline-round-trip-and-delete); ... [AWS::ImageBuilder::LifecyclePolicy] (lifecycle-policy-round-trip-and-delete). HTTP 400, no stack created.
'Template format error: Unrecognized resource types: ' is the fixed text and the bracketed list comes from the submitted template; the defect is that these registry types appear in it.

## Steps to Reproduce
1. Boot the emulator and replay the behavioral suite.
2. Run cloudformation__iam__imagebuilder.deploy-imagebuilder-infrastructure-configuration-round-trip-and-delete: it calls CreateStack with a template of AWS::IAM::Role, AWS::IAM::InstanceProfile and AWS::ImageBuilder::InfrastructureConfiguration.
3. Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::ImageBuilder::InfrastructureConfiguration]' instead of HTTP 200 with a StackId.
4. Repeat for the image-pipeline and lifecycle-policy templates, and for deploy-imagebuilder-infra-config-unknown-instance-profile-rejected-and-rolled-back, which must be accepted and then roll back with Image Builder's instanceProfileName InvalidRequest reason.
