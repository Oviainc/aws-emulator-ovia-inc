# xray: 3 net-new behavioral root causes — GetServiceGraph never reports a submitted segment's service, GetTraceSummaries never derives ResponseTimeRootCauses, and an explicit IAM Deny on xray:StartTraceRetrieval is not enforced

> _Note: this issue was identified against the code base at commit `ca5695aff0f0131b4dfb4047505400668f64cb69`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetServiceGraph

## Description
THREE distinct root causes in the X-Ray service (all failing checks carry SERVICES = ["xray"]). The xray service is bootstrapped and answering (81/127 xray checks pass), so these are fidelity defects, not a bootstrap gap. All three failing checks are reported by the suite as `Check timed out after 60.0s`: each check polls for a condition with its own (much larger) budget, so the condition the emulator never satisfied is what the poll was waiting for, and the harness ceiling is where it was cut off. None of these three checks is marked ALREADY FILED or OWNED in the replay report.

Cause 1 of 3: GetServiceGraph never reports a service-graph node for a service whose segment PutTraceSegments has just accepted.
AWS: Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models GetServiceGraph as POST /ServiceGraph (success 200) with required StartTime/EndTime and output Services -> ServiceList of Service{Name, Names, Type, State, Edges, SummaryStatistics, ...}; its only errors are InvalidRequestException (400) and ThrottledException (429). Recorded behavior (the check states a real-AWS replay, us-west-2 2026-09-11): a segment submitted via PutTraceSegments makes its `name` appear in the graph for a window containing the segment (25-65 s on real AWS), as a node Name or as an entry of some node's Names alias list, while a host that only called PutTelemetryRecords never becomes a node.
Emulator: PutTraceSegments accepted the segment (UnprocessedTraceSegments == [], asserted before the poll) and PutTelemetryRecords answered 200, but a fully paginated GetServiceGraph walk over [now-600s, now+300s] never contains the traced service name; the check is cut off inside that poll (its own budget is 900 s) at the 60 s replay ceiling. The absence-side assertion (the telemetry-only hostname must never be a node) is therefore never even reachable.
Why: the service map is the primary aggregate read of X-Ray. A client that submits segments and then reads GetServiceGraph to discover topology, latency and fault statistics sees an empty/unrelated graph, so every console view, dependency discovery and alarm built on the service map is blind; and because the node never appears, a client cannot distinguish 'no traffic' from 'the graph is not derived'.
Fix: derive the service-graph projection (nodes keyed by segment `name`, with Names/Type/State/Edges/SummaryStatistics) from the stored segment documents in the GetServiceGraph handler and the segment/service index it reads (services/service-com-amazonaws-xray-awsxray/src/ops/get_service_graph.rs plus the trace/segment state).
Traces: xray.telemetry-only-host-absent-from-service-graph.

Cause 2 of 3: GetTraceSummaries never populates ResponseTimeRootCauses, so a latency root cause is not derivable for any trace.
AWS: Smithy models TraceSummary.ResponseTimeRootCauses -> ResponseTimeRootCause{Services -> ResponseTimeRootCauseService{Name, Type, AccountId, Inferred, EntityPath -> ResponseTimeRootCauseEntity{Name, Coverage, Remote}}, ClientImpacting}. Recorded behavior for the derivation: for a root segment of 21 s containing an InternalPipeline subsegment (2 s) and a downstream QuartzAPI subsegment (19 s), GetTraceSummaries reports one response-time root cause whose EntityPath runs <root service> -> QuartzAPI with Coverage 19/21; when the downstream subsegment additionally carries `namespace: "remote"`, that terminal entity's Remote flips to true, the summary's ServiceIds gains a QuartzAPI entry of Type 'remote', and the root cause gains an Inferred QuartzAPI service. Without `namespace`, Remote is false and no inferred service is added.
Emulator: polling get_trace_summaries(StartTime=now-15m, EndTime=now+1m, FilterExpression='service("<submitted service>")') for a summary of the submitted trace id WITH a non-empty ResponseTimeRootCauses never succeeds (check poll budget 180 s, cut off at the 60 s ceiling), for both the plain and the remote-namespace twin. The Remote / ServiceIds / Inferred assertions are never reached because no root cause is ever produced.
Why: the response-time root cause is how a client (or an agent diagnosing latency) learns WHICH entity in a trace consumed the time and whether it was an external dependency. With the list permanently empty, every latency-attribution read returns 'no root cause' for traces that plainly have one, and the `namespace: remote` key a producer sets is unobservable.
Fix: compute the response-time root-cause projection (entity path, per-entity Coverage, Remote from the subsegment `namespace`, and the inferred remote service) when building trace summaries, in services/service-com-amazonaws-xray-awsxray/src/ops/get_trace_summaries.rs and the summary-building state code.
Traces: xray.remote-namespace-marks-the-quartz-root-cause-remote-and-infers-its-service.

Cause 3 of 3: X-Ray requests are not authorized against the caller's IAM identity policy — an explicit Deny on xray:StartTraceRetrieval is silently ineffective.
AWS: recorded behavior only for the IAM layer (Smithy models StartTraceRetrieval, POST /StartTraceRetrieval, with errors InvalidRequestException 400, ResourceNotFoundException 404 and ThrottledException 429; AccessDeniedException is the authorization layer's refusal and is not in the operation's modeled error set). A request signed with an IAM user's own access key whose inline policy is {Allow xray:*} plus {Deny xray:StartTraceRetrieval} is refused with error code AccessDeniedException, message built from the request ('User: <user arn> is not authorized to perform: xray:StartTraceRetrieval with an explicit deny in an identity-based policy'), while the SAME credentials keep succeeding on an unrelated action (GetSamplingRules) and the call reverts to its IAM-independent outcome once the Deny is removed.
Emulator: with the Deny in force, the signed StartTraceRetrieval keeps returning its IAM-independent outcome instead of AccessDeniedException, so the check's convergence poll (90 s budget) never converges and is cut off at the 60 s ceiling. That the pre-Deny leg passed and the Deny leg did not is what locates the failure at the authorization step: the operation itself answers (another check in this run reaches CancelTraceRetrieval with a token StartTraceRetrieval minted). Hypothesis: xray has no identity-policy authorization gate at all, the same shape already filed for other services (e.g. 20261025T015953Z-iam-an-explicit-deny-naming-iam-listgroups-is.md, 20261024T015148Z-dynamodb-does-not-enforce-iam-listtables-succeeds-for.md); no open issue names xray.
Why: a client cannot validate a least-privilege X-Ray policy against the emulator — a Deny that would block the call in AWS is ignored, so the emulator reports success for a call production refuses, which is the direction that hides real breakage; and any automation that asserts AccessDeniedException for an unauthorized principal can never pass.
Fix: evaluate the resolved caller's IAM identity-based policy (explicit Deny first) in the xray request authorization path before dispatching to the operation handler, returning AccessDeniedException with the standard 'is not authorized to perform' text (services/service-com-amazonaws-xray-awsxray request authorization, shared with the emulator's IAM policy evaluator).
Traces: xray.start-trace-retrieval-missing-permission-denied.
