# Auto Scaling client-error refusals diverge: emulator-authored messages, wrong error code, and accepted malformed filters

> _Note: this issue was identified against the code base at commit `e6d9764b7c2fffef8d3218e52b84d80407a24432`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAutoScalingGroup

## Description
Eight net-new causes on the Auto Scaling (awsQuery, api version 2011-01-01) client-error paths. All eight share one fault: the refusal an operation serves is authored by the emulator rather than reproduced as AWS words it — wrong fixed text, an identifier echoed that AWS does not echo, the wrong error Code, or no refusal at all. A fixer must close ALL EIGHT before submitting.

Cause 1 of 8 — CreateAutoScalingGroup with no launch source. AWS: HTTP 400, ErrorResponse.Error.Type Sender, Code ValidationError, Message (entirely fixed text, nothing substituted from the request) 'Valid requests must contain either LaunchTemplate, LaunchConfigurationName, InstanceId or MixedInstancesPolicy parameter.' Smithy: CreateAutoScalingGroupType models LaunchTemplate, LaunchConfigurationName, InstanceId and MixedInstancesPolicy as the four mutually alternative launch sources; the refusal class itself is the service-common ValidationError (recorded behavior only for the sentence). Emulator: same status and Code, but the Message is truncated to 'Valid requests must contain either LaunchTemplate, LaunchConfigurationName, InstanceId or MixedInstancesPolicy' — the trailing ' parameter.' (including the full stop) is missing. Why: a client or test that matches on AWS's documented sentence, or logs it for an operator, sees a sentence AWS never sends; nothing in it is per-run, so the mismatch is permanent. Fix: the CreateAutoScalingGroup handler's launch-source validation message text. Trace: autoscaling-account-level-reads-and-create-validation#task#7 (also autoscaling-resource-creation-validation-errors#task#1 and #task#2).

Cause 2 of 8 — DeleteAutoScalingGroup on a group whose DeletionProtection is set. AWS: HTTP 400, Code ValidationError, Message 'You cannot delete this group because its deletion protection is set to <deletion-protection-value>. If you are sure that you want to delete this group, remove deletion protection for the group and try again.' — the two sentences are fixed text, and the ONLY variable part is the group's DeletionProtection setting (the recorded run shows prevent-all-deletion); the group name does NOT appear in AWS's message. Smithy: DeleteAutoScalingGroupType, DeletionProtection enum on CreateAutoScalingGroup/UpdateAutoScalingGroup; refusal text is recorded behavior only. Emulator: 400 with its own sentence 'Cannot delete AutoScalingGroup <name> because its DeletionProtection is set to <value>' — different wording, no remediation sentence, and it echoes the AutoScalingGroupName AWS omits. Why: an operator or tool keying off AWS's remediation sentence ('remove deletion protection ... and try again') never sees it, and a consumer parsing the message for the protection state reads a different layout. Fix: the DeleteAutoScalingGroup handler's deletion-protection refusal message. Trace: autoscaling-deletion-protection-blocks-delete-until-cleared#task#5 (also #task#9, autoscaling-group-dependent-operations-on-nonexistent-group#task#20, autoscaling-resource-creation-validation-errors#task#3).

Cause 3 of 8 — DescribeAutoScalingGroups with an unsupported Filter Name. AWS: HTTP 400, Code ValidationError, Message "The filter criteria isn't valid. Valid filter types for the Name attribute of filters are: tag-key, tag-value and tag:<key>." — ALL fixed text; the literal 'tag:<key>' is part of the sentence and the offending filter name is NOT echoed. Smithy: DescribeAutoScalingGroups input member Filters (Filters list); the valid Name set (tag-key, tag-value, tag:<key>) is documentation/recorded behavior only. Emulator: 400 with its own sentence "The filter 'foo' is not valid: valid filter names are tag-key, tag-value and tag:<key>" — it quotes the rejected name and rewords both halves. Why: the message is the only machine-visible explanation of a filter rejection (the Code is the generic ValidationError), so a client that matches AWS's sentence treats the emulator's refusal as an unknown failure. Fix: the DescribeAutoScalingGroups filter validation message. Trace: autoscaling-describe-groups-malformed-filters-rejected#task#2 (also #task#3, #task#6, #task#8, #task#9).

Cause 4 of 8 — DescribeAutoScalingGroups accepts malformed Filter entries AWS refuses. AWS: HTTP 400 with the Cause-3 envelope — Error.Type Sender, Error.Code ValidationError, Error.Message "The filter criteria isn't valid. Valid filter types for the Name attribute of filters are: tag-key, tag-value and tag:<key>.", plus a RequestId. Emulator: HTTP 200 with an ordinary DescribeAutoScalingGroupsResponse and no ErrorResponse at all — the malformed filter is silently ignored. Why: this is the worse direction of the same defect — a caller that sends a bad filter gets a result set it believes was filtered, so it reads unfiltered groups as if they matched; against AWS the call fails loudly. Fix: the DescribeAutoScalingGroups filter validation must reject every Filter whose Name is not tag-key, tag-value or tag:<key> (and the malformed Name forms the fixture exercises) before any group is matched. Trace: autoscaling-describe-groups-malformed-filters-rejected#task#4 (also #task#5, #task#7).

Cause 5 of 8 — DescribeInstanceRefreshes naming a group that does not exist. AWS: HTTP 400, Code ValidationError, Message 'AutoScalingGroup name not found - AutoScalingGroup <group-name> not found' — fixed text 'AutoScalingGroup name not found - AutoScalingGroup ' + the requested AutoScalingGroupName + ' not found', with NO colon after the second 'AutoScalingGroup'. Smithy: DescribeInstanceRefreshesType.AutoScalingGroupName is required; the only modeled client error is InvalidNextToken, so a missing group is reported through the service-common ValidationError (recorded behavior only for the sentence). Emulator: same status and Code but inserts a colon — 'AutoScalingGroup name not found - AutoScalingGroup: <group-name> not found'. Why: the one punctuation difference breaks exact-match assertions and any log scraper keyed to AWS's sentence. Fix: the shared group-not-found message builder used by the group-scoped Auto Scaling handlers. Trace: autoscaling-group-and-policy-dependent-operations-on-nonexistent-group#task#5 (also autoscaling-group-scoped-describes-on-missing-group#task#5).

Cause 6 of 8 — StartInstanceRefresh naming a group that does not exist. AWS: HTTP 400, Code ValidationError, Message exactly 'AutoScalingGroup name not found - null' — for this operation AWS substitutes nothing at all after the dash; the whole string is fixed text and the requested group name does NOT appear. Smithy: StartInstanceRefreshType.AutoScalingGroupName required; modeled client errors are only InstanceRefreshInProgressFault and LimitExceededFault, so the missing group surfaces as the common ValidationError (message is recorded behavior only). Emulator: 'AutoScalingGroup name not found - AutoScalingGroup: <group-name> not found' — it reuses the group-scoped describe wording and echoes the name. Why: the emulator reports a per-operation message shape AWS does not use, so a client cannot distinguish the two refusal shapes AWS actually serves. Fix: the StartInstanceRefresh handler's group-lookup refusal must use the no-detail form, not the shared echoing builder. Trace: autoscaling-group-and-policy-dependent-operations-on-nonexistent-group#task#6 (also autoscaling-warm-pool-and-instance-refresh-negative#task#3).

Cause 7 of 8 — SetDesiredCapacity naming a group that does not exist. AWS: HTTP 400, Code ValidationError, Message exactly 'AutoScalingGroup name not found - null' (all fixed text, no name echoed), same form as Cause 6. Smithy: SetDesiredCapacityType.AutoScalingGroupName and DesiredCapacity required; modeled client error is only ScalingActivityInProgressFault, so a missing group is the common ValidationError (message recorded behavior only). Emulator: 'AutoScalingGroup name not found - AutoScalingGroup: <group-name> not found'. Why: same as Cause 6 — a client matching AWS's sentence for a missing group on a write path never matches. Fix: the SetDesiredCapacity handler's group-lookup refusal message. Trace: autoscaling-group-configuration-and-topology-negative#task#2 (also autoscaling-group-dependent-operations-on-nonexistent-group#task#2).

Cause 8 of 8 — DescribeInstanceRefreshes with BOTH an unknown group and an invalid NextToken: the emulator validates in the wrong order and so reports the wrong error identity. AWS: the group is resolved first, so the answer is HTTP 400, Code ValidationError, Message 'AutoScalingGroup name not found - AutoScalingGroup <group-name> not found' (fixed text + the requested group name, per Cause 5). Smithy: DescribeInstanceRefreshes models InvalidNextToken (awsQueryError code InvalidNextToken, 400) but AutoScalingGroupName is required and is validated before the token (recorded behavior). Emulator: HTTP 400 with Code InvalidNextToken and Message "The token '<token>' was invalid" — it reports the token problem for a group that does not exist, and the token value is echoed. Why: a client retrying on InvalidNextToken by restarting pagination loops forever against a group that will never exist, instead of failing with ValidationError. Fix: order the DescribeInstanceRefreshes handler's validation so the AutoScalingGroupName lookup precedes NextToken decoding. Trace: autoscaling-pagination-invalid-next-token-errors#task#9.
