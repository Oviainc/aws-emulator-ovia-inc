# cloudfront__events: 2 net-new causes — a CFN-provisioned rule's Lambda target never produces its downstream effect, and the matching-detail-type positive control is never delivered

> _Note: this issue was identified against the code base at commit `3c2de54b538cfaae335289815f0a91bb1b09b1bd`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutEvents

## Description
Two net-new root causes in the EventBridge rule -> Lambda-target delivery path, grounded in the only two failing cloudfront__events checks the replay report marks neither OWNED nor ALREADY FILED (42 of the 44 cloudfront__events failures are marked and were skipped). Both must be closed before submitting.

Related open issues — none of them carries either replay key below, so this is filed separately and should be de-duplicated against them if one dispatch/runtime fix closes them all: 20261105T190602Z-cloudfront-events-2-net-new-causes-a-matched.md (same symptom class, its trace ids are eventbridge-rule-input-path-extracts-distribution-id / eventbridge-target-arn-resolves-to-specific-cloudfront-distribution / eventbridge-lambda-target-missing-permission-blocks-delivery), 20261105T094343Z-cloudfront-events-the-lambda-python-runtime-provides-no.md (the python runtime provides no AWS SDK, for a different check set), 20261023T140640Z-cloudfront-events-3-of-the-4-causes-remain-open.md, 20261102T091831Z-cloudfront-events-a-matched-rule-never-invokes-its.md, 20261105T033500Z-cloudfront-events-a-cfn-provisioned-eventbridge-rule-never.md.

Cause 1 of 2: a CloudFormation-provisioned AWS::Events::Rule whose Lambda target is admitted by a stack-declared AWS::Lambda::Permission never produces the target's downstream effect, so the end-to-end deployment check never completes. Failing check: cloudfront__events.deploy-cfn-eventbridge-rule-cloudfront-invalidation-lambda.
AWS: Smithy (services/service-com-amazonaws-eventbridge-awsevents) PutEvents input Entries (@required, @length 1..10) models only InternalException; an accepted entry (FailedEntryCount 0, each result entry carrying an EventId) is a promise of asynchronous delivery. PutTargets input Rule (@required, @length 1..64, @pattern ^[\.\-_A-Za-z0-9]+$) + Targets (@required, @length 1..100) and models no error for the wiring used here. Smithy lambda (services/service-com-amazonaws-lambda-awsgirapiservice) Invoke: POST /2015-03-31/functions/{FunctionName}/invocations, output StatusCode (httpResponseCode), FunctionError (X-Amz-Function-Error, present ONLY when the handler faulted) and Payload (the handler's return value). On AWS, after the stack reaches CREATE_COMPLETE: (a) a direct RequestResponse Invoke of the stack's function runs the handler, which calls sqs:SendMessage under its execution role and returns {"ok": true} with no FunctionError; and (b) a PutEvents entry matching the rule's ENABLED EventPattern invokes that function once with the full event envelope, so the handler relays the envelope to the queue — the relayed body carries source, detail-type, resources and the published detail (the check asserts source == the published source, detail-type == the published detail type, resources == [] for an injected event, and detail.marker == the published marker). Recorded behavior only for timing: the recording shows both the warm-up invoke and the rule-driven relay landing well inside the check's budget.
Emulator: every setup call is accepted — cfn.CreateStack / DescribeStacks reaching CREATE_COMPLETE with its outputs, events.PutRule, events.PutTargets, lambda Permission, sqs.CreateQueue — and then the Lambda-target leg never produces an observable effect: the check's warm-up loop (a direct RequestResponse Invoke repeated every 3 s until the handler's own payload reports {"ok": true}) and the subsequent PutEvents/ReceiveMessage relay loop both run to exhaustion, and the harness kills the check with "Error: Check timed out after 60.0s" before any assertion is reached. Nothing is refused anywhere on the path: there is no status, error code or message to compare — the divergence is silent non-delivery.
Hypothesis: the observable is consistent with either leg failing — the direct Invoke never returning a successful handler payload (e.g. the handler faults because the python runtime has no AWS SDK for its `import boto3`, which keeps the warm-up predicate false forever), or the PutEvents -> rule-match -> Lambda-target dispatch never happening. The replay output carries only the harness timeout, so which leg is at fault is not stated by the recording; both legs are in scope for the fix.
Why: a client that provisions the standard CloudFront-audit automation declaratively (Rule + Lambda target + Lambda::Permission + queue in one stack) gets a stack that reports CREATE_COMPLETE and a pipeline that silently drops 100% of its traffic. PutEvents reports success, nothing lands on the queue, and no DLQ record or FailedInvocations signal distinguishes "pattern did not match" from "matched but never delivered", so the deployment looks correct and is inert.
Fix: the EventBridge target-dispatch component for rules on the default bus (match an accepted entry against each ENABLED rule's EventPattern and invoke each permitted target with the event envelope) together with the Lambda invoke/runtime path that must run a handler using the AWS SDK and return its payload with no FunctionError. CFN resource providers for AWS::Events::Rule / AWS::Events::Rule Targets / AWS::Lambda::Permission must register wiring the dispatcher actually consults.
Traces: cloudfront__events.deploy-cfn-eventbridge-rule-cloudfront-invalidation-lambda (group deployment-order).

Cause 2 of 2: a rule that requires a specific detail-type never delivers the positive-control event that carries exactly that detail-type, so detail-type matching cannot be distinguished from blanket non-delivery. Failing check: cloudfront__events.eventbridge-cloudfront-event-missing-detail-type-not-matched.
AWS: Smithy PutRule/PutTargets accept the pattern and target; PutEvents models only InternalException, so FailedEntryCount 0 is a delivery promise. AWS's event-pattern matching is exact and case-sensitive on each named field: an entry whose DetailType is "CloudFront Distribution State-Change" does NOT match a pattern requiring "detail-type": ["AWS API Call via CloudTrail"] (so the observation queue must stay empty for the check's 30 s negative window), while the identical entry published with DetailType "AWS API Call via CloudTrail" DOES match and is delivered to the Lambda target with the full envelope — the relayed body must carry detail-type == "AWS API Call via CloudTrail" and detail.requestParameters.distributionId == the distribution id published in the request (fixed text: the member names and the literal detail-type string; variable part: the generated distribution id).
Emulator: the negative half is indistinguishable from the defect, because the positive control never arrives either. CreateQueue, CreateRole/AttachRolePolicy/PutRolePolicy, CreateFunction, PutRule(State=ENABLED), AddPermission(Principal events.amazonaws.com, SourceArn the rule ARN), PutTargets and both PutEvents calls are all accepted, and no message ever reaches the observation queue; the check is killed with "Error: Check timed out after 60.0s" before its positive-control assertions. No refusal, no error code, no DLQ record.
Why: a client cannot rely on near-miss suppression being real — an emulator that delivers nothing passes every negative-delivery expectation and fails every positive one, so a rule that is silently over- or under-matching is undetectable, and any consumer wired to the target receives nothing at all.
Fix: same component as Cause 1 — the PutEvents -> pattern-match -> target-dispatch path (exact, case-sensitive comparison of source/detail-type/detail fields, then invocation of each permitted target with the unmodified envelope) and the Lambda invoke/runtime path the relay handler needs.
Traces: cloudfront__events.eventbridge-cloudfront-event-missing-detail-type-not-matched (group overly-permissive).

## Evidence
Replay of suite simparity-behavioral-aws-v1: 333/791 passed (42.1%), 407 mismatched, 51 errored. Service cloudfront__events: 11/55 (20%), 44 failed; 42 are marked OWNED by an open issue or ALREADY FILED (stub-blocked) and were skipped. The two remaining failures are the two causes above.

Cause 1 — [mismatch] cloudfront__events.deploy-cfn-eventbridge-rule-cloudfront-invalidation-lambda: "Error: Check timed out after 60.0s".
Setup, all accepted by the emulator: CreateStack (Capabilities CAPABILITY_IAM/CAPABILITY_NAMED_IAM) of a template declaring an SQS queue, a Lambda execution role with sqs:SendMessage, an AWS::Lambda::Function (python3.12, inline code relaying its event with sqs.send_message), an AWS::Events::Rule with a Lambda target, and an AWS::Lambda::Permission for events.amazonaws.com; DescribeStacks reaches CREATE_COMPLETE and the outputs QueueUrl/RuleArn/FunctionName are read.
Expected (AWS): (1) a direct Invoke(InvocationType=RequestResponse, Payload {"warmup": true}) returns no FunctionError and a payload with ok == true; (2) after draining the warm-up messages, PutEvents of one entry {Source: <customer-namespaced source>, DetailType: "CloudFront API Call (Simulated CloudTrail)", Detail: {eventSource: cloudfront.amazonaws.com, eventName: CreateInvalidation, awsRegion: <region>, marker: <marker>}} results in exactly one queue message whose body is the event envelope with source == the published source, detail-type == the published detail type, resources == [] and detail.marker == the marker.
Actual (emulator): neither is observable. The warm-up poll (interval 3 s, budget 60 s, predicate "handler payload reports ok") and the republish/receive loop (total 120 s, resend every 20 s) never succeed and the harness kills the check at its 60 s cap. No error code or message is produced by any call on the path.

Cause 2 — [mismatch] cloudfront__events.eventbridge-cloudfront-event-missing-detail-type-not-matched: "Error: Check timed out after 60.0s".
Setup, all accepted: CreateQueue + GetQueueAttributes(QueueArn); CreateRole trusted by lambda.amazonaws.com + AttachRolePolicy(AWSLambdaBasicExecutionRole) + PutRolePolicy(sqs:SendMessage on the queue); CreateFunction whose handler relays its event to the queue, then a warm-up role/invoke step; PutRule(EventPattern {"source":["sim2real.cloudfront"],"detail-type":["AWS API Call via CloudTrail"],"detail":{"eventName":["CreateInvalidation"],"requestParameters":{"distributionId":[<generated E-id>]}}}, State=ENABLED); AddPermission(Principal events.amazonaws.com, SourceArn the rule ARN); PutTargets([{Id: target-1, Arn: <fn arn>}]); PutEvents twice (both FailedEntryCount 0) — first with DetailType "CloudFront Distribution State-Change" (must NOT match), then with DetailType "AWS API Call via CloudTrail" (must match).
Expected (AWS): no message during the 30 s negative window, then one message whose payload has detail-type == "AWS API Call via CloudTrail" and detail.requestParameters.distributionId == the published distribution id.
Actual (emulator): the observation queue is empty for both halves; the 90 s positive-control poll never returns and the harness kills the check at 60 s before the assertions.

Not environment-dependent: the generated queue/role/function/rule/stack names, the account id, the distribution id, the markers and the host/port differ per run and are not part of the requirement. The requirements are (1) a direct RequestResponse Invoke runs an AWS-SDK-using handler and returns its payload with no FunctionError, and (2) an accepted PutEvents entry that matches an ENABLED rule's pattern is delivered once to each permitted Lambda target with the unmodified envelope, while an entry differing in detail-type is not.
