# AWS-managed schema Content document is still not the published one on DescribeSchema and ExportSchema

> _Note: this issue was identified against the code base at commit `ea8447640442a063890341d04cda7629f55a3fd9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeSchema

## Description
Reading an AWS-managed (service-owned) catalogue schema still answers 200 with a `Content` document that is not the one AWS publishes, on BOTH the describe path and the export path. The whole `$.Content` string is compared, so the step diverges as one value_mismatch; the concrete difference the replay exposes is in the CloudTrail record's `userIdentity.sessionContext`, which the published document declares inline WITH its own properties and the emulator declares as a propertyless object. 2 causes, one per fixture step/operation; they share the seeded source document, so the second is the first document converted.

NOTE on prior issues: the earlier reports of this exact pair of fixture steps — `20261029T203553Z-schemas-aws-managed-schema-content-is-wrong-for-both.md` and `20261023T194150Z-schemas-describeschema-and-exportschema-return-the-wrong-content.md` — are both in the RESOLVED folder, yet `schemas-export-aws-managed-schema#task#2` and `#task#3` still diverge in this replay (the clusters carry no `owned_by` and no `stub_path`), so this is net-new. It is also NOT the open `20261030T050932Z-schemas-listschemas-serves-a-fabricated-aws-managed-catalogue-digest.md` (which is about which entries ListSchemas lists and what `LastModified` it reports, not the document a schema read returns), and not the open `20261029T073056Z-schemas-describeschema-wrong-behavior.md` (an empty `schemaVersion` answered 404).

Cause 1 of 2: DescribeSchema serves an OpenApi3 document whose CloudTrail record declaration is incomplete — `userIdentity.sessionContext` carries no `properties`.
AWS: Smithy: `DescribeSchema` GET /v1/registries/name/{RegistryName}/schemas/name/{SchemaName} -> 200, output member `Content` targets `__string`; WHAT the document is, is recorded behavior only. The recording for the catalogue entry `aws.events@AWSAPICallviaCloudTrail` is an OpenAPI 3.0.0 document `{"openapi":"3.0.0","info":{"title":"<Detail Type> published by <source>","version":"1.0.0"},"paths":{},"components":{"schemas":{"<EventName>":{"type":"object","properties":{...}}}}}` whose event component declares the full CloudTrail record, with the record's nested structures declared INLINE and each of them carrying its own `properties` — including `userIdentity.sessionContext`, which the recorded draft-4 translation of the same document shows as `"sessionContext":{"properties":{"assumedRoot":{"type":"string"},...}}`. The title is the detail type in spelled-out form, ' published by ', then the publishing source; `paths` is empty; the four free-form members (`addendum`, `additionalEventData`, `requestParameters`, `responseElements`) are `{"type":"object","nullable":true}`; `eventTime` is `{"pattern":"yyyy-MM-dd'T'HH:mm:ss'Z'","type":"string","format":"date-time"}`. Member order is part of the document, since `Content` is text a client caches, diffs and hashes.
Emulator: it serves the document rendered from its seeded components template, in which the deepest nested structure is declared without members: `"sessionContext": {"type": "object"}`. The replay reports the whole `$.Content` as a value_mismatch against the recorded document for the very first catalogue read of the fixture.
Why: `Content` is the entire point of the operation — it is the document a client validates delivered events against or generates bindings from. A client generating code from the describe output gets a `sessionContext` with no members at all, so every field of the session context (the assumed-root marker and the rest of the session record) is invisible to the generated binding and unvalidatable by a validator fed this document, while the same call against AWS describes them.
Fix: the AWS-managed catalogue seed in the schemas service's state module — the CloudTrail components template the catalogue publishes every CloudTrail-delivered event under, reached by the DescribeSchema handler through the seeded schema row. Nothing in the handler or the serializer needs to change; this is catalogue DATA. File/line citations under Traces.
Traces: `schemas-export-aws-managed-schema#task#2` (representative).

Cause 2 of 2: ExportSchema serves the draft-4 translation of that same incomplete document, so the exported `definitions` entry is incomplete in the same place.
AWS: Smithy: `ExportSchema` GET /v1/registries/name/{RegistryName}/schemas/name/{SchemaName}/export with required `@httpQuery("type")` member `Type` -> 200, output `Content` targets `__string`; the document is recorded behavior only. The recording shows the JSONSchemaDraft4 rendering of the describe document: `{"$schema":"http://json-schema.org/draft-04/schema#","title":"<Detail Type> published by <source>","definitions":{"<EventName>":{"properties":{...},"type":"object"}}}` — `components.schemas` becomes `definitions`, the OpenAPI nullable form becomes the draft-4 union `{"type":["object","null"]}`, the OpenAPI-only keyword `readOnly` does not travel, members are rendered in name order (`properties` before `type`, `format` before `pattern` on `eventTime`), and `userIdentity.sessionContext` appears as `{"properties":{"assumedRoot":{"type":"string"},...}}`.
Emulator: the export path converts the seeded source document of cause 1, so the whole `$.Content` is reported as a value_mismatch: the `definitions` entry carries `"sessionContext":{"type":"object"}` with no `properties`, because the document being converted declares none. The envelope-promotion, nullable-union, readOnly-dropping and name-ordering behaviour of the conversion is as recorded; what is wrong is what it has to convert.
Why: a client exporting to draft-4 to feed a JSON-schema validator gets a document that does not constrain the session-context members AWS's document constrains, so validation of real CloudTrail events disagrees with AWS — and anything keyed on the exported text (a cached copy, a digest) differs from the published export.
Fix: the same seeded source document as cause 1; the ExportSchema handler's OpenApi3 -> JSONSchemaDraft4 conversion is the component that renders it, so this step must be re-replayed after the seed is corrected even though no conversion code changes. Both steps have to pass: fixing only one leaves the other diverging.
Traces: `schemas-export-aws-managed-schema#task#3`.
