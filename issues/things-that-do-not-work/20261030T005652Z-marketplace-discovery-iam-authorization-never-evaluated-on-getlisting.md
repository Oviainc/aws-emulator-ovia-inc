# marketplace-discovery: IAM authorization never evaluated on GetListing/GetOffer, ListFulfillmentOptions exposes one option per product, duplicate filterType accepted, and three ValidationException messages are misworded

> _Note: this issue was identified against the code base at commit `1e71a3102b418a18abda1ed5ba2c04b37249c268`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetListing

## Description
This issue bundles 6 net-new root causes, all in marketplace-discovery, found by replaying the behavioral suite (simparity-behavioral-aws-v1) against the emulator built from this checkout (69/78 passed; all 9 failures are in this service). None of them is grounded in a per-run value (no request id, clock reading, generated name or account-specific id is asserted on): every assertion that fails is on an HTTP status, an error code, a fixed-text error message with request-derived variable parts, or the number of items a listing returns.

Two already-open marketplace-discovery issues are adjacent but cover none of these replay keys, so they do not cover these causes: 20261029T201942Z-marketplace-discovery-refusals-carry-messages-aws-does-not.md (GetOfferSet not-found wording, SearchListings SearchFilterType value-set order, SearchFacets searchText newline wording) and 20261029T201942Z-marketplace-discovery-getlisting-getproduct-and-listfulfillmentoptions-serve-synthesized-placeholder-records.md (ListFulfillmentOptions serving synthesized content). Cause 4 below is the SAME class of defect as that first issue's Cause 2 but on a DIFFERENT operation and a DIFFERENT enum (ListPurchaseOptions / PurchaseOptionFilterType), and Cause 2 below is about the CARDINALITY of what ListFulfillmentOptions returns, not about its content being synthesized; both must be closed on their own.

=== Cause 1 of 6: no IAM authorization is evaluated on GetListing or GetOffer — every caller is allowed, so AccessDeniedException is never produced ===
AWS: Smithy: GetListing and GetOffer both model AccessDeniedException (errorKind client, httpError 403), doc "You don't have sufficient access to perform this action.", structure member `message` -> ExceptionMessage. These are aws-marketplace:GetListing / aws-marketplace:GetOffer actions, so ordinary IAM evaluation applies: a principal with an explicit Deny on the action is refused, and a brand-new principal with NO attached policy is refused by implicit deny. Recorded behavior for the explicit-deny message: 403 AccessDeniedException whose message is the standard IAM explicit-deny sentence — fixed text "User: ", " is not authorized to perform: ", " on resource: ", " with an explicit deny in an identity-based policy" — with the variable parts taken from the request and state: the caller's user ARN (arn:aws:iam::<account>:user/<user-name>), the action (aws-marketplace:GetListing), and the resource ARN (arn:aws:aws-marketplace:::catalog/<catalog>/listing/<listingId>). The no-policy (implicit-deny) case is refused with the same AccessDeniedException code. The account id, user name and listing id in those ARNs are values from the request/state, not literals to copy.
Emulator: authorization is not evaluated at all. With an explicit Deny on aws-marketplace:GetListing attached to the calling user, GetListing answers HTTP 200 with the full listing body (observed: a 3043-byte GetListingOutput for listing l-0123-cirrus-query-lens). With an IAM user that has NO policy attached at all, GetOffer likewise keeps answering 200, so the check that polls for the steady-state denial never observes one and is killed at the 60s harness timeout. No 403 and no AccessDeniedException is ever emitted by either operation.
Why: this is the overly-permissive direction. A client, a policy test or a least-privilege CI gate that asserts a scoped-down principal CANNOT read a listing or an offer passes against the emulator and then fails against AWS; worse, a tenant-isolation test built on an explicit Deny appears to hold while the emulator in fact serves the data to everyone. The reverse is also wrong: nothing in the emulator can be used to exercise a client's AccessDeniedException handling path, because that response is unreachable.
Fix: the service's request-authorization layer — the pre-handler authorization hook for this crate that must resolve the signing principal, evaluate its identity-based policies for the operation's aws-marketplace action and the target resource ARN, and raise the modelled AccessDeniedException with the IAM explicit-deny / implicit-deny sentence. The decision belongs in that shared hook, not duplicated in each handler; GetListing's and GetOffer's handlers only need to pass the resource they resolve. Traces: services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/ops/get_listing.rs and .../src/ops/get_offer.rs run their handle bodies unconditionally.
Traces: marketplace-discovery.get-listing-denied-principal-rejected, marketplace-discovery.get-listing-denied-without-permission-rejected, marketplace-discovery.get-offer-access-denied-without-permission-rejected.

=== Cause 2 of 6: ListFulfillmentOptions never exposes more than one fulfillment option for any product, so maxResults truncation and nextToken are unreachable ===
AWS: Smithy: ListFulfillmentOptions output `fulfillmentOptions` -> FulfillmentOptionsList (required) plus `nextToken` -> NextToken, and the operation is @paginated {inputToken: nextToken, outputToken: nextToken, pageSize: maxResults, items: fulfillmentOptions}; input `maxResults` -> Integer @range(1..50) default 25. FulfillmentOptionType enumerates 12 values (AMAZON_MACHINE_IMAGE, API, CLOUDFORMATION_TEMPLATE, CONTAINER, HELM, EKS_ADD_ON, EC2_IMAGE_BUILDER_COMPONENT, DATA_EXCHANGE, PROFESSIONAL_SERVICES, SAAS, SAGEMAKER_ALGORITHM, SAGEMAKER_MODEL), and a real AWS Marketplace product commonly carries several of them, so a page bounded by maxResults returns exactly maxResults items and a nextToken for the remainder. Recorded behavior only for the catalog contents themselves.
Emulator: scanning up to 20 listing summaries from SearchListings and calling ListFulfillmentOptions(maxResults=50) on every distinct associated productId, NO product returns 2 or more fulfillment options — the catalog the emulator serves gives each product at most one. (Consistent with the GetListing bodies it serves, e.g. fulfillmentOptionSummaries of length 1.) Because of that the truncation path and the nextToken path of this paginated operation are never entered and cannot be observed at all.
Why: a client that paginates ListFulfillmentOptions is never exercised against the emulator: its nextToken loop always terminates on the first page, so a token-handling bug in the client, or an off-by-one in its page assembly, is invisible until it reaches AWS. It also makes the emulator unusable for testing anything that branches on a multi-fulfillment product (for example an installer that must choose between CONTAINER and HELM).
Fix: the service's seeded catalog state — give products more than one fulfillment option so the modelled many-per-product relationship exists, and ensure ListFulfillmentOptions' handler then honours maxResults by truncating to it and emitting nextToken whenever items remain. Traces: .../src/ops/list_fulfillment_options.rs and the crate's catalog seed in .../src/state.rs.
Traces: marketplace-discovery.list-fulfillment-options-maxresults-respected, marketplace-discovery.list-fulfillment-options-pagination-respects-max-results.

=== Cause 3 of 6: SearchFacets' invalid-facetTypes refusal is reported per list member instead of aggregated at the list, and its enum value set is derived from the model rather than being the service's fixed set ===
AWS: Smithy: SearchFacets.facetTypes -> FacetTypeList (@length max 30) whose member targets the SearchFacetType enum; an out-of-enum value is refused with ValidationException (errorKind client, httpError 400, member `message` -> ExceptionMessage). Recorded behavior for the message: AWS aggregates this failure at the LIST member, not at the element — "1 validation error detected: Value '[<the whole submitted list>]' at 'facetTypes' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [FULFILLMENT_OPTION_TYPE, PRICING_MODEL, NUMBER_OF_PRODUCTS, DEPLOYED_ON_AWS, CERTIFICATES, PUBLISHER, AVERAGE_CUSTOMER_RATING, PRICING_UNIT, CATEGORY]]". Fixed text: the "1 validation error detected: Value '" prefix, the "' at '" / "' failed to satisfy constraint: Member must satisfy constraint: [Member must satisfy enum value set: [" joiners, and the bracketed 9-value set itself, which is a constant of the service. Variable parts: the echoed value (the whole list, rendered bracketed) and the member path, both from the request. Note the service's constant set contains CERTIFICATES, which this model's SearchFacetType does not declare, and its order is not the model's declaration order — so it cannot be generated from the model.
Emulator: 400 ValidationException with the right code but a differently built message: "1 validation error detected: Value 'NOT_A_REAL_FACET_TYPE' at 'facetTypes.1.member' failed to satisfy constraint: Member must satisfy enum value set: [AVERAGE_CUSTOMER_RATING, CATEGORY, PUBLISHER, FULFILLMENT_OPTION_TYPE, PRICING_MODEL, PRICING_UNIT, DEPLOYED_ON_AWS, NUMBER_OF_PRODUCTS]". Three independent divergences in one sentence: (a) the path is the element path 'facetTypes.<i>.member' and the echoed value is the single bad element, where AWS names the list member 'facetTypes' and echoes the whole list; (b) the nested "Member must satisfy constraint: [...]" wrapper AWS uses for a list-of-constrained-member failure is absent; (c) the value set is exactly SearchFacetType's 8 declared members in declaration order, so it omits CERTIFICATES and is misordered.
Why: this message is the only actionable part of the refusal — it is what tells a caller which facet types exist. A caller reading the emulator's set concludes CERTIFICATES is not a valid facet type when AWS accepts it, and any client or snapshot test that matches the documented list-level wording does not match the emulator's element-level wording.
Fix: the input-validation path's enum/list renderer as this service configures it — a list whose member carries an enum constraint must be reported at the list member with the nested "Member must satisfy constraint: [...]" wrapper and the whole submitted list echoed, and the SearchFacetType value-set listing must be this service's fixed set in this service's fixed order rather than generated from the model's member order. Traces: .../src/ops/search_facets.rs and the crate's shared validation message builder in .../src/state.rs.
Traces: marketplace-discovery.search-facets-invalid-facet-type-rejected.

=== Cause 4 of 6: ListPurchaseOptions renders the PurchaseOptionFilterType value set in model declaration order instead of the service's fixed order ===
AWS: Smithy: ListPurchaseOptions.filters -> PurchaseOptionFilterList (@length 1..10) whose entries carry a `filterType` targeting the PurchaseOptionFilterType enum; an out-of-enum value is refused with ValidationException (client, httpError 400). Recorded behavior for the message: "1 validation error detected: Value '<rejected value>' at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [PURCHASE_OPTION_TYPE, VISIBILITY_SCOPE, PRODUCT_ID, AVAILABILITY_STATUS, SELLER_OF_RECORD_PROFILE_ID]". The rejected value and the member path (e.g. 'filters.<i>.member.filterType') are the variable parts, taken from the request; the bracketed 5-value set is FIXED text — a constant of the service — and the order AWS emits it in is NOT the model's declaration order.
Emulator: the same status (400), the same code (ValidationException), the same path and the same echoed value, but the set is rendered in PurchaseOptionFilterType's declaration order: "[PRODUCT_ID, SELLER_OF_RECORD_PROFILE_ID, PURCHASE_OPTION_TYPE, VISIBILITY_SCOPE, AVAILABILITY_STATUS]" (confirmed identical to smithy_query shape=PurchaseOptionFilterType values).
Why: a client that parses or snapshots the enumerated set to present the supported filter types, and any transcript diff, sees a constant that differs from the service's even though every value is in fact supported.
Fix: the input-validation path's enum renderer as this service configures it, for the PurchaseOptionFilterType value-set listing used to build ValidationException messages — emit the service's fixed order, not model order. This is the same renderer named by the already-open issue 20261029T201942Z-marketplace-discovery-refusals-carry-messages-aws-does-not.md Cause 2 for SearchFilterType, but the PurchaseOptionFilterType ordering is a separate constant and is not covered there. Traces: .../src/ops/list_purchase_options.rs.
Traces: marketplace-discovery.list-purchase-options-invalid-filter-type-rejected.

=== Cause 5 of 6: the @length refusal for searchText truncates the echoed value and appends a byte count, instead of echoing the submitted value in full ===
AWS: Smithy: SearchListings.searchText -> SearchText, @length(1..512); over-length input is refused with ValidationException (client, httpError 400). Recorded behavior for the message: "1 validation error detected: Value '<the submitted value, in full>' at 'searchText' failed to satisfy constraint: Member must have length less than or equal to 512". Fixed text: the prefix, the "' at '" / "' failed to satisfy constraint: Member must have length less than or equal to " joiners, and the limit, which is the member's modelled max (512). Variable parts: the member path and the echoed value — and the echoed value is the WHOLE submitted string, however long; AWS does not abbreviate it.
Emulator: right status and right code, but the echoed value is cut off and replaced with an elision marker and a byte count: "... Value 'xxxx…xxx... [513 bytes]' at 'searchText' failed to satisfy constraint: Member must have length less than or equal to 512". The "... [<n> bytes]" suffix is an emulator invention that appears in no AWS message. The boundary case is correct (exactly 512 characters is accepted), so only the refusal's rendering is wrong.
Why: the echoed value is how a caller identifies WHICH of several candidate inputs was rejected; truncating it loses that, and the injected "[N bytes]" text breaks any client or test that matches on the documented sentence. Because the truncation is length-triggered, it will corrupt the message for every over-long-string refusal in this service, not just searchText.
Fix: the crate's shared validation message builder — the @length violation renderer must echo the submitted value in full rather than abbreviating it past some internal cap. Traces: .../src/ops/search_listings.rs and the shared message builder in .../src/state.rs.
Traces: marketplace-discovery.search-listings-searchtext-too-long-rejected.

=== Cause 6 of 6: SearchListings accepts a filters list that repeats a filterType, instead of refusing it with ValidationException ===
AWS: Smithy: SearchListings.filters -> SearchFilterList (@length 1..30) of SearchFilter{filterType: SearchFilterType (required), filterValues: SearchFilterValueList @length(1..30) (required)}; the filterValues doc states "Term filters accept multiple values (OR logic)", i.e. OR-combination belongs inside ONE entry's filterValues, so a filterType may appear at most once per request. The modelled refusal is ValidationException (client, httpError 400). Recorded behavior for the message: "Duplicate filter types: [<the repeated filterType>]" — fixed text "Duplicate filter types: [" plus the offending filterType name(s) taken from the request, bracketed. Note this refusal is independent of the 30-entry list cap: two entries are well inside it.
Emulator: no such check. SearchListings with two entries that repeat the same filterType (even with two different, catalog-valid filterValues) answers HTTP 200 with a body — observed {'totalResults': 0, 'listingSummaries': []} — rather than a 400 ValidationException. The accompanying positive control (one entry per distinct filterType) is accepted, so the emulator accepts both the legal and the illegal shape and silently returns an empty result set for the illegal one.
Why: overly permissive AND silently wrong. A client that builds a filter list by appending one entry per selected value — the natural but incorrect way to express OR — gets a 200 with zero results from the emulator and will be read as "nothing matches", so the bug ships; against AWS the same request is refused outright with an actionable message. Nothing in the emulator can exercise the client's handling of that refusal.
Fix: SearchListings' input validation — after the list's @length check, reject a filters list containing more than one entry with the same filterType, raising ValidationException with the "Duplicate filter types: [<types>]" message. SearchFacets takes the same SearchFilterList on its `filters` member and should be guarded by the same check. Traces: .../src/ops/search_listings.rs.
Traces: marketplace-discovery.search-listings-too-many-filters-rejected.
