## Description

Cause 1 of 5 — the MalformedQueryException for an aggregate inside a SQL HAVING clause reports the wrong character span, and formats it with a space after the comma.
AWS: Smithy (com.amazonaws.cloudwatchlogs) StartQuery models MalformedQueryException with httpError 400; the model carries no message text, so the text is recorded behavior only. A SQL-dialect query of the shape `SELECT svc, COUNT(*) AS n, SUM(ms) AS total FROM `<log-group>` WHERE run = '<marker>' GROUP BY svc HAVING COUNT(*) > 1` is refused with HTTP 400, error code MalformedQueryException and the message `No aggregation function expression allowed: <translated-predicate> ([<start>,<end>]) (Service: AWSLogs; Status Code: 400; Error Code: MalformedQueryException; Request ID: <request id>; Proxy: null)`. Fixed text: `No aggregation function expression allowed: `, the `([`/`,`/`])` span punctuation with NO space after the comma, and the ` (Service: AWSLogs; Status Code: 400; Error Code: MalformedQueryException; Request ID: `/`; Proxy: null)` suffix. Variable parts: the translated predicate taken from the request (`filtercount(*)>1` for `HAVING COUNT(*) > 1`, `filtersum(ms)>50` for `HAVING SUM(ms) > 50`), the span, which is the HAVING clause's offset into the service's TRANSLATED pipeline (not into the submitted SQL text), and the per-call request id. For the recorded query shape, whose log-group name and marker have fixed length, that span is the same on every run and the same for both HAVING forms.
Emulator: the error code and the leading sentence are right, but the span is `([73, 148])` where AWS reports `([164,182])` — a different, much wider range, and with a space inserted after the comma that AWS does not emit.
Why: the span is the only thing that points the query author at the offending clause; a client (or console) that highlights `[start,end]` in the query text highlights the wrong region, and any caller matching the message byte-for-byte (the documented way to tell this refusal from other MalformedQueryException causes) fails on the stray space.
Fix: the SQL-dialect validation path behind StartQuery that builds the aggregate-in-filter refusal — it must compute the offset of the rejected predicate in the translated pipeline it reports against, and format the span without whitespace.
Traces: logs.deep-logs-1-logsql-sql-having-on-aggregate-expression-rejected.

Cause 2 of 5 — the StartQuery log-group selector-conflict refusal uses emulator-authored wording and wraps it in the backend error envelope AWS does not use for this error.
AWS: Smithy StartQuery takes the three mutually exclusive selectors `logGroupName`, `logGroupNames` and `logGroupIdentifiers` and models InvalidParameterException with httpError 400. Recorded behavior for the text: a SQL query that names its source in the queryString (a `FROM `<log-group>`` clause) AND also passes `logGroupName` — or `logGroupNames` — is refused with HTTP 400, error code InvalidParameterException, and the message `Only one of the parameters 'logGroupName', 'logGroupNames' or 'logGroupIdentifiers' may be specified in a request`. That message is entirely fixed text: it quotes the three member names, and it carries NO ` (Service: AWSLogs; ...; Proxy: null)` suffix.
Emulator: the code is right, but the message is `Only one of logGroupName, logGroupNames, logGroupIdentifiers, or a source named in the queryString can be specified (Service: AWSLogs; Status Code: 400; Error Code: InvalidParameterException; Request ID: <per-call id>; Proxy: null)` — different fixed text (unquoted member names, an invented trailing `, or a source named in the queryString`, `can be specified` for `may be specified in a request`) plus a backend envelope AWS does not append to this request-shape refusal.
Why: this is a request-shape error clients surface verbatim and match on to tell a selector conflict from other InvalidParameterException causes; diverging wording breaks that matching, and the spurious envelope makes an input-validation refusal look like a relayed query-backend failure.
Fix: StartQuery's input validation in the logs crate — the mutually-exclusive-selector check must emit AWS's exact sentence and must not route through the query-backend envelope formatter.
Traces: logs.deep-logs-1-logsql-sql-with-log-group-name-parameter-rejected.

Cause 3 of 5 — revoking the CloudWatch Logs grant on the account's query-result CMK does not stop Insights queries; StartQuery keeps succeeding.
AWS: Smithy AssociateKmsKey takes `kmsKeyId` plus `resourceIdentifier` (here `arn:<partition>:logs:<region>:<account>:query-result:*`) and models ResourceNotFoundException with httpError 400. Recorded behavior: once the account query-result CMK is associated, the CMK is in the read path for query results — if the key policy's statement granting CloudWatch Logs is removed (PutKeyPolicy with a policy that no longer grants logs.amazonaws.com), subsequent StartQuery calls are refused with HTTP 400, error code ResourceNotFoundException and the message `The KMS Key associated with the Account does not have access on query results ARN (Service: AWSLogs; Status Code: 400; Error Code: ResourceNotFoundException; Request ID: <request id>; Proxy: null)` — all fixed text except the per-call request id. Disassociating the key restores queries.
Emulator: after the grant is revoked, StartQuery/GetQueryResults keep returning `Complete` with the full result set for 50 s of polling — the check times out waiting for a refusal, with the last observation `('ok', [<the 4 ingested lines>], '<the associated key arn>')`. The association is recorded (the key is reported as `encryptionKey`), but it is never consulted as an authorization decision on the read path.
Why: the query-result CMK is a data-protection control — a client that revokes the key's Logs grant (key compromise, offboarding, break-glass) expects query results to become unreadable immediately. The emulator keeps serving the plaintext rows, so any test or runbook that validates that control passes against an emulator that does not enforce it.
Fix: the Insights read path behind StartQuery/GetQueryResults must evaluate the associated query-result CMK's key policy for the CloudWatch Logs principal on every query and refuse with the modeled ResourceNotFoundException and AWS's sentence when the grant is absent.
Traces: logs.deep-logs-2-logcmk-query-result-key-gates-insights.

Cause 4 of 5 — the unknown-function refusal names the rule with the wrong fixed text and a span that does not cover the function call.
AWS: Smithy StartQuery, MalformedQueryException httpError 400; message text is recorded behavior only. A pipeline whose `stats` names a function the engine does not know — `fields ms | stats bogusfn(ms) as z` — is refused with the message `Unrecognized function name: <name> ([<start>,<end>]) (Service: AWSLogs; Status Code: 400; Error Code: MalformedQueryException; Request ID: <request id>; Proxy: null)`, and the span is an offset into the query text that covers the whole offending clause exactly, i.e. `<end> - <start>` equals the clause length minus one (for `bogusfn(ms)`, 11 characters at offset 18, the span is `[18,28]`). Fixed text: `Unrecognized function name: ` plus the span punctuation and the service suffix; variable parts: the function name from the queryString and the clause's offsets.
Emulator: the code and the suffix are right, but the message reads `Unknown function: bogusfn ([18,25])` — the fixed sentence is `Unknown function: ` instead of `Unrecognized function name: `, and the span ends at 25, covering only `bogusfn(` rather than the whole `bogusfn(ms)` call.
Why: callers distinguish a misspelled aggregate from other parse failures by this exact sentence, and editors/consoles underline the reported span; the wrong wording defeats the first and the short span underlines a truncated, confusing region of the query.
Fix: the semantic-validation stage of the Insights query parser that reports unresolved function names — AWS's sentence, and the span taken from the full function-call clause.
Traces: logs.logs-insights-semantics-semantic-error-rejected-at-start.

Cause 5 of 5 — a later `fields` command that re-declares a field an earlier `parse` created is ACCEPTED; StartQuery returns 200 and a queryId where AWS refuses the query.
AWS: Smithy StartQuery models MalformedQueryException (httpError 400) for a query it will not run; recorded behavior for the text: a pipeline that names an ephemeral field a previous `parse` already produced — `filter @message like /<marker>/ | parse @message "svc=* lat=* status=*" as svc, lat, st | sort @timestamp asc | fields @message, lat` — is refused with HTTP 400, MalformedQueryException and the message `Ephemeral field is already defined: <field> ([<start>,<end>]) (Service: AWSLogs; Status Code: 400; Error Code: MalformedQueryException; Request ID: <request id>; Proxy: null)`; the fixed text is `Ephemeral field is already defined: ` plus the span punctuation and the service suffix, and the variable parts are the field name from the query, the span (an offset into the service's rewritten query text) and the per-call request id. No query is created: DescribeQueries for the log group lists nothing for the refused string.
Emulator: the call succeeds — HTTP 200 with a `queryId` — so the redefinition is never detected and a phantom query is started. (Note: the sibling check logs.logs-insights-semantics-semantic-error-rejected-at-start expects the same `Ephemeral field is already defined:` refusal for `parse ... as tg | fields tg`; it is blocked earlier by Cause 4, so that leg is unmeasured here.)
Why: a client that relies on AWS rejecting the redefinition gets a running query whose output columns are whatever the emulator chose, instead of a diagnosable 400 naming the duplicated field; validation tests for query authoring pass against a service that accepts invalid queries.
Fix: the ephemeral-field scope/duplicate check in the Insights semantic-validation layer behind StartQuery — it must reject a `fields`/`display` that re-declares a parsed field with the modeled MalformedQueryException and AWS's sentence, and must not register a query.
Traces: logs.logsquery-redefining-a-parsed-field-rejected.
