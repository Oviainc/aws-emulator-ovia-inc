# cloudcontrol: 4 net-new causes — CloudFormation-provisioned resources are invisible to GetResource, the stored resource model carries only client-supplied properties (so a JSON Patch replace of a server-defaulted property is refused), and two refusal messages are wrong

> _Note: this issue was identified against the code base at commit `adb5576e5b4c8de09688914f068f290c40dc2de8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateResource

## Description
FOUR net-new root causes, all in the cloudcontrol (Cloud Control API) service. A fixer must close all four before submitting.

Cause 1 of 4: GetResource/ListResources do not resolve a resource that a CloudFormation stack provisioned.
AWS: GetResource (Smithy: com.amazonaws.cloudcontrol#CloudApiService, GetResource input required TypeName+Identifier, output ResourceDescription{Identifier, Properties}) is documented to return an existing resource in the account/Region whether or not it was provisioned through Cloud Control API. So an AWS::SQS::Queue created by a CloudFormation stack resolves through GetResource under its primary identifier (the queue URL CloudFormation reports as PhysicalResourceId / the Ref output), appears in ListResources for that TypeName, reflects a later stack update, and only answers ResourceNotFoundException once the owning stack has been deleted.
Emulator: every GetResource for a stack-created queue is refused ResourceNotFoundException, message "<TypeName> Handler returned status FAILED: Resource of type '<TypeName>' with identifier '<queue url>' was not found. (HandlerErrorCode: NotFound, RequestToken: <uuid>)" — the lookup consults only Cloud Control's own store, which has no record of anything CloudFormation created. (Fixed text: "Handler returned status FAILED: Resource of type ... was not found. (HandlerErrorCode: NotFound, RequestToken: ...)"; the type name, identifier and token are per-request/per-run values.)
Why: Cloud Control is the uniform read API over existing infrastructure. A client that provisions with CloudFormation and then inventories, reads or patches through Cloud Control sees an empty account, and the data-plane/teardown assertions behind that read are never reached.
Fix: the resource lookup used by the GetResource and ListResources handlers must resolve from the owning service's state (the resource the CloudFormation stack actually created) instead of Cloud Control's private index.
Already-filed note: the open issue 20261102T095426Z-cloudcontrol-6-net-new-causes-cloud-control-s.md describes this same split-store read gap as its Cause 2 of 6 and lists these six check ids in its Issue-Trace-Ids, but the suite did not mark these checks owned, so they are re-reported here for completeness; if that issue's Cause 2 is fixed, this cause closes with it.
Failing checks: cloudcontrol.deploy-cfn-resource-behaves, cloudcontrol.deploy-cfn-resource-behaves-post-create, cloudcontrol.deploy-cfn-stack-deletion-removes-resource, cloudcontrol.deploy-cfn-update-reflected-in-getresource, cloudcontrol.deploy-cloudformation-resource-behaves, cloudcontrol.deploy-cloudformation-stack-deletion-removes-resource

Cause 2 of 4: the stored resource model contains only the properties the caller put in DesiredState, so server-defaulted properties are missing from GetResource and a JSON Patch "replace" on one of them is refused.
AWS: ResourceDescription.Properties is documented as "A list of the resource properties and their current values" and ProgressEvent.ResourceModel as "a JSON string containing the resource model, consisting of each resource property and its current value" — i.e. the resource's full current model as the owning service reports it, including properties the service defaults when the client did not supply them. For AWS::SQS::Queue created with only QueueName/Tags, GetResource Properties therefore carries the queue's VisibilityTimeout (and the other attribute-backed properties such as DelaySeconds) at their service defaults, and UpdateResource with PatchDocument [{"op":"replace","path":"/VisibilityTimeout","value":<n>}] is accepted, reaches OperationStatus SUCCESS and sets the native attribute. (Smithy: UpdateResource required TypeName/Identifier/PatchDocument; ValidationException is not a modeled shape of this service — recorded behavior only for the error code the checks observe.)
Emulator: GetResource Properties omits the property entirely (the replay dies with KeyError: 'VisibilityTimeout' on json.loads(ResourceDescription.Properties)), and because the property is absent from the stored model, UpdateResource refuses the replace synchronously with ValidationException and the message "Invalid PatchDocument: the replace operation at path '/<pointer>' could not be applied to the resource model" (observed for '/VisibilityTimeout' and '/DelaySeconds'). The fixed text here is the emulator's own invention; AWS has no such message and does not refuse the call at all.
Why: a client reads the current model from GetResource before patching, so an absent server-defaulted key breaks it; and the patch AWS accepts is rejected, which makes every "adjust one attribute of an existing resource" workflow impossible. It also hides the behaviour layered on top of a successful update: the overlapping-update check never reaches AWS's ConcurrentOperationException (Smithy: modeled on UpdateResource, httpError 409, "Another resource operation is currently being performed on this resource", message "Concurrent operation found for resource <Identifier> with RequestToken <winner token>") because both concurrent updates are refused with ValidationException first.
Fix: the resource state the cloudcontrol crate keeps for a created resource (and the model GetResource/ListResources serialize) must be the owning service's full property set including service defaults, and the UpdateResource patch application must then apply a `replace` against those properties.
Failing checks: cloudcontrol.update-resource-invalid-client-token-format-rejected, cloudcontrol.create-only-property-mutation-rejected, cloudcontrol.list-resource-requests-ordering-reflects-submission-order, cloudcontrol.server-enforced-concurrent-operation-limit-rejected

Cause 3 of 4: the refusal of a JSON Patch "replace" on a genuinely absent path carries the wrong message.
AWS: for a resource whose model legitimately lacks the pointer (an AWS::Logs::LogGroup created with no RetentionInDays), UpdateResource with [{"op":"replace","path":"/RetentionInDays","value":7}] is refused with error code ValidationException (HTTP 400) and the message "[REPLACE Operation] noSuchPath in source, path provided : /<patch path>" — for this request literally "[REPLACE Operation] noSuchPath in source, path provided : //RetentionInDays". Fixed text: "[REPLACE Operation] noSuchPath in source, path provided : /"; the variable part is the patch operation's own path from the request. AWS keeps this distinct from its neighbouring rule, where a write-only property is refused with "Invalid patch update: writeOnlyProperties [/<pointer>] can only be updated using 'add' operation". (Recorded behavior only: ValidationException is not a modeled shape of this service.)
Emulator: the code is right but the message is the same catch-all as in Cause 2 — "Invalid PatchDocument: the replace operation at path '/RetentionInDays' could not be applied to the resource model".
Why: Cloud Control funnels every PatchDocument violation into one error code, so the message is the only thing that tells a client what to fix. One catch-all string makes an absent path indistinguishable from a write-only property, a read-only property or a create-only property, and clients and operators diagnose the wrong thing.
Fix: the UpdateResource patch validation must emit per-rule messages — the noSuchPath form for an absent source path and the writeOnlyProperties form for a write-only property (which must stay refused even after an `add` has set it).
Failing check: cloudcontrol.patch-replace-nonexistent-path-rejected

Cause 4 of 4: the NotFound refusal of a DeleteResource on an already-deleted resource reports the handler-wrapped exception text instead of the bare handler message.
AWS: deleting a resource that no longer exists is refused as ResourceNotFoundException with the bare handler message "Resource of type '<TypeName>' with identifier '<Identifier>' was not found." — fixed text "Resource of type '", "' with identifier '", "' was not found." with TypeName and Identifier taken from the request. The wrapped form ("<TypeName> Handler returned status FAILED: ... (HandlerErrorCode: NotFound, RequestToken: <uuid>)") is what AWS uses for the GetResource read path, not for this refusal, which is exactly why the check grades the two differently.
Emulator: the second delete is refused with the right code but the GetResource-style wrapped message: "AWS::SSM::Parameter Handler returned status FAILED: Resource of type 'AWS::SSM::Parameter' with identifier '<name>' was not found. (HandlerErrorCode: NotFound, RequestToken: <uuid>)".
Why: the message is a requirement of the error class, and the wrapped form leaks an internal RequestToken the caller never issued into the one field clients log, match and surface; a client that parses the documented NotFound text does not recognise the refusal.
Fix: the DeleteResource refusal path (the error/ProgressEvent StatusMessage serialization for a missing resource) must report the bare handler message and keep the handler-wrapped form to the read path.
Failing check: cloudcontrol.delete-resource-twice-not-found

Traces: the failing check ids listed per cause above, collected in trace_ids. ## Steps to Reproduce
Boot the emulator; cc = client("cloudcontrol"), cfn = client("cloudformation"), sqs = client("sqs").

Cause 1: cfn.create_stack with a template whose only resource is an AWS::SQS::Queue (QueueName, VisibilityTimeout 45, MessageRetentionPeriod 345600) and an Output Ref'ing it; wait for CREATE_COMPLETE; take the queue URL from DescribeStacks Outputs. cc.get_resource(TypeName="AWS::SQS::Queue", Identifier=<that url>) must return a ResourceDescription whose Properties show VisibilityTimeout 45, and cc.list_resources(TypeName="AWS::SQS::Queue") must enumerate that identifier. It must answer ResourceNotFoundException only after the owning stack is deleted.

Cause 2: cc.create_resource(TypeName="AWS::SQS::Queue", DesiredState=json.dumps({"QueueName": n})) and poll GetResourceRequestStatus to SUCCESS. (a) json.loads(cc.get_resource(TypeName="AWS::SQS::Queue", Identifier=<Identifier>)["ResourceDescription"]["Properties"]) must contain VisibilityTimeout (the queue's current value, not an echo of DesiredState). (b) cc.update_resource(TypeName="AWS::SQS::Queue", Identifier=<Identifier>, PatchDocument=json.dumps([{"op":"replace","path":"/VisibilityTimeout","value":77}])) must be accepted and reach SUCCESS, and GetResource must then report 77; the same holds for /DelaySeconds. (c) submit two such updates concurrently on one queue: exactly one is accepted and exactly one is refused with ConcurrentOperationException (HTTP 409) "Concurrent operation found for resource <Identifier> with RequestToken <accepted request's token>".

Cause 3: cc.create_resource(TypeName="AWS::Logs::LogGroup", DesiredState=json.dumps({"LogGroupName": g})), poll to SUCCESS (GetResource Properties must have no RetentionInDays). cc.update_resource(TypeName="AWS::Logs::LogGroup", Identifier=g, PatchDocument=json.dumps([{"op":"replace","path":"/RetentionInDays","value":7}])) must be refused ValidationException (HTTP 400) with message "[REPLACE Operation] noSuchPath in source, path provided : //RetentionInDays" and must not create the property; the same patch with "op":"add" must succeed, after which the identical replace must succeed. Cause 4: cc.create_resource(TypeName="AWS::SSM::Parameter", DesiredState=json.dumps({"Name": n, "Type": "String", "Value": "v1"})), poll to SUCCESS; cc.delete_resource for it and poll to SUCCESS; call cc.delete_resource again for the same Identifier.
