# AppSync authorization gaps: domain-name and FlushApiCache calls are served to unauthorized principals, and the EvaluateCode/EvaluateMappingTemplate sandbox is still a NotImplemented stub (3 causes)

> _Note: this issue was identified against the code base at commit `1f5faf3c8256779e62f28c9306d3764c9324fb2e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
FlushApiCache

## Description
Three distinct net-new root causes in the AppSync control plane, all of them authorization boundaries. 3 causes in this issue; all three must be closed before submitting. For each cause, the open issue that looks adjacent is named — none of them carries this cause's replay key, so none of them re-runs these checks.

=== Cause 1 of 3: CreateDomainName (and the rest of the domain-name surface) is not gated by identity-based IAM — the request is validated before it is authorized ===
AWS: Smithy (appsync) CreateDomainName — POST /v1/domainnames, required domainName (@length 1-253, @pattern ^(\*[\w\d-]*\.)?([\w\d-]+\.)+[\w\d-]+$) and certificateArn (@length 20-2048, @pattern ^arn:[a-z-]*:(acm|iam):[a-z0-9-]*:\d{12}:(certificate|server-certificate)/[0-9A-Za-z_/-]*$); modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. GetDomainName/UpdateDomainName/DeleteDomainName/ListDomainNames model AccessDeniedException|403 as well. AWS evaluates identity-based policy BEFORE it looks at the request's contents or at the resource, so a principal whose identity policy grants nothing (implicit deny) is refused 403 AccessDeniedException with the IAM-standard message 'User: <principal arn> is not authorized to perform: appsync:<Action> on resource: <resource arn> because no identity-based policy allows the appsync:<Action> action'. Fixed text: 'User: ', ' is not authorized to perform: appsync:', ' on resource: ', ' because no identity-based policy allows the appsync:', ' action'. Variable parts: the caller's IAM user/session ARN, the operation's action name, and the resource ARN derived from the request — arn:aws:appsync:<region>:<account>:domainnames/<domainName> for the per-domain operations and arn:aws:appsync:<region>:<account>:* for ListDomainNames. Recorded behavior additionally pins the authorized path: the unrestricted principal's CreateDomainName with a certificate outside us-east-1 is refused 400 BadRequestException 'Certificate must be in us-east-1.' (fixed sentence, no variable part), and Get/Update/DeleteDomainName on a domain that was never created are refused 404 NotFoundException ('Domain name not found' for Get/Update, 'Domain name not found.' for Delete).
Emulator: the zero-policy principal's CreateDomainName is answered BadRequestException instead of AccessDeniedException — i.e. the handler ran its certificate-region validation and produced a request-validation refusal for a caller that holds no appsync permission at all. The check polls 60s for AccessDeniedException and only ever observes code='BadRequestException'. Open issues 20261024T032443Z-appsync-control-plane-fidelity-domain-name-operations-unimplemented.md, 20261027T212657Z-appsync-custom-domain-names-createdomainname-performs-no-certificate.md and 20261106T124249Z-appsync-listdomainnames-is-not-gated-by-identity-based.md touch the domain-name surface and ListDomainNames IAM gating, but none carries this check's replay key and none covers CreateDomainName/GetDomainName/UpdateDomainName/DeleteDomainName authorization.
Why: a client relying on AWS's ordering cannot distinguish 'you may not call this' from 'your certificate is in the wrong region'. A least-privilege test run against the emulator concludes an unprivileged principal is blocked by validation when in fact nothing authorizes the call, and the same principal would be refused 403 by AWS. Worse, the 400 leaks that the request reached service-side validation.
Fix: the request authorization layer must evaluate identity-based policy for appsync:CreateDomainName / GetDomainName / UpdateDomainName / DeleteDomainName / ListDomainNames and emit 403 AccessDeniedException with the implicit-deny message before the CreateDomainName handler's certificate validation runs.
Traces: appsync.access-denied-domain-name.

=== Cause 2 of 3: FlushApiCache ignores an explicit IAM Deny and answers the resource-state refusal instead ===
AWS: Smithy (appsync) FlushApiCache — DELETE /v1/apis/{apiId}/FlushCache, required apiId (httpLabel); modeled errors BadRequestException|400, ConcurrentModificationException|409, InternalFailureException|500, NotFoundException|404, UnauthorizedException|401. AWS enforces identity-based policy first: a principal whose policy carries an explicit Deny on appsync:FlushApiCache for the API is refused 403 AccessDeniedException with 'User: <session arn> is not authorized to perform: appsync:FlushApiCache on resource: <resource arn> with an explicit deny in an identity-based policy' — fixed text 'User: ', ' is not authorized to perform: appsync:FlushApiCache on resource: ', ' with an explicit deny in an identity-based policy'; variable parts are the assumed-role session ARN and the resource ARN built from the request, arn:aws:appsync:<region>:<account>:/v1/apis/<apiId>/FlushCache. Recorded behavior pins the authorized path for the same call on an API that holds no cache: 404 NotFoundException with the fixed sentence 'Unable to flush the cache as it doesn't exist, please create the cache first.'
Emulator: the explicitly-denied principal is served the resource-state refusal — NotFoundException — so the Deny is never enforced; the check polls 60s and the last observation is code='NotFoundException' where AccessDeniedException was required. Open issue 20261029T174359Z-appsync-no-iam-deny-gate-on-flushapicache-listdomainnames.md describes this defect class (its Cause 1), but its replay key for this check is a harness Timeout at run#10; the check now fails on an assertion against NotFoundException, so that issue does not carry this key and will not re-run it. The operation now reaches its handler and refuses correctly on resource state — only the authorization gate in front of it is missing.
Why: an explicit Deny is the strongest control AWS offers, and a cache flush changes what every consumer of the API reads. A policy/guardrail test passes against the emulator while the real deployment refuses the principal with 403, and conversely a client that treats NotFoundException as 'nothing to flush, carry on' silently proceeds where AWS would have blocked it.
Fix: the request authorization layer must evaluate identity-based policy for appsync:FlushApiCache (including explicit Deny) and return 403 AccessDeniedException before the FlushApiCache handler inspects cache state.
Traces: appsync.access-denied-flush-api-cache.

=== Cause 3 of 3: EvaluateCode/EvaluateMappingTemplate answer the scaffold error NotImplemented, so the sandbox is unusable and its IAM gate is unverifiable ===
AWS: Smithy (appsync) EvaluateCode — POST /v1/dataplane-evaluatecode, required runtime (AppSyncRuntime), code (@length 1-32768) and context (@length 2-28000); output evaluationResult/error/logs/stash/outErrors; modeled errors AccessDeniedException|403, BadRequestException|400, InternalFailureException|500. EvaluateMappingTemplate — POST /v1/dataplane-evaluatetemplate, required template (@length 2-65536) and context (@length 2-28000), same three modeled errors. A principal whose identity policy allows appsync:EvaluateCode / appsync:EvaluateMappingTemplate on Resource '*' gets 200 with an evaluationResult; after the grant is removed the identical call is refused 403 AccessDeniedException with 'User: <user arn> is not authorized to perform: appsync:<EvaluateCode|EvaluateMappingTemplate> on resource: arn:aws:appsync:<region>:<account>:* because no identity-based policy allows the appsync:<action> action' (same fixed/variable split as Cause 1); reattaching the identical grant restores the 200.
Emulator: every call is refused with error code 'NotImplemented' ('operation EvaluateCode is scaffolded but not implemented in this emulator') — a code AppSync does not model at all — even under an identity policy that grants the action, so the granted path never succeeds and the denied path can never be told apart from it. Open issues 20261024T032443Z-appsync-evaluatecode-stub.md and 20261029T174359Z-appsync-evaluatemappingtemplate-stub.md record the two scaffold stubs, but neither carries this check's replay key, so the grant/deny/re-grant contract this check pins stays unverified after the stubs are implemented; whoever implements them must also put the authorization gate in front of them.
Why: resolver-development tooling (the AppSync console sandbox, `aws appsync evaluate-code`, CI checks that lint resolver code) gets an unmodeled error its error handling cannot classify, and any test of who may use the sandbox cannot run at all.
Fix: implement the EvaluateCode and EvaluateMappingTemplate handlers (services/service-com-amazonaws-appsync-awsdeepdishcontrolplaneservice/src/ops/evaluate_code.rs and .../evaluate_mapping_template.rs) and authorize both operations in the request authorization layer so a principal without the action is refused 403 AccessDeniedException with the implicit-deny message rather than NotImplemented.
Traces: appsync.access-denied-sandbox-eval.

## Evidence
Cause 1 — expected ('AccessDeniedException', "User: <denied user arn> is not authorized to perform: appsync:CreateDomainName on resource: arn:aws:appsync:<region>:<account>:domainnames/<domain> because no identity-based policy allows the appsync:CreateDomainName action"). Actual: no AccessDeniedException in 60s of polling — 'AssertionError: CreateDomainName denied for the unauthorized principal not met within 60.0s; last code=\'BadRequestException\'' (check_appsync_access_denied_domain_name.py line 86 -> _poll_until_denied line 37). The check never reached its Get/Update/Delete/ListDomainNames labels, so only CreateDomainName is observed here; the same gate is missing in front of all five.

Cause 2 — expected ('AccessDeniedException', "User: <assumed-role session arn> is not authorized to perform: appsync:FlushApiCache on resource: arn:aws:appsync:<region>:<account>:/v1/apis/<apiId>/FlushCache with an explicit deny in an identity-based policy") for a session whose role policy is Allow appsync:* plus Deny appsync:FlushApiCache. Actual: 'AssertionError: expected AccessDeniedException, got NotFoundException' (check_appsync_access_denied_flush_api_cache.py line 48, after the 60s propagation poll at lines 984-990) — the denied principal is handed the same 404 'Unable to flush the cache as it doesn't exist, please create the cache first.' that the unrestricted principal must get.

Cause 3 — expected a 200 EvaluateCode response (the check's 'UNEXPECTED_SUCCESS' sentinel) while the user policy grants appsync:EvaluateCode on '*'. Actual: 'AssertionError: the identity policy becomes effective for appsync:EvaluateCode not reached within 90s; last observation \'NotImplemented\'' (check_appsync_access_denied_sandbox_eval.py line 110 -> _poll line 28); message 'operation EvaluateCode is scaffolded but not implemented in this emulator'. EvaluateMappingTemplate is the same stub, so the check's later deny/re-grant assertions on both operations are unreachable.

## Steps to Reproduce
