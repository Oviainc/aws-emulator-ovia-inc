# ElastiCache: CreateServerlessCache refuses every real subnet id, the bogus MajorEngineVersion refusal uses the wrong error code, and two parameter-group refusal messages diverge from AWS (4 causes)

> _Note: this issue was identified against the code base at commit `7fd8acd3be042b6d00a1996e0a0d05df0b6f87ae`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateServerlessCache

## Description
FOUR net-new root causes in the elasticache crate, all in the SAME service. Cause 1 makes the entire serverless-cache surface unreachable; causes 3 and 4 are refusals where the status and error code are right and only Error.Message diverges from AWS's sentence for that error class. Each cause must be closed separately.

Relationship to open issues: 20261023T155010Z-elasticache-control-plane-is-unusable-end-to-end.md describes the SAME subnet-resolution defect as its Cause 1, but only for the CreateCacheSubnetGroup handler, and it no longer carries the replay keys of the serverless checks below (the replay report lists every check in this issue as unowned). 20261103T145814Z-elasticache-refusal-messages-diverge-from-aws-on-three.md states the DeleteCacheParameterGroup not-found wording, not the DescribeCacheParameterGroups one in Cause 4. The fixed issue 20261029T174147Z-elasticache-error-messages-diverge-from-aws-across-six.md recorded the "value:... is outside of range:..." template for the NUMERIC parameter slowlog-max-len; Cause 4 below shows that template is now applied to enum parameters too, where AWS uses a different sentence. Neither this nor Cause 3 is a call left refused — in every one of them the refusal decision is correct.

Cause 1 of 4: CreateServerlessCache refuses every subnet id EC2 actually holds, so no serverless cache can ever be created.
AWS: Smithy (services/service-com-amazonaws-elasticache-amazonelasticachev9/smithy-model/com-amazonaws-elasticache-amazonelasticachev9.json): CreateServerlessCache takes SubnetIds (SubnetIdsList, optional) and models InvalidParameterValueException {errorKind client, httpError 400, awsQueryError InvalidParameterValue/400} plus ServerlessCacheAlreadyExistsFault/ServerlessCacheNotFoundFault. The model does not state when subnets are refused, so recorded behavior only: subnet ids that EC2 CreateSubnet returned in the caller's VPC are ACCEPTED with HTTP 200 and the cache is created in them (Status 'creating', then 'available'); only an id that names no subnet is refused, with HTTP 400 InvalidParameterValue and the fixed text "Some input subnets in :[" + the offending ids, comma-space separated + "] are invalid."
Emulator: every freshly created EC2 subnet id is refused with HTTP 400 InvalidParameterValue and that same template — i.e. the emulator classifies real subnets as nonexistent. The ids in the recorded message are this run's generated subnet ids filling the template's variable part; the fixed text is AWS's. This is the identical failure mode the open control-plane issue documents for CreateCacheSubnetGroup: the elasticache crate resolves a subnet id against a synthetic per-Region derived catalog (crate::state::resolve_subnet / region_subnets) instead of the subnets the EC2 service holds.
Why: CreateServerlessCache is the first call of every serverless flow. A client that creates a VPC and subnets and then asks for a serverless cache is blocked at call one, and eight checks covering the serverless lifecycle, its snapshots, its usage limits and its name-collision and not-found contracts never reach the behavior they test.
Fix: the subnet resolution used by the CreateServerlessCache handler in the elasticache crate (the shared crate::state::resolve_subnet / region_subnets helper the create_cache_subnet_group handler also calls) must resolve a subnet id against the subnets EC2 holds, and keep refusing only ids that name nothing.
Traces: elasticache.create-serverless-cache-conflicting-name-rejected, elasticache.create-serverless-cache-usage-limit-out-of-range-rejected, elasticache.e2e-serverless-snapshot-restore-flow, elasticache.serverless-cache-description-omitted-normalizes-to-single-space, elasticache.serverless-cache-lifecycle, elasticache.serverless-cache-snapshot-full-lifecycle, elasticache.serverless-cache-snapshot-retention-limit-out-of-range-rejected, elasticache.serverless-snapshot-not-found-semantics, elasticache.deploy-serverless-cache-cfn-invalid-engine-version-rejected.

Cause 2 of 4: a MajorEngineVersion that does not exist is refused with the wrong error code and message.
AWS: Smithy: CreateServerlessCache models BOTH InvalidParameterCombinationException {client, httpError 400, awsQueryError InvalidParameterCombination/400} and InvalidParameterValueException {client, 400, InvalidParameterValue/400}, and MajorEngineVersion is a free String (no enum, no pattern), so the version catalog is enforced server-side and the code/message is the whole diagnosis. Recorded behavior for Engine=redis with a MajorEngineVersion that is not offered: HTTP 400, code InvalidParameterCombination, message = the fixed text "Specified engine does not support major engine version (" + the request's MajorEngineVersion + ")." — the version in parentheses is the only variable part, taken from the request.
Emulator: answers code InvalidParameterValue for that call, so a client that keys on the combination error (or on the per-code retry/report path) does not recognise the refusal. Hypothesis: the code observed is the Cause 1 subnet refusal arriving before any engine-version check, since the same call also carries SubnetIds; once Cause 1 is fixed this call must be re-checked and must answer InvalidParameterCombination with AWS's sentence, and must leave no cache behind.
Why: the two codes are distinguishable on real AWS; a client told InvalidParameterValue is pointed at a single bad member when the service is reporting an incompatible Engine/MajorEngineVersion pair, and a CFN stack carrying that template must roll back for that reason.
Fix: the CreateServerlessCache handler's engine/major-version validation in the elasticache crate — it must run after subnet resolution succeeds, raise InvalidParameterCombinationException, and word the message as AWS does.
Traces: elasticache.deploy-serverless-cache-cfn-invalid-engine-version-rejected.

Cause 3 of 4: ModifyCacheParameterGroup uses the numeric out-of-range sentence for an ENUM parameter.
AWS: Smithy: ModifyCacheParameterGroup models InvalidParameterValueException {client, httpError 400, awsQueryError InvalidParameterValue/400}; the model states nothing about the text, so recorded behavior only — AWS emits two sibling templates chosen by the parameter's own metadata. For a parameter whose AllowedValues is an enumerated list (maxmemory-policy -> "volatile-lru,allkeys-lru,volatile-lfu,allkeys-lfu,volatile-random,allkeys-random,volatile-ttl,noeviction"; acl-pubsub-default -> "allchannels,resetchannels"), the message is the fixed text "invalid parameter value, allowed values are:" followed by that AllowedValues string exactly as DescribeCacheParameters reports it, and the rejected value is NOT echoed. For a parameter whose AllowedValues is a numeric range (slowlog-max-len -> "0-") the message is the other template, "value:" + the rejected ParameterValue + " is outside of range:" + AllowedValues — that one was recorded in the fixed issue 20261029T174147Z and must keep working.
Emulator: answers 400/InvalidParameterValue (correct) but emits the range template for enum parameters too: "value:<rejected value> is outside of range:<AllowedValues>" where AWS says "invalid parameter value, allowed values are:<AllowedValues>". The same wrong template appears when the illegal value is one entry of a mixed ParameterNameValues batch, where the message is the only thing naming which member was refused.
Why: the message is the whole diagnosis for this error class; a client, fixture or tool matching AWS's enum sentence does not recognise the refusal, and the per-parameter-kind distinction a caller can observe on AWS is erased. The refusal decision and the effect-absence (the parameter stays at its prior value and Source) are already correct.
Fix: the ModifyCacheParameterGroup handler's parameter-value validation in the elasticache crate must select the message template from the parameter's AllowedValues kind (enumerated list vs numeric range), not emit one template for both.
Traces: elasticache.cache-parameter-invalid-value-rejected, elasticache.modify-cache-parameter-invalid-value-rejected, elasticache.parameter-value-outside-allowed-values-rejected, elasticache.modify-parameter-group-batch-atomicity-on-unknown-parameter.

Cause 4 of 4: DescribeCacheParameterGroups' CacheParameterGroupNotFound message uses the colon-form template.
AWS: Smithy: DescribeCacheParameterGroups models CacheParameterGroupNotFoundFault {client, httpError 404, awsQueryError CacheParameterGroupNotFound/404}. Recorded behavior only for the text: on DescribeCacheParameterGroups the message is the type name, then the group name, then the words — "CacheParameterGroup " + the request's CacheParameterGroupName + " not found." (with the trailing period). This is a third sibling of the colon-form templates the other parameter-group operations use ("CacheParameterGroupnot found: <name>" on Delete/DescribeCacheParameters/Reset, "CacheParameterGroup not found: <name>" on Modify and on CreateCacheCluster's resolution); the only variable part in all of them is the request-supplied name.
Emulator: DescribeCacheParameterGroups now answers 404/CacheParameterGroupNotFound with "CacheParameterGroup not found: <name>" — the Modify-style colon form — so the name/words order AWS uses on this operation is never produced. The shared not-found helper appears to have been pointed at the colon form for every caller.
Why: this is the read a client uses to confirm a group is gone (after a delete, or when probing a name before creating it); a caller or fixture matching AWS's sentence sees an unrecognised refusal, and the per-operation distinction AWS exposes is lost.
Fix: the DescribeCacheParameterGroups handler's not-found path in the elasticache crate must use its own template rather than the shared colon-form helper, while the Delete/Modify/Reset forms keep theirs.
Traces: elasticache.delete-default-parameter-group-forbidden, elasticache.tags-add-list-remove.
