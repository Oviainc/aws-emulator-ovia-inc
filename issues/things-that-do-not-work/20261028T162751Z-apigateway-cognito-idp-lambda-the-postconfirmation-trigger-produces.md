# apigateway__cognito-idp__lambda: the PostConfirmation trigger produces no effect because Lambda Invoke (RequestResponse) still answers 501 NotImplemented instead of running the deployment package (1 cause)

> _Note: this issue was identified against the code base at commit `eba09938c5757f116b88f59710a766eb7f22de4f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation

## Description
Attribution note: the grounding check's leading token is the composite "apigateway__cognito-idp__lambda", so this issue is filed under that token; apigateway, cognito-idp (cognito-identity-provider) and lambda are all bootstrapped, so the per-service gate is FILE. The diverging operation is Lambda's Invoke.

One net-new root cause, re-grounded in a check that no open issue carries the replay key for.

Cause 1 of 1 - a synchronous (RequestResponse) Invoke of a deployed, Active function is refused rather than executed, so a user-pool Lambda trigger that Cognito now DOES dispatch still has no observable effect.

AWS: Smithy (lambda, services/service-com-amazonaws-lambda-awsgirapiservice/smithy-model/com-amazonaws-lambda-awsgirapiservice.json): Invoke is POST /2015-03-31/functions/{FunctionName}/invocations with success code 200; output InvocationResponse carries StatusCode (@httpResponseCode), Payload (@httpPayload blob = exactly what the handler returned), ExecutedVersion (X-Amz-Executed-Version, matching ^(\$LATEST|[0-9]+)$) and FunctionError (X-Amz-Function-Error) ONLY when the function itself failed. Invoke's modeled error set is large (InvalidRequestContentException 400, ResourceNotFoundException 404, RequestTooLargeException 413, TooManyRequestsException 429, ServiceException 500, the 502 ENI/KMS/runtime family, ...) and contains NO NotImplemented error at all: a function that resolves and is Active is executed and the caller gets its payload. Default InvocationType is RequestResponse. Composed with the recorded Cognito behavior, a pool whose LambdaConfig.PostConfirmation names an invokable function has that function RUN once when AdminConfirmSignUp completes a sign-up, with an event carrying triggerSource="PostConfirmation_ConfirmSignUp", userName = the confirmed username, userPoolId = the pool id, and request.userAttributes holding the attributes supplied to SignUp - and whatever the handler body does (here: sqs:SendMessage of those four fields) actually happens. Those four field names are the fixed part of the contract; their values come from the request and the emulator's own state (generated pool id, generated username, that username's email) and are never fixed text.

Emulator: the Cognito side of the dispatch now issues the invocation (see the Resolution of the already-FIXED 20261026T100510Z-apigateway-cognito-idp-lambda-the-postconfirmation-user-pool.md, which added the trigger dispatch in services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/lambda_triggers.rs), but Lambda refuses to run the package: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs documents that "Running the deployment package is NOT implemented ... RequestResponse answers HTTP 501", and the error the caller sees is code NotImplemented (HTTP 501) whose message states the function ARN resolved at version $LATEST but that running its python3.12 deployment package is not implemented. The handler body therefore never executes, no SQS message is ever produced, and the check hangs in its ReceiveMessage poll until the harness cap: `[mismatch] apigateway__cognito-idp__lambda.cognito-post-confirmation-trigger-invokes-lambda - Error: Check timed out after 60.0s`. Both Cognito calls (SignUp, AdminConfirmSignUp) return success, so nothing surfaces to the client. Requirement restated precisely: HTTP 200 with StatusCode 200, ExecutedVersion $LATEST and the handler's bytes in Payload; the diverging status/code/message is `501` / `NotImplemented` / "Invoke resolved <function arn> at version $LATEST, but running its <runtime> deployment package is not implemented in this emulator..." - the fixed text there is emulator-authored and has no counterpart in AWS, and the ARN/runtime in it are per-request values, not part of any contract.

Why: every flow whose outcome is produced INSIDE a function body is unreachable. A client sees a confirmed user, a 200 from the confirmation call and a dispatched trigger, but none of the state the trigger was supposed to create (profile row, group membership, downstream queue/table write, welcome notification). Because NotImplemented is not a modeled Invoke error, a caller cannot distinguish it from a real FunctionError or a service refusal, and no retry/compensation path a client has can fire. The same gap makes every Cognito trigger whose verdict is read back from the function (PreSignUp abort, PreTokenGeneration overrides, UserMigration, CustomEmailSender) permanently unobservable.

Fix: the Invoke handler's execution path in the lambda service (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs) - an in-process or sandboxed runtime for the function's deployment package, and at minimum a faithful 200 + StatusCode/Payload/ExecutedVersion path for a function that resolved, plus the error mapping, which must never answer NotImplemented for a resolved, Active function. Preserve the existing DryRun and Event paths. The already-open 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md describes the same execution gap but is grounded in lambda__s3__s3control.xsvc-s3-3-access-point-policy-denied-lambda-role-still-reads-bucket-directly and does not carry this check's replay key, so this check is still unowned; the Cognito-side dispatch itself is NOT the defect here (that was fixed by 20261026T100510Z).

## Evidence
Cause 1: expected - after CreateUserPool(LambdaConfig={'PostConfirmation': <fn arn>}), SignUp(Username=<generated>, UserAttributes=[{'Name':'email','Value':'<generated>@example.com'}]) and AdminConfirmSignUp(UserPoolId=<pool id>, Username=<generated>), the PostConfirmation function RUNS once; its handler's sqs:SendMessage lands a message whose body satisfies triggerSource == 'PostConfirmation_ConfirmSignUp', userName == the signed-up username, userPoolId == the created pool's id and email == the email supplied to SignUp. Per the Smithy model, the invocation Cognito issues answers HTTP 200 with StatusCode 200, ExecutedVersion $LATEST and the handler's return value in Payload; Invoke models no NotImplemented error.
Actual - the RequestResponse invocation is refused with HTTP 501, error code NotImplemented, message "Invoke resolved arn:aws:lambda:<region>:<account>:function:<name> at version $LATEST, but running its python3.12 deployment package is not implemented in this emulator: there is no in-process runtime for it, and no response payload is returned that the function did not produce. InvocationType=DryRun validates an invocation without running the function." (fixed text emulator-authored, with the function ARN and runtime filled from the request/state). Consequently the queue stays empty on every ReceiveMessage (WaitTimeSeconds=5, retried against the check's 90 s budget) and the harness reports `Check timed out after 60.0s`. Both Cognito calls returned 2xx with no error code. Current-HEAD confirmation: services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs, lines 24-30 ("Running the deployment package is NOT implemented ... RequestResponse answers HTTP 501"). No per-run value (pool id, username, function name, queue URL, request id) is part of the requirement.
