# xray does not enforce an explicit IAM Deny: StartTraceRetrieval succeeds under credentials whose identity policy denies xray:StartTraceRetrieval (1 cause)

> _Note: this issue was identified against the code base at commit `885965a44b7ceb28a47f9ba92cf63bd950a83073`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
ONE net-new root cause in the X-Ray service. The check carries SERVICES = ["xray"], and xray is bootstrapped and answering (135/159 xray checks pass in this run), so this is a fidelity defect, not a bootstrap gap. The failing check is NOT marked ALREADY FILED or OWNED in this replay report.

RELATED, NOT COVERING / OWNERSHIP NOTE: open issue 20261025T043615Z-xray-3-net-new-behavioral-root-causes-getservicegraph.md describes this same authorization gap as its Cause 3 and lists this check id, but it does so against a DIFFERENT observed failure signature (it recorded the check as `Check timed out after 60.0s`, keyed `xray.start-trace-retrieval-missing-permission-denied|_poll_until_code#17|Timeout|time.sleep(interval_s)`). The replay report therefore did not mark this check as owned, and the surviving evidence is filed here. A fixer closing either issue should re-replay the check id below.

Cause 1 of 1: X-Ray requests are not authorized against the caller's IAM identity-based policy — an explicit Deny on xray:StartTraceRetrieval is silently ineffective and the operation answers success.
AWS: recorded behavior only for the authorization layer. Smithy (services/service-com-amazonaws-xray-awsxray/smithy-model/com-amazonaws-xray-awsxray.json) models StartTraceRetrieval as POST /StartTraceRetrieval, success 200, required TraceIds/StartTime/EndTime, output RetrievalToken, with modeled errors InvalidRequestException (400), ResourceNotFoundException (404) and ThrottledException (429); AccessDeniedException is the IAM authorization layer's refusal and is deliberately not in the operation's modeled error set. The recording shows that a request signed with an IAM user's own access key, whose inline policy is {Allow xray:* on *} plus {Deny xray:StartTraceRetrieval on *}, is refused with HTTP 403, error code `AccessDeniedException` and message `User: <caller user ARN> is not authorized to perform: xray:StartTraceRetrieval with an explicit deny in an identity-based policy`. In that message the fixed text is `User: ` / ` is not authorized to perform: ` / ` with an explicit deny in an identity-based policy`; the variable parts are the resolved caller's user ARN (from the signing credentials / IAM state) and the action name `xray:StartTraceRetrieval` (the operation being dispatched) — no value from any single run belongs in the template. The same recording shows the refusal is scoped to the denied action only: an unrelated action (GetSamplingRules) keeps succeeding under the identical credentials, and once the Deny statement is removed the call reverts to its IAM-independent outcome (here ResourceNotFoundException, because with the XRay trace-segment destination there is no aws/spans log group, or 200 if the destination is CloudWatchLogs).
Emulator: the pre-Deny leg behaves correctly (the call reaches the service layer and lands on an IAM-independent outcome), but after put_user_policy attaches {Allow xray:* on *} + {Deny xray:StartTraceRetrieval on *}, the identical signed StartTraceRetrieval keeps returning success for the full 90 s convergence poll (polled every 2 s). The suite reports `AssertionError: start_trace_retrieval once the Deny is attached never converged on frozenset({'AccessDeniedException'}) within 90.0s; last observed 'UNEXPECTED_SUCCESS'`. No AccessDeniedException is ever produced, so neither the 403 status, the error code, nor the message text exists in the emulator for this surface. That the pre-Deny leg passes and only the Deny leg fails locates the defect precisely at the request-authorization step, not in the operation handler.
Why: a client cannot validate a least-privilege X-Ray policy against the emulator. A call that production refuses with 403 AccessDeniedException is reported as a 200 success with a retrieval token, which is the failure direction that hides real breakage — a deploy that passes against the emulator then breaks in AWS. Conversely any automation, policy test or guardrail that asserts AccessDeniedException for an unauthorized principal can never pass, and a Deny-based blast-radius control is unverifiable.
Fix: the xray request-authorization path, ahead of operation dispatch: resolve the signing identity, evaluate its IAM identity-based policy with explicit-Deny-first semantics, and on refusal return HTTP 403 with error code AccessDeniedException and the standard `is not authorized to perform` text, instead of falling through to the operation handler (services/service-com-amazonaws-xray-awsxray request authorization, shared with the emulator's IAM policy evaluator).
