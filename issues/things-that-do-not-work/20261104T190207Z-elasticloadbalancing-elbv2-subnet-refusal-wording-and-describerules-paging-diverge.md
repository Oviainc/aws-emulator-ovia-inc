# ELBv2 subnet refusal wording and DescribeRules paging diverge from AWS

> _Note: this issue was identified against the code base at commit `96b1cd775c53225a6d4bf8c1fc7ed76785b74794`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateLoadBalancer

## Description
Three net-new wire divergences on the ELBv2 (elasticloadbalancing) surface. Causes 1 and 2 share one root: a placement operation that must refuse a subnet the account does not hold relays the EC2 lookup's own sentence into the ELB error shape's Message instead of the sentence ELB words for that refusal class. Cause 3 is a paginated read that ends a page early. All three are on the same service and the same crate (services/service-com-amazonaws-elasticloadbalancingv2-elasticloadbalancing-v10). A fixer must close ALL THREE before submitting.

Cause 1 of 3: CreateLoadBalancer with a subnet id the account holds no subnet for.
AWS: Smithy: CreateLoadBalancer declares SubnetNotFoundException (awsQueryError code "SubnetNotFound", httpResponseCode 400) and InvalidSubnetException (code "InvalidSubnet", 400) for the Subnets/SubnetMappings members; the model states nothing about the refusal text, so for the message this is recorded behavior only. The recorded AWS response is HTTP 400 whose ErrorResponse/Error/Code the emulator already matches, with ErrorResponse/Error/Message exactly the bare EC2 error-code token 'InvalidSubnetID.NotFound' — that whole string is FIXED text for this class and it carries NO variable part at all (no subnet id, no service name, no request id).
Emulator: answers HTTP 400 with the right Code but Error.Message "The subnet ID '<subnet-id>' does not exist (Service: AmazonEC2; Status Code: 400; Error Code: InvalidSubnetID.NotFound; Request ID: <uuid>; Proxy: null)" — EC2's full SDK-style refusal relayed verbatim. Fixed text of the emulator's sentence: "The subnet ID '...' does not exist (Service: AmazonEC2; Status Code: 400; Error Code: InvalidSubnetID.NotFound; Request ID: ...; Proxy: null)"; its variable parts are the subnet id from the request and a per-run request id. The per-run id is NOT the finding — the whole sentence is wrong for this class, and it additionally injects a per-run value into a message AWS keeps constant.
Why: a client that branches on the ELB refusal text (CLI diagnostics, IaC error matching, retry/branch logic, pinned test assertions) never sees AWS's 'InvalidSubnetID.NotFound' message, so it reports an unexpected failure even though status and code are right; it also leaks the cross-service detail that ELB asked EC2, plus a request id that changes on every call, which AWS's ELBv2 surface never exposes here.
Emulator: the message is built at the error-construction site in the CreateLoadBalancer handler from the EC2 lookup's relayed sentence, not worded by ELB.
Fix: the error-construction site in the CreateLoadBalancer handler (its refusal wording), together with the shared refusal-message helpers in this crate's state module, so the relayed EC2 sentence is replaced by the message ELB itself states for a subnet it cannot resolve. Do not change the status or the code — both already match.
Traces: elasticloadbalancing-elbv2-distinct-error-conditions#task#1, and the same cause on elbv2-load-balancer-listener-rule-lifecycle-error-conditions#task#3, elbv2-loadbalancer-creation-subnet-validation-error#task#1, elbv2err-create-load-balancer-input-rejections#task#6.

Cause 2 of 3: SetSubnets with a subnet id the account holds no subnet for.
AWS: Smithy: SetSubnets declares SubnetNotFoundException (awsQueryError code "SubnetNotFound", 400) and InvalidSubnetException (code "InvalidSubnet", 400); again the model is silent on the text, so recorded behavior only. The recorded AWS response is HTTP 400 with the matching Code and ErrorResponse/Error/Message exactly 'InvalidSubnetID.NotFound' — entirely fixed text, no variable part.
Emulator: answers HTTP 400 with the right Code but Error.Message "The subnet ID '<subnet-id>' does not exist (Service: AmazonEC2; Status Code: 400; Error Code: InvalidSubnetID.NotFound; Request ID: <uuid>; Proxy: null)" — the same relayed EC2 sentence as cause 1, from the same lookup.
Why: same as cause 1, on the reconfiguration path: a caller changing a load balancer's subnets cannot match ELB's documented refusal text and sees an EC2-shaped message instead.
Fix: the error-construction site in the SetSubnets handler and the same shared refusal-message helper as cause 1, so both placement paths word one ELB message for an unresolvable subnet.
Traces: elbv2env-alb-create-provisioning-and-subnet-reconfig#task#9.

Cause 3 of 3: DescribeRules truncates a listener's rule selection to one rule and hands back a NextMarker AWS does not send.
AWS: Smithy: DescribeRules is @paginated(inputToken: Marker, outputToken: NextMarker, items: Rules); PageSize is an integer with @range min 1 max 400 and is documented "The maximum number of results to return with this call"; NextMarker is documented "If there are additional results, this is the marker for the next set of results. Otherwise, this is null." For this recorded step AWS returns the listener's remaining rules — three Rules entries, including the non-default rules at Priority 20 and Priority 30 with their path-pattern conditions and fixed-response actions — in ONE page, with NextMarker absent (null).
Emulator: answers HTTP 200 with only the FIRST of those rules (Rules.member[1] and Rules.member[2] missing) and a NextMarker present, i.e. it reports the selection as having further pages when AWS reported it complete. Replay detail: "$.DescribeRulesResponse.DescribeRulesResult.Rules.member[1]: missing ... member[2]: missing ... NextMarker: unexpected_present". The specific marker string and the recorded rule ARNs are per-run values, not requirements; the requirement is that this request's page holds the whole remaining selection and NextMarker is omitted.
Why: a client that does not paginate (the case the operation's own contract covers by returning everything when the call asks for no page limit) sees one rule out of three and silently routes or renders an incomplete rule set; a client that does paginate is handed a marker for a page that AWS says does not exist. This is silent data loss in a read, which is why this bundle is HIGH.
Fix: the DescribeRules handler's page step and the shared page walk it calls (this crate's state pagination helper, src/state/pagination.rs, reached from src/ops/describe_rules.rs around the crate::state::paginate call): the page limit applied to this request must be the one the request actually carries — a call that names no limit, including one resuming at a Marker, must return the whole remaining selection and omit NextMarker, and NextMarker must be emitted only when items remain beyond the page served. Hypothesis: a page size is applied to this call that the call did not carry (a default, or one carried over from the earlier page of the same walk), so the walk stops a page early.
Traces: elbv2env-listener-attributes-targets-and-rule-pagination#task#17.
