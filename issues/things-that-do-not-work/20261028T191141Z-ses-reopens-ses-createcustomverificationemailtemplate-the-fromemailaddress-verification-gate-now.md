# REOPENS ses CreateCustomVerificationEmailTemplate: the FromEmailAddress verification gate now refuses the account's own freshly verified sender, so no custom verification email template can be created at all (1 cause)

> _Note: this issue was identified against the code base at commit `7027025c5fd5dfe34e91978241957b132a94afec`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
REOPENS 20261028T091851Z-ses-2-net-new-behavioral-root-causes-v1.md: its fix left the call refused.

This issue carries ONE net-new root cause, grounded in 2 failing checks. Neither check is marked ALREADY FILED nor OWNED in the replay report.

Cause 1 of 1: CreateCustomVerificationEmailTemplate refuses 400 FromEmailAddressNotVerified for an email identity THIS account verified through this same API moments earlier, so the operation's success path (and every reader of a created template) is unreachable in a single verify-then-create call sequence.

AWS: Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery) CreateCustomVerificationEmailTemplate input {TemplateName, FromEmailAddress: FromAddress, TemplateSubject, TemplateContent, SuccessRedirectionURL, FailureRedirectionURL — all required} / output Unit; modelled errors CustomVerificationEmailInvalidContentException, CustomVerificationEmailTemplateAlreadyExistsException, FromEmailAddressNotVerifiedException (errorKind client, awsQueryError code "FromEmailAddressNotVerified", httpResponseCode 400) and LimitExceededException. FromEmailAddressNotVerifiedException is documented "Indicates that the sender address specified for a custom verification email is not verified, and is therefore not eligible to send the custom verification email" — i.e. it is the refusal for an address that is NOT a verified sending identity of the account, and nothing else. For an address that IS a verified sending identity the call is a 200 with an empty body, and GetCustomVerificationEmailTemplate (output {TemplateName, FromEmailAddress, TemplateSubject, TemplateContent, SuccessRedirectionURL, FailureRedirectionURL}, only modelled error CustomVerificationEmailTemplateDoesNotExistException, 400) then echoes the stored FromEmailAddress and TemplateSubject. VerifyEmailIdentity itself models no errors and no status member; on AWS the identity reaches VerificationStatus 'Success' (GetIdentityVerificationAttributes -> VerificationAttributes map, required) only after the address's owner follows the confirmation link — an out-of-band step neither a check nor an emulator can perform, which is why every eligible-sender path in this emulator has to be reachable from the API surface itself (recorded behavior only for how that completion is reached).

Emulator: the negative half of the contract now works — an address whose verification was merely requested is refused, so the gate added by the fixed issue 20261028T091851Z-ses-2-net-new-behavioral-root-causes-v1.md (Cause 2) is in place. But the POSITIVE half is refused as well: the only way a caller can register an email identity on this surface is VerifyEmailIdentity, and the identity store records it as VerificationStatus Pending with the move to Success owed to the wall clock IDENTITY_VERIFICATION_SPAN later (services/service-com-amazonaws-ses-simpleemailservice/src/state.rs, IDENTITY_VERIFICATION_SPAN = 3s; ComAmazonawsSesSimpleemailserviceState::verify_identity sets verification_status = Pending and verification_due = now + span; settle_identities/is_verified_sender are what the handler reads). CreateCustomVerificationEmailTemplate called straight after that VerifyEmailIdentity therefore answers HTTP 400, Error.Code 'FromEmailAddressNotVerified', message "From email address <sim2real-ses-sender-1edd88e7dc4f@example.com> is not verified." — fixed text "From email address <" … "> is not verified." with the address taken verbatim from the request's FromEmailAddress; the address shown is a per-run value, not part of the requirement. No API call on this surface can complete the verification, so a caller that does not sleep on a wall clock has NO eligible sender and the operation can never succeed: both checks fail on this one refusal (one at its positive control after the negative assertion passed, one at its very first create).

Why: a client gets a surface on which custom verification email templates cannot be created at all. It verifies the sender with the only operation SES offers for it, receives a 200, and the very next create is refused with the error class AWS reserves for a sender the account has not verified — so the client cannot tell an ineligible sender from an eligible one, has no documented signal to wait for (the refusal is not retryable in any modelled sense), and every downstream read (GetCustomVerificationEmailTemplate, UpdateCustomVerificationEmailTemplate, SendCustomVerificationEmail) is unreachable. The two fixed issues interact: 20261025T214303Z-ses-identity-verification-is-auto-completed-and-the.md made a requested identity start Pending, and 20261028T091851Z-ses-2-net-new-behavioral-root-causes-v1.md made this operation gate on verified-for-sending — together they leave the account with no reachable verified email sender.

Fix: the ses v1 identity store's verification settlement plus this handler's sender gate (services/service-com-amazonaws-ses-simpleemailservice/src/state.rs and services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_custom_verification_email_template.rs): an email identity the account registers through VerifyEmailIdentity must become a verified sending identity on a path a caller can reach from the API alone (there is no inbox to click in an emulator), so that the operation's 200 path exists; the FromEmailAddressNotVerified refusal must stay reserved for an address the account never verified, which is what keeps the negative check passing. Reconciling the two is the work: a wall-clock-only transition is not a path any AWS-documented client loop can rely on for a single verify-then-create sequence.

Traces: ses.custom-verification-template-unverified-from-fails (fails at its positive control, after the FromEmailAddressNotVerified negative assertion passes), ses.custom-verification-template-not-found-semantics (fails at its first create, so its DoesNotExist assertions for Get/Update on an absent template are never reached). Adjacent open issue: 20261028T091851Z-ses-listcustomverificationemailtemplates-stub.md (ListCustomVerificationEmailTemplates is an unimplemented scaffold stub) — ses.custom-verification-template-not-found-semantics also lists templates, so that stub must be implemented as well before that check can pass; it does not carry either of these checks' replay keys and does not cover this refusal.
