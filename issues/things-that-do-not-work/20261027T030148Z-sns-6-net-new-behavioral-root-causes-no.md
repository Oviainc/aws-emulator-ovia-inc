# SNS: 6 net-new behavioral root causes — no delivery path for http/https, lambda or firehose subscriptions, Publish ignores the topic KMS key state, and CFN-provisioned topic/subscription pairs never deliver

> _Note: this issue was identified against the code base at commit `464a2835635950cb0afe23fa38546fc133c528e8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Publish

## Description
SIX distinct net-new root causes in the SNS data plane, all grounded in failing behavioral checks of the `sns` service. Each must be closed before this issue is submitted. None of these 16 checks is marked ALREADY FILED or OWNED in the replay report; related open issues are named per cause where they exist, and none of them covers these checks.

--- Cause 1 of 6: SNS has no http/https delivery path at all — no SubscriptionConfirmation, no Notification, no UnsubscribeConfirmation, no SubscribeURL/UnsubscribeURL endpoint ---

AWS: Smithy: SubscribeInput$Protocol documents `http` — "delivery of JSON-encoded message via HTTP POST" — and `https` — "delivery of JSON-encoded message via HTTPS POST". Subscribe on either protocol makes SNS immediately POST a JSON body to the endpoint with `Type: "SubscriptionConfirmation"`, a `MessageId`, the `TopicArn`, a `Token`, a `SubscribeURL` whose query is `Action=ConfirmSubscription&TopicArn=<the topic ARN>&Token=<that token>`, and a `SigningCertURL`; the POST carries headers `x-amz-sns-message-type: SubscriptionConfirmation`, `x-amz-sns-topic-arn: <topic ARN>`, `x-amz-sns-message-id: <that MessageId>`. Until ConfirmSubscription is called with that token GetSubscriptionAttributes reports `PendingConfirmation` = `"true"` and messages published meanwhile are not delivered. After confirmation each Publish is POSTed with `Type: "Notification"` and headers `x-amz-sns-message-type: Notification`, `x-amz-sns-topic-arn`, `x-amz-sns-message-id` (the MessageId Publish returned) and `x-amz-sns-subscription-arn`, the body carrying `MessageId`, `TopicArn`, `Message` and an `UnsubscribeURL` whose query is `Action=Unsubscribe&SubscriptionArn=<that subscription ARN>`. With `RawMessageDelivery` = `true` the POST carries the bare published body, an `x-amz-sns-rawdelivery` header, and NO message attributes in any form (the same publish's SQS raw subscriber does receive them as native SQS MessageAttributes) — recorded behavior plus the SubscribeInput$Attributes `RawMessageDelivery` documentation. An endpoint that answers 500 is retried according to the subscription's DeliveryPolicy (a policy with zero retries is attempted exactly once) and the notification is then written to the queue the subscription's `RedrivePolicy` names ("sends undeliverable messages to the specified Amazon SQS dead-letter queue", SetSubscriptionAttributesInput$AttributeName). An unsigned GET of a notification's UnsubscribeURL deletes the subscription (HTTP 200, `UnsubscribeResponse`) and POSTs an `UnsubscribeConfirmation` to the endpoint — unless ConfirmSubscription was called with `AuthenticateOnUnsubscribe="true"`, in which case that anonymous GET is refused HTTP 403 with error code `AuthorizationError` and the fixed message "This subscription may only be deleted by an authorized user." (no variable parts), and the subscription stays listed.

Emulator: nothing is ever sent to an http or https endpoint. services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/publish.rs, `QueueTarget::of`, returns `None` for every protocol other than `sqs`, with the in-tree comment "Every other protocol (`http`, `lambda`, `email`, `firehose`, …) needs its own delivery path, which is not implemented here. The message is still RECORDED against the subscription, so nothing claims a delivery that did not happen." Publish still answers 200 with a MessageId. Subscribe likewise POSTs no SubscriptionConfirmation, so no real Token ever reaches a subscriber and the three confirmation-semantics checks cannot even obtain the token they must echo back; there is also no endpoint serving the unsigned `Action=ConfirmSubscription` / `Action=Unsubscribe` GETs that SubscribeURL and UnsubscribeURL name. All eight checks consequently block on a capture that never arrives and are killed at the 60 s harness cap ("Error: Check timed out after 60.0s").

Why: a webhook consumer — the single most common non-AWS SNS subscriber — is told its subscription exists and every Publish is accepted with a MessageId, yet it receives nothing, ever: no confirmation to echo, no notification, no dead letter when its endpoint fails, and no way to unsubscribe from a delivered URL. The loss is silent and total, and a client that gates on `PendingConfirmation` can never leave the pending state by the documented route.

Fix: the SNS Publish/Subscribe delivery dispatch component — `QueueTarget::of` / `queue_deliveries` / `deliver_to_queues` in the Publish handler, plus the Subscribe handler's confirmation emission and the service's handling of the unsigned ConfirmSubscription/Unsubscribe GET URLs it mints. Note: the checks' webhook receiver is a Lambda function URL, and Lambda invocation is separately filed as 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md; the SNS-side absence described here is evidenced directly in publish.rs and must be fixed independently of that.

Traces: sns.https-subscription-receives-nothing-until-confirmed-then-gets-the-notification, sns.https-raw-message-delivery-posts-the-bare-body-with-the-rawdelivery-header, sns.https-endpoint-failing-with-500-is-retried-then-dead-lettered, sns.https-subscription-with-a-zero-retry-delivery-policy-attempts-a-failing-notification-exactly-once, sns.raw-message-delivery-drops-message-attributes-for-an-https-subscriber-but-keeps-them-for-sqs, sns.confirm-subscription-token-confirms-only-its-own-subscription-whatever-the-topic-arn, sns.confirm-subscription-token-is-reusable-until-unsubscribe-then-not-found, sns.authenticate-on-unsubscribe-refuses-the-anonymous-unsubscribe-url.

--- Cause 2 of 6: a `lambda` subscription is never invoked, so no SNS Records envelope, no cross-region invocation and no dead-letter on a refused invocation ---

AWS: Smithy: SubscribeInput$Protocol documents `lambda` — "delivery of JSON-encoded message to an Lambda function". SNS invokes the subscribed function with a one-element `Records` list; the record's only top-level keys are `EventSource` = `"aws:sns"`, `EventVersion` = `"1.0"`, `EventSubscriptionArn` = the subscription ARN, and `Sns`, which carries `TopicArn`, the `MessageId` Publish returned, `Message`, a `Subject` that is null when the publish set none, `SigningCertUrl`/`UnsubscribeUrl` (that casing, unlike the HTTP envelope's `SigningCertURL`/`UnsubscribeURL`), and `MessageAttributes` as `{Type, Value}` where a Number attribute is reported with Type `String` and a Binary value is base64-encoded. The subscription's FilterPolicy decides which notifications are invoked. A function ARN in another region of the same account is invoked in ITS region while the subscription ARN extends the topic's (topic-region) ARN. If the function's resource policy grants SNS no `lambda:InvokeFunction`, SNS does not invoke it, treats the refused invocation as a failed delivery, and writes the notification envelope to the queue the subscription's RedrivePolicy names; granting the permission makes the next notification invoke the function and not be dead-lettered.

Emulator: `QueueTarget::of` (publish.rs) returns `None` for `protocol != "sqs"`, so a `lambda` subscription is accepted, reads back confirmed, is recorded as having received the message — and the function is never invoked, nothing is written to the subscription's dead-letter queue, and no resource-policy decision is made. All three checks hang to the 60 s cap waiting for an invocation. Related but not covering: 20261025T002357Z-events-lambda-sns-eventbridge-sns-targets-never-publish-and-an-sns.md and 20261025T022656Z-lambda-sns-sqs-sns-sqs-to-lambda-delivery.md describe SNS→Lambda delivery from the events/lambda side; neither carries these `sns` check keys.

Why: every SNS→Lambda fan-out silently drops all messages while Publish reports success, so a consumer sees no invocation, no error and no dead letter; and because nothing is invoked, neither the Records envelope representation nor the invoke-permission gate is observable at all.

Fix: the SNS Publish delivery dispatch component — add a `lambda` protocol path to `QueueTarget::of`/`deliver_to_queues` in the Publish handler that resolves the endpoint function ARN in the ARN's own region, evaluates the function's resource policy, renders the Records envelope, and routes a refused invocation through the subscription's RedrivePolicy.

Traces: sns.lambda-subscription-invocation-carries-the-sns-records-envelope, sns.cross-region-lambda-subscription-invokes-the-function-in-its-own-region, sns.lambda-subscription-the-function-refuses-to-sns-dead-letters-into-the-subscription-dlq.

--- Cause 3 of 6: a `firehose` subscription puts no record into the delivery stream, and its SubscriptionRoleArn permissions are never evaluated ---

AWS: Smithy: SubscribeInput$Protocol documents `firehose` — "delivery of JSON-encoded message to an Amazon Data Firehose delivery stream." A firehose subscription is confirmed at once (`PendingConfirmation` = `"false"`) and keeps its `Endpoint` (the stream ARN) and `SubscriptionRoleArn`. SNS assumes that role and puts one newline-terminated JSON notification envelope per publish into the stream — `Type` = `"Notification"`, the `MessageId` Publish returned, `TopicArn`, `Subject` and `Message` as published, and `MessageAttributes` as `{Type, Value}` — and nothing for a publish the subscription's FilterPolicy rejects. If the subscription role may not call `firehose:PutRecord`/`PutRecordBatch`, nothing reaches the stream and SNS writes the notification envelope to the subscription's RedrivePolicy dead-letter queue instead; granting the permission makes the next notification land in the stream.

Emulator: same single cause as above — `QueueTarget::of` admits only `sqs`, so a `firehose` subscription receives no record, the subscription role is never assumed or authorized, and nothing is dead-lettered. Both checks hang to the 60 s cap.

Why: an analytics pipeline fed by SNS→Firehose→S3 receives no data while every Publish succeeds, and a mis-scoped subscription role produces neither a stream record nor a dead letter, so the misconfiguration is undiagnosable.

Fix: the SNS Publish delivery dispatch component — add a `firehose` protocol path to `QueueTarget::of`/`deliver_to_queues` that assumes the subscription's `SubscriptionRoleArn`, authorizes the PutRecord call against it, and falls back to the subscription's RedrivePolicy on refusal.

Traces: sns.firehose-subscription-writes-each-notification-envelope-into-the-stream-bucket, sns.firehose-subscription-role-without-put-record-dead-letters-until-granted.

--- Cause 4 of 6: Publish to an SSE-KMS topic never consults the live KMS key state, so a key pending deletion or disabled still accepts publishes ---

AWS: Smithy: Publish declares `KMSInvalidStateException` (HTTP 400) — "the state of the specified resource isn't valid for this request" — and `KMSDisabledException` (HTTP 400) — "the specified Amazon Web Services KMS key isn't enabled". SNS resolves the topic's `KmsMasterKeyId` state on the publish path, so after ScheduleKeyDeletion Publish is refused with error code `KMSInvalidState` and the message SNS relays verbatim from KMS: fixed text " is pending deletion. (Service: AWSKMS; Status Code: 400; Error Code: KMSInvalidStateException; Request ID: " … "; Proxy: null)", with the key ARN (from the topic's own KmsMasterKeyId) prefixed and the KMS request id as the only per-call value. After CancelKeyDeletion the key is `Disabled` and the same byte-identical Publish is refused with error code `KMSDisabled` and the same template around the fixed text " is disabled." and `Error Code: DisabledException`. EnableKey restores Publish.

Emulator: Publish keeps succeeding in all three states. The check publishes on a 15 s poll until the wanted refusal code appears, and nothing but success is ever returned, so it burns the harness budget and is killed at 60 s. Related but not covering: 20261025T025317Z-sns-authorizes-nothing-on-the-data-plane-topic.md covers the topic's KMS key POLICY never being evaluated; this cause is the key's lifecycle STATE (PendingDeletion/Disabled/Enabled), a different input and two different refusal codes.

Why: a caller that revokes a topic's CMK — the standard break-glass control — is told the topic still accepts and saves messages, so an operator believes encryption-at-rest is enforced and a security runbook that proves revocation by a failing Publish silently passes. It also makes the two refusal codes, which clients branch on to distinguish "recoverable, re-enable the key" from "pending deletion", unreachable.

Fix: the Publish handler's KMS key resolution (and the same path used by PublishBatch) in services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/publish.rs — read the key's state per request rather than at CreateTopic, and map it onto the already-declared KMSInvalidStateException/KMSDisabledException error channel.

Traces: sns.publish-to-topic-whose-key-is-pending-deletion-fails-kms-invalid-state.

--- Cause 5 of 6: a CloudFormation-provisioned AWS::SNS::Topic + AWS::SNS::Subscription(sqs) pair reaches CREATE_COMPLETE but delivers nothing ---

AWS: recorded behavior only (CloudFormation's AWS::SNS::Subscription has no Smithy operation of its own). A stack declaring an AWS::SNS::Topic, an AWS::SQS::Queue, an AWS::SQS::QueuePolicy granting `sns.amazonaws.com` `sqs:SendMessage` on the queue conditioned on `aws:SourceArn` = the topic, and an AWS::SNS::Subscription with Protocol `sqs` and Endpoint `Fn::GetAtt [Queue, Arn]` produces a REAL SNS subscription: after CREATE_COMPLETE, a Publish to the stack's topic arrives in the stack's queue, exactly as a Subscribe call made directly would.

Emulator: the stack is created, GetTopicAttributes answers for the stack's topic, and a message published to it never arrives in the stack's queue; the check polls for it and is killed at the 60 s cap. Delivery through a directly-created SQS subscription does work in this emulator (other sns/sqs delivery checks pass), which localizes the defect to the CloudFormation-provisioned subscription rather than to the SQS delivery path. Hypothesis: the AWS::SNS::Subscription resource is materialized as stack state only and never registered as an SNS subscription with a resolvable queue-ARN endpoint — consistent with the already-filed observation that a Subscription's `Ref` is not an ARN in 20261025T025317Z-sns-cloudformation-provisioned-sns-resources-topicinlinepolicy-unknown-a-subscription.md, which does not carry this check's key.

Why: an infrastructure-as-code user — the normal way SNS fan-out is deployed — gets a green stack whose event pipeline is inert, and the failure appears only in the consumer's silence, not in any stack event or API answer.

Fix: the CloudFormation AWS::SNS::Subscription resource provisioner must create the subscription through the same SNS Subscribe path a direct call uses, so the subscription appears in the SNS store with its endpoint queue ARN and is picked up by the Publish fan-out.

Traces: sns.deploy-cfn-topic-publish-subscribe-flow.

--- Cause 6 of 6: a stack UPDATE that changes only a subscription's FilterPolicy does not update that subscription in place ---

AWS: recorded behavior only. An UpdateStack whose sole change is the `FilterPolicy` property of an AWS::SNS::Subscription updates that subscription in place: the subscription ARN is unchanged across the update, GetSubscriptionAttributes reads back the new policy, and the next Publish follows it — the value that used to match no longer reaches the filtered queue and the value that used to be filtered out now does, while an unfiltered control subscription on the same topic receives both before and after.

Emulator: the check creates the stack, updates it and then waits for the post-update delivery/absence pair, and is killed at the 60 s cap, so neither the ARN-stability claim nor the new policy taking effect on delivery is satisfied. This cause rides on Cause 5 (the CFN-provisioned subscription delivering at all) but is a separate requirement — an in-place property update that neither replaces the subscription nor leaves the old policy in force — and must be verified separately once Cause 5 is fixed.

Why: a client that manages subscription filters through CloudFormation (the documented way to change them) gets an UPDATE_COMPLETE that changes nothing about delivery, or a silently replaced subscription ARN that breaks anything holding the old one.

Fix: the CloudFormation AWS::SNS::Subscription resource updater — route a FilterPolicy-only change to SetSubscriptionAttributes on the existing subscription rather than to a replace or a no-op.

Traces: sns.deploy-cfn-stack-update-changes-a-filter-policy-in-place.
