# CloudFormation-provisioned AWS::OpenSearchService::Domain is refused by OpenSearch CreateDomain with HTTP 400 "expected string, got object start", so the stack rolls back and the VPC-domain/ALB lifecycle never starts

> _Note: this issue was identified against the code base at commit `1ac7afa977ab22208452bb66f8c5de757e9e028d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomain

## Description
One root cause, grounded in 1 failing behavioral check whose check-id leading token is the composite 'ec2__elbv2__opensearch'.

Related open issue that does NOT carry this cause or this replay key: 20261023T025808Z-ec2-elbv2-opensearch-opensearch-alb-diagnosis-scenarios-blocked-cfn-stack-outputs.md. Its Cause 1 names this same check, but its replay key is a later frame (`phase#8|_PhaseError`) reached AFTER a CREATE_COMPLETE stack, where the failure was a stack Output carrying no OutputValue (KeyError: 'OutputValue'). The check now fails EARLIER and differently: the stack never reaches CREATE_COMPLETE at all — it ends ROLLBACK_COMPLETE because the Domain resource is refused at create time. That is a different root cause in a different component, so this is net-new work rather than a restatement of that issue. It is also NOT a reopen of the fixed issue 20261024T055421Z-opensearch-createdomain-skips-documented-validation-describedomain-fabricates-empty.md: that one added semantic VALIDATION to CreateDomain (password complexity, storage tiers, log options), whereas this refusal happens before any validation, while the request body is being deserialized, and it rejects a request real AWS accepts.

Cause 1 of 1: a CloudFormation-provisioned AWS::OpenSearchService::Domain cannot be created, because the CreateDomain request the provisioner issues does not satisfy the OpenSearch input deserializer: a member modeled as a string is sent as a JSON object. CreateDomain answers HTTP 400 with the parser's own text, CloudFormation fails the Domain resource, and the whole stack rolls back.

AWS: Smithy com.amazonaws.opensearch#CreateDomain — POST /2021-01-01/opensearch/domain, success code 200; members include DomainName (required, @length 3..28, @pattern ^[a-z][a-z0-9\-]+$), ClusterConfig, EBSOptions, VPCOptions, CognitoOptions, DomainEndpointOptions, and AccessPolicies, whose target is the shape PolicyDocument — a STRING with @length 0..102400 and @pattern .* . Modeled client errors are ValidationException (400), BaseException (400), InvalidTypeException (409), ResourceAlreadyExistsException (409), LimitExceededException (409), DisabledOperationException (409). A well-formed CreateDomain for a VPC domain (ClusterConfig + EBSOptions + VPCOptions + CognitoOptions + DomainEndpointOptions with EnforceHTTPS and a TLSSecurityPolicy) is ACCEPTED with HTTP 200 and a DomainStatus, and under CloudFormation the AWS::OpenSearchService::Domain resource reaches CREATE_COMPLETE, so the stack reaches CREATE_COMPLETE and publishes its Outputs. For a request that genuinely is ill-typed, AWS answers one of the modeled client errors above with a message naming the offending member and the expected type — it never returns a deserializer's internal parser text. Recorded behavior only for CloudFormation's wrapper text, which the recording shows in AWS's documented resource-failure shape: `Resource handler returned message: "<service message> (Service: OpenSearch, Status Code: <status>, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: <code>)` — the fixed text is that frame, and <service message>/<status>/<id>/<token>/<code> are per-request values.

Emulator: CreateDomain is refused with HTTP 400 and the message `Invalid request provided: expected string, got object start`. CloudFormation surfaces it as the Domain resource's failure reason — `Resource handler returned message: "Invalid request provided: expected string, got object start (Service: OpenSearch, Status Code: 400, Request ID: <id>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)` — then the stack-level reason `The following resource(s) failed to create: [Domain]. ` and the stack ends ROLLBACK_COMPLETE instead of CREATE_COMPLETE. Two things diverge: (a) a CreateDomain request real AWS accepts is refused, and (b) the refusal's message is the input deserializer's internal text ('expected string, got object start') rather than an AWS error message naming the member and the expected type under a modeled error class. In the recorded reason the fixed text is 'Invalid request provided: expected string, got object start' and only the request/token ids vary, so this is a template-level defect and not a per-run value difference.

Hypothesis (neither the model nor the recording states which member it is): the member is AccessPolicies. It is the one top-level CreateDomain member typed as a plain string (target PolicyDocument) whose CloudFormation template representation is a nested JSON object — the AWS::OpenSearchService::Domain `AccessPolicies` property is written as a policy document object and the resource handler must serialize it to a JSON STRING before calling CreateDomain. Passing the object through unserialized produces exactly 'expected string, got object start' at the first member the deserializer reads as a string. A fixer should confirm by logging the CreateDomain body the provisioner emits for this template before changing either side.

Why: a client relying on AWS's behavior cannot deploy a VPC OpenSearch domain through CloudFormation at all — the single most common way these domains are created. Every downstream read is unreachable: the stack publishes no Outputs, so the domain name, VPC endpoint, Cognito pool ids, ALB ARN and target-group ARN can never be resolved, and the five-phase diagnosis lifecycle (deploy, setup, solve, cleanup, destroy) aborts in phase 1 of 5 with nothing exercised. Because the failure is reported as a resource-handler InvalidRequest, an IaC user reads it as a fault in their own template and has no way to correct it; and because the message is raw parser text, neither a human nor tooling can tell WHICH property is wrong.

Fix: the CloudFormation AWS::OpenSearchService::Domain provisioner's property-to-request mapping — the properties it forwards to CreateDomain must match the modeled member types, in particular a policy-document property must be serialized to a JSON string before it is placed in the CreateDomain body; and the OpenSearch CreateDomain input deserializer/handler, which must report a genuine type mismatch through a modeled client error whose message names the member and the expected type, rather than emitting its internal parser text as the service message.

Traces: ec2__elbv2__opensearch.e2e-opensearch-cognito-alb-timeout-diagnosis-lifecycle (phase 1/5 'deploy'; this failure is NOT marked ALREADY FILED or OWNED in the replay report).
