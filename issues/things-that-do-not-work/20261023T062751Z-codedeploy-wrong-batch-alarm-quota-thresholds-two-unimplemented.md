# CodeDeploy: wrong batch/alarm quota thresholds, two unimplemented deployment operations, two missing input gates, one misclassified rejection, un-suffixed on-premises instanceArn, and divergent rejection text (9 causes)

> _Note: this issue was identified against the code base at commit `1bf7f94f5369037d1be2743fe86a59b83a69434a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
BatchGetDeployments

## Description
Nine independent root causes in the CodeDeploy emulator, found by replaying the behavioral suite (simparity-behavioral-aws-v1). Nine causes, nine fixes; all nine must be closed before submitting.

Cause 1 of 9: the BatchGet* request-size quota is enforced at 25 names/ids instead of AWS's 100.
AWS: Smithy BatchGetDeployments.deploymentIds (DeploymentsList, required) and BatchGetOnPremisesInstances.instanceNames (InstanceNameList, required); both model BatchLimitExceededException (HTTP 400), whose own model doc states the rule: "The maximum number of names or IDs allowed for this request (100) was exceeded." So a request of 26..100 entries must be ACCEPTED and only >100 refused.
Emulator: refuses with BatchLimitExceededException but enforces a threshold of 25 — its refusal text names its own limit ("The maximum number of deployment IDs allowed for this request (25) was exceeded: 101 were specified" and "The maximum number of names you can specify for instanceNames is 25, but 101 were specified"). The HTTP status and error code match; the threshold does not.
Why: a client batching the AWS-documented 100 ids per call (the standard way to page BatchGetDeployments / BatchGetOnPremisesInstances) is refused for every batch between 26 and 100 entries, so bulk inspection fails against the emulator while working on AWS.
Fix: the request-size validation of BatchGetDeployments and BatchGetOnPremisesInstances (shared batch-limit constant) in the codedeploy service crate's op handlers/validation.
Traces: codedeploy.batch-get-deployments-limit-exceeded-rejected, codedeploy.batch-get-on-premises-instances-limit-exceeded-rejected.

Cause 2 of 9: CreateDeployment's overrideAlarmConfiguration alarm quota is enforced at 10 instead of 50.
AWS: Smithy CreateDeployment takes overrideAlarmConfiguration (AlarmConfiguration) and models AlarmsLimitExceededException (HTTP 400); the model's AlarmConfiguration doc says "A maximum of 10 alarms can be added" and AlarmsLimitExceededException's doc says "The maximum number of alarms for a deployment group (10) was exceeded" — i.e. 10 is the DEPLOYMENT GROUP rule. Recorded behavior for CreateDeployment: AWS refuses 51 alarms with AlarmsLimitExceededException and the message example 'Deployments cannot contain more than 50 alarms.', so the quota enforced on this operation is 50, not the deployment-group 10.
Emulator: refuses with the right code but names the deployment-group limit: 'The maximum number of alarms for a deployment group (10) was exceeded: 51 alarms were specified'. Hypothesis: the deployment-group alarm limit is being applied to CreateDeployment's override, which would also refuse the 11..50-alarm overrides AWS accepts (not directly exercised by this check, which sends 51).
Why: a deployment that overrides alarms with more than 10 alarms is refused where AWS accepts it, and the quota a client reads back from the refusal is wrong.
Fix: CreateDeployment's overrideAlarmConfiguration validation — use the deployment-level alarm quota, distinct from the deployment-group quota used by CreateDeploymentGroup/UpdateDeploymentGroup.
Traces: codedeploy.create-deployment-alarms-limit-exceeded-rejected.

Cause 3 of 9: ContinueDeployment answers NotImplemented instead of any modeled outcome.
AWS: Smithy ContinueDeployment models DeploymentAlreadyCompletedException, DeploymentDoesNotExistException, DeploymentIdRequiredException, DeploymentIsNotInReadyStateException, InvalidDeploymentIdException, InvalidDeploymentStatusException, InvalidDeploymentWaitTypeException and UnsupportedActionForDeploymentTypeException (all HTTP 400). For an in-place (IN_PLACE) deployment the recorded AWS answer is HTTP 400 / UnsupportedActionForDeploymentTypeException (message example: 'Operation is not supported for the deployment <id> of type IN_PLACE.').
Emulator: HTTP 501 with error code 'NotImplemented' ("operation ContinueDeployment is scaffolded but not implemented in this emulator").
Why: NotImplemented is unmodeled, so a client branching on the modeled blue/green errors never matches, and blue/green traffic-shift control cannot be exercised at all.
Fix: implement the ContinueDeployment handler in the codedeploy crate's ops (services/service-com-amazonaws-codedeploy-codedeploy-20141006/src/ops/continue_deployment.rs) and remove its scaffold marker.
Traces: codedeploy.continue-deployment-already-completed-rejected.

Cause 4 of 9: GetDeploymentTarget answers NotImplemented instead of resolving target membership.
AWS: Smithy GetDeploymentTarget (deploymentId, targetId both required) returns deploymentTarget and models DeploymentTargetDoesNotExistException, DeploymentNotStartedException, DeploymentDoesNotExistException, InvalidDeploymentTargetIdException and others (all HTTP 400). Recorded behavior: a targetId that is not a member of the deployment is refused HTTP 400 / DeploymentTargetDoesNotExistException (message example: 'The target <target-arn> is not part of deployment <id>'), and once the deployment resolves its targets the same call for a real member returns that target's record.
Emulator: HTTP 501 with error code 'NotImplemented'.
Why: per-target deployment inspection — the only way to read an individual instance's/task-set's deployment outcome — is unavailable, and the unmodeled code defeats membership branching.
Fix: implement the GetDeploymentTarget handler in the codedeploy crate's ops (services/service-com-amazonaws-codedeploy-codedeploy-20141006/src/ops/get_deployment_target.rs) and remove its scaffold marker.
Traces: codedeploy.get-deployment-target-not-started-rejected.

Cause 5 of 9: DeregisterOnPremisesInstance has no instanceName format gate — a reserved EC2-instance-ID-shaped name is accepted as a no-op 200.
AWS: Smithy DeregisterOnPremisesInstance declares instanceName (InstanceName) required and models InvalidInstanceNameException (HTTP 400, doc "The on-premises instance name was specified in an invalid format"). Recorded behavior: a name shaped like an EC2 instance id (i-xxxxxxxxxxxxxxxxx) is refused HTTP 400 / InvalidInstanceNameException (message example: 'Host name cannot start with "i-"') — the "i-" prefix is reserved and never a valid on-premises host name.
Emulator: HTTP 200 with an empty body, i.e. the call reads as a successful deregistration of a name that can never exist.
Why: a caller that passes an EC2 instance id by mistake is told the deregistration succeeded, so a still-registered on-premises host is believed gone; the modeled format error that should force the caller to fix the id never fires.
Fix: DeregisterOnPremisesInstance's input validation — reject the reserved i-* name shape (and other InstanceName format violations) before the existence/no-op path.
Traces: codedeploy.deregister-invalid-instance-name-rejected.

Cause 6 of 9: RegisterApplicationRevision accepts an over-length revision description.
AWS: Smithy RegisterApplicationRevision declares description (Description) and models DescriptionTooLongException (HTTP 400). Recorded behavior: a description past the 512-character maximum is refused HTTP 400 / DescriptionTooLongException (message example: 'Revision description has a maximum length of 512') and the revision is NOT registered (a following GetApplicationRevision answers RevisionDoesNotExistException).
Emulator: HTTP 200 with an empty body for a 4001-character description.
Why: a revision is registered carrying a description AWS would never store, so later reads diverge and the client's length guard (keyed on the modeled error) never fires.
Fix: RegisterApplicationRevision's input validation (description length gate before persistence). Note the open wire issue "CodeDeploy accepts invalid input and misclassifies rejections" describes this same gate as its Cause 3 and the open issue "Implement codedeploy RegisterApplicationRevision: unimplemented scaffold stub" names this operation; neither carries this behavioral check's replay key, so this cause is recorded here and all must be closed together.
Traces: codedeploy.register-application-revision-description-too-long-rejected.

Cause 7 of 9: PutLifecycleEventHookExecutionStatus misclassifies a fabricated hook-execution id as UnsupportedActionForDeploymentTypeException.
AWS: Smithy PutLifecycleEventHookExecutionStatus models both InvalidLifecycleEventHookExecutionIdException and UnsupportedActionForDeploymentTypeException (HTTP 400). Recorded behavior: against a deployment that EXISTS, a lifecycleEventHookExecutionId that was never issued is refused HTTP 400 / InvalidLifecycleEventHookExecutionIdException (message example: 'The lifecycleEventHookExecutionId is invalid'), distinct from the DeploymentDoesNotExistException returned for an id of a deployment that was never created (that branch the emulator gets right).
Emulator: HTTP 400 / UnsupportedActionForDeploymentTypeException.
Why: the two errors mean opposite things to a deployment hook — "your hook id is wrong, re-read it" versus "this deployment type has no hooks, stop calling" — so a Lambda/ECS hook implementation retries or aborts on the wrong signal, and the error can no longer discriminate deployment existence from hook-id validity.
Fix: PutLifecycleEventHookExecutionStatus's validation/handler — resolve the hook-execution id for an existing deployment and refuse through InvalidLifecycleEventHookExecutionIdException, reserving UnsupportedActionForDeploymentTypeException for deployment types that have no hooks.
Traces: codedeploy.put-lifecycle-event-hook-status-deployment-not-exist-rejected.

Cause 8 of 9: on-premises instanceArn is minted without the server-side registration suffix.
AWS: Smithy InstanceInfo.instanceArn (InstanceArn) — "The ARN of the on-premises instance" — carries no pattern in the model, so recorded behavior only: AWS mints the ARN as arn:<partition>:codedeploy:<region>:<account>:instance/<instanceName>_<server-minted-suffix>, i.e. the registration's own identity is appended to the host name.
Emulator: returns arn:aws:codedeploy:<region>:<account>:instance/<instanceName> with no suffix.
Why: the ARN no longer identifies a REGISTRATION, only a name, so re-registering a name is indistinguishable from the previous one; clients that parse or compare the ARN (and operations that name targets by ARN, e.g. GetDeploymentTarget refusal messages) diverge from AWS.
Fix: the on-premises instance registration state/projection — mint and persist the suffixed instanceArn at RegisterOnPremisesInstance time and serialize it from GetOnPremisesInstance / BatchGetOnPremisesInstances.
Traces: codedeploy.on-premises-instance-deregister-reflects-in-status-filters (the same un-suffixed ARN is read by codedeploy.get-deployment-target-not-started-rejected).
