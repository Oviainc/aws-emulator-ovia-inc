# schemas: 5 net-new causes — DeleteSchemaVersion deletes a schema's last version, ExportSchema accepts a non-export Type, SearchSchemas indexes neither content nor name, and two refusal sentences are emulator-authored

> _Note: this issue was identified against the code base at commit `716594ad03747236be5f362ba3ba8170b7a2d152`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteSchemaVersion

## Description
Five independent net-new root causes in the schemas emulator, all reached by the behavioral suite. Two are over-permissive writes/reads (a delete AWS refuses and an export Type AWS refuses are both answered 2xx), one is a search index that selects nothing a caller can search for, and two are refusal sentences the emulator authors itself.

Cause 1 of 5 — DeleteSchemaVersion removes a schema's ONLY remaining version.
AWS: DeleteSchemaVersion is DELETE /v1/registries/name/{RegistryName}/schemas/name/{SchemaName}/version/{SchemaVersion}, modeled success 204 (Smithy: DeleteSchemaVersion, input RegistryName/SchemaName/SchemaVersion all @httpLabel @required). The operation's modeled error list is BadRequestException 400, ForbiddenException 403, InternalServerErrorException 500, NotFoundException 404, ServiceUnavailableException 503, UnauthorizedException 401 — ConflictException (modeled in this service at httpError 409) is not bound to this operation, so for this rule the recorded behavior is the requirement: AWS refuses a DeleteSchemaVersion that would leave the schema with no versions with HTTP 409, error code ConflictException, and the message "Cannot delete all versions of a Schema. To delete a Schema use the DeleteSchema API." — that sentence is entirely fixed text with no variable parts. DeleteSchema is the only path that removes a schema's final version.
Emulator: there is no last-version guard at all. The handler resolves the registry and schema, then calls Schema::remove_version_named and answers 204 whenever the named version existed, so deleting the sole remaining version succeeds and leaves a version-less schema behind. Replay: the identical call that must be refused returned HTTPStatusCode 204 with an empty body.
Why: a client that relies on the service to protect the last version loses the schema's only definition on a call it expects to be rejected, and the error class it branches on (ConflictException) never arrives, so a create-or-restore recovery path never runs. The schema is also left in a state no AWS account can produce.
Fix: the DeleteSchemaVersion handler's pre-delete checks — the guard belongs next to the existing registry/schema resolution, before the version is removed, and must raise the service's conflict payload.
Traces: schemas.delete-last-schema-version-removes-schema. Code: services/service-com-amazonaws-schemas-schemas/src/ops/delete_schema_version.rs lines 219-243 (remove_version_named, then Ok(DeleteSchemaVersionOutput); no conflict branch exists).

Cause 2 of 5 — the "version does not exist" sentence is the emulator's own template, not AWS's.
AWS: NotFoundException (httpError 404) on DescribeSchema (GET .../schemas/name/{SchemaName} with ?schemaVersion=) and on DeleteSchemaVersion. AWS words the body "Schema with name <SchemaName> and version <SchemaVersion> does not exist." — fixed text "Schema with name ", " and version ", " does not exist.", with the request's SchemaName and SchemaVersion as the only variable parts. The registry name does not appear.
Emulator: answers 404 with the right code but "Schema <SchemaName> in registry <RegistryName> has no version <SchemaVersion>." — a different template that drops "with name", injects the registry, and replaces "does not exist" with "has no version". Both the read of a deleted version and the re-delete of it carry it, because both go through one helper.
Why: the message is part of the contract for this error class. A client or test asserting the service's refusal text sees a sentence AWS never emits, and anything parsing the schema/version out of the message reads members in the wrong positions.
Fix: the shared not-found message helper the schema-version paths use — crate::state::schema_version_not_found (services/service-com-amazonaws-schemas-schemas/src/state.rs ~line 4196), which must build AWS's sentence from SchemaName and SchemaVersion only. One edit closes both call sites, but both must be re-replayed.
Traces: schemas.delete-schema-version-keeps-remaining-versions.

Cause 3 of 5 — ExportSchema accepts an export Type that is not an export target.
AWS: ExportSchema is GET /v1/registries/name/{RegistryName}/schemas/name/{SchemaName}/export with Type as a @required @httpQuery("type") __string (Smithy: ExportSchema; errors include BadRequestException 400 and ForbiddenException 403). The only accepted export target is JSONSchemaDraft4; any other value is rejected server-side with HTTP 400, code BadRequestException, message "1 validation error detected: Value '<Type>' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [JSONSchemaDraft4]" — fixed text is the "1 validation error detected: Value '" / "' at 'type' failed to satisfy constraint: Member must satisfy enum value set: [JSONSchemaDraft4]" frame, and the one variable part is the rejected value taken from the request.
Emulator: validates Type against the service-wide SchemaType set, which admits OpenApi3 as well, and then treats SchemaType::OpenApi3 as "the export is the stored document" and answers HTTP 200 with the stored OpenAPI content, SchemaArn, SchemaName, SchemaVersion and Type. Replay: ExportSchema(Type="OpenApi3") returned 200 with Content equal to the stored OpenAPI 3 document.
Why: a client gets a 200 where AWS refuses, so an input-validation bug in the caller is silently "successful" and the caller treats an OpenAPI document as a draft-4 export. It also makes the two independent preconditions AWS enforces indistinguishable.
Also behind this gate, and part of this cause's fix: the second precondition is not implemented either. AWS refuses ExportSchema(Type=JSONSchemaDraft4) for a schema that is neither discovered nor AWS-managed with HTTP 403 ForbiddenException and the fixed sentence "You cannot export non discovered or non aws managed schemas." The handler's only 403 is keyed on the STORED type ("Exporting of a schema with type <type> is not supported."), so a caller-created OpenApi3 schema exports successfully. The check asserts this immediately after the Type gate, so fixing only the Type gate will not make it pass.
Fix: the ExportSchema handler's Type admission and eligibility gates (export-target set must be JSONSchemaDraft4 alone, separately from the service-wide schema-language set) plus its refusal payloads.
Traces: schemas.export-schema-json-schema-draft4-conversion. Code: services/service-com-amazonaws-schemas-schemas/src/ops/export_schema.rs lines ~163-171 (SchemaType::from_modeled admits OpenApi3), ~221-229 (403 keyed on stored type), ~245-247 (SchemaType::OpenApi3 => stored content returned).

Cause 4 of 5 — SearchSchemas indexes only the EventBridge extensions, so a caller's own schema is unfindable by anything in it.
AWS: SearchSchemas is GET /v1/registries/name/{RegistryName}/schemas/search with @required Keywords (@httpQuery "keywords"), 200, @paginated over Schemas. Recorded behavior: a keyword occurring in the schema's content (here, a property name inside the OpenAPI components) matches that schema once indexing catches up, and a search for the schema's own name matches it; an unrelated keyword does not.
Emulator: matching is restricted to the values a schema "is INDEXED under — the event keywords its document declares … and nothing else": only the x-amazon-events-source and x-amazon-events-detail-type extension values, with the schema NAME deliberately excluded. A caller-created OpenApi3 document declares neither extension, so it is indexed under no value and every keyword fails against it. Replay: the check polled SearchSchemas for 60s and the schema never appeared, so the check timed out (HTTP 200 with an empty Schemas list each time).
Why: SearchSchemas is unusable for any schema a caller created — the operation always answers an empty page, so a client's discovery-by-keyword flow finds nothing and cannot distinguish "not indexed yet" from "never matches". Note the resolved issue 20261024T060347Z-schemas-searchschemas-wrong-behavior.md ("SearchSchemas matches only x-amazon-events-* extensions, so a caller's own schemas are unfindable by any keyword") described this same narrowness; the handler still implements it, with the exclusion written into its documentation.
Fix: the SearchSchemas handler's match predicate and the indexed-value set it builds (matches_every_keyword / declared_event_keywords / EVENT_KEYWORD_EXTENSIONS), which must also index the stored document text and the schema name.
Traces: schemas.search-schemas-keyword-filters-results. Code: services/service-com-amazonaws-schemas-schemas/src/ops/search_schemas.rs lines ~318-401.

Cause 5 of 5 — the duplicate-CreateDiscoverer conflict sentence names the source instead of the existing discoverer.
AWS: ConflictException (httpError 409) on CreateDiscoverer (POST /v1/discoverers, SourceArn the only required member). AWS words the 409 body "Discoverer <DiscovererId> already exists." — fixed text "Discoverer " + " already exists.", the one variable part being the DiscovererId of the discoverer the store already holds for that source.
Emulator: answers 409 with the right code but "Discoverer for source <SourceArn> already exists.", built from the request's SourceArn rather than from the existing resource's id.
Why: a client that parses the colliding resource's id out of the refusal in order to switch to a describe-and-reuse path gets back only the source ARN it already sent, and a client surfacing the message shows a sentence AWS never emits.
Fix: the conflict payload the CreateDiscoverer handler raises — crate::state::discoverer_already_exists (services/service-com-amazonaws-schemas-schemas/src/state.rs ~line 4102), which must take the existing discoverer's id.
Not covered by an existing issue for this suite: the open wire issue 20261029T203553Z-schemas-discoverer-operations-diverge-from-aws-on-discovererid-derivation.md describes the same helper in its Cause 2, but it carries only wire fixture keys (schemas-discoverer-lifecycle#task#2) and not this check, so this behavioral check is recorded here. A fixer closing that issue's Cause 2 should re-replay this check too.
Traces: schemas.create-discoverer-duplicate-source-rejected-conflict.
