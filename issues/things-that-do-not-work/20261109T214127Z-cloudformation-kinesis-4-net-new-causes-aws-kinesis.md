# cloudformation__kinesis: 4 net-new causes — AWS::Kinesis::Channel and AWS::Kinesis::ResourcePolicy are unregistered resource types, property-validation diagnostics (VALIDATION_ERROR events and the stack CREATE_FAILED reason) are never emitted, and a stack's Outputs come back with no OutputValue

> _Note: this issue was identified against the code base at commit `19c62db1539bfab1a25075fa0f8ae1a77a215876`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Four net-new root causes in the CloudFormation handling of Kinesis resources. All four are grounded in failing checks the replay report lists under `### cloudformation__kinesis` and marks NEITHER "ALREADY FILED" nor "OWNED by"; the other failures under that heading are owned by existing issues. Open issue 20261109T174330Z-cloudformation-kinesisvideo-no-aws-kinesisvideo-resource-type-is.md reports the same class of gap for the AWS::KinesisVideo::* types and carries none of the check ids below, so it does not cover these.

=== Cause 1 of 4: AWS::Kinesis::Channel is not a registered resource type, so no template containing one can be created ===
AWS: recorded behavior only (CloudFormation's resource-type registry is not in the Smithy model; the Kinesis Smithy model com-amazonaws-kinesis-kinesis-20131202 does bind CreateChannel/DescribeChannel/DeleteChannel, so the underlying resource exists in the service). A CreateStack whose template declares a resource of type `AWS::Kinesis::Channel` is ACCEPTED (HTTP 200, a StackId is returned) and the stack provisions the channel, reaching CREATE_COMPLETE; deleting the stack removes the channel. CreateStack's `Template format error: Unrecognized resource types: [<type>]` ValidationError is reserved for types CloudFormation genuinely does not support — the fixed text is `Template format error: Unrecognized resource types: [` + the list of unrecognized type names from the request + `]`.
Emulator: CreateStack is refused HTTP 400 `ValidationError` with `Template format error: Unrecognized resource types: [AWS::Kinesis::Channel]`, so the check dies on its first call and the whole provisioned-and-removed lifecycle is ungraded.
Why: a client cannot model a Kinesis channel in CloudFormation/CDK at all — the stack is rejected at submit time, so neither the provisioning nor the deletion path exists for it.
Fix: register `AWS::Kinesis::Channel` in the CloudFormation service crate's resource-type registry and give it a provisioner that maps template properties onto the Kinesis CreateChannel/DeleteChannel handlers and resolves its Ref/GetAtt attributes.
Traces: cloudformation__kinesis.deploy-cfn-kinesis-channel-provisioned-and-removed.

=== Cause 2 of 4: AWS::Kinesis::ResourcePolicy is not a registered resource type, so neither CreateStack nor UpdateStack accepts one ===
AWS: recorded behavior only; the Kinesis Smithy model binds PutResourcePolicy/GetResourcePolicy/DeleteResourcePolicy, and CloudFormation supports `AWS::Kinesis::ResourcePolicy` (properties ResourceArn + ResourcePolicy). A CreateStack or UpdateStack carrying one is accepted, the policy is attached to the named stream/consumer and is readable through GetResourcePolicy, and an invalid policy document (for example one granting a foreign service's action) is refused during provisioning with the resource's own failure reason rather than at template parse time.
Emulator: both CreateStack and UpdateStack are refused HTTP 400 `ValidationError` with `Template format error: Unrecognized resource types: [AWS::Kinesis::ResourcePolicy]`, so the resource-policy lifecycle and its negative case are both ungraded.
Why: resource-policy-based cross-account sharing of a stream cannot be expressed in a stack; a client's deploy fails at submit time with a template-format error that suggests its template is malformed when it is not.
Fix: register `AWS::Kinesis::ResourcePolicy` in the CloudFormation resource-type registry and provision it through the Kinesis PutResourcePolicy/DeleteResourcePolicy handlers, surfacing a policy-validation refusal as the resource's CREATE_FAILED reason.
Traces: cloudformation__kinesis.deploy-cfn-kinesis-resourcepolicy-provisioned-and-removed, cloudformation__kinesis.deploy-cfn-kinesis-resourcepolicy-foreign-service-action-rejected.

=== Cause 3 of 4: a stack rolled back for a property-value violation records no diagnosis — DescribeEvents returns no VALIDATION_ERROR operation events and the stack's CREATE_FAILED event carries no ResourceStatusReason ===
AWS: recorded behavior only (property validation is CloudFormation's, not a Kinesis Smithy constraint; the Kinesis model does pin the same value domains — StreamName @length min 1 max 128 @pattern ^[a-zA-Z0-9_.-]+$ — which is what the resource schema mirrors). A template whose AWS::Kinesis::Stream properties violate the resource schema is refused BEFORE anything is provisioned: the stack settles in ROLLBACK_COMPLETE, ListStackResources is empty, the stack-level CREATE_FAILED StackEvent carries the fixed reason `Validation failed with <n> error(s). Call DescribeEvents to retrieve the full list of issues with resource and property details, resolve each error, then retry the operation.` (only <n>, the number of violations found, varies), and DescribeEvents returns one `VALIDATION_ERROR` OperationEvent per violation with ValidationName `PROPERTY_VALIDATION`, ValidationStatus `FAILED`, ValidationFailureMode `FAIL`, the ResourceType and LogicalResourceId of the offending resource, a ValidationPath of the form `/Resources/<LogicalId>/Properties/<Property>`, and a ValidationStatusReason whose shape is fixed per violation class with the request's own values filled in: `Property value [<value>] does not match pattern: <pattern>` for a pattern violation, `#/<Property>: expected maxLength: <limit>, actual: <actual>` and `#/<Property>: expected minLength: <limit>, actual: <actual>` for length violations, `#/<Property>: <value> is not greater or equal to <min>` for a numeric minimum, and `<value> is not a valid enum value. Supported values: [<allowed values>]` for an enum violation.
Emulator: the rollback itself happens, but the diagnosis is entirely absent. DescribeEvents returns no OperationEvents with EventType `VALIDATION_ERROR` for the offending property path (the collected reason list is `[]` for a `:`-bearing Name, for a 129-character Name and for an empty Name), and the stack's own CREATE_FAILED StackEvent list of ResourceStatusReason values is `[]` where the `Validation failed with 2 error(s)...` sentence is required (RetentionPeriodHours=1 plus RecordDistributionStrategy=BOGUS).
Why: CloudFormation's documented workflow for a failed deploy is "read the stack reason, then call DescribeEvents for the per-property detail". With neither present, a client is told only that the stack rolled back and can never learn WHICH property of WHICH resource was wrong or why — CI output and console diagnostics are empty.
Fix: the CloudFormation service crate's template/property validation stage and its event recorder — run the resource schema's pattern/length/range/enum checks before provisioning, record one VALIDATION_ERROR OperationEvent per violation (with ValidationName/ValidationStatus/ValidationFailureMode/ValidationPath/ValidationStatusReason populated as above) so DescribeEvents can page them, and attach the aggregate `Validation failed with <n> error(s)...` reason to the stack-level CREATE_FAILED StackEvent.
Traces: cloudformation__kinesis.cfn-kinesis-stream-name-length-and-pattern-rejected, cloudformation__kinesis.deploy-kinesis-stream-value-constraints-rejected.

=== Cause 4 of 4: DescribeStacks returns Outputs entries with no OutputValue, so no stack output can be read ===
AWS: recorded behavior only. For a stack that reached CREATE_COMPLETE, every entry of `Stacks[0].Outputs` carries both `OutputKey` (the name declared under Outputs) and `OutputValue` (the RESOLVED value of the declared Value expression) — `{"Fn::GetAtt": ["Stream", "Arn"]}` resolves to the stream ARN Kinesis reports, `{"Ref": "Consumer"}` to the registered consumer's ARN, and `{"Fn::GetAtt": ["Consumer", "ConsumerStatus"]}` to `ACTIVE`.
Emulator: the stack reaches CREATE_COMPLETE, but building `{o["OutputKey"]: o["OutputValue"] for o in stack["Outputs"]}` raises `KeyError: 'OutputValue'` — at least one Output entry is serialized without the member, so the intrinsic was never resolved into a value. Everything the check grades downstream (GetAtt Stream.Arn against DescribeStreamSummary, Ref Consumer against ListStreamConsumers, GetAtt Consumer.ConsumerStatus == ACTIVE, the consumer-dropping update and the final deletion) is therefore ungraded.
Why: stack outputs are the standard hand-off between a stack and its consumers (nested stacks, CDK cross-stack references, scripts reading DescribeStacks). An Output with no OutputValue breaks every SDK consumer — botocore hands the caller a dict missing the key, so clients raise rather than read the value.
Fix: the CloudFormation service crate's output-resolution step and the DescribeStacks serializer — evaluate each declared Output's Value (Ref and Fn::GetAtt against the provisioned resource's attributes, including AWS::Kinesis::Stream Arn and AWS::Kinesis::StreamConsumer Ref/ConsumerStatus) and always emit OutputValue alongside OutputKey.
Traces: cloudformation__kinesis.deploy-cfn-kinesis-streamconsumer-provisioned-and-removed.
