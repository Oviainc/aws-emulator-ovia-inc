# maps.geo serves synthetic glyph and sprite assets instead of the real basemap asset payloads

> _Note: this issue was identified against the code base at commit `d4c3381173b09dc1be1da315e64a87a78d438272`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSprites

## Description
The maps.geo asset operations answer 200 with a well-formed body, but the body is emulator-synthesized rather than the basemap asset AWS serves for the requested (FontStack, FontUnicodeRange) / (Style, ColorScheme, Variant, FileName) coordinates. Four distinct causes, all in the asset-production path of this crate.

This bundle contains 4 causes. All four must be closed before submitting.

Cause 1 of 4 - GetGlyphs returns a glyph PBF of the wrong content and size.
AWS: Smithy GetGlyphs -> GET /v2/glyphs/{FontStack}/{FontUnicodeRange}, FontUnicodeRange @pattern ^[0-9]+-[0-9]+\.pbf$, output GetGlyphsResponse.Blob is the @httpPayload blob with Content-Type/Cache-Control/ETag headers; the model declares no errors. The model does not describe the blob's bytes, so: recorded behavior only - the recording shows a glyph PBF whose byte length is determined by the font stack and the requested unicode range (the recorded response for this step is 74786 bytes, sha256 73b6ca0b...ac18).
Emulator: returns 200 with a blob of a different length and digest for the same FontStack/FontUnicodeRange pair (121491 bytes, sha256 7170b45e...2ddb). The size is not a function of the requested range in the way the recording shows - it is a generated placeholder.
Why: a client renders labels from these glyph metrics. A PBF that is not the glyph set for the requested range makes every label on the map render with wrong advance/bitmap data or fail to decode, and ETag/Cache-Control-based caching keys a wrong body.
Fix: the GetGlyphs handler and the glyph asset source it reads (src/ops/, glyph asset data in src/state.rs) - the response blob must be the glyph set for the requested font stack and unicode range, not a synthesized body.
Traces: geo-maps-glyphs-fontstack-unicode-ranges#task#1 (cluster also covers that fixture's task#2 and task#3 and geo-maps-vector-basemap-style-workflow#task#4).

Cause 2 of 4 - GetSprites returns a sprite image payload of the wrong content and size.
AWS: Smithy GetSprites -> GET /v2/styles/{Style}/{ColorScheme}/{Variant}/sprites/{FileName}, FileName @pattern ^sprites(@2x)?\.(png|json)$, Style/ColorScheme/Variant are required enum @httpLabels, output Blob is the @httpPayload; no modeled errors. Recorded behavior only for the bytes: the sprite image recorded for this style/color-scheme/variant is 121655 bytes, sha256 f0d727b2...6b54.
Emulator: 200 with a much smaller, different payload (21827 bytes, sha256 2527bf99...5ca4) - a generated image rather than the style's sprite sheet.
Why: a renderer slices icons out of this image using the sprite JSON's x/y/width/height. An image that is not the style's sprite sheet means every icon is sliced out of the wrong pixels, so POI, shield and marker icons are garbage or blank.
Fix: the GetSprites handler and the sprite asset source (src/ops/, sprite assets in src/state.rs) - serve the sprite sheet bound to the requested Style/ColorScheme/Variant/FileName.
Traces: geo-maps-sprites-style-color-variants#task#1 (cluster also covers that fixture's task#2 and geo-maps-vector-basemap-style-workflow#task#2).

Cause 3 of 4 - GetSprites sprites.json describes a different sprite-sheet layout than the sheet AWS publishes (Monochrome/Dark variant path).
AWS: recorded behavior only. The sprites.json body is a map of icon name -> {x, y, width, height, pixelRatio}; the geometry for each icon is fixed by the published sheet, icons of the same class share a size (e.g. the small city-dot icons are 5-6 px, transit/marker icons 20-22 px), and each icon's x/y is its offset in that sheet.
Emulator: emits a synthetic grid layout - uniform sizes where AWS varies them and vice versa (citydot 5x5 -> 12x12, citydot-open 6x6 -> 12x12, citydot_lowrank 5x5 -> 8x8, bicycle 22x20 -> 21x21, bus/entrance 20x20 -> 21x21) and shifted or wrapped offsets (book.x 117 -> 116, bus.x 138 -> 137, cocktail.x 327 -> 345, education 475,0 -> 0,32, entrance 496,0 -> 21,32, facilities 516,0 -> 42,32 - i.e. the emulator wraps to a new row where AWS continues the row). Hundreds of icon entries diverge this way.
Why: the JSON is the index into the PNG. Wrong width/height crops or over-reads each icon and wrong x/y picks the neighbouring icon, so a client that pairs the emulator's JSON with the real sheet (or with any other sheet) renders the wrong symbol at the wrong size for essentially every map icon.
Fix: the GetSprites handler's sprites.json serializer / the sprite-sheet metadata it is generated from - the geometry must come from the published sheet layout for that style, not from a generated uniform grid.
Traces: geo-maps-sprites-style-color-variants#task#3.

Cause 4 of 4 - the same sprites.json layout divergence on the Standard/Light sprite request.
AWS: recorded behavior only, as in cause 3 - per-icon geometry fixed by the published sheet for the requested Style/ColorScheme/Variant.
Emulator: identical synthetic-grid geometry as cause 3 (same per-icon width/height and x/y divergences), which confirms the layout is generated once and is independent of the requested style rather than looked up per style.
Why: same as cause 3, and additionally means the sprite JSON does not vary with Style/ColorScheme/Variant at all, so a client cannot distinguish variants.
Fix: same component as cause 3; the lookup must be keyed by Style/ColorScheme/Variant/FileName.
Traces: geo-maps-vector-basemap-style-workflow#task#3.

Note on excluded values: the recorded byte lengths and sha256 digests above are cited as evidence that the payload is not the recorded asset; the requirement is that the blob be the asset for the requested coordinates, not that it equal one recording's digest. No status code or error code diverges here - every step is 200 vs 200.
