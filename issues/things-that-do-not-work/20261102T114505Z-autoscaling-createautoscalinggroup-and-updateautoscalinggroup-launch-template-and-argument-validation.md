# CreateAutoScalingGroup and UpdateAutoScalingGroup launch-template and argument validation refusals diverge

> _Note: this issue was identified against the code base at commit `a4ef059b31cd49fc5529baf331c68065b4514ad5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateAutoScalingGroup

## Description
SIX net-new causes on the Auto Scaling (awsQuery, 2011-01-01) write-path validation. They share one fault: the emulator does not validate the group's launch source and arguments the way AWS does - it accepts requests AWS refuses, refuses a request AWS accepts, and when it does refuse it serves the wrong Code or an emulator-authored sentence. A fixer must close ALL SIX before submitting.

Cause 1 of 6 - CreateAutoScalingGroup referencing a launch template that does not exist is ACCEPTED. AWS: HTTP 400, ErrorResponse.Error.Type Sender, Code ValidationError, Message 'The specified launch template, with template name <launch-template-name>, does not exist.' - fixed text with the requested LaunchTemplateName substituted in. Smithy: CreateAutoScalingGroupType.LaunchTemplate targets LaunchTemplateSpecification; the modeled client errors are AlreadyExistsFault and LimitExceededFault only, so an unresolvable template is reported through the service-common ValidationError (sentence is recorded behavior only). Emulator: HTTP 200 and no ErrorResponse - the group is created against a template that does not exist. Why: this is the dangerous direction. A caller that typo'd a template name believes it has a working group; against AWS the call fails immediately. Fix: CreateAutoScalingGroup input validation must resolve LaunchTemplate (by name and by id) against EC2 launch-template state before the group is created. Traces: asglf-lt-identity-refusals#task#6 (4 steps across 4 fixtures).

Cause 2 of 6 - CreateAutoScalingGroup with a malformed LaunchTemplateId reports the wrong refusal. AWS: HTTP 400, Code ValidationError, Message 'Malformed launch template Id: <launch-template-id>' - fixed prefix 'Malformed launch template Id: ' plus the offending id from the request; the id's syntax is checked BEFORE the group-name uniqueness check. Smithy: CreateAutoScalingGroupType.LaunchTemplate; AlreadyExistsFault (awsQueryError AlreadyExists, 400) is modeled for a duplicate group name only. Emulator: HTTP 400 but Code AlreadyExists with Message 'AutoScalingGroup by this name already exists - A group with the name <group-name> already exists' - it skips the id syntax check and reports the later uniqueness failure instead. Why: a client is told its group name is taken when the real fault is a malformed template id, so it renames and retries forever. Fix: CreateAutoScalingGroup validation order - launch-template identity syntax before group-name uniqueness. Traces: asglf-lt-identity-refusals#task#7 (4 steps).

Cause 3 of 6 - CreateAutoScalingGroup with a well-formed, existing launch template is REFUSED. AWS: HTTP 200, CreateAutoScalingGroupResponse with ResponseMetadata.RequestId only (output Unit). Emulator: HTTP 400 with no CreateAutoScalingGroupResponse element. Why: the valid create at the end of a refusal sequence cannot succeed, so no subsequent step in the workflow can run. Hypothesis: the state left by Causes 1 and 2 (a group created against a non-existent template in Cause 1) makes the group name collide, so the emulator refuses the create AWS accepts; verify after Causes 1 and 2 are closed. Fix: CreateAutoScalingGroup handler / group state. Traces: asglf-lt-identity-refusals#task#11 (3 steps).

Cause 4 of 6 - UpdateAutoScalingGroup pointing a group at an unlaunchable launch template version is ACCEPTED. AWS: HTTP 400, Error.Type Sender, Code ValidationError, Message 'You must use a valid fully-formed launch template. The associatePublicIPAddress parameter cannot be specified when launching with multiple network interfaces.' - entirely fixed text (the first sentence is AWS's generic launch-template preamble, the second names the conflicting parameter pair); nothing is substituted from the request. Smithy: UpdateAutoScalingGroupType.LaunchTemplate targets LaunchTemplateSpecification; the only modeled client error is ScalingActivityInProgressFault, so this refusal is the service-common ValidationError (sentence is recorded behavior only). Emulator: HTTP 200 with no ErrorResponse - the group is repointed at a template version that cannot launch. Why: the group is left permanently unable to launch capacity, and the client never learns why; AWS blocks the update at the API. Fix: UpdateAutoScalingGroup validation must fetch the referenced launch-template version and reject conflicting network-interface/associatePublicIpAddress contents. Traces: autoscaling-asgeni-traj-create-group-validates-template-network-interfaces#task#11 (2 steps).

Cause 5 of 6 - UpdateAutoScalingGroup HealthCheckType refusal uses an emulator-authored sentence. AWS: HTTP 400, Code ValidationError, Message exactly 'Valid health check types are: [EC2, ELB, EBS, VPC_LATTICE].' - entirely fixed text in that order and bracket form; the rejected value is NOT echoed. Smithy: UpdateAutoScalingGroupType.HealthCheckType targets XmlStringMaxLen32 (length 1..32) with no enum, so the valid set is enforced by the service and the sentence is recorded behavior only. Emulator: HTTP 400 with its own sentence 'The HealthCheckType value <value> is not valid: it must be a comma-separated list of ["EC2", "EBS", "ELB", "VPC_LATTICE"]' - it echoes the value, reorders the list and quotes the members. Why: the Code is the generic ValidationError, so the message is the only machine-visible explanation; a client matching AWS's sentence treats the refusal as an unknown failure. Fix: the UpdateAutoScalingGroup health-check validation message text. Traces: autoscaling-asghc-traj-health-check-type-and-grace-update-refusals#task#6 (6 steps across 3 fixtures).

Cause 6 of 6 - SetInstanceHealth argument refusals carry the wrong error Code. AWS: HTTP 400 with ErrorResponse.Error.Code ValidationError for a bad HealthStatus/InstanceId argument. Smithy: SetInstanceHealthQuery marks InstanceId and HealthStatus required (XmlStringMaxLen19 / XmlStringMaxLen32, no enum); the only modeled error is the server-side ResourceContentionFault, so argument refusals are the service-common ValidationError (Type Sender). Emulator: HTTP 400 with Code MalformedInput. Why: MalformedInput is not an Auto Scaling error code at all, so a client branching on ValidationError versus a retryable protocol error misclassifies the failure. Fix: the SetInstanceHealth handler's argument validation must raise the common ValidationError rather than a protocol-level MalformedInput. Traces: autoscaling-asghc-traj-set-instance-health-argument-mistakes#task#3 (2 steps).
