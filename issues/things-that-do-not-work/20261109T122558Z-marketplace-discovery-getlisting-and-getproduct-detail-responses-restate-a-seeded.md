# GetListing and GetProduct detail responses restate a seeded row, including its promotional media and review links

> _Note: this issue was identified against the code base at commit `5386ff6290ae18fab3ce660917360d5fb6557b5e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

GetListing

## Description
This issue bundles 2 causes, both in marketplace-discovery, both in the same drill-down flow (SearchListings -> GetListing -> GetProduct). Each cause is one replay cluster and each needs its own re-replay to be confirmed closed.

NOTE ON OVERLAP - read before closing: two open issues describe this flow, 20261029T201942Z-marketplace-discovery-getlisting-getproduct-and-listfulfillmentoptions-serve-synthesized-placeholder-records.md and 20261108T055939Z-marketplace-discovery-getlisting-and-getproduct-answer-from-a-seeded-catalog.md, and the second of them already names these same two steps. The replay nonetheless reports BOTH clusters as UNOWNED (no issue carries their replay key) and their diverging-key sets are wider than either issue records: they now also include $.promotionalMedia[0].embeddedImage.url and $.reviewSummary.reviewSourceSummaries[0].sourceUrl on GetListing, and $.resources[*]/$.sellerEngagements[*]/$.purchaseIndicators still diverge on GetProduct. Neither of those two issues is a substitute for closing the causes below; treat this issue as the one carrying the replay keys for these two steps.

Cause 1 of 2: GetListing answers 200 for the requested listingId but every content member describes a generated seed row rather than the record that id names - including its promotional media URL and its review source link.
AWS: Smithy GetListing (POST /2026-02-05/getListing, input listingId ListingId @required @length(1..255) @pattern ^[\w\-]+$) returns 200 with associatedEntities (@required, @length ..100, ListingAssociatedEntity pairs of ProductInformation and OfferInformation), badges (@required, @length ..20), catalog, categories (@required, @length ..30, Category{categoryId NonEmptyString @required "machine-readable identifier of the category", displayName @required "human-readable name"}), fulfillmentOptionSummaries (@required, FulfillmentOptionSummary{fulfillmentOptionType @required, displayName @required}), highlights (@required, @length ..10), listingName, logoThumbnailUrl (URL @required @pattern ^https?://.*$), longDescription (@length ..32768), pricingModels, pricingUnits, promotionalMedia (@required, @length ..100, PromotionalMedia union of PromotionalEmbeddedImage | PromotionalEmbeddedVideo), publisher (SellerInformation), resources, reviewSummary (ReviewSummary, OPTIONAL; its ReviewSourceSummary$sourceUrl is also optional), sellerEngagements, shortDescription, useCases; errors ResourceNotFoundException 404 / AccessDeniedException 403 / ValidationException 400 / ThrottlingException 429 / InternalServerException 500. The model does not fix the CONTENT, so for content this is recorded behavior only: the response restates the listing the id names - categoryId is an opaque taxonomy identifier (a UUID in the recording, not a lowercased form of the display name) and the categories come back in the listing's stored order rather than ancestors-first; highlights are the seller's own highlight sentences (three here, within the modelled ten); badges is EMPTY when the listing has earned no badge; associatedEntities names that listing's real product AND its real offer with their real seller of record; the embedded promotional image URL and the review sourceUrl are the listing's own, served from the marketplace's media/review hosts; and listingName, shortDescription, longDescription, logoThumbnailUrl, publisher, resources, sellerEngagements and useCases all come from the record. ($.purchaseIndicators appears in the recorded response but is not declared on GetListingOutput in the on-disk model - recorded behavior only.)
Emulator: 200, but the body describes a different, generated record. categoryId is a slug derived from the display name ('machine-learning', 'structured-data-ml', 'industries', 'retail') and the list is expanded ancestors-first, so element-for-element both id and displayName differ from the record's. highlights is the two generated sentences 'Fulfilled as <fulfillment display name>' / 'Listed under <category display name>', so the listing's own highlights are gone. Two badges are reported (AWS_FREE_TIER, DEPLOYED_ON_AWS) where the recording reports none. associatedEntities[0] resolves the SAME productId to a different product and offer, with a template seller profile id. fulfillmentOptionSummaries[0] reports CLOUDFORMATION_TEMPLATE / 'AWS CloudFormation template' where the record says SAAS / 'SaaS'. listingName, shortDescription, longDescription, logoThumbnailUrl, publisher, resources, sellerEngagements, useCases and purchaseIndicators are generated text, logoThumbnailUrl being a 'https://example.com/logos/<slug>.png' URL on a host the emulator does not serve; $.promotionalMedia[0] and its embeddedImage.url diverge the same way ('https://example.com/media/<slug>/overview.png'), and $.reviewSummary.reviewSourceSummaries[0].sourceUrl is the shared constant the seeder gives every row rather than this listing's own review link.
Why: GetListing is the detail view the whole discovery flow funnels into, so a client that looked a listing up by id renders someone else's generated record. The identifiers and enums are load-bearing: a client that feeds a returned categoryId back as a CATEGORY search filter, or persists it, handles an identifier shape this service never issues; a client that reads fulfillmentOptionType branches on a deployment model the listing does not have; a client that reads badges advertises a free-tier / deployed-on-AWS status the listing has not earned; and the media and review URLs point at hosts nothing serves, so the detail page's image and reviews link are both dead.
Fix: the seeded catalog and the projections GetListing restates it through, in the marketplace-discovery crate's state (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs): the per-row seeder that synthesizes highlights, long descriptions, logo and promotional-media URLs and the review summary, the slug-keyed taxonomy helper that mints categoryId and expands ancestors ahead of the stored category, the positional pricing/fulfillment assignment, and the derived badges. The handler must restate the stored record for the requested listingId.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#2 (GetListing, expected 200 / got 200, 45 diverging keys).

Cause 2 of 2: GetProduct repeats the substitution for the product resolved from that listing, and inverts deployedOnAws.
AWS: Smithy GetProduct (POST /2026-02-05/getProduct, input productId @required @pattern ^[\w\-]+$) returns 200 with productId, catalog, productName, manufacturer (SellerInformation @required), deployedOnAws (DeployedOnAwsStatus @required: DEPLOYED | NOT_DEPLOYED | NOT_APPLICABLE), shortDescription, longDescription, logoThumbnailUrl, fulfillmentOptionSummaries, categories, highlights (@length ..10), promotionalMedia, resources, sellerEngagements, listingId; same five modelled errors. Recorded behavior for content: the product restates its own stored record - taxonomy-identifier categories in stored order, the seller's own three highlight sentences, its own manufacturer, productName, descriptions, logo URL, resources and seller engagements - and deployedOnAws reports that product's stored deployment status (NOT_DEPLOYED for this SaaS product), not a value inferred from its fulfillment type.
Emulator: 200 with the same substitutions as cause 1 - $.categories[0..3] differ whole-element (slug ids, ancestors-first), highlights[0] is 'Fulfilled as AWS CloudFormation template' with highlights[1] and [2] absent, fulfillmentOptionSummaries[0] is CLOUDFORMATION_TEMPLATE / 'AWS CloudFormation template' instead of SAAS / 'SaaS', logoThumbnailUrl is the example.com placeholder, and productName, manufacturer, shortDescription, longDescription, resources[0..3], sellerEngagements[0..1] and purchaseIndicators are template text. $.deployedOnAws is 'DEPLOYED' where the record reports 'NOT_DEPLOYED'. Hypothesis: deployedOnAws is derived from the seeded fulfillment option type (a CloudFormation row counting as deployed) rather than read off the product.
Why: a client that drills product detail after a listing gets a second, independently wrong copy of the same record, so cross-checking listing against product cannot detect the substitution. deployedOnAws is what a buyer-side client uses to decide whether the product runs in the buyer's own account, so inverting it sends the client down a deployment path AWS would not offer for that product.
Fix: same component as cause 1 - the seeder and the category / highlight / fulfillment-summary projections GetProduct shares with GetListing in that crate's state, plus the deployedOnAws derivation, which must restate the product's stored status.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#3 (GetProduct, expected 200 / got 200, 32 diverging keys).

Explicitly NOT claimed as requirements anywhere in this issue: the recorded literal ids, names and URLs (listing / product / offer / fulfillment-option ids, sellerProfileId values, CloudFront media and review-list paths) and any clock-derived timestamp. Those differ per environment and per run. The defects are the identifier FORMAT, the list lengths and ordering, which badges and optional members appear, the enum values reported for fulfillment and deployment, that the media and review URLs address a host the emulator does not serve, and that the content is a generated template rather than the record the requested id names.
