# cloudfront: three error-contract divergences — EntityNotFound messages append the identifier, an enum violation answers ValidationException instead of InvalidArgument, and TagResource on a cache-policy ARN answers NoSuchResource

Cause 1 of 3: the EntityNotFound refusals of GetAnycastIpList and GetConnectionGroupByRoutingEndpoint return an emulator-authored sentence with the looked-up identifier appended, instead of the service's fixed per-code sentence.
AWS: Smithy: GetAnycastIpList (GET /2020-05-31/anycast-ip-list/{Id}) and GetConnectionGroupByRoutingEndpoint (GET /2020-05-31/connection-group?RoutingEndpoint=...) both model EntityNotFound as a client error with httpError 404 (shape com.amazonaws.cloudfront#EntityNotFound, doc "The entity was not found.", single Message member). The wire text for each is a CONSTANT per operation and carries nothing from the request (recorded behavior): GetAnycastIpList answers 404 EntityNotFound with Message "The specified Anycast IP list does not exist" and GetConnectionGroupByRoutingEndpoint answers 404 EntityNotFound with Message "The specified connection group does not exist." — the whole sentence is fixed text; there is no variable part at all, in particular no Id and no routing endpoint.
Emulator: the status (404) and the code (EntityNotFound) match, but the message is a different sentence with the request's identifier appended: for a well-formed, non-existent Anycast list Id it answers "The specified Anycast static IP list does not exist: <Id>" (replay: '...does not exist: aip_AAAAAAAAAAAAAAAAAAAAAA'), and for an unknown routing endpoint it answers "The specified connection group does not exist: <RoutingEndpoint>" (replay: '...does not exist: sim2real-nonexistent.cloudfront.net'). Both the fixed text ("Anycast static IP list" vs "Anycast IP list"; trailing-period difference on the connection-group sentence) and the appended identifier diverge.
Why: a client or golden-file test that compares the documented per-code sentence sees a mismatch on every not-found path, and the appended value leaks the caller's identifier into an error contract that carries none — code that parses the message for a resource name gets a value real AWS never sends.
Fix: the per-code message constants used by these two handlers (the EntityNotFound construction in the GetAnycastIpList and GetConnectionGroupByRoutingEndpoint handlers, plus any shared message constructor in the service's state/error module) — serve the per-code sentence with no request-derived suffix.
Traces: cloudfront.get-anycast-ip-list-malformed-id-invalid-argument-rejected, cloudfront.op-contract-get-connection-group-by-routing-endpoint.

Cause 2 of 3: UpdateAnycastIpList refuses an out-of-enum IpAddressType with the foreign error code ValidationException and a Smithy-constraint message, instead of CloudFront's modeled InvalidArgument.
AWS: Smithy: UpdateAnycastIpList (PUT /2020-05-31/anycast-ip-list/{Id}) models exactly these errors — AccessDenied (403), EntityNotFound (404), InvalidArgument (400), InvalidIfMatchVersion (400), PreconditionFailed (412), UnsupportedOperation (400). IpAddressType targets the enum com.amazonaws.cloudfront#IpAddressType with values [ipv4, ipv6, dualstack], so a value outside that set is an invalid argument and the refusal is InvalidArgument (400, shape doc "An argument is invalid."). There is NO ValidationException shape anywhere in the CloudFront model (the model has no such shape), so that code can never appear on this wire. The refusal's message is not recorded for this value (recorded behavior only: the pool account sits at the zero-default Anycast static IP list quota, so AWS refuses CreateAnycastIpList first) — the requirement asserted here is the code and the error class, not the message text.
Emulator: the call is refused with code 'ValidationException' and the message "1 validation error detected: Value 'ipv7-bogus' at 'ipAddressType' failed to satisfy constraint: Member must satisfy enum value set: [ipv4, ipv6, dualstack]" — an awsJson/awsQuery-style constraint report, with a lowerCamel member path, emitted for a rest-xml service that does not model that error. Context (not a filed cause): the emulator also let CreateAnycastIpList succeed, which is why the update leg was reached at all; the check accepts a successful create, so that is not asserted.
Why: clients branch on the error code, and `except ClientError as e: e.response['Error']['Code'] == 'InvalidArgument'` never matches; botocore cannot even model the response as a known CloudFront error, so retry/validation logic written against AWS takes the wrong branch and surfaces an unmodeled failure.
Fix: the enum/shape validation layer for the cloudfront service must map constraint violations to the operation's modeled error — raise InvalidArgument (400) from UpdateAnycastIpList's input validation (its handler/validation in the cloudfront service crate) rather than letting the generic ValidationException path answer for a rest-xml service that does not model it.
Traces: cloudfront.update-anycast-ip-list-invalid-argument-rejected.

Cause 3 of 3: TagResource on a cache-policy ARN answers NoSuchResource (resource-missing) instead of InvalidArgument (resource type not taggable).
AWS: Smithy: TagResource (POST /2020-05-31/tagging?Operation=Tag, success 204) takes Resource as an httpQuery ResourceARN constrained by pattern ^arn:aws(-cn)?:cloudfront::[0-9]+: and models AccessDenied (403), InvalidArgument (400), InvalidTagging (400) and NoSuchResource (404). CloudFront's tagging API accepts only taggable resource types; a cache-policy ARN is not one, so it is refused as a bad PARAMETER, not as a missing resource: 400 InvalidArgument with Message "The parameter resource type: cache-policy is invalid." (recorded behavior). The sentence's fixed text is "The parameter resource type: " + <the resource type parsed out of the submitted ARN> + " is invalid." — the only variable part is the resource-type token taken from the request's ARN; it holds even when the cache policy named by the ARN genuinely exists and is attached to a live distribution's DefaultCacheBehavior. The same resource-type rule governs ListTagsForResource and UntagResource, which the check asserts next but never reached.
Emulator: the call is refused 404 NoSuchResource with Message "The specified resource doesn't exist. Update your request and try again." — the emulator classified an untaggable resource TYPE as an absent resource, so it reports an existence failure for a cache policy that exists.
Why: a client distinguishing "I passed an ARN of the wrong kind" (permanent, fix the request) from "the resource is gone" (retry/recreate) is told the wrong thing, and an existence probe built on TagResource reports a live cache policy as missing.
Fix: TagResource's Resource-ARN validation (and the shared tagging resource-type check used by ListTagsForResource/UntagResource) in the cloudfront service's tagging handlers — parse the resource type out of the ARN and refuse an unsupported type with InvalidArgument before any lookup, reserving NoSuchResource for a supported type whose id is absent.
Traces: cloudfront.tag-resource-on-cache-policy-arn-via-distribution.
