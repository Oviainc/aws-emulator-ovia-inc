# EMR Studio/notebook refusals drop AWS's sentence and the AWSEditors wrapper, CreateStudio accepts an unresolvable network, and three more refusal/lifecycle paths diverge (6 causes)

> _Note: this issue was identified against the code base at commit `ebea418ed7238d7557ed4699ab6be023240b4505`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStudio

## Description
This issue bundles 6 net-new root causes in the EMR surface the suite lists under the `emr` service heading. Causes 1-2 are the Studio/notebook (AWSEditors backend) refusal format, Cause 3 is a request AWS refuses that is accepted with HTTP 200, Causes 4-5 are emulator-authored refusal messages on the cluster plane, and Cause 6 is a lifecycle divergence on EMR Serverless job runs. Each cause must be closed before submitting.

In every message below the fixed text is the requirement and the variable parts are named; the ids/values in the recordings are per-run values that only fill the template. Per-call request ids are NOT part of the requirement — the checks extract the actual request id out of the observed message before comparing.

--- Cause 1 of 6: Studio/notebook enum refusals serve the framework's raw constraint text instead of AWS's sentence plus the AWSEditors service wrapper ---
AWS: Smithy: ListNotebookExecutions.Status targets enum NotebookExecutionStatus, ListStudioSessionMappings.IdentityType targets enum IdentityType; both operations model InvalidRequestException (client, HTTP 400). The message is recorded behavior only: EMR's Studio/notebook plane is fronted by the `AWSEditors` backend, and its 400 InvalidRequestException message is `<AWS sentence> (Service: AWSEditors; Status Code: 400; Error Code: InvalidRequestException; Request ID: <request id>; Proxy: null)` — i.e. a leading per-error sentence (`Invalid Execution Status: <Status>` for ListNotebookExecutions; the constant `IdentityType is not valid.` for ListStudioSessionMappings, which does NOT echo the value) followed verbatim by that parenthesised wrapper. Fixed text: ` (Service: AWSEditors; Status Code: 400; Error Code: InvalidRequestException; Request ID: ` / `; Proxy: null)`; variable parts: the leading sentence's own value (the rejected Status) and the per-call request id.
Emulator: returns only the generic boundary-validation diagnostic, e.g. `1 validation error detected: Value 'NOT_A_REAL_STATUS' at 'status' failed to satisfy constraint: Member must satisfy enum value set: [START_PENDING, STARTING, RUNNING, FINISHING, FINISHED, FAILING, FAILED, STOP_PENDING, STOPPING, STOPPED]` and `1 validation error detected: Value 'ADMIN' at 'identityType' failed to satisfy constraint: Member must satisfy enum value set: [USER, GROUP]` — the AWS sentence and the whole AWSEditors wrapper are absent, and the enum set AWS does not disclose is leaked.
Why: every client that classifies these refusals by message (the CLI prints it, operator runbooks and SDK branch logic key on it) sees an unrecognised string; the absence of the wrapper also means the caller cannot recover the backend service name or request id AWS puts in the message for support.
Fix: the enum validation of these operations must happen in the handlers (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/list_notebook_executions.rs, list_studio_session_mappings.rs) — or in the EMR crate's shared Editors-plane error mapping — emitting AWS's sentence plus the AWSEditors wrapper rather than letting the framework's generic constraint message reach the wire.
Traces: emr.list-notebook-executions-invalid-status-filter-rejected, emr.list-studio-session-mappings-invalid-identity-type-filter-rejected, emr.list-studio-session-mappings-invalid-identity-type-rejected.

--- Cause 2 of 6: the unknown-notebook-execution refusal omits AWS's sentence and the same AWSEditors wrapper ---
AWS: Smithy: DescribeNotebookExecution / StopNotebookExecution (NotebookExecutionId required) model InvalidRequestException (client, 400). Recorded behavior only for the text: an unknown execution id is refused 400 InvalidRequestException with `Execution does not exist (Service: AWSEditors; Status Code: 400; Error Code: InvalidRequestException; Request ID: <request id>; Proxy: null)` — the leading sentence is the CONSTANT `Execution does not exist` (no id echoed); the only variable part is the request id.
Emulator: right code, but the message is `Notebook execution id 'ex-ZZZZZZZZZZZZZZZZZZZZZZZZZ' is not valid or does not exist.` — an emulator-authored sentence that echoes the id AWS omits and carries no wrapper. Both DescribeNotebookExecution and StopNotebookExecution are affected.
Why: a caller cannot tell an unknown-execution refusal from any other InvalidRequestException on these operations, and polling code that branches on the not-found sentence loops or aborts wrongly.
Fix: the unknown-id branch of describe_notebook_execution.rs / stop_notebook_execution.rs in the EMR crate (shared Editors-plane refusal helper).
Traces: emr.op-notebook-execution-ops-reject-unknown-execution.

--- Cause 3 of 6: CreateStudio accepts an unresolvable VPC/subnet/security groups and a ServiceRole that does not exist ---
AWS: Smithy: CreateStudio requires Name, AuthMode, VpcId, SubnetIds, ServiceRole, WorkspaceSecurityGroupId, EngineSecurityGroupId, DefaultS3Location and models InvalidRequestException (client, 400). Recorded behavior only for the text: a request naming network objects that do not resolve and a role the service cannot assume is refused 400 InvalidRequestException with `This entity does not have permissions to assume role '<ServiceRole>' (Service: AWSEditors; Status Code: 400; Error Code: InvalidRequestException; Request ID: <request id>; Proxy: null)` — fixed text `This entity does not have permissions to assume role '` / `'` plus the AWSEditors wrapper; variable parts: the ServiceRole ARN from the request and the request id. No studio is left behind (ListStudios must not report the Name).
Emulator: answers HTTP 200 with a StudioId and a Url for a VPC, subnets, security groups and role that do not exist, so the studio is created and then listed.
Why: a client gets a Studio that cannot possibly work and no signal that its network/role wiring is wrong; the negative path of any Studio provisioning tool is untestable, and the resource leaks into ListStudios.
Fix: the CreateStudio handler (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/create_studio.rs) — resolve VpcId/SubnetIds/security groups and the ServiceRole against the EC2/IAM state before writing any record, and refuse with the sentence above. The open issue 20261029T175551Z-emr-accepts-two-requests-aws-refuses-unknown-releaselabel.md names the unresolvable-Studio-network acceptance but carries no replay key for this check.
Traces: emr.op-create-studio-rejects-unresolvable-network.

--- Cause 4 of 6: CreateSecurityConfiguration's illegal-EncryptionMode refusal is the emulator's own sentence ---
AWS: Smithy: CreateSecurityConfiguration(Name required, SecurityConfiguration required — a plain String), error InvalidRequestException (client, 400). The document's encryption semantics are not modelled, so recorded behavior only: an unmodelled EncryptionMode value is refused 400 with `Invalid security configuration; instance value (<EncryptionMode>) is not allowed; allowed values: [SSE-S3, SSE-KMS, CSE-KMS, CSE-Custom].` — fixed text `Invalid security configuration; instance value (` / `) is not allowed; allowed values: [SSE-S3, SSE-KMS, CSE-KMS, CSE-Custom].`; variable part: the rejected EncryptionMode from the submitted document.
Emulator: `EncryptionMode 'SSE-XYZ' is not valid; it must be one of SSE-S3, SSE-KMS, CSE-KMS, CSE-Custom.` — a different sentence with a different list rendering and without AWS's `Invalid security configuration;` prefix.
Why: the `Invalid security configuration;` prefix is how callers group every document-level rejection of this operation; without it, and with a reworded clause, no match or classification works.
Fix: the security-configuration document validation in create_security_configuration.rs (EMR crate). Related but not covering: 20261029T175551Z-emr-control-plane-refusals-use-emulator-authored-messages.md (fixed) covers the MALFORMED-JSON constant for this operation, not the per-field allowed-values sentence.
Traces: emr.security-configuration-rejects-illegal-encryption-semantics.

--- Cause 5 of 6: the DescribeJobFlows deprecation refusal is the emulator's own sentence ---
AWS: Smithy: DescribeJobFlows carries @deprecated and models InternalServerError only, so recorded behavior only: the operation is refused with the CONSTANT message `DescribeJobFlows API is deprecated. Please refer to http://docs.aws.amazon.com/ElasticMapReduce/latest/API/API_DescribeJobFlows.html for further information.` — no variable part.
Emulator: `The DescribeJobFlows API is deprecated and no longer serves job flows. Use ListClusters, DescribeCluster, ListSteps, ListInstanceGroups and ListBootstrapActions instead.` — an emulator-authored sentence naming replacement operations AWS does not name.
Why: a client matching AWS's deprecation sentence (or parsing the documentation URL out of it) does not recognise the refusal.
Fix: the DescribeJobFlows handler (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/describe_job_flows.rs) — emit AWS's constant sentence verbatim, URL included.
Traces: emr.op-describe-job-flows-is-deprecated.

--- Cause 6 of 6: an EMR Serverless Spark job run never executes — it settles terminal FAILED instead of SUCCESS ---
AWS: recorded behavior only (the StartJobRun/GetJobRun models carry no execution semantics): a StartJobRun submitting a valid Spark entry point on a STARTED application progresses through the run states and reaches state `SUCCESS`, with the driver's work observable; a FAILED run carries a stateDetails describing the actual failure.
Emulator: the run reaches terminal `FAILED` with stateDetails `This emulator records job runs but executes no Spark or Hive workload, so the job run ended without running.` — i.e. no submitted workload ever runs and SUCCESS is unreachable.
Why: every client that waits for a job run to succeed (and every negative control that needs a successful sibling run to isolate its failure) can never pass; a SUCCESS state is simply not reachable on this service.
Fix: the EMR Serverless job-run lifecycle/state machine in the emr-serverless crate (the StartJobRun handler and the run-state progression it schedules), so a valid submission settles SUCCESS. Related open issues, neither of which carries this check's replay key: 20261024T013257Z-emr-serverless-job-runs-never-execute-the-submitted.md and 20261022T154846Z-emr-serverless-job-runs-are-recorded-but-never-executed.md (the latter owns the sibling failing-script check).
Traces: emr.emr-serverless-spark-job-run-reaches-success.
