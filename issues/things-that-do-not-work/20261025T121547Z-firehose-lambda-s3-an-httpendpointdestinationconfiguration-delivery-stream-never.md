# firehose__lambda__s3: an HttpEndpointDestinationConfiguration delivery stream never issues an HTTPS request to the configured endpoint, so the documented request envelope is never produced (1 cause)

> _Note: this issue was identified against the code base at commit `2e55e3f174321d59189949bdc160ce3c5e1a8b8d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRecordBatch

## Description
Cause 1 of 1: Firehose's HTTP-endpoint destination has no delivery path at all — a stream created with HttpEndpointDestinationConfiguration reaches ACTIVE and accepts PutRecordBatch with FailedPutCount 0, but no HTTPS request is ever sent to HttpEndpointConfiguration.Url, so none of the documented request envelope (headers or body) is ever produced and nothing is observable at the endpoint.

AWS: Smithy (com.amazonaws.firehose) models HttpEndpointDestinationConfiguration with required EndpointConfiguration (HttpEndpointConfiguration: required Url, pattern ^https://, plus optional Name and AccessKey), required S3Configuration, and optional BufferingHints, RequestConfiguration (ContentEncoding enum, CommonAttributes list, @length 0..50), RetryOptions and S3BackupMode (AllData | FailedDataOnly). Per the documented HTTP delivery request/response spec (docs.aws.amazon.com/firehose/latest/dev/httpdeliveryrequestresponse.html), once such a stream is ACTIVE and records are put, Firehose POSTs the buffered batch to that Url and the request carries: X-Amz-Firehose-Protocol-Version: "1.0" (fixed text); X-Amz-Firehose-Request-Id: an opaque GUID in 8-4-4-4-12 hex form (per-request value); X-Amz-Firehose-Source-Arn: the delivery stream's own ARN as DescribeDeliveryStream reports it (value from state); X-Amz-Firehose-Access-Key: the configured AccessKey copied verbatim (value from the stream's configuration, never re-encoded); Content-Type: application/json (fixed text); X-Amz-Firehose-Common-Attributes: a JSON object of the fixed shape {"commonAttributes": { <AttributeName>: <AttributeValue>, ... }} whose members are the CommonAttributes configured on the stream; and NO Content-Encoding header at all when RequestConfiguration.ContentEncoding is NONE. The body is one JSON document of the fixed shape {"requestId": <same value as the X-Amz-Firehose-Request-Id header>, "timestamp": <integer milliseconds since epoch at which Firehose generated the request>, "records": [{"data": <base64 of exactly the record bytes that were put, with no envelope and no appended delimiter>}, ...]}, each records[] entry having exactly the one member `data`. When the endpoint answers 200 with the documented success envelope, the batch is acknowledged: nothing is copied to the ErrorOutputPrefix location, nothing is written to the S3 backup under S3BackupMode FailedDataOnly, and the batch is not retried.

Emulator: the control plane accepts the stream and DescribeDeliveryStream echoes HttpEndpointDestinationDescription.EndpointConfiguration.Url, and PutRecordBatch answers 200 with a RecordId per record, but the data plane never contacts the endpoint. The behavioral check's endpoint records every request it receives into S3 as a side channel, and that capture prefix stays empty for the whole poll; the check fails while waiting on it (the harness reports `Check timed out after 60.0s`, and the check's own poll raises `DATAPLANE_UNIMPLEMENTED?: the HTTP endpoint receives all 3 records ... did not happen within 300.0s. A target that accepts an HttpEndpointDestinationConfiguration and never issues an HTTPS request has no HTTP delivery path at all`). Because no request is made, none of the headers, the requestId/timestamp/records body, or the 200-acknowledgement semantics above can be exercised.

Why: a client that wires a stream to its own HTTP endpoint (the standard pattern for third-party/partner destinations and for any custom HTTPS sink) sees a healthy, ACTIVE stream and successful puts while its endpoint receives nothing. Integration tests of an endpoint implementation — header auth via X-Amz-Firehose-Access-Key, protocol-version negotiation, requestId echoing, common-attribute propagation, the retry/backup contract — all pass vacuously against the emulator and then break against real AWS. Data put into the stream is silently lost: it neither reaches the endpoint nor appears under the failure backup.

Fix: the Firehose service's delivery engine needs an HTTP-endpoint destination path alongside its S3 path — the buffered-batch flusher must, for a stream whose destination is HttpEndpointDestinationDescription, build and POST the documented envelope to EndpointConfiguration.Url (header set and JSON body as above, generated per flush), interpret the endpoint's response (200 with a matching requestId = acknowledged, no backup/error write, no retry; otherwise RetryOptions then the S3BackupMode path), and honour HttpEndpointBufferingHints and RequestConfiguration.ContentEncoding when deciding when to flush and whether to compress. This is a distinct destination type from the already-open S3/OpenSearch/Glue-conversion delivery issues (e.g. 20261024T005347Z-firehose-never-delivers-buffered-records-to-the-s3.md, 20261024T005347Z-firehose-iam-opensearch-s3-firehose-opensearch-destination-is-inert-no-document-is.md, 20261025T083505Z-firehose-s3-delivery-ignores-bufferinghints-the-destination-role.md); none of those names the HTTP endpoint destination, so fixing them does not make this request appear.
