# Elastic Beanstalk control-plane guards are not enforced: authorization, OperationsRole validation, terminated/launching state gates, and CheckDNSAvailability shape

> _Note: this issue was identified against the code base at commit `8bb3e31d2bc3a99611966740f58be573e66087fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociateEnvironmentOperationsRole

## Description
SEVEN net-new root causes on the Elastic Beanstalk control plane, all of the same family: calls real AWS refuses are accepted (or refused with the wrong code), and one response carries a member AWS omits. Each cause is independent and must be closed separately.

Cause 1 of 7: no IAM authorization enforcement — calls made with explicitly denied credentials succeed.
AWS: Smithy models InsufficientPrivilegesException (httpError 403, awsQueryError code InsufficientPrivilegesException) on AssociateEnvironmentOperationsRole, RebuildEnvironment, ComposeEnvironments and CreateEnvironment; recorded behavior for a caller whose IAM policy denies the action/resource is a 4xx rejection with Error.Code 'AccessDenied' and no side effect. Emulator: the restricted-caller call returns HTTP 200 with an empty result (AssociateEnvironmentOperationsRole, RebuildEnvironment), returns 200 with a PlatformSummary (CreatePlatformVersion), or fails identically to the full-privilege caller with 'MissingParameter' (ComposeEnvironments) — i.e. the authorization check never runs. Why: every negative-authorization path a client or a least-privilege deployment relies on silently becomes a success; a mutation that must be blocked is actually performed. Fix: the shared request-authorization layer the elasticbeanstalk handlers call (it must evaluate the caller's IAM identity and return the modeled 403/AccessDenied) plus the per-op wiring in the elasticbeanstalk service crate's src/ops/. Traces: elasticbeanstalk.associate-environment-operations-role-insufficient-privileges-denied, elasticbeanstalk.create-platform-version-insufficient-privileges-denied, elasticbeanstalk.rebuild-environment-insufficient-privileges-denied, elasticbeanstalk.compose-environments-insufficient-privileges-blocked.

Cause 2 of 7: AssociateEnvironmentOperationsRole accepts an OperationsRole ARN that names no IAM role.
AWS: Smithy AssociateEnvironmentOperationsRole.OperationsRole is required (@length 1..256); recorded behavior for an ARN naming a role that does not exist is a 400 with Error.Code 'InvalidParameterValue' and a message of the form "Operations role ARN '<arn>' isn't valid. Specify an existing IAM role." (message quoted as the recorded example), and the environment's previously associated OperationsRole is left untouched. Emulator: HTTP 200, empty body, association accepted. Why: an environment can be put into operations-role mode pointing at a nonexistent role, and a client that treats success as proof the role is usable then sees every subsequent operation fail for an unrelated reason. Fix: validation in the AssociateEnvironmentOperationsRole handler — resolve the ARN against IAM state before mutating the environment. Traces: elasticbeanstalk.associate-environment-operations-role-untrusted-role-rejected, elasticbeanstalk.associate-operations-role-nonexistent-rejected.

Cause 3 of 7: ApplyEnvironmentManagedAction does not gate on the environment's state before resolving ActionId.
AWS: Smithy ApplyEnvironmentManagedAction models ElasticBeanstalkServiceException (400) and ManagedActionInvalidStateException (400); recorded behavior is that an unknown ActionId against a Ready environment is rejected with Error.Code 'ElasticBeanstalkServiceException', while the IDENTICAL ActionId against a Terminated environment is rejected first for the environment being unavailable, with Error.Code 'InvalidParameterValue'. Emulator: the Terminated-environment call still returns 'ElasticBeanstalkServiceException' (message example: "No scheduled managed action with ActionId = '<id>' exists for environment <env>."), i.e. it goes straight to action-id lookup. Why: a client cannot distinguish 'the action id is wrong' from 'this environment is gone', and the two codes drive different retry logic. Fix: the environment-availability gate in the ApplyEnvironmentManagedAction handler, ahead of action-id resolution. Traces: elasticbeanstalk.apply-environment-managed-action-invalid-state-rejected.

Cause 4 of 7: DeleteApplication with a running environment is refused with the wrong error code.
AWS: recorded behavior — DeleteApplication without TerminateEnvByForce while the application still has a Ready environment is a 400 with Error.Code 'InvalidParameterValue' (message example: "Unable to delete application <app> because it has a version that is deployed to a running environment."); the application and environment survive, and the same call with TerminateEnvByForce=true succeeds. Smithy: DeleteApplication models OperationInProgressException (awsQueryError code OperationInProgressFailure) — that is the modeled error for a concurrent operation, not for this case. Emulator: Error.Code 'OperationInProgressFailure'. Why: a client branching on InvalidParameterValue to retry with the force flag never takes that branch and treats the refusal as a transient in-progress conflict to retry forever. Fix: the DeleteApplication handler's running-environment check must raise the InvalidParameterValue rejection rather than the operation-in-progress error. Traces: elasticbeanstalk.delete-application-with-active-environment-rejected.

Cause 5 of 7: TerminateEnvironment is accepted while the environment is still in its initial launch phase.
AWS: recorded behavior — TerminateEnvironment issued immediately after CreateEnvironment is rejected with a 400 Error.Code 'InvalidParameterValue' whose message names the current launch sub-phase ("... It is currently initial." / "... It is currently pending creation."); it is only accepted once that phase clears, and then returns Status 'Terminating'. Emulator: the immediate call returns HTTP 200 with Status 'Terminating'. Why: the temporal guard that keeps a launch from being torn down mid-provision is absent, so a client's immediate-rollback path appears to work where AWS refuses it, and the state machine it is testing is not modelled. Fix: the launch-phase guard in the TerminateEnvironment handler / environment state machine. Traces: elasticbeanstalk.environment-terminate-guarded-then-enters-terminating.

Cause 6 of 7: CreateEnvironment reports a CNAME in the launch response, before the environment is provisioned.
AWS: Smithy CreateEnvironment -> EnvironmentDescription with optional CNAME (DNSCname); recorded behavior is that the synchronous CreateEnvironment response for a web-server-tier launch carries no CNAME yet — it appears on later DescribeEnvironments reads once provisioning assigns it. Emulator: CreateEnvironment's own response already contains a fully-formed CNAME. Why: a client that treats the presence of CNAME as 'the endpoint exists' starts resolving/probing a hostname that is not yet serving; the launch response is claiming state that has not happened. Fix: the CreateEnvironment handler/serializer — populate CNAME only once the environment record has been assigned one. Traces: elasticbeanstalk.environment-create-enters-launching.

Cause 7 of 7: CheckDNSAvailability returns FullyQualifiedCNAME for a prefix that is NOT available.
AWS: Smithy CheckDNSAvailability -> CheckDNSAvailabilityResultMessage{Available (boolean), FullyQualifiedCNAME (optional)}; recorded behavior is that once a prefix is taken the response carries Available=false and OMITS FullyQualifiedCNAME entirely (the key is absent, not empty). Emulator: Available=false together with FullyQualifiedCNAME='<prefix>.<region>.elasticbeanstalk.com'. Why: a client that reads FullyQualifiedCNAME as 'this is the hostname I just reserved' is handed a hostname belonging to somebody else's environment. Fix: the CheckDNSAvailability handler/serializer — emit FullyQualifiedCNAME only on the Available=true path. Traces: elasticbeanstalk.e2e-swap-cnames-then-dns-check-flips (the same response shape is visible in elasticbeanstalk.e2e-swap-cname-then-verify-dns-and-traffic-consequence).
