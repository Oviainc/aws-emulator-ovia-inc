# apigateway__dynamodb__lambda__logs: 4 net-new causes — an HTTP-API AWS_PROXY integration invokes a Lambda with no resource-policy grant, the Lambda Python runtime has no _socket module, and in-function API Gateway / CloudWatch Logs calls are never IAM-denied

## Operation

## Description
FOUR net-new root causes carried by failing checks of this service that no open issue claims. A fixer must close all four before submitting.

Cause 1 of 4: an API Gateway v2 HTTP API AWS_PROXY integration invokes its Lambda target with no resource-policy grant at all, and answers 200.
AWS: an HTTP API route whose integration is IntegrationType=AWS_PROXY / PayloadFormatVersion=2.0 pointing at a function ARN may invoke that function only when the function's resource policy carries a lambda:InvokeFunction statement whose Principal is apigateway.amazonaws.com and whose SourceArn matches the API/route (added with lambda AddPermission — Smithy: AddPermission input members Action, Principal, SourceArn, StatementId). Without that statement the integration invoke is refused by Lambda and the stage answers HTTP 500 with body {"message":"Internal Server Error"}; the function never executes, so nothing it prints appears in /aws/lambda/<fn>. Adding the statement afterwards makes the identical request return the handler's own 200 body. The requirement is the fixed 500 refusal plus a non-executing integration; the function name, API id and SourceArn are values of the request.
Emulator: the same GET on the $default auto-deployed stage is served HTTP 200 with the handler's body, i.e. the integration invoked the function without evaluating its resource policy at all, so the negative case is indistinguishable from the positive control.
Why: the Lambda resource policy is the only thing between a public HTTP API stage and a function. A client whose integration permissions were never wired (or were wired to the wrong SourceArn) sees a working API against the emulator and a 500 in production, and every least-privilege/permission-boundary test over HTTP APIs passes vacuously.
Fix: the apigatewayv2 execute-api integration-invoke path — it must evaluate the target function's resource policy (principal, action, source ARN) before invoking and serve the documented 500 refusal when no statement matches. Open issue 20261107T035448Z-apigateway-dynamodb-lambda-logs-3-net-new-causes.md describes the same gap for the REST (apigateway v1) AWS_PROXY integration and does not claim the HTTP-API path.
Traces: apigateway__dynamodb__lambda__logs.apigw-http-api-lambda-missing-permission-negative.

Cause 2 of 4: the Lambda Python runtime has no _socket extension module, so any handler importing botocore/urllib-over-TLS faults Runtime.ImportModuleError.
AWS: recorded behavior only — the managed python3.x Lambda runtimes ship a complete CPython standard library (including the _socket extension) and the AWS SDK, so a handler that does `import botocore.session` / `from botocore.auth import SigV4Auth` loads and runs, and Invoke returns its result payload with no FunctionError.
Emulator: Invoke returns a function error payload {"errorMessage": "Unable to import module 'index': No module named '_socket'", "errorType": "Runtime.ImportModuleError", "stackTrace": []}, so the handler body never runs and nothing it was meant to exercise (here, a SigV4-signed outbound call to an execute-api endpoint) is observable.
Why: a client's handler is the unit of work; a runtime whose stdlib cannot open a socket cannot make any AWS or HTTP call, so every in-function integration path is untestable and the emulator reports a runtime fault where AWS reports the handler's own answer.
Fix: the Lambda runtime/sandbox that assembles the Python interpreter for an invocation — the stdlib extension modules it exposes (at minimum _socket) must match the managed runtime. Related open issues cover other services' instances of the same crippled runtime (20261105T083215Z-ec2-lambda-route53-the-lambda-python-runtime-has-no-socket-extension.md, 20261105T095706Z-lambda-xray-the-lambda-python-runtime-has-no.md); none claims this service's check.
Traces: apigateway__dynamodb__lambda__logs.lambda-apigateway-cross-account-negative.

Cause 3 of 4: an in-function API Gateway control-plane call from a role with NO apigateway permissions succeeds and creates the resource, instead of being denied.
AWS: API Gateway control-plane calls are authorized by IAM before the operation runs. A Lambda execution role carrying only the basic-execution/logs permissions (no apigateway:POST) calling CreateResource is refused with HTTP 403 and error code AccessDeniedException; the message's fixed text is "User: <caller arn> is not authorized to perform: apigateway:POST on resource: <resource arn> because no identity-based policy allows the apigateway:POST action", with the caller ARN, the action and the resource ARN taken from the request and the caller's identity. The effect is absent: GetResources shows no resource with that pathPart. Smithy models CreateResource's per-operation errors as BadRequestException/ConflictException/LimitExceededException/NotFoundException/TooManyRequestsException/UnauthorizedException — the authorization refusal is served by the IAM layer ahead of the handler, not by one of those.
Emulator: the handler reports success — {'ok': True, 'id': '<generated>', 'path': '/<pathPart>'} — and the resource is actually created, so an unauthorized role mutated the API. There is no refusal, no error code and no message.
Why: a client relying on IAM to bound what its functions may do gets no boundary at all: a role audit, a least-privilege rollout or a blast-radius test all pass on the emulator while the same code is denied in production (or, worse, the emulator lets a function mutate control-plane state it must not touch).
Fix: the IAM authorization gate in front of the apigateway control-plane handlers (identity-based policy evaluation for apigateway:POST/GET on the resource ARN), returning the 403 AccessDeniedException refusal before CreateResource mutates state. Open issue 20261106T151148Z-apigateway-dynamodb-lambda-logs-in-function-api-gateway.md reports in-function API Gateway SDK calls failing with no error code or message for other checks; it does not claim this check, and this is the opposite failure mode (the call is permitted).
Traces: apigateway__dynamodb__lambda__logs.lambda-apigateway-missing-permission-negative.

Cause 4 of 4: an in-function logs:PutLogEvents call from a role that lacks logs:PutLogEvents succeeds, instead of being denied.
AWS: PutLogEvents is authorized by IAM. A role granted only logs:CreateLogGroup and logs:CreateLogStream can create the group and the stream but its PutLogEvents is refused with HTTP 403 and error code AccessDeniedException, message fixed text "User: <caller arn> is not authorized to perform: logs:PutLogEvents on resource: <log-group/log-stream arn> because no identity-based policy allows the logs:PutLogEvents action" (caller ARN and resource ARN come from the request and the caller's identity). No event lands in the stream, so GetLogEvents on it stays empty. Smithy: PutLogEvents errors are DataAlreadyAcceptedException/InvalidParameterException/InvalidSequenceTokenException/ResourceNotFoundException/ServiceUnavailableException/UnrecognizedClientException — the authorization refusal is served by the IAM layer ahead of the handler.
Emulator: the handler returns {'ok': True}; the call was accepted with no refusal, so the event is written into a stream the role may not write.
Why: logs:PutLogEvents is the canonical permission-boundary example in AWS's own documentation; an emulator that accepts it unconditionally makes every log-permission scenario (and any audit that asserts an under-permissioned role cannot write) pass vacuously, and lets data appear in log groups a client proved it could not reach.
Fix: the IAM authorization gate in front of the CloudWatch Logs PutLogEvents handler, returning the 403 AccessDeniedException refusal before any event is appended.
Traces: apigateway__dynamodb__lambda__logs.lambda-logs-missing-putlogevents-permission-negative.
