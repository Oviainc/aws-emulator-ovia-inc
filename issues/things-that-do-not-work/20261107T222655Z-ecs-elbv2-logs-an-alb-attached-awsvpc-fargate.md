# ecs__elbv2__logs: an ALB-attached awsvpc Fargate service never converges to a healthy registered target serving HTTP 200, so the UpdateService network-mode rejection (InvalidParameterException "Task definition does not support launch_type FARGATE.") is never reached

> _Note: this issue was identified against the code base at commit `f1f9f5b66979f27b8680cd8e6119d18c6179a071`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
UpdateService

## Description
Cause 1 of 1: an ALB-attached awsvpc Fargate service never reaches the state AWS guarantees before an update can be attempted — one RUNNING task with an awsvpc private IP, that IP healthy in the target group, and HTTP 200 served through the load balancer — so the whole negative contract behind it (UpdateService refusing a network-mode change, the service keeping its old revision and keeping serving, and the positive control update rolling onto a repaired awsvpc revision) is ungradeable.

AWS: Smithy (ecs) — CreateService/UpdateService on a Fargate service with loadBalancers=[{targetGroupArn,containerName,containerPort}] registers each task's awsvpc ENI private IP into the target group; DescribeTasks exposes that IP under the task's attachments, and Smithy (elasticloadbalancingv2) DescribeTargetHealth must then report that IP with TargetHealth.State="healthy" (TargetHealthStateEnum; "If the target state is healthy, a reason code is not provided"), after which the ALB listener answers GET / with 200 from that task. On top of that converged state AWS enforces two refusals this check measures: RegisterTaskDefinition with requiresCompatibilities=["FARGATE"] and networkMode="bridge" is refused with ClientException (Smithy: RegisterTaskDefinition errors include ClientException, httpError 400) and the message "Fargate only supports network mode ‘awsvpc’."; and UpdateService moving a live Fargate service onto an EC2/bridge revision is refused with InvalidParameterException (Smithy: UpdateService errors include InvalidParameterException, httpError 400) and the message "Task definition does not support launch_type FARGATE." — in both messages the whole string is fixed text, with no value interpolated from the request. After the refusal DescribeServices must still report the original taskDefinition ARN, the original task must still be the one RUNNING task, and the ALB must still answer 200 with the original revision's body; only a repaired awsvpc revision may roll the primary deployment to rolloutState=COMPLETED.
Emulator: the check is killed at the harness's 180 s cap with no assertion having fired, so it never got past its first convergence poll (1 RUNNING task, 600 s; task IP healthy in the target group, 600 s; HTTP 200 through the ALB, 420 s). The emulator therefore never produces a healthy registered target or a 200 through the load balancer for an awsvpc Fargate service, and the two modelled refusals and the post-refusal no-effect assertions are never exercised. Hypothesis: the same missing ECS-task-to-ELBv2-target registration/health path the suite reports across these services, which is why the check dies in the setup rather than on a wrong error code. The closest open issue, 20261105T143800Z-ecs-elbv2-logs-2-net-new-causes-an.md, does not carry this check's replay key.
Why: a client that creates an ALB-attached Fargate service and waits for services-stable / target-in-service before sending traffic never proceeds, and because the service never becomes live the emulator is also never asked to enforce the network-mode refusals — so an application that would be refused by AWS gets no signal here at all, and the "rejected update must not take effect" guarantee (unchanged taskDefinition, unchanged task, uninterrupted 200s) is unverifiable.
Fix: the ECS service's load-balancer registration (it must register each awsvpc task's ENI private IP into the configured target group) and the ELBv2 ip-type target-health evaluator that must then drive that IP to healthy, plus the ALB listener's forwarding to ip targets; once converged, UpdateService's validation must add the launch-type/network-mode compatibility refusal and RegisterTaskDefinition's validation the FARGATE/bridge refusal, with AWS's exact messages.
Traces: ecs__elbv2__logs.ecs-update-service-to-a-different-network-mode-rejected.

## Evidence
Check ecs__elbv2__logs.ecs-update-service-to-a-different-network-mode-rejected — verdict [mismatch], detail "Error: Check timed out after 180.0s".
Expected (AWS), in order:
1. After CreateService(launchType FARGATE, networkConfiguration with the task SG and two subnets, desiredCount=1, loadBalancers=[{targetGroupArn, containerName="app", containerPort=80}], healthCheckGracePeriodSeconds=120): exactly one RUNNING task with an awsvpc private IP in its attachments; DescribeTargetHealth(tg)[<task-ip>].State == "healthy"; GET http://<alb-dns>/ -> 200 whose body carries the revision-A marker.
2. RegisterTaskDefinition(requiresCompatibilities=["FARGATE"], networkMode="bridge") -> HTTP 400, code "ClientException", message "Fargate only supports network mode ‘awsvpc’." (entirely fixed text).
3. UpdateService(cluster, service, taskDefinition=<EC2/bridge revision>) -> HTTP 400, code "InvalidParameterException", message "Task definition does not support launch_type FARGATE." (entirely fixed text).
4. After that refusal: DescribeServices(...).services[0].taskDefinition still equals the original awsvpc revision ARN; the one RUNNING task is still the same taskArn; GET / still 200 with the revision-A marker.
5. UpdateService onto a repaired awsvpc revision -> the primary deployment reaches rolloutState "COMPLETED" on that revision and the ALB serves the control marker.
Actual (emulator): step 1 never completes — no RUNNING task with a healthy registered target IP and no 200 through the load balancer within the check's 600/600/420 s budgets; the run is cut off at the harness's 180 s cap and steps 2-5 are never issued, so the emulator's status/code/message for the two refusals is unobserved.
The requirement here is the pair of error codes and their fixed message text plus the 400 status; the cluster name, service name, task ARNs, target-group ARN, load-balancer DNS name, task IP and body markers are per-run values from the request and the emulator's state.

## Steps to Reproduce
In the shared VPC (two subnets): create an ALB security group open on :80 to the harness CIDRs and a task security group open on :80 from the ALB group; create a CloudWatch Logs group; create an execution role trusted by ecs-tasks.amazonaws.com with logs:CreateLogStream/logs:PutLogEvents; create an ECS cluster. RegisterTaskDefinition an awsvpc FARGATE revision (cpu 256, memory 512, container "app" on :80, awslogs to that group). Create an ip-type target group and an internet-facing ALB with a listener forwarding to it. CreateService(launchType FARGATE, desiredCount=1, that task definition, the two subnets and task SG, loadBalancers=[{targetGroupArn, containerName="app", containerPort=80}], healthCheckGracePeriodSeconds=120). Then poll: one RUNNING task with an awsvpc private IP; DescribeTargetHealth for that IP == "healthy"; GET http://<alb-dns>/ == 200 with the revision marker. Observe none of the three converge. (Then, once they do: RegisterTaskDefinition FARGATE+bridge must answer 400 ClientException "Fargate only supports network mode ‘awsvpc’.", and UpdateService onto an EC2/bridge revision must answer 400 InvalidParameterException "Task definition does not support launch_type FARGATE." while the service keeps serving the old revision.)
