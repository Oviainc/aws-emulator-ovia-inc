# s3: 2 net-new causes — a CloudFormation-declared one-entry TagFilters lifecycle rule is reported as Filter.Tag instead of Filter.And{Prefix:"",Tags:[…]}, and virtual-hosted-style addressing makes the whole SigV4 credential-scope / clock-skew refusal surface unreachable

> _Note: this issue was identified against the code base at commit `bf05938345e3744e1c8e3343a2f8d43b66feefe9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetBucketLifecycleConfiguration

## Description
TWO net-new root causes in the s3 emulator, both grounded in failing behavioral checks that the replay report did not mark ALREADY FILED or OWNED. A fixer must close BOTH before submitting.

=== Cause 1 of 2: a lifecycle rule provisioned from CloudFormation's flat one-entry TagFilters is reported as Filter.Tag, not as Filter.And with an empty Prefix ===

AWS: Smithy: com.amazonaws.s3#LifecycleRule.Filter targets LifecycleRuleFilter, whose members are Prefix, Tag, ObjectSizeGreaterThan, ObjectSizeLessThan and And (And targets LifecycleRuleAndOperator{Prefix, Tags, ObjectSizeGreaterThan, ObjectSizeLessThan}); the modeled doc on LifecycleRule.Filter states "A Filter must have exactly one of Prefix, Tag, ObjectSizeGreaterThan, ObjectSizeLessThan, or And specified". The model does not describe the CloudFormation-to-API translation, so for that part: recorded behavior only — a rule declared on an AWS::S3::Bucket LifecycleConfiguration with a FLAT one-entry TagFilters array (together with Id, Status and ExpirationInDays) is reported by GetBucketLifecycleConfiguration with Filter = {"And": {"Prefix": "", "Tags": [{"Key": <the declared tag key>, "Value": <the declared tag value>}]}} — an And whose Prefix is the EMPTY string — and NOT as Filter.Tag. Filter.Tag is the shape the same single tag takes when the configuration is written directly through PutBucketLifecycleConfiguration; the CloudFormation path normalises to And. The same read must keep the declared ID and Status ("Enabled"), report Expiration = {"Days": <ExpirationInDays>}, and carry no legacy top-level Prefix member. After DeleteBucketLifecycle the read must be refused with Code NoSuchLifecycleConfiguration and Message "The lifecycle configuration does not exist" (fixed text; no variable part).

Emulator: GetBucketLifecycleConfiguration on the bucket the stack created reports the rule's Filter as {"Tag": {"Key": <tag key>, "Value": <tag value>}} — the Tag branch instead of the And branch. The check fails in its first phase (phase 1/4 "deploy") with: "CloudFormation's flat one-entry TagFilters must surface as {'And': {'Prefix': '', 'Tags': [{'Key': 'shouldDelete', 'Value': 'true'}]}} — an And with an EMPTY Prefix — not as Filter.Tag; the API reports {'Tag': {'Key': 'shouldDelete', 'Value': 'true'}}". (shouldDelete/true are this recording's values filling the template, not part of the requirement.) Because the deploy phase fails first, the later phases of that check — the frozen ListBuckets + GetBucketLifecycleConfiguration solve trajectory, the DeleteBucketLifecycle reverse transition and the stack destroy — are never graded here.

Why: clients discriminate on exactly this branch. Real-world tooling that walks lifecycle rules written by CloudFormation/CDK tests `Filter.And.Tags` (that is the shape AWS returns for them) and falls back to `Filter.Tag` only for hand-written configurations. Against the emulator the And branch is never present, so such a predicate selects no rules at all and a user concludes the tag-filtered expiration rule was never deployed — or, in the opposite direction, writes code against the emulator's Tag-only shape that then fails to match anything on AWS.

Fix: the CloudFormation AWS::S3::Bucket provisioner's LifecycleConfiguration translation (the step that maps a template rule's TagFilters array onto a LifecycleRuleFilter) and/or the s3 crate's lifecycle-configuration state and its GetBucketLifecycleConfiguration serializer, which must preserve the And normalisation including the empty Prefix member.

Traces: s3.s3-lifecycle-tag-e2e-tag-filter-expiration-lifecycle.

=== Cause 2 of 2: virtual-hosted-style bucket addressing cannot be reached, so the SigV4 credential-scope and clock-skew refusals are never served ===

AWS: S3 serves the same operations in virtual-hosted style, where the bucket is the leading DNS label of the Host header and the URI path carries no bucket segment (Host: <bucket>.s3.<region>.amazonaws.com, request line PUT /<key>); Smithy: AmazonS3 (restXml, sigv4Name s3, endpointPrefix s3) declares endpointResolution.endpointRuleSet: true, the rule set that rewrites the Bucket input member into the endpoint authority. The refusals these checks grade are (a) a correctly-timed PUT whose Authorization credential scope names a region other than the bucket's region: HTTP 400 with an <Error> body whose Code is AuthorizationHeaderMalformed, whose <Region> element names the region expected (the bucket's own region) and whose Message is "The authorization header is malformed; the region '<signed region>' is wrong; expecting '<bucket region>'" — the sentence is fixed text, the two region names are taken from the request's credential scope and the addressed bucket's region; and (b) an x-amz-date outside S3's signing window, measured against S3's own clock as read from the Date response header, which must be refused and must write nothing. Both are reached only over a raw, hand-signed, virtual-hosted request, because botocore's own signer cannot sign a skewed date.

Emulator: the endpoint the emulator announces is a bare IP literal, so the virtual-hosted authority <bucket>.<announced authority> is not the endpoint the run is reached on and the request never leaves the harness: all three checks die with simparity.egress.EgressRefused — "egress refused: '<bucket>.<announced authority>' is not the endpoint under test (<announced authority>); an emulator run may reach only the emulator. If the host came from a URL the emulator returned, the emulator announces an address other than the endpoint it is reached on" (egress.py line 281 _hook -> line 238 refuse). The bucket name and address in that message are per-run values. Consequence: not one of the three refusals above is ever exercised — the emulator is never asked for AuthorizationHeaderMalformed or for a skew refusal, so this entire refusal surface is unverified.

Related open issue: 20261029T083133Z-s3-virtual-hosted-style-bucket-addressing-is-unreachable.md names the same component (the announced endpoint authority is an IP literal, so the Host-label bucket resolution path is never served), but it carries only s3.sdk-virtual-hosted-requests-round-trip-an-object-and-its-deletion in its trace ids, and the suite does not bind these three checks to it. Closing that issue against its one check leaves these three still failing, so the cause is filed here with its own replay keys.

Why: a client relying on AWS's behavior gets no refusal where AWS refuses. An application, SDK or proxy that addresses S3 the AWS-default way (virtual-hosted) cannot be exercised at all, and the two authorization guards that protect against replayed/misscoped signatures — wrong-region credential scope and out-of-window dates — are silently untested, so a regression in either is invisible and a mis-scoped or stale-dated request that AWS rejects with 400 may be accepted by the emulator.

Fix: the s3 crate's listener/front door and its endpoint announcement — announce an authority for which <bucket>.<authority> reaches the same listener, and resolve the bucket from the leading Host label when the request path carries no bucket segment — and then the SigV4 verifier in the request-admission path, which must compare the credential scope's region against the addressed bucket's region and the x-amz-date against the server clock window, and emit the AuthorizationHeaderMalformed / skew refusals with the wording above. The requirement is not a particular host name or port; those are per-environment values.

Traces: s3.sigv4skew-cross-region-credential-scope-rejected, s3.sigv4skew-future-dated-put-outside-window-rejected, s3.sigv4skew-window-enforced-in-derived-second-region-rejected.
