# rds serves emulator-authored values on success paths: engine-default parameter rows and the global-cluster resource id

> _Note: this issue was identified against the code base at commit `1f4cf209e4b6def02b8dc25f0332c16acb014f54`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEngineDefaultParameters

## Description
This bundle carries 2 net-new causes. Both are 200 success paths whose payload is filled from data the emulator authored itself rather than from AWS's reference data or AWS's identifier minting: an engine-family default-parameter catalog that is paraphrased and partly a different parameter set, and a global-cluster resource id minted as a counter instead of in AWS's resource-id shape.

Cause 1 of 2: DescribeEngineDefaultParameters serves a paraphrased, partly-different default parameter catalog for the requested family.
AWS: Smithy DescribeEngineDefaultParameters takes the required DBParameterGroupFamily, returns output member EngineDefaults, declares no errors, and is paginated {inputToken Marker, outputToken EngineDefaults.Marker, items EngineDefaults.Parameters, pageSize MaxRecords}. For a family AWS serves that engine family's REAL default parameter set, in ParameterName order, and each Parameter row carries that parameter's own reference Description verbatim together with its own ApplyType, DataType, AllowedValues, IsModifiable, MinimumEngineVersion and (where defaulted) ParameterValue/Source. The Descriptions are AWS's engine-reference strings — e.g. 'Intended for use with master-to-master replication, and can be used to control the operation of AUTO_INCREMENT columns', 'Determines the starting point for the AUTO_INCREMENT column value', 'Sets the autocommit mode', 'When this variable has a value of 1 (the default), the server automatically grants the EXECUTE and ALTER ROUTINE privileges to the creator of a stored routine, if the user cannot already execute and alter or drop the routine.' — reproduced exactly, including their punctuation. The requirement is the family's catalog, not any single run's values.
Emulator: status 200, but the page's contents are the emulator's own catalog. Rows [2] through [10] and [14] through [19] carry re-written Descriptions (paraphrased and re-punctuated with an added trailing period: 'Controls the increment between successive AUTO_INCREMENT values.' for the AUTO_INCREMENT row, 'Sets the autocommit mode.' for autocommit, 'Whether the server automatically grants the EXECUTE and ALTER ROUTINE privileges to the creator of a stored routine.' for automatic_sp_privileges, 'Whether ALTER TABLE implicitly upgrades temporal columns found to be in pre-5.6.4 format.' for the temporal-column row), and from row [8] onward the catalog is a different parameter set in a different order: ParameterName diverges at rows [8], [11], [12], [13], [14] and [15], dragging AllowedValues, DataType, ApplyType, IsModifiable, MinimumEngineVersion, ParameterValue and Source with it.
Why: this operation is the authoritative discovery call a client makes before creating or modifying a parameter group. A caller reads parameters that do not exist for the family and never sees ones that do, reads ApplyType/IsModifiable wrongly (so it believes a static parameter needs no reboot, or that a modifiable one cannot be changed) and issues ModifyDBParameterGroup calls AWS would reject. The paraphrased Descriptions are what a console, a doc generator or a configuration-drift check surfaces to a human, so the same family reads differently against the emulator than against AWS.
Fix: the per-DBParameterGroupFamily engine-default reference data behind the DescribeEngineDefaultParameters handler in the rds crate, plus its ParameterName ordering — rows, their attributes and their descriptions must come from the family's real default set verbatim.
Note: the resolved issue 20261106T224204Z-rds-createdbcluster-envelope-and-the-engine-default-parameter.md previously carried this step; rows [0]-[1] and EngineDefaults.Marker now match, but the residual divergence above remains and the replay reports this cluster unowned.
Traces: rds-db-parameter-group-lifecycle-and-engine-defaults#task#10.

Cause 2 of 2: CreateDBCluster reports GlobalClusterResourceId as a zero-padded DB-cluster-style counter, which is not AWS's global-cluster resource-id shape.
AWS: a DB cluster created with GlobalClusterIdentifier comes back with DBCluster.GlobalClusterResourceId — the immutable resource id of the global cluster it joined. Recorded behavior only for the member itself (the on-disk model's DBCluster shape declares no GlobalClusterResourceId; the recording shows AWS always returning one for a global-cluster member). The recording asserts the value's SHAPE, not its literal: AWS mints a global-cluster resource id as 'cluster-' followed by a random fixed-length alphanumeric token, unique per global cluster. Status 200.
Emulator: status 200 but the member is 'cluster-00000000000000000000000001' — a zero-padded sequential counter in the emulator's DB-cluster id style, which fails the recorded resource-id shape and repeats identically across runs.
Why: a client that reads GlobalClusterResourceId from the create response and uses it as a global-cluster handle (correlating a regional member with its global parent, or looking up the global cluster's automated backups) passes RDS a token it would never have minted, so the lookup fails against AWS while 'working' against the emulator; and because the value is a counter, two global clusters in one run are indistinguishable to any consumer that treats the id as opaque-but-unique.
Fix: the global-cluster resource-id minting in the rds crate (the shared id generator used by the GlobalCluster record and projected into the CreateDBCluster DBCluster envelope) — mint in AWS's resource-id shape, not from the DB-cluster counter.
Also diverging at this same step, and NOT part of this issue: DBCluster.Port is 46133 instead of the aurora-mysql default 3306; that cause is owned by open issue 20261108T233943Z-rds-db-cluster-envelopes-report-the-emulator-s-random.md (its cause 3 of 6). Open issue 20261029T214632Z-rds-omits-vpc-subnet-and-availability-zone-attributes.md (cause 9 of 9) owns the identical minting defect on CreateGlobalCluster's own GlobalCluster.GlobalClusterResourceId; neither carries this CreateDBCluster cluster, which the replay reports unowned.
Traces: rds-global-cluster-delete-with-member#task#7.
