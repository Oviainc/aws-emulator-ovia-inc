# CreateExport skips S3 delivery-policy validation, export ARNs carry the caller's region, and the tag-count/authz error messages are built to the wrong rule

> _Note: this issue was identified against the code base at commit `048778663a26e363156c6db724999c4fb229af36`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateExport

## Description
Behavioral replay of simparity-behavioral-aws-v1 against the emulator booted from mainline (14/21 checks passed, bootstrap_signal=false, so the service is serving) leaves four distinct defects on the export control plane: a creation-time validation AWS performs is not performed at all, the ARN the service mints is stamped with the wrong region, and two error messages whose construction rule is known are built to a different rule. 4 causes.

Cause 1 of 4: CreateExport does not validate the destination S3 bucket's delivery-grant policy at creation time.
AWS: recorded behavior only for the message; the status and error code come from the recorded response — CreateExport pointed at an S3 bucket that carries no bucket policy granting bcm-data-exports.amazonaws.com s3:PutObject is rejected SYNCHRONOUSLY with HTTP 400 / ValidationException and the message 'S3 bucket permission validation failed', and no export is created. Smithy: CreateExport errors are AccessDeniedException(403), InternalServerException(500), ServiceQuotaExceededException(402), ThrottlingException(429) plus the service-common ValidationException (@httpError 400, Message required); the model does not describe the bucket-policy precondition, so the rejection itself is from the recording. Granting the identical policy on the same bucket afterwards makes the identical call succeed, i.e. this is a precondition evaluated per call, not a one-time bucket state.
Emulator: HTTP 200 with an ExportArn — the export is created against the unpolicied bucket (replay: {'ExportArn': 'arn:aws:bcm-data-exports:...:export/<name>', 'ResponseMetadata': {'HTTPStatusCode': 200 ...}}).
Why: this is the overly-permissive direction. A client whose bucket policy is missing or mis-scoped gets a success and an ARN, so its error branch for a mis-configured destination never runs; it believes it has a working export that in reality would never deliver data. Infrastructure tooling that depends on create failing (so it can fix the policy and retry) silently proceeds.
Fix: CreateExport's handler/validation — evaluate the destination bucket's policy for an s3:PutObject grant to the service principal before persisting, and raise the 400 ValidationException instead of creating the export.
Traces: bcm-data-exports.export-delivery-fails-without-bucket-policy-positive-control-succeeds.

Cause 2 of 4: export ARNs are minted with the caller's configured region instead of this service's pinned region.
AWS: recorded behavior only — bcm-data-exports is a region-pinned control plane: every export ARN it returns carries us-east-1 regardless of the region the client is configured for. The recorded AccessDeniedException names the resource 'arn:aws:bcm-data-exports:us-east-1:<account>:export/*' for a client configured in another region, and the checks' S3 bucket policies condition aws:SourceArn on 'arn:aws:bcm-data-exports:us-east-1:<account>:export/*' for that reason. Smithy: Arn is @pattern ^arn:aws[-a-z0-9]*:(bcm-data-exports):[-a-z0-9]*:[0-9]{12}:[-a-zA-Z0-9/:_]+$ — the region segment is unconstrained by the model, so the pinning is recorded behavior.
Emulator: the ARN carries the client's region — CreateExport returned 'arn:aws:bcm-data-exports:us-west-2:000000000000:export/<name>' and the AccessDeniedException named 'arn:aws:bcm-data-exports:us-west-2:...' for a client configured in us-west-2.
Why: the ARN is the export's identity and is what IAM and S3 bucket policies are written against. A policy or SCP whose Resource/aws:SourceArn condition is scoped to the us-east-1 ARN AWS actually emits will not match the emulator's ARN, so permission checks and delivery grants evaluate differently from production, and any stored/compared ARN is region-wrong.
Fix: the region used when composing export ARNs (the service's effective-region helper and whatever CreateExport/GetExport/error serialization use to build the ARN) — pin it to this service's region rather than the request's.
Traces: bcm-data-exports.create-export-without-iam-permission-rejected (the ARN also appears in the 200 response of bcm-data-exports.export-delivery-fails-without-bucket-policy-positive-control-succeeds).

Cause 3 of 4: the AccessDeniedException message is built to a different rule than AWS's standard authorization-failure sentence.
AWS: the standard AWS authz denial message is built from the request and the calling identity with the rule 'User: <principal ARN> is not authorized to perform: <service>:<Action> on resource: <resource ARN> because no identity-based policy allows the <service>:<Action> action'. For CreateExport the resource the decision is taken against is the wildcard 'export/*' (the export does not exist yet, so there is no specific resource to evaluate). Recorded example: "User: arn:aws:iam::000000000000:user/<user> is not authorized to perform: bcm-data-exports:CreateExport on resource: arn:aws:bcm-data-exports:us-east-1:000000000000:export/* because no identity-based policy allows the bcm-data-exports:CreateExport action". Smithy: AccessDeniedException is modeled on CreateExport with @httpError 403. The rule — not the recorded sentence — is the requirement; the status (403) and code (AccessDeniedException) already match.
Emulator: same status and code, but the sentence names the not-yet-existent specific export ('…:export/<requested name>') instead of 'export/*', and says 'because no policy allows the …' instead of 'because no identity-based policy allows the …'.
Why: clients, test suites and policy-debugging tooling parse this sentence to tell an identity-based denial from a resource-policy/SCP denial and to learn which resource ARN a policy must name. Naming a resource AWS never evaluates, and dropping 'identity-based', makes that diagnosis wrong — a user following the emulator's message would write a policy scoped to one export name rather than the wildcard.
Fix: the authorization-denial message renderer for this service — emit the identity-based wording and, for create-style actions, the wildcard resource ARN (it must also pick up the pinned region from cause 2).
Traces: bcm-data-exports.create-export-without-iam-permission-rejected.

Cause 4 of 4: TagResource rejects an over-limit tag batch but does not render the standard constraint-violation message.
AWS: Smithy TagResource input ResourceTags targets ResourceTagList with @length(min 0, max 200) and errors include the service-common ValidationException (@httpError 400, Message required). AWS builds the message from the request, naming the member path and the constraint it failed: "1 validation error detected: Value '[ResourceTag(key=k0, value=v0), …]' at 'resourceTags' failed to satisfy constraint: Member must have length less than or equal to 200". That rule (member path + rendered constraint + the submitted value) is the requirement, not the recorded sentence; note the same message family is already called out as a requirement in open issue 20261022T061241Z-bcm-data-exports-export-lifecycle-errors-validation-and-tag-state-diverge.md (its cause 7, pattern constraints on export.name) — the length-constraint rendering on a list member is a separate renderer path and that issue's keys do not cover it.
Emulator: the call IS rejected with ValidationException (the check's code assertion passes), but the Message is not the standard rendering above — the replay's assertion failed on the message comparison. The emulator's exact string was elided by the report's detail truncation; what is established is that the code matches and the message is built to a different rule.
Why: callers and conformance suites discriminate validation failures only by this message (status 400 and __type ValidationException are shared by every validation failure in the service), so a non-standard rendering means a client cannot tell which member or which limit it violated.
Fix: the validation-message renderer for @length constraints on list members, on the TagResource validation path; keep the 400 ValidationException.
Traces: bcm-data-exports.tag-resource-exceeds-max-tag-count-rejected.
