# ACM PCA DescribeCertificateAuthority reports CertificateAuthority.Serial as unseparated minted hex instead of the CA certificate's serial number in AWS's rendering

> _Note: this issue was identified against the code base at commit `fb003e0a3fdd2a31392ea928ed9540deb9fe4c34`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeCertificateAuthority

## Description
ONE net-new cause on the acm-pca CA-description surface, reached over the wire: DescribeCertificateAuthority answers HTTP 200 with a CertificateAuthority whose `Serial` member is not in the form AWS's recorded value has. The step is not marked OWNED or ALREADY FILED in this replay (the other five acm-pca divergences in the same replay are owned by 20261029T190010Z-acm-pca-resource-policy-wire-contract-diverges-a.md and 20261108T124234Z-acm-pca-not-found-refusals-diverge-getcertificate-classifies.md; this one is not). The nearest open issue, 20261108T062219Z-acm-pca-representation-and-refusal-gaps-audit-report.md, has a cause 1 about the SAME serial-rendering mistake in a DIFFERENT place -- the JSON audit report's row `serial` -- and is grounded only in behavioral check ids; it does not name DescribeCertificateAuthority, does not touch the CertificateAuthority wire projection, and does not carry this replay key, so this cause must be closed and this step re-replayed on its own.

Cause 1 of 1: the `Serial` reported for a private CA is a 32-character run of unseparated lowercase hex that the emulator MINTS at creation time, rather than the CA certificate's serial number rendered the way AWS renders ACM PCA serial numbers.
AWS: Smithy (services/service-com-amazonaws-acmpca-acmprivateca/smithy-model/com-amazonaws-acmpca-acmprivateca.json) models DescribeCertificateAuthority {CertificateAuthorityArn @required (Arn, @length 5..200)} -> {CertificateAuthority}, errors InvalidArnException and ResourceNotFoundException (both httpError 400), and CertificateAuthority.Serial as plain `com.amazonaws.acmpca#String` with NO length, pattern or format trait, documented only as 'Serial number of your private CA.' The model therefore constrains nothing about the value, so the rendering is recorded behavior only. What the recording shows: the fixture carries the recorded AWS value shape-classified and masked (`<shaped-not-asserted>`, because the serial itself is a per-run value), and the emulator's string is NOT accepted into that class -- i.e. the emulator's value is outside the form the recorded AWS value had, independently of which digits a given run produces. The rendering AWS uses for an ACM PCA serial number is colon-delimited lowercase hex octet pairs (`0a:1b:2c:3d:...`): that is the form `openssl x509 -text` / `openssl x509 -serial` print, it is the listing RevokeCertificateRequest$CertificateSerial's own docs have the caller copy the serial out of ('must be in hexadecimal format'), and the project's own behavioral recordings establish exactly that rendering for the serial ACM PCA reports in the audit report (see cause 1 of 20261108T062219Z-acm-pca-representation-and-refusal-gaps-audit-report.md, where AWS emits 'c8:5c:fc:5c:68:f9:0d:55:ac:9d:39:09:a4:9a:ed:4f' for a certificate the emulator reports as 'c85cfc5c68f90d55ac9d3909a49aed4f'). Hypothesis: the shape class the masked value belongs to is that colon-delimited octet-pair rendering, which a bare run of 32 hex digits cannot match; and since the field names the serial number OF the private CA, the number it denotes is the serial of the X.509 certificate the CA was activated with, which is why AWS has a serial to report only once the CA holds one.
Emulator: returns `CertificateAuthority.Serial` as 32 unseparated lowercase hex digits (the replayed step shows '0fdbfb983cc48fcadebf03cf3283baac'; the digits are per-run, the unseparated 16-byte hex FORM is not). Two things produce that: `state::mint_serial` (services/service-com-amazonaws-acmpca-acmprivateca/src/state.rs) mints the CA record's `serial` as `hex::encode(&mint_digest(seed)[..16])` -- 16 bytes of digest, no separators -- and `CertificateAuthorityRecord::to_wire` copies that stored field straight onto the wire (`serial: Some(self.serial.clone())`). Because the value is minted when the CA is created and never reconciled with the certificate imported later, it also does not denote the serial of the certificate the CA was activated with, even though the record can read that serial (`CertificateAuthorityRecord::own_certificate_serial`, which decodes the stored CA certificate PEM). The same field is reported in the same form before and after activation.
Why: a serial number is the only identifier that joins a CA, the certificate it holds, the rows of its audit report, the entries of its CRL and the CertificateSerial a caller passes to RevokeCertificate. A client that takes `CertificateAuthority.Serial` from DescribeCertificateAuthority and compares it with the serial it read out of the CA certificate PEM (via X.509 tooling, which yields the colon-delimited form) finds no match and concludes the CA is holding a different certificate than the one it imported; a client that logs, displays or re-submits the value gets a string production never emits. Because the emulator's value is additionally unrelated to the activated certificate, correlation fails on the VALUE as well as on the rendering, and nothing in the 200 response tells the caller either is wrong.
Fix: the CertificateAuthority wire projection and the CA record field behind it in the acm-pca service crate -- derive the reported serial from the CA certificate the CA holds rather than from a mint at creation time, and render it the way AWS renders an ACM PCA serial number (lowercase hex octet pairs separated by colons), so the value a caller reads back denotes the same number its X.509 tooling reads off the certificate. Hypothesis (not asserted by this step): a CA that holds no certificate yet should report no Serial at all rather than a minted one.
Traces: acm-pca-root-ca-activates-and-issues-end-entity-certificate#task#7; services/service-com-amazonaws-acmpca-acmprivateca/src/state.rs (CertificateAuthorityRecord::to_wire, mint_serial, own_certificate_serial), services/service-com-amazonaws-acmpca-acmprivateca/src/ops/describe_certificate_authority.rs.

## Steps to Reproduce
1. acmpca.create_certificate_authority(CertificateAuthorityConfiguration={'KeyAlgorithm':'RSA_2048','SigningAlgorithm':'SHA256WITHRSA','Subject':{'CommonName': <any name>}}, CertificateAuthorityType='ROOT'); keep CertificateAuthorityArn.
2. Poll describe_certificate_authority until Status='PENDING_CERTIFICATE'. Note CertificateAuthority.Serial already carries a value at this point.
3. csr = get_certificate_authority_csr(CertificateAuthorityArn=<ca>)['Csr'].
4. cert_arn = issue_certificate(CertificateAuthorityArn=<ca>, Csr=csr, SigningAlgorithm='SHA256WITHRSA', TemplateArn='arn:aws:acm-pca:::template/RootCACertificate/V1', Validity={'Value':10,'Type':'YEARS'}); pem = get_certificate(CertificateAuthorityArn=<ca>, CertificateArn=cert_arn)['Certificate']; import_certificate_authority_certificate(CertificateAuthorityArn=<ca>, Certificate=pem).
5. Poll describe_certificate_authority until Status='ACTIVE', then read CertificateAuthority.Serial.
   Expected: a serial number in AWS's rendering -- lowercase hex octet pairs separated by colons (e.g. '0f:db:fb:98:3c:c4:8f:ca:de:bf:03:cf:32:83:ba:ac'), denoting the SAME number as the serial of the certificate get_certificate_authority_certificate(CertificateAuthorityArn=<ca>)['Certificate'] returns (read it with X.509 tooling: cryptography's cert.serial_number, or `openssl x509 -noout -serial`).
   Actual: 32 unseparated lowercase hex characters (e.g. '0fdbfb983cc48fcadebf03cf3283baac'), and the number it denotes is NOT the serial of that certificate -- it was minted when the CA was created.
