=== Cause 1 of 4: RejectDomainNameAccessAssociation resolves the pair and then answers 501 NotImplemented instead of the modeled refusal AWS gives for a same-account association ===
AWS: Smithy (com.amazonaws.apigateway#RejectDomainNameAccessAssociation): POST /rejectdomainnameaccessassociations, required httpQuery members domainNameAccessAssociationArn and domainNameArn, success status 202 with an empty body (output targets smithy.api#Unit); modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). The operation documentation states it rejects an access association whose source is in ANOTHER AWS account, and that an association whose source is in your OWN account must be removed with DeleteDomainNameAccessAssociation instead. Recorded behavior for that same-account case: the call is refused BadRequestException with the message "Cannot reject the domain name access association when the private custom domain and domain name access association are in the same account." — this string is entirely FIXED text for this error class; no part of it is taken from the request or from state.
Emulator: the handler reads and resolves both ARNs (so malformed and unknown pairs do answer 400/404 correctly), and then, for a pair that names records it holds, returns the scaffold refusal — Error.Code "NotImplemented", Error.Message "operation RejectDomainNameAccessAssociation is scaffolded but not implemented in this emulator". The check asserts ('BadRequestException', 'Cannot reject the domain name access association when the private custom domain and domain name access association are in the same account.') and gets ('NotImplemented', 'operation RejectDomainNameAccessAssociation is scaffolded but not implemented in this emulator'). The same-account distinction is never made: the only answer a resolvable pair can get is 501.
Why: a client cannot tell "you used the wrong operation for a same-account association" (a permanent, actionable 400) from "the service is broken" (a 501 that an SDK retry policy and most IaC tools treat as a transient server fault). Code that reconciles private custom-domain access associations retries forever instead of switching to DeleteDomainNameAccessAssociation, and the cross-account rejection path has no success behavior at all.
Fix: the RejectDomainNameAccessAssociation handler and the access-association state it reads — after the two ARNs resolve, the handler must compare the association's access-association-source account with the private custom domain's owning account and refuse the same-account case with BadRequestException carrying exactly AWS's fixed text above, and must implement the cross-account success path (202, empty body, the association removed from the pending set) rather than falling through to the scaffold 501. Related open issue that does NOT carry this replay key and does not describe this cause: 20261027T111730Z-apigateway-the-domain-name-access-association-surface-diverges.md (create/duplicate causes) and 20261026T090242Z-apigateway-every-private-custom-domain-domain-name-access.md (the EC2 endpoint state machine). File citations are under Traces.
Traces: apigateway.domain-access-association-concurrent-reject-delete. Code: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/reject_domain_name_access_association.rs (lines 243-251: the comment concedes the success path is the scaffold's 501, and `Err(crate::scaffolded::Scaffolded::not_implemented("RejectDomainNameAccessAssociation"))` is returned for every pair that resolves).

=== Cause 2 of 4: a deployed stage whose method uses a CUSTOM REQUEST Lambda authorizer answers HTTP 500 {"message":"Internal server error"} on every request, so no authorize decision is ever produced and FlushStageAuthorizersCache cannot be exercised ===
AWS: Smithy (com.amazonaws.apigateway#CreateAuthorizer) accepts type REQUEST with authorizerUri, identitySource and authorizerResultTtlInSeconds; PutMethod accepts authorizationType="CUSTOM" with authorizerId. Smithy (com.amazonaws.apigateway#FlushStageAuthorizersCache): DELETE /restapis/{restApiId}/stages/{stageName}/cache/authorizers, success 202, modeled errors BadRequestException(400), ConflictException(409), LimitExceededException(429), NotFoundException(404), TooManyRequestsException(429), UnauthorizedException(401). Recorded behavior for the data plane (not spelled by the control-plane model): a request carrying the configured identity source invokes the authorizer Lambda, and an Allow policy makes the gateway run the method's integration and return the integration's own status and body — here HTTP 200 from a MOCK integration. Within authorizerResultTtlInSeconds (300 s) a repeat request with the SAME identity-source value reuses the cached decision and does NOT re-invoke the Lambda; a different identity-source value invokes it once; after FlushStageAuthorizersCache the next request with the original identity re-invokes it exactly once. A 500 is reserved for an authorizer that errors, times out or returns a malformed policy, and carries the body {"message":"Internal server error"}.
Emulator: every GET on the deployed stage URL with the Authorization header set answers HTTP 500 with body {"message":"Internal server error"} — the check polls for a 200 for 180 s and the last observed value is (500, b'{"message":"Internal server error"}'). The authorizer Lambda is never seen to run (its per-invocation record never reaches the SQS queue it writes to), so the authorize decision is never obtained, the TTL caching behaviour is never reached, and FlushStageAuthorizersCache is never exercised.
Why: the whole CUSTOM-authorizer data plane is unusable for REQUEST authorizers: a client gets a 500 where AWS returns the integration's 200, cannot distinguish "my authorizer code failed" from "the gateway cannot call authorizers at all", and every caching/invalidation behaviour that depends on an authorize decision (TTL reuse, per-identity keying, cache flush) is silently unverifiable.
Why it is distinct from the open TOKEN-authorizer issue: 20261027T030000Z-apigateway-a-token-lambda-authorizer-allow-decision-is-never-obtained.md owns apigateway.e2e-custom-authorizer-protected-method-flow (a TOKEN authorizer); it does not carry this check id and does not cover the REQUEST authorizer type, its identitySource=method.request.header.Authorization keying, or FlushStageAuthorizersCache.
Fix: the API Gateway data-plane invoke path's authorizer stage and its authorizer-result cache — the gateway must invoke the configured REQUEST authorizer's Lambda through its authorizerUri, interpret the returned IAM policy document, run the method integration on Allow (returning the integration's status and body, not 500), key the cache by the identitySource value for authorizerResultTtlInSeconds, and have FlushStageAuthorizersCache drop those entries for the named stage. The 500 envelope must be produced only when the authorizer genuinely errors.
Traces: apigateway.e2e-authorizer-cache-invalidation-flow (AssertionError: condition never satisfied within 180s, last value=(500, b'{"message":"Internal server error"}')).
