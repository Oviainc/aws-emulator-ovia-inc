# resource-groups resolves no real resources: SearchResources and ListGroupResources answer empty because they only search this service's own group store, and a CLOUDFORMATION_STACK_1_0 query always reports the stack as nonexistent

> _Note: this issue was identified against the code base at commit `5b71589754f95f05f88c1a0ee9ccd691bbc5f701`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchResources

## Description
This issue bundles 2 causes: the two operations that are supposed to RESOLVE a resource query both report only resource-groups' own in-crate records, so no resource of any other service is ever discoverable. Both must be closed before this issue is submitted. All six grounding checks surfaced as 'Check timed out after 60.0s' because each one polls (up to 240s, 15s interval) for a resource to appear; the emulator answers each poll immediately with HTTP 200 and an EMPTY list, so the predicate can never become true and the harness timeout is reached. The divergence is the empty 200, not slowness — the handlers cannot match a resource they do not store.

Cause 1 of 2: SearchResources never matches a resource of another service, and a stack query always reports CLOUDFORMATION_STACK_NOT_EXISTING.
AWS: Smithy: SearchResources (POST /resources/search, success 200), ResourceQuery required, output ResourceIdentifiers (ResourceArn + ResourceType) and QueryErrors. Documented as "Returns a list of Amazon Web Services resource identifiers that matches the specified query", with required permissions resource-groups:SearchResources, tag:GetResources, cloudformation:DescribeStacks and cloudformation:ListStackResources — i.e. the query is run over the account's TAGGED RESOURCES and over CloudFormation stacks, not over resource groups. So a TAG_FILTERS_1_0 query {ResourceTypeFilters:['AWS::SQS::Queue'], TagFilters:[{Key:K, Values:[V]}]} returns the ARN of an SQS queue created with tag K=V, with ResourceType 'AWS::SQS::Queue'; a ResourceTypeFilters-scoped query excludes a same-tagged resource of another type (an SNS topic tagged identically is returned by ['AWS::SNS::Topic'] and NOT by ['AWS::SQS::Queue']); and a tag value nothing carries returns an empty ResourceIdentifiers list with no error.
Emulator: HTTP 200 with ResourceIdentifiers: [] for every such query. services/service-com-amazonaws-resourcegroups-ardi/src/ops/search_resources.rs:357-387 (matching) walks ONLY store.groups_in(region) — the group ARNs stored by this crate plus the ARNs recorded as STATIC memberships of those groups — and its own doc comment states "Nothing else is searchable: this service stores no resources of its own beyond those". It additionally decides at line 366 that a query with ANY TagFilter can match no membership at all, since membership tags are not recorded. There is no read of the emulator's cross-service tag index, so an SQS queue or SNS topic tagged through its own service is invisible. For a CLOUDFORMATION_STACK_1_0 query, lines 223-233 unconditionally return an empty result plus QueryErrors [{ErrorCode: 'CLOUDFORMATION_STACK_NOT_EXISTING', Message: 'Stack with id <id> does not exist'}] even when the emulator's CloudFormation service does hold that stack.
Why: SearchResources is the discovery primitive of this service. A client that tags resources and then finds them by query (inventory tooling, cost/ops dashboards, anything built on tag:GetResources semantics) gets a permanently empty answer with no error to signal the gap, and a negative assertion ('no match returns empty') passes for the wrong reason while the positive control never does — so the emulator cannot be distinguished from one that never filters at all.
Fix: the SearchResources handler's query evaluation (ops/search_resources.rs matching/tag_filters path) must resolve the query against the emulator's cross-service resource/tag inventory (the same source the resource-groups-tagging-api GetResources index uses) and derive ResourceType from the matched resource, and a CLOUDFORMATION_STACK_1_0 query must resolve the named stack's resources from the CloudFormation service state, reporting CLOUDFORMATION_STACK_NOT_EXISTING only when no such stack exists.
Traces: resource-groups.search-resources-tag-filter-matches-tagged-resource, resource-groups.search-resources-no-match-returns-empty, resource-groups.search-resources-type-filter-restricts-results.

Cause 2 of 2: ListGroupResources reports only static memberships, so a query-based group's membership never resolves, never re-evaluates after UpdateGroupQuery, and never reflects a CloudFormation stack.
AWS: Smithy: ListGroupResources (POST /list-group-resources) outputs Resources (Identifier.ResourceArn + Identifier.ResourceType), ResourceIdentifiers and QueryErrors; documented as returning the ARNs of the resources that are MEMBERS of the group, with required permissions tag:GetResources, cloudformation:DescribeStacks and cloudformation:ListStackResources — membership of a query-based group is derived by running the group's stored ResourceQuery. Recorded behavior: a TAG_FILTERS_1_0 group whose query selects an SQS queue eventually lists that queue with Identifier.ResourceType 'AWS::SQS::Queue'; after UpdateGroupQuery replaces the query, membership re-evaluates to admit the newly matching resource AND drop the one that no longer matches (replace, not union), while GetGroupQuery echoes the new query synchronously; a CLOUDFORMATION_STACK_1_0 group lists the stack's resources (e.g. the stack's AWS::SNS::Topic physical id), and once the group is deleted ListGroupResources answers 404 NotFoundException with the fixed Message 'The specified group does not exist'.
Emulator: HTTP 200 with Resources: [] for every query-based group, forever. ops/list_group_resources.rs:283-287 builds the page from group.members only — the list written exclusively by GroupResources (static membership) — and line 320-322 hardcodes query_errors: None with the comment "listing recorded memberships runs none". The stored ResourceQuery is write-only state: nothing reads it for membership, so UpdateGroupQuery changes what GetGroupQuery echoes but cannot change what ListGroupResources returns, and a CLOUDFORMATION_STACK_1_0 group lists nothing even though the emulator's CloudFormation service created the stack and DescribeStackResources reports its resources.
Why: a query-based group is the normal way this service is used; a client sees a group that exists, echoes the right query, and is permanently empty, with no QueryErrors to explain it. Membership-driven automation (grouped dashboards, bulk tagging, drift checks) silently operates on an empty set.
Fix: the ListGroupResources handler's membership resolution — for a group that stores a ResourceQuery, evaluate that query (sharing the evaluator with SearchResources from cause 1) instead of reading only GroupRecord::members, and report QueryErrors for a stack identifier it cannot resolve. NOTE: open issue 20261024T072908Z-resource-groups-listgroupresources-wrong-behavior describes this same handler gap from the static pass; these three behavioral checks are its behavioral grounding, and if it is fixed first this cause closes with it — verify by re-replaying the check ids below.
Traces: resource-groups.list-group-resources-reflects-tag-query-membership, resource-groups.update-group-query-changes-membership, resource-groups.cloudformation-stack-query-group-membership.

## Evidence
Replay of simparity-behavioral-aws-v1, resource-groups 9/20 passed; all six checks verdict=mismatch with 'Error: Check timed out after 60.0s'. Each check creates a real resource in a bootstrapped sibling service, then polls resource-groups for it:
- search-resources-tag-filter-matches-tagged-resource: creates an SQS queue with tag sim2real-rg-marker=<qname>, polls SearchResources with TAG_FILTERS_1_0 {ResourceTypeFilters:['AWS::SQS::Queue'], TagFilters:[{Key:'sim2real-rg-marker', Values:[<qname>]}]}; the queue ARN never appears. Expected: the ARN with ResourceType 'AWS::SQS::Queue'.
- search-resources-no-match-returns-empty: the positive-control leg (search for the tag value the queue actually carries) never returns the ARN, so the empty-result leg is never reached.
- search-resources-type-filter-restricts-results: the positive control (an SNS topic discoverable by its own ['AWS::SNS::Topic'] filter) never returns the topic ARN.
- list-group-resources-reflects-tag-query-membership: group with query ResourceTypeFilters ['AWS::SQS::Queue'] + TagFilters on the queue's own tag; ListGroupResources never lists the queue (expected Identifier.ResourceType 'AWS::SQS::Queue').
- update-group-query-changes-membership: the initial queue never appears as a member before the UpdateGroupQuery leg, so the replace-not-union assertion is never reached.
- cloudformation-stack-query-group-membership: a real CloudFormation stack is created and waited to CREATE_COMPLETE, its AWS::SNS::Topic PhysicalResourceId read, and a CLOUDFORMATION_STACK_1_0 group created for StackIdentifier=<stack id>; the topic ARN never appears in ListGroupResources. The check's final leg (ListGroupResources on the DELETED group must answer NotFoundException with Message 'The specified group does not exist') is never reached.
Source confirmation that the polls can only ever answer empty: ops/search_resources.rs:357-387 searches only store.groups_in(region) and line 366 excludes memberships from any tag-filtered query; ops/search_resources.rs:223-233 always answers a stack query with CLOUDFORMATION_STACK_NOT_EXISTING; ops/list_group_resources.rs:283-287 pages group.members only and :320-322 hardcodes query_errors: None. Queue/topic/stack names, ARNs and ids above are per-run values; the requirement is that a tagged or stack-member resource is resolvable by its query at all.

## Steps to Reproduce
1. Create an SQS queue with tag K=V and read its QueueArn. Call SearchResources with ResourceQuery={Type:'TAG_FILTERS_1_0', Query:'{"ResourceTypeFilters":["AWS::SQS::Queue"],"TagFilters":[{"Key":"K","Values":["V"]}]}'}. Expect ResourceIdentifiers to contain the queue ARN with ResourceType 'AWS::SQS::Queue'; observe 200 with [].
2. Create an SNS topic tagged with the SAME K=V. SearchResources scoped to ['AWS::SNS::Topic'] must return the topic; scoped to ['AWS::SQS::Queue'] must return the queue and NOT the topic. Observe [] for both.
3. SearchResources with a tag value no resource carries must return an empty list with no error (it does, but only because every query returns empty — the positive control in step 1 must pass first).
4. CreateGroup with that same TAG_FILTERS_1_0 query, then ListGroupResources: expect the queue with Identifier.ResourceType 'AWS::SQS::Queue'; observe 200 with Resources: [].
5. UpdateGroupQuery on that group to a query matching a SECOND tagged queue. GetGroupQuery must echo the new query (it does); ListGroupResources must then list queue2 and NOT queue1. Observe [] throughout.
6. CreateStack a template with an AWS::SNS::Topic, wait for CREATE_COMPLETE, read the topic's PhysicalResourceId, CreateGroup with ResourceQuery={Type:'CLOUDFORMATION_STACK_1_0', Query:'{"ResourceTypeFilters":["AWS::AllSupported"],"StackIdentifier":"<stack id>"}'}, then ListGroupResources: expect the topic ARN as a member. Then DeleteGroup and call ListGroupResources again: expect 404 NotFoundException with Message 'The specified group does not exist'.
