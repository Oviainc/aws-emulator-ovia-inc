=== Cause 1 of 2: a PRE_START_DEPLOYMENT extension action is never invoked, so StartDeployment is never gated and a raising target never vetoes it ===
Failing check id: appconfig__lambda.extension-action-point-invokes-lambda-during-deployment.
AWS: Smithy (services/service-com-amazonaws-appconfig-amazonappconfig/smithy-model/com-amazonaws-appconfig-amazonappconfig.json) models CreateExtension (POST /extensions, success 201) with an @required Actions map keyed by action point, CreateExtensionAssociation, and StartDeployment (POST /applications/{ApplicationId}/environments/{EnvironmentId}/deployments, success 201, errors BadRequestException 400 / ConflictException 409 / ResourceNotFoundException 404 / InternalServerException 500). The event payload and the veto message are NOT modelled — recorded behavior: with an extension declaring PRE_START_DEPLOYMENT [{Name, Uri=<lambda arn>, RoleArn}] associated to the environment ARN, StartDeployment synchronously invokes that target BEFORE creating the deployment, with an event whose Type is 'PreStartDeployment' (PascalCase, not the SCREAMING_SNAKE action-point key), whose Application.Id / Environment.Id / ConfigurationProfile.Id equal the ids on the request, whose ContentVersion is the request's ConfigurationVersion AS A STRING, whose Content base64-encodes the exact candidate configuration bytes, and whose TriggeredBy is 'USER' for a customer-issued StartDeployment. A target that returns normally lets the deployment be created and reach State COMPLETE, and the data plane then serves those bytes. A target that raises refuses StartDeployment with BadRequestException / HTTP 400 and the message template "Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <requestId>" — fixed text "Error invoking extension " and ": Unhandled error, Lambda Request ID: ", with the extension name taken from the associated extension in state and the request id taken from the failing invocation — creates NO deployment record, and leaves the previously deployed version in service.
Emulator: the action point is never dispatched. The check is killed with 'Check timed out after 60.0s': its StartDeployment barrier (which retries only on BadRequestException while the invoke role's trust propagates) never gets a deployment started, nothing ever arrives at the SQS observation sink the target forwards its event to, and the refusal leg is never reached — so neither the 201 path, nor the event shape, nor the 400 veto is observable. CreateExtension and CreateExtensionAssociation are accepted (VersionNumber 1, Actions and ResourceArn round-trip), so the association exists but is inert. Hypothesis: extension associations are stored as metadata only, with no action-point dispatch in the StartDeployment path.
Why: PRE_START_DEPLOYMENT is the one hook a customer uses to VETO a release. A client relying on AWS's behavior either never gets a release started at all, or (for an emulator that treats action points as fire-and-forget) has content its gate was written to reject reach the data plane with no refusal — the pre-flight approval, the content handed to the approver and the 400 a failing approver must produce are all unobservable.
Fix: the AppConfig extension action-point dispatch seam called from the StartDeployment handler — resolve the extension associations bound to the target environment's ARN, synchronously invoke each matching action's Uri through its RoleArn with the documented event body, and map a target failure onto BadRequestException/400 with AWS's 'Error invoking extension ...' message while creating no deployment record.
Traces: appconfig__lambda.extension-action-point-invokes-lambda-during-deployment.

=== Cause 2 of 2: AT_DEPLOYMENT_TICK is never invoked during an in-flight deployment, so a ROLL_BACK directive cannot revert it and the deployment never leaves its transitional state ===
Failing check id: appconfig__lambda.at-deployment-tick-directive-rollback-reverts-the-deployment.
AWS: the event and directive contract is not modelled (Hypothesis, from AppConfig's custom-Lambda extension documentation, as the check's own header states): an extension action bound to AT_DEPLOYMENT_TICK is invoked repeatedly while a deployment is in flight, and a target response of {"Directive": "ROLL_BACK", "Description": "<text>"} makes AppConfig roll the deployment back; the rollback is attributed to TriggeredBy 'EXTENSION', the deployment then settles in a terminal state (ROLLED_BACK/REVERTED — State is the modelled DeploymentState enum on GetDeployment/StartDeployment output) and the environment leaves its transitional Deploying/RollingBack state. Independently of any directive, a non-zero-duration deployment (the check uses DeploymentDurationInMinutes=2) must progress to a terminal state on its own.
Emulator: killed with 'Check timed out after 60.0s'. The deployment is never ticked, so the directive is never read, no rollback is attributable to the extension, and the check cannot even tear the environment down because it never leaves a transitional state.
Why: AT_DEPLOYMENT_TICK plus ROLL_BACK is AppConfig's programmable abort. A client relying on it keeps a configuration in service that production would have rolled back, and any caller polling for a terminal deployment state never returns.
Fix: the same action-point dispatch seam, driven from the deployment state machine's growth-tick loop — each tick must invoke the associated AT_DEPLOYMENT_TICK actions and interpret a {"Directive":"ROLL_BACK"} response by driving the deployment to a terminal rolled-back state with TriggeredBy 'EXTENSION'; the state machine must also advance a non-zero-duration deployment to a terminal state on its own.
Traces: appconfig__lambda.at-deployment-tick-directive-rollback-reverts-the-deployment.

Generated function names, extension names, resource ids and Lambda request ids in these checks are per-run values that only fill the templates; the requirements are the invocation itself, the event's documented key/case shape, the 400 BadRequestException veto with AWS's wording, and the terminal deployment state.

## Steps to Reproduce
Boot the emulator and point appconfig, appconfigdata, lambda, iam and sqs clients at its data listener.

Cause 1 (PRE_START_DEPLOYMENT veto):
1. Create an SQS queue as the observation sink and an execution role allowing sqs:SendMessage on it; create a Lambda that forwards its event to that queue and raises when its REFUSE env var is '1'.
2. AddPermission for Principal appconfig.amazonaws.com, and create a role appconfig.amazonaws.com can assume that allows lambda:InvokeFunction on the function ARN.
3. CreateExtension(Actions={'PRE_START_DEPLOYMENT': [{'Name':'gate','Uri':<fn-arn>,'RoleArn':<invoke-role>}]}).
4. Create an application, an environment and a hosted configuration profile; CreateHostedConfigurationVersion twice (versions 1 and 2).
5. CreateExtensionAssociation binding the extension to arn:aws:appconfig:<region>:<account>:application/<app-id>/environment/<env-id>.
6. CreateDeploymentStrategy(DeploymentDurationInMinutes=1, GrowthFactor=100, GrowthType='LINEAR', FinalBakeTimeInMinutes=0, ReplicateTo='NONE').
7. With REFUSE='0', StartDeployment for version 1. EXPECTED: 201, an event on the queue with Type 'PreStartDeployment' and Content base64-decoding to version 1's exact bytes, deployment reaching COMPLETE, and the data plane serving those bytes. OBSERVED: nothing is enqueued and the deployment never settles.
8. Set REFUSE='1' and StartDeployment for version 2. EXPECTED: BadRequestException/400 with Message 'Error invoking extension <extensionName>: Unhandled error, Lambda Request ID: <requestId>', no new record in ListDeployments, version 1 still served. Then restore REFUSE='0' and repeat the identical call: it must now succeed and version 2 must reach the data plane.

Cause 2 (AT_DEPLOYMENT_TICK ROLL_BACK):
1. Same wiring, with Actions={'AT_DEPLOYMENT_TICK': [{'Name':'tick','Uri':<fn-arn>,'RoleArn':<invoke-role>}]} and a target that forwards each tick event to the queue and returns {'Directive': <value of its DIRECTIVE env var>, 'Description': <REASON>}.
2. CreateDeploymentStrategy with DeploymentDurationInMinutes=2 (a non-instant strategy) and StartDeployment.
3. With DIRECTIVE='ROLL_BACK'. EXPECTED: repeated tick events on the queue, the deployment reaching ROLLED_BACK/REVERTED with the rollback attributed to TriggeredBy 'EXTENSION', and GetEnvironment.State leaving Deploying/RollingBack. OBSERVED: no invocation, and the deployment and environment never leave their transitional states.
