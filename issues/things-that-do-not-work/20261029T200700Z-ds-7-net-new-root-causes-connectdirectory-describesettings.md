## Description

Cause 1 of 7: ConnectDirectory is an unimplemented scaffold stub, so AD Connector input validation does not exist.
AWS: Smithy: ConnectDirectory (ConnectSettings, Name, Password, Size all @required) models ClientException, DirectoryLimitExceededException, InvalidParameterException (client, 400) and ServiceException (500). Recorded behavior: ConnectSettings carrying exactly ONE subnet is refused HTTP 400 InvalidParameterException (AD Connector, like every ds directory, requires two subnets in two AZs).
Emulator: HTTP 501 with code NotImplemented — services/service-com-amazonaws-directoryservice-directoryservice-20150416/src/ops/connect_directory.rs still carries the "SCAFFOLDED, NOT IMPLEMENTED" marker and returns crate::scaffolded::Scaffolded::not_implemented("ConnectDirectory").
Why: every AD Connector flow is unavailable, and a caller probing the one-subnet refusal gets a 501 that no SDK maps to InvalidParameterException, so negative-path handling cannot be exercised at all.
Fix: implement the ConnectDirectory handler (src/ops/connect_directory.rs) — validate ConnectSettings (two subnets, two AZs, VPC resolution) and refuse InvalidParameterException before creating the connector; then delete the SCAFFOLDED marker.
Traces: ds.connect-directory-invalid-vpc-settings-rejected.

Cause 2 of 7: DescribeSettings is an unimplemented scaffold stub, so the directory-settings not-found error class is unreachable.
AWS: Smithy: DescribeSettings (DirectoryId @required @pattern ^d-[0-9a-f]{10}$) models ClientException, DirectoryDoesNotExistException ("The specified directory does not exist in the system."), InvalidNextTokenException, InvalidParameterException, UnsupportedOperationException (client, 400) and ServiceException (500). For a well-formed DirectoryId the account was never issued, the refusal is HTTP 400 DirectoryDoesNotExistException — distinct from the EntityDoesNotExistException other ds reads use, which is exactly the distinction the check exercises.
Emulator: HTTP 501 NotImplemented (src/ops/describe_settings.rs still carries the SCAFFOLDED marker and returns not_implemented("DescribeSettings")).
Why: callers cannot read directory settings at all, and the ds not-found error families (DirectoryDoesNotExistException vs EntityDoesNotExistException) collapse into one unusable 501, so error-routing logic written against AWS cannot be tested.
Fix: implement the DescribeSettings handler (src/ops/describe_settings.rs) — resolve the DirectoryId against state, refuse DirectoryDoesNotExistException when absent, and project SettingEntries for an existing directory; delete the SCAFFOLDED marker.
Traces: ds.not-found-error-families-are-distinct.

Cause 4 of 7: DescribeDirectories omits the derived DirectoryDescription.Size for a Managed Microsoft AD.
AWS: Smithy: DirectoryDescription.Size targets the DirectorySize enum (values Small, Large) and is documented "The directory size." CreateMicrosoftAD takes NO Size parameter, so this member is DERIVED by the service, not echoed from the request; recorded behavior for a Standard-edition MicrosoftAD is Size "Small" alongside Edition "Standard".
Emulator: the member is absent from the description (replay: "a Standard MicrosoftAD also reports the derived Size 'Small', got None") while the sibling echo members in the same read matched.
Why: a client that reads Size to size its own capacity planning, to render the directory in a console, or to branch on Small vs Large gets null where AWS always sends an enum value — and because the value is derived, the caller cannot reconstruct it from its own request.
Fix: the directory record's projection in src/state.rs (Directory::to_description) feeding DescribeDirectories (src/ops/describe_directories.rs) — derive and emit Size for MicrosoftAD (and Simple AD) directories.
Traces: ds.simple-ad-small-lifecycle-to-active-then-deleted.

Cause 5 of 7: ds evaluates no IAM authorization — AddRegion answers a caller whose policy explicitly denies ds:AddRegion.
AWS: Smithy: AddRegion models AccessDeniedException (client, 400) among its errors, as RemoveRegion does. Recorded behavior: a sigv4 identity whose attached policy carries an explicit Deny on ds:AddRegion is refused AccessDeniedException BEFORE the call reaches the DS business logic, whereas the same call from an unrestricted identity reaches the business logic and is refused there (UnsupportedOperationException when it targets the directory's home Region) — that contrast is what proves the block was the missing permission.
Emulator: the restricted identity never receives AccessDeniedException. The check creates the role and policy, assumes it, and polls AddRegion for AccessDeniedException; the observation never arrives and the check is killed at its 60 s budget ("Check timed out after 60.0s", no exception frame). The sibling check ds.remove-region-access-denied (OWNED by 20261024T081601Z) records the same ground concretely: "expected AccessDeniedException for the IAM-denied caller, got 'DirectoryDoesNotExistException'" — the call is executed on its merits, so the explicit Deny is ignored. Hypothesis (neither the model nor a recording states it): the ds request path performs no policy evaluation at all, so no ds operation can produce AccessDeniedException.
Why: this is an over-permissive divergence — a least-privilege test suite or a guardrail that relies on AWS refusing an unpermitted multi-Region change passes against the emulator and fails (or, worse, mutates) against AWS; callers also never see the AccessDeniedException branch their error handling is written against.
Fix: the authorization seam in front of the ds operation handlers (the request walk that reaches src/ops/add_region.rs and its siblings) — evaluate the caller's identity policy, including explicit Deny, and refuse AccessDeniedException before the handler runs.
Traces: ds.add-region-access-denied.

Cause 6 of 7: the trust inventory never settles — DescribeTrusts does not converge on a created trust and DeleteTrust does not converge on its removal.
AWS: Smithy: CreateTrust returns TrustId (@pattern ^t-[0-9a-f]{10}$); Trust carries TrustState (Creating, Created, Verifying, VerifyFailed, Verified, Updating, UpdateFailed, Updated, Deleting, Deleted, Failed) and TrustStateReason; DescribeTrusts scoped by DirectoryId lists that directory's trusts and the unscoped call lists the account's. Recorded behavior: a created trust appears in DescribeTrusts(DirectoryId=…) with its own TrustId/DirectoryId/RemoteDomainName/TrustDirection, reaches a terminal TrustState within minutes, and after DeleteTrust disappears from the inventory.
Emulator: both checks exhaust the harness budget with no exception frame ("Check timed out after 60.0s") while polling exactly these conditions — ds.describe-trusts-returns-inventory polls DescribeTrusts(DirectoryId=…) for the single created trust and then for the empty inventory after DeleteTrust; ds.create-trust-duplicate-remote-domain-rejected polls DescribeTrusts for the trust to reach one of {Created, Verified, VerifyFailed, Failed} and then for it to disappear after DeleteTrust. Nothing the emulator serves moves those polls to their predicate. Hypothesis (neither the model nor a recording states which leg stalls): this is the same trust subsystem whose state machine 20261025T030730Z Cause 4 shows is driven only by an unconditional Creating->Created clock transition, with no deletion settle path; re-replay must show the inventory converging on both legs.
Why: a caller cannot confirm that a trust was created or that a deletion completed — every poll-until-converged loop (the normal way to use CreateTrust/DeleteTrust) hangs instead of finishing, so trust provisioning cannot be automated against this emulator at all.
Fix: the trust lifecycle — src/ops/create_trust.rs, src/ops/delete_trust.rs and the trust branch of advance_clock in src/state.rs feeding src/ops/describe_trusts.rs — a created trust must be listed by DescribeTrusts for its directory and in the unscoped listing, settle into a terminal TrustState, and be removed from the inventory once DeleteTrust completes.
Traces: ds.describe-trusts-returns-inventory, ds.create-trust-duplicate-remote-domain-rejected.

Cause 7 of 7: two concurrent AddIpRoutes calls for the identical CIDR do not resolve to one success and one refusal, and the route never reaches Added.
AWS: Smithy: AddIpRoutes (DirectoryId, IpRoutes @required) models ClientException, EntityAlreadyExistsException, DirectoryUnavailableException and IpRouteLimitExceededException (client, 400). Recorded behavior: the directory serializes mutating calls, so of two concurrent identical AddIpRoutes exactly ONE succeeds and the loser is refused — either as a duplicate route, or with a ClientException naming the in-progress update/maintenance — and ListIpRoutes ends with exactly ONE entry for that CIDR whose IpRouteStatusMsg settles to Added.
Emulator: the check is killed at its 60 s budget with no exception frame while waiting for that CIDR's route to reach a terminal status after the race, so neither the one-success/one-refusal outcome nor the single Added entry is ever observable. Hypothesis (neither the model nor a recording states it): concurrent mutations on the same directory are not serialized, leaving the route's status transition unresolved; the requirement the fix must restore is the one stated above — exactly one success, a modelled refusal for the loser, and one route entry that settles to Added.
Why: callers legitimately issue the same AddIpRoutes from parallel workers or retried deployments; against this emulator such a flow neither errors nor converges, so the route's state is indeterminate and automation hangs.
Fix: the AddIpRoutes handler and the IP-route state transition (src/ops/add_ip_routes.rs plus the ip-route branch of advance_clock in src/state.rs) — serialize concurrent mutations per directory, refuse the loser with a modelled error, and settle the single route entry to Added.
Traces: ds.concurrent-add-ip-routes-duplicate-conflict.
