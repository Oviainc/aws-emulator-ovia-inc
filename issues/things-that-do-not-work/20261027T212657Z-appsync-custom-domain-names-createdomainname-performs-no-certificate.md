# AppSync custom domain names: CreateDomainName performs no certificate validation (accepts a cert AWS refuses with BadRequestException "Certificate is invalid."), and the domain-name operations are still not gated by identity-based IAM

> _Note: this issue was identified against the code base at commit `c0eb4295fc6918b9011f996ea325c28045b54b65`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDomainName

## Description
Two distinct root causes on the AppSync custom-domain-name control plane. 2 causes in this issue; BOTH must be closed before submitting.

=== Cause 1 of 2: CreateDomainName accepts any syntactically valid certificateArn — no certificate-provenance and no certificate-region validation ===
AWS: Smithy (com.amazonaws.appsync#AWSDeepdishControlPlaneService) models CreateDomainName as POST /v1/domainnames, success code 200, input `domainName` (required, @length 1..253, @pattern ^(\*[\w\d-]*\.)?([\w\d-]+\.)+[\w\d-]+$) and `certificateArn` (required, @length 20..2048, @pattern ^arn:[a-z-]*:(acm|iam):[a-z0-9-]*:\d{12}:(certificate|server-certificate)/[0-9A-Za-z_/-]*$), with errors {AccessDeniedException 403, BadRequestException 400, InternalFailureException 500}. The ARN pattern is only a syntax gate: AWS additionally resolves the certificate cross-service and refuses it when it is not an ACM-issued, publicly trusted certificate for the requested domain. Recorded behavior: a certificate that ACM itself reports Status=ISSUED but whose chain is self-signed / imported via ImportCertificate is refused with BadRequestException / HTTP 400 and the message "Certificate is invalid." — that sentence is entirely FIXED text, with no request- or state-derived parts. Recorded behavior also shows a second, independent refusal on the same operation: a certificate that lives in the caller's own region rather than us-east-1 gets BadRequestException / HTTP 400 "Certificate must be in us-east-1.", again wholly fixed text. Because the refusal happens before any state is written, the domain is absent afterwards: GetDomainName (GET /v1/domainnames/{domainName}) answers NotFoundException / 404 with the fixed message "Domain name not found" (no trailing period), AssociateApi (POST /v1/domainnames/{domainName}/apiassociation) answers NotFoundException / 404 with the fixed message "Domain name not found." (with the trailing period), and ListDomainNames does not list it.
Emulator: CreateDomainName returns HTTP 200 with a fully populated `domainNameConfig` for exactly those certificates. For the self-signed/imported-certificate case the replay recorded `CreateDomainName unexpectedly SUCCEEDED with a self-signed-provenance certificate` and `CreateDomainName ACCEPTED an ImportCertificate-sourced certificate for domainName=<request domainName>`; for the wrong-region case a create whose certificateArn is an acm certificate in the caller's region (not us-east-1) returned 200 with `domainNameConfig` {domainName, certificateArn echoed back, appsyncDomainName, hostedZoneId, tags, domainNameArn} instead of the BadRequestException. No certificate resolution of any kind appears to happen: the handler validates the ARN's shape and stores the string. The knock-on effect is visible in the concurrency check — because the first of two racing creates is accepted, the loser is refused with the wrong class of error entirely: BadRequestException "Domain name already exists." where AWS gives both racers BadRequestException "Certificate is invalid." and creates nothing.
Why: a client that provisions an AppSync custom domain against the emulator believes it holds a working custom domain built on a certificate AWS would never accept, so the same deployment template fails at the first real-AWS run; and any code branching on the certificate refusal (catch BadRequestException, inspect the message, re-issue the certificate in us-east-1 via ACM) is never exercised, because the error never arrives. Downstream assertions that the refusal left NO state — GetDomainName 404, absence from ListDomainNames, AssociateApi 404 — are inverted: the domain exists.
Note: open issue 20261025T182150Z-appsync-createdomainname-answers-501-notimplemented-instead-of-rejecting.md describes this operation answering 501 NotImplemented for an untrusted private-CA-chain certificate, and 20261025T182150Z-appsync-createdomainname-stub.md covers the scaffold stub. Neither covers the behavior replayed here: the operation now ANSWERS, with a 200 success, so the defect has moved from "not implemented" to "implemented without the certificate validation". These replay keys are not carried by either issue.
Fix: the CreateDomainName handler in the AppSync service crate (its validation step and the cross-service certificate resolution it must perform against the ACM state) plus the error mapping that must emit the modeled BadRequestException/400 with AWS's fixed messages; the domain-name record must not be written on refusal.
Traces: appsync.domain-api-association-lifecycle, appsync.domain-name-api-association-lifecycle, appsync.concurrent-update-domain-name-single-winner.

=== Cause 2 of 2: the domain-name operations apply no identity-based IAM authorization — neither an implicit default deny nor an explicit Deny is honored ===
AWS: Smithy models AccessDeniedException (403) on every domain-name operation: CreateDomainName, GetDomainName, ListDomainNames, UpdateDomainName, DeleteDomainName. The authorization decision happens BEFORE resource lookup, so a principal with no identity-based policy granting the action gets AccessDeniedException/403 whether or not the domain exists. The implicit-deny message is rule-derived, not fixed: "User: <caller principal ARN> is not authorized to perform: appsync:<ActionName> on resource: <resource ARN> because no identity-based policy allows the appsync:<ActionName> action" — the fixed text is "User: ", " is not authorized to perform: appsync:", " on resource: ", " because no identity-based policy allows the appsync:", " action"; the variable parts are the caller's principal ARN (the IAM user/assumed-role session ARN from the signature), the action name, and the resource ARN (arn:aws:appsync:<region>:<account>:domainnames/<domainName> for the per-domain operations, arn:aws:appsync:<region>:<account>:* for ListDomainNames). When an explicit Deny statement matches, the tail of the same template changes to " with an explicit deny in an identity-based policy" and the "because no identity-based policy allows ..." clause is dropped. Removing the Deny restores the pre-Deny outcome on the identical signed call.
Emulator: requests signed by a freshly created IAM user with ZERO attached policies are executed as if fully authorized. Recorded: CreateDomainName from that zero-policy principal returned HTTP 200 with a populated `domainNameConfig` (the check's assertion reads `expected a rejection, but the call succeeded and returned {'ResponseMetadata': {'HTTPStatusCode': 200 ...}, 'domainNameConfig': {...}}`) instead of AccessDeniedException/403. Likewise, an appsync:*-granted role carrying an explicit Deny on appsync:GetDomainName never produces AccessDeniedException: the check's bounded retry loop never observes the expected (code, message) pair and the check is killed at the 60s harness timeout (`Check timed out after 60.0s`). The emulator makes no identity-based policy evaluation for these operations at all, so no IAM statement — Allow or Deny — changes the response.
Why: this is an overly-permissive boundary. A least-privilege regression (a role that lost, or never had, appsync:CreateDomainName) is indistinguishable from a correctly permissioned one, so policy tests pass against the emulator and fail in AWS — or worse, a real misconfiguration ships undetected. The retry-until-denied pattern real SDK users write to absorb IAM propagation lag becomes an unbounded hang rather than a converging poll.
Note: open issue 20261024T032443Z-appsync-control-plane-fidelity-domain-name-operations-unimplemented.md lists these two check ids, but its Cause 1 diagnoses the domain-name operations as scaffold stubs answering `NotImplemented` and its Cause 4 is scoped to the sandbox operations EvaluateCode/EvaluateMappingTemplate; the operations now answer 200, so the missing authorization gate in front of domain-name dispatch is not the defect it describes and the replay keys are no longer carried by it. 20261025T022306Z (GraphQL-API ops), 20261025T041655Z (Event-API/domain ops), 20261026T233737Z (channel namespaces) and 20261027T010308Z (ListApis/ListGraphqlApis) report the same missing gate on OTHER operation families and do not cover these.
Fix: the request-authorization layer in front of AppSync operation dispatch (sigv4 principal -> IAM identity-policy evaluation -> AccessDeniedException/403 built from the implicit-deny / explicit-deny templates), applied to the domain-name handlers (create_domain_name.rs, get_domain_name.rs, list_domain_names.rs, update_domain_name.rs, delete_domain_name.rs) before any state lookup.
Traces: appsync.access-denied-domain-name, appsync.access-denied-get-domain-name.

## Evidence

After the refusal: GetDomainName -> NotFoundException/404 "Domain name not found"; AssociateApi -> NotFoundException/404 "Domain name not found."; the domain absent from ListDomainNames.
  Actual: HTTP 200 with `domainNameConfig`.

    appsync.domain-name-api-association-lifecycle: `AssertionError: CreateDomainName ACCEPTED an ImportCertificate-sourced certificate for domainName='<generated>.example-test.com' - real AWS has been observed to reject this unconditionally; this target's certificate-provenance check diverges from AWS`.
    appsync.concurrent-update-domain-name-single-winner: `AssertionError: expected the exact certificate-invalid refusal, got 'Domain name already exists.'` — i.e. the first racer was ACCEPTED and the second was refused with the duplicate-name error instead of both getting "Certificate is invalid.".

Cause 2 — no identity-based IAM gate on the domain-name operations.
  Expected: AccessDeniedException, HTTP 403, message "User: <principal ARN> is not authorized to perform: appsync:CreateDomainName on resource: arn:aws:appsync:<region>:<account>:domainnames/<domainName> because no identity-based policy allows the appsync:CreateDomainName action" for a zero-policy IAM user (same template for GetDomainName/UpdateDomainName/DeleteDomainName; resource arn:aws:appsync:<region>:<account>:* for ListDomainNames). With an explicit Deny attached to an appsync:*-granted role: AccessDeniedException, HTTP 403, "User: <assumed-role session ARN> is not authorized to perform: appsync:GetDomainName on resource: arn:aws:appsync:<region>:<account>:domainnames/<domainName> with an explicit deny in an identity-based policy"; after the Deny is deleted, the same call returns to NotFoundException/404 "Domain name not found".
  Actual: appsync.access-denied-domain-name — `AssertionError: expected a rejection, but the call succeeded and returned {'ResponseMetadata': {'HTTPStatusCode': 200, 'HTTPHeaders': {'content-type': 'application/json', ...}}, 'domainNameConfig': {...}}` on CreateDomainName signed by an IAM user with no attached policies.
  appsync.access-denied-get-domain-name — `Check timed out after 60.0s`: the explicit-deny probe polls for the (AccessDeniedException, explicit-deny message) pair and never sees it, so the check never converges and is killed by the harness.

## Steps to Reproduce
Cause 1:
1. ACM (us-east-1): ImportCertificate / create a self-signed certificate for a non-RFC-2606 domain, e.g. <unique>.sim2real-appsync-test.com, and confirm DescribeCertificate reports Status=ISSUED (positive control: the certificate itself is well-formed).
2. appsync CreateDomainName(domainName=<that domain>, certificateArn=<that cert>). Observe HTTP 200 and a populated domainNameConfig; AWS answers BadRequestException/400 "Certificate is invalid.".
3. Then GetDomainName(domainName=<that domain>) and ListDomainNames() — the domain is present, where AWS has NotFoundException/404 "Domain name not found" and an empty listing; AssociateApi(domainName=<that domain>, apiId=<any api>) likewise should be NotFoundException/404 "Domain name not found.".
4. Wrong-region variant: CreateDomainName with certificateArn = arn:aws:acm:<caller region>:<account>:certificate/<uuid> (not us-east-1). Observe 200 instead of BadRequestException/400 "Certificate must be in us-east-1.".
5. Concurrency variant: fire two CreateDomainName calls for the same domain/certificate concurrently. Observe one 200 and one BadRequestException "Domain name already exists."; AWS refuses both with "Certificate is invalid." and creates nothing.

Cause 2:
1. iam CreateUser with NO attached policies, CreateAccessKey, build an appsync client with those credentials.
2. Call CreateDomainName / GetDomainName / UpdateDomainName / DeleteDomainName / ListDomainNames with them. Each returns 2xx (CreateDomainName returns 200 and actually creates the domain) instead of AccessDeniedException/403 with the implicit-deny message.
3. Explicit-deny variant: CreateRole trusted by the account root, PutRolePolicy granting Allow appsync:* on *, AssumeRole, then GetDomainName on a never-created domain (AWS: NotFoundException/404 "Domain name not found"). PutRolePolicy adding Deny appsync:GetDomainName on * and poll the same call — AccessDeniedException with the explicit-deny message never appears; DeleteRolePolicy and poll again — no observable change either way.
