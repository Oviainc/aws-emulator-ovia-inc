# cognito-identity: 3 net-new GetCredentialsForIdentity root causes — vended access key id is not an STS 'ASIA' key, Rules role mapping with AmbiguousRoleResolution=Deny answers the wrong error (and never vends for a matching rule), and PrincipalTag session tags are not enforced so one tenant's session reads another tenant's object

> _Note: this issue was identified against the code base at commit `40b622ed07403ef350d596bb19a34a2d990a98a6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetCredentialsForIdentity

## Description
Three independent net-new root causes in the cognito-identity GetCredentialsForIdentity credential-vending path, all grounded in failing behavioral checks of this suite. None of them is marked ALREADY FILED or OWNED by the replay report.

=== Cause 1 of 3: GetCredentialsForIdentity vends an access key id that is not an STS temporary-credential key id ===
AWS: Smithy (com.amazonaws.cognitoidentity) — GetCredentialsForIdentity returns `Credentials` with members AccessKeyId (AccessKeyString, "The Access Key portion of the credentials"), SecretKey, SessionToken, Expiration. The model places no pattern on AccessKeyString, so this is recorded behavior only: real Cognito Identity vends the credentials of an sts:AssumeRoleWithWebIdentity session, and a temporary (session) access key id always carries the temporary-credential key-type prefix `ASIA` — never a long-term `AKIA` and never a vendor-specific literal. The recorded runs assert exactly that prefix on the vended key id, for a developer-authenticated identity and for a Rules-role-mapping-selected role.
Emulator: the vended key id begins with the literal string `EMULATOR` — observed values `EMULATORASHQISVY5Q7D` (developer-identity check) and `EMULATORASHCWWIBKDGZ` (rules-claim-match check). The `EMULATOR` prefix and the trailing random body are per-run values; the requirement is only the key-type prefix `ASIA` on a vended session key id.
Why: a client that inspects the vended key id to tell a temporary session from a long-term key (SDK credential-type detection, audit/compliance tooling, test harnesses that distinguish role sessions, policy conditions keyed on the credential type) classifies a Cognito-vended session as a non-session credential. The downstream caller identity is therefore also not provably a role session.
Fix: the cognito-identity GetCredentialsForIdentity handler's credential-vending component — the place where it mints/relays the AssumeRoleWithWebIdentity session instead of fabricating an access key id. It must return a key id generated with the STS temporary-credential key-type prefix.
Traces: cognito-identity.developer-identity-vends-authenticated-role-credentials, cognito-identity.role-mapping-rules-claim-match-selects-role.
Related but NOT covering: open issues 20261026T234020Z-cognito-identity-4-net-new-root-causes-web.md (web-identity sessions carry a non-ASIA access key id) and 20261028T040721Z-cognito-identity-cognito-idp-iam-getcredentialsforidentity-vends-an.md (the IAM-OIDC-registered-issuer path) describe the same symptom on other paths; neither carries these two checks' replay keys, and the report marked neither of these checks OWNED.

=== Cause 2 of 3: Rules role mapping is not evaluated — AmbiguousRoleResolution=Deny answers InvalidIdentityPoolConfigurationException instead of NotAuthorizedException, and a login that DOES match a rule is never vended credentials ===
AWS: Smithy — SetIdentityPoolRoles accepts RoleMapping{Type, AmbiguousRoleResolution, RulesConfiguration}; RulesConfigurationType.Rules is "evaluated in order. The first one to match specifies the role", and AmbiguousRoleResolution "specifies the action to be taken if either no rules match the claim value for the Rules type". GetCredentialsForIdentity models NotAuthorizedException (httpError 403) "Thrown when a user is not authorized to access the requested resource" and InvalidIdentityPoolConfigurationException (httpError 400), documented for "the identity pool has no authenticated role configured, or STS returned an error response" — i.e. a pool-configuration fault, not a role-mapping denial. The recording shows AWS refusing a Deny-resolved, rule-unmatched login with code `NotAuthorizedException` and message `The ambiguous role mapping rules for: <provider-name> denied this request.` — the fixed text is `The ambiguous role mapping rules for: ` … ` denied this request.` and the single variable part is the role-mapping provider name from the request/pool configuration (`cognito-idp.<region>.amazonaws.com/<user-pool-id>`), never a literal from one run. In the same recording a login whose claim DOES match a rule is vended credentials for that rule's RoleARN (GetCallerIdentity shows `:assumed-role/<rule-role-name>/`).
Emulator: the Deny-resolved login is refused with the wrong error — code `InvalidIdentityPoolConfigurationException`, message `Invalid identity pool configuration. Check assigned IAM roles for this pool.` (HTTP 400) instead of `NotAuthorizedException` / the ambiguous-role-mapping message (HTTP 403). On the positive side of the same feature, the rule-matching login is never vended credentials at all: the check's poll for a response carrying Credentials.SessionToken never succeeds and the check runs to the 60 s harness cap. Hypothesis: the pool's RoleMappings of Type=Rules are not evaluated, so every mapped login falls through to the same pool-configuration rejection — the wrong-code refusal and the never-vending positive path are the two faces of it.
Why: a client cannot distinguish an authorization decision (403, retry pointless, user is simply not entitled to a role) from a pool misconfiguration (400, operator must fix role attachment) — error-handling branches on code, and the emulator sends every Rules-mapped caller down the misconfiguration branch. Worse, Rules-based role mapping, the mechanism that scopes a tenant/tier to a narrower role, never takes effect, so no caller ever receives the mapped role.
Fix: the cognito-identity GetCredentialsForIdentity handler's role-resolution component (RoleMappings/Rules evaluation and the AmbiguousRoleResolution branch) and the error classification it raises.
Traces: cognito-identity.get-credentials-ambiguous-role-resolution-denied (wrong code/message), cognito-identity.role-mapping-ambiguous-resolution-deny-blocks-credentials (positive control never vends; check hits the 60 s cap).
Related but NOT covering: 20261026T054328Z-cognito-identity-4-net-new-root-causes-a.md mentions rules-based role mapping ignoring declared order, and 20261023T185902Z-cognito-identity-cognito-idp-both-group-role-mapping.md covers the cognito-idp group/token-mapping checks; neither carries these replay keys and the report marked neither check OWNED.

=== Cause 3 of 3: PrincipalTag attribute map produces no enforced session tag — a vended session reads the other tenant's object ===
AWS: recorded behavior only (the Smithy model defines SetPrincipalTagAttributeMap/GetPrincipalTagAttributeMap but not the downstream authorization semantics). The recording configures PrincipalTags {tenant: custom:tenant} with UseDefaults=false on the identity provider, an authenticated role whose trust policy allows sts:AssumeRoleWithWebIdentity + sts:TagSession, and an inline role policy allowing s3:GetObject only on `arn:aws:s3:::<bucket>/${aws:PrincipalTag/tenant}/*`. Each tenant's vended session reads its OWN prefix successfully, and a read of the OTHER tenant's key is refused by S3 with error code `AccessDenied` and the identity-based-policy refusal message (fixed wording for "not authorized to perform s3:GetObject because no identity-based policy allows the action", with the assumed-role ARN, bucket and key taken from the request/state). Both directions are refused, proving the policy variable resolves to the caller's own tag.
Emulator: the cross-tenant read SUCCEEDS and returns the other tenant's object bytes — no error code at all is raised (the check observed tenant-a's session returning tenant-b's payload). The `${aws:PrincipalTag/tenant}` scope grants everything, i.e. the mapped principal tag never becomes an enforced session tag on the vended session.
Why: this is a silent cross-tenant data leak. Every multi-tenant design that scopes object access by `aws:PrincipalTag` passes its tests against the emulator and ships a policy that was never enforced; an exfiltration test that must fail closed instead reads another tenant's data.
Fix: the cognito-identity GetCredentialsForIdentity handler's session-tag propagation (mapped PrincipalTags must be attached to the vended role session) together with the policy-evaluation component that resolves `aws:PrincipalTag/<key>` policy variables and condition keys for that session.
Traces: cognito-identity.principal-tag-condition-denies-the-other-tenants-object.
Related but NOT covering: 20261025T005354Z-cognito-identity-getid-admits-unvalidatable-login-tokens-setprincipaltagattributemap.md (owns the e2e-principal-tags-flow-into-sts-session-tags check) and 20261026T054328Z-cognito-identity-s3-a-bucket-policy-is-never.md; the report marked this check neither OWNED nor ALREADY FILED.
