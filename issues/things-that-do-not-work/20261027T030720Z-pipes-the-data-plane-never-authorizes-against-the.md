Cause 1 of 3: target delivery performs no authorization at all against the pipe's execution role, so a pipe whose role lacks sqs:SendMessage on its target delivers anyway — and because the delivery "succeeds", the source record is deleted instead of being retried and eventually redriven to the source's dead-letter queue.
AWS: Smithy (com.amazonaws.pipes#CreatePipe) models RoleArn as required and documents it as "The ARN of the role that allows the pipe to send data to the target"; the data-plane consequence is recorded behavior only (the model describes only the control plane). EventBridge Pipes assumes that role and makes the target call under it, so a target invocation the role does not permit FAILS: the record is not delivered, it is not deleted from the SQS source, it reappears when its visibility timeout lapses, and once the source queue's own redrive policy maxReceiveCount is exceeded the record is moved to the source's dead-letter queue (Pipes has no DeadLetterConfig for an SQS source — the source queue's redrive policy is the failure path). A grant added later does not retroactively deliver a record the pipe already gave up on, but a permitted twin on identical wiring does deliver — that is the reachability control each of these checks carries.
Emulator: delivery happens regardless of the role. pipes.pipe-target-permission-missing-delivery-rejected fails with "message delivered to target despite missing SendMessage permission" and the target queue holds the full aws:sqs record envelope; pipes.pipe-target-send-grant-restored-delivers-the-message-it-withheld fails with "pipe '<name>' delivered '<marker>-WITHHELD' to '<target queue>' even though its execution role '<role>' has no sqs:SendMessage grant on that queue"; pipes.pipe-target-denied-records-are-redriven-to-the-source-dead-letter-queue reaches the 60 s harness cap waiting for the record on the source's DLQ, because the record was delivered and deleted and so never accumulates receive counts. The code confirms the mechanism: services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs resolves the pipe into SqsSourcedPipe (source_queue, batch_size, batching_window, enrichment, target) and never reads PipeRecord::role_arn at all — the stages call the sqs/lambda/states surfaces of this same emulator over smithy_server_runtime::EmbeddedEmulator with no assumed role and no permission evaluation, so there is no code path on which a target call can be refused for lack of a grant.
Why: a client cannot distinguish a correctly configured pipe from one whose execution role is missing the target grant — the most common Pipes misconfiguration is reported as a working pipe. Worse, data that AWS withholds is delivered: a least-privilege boundary a customer relies on to keep records out of a queue is not enforced, and the failure path (redelivery after the visibility timeout, then the source DLQ) is never exercised, so no record is ever preserved for inspection and the "delivered" record is deleted from the source.
Fix: the target (and enrichment) stage of the pipes data plane in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs — evaluate the pipe's stored RoleArn against the iam surface for the action the stage is about to perform (sqs:SendMessage on the resolved target queue, sqs:ReceiveMessage/DeleteMessage on the source, lambda:InvokeFunction / states:StartSyncExecution for an enrichment) and treat a denial as the existing Batch::Failed outcome: do not deliver, do not delete the source records, let them reappear on the source so the source's own redrive policy can dead-letter them.

Cause 2 of 3: a pipe whose SourceParameters carry FilterCriteria (or whose TargetParameters/EnrichmentParameters carry an InputTemplate) is accepted, reaches RUNNING, and then moves nothing at all — the data plane refuses to serve that configuration silently.
AWS: Smithy (com.amazonaws.pipes): CreatePipe accepts SourceParameters -> PipeSourceParameters.FilterCriteria (FilterCriteria.Filters[].Pattern, an EventBridge event pattern) and PipeTargetParameters.InputTemplate; DescribePipe reports CurrentState from PipeState. The documented contract is that a RUNNING pipe evaluates FilterCriteria against each polled record, DROPS the records that do not match (deleting them from the SQS source without delivering), DELIVERS the records that do match, and renders InputTemplate over the matching record before the target call. A malformed (non-JSON) Pattern is refused at CreatePipe time with ValidationException (400) whose fieldList names Pattern.
Emulator: pipes.pipe-filter-blocks-nonmatching-events reaches the 60 s harness cap. Its non-matching leg sees nothing at the target (vacuously correct) and its positive control — a record matching {"body":{"type":["match-me"]}} with TargetParameters.InputTemplate "<$.body.id>" — never arrives. The code states the cause outright: services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs resolve_run returns Err("it carries FilterCriteria, which this emulator does not evaluate yet") for any pipe with FilterCriteria, and the sibling branches return Err for an EnrichmentParameters InputTemplate ("which this emulator does not render yet") and for a TargetParameters InputTemplate; the module documents that a configuration it cannot serve faithfully "leaves the source untouched". So the pipe reports CurrentState RUNNING while its poller declines to run.
Why: filtering and input templating are the two features most Pipes deployments configure, and a pipe that uses either becomes a silent black hole: DescribePipe says RUNNING, the source backlog is never consumed, nothing reaches the target, and no state, reason, log or metric says why. A client cannot tell "my filter pattern matched nothing" from "this pipe is not implemented", which is exactly the confusion an emulator must not create.
Fix: the filter and input-template stages of the pipes data plane in services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs — evaluate each FilterCriteria pattern as an EventBridge event pattern against the record envelope (dropping and deleting non-matching records rather than refusing the pipe), and render InputTemplate (including <$.…> JSON-path references over the parsed body) in the enrichment and target stages, so resolve_run no longer rejects these configurations wholesale.
Traces: pipes.pipe-filter-blocks-nonmatching-events.

Cause 3 of 3: CreatePipe's refusal of a FIFO queue target with no MessageGroupId reports the wrong fieldList entry — both the field name and the message are the emulator's own wording, not AWS's.
AWS: Smithy (com.amazonaws.pipes): ValidationException is HTTP 400 with members message and fieldList -> ValidationExceptionField{name, message} (both required); PipeTargetSqsQueueParameters.MessageGroupId is optional in the model, so this rule is conditional on a property of another service's resource (whether the Target ARN names a .fifo queue) and is recorded behavior only. The recorded refusal is HTTP 400, error code ValidationException, and its message is the serialized field list {"ValidationErrorFields":[{"Name":"TargetParameters.SqsQueueParameters","Message":"Missing required target parameter."}]} — i.e. AWS reports the absent PARENT member it needed (the fixed text is the member path "TargetParameters.SqsQueueParameters" and the fixed sentence "Missing required target parameter."; neither part is derived from the request, so nothing in it varies per run).
Emulator: same status and error code, different message: {"ValidationErrorFields":[{"Name":"MessageGroupId","Message":"MessageGroupId is required for a FIFO queue target."}]} — the check fails with "the refusal must carry AWS's exact message … got …". The wording comes from services/service-com-amazonaws-pipes-pipes/src/state.rs, where MESSAGE_GROUP_ID_FIELD = "MessageGroupId" and cross_resource_field returns validation_field(MESSAGE_GROUP_ID_FIELD, "MessageGroupId is required for a FIFO queue target.") (the FIFO branch around lines 601-616), reached from create_pipe.rs via crate::state::cross_resource_violation and from UpdatePipe through the same helper.
Why: the fieldList is machine-read. A client that keys off Name to point the user at the member it must supply, or that asserts on the documented sentence, gets a field path AWS never emits ("MessageGroupId" instead of the "TargetParameters.SqsQueueParameters" path) and a message that will not match; CloudFormation/CDK error surfacing and any retry-with-correction logic built on the field path diverge.
Fix: the shared cross-resource validation in services/service-com-amazonaws-pipes-pipes/src/state.rs (the FIFO-target branch of cross_resource_field, used by both CreatePipe and UpdatePipe) — report the parent member path AWS names with AWS's fixed sentence, keeping status 400 and code ValidationException.
