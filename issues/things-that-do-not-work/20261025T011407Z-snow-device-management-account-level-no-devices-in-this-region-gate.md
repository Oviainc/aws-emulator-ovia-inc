# Account-level "no devices in this region" gate is not enforced: device/task reads and CreateTask/CancelTask answer 200 or 404 ResourceNotFoundException instead of 403 AccessDeniedException

> _Note: this issue was identified against the code base at commit `e5b04c00ada8052fad6ddec319a50738ff12651d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDevices, ListTasks, DescribeDevice, DescribeTask, DescribeDeviceEc2Instances, ListDeviceResources, ListExecutions, DescribeExecution, CreateTask, CancelTask

## Description
The behavioral suite exercises a Snow Device Management account/region in which no Snow device has Snow Device Management activated. In that state the service evaluates an account/region-level precondition ("No devices found in this region.") BEFORE any per-resource id resolution and before any field-level validation, and refuses every device/task read, list and invoke API with 403 AccessDeniedException. The emulator has no such precondition: each handler goes straight to its own (empty) regional store and answers either HTTP 200 with an empty page (collection operations) or 404 ResourceNotFoundException (id-addressed operations). 8 of 11 behavioral checks fail on exactly this.

This is the same missing precondition the OPEN wire issue 20261025T004003Z-snow-device-management-ignores-the-account-level-no reports from the wire corpus; that issue does not carry these behavioral replay keys, and the report marked none of these checks as owned or already filed, so they are filed here with their own check ids so a fixer can re-replay them. Historical context: the resolved issue 20261022T034615Z-snow-device-management-the-account-level-no-devices once asked for this gate, and the later resolved issues 20261024T151437Z-snow-device-management-describedevice-error-response and ...-describedeviceec2instances-error-response asked for the OPPOSITE (ResourceNotFoundException in place of the 403) — which is precisely the behavior observed now. The still-open 20261024T151437Z-snow-device-management-listdevices-wrong-behavior / ...-listtasks-wrong-behavior likewise ask for an empty list where the gate is owed. The recorded/replayed behavior is the authority: the gate must be restored ahead of per-resource resolution and ahead of input validation for all ten gated operations. Two causes below; both must be closed before this issue is submitted.

=== Cause 1 of 2: collection operations answer 200 with an empty page instead of the 403 gate ===
AWS: ListDevices and ListTasks on a gated account are refused, not answered — HTTP 403, error code AccessDeniedException, message "No devices found in this region." (Smithy: ListDevices/ListTasks errors are AccessDeniedException errorKind client @httpError 403, ThrottlingException 429, ValidationException 400, InternalServerException 500 — a gated account has no success representation here). The refusal is independent of the request's filters and is stable over time: the gate also outranks any field-level validation of the jobId filter, so a syntactically bogus jobId ("not a valid job id!!") and a plausible one both surface the identical AccessDeniedException with the identical message — the emulator must NOT invent a ValidationException for the malformed filter. Repeated sampling over ~15s yields the same code and the same message every time (no flapping, no "devices provisioned in the background" resolution).
Emulator: ListDevices returns HTTP 200 with {"devices": []} and no error header, for both a bare call and a call carrying a malformed jobId filter; repeated sampling returns 200 every time (the check observed four (None, None) samples, i.e. four successes). ListTasks is reached through the same path.
Why: the client's negative path is never taken. Code that must learn "this account/region is not enabled for Snow Device Management" instead reads "this account genuinely owns zero devices" — a different fact that silently suppresses the enablement error, and a retry/provisioning loop keyed on the 403 never runs.
Fix: the ListDevices and ListTasks handlers, plus a shared account/region precondition in the service state module that the handlers consult before enumerating their store and before validating filters.
Traces: snow-device-management.account-device-gate-blocks-all-reads (list_devices/list_tasks), snow-device-management.list-devices-param-validation, snow-device-management.service-gate-error-stable-not-flaky.

=== Cause 2 of 2: id-addressed operations answer 404 ResourceNotFoundException instead of the 403 gate ===
AWS: on a gated account DescribeDevice, DescribeTask, DescribeDeviceEc2Instances, ListDeviceResources, ListExecutions, DescribeExecution, CreateTask and CancelTask are all refused by the account gate ahead of id resolution — HTTP 403, error code AccessDeniedException, message "No devices found in this region." (Smithy: each of these operations declares both AccessDeniedException @httpError 403 and ResourceNotFoundException @httpError 404; the gate outranks the existence check, so a caller on a gated account never learns whether a specific device/task id exists). The gate also precedes field-level validation on DescribeDeviceEc2Instances: a malformed instance id, a well-formed-but-nonexistent one, and an empty instanceIds list all produce the identical 403/AccessDeniedException with the identical message. The refusal is deterministic: repeated CancelTask calls over several seconds, and 8 concurrent CreateTask calls against the same nonexistent target, all return the same code with no racing success or alternate code. By contrast TagResource/UntagResource/ListTagsForResource are NOT gated (Smithy: they do not declare AccessDeniedException at all; only ResourceNotFoundException 404 and ValidationException 400) and must still reach the per-resource existence check — the asymmetry is part of the contract.
Emulator: every one of these answers 404 with error code ResourceNotFoundException and a body naming the unresolved id, e.g. "managed-device <id> not found" / "task <id> not found" (messages quoted as examples; the requirements are the 403 status and the AccessDeniedException code). Observed identically for CreateTask (single and 8-way concurrent), CancelTask (3 samples), DescribeDevice, DescribeTask and DescribeDeviceEc2Instances (malformed, well-formed and empty instanceIds alike).
Why: a client cannot distinguish "account/region not enabled" (403, not fixable by supplying a different id) from "that id does not exist" (404) and takes the wrong branch; retry/idempotency logic keyed on 404 loops on a condition that never resolves; and the inverted ordering leaks per-id existence that AWS does not disclose on a gated account.
Fix: the CreateTask, CancelTask, DescribeDevice, DescribeTask, DescribeDeviceEc2Instances, ListDeviceResources, ListExecutions and DescribeExecution handlers — consult the shared account/region precondition in the service state module before resolving ids and before input validation; leave the tag handlers ungated.
Traces: snow-device-management.create-task-device-gate-precedes-validation, snow-device-management.create-task-concurrent-calls-consistent-gate, snow-device-management.cancel-task-device-gate-and-idempotency, snow-device-management.describe-device-ec2-instances-validation, snow-device-management.tag-apis-bypass-device-gate-notfound (fails on its describe_device positive control), snow-device-management.account-device-gate-blocks-all-reads.
