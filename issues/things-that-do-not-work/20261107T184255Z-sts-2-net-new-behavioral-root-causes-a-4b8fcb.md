=== Cause 1 of 2: a session tag that is NOT listed in TransitiveTagKeys satisfies an aws:PrincipalTag condition in the chained session, so a role-chained session is granted what only the first hop's tag allows ===
AWS: Smithy com.amazonaws.sts#AssumeRole input carries Tags (tagListType, @length 0..50) and TransitiveTagKeys (tagKeyListType, @length 0..50), documented as: "A list of keys for session tags that you want to set as transitive. If you set a tag key as transitive, the corresponding key and value passes to subsequent sessions in a role chain. ... If you choose not to specify a transitive tag key, then no tags are passed from this session to any subsequent sessions." (ref: IAM User Guide id_session-tags.html#id_session-tags_role-chaining). So in a chain A -> B where hop 1 passed Tags [T1=v1, T2=v2] with TransitiveTagKeys [T1]: in the hop-2 session, aws:PrincipalTag/T1 is v1 and aws:PrincipalTag/T2 DOES NOT EXIST. A hop-2 inline session policy whose only Allow for s3:ListAllMyBuckets is conditioned StringEquals {aws:PrincipalTag/T2: v2} therefore grants nothing, and the call is refused AccessDenied / HTTP 403 (an absent condition key never satisfies StringEquals); the same policy conditioned on aws:PrincipalTag/T1 grants, and the call answers 200.
Emulator: the non-transitive tag's condition is satisfied in the chained session — s3:ListAllMyBuckets under the hop-2 session whose session policy is conditioned on aws:PrincipalTag/<non-transitive key> SUCCEEDS (200) and keeps succeeding for the whole 60 s poll ('(no error: the call succeeded)' is the last observation). The legs around it PASS in the same run, which bounds the defect tightly: the chained AssumeRole into a target role that trusts only sts:AssumeRole (not sts:TagSession) is correctly refused AccessDenied with "User: <hop-1 session ARN> is not authorized to perform: sts:TagSession on resource: <target role ARN>", and the transitive tag's condition correctly ALLOWS. Hypothesis (neither the model nor the recording states which half is at fault): either every session tag is forwarded across the chained AssumeRole regardless of TransitiveTagKeys, or the chained session's session-policy Condition is not evaluated at all and the statement grants as if unconditioned — the sibling check sts.assume-role-session-tag-decides-policy-condition (already carried by 20261029T120000Z, not claimed here) shows a MISMATCHED value of a tag that IS present also allowing, which points at the condition evaluation.
Why: this is over-permissive in the exact place clients use session tags as a tenancy boundary. A chained session is handed a tag it must not carry, so a least-privilege design that scopes hop 2 by aws:PrincipalTag ("only the tenant the first hop was tagged with") grants every tenant here, and a regression that widens tag propagation is undetectable against this emulator. The transitive/non-transitive distinction — the whole point of TransitiveTagKeys — has no observable effect.
Fix: the AssumeRole handler's session-minting path and the session record it writes (the chained-assume branch must copy forward ONLY the tags whose keys the parent session recorded as transitive, and must record the new session's transitive set), together with the aws:PrincipalTag/<key> publication and Condition evaluation used when a later service authorizes a request signed with that session credential (an absent key must leave a StringEquals clause undecided and withhold the grant).
Traces: sts.assume-role-transitive-tag-survives-role-chaining.

=== Cause 2 of 2: an ec2:RunInstances DryRun that a session policy explicitly denies answers DryRunOperation instead of UnauthorizedOperation, and no "Encoded authorization failure message:" is ever produced, so DecodeAuthorizationMessage's positive control and its invalid-input refusal are both unreachable ===
AWS: Smithy com.amazonaws.ec2#RunInstancesRequest$DryRun — "Checks whether you have the required permissions for the operation, without actually making the request, and provides an error response. If you have the required permissions, the error response is DryRunOperation. Otherwise, it is UnauthorizedOperation." So DryRun is an authorization probe, and an explicit Deny in the AssumeRole inline session policy (AssumeRole.Policy, sessionPolicyDocumentType) decides it. Recorded behavior for the sentence: HTTP 403, code UnauthorizedOperation, message "You are not authorized to perform this operation. User: <assumed-role session ARN> is not authorized to perform: ec2:RunInstances on resource: arn:aws:ec2:<region>:<account>:instance/* with an explicit deny in a session policy. Encoded authorization failure message: <blob>" — fixed text is "You are not authorized to perform this operation. User: ", " is not authorized to perform: ", " on resource: ", the deny-classification clause " with an explicit deny in a session policy." and the trailer "Encoded authorization failure message: "; the variable parts are the session ARN, the action, the instance ARN built from the request's region/account, and the per-failure blob. Smithy com.amazonaws.sts#DecodeAuthorizationMessage then decodes that blob (input EncodedMessage @required @length 1..10240; output DecodedMessage; its documentation: "if a user is not authorized to perform an operation ... the request returns a Client.UnauthorizedOperation response (an HTTP 403 response). Some Amazon Web Services operations additionally return an encoded message" and the decoded message includes "Whether the request was denied due to an explicit deny", "The principal who made the request", "The requested action", "The requested resource", "The values of condition keys in the context of the user's request"), i.e. allowed=false, explicitDeny=true, context.principal.arn/id = the session ARN and the AssumedRoleId AssumeRole returned, context.action = the BARE operation name "RunInstances", context.resource = the instance ARN, context.conditions carrying the keys EC2 derived from the request (ec2:InstanceType = the type this request asked for), and exactly one matchedStatements item with effect DENY naming the service-qualified action and this session's principal id. A malformed EncodedMessage is refused with InvalidAuthorizationMessageException (Smithy: errorKind client, httpError 400, awsQueryError code InvalidAuthorizationMessageException/400) whose message is "Message is not valid: [<the base64url-decoded input as signed decimal bytes, comma-separated>]" — fixed text "Message is not valid: [" ... "]" with the byte list determined entirely by the submitted input.
Emulator: the denied DryRun is never refused. Under a session whose inline session policy is [Allow ec2:DescribeInstances+ec2:RunInstances on *, Deny ec2:RunInstances on *] — with the role's own identity policy allowing "*", and with the Allow half proven live first (DescribeInstances answers 200 on the same credentials) — RunInstances(DryRun=true) answers the DryRunOperation error "Request would have succeeded, but DryRun flag is set." and keeps answering it for the whole 240 s poll, so the checks exhaust their budget ("Check timed out after 180.0s"; the sibling round-trip check reports its last observation verbatim as 'Request would have succeeded, but DryRun flag is set.'). Consequently no encoded authorization failure message is ever minted anywhere, the genuine DecodeAuthorizationMessage round trip (allowed=false / explicitDeny=true / the decoded principal, action, resource, condition keys and matched DENY statement) is unreachable, and the InvalidAuthorizationMessageException leg that must follow that positive control is never reached either.
Why: DryRun exists so a caller can test a grant without creating anything, and DryRunOperation is read as positive confirmation — so every unauthorized principal is told it IS authorized, and preflight checks, policy-tightening CI gates and least-privilege reviews pass here and fail in AWS. Separately, the entire authorization-diagnostics path is dead: a client that captures "Encoded authorization failure message:" from a 403 and calls sts:DecodeAuthorizationMessage to find out WHICH statement denied it gets no blob to decode, so troubleshooting tooling built on that loop cannot be exercised at all, and an implementation that rejects every decode request would be indistinguishable from a correct one.
Fix: EC2's RunInstances handler must run the normal request authorization — the intersection of the role's identity policy, the session policy and the permissions boundary, with an explicit Deny winning — BEFORE taking its DryRun shortcut, and serialize HTTP 403 / UnauthorizedOperation with the sentence above (including the deny-classification clause and the encoded trailer) when it does not allow, answering DryRunOperation only when it does; the shared request-authorization gate must mint the encoded blob from the decision it already made (principal ARN + AssumedRoleId, bare action name, request-derived resource ARN, the request's condition keys, and the matched statement with its effect/actions/principals) so that the STS DecodeAuthorizationMessage handler decodes a genuine message to that content, and that handler's invalid-input path must keep refusing InvalidAuthorizationMessageException / 400 with the "Message is not valid: [...]" sentence.
Traces: sts.encoded-authorization-failure-message-decodes-to-the-denied-principal-and-action, sts.decode-authorization-message-invalid-rejected.
