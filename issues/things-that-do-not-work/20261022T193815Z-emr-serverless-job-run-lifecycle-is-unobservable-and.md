# EMR Serverless job-run lifecycle is unobservable and terminal-FAILED, UpdateApplication refuses documented running-application updates, and autoStopConfiguration never stops an idle application (4 causes)

> _Note: this issue was identified against the code base at commit `17f16131651e3a76635c083c093a8581359ec045`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartJobRun

## Description
Four root causes in the EMR Serverless control plane the emulator DOES serve (all four are reached after successful calls, so they are fidelity divergences rather than scaffold gaps).

NOTE on overlap: open issue 20261022T154846Z-emr-enum-filter-refusals-use-unmodeled-validationexception-runjobflow.md describes the same "job runs never execute" effect as its Cause 4, but it is filed under the `emr` service token and carries only the `emr.*` replay keys (emr.emr-serverless-spark-job-run-reaches-success, emr.emr-serverless-failing-script-reports-failed-and-writes-no-output). None of the six checks below are marked OWNED by it, and Causes 2-4 here are not described there at all, so they are filed here against the emr-serverless service.

Cause 1 of 4: a job run never reaches RUNNING or SUCCESS — every submitted run settles in FAILED because nothing executes.
AWS: StartJobRun on a STARTED application runs the submitted driver; GetJobRun/ListJobRuns report the run moving through the modelled JobRunState values up to RUNNING and then SUCCESS for a driver that exits 0 (Smithy: JobRunState = SUBMITTED | PENDING | SCHEDULED | RUNNING | SUCCESS | FAILED | CANCELLING | CANCELLED; JobRun$state required, JobRun$stateDetails). Recorded behavior: a trivial Spark entry point reaches state SUCCESS and the artifacts the script writes exist in S3.
Emulator: the run is driven by a fixed stage ladder whose last entry is the failure state — PENDING -> QUEUED -> SCHEDULED -> FAILED — with stateDetails "This emulator records job runs but executes no Spark or Hive workload, so the job run ended without running." (example text). RUNNING and SUCCESS are never reachable for any input.
Why: a client cannot distinguish success from failure at all, because both end FAILED. Every happy-path orchestration built on EMR Serverless inverts against the emulator: wait-for-success loops never succeed, and a negative check that proves a permission denial cannot be grounded because its positive control fails identically (see emr-serverless.spark-write-outside-execution-role-prefix-is-denied, whose own assertion message says the fixture is broken so the denial below proves nothing).
Fix: the job-run state machine in services/service-com-amazonaws-emrserverless-awstoledowebservice/src/state.rs (JOB_RUN_STAGES / job_run_stages) together with services/service-com-amazonaws-emrserverless-awstoledowebservice/src/ops/start_job_run.rs — a recorded-only run should still converge through RUNNING to SUCCESS for a well-formed jobDriver, and reserve FAILED for runs the request itself makes unrunnable.
Traces: emr-serverless.start-job-run-native-spark-execution-succeeds, emr-serverless.spark-shuffle-partitioned-parquet-roundtrip, emr-serverless.spark-write-outside-execution-role-prefix-is-denied.

Cause 2 of 4: the in-flight window of a job run is too short to be observed, so CancelJobRun can never be seen driving a run to CANCELLED and ListJobRuns(states=[non-terminal...]) reports nothing for a run that was just submitted.
AWS: a submitted run stays non-terminal for as long as the work takes; CancelJobRun (Smithy: DELETE /applications/{applicationId}/jobruns/{jobRunId}, errors ValidationException 400 / ResourceNotFoundException 404) on a run that is PENDING/SCHEDULED/RUNNING moves it through CANCELLING to the terminal CANCELLED, and ListJobRuns with states=[SUBMITTED,PENDING,SCHEDULED,QUEUED,RUNNING] (states is a JobRunStateSet, @length 0..8, @uniqueItems) includes that still-running run.
Emulator: each stage of the ladder lasts JOB_RUN_STAGE_TRANSITION = 750 ms, so a run is terminal (FAILED) roughly 3 seconds after StartJobRun returns regardless of the submitted work. A client polling on any realistic interval observes only the terminal state: the cancel check never sees SCHEDULED/RUNNING/PENDING and hangs until the harness kills it, and the state-filtered listing returns an empty set for a run submitted seconds earlier (the state filter itself is a plain membership test in src/ops/list_job_runs.rs and works for CANCELLED, so the divergence is the state, not the filter).
Why: cancellation and state-filtered inventory — the two things clients use to manage in-flight batch work — are unexercisable. A cancel arrives at an already-terminal run, so CANCELLED is never produced, and dashboards/pollers that list non-terminal runs always see none.
Fix: the stage timing and cancellation path in services/service-com-amazonaws-emrserverless-awstoledowebservice/src/state.rs (JOB_RUN_STAGE_TRANSITION, JOB_RUN_STAGES, JobRunRecord::settle) and src/ops/cancel_job_run.rs — a run must remain non-terminal long enough for a client to observe and cancel it, and a cancel of a non-terminal run must settle on CANCELLED.
Traces: emr-serverless.cancel-job-run-transitions-to-cancelled, emr-serverless.list-job-runs-filters-by-state.

Cause 3 of 4: UpdateApplication refuses EVERY update while the application is STARTED, including the running-application updates AWS accepts.
AWS: UpdateApplication (Smithy: PATCH /applications/{applicationId}; errors ValidationException 400, ResourceNotFoundException 404, InternalServerException 500) accepts a documented subset of members on a STARTED application and returns 200 with the updated Application; maximumCapacity (MaximumAllowedResources) is one of them, and the application stays STARTED across it. Recorded behavior: UpdateApplication(maximumCapacity={cpu:8vCPU,memory:16GB}) on a STARTED application succeeds, while UpdateApplication(releaseLabel=...) on the same application is refused 400 ValidationException whose message enumerates the updatable set (example: "Only the following configurations can be updated when an application is in STARTED state: schedulerConfiguration.maxConcurrentRuns, extendedSupportConfiguration, imageConfiguration, workerTypeSpecifications.imageConfiguration, maximumCapacity.").
Emulator: the handler gates on UPDATABLE_APPLICATION_STATES before looking at which members the request names and answers 400 ValidationException "Application is in STARTED state; an application has to be in CREATED or STOPPED state in order to be updated" for any member, so the capacity update fails. (The operation-level model doc only says an application has to be stopped or created to be updated; the member-level carve-out is the recorded behavior above.)
Why: a client that resizes a running application — the normal way maximumCapacity is managed — gets a 400 instead of a 200 and must stop the application, which changes the workload's availability. Autoscaling/capacity-management code paths cannot run at all against the emulator.
Fix: the state precondition in services/service-com-amazonaws-emrserverless-awstoledowebservice/src/ops/update_application.rs — judge the precondition per NAMED member rather than per request, admitting the running-application members on a STARTED application and refusing only the others.
Traces: emr-serverless.update-application-while-started-rejected.

Cause 4 of 4: an application with autoStopConfiguration enabled is never observed stopping itself when idle.
AWS: AutoStopConfig (enabled, idleTimeoutMinutes @range 1..10080) makes the service move an idle application from STARTED to STOPPED once the idle span elapses, with no StopApplication call; GetApplication then reports state STOPPED.
Emulator: the auto-stop due instant is computed as last_activity_at + idleTimeoutMinutes in real wall-clock minutes (state.rs: ApplicationRecord::auto_stop_due / idle_timeout), while every other transition in this service is deliberately compressed to sub-second (LIFECYCLE_TRANSITION = 500 ms, JOB_RUN_STAGE_TRANSITION = 750 ms). With the documented minimum idleTimeoutMinutes=1 the application therefore still reports STARTED for the whole observation window and the check times out without ever seeing STOPPED. Hypothesis: the idle span is the one clock in this service that was left un-compressed, so the transition is modelled but unreachable in a replay.
Why: a client (or a test) that relies on idle applications releasing capacity on their own never observes the STOPPED state, so cost-control and lifecycle logic keyed on auto-stop is unexercisable; a follow-on call that requires a STOPPED application (e.g. UpdateApplication, see Cause 3) also never becomes admissible.
Fix: the auto-stop clock in services/service-com-amazonaws-emrserverless-awstoledowebservice/src/state.rs (ApplicationRecord::auto_stop_due / idle_timeout, and its materialisation in ApplicationRecord::settle) — scale the idle span the same way the other transitions of this service are scaled so the modelled STOPPED transition is actually reachable.
Traces: emr-serverless.auto-stop-configuration-stops-idle-application.
