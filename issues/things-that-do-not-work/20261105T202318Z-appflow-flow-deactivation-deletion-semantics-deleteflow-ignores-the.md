# AppFlow flow deactivation/deletion semantics: DeleteFlow ignores the Active-flow conflict, StopFlow is unimplemented, and the DescribeFlow not-found sentence is emulator prose

> _Note: this issue was identified against the code base at commit `a6bd8162e254cd53a71309df843cd006b7af8737`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteFlow

## Description
Three independent root causes in the AppFlow control plane around deactivating and deleting a flow. 3 causes.

Cause 1 of 3: DeleteFlow without forceDelete on an Active flow is accepted instead of rejected with ConflictException.
AWS: Smithy: DeleteFlow input flowName (@required) and forceDelete (Boolean, @default false); modeled errors ConflictException (httpError 409, "There was a conflict when processing the request... Check for conflicting resource names and try again."), ResourceNotFoundException (404), InternalServerException (500); http POST /delete-flow, success code 200 with an empty DeleteFlowResponse. Recorded behavior for the text: when the named flow's flowStatus is Active and forceDelete is absent/false, AWS refuses the call with 409 / ConflictException and the message whose FIXED text is "Conflict executing request: Flow is in active state, please set forceDelete to true or deactivate the flow: " followed by the one VARIABLE part, the flowName taken verbatim from the request. The flow is left untouched, so a following DescribeFlow still reports flowStatus Active. Once the flow is deactivated (flowStatus Suspended, see FlowStatus enum Active|Deprecated|Deleted|Draft|Errored|Suspended), the identical DeleteFlow call — still without forceDelete — succeeds with 200.
Emulator: the un-forced DeleteFlow on an Active flow returns HTTP 200 with an empty JSON body ({}), i.e. no conflict check at all: the delete is performed unconditionally regardless of flowStatus and regardless of forceDelete.
Why: forceDelete is the client's explicit opt-in to destroying a running flow. A client that relies on AWS refusing the unforced delete (a guard-rail delete, a "delete only if idle" reconciler, an IaC destroy that first expects the conflict and then suspends the flow) silently destroys a live, executing flow against the emulator — an irreversible overly-permissive outcome that real AWS prevents, and the client never sees the 409 it is coded to handle.
Fix: the appflow DeleteFlow handler — its pre-delete state check must consult the flow's flowStatus and the request's forceDelete (defaulting to false) and raise ConflictException(409) with the message above before mutating state; only forceDelete=true or a non-Active flow may proceed to the state removal.
Traces: appflow.delete-active-flow-without-force-rejected.

Cause 2 of 3: StopFlow is not implemented, so flow deactivation and its state-conflict rejections are unreachable.
AWS: Smithy: StopFlow input flowName (@required); output flowArn + flowStatus (FlowStatus enum); modeled errors ConflictException (409), ResourceNotFoundException (404), UnsupportedOperationException (400), InternalServerException (500); http POST /stop-flow, 200. On a Scheduled flow in Active state StopFlow succeeds with 200 and returns flowStatus "Suspended", and a subsequent DescribeFlow reports Suspended. StopFlow is rejected as a state conflict in two cases — a flow whose trigger is OnDemand (never activatable/deactivatable) and a Scheduled flow already Suspended — with 409 / ConflictException whose FIXED text is "Conflict executing request: Flow is already deactivated: " plus the single VARIABLE part, the flowName from the request; the flow's status is unchanged by the rejected call. Resuming the flow with StartFlow makes the identical StopFlow call succeed again, so the rejection is about the current state, not about the flow.
Emulator: every StopFlow call answers with error code "NotImplemented" (the operation is an unimplemented scaffold stub in services/service-com-amazonaws-appflow-sandstoneconfigurationservicelambda/src/ops/stop_flow.rs), so neither the successful Active->Suspended transition nor either ConflictException rejection exists. A scaffold-stub issue for the StopFlow operation has been filed from the checkout and is this cause's prerequisite; this cause records the state-machine semantics that implementation must satisfy, which that stub issue does not state.
Why: a client cannot deactivate a flow at all, and because StopFlow never returns, the whole Active/Suspended lifecycle (and the unforced-delete path in Cause 1, which requires Suspended) is unreachable; a client that distinguishes "already deactivated" (ConflictException) from a real failure gets an unmodelled NotImplemented instead.
Fix: the appflow StopFlow handler and the flow state machine it reads/writes — implement the Active->Suspended transition returning flowArn + flowStatus, and the two ConflictException(409) rejections for OnDemand-trigger flows and already-Suspended flows, leaving flowStatus untouched when rejecting.
Traces: appflow.stop-flow-state-conflicts-rejected.

Cause 3 of 3: DescribeFlow's not-found message for a deleted flow is emulator prose, not AWS's sentence.
AWS: Smithy: DescribeFlow has modeled errors ResourceNotFoundException (httpError 404, "The resource specified in the request (such as the source or destination connector profile) is not found.") and InternalServerException (500); ResourceNotFoundException carries one member, message. Recorded behavior only for the text: after the flow is deleted, DescribeFlow answers 404 / ResourceNotFoundException with the FIXED text "There is no flow with the name " followed by the one VARIABLE part, the flowName taken verbatim from the request; StartFlow on the same deleted name answers with the same code and the same sentence.
Emulator: the same 404 and the same error code, but message "No flow named <flowName> exists in this account" — different fixed text, with the flow name interpolated mid-sentence instead of at the end.
Why: a client or test that matches AWS's not-found sentence, or that lifts the flow name out of its documented position in that sentence, does not recognise the emulator's error, so a legitimately absent flow reads as an unclassified failure; the correct status and code make the divergence silent.
Fix: the appflow DescribeFlow handler's lookup-miss branch (and the shared not-found message builder StartFlow uses for the same case) where the ResourceNotFoundException message text is constructed. Note: open issue 20261029T192701Z-appflow-error-message-text-diverges-from-aws-wording.md describes this same wording divergence as its Cause 2 from the wire corpus; this behavioral check is still failing on it, and that issue does not carry this check's replay key.
Traces: appflow.describe-flow-after-delete-not-found.

## Evidence
Cause 1 — check appflow.delete-active-flow-without-force-rejected: after CreateFlow (Scheduled trigger) + StartFlow and waiting for flowStatus Active, DeleteFlow(flowName=<flow>) with no forceDelete was expected to raise ConflictException (409) with message "Conflict executing request: Flow is in active state, please set forceDelete to true or deactivate the flow: <flowName>". Actual: the call SUCCEEDED — HTTPStatusCode 200, content-type application/json, body {} (content-length 2). Harness: AssertionError: expected the call to be rejected, but it SUCCEEDED and returned {'ResponseMetadata': {'HTTPStatusCode': 200, ...}}.

Cause 2 — check appflow.stop-flow-state-conflicts-rejected: StopFlow(flowName=<on-demand flow>) was expected to be refused with code "ConflictException" and message "Conflict executing request: Flow is already deactivated: <flowName>". Actual error code: 'NotImplemented' (AssertionError: expected ConflictException, got 'NotImplemented'). The positive leg (Active Scheduled flow -> StopFlow returns flowStatus "Suspended") and the second rejection (already-Suspended flow) are therefore never exercised.

Cause 3 — check appflow.describe-flow-after-delete-not-found: after DeleteFlow(forceDelete=True), DescribeFlow(flowName=<flow>) returned code ResourceNotFoundException (as expected) but message "No flow named <flowName> exists in this account"; expected "There is no flow with the name <flowName>" (AssertionError: No flow named sim2real-af-flow-<id> exists in this account — the id shown is this run's generated name, only the surrounding sentence is the requirement).

Model basis: Smithy DeleteFlow{flowName @required, forceDelete Boolean default false} errors ConflictException(409)/ResourceNotFoundException(404); StopFlow{flowName} -> {flowArn, flowStatus} errors ConflictException(409)/ResourceNotFoundException(404)/UnsupportedOperationException(400); DescribeFlow errors ResourceNotFoundException(404); FlowStatus enum = Active|Deprecated|Deleted|Draft|Errored|Suspended.
