## Description
Wire replay of trace set simparity-wire-aws-v1 against this checkout left 6 diverging steps on neptune-graph, clustering into THREE distinct net-new root causes. All three are in this one service, none is blocked by an unimplemented operation and none is owned by an open issue's replay key. A fixer must close ALL THREE before submitting. Smithy model consulted: services/service-com-amazonaws-neptunegraph-amazonneptunegraph/smithy-model/com-amazonaws-neptunegraph-amazonneptunegraph.json.

=== Cause 1 of 3: the host-prefixed graph data plane must refuse a graph that does not exist as an AUTHENTICATION failure (403 AccessDeniedException, data-plane envelope), not as a control-plane 404 ResourceNotFoundException ===
AWS: GetGraphSummary, GetQuery and CancelQuery are bound to the graph's own data endpoint — Smithy: each carries @endpoint hostPrefix "{graphIdentifier}." with graphIdentifier @hostLabel, pattern ^g-[a-z0-9]{10}$ — and each models AccessDeniedException @httpError 403 ("Raised in case of an authentication or authorization failure") as well as ResourceNotFoundException @httpError 404. Recorded behavior: when graphIdentifier names a graph that does not exist in the account, the request never reaches a resource lookup, because there is no graph endpoint for that host prefix to authenticate the signature against; the call is refused with HTTP 403 and the Neptune Analytics data-plane error envelope, whose JSON body carries `code`, `requestId` and `message` members. Fixed text of the message for this error class is exactly "Authentication Failed"; `code` is the fixed string "AccessDeniedException"; the ONE variable part of the body is `requestId`, a per-request id generated by the service (its value is never part of the requirement). The refusal is identical for all three operations and does not depend on which data-plane operation was attempted, nor on the queryId for the two query operations.
Emulator: all three operations resolve the graph out of the control-plane store inside the handler and report a miss as the control-plane not-found refusal, so the replay gets HTTP 404 with an x-amzn-errortype of ResourceNotFoundException, no `code` member, no `requestId` member, and the message "No graph found for customer [<account>] with graph id [<graphIdentifier>]" where AWS says "Authentication Failed". services/service-com-amazonaws-neptunegraph-amazonneptunegraph/src/ops/get_graph_summary.rs reaches store.settled_graph(...) and on None returns ResourceNotFoundException from crate::state::graph_not_found(&input.graph_identifier); ops/get_query.rs and ops/cancel_query.rs refuse the same way for the same input. So the status class (4xx-not-found vs 4xx-auth), the error code, the error message and the body SHAPE all diverge.
Why: a client that reaches a graph data endpoint for a graph it does not own, mistyped, or that has already been deleted must distinguish "your credentials/endpoint are not accepted" (403, not retryable, re-resolve the endpoint or fix credentials) from "the resource is gone" (404, stop polling). Here every such call is reported as a plain missing resource, and the data-plane envelope the AWS SDKs and Neptune tooling parse for `code`/`requestId` is absent, so error handling keyed on `code` sees no error code at all and support correlation by `requestId` is impossible.
Fix: the graph data-plane front door — the host-prefix dispatch that routes {graphIdentifier}. requests to the host-prefixed operations (GetGraphSummary, GetQuery, CancelQuery and their siblings on that endpoint) — must refuse an unresolvable graph host prefix with the 403 AccessDeniedException "Authentication Failed" refusal and serialize it in the data-plane envelope (code/requestId/message), ahead of the per-handler store lookup in ops/get_graph_summary.rs, ops/get_query.rs and ops/cancel_query.rs; crate::state::graph_not_found must stay the refusal only for control-plane operations addressed by graphIdentifier in the request body/URI.
Traces: neptune-graph-host-prefixed-graph-ops-nonexistent-graph-auth-rejected#task#1 (GetGraphSummary, expected 403 got 404), #task#3 (GetQuery, expected 403 got 404), #task#4 (CancelQuery, expected 403 got 404) — each reports $.code missing (expected 'AccessDeniedException'), $.requestId missing, and $.message 'No graph found for customer [000000000000] with graph id [g-9568964df1]' where 'Authentication Failed' was expected.

=== Cause 2 of 3: CancelImportTask / CancelExportTask word the not-found identifier clause as "<resource> task id" where AWS words it "task id" ===
AWS: CancelImportTask and CancelExportTask refuse an unknown but well-formed taskIdentifier with ResourceNotFoundException (Smithy: both model ResourceNotFoundException @httpError 404; taskIdentifier pattern ^t-[a-z0-9]{10}$, so a well-formed unknown id reaches resource lookup). Recorded behavior: the CANCEL operations spell the identifier clause bare. Fixed text, per operation: "No import task found for customer [" / "No export task found for customer [" + "] with task id [" + "]". Variable parts: the account the lookup resolved in (from the request's credentials) and the taskIdentifier taken verbatim from the request. The READ operations (GetImportTask / GetExportTask) spell it out as "import task id" / "export task id", and those replay steps pass — so the wording differs per operation and must not be shared.
Emulator: both cancel handlers reach the shared not-found builder the reads use, so they inherit the spelled-out clause: src/ops/cancel_import_task.rs returns ResourceNotFoundException from crate::state::import_task_not_found(&input.task_identifier), which goes through crate::state::resource_not_found_for_caller("import task", "id", ...) and formats "No {resource} found for customer [{acct}] with {resource} {identifier_kind} [{id}]" — i.e. "... with import task id [t-0000000000]" where AWS says "... with task id [t-0000000000]". ops/cancel_export_task.rs has the identical structure through export_task_not_found. Status 404 and code ResourceNotFoundException are correct; only the message rule diverges.
Why: a client, retry wrapper or log scraper that matches AWS's refusal text for cancelling a task that no longer exists does not recognise the refusal, and the per-operation wording distinction AWS actually makes between the read and the cancel of a task is erased.
Fix: the not-found wording builders in crate::state (resource_not_found_for_caller / import_task_not_found / export_task_not_found) must let ops/cancel_import_task.rs and ops/cancel_export_task.rs render the bare "task id" identifier clause while ops/get_import_task.rs and ops/get_export_task.rs keep "import task id" / "export task id". NOTE: the same defect was already filed from the BEHAVIORAL corpus as cause 1 of the open issue 20261029T191032Z-neptune-graph-3-net-new-fidelity-causes-cancel.md; that issue carries behavioral check ids only, so these two wire fixture steps are not covered by its replay pointer and are filed here so the wire corpus re-runs them.
Traces: neptune-graph-import-export-task-nonexistent-not-found#task#2 (CancelImportTask, 404 with 'No import task found for customer [000000000000] with import task id [t-0000000000]' where 'No import task found for customer [000000000000] with task id [t-0000000000]' was expected) and #task#4 (CancelExportTask, same divergence with 'export task id' for 'task id').

=== Cause 3 of 3: CreateGraphUsingImportTask accepts an S3 source with no format and creates the task, where AWS refuses the request ===
AWS: CreateGraphUsingImportTask takes a required `source` plus an optional `format` whose documentation is "Specifies the format of S3 data to be imported. Valid values are CSV ..., OPEN_CYPHER ..., or ntriples ..." (Smithy: CreateGraphUsingImportTaskInput.source required String, format enum Format [CSV, OPEN_CYPHER, PARQUET, NTRIPLES]; errors ValidationException @httpError 400, ConflictException 409, ServiceQuotaExceededException 402, ThrottlingException 429, InternalServerException 500; success is HTTP 201). Recorded behavior: when `source` is an S3 location and `format` is omitted, the service cannot infer how to parse the data and refuses the call with HTTP 400 before any graph or task is minted. The message is entirely fixed text for this error class, with no variable part: "Source format should be specified when Source type is S3."
Emulator: the request is ACCEPTED — HTTP 201 with a CreateGraphUsingImportTaskOutput (graphId/taskId minted, status reported) and no body members for a refusal at all ($.message missing, no x-amzn-errortype). src/ops/create_graph_using_import_task.rs collects its handler-enforced violations (graphName pattern, crate::state::import_source_requirement for an empty source, crate::state::blank_node_handling_clause for the format/blankNodeHandling dependency, min/maxProvisionedMemory ordering, crate::state::bound_tags) and none of them states the "format is required for an S3 source" rule, so the omission falls through to the minting path.
Why: a caller that omits `format` gets a graph and an import task id back and then has to discover from task status that the import was never parseable, instead of being told at submit time which member is missing — and because the accept MINTS a graph and a task, the caller is left with resources (and a reserved graphName) AWS would never have created. An over-permissive accept also means a test suite asserting the refusal passes against AWS and fails against the emulator only later, on state.
Fix: the request-validation block of ops/create_graph_using_import_task.rs must refuse an S3 `source` with no `format`, with the 400 refusal worded as above, before the store is reached and before any graph/task is minted; the rule belongs beside the other import-source rules stated once in crate::state (import_source_requirement / blank_node_handling_clause) so StartImportTask, which takes the same source/format pair, cannot drift to a different acceptance set.
Traces: neptune-graph-create-graph-using-import-task-validation-rejected#task#1 — expected 400, got 201.
