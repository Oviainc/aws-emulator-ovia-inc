# MediaConvert: 3 net-new divergences — DeleteQueue in-use refusal message, UpdateJobTemplate SYSTEM refusal message, and no Job State Change event is ever published to EventBridge

> _Note: this issue was identified against the code base at commit `0d251cb15d5c6a3e8a766cb6c72620a30f43ef7f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DeleteQueue

## Description
This issue bundles 3 distinct net-new root causes in the MediaConvert emulator. All 3 must be closed before submitting. None of them is covered by the open issues 20261022T040904Z-mediaconvert-queue-job-control-plane-4-fidelity-divergences.md (which owns CreateQueue idempotency, the unassumable-Role CreateJob acceptance, the Default SYSTEM queue and the UpdateQueue enum message) or 20261024T051247Z-mediaconvert-getjob-wrong-behavior.md (which owns the job lifecycle settling straight to ERROR, not the absence of event publication).

=== Cause 1 of 3: DeleteQueue's in-use ConflictException carries an emulator-authored sentence instead of MediaConvert's fixed remediation text ===
AWS: Smithy: DeleteQueue, DELETE /2017-08-29/queues/{Name}, success 202, Name is an @httpLabel @required __string; modeled errors include ConflictException (httpError 409) documented as "The service couldn't complete your request because there is a conflict with the current state of the resource." The error CODE and status already agree (ConflictException / 409); only the message diverges. Recorded behavior: when the addressed queue still holds a job in SUBMITTED or PROGRESSING, the refusal message is ENTIRELY FIXED TEXT with no request-derived or state-derived slot at all: "The queue is currently in use and cannot be deleted. To resolve: Stop submitting any other requests to modify this queue, and cancel any remaining jobs that are in a SUBMITTED or PROGRESSING state in this queue. Then, resubmit your request." It names neither the queue nor any count.
Emulator: returns ConflictException with a hand-rolled sentence that interpolates the queue name and the two job counters: "Queue <queueName> still has <n> submitted and <m> progressing job(s) and can't be deleted." (<queueName>, <n> and <m> are the only variable parts; the rest is the emulator's own fixed text, which AWS never emits). Observed instance: "Queue sim2real-mc-queue-b6c10d0c02ce still has 1 submitted and 0 progressing job(s) and can't be deleted."
Why: a client or operator-facing tool that matches or surfaces MediaConvert's documented in-use message gets a foreign sentence, and loses the remediation instruction AWS returns (cancel the SUBMITTED/PROGRESSING jobs, then resubmit). Teardown code that keys on the AWS wording to distinguish "queue busy, retry" from other 409s misclassifies the refusal, and the emulator additionally discloses internal job counters AWS does not put in this message.
Fix: the DeleteQueue handler's HasActiveJobs refusal arm — emit MediaConvert's fixed in-use sentence verbatim instead of formatting the queue name and counters. The rest of the check is not in dispute: the code (ConflictException), the surviving queue and job, the restored delete succeeding once the job is CANCELED, and the NotFoundException 404 "The resource you specified in name was not found." afterwards all behave correctly.
Traces: mediaconvert.delete-queue-with-active-job-conflict-rejected. Handler site: services/service-com-amazonaws-mediaconvert-mediaconvert/src/ops/delete_queue.rs lines 197-206.

=== Cause 2 of 3: UpdateJobTemplate's SYSTEM-template refusal reuses the crate's generic system-resource template instead of the job-template-specific sentence AWS returns ===
AWS: Smithy: UpdateJobTemplate, PUT /2017-08-29/jobTemplates/{Name}, success 200, Name is an @httpLabel @required __string; modeled errors include ForbiddenException (httpError 403) documented as "You don't have permissions for this action with the credentials you sent." The JobTemplate$Type documentation states "System or built-in job templates can't be modified or deleted by the user." The error CODE and status already agree (ForbiddenException / 403); only the message diverges. Recorded behavior: UpdateJobTemplate on a built-in SYSTEM template is refused with the fixed sentence "You are not allowed to update system job templates." — all fixed text, with no slot for the template name or the member it arrived in.
Emulator: returns ForbiddenException with the crate's cross-resource system-resource template, "You specified an invalid value for name. You are not allowed to modify system resources." — here the fixed text is the emulator's own generic two-clause sentence and "name" is the member label passed to the shared helper; AWS emits neither clause for this operation. (AWS does use a "You specified an invalid value for name. You are not allowed to delete system resources." shape for the DELETE doors, which is presumably why the shared helper was reused — but the UPDATE door on a job template has its own distinct sentence.)
Why: a client validating that built-in templates are immutable, or surfacing the refusal to an operator, sees a message that names a different rule class ("modify system resources") than the one AWS states ("update system job templates"), so message-keyed assertions and log scrapers that pass against the emulator fail against AWS. Hypothesis: the same generic helper is likely applied to the sibling SYSTEM refusals (UpdatePreset/DeleteJobTemplate/DeletePreset); only the UpdateJobTemplate door is evidenced by a failing check here, so only it is the claim.
Fix: the UpdateJobTemplate handler's SYSTEM-template refusal arm (it currently calls the shared crate::state::system_resource_modify_message("name") helper) — give the job-template update door MediaConvert's own fixed sentence rather than the crate-wide generic one. The remainder of the check is not in dispute: the code (ForbiddenException), the template's Description being left unchanged, and the CUSTOM-template positive control all behave correctly.
Traces: mediaconvert.update-system-job-template-conflict-rejected. Handler site: services/service-com-amazonaws-mediaconvert-mediaconvert/src/ops/update_job_template.rs lines 254-259.

=== Cause 3 of 3: MediaConvert publishes no "MediaConvert Job State Change" event, so a wired EventBridge rule target never receives a job event ===
AWS: recorded behavior only (the Smithy model does not describe event publication; it does model UpdateJobTemplate/CreateJob StatusUpdateInterval as "how often MediaConvert sends STATUS_UPDATE events to Amazon CloudWatch Events", which establishes that the service is an event source). Recorded behavior: once a job begins processing, MediaConvert publishes events to the account's default EventBridge bus with source "aws.mediaconvert" and detail-type "MediaConvert Job State Change", whose detail carries at least jobId and status; a job that reaches ERROR therefore delivers an event with detail.status == "ERROR" and detail.jobId == the job's Id to any rule target matching that pattern (here an SQS queue whose resource policy grants events.amazonaws.com sqs:SendMessage for that rule ARN). A job canceled before it begins processing emits no event at all.
Emulator: no such event is ever published. With the rule, the SQS target and the matching queue policy all in place (PutTargets reports FailedEntryCount 0) and the job reaching a terminal state on the control plane, the bounded poll of the target queue never observes any message for the job, so both checks that depend on that delivery exhaust their window and are killed by the harness timeout ("Check timed out after 60.0s") rather than observing the event. Nothing in the MediaConvert crate's state module or job-lifecycle settling path has an event-publication seam at all — the job status transition is applied to the store only.
Why: the entire MediaConvert eventing contract is unobservable. A client that drives work off job-state-change events (an EventBridge rule fanning out to SQS/Lambda/Step Functions, a post-processing pipeline triggered on COMPLETE/ERROR, an alarm on ERROR) sees a job finish on the control plane while nothing downstream ever fires; code that waits on the event hangs instead of failing fast. It also makes the negative side of the contract unverifiable: a target with NO queue policy and a target WITH one are indistinguishable when nothing is ever delivered, so a missing-resource-policy regression cannot be caught.
Fix: the MediaConvert job lifecycle — the state module's job status-transition/settling path plus a publish seam onto the emulator's EventBridge default bus — must emit a "MediaConvert Job State Change" event (source "aws.mediaconvert", detail carrying jobId and the new status) at each state transition a processing job makes, and emit none for a job canceled before it began processing. Note on the second trace: mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected also spends part of its window on an intentional 45s negative poll, so its timeout is partly structural; it is listed because it cannot pass without this publication either, and its positive control is the same missing delivery. The grounding evidence for the cause itself is mediaconvert.job-canceled-event-delivered-via-eventbridge, whose only unbounded wait is the poll for the ERROR event that never arrives.
Traces: mediaconvert.job-canceled-event-delivered-via-eventbridge, mediaconvert.eventbridge-delivery-blocked-without-queue-policy-rejected.
