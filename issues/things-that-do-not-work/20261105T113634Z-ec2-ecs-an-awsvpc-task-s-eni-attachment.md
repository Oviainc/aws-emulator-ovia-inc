# ec2__ecs: an awsvpc task's ENI attachment names a networkInterfaceId EC2 does not have, and the VPC it ran in cannot be torn down (2 causes)

> _Note: this issue was identified against the code base at commit `9fc0802c1fad78cd4c44ae6731253718bd889678`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RunTask

## Description
Two root causes, both reached by the single failing behavioral check ec2__ecs.awsvpc-task-eni-matches-the-ec2-view-and-is-released-on-stop. A fixer must close BOTH before submitting: cause 1 is the assertion that fails, cause 2 is the in-band teardown that fails the same check even once cause 1 is fixed.

Cause 1 of 2: ECS reports an ElasticNetworkInterface attachment for a RUNNING awsvpc task whose networkInterfaceId is not a network interface EC2 knows about — ECS never allocates the task ENI through the EC2 service, it only fabricates an id for the attachment detail.
AWS: Smithy com.amazonaws.ecs#Attachment.details documents that "For elastic network interfaces, this includes the network interface ID, the MAC address, the subnet ID, and the private IPv4 address", and Attachment.status's valid values include ATTACHED. On real AWS the id in that detail is a real EC2 network interface: Smithy com.amazonaws.ec2#DescribeNetworkInterfaces (no modelled errors; 200 with DescribeNetworkInterfacesResult) returns it, and the returned com.amazonaws.ec2#NetworkInterface agrees with the ECS attachment member-for-member — PrivateIpAddress == privateIPv4Address, SubnetId == subnetId, MacAddress == macAddress, VpcId is the task's VPC, Status is 'in-use', Attachment.Status is 'attached', Groups is exactly the security-group set RunTask was given, RequesterManaged is true ("Indicates whether the network interface is being managed by Amazon Web Services") and InterfaceType is 'interface'. Because that interface exists and holds an address, the subnet's AvailableIpAddressCount drops by exactly one while the task runs; DeleteNetworkInterface on it is refused (recorded behavior: 400 InvalidParameterValue, message "Network interface '<eni-id>' is currently in use." — fixed text with the requested interface id substituted), while the same call on an interface the account created in that subnet succeeds; and after StopTask the ENI is deleted and the address returns to the pool.
Emulator: DescribeTasks reports the attachment as type ElasticNetworkInterface / status ATTACHED carrying all four detail names, but the networkInterfaceId it names does not exist in EC2 — DescribeNetworkInterfaces on it is refused InvalidNetworkInterfaceID.NotFound (the check's _describe_eni maps that code to None and the assertion fires: "ECS reports networkInterfaceId 'eni-00000000000000001' for the RUNNING task, but EC2 has no such interface — the attachment names an ENI that does not exist"). The id is a counter-shaped placeholder, not an interface allocated in the task's subnet, so none of the joined assertions downstream can hold either: no in-use interface, no address consumed from the subnet, no in-use DeleteNetworkInterface refusal, and nothing to delete on StopTask.
Why: a client cannot join the ECS view of a task to the EC2 view of its network. Nothing that depends on the task's real interface works: resolving the task's private address, registering it as an ip target behind an ALB/NLB, attributing subnet address consumption, auditing or protecting the interface, or observing its release when the task stops. Worse, the attachment reads as ATTACHED and fully populated, so the client has no signal that the id is fictional — it fails later at an EC2 call with a not-found.
Fix: the ECS task-materialisation/attachment path for networkMode=awsvpc (the RunTask handler and the task-state model it writes), which must allocate a real interface in the named subnet through the EC2 service's network-interface state — requester-managed, carrying the given security groups, holding one subnet address, reported in-use/attached by EC2 and protected from DeleteNetworkInterface while attached — and must delete that interface and release the address when the task reaches STOPPED. Note the open issue 20261104T062603Z-ecs-awsvpc-task-enis-never-attach-the-elasticnetworkinterface.md describes the earlier symptom of this surface (attachment stuck PRECREATED with only subnetId, no connectivity) under the `ecs` suite; it does not cover and does not carry this check's replay key — the attachment now reaches ATTACHED with all four details, and the remaining defect is that the id in it is not a real EC2 interface.

Cause 2 of 2: the VPC this check builds cannot be removed, so the check's in-band teardown reports a leak and fails the run regardless of cause 1.
AWS: Smithy com.amazonaws.ec2#DetachInternetGateway and #DeleteInternetGateway declare no modelled errors and answer an empty 200 once the gateway has no dependencies; DeleteVpc then succeeds and DescribeVpcs no longer returns the VPC. DependencyViolation is AWS's answer only for a VPC that still has dependencies.
Emulator: DetachInternetGateway and DeleteInternetGateway both answer NotImplemented, and DeleteVpc then answers DependencyViolation — reported verbatim by the teardown as "['detach-igw: NotImplemented', 'delete-igw igw-...: NotImplemented', 'delete-vpc vpc-...: DependencyViolation']". The gateway ids and VPC ids in that list are per-run values, not part of the requirement; the three status/code answers are.
Why: any caller that creates a VPC with an internet gateway is left with resources it has no API to remove, and the DependencyViolation on DeleteVpc misattributes the cause to the caller's own dependencies rather than to the gateway the service refuses to detach. Every check that builds its own network and tears it down fails on the leak even when the behaviour under test is correct.
Fix: the DetachInternetGateway and DeleteInternetGateway handlers in the ec2 service crate and the VPC dependency bookkeeping DeleteVpc consults. The open issue 20261104T055008Z-ec2-s3-ssm-createvpcendpoint-with-route-tables-and.md names the same two handlers for the ec2__s3__ssm suite; it does not carry this check's replay key, so this check stays red until that fix also lands for this path.

Cause 1 — expected (AWS): DescribeNetworkInterfaces on the id in the attachment's networkInterfaceId detail returns 200 with one NetworkInterface whose PrivateIpAddress == the attachment's privateIPv4Address, SubnetId == subnetId == the RunTask subnet, MacAddress == macAddress, VpcId == the task's VPC, Status == 'in-use', Attachment.Status == 'attached', Groups == exactly the RunTask security groups, RequesterManaged == true, InterfaceType == 'interface'; the subnet's AvailableIpAddressCount is one lower than before the task; DeleteNetworkInterface on that id is refused 400 InvalidParameterValue "Network interface '<that eni id>' is currently in use." while DeleteNetworkInterface on an interface the account just created in the same subnet succeeds; after StopTask the interface is gone and AvailableIpAddressCount is back to its pre-task value. Actual (emulator): DescribeNetworkInterfaces on that id is refused InvalidNetworkInterfaceID.NotFound — the interface does not exist, so none of the above is observable.

Cause 2 — expected (AWS): DetachInternetGateway and DeleteInternetGateway answer empty 200; DeleteVpc succeeds and the VPC stops being describable. Actual (emulator): both gateway calls answer NotImplemented and DeleteVpc answers DependencyViolation.
