# lambda: the sandbox-egress check can never be exercised — the emulator announces an IP-literal S3 endpoint, so a presigned GET URL silently degrades to path style and no virtual-hosted S3 hostname is ever produced for the function to resolve

> _Note: this issue was identified against the code base at commit `cb9254e7b4a839ef1fe220636b4ce55207805929`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetObject

## Description
One net-new root cause, surfaced by a `lambda`-group behavioral check. The check id's leading token is `lambda`, so this issue is filed under service `lambda`; the defective component is the S3 front door / endpoint announcement that the lambda sandbox-egress scenario depends on.

Related open issue: 20261029T083133Z-s3-virtual-hosted-style-bucket-addressing-is-unreachable.md describes the same underlying endpoint-announcement defect, but it is bound only to the replay key of the S3 check `s3.sdk-virtual-hosted-requests-round-trip-an-object-and-its-deletion` (Issue-Key `s3.sdk-virtual-hosted-requests-round-trip-an-object-and-its-deletion|run#33|AssertionError|...`). The suite does NOT bind this lambda check to it, so a fixer who closes that issue and re-replays only its trace id will leave this check still failing. It is filed here so the lambda-side consequence carries its own replay key. Also related: 20261028T105230Z-s3-8-net-new-root-causes-in-the.md (its "Cause 2 of 8: virtual-hosted-style addressing fails SigV4 verification" is the same component one layer further in).

Cause 1 of 1: the endpoint the emulator announces for S3 is an IP literal, so virtual-hosted (DNS-style) bucket addressing cannot be formed; an SDK asked for `addressing_style=virtual` silently keeps path style, and a presigned URL generated from it never carries the bucket as a Host label. The lambda sandbox-egress scenario — a non-VPC function resolving an S3 virtual-hosted hostname from inside its execution environment and completing an HTTPS GET of a presigned URL — therefore cannot be exercised at all.

AWS: S3 serves the same operations under two addressing forms. In virtual-hosted style the bucket is the leading DNS label of the Host header and the path omits the bucket (`Host: <bucket>.s3.<region>.amazonaws.com`, request line `GET /payload.txt?...`); in path style the bucket is the first path segment. Smithy (services/service-com-amazonaws-s3-amazons3/smithy-model/com-amazonaws-s3-amazons3.json): AmazonS3 version 2006-03-01, protocol restXml, sigv4Name `s3`, endpointPrefix `s3`, `endpointResolution.endpointRuleSet: true` — the modeled endpoint rule set is exactly what rewrites the `Bucket` input member out of the path and into the endpoint authority. `GetObject` models `Bucket` as `@httpLabel @required` and `Key` as `@httpLabel @required` with `http {method: GET, uri: "/{Bucket}/{Key+}?x-id=GetObject", code: 200}` — i.e. the modeled URI is the path-style fallback form only. Virtual-hosted style is the DEFAULT an AWS SDK uses against real S3. Because it is a DNS form it requires the endpoint authority to be a resolvable host name: botocore refuses to rewrite to virtual-hosted style when the configured endpoint authority is an IP literal and keeps path style instead (recorded behavior only for that degradation rule — it is an SDK/endpoint-rules property, not a wire shape). Real AWS also presigns with the SigV4 query form (`X-Amz-Algorithm=AWS4-HMAC-SHA256`, `X-Amz-Credential`, `X-Amz-Date`, `X-Amz-Expires`, `X-Amz-SignedHeaders`, `X-Amz-Signature`) for a modern client; the recording shows the legacy SigV2 query form instead (see Evidence) — that secondary observation is recorded behavior only and is already covered by 20261027T190000Z-s3-legacy-query-credential-presigned-get.md, so it is NOT a separate cause here.

Emulator: the check builds `boto3.client('s3', config=Config(s3={'addressing_style': 'virtual'}))` against the endpoint the emulator announces, puts an object, then calls `generate_presigned_url('get_object', ...)`. The generated URL's authority is the bare announced endpoint — an IP literal with a port — and the bucket appears as the first PATH segment, not as a Host label. The check's setup assertion `host.startswith(bucket)` therefore fails before any Lambda call is made: no function is created, no `Invoke` is issued, and the behavior under test (a function's own outbound HTTPS GET of a virtual-hosted S3 URL from inside the execution sandbox, expected to return `{"ok": true, "status": 200, "body": <exact object bytes>}`) is never reached. No status code or error code is returned by the emulator on this path — the divergence is in the transport form of the endpoint the emulator announces, so there is no refusal to quote. Hypothesis: the listener/front door advertises its bind address (an IP) as the endpoint authority rather than a DNS name for which `<bucket>.<authority>` resolves to the same listener, and the S3 router resolves the bucket only from a path segment.

The requirement is NOT a particular host name, IP or port (those are per-run environment values and never part of the requirement). It is that (a) the announced S3 endpoint authority be a DNS name under which `<bucket>.<authority>` reaches the same listener, (b) the S3 front door resolve the bucket from the leading Host label when the request path carries no bucket segment, canonicalizing SigV4 over the `Host` header exactly as signed, and (c) that hostname be resolvable from inside a Lambda execution environment so a handler's own outbound HTTPS GET of the presigned URL succeeds and returns the object's exact bytes with HTTP 200.

Why: a client relying on AWS's behavior gets two wrong answers. First, virtual-hosted addressing is the AWS default, so any application, tool or test that presigns an S3 URL and hands it to another component (a Lambda handler, a browser, a CDN origin, a webhook consumer) produces a bucket-in-hostname URL in production but a bucket-in-path URL against the emulator; code paths that depend on the bucket being in the authority (SigV4 host canonicalization, DNS-compatible bucket-name validation, OAC/OAI origins, host-based routing) are untestable. Second, the degradation is SILENT — no error, no warning — and here it does not merely pass vacuously, it also makes an entire class of Lambda behavior (does the execution sandbox have working DNS and outbound HTTPS to a service hostname?) impossible to verify: the scenario aborts in setup, so a real egress or DNS regression inside the sandbox would be indistinguishable from this.

Fix: the s3 crate's listener / front door and its endpoint announcement (the same component named by 20261029T083133Z-s3-virtual-hosted-style-bucket-addressing-is-unreachable.md), plus the presigner that builds URLs from that announced endpoint. The announced authority must be a DNS-resolvable name for which the `<bucket>.`-prefixed form reaches the same listener; the request router must strip a leading bucket label from `Host` when the path carries no bucket segment; and that hostname must be resolvable from the Lambda execution environment so the handler's outbound GET completes.

Traces: lambda.outbound-https-fetches-s3-object-via-virtual-hosted-presigned-url.

## Evidence
Cause 1 — expected: with an S3 client pinned to `Config(s3={'addressing_style':'virtual'})`, `generate_presigned_url('get_object', Params={'Bucket': <bucket>, 'Key': 'payload.txt'}, ExpiresIn=300)` returns a URL whose hostname begins with the bucket name (`https://<bucket>.<s3-endpoint-authority>/payload.txt?X-Amz-Algorithm=AWS4-HMAC-SHA256&X-Amz-Credential=...&X-Amz-Date=...&X-Amz-Expires=300&X-Amz-SignedHeaders=host&X-Amz-Signature=...`). The check then creates a python3.12 function, waits for State=Active, and `Invoke`s it with `{"url": <that url>}`; the handler does `urllib.request.urlopen(url)` from inside the sandbox and the check asserts StatusCode 200, no `FunctionError`, and a payload of `{"ok": true, "status": 200, "body": <the exact object body>}`.

Actual: the check aborts in setup at check_lambda_outbound_https_fetches_s3_object_via_virtual_hosted_presigned_url.py line 133 with

  AssertionError: test setup did not produce a virtual-hosted-style URL: host='127.0.0.1' for bucket 'sim2real-behav-lambdadns-41b4a36d6840' (url='https://127.0.0.1:41959/sim2real-behav-lambdadns-41b4a36d6840/payload.txt?AWSAccessKeyId=EMULATOR87A979375FAA&Signature=MdMWM1%2Ft%2Fz1ZgaDY9%2BRpB7S3VqQ%3D&Expires=1793290639')

Which parts are the requirement and which are per-run values: the FIXED requirement is that the URL's hostname be `<bucket>.` + the announced endpoint authority and that the path omit the bucket segment. The host `127.0.0.1`, the port `41959`, the bucket name `sim2real-behav-lambdadns-41b4a36d6840`, the access key id `EMULATOR87A979375FAA`, the `Signature` value and the `Expires` epoch are all per-run/per-environment values that merely fill the template — they are not part of the requirement. What the recording shows structurally is: authority = a bare IP literal, bucket = first path segment (path style), and a LEGACY SigV2 query credential form (`AWSAccessKeyId` / `Signature` / `Expires`) where AWS emits the SigV4 query form (`X-Amz-Algorithm` / `X-Amz-Credential` / `X-Amz-Date` / `X-Amz-Expires` / `X-Amz-SignedHeaders` / `X-Amz-Signature`).

Status/code/message divergence: none to quote — the emulator is never asked for this URL, because the degradation happens while the SDK resolves the announced endpoint. `PutObject` and `CreateBucket` earlier in the check both succeeded, so the object plane is not the defect; the defect is confined to the announced endpoint's addressing form, and its lambda-side consequence is that the sandbox-egress/DNS behavior is never exercised at all.

Context: the same endpoint-announcement defect is recorded from the S3 side in open issue 20261029T083133Z-s3-virtual-hosted-style-bucket-addressing-is-unreachable.md, where all eight requests of a virtual-hosted round trip were sent with the bare IP-literal authority as Host.

## Steps to Reproduce
Replay the behavioral suite and re-run exactly the check id in trace_ids: lambda.outbound-https-fetches-s3-object-via-virtual-hosted-presigned-url.

Manually:
1. Create a bucket (adding `CreateBucketConfiguration.LocationConstraint=<region>` when the region is not us-east-1) and `put_object(Bucket=<bucket>, Key='payload.txt', Body=b'...')`.
2. Build an S3 client pinned to virtual-hosted addressing against the endpoint the emulator announces: `boto3.client('s3', endpoint_url=<announced endpoint>, config=Config(s3={'addressing_style': 'virtual'}))`.
3. `url = s3.generate_presigned_url('get_object', Params={'Bucket': <bucket>, 'Key': 'payload.txt'}, ExpiresIn=300)`.
4. Inspect `urllib.parse.urlparse(url).hostname`. Observe it is the bare announced authority (an IP literal) and that the bucket is the first path segment, i.e. botocore kept path style because the authority is not a DNS name; also observe the query carries the legacy `AWSAccessKeyId`/`Signature`/`Expires` trio instead of the `X-Amz-*` SigV4 query form.
5. Confirm the server side independently: hand-build `GET /payload.txt` with `Host: <bucket>.<authority>`, SigV4-signed over that Host, and observe whether the bucket is resolved from the leading Host label.
6. For the lambda-side behavior the check exists to verify: create a python3.12 function (handler doing `urllib.request.urlopen(event['url'])`) with an execution role trusting lambda.amazonaws.com plus AWSLambdaBasicExecutionRole, wait for `State=Active`, and `Invoke` it with `{"url": <a virtual-hosted presigned URL>}`. Expect StatusCode 200, no FunctionError, and `{"ok": true, "status": 200, "body": <exact object body>}` — currently unreachable because step 3 cannot produce such a URL.
