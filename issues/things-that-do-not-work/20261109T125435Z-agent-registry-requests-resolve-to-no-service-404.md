# agent-registry requests resolve to no service: 404 UnknownService instead of modeled restJson1 responses

> _Note: this issue was identified against the code base at commit `fb003e0a3fdd2a31392ea928ed9540deb9fe4c34`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
SearchDiscoverableRegistryRecords

## Description
Three net-new wire divergences on service `agent-registry` (AgentRegistry, sdkId 'Agent Registry', protocol restJson1, authSchemes [sigv4]) share one fault: for these requests the emulator's request router resolves NO emulated service and answers HTTP 404 with `$.__type` = "UnknownService", `$.message` = "no emulated service is registered for '<signing-or-service-name>'" and `$headers.content-type` = `application/x-amz-json-1.1`, so no AgentRegistry handler is reached and neither the modeled error nor the modeled success body is produced. The other ListDiscoverableRegistryRecords steps of the same corpus DO reach a handler (they pass, or diverge only on message wording), so the service is registered for the route `/registries/{registryId}/discoverable-records-list` but not for the operations whose `@http` URIs are root-level (`/discoverable-records-batch`, `/discoverable-records-search`), nor for a request whose path cannot be bound to the labelled route. Hypothesis: the router's route/service table for this crate only carries the `/registries/...`-prefixed route, and anything else falls through to the generic UnknownService refusal. Two framing defects travel with every one of these refusals: `UnknownService` is in neither the service's modeled error set (AccessDeniedException 403, InternalServerException 500, ResourceNotFoundException 404, ThrottlingException 429, UnauthorizedException 401, ValidationException 400) nor AWS's error vocabulary, and the refusal is serialized with awsJson1_1 framing (`application/x-amz-json-1.1`) even though AgentRegistry is restJson1, whose responses and error responses carry `application/json`.

Relation to already-open issues (none covers these three causes): 20261029T192216Z-agent-registry-wire-replay-every-request-refused-pre.md describes the EARLIER router behavior (pre-dispatch `AmbiguousService` HTTP 500 on all 14 steps) and carries only `4xx->5xx` replay keys; the emulator now answers 404 `UnknownService` and 20 of 26 corpus steps pass, so none of the keys below is exercised by it. 20261029T185843Z-agent-registry-is-entirely-unreachable-router-resolves-services.md is a behavioral finding with behavioral check keys only, and 20261029T185813Z-agent-registry-control-every-agentregistrycontrol-request-is-rejected-with-ambiguousservice-two.md is about the agent-registry-control service. The ListDiscoverableRegistryRecords enum-order divergence (task#5) and the GetRegistryRecord status-poll divergence are already owned by open issues and are deliberately NOT part of this bundle.

--- Cause 1 of 3: ListDiscoverableRegistryRecords, unbindable request, must be 400 ValidationException "Request invalid", not 404 UnknownService.
AWS: Smithy ListDiscoverableRegistryRecords, POST /registries/{registryId}/discoverable-records-list, `registryId` @httpLabel required @length 1..2048 @pattern ^(arn:aws(-[^:]+)?:agent-registry:[a-z0-9-]+:[0-9]{12}:registry/)?[a-zA-Z0-9]{12,16}$; modeled client error ValidationException httpError 400 (members message required, reason required default FieldValidationFailed, fieldList). Recorded behavior for this rejection class: HTTP 400, content-type `application/json`, `$.__type` = "ValidationException", `$.message` = "Request invalid". Both of those strings are FIXED text for this class — no request-derived or state-derived value appears in the message. Hypothesis: the request cannot be bound to the labelled route (an empty/absent httpLabel collapses the path), which AWS answers as a non-field ValidationException rather than a route miss.
Emulator: HTTP 404; `$.__type` = "UnknownService"; `$.message` = "no emulated service is registered for 'agent-registry'"; `$headers.content-type` = `application/x-amz-json-1.1`.
Why: a client cannot distinguish a malformed request from a service that does not exist — the error discriminator carries a code no SDK error shape for this service matches, and 404 vs 400 misroutes every retry/error classifier that branches on ValidationException.
Fix: the shared request-router / service-resolution layer (register all of the service's restJson1 routes, and frame a pre-dispatch refusal in the resolved service's protocol), then the ListDiscoverableRegistryRecords request-binding path so an unbindable request answers the modeled ValidationException discriminator with the fixed message text.
Traces: agent-registry-list-discoverable-registry-records-validation-and-not-found#task#3.

--- Cause 2 of 3: SearchDiscoverableRegistryRecords success path answers 404 UnknownService instead of 200 with the matching records.
AWS: Smithy SearchDiscoverableRegistryRecords, POST /discoverable-records-search, http code 200; input searchQuery (required, @length 0..256, sensitive), registryIds (required, RegistryIdList @length 1..1), maxResults (1..20, default 10), filters (document, sensitive); output SearchDiscoverableRegistryRecordsResponse.registryRecords (required list of RegistryRecordSummary). A search over an existing registry whose record has been published/approved returns HTTP 200, content-type `application/json`, with that record's summary in `registryRecords` (name, description, recordId, recordType, recordArn, registryArn, status APPROVED, descriptors, createdAt/updatedAt). The response also carries `searchType` = "HYBRID" — recorded behavior only, that member is not in the Smithy output shape; the recording shows it present on every successful search.
Emulator: HTTP 404; body carries neither `registryRecords` nor `searchType`; `$.__type` = "UnknownService" with the "no emulated service is registered for 'agent-registry'" message and awsJson1_1 content-type. The operation is unreachable at its modeled URI.
Why: discovery of published records is impossible — a client that creates a record, submits it for approval and then searches for it is told the service does not exist, so the whole publish-then-discover workflow cannot be exercised against the emulator.
Fix: the router/service-resolution layer must register the root-level `/discoverable-records-search` route for this service; then the SearchDiscoverableRegistryRecords handler and serializer must return the modeled 200 body (required `registryRecords`, plus the recorded `searchType`).
Traces: agent-registry-search-and-batch-get-return-published-record#task#8.

--- Cause 3 of 3: BatchGetDiscoverableRegistryRecord success path answers 404 UnknownService instead of 200 with records and an empty errors list.
AWS: Smithy BatchGetDiscoverableRegistryRecord, POST /discoverable-records-batch, http code 200; input entries (required, RegistryRecordsEntryList @length 1..1); output BatchGetDiscoverableRegistryRecordResponse.registryRecords (required list) and errors (required BatchGetDiscoverableRegistryRecordErrorList, documented as empty when every requested record was returned). A batch-get naming one existing approved record returns HTTP 200, content-type `application/json`, that record's summary in `registryRecords` and `errors` present and empty.
Emulator: HTTP 404; `registryRecords` and `errors` both absent; `$.__type` = "UnknownService", message "no emulated service is registered for 'agent-registry'", content-type `application/x-amz-json-1.1`.
Why: both required output members are missing, so a generated client fails deserialization rather than seeing a record; a caller cannot read back by recordId at all, and the required-but-empty `errors` contract (the signal that nothing failed) is never produced.
Fix: the router/service-resolution layer must register the root-level `/discoverable-records-batch` route; then the BatchGetDiscoverableRegistryRecord handler/serializer must emit both required output members, with `errors` serialized as an empty list when all entries resolved.
Traces: agent-registry-search-and-batch-get-return-published-record#task#9.

All 3 causes must be closed and re-replayed: making the routes resolve is necessary but not sufficient — Cause 1 additionally requires the ValidationException discriminator and its fixed "Request invalid" text, and Causes 2 and 3 require the operations' success bodies (including the required `errors` list and the recorded `searchType`).
