# FIS: 4 fidelity divergences — CloudFormation AWS::FIS::ExperimentTemplate never provisioned into FIS, EC2 DescribeImages stub, SSM public AMI alias parameters missing, api-fault injection unobservable

> _Note: this issue was identified against the code base at commit `0b8884c4ab978d23b4fe746f795a1277a2a36df3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetExperimentTemplate

## Description
Four distinct net-new root causes on the FIS deploy/data-plane paths, each grounded in a failing behavioral check of the replay suite. A fixer must close ALL FOUR causes before submitting. Smithy citations are from services/service-com-amazonaws-fis-faultinjectionsimulator/smithy-model/com-amazonaws-fis-faultinjectionsimulator.json. Three issues are already open on this service (20261022T043627Z-fis-control-plane-9-fidelity-divergences-no-wait.md, 20261022T043627Z-fis-describestacks-omits-the-outputs-member-for-a-stack.md, 20261022T063355Z-fis-8-fidelity-divergences-targetaccountconfiguration-accepts-invalid-accountid.md); the causes below are NOT carried by any of them, and where one of them touches the same code path that is called out explicitly on the cause.

Cause 1 of 4: a CloudFormation-deployed AWS::FIS::ExperimentTemplate is never created in the FIS service, and !Ref on it resolves to a synthetic CloudFormation physical id instead of the FIS experiment-template id.
AWS: CloudFormation provisions an AWS::FIS::ExperimentTemplate by calling FIS CreateExperimentTemplate; the resource's physical id — and therefore the value of !Ref on it, which both checks publish as a stack Output — is the FIS experiment template id (Smithy: ExperimentTemplateId, @length 0..64, @pattern ^[\S]+$; the emulator's own id space for these is EXT-prefixed, e.g. EXT000000000001). Reading that id back with GetExperimentTemplate (Smithy: GET /experimentTemplates/{id}, errors ResourceNotFoundException errorKind client httpError 404, ValidationException 400) returns a template carrying the actions/targets/stopConditions/roleArn the stack declared. Recorded behavior only for the exact id text; the requirement is that the id a CREATE_COMPLETE stack publishes for that resource resolves in FIS and describes the declared template.
Emulator: the stack reaches CREATE_COMPLETE and DescribeStacks does now return Outputs, but the TemplateId output value is a CloudFormation-fabricated name of the form <stackName>-<logicalId>-<hex> (observed 'sim2real-fis-cfn-08277e828a91-ExperimentTemplate-CDB2F15D36F1' and 'sim2real-fis-stack-4efcedf7d6da-FisTemplate-EA7250AA5029'), and fis.GetExperimentTemplate(id=<that value>) answers 404 ResourceNotFoundException (message example: 'No experiment template found with id sim2real-fis-cfn-...-ExperimentTemplate-CDB2F15D36F1'). No experiment template is created in FIS state at all — the resource is accounted for in the stack only.
Why: the stack reports success while nothing was provisioned, so every deploy-then-use workflow breaks immediately after CREATE_COMPLETE: the client cannot read, start or delete the experiment template it just deployed, and infrastructure-as-code tests pass vacuously against a stack that created no FIS resource.
Fix: the CloudFormation resource provider for AWS::FIS::ExperimentTemplate — create the template through the FIS CreateExperimentTemplate path at stack-create time, use the FIS-returned id as the resource's physical id (hence the !Ref/GetAtt value), and delete it on stack delete.
NOTE for the fixer: the open issue 20261022T043627Z-fis-describestacks-omits-the-outputs-member-for-a-stack.md carries these same two check ids for an EARLIER failure on this path (DescribeStacks omitted Outputs entirely, KeyError: 'Outputs'). Outputs are now present; this is the next, different divergence on the same path and is not covered by that issue's replay key.
Traces: fis.deploy-experiment-template-cloudformation-then-start, fis.deploy-experiment-template-via-cloudformation-starts-experiment

Cause 2 of 4: EC2 DescribeImages is an unimplemented scaffold, so no FIS check that has to target a real instance can resolve an AMI.
AWS: DescribeImages returns the AMIs matching the given filters/owners and is the normal way to pick an image id before RunInstances; it is a plain 200 read operation with no precondition.
Emulator: the call is rejected with error code 'NotImplemented' and the message 'operation DescribeImages is scaffolded but not implemented in this emulator', aborting the check during setup. (The suite did NOT mark this failure ALREADY FILED, so no issue currently names this operation.)
Why: every workflow that discovers an AMI before launching an instance fails at the first call, which also makes all downstream FIS target-resolution behavior unreachable rather than wrong.
Fix: implement the DescribeImages handler in services/service-com-amazonaws-ec2-amazonec2/src/ops/describe_images.rs over the emulated EC2 image state.
Traces: fis.list-experiment-resolved-targets-reflects-server-side-resolution

Cause 3 of 4: the AWS-managed public SSM parameters for the latest Amazon Linux AMIs do not exist, so GetParameter on an AMI alias returns ParameterNotFound.
AWS: parameters under /aws/service/ami-amazon-linux-latest/ are AWS-published public parameters that exist in every account and region; GetParameter(Name='/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64') returns a String parameter whose Value is the current AL2023 x86_64 AMI id. Recorded behavior only (these parameters are not part of any service's Smithy model); the requirement is that the public AMI alias namespace resolves rather than 404-ing, and that the returned value is usable as an ImageId by RunInstances.
Emulator: the call is refused with error code 'ParameterNotFound' and the message 'Parameter /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64 not found', aborting the check before any FIS call is made.
Why: the public AMI alias is the standard, account-independent way to launch an instance; with the namespace empty, every emulated workflow that boots an instance from the current Amazon Linux image fails at setup and cannot be tested against the emulator at all.
Fix: the emulated SSM GetParameter handler / its public-parameter catalog — seed the /aws/service/ami-amazon-linux-latest/* aliases and resolve them to ImageIds that the emulated EC2 image state also knows.
Traces: fis.fis-reboot-instances-restarts-the-guest-kernel-and-the-boot-id-changes

Cause 4 of 4: a running aws:fis:inject-api-internal-error experiment produces no observable injected fault, so the fault-injection data plane cannot be exercised.
AWS: an experiment whose action is aws:fis:inject-api-internal-error with parameters service=ec2, operations=DescribeAvailabilityZones, percentage=100 and an aws:iam:role target makes the targeted role's EC2 DescribeAvailabilityZones calls fail with HTTP 500 and Error.Code 'InternalError' for the action's duration, while other operations on the same client and other principals are unaffected; the 500 stops once the experiment is terminal. The requirement is the 500 status and the 'InternalError' code (recorded message example: 'An internal error has occurred'); the check also asserts GetAction(id='aws:fis:inject-api-internal-error').action.targets == ['Roles'].
Emulator: the check never completes — it is reported as 'Check timed out after 60.0s'. Its only unbounded waits are polling GetExperiment for status 'running' and then polling the role-scoped EC2 client for the injected error; the emulator's EC2 handler is never coupled to the FIS control plane, so no injected 500 is produced and the poll cannot terminate. Hypothesis: the experiment runtime neither drives the experiment past its initial state nor registers an active fault against the targeted role, so both loops spin until the harness ceiling.
Why: the whole point of FIS is that a running experiment changes the behavior of the targeted API for the targeted principal. With no coupling, a client's fault-handling and retry paths are never exercised and a resilience test passes vacuously against the emulator.
Fix: the experiment runtime plus the request dispatcher — register the active action's (service, operations, percentage, target role, duration) while an experiment is running, and have the EC2 handler return a 500 'InternalError' for requests signed by a targeted role for the named operations until the duration elapses. See also the open issue 20261022T043627Z-fis-control-plane-9-fidelity-divergences-no-wait.md for the missing time-driven experiment progression this cause also depends on; that issue does not carry this check.
Traces: fis.fis-injected-api-internal-error-fails-a-role-scoped-ec2-call-and-spares-a-control-caller
