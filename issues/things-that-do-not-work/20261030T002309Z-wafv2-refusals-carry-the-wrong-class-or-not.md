# wafv2 refusals carry the wrong class or not WAF's own sentence, and the regex validator refuses a pattern WAF accepts

> _Note: this issue was identified against the code base at commit `de414c514180eddfb96a534a3f6304a808cc952a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateIPSet

## Description
Six wafv2 refusals diverge from AWS WAF: five refuse with the wrong error class or a sentence WAF never writes, and one refuses a write AWS accepts outright. This is ONE issue with SIX causes; every cause below must be closed before the fix is submitted. (The open issue 20261026T120000Z-wafv2-two-refusals-carry-the-right-class-but-not-wafs-own-sentence covers the Challenge immunity-time Reason and the PutManagedRuleSetVersions version-key clause; 20261029T192556Z-wafv2-refusals-carry-the-wrong-exception-class-sentence covers wire-corpus refusals. Neither carries any of the replay keys below.)

Cause 1 of 6: CreateIPSet's refusal for an address that is not valid CIDR for the declared IPAddressVersion uses the emulator's own sentence instead of WAF's.
AWS: Smithy: CreateIPSet.IPAddressVersion (enum IPV4|IPV6) and CreateIPSet.Addresses are both required; the operation models WAFInvalidParameterException (client, httpError 400). WAF refuses with HTTP 400, code `WAFInvalidParameterException`, and ONE message template for every malformed/mismatched address: `Error reason: The parameter contains formatting that is not valid., field: IP_ADDRESS, parameter: <address>`. The fixed text is `Error reason: The parameter contains formatting that is not valid., field: IP_ADDRESS, parameter: `; the only variable part is the offending Addresses entry, echoed verbatim from the request. The structured members carry Field `IP_ADDRESS` and Parameter = that address. The same template applies whether the entry is syntactic garbage or a well-formed address of the other family.
Emulator: the code and HTTP status are right, but the message is `Error reason: "<address>" is not an IPV4 address in CIDR notation, field: IP_ADDRESS, parameter: <address>` — a sentence WAF does not write, quoting the address and naming the family.
Why: clients and test suites match WAF's reason sentence (it is also what Reason carries); a different sentence breaks error-classification code and any golden-file comparison, and the family name leaks an implementation detail that AWS deliberately does not disclose per-address.
Fix: the message/Reason construction for the IP_ADDRESS validation failure in the CreateIPSet (and UpdateIPSet) handler's validation — emit WAF's single fixed sentence.
Traces: wafv2.ipset-invalid-cidr-rejected (syntactic garbage, IPV4 set), wafv2.ipset-malformed-cidr-rejected and wafv2.ipset-mismatched-ip-version-rejected and wafv2.ipset-version-mismatch-rejected (IPv6 CIDR in an IPV4 set).

Cause 2 of 6: DescribeManagedRuleGroup for a vendor/group that does not exist returns the generic not-found sentence instead of the catalog-specific one.
AWS: Smithy: DescribeManagedRuleGroup takes required VendorName and Name and models WAFNonexistentItemException (client, 400). For an unpublished managed rule group WAF refuses with HTTP 400, code `WAFNonexistentItemException`, and the message `ManagedRules with name <Name> by vendor <VendorName> does not exist. Please check your inputs.` — fixed text `ManagedRules with name ` / ` by vendor ` / ` does not exist. Please check your inputs.`, with Name and VendorName taken from the request. This is NOT the generic resource-doesn't-exist sentence WAF uses for customer resources.
Emulator: HTTP 400 and the right code, but the message is the generic `AWS WAF couldn't perform the operation because your resource doesn't exist.`
Why: the catalog-specific sentence is the only thing that tells a client WHICH vendor/name it got wrong; the generic sentence is indistinguishable from a deleted customer resource, so a typo in a managed-rule reference is undiagnosable.
Fix: the not-found message in the DescribeManagedRuleGroup handler — use the ManagedRules sentence with the request's Name and VendorName, not the shared WAFNonexistentItemException text.
Traces: wafv2.describe-managed-rule-group-nonexistent-rejected. The positive control in the same check (AWS/AWSManagedRulesCommonRuleSet resolving with Capacity > 0) passed.

Cause 3 of 6: GetTopPathStatisticsByTraffic refuses a Scope/WebAclArn mismatch with the wrong exception class.
AWS: Smithy: GetTopPathStatisticsByTraffic takes required WebAclArn (ResourceArn, @length 20..2048) and required Scope, and models WAFInvalidParameterException and WAFNonexistentItemException (both client, 400). A REGIONAL web ACL ARN supplied with Scope=CLOUDFRONT fails ARN-shape validation for that scope, so the refusal is HTTP 400 with code `WAFInvalidParameterException` and message `Error reason: The ARN isn't valid. A valid ARN begins with arn: and includes other information separated by colons or slashes., field: RESOURCE_ARN, parameter: <WebAclArn>` — fixed text through `field: RESOURCE_ARN, parameter: `, variable part the ARN from the request.
Emulator: HTTP 400 but code `WAFNonexistentItemException` — it treats the mismatch as a lookup miss rather than a parameter-shape failure.
Why: the two classes are handled differently by clients: WAFNonexistentItemException reads as "create it / retry later" while WAFInvalidParameterException reads as "fix the request". A scope/ARN mismatch sent into a retry loop never resolves.
Fix: the Scope/WebAclArn consistency check in the GetTopPathStatisticsByTraffic handler's validation — classify it as a RESOURCE_ARN parameter failure, before the web-ACL lookup. The same check's Scope=REGIONAL positive control (TotalRequestCount 0, PathStatistics []) already passes, so only the mismatch branch is wrong.
Traces: wafv2.get-top-path-statistics-pricing-plan-denied.

Cause 4 of 6: CreateAPIKey refuses a sixth token domain as a parameter-format error instead of a limit violation.
AWS: Smithy: CreateAPIKey.TokenDomains is required (APIKeyTokenDomains, @length min 1; member TokenDomain @length 1..253 @pattern ^[\w\.\-/]+$) and the operation models BOTH WAFInvalidParameterException and WAFLimitsExceededException (client, 400). Exceeding the documented five-domain ceiling is the LIMIT error: HTTP 400, code `WAFLimitsExceededException`, message `AWS WAF couldn't perform the operation because you exceeded your resource limit NUM_TOKEN_DOMAINS_IN_API_KEY` — entirely fixed text (the limit token names which quota was hit); no Field/Parameter members. WAFInvalidParameterException with Field `TOKEN_DOMAIN` is reserved for a domain that is malformed (e.g. one carrying a path), whose message is `Error reason: The parameter contains formatting that is not valid., field: TOKEN_DOMAIN, parameter: <domain>`.
Emulator: six domains are refused with code `WAFInvalidParameterException`, message `Error reason: a single API key can be used for up to 5 token domains, field: TOKEN_DOMAIN, parameter: <the 6th domain>`, Field TOKEN_DOMAIN, Parameter the sixth domain — the wrong class, a sentence WAF does not write, and detail members WAF does not attach to this refusal.
Why: a client distinguishes "this request is malformed" from "you hit a quota — request an increase or split the key" by the exception class; collapsing the quota error into the format error sends quota handling down the wrong branch, and the invented sentence breaks message matching.
Fix: separate the TokenDomains count limit from per-domain format validation in the CreateAPIKey handler's validation; raise WAFLimitsExceededException with the NUM_TOKEN_DOMAINS_IN_API_KEY sentence and no detail members.
Traces: wafv2.apikey-token-domain-limit-and-validation-layers-rejected.

Cause 5 of 6: the ValidationException constraint message lists an enum's value set in a different order than AWS.
AWS: recorded behavior only — the Smithy model declares OversizeHandling as CONTINUE, MATCH, NO_MATCH, but WAF's request-validation message lists the set as `[MATCH, NO_MATCH, CONTINUE]`. For an out-of-enum OversizeHandling on a Body FieldToMatch, UpdateWebACL refuses with HTTP 400, code `ValidationException`, and the message `1 validation error detected: Value '<value>' at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [MATCH, NO_MATCH, CONTINUE]`. Fixed text is the `1 validation error detected: Value '` / `' at '` / `' failed to satisfy constraint: Member must satisfy enum value set: ` scaffolding plus that bracketed list; variable parts are the rejected value and the 1-based member path from the request (e.g. rules.2.member.statement.byteMatchStatement.fieldToMatch.body.oversizeHandling for the second rule).
Emulator: everything matches except the bracketed list, which is emitted as `[CONTINUE, MATCH, NO_MATCH]` — the values sorted (or in model-declaration order) rather than in AWS's order.
Why: the whole message is a documented, client-visible string that test suites and error parsers compare verbatim; a reordered value set makes every enum-constraint refusal differ from AWS, on every operation that shares this serializer.
Fix: the enum value-set rendering in the shared request-validation message builder — emit AWS's per-enum ordering rather than sorting or reusing the model order.
Traces: wafv2.webacl-update-configuration-warning-surfaced. The rest of that check passes: omitting OversizeHandling is correctly committed with the CONTINUE default rather than raising WAFConfigurationWarningException, and the rejected update correctly leaves the rule set and LockToken untouched.

Cause 6 of 6: Create/UpdateRegexPatternSet refuses regex constructs AWS WAF accepts, so a valid write is blocked.
AWS: Smithy: CreateRegexPatternSet.RegularExpressionList is required and the operation models WAFInvalidParameterException (client, 400). Recorded behavior: WAF's write-time validator does NOT reject every construct the documentation lists as unsupported by the matching engine — a capturing group `(abc)` and the single-byte directive `\C` are both ACCEPTED at write time and round-trip verbatim through GetRegexPatternSet. The constructs it DOES refuse are the zero-width-assertion/backtracking class (all three lookaround forms, backreferences, atomic groups, possessive quantifiers, \K, recursion, \R, conditionals, control verbs), each with HTTP 400, code `WAFInvalidParameterException`, Field `REGEX_PATTERN_SET`, Reason `The parameter contains formatting that is not valid.`, Parameter = the single offending pattern, and message `Error reason: The parameter contains formatting that is not valid., field: REGEX_PATTERN_SET, parameter: <pattern>`.
Emulator: CreateRegexPatternSet refuses `\C` with exactly that 400/WAFInvalidParameterException/REGEX_PATTERN_SET refusal, so a pattern list AWS accepts cannot be created at all. The refusal fired on the check's setup call, which means the emulator's accepted-construct set is narrower than WAF's; the complementary half (whether it also wrongly ACCEPTS the lookaround/backreference class, which Python's `re` compiles) was never reached and must be verified by the same fix.
Why: this is a refusal of a valid request, the one direction a client cannot work around: a regex pattern set that exists on AWS cannot be created against the emulator, so the whole rule set depending on it is unbuildable.
Fix: the regex-flavour validator behind the CreateRegexPatternSet/UpdateRegexPatternSet handlers — accept `\C` and capturing groups, and refuse exactly the PCRE-excluded class (all lookaround forms, backreferences, atomic groups, possessive quantifiers, \K, (?R), \R, conditionals, (*VERB)) rather than deriving the set from Python `re` compilability or from the documentation's unsupported list.
Traces: wafv2.regex-pattern-set-unsupported-pcre-construct-rejected.
