# pipes: UpdatePipe re-installing FilterCriteria on a RUNNING pipe is never applied by the live poller — the tighten-then-revert swap never converges

Cause 1 of 1: UpdatePipe on a pipe whose CurrentState is RUNNING stores a replacement FilterCriteria, but the pipe's already-running source poller never demonstrably moves onto the replaced pattern, so neither direction of the swap (tighten, then revert) can be observed by a client. Failing check: pipes.update-pipe-filter-criteria-takes-effect-on-a-running-pipe-and-reverts.

AWS: Smithy (model services/service-com-amazonaws-pipes-pipes/smithy-model/com-amazonaws-pipes-pipes.json) — com.amazonaws.pipes#UpdatePipe, PUT /v1/pipes/{Name}, success 200, idempotent; input members Name (PipeName, httpLabel, required, @length 1..64, @pattern ^[\.\-_A-Za-z0-9]+$) and RoleArn (required) plus SourceParameters -> UpdatePipeSourceParameters; modeled errors ConflictException 409, NotFoundException 404, ValidationException 400, ThrottlingException 429, InternalException 500. The operation's own documentation states that EventBridge updates only the fields specified, EXCEPT that the Amazon-Web-Services-service-specific objects inside SourceParameters are updated "atomically as one and overrides existing values" — so a SourceParameters block carrying a FilterCriteria REPLACES the stored criteria rather than merging with them. FilterCriteria.Filters is a FilterList (@length 0..5) and the member is documented as "The collection of event patterns used to filter events. To remove a filter, specify a FilterCriteria object with an empty array of Filter objects." UpdatePipe's output and DescribePipe report CurrentState from PipeState (UPDATING, RUNNING, ...), which is how a client observes the update settling. The data-plane consequence is recorded behavior only (the model covers the control plane): a RUNNING pipe polls its source with no client action and admits only the records matching the patterns it currently holds, so after an UpdatePipe that replaces the patterns the newly admitted shape must start reaching the target and the shape only the superseded pattern admitted must stop; reverting the patterns must swap those two back, because the revert is a replacement and not an addition.

Emulator: the check never completes. Replay reports `[mismatch] pipes.update-pipe-filter-criteria-takes-effect-on-a-running-pipe-and-reverts / Error: Check timed out after 60.0s`, with no frame captured, so neither of the two decisive assertions is ever evaluated: (a) after the tightened pattern is installed, that the shape only the ORIGINAL pattern admitted is no longer delivered while the twin shape admitted by BOTH patterns keeps arriving, and (b) after the original pattern is restored, that the previously withheld shape is delivered again while the shape only the tightened pattern admitted is now withheld. The control-plane half does work — services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs computes `updated_source_parameters(...)`, which sets `filter_criteria: update.filter_criteria.clone()` (the atomic override the model documents, with the comment "`SourceParameters` is itself one of the objects AWS overrides atomically") and writes `pipe.source_parameters` — but the hand-off to the data plane only calls `crate::state::data_plane::drive_pipe(...)` under the comment "An update that leaves the pipe meant to RUN starts its poller if the pipe has none". An ALREADY-running poller is never signalled and never observably re-reads the pipe record, so the stored replacement is not what the running poller applies. Hypothesis (the replay reached no stage, so this is not confirmed by it): the in-flight poller holds the configuration it started with, so the newly admitted shape never arrives after the update and the check's probe loop waits out its budget.

Why: replacing FilterCriteria with UpdatePipe is the normal way to change which records a live pipe admits without tearing it down. A client doing that reads back the new pattern from DescribePipe while the records actually reaching the target are still governed by the old one: a tightening meant to stop a record class keeps delivering it, and a revert may either fail to re-admit the old class or stop filtering altogether. "Stored but not applied" is indistinguishable from "applied" from outside, and because filter changes are a security- and cost-relevant control, a client will believe it has cut off a record class that is still flowing.

Fix: the UpdatePipe handler's hand-off to the data plane and the poller's configuration re-read — services/service-com-amazonaws-pipes-pipes/src/ops/update_pipe.rs (the branch that calls `drive_pipe` only when the pipe has no poller, and the UPDATING->RUNNING settle it leaves behind) together with services/service-com-amazonaws-pipes-pipes/src/state/data_plane.rs (the filter stage must evaluate the FilterCriteria the pipe record holds at the moment of each poll, so an in-flight poller picks up a replaced pattern, and a replacement must never be merged with the pattern it superseded).
