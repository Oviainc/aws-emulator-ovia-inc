# mediapackagev2 data-plane URLs (channel ingest and origin-endpoint HLS manifest) are minted on public AWS hostnames the emulator does not serve, so no data-plane check can reach it

> _Note: this issue was identified against the code base at commit `795c74e692207bc8fa0a6278ad393ecb317bba54`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateChannel

## Description
Behavioral replay of simparity-behavioral-aws-v1 (56/68 passed) leaves two mediapackagev2 failures that are not marked ALREADY FILED and are not OWNED by any open issue's replay key. Both are the same family of defect: an address-bearing member of a 200 control-plane response is minted under the PUBLIC AWS domain `*.mediapackagev2.<region>.amazonaws.com` instead of under a host the emulator itself answers on, so the harness's published-URL guard refuses the value (`PublishedUrlRejected: ... its host is not one of the emulator's own hosts`) and the data-plane leg of the check is never even attempted. This is a TWO-cause bundle; a fixer MUST close both causes below and re-replay both listed checks before submitting.

Related open issues, named explicitly because neither covers these checks: 20261109T115329Z-mediapackagev2-channel-group-and-channel-responses-advertise-aws-owned.md and 20261109T115329Z-mediapackagev2-origin-endpoint-manifest-urls-advertise-aws-owned-egress.md describe the same host fault from the WIRE corpus (simparity-wire-aws-v1) and carry only wire replay keys (`mediapackagev2|CreateChannel|2xx->2xx|$.IngestEndpoints[*].Url` etc.); they do not carry either behavioral check id, so neither behavioral check is gated by them and a fix verified only against the wire corpus will not re-run the two data-plane checks below. 20261029T201731Z-mediapackagev2-five-rejection-messages-worded-differently-from-aws.md covers the STATUS the ingest/manifest data plane returns once reached (404 where AWS returns 403); that is a different defect and is already OWNED for its own checks. Fixing the host is a precondition for ever reaching that status check from these two.

Cause 1 of 2: CreateChannel's IngestEndpoints[].Url announces an ingest host the emulator is not reached on, so the live-ingest round trip cannot run at all.
  AWS: Smithy mediapackagev2 CreateChannel -> POST /channelGroup/{ChannelGroupName}/channel; output member IngestEndpoints is a list of IngestEndpoint{Id, Url}, and IngestEndpoint.Url is documented as "The ingest domain URL where the source stream should be sent." The member exists so a contribution encoder can PUT to it, i.e. the URL must name a host the responder answers on. Recorded behavior only for the host component: the recording shows the responder returning an ingest URL rooted at the endpoint the client is talking to. The generated label, the account label and the port are per-environment values and are NOT the requirement; the host being servable by the responder is. The behavioral expectation for the data plane behind it (also recorded behavior only, from the check): an unauthenticated PUT answers HTTP 403 with a body containing "Access denied", and a PUT carrying a syntactically valid but cryptographically wrong SigV4 Authorization header answers HTTP 403 with a DIFFERENT, signature-specific body (one mentioning the signature), never a 2xx and never the identical body for both classes. The fixed text of each denial is the class's message; any resource/channel names, request ids or signature strings inside it are values taken from the request and the emulator's state.
  Emulator: CreateChannel returns IngestEndpoints[0].Url of the form `https://<label>-<n>.ingest.<account-label>.mediapackagev2.<region>.amazonaws.com/in/v1/<group>/<n>/<channel>/index` — a hostname owned by AWS, not one the emulator is reached on. The harness rejects it before any PUT: `simparity.published.PublishedUrlRejected: endpoint_url was given https://<label>-1.ingest.<account-label>.mediapackagev2.us-west-2.amazonaws.com/in/v1/<group>/1/<channel>/index (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener`. The path structure and the HTTPS scheme are correct; only the host is wrong, and consequently the two 403 negative classes above are untested.
  Why: a client that performs the documented live-ingest round trip pushes its stream at real AWS (or fails name resolution in an isolated environment) instead of at the emulator, with nothing in the 200 control-plane response indicating the address is unusable. Ingest, and every authorization behavior layered on it, is unreachable against the emulator.
  Fix: the CreateChannel handler's ingest-endpoint URL minting and the channel state record that persists those URLs — the host must be derived from the emulator's advertised endpoint (the endpoint the request arrived on) rather than a hard-wired amazonaws.com template; the same derivation must be applied on the read/update paths so persisted records stop re-serving the public host. A listener must then answer PUTs on that path with the two distinct 403 denials described above.
  Traces: mediapackagev2.cmaf-ingest-native-protocol-round-trip.

Cause 2 of 2: CreateOriginEndpoint's HlsManifests[].Url announces an egress host the emulator is not reached on, so the manifest data plane cannot be fetched.
  AWS: Smithy mediapackagev2 CreateOriginEndpoint -> POST /channelGroup/{ChannelGroupName}/channel/{ChannelName}/originEndpoint; output member HlsManifests is a list of GetHlsManifestConfiguration whose Url (String, @required) is documented as "The egress domain URL for stream delivery from MediaPackage." It is the address a player fetches, so it must name a host the responder answers on. Recorded behavior only for the host component: the recording shows the responder returning a manifest URL rooted at the endpoint the client is talking to; the generated label and account label are per-environment values, not requirements. The behavioral expectation for the data plane behind it (recorded behavior only, from the check): a GET of the manifest URL answers HTTP 403 while no resource policy grants `mediapackagev2:GetObject`, and HTTP 404 after PutOriginEndpointPolicy grants it but before any content has been ingested.
  Emulator: CreateOriginEndpoint returns HlsManifests[0].Url of the form `https://<label>.egress.<account-label>.mediapackagev2.<region>.amazonaws.com/out/v1/<group>/<channel>/<endpoint>/<manifest>.m3u8`, and the harness refuses it: `simparity.published.PublishedUrlRejected: endpoint_url was given https://<label>.egress.<account-label>.mediapackagev2.us-west-2.amazonaws.com/out/v1/<group>/<channel>/<endpoint>/index.m3u8 (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener`. Status 200 and the path structure are correct; only the host is a public AWS name. The 403-then-404 policy transition is therefore never exercised.
  Why: a player handed the advertised manifest URL fetches from real AWS or fails DNS instead of reaching the emulator, so the documented playback contract — including the resource-policy gate that turns 403 into 404 — cannot be exercised against the emulator even though the control plane reported success.
  Fix: the CreateOriginEndpoint handler's manifest-URL minting and the origin-endpoint state record that persists the URLs, plus the shared host derivation used by the Get/Update/List serializers, so the host comes from the emulator's advertised endpoint. A listener must then serve that path with the 403 (no read policy) / 404 (policy granted, no content) statuses above.
  Traces: mediapackagev2.origin-endpoint-manifest-url-data-plane-reachable.

## Steps to Reproduce
Boot the emulator from this checkout and replay the two behavioral checks, or reproduce directly with botocore pointed at the emulator's endpoint.

Cause 1 (mediapackagev2.cmaf-ingest-native-protocol-round-trip):
  1. mp = boto3 client('mediapackagev2', endpoint_url=<emulator endpoint>)
  2. mp.create_channel_group(ChannelGroupName=g)
  3. created = mp.create_channel(ChannelGroupName=g, ChannelName=c, InputType='HLS')
  4. url = created['IngestEndpoints'][0]['Url'] — observe the host is `*.ingest.*.mediapackagev2.<region>.amazonaws.com`, not the emulator's host/port. Connecting to it never reaches the emulator (and fails name resolution in an isolated environment).
  5. With the host fixed, PUT arbitrary bytes to that URL with no Authorization header: expect HTTP 403 and a body containing "access denied". Then PUT the same bytes with a SigV4 header signed for service 'mediapackagev2' with the caller's credentials: expect HTTP 403, a body mentioning the signature, and a body DIFFERENT from the unauthenticated one. Neither class may return 2xx.

Cause 2 (mediapackagev2.origin-endpoint-manifest-url-data-plane-reachable):
  1. mp.create_channel_group(ChannelGroupName=g); mp.create_channel(ChannelGroupName=g, ChannelName=c)
  2. created = mp.create_origin_endpoint(ChannelGroupName=g, ChannelName=c, OriginEndpointName=e, ContainerType='TS', HlsManifests=[{'ManifestName': 'index'}])
  3. url = created['HlsManifests'][0]['Url'] — observe the host is `*.egress.*.mediapackagev2.<region>.amazonaws.com`, not the emulator's.
  4. With the host fixed, GET the URL: expect HTTP 403 (no resource policy grants mediapackagev2:GetObject yet).
  5. mp.put_origin_endpoint_policy(ChannelGroupName=g, ChannelName=c, OriginEndpointName=e, Policy=<Allow Principal '*' Action 'mediapackagev2:GetObject' on created['Arn']>), then GET again: expect HTTP 404 (policy allows the read, no content ingested yet).

Pass criterion for both causes: every data-plane URL the control plane publishes (IngestEndpoints[].Url, HlsManifests[].Url, and the same members on the Get/Update/List paths) must have a host the emulator answers on, derived from the endpoint the request arrived on, and a listener must serve those paths with the statuses and denial bodies above. Generated labels, account labels, ports and resource ids may differ freely; the per-endpoint and per-manifest path uniqueness must be preserved.
