# route53globalresolver refusal classification: ValidationException quotes @pattern with its regex anchors, and the tag family validates resourceArn shape instead of denying a non-ARN first (2 causes)

> _Note: this issue was identified against the code base at commit `63738de0101ebf6c323b1ab59b247c4705f0deaf`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
Two distinct defects on route53globalresolver's refusal path, both found by the behavioral suite. THIS IS TWO CAUSES — close both before submitting.

Cause 1 of 2: the ValidationException message for a @pattern violation renders the regex with its anchors still attached.
Failing checks: route53globalresolver.create-dns-view-validates-shape-before-checking-global-resolver-existence, route53globalresolver.create-firewall-rule-layers-field-validation-ahead-of-dns-view-lookup.
AWS: Smithy CreateDNSView.globalResolverId and CreateFirewallRule.dnsViewId both target ResourceId with @length 1..64 and @pattern ^[-.a-zA-Z0-9]+$; both operations model ValidationException @error(client) @httpError(400) (model: services/service-com-amazonaws-route53globalresolver-ec2dnsglobalresolvercustomerapi/smithy-model/com-amazonaws-route53globalresolver-ec2dnsglobalresolvercustomerapi.json). Recorded behavior for the message template: "1 validation error detected: Value '<value>' at '<memberName>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>". Fixed text = "1 validation error detected: Value '" / "' at '" / "' failed to satisfy constraint: Member must satisfy regular expression pattern: "; variable parts = the rejected value taken from the request, the offending member's name, and the pattern. The rule the recordings establish is that AWS renders the pattern with the leading ^ and trailing $ STRIPPED — the bare body of the regex.
Emulator: status 400 and the class ValidationException are correct and the whole template is correct, but the pattern is printed verbatim from the model, so every pattern rejection in this service differs from AWS by exactly those two characters: for globalResolverId it answers "...regular expression pattern: ^[-.a-zA-Z0-9]+$" where AWS answers "...regular expression pattern: [-.a-zA-Z0-9]+", and identically for dnsViewId on CreateFirewallRule. The same anchored rendering appears on resourceArn in the tag family (see Cause 2's evidence), i.e. it is the shared formatter, not one handler.
Why: a client asserting on the validation message (or surfacing it to a user) sees a regex AWS never emits, and a client that parses the pattern out of the message and re-applies it gets a subtly different, anchored expression. Message-equality tests pass against AWS and fail against the emulator on every pattern-constrained member of this service.
Fix: the shared ValidationException message formatter for this service's @pattern constraint — strip the leading ^ and trailing $ when rendering the pattern. Note the open issue 20261109T193053Z-route53globalresolver-route-53-global-resolver-refusal-bodies-are-emulator.md names the same formatter in its Cause 6, but it is keyed only on wire steps for GetGlobalResolver and carries neither of these behavioral check ids, so these two checks are not covered by it; fixing that formatter once should close both. Once the anchors are fixed these two checks continue past this assertion and additionally require the GR-ERR00309 not-found template for a well-formed-but-absent globalResolverId, and (for CreateFirewallRule) the cross-field rules "[GR-ERR04003] Input should contain exactly one of FirewallDomainListId or DnsAdvancedProtection." and "[GR-ERR04001] BlockResponse must be provided if Action is BLOCK." to be evaluated BEFORE the dnsViewId is looked up; those later assertions were never reached in this run and are not themselves evidenced here.

Cause 2 of 2: TagResource / UntagResource / ListTagsForResource validate the resourceArn's modeled shape instead of authorizing the caller against it first, so a non-ARN value is answered with the wrong error class.
Failing check: route53globalresolver.tag-resource-family-denies-a-non-arn-resource-before-validating-its-shape.
AWS: Smithy TagResource (POST /tag-resource), UntagResource (POST /untag-resource) and ListTagsForResource (POST /get-all-tags) all take a @required resourceArn targeting ResourceArn with @length 1..2048 and @pattern ^arn:[-.a-z0-9]{1,63}:[-.a-z0-9]{1,63}:[-.a-z0-9]{0,63}:[-.a-z0-9]{0,63}:[^/].{0,1023}$. AccessDeniedException is not modeled on these three operations — recorded behavior only: AWS authorizes the caller against the supplied resourceArn BEFORE the member's shape is validated, so a value that is not ARN-shaped at all comes back as AccessDeniedException whose message is "User: <caller ARN> is not authorized to perform: route53globalresolver:<OperationName> on resource: <the resourceArn as supplied>" — fixed text "User: " / " is not authorized to perform: route53globalresolver:" / " on resource: "; variable parts are the calling principal's ARN, the operation name, and the request's resourceArn verbatim. The ordering is observable in three ways the check asserts: (a) a non-ARN string is denied, not shape-rejected; (b) a well-formed own-service ARN naming an absent resource reaches resource lookup and is refused ResourceNotFoundException with the "[GR-ERR00309] No GlobalResolver found with the ID: <id>" template (fixed text plus the id parsed from the ARN); (c) only once the value IS ARN-shaped but names another service does TagResource/UntagResource fail shape validation, with message "Invalid ARN format: <resourceArn>" (fixed text "Invalid ARN format: " plus the supplied ARN).
Emulator: it runs modeled @pattern validation first and answers ValidationException (400) with "1 validation error detected: Value 'not-an-arn' at 'resourceArn' failed to satisfy constraint: Member must satisfy regular expression pattern: ^arn:[-.a-z0-9]{1,63}:[-.a-z0-9]{1,63}:[-.a-z0-9]{0,63}:[-.a-z0-9]{0,63}:[^/].{0,1023}$" instead of AccessDeniedException with the authorization message. (That message also exhibits Cause 1's anchors, but the divergence here is the status/class itself: 400 ValidationException where AWS answers 403 AccessDeniedException.) Because the check stops at the first rejection, the emulator's answers for the own-service-absent-ARN and wrong-service-ARN inputs were not observed and the not-found / "Invalid ARN format" behaviors above are the requirement they must meet.
Why: a client that distinguishes "you may not touch this resource" from "your request was malformed" branches the wrong way — permission-probing and cross-account tagging logic that expects AccessDeniedException sees a 400 it treats as a client bug, and retry/escalation policies keyed on 403 never fire. The error class and status, not just the wording, are wrong.
Fix: the tag-family handlers (TagResource, UntagResource, ListTagsForResource) and their request-validation ordering — authorize the caller against the raw resourceArn before the modeled shape constraints run, then resource lookup, then ARN shape validation for ARN-shaped values of other services.
