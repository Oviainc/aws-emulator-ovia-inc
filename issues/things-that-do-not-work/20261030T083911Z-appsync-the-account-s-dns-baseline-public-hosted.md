# appsync: the account's DNS-baseline public hosted zone is not tag-discoverable through route53 ListHostedZones/ListTagsForResource, so the whole AppSync custom-domain-name path (CreateDomainName/AssociateApi/GetApiAssociation/DeleteDomainName) is unreachable

> _Note: this issue was identified against the code base at commit `038741e80bb0184996176715a8cc027a0310b035`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListHostedZones

## Description
One root cause, grounded in six net-new failing behavioral checks that all abort in their very first step, before any AppSync call is made.

Cause 1 of 1: the account's tagged PUBLIC hosted zone — the DNS baseline in which these checks publish an ACM DNS-validation CNAME so that AppSync's CreateDomainName has a certificate it will accept — cannot be found through route53's own listing and tagging reads. Every AppSync custom-domain-name check therefore dies in its precondition helper (`_dns_zone`) and the AppSync domain-name/API-association state machine is never exercised at all. Failing checks: appsync.api-association-get-not-found-when-unassociated, appsync.associate-api-domain-mismatched-certificate-rejected, appsync.deploy-domain-name-association-cfn-behavioral, appsync.domain-name-get-not-found-after-delete, appsync.domain-name-lifecycle, appsync.domain-name-lifecycle-state-transitions.

AWS: Smithy (com.amazonaws.route53) models ListHostedZones — input {Marker (httpQuery marker, @length 0..64), MaxItems (httpQuery maxitems), DelegationSetId, HostedZoneType}, output ListHostedZonesResponse{HostedZones (required, list), Marker (required), IsTruncated (required, default false), NextMarker, MaxItems (required)}, GET /2013-04-01/hostedzone, success 200, @paginated inputToken=Marker outputToken=NextMarker items=HostedZones pageSize=MaxItems; modeled refusals InvalidInput(400), NoSuchDelegationSet(400), DelegationSetNotReusable(400). The requirement is general: a hosted zone created and tagged in this account must be enumerated by ListHostedZones and must report, through ListTagsForResource, the tags written on it. Two readings are consistent with the replay and the recording does not distinguish them — Hypothesis: either ListHostedZones enumerates no (or not this) public hosted zone for the account (or reports Config.PrivateZone true for it), or ListTagsForResource('hostedzone', <id>) answers with a ResourceTagSet that omits the tags ChangeTagsForResource wrote, so the zone is enumerated but never recognised.

Why: a client cannot discover, enumerate or tag-select its own DNS zones, so nothing that depends on a delegated public zone can run. Concretely the entire AppSync custom-domain surface is unverifiable behind this one read: CreateDomainName against an ACM DNS-validated certificate, GetDomainName/ListDomainNames projection of domainNameConfig, GetApiAssociation answering NotFoundException/404 "Domain name is not associated." while unassociated and associationStatus PROCESSING -> SUCCESS with the right apiId after AssociateApi, DeleteDomainName then GetDomainName -> NotFoundException/404, the mismatched-certificate refusal on AssociateApi/CreateDomainName, the domain-name lifecycle state transitions, and the CloudFormation AWS::AppSync::DomainName / DomainNameApiAssociation deploy path. Any tag-driven discovery tooling (`aws route53 list-hosted-zones` + `list-tags-for-resource`, Terraform/CDK data sources, inventory and compliance scans) likewise sees an account with no zones.

Fix: route53's hosted-zone listing and hostedzone tag reads in the route53 service crate — the ListHostedZones enumeration over the account's zones (its Marker/NextMarker pagination and the Config.PrivateZone flag it reports) and the hostedzone tag store that ListTagsForResource projects after ChangeTagsForResource has written to it — so a zone created and tagged in this account is enumerated and reports its tags. Once the lookup resolves, the AppSync domain-name handlers (create_domain_name / get_domain_name / delete_domain_name / associate_api / disassociate_api / get_api_association) and their state must carry the domain and its association through the modeled lifecycle and error classes.

## Steps to Reproduce
1. Clone the repo, build and boot the emulator, then run the behavioral suite (region us-west-2).
2. Ensure the account holds a PUBLIC hosted zone tagged {'Key': 'sim2real-infra-dns-baseline', 'Value': 'true'} (route53 CreateHostedZone + ChangeTagsForResource).
3. Page route53.list_hosted_zones() and, for each zone with Config.PrivateZone false, call route53.list_tags_for_resource(ResourceType='hostedzone', ResourceId=<zone id after the last '/'>).
4. Observe that no enumerated public zone's ResourceTagSet.Tags contains the baseline tag — either the zone is not enumerated at all (or is reported as private), or its tag set comes back without the entry ChangeTagsForResource wrote. Expected: the zone is enumerated and reports its tags, both HTTP 200.
5. With that zone resolved, request a DNS-validated ACM certificate in us-east-1 for '<label>.<apex>', UPSERT the validation CNAME into the zone, wait for ISSUED, then call appsync.create_domain_name(domainName='<label>.<apex>', certificateArn=<that cert>).
6. Call appsync.get_api_association(domainName='<label>.<apex>') on the unassociated domain and expect NotFoundException/404 "Domain name is not associated."; then appsync.associate_api(domainName=..., apiId=<an API_KEY GraphQL api>) and poll GetApiAssociation until associationStatus is SUCCESS with the matching apiId; then delete_domain_name and expect get_domain_name -> NotFoundException/404.
7. Re-replay the six checks (appsync.api-association-get-not-found-when-unassociated, appsync.associate-api-domain-mismatched-certificate-rejected, appsync.deploy-domain-name-association-cfn-behavioral, appsync.domain-name-get-not-found-after-delete, appsync.domain-name-lifecycle, appsync.domain-name-lifecycle-state-transitions) to confirm the fix; they then proceed to their own AppSync assertions, which this lookup is currently masking.
