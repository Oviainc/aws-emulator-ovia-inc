=== Cause 1 of 9: CreatePullRequestApprovalRule answers the framework's generic ValidationException instead of the modeled InvalidApprovalRuleContentException for empty approval-rule content ===
AWS: Smithy CreatePullRequestApprovalRule takes approvalRuleContent (@required, ApprovalRuleContent, @length min 1 max 3000) and models InvalidApprovalRuleContentException (errorKind client, httpError 400 [defaulted]) as well as ApprovalRuleContentRequiredException. Recorded behavior: with an EXPLICIT empty string on the wire (botocore parameter_validation disabled so the client-side @length min 1 does not fire locally), AWS answers HTTP 400 with code InvalidApprovalRuleContentException — not ApprovalRuleContentRequiredException, and not a protocol-level ValidationException — and message 'Content for an approval rule is required, but the content of the approval rule was either empty or null.' That message is entirely FIXED text: it interpolates nothing from the request or from state. No rule is attached to the pull request.
Emulator: HTTP 400 with code 'ValidationException'. The empty string is being refused by the generic modeled-constraint/validation channel (the crate's Scaffolded::validation / pre-handler constraint rejection) rather than by the operation's own content validation, so the modeled error class never reaches the wire.
Why: a client that catches InvalidApprovalRuleContentException (every AWS SDK models it as a distinct exception type) sees an unrelated ValidationException instead, so the catch block never runs and the failure surfaces as an unmodeled protocol error. Clients cannot distinguish 'the content you sent is malformed' from 'your request did not parse'.
Fix: the approvalRuleContent validation in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_pull_request_approval_rule.rs — the empty/blank-content case must return the modeled InvalidApprovalRuleContentException with the fixed message above, ahead of (or instead of) the generic length-constraint rejection for this member.

=== Cause 5 of 9: CreatePullRequest ACCEPTS a request with no clientRequestToken on the wire and creates the pull request ===
AWS: Smithy CreatePullRequest declares clientRequestToken as an @idempotencyToken member and models ClientRequestTokenRequiredException (client, httpError 400 [defaulted]). Recorded behavior: a request whose body genuinely omits clientRequestToken is refused with HTTP 400, code ClientRequestTokenRequiredException and message 'A client request token is required.' (entirely fixed text), and NO pull request is created — ListPullRequests is unchanged afterwards. (SDKs normally autofill the token client-side, so reaching this error requires unregistering botocore's generate_idempotent_uuid handler, which is exactly what the check does; an explicit empty string is a different, valid input.)
Emulator: HTTP 200. The tokenless CreatePullRequest SUCCEEDS and returns a full pullRequest body (pullRequestStatus OPEN, a pullRequestTargets entry, a revisionId), leaking a pull request that AWS would never have created.
Why: this is the emulator accepting input real AWS refuses — the strongest class of divergence. The server-side idempotency contract is simply absent, so a client (or a hand-rolled signer, or a non-AWS SDK) that omits the token is silently allowed to create duplicate pull requests, and the modeled ClientRequestTokenRequiredException path is never exercised.
Fix: the request-level required-token guard in services/service-com-amazonaws-codecommit-codecommit-20150413/src/ops/create_pull_request.rs — refuse an absent (not merely empty) clientRequestToken with ClientRequestTokenRequiredException BEFORE any state mutation, so no pull request id is allocated.
Traces: codecommit.create-pull-request-missing-token-rejected.
