# apigateway__logs__wafv2: the WAF-logging destination-prefix check now hangs to the 60 s cap — the deployed REST stage / AssociateWebACL path no longer converges, so PutLoggingConfiguration is never even reached

> _Note: this issue was identified against the code base at commit `3744c0b73d0da990856091a9dde679d904464991`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutLoggingConfiguration

## Description
One net-new root cause: a REGRESSION in the failure MODE of a check that previously got all the way to its PutLoggingConfiguration assertion and now cannot get there at all. The suite marked this check neither ALREADY FILED nor OWNED.

Related open issues that do NOT cover this cause: 20261026T010229Z-apigateway-logs-wafv2-waf-logging-is-now-accepted.md carries this check id, but for the OPPOSITE observation — it records the check reaching PutLoggingConfiguration inside the 60 s cap and being ACCEPTED where AWS refuses, and it explicitly cites that as evidence that the stage pre-flight was NOT the stall. That is no longer what happens, so that issue's assertion-level description does not describe the behaviour now observed. 20261023T210711Z-apigateway-logs-wafv2-both-wafv2-logging-configuration-checks.md and 20261025T081755Z-apigateway-logs-wafv2-both-wafv2-logging-configuration-checks-2e88ae.md describe an earlier hang-at-the-stage mode for these two checks; 20261025T092822Z-apigateway-logs-wafv2-putloggingconfiguration-answers-notimplemented-so-waf.md and 20261024T065754Z-wafv2-putloggingconfiguration-stub.md describe the 501/NotImplemented mode, which no longer reproduces. A fixer closing any of those on its own wording would leave this check failing.

Cause 1 of 1: with a deployed API Gateway REST stage and a REGIONAL web ACL, none of the steps the check must complete BEFORE its PutLoggingConfiguration assertion converges, so the check exhausts the harness cap and the aws-waf-logs- destination refusal is unobservable again.
Failing check: apigateway__logs__wafv2.wafv2-put-logging-configuration-log-group-without-the-waf-prefix-rejected
AWS: each step the check performs before its refusal assertion is a plain, promptly answered control- or data-plane call. (a) logs CreateLogGroup + DescribeLogGroups make the group readable immediately, and the ARN DescribeLogGroups returns ends in ":*" which the caller strips. (b) apigateway CreateRestApi/PutMethod/PutIntegration/CreateDeployment/CreateStage then serve the stage: a GET of <invoke-url>/<marker> answers HTTP 200 with the MOCK integration's body. (c) wafv2 CreateWebACL (Scope=REGIONAL, DefaultAction Allow, one Priority 0 Block rule) succeeds, and AssociateWebACL(WebACLArn=<acl arn>, ResourceArn=arn:aws:apigateway:<region>::/restapis/<api-id>/stages/<stage>) succeeds — real AWS may answer WAFUnavailableEntityException for a freshly created stage for roughly 40 s, which is why the caller polls, but it then succeeds. Smithy (services/service-com-amazonaws-wafv2-awswaf-20190729/smithy-model/com-amazonaws-wafv2-awswaf-20190729.json): AssociateWebACL input WebACLArn/ResourceArn (both required), errors WAFInternalErrorException (500), WAFInvalidParameterException (400), WAFNonexistentItemException (400), WAFUnavailableEntityException (400), WAFInvalidOperationException (400); PutLoggingConfiguration input LoggingConfiguration (required) with member LogDestinationConfigs, errors including WAFInvalidParameterException (400) and WAFNonexistentItemException (400). Only after all of (a)-(c) does AWS's actual requirement under test apply: PutLoggingConfiguration with a CloudWatch Logs destination whose log-group NAME lacks the aws-waf-logs- prefix is refused HTTP 400 WAFInvalidParameterException, nothing is stored, GetLoggingConfiguration then answers HTTP 400 WAFNonexistentItemException, the unprefixed group receives no log streams, and the prefixed twin of the same suffix is accepted and round-trips LogDestinationConfigs and RedactedFields.
Emulator: the check never completes — the replay reports only "Check timed out after 60.0s", with no assertion reached. Every call before the refusal assertion is either immediate or inside a bounded poll whose own budget exceeds the harness cap (the stage pre-flight waits up to 180 s for the first HTTP 200, and AssociateWebACL is polled for up to 420 s), so a stall in any one of them consumes the whole cap and produces exactly this bare timeout. This is strictly worse than the previously recorded behaviour for this same check, which reached the PutLoggingConfiguration call inside the same 60 s cap: the pre-PutLoggingConfiguration path has regressed. Hypothesis: the stall is in the deployed stage never answering HTTP 200 at the invoke URL the emulator itself advertises, and/or AssociateWebACL never leaving its unavailable-entity answer for the stage ARN — the replay output does not say which, and neither does the model. Observable consequence either way: the whole WAF-logging surface behind an API Gateway stage is unreachable again, so the aws-waf-logs- prefix refusal, the GetLoggingConfiguration not-found leg and the no-streams-on-a-refused-destination leg are all unverifiable.
Why: a client wiring WAF logging in front of a REST stage follows exactly this order — create the log groups, deploy the stage, create and associate the web ACL, then enable logging. If the stage does not serve, or the association never completes, the client is stuck at step two or three with no error to act on: calls that AWS answers in seconds hang until the client's own timeout, and every downstream behaviour (block at the edge, logging validation, log delivery) is untestable. A silent hang gives a client no code, no message and nothing to retry on, which is worse than a refusal.
Fix: the API Gateway deployed-stage data-plane route (the execute-api invoke path the emulator advertises for a created api-id/stage must answer the stage's MOCK integration with HTTP 200 promptly after CreateDeployment/CreateStage) and the wafv2 AssociateWebACL handler for an apigateway stage ResourceArn (it must reach success rather than remaining in its unavailable-entity answer indefinitely). Once those two converge, the wafv2 PutLoggingConfiguration handler's LogDestinationConfigs validation is the next thing this check measures, as described in the related issues named above.
Traces: apigateway__logs__wafv2.wafv2-put-logging-configuration-log-group-without-the-waf-prefix-rejected (mismatch, timed out at the 60 s cap, no assertion reached).
