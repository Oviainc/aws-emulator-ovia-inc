# bedrock-agent-runtime__lambda__s3vectors: the Lambda python runtime's bundled botocore ships a 4-service data catalog, so boto3.client("s3vectors") / boto3.client("bedrock-agent-runtime") raise UnknownServiceError inside every handler (11 checks)

> _Note: this issue was identified against the code base at commit `1728eefb95ec8e4c4780b092ea8f416de5c45288`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Cause 1 of 1: the AWS SDK now present in the emulator's managed python Lambda execution environment carries a truncated botocore service-model data directory — it knows only sqs, events, eventbridge and dynamodb — so a handler that constructs a client for any other service dies inside boto3 with UnknownServiceError instead of reaching the service.

Failing check ids (11): bedrock-agent-runtime__lambda__s3vectors.cfn-lambda-role-missing-s3vectors-permission-negative, .cfn-lambda-role-s3vectors-permission-positive, .cfn-lambda-s3vectors-policy-wrong-resource-arn-negative, .lambda-bedrock-agent-missing-invokeagent-permission-negative, .lambda-bedrock-agent-missing-retrieve-permission-negative, .lambda-bedrock-retrieve-positive, .lambda-bedrock-retrieve-and-generate-positive, .cfn-deploy-lambda-bedrock-s3vectors-full-stack-positive, .cfn-deploy-wrong-execution-role-mismatch-negative, .cfn-stack-update-add-bedrock-agent-permission-positive, .cfn-stack-update-add-s3vectors-permission-positive.

AWS: recorded behavior only for the contents of the managed runtime — the Smithy model describes the Invoke wire shape, not the execution environment. AWS's managed python3.12 runtime ships a current boto3/botocore whose data directory contains the service models for every public AWS service, so inside a handler boto3.client("s3vectors") and boto3.client("bedrock-agent-runtime") construct normally and their calls are dispatched to those services; the handler then observes the service's own answer (a result, or an s3vectors / bedrock-agent-runtime AccessDeniedException when the execution role lacks the action). Smithy (lambda Invoke -> InvocationResponse, http {method: POST, uri: /2015-03-31/functions/{FunctionName}/invocations, code: 200}): StatusCode is httpResponseCode, FunctionError is header X-Amz-Function-Error, Payload is the httpPayload blob. On a successful RequestResponse invocation AWS answers 200 with X-Amz-Function-Error ABSENT and Payload equal to exactly the JSON the handler returned — and the handler's JSON reflects the called service's outcome, never a client-construction failure.

Emulator: Invoke returns 200 and the handler runs (import boto3 now succeeds, unlike the state recorded in the two open issues named below), but client construction fails. The handler's own except-branch reports botocore's exception type and message, so the invocation payload comes back as e.g. {"ok": false, "error_code": "UnknownServiceError", "error_message": "Unknown service: 'bedrock-agent-runtime'. Valid service names are: sqs, events, eventbridge, dynamodb"} and, for the s3vectors arms, "__unexpected__:UnknownServiceError:Unknown service: 's3vectors'. Valid service names are: sqs, events, eventbridge, dynamodb". Fixed text of that botocore message: "Unknown service: '<service-name>'. Valid service names are: <comma-separated list of the models the runtime actually has>"; the variable parts are the service id the handler asked for (taken from the boto3.client call — observed for both s3vectors and bedrock-agent-runtime) and the list of installed models (here sqs, events, eventbridge, dynamodb). Nothing about the request or the state justifies that list: it is simply the set of service models the runtime image contains. No s3vectors or bedrock-agent-runtime HTTP request leaves the sandbox at all, so neither the data-plane effect nor the IAM decision is ever exercised.

Four of the eleven checks show the same cause as a timeout rather than an assertion: cfn-deploy-lambda-bedrock-s3vectors-full-stack-positive, cfn-deploy-wrong-execution-role-mismatch-negative, cfn-stack-update-add-bedrock-agent-permission-positive and cfn-stack-update-add-s3vectors-permission-positive deploy a CFN stack and then poll _poll_until(..., timeout_s=60, interval_s=5.0) for the invocation result to report s3vectors/bedrock ok=True (their handler is the same `import boto3` / boto3.client("s3vectors") / boto3.client("bedrock-agent-runtime") body). Hypothesis: because the client can never be constructed, that predicate can never become true and the run is killed at the harness's 60s cap ("Check timed out after 60.0s") before any assertion is reached. Those four are listed here as examples of the same cause, not as a separate defect.

Why: a client gets a Lambda that can reach only four AWS services. Every function whose code calls any other service through the standard SDK — the entire subject of these checks (Lambda -> s3vectors PutVectors/GetVectors/ListVectorBuckets, Lambda -> bedrock-agent-runtime Retrieve/RetrieveAndGenerate/InvokeAgent/ListSessions) — fails before a request is made. The positive arms never observe the intended effect. The negative arms are worse than failed: an under-permissioned role that must surface s3vectors or bedrock-agent-runtime AccessDeniedException instead surfaces a botocore UnknownServiceError, so an emulator user cannot distinguish an IAM denial from a broken runtime image and concludes their deployment package or their policy is wrong when neither is. Every CFN-deployed cross-service pipeline that fans out through Lambda glue is unverifiable.

Fix: the Lambda service's execution-environment component — the part that assembles the python runtime/filesystem for the sandbox and puts boto3/botocore on the handler's import path. It must install a botocore whose data directory carries the full set of service models (at minimum every service the emulator itself serves), the way the managed python3.12 runtime does, rather than a four-service subset. Not the Invoke serializer: the Invoke response wire shape is correct; the SDK data shipped into the sandbox is incomplete.

Related open work (does NOT cover these checks; the suite marked none of the eleven as owned): 20261105T105400Z-bedrock-agent-runtime-lambda-s3vectors-2-net-new.md and 20261105T090020Z-bedrock-agent-runtime-lambda-s3vectors-the-python-lambda.md describe the earlier symptom of this same runtime, where boto3 was absent entirely (Runtime.ImportModuleError "No module named 'boto3'"). Here `import boto3` succeeds and the failure has moved to the botocore data catalog, so adding boto3 alone does not close it.

Traces: the 11 failing check ids listed above; see trace_ids.

## Steps to Reproduce
1. iam CreateRole with a lambda.amazonaws.com trust policy plus an inline policy allowing s3vectors:* and bedrock:Retrieve/bedrock:RetrieveAndGenerate/bedrock:InvokeAgent and logs:*.
2. lambda CreateFunction with Runtime=python3.12, Handler=index.handler, MemorySize=256, Timeout=30, Code.ZipFile = a zip containing only index.py:
       import boto3
       def handler(event, context):
           try:
               boto3.client("s3vectors")
               return {"ok": True}
           except Exception as e:
               return {"ok": False, "error_code": type(e).__name__, "error_message": str(e)}
   Poll GetFunction until Configuration.State == Active.
3. lambda Invoke(FunctionName=<fn>, InvocationType=RequestResponse, Payload={}).
4. Observe HTTP 200 whose Payload is {"ok": false, "error_code": "UnknownServiceError", "error_message": "Unknown service: 's3vectors'. Valid service names are: sqs, events, eventbridge, dynamodb"} instead of {"ok": true}. Substituting "bedrock-agent-runtime" (or any service outside sqs/events/eventbridge/dynamodb) for "s3vectors" reproduces identically.
5. For the timeout manifestation: deploy the same handler via a CloudFormation stack (AWS::IAM::Role + AWS::Lambda::Function, Capabilities CAPABILITY_IAM/CAPABILITY_NAMED_IAM), then poll Invoke every 5s for up to 60s waiting for the handler to report s3vectors/bedrock ok=True. The predicate never becomes true and the run is killed at the 60s cap, where on AWS the first invocation already reports ok=True (or AccessDeniedException on an under-permissioned role).
