# Bedrock Runtime is unreachable: every inference, async-invoke and guardrail-check request refused 500 AmbiguousService by signing-name routing

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Converse

## Description
Cause 1 of 1 — the emulator's request router resolves an incoming request to an emulated service by its SigV4 signing name, and six emulated Bedrock-family services share the signing name 'bedrock', so no Bedrock Runtime request is dispatched at all. All 92 behavioral checks listed in trace_ids fail on their first bedrock-runtime call with the same emulator-invented refusal.

AWS: Smithy (smithy_query service_info on services/service-com-amazonaws-bedrockruntime-amazonbedrockfrontendservice/smithy-model/com-amazonaws-bedrockruntime-amazonbedrockfrontendservice.json) — service AmazonBedrockFrontendService, version 2023-09-30, sdkId 'Bedrock Runtime', awsService.endpointPrefix 'bedrock-runtime', sigv4Name 'bedrock', protocols ['restJson1'] with eventStreamHttp over h2/http1.1, 11 bound operations, service-common errors ['AccessDeniedException', 'InternalServerException', 'ThrottlingException', 'ValidationException']. The control-plane model (services/service-com-amazonaws-bedrock-amazonbedrockcontrolplaneservice/...) reports endpointPrefix 'bedrock' with the SAME sigv4Name 'bedrock', so the signing name is not a unique key while the endpoint prefix is. AWS has no 'AmbiguousService' error code: each operation answers its modeled success (Converse/InvokeModel/CountTokens 200 application/json; ConverseStream/InvokeModelWithResponseStream 200 application/vnd.amazon.eventstream; StartAsyncInvoke/GetAsyncInvoke/ListAsyncInvokes 200; ApplyGuardrail 200) or a modeled error from its own list — ValidationException 400, ResourceNotFoundException 404, AccessDeniedException 403, ConflictException 409, ThrottlingException 429, ServiceUnavailableException 503, ModelErrorException, ModelNotReadyException, ModelTimeoutException.

Emulator: every request signed for 'bedrock' is answered HTTP 500 with x-amzn-errortype 'AmbiguousService', content-type 'application/x-amz-json-1.1', body {"__type":"AmbiguousService","message":"6 emulated services all claim requests for 'bedrock': bedrock, bedrock, bedrock, bedrock, bedrock, bedrock; the request is rejected rather than served by an arbitrary one"} (the message text is an example of the router's wording; the 500 status and the 'AmbiguousService' code are the divergence). Observed uniformly on Converse, ConverseStream, InvokeModel, InvokeModelWithResponseStream, CountTokens, ApplyGuardrail, InvokeGuardrailChecks, StartAsyncInvoke, GetAsyncInvoke, ListAsyncInvokes and on CreateGuardrail setup steps. Secondary defect in the same response: this service speaks restJson1, whose responses (errors included) are 'application/json', and whose streaming responses are 'application/vnd.amazon.eventstream'; the refusal uses 'application/x-amz-json-1.1' and carries no event stream at all. Two checks (bedrock-runtime.invoke-model-missing-permission-denied and bedrock-runtime__iam__sts.bedrock-runtime-model-arn-scoped-session-denied-for-second-model) do not even return a code — they report only 'Check timed out after 60.0s', consistent with the SDK retrying the retryable 500 until the check's deadline.

Why: the entire Bedrock Runtime data plane is unusable, and the failure mode is actively harmful rather than merely absent. Because 'AmbiguousService' is returned as a 500, botocore classifies it as retryable and loops ('reached max retries: 3', and in two cases past a 60s deadline) on requests that can never succeed. Clients that branch on modeled errors never see them: checks assert ValidationException for a malformed s3Uri, an undeclared modelInput key, a bad maxResults, an out-of-range temperature; ResourceNotFoundException for an unknown modelId or a nonexistent invocationArn; AccessDeniedException for a foreign account's invocationArn; ServiceUnavailableException distinct from a server error — all get 'AmbiguousService' instead. Streaming clients get no event-stream frames, so no incremental generation, no frame CRC and no chunk ordering can be observed. Even the error-classification contract under concurrency breaks: one check reports "unexpected outcome codes under concurrent load: {'AmbiguousService'}", and another that an empty checks object "must deterministically be ValidationException on every attempt, got ['AmbiguousService','AmbiguousService','AmbiguousService']".

Fix: the request router / service-resolution layer — dispatch on the endpoint prefix (host) and URI path instead of the SigV4 signing name, so 'bedrock-runtime' resolves distinctly from 'bedrock' and the bedrock-agent / bedrock-data-automation families; the same layer must serialize its own refusals with the resolved service's protocol content-type rather than application/x-amz-json-1.1. Only then can the Converse / ConverseStream / InvokeModel / InvokeModelWithResponseStream / CountTokens / ApplyGuardrail / InvokeGuardrailChecks / StartAsyncInvoke handlers, their validation, their event-stream serializers and their async-invoke state be graded.

Traces: all 92 check ids in trace_ids. Representative: bedrock-runtime.converse-basic-text-roundtrip (Converse), bedrock-runtime.converse-stream-reassembles-exactly-what-converse-returns (ConverseStream), bedrock-runtime.invoke-model-nova-native-body-roundtrip (InvokeModel), bedrock-runtime.invoke-model-response-stream-byte-ordering (InvokeModelWithResponseStream), bedrock-runtime.start-async-invoke-lifecycle-and-idempotency (StartAsyncInvoke), bedrock-runtime.invoke-guardrail-checks-structural-roundtrip (InvokeGuardrailChecks), bedrock-runtime.count-tokens-rejects-unsupported-model-not-blanket-failure (CountTokens). The five cross-service ids (bedrock-runtime__cloudwatch.*, bedrock-runtime__iam__sts.*, bedrock-runtime__s3.*) carry composite service tokens whose leading service is bedrock-runtime; each fails on the bedrock-runtime call the router refuses, before any CloudWatch / STS / S3 assertion runs, which is why they are bundled here.
