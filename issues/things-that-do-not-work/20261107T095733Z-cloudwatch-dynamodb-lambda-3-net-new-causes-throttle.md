# cloudwatch__dynamodb__lambda: 3 net-new causes — throttle-refused invokes publish no AWS/Lambda Throttles datapoint, and two DynamoDB-stream→Lambda→CloudWatch checks never complete

> _Note: this issue was identified against the code base at commit `6687e38a12cdc9df434fb5352a33398cb021dd22`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Three net-new root causes on the DynamoDB-stream → Lambda → CloudWatch path. Each must be closed before this issue is submitted.

=== Cause 1 of 3: an invoke refused by reserved-concurrency admission control publishes no AWS/Lambda Throttles datapoint, so the Throttles series stays empty ===
AWS: PutFunctionConcurrency(FunctionName=f, ReservedConcurrentExecutions=0) (Smithy: ReservedConcurrentExecutions @required, @range min 0) sets a reserved ceiling of zero; every subsequent Invoke of f is refused by admission control before any code runs (Smithy: Invoke error TooManyRequestsException, errorKind client, @httpError 429, whose Reason for this class is ReservedFunctionConcurrentInvocationLimitExceeded and whose message is the fixed text "Rate Exceeded."). Beyond the refusal itself, AWS counts EVERY request refused that way in the CloudWatch built-in metric AWS/Lambda Throttles, dimensioned FunctionName=f (recorded behavior only — the metric is not part of the Smithy model). So after N refused invokes, GetMetricStatistics(Namespace='AWS/Lambda', MetricName='Throttles', Dimensions=[{FunctionName: f}], Statistics=['Sum']) sums to exactly N, and AWS/Lambda Invocations counts only the invokes that were admitted. N here is a value of the run (the number of requests the client issued), not a constant.
Emulator: the refusal leg is now correct — the replay passes the (code, message) == ("TooManyRequestsException", "Rate Exceeded.") assertion, the Reason == "ReservedFunctionConcurrentInvocationLimitExceeded" assertion and the HTTP 429 assertion, and after DeleteFunctionConcurrency an invoke is admitted and returns 200 with the handler payload. The metric leg is absent: the AWS/Lambda Throttles series for the function is never created at all. The check polls GetMetricStatistics for up to its remaining budget and fails with "timed out after 46.75s waiting for the AWS/Lambda Throttles metric for this function to reach 2 ...; last observed value was []" — zero Datapoints, not a wrong Sum.
Why: a client cannot observe throttling as AWS exposes it. A CloudWatch alarm on AWS/Lambda Throttles (the standard way to detect a function being refused — including the standard "disable a function" pattern of reserving 0) can never leave INSUFFICIENT_DATA, dashboards and metric-math on Throttles read empty, and no automation keyed on the Throttles series can fire even though the emulator does refuse the requests.
Fix: the AWS/Lambda metric emission behind the Lambda Invoke handler (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs) — the reserved-concurrency admission gate must publish one Throttles datum (Unit=Count, value 1) under FunctionName for each refused request into the same CloudWatch metric state that already serves Invocations, so a Sum read over the window equals the number of refused requests. This is the metric half of open issue 20261027T233731Z-cloudwatch-dynamodb-lambda-invoke-ignores-reserved-concurrency-admission.md: that issue carries this check under a replay key on the refusal assertion (Issue-Key ...|run#7|AssertionError|assert (code, message) == ...), which no longer matches because the refusal now behaves correctly; the check fails further on, at the Throttles poll, and that open issue does not carry this key.
Traces: cloudwatch__dynamodb__lambda.lambda-throttle-metric-visible-in-cloudwatch.

=== Cause 2 of 3: the stream-triggered custom-metric permission scenario never completes — it hangs to the 60 s cap ===
AWS: a DynamoDB-stream ESM (BatchSize=5) on a table whose Lambda's role GRANTS cloudwatch:PutMetricData invokes the handler, the handler's in-function PutMetricData lands, and GetMetricStatistics over the handler's namespace returns at least one datapoint; the identical twin whose role omits cloudwatch:PutMetricData is still invoked (AWS/Lambda Invocations >= 1, Errors == 0 because the handler swallows the AccessDenied) but its namespace stays empty. The whole sequence is observable within the check's budget on the recording.
Emulator: the check never reaches any assertion. The replay reports only "Check timed out after 60.0s", so the stage that stalls is not named in the output. Hypothesis: the leg that cannot settle is the permitted twin's in-function PutMetricData landing as a readable datapoint — the open issue 20261105T111951Z-cloudwatch-dynamodb-lambda-the-lambda-python-runtime-has.md reports that the python runtime has no AWS SDK and that in-function metrics never reach CloudWatch, and 20261104T044826Z-cloudwatch-dynamodb-lambda-custom-cloudwatch-metrics-published-from-a-lambda-never.md reports the same for a different check; neither carries this check's replay key, so neither covers it.
Why: the negative half of this scenario (a metric that must NOT appear without the permission) is only meaningful once the positive half appears, so a client cannot tell "the permission boundary is enforced" from "custom metrics never work at all" — the emulator looks correct for the wrong reason, and any workload that publishes its own metrics from a stream-triggered function hangs instead of failing.
Fix: the in-function CloudWatch PutMetricData path of the Lambda runtime and the ESM delivery loop that drives it (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs and the event-source-mapping poller), so a handler's PutMetricData reaches the same CloudWatch metric state that GetMetricStatistics reads, and the role's lack of cloudwatch:PutMetricData refuses only that call.
Traces: cloudwatch__dynamodb__lambda.ddb-stream-lambda-missing-cloudwatch-permission-negative.

=== Cause 3 of 3: the BatchSize comparison cannot finish inside the check budget — the Invocations count is still unsettled when the budget runs out ===
AWS: two DynamoDB-stream ESMs over the same 20-record burst, one with BatchSize=1 and one with BatchSize=100, produce AWS/Lambda Invocations Sums where the BatchSize=1 mapping invokes at least once per record and the BatchSize=100 mapping invokes strictly fewer times; the count stops advancing (settles) well inside the check's budget, so the comparison can be read (recorded behavior only — Invocations is a CloudWatch built-in metric, not modeled in Smithy).
Emulator: the values themselves look right (the BatchSize=1 probe reaches >= 20 and the BatchSize=100 probe reads 1.0), but getting there consumes almost the whole budget: the check then needs a 30 s quiet window to confirm the count has stopped moving and only ~20.7 s of budget is left, so it fails with "large-batch invocation count did not stabilize within 20.684994003000043s (last=1.0)". The elapsed seconds in that message are a per-run value; the divergence is that the stream-delivery-plus-metric-ingestion path does not reach a settled state early enough in the budget for the BatchSize comparison to be read at all.
Why: a client comparing batching configurations — the normal way to tune an ESM — cannot complete the comparison; the result is a timeout rather than an answer, and any caller that waits for a stream-driven metric to stop advancing before acting never gets there.
Fix: the latency of the DynamoDB-stream event-source-mapping poller and of AWS/Lambda metric ingestion behind it (the event-source-mapping delivery loop and the CloudWatch metric publication it drives), so the Invocations series for a mapping reaches its final value promptly after the last record is delivered instead of still advancing when the budget expires.
Traces: cloudwatch__dynamodb__lambda.ddb-stream-lambda-batch-size-limit-metric.

The empty list is the whole divergence — no Datapoints exist for the series; the 46.75 s and the function name are per-run values.

Cause 2 — expected: the permitted twin's in-function PutMetricData yields >= 1 datapoint in its namespace, the unpermitted twin is still invoked (Invocations >= 1, Errors == 0) and its namespace stays empty; all within the check budget.
Cause 2 — actual (replay, check cloudwatch__dynamodb__lambda.ddb-stream-lambda-missing-cloudwatch-permission-negative): "Check timed out after 60.0s" — no assertion is ever reached, so the emulator never produces the positive datapoint the negative comparison is read against.
