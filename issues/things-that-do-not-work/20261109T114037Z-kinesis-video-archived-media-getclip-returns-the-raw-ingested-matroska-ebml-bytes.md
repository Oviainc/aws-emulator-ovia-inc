# GetClip returns the raw ingested Matroska/EBML bytes instead of muxing an MP4 container, while still declaring Content-Type video/mp4

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetClip

## Description
One net-new root cause in the kinesis-video-archived-media (KVAM) data plane, grounded in two failing behavioral checks. A fixer must close 1 cause before submitting.

Cause 1 of 1: GetClip does not transmux the archived fragments into an MP4 container — it streams back the Matroska bytes it received from PutMedia verbatim.
AWS: Smithy GetClip (POST /getClip, HTTP 200) returns output members ContentType (bound to the Content-Type HTTP header) and Payload (@httpPayload, @streaming blob). AWS's GetClip reference states the operation downloads an MP4 file (clip) containing the archived, on-demand media from the requested stream and time range: the response's ContentType is 'video/mp4' and the Payload is an MP4 container, i.e. its first top-level box is the File Type box, so bytes 4..8 of the payload are the ASCII literal 'ftyp' (preceded by that box's 4-byte big-endian size). The media ingested through PutMedia as Matroska (MKV) fragments must be re-containerised: the H.264 access units ingested in SimpleBlocks appear in the MP4's media data, and the track's CodecPrivate (AVCDecoderConfigurationRecord) becomes the avcC sample description — this is why GetClip models MissingCodecPrivateDataException ('No codec private data was found in at least one of tracks of the video stream.', errorKind client, httpError 400) and InvalidCodecPrivateDataException at all: the mux needs that record.
Emulator: ContentType is correctly 'video/mp4', but the Payload body begins b'\x1aE\xdf\xa3\xa3B\x86\x81\x01B\xf7\x81' — the EBML header magic 0x1A45DFA3 followed by the EBMLVersion/EBMLReadVersion elements of the very MKV stream the check pushed through PutMedia. Bytes 4..8 are not 'ftyp'; no MP4 box structure is produced at all. The emulator is echoing the stored ingest bytes as the clip payload, so the declared Content-Type contradicts the body it serves.
Why: any client that does what the documented contract allows — hand the GetClip payload to an MP4 demuxer/player, probe the ftyp brand, write it to a .mp4 file, or feed it to a pipeline that trusts the video/mp4 header — fails on a byte stream that is Matroska. The failure is silent at the HTTP layer (200 + video/mp4) and only surfaces as a corrupt/unplayable file, so clients validated against the emulator ship code that cannot consume real GetClip output. It also masks every codec-private-data refusal GetClip models: because no mux is attempted, a stream whose track declares no CodecPrivate is served a 200 clip instead of being refused HTTP 400 MissingCodecPrivateDataException (that downstream assertion in get-clip-missing-codec-private-data-rejected is unreachable until the mux exists, so it is reported here as part of the same cause rather than as a separate one).
Fix: GetClip's payload construction in the KVAM data-plane handler — build the clip from the selected fragment index by remuxing the stored Matroska fragments into an MP4 (ftyp + moov with an avcC sample description taken from the track's CodecPrivate + the frame data), and keep the ContentType header consistent with the container actually emitted; the codec-private-data preconditions of that mux are what raise MissingCodecPrivateDataException / InvalidCodecPrivateDataException.
Traces: kinesis-video-archived-media.list-fragments-and-get-clip-serve-ingested-video, kinesis-video-archived-media.get-clip-missing-codec-private-data-rejected.

Related open issues on this service do NOT own this cause: 20261029T202349Z-kinesis-video-archived-media-data-plane-streams-never.md covers stream resolution, GetClip range validation, GetMediaForFragmentList and ListFragments refusal wording and the GetImages authorization gate; 20261030T210022Z (ListFragments empty list), 20261031T164553Z (GetImages input validation), 20261107T004725Z (data endpoint scheme) and 20261108T005310Z (GetImages IAM deny) are all about other operations or other paths. None of them mentions the clip container format, and neither of the two checks listed above is carried by any of them.

## Evidence
Check kinesis-video-archived-media.list-fragments-and-get-clip-serve-ingested-video: after PutMedia ingests two H.264 frames as MKV and ListFragments reports both PERSISTED fragments, GetClip(StreamName=<stream>, ClipFragmentSelector={FragmentSelectorType: PRODUCER_TIMESTAMP, TimestampRange: {StartTimestamp: start-60, EndTimestamp: start+600}}) answers HTTP 200 with ContentType 'video/mp4' (as expected) but a payload whose first 12 bytes are b'\x1aE\xdf\xa3\xa3B\x86\x81\x01B\xf7\x81'. Expected payload[4:8] == b'ftyp' (MP4 File Type box); got b'\xa3B\x86\x81'. Assertion: "GetClip must return an MP4 container, got b'\x1aE\xdf\xa3\xa3B\x86\x81\x01B\xf7\x81'". The follow-on requirement of the same check — that the MP4 carry both ingested access units' payload bytes — is therefore also unmet.
Check kinesis-video-archived-media.get-clip-missing-codec-private-data-rejected: its positive control (a stream whose track DOES declare CodecPrivate / AVCDecoderConfigurationRecord) fails identically — "positive control must clip the stream whose track declares CodecPrivate, got b'\x1aE\xdf\xa3\xa3B\x86\x81\x01B\xf7\x81'" — so the check never reaches its negative class, where AWS refuses the sibling stream with no CodecPrivate using HTTP 400, code MissingCodecPrivateDataException, message 'Missing codec private data in fragment for track 1.' (fixed text; the track number is taken from the offending track in the request's stream).
The specific stream names, fragment numbers and timestamps in these runs are per-run values and are not part of the requirement; the HTTP 200, the ContentType 'video/mp4' and an MP4-container payload are.

## Steps to Reproduce
1. Replay the behavioral suite simparity-behavioral-aws-v1 against the emulator (service kinesis-video-archived-media).
2. Run check list-fragments-and-get-clip-serve-ingested-video: create a stream via kinesisvideo CreateStream (DataRetentionInHours=1), wait for ACTIVE, resolve PUT_MEDIA via GetDataEndpoint, PutMedia an MKV segment carrying two H.264 IDR frames with the track's CodecPrivate set to the AVCDecoderConfigurationRecord, wait for both fragments to be PERSISTED and listed by ListFragments.
3. Resolve GET_CLIP via GetDataEndpoint and call GetClip with ClipFragmentSelector FragmentSelectorType=PRODUCER_TIMESTAMP and a TimestampRange spanning the ingest.
4. Read the Payload stream: inspect bytes 0..12. The emulator returns the EBML/Matroska header (b'\x1aE\xdf\xa3...') rather than an MP4 whose bytes 4..8 are b'ftyp', even though the Content-Type header says video/mp4.
5. Run check get-clip-missing-codec-private-data-rejected: the same ingest-and-clip flow fails on its positive control for the same reason; once the mux is in place, the sibling stream ingested WITHOUT CodecPrivate must be refused HTTP 400 MissingCodecPrivateDataException with message 'Missing codec private data in fragment for track 1.'
