# REOPENS: the OpenSearch domain REST data plane is unrouted again — every signed/basic-auth request to DomainStatus.Endpoint answers 404 UnknownService 'es' (2 causes)

> _Note: this issue was identified against the code base at commit `78e103bf1f1da55b7fd78818f2069120cd5b46a5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DomainRestDataPlane

## Description
REOPENS 20261029T121521Z-opensearch-domain-rest-endpoint-serves-nothing-so-a.md: its fix left the call refused.

That issue was filed on exactly this replay key (Issue-Trace-Ids: opensearch.deploy-domain-cfn-access-policy-enforced) and is marked fixed; the same check is refused again with the identical 404 UnknownService 'es' body. The intervening open issue 20261101T140814Z-opensearch-the-domain-rest-data-plane-serves-only.md records in its own text that the data plane HAD become reachable at commit 67f5fadccaf81bef3549b8820a70ca0b0ed0533e ("signed requests to DomainStatus$Endpoint no longer answer 404 UnknownService 'es'") and goes on to grade routes BEHIND that endpoint, so the endpoint has regressed from served back to unrouted. This is therefore not a new defect report but the re-refusal of a call a fixed issue claimed to serve. Open issue 20261029T182036Z-opensearch-the-domain-rest-data-plane-answers-404.md describes the same family but does not carry any of the replay keys listed here (the suite reported none of these checks as owned by it).

Two causes, each with its own failing check ids.

Cause 1 of 2 — the 'es' endpoint prefix / published domain endpoint host is not registered in the request router, so every SigV4-signed data-plane request is answered by the generic front door with 404 UnknownService.
AWS: Smithy (com.amazonaws.opensearch#AmazonOpenSearchService; awsService.endpointPrefix 'es', sigv4Name 'es') documents DomainStatus$Endpoint as the "Domain-specific endpoint used to submit index, search, and data upload requests to the domain." A domain reported Created=true / Processing=false with an Endpoint therefore answers SigV4-signed ('es') HTTPS requests at that host AS AN OPENSEARCH ENGINE: PUT /{index} creates an index and answers 200 {"acknowledged":true}; PUT /{index}/_doc/{id} answers 201 with result "created"; GET /{index}/_doc/{id} answers 200 with the stored _source; POST /{index}/_search answers 200 with a hits envelope; GET / and GET /_nodes answer 200 with the cluster/node document; PUT /_cluster/settings, PUT /_plugins/_ism/policies/{id} and the snapshot/restore routes answer their documented 200/201. Where an engine body is not stated by the model this is recorded behavior only; the requirement under test is that the host the control plane PUBLISHED is served at all, and that the domain's stored AccessPolicies document is evaluated per signing principal (explicit Deny wins, refused with HTTP 403 whose body states the principal is not authorized).
Emulator: every request to that host — whatever the method, path or principal — is answered with HTTP 404 and the body {"__type": "UnknownService", "message": "no emulated service is registered for 'es'"}. Fixed text of that message: "no emulated service is registered for '" + the endpoint prefix + "'"; the variable part is the resolved endpoint prefix, here 'es'. It is not an OpenSearch response and not an AWS error shape for this service: there is no __type in the opensearch model named UnknownService, and the engine's own error envelope ({"error": {"type": ...}, "status": ...}) is absent. Because the answer is identical for every principal, an AccessPolicies Allow and an explicit Deny are indistinguishable.
Why: a client that provisions a domain (directly or through an AWS::OpenSearchService::Domain stack), reads DomainStatus.Endpoint and then talks to it cannot index, refresh, search, read _nodes, drive an ISM policy, or snapshot/restore anything — the service's entire purpose is unreachable. Worse, no OpenSearch client or AWS SDK recognises a 404 UnknownService body, so the failure surfaces as an unparseable response rather than a refusal, and resource-policy authorization is unobservable: a caller cannot verify that the AccessPolicies document it deployed denies the principal it meant to deny, so a deny-by-policy posture silently reads as untestable.
Fix: the emulator's request router must register and serve the 'es' endpoint prefix and the per-domain endpoint host again, dispatching to the domain-scoped index/search engine behind it (the domain REST data-plane router in the opensearch service crate, services/service-com-amazonaws-opensearch-amazonopensearchservice/src/service/domain_rest.rs, which open issue 20261101T140814Z names as the module that was serving these routes); that engine's request path needs the SigV4 principal resolution and AccessPolicies evaluation the earlier fix added, before route dispatch.
Traces: opensearch.deploy-domain-cfn-access-policy-enforced (poll for {200,201} never leaves 404), opensearch.access-policy-denies-data-plane-index-path, opensearch.cluster-settings-flat-form-only-and-auto-create-index-false-refuses-implicit-index, opensearch.e2e-data-source-attachment-ingest-search-detach, opensearch.e2e-package-association-search-flow, opensearch.ism-policy-transition-sets-read-only-and-unmet-condition-stays-writable, opensearch.nested-mapping-isolates-sub-documents-from-flattened-object-matching, opensearch.nodes-apis-redact-service-internals-while-reporting-the-configured-topology, opensearch.osq-deep-opensearch-2-highlight-wraps-matched-term-on-text-but-not-keyword-sibling, opensearch.restore-over-open-index-rejected, opensearch.snapshot-restore-index-round-trip.

Cause 2 of 2 — the FGAC internal-user (HTTP basic auth) path on the same published endpoint never answers an authorized call, so the role-pattern denial walk never reaches a verdict.
AWS: fine-grained access control authenticates the internal user database over HTTP basic auth, not SigV4. Recorded behavior only: a domain created with AdvancedSecurityOptions.InternalUserDatabaseEnabled answers the master user's basic-auth GET /_cluster/health with HTTP 200 once the security plugin has loaded, then serves PUT /{index} (200), PUT /{index}/_doc/{id} (201), POST /{index}/_refresh (200), and the security-plugin config routes PUT /_plugins/_security/api/roles/{role}, /internalusers/{user} and /rolesmapping/{role} (201 each). An internal user mapped to a role whose index_patterns do not match an index is then refused HTTP 403 with error.type "security_exception" naming the refused action "indices:data/read/search", while the master user still reads the same document 200.
Emulator: the check is cut off — "Check timed out after 180.0s" — with no verdict produced. Its first barrier is _wait_admin_auth, a 420 s poll of the master user's basic-auth GET /_cluster/health that only exits on HTTP 200; that poll is longer than the harness cap, so a barrier that never turns 200 consumes the whole check. Hypothesis: this is the same unrouted endpoint as Cause 1 (the basic-auth request reaches the same host and is answered 404 UnknownService 'es', which is never 200), so serving the endpoint should close this too — it is listed as its own cause only because its recorded symptom is a timeout, not a 404 body, and must be confirmed separately.
Why: the whole FGAC authorization surface (internal users, roles, role mappings, index-pattern scoping) is unverifiable, and a client waiting on the documented barrier hangs instead of being told anything, burning its entire deadline rather than receiving a refusal.
Fix: the same data-plane router and its authentication layer — the basic-auth credential path into the security-plugin's internal user/role/rolesmapping state in the opensearch service crate, reached once the 'es' host is routed again.
Traces: opensearch.osm-fgac-role-pattern-read-outside-pattern-denied.
