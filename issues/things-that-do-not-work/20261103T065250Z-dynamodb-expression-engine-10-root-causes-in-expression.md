# DynamoDB expression engine: 10 root causes in expression parsing, condition error classes, limit messages and error precedence

> _Note: this issue was identified against the code base at commit `ce4f28f15b4841beefbad6c596b9d2158570753e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Query

## Description
Ten net-new root causes in the DynamoDB expression/validation layer. Each is an emulator defect; the listed checks are examples. All ten must be closed before submitting.

Cause 1 of 10: the expression parser reports every defect as one generic parser error. AWS: an expression defect is reported by CLASS with a specific ValidationException message -- an empty expression is 'Invalid <Member>: The expression can not be empty;', a function given a literal where a path is required is 'Invalid <Member>: Operator or function requires a document path; operator or function: attribute_exists', and wrong arity is 'Invalid <Member>: Incorrect number of operands for operator or function; operator or function: attribute_exists, number of operands: 2' (Smithy: Query.FilterExpression/ConditionExpression target ConditionExpression; the service's common error is ValidationException, 400). Emulator: all of them come back as 'Invalid FilterExpression: Syntax error; token: "<EOF>", near: ""' / 'Invalid FilterExpression: Syntax error; token: ")", near: ":v )"' / 'Invalid FilterExpression: Syntax error; token: ",", near: "#a , #a"'. Fixed text is the AWS sentence; the variable parts are the member name (FilterExpression/ConditionExpression/UpdateExpression/ProjectionExpression), the function name and the operand count taken from the request. Why: clients that branch on the message class (and the many SDK/ORM layers that surface it) cannot tell an empty expression from a mis-arity call. Fix: the expression parser/validator shared by the item and query handlers. Checks: dynamodb.ddb-frc-empty-filter-expression-rejected, dynamodb.ddb-sfa-unused-expression-attribute-name-in-scan-rejected, dynamodb.empty-string-expression-rejected-across-operations, dynamodb.ddb-sfa-attribute-exists-on-a-value-placeholder-rejected, dynamodb.ddb-sfa-attribute-exists-with-two-operands-rejected, dynamodb.transact-write-items-condition-expression-defects-match-putitem-message, dynamodb.expression-attribute-map-key-syntax-and-length-rejected, dynamodb.transact-write-expression-parse-errors-rejected-top-level.

Cause 2 of 10: KeyConditionExpression analysis rejects legal forms and mislabels illegal ones. AWS: a value-first comparison (':lo <= sk') is LEGAL and must be served; an illegal operator/operand on the sort key is 'Invalid KeyConditionExpression: Incorrect operand type for operator or function; operator or function: begins_with, operand type: N'; two clauses on one key is 'Invalid KeyConditionExpression: KeyConditionExpressions must only contain one condition per key'. Emulator: ':lo <= sk' is refused ValidationException 'Invalid KeyConditionExpression: Syntax error; token: "<=", near: ":lo <= sk"'; the operand-type case is answered 'One or more parameter values were invalid: Type mismatch for key sk expected: S actual: N'; the duplicate clause is 'Invalid key condition: the sort key sk is constrained more than once'; a document path on the partition key is 'Query condition missed key schema element: pk'. Why: a legal query fails outright, and the error text for the illegal ones is not AWS's. Fix: Query's key-condition analyser. Checks: dynamodb.query-value-first-sort-key-comparison-and-size-of-absent-attribute, dynamodb.key-condition-illegal-sort-key-operator-rejected, dynamodb.query-key-condition-operand-type-vs-schema-type-rejected, dynamodb.query-key-condition-duplicate-sort-key-clause-and-nested-path-rejected, dynamodb.query-key-condition-document-path-forms-and-reserved-head-rejected.

Cause 3 of 10: a malformed or non-orderable condition operand is EVALUATED instead of validated, so the call is refused with the wrong error class. AWS: a type error in a condition is a ValidationException (400) before evaluation -- a BOOL operand under '<', an unknown type name in attribute_type, a malformed N literal, reversed BETWEEN bounds. Emulator: these come back as ConditionalCheckFailedException 'The conditional request failed' (and inside a transaction as TransactionCanceledException 'Transaction cancelled, please refer cancellation reasons for specific reasons [ConditionalCheckFailed, None]'). Why: a caller sees a business-logic conflict where AWS reports a bad request, so retry/compensation logic fires on a permanent defect. Fix: condition-expression type validation, ahead of evaluation, in the item/transact handlers. Checks: dynamodb.condition-expression-contains-same-path-and-between-reversed-rejected, dynamodb.condition-ordering-comparison-non-orderable-literal-rejected, dynamodb.ddb-sfa-condition-attribute-type-with-an-unknown-type-name-rejected, dynamodb.malformed-n-in-expression-value-rejected-before-evaluation, dynamodb.delete-item-condition-between-bounds-validated, dynamodb.transact-write-condition-non-orderable-literal-rejected.

Cause 4 of 10: placeholder maps supplied with NO expression get the 'unused placeholder' message instead of the 'only with expressions' message. AWS: '1 validation error detected: ExpressionAttributeValues can only be specified when using expressions' (and the ExpressionAttributeNames counterpart). Emulator: 'Value provided in ExpressionAttributeValues unused in expressions: keys: {:v}' / 'Value provided in ExpressionAttributeNames unused in expressions: keys: {#a}'. The fixed text is AWS's sentence; the only variable part in AWS's form is the member name. Why: the two cases are different defects and the emulator conflates them. Fix: the request-level placeholder validation shared by PutItem/UpdateItem/Query/TransactWriteItems. Checks: dynamodb.expression-attribute-placeholders-without-an-expression-rejected, dynamodb.query-and-update-item-placeholders-without-an-expression-rejected, dynamodb.transact-items-accept-placeholders-without-an-expression, dynamodb.expression-attribute-keys-without-prefix-rejected-on-item-ops.

Cause 5 of 10: the '1 validation error detected: ' prefix is applied to messages that do not carry it and omitted from ones that do. AWS: the prefix marks a Smithy constraint violation only; the expression/semantic messages above carry no prefix. Emulator: emits '1 validation error detected: Value provided in ExpressionAttributeValues unused in expressions: keys: {:unused}' where AWS emits it bare, and '1 validation error detected: Invalid FilterExpression: Expression size has exceeded the maximum allowed size;' where AWS has no prefix. Why: clients and fixtures matching on the message see a different string for the same defect. Fix: the ValidationException formatter. Checks: dynamodb.transact-write-items-duplicate-key-rejected, dynamodb.transact-write-items-unused-expression-attribute-value-on-second-action-rejected, dynamodb.transact-unused-expression-attribute-name-on-condition-check-and-get-rejected, dynamodb.filter-and-key-condition-expression-size-limit-rejected.

Cause 6 of 10: constraint-violation messages name the wrong member path/case and report violations AWS suppresses. AWS: the member is named by its MODELED path and case -- "Value at 'TotalSegments' failed to satisfy constraint: Member must have value less than or equal to 1000000", and inside a transaction "Value 'bad name' at 'transactItems.1.member.put.tableName' failed to satisfy constraint: Member must satisfy regular expression pattern: [a-zA-Z0-9_.-]+"; an over-length ClientRequestToken (Smithy: TransactWriteItems.ClientRequestToken @length max 36) masks the other violations and is reported alone. Emulator: uses lowercase 'totalSegments', flattens the transact path to 'tableName', and reports '2 validation errors detected: ...returnConsumedCapacity...; Value at 'ClientRequestToken'...'. Why: the member path is how a client locates the offending field. Fix: the constraint-violation serializer. Checks: dynamodb.ddb-gsi-scan-total-segments-above-one-million-rejected, dynamodb.transact-write-items-invalid-table-name-names-member-path, dynamodb.transact-write-items-overlength-token-masks-other-violations-rejected.

Cause 7 of 10: every size-limit refusal carries one generic message, and the 4 MB transaction aggregate is not enforced at all. AWS: the 400 KB item limit is reported with the op-specific message naming the item/update path, and TransactWriteItems over 4 MB aggregate is refused with ValidationException. Emulator: answers 'Item size has exceeded the maximum allowed size' for PutItem, UpdateItem SET, TransactWriteItems update and PartiQL growth alike, and ACCEPTS the over-4 MB transaction with HTTP 200. Why: a client cannot tell which action in a batch/transaction exceeded the limit, and an oversized transaction silently commits. Fix: size accounting in the item/transact/PartiQL handlers and their refusal messages. Checks: dynamodb.item-size-limit-enforced-at-400kb, dynamodb.update-item-set-list-append-add-exceeding-400kb-rejected, dynamodb.transact-write-items-update-grows-item-over-size-limit, dynamodb.partiql-update-growth-past-400kb-matches-update-item, dynamodb.transact-write-aggregate-size-over-4mb-rejected.

Cause 8 of 10: the nesting-depth refusal uses a non-AWS message and the wrong precedence. AWS: over-deep attributes are refused with the documented nesting message, and when another defect is also present the OTHER defect (e.g. the ConditionalOperator enum violation) is reported first; inside a transaction the nesting violation is a top-level ValidationException, not a cancellation. Emulator: always answers '1 validation error detected: Nesting Levels have exceeded supported limits: Attributes in the item have nested levels beyond supported limit', including where AWS reports the enum violation instead. Why: error precedence is part of the contract clients debug against. Fix: item validation ordering in PutItem/BatchWriteItem/TransactWriteItems. Checks: dynamodb.nesting-depth-error-precedence-across-malformed-requests, dynamodb.nesting-depth-limit-covers-transact-condition-check-and-legacy-expected-values, dynamodb.batch-write-item-rejects-whole-call-for-one-oversized-nested-put, dynamodb.transact-write-items-nesting-violation-is-top-level-validation-not-cancellation.

Cause 9 of 10: request validation does not precede resource lookup, so the wrong error class is returned. AWS: a malformed request against a MISSING table is a ValidationException (the request is checked first) -- e.g. '1 validation error detected: One or more parameter values were invalid: Value or AttributeValueList must be used with ComparisonOperator: EQ for Attribute: a' -- and an oversized item to a missing table is ResourceNotFoundException on PutItem but a validation refusal on BatchWriteItem. Emulator: answers ResourceNotFoundException 'Requested resource not found' for the malformed call, 'Item size has exceeded the maximum allowed size' for the missing-table put, ResourceNotFoundException where a transaction's first fatal defect is a validation one, and "1 validation error detected: Value null at 'Key' failed to satisfy constraint: Member must not be null" where AWS names the real defect. Fix: validation-before-lookup ordering in the data-plane dispatch. Checks: dynamodb.request-validation-precedes-missing-table-lookup-rejected, dynamodb.oversized-item-to-a-missing-table-not-found-on-put-rejected-on-batch-write, dynamodb.transact-write-items-first-fatal-defect-reported-depends-on-defect-class, dynamodb.multiple-simultaneous-constraint-violations-rejected, dynamodb.batch-request-items-key-not-a-table-name-rejected.

Cause 10 of 10: the empty-string secondary-index-key refusal uses a non-AWS message. AWS: 'One or more parameter values are not valid. The update expression attempted to update a secondary index key to a value that is not supported. The AttributeValue for a key attribute cannot contain an empty string value.' -- fixed text, no index name interpolated. Emulator: 'One or more parameter values are not valid. A value specified for a secondary index key is not supported. The AttributeValue for a key attribute cannot contain an empty string value. IndexName: gsi1, IndexKey: gpk', and inside a transaction it cancels instead of validating. Fix: index-key validation in the item/transact write path. Checks: dynamodb.put-batch-write-update-index-key-empty-value-rejected, dynamodb.transact-write-items-empty-index-key-validates-not-cancels, dynamodb.update-item-and-transact-update-empty-gsi-and-lsi-keys-rejected, dynamodb.transact-write-items-update-key-and-empty-index-key-rejections.
