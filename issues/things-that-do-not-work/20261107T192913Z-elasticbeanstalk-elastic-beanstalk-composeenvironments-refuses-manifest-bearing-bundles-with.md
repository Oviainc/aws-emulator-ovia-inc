# Elastic Beanstalk: ComposeEnvironments refuses manifest-bearing bundles with MissingParameter, created platform versions are not counted by ListPlatformVersions, RebuildEnvironment drives no transition, and RetrieveEnvironmentInfo hands out a URL that 404s (4 causes)

## Description

Cause 1 of 4: ComposeEnvironments rejects every request with MissingParameter claiming the env.yaml manifest is unavailable, even when the referenced versions' source bundles carry it.
AWS: Smithy: ComposeEnvironments(ApplicationName len 1..100, GroupName len 1..19, VersionLabels) -> EnvironmentDescriptionsMessage{Environments, NextToken}; modeled errors only InsufficientPrivilegesException (403) and TooManyEnvironmentsException (400) — MissingParameter is not among them. Recorded behavior: for application versions whose bundles contain an env.yaml manifest naming the environment, the call succeeds (HTTP 200) and returns one EnvironmentDescription per version label, each transitioning Launching -> Ready with the tier taken from the manifest; composing the same group twice does not duplicate environments.
Emulator: every ComposeEnvironments call is refused with error code MissingParameter and the message "The environment manifest (env.yaml) naming the environment to compose is not available from the source bundle of version label '<label>'." — the fixed text is the sentence, and the only variable part is the version label, yet the emulator also interpolates the WHOLE VersionLabels list into that single-label slot, producing "... of version label 'front-v1', 'worker-v1'." for a two-label request. Hypothesis: the handler never reads the uploaded bundle from the storage location, so the manifest can never be found.
Why: group/multi-tier composition is unusable — the documented success path always fails, with an error code the operation does not model; a client cannot even distinguish a genuinely manifest-less bundle from one it uploaded correctly. It also masks the authorization refusal: the privileges check must precede manifest validation (see the OWNED issue 20261023T205650Z-elasticbeanstalk-elastic-beanstalk-control-plane-guards-are-not-enforced.md for the AccessDenied gate itself), so an unprivileged caller now sees MissingParameter.
Fix: the ComposeEnvironments handler — reading each referenced version's source bundle from its S3 location, parsing env.yaml, and creating one environment per manifest in the service's environment state (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/compose_environments.rs plus the service state module); the message template must bind exactly one version label.
Traces: elasticbeanstalk.compose-environments-creates-envs-from-versions-lifecycle, elasticbeanstalk.compose-environments-concurrent-launch-no-duplicate-envs, elasticbeanstalk.compose-environments-insufficient-privileges-denied, elasticbeanstalk.e2e-compose-environments-from-templates-produces-linked-envs, elasticbeanstalk.e2e-compose-multi-tier-application-environments, elasticbeanstalk.e2e-compose-swap-cnames-traffic-consequence.

Cause 2 of 4: platform versions created by CreatePlatformVersion are never counted by ListPlatformVersions, so the custom-platform quota can never be reached.
AWS: Smithy: CreatePlatformVersion(PlatformName, PlatformVersion, PlatformDefinitionBundle required) -> CreatePlatformVersionResult{PlatformSummary, Builder}, errors ElasticBeanstalkServiceException (400), InsufficientPrivilegesException (403), TooManyPlatformsException (400); ListPlatformVersions -> ListPlatformVersionsResult{PlatformSummaryList}. Recorded behavior: each successfully created custom platform version appears in ListPlatformVersions for the account, so after creating N of them the account's custom-platform count is N; at the account's CustomPlatformQuota (50) the next CreatePlatformVersion is refused with TooManyPlatformsException.
Emulator: CreatePlatformVersion returns 200 with a PlatformSummary, but ListPlatformVersions keeps counting 0 of the account's own platform versions — "expected the account to sit at its CustomPlatformQuota of 50 after creating 50 platform version(s), ListPlatformVersions counts 0".
Why: a client cannot enumerate, select or delete the custom platforms it created, and cannot observe or test the quota boundary; the quota refusal is unreachable through the documented path.
Fix: the CreatePlatformVersion handler must register the created platform version in the service's platform state, and ListPlatformVersions must enumerate the account's own platform versions from that state (src/ops/create_platform_version.rs, src/ops/list_platform_versions.rs and the platform state module).
Traces: elasticbeanstalk.create-platform-version-too-many-platforms-rejected.

Cause 3 of 4: RebuildEnvironment is accepted but the environment never reports a transitional status.
AWS: Smithy: RebuildEnvironment(EnvironmentId | EnvironmentName len 4..40) -> Unit, modeled error InsufficientPrivilegesException (403). Recorded behavior: against a Ready environment the call is accepted AND the environment reports a transitional EnvironmentStatus ('Updating', per the EnvironmentStatus enum's documented 'Environment is in the process of updating its configuration settings or application version') before settling back to 'Ready'.
Emulator: the call returns success and DescribeEnvironments reports 'Ready' for the whole poll window — "expected RebuildEnvironment to move the environment through a transitional Updating status before Ready, last observed 'Ready'". Hypothesis: the handler validates and returns without scheduling the status transition the state module already models for Launching/Terminating.
Why: a client that rebuilds and then waits for the environment to cycle cannot tell the rebuild happened at all, and any wait-for-transition logic either hangs or proceeds while the rebuild is notionally still running.
Fix: the RebuildEnvironment handler and the Updating -> Ready transition it must schedule (src/ops/rebuild_environment.rs plus the clock-owed transitions in the service's state module).
Traces: elasticbeanstalk.rebuild-environment-cycles-through-launching-to-ready.

Cause 4 of 4: the URL RetrieveEnvironmentInfo reports cannot be fetched — it answers HTTP 404.
AWS: Smithy: RequestEnvironmentInfo(InfoType required) then RetrieveEnvironmentInfo(InfoType required) -> RetrieveEnvironmentInfoResultMessage{EnvironmentInfo: EnvironmentInfoDescriptionList}, whose Message member is documented as "The retrieved information. Currently contains a presigned Amazon S3 URL. The files are deleted after 15 minutes." Recorded behavior: fetching that URL returns HTTP 200 and the compiled log bundle body.
Emulator: RetrieveEnvironmentInfo returns an EnvironmentInfoDescription whose Message is a URL that does not resolve to an object — the fetch raises urllib.error.HTTPError: HTTP Error 404: Not Found. Hypothesis: the handler synthesizes a presigned-looking URL without writing the bundle object behind it.
Why: log retrieval is wholly unusable: the operation reports success and hands the client a dead link, so no caller can ever read the environment information it requested.
Fix: the environment-information compile behind RequestEnvironmentInfo / RetrieveEnvironmentInfo — it must store the bundle object and report a URL that serves it (src/ops/request_environment_info.rs, src/ops/retrieve_environment_info.rs and the environment-information state).
Traces: elasticbeanstalk.environment-info-log-payload-preserved.
