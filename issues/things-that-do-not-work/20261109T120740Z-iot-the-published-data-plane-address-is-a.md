# iot: the published data-plane address is a real-AWS host the emulator does not serve — DescribeEndpoint(iot:Data-ATS) and the apigatewayv2 ApiEndpoint it chains to make the whole IoT data plane unreachable (2 causes)

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEndpoint

## Description
Two net-new root causes, both of the same kind: an operation answers 200 with an endpoint address that names a real AWS host instead of the address the emulator is actually reached on, so every client that follows the published address leaves the emulator and the operations behind that address are never exercised.

Cause 1 of 2: iot DescribeEndpoint(endpointType="iot:Data-ATS") publishes an account-shaped AWS ATS hostname that the emulator does not serve.
AWS: Smithy (service-com-amazonaws-iot-awsiotservice): DescribeEndpoint — GET /endpoint, input member endpointType bound to the httpQuery "endpointType" (@length 0..128), output member endpointAddress : EndpointAddress, modeled errors InternalFailureException (500), InvalidRequestException (400), ThrottlingException (400), UnauthorizedException (401). The contract of the operation is that endpointAddress is the address of the caller's own data plane: the host that serves the Thing Shadow / retained-message / Publish HTTPS API on 443 and the MQTT broker on 8883 for that account and region. On AWS the value resolves to and is served by the endpoint the caller then uses; the address is a per-account, per-region value, never a fixed string.
Emulator: DescribeEndpoint returns 200 with a hostname of AWS's public form (an "<prefix>-ats.iot.<region>.amazonaws.com" style name) which is not one of the emulator's own hosts and which the emulator does not listen on. Replay refuses to follow it: "endpoint_url was given https://<prefix>-ats.iot.<region>.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://<own host>:<port>/<path>". Nothing behind the address is reached, so the entire iot-data plane (UpdateThingShadow / GetThingShadow / DeleteThingShadow / Publish / GetRetainedMessage) is unreachable through the documented discovery path, and all 18 shadow, retained-message and mTLS/sigv4 publish checks below stop at endpoint discovery with no data-plane call made at all.
Why: the documented and only supported way for a client to find the IoT data plane is DescribeEndpoint. A client that honours the returned address (every AWS SDK example and the AWS CLI's documented iot-data usage does) is sent to a host outside the emulator — in a sealed environment the call fails to connect, and in a connected one it would be sent to real AWS. Shadow versioning, delta computation, retained messages and policy enforcement can never be observed even though those handlers may exist.
Fix: the iot DescribeEndpoint handler's endpoint-address construction in the iot service crate — the address it serves must be the emulator's own serving host (and port, where the listener is not on 443) for the requested endpointType, not a synthesized amazonaws.com name. The same construction feeds iot:Data, iot:Data-ATS, iot:CredentialProvider and iot:Jobs and should resolve to an address the emulator answers on for each.
Note: 20261022T012827Z-iot-describeendpoint-stub.md (fixed) made DescribeEndpoint answer rather than refuse; it is not reopened here because the call now succeeds — the defect is the value it serves. No open issue listed by list_existing_issues covers the published value.

Cause 2 of 2: the HTTP topic-rule-destination trajectory cannot run because the apigatewayv2 API the destination points at publishes an execute-api address the emulator does not serve.
AWS: Smithy (service-com-amazonaws-apigatewayv2-apigatewayv2): Api member ApiEndpoint is documented as "The URI of the API, of the form {api-id}.execute-api.{region}.amazonaws.com" — on AWS that URI is served by the API itself, so CreateApi's caller can POST to ApiEndpoint and reach the integration. recorded behavior only for the emulator case: the recording shows the caller taking ApiEndpoint + "/" and both self-testing it and handing it to iot CreateTopicRuleDestination as the HTTP confirmation URL.
Emulator: CreateApi answers 200 with an ApiEndpoint of the literal AWS public form ("https://<api-id>.execute-api.<region>.amazonaws.com/") that is not one of the emulator's own hosts, so replay refuses it with the same PublishedUrlRejected diagnosis as cause 1. The destination is never created or confirmed and the unconfirmed-vs-ENABLED delivery gate reaches no verdict.
Why: a client that uses ApiEndpoint as published — as both the IoT topic-rule-destination confirmation flow and any HTTP caller must — is sent off the emulator, so an HTTP-integration estate built against the emulator cannot be driven end to end even though the control-plane calls all succeed.
Fix: the apigatewayv2 CreateApi/GetApi handler's ApiEndpoint construction (and the per-resource listener it should name) must publish an address the emulator answers on; the iot CreateTopicRuleDestination handler must likewise accept and fetch such an address for its confirmation POST.

## Evidence
Cause 1 — expected: DescribeEndpoint(endpointType='iot:Data-ATS') -> 200 {"endpointAddress": "<host the emulator serves>"}, and the subsequent iot-data call against it returns the shadow document. Actual: 200 with a host of AWS's public ATS form; replay aborts before any data-plane call with simparity.published.PublishedUrlRejected: "endpoint_url was given https://<prefix>-ats.iot.<region>.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". 18 checks fail this way, all at the endpoint-discovery step; the fixed and generated parts of the address are: fixed = the AWS public suffix the emulator must NOT serve; variable = the per-account prefix and region. The only requirement is that the value be an address the emulator answers on.

Cause 2 — expected: apigatewayv2 CreateApi -> 200 with ApiEndpoint reachable by the caller, then POST ApiEndpoint/ reaches the AWS_PROXY integration and iot CreateTopicRuleDestination(httpUrlConfiguration.confirmationUrl=ApiEndpoint) confirms. Actual: ApiEndpoint = "https://<api-id>.execute-api.<region>.amazonaws.com/", refused with the same PublishedUrlRejected diagnosis; the confirm-then-deliver and unconfirmed-blocks-delivery gates never execute.

## Steps to Reproduce
1. Boot the emulator and call iot DescribeEndpoint with endpointType='iot:Data-ATS'. Observe the returned endpointAddress host is an amazonaws.com name, not the emulator's own host:port.
2. Point an iot-data client at that address and call UpdateThingShadow for any created thing — the call does not reach the emulator.
3. Replay iot.shadow-update-get-delta-and-delete-lifecycle (or any of the 18 trace ids in cause 1) and observe PublishedUrlRejected at endpoint discovery.
4. For cause 2: call apigatewayv2 CreateApi (ProtocolType=HTTP, AWS_PROXY integration to a Lambda), read Api.ApiEndpoint, and POST to it — the host is not served by the emulator. Replay iot.e2e-topic-rule-destination-confirm-then-deliver.
