# wisdom: 5 net-new behavioral causes — clientToken reuse with changed parameters replays instead of conflicting, CreateContent/NotifyRecommendationsReceived/UntagResource are 501 stubs, and pattern-validation messages echo the anchored model pattern

> _Note: this issue was identified against the code base at commit `685e94dfb816aa33c7cd8ca632f897bdb6a87341`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

CreateAssistant

## Description
This bundle carries 5 root causes, all on service `wisdom` (crate services/service-com-amazonaws-wisdom-wisdomservice, service shape com.amazonaws.wisdom#WisdomService, protocol restJson1), all net-new: none of the five is marked ALREADY FILED or OWNED in the behavioral replay report, and none is covered by the two open wisdom issues (20261022T141946Z-wisdom-model-operations-refused-500-ambiguousservice-delete-list.md, which reports the router's 500 AmbiguousService refusal on wire fixtures and names none of these checks, and 20261023T054358Z-wisdom-qconnect-assistant-and-session-configuration-state-is-not.md, which is about assistant/session configuration persistence). Three of the five are operations that answer 501; they are reported here because each surfaced as an error-CODE mismatch on a check that caught the ClientError, so the suite's stub auto-filer did not cover them (it covered CreateAssistantAssociation, StartContentUpload, ListTagsForResource, CreateQuickResponse, GetRecommendations, DeleteKnowledgeBase and TagResource, which are deliberately excluded from this bundle). All five must be closed before this issue is submitted, and all five check ids in trace_ids must be re-replayed.

Cause 1 of 5 — CreateAssistant: a reused clientToken carrying DIFFERENT parameters replays the original resource with HTTP 200 instead of refusing with ConflictException.
AWS: Smithy CreateAssistant POST /assistants -> 200; member `clientToken` (ClientToken, @idempotencyToken, @length 1..4096); modeled errors AccessDeniedException 403, ConflictException 409, ServiceQuotaExceededException 402, ValidationException 400. An idempotency token identifies ONE request: replaying it with the identical request is idempotent and returns the original resource, while replaying it with a different request body is an idempotency conflict and is refused with ConflictException (HTTP 409). The recording shows message 'Idempotency conflict' (example text only; the requirement is the 409 status and the ConflictException error code).
Emulator: the identical-parameters replay is correct, but reusing the token with a different `name` also returns HTTP 200 and the FIRST assistant's record — the replay in the failing check returned assistantId/name/tags of the originally created assistant, not the requested name, and no error at all. services/service-com-amazonaws-wisdom-wisdomservice/src/ops/create_assistant.rs:171-182 looks the token up with `state.replayed_resource_id(Self::NAME, "", token)` and returns the stored resource unconditionally; nothing of the original request is remembered, so a changed request is indistinguishable from a retry.
Why: a client that reuses a token by mistake (loop variable not rotated, token derived from a stale key) is told its create succeeded and is handed a resource whose name/type/tags are NOT what it asked for. It then operates on the wrong assistant instead of seeing the 409 that AWS raises, and conflict-handling branches in client code are dead.
Fix: the CreateAssistant handler's idempotency path and the client-token store it uses (src/ops/create_assistant.rs, src/state.rs `remember_client_token`/`replayed_resource_id`): remember a fingerprint of the idempotency-relevant request members alongside the resource id and refuse a reuse whose fingerprint differs with the modeled ConflictException (409). The same store is shared by the other @idempotencyToken creates in this service, so fix it at that seam rather than per operation.
Traces: wisdom.create-assistant-client-token-idempotent-conflict-rejected.

Cause 2 of 5 — CreateContent answers 501 NotImplemented, so no content can be created and its ValidationException path never runs.
AWS: Smithy CreateContent POST /knowledgeBases/{knowledgeBaseId}/contents -> 200 with output member `content` (ContentData); required input `name`, `uploadId` (UploadId @length 1..1200); modeled errors AccessDeniedException 403, ConflictException 409, ResourceNotFoundException 404, ServiceQuotaExceededException 402, ValidationException 400. A `uploadId` that was never issued by StartContentUpload is refused with ValidationException (400); the recording shows message 'Invalid uploadId' (example).
Emulator: HTTP 501 with error code `NotImplemented` and message 'operation CreateContent is scaffolded but not implemented in this emulator'. services/service-com-amazonaws-wisdom-wisdomservice/src/ops/create_content.rs:189 returns `Scaffolded::not_implemented("CreateContent")`; the file still carries the `SCAFFOLDED, NOT IMPLEMENTED` marker.
Why: 501/NotImplemented is not a modeled wisdom outcome, so SDK error handling finds no match; a 5xx is also retried as transient, so a caller burns its retry budget on a call that can never succeed. The whole content ingestion flow (StartContentUpload -> CreateContent -> GetContent/ListContents) is unusable and its bad-uploadId rejection is unobservable.
Fix: implement the handler in src/ops/create_content.rs (validate `uploadId` against the uploads issued by StartContentUpload, return ValidationException for an unknown one, persist a ContentData in src/state.rs reachable by GetContent/ListContents) and delete the SCAFFOLDED marker.
Traces: wisdom.create-content-invalid-upload-id-not-found.

Cause 3 of 5 — NotifyRecommendationsReceived answers 501 NotImplemented, so the assistant not-found refusal and the per-recommendation soft-error response never happen.
AWS: Smithy NotifyRecommendationsReceived POST /assistants/{assistantId}/sessions/{sessionId}/recommendations/notify -> 200 with output members `recommendationIds` and `errors` (NotifyRecommendationsReceivedErrorList); modeled errors AccessDeniedException 403, ResourceNotFoundException 404, ValidationException 400. An assistantId that does not exist is refused with ResourceNotFoundException (404) — recorded message 'Assistant does not exist.' (example) — whereas an unrecognized recommendationId against a real assistant/session is only a per-entry error inside the 200 response body.
Emulator: HTTP 501, error code `NotImplemented`, message 'operation NotifyRecommendationsReceived is scaffolded but not implemented in this emulator' (handler services/service-com-amazonaws-wisdom-wisdomservice/src/ops/notify_recommendations_received.rs, still SCAFFOLDED).
Why: a client cannot distinguish a bad assistant id (hard 404) from a bad recommendation id (soft error in a 200 body) — both paths are replaced by a retried 5xx — so recommendation-acknowledgement logic cannot be exercised at all.
Fix: implement the handler in src/ops/notify_recommendations_received.rs (resolve assistantId/sessionId against src/state.rs, return the modeled ResourceNotFoundException when the assistant is unknown, otherwise return 200 with `recommendationIds` for the recognized ids and one `errors` entry — carrying the recommendationId and a non-empty message — per unrecognized id) and delete the SCAFFOLDED marker.
Traces: wisdom.notify-recommendations-received-nonexistent-assistant-rejected.

Cause 4 of 5 — UntagResource answers 501 NotImplemented, so tags can never be removed and an unknown ARN is not refused as not-found.
AWS: Smithy UntagResource DELETE /tags/{resourceArn} -> 200 with an empty output; required `resourceArn` (Arn, pattern ^arn:[a-z-]*?:wisdom:...) and `tagKeys` (@httpQuery tagKeys, @length 1..50); the model declares exactly one error, ResourceNotFoundException httpError 404. Recorded behavior for an ARN that matches the pattern but names no existing wisdom resource: a 4xx rejection with error code `NotFoundException` and message 'Resource was not found' (recorded behavior only — the recorded code differs from the modeled shape name, so treat the requirement as a 4xx not-found rejection carrying the recorded code, not a 501). Untagging a real, tagged resource succeeds and the tag is gone on a subsequent ListTagsForResource.
Emulator: HTTP 501, error code `NotImplemented` (handler services/service-com-amazonaws-wisdom-wisdomservice/src/ops/untag_resource.rs:148, still SCAFFOLDED).
Why: the tagging surface is write-only — no caller can remove a tag, and a typo in an ARN is reported as a server fault (and retried) instead of a not-found, so cleanup and tag-reconciliation code paths break.
Fix: implement the handler in src/ops/untag_resource.rs: resolve `resourceArn` against the resource tables in src/state.rs, refuse an unresolvable ARN with the not-found error (status/code per the recording above), otherwise remove the listed `tagKeys` from the resource's tag map, leave unknown keys alone, and answer the empty 200 body; delete the SCAFFOLDED marker. Note that ListTagsForResource and TagResource are stubs owned by their own auto-filed issues — this cause is about UntagResource only, but the three share the tag store.
Traces: wisdom.untag-resource-nonexistent-arn-rejected.

Cause 5 of 5 — ValidationException pattern-violation messages echo the model's anchored @pattern (^...$) where AWS renders the pattern unanchored.
AWS: Smithy CreateQuickResponse POST /knowledgeBases/{knowledgeBaseId}/quickResponses, member `contentType` (QuickResponseType) carries @pattern ^(application/x\.quickresponse;format=(plain|markdown))$; modeled error ValidationException 400. AWS's constraint-violation message is built from the request and the member's constraint, which makes its rule known: "1 validation error detected: Value '<value>' at '<member>' failed to satisfy constraint: Member must satisfy regular expression pattern: <pattern>", and the pattern is rendered WITHOUT the anchoring ^ and $ — the recording shows '... pattern: (application/x\.quickresponse;format=(plain|markdown))'.
Emulator: the status (400) and the error code (ValidationException) are correct, but the rendered pattern is the raw model string including the anchors: "1 validation error detected: Value 'application/json' at 'contentType' failed to satisfy constraint: Member must satisfy regular expression pattern: ^(application/x\.quickresponse;format=(plain|markdown))$".
Why: clients and test suites that assert on, log-scrape, or re-compile the echoed pattern from a ValidationException get a different regular expression than AWS returns for every @pattern-constrained member in this service, not just this one. This is the same defect class already filed for other services (20261023T173407Z-networkmonitor-response-code-and-validation-message-fidelity-tagging.md 'anchored pattern echoed' and 20261023T173855Z-notifications-4-fidelity-divergences-pattern-validation-message-rendering.md), so fixing it at the shared renderer closes it here too.
Fix: the constraint-validation message renderer in the request-validation layer that runs before the operation handlers (it is the pre-handler validate step of the shared smithy_server_runtime request walk, not src/ops/create_quick_response.rs): strip a leading ^ and a trailing $ from the member's @pattern when formatting the 'Member must satisfy regular expression pattern:' clause.
Traces: wisdom.create-quick-response-invalid-content-type-rejected (CreateQuickResponse.contentType is the member this check exercises; the same renderer serves every @pattern member of the service).
