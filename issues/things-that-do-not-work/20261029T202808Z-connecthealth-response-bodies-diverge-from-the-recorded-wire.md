# connecthealth response bodies diverge from the recorded wire: error detail served under Message instead of message, DeleteDomain answers 500 AuthorizerConfigurationException for a not-found domain, CreateSubscription adds lastUpdatedAt

> _Note: this issue was identified against the code base at commit `6bd726e14a5c3a202f9e89e1e854b8dfcc8d4492`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetDomain, DeleteDomain, GetMedicalScribeListeningSession, CreateSubscription

## Description
Bundled report of 3 distinct root causes in the connecthealth emulator, all found by replaying the wire fixture corpus simparity-wire-aws-v1 (38/43 steps passed, 5 mismatched, 4 divergence clusters, bootstrap_signal false, no cluster marked stub-blocked or owned). Each cause is independent and must be closed separately; the service token for all three is connecthealth.

=== Cause 1 of 3: every refused connecthealth call serves the exception's detail text under the body member `Message`, so the modelled `message` member AWS sends is absent from the wire ===
AWS: Smithy (services/service-com-amazonaws-connecthealth-connecthealth/smithy-model/com-amazonaws-connecthealth-connecthealth.json): `ResourceNotFoundException` is a client error, httpError 404, with exactly one member `message` targeting `String` and NO `@jsonName` trait (same for `InternalServerException` and the service's other exception shapes). The service speaks restJson1, so the error body member name on the wire is the Smithy member name: `message`, lowercase. The recorded responses confirm it: the 404 body for a domainId that resolves to no domain carries `message` = "Domain not found: <domainId>" (fixed text "Domain not found: " plus the `domainId` taken verbatim from the request), and the 404 body for an unresolvable Medical Scribe listening session carries `message` = "Resource not found: sessionId with ID <sessionId> does not exist" (fixed text "Resource not found: sessionId with ID " + the request's `sessionId` + " does not exist"). The values in the recordings (dom-a1a1a1a1a1a1a1a1a1a1a, 00000000-0000-4000-8000-000000000000) are the requests' own identifiers filling that template, not part of it.
Emulator: the status and the error code are right, but the body has NO `message` member at all — replay reports `$.message: missing (expected 'Domain not found: dom-a1a1a1a1a1a1a1a1a1a1a', got None)` on GetDomain and `$.message: missing (expected 'Resource not found: sessionId with ID 00000000-0000-4000-8000-000000000000 does not exist', got None)` on GetMedicalScribeListeningSession. The handlers do build the text (`ResourceNotFoundException { message: Some(domain_not_found_message(..)) }`), but a service-wide operation wrapper renames the rendered member before the response leaves: `DETAIL_MEMBER = "Message"` / `RENDERED_DETAIL_MEMBER = "message"`, and `with_detail_member` removes `message` and inserts the value under `Message`. So the text is on the wire under a key the model declares nowhere, and the key every client reads is gone. This affects EVERY error body of this service, not just the two operations the corpus happens to exercise (the wrapper claims any routable request and rewrites any >=400 body).
Why: an AWS SDK or botocore client populates `Error.Message` from the modelled `message` member. Against this emulator every connecthealth failure surfaces with an empty message, so error text never reaches logs, operator alerts or user-facing messages, and any client branching on the message (telling "Domain not found" from "Subscription not found" at the same 404) takes the wrong branch. A client that reads the non-standard `Message` key would conversely break against real AWS.
Emulator: see also the open issue 20261029T110643Z-connecthealth-listdomains-error-response.md, which covers a different ListDomains error-class defect and does NOT cover this rename.
Fix: the service-wide error-body rename in connecthealth's error-detail operation wrapper (`src/service/error_detail.rs`, the `with_detail_member` / `with_service_detail_member` layer and the `DETAIL_MEMBER` constant it renames to) must be dropped so the restJson1 renderer's modelled member name `message` is what is served; the message TEXT constructors it also hosts (`domain_not_found_message`, `scribe_session_not_found_message`) are correct and must stay. The module's own premise — that this service reports detail text in a member spelled `Message` — is contradicted by the recordings.
Traces: connecthealth-domain-lifecycle#task#4 (GetDomain, also affects connecthealth-domain-lifecycle#task#7), connecthealth-medical-scribe-listening-session-not-found#task#4 (GetMedicalScribeListeningSession).

=== Cause 2 of 3: DeleteDomain refuses a domainId it holds no domain for with an unmodelled AuthorizerConfigurationException at HTTP 500 instead of the modelled 404 ResourceNotFoundException ===
AWS: Smithy: `DeleteDomain` is DELETE /domain/{domainId}, `@idempotent`, and its ONLY modelled error is `ResourceNotFoundException` (errorKind client, httpError 404). `AuthorizerConfigurationException` is in no shape of this model at all (`smithy_query(query="shape", shape="AuthorizerConfigurationException")` reports "shape not found"). The recorded response for the DeleteDomain step of this domain lifecycle is HTTP 404 with error code ResourceNotFoundException and `message` = "Domain not found: <domainId>" — fixed text "Domain not found: " plus the requested `domainId` (the recording's dom-b2b2b2b2b2b2b2b2b2b2b is that request's value).
Emulator: answers HTTP 500 with `x-amzn-errortype: AuthorizerConfigurationException` and a body carrying no detail member — replay reports `status: expected 404, got 500`, `$headers.x-amzn-errortype` shaped-not-asserted vs 'AuthorizerConfigurationException', and `$.message: missing (expected 'Domain not found: dom-b2b2b2b2b2b2b2b2b2b2b', got None)`. Hypothesis: `src/ops/delete_domain.rs` splits the not-found path on its own allocation ledger — `if !store.has_allocated_domain(&input.domain_id)` returns the hand-rolled `DeleteDomainError::AuthorizerConfiguration` (status constant 500, shape id in the synthetic `smithy.framework` namespace), and only an id the ledger remembers reaches the modelled 404 branch — so this fixture's domainId is classified as never-allocated and takes the invented front-door branch. Note the conflict a fixer must resolve: the open behavioral issue 20261029T183834Z-connecthealth-startpatientinsightsjob-answers-a-nonexistent-domain-404-resourcenotfoundexception.md (its Cause 2) asserts AuthorizerConfigurationException with a null message is correct for a never-allocated domainId; this RECORDED wire step for DeleteDomain in the domain-lifecycle fixture is answered 404 ResourceNotFoundException with the domain-not-found text, so the allocation-ledger condition the emulator branches on does not reproduce the recording, and at minimum the status must not be a 500.
Why: 500 is a retryable server fault. An SDK's default retry policy retries a permanent client-side condition several times and then surfaces a server error, so a caller deleting an absent domain — the normal idempotent-cleanup path — sees a service outage instead of "already gone", and teardown/retry logic that keys on 404 never terminates. The error code is also one no connecthealth client can model, so no generated exception type matches it.
Fix: `DeleteDomain`'s handler not-found path (`src/ops/delete_domain.rs`), in its id-resolution branch: answer the modelled `ResourceNotFoundException` (404) with the shared `domain_not_found_message(domainId)` text for a domainId this service resolves no domain for, rather than routing it into the locally defined `AuthorizerConfigurationException` / 500 channel.
Traces: connecthealth-domain-lifecycle#task#5 (DeleteDomain).

=== Cause 3 of 3: CreateSubscription's 201 response carries a lastUpdatedAt member the recorded create response does not have ===
AWS: recorded behavior only for the member's presence. Smithy: `CreateSubscription` is POST /domains/{domainId}/subscriptions with success status 201, and `CreateSubscriptionOutput` declares `domainId`, `subscriptionId`, `arn`, `status`, `createdAt`, `lastUpdatedAt` (all required) plus optional `activatedAt` / `deactivatedAt`. The recorded 201 for a freshly created subscription carries NO `lastUpdatedAt` value: replay's expected value for `$.lastUpdatedAt` is absent/null. Hypothesis: a subscription that has never been updated has no update instant to report, so the create response leaves the member out even though the model marks it required (the same way the recorded responses leave `activatedAt` / `deactivatedAt` out until those transitions happen).
Emulator: emits `lastUpdatedAt` as a timestamp on the create response — replay reports `$.lastUpdatedAt: type_mismatch (expected None, got 1793305518.7310565)`. The number is this run's clock reading, not a requirement; the divergence is the member's PRESENCE. `src/ops/create_subscription.rs` stamps it from the stored record (`last_updated_at: to_timestamp(stored.last_updated_at)`), which for a just-created record equals `createdAt`.
Why: `lastUpdatedAt` is how a client tells a subscription that has been modified from one that has not — change feeds, cache invalidation and "modified since" polling read exactly that member. Against this emulator every brand-new subscription already presents as updated, so such logic is exercised on a shape real AWS never sends, and a client written against the emulator cannot handle the absent member AWS actually returns.
Fix: `CreateSubscription`'s response projection (`src/ops/create_subscription.rs`, the handler's output block — and the shared `Subscription::description()` projection in `src/state.rs` if the create is collapsed onto it, as open issue 20261029T135949Z-connecthealth-createsubscription-maintainability.md proposes): omit `lastUpdatedAt` from the create response while the stored subscription has taken no update, and keep serving it once a transition has stamped one. That open maintainability issue is about de-duplicating the projection and does NOT cover this member's presence.
Traces: connecthealth-subscription-lifecycle#task#2 (CreateSubscription).
