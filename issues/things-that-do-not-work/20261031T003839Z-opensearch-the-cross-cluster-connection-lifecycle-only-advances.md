# opensearch: the cross-cluster connection lifecycle only advances one step per CALL, so a poll-driven accept/reject/delete walk never reaches ACTIVE/DELETED inside a client's deadline

> _Note: this issue was identified against the code base at commit `f4f656b1bd7a513d31ed52598c20b4db3f989ef9`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeOutboundConnections

## Description
Cause 1 of 1: a client that drives the whole cross-cluster connection state machine with a conventional poll loop (CreateOutboundConnection -> wait for the inbound view -> AcceptInboundConnection -> wait for ACTIVE -> CreateOutboundConnection on the reversed pair -> RejectInboundConnection -> wait for REJECTED -> DeleteOutboundConnection -> wait for DELETED) never gets through the walk: every mutating call is answered with the TRANSIENT status, and the status the clock owes it becomes observable only on a LATER call, so each of the ~9 transitions in this lifecycle costs the client one whole poll interval and the check is killed by the suite's 60 s per-check budget before the last wait resolves. Failing check: opensearch.inbound-outbound-connection-accept-reject-lifecycle (the only failure in this suite run that is neither OWNED by an open issue nor blocked by a filed unimplemented-operation issue).

AWS: Smithy: OutboundConnectionStatus.StatusCode is the enum VALIDATING | VALIDATION_FAILED | PENDING_ACCEPTANCE | APPROVED | PROVISIONING | ACTIVE | REJECTING | REJECTED | DELETING | DELETED, documented as 'VALIDATING - The outbound connection request is being validated', 'PENDING_ACCEPTANCE: ... validated and is not yet accepted by the remote domain owner', 'APPROVED - ... approved by the remote domain owner for getting provisioned', 'PROVISIONING - Outbound connection request is in process', 'ACTIVE - Outbound connection is active and ready to use', 'REJECTING'/'REJECTED', 'DELETING'/'DELETED'. InboundConnectionStatusCode carries the same set minus the two validation states. AWS therefore does publish these transient states, and a client is expected to poll DescribeInboundConnections / DescribeOutboundConnections until the terminal one appears; nothing in the model states how long a step takes (recorded behavior only — the recording shows each step completing on its own, with the status advancing between polls without any further mutating call).

Emulator: the emulator models each step as an 'owed status' stored on the connection record with a due instant of now + PROVISIONING, where PROVISIONING = Duration::from_millis(500) (state.rs), and nothing is materialised until some later request reads the record. CreateOutboundConnection stores status=VALIDATING and owes PENDING_ACCEPTANCE; AcceptInboundConnection writes status=APPROVED and owes PROVISIONING, which in turn owes ACTIVE (connection_successor); RejectInboundConnection/DeleteOutboundConnection owe REJECTED/DELETED behind REJECTING/DELETING the same way. Because the owed status is due 500 ms in the FUTURE, the read a poller takes immediately after the mutating call always answers the transient status (APPROVED, REJECTING, DELETING, or — for a just-created outbound connection — VALIDATING, which has no inbound view at all so DescribeInboundConnections answers an EMPTY Connections list). The settle only lands on the poller's NEXT read, a full interval later. Combined with the domain side (DOMAIN_WORK = Duration::from_secs(3) and the same later-read settle, so a just-created domain reads Processing=true and only goes idle on the following poll), this check spends ~20 s waiting for its two peer domains, then one 5 s interval waiting for the inbound view, one 15 s interval waiting for ACTIVE after the accept, one 5 s and one 10 s interval on the reject path, and is killed at 60.0 s on the first DELETED wait — with no assertion having failed: replay verdict '[mismatch] opensearch.inbound-outbound-connection-accept-reject-lifecycle / Error: Check timed out after 60.0s'. Nothing after DeleteOutboundConnection was exercised.

Why: a client relying on AWS's behavior polls these two Describe operations and expects the service's own work to progress between polls, independent of whether it calls. Against this emulator the work progresses only when the client calls again, so every transition costs the client exactly one poll interval instead of the ~500 ms the emulator actually needs, and a multi-step walk (two peer domains, validate, accept, provision, active, reject, rejected, delete, deleted) blows any bounded deadline. The whole accept/reject/delete surface — AcceptInboundConnection reporting APPROVED/PROVISIONING/ACTIVE, the inbound record freezing at REJECTED after its outbound side is deleted, DeleteInboundConnection being refused with ValidationException on a REJECTED connection — therefore reads as unreachable rather than as served, even though each individual handler is implemented.

Note: the open issue 20261030T083920Z-opensearch-a-createdomain-updatedomainconfig-sequence-never-reaches-an.md describes the same later-read settle policy for the DOMAIN state machine (DescribeDomain Processing) and carries a different check's replay key; it does not cover the CONNECTION state machine's chained owed statuses or this check, which is why this is filed separately.

Fix: the connection state machine's settle/materialise path and the PROVISIONING window in the service's state module, plus the Describe projections that report the status from it — let a settle that is already complete be published on the SAME call that owes it (or make the window short enough, relative to a conventional poll interval, that a single wait does not cost a full interval), so a chained PROVISIONING->ACTIVE / REJECTING->REJECTED / DELETING->DELETED move is visible to the next read a client makes rather than to the one after it.

## Evidence
Expected (AWS): CreateOutboundConnection returns a VALIDATING connection; within the validation step DescribeInboundConnections(Filters=[{Name: connection-id, Values: [<id>]}]) reports the connection in PENDING_ACCEPTANCE/VALIDATING/APPROVED; AcceptInboundConnection answers Connection.ConnectionStatus.StatusCode in APPROVED|PROVISIONING|ACTIVE and the connection then reaches ACTIVE on both views without further mutating calls; a reversed-pair connection rejected with RejectInboundConnection answers REJECTING|REJECTED and settles to REJECTED on both views; DeleteOutboundConnection answers DELETING|DELETED and the outbound record disappears or reads DELETED; DeleteInboundConnection on the REJECTED connection is refused with ValidationException; the inbound record of that rejected, outbound-deleted connection stays REJECTED across repeated reads.

Actual (emulator): suite verdict '[mismatch] opensearch.inbound-outbound-connection-accept-reject-lifecycle', detail 'Error: Check timed out after 60.0s'. No response assertion failed — the walk never finished. Each mutating call is answered with the transient status only (CreateOutboundConnection -> VALIDATING, which has no inbound view, so DescribeInboundConnections answers Connections: []; AcceptInboundConnection -> APPROVED; RejectInboundConnection -> REJECTING; DeleteOutboundConnection -> DELETING) and the owed successor status (PENDING_ACCEPTANCE, PROVISIONING->ACTIVE, REJECTED, DELETED) is due 500 ms later and materialised only by a subsequent request, so each poll interval yields exactly one transition. Backing state: PROVISIONING = Duration::from_millis(500) and DOMAIN_WORK = Duration::from_secs(3) with Connection::settle run from a caller's read (state.rs:486, :500, :3014). Per-run values in the payloads (connection ids, domain names, account id, timestamps) are not part of the requirement.

## Steps to Reproduce
1. CreateDomain twice (cross-cluster-eligible peers: EngineVersion=OpenSearch_2.13, ClusterConfig={InstanceType: m5.large.search, InstanceCount: 1}, EBSOptions={EBSEnabled: true, VolumeType: gp3, VolumeSize: 10}, NodeToNodeEncryptionOptions={Enabled: true}, EncryptionAtRestOptions={Enabled: true}, DomainEndpointOptions={EnforceHTTPS: true}, AdvancedSecurityOptions with InternalUserDatabaseEnabled and a MasterUserOptions pair).
2. Poll DescribeDomain on both until Created=true and Processing=false: the read taken immediately after each CreateDomain answers Processing=true, so a 20 s-interval wait costs a full interval for work the emulator completes in 3 s.
3. CreateOutboundConnection(ConnectionAlias=<alias>, LocalDomainInfo={AWSDomainInformation:{OwnerId, DomainName: <domain A>, Region}}, RemoteDomainInfo={... DomainName: <domain B> ...}). The answer is ConnectionStatus.StatusCode=VALIDATING.
4. Immediately call DescribeInboundConnections(Filters=[{Name: connection-id, Values: [<ConnectionId>]}]): Connections is EMPTY (a VALIDATING connection has no inbound view). Only the NEXT poll, one interval later, reports PENDING_ACCEPTANCE.
5. AcceptInboundConnection(ConnectionId=<id>): answer is APPROVED. Immediately call DescribeOutboundConnections with the same filter: still APPROVED, not PROVISIONING/ACTIVE. ACTIVE appears only on the following poll, one whole interval later.
6. Repeat on the reversed domain pair with RejectInboundConnection, then DeleteOutboundConnection: each answers the transient status (REJECTING, DELETING) and the terminal one (REJECTED, DELETED) appears only on a subsequent read.
7. With a 60 s client deadline the walk is killed during the first wait for DELETED, before DeleteInboundConnection on the REJECTED connection (expected ValidationException) and the freeze-check that the rejected inbound record stays REJECTED are ever issued.
