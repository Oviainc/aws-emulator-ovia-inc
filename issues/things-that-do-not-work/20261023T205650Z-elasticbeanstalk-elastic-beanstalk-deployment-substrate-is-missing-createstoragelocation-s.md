# Elastic Beanstalk deployment substrate is missing: CreateStorageLocation's bucket does not exist, CloudFormation EB environments are never created, and the platform catalog rejects AWS's own filter values

> _Note: this issue was identified against the code base at commit `8bb3e31d2bc3a99611966740f58be573e66087fa`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStorageLocation

## Description
FOUR net-new root causes that between them make the whole Elastic Beanstalk deployment path unusable. Each must be closed separately.

Cause 1 of 4: CreateStorageLocation returns the name of a bucket it never creates, so no source bundle can be uploaded (34 failing checks).
AWS: Smithy CreateStorageLocation -> CreateStorageLocationResultMessage{S3Bucket}; recorded behavior is that it idempotently creates the account/region Elastic Beanstalk storage bucket (elasticbeanstalk-<region>-<account-id>) and returns its name, and that the returned bucket is immediately usable — s3.PutObject into it returns 200 and CreateApplicationVersion can reference it as SourceBundle.S3Bucket. Emulator: the call returns an S3Bucket name but the bucket is absent from S3 state: the immediately following PutObject fails 404 NoSuchBucket ('The specified bucket does not exist') and HeadBucket on the same name returns 404. Why: uploading the application source bundle to the EB storage location is the documented first step of every EB deployment, so no application version, environment deployment, custom platform build or log-retrieval flow can run at all; the response is actively misleading in naming a bucket that does not exist. Fix: the CreateStorageLocation handler in the elasticbeanstalk service crate — create (idempotently) the named bucket in the emulator's S3 state before returning S3Bucket. NOTE: open issue 20261023T113357Z-elasticbeanstalk-elastic-beanstalk-createstoragelocation-returns-an-s3-bucket-name.md describes this same defect but its replay key covers only the elasticbeanstalk__logs check; this cause carries the 34 elasticbeanstalk.* checks it blocks so the fix can be confirmed against them (close both together). Traces: see this issue's trace_ids (elasticbeanstalk.create-storage-location-idempotent is the minimal reproducer; elasticbeanstalk.application-version-processing-reaches-failed-for-malformed-bundle and the eb-* end-to-end checks all die on the first PutObject).

Cause 2 of 4: a CloudFormation stack containing an AWS::ElasticBeanstalk::Environment reaches CREATE_COMPLETE without creating any environment, and does not fail on a bogus platform.
AWS: recorded behavior — a stack whose template declares AWS::ElasticBeanstalk::Application + AWS::ElasticBeanstalk::Environment reaches CREATE_COMPLETE only after the environment really exists: DescribeEnvironments(EnvironmentNames=[<env>]) then returns exactly one environment which becomes Ready and serves its endpoint; conversely a template naming a platform ARN that does not exist drives the stack to CREATE_FAILED. Emulator: the stack reports CREATE_COMPLETE while DescribeEnvironments for the declared EnvironmentName returns 0 environments, and the invalid-platform stack also reports CREATE_COMPLETE instead of CREATE_FAILED. Why: a client that provisions Elastic Beanstalk through CloudFormation (the common path) is told its environment is up when nothing was created, and an invalid platform reference is silently accepted instead of failing the stack. Fix: the CloudFormation resource provider for the AWS::ElasticBeanstalk::* resource types — it must call through to the elasticbeanstalk service state (CreateApplication/CreateEnvironment, validating SolutionStackName/PlatformArn) and fail the stack when that call fails. Traces: elasticbeanstalk.deploy-environment-via-cloudformation-then-active-and-reachable, elasticbeanstalk.deploy-environment-via-cloudformation-serves-traffic, elasticbeanstalk.deploy-cloudformation-invalid-platform-arn-rejected.

Cause 3 of 4: ListPlatformBranches rejects the LifecycleState filter value AWS accepts.
AWS: Smithy ListPlatformBranches takes Filters: SearchFilters (Attribute/Operator/Values, all free-form strings — the model constrains no value set); recorded behavior is that the branch catalog's lifecycle states are capitalized ('Supported', 'Deprecated', 'Retired', 'Beta') and a filter {Attribute: 'LifecycleState', Operator: '=', Values: ['Supported']} is accepted and returns the supported branches. Emulator: that request is rejected 400 InvalidParameterValue 'Invalid SearchFilter value for Attribute LifecycleState: Supported. Valid values: beta | deprecated | retired | supported' — only the emulator's own lowercase spellings are accepted. Why: a client filtering the catalog by the state AWS itself reports cannot enumerate platform branches at all. Fix: the ListPlatformBranches handler's filter validation and the lifecycle-state values its catalog stores in the elasticbeanstalk service crate (src/ops/list_platform_branches.rs). Related: open issue 20261022T233132Z-elasticbeanstalk-elastic-beanstalk-listplatformbranches-serves-a-placeholder-branch-catalog.md covers the lowercase values on the RESPONSE side; this is the request-validation side of the same seed data and is not covered by its replay keys. Traces: elasticbeanstalk.list-platform-branches-filters-by-lifecycle-state.

Cause 4 of 4: no platform branch in the seeded catalog has two Ready versions, so a managed platform update can never be scheduled.
AWS: recorded behavior — the AWS-managed platform catalog always carries, for at least one supported branch, a current Ready platform version alongside its still-Ready predecessor, which is what makes a minor platform update available for an environment and lets Elastic Beanstalk schedule a managed action for it. Emulator: ListPlatformVersions over all 15 supported branches yields no branch with two or more Ready versions, so the managed-action checks cannot reach the behavior under test (they fail before exercising it). Hypothesis: the catalog is seeded with a single version per branch. Why: managed platform updates — scheduling, the Scheduled->Pending transition and ApplyEnvironmentManagedAction's happy path — are unreachable for every client. Fix: the seeded platform catalog the elasticbeanstalk crate serves (ListPlatformVersions/ListPlatformBranches data) must include a superseded-but-Ready version per supported branch. Traces: elasticbeanstalk.concurrent-apply-same-managed-action-id-race, elasticbeanstalk.managed-action-scheduled-then-becomes-pending-after-window.
