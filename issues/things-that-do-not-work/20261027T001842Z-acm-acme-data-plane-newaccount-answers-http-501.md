# ACM ACME data-plane newAccount answers HTTP 501 serverInternal, so nonce-replay protection, the revoked-account write guard and ListAcmeAccounts pagination are all unreachable (1 cause, 3 checks)

> _Note: this issue was identified against the code base at commit `df009dd79b3a670d3c0c53c12bb5e37a115b862c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAcmeAccounts

## Description
ONE root cause, grounded in three failing behavioral checks of this suite that are NOT carried as replay keys by any open issue. Related filing: open issue 20261026T043337Z-acm-acme-account-surface-diverges-in-two-places.md describes this same not-implemented JWS arm as its Cause 2 of 2, but its Issue-Trace-Ids carry only acm.e2e-acme-endpoint-binding-revoke-flow (and acm.create-acme-external-account-binding-unassumable-role-rejected for its other cause). It therefore does NOT gate the fix on the three checks below, each of which asserts a DIFFERENT downstream contract that the same 501 hides. This issue records those three replay keys and the extra contracts they pin; a fixer closing the other issue must satisfy these too.

Cause 1 of 1: every ACME JWS POST on an ACME endpoint's data plane -- newAccount above all -- is answered HTTP 501 with the RFC 8555 problem type urn:ietf:params:acme:error:serverInternal, so no ACME account can ever be registered and nothing that needs an account URL can be exercised.
AWS: recorded behavior only for the ACME wire itself (RFC 8555; the ACME data plane is not a modeled Smithy operation). The control-plane operations that read its result ARE modeled: ListAcmeAccounts(AcmeEndpointArn required @length 1..200 @pattern ^arn:aws[a-z-]*:acm:[a-z0-9-]+:[0-9]{12}:acme-endpoint/[a-zA-Z0-9-]+$, MaxResults @range 1..100, NextToken) -> {AcmeAccounts, NextToken}, @readonly @paginated(inputToken=NextToken, outputToken=NextToken, pageSize=MaxResults, items=AcmeAccounts), errors AccessDeniedException(403)/InternalServerException(500)/ResourceNotFoundException(400)/ThrottlingException(400)/ValidationException(400); DescribeAcmeAccount(AcmeEndpointArn, AccountUrl) -> AcmeAccount @readonly; RevokeAcmeAccount(AcmeEndpointArn, AccountUrl) -> Unit @idempotent. The recording behind the already-filed cause shows the shape of the accepted interaction: GET <EndpointUrl> returns the directory, HEAD <newNonce> returns a Replay-Nonce, and a correctly-signed JWS POST to directory['newAccount'] with payload {"termsOfServiceAgreed": true, "contact": [...]} is answered 200 or 201 with a Location header carrying the new account URL (preceded, on an endpoint that requires an external account binding, by HTTP 400 urn:ietf:params:acme:error:externalAccountRequired until the HS256 externalAccountBinding JWS built from GetAcmeExternalAccountBindingCredentials' KeyId/MacKey is attached). Three further contracts, each asserted by one of the checks below, hang off that door: (a) a nonce is single-use -- replaying an already-consumed nonce is answered HTTP 400 with problem type urn:ietf:params:acme:error:badNonce and that error response itself MUST carry a Replay-Nonce header whose nonce the server then accepts (RFC 8555 section 6.5 states both as MUSTs; the check that pins this is marked unblessed/DRAFT in its own docstring, so treat the exact badNonce statuses as Hypothesis: grounded in RFC 8555 rather than in a recording); (b) after RevokeAcmeAccount, the SAME account key replaying the same RFC 8555 7.3.2 account-update request is rejected by the ACME server with problem type urn:ietf:params:acme:error:unauthorized and the account's contacts are left exactly as the pre-revocation update left them, while a second still-valid account on the same endpoint updates itself normally; (c) ListAcmeAccounts paginates the registered accounts server-side -- MaxResults is honoured, NextToken is opaque and the union of pages is the full set without duplicates.
Emulator: the POST is answered HTTP 501 with {"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501}. Only the directory (GET) and newNonce (HEAD/GET) resources are served; newAccount, newOrder, revokeCert, keyChange and an account's own URL are collapsed onto one not-implemented refusal, and no JWS signature or nonce is ever verified, so neither badNonce nor unauthorized nor any non-empty ListAcmeAccounts page can be produced.
Why: 501 with type serverInternal tells an ACME client (certbot, lego, acme.sh) that the CA itself is broken; such a client retries or aborts instead of branching on the problem type, which is the opposite of the externalAccountRequired(400) and badNonce(400) signals the real flow depends on. Because no account URL can be minted, a caller cannot observe nonce single-use at all (the emulator silently accepts replayed nonces as far as any client can tell), cannot observe that RevokeAcmeAccount actually disables the revoked account's further ACME writes -- an over-permissive security boundary that would pass here and fail in production -- and cannot observe ListAcmeAccounts paginating anything, since the account list is permanently empty.
Fix: the ACME data-plane handler, services/service-com-amazonaws-acm-certificatemanager/src/service/acme_http.rs -- the ("POST", AcmeResource::Jws) arm of AcmeHttpSurface::serve routes to not_implemented(). Implement newAccount there: verify the JWS, enforce the endpoint's external-account-binding requirement with the RFC 8555 externalAccountRequired problem at 400 and accept the HS256 EAB JWS keyed by the binding's KeyId/MacKey, keep a single-use nonce store (so a replayed nonce yields 400 badNonce WITH a fresh usable Replay-Nonce header), mint and store the account record, and answer 201 with the account's Location URL. The account state it writes must then back the control-plane handlers in services/service-com-amazonaws-acm-certificatemanager/src/ops/ (list_acme_accounts.rs pagination over MaxResults/NextToken, describe_acme_account.rs, revoke_acme_account.rs) and the revoked-account gate on subsequent ACME writes.
Traces: acm.acme-replayed-nonce-rejected-and-the-error-carries-a-usable-nonce, acm.create-domain-validation-on-revoked-account-blocked, acm.list-acme-accounts-pagination-server-enforced.

## Evidence
All three checks died at the same door, with the identical 501 problem document:
- acm.acme-replayed-nonce-rejected-and-the-error-carries-a-usable-nonce [mismatch]: AssertionError: a newAccount with a fresh nonce must be accepted; got HTTP 501 b'{"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501}'. Unreached after that point: the badNonce replay leg (expected HTTP 400 urn:ietf:params:acme:error:badNonce whose response carries a Replay-Nonce header that the server then accepts) and the second-account-key control.
- acm.create-domain-validation-on-revoked-account-blocked [mismatch]: AssertionError: ACME newAccount failed (501): b'{"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501}' (raised from _register_acme_account for account A, before revocation). Unreached: the pre-revocation account update succeeding and being visible through DescribeAcmeAccount, RevokeAcmeAccount, the identical post-revocation update being refused with urn:ietf:params:acme:error:unauthorized with contacts unchanged, and the still-valid account B updating normally.
- acm.list-acme-accounts-pagination-server-enforced [mismatch]: AssertionError: ACME newAccount failed: 501 b'{"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501}' while registering the FIRST of several accounts. Unreached: ListAcmeAccounts(AcmeEndpointArn, MaxResults=1) returning one AcmeAccount plus a NextToken, and the pages unioning to the registered set.
Everything upstream worked in all three: CreateAcmeEndpoint reaching ACTIVE, the EAB creation, GET <EndpointUrl> directory and HEAD newNonce (Replay-Nonce present), so the failure is the JWS arm alone.
Status/code/message quoted exactly: HTTP 501, problem type 'urn:ietf:params:acme:error:serverInternal', detail 'This ACME server does not implement the new-account interaction yet'. Required instead: 200/201 with a Location header (or 400 with type 'urn:ietf:params:acme:error:externalAccountRequired' first). In the required refusals the FIXED parts are the problem types ('urn:ietf:params:acme:error:badNonce', 'urn:ietf:params:acme:error:unauthorized', 'urn:ietf:params:acme:error:externalAccountRequired') and the HTTP 400 status; the variable parts are the account URL in Location and the nonce value in Replay-Nonce, both minted per request.
Smithy citations (services/service-com-amazonaws-acm-certificatemanager/smithy-model/com-amazonaws-acm-certificatemanager.json): ListAcmeAccounts(AcmeEndpointArn required, MaxResults @range 1..100, NextToken) -> {AcmeAccounts, NextToken}, @readonly, @paginated(items=AcmeAccounts), errors AccessDeniedException(403)/InternalServerException(500)/ResourceNotFoundException(400)/ThrottlingException(400)/ValidationException(400).

## Steps to Reproduce
1. Boot the emulator and point botocore at it.
2. acm.create_acme_endpoint(...) and poll acm.describe_acme_endpoint until Status is ACTIVE; read AcmeEndpoint.EndpointUrl. Create an external account binding on it and read its KeyId/MacKey with acm.get_acme_external_account_binding_credentials.
3. GET <EndpointUrl> (directory, served 200) and HEAD directory['newNonce'] (Replay-Nonce present, served 200).
4. POST a correctly-signed JWS to directory['newAccount'] with Content-Type application/jose+json and payload {"termsOfServiceAgreed": true, "contact": ["mailto:..."]}.
5. Observe HTTP 501 {"type":"urn:ietf:params:acme:error:serverInternal","detail":"This ACME server does not implement the new-account interaction yet","status":501} and no Location header. AWS answers 200/201 with Location (optionally after one 400 urn:ietf:params:acme:error:externalAccountRequired round trip satisfied by the EAB's KeyId/MacKey).
6. Nonce leg: repeat step 4 reusing the nonce already consumed by a previous POST -- AWS answers HTTP 400 with type urn:ietf:params:acme:error:badNonce AND a Replay-Nonce header whose nonce the next POST is allowed to use; the emulator cannot produce either, since it verifies no nonce.
7. Revoked-account leg: register account A, update its contact via an RFC 8555 7.3.2 account-update POST (visible through acm.describe_acme_account), call acm.revoke_acme_account(AcmeEndpointArn=..., AccountUrl=<A>), then replay the identical update -- AWS refuses it with type urn:ietf:params:acme:error:unauthorized and leaves the contacts as the pre-revocation update left them, while an account B on the same endpoint still updates normally.
8. Pagination leg: register several accounts, then acm.list_acme_accounts(AcmeEndpointArn=..., MaxResults=1) -- AWS returns one account and a NextToken; the emulator's list is permanently empty because no account can be registered.
9. Re-replay the 3 checks in trace_ids.
