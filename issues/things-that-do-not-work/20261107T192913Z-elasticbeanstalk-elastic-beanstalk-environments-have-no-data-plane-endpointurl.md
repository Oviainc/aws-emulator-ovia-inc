# Elastic Beanstalk environments have no data plane: EndpointURL is never published, nothing ever answers at the environment CNAME, and DescribeEnvironments omits SolutionStackName for a template-launched environment (3 causes)

> _Note: this issue was identified against the code base at commit `ab92470025dd8eeb501814706ada4aa2b617e26c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEnvironments

## Description
THREE distinct root causes in the elasticbeanstalk emulator, all in the same service, all grounded in failing behavioral checks of this suite. THREE causes must be closed before submitting. Adjacent OPEN issues describe neighbouring ground but do NOT carry these checks (the suite did not mark them OWNED, their recorded failure signatures have changed): 20261024T015947Z-elasticbeanstalk-elastic-beanstalk-application-version-environment-state-machines-never.md and 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-application-versions-stay-status-unprocessed-forever.md (application versions now do become deployable and environments now do reach Ready in this replay — the failures below happen AFTER that point).

Cause 1 of 3: EnvironmentDescription.EndpointURL is never populated for a launched environment.
AWS: Smithy: DescribeEnvironments -> EnvironmentDescriptionsMessage/EnvironmentDescription, member EndpointURL (target EndpointURL) documented as "For load-balanced, autoscaling environments, the URL to the LoadBalancer. For single-instance environments, the IP address of the instance." Recorded behavior: once an environment reaches Status='Ready' it reports a non-empty EndpointURL alongside its CNAME, and clients dial that endpoint.
Emulator: DescribeEnvironments returns the environment with CNAME set but EndpointURL empty or absent — "a load-bearing environment must publish an EndpointURL; DescribeEnvironments returned '' alongside CNAME '<env>.<region>.elasticbeanstalk.com'", and a sibling check raises KeyError 'EndpointURL' because the member is omitted from the serialized EnvironmentDescription entirely.
Why: any client that resolves an environment's reachable address from the API (health probes, smoke tests, CNAME-swap verification, deployment gates) gets nothing to dial and cannot distinguish a Ready environment from an unreachable one.
Fix: the EnvironmentDescription serializer and the environment state that must carry the endpoint, in the DescribeEnvironments / CreateEnvironment handlers and the service's environment state module (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/, plus the service state module).
Traces: elasticbeanstalk.eb-deployed-application-serves-its-own-content-over-http, elasticbeanstalk.eb-swap-environment-cnames-swaps-which-application-answers.

Cause 2 of 3: a Ready environment never serves the deployed application over HTTP at its CNAME.
AWS: recorded behavior only — after a Processed application version is deployed and the environment reaches Ready, an HTTP GET of 'http://<CNAME>/' returns 200 with the content baked into that version's source bundle; the served content changes when a new version is deployed, keeps serving the previous version when a deploy fails, reflects option settings as process environment variables, reflects .ebextensions, stops answering once the environment is Terminated, and reports degraded health when the application answers HTTP 500.
Emulator: nothing ever answers at the environment's CNAME. Three checks carry the explicit frame TimeoutError "<env> serving its own nonce, so its instance is genuinely in service at 'http://<env>.<region>.elasticbeanstalk.com/': the run budget ended first; not graded" (and the same for '/sim2real/boot' and for the load-balanced pre-deployment probe); the remaining checks in this family are killed by the harness with 'Check timed out after 180.0s' while polling that same URL, with no assertion frame. Hypothesis: the emulator models the environment only as control-plane state and stands up no HTTP responder for the CNAME, so every data-plane consequence of a deployment is unobservable.
Why: every Elastic Beanstalk consumer whose purpose is to run an application — deploy/verify pipelines, rolling-vs-all-at-once deployment policy, ebextensions, environment variables, enhanced health, log retrieval from the running app, CNAME swaps, termination — observes a successful control-plane response and an application that does not exist. The checks grounded only in the 180s budget are the weakest-grounded part of this cause: re-replay them first and, if one then fails on an assertion instead, treat that assertion as its own cause.
Fix: the environment data plane — the HTTP responder the emulator must stand up for an environment's CNAME/EndpointURL serving the deployed application version's bundle, driven from the CreateEnvironment / UpdateEnvironment / TerminateEnvironment handlers and the environment state module.
Traces: elasticbeanstalk.eb-describe-instances-health-reports-the-environments-real-instances, elasticbeanstalk.eb-restart-app-server-restarts-the-process-without-replacing-the-instance, elasticbeanstalk.eb-rolling-deployment-keeps-serving-where-all-at-once-does-not (these three carry the explicit TimeoutError on the CNAME), elasticbeanstalk.eb-deploying-a-new-application-version-replaces-the-served-content, elasticbeanstalk.eb-failed-version-deploy-leaves-the-previous-version-serving, elasticbeanstalk.eb-option-setting-becomes-a-real-environment-variable-in-the-application, elasticbeanstalk.eb-ebextensions-config-files-really-run-on-the-instance, elasticbeanstalk.eb-ebextensions-option-setting-loses-to-the-direct-environment-setting, elasticbeanstalk.eb-enhanced-health-degrades-when-the-application-returns-http-500, elasticbeanstalk.eb-retrieved-environment-info-carries-the-applications-own-log-line, elasticbeanstalk.eb-terminated-environment-stops-serving-and-frees-its-cname-prefix, elasticbeanstalk.eb-abort-environment-update-withholds-the-instance-replacement, elasticbeanstalk.eb-concurrent-update-environment-yields-a-single-winner, elasticbeanstalk.eb-create-environment-with-a-cname-prefix-already-in-use-rejected, elasticbeanstalk.eb-update-environment-refuses-the-settings-validate-configuration-flags.

Cause 3 of 3: DescribeEnvironments omits SolutionStackName for an environment launched from a saved configuration template.
AWS: Smithy: EnvironmentDescription.SolutionStackName — "The name of the SolutionStack deployed with this environment." Recorded behavior: an environment created with TemplateName (no SolutionStackName in the request) inherits the template's solution stack and reports it in SolutionStackName once Ready.
Emulator: the EnvironmentDescription for a template-launched environment carries no SolutionStackName member at all — the check raises KeyError: 'SolutionStackName' on the Ready environment.
Why: a client that reads back which platform a template-launched environment is running gets a response missing a modeled member and crashes or mis-reports the platform; the template -> environment inheritance is unverifiable.
Fix: the CreateEnvironment handler's template-resolution path (it must copy the template's solution stack / platform ARN onto the new environment's state) and the EnvironmentDescription serializer.
Traces: elasticbeanstalk.eb-saved-configuration-template-reproduces-its-option-in-a-new-environment.
