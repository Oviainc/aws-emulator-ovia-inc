# ssm-quicksetup routes enforce no identity-policy authorization: an explicitly denied GetConfigurationManager answers 200 instead of 403 AccessDeniedException

> _Note: this issue was identified against the code base at commit `9d7649b3311435a15d98db18f1b7b1fd192e85c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetConfigurationManager

## Description
1 cause; it must be closed before this issue is submitted. NOTE: open issue 20261029T184830Z-ssm-quicksetup-4-net-new-root-causes-anchored.md describes this same defect as its cause 4, but the replay report does NOT mark this check as OWNED by it (a check killed by the harness budget produces no step/exception key, so that issue's replay key no longer binds this check), so it is recorded here with its own replay key. Fixing the authorization stage once closes both.

Cause 1 of 1: the ssm-quicksetup control plane performs no authorization of the calling principal, so an identity-based policy that explicitly denies ssm-quicksetup:GetConfigurationManager is not enforced and the denied caller's read succeeds.
AWS: a caller whose in-effect identity policy carries an explicit Deny for the action is refused 403 AccessDeniedException (Smithy: GetConfigurationManager binds AccessDeniedException, errorKind client, httpError 403, documented "The requester has insufficient permissions to perform the operation"; the same error is bound to ListConfigurationManagers and the rest of the service). The message follows AWS's explicit-deny template: the fixed text "User: " <caller principal ARN> " is not authorized to perform: ssm-quicksetup:GetConfigurationManager on resource: " <ManagerArn> " with an explicit deny in an identity-based policy", whose variable parts are the assumed-role principal ARN taken from the signing credentials of the request and the ManagerArn taken from the request path (httpLabel member ManagerArn); the action name is fixed per operation. The code and this template are recorded behavior; the status and error shape are modeled. Authorization is scoped to the one denied action: the SAME principal, holding only ssm-quicksetup:ListConfigurationManagers, must keep getting 200 from ListConfigurationManagers and must still see that manager there.
Emulator: GetConfigurationManager has no authorization step at all — services/service-com-amazonaws-ssmquicksetup-quicksetup/src/ops/get_configuration_manager.rs::handle goes straight from crate::state::request_region to store.manager_in(...) and returns 200 with the manager body; nothing reads the caller identity and no AccessDeniedException is ever constructed in this crate's read paths. The behavioral check therefore polls for the refusal that never appears and is killed at its 60s budget (verdict line: "Error: Check timed out after 60.0s"). The infrastructure exists elsewhere in the emulator (the STS crate evaluates caller permissions via crate::state::caller_may_call / not_authorized_message in ops/assume_role.rs), so this is a missing authorization stage in front of the ssm-quicksetup routes, not a missing policy engine.
Why: every authorization-negative test against this service passes silently and a client cannot distinguish "not permitted" from "permitted". A principal AWS refuses can read — and, by the same absent check, mutate — configuration managers it has been explicitly denied, so security regressions that real AWS would surface as 403 are undetectable against the emulator; code paths that branch on AccessDeniedException are never exercised.
Fix: the request-authorization stage fronting the ssm-quicksetup routes (the service crate's request walk, before each handler's resource lookup in services/service-com-amazonaws-ssmquicksetup-quicksetup/src/ops/*.rs): evaluate the caller's in-effect identity policy for the ssm-quicksetup action of the operation being served and refuse an explicit Deny with 403 AccessDeniedException carrying AWS's explicit-deny sentence, while leaving actions the policy allows (ListConfigurationManagers here) answering normally.
Traces: ssm-quicksetup.access-denied-without-permission-rejected.

## Evidence
Check ssm-quicksetup.access-denied-without-permission-rejected [mismatch], suite simparity-behavioral-aws-v1 (ssm-quicksetup 14/21 passed).
Scenario: the fully permissioned caller creates an AWSQuickSetupType-SSMHostMgmt configuration manager; an IAM role is created whose inline policy Allows sts:GetCallerIdentity and ssm-quicksetup:ListConfigurationManagers and Denies ssm-quicksetup:GetConfigurationManager; sts:AssumeRole is called into that role; GetConfigurationManager(ManagerArn=<created manager>) is issued with those credentials.
Expected (AWS): ClientError, HTTP 403, Code "AccessDeniedException", Message "User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: ssm-quicksetup:GetConfigurationManager on resource: <ManagerArn> with an explicit deny in an identity-based policy" — fixed text as quoted, with the principal ARN from the signing credentials and the ManagerArn from the request path as the only variable parts (the per-run role name, session name, account id and manager uuid are fillers, not requirements). ListConfigurationManagers for the same principal keeps answering 200 and still reports that manager.
Actual (emulator): the denied principal's GET /configurationManager/{ManagerArn} keeps answering HTTP 200 with the full manager body; no AccessDeniedException is ever returned, so the check's bounded poll for the refusal never breaks and the harness terminates the check — reported verdict "Error: Check timed out after 60.0s".
Code: services/service-com-amazonaws-ssmquicksetup-quicksetup/src/ops/get_configuration_manager.rs lines 162-215 — handle() reads the region, locks the store, settles, looks the ARN up and returns the output; there is no caller-identity or policy evaluation anywhere in the path, and GetConfigurationManagerErrorModeled::AccessDeniedException is never constructed. Compare services/service-com-amazonaws-sts-awssecuritytokenservicev20110615/src/ops/assume_role.rs lines 318-325, which imports caller_may_call / not_authorized_message, showing a policy-evaluation seam exists in the emulator.

2. 6. Call POST /listConfigurationManagers with the same credentials and confirm it answers 200 and lists that manager (it must keep succeeding after the fix, proving the denial is scoped to the one action).
7. Call GET /configurationManager/{ManagerArn} with the original fully permissioned credentials and confirm it still answers 200 (positive control).
