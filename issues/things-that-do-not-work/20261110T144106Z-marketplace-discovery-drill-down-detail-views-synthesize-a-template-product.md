# Drill-down detail views synthesize a template product record and misreport its fulfillment model

> _Note: this issue was identified against the code base at commit `b675dd39ab70f935a04f17e1ddfdffc8fec4d0b8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetListing

## Description
This issue bundles 3 causes, all in marketplace-discovery, all three the detail stages of one drill-down flow (SearchListings -> GetListing -> GetProduct -> ListFulfillmentOptions). The shared fault: each detail handler answers 200 but projects a GENERATED template row keyed off the requested id's slug instead of restating the catalog record that id names, and the template it generates describes a DIFFERENT KIND of product than the record does. The record is a SaaS product (one SAAS fulfillment option summary, a saasFulfillmentOption union member, deployedOnAws NOT_DEPLOYED, no badges); the emulator reports an Amazon-Machine-Image product with CloudFormation and EC2-Image-Builder options, deployedOnAws DEPLOYED, and two badges the record has not earned. So the divergence is not only textual: the required enum values, the union member chosen, list LENGTH, list ORDER and identifier FORMAT all differ from what this API returns.

NONE of them owns the replay keys for the three steps below: the replay reported owned_by = [] for all three clusters, and the emulator's current answers differ from the ones those issues recorded (they describe a SaaS projection with quickLaunch ENABLED and example.com logo URLs; the emulator now emits an AMI/CloudFormation/Image-Builder projection and a different badge set). These three causes are therefore filed here so a fixer has a replayable pointer at them.

Cause 1 of 3: GetListing describes a different kind of product than the listing record, mints categoryIds as slugs of their own display names, and awards badges the listing has not earned. Fixture marketplace-discovery-search-listings-and-drill-into-listing, step task#2.
AWS: Smithy: GetListing output requires associatedEntities (ListingAssociatedEntityList @length ..100, each a ListingAssociatedEntity{product: ProductInformation, offer: OfferInformation}), badges (ListingBadgeList @length ..20 of ListingBadge{displayName required, badgeType required: ListingBadgeType}), categories (CategoryList @length ..30 of Category{categoryId required NonEmptyString @length 1..1024, documented "the machine-readable identifier of the category"; displayName required, documented "the human-readable name of the category"}), fulfillmentOptionSummaries (FulfillmentOptionSummaryList @length ..20 of FulfillmentOptionSummary{fulfillmentOptionType required: FulfillmentOptionType enum AMAZON_MACHINE_IMAGE|API|CLOUDFORMATION_TEMPLATE|CONTAINER|HELM|EKS_ADD_ON|EC2_IMAGE_BUILDER_COMPONENT|DATA_EXCHANGE|PROFESSIONAL_SERVICES|SAAS|SAGEMAKER_ALGORITHM|SAGEMAKER_MODEL; displayName required}), highlights (HighlightList @length ..10), listingName, logoThumbnailUrl, longDescription, pricingModels, pricingUnits, promotionalMedia, publisher, resources, sellerEngagements, shortDescription, useCases. http POST /2026-02-05/getListing, 200. The model does not fix the CONTENT, so for content this is recorded behavior only: the response restates the stored listing. In the recording that means categoryId is an opaque taxonomy identifier the service issues (a 36-char UUID), NOT a lowercased slug of displayName, and the categories come back in the listing's stored order; fulfillmentOptionSummaries is exactly ONE entry whose fulfillmentOptionType is the option the record actually offers (SAAS, displayName 'SaaS'); badges is EMPTY when the listing earns no badge; highlights are the seller's own highlight sentences from the record (three of them here, within the modelled ten); associatedEntities[0] carries the listing's own product and offer, with the record's offerId, offerName and sellerOfRecord (sellerProfileId + displayName); and listingName, shortDescription, longDescription, logoThumbnailUrl, promotionalMedia, publisher, pricingModels, pricingUnits, resources, sellerEngagements, useCases and purchaseIndicators are the record's values.
Emulator: 200, with 43 diverging keys. categories[0..3].categoryId are slugs derived from the emulator's own display names ('machine-learning', 'structured-data-ml', 'industries', 'retail') where the record has taxonomy identifiers, and element-for-element the displayName differs too ('Machine Learning' vs 'Data Integration', 'Structured Data' vs 'Data Analytics', 'Industries' vs 'Infrastructure Software', 'Retail' vs 'Data Preparation'), so neither half of any category element lines up. fulfillmentOptionSummaries[0] reports fulfillmentOptionType AMAZON_MACHINE_IMAGE / displayName 'Amazon Machine Image' where the record reports SAAS / 'SaaS', and two further entries are present that the record does not have at all (CLOUDFORMATION_TEMPLATE 'AWS CloudFormation template', EC2_IMAGE_BUILDER_COMPONENT 'EC2 Image Builder component'). badges[0] and badges[1] are extra -- {displayName 'AWS Free Tier', badgeType 'AWS_FREE_TIER'} and {displayName 'Deployed on AWS', badgeType 'DEPLOYED_ON_AWS'} -- where the record reports none. associatedEntities[0]'s product and offer are template values generated from the slug (productId/offerId built as '<p|o>-0227-<slug>', offerName '<name> - Free', one synthesized sellerProfileId/displayName pair) instead of the record's product and offer. listingName, shortDescription, longDescription, logoThumbnailUrl, promotionalMedia[0], publisher.sellerProfileId/displayName, pricingModels[0].displayName/pricingModelType, pricingUnits[0].displayName/pricingUnitType, resources[0..3].*, sellerEngagements[0..1], useCases[0], highlights[0..2] and purchaseIndicators are likewise generated text rather than the record's.
Why: GetListing is the detail view the whole discovery flow funnels into. A client that renders it shows filler, but worse, the machine-readable members mislead: a client that reads fulfillmentOptionSummaries to decide which deployment path to offer is told to build an AMI/CloudFormation launch flow for a product that is only fulfillable as SaaS; a client that takes a returned categoryId and feeds it back as a CATEGORY search filter, or persists it, is handling an identifier shape this service never issues; and a client that reads badges advertises free-tier eligibility the listing does not have.
Fix: the seeded catalog and the projections GetListing reads it through, in the service's state module -- the breadth-row seeder that generates names, descriptions, logo URLs, highlights and resources per slug; the slug-keyed taxonomy helper that mints categoryId from displayName and expands ancestors ahead of the stored category; the per-row fulfillment-option assignment that gives each row a multi-type option set; and the badge derivation that awards AWS_FREE_TIER / DEPLOYED_ON_AWS to seeded rows. GetListing's handler should restate the stored record rather than a generated template.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#2 (GetListing, expected 200 / got 200).

Cause 2 of 3: GetProduct repeats the same generated template for the product the listing resolves to, and reports deployedOnAws DEPLOYED for a product the record marks NOT_DEPLOYED. Fixture marketplace-discovery-search-listings-and-drill-into-listing, step task#3.
AWS: Smithy: GetProduct output requires productId, catalog, productName, manufacturer (SellerInformation), deployedOnAws (DeployedOnAwsStatus enum DEPLOYED|NOT_DEPLOYED|NOT_APPLICABLE), shortDescription, longDescription, logoThumbnailUrl, fulfillmentOptionSummaries (FulfillmentOptionSummaryList @length ..20), categories (CategoryList @length ..30 of Category), highlights (HighlightList @length ..10), promotionalMedia, resources, sellerEngagements and listingId. http POST /2026-02-05/getProduct, 200. Content is recorded behavior only: the product restates its stored record -- the same taxonomy-identifier categories in stored order, the single SAAS fulfillment option summary, deployedOnAws NOT_DEPLOYED for a product that is not deployed on AWS, the seller's own three highlight sentences, and the record's own manufacturer, productName, descriptions, logoThumbnailUrl, resources and sellerEngagements.
Emulator: 200 with 31 diverging keys, the same substitutions as cause 1 carried into the product view. deployedOnAws is 'DEPLOYED' where the record says 'NOT_DEPLOYED'. categories[0..3] are whole-element mismatches (slug categoryId + the emulator's own displayName). fulfillmentOptionSummaries[0] is AMAZON_MACHINE_IMAGE / 'Amazon Machine Image' instead of SAAS / 'SaaS', and [1] CLOUDFORMATION_TEMPLATE and [2] EC2_IMAGE_BUILDER_COMPONENT are extra. highlights[0] is a sentence generated from the fulfillment option ('Fulfilled as AWS CloudFormation template') instead of the seller's first highlight, and highlights[1] and highlights[2] -- stored highlight sentences in the record -- are absent entirely (got None). productName, manufacturer.sellerProfileId/displayName, shortDescription, longDescription, logoThumbnailUrl, resources[0..3].*, sellerEngagements[0..1] and purchaseIndicators are generated text.
Why: a client that drills product-level detail after the listing gets a SECOND, independently generated copy of the same wrong record, so cross-checking listing against product cannot detect the substitution. deployedOnAws is the member a client branches on to decide whether the product runs in the buyer's account, and the slug-shaped categoryId leaks here too.
Fix: same component as cause 1 -- the state module's breadth-row seeder and the category, highlight, fulfillment-summary and deployedOnAws projections GetProduct shares with GetListing.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#3 (GetProduct, expected 200 / got 200).

Cause 3 of 3: ListFulfillmentOptions returns the wrong FulfillmentOption union member -- an amazonMachineImageFulfillmentOption for a product whose only fulfillment option is SaaS. Fixture marketplace-discovery-search-listings-and-drill-into-listing, step task#4.
AWS: Smithy: ListFulfillmentOptions output requires fulfillmentOptions (FulfillmentOptionsList of FulfillmentOption, a UNION documented "Each element contains exactly one fulfillment option type", members including saasFulfillmentOption and amazonMachineImageFulfillmentOption). SaasFulfillmentOption requires fulfillmentOptionId, fulfillmentOptionType, fulfillmentOptionDisplayName and quickLaunch (SaasQuickLaunchStatus), and makes fulfillmentUrl ('the URL of the seller's software registration landing page'), usageInstructions, availableFromTime and launchUrl optional. AmazonMachineImageFulfillmentOption requires fulfillmentOptionId, fulfillmentOptionName, fulfillmentOptionType, fulfillmentOptionDisplayName, operatingSystems and architecture. http POST /2026-02-05/listFulfillmentOptions, 200. Recorded behavior: for this product the single element is a saasFulfillmentOption with fulfillmentOptionType 'SAAS', fulfillmentOptionDisplayName 'SaaS', quickLaunch 'DISABLED' (the product does not support quick-launch deployment), fulfillmentUrl the seller's own registration URL, and NO AMI-shaped members -- consistent with the SAAS fulfillmentOptionSummaries the listing and product report. (The recording additionally carries a deploymentTemplates member on the SaaS option that the on-disk SaasFulfillmentOption does not declare: recorded behavior only; a fixer should treat the modelled members above as the requirement.)
Emulator: 200, but fulfillmentOptions[0] is an amazonMachineImageFulfillmentOption -- the wrong arm of the union -- carrying AMI-only members the record has nothing to populate (fulfillmentOptionType 'AMAZON_MACHINE_IMAGE', fulfillmentOptionDisplayName 'Amazon Machine Image', operatingSystems, recommendation.instanceType/securityGroups, architecture, amiAlias, ebsVolume.volumeTypes/iops, releaseNotes, usageInstructions, shortDescription), and no saasFulfillmentOption at all. Its accessUrlTemplate is additionally announced as a URL whose host is an unresolved placeholder ('https://{instance_dns}/'), flagged host_not_own by the replay; the requirement is not any particular URL but that this member -- and the AMI variant that carries it -- must not be emitted for a product with no AMI fulfillment option.
Why: the union member is exactly what a client switches on: it deserializes the arm named in the response and drives the deployment UX from it. Serving the AMI arm makes every client of this product take an EC2-launch path that AWS never offers for it, and the quickLaunch / launchUrl signals a buyer needs to decide whether a one-click SaaS launch is possible are missing altogether rather than merely wrong.
Fix: the state module's per-row fulfillment-option seeding and ListFulfillmentOptions' projection of it -- the row's option set must be the one the record offers (so the FulfillmentOption union member matches the type reported in fulfillmentOptionSummaries), and optional members must be emitted only when the record carries them.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#4 (ListFulfillmentOptions, expected 200 / got 200).

Explicitly NOT claimed as requirements anywhere in this issue: the literal generated ids (productId, offerId, fulfillmentOptionId, sellerProfileId), the numeric availableFromTime (the emulator derives it from its own clock), and the specific host of any URL. Those differ per environment and per run. The defects above are the required ENUM values (fulfillmentOptionType, deployedOnAws), the UNION member chosen, which badges and optional members appear, the identifier FORMAT of categoryId, the list lengths and order, and the fact that the content is a generated template rather than the record the requested id names.
