# cloudwatch__dynamodb__lambda: Invoke ignores reserved-concurrency admission control and answers 501 NotImplemented where AWS answers 429 TooManyRequestsException or runs the function (2 causes)

> _Note: this issue was identified against the code base at commit `6f028cab8dcb36872de9487c20527f3d87d76c81`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke

## Description
Two net-new root causes, both in the Lambda Invoke path. Each must be closed before this issue is submitted.

=== Cause 1 of 2: a function reserved to 0 concurrent executions is not refused by admission control; Invoke answers the emulator's 501 NotImplemented instead of the modeled 429 throttle ===
AWS: PutFunctionConcurrency(FunctionName=f, ReservedConcurrentExecutions=0) (Smithy: ReservedConcurrentExecutions @range min 0, required) sets a reserved ceiling of zero, and GetFunctionConcurrency reports 0. Every subsequent Invoke of f is then refused by admission control BEFORE any function code is considered: Smithy models TooManyRequestsException on Invoke with @httpError 429, and the exception shape carries Reason (target ThrottleReason, whose values include ReservedFunctionConcurrentInvocationLimitExceeded), retryAfterSeconds (bound to the Retry-After header), Type and message. For this class AWS's message is the fixed text "Rate Exceeded." — the entire message is fixed text, it interpolates nothing from the request or from state; the variable parts of the refusal are Reason (here ReservedFunctionConcurrentInvocationLimitExceeded, selected by which ceiling was hit) and retryAfterSeconds. The refusal does not depend on being able to run the deployment package, because nothing is ever dispatched.
Emulator: the reserved-0 Invoke is refused with error code 'NotImplemented' and the message "Invoke resolved arn:aws:lambda:<region>:<account>:function:<name> at version $LATEST, but running its python3.12 deployment package is not implemented in this emulator: there is no in-process runtime for it, and no response payload is returned that the function did not produce. InvocationType=DryRun validates an invocation without running the function." — not the modeled TooManyRequestsException, and not HTTP 429. services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs documents that a RequestResponse invocation answers HTTP 501; the reserved-concurrency ceiling set moments earlier is never consulted on the invoke path, so the admission decision is simply absent and is pre-empted by the runtime refusal.
Why: 'NotImplemented' is not a Lambda error code, so a client's throttle handling — retry on TooManyRequestsException, honour Retry-After, branch on Reason to tell a reserved-concurrency ceiling from an account ceiling — never fires; it sees an unrecognized non-retryable error instead. A reserved concurrency of 0, the standard way to disable a function, cannot be shown to disable anything, and because no request is ever classified as throttled no AWS/Lambda Throttles datapoint is produced for the function either, so an alarm built on Throttles can never transition.
Fix: the reserved-concurrency admission gate in the Lambda Invoke handler (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs), evaluated after function/version resolution and BEFORE any attempt to run the deployment package, raising the modeled TooManyRequestsException with Reason=ReservedFunctionConcurrentInvocationLimitExceeded; plus the AWS/Lambda Throttles metric publication that must count each refused request.
Traces: cloudwatch__dynamodb__lambda.lambda-throttle-metric-visible-in-cloudwatch.

=== Cause 2 of 2: invocations well inside a function's reserved capacity are refused rather than run, so an admitted wave is indistinguishable from a throttled one ===
AWS: with ReservedConcurrentExecutions=5, a 5-way concurrent wave of Invoke(InvocationType=RequestResponse) is entirely admitted: each call answers HTTP 200 with the function's own payload, none is refused, and the AWS/Lambda ConcurrentExecutions / Throttles series agree with those admission decisions (5 admitted, 0 throttled). Smithy: Invoke's success response carries StatusCode (@httpResponseCode), Payload (@httpPayload) and ExecutedVersion.
Emulator: all 5 of the 5 concurrent invokes inside the function's reserved capacity were refused with code 'NotImplemented' (no message surfaced on the error), so the check cannot distinguish an admitted wave from a refused one and the metric-agreement leg is unreachable.
Why: a caller cannot verify that a concurrency ceiling admits what it is supposed to admit, and because every invocation is refused, the throttle counts a client observes and the metrics it alarms on can never be made to agree — every concurrency-limit scenario reports total refusal.
Fix: the function-execution path behind the Lambda Invoke handler (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs), which must answer an admitted RequestResponse invocation with the function's result rather than HTTP 501, together with the AWS/Lambda ConcurrentExecutions/Throttles emission that mirrors the admission decisions. The open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md describes this refusal for Invoke generally and does not carry this check's replay key; the open issue 20261025T020208Z-cloudwatch-dynamodb-lambda-lambda-listeventsourcemappings-answers-resourcenotfoundexception-function-not-found-for.md names the same check under a timeout replay key (Issue-Key ...|run#34|Timeout|time.sleep(10)), which no longer matches — the check now reaches the invoke wave and fails on the NotImplemented refusals quoted above.
Traces: cloudwatch__dynamodb__lambda.reserved-concurrency-admission-control-and-metric-agreement-rejected.
