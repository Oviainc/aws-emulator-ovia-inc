=== Cause 1 of 3: SetSubscriptionAttributes accepts an EMPTY RedrivePolicy value instead of refusing it ===
AWS: Smithy (services/service-com-amazonaws-sns-amazonsimplenotificationservice/smithy-model/com-amazonaws-sns-amazonsimplenotificationservice.json): SetSubscriptionAttributes input is {SubscriptionArn (required), AttributeName (required), AttributeValue (OPTIONAL)}, output Unit; its modeled client refusals are InvalidParameterException (awsQueryError code 'InvalidParameter', HTTP 400), NotFoundException (NotFound, 404), AuthorizationErrorException (403), FilterPolicyLimitExceededException (403), ReplayLimitExceededException (403). Recorded behavior: an empty AttributeValue for RedrivePolicy is NOT read as 'clear the policy' — it is refused HTTP 400, error code 'InvalidParameter', message "Invalid parameter: RedrivePolicy: missing required value". Message rule: fixed text "Invalid parameter: " + the attribute name taken from the request's AttributeName + ": missing required value"; nothing in it comes from a recording-specific value. The previously stored RedrivePolicy must survive the refused write, and RawMessageDelivery must be untouched.
Emulator: the call SUCCEEDS. HTTP 200, text/xml body, no Error element at all (replay: "expected the call to be rejected, but it SUCCEEDED and returned {'ResponseMetadata': {... 'HTTPStatusCode': 200 ...}}"). No 400/InvalidParameter is produced for the empty value.
Why: a client that sends an empty value gets silent success where AWS refuses, so two different intents collapse. If the emulator also treats the empty value as a clear, the subscription's dead-letter target disappears and messages AWS would have dead-lettered are lost with no diagnostic; if it stores an empty policy, every later read-back of RedrivePolicy is malformed JSON for the client.
Fix: the attribute-value validation in SetSubscriptionAttributes' handler (services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/set_subscription_attributes.rs) — reject an empty value for RedrivePolicy with InvalidParameterException/'InvalidParameter' using AWS's sentence template and leave the stored policy and the other subscription attributes unchanged.
Traces: sns.subscription-redrive-policy-round-trip-and-replace (the preceding legs — absent RedrivePolicy on a new subscription, store, then replace-not-merge — all passed; the check dies on this refusal).

=== Cause 2 of 3: a FilterPolicy set AFTER a policy-less FilterPolicyScope write matches NOTHING, so the subscriber receives no message at all ===
AWS: Smithy models the subscription attribute map for Subscribe/SetSubscriptionAttributes, whose vocabulary includes FilterPolicy and FilterPolicyScope ('MessageAttributes' | 'MessageBody'); the sequence itself is recorded behavior only: a FilterPolicyScope supplied without a FilterPolicy (at Subscribe or by SetSubscriptionAttributes) is accepted and is NOT reported by GetSubscriptionAttributes, but it is retained — a FilterPolicy set later reads back together with FilterPolicyScope='MessageBody' and is evaluated against the message BODY. With policy {"kind": ["wanted"]}, a publish whose JSON body carries kind=wanted is DELIVERED, and a publish whose body carries kind=unwanted is withheld even when it carries a message attribute kind=wanted.
Emulator: the read-back legs are correct (the scope is hidden while there is no policy, and the later policy reads back under scope 'MessageBody'), but the delivery leg receives NOTHING: "the policy must filter on the message body (the hidden scope): expected only the body match, got []". In the same loop iteration the unfiltered twin subscription on the SAME topic received BOTH publishes, so delivery to SQS is live; the subscription holding the body-scoped policy received neither the body-matching message (which AWS delivers) nor the attribute-matching one (which a MessageAttributes-scoped evaluation would have delivered). So the stored policy matches no message under either scope — the filter evaluation drops everything once the scope was written before the policy.
Why: total, silent message loss on a correctly configured subscription. The client sees an accepted Subscribe, a FilterPolicy that reads back exactly as written under scope MessageBody, and a queue that stays empty forever, with no error anywhere to attribute it to.
Fix: the filter evaluation on the publish/delivery path and the scope state it reads (services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/publish.rs plus the subscription record written by src/ops/subscribe.rs and src/ops/set_subscription_attributes.rs) — when a scope was stored before any policy, the later policy must be evaluated against the parsed JSON message body, not against an empty/attribute source.
Traces: sns.filter-policy-scope-set-without-a-policy-is-hidden-until-a-policy-is-set.

=== Cause 3 of 3: a FIFO topic with an ArchivePolicy neither delivers live messages nor replays archived ones ===
AWS: recorded behavior only (the model carries ArchivePolicy/BeginningArchiveTime as topic attributes and ReplayPolicy/ReplayStatus as subscription attributes; no constraint in the model describes the replay semantics). Expected: on a FIFO topic whose ArchivePolicy is {"MessageRetentionPeriod": "1"}, messages published before a subscription existed are replayed, in publish order, to a new subscription whose ReplayPolicy starts at the topic's BeginningArchiveTime; a subscription created at the same moment WITHOUT a ReplayPolicy is not backfilled and receives only messages published after it; the replaying subscription's ReplayStatus converges to 'Completed'.
Emulator: the check's control-plane legs are reached without error (the ArchivePolicy round-trip and the presence of BeginningArchiveTime are asserted before any delivery), and then nothing arrives: the check makes no progress and is killed by the harness bound — "Check timed out after 60.0s" — inside its delivery polls, whose own deadlines are 120s. Neither the live leg (the no-replay FIFO subscriber never receives a live publish) nor the replay leg (the archived bodies never appear) converges. Hypothesis: Publish on an archiving FIFO topic performs no delivery to confirmed sqs subscriptions and no archive/replay is implemented, so both legs poll an empty queue until the bound.
Why: SNS message archive and replay are unusable: a client cannot recover messages published before a subscriber existed, and — worse — a FIFO topic that merely HAS an ArchivePolicy appears to stop delivering live messages, so enabling archiving silently breaks a working fan-out.
Fix: the FIFO delivery path in Publish's handler and the archive/replay state (services/service-com-amazonaws-sns-amazonsimplenotificationservice/src/ops/publish.rs, the topic/subscription records in src/state.rs, and the ReplayPolicy/ReplayStatus handling in src/ops/subscribe.rs and src/ops/set_subscription_attributes.rs).
Traces: sns.fifo-archive-replay-redelivers-archived-messages-to-a-new-subscription.
