=== Cause 1 of 2: a session policy whose only Allow is conditioned on aws:PrincipalTag/<key> grants the action regardless of the session's tags — a MISMATCHED tag value and an ABSENT tag key both still allow ===
AWS: Smithy com.amazonaws.sts#AssumeRole input carries `Tags` (tagListType, @length 0..50) and `Policy` (unrestrictedSessionPolicyDocumentType, @length min 1, the inline session policy). A session tag with key K is published to later authorization decisions as the condition key `aws:PrincipalTag/K`. The effective permissions of the session are the INTERSECTION of the role's identity policy and the session policy, so when the session policy's only statement allowing `s3:ListAllMyBuckets` carries `Condition: {StringEquals: {"aws:PrincipalTag/<K>": "<expected>"}}`, the call is permitted ONLY when the session actually carries K with exactly that value. A session tagged K=<other value> does not satisfy StringEquals, and a session with NO tag K does not satisfy it either (an absent condition key never satisfies StringEquals) — in both cases the intersection grants nothing and `s3:ListAllMyBuckets` is refused HTTP 403 / `AccessDenied`. Recorded behavior for the message (the model states the member and condition surface, not the authorization sentence): "User: <ARN> is not authorized to perform: s3:ListAllMyBuckets because no session policy allows the s3:ListAllMyBuckets action" — the FIXED text is "User: ", " is not authorized to perform: ", " because no session policy allows the " and " action"; the VARIABLE parts are the session's `AssumedRoleUser.Arn` as AssumeRole returned it and the action name taken from the request. The role's own identity policy allowing the action unconditionally does not widen the session: only the condition decides.
Emulator: none of the three legs is decided by the tag. With a role whose inline identity policy allows `s3:ListAllMyBuckets` on `*` and a session policy allowing it only when `aws:PrincipalTag/sim2real-env == "allowed"`: the matching-tag session is correctly allowed (200), but the session tagged `sim2real-env=blocked` keeps answering HTTP 200 for the whole 60 s poll (last observation `'(no error: the call succeeded)'`), and the leg that follows it — a session carrying NO tags at all — is never reached because the mismatched leg never refuses. So neither a wrong tag value nor a missing tag key withholds the grant.
Why: a client that uses session tags as its tenancy boundary ("this session may only touch what its aws:PrincipalTag says") is granted everything the ROLE can do here. Every tenant passes a per-tenant scope-down test against this emulator, cross-tenant access is invisible, and a policy regression that drops the Condition entirely is undetectable; the whole observable effect of session tags on authorization is absent.
Fix: the AssumeRole handler's session-minting path must record the minted session's SCOPE (its inline `Policy`/`PolicyArns` and its `Tags`) where a data plane can read it for a request signed with that credential, and the authorization gate that S3 consults for `s3:ListAllMyBuckets` must publish `aws:PrincipalTag/<key>` from that record and evaluate the statement's `Condition` — leaving a StringEquals clause unsatisfied both when the key's value differs and when the key is absent — then serialize the 403/AccessDenied sentence above.
Traces: sts.assume-role-session-tag-decides-policy-condition.

=== Cause 2 of 2: ec2:CreateVolume with DryRun=true is answered DryRunOperation for a principal whose policies do not allow the action, so no "Encoded authorization failure message:" is ever minted and the DecodeAuthorizationMessage round trip cannot be exercised ===
AWS: Smithy com.amazonaws.ec2#CreateVolumeRequest$DryRun — "Checks whether you have the required permissions for the action, without actually making the request, and provides an error response. If you have the required permissions, the error response is DryRunOperation. Otherwise, it is UnauthorizedOperation." DryRun is therefore an AUTHORIZATION probe evaluated before the dry-run short-circuit: for a role session whose only inline identity policy allows `sts:GetCallerIdentity`, `ec2:CreateVolume` is not allowed and the answer is HTTP 403 / `UnauthorizedOperation` whose message carries the encoded trailer — recorded behavior: "You are not authorized to perform this operation. User: <session ARN> is not authorized to perform: ec2:CreateVolume on resource: <the volume ARN built from the request's region and account> because no identity-based policy allows the ec2:CreateVolume action. Encoded authorization failure message: <blob>" — FIXED text is "You are not authorized to perform this operation. User: ", " is not authorized to perform: ", " on resource: ", the deny-classification clause " because no identity-based policy allows the <action> action." and the trailer "Encoded authorization failure message: "; VARIABLE parts are the session ARN, the action, the request-derived resource ARN and the per-failure blob. Nothing is created in either outcome. Smithy com.amazonaws.sts#DecodeAuthorizationMessage then decodes that blob (input `EncodedMessage` @required @length 1..10240; output `DecodedMessage`) to JSON stating whether the request was allowed, the principal, the requested action and resource, and the condition keys — i.e. `allowed: false`, a `context.principal` naming the role/session that was denied, and `context.action` ending in `CreateVolume`.
Emulator: the denied DryRun is never refused. A session minted from a role whose inline policy allows ONLY `sts:GetCallerIdentity` (its credentials proven live first — GetCallerIdentity answers 200) calls `ec2:CreateVolume(DryRun=true, AvailabilityZone=<an available AZ>, Size=1)` and is answered the DryRunOperation sentence "Request would have succeeded, but DryRun flag is set." on every poll for 60 s. No message containing "Encoded authorization failure message:" is produced anywhere, so the genuine `DecodeAuthorizationMessage` positive round trip (allowed=false, the decoded principal, the decoded action) has nothing to decode and the check cannot be graded past that point.
Why: DryRun exists precisely so a caller can test a grant without creating anything, and `DryRunOperation` is read as positive confirmation — so here an unauthorized principal is told it IS authorized. Preflight permission checks, policy-tightening CI gates and least-privilege reviews all pass against this emulator and fail in AWS. Separately the authorization-diagnostics loop is dead: a client that captures the encoded blob from a 403 and calls sts:DecodeAuthorizationMessage to learn which statement denied it never receives a blob, so an implementation that decoded nothing at all would be indistinguishable from a correct one.
Fix: EC2's CreateVolume handler must run the normal request authorization (the intersection of the role's identity policy, the session policy and the permissions boundary, explicit Deny winning) BEFORE its DryRun shortcut, and serialize 403 / UnauthorizedOperation with the sentence above — including the deny-classification clause and the encoded trailer — answering DryRunOperation only when the principal IS authorized; the shared authorization gate must mint the encoded blob from the decision it just made (principal ARN and assumed-role id, the bare action name, the request-derived resource ARN, the request's condition keys) so that the STS DecodeAuthorizationMessage handler decodes a genuine message to that content.
Traces: sts.decode-authorization-message-round-trip.
