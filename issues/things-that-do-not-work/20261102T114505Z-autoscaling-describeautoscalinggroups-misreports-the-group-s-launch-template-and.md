# DescribeAutoScalingGroups misreports the group's launch template and mixed-instances policy

> _Note: this issue was identified against the code base at commit `a4ef059b31cd49fc5529baf331c68065b4514ad5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeAutoScalingGroups

## Description
FOUR net-new causes on the DescribeAutoScalingGroups projection (awsQuery, api version 2011-01-01). They share one fault: the group AWS returns carries its full launch-source description plus the server-side defaults AWS always materialises, and the emulator's projection drops or misstates them. A fixer must close ALL FOUR before submitting.

Cause 1 of 4 - the described group omits the launch template's identity and the group's defaulted members. AWS: a described group always carries LaunchTemplate.LaunchTemplateId AND LaunchTemplate.LaunchTemplateName (plus Version), and carries its defaults even when the client never set them - CapacityReservationSpecification {CapacityReservationPreference default}, AvailabilityZoneDistribution {CapacityDistributionStrategy balanced-best-effort}, InstanceLifecyclePolicy {RetentionTriggers {TerminateHookAbandon terminate}}, ServiceLinkedRoleARN (the AWSServiceRoleForAutoScaling role arn), AvailabilityZoneIds, and the present-but-empty collections EnabledMetrics, TargetGroupARNs, TrafficSources, LoadBalancerNames, SuspendedProcesses. Smithy: shape AutoScalingGroup declares every one of those members, and LaunchTemplateSpecification carries LaunchTemplateId, LaunchTemplateName and Version. Emulator: each of those paths is reported missing (got None) and the LaunchTemplateName it does serve does not match the template the group was created from. Why: a client reading a group's effective configuration - to display it, to diff it before UpdateAutoScalingGroup, or to find the launch template id it was created with - reads null where AWS gives a value, so round-tripping a described group back into an update silently drops settings. Fix: the DescribeAutoScalingGroups serializer plus the group's creation defaults in autoscaling state. Traces: asglf-lt-identity-refusals#task#12.

Cause 2 of 4 - a group created with a MixedInstancesPolicy is described without one. AWS: the described group carries MixedInstancesPolicy.LaunchTemplate.LaunchTemplateSpecification (LaunchTemplateId + LaunchTemplateName) and MixedInstancesPolicy.LaunchTemplate.Overrides (one member per InstanceType override, in request order), plus MixedInstancesPolicy.InstancesDistribution with its defaulted OnDemandAllocationStrategy, OnDemandPercentageAboveBaseCapacity, SpotAllocationStrategy and SpotInstancePools. Smithy: AutoScalingGroup.MixedInstancesPolicy targets MixedInstancesPolicy (LaunchTemplate + InstancesDistribution); CreateAutoScalingGroupType accepts MixedInstancesPolicy as one of the four launch sources. Emulator: MixedInstancesPolicy.LaunchTemplate and every InstancesDistribution member are missing (got None), alongside the same defaulted members as Cause 1. Why: a client that chose instance-type diversification cannot read back which types or distribution the group actually uses, and a diff-then-update loop erases the policy. Fix: persist MixedInstancesPolicy (with its distribution defaults) at create time and project it in the DescribeAutoScalingGroups serializer. Traces: asglf-mixed-instances-policy-refusals#task#16.

Cause 3 of 4 - the group's LaunchTemplate.Version does not follow the version the group was updated to. AWS: when a group is pointed at a specific launch template version, the described group reports exactly that version number as a string, and reports LaunchTemplateName alongside it. Smithy: LaunchTemplateSpecification.Version. Emulator: reports the FIRST version instead of the one the group references (recorded run: expected '3', got '1') and omits LaunchTemplateName. Why: a caller verifying which template version a group will launch is told the wrong one, so a rollout that was repointed looks un-rolled; the specific numbers are per-run, the requirement is that the described version equals the version the group references. Fix: the group's launch-template reference in autoscaling state must record the version supplied by Create/UpdateAutoScalingGroup, and the describe serializer must emit it with the name. Traces: autoscaling-asgeni-traj-create-group-validates-template-network-interfaces#task#10.

Cause 4 of 4 - the same version drift in the other direction. AWS: a group left on the version it was created with keeps reporting that version even after the launch template itself gains newer versions. Smithy: LaunchTemplateSpecification.Version (a literal version number, or the aliases $Latest/$Default). Emulator: reports a later version than the group references (recorded run: expected '1', got '2'), together with the missing defaulted members of Cause 1. Why: the emulator resolves the group's template reference against the template's newest version rather than the stored reference, so a client believes a group will launch instances from a template revision it was never pointed at. Fix: resolve a group's LaunchTemplate version from the group's stored reference, not from the current head of the template, in the DescribeAutoScalingGroups projection. Traces: autoscaling-asghc-traj-unlaunchable-template-refused-until-fixed-version#task#10 (2 steps).

Related but not covering: open issue 20261022T112459Z-autoscaling-group-round-trip-create-skips-min-max.md owns the plain default-member omission on its own replay keys; none of the four bindings above is one of them, and the launch-template identity/version and MixedInstancesPolicy failures above are not described there.
