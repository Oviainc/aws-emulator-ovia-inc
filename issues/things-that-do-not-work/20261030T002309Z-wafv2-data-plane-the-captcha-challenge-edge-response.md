# wafv2 data plane: the Captcha/Challenge edge response omits x-amzn-waf-action, and four WAF-at-the-edge e2e checks never reach a verdict

> _Note: this issue was identified against the code base at commit `de414c514180eddfb96a534a3f6304a808cc952a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetSampledRequests

## Description
Two data-plane divergences on the wafv2 edge surface. This is ONE issue with TWO causes; both must be closed before the fix is submitted.

Cause 1 of 2: a Captcha-intercepted (and Challenge-intercepted) request is served with the right status but without the documented x-amzn-waf-action response header.
AWS: recorded behavior, documented envelope — Captcha and Challenge are the two WAF rule actions whose edge response AWS documents as an exact status plus an exact header. A request matching a Captcha rule with no valid CAPTCHA token is answered `405` and MUST carry `x-amzn-waf-action: captcha`; a request matching a Challenge rule with no challenge token is answered `202` and MUST carry `x-amzn-waf-action: challenge`. The header value is the fixed action token, not a per-run value. The header must NOT be present on an allowed request, nor after the rule producing it is removed. WAF's own record of the interception reports Action CAPTCHA with CaptchaResponse.ResponseCode 405 (respectively CHALLENGE / ChallengeResponse.ResponseCode 202) through GetSampledRequests.
Emulator: the status is right — the edge answered 405 on four successive Captcha-matched requests — but the response carries no x-amzn-waf-action header at all; the response headers observed were only ['connection', 'content-length', 'content-type', 'date', 'x-amzn-requestid'].
Why: the AWS WAF JavaScript/mobile CAPTCHA integration keys off exactly that header together with the status to decide whether to render the interstitial and retry. A 405 with no action header is indistinguishable at the client from an ordinary method-not-allowed, so the token-based-mitigation flow cannot be exercised at all against the emulator.
Fix: the Captcha/Challenge action's edge response construction in the data-plane rule-evaluation path — stamp x-amzn-waf-action with the matching action's token when (and only when) that action terminates evaluation.
Traces: wafv2.captcha-and-challenge-actions-return-their-documented-edge-response.

Cause 2 of 2: four WAFv2 data-plane/e2e checks never reach a verdict — each is still polling an observable WAF effect when the 60 s harness cap kills it.
AWS: recorded behavior only. Each of these checks builds a real API Gateway REST stage, associates a web ACL, confirms the origin answers 200 BEFORE WAF is attached, and then polls one observable WAF effect; against real AWS each effect becomes observable within the check's budget. The effects are: (a) a Count rule neither blocking nor terminating evaluation, with the match recorded through GetSampledRequests as Action COUNT and a Block rule at a higher priority number still firing behind it; (b) a PutLoggingConfiguration-ed, associated web ACL yielding at least one GetSampledRequests sample under the rule's own RuleMetricName, then DeleteLoggingConfiguration removing it from ListLoggingConfigurations and GetLoggingConfiguration refusing with WAFNonexistentItemException; (c) a RuleActionOverride turning a referenced rule group's Block into a Count at the edge, with the sample reporting Action COUNT and OverriddenAction BLOCK; (d) TextTransformations applied in ascending Priority order, so an order-sensitive header value is blocked under URL_DECODE-then-LOWERCASE and served under LOWERCASE-then-URL_DECODE.
Emulator: all four end as `Check timed out after 60.0s` — no assertion verdict, so the polled effect was never observed within the cap. Every one of the four polls a GetSampledRequests result or an edge status transition; the common dependency is that a matched request becomes observable (as a sample, or as a changed edge status after a rule change).
Why: these are the only checks that prove a stored WAF configuration actually DOES something — Count semantics, override downgrade, transformation ordering, and log/sample delivery. While they cannot complete, every one of those behaviours is unverified, and a client that depends on the edge honouring its rule set gets no signal here either way.
Fix: the data-plane rule-evaluation path and the GetSampledRequests sample store it feeds, for a web ACL associated with an API Gateway REST stage — a matched request must become observable (sampled under its rule's RuleMetricName, and reflected in the edge status after a rule change) promptly rather than never. Related open issues: 20261029T070050Z-wafv2-getsampledrequests-never-returns-a-sample-for-a (GetSampledRequests returning no sample for a matched rule, which owns wafv2.e2e-logging-configuration-capture-flow but none of the four keys here), 20261029T070050Z-cloudwatch-wafv2-a-web-acl-associated-with-a and 20261025T081755Z-apigateway-wafv2-six-more-wafv2-at-the-edge (edge checks hanging to the cap on other service tokens).
Traces: wafv2.count-action-does-not-block-and-does-not-terminate-evaluation, wafv2.e2e-logging-capture-then-teardown, wafv2.rule-action-overrides-downgrade-a-rule-group-block-to-count-at-the-edge, wafv2.text-transformations-apply-in-priority-order-at-the-edge.

## Evidence
Replay of simparity-behavioral-aws-v1 against the booted emulator (137/194 passed). All five checks below are grounded failures in that report; none is marked ALREADY FILED or OWNED.

Cause 1 — wafv2.captcha-and-challenge-actions-return-their-documented-edge-response: "AssertionError: the Captcha response did not carry the documented header x-amzn-waf-action: captcha; got None among ['connection', 'content-length', 'content-type', 'date', 'x-amzn-requestid']". The preceding legs passed: the origin answered 200 with no x-amzn-waf-action header before WAF was attached, and the Captcha-matched request then returned 405 on four successive polls — so the status half of the envelope is already correct and only the header is missing. The Challenge leg (202 + x-amzn-waf-action: challenge), the allowed-request leg (no such header) and the restore leg were not reached.

Cause 2 — four checks, each reported only as "Error: Check timed out after 60.0s":
  * wafv2.count-action-does-not-block-and-does-not-terminate-evaluation — polls _stable_http for the Count-matched request to keep being served and _sample_for a GetSampledRequests sample with Action COUNT under RuleMetricName 'countrule'.
  * wafv2.e2e-logging-capture-then-teardown — PutLoggingConfiguration + AssociateWebACL, then a 240 s poll on GetSampledRequests returning a non-empty SampledRequests under the rule's metric name before the teardown assertions.
  * wafv2.rule-action-overrides-downgrade-a-rule-group-block-to-count-at-the-edge — polls for 403 from the rule group's own Block, then _sample_for Action BLOCK / RuleNameWithinRuleGroup '<rule group>#innerblock', then 200 once the override is applied with Action COUNT / OverriddenAction BLOCK.
  * wafv2.text-transformations-apply-in-priority-order-at-the-edge — polls for 403 under URL_DECODE(0)+LOWERCASE(1), a sample with Action BLOCK, then 200 after swapping only the two transformation priorities.
  No assertion message is available for these four, so the localisation above is the set of polled effects each check blocks on, not a measured per-assertion verdict. The checks are otherwise identical in shape to wafv2.captcha-and-challenge-actions-..., which did get far enough to show the edge answering, so the edge itself responds and the unobserved effect is the sample/status transition.
