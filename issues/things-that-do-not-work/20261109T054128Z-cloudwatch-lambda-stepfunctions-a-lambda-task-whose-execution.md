# cloudwatch__lambda__stepfunctions: a Lambda Task whose execution role is denied lambda:InvokeFunction never settles FAILED/Lambda.AWSLambdaException, and neither the denied nor the control AWS/States LambdaFunction* series is readable

> _Note: this issue was identified against the code base at commit `c53162cdb93053ed8a8d23be086345dc123b2ab0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeExecution

## Description
Cause 1 of 1: the Step Functions Task-state Lambda integration takes no authorization decision for the state machine's execution role, so an execution started against a machine whose roleArn carries no lambda:InvokeFunction grant never reaches a terminal FAILED status with error Lambda.AWSLambdaException; and the AWS/States per-function counters that the denied task must move (and the ones it must NOT move) are never published either, so the check cannot reach any verdict and is killed at the harness cap.

AWS: StartExecution is accepted for a state machine whose role is not permitted lambda:InvokeFunction on the Task's target function. Step Functions assumes that role, Lambda refuses the Invoke with a 403, the Task fails and the execution becomes terminal. DescribeExecution (Smithy: sfn#DescribeExecution output members status -> ExecutionStatus enum (required), error -> SensitiveError @length 0..256, cause -> SensitiveCause @length 0..32768) then reports status FAILED, error exactly `Lambda.AWSLambdaException`, and a cause that is Lambda's authorization text. The fixed text of that message is `... is not authorized to perform: lambda:InvokeFunction on resource: ...`; its variable parts are the assumed-role principal ARN and the target function ARN, taken from the request and the emulator's own state — never the literal principal/function of one recording. On the metric side the CloudWatch and Step Functions Smithy models state nothing about publication, so: recorded behavior only — real AWS still accounts the refused task in the function's AWS/States family under Dimensions exactly [{Name: LambdaFunctionArn, Value: <denied function ARN>}] as LambdaFunctionsScheduled, LambdaFunctionsStarted and LambdaFunctionsFailed (one each, for one refused dispatch), and in AWS/States ExecutionsFailed under [{Name: StateMachineArn, Value: <denied machine ARN>}]; while AWS/States LambdaFunctionsSucceeded under [LambdaFunctionArn], AWS/States ExecutionsSucceeded under [StateMachineArn] and AWS/Lambda Invocations under [FunctionName] for that function must have no positive Sum. The counts are a function of how many times the machine schedules/starts/fails the task in the window, not literal values. The granted control path in the same window publishes AWS/States LambdaFunctionsSucceeded under its own [LambdaFunctionArn] and AWS/Lambda Invocations under its [FunctionName] (including the warm-up call made through its alias). Finally, granting lambda:InvokeFunction to the previously denied role lets the SAME state machine reach SUCCEEDED and return the handler's payload.

Emulator: nothing on that path is observable. The replay ends with `Error: Check timed out after 180.0s` (verdict [mismatch]). The denied execution does not settle into a terminal FAILED status carrying error `Lambda.AWSLambdaException` and the authorization cause, so the terminal-status poll never returns, and the following GetMetricStatistics polls for the moved counters (control LambdaFunctionsSucceeded, control AWS/Lambda Invocations, deny ExecutionsFailed, deny LambdaFunctionsScheduled/Started/Failed) never reach the expected sums. No AWS/States data point attributed to the [LambdaFunctionArn] dimension family is produced at all, so the moved-vs-unmoved contrast AWS guarantees cannot be read, and the post-repair assertion (same machine SUCCEEDED with the handler payload) is never reached.

Why: a client relying on AWS's behavior cannot tell a denied workflow from one that never dispatched anything. Least-privilege negative tests are unverifiable; Catch/Retry branches keyed on `Lambda.AWSLambdaException` are unreachable; DescribeExecution pollers block instead of reading a terminal status; alarms and dashboards over AWS/States LambdaFunctionsFailed / ExecutionsFailed stay silent for a workflow real AWS refuses, and per-function attribution (task counters keyed by LambdaFunctionArn, execution counters keyed by StateMachineArn) is simply unavailable.

Fix: the Step Functions execution/Task-dispatch component that resolves the state machine's roleArn and dispatches the Lambda integration (both the bare-function-ARN Resource form and the optimized arn:aws:states:::lambda:invoke form) must authorize the integration action/resource under the assumed execution role, fail the Task with error `Lambda.AWSLambdaException` and the Lambda authorization cause, drive the execution to the terminal FAILED status served by DescribeExecution, and the metric-emission side of that path together with the CloudWatch metric store must publish the AWS/States LambdaFunctionsScheduled/Started/Failed/Succeeded points under [LambdaFunctionArn] and Executions* under [StateMachineArn] so GetMetricStatistics serves them. Three open issues describe neighbouring symptoms of this area but the suite marks this check neither ALREADY FILED nor OWNED by any of them, so it is filed as a surviving cause and should be closed together with them: 20261105T130814Z-cloudwatch-lambda-stepfunctions-a-lambda-task-under-an.md (same check, but its replay key pins an older hang site inside _stats), 20261107T044335Z-cloudwatch-lambda-stepfunctions-aws-states-lambda-task-metric.md (the [LambdaFunctionArn] metric family never materialising for a function-ARN Task) and 20261105T081644Z-cloudwatch-lambda-stepfunctions-a-lambda-task-whose-function.md (a raising handler not failing the Task).

## Evidence
Expected: DescribeExecution on the execution started against the state machine whose role has no lambda:InvokeFunction grant returns status `FAILED`, error `Lambda.AWSLambdaException`, and a cause containing the fixed text `not authorized to perform: lambda:InvokeFunction on resource:` with the assumed-role principal and the target function ARN filled in from the request and the emulator's state. GetMetricStatistics (Period 60, Statistics [Sum]) over the execution window then reads AWS/States LambdaFunctionsScheduled / LambdaFunctionsStarted / LambdaFunctionsFailed under Dimensions [LambdaFunctionArn = <denied function>] and AWS/States ExecutionsFailed under [StateMachineArn = <denied machine>] at the counts implied by the one refused dispatch, plus the granted control machine's AWS/States LambdaFunctionsSucceeded under its [LambdaFunctionArn] and AWS/Lambda Invocations under its [FunctionName]; and no positive Sum for AWS/States LambdaFunctionsSucceeded under the denied [LambdaFunctionArn], AWS/States ExecutionsSucceeded under the denied [StateMachineArn], or AWS/Lambda Invocations under the denied [FunctionName]. After put_role_policy grants lambda:InvokeFunction, a new execution of the SAME machine ends SUCCEEDED with the handler's payload as output.

Actual: `Error: Check timed out after 180.0s` (verdict [mismatch]). The denied execution never reaches the terminal FAILED status with that error/cause, so the terminal-status poll never returns and the subsequent metric-sum poll never settles; no AWS/States datapoint in the [LambdaFunctionArn] family is ever served and no verdict is produced. The suite report lists this check under `### cloudwatch__lambda__stepfunctions` and marks it neither ALREADY FILED nor OWNED (its sibling check in the same section is marked OWNED by 20261107T044335Z-...-aws-states-lambda-task-metric.md).

## Steps to Reproduce
1. Create three IAM roles: two trusted by lambda.amazonaws.com as function execution roles, plus a control role trusted by states.amazonaws.com with `lambda:InvokeFunction` allowed on the control function ARN and its `:*` alias form, and a subject role trusted by states.amazonaws.com with NO lambda:InvokeFunction statement.
2. Create two python3.12 Lambda functions whose handler returns {'echo': event['n']} (and raises ValueError when event['mode'] == 'boom'); wait for both to become Active. Create alias `warm` on the control function at $LATEST.
3. Warm the control path: create a state machine with the control role whose single Task Resource is the alias ARN, and run it until it SUCCEEDS.
4. Create two STANDARD state machines, each a single Task state with End: true whose Resource is the corresponding bare function ARN — one with the control role, one with the subject (denied) role.
5. StartExecution on the control machine with {"mode":"ok","n":7} and poll DescribeExecution to terminal: it SUCCEEDS.
6. StartExecution on the denied machine with the same input and poll DescribeExecution to terminal. Expected: FAILED, error `Lambda.AWSLambdaException`, cause naming `not authorized to perform: lambda:InvokeFunction on resource: <denied function ARN>`. Against the emulator no terminal FAILED outcome arrives, so the poll runs to the harness budget.
7. Call GetMetricStatistics (Period 60, Statistics [Sum]) over the window for AWS/States LambdaFunctionsScheduled/Started/Failed/Succeeded with Dimensions [LambdaFunctionArn] (denied and control functions), AWS/States ExecutionsFailed/ExecutionsSucceeded with [StateMachineArn], and AWS/Lambda Invocations with [FunctionName]: against the emulator every one of these reads stays empty, so neither the moved nor the must-not-move counters can be contrasted.
8. put_role_policy the lambda:InvokeFunction grant onto the subject role and StartExecution the same denied machine again with {"mode":"ok","n":9}: it must now reach SUCCEEDED with output {"echo": 9}.
