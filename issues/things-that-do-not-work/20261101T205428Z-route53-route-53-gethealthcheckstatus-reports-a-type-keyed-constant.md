# Route 53 GetHealthCheckStatus reports a Type-keyed constant Success from every checker, so an endpoint-type health check can never be observed to go unhealthy (and contradicts the evaluator feeding AWS/Route53 HealthCheckStatus)

> _Note: this issue was identified against the code base at commit `92d1533bc984843777edac81f6082914baeb07b3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description

It is filed here because the check is still failing at the current commit and is not covered by any ownership marker; if that issue is being worked, close both together — the code citations below are re-verified against the current checkout, and this issue adds the evaluator contradiction described under Emulator.

Cause 1 of 1: what a Route 53 health checker reports about an ENDPOINT-type health check (HTTP, HTTPS, HTTP_STR_MATCH, HTTPS_STR_MATCH, TCP) is a constant selected only by HealthCheckConfig$Type. Nothing about the endpoint the stored configuration names — FullyQualifiedDomainName, IPAddress, Port, ResourcePath, SearchString, or the response that endpoint actually gives — is consulted on this path, so no input can produce a status that is not "Success: ...", and the "this health check has gone unhealthy" transition is unreachable.

AWS: Smithy StatusReport$Status — "A description of the status of the health check endpoint as reported by one of the Amazon Route 53 health checkers" (free text; the model constrains no value). GetHealthCheckStatus returns HealthCheckObservations, "one HealthCheckObservation element for each Amazon Route 53 health checker that is reporting a status about the health check endpoint". Smithy HealthCheckConfig$ResourcePath — "The path, if any, that you want Amazon Route 53 to request when performing health checks. The path can be any value for which your endpoint will return an HTTP status code of 2xx or 3xx when the endpoint is healthy". So ResourcePath (with FQDN/Port) is a PROBE TARGET re-evaluated every RequestInterval, and UpdateHealthCheck — which is what CloudFormation applies an AWS::Route53::HealthCheck property change through — repoints a live check. The reported wording: while the probed path answers 2xx/3xx, every checker reports a status whose fixed opening text is "Success: " (recorded behavior for an HTTPS check whose probe got a 200: "Success: HTTP Status Code 200, OK", where "Success: HTTP Status Code " is the fixed text and the numeric code and reason phrase are values taken from the probed response); once the path answers a non-2xx/3xx, every checker reports a status whose fixed opening text is "Failure: " and whose remainder names what that probe observed. The exact trailing wording of the failure class is recorded behavior only (the model documents no wording); the requirements are the "Failure: "/"Success: " opening and that the opening reflect what the probe actually observed, because a frozen Success is a different fact about the endpoint. No error code or non-2xx status is involved — GetHealthCheckStatus answers 200 in both phases; the divergence is the reported value.

Emulator: services/service-com-amazonaws-route53-awsdnsv20130401/src/state.rs:1244-1249 — reported_status(): `if self.config.r#type == HEALTH_CHECK_TYPE_TCP { return STATUS_TCP_CONNECTION_ESTABLISHED; } STATUS_HTTP_OK`, i.e. the constants "Success: TCP connection established" / "Success: HTTP Status Code 200, OK" (state.rs:1315-1319). state.rs:1255-1273 — to_health_check_observations() stamps that ONE StatusReport onto every checker Region. The stored config only decides WHICH Regions report (checker_regions, state.rs:1202-1211), WHETHER any report (endpoint_is_being_checked, state.rs:1187-1190) and WHEN (last_checked_at_millis, state.rs:1221-1230). Consequence on the dependent reader: to_last_failure_observations() (state.rs:1289-1300) filters observations by the "Failure: " prefix, so GetHealthCheckLastFailureReason can never report an observation either. Additionally, the service DOES have a real evaluator whose verdict for these types is the opposite: services/service-com-amazonaws-route53-awsdnsv20130401/src/state/health_check_status.rs:26-29 documents that for the endpoint types "This emulator makes no outbound connection, so no endpoint outside it answers one of its health checkers and the probe FAILS", and that evaluation drives reported_healthy() (state.rs:1165-1173) and the AWS/Route53 HealthCheckStatus series. One health check therefore reports two contradictory facts: the CloudWatch series eventually flips to 0/unhealthy while every checker observation in GetHealthCheckStatus stays "Success: ..." forever.

Why: a client gets the one fact a health check exists to supply frozen at healthy, and gets it inconsistently with the metric an alarm is built on. Configuration round-trips perfectly (GetHealthCheck reports the new ResourcePath and an advanced HealthCheckVersion), while the monitoring behind it is inert — so a DNS-failover drill, a deployment gate, or any test that waits for a health check to go unhealthy after its monitored path breaks hangs instead of observing the transition, and GetHealthCheckLastFailureReason never yields a failure report to branch on. Any target that merely stores ResourcePath is indistinguishable from Route 53 on this path.

Fix: the route53 health-check state/evaluator, not the GetHealthCheckStatus serializer. reported_status()/to_health_check_observations() must stop returning a Type-keyed constant and derive each checker's report from the same per-probe assessment the evaluator already performs for the aggregate status and the CloudWatch series (health_check_status::observe / HealthCheckEvaluation), so a "Success: "-prefixed report is produced when the probed path answers 2xx/3xx and a "Failure: "-prefixed report naming the observed non-success otherwise, re-evaluated per probe so a later ResourcePath/endpoint change flips the report, and so one health check has one status across GetHealthCheckStatus, GetHealthCheckLastFailureReason and AWS/Route53 HealthCheckStatus.

## Steps to Reproduce
1. route53 CreateHealthCheck with HealthCheckConfig {Type: HTTPS, FullyQualifiedDomainName: <an HTTPS endpoint this emulator serves>, Port: 443, ResourcePath: "/prod/healthy" (a path that endpoint answers 200), RequestInterval: 10, FailureThreshold: 1}. (The replayed check creates it through CloudFormation: create_stack with an AWS::Route53::HealthCheck whose ResourcePath is a template parameter, beside an AWS::ApiGateway::RestApi/Resource/Method/Deployment/Stage serving /prod/healthy, taking the id from the stack output that Refs the health check.)
2. GetHealthCheckStatus(HealthCheckId): every HealthCheckObservations[].StatusReport.Status is "Success: HTTP Status Code 200, OK" immediately.
3. Repoint the check at a path the endpoint does not define: UpdateHealthCheck(HealthCheckId, ResourcePath="/prod/sim2real-404-nonexistent") — or update_stack with that parameter value and wait for UPDATE_COMPLETE.
4. GetHealthCheck(HealthCheckId): HealthCheckConfig.ResourcePath is the new path and HealthCheckVersion has advanced, confirming the reconfiguration landed.
5. Poll GetHealthCheckStatus again. AWS: within a few RequestIntervals every checker reports a "Failure: "-prefixed status naming the non-success the probe observed. Emulator: every checker keeps reporting "Success: HTTP Status Code 200, OK" indefinitely, so the poll never terminates.
6. GetHealthCheckLastFailureReason(HealthCheckId): always an empty HealthCheckObservations, because nothing can ever carry the "Failure: " prefix the reader filters on.
7. Contrast with the aggregate plane: read CloudWatch GetMetricStatistics for AWS/Route53 HealthCheckStatus dimensioned HealthCheckId=<id>. It reports the evaluator's verdict for an unreachable endpoint (flipping to 0/unhealthy), disagreeing with the frozen Success every checker observation reports for the same check.
8. Create the same check with Type: TCP — the status is the other constant, "Success: TCP connection established", regardless of whether anything listens on the port.
