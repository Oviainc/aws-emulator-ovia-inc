# opensearch package APIs refuse an unresolvable PackageID as ResourceNotFoundException/409 "Package not found: <id>" instead of AWS's ValidationException/400 "Package not found." (3 causes: AssociatePackages, GetPackageVersionHistory/DeletePackage, UpdatePackage)

> _Note: this issue was identified against the code base at commit `a8bdac89d1e747b372c0bf4c08847aac78d5e939`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AssociatePackages

## Description
Three net-new root causes in the OpenSearch Service package control plane, all grounded in surviving behavioral checks of the `opensearch` service (every other opensearch failure in this run was marked ALREADY FILED or OWNED and was skipped). All three share the service token `opensearch` and one gate verdict, so they are bundled here. A fixer must close ALL THREE before submitting.

They share one underlying mechanism — the store's single package-lookup refusal builder, `package_not_found()` in services/service-com-amazonaws-opensearch-amazonopensearchservice/src/state.rs, which mints a ResourceNotFoundException payload whose message interpolates the requested PackageID — but each operation classifies and returns it on its own path, so each must be corrected (and each is grounded in its own failing checks). Note the open issue 20261027T004336Z-opensearch-ten-net-new-control-plane-causes-getmigration.md touches GetPackageVersionHistory, but its cause 6 is the MISSING IAM AUTHORIZATION check on that operation (an unprivileged caller gets 200); it carries none of the replay keys below and says nothing about how an unresolvable PackageID is classified. This is a different defect on the same operation.

=== Cause 1 of 3: AssociatePackages answers ResourceNotFoundException/409 for a PackageID that resolves to no package, where AWS answers ValidationException/400 ===
AWS: Smithy: `AssociatePackages` is `POST /2021-01-01/packages/associateMultiple` with required `DomainName` (@length 3..28, pattern `^[a-z][a-z0-9\-]+$`) and `PackageList`; it models both ValidationException (HTTP 400) and ResourceNotFoundException (HTTP 409), and the model's own doc string for ValidationException is literally "An exception for accessing or deleting a resource that doesn't exist" — so which of the two carries a missing package is not settled by the model and is recorded behavior only. The recording shows AWS refusing a PackageID that names no package (because it was deleted, or never existed) with code `ValidationException`, not with the not-found code the API reference documents; the package APIs treat any PackageID that does not resolve as a bad input value rather than a missing resource. The message's fixed text is `Package not found.` in full — there is no variable part, and in particular the rejected PackageID is NOT interpolated into it. The refused call creates no association (ListPackagesForDomain / ListDomainsForPackage show none).
Emulator: answers code `ResourceNotFoundException` with HTTP 409 and the message `Package not found: pkg-<hex>` — the wrong code, the wrong status, and a message that appends `: <requested PackageID>` to text AWS ends at the period.
Why: a client branching on the documented/recorded refusal class sees the opposite answer: 409 is a retryable-conflict-shaped status, so an SDK retry policy or a client that treats 409 as "try again later" loops on an input that will never succeed, while a client that validates its own input on ValidationException never learns the package id it passed is dead. The message divergence also breaks any client (or operator log scrape) matching AWS's exact wording, and leaks the caller's id back into a message AWS keeps id-free.
Fix: the package-id resolution refusal in the AssociatePackages handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/associate_packages.rs) and the shared refusal builder and classifier it uses (`package_not_found` and `AssociationRefusal::NotFound` in src/state.rs, lifted by that file's `refuse`), which must classify an unresolvable PackageID as the modeled ValidationException (400) and word the message with no id. The sibling single-package path (src/ops/associate_package.rs) shares `plan_package_association` and must not be left answering differently.
Traces: opensearch.delete-package-while-associated-rejected, opensearch.package-catalog-listing-consistency.

=== Cause 2 of 3: GetPackageVersionHistory (and DeletePackage) on a deleted PackageID answer ResourceNotFoundException/409 instead of ValidationException/400 ===
AWS: Smithy: `GetPackageVersionHistory` is `GET /2021-01-01/packages/{PackageID}/history` with required `PackageID` (httpLabel, pattern `^([FG][0-9]+)$|^(pkg-[a-f0-9]+)$`) and models ValidationException (HTTP 400) alongside ResourceNotFoundException (HTTP 409); `DeletePackage` is `DELETE /2021-01-01/packages/{PackageID}` and models the same pair. Recorded behavior: once DeletePackage has completed (the id stops appearing in DescribePackages — real AWS keeps no DELETED tombstone row), the by-id read is refused with code `ValidationException`, HTTP status `400`, and the message whose fixed text is the whole string `Package not found.`; a second DeletePackage for the same id is refused identically. The PackageID that was requested is deliberately absent from the message. The positive control in the same recording is that both calls succeed on the live package, so the refusal means "deleted", not "malformed request".
Emulator: answers code `ResourceNotFoundException` with HTTP status `409` and the message `Package not found: pkg-<hex>`.
Why: the status is the load-bearing part here — 400 tells a client its request will never succeed, 409 tells it the resource is in a conflicting state and the call is worth retrying, so a poller waiting for a package read to come back after a delete never terminates. A client cannot distinguish a deleted package from a transient conflict, and the appended id makes the message unmatchable against AWS's wording.
Fix: the not-found path of the GetPackageVersionHistory handler and the DeletePackage handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/get_package_version_history.rs and src/ops/delete_package.rs) plus the shared `package_not_found` builder in src/state.rs: raise the modeled ValidationException with HTTP 400 and the id-free message for any PackageID the store does not hold.
Traces: opensearch.package-lifecycle-create-delete, opensearch.package-version-history-chronological-ordering.

=== Cause 3 of 3: UpdatePackage on a deleted PackageID answers ResourceNotFoundException instead of ValidationException/400 ===
AWS: Smithy: `UpdatePackage` is `POST /2021-01-01/packages/update` with required `PackageID` (pattern `^([FG][0-9]+)$|^(pkg-[a-f0-9]+)$`) and `PackageSource`, `CommitMessage` (@length 0..160), and models ValidationException (HTTP 400) and ResourceNotFoundException (HTTP 409). Recorded behavior: after the package is deleted and gone from DescribePackages, an UpdatePackage naming the same PackageID with a perfectly valid PackageSource is refused `ValidationException` with the message whose fixed text is the entire string `Package not found.` (no variable part, and no PackageID interpolated), and no new package version is created.
Emulator: answers code `ResourceNotFoundException` (status 409, message `Package not found: pkg-<hex>` on the same shared builder).
Why: this is the mutating member of the family, so a client that retries a write on 409 re-issues an update against a dead id indefinitely, and a deploy pipeline that distinguishes "bad input, fix the template" (400) from "resource busy, retry" (409) takes the wrong branch on a package that was deleted underneath it.
Fix: the package-resolution refusal in the UpdatePackage handler (services/service-com-amazonaws-opensearch-amazonopensearchservice/src/ops/update_package.rs), via the same corrected `package_not_found` classification in src/state.rs so all four package operations refuse an unresolvable PackageID identically.
Traces: opensearch.representation-package-version-numeric-size-precision-preserved.
