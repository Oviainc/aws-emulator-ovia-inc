# DynamoDB data-plane validation gaps: PartiQL semantics, number limits, size/nesting limits, request defects and vector metering (6 causes)

> _Note: this issue was identified against the code base at commit `6a6bdf627b2774134f5b74f649503c2b12968e19`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutItem

## Description
Six net-new root causes where the emulator ACCEPTS input real AWS refuses, or computes a different result. Open issue 20261030T060227Z-dynamodb-validationexception-messages-diverge-from-the-wording-aws.md and 20261029T180026Z-dynamodb-createtable-updatetable-putitem-validation-10-missing-or.md touch neighbouring ground but carry none of the replay keys below.

=== Cause 1 of 6: PartiQL evaluation semantics ===
AWS: in PartiQL over DynamoDB a MISSING attribute is not NULL, so "WHERE a IS NULL" matches only items whose attribute is the NULL AttributeValue type; a PartiQL UPDATE ... REMOVE against a key that does not exist is a no-op and creates nothing; and a SELECT that projects a nested path renders the result keyed by the path as written, including a list index ("l[1]"). Recorded behavior only for the exact rendering.
Emulator: IS NULL also matches items whose attribute is absent; REMOVE of an absent attribute on an absent key returns ALL_NEW and creates the item; and a nested list path is rendered as the bare attribute name ("l") instead of "l[1]".
Why: a client reading or deleting by PartiQL gets extra rows, creates phantom items, and cannot correlate projected values back to the paths it asked for.
Fix: the PartiQL evaluator behind ExecuteStatement (predicate evaluation, REMOVE application, projection rendering).
Traces: ddb-sfa-partiql-is-not-null-counts-a-missing-attribute-as-not-null, ddb-sfa-remove-on-an-absent-key-is-a-no-op-unlike-set, partiql-select-projects-nested-map-and-list-paths.

=== Cause 2 of 6: PartiQL index/projection and operand-type enforcement is absent ===
AWS: a PartiQL SELECT through an index qualifier ("FROM \"table\".\"index\"") may only filter on attributes that index projects — filtering on a non-projected attribute of an INCLUDE GSI or a KEYS_ONLY LSI is refused with ValidationException; relational operators over complex-type (M/L/set) operands are refused; and size()/attribute_type over an incompatible operand is refused.
Emulator: all of these succeed — the non-projected filter returns the item, the complex-operand comparison returns an empty page with HTTP 200, and the incompatible size() comparison returns HTTP 200.
Why: a client developing against the emulator ships queries AWS refuses, and relies on reading attributes the index does not hold.
Fix: index-projection and operand-type checks in the PartiQL planner/validator behind ExecuteStatement.
Traces: partiql-relational-operators-reject-complex-type-operands, partiql-select-gsi-include-projection-nonprojected-filter-rejected, partiql-select-lsi-keys-only-nonprojected-filter-and-in-between-key-forms, partiql-select-through-lsi-qualifier, partiql-size-and-attribute-type-select-exact-sets-and-reject-incompatible-size.

=== Cause 3 of 6: the N (number) domain is not enforced on write, and its refusals are worded wrongly ===
AWS: a DynamoDB N value carries at most 38 significant digits and an exponent in [-128, 126]; a value outside that domain, a non-numeric string in an N slot, and an arithmetic result that overflows the range are each refused with ValidationException. Recorded AWS wording is a fixed sentence per class with the offending value substituted (e.g. the "cannot be converted to a numeric value" and overflow sentences); the emulator's text differs.
Emulator: number-canonicalization-boundaries, number-precision-limited-to-38-digits and zero-with-out-of-range-exponent-rejected all SUCCEED with HTTP 200; ddb-frc-non-numeric-number-operand-rejected and execute-statement-rejects-non-numeric-n-parameter / execute-statement-rejects-out-of-range-n-parameter also succeed; where a refusal does occur the message is emulator-authored ('1 validation error detected: The parameter cannot be converted to a numeric value: abc', '1 validation error detected: Number overflow. Attempting to store a number with magnitude larger than supported range').
Why: items that real AWS will never accept are written and later read back, so data written against the emulator is unmigratable; and a client that branches on the refusal message cannot.
Fix: N canonicalisation/validation in the AttributeValue deserializer shared by the item handlers and the PartiQL parameter binder.
Traces: number-canonicalization-boundaries, number-precision-limited-to-38-digits, zero-with-out-of-range-exponent-rejected, update-item-malformed-or-overflowing-number-rejected, malformed-n-in-key-is-top-level-validation-not-cancellation, ddb-frc-non-numeric-number-operand-rejected, execute-statement-rejects-non-numeric-n-parameter, execute-statement-rejects-out-of-range-n-parameter.

=== Cause 4 of 6: item-size, request-size, key-size and nesting-depth refusals carry invented text, and the 4 MB transaction ceiling is not enforced ===
AWS: the 400 KB item ceiling, the 2048-byte partition-key ceiling, the 32-level nesting ceiling and the 4 MB aggregate TransactWriteItems ceiling are each refused with ValidationException and a fixed AWS sentence; on TransactWriteItems these are top-level validation, not a cancellation. The oversized-item refusal takes precedence as AWS orders it, and a request-level defect is reported before the table lookup.
Emulator: the refusals that do fire carry emulator-authored text — 'Item size has exceeded the maximum allowed size', '1 validation error detected: Nesting Levels have exceeded supported limits: Attributes in the item have nested levels beyond supported limit', 'One or more parameter values were invalid: Size of hashkey has exceeded the maximum size limit of2048 bytes' (note the missing space) — and transact-write-aggregate-size-over-4mb-rejected is not refused at all (HTTP 200). oversized-item-to-a-missing-table-not-found-on-put-rejected-on-batch-write shows the wrong precedence between the size defect and the missing table.
Why: a client cannot detect which limit it hit, and a 4 MB+ transaction that AWS refuses is committed here.
Fix: the size/nesting validators in the item, batch and transaction handlers, and the ordering of validation versus table lookup.
Traces: item-size-limit-enforced-at-400kb, partiql-update-growth-past-400kb-matches-update-item, transact-write-items-update-grows-item-over-size-limit, update-item-set-list-append-add-exceeding-400kb-rejected, oversized-item-to-a-missing-table-not-found-on-put-rejected-on-batch-write, transact-write-aggregate-size-over-4mb-rejected, transact-oversized-hash-key-cancels-with-validation-error, nesting-depth-error-precedence-across-malformed-requests, nesting-depth-limit-covers-transact-condition-check-and-legacy-expected-values.

=== Cause 5 of 6: assorted Query/Scan/DescribeTable/RestoreTable request defects are not validated, or name the wrong member ===
AWS: IN with more than 100 operands is refused; an ExclusiveStartKey outside the queried range or missing a key attribute is refused; a bare reserved word used as a sort key in a key condition is refused; Select=SPECIFIC_ATTRIBUTES without a ProjectionExpression and Select=ALL_PROJECTED_ATTRIBUTES on a base-table scan are refused with AWS's fixed sentences; a set value with a repeated member is refused for SS/NS/BS; TotalSegments above 1000000 is refused naming the member as 'TotalSegments' (capitalised, no value interpolation): "1 validation error detected: Value at 'TotalSegments' failed to satisfy constraint: Member must have value less than or equal to 1000000"; DescribeTable given another region's table ARN is refused with "1 validation error detected: Invalid AWS region in '<arn>'"; RestoreTableToPointInTime with a RestoreDateTime outside the restorable window is refused with AWS's sentence.
Emulator: ddb-ss-in-operator-with-101-operands-rejected, exclusive-start-key-outside-range-and-missing-attribute-rejected, ddb-sfa-bare-reserved-sort-key-timestamp-in-key-condition-rejected and empty-and-duplicate-set-members-rejected-for-ss-ns-and-bs all SUCCEED; the Select refusals carry invented text ('One or more parameter values were invalid: Select type SPECIFIC_ATTRIBUTES requires the attributes to be listed in ProjectionExpression', '... ALL_PROJECTED_ATTRIBUTES is allowed only when an index is scanned'); TotalSegments names the lower-cased member and interpolates the value ("Value '1000001' at 'totalSegments' ..."); the cross-region DescribeTable answers ResourceNotFoundException instead of ValidationException; and query-reverse-pages-at-1mb-in-descending-key-order cannot even set up because BatchWriteItem left 6 items unprocessed for a batch AWS would absorb.
Why: invalid requests are accepted (so they fail only in production) and the refusals that do occur name members and values AWS does not.
Fix: Query/Scan input validation, the Select/ProjectionExpression consistency check, the shared constraint-violation renderer (member path casing and no value interpolation where AWS omits it), DescribeTable ARN parsing, and BatchWriteItem's unprocessed-items policy.
Traces: ddb-ss-in-operator-with-101-operands-rejected, exclusive-start-key-outside-range-and-missing-attribute-rejected, ddb-sfa-bare-reserved-sort-key-timestamp-in-key-condition-rejected, empty-and-duplicate-set-members-rejected-for-ss-ns-and-bs, ddb-frc-specific-attributes-without-a-projection-rejected, ddb-ss-all-projected-attributes-on-a-base-table-scan-rejected, ddb-gsi-scan-total-segments-above-one-million-rejected, ddb-ltr-describe-table-with-another-regions-arn-rejected, restore-invalid-time, query-reverse-pages-at-1mb-in-descending-key-order.

=== Cause 6 of 6: vector-index writes are neither validated nor metered ===
AWS: a PutItem whose vector attribute does not satisfy the index's configured dimension/schema is refused with ValidationException, and a vector write is metered per index over that attribute with a per-write byte floor reported in the consumed-capacity breakdown (VectorIndexes / VectorWriteRequestBytes).
Emulator: the malformed vector write succeeds (HTTP 200) and the consumed-capacity response carries no vector metering at all — VectorIndexes is {} and VectorWriteRequestBytes is absent.
Why: vector-index capacity planning is impossible and invalid embeddings are stored.
Fix: PutItem vector validation and the consumed-capacity accounting in the item write path/state.
Traces: put-item-vector-write-validation-and-search-projection, vector-write-request-bytes-floor-and-per-dimension-cost.
