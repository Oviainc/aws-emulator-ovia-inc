# Cloud Map private DNS namespaces publish no Route 53 zone or records: GetNamespace reports a HostedZoneId Route 53 answers NoSuchHostedZone for

> _Note: this issue was identified against the code base at commit `2bfbb03c7bd3982d98fd2c53f75176784e229027`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreatePrivateDnsNamespace

## Description
ONE net-new root cause, exercised by three failing checks of the behavioral replay. It must be closed before this issue is submitted. Model citations use services/service-com-amazonaws-servicediscovery-route53autonaming-v20170314/smithy-model/com-amazonaws-servicediscovery-route53autonaming-v20170314.json. (The checks are listed under the suite heading ecs__servicediscovery; the defect itself is in the servicediscovery -> route53 integration, and both of those services are stood up in this checkout.)

Cause 1 of 1: CreatePrivateDnsNamespace reports a Route 53 hosted-zone id that does not exist in Route 53, and no DNS record sets are ever published for the namespace's services and instances.
AWS: Smithy CreatePrivateDnsNamespace{Name (required, pattern ^(?!arn:)[!-~]{1,253}$), Vpc: ResourceId (required), CreatorRequestId, Description, Tags, Properties} -> {OperationId}; the namespace exists once GetOperation reports the terminal CREATE_NAMESPACE operation, whose Targets['NAMESPACE'] is the namespace id. Recorded behavior: the completed namespace's Namespace.Properties.DnsProperties.HostedZoneId names a Route 53 PRIVATE hosted zone that really exists, associated with the request's Vpc, and it is readable through route53 GetHostedZone and route53 ListResourceRecordSets. Cloud Map then keeps that zone in sync with its own state: a MULTIVALUE service with an A DnsRecord publishes ONE A record set per registered instance at <serviceName>.<namespaceName>., keyed by SetIdentifier = the instance id, with MultiValueAnswer true, TTL = the service's DnsConfig TTL and the instance's AWS_INSTANCE_IPV4 as its value; UpdateService's new TTL rewrites those record sets; DeregisterInstance deletes exactly the deregistered instance's record set and leaves its siblings; DeleteNamespace deletes the hosted zone with the namespace (GetHostedZone then answers NoSuchHostedZone).
Emulator: GetNamespace does return a HostedZoneId, but Route 53 has no such zone — every route53 read against it is refused with NoSuchHostedZone, 'No hosted zone found with ID: <that id>' — so no record set can be observed, rewritten or deleted. The id is therefore a fabricated label rather than a reference to emulator Route 53 state, and the Cloud Map -> Route 53 record synchronisation (register, TTL update, deregister, namespace delete) does not exist.
Why: private-DNS service discovery is the whole point of a private namespace — clients resolve <service>.<namespace> through the VPC's Route 53 zone rather than calling DiscoverInstances. Against this emulator the control plane claims a zone that cannot be inspected, so anything that verifies or depends on the published records (an ECS service that registers tasks in Cloud Map, a DNS-based client, a test that asserts one record set per instance) fails with NoSuchHostedZone instead of resolving. It also makes the namespace's teardown unverifiable.
Fix: the CreatePrivateDnsNamespace handler and its async CREATE_NAMESPACE operation must create a real private hosted zone in the emulator's Route 53 state, associated with the requested Vpc, and store THAT zone's id in DnsProperties.HostedZoneId; the service/instance write paths (CreateService, RegisterInstance, UpdateService, DeregisterInstance, DeleteService) and DeleteNamespace must maintain the record sets and the zone in that shared Route 53 state.
Traces: ecs__servicediscovery.cloudmap-private-dns-namespace-is-a-route53-private-zone-removed-with-it (route53 GetHostedZone on the reported id), ecs__servicediscovery.cloudmap-deregister-instance-removes-only-its-route53-record and ecs__servicediscovery.cloudmap-update-service-ttl-rewrites-the-registered-instance-route53-record (route53 ListResourceRecordSets on the reported id).

## Steps to Reproduce
Boot the emulator from this checkout and replay the three checks in trace_ids, or with botocore (sd = boto3.client('servicediscovery', endpoint_url=<emulator>), r53 = boto3.client('route53', endpoint_url=<emulator>), ec2 = boto3.client('ec2', endpoint_url=<emulator>)):
1. vpc = ec2.create_vpc(CidrBlock='10.0.0.0/16')['Vpc']['VpcId']; wait for 'available' and set EnableDnsSupport/EnableDnsHostnames.
2. op = sd.create_private_dns_namespace(Name='<token>.local', Vpc=vpc)['OperationId']; poll sd.get_operation(OperationId=op) to SUCCESS and take ns = Operation['Targets']['NAMESPACE'].
3. zone = sd.get_namespace(Id=ns)['Namespace']['Properties']['DnsProperties']['HostedZoneId']; r53.get_hosted_zone(Id=zone) -> emulator 404 NoSuchHostedZone 'No hosted zone found with ID: <zone>'; AWS returns a private hosted zone for '<token>.local' associated with vpc.
4. svc = sd.create_service(Name='<svc>', NamespaceId=ns, DnsConfig={'RoutingPolicy':'MULTIVALUE','DnsRecords':[{'Type':'A','TTL':60}]})['Service']['Id']; sd.register_instance(ServiceId=svc, InstanceId='i1', Attributes={'AWS_INSTANCE_IPV4':'10.0.0.11'}) and again for 'i2'/10.0.0.12, polling each operation to SUCCESS.
5. r53.list_resource_record_sets(HostedZoneId=zone, StartRecordName='<svc>.<token>.local.', StartRecordType='A') -> emulator NoSuchHostedZone; AWS returns one A record set per instance (SetIdentifier = instance id, MultiValueAnswer true, TTL 60).
6. sd.update_service(Id=svc, Service={'DnsConfig':{'DnsRecords':[{'Type':'A','TTL':30}]}}) and re-read the record sets -> AWS shows TTL 30. Then sd.deregister_instance(ServiceId=svc, InstanceId='i1') -> AWS deletes only i1's record set. Finally delete the service and sd.delete_namespace(Id=ns) -> AWS's r53.get_hosted_zone(Id=zone) then answers NoSuchHostedZone.
