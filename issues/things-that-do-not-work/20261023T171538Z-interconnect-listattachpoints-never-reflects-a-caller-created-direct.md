# Interconnect ListAttachPoints never reflects a caller-created Direct Connect gateway, so the Connection create/delete lifecycle is unreachable (check hangs to timeout)

> _Note: this issue was identified against the code base at commit `326b33f63f33ac22c419b7169b10d47cfd8c011f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListAttachPoints

## Description
One root cause, surfaced by the one behavioral Interconnect failure that is not already owned by an open issue.

Related but NOT covering: the open WIRE issue "Interconnect wire fidelity: seeded environment/attach-point catalog, not-found HTTP status, and validation-message form diverge from the recorded wire" (20261023T095130Z-interconnect-wire-fidelity-seeded-environment-attach-point-catalog.md). Its Cause 2 reports the inverse symptom of the same handler from the wire corpus (ListAttachPoints returns FABRICATED descriptors where the recording shows an EMPTY list) and carries only wire replay keys. This issue is the behavioral half: the list is also never POPULATED by a gateway the caller really created, which blocks the Connection lifecycle check. Both halves are satisfied by the same change — derive the list from caller-owned gateways — so close them together, but this issue carries the behavioral replay key the wire issue does not.

=== Cause 1 of 1: ListAttachPoints is served entirely from a per-environment seed and ignores Direct Connect gateways the caller owns ===
AWS: Smithy (services/service-com-amazonaws-interconnect-interconnect/smithy-model/com-amazonaws-interconnect-interconnect.json): ListAttachPoints is @readonly, input environmentId (required, EnvironmentId @length 1..64) + maxResults (@range 1..100) + nextToken, output attachPoints (AttachPointDescriptorList, @required) + nextToken, paginated on nextToken/maxResults; documented as "Lists all Attach Points the caller has access to that are valid for the specified Environment". AttachPointType's only modeled value is DirectConnectGateway and AttachPoint$directConnectGateway is a DX-gateway UUID, so the set is derived from Direct Connect gateways the CALLER owns, intersected with what the Environment accepts — it is account state, not a service-published catalog. Consequently a gateway created with directconnect:CreateDirectConnectGateway becomes listable as an attach point for a usable Environment, and that descriptor's identifier is what CreateConnection$attachPoint.directConnectGateway then takes (CreateConnection requires attachPoint + environmentId + bandwidth; DeleteConnection is @idempotent and returns the Connection).
Emulator: ListAttachPoints resolves the environmentId against the seeded environment catalog and then returns ONLY store.attach_points[environmentId] — a fixed per-environment seed computed from the environment id (src/state.rs seed_attach_points / seeded_attach_point_count, name-based v5 UUIDs named "dxgw-<n>-for-<environmentId>"). The handler's own comment states that reading Direct Connect's gateways is deliberately left out (src/ops/list_attach_points.rs lines 203-209: "reading Direct Connect's gateways from here needs that service's SDK client on this crate ... left to its own change"). A gateway the client just created through the directconnect emulator therefore never appears, no matter how long the client polls.
Why: this is the only path a client has from "I own a gateway" to "I can create a Connection on it". A client that creates a DX gateway and waits for it to become a valid attach point waits forever against this emulator, so the whole Connection create/delete lifecycle behind that step is unreachable: CreateConnection, the requested->available provisioning transition, DeleteConnection's deleting->deleted transition and the terminal GetConnection read are never exercised. Conversely, a client that instead takes a seeded descriptor's identifier gets a gateway UUID that does not exist in the account, so what succeeds here fails against AWS. Note the downstream lifecycle itself is UNVERIFIED by this check, not reported broken — DeleteConnection does set state "deleting" with a pending transition to "deleted" (src/ops/delete_connection.rs lines 160-183) — so after fixing the attach-point derivation, re-replay the check and confirm the delete transition separately.
Fix: the ListAttachPoints handler and the attach-point state it reads (src/ops/list_attach_points.rs, src/state.rs attach_points / seed_attach_points): compute the descriptors for an Environment from the Direct Connect gateways that exist in the emulator for the caller (empty when none has been created), and stop serving an environment-id-derived seed. Pagination, the unknown-environment InterconnectClientException and the cursor-tag validation in that handler can stay as they are.
Traces: interconnect.delete-connection-transitions-to-deleting-then-gone.

## Evidence
Behavioral suite (simparity-behavioral-aws-v1): interconnect 9/15 passed (60%), 6 mismatched. Five of the six failures are marked OWNED by 20261022T145736Z-interconnect-error-semantics-three-operations-still-501-environment.md and are skipped here. The remaining failure:

- interconnect.delete-connection-transitions-to-deleting-then-gone — verdict mismatch, "Error: Check timed out after 60.0s". The check's prologue (_provision_prereqs -> _create_attach_point) calls directconnect CreateDirectConnectGateway, then polls ListAttachPoints for that gateway id with _poll_until(..., timeout_s=60, interval_s=3) waiting for an attachPoints entry whose identifier == the created directConnectGatewayId. The gateway never appears, so the poll spins until the harness's 60s budget expires; CreateConnection / DeleteConnection / GetConnection in the body of the check are never reached. The 60.0s expiry coinciding with that 60s poll is the signature of this step, and the positive controls in the sibling checks show the emulator is otherwise answering interconnect (ListConnections, ListEnvironments, GetEnvironment all succeed).

Source corroboration in the checkout:
- services/service-com-amazonaws-interconnect-interconnect/src/ops/list_attach_points.rs lines 163-180: the response body is `store.attach_points.get(&input.environment_id).cloned().unwrap_or_default()` only; lines 203-210 comment that caller-owned Direct Connect gateways are intentionally NOT consulted and `let descriptors = seeded;`.
- services/service-com-amazonaws-interconnect-interconnect/src/state.rs lines 618-659: seeded_attach_point_count(index) = 1 + index % 3 and seed_attach_points() build descriptors {type: DirectConnectGateway, identifier: uuid_v5("<environmentId>#<ordinal>"), name: "dxgw-<ordinal>-for-<environmentId>"} from the environment catalog alone — no account/gateway input.
- services/service-com-amazonaws-interconnect-interconnect/src/ops/delete_connection.rs lines 160-183: the deleting -> deleted transition the check wanted to assert IS implemented, which is why this is filed as an attach-point discovery defect and not as a delete-state defect.

InterconnectClientException(400)/ResourceNotFoundException(404); CreateConnection requires bandwidth (@pattern ^\d+[MG]bps$), attachPoint, environmentId; DeleteConnection idempotent, identifier @pattern ^(mcc|lmcc)-[a-z0-9]{8}$, output connection @required.

5. After the fix, re-replay interconnect.delete-connection-transitions-to-deleting-then-gone end to end: the check must get past _create_attach_point, create a Connection on the discovered attach point, see DeleteConnection return the connection, and then observe GetConnection report state 'deleted' (or ResourceNotFoundException) within its 150s wait.
