## Description
Five net-new root causes in the apigatewayv2 service. Each is listed with its own failing check ids; all five must be closed.

Cause 1 of 5: the published ApiEndpoint is an AWS public execute-api hostname the emulator does not serve, so the entire HTTP-API data plane is unreachable (48 checks).
AWS: Smithy (service-com-amazonaws-apigatewayv2-apigatewayv2): CreateApi — POST /v2/apis, 201; output member ApiEndpoint (jsonName apiEndpoint), documented as "The URI of the API, of the form {api-id}.execute-api.{region}.amazonaws.com". The contract is that this URI is served by the API itself: ApiEndpoint (+ '/<stage>' for a named stage) + the route path reaches the route's integration. ImportApi/GetApi/GetApis publish the same member.
Emulator: the value served is the literal AWS public form "https://<api-id>.execute-api.<region>.amazonaws.com", which is not one of the emulator's own hosts and which it does not listen on. Replay refuses to follow it: simparity.published.PublishedUrlRejected "endpoint_url was given https://<api-id>.execute-api.<region>.amazonaws.com (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener". Every check below stops at endpoint resolution with no HTTP request made, so route-key precedence, stage prefixes, CORS, parameter mapping, payload-format 1.0/2.0 envelopes, Lambda/HTTP_PROXY integrations, authorizer caching, throttling and deletion-stops-serving are all ungradeable.
Why: ApiEndpoint is the only documented way a client finds a deployed API. Published as an amazonaws.com name it sends every client off the emulator, so an estate built against the emulator cannot be driven end to end even though all control-plane calls succeed.
Fix: the ApiEndpoint construction in the apigatewayv2 crate's CreateApi/GetApi/GetApis/ImportApi handlers plus the execute-api front-door listener that must serve what they publish.

Cause 3 of 5: a deployed WEBSOCKET stage never completes the RFC 6455 upgrade — the handshake is answered 500 "Internal server error" or hangs (4 checks).
AWS: recorded behavior only. A correct WebSocket handshake against wss://<api-id>.execute-api.<region>.amazonaws.com/<stage> is answered HTTP/1.1 101 Switching Protocols with the Sec-WebSocket-Accept header; the $connect integration's response decides 101 vs 403/401, and no successful handshake is ever answered 500.
Emulator: the handshake is answered "HTTP/1.1 500 Internal Server Error" with content-type application/json and body {"message":"Internal server error"}, or nothing at all until the check's deadline (last result None / read timeout). With the handshake refused, route dispatch, two-way RouteResponse semantics, @connections broadcast and MOCK integration response selection are unobservable.
Why: no WebSocket client can connect to an emulated WebSocket API, so an estate that depends on $connect/$disconnect, route responses or server pushes cannot run; a 500 also tells a client to retry a request AWS would have accepted.
Fix: the WEBSOCKET execute-api front door — the upgrade path that must hand the connection to the api's socket after running $connect — and the $connect integration invocation in the apigatewayv2 crate's data-plane handler.

Cause 4 of 5: on a connection that DID upgrade, every inbound frame is answered with the gateway's own error frame {"connectionId":...,"message":"Internal server error","requestId":...} instead of the route integration's reply (2 checks).
AWS: recorded behavior only. On a two-way WebSocket route whose integration returns a body, the client receives that body verbatim (e.g. the 'pong' reply of a 'ping' action, or the named route's own payload). API Gateway's "Internal server error" frame is reserved for an integration failure; a healthy Lambda/MOCK integration never produces it.
Emulator: the frame returned carries message "Internal server error" with a connectionId and requestId, so route selection by $request.body.action and the post-to-connection/GoneException lifecycle both fail on the control leg. The fixed text here is "Internal server error"; connectionId and requestId are per-run values and are not themselves the defect.
Why: a client sees a 5xx-equivalent error frame for a request AWS answers successfully, so WebSocket applications behave as if their backend were broken.
Fix: the WEBSOCKET route-dispatch path of the apigatewayv2 data-plane handler (route selection expression evaluation and integration invocation), which must deliver the integration's reply and only frame a real integration failure.

API Gateway's parameter-mapping rules reserve a set of headers; a mapping keyed "overwrite:header.authorization" is refused with 400 BadRequestException and the message "Invalid mapping expression specified: Validation Result: warnings : [], errors : [Operations on header authorization are restricted]" — all of that text is fixed except the header name, which is taken from the request's mapping key.
