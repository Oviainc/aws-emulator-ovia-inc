# SageMaker: AttachClusterNodeVolume's cluster-not-found Message is prefixed with the internal exception class name, and GetSearchSuggestions never suggests a TrainingJob's HyperParameters facet (2 causes)

> _Note: this issue was identified against the code base at commit `8fe1b88606c77dfa59d771b1a110885b6dfaed56`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
AttachClusterNodeVolume

## Description
Two independent net-new root causes in the SageMaker control plane, each grounded in its own failing behavioral check. Neither is named by an already-filed scaffold-stub issue, and neither check was reported as OWNED by an open issue's replay key. This issue bundles TWO causes and BOTH must be closed before submitting.

Cause 1 of 2: the cluster-not-found refusal of the HyperPod cluster-node lookup carries the emulator's internal exception class name as a prefix on the error Message.
Failing check ids: sagemaker.attach-cluster-node-volume-unknown-node-not-found
AWS: Smithy: AttachClusterNodeVolume (com.amazonaws.sagemaker#AttachClusterNodeVolume) requires ClusterArn (@pattern ^arn:aws[a-z\-]*:sagemaker:[a-z0-9\-]*:[0-9]{12}:cluster/[a-z0-9]{12}$), NodeId (@pattern ^i-[a-f0-9]{8}(?:[a-f0-9]{9})?$) and VolumeId, and models exactly one error: ResourceNotFound (HTTP 400, "Resource being access is not found."). Recorded behavior for the two distinct not-found classes: a syntactically valid ClusterArn that no cluster in the account holds is refused 400 ResourceNotFound with Message exactly "Specified cluster not found"; an unknown NodeId on a cluster that DOES exist is refused 400 ResourceNotFound with Message exactly "Specified cluster node not found". Both messages are entirely FIXED TEXT — AWS interpolates nothing from the request into either one (no cluster ARN, no node id), and the two sentences differ so a caller can tell which identifier was unknown. The response Message carries the sentence only; the error code is carried in the error code field (ResourceNotFound), never repeated inside the Message.
Emulator: the error code is correct (ResourceNotFound) and the node-not-found sentence is correct, but the cluster-not-found Message is returned as "ClusterNotExistsException: Specified cluster not found" — AWS's fixed sentence with the internal exception class name "ClusterNotExistsException: " prepended. The correct fixed text is present; the defect is purely the leading "<ExceptionClassName>: " prefix. The sibling DescribeClusterNode node-not-found path on the same lookup returns the clean "Specified cluster node not found", so only the cluster-not-found sentence is affected.
Why: the Message of a modeled refusal is part of the contract. A client that distinguishes an unknown cluster from an unknown node by comparing (or prefix/equality matching) the message text takes the wrong branch or fails outright, and operators see an emulator-internal Java/Rust exception class name leaked into a customer-visible API message, which real AWS never emits. Any assertion or log scraper keyed on AWS's sentence breaks even though the underlying resolution decision is right.
Fix: the message constant behind the cluster-not-found arm of the cluster-node lookup, not the handler's resolution logic — the handler already returns the modeled ResourceNotFound on the correct branch; the constant it stringifies carries the exception-class prefix and must carry the bare sentence only. Both the AttachClusterNodeVolume handler and the DescribeClusterNode handler read the same constant, so fixing the constant fixes every operation that reports an unknown cluster through that lookup.
Traces: sagemaker.attach-cluster-node-volume-unknown-node-not-found — the check's unknown-node assertions (ResourceNotFound + "Specified cluster node not found", for both AttachClusterNodeVolume and DescribeClusterNode) PASS; it fails only on the discriminating control that passes a nonexistent ClusterArn. Handler: services/service-com-amazonaws-sagemaker-sagemaker/src/ops/attach_cluster_node_volume.rs line 178 returns ResourceNotFound{message: crate::state::CLUSTER_NODE_LOOKUP_CLUSTER_NOT_FOUND} — that constant in src/state.rs is the value to correct (compare the clean crate::state::CLUSTER_NODE_NOT_FOUND used at line 225).

Cause 2 of 2: GetSearchSuggestions offers no HyperParameters facet for Resource=TrainingJob at all, so a hint naming a real training job's hyperparameter key returns an empty PropertyNameSuggestions list.
Failing check ids: sagemaker.get-search-suggestions-reflects-existing-resources
AWS: Smithy: GetSearchSuggestions documentation — "An auto-complete API for the search functionality in the SageMaker console. It returns suggestions of possible matches for the property name to use in Search queries. Provides suggestions for HyperParameters, Tags, and Metrics." The operation takes Resource (ResourceType enum, required) plus SuggestionQuery.PropertyNameQuery.PropertyNameHint, returns PropertyNameSuggestions (PropertyNameSuggestionList of PropertyNameSuggestion{PropertyName}) and models NO errors — so there is no refusal path and an unsupported facet can only be reported as a missing suggestion. Recorded behavior for the facet rendering (the model leaves PropertyName unconstrained): for Resource=TrainingJob, a hyperparameter key the caller supplied on CreateTrainingJob is suggested as "hyperparameters.<key>" — the facet namespace prefix is LOWERCASE, which is the form Search's Filter.Name accepts, and a hint that is a prefix of that full lowercase property name (e.g. "hyperparameters.<key-minus-a-few-chars>") returns exactly that property name. The variable part is the hyperparameter key taken verbatim from the request's HyperParameters map; "hyperparameters." is the fixed prefix.
Emulator: the response is HTTP 200 with PropertyNameSuggestions == [] — not a wrong-cased suggestion, but no suggestion whatsoever. The stored-property-name collector has no TrainingJob arm, and the operation's own module comment states the gap: the training-job record is only the TrainingJobSummary projection ListTrainingJobs needs, so it keeps neither tags nor hyperparameters, "which is also why no HyperParameters.<name> is suggested yet". The only names offered for Resource=TrainingJob are the modeled SearchRecord member names in the model's own casing, and the hint is filtered case-sensitively against them, so a lowercase "hyperparameters."-prefixed hint matches nothing and the list comes back empty.
Why: this is the console autocomplete contract. A client (or the SageMaker console itself) that asks for completions of a hyperparameter name gets nothing back and cannot discover the property name to put in Search's Filter.Name, so hyperparameter-based search is undiscoverable even though the training job was created successfully with that hyperparameter. It is strictly worse than a mis-cased answer: there is no string to correct and no modeled error to branch on — just a silently empty 200 that reads as "this account has no such property".
Why this is NOT already covered: the open issue 20261024T160943Z-sagemaker-control-plane-gaps-createuserprofile-and-deleteaibenchmarkjob-are.md carries cause 5 about GetSearchSuggestions, but that cause is scoped to Resource=ExperimentTrialComponent emitting the facet prefix as "Parameters.<key>" instead of "parameters.<key>" (its replay key is sagemaker.search-suggestions-returns-matching-property-names, a different check), i.e. a RENDERING fix at the push("Parameters", ...) site for a facet that IS collected. This cause is the TrainingJob HyperParameters facet not being collected at all — there is no TrainingJob arm to re-case — so correcting that casing leaves this check still returning []. Both must be fixed for GetSearchSuggestions to be faithful.
Fix: the stored-property-name collection in GetSearchSuggestions' handler plus the training-job record in the service state — persist the caller-supplied HyperParameters (and Tags) on the training-job record that CreateTrainingJob writes, add a TrainingJob arm that offers each stored hyperparameter key under the lowercase "hyperparameters" facet, and make the hint filter match the facet prefix the way AWS cases it.
Traces: sagemaker.get-search-suggestions-reflects-existing-resources — the check creates a training job with a unique custom HyperParameters key, then polls GetSearchSuggestions(Resource="TrainingJob", PropertyNameHint="hyperparameters.<key-prefix>") for 90s for a suggestion equal to "hyperparameters.<key>"; every probe returns []. Handler: services/service-com-amazonaws-sagemaker-sagemaker/src/ops/get_search_suggestions.rs — stored_property_names has arms for TrainingJob's siblings (Model line 341, ModelPackage lines 348-352, trial components lines 377-394) but falls through to the catch-all `_ => {}` at line 419 for TrainingJob; the module comment at lines 400-406 records the missing record fields, and the modeled-member offer loop is at lines 480-485.
