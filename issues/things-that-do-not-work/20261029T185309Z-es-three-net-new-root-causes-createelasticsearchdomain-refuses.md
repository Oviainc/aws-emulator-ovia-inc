# es: three net-new root causes — CreateElasticsearchDomain refuses valid T3 instance types from a stale instance-type enum, a duplicate create is refused instead of echoing the existing config, and CreatePackage is a 501 stub

> _Note: this issue was identified against the code base at commit `611eef386f1100e1b77f5a1515bab52b7a7a6aeb`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateElasticsearchDomain

## Description
The Amazon Elasticsearch Service emulator (crate services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015) answers, but every behavioral check in this suite is blocked by one of three distinct defects. 3 causes are bundled here; all must be closed.

Cause 1 of 3: CreateElasticsearchDomain refuses a valid T3 instance type because the service's instance-type enum is stale (checks es.describe-domains-batch-scoped-to-requested-names-only, es.domain-tag-lifecycle-add-list-remove, es.duplicate-create-domain-returns-existing-config-unchanged, es.get-compatible-versions-reflects-created-domain-version).
AWS: CreateElasticsearchDomain accepts ElasticsearchClusterConfig.InstanceType = "t3.small.elasticsearch" for a 7.10 domain and answers HTTP 200 with DomainStatus; T3 (t3.small.elasticsearch / t3.medium.elasticsearch) are generally-available Amazon ES instance types and are members of ESPartitionInstanceType in the current AWS model. Recorded behavior: all four checks create a domain with {"InstanceType": "t3.small.elasticsearch", "InstanceCount": 1} and proceed, i.e. real AWS returned 200 for exactly this request. Smithy (as checked in): ElasticsearchClusterConfig.InstanceType targets com.amazonaws.elasticsearchservice#ESPartitionInstanceType, whose `values` list in services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015/smithy-model/com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015.json stops at the i3.* family and contains NO t3.* member — the model slice is older than the API it is meant to emulate.
Emulator: the framework's pre-handler constraint validation refuses the request with HTTP 400 ValidationException and the message "1 validation error detected: Value 't3.small.elasticsearch' at 'elasticsearchClusterConfig.instanceType' failed to satisfy constraint: Member must satisfy enum value set: [m3.medium.elasticsearch, ... i3.16xlarge.elasticsearch]". In that message the fixed text is "1 validation error detected: Value '<value>' at '<member path>' failed to satisfy constraint: Member must satisfy enum value set: [<members>]"; the value, the member path and the member list are taken from the request and the model. The shape of the message is AWS-like — the defect is that the call is refused at all, so no domain is ever created.
Why: a client that creates a T3 domain (the cheapest and the one every tutorial and test harness uses) cannot create any domain at all. Everything downstream of a domain — AddTags/ListTags/RemoveTags, DescribeElasticsearchDomains, GetCompatibleElasticsearchVersions, AssociatePackage — is unreachable, so the emulator cannot stand in for Amazon ES for any domain-scoped workflow.
Fix: the service's checked-in Smithy model slice (ESPartitionInstanceType must carry the full current member set, including the t3.* family) so the framework's enum validation stops rejecting instance types AWS accepts; no change is needed in the handler itself, which never inspects the instance type.
Traces: es.describe-domains-batch-scoped-to-requested-names-only, es.domain-tag-lifecycle-add-list-remove, es.duplicate-create-domain-returns-existing-config-unchanged, es.get-compatible-versions-reflects-created-domain-version.

Cause 2 of 3: a second CreateElasticsearchDomain naming an existing domain is refused instead of answering 200 with the first call's configuration (check es.duplicate-create-domain-returns-existing-config-unchanged).
AWS: recorded behavior only — the check asserts that a repeat CreateElasticsearchDomain for a name that already exists answers HTTP 200 and reports the FIRST call's ElasticsearchClusterConfig (InstanceCount 1) while silently ignoring the retry's differing InstanceCount 2, and that a later DescribeElasticsearchDomain still reports the original InstanceCount. The operation does model ResourceAlreadyExistsException (HTTP 409 per the model's httpError, documented "An exception for creating a resource that already exists"), but the recording shows it is not raised for this retry.
Emulator: services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015/src/ops/create_elasticsearch_domain.rs refuses unconditionally on an existing key — it returns ResourceAlreadyExistsException with the emulator-authored message "Domain already exists: <DomainName>" (fixed text "Domain already exists: " plus the requested DomainName) whenever store.domains already contains domain_key(region, DomainName). This cause is currently MASKED by Cause 1 (the check never reaches the second create), so it must be re-replayed after Cause 1 is fixed.
Why: a client that retries a create — the normal reaction to a timeout or a throttle, and what the AWS SDK retry layer does on its own — gets a hard failure from the emulator where AWS returns the existing domain, so idempotent provisioning code (CloudFormation-style converge loops, Terraform-style retries) breaks against the emulator and the emulator's refusal message is also not AWS's wording for this class.
Fix: CreateElasticsearchDomain's handler (its existing-domain branch) must answer from the stored record instead of refusing, leaving the stored config untouched; if any input combination genuinely warrants ResourceAlreadyExistsException, its message must be AWS's text for that error, not emulator prose.
Traces: es.duplicate-create-domain-returns-existing-config-unchanged.

Cause 3 of 3: CreatePackage is an unimplemented scaffold stub, so the whole package surface is unreachable (checks es.associate-package-rejected-on-processing-domain-leaves-association-unset, es.update-package-creates-new-version-visible-in-history).
AWS: CreatePackage accepts PackageName, PackageType="TXT-DICTIONARY" and PackageSource={S3BucketName, S3Key} and answers HTTP 200 with PackageDetails carrying PackageID and PackageStatus (COPYING, settling to AVAILABLE). Smithy: CreatePackage models AccessDeniedException, BaseException, InternalException, InvalidTypeException, LimitExceededException, ResourceAlreadyExistsException and ValidationException — HTTP 501/NotImplemented is not among them.
Emulator: the request is answered HTTP 501 with code NotImplemented and the message "operation CreatePackage is scaffolded but not implemented in this emulator" — the handler body in services/service-com-amazonaws-elasticsearchservice-amazonelasticsearchservice2015/src/ops/create_package.rs returns crate::scaffolded::Scaffolded::not_implemented("CreatePackage") without touching state.
Why: no package can be created, so nothing can exercise AssociatePackage / ListPackagesForDomain / ListDomainsForPackage, UpdatePackage, DescribePackages or GetPackageVersionHistory; a client gets an unmodeled 501 with an error code no SDK error shape knows, so retry and error-handling logic cannot classify it. Two independent package workflows are blocked on this one operation. (Note: a separate auto-filed issue already covers the unimplemented CreateOutboundCrossClusterSearchConnection stub; no open issue covers CreatePackage.)
Fix: implement CreatePackage in its handler file above, persisting a package record in the service state so the Describe/Update/History/Associate operations can read it back.
Traces: es.associate-package-rejected-on-processing-domain-leaves-association-unset, es.update-package-creates-new-version-visible-in-history.
