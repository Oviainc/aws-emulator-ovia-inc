# cognito-idp__kms__lambda__sqs: a user pool's CustomEmailSender Lambda trigger is never invoked, so no real verification code is ever issued and every code-dependent flow (sign-up, forgot-password, attribute verification, EMAIL_OTP) is unreachable (1 cause)

## Description
Cause 1 of 1: a user pool configured with LambdaConfig.CustomEmailSender never invokes that function, so no verification code is ever produced and no flow that consumes a code can run. Failing check ids for this cause (10): cognito-idp__kms__lambda__sqs.deep-cognito-idp-1-real-code-email-otp-wrong-code-rejected, .deep-cognito-idp-1-real-code-forgot-password-code-reuse-rejected, .deep-cognito-idp-1-real-code-forgot-password-confirm, .deep-cognito-idp-1-real-code-forgot-password-wrong-code-rejected, .deep-cognito-idp-1-real-code-reissued-reset-code-invalidates-first-rejected, .deep-cognito-idp-1-real-code-resent-signup-code-invalidates-first-rejected, .deep-cognito-idp-1-real-code-signup-confirm, .deep-cognito-idp-1-real-code-signup-wrong-code-rejected, .deep-cognito-idp-1-real-code-verify-email-wrong-code-rejected, .deep-cognito-idp-1-real-code-verify-updated-email.

AWS: Smithy (cognito-idp) models the trigger but not its dispatch — LambdaConfigType.CustomEmailSender targets CustomEmailLambdaVersionConfigType with REQUIRED members LambdaVersion (CustomEmailSenderLambdaVersionType, documented as 'You must use a LambdaVersion of V1_0 with a custom sender function') and LambdaArn, alongside LambdaConfigType.KMSKeyID ('Amazon Cognito uses the key to encrypt codes and temporary passwords sent to ...'). The dispatch itself is recorded behavior only: on AWS, once a pool carries that configuration every code-bearing message is handed to the named function instead of being emailed. SignUp, ResendConfirmationCode, ForgotPassword, GetUserAttributeVerificationCode and the EMAIL_OTP sign-in challenge each invoke it with triggerSource = CustomEmailSender_SignUp / _ResendCode / _ForgotPassword / _VerifyUserAttribute / _Authentication, with userName, request.userAttributes and request.code — an AWS Encryption SDK message whose aws-kms encrypted data key is decryptable under the pool's KMSKeyID with the message's own encryption context. The decrypted string IS the live credential: ConfirmSignUp / ConfirmForgotPassword / VerifyUserAttribute / RespondToAuthChallenge with it succeed, and with any other value the call is refused CodeMismatchException (Smithy: CodeMismatchException, client error, httpError 400, message 'Invalid code or auth state for the user.' — fixed text, no variable part).

Emulator: the function is never invoked at all. Every check builds the whole estate successfully (kms CreateKey with a policy allowing cognito-idp.amazonaws.com kms:Encrypt/kms:CreateGrant, sqs CreateQueue, an execution role with kms:Decrypt + sqs:SendMessage, lambda CreateFunction on nodejs22.x polled to State=Active, lambda AddPermission for cognito-idp.amazonaws.com, cognito-idp CreateUserPool with LambdaConfig={'CustomEmailSender': {'LambdaVersion': 'V1_0', 'LambdaArn': <fn>}, 'KMSKeyID': <key ARN>}, CreateUserPoolClient) and SignUp/ForgotPassword themselves answer 200 — then the inbox poll over the trigger's SQS sink (ReceiveMessage, WaitTimeSeconds=5, 120 s budget) raises "no 'CustomEmailSender_SignUp' code for '<user>' reached the trigger's queue within 120.0s; deliveries seen but unmatched: []". The deployed handler reports its own decrypt failures to the same queue (ok=false), so an empty queue proves it never ran rather than that it ran and failed.

Why: with a CustomEmailSender configured, that trigger is the ONLY place a code exists — there is no email and no API that returns it. A client gets a pool where confirmation, password reset, email re-verification and EMAIL_OTP sign-in can never be completed, and the negative half of each contract (CodeMismatchException for a wrong, reused, or superseded code) cannot be demonstrated either, because no correct code exists to contrast it with. Code-rotation semantics (a resent sign-up code or a reissued reset code invalidating the first) are equally unobservable.

Fix: the cognito-idp user-pool trigger-dispatch component — the code-issuing paths of SignUp, ResendConfirmationCode, ForgotPassword, GetUserAttributeVerificationCode/UpdateUserAttributes and the EMAIL_OTP challenge generator must invoke the configured CustomEmailSender function with triggerSource, userName, userAttributes and request.code encrypted under the pool's LambdaConfig.KMSKeyID as an AWS Encryption SDK message, and the code store they write must be the same one ConfirmSignUp/ConfirmForgotPassword/VerifyUserAttribute/RespondToAuthChallenge validate against (so a wrong value yields CodeMismatchException). This requires the Lambda invoke path to actually execute the deployment package.

## Evidence
Expected (AWS): after cognito-idp SignUp on a pool whose LambdaConfig.CustomEmailSender names a function, that function is invoked within seconds with triggerSource='CustomEmailSender_SignUp', userName=<the signed-up user> and request.code = an AWS Encryption SDK message that KMS-decrypts under the pool's KMSKeyID; the decrypted code is the one ConfirmSignUp accepts, and any other value is refused HTTP 400 CodeMismatchException with message 'Invalid code or auth state for the user.' The same holds for ForgotPassword (CustomEmailSender_ForgotPassword), ResendConfirmationCode (CustomEmailSender_ResendCode), GetUserAttributeVerificationCode (CustomEmailSender_VerifyUserAttribute) and the EMAIL_OTP challenge (CustomEmailSender_Authentication, an 8-digit code).

Actual (emulator): no invocation occurs. All 10 checks fail inside _CodeInbox.next_code with AssertionError "no '<triggerSource>' code for '<username>' reached the trigger's queue within 120.0s; deliveries seen but unmatched: []" — an empty list, i.e. the sink received nothing at all, not even the handler's own ok=false failure report. The user names in those messages (e.g. 'sim2real-xsvc-user-966c803b98bc') and the generated key/queue/function names are per-run values, not requirements; the requirement is that one delivery per code-bearing flow arrives, carrying that flow's triggerSource and a code decryptable under the pool's CMK.

## Steps to Reproduce
1. kms CreateKey (SYMMETRIC_DEFAULT, ENCRYPT_DECRYPT) with a key policy allowing the account root kms:* and Service principal cognito-idp.amazonaws.com kms:Encrypt + kms:CreateGrant.
2. sqs CreateQueue (the sink) and note its ARN/URL.
3. iam CreateRole trusting lambda.amazonaws.com with an inline policy allowing kms:Decrypt on the key and sqs:SendMessage on the queue.
4. lambda CreateFunction (any runtime) whose handler KMS-decrypts event.request.code and SendMessages {triggerSource, userName, code, ok} to the queue; poll to State=Active. lambda AddPermission(Principal=cognito-idp.amazonaws.com, SourceArn=<pool ARN>).
5. cognito-idp CreateUserPool with AutoVerifiedAttributes=['email'] and LambdaConfig={'CustomEmailSender': {'LambdaVersion': 'V1_0', 'LambdaArn': <fn ARN>}, 'KMSKeyID': <key ARN>}; CreateUserPoolClient.
6. cognito-idp SignUp a user with an email attribute, then poll the queue for up to 120 s: no message ever arrives, so no code exists to pass to ConfirmSignUp and no CodeMismatchException can be elicited for a wrong one.
7. Repeat with ForgotPassword, ResendConfirmationCode, GetUserAttributeVerificationCode and an EMAIL_OTP InitiateAuth challenge — each is equally silent.
8. Re-replay the 10 check ids in trace_ids to confirm.
