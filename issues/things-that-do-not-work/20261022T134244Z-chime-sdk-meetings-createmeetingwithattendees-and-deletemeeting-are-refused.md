# chime-sdk-meetings: CreateMeetingWithAttendees and DeleteMeeting are refused with unmodeled AmbiguousService because the router resolves services by sigv4 signing name

> _Note: this issue was identified against the code base at commit `67b7a4ea014b7cfd9cdb5213b26731b0db184c45`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateMeetingWithAttendees

## Description
Cause 1 of 1: the emulator's front-door service-resolution layer dispatches an inbound request on the sigv4 signing name from the Authorization credential scope rather than on the request's endpoint prefix / Host and the restJson1 @http method+URI. Chime is a family in which several distinct AWS services deliberately share the signing name 'chime', so that key is not unique: the router finds 6 candidate emulated services for every chime-signed request and refuses to serve any of them, returning the unmodeled error code 'AmbiguousService'. No chime-sdk-meetings handler is ever reached. Failing checks for this cause: chime-sdk-meetings.create-meeting-with-attendees-creates-all-attendees (refused on CreateMeetingWithAttendees) and chime-sdk-meetings.delete-meeting-not-found-rejected (refused on DeleteMeeting).

AWS: Smithy (services/service-com-amazonaws-chimesdkmeetings-chimemeetingssdkservice/smithy-model/com-amazonaws-chimesdkmeetings-chimemeetingssdkservice.json) — service ChimeMeetingsSDKService, version 2021-07-15, protocol restJson1, aws.auth#sigv4 name = 'chime', aws.api#service endpointPrefix = 'meetings-chime', arnNamespace = 'chime', 16 operations. The sibling Chime SDK services (Chime, Chime SDK Identity, Chime SDK Messaging, Chime SDK Media Pipelines, Chime SDK Voice) share the SAME sigv4 signing name 'chime' while each carries its OWN endpointPrefix ('chime', 'identity-chime', 'messaging-chime', 'media-pipelines-chime', 'voice-chime'), so real AWS disambiguates by the endpoint host the client was pointed at and by the operation's URI path, never by signing name alone. Per the model: CreateMeetingWithAttendees is POST /meetings?operation=create-attendees -> HTTP 200 with {Meeting, Attendees, Errors}; required members ClientRequestToken (@length 2..64, pattern ^[-_a-zA-Z0-9]*$, idempotencyToken), MediaRegion (@length 2..64), ExternalMeetingId (@length 2..64), Attendees (@length 1..20); modeled errors BadRequestException(400), ConflictException(409), ForbiddenException(403), LimitExceededException(400), ThrottlingException(429), UnauthorizedException(401), ServiceFailureException(500), ServiceUnavailableException(503). DeleteMeeting is DELETE /meetings/{MeetingId} -> HTTP 204 with an empty body, MeetingId a @pattern-constrained GUID, modeled errors BadRequestException(400), ForbiddenException(403), NotFoundException(404), ThrottlingException(429), UnauthorizedException(401), ServiceFailureException(500), ServiceUnavailableException(503). 'AmbiguousService' is not a modeled error of this service and is not in its common_errors (BadRequestException, ForbiddenException, ServiceFailureException, ServiceUnavailableException, ThrottlingException, UnauthorizedException). Recorded behavior only, for the idempotency semantics the delete check asserts: DeleteMeeting against a well-formed but never-created MeetingId succeeds as a no-op (2xx) and leaves nothing behind, while GetMeeting on a deleted meeting is NotFoundException.

Emulator: every chime-signed call from a correctly configured botocore 'chime-sdk-meetings' client is refused before any handler runs with error code 'AmbiguousService' and a message of the form "6 emulated services all claim requests for 'chime': chime, chime, chime, chime, chime, chime; the request is rejected rather than served by an arbitrary one" (that text is an EXAMPLE, not a requirement). botocore also exhausted its retry budget on both calls ('reached max retries: 3'), i.e. the refusal is delivered in a form the SDK classifies as retryable rather than as a terminal 4xx. Hypothesis: the refusal is emitted from the router layer with a 5xx status; the replay output records only the parsed error code and message. The message renders every candidate with the same display name 'chime' instead of their distinct sdkIds, so it does not even identify which services collided. Concretely: CreateMeetingWithAttendees never creates a meeting or its attendees (so the whole downstream e2e lifecycle — ListAttendees, TagResource/ListTagsForResource, Start/StopMeetingTranscription, UpdateAttendeeCapabilities, DeleteMeeting, and the post-delete NotFoundException assertions — is unreachable), and DeleteMeeting on a never-created GUID returns AmbiguousService instead of an idempotent 2xx no-op.

Why: a client relying on AWS's behavior cannot reach Chime SDK Meetings at all — not one of the 16 modeled operations is exercisable, and no modeled error path can be observed. Worse, the refusal masquerades as a retryable server fault, so SDK and application retry loops spin to max attempts and then surface an error code AWS never returns, instead of failing fast with NotFoundException/ConflictException or succeeding. Idempotent teardown patterns (delete-if-exists cleanup, not-found probes) and error handling keyed on documented codes all break, and callers see latency amplified by the full retry budget on every call.

Fix: the front-door service-resolution/routing component that maps an inbound request to an emulated service — not any chime-sdk-meetings handler. Resolution must key on the request's endpoint prefix / Host header and, where that is absent, on the operation's restJson1 method + URI path, with the sigv4 signing name used only as a weak hint; a shared signing name must never be treated as a service identity. A genuine resolution failure must additionally be rendered as a terminal AWS error shape rather than a retryable one. This is the same class of defect already filed for sibling signing-name families, including 20261022T075458Z-chime-sdk-media-pipelines-is-entirely-unreachable-the.md and 20261022T042904Z-chime-sdk-identity-is-entirely-unreachable-the-router.md. Neither of those carries the replay keys chime-sdk-meetings|CreateMeetingWithAttendees|AmbiguousService or chime-sdk-meetings|DeleteMeeting|AmbiguousService (the media-pipelines issue carries only chime-sdk-meetings|CreateMeeting|AmbiguousService), so these two operations are filed here and must be re-replayed against chime-sdk-meetings.

Traces: chime-sdk-meetings.create-meeting-with-attendees-creates-all-attendees and chime-sdk-meetings.delete-meeting-not-found-rejected, each aborting on its first chime-signed call with AmbiguousService.

Key facts: error code AmbiguousService (unmodeled) replaces both the success responses (200 / 204) and the modeled 404 NotFoundException; the refusal is retried to the SDK's max attempts, so it is classified retryable rather than a terminal client error; the collision set is exactly the services sharing sigv4Name 'chime' even though each has a distinct endpointPrefix (meetings-chime vs chime / identity-chime / messaging-chime / media-pipelines-chime / voice-chime), which is the key the router should have used. The quoted message text is an example; the code, the status class and the fact of refusal are the divergence.
