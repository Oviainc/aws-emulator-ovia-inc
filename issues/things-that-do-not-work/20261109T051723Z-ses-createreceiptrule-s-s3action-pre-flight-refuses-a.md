# ses: CreateReceiptRule's S3Action pre-flight refuses a bucket carrying the documented SES AllowSESPuts policy — InvalidS3Configuration 'Could not write to bucket: <BucketName>' for a destination SES accepts, because the authorization context omits aws:Referer

> _Note: this issue was identified against the code base at commit `c53162cdb93053ed8a8d23be086345dc123b2ab0`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateReceiptRule

## Description
One net-new root cause on the SES v1 (awsQuery) receipt-rule surface. The failing check is NOT marked ALREADY FILED or OWNED in the replay report. The open issue 20261027T223106Z-ses-7-net-new-behavioral-root-causes-in.md touches the same operation (its Cause 2 asked for the S3Action pre-flight to EXIST at all, where the emulator answered 200 for every S3Action), but it does not carry this failure: the pre-flight now exists and has moved from under-refusing to OVER-refusing, so the divergence and its replay signature are new (the check no longer fails on 'it SUCCEEDED', it fails on a refusal of the positive control).

Cause 1 of 1: the S3Action bucket-policy pre-flight refuses a bucket whose policy is exactly the grant AWS documents for SES email receiving, so no S3Action rule can be created at all.

AWS: Smithy (com.amazonaws.ses#SimpleEmailService, awsQuery) CreateReceiptRule declares InvalidS3ConfigurationException (awsQueryError code InvalidS3Configuration, httpResponseCode 400), documented 'Indicates that the provided Amazon S3 bucket or Amazon Web Services KMS encryption key is invalid, or that Amazon SES could not publish to the bucket, possibly due to permissions issues.' AWS refuses an S3Action ONLY when SES really cannot write the received message: recorded behavior is InvalidS3Configuration with message 'No such bucket: <BucketName>' for an absent bucket and 'Could not write to bucket: <BucketName>' for an existing bucket whose policy grants SES nothing (fixed sentence prefix plus the BucketName taken from the request's S3Action). A bucket that DOES carry the grant AWS documents at https://docs.aws.amazon.com/ses/latest/dg/receiving-email-permissions.html is accepted with HTTP 200 and an empty CreateReceiptRuleResponse, and the rule is persisted and readable through DescribeReceiptRuleSet. That documented grant is: Effect Allow, Principal {"Service": "ses.amazonaws.com"}, Action "s3:PutObject", Resource "arn:aws:s3:::<bucket>/*", Condition {"StringEquals": {"aws:Referer": "<account-id>"}} — i.e. AWS's own policy form conditions on aws:Referer carrying the account id, and SES supplies that key on the write it performs. (The newer documented form conditions on aws:SourceAccount/aws:SourceArn instead; both must be honoured, since AWS accepts a bucket granted either way.)

Emulator: the positive-control leg — a bucket created in the caller's account, tagged, and given exactly that AllowSESPuts policy through PutBucketPolicy immediately before the call — is refused: HTTP 400, Error.Code 'InvalidS3Configuration', Error.Message 'Could not write to bucket: <BucketName>' (replay: botocore.errorfactory.InvalidS3ConfigurationException: An error occurred (InvalidS3Configuration) when calling the CreateReceiptRule operation: Could not write to bucket: <bucket>; the bucket name in that message is the per-run name the check generated, which is the message's variable part). The refusal happens before anything is stored, so the rule is never created. Hypothesis (from the handler the refusal comes out of): the pre-flight builds its IAM request with only aws:SourceAccount and aws:SourceArn in the context and publishes only those two keys, so a statement whose Condition names any other key — notably the aws:Referer key AWS's own documented SES bucket policy uses — can never match, the decision is not Allowed, and the destination is reported unwritable. The same code path is shared by UpdateReceiptRule, so an update naming such a bucket is refused the same way.

Why: the whole S3Action class becomes unusable. A client that follows the SES documentation, publishes the documented AllowSESPuts bucket policy and then creates a receipt rule with an S3Action is told its correctly-granted bucket is unwritable, and cannot create the rule at all; worse, the refusal is byte-identical to the genuine 'bucket grants SES nothing' refusal, so the caller is sent to fix a policy that is already correct. A negative-class test suite also loses its contrast: with the positive control refused, 'rejects a missing bucket' is indistinguishable from 'rejects every S3Action'.

Fix: the S3Action bucket-authorization pre-flight shared by the CreateReceiptRule and UpdateReceiptRule handlers of the ses v1 crate — the authorization request it builds for principal ses.amazonaws.com must carry (and publish) the condition keys AWS's documented SES receiving policies use, including aws:Referer with the account id, alongside aws:SourceAccount/aws:SourceArn, so a bucket carrying either documented grant form evaluates to Allowed and the rule is persisted with HTTP 200. Only a destination that genuinely grants SES nothing may earn 'Could not write to bucket: <BucketName>'.

Traces: ses.create-receipt-rule-invalid-s3-bucket-fails (the check's positive control, before it ever gets to the missing-bucket leg). Code the refusal is emitted from: services/service-com-amazonaws-ses-simpleemailservice/src/ops/create_receipt_rule.rs lines 231-249 and services/service-com-amazonaws-ses-simpleemailservice/src/state/s3_action_authorization.rs lines 230-234 and 275-289.

## Evidence
Expected: CreateReceiptRule(RuleSetName=<set>, Rule={'Name':'s3-rule-control','Enabled':True,'Actions':[{'S3Action':{'BucketName':<bucket>}}]}) answers HTTP 200 with an empty CreateReceiptRuleResponse and the rule appears in DescribeReceiptRuleSet(RuleSetName=<set>)['Rules'], because the bucket exists in the caller's account and carries the documented AllowSESPuts policy (Allow / Principal Service ses.amazonaws.com / s3:PutObject / arn:aws:s3:::<bucket>/* / StringEquals aws:Referer = <account-id>) published a moment earlier.
Actual: HTTP 400 — Error.Code 'InvalidS3Configuration', Error.Message 'Could not write to bucket: <bucket>' (replay: "botocore.errorfactory.InvalidS3ConfigurationException: An error occurred (InvalidS3Configuration) when calling the CreateReceiptRule operation: Could not write to bucket: sim2real-behav-good-bucket-4ed14afc4777"). In that message 'Could not write to bucket: ' is the fixed text and the bucket name is the value from the request's S3Action.BucketName — the per-run suffix in the recording is not part of the requirement. The refusal is the same message AWS reserves for a bucket that grants SES nothing, so the two cases are indistinguishable. Nothing is persisted, and the check cannot reach its missing-bucket leg ('No such bucket: <ghost-bucket>') or its restore leg at all.

## Steps to Reproduce
1. Boot the emulator and point boto3 at it (clients 'ses', 's3', 'sts'; a receiving region such as us-east-1/us-west-2/eu-west-1).
2. account = sts.get_caller_identity()['Account'].
3. ses.create_receipt_rule_set(RuleSetName=RS).
4. s3.create_bucket(Bucket=B) (with CreateBucketConfiguration.LocationConstraint outside us-east-1), then s3.put_bucket_policy(Bucket=B, Policy=json.dumps({'Version':'2012-10-17','Statement':[{'Sid':'AllowSESPuts','Effect':'Allow','Principal':{'Service':'ses.amazonaws.com'},'Action':'s3:PutObject','Resource':f'arn:aws:s3:::{B}/*','Condition':{'StringEquals':{'aws:Referer':account}}}]})) — the policy AWS documents at ses/latest/dg/receiving-email-permissions.html.
5. ses.create_receipt_rule(RuleSetName=RS, Rule={'Name':'s3-rule-control','Enabled':True,'Actions':[{'S3Action':{'BucketName':B}}]}) — observe HTTP 400 InvalidS3Configuration 'Could not write to bucket: B' instead of HTTP 200, and the rule absent from ses.describe_receipt_rule_set(RuleSetName=RS)['Rules'].
6. Repeat step 5 against ses.update_receipt_rule for an existing rule — the same shared pre-flight refuses it.
7. Re-replay ses.create-receipt-rule-invalid-s3-bucket-fails to confirm the fix (its later legs must then exercise 'No such bucket: <ghost-bucket>' and the restore-and-retry success).
