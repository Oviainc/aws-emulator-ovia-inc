# ecs: 4 net-new causes — EC2-launched hosts never become ACTIVE agent-connected container instances, an in-use capacity provider can be detached, CreateCapacityProvider's out-of-range targetCapacity is refused with the wrong error class, and UpdateCapacityProvider is a 501 stub under concurrency

> _Note: this issue was identified against the code base at commit `e3ea9c3d18c5ac215ea88ebad8a0c22355767e25`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
RegisterContainerInstance

## Description
Four independent root causes in the ECS surface, every one grounded in a failing check the suite lists under `### ecs` and none of them marked ALREADY FILED or OWNED by an open issue. All four must be closed before submitting.

Cause 1 of 4: an EC2 instance launched with an ECS-capable instance profile and the standard `echo ECS_CLUSTER=<cluster> >> /etc/ecs/ecs.config` user data never appears as an ACTIVE, agent-connected ECS container instance, so every scenario that needs real EC2 capacity burns its whole budget without reaching a verdict.
  AWS: RunInstances with an ECS-enabled AMI/instance profile and `ECS_CLUSTER` user data causes the ECS agent to call RegisterContainerInstance; ListContainerInstances/DescribeContainerInstances then report that instance with `status: ACTIVE` and `agentConnected: true`, and its `registeredResources`/`remainingResources` (CPU, MEMORY, PORTS) are what the scheduler places against. Smithy (com.amazonaws.ecs#AmazonEC2ContainerServiceV20141113): RegisterContainerInstance input {cluster, instanceIdentityDocument, instanceIdentityDocumentSignature, totalResources, versionInfo, containerInstanceArn, attributes, platformDevices, tags} -> output {containerInstance: ContainerInstance}, errors ClientException/ClusterNotFoundException/InvalidParameterException at 400, AccessDeniedException at 403, ServerException at 500; DeregisterContainerInstance, UpdateContainerInstancesState, StartTask (input requires `containerInstances`), DiscoverPollEndpoint and PutAttributes (TargetNotFoundException/AttributeLimitExceededException at 400) are all defined only over such a registered instance. The model states the shapes, not the timing; the timing is recorded behavior only — in the recording an instance reaches ACTIVE with its agent connected in roughly 25-60s, well inside every check's budget.
  Emulator: the instance never registers. Checks that poll explicitly report it (`TimeoutError: EC2 instance i-... registers as an ACTIVE ECS container instance: the run budget ended first; not graded`, `TimeoutError: EC2 instances [...] register as ACTIVE, connected container instances: the run budget ended first; not graded`); the rest are cut mid-poll with `Error: Check timed out after 180.0s` (or 60.0s) because the first thing their body waits on is that registration. The instance ids in those messages are per-run values; the never-registering behaviour is the divergence.
  Why: the whole ECS-on-EC2 plane is unusable and unfalsifiable for a client. Nothing that is scoped to a container instance can be exercised or refused: StartTask onto named instances and its partial-failure reporting, DeregisterContainerInstance's force requirement, UpdateContainerInstancesState's DRAINING/invalid-status handling, DiscoverPollEndpoint's registered-instance requirement, PutAttributes' per-target attribute limit, the agent-side SubmitTaskStateChange ordering rules, and every EC2 placement rule (binpack vs spread, distinctInstance, memberOf over a custom attribute, dynamic host-port mapping, relocation off a DRAINING instance). A client gets neither success nor an error — the call simply never converges.
  Fix: whatever stands an emulator-launched EC2 instance up as an ECS agent host, plus the ECS `register_container_instance` handler and the container-instance records in `crate::state` the reads above are served from (an instance launched into a cluster must become an ACTIVE, agentConnected container instance with registered/remaining resources, and the scheduler must place against it).
  Related open issues, neither of which carries any of these checks' replay keys: 20261107T220512Z-ecs-5-net-new-causes-no-obtainable-ec2.md (its cause 1 is the same plane, keyed on explicit `identity-fetch EC2 instance never registered Online with SSM` AssertionErrors from a different set of checks) and 20261107T080429Z-ecs-2-net-new-causes-no-aws-signed.md. Closing either without replaying the ids below leaves these sixteen checks unrun.
  Failing check ids: ecs.concurrent-container-instance-state-update, ecs.container-instance-register-state-deregister, ecs.container-state-change-sequencing, ecs.deep-ecs-2-ec2place-binpack-colocates-while-spread-separates, ecs.deep-ecs-2-ec2place-bridge-dynamic-host-port-serves-sibling-and-fixed-port-collision-rejected, ecs.deep-ecs-2-ec2place-distinct-instance-third-task-on-two-hosts-rejected, ecs.deep-ecs-2-ec2place-draining-instance-relocates-service-task-to-other-host, ecs.deregister-container-instance-requires-force, ecs.placement-constraint-memberof-attribute-filters-candidate-instances, ecs.poll-endpoint-requires-registered-instance, ecs.put-attributes-exceeding-limit-rejected, ecs.start-task-batch-partial-failure, ecs.task-state-change-ordering-enforced, ecs.task-state-change-sequencing, ecs.update-container-instance-invalid-status-fails, ecs.update-container-instances-state-unknown.

Cause 2 of 4: PutClusterCapacityProviders SUCCEEDS when it detaches a capacity provider an ACTIVE service still uses, instead of refusing with ResourceInUseException.
  AWS: PutClusterCapacityProviders replaces a cluster's whole capacityProviders list and defaultCapacityProviderStrategy; a call that removes a provider still referenced by an ACTIVE service is refused with HTTP 400 and error code ResourceInUseException (Smithy: PutClusterCapacityProviders models ResourceInUseException at httpError 400 alongside ClientException/ClusterNotFoundException/InvalidParameterException/UpdateInProgressException; ResourceInUseException is documented "The specified resource is in-use and can't be removed."), and the cluster's capacityProviders list is left unchanged. Recorded behavior for the message: the whole message is AWS's fixed sentence `The specified capacity provider is in use and cannot be removed.` with no value from the request in it. Once the dependent service is deleted and INACTIVE, the identical call is accepted and the list becomes empty.
  Emulator: the detach returns HTTP 200 with the cluster payload (`attachmentsStatus: UPDATE_IN_PROGRESS`, `capacityProviders: []`, `activeServicesCount: 1`) — `AssertionError: expected the call to be rejected, but it SUCCEEDED and returned {...}`. The provider is removed from the cluster while a service that uses it is still ACTIVE; no error code and no message are produced. (The cluster ARN/name and timestamps in that payload are per-run values.)
  Why: a client that relies on ECS refusing to strand a running service's capacity source gets a silent, destructive success; the cluster's capacity-provider list and its services disagree, and the negative test for the in-use conflict is indistinguishable from the positive detach.
  Fix: the PutClusterCapacityProviders handler's validation — before replacing the association, reject with ResourceInUseException (and leave the stored cluster association untouched) when any provider being removed is still named by a non-INACTIVE service's capacityProviderStrategy or by the cluster's default strategy in use.
  Failing check id: ecs.put-cluster-capacity-providers-detach-in-use-conflict.

Cause 3 of 4: CreateCapacityProvider with an out-of-range managedScaling.targetCapacity is refused with the wrong error class and message.
  AWS: `autoScalingGroupProvider.managedScaling.targetCapacity` is constrained to 1-100 (Smithy: ManagedScaling.targetCapacity -> ManagedScalingTargetCapacity, @range min 1 max 100, documented "The specified value must be greater than 0 and less than or equal to 100"), and a value outside it is refused with HTTP 400, error code ClientException (modeled on CreateCapacityProvider at httpError 400). Recorded behavior for the message: the whole message is AWS's fixed sentence `The managed scaling target capacity value is invalid. Specify an integer greater than 0 and less than or equal to 100 and try again.` — there is no value from the request in it. Nothing is created: DescribeCapacityProviders for that name returns an empty list.
  Emulator: the same call is refused with error code `InvalidParameterException` instead — `AssertionError: expected a rejection for targetCapacity=150 (outside the documented 1-100 range), got InvalidParameterException`. The refusal happens, but under the wrong error class (the message was not reached by the check, so only the code is established as diverging).
  Why: both codes are 400 client errors but they are distinct SDK exception types; a client that catches ClientException (or branches on `Error.Code == "ClientException"` to tell "this request is structurally wrong" from "this parameter value is wrong") does not catch this refusal at all and surfaces an unhandled error.
  Fix: the CreateCapacityProvider handler's managed-scaling validation — raise ClientException with AWS's fixed target-capacity sentence for an out-of-range targetCapacity, keeping InvalidParameterException for the parameter classes AWS uses it for.
  Failing check id: ecs.capacity-provider-managed-scaling-enforced.

Cause 4 of 4: UpdateCapacityProvider answers HTTP 501 `NotImplemented`, so no concurrent-update semantics exist at all.
  AWS: UpdateCapacityProvider returns HTTP 200 with the updated `capacityProvider` (Smithy: input {name (required), cluster, autoScalingGroupProvider: AutoScalingGroupProviderUpdate, managedInstancesProvider}; output {capacityProvider}; modeled errors AccessDeniedException 403, ClientException/ClusterNotFoundException/InvalidParameterException/UnsupportedFeatureException 400, ServerException 500). ECS serializes mutations on one provider: of two concurrent UpdateCapacityProvider calls setting different targetCapacity values at least ONE returns 200 and the settled state equals exactly one of the racing values; and when PutClusterCapacityProviders races UpdateCapacityProvider on the same provider a losing racer fails only with a real contention code (ClientException or UpdateInProgressException, both modeled at 400) — never with a server-class code. Recorded behavior for which racer wins; the model gives the shapes and the error set.
  Emulator: every call answers error code `NotImplemented` (HTTP 501) regardless of input — `AssertionError: expected at least one of the two racing updates to succeed, got codes ['NotImplemented', 'NotImplemented']` and `AssertionError: expected a losing racer (if any) to fail with a real contention code, got NotImplemented`.
  Why: a capacity provider is immutable in the emulator, and a 501 flips SDK error classification from client to server, so a client's retry/contention handling takes the server-error branch and retries a call that can never succeed.
  Fix: implement the operation in its own handler, `services/service-com-amazonaws-ecs-amazonec2containerservicev20141113/src/ops/update_capacity_provider.rs` (resolve the named provider, apply the update onto the stored provider record in `crate::state`, return the updated provider) and serialize it against PutClusterCapacityProviders on the same provider so a losing racer gets UpdateInProgressException/ClientException. Two existing issues name this operation but NEITHER carries these two checks' replay keys, so neither owns them: the auto-filed scaffold-stub issue for `update_capacity_provider.rs` (reported in this run against ecs.capacity-provider-create-update-delete-lifecycle) and the open 20261108T150857Z-ecs-2-net-new-causes-updatecapacityprovider-is-a.md (keyed on ecs.capacity-provider-ops-on-missing-cluster-not-found). Fixing the stub will very likely close this cause too — replay both ids below to confirm.
  Failing check ids: ecs.concurrent-capacity-provider-association, ecs.concurrent-capacity-provider-update-contention.
