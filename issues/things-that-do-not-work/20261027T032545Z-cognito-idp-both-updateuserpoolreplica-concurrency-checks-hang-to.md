# cognito-idp: both UpdateUserPoolReplica concurrency checks hang to the 60 s cap because CreateUserPoolReplica answers 501 NotImplemented inside the checks' retry loop (1 cause)

> _Note: this issue was identified against the code base at commit `4e0be56b24c0fc13c424c1a1b18bb5f0120957ed`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateUserPoolReplica

## Description
Cause 1 of 1: CreateUserPoolReplica is an unimplemented scaffold that answers 501 NotImplemented, and because both multi-Region replica CONCURRENCY checks call it inside a bounded retry loop rather than once, the refusal is swallowed and each check burns its whole budget retrying, hanging to the 60 s harness cap instead of surfacing the refusal.
  AWS: Smithy: CreateUserPoolReplica(UserPoolId required, pattern ^[\\w-]+_[0-9a-zA-Z]+$, RegionName required @length 5..32, optional UserPoolTags) -> CreateUserPoolReplicaResponse{UserPoolReplica: UserPoolReplicaType}; its modeled errors are FeatureUnavailableInTierException (403), InvalidParameterException (400), LimitExceededException (400), NotAuthorizedException (403), OperationNotEnabledException (400), ResourceNotFoundException (404), TooManyRequestsException (429), UserPoolTaggingException (400) and InternalErrorException (500) — NotImplemented is not among them and 501 is not a modeled status. On a user pool on the Essentials/Plus feature plan whose KeyConfiguration names a multi-Region customer managed key, the call creates a secondary replica which ListUserPoolReplicas then reports (initially Status CREATING, settling to ACTIVE/INACTIVE), after which UpdateUserPoolReplica (Smithy: UserPoolId, RegionName and Status all required, Status target UpdateReplicaStatusType; no conflict error is modeled) flips it.
  Emulator: every CreateUserPoolReplica call returns HTTP 501 with code NotImplemented and message "operation CreateUserPoolReplica is scaffolded but not implemented in this emulator", and persists nothing — so ListUserPoolReplicas never reports a secondary replica and UpdateUserPoolReplica can never be exercised. Both checks wrap the call in a poll (timeout 120 s, interval 5 s) that treats any ClientError as "not ready yet" and retries, so the 501 is never raised; the harness kills each check at 60 s with "Check timed out after 60.0s" and the NotImplemented never appears in the verdict.
  Why: a client provisioning a multi-Region user pool gets an unmodeled 501 its SDK cannot classify as either retryable-throttling or a permanent configuration error, and a client that (correctly) treats the call as eventually-consistent and retries it hangs forever instead of failing. Downstream, the whole replica lifecycle — ListUserPoolReplicas, UpdateUserPoolReplica's last-write-wins resolution of concurrent ACTIVE/INACTIVE flips, each racer's own response echoing the status it requested, status stability across immediately-repeated reads, and DeleteUserPoolReplica/DeleteUserPool refusing while a secondary replica is still listed — is unobservable.
  Fix: the CreateUserPoolReplica handler (services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/ops/create_user_pool_replica.rs) must replace its scaffold refusal with a real handler that records the replica in the service's user-pool state, and the UpdateUserPoolReplica handler must resolve two concurrent status writes on the same (UserPoolId, RegionName) deterministically — each response echoing its own requested Status, the stored status settling on exactly one of the two requested values, never a stuck CREATING/DELETING and never flapping across repeated ListUserPoolReplicas reads.
  Traces: cognito-idp.update-user-pool-replica-concurrent-modification-race, cognito-idp.update-user-pool-replica-concurrent-updates-serialized.

Not covered by an existing issue. 20261026T235252Z-cognito-idp-createuserpoolreplica-stub.md reports the same stub, but its Issue-Trace-Ids carry only cognito-idp.update-user-pool-replica-immutable-field-change-rejected, cognito-idp.update-user-pool-replica-reflects-region-config-change and cognito-idp.user-pool-replica-update-propagates-to-describe — all of which fail on the refusal directly. The two concurrency checks named here are NOT in that list, their verdict is a 60 s timeout rather than a NotImplemented, and they additionally assert the concurrent-write resolution of UpdateUserPoolReplica, which no filed issue states. Whoever implements the stub must re-replay these two keys as well.

## Evidence

The check provisions a multi-Region CMK (kms CreateKey MultiRegion=true + ReplicateKey) and a PLUS-tier pool with KeyConfiguration KeyType=CUSTOMER_MANAGED_KEY, then calls `_poll_until(_try_create_replica, lambda r: r[0], timeout_s=120.0, interval_s=5.0)` where `_try_create_replica` returns (False, exc.response["Error"]["Code"]) on any ClientError. Actual: CreateUserPoolReplica answers 501 NotImplemented ("operation CreateUserPoolReplica is scaffolded but not implemented in this emulator") on every attempt, so the predicate is never satisfied and the harness cap fires at 60 s before the loop's own 120 s diagnostic ("CreateUserPoolReplica did not succeed within the polling window ... NotImplemented") can be raised.

Report lines 20366-20611 — [mismatch] cognito-idp.update-user-pool-replica-concurrent-updates-serialized, "Error: Check timed out after 60.0s". Same structure with an ESSENTIALS-tier pool: `_poll_until(try_create_replica, ..., timeout_s=120, interval_s=5)` on CreateUserPoolReplica, then a 600 s wait for the replica to leave CREATING via ListUserPoolReplicas, then two concurrent UpdateUserPoolReplica calls asserting result_active["UserPoolReplica"]["Status"] == "ACTIVE", result_inactive["UserPoolReplica"]["Status"] == "INACTIVE", a final status in (ACTIVE, INACTIVE) and three stable re-reads. Corroboration from the same replay: cognito-idp.update-user-pool-replica-immutable-field-change-rejected, which calls CreateUserPoolReplica once rather than in a loop, surfaces the refusal directly as "AssertionError: CreateUserPoolReplica with a valid secondary region and a correctly provisioned multi-Region CMK failed with NotImplemented; cannot exercise UpdateUserPoolReplica without a real replica." — the same root cause, visible because no retry loop hid it.

## Steps to Reproduce
1. Boot the emulator (cognito-idp and kms both answer).
2. kms CreateKey with MultiRegion=true and a key policy that grants the account root kms:* plus cognito-idp.amazonaws.com and identitystore.amazonaws.com the actions kms:Encrypt, kms:Decrypt, kms:ReEncrypt*, kms:GenerateDataKeyWithoutPlainText and kms:DescribeKey; then kms ReplicateKey into a second Region with the same policy.
3. cognito-idp CreateUserPool with UserPoolTier=ESSENTIALS (or PLUS) and KeyConfiguration={KeyType: CUSTOMER_MANAGED_KEY, KmsKeyArn: <multi-Region key ARN>}.
4. Call CreateUserPoolReplica(UserPoolId=<poolId>, RegionName=<secondary region>). Observe HTTP 501 / code NotImplemented / message "operation CreateUserPoolReplica is scaffolded but not implemented in this emulator", instead of a 200 carrying UserPoolReplica. Call ListUserPoolReplicas(UserPoolId=<poolId>) and observe no secondary replica was persisted.
5. Retry step 4 on a 5 s interval the way the checks do: every attempt returns the same 501, so the loop runs to its 120 s budget and the check is killed at the 60 s harness cap with "Check timed out after 60.0s".
6. After CreateUserPoolReplica is implemented, wait for the replica to leave CREATING, then issue two concurrent UpdateUserPoolReplica calls on the same (UserPoolId, RegionName) — one with Status=ACTIVE, one with Status=INACTIVE. Each response must echo the Status it requested, both must complete without a conflict error (none is modeled), and repeated ListUserPoolReplicas reads must all report the same settled ACTIVE or INACTIVE value.
