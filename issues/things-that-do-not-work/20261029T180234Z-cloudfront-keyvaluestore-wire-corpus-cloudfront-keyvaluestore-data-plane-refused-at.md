# Wire corpus: cloudfront-keyvaluestore data plane refused at auth - 8 read and list divergences answer unmodeled 403 AccessDenied

> _Note: this issue was identified against the code base at commit `a1be48b455f77208774c140f08575194e8ab84c8`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeKeyValueStore

## Description
Every CloudFront KeyValueStore data-plane request in the wire corpus is rejected by the emulator's authentication layer before the operation runs: HTTP 403 with body {"__type": "AccessDenied", "message": "Sign the request with the emulator credentials"} and response header x-amzn-errortype: AccessDenied. The refusal replaces both the success responses and the modeled refusals the corpus records, so neither the happy path nor the error path of the service is observable. This issue bundles EIGHT causes (eight distinct divergence clusters, each a different operation/expected-status surface) and ALL EIGHT must be closed before submitting: the shared auth fix unblocks them, but each cause then needs its own handler/serializer/state behavior to be correct, and the replay keys for all eight are listed under Traces.

Shared AWS baseline (Smithy, services/service-com-amazonaws-cloudfrontkeyvaluestore-cloudfrontkeyvaluestore): service CloudFrontKeyValueStore, sdkId "CloudFront KeyValueStore", protocol restJson1, sigv4Name cloudfront-keyvaluestore, authSchemes [sigv4] with the endpoint ruleset overriding to sigv4a. Every operation's modeled client-side 403 is the shape AccessDeniedException; the bare code `AccessDenied` is modeled nowhere in this service, and the message "Sign the request with the emulator credentials" is emulator-authored text AWS never emits for any error class. Where AWS does deny by identity it returns AccessDeniedException whose message is the IAM sentence - fixed text "User: ", " is not authorized to perform: ", " on resource: " with the caller principal ARN, the action (cloudfront-keyvaluestore:<Action>) and the KvsARN taken from the request and the emulator's IAM state, plus " with an explicit deny in an identity-based policy" when an explicit Deny matched. Where it rejects a signature it returns a signature error (InvalidSignatureException), still not `AccessDenied`. Hypothesis (neither the model nor the recording states the mechanism): the SDK signs this service with sigv4a (AWS4-ECDSA-P256-SHA256 plus X-Amz-Region-Set) and the emulator's credential check only accepts AWS4-HMAC-SHA256 bearing its own access key, so it treats every signed request as unsigned.

Cause 1 of 8: DescribeKeyValueStore on an existing, provisioned store must answer 200. AWS: GET /key-value-stores/{KvsARN}, success code 200, output requires ItemCount, TotalSizeInBytes, KvsARN, Created and the `ETag` httpHeader, with optional LastModified/Status/FailureReason; a freshly created store reports Status "READY" with ItemCount 0 and TotalSizeInBytes 0. Emulator: 403 AccessDeniedwith no modeled member and no ETag header, so the fixture's poll for Status == READY never terminates (61 attempts, 60s cap). Why: a client can neither confirm the store is usable nor obtain the ETag that every conditional write (PutKey/UpdateKeys/DeleteKey If-Match, all required) is built from, so the whole KVS workflow is unreachable. Fix: the front door's SigV4/SigV4a credential verification for the cloudfrontkeyvaluestore crate, then the DescribeKeyValueStore handler, its restJson1 serializer (including the required ETag response header) and the store lifecycle/state it reads. Traces: cloudfront-keyvaluestore-absent-store-error-precedence#task#2.

Cause 2 of 8: DescribeKeyValueStore against a store ARN that does not exist must answer the modeled 404. AWS: ResourceNotFoundException, httpError 404, with a single Message member; the recording shows the message "No such Key-Value-Store exists" - fixed text, no variable part. Emulator: 403 with x-amzn-errortype AccessDenied and no Message. Why: not-found is indistinguishable from an auth failure, so a client's create-or-repair path never triggers and an unmodeled code is retried as an infrastructure fault. Fix: as cause 1, then DescribeKeyValueStore's store lookup and the ResourceNotFoundException mapping. Traces: cloudfront-keyvaluestore-absent-store-error-precedence#task#3. NOTE: the open issue 20261023T150809Z-cloudfront-keyvaluestore-keyvaluestore-refusals-answer-unknownservice-instead-of-resourcenotfoundexception-and.md describes this same surface keyed to the earlier 404/UnknownService refusal; the replay reports this cluster as unowned, so it is filed here against the current 403/AccessDenied behavior.

Cause 3 of 8: GetKey against an absent store must answer the store-level 404, not a key-level outcome (error precedence). AWS: GET /key-value-stores/{KvsARN}/keys/{Key}, modeled ResourceNotFoundException httpError 404; the store is resolved before the key, and the recorded message is "No such Key-Value-Store exists". Emulator: 403 AccessDenied, no Message. Why: a reader cannot tell the store is gone, so it retries a key read against a resource that will never exist. Fix: as cause 1, then GetKey's lookup order (store before key) and its error mapping. Traces: cloudfront-keyvaluestore-absent-store-error-precedence#task#4 (cluster also covers absent-store-error-precedence#task#8, put-get-describe-etag-chain#task#8, stale-etag-conflict-exact-message-then-retry-succeeds#task#5 and #task#10, update-keys-batch-validation-exact-messages#task#4, update-keys-combined-atomic-batch-and-delete-of-never-written-key#task#6 and #task#10).
