# apigatewayv2: a deployed WEBSOCKET stage never completes the RFC 6455 upgrade, so a Lambda @connections broadcast never reaches any connection (1 cause)

> _Note: this issue was identified against the code base at commit `49d4e81f9c14b9ea7dd829b0faa6f7c6d506b5c4`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
Invoke (execute-api WebSocket data plane), PostToConnection

## Description
One net-new root cause in the apigatewayv2 emulator, grounded in a failing behavioral check of this suite whose replay key is carried by no open issue. A fixer must close this ONE cause before submitting.

=== Cause 1 of 1: the execute-api WEBSOCKET data plane accepts no upgrade, so a server-side fan-out over @connections to several live sockets is unobservable ===
AWS: recorded behavior only for the handshake, route selection and frame delivery (the execute-api data plane is not modeled in Smithy). After apigatewayv2 CreateApi(ProtocolType=WEBSOCKET, RouteSelectionExpression="$request.body.action") + CreateIntegration(IntegrationType=AWS_PROXY, IntegrationMethod=POST, IntegrationUri=<function arn>) + CreateRoute(RouteKey="$default", RouteResponseSelectionExpression="$default") + CreateRouteResponse(RouteResponseKey="$default") + CreateStage + CreateDeployment reaching DeploymentStatus=DEPLOYED, an RFC 6455 upgrade (GET with Connection: Upgrade, Upgrade: websocket, Sec-WebSocket-Key, Sec-WebSocket-Version: 13) to that stage's announced wss:// URL is answered HTTP 101 Switching Protocols. Each accepted socket is given its OWN server-minted connectionId, delivered to the integration in requestContext.connectionId alongside requestContext.domainName and requestContext.stage; two independent sockets must carry two distinct ids. A text frame routed to the integration whose handler returns {statusCode:200, body:...} is answered on the SAME socket because the route has a RouteResponse. The push side IS modeled: Smithy apigatewaymanagementapi PostToConnection POST /@connections/{ConnectionId}, response code 200, member Data @httpPayload blob @required @length min 0 max 131072, errors ForbiddenException (httpError 403), GoneException (410), LimitExceededException (429), PayloadTooLargeException (413). A PostToConnection naming a live connectionId answers 200 and delivers exactly the posted bytes as one text frame to THAT connection's socket — including to connections other than the one whose message triggered the handler, which is what makes a broadcast possible. A client close frame (opcode 0x8, status 1000) is answered by the server with a close frame (opcode 0x8).
Emulator: nothing ever accepts a WebSocket connection at the stage URL the emulator itself announced. The check polls the upgrade for up to 120 s at 3 s intervals and never observes status 101, so the runner kills it at the suite cap: "Error: Check timed out after 60.0s" (verdict mismatch). Because no handshake completes, no connectionId is ever minted, so none of the downstream contract is reachable: the two sockets' distinct ids, the $default route dispatch that answers 'whoami' on the sender's own socket, the Lambda's PostToConnection fan-out to a list of target ids, the byte-exact arrival of the same payload on a NON-sender socket, and the server's close-frame echo.
Why: a client writing any realtime fan-out application (chat, presence, notification push) gets a control plane that bookkeeps the API, route, integration, route response, stage and a DEPLOYED deployment, and an ApiEndpoint that looks like a wss:// URL, yet no socket can be opened against it and no server-initiated push can ever be observed. The multi-connection case is strictly worse than the single-socket case: even code that avoids echoing on the request socket and pushes only through @connections cannot be exercised at all, so an application verified against this emulator fails on AWS.
Fix: the execute-api WebSocket listener for a WEBSOCKET stage — the upgrade handler and the front-door router entry that maps the announced host/path for (api id, stage) onto it — plus the per-connection registry it must populate so the apigatewaymanagementapi PostToConnection handler can resolve an arbitrary live connectionId (not just the caller's) and write the posted bytes to that connection's socket. Related open issues describe the same unservable surface but do NOT carry this check's replay key: 20261025T023548Z-apigatewayv2-websocket-stage-never-completes-the-rfc-6455.md (single-socket route dispatch, push and post-close 410), 20261104T160000Z-apigatewayv2-websocket-execute-api-upgrade-remains-unservable.md, 20261023T124140Z-apigatewayv2-websocket-duplex-data-plane-is-not-served.md and 20261029T192401Z-apigatewayv2-a-websocket-two-way-route-s-routeresponse.md. This cause adds the MULTI-connection fan-out leg: distinct ids across concurrent sockets and delivery to a connection that did not send the triggering frame.
Traces: apigatewayv2.websocket-broadcast-to-multiple-connections.

## Evidence
Check apigatewayv2.websocket-broadcast-to-multiple-connections, verdict mismatch.
Expected: `_poll_until(lambda: _ws_connect(url), lambda r: r["status"] == 101, timeout_s=120.0, interval_s=3.0, description=f"a 101 WebSocket upgrade at {url}")` observes HTTP 101 on ctx.api_url(api_id, 's', websocket=True) for TWO independent sockets; each socket's {"action":"whoami"} frame is answered on that same socket with an opcode-1 frame carrying a non-empty connectionId, and the two ids differ (`assert cid1 != cid2`); then one socket sends {"action":"broadcast","targets":[cid1,cid2],"message":<marker>} and the integration's two PostToConnection calls (Data=<marker> bytes) each answer 200 and deliver an opcode-1 frame equal to <marker> to BOTH sockets, including the non-sender (`assert payload2 == marker.encode()`); finally each client close frame (opcode 8, status 1000) is answered with an opcode-8 close frame.
Actual: no upgrade is ever accepted at the announced stage URL, so the check never gets past the handshake poll and is killed by the runner: `Error: Check timed out after 60.0s`. No HTTP status, error code or error message is produced on the upgrade at all — the socket poll simply never yields 101, so the whole fan-out contract is ungradeable.
Model citations used: apigatewaymanagementapi PostToConnection POST /@connections/{ConnectionId} code 200, Data @httpPayload @required @length 0..131072, errors ForbiddenException 403 / GoneException 410 / LimitExceededException 429 / PayloadTooLargeException 413. The handshake, connectionId minting, route selection and close echo are recorded behavior only. The marker string, generated function/role/api names and the stage name are per-run values, not part of the requirement.

## Steps to Reproduce
1. Boot the emulator from this checkout and point an SDK/CLI at it.
2. Create an IAM role assumable by lambda.amazonaws.com with execute-api:ManageConnections, and a python3.12 Lambda whose handler answers {"action":"whoami"} with its own requestContext.connectionId and, for {"action":"broadcast"}, builds an apigatewaymanagementapi client at https://<requestContext.domainName>/<requestContext.stage> and calls PostToConnection for every id in the request's targets list. Wait for State=Active.
3. apigatewayv2 CreateApi(ProtocolType='WEBSOCKET', RouteSelectionExpression='$request.body.action'); lambda AddPermission for apigateway.amazonaws.com on arn:aws:execute-api:<region>:<account>:<apiId>/*/*.
4. CreateIntegration(IntegrationType='AWS_PROXY', IntegrationMethod='POST', IntegrationUri=<fn arn>); CreateRoute(RouteKey='$default', Target='integrations/<id>', RouteResponseSelectionExpression='$default'); CreateRouteResponse(RouteResponseKey='$default'); CreateStage(StageName='s'); CreateDeployment(StageName='s') and wait for DeploymentStatus=DEPLOYED.
5. Open TWO RFC 6455 upgrades against the emulator's announced WebSocket URL for (that api id, stage 's'). Neither returns 101 — nothing accepts the connection, so no connectionId is minted.
6. Consequently none of the following can be reached: two distinct connection ids learned via 'whoami' on each socket; the broadcast frame on socket 1 triggering PostToConnection to both ids; the identical marker payload arriving as an opcode-1 frame on socket 2 (the non-sender); and the server's close-frame echo for each client close.
7. Replay apigatewayv2.websocket-broadcast-to-multiple-connections to confirm the fix.
