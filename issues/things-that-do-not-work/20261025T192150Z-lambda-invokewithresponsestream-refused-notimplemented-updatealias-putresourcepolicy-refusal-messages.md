# lambda: InvokeWithResponseStream refused NotImplemented, UpdateAlias/PutResourcePolicy refusal messages diverge, DeleteEventSourceMapping accepted mid-Updating, and SQS ESM delivery never happens (5 causes)

> _Note: this issue was identified against the code base at commit `029c92a6d753af7d483a2e508209908fa6f0a80e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeWithResponseStream

## Description
This issue bundles 5 NET-NEW root causes in the lambda service. Causes are numbered Cause 1 of 5 .. Cause 5 of 5; each carries its own failing check ids and each must be closed before this issue is submitted. Three of the fifteen grounding checks are cross-service (their check ids lead with the composite tokens dynamodb__lambda__sqs and lambda__sfn__sqs, which match no single service token); the diverging component in every one of them is Lambda's event-source-mapping poller, so they are filed here under service 'lambda', which is bootstrapped, so the per-service gate is FILE.

=== Cause 1 of 5: InvokeWithResponseStream refuses every real streaming invocation with NotImplemented instead of streaming the function's response. ===
AWS: Smithy (lambda) InvokeWithResponseStream — POST /2021-11-15/functions/{FunctionName}/response-streaming-invocations, success code 200. Output InvokeWithResponseStreamResponse carries StatusCode (httpResponseCode), ExecutedVersion (header X-Amz-Executed-Version, e.g. $LATEST), ResponseStreamContentType (header Content-Type) and EventStream (httpPayload, @streaming union InvokeWithResponseStreamResponseEvent) — i.e. PayloadChunk frames as the handler writes them, then an InvokeComplete frame that carries ErrorCode/ErrorDetails only when the handler itself failed, plus LogResult. The modeled error set is the Invoke family (InvalidRequestContentException 400, InvalidParameterValueException 400, ResourceNotFoundException 404, RequestTooLargeException 413, TooManyRequestsException 429, ServiceException 500, and the 502 EC2/ENI/KMS/runtime family: EC2AccessDeniedException, EC2ThrottledException, EC2UnexpectedException, ENILimitReachedException, InvalidRuntimeException, KMS*Exception, ResourceNotReadyException, …). NotImplemented is NOT a modeled error: a function that exists and is Active is executed and its bytes are streamed back.
Emulator: the call is refused with error code 'NotImplemented' and the message 'InvokeWithResponseStream resolved <function ARN> at version <qualifier>, but running its <runtime> deployment package is not implemented in this emulator: there is no in-process runtime for it, so no response chunk, trailer error code or log tail is streamed that the function did not produce. InvocationType=DryRun validates an invocation without running the function.' The fixed text is everything outside the angle brackets; the function ARN, the resolved version and the runtime identifier come from the request and the emulator's own state (observed with nodejs20.x, nodejs22.x and python3.12). Control-plane resolution clearly works (the ARN and $LATEST are resolved and named) — only execution/streaming is absent.
Why: no client can observe anything that streaming exists for. Time-to-first-byte is unobservable (a chunk never arrives before the handler returns), the chunk boundaries that map onto the handler's writes never exist, a handler that throws after the first chunk can never be distinguished from a service refusal because the trailer ErrorCode/ErrorDetails never arrive, and a provisioned-concurrency streaming invocation can never be shown to run from a prewarmed environment. Every one of these is a documented, load-bearing property of response streaming.
Fix: the InvokeWithResponseStream handler's execution and event-stream framing path (an in-process/sandboxed runtime for the deployment package, PayloadChunk framing, and the terminal InvokeComplete frame carrying ErrorCode/ErrorDetails/LogResult), plus its error mapping, which must never answer NotImplemented for a function that resolved. What already works and must be preserved: InvocationType=DryRun validation without running the function. NOTE: open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md covers the synchronous Invoke operation (its Issue-Key is lambda|Invoke|NotImplemented) and does NOT cover InvokeWithResponseStream, which is a separate operation with its own URI, output shape, event-stream framing and trailer semantics.
Traces: lambda.deep-lambda-runtime-truth-stream-error-after-first-chunk-rejected-in-trailer, lambda.deep-lambda-runtime-truth-stream-first-chunk-reaches-client-before-handler-finishes, lambda.invoke-with-response-stream-ec2-errors, lambda.stream-handler-throw-delivers-no-bytes-and-no-error-code, lambda.stream-provisioned-streaming-function-streams-from-prewarmed-environment, lambda.stream-response-chunks-map-onto-handler-writes.

=== Cause 2 of 5: UpdateAlias on an absent/deleted alias returns GetAlias's not-found message instead of its own. ===
AWS: Smithy (lambda) UpdateAlias — PUT /2015-03-31/functions/{FunctionName}/aliases/{Name}, modeled errors include ResourceNotFoundException (httpError 404). Recorded behavior only for the exact text: the message is 'Alias not found: <aliasArn>'. 'Alias not found: ' is the fixed text; <aliasArn> is a value derived from the request and state — arn:aws:lambda:<region>:<account-id>:function:<function-name>:<alias-name>. This is deliberately NOT the wording GetAlias uses for the same vanished alias, which is 'Cannot find alias arn: <aliasArn>'; the two operations have distinct messages and the emulator already produces the GetAlias one correctly (the GetAlias assertion in lambda.alias-lifecycle-full passes).
Emulator: UpdateAlias on a deleted alias correctly returns code ResourceNotFoundException but reuses the GetAlias wording: 'Cannot find alias arn: arn:aws:lambda:us-west-2:000000000000:function:<fn>:<alias>'. (The region, account, function and alias in that string are per-run values filling the template; the defect is the fixed prefix 'Cannot find alias arn: ' where AWS says 'Alias not found: '.)
Why: clients and tooling that branch on, log or assert the refusal text for a mutation against a vacated alias id get a message AWS never emits for UpdateAlias, and cannot tell a failed read apart from a failed write. Any consumer matching AWS's documented UpdateAlias message mis-handles the refusal.
Fix: the UpdateAlias handler's not-found path in the lambda service — it must emit its own message template rather than delegating to the GetAlias lookup's message.
Traces: lambda.alias-lifecycle, lambda.alias-lifecycle-full, lambda.update-alias-precondition-failed-stale-revision.

=== Cause 3 of 5: DeleteEventSourceMapping succeeds on a mapping that is State=Updating instead of refusing it. ===
AWS: Smithy (lambda) DeleteEventSourceMapping — DELETE /2015-03-31/event-source-mappings/{UUID}, success code 202, and ResourceInUseException is a modeled error (httpError 400). A mapping that is still settling an UpdateEventSourceMapping (State=Updating) cannot be deleted: the delete is refused with ResourceInUseException and the message 'Cannot delete the event source mapping because it is in use.' That message is entirely fixed text — it carries no request or state values. Once the update settles, the identical delete succeeds.
Emulator: UpdateEventSourceMapping does report State='Updating' immediately after it returns, but the DeleteEventSourceMapping issued while the mapping is in that state SUCCEEDS instead of being refused ('deleting the mapping mid-Updating unexpectedly SUCCEEDED'). No ResourceInUseException is ever produced.
Why: a client can destroy a mapping in the middle of a configuration change, so a concurrent update and delete have no defined order and the mapping can disappear while a change it already acknowledged is in flight. Code that retries on ResourceInUseException (the normal pattern for deleting a just-updated mapping) never takes that branch, and the guarantee that a mapping is immutable while Updating is simply absent.
Fix: the DeleteEventSourceMapping handler's validation against the mapping's State in the lambda service — reject with ResourceInUseException while State=Updating (the check's positive control proves deletes of untouched mappings already work, so the gate must be state-scoped, not blanket).
Traces: lambda.delete-event-source-mapping-in-use-rejected.

=== Cause 4 of 5: the oversized-policy ValidationException message truncates the offending value instead of echoing it. ===
AWS: Smithy (lambda) PutResourcePolicy — PUT /2026-07-09/resource-policy/{ResourceArn}; member Policy is @required with @length min 1, max 20480. A document over that limit is refused with ValidationException and the standard constraint message: "1 validation error detected: Value '<the submitted policy document, in full>' at 'policy' failed to satisfy constraint: Member must have length less than or equal to 20480". The fixed text is '1 validation error detected: Value ', "' at 'policy' failed to satisfy constraint: Member must have length less than or equal to "; the variable parts are the submitted value (echoed verbatim and in full) and the limit taken from the model (20480). The rejected call must also leave the previously stored policy untouched.
Emulator: the code (ValidationException), the member path ('policy') and the limit (20480) are right, but the echoed value is elided: the message contains only a prefix of the document followed by a byte-count marker — e.g. "Value '{\"Version\": \"2012-10-17\", \"Statement\": [{\"Sid\": \"sim2realbehavpad0000xxxx…\", … \"Resource\": \"arn:aws:lambda:us-west... [22040 bytes]' at 'policy' failed to satisfy constraint: Member must have length less than or equal to 20480". The '... [<N> bytes]' suffix is emulator-invented text that appears in no AWS message.
Why: AWS's constraint messages are contractual and are parsed/compared by SDK tests, CDK/Terraform error surfacing and user tooling; a message whose value is replaced by a synthetic byte-count marker never matches, and a caller cannot recover from the message which document was rejected.
Fix: the validation/constraint-violation message serializer for the lambda service (the layer that renders '1 validation error detected: …') — echo the offending member value in full rather than truncating it and appending a byte count.
Traces: lambda.policy-length-exceeded-enforcement.

=== Cause 5 of 5: an SQS event source mapping never consumes or delivers, so every delivery/redelivery flow built on one makes no progress and is killed at the suite's 60 s cap. ===
AWS: a Lambda event source mapping on an SQS queue polls the queue and invokes the function. Recorded behavior only for the timings. For a FIFO source with one MessageGroupId per message: every queued message is delivered at least once once the mapping moves to State=Enabled; when the handler throws, the WHOLE batch returns to the queue even with ReportBatchItemFailures enabled, so each member of the failed batch ends at exactly 2 deliveries and messages that succeeded in other batches at exactly 1; a batchItemFailures list naming an identifier that was not in the batch is treated as an invalid response and the whole batch is redelivered; a valid partial-failure report redelivers exactly the reported items. Independently, a mapping created with Enabled=False reports State=Disabled and consumes nothing (the message stays at ApproximateNumberOfMessages=1), and UpdateEventSourceMapping(Enabled=True) moves it to State=Enabled after which the parked message IS delivered.
Emulator: none of these flows reaches a verdict — all four grounding checks report 'Check timed out after 60.0s'. No invocation, no DynamoDB delivery tally, and no result-queue message is ever observable, so neither the whole-batch redelivery rule, nor the invalid-identifier rule, nor the exact partial-batch redelivery set, nor the disabled-mapping positive control can be exercised. The negative half of the disabled case is vacuously satisfied only because nothing is ever delivered at all.
Why: the entire failure-handling contract of an SQS-triggered function is invisible. A client cannot verify that a throwing handler redelivers its batch, that a malformed batchItemFailures report is rejected safely, that a correct partial-failure report redelivers exactly the named items, or that Enabled=False actually parks traffic and re-enabling drains it — i.e. every retry/idempotency assumption an SQS-driven architecture rests on is unverifiable here.
Fix: the SQS event-source-mapping poller and delivery path in the lambda service (receive, batch, invoke, interpret the function's ReportBatchItemFailures response, redrive/visibility handling) and the Enabled/Disabled state gate on polling. Related but NOT covering: open issues 20261024T043150Z-lambda-sqs-event-source-mapping-never-consumes-messages.md and 20261025T022656Z-dynamodb-lambda-sqs-createeventsourcemapping-accepts-a-queue-whose.md describe adjacent ESM gaps (visibility-timeout extension; VisibilityTimeout-vs-Timeout validation and the DLQ/permission-revocation flow); neither carries the replay keys of the four checks listed here.
Traces: dynamodb__lambda__sqs.conc-limits-and-fanout-sqs-esm-handler-error-redelivers-whole-batch, dynamodb__lambda__sqs.conc-limits-and-fanout-sqs-esm-invalid-item-identifier-rejected-whole-batch-redelivered, dynamodb__lambda__sqs.conc-limits-and-fanout-sqs-esm-partial-batch-redelivers-exactly-reported-items, lambda__sfn__sqs.sqs-esm-disabled-mapping-no-invocation-negative.
