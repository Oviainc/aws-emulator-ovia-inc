# cloudfront: a Deployed distribution's edge domain serves nothing, so MinTTL flooring of an origin no-cache directive and Range (416/206) handling over a cached object are never observable

> _Note: this issue was identified against the code base at commit `18c9e77d26f229766ffd8c87453fda7296284d7c`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CloudFront edge data plane (viewer GET through a distribution DomainName)

## Description
One net-new root cause, grounded in two failing checks that the replay report marks neither ALREADY FILED nor OWNED.

Cause 1 of 1: a distribution that CloudFront reports as Deployed never answers a viewer HTTP request at its own DomainName, so every caching contract that can only be read off the edge response is unreachable.

AWS: The CloudFront Smithy model (com.amazonaws.cloudfront, cloudfront2020-05-31) models only the control plane — CreateDistribution/CreateCachePolicy/CreateOriginAccessControl/GetDistribution and friends — and models no edge data plane, so the HTTP behaviour below is recorded behavior only. Recorded: once GetDistribution reports Distribution.Status == "Deployed", a plain HTTP GET of https://<DomainName>/<key> for a key present at the S3 origin is answered 200 with the origin object's exact bytes; the first response carries X-Cache: "Miss from cloudfront" and a repeat of the same cache key carries X-Cache: "Hit from cloudfront". In those header values the fixed text is "Miss from cloudfront" / "Hit from cloudfront" — there is no variable part. On top of that the two checks assert two documented CloudFront caching rules: (a) a cache behaviour whose cache policy sets MinTTL > 0 keeps the response it already has even though the origin sent Cache-Control: "no-cache, max-age=0" (CloudFront documents that MinTTL overrides the origin's no-cache/max-age=0), while a sibling behaviour on the SAME distribution with MinTTL=DefaultTTL=MaxTTL=0 obeys the origin and serves the rewritten bytes; (b) a Range request whose first byte is past the end of the object is refused 416 and the refusal body carries none of the object's bytes, while a satisfiable Range is answered 206 with the exact slice, Content-Range: "bytes <first>-<last>/<total>" and Content-Length equal to the window size — the fixed text there is "bytes ", "-" and "/", and first/last/total are values taken from the request's Range header and the object's length, never literal numbers from one recording.

Emulator: nothing is served at all. Both checks complete their control-plane setup (bucket, object with Cache-Control, cache policies, OAC, CreateDistribution, TagResource, PutBucketPolicy) and then poll the distribution's DomainName for a first 200 every 5 s; no 200 ever arrives, and the poll consumes the whole 180 s check budget, so the harness kills each check with "Check timed out after 180.0s" before the check's own DATAPLANE_UNIMPLEMENTED assertion can even be raised. Because the edge answers nothing, neither the X-Cache values, nor the MinTTL floor, nor 416/206 can be observed; the zero-TTL positive control on the same distribution is equally unreachable, so the emulator is not merely getting the TTL arithmetic wrong — it is not serving the request path at all. Sibling checks in this same suite that are owned by other issues show the emulator's HTTP front end answering a distribution domain with 404 UnknownService (see 20261102T102137Z-cloudfront-a-deployed-distribution-s-edge-domain-answers.md and 20261108T005735Z-cloudfront-a-deployed-distribution-s-edge-domain-still.md), which is consistent with the distribution DomainName never being routed to a viewer-request handler. Those open issues do not carry either replay key below, and the report marked neither of these checks OWNED, so they are filed here.

Why: a client that puts a distribution in front of an origin relies on the edge being the thing it talks to. With no edge, a CDN-shaped application cannot be exercised against the emulator at all: a browser or SDK caller gets no response (or a 404 UnknownService that names no distribution) where AWS returns the object, so cache correctness, conditional/partial downloads (media players and resumable downloaders depend entirely on 206/Content-Range and on 416 for an out-of-range request) and TTL policy decisions all silently appear to work in code that is never actually tested. Worse, an over-permissive edge that answered an unsatisfiable Range with the whole object would hand a client 200 + full body where AWS refuses 416, so this path must be implemented, not stubbed.

Fix: the CloudFront edge data-plane request path — host-based routing of a distribution's DomainName to a viewer-request handler, selection of the matching cache behaviour by PathPattern, the origin fetch (OAC-signed for an S3 origin), the edge cache keyed by the behaviour's cache policy with MinTTL/DefaultTTL/MaxTTL applied over the origin's Cache-Control, emission of the X-Cache header, and Range evaluation against the cached entry (416 with no payload when unsatisfiable, 206 with Content-Range/Content-Length when satisfiable).

Traces: cloudfront.cfcache-min-ttl-floors-origin-no-cache-directive, cloudfront.cfcache-range-beyond-object-rejected-and-partial-served-from-cache.
