# Glue: 2 net-new root causes — DeleteColumnStatisticsTaskSettings leaks a database-level miss message, and CreateColumnStatisticsTaskSettings with no Schedule starts no task run so the running-task conflict is unreachable

## Description
Two distinct, net-new root causes in the Glue Data Catalog's column-statistics-task-settings surface. Both failing checks were marked neither ALREADY FILED nor OWNED in this replay report. There are 2 causes in this issue; both must be closed before submitting.

=== Cause 1 of 2: DeleteColumnStatisticsTaskSettings for a database the catalog does not hold reports the database-level miss message instead of the settings-entry miss ===
AWS: Smithy (com.amazonaws.glue) — `DeleteColumnStatisticsTaskSettings` takes `DatabaseName` and `TableName` (both @required, NameString, @length 1..255) plus optional `CatalogID`, returns an empty output, and models `EntityNotFoundException` (client, HTTP 400, "A specified entity does not exist"), `InvalidInputException` and `OperationTimeoutException`. AWS addresses the settings record by the (DatabaseName, TableName) pair as a single sub-resource and does not disclose which half of the pair is missing: recorded behavior shows that EVERY miss on this operation — a stored table that was never given settings, and an entirely unrelated nonexistent database/table pair — is refused with HTTP 400, Error.Code `EntityNotFoundException`, and Error.Message "ColumnStatisticsTaskSettings entry for input DatabaseName and TableName does not exist". That message is 100% fixed text: it has NO variable parts, and in particular it never embeds the requested DatabaseName or TableName. The replayed check proves the emulator already emits exactly this message for the stored-table-without-settings case, so the divergence is confined to the absent-database case.
Emulator: the handler decides the database lookup first and returns the catalog's generic database-not-found wording. Error.Code is right (`EntityNotFoundException`, HTTP 400) but Error.Message is "Database <DatabaseName> not found." — fixed text "Database " + the DatabaseName taken verbatim from the request + " not found." (recorded instance: "Database sim2real-glue-cstset-nx-db-4805ed41602d not found.", where the name is a per-run value, not part of the requirement).
Why: a client that distinguishes "this table has no statistics schedule yet" from "the database is gone" by the message text — the only signal available, since both answers share code EntityNotFoundException and status 400 — branches the wrong way. Tooling that creates settings on first use, or that treats a database-level miss as a fatal catalog error while a sub-resource miss is a benign first-run condition, inverts its behavior; and the emulator discloses which half of the address is missing where AWS deliberately does not.
Fix: the DeleteColumnStatisticsTaskSettings handler's not-found classification — the absent-database branch must report the operation's own settings-entry miss message, the same fixed string the absent-table and no-settings branches already report, rather than the catalog's database-level message. The same precedence should be audited on GetColumnStatisticsTaskSettings, which addresses the identical sub-resource (the replayed check only exercises Delete).
Traces: glue.delete-column-statistics-task-settings-nonexistent-not-found. Handler: services/service-com-amazonaws-glue-awsglue/src/ops/delete_column_statistics_task_settings.rs lines 171-186 (the `database_mut` miss returns `crate::state::messages::database_not_found(&input.database_name)` where the two branches below it return `crate::state::messages::COLUMN_STATISTICS_TASK_SETTINGS_NOT_FOUND`).

=== Cause 2 of 2: CreateColumnStatisticsTaskSettings submitted without a Schedule starts no column statistics task run, so GetColumnStatisticsTaskRuns stays empty and the in-flight-run conflict can never be raised ===
AWS: Smithy (com.amazonaws.glue) — `CreateColumnStatisticsTaskSettings` takes `DatabaseName`, `TableName` and `Role` (@required) plus optional `Schedule` (CronExpression), `ColumnNameList`, `SampleSize` (@range 0..100), `CatalogID`, `SecurityConfiguration` and `Tags`, and models `AccessDeniedException`, `AlreadyExistsException`, `ColumnStatisticsTaskRunningException`, `EntityNotFoundException`, `InvalidInputException`, `OperationTimeoutException`, `ResourceNumberLimitExceededException` (all client, HTTP 400). `ColumnStatisticsTaskRunningException` is documented as "An exception thrown when you try to start another job while running a column stats generation job". Recorded behavior: a create with NO `Schedule` immediately starts a statistics task run for that catalog/database/table, so `GetColumnStatisticsTaskRuns(DatabaseName, TableName)` lists exactly one `ColumnStatisticsTaskRun` whose `Role` is the submitted Role and whose `Status` (ColumnStatisticsState: STARTING | RUNNING | SUCCEEDED | FAILED | STOPPED) is STARTING or RUNNING. While that run is in flight, a second CreateColumnStatisticsTaskSettings for the SAME table with a DIFFERENT Role is refused HTTP 400, Error.Code `ColumnStatisticsTaskRunningException`, Error.Message "Column statistics task for input table has already started" (entirely fixed text, no variable parts); the refusal has no effect — GetColumnStatisticsTaskRuns still lists exactly one run and its Role is still the first Role. After `StopColumnStatisticsTaskRun(DatabaseName, TableName)` drives that run to `STOPPED`, the identical create with the second Role succeeds.
Emulator: the create validates the Schedule, settles due runs, checks for an in-flight run, looks the table up, refuses a duplicate, and then only stores the settings record — it never starts a run. Consequently `GetColumnStatisticsTaskRuns(DatabaseName, TableName)` returns an empty `ColumnStatisticsTaskRuns` list after a successful create, the replayed check's bounded 60s poll for "a run after a successful Create" never observes one, and the check is reported as `Check timed out after 60.0s`. Because no run is ever in flight on this path, the handler's `ColumnStatisticsTaskRunningException` branch is dead code here: a second create for the same table is instead refused with `AlreadyExistsException`, so the modelled conflict error and its fixed message are unreachable, and the Stop-then-recreate restore path is unreachable too.
Why: a client that submits settings without a Schedule and then waits on GetColumnStatisticsTaskRuns for the statistics run to appear waits forever and times out — no statistics are ever requested, computed or reported, and `GetColumnStatisticsForTable` stays empty. A client that handles the documented transient conflict (retry once the in-flight run drains) instead receives `AlreadyExistsException`, a permanent-looking refusal, and gives up; the two conditions are genuinely different (one clears by itself, the other requires a delete) and the emulator collapses them onto the wrong one. Scheduled/on-demand statistics refresh is therefore unobservable end to end.
Fix: the CreateColumnStatisticsTaskSettings handler together with the catalog's column-statistics run state — a create with no `Schedule` must start a task run for that catalog/database/table (recorded with the submitted `Role` and `ColumnNameList`/`SampleSize`) so GetColumnStatisticsTaskRuns lists it as STARTING/RUNNING, which in turn makes the existing in-flight check refuse a second create with `ColumnStatisticsTaskRunningException` and its fixed message, leaves the stored settings and the single run untouched on that refusal, and lets the create succeed once StopColumnStatisticsTaskRun has left the run STOPPED. (Whether that run then computes real statistics is the already-open run-state-machine issue; what is missing here is the run's existence.)
Traces: glue.column-statistics-task-settings-duplicate-create-rejected. Handler: services/service-com-amazonaws-glue-awsglue/src/ops/create_column_statistics_task_settings.rs lines 220-301 (the handler returns `Ok(CreateColumnStatisticsTaskSettingsOutput {})` after writing `table.column_statistics_task_settings` and never records a run; the in-flight branch at lines 234-271 is therefore never reached on this path).
