# AssociationSummary associationId is serialized in a form that is not byte-identical to its own ARN suffix

> _Note: this issue was identified against the code base at commit `4a9463f06c8da54961be1caf9572b353149b691e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListCustomDetectionRuleAssociations

## Description
This issue bundles 4 distinct net-new replay clusters. All 4 are in the guardduty service, all are on ListCustomDetectionRuleAssociations, and all are on the SAME member of the SAME shape: the `associationId` the emulator serializes into each AssociationSummary of the `ruleAssociations` listing, for an entry the replay locates by that entry's own `arn`. Fix ALL FOUR causes and re-replay every fixture#step named under Traces (the representative in Issue-Trace/Issue-Step plus the three in Issue-Trace-Ids) before submitting; closing fewer than four leaves this issue's remaining causes unexercised. None of the 4 clusters is blocked by a stub (stub_path="") and none is marked owned by an open issue (owned_by=[]).

SHARED FAULT: the identity an association advertises in the list projection is not interchangeable with the identity that same entry's ARN names and that the recording establishes for the association, so a list-then-act client receives a handle the service does not accept. In all 4 clusters the HTTP status is correct (200) and every other member of the summary matches; only `associationId` is reported as a value_mismatch, and the deterministic comparator renders expected and actual with the SAME visible characters. The diverging dimension is therefore NOT the visible digits: it is one the report's rendering collapses (the serialized member's JSON type -- e.g. a non-string -- its case, or surrounding whitespace), or it is the identity the record is bound to rather than how it prints. A fixer MUST compare the serialized `associationId` byte-for-byte -- JSON type included -- against the trailing `/association/<id>` segment of the `arn` in the SAME entry, and against the id a following Get accepts as its path label. Do not compare by eye against the replay report.

Recorded behavior only for the VALUE: the recording pins no literal id; it requires the listed entry to carry the identity the association already holds, and requires the two members of one summary to agree -- the ARN's trailing `/association/<id>` segment is exactly that entry's own `associationId`. The id digits, the region/account parts of the ARN and the counter suffix on a minted id are per-run values and are NOT the requirement.
Why: list-then-act is the normal discovery path for associations. A client that lists associations and then calls GetCustomDetectionRuleAssociation / UpdateCustomDetectionRuleAssociation / DeleteCustomDetectionRuleAssociation with the id a listed entry advertises addresses a handle the service does not recognize, so the call answers 404 ResourceNotFoundException or acts on the wrong record; ARN-keyed IAM policy and inventory joins built from the listing stop matching the id the same payload reports.
Fix: the AssociationSummary projection of the ListCustomDetectionRuleAssociations handler and the shared association view / ARN helper it serializes through, so the id member and the ARN's trailing segment are derived from one value and emitted as the same JSON string, and so one projection serves create, get and list and the id cannot drift from the ARN it is embedded in.
