## Description
Two net-new root causes behind the five surviving autoscaling__ec2__elbv2 failures.

Related open filing that does NOT cover these replays: 20261107T075601Z-autoscaling-ec2-elbv2-auto-scaling-elbv2-asg-instances-never-register-with.md describes the same family in its Cause 1 and even lists three of these check ids, but its replay keys for them are 60 s `Timeout|time.sleep(interval_s)` keys; this replay produces different keys (explicit AssertionErrors naming the empty/`unused` observation, and a 180 s cap), so the suite does not mark these checks OWNED and they survive as live failures. Two of the five checks below (cli-describe-target-health-reflects-asg-instances, elb-target-health-change-event-not-delivered-without-eventbridge-rule) appear in no open issue's trace ids at all.

Cause 1 of 2: an Auto Scaling group never registers its launched instances into its attached target groups, so elbv2 target health never shows them and no ASG/ELB feedback loop converges.
AWS: recorded behavior, with the representation modeled. Smithy: elbv2 DescribeTargetHealth(TargetGroupArn required, Targets, Include) -> DescribeTargetHealthOutput{TargetHealthDescriptions}; TargetHealth.State is TargetHealthStateEnum [initial, healthy, unhealthy, unhealthy.draining, unused, draining, unavailable] and TargetHealth.Reason is TargetHealthReasonEnum, where the model documents 'Target.NotRegistered — The target is not registered with the target group' as a reason only for state 'unused', and 'Elb.RegistrationInProgress'/'Elb.InitialHealthChecking' as the reasons for state 'initial'. Recorded AWS behavior: a group created with TargetGroupARNs (or attached afterwards) registers every instance it launches into every attached target group; DescribeTargetHealth then lists that target moving initial -> healthy (or unhealthy when the check cannot pass), the group's Instance.LifecycleState reaches InService once the ELB health check passes, scale-in/terminate deregisters the target, and the same holds for a group provisioned by a CloudFormation AWS::AutoScaling::AutoScalingGroup.
Emulator: the instance is never registered. DescribeTargetHealth answers an empty TargetHealthDescriptions list for the group's target group indefinitely, or — when the check names the instance id explicitly — reports it forever as State 'unused', Reason 'Target.NotRegistered', Description 'Target is not registered to the target group', which is the answer for an instance the ASG never registered. Nothing ever leaves that state, so every waiter burns its whole budget (60 s, 90 s, 120 s or the 180 s check cap) and no deregistration, replacement or InService transition can be observed either.
Why: the entire 'ASG behind a load balancer' surface is unusable. A client cannot wait for a target to become healthy before cutting traffic over, cannot observe deregistration at scale-in, cannot drive HealthCheckType=ELB replacement, and a CloudFormation stack that wires an ASG to a target group reports success while serving no targets. The failure is silent — an empty list is also the legitimate answer for a group that has nothing registered yet — so callers hang rather than receive an error.
Fix: the Auto Scaling instance-lifecycle machinery in the autoscaling service crate and its ELBv2 registration hop — on launch, register each instance into every TargetGroupARNs entry (the equivalent of elbv2 RegisterTargets: input TargetGroupArn + Targets, errors InvalidTargetException/TargetGroupNotFoundException at 400) and advance the resulting target health in elbv2 state; on terminate/scale-in, deregister it; feed the resulting target health back into the group's Instance.LifecycleState/HealthStatus.
Traces: autoscaling__ec2__elbv2.asg-deregisters-terminated-instance-from-target-group, autoscaling__ec2__elbv2.asg-waits-for-elb-healthy-before-marking-instance-inservice, autoscaling__ec2__elbv2.cli-describe-target-health-reflects-asg-instances, autoscaling__ec2__elbv2.deploy-cfn-asg-launch-template-ec2-instances.

Cause 2 of 2: a CloudWatch alarm state transition produces no EventBridge event, so a matching rule with an SQS target receives nothing.
AWS: recorded behavior only (no Smithy shape describes the emitted envelope). A metric alarm whose state changes — including a forced change via cloudwatch SetAlarmState — publishes an event on the default event bus with source 'aws.cloudwatch', detail-type 'CloudWatch Alarm State Change', detail.alarmName = the alarm's name and detail.state.value = the new state ('OK' here); an EventBridge rule whose pattern matches {source: ['aws.cloudwatch'], detail-type: ['CloudWatch Alarm State Change'], detail: {alarmName: [<name>]}} with an SQS queue target then delivers that envelope to the queue. Before any such rule exists, nothing is delivered — which is the negative leg this check passes.
Emulator: the negative leg holds trivially, but the positive control never delivers. After PutRule + PutTargets with the SQS queue and its queue policy, the check drives SetAlarmState ALARM -> OK repeatedly for 120 s (DescribeAlarms confirms the state does change) and no message with detail.alarmName == the alarm name ever arrives: `AssertionError: expected message for alarm <name> never received on <queue-url> despite retrying the OK transition for 120s`. The alarm name and queue URL are per-run values.
Why: this is the documented way to react to a target-group health alarm. With no event emitted, a client cannot distinguish 'my rule/pattern/permissions are wrong' from 'the alarm never changed state' — the two outcomes the check exists to separate — and every alarm-driven automation (notify, scale, page, remediate) silently never fires while the alarm itself looks correct in DescribeAlarms.
Why this is not a per-run artifact: the check re-drives the transition for 120 s and verifies via DescribeAlarms that the state really moved, so the absent event is not a timing or request-id difference.
Fix: the CloudWatch alarm state-transition path (including SetAlarmState) in the cloudwatch service crate — publish the 'CloudWatch Alarm State Change' envelope onto the default event bus on every state change, so EventBridge rule matching and target delivery can run.
Traces: autoscaling__ec2__elbv2.elb-target-health-change-event-not-delivered-without-eventbridge-rule.

## Steps to Reproduce
Cause 1:
1. Create a VPC with two subnets, an elbv2 target group (TargetType=instance) and an ALB/NLB listener forwarding to it.
2. Create a launch template and an Auto Scaling group with TargetGroupARNs=[<tg>], DesiredCapacity=1, HealthCheckType='ELB'.
3. Poll elbv2.describe_target_health(TargetGroupArn=<tg>): AWS lists the launched instance (initial -> healthy) and autoscaling reports Instance.LifecycleState InService. The emulator returns TargetHealthDescriptions=[] forever, or State 'unused'/Reason 'Target.NotRegistered' when the instance id is passed in Targets.
4. Terminate/scale in and poll again: AWS removes the target; the emulator has nothing to remove.
5. Repeat step 2-3 through a CloudFormation stack declaring AWS::AutoScaling::AutoScalingGroup with TargetGroupARNs for .deploy-cfn-asg-launch-template-ec2-instances.
6. Re-replay the four Cause 1 check ids.

1. Create a target group + internal ALB and cloudwatch.put_metric_alarm on Namespace='AWS/ApplicationELB', MetricName='UnHealthyHostCount' with TargetGroup/LoadBalancer dimensions.
