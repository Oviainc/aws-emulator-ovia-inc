=== Cause 1 of 3: the UpdateSchedulingPolicy not-found refusal drops the sentence's terminating period ===
AWS: Smithy com.amazonaws.batch#UpdateSchedulingPolicy binds POST /v1/updateschedulingpolicy, takes required arn plus optional fairsharePolicy/quotaSharePolicy, returns an empty 200 and declares exactly ClientException (httpError 400) and ServerException (500). The message text is recorded behavior only, but its RULE is known because it is built from the request: for an arn of the right shape that names no stored scheduling policy, the refusal is HTTP 400 / ClientException with message '<the ARN the identifier resolved to> does not exist.' — the ARN from the request followed by that sentence, terminated by a period.
Emulator: status 400 and code ClientException are correct, and the ARN interpolation is correct, but the sentence is emitted WITHOUT its terminating period: '<arn> does not exist'. The shared builder state::does_not_exist_message() deliberately omits the period and documents that the call sites which need it add it (the job-queue and quota-share resolvers do); the UpdateSchedulingPolicy call site does not.
Why: a client or operator matching Batch's known not-found sentence (log scraping, support tooling, golden-file/snapshot tests over error payloads, exact-match assertions) does not match, and the same emulator answers the identical condition with two different renderings depending on which resource resolver refused — so the message cannot be relied on even for internal consistency.
Fix: the not-found refusal construction in the UpdateSchedulingPolicy handler (the does_not_exist_message / resolved_arn call site in services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/update_scheduling_policy.rs), so the scheduling-policy resolver terminates the sentence the way AWS does; the rest of the operation (the 200 success path, in-place fairsharePolicy mutation, and the untouched real policy) already matches.
Traces: batch.op-contract-updateschedulingpolicy.

=== Cause 2 of 3: the policy-kind-change refusal states an emulator-authored sentence instead of Batch's type-change refusal ===
AWS: the same operation and the same modeled error channel (ClientException 400 only). UpdateSchedulingPolicy$fairsharePolicy documents 'Once set during creation, a fairsharePolicy cannot be removed or changed to a quotaSharePolicy' (and the mirror sentence on $quotaSharePolicy), so the refusal itself is modeled documentation; the message is recorded behavior only, but it is a per-rule message naming the from-kind and the to-kind plus the remediation: 'Cannot change scheduling policy type from fairsharePolicy to quotaSharePolicy. Create a new scheduling policy instead.'
Emulator: the refusal happens, the status is 400 and the code is ClientException (the check reaches its message assertion), but the detail is the emulator's own constant (state::POLICY_KIND_IS_FIXED): "A scheduling policy's fairsharePolicy or quotaSharePolicy cannot be changed to the other once it is set" — it names neither the kind the policy has nor the kind that was asked for, and offers no remediation.
Why: the message is the only place Batch states WHICH direction of type change was refused; a client that surfaces it to a user, or that matches the known sentence, gets text that exists nowhere in AWS, and tooling that extracts the from/to kinds from the message finds nothing to extract.
Fix: the policy-kind guard in the UpdateSchedulingPolicy handler (the two POLICY_KIND_IS_FIXED refusals in services/service-com-amazonaws-batch-awsbatchv20160810/src/ops/update_scheduling_policy.rs, backed by the constant in src/state.rs) must emit AWS's per-direction detail built from the stored kind and the requested kind rather than one direction-free constant. The effect-absent behavior is already right: the stored fairsharePolicy is unchanged and no quotaSharePolicy materializes.
Traces: batch.scheduling-policy-type-immutable-after-creation-rejected.

=== Cause 3 of 3: a service job that cannot be placed is driven to terminal FAILED within ~1s instead of resting in RUNNABLE, so its representation can never be read back ===
AWS: Smithy SubmitServiceJob (POST /v1/submitservicejob, success 200) returns {jobArn, jobName, jobId} and DescribeServiceJob (POST /v1/describeservicejob) returns status (ServiceJobStatus enum, required) plus schedulingPriority, shareIdentifier, quotaShareName, timeoutConfig, retryStrategy and serviceRequestPayload. Recorded behavior: a SAGEMAKER_TRAINING service job whose requested capacity exceeds the service environment's capacityLimits is ACCEPTED and then RESTS in the non-terminal status RUNNABLE (it cannot be placed, so it is not failed), and DescribeServiceJob reads every submitted member back unchanged — schedulingPriority and retryStrategy.attempts as the integers submitted, timeoutConfig.attemptDurationSeconds unchanged, serviceRequestPayload byte-identical (so embedded JSON numbers keep their precision), shareIdentifier as supplied, and an optional member never supplied (quotaShareName) absent rather than defaulted.
Emulator: the service job is walked by the clock SUBMITTED -> RUNNABLE -> FAILED, each step JOB_PHASE_MILLIS = 500 ms apart (services/service-com-amazonaws-batch-awsbatchv20160810/src/state.rs, advance_service_jobs), ending with statusReason 'This emulator does not run SageMaker AI, so the service job was never dispatched'. RUNNABLE is therefore a ~500 ms transient regardless of the service environment's capacity, so a client polling at any realistic interval only ever observes FAILED and the check never leaves its poll (it is killed by the harness while the emulator keeps answering FAILED). Everything else in the check's path is fast in the emulator (service environment and job queue reach VALID in ~500 ms), so the budget overrun is caused by the status that never comes, not by slow setup.
Why: the whole service-job representation plane is unobservable. A client that submits a service job and waits for a non-terminal status sees an immediate spurious terminal failure with a statusReason that exists nowhere in AWS, retry/backoff logic keyed on RUNNABLE never fires, and nothing proves the emulator round-trips the submitted numeric members and the omitted optional member — the assertions that would prove it are unreachable behind the status.
Fix: the service-job state machine in the Batch service state (advance_service_jobs in src/state.rs, with SubmitServiceJob/DescribeServiceJob) — hold an unplaceable service job in RUNNABLE against the service environment's capacityLimits instead of expiring it into FAILED after two 500 ms phases, and keep the submitted members readable from DescribeServiceJob while it rests there. This is the same state machine as cause 8 of '20261024T120647Z-batch-overly-permissive-control-and-service-job-planes.md' (which covers the dispatch path to RUNNING/SUCCEEDED) but a different observable: that issue's pointer does not replay this check, so a fix must be confirmed against it too.
Traces: batch.service-job-numeric-parameters-precision-preserved.
