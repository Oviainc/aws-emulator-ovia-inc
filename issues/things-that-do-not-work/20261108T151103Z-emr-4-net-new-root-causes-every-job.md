# EMR: 4 net-new root causes — every job-flow step settles FAILED without running its application, notebook executions never run, ActionOnFailure=TERMINATE_CLUSTER never terminates the cluster, and the unknown PersistentAppUIId refusal names the wrong member

> _Note: this issue was identified against the code base at commit `4466ef5882b584b00b87b338b6098c1e65748c9e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Description
This issue bundles 4 net-new root causes, all under the suite's `### emr` heading. Related open issues that do NOT cover these checks (the suite marks none of them OWNED here): 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md, 20261108T093128Z-ec2-emr-emr-job-flow-steps-always-end-failed-a.md, 20261107T182201Z-emr-notebook-executions-never-run-a-healthy-notebook.md, 20261105T111420Z-emr-three-cluster-scoped-refusal-paths-are-unreachable.md and 20261029T212242Z-elasticmapreduce-emr-unknown-id-refusal-messages-are-reworded-or.md.

--- Cause 1 of 4: every job-flow step reaches FAILED with an emulator-authored reason instead of running its application ---
AWS: Smithy: DescribeStep(ClusterId: ClusterId required, StepId: StepId required) -> {Step: Step}; Step.Status is StepStatus {State: StepState, StateChangeReason: StepStateChangeReason, FailureDetails: FailureDetails, Timeline: StepTimeline}; StepState enumerates PENDING, CANCEL_PENDING, RUNNING, COMPLETED, CANCELLED, FAILED, INTERRUPTED; the model does not say which state a given command yields, so recorded behavior only: real EMR runs the step's Jar/Args on the cluster (command-runner.jar, spark-submit, hadoop fs, s3-dist-cp, hive) and settles the step COMPLETED when the command exits 0 and FAILED when it exits non-zero; the command's side effects (objects written to S3, HDFS files, Glue partitions, step logs under LogUri) are produced. FailureDetails is populated only for a genuine failure.
Emulator: every step — including steps whose command is `exit 0` or a trivially successful `hadoop fs -put` — settles FAILED about two seconds after submission with Status.StateChangeReason.Message 'This emulator runs the step lifecycle but executes no Hadoop jar, so the step ended without running its application.' and FailureDetails {Reason: that same sentence, Message: "No application was started for this step: this emulator holds the cluster's step state and runs no Hadoop, Spark or MapReduce runtime, so the step's own side effects did not happen."}. No step output, no S3/HDFS side effect and no step log is produced. Neither sentence is AWS text; AWS never reports a successful command as FAILED.
Why: a client that submits work and waits for COMPLETED never succeeds, and one that branches on FAILED/FailureDetails takes the failure branch for work that would have succeeded on AWS. Because the exit code is ignored, the distinction between a succeeding and a failing step is lost entirely, so no negative step test can be graded either: a check that expects a specific step to fail cannot tell that failure from the blanket one. Step logs, EMRFS/HDFS writes, Parquet/Hive-partitioned output, s3-dist-cp aggregation and installed-application version reporting are all unobservable.
Fix: the step execution/state machine in the EMR crate (the step lifecycle that drives PENDING->RUNNING->terminal and the AddJobFlowSteps/RunJobFlow Steps handling plus the DescribeStep/ListSteps projection over it) — a step's terminal state must be derived from the modelled outcome of its command, COMPLETED for a command that succeeds, and FailureDetails must be left unset for a step that did not fail.
Traces: the 27 check ids listed in this cause's evidence section (emr.deploy-cfn-cluster-executes-step, emr.e2e-cluster-create-step-execute-terminate-flow, emr.emr-run-step-spark, emr.step-writes-real-output-to-s3, ... ).

--- Cause 2 of 4: notebook executions never run — a healthy notebook ends FAILED with an emulator-authored reason ---
AWS: Smithy: DescribeNotebookExecution(NotebookExecutionId: XmlStringMaxLen256 required) -> {NotebookExecution}, errors InvalidRequestException (client, 400) and InternalServerError (500). NotebookExecution.Status is NotebookExecutionStatus (START_PENDING, STARTING, RUNNING, FINISHING, FINISHED, FAILING, FAILED, STOP_PENDING, STOPPING, STOPPED) and LastStateChangeReason carries the reason. Recorded behavior only for the outcome: real EMR executes the notebook on the execution engine and a well-formed notebook in an existing S3 location reaches FINISHED, writing the executed notebook to OutputNotebookS3Location; LastStateChangeReason then describes a successful completion, not a failure.
Emulator: StartNotebookExecution is accepted and the execution transitions STARTING -> FAILING -> FAILED within seconds with LastStateChangeReason 'This emulator records notebook executions but runs no notebook, so the execution ended without running.' — not AWS text — and no output notebook is written.
Why: no notebook-driven workflow can complete; a client polling for FINISHED never finishes, and one reading LastStateChangeReason gets an explanation AWS never emits. The persistent-app-UI flow that depends on a finished execution is cut off as well.
Fix: the notebook-execution lifecycle in the EMR crate (the StartNotebookExecution handler and the notebook-execution state machine DescribeNotebookExecution/ListNotebookExecutions project) — drive a well-formed execution to FINISHED and write the output notebook, reserving FAILED for executions that actually fail.
Traces: emr.e2e-notebook-execution-persistent-app-ui-flow, emr.e2e-notebook-execution-run-to-completion, emr.notebook-execution-state-transitions-starting-to-finished.

--- Cause 3 of 4: a failed step with ActionOnFailure=TERMINATE_CLUSTER does not terminate the cluster ---
AWS: Smithy: StepConfig.ActionOnFailure is ActionOnFailure enumerating TERMINATE_JOB_FLOW, TERMINATE_CLUSTER, CANCEL_AND_WAIT, CONTINUE; Cluster.Status is ClusterStatus {State, StateChangeReason: ClusterStateChangeReason {Code: ClusterStateChangeReasonCode, Message}, Timeline} and ClusterStateChangeReasonCode includes STEP_FAILURE. Recorded behavior for the sequencing: when a step whose ActionOnFailure is TERMINATE_CLUSTER fails, EMR cancels the still-pending steps (they end CANCELLED) and shuts the cluster down into TERMINATED_WITH_ERRORS with StateChangeReason.Code STEP_FAILURE and a human-readable Message, with Cluster.Timeline.EndDateTime at or after the terminating step's own EndDateTime. A step with ActionOnFailure=CONTINUE must leave the following step free to run.
Emulator: on a KeepJobFlowAliveWhenNoSteps=true cluster carrying four steps (CONTINUE, CONTINUE, TERMINATE_CLUSTER, CONTINUE) the TERMINATE_CLUSTER step settles FAILED (see Cause 1) and the cluster is left running: DescribeCluster never reports TERMINATED or TERMINATED_WITH_ERRORS and the check is cut off at the 180 s harness budget while polling for a terminal state. The configured AutoTerminationPolicy IdleTimeout of 60 s does not end it either. Hypothesis: ActionOnFailure is stored on the step but never consulted when the step settles, so neither the cancel-the-remaining-steps nor the terminate-the-cluster effect is applied.
Why: a client relying on TERMINATE_CLUSTER to bound a cluster's lifetime on failure is left with a cluster that runs forever and never produces the TERMINATED_WITH_ERRORS / STEP_FAILURE signal its error handling and its cost controls key off; a client waiting for the terminal state hangs.
Fix: the step state machine's terminal-transition handling in the EMR crate — on a step failure apply its ActionOnFailure (CANCEL the pending steps and drive the cluster to TERMINATED_WITH_ERRORS with StateChangeReason.Code=STEP_FAILURE for TERMINATE_CLUSTER/TERMINATE_JOB_FLOW, CANCEL_AND_WAIT and CONTINUE as modelled), setting Cluster.Timeline.EndDateTime no earlier than the terminating step's EndDateTime.
Traces: emr.action-on-failure-continue-then-terminate-cluster.

--- Cause 4 of 4: GetPersistentAppUIPresignedURL refuses an unknown PersistentAppUIId by naming the wrong member ---
AWS: Smithy: GetPersistentAppUIPresignedURL(PersistentAppUIId: XmlStringMaxLen256 required, PersistentAppUIType: PersistentAppUIType, ApplicationId, AuthProxyCall, ExecutionRoleArn) -> {PresignedURLReady, PresignedURL}; modeled errors InvalidRequestException (client, 400) and InternalServerError (500). Recorded behavior for the message: a PersistentAppUIId that does not exist is refused HTTP 400 InvalidRequestException with the message 'ProfilerId is not valid.' — fixed text, with no variable part; the member AWS names in this refusal is the profiler id behind PersistentAppUIId, not PersistentAppUIType.
Emulator: refuses the same request with the message 'PersistentAppUIType is not valid.', i.e. it reports the wrong member as invalid. The identifier that was actually unresolvable is PersistentAppUIId; PersistentAppUIType was well-formed.
Why: a client (or an operator reading the error) is told the UI type it sent is wrong when the real problem is an unknown/expired persistent-app-UI id, so the retry it chooses — correcting the type — can never succeed. Any error handling that matches on AWS's sentence does not match at all.
Fix: the unknown-id refusal in the GetPersistentAppUIPresignedURL handler's validation in the EMR crate — resolve PersistentAppUIId first and refuse with InvalidRequestException/400 and AWS's 'ProfilerId is not valid.' sentence, keeping the PersistentAppUIType refusal for a genuinely invalid type.
Traces: emr.persistent-app-ui-presigned-url-expires-after-ttl.
