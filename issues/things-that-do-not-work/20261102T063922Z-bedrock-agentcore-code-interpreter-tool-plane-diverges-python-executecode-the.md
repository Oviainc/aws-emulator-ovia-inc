# Code Interpreter tool plane diverges: python executeCode, the shell/executeCommand and async task tools run nothing, path-escape is refused out of band as 400 ValidationException, and a stopped session answers ConflictException (5 causes)

> _Note: this issue was identified against the code base at commit `ca72e8d5fc2000c02a01dcf678a8fed8074b0f2e`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeCodeInterpreter

## Description
Five net-new root causes, all in bedrock-agentcore's InvokeCodeInterpreter tool plane (built-in interpreter aws.codeinterpreter.v1). The operation is now routed and the workspace tools (writeFiles/readFiles/listFiles/removeFiles) work, so this is NOT the routing failure recorded in the open issue 20261029T215145Z-bedrock-agentcore-agentcore-data-plane-invocation-unserved-invokecodeinterpreter-and-invokeharness.md (InvokeCodeInterpreter answering UnknownService). That issue lists the same seven check ids but describes a cause that no longer reproduces; what follows is what the served tool plane now gets wrong, and these checks must be replayed against the causes below even if that issue is closed.

Cause 1 of 5: an out-of-sandbox path argument is refused as an API error instead of in band on the tool result.
AWS: Smithy: InvokeCodeInterpreter is POST /code-interpreters/{codeInterpreterIdentifier}/tools/invoke with @http code 200; its output member `stream` (CodeInterpreterStreamOutput) is @httpPayload @required @streaming and its success member is `result`: CodeInterpreterResult {content @required, structuredContent, isError}. `isError` is documented as 'Indicates whether the result represents an error. If true, the content contains error messages or exception information', i.e. a tool-level failure is a 200 carrying isError=true, not a modeled API error. Recorded behavior: for a path that leaves the session workspace (both a `../` traversal and an absolute path, on readFiles/writeFiles/removeFiles/listFiles) the call answers 200 and the result's text block has the fixed lead-in 'Error executing tool ' + the tool name, and the reason names path traversal; the variable parts are the tool name and the offending path from the request. No file content and no resource_link entries accompany the refusal.
Emulator: the call is rejected as a modeled API error — HTTP 400 ValidationException, message 'The tool path ../../etc/hostname leaves the session workspace; a path cannot contain a parent segment.' (fixed text is emulator-authored; the path is the request's). The botocore call therefore raises instead of yielding a stream, so no result event with isError is ever produced. (The absolute-path arm has a sibling emulator-authored sentence, 'The tool path {path} is absolute; a path addresses the session workspace and is relative to it.')
Why: a client that handles sandbox rejections the way AWS reports them — inspect result.isError and the content text, keep using the session — instead gets a ClientError that aborts its loop; and a client that branches on ValidationException sees a 400 where AWS never sends one. The refusal reason also differs in wording, so tooling that matches on 'path traversal' misclassifies the rejection.
Fix: InvokeCodeInterpreter's handler/path-validation arm for the file tools (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/invoke_code_interpreter.rs, the PathRejection->error mapping around lines 900-920, which must become a ToolOutcome rather than InvokeCodeInterpreterErrorModeled::ValidationException), and the result serializer that frames it as a 200 `result` event.
Traces: bedrock-agentcore.agc-code-interpreter-file-tool-path-escape-rejected.

Cause 2 of 5: executeCode with language 'python' is not executed at all.
AWS: Smithy: ToolArguments.language targets ProgrammingLanguage with values python, javascript, typescript, and ToolArguments.runtime targets LanguageRuntime with values nodejs, deno, python; the docs for `runtime` state it 'defaults to deno for JavaScript and TypeScript', i.e. python is a first-class language of the same built-in interpreter. Recorded behavior: executeCode {language: 'python', code: "x = '...'\nprint('set-ok')"} answers 200 with isError absent/false and the printed text in the result (content text and/or structuredContent.stdout); a later call in the same session can read the binding back; an undefined name surfaces as isError=true with 'NameError' in the text; and clearContext=true discards the session namespace before the submitted code runs.
Emulator: every python executeCode answers isError=true with the emulator-authored sentence 'This code interpreter session has no python engine, so the code was not run. The engine it embeds runs javascript.' — emitted TWICE (once as a content text block, once as structuredContent.stderr, see ToolOutcome::NothingRan, invoke_code_interpreter.rs ~lines 466 and 607-614). Nothing runs, so no stdout, no namespace and no NameError is ever produced.
Why: python is the default language clients use with aws.codeinterpreter.v1; every agent that computes with it gets an error result for valid code, cannot observe its own prints, cannot rely on per-session namespace persistence or on clearContext resetting it, and any test of sandbox isolation (a variable from one session must not be visible in another) cannot be run at all.
Fix: the executeCode arm of InvokeCodeInterpreter's handler (src/ops/invoke_code_interpreter.rs, the `runs_javascript` gate) plus the per-session execution-context state it keeps in src/state.rs — a python execution substrate with captured stdout/stderr, a persisted per-session namespace, and clearContext honoured before the submitted code runs.
Traces: bedrock-agentcore.invoke-code-interpreter-sandbox-isolation, bedrock-agentcore.invoke-code-interpreter-clear-context-resets-the-namespace, bedrock-agentcore.agc-code-interpreter-file-tools-share-one-sandbox-filesystem.

Cause 3 of 5: executeCommand runs nothing and its result carries no exitCode/stdout.
AWS: Smithy: ToolName includes executeCommand and ToolArguments carries `command`; CodeInterpreterResult.structuredContent is ToolResultStructuredContent {taskId, taskStatus, stdout, stderr, exitCode, executionTime}, whose exitCode is documented as 'The exit code from the tool execution'. Recorded behavior: executeCommand runs the command in a shell inside the session's sandbox, sharing one filesystem with the file tools, and the result's structuredContent reports stdout, stderr and exitCode — 0 for a command that succeeded and non-zero for one that failed (e.g. `cat` of a path that does not exist in this session, which also prints 'No such file').
Emulator: executeCommand answers isError=true with 'This code interpreter session has no command runtime, so the executeCommand tool ran nothing.' and a structuredContent that contains ONLY stderr (that same sentence) — exitCode, stdout and executionTime are absent, so a client reading structuredContent['exitCode'] gets a missing key rather than a status.
Why: the shell is one of the three views of a code-interpreter sandbox; a client cannot run a command, cannot tell success from failure (no exitCode at all, and the only signal is a non-AWS sentence), and the cross-session filesystem-isolation guarantee it would verify through the shell is unassertable.
Fix: the command-plane arm of InvokeCodeInterpreter's handler (src/ops/invoke_code_interpreter.rs, `no_command_runtime`, ~line 646) and ToolOutcome::into_result, which must report a real run as Ran {stdout, stderr, exit_code, elapsed} against the session's workspace state.
Traces: bedrock-agentcore.agc-code-interpreter-filesystem-isolated-across-sessions.

Cause 4 of 5: the async task tools startCommandExecution / getTask / stopTask start nothing, so no task lifecycle exists.
AWS: Smithy: ToolName includes startCommandExecution, getTask and stopTask; ToolArguments carries `taskId`; ToolResultStructuredContent carries taskId and taskStatus, and TaskStatus's values are submitted, working, completed, canceled, failed. Recorded behavior (per the check's stated hypotheses, otherwise recorded behavior only): startCommandExecution returns immediately with structuredContent.taskId and a non-terminal taskStatus, getTask on that taskId converges to 'completed' with exitCode 0 for a script that exits 0, and stopTask drives a running task to 'canceled'.
Emulator: startCommandExecution answers isError=true with 'This code interpreter session has no command runtime, so the startCommandExecution tool ran nothing.' (again duplicated into structuredContent.stderr), and no taskId is ever minted, so getTask and stopTask have nothing to address.
Why: the asynchronous execution surface — submit, poll, cancel — is entirely unavailable, and because the refusal is in band with an unmodeled sentence rather than a modeled error, a client cannot distinguish 'task tooling unsupported' from 'the command failed'.
Fix: the same command-plane arm plus new per-session task state (src/ops/invoke_code_interpreter.rs and src/state.rs): mint a taskId on startCommandExecution, report taskStatus transitions submitted->working->completed/failed, let getTask read it and stopTask drive it to canceled.
Traces: bedrock-agentcore.code-interpreter-async-task-converges-and-stop-task-cancels.

Cause 5 of 5: a tool call against a STOPPED session is refused with the wrong error class and message.
AWS: Smithy: InvokeCodeInterpreter models ValidationException (@httpError 400, members message @required + reason @required) and ConflictException (@httpError 409). Recorded behavior: after StopCodeInterpreterSession, a further InvokeCodeInterpreter on that sessionId is refused with code ValidationException and message 'Code interpreter session ' + the sessionId from the request + ' is not active' — the fixed text is 'Code interpreter session ' and ' is not active', the variable part is the session id.
Emulator: the same call is refused with ConflictException (HTTP 409) and the emulator's own already-terminated sentence (crate::state::session_already_terminated), see invoke_code_interpreter.rs ~lines 298-307 where a TERMINATED session returns ConflictException.
Why: ConflictException is retry/conflict-shaped, so an SDK or agent framework that treats 409 as 'retry or resolve the conflict' loops against a session that can never come back, while the AWS branch (ValidationException = the session id is no longer usable, start a new session) is never taken; the message text also differs, so clients matching the 'is not active' sentence misreport the condition.
Fix: the session-resolution gate in InvokeCodeInterpreter's handler (src/ops/invoke_code_interpreter.rs, the status_as_of/TERMINATED branch) and the message it builds in src/state.rs.
Traces: bedrock-agentcore.e2e-code-interpreter-side-effect-persistence.
