# opensearch: the server-managed engine-upgrade progression never becomes observable — UpgradeDomain is accepted but GetUpgradeStatus is never reached before the scenario's deadline (1 cause)

> _Note: this issue was identified against the code base at commit `7f29b57fbd359e50cf77d7b64047ddbb2b827597`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetUpgradeStatus

## Description
Cause 1 of 1 — a service-managed engine-version upgrade of a domain never produces an observable progression to a terminal UPGRADE step on this emulator: the end-to-end scenario (create a domain on an advertised source version, wait for it to go idle, UpgradeDomain to an advertised target, then poll GetUpgradeStatus only) spends its whole wall budget before it can read GetUpgradeStatus even once, so the contract is ungraded and nothing about the upgrade's progress is ever served.

AWS: Smithy (com.amazonaws.opensearch#AmazonOpenSearchService): UpgradeDomain (input DomainName required DomainName len 3..28 pattern ^[a-z][a-z0-9\-]+$, TargetVersion required VersionString len 14..18 pattern ^Elasticsearch_[0-9]{1}\.[0-9]{1,2}$|^OpenSearch_[0-9]{1,2}\.[0-9]{1,2}$, PerformCheckOnly Boolean) "allows you to either upgrade your Amazon OpenSearch Service domain or perform an upgrade eligibility check" and answers UpgradeId plus ChangeProgressDetails. GetUpgradeStatus "returns the most recent status of the last upgrade or upgrade eligibility check performed on an Amazon OpenSearch Service domain" and answers UpgradeStep (one of PRE_UPGRADE_CHECK | SNAPSHOT | UPGRADE), StepStatus (one of FAILED | IN_PROGRESS | SUCCEEDED | SUCCEEDED_WITH_ISSUES) and UpgradeName. GetUpgradeHistory answers UpgradeHistories entries carrying UpgradeName, StartTimestamp, UpgradeStatus and StepsList. On AWS the upgrade is SERVICE-managed: once UpgradeDomain is accepted, no further client call is needed to advance it — polling GetUpgradeStatus alone eventually reports UpgradeStep=UPGRADE with StepStatus in (SUCCEEDED, SUCCEEDED_WITH_ISSUES), the newest GetUpgradeHistory entry reaches the same terminal UpgradeStatus with at least one StepsList entry, and DescribeDomain then reports EngineVersion equal to the requested TargetVersion. Recorded behavior: the recording reaches that terminal state within the scenario's budget, having created the domain, waited for DescribeDomain to report Processing=false on two consecutive 30 s polls, and called UpgradeDomain with a target GetCompatibleVersions advertises.
Emulator: the scenario never gets as far as a single GetUpgradeStatus call. GetCompatibleVersions offered an OpenSearch_X.Y -> OpenSearch_X.Y path, CreateDomain was accepted, the domain went idle, and UpgradeDomain was accepted (no ClientError propagated) — but by the time the poll loop was entered the scenario's remaining time was already below the margin it reserves, so the loop body ran zero times and the observation is literally absent: "AssertionError: upgrade never reached a terminal UPGRADE step; last GetUpgradeStatus None". No UpgradeStep, StepStatus, UpgradeName, GetUpgradeHistory entry or post-upgrade DescribeDomain EngineVersion was ever obtained from this emulator, so the whole server-managed-progress contract of this service is unverified rather than merely wrong in one field. Hypothesis (neither the model nor the recording states which of these the emulator does): the pre-poll phase of the scenario is what consumes the budget — either DescribeDomain keeps reporting Processing=true (DomainProcessingStatus not settled) long enough that the idle wait burns many 30 s polls, or UpgradeDomain keeps answering the BaseException whose message contains "background tasks in progress" (crate::state::upgrade_blocked_by_background_tasks, reached from Domain::work_in_flight) for minutes AFTER DescribeDomain already reports Processing=false, so the accepted call lands only at the end of the retry window. The emulator's own upgrade spans are short (state.rs DOMAIN_WORK = 3 s, UpgradeRun::current_step derives the three steps over that span), which is why the divergence shows up as time spent BEFORE the first poll and not as a stalled IN_PROGRESS.
Why: a client that starts an engine upgrade and then observes it the way AWS supports — polling GetUpgradeStatus (and GetUpgradeHistory) until the UPGRADE step is terminal, then reading EngineVersion back — gets no progress at all against this emulator: upgrade orchestration, CloudFormation/IaC upgrade waiters and operational runbooks that gate on "UpgradeStep=UPGRADE and StepStatus=SUCCEEDED" never complete, and because the domain's readiness signals (DescribeDomain Processing / DomainProcessingStatus) and the UpgradeDomain in-flight guard are what hold the caller up, a caller cannot even tell whether its upgrade was started.
Fix: the domain readiness and upgrade-admission seam of the opensearch crate rather than the reporting of the status itself — make DescribeDomain's Processing / DomainProcessingStatus and the UpgradeDomain admission guard agree on when a freshly created domain is quiet (Domain::work_in_flight and the settle path in the crate's state, used by the UpgradeDomain handler), so an UpgradeDomain issued after the domain reports Processing=false is admitted immediately, and the run GetUpgradeStatus / GetUpgradeHistory derive from advances to its terminal UPGRADE step and materialises the target EngineVersion on the domain without any client-driven step call.
Traces: opensearch.upgrade-domain-server-managed-progress-tracking (the only failing check in this suite run that is neither OWNED by an open issue nor blocked by an unimplemented stub). Related but not covering: the open issue 20261106T101405Z-opensearch-2-net-new-causes-upgradedomain-s-unsupported.md carries only UpgradeDomain refusal-wording and FGAC-validation keys for refused calls, and the resolved 20261029T182036Z-opensearch-domain-upgrade-and-maintenance-state-machines-report.md does not carry this check's replay key — this check fails on an ACCEPTED upgrade that produces no observation, not on a refusal.
