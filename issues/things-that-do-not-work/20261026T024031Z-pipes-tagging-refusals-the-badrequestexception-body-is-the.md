# Pipes tagging refusals: the BadRequestException body is the bare validation sentence instead of the JSON {"message": ...} document, the reserved aws: prefix sentence is emulator-authored, and an empty UntagResource key is reclassified from ValidationException to BadRequestException

> _Note: this issue was identified against the code base at commit `bd135f31176b365c7ab9fd0ab0731a7700969a26`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
TagResource

## Description
This bundle has 3 causes; all three must be closed before submitting. All three are fidelity defects of the now-implemented pipes tagging surface (TagResource/UntagResource), grounded in failing behavioral checks of this run that no filed issue carries.

Context, not coverage. The resolved 20261025T025049Z-pipes-tagging-surface-the-arn-addressed-tag-operations.md required (its Cause 2) BOTH the 400/BadRequestException classification for a tag-key bound violation AND the validation-framework body; the classification landed (the checks below now get code BadRequestException and their effect-absence and positive-control legs pass) but the body did not, so Cause 1 here is the half of that requirement that is still wrong — a resolved issue does not cover it. The open 20261023T235727Z-pipes-control-plane-cross-resource-createpipe-validation-is.md names pipes.untag-resource-malformed-empty-key-rejected under its Cause 2 against the old generic boundary-validator wording; that check now fails one assertion EARLIER, on the error CODE, which that issue does not carry — Cause 3 below. The calls are not refused with NotImplemented anywhere here: every cause is a wrong answer from a working handler.

Cause 1 of 3: a tag key outside TagKey's published bound is refused with the right code but with the bare validation sentence, not the JSON document AWS puts in the exception's message.
AWS: Smithy (services/service-com-amazonaws-pipes-pipes/smithy-model/com-amazonaws-pipes-pipes.json) — TagKey is @length(min 1, max 128); it is the key member of TagMap (TagResource.tags, @length 1..50) and the member of TagKeyList (UntagResource.tagKeys, @length 0..50). TagResource and UntagResource model only InternalException (500), NotFoundException (404) and ValidationException (400); BadRequestException is NOT modeled by either — it is the resource-tagging layer's code, which is why the checks state it empirically. Recorded behavior for the body: the exception's Message member is itself a JSON document with a single key, whose value is the validation-framework sentence with every apostrophe backslash-escaped — for TagResource '{"message": "1 validation error detected: Value \'{<key>=<value>}\' at \'addedTags\' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]"}' and for UntagResource the same form with Value '[<key>]' at 'removedTagKeys' and 'Member must satisfy constraint: [...]'. The REQUIREMENT is: HTTP 400, code BadRequestException, and a Message that is that JSON envelope; its fixed text is the envelope plus the sentence template, and its variable parts are the member's echoed value (the {key=value} map rendering or the [key] list rendering, taken from the request) and the two bounds (from TagKey's @length in the model). The 129-/200-character keys in the recordings are example values, not part of the template.
Emulator: the sentence is returned UNWRAPPED — "1 validation error detected: Value '{kkk…=irrelevant}' at 'addedTags' failed to satisfy constraint: Map keys must satisfy constraint: [Member must have length less than or equal to 128, Member must have length greater than or equal to 1]" — with no {"message": …} envelope and with plain, unescaped apostrophes. The inner sentence, the member names and the bounds are otherwise byte-identical to AWS's, so the ONLY divergence is the missing JSON envelope/escaping.
Why: a client that reads this refusal gets a string where AWS gives it a JSON document. Tagging code and CLIs that json-decode the message to recover the single 'message' field (the shape the tagging layer always returns) fail to parse against the emulator, and a test written against AWS fails on a request both services refuse identically.
Fix: the refusal-wording seam of the pipes service — the BadRequestException construction that fronts the tagging operations (the override_refusal path and the shared tag-refusal sentence builders it calls) must emit the JSON envelope around the validation sentence, for both the addedTags (TagResource) and removedTagKeys (UntagResource) members, instead of the bare sentence.
Traces: pipes.tag-resource-invalid-key-rejected, pipes.tag-resource-invalid-key-validation-rejected, pipes.untag-resource-malformed-key-validation-rejected.

Cause 2 of 3: the reserved 'aws:' tag-key prefix is refused with an emulator-authored sentence instead of the fixed sentence AWS returns.
AWS: Smithy models no character or prefix rule for TagKey (only @length 1..128), so recorded behavior only: TagResource with a key beginning 'aws:' is refused with HTTP 400, code BadRequestException and the FIXED sentence 'Invalid tag key. Customers cannot set tag keys starting with aws: (case insensitive)'. That sentence is entirely fixed text — it names neither the key nor the resource — and the parenthetical states the rule itself (the prefix is matched case-insensitively), so the whole string is the requirement.
Emulator: HTTP 400 and code BadRequestException are correct, but the message is "Tag key 'aws:reserved-probe' uses the prefix 'aws:', which is reserved for Amazon Web Services use." — a different sentence that additionally echoes the caller's key back, where AWS's wording is key-agnostic. Built in services/service-com-amazonaws-pipes-pipes/src/state.rs by tag_refusal's TagViolation::ReservedKeyPrefix arm (state.rs:258-262, using RESERVED_TAG_KEY_PREFIX and echoed_key).
Why: operators and tests read this sentence; one asserting on the documented wording, or grepping logs for it, sees a message AWS never produces, and the emulator reveals the rejected key in a message AWS keeps generic.
Fix: the reserved-prefix arm of the tag-refusal wording in the pipes service state/validation layer — return the fixed documented sentence with no interpolation.
Traces: pipes.tag-resource-with-aws-reserved-prefix-rejected.

Cause 3 of 3: an EMPTY-string tag key on UntagResource is reclassified into the tagging layer's BadRequestException, where AWS answers the modeled ValidationException.
AWS: Smithy — UntagResource.tagKeys targets TagKeyList whose member is TagKey @length(min 1, max 128); UntagResource models ValidationException (HTTP 400, members message and fieldList). Recorded behavior: a tagKeys entry that is the empty string (the MIN bound, not the max) is refused with HTTP 400, code ValidationException and message '[tagKeys]' — the member name in square brackets, so the fixed text is the brackets and the variable part is the refused member's name taken from the request path. AWS therefore splits the two TagKey bound violations across two codes: the over-128 key is the tagging layer's BadRequestException with the envelope of Cause 1, while the empty key is the service's own modeled ValidationException naming just the member.
Emulator: the empty key is answered with code BadRequestException — 'AssertionError: an empty-string tag key must be rejected server-side, got BadRequestException'. The request IS refused and no tags are removed (the effect-absence and positive-control legs pass), so only the classification (and with it the body) diverges. Cause: src/service.rs override_refusal routes EVERY violation whose first path segment is 'tags'/'tagKeys' to the tagging layer's code (TAG_RULE_REFUSAL_CODE, service.rs:52 and 170-190, via tag_content_clause -> state::tag_key_refusal), without distinguishing which bound of TagKey was broken.
Why: SDK error handling branches on the error code. ValidationException is modeled on UntagResource and BadRequestException is not, so a client catching the modeled validation error for a malformed key falls through to its generic/unknown-error path, and the refusal it does see carries the length-template body instead of '[tagKeys]'.
Fix: the pipes refusal-wording seam — keep the tagging layer's BadRequestException for a key over TagKey's maximum, and let a tagKeys element that violates the MINIMUM bound stay the modeled ValidationException with message '[tagKeys]'.
Traces: pipes.untag-resource-malformed-empty-key-rejected.
