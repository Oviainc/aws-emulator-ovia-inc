# memorydb: DescribeEvents event messages do not follow AWS's "<Operation> <resource> operation completed." form and ACL membership changes record no per-member event

> _Note: this issue was identified against the code base at commit `7f205ee96657d4151f96c4aa7296372f34590a63`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEvents

## Description
One root cause in the memorydb emulator's event log, found by replaying the behavioral suite (memorydb scored 4/20).

=== Cause 1 of 1: lifecycle event messages use the emulator's own wording, and an ACL membership add/remove records one generic 'modified' event instead of a per-member one ===

AWS: every call that creates, modifies or deletes a MemoryDB user or ACL records a DescribeEvents entry whose Event$Message is built from the operation that was performed and the resource(s) it named, in the form '<Operation> <resource-kind> <name> operation completed.' — recorded behavior only; the model says nothing about the text (Smithy: Event$Message -> String, doc 'The text of the event.', Event$SourceType -> SourceType enum [node|parameter-group|subnet-group|cluster|user|acl], DescribeEvents paginated by NextToken over Events). The recording shows these messages for a user/ACL lifecycle, under SourceType 'user' / 'acl' and SourceName = the resource's (folded) name, newest first:
  - 'Create user <user> operation completed.'
  - 'Modify user <user> operation completed.'
  - 'Delete user <user> operation completed.'
  - 'Create ACL <acl> operation completed.'
  - 'Add user <user> to ACL <acl> operation completed.'
  - 'Remove user <user> from ACL <acl> operation completed.'
So the message rule is request-derived: it names the operation and the resources the request named, and an ACL membership change produces ONE EVENT PER MEMBER added or removed, naming both the user and the ACL — not a single opaque 'the ACL changed' entry.

Emulator: DescribeEvents itself is implemented and does filter/page correctly (services/service-com-amazonaws-memorydb-amazonmemorydb/src/ops/describe_events.rs), but the recorded text is generated by a single rule in the store that ignores the operation and the resource name: state.rs record_event() builds message = format!("{} {}", source_type_label(source_type), kind.verb()), i.e. 'User created', 'User modified', 'User deleted', 'ACL created', 'ACL modified', 'Parameter group modified' (src/state.rs: EventKind::verb() -> "created"/"modified"/"deleted"; source_type_label() -> "Cluster"/"ACL"/"User"/"Parameter group"; the doc comment there states the wording is the emulator's own). UpdateACL with UserNamesToAdd/UserNamesToRemove therefore records at most one 'ACL modified' event and no event naming the added or removed user. Replaying memorydb.events-record-user-and-acl-lifecycle, the check's poll loop for the AWS messages never matches and the check is killed by the harness after 60s (reported as 'Check timed out after 60.0s'); the same loop completes in seconds against AWS.

Why: DescribeEvents is the only way a client can see what MemoryDB did to a user or ACL after the fact. A client that greps event messages for a completed lifecycle step ('Create user X operation completed.') or that reconstructs ACL membership history from 'Add user X to ACL Y' / 'Remove user X from ACL Y' entries — console-style audit views, operator scripts that wait on an event rather than polling status, log pipelines keyed on the message — sees nothing it recognises and either waits forever or concludes the operation never happened. The per-member gap additionally loses information that is not recoverable from any other call: after the fact there is no way to learn which member an ACL update added or removed.

Fix: in the event-recording path (services/service-com-amazonaws-memorydb-amazonmemorydb/src/state.rs record_event / EventKind / source_type_label) and in the write handlers that call it (src/ops/create_user.rs, update_user.rs, delete_user.rs, create_acl.rs, update_acl.rs, delete_acl.rs, create_parameter_group.rs, update_parameter_group.rs): record the message from the operation and the resource names the request carried, in AWS's '<Operation> <kind> <name> operation completed.' form, and have UpdateACL record one event per user added ('Add user <u> to ACL <a> operation completed.') and per user removed ('Remove user <u> from ACL <a> operation completed.') against SourceType 'acl'. The existing SourceType/SourceName/Date/ordering behavior is already correct and must be preserved.

Traces: memorydb.events-record-user-and-acl-lifecycle.

The check creates a user, updates its AccessString, creates an ACL, adds then removes the user, deletes the user, and polls DescribeEvents (SourceType='user'/'acl', SourceName=<name>, StartTime=now-5m) until these messages appear:
  Expected (AWS, recorded): 'Create ACL <acl> operation completed.', 'Add user <user> to ACL <acl> operation completed.', 'Remove user <user> from ACL <acl> operation completed.', 'Create user <user> operation completed.', 'Modify user <user> operation completed.', 'Delete user <user> operation completed.' (newest first; the delete is got[0], the create got[-1]).
  Actual (emulator): the log holds messages built as '<source-type label> <verb>' — 'User created', 'User modified', 'User deleted', 'ACL created', 'ACL modified' — and no event at all naming the user added to or removed from the ACL, so the poll never matches and the harness kills the check at 60s.

Source of the actual text, from the checkout:
  services/service-com-amazonaws-memorydb-amazonmemorydb/src/state.rs, record_event():
      message: format!("{} {}", source_type_label(source_type), kind.verb()),
  with EventKind::verb() -> "created" | "modified" | "deleted" and source_type_label() -> "Cluster" | "ACL" | "User" | "Parameter group".

Smithy (services/service-com-amazonaws-memorydb-amazonmemorydb/smithy-model/com-amazonaws-memorydb-amazonmemorydb.json): DescribeEvents input {SourceName, SourceType, StartTime, EndTime, Duration, MaxResults, NextToken} -> output {Events: EventList, NextToken}; Event {SourceName, SourceType, Message, Date}; SourceType enum values include 'user' and 'acl'. The model fixes the members but not the message text, so the message form above is recorded behavior only.

## Steps to Reproduce
Boot the emulator and use a botocore memorydb client.
1. CreateUser(UserName=u, AccessString='on ~* +@all', AuthenticationMode={'Type':'password','Passwords':['Sim2realPassword-1']}); wait until the user is 'active'.
2. UpdateUser(UserName=u, AccessString='on ~app:* +@read'); wait until active.
3. CreateACL(ACLName=a); UpdateACL(ACLName=a, UserNamesToAdd=[u]); wait until the ACL is 'active'.
4. DescribeEvents(SourceType='acl', SourceName=a, StartTime=now-5m) and collect Events[*].Message.
   Expected: contains 'Create ACL <a> operation completed.' and 'Add user <u> to ACL <a> operation completed.'
   Actual: contains only 'ACL created' / 'ACL modified'; nothing names <u>.
5. UpdateACL(ACLName=a, UserNamesToRemove=[u]); wait active; DescribeEvents again.
   Expected: 'Remove user <u> from ACL <a> operation completed.'  Actual: another 'ACL modified'.
6. DeleteUser(UserName=u); DescribeEvents(SourceType='user', SourceName=u, StartTime=now-5m).
   Expected (newest first): 'Delete user <u> operation completed.', 'Modify user <u> operation completed.', 'Create user <u> operation completed.'
   Actual: 'User deleted', 'User modified', 'User created'.
