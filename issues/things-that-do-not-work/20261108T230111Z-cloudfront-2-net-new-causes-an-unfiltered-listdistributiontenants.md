# cloudfront: 2 net-new causes — an unfiltered ListDistributionTenants is refused InvalidArgument "Exactly one association filter must be set.", and a TrustedKeyGroups distribution's edge domain never admits a correctly signed cookie set

> _Note: this issue was identified against the code base at commit `6211fb78e0841381478152dba6893fe342be7489`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDistributionTenants

## Description
Two net-new root causes in the cloudfront emulator, found by replaying suite simparity-behavioral-aws-v1. Neither is marked ALREADY FILED (stub-blocked) nor OWNED by an open issue in the replay report. Both causes must be closed before submitting.

Cause 1 of 2: ListDistributionTenants with no AssociationFilter is refused instead of listing the account's tenants.
AWS: Smithy (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/smithy-model/com-amazonaws-cloudfront-cloudfront2020-05-31.json) models ListDistributionTenants with input members AssociationFilter (DistributionTenantAssociationFilter), Marker (string) and MaxItems (integer) — NONE of them @required — output members DistributionTenantList and NextMarker, errors AccessDenied (403), EntityNotFound (404), InvalidArgument (400), HTTP POST /2020-05-31/distribution-tenants -> 200, and @paginated {inputToken: Marker, outputToken: NextMarker, items: DistributionTenantList, pageSize: MaxItems}. A paginated listing whose every input member is optional is callable with NO arguments: AWS answers 200 with a DistributionTenantList holding every distribution tenant in the account (empty list when there are none), and AssociationFilter only NARROWS that list. Recorded behavior: the four checks below each call list_distribution_tenants() with no arguments as a positive control and the recording answers with a DistributionTenantList.
Emulator: every unfiltered call is refused 400 InvalidArgument with the message "Exactly one association filter must be set." In that message all of the text is emulator-authored fixed text — AWS has no such sentence for this operation, and there is no variable part. services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/list_distribution_tenants.rs lines 194-212 compute distribution_id/connection_group_id out of input.association_filter and return InvalidArgument(ONE_ASSOCIATION_FILTER_REQUIRED_MESSAGE) for every combination other than exactly-one-present, so the no-filter case (the default call) can never reach the store walk at lines 247-273, which already supports an unfiltered enumeration ordered by tenant id.
Why: a client that enumerates its tenants (console listing, pagination loop, cleanup/reaper, `aws cloudfront list-distribution-tenants`) is told its request is invalid and has nothing to correct — the parameter it is accused of omitting is optional in the model, so an SDK caller cannot satisfy the emulator without inventing a distribution id it does not yet know. It also makes the tenant API look wholly denied: three of the checks below use the unfiltered list purely as a positive control before exercising something else (tenant lifecycle, marker pagination, GetInvalidationForDistributionTenant's EntityNotFound), and all three abort at that control.
Fix: ListDistributionTenants' handler validation in services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/list_distribution_tenants.rs — treat an absent (or empty-valued) AssociationFilter as "no predicate" and enumerate every stored tenant through the existing ordered range walk, keeping the refusal only for a filter that names BOTH DistributionId and ConnectionGroupId; Marker/MaxItems handling must stay as-is so paging an unfiltered listing works.
Traces: cloudfront.op-contract-listDistributionTenants, cloudfront.distribution-tenant-lifecycle, cloudfront.list-distribution-tenants-pagination-consistent-ordering, cloudfront.op-contract-get-invalidation-for-distribution-tenant-not-found-rejected.

Cause 2 of 2: a Deployed distribution with a TrustedKeyGroups cache behavior never answers 200 to a correctly signed-cookie request at its edge domain, so the whole signed-cookie custom-policy contract is unreachable.
AWS: recorded behavior only for the data plane (CloudFront's edge is not a modeled API). The documented contract (https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-setting-signed-cookie-custom-policy.html) and the recording: with a distribution whose default cache behavior carries TrustedKeyGroups referencing a key group over an uploaded public key, a GET to the distribution DomainName carrying the three cookies CloudFront-Policy / CloudFront-Signature / CloudFront-Key-Pair-Id (CloudFront's own URL-safe base64 alphabet, '+'->'-', '='->'_', '/'->'~', signature over the exact policy bytes sent) for a wildcard-Resource custom policy whose DateLessThan is in the future is admitted with HTTP 200 and the origin object's exact bytes, for EVERY key under the policy's prefix; a request with no cookies is refused 403 with CloudFront's XML error document whose Code element is MissingKey; a request whose policy has expired is refused 403 with a different Code; and neither refusal returns any protected bytes. The fixed text here is the cookie names, the base64 alphabet and the error Code tokens; the variable parts are the distribution domain, the object keys, the policy's Resource/expiry and the key pair id, all taken from the request and the caller's own state.
Emulator: the check never gets past its FIRST data-plane assertion. It polls the signed GET for a 200 every 5 s for up to 180 s and no 200 ever arrives, so the harness kills the check at its 180 s cap ("Check timed out after 180.0s") before any refusal assertion runs. The control-plane setup (CreatePublicKey, CreateKeyGroup, CreateOriginAccessControl, CreateDistribution, S3 bucket/objects/policy) all succeeds, which localises this to the edge data plane, not to the signed-cookie admission logic alone.
Why: private content is a security contract. A client cannot verify that its signed cookies admit the right objects, and — worse — cannot verify that a missing or expired policy is REFUSED: nothing is served at all, so an integration test that expects the 403 MissingKey / expired-policy path passes vacuously or hangs, and an application built against the emulator never learns whether its trusted-key-group configuration actually protects anything. Every such check also consumes its full 180 s budget.
Fix: the emulator's CloudFront edge/data-plane request path — the component that resolves a request's Host (a distribution DomainName) to the Deployed distribution and serves its origin — and, once a request reaches it, the TrustedKeyGroups admission step for that distribution's cache behavior (signed-cookie policy/signature verification against the key group's public keys, and the 403 CloudFront XML error document for a missing or expired policy).
Traces: cloudfront.signed-cookies-custom-policy-admits-wildcard-and-expired-policy-refused. Related but NOT owning this check: open issue 20261027T001538Z-cloudfront-the-edge-data-plane-serves-nothing-so.md describes the same family of edge-serving gaps (field-level encryption and signed-cookie admission/expiry) and the many open "a Deployed distribution's edge domain answers nothing" issues (e.g. 20261102T102137Z-cloudfront-a-deployed-distribution-s-edge-domain-answers.md, 20261108T005735Z-cloudfront-a-deployed-distribution-s-edge-domain-still.md) carry neither this check's id nor its replay key; the replay report marked this check neither OWNED nor ALREADY FILED.
