# apigatewayv2__dynamodb__lambda: a $connect integration returning statusCode 403 never refuses the WebSocket handshake — the deployed WEBSOCKET stage answers no RFC 6455 upgrade at all (1 cause)

> _Note: this issue was identified against the code base at commit `0df9dc9e6fa18e0bd9ddfa393114d8e439af5a61`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
$connect (apigatewayv2 execute-api WebSocket data plane)

## Description
This issue carries ONE root cause. Cause 1 of 1 must be closed before submitting.

Cause 1 of 1: the execute-api data plane of a deployed apigatewayv2 WEBSOCKET stage never answers the opening RFC 6455 handshake, so the $connect authorization decision (admit on statusCode 200, refuse on statusCode 403) is never exercised and neither the admitted duplex round trip that brackets it nor the refusal itself can be observed. Failing check id: apigatewayv2__dynamodb__lambda.wsduplex-connect-denial-rejects-handshake.

AWS: recorded behavior only for the wire sequence — the opening handshake, route selection and frame routing are the execute-api data plane, not modelled operations. Model facts used (apigatewayv2, services/service-com-amazonaws-apigatewayv2-apigatewayv2/smithy-model/com-amazonaws-apigatewayv2-apigatewayv2.json): Api.ProtocolType is an enum with values [WEBSOCKET, HTTP] and is @required; Api.RouteSelectionExpression is @required and selects the route from the frame; Api.ApiEndpoint is documented as '{api-id}.execute-api.{region}.amazonaws.com' with the stage name appended to form the deployed stage path; Api.DisableExecuteApiEndpoint gates that default endpoint. Push-back is ApiGatewayManagementApi PostToConnection (POST /@connections/{ConnectionId}, restJson1).

What the recording requires, in two classes:
(a) Admitted handshake: a handshake against the deployed stage path is answered 'HTTP/1.1 101 Switching Protocols' with a Sec-WebSocket-Accept header derived from the client's Sec-WebSocket-Key; $connect is invoked with requestContext.connectionId / requestContext.domainName / requestContext.stage and with queryStringParameters carrying the request's query string; the integration returning {"statusCode": 200} admits the socket; a subsequent client TEXT frame (opcode 0x1) is routed to $default, which writes its row and pushes back via PostToConnection on the same socket.
(b) Refused handshake (the behavior under test): the same API, same stage, with query parameter deny=1, so $connect returns {"statusCode": 403, "body": "denied"}. AWS then refuses the upgrade: the handshake response status is HTTP 403 (not 101), the response carries NO Sec-WebSocket-Accept header, the response body is the $connect integration's own body bytes (here exactly b'denied' — the body is whatever the integration returned, the fixed requirement is that the integration's body is what the client receives and not a gateway-synthesised one), and the socket is then torn down. The integration nonetheless RAN and was given a connection id (its denied# row carries a non-empty connectionId), no admitted connection exists for that handshake, a frame written into the refused socket never reaches $default, and the refusal is connection-scoped: the socket admitted before it still round-trips, and a fresh un-denied handshake on the same stage still upgrades to 101. Status 403, the absence of Sec-WebSocket-Accept, and the body being the integration's body are the fixed requirements; the markers, generated api id, stage name, connection id and sha256 digests in the recording are per-run values.

Emulator: no handshake response is produced on the deployed stage at all. The check blocks in its first handshake poll — _poll_until(lambda: _try_marked_connect(ctx, api, allow_marker, deny=False), lambda s: s is not None, timeout_s=150.0, description=f"WebSocket handshake against stage {api['stage']}") — which only returns a socket once the response line contains ' 101 '. It is cut by the harness cap and reported as [mismatch] 'Error: Check timed out after 60.0s'. The control-plane setup ahead of it (CreateApi ProtocolType=WEBSOCKET, AWS_PROXY integration on the Lambda, $connect/$disconnect/$default routes, lambda AddPermission, CreateDeployment, CreateStage, DynamoDB table) completed, so the divergence is squarely the absence of any upgrade answer on the stage endpoint. Because nothing ever upgrades, the emulator produces neither the 403 refusal, nor the integration body, nor the denied# evidence that $connect ran, nor the absence-of-$default evidence.

Why: a client relying on $connect authorization gets no answer instead of a decision. wss:// never upgrades, so $connect/$default/$disconnect never fire and nothing is written downstream; and critically, an emulator that never completes a handshake is indistinguishable from one that ignores the $connect status code entirely — a caller cannot tell an over-permissive gateway (admits a connection its $connect refused with 403) from a correctly refusing one. Instead of a wrong status the client gets an indefinite wait, so client-side connect-time authorization and its error handling are untestable.

Fix: the execute-api data-plane front door plus the apigatewayv2 WebSocket session layer — recognise the RFC 6455 upgrade on a deployed WEBSOCKET API's stage path and answer 101 + Sec-WebSocket-Accept; mint a connection id and invoke $connect with requestContext.connectionId/domainName/stage and queryStringParameters; then honour the integration's returned statusCode at the handshake boundary: on a non-2xx (403 here) answer the handshake with that HTTP status, omit Sec-WebSocket-Accept, write the integration's response body, close the socket, register no connection, and route no subsequent bytes from that socket to any route; on 2xx complete the upgrade and route frames through the route-selection expression, firing $disconnect on close.
