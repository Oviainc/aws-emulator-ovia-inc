# ECR Public: PutRepositoryCatalogData mints logoUrl on the real AWS host public.ecr.aws instead of the emulator's own host, so the minted logo URL is unreachable for any client of the emulator

> _Note: this issue was identified against the code base at commit `5252be52e0cc9f5d73bee5aa197523afb271707f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutRepositoryCatalogData

## Description
Behavioral replay of simparity-behavioral-aws-v1 (85/92 passed; ecr-public 84/91 with 7 failures) leaves ONE net-new root cause after excluding the 5 checks the report marked OWNED by an open issue. The emulator IS serving (PutRepositoryCatalogData/GetRepositoryCatalogData answer 200) and ecr-public is bootstrapped (service-com-amazonaws-ecrpublic-spencerfrontendservice, with no pending bootstrap issues), so this is a fidelity finding, not a bootstrap gap.

NOTE on overlapping open issues: 20261107T170252Z-ecr-public-the-logoimageblob-accepted-by-putrepositorycatalogdata-is.md (and cause 2 of 20261023T055032Z-ecr-public-getauthorizationtoken-is-not-authorization-gated-stored.md) describe the same two checks failing one leg LATER — they recorded the minted URL as pointing at the emulator's own published host and answering HTTP 404. The emulator's behavior has since changed: the URL is now rejected by the harness before any fetch happens because its HOST is the real AWS gallery host, so the replay report no longer binds these checks to those issues and the current keys are filed here. Fixing the hosting leg described there is necessary but not sufficient: the URL must also be minted on the emulator's own address, which is what this issue is about. Re-replay both checks listed below after either fix.

=== Cause 1 of 1: the logoUrl the service mints points at the public AWS gallery host rather than at an address the emulator itself answers on ===
AWS: Smithy RepositoryCatalogDataInput.logoImageBlob is a blob with @length 0..512000, documented "The base64-encoded repository logo payload", and is INPUT-only — the output shape RepositoryCatalogData models no logoImageBlob and instead carries logoUrl -> ResourceUrl (string, @length 0..2048), documented "The URL that contains the logo that's associated with the repository." The uploaded bytes therefore become a hosted asset and the minted URL is the ONLY way a client can observe them. Recorded behavior only for the hosting leg (it is outside the modeled API surface): on real AWS the minted URL is a URL of the service that served the API call, and an anonymous GET of it answers 200 with the byte-identical uploaded payload and Content-Type image/png. The requirement for an emulator is therefore that the URL it publishes be an address the emulator answers on — http(s)://<its own host>:<its port>/<resource path> — never a hard-coded aws.com host; the path component and the asset hash are free, per-run values.
Emulator: PutRepositoryCatalogData accepts the blob and GetRepositoryCatalogData reports a logoUrl whose host is the literal public AWS host, of the general form https://public.ecr.aws/logos/<repositoryName>/<assetHash>. No part of that URL is reachable from a client of the emulator: the harness's published-URL check rejects it ('its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener'), and routing the fetch raises simparity.published.PublishedUrlRejected before any request is issued. Because the URL is unusable, every downstream leg stays unverified: byte identity of the served PNG, Content-Type image/png, a refused undersized blob leaving the stored asset and URL intact, and an accepted replacement blob minting a new URL that serves the new bytes.
Why: logoImageBlob is echoed in no response, so dereferencing the minted logoUrl is the only way a client can confirm the logo was stored or render it. A client that uploads a logo and then verifies or displays it (a gallery preview, a publish pipeline, an IaC post-condition) is handed a URL that points at the real internet instead of the emulator: against the emulator it either fails to resolve/connect, or — worse — silently reaches real public.ecr.aws and reads an unrelated (or absent) asset, so a test can pass or fail for reasons entirely outside the emulated account. The API call reports success with a well-formed URL, so the defect only surfaces at the HTTP fetch, far from the call that caused it.
Fix: the logoUrl minting in the PutRepositoryCatalogData handler (and whatever GetRepositoryCatalogData reads it back from in the repository-catalog state) must build the URL from the emulator's own advertised scheme/host/port rather than a compiled-in public.ecr.aws base, and the emulator's HTTP front door must claim that logo path and serve the stored bytes with the image content type; a replacement blob must mint a distinct URL on the same own-host base, and a refused blob must leave the stored bytes and the existing logoUrl unchanged.
Traces: ecr-public.catalog-logo-blob-is-stored-and-served-as-a-real-image, ecr-public.repository-catalog-data-base64-logo-round-trip.
