# EMR: 2 net-new root causes — GetClusterSessionCredentials refuses every cluster as having no runtime roles, and a Spark step that fails in the driver never settles or produces gzipped step logs (2 causes)

> _Note: this issue was identified against the code base at commit `5378a66c6079b2af7ea00e2980dbc1f9f47fc08b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetClusterSessionCredentials

## Description
This issue bundles 2 net-new root causes in the EMR (elasticmapreduce) crate. Both are grounded in failing behavioral checks of suite simparity-behavioral-aws-v1 that no open issue carries: the replay report marked neither as ALREADY FILED nor as OWNED by an existing issue. Related open issues are named per cause below; none of them carries these check ids or these causes.

--- Cause 1 of 2: GetClusterSessionCredentials never issues credentials — it refuses EVERY existing cluster with the "no runtime roles" sentence, including a cluster created with a security configuration that enables application-scoped IAM roles ---
AWS: Smithy (services/service-com-amazonaws-emr-elasticmapreduce/smithy-model/com-amazonaws-emr-elasticmapreduce.json): GetClusterSessionCredentials takes ClusterId (XmlStringMaxLen256, required) and ExecutionRoleArn (ArnType, len 20..2048) and returns, on HTTP 200, Credentials (union com.amazonaws.emr#Credentials with member UsernamePassword -> structure UsernamePassword{Username, Password}, both sensitive) plus ExpiresAt (timestamp). Its only modeled client error is InvalidRequestException (HTTP 400); the operation's own documentation says it "Provides temporary, HTTP basic credentials that are associated with a given runtime IAM role and used by a cluster with fine-grained access control activated." On AWS, a cluster launched with a SecurityConfiguration whose AuthorizationConfiguration.IAMConfiguration.EnableApplicationScopedIAMRole is true and whose EncryptionConfiguration enables in-transit encryption IS fine-grained-access-control activated, so the call succeeds: it returns a non-empty Username and Password, a DIFFERENT Username for a different ExecutionRoleArn, and the SAME Username when the same ExecutionRoleArn is requested again. The "You haven\u2019t enabled runtime roles or IAM Identity Center for your cluster in its security configuration." refusal is reserved for a cluster whose security configuration enables neither.
Emulator: the handler never looks at the cluster's stored security configuration at all. services/service-com-amazonaws-emr-elasticmapreduce/src/ops/get_cluster_session_credentials.rs resolves the cluster and then UNCONDITIONALLY returns HTTP 400 InvalidRequestException with the message "You haven\u2019t enabled runtime roles or IAM Identity Center for your cluster in its security configuration." (crate::state::runtime_roles_not_enabled_message()), as the module's own doc comment states ("this emulator enables neither on any cluster"). In that message the whole sentence is fixed text — it carries no value from the request or from state; the diverging part is that it is served for a cluster that DOES enable runtime roles, where AWS answers 200 with a Credentials union. The check retries the call (its helper swallows every exception and retries for 180 s), so the replay reports only `Error: Check timed out after 60.0s` — the emulator answered every call, always with the same refusal, and never once with credentials.
Why: a client doing interactive workload submission against an FGAC cluster (JDBC/HTTP-basic connections to Livy/Presto/Trino endpoints, EMR Studio runtime-role submission) can never obtain a username/password. The refusal is indistinguishable from a genuinely mis-configured cluster, so the caller is told to fix a security configuration that is already correct, and no test of per-execution-role credential scoping (distinct username per role, stable username per role) can run.
Fix: the GetClusterSessionCredentials handler and the cluster state it reads (services/service-com-amazonaws-emr-elasticmapreduce/src/ops/get_cluster_session_credentials.rs plus the SecurityConfiguration record in services/service-com-amazonaws-emr-elasticmapreduce/src/state.rs): decide the refusal from the cluster's stored security configuration instead of returning it always, and on an FGAC-enabled cluster return Credentials.UsernamePassword with a non-empty Username derived deterministically from (ClusterId, ExecutionRoleArn) and a non-empty Password, plus ExpiresAt. The existing refusal must stay for a cluster whose security configuration enables neither runtime roles nor IAM Identity Center.
Traces: emr.get-cluster-session-credentials-returns-scoped-credentials. (The sibling check emr.get-cluster-session-credentials-without-execution-role-denied is OWNED by 20261104T102001Z-emr-8-net-new-root-causes-createvpcendpoint-refuses.md and is a different, blocked cause; no open issue covers the always-refused positive path.)

--- Cause 2 of 2: a Spark step that raises in its driver never reaches a terminal StepState, and no gzipped step logs are written under the cluster's LogUri ---
AWS: Smithy: StepState is PENDING | CANCEL_PENDING | RUNNING | COMPLETED | CANCELLED | FAILED | INTERRUPTED, and StepTimeline carries CreationDateTime, StartDateTime and EndDateTime. Recorded behavior only for the log layout (the step payload is opaque to the model): a `command-runner.jar spark-submit` step whose driver raises ends FAILED while a preceding control step ends COMPLETED (ActionOnFailure=CONTINUE, StepConcurrencyLevel=1 keeps them sequential), and EMR's log-push agent delivers that step's log directory under `<LogUri>/<cluster-id>/steps/<step-id>/` holding exactly controller.gz, stderr.gz and stdout.gz (gzip-compressed), with the driver's Python traceback and the non-zero exit visible in the failed step's logs and no traceback plus a zero exit in the control step's. The failed step writes no output under its output prefix.
Emulator: both steps stay non-terminal. The check polls DescribeStep for a state in {COMPLETED, FAILED, CANCELLED, INTERRUPTED} and is killed by its own budget: `TimeoutError: both steps on cluster j-0000000000001 reaching a terminal state: the run budget ended first; not graded` (raised from _poll_until). Nothing downstream is reachable, so the step-log directory under `<LogUri>/<cluster-id>/steps/<step-id>/` is never created and no controller.gz/stderr.gz/stdout.gz ever appears.
Why: a client that submits a failing Spark step and then diagnoses it the standard way — wait for FAILED, read stderr.gz out of S3, find the driver traceback — blocks forever and finds an empty log prefix, while the control plane keeps reporting the step as non-terminal. Failure classification (FAILED vs COMPLETED) and log-based debugging are both unreachable.
Fix: the EMR crate's step scheduler / cluster state machine and its log-delivery path (the state behind services/service-com-amazonaws-emr-elasticmapreduce/src/ops/add_job_flow_steps.rs, run_job_flow.rs, describe_step.rs and list_steps.rs): drive each submitted step PENDING -> RUNNING -> a terminal StepState with a populated StepTimeline, and write the step's gzipped controller/stderr/stdout objects under the configured LogUri through the S3 service state.
Traces: emr.failed-spark-step-driver-traceback-in-gzipped-s3-step-log-fails. The open issue 20261029T184212Z-emr-clusters-accept-steps-but-never-execute-them.md describes the same family of defect but does not carry this check id or its replay key (its Issue-Trace-Ids list this check nowhere), and it does not cover the per-step gzipped step-log directory contract (controller.gz/stderr.gz/stdout.gz under `<LogUri>/<cluster-id>/steps/<step-id>/`) or the FAILED-vs-COMPLETED driver-failure classification; 20261029T175551Z-glue-job-runs-reached-through-the-emr-glue.md and the EMR Serverless execution issues concern other services.
