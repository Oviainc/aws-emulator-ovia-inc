# snow-device-management: the account-level "no devices in this region" gate is absent (fabricated device inventory, 404 instead of 403), CreateTask empty-targets rejection class is wrong, and the ListTasks enum message lists the wrong value order (4 causes)

> _Note: this issue was identified against the code base at commit `37e4b54b7f2f231778aa0090f22742466dbbad1b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListDevices, ListTasks, DescribeDevice, DescribeTask, CreateTask, CancelTask

## Description
Four distinct root causes in the emulated Snow Device Management service, all grounded in failing behavioral checks of this suite. None of them is an unimplemented-stub failure (those checks — CreateRole, ListTagsForResource, DescribeDeviceEc2Instances, TagResource, UntagResource — are already filed separately and are excluded here). No open issue mentions snow-device-management (list_existing_issues query 'snow' / 'snowdevicemanagement' returns nothing).

=== Cause 1 of 4: the list/read APIs serve a fabricated device inventory instead of the account-level device gate ===
AWS: for an account that has no Snow device with Snow Device Management activated in the region, ListDevices and ListTasks are refused, not answered: the recorded responses are AccessDeniedException (Smithy: ListDevices and ListTasks both declare AccessDeniedException, com.amazonaws.snowdevicemanagement#AccessDeniedException, @httpError 403) with the message "No devices found in this region." — a service-level precondition, distinguishable from an IAM implicit deny because the message names device/region availability rather than "is not authorized to perform". The account-level gate fires ahead of any per-resource lookup and is stable over time (it is a precondition, not a transient error). Recorded behavior supplies the message text; the model only supplies the error and its 403 status.
Emulator: ListDevices returns HTTP 200 with a device the caller never created — devices: [{managedDeviceId: smd-00000000000000000, managedDeviceArn: arn:aws:snow-device-management:…:managed-device/smd-…, associatedWithJob: JID…}] plus a nextToken. The handler seeds a synthetic inventory (store.ensure_seeded(&region, now)) and then enumerates it, so no gate is ever consulted. The same happens for a request carrying a syntactically bogus jobId filter ("not a valid job id!!"), which AWS also answers with the gate, and the success repeats on every sample across ~15 seconds.
Why: a client of an account in this state sees a managed device that does not exist. Code written against AWS either never reaches its error path (it expects 403 AccessDeniedException and gets 200) or proceeds to operate on a device id that no later operation can honour, and negative-path/retry logic keyed on the gate is never exercised.
Fix: the ListDevices and ListTasks handlers plus the service's state seeding — the account/region precondition must be modelled in state (an account with no activated devices must have an EMPTY inventory and must answer the gate), instead of unconditionally seeding a device at request time.
Traces: snow-device-management.account-device-gate-blocks-all-reads (ListDevices SUCCEEDED and returned devices/nextToken where a ClientError was expected), snow-device-management.list-devices-param-validation ("expected list_devices to be denied, but it succeeded"), snow-device-management.service-gate-error-stable-not-flaky (4 samples, all with no error at all: [(None, None) x4]). Code: services/service-com-amazonaws-snowdevicemanagement-snowdevicemanagement/src/ops/list_devices.rs:182 (ensure_seeded) and :185-214 (page built from the seeded store).

=== Cause 2 of 4: per-resource and invoke APIs answer 404 ResourceNotFoundException where AWS answers the 403 account gate ===
AWS: on the same gated account, DescribeDevice, DescribeTask, CreateTask and CancelTask against a well-formed but non-existent id are refused by the account-level gate BEFORE any per-resource existence check — recorded code AccessDeniedException (Smithy: declared on all four operations, @httpError 403) with message "No devices found in this region.". Ordering is part of the contract: the gate precedes id resolution, so the caller never learns whether the specific id exists. The refusal is deterministic — identical repeated calls and 8 concurrent CreateTask calls against the same target all produce the identical code and message.
Emulator: these operations skip the gate and report the per-resource lookup against the synthetic store, answering 404 ResourceNotFoundException (Smithy: @httpError 404) — e.g. 'managed-device mdev-sim2real-ghost-70d421d7da1a not found' for CreateTask/DescribeDevice and 'task sim2real-ghost-task-5184fd4b0538 not found' for CancelTask. Under 8 concurrent CreateTask calls all 8 answered ResourceNotFoundException.
Why: the rejection class and HTTP status both differ (404 vs 403). A client distinguishing "my account is not enabled for Snow Device Management in this region" from "that device/task id does not exist" takes the wrong branch, and the inverted ordering leaks per-id existence information AWS does not disclose on a gated account.
Fix: the account-level gate belongs ahead of the per-resource lookup in the DescribeDevice / DescribeTask / DescribeExecution / ListDeviceResources / ListExecutions / CreateTask / CancelTask handlers (a shared precondition check in the service's state module, consulted before id resolution).
Traces: snow-device-management.create-task-device-gate-precedes-validation, snow-device-management.create-task-concurrent-calls-consistent-gate, snow-device-management.cancel-task-device-gate-and-idempotency, snow-device-management.tag-apis-bypass-device-gate-notfound (its positive control: describe_device -> ('ResourceNotFoundException', 'managed-device … not found')). Code: src/ops/create_task.rs:196-203 (target existence check with no preceding gate), src/ops/create_task.rs:177 (ensure_seeded).

=== Cause 3 of 4: CreateTask with an empty targets list is answered with ValidationException instead of the recorded UnauthorizedException ===
AWS: with botocore parameter validation disabled so the request reaches the wire, CreateTask carrying targets=[] is answered with error code UnauthorizedException and message "Unauthorized" — the generic front-door denial, emitted BEFORE either shape validation or the account-level gate. Recorded behavior only: UnauthorizedException is not a shape in this service's Smithy model (modelled CreateTask errors are AccessDeniedException, ResourceNotFoundException, ServiceQuotaExceededException, ThrottlingException, plus common InternalServerException/ValidationException). Hypothesis: the request with no targets fails an upstream authorization/routing step that never reaches the service's modelled validation. The model does carry the bound it is being confused with: CreateTaskInput.targets is @required with @length min 1, max 10 — and the OVERSIZED case (11 targets) is indeed ValidationException, so the two cases are different classes and must not share one path.
Emulator: 400 ValidationException, message "1 validation error detected: Value '0 items' at 'targets' failed to satisfy constraint: Member must have length greater than or equal to 1" — i.e. the generic min-length constraint check runs where AWS answers UnauthorizedException.
Why: a client that handles the empty-targets case sees a different error code (and a retriability/credentials signal rather than a request-shape signal) than AWS gives, so error-class branching and alarming diverge. The check also stops here, leaving the oversized-targets ValidationException message and the subsequent gate assertion unverified in the same check.
Fix: CreateTask's request-handling order — the empty-targets rejection must be emitted as the recorded UnauthorizedException ahead of the length-constraint validation, in the CreateTask handler/validation layer; min-length of targets must not be the thing that answers it.
Traces: snow-device-management.create-task-input-validation-bounds-and-command (AssertionError: ('ValidationException', "1 validation error detected: Value '0 items' at 'targets' …") where UnauthorizedException/'Unauthorized' was expected). Code: src/ops/create_task.rs (centralized deserialize → validate → handle walk; CREATE_TASK_INPUT_SCHEMA constraint check at :149).

=== Cause 4 of 4: the ListTasks state-enum ValidationException message lists the enum value set in the wrong order ===
AWS: ListTasks with state outside TaskState is rejected with ValidationException (Smithy: ValidationException is a common error, @httpError 400) and the message is built from the request and the member's constraint; the recorded message enumerates the value set as "1 validation error detected: Value 'BOGUS_STATE' at 'state' failed to satisfy constraint: Member must satisfy enum value set: [IN_PROGRESS, COMPLETED, CANCELED]". The ORDER of the listed values is recorded behavior only — note the Smithy model declares TaskState as [IN_PROGRESS, CANCELED, COMPLETED], so the model's declaration order is NOT the order AWS prints.
Emulator: same status and same error code (ValidationException — that part matches), but the message prints the model declaration order: "… Member must satisfy enum value set: [IN_PROGRESS, CANCELED, COMPLETED]".
Why: lowest-impact cause of this bundle — status and code agree, so only a consumer that compares the rendered enum-set text (as the recorded AWS behavior for this member does) sees a difference. Filed because the message here is request-derived and constraint-derived, so its content is a rule rather than incidental text; the diverging part is the value ordering only.
Fix: the enum-set rendering used by the shared constraint-validation message builder for this service (ListTasks state member) must emit the service's recorded value order rather than the model's declaration order.
Traces: snow-device-management.list-tasks-state-filter-validation (AssertionError on the message; the same check's second half — state=IN_PROGRESS surfacing the AccessDeniedException gate with 'No devices found in this region.' — is Cause 1/2 above and was never reached).
