# AgentCore data-plane invocation unserved: InvokeCodeInterpreter and InvokeHarness answer UnknownService, and GetMemoryRecord/StopRuntimeSession/InvokeAgentRuntime/StartBatchEvaluation answer NotImplemented instead of the modeled refusal

> _Note: this issue was identified against the code base at commit `7240e32f2500d20910730c71d4ad0714ff1f3217`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
InvokeCodeInterpreter

## Description
Three net-new causes, all in the bedrock-agentcore data plane: two tool-invocation operations are not routed at all (the emulator answers a service-level 'UnknownService' error rather than the operation), and a group of data-plane operations answers 501 NotImplemented, which means the authorization-refusal class (AccessDeniedException) those operations must produce for an unauthorized principal is never reachable.

Cause 1 of 3: InvokeCodeInterpreter is not routed — the request is answered with an UnknownService error naming the whole service.
AWS: Smithy: InvokeCodeInterpreter POST /code-interpreters/{codeInterpreterIdentifier}/tools/invoke, @http code 200; input name: ToolName (required enum), arguments: ToolArguments, sessionId bound to header x-amzn-code-interpreter-session-id; output stream: CodeInterpreterStreamOutput is @httpPayload @required @streaming (an AWS event stream whose success member is result: CodeInterpreterResult {content required, structuredContent, isError}). Modeled errors are AccessDeniedException(403), ConflictException(409), ResourceNotFoundException(404), ServiceQuotaExceededException(402), ThrottlingException(429), ValidationException(400), InternalServerException(500) — there is no modeled outcome in which a live session answers with an unknown-service error.
Emulator: every InvokeCodeInterpreter call in this suite fails with botocore ClientError code 'UnknownService', message 'no emulated service is registered for 'bedrock-agentcore'' — even though the immediately preceding StartCodeInterpreterSession on the SAME client and endpoint succeeded. So the dispatcher resolves other bedrock-agentcore operations but fails to resolve this one's method+URI, and reports the failure as if the whole service were absent.
Why: every use of a code interpreter — executeCode, executeCommand, readFiles, writeFiles, removeFiles, listFiles, startCommandExecution/getTask/stopTask — goes through this one operation, so a client can start a session and then do nothing with it. Because the reply is not even a modeled service error, SDK error handling (retry classification, ResourceNotFoundException/ValidationException branches) never sees a usable code, and sandbox guarantees a client depends on (path-escape rejection, per-session filesystem isolation, filesystem persistence across calls in a session) cannot be exercised at all.
Note: the open issue 20261029T170914Z-bedrock-agentcore-code-interpreter-tool-invocation-unserved-and-session-status.md reports the WIRE-side form of an unserved InvokeCodeInterpreter (404 application/x-amz-json-1.1 with no event stream). It is plausibly the same root cause seen through a different corpus; it does not carry any of the behavioral check ids below, so they are filed here. If a fixer closes that issue, these checks must still be replayed.
Fix: InvokeCodeInterpreter's routing + handler + event-stream serializer (services/service-com-amazonaws-bedrockagentcore-amazonbedrockagentcore/src/ops/invoke_code_interpreter.rs and the service's request router): bind POST /code-interpreters/{codeInterpreterIdentifier}/tools/invoke, resolve the session from the x-amzn-code-interpreter-session-id header against started-session state, execute the named ToolName against that session's sandbox state, and emit CodeInterpreterStreamOutput as an application/vnd.amazon.eventstream 'result' event.
Traces: bedrock-agentcore.invoke-code-interpreter-sandbox-isolation, bedrock-agentcore.invoke-code-interpreter-clear-context-resets-the-namespace, bedrock-agentcore.agc-code-interpreter-file-tool-path-escape-rejected, bedrock-agentcore.agc-code-interpreter-file-tools-share-one-sandbox-filesystem, bedrock-agentcore.agc-code-interpreter-filesystem-isolated-across-sessions, bedrock-agentcore.code-interpreter-async-task-converges-and-stop-task-cancels, bedrock-agentcore.e2e-code-interpreter-side-effect-persistence.

Cause 2 of 3: InvokeHarness is not routed — same UnknownService answer.
AWS: Smithy: InvokeHarness POST /harnesses/invoke, @http code 200; required input harnessArn (httpQuery), runtimeSessionId (header X-Amzn-Bedrock-AgentCore-Runtime-Session-Id, length 33-100), messages: HarnessMessages; output stream: InvokeHarnessStreamOutput is @httpPayload @required @streaming. Modeled errors: AccessDeniedException(403), ResourceNotFoundException(404), RuntimeClientError(424), ServiceQuotaExceededException(402), ThrottlingException(429), ValidationException(400), InternalServerException(500).
Emulator: ClientError code 'UnknownService', message 'no emulated service is registered for 'bedrock-agentcore'' when calling InvokeHarness, on the same client that successfully reaches other bedrock-agentcore operations.
Why: the managed agent-loop surface is completely unavailable, and the failure does not look like any modeled error, so a client cannot distinguish 'harness does not exist' from 'service not reachable' and no streamed orchestration result is ever produced.
Fix: InvokeHarness's routing + handler + event-stream serializer (src/ops/invoke_harness.rs plus the router binding for POST /harnesses/invoke).
Traces: bedrock-agentcore.invoke-harness-managed-orchestration-result.

Cause 3 of 3: unauthorized and ordinary calls alike are answered with error code NotImplemented, so the AccessDeniedException refusal class is unreachable on GetMemoryRecord, StopRuntimeSession, InvokeAgentRuntime and StartBatchEvaluation.
AWS: Smithy: AccessDeniedException is modeled @httpError 403 on these operations, with a single message member. AWS's message for an identity-based denial is the standard IAM template: fixed text 'User: ' + the caller's principal ARN + ' is not authorized to perform: ' + '<service>:<Action>' + ' on resource: ' + the target resource ARN + ' because no identity-based policy allows the ' + '<service>:<Action>' + ' action' — the fixed text is that template; the variable parts are the assumed-role principal ARN (from the signing credentials), the action name (the operation), and the resource ARN (from the request). Once the caller IS authorized, these operations must reach resource lookup and answer their modeled 404 (recorded behavior: GetMemoryRecord 'MemoryItem does not exist'; InvokeAgentRuntime "No endpoint or agent found with qualifier 'DEFAULT' for agent '<runtimeArn>'"). A duplicate-name StartBatchEvaluation pair must both succeed with distinct ids (recorded behavior only).
Emulator: each of these calls returns error code 'NotImplemented' (the scaffold stub's 501), both for the restricted principal and for the fully-permitted control, so no authorization decision is made and no modeled error class is produced. Observed: expected AccessDeniedException, got NotImplemented (GetMemoryRecord, InvokeAgentRuntime twice, StopRuntimeSession); expected two successful concurrent StartBatchEvaluation starts, got [('error','NotImplemented'), ('error','NotImplemented')].
Why: a client that relies on AWS refusing a cross-tenant or unpermitted call gets an error code that is not in the model, cannot classify it (not retryable, not a permission problem, not a 404), and any authorization test or least-privilege validation against the emulator silently reports the wrong outcome; the permitted path is equally unavailable.
Note: the stub for InvokeAgentRuntime is already filed as 20261023T113357Z-bedrock-agentcore-invokeagentruntime-stub.md and the StartBatchEvaluation stub was auto-filed by this suite run; those issues cover IMPLEMENTING the operations. What is recorded here is that the suite's authorization checks and the duplicate-name concurrency check are blocked on them and must be replayed once they answer, and that GetMemoryRecord and StopRuntimeSession show the same 501.
Fix: the handlers/validation of GetMemoryRecord, StopRuntimeSession, InvokeAgentRuntime and StartBatchEvaluation (src/ops/get_memory_record.rs, src/ops/stop_runtime_session.rs, src/ops/invoke_agent_runtime.rs, src/ops/start_batch_evaluation.rs) plus the shared sigv4 principal/authorization layer that must emit AccessDeniedException(403) with the IAM message template before resource lookup.
Traces: bedrock-agentcore.get-memory-record-cross-tenant-read-denied, bedrock-agentcore.invoke-agent-runtime-cross-tenant-denied, bedrock-agentcore.invoke-agent-runtime-missing-permission-denied, bedrock-agentcore.stop-runtime-session-unauthorized-denied, bedrock-agentcore.start-batch-evaluation-duplicate-name-both-succeed.
