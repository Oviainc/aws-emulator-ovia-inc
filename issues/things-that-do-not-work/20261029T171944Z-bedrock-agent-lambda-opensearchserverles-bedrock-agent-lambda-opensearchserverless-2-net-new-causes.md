# bedrock-agent__lambda__opensearchserverless: 2 net-new causes — the OpenSearch Serverless collection endpoint answers 400 SerializationException 'missing required header x-amz-target' so no knowledge base can be provisioned, and `aws lambda invoke` is refused NotImplemented so the Bedrock IAM boundary is unobservable

> _Note: this issue was identified against the code base at commit `d7c92a359e65b119da339df847b0735e9ef403e3`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateIndex

## Description
TWO net-new root causes reached through the cross-service bedrock-agent + lambda + opensearchserverless checks (service token taken from the leading segment of the check ids).

=== Cause 1 of 2: a VECTORSEARCH collection's published collectionEndpoint serves the AWS-JSON RPC dispatcher instead of the OpenSearch REST data plane ===
AWS: recorded behavior only (a collection's data plane is the OpenSearch REST API and is not described by the opensearchserverless Smithy model, which covers the control plane). Recorded behavior: once a VECTORSEARCH collection is ACTIVE, BatchGetCollection publishes a collectionEndpoint, and a SigV4-signed (service name `aoss`) `PUT https://<collectionEndpoint>/<indexName>` carrying a knn_vector mapping — exactly the request opensearch-py's `indices.create` issues, with NO `x-amz-target` header, because the OpenSearch REST API has no RPC target — is accepted when the collection's data-access policy names the calling principal, and refused (403) when it does not. That accepted index is the precondition for bedrock-agent CreateKnowledgeBase's OPENSEARCH_SERVERLESS storageConfiguration.
Emulator: the request is answered HTTP 400 with body `{"__type":"SerializationException","message":"missing required header `x-amz-target`"}` — the published endpoint is wired to the emulator's AWS-JSON protocol front door, which requires an `X-Amz-Target` header. No OpenSearch REST verb is servable on a collection endpoint, for ANY principal.
Why: two things are lost. (a) No knowledge base can be provisioned, so the Lambda-driven Retrieve / RetrieveAndGenerate data-plane flows are unreachable. (b) The data-access-policy boundary this cluster exists to prove is unobservable: the permitted principal and the unpermitted one get the same 400 SerializationException, so 'allowed' and 'denied' are indistinguishable — the negative check cannot tell a policy denial from a protocol error.
Fix: the opensearchserverless collection data plane — route the published collectionEndpoint host to an OpenSearch REST handler (index create/get/delete, document index/search) that authorises SigV4 `aoss` requests against the collection's data-access policy, instead of letting the host fall through to the AWS-JSON `x-amz-target` dispatcher (services/service-com-amazonaws-opensearchserverless-opensearchserverless, plus the emulator's host/endpoint routing table that resolves collection endpoints). The same wall is reported under the bedrock-agent and bedrock-agent-runtime service tokens in their own issues.
Traces: bedrock-agent__lambda__opensearchserverless.deploy-opensearchserverless-collection-data-access-policy-positive and .deploy-stack-missing-opensearchserverless-data-access-negative (both surface the 400 directly from `_create_vector_index`); .lambda-bedrock-agent-retrieve-and-generate-positive and .lambda-bedrock-agent-retrieve-knowledge-base-positive (both reported as 'Check timed out after 60.0s' because their `_build_ready_knowledge_base` setup retries the same failing index create; they are additionally blocked by Cause 2 once they get past it).

=== Cause 2 of 2: `aws lambda invoke` of a real deployment package is refused 501 NotImplemented, so the bedrock:InvokeAgent permission boundary is never reached ===
AWS: recorded behavior only for the runtime (Smithy models Invoke's success and its error set, not the execution). Recorded behavior: `aws lambda invoke --function-name <fn> --payload <file> out.json` runs the function's python3.12 deployment package and writes the handler's payload; the handler then calls bedrock-agent-runtime InvokeAgent and the response distinguishes 403 AccessDeniedException (role lacks bedrock:InvokeAgent) from 404 ResourceNotFoundException (role has it, but the agent id does not exist) — that pair is what proves the IAM boundary.
Emulator: the CLI exits rc=254 with `An error occurred (NotImplemented) when calling the Invoke operation: Invoke resolved arn:aws:lambda:<region>:<account>:function:<name> at version $LATEST, but running its python3.12 deployment package is not implemented in this emulator: there is no in-process runtime for it, and no response payload is returned that the function did not produce.`
Why: the function body never executes, so no AccessDenied-vs-NotFound verdict is ever produced and the permission boundary is untested. NOTE for the fixer: the open issue 20261022T213144Z-lambda-invoke-refuses-every-real-invocation-with-notimplemented.md describes the same NotImplemented refusal and the replay suite marked the SDK-path siblings of this check as owned by it; this check was NOT marked owned (it reaches Invoke through the AWS CLI, so its replay key differs) and is therefore recorded here so it is re-replayed. If that issue's fix lands first, this cause should close with it rather than be fixed twice.
Fix: the lambda Invoke handler's execution path (services/service-com-amazonaws-lambda-awsgirapiservice/src/ops/invoke.rs and the function-runtime component it would call) — execute the stored deployment package and return the handler's payload.
Traces: bedrock-agent__lambda__opensearchserverless.cli-bedrock-agent-invoke-missing-permission-negative.

## Evidence
Cause 1 — expected: SigV4-`aoss`-signed `PUT https://<collectionEndpoint>/<indexName>` accepted for the principal the data-access policy names (and 403-denied for one it does not). actual: `AssertionError: vector index creation failed: 400 {'__type': 'SerializationException', 'message': 'missing required header `x-amz-target`'}` — identical for the permitted and the unpermitted principal. The two Lambda-driven retrieve checks instead report 'Error: Check timed out after 60.0s', which is this same 400 inside their index-create retry loop.
Cause 2 — expected: `aws lambda invoke` rc=0 with the handler's JSON payload, reporting AccessDeniedException for a role without bedrock:InvokeAgent and ResourceNotFoundException for a role with it against agentId 'zzzzzzzzz9'/aliasId 'zzzzzzzz88'. actual: rc=254, stderr `aws: [ERROR]: An error occurred (NotImplemented) when calling the Invoke operation: Invoke resolved arn:aws:lambda:us-west-2:000000000000:function:<fn> at version $LATEST, but running its python3.12 deployment package is not implemented in this emulator ...`
