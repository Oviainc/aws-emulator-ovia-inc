# apigateway: 2 net-new causes — a CloudFormation stack declaring UsagePlan/ApiKey/UsagePlanKey ends ROLLBACK_COMPLETE instead of CREATE_COMPLETE, and the execute-api 403 explicit-deny body truncates AWS's "in an identity-based policy" clause

> _Note: this issue was identified against the code base at commit `65212c3fd92127ed07f35725400800f7ae6b05ca`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateUsagePlan

## Description
Two independent net-new root causes in the API Gateway surface, grounded in failing checks of this suite that are neither ALREADY FILED nor OWNED by an open issue. Both must be closed before this issue is submitted.

=== Cause 1 of 2: a CloudFormation stack that declares AWS::ApiGateway::UsagePlan + ApiKey + UsagePlanKey rolls back instead of creating ===
AWS: recorded behavior only (CloudFormation models no status for a particular resource set). A stack whose Resources are AWS::ApiGateway::RestApi + Resource + Method (ApiKeyRequired: true, MOCK integration) + Deployment + Stage + AWS::ApiGateway::UsagePlan (ApiStages/Throttle/Quota, NO UsagePlanName) + AWS::ApiGateway::ApiKey (Enabled: true, NO Name) + AWS::ApiGateway::UsagePlanKey settles CREATE_COMPLETE, publishes its Outputs (the RestApi id, the ApiKey id, the UsagePlan id), and the provisioned key then authenticates a call to the key-required method. The underlying control-plane calls are modelled: Smithy CreateUsagePlan (POST /usageplans, success 201, errors BadRequestException 400 / ConflictException 409 / LimitExceededException 429 / NotFoundException 404 / TooManyRequestsException 429 / UnauthorizedException 401) with input member `name` REQUIRED; CreateApiKey (POST /apikeys, 201) with every input member optional; CreateUsagePlanKey (POST /usageplans/{usagePlanId}/keys, 201) requiring keyId and keyType.
Emulator: CreateStack for that template settles ROLLBACK_COMPLETE, so the stack never exists, no Outputs are published, and every assertion downstream of the deploy is unreachable. The replay only ever observes the terminal StackStatus (botocore WaiterError: Waiter StackCreateComplete failed ... we matched expected path: "ROLLBACK_COMPLETE"); it does not read the per-resource failure reason, so WHICH resource handler failed is not established by the recording. Hypothesis: the AWS::ApiGateway::UsagePlan provisioner forwards the template's properties straight to CreateUsagePlan without synthesising a `name`, and the required-member check refuses it with BadRequestException, which fails the resource and rolls the stack back; the same would apply to AWS::ApiGateway::ApiKey, whose Name is likewise absent from the template.
Why: usage plans, API keys and plan keys cannot be provisioned through CloudFormation at all against the emulator — the documented (and, for CDK/SAM users, the only) way to declare API key metering. A client sees a stack that rolls back with no usable API, so neither the key-gated 200 nor the keyless 403 of a key-required method can be exercised, and GetUsage can never be reached.
Fix: the CloudFormation resource provisioners for AWS::ApiGateway::UsagePlan, AWS::ApiGateway::ApiKey and AWS::ApiGateway::UsagePlanKey (the create path that translates template properties into the CreateUsagePlan / CreateApiKey / CreateUsagePlanKey calls, including defaulting the names CloudFormation generates when the template omits them). Whatever the failing resource turns out to be, its handler must also surface a CREATE_FAILED event whose ResourceStatusReason names it, which is how this cause should be diagnosed.
Traces: apigateway.deploy-usage-plan-cfn-behaves, apigateway.usage-plan-missing-api-key-rejected. No open issue carries either check; the three open usage-plan issues (20261025T081755Z-apigateway-api-gateway-a-usage-plan-s-day-quota.md, 20261027T004324Z-apigateway-api-gateway-per-method-usage-plan-throttle-overrides.md, 20261029T193654Z-apigateway-api-gateway-refusal-contracts-part-2-10-root.md) are about quota enforcement, per-method throttle overrides and refusal contracts, not about the CFN provisioning path.

=== Cause 2 of 2: the execute-api 403 body for an authorizer policy's explicit Deny is truncated before AWS's reason clause ===
AWS: the execute-api data plane is not Smithy-modelled; recorded behavior. When a TOKEN Lambda authorizer returns a policy whose Statement matches the invoked methodArn with Effect Deny, API Gateway answers HTTP 403 with body {"Message":"User is not authorized to access this resource with an explicit deny in an identity-based policy"}. The whole sentence is FIXED text — it interpolates nothing from the request, the method ARN, the principalId or the emulator's state — and the trailing clause is what distinguishes a matched explicit Deny from the no-matching-Allow refusal ("...because no identity-based policy allows the execute-api:Invoke action").
Emulator: answers the correct 403 but with the body {"Message":"User is not authorized to access this resource with an explicit deny"} — the clause `in an identity-based policy` is missing. Status (403) is right; only the message diverges.
Why: a client or operator that matches on AWS's documented sentence to tell "a Deny matched" from "no Allow matched" cannot distinguish the two refusals, so authorizer policies are mis-diagnosed, and assertions on AWS's wording fail.
Fix: the execute-api authorizer-decision serializer that renders the AccessDeniedException body after evaluating a Lambda authorizer's returned policy document; it must emit AWS's full sentence for the explicit-deny outcome.
Traces: apigateway.deploy-authorizer-cfn-enforces-identity-source. Related but NOT covering: 20261107T191316Z-apigateway-lambda-3-net-new-causes-non-proxy-d346f3.md reports the same truncation for service apigateway__lambda (its Cause 2); this check is listed under the `apigateway` service and is not owned by it. Also related: 20261108T130100Z-apigateway-6-net-new-causes-createdomainnameaccessassociation-s-invalid.md lists this same check id, but its recorded key is the earlier assertion `status_missing == 401` (the identity-source 401 pre-check); that leg now passes and the check fails later, at the explicit-deny body, so this is a separate cause from that issue's Cause 6.
