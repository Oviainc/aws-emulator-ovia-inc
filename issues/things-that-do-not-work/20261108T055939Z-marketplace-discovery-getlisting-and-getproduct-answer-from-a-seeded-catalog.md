# GetListing and GetProduct answer from a seeded catalog row instead of the record the requested id names

> _Note: this issue was identified against the code base at commit `c6500b5cf3adeb9a3f2b2b71dc2b2ed0ef0fcc51`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetListing

## Description
This issue bundles 2 causes, both in marketplace-discovery, both in the same drill-down flow (SearchListings -> GetListing -> GetProduct). In each one the emulator answers 200 but builds the whole response from a generated seed row rather than from the catalog record the requested id names, and the divergence is structural as well as textual: identifier FORMAT (taxonomy ids vs slugs), list LENGTH and ORDER (categories, highlights, badges), and the ENUM values a client branches on (fulfillmentOptionType, pricingModelType, pricingUnitType, deployedOnAws) all differ from what this API returns for the record.

NOTE ON OVERLAP: open issue 20261029T201942Z-marketplace-discovery-getlisting-getproduct-and-listfulfillmentoptions-serve-synthesized-placeholder-records.md describes the same flow and already owns the ListFulfillmentOptions step (task#4) of this fixture, but the replay reports these two clusters as UNOWNED: their diverging-key sets are wider than that issue's recorded keys and now include $.fulfillmentOptionSummaries[0].fulfillmentOptionType/displayName, $.pricingModels[0].pricingModelType/displayName, $.pricingUnits[0].pricingUnitType/displayName and $.deployedOnAws, none of which that issue claims. Both causes below must be closed in their own right, not assumed covered by it.

Cause 1 of 2: GetListing restates a seeded row, not the listing the listingId identifies — slug categoryIds in ancestors-first order, two generated highlights, unearned badges, and the wrong fulfillment/pricing enums.
AWS: Smithy GetListing (POST /2026-02-05/getListing, input listingId ListingId @required @length(1..255) @pattern ^[\w\-]+$) returns 200 with associatedEntities (ListingAssociatedEntityList @length ..100), badges (ListingBadgeList @length ..20), catalog, categories (CategoryList @length ..30 of Category{categoryId NonEmptyString @required, documented "the machine-readable identifier of the category"; displayName NonEmptyString @required, "the human-readable name of the category"}), fulfillmentOptionSummaries (FulfillmentOptionSummaryList @length ..20 of FulfillmentOptionSummary{fulfillmentOptionType FulfillmentOptionType @required - one of AMAZON_MACHINE_IMAGE|API|CLOUDFORMATION_TEMPLATE|CONTAINER|HELM|EKS_ADD_ON|EC2_IMAGE_BUILDER_COMPONENT|DATA_EXCHANGE|PROFESSIONAL_SERVICES|SAAS|SAGEMAKER_ALGORITHM|SAGEMAKER_MODEL; displayName @required}), highlights (HighlightList @length ..10), listingName, logoThumbnailUrl (URL @pattern ^https?://.*$), longDescription, pricingModels (PricingModelList of PricingModel{pricingModelType USAGE|CONTRACT|BYOL|FREE @required, displayName @required}), pricingUnits (PricingUnitList of PricingUnit{pricingUnitType USERS|HOSTS|BANDWIDTH|DATA|TIERS|REQUESTS|UNITS @required, displayName @required}), promotionalMedia, publisher (SellerInformation), resources, sellerEngagements, shortDescription, useCases; errors ResourceNotFoundException 404 / AccessDeniedException 403 / ValidationException 400 / ThrottlingException 429 / InternalServerException 500. The model does not fix the CONTENT, so for content this is recorded behavior only: the response restates the stored listing the id names — each categoryId is an opaque taxonomy identifier (a UUID in the recording, not a lowercased form of displayName) and the categories come back in the listing's stored order rather than ancestors-first; highlights are the seller's own highlight sentences (three here, within the modelled ten); badges is EMPTY when the listing has earned no badge; fulfillmentOptionSummaries, pricingModels and pricingUnits report the enums of that listing's own fulfillment and pricing; associatedEntities names that listing's real product and offer with their real seller of record; and listingName, shortDescription, longDescription, logoThumbnailUrl, promotionalMedia, publisher, resources, sellerEngagements and useCases all come from the record. ($.purchaseIndicators appears in the recorded response but is not declared on GetListingOutput in the on-disk model — recorded behavior only.)
Emulator: 200, but the response describes a different, generated record entirely. categoryId is a slug derived from the display name ('machine-learning', 'structured-data-ml', 'industries', 'retail') instead of a taxonomy identifier, and the list is expanded ancestors-first, so element-for-element both the id and the displayName differ from the record's. highlights is exactly the two generated sentences 'Fulfilled as <fulfillment option display name>' and 'Listed under <category display name>', so the listing's own highlights are gone and the third is absent entirely. Two badges are reported (AWS_FREE_TIER 'AWS Free Tier' and DEPLOYED_ON_AWS 'Deployed on AWS') where the recording reports none. fulfillmentOptionSummaries[0] reports fulfillmentOptionType CLOUDFORMATION_TEMPLATE / displayName 'AWS CloudFormation template' instead of the record's SAAS / 'SaaS', and pricingModels[0]/pricingUnits[0] report the enum pair the seeder assigns the row by position rather than the listing's own. associatedEntities[0] names a template product/offer and a template seller profile id, and listingName, shortDescription, longDescription, logoThumbnailUrl ('https://example.com/logos/<slug>.png'), promotionalMedia, publisher, resources, sellerEngagements, useCases and purchaseIndicators are all generated text of the form '<short description> <name> is listed under <category> and fulfilled as <fulfillment>.'
Why: GetListing is the detail view the whole discovery flow funnels into, so a client renders generated filler for a listing it looked up by id. Worse, the identifiers and enums are load-bearing: a client that feeds a returned categoryId back as a CATEGORY search filter, or persists it, is handling an identifier shape this service never issues; a client that reads fulfillmentOptionType, pricingModelType or pricingUnitType branches on a deployment and billing model the listing does not have; and a client that reads badges advertises an AWS Free Tier / Deployed on AWS status the listing has not earned.
Fix: the seeded catalog and the projections GetListing restates it through, in the marketplace-discovery crate's state (services/service-com-amazonaws-marketplacediscovery-awsmarketplacediscovery/src/state.rs): the per-row seeder that synthesizes highlights, long descriptions and logo URLs, the slug-keyed taxonomy helper that mints categoryId and expands ancestors ahead of the stored category, the positional pricing-model/pricing-unit assignment, and the badge derivation. GetListing's handler must restate the stored record for the requested listingId rather than a template built from the row.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#2 (GetListing, expected 200 / got 200, 42 diverging keys).

Cause 2 of 2: GetProduct repeats the substitution for the product resolved from that listing, and additionally reports the wrong deployedOnAws status.
AWS: Smithy GetProduct (POST /2026-02-05/getProduct, input productId @required) returns 200 with productId, catalog, productName, manufacturer (SellerInformation), deployedOnAws (DeployedOnAwsStatus @required - DEPLOYED|NOT_DEPLOYED|NOT_APPLICABLE), shortDescription, longDescription, logoThumbnailUrl, fulfillmentOptionSummaries, categories (CategoryList of Category), highlights (HighlightList @length ..10), promotionalMedia, resources, sellerEngagements, listingId; same five modelled errors. Recorded behavior for content: the product restates its own stored record — taxonomy-identifier categories in stored order, the seller's own three highlight sentences, its own manufacturer, productName, descriptions, logo URL, resources and seller engagements — and deployedOnAws reports that product's stored deployment status (NOT_DEPLOYED for the SaaS product in this recording), not a value derived from its fulfillment type.
Emulator: 200 with the same substitutions as cause 1 — slug categoryIds in ancestors-first order ($.categories[0..3] differ whole-element), a single generated highlight so highlights[1] and highlights[2] are absent, fulfillmentOptionSummaries[0] reporting CLOUDFORMATION_TEMPLATE / 'AWS CloudFormation template' instead of SAAS / 'SaaS', and template productName, manufacturer, shortDescription, longDescription, logoThumbnailUrl, resources, sellerEngagements and purchaseIndicators. deployedOnAws comes back 'DEPLOYED' where the record reports 'NOT_DEPLOYED'. Hypothesis: deployedOnAws is derived from the seeded fulfillment option type (a CloudFormation row counting as deployed) rather than read off the product.
Why: a client that drills product-level detail after a listing gets a second, independently wrong copy of the same record, so cross-checking listing against product cannot detect the substitution. deployedOnAws is what a buyer-side client uses to decide whether the product runs in the buyer's own account, so inverting it sends the client down a deployment path AWS would not offer for that product, and the slug-shaped categoryId leaks here too.
Fix: same component as cause 1 — the seeder and the category/highlight/fulfillment-summary projections GetProduct shares with GetListing in that crate's state, plus the deployedOnAws derivation, which must restate the product's stored status instead of inferring it from the fulfillment option type.
Traces: marketplace-discovery-search-listings-and-drill-into-listing#task#3 (GetProduct, expected 200 / got 200, 29 diverging keys).

Explicitly NOT claimed as requirements anywhere in this issue: the recorded literal ids, names and URLs (listing/product/offer/fulfillment-option ids, sellerProfileId values, CloudFront URLs) and the numeric availableFromTime the emulator derives from its own clock. Those differ per environment and per run. The defects are the identifier FORMAT, the list lengths and ordering, which badges and optional members appear, the enum values reported for fulfillment/pricing/deployment, and the fact that the content is a generated template rather than the record the requested id names.
