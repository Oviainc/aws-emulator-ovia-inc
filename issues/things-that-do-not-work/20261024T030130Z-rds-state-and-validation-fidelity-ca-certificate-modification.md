# RDS state and validation fidelity: CA-certificate modification, DeleteDBInstance parameter-combination class, no-op ModifyOptionGroup, DBSubnetGroup.VpcId, Multi-AZ standby, aurora-postgresql16 parameter catalogue

> _Note: this issue was identified against the code base at commit `768bbe4b7ea7973f1ee2efc8bf0f22146be54ed5`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ModifyDBInstance

## Description
Six independent fidelity defects in implemented RDS operations: a modification that is neither staged nor echoed, an error class the SDK cannot match, a no-op mutation that is accepted, a response member that is dropped, a Multi-AZ deployment that has no standby, and a parameter catalogue with no modifiable boolean entries. These are distinct from the already-open wire issues 'RDS awsQuery error envelopes omit RequestId and misclassify parameter validation', 'RDS omits state and existence preconditions and misclassifies the resulting errors' and 'RDS DescribeDBInstances omits modeled members and reports wrong storage and engine defaults', which cover other operations and other members. Six causes.

Cause 1 of 6: ModifyDBInstance neither stages nor echoes CACertificateIdentifier, and the active CA changes with no reboot. AWS: Smithy ModifyDBInstance input models CACertificateIdentifier (String) and the PendingModifiedValues structure models CACertificateIdentifier ('The identifier of the CA certificate for the DB instance'); PendingModifiedValues is documented as 'changes that will be applied during the next maintenance window'. So a ModifyDBInstance that changes the CA must return the requested value in PendingModifiedValues and must NOT change the instance's active CACertificateIdentifier until a reboot (or CertificateRotationRestart) applies it. Emulator: the ModifyDBInstance response carries PendingModifiedValues = {} — the requested CACertificateIdentifier is nowhere in the response — while the instance's CURRENT CACertificateIdentifier has already changed before any RebootDBInstance was issued. Why: a client that rotates a CA reads back no pending change (so it cannot confirm the request landed or tell a user a reboot is required), and a client that relies on the rotation being deferred sees connections re-keyed at an unplanned instant. Fix: the ModifyDBInstance handler's pending-modification staging for CACertificateIdentifier, the PendingModifiedValues projection in the RDS state module, and the RebootDBInstance apply step. Traces: rds.ca-certificate-identifier-round-trip, rds.e2e-certificate-rotation-consequence-flow.

Cause 2 of 6: DeleteDBInstance with SkipFinalSnapshot=false and no FinalDBSnapshotIdentifier is rejected with the framework's generic 'ValidationException' instead of RDS's InvalidParameterCombination. AWS: Smithy DeleteDBInstance input models SkipFinalSnapshot (Boolean) and FinalDBSnapshotIdentifier (String); recorded behavior rejects the combination with HTTP 400 and awsQuery Error.Code 'InvalidParameterCombination' (the message, which names the combination, is an example). 'ValidationException' is not an RDS query error code at all. Emulator: HTTP 400 with Error.Code 'ValidationException'. Why: SDK/CLI error handling, retry classification and user-facing branching keyed on InvalidParameterCombination never fire; the caller sees an error code that does not exist in the RDS API. Fix: the DeleteDBInstance handler's parameter-combination validation must raise the RDS awsQuery error rather than the generic framework ValidationException. Traces: rds.delete-without-final-snapshot-identifier-rejected.

Cause 3 of 6: ModifyOptionGroup accepts a request with nothing to change. AWS: Smithy ModifyOptionGroup input models OptionsToInclude (OptionConfigurationList) and OptionsToRemove (OptionNamesList), both optional, and the operation's modeled errors are OptionGroupNotFoundFault (404) and InvalidOptionGroupStateFault (400); recorded behavior rejects a ModifyOptionGroup that supplies neither list with HTTP 400 (a parameter-combination rejection — the recorded message is an example). Emulator: the call SUCCEEDS and returns the option group. Why: a client that treats success as 'my option change was applied' silently proceeds on a request AWS refuses, and a validation bug in the caller (an empty option list) is never surfaced. Fix: the ModifyOptionGroup handler's input validation. Traces: rds.modify-option-group-empty.

Cause 4 of 6: the DBSubnetGroup envelope omits VpcId. AWS: Smithy models DBSubnetGroup {DBSubnetGroupName, DBSubnetGroupDescription, VpcId ('Provides the VpcId of the DB subnet group'), SubnetGroupStatus, Subnets, DBSubnetGroupArn, SupportedNetworkTypes}; AWS always emits VpcId, derived from the VPC the named subnets belong to. Emulator: the DBSubnetGroup returned for a group created over real subnets has no 'VpcId' key at all (KeyError 'VpcId' when the check reads it). Why: a client that discovers which VPC a DB subnet group (and therefore an instance placed in it) belongs to — to pick security groups, or to validate that a proxy's subnets share the instance's VPC — gets nothing to read. Fix: the DBSubnetGroup projection in the RDS state module, and the subnet->VPC resolution in CreateDBSubnetGroup that it must record. Traces: rds.subnet-group-vpc-and-arn-round-trip.

Cause 5 of 6: an instance created with MultiAZ=true has no standby, so RebootDBInstance(ForceFailover=true) can never swap AZs. AWS: the DBInstance shape models SecondaryAvailabilityZone, and a Multi-AZ instance reports it once provisioning completes; RebootDBInstance(ForceFailover=true) is the documented way to test failover and the service promotes the standby so AvailabilityZone and SecondaryAvailabilityZone exchange values. Emulator: the instance reaches 'available' but SecondaryAvailabilityZone never appears, so the check polls for it until the harness's wall-clock budget expires (verdict: 'Check timed out after 60.0s'). Note the emulator materializes its creating->available transition in 300ms (services/service-com-amazonaws-rds-amazonrdsv19/src/state.rs STATUS_TRANSITION_DELAY), so 60s is ample and the timeout is an absent member, not slow provisioning. Why: a client that verifies a Multi-AZ deployment, or that exercises failover before a maintenance event, can neither see the standby nor observe a failover. Fix: the CreateDBInstance/ModifyDBInstance handling of MultiAZ (record a secondary AZ distinct from the primary) and the RebootDBInstance ForceFailover path that must swap them. Traces: rds.multi-az-standby-auto-failover-on-primary-failure.

Cause 6 of 6: the published cluster-parameter catalogue for family 'aurora-postgresql16' exposes no modifiable boolean parameter with resolvable values, so the invalid-value rejection cannot be exercised. AWS: DescribeDBClusterParameters for an aurora-postgresql16 group publishes many parameters with IsModifiable=true, DataType 'boolean' and AllowedValues '0,1', and ModifyDBClusterParameterGroup rejects a value outside AllowedValues with HTTP 400 InvalidParameterValue. Emulator: the check scans the catalogue the emulator publishes for that family and finds no boolean, modifiable, value-resolvable parameter at all. Why: a client that enumerates a family's tunables to build a UI or to validate a desired configuration sees a catalogue that does not match the engine family it asked for, and the value-range rejection path is unreachable. Fix: the family parameter catalogue shared in service_common::rds_cluster_parameters (re-exported via the RDS state module) and the DescribeDBClusterParameters projection over it. Traces: rds.modify-cluster-parameter-invalid-value-rejected.

## Steps to Reproduce
1. Boot the emulator from this checkout.
2. Cause 1: CreateDBInstance, wait for available, then Action=ModifyDBInstance with CACertificateIdentifier=<another published CA> and read PendingModifiedValues (empty) and the instance's current CACertificateIdentifier (already changed, with no RebootDBInstance).
3. Cause 2: Action=DeleteDBInstance with SkipFinalSnapshot=false and no FinalDBSnapshotIdentifier; read Error.Code ('ValidationException' instead of 'InvalidParameterCombination').
4. Cause 3: CreateOptionGroup, then Action=ModifyOptionGroup with neither OptionsToInclude nor OptionsToRemove; the call returns 200.
5. Cause 4: CreateDBSubnetGroup over two subnets, then Action=DescribeDBSubnetGroups and look for VpcId in the DBSubnetGroup element.
6. Cause 5: CreateDBInstance with MultiAZ=true, wait for 'available', then poll DescribeDBInstances for SecondaryAvailabilityZone; it never appears, so RebootDBInstance(ForceFailover=true) can never swap AvailabilityZone and SecondaryAvailabilityZone.
7. Cause 6: CreateDBClusterParameterGroup with DBParameterGroupFamily=aurora-postgresql16, then Action=DescribeDBClusterParameters and look for any parameter with IsModifiable=true, DataType boolean and AllowedValues.
