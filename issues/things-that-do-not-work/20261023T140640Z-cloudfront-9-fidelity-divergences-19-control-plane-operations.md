# CloudFront: 9 fidelity divergences — ~19 control-plane operations answer 501 NotImplemented, CreateDistribution validates nothing, KeyValueStore data plane unroutable, CFN CloudFront resources broken

> _Note: this issue was identified against the code base at commit `a59989a9f63c403b66485a4e93f54ab6df22c2a6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateDistribution

## Description
Nine independent CloudFront defects surfaced by the cloudfront behavioral checks. Each is its own root cause and its own work item; this issue bundles NINE causes and all nine must be closed before submitting.

Cause 1 of 9: a large set of CloudFront control-plane operations are scaffold stubs that answer the unmodeled error code `NotImplemented` instead of their modeled result or their modeled 4xx error. The operations observed are GetAnycastIpList, GetDistributionTenant, GetDistributionTenantByDomain, GetInvalidationForDistributionTenant, GetManagedCertificateDetails, GetOriginRequestPolicyConfig, GetFieldLevelEncryptionProfile, GetConnectionFunction, GetConnectionGroup, GetConnectionGroupByRoutingEndpoint, GetVpcOrigin, CreateVpcOrigin, AssociateAlias, DeleteKeyValueStore, DisassociateDistributionTenantWebACL, ListConflictingAliases, ListDistributionsByOwnedResource, ListDomainConflicts and ListFunctions.
AWS: each of these is a modeled operation with a modeled error set — e.g. Smithy: GetVpcOrigin -> GET /2020-05-31/vpc-origin/{Id}, errors AccessDenied(403)/EntityNotFound(404)/InvalidArgument(400)/UnsupportedOperation(400); AssociateAlias -> PUT /2020-05-31/distribution/{TargetDistributionId}/associate-alias, errors AccessDenied(403)/IllegalUpdate(400)/InvalidArgument(400)/NoSuchDistribution(404)/TooManyDistributionCNAMEs(400); GetManagedCertificateDetails -> GET /2020-05-31/managed-certificate/{Identifier}, errors AccessDenied(403)/EntityNotFound(404). `NotImplemented` is not a modeled error for any CloudFront operation, and the service is REST-XML.
Emulator: every call returns `NotImplemented` with the body "operation <Name> is scaffolded but not implemented in this emulator", so a malformed id yields NotImplemented where AWS yields 400 InvalidArgument, and an unknown id yields NotImplemented where AWS yields 404 EntityNotFound / NoSuchDistribution / NoSuchOriginRequestPolicy / NoSuchFieldLevelEncryptionProfile.
Why: a client cannot distinguish 'this resource does not exist' from 'this request is malformed' from 'the service is broken'; SDK retry logic treats the unmodeled code as a server fault and retries a request AWS rejected deterministically, and no read-back of these resources is possible at all.
Fix: the per-operation handler files in the cloudfront service crate (services/service-com-amazonaws-cloudfront-cloudfront2020-05-31/src/ops/) plus the id/ARN validation and the entity lookups in that crate's state. Operations already covered by their own auto-filed stub issues (CreateCachePolicy, CreateResponseHeadersPolicy, ListAnycastIpLists, GetResourcePolicy, AssociateDistributionWebACL, DisassociateDistributionWebACL, CreateFunction, TagResource, ...) are NOT part of this cause.
Traces: cloudfront.get-anycast-ip-list-invalid-argument-rejected, cloudfront.get-anycast-ip-list-malformed-id-invalid-argument-rejected, cloudfront.get-distribution-tenant-by-domain-malformed-domain-invalid-argument-rejected, cloudfront.get-distribution-tenant-by-domain-not-found-fails, cloudfront.get-managed-certificate-details-nonexistent-rejected, cloudfront.managed-certificate-details-not-found-rejected, cloudfront.op-contract-get-managed-certificate-details, cloudfront.op-contract-get-managed-certificate-details-not-found-rejected, cloudfront.get-origin-request-policy-config-nonexistent-rejected, cloudfront.list-conflicting-aliases-nonexistent-distribution-rejected, cloudfront.op-contract-listConflictingAliases, cloudfront.list-distributions-by-owned-resource-filters-correctly, cloudfront.list-domain-conflicts-invalid-argument-rejected, cloudfront.list-functions-unsupported-operation-rejected, cloudfront.op-contract-associate-alias, cloudfront.op-contract-deleteKeyValueStore, cloudfront.op-contract-disassociateDistributionTenantWebACL, cloudfront.op-contract-get-connection-function, cloudfront.op-contract-get-connection-group, cloudfront.op-contract-get-connection-group-by-routing-endpoint, cloudfront.op-contract-get-distribution-tenant, cloudfront.op-contract-get-distribution-tenant-by-domain, cloudfront.op-contract-get-field-level-encryption-profile, cloudfront.op-contract-get-invalidation-for-distribution-tenant, cloudfront.op-contract-getVpcOrigin, cloudfront.vpc-origin-create-invalid-arn-rejected, cloudfront.vpc-origin-invalid-arn-fails, cloudfront.vpc-origin-invalid-endpoint-arn-rejected.

Cause 2 of 9: request-validation failures on CloudFront operations are emitted with the error code `ValidationException`, which belongs to the AWS JSON protocols and is not part of CloudFront's REST-XML error surface.
AWS: Smithy: ListConnectionFunctions models exactly three client errors — AccessDenied(403), InvalidArgument(400), UnsupportedOperation(400) — and its `Stage` member targets the FunctionStage enum; a value outside the enum is refused by the XML/query front door (recorded behavior: MalformedXML), never with ValidationException.
Emulator: a ListConnectionFunctions call carrying an out-of-enum Stage is refused with code `ValidationException`; the valid-stage positive control in the same check is then unreachable.
Why: a client switching on the documented CloudFront error codes never matches, and generated SDK error unions have no member for ValidationException, so it surfaces as an unmodeled generic failure.
Fix: the input-validation/error-serialization layer of the cloudfront crate (map member and enum violations onto the service's modeled codes, rendered in the REST-XML <Error> envelope), not the individual handler.
Traces: cloudfront.list-connection-functions-invalid-stage-malformed-xml-rejected, cloudfront.list-connection-functions-invalid-stage-rejected-valid-stage-succeeds.

Cause 3 of 9: CreateDistribution / CreateDistributionWithTags accept DistributionConfig documents AWS refuses, creating a distribution instead of failing.
AWS: Smithy: CreateDistribution models a large rejection set, including InvalidArgument(400), NoSuchOrigin(404), InvalidForwardCookies(400), InvalidQueryStringParameters(400) and InconsistentQuantities(400); a DefaultCacheBehavior that sets both the legacy ForwardedValues and a CachePolicyId is refused, as is a behavior whose TargetOriginId names no origin in Origins.
Emulator: both calls return 201 with a fully-populated Distribution (Status InProgress, generated Id/ARN/DomainName), i.e. no cross-member validation of DistributionConfig is performed at all; the same is true of the tagged variant, whose request real AWS rejects.
Why: a client's broken configuration is silently accepted, so the emulator reports a working distribution for a configuration that can never exist in AWS, and negative-path handling in deployment tooling is never exercised.
Fix: DistributionConfig validation in the CreateDistribution/CreateDistributionWithTags handlers of the cloudfront crate (origin-reference resolution and the mutually-exclusive cache-key members). The open issue 20261022T025800Z-cloudfront-createdistribution-accepts-configurations-aws-rejects.md describes the same class of gap but does not carry these replay keys.
Traces: cloudfront.distribution-forwarded-values-with-cache-policy-rejected, cloudfront.distribution-invalid-target-origin-rejected, cloudfront.op-contract-create-distribution-with-tags.

Cause 4 of 9: CreateInvalidation stores the submitted paths verbatim instead of the deduplicated set.
AWS: recorded behavior only — Smithy models Paths{Quantity:integer(required), Items:PathList} and does not state the dedup rule; the recording shows that a batch submitted with one duplicated path is stored and returned as the set of distinct paths, with Quantity equal to that distinct count.
Emulator: a batch of 4 paths containing one duplicate is stored with Quantity 4 and the duplicate retained.
Why: a client that reads back an invalidation to reconcile what it asked for sees a path count that does not match AWS, and anything billing/quota-aware that counts invalidation paths double-counts.
Fix: the CreateInvalidation handler and the invalidation state it writes in the cloudfront crate.
Traces: cloudfront.invalidation-paths-are-deduplicated-and-returned-as-a-set.

Cause 5 of 9: the CloudFront KeyValueStore data plane is not reachable: requests addressed to it are not routed to a service.
AWS: the cloudfront-keyvaluestore API is its own endpoint/service (DescribeKeyValueStore, GetKey, PutKey, DeleteKey) keyed by the KVS ARN; DescribeKeyValueStore answers 200 with an ETag that PutKey then uses for its IfMatch.
Emulator: a DescribeKeyValueStore call is refused with `UnknownService` — "could not resolve a target service from the request (no SigV4 credential scope, X-Amz-Target, or Host header)" — so the emulator's front door does not recognise this service at all; via the CLI the same call fails to connect because the endpoint announced for it is not an address the emulator serves ("Could not connect to the endpoint URL: https://<account-id>.<emulator-host>/key-value-stores/<url-encoded kvs arn>").
Why: nothing in the key-value-store data plane can be exercised — a CloudFront Function that reads KVS at the edge cannot be set up or verified, and the failure surfaces as a transport/endpoint error rather than an API error, which looks like a client misconfiguration.
Fix: request routing/endpoint resolution for the cloudfrontkeyvaluestore service (service-com-amazonaws-cloudfrontkeyvaluestore-cloudfrontkeyvaluestore) in the emulator's front door, plus the endpoint it announces for that service.
Traces: cloudfront.cf-keyvaluestore-put-key-visible-to-function-at-edge, cloudfront.deep-cloudfront-1-cf-edge-fn-kvs-put-key-serves-new-value.

Cause 6 of 9: every CloudFormation-deployed CloudFront scenario fails because the stack's Outputs entries carry no OutputValue.
AWS: recorded behavior only — DescribeStacks on a CREATE_COMPLETE stack whose template declares Outputs returns each output as {OutputKey, OutputValue, ...}; the checks index `o["OutputValue"]` directly.
Emulator: the Outputs members are present but have no OutputValue key, so every check raises KeyError: 'OutputValue' before it can address the deployed distribution or cache policy.
Why: no client can consume a stack's outputs, so the entire deploy-then-use workflow (deploy a distribution/cache policy by template, then drive traffic or read it back) is unreachable.
Fix: the CloudFormation DescribeStacks output serialization and the output-resolution step that evaluates Ref/Fn::GetAtt for the declared resources. Related open issues on the same serializer that do NOT carry these CloudFront replay keys: 20261022T235108Z-cloudformation-stack-outputs-carry-no-outputvalue-failing-resources.md and 20261023T114649Z-cloudformation-outputs-carry-no-outputvalue-failed-resources-never.md.
Traces: cloudfront.deploy-cache-policy-cfn-enforced-on-distribution, cloudfront.deploy-cache-policy-cfn-ttl-enforced, cloudfront.deploy-cache-policy-enforced-via-cloudformation, cloudfront.deploy-cloudfront-2-function-autopublish-toggle-publishes-live, cloudfront.deploy-cloudfront-distribution-serves-origin-content, cloudfront.deploy-distribution-cfn-serves-live-traffic, cloudfront.deploy-distribution-serves-content-via-cloudformation.

Cause 7 of 9: CloudFormation does not know the AWS::CloudFront::KeyValueStore resource type.
AWS: recorded behavior only — a template declaring AWS::CloudFront::KeyValueStore is accepted by CreateStack and the resource is provisioned (the type is a supported CloudFront resource provider).
Emulator: CreateStack is refused with 400 `ValidationError` "Template format error: Unrecognized resource types: [AWS::CloudFront::KeyValueStore]".
Why: a stack that models a CloudFront Function with its key-value store cannot be deployed at all, and the refusal is attributed to the client's template rather than to a missing provider.
Fix: the CloudFormation resource-type registry/provider set — add the AWS::CloudFront::KeyValueStore provider that creates the store in the cloudfront state and resolves Ref/Fn::GetAtt to its real id/ARN.
Traces: cloudfront.deploy-cloudfront-2-function-kvs-rename-replaces-code-update-in-place, cloudfront.deploy-cloudfront-2-function-second-kvs-association-rejected.

Cause 8 of 9: a stack whose resource refusal should roll it back reports success instead.
AWS: recorded behavior only — a stack whose AWS::CloudFront::Distribution references a cache-policy id that does not exist fails that resource (CloudFront answers NoSuchCachePolicy, Smithy: CreateDistribution error NoSuchCachePolicy httpError 404) and the stack ends ROLLBACK_COMPLETE.
Emulator: the stack reaches CREATE_COMPLETE; the invalid reference is never propagated as a resource failure.
Why: a client's broken template is reported as a successful deployment, so a deploy pipeline proceeds against an estate that does not exist.
Fix: resource-level failure propagation and rollback in the CloudFormation engine, plus the AWS::CloudFront::Distribution provider's validation of referenced policy ids.
Traces: cloudfront.deploy-cloudfront-1-distribution-nonexistent-cache-policy-rejected-rolls-back.

Cause 9 of 9: ACM ImportCertificate is an unimplemented scaffold stub, which blocks the CloudFront domain-conflict detection path.
AWS: ImportCertificate is a modeled ACM operation returning a CertificateArn; NotImplemented is not one of its modeled errors.
Emulator: `NotImplemented` — "operation ImportCertificate is scaffolded but not implemented in this emulator" — so the check cannot mint the certificate that a conflicting CloudFront alias needs.
Why: any workflow that imports a certificate before attaching an alternate domain name to a distribution (the normal custom-domain path) cannot run.
Fix: the ImportCertificate handler in the acm service crate (services/service-com-amazonaws-acm-certificatemanager/src/ops/import_certificate.rs) and its certificate state.
Traces: cloudfront.list-domain-conflicts-detects-collision.
