# s3__ses__sesv2: SES inbound mail receiving is unreachable — the account's DNS-baseline public hosted zone is not tag-discoverable through route53 ListHostedZones/ListTagsForResource, so all four receipt-rule/S3-delivery checks abort before any SES or S3 call (1 cause)

## Operation
ListHostedZones

## Description
One root cause, grounded in the four failing checks of the `s3__ses__sesv2` suite directory. All four are net-new: none is marked ALREADY FILED and none is OWNED by an open issue in this replay.

Cause 1 of 1: tag-based discovery of the account's public hosted zones yields no zone carrying the DNS-baseline tag, so no SES-verified receiving domain can be resolved and every check aborts inside its precondition helper `_receiving_domain`, before a receipt rule set, a receipt rule, a send or any S3 delivery is exercised. Failing checks: s3__ses__sesv2.inbound-message-carries-authentication-and-scan-headers, s3__ses__sesv2.mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule, s3__ses__sesv2.raw-multipart-attachment-arrives-byte-exact, s3__ses__sesv2.s3-action-object-key-prefix-and-kms-encryption.

Beyond those signatures this is recorded behavior only: against real AWS, paging ListHostedZones enumerates every hosted zone the account holds, a public zone reports HostedZone.Config.PrivateZone false, ListTagsForResource(ResourceType='hostedzone', ResourceId=<the segment of HostedZone.Id after the last '/'>) answers 200 with a ResourceTagSet whose Tags are exactly the tags ChangeTagsForResource wrote on that zone, and GetEmailIdentity on that zone's apex (trailing dot stripped) answers 200 with VerifiedForSendingStatus true. The requirement is general and names no particular zone: a zone that exists is enumerated as public, and the tags written on it are projected back for ResourceType 'hostedzone'.

Emulator: nothing is refused — every route53 read in the discovery loop answers 2xx — yet not one enumerated public zone carries the baseline tag, so each helper falls through to its precondition assertion and the check stops at its first statement. Messages seen: 'this account has no DNS baseline zone (a public hosted zone tagged sim2real-infra-dns-baseline) and so no domain to receive mail for; provision it with SimParityProbe infra/pool/setup_domain_baseline.py' (three checks) and 'no public hosted zone carries the DNS baseline tag, so the account has no verified domain to receive mail for' (mail-to-a-verified-domain-is-received-into-s3-by-a-receipt-rule). In those assertions the fixed text is the sentence itself; the tag searched for ({'Key': 'sim2real-infra-dns-baseline', 'Value': 'true'}) and the zone apex that would have been returned are values from the account's state, not part of any template. Hypothesis: either ListHostedZones enumerates no public zone for the account (HostedZones empty, or zones reported with Config.PrivateZone true), or the hostedzone tag store is not projected by ListTagsForResource so the ResourceTagSet comes back without the tag ChangeTagsForResource wrote.

Why: a client cannot tag-discover its own DNS zones — the standard way SES receiving tooling locates the domain it accepts mail for — and because that identity is undiscoverable the entire SES inbound-receiving plane behind these checks is masked and its fidelity unknown: delivery of mail for a verified domain into S3 by an active receipt rule, the ScanEnabled stamping of Received-SPF / Authentication-Results (dkim=pass) / X-SES-Spam-Verdict / X-SES-Virus-Verdict on the stored raw message, byte-exact storage of a raw multipart message with an attachment, and S3Action ObjectKeyPrefix placement with KMS encryption of the delivered object. None of these can even be attempted while this read is empty.

Fix: route53's hosted-zone enumeration and its hostedzone tag reads — ListHostedZones' listing/pagination and the PrivateZone flag it reports, and the tag state ListTagsForResource projects for ResourceType 'hostedzone' — must agree with what CreateHostedZone/ChangeTagsForResource recorded; the sesv2 email-identity state for that apex must then report it verified for sending.
