=== Cause 1 of 1: a session-policy AccessDenied refusal stops at '... action' and omits the authorization-details sentence ===
AWS: IAM speaks awsQuery (com.amazonaws.iam#AWSIdentityManagementV20100508, version 2010-05-08). Smithy: ListRoleTags takes RoleName (roleNameType, @required, @length 1..64, @pattern ^[\w+=,.@-]+$), Marker, MaxItems (@range 1..1000) and models only NoSuchEntityException (awsQueryError NoSuchEntity, HTTP 404) and ServiceFailureException (ServiceFailure, HTTP 500); ListAttachedRolePolicies additionally models InvalidInputException (InvalidInput, 400). The authorization refusal AccessDenied / HTTP 403 is a service-common error whose message text is not modeled, so this is recorded behavior only. When a role's permissions allow an action but the session's inline policy does not, the recorded refusal is TWO sentences — the session-policy implicit-deny sentence followed by a pointer to the request's authorization details:
  `User: <assumed-role-caller-arn> is not authorized to perform: <service>:<Action> on resource: <resource-description> because no session policy allows the <service>:<Action> action. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/<authorization-id> for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: <authorization-id>`
Fixed text that must appear verbatim: `User: `, ` is not authorized to perform: `, ` on resource: `, ` because no session policy allows the `, ` action. Go to https://us-east-1.console.aws.amazon.com/iam/home?region=us-east-1#/authorization-details/`, ` for complete details, or call the GetRequestAuthorizationDetails API with the following authorization id: `. The us-east-1 host and the region query parameter are fixed text, because IAM is a global service signed in us-east-1. Variable parts, taken from the signed request and the emulator's own state: <assumed-role-caller-arn> (the arn:aws:sts::<account>:assumed-role/<role>/<session-name> of the session that signed the request), <service>:<Action> (the IAM action of the refused operation — iam:ListRoleTags and iam:ListAttachedRolePolicies in these two checks, appearing twice in the sentence), <resource-description> (how IAM names the evaluated resource for the action — the recorded form here is `role <RoleName>`, with RoleName from the request), and <authorization-id> (the per-request authorization id, which also appears inside the console URL). Both checks read the authorization id back OUT of the emulator's own message (splitting on the marker 'authorization id: ') and substitute a placeholder only when the marker is absent entirely, so no per-run value is compared: the requirement is that the sentence exist at all.
Emulator: the decision and the code are right — the session policy does narrow the session, Error.Code is `AccessDenied`, HTTP 403, and the first sentence is byte-for-byte correct — and then the message ends. Observed Error.Message: `User: arn:aws:sts::<account>:assumed-role/<role>/<session> is not authorized to perform: iam:ListRoleTags on resource: role <role> because no session policy allows the iam:ListRoleTags action` (and the same shape with iam:ListAttachedRolePolicies). The entire second sentence — the console authorization-details URL plus 'or call the GetRequestAuthorizationDetails API with the following authorization id: <id>' — is missing, and with it any authorization id to point at. The expected text is the received text plus that whole trailing sentence.
Why: a client that reads AWS's denial text to route a developer to the authorization-details console page, or that parses the message to hand an authorization id to GetRequestAuthorizationDetails, receives a truncated string and has nothing to follow — the troubleshooting hook IAM refusals exist to provide. Parity harnesses and log scrapers that match the full documented refusal do not recognise the session-policy denial. Hypothesis: the trailer is decided in one shared denial-message builder and the fixes for the two FIXED issues above re-enabled it on the identity-based-policy branch only, leaving the session-policy branch emitting the bare first sentence.
Fix: the shared authorization-refusal denial-message builder in the IAM crate — the component that renders the AccessDenied message for iam operations ahead of the operation handlers (the policy-evaluation / denial-message module reached from services/service-com-amazonaws-iam-awsidentitymanagementv20100508/src/service.rs), not the ListRoleTags or ListAttachedRolePolicies handlers, which are never reached once the request is refused. The trailer must be selected per refusal from the recorded message for that refusal class, so the session-policy denial sentence carries the console-URL + GetRequestAuthorizationDetails sentence with the console host and region pinned to us-east-1 and the authorization id taken from the request's authorization context.
Traces: iam.sep-policy-composition-session-policy-narrows-never-widens-denied-by-simulator-and-real-call (assertion `message == want` on the iam:ListRoleTags refusal, check line 264) and iam.session-policy-intersects-the-role-policy (assertion `narrow_msg == expected_msg` on the iam:ListAttachedRolePolicies refusal, check line 221).
