=== Cause 1 of 2: an accepted replay never re-emits the archived events, so neither Destination.FilterArns scoping nor the presence of `replay-name` at pattern-matching time can be observed ===

AWS: Smithy (com.amazonaws.eventbridge#StartReplay) models required {ReplayName @length 1..64 @pattern ^[\.\-_A-Za-z0-9]+$, EventSourceArn (an ArchiveArn), EventStartTime, EventEndTime, Destination (ReplayDestination{Arn, FilterArns})} and output {ReplayArn, State, StateReason, ReplayStartTime}; errors InternalException (500), InvalidEventPatternException (400), LimitExceededException (400), ResourceAlreadyExistsException (400), ResourceNotFoundException (400). DescribeReplay reports {State, StateReason, Destination, EventStartTime, EventEndTime, EventLastReplayedTime, ReplayStartTime, ReplayEndTime}. The modeled documentation states that a replay "processes events to replay based on the time in the event" and that DescribeReplay is how progress is determined. So the behavior: the replay settles at State=COMPLETED; the archived events whose own envelope `time` lies inside [EventStartTime, EventEndTime] are re-emitted onto Destination.Arn; routing is CONFINED to the rule ARNs named in Destination.FilterArns (a rule on the same bus whose pattern matches the same event but that is NOT in FilterArns receives nothing from the replay); DescribeReplay echoes Destination.FilterArns back unchanged; and each redelivered envelope carries a `replay-name` field equal to the ReplayName. `replay-name` is a real, matchable envelope field, so a rule whose pattern requires `"replay-name": [{"exists": false}]` receives live events but must NOT receive replayed ones even when that rule IS named in FilterArns — i.e. the field has to be present when the pattern engine evaluates the event, not stamped on afterwards during serialization.
Emulator: both checks report `Check timed out after 60.0s` and never reach their replay assertions. Nothing from a replay is ever observed arriving at the destination bus's rule target, so the FilterArns scoping (rule A in, rule B out) and the `replay-name exists:false` opt-out (rule Y receives the replay, rule X must not) are both ungraded. Each check had already succeeded at CreateEventBus, two PutRule+PutTargets pairs, CreateArchive, the ENABLED poll and the live PutEvents leg before the cap.
Why: archive + replay is EventBridge's documented backfill/recovery story and FilterArns is the only way a consumer bounds which rules a backfill re-runs. A consumer that asks for a scoped backfill gets an accepted StartReplay and then either nothing at all (no recovery) or — if re-emission is added without the scoping — duplicated side effects on rules it deliberately excluded. Because `replay-name` is never observed, the documented opt-out that lets a consumer refuse to re-process history cannot be relied upon at all.
Fix: the replay re-emission path in the eventbridge service crate — the StartReplay handler plus the replay progression/settling in the crate's state, the window selection over the archive, the FilterArns restriction applied when choosing which rules the re-emitted event is evaluated against, and the point at which `replay-name` is attached to the envelope (it must be attached BEFORE pattern evaluation, not during target serialization). The rule->SQS target delivery branch those replayed events are handed to is shared with Cause 2.

=== Cause 2 of 2: a live rule's SQS target never delivers, so a refused PutRule pattern update cannot be shown to have left the rule matching ===

AWS: Smithy models PutRule with EventPattern @length 0..4096 and the client error InvalidEventPatternException (400). A malformed pattern is refused with code `InvalidEventPatternException` and an HTTP 400, and the refusal is ATOMIC: a PutRule that updates an existing rule's pattern and is refused leaves the stored EventPattern byte-identical and the rule's State ENABLED, and the rule keeps routing exactly what its prior pattern routed; a refused PutRule under a fresh name leaves no rule at all (a later DescribeRule on that name answers ResourceNotFoundException). The message's fixed text is `Event pattern is not valid. Reason: ` followed by AWS's own reason sentence for the failure class — the reason is the variable part and is drawn from the class of malformation, e.g. `Unrecognized numeric range operator: !=` for a non-comparator operand, `Value of > must be numeric` for a string operand to a numeric comparator, `Only one key allowed in match expression` for two matchers in one object, `exists match pattern must be either true or false.` for a non-boolean exists, `Consecutive wildcard characters at pos <n>` for `**` (the position is taken from the submitted pattern), `IPv4 mask bits must be < 32` for a single-host cidr, `Empty arrays are not allowed` for `[]`, and `Unrecognized match type <op>` for an unknown operator (the operator name is taken from the request) — and then the source-location suffix `\n at [Source: (String)"<the pattern exactly as submitted>"; line: <n>, column: <c>]`, every part of which is derived from the request. TestEventPattern must refuse the same fragments with the same code and the same Reason, with one recorded exception: for a single-branch `$or` AWS's two validators word it differently (PutRule `Unrecognized match type detail`, TestEventPattern `There must have at least 2 Objects in $or relationship.`), both still InvalidEventPatternException (recorded behavior only for that split).
Emulator: `Check timed out after 60.0s`. The check is a differential: each malformed update is aimed at a rule that is ALREADY delivering to an SQS target, and the absence of the "zz" event is only asserted in a round in which the same rule provably delivered its matching "ok" event from the same PutEvents batch. That live leg never produces a message, so the check cannot complete and neither the nine refusals nor the preserved routing is observable. The rule, its target and the PutEvents call are all accepted first; only the delivery to the queue never happens.
Why: atomicity of a refused rule update is the property that makes a failed deploy safe — a client that pushes a bad pattern must be able to rely on the previous pattern still being in force and still routing. Here a client cannot confirm that at all, and because the live delivery leg is dead it cannot distinguish "the refused update was atomic" from "the refused update silently broke the rule".
Fix: the eventbridge rule-target delivery path for SQS targets in the eventbridge service crate (the PutEvents routing/dispatch branch that hands a matched event to an SQS queue target), and, paired with it, PutRule's shared event-pattern validator so each refused fragment answers InvalidEventPatternException with AWS's reason sentence plus the request-derived source-location suffix and mutates nothing. Note the open issue 20261025T002357Z-events-eventbridge-target-delivery-never-completes-for-sns-step.md covers the SNS/Step Functions target branches; this is the SQS branch under the events__sqs group and is not named there.
Traces: events__sqs.events-pattern-language-malformed-pattern-update-rejected-and-live-rule-keeps-matching.
