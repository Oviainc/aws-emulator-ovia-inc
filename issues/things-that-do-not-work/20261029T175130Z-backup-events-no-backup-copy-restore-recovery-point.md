## Description

=== Cause 1 of 5: AWS Backup publishes no state-change event of any kind onto the EventBridge default bus, so every rule, target, filter and suppression check hangs ===
AWS: recorded behavior only (the event envelope is not in either service's Smithy model). AWS Backup natively emits events on the default event bus with `source` = "aws.backup" and a `detail-type` of "Backup Job State Change", "Copy Job State Change", "Restore Job State Change" or "Recovery Point State Change", each carrying a `detail` with at least the job/recovery-point id, `backupVaultName`/`backupVaultArn`, `resourceArn` and `state`, plus the standard envelope fields (version, id, account, time, region, resources). An ENABLED rule whose pattern matches delivers that envelope UNCHANGED to every configured target — SQS queue, SNS topic (and on to an SQS subscriber), Lambda function, Step Functions state machine — and an InputTransformer rewrites it per its template. The negative half of the contract is the same emission: a pattern that does not match, an account-id filter that excludes the event, a rule whose target lacks the resource-based permission, and a restore from a nonexistent recovery point must each deliver NOTHING while a matching positive control on the same bus DOES arrive.
Emulator: nothing is ever published. services/service-com-amazonaws-backup-cryocontrollerusermanager/src/ops/start_backup_job.rs (and the rest of the job/recovery-point lifecycle in crate::state) writes vault, job and recovery-point records only — there is no emission to the EventBridge default bus anywhere in the lifecycle. Every one of the 22 checks below therefore sits in its receive loop until the harness's cap and is reported as `Error: Check timed out after 60.0s`; the suppression checks cannot even reach their negative assertion because their positive control never arrives either.
Why: any client built on Backup eventing — notify-on-completion, a queue or Lambda consumer reacting to job state, fan-out, content filtering, input transformation — observes absolutely nothing and hangs with no error distinguishing "not delivered" from "not yet". A suppression test passes vacuously against an emulator that delivers nothing at all.
Fix: the backup job / copy job / restore job / recovery-point lifecycle's event-emission path (publish a state-change event onto the EventBridge default bus on every state transition, with AWS's source, detail-type and detail members) plus the EventBridge rule-matching and target-dispatch path that must deliver one matched event to ALL of a rule's targets.
Traces: backup__events.backup-job-completed-emits-eventbridge-event, backup__events.backup-job-completed-event-delivered-to-eventbridge-rule, backup__events.backup-job-state-change-event-matches-eventbridge-rule, backup__events.backup-job-event-detail-format-preserved, backup__events.backup-job-event-resource-arn-propagated, backup__events.backup-job-failed-state-routes-to-sqs-target, backup__events.backup-describe-job-correlates-with-eventbridge-event, backup__events.backup-continuous-backup-event-delivered-to-sns-via-eventbridge, backup__events.backup-event-triggers-lambda-remediation, backup__events.backup-vault-notification-event-detail-format, backup__events.backup-vault-notifications-eventbridge-rule-scoped-by-detail-type, backup__events.copy-job-state-change-event-pattern-match, backup__events.eventbridge-content-based-filtering-on-backup-vault-name, backup__events.eventbridge-pattern-mismatch-suppressed-for-backup-source, backup__events.eventbridge-rule-account-id-filter-blocks-backup-event, backup__events.eventbridge-rule-missing-target-permission-backup-job-event-not-invoked, backup__events.eventbridge-rule-missing-target-permission-blocks-backup-event-delivery, backup__events.eventbridge-rule-scoped-to-specific-backup-vault-arn, backup__events.eventbridge-target-input-transformer-passes-backup-vault-param, backup__events.restore-from-nonexistent-recovery-point-emits-no-state-change-event, backup__events.cfn-deploy-backup-plan-with-eventbridge-notification, backup__events.cfn-deploy-backup-plan-with-eventbridge-rule-target (the last two also depend on cause 4/5).

=== Cause 2 of 5: a Step Functions Task state cannot make an `arn:aws:states:::aws-sdk:backup:*` integration call, so every EventBridge-to-SFN-to-Backup path fails States.Runtime ===
AWS: recorded behavior only (the SFN AWS SDK integration surface is not in the Smithy model). A Task state whose Resource is "arn:aws:states:::aws-sdk:backup:startBackupJob" or "arn:aws:states:::aws-sdk:backup:startCopyJob" calls that Backup API with the state machine's role and the execution reaches SUCCEEDED, carrying the API's response as the state's result; this is how EventBridge rules drive Backup through a state-machine target, and it is also how the negative half is proven (a target role WITHOUT the backup trust/permission must fail while the positive control SUCCEEDS).
Emulator: the execution ends `status='FAILED'`, `error='States.Runtime'`, `cause="state 'StartBackupJob': 'arn:aws:states:::aws-sdk:backup:startBackupJob' names an integration with 'backup', which is not one of the services this emulator makes a 'Task' state's integration call to, so nothing was run for it"` (same sentence for startCopyJob). So the positive controls fail for a reason unrelated to the authorization behavior under test, and the checks cannot distinguish "denied" from "never attempted".
Why: a client that orchestrates Backup from Step Functions — the documented way to trigger StartBackupJob from an EventBridge rule — cannot run its workflow at all, and every permission boundary built on it is untestable: the deny case and the allow case both fail identically.
Fix: the Step Functions Task-state AWS SDK integration dispatch (the `aws-sdk:<service>:<operation>` resolver in the sfn crate) must include the backup service and route startBackupJob/startCopyJob to the Backup emulator with the state machine's role.
Traces: backup__events.eventbridge-rule-triggers-startbackupjob-via-target-role, backup__events.eventbridge-role-trusts-events-service-for-backup-target, backup__events.eventbridge-role-missing-backup-trust-policy-target-not-invoked, backup__events.eventbridge-target-missing-backup-permission-not-invoked, backup__events.eventbridge-onetime-rule-triggers-start-copy-job.

=== Cause 3 of 5: StartBackupJob accepts a caller/role with no backup permission and the job always settles COMPLETED, so the permission boundary and the FAILED outcome are both unobservable ===
AWS: recorded behavior (authorization is not modeled; Smithy lists only InvalidParameterValueException/InvalidRequestException/LimitExceededException/MissingParameterValueException/ResourceNotFoundException/ServiceUnavailableException for StartBackupJob, so AccessDeniedException is the service-common refusal class). A caller that is not authorized for backup:StartBackupJob on the vault is refused AccessDeniedException and NO job is created; separately, a job started with a role that has the backup.amazonaws.com trust policy but no permissions IS accepted and then fails asynchronously — DescribeBackupJob reaches the modeled BackupJobState value FAILED with a non-empty StatusMessage, and that transition is what the "Backup Job State Change" event with detail.state=FAILED reports.
Emulator: the unauthorized call SUCCEEDS — the replay recorded HTTP 200 with a BackupJobId and a RecoveryPointArn where a refusal was required — and every accepted job settles to COMPLETED with no StatusMessage (start_backup_job.rs stores state CREATED with a single settle instant and the only transition available is to COMPLETED; no caller identity or policy is consulted anywhere).
Why: overly permissive on two axes at once — a least-privilege regression passes silently, and a client that branches on FAILED/StatusMessage can never exercise its failure path; every backup appears to succeed, including ones AWS would refuse to perform.
Fix: caller authorization in the StartBackupJob handler (refuse the AccessDeniedException class before creating job state) and the job state machine's terminal-state selection in start_backup_job.rs + crate::state, which needs a FAILED outcome carrying a StatusMessage. The FAILED half overlaps cause 1 of 20261024T031359Z-backup-events-aws-backup-job-lifecycle-and-eventing-diverge-jobs.md; the authorization half is not named by any open issue.
Traces: backup__events.eventbridge-rule-target-missing-startbackupjob-permission-denied, backup__events.backup-job-failed-event-matches-pattern.

=== Cause 4 of 5: a CloudFormation stack declaring an IAM role (with inline Policies), a Step Functions state machine and an Events rule with targets rolls back instead of creating ===
AWS: recorded behavior only. CreateStack on that template reaches CREATE_COMPLETE, GetRole reports the EventsInvokeRole whose AssumeRolePolicyDocument trusts events.amazonaws.com, DescribeRule reports State=ENABLED, and the stack Outputs resolve Fn::GetAtt RoleArn / RuleArn and Ref on the state machine.
Emulator: the stack ends in ROLLBACK_COMPLETE, so none of its resources exists and the check cannot proceed past deployment. (Which resource failed is not in the replay output — Hypothesis: one of AWS::IAM::Role with inline `Policies`, AWS::StepFunctions::StateMachine, or AWS::Events::Rule with an inline `Targets` list carrying a target RoleArn is not provisionable by the CFN resource layer.)
Why: the documented infrastructure-as-code path for backup notifications cannot be deployed at all, so every client that provisions its Backup/EventBridge wiring from a template is blocked, and the rollback gives no indication of which property is unsupported.
Fix: the CloudFormation resource-provisioning path for these types (AWS::IAM::Role inline Policies, AWS::StepFunctions::StateMachine, AWS::Events::Rule with inline Targets including RoleArn) — identify the failing resource from the stack events and make the create succeed, with Fn::GetAtt/Ref on its outputs resolving.
Traces: backup__events.cfn-deploy-iam-role-trusts-events-for-backup-notifications.

=== Cause 5 of 5: a stack that declares AWS::Lambda::Function reports success without the function existing ===
AWS: recorded behavior only. Once CreateStack reaches CREATE_COMPLETE, every declared AWS::Lambda::Function exists: lambda.GetFunction on the templated function name answers 200 with its configuration, and the EventBridge rule targeting it can invoke it.
Emulator: after the deploy step returned, lambda.GetFunction on the stack's own function name is refused ResourceNotFoundException "Function not found: arn:aws:lambda:<region>:<account>:function:<templated name>" — the stack either never created the function or reported completion without it, so the check errors out before reaching its subject (a rule target without invoke permission must not be invoked).
Why: a client cannot rely on stack completion as a provisioning guarantee: it reads back a resource the stack claims to have created and gets a not-found, which is worse than an explicit stack failure because nothing signals the gap.
Fix: the CloudFormation AWS::Lambda::Function resource provisioning (create the function in the lambda emulator during the stack create, and fail the resource rather than completing the stack if it cannot be created).
Traces: backup__events.cfn-deploy-eventbridge-rule-without-target-permission-rejected.
