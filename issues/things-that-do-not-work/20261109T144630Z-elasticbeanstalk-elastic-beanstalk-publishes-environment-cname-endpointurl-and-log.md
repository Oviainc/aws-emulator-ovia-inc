# Elastic Beanstalk publishes environment CNAME/EndpointURL and log URLs on hosts it does not serve, and 3 more divergences (5 causes)

> _Note: this issue was identified against the code base at commit `6bab9504f4457a639e729a9dc2b08c46f536304f`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEnvironments

## Description
FIVE distinct root causes in the elasticbeanstalk emulator, all in the same service, each grounded in failing behavioral checks of this suite that the replay marked neither ALREADY FILED nor OWNED. FIVE causes must be closed before submitting.

Adjacent OPEN issues describe neighbouring ground but do NOT carry these checks (the suite marked none of these failures OWNED, so their recorded replay keys no longer match): 20261107T192913Z-elasticbeanstalk-elastic-beanstalk-environments-have-no-data-plane-endpointurl.md (its Cause 1/2 read 'EndpointURL is never published' and 'nothing answers at the CNAME' — in THIS replay the emulator now DOES publish an EndpointURL and a CNAME, and the failure has moved to WHICH host it publishes, so Cause 1 below is a new, still-unowned grounding), 20261023T205650Z-elasticbeanstalk-elastic-beanstalk-control-plane-guards-are-not-enforced.md (CheckDNSAvailability guard enforcement generally, not the post-swap registry), 20261104T102022Z-elasticbeanstalk-elastic-beanstalk-state-guard-refusals-use-the-wrong.md and 20261029T180136Z-elasticbeanstalk-elastic-beanstalk-refusal-messages-use-non-aws-templates.md (other rejection paths), 20261102T085012Z-elasticbeanstalk-elastic-beanstalk-managed-action-and-platform-quota-refusals.md (managed-action refusal wording, not the Scheduled->Pending transition).

Cause 1 of 5: an environment's published CNAME and EndpointURL name '<name>.<region>.elasticbeanstalk.com', a host the emulator does not serve, so no customer of the emulator can reach the environment it just announced.
AWS: Smithy: DescribeEnvironments -> EnvironmentDescription members CNAME ('The URL to the CNAME for this environment') and EndpointURL ('For load-balanced, autoscaling environments, the URL to the LoadBalancer. For single-instance environments, the IP address of the instance'). Recorded behavior: once an environment reaches Status='Ready' the address it publishes is the address a client dials and gets the deployed bundle back from; the published address and the reachable address are the same address.
Emulator: DescribeEnvironments now publishes a non-empty CNAME/EndpointURL, but it is a real-AWS public hostname that the emulator does not listen on, so every attempt to dial it is refused by the harness's own routing with simparity.published.PublishedUrlRejected / AssertionError: "endpoint_url was given http://<env>.<region>.elasticbeanstalk.com/<path> (published by the emulator or built by the check): its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>, or http(s)://<own host>:<port>/<path> on a per-resource listener" and "DescribeEnvironments must report the CNAME the prefix minted: the emulator published http://<env>.<region>.elasticbeanstalk.com: its host is not one of the emulator's own hosts". The host/port in those messages are per-run values; the requirement is that the announced host is one the emulator answers on.
Why: the whole purpose of an Elastic Beanstalk environment is to run an application. A client reads EndpointURL/CNAME from the API and dials it: against the emulator it is sent to a public AWS domain (or to nothing at all), so every data-plane consequence of a deployment — content served, option settings becoming process environment variables, .ebextensions, rolling vs all-at-once, restart-app-server, instance health, termination freeing the address — is unobservable, and a correct client is actively mis-directed off the emulator.
Fix: the environment endpoint publication — the CNAME/EndpointURL the environment state records and the EnvironmentDescription serializer emits must be an address on one of the emulator's own listeners (its own host/port, or a per-resource listener), and that listener must serve the deployed application version. Belongs in the CreateEnvironment / UpdateEnvironment / DescribeEnvironments handlers and the service's environment state module (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/, plus the environment state module).
Traces: elasticbeanstalk.eb-deployed-application-serves-its-own-content-over-http, elasticbeanstalk.eb-describe-instances-health-reports-the-environments-real-instances, elasticbeanstalk.eb-ebextensions-config-files-really-run-on-the-instance, elasticbeanstalk.eb-ebextensions-option-setting-loses-to-the-direct-environment-setting, elasticbeanstalk.eb-restart-app-server-restarts-the-process-without-replacing-the-instance, elasticbeanstalk.eb-retrieved-environment-info-carries-the-applications-own-log-line, elasticbeanstalk.eb-rolling-deployment-keeps-serving-where-all-at-once-does-not, elasticbeanstalk.eb-saved-configuration-template-reproduces-its-option-in-a-new-environment, elasticbeanstalk.eb-terminated-environment-stops-serving-and-frees-its-cname-prefix, elasticbeanstalk.eb-abort-environment-update-withholds-the-instance-replacement, elasticbeanstalk.deploy-cfn-application-version-behaves.

Cause 2 of 5: RetrieveEnvironmentInfo's presigned log URL names s3.<region>.amazonaws.com instead of the emulator's own S3 endpoint, so the retrieved log can never be downloaded.
AWS: Smithy: RetrieveEnvironmentInfo(EnvironmentName/EnvironmentId, InfoType required) -> RetrieveEnvironmentInfoResultMessage/EnvironmentInfoDescription, member Message documented as 'The retrieved information. Currently contains a presigned Amazon S3 URL. The files are deleted after 15 minutes.' Recorded behavior: that URL is fetchable with a plain HTTP GET and returns the instance's log bytes with a matching Content-Length.
Emulator: the Message is a presigned URL whose host is the real AWS S3 endpoint — 'https://s3.<region>.amazonaws.com/elasticbeanstalk-<region>-<account>/resources/environments/logs/tail/<env-id>/<instance-id>/eb-activity.log?x-id=GetObject&X-Amz-Algorithm=AWS4-HMAC-SHA256&...' — and the fetch is refused: "the emulator published https://s3.<region>.amazonaws.com/...: its host is not one of the emulator's own hosts; a customer of the emulator needs http(s)://127.0.0.1:<port>/<resource path>". The bucket name, env id, instance id, signature and expiry are per-run values; the requirement is that the presigned URL addresses the emulator's own S3 listener.
Why: a client that follows the documented presigned URL (the only way to read tailed/bundled environment logs) is sent to public AWS, where its emulator credentials and object do not exist. Log retrieval — the single observable output of RequestEnvironmentInfo/RetrieveEnvironmentInfo — is unusable, and the round-trip of the log payload cannot be verified.
Fix: the presigned-URL construction in the RetrieveEnvironmentInfo handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/retrieve_environment_info.rs) — it must presign against the emulator's own S3 endpoint rather than a hard-coded s3.<region>.amazonaws.com host.
Traces: elasticbeanstalk.environment-info-log-payload-preserved, elasticbeanstalk.environment-info-tail-log-content-round-trip, elasticbeanstalk.retrieve-environment-info-log-content-round-trip.

Cause 3 of 5: after SwapEnvironmentCNAMEs, CheckDNSAvailability reports a prefix that is now in use as available (and still returns FullyQualifiedCNAME).
AWS: Smithy: CheckDNSAvailability(CNAMEPrefix required @length 4..63) -> CheckDNSAvailabilityResultMessage{Available: boolean, FullyQualifiedCNAME}; no modelled operation errors. Recorded behavior: a CNAME prefix an existing environment holds answers Available=false, and FullyQualifiedCNAME is ABSENT from the response (not empty) once a prefix is taken; it is returned only when Available is true. A CNAME swap moves ownership of each prefix to the other environment but leaves both prefixes in use.
Emulator: after a successful swap (both environments correctly report each other's former CNAME), CheckDNSAvailability on either swapped prefix answers HTTP 200 {'Available': True, 'FullyQualifiedCNAME': '<prefix>.<region>.elasticbeanstalk.com'} — available, and with the member AWS omits.
Why: a client that uses CheckDNSAvailability to pick a free prefix is told a prefix an environment is actively serving is free; the subsequent CreateEnvironment either collides or silently steals the address, and a client that keys on FullyQualifiedCNAME's presence to mean 'free' gets the opposite signal.
Fix: the CNAME-prefix registry consulted by the CheckDNSAvailability handler (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/check_dns_availability.rs) and its update in the SwapEnvironmentCNAMEs handler — swapping must keep both prefixes recorded as in use by their new owners, and the serializer must omit FullyQualifiedCNAME when Available is false.
Traces: elasticbeanstalk.e2e-swap-cnames-then-dns-check-flips.

Cause 4 of 5: a Scheduled managed action never becomes Pending when its maintenance window opens.
AWS: Smithy: DescribeEnvironmentManagedActions(EnvironmentName/EnvironmentId, Status) -> DescribeEnvironmentManagedActionsResult/ManagedActions; ManagedAction.Status targets enum ActionStatus with values Scheduled, Pending, Running, Unknown, documented 'The status of the managed action. If the action is Scheduled, you can apply it immediately with ApplyEnvironmentManagedAction', and ManagedAction.WindowStartTime is 'The start time of the maintenance window in which the managed action will execute'. Recorded behavior: an environment with aws:elasticbeanstalk:managedactions ManagedActionsEnabled=true and a PreferredStartTime a few minutes ahead reports the recommended platform update as Status='Scheduled', and once WindowStartTime passes the same ActionId is reported with Status='Pending' before it runs.
Emulator: the action is discovered as Scheduled and then never changes — polling DescribeEnvironmentManagedActions for the same ActionId for 900 s never observes Status='Pending' (AssertionError 'managed action never transitioned from Scheduled to Pending as the window opened'), and the action does not leave the live list either.
Why: the managed-action state machine is frozen at its initial state, so any client that waits for Pending/Running to know a managed platform update has entered its window (or that distinguishes 'apply it now' from 'it is already starting') waits forever; managed-update automation cannot be exercised at all.
Fix: the managed-action state machine — the window-driven Scheduled->Pending->Running transition in the managed-action state the DescribeEnvironmentManagedActions handler reads (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/describe_environment_managed_actions.rs and the service's managed-action state module), driven from WindowStartTime/PreferredStartTime.
Traces: elasticbeanstalk.managed-action-scheduled-then-becomes-pending-after-window.

Cause 5 of 5: RebuildEnvironment on a Terminated environment is refused with the emulator's own invalid-state sentence instead of AWS's not-found sentence.
AWS: Smithy: RebuildEnvironment(EnvironmentId, EnvironmentName @length 4..40) -> Unit, with InsufficientPrivilegesException (HTTP 403) as its only modelled operation error, so this refusal is the service-common InvalidParameterValue. Recorded behavior: a Terminated environment is not addressable by RebuildEnvironment at all — the call is refused with Error.Code 'InvalidParameterValue' / HTTP 400 and Error.Message "No Environment found for EnvironmentName = '<EnvironmentName>'.", identically whether or not the deployed application version still exists. The fixed text is "No Environment found for EnvironmentName = '" ... "'."; the only variable part is the environment name taken from the request.
Emulator: the code matches ('InvalidParameterValue'), but the message is the emulator's own state-guard wording: 'Environment <EnvironmentName> is not in a state from which it can be rebuilt. Current status: Terminated.' — a different sentence that additionally leaks the current status AWS does not report here.
Why: AWS reports this class as 'that environment does not exist', the emulator as 'that environment exists but is in the wrong state'. A client keying on AWS's not-found sentence does not recognise the refusal, and one parsing the emulator's text concludes a terminated environment is still addressable and retries waiting for a state change that will never come.
Fix: the terminated-environment branch of the RebuildEnvironment handler's validation (services/service-com-amazonaws-elasticbeanstalk-awselasticbeanstalkservice/src/ops/rebuild_environment.rs) — a Terminated environment must be invisible to this lookup and refused with AWS's "No Environment found for EnvironmentName = '<name>'." template, with only the request's environment name substituted.
Traces: elasticbeanstalk.rebuild-terminated-environment-version-deleted-rejected.
