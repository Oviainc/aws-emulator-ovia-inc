## Description

=== Cause 1 of 3: TestConnection can never report a usable connection — Status is unconditionally ERROR and SftpConnectionDetails is never populated, so every connector-gated flow spins forever ===
AWS: Smithy TestConnection input ConnectorId (@required, len 19..19, pattern ^c-([0-9a-f]{17})$); output {ConnectorId, Status, StatusMessage, SftpConnectionDetails (SftpConnectorConnectionDetails, carrying HostKey)}; modeled errors InternalServiceError 503, InvalidRequestException 400, ResourceNotFoundException 404, ServiceUnavailableException 503. The model documents Status as 'OK for successful test, or ERROR if the test fails', StatusMessage as 'Connection succeeded' on success, and SftpConnectionDetails as the structure carrying the connector host key observed on the initial connection attempt. Recorded behavior: for an SFTP connector whose Url names a reachable Transfer server and whose SftpConfig.UserSecretId holds that server user's {Username, PrivateKey}, TestConnection eventually returns SftpConnectionDetails.HostKey; after UpdateConnector pins that key as SftpConfig.TrustedHostKeys, a subsequent TestConnection returns Status='OK'. The host key VALUE is environment-specific and is not a requirement — only that a key is reported, and that the pinned-key retest reaches Status 'OK' with a success StatusMessage.
Emulator: services/service-com-amazonaws-transfer-transferservice/src/ops/test_connection.rs returns, for every connector that configures SftpConfig, status = crate::state::TEST_CONNECTION_STATUS_ERROR and sftp_connection_details: None unconditionally (its own module doc states the emulator 'opens no outbound connection, so no session can run here ... this handler reports neither'). It never resolves the Transfer server its connector Url names inside the same emulator. Status therefore never becomes 'OK' and no host key is ever observable.
Why: a client cannot bring a connector into service at all. The AWS-documented provisioning sequence — probe TestConnection, read SftpConnectionDetails.HostKey, pin it with UpdateConnector, re-probe until Status 'OK', then transfer — never advances, so the caller hangs instead of failing, and cannot distinguish 'this connector is misconfigured' (a real ERROR verdict) from 'this target does not evaluate connections'. All four checks are killed inside exactly these poll loops at the suite's 60s per-check budget, having raised no assertion at all.
Fix: the TestConnection handler (src/ops/test_connection.rs) and the connector state it reads must derive the verdict from the emulated target: resolve the Transfer server named by the connector Url, report that server's host key in SftpConnectionDetails.HostKey, and answer Status 'OK' with the success StatusMessage when the stored secret and TrustedHostKeys match it — while keeping Status 'ERROR' with the defect-naming StatusMessage when they do not.
Traces: transfer.e2e-connector-remote-directory-flow, transfer.e2e-server-user-file-transfer-flow, transfer.file-transfer-result-status-visibility-ttl, transfer.workflow-step-state-out-of-order-rejected.

=== Cause 2 of 3: every operation a connector accepts is recorded QUEUED and never advanced or applied — ListFileTransferResults never reaches a terminal StatusCode, and StartRemoteMove/StartRemoteDelete/StartDirectoryListing change nothing in the backing storage ===
AWS: Smithy StartFileTransfer(ConnectorId @required, SendFilePaths @length 1..10, RemoteDirectoryPath) -> TransferId @required; ListFileTransferResults(ConnectorId, TransferId @required) -> FileTransferResults @required (list 0..1000, entries carrying StatusCode, FilePath and, on failure, FailureCode/FailureMessage) + NextToken; StartRemoteMove(ConnectorId, SourcePath, TargetPath @required) -> MoveId @required; StartRemoteDelete(ConnectorId, DeletePath @required) -> DeleteId @required; StartDirectoryListing(ConnectorId, RemoteDirectoryPath, OutputDirectoryPath @required) -> {ListingId, OutputFileName} @required. Recorded behavior: an accepted transfer leaves QUEUED and reaches a TERMINAL StatusCode — COMPLETED (or FAILED with FailureCode/FailureMessage) — with FilePath equal to the path that was sent, and the effect is observable in the remote storage: the sent bytes land under RemoteDirectoryPath, a move makes the source path absent and the target path present with identical bytes, a delete makes the path absent, and a listing written to OutputDirectoryPath reflects what is actually there.
Emulator: accepted connector work is recorded and never progressed. src/ops/start_remote_move.rs:15-18 states it plainly: 'the accepted request stays QUEUED, like every other operation a connector accepts (crate::state::ConnectorTransfer), and nothing here reports a file as moved.' src/ops/list_file_transfer_results.rs returns whatever crate::state::ConnectorTransfer::results() holds, i.e. the non-terminal QUEUED entries, forever. No S3 object is created, moved or deleted by any of these operations.
Why: the entire purpose of the connector plane is to move bytes and let the caller observe the outcome. A client following AWS's flow polls ListFileTransferResults for COMPLETED/FAILED and never gets either, so a CI job or orchestration step modelled on real Transfer Family never terminates; and code that verifies the effect in S3 (bytes landed, source gone after a move, path gone after a delete) sees unchanged storage with no error reported anywhere.
Fix: the connector data-plane state machine — crate::state ConnectorTransfer plus the StartFileTransfer, StartRemoteMove, StartRemoteDelete, StartDirectoryListing and ListFileTransferResults handlers in src/ops — must advance an accepted record to a terminal state and apply it against the emulated storage the connector's Url/paths name: a sent file written at RemoteDirectoryPath with a COMPLETED result whose FilePath is the sent path, a move relocating the object, a delete removing it, and a listing serialized to OutputFileName under OutputDirectoryPath.
Traces: transfer.e2e-connector-remote-directory-flow (polls S3 for the moved/deleted object and for a listing that no longer shows it), transfer.e2e-server-user-file-transfer-flow and transfer.file-transfer-result-status-visibility-ttl (poll ListFileTransferResults for COMPLETED and then read the landed bytes). Both are reached only once cause 1 is fixed.

=== Cause 3 of 3: an upload through the connector fires no OnUpload workflow execution, so no CUSTOM step callback token is ever issued and the replayed-token refusal cannot occur ===
AWS: Smithy CreateWorkflow(Steps with Type CUSTOM and CustomStepDetails{Name, Target, TimeoutSeconds, SourceFileLocation}); UpdateServer(WorkflowDetails.OnUpload=[{WorkflowId, ExecutionRole}]); SendWorkflowStepState(WorkflowId, ExecutionId, Token, Status @required) -> empty output, with modeled errors AccessDeniedException 403, InvalidRequestException 400, ResourceNotFoundException 404, ThrottlingException 429, InternalServiceError/ServiceUnavailableException 503; ListExecutions/DescribeExecution(WorkflowId, ExecutionId @required). Recorded behavior: a file uploaded over SFTP to a server whose WorkflowDetails.OnUpload names the workflow starts an execution, the CUSTOM step invokes its Lambda Target with serviceMetadata.executionDetails.{workflowId, executionId} and a callback token, and the step's in-order SendWorkflowStepState(Status='SUCCESS') succeeds. Replaying that SAME token after the step has already completed is refused with HTTP 404 ResourceNotFoundException and the message 'Unknown execution' — the message is fixed text with no request-derived part — and DescribeExecution's answer for that ExecutionId is unchanged by the refused replay.
Emulator: the check never reaches this assertion because it stalls at cause 1, and nothing in the connector/upload path creates a workflow execution: the connector push is only recorded as a QUEUED ConnectorTransfer (cause 2), so no OnUpload execution, no CUSTOM-step invocation and no callback token exist for SendWorkflowStepState to accept or later refuse. Hypothesis (neither the model nor the replay output states this, since the check is killed before the call): with no execution record, a replayed SendWorkflowStepState cannot produce the 404 ResourceNotFoundException 'Unknown execution' that AWS returns for a consumed token.
Why: a client that builds the documented managed-workflow pattern (OnUpload workflow + CUSTOM step + callback) sees its workflow never run on upload, and the at-most-once guarantee of a callback token — the thing that makes the token safe to retry against — cannot be exercised at all, so retry/idempotency logic written against real Transfer Family is untestable here.
Fix: the server upload path and the workflow/execution state in the transfer crate (crate::state executions plus the SendWorkflowStepState, ListExecutions and DescribeExecution handlers in src/ops) must start an execution for a server whose WorkflowDetails.OnUpload names a workflow when a file arrives through that server, issue the CUSTOM step's callback token, accept the in-order SendWorkflowStepState once, and refuse a replay of the same token with the modeled 404 ResourceNotFoundException whose message is exactly 'Unknown execution', leaving DescribeExecution's answer unchanged.
Traces: transfer.workflow-step-state-out-of-order-rejected.
