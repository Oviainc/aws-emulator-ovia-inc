# Redshift reference-catalog reads serve empty or synthesized data

> _Note: this issue was identified against the code base at commit `7e082a9dfef7650059a714e1b731386462df20dc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeEventCategories

## Description
Three net-new causes, all in the same family: Redshift's read-only *reference catalog* operations — the ones whose whole response body is service-published static data rather than account state — are served from emulator-authored or empty data, and one of them ignores its modeled request filter. Each replays at HTTP 200 on both sides, so the divergence is entirely in the payload: a client sees a well-formed but wrong or empty catalog. All three are DISTINCT causes in distinct handlers and each must be closed separately.

=== Cause 1 of 3: DescribeEventCategories returns an empty EventCategoriesMapList ===
AWS: Smithy: DescribeEventCategories -> output EventCategoriesMessage.EventCategoriesMapList (list of EventCategoriesMap). EventCategoriesMap = {SourceType: String, Events: EventInfoMapList}; EventInfoMap = {EventId, EventCategories, EventDescription, Severity ("Values: ERROR, INFO")}. The model documents SourceType as "The source type, such as cluster or cluster-snapshot, that the returned categories belong to" and Events as "The events in the event category". The model does not enumerate the catalog rows themselves, so the row content is recorded behavior only: the recording returns one EventCategoriesMap per Redshift source type (the replay asserts indices [0]..[5], i.e. six source-type groups), and each group carries its EventInfoMap rows — e.g. SourceType 'cluster' with EventId REDSHIFT-EVENT-2000 / Severity INFO / EventCategories.EventCategory 'management' / EventDescription 'Cluster <cluster name> created at <time in UTC>.', REDSHIFT-EVENT-2001 ('Cluster <cluster name> deleted at <time in UTC>.', management), REDSHIFT-EVENT-3000/3001/3014/3016 (monitoring), REDSHIFT-EVENT-3015 (pending), REDSHIFT-EVENT-4000 (security), REDSHIFT-EVENT-4502 (ERROR, security). Note these EventDescription strings are AWS's TEMPLATES: the fixed text is the sentence, and '<cluster name>', '<time in UTC>', '<start time in UTC>', '<end time in UTC>' are literal placeholder tokens AWS itself emits in this catalog — they are not values from any request or any run.
Emulator: every asserted EventCategoriesMap index is reported 'missing' — EventCategoriesMapList comes back with no members at all, so the operation returns a 200 with an empty catalog.
Why: DescribeEventCategories is how a client discovers which event categories and source types exist before calling CreateEventSubscription / ModifyEventSubscription with an EventCategories or SourceType filter. With an empty list, any client that validates its requested categories against the catalog, or that renders a category picker, concludes Redshift supports no event categories at all and cannot build a subscription; no amount of account state changes the answer, because the catalog is service-published.
Fix: the DescribeEventCategories handler / its static reference-data table in the redshift service crate — the catalog must be seeded with the Redshift source types and their EventInfoMap rows (EventId, Severity, EventCategories, EventDescription template) and filtered by the request's optional SourceType member.
Traces: redshift-catalog-describe-event-categories#task#1.

=== Cause 2 of 3: DescribeReservedNodeOfferings serves a synthesized offerings catalog instead of the published one ===
AWS: Smithy: DescribeReservedNodeOfferings -> ReservedNodeOfferingsMessage{Marker, ReservedNodeOfferings: ReservedNodeOfferingList}, errors DependentServiceUnavailableFault(400), ReservedNodeOfferingNotFound(404), UnsupportedOperation(400); paginated by Marker/MaxRecords. ReservedNodeOffering = {ReservedNodeOfferingId, NodeType, Duration (Integer, "duration, in seconds, for which the offering will reserve the node"), FixedPrice (Double), UsagePrice (Double), CurrencyCode, OfferingType ("anticipated utilization ... as defined in the reserved node offering"), RecurringCharges, ReservedNodeOfferingType (enum)}. The specific rows are a service-published price list, so the catalog contents are recorded behavior only: the recording returns a catalog spanning the current reserved-node families and both term lengths — entries with NodeType values in the rg.* family (e.g. rg.large, rg.xlarge), Duration 94608000 (3-year) alongside 31536000 (1-year), and all three OfferingType values ('All Upfront', 'No Upfront', 'Partial Upfront') with the matching FixedPrice/UsagePrice/RecurringCharges combination for each (All Upfront => nonzero FixedPrice with a 0.0 hourly RecurringChargeAmount; No Upfront => FixedPrice 0.0 with a nonzero hourly RecurringChargeAmount). The replay asserts 60 rows, indices [0]..[59].
Emulator: all 60 asserted rows diverge. The emulator answers 200 with a catalog whose every row is NodeType 'dc2.large' and Duration 31536000 only — no rg.* node types and no 3-year (94608000) term appear at all — and whose ReservedNodeOfferingIds are freshly generated GUIDs per boot rather than the stable published offering identifiers. The per-run GUIDs themselves are not the requirement being asserted here; the structural divergence is that the catalog covers one node type and one term instead of the published node-type families and both term lengths, so both the row count and every row's NodeType/Duration/OfferingType/pricing tuple are wrong.
Why: this operation is the input to PurchaseReservedNodeOffering and to any cost-planning or reserved-node-exchange flow. A client that looks up a 3-year rg.xlarge All-Upfront offering — or any offering outside dc2.large/1-year — finds none and cannot proceed, and a client that caches ReservedNodeOfferingId across restarts finds every cached id invalid because the ids are regenerated.
Fix: the DescribeReservedNodeOfferings handler and the reserved-node offering reference table it reads in the redshift service crate — seed the published offering rows (stable ReservedNodeOfferingId, NodeType families, both Duration terms, OfferingType with its consistent FixedPrice/UsagePrice/RecurringCharges) instead of generating them, and keep the ids stable across boots; honor the ReservedNodeOfferingId filter and Marker/MaxRecords pagination over that table.
Traces: redshift-catalog-describe-reserved-node-offerings#task#1.

=== Cause 3 of 3: DescribeClusterTracks ignores the MaintenanceTrackName filter and returns the whole track list ===
AWS: Smithy: DescribeClusterTracks -> TrackListMessage{MaintenanceTracks: TrackList, Marker}, input {MaintenanceTrackName: String, MaxRecords, Marker}, errors InvalidClusterTrack(400), UnauthorizedOperation(400); paginated by Marker/MaxRecords. MaintenanceTrack = {MaintenanceTrackName ("Possible values are current and trailing"), DatabaseVersion ("The version number for the cluster release"), UpdateTargets: EligibleTracksToUpdateList}. The recording returns EXACTLY ONE top-level MaintenanceTracks member — the 'current' track — carrying its UpdateTargets.UpdateTarget for 'trailing' with that target's DatabaseVersion and SupportedOperations ('restore-from-cluster-snapshot', 'modify-cluster'). Hypothesis: the step supplies MaintenanceTrackName, and AWS returns only the named track; the model binds MaintenanceTrackName as an input member, which is consistent with a single-member result.
Emulator: returns 200 with a TWO-member MaintenanceTracks list — both 'current' and 'trailing' as top-level entries, each pointing at the other via UpdateTargets — so the replay reports a type_mismatch at $.DescribeClusterTracksResponse.DescribeClusterTracksResult.MaintenanceTracks.MaintenanceTrack: a single serialized element (which the Query/XML response parses as one object) versus a two-element list. The concrete DatabaseVersion strings differ too, but a release version is environment data and is NOT the requirement here; the requirement is the result CARDINALITY — only the requested track must be returned, with the other track appearing solely inside UpdateTargets.
Why: a client that asks for one maintenance track and switch-cases on the single returned element gets a list and either mis-parses the response or reads the wrong track's DatabaseVersion, and any client using MaintenanceTrackName as a server-side filter silently receives unfiltered data — so a cluster can be pinned to the wrong release track.
Fix: the DescribeClusterTracks handler in the redshift service crate — apply the request's MaintenanceTrackName filter to the track list before serializing (and refuse an unknown name with InvalidClusterTrack, per the modeled error), rather than always returning the full table.
Traces: redshift-static-catalog-metadata-reads#task#2.
