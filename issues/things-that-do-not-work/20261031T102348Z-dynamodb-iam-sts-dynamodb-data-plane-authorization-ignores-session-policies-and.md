# DynamoDB data-plane authorization ignores session policies and carries no condition context, so an explicit session-policy Deny is served and a LeadingKeys/PrincipalTag grant never matches (2 causes)

> _Note: this issue was identified against the code base at commit `3227a483a6739d1d495ce0f6668dabbc01e8fd5a`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetItem

## Description
This issue bundles TWO distinct net-new root causes in the DynamoDB data-plane authorization gate as exercised by assumed-role sessions. A fixer must close BOTH before submitting. Neither replay key is carried by an existing issue: open issue 20261024T065715Z-dynamodb-iam-sts-dynamodb-data-plane-reads-are-never-authorized-identity.md records the earlier state in which NO authorization happened at all (the gate now exists — the implicit-deny control and the resource-policy control of the explicit-deny check both pass), and open issue 20261029T180026Z-dynamodb-iam-sts-dynamodb-ignores-dynamodb-leadingkeys-with-a-principal-tag.md records the LeadingKeys check in its earlier failure mode (the cross-tenant read SUCCEEDED); both issues are named here for cross-reference only, they do not cover the two behaviors below.

Cause 1 of 2: an explicit Deny in the INLINE SESSION POLICY passed to sts:AssumeRole is not evaluated for a DynamoDB data-plane call, so the call is served.
AWS: a request by an assumed-role session is authorized against the role's identity-based policies INTERSECT the session policy passed at AssumeRole time (and the table's resource-based policy), and an explicit Deny in ANY of those wins over every Allow. A session whose session policy contains {"Effect":"Deny","Action":"dynamodb:GetItem","Resource":<table arn>} is refused with AccessDeniedException, HTTP 400, message "User: <session principal ARN> is not authorized to perform: dynamodb:GetItem on resource: <table ARN> with an explicit deny in a session policy" — fixed text is "User: ", " is not authorized to perform: dynamodb:GetItem on resource: " and the trailing attribution " with an explicit deny in a session policy"; the variable parts are the session principal ARN (the AssumedRoleUser ARN STS returned for that session) and the table ARN from the request. The deny names only GetItem, so PutItem in the SAME session still succeeds. Recorded behavior only for the refusal itself: the Smithy model for GetItem/Query declares errors InternalServerError, InvalidEndpointException, ProvisionedThroughputExceededException, RequestLimitExceeded, ResourceNotFoundException and ThrottlingException and no AccessDeniedException, and carries no authorization trait, so the oracle is the recorded AWS response.
Emulator: GetItem returns HTTP 200 with the item ({'Item': {'v': {'S': 'seed'}, 'pk': {'S': 'seed'}}}) under the denying session, for both the role granted by its identity policy and the role granted only by the table's resource policy. The gate at services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/ops/get_item.rs (crate::state::policy_denial) decides from exactly two inputs — the table's resource policy and the identity-based documents the IAM store holds for the role (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state/authorization.rs, Caller::documents, populated from principal_policies(role_arn)). The session policy minted into the credential is never part of that set, so it can neither deny nor scope down; the Allow-only session-policy control "passes" only because the role's own grant admits the read.
Why: a client that scopes down a credential before handing it out (the standard confused-deputy and least-privilege pattern, and what every session-policy-based broker relies on) gets the UNSCOPED permissions of the role: the Deny it attached is silently dropped, and the AccessDeniedException its code must handle never occurs. A design validated against the emulator leaks exactly what the session policy was written to forbid.
Fix: the DynamoDB data-plane authorization path — crate::state::authorization must collect the session's inline/managed session policy from the STS session the access key resolves to and include it in the evaluation as a separate scoping document (explicit Deny wins; an Allow is required from both the identity set and the session policy), and the refusal wording must attribute the decision to the session policy.
Traces: dynamodb__iam__sts.xsvc-dynamodb-2-explicit-deny-beats-identity-and-resource-policy-allow.

Cause 2 of 2: the data-plane gate passes NO request condition context, so an identity-policy Allow conditioned on dynamodb:LeadingKeys = ${aws:PrincipalTag/tenant} never grants and the caller's OWN partition is refused.
AWS: dynamodb:LeadingKeys is evaluated against the partition-key value(s) the request addresses, and ${aws:PrincipalTag/<key>} is substituted from the session tags STS attached at AssumeRole time. A session tagged tenant=tenant-one therefore GETs, PUTs and QUERIEs pk='tenant-one' successfully (HTTP 200), while the same role's session tagged tenant-two is refused on that partition with AccessDeniedException, HTTP 400, "User: <session principal ARN> is not authorized to perform: dynamodb:GetItem on resource: <table ARN> because no identity-based policy allows the dynamodb:GetItem action" (fixed text as quoted, with the action name repeated for the operation actually called — GetItem/PutItem/Query — and the session ARN and table ARN taken from the request/state), and an UNTAGGED session of the same role is refused on both partitions. Recorded behavior only (same model note as cause 1).
Emulator: the check no longer reaches its cross-tenant assertion at all — it runs past the harness cap ("Check timed out after 60.0s"). The gate builds its request as iam::Request::new(action, table_arn, principals) with no condition context (services/service-com-amazonaws-dynamodb-dynamodb-20120810/src/state/authorization.rs), and services/common/src/iam_authorization.rs documents that a clause whose key the request context does not carry makes the statement UNDECIDED and that "an undecided statement never grants". Hypothesis for the timeout: the conditioned Allow is therefore undecided, so the tenant's OWN-partition read is refused AccessDeniedException and the check's bounded 90 s AccessDenied retry on that positive control outruns the 60 s cap. Either way the emulator does not serve the own-tenant read AWS serves, and the condition key that would separate the tenants is never evaluated.
Why: this is over-restrictive in the direction that breaks the caller (the tenant cannot read its own partition) on top of the over-permissive direction already filed: dynamodb:LeadingKeys with a principal-tag variable is THE mechanism for single-table multi-tenancy, and in the emulator it neither grants the owner nor refuses the stranger on evidence — it decides by default.
Fix: the DynamoDB data-plane handlers must build the IAM condition context for the request — dynamodb:LeadingKeys from the partition-key value(s) the GetItem Key / PutItem Item / Query KeyConditionExpression addresses, dynamodb:Attributes where projected, and aws:PrincipalTag/<key> from the STS session's tags — and pass it through iam::Request::context so services/common/src/iam_authorization.rs can decide the clause instead of leaving it undecided.
Traces: dynamodb__iam__sts.xsvc-dynamodb-2-leading-keys-principal-tag-variable-cross-tenant-denied.
