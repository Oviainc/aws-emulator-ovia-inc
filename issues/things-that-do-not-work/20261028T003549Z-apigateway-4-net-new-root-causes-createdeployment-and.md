=== Cause 1 of 4: CreateDeployment refuses an out-of-charset stageName with the wrong message body — emulator-authored text that also echoes the offending value AWS never echoes ===
AWS: Smithy (com.amazonaws.apigateway#BackplaneControlService) CreateDeployment — POST /restapis/{restApiId}/deployments, success code 201. `stageName` is a plain `String` member with NO @pattern and NO @length in the model, so the stage-name charset rule is enforced only server-side; modeled errors are BadRequestException (400), ConflictException (409), LimitExceededException (429), NotFoundException (404), ServiceUnavailableException (503), TooManyRequestsException (429), UnauthorizedException (401). Recorded behavior: a stageName containing any character outside [A-Za-z0-9_-] is refused with HTTP 400, Error.Code `BadRequestException`, and the message `Stage name only allows a-zA-Z0-9_` — that string is ENTIRELY fixed text, with NO variable parts: AWS does not quote the rejected value, does not name the member, and does not mention hyphens even though a hyphen is in fact accepted (the check's own positive control deploys stage `good-stage_1` successfully). The refusal must also leave no stage behind: a following GetStage on the malformed name answers 404 NotFoundException with the fixed message `Invalid stage identifier specified`.
Emulator: the error CODE and class are right (BadRequestException) but the message body is emulator-authored. The replay shows `stageName may contain only alphanumeric characters, hyphens and underscores, got "bad stage!"` — different fixed text, the member name `stageName` prepended, and the request's own stageName value interpolated at the end (`bad stage!` here is the value this run sent; the template, not that literal, is what matters — the defect is that AWS's message has no such slot at all).
Why: the HTTP status, the error code and the error MESSAGE are all requirements. Clients and infrastructure tools that match on API Gateway's documented refusal text (`Stage name only allows a-zA-Z0-9_`) to distinguish a bad stage name from the other BadRequestException causes CreateDeployment can raise (no methods on the API, bad cache cluster size, bad canary settings) cannot tell them apart against this emulator; a value echoed back where AWS echoes nothing also leaks request content into a message consumers log and assert on.
Fix: the stageName validation step of the CreateDeployment handler — its refusal-message construction must emit AWS's fixed sentence verbatim and interpolate nothing, while keeping the modeled BadRequestException (400) class and the existing effect-absent behavior (no stage created). The permissive charset itself is correct and must stay: hyphen and underscore are accepted.

=== Cause 2 of 4: UpdateIntegrationResponse refuses an invalid /contentHandling patch value with the generic patch-path message instead of API Gateway's ContentHandlingType sentence ===
AWS: Smithy UpdateIntegrationResponse — PATCH /restapis/{restApiId}/resources/{resourceId}/methods/{httpMethod}/integration/responses/{statusCode}, success code 200; input `patchOperations` is a ListOfPatchOperation; the output member `contentHandling` targets the enum `ContentHandlingStrategy`, whose only members are CONVERT_TO_BINARY and CONVERT_TO_TEXT; modeled errors BadRequestException (400), ConflictException (409), LimitExceededException (429), NotFoundException (404), TooManyRequestsException (429), UnauthorizedException (401). Because the value arrives inside a patch operation as a free string, the enum is not enforced by the protocol and the service validates it. Recorded behavior: a `replace /contentHandling` whose value is not one of the two enum members is refused with HTTP 400, Error.Code `BadRequestException`, message `Invalid ContentHandlingType specified. Valid options are CONVERT_TO_BINARY,CONVERT_TO_TEXT` — entirely fixed text, with NO variable parts (the rejected value is not quoted, the patch path is not named, and the two options are comma-separated with no space after the comma). The refusal is also side-effect free: the integration response keeps exactly what the preceding valid patch left (`contentHandling` = CONVERT_TO_TEXT and the original responseTemplates), neither the invalid value nor a revert.
Emulator: code BadRequestException is right; the message is the crate's generic patch-value message — `/contentHandling takes one of CONVERT_TO_BINARY, CONVERT_TO_TEXT, got "NOT_A_REAL_ENCODING"` — which leads with the JSON-pointer path, uses `takes one of` with a space after the comma, and interpolates the rejected value (here `NOT_A_REAL_ENCODING`, a per-run request value; the slot itself is the defect, since AWS's message has none).
Why: the message is a requirement. A client distinguishing "this enum value is wrong" from the other reasons a patchOperations request is refused (unsupported path, unsupported op, bad index) has only the message to go on, since every one of them is BadRequestException/400; AWS's text names the TYPE (`ContentHandlingType`), the emulator's names the PATH, so error-text matching and operator triage both break. Note the positive control in this same check — the identical patch with CONVERT_TO_TEXT succeeds and is persisted — so the handler is otherwise correct and this is purely the refusal's wording.
Fix: the patchOperations value-validation component used by the UpdateIntegrationResponse handler (the shared patch validator that today renders `<path> takes one of ...`) must special-case /contentHandling to AWS's fixed sentence above, keeping BadRequestException (400) and the already-correct no-mutation-on-refusal behavior.
Traces: apigateway.update-integration-response-invalid-template-bad-request.

=== Cause 3 of 4: RejectDomainNameAccessAssociation answers 501 NotImplemented when raced against DeleteDomainNameAccessAssociation, so neither legal outcome of the race is reachable ===
AWS: Smithy RejectDomainNameAccessAssociation — POST /rejectdomainnameaccessassociations, success code 202, required query members `domainNameAccessAssociationArn` and `domainNameArn`; modeled errors BadRequestException (400), ConflictException (409), NotFoundException (404), TooManyRequestsException (429), UnauthorizedException (401). Its documentation scopes it to an association whose source lives in ANOTHER AWS account and directs an owner to DeleteDomainNameAccessAssociation for their own, so rejecting an association the caller owns is never a legal transition. Recorded behavior, racing Reject against Delete on one same-account association: Delete always succeeds, and Reject is always refused with exactly one of two fully fixed pairs — (`BadRequestException`, `Cannot reject the domain name access association when the private custom domain and domain name access association are in the same account.`) when Reject is evaluated while the association still exists, or (`NotFoundException`, `This private custom domain name doesn't have any domain name access associations.`) when Delete won the race and removed it first. Both messages are entirely fixed: no ARN, id, domain name or count is interpolated. Two further requirements the race carries: the terminal state is single and consistent — after the race the association ARN is absent from GetDomainNameAccessAssociations and Reject has never left it half-applied — and the id is DEAD, not merely unlisted, so a further DeleteDomainNameAccessAssociation on it is refused with that same NotFoundException pair.
Emulator: the Reject arm never reaches either outcome. The replay reports Error.Code `NotImplemented` with the scaffold message `operation RejectDomainNameAccessAssociation is scaffolded but not implemented in this emulator`, i.e. a 501 server-class refusal for a resolved, held, same-account pair. The report does NOT mark this check ALREADY FILED, so no unimplemented-operation issue carries it.
RELATED, and specifically why this is still open work: 20261027T111730Z-apigateway-the-domain-name-access-association-surface-diverges.md Cause 3 describes the same stub for the SEQUENTIAL same-account Reject, but its Issue-Trace-Ids list only create-domain-name-access-association-without-vpce-fails, concurrent-domain-name-access-association-duplicate, reject-domain-name-access-association-removes-pending and reject-domain-name-access-association-wrong-state-fails. It does not carry apigateway.domain-access-association-concurrent-reject-delete, so the concurrency requirements above — the NotFoundException alternative when Delete wins, the single consistent terminal state, and the dead-id second Delete — are not gated by it and a fix verified only against that issue's four ids can still leave this race wrong.
Why: a 501 is a server-class error. SDK retry policies and most client error handling treat NotImplemented as a transient server fault and retry, where AWS is stating a permanent client-side refusal; the caller can therefore neither learn that same-account associations must be deleted rather than rejected, nor observe that a concurrent Reject/Delete settles on one terminal state. The documented ownership rule and the race's atomicity are both untestable against this emulator.
Fix: the resolved-pair branch of the RejectDomainNameAccessAssociation handler — once both ARNs resolve under the same lock hold that Delete takes, a pair whose access-association source belongs to the caller's own account must be refused with the modeled BadRequestException (400) carrying AWS's fixed same-account sentence and the stored association left untouched; a pair whose association is already gone (the Delete-won-the-race path) must be refused with the modeled NotFoundException (404) carrying AWS's fixed no-associations sentence; and the association id must be retired, not just unlisted, so a repeat Delete answers that same NotFoundException. The cross-account 202 success path remains this operation's separate remaining work.

=== Cause 4 of 4: a CloudFormation-provisioned AWS::ApiGateway::Deployment never converges — neither the control stack's served stage nor the method-less stack's rejection+rollback is reached inside the check budget ===
AWS: CloudFormation + API Gateway. Two stacks differing by exactly one resource are launched together. The control stack (RestApi + Resource `/old` + Method GET with a MOCK integration and an IntegrationResponse template + Deployment DependsOn the Method + Stage) reaches `CREATE_COMPLETE`, and its stage serves `GET /old` as HTTP 200 with the MOCK integration's rendered response template. The broken stack omits the Method, so creating the Deployment on a method-less RestApi is refused: Smithy CreateDeployment models BadRequestException (400) and real API Gateway refuses a deployment of an API with no methods with that 400 (recorded reason text contains the fixed phrase `doesn't contain any methods`). CloudFormation surfaces that as exactly one `Deployment` / `CREATE_FAILED` stack event whose `ResourceStatusReason` carries `HandlerErrorCode: InvalidRequest` and `Status Code: 400` plus that phrase, with `Deployment` the ONLY CREATE_FAILED logical id; the stack then settles at `ROLLBACK_COMPLETE` and every resource it had created is deleted (`Api` and `OldResource` reach DELETE_COMPLETE, and GetRestApi on the rolled-back physical id answers 404 NotFoundException). The control stack keeps serving `GET /old` = 200 after the broken stack has rolled back.
Emulator: the check never completes — the replay verdict is `Check timed out after 60.0s`, with no assertion reached. Everything the check does before its first assertion is two CreateStack calls and then two blocking waits: `_wait_stack(control)` (polls DescribeStacks every 5 s for a status without `IN_PROGRESS`, 900 s budget) and `_poll_http(control stage GET /old == 200)` (120 s budget). Both budgets exceed the 60 s harness budget, so the timeout means the control stack never left IN_PROGRESS and/or its deployed stage never answered 200 — the broken stack's rejection and rollback are never even examined. Hypothesis (neither the model nor the replay states which of the two stalls): the CloudFormation provisioner for AWS::ApiGateway::Deployment/Stage does not drive these resources to a terminal state, which is the same family of non-convergence that 20261023T125454Z-apigateway-cloudformation-provisioned-api-gateway-resources-are-unaddressable-through.md and 20261024T043741Z-apigateway-api-gateway-6-control-plane-convergence-causes-updateaccount.md report for sibling CFN checks; neither of those issues carries this check id, and this check uniquely asserts the method-less-Deployment rejection and the rollback-to-nothing differential.
Why: a client cannot provision an API Gateway REST API through CloudFormation at all against this emulator — a stack that hangs IN_PROGRESS is indistinguishable from one still working, so every deploy-time guarantee built on it is lost: the `DependsOn: <Method>` idiom cannot be validated, a Deployment on a method-less API is never refused (the over-permissive direction: CloudFormation reports no failure where AWS fails the resource with InvalidRequest/400), and failed-stack rollback is never observed to delete the RestApi it created, so test suites that rely on rollback leaving no resources behind will leak them.
Fix: the CloudFormation provisioner's resource handlers for AWS::ApiGateway::Deployment and AWS::ApiGateway::Stage, plus the stack state machine that must take CreateStack to a terminal status — a Deployment created against a RestApi with no methods must fail the resource with CloudFormation's InvalidRequest/400 reason carrying API Gateway's `doesn't contain any methods` text, mark only that logical id CREATE_FAILED, roll the stack back to ROLLBACK_COMPLETE deleting the already-created RestApi and Resource, and the successful variant must reach CREATE_COMPLETE with its stage served by the data plane.
