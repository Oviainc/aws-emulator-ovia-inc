# CloudWatch Logs subscription/destination plumbing: a logical-destination subscription is refused without roleArn, a wildcard destination policy is accepted, and the per-group filter quota is 2 instead of 5 (3 causes)

> _Note: this issue was identified against the code base at commit `b85e004afeca5b94af710d01f72a017b1b3c1318`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutSubscriptionFilter

## Description
Three net-new root causes in the CloudWatch Logs (`logs`) subscription-filter / destination surface. Cause count: 3 — each is numbered below with its own failing check ids, and ALL THREE must be closed before this issue is submitted.

SERVICE ATTRIBUTION: causes 1 and 2 are grounded in checks whose id leads with `logs.`. Cause 3 additionally cites a check whose id carries the compound leading token `kinesis__logs.`; the operation that diverges there is `logs:PutSubscriptionFilter` (the check never reaches a Kinesis call — it is refused at subscription filter #3), so the cause belongs to `logs` and this issue is filed against `logs`.

RELATED OPEN ISSUES (none of them covers these causes): 20261025T014519Z-logs-cloudwatch-logs-vended-delivery-and-subscription-plumbing-is.md records, as its cause 4, that PutSubscriptionFilter against a Destination carrying NO access policy answers InvalidParameterException where AWS answers AccessDeniedException, and as its cause 5 that an unassumable roleArn is accepted — cause 1 below is the different defect that a logical-destination subscription WITH a destination policy and WITHOUT roleArn is refused outright. 20261023T113357Z-logs-cloudwatch-logs-startlivetail-and-getlogobject-answer-501-three.md records, inside its cause 5, the same fixed-message divergence for the check id `logs.put-subscription-filter-exceeds-quota-rejected`; it does not carry the check ids below and says nothing about the quota COUNT, which is the substantive half of cause 3.

=== Cause 1 of 3: PutSubscriptionFilter refuses a CloudWatch Logs logical-destination ARN when roleArn is omitted ===
AWS: Smithy (cloudwatchlogs) PutSubscriptionFilter requires logGroupName, filterName, filterPattern and destinationArn; `roleArn` is NOT required, and its own documentation states "The ARN of an IAM role that grants CloudWatch Logs permissions to deliver ingested log events to the destination stream. You don't need to provide the ARN when you are working with a logical destination for cross-account delivery." The operation's documentation lists "A logical destination created with PutDestination" as a supported destination. A logical destination already carries its own roleArn (supplied to PutDestination), so the recorded flow PutDestination(targetArn=<kinesis stream>, roleArn=<role>) -> PutDestinationPolicy(accessPolicy granting this account logs:PutSubscriptionFilter) -> PutSubscriptionFilter(destinationArn=<arn:aws:logs:...:destination:NAME>, no roleArn) is accepted with HTTP 200.
Emulator: that PutSubscriptionFilter is refused with HTTP 400 InvalidParameterException, message (example) 'destinationArn for vendor logs cannot be used without roleArn'. The emulator applies a roleArn requirement to an ARN class whose whole purpose is to supply the role itself, and additionally misclassifies a `destination:` ARN as a vended-logs ARN.
Why: cross-account / logical-destination log subscription is impossible against the emulator. A client following the documented PutDestination + PutDestinationPolicy + PutSubscriptionFilter sequence is hard-refused, and the entire end-to-end subscription-delivery path behind a logical destination can never be exercised.
Fix: the roleArn-requirement branch of the PutSubscriptionFilter handler in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/put_subscription_filter.rs — recognise an `arn:<partition>:logs:<region>:<account>:destination:<name>` destinationArn as a logical destination that supplies its own role, and only require roleArn for the direct Kinesis / Firehose target classes.
Traces: logs.e2e-log-group-subscription-destination-delivery-flow.

=== Cause 2 of 3: PutDestinationPolicy accepts an accessPolicy whose Principal is the wildcard "*" ===
AWS: Smithy (cloudwatchlogs) PutDestinationPolicy takes destinationName + accessPolicy (both @required) and models InvalidParameterException (400), OperationAbortedException (400) and ServiceUnavailableException (500). Recorded behavior: an accessPolicy statement whose Principal is the bare wildcard "*" is REFUSED with 400 InvalidParameterException; the recorded message, as an example, is "Error occurred while parsing accessPolicy. Please check if the accessPolicy has been constructed correctly using IAM grammar." The positive control in the same run — the identical policy with Principal {"AWS": "<account-id>"} — is accepted and round-trips verbatim through DescribeDestinations.
Emulator: the wildcard-principal call answers HTTP 200 with an empty body (content-length 2) and the policy is stored, so a cross-account log destination that ANY AWS principal may subscribe to is created silently.
Why: this is an over-permissive boundary on a cross-account sharing surface. A client (or an IaC template) that accidentally writes Principal "*" is told the destination policy is valid; against AWS the same call is a hard 400, so the emulator hides a real security misconfiguration and the client's InvalidParameterException handling never runs.
Fix: the accessPolicy parsing/validation in the PutDestinationPolicy handler in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/put_destination_policy.rs — reject a statement whose Principal is not a concrete principal, with 400 InvalidParameterException.
Traces: logs.put-destination-policy-wildcard-principal-rejected.

=== Cause 3 of 3: the per-log-group subscription-filter quota is 2 instead of 5, and LimitExceededException does not carry AWS's fixed message ===
AWS: the Smithy documentation for PutSubscriptionFilter says "Each log group can have up to two subscription filters associated with it", but that sentence is stale: recorded AWS behavior accepts FIVE attached subscription filters on one log group and refuses the SIXTH with 400 LimitExceededException (LimitExceededException is in the operation's modeled error set). The message is the fixed, request-independent text "Resource limit exceeded." — two independent checks in this suite assert that exact constant against recordings, and the limit counts ATTACHED filters, not calls (freeing one slot lets the previously refused filter in).
Emulator: the THIRD PutSubscriptionFilter on a log group is already refused with 400 LimitExceededException, message 'a log group can have up to 2 subscription filters associated with it'. The status and the error code are correct; the quota constant (2 vs 5) and the message rule are not.
Why: a client that fans one log group out to three, four or five destinations — a supported AWS configuration — is refused by the emulator, so any topology with more than two subscribers per group is untestable. Separately, a client or suite keyed on AWS's fixed LimitExceededException text does not match.
Fix: the per-log-group filter quota constant and the LimitExceededException construction in the PutSubscriptionFilter handler in services/service-com-amazonaws-cloudwatchlogs-logs-20140328/src/ops/put_subscription_filter.rs — raise the attached-filter limit to 5 and emit the fixed message "Resource limit exceeded."
Traces: logs.put-subscription-filter-then-describe, kinesis__logs.log-cwl-plumbing-sixth-subscription-filter-rejected-while-five-deliver.
