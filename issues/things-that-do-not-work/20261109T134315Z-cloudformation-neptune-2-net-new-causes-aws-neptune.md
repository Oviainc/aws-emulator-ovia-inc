# cloudformation__neptune: 2 net-new causes — AWS::Neptune::DBClusterParameterGroup/DBParameterGroup provision nothing in Neptune and never validate, and AWS::Neptune::GlobalCluster is rejected as an unrecognized resource type

> _Note: this issue was identified against the code base at commit `e0227173af353a179b5497df80ad91b1569c5be2`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Two independent root causes make the CloudFormation-driven Neptune parameter-group and global-cluster surfaces unusable. All three failing checks under this heading fail inside the emulator's own responses.

Cause 1 of 2: the AWS::Neptune::DBClusterParameterGroup and AWS::Neptune::DBParameterGroup resource provisioners are effectively no-ops — they report CREATE_COMPLETE without creating anything in Neptune and without letting Neptune validate the declared Parameters.
AWS: CloudFormation's handlers for these two types call Neptune CreateDBClusterParameterGroup / CreateDBParameterGroup and then ModifyDBClusterParameterGroup / ModifyDBParameterGroup for the declared Parameters map. Afterwards the groups are real Neptune resources (Smithy, com-amazonaws-neptune-amazonrdsv19): DescribeDBClusterParameterGroups(DBClusterParameterGroupName=<name>) returns HTTP 200 with exactly one DBClusterParameterGroup whose DBClusterParameterGroupName, DBParameterGroupFamily and Description equal the declared values and whose DBClusterParameterGroupArn is tag-readable via ListTagsForResource (the resource's own Tags plus the propagated stack tag); DescribeDBClusterParameters lists the declared parameter with the declared ParameterValue. The same holds for DescribeDBParameterGroups / DescribeDBParameters. Each resource's Ref is its group name. After DeleteStack both groups are gone and Neptune answers HTTP 404 with error code DBParameterGroupNotFound — fixed text "DBClusterParameterGroup not found: " + the requested cluster-group name, and "DBParameterGroup not found: " + the requested instance-group name (DescribeDBClusterParameterGroups / DescribeDBParameterGroups model DBParameterGroupNotFoundFault with awsQueryError code DBParameterGroupNotFound, httpError 404). Conversely, when a declared Parameters value lies outside the parameter's AllowedValues range, CloudFormation does NOT refuse at template validation: it accepts the stack, the parameter-group resource goes CREATE_FAILED, the stack ends ROLLBACK_COMPLETE, no group survives, and the CREATE_FAILED StackEvent's ResourceStatusReason is the registry-handler envelope Resource handler returned message: "<service message>" (RequestToken: <uuid>, HandlerErrorCode: InvalidRequest), where the Neptune message's fixed text is "Value: " + <the declared value> + " is outside of range: " + <the parameter's low>-<high> + " for parameter: " + <the parameter name> + " (Service: Neptune, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" — the value, range and parameter name taken from the request and the engine-default catalog, the request id and attempt count per-run.
Emulator: the happy-path stack reaches CREATE_COMPLETE, but the first read-back, neptune.DescribeDBClusterParameterGroups(DBClusterParameterGroupName=<declared name>), answers the NotFound refusal "An error occurred (DBParameterGroupNotFound) when calling the DescribeDBClusterParameterGroups operation: DBClusterParameterGroup not found: <name>" — the group CloudFormation claims to have created is absent from Neptune's state. The out-of-range stack, which AWS rolls back, also reaches CREATE_COMPLETE: the check reads the terminal status and gets 'CREATE_COMPLETE' where ROLLBACK_COMPLETE is required, so no CREATE_FAILED event and no handler reason exist. Both symptoms are the one missing behaviour: the provisioners never reach the Neptune control plane, so they neither record the groups nor surface Neptune's range refusal.
Why: a client that manages Neptune parameter groups through IaC gets a green stack and then cannot reference the groups — a later CreateDBCluster/CreateDBInstance that names them, or any Describe/tagging call, fails as if they were never declared. And an out-of-range parameter value is reported as a successful deployment, so a pipeline relying on CloudFormation to catch and roll back the bad value ships it silently and never sees the error AWS would have raised.
Fix: the CloudFormation service's AWS::Neptune::DBClusterParameterGroup and AWS::Neptune::DBParameterGroup resource provisioners — their create/update/delete paths must dispatch to the corresponding Neptune Create*/Modify*/Delete* handlers and write Neptune state, apply the declared Parameters, propagate the resource and stack tags onto the group ARNs, expose Ref as the group name, and translate a Neptune refusal into a CREATE_FAILED resource carrying the handler-error envelope with HandlerErrorCode InvalidRequest so the stack rolls back. Note: open issue 20261029T174713Z-neptune-parameter-group-and-event-subscription-handlers-skip.md reports gate gaps in the Neptune-side parameter-group handlers and does not cover the CloudFormation provisioners never calling them.
Traces: cloudformation__neptune.cfn-deploy-neptune-cluster-and-db-parameter-groups-round-trip-and-delete (errors on the post-CREATE_COMPLETE DescribeDBClusterParameterGroups) and cloudformation__neptune.cfn-deploy-neptune-cluster-parameter-group-invalid-value-rejected-and-rolled-back (mismatch: CREATE_COMPLETE where ROLLBACK_COMPLETE is required).

Cause 2 of 2: CloudFormation's template resource-type registry does not know AWS::Neptune::GlobalCluster, so CreateStack refuses the whole template at validation time.
AWS: CloudFormation publishes AWS::Neptune::GlobalCluster as a first-class resource type and provisions it through Neptune's CreateGlobalCluster. CreateStack therefore ACCEPTS a template declaring it and returns a StackId; the stack reaches CREATE_COMPLETE and the resource reads back through Neptune DescribeGlobalClusters(GlobalClusterIdentifier=<id>) as one GlobalCluster with GlobalClusterIdentifier = the declared identifier, Engine = "neptune", EngineVersion = the declared version, Status = "available" and a GlobalClusterArn whose ListTagsForResource carries the resource's Tags plus the propagated stack tag; the resource's Ref is the global cluster identifier. After DeleteStack, DescribeGlobalClusters answers error code GlobalClusterNotFoundFault with message "Global cluster '<identifier>' not found" — fixed text "Global cluster '" ... "' not found" around the requested identifier.
Emulator: CreateStack is refused synchronously with HTTP 400, error code ValidationError and message "Template format error: Unrecognized resource types: [AWS::Neptune::GlobalCluster]". The fixed text is "Template format error: Unrecognized resource types: [" ... "]"; the bracketed list is the set of type names taken from the submitted template. That code and message shape is what AWS emits for a genuinely unknown type — the defect is that this type is classified as unknown at all. Consequently no stack id is minted, no global cluster is ever created, and there is no CREATE_COMPLETE, no Outputs and no delete path to exercise.
Why: a client provisioning a Neptune global database through IaC cannot create the stack at all, and the ValidationError makes a correct template look malformed, so the caller debugs a template bug that does not exist. The entire global-cluster deploy and teardown surface is unreachable.
Fix: the cloudformation service crate's template resource-type registry consulted during CreateStack validation, plus the AWS::Neptune::GlobalCluster provisioner it must route to — create/delete against Neptune's global-cluster state, Ref = GlobalClusterIdentifier, tag propagation to the GlobalClusterArn. Note: open issue 20261029T174713Z-neptune-global-clusters-are-rejected-outright-so-the.md covers the Neptune-side global-cluster API and not the CloudFormation type registry; open issues 20261109T115129Z-cloudformation-neptune-graph-cloudformation-aws-neptunegraph-graph-and-aws-neptunegraph-graphsnapshot.md and 20261109T115129Z-cloudformation-ec2-neptune-graph-cloudformation-aws-neptunegraph-graph-and-aws-neptunegraph-privategraphendpoint.md report the same class of gap for the AWS::NeptuneGraph::* types and do not cover AWS::Neptune::GlobalCluster.
Traces: cloudformation__neptune.cfn-deploy-neptune-global-cluster-round-trip-and-delete (errors on its first CreateStack).

## Evidence
Cause 1 — check cloudformation__neptune.cfn-deploy-neptune-cluster-and-db-parameter-groups-round-trip-and-delete
Expected (AWS): after the stack declaring a ClusterParamGroup (AWS::Neptune::DBClusterParameterGroup) and a DbParamGroup (AWS::Neptune::DBParameterGroup) reaches CREATE_COMPLETE, neptune.DescribeDBClusterParameterGroups(DBClusterParameterGroupName=<Ref>) returns HTTP 200 with one group whose DBParameterGroupFamily and Description are the declared ones, its ARN tagged with the template and stack tags, and DescribeDBClusterParameters listing the declared parameter at the declared value; the same for the instance group. Only AFTER DeleteStack do both describes answer DBParameterGroupNotFound with "DBClusterParameterGroup not found: <name>" / "DBParameterGroup not found: <name>".
Actual (emulator): botocore.errorfactory.DBParameterGroupNotFoundFault: An error occurred (DBParameterGroupNotFound) when calling the DescribeDBClusterParameterGroups operation: DBClusterParameterGroup not found: <declared cluster-group name> — raised on the FIRST describe, immediately after CREATE_COMPLETE.

Cause 1 — check cloudformation__neptune.cfn-deploy-neptune-cluster-parameter-group-invalid-value-rejected-and-rolled-back
Expected (AWS): the stack whose DBClusterParameterGroup declares a Parameters value one above the parameter's AllowedValues maximum is accepted and then ends ROLLBACK_COMPLETE; the Cpg CREATE_FAILED event's handler reason is ("Value: <bad value> is outside of range: <lo>-<hi> for parameter: <parameter name> (Service: Neptune, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)", "InvalidRequest"); DescribeDBClusterParameterGroups(<bad name>) then answers DBParameterGroupNotFound.
Actual (emulator): AssertionError: stack '<stack>' ended 'CREATE_COMPLETE', expected ROLLBACK_COMPLETE — the out-of-range value is accepted, so no CREATE_FAILED event, no handler reason and no rollback exist.

Cause 2 — check cloudformation__neptune.cfn-deploy-neptune-global-cluster-round-trip-and-delete
Expected (AWS): CreateStack with Resources.GlobalCluster = {Type: AWS::Neptune::GlobalCluster, Properties: {GlobalClusterIdentifier: "<id>", Engine: "neptune", EngineVersion: "<a version whose DBEngineVersion reports SupportsGlobalDatabases>", Tags: [...]}} and Outputs.GlobalClusterId = {Ref: GlobalCluster} is ACCEPTED and returns a StackId; the stack reaches CREATE_COMPLETE, the Ref equals the declared identifier, and DescribeGlobalClusters reports Engine "neptune", the declared EngineVersion and Status "available".
Actual (emulator): botocore.exceptions.ClientError: An error occurred (ValidationError) when calling the CreateStack operation: Template format error: Unrecognized resource types: [AWS::Neptune::GlobalCluster] — refused synchronously, so no stack, no global cluster and no delete path exist.

## Steps to Reproduce
1. Boot the emulator and point botocore at it; nep = client("neptune"), cfn = client("cloudformation").
2. Cause 1 (happy path): CreateStack with Resources = ClusterParamGroup {Type: AWS::Neptune::DBClusterParameterGroup, Properties: {Name: "<cluster-group>", Family: "<neptune family>", Description: "<description>", Parameters: {<cluster parameter>: "<value>"}, Tags: [...]}} and DbParamGroup {Type: AWS::Neptune::DBParameterGroup, Properties: {Name: "<db-group>", Family: "<neptune family>", Description: "<description>", Parameters: {<instance parameter>: "<value>"}, Tags: [...]}}, with Outputs ClusterParamGroupName/DbParamGroupName as the Refs. Wait for CREATE_COMPLETE, then call nep.describe_db_cluster_parameter_groups(DBClusterParameterGroupName="<cluster-group>") -> observe DBParameterGroupNotFound instead of the one group.
3. Cause 1 (rejection path): read the parameter's AllowedValues range via nep.describe_engine_default_cluster_parameters(DBParameterGroupFamily="<neptune family>"), then CreateStack the same single-cluster-group template with that parameter set to (high + 1). Wait for a terminal status -> observe CREATE_COMPLETE instead of ROLLBACK_COMPLETE, and DescribeStackEvents showing no CREATE_FAILED row for the group's logical id.
4.
