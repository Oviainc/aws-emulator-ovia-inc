# CodePipeline: DeregisterWebhookWithThirdParty's non-GITHUB_HMAC refusal carries invented wording, PutActionRevision enforces no active-execution ceiling, and UpdateActionType succeeds for an AWS-owned action type (3 causes)

> _Note: this issue was identified against the code base at commit `6c3c71af8518aefa24fa94ce6987bd799f7db4df`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
PutActionRevision

## Description
Three distinct root causes found in the codepipeline behavioral sweep. All three must be closed before this issue is submitted. None of the three failing checks is marked ALREADY FILED or OWNED by the replay report. Related open issues, neither of which carries these check ids: 20261023T080113Z-codepipeline-control-plane-declaration-validation-stage-transition-state.md (its Cause 10 covers the active-execution ceiling reached through StartPipelineExecution only, not through PutActionRevision) and 20261025T120551Z-codepipeline-putapprovalresult-approvalalreadycompletedexception-carries-a-locally-invented-message.md (same class of defect as Cause 1 here, but for PutApprovalResult).

=== Cause 1 of 3: DeregisterWebhookWithThirdParty refuses a non-GITHUB_HMAC webhook with locally-invented message text ===
AWS: Smithy: DeregisterWebhookWithThirdParty.input.webhookName targets WebhookName (@length 1..100, @pattern ^[A-Za-z0-9.@\-_]+$); modeled errors are ValidationException and WebhookNotFoundException, both errorKind client, httpError 400. Recorded behavior: the operation only acts on a webhook actually connected to a supported third party, so a well-formed, registered webhook whose authentication is UNAUTHENTICATED is refused with error code ValidationException and the message template "Webhook <webhookName> must be configured with GITHUB_HMAC authentication type. Type is <authentication>." The fixed text is "Webhook ", " must be configured with GITHUB_HMAC authentication type. Type is " and the trailing "."; the variable parts are the webhookName taken from the request and the webhook's recorded authentication value taken from emulator state (UNAUTHENTICATED for this webhook). The emulator's handling of the other two rejection classes in this check is already correct (ValidationException with AWS's "1 validation error detected: Value at 'webhookName' failed to satisfy constraint: Member must satisfy regular expression pattern: [A-Za-z0-9.@\-_]+" for a malformed name, and WebhookNotFoundException with an empty message for an unregistered one) — only this third class diverges.
Emulator: the status (400) and the error code (ValidationException) are right, but the message is a different sentence that names the wrong rule: "Webhook <webhookName> does not target an action type of GitHub, and deregistering a webhook with a third party is supported only for those". It talks about the target action type instead of the webhook's authentication type, and it states no authentication value at all.
Why: the message is the only place the authentication type that blocked the call is reported, so a client (or a human reading a log) is told to change the target action type when the actual requirement is GITHUB_HMAC authentication. Tests and runbooks that match AWS's wording, and any code that parses the authentication type out of the message, break against the emulator while passing on AWS.
Fix: the error-message construction in the DeregisterWebhookWithThirdParty handler's validation path (the branch that rejects a webhook whose stored authentication is not GITHUB_HMAC) — it must render AWS's template from the request's webhookName and the webhook's stored authentication value rather than its own sentence.
Traces: codepipeline.deregister-webhook-validation-rejected.

=== Cause 2 of 3: PutActionRevision never enforces the pipeline's active-execution ceiling ===
AWS: Smithy: PutActionRevision.errors includes ConcurrentPipelineExecutionsLimitExceededException (errorKind client, httpError 400) alongside ActionNotFoundException, PipelineNotFoundException, StageNotFoundException and ValidationException; the output carries newRevision (boolean) and pipelineExecutionId. Supplying a genuinely new action revision triggers a pipeline execution, so once a PARALLEL-execution-mode V2 pipeline is at its active-execution ceiling (AWS General Reference, CodePipeline quotas: 50 active executions per pipeline, non-adjustable) the next new-revision PutActionRevision is refused with that error code at HTTP 400 and no further execution is created.
Emulator: every PutActionRevision succeeds. The check issued a positive-control revision plus 70 further new revisions against one PARALLEL/V2 pipeline and observed 71 distinct pipelineExecutionIds with no refusal: "never hit the concurrency ceiling after 71 executions; last error code=None". The emulator keeps no active-execution accounting on this path, so the modeled error is unreachable and the ceiling is unbounded.
Why: a client that handles the ceiling (back off, queue the revision, surface the quota to the operator) never exercises that path against the emulator, so a load-shedding or retry regression ships unnoticed; and the emulator reports an execution count a real pipeline could never reach, so downstream assertions about active executions are wrong.
Fix: active-execution accounting in the PutActionRevision handler and the shared pipeline-execution state it must consult before starting a revision-triggered execution — the same accounting the StartPipelineExecution path needs (Cause 10 of 20261023T080113Z-codepipeline-control-plane-declaration-validation-stage-transition-state.md); that issue's trace list does not contain this check id, so re-replay it here.
Traces: codepipeline.put-action-revision-concurrency-limit-rejected.

=== Cause 3 of 3: UpdateActionType succeeds for an AWS-owned action type instead of refusing it ===
AWS: Smithy: UpdateActionType.input is actionType (ActionTypeDeclaration, required) and its output is Unit; modeled errors are ActionTypeNotFoundException, RequestFailedException and ValidationException, all errorKind client, httpError 400. Recorded behavior: in a standard non-partner account UpdateActionType is unreachable for success — it refuses BOTH a never-created ThirdParty id AND a real, currently-listed AWS-owned id (Approval/AWS/Manual/1) with the same error code ActionTypeNotFoundException and the message template "An action type with owner=[<owner>], category=[<category>], provider=[<provider>] and version=[<version>] doesn't exist. To create an action type, contact the CodePipeline service team." The fixed text is that sentence; the variable parts are owner, category, provider and version taken from actionType.id in the request. The emulator already produces exactly this code and message for the nonexistent ThirdParty id in the same check, so only the AWS-owned id diverges.
Emulator: UpdateActionType with actionType.id = {category: Approval, owner: AWS, provider: Manual, version: 1} and a lambdaExecutorConfiguration executor returns success instead of HTTP 400 ActionTypeNotFoundException — "UpdateActionType unexpectedly succeeded for the real, AWS-owned Approval/AWS/Manual/1 action type". The handler evidently keys the refusal on "the id is not registered" and treats a listed AWS-owned id as updatable by the caller.
Why: this is an overly-permissive accept on a mutation AWS never allows: a caller can redefine a service-owned action type (here, pointing Approval/AWS/Manual/1 at an arbitrary Lambda executor), silently changing the behavior of every pipeline that declares it. A client written against AWS catches ActionTypeNotFoundException for this id; against the emulator the call appears to have taken effect, so the account-entitlement gate AWS enforces is invisible and negative tests pass there and fail here.
Fix: the ownership/entitlement gate in the UpdateActionType handler — the refusal must be driven by the caller not owning an AWS or ThirdParty provider registration, not by mere absence of the id from the action-type store, so a listed AWS-owned id is refused with the same ActionTypeNotFoundException code and message template as an absent one.
Traces: codepipeline.update-action-type-not-found.
