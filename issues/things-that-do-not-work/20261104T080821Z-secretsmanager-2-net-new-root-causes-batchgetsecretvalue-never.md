# secretsmanager: 2 net-new root causes — BatchGetSecretValue never evaluates a secret's resource policy per entry (denied plaintext returned), and aws:PrincipalArn is never published so a conditioned resource-policy Deny refuses the principal it exempts

=== Cause 1 of 2: BatchGetSecretValue authorizes once for the whole call and never per secret, so a secret whose resource policy explicitly denies reads is returned in full plaintext ===
AWS: Smithy: BatchGetSecretValue documentation — "If Secrets Manager encounters errors such as AccessDeniedException while attempting to retrieve any of the secrets, you can see the errors in Errors in the response"; output members SecretValues (SecretValuesType) and Errors (APIErrorListType, entries carrying SecretId/ErrorCode/Message). "Required permissions: secretsmanager:BatchGetSecretValue, and you must have secretsmanager:GetSecretValue for each secret." The request therefore degrades PER ENTRY, not per call: asked for N secrets of which one carries a resource-policy Deny on secretsmanager:GetSecretValue, the call is HTTP 200 carrying the readable plaintexts in SecretValues and exactly one Errors entry for the denied secret — SecretId = that secret as the request named it, ErrorCode = "AccessDeniedException", Message = AWS's explicit-deny sentence. That sentence's FIXED text is "User: <caller> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret> with an explicit deny in a resource-based policy"; its VARIABLE parts are the caller ARN, taken from the request's signing identity, and the secret ARN, taken from the requested SecretId — neither is a literal from any one run. Deleting the policy must restore N SecretValues with an empty Errors.
Emulator: the handler calls crate::state::authorization::authorize(..., ANY_RESOURCE) ONCE at the head of the call and then resolves every selection through entry_for, which consults only the stored secret's existence, its pending-deletion flag and its AWSCURRENT stage. No principal and no resource policy is evaluated for the individual secrets, and AccessDeniedException is not constructible on that path at all (entry_for emits only "ResourceNotFoundException" and "InvalidRequestException"; the decrypt loop adds only "DecryptionFailure"). Replay: with an explicit Deny attached to secret B of {A,B,C}, the batch returned all three ARNs in SecretValues (recorded: got the A, B and C ARNs, expected only A and C) and an empty Errors — a 200 handing out the plaintext of a secret whose resource policy denies reading it, while the single-secret GetSecretValue on the very same secret is correctly refused AccessDeniedException in the same check run.
Why: this is the over-permissive direction and the worst kind of it — secret material an explicit resource-policy Deny forbids is disclosed inside a success. A client that relies on the SecretValues/Errors partition to detect and report partially denied batches sees an all-success batch here and, against real AWS, suddenly finds one entry missing from SecretValues and an AccessDeniedException it never coded a branch for — after it has already consumed values the emulator told it were readable. It also makes a least-privilege review pass locally that production refuses.
Fix: per-entry authorization in the BatchGetSecretValue handler — services/service-com-amazonaws-secretsmanager-secretsmanager/src/ops/batch_get_secret_value.rs: entry_for owns the per-entry error channel and must run the same identity+resource-policy decision GetSecretValue now runs (crate::state::authorization, action secretsmanager:GetSecretValue against each selected secret's ARN) and turn its refusal into an APIErrorType entry with ErrorCode "AccessDeniedException" and the explicit-deny message, instead of failing the whole call or dropping the secret.
Traces: secretsmanager.batch-get-secret-value-returns-partial-results-with-a-per-secret-error-for-a-denied-secret.

=== Cause 2 of 2: aws:PrincipalArn is never published into the condition context, so a resource-policy Deny conditioned on StringNotEquals aws:PrincipalArn refuses the principal the condition exempts ===
AWS: recorded behavior only for the condition key itself (the Smithy model declares no condition keys; GetSecretValue's modeled errors are DecryptionFailure, InternalServiceError, InvalidParameterException, InvalidRequestException, ResourceNotFoundException, with the authorization refusal being the AWS-common AccessDeniedException). IAM's global key aws:PrincipalArn is populated for every signed request with the ARN of the IAM PRINCIPAL the request speaks for — for an assumed-role session that is the ROLE ARN (arn:aws:iam::<account>:role/<role-name>), not the session ARN (arn:aws:sts::<account>:assumed-role/<role-name>/<session>). So a resource policy of {"Effect":"Deny","Principal":"*","Action":"secretsmanager:GetSecretValue","Resource":"*","Condition":{"StringNotEquals":{"aws:PrincipalArn":"<app role ARN>"}}} must refuse every other identity — another identically granted role and the account's own owning principal — with AccessDeniedException and the explicit-deny sentence (fixed text "User: <principal> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret ARN> with an explicit deny in a resource-based policy"; variable parts: the refused principal's own ARN as the request signed it, and the addressed secret's ARN), while a session of the exempted app role KEEPS READING and gets HTTP 200 with the SecretString.
Emulator: the two refusals are produced correctly (the other role and the owner both get AccessDeniedException with the exact expected sentence), but the exempted role is refused too: replay recorded ('error', 'AccessDeniedException', 'User: arn:aws:sts::<account>:assumed-role/<app-role>/<session> is not authorized to perform: secretsmanager:GetSecretValue on resource: <secret ARN> with an explicit deny in a resource-based policy') where a 200 with the SecretString was required. Cause, from the code: services/service-com-amazonaws-secretsmanager-secretsmanager/src/state/condition_keys.rs publishes only the tag families and this service's own request-member keys (secretsmanager:SecretId, Name, Description, KmsKeyId, VersionId, VersionStage, RotationLambdaARN, BlockPublicPolicy, ForceDeleteWithoutRecovery, RecoveryWindowInDays, ForceOverwriteReplicaSecret, AddReplicaRegions) — no principal key at all. The module documents the consequence: "A key this context does not model is left out of both lists, where the shared evaluator's fail-closed reading of an undecided clause takes over — such a statement never grants and never stops denying." The StringNotEquals clause over aws:PrincipalArn is therefore undecided and the Deny applies to EVERY principal, including the one it names. (Hypothesis: a second, independent way to produce the same observation would be publishing the key with the assumed-role SESSION ARN rather than the role ARN — whichever the fix chooses, the exempted role's session must satisfy an equality against the IAM role ARN.)
Why: the over-restrictive direction, and it silently inverts a very common lock-down idiom. A caller who locks a secret to exactly one role and verifies the lock here concludes the application is broken: the application role is denied, so the "only this role may read" policy appears impossible to express. Worse, both the deny and the exemption read as working in the two negative probes, so the divergence looks like an application bug rather than an emulator gap. Any conditioned Deny over an unmodelled key behaves this way, so the fix must publish the principal keys, not special-case one statement.
Fix: the request condition context and the gate that hands it to the shared evaluator — services/service-com-amazonaws-secretsmanager-secretsmanager/src/state/condition_keys.rs (publish the global principal keys) together with services/service-com-amazonaws-secretsmanager-secretsmanager/src/state/authorization.rs, which already resolves the caller principal for the refusal message and is the one place that knows the role behind a session (it reads an identity through ::service_common::iam_role::assumed_role_session_role_name / user_name); aws:PrincipalArn must be populated from that resolved IAM entity ARN for every request, not only for resource-policy evaluation.
Traces: secretsmanager.resource-policy-deny-unless-principal-arn-locks-reads-to-one-role.

## Steps to Reproduce
Cause 1 (BatchGetSecretValue per-entry authorization):
1. CreateSecret three secrets A, B, C, each with a distinct SecretString.
2. BatchGetSecretValue(SecretIdList=[A,B,C]) -> 200, 3 SecretValues, Errors == [] (baseline; passes today).
3. PutResourcePolicy(SecretId=B, ResourcePolicy={"Version":"2012-10-17","Statement":[{"Effect":"Deny","Principal":{"AWS":"*"},"Action":["secretsmanager:GetSecretValue","secretsmanager:BatchGetSecretValue"],"Resource":"*"}]}).
4. GetSecretValue(SecretId=B) -> AccessDeniedException with the explicit-deny sentence (correct today; confirms the Deny is in force).
5. BatchGetSecretValue(SecretIdList=[A,B,C]) -> OBSERVE 200 with three SecretValues including B's plaintext and an empty Errors. AWS returns A and C in SecretValues plus one Errors entry {SecretId: B, ErrorCode: "AccessDeniedException", Message: "User: <caller> is not authorized to perform: secretsmanager:GetSecretValue on resource: <B ARN> with an explicit deny in a resource-based policy"}.
6. DeleteResourcePolicy(SecretId=B); repeat step 5 -> 3 SecretValues, empty Errors (positive control).

Cause 2 (aws:PrincipalArn in the condition context):
1. CreateSecret one secret with SecretString "locked-value".
2. CreateRole APP and CreateRole OTHER, both trusting arn:aws:iam::<account>:root for sts:AssumeRole, and PutRolePolicy on each allowing secretsmanager:GetSecretValue on that secret's ARN.
3. AssumeRole into each; both GetSecretValue -> 200 with "locked-value".
4. PutResourcePolicy(SecretId=<secret>, BlockPublicPolicy=True, ResourcePolicy={"Version":"2012-10-17","Statement":[{"Effect":"Deny","Principal":"*","Action":"secretsmanager:GetSecretValue","Resource":"*","Condition":{"StringNotEquals":{"aws:PrincipalArn":"<APP role ARN>"}}}]}).
5. GetSecretValue as OTHER -> AccessDeniedException + explicit-deny sentence (correct). As the account owner -> same (correct).
6. GetSecretValue as APP (the exempted principal) -> OBSERVE AccessDeniedException + explicit-deny sentence naming the APP session ARN. AWS returns 200 with SecretString "locked-value", because aws:PrincipalArn for that session is the APP ROLE ARN and the StringNotEquals clause therefore does not hold.
7. DeleteResourcePolicy; GetSecretValue as OTHER -> 200 again (positive control).
