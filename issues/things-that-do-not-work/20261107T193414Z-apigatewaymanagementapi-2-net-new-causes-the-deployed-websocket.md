# apigatewaymanagementapi: 2 net-new causes — the deployed WEBSOCKET stage still never yields a 101 upgrade (5 more checks), and a well-formed unknown ConnectionId is still refused 400 BadRequestException instead of 410 GoneException (2 more checks)

## Description
TWO net-new root causes on the apigatewaymanagementapi service token, clustered from the 7 apigatewaymanagementapi failures the replay marks neither ALREADY FILED nor OWNED (the other 21 are owned by existing issues). BOTH must be closed before this issue is submitted.

=== Cause 1 of 2: a deployed WEBSOCKET stage never completes an RFC 6455 upgrade, so no connection is ever minted and every live-connection contract of @connections is unobservable (5 checks) ===

AWS: recorded behavior only for the handshake itself — the Smithy model of apigatewaymanagementapi describes only the @connections control surface, not the socket. Recorded: a GET to a deployed WEBSOCKET stage's wss endpoint carrying `Connection: Upgrade`, `Upgrade: websocket`, `Sec-WebSocket-Key: <client nonce>` and `Sec-WebSocket-Version: 13` is answered `HTTP/1.1 101 Switching Protocols` with `Upgrade: websocket`, `Connection: Upgrade` and `Sec-WebSocket-Accept: <base64(sha1(key + GUID))>`; the gateway then mints a connectionId (base64 of 11 bytes), invokes the `$connect` route, and exposes that id to @connections. Smithy, for what the socket feeds: GetConnection GET /@connections/{ConnectionId} returns connectedAt/lastActiveAt (__timestampIso8601, date-time) and identity; PostToConnection POST /@connections/{ConnectionId} takes Data as an @httpPayload blob @length 0..131072 and answers 200; DeleteConnection DELETE /@connections/{ConnectionId} answers 204; all three declare GoneException (@httpError 410, memberless) for a connection that no longer exists.

Emulator: the handshake never succeeds. Every one of the five checks polls for a 101 for its whole 120 s budget and gets nothing back at all — `AssertionError: a 101 WebSocket upgrade against API <apiId> stage dev not met within 120.0s. Last result: None` (and, for the sibling apigatewayv2 checks against the same front door, a literal `HTTP/1.1 404 Not Found` with `x-amzn-errortype: UnknownService`). Because the socket never opens, no connectionId is ever registered, so the whole live half of @connections — a successful PostToConnection to a live id, 1000-code close on DeleteConnection, lastActiveAt advancing on traffic but not on reads, a cross-API live id being refused GoneException, and a >frame-size payload being fragmented across continuation frames — is dead code and reaches no verdict.

Why: a client built against AWS learns its own connectionId from the socket and then addresses it over @connections; on this emulator neither half exists, so a fan-out/presence application cannot be exercised at all and every refusal code it keys on (410 vs 400 vs 403) is unreachable. An emulator that answers 404/nothing to a correct RFC 6455 handshake also mis-teaches clients that the stage does not exist.

Fix: the emulator's front-door HTTP router for the execute-api data plane (the entry serving /_aws/execute-api/{apiId}/{stage}) must detect the Upgrade: websocket handshake, answer 101 with the computed Sec-WebSocket-Accept, and hand the hijacked connection to the apigatewayv2 WEBSOCKET data plane, which must mint a connectionId, run the $connect route and register it through the apigatewaymanagementapi connection-store seam (`register_connection` in that service's state module) so @connections can resolve it.

=== Cause 2 of 2: the @connections 400-vs-410 split is still keyed on whether THIS emulator minted the id, so a well-formed unknown ConnectionId is refused 400 BadRequestException and the connection-store miss (410 GoneException) is unreachable (2 checks) ===

AWS: the split is recorded behavior only — the model declares NO BadRequestException for this service; GetConnection/PostToConnection/DeleteConnection declare exactly ForbiddenException (403), GoneException (410), LimitExceededException (429) (+PayloadTooLargeException 413 on PostToConnection), and ConnectionId is an @httpLabel @required __string with no pattern or length. Recorded: a WELL-FORMED id of the shape API Gateway mints (base64 of 11 bytes, e.g. the checks' probe value) that no connection owns reaches the connection store and is refused HTTP 410, Error.Code GoneException, Error.Message "" (the shape has no members, so the message is empty). Only an id whose FORM is not one API Gateway mints (a single character, characters outside the base64 alphabet, unpadded base64, an over-long id) is refused HTTP 400, Error.Code BadRequestException, Error.Message "Invalid connectionId: <ConnectionId>" — fixed text "Invalid connectionId: " plus the ConnectionId exactly as the request sent it. The decision is a property of the submitted VALUE, never of the server's own mint log, so AWS answers 410 for a well-formed id it did not mint.

Emulator: every @connections call with the well-formed unknown probe id answers HTTP 400, Error.Code BadRequestException, Error.Message "Invalid connectionId: <the submitted id>" — the replay shows the readiness poll converging on `('BadRequestException', 'Invalid connectionId: <id>')` and `'BadRequestException'` for the whole 120 s budget instead of GoneException. The refusal is decided by an emulator-local set of ids it issued itself, and since no WebSocket upgrade ever completes (Cause 1) that set is permanently empty, so the GoneException branch is dead for every externally supplied id. Both checks use GoneException-for-an-unknown-id as their "the deployed stage's @connections route is serving" readiness condition, never reach it, and so never grade their actual subjects: PostToConnection's payload-size gate ordering AHEAD of id validation and lookup (over the 131072-byte ceiling AWS answers HTTP 413 with Error.Code "413", not GoneException and not BadRequestException), and the undeployed-stage refusal (ForbiddenException, HTTP 403, Error.Message "Forbidden", on all three operations, while the deployed stage of the same API answers 410).

Why: 410 GoneException is the documented "this peer went away" signal a fan-out application keys its prune-this-row branch on; 400 BadRequestException means "your id is malformed, retrying is pointless". Keying the split on the emulator's own mint log inverts that for exactly the cases clients hit in production — ids persisted in a table across a restart, ids minted by a sibling process, ids whose socket already closed — so prune logic never fires against the emulator and fires in production, and every contract gated behind reaching the store (payload ceiling ordering, the undeployed-stage 403) is unobservable.

Fix: the shared @connections ConnectionId validation and the refusal ordering in front of the three handlers (the issued-set test in the GetConnection/PostToConnection/DeleteConnection handlers and the helpers in this service's state module). Decide 400 BadRequestException from the FORM of the submitted ConnectionId alone, let any well-formed id fall through to the connection store whose miss is 410 GoneException with an empty message, and check the Data size before either.
