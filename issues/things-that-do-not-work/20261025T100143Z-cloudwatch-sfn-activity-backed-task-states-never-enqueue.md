# cloudwatch__sfn: activity-backed Task states never enqueue a task, so GetActivityTask hands out no token and the AWS/States ActivityArn series and redrive ledger are unobservable

> _Note: this issue was identified against the code base at commit `e9d80a3410239f9e9b1338b43cf9bb86ccbcdb95`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
GetActivityTask

## Description
One net-new root cause, grounded in two failing behavioral checks the replay report left unmarked (no ALREADY-FILED and no OWNED marker).

Cause 1 of 1 — a RUNNING execution whose Task state names an activity ARN never enqueues a task against that activity, so every GetActivityTask long-poll returns without a taskToken and no activity-worker scenario can proceed past its first claim.
Failing check ids: cloudwatch__sfn.metrics-states-stream-activity-metrics-attribute-worker-outcomes-to-the-activity-arn-series, cloudwatch__sfn.obs-sfn-1-redrive-to-succeeded-counts-once-and-second-redrive-rejected.

AWS: Smithy (services/service-com-amazonaws-sfn-awsstepfunctions/smithy-model/com-amazonaws-sfn-awsstepfunctions.json) models GetActivityTask with input {activityArn (required, @length 1..256), workerName (@length 1..80)} and output {taskToken (@length 1..2048, @sensitive), input (@length 0..1048576, @sensitive)}; its modeled errors are ActivityDoesNotExist, ActivityWorkerLimitExceeded, InvalidArn, KmsAccessDeniedException, KmsInvalidStateException, KmsThrottlingException — all HTTP 400. In AWS, as soon as an execution enters a Task state whose Resource is an activity ARN the task is enqueued on that activity, and the next long-poll returns a non-empty taskToken together with the state input; the worker then answers with SendTaskSuccess or SendTaskFailure. On top of that, these two checks grade behavior that is recorded behavior only for the metric part (the Smithy model does not describe AWS/States publication): (a) a worker that succeeds one task and fails another is accounted for in namespace AWS/States under Dimensions exactly [ActivityArn] as ActivitiesScheduled/ActivitiesStarted/ActivitiesSucceeded/ActivitiesFailed, while the owning state machine's own series under Dimensions exactly [StateMachineArn] carries ExecutionsStarted/ExecutionsSucceeded/ExecutionsFailed, and the activity counters do NOT appear under the state-machine dimension nor under a never-polled twin activity; (b) a FAILED Standard execution reports redriveStatus REDRIVABLE, RedriveExecution (Smithy: input {executionArn required, clientToken}, output {redriveDate required}, modeled errors ExecutionDoesNotExist, ExecutionLimitExceeded, ExecutionNotRedrivable, InvalidArn, ValidationException — all HTTP 400) re-runs the failed Task with the ORIGINAL execution input so the same execution ends SUCCEEDED with redriveCount 1, and a second RedriveExecution on the now-SUCCEEDED execution is refused with HTTP 400, error code ExecutionNotRedrivable, changing nothing in the ledger (ExecutionsStarted 1, ExecutionsFailed 1 not decremented, ExecutionsSucceeded 1, ExecutionsRedriven 1, RedrivenExecutionsSucceeded 1, RedrivenExecutionsFailed 0, ExecutionsAborted 0).

Emulator: both checks are killed by the harness with "Check timed out after 60.0s" while still inside their first activity claim — the first inside its GetActivityTask poll helper for the subject activity, the second inside _claim() immediately after StartExecution. No taskToken is ever produced, so SendTaskSuccess/SendTaskFailure, RedriveExecution, DescribeExecution's redriveStatus/redriveCount and every GetMetricStatistics read are never reached. The executions never leave RUNNING and no AWS/States datapoint under either the ActivityArn or the StateMachineArn dimension is ever written.

Why: a client implementing the first-class activity-worker pattern (CreateActivity -> Task on the activity ARN -> long-poll GetActivityTask -> SendTaskSuccess/SendTaskFailure) never receives work and gets no error telling it why; its executions hang in RUNNING forever. Operational tooling that watches AWS/States counters sees an empty namespace, so dashboards and alarms built against activity-level attribution silently read zero. And because the failure/redrive path is unreachable, redrive semantics (a redrive is not a new start, the earlier failure stays booked, a redrive of a terminal-SUCCEEDED execution is refused with ExecutionNotRedrivable) cannot be relied on by any emulator-based test.

Fix: the activity task scheduling path shared by the interpreter's Task-state handler and GetActivityTask's handler/state — entering a Task state whose Resource is an activity ARN must enqueue a task against that activity, and GetActivityTask must dequeue it and mint a token with the state input; then the SendTaskSuccess/SendTaskFailure resolution path, the RedriveExecution handler (redriveStatus/redriveCount on DescribeExecution, ExecutionNotRedrivable on a terminal-SUCCEEDED execution) and the AWS/States metric emission for the ActivityArn dimension family (ActivitiesScheduled/Started/Succeeded/Failed) and the redrive counters (ExecutionsRedriven, RedrivenExecutionsSucceeded/Failed).

## Steps to Reproduce
1. iam:CreateRole with a trust policy for states.amazonaws.com.
2. sfn:CreateActivity twice -> <subject_act>, <twin_act> (the twin is deliberately never polled).
3. sfn:CreateStateMachine (Standard) with definition {"StartAt":"Work","States":{"Work":{"Type":"Task","Resource":"<subject_act>","TimeoutSeconds":300,"End":true}}} and the role above.
4. sfn:StartExecution with input {"order":7} (and a second execution for the metrics check).
5. sfn:GetActivityTask(activityArn=<subject_act>, workerName="sim2real-worker") in a loop. Expected: a non-empty taskToken whose `input` is the posted execution input, within seconds. Observed: no taskToken for the whole window; the check is killed at the 60 s harness cap.
