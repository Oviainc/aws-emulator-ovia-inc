# scheduler delivery-failure handling: 5 causes — DeadLetterConfig never receives a failed event, Target.RoleArn is never authorized at invocation time, universal targets never issue their SDK call, UpdateSchedule accepts an unassumable role, and the past-EndDate refusal is misworded

> _Note: this issue was identified against the code base at commit `e2ad54ee7b8ee1b2faa65791f8cb738708e5249b`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateSchedule

## Description
This issue carries 5 root causes, all in the `scheduler` service. Each must be closed before this issue is submitted; each cause lists the failing check ids it is grounded in. None of these checks is marked ALREADY FILED or OWNED in the replay report. Related but NOT covering: 20261023T191008Z-scheduler-eventbridge-scheduler-never-fires-a-schedule-no-invocation.md (the dispatcher in general) and 20261108T032912Z-scheduler-5-net-new-behavioral-causes-three-refusal.md (whose Cause 3 is the reversed StartDate/EndDate message, a different branch from Cause 5 here) carry none of the check ids below.

=== Cause 1 of 5: Target.DeadLetterConfig.Arn never receives a failed event ===
Failing checks: scheduler.e2e-schedule-retry-then-dlq-delivery, scheduler.schedule-dead-letter-queue-receives-failed-invocation, scheduler.schedule-retry-policy-exhausted-lands-in-dlq-exactly-once, scheduler.scheduler-invocation-attempt-count-metric-counts-every-retry, scheduler.scheduler-retry-exhaustion-condition-reported-only-for-event-age-bound, scheduler.server-side-dead-letter-queue-receives-failed-event-payload, scheduler.server-side-retry-policy-exhaustion-triggers-dlq, scheduler.server-side-retry-policy-retries-on-target-failure
AWS: Smithy (com.amazonaws.scheduler) — Target.DeadLetterConfig -> DeadLetterConfig, member Arn @pattern ^arn:aws(-[a-z]+)?:sqs:[a-z0-9\-]+:\d{12}:[a-zA-Z0-9\-_]+$, @length 1..1600, documented as "An object that contains information about an Amazon SQS queue that EventBridge Scheduler uses as a dead-letter queue for your schedule. If specified, EventBridge Scheduler delivers failed events that could not be successfully delivered to a target to the queue." Target.RetryPolicy -> RetryPolicy with MaximumEventAgeInSeconds (@range 60..86400) "The maximum amount of time, in seconds, to continue to make retry attempts" and MaximumRetryAttempts (@range 0..185) "The maximum number of retry attempts to make before the request fails. Retry attempts with exponential backoff continue until either the maximum number of attempts is made or until the duration of the MaximumEventAgeInSeconds is reached." So an occurrence whose target call fails is retried with exponential backoff until the first of the two bounds is reached, and the event is then placed on the dead-letter queue — exactly once per occurrence. Recorded behavior: the dead-letter message describes the failed invocation and carries the retry-exhaustion condition that was hit (the attempt bound vs the event-age bound are reported distinctly).
Emulator: nothing is EVER written to the dead-letter queue, in eight independent checks across every way of making a delivery fail (a target that errors, a target that is denied, retry exhaustion by attempt count, retry exhaustion by event age). The checks poll for 170-300 s and receive zero messages.
Why: the dead-letter queue is the only channel through which a client can learn that a scheduled invocation failed — Scheduler returns nothing to the caller at occurrence time and the control plane keeps reporting State=ENABLED. With the DLQ silent, a schedule that fails every occurrence is indistinguishable from one that is working, so a client's alarms and retry-exhaustion dashboards never fire and failed work is lost without trace.
Fix: the occurrence/dispatch component of the scheduler crate (services/service-com-amazonaws-scheduler-awschronosservice/src/). On a failed target call it must retry per Target.RetryPolicy (both bounds, with backoff) and then SendMessage the failed-event payload to Target.DeadLetterConfig.Arn exactly once, recording which bound ended the retries.

=== Cause 2 of 5: Target.RoleArn is never authorized at invocation time, so delivery happens even when the role has no permission ===
Failing checks: scheduler.create-schedule-role-without-invoke-permission-denied, scheduler.e2e-schedule-missing-iam-permission-blocks-delivery-rejected, scheduler.server-side-schedule-invocation-uses-declared-role-arn
AWS: Smithy (com.amazonaws.scheduler) — Target.RoleArn is required, @pattern ^arn:aws(-[a-z]+)?:iam::\d{12}:role\/[\w+=,.@\/-]+$, "The Amazon Resource Name (ARN) of the IAM role that EventBridge Scheduler will use for this target when the schedule is invoked." Every occurrence is delivered AS that role, so when the role's policy does not permit the target action (e.g. sqs:SendMessage on the target queue) the target receives nothing and the occurrence is a failed event routed to DeadLetterConfig.Arn.
Emulator: delivery occurs regardless — the checks observe the target receiving the payload while the role has no permission, and the configured dead-letter queue receives nothing.
Why: Target.RoleArn is the authorization boundary of the whole data plane. An emulator that ignores it will accept and execute a schedule a real account would refuse, so a client validating least-privilege roles against the emulator ships a configuration that silently stops working in AWS (and conversely, a negative test asserting "no delivery without permission" cannot pass).
Fix: the dispatch component must evaluate the target call under Target.RoleArn before issuing it, and classify an authorization refusal as a delivery failure feeding Cause 1's path.

=== Cause 3 of 5: a universal target (arn:aws:scheduler:::aws-sdk:<service>:<operation>) never issues the SDK call ===
Failing checks: scheduler.scheduler-universal-target-invokes-the-aws-sdk-operation, scheduler.scheduler-universal-target-operation-name-case-rejected
AWS: Smithy (com.amazonaws.scheduler) — the Target shape documents that Scheduler "supports templated target that invoke common API operations, as well as universal targets that you can customize to invoke over 6,000 API operations across more than 270 services"; Target.Arn is required (@length 1..1600) and Target.Input (@length min 1) is "The text, or well-formed JSON, passed to the target". For a universal target the Input IS the request body, so a schedule with Target.Arn = arn:aws:scheduler:::aws-sdk:sqs:sendMessage and an Input of {QueueUrl, MessageBody, MessageAttributes} causes Scheduler to call sqs:SendMessage under Target.RoleArn: the MessageBody arrives byte-exact and the MessageAttributes map survives. The operation segment is the SDK's lowerCamelCase name; the capitalised form (sqs:SendMessage) is refused with ValidationException — the subject of the second check.
Emulator: nothing is ever delivered by a universal target. Both checks report the target queue empty after 300 s with 'Bodies seen: []', and the second therefore cannot reach its case-rejection subject at all.
Why: universal targets are how clients reach every operation Scheduler has no templated parameter block for. CreateSchedule returns 200 and GetSchedule round-trips the universal ARN, so the client sees a healthy ENABLED schedule whose work never runs, with nothing to observe.
Fix: the dispatch component must parse arn:aws:scheduler:::aws-sdk:<service>:<operation> (SDK service id, lowerCamelCase operation), issue that call with Target.Input as the request body under Target.RoleArn, and refuse a mis-cased operation segment with ValidationException at write time.

=== Cause 4 of 5: UpdateSchedule accepts a Target.RoleArn that Scheduler cannot assume, instead of refusing it ===
Failing check: scheduler.scheduler-update-target-role-to-an-unassumable-role-rejected
AWS: Target.RoleArn is required and must be assumable by Scheduler; the writing operations validate it by assuming it. UpdateSchedule with a Target.RoleArn naming a role that does not exist (or does not trust scheduler.amazonaws.com) is refused with HTTP 400 ValidationException whose Message is the fixed sentence 'The execution role you provide must allow AWS EventBridge Scheduler to assume the role.' — entirely fixed text, with no part taken from the request — and the stored Target.RoleArn is left unchanged, so the schedule keeps delivering with its previous role.
Emulator: the UpdateSchedule call SUCCEEDS (the check's helper reports 'the call was expected to fail but succeeded'), so the unassumable role is written into the record.
Why: this refusal is what stops a client from breaking a working schedule with a typo or a deleted role. On the emulator the update is accepted, the control plane reports a role that can never be assumed, and every subsequent occurrence must fail — but since Cause 1 keeps the DLQ silent and Cause 2 delivers anyway, the client has no signal at all. A client that relies on the refusal to gate a role change (and on the stored role being preserved) gets the opposite outcome.
Fix: UpdateSchedule's target validation (services/service-com-amazonaws-scheduler-awschronosservice/src/ops/update_schedule.rs, with the shared role check used by CreateSchedule) must verify the role is assumable by scheduler.amazonaws.com and otherwise answer 400 ValidationException with that exact sentence, leaving the stored record untouched.

=== Cause 5 of 5: CreateSchedule with a past EndDate and no StartDate is refused with the wrong message ===
Failing check: scheduler.events-scheduler-semantics-create-with-a-past-end-date-and-no-start-date-rejected
AWS: StartDate is "The date, in UTC, after which the schedule can begin invoking its target" and EndDate "The date, in UTC, before which the schedule can invoke its target"; both are plain modelled timestamps and both optional. When EndDate is already in the past and StartDate is omitted, the service compares EndDate against an IMPLICIT StartDate of now and refuses with HTTP 400 ValidationException whose Message is the fixed sentence 'The StartDate you specify must come before the EndDate.' — entirely fixed text, naming a StartDate the caller never sent. Nothing is stored (GetSchedule then answers 404 ResourceNotFoundException with 'Schedule <Name> does not exist.') and the schedule delivers nothing.
Emulator: the status and code are right (400 ValidationException) but the Message is 'EndDate must be in the future.' — a message form this service does not produce. It is a different refusal class from the reversed-pair message, so this is a distinct branch from Cause 3 of open issue 20261108T032912Z-scheduler-5-net-new-behavioral-causes-three-refusal.md, which covers the explicit StartDate > EndDate case.
Why: the message is the whole diagnostic payload of the refusal. AWS tells the caller the rule it violated in terms of the (implicit) StartDate, which is what makes the refusal comprehensible for a request that carried no StartDate at all; the emulator states a different rule ('must be in the future'), so a client or test matching AWS's wording sees an unrecognised rejection and an operator is told the wrong constraint.
Fix: the schedule-window validation in the schedule-definition module (the branch that fires when EndDate is in the past and StartDate is absent) must emit the shared START_DATE_BEFORE_END_DATE sentence rather than a separate past-EndDate message, from both writing handlers.
