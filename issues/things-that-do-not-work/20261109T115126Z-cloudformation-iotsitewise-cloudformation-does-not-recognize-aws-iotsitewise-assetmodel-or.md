# CloudFormation does not recognize AWS::IoTSiteWise::AssetModel or AWS::IoTSiteWise::Asset, so no SiteWise estate can be deployed or rejected by template

> _Note: this issue was identified against the code base at commit `e38416fc0970ac2ae0c65df6bda0d7aff4be2337`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Every CloudFormation template that declares an IoT SiteWise asset model or asset is refused at CreateStack as a template format error, so both the provisioning path and the template-rejection path into this service are unavailable. This issue bundles 2 causes; both must be closed. Related open issue 20261102T084333Z-iotsitewise-cloudformation-refuses-aws-iotsitewise-assetmodel-as-an-unrecognized.md records the same registry gap from a check filed under the iotsitewise heading (the windfarm e2e lifecycle); it does not cover either check below (neither was marked OWNED/ALREADY FILED by the replay), and it says nothing about AWS::IoTSiteWise::Asset or about the handler-failure/rollback path of cause 2.

Cause 1 of 2: AWS::IoTSiteWise::AssetModel and AWS::IoTSiteWise::Asset are not registered resource types, so a stack that provisions a model plus an asset on it cannot be created, read back, or deleted.
AWS: recorded behavior only — the resource type registry is a CloudFormation fact, not part of the iotsitewise Smithy model; the operations it must drive ARE modeled (Smithy: CreateAssetModel POST /asset-models code 202, output assetModelId/assetModelArn/assetModelStatus @required; CreateAsset; DeleteAssetModel DELETE /asset-models/{assetModelId} code 202; DescribeAssetModel/DescribeAsset). Real AWS accepts a CreateStack whose Resources declare {Type: AWS::IoTSiteWise::AssetModel} with AssetModelName and AssetModelProperties (here one Attribute property named Operator, DataType STRING, Attribute.DefaultValue) and {Type: AWS::IoTSiteWise::Asset} with AssetName and AssetModelId: !Ref AssetModel. The stack reaches CREATE_COMPLETE; Ref of each logical id resolves to the created assetModelId / assetId, GetAtt AssetModel.AssetModelArn and GetAtt Asset.AssetArn resolve to the resources' ARNs, DescribeAssetModel/DescribeAsset settle ACTIVE and agree with those outputs, ListAssetModels and ListAssets(assetModelId) list them once each, DescribeAssetProperty reads the attribute default back, and DeleteStack removes both so DescribeAsset answers ResourceNotFoundException 'Asset with ID <assetId> not found' and DescribeAssetModel answers ResourceNotFoundException 'Asset Model with ID <assetModelId> not found'.
Emulator: CreateStack is refused with HTTP 400 ValidationError and the message 'Template format error: Unrecognized resource types: [AWS::IoTSiteWise::AssetModel, AWS::IoTSiteWise::Asset]'. Fixed text of that message: 'Template format error: Unrecognized resource types: ['...']'; the variable part is the list of type names taken from the request template. The check therefore never gets past CreateStack and nothing downstream is exercised.
Why: a client provisions SiteWise through CDK/CloudFormation rather than hand-written API calls; its stack is refused outright, and the refusal blames the client's template ('template format error') instead of disclosing an unimplemented resource type, so the user has no way to diagnose it.
Fix: the CloudFormation crate's resource-type registry and its provisioner — register AWS::IoTSiteWise::AssetModel and AWS::IoTSiteWise::Asset, map their template properties (AssetModelName, AssetModelProperties incl. LogicalId/Name/DataType/Type.TypeName=Attribute with Attribute.DefaultValue; AssetName, AssetModelId) onto CreateAssetModel/CreateAsset, resolve Ref to the created id and GetAtt AssetModelArn/AssetArn to the ARN, and implement update and delete so stack deletion deletes both resources.
Traces: cloudformation__iotsitewise.cfn-deploy-iotsitewise-asset-model-and-asset.

Cause 2 of 2: a template whose asset-model property is invalid is also refused at CreateStack instead of being accepted and rolled back with the IoT SiteWise refusal forwarded as the resource's failure reason.
AWS: recorded behavior only for the registry/rollback mechanics; the underlying refusal is the modeled InvalidRequestException (Smithy: CreateAssetModel error InvalidRequestException, httpError 400, member message). A template declaring an Attribute property with DataType INTEGER and Attribute.DefaultValue 'not-a-number' is ACCEPTED by CreateStack; the AssetModel resource then fails, the stack ends ROLLBACK_COMPLETE, and the single CREATE_FAILED event for that logical id carries a resource-handler failure reason whose message is the forwarded service error 'Property Operator Attribute default value is not the expected type. (Service: IoTSiteWise, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)' with HandlerErrorCode 'InvalidRequest'. Fixed text: 'Property ', ' Attribute default value is not the expected type.' plus the '(Service: IoTSiteWise, Status Code: 400, ...)' suffix; variable parts: the property name from the template ('Operator' here) and the per-run request id / attempt count, which are masked by the check. No asset model of that name is left in ListAssetModels after the rollback, while an otherwise identical STRING-typed template deploys to CREATE_COMPLETE and settles ACTIVE.
Emulator: the same ValidationError 'Template format error: Unrecognized resource types: [AWS::IoTSiteWise::AssetModel]' at CreateStack — the positive control is refused before anything is created, so neither the ROLLBACK_COMPLETE path nor the forwarded handler reason exists.
Why: a client's CI relies on a bad template failing as a stack rollback with the service's own diagnosis in the stack events; here it gets a generic template-format rejection with no service diagnosis, and no rollback is ever observed, so cleanup-on-failure behaviour is untested and unimplemented.
Fix: the CloudFormation provisioner's resource-handler error path for the newly registered AWS::IoTSiteWise::AssetModel type — forward the IoTSiteWise InvalidRequestException as the resource's CREATE_FAILED ResourceStatusReason in resource-handler form with HandlerErrorCode InvalidRequest, and roll the stack back to ROLLBACK_COMPLETE leaving no asset model behind. The underlying synchronous DataType/DefaultValue validation in the iotsitewise CreateAssetModel handler is the subject of open issue 20261102T084333Z-iotsitewise-createassetmodel-updateassetmodel-perform-no-synchronous-property-variable-expression.md; this cause is about CloudFormation accepting the stack and surfacing that refusal.
Traces: cloudformation__iotsitewise.cfn-iotsitewise-asset-model-invalid-attribute-default-value-rejected.

1.
