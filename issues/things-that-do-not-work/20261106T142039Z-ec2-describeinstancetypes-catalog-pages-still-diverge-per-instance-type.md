## Description
This replay leaves 95 unowned DescribeInstanceTypes divergence clusters - one per probed instance-type page across the ec2-catalog-describe-instance-types-* fixtures (seen here in the a1-c9g and r9g-z1d pages) - and they all share one root cause: the emulator's instance-type catalog is emulator-authored, so per-type EBS, network, storage and capability attributes are computed from a formula instead of carried as AWS's data, and several modeled members are left out of the entry entirely. The open issue '20261030T063325Z-ec2-static-catalogs-diverge-from-aws-instance-type.md' describes this family and names a few pages, but it does not carry the replay keys for these clusters, so a fixer replaying that issue never exercises them; '20261029T200817Z-ec2-read-paths-omit-modeled-members-and-serve.md' likewise covers other steps only. This issue bundles 3 causes; all 3 must be closed, and the remaining clusters of the same family should be re-replayed with them.

Cause 1 of 3: on a metal/compute page, the per-type EBS-optimized figures, attachment limit, instance-store geometry and several network members do not match AWS and some modeled members are absent.
AWS: recorded behavior only - the catalog is service data, not a modeled constraint; the Smithy model only states the members exist (DescribeInstanceTypes -> InstanceTypeInfo: cpuBurstModel, ebsInfo.ebsOptimizedInfo.{baselineBandwidthInMbps,baselineIops,baselineThroughputInMBps,maximumBandwidthInMbps,maximumIops,maximumThroughputInMBps}, ebsInfo.maximumEbsAttachments, instanceStorageInfo.{disks.sizeInGB,totalSizeInGB}, networkInfo.{bandwidthWeightings,connectionTrackingConfiguration,defaultNetworkCardIndex,enaSrdSupported,flexibleEnaQueuesSupport,maximumNetworkCards,networkCards,...}). The recording carries AWS's concrete value for each of those members, per instance type, and carries the members that the emulator omits.
Emulator: for each type on the page the ebsOptimizedInfo baseline/maximum bandwidth, IOPS and throughput, maximumEbsAttachments, instanceStorageInfo disk size and total size differ from the recorded values, and cpuBurstModel, networkInfo.bandwidthWeightings, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.networkCards, phcSupport, processorInfo.supportedFeatures and rebootMigrationSupport are missing. HTTP status matches (200 expected, 200 observed) - the divergence is entirely in the body.
Why: callers size storage and network capacity, pick EBS-optimized baselines and gate features (ENA SRD, PHC, burst model, network cards) off this catalog. A client reading these fields plans against figures no real instance has, and code that reads an omitted member sees nothing at all rather than AWS's value.
Fix: the DescribeInstanceTypes handler's instance-type catalog data/derivation - entries must be seeded with AWS's per-type values and must include every modeled member, rather than deriving numbers in the serializer.
Traces: ec2-catalog-describe-instance-types-a1-c9g#task#31.

Cause 2 of 3: the same defect on the burstable t4g page, where the formula also produces the wrong burst/attachment story.
AWS: recorded behavior only; the recorded page carries each t4g.* type with cpuBurstModel present, its own ebsOptimizedInfo baseline/maximum numbers, its maximumEbsAttachments, and the networkInfo members listed in cause 1.
Emulator: cpuBurstModel, networkInfo.defaultNetworkCardIndex, networkInfo.enaSrdSupported, networkInfo.flexibleEnaQueuesSupport, networkInfo.maximumNetworkCards, networkInfo.networkCards, networkInfo.networkPerformance, networkInfo.secondaryNetworkSupported, networkInfo.trafficMirroringSupport, phcSupport, processorInfo.sustainedClockSpeedInGhz and rebootMigrationSupport are missing, and the ebsOptimizedInfo numbers and maximumEbsAttachments differ from AWS for every type on the page.
Why: as cause 1, for the burstable family - a client cannot even tell that a burstable type has a credit burst model, because the member is absent.
Fix: same component as cause 1.
Traces: ec2-catalog-describe-instance-types-r9g-z1d#task#7.

Cause 3 of 3: the same defect on the t8i page, which additionally reports the wrong EBS attachment-limit type and the wrong connection-tracking default.
AWS: recorded behavior only; the recorded page carries ebsInfo.attachmentLimitType, networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout and the per-type ebsOptimizedInfo numbers for each t8i.* type.
Emulator: ebsInfo.attachmentLimitType is reported as the catalog-wide default instead of the type's own value, networkInfo.connectionTrackingConfiguration.defaultTcpEstablishedTimeout is reported as the emulator's single global default rather than the type's recorded timeout, the ebsOptimizedInfo numbers and maximumEbsAttachments differ, and the same network/capability members as causes 1-2 are missing.
Why: a client that reasons about dedicated vs shared EBS attachment limits, or about idle-connection timeouts, gets one global answer for every instance type instead of the per-type answer AWS publishes.
Fix: same component as cause 1 (per-type data, including attachmentLimitType and connectionTrackingConfiguration, must come from the seeded catalog).
Traces: ec2-catalog-describe-instance-types-r9g-z1d#task#8.
