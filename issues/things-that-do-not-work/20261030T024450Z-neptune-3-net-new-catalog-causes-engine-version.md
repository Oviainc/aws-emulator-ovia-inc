# neptune: 3 net-new catalog causes — engine-version, event-category and orderable-option reports still diverge from the Neptune catalog

> _Note: this issue was identified against the code base at commit `d6aa252f09dfe86e7f4b30505c74249c49cdaee6`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
DescribeDBEngineVersions

## Description
The three read-only Neptune catalog operations all answer the expected HTTP 200, but the reference data in the body is still not the catalog the Neptune front door serves: the engine-version list does not contain the engine's release line at any index, the event-category report is rendered in a different order from the service's own, and the orderable-instance-option elements carry RDS-generic capability flags and omit modelled members. Replay of simparity-wire-aws-v1 reports these three clusters with an EMPTY owned_by and an EMPTY stub_path, so no open issue carries their replay keys. The closest prior work item, 20261029T174713Z-neptune-catalog-describes-serve-rds-wide-data-instead.md, is RESOLVED (it fixed the release-line structure, the ORDERABLE/licence-model coupling, the category SETS and the OrderableDBInstanceOptions list serialization, and declined the rest), so it does not cover what still diverges here. THIS ISSUE HAS 3 CAUSES — all three must be closed before submitting.

Cause 1 of 3: DescribeDBEngineVersions does not serve the Neptune engine-version catalog — no recorded DBEngineVersion element is present at its index. AWS: the operation is modelled with output shape com.amazonaws.neptune#DBEngineVersionMessage carrying DBEngineVersions (a list of com.amazonaws.neptune#DBEngineVersion) plus the pagination Marker (Smithy: DescribeDBEngineVersions paginated inputToken/outputToken=Marker, items=DBEngineVersions, pageSize=MaxRecords). Each DBEngineVersion models Engine, EngineVersion, DBParameterGroupFamily, DBEngineDescription, DBEngineVersionDescription, ValidUpgradeTarget (a list of upgrade targets), SupportsReadReplica and SupportsGlobalDatabases. An unfiltered DescribeDBEngineVersions against the Neptune front door enumerates every published release of the graph engine: each element names Engine 'neptune', its own EngineVersion, the DB parameter group family that release belongs to, a version description naming the product and that release, and a ValidUpgradeTarget chain of the releases it can be upgraded to (each target carrying EngineVersion, Description, AutoUpgrade and IsMajorVersionUpgrade), together with the per-release capability flags the model and its RDS-shared members publish (SupportsReadReplica, SupportsGlobalDatabases, SupportsCluster, SupportsParallelQuery, SupportsRDSProxy, SupportsBabelfish, SupportsCertificateRotationWithoutRestart, SupportsLimitlessDatabase, SupportsChangeDataCaptureStreams, SupportsDataGroups, SupportedEngineModes, SupportedCACertificateIdentifiers, MajorEngineVersion/MinorEngineVersion). Emulator: every element the recording reports at DBEngineVersions.DBEngineVersion[0] through [28] is reported 'missing' at that index — the list the emulator serves does not present the engine's releases, their family grouping, their per-release capability flags or their ValidUpgradeTarget chains in the identity and ordering the service publishes. Why: a client that discovers which engine versions exist before creating a cluster, or that computes an upgrade path by walking ValidUpgradeTarget from the version it is on, reads a catalog whose entries are not the ones the service offers, so it either finds no version to create with or plans an upgrade to a release the service will refuse. Fix: the engine-version reference catalog read by the DescribeDBEngineVersions handler, and that handler's assembly of the DBEngineVersions list (release set, family grouping, per-release flag values and the upgrade-target chain). Traces: neptune-catalog-describe-db-engine-versions#task#1.

Cause 2 of 3: DescribeEventCategories renders EventCategoriesMapList, and each entry's EventCategories list, in a different order from the service's own report. AWS: the operation's output shape com.amazonaws.neptune#EventCategoriesMessage carries EventCategoriesMapList, a list of com.amazonaws.neptune#EventCategoriesMap, each pairing SourceType with that source type's EventCategories list. Recorded behavior only for the ORDER: the recording returns the source-type entries in the service's own sequence (position 0 is the db-snapshot entry, position 2 the db-instance entry, position 5 the db-cluster entry), and each entry's EventCategories list in the service's own sequence (the db-proxy entry reports creation, configuration change, deletion, failure in that order). Neither the model nor AWS documentation states a sort rule, so the requirement is the service's published sequence, not an alphabetical one. Emulator: the same source types and the same category sets are served in a re-sorted sequence — position 0 is the db-instance entry, position 2 the db-parameter-group entry, position 5 the db-cluster-snapshot entry, and the db-proxy entry's categories come back alphabetised as configuration change, creation, deletion, failure; 9 of the 11 EventCategoriesMap positions diverge ([0], [1], [2], [4], [5], [7], [8], [9], [10]). Why: a client that indexes this report positionally, or that renders/compares it as an ordered list (a console-style listing, a cached diff of the category catalog, or a test that pins the first entry), reads a different source type than the service reports at that position. Fix: the ordering applied when the DescribeEventCategories handler emits its event-category catalog — the source-type entry order and the per-entry category order must be the catalog's published order, not a sort imposed by the serializer. Traces: neptune-catalog-describe-event-categories#task#1.

Cause 3 of 3: DescribeOrderableDBInstanceOption elements carry RDS-generic capability values and omit modelled members, so the per-element capability report contradicts the engine. AWS: com.amazonaws.neptune#OrderableDBInstanceOption models MultiAZCapable, ReadReplicaCapable, SupportsEnhancedMonitoring, SupportsIAMDatabaseAuthentication, SupportsPerformanceInsights, SupportsGlobalDatabases, SupportedNetworkTypes, AvailabilityZones, Vpc, StorageType, SupportsStorageEncryption and SupportsIops; the model documents SupportsPerformanceInsights as '(Not supported by Neptune)' and StorageType as 'Not applicable. In Neptune the storage type is managed at the DB Cluster level.' The recording's elements accordingly report MultiAZCapable false, ReadReplicaCapable false, SupportsEnhancedMonitoring false, SupportsPerformanceInsights false and SupportsIAMDatabaseAuthentication true, and carry SupportsGlobalDatabases, SupportsClusters, SupportedNetworkTypes, SupportsHttpEndpoint, SupportsOptimizedReads, SupportsOptimizedWrites, SupportsKerberosAuthentication, SupportsStorageThroughput, SupportsAdditionalStorageVolumes, SupportsDedicatedLogVolume, RequiresCustomProcessorFeatures, AvailableProcessorFeatures, SupportedActivityStreamModes and OutpostCapable, with the AvailabilityZones list covering every zone in which the class is orderable. Emulator: each element inverts the engine-specific flags to the RDS-generic defaults — MultiAZCapable 'true', ReadReplicaCapable 'true', SupportsEnhancedMonitoring 'true' and SupportsPerformanceInsights 'true' where the engine reports false, and SupportsIAMDatabaseAuthentication 'false' where the engine reports true — omits the modelled SupportsGlobalDatabases, SupportedNetworkTypes, SupportsClusters, SupportsHttpEndpoint, SupportsOptimizedReads, SupportsOptimizedWrites, SupportsKerberosAuthentication, SupportsAdditionalStorageVolumes, SupportsDedicatedLogVolume, RequiresCustomProcessorFeatures and AvailableProcessorFeatures entirely, emits a SupportsStorageAutoscaling member the recording does not carry, and reports a shorter AvailabilityZones list than the zone set in which the class is actually orderable. Why: a client that pre-flights a CreateDBInstance against this report provisions on a false premise — it offers Multi-AZ and read replicas the engine cannot give it, enables Performance Insights the engine does not support, believes IAM database authentication is unavailable when it is the engine's own auth mode, and cannot discover global-database support or the network types (SupportsGlobalDatabases/SupportedNetworkTypes are simply absent), so the subsequent create is refused or silently placed in the wrong zone. Fix: the orderable-options reference catalog read by the DescribeOrderableDBInstanceOptions handler and that handler's projection of OrderableDBInstanceOption — the capability flags must be the engine's, and every modelled member must be emitted. Traces: neptune-catalog-describe-orderable-db-instance-options#task#1.
