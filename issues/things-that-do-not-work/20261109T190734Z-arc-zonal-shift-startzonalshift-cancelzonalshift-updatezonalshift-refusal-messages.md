# arc-zonal-shift: StartZonalShift/CancelZonalShift/UpdateZonalShift refusal messages are emulator-invented prose instead of AWS's fixed wording (5 causes)

> _Note: this issue was identified against the code base at commit `fdb8a4e953f01d6c4e0b3bc9b573d323716eabbc`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
StartZonalShift

## Description
Five net-new root causes in arc-zonal-shift's zonal-shift refusal paths, found by replaying the behavioral suite simparity-behavioral-aws-v1. THIS BUNDLE HAS 5 CAUSES; ALL FIVE must be closed before submitting. In every one of them the HTTP status and the error code are already correct (409 ConflictException / 400 ValidationException) and, where the check inspects it, the ConflictException `reason` is correct too; the sole divergence is the error MESSAGE, which the emulator composes as its own descriptive prose (interpolating the shift id, the resource ARN or the rejected value) instead of the fixed sentence AWS answers for that refusal class. An error message is a requirement, so each of these is a defect.

Not already covered: the replay report marks none of these six checks as ALREADY FILED or OWNED. Related but distinct open issues: 20261102T015300Z-arc-zonal-shift-cancelzonalshift-validationexception-for-a-pattern.md (CancelZonalShift.zonalShiftId @pattern message) and 20261109T145139Z-arc-zonal-shift-validationexception-messages-interpolate-the-rejected.md (the same value-interpolation fault on ListZonalShifts.maxResults, ListAutoshifts.status and UpdateAutoshiftObserverNotificationStatus.status) — neither names the StartZonalShift.expiresIn path of Cause 5, and neither touches the ConflictException messages of Causes 1-3 or the awayFrom validation of Cause 4. 20261029T193235Z-arc-zonal-shift-accessdenied-message-on-unknown-shift.md carries the AccessDenied/enum-order causes, not these.

Cause 1 of 5 — CancelZonalShift on a shift that is already CANCELED answers the wrong ConflictException message. AWS: Smithy (services/service-com-amazonaws-arczonalshift-percdataplane/smithy-model/com-amazonaws-arczonalshift-percdataplane.json): CancelZonalShift is DELETE /zonalshifts/{zonalShiftId} (code 200) and models ConflictException (errorKind client, httpError 409) whose members are message (@required), reason (@required, ConflictExceptionReason, which includes ZonalShiftStatusNotActive) and zonalShiftId. Recorded behavior only for the message text: cancelling an already-CANCELED shift is refused with 409 ConflictException and the message "You can't update this zonal shift because it's no longer active". That message class is entirely FIXED text — it has no variable parts at all: no shift id, no resource ARN, no status token. Emulator: correct code ConflictException, but message 'zonal shift <shiftId> is CANCELED and can no longer be canceled' — invented prose that interpolates the shift id and the current status (the literal zs-0000000001 in the replay output is this run's generated id filling the emulator's own template; the defect is the template, not that id). Why: a client or contract test pinned to AWS's wording for this refusal — and any UI or log pipeline matching on it — never sees the sentence AWS emits, so the refusal is unrecognizable even though status and code are right. Fix: the CancelZonalShift handler's status precondition (the not-ACTIVE branch) in the arc-zonal-shift service crate, which must emit the fixed sentence rather than formatting one from state. Traces: arc-zonal-shift.cancel-zonal-shift-already-canceled-rejected.

Cause 2 of 5 — UpdateZonalShift on a CANCELED shift answers the wrong ConflictException message. AWS: Smithy: UpdateZonalShift is PATCH /zonalshifts/{zonalShiftId} (code 200), models ConflictException (client, 409) with reason ZonalShiftStatusNotActive available. Recorded behavior only for the text: updating a shift that is no longer active is refused with 409 ConflictException and the same wholly-fixed message "You can't update this zonal shift because it's no longer active" (no variable parts). Emulator: message 'zonal shift <shiftId> is CANCELED and can no longer be updated' — again invented prose with the shift id and status spliced in. Why: as Cause 1; additionally, because AWS uses ONE sentence for both the cancel and the update precondition, a client that matches that single string on either operation misses both. Fix: the UpdateZonalShift handler's status precondition branch; share the one fixed message with Cause 1 instead of per-operation prose. Traces: arc-zonal-shift.update-zonal-shift-after-cancel-rejected.

Cause 3 of 5 — StartZonalShift refusing a second shift for a resource that already has an ACTIVE one answers the wrong ConflictException message. AWS: Smithy: StartZonalShift is POST /zonalshifts (code 201) with required input {resourceIdentifier, awayFrom, expiresIn, comment} and models ConflictException (client, 409) whose reason enum includes ZonalShiftAlreadyExists and SimultaneousZonalShiftsConflict. Recorded behavior only for the text: the refusal carries the fixed sentence "There's already an active zonal shift for that resource." — all fixed text, including the trailing period, with NO variable parts (no shift id, no ARN). Emulator: code ConflictException and reason ZonalShiftAlreadyExists are correct, but the message is 'zonal shift <shiftId> is already active for resource <resourceArn>' — the emulator's own template filled from the existing shift's id and the request's resourceIdentifier. The same wrong message is answered to all four losing racers when five StartZonalShift calls race for one resource+AZ (the one-winner invariant itself holds). Why: a client distinguishing "already shifted" from other conflicts by AWS's documented sentence cannot recognize it, and the emulator additionally leaks internal state (the other shift's id) into a message AWS keeps value-free. Fix: the StartZonalShift handler's duplicate/active-shift conflict branch in the arc-zonal-shift service crate. Traces: arc-zonal-shift.start-zonal-shift-duplicate-active-conflict-rejected, arc-zonal-shift.concurrent-start-zonal-shift-exactly-one-wins.

Cause 4 of 5 — StartZonalShift with an awayFrom that is not one of the resource's Availability Zones answers the wrong ValidationException message. AWS: Smithy: StartZonalShift.awayFrom is @required targeting AvailabilityZone (@length max 20) and the operation models ValidationException (client, httpError 400) with members message (@required) and reason (@required). Recorded behavior only for the text: an awayFrom that is not an AZ the resource is deployed in is refused with 400 ValidationException and the fixed message "Invalid availability zone." — wholly fixed text, no variable parts (the rejected zone name and the resource ARN do NOT appear). Emulator: correct code ValidationException, but message 'awayFrom <value> is not an Availability Zone that resource <resourceArn> is deployed in' — invented prose interpolating the rejected awayFrom and the resource ARN from the request. Why: the refusal is correct in status and code but unmatchable by a client pinned to AWS's wording; message-based error classification in SDK wrappers and runbooks breaks. Fix: the StartZonalShift handler's awayFrom/AZ-membership validation branch. Traces: arc-zonal-shift.start-zonal-shift-invalid-az-rejected.

Cause 5 of 5 — the shared ValidationException formatter interpolates the rejected value on the StartZonalShift.expiresIn @pattern path, which AWS leaves value-free. AWS: Smithy: StartZonalShift.expiresIn is @required, @length min 2 max 5, @pattern ^([1-9][0-9]*)(m|h)$; ValidationException is client/400. Recorded behavior only for the message composition: a value that satisfies the length but not the pattern is refused with 400 ValidationException and "1 validation error detected: Value at 'expiresIn' failed to satisfy constraint: Member must satisfy regular expression pattern: ([1-9][0-9]*)(m|h)". Fixed text of this class: "1 validation error detected: Value at '", "' failed to satisfy constraint: Member must satisfy regular expression pattern: "; variable parts: the member path taken from the request (here expiresIn) and the pattern taken from the model (anchors stripped) — and NO quoted rejected value. Emulator: same status, code, member path and pattern, but it prefixes the segment "Value '<rejected value>' at '" (replay output: "Value '10d' at 'expiresIn' ..."; the literal 10d is the check's own input filling the emulator's template, not part of the requirement). Why: identical to the already-filed value-interpolation causes — a message AWS never emits, plus the caller's rejected input echoed back where AWS keeps it out. Fix: the shared arc-zonal-shift input-validation message formatter in the centralized deserialize->validate step, @pattern path for a body member. This is a NEW path for that formatter: 20261109T145139Z-arc-zonal-shift-validationexception-messages-interpolate-the-rejected.md claims only ListZonalShifts.maxResults, ListAutoshifts.status and UpdateAutoshiftObserverNotificationStatus.status, and 20261102T015300Z claims only CancelZonalShift.zonalShiftId — per the coordination note in those issues the formatter must decide per operation/member/constraint, so add this path value-free rather than flipping a service-wide switch. Traces: arc-zonal-shift.start-zonal-shift-invalid-expires-in-format-rejected.
