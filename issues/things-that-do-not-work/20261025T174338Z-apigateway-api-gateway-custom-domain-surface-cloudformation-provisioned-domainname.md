# API Gateway custom-domain surface: CloudFormation-provisioned DomainName/BasePathMapping are control-plane no-ops, and CreateBasePathMapping + UpdateDomainName answer 501 NotImplemented instead of their modeled BadRequestException refusals (3 causes)

> _Note: this issue was identified against the code base at commit `3fffece81be5f9cdcba63f22f8252b41b774e64d`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateBasePathMapping

## Description
Three net-new root causes on the API Gateway (REST, v1) custom-domain surface. This surface only became reachable now that `acm ImportCertificate` and `apigateway CreateDomainName` answer (the fixed issue 20261023T125454Z-apigateway-createdomainname-stub.md), so these are the next layer down. A fixer must close ALL THREE before submitting.

Cause 1 of 3: a CloudFormation stack containing AWS::ApiGateway::DomainName and AWS::ApiGateway::BasePathMapping reaches CREATE_COMPLETE, but neither resource is created in API Gateway's own control plane.
AWS: Smithy (com.amazonaws.apigateway#GetDomainName): GET /domainnames/{domainName}, success 200 returning DomainName with `domainNameStatus` (enum DomainNameStatus) and `regionalDomainName`/`regionalHostedZoneId` for a REGIONAL endpoint; NotFoundException is modeled at HTTP 404 only for a domain that does not exist. GetBasePathMapping (GET /domainnames/{domainName}/basepathmappings/{basePath}, 200 -> BasePathMapping{basePath,restApiId,stage}) resolves a mapping the stack created. CloudFormation only reports CREATE_COMPLETE for a resource it actually created, so after the waiter returns, the templated domain is addressable through the API Gateway API and its REGIONAL domain converges to domainNameStatus=AVAILABLE. Recorded behavior for the deletion half: once the stack is deleted, GetDomainName answers 404 BadRequest-class NotFoundException with the fixed message "Invalid domain name identifier specified" (no variable parts).
Emulator: cloudformation.CreateStack + the stack_create_complete waiter succeed and the stack's Outputs resolve (RestApiId/StageName come back), but the very first apigateway.GetDomainName(domainName=<the templated DomainName>) answers HTTP 404 Error.Code=NotFoundException, Message="Invalid domain name identifier specified" — i.e. the DomainName resource was never materialised. The BasePathMapping the template declares is therefore absent too, and the stack's reported success is a lie.
Why: a client that provisions a custom domain by template gets CREATE_COMPLETE and then cannot find, poll, map or route the domain through the API Gateway API at all; readiness polling on domainNameStatus fails immediately, and tear-down assertions cannot distinguish "never created" from "correctly deleted". Infrastructure-as-code over API Gateway custom domains is unusable and silently so.
Fix: the CloudFormation resource providers for AWS::ApiGateway::DomainName and AWS::ApiGateway::BasePathMapping (services/service-com-amazonaws-cloudformation-cloudformation), which must drive the apigateway CreateDomainName/CreateBasePathMapping state rather than only recording the logical resource. Related open issue that does NOT carry these replay keys: 20261023T125454Z-apigateway-cloudformation-provisioned-api-gateway-resources-are-unaddressable-through.md (same family for RestApi/Stage/Authorizer/UsagePlan); 20261023T151100Z-apigateway-api-gateway-putrestapi-overwrite-imports-paths-but-no.md lists these two check ids but under its ACM ImportCertificate cause, which no longer refuses the call.
Traces: apigateway.deploy-custom-domain-cfn-mapping-active, apigateway.deploy-domain-name-basepathmapping-cfn-resolves.

Cause 2 of 3: CreateBasePathMapping answers HTTP 501 NotImplemented, so the restApiId-existence refusal AWS emits never happens.
AWS: Smithy (com.amazonaws.apigateway#CreateBasePathMapping): POST /domainnames/{domainName}/basepathmappings, success 201 returning BasePathMapping; modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), LimitExceededException(429), TooManyRequestsException(429), UnauthorizedException(401). Recorded behavior: with the domain present and the referenced REST API absent (or already deleted), the call is refused BadRequestException with the fixed message "Invalid REST API identifier specified" — all fixed text, no values interpolated from the request — and no mapping is left behind under that domain (GetBasePathMappings returns an empty items list). The same call against a real, deployed restApiId+stage succeeds 201 and GetBasePathMapping then reports that restApiId and stage.
Emulator: the call answers HTTP 501 Error.Code=NotImplemented, Message="operation CreateBasePathMapping is scaffolded but not implemented in this emulator", for every input — both the unknown-restApiId refusal and the positive mapping.
Why: a client cannot map any base path onto a custom domain, and a client testing its error handling sees NotImplemented (a server-side 501, normally retried or surfaced as an outage) where AWS gives a deterministic 400 it must not retry. The negative-effect guarantee (a refused create leaves no mapping) is unobservable.
Fix: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/create_base_path_mapping.rs — implement the handler, validate restApiId/stage existence against the REST API state, and return BadRequestException("Invalid REST API identifier specified") rather than the scaffold 501. Related: the auto-filed scaffold-stub issue for CreateBasePathMapping names the same file but does not carry these two check ids or the required refusal message.
Traces: apigateway.create-base-path-mapping-unknown-restapi-returns-badrequest, apigateway.delete-rest-api-racing-base-path-mapping-leaves-orphaned-mapping.

Cause 3 of 3: UpdateDomainName answers HTTP 501 NotImplemented, so an out-of-enum securityPolicy patch is not refused.
AWS: Smithy (com.amazonaws.apigateway#UpdateDomainName): PATCH /domainnames/{domainName} with patchOperations, success 200 returning DomainName whose `securityPolicy` targets the SecurityPolicy enum; modeled errors BadRequestException(400), ConflictException(409), NotFoundException(404), LimitExceededException(429), TooManyRequestsException(429), UnauthorizedException(401). Recorded behavior: a patch {op: replace, path: /securityPolicy, value: <not a SecurityPolicy member>} is refused BadRequestException with the fixed message "Invalid security policy specified" (fixed text only), and the domain's existing securityPolicy is left unchanged, so a subsequent GetDomainName still reports the value it was created with.
Emulator: the call answers HTTP 501 Error.Code=NotImplemented, Message="operation UpdateDomainName is scaffolded but not implemented in this emulator".
Why: no property of an existing custom domain can be changed at all, and a client that relies on the 400 to validate operator input instead sees a 501 it will treat as a transient server fault; the "rejected patch leaves state untouched" guarantee cannot be relied on.
Fix: services/service-com-amazonaws-apigateway-backplanecontrolservice/src/ops/update_domain_name.rs — implement patchOperations application, validate /securityPolicy against the SecurityPolicy enum and refuse with BadRequestException("Invalid security policy specified") without mutating stored state. Related: the auto-filed scaffold-stub issue for UpdateDomainName names the same file but does not carry this check id or the required refusal message.
Traces: apigateway.update-domain-name-invalid-security-policy-bad-request.
