# ec2__ecs__servicediscovery: an EC2 instance launched from the ECS-optimized AMI with ECS_CLUSTER user data never auto-registers as a container instance, so every ECS-on-EC2 scenario stalls before its subject

> _Note: this issue was identified against the code base at commit `4443a2ba0353c6ce642ed6cfa5c5308f0d2c2053`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
ListContainerInstances

## Description
Cause 1 of 1: the emulator never turns an EC2 instance launched from the ECS-optimized AMI into an ECS container instance, so ListContainerInstances for the cluster named in the instance's user data stays empty forever and both ECS-on-EC2 checks burn their whole budget in that wait. Failing check ids: ec2__ecs__servicediscovery.ecs-on-ec2-places-a-task-that-ecs-auto-registers-in-cloud-map, ec2__ecs__servicediscovery.ecs-run-task-is-blocked-by-insufficient-memory-on-the-only-container-instance.

  AWS: when an instance is launched with the ECS-optimized AMI (resolved from the public SSM parameter /aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id), an instance profile carrying AmazonEC2ContainerServiceforEC2Role, and user data writing `ECS_CLUSTER=<cluster>` into /etc/ecs/ecs.config, the on-host ECS agent calls RegisterContainerInstance itself. Within tens of seconds (the recordings measured 25-50 s for this half of the chain) ecs ListContainerInstances(cluster=<cluster>) returns exactly one containerInstanceArn, and DescribeContainerInstances on it reports status `ACTIVE` with `agentConnected: true` and a `registeredResources` list whose `MEMORY` integerValue is the host's registrable memory (for t3.micro, a value strictly between the 128 MiB and 8192 MiB the second check's two task definitions ask for). Smithy: ecs ListContainerInstances is readonly and returns `containerInstanceArns` (StringList) with only ClusterNotFoundException/InvalidParameterException/ClientException/AccessDeniedException/ServerException modeled — an empty list for a live, correctly-configured host is a successful 200 that reports no capacity, not a modeled refusal; DescribeContainerInstances returns `containerInstances`/`failures`. The registration being driven by the host agent rather than by the client is recorded behavior only (no client call appears in the recording between RunInstances and the first non-empty ListContainerInstances).

  Emulator: RunInstances succeeds and the instance exists (the recorded run got i-00000000000000001, a per-run id), the VPC/subnet/IGW, the IAM role and instance profile, and the SSM public-parameter AMI lookup all succeed, but ListContainerInstances(cluster=<cluster>) returns an empty `containerInstanceArns` list on every poll and never changes. The first check fails with `TimeoutError: instance <instance-id> registered into cluster <cluster-name> as a container instance: the run budget ended first; not graded` raised from the ListContainerInstances poll at line 330 of its check (the instance id and cluster name are per-run values; the never-satisfied condition is the divergence). The second check runs the same helper and ends `Error: Check timed out after 180.0s`, never reaching its RunTask assertions.

  Why: a client that provisions ECS capacity the way AWS documents — plain RunInstances on the ECS-optimized AMI with ECS_CLUSTER user data, no Auto Scaling group and no capacity provider — gets a cluster that reports zero capacity forever. Nothing downstream is reachable: launchType=EC2 RunTask has no instance to place on, so a right-sized task definition cannot be placed, the ECS-driven Cloud Map auto-registration of a task's SRV/A record never happens, and the negative contract the second check exists for (an oversized definition must return HTTP 200 with `tasks: []` and exactly one `failures` entry whose `reason` is the structured code `RESOURCE:MEMORY` and whose `arn` is the SHORT container-instance ARN form, without the cluster segment) cannot be distinguished from the same emptiness an empty cluster produces. Client code waiting on ListContainerInstances or DescribeContainerInstances(agentConnected) hangs rather than failing.

  Fix: the ECS-on-EC2 capacity path — whatever models the on-host ECS agent for an emulator-launched instance must detect an instance whose AMI is the ECS-optimized image and whose user data sets ECS_CLUSTER, and drive the ECS RegisterContainerInstance handler and its container-instance state (the ECS crate's container-instance state and register/list/describe ops) so the instance appears ACTIVE with agentConnected true and a registeredResources MEMORY/CPU set derived from its instance type. The open issue 20261107T080429Z-ecs-2-net-new-causes-no-aws-signed.md covers the DIFFERENT, client-driven path (a caller obtaining a signed instance identity document via SSM Run Command and calling RegisterContainerInstance itself) under service `ecs` and carries neither of these replay keys; this cause is the agent-driven auto-registration that needs no client call at all.

  Traces: ec2__ecs__servicediscovery.ecs-on-ec2-places-a-task-that-ecs-auto-registers-in-cloud-map (ListContainerInstances poll, line 330 of the check, _ec2_capacity), ec2__ecs__servicediscovery.ecs-run-task-is-blocked-by-insufficient-memory-on-the-only-container-instance (same _ec2_capacity helper, 180 s check timeout).

## Evidence
Expected (AWS): after RunInstances with ImageId = the value of SSM /aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id, InstanceType t3.micro, an instance profile holding AmazonEC2ContainerServiceforEC2Role, and UserData `#!/bin/bash\necho ECS_CLUSTER=<cluster> >> /etc/ecs/ecs.config`, ecs ListContainerInstances(cluster=<cluster>) returns one containerInstanceArn within ~25-50 s, and DescribeContainerInstances on it returns status=ACTIVE, agentConnected=true, and registeredResources containing MEMORY with an integerValue strictly between 128 and 8192 for t3.micro.

Actual (emulator): ListContainerInstances(cluster=<cluster>) returns `{'containerInstanceArns': []}` on every poll for the full 420 s/180 s budget. Check 1: `TimeoutError: instance i-00000000000000001 registered into cluster sim2real-behav-ecs-cl-<suffix> as a container instance: the run budget ended first; not graded` (raised at check line 53 from the poll started at line 330; the instance id and the cluster name/suffix are per-run values). Check 2: `Error: Check timed out after 180.0s`, so its RunTask assertions — `failures[0].reason == 'RESOURCE:MEMORY'`, `failures[0].arn` in the short container-instance form, `tasks == []`, and ListTasks showing only the control task — are never evaluated.

Both checks succeed on every preceding call (DescribeInstanceTypeOfferings, CreateVpc + vpc_available waiter, ModifyVpcAttribute, CreateSubnet, CreateInternetGateway/AttachInternetGateway/CreateRoute, IAM CreateRole/AttachRolePolicy/CreateInstanceProfile/AddRoleToInstanceProfile, SSM GetParameter, EC2 RunInstances, ECS CreateCluster and RegisterTaskDefinition), which isolates the divergence to the container-instance registration step.

## Steps to Reproduce
1. `ec2 create-vpc` + a public subnet with an internet gateway and a default route; enable DNS support and DNS hostnames on the VPC.
2. `iam create-role` trusting ec2.amazonaws.com, `iam attach-role-policy --policy-arn arn:aws:iam::aws:policy/service-role/AmazonEC2ContainerServiceforEC2Role`, `iam create-instance-profile`, `iam add-role-to-instance-profile`.
3. `ecs create-cluster --cluster-name <cluster>`.
4. `ssm get-parameter --name /aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id` and use its value as ImageId.
5. `ec2 run-instances --image-id <that ami> --instance-type t3.micro --subnet-id <subnet> --iam-instance-profile Name=<profile> --user-data '#!/bin/bash\necho ECS_CLUSTER=<cluster> >> /etc/ecs/ecs.config'`.
6. Poll `ecs list-container-instances --cluster <cluster>`: on AWS one ARN appears within ~25-50 s; on the emulator it stays `[]` indefinitely. Then `ecs describe-container-instances` on that ARN and expect status ACTIVE, agentConnected true, registeredResources MEMORY set.
7. With that capacity present, `ecs run-task --cluster <cluster> --task-definition <family asking 128 MiB> --launch-type EC2` (expect one task placed on that instance) and `ecs run-task --cluster <cluster> --task-definition <family asking 8192 MiB> --launch-type EC2` (expect HTTP 200, tasks [], one failure with reason RESOURCE:MEMORY and the short container-instance arn).
