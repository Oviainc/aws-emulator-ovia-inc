# cloudformation__ec2__vpc-lattice: AWS::VpcLattice::ResourceGateway, ::ResourceConfiguration, ::ServiceNetworkResourceAssociation and ::ServiceNetworkVpcAssociation are refused as unrecognized resource types, so no VPC Lattice resource-gateway estate can be deployed

> _Note: this issue was identified against the code base at commit `22941ee6d43df66d29bcadd7a62b7906e5868e84`. If you are an issue fixer working on this, the code base you are currently working in can have drifted, so you might need to trace the issue back to the current code base._

## Operation
CreateStack

## Description
Cause 1 of 1: CloudFormation's template resource-type registry does not carry the AWS::VpcLattice::ResourceGateway, AWS::VpcLattice::ResourceConfiguration, AWS::VpcLattice::ServiceNetworkResourceAssociation or AWS::VpcLattice::ServiceNetworkVpcAssociation resource types, so CreateStack refuses at template-format validation any stack that declares one. Failing check ids: cloudformation__ec2__vpc-lattice.deploy-vpclattice-gateway-configuration-and-associations-round-trip-and-delete, cloudformation__ec2__vpc-lattice.deploy-vpclattice-resource-configuration-invalid-port-range-rejected-and-rolled-back.

AWS: AWS CloudFormation registers all four types (documented at https://docs.aws.amazon.com/AWSCloudFormation/latest/TemplateReference/AWS_VpcLattice.html, e.g. aws-resource-vpclattice-resourceconfiguration.html), so CreateStack ACCEPTS a template declaring them and answers 200 with a StackId; provisioning or refusal is then decided by each type's registry handler DURING the stack operation, not by template-format validation. Smithy (services/service-com-amazonaws-cloudformation-cloudformation/smithy-model/com-amazonaws-cloudformation-cloudformation.json): CreateStack input TemplateBody (@length min 1), output StackId; the only modeled errors are AlreadyExistsException, InsufficientCapabilitiesException, LimitExceededException and TokenAlreadyExistsException — none of which is this refusal. The 'Template format error: Unrecognized resource types: [...]' ValidationError is recorded behavior only: HTTP 400, Code ValidationError, message fixed text 'Template format error: Unrecognized resource types: [' ... ']' with the comma-separated list of the template's genuinely unregistered type names as its variable part; AWS raises it only for type names it does not register, which excludes these four. Downstream of acceptance the recordings show: (a) a VPC + subnet + security group + ResourceGateway + ResourceConfiguration + ServiceNetworkResourceAssociation + ServiceNetworkVpcAssociation stack reaches CREATE_COMPLETE; Ref of the ResourceGateway and of the ResourceConfiguration each equal that resource's Arn; every Ref/GetAtt id agrees with VPC Lattice's own ListServiceNetworks/ListResourceGateways/ListResourceConfigurations/ListServiceNetworkResourceAssociations/ListServiceNetworkVpcAssociations; GetResourceGateway reads vpcId, subnetIds, securityGroupIds and status ACTIVE as declared; GetResourceConfiguration reads type SINGLE, the declared portRanges and resourceConfigurationDefinition {'ipResource': {'ipAddress': <ip>}} and status ACTIVE; both associations read ACTIVE and name their parents; every VPC Lattice and EC2 resource carries the template Tags plus aws:cloudformation:stack-name/logical-id/stack-id; an UpdateStack dropping only the associations deletes each (GetServiceNetworkVpcAssociation then answers ResourceNotFoundException 'Association <id> cannot be found.' and GetServiceNetworkResourceAssociation 'Service Network Resource Association not found: <id>') while the service network, configuration and VPC still answer; after delete_stack GetResourceConfiguration answers 'Resource Configuration not found: <id>', GetResourceGateway 'Resource not found: <id>' and GetServiceNetwork 'ServiceNetwork <id> cannot be found.'; (b) a ResourceConfiguration whose PortRanges entry has FromPort greater than ToPort is refused by the VPC Lattice handler, NOT by early validation, driving the stack to ROLLBACK_COMPLETE with a CREATE_FAILED ResourceStatusReason of the form 'Resource handler returned message: "<from>-<to> is not a valid port range (Service: VpcLattice, Status Code: 400, Request ID: <id>) (SDK Attempt Count: <n>)" (RequestToken: <token>, HandlerErrorCode: InvalidRequest)' — fixed text ' is not a valid port range' plus the envelope, with the port-range string taken from the request and request id/token/attempt count per-run — the failed ResourceConfiguration carries NO PhysicalResourceId, the already-created ResourceGateway and VPC are rolled back in order (Vpc CREATE_COMPLETE, ResourceGateway CREATE_COMPLETE, ResourceConfiguration CREATE_FAILED, ResourceGateway DELETE_COMPLETE, Vpc DELETE_COMPLETE), and afterwards GetResourceGateway answers 'Resource not found: <rgw-id>' and EC2 DescribeVpcs answers InvalidVpcID.NotFound "The vpc ID '<vpc-id>' does not exist".

Emulator: CreateStack is refused outright with HTTP 400 ValidationError. The round-trip check gets 'Template format error: Unrecognized resource types: [AWS::VpcLattice::ResourceGateway, AWS::VpcLattice::ResourceConfiguration, AWS::VpcLattice::ServiceNetworkResourceAssociation, AWS::VpcLattice::ServiceNetworkVpcAssociation]'; the port-range check gets '...: [AWS::VpcLattice::ResourceGateway, AWS::VpcLattice::ResourceConfiguration]'. AWS::EC2::VPC, ::Subnet, ::SecurityGroup and AWS::VpcLattice::ServiceNetwork are absent from both lists, so they are registered and the gap is exactly the four VPC Lattice types above. Because the call raises at CreateStack, no stack is created and every downstream assertion of both checks is unreachable.

Why: a client that provisions VPC Lattice resource gateways, resource configurations or service-network associations declaratively cannot deploy at all against the emulator. The refusal arrives as a template-format ValidationError at submit time, which a client reads as 'my template is malformed' and will neither retry nor poll, instead of as a stack operation whose outcome it can observe. The emulator also cannot reproduce AWS's rejection-and-rollback path for an invalid port range, which must surface as a resource-handler CREATE_FAILED reason with HandlerErrorCode InvalidRequest and a rollback of the already-created VPC and gateway, not as an up-front template error.

Fix: CloudFormation's template resource-type registry and the VPC Lattice resource-type handlers it dispatches to. Register the four types so template-format validation accepts them, and implement their create/update/delete handlers against VPC Lattice state so Ref equals each resource's ARN, GetAtt Id/Arn/Status agree with VPC Lattice's reads, template and aws:cloudformation:* tags propagate, VPC Lattice's port-range refusal surfaces as a handler CREATE_FAILED reason that rolls the stack back without leaving a PhysicalResourceId, and stack delete/association-dropping updates remove exactly the right resources.

Traces: cloudformation__ec2__vpc-lattice.deploy-vpclattice-gateway-configuration-and-associations-round-trip-and-delete (all four types refused), cloudformation__ec2__vpc-lattice.deploy-vpclattice-resource-configuration-invalid-port-range-rejected-and-rolled-back (ResourceGateway + ResourceConfiguration refused).

## Steps to Reproduce
1. Point a boto3/botocore cloudformation client at the emulator.
2. Submit a template declaring an EC2 VPC/subnet/security group plus a VPC Lattice resource gateway and resource configuration:
   cf.create_stack(StackName='t1', TemplateBody=json.dumps({'AWSTemplateFormatVersion':'2010-09-09','Resources':{
     'Vpc':{'Type':'AWS::EC2::VPC','Properties':{'CidrBlock':'10.121.0.0/16'}},
     'Subnet':{'Type':'AWS::EC2::Subnet','Properties':{'VpcId':{'Ref':'Vpc'},'CidrBlock':'10.121.0.0/24','AvailabilityZone':'<az>'}},
     'Sg':{'Type':'AWS::EC2::SecurityGroup','Properties':{'GroupDescription':'sg','VpcId':{'Ref':'Vpc'}}},
     'ResourceGateway':{'Type':'AWS::VpcLattice::ResourceGateway','Properties':{'Name':'rg1','VpcIdentifier':{'Ref':'Vpc'},'SubnetIds':[{'Ref':'Subnet'}],'SecurityGroupIds':[{'Ref':'Sg'}]}},
     'ResourceConfiguration':{'Type':'AWS::VpcLattice::ResourceConfiguration','Properties':{'Name':'rc1','ResourceConfigurationType':'SINGLE','ResourceGatewayId':{'Fn::GetAtt':['ResourceGateway','Id']},'ResourceConfigurationDefinition':{'IpResource':'10.121.0.50'},'PortRanges':['443']}}}}))
   Observe HTTP 400 ValidationError 'Template format error: Unrecognized resource types: [AWS::VpcLattice::ResourceGateway, AWS::VpcLattice::ResourceConfiguration]' instead of a 200 with a StackId.
3. Add an AWS::VpcLattice::ServiceNetwork plus ::ServiceNetworkResourceAssociation and ::ServiceNetworkVpcAssociation and resubmit: the refusal lists the four VPC Lattice types while ::ServiceNetwork and the EC2 types are accepted.
4. Change PortRanges to ['100-50'] and resubmit: AWS would accept the template and roll the stack back with the handler reason above; the emulator refuses at CreateStack instead.
5. Replay both behavioral checks listed in Issue-Trace-Ids; both abort at their first create_stack call.
